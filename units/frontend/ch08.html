CHAPTER 08

Cascade, specificity and the box model

CSS has a reputation for being unpredictable, which is untrue: it is entirely deterministic and the algorithm is short. This chapter is that algorithm — how one value is chosen from many competing declarations — followed by the box every element occupies, the units you size it in, and custom properties, which turn CSS from a list of declarations into something you can program.

Part 3 CSS·Reading time 55 minutes·Demos cascade resolver, unit calculator·Prerequisites Chapters 3–4

1How a value is chosen

Six sort criteria, applied strictly in order. The first one that produces a difference decides, and nothing later matters.

Several declarations often target the same property on the same element. The cascade sorts them and picks one. It is a tie-break chain: compare on criterion 1, and only if they are equal move to criterion 2.

#CriterionDetail
1Origin and importanceWhere the style came from, combined with whether it is !important. Table below.
2ContextStyles from outside a shadow tree beat styles from inside it — Chapter 20.
3Element-attached stylesA style attribute beats any selector of the same origin and importance.
4Cascade layerLater layers beat earlier ones. Unlayered styles beat all layers. Reversed for !important. Section 3.
5SpecificityThe three-number score in section 2.
6Order of appearanceThe last matching declaration in source order wins. This is the final tie-break and it never fails.

Origin and importance, in full

Note the inversion: for !important declarations the whole precedence order flips, so an important user-agent style outranks an important author style. That is not an accident — it exists so a user's own stylesheet can force a larger font that your site cannot override.

RankOriginNotes
1User-agent !importantHighest of all. Very few of these exist.
2User !importantThe reader's own stylesheet or browser accessibility setting. Deliberately unbeatable by you.
3Author !importantYour stylesheet, with !important.
4AnimationsA running CSS animation's current value.
5Author normalYour stylesheet. Where you live.
6User normalThe reader's preferences.
7User-agent normalThe browser's defaults — margins on <p>, blue underlined links.
8TransitionsA running transition beats everything while it runs, which is why a transitioning value briefly ignores your rules.
The mental model that fixes most confusion

"My rule isn't applying" almost always means one of three things: another declaration wins on this chain; your selector does not actually match the element; or the property is not inherited and you set it on the wrong node. Open the Elements panel, look at the Styles pane, and find your rule struck through — the browser will show you exactly which declaration beat it.

2Specificity

Three numbers, counted from the selector. Not a single score — compared left to right.

Specificity is written (A, B, C):

A — identifiers
Every #id in the selector.
B — classes, attributes and pseudo-classes
.class, [attr], [attr="v"], :hover, :nth-child(), :focus-visible.
C — types and pseudo-elements
Element names such as div, and ::before, ::marker, ::placeholder.

Comparison is column by column, left to right, and it is not base-10 arithmetic. (1,0,0) beats (0,99,0): a single id outranks any number of classes. The universal selector * and the combinators >, +, ~ and descendant space contribute nothing.

The !important problem

!important is not a strength modifier on a declaration — it moves the declaration into a different origin bucket, above everything normal. The consequences are practical:

  • Once one !important exists, beating it requires another !important with higher specificity, and you have started an arms race with no ceiling.
  • It is genuinely correct in exactly two places: overriding a third-party stylesheet you cannot edit, and utility classes that are meant to be final (some utility frameworks offer this as an option).
  • Cascade layers, in the next section, solve almost every other case that people reach for !important to fix.
Keeping specificity flat on purpose

Two modern tools make it easy. :where() zeroes out specificity, so :where(.prose) a { … } can be overridden by a plain .link class anywhere. And cascade layers let you win by position rather than by adding classes. Between them, there is very little reason for any selector in new code to exceed (0,2,0).

3Cascade layers

The feature that ends specificity wars, by making order the thing you control instead.

@layer creates named buckets that are sorted before specificity is even considered. A (0,0,1) rule in a later layer beats a (1,2,0) rule in an earlier one. That inverts the usual dynamic: instead of escalating selectors, you declare an intent about precedence once, at the top of your stylesheet.

Declare the order first, populate later CSS
/* One line that decides everything. Later layers win. */
@layer reset, vendor, base, layout, components, utilities;

@layer vendor {
  @import url("some-library.css") layer(vendor);
  /* Even its #id .class .class rules now sit below your base layer. */
}

@layer components {
  .card { padding: 1rem; }
}

@layer utilities {
  .p-0 { padding: 0; }   /* wins over .card without !important */
}

/* Anything NOT in a layer beats every layer. Useful for a page-level
   override; dangerous if it happens by accident. */
.p-0 { padding: 0; }
Unlayered wins
Styles outside any layer sit above all layers. Treat that as an escape hatch, not a default — a codebase where half the rules are unlayered has layers in name only.
!important reverses layer order
An important declaration in the earliest layer beats an important declaration in a later one. This is deliberate: it lets a reset layer make a genuinely non-negotiable rule.
Nested layers
@layer components.forms { … } sorts within the parent layer. Useful for a design system with internal ordering.
revert-layer
Rolls a property back to whatever the previous layer said. The precise tool for "undo the component style, keep the base".
Layer order is fixed by first mention
Declaring the order in one statement at the top of the entry stylesheet is the whole technique — otherwise the order depends on import order, which is exactly the fragility you were escaping.

4Inheritance and the global keywords

Some properties flow down the tree, most do not, and five keywords let you say what should happen when nothing matched.

If no declaration wins for a property on an element, the browser falls back: inherited properties take the parent's computed value; the rest take their initial value from the specification.

InheritedNot inherited
color, font-*, line-height, letter-spacing, word-spacing, text-align, text-indent, text-transform, white-space, visibility, cursor, list-style-*, direction, and all custom properties display, width, height, margin, padding, border, background, position, float, overflow, z-index, opacity, transform, flex, grid-*

The pattern: things about text inherit, things about boxes do not. That heuristic is right nearly every time.

KeywordSets the property to
inheritThe parent's computed value, whether or not the property normally inherits.
initialThe specification's initial value — often not what you want. display: initial is inline, not block; color: initial is black, not the surrounding text colour.
unsetinherit if the property inherits, initial if it does not. Usually the sensible one of the pair.
revertRoll back to what the previous origin said — normally the browser's default. display: revert on a <div> gives block.
revert-layerRoll back to what the previous cascade layer said.
Two things the all shorthand is good for CSS
/* Strip a button back to a plain box, keeping its behaviour */
.reset-button { all: unset; display: inline-block; cursor: pointer; }
/* ⚠ `all: unset` also removes the focus ring and the button role's
   default styles. Add :focus-visible back, or use appearance:none. */

/* Isolate an embedded widget from inherited page styles */
.widget-root { all: revert; }

5The box model

Four rings around every element, and one line of CSS that makes them behave sensibly.

Every element generates a box with, from the inside out: content, padding, border, margin. The only real question is what width refers to.

min-width / max-width
Clamp the computed width and always beat width. max-width: 100% on images is the classic fix for overflow; min-width: 0 is the classic fix for a flex item refusing to shrink (Chapter 9).
aspect-ratio
Set one dimension and let the other follow: aspect-ratio: 16 / 9. Removes the old padding-top percentage hack entirely.
overflow
visible (default), hidden, scroll, auto, clip. Note that any value other than visible creates a new block formatting context and a scroll container, which has knock-on effects on margin collapsing and position: sticky.
Logical properties
margin-inline, padding-block, inline-size, border-inline-start. They follow the writing mode, so a layout built with them works unchanged in Arabic or Japanese. margin-inline: auto is the modern way to centre a block. Prefer them by default in new code.

padding: max(1rem, 3vw);           /* a floor that grows on big screens */

/* Always include a rem term in the middle so browser zoom still works.
   A pure-vw preferred value is a WCAG 1.4.4 failure. */

7Custom properties

Not variables in the preprocessor sense — live values that participate in the cascade, inherit, and can be changed at runtime.

A Sass variable is substituted at build time and then gone. A CSS custom property exists in the browser: it inherits down the tree, can be overridden per selector, per media query, per element, and can be read and written from JavaScript. That difference is what makes theming, component variants and dark mode straightforward.

Declaration, fallback, scoping, runtime CSS + JS
:root {
  --space: 1rem;
  --brand: #4BA3E3;
  --brand-ink: #1F6FA8;
}

.card {
  padding: var(--space);
  /* second argument is the fallback if the property is not set */
  border-color: var(--card-border, #CFD8E0);
}

/* Scoped override — everything inside inherits the new value */
.card--compact { --space: 0.5rem; }

@media (prefers-color-scheme: dark) {
  :root { --brand: #7FC4F5; }   /* one place, whole theme */
}

// From JavaScript
el.style.setProperty('--space', '2rem');
getComputedStyle(el).getPropertyValue('--space');
They inherit
Which is the point. Set --space on a container and every descendant sees it, unless one of them overrides it. That makes component variants a one-line change rather than a cascade of selectors.
Invalid at computed-value time
The trap. --gap: banana; padding: var(--gap) does not fall back to the previous padding — the property becomes unset and inherits or takes its initial value. The failure looks nothing like a syntax error, which makes it hard to spot.
They are strings until used
So --x: 10; width: calc(var(--x) * 1px) works, but --x: 10px; width: calc(var(--x) * 2) also works while --x: 10px; --y: calc(var(--x) * var(--x)) does not. Compose carefully.
@property registration
Declares a type, an initial value and whether the property inherits. Two big wins: the value is validated (so a bad value falls back instead of unsetting), and typed properties can be animated and transitioned, which plain custom properties cannot.
Registering a property so it can animate CSS
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}

.spinner {
  background: conic-gradient(from var(--angle), #4BA3E3, transparent);
  transition: --angle .4s ease;   /* impossible without @property */
}
.spinner:hover { --angle: 180deg; }
Naming that survives

Two tiers work well. Primitives describe the value: --blue-500, --space-3. Semantic tokens describe the use and point at a primitive: --color-action: var(--blue-500), --space-card-padding: var(--space-3). Components consume only semantic tokens, so a rebrand or a dark theme changes one layer and nothing else. Chapter 12 builds this out properly.

Native nesting

CSS nests now, without a preprocessor CSS

  /* & is required when the nested selector starts with an element name */
  & h3 { margin-block: 0 .5rem; }

  &:hover { border-color: var(--brand); }

}

9Check yourself

Six questions.

1. #sidebar a { color: blue } and .link.external.important-thing.really { color: red } both match. Which wins, and what would you change?

Blue. Specificity is compared column by column, not summed: (1,0,1) versus (0,4,0), and a single id beats any number of classes. Adding more classes can never catch up. The fixes, in order of preference: put the two rules in cascade layers and order the layers; stop using ids as styling hooks (use #sidebar only as a link target and add a class for styling); or wrap the id selector in :where(#sidebar) a, which drops its specificity to (0,0,1).

2. Why does a rule in a later cascade layer beat a much more specific rule in an earlier one?

Because layer order is criterion 4 and specificity is criterion 5. The cascade is a strict tie-break chain, so once the layers differ the comparison stops and specificity is never consulted. That inversion is the whole value of layers: you decide precedence once, structurally, instead of escalating selectors forever. Note the two exceptions — unlayered styles beat every layer, and !important reverses the layer order.

3. You set padding: 5% on a box that is 400px wide and 100px tall. How much vertical padding do you get?

20px, not 5px. Percentage padding and margin resolve against the inline size of the containing block — its width — in all four directions, including top and bottom. This is why the old padding-top: 56.25% trick produced a 16:9 box before aspect-ratio existed, and it catches people who expect vertical percentages to use height. Height percentages themselves are different again: they resolve against the containing block's height, and are ignored entirely if that height is auto.

4. A colleague writes --pad: 1rm; (typo) and uses padding: var(--pad). What do you see in the browser?

Not the previous padding, and not a console error. Custom properties accept almost any token at parse time, so the mistake is only discovered when the value is substituted — at computed-value time — at which point the padding declaration becomes invalid and the property is treated as unset. Since padding does not inherit, it falls back to its initial value of 0. The element loses its padding entirely, with no clue why. Registering the property with @property { syntax: '<length>'; initial-value: 1rem } makes the browser reject the bad value and use the declared initial instead.

5. What is the difference between :is(.a, .b) and :where(.a, .b), and when does it matter?

They match identically. The only difference is specificity: :is() takes the specificity of its most specific argument, while :where() always contributes zero. It matters whenever you are writing styles other people will override — a reset, a base layer, a design-system default, or typography applied to a content area. :where(.prose) a { color: … } can be overridden by a bare .link class, whereas :is(.prose) a requires matching or exceeding (0,1,1).

6. Your hero section uses width: 100vw and a horizontal scrollbar appears on desktop but not on your Mac. Why?

vw is 1% of the viewport width including the space taken by a classic scrollbar. On Windows and Linux, where scrollbars are overlaid on top of the layout viewport rather than floating, 100vw is roughly 15px wider than the available content width, so the section overflows and a horizontal scrollbar appears — which then narrows things further. Macs default to overlay scrollbars, so you never see it. Use width: 100%, or the newer 100dvw family, or clamp with max-width: 100%. It is one of the most reported "works on my machine" CSS bugs.
