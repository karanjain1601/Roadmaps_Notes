CHAPTER 17

TypeScript for the front end

A type layer that disappears before the browser sees it. That single fact — erasure — explains both what TypeScript is excellent at and the one class of bug it cannot possibly catch: the moment untyped data crosses into your program from a network response.

Part 4 JavaScript in the browser·Reading time 50 minutes·Demos runtime validator, utility types·Prerequisites Chapters 13–16

1What it is, and what it is not

Three properties that between them explain almost every TypeScript question.

1 · Types are erased
The compiler checks, then deletes every annotation. The emitted JavaScript has no types in it, so there is no runtime enforcement whatsoever. A function declared to take a number will happily receive a string at runtime if the value came from somewhere the compiler could not see.
2 · The type system is structural
Compatibility is decided by shape, not by name or declared lineage. Anything with a name: string is assignable to { name: string }, regardless of which class or interface it came from. This is very different from Java or C#, and it is why "duck typing with checking" is a fair description.
3 · It is deliberately unsound in places
A few rules are knowingly unsafe because the safe version would be unusable — array covariance and method parameter bivariance, for instance. TypeScript optimises for catching real mistakes in real code, not for a proof.
What you actually get

Errors at the point of the mistake rather than three files away at runtime. Refactoring that a machine can verify — rename a property and every use is found. Autocomplete that knows your data. Documentation that cannot drift, because it fails the build when it does. On a codebase of any size those compound; on a fifty-line script they do not, and that is a legitimate reason to skip it.

2The type vocabulary

Enough to write real code, in one block.

The shapes you will write daily TypeScript
// Primitives and literals
let n: number; let s: string; let ok: boolean;
let status: 'idle' | 'loading' | 'error';   // a union of literal types

// Arrays and tuples
let ids: number[];
let pair: [string, number];                     // fixed length and order
let frozen: readonly string[];

// Objects
type User = {
  id: string;
  name: string;
  email?: string;              // optional: string | undefined
  readonly createdAt: Date;      // compile-time only, not frozen
};

// Functions
type Fetcher = (url: string, init?: RequestInit) => Promise<Response>;

// Unions and intersections
type Id = string | number;
type Timestamped = User & { updatedAt: Date };

// Deriving instead of duplicating
const ROLES = ['admin', 'editor', 'viewer'] as const;
type Role = typeof ROLES[number];   // 'admin' | 'editor' | 'viewer'
type UserKey = keyof User;         // 'id' | 'name' | 'email' | 'createdAt'
TypeMeans, and when to reach for it
anyChecking off. It spreads: anything derived from an any is also unchecked. Treat every one as a to-do, and turn on noImplicitAny so you never get one by accident.
unknownThe safe any: you can hold it but not use it until you narrow. The correct type for a parsed JSON response and for a caught error.
neverA value that cannot exist. A function that always throws returns never, and it is the trick behind exhaustiveness checking in the next section.
voidA function returns nothing useful. Different from undefined: a void-returning callback type accepts a function that returns something, which is what makes arr.forEach(x => set.add(x)) legal.
objectAny non-primitive. Almost never what you want — use a shape, or Record<string, unknown>.
type or interface?
Both describe object shapes and are interchangeable for most purposes. interface can be reopened and merged, which is essential for augmenting third-party declarations and a hazard everywhere else. type can express unions, tuples, mapped and conditional types, which interface cannot. A workable convention: interface for public object contracts you expect others to extend, type for everything else.
as const
Freezes literals into their narrowest types and makes everything readonly. It is the difference between string[] and a union of exact strings, and it is how you derive types from data instead of maintaining both.
satisfies
Checks a value against a type without widening it. const routes = {...} satisfies Record<string, Route> validates the shape while keeping the exact keys available for autocomplete — which a plain annotation would throw away.

3Narrowing

The heart of using TypeScript well: start wide, prove your way down.

Every narrowing tool TypeScript
function handle(v: string | number | Date | null) {
  if (v === null) return;                // equality narrowing
  if (typeof v === 'string') v.trim();     // typeof, for primitives
  else if (v instanceof Date) v.getTime();  // instanceof, for classes
  else v.toFixed(2);                      // narrowed to number by elimination
}

// `in` narrows by property presence
if ('radius' in shape) shape.radius;

// A type predicate teaches the compiler about your own check
function isUser(v: unknown): v is User {
  return typeof v === 'object' && v !== null && 'id' in v;
}

// An assertion function narrows everything after it
function assertDefined<T>(v: T): asserts v is NonNullable<T> {
  if (v == null) throw new Error('expected a value');
}

Discriminated unions, and exhaustiveness

The single most useful pattern in application TypeScript. Give every member of a union a shared literal field, and the compiler narrows on it — then a never assignment in the default branch makes it a build error to add a case and forget to handle it.

Modelling state so impossible states cannot be expressed TypeScript
type Result<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

function render(r: Result<User>) {
  switch (r.status) {
    case 'idle':    return null;
    case 'loading': return spinner();
    case 'success': return profile(r.data);   // .data exists only here
    case 'error':   return oops(r.error);
    default: {
      const _exhaustive: never = r;   // add a case above → this line errors
      return _exhaustive;
    }
  }
}

// Compare with the shape people write first, which permits nonsense:
//   { loading: boolean; data?: User; error?: Error }
// …allowing loading AND error AND data all at once.

4Generics and utility types

Types that take arguments. Most of the time you consume them rather than write them.

Generics with constraints and inference TypeScript
// T is inferred from the call — you rarely pass it explicitly
function first<T>(arr: T[]): T | undefined { return arr[0]; }

// A constraint says "T must at least look like this"
function byId<T extends { id: string }>(items: T[], id: string) {
  return items.find(i => i.id === id);
}

// keyof gives type-safe property access with a precise return type
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
pluck(user, 'name');     // string
pluck(user, 'nmae');     // error: not a key of User

Awaited<P>The value inside a promise, recursively.

            
NonNullable<T>T without null and undefined.

            
Extract<T, U> / Exclude<T, U>Filter a union.

          
        

      


      

        
The three type-level tools worth recognising TypeScript

        
// Mapped type — transform every property
type Nullable<T> = { [K in keyof T]: T[K] | null };

// Conditional type — branch on assignability
type Unwrap<T> = T extends Promise<infer U> ? U : T;

// Template literal type — string patterns as types
type EventName = `on${Capitalize<'click' | 'focus'>}`;  // 'onClick' | 'onFocus'

// You will read these far more often than you write them. Type-level
// cleverness is a real maintenance cost — reach for it when it removes
// duplication, not to prove it can be done.

      

    


    
    

      
5Typing the DOM

      
Where beginners meet as and start using it wrongly.


      

        
The patterns that come up constantly TypeScript

        
// querySelector is generic — pass the element type, do not cast
const input = document.querySelector<HTMLInputElement>('#email');
// type: HTMLInputElement | null  — the null is real, handle it
if (!input) throw new Error('#email is missing');
input.value;                       // now safe

// Events: the handler parameter is typed from the event name
button.addEventListener('click', (e) => {
  e.clientX;                       // PointerEvent — inferred
  // currentTarget is typed; target is EventTarget | null and is not
  (e.currentTarget as HTMLButtonElement).disabled = true;
});

// Delegation: narrow with instanceof rather than casting
list.addEventListener('click', (e) => {
  if (!(e.target instanceof HTMLElement)) return;
  const row = e.target.closest<HTMLLIElement>('li');
  if (row) select(row.dataset.id);   // string | undefined
});

// Custom events, typed globally
declare global {
  interface HTMLElementEventMap {
    'cart:add': CustomEvent<{ id: string; qty: number }>;
  }
}

      


      

        as is not a conversion
        
A type assertion tells the compiler to stop checking. It changes nothing at runtime and it is a promise you are making — if you are wrong, the error simply moves to a later line with less context. as is legitimate when you genuinely know something the compiler cannot, such as the element type behind a selector you control. It is illegitimate as a way to silence an error you have not understood, and as unknown as T — the double assertion used to force incompatible types together — should be treated as a code smell that needs a comment explaining itself.

      

    


    
    

      
6The boundary problem

      
Your types describe what you hope arrived. Here is what to do about that.


      
This is the most important idea in the chapter. await res.json() returns any. Annotating it as User makes the compiler stop worrying, but nothing checked anything — if the API renamed a field, shipped null where you expected a string, or returned an error envelope, TypeScript is entirely silent and you get a runtime failure somewhere deeper, with a stack trace pointing at the wrong place.

    Parse, do not assert TypeScript
    
        
    // ✗ A lie the compiler believes
const user = await res.json() as User;

// ✓ A schema that validates at runtime AND infers the static type,
//   so there is exactly one definition of the shape.
const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
  age: z.number(),
  active: z.boolean(),
  email: z.string().email().optional(),
  role: z.enum(['admin', 'editor', 'viewer'])
});
type User = z.infer<typeof UserSchema>;

const user = UserSchema.parse(await res.json());
// Throws HERE, at the boundary, with a message naming the field —
// rather than three components later with "cannot read property of null".
    
      
    

      
    
        
    Where else data enters untyped
    
        
    JSON.parse, localStorage, URL parameters, postMessage, form values, environment variables, third-party SDK callbacks, and anything from a CMS. Every one is an any in disguise. Validate at each boundary and the interior of your program can be trusted.
    
        
    Generated types
    
        
    If the API has an OpenAPI or GraphQL schema, generate the types from it rather than hand-writing them — they then cannot drift. This gives you accuracy at build time; it still does not guarantee the running server matches its own spec, which is why validation and generation are complements rather than alternatives.
    
        
    Validate what you use
    
        
    You do not need a schema for every field of a large response. Validating the fields you actually read catches the failures that matter and keeps the schema maintainable.
    
      
    
    
    

    
    
    
      
    7Configuration and adoption
    
      
    Seven flags, and a migration order that does not stall.
    

      
    
        
    
          
    FlagWhy
    
          
            
    "strict": trueTurns on the whole family, including strictNullChecks — which is the one that provides most of TypeScript's value. Non-negotiable for new code.
    
            
    noUncheckedIndexedAccessMakes arr[i] and obj[key] return T | undefined, which is the truth. Noisy at first and it catches real bugs.
    
            
    exactOptionalPropertyTypesDistinguishes "absent" from "present and undefined". Matters when you serialise.
    
            
    noImplicitOverrideRequires the override keyword, so renaming a base method fails loudly.
    
            
    verbatimModuleSyntaxForces import type for type-only imports, so the emitted JavaScript is predictable and bundlers can drop them.
    
            
    isolatedModulesGuarantees every file can be transpiled independently, which is what esbuild, SWC and Vite actually do.
    
            
    skipLibCheckSkips type-checking .d.ts files from dependencies. Almost everyone enables it, because you cannot fix someone else's declarations.
    
              
        
    
      
    

      
    
        
    Type-checking is not transpiling
    
        
    Modern build tools strip types without checking them — that is why they are fast. tsc --noEmit must therefore run separately, in CI and in your editor, or nothing is actually being verified.
    
        
    Migrating an existing codebase
    
        
    Enable allowJs and checkJs with JSDoc types first — you get real checking with no file renames. Then convert leaf modules upward, ending at the entry points. Turn on strict from day one for new files only, using a per-directory config, rather than trying to fix thousands of errors at once.
    
        
    How strict is too strict
    
        
    The failure mode of an over-typed codebase is real: generics five parameters deep, conditional types nobody can debug, and a build that takes four minutes. The test is whether a type makes the next change safer or merely more impressive. Prefer a simple type plus a runtime check over a clever type with none.
    
      
    
    
    

    
    
    
      
    8Check yourself
    
      
    Six questions, closing Part 4.
    

      
    
        
    1. Your code declares const user = await res.json() as User. The API drops the email field. What does TypeScript do?
    
        
        
    
          
    Nothing at all. Types are erased before the code runs, and an assertion switches checking off rather than performing a conversion, so the compiler is content and the runtime has an object missing a property your code believes exists. The failure appears later — a template rendering undefined, or a .toLowerCase() throwing — with a stack trace pointing at the consumer rather than the boundary. Parse the response against a schema instead, so it throws at the point of entry with the offending field named.
    
        
    
      
    

      
    
        
    2. What is the difference between any and unknown, and which belongs on a caught error?
    
        
        
    
          
    any disables checking and is contagious — every expression derived from it is also unchecked, so one any can quietly hollow out a module. unknown is the safe counterpart: you can store and pass it, but you cannot access a property or call it until you narrow. A caught value should be unknown, because JavaScript allows throwing anything, so err.message is not guaranteed to exist. Narrow with err instanceof Error first. Setting useUnknownInCatchVariables — included in strict — makes this the default.
    
        
    
      
    

      
    
        
    3. Why is { status: 'loading' } | { status: 'success'; data: T } better than { loading: boolean; data?: T }?
    
        
        
    
          
    Because the second permits states that cannot happen: loading and having data at the same time, or neither loading nor having data nor an error. Every consumer then has to handle combinations that the system never produces, and the compiler cannot help because data is optional everywhere. A discriminated union makes data available exactly in the branch where it exists, so no null check is needed there and no impossible branch can be written. Add an exhaustiveness check with never and adding a fifth state becomes a compile error in every place that must handle it.
    
        
    
      
    

      
    
        
    4. A colleague fixes a type error with as unknown as HTMLInputElement. What are you looking at?
    
        
        
    
          
    A double assertion, used because a single as was rejected — TypeScript refuses direct assertions between types with no overlap, so routing through unknown forces it. That refusal was information: the compiler was saying these shapes are unrelated. Occasionally the assertion is genuinely correct and unavoidable at a boundary the type system cannot see, in which case it deserves a comment saying why. Far more often it is a real mismatch being hidden, and the failure resurfaces at runtime with the original context lost.
    
        
    
      
    

      
    
        
    5. Does TypeScript make your application faster or safer at runtime?
    
        
        
    
          
    Neither, directly. The output is the same JavaScript with annotations removed, so there is no performance effect and no runtime guarantee — a value that violates its declared type behaves exactly as it would have without TypeScript. What it provides is earlier detection: mistakes surface at the keystroke or the build rather than in production, and refactors become verifiable. Runtime safety at the edges requires runtime validation, which is a separate tool that happens to compose very well with the type system.
    
        
    
      
    

      
    
        
    6. Why does noUncheckedIndexedAccess produce so many errors, and is it worth it?
    
        
        
    
          
    Because by default TypeScript assumes arr[5] is a T, when in fact it is T | undefined — the index may be out of range, and the same applies to Record lookups for keys that are not present. Enabling the flag tells the truth, and the truth is that a large amount of existing code accesses possibly-missing values without checking. It is worth it on new codebases, where the errors appear as you write; on a large existing one it can be thousands of errors at once, so enable it per-directory as you migrate. The alternative is a class of undefined bugs that the type system was silently promising could not occur.
