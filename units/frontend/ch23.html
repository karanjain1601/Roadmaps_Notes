CHAPTER 23

Bundlers and build pipelines

Between the files you write and the files a browser downloads sits a program that resolves a graph, transforms every node in it, deletes what is unreachable, and decides how to cut the result into cacheable pieces. Understanding those four jobs turns build configuration from guesswork into a set of decisions.

Part 6 The toolchain·Reading time 50 minutes·Demos chunking strategy, exports resolver·Prerequisites Chapters 2, 13, 22

1Why a build step exists

Browsers support modules natively now. Five reasons the build stayed anyway.

Transformation
TypeScript, JSX, Svelte and Vue components, Sass, PostCSS — none of it is something a browser can execute. Something must convert it.
Resolution
import { z } from 'zod' is not a URL. Bare specifiers require a resolution algorithm over node_modules and exports maps — section 2 — which browsers only partly support via import maps.
Deletion
Tree shaking removes code nothing reaches. Nothing at runtime can do this.
Chunking and cache strategy
Deciding what ships together and giving each output a content hash so it can be cached forever (Chapter 2). Native modules would mean hundreds of requests and no hashing.
Optimisation
Minification, dead-code elimination behind flags, environment inlining, asset processing, polyfill selection by target.

The pipeline is always the same shape: resolve → load → transform → graph → optimise → emit. Every tool in section 7 implements those stages; they differ in the language they are written in and where they place the boundaries.

2Module formats, and the interop mess

Two real formats, twenty years of history, and the field that decides which file you actually get.

FormatSyntaxStatus
ESMimport / exportThe standard. Statically analysable, so it can be tree-shaken and it works natively in browsers.
CJSrequire / module.exportsNode's original format. Dynamic — require is a function call that can take a computed path — so it cannot be reliably tree-shaken.
UMDA wrapper detecting the environmentLegacy. Works everywhere, optimises nowhere.
IIFE(function(){ … })()An output format for a script tag, not something you author.

The friction is that node_modules contains both, and a package must declare which file to hand to which consumer. That is the exports map, and it is the most commonly misunderstood field in package.json.

    Order matters, and default goes last
    Conditions are matched top to bottom and the first hit wins, so a default key placed above import makes everything below it unreachable. types must come first for the same reason.
    exports is an encapsulation boundary
    Once a package declares it, nothing outside the listed paths can be imported. my-lib/dist/internal/thing.js stops resolving even though the file exists — which breaks consumers who were reaching into internals, deliberately.
    The dual-package hazard
    If a package ships both ESM and CJS and a dependency graph loads both, you get two copies with two separate module states. For a library holding a singleton — a client instance, a registry, a React context — that is a real bug that presents as "my provider isn't found".
    "type": "module"
    Makes .js files in that package ESM. Without it they are CJS. The .mjs and .cjs extensions override the field explicitly, which is why you see them in published packages.

    3The graph and the transforms

    Start at an entry point, follow every import, and do something to each file on the way.

    A minimal, realistic config vite.config.js
    import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],              // transforms: JSX, fast refresh
  resolve: {
    alias: { '@': '/src' }        // stop writing ../../../
  },
  build: {
    target: 'baseline-widely-available',
    sourcemap: true,             // upload to error tracking, do not deploy publicly
    rollupOptions: {
      output: { manualChunks: { /* section 5 */ } }
    }
  },
  server: { proxy: { '/api': 'http://localhost:8080' } }   // avoids CORS in dev
});
    Everything is a module
    Importing a CSS file, an SVG or a JSON file works because a plugin claims that extension and returns JavaScript — a string, a component, a URL. That is why an import of a .css file has no named export and still affects the page.
    Assets get three treatments
    Small files are inlined as data URIs to save a request; larger ones are copied out with a content hash and the import returns the URL; some are processed — images resized, SVGs optimised. The inline threshold is configurable and worth checking, since inlining a 30 KB image into your JavaScript bundle is a bad trade.
    Environment variables are inlined, not read
    import.meta.env.VITE_API_URL is textually replaced at build time. Two consequences: changing it requires a rebuild, and anything you put there ships to the browser in plain text. Chapter 1's third constraint. Prefixes such as VITE_ or NEXT_PUBLIC_ exist to make the exposure deliberate.
    The graph is per entry
    Multiple entries — a main app and a service worker, say — produce separate graphs that may share chunks.

    4Tree shaking

    Deleting what nothing reaches. It works better than people expect and fails for reasons that are always the same five.

    Because ESM imports and exports are static, a bundler can build a graph of which exported binding is reached from an entry point and delete the rest. It is dead-code elimination with module-level scope.

    What defeats itWhy
    CommonJSrequire() is a runtime function call with a possibly-computed path. The bundler cannot prove what is used, so it includes everything.
    Namespace importsimport * as utils followed by dynamic access such as utils[name]() means any export might be used.
    Missing "sideEffects": falseWithout that declaration a bundler must assume importing a module does something, so it cannot drop it even if nothing is used from it. Set it, and list the exceptions — CSS imports, polyfills.
    Side effects at module top levelA module that registers a plugin, patches a prototype or writes to window when imported cannot be removed. This is real, and it is why the flag has an escape list.
    Class methods and property accessShaking works on module exports, not inside them. An unused method on an exported class stays.
    Barrel files

    An index.ts that re-exports fifty modules is convenient and quietly expensive. Importing one thing from it forces the bundler to load and analyse all fifty to prove the rest are unused, which slows every build and every dev-server request — and if any of those modules has a side effect, the shaking fails and they all ship. For a design system this is a measurable build-time cost. Import from the specific path in hot paths, and keep barrels shallow.

    5Code splitting

    One file is simple and cached badly. A hundred is cached well and requested slowly. The middle is a design decision.

    Where split points come from JavaScript
    // 1. Dynamic import — the universal split point. The bundler sees the
//    static string and emits a separate chunk.
const { Chart } = await import('./chart.js');

// 2. Route-level, via the router
{ path: '/reports', component: () => import('./routes/Reports.vue') }

// 3. Conditional — load only when actually needed
if (needsEditor) await import('./rich-editor.js');

// ⚠ A computed specifier cannot be statically analysed. This either
//   fails or bundles every possible match, depending on the tool.
await import(`./locales/${lang}.js`);
// Use an explicit map instead:
const loaders = { en: () => import('./locales/en.js'),
                  fr: () => import('./locales/fr.js') };

    The cache-invalidation argument
    Content-hashed filenames (Chapter 2) mean a chunk is cached forever until its content changes. One giant bundle means every deploy invalidates everything, including the framework code that has not changed in six months. Splitting vendor code out is mostly about which bytes survive a deploy, not about the first visit.
    Do not over-split
    Under HTTP/2 many requests are cheap but not free, and very small chunks compress badly — gzip and Brotli work on repetition, and a 2 KB chunk has little to repeat. Somewhere around 20–100 KB per chunk is a reasonable target.
    Preload the chunks you know you need
    A dynamically imported chunk is discovered only when the importing code runs, which is late. Bundlers emit modulepreload hints for chunks needed on load; for a route the user is likely to visit, prefetch on link hover or when the link scrolls into view.
    Beware the shared-chunk explosion
    Automatic strategies that extract every module shared by two routes can produce dozens of tiny chunks with a complex dependency graph, so a single navigation needs eleven requests. Check the actual output rather than trusting the heuristic.

    6The dev server

    Development and production builds do genuinely different things, and the gap is where surprises live.

    Native-ESM dev servers
    Vite's model: do not bundle in development at all. Serve source files over HTTP as modules, transform each one on request, and let the browser build the graph. Start-up is near-instant regardless of project size, because nothing is built until it is requested.
    Dependency pre-bundling
    The exception. node_modules packages are bundled once with esbuild, because a package like lodash is 600 individual modules and requesting them separately would be far slower than one pre-built file. This is also where CJS dependencies are converted to ESM.
    Hot module replacement
    Swap a changed module in place without reloading, preserving state. Frameworks add fast refresh so component state survives an edit. It fails on modules with top-level side effects and on some circular graphs, which is why it sometimes falls back to a full reload.
    Why dev and prod differ
    Development skips minification and tree shaking, keeps development-only warnings, and uses different module handling. That means a bug can exist only in production — most often through process.env.NODE_ENV branches, minifier assumptions, or a dependency behaving differently once bundled. Build and preview locally before releasing; vite preview and its equivalents exist for exactly this.
    Type checking is not part of it
    esbuild and SWC strip TypeScript types without checking them, which is why they are fast. tsc --noEmit must run separately in CI or nothing is verifying your types. Chapter 17.

    7The tools

    Two layers: transformers that convert one file, and bundlers that own the graph.

    ToolLayerCharacter
    ViteBundler / dev serverThe default choice for new projects. Native-ESM dev, Rollup-based production build, huge plugin ecosystem, used by most framework CLIs.
    RollupBundlerExcellent tree shaking and clean ESM output. The standard for publishing libraries, and Vite's production engine.
    esbuildBundler / transformerWritten in Go and enormously fast. Fewer optimisation features and no type checking; widely used as a component inside other tools.
    RolldownBundlerRollup's API in Rust, intended to replace both Rollup and esbuild inside Vite so dev and production share one engine — historically a source of dev/prod differences.
    webpackBundlerThe most configurable and the slowest. Still correct for complex legacy setups, module federation, and anything relying on its plugin ecosystem.
    TurbopackBundlerRust, incremental, built for Next.js and tied to it.
    ParcelBundlerZero configuration by design. Good for small projects and prototypes.
    SWC / BabelTransformersPer-file compilation. SWC is Rust and fast; Babel is slower with an unmatched plugin ecosystem and is still how experimental syntax gets used.

    In practice most people do not choose: the framework's CLI has chosen. What is worth knowing is which engine you have, so that when a build behaves oddly you know whose documentation to read.

    8Output concerns

    Seven settings that decide what actually lands on the CDN.

    ConcernWhat to know
    TargetsA browserslist query decides which syntax is downlevelled and which polyfills are added. Targeting too old costs bytes for browsers nobody uses; too new breaks silently for someone. baseline-widely-available is a good modern default.
    MinificationShortens names, drops whitespace, removes provably dead branches. Combined with Brotli it typically leaves about a quarter of the original text. Note it can change behaviour if code relies on function names or on toString().
    Content hashingapp.9f3c1a2e.js. The mechanism that makes Cache-Control: immutable safe (Chapter 2). On by default in every modern tool.
    Source mapsMap minified output back to source in devtools and error reports. Generate them always; upload them to your error tracker; think carefully before serving them publicly, since they reveal your source. hidden-source-map emits them without the reference comment.
    CSS extractionImported CSS is pulled into real stylesheets rather than injected by JavaScript, so it is render-blocking in the right way instead of arriving after first paint. Chapter 1.
    PolyfillsOnly for what your targets actually lack, ideally loaded conditionally so modern browsers pay nothing. A blanket polyfill bundle is one of the largest easy savings in most projects.
    Legacy buildsShipping a second, downlevelled bundle behind nomodule. Almost always unnecessary now, and it doubles your build output — check whether the browsers it serves are still in your analytics.
    Analyse the output
    rollup-plugin-visualizer, webpack-bundle-analyzer or source-map-explorer give a treemap of what is in each chunk, attributed back to source files. Run it after any dependency change; the surprises are usually a moment-style date library, a whole icon set, or two copies of the same package.
    Budget it in CI
    A hard byte limit per entry chunk that fails the build. It is the only mechanism that reliably prevents slow drift, because it forces a conversation at the moment the bytes are added rather than six months later.
    Measure compressed, not raw
    Users download the Brotli-compressed size. A 900 KB bundle that compresses to 180 KB is a different problem from one that compresses to 600 KB — though remember from Chapter 1 that execution cost tracks the uncompressed size.

    9Check yourself

    Six questions.

    1. A library advertises tree shaking, but importing one function adds 60 KB. Give three possible causes.

    First, you may be getting the CommonJS build — check the exports map for an import condition, and check that your bundler is resolving it rather than falling back to main. CJS cannot be shaken. Second, the package may not declare "sideEffects": false, so the bundler must assume every module does something observable when imported and cannot drop any of them. Third, your import style: import _ from 'lib' or a namespace import with dynamic property access pulls everything, where a named import from an ESM build pulls one binding. A fourth possibility is a genuine top-level side effect in the library, in which case it is not shakeable and the documentation is optimistic.

    2. Why split vendor code into its own chunk when it makes the first visit no faster?

    Because the benefit is on every visit after a deploy. Output files carry a content hash, so a chunk is cached indefinitely until its bytes change. In a single bundle, changing one line of your own code changes the hash of everything, and returning users re-download the framework, the date library and the charting code that have not changed in months. With vendor code in a separate chunk, a typical deploy invalidates only the application chunk. The demo makes this visible: switch on "after a deploy" and compare the re-downloaded figure across strategies.

    3. What does "exports" in a package.json do beyond pointing at a file?

    Two things. It maps conditions to files, so an ESM consumer, a CJS consumer, a browser build and a Node build can each receive a different file from the same package — matched top to bottom, first hit wins, which is why key order matters and default must be last. And it is an encapsulation boundary: once present, only the listed subpaths are importable at all, so deep imports into dist/internal/ stop resolving even though the files exist. That second effect breaks consumers who were reaching into internals, which is deliberate — it lets a package have a real public API.

    4. Your app works in development and throws in production. What differs?

    A lot. Production minifies — so anything relying on function or class names, or on Function.prototype.toString, changes behaviour. It tree-shakes, so a module with an unrecognised side effect may be dropped. It sets NODE_ENV to production, which strips development warnings and can take a different code path inside dependencies. It inlines environment variables at build time rather than reading them. And with a native-ESM dev server the module graph is genuinely different: dependencies are pre-bundled in dev and bundled properly in prod. The routine that catches nearly all of it is building and previewing the production output locally before release, and having source maps uploaded so the stack trace is readable when it does happen.

    5. Why is a barrel index.ts re-exporting fifty components a build-performance problem?

    Because importing one thing from it makes the tool load, parse and analyse all fifty modules — plus their imports — to prove the other forty-nine are unused. In production that is slower builds; in a native-ESM dev server it is worse, because each of those modules becomes a separate transform and request on every cold navigation. And if any one of them has a top-level side effect the shaking fails and all fifty ship. Keep barrels shallow, do not re-export from barrels inside barrels, and import from the specific path in code that is on a hot path.

    6. A colleague adds API_SECRET to .env and reads it with import.meta.env.VITE_API_SECRET. What is wrong?

    The value is textually inlined into the bundle at build time and shipped to every browser in plain text — one devtools search away. The VITE_ prefix exists precisely to mark a variable as public; unprefixed variables are deliberately excluded from client code, and the same convention applies to NEXT_PUBLIC_ and equivalents. Chapter 1's third constraint: nothing you ship is secret. A secret must live on a server, with the browser calling an endpoint that uses it. The related trap is that inlining happens at build time, so changing the value requires a rebuild, not a restart.
