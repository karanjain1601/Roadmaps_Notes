Talking to servers

Every interesting front end is mostly a client for something. This chapter is fetch in the detail its API deserves, the failure taxonomy that decides whether to retry, the three real-time transports and when each is right, and streaming — which stopped being exotic the moment interfaces started rendering tokens as they arrive.

1fetch, properly

One function, two objects, and one default that surprises everybody exactly once.

The options that matter JavaScript
const res = await fetch('/api/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Accept: 'application/json' },
  body: JSON.stringify(order),

  credentials: 'same-origin',   // 'include' to send cookies cross-origin
  mode: 'cors',                 // 'no-cors' gives an OPAQUE response you cannot read
  cache: 'default',             // 'no-store', 'reload', 'force-cache'…
  redirect: 'follow',           // 'manual' to inspect a 3xx yourself
  signal: controller.signal,     // cancellation — Chapter 15
  keepalive: false              // true lets a small request outlive the page
});
fetch does not reject on 404 or 500

The returned promise rejects only on a network-level failure: DNS failure, connection refused, CORS blocked, request aborted. A perfectly delivered 500 Internal Server Error is a fulfilled promise with res.ok === false. Every wrapper you write must check res.ok — this is the single most common fetch bug, and it fails by silently treating an error page as data.

A wrapper worth having JavaScript
class HttpError extends Error {
  constructor(res, body) {
    super(`${res.status} ${res.statusText}`);
    this.name = 'HttpError';
    this.status = res.status;
    this.body = body;
  }
}

export async function api(path, init = {}) {
  const res = await fetch(path, {
    headers: { Accept: 'application/json', ...init.headers },
    signal: init.signal ?? AbortSignal.timeout(15000),
    ...init
  });

  // 204 and 205 have no body; calling .json() on them throws
  const body = res.status === 204 ? null
    : (res.headers.get('content-type') ?? '').includes('json')
      ? await res.json()
      : await res.text();

  if (!res.ok) throw new HttpError(res, body);
  return body;
}
The body can be read once
res.json(), res.text(), res.blob(), res.arrayBuffer(), res.formData() all consume the stream. Calling two of them throws. Use res.clone() if you genuinely need both — for a logger, say.
Headers is a Map-like object
res.headers.get('content-type'), case-insensitive. Cross-origin responses only expose a safelist unless the server sends Access-Control-Expose-Headers, which is why a custom pagination header is often mysteriously null.
Request and Response are real objects
You can construct a Request and pass it around, and a service worker can synthesise a Response from nothing. That symmetry is what Chapter 28 relies on.
keepalive
Lets a small request (under 64 KB) survive the page being closed — the modern replacement for navigator.sendBeacon for analytics on unload. Cannot be used with a streaming body.

2Failure, retries and backoff

Not every failure should be retried, and retrying badly makes an outage worse.

FailureRetry?Because
Network error / DNS / offlineYesTransient by nature. Check navigator.onLine and the online event too.
408, 425, 429YesExplicitly retryable. Honour Retry-After if present.
500, 502, 503, 504YesServer-side and usually temporary. 502/503/504 especially.
400, 422NoThe request is wrong. Retrying sends the same wrong request.
401OnceRefresh the token, retry once, then send the user to sign in. Never loop.
403, 404, 409NoA definite answer. Surface it.
Aborted by youNoAbortError is expected control flow, not a failure to report.

And only retry methods that are safe to repeat. GET, PUT and DELETE are idempotent (Chapter 2); POST is not, unless the server supports an idempotency key.

Exponential backoff with full jitter JavaScript
const RETRYABLE = new Set([408, 425, 429, 500, 502, 503, 504]);

async function withRetry(fn, { tries = 4, base = 300, cap = 8000 } = {}) {
  for (let n = 0; ; n++) {
    try {
      return await fn();
    } catch (err) {
      const retryable = err.name === 'TypeError'          // network
        || (err instanceof HttpError && RETRYABLE.has(err.status));
      if (!retryable || n >= tries - 1) throw err;

      const ceiling = Math.min(cap, base * 2 ** n);
      const delay = Math.random() * ceiling;   // FULL jitter, not ±10%
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Why full jitter, not "backoff plus a little randomness"
If every client uses the same deterministic schedule, they all retry at exactly the same instants and the recovering server is hit by a synchronised wave — repeatedly, at each backoff step. Spreading each delay uniformly across the whole interval flattens that wave completely. The histogram above shows the difference.
Circuit breaking
After several consecutive failures, stop trying for a while and fail fast. It protects the server from a client that will not give up, and it lets the interface say "we cannot reach the service" instead of spinning.
Do not retry in a tight loop on 429
Read Retry-After — seconds or an HTTP date — and wait at least that long. Ignoring it is how a client gets banned.

3Caching and deduplication on the client

Chapter 2 covered HTTP caching. This is the layer above it, in your application.

Three components mount at once and each asks for the current user. HTTP caching may or may not help — the response might be no-cache, or the requests might race before either lands. An in-memory layer solves it.

Request deduplication in fifteen lines JavaScript
const inflight = new Map();

function dedupe(key, fn) {
  if (inflight.has(key)) return inflight.get(key);   // join the existing one
  const p = fn().finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}

// Three simultaneous callers, one network request, three resolutions
dedupe('user:me', () => api('/api/me'));
Stale-while-revalidate, in the client
Return the cached value immediately, fire a refresh in the background, update when it lands. The interface never shows a spinner for data it already has. This is the core behaviour of every serious data library.
Invalidation
The hard part. After a mutation you must decide what is now wrong — usually a set of keys by prefix — and either refetch or patch the cache optimistically. Getting this right by hand across a real app is where the effort goes.
Use a library
TanStack Query, SWR, RTK Query, Apollo. They give you deduplication, caching, background refetch, retry, pagination, optimistic updates and request cancellation as a coherent whole. Writing these individually is easy; writing them together, correctly, is not. Chapter 19 goes into where this fits in an application's state.
The Cache API is a different thing
caches.open() stores Request/Response pairs persistently and is designed for service workers. It survives reloads; an in-memory map does not. Chapter 28.

SSE is genuinely this small JavaScript
const es = new EventSource('/api/stream');

es.onmessage = (e) => append(JSON.parse(e.data));      // unnamed events
es.addEventListener('price', (e) => update(e.data)); // named events

// The wire format the server sends:

Choose polling when
Updates are infrequent and staleness of a few seconds is fine. It is stateless, cacheable, trivially debuggable and survives every proxy. Do not be embarrassed by it.
Choose SSE when
The server pushes and the client does not — notifications, live prices, progress, log tails, and streamed model output. Automatic reconnection with event-id replay is a genuine engineering saving.
Choose WebSocket when
The client sends frequently too: chat, collaborative editing, multiplayer, live cursors. Budget for the parts nobody mentions — heartbeat ping/pong to detect dead connections, exponential-backoff reconnect, and resynchronising state after a gap.
WebTransport
Over HTTP/3, with unreliable datagrams and multiple streams. Interesting for games and media; not yet a default.
Transport cost over one minute Same server-side events, four delivery strategies.

5Streaming responses

Render as it arrives instead of waiting for the last byte.

res.body is a ReadableStream. Reading it chunk by chunk lets a long response start appearing immediately — which is why model output appears token by token, and why a large table can render its first rows while the rest is still downloading.

Two patterns you will meet JavaScript
// 1. Plain text arriving progressively
const res = await fetch('/api/generate');
for await (const chunk of res.body.pipeThrough(new TextDecoderStream())) {
  output.textContent += chunk;      // chunks are NOT line- or word-aligned
}

// 2. NDJSON — one JSON object per line. Must buffer partial lines.
let buffer = '';
for await (const chunk of res.body.pipeThrough(new TextDecoderStream())) {
  buffer += chunk;
  const lines = buffer.split('\n');
  buffer = lines.pop();             // last element may be incomplete
  for (const line of lines) if (line) handle(JSON.parse(line));
}

// Progress on a download, when Content-Length is present
const total = +res.headers.get('content-length');
let received = 0;
for await (const bytes of res.body) {
  received += bytes.length;
  bar.value = received / total;
}
Chunk boundaries are arbitrary
A chunk can split a multi-byte character, a JSON object or a word. TextDecoderStream handles the character case; everything else is your buffer's job. Assuming one chunk equals one message is the standard streaming bug.
Streams and compression
CompressionStream and DecompressionStream give you gzip and deflate in the browser, which is occasionally useful for uploads.
Reading twice
A stream can only be consumed once, and consuming res.body means res.json() will throw. res.clone() if you need both, at the cost of buffering.

6CORS, enough to debug it

The full treatment is Chapter 27. This is the version you need when a request is failing right now.

The same-origin policy stops one site reading another's responses. CORS is the mechanism by which a server opts in. Three things follow, and they explain almost every CORS ticket:

The browser blocks the response, not always the request
For a simple request the server often received and processed it — your POST may well have created the record — and only the reading of the reply was blocked. The Network panel shows the request as sent.
Preflight
Anything beyond a plain GET/POST with simple headers triggers an OPTIONS request first. Adding Content-Type: application/json or an Authorization header is enough. If the preflight fails, the real request is never sent, and the console error mentions the preflight rather than your call.
Credentials tighten everything
With credentials: 'include' the server may not answer Access-Control-Allow-Origin: * — it must echo the specific origin and add Access-Control-Allow-Credentials: true. This is the most common single cause.
Only the server can fix it
No client-side header, option or flag makes CORS pass. mode: 'no-cors' does not "turn it off" — it returns an opaque response with status 0 and no readable body. A dev proxy avoids it locally by making the request same-origin; it does not solve production.

7Uploads, downloads and progress

The one place XHR is still the right tool.

Upload progress
fetch has no upload progress event. XMLHttpRequest does, via xhr.upload.onprogress, and remains the pragmatic choice for a file uploader with a progress bar. Streaming request bodies are the eventual replacement but are not universally available.
Download progress
fetch handles this fine — read res.body and count bytes against Content-Length, as in the previous section. Note the header is absent for chunked or compressed responses, so have a fallback.
Triggering a download
Create an object URL from a blob, click a temporary anchor with a download attribute, then URL.revokeObjectURL() — forgetting that leaks the whole blob for the life of the document.
Large files
Upload directly to object storage with a pre-signed URL rather than through your application server, and chunk anything big enough that a dropped mobile connection would be painful to repeat. Chapter 5.

8Check yourself

Six questions.

1. Your fetch wrapper is in a try/catch and users still see broken pages on server errors. Why?

Because fetch only rejects on network-level failures. A 500 arrives as a fulfilled promise with res.ok === false, so the catch never runs and the code proceeds to parse an error page as if it were data. Every wrapper must check res.ok explicitly and throw. The second half of the same bug: calling res.json() on a 204, which has no body and throws a parse error that looks like a server problem.

2. Why is Math.random() * delay better than delay ± 10% for retry backoff?

Because the problem is synchronisation, not precision. When a service goes down, every client fails at roughly the same moment and then follows the same deterministic schedule, so they all retry together — repeatedly — and the recovering server is knocked over by each wave. A ±10% band still leaves a tight cluster. Full jitter spreads each client uniformly across the entire interval, flattening the distribution completely. The demo's histogram shows the two side by side: one produces spikes, the other a flat spread.

3. A file upload works with curl but the server reports a malformed body when sent from the browser with FormData. What is the likely mistake?

Setting Content-Type: multipart/form-data manually. That header must include a boundary parameter — a random delimiter the browser generates when it serialises the FormData. If you set the header yourself the boundary is missing, so the server cannot find where each part begins. Omit the header entirely and the browser supplies the complete, correct value. This is the one case where letting the platform set a header matters.

4. You need live updates from server to client. Why might SSE be the better choice over WebSockets even for a "real-time" feature?

Because most "real-time" features are one-directional — notifications, prices, progress, streamed output — and SSE gives you that over plain HTTP with automatic reconnection and event-id replay built in. With WebSockets you own the reconnect logic, the heartbeat that detects a silently dead connection, and the state resynchronisation after a gap, all of which is real work that is easy to get subtly wrong. Choose WebSockets when the client genuinely needs to send frequently; otherwise the simpler transport is the better engineering decision.

5. Your streaming handler parses each chunk with JSON.parse and intermittently throws. What is wrong?

Chunk boundaries have nothing to do with message boundaries. A chunk is whatever bytes happened to arrive together, so it can end halfway through a JSON object, or contain two and a half of them. You must accumulate into a buffer, split on your delimiter — a newline for NDJSON — process the complete records, and keep the trailing partial for the next chunk. TextDecoderStream handles the analogous problem for multi-byte characters, but only that one.

6. Three components mount together and each fetches the current user. How do you end up with one request without lifting state?

Deduplicate by key. Keep a Map from request key to in-flight promise: the first caller starts the request and stores the promise, subsequent callers with the same key receive the same promise, and the entry is deleted in a finally. All three components await the same promise and resolve together from one network call. This is the simplest useful piece of a data-fetching layer — and the point at which most teams adopt a library, because caching, invalidation and background refetch on top of it are where the real complexity lives.
