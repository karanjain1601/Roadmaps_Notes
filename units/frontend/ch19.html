CHAPTER 19

Components, state and routing

Frameworks give you components and a way to hold state. They do not tell you where a piece of state belongs, and that single decision — repeated a few hundred times — is what makes an application pleasant or miserable to work in. This chapter is a taxonomy, a placement rule, and the routing layer that ties it together.

Part 5 Building applications·Reading time 50 minutes·Demos state placement, router and history·Prerequisites Chapters 6, 16, 18

1Component boundaries

A good boundary is not "about 100 lines". It is a seam that the next change is likely to respect.

Split on responsibility, not on length
A 300-line form component doing one coherent job is fine. Three 40-line components that must always change together are worse, because now the change is spread across three files and a props interface.
Props down, events up
Data flows in through props, intent flows out through callbacks or events. A child that reaches upwards — mutating a prop, writing to a shared object it did not own — is the point at which a codebase becomes hard to reason about.
Prefer composition to configuration
When a component has grown seven boolean flags, the flags are describing structural variants. Accept children or slots instead: <Card><Card.Header/><Card.Body/></Card> scales; <Card hasHeader hasFooter compact bordered …> does not.
Separate the thing from its data
A presentational <UserCard user={…}/> that renders whatever it is given is reusable, testable and storybook-able. The same component fetching its own user by id is none of those. Put the fetching in a container, or a route loader, one level up.
Extract behaviour, not just markup
Hooks, composables and stores let you share logic without sharing a DOM shape. Two components that need the same debounced search behaviour should share a hook, not a wrapper component that renders both.
Prop drilling is a symptom, not the disease

Passing a value through four components that do not use it is annoying, and the usual reaction — put it in context, or in a global store — often makes things worse by turning a visible dependency into an invisible one. Check the other fixes first: pass the rendered element as children so the intermediate layers never see the data; move the state closer to where it is used; or colocate the fetch with the consumer. Reach for context when a value is genuinely ambient — theme, locale, the current user, a router.

2Six kinds of state

The most useful idea in this chapter: "state management" is six different problems, and most of them are not the one people reach for a library to solve.

KindExamplesWhere it belongs
Local UIIs this menu open, which tab is active, hover stateIn the component. Never anywhere else.
Shared UISidebar collapsed, theme, a toast queueLifted to the nearest common ancestor, or a small store.
Server cacheThe product list, the current user, search resultsNot state at all — a cache of someone else's data. Section 4.
URLCurrent route, filters, sort, page, an open detail idIn the address bar. Section 5.
FormField values, dirty flags, validation errorsIn the form, or in the DOM itself. Section 6.
SessionAuth tokens, a draft the user should not loseStorage plus a small store, hydrated once at start-up.

The historic mess — enormous Redux stores holding fetched entities — came from treating rows 3 and 4 as if they were rows 1 and 2. Once server cache moves to a query library and URL state moves to the URL, what is left for a global store is usually small enough to be unremarkable.

Where should this state live? Four questions. The recommendation is derived, with its reasoning.

3Local and shared state

Start at the bottom. Lift only when you must, and only as far as you must.

The placement rule
Put state in the lowest component that needs it. When two siblings need it, lift it to their nearest common parent — not to the root, and not to a global store. Every level you lift it costs re-renders in the virtual DOM models from Chapter 18 and makes the component harder to reuse.
When to use a reducer
When several fields change together, or the next value depends on the previous one in non-trivial ways. A reducer moves the transitions into one testable function and gives every change a name, which pays for itself the first time you have to debug an ordering bug. For anything with genuinely complex transitions, a state machine (XState and similar) makes the illegal transitions impossible rather than merely unlikely.
Context is a delivery mechanism, not a store
It solves "how does this value reach a deep component", not "how is this value managed". In React, every consumer re-renders when the provider's value changes, and passing a fresh object literal makes that every render. Split contexts by update frequency, memoise the value, and keep rapidly changing data out of context entirely.
External stores
Zustand, Jotai, Nanostores, Pinia, NgRx, Svelte stores. Their real advantage over context is selector-based subscription: a component subscribes to one slice and re-renders only when that slice changes, instead of when anything in the store changes. Choose one for shared UI and session state; do not put server data in it.
Keep it serialisable
Plain data — no class instances, no DOM nodes, no functions. It makes state easy to log, persist, time-travel and send to a worker, and it removes a whole family of "why is this undefined after a reload" bugs.

4Server state is a cache

The single most useful reframing available. Everything awkward about it follows from one fact: you do not own the data.

Client state is owned by the client and is always correct by definition. Server data is a copy that was accurate at the moment it arrived and may already be wrong — someone else edited it, another tab changed it, the request failed halfway. Treating it as ordinary state means hand-writing loading flags, error flags, staleness handling, refetch triggers and race protection in every component that touches it.

ProblemWhat a query library gives you
Three components ask for the same thingDeduplication by key — one request, three consumers (Chapter 16)
Data goes staleConfigurable staleness, refetch on window focus, on reconnect, on interval
Loading and error statesA status per query, so components branch on a discriminated union rather than three booleans
Responses arriving out of orderCancellation and last-write-wins by key
Showing something immediatelyServe the cached value, revalidate in the background
Mutations invalidating readsKey-based invalidation, plus optimistic updates with automatic rollback
Pagination and infinite listsCursor handling and previous-page retention while the next loads
An optimistic update, with the rollback that makes it safe pseudo-code
mutate(toggleFavourite, {
  // 1. Cancel in-flight reads so they cannot overwrite our guess
  onMutate(next) {
    cancelQueries(['product', id]);
    const previous = getQueryData(['product', id]);
    setQueryData(['product', id], { ...previous, favourite: next });
    return { previous };            // 2. keep the old value
  },
  // 3. Put it back if the server disagreed
  onError(err, next, ctx) { setQueryData(['product', id], ctx.previous); },
  // 4. Either way, reconcile with the truth
  onSettled() { invalidateQueries(['product', id]); }
});

// Skipping step 1 is the classic bug: a read that was already in flight
// lands after your optimistic write and reverts the UI for two seconds.

5The URL is state

The most under-used store in the browser, and the only one users can email to a colleague.

Filters, sort order, page number, an open detail panel, a selected tab: if a user would reasonably expect to bookmark it, share it, or get back to it with the back button, it belongs in the URL. This is not a nicety — it is the difference between "here is the report" and "click Reports, then set the date range to last quarter, then filter by region…".

Put in the URLKeep out of the URL
Route, entity ids, filters, sort, page, search query, a selected tab worth linking to, an open modal that represents a resource Transient UI (hover, a dropdown's open state), anything sensitive, large blobs, and high-frequency values such as a scroll position or a drag in progress
URL state and the back button A real history stack, simulated safely. Watch what push and replace do differently.

History stack

    pushState or replaceState?
    Push for anything the user would expect the back button to undo — a navigation, applying a filter set, opening a detail view. Replace for continuous or throwaway changes: every keystroke in a search box, otherwise one search fills the history with twelve entries and back becomes unusable.
    Parse defensively
    Query strings are user input. ?page=-4&sort=;drop will arrive eventually. Validate with the same schema approach as Chapter 17, and fall back to defaults rather than crashing.
    Scroll restoration
    Set history.scrollRestoration = 'manual' and handle it yourself: scroll to top on a forward navigation, restore the saved position on a back navigation. Most routers do this; verify it, because getting it wrong is very noticeable on a long list.

    6Forms inside components

    Chapter 5 covered the platform. This is the framework layer on top.

    ApproachHow it worksTrade-off
    Controlled Component state is the source of truth; every keystroke sets state and re-renders Full control — live validation, formatting, dependent fields. Costs a render per keystroke, which on a large form is felt.
    Uncontrolled The DOM holds the value; you read it on submit with FormData Fast and simple, and it keeps working when JavaScript fails. Harder to do cross-field logic.
    Form library Uncontrolled inputs registered with a library that subscribes only where needed The usual answer for anything non-trivial: performance of uncontrolled, ergonomics of controlled.
    Server actions The form posts to a server function; the framework handles the round trip and pending state Least client code, and it degrades to a native form submit. Ties you to a meta-framework — Chapter 21.
    Validate in one place
    Define the schema once and use it for client validation, server validation and the TypeScript type (Chapter 17). Two hand-maintained copies of the rules will disagree, and the disagreement will be discovered by a user.
    Do not reimplement the platform
    Keep the <form>, keep <label>, keep real input types and autocomplete. A framework form that renders divs loses password managers, autofill, Enter-to-submit and the accessible name — all of Chapter 5, thrown away for no gain.
    Pending and error states are part of the form
    Disable submit while in flight, keep the user's input on failure, announce the result in a live region (Chapter 6), and move focus to the error summary.

    7Routing

    Mapping a URL to a view, plus five obligations that come with taking over navigation from the browser.

    Nested routes and layouts
    /settings/billing renders the app shell, inside it the settings layout, inside that the billing panel. Nesting means a navigation between siblings re-renders only the innermost part, and shared layout state — a scroll position, an open section — survives.
    Loaders and route-level data
    Declaring a route's data requirements alongside the route lets the router fetch in parallel with loading the code, instead of the waterfall you get when each component fetches after it mounts. This is the largest single performance difference between routers.
    Code splitting per route
    Lazy-load each route's bundle so the initial download is one screen, not the whole application. Prefetch on hover or on link visibility so the click still feels instant. Chapter 23.
    Pending and error boundaries
    Every route needs a defined loading state and a defined error state. Without them a failed loader shows a blank page and a slow one shows the old page frozen with no feedback.
    Hash routing
    Only when you cannot configure the server to serve index.html for unknown paths. Everything after # is never sent to the server, so it is invisible to crawlers and to server rendering — Chapter 7.
    The five things a client-side navigation must do that a browser did for free

    1. Update document.title. 2. Move focus to the new view's heading, given tabindex="-1" — without this a screen-reader user gets no signal that anything happened. 3. Announce the new page politely in a live region. 4. Reset scroll on forward navigation and restore it on back. 5. Cancel in-flight requests belonging to the view you just left. Routers vary in how many of these they handle; assume none and verify each. Chapter 6 covers why 2 and 3 are not optional.

    8Derived state, and when not to use an effect

    More state bugs come from unnecessary effects than from any other single cause.

    Four things people write effects for that need no effect pseudo-code
    // ✗ 1. Deriving a value into state
const [total, setTotal] = useState(0);
useEffect(() => setTotal(items.reduce(sum)), [items]);
// ✓ Just compute it. It cannot go stale and there is no extra render.
const total = items.reduce(sum);

// ✗ 2. Resetting state when a prop changes
useEffect(() => setDraft(''), [userId]);
// ✓ Change the component's identity instead; the framework discards
//   the old instance and its state entirely.
<Editor key={userId} />

// ✗ 3. Responding to a user event
useEffect(() => { if (submitted) postForm(); }, [submitted]);
// ✓ Do it in the handler. The event already happened; you know when.
function onSubmit() { postForm(); }

// ✗ 4. Fetching on mount, by hand
useEffect(() => { fetch(url).then(setData); }, [url]);
// ✓ Missing: cancellation, race protection, error state, caching,
//   refetch, and a StrictMode double-invoke guard. Use a query library
//   or a route loader — this is section 4's whole argument.
    What effects are actually for
    Synchronising with something outside the framework: a subscription, a timer, a non-framework widget, an imperative browser API, an analytics call. If the code is not talking to the outside world, it probably belongs in render or in an event handler.
    Always clean up
    Return the teardown. One AbortController per effect — Chapter 14 — removes listeners, cancels fetches and disconnects observers in one call, and it is the only version that cannot be partially forgotten.
    Derived state duplicates the truth
    The moment the same fact exists in two places, they can disagree. Compute, memoise if it is genuinely expensive, and store only what cannot be derived.

    9Check yourself

    Six questions.

    1. Why is fetched data not really "application state"?

    Because you do not own it. Client state is correct by definition — if the sidebar flag says open, the sidebar is open. Fetched data is a cached copy of something another system owns, which was true when it arrived and may be wrong now: another user edited it, another tab changed it, the request half-failed. That difference generates all the machinery — staleness, revalidation, deduplication, invalidation, optimistic updates with rollback — that has no analogue for client state. Treating it as ordinary state means writing that machinery by hand in every component, which is why query libraries exist and why global stores full of fetched entities aged so badly.

    2. A user filters a product list, then emails the link to a colleague, who sees the unfiltered list. What went wrong?

    The filter lives in component state instead of the URL. Anything a user would reasonably expect to bookmark, share or return to with the back button belongs in the query string: filters, sort, page, search term, an open detail view. Moving it there also fixes three other things at once — the back button starts working, a page refresh keeps the view, and the state survives being restored from history. The exceptions are transient UI, sensitive values and anything high-frequency, which would flood the history.

    3. What is wrong with useEffect(() => setFullName(first + ' ' + last), [first, last])?

    It stores something derivable, which creates a second source of truth that can disagree with the first, and it costs an extra render every time — the component renders with the stale name, the effect runs, state is set, it renders again. Just compute it: const fullName = first + ' ' + last. It cannot be stale, needs no dependency array, and does no extra work. If the derivation were genuinely expensive, memoise it; storing it in state is still the wrong answer.

    4. A colleague puts the current user, the theme and a live scroll position in one context. What breaks?

    Every consumer of that context re-renders whenever any of the three changes — and the scroll position changes many times per second, so the whole subtree re-renders continuously. Context has no selector: subscribing means subscribing to the entire value. Fixes, in order: take the scroll position out of context entirely, since it is transient UI that belongs to whoever needs it; split the remaining values into separate contexts by update frequency; memoise each provider value so a new object literal is not created on every render; or use an external store with selector-based subscription, which is the feature context lacks.

    5. Your optimistic update flickers back to the old value for about a second before settling correctly. Why?

    A read that was already in flight when you wrote optimistically landed afterwards and overwrote your guess with pre-mutation data — then the invalidation refetch corrected it again, producing the flicker. The fix is the first step of the optimistic pattern: cancel outstanding queries for that key before writing the optimistic value, so nothing stale can arrive after it. Keep the snapshot for rollback on error, and invalidate on settle regardless of outcome.

    6. What must a client-side route change do that a full page load did automatically?

    Five things. Update document.title, since the tab and the history entry are otherwise wrong. Move focus to the new view's heading — without a page load there is no focus reset, so focus stays on the link that no longer exists, and a screen-reader user receives no signal at all. Announce the new page in a polite live region. Handle scroll: top on forward navigation, restored position on back. And cancel requests belonging to the view being left, or their responses will render into a screen the user has moved on from. Routers handle some of these; assume none and check each one with the keyboard and a screen reader.
