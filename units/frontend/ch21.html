Rendering strategies

Where should the HTML be built — at build time, on a server per request, at the edge, or in the browser? It is the highest-leverage architectural decision in a front end, it is usually made once by accident, and the right answer is almost always "different answers for different routes".

1Four places rendering can happen

Everything in this chapter is a combination of these, plus who finishes the job.

WhereWhenConsequence
Build timeOnce, before deployFastest possible response — it is a file on a CDN. Content is as fresh as the last build.
Origin serverPer requestAlways fresh, personalised, but every request costs server time and the user waits for it.
EdgePer request, near the userServer rendering with the latency of a CDN. Constrained runtime — no long-running work, limited APIs.
BrowserAfter the bundle loadsCheapest for you, most expensive for the user, and invisible to anything that does not run JavaScript.

Two questions decide which applies to a given page. How fresh must this be? — build time is impossible for a stock price and wasteful for a blog post. Who is it for? — anything personalised cannot be a shared cached file.

2The strategies

Five names, and the acronyms are less interesting than the timelines.

CSR — client-side rendering
The server sends an almost empty shell plus a script tag. The browser downloads the bundle, runs it, fetches data, then renders. Simple to deploy — static hosting, no server. The costs are all on the critical path: nothing is visible until the JavaScript has downloaded and executed, and Chapter 7's crawler and preview problems all apply.
SSR — server-side rendering
The server runs the components per request and sends complete HTML. First paint no longer waits for JavaScript. Then the same components run again in the browser to attach event handlers — hydration, section 3. Fresh and personalised, at the cost of server compute and a TTFB that includes your data fetching.
SSG — static site generation
The same rendering, done once at build time, producing files. The best possible TTFB and trivially cacheable. Unusable when content changes more often than you can deploy, or when the page differs per user. Build time also grows with page count, which becomes real at tens of thousands of pages.
ISR — incremental static regeneration
Static files with a staleness policy: serve the cached page instantly, regenerate it in the background after n seconds or when a webhook says the content changed. It is Chapter 2's stale-while-revalidate applied to whole pages, and it covers the large middle ground where content is mostly static but not deploy-static.
Streaming SSR
Rather than building the whole page and then sending it, the server flushes the shell immediately and streams each slower section as its data resolves. The user sees the header and layout in a few hundred milliseconds while the personalised panel is still being fetched. This is what makes SSR viable when one part of a page is slow.

3Hydration, and why it is the expensive part

Server rendering gives you pixels early and interactivity late. The gap between them is the whole problem.

Server-rendered HTML is inert: the markup is right, but no event handler is attached and no component state exists. Hydration is the browser re-running the same component tree, building the framework's internal representation, and wiring it to the existing DOM. Which means the work is done twice — once on the server to produce HTML, once in the browser to produce behaviour.

The uncanny valley

Between first paint and the end of hydration, the page looks completely finished and responds to nothing. Users click, and the click is discarded — no visual feedback, no queued action. It is worse than a visible spinner, because a spinner sets expectations. On a cheap phone with a large bundle this window can last several seconds, and it is measured as poor Interaction to Next Paint (Chapter 26).

4Islands and server components

Two different answers to the same observation: most of a page is not interactive.

The islands model
Render everything to HTML. Mark the few components that genuinely need behaviour — a search box, a carousel, an add-to-cart button — and ship JavaScript only for those, each hydrating independently. The rest is HTML that never becomes a component again. On a typical content page this removes 80–95% of the bundle. The constraint is that islands cannot share client state easily, since they are separate roots; you coordinate through props, the URL, or a tiny shared store.
Server components
A component that runs only on the server. It can query a database directly, use a large Markdown or date library, and read secrets — and none of that code is sent to the browser. It renders to a serialised description that the client merges into its tree. Client components are opted into explicitly, and can be nested inside server ones. The mental shift is that the network boundary is now inside your component tree rather than at an API call, which is powerful and takes a while to internalise.
How they differ
Islands are a build-time partition into interactive and non-interactive, and work with any framework. Server components are a runtime partition that streams and can re-render on the server after a mutation, keeping data-fetching code on the server permanently. Islands are simpler; server components compose better with dynamic data.
What both fix
The same thing: shipping the code for a static product description, a footer and a formatted date to every visitor so it can be executed a second time to produce markup that was already correct.

5Deciding per route

The important idea in this chapter. There is no project-wide answer.

RouteStrategyReasoning
Marketing and landing pagesSSGIdentical for everyone, changes on a content schedule, and needs the best possible load. Often needs no client JavaScript at all.
Blog and documentationSSG, or ISR at volumeSame, plus Chapter 7's indexing requirements.
Product listings and detailISR or streaming SSRMust be indexable and shareable; prices and stock change, but not per user. Regenerate on a webhook from the CMS or catalogue.
Search resultsSSRParameter-driven and effectively infinite, so nothing to pre-build. Server-render the first page so it is indexable and fast, paginate on the client.
Authenticated dashboardCSR behind a server-rendered shellPersonal, private, noindex. The app-like interactivity is the point and the SEO argument does not apply.
CheckoutSSR, minimal client codeCorrectness and reliability outrank everything. Server-validated, works with a flaky connection, degrades to form posts.
Admin toolsCSRSmall audience on good hardware; developer velocity is the right thing to optimise.
Start static, add dynamism where required

The cheapest architecture that meets the requirement is almost always the right one, and the default should be the most static option a route can tolerate. Going from SSG to ISR to SSR is a small change in every meta-framework; going from a full client app back to static is a rewrite. Note also that a genuinely static content site needs no framework at all — Chapter 12's stylesheet plus a little progressive enhancement will beat any of this, and that option deserves to be considered rather than assumed away.

Caching, which changes all of it

CDN page cache
The layer with the largest effect. A cached page has the TTFB of SSG regardless of how it was produced. Chapter 2's s-maxage and stale-while-revalidate are the mechanism, and getting the cache key right — no cookie-driven Vary — is what makes it work.
Data cache
Between your server rendering and your database or API. Turns a 220 ms query into a 3 ms lookup, which is often the difference between SSR being viable and not.
Client router cache
After the first load, subsequent navigations fetch only the new route's data. This is why an SSR application can feel like a single-page app once it is running, and why prefetching links on hover matters so much.

8Check yourself

Six questions, closing Part 5.

1. Your team server-renders everything and Lighthouse still reports poor interactivity. How is that possible when the HTML arrives complete?

Because SSR fixes first paint, not interactivity. The HTML is inert until hydration re-runs the component tree in the browser and attaches handlers, and that work is proportional to the bundle and the page size, on the user's CPU. Between paint and the end of hydration the page looks finished and ignores every click — which is measured as poor Interaction to Next Paint and feels worse than a visible loading state. The fixes are to hydrate less (islands or server components), to hydrate later and progressively, or to ship less JavaScript in the first place.

2. When is SSG impossible, and what is the nearest thing that works?

Two cases. When the page is personalised — a dashboard, a basket, anything showing "your" anything — because a static file is shared by every visitor. And when content changes more often than you can rebuild, or there are too many pages to build at all. For the second case ISR is the answer: serve the static file instantly and regenerate it in the background on a timer or a webhook, which covers the large middle ground of catalogues and news. For the first, server-render the shell and fetch the personal parts on the client, or stream them, so the shared part is still cacheable.

3. What is the practical difference between islands and React Server Components?

Both stop shipping JavaScript for non-interactive parts of the page, but at different times and with different composition. Islands are a build-time partition: you mark components as interactive, they hydrate as independent roots, and everything else is permanently HTML — simple, framework-agnostic, and awkward when two islands need to share state. Server components are a runtime partition inside one tree: they render on the server, never send their code, can be nested with client components, stream progressively, and can re-render on the server after a mutation. Islands are the simpler model for content sites; server components compose better when the data is dynamic.

4. Your SSR site has a 900 ms TTFB. Where do you look first?

At the data fetching inside the render, because with SSR the user's TTFB includes everything your server does before the first byte — every database query and every upstream API call, serialised if they are awaited one after another (Chapter 15). Three fixes in order: parallelise independent fetches with Promise.all; add a data cache so repeat renders are not repeat queries; and switch to streaming so the shell flushes immediately and the slow section arrives later. If the content is not personalised, a CDN page cache removes the problem entirely for everyone after the first visitor.

5. Is it reasonable to use different strategies for different routes in one application?

It is the recommended approach, and every current meta-framework supports it per route. The requirements genuinely differ: a marketing page needs to be indexable and instant and has no personalisation, while a dashboard is private, needs no SEO, and benefits from client-side interactivity. Forcing one strategy across both means one of them is wrong. The practical guidance is to default each route to the most static option it can tolerate and move it only when a requirement forces you — the direction from static towards dynamic is a configuration change, while the reverse is usually a rewrite.

6. A colleague proposes moving a documentation site from a static generator to a full SSR application "so it feels modern". What is the argument against?

It makes every metric worse for no gain. Documentation is identical for every reader and changes when someone commits, which is exactly the profile SSG exists for: files on a CDN, best possible TTFB, no server to run, scale and cost effectively free. SSR adds per-request compute, a TTFB that includes rendering, an operational surface to keep alive, and — if it hydrates — a bundle and an interactivity gap that the static version did not have. The honest version of the request is usually about client-side navigation and a search box, both of which can be added to a static site as islands without giving up any of its advantages.
