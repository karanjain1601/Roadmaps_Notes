Linting, formatting and Git

The unglamorous layer that decides whether a codebase stays changeable. Automated checks so that review is about design rather than semicolons, and a version-control practice that lets six people work on one thing without standing on each other.

Part 6 The toolchain·Reading time 45 minutes·Demos merge strategies, commit linter·Prerequisites none

1Formatter and linter are different tools

Confusing them produces a config that fights itself and a review process that argues about commas.

FormatterLinter
QuestionHow should this look?Is this correct?
ExamplesQuote style, indentation, line width, trailing commasUnused variables, missing await, a click handler on a div, an unreachable branch
OpinionsNone worth having. Pick a default and never discuss it againMany, and each should be a deliberate choice
On saveAlwaysShow inline; auto-fix only the safe rules
ToolsPrettier; Biome; dprintESLint; Biome; oxlint

The key configuration rule: turn off every stylistic rule in your linter. ESLint's formatting rules were deprecated precisely because they duplicate the formatter and then disagree with it. eslint-config-prettier exists to disable them in one line.

The point of a formatter is that it ends the discussion

Not that its output is optimal — sometimes it is worse than what you would have written. The value is that nobody spends attention on it, diffs contain only real changes, and code review never mentions whitespace. Adopt it in one commit across the whole repository, add that commit's hash to .git-blame-ignore-revs so git blame skips it, and move on.

The newer Rust-based tools — Biome, which does both jobs, and oxlint — are ten to a hundred times faster and increasingly complete. ESLint retains the larger plugin ecosystem, which is what most teams stay for, particularly the type-aware and accessibility rules below.

2Linting in practice

Which rules actually earn their noise.

Flat config, with the plugins that matter eslint.config.js
import js from '@eslint/js';
import ts from 'typescript-eslint';
import a11y from 'eslint-plugin-jsx-a11y';
import prettier from 'eslint-config-prettier';

export default [
  js.configs.recommended,
  ...ts.configs.recommendedTypeChecked,   // needs a tsconfig; slower, far better
  a11y.flatConfigs.recommended,
  {
    rules: {
      'no-console': ['warn', { allow: ['warn', 'error'] }],
      '@typescript-eslint/no-floating-promises': 'error',
      '@typescript-eslint/no-misused-promises': 'error',
      '@typescript-eslint/consistent-type-imports': 'error'
    }
  },
  prettier   // LAST — disables every stylistic rule the formatter owns
];
Rule or pluginCatches
no-floating-promisesAn async call whose result and errors are discarded. The highest-value type-aware rule there is — Chapter 15.
no-misused-promisesAn async function passed where a synchronous one is expected, such as a forEach callback that silently does not wait.
eslint-plugin-jsx-a11yMissing alt, click handlers on non-interactive elements, invalid ARIA. Chapter 6's automated slice.
react-hooksConditional hooks and missing effect dependencies. Not optional if you use React.
eslint-plugin-importUnresolvable imports, cycles, and a consistent import order.
no-restricted-importsYour own architectural rules — "no importing from another feature's internals", "use the wrapper, not the raw client".
exhaustive-deps, no-unused-varsThe everyday ones. Configure no-unused-vars to allow a leading underscore for deliberate placeholders.
Type-aware rules cost time and are worth it
recommendedTypeChecked requires the type checker to run, so linting is slower. In exchange it catches an entire class of bug that syntax-only rules cannot see. Run the fast rules on save and the full set in CI if the latency hurts.
Disable a rule properly
// eslint-disable-next-line rule-name — reason. Never a bare file-level disable, never without naming the rule, never without the reason. A disable comment is a decision, and decisions get reviewed.
Warnings rot
A codebase with 340 warnings has zero warnings, because nobody reads them. Either make a rule an error or delete it. --max-warnings=0 in CI enforces that honestly.

3Three gates, three purposes

The same check in the wrong place is either useless or infuriating.

GateRunsPurpose, and what belongs here
Editor As you type / on save Feedback. Format on save, lint inline, type errors underlined. Nothing blocking.
Pre-commit Before the commit lands, on changed files only Hygiene. Format and auto-fix the staged files with lint-staged. Must take under a couple of seconds.
CI On every push and pull request The real gate. Full lint, type check, tests, build, bundle budget. This is the only one that cannot be skipped.
Do not put the test suite in a pre-commit hook

Hooks that take thirty seconds get bypassed with --no-verify within a week, and then none of your hooks run. Keep pre-commit to formatting and auto-fixing the staged files. Everything slow belongs in CI, where it runs on a machine that is not the one someone is trying to think on. A pre-push hook running a fast subset is a reasonable middle ground.

A pre-commit setup that people do not disable package.json
{
  "lint-staged": {
    "*.{js,ts,tsx,css,md,json}": "prettier --write",
    "*.{js,ts,tsx}": "eslint --fix --max-warnings=0"
  }
}
// Hook manager: husky, lefthook or simple-git-hooks.
// Runs only on STAGED files, so cost is proportional to the change.

4Git's actual mental model

Four sentences that make every command make sense.

A commit is a snapshot, not a diff
Each commit records the complete state of the tree plus a pointer to its parent. Diffs are computed between snapshots when you ask for them. This is why checking out an old commit is instant and why history is cheap.
A branch is a movable pointer to a commit
That is all it is — a file containing a hash. Creating a branch is free; deleting one deletes no commits.
There are three places a file can be
The working tree (your files), the index or staging area (what will go in the next commit), and the repository (committed). git add moves working tree → index; git commit moves index → repository. Almost all Git confusion is confusion about which of the three you are addressing.
Almost nothing is lost
Commits persist even when no branch points at them, and git reflog records every position HEAD has held. Section 8.
CommandWhat it does
git switch -c feat/xNew branch from here. Clearer than the overloaded checkout.
git add -pStage hunk by hunk. The single best habit for producing focused commits — it forces you to read your own change.
git commit --amendRewrite the last commit. Safe before pushing; a force-push after.
git rebase -i mainReplay your commits on top of main, reordering, squashing or editing them.
git restore --staged fUnstage without touching the file.
git log --oneline --graphThe history as a shape. Add --all to see every branch.
git push --force-with-leaseForce-push that refuses if someone else pushed since you last fetched. Always this, never plain --force.

The golden rule of rebasing
Never rebase commits that other people have pulled. Rebasing rewrites hashes, so anyone who has the old commits now has a divergent history and their next pull produces a mess. Rebasing your own unpushed or unshared branch is entirely safe and is how you keep a feature branch current.
Trunk-based development
Short-lived branches — hours to a couple of days — merged into main frequently, with anything incomplete hidden behind a feature flag. It is what makes continuous delivery possible and it dramatically reduces merge pain, because branches never diverge far enough to conflict badly.
Git Flow
Long-lived develop, release and hotfix branches. Designed for versioned software with scheduled releases; almost always overkill for a continuously deployed web application, where it mainly generates merge conflicts and confusion about where a fix should go.
Atomic commits
One logical change per commit, each leaving the build green. It makes git bisect useful, makes reverting precise, and makes review possible commit by commit. git add -p and interactive rebase are how you get there from a messy afternoon.

Commit messages

Conventional commit linter Real parsing, with the release impact the message implies.

    Conventional Commits is not the only good convention, and a team that writes clear plain-English subjects is fine. What it buys is machine readability: automated changelogs, automated semver bumps, and a release pipeline that does not need a human to decide whether something was a breaking change.

    6Reviewable changes

    Review quality falls off a cliff with size. Everything here follows from that.

    Small
    Under about 400 lines is where reviewers still find defects; beyond roughly 1,000 they skim and approve. If a change is genuinely large, split it: a refactor commit that changes no behaviour, then the behaviour change. Reviewers can verify the first mechanically and concentrate on the second.
    Separate the mechanical from the meaningful
    A rename touching 60 files and a logic change in one file should never be the same pull request. The logic change becomes invisible.
    Write the description for someone who was not there
    What problem, what approach, what alternatives were rejected, what to look at first, and how to verify. A screenshot or a short recording for anything visual.
    Self-review first
    Read your own diff in the review interface before requesting anyone else. You will find the leftover console.log, the commented-out block and the accidentally committed file — and you will re-read the change as a reader rather than an author.
    What a reviewer is actually for
    Correctness, edge cases, security, accessibility, naming, and whether this is the right shape. Not formatting — that is section 1's job — and not personal style preferences. A useful convention is to prefix optional remarks with "nit:" so the author knows what blocks and what does not.

    7CI that fails for the right reasons

    A pipeline people trust is one that is fast, deterministic, and never red for reasons unrelated to the change.

    A pipeline shape that scales CI
    install  →  ┌ lint          ┐
             ├ typecheck     │  in parallel, all cheap
             ├ unit tests    │
             └ build         ┘
                    ↓
             ┌ e2e tests     ┐  slower, needs the build
             └ bundle budget ┘
                    ↓
                  deploy

# The three things that make it fast:
#   1. Cache node_modules keyed on the lockfile hash
#   2. Run independent jobs in parallel, not in one long script
#   3. On a monorepo, only run tasks for packages that changed
    Required checks and branch protection
    Make main unpushable directly, require the checks to pass, and require the branch to be current before merging. Merge queues do the last part without forcing everyone to rebase manually.
    Flaky tests destroy the value of the whole suite
    Once people learn that red sometimes means nothing, they re-run instead of reading. Quarantine a flaky test the day it is noticed — skip it, open a ticket, fix or delete it — rather than letting it erode trust. Chapter 25 covers the usual causes.
    Fail fast, report clearly
    Surface the actual failing assertion at the top of the log, not on line 4,000. Annotations on the pull request diff are better still.
    Run the same commands locally
    If CI runs something a developer cannot reproduce with one npm script, the feedback loop is broken. npm run verify should do exactly what CI does.

    8Rescue commands

    Six commands worth knowing before you need them at 6pm on a Friday.

    SituationCommand
    I destroyed something and do not know how to get it backgit reflog, find the hash, git reset --hard <hash>. Reflog records every position HEAD has held, including ones no branch points at. This recovers almost anything committed in the last 90 days.
    I need to undo a commit that is already pushedgit revert <hash> — a new commit that inverts it. Never reset shared history.
    I need to undo local commitsgit reset --soft HEAD~2 keeps the changes staged; --mixed keeps them in the working tree; --hard discards them.
    I committed to the wrong branchgit cherry-pick <hash> onto the right one, then reset the wrong one.
    I need to switch branches with work in progressgit stash push -m "wip", then git stash pop. Or git worktree add, which gives you a second checkout in another directory and avoids stashing entirely.
    Something broke and I do not know which commitgit bisect start, mark a good and a bad commit, and Git binary-searches. With a script, git bisect run ./test.sh finds it unattended.
    One habit that prevents most disasters

    Commit early and often on your own branch, however messy. Unfinished work in a commit is recoverable; unfinished work in a working tree is one git checkout . away from gone. You can always tidy the history afterwards with an interactive rebase — the tidying is cheap, and the recovery is impossible.

    9Check yourself

    Six questions.

    1. Your linter and formatter disagree and fight on every save. What is the configuration mistake?

    Stylistic rules are still enabled in the linter. They duplicate the formatter's job and then reach different conclusions, so each tool undoes the other. The fix is eslint-config-prettier — or the equivalent — placed last in the config array so it switches every formatting rule off, leaving the linter to do correctness only. ESLint deprecated its own formatting rules for exactly this reason. The general principle: exactly one tool owns each concern.

    2. When is rebasing dangerous, and why?

    When the commits have already been pulled by someone else. Rebasing replays commits onto a new base, which produces new commits with new hashes — the originals still exist but nothing points at them. A colleague who has the old hashes now has a history that diverges from yours, and their next pull either creates a confusing merge or duplicates every commit. On your own unshared branch it is completely safe and is the normal way to stay current with main. If you must force-push a shared branch, use --force-with-lease, which aborts if someone else has pushed since your last fetch.

    3. What is the difference between squash-merging and rebase-merging a five-commit branch?

    Squash collapses all five into a single new commit on main, so main gains one commit and the individual steps are gone — clean, linear history, and a revert is one command, at the cost of losing the granularity that makes git bisect precise. Rebase-and-merge replays all five onto main as five separate commits, keeping the individual steps and a linear history, but there is no single commit representing the feature and reverting means reverting a range. Squash suits branches whose intermediate commits are working notes; rebase suits branches where each commit is a deliberate, self-contained step.

    4. Why should the test suite not run in a pre-commit hook?

    Because of what happens next. A hook that adds thirty seconds to every commit teaches people to use --no-verify, and once that is habitual none of your hooks run — including the fast, valuable ones. Worse, it discourages committing frequently, which is the habit that makes work recoverable. Pre-commit should be formatting and auto-fixing staged files, measured in low single-digit seconds. The full suite belongs in CI, which cannot be bypassed and runs on a machine nobody is waiting on. A pre-push hook running a fast subset is a reasonable compromise if you want earlier feedback.

    5. A colleague opens a 2,400-line pull request. What is the concrete problem?

    It will be approved without being reviewed. Defect-detection rates fall sharply with size — reviewers stay effective to a few hundred lines and then start skimming — so the review provides the appearance of scrutiny with none of the substance. The practical response is to split it: separate any mechanical change (a rename, a move, a formatting pass) into its own commit or pull request that a reviewer can verify at a glance, then review the behavioural change on its own. If it genuinely cannot be split, ask for a walkthrough and review it commit by commit rather than as one diff.

    6. You hard-reset a branch and lost two hours of commits. Are they gone?

    Almost certainly not. A commit is not deleted when no branch points at it — it becomes unreachable, and unreachable objects survive until garbage collection, typically 90 days by default. git reflog lists every position HEAD has held, including the one before the reset, so you find the hash and git reset --hard back to it, or git branch rescue <hash> to be safer. The only work genuinely at risk is what was never committed at all, which is the argument for committing messy work-in-progress early and tidying the history later.
