CHAPTER 18

Reactivity: how frameworks differ

Every framework solves one problem: keep the DOM matching the state. There are only four mechanisms for doing it, and once you can name which one you are using, most framework-specific advice stops being folklore and becomes a consequence. This chapter compares by mechanism, not by syntax.

Part 5 Building applications·Reading time 50 minutes·Demos a working signal engine, re-render scope·Prerequisites Chapters 3, 13–14

1The problem

Not "rendering". Keeping two things in sync, forever, cheaply.

Rendering once is easy — Chapter 14's DOM API does it in a few lines. The difficulty is the second render and every one after it: something changed, and you need the DOM to reflect it without rebuilding the page, losing focus, resetting scroll, or dropping the text the user was halfway through typing.

Why hand-written synchronisation stops scaling JavaScript
// Every piece of state needs a hand-written update path to every
// place it appears. n states × m views = a lot of small functions
// that must all be remembered on every change.
function setCount(n) {
  state.count = n;
  countLabel.textContent = n;                       // 1
  badge.hidden = n === 0;                        // 2
  total.textContent = format(n * state.price);      // 3
  checkoutBtn.disabled = n === 0;                 // 4  …and the one
                                                    //    someone forgot
}

// The bug is always the same: state changed through a path that
// did not know about view #5. The DOM and the data disagree.

Frameworks make this declarative: you write what the UI should look like for a given state, and the framework works out the DOM operations. The whole design space is how it works those out.

2The four mechanisms

Two questions distinguish them: how does it know something changed, and how much does it re-examine?

These combine. Solid uses signals and compilation. Vue uses signals internally and a virtual DOM for the render output. Angular is migrating from dirty checking to signals. The interesting comparison is per-framework-version, not per-brand.

3Virtual DOM, in detail

The model most people learned first, and the one with the most widely misunderstood cost.

A render function returns a plain-object description of the UI — a tree of {type, props, children}. The framework compares the new tree with the previous one and applies the minimum set of real DOM operations. The virtual tree is cheap to build; touching the real DOM is not, which is the whole premise.

The reconciliation heuristics
A general tree-diff is O(n³), which is unusable, so every implementation uses the same two shortcuts. First, different element types produce a completely new subtree — changing a <div> to a <section> destroys and recreates everything inside, including component state and focus. Second, children are matched by key, or by position if no key is given.
Why keys matter so much
Without keys, item 3 of the old list is compared with item 3 of the new one. Delete the first item and every subsequent element is diffed against the wrong original: the framework patches text content down the whole list rather than removing one node, and any component state — an open menu, a half-typed input, a CSS transition — ends up attached to the wrong row. Using the array index as a key reproduces exactly this, which is why it is only safe for a list that never reorders, inserts or deletes.
The real cost is re-running render
The diff itself is fast. What is expensive is that a parent re-render re-runs every descendant's render function by default, building virtual trees for components whose output has not changed. On a large tree this is the dominant cost — and it is why React needs memo, useMemo and useCallback, which are opt-in fixes for a default that does too much.
"The virtual DOM is fast"
It is not, particularly. It is fast enough, and it buys a very good programming model: render as a pure function of state, with no manual update paths. Its competitors are faster at update time and give up some of that simplicity. Both statements are true at once.

4Signals

Track reads, so writes know precisely who cares. Fifty lines of principle, and the demo below is a real implementation.

A signal is a value with a subscriber list. The trick is that subscription is automatic: while a computation runs, a global "who is currently running" pointer is set, and every signal read during that window registers the computation as a dependency. No dependency arrays, no manual wiring — the graph is discovered by executing the code.

The entire idea, in about twenty lines JavaScript
let active = null;                     // the computation currently running

function signal(value) {
  const subs = new Set();
  return {
    get() {
      if (active) subs.add(active);    // ← the dependency is recorded HERE,
      return value;                   //   simply because it was read
    },
    set(next) {
      if (Object.is(next, value)) return;   // equal → nothing downstream runs
      value = next;
      [...subs].forEach(s => s.run());
    }
  };
}

function effect(fn) {
  const e = { run() { const prev = active; active = e; try { fn(); }
                     finally { active = prev; } } };
  e.run();                              // first run discovers the dependencies
}
A signal engine, running This is not a diagram — the code above is implemented on this page and the counts are real.

Computed values are lazy and cached
A computed is a signal that derives from others. It recomputes only when a dependency actually changed and something reads it — so an expensive derivation in a hidden panel costs nothing until the panel opens.
Equality checks stop propagation early
Setting a signal to its current value does nothing at all. And if a computed recomputes but produces an equal result, its own subscribers are not notified. Whole branches of the graph go quiet.
Glitch-free propagation
If an effect depends on two signals and both change, a naive implementation runs it twice, once with inconsistent intermediate data. Real implementations topologically sort the graph and batch, so each effect runs once per update with a consistent view.
Dependencies are dynamic
Because the graph is rebuilt on each run, show() ? a() : b() depends on a or b, not both — and switching branches re-wires automatically. This is precisely what React's dependency array cannot express, which is why it is a lint rule rather than a language feature.
The cost
Values are accessed through a function or a proxy rather than being plain variables, which is a syntactic tax. And a very large graph of tiny nodes has its own bookkeeping overhead; signals win decisively on targeted updates, not universally.

5Compilation

Do the analysis at build time and ship the answer instead of the machinery.

If a compiler can see which parts of a template depend on which pieces of state, it can emit direct DOM instructions and skip the runtime diffing entirely. Svelte pioneered this at scale; Solid's JSX compiles to the same kind of output over a signal graph; Vue Vapor is Vue's version.

Roughly what a compiler emits conceptual output
// You write:
//   <h1>Hello {name}</h1>
//   <p>You have {count} messages</p>

// It emits something along these lines:
const h1 = createElement('h1'), text1 = createTextNode('');
const p  = createElement('p'),  text2 = createTextNode('');

function update(changed) {
  if (changed & NAME)  text1.data = 'Hello ' + ctx.name;
  if (changed & COUNT) text2.data = 'You have ' + ctx.count + ' messages';
}

// No virtual tree. No diff. A bitmask and two direct assignments.
GainsCosts
Smaller runtime — much of the framework is not shipped at allYou cannot run the source directly; a build step is mandatory
Faster updates: no tree construction, no diffThe compiler must be able to see the dependency, so dynamic patterns can defeat it
Less code to write, because the compiler handles the wiringDebugging steps through generated code unless source maps are good

The bundle-size argument is more nuanced than it is usually stated: a compiled framework ships less runtime but more per-component code, so the advantage narrows as an application grows. It is still real, and it is largest for small-to-medium applications.

6The five, by mechanism

What each actually does, and the consequence you feel while writing code.

React
Virtual DOM. setState marks a component dirty; the component and, by default, all of its descendants re-render, and the results are diffed. Everything is a function that re-runs top to bottom, which is a very simple mental model — and it means every value is recreated on every render, hence useMemo, useCallback and memo. The React Compiler now inserts most of that memoisation automatically, which removes the largest ergonomic complaint. Hooks must run unconditionally and in the same order, because they are matched by call index.
Vue
Signals underneath, virtual DOM on top. ref and reactive track reads through proxies, so Vue knows which components depend on what and re-renders only those — no memoisation needed. Its compiler also marks static parts of a template so the diff skips them. The trade is proxy semantics: .value in script, automatic unwrapping in templates, and reactivity lost if you destructure a reactive object.
Angular
Historically dirty checking via Zone.js, which monkey-patches every async API so it can re-check the component tree after anything happens. Correct, and coarse. Modern Angular adds signal(), computed() and effect() plus zoneless change detection, moving it to the fine-grained model. In a current codebase you may meet both, which is worth knowing before debugging a performance problem.
Svelte
Compiled. Version 5 replaced the compiler's assignment-tracking with explicit runes — $state, $derived, $effect — which are signals with compiler support. That fixed the older model's main limitation: reactivity that only worked at the top level of a component and not in extracted helper modules.
Solid
Signals plus compilation, and the most consistent expression of the fine-grained idea. A component function runs once — it sets up the reactive graph and is never called again. Updates are individual DOM node mutations. This is why Solid's JSX looks like React's and behaves nothing like it: there is no re-render, so nothing recreates, so no memoisation exists. The catch is that destructuring props breaks reactivity, because it reads the value once at setup time.

7What this means for your code

Each mechanism generates its own class of bug. Here are both, by name.

If you are onThe bug you will hitBecause
Virtual DOM A child re-renders on every parent update, tanking a big list Re-render cascades by default; the fix is memoisation, or moving state down so the parent stops changing
An input loses focus, or the wrong row animates, after a delete Missing or index-based keys, so children were matched by position
A useEffect runs in an infinite loop An object or function in the dependency array is recreated every render, so it is never equal
Signals A value stops updating after you extract it into a variable Reading it once outside a tracked scope captures a snapshot; you must pass the signal, not its value
Destructuring props silently breaks reactivity Same cause: destructuring is a read at setup time
Dirty checking Mutating state outside the framework's zone changes nothing on screen The check never ran, because the framework did not know anything happened
Compiled An update fires for a plain assignment but not for arr.push() The compiler tracks assignments it can see; a mutating method call is invisible to it
Three rules that apply in every model

1. Keep state as low in the tree as it will go. State that lives above where it is used causes work everywhere below. This one habit removes more performance problems than any amount of memoisation.

2. Give lists stable keys from the data — an id, never the index, unless the list is genuinely append-only and static.

3. Do not mutate state in place. Signals compare with Object.is; virtual DOM implementations compare props by reference. Either way, a mutated array is the same object and the change is invisible. Chapter 13's copying section is the mechanism behind this.

8Choosing one

An honest guide, given that all five are good and none is a mistake.

SituationReasonable choice, and why
A team already knows oneThat one. Framework fluency is worth more than a benchmark difference nobody will measure.
Hiring is the constraintReact. The ecosystem and labour market are larger than the rest combined, and that is a legitimate engineering input.
Content-heavy site with islands of interactivityAstro with any of them, or plain HTML. Chapter 21 argues this properly — most "app" frameworks are the wrong tool for a marketing site.
An enterprise application with many teamsAngular, whose opinionated structure and batteries-included tooling are the point. Or React with a strict internal convention, which is the same idea with more work.

A pleasant middleVue: fine-grained updates without memoisation, a gentle learning curve and a coherent official ecosystem.

What matters more than the choice: the parts of Part 6 that are identical whichever you pick. Bundling, testing, accessibility, performance budgets and deployment do not care, and they are where most of the long-term cost lives.

9Check yourself

Six questions.

1. Why does React need useMemo and useCallback while Vue and Solid have no equivalent?

Because of the update granularity. React re-runs a component's entire function on every render, so every object, array and closure inside it is a new value — which then invalidates any child comparing props by reference, and any effect with that value in its dependency array. Memoisation manually preserves identity across renders. Vue tracks reads through proxies and re-renders only components that actually depend on the changed value, so identity across renders is not load-bearing. Solid goes further: a component function runs once, ever, so nothing is recreated and there is nothing to memoise. React's compiler now inserts most of this automatically, which is a fix for the symptom rather than a change of mechanism.

2. What actually goes wrong when you use the array index as a key?

Keys tell the reconciler which old element corresponds to which new one. With index keys, deleting the first item means old index 1 is matched with new index 1 — but those are different items, so instead of removing one node the framework patches the text of every subsequent node. Anything attached to the element rather than the data goes to the wrong row: input values, focus, open menus, running CSS transitions, uncontrolled component state. It is safe only when the list is never reordered, inserted into or deleted from — at which point the key is doing nothing anyway.

3. In a signal system, why does const n = count() at the top of a component break reactivity?

Because tracking happens at the moment of reading. Calling count() in the component body registers a dependency for whatever computation is running then — in Solid, that is the one-time setup — and stores the current number in n. From that point n is an ordinary number with no connection to the signal, so later writes update the graph but not your variable. The fix is to keep the read inside the reactive scope that consumes it: pass count itself, or read it inside the JSX expression, so the read happens in a tracked context each time. Destructuring props is the same bug wearing different clothes.

4. Is the virtual DOM faster than direct DOM manipulation?

No. Careful hand-written DOM updates are faster than any virtual DOM, and fine-grained signals get much closer to that floor. What the virtual DOM buys is a programming model: render as a pure function of state, with no manually maintained update paths and no risk of forgetting one. It is fast enough for most applications, and the abstraction is worth real cycles. The claim to be sceptical of is the marketing version — "faster because it batches DOM writes" — which conflates the diff with the batching, and batching is available to every approach.

5. A colleague adds memo() to a component and it still re-renders on every parent update. Why?

memo does a shallow comparison of props, and something being passed is a new reference each time — most often an inline arrow function (onClick={() => …}), an object literal (style={{…}}), or an array built during render. Any one of those defeats the comparison entirely. Fixes: wrap the callback in useCallback and the object in useMemo, hoist static values out of the component, or — usually better — restructure so the state causing the parent to re-render lives lower down, at which point no memoisation is needed at all.

6. In the signal demo, why does changing unreadCount not re-run the greeting effect?

Because the greeting effect never read unreadCount, so it was never added to that signal's subscriber set. Dependencies are discovered by execution: whatever a computation reads while it runs is what it subscribes to, and nothing else. That is the entire difference from the virtual DOM model, where a state change in a component re-runs the whole component regardless of which fields the output actually used. It is also why signals need no dependency array — the array is a manual approximation of information the runtime can simply observe.
