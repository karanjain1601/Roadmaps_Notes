CHAPTER 20

Web components

The platform has its own component model, and it is the only one that outlives your framework choice. It is also genuinely different — real style encapsulation, no re-render, attributes that are strings — and those differences are why it wins decisively in a few situations and loses in most of the others.

Part 5 Building applications·Reading time 45 minutes·Demos a live custom element, style penetration·Prerequisites Chapters 13–14, 18

1Four specifications, one idea

"Web components" is not one API. It is four that happen to compose.

Custom elements
Define your own tag names, backed by a class, with lifecycle callbacks the browser invokes. <stock-ticker symbol="ACME"> becomes as real to the DOM as <input>.
Shadow DOM
A separate DOM subtree attached to an element, with genuine style and query encapsulation. Not a convention — the browser enforces it.
<template>
Inert markup that is parsed but not rendered, cloned when needed. Chapter 4.
ES modules
The distribution mechanism. A component is a module that calls customElements.define() as a side effect of being imported.

Used together you get something no framework component can be: an element that works in any page, under any framework or none, with styles that cannot leak in either direction. That is the entire value proposition, and it is worth a lot in exactly the cases where it applies.

2Custom elements

A class, a registration, five callbacks, and one distinction that trips everyone.

A complete custom element JavaScript
class StarRating extends HTMLElement {
  // Which attributes trigger attributeChangedCallback
  static observedAttributes = ['value', 'max', 'readonly'];

  #root;

  constructor() {
    super();
    // Set up internal structure. DO NOT read attributes or touch
    // children here — the element may not be parsed or upgraded yet.
    this.#root = this.attachShadow({ mode: 'open' });
  }

  connectedCallback()    { /* in the document: render, subscribe */ }
  disconnectedCallback() { /* removed: unsubscribe, abort, clear timers */ }
  adoptedCallback()      { /* moved to another document */ }

  attributeChangedCallback(name, oldValue, newValue) {
    if (oldValue !== newValue) this.#render();
  }

  // A property that reflects to an attribute — the standard pattern
  get value() { return Number(this.getAttribute('value') ?? 0); }
  set value(v) { this.setAttribute('value', String(v)); }
}

customElements.define('star-rating', StarRating);
The name must contain a hyphen
Guaranteeing it can never collide with a future HTML element. <user-card> is legal, <usercard> is not.
Attributes are strings; properties are anything
This is the distinction that catches every framework developer. setAttribute('items', array) stores "[object Object]". Attributes are for simple, declarative, serialisable configuration; properties are for rich data. Well-behaved components accept both for scalars and reflect one to the other — exactly as <input> does with value.
Upgrading
An element written in HTML before its definition loads exists as an unknown element, then is upgraded when define() runs — its constructor and connectedCallback fire late. Two consequences: style unresolved elements with :not(:defined) to avoid a flash of unstyled content, and handle the case where a framework set a property before upgrade, which shadows your accessor. The standard fix is a small "capture and delete own property" dance in connectedCallback.
connectedCallback can fire more than once
Moving an element in the DOM disconnects and reconnects it. Make setup idempotent and always tear down in disconnectedCallback.
Customised built-ins
class FancyButton extends HTMLButtonElement with <button is="fancy-button"> would let you extend a real button and inherit all its behaviour. Safari has declined to implement it, so in practice it is unavailable.

Lifecycle callbacks, as they fire

    3Shadow DOM

    The only real encapsulation boundary on the platform. Everything scoping-related in Chapter 12 was a convention; this is enforced.

    What the boundary blocksDetail
    Page CSS selecting insideA page rule for .title does not match a .title in the shadow tree. There is no selector that crosses in — >>> was removed years ago.
    Component CSS leaking outStyles defined inside apply only inside. You can write button { … } without fear.
    querySelector from outsidedocument.querySelector('.inner') finds nothing. You must go through el.shadowRoot, and only if the mode is open.
    Ids and formsIds are scoped per shadow root, so two instances can both use #input. But a <label for> cannot reach across, and a form outside cannot see inputs inside — see section 6.
    open or closed
    open exposes el.shadowRoot; closed returns null. Closed is not a security boundary — anyone can patch attachShadow before your code runs — and it mostly obstructs testing and debugging tools. Use open.
    What still crosses
    Inherited CSS properties — color, font, line-height — flow in from the host as they do anywhere. Custom properties inherit too, which is the intended theming channel. And composed events bubble out, section 6.
    Focus
    document.activeElement reports the host element, not the inner control. To find the real one you walk shadowRoot.activeElement down. Add delegatesFocus: true when attaching so that focusing the host forwards to the first focusable child and :focus-visible works on the host.

    4Slots

    How content from the page appears inside a shadow tree without moving there.

    Default and named slots HTML
    <!-- Inside the shadow root -->
<article part="card">
  <header><slot name="title">Untitled</slot></header>
  <slot></slot>                          <!-- default slot -->
  <footer><slot name="actions"></slot></footer>
</article>

<!-- In the page -->
<info-card>
  <h3 slot="title">Seed trays</h3>
  <p>Forty cells, stacks flat.</p>
  <button slot="actions">Add</button>
</info-card>
    Slotted content stays in the light DOM
    It is projected, not moved. So the page's own CSS still styles it, document.querySelector still finds it, and framework bindings on it still work. This is what makes web components usable from inside React or Vue: children you pass keep behaving normally.
    Fallback content
    Whatever is inside the <slot> renders when nothing is assigned to it.
    slotchange
    Fires when the assigned nodes change, which is how a component reacts to children being added or removed. slot.assignedElements() gives you the current set.
    Styling projected content
    ::slotted(p) from inside the shadow root matches top-level slotted elements only — it cannot reach their descendants. Page styles win over ::slotted rules, because the content belongs to the page.

    5Styling across the boundary

    Encapsulation is the feature, so theming needs deliberate holes. There are exactly four.

    What gets through the shadow boundary Real page rules applied to a real shadow root. Tick one and watch.

    HoleWritten asUse
    Inherited propertiesNothing special — color, font-familyAutomatic. It is why a component picks up the page's typography without being asked.
    Custom properties--card-bg: navy on the hostThe primary theming channel. Document the ones you support; they are your public styling API.
    ::part()my-card::part(header) { … }Expose specific internal elements for arbitrary styling. You choose which, by adding part="header" inside.
    :host selectors:host, :host([open]), :host-context(.dark)Style the element itself from inside, and react to its attributes or to an ancestor's class.

    Two more mechanisms worth knowing: adoptedStyleSheets shares one CSSStyleSheet object across every instance instead of duplicating a <style> tag per shadow root, which matters at a hundred instances; and ::theme() plus the newer parts of the shadow styling specification are still settling, so check support before depending on them.

    Utility CSS does not reach in

    This is the single biggest practical friction. A Tailwind class on the host works; the same class inside the shadow tree matches nothing, because the utility stylesheet lives in the document. Teams hit this immediately and respond in one of three ways: use custom properties and ::part as the styling API and accept the discipline; adopt the shared stylesheet into each shadow root with adoptedStyleSheets; or skip shadow DOM entirely and define custom elements that render into the light DOM, keeping the lifecycle and losing the encapsulation. All three are legitimate; the third is more common than the evangelism suggests.

    6Events and forms

    Two areas where the boundary changes behaviour in ways you must plan for.

    Retargeting and composed

    An event from inside a shadow tree is retargeted as it crosses the boundary: to a listener on the page, event.target is the host element, not the internal button. That is deliberate — it preserves encapsulation, since the page has no business knowing your internals. Use event.composedPath() when you genuinely need the real origin.

    Emitting an event that escapes JavaScript
    this.dispatchEvent(new CustomEvent('rating-change', {
  detail: { value },
  bubbles: true,      // travels up…
  composed: true      // …and crosses the shadow boundary. Both are needed.
}));

// Most native events are composed (click, input, keydown).
// focus and blur are not composed and do not bubble at all —
// use focusin and focusout, as in Chapter 14.

    Form-associated custom elements

    A form cannot see an <input> hidden inside a shadow root, so a naive custom control submits nothing — the Chapter 5 problem in a new costume. ElementInternals fixes it properly.

    A custom control that behaves like a real one JavaScript
    class RatingInput extends HTMLElement {
  static formAssociated = true;      // opt in
  #internals = this.attachInternals();

  set value(v) {
    this.#internals.setFormValue(v);   // appears in FormData
    this.#internals.setValidity(
      v ? {} : { valueMissing: true },
      'Choose a rating'
    );                                 // participates in constraint validation
  }

  get role() { return this.#internals.role; }
  formResetCallback()   { this.value = null; }
  formStateRestoreCallback(state) { this.value = state; }
}

// ElementInternals also carries the accessibility defaults:
//   this.#internals.role = 'slider';
//   this.#internals.ariaValueNow = String(v);
// …which set the element's implicit semantics rather than
// requiring ARIA attributes in the page's markup.

    7Declarative shadow DOM

    The piece that was missing for a decade: shadow roots that exist before JavaScript runs.

    Historically a shadow root could only be created by script, which meant a server could not render one — so any page relying on web components had an empty shell until the bundle executed. Everything in Chapter 7 about crawlers and preview bots applied.

    A shadow root in the HTML itself HTML
    <star-rating value="4">
  <template shadowrootmode="open">
    <style>:host { display: inline-flex; gap: 2px }</style>
    <span part="stars">★★★★☆</span>
  </template>
</star-rating>

<!-- The parser attaches this as a real shadow root during parsing.
     The component renders correctly with JavaScript disabled, and
     the class later "hydrates" it by adopting the existing root
     rather than building a new one. -->

    The consequence is that web components can now be server-rendered, which removes the largest architectural objection to them. Note that innerHTML ignores declarative shadow roots by default for security reasons — use setHTMLUnsafe() or the parser.

    8When to use them

    A short list of clear wins and an honest account of where a framework is simply better.

    Use web componentsUse a framework component
    A design system consumed by teams on React, Angular, Vue and server-rendered templates at once An application where every component lives in the same codebase and framework
    A widget embedded in third-party pages you do not control, where style isolation is the requirement Anything needing fine-grained reactivity, derived state and a component-level compiler
    Long-lived markup that must outlast a framework migration — documentation, email templates, a CMS Anything where the ecosystem matters: routing, data fetching, forms, testing, dev tools
    Enhancing existing server-rendered HTML with islands of behaviour Rapid application development, where framework ergonomics are worth more than portability
    The honest limitations
    No built-in reactivity — you write your own rendering, or use a library. No templating. Attributes are strings. Server rendering only became practical with declarative shadow DOM. Styling from outside is deliberately restricted, which is a feature until a designer asks for a change you did not expose. And passing rich data requires properties, which plain HTML cannot express.
    Libraries that fill the gaps
    Lit is the pragmatic default: about 5 KB, reactive properties, an efficient template system, and it stays close to the platform. Stencil compiles to standards-compliant components and generates framework wrappers. FAST and Shoelace ship component sets. Writing raw custom elements is instructive and rarely the right long-term choice for a component library.
    Using them from a framework
    Angular and Vue handle custom elements well, including property binding and custom events. React added full support in version 19 — before that, attributes were stringified and custom events needed manual listeners, which is why so much older advice says they do not mix. Check the framework's custom-elements-everywhere score before committing.

    9Accessibility across the boundary

    Everything from Chapter 6 still applies, and two mechanisms stop working.

    ARIA references cannot cross
    aria-labelledby, aria-describedby, aria-controls and <label for> all take element ids, and ids do not resolve across a shadow boundary. A label in the page cannot name an input in the shadow tree. Workarounds: keep the labelled control in the light DOM, mirror the text with aria-label on the host, or use ElementInternals to set the semantics directly.
    ElementInternals is the right tool
    Setting internals.role and the internals.aria* properties gives the host element real default semantics, which the page can still override with explicit ARIA attributes. That is the correct layering, and it avoids requiring consumers to remember role="slider" on your tag.
    Focus management
    Use delegatesFocus: true so the host is focusable and forwards to the right child. Remember that document.activeElement stops at the host, so any focus-trap or focus-restore code written for a normal tree needs adjusting.
    Test it the same way
    Keyboard pass, screen reader, accessibility tree in devtools. Encapsulation hides nothing from assistive technology — the accessibility tree flattens shadow trees — so a broken component is broken in exactly the visible ways.

    10Check yourself

    Six questions.

    1. You pass an array of options to a custom element with setAttribute('items', options) and it receives nothing useful. Why?

    Attributes are strings. Any object passed to setAttribute is coerced, so the element receives the literal text "[object Object]". Rich data must go through a property: el.items = options. This is the standard division — attributes for simple declarative configuration that could sensibly appear in HTML, properties for anything structured. A well-behaved component supports both for scalars and reflects one to the other, which is exactly what <input> does. It is also why older React versions were awkward with custom elements: JSX set attributes, so every non-string prop was stringified.

    2. A page rule .title { color: red } does not affect a .title inside your shadow root, but color set on the host does reach the text inside. Explain both.

    Selectors do not cross the shadow boundary — there is no combinator that matches into a shadow tree, so .title in the page matches nothing inside. But inheritance is not selection: inheritable properties such as color, font-family and line-height pass from the host to its shadow children exactly as they would anywhere in the DOM. That combination is the design: the component controls its own layout and structure, and still picks up the page's typography and colour context without either side coordinating. Custom properties inherit for the same reason, which is what makes them the theming channel.

    3. Your component dispatches new CustomEvent('change') and the page listener never fires. What is missing?

    Two flags, both defaulting to false. bubbles: true is needed for it to travel up at all, and composed: true is needed for it to cross the shadow boundary — without the second it bubbles to the shadow root and stops. A third point worth knowing: once it does escape, the event is retargeted, so event.target in the page's listener is your host element rather than the internal control. Use composedPath() if you need the real origin. And avoid the name change — it collides with a native event; namespace it as rating-change.

    4. A custom input inside a form submits nothing. Why, and what is the fix?

    Form association is based on the form's tree, and an input inside a shadow root is not in it — the form cannot see it, so it contributes nothing to FormData. The fix is static formAssociated = true plus attachInternals(), then calling internals.setFormValue() whenever the value changes. That also unlocks setValidity() for constraint validation, formResetCallback for form resets, and state restoration on back-navigation — that is, everything from Chapter 5 that a naive custom control silently loses. The older workaround of a hidden input in the light DOM works but handles none of the validation or reset behaviour.

    5. Your team uses Tailwind. Classes on the custom element work; classes inside its shadow root do nothing. What are the options?

    The utility stylesheet is in the document, so its rules cannot select into the shadow tree — the boundary is doing exactly what it was designed to do. Three responses. Treat custom properties and ::part() as the component's public styling API and accept that internals are not utility-styleable, which is the most principled option. Adopt the compiled stylesheet into each shadow root with adoptedStyleSheets, sharing one CSSStyleSheet object across instances so it is not duplicated. Or define custom elements that render into the light DOM instead, keeping the lifecycle, slots-by-convention and portability while giving up encapsulation — which is a very common real-world choice and worth considering before the other two.

    6. When is a web component clearly the right choice over a framework component?

    When the consumers do not share your framework. A design system used simultaneously by React, Angular and server-rendered templates has exactly one option that does not mean maintaining three implementations. Likewise a widget embedded in third-party pages, where the style isolation is the product requirement rather than a nicety, and markup that must outlive a framework migration. Inside a single-framework application the calculus reverses: you give up reactivity, templating, the routing and data ecosystem and the dev tools, in exchange for a portability nobody will use. The two are not competitors so much as answers to different questions.
