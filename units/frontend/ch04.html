CHAPTER 04

HTML documents and semantics

HTML is not a formatting language and it never was. It is a description of what things are, consumed by three audiences with completely different needs. This chapter covers the document skeleton, the element vocabulary worth knowing by heart, and the specific places where choosing the wrong tag causes real, reproducible harm.

Part 2 Markup and meaning·Reading time 50 minutes·Demos outline extractor, table headers·Prerequisites Chapters 1–3

1Three audiences, one document

"Semantic HTML" sounds like a style preference until you know who is reading it.

Every element you write is consumed by three very different things, and only one of them has eyes.

AudienceWhat it does with your markupWhat breaks if you get it wrong
The browser Builds the DOM, applies default behaviour: focusability, keyboard handling, form submission, link navigation, native controls You reimplement behaviour badly. A <div onclick> has no keyboard support, no focus ring, no Enter key, no middle-click, no context menu, no "open in new tab".
Assistive technology Reads the accessibility tree the browser derives from your DOM. Announces roles, offers landmark and heading navigation, exposes state The page becomes unnavigable. A screen-reader user jumping by heading finds nothing; a keyboard user cannot reach half your interface. Chapter 6.
Machines Search crawlers, reader modes, social preview bots, translation tools, browser extensions, AI agents, RSS parsers Your content is misunderstood or invisible. Reader mode strips the wrong parts; search snippets are wrong; the article date is not recognised as a date. Chapter 7.

The honest framing is this: semantic HTML is free behaviour. A <button> arrives with focus management, keyboard activation on both Enter and Space, a disabled state, form association and a correct accessibility role, all of which you would otherwise have to write and maintain yourself. Choosing <div> is choosing to reimplement it, worse.

The rule that resolves most arguments

Use the element that describes the content. If none describes it, use <div> for a block or <span> for inline text — those two are the honest "no meaning here" elements and there is nothing wrong with them. What is wrong is using <div> for something that already has an element.

2Document anatomy

Eight lines that every page needs, and the reasons each one is there.

The minimum viable modern document HTML
<!DOCTYPE html>
<html lang="en-GB">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Order confirmed — Northwind</title>
  <meta name="description" content="Your order #4821 has shipped.">
  <link rel="stylesheet" href="/assets/app.9f3c1a.css">
</head>
<body>
  <!-- content -->
  <script src="/assets/app.9f3c1a.js" defer></script>
</body>
</html>
<!DOCTYPE html>
Not a version declaration — it is a switch. Present, the browser uses standards mode. Absent, it falls into quirks mode, where the box model is the pre-standard one (width includes padding and border) and a long list of other behaviours change. Nothing else about it matters; it is five words you type once.
lang on <html>
Tells screen readers which voice and pronunciation rules to use, tells browsers which hyphenation and quotation conventions apply, and tells translation tools the source language. A French page announced by an English synthesiser is unintelligible. Use a region subtag when spelling or currency conventions differ (en-GB versus en-US). Mark inline language changes on the element itself: <span lang="fr">.
<meta charset="utf-8">
First thing in the head, always. It must appear within the first 1024 bytes or the parser may have to restart with a different encoding, discarding work. UTF-8 is the only correct answer in 2026.
<meta name="viewport">
Without it, mobile browsers assume a 980-pixel-wide desktop layout and zoom out, producing the "tiny unreadable page" effect. width=device-width maps the layout viewport to the device. Chapter 10 covers this properly.
<title>
The browser tab, the bookmark name, the browser history entry, the search result heading, and the first thing a screen reader announces on page load. Put the specific part first: "Order confirmed — Northwind" beats "Northwind — Order confirmed", because tabs and search results truncate from the right.
Never disable zoom

maximum-scale=1 or user-scalable=no in the viewport meta prevents pinch-zoom. It was a workaround for a long-fixed iOS bug and it is now a genuine accessibility failure for anyone with low vision. Modern browsers ignore it in some contexts precisely because it was so widely abused, but do not rely on that — just do not write it.

What belongs in the head

Only metadata: <title>, <meta>, <link>, <style>, <script>, <base>. Anything else — a stray <div>, a comment containing markup that confuses the parser — implicitly closes the head and starts the body early, which silently moves your remaining stylesheets into the body where they behave differently.

Order inside the head matters for performance, not correctness. A useful ordering: charset first, then viewport, then any preconnect hints, then the title, then render-blocking CSS, then everything else. Anything above your stylesheet delays the stylesheet.

3Landmarks and the heading outline

Two independent navigation systems, both derived entirely from your element choices.

Sighted users navigate visually: they scan for the header, spot the sidebar, skip to the content. Screen-reader users cannot scan, so they navigate with two keyboard-driven lists — landmarks and headings. Both are generated automatically from your markup, and both are empty if you used only <div>.

Landmark elements

ElementImplicit roleUse and caveats
<header>bannerOnly when it is a direct child of <body>. Inside an <article> or <section> it is just a grouping element with no landmark role — which is fine and intended.
<nav>navigationFor major navigation blocks, not every group of links. Two or more on a page must be distinguished with aria-label: "Main", "Breadcrumb", "Pagination".
<main>mainExactly one per page, containing the unique content. This is what "skip to content" links target. Must not be nested inside the other landmarks.
<aside>complementaryTangentially related content: a sidebar, a pull quote, related links. Not "the thing on the right".
<footer>contentinfoSame rule as <header> — landmark only as a direct child of <body>.
<section>region if namedOnly becomes a landmark when it has an accessible name via aria-labelledby or aria-label. An unnamed <section> is semantically a <div>. This surprises almost everybody.
<article>articleA self-contained item that would still make sense syndicated elsewhere: a blog post, a comment, a product card, a forum reply.
<search>searchThe newest landmark. Wraps a search form. Replaces the old role="search" pattern.
<form>form if namedSame conditional-naming rule as <section>.

Headings are a hierarchy, not a size chart

Heading levels describe document structure. They are not a way to make text bigger — that is what CSS is for, and <h3 class="text-2xl"> is perfectly normal if the structure calls for an h3.

Do not skip levels going down
An <h2> followed by an <h4> tells a screen-reader user that a level-3 section exists and they have missed it. Jumping back up several levels is fine — that just closes sections.
One <h1>, in practice
The specification permits more; every real-world audit tool and most users expect exactly one, matching the page's subject. Make it the page title, not the site name.
The outline algorithm is dead
HTML5 once specified that nesting <section> elements would automatically demote heading levels, so you could use <h1> everywhere. No browser ever implemented it and it has been removed from the specification. Write explicit levels.

      Skip links

      A keyboard user landing on your page tabs through the entire header and navigation before reaching content — on every page. A skip link fixes it in four lines: an anchor as the first focusable element in the body, pointing at #main, positioned off-screen until focused. Do not use display: none to hide it, because that removes it from the tab order entirely; move it off-screen with position: absolute and bring it back on :focus.

      4Text-level semantics

      The inline elements, including the four pairs that look identical and are not.

      The pairs people get wrong

      ElementMeansUse it when
      <strong>Strong importance, seriousness or urgency"Warning: this cannot be undone." Announced with emphasis by some screen readers.
      <b>Stylistically offset, no added importanceProduct names in a review, keywords in an abstract, the lead sentence of an article. Bold with no meaning.
      <em>Stress emphasis that changes the sentence's meaning"I did not say that." Where the spoken stress falls.
      <i>An alternate voice or moodTaxonomic names, transliterations, a thought, a technical term on first use. Italic with no stress.

      In practice: if reading it aloud would sound different, use <strong> or <em>. If it only looks different, use <b> or <i> — or, better, a <span> with a class that says what it is.

      The rest of the vocabulary

      ElementWhat it is for
      <a href>Navigation to a URL. Without href it is not a link, is not focusable and has no role — a placeholder, nothing more.
      <time datetime>Machine-readable dates and durations. <time datetime="2026-03-14">last Tuesday</time>. Search engines and calendar tools read the attribute, humans read the text.
      <abbr title>An abbreviation with its expansion. Genuinely useful, but the title tooltip is invisible on touch devices and to keyboard users — spell it out in the text on first use as well.
      <q> / <blockquote cite>Inline and block quotations. <q> adds quotation marks automatically, correct for the current lang. Attribution goes outside the blockquote, usually in a <figcaption>.
      <cite>The title of a work — a book, film, paper. Not the author's name, despite decades of misuse.
      <code>, <kbd>, <samp>, <var>Code fragment, keyboard input, sample program output, a variable name. Four distinct things that all default to monospace.
      <mark>Highlighted for relevance in the current context — search-result matches, the line an error points at. Not a general highlighter pen.
      <del> / <ins>Removed and added content, with optional datetime and cite. For a struck-through price use <s> instead — that means "no longer accurate", not "edited out".
      <dfn>The defining instance of a term — the place the term is explained, not every use of it.
      <small>Side comments and legal small print. A semantic, not a size.
      <sub> / <sup>Subscript and superscript where the position carries meaning: H2O, x2. Not for stylistic raised text.
      <bdi> / <bdo>Bidirectional text isolation and override. Wrap user-supplied names in <bdi> so an Arabic username cannot rearrange the surrounding English sentence.
      <wbr>An optional line-break opportunity inside a long unbreakable string, such as a URL.
      <span>No meaning. The correct choice when there genuinely is none.

      Grouping elements

      <p>
      A paragraph. Cannot contain block-level content — putting a <div> inside one causes the parser to close the paragraph early, producing a DOM that does not match your source. A frequent cause of "my CSS selector matches nothing".
      <ul>, <ol>, <li>
      Screen readers announce "list, 7 items", which is genuinely useful orientation. Only <li>, <script> and <template> may be direct children. <ol> supports start, reversed and per-item value.
      <dl>, <dt>, <dd>
      Name–value groups: glossaries, metadata panels, key–value specs. One <dt> may have several <dd>s and vice versa. Wrapping each pair in a <div> is explicitly allowed and makes grid layout far easier.
      <figure> / <figcaption>
      Self-contained referenced content with a caption — images, diagrams, code listings, tables, quotes. The caption becomes the figure's accessible name, so a captioned image often needs only a short alt.
      <pre>
      Preserved whitespace. The only element where leading newlines and indentation survive. Usually wraps a <code>.
      <hr>
      A thematic break — a scene change in prose, not a decorative line. For decoration use a border.

      5Tables done properly

      Tables are correct for tabular data and only for tabular data. Getting the header associations right is the whole job.

      A sighted reader understands a table by looking along a row and up a column simultaneously. A screen-reader user hears one cell at a time and depends entirely on the browser telling them which headers apply. That association comes from your markup — nowhere else.

      A correctly marked-up table HTML
      <table>
  <caption>Quarterly revenue by region, 2026 (£m)</caption>
  <colgroup><col><col span="4" class="num"></colgroup>
  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">Q1</th>
      <th scope="col">Q2</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Northern</th>
      <td>4.2</td>
      <td>5.1</td>
    </tr>
  </tbody>
</table>
      <caption>
      The table's accessible name, and the first thing announced. Must be the first child. Far better than a heading above the table, because it travels with the table when someone jumps to it directly.
      scope="col" / scope="row"
      The association mechanism. Without scope, browsers guess using heuristics that work for simple tables and fail for anything else. It costs eleven characters — always write it.
      <thead>, <tbody>, <tfoot>
      Row grouping. <thead> repeats on printed pages and enables position: sticky headers. Note that <tbody> is inserted by the parser whether you write it or not, which trips up querySelector paths.
      headers and id
      The escape hatch for complex tables with multi-level or spanning headers: each <td> lists the ids of every header that applies. Verbose, so use it only where scope cannot express the relationship — and consider splitting the table instead.
      <colgroup> / <col>
      Column-level styling hooks. Limited to a handful of properties (background, border, width, visibility) but the only way to style a column without touching every cell.
      What a screen reader announces Click any data cell. Toggle scope to see the associations break.
      Green cells are the headers currently associated with your selection.
      Select a cell to hear what would be announced.

      Responsive tables

      The common trick of setting display: block on table elements to stack them on narrow screens destroys the table semantics entirely — the browser stops exposing rows, columns and header associations, because those come from the display type as much as the tag. If you must restyle, add explicit ARIA roles back (role="table", role="row", role="cell") or, far better, wrap the table in a scrolling container with overflow-x: auto and give it tabindex="0" plus an accessible name so keyboard users can scroll it.

      6Embedded content

      Images, media and frames — plus the alt-text decision that everyone gets wrong in the same direction.

      Images and the alt decision

      Every <img> needs an alt attribute. What goes in it depends entirely on the image's job, not its content.

      The image is…WriteExample
      Informative — conveys contentWhat the image tells you, conciselyalt="Bar chart: sales doubled between Q1 and Q3"
      Decorative — pure ornamentalt="" — empty, but presentA background flourish. Omitting alt entirely makes screen readers read the filename instead.
      Functional — inside a link or buttonThe destination or action, not the pictureA logo linking home: alt="Northwind home", not alt="Northwind logo".
      Text as imageThe exact text in the imagealt="50% off everything"
      Complex — chart, diagram, mapA short alt plus a full description nearbyShort summary in alt, the data table or prose description in a <figcaption> or adjacent section.

      Two consistent mistakes: starting with "Image of" (the screen reader already said "graphic"), and describing a functional image's appearance instead of its purpose.

      Responsive and modern images

      The two mechanisms, and when each applies HTML
      <!-- Same image, different sizes: let the browser choose. `sizes` tells it
     how wide the image will be at each breakpoint, BEFORE CSS loads. -->
<img src="/hero-800.jpg"
     srcset="/hero-400.jpg 400w, /hero-800.jpg 800w, /hero-1600.jpg 1600w"
     sizes="(max-width: 700px) 100vw, 700px"
     width="800" height="450"
     alt="Harvesting at Ridgeway Farm">

<!-- Different formats or genuinely different crops: you choose. -->
<picture>
  <source srcset="/hero.avif" type="image/avif">
  <source srcset="/hero.webp" type="image/webp">
  <img src="/hero.jpg" alt="Harvesting at Ridgeway Farm"
       width="800" height="450" loading="lazy" decoding="async">
</picture>
      Always set width and height
      Not to size the image — CSS does that — but so the browser can compute the aspect ratio and reserve the space before the file arrives. This is the single largest cause of layout shift, and the fix is two attributes. It works even when CSS overrides the dimensions, because modern browsers derive aspect-ratio from them.
      loading="lazy"
      Defers the request until the image nears the viewport. Correct for everything below the fold. Never put it on your LCP image — it delays the very thing the metric measures.
      fetchpriority="high"
      The counterpart: promote the hero image so it competes with the stylesheet rather than queueing behind twelve thumbnails.
      decoding="async"
      Lets the browser decode off the main thread. Safe almost everywhere.

      SVG: inline or as an image?

      ApproachChoose whenTrade-off
      <img src="icon.svg">Static, reused, cacheableSeparate request, but cached. Cannot be styled by page CSS or animated by page script.
      Inline <svg>You need CSS control, currentColor, or animationNo request, full control — but the markup ships with every page and bloats the DOM if repeated.
      CSS background-imagePurely decorativeInvisible to assistive tech, which is correct here. Not discoverable by the preload scanner.

      Accessibility for inline SVG: add role="img" and a <title> as the first child if it conveys meaning, or aria-hidden="true" plus focusable="false" if it is decorative. Decorative SVGs without aria-hidden are announced as unlabelled graphics.

      Media and frames

      <video> / <audio>
      Use controls unless you are building your own, and if you build your own you own all the keyboard handling. poster gives a still frame before playback. preload="metadata" is a sensible default — auto can download megabytes nobody watches. Autoplay only works muted, by policy.
      <track kind="captions">
      A WebVTT file. Legally required in many jurisdictions, useful to everyone in a noisy room, and indexed by search engines. kind="descriptions" covers what is happening visually.
      <iframe>
      Always give it a title — it appears in the landmark list and "iframe" alone tells nobody anything. Add loading="lazy" for below-the-fold embeds, and sandbox plus allow to restrict what third-party content can do. An unsandboxed third-party iframe can navigate your top-level page.
      <canvas>
      A pixel buffer with no semantics at all. Whatever you draw is invisible to assistive technology; you must provide an accessible alternative in the fallback content or alongside it.

      7Interactive elements

      Four native widgets that save hundreds of lines, and one distinction worth tattooing somewhere.

      Link or button?

      This is the most consequential single choice in day-to-day HTML, and the rule is simple: a link goes somewhere; a button does something.

      <a href><button>
      PurposeNavigate to a URL or a fragmentTrigger an action in the current page
      Activated byEnterEnter and Space
      Announced as"link""button"
      Middle-click, Cmd-click, right-click menuYes — opens in a new tabNo, correctly
      Appears in the screen reader's link listYesNo
      Works without JavaScriptYesOnly as a form submit

      A "Delete account" control that is an <a href="#"> can be middle-clicked into a new tab and appears in the link list as a destination. A "Next page" control that is a <button> cannot be opened in a new tab or bookmarked. Both are wrong in ways users notice.

      Never <div onclick>

      To make a div behave like a button you must add role="button", tabindex="0", a keydown handler for both Enter and Space, a visible focus style, and a disabled state that also removes it from the tab order. That is roughly twenty lines to reproduce something the platform gives you for free — and you will still miss the Windows high-contrast rendering and the forced-colors adjustments. Set appearance: none on a real button instead; it strips every native style and leaves the behaviour.

      Native widgets worth using

      <details> / <summary>
      An accordion with zero JavaScript: focusable, keyboard-operable, correct expanded state, and in-page find can open it. Add name="group" to several and they behave as an exclusive accordion. Animating it needs a little care because the content is display: none when closed — ::details-content and interpolate-size are the modern route.
      <dialog>
      Call showModal() and you get the top layer, a backdrop you can style with ::backdrop, focus trapped inside, Escape to close, and the rest of the page marked inert — all natively. Doing this by hand is a genuinely hard problem that libraries have got wrong for a decade. Note the difference between show() (non-modal, no trap) and showModal().
      The Popover API
      popover plus popovertarget gives declarative tooltips, menus and disclosure panels in the top layer, with light-dismiss behaviour, no JavaScript required. Combined with CSS anchor positioning it replaces most of what a positioning library was for.
      <template>
      Inert markup that is parsed but not rendered, cloned by script when needed. The basis of web components (Chapter 20) and a clean way to ship list-item markup without building HTML strings.

      8Global attributes and content models

      Attributes every element accepts, and the nesting rules the parser silently enforces.

      AttributeNotes
      idUnique per document. Powers fragment links, <label for>, and every ARIA relationship attribute. Duplicated ids silently break all three.
      classStyling and scripting hook, no semantics. Space-separated.
      data-*Your own metadata, readable as el.dataset.thing. The right home for state a script needs. Do not store secrets there — see Constraint 3 in Chapter 1.
      hiddenEquivalent to display: none, and just as overridable by CSS. hidden="until-found" keeps content findable by in-page search and reveals it on a match.
      inertRemoves an entire subtree from the tab order, from pointer events and from the accessibility tree. The correct way to disable the background behind a custom overlay.
      tabindex0 puts an element in the natural tab order; -1 makes it focusable only by script. Positive values are almost always a bug — they jump ahead of every natural element on the page and are nearly impossible to maintain.
      titleA tooltip that does not appear on touch, does not appear on keyboard focus in most browsers, cannot be styled and is inconsistently announced. Only reliable use: naming an <iframe>. Never put essential information here.
      lang, dir, translateLanguage of the subtree, text direction (auto is right for user-generated content), and whether translation tools should leave it alone.
      contenteditableMakes content editable. Powerful and a large source of cross-browser pain; reach for it knowingly.

      Content models: what may nest inside what

      Every element declares which children are permitted. The parser enforces this by silently restructuring your DOM, which means the tree your CSS and JavaScript see is not always the markup you wrote.

      You wroteThe browser produced
      <p>text <div>block</div></p>The <p> is closed before the div, and the stray </p> becomes an empty paragraph. Three siblings, not one parent.
      <ul><div><li>…</li></div></ul>Invalid; the div is not a permitted child. Behaviour varies and the list semantics may be lost.
      <table><tr>…</tr></table>A <tbody> is inserted around the row. Your table > tr selector matches nothing.
      <a href>…<a href>…</a></a>Links cannot nest; the first is closed. Same for nested <button>, and a button inside a link is invalid too.
      <br />Identical to <br>. The trailing slash is ignored on void elements in HTML — it is not "self-closing", it is simply permitted noise. On a non-void element such as <div /> it does nothing at all and the div stays open.
      Void elements
      area, base, br, col, embed, hr, img, input, link, meta, source, track, wbr. No closing tag, no children, ever.
      Character references
      Four you must escape in text content: &amp;, &lt;, &gt;, and &quot; inside attribute values. Everything else is optional now that UTF-8 is universal — type the actual character.
      Validation
      Run the W3C validator, or a linter such as html-validate in CI. It catches duplicate ids, invalid nesting and missing required attributes in seconds. Frameworks that generate markup make this more important, not less, because nobody reads the output.

      9Check yourself

      Six questions. Three are standard interview material.

      1. When does a <section> element actually do anything?

      Only when it has an accessible name, via aria-labelledby pointing at its heading or an explicit aria-label. Named, it becomes a region landmark and appears in the screen reader's landmark list. Unnamed, it is semantically indistinguishable from a <div>. The same conditional rule applies to <form>. This is why wrapping everything in <section> "for semantics" achieves nothing.

      2. A designer wants a struck-through old price next to a new one. Which element, and why not the obvious alternative?

      <s> — "no longer accurate or relevant". <del> means content that was removed in an edit, which carries a document-revision meaning that a sale price does not have, and it pairs with <ins>, datetime and cite attributes that make no sense here. If neither meaning applies and it is purely visual, a <span> with a class and text-decoration: line-through is honest. In all three cases, also make sure the current price is not conveyed by strikethrough alone.

      3. Your logo is an image inside a link to the home page. What should the alt text be?

      The link's destination, not the image's content: alt="Northwind home". When an image is the only content of a link, its alt text becomes the link's accessible name, so alt="Northwind logo" produces a link announced as "Northwind logo, link" — which describes a picture rather than telling the user where they will end up. And alt="" here produces an unlabelled link, one of the most common failures on the web.

      4. Why does document.querySelector('table > tr') return null on a table that visibly has rows?

      Because the HTML parser inserts a <tbody> around any rows that are not already inside <thead>, <tbody> or <tfoot>, whether or not you wrote one. The rows are children of that generated tbody, so table > tr matches nothing. Use table tr, or write the <tbody> explicitly. It is a good illustration of the general point: your selectors run against the parsed DOM, not your source file.

      5. A teammate makes a card clickable by putting onclick on the wrapping <div>. List what breaks.

      It is not focusable, so keyboard users cannot reach it. It has no role, so a screen reader announces nothing actionable and it appears in no list. Enter and Space do nothing. There is no focus indicator. It cannot be opened in a new tab, middle-clicked, bookmarked, or copied as a link. It does not respect Windows high-contrast mode. It has no disabled state. If the card leads somewhere, wrap the card's title in an <a href> and expand its hit area with a stretched pseudo-element; if it performs an action, use a real <button>.

      6. What is the practical difference between hidden, inert and aria-hidden="true"?

      hidden removes the element visually and from the accessibility tree — it is display: none with a semantic name, and CSS can override it. inert leaves the element visible but removes it from the tab order, from pointer events and from the accessibility tree; it is designed for the page behind a modal. aria-hidden="true" removes it from the accessibility tree only — it stays visible and, crucially, stays focusable, so applying it to something containing a focusable element creates the worst outcome: a control a keyboard user can reach but a screen reader cannot describe.
