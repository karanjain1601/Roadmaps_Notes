CHAPTER 14

The DOM and events

The API JavaScript was put in a browser to drive. This chapter covers reading and changing the document, the event model in its three phases — which almost nobody can describe accurately and everybody depends on — delegation, the four observers, and the cleanup discipline that stops a long-lived page leaking.

Part 4 JavaScript in the browser·Reading time 50 minutes·Demos propagation, delegation·Prerequisites Chapters 3, 13

1The DOM as an API

A tree of objects, not your HTML file. The distinction matters more often than it sounds.

The DOM is the browser's in-memory model of the document, built by the parser and mutable afterwards. Your HTML file is the initial input; the DOM is what exists at runtime. Chapter 4 showed the parser silently restructuring invalid markup, and this is where you meet the consequences: your selectors and traversal run against the tree, not the source.

Node versus Element
A Node is anything in the tree, including text and comment nodes. An Element is a tag. This distinction produces the most common traversal bug: firstChild is often a whitespace text node, while firstElementChild is the tag you meant. The *Element* variants — children, nextElementSibling, parentElement — are almost always what you want.
Live versus static collections
getElementsByClassName and getElementsByTagName return live HTMLCollections that update as the DOM changes — which turns for (let i = 0; i < els.length; i++) els[i].remove() into a loop that removes every other element. querySelectorAll returns a static NodeList, a snapshot. Prefer the static one unless you specifically want liveness.
Neither is an array
NodeList has forEach but not map or filter; HTMLCollection has neither. Convert with [...nodes] or Array.from(nodes).
MethodReturnsNotes

All of the query* methods exist on elements too, and scope to that subtree: card.querySelectorAll('.btn'). Note that querySelector takes a full selector, so a scoped search still matches descendants — use :scope > .btn for direct children only.

2Creating and changing nodes

Six insertion methods, two content properties, and one security decision.

The modern insertion API JavaScript
const li = document.createElement('li');
li.textContent = item.name;              // text, always escaped
li.className = 'row';
li.dataset.id = item.id;                 // data-id="…"

list.append(li);                          // end; accepts nodes AND strings, many at once
list.prepend(li);                         // start
ref.before(li);  ref.after(li);           // as a sibling
ref.replaceWith(li);                      // swap
li.remove();                              // no parentNode dance needed

// Batch: build off-document, insert once. One layout instead of n.
const frag = document.createDocumentFragment();
for (const item of items) frag.append(rowFor(item));
list.append(frag);                        // the fragment itself vanishes

// Or clone a <template>, which keeps the markup in HTML where it belongs
const node = rowTemplate.content.cloneNode(true);
node.querySelector('.name').textContent = item.name;
textContent, innerHTML, innerText

textContent gets and sets plain text, escaping everything. It is fast and safe, and it is what you want almost always.

innerHTML parses a string as markup. Assigning any value that contains user input is a cross-site-scripting vulnerability, full stop — and note that <img src=x onerror=alert(1)> executes even though <script> tags inserted this way do not. If you must build markup from a string, sanitise it, or use the platform's setHTML() where available. Chapter 27 covers this properly.

innerText is a third thing: it reflects rendered text, so it respects display: none and collapses whitespace — and reading it forces a layout, which makes it a silent performance trap inside a loop.

3Events: three phases

An event does not fire on an element. It travels a path, twice.

When you click a button nested three levels deep, the browser computes the path from window down to the button, then dispatches in three phases:

1 · Capture
From window down to the target's parent. Only listeners registered with { capture: true } run.
2 · Target
At the target itself. Both capture and bubble listeners run here, in registration order — the phase distinction does not apply.
3 · Bubble
Back up from the target's parent to window. Normal listeners run. This is the default and where nearly all your handlers live.
Propagation, traced Real listeners on real nested elements. Click the button.

addEventListener options

OptionEffect
capture: trueRun during the capture phase instead of bubble. Also part of the listener's identity — you must pass the same value to removeEventListener.
once: trueAutomatically removed after firing once. Saves the manual removal that is always forgotten.
passive: truePromises never to call preventDefault(), so the browser can start scrolling immediately instead of waiting for your handler. Already the default for touchstart, touchmove and wheel on the document.
signalAn AbortSignal. Aborting it removes the listener. The cleanest cleanup mechanism there is — section 7.

The three "stop" methods, which do different things

MethodStops
event.preventDefault()The browser's default action — following the link, submitting the form, ticking the checkbox. Propagation continues normally. Has no effect on a passive listener.
event.stopPropagation()Further travel along the path. Other listeners on the same element still run.
event.stopImmediatePropagation()Everything, including remaining listeners on the same element.

Returning false from a handler is a jQuery idiom that did both of the first two. In a plain addEventListener handler it does nothing at all.

stopPropagation is usually the wrong fix

It is reached for to stop a click "escaping" a dropdown to a document-level close handler. But it silently breaks anything else listening further up: analytics, a parent's delegation, a focus manager, a third-party widget. The problems it creates appear far from the line that caused them. Prefer a check in the outer handler — if (panel.contains(e.target)) return; — which is explicit, local, and does not affect anyone else.

4Delegation

One listener on a container instead of one per child. The most useful consequence of bubbling.

The pattern, with the two properties that matter JavaScript
list.addEventListener('click', (e) => {
  // e.target        — the deepest element actually clicked (maybe an icon
  //                    inside the button)
  // e.currentTarget — the element this listener is attached to (list)
  const btn = e.target.closest('[data-action]');
  if (!btn || !list.contains(btn)) return;   // clicked the gap: ignore

  switch (btn.dataset.action) {
    case 'delete': remove(btn.closest('li').dataset.id); break;
    case 'edit':   edit(btn.closest('li').dataset.id);   break;
  }
});
Why it scales
One listener regardless of item count, so adding a thousand rows costs nothing extra. And it works for elements that do not exist yet — added later by a render, a fetch, or an infinite scroll — because the listener is on the ancestor.
Always use closest()
e.target may be a <span> or an <svg> inside the button. Comparing e.target.matches('.btn') fails whenever the button has children; closest walks up to find it.
Events that do not bubble
focus, blur, load, error, mouseenter and mouseleave. Use their bubbling counterparts — focusin, focusout, mouseover, mouseout — or register in the capture phase, which reaches them anyway.
The trade-off
Handler logic gets a dispatch layer, and a listener on document for a high-frequency event such as mousemove runs for the entire page. Delegate to the nearest sensible container, not always to the document.
Delegation versus one listener each Both are wired for real. Watch what happens to items added afterwards.

5Custom events

Components talking to each other through the DOM rather than through imports.

Dispatching and listening JavaScript
// Fire from a component
el.dispatchEvent(new CustomEvent('cart:add', {
  detail: { id, qty },       // your payload lives here, and only here
  bubbles: true,            // default is FALSE — the usual reason nothing fires
  composed: true,           // crosses shadow DOM boundaries (Chapter 20)
  cancelable: true           // allows preventDefault()
}));

// Listen anywhere up the tree
document.addEventListener('cart:add', (e) => addToCart(e.detail));

// Cancellable: dispatchEvent returns false if a listener prevented it
const ok = el.dispatchEvent(new CustomEvent('row:delete', { cancelable: true }));
if (ok) actuallyDelete();
When it is a good fit
Web components signalling outwards; decoupling a widget from the page that hosts it; anywhere you would otherwise reach for a global event bus, since the DOM already is one, with a tree structure that scoping can exploit.
When it is not
Inside a framework, where props and callbacks are typed, traceable and testable. Custom events are stringly typed and invisible to your compiler; a listener that never fires because of a typo is silent.
Namespace the names
cart:add, editor:dirty. A bare change or close collides with real DOM events with real default behaviour.
Synchronous dispatch
dispatchEvent runs every listener before returning — it is not queued. That is convenient for cancelable checks and surprising if you expected asynchrony.

The two you will use most JavaScript
// Lazy-load, reveal on scroll, infinite scroll, scroll-spy
const io = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (entry.isIntersecting) {
      reveal(entry.target);
      io.unobserve(entry.target);        // one-shot: stop watching
    }
  }
}, {
  root: null,                          // null = the viewport
  rootMargin: '0px 0px -20% 0px',     // shrink the trigger area
  threshold: 0.25                       // fire at 25% visible
});
document.querySelectorAll('.reveal').forEach(el => io.observe(el));

// Element-level responsiveness in JS (CSS should use container queries)
const ro = new ResizeObserver((entries) => {
  for (const e of entries) chart.resize(e.contentRect.width);
});
ro.observe(chartBox);
"ResizeObserver loop completed with undelivered notifications"

This error means your callback changed the size of something the observer watches, which schedules another callback, which changes it again. The browser breaks the loop and warns. Fix it by writing to a different element than you observe, by guarding against no-op writes, or by deferring the write to the next frame. It is common enough that many teams filter it out of error reporting — resist that; it usually indicates a real feedback loop that also costs frames.

7Cleanup and cost

Long-lived pages leak. Three habits prevent nearly all of it.

One signal to remove everything

AbortController as a universal teardown JavaScript
function mount(el) {
  const ac = new AbortController();
  const { signal } = ac;

  el.addEventListener('click', onClick, { signal });
  window.addEventListener('resize', onResize, { signal });
  document.addEventListener('keydown', onKey, { signal });
  fetch(url, { signal });                     // cancels the request too

  return () => ac.abort();                   // one call removes all four
}

// The old way needed a matching removeEventListener per listener,
// with the SAME function reference and the SAME capture value —
// which is why cleanup was so often incomplete.
What actually leaks
A listener on window or document that closes over a component's state, never removed. A setInterval that outlives the view. An observer never disconnected. A detached DOM node still referenced by an array or a closure — visible in the Memory panel as "Detached HTMLDivElement".
How to find one
Devtools Memory panel: take a heap snapshot, exercise the flow, take another, and compare. Or open the Performance monitor and watch the DOM node count and JS heap size while repeatedly opening and closing a view. A number that only goes up is your leak.
Attach metadata weakly
A WeakMap keyed by element lets the entry disappear when the element is garbage collected. Storing the same thing in a plain Map or an array keeps the node alive forever.
Batch DOM work
Chapter 3's rule applies here directly: read everything, then write everything. Build off-document with a fragment. Prefer classList.toggle over reading a computed style to decide. Anything that reads offsetWidth, getBoundingClientRect or innerText inside a loop is forcing a synchronous layout per iteration.
Throttle high-frequency events
scroll, mousemove, pointermove and resize can fire faster than frames. Coalesce with requestAnimationFrame — set a flag, do the work once per frame — rather than a fixed-millisecond throttle, which is either too slow or wasted. Better still, check whether an observer does the job without any listener at all.

8Check yourself

Six questions.

1. What is the difference between event.target and event.currentTarget?

target is the deepest element the event originated on — where the user actually clicked, which may be an icon or a text span inside your button. currentTarget is the element whose listener is currently running, so it changes as the event travels the path and is always the element you called addEventListener on. In delegation you read target to find out what was hit and then closest() up to the thing you care about. Note that currentTarget is only valid during dispatch; reading it later, for example inside a setTimeout, gives null.

2. A dropdown closes when you click outside it. Someone fixed clicks inside closing it too, by calling stopPropagation() on the panel. What might that break?

Anything else listening above the panel. Analytics click tracking on document stops recording those clicks. A parent component's delegated handler no longer fires. A focus manager or a modal's outside-click detection breaks. Third-party widgets misbehave. And the damage appears far from the line that caused it, which makes it hard to diagnose. The local fix is better: in the document-level close handler, write if (panel.contains(e.target)) return;. It affects nobody else and its intent is readable.

3. You attach a click listener to every row of a list. Rows loaded later by a fetch do nothing when clicked. Why, and what is the fix?

Listeners attach to element instances, not to selectors. The rows that existed when the loop ran got listeners; rows created afterwards are different objects with none. The fixes are to re-attach after every render — fragile and easy to double up — or, much better, to attach one delegated listener to the container that exists from the start, and use e.target.closest('.row'). Delegation handles current and future children identically, which is the demo in section 4.

4. Why does for (let i = 0; i < els.length; i++) els[i].remove() only remove half the elements when els came from getElementsByClassName?

Because that collection is live: it re-queries the document as it changes. Removing element 0 shifts everything down, so the element that was at index 1 is now at index 0 — and then i increments to 1, skipping it. Use querySelectorAll, which returns a static snapshot, or iterate backwards, or spread into an array first with [...els]. The same liveness bites when you cache .length in a loop that adds elements: the loop never terminates.

5. What does { passive: true } actually do, and why is it the default for touchmove?

It promises the handler will never call preventDefault(). Without that promise the browser must run your JavaScript before it knows whether the scroll is allowed to proceed, so every scroll gesture waits on the main thread — and if the main thread is busy, scrolling visibly lags. With the promise, scrolling starts immediately on the compositor. Browsers made it the default for touchstart, touchmove and wheel on the document precisely because so many pages were making scrolling janky by accident. If you genuinely need to prevent a touch default, you must now pass { passive: false } explicitly.

6. A single-page app gets slower the longer it runs, and the DOM node count in the Performance monitor only climbs. What are you looking for?

Detached nodes kept alive by references — the classic leak. Common causes: listeners on window or document that close over component state and are never removed; intervals or timeouts never cleared; observers never disconnected; and nodes pushed into an array or a Map "for later". Confirm with two heap snapshots either side of opening and closing the view and filter for "Detached". The structural fix is to create an AbortController per view, pass its signal to every listener and fetch, and call abort() on teardown — one call that cannot be partially forgotten.
