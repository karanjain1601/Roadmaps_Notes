CHAPTER 05

Forms, inputs and validation

Forms are where your interface stops being a document and starts being an application, and they are the part of HTML with the most free behaviour to inherit — and the most to lose by reimplementing. Every input type, the accessible name computation, the validation API browsers already ship, and error messaging that does not fight the user.

Part 2 Markup and meaning·Reading time 55 minutes·Demos validity inspector, accessible name·Prerequisites Chapter 4

1Why the native form still wins

Before any framework: a plain form is a complete, working, accessible feature.

A <form> with an action and a submit button collects data, validates it, serialises it, sends it, handles the response and navigates — with no JavaScript at all. Everything you add on top should be an enhancement of that, not a replacement for it.

This is not nostalgia. It is the most practical application of progressive enhancement there is, because forms are exactly where failure hurts most. If the bundle times out on a train, a JavaScript-only form is a dead end; a native form still submits. If a password manager cannot recognise your fields, users invent weaker passwords. If autofill does not work, checkout conversion drops measurably.

You get for freeWhat reimplementing costs
Enter submits the formA keydown handler on every field, plus knowing which key means submit in a textarea
Correct mobile keyboardsImpossible to fake — the OS decides from the input type
Password-manager and autofill integrationImpossible to fake — driven by type, name and autocomplete
Validation messages in the user's languageYour own translations for every rule in every locale
Required-field and error state exposed to screen readersARIA attributes you must keep in sync by hand
Reset, form association, disabled propagation via <fieldset>Manual state plumbing

2The form element and submission

Four attributes, one event, and the object that turns a form into data.

The shape of it HTML
<form action="/subscribe" method="post" enctype="multipart/form-data">
  <fieldset>
    <legend>Delivery address</legend>
    <label for="line1">Address line 1</label>
    <input id="line1" name="line1" autocomplete="address-line1" required>
  </fieldset>

  <button>Save address</button>
  <button formaction="/draft" formnovalidate>Save as draft</button>
</form>
method="get"
Values become a query string. Use for searches and filters: the result is bookmarkable, shareable and back-button friendly. Never for anything that changes state, and never for passwords — the query string lands in browser history, server logs and referrer headers.
method="post"
Values go in the request body. Use for anything with a side effect. Comes with the double-submit problem, which the server solves by redirecting after success (the POST-redirect-GET pattern).
enctype
application/x-www-form-urlencoded is the default. multipart/form-data is required for file uploads. text/plain exists and is for debugging only.
name is what gets sent
Not id. A field with no name is not submitted at all — a silent, extremely common bug. id exists to connect the label; name exists to carry the value.
Buttons
<button> defaults to type="submit" inside a form. A button meant to do something else must say type="button" or it will submit the form. Per-button overrides — formaction, formmethod, formnovalidate, formtarget — let one form have several destinations.
<fieldset> and <legend>
Groups related controls and gives the group a name. Essential for radio groups and checkbox groups, where the individual labels ("Yes", "No") are meaningless without the question. Disabling a fieldset disables everything inside it.
The form attribute
A control anywhere in the document can be associated with a form by id: <button form="checkout">. Useful when layout forces a submit button outside the form element.

Intercepting submission properly

Enhance, do not replace JavaScript
form.addEventListener('submit', async (e) => {
  // Native validation has already run and blocked invalid submits,
  // unless the form or the submitter has [novalidate].
  e.preventDefault();

  const data = new FormData(form, e.submitter);  // 2nd arg includes the
  // clicked button's own name/value — often forgotten

  const body = new URLSearchParams(data);       // urlencoded…
  // …or send `data` directly for multipart, or:
  const json = Object.fromEntries(data);        // ⚠ drops duplicate keys
  const tags = data.getAll('tags');             // ✓ keeps them

  const res = await fetch(form.action, { method: 'POST', body });
  // …handle result, restore the button, announce the outcome
});
Three submission bugs that ship constantly

1. Object.fromEntries(formData) silently keeps only the last value for repeated names, so multi-selects and checkbox groups lose data. Use getAll(). 2. Forgetting e.submitter means the server cannot tell which of two buttons was pressed. 3. Not disabling the submit button during the request, so an impatient user creates three orders. Disable it, and re-enable it in a finally block or the form is dead after any error.

3Labels and the accessible name

Every control needs a name. There are six ways to give it one, they have a strict precedence order, and the popular option is the worst.

The accessible name is the string assistive technology announces for a control. It is computed by an algorithm with a defined order, and understanding that order explains most "why is my label ignored" bugs.

The two correct ways to label an input HTML
<!-- Explicit: `for` matches the input's `id`. Preferred — works anywhere
     in the document and survives layout changes. -->
<label for="email">Email address</label>
<input id="email" name="email" type="email">

<!-- Implicit: the input is inside the label. No ids needed, but
     harder to style and some older assistive tech handles it poorly. -->
<label>Email address
  <input name="email" type="email">
</label>

Both give you the second benefit of a real label, which people forget: clicking the label focuses the control, and for a checkbox or radio it toggles it. That enlarges a 16-pixel tap target to the full width of the text, which matters enormously on touch.

A placeholder is not a label

It disappears the moment the user types, so anyone interrupted mid-form loses the question. Its default contrast fails WCAG in most browsers. It is announced inconsistently — sometimes as the name, sometimes as a description, sometimes not at all. It defeats autofill heuristics. And a field that looks filled-in when it is empty confuses everyone. Use a visible <label>; use the placeholder for a format example if at all, and even then a hint below the field is better because it stays visible.

Accessible name computation Toggle the sources. The precedence order is the specification's, not a preference.

Grouped controls

Radios and checkboxes need a group name too HTML
<fieldset>
  <legend>How should we contact you?</legend>

  <label><input type="radio" name="contact" value="email"> Email</label>
  <label><input type="radio" name="contact" value="post"> Post</label>
</fieldset>

<!-- Without the fieldset, a screen reader announces only "Email, radio
     button, 1 of 2" — with no idea what the question was. -->

Radios sharing a name form one group: arrow keys move between them, only one can be selected, and the group takes a single tab stop. Checkboxes with the same name are independent and each takes its own tab stop; they submit as repeated keys, which is why getAll() matters.

4The input types

Twenty-two of them. Choosing the right one changes the keyboard, the validation and the autofill behaviour on every phone in the world.

inputmode and enterkeyhint: the two attributes nobody uses

Control the on-screen keyboard without changing validation HTML
<!-- A 6-digit code: numeric keypad, but no spinner, no scroll-wheel
     surprises, leading zeros preserved. -->
<input type="text" inputmode="numeric" pattern="[0-9]{6}"
       autocomplete="one-time-code" enterkeyhint="done">

inputmode:    none | text | decimal | numeric | tel | search | email | url
enterkeyhint: enter | done | go | next | previous | search | send

The other controls

<textarea>
Its value is its text content, not a value attribute — so whitespace in your template becomes whitespace in the field. rows sets the initial height; auto-growing needs script or the field-sizing: content CSS property.
<select> and <optgroup>
Native, keyboard-accessible, and rendered by the OS on mobile. A custom replacement must reimplement type-ahead, arrow navigation, Home/End, screen-reader announcements and touch behaviour. Under about seven options, radios are usually kinder. multiple selects are notoriously hard to use — prefer checkboxes.
<datalist>
Suggestions attached to a text input that do not restrict what can be typed. Styling is not possible and behaviour differs across browsers, but for optional autocomplete over a short list it is free.
<output>
A calculated result. Implicitly a live region, so changes are announced — perfect for showing a slider's value or a running total.
<progress> and <meter>
Task completion versus a measurement within a known range. <progress> with no value is indeterminate.

5The Constraint Validation API

Browsers ship a validation engine. Most teams write their own without ever looking at it.

Attributes declare the constraints; the browser enforces them, blocks submission, and produces a localised message. JavaScript can inspect the result, add custom rules, and take over the presentation — which is usually what you want, because the native bubble is unstyleable and disappears on the next click.

AttributeConstraintValidityState flag when it fails
requiredMust not be emptyvalueMissing
type="email|url"Must match the formattypeMismatch
patternMust match the regex — anchored automatically, and always add title to explain itpatternMismatch
minlength / maxlengthCharacter count. maxlength also blocks typingtooShort / tooLong
min / maxNumeric or date boundsrangeUnderflow / rangeOverflow
stepValue must fall on the step grid. step="any" disables itstepMismatch
setCustomValidity(msg)Your own rulecustomError

Also: badInput when the user typed something the control cannot parse at all, and valid, which is true when every other flag is false.

Validity inspector A real input with real constraints. Every flag below is read live from the browser.
:valid :invalid :user-valid :user-invalid :required :placeholder-shown

The styling problem, and its fix

:invalid matches an empty required field the moment the page loads, so styling it red paints the whole form in errors before the user has typed a character. The old workaround was a JavaScript class toggle. The modern answer is a CSS pseudo-class:

Only complain after they have had a go CSS
/* ✗ Red before the user has done anything */
input:invalid { border-color: red; }

/* ✓ Matches only after the user has interacted and then blurred
   or attempted submission. Widely supported. */
input:user-invalid { border-color: red; }
input:user-valid   { border-color: green; }
form.checkValidity()
Returns a boolean and fires an invalid event on each failing control. Shows nothing.
form.reportValidity()
Same, but also focuses the first invalid control and shows the native bubble.
novalidate
On the form, stops the browser blocking submission — while keeping all the validity state available to your code. This is the standard setup for custom messaging: declare constraints in HTML, suppress the native UI, read the flags yourself.
setCustomValidity()
Sets customError and the message. Must be cleared with an empty string when the value becomes valid, or the field is stuck invalid forever. This catches everyone once.

6Error messaging that works

Where the message goes, when it appears, and what it says. All three are usually wrong.

Where: wire it to the field

The full accessible pattern for one field HTML
<label for="pw">New password</label>
<p id="pw-hint" class="hint">At least 12 characters.</p>

<input id="pw" name="password" type="password"
       autocomplete="new-password" minlength="12" required
       aria-describedby="pw-hint pw-error"
       aria-invalid="true">

<p id="pw-error" class="error">Password must be at least 12 characters.</p>
aria-describedby
Takes a space-separated list of ids, all announced after the label. Point it at both the hint and the error container permanently, and leave the error container empty when there is no error — that way you never have to add and remove the attribute, which is where sync bugs live.
aria-invalid="true"
Announces the field as invalid. Set it only when an error is actually showing; remove it or set false when fixed.
An error summary
On submit, render a list of every error at the top of the form, each item a link to the offending field, and move focus to it. This is the pattern the UK Government Digital Service tested extensively and it beats per-field-only messaging for long forms — a user with a magnifier or a small screen otherwise cannot find what failed.

When: not on every keystroke

MomentShow errors?Why
While typing, first attemptNo"Invalid email" after the second character is nagging, not helping.
On blurYesThey have finished with the field. This is the right first moment.
While typing, after it has already failedYesNow live feedback is welcome — it confirms the fix as they make it.
On submitYesEverything, plus the summary, plus focus moved to it.
Password strengthLiveThe exception. Show requirements from the start and tick them off as they are met.

What: name the fix, not the failure

Instead ofWrite
"Invalid input""Enter a date in the past"
"Field required""Enter your postcode"
"Password does not meet requirements""Add at least one number to your password"
"Error 422""That email address is already registered. Sign in instead?"

And never clear the user's input because it failed validation — particularly passwords. Making someone retype everything is the fastest way to lose them.

7Autofill and autocomplete

One attribute, a fixed vocabulary, and a measurable effect on completion rates.

autocomplete is not a hint — it is a defined token list that browsers and password managers match against. Getting it right means a user completes checkout in two taps. Getting it wrong, or writing autocomplete="off", means they type an address on a phone keyboard.

GroupTokens
Identityname, given-name, family-name, additional-name, nickname, honorific-prefix, organization
Credentialsusername, current-password, new-password, one-time-code
Contactemail, tel, tel-national, tel-extension, url
Addressstreet-address, address-line1–3, address-level1–4, postal-code, country, country-name
Paymentcc-name, cc-number, cc-exp, cc-exp-month, cc-exp-year, cc-csc, cc-type
Prefixesshipping and billing qualify an address group: autocomplete="shipping postal-code"
Sectionssection-* separates two of the same thing on one page: autocomplete="section-passenger1 given-name"
The password-manager triad

A sign-in form needs autocomplete="username" and autocomplete="current-password". A registration or change-password form needs autocomplete="new-password" on both the new field and the confirmation — this is what makes browsers offer to generate a strong password. Getting these two wrong is why so many sites save the wrong credentials.

autocomplete="off" is widely ignored on login fields (browsers decided user benefit outweighed the developer's preference) and is a genuine accessibility barrier elsewhere. The legitimate uses are narrow: a one-time code field, or a shared kiosk.

8File uploads and the server boundary

The last stretch, including the part where you stop trusting anything the browser sent.

File inputs

Reading, validating and uploading with progress HTML + JavaScript
<label for="docs">Upload receipts</label>
<input id="docs" name="docs" type="file"
       accept=".pdf,image/*" multiple>

// `files` is a FileList, not an array
const files = [...input.files];
for (const f of files) {
  if (f.size > 10 * 1024 * 1024) reject(f, 'Files must be under 10 MB');
  // f.type comes from the OS and is trivially spoofed — the server
  // must sniff the real content type itself.
}

// fetch() has no upload progress event; XHR still does.
const xhr = new XMLHttpRequest();
xhr.upload.addEventListener('progress', e => {
  if (e.lengthComputable) bar.value = e.loaded / e.total;
});
Styling the control
The native button is essentially unstyleable. The accessible approach is a real <input type="file"> visually hidden with a clip-path technique (never display: none, which removes it from the tab order) plus a <label> styled as a button. The label already focuses and activates the input, so no JavaScript is needed.
Drag and drop
An enhancement, never the only route. Handle dragover with preventDefault() or the browser navigates to the file, and read e.dataTransfer.files on drop. Keyboard and screen-reader users need the file input regardless.
Large files
Beyond tens of megabytes, upload directly to object storage with a pre-signed URL rather than through your application server, and consider chunked or resumable uploads. Mobile connections drop.

Everything you validated, validate again

Chapter 1's third constraint applies most sharply here. Every client-side rule is a courtesy; the server enforces. Specifically:

  • required, maxlength and pattern are removable in devtools in three seconds.
  • <input type="hidden"> and disabled attributes are editable. A price in a hidden field is a free-shopping bug.
  • <select> options can be edited, so a value outside your list will arrive eventually.
  • File accept filters a dialog. It does not stop an upload of anything at all.
  • Requests need not come from your form at all — curl works fine.
CSRF
A form on another site can POST to yours with the user's cookies attached. Defences are anti-CSRF tokens and SameSite cookies. Chapter 27.
Spam
A hidden honeypot field that real users never fill, plus a minimum time-to-submit, removes most low-effort bots without a CAPTCHA. Label the honeypot with aria-hidden="true" and tabindex="-1" so assistive technology does not present it.
Rate limiting
Server side, always. On the client, disable the submit button and show progress so honest users do not need to retry.

9Check yourself

Six questions. Two of them are the bugs you are most likely to ship this month.

1. A form submits successfully but one field's value never arrives at the server. The input renders, has an id, and is definitely filled in. What is missing?

The name attribute. Only named controls are serialised into the form data — id exists to associate the label and is never submitted. It fails silently with no console warning, which is why it is such a durable bug. Two related cases: an unchecked checkbox is not submitted at all (so the server sees an absent key, not false), and a disabled control is never submitted even when it has a value.

2. Why does styling input:invalid red usually look broken, and what should you use instead?

Because an empty required field is invalid from the moment the page loads, so the entire form appears in an error state before the user has typed anything. :user-invalid matches only after the user has interacted with the control and left it, or attempted to submit — which is the moment an error message is actually helpful. Its counterpart :user-valid gives you the green confirmation state with the same timing.

3. You add setCustomValidity() to check that two password fields match. It works once and then the field is permanently invalid. Why?

Because setCustomValidity() is sticky. Once you set a non-empty message, the customError flag stays true until you explicitly call setCustomValidity(''). The pattern is to call it on every check — with the message when the rule fails, and with an empty string when it passes — rather than only calling it on failure.

4. Your checkout collects a card number with <input type="number">. List the problems.

The scroll wheel and arrow keys silently change the value while the user is scrolling the page. Leading zeros are stripped. Spaces and grouping separators are rejected, so the user cannot format it readably. The spinner arrows are meaningless for an identifier. Values above 253 lose precision. And maxlength does not apply to type="number" at all. The correct control is type="text" with inputmode="numeric", autocomplete="cc-number" and a pattern. The rule generalises: type="number" is for quantities you would do arithmetic on, not for digit strings.

5. Your form has an aria-label on an input and a visible <label for>. Which one does a screen reader announce, and why is this a problem?

aria-label wins — it sits above <label> in the accessible name computation, and it silently overrides the visible text. That creates a mismatch between what a sighted user reads and what a screen-reader user hears, which breaks voice-control software outright: someone saying "click Email address" finds nothing, because the accessible name is something else. WCAG's "label in name" criterion requires the visible label text to be contained in the accessible name. If both exist, delete the aria-label.

6. A registration form uses autocomplete="off" on the password field "for security". What actually happens?

Browsers largely ignore it on credential fields, so the intended effect does not occur. What it does achieve is suppressing the offer to generate a strong password, which pushes users towards reusing a memorable one — the opposite of the security goal. The correct markup is autocomplete="new-password" on the new and confirmation fields, and autocomplete="username" plus autocomplete="current-password" on sign-in. Password managers are a security improvement; the form's job is to cooperate with them.
