CHAPTER 12

CSS at scale

CSS is easy to write and hard to delete. On a project of any size the difficulty is never a property you cannot remember — it is that nobody can tell whether removing a rule will break a page nobody has opened this quarter. This chapter is about the four architectures the industry converged on, what each actually buys, and the token layer underneath all of them.

Part 3 CSS·Reading time 45 minutes·Demos approach comparator, token pipeline·Prerequisites Chapters 8–11

1Why CSS rots

Four structural properties of the language, none of them bugs, that combine badly at scale.

One global namespace
Every selector can match every element in the document. There is no module boundary. A rule written for the marketing page applies to the checkout, and nothing warns you.
Source order matters
Criterion 6 of the cascade. Change the order files are concatenated in — by adding an import, by a bundler chunking differently — and appearance changes with no diff in any rule.
Specificity only ratchets upwards
The cheapest way to make a change stick is a more specific selector. Do that for two years and the floor rises until nothing can be overridden without !important.
Deleting is unsafe
You cannot statically prove a class is unused when class names are built at runtime, injected by a CMS, or referenced by a test. So nobody deletes, and the stylesheet only grows.

Put together, these produce the same failure everywhere: append-only CSS. Each change is a new rule at the bottom of the file, slightly more specific than the last, because that is the only edit guaranteed not to break something else. Every approach in this chapter is an attempt to break that cycle by making one of the four properties untrue.

ApproachWhich property it attacks

2Naming conventions

The zero-tooling answer. Still the right one for a great many projects.

BEM — Block, Element, Modifier — encodes the component boundary in the class name itself.

BEM, and what it is actually doing CSS
/* block__element--modifier */
.card { }
.card__title { }
.card__media { }
.card--featured { }
.card__title--truncated { }

/* The point is not the underscores. It is that every selector is a
   SINGLE CLASS, so every rule has specificity (0,1,0) and source
   order is the only tie-break. Nothing can ratchet. */

/* ✗ This throws the benefit away */
.card .card__title span a:hover { }   /* (0,3,2) and coupled to markup */
What it gets right
Flat specificity, obvious ownership, a class name that tells you where the rule lives, and no build step at all.
What it does not solve
Nothing enforces it. One developer writing .card .title reintroduces the coupling, and no tool complains. Names get long, and nested components produce .product-card__footer__action--disabled.
Relatives
SUIT CSS uses ComponentName-descendant--modifier. SMACSS categorises rules (base, layout, module, state, theme). ITCSS orders the whole stylesheet by increasing specificity — settings, tools, generic, elements, objects, components, utilities — which is essentially what cascade layers now do natively and better.
The modern minimum

Single-class selectors, one component per file, and @layer for ordering. That combination gets you most of the benefit of any architecture in this chapter with no tooling, and it is a perfectly defensible choice for a team of any size.

3Preprocessors, and what is left of them

Sass won, then CSS absorbed most of its features. Here is the honest remainder.

Sass featureNative CSS nowStill worth it?
VariablesCustom propertiesNo — and custom properties are strictly better, because they are live at runtime and inherit
NestingNative nestingNo
Partials and @use@import is discouraged; bundlers handle itMarginal — your build tool already concatenates
Mixins with arguments—Yes. No native equivalent for emitting a parameterised block of declarations
Loops and maps—Yes. Generating a 12-step spacing scale or a utility set by hand is miserable
Functions with logiccalc, min, max, clamp, color-mixMostly covered now
Compile-time colour mathscolor-mix, relative colour syntaxNo, and the native versions work at runtime with theme variables

Net: reach for Sass when you need to generate CSS from data — scales, utility sets, theme matrices. Do not reach for it for variables and nesting; those are the platform's now.

PostCSS is a different tool that gets confused with preprocessors. It is a plugin pipeline that transforms CSS you have already written: Autoprefixer adds vendor prefixes from your browserslist, postcss-preset-env polyfills newer syntax, and plugins can lint, minify or inline assets. It composes with everything here, including Sass, and with Tailwind, which is itself a PostCSS plugin.

4Scoped styles

Make the global namespace untrue, enforced by a machine rather than a convention.

CSS Modules
Write ordinary CSS in Button.module.css; the build tool rewrites every class to a unique hashed name and gives you an object mapping originals to generated names. Zero runtime, works with any framework, and collisions become impossible. The composition primitive is composes:, and :global() is the escape hatch.
Single-file component scoping
Vue's <style scoped> and Svelte's default behaviour add a generated attribute to elements and to selectors. Same effect, no separate file, and the framework can strip styles it can prove are unused within the component.
CSS-in-JS, runtime
styled-components, Emotion. Styles are JavaScript, so they can be computed from props. The cost is real: a runtime that injects rules during render, larger bundles, and awkward interaction with server components and streaming. Its popularity has fallen sharply for exactly these reasons.
CSS-in-JS, zero-runtime
vanilla-extract, Linaria, Panda CSS, StyleX. You author in TypeScript, get type-checked tokens and autocomplete, and the build extracts static CSS files. This is where the CSS-in-JS idea ended up: the developer experience without the runtime.
Shadow DOM
The platform's own scoping, and the strongest — page styles genuinely cannot reach in, except through custom properties and ::part(). That strength is also the drawback for app code. Chapter 20.
@scope
Native scoping without a build step: @scope (.card) to (.card__content) { … } limits a block to a subtree and can exclude an inner boundary, which finally solves "style this component but not the widget nested inside it".

5Utility CSS

      
The approach that provokes the strongest reactions, stated fairly in both directions.


      
Utility CSS inverts the model: instead of naming components and describing them in a stylesheet, you compose from a fixed set of single-purpose classes in the markup. class="flex items-center gap-3 rounded-lg p-4 bg-white shadow-sm".


      

        

          
The case forThe case against

          
            

              The stylesheet stops growing. Utilities are reused, so CSS size flattens while the app keeps growing — the append-only cycle is broken structurally.
              Markup gets noisy. A dense component can carry thirty classes on one element, and diffs become hard to read.
            

            

              No naming. A genuine share of front-end time goes on inventing class names for wrappers that have no meaning.
              You are still naming — in the component layer instead. If you have no component layer, you are copy-pasting.
            

            

              Deleting a component deletes its styles, automatically. Dead CSS becomes structurally impossible.
              Design decisions live in markup, so a global change needs a find-and-replace across templates unless you disciplined yourself into tokens.
            

            

              Constraint by default: spacing and colour come from a scale, so nobody types 13px.
              Escaping the scale is deliberately awkward, which is a feature until the day it is not.
            

            

              Locality. Everything about an element is visible where the element is, with no file-hopping.
              Learning curve: an abbreviation vocabulary on top of CSS, and it is tool-specific knowledge.
            

          
        

      


      

        
How it works mechanically

        
A scanner reads your source files, finds candidate class names, and generates only the CSS for the ones present. Nothing you did not use is emitted. The critical constraint follows: class names must appear as complete literal strings. `text-${color}-500` generates nothing, because the scanner never sees the finished name.

        
Where the component layer goes

        
Into your components. In a framework, <Button variant="primary"> holds the class list in one place and the repetition problem disappears. In a template language, a partial does the same job. Utility CSS without a component abstraction genuinely is copy-paste, and that is the fair version of the criticism.

        
The honest fit

        
It suits application UI built from components and maintained by a team. It suits long-form editorial content less well — that is what a typography plugin or a scoped .prose block is for. And it does not remove the need to know CSS; every utility maps to a declaration you still have to understand.

These combine. A very common shape is: cascade layers for ordering, custom properties for tokens, CSS Modules or utilities for components, and one small global layer for the reset and base typography.

      

    


    
    

      
6Design tokens

      
The layer underneath every approach above. Get this right and the rest matters much less.


      
A design token is a named design decision. The value of the system is not the names — it is the indirection: components refer to intent, intent refers to a value, and you can change the value without touching a component.

Naming

        
Semantic names describe role, never appearance. --color-danger survives a rebrand; --color-red becomes a lie the day danger turns orange. The same applies to --space-card-gap versus --space-12px.

        
Distribution

        
Tokens usually live in one source of truth — often JSON in the DTCG format — and a tool such as Style Dictionary generates CSS custom properties, a TypeScript module, iOS and Android resources, and Figma variables from it. That is what stops the design tool and the code drifting apart.

        
Theming

        
Override tier 2 only. A dark theme, a high-contrast theme and a white-label brand are each a block redefining semantic tokens. Components never change. Scope by attribute ([data-theme="dark"]) rather than a class if you also want @container style() queries against them.

        
Numbers in a numeric scale

        
Prefer 100…900 over light/medium/dark. You will need a value between two of them within a year, and --blue-450 is easier to justify than --blue-medium-light.

      

    


    
    

      
7Practical hygiene

      
Six things worth setting up once, in the order they pay off.


      

        
A layer order that works for real applications CSS

        
@layer reset, tokens, base, layouts, components, utilities, overrides;

/* reset      – box-sizing, margin zeroing, media defaults
   tokens     – :root custom properties, theme blocks
   base       – element defaults: body type, headings, links, form controls
   layouts    – page-level composition primitives (stack, sidebar, grid)
   components – buttons, cards, tables
   utilities  – single-purpose helpers, must win over components
   overrides  – the deliberate escape hatch, reviewed and rare */

      


      

        
A modern reset, not a normalisation

        
Five to fifteen lines is enough now: box-sizing: border-box everywhere, zero the default margins, img, svg, video { display: block; max-inline-size: 100% }, font: inherit on form controls, line-height and text-size-adjust on the root, and a prefers-reduced-motion guard. Normalize.css solved 2012's browser inconsistencies and mostly is not needed.

        
Stylelint

        
The CSS equivalent of ESLint. The rules worth turning on immediately: no descending specificity, maximum specificity limits, no duplicate selectors, no unknown properties, and a property-order convention so diffs stay small.

        
Finding dead CSS

        
Devtools Coverage tab shows unused bytes on a loaded page — useful, but per-page and only for the paths you exercised. Static tools such as PurgeCSS work from your source. Neither can prove a class built at runtime is unused, which is exactly why utility CSS and scoped modules sidestep the problem instead of solving it.

        
Critical CSS

        
Inline the rules needed for the visible area, load the rest asynchronously. It removes a render-blocking round trip (Chapter 1's simulator). Worth it for content sites with a cold-cache-heavy audience; usually not worth the build complexity for an authenticated application.

        
Budgets

        
Put a byte budget on the stylesheet in CI and fail the build when it is exceeded. A number that must be argued with is the only mechanism that reliably prevents drift.

        
Document decisions where they are made

        
A short comment above a non-obvious rule saves more time than a wiki page nobody opens. Especially for anything that exists to work around a browser bug — record the browser, the version and the symptom, or it will never be deleted.

      

    


    
    

      
8Check yourself

      
Five questions closing Part 3.


      

        
1. A colleague argues that BEM is unnecessary now that we have CSS Modules. Are they right?

        
        

          
Partly. CSS Modules solve the problem BEM's naming exists to solve — collisions — and solve it by enforcement rather than convention, so the block__element prefixes become redundant noise inside a module. But BEM's second, less-discussed benefit remains: the discipline of single-class selectors, which keeps specificity flat. It is entirely possible to write .card .title a:hover inside a CSS Module and reintroduce the ratcheting. Keep the flat-specificity habit, drop the naming ceremony.

        

      


      

        
2. Your utility-CSS build produces no styles for a class you can see in the browser inspector. Why?

        
        

          
Because the class name was constructed at runtime rather than written as a literal string. The scanner does a textual pass over your source files looking for complete candidate names; `bg-${colour}-500` or 'text-' + size never appears in the source as a finished name, so no rule is generated — the class lands in the DOM and matches nothing. The fix is to write the full strings out, usually as a lookup map from a variant name to a complete class string, so every possible value is statically visible.

        

      


      

        
3. Why should a component reference --color-action rather than --blue-500?

        
        

          
Because the indirection is where theming happens. If components point at primitives, a dark theme or a white-label brand has to redefine every primitive — and primitives are named after their values, so --blue-500 holding an orange is nonsense. With a semantic tier, a theme is a single block redefining perhaps thirty role-named tokens, and no component file changes at all. The rule of thumb: primitives are the palette, semantics are the decisions, and only decisions get consumed.

        

      


      

        
4. You inherit a codebase with 340 uses of !important. What is the first structural change to make?

        
        

          
Introduce cascade layers and move the third-party and legacy stylesheets into an early layer. Because layer order is compared before specificity (Chapter 8, criterion 4), your own rules in a later layer win without needing any !important at all — which lets you delete them incrementally rather than in one risky sweep. Do not start by removing them one at a time; each removal is a behavioural change with no test coverage. Change the structure so they become unnecessary, then delete.

        

      


      

        
5. Is Sass still worth adding to a new project?

        
        

          
Only for what CSS still cannot do: mixins that emit a parameterised block of declarations, and loops or maps that generate CSS from data — a spacing scale, a utility set, a theme matrix. Variables, nesting and colour manipulation are all native now, and the native versions are better because they work at runtime and participate in the cascade. If your project has no generation needs, adding Sass buys a build step and a second syntax for no benefit. If it does, the generation features alone can justify it.
