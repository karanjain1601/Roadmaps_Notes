CHAPTER 03

Inside the rendering engine

Five stages turn your bytes into pixels, and every performance problem you will ever debug is one of them running too often or taking too long. This chapter walks the pipeline, then hands you two demos that measure it in the page you are reading.

Part 1 The platform·Reading time 40 minutes·Demos frame cost, layout thrashing·Prerequisites Chapters 1–2

1The pipeline, end to end

Five stages, always in this order, and you can sometimes skip the expensive ones.

Everything a browser does visually runs through the same sequence. Learn the order and the cost of each stage and you can predict, from a line of CSS, how expensive an animation is going to be — before you write it.

Two vocabulary notes before the detail. Reflow is an older word for layout, still used everywhere including in devtools. Repaint means paint without layout. And "the main thread" means the single thread on which parsing, style, layout, paint scheduling, JavaScript and event handling all take turns — Constraint 2 from Chapter 1.

2Stage 1 — parsing

Bytes to characters to tokens to nodes to a tree, incrementally, and interruptibly.

The HTML parser is a streaming state machine. It does not wait for the whole document. Bytes are decoded to characters using the encoding — declared by <meta charset="utf-8">, which must appear in the first 1024 bytes or the parser may have to restart — then tokenised into start tags, end tags, text and comments, then assembled into the DOM tree.

HTML parsing is famously forgiving. Unclosed tags are closed for you, misnested tags are re-parented, and invalid structure produces a well-defined tree rather than an error. This is a specified algorithm, not guesswork: every browser produces the same DOM from the same malformed input. It is also why "it renders fine" is not evidence that your markup is correct.

The three script behaviours

Scripts are the parser's problem, because a script can call document.write and change the very stream being parsed. The browser therefore stops.

Two more rules that surprise people: a script placed after a stylesheet waits for that stylesheet, because it might read a computed style. And defer scripts run in order while async ones race, so async on two files where one depends on the other is a bug that appears only on slow connections.

The preload scanner

While the main parser is blocked on a script, a secondary lightweight parser races ahead through the raw bytes looking for things it can start downloading: src, href, srcset. This is why a blocking script hurts less than it theoretically should, and it is also why some optimisations quietly defeat it.

Things the preload scanner cannot see

Anything constructed by JavaScript. An image whose src is assigned in a script, a stylesheet injected by a loader, a background image referenced only from a CSS file that has not downloaded yet, a font referenced from that same stylesheet. Every one of these is discovered one or two round trips later than a plain tag in the HTML would have been. If a resource is important and known at build time, put it in the markup — or hint it with preload.

3Stage 2 — style

Every element gets a complete set of computed values. There is no "unset" at the end of this stage.

The browser parses every stylesheet into the CSSOM, then for each element in the DOM works out the value of every CSS property. Not just the ones you declared — all of them, from your declarations, inherited values, or the initial value defined in the specification. The result is the computed style, and it is what the Computed tab in devtools shows you.

Selector matching runs right to left

Given .sidebar ul li a, the engine does not find sidebars and walk down. It takes every <a> and walks up, checking each ancestor condition, bailing out as soon as one fails. Right-to-left evaluation means the rightmost part of the selector — the "key selector" — determines how many elements are considered at all.

The practical guidance this used to generate ("avoid descendant selectors, they are slow") is largely obsolete; modern engines index rules by the key selector and style recalculation is rarely the bottleneck. What still matters is the number of elements whose style must be recalculated when something changes. Adding a class to <body> can invalidate the style of the entire document.

The render tree

DOM plus CSSOM produces a tree of boxes to be rendered. Two exclusions worth remembering, because they behave differently:

display: none
The element generates no box at all. It is absent from layout, takes no space, and its subtree is skipped. Toggling it forces a full layout of the surrounding content.
visibility: hidden
The box exists and occupies space; it is simply not painted. Toggling it costs paint, not layout.
opacity: 0
The box exists, occupies space, is painted, and is composited at zero alpha. Still hit-testable — a common accessibility bug, because it stays in the accessibility tree and remains clickable.

4Stage 3 — layout

The expensive one. Position and size for every box, and it is global by nature.

Layout computes the exact geometry of every box: where it starts, how wide it is, how tall the text makes it, where the next box therefore begins. It works in one pass down the tree and, for some layout modes, additional passes back up.

The cost is superlinear in the number of boxes and, crucially, changes propagate. Making one paragraph one pixel wider can change where every following element sits. This is why layout is the stage worth avoiding, and why the containment properties in section 8 exist.

5Stages 4 and 5 — paint and composite

Turning geometry into coloured pixels, then stacking the results.

Paint

Paint fills in the actual pixels: backgrounds, borders, text glyphs, shadows, images. It happens in a specific order derived from the stacking contexts described in Chapter 9 — backgrounds first, then floats, then inline content, then positioned elements — so that things overlap correctly.

Paint is done into one or more layers. Most of the page is a single layer. Some content gets promoted to its own layer so it can be moved without repainting everything underneath.

Compositing

The layers are handed to the compositor, which positions and stacks them, usually on the GPU. This is the cheap stage: moving an existing layer around is close to free, because no pixels are recomputed — the same texture is drawn at a different offset.

This is the whole reason transform and opacity are the two properties everybody tells you to animate. They can be handled entirely by the compositor, sometimes on a separate compositor thread, which means an animation using them keeps running smoothly even while the main thread is busy executing JavaScript. An animation of left cannot: every frame needs layout and paint on the main thread, so it stutters the moment anything else runs.

Layer promotion

What promotes an element
3D transforms, will-change: transform or opacity, video and canvas elements, elements with a CSS animation on a compositable property, position: fixed in some engines, and backdrop-filter.
The cost
Each layer consumes GPU memory — roughly width × height × 4 bytes, before device pixel ratio, so a full-screen layer on a retina display is several megabytes. Too many layers and you trade a main-thread problem for a memory problem, which on a cheap phone is worse.
How to use will-change
Sparingly, added shortly before the animation and removed after. Applying it to a hundred elements permanently in a stylesheet is the classic misuse; it is a hint to the browser, not a performance switch.

6The frame budget

16.7 milliseconds, shared between your code and the browser's. Here is what fits.

At 60 Hz a frame is 16.7 ms. The browser needs part of that for style, layout, paint and composite, so the working budget for your JavaScript is nearer 8–10 ms. Miss it and a frame is dropped: the previous image stays on screen for two refresh intervals and the eye reads it as a stutter.

Within a frame the order is fixed. Input events fire, then requestAnimationFrame callbacks run, then style, layout, paint and composite. Anything scheduled with requestIdleCallback runs only if time is left over. Chapter 15 places this inside the larger event-loop picture.

7Layout thrashing

The most common self-inflicted performance bug in front-end code, and the easiest to fix.

The browser batches style changes. When you set el.style.width, nothing is computed immediately — the change is queued and layout happens once, later, before the next paint. That batching is what keeps DOM manipulation affordable.

Reading a layout property breaks the batch. Because offsetHeight must be accurate, the browser has to flush every pending change and run layout right now, synchronously. Do that once and you have paid for one extra layout. Do it inside a loop, alternating a write and a read, and you force a full layout on every single iteration.

The bug and the fix JavaScript
// ✗ Thrashing: write, read, write, read — one forced layout per item
for (const box of boxes) {
  box.style.width = '0px';                // invalidates layout
  box.style.width = box.offsetWidth + 'px';  // forces layout NOW
}

// ✓ Batched: every read first, then every write
const widths = boxes.map(b => b.offsetWidth);  // one layout, at most
boxes.forEach((b, i) => { b.style.width = widths[i] + 'px'; });

// ✓ Or move the reads into a rAF callback so they happen once per frame
requestAnimationFrame(() => {
  const rect = el.getBoundingClientRect();   // read phase
  requestAnimationFrame(() => {
    el.style.transform = `translateY(${rect.top}px)`; // write phase
  });
});

Both loops read every element's width and set it back. The only difference is whether the reads and writes alternate.

The general rule

Separate your reads from your writes. Do all measurement, then all mutation. If a library needs to do both, it should batch across the whole frame rather than per element — this is the entire premise of "FastDOM"-style schedulers, and of why frameworks batch DOM updates instead of applying them as you call setState. 8Opting out of work

Four CSS properties that let you tell the browser it can skip things. Plus how to see the pipeline for yourself.

Layout is global by default: the browser cannot know that a change inside one card is guaranteed not to affect the rest of the page. CSS containment lets you promise that it will not.

PropertyPromise you are makingEffect
contain: layout Nothing inside this element affects layout outside it Layout changes inside stop propagating up the tree. Big wins on long lists of independent cards.
contain: paint Descendants never paint outside this element's bounds Off-screen descendants can be skipped entirely; also creates a containing block and a stacking context.
contain: size The element's size does not depend on its contents Rarely used alone; you must supply the size yourself or it collapses.
content-visibility: auto Skip all rendering work for this subtree while it is off-screen The big one. Combine with contain-intrinsic-size so the scrollbar does not jump when content is skipped.
A long list of independent cards CSS
.card {
  /* Rendering work for off-screen cards is skipped entirely.
     The browser still needs a size guess so scrolling is stable. */
  content-visibility: auto;
  contain-intrinsic-size: auto 240px;
}
Containment has real side effects

contain: paint and content-visibility create a stacking context and a containing block for absolutely positioned descendants, and they clip overflow. A dropdown that escapes its card will stop escaping. Test the interactive parts, not just the scroll performance. Content skipped by content-visibility is also skipped by in-page find on some browsers — acceptable for a feed, not for documentation.

9Check yourself

Five questions. The first two are asked in interviews almost verbatim.

1. Why is animating transform: translateX() cheaper than animating left, when both move the element the same distance?

left changes geometry, so every frame must re-run layout, then paint, then composite — all on the main thread, and layout can propagate to sibling and descendant boxes. transform only changes how an already-painted layer is positioned when the layers are stacked, so only the composite stage runs, frequently on the compositor thread. The practical consequence is that a transform animation keeps running smoothly even while the main thread is blocked by JavaScript, and a left animation freezes.

2. What is layout thrashing and how do you fix it?

Alternating DOM writes and layout reads in a loop. Writes are normally batched and flushed once before paint, but reading a geometry property like offsetHeight forces the browser to compute layout immediately so it can return an accurate value. Interleaving them therefore forces one full layout per iteration instead of one for the whole loop. The fix is to separate the phases: perform every read first, store the values, then perform every write — or schedule reads and writes into different requestAnimationFrame callbacks.

3. Your team adds will-change: transform to every card in a 500-item list "for performance". What happens?

Five hundred composited layers, each costing roughly width × height × 4 bytes of GPU memory multiplied by the device pixel ratio. On a desktop it may be merely wasteful; on a phone it can exhaust GPU memory, at which point the browser falls back to software compositing and everything gets dramatically slower — the opposite of the intent. will-change is a hint for an element that is about to animate, applied shortly before and removed after, not a decoration for a stylesheet.

4. A page renders correctly but the text visibly jumps a moment after load. What is the most likely mechanism, and which pipeline stage is involved?

A web font finished downloading and replaced the fallback. The two faces have different metrics — character widths, ascender heights — so line breaks change and every following box moves: a full layout pass. It is measured as Cumulative Layout Shift. The fixes are covered in Chapter 11: font-display: optional or swap combined with metric overrides such as size-adjust and ascent-override on the fallback so the swap is geometrically neutral, plus preloading the font so it arrives before first paint.

5. You put content-visibility: auto on every section of a long article and scrolling gets much smoother, but the scrollbar now jumps around while scrolling and Ctrl+F stops finding some text. Why?

Off-screen sections are no longer laid out, so the browser does not know how tall they are and substitutes a guess — the scrollbar resizes as real heights are discovered. Supplying contain-intrinsic-size with a realistic estimate fixes that. The find-in-page behaviour is a genuine trade-off of skipping rendering work for hidden subtrees, and it is why containment suits feeds and lists rather than documents people search.
