CHAPTER 06

Accessibility

Not an audit you run at the end and not a checklist of ARIA attributes. Accessibility is the discipline of making sure the thing you built is operable by people using it in ways you did not picture. This chapter covers the machinery — the accessibility tree, roles, focus, live regions — and the specific defaults that get it right by construction.

1What this actually is

Four principles, one spectrum, and the reason the business case is easier than people expect.

Roughly one person in six lives with a disability. That framing undersells it, because disability is not a fixed category of other people — it is a mismatch between a person's current capability and the environment, and everyone's capability changes.

AbilityPermanentTemporarySituational
SightBlind, low visionEye surgery, dilated pupilsBright sunlight, driving, tiny phone screen
HearingDeafEar infectionLoud train, no headphones, sleeping baby
MotorLimb difference, tremorBroken arm, sprainHolding a bag, on a moving bus, cold hands
CognitiveDyslexia, ADHDConcussion, medicationDistracted, exhausted, new to the domain, second language

The right column is why accessible interfaces measurably work better for everyone. Captions are used mostly by hearing people. Large tap targets help everyone on a bumpy train. Clear error messages help everyone at 11 pm.

POUR: the four principles

Perceivable
Information must be available to at least one sense the person has. Text alternatives for images, captions for audio, sufficient contrast, content that survives 400% zoom.
Operable
Every function must be reachable and usable by every input method. Keyboard, switch device, voice, touch, mouse. No time limits you cannot extend, no seizure-inducing flashing.
Understandable
Readable language, predictable behaviour, errors that explain the fix. Navigation that stays in the same place.
Robust
Valid markup that assistive technologies past and future can parse. Correct roles, names and states, kept in sync.

WCAG (Web Content Accessibility Guidelines) organises success criteria under those four principles at three levels: A (bare minimum), AA (the level nearly every law and contract references), and AAA (not expected for a whole site). When someone says "we need to be accessible", they almost always mean WCAG 2.2 AA. The European Accessibility Act, the UK Equality Act, the US ADA and Section 508, and Canada's ACA all converge on it.

The one habit that matters most

Do it while building, not after. Retrofitting accessibility onto a finished component tree is expensive and produces bolt-on ARIA that drifts out of sync. Almost everything in this chapter is free if you make it a default: correct elements, visible focus, a real label, a keyboard pass before you open the pull request.

2The accessibility tree

Assistive technology never sees your DOM. It sees a derived tree, and that derivation is the whole game.

Alongside the DOM and the render tree from Chapter 3, the browser builds a third structure: the accessibility tree. It is a filtered, annotated version of the DOM exposed through the operating system's accessibility API — UI Automation on Windows, NSAccessibility on macOS, AT-SPI on Linux — which screen readers, voice control software, switch devices and browser extensions read.

Every node in it carries up to five things:

PropertyWhat it answersWhere it comes from
RoleWhat kind of thing is this?The element's implicit role, or an explicit role attribute that overrides it
NameWhat is it called?The accessible name computation from Chapter 5 — aria-labelledby, aria-label, <label>, content, alt, title
DescriptionAnything more to say?aria-describedby, or title when it was not used for the name
StateWhat condition is it in?Native (checked, disabled, open) or ARIA (aria-expanded, aria-pressed, aria-current)
ValueWhat does it hold?Input values, aria-valuenow for sliders and progress

What gets pruned

Nodes are removed from the tree by display: none, visibility: hidden, the hidden attribute, aria-hidden="true", and inert on an ancestor. Everything else, including purely presentational wrappers, is either exposed or collapsed into a generic node.

The aria-hidden trap

aria-hidden="true" removes a node from the accessibility tree but not from the tab order. Put it on a container holding a focusable element and you create the worst possible state: a keyboard user can tab to a control that the screen reader refuses to describe, so focus simply disappears into silence. If you need to hide interactive content, use inert or hidden, which handle both.

Seeing it yourself

Chrome and Edge

Safari

Get into the habit of opening this pane when you build a component. If the role is generic and the name is empty, you have built something invisible.

3ARIA, and its five rules

A vocabulary for describing widgets the platform has no element for. Powerful, and the most commonly misused tool in front-end work.

ARIA (Accessible Rich Internet Applications) adds attributes that change what the accessibility tree says about an element. Crucially, it changes only the tree. It adds no behaviour, no keyboard handling, no focus, no styling. role="button" does not make Enter work.

The five rules of ARIA use

1. Do not use ARIA if a native element will do
<button> beats <div role="button" tabindex="0"> every time. This rule alone removes most ARIA from most codebases.
2. Do not change native semantics unless you must
<h2 role="tab"> destroys the heading. Wrap instead: <div role="tab"><h2>…</h2></div>.
3. All interactive ARIA controls must be keyboard operable
If you declare role="slider" you owe arrow keys, Home and End. The role is a promise about behaviour that you must then keep.
4. Do not put role="presentation" or aria-hidden="true" on a focusable element
The trap from the previous section, stated as a rule.
5. Every interactive element needs an accessible name
An icon-only button with no text needs aria-label. This is ARIA's single most legitimate everyday use.
No ARIA is better than bad ARIA

This is the official guidance and it is backed by data: analyses of millions of home pages consistently find that pages using ARIA average more detected failures than pages without it. A missing aria-label leaves a control unnamed; a wrong role actively lies about what the control is, and the user believes it.

A disclosure widget with the minimum correct ARIA HTML
<!-- Native first. <details> needs none of this. But when you must
     build it yourself, this is the complete set. -->
<button id="trig" aria-expanded="false" aria-controls="panel">
  Delivery options
</button>
<div id="panel" hidden> … </div>

// Exactly one line of state, kept in one place
trig.addEventListener('click', () => {
  const open = trig.getAttribute('aria-expanded') === 'true';
  trig.setAttribute('aria-expanded', String(!open));
  panel.hidden = open;
});

For anything more complex — tabs, comboboxes, tree views, grids — do not invent the interaction. The ARIA Authoring Practices Guide specifies the exact roles, states and keyboard behaviour users expect for each pattern, and deviating from it is how you produce a widget that is technically labelled and practically unusable.

4Keyboard and focus

If it works with a keyboard alone, most of the rest follows. If it does not, nothing else you do matters.

Keyboard operability is the load-bearing requirement. Screen readers, switch access, voice control and mouth sticks all ultimately drive the same focus model, so a keyboard pass catches an enormous share of problems in about ninety seconds per page.

What is focusable by default

Links with href, all form controls, <button>, <summary>, <iframe>, elements with contenteditable, and anything with tabindex. Nothing else. A <div>, a <span> and an <li> are not focusable and never become so by adding a click handler.

ValueEffectUse
tabindex="0"Focusable, in document orderA custom widget that genuinely has no native equivalent. Rare.
tabindex="-1"Focusable by script only, not by TabVery common and correct: a dialog you move focus into, an error summary, a route-change target.
tabindex="1" or moreJumps ahead of every element with 0 or implicit orderEssentially always a bug. One positive value on the page reorders the whole document.
Tab order, computed Real elements in a sandbox. Step through the order the browser would use.

      Focus must be visible

      Removing the focus ring is the most damaging one-line change in front-end development, and it is still in thousands of stylesheets as outline: none. Without it a keyboard user has no idea where they are on the page.

      Restyle it; never remove it CSS
      /* ✗ Removes the only positional feedback a keyboard user has */
:focus { outline: none; }

/* ✓ :focus-visible applies the ring for keyboard focus but not for
   mouse clicks, which is what people were trying to achieve. */
:focus-visible {
  outline: 3px solid #1F6FA8;
  outline-offset: 2px;
  border-radius: 2px;
}

/* WCAG 2.2 requires the indicator to be at least 2px thick and to have
   3:1 contrast against BOTH the component and the adjacent background.
   A thin grey ring on a grey button fails. */

      Managing focus when things change

      Opening a modal
      Move focus into the dialog, trap it there, return it to the trigger on close, and mark the rest of the page inert. <dialog>.showModal() does all four natively — Chapter 4.
      Client-side route change
      The browser does not reset focus, so it stays on the link you just clicked while the entire page changes underneath. Move focus to the new page's <h1> (given tabindex="-1") and update document.title. Without this, screen-reader users have no idea navigation occurred. Chapter 19 revisits it.
      Deleting the focused element
      Focus falls back to <body> and the user is silently teleported to the top of the page. Before removing a row, move focus to the next row, the previous one, or the container.
      Revealing content
      For a disclosure, do not move focus — the trigger keeps it and aria-expanded reports the change. For a dialog or a wizard step, do move it.
      Roving tabindex
      In a composite widget — a toolbar, a tab list, a menu — the whole group takes one tab stop and arrow keys move within it. Exactly one child has tabindex="0" at a time; the rest have -1. This is how native radio groups and select menus behave, so it is what users expect.
      The ninety-second test

      Put the mouse down. Press Tab from the top of the page to the bottom. Three questions: can you see where you are at every step? can you reach every interactive thing? does the order match the visual order? Then open every menu, dialog and dropdown with Enter or Space, close each with Escape, and check where focus lands. Most accessibility bugs surface in that minute and a half.

      5How screen readers actually work

      Two modes, a virtual cursor, and why your beautiful component announces "clickable, clickable, clickable".

      A screen reader is not a linear text-to-speech engine reading top to bottom. Users navigate structurally, at speed — often 300 to 500 words per minute — and they jump.

      NavigationTypical keyDepends on
      Next headingH, or 1–6 by levelReal <h1>–<h6> elements
      List of landmarksD, or a dialogLandmark elements — Chapter 4
      List of linksK, or a dialog<a href> with meaningful text
      Next form fieldFReal form controls with names
      Next tableT, then arrow keys within<table> with scope

      Every row of this table is a feature you enable or destroy purely by element choice. Div soup does not just read badly — it removes the navigation entirely.

      Browse mode and focus mode

      On Windows, JAWS and NVDA operate in two modes. In browse mode the screen reader intercepts keystrokes for its own navigation, and a virtual cursor moves through a flattened copy of the page. In focus mode (also called forms mode) keystrokes pass through to the page so you can type.

      Switching is usually automatic: focusing a text input enters focus mode; leaving it exits. Custom widgets frequently break this — a role="application" container, or a listbox that traps arrow keys — leaving the user in the wrong mode with keys doing nothing they expect. It is the most common reason a widget "works with a keyboard" but is unusable with a screen reader. This is why testing with the keyboard alone is necessary but not sufficient.

      What to test with
      NVDA with Firefox or Chrome on Windows (free, and the most widely used combination worldwide). VoiceOver with Safari on macOS and iOS — turn it on with Cmd+F5, and learn the rotor. TalkBack with Chrome on Android. Testing on one is far better than testing on none.
      What you are listening for
      Does each control announce a role and a name? Does state change get announced? Can you complete the task without seeing the screen? Turn the monitor off for five minutes and try to buy something on your own site.

      6Live regions

      How to announce something that changed without moving focus. Small API, many sharp edges.

      When content updates without a navigation — a search result count, a saved confirmation, a validation error, a chat message — a sighted user notices. A screen-reader user does not, unless the region is marked live.

      MarkupBehaviourUse for
      aria-live="polite"
      or role="status"      		Announced when the user pausesAlmost everything: "3 results", "Draft saved", loading finished
      aria-live="assertive"
      or role="alert"      		Interrupts immediately, cutting off whatever is being readGenuine urgency only: session about to expire, payment failed, data loss imminent
      aria-atomic="true"Re-read the whole region, not just the changed part"Page 3 of 12" — otherwise only "3" is announced
      aria-relevantWhich mutations countRarely needed; the default (additions text) is usually right
      aria-busy="true"Suppress announcements while updatingWrapping a multi-step DOM update so it is announced once
      Four things that silently break live regions

      1. The region must exist in the DOM before the content changes. Injecting a <div aria-live> that already contains the message announces nothing — render the empty container on load and fill it later. 2. Replacing the container element rather than its text content re-registers it and loses the update; many framework re-renders do exactly this. 3. Setting identical text twice announces once — append a space or clear it first. 4. assertive on anything routine is genuinely hostile; it cuts users off mid-sentence, repeatedly.

      A general-purpose announcer JavaScript
      // Rendered once, on page load, empty.
// <p id="announcer" role="status" aria-live="polite" class="visually-hidden"></p>

const region = document.getElementById('announcer');

export function announce(message) {
  region.textContent = '';              // force a change even if identical
  requestAnimationFrame(() => { region.textContent = message; });
}

announce(`${results.length} results`);

      Hiding text visually but not from screen readers

      The one utility class every project needs CSS
      .visually-hidden {
  position: absolute;
  width: 1px; height: 1px;
  margin: -1px; padding: 0;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;   /* stops long text collapsing to one column */
  border: 0;
}
/* Do NOT use display:none or visibility:hidden — both remove the text
   from the accessibility tree, which is the opposite of the intent. */

      7Colour, contrast, motion and zoom

      The criteria most often failed, and the only ones you can check with a calculator.

      Contrast

      WCAG defines contrast as a ratio between the relative luminance of two colours, from 1:1 (identical) to 21:1 (black on white). The thresholds:

      ContentAAAAANotes
      Body text4.5:17:1Anything under 18.66px, or under 14px bold

      UI components and graphics3:1—Input borders, icons, focus indicators, chart lines
      Disabled controlsexempt—Exempt, but users still need to read them. Do not take the exemption literally.

      Large heading, 24px bold

      Body copy at 15px, which is the size most interfaces actually use for paragraphs and form labels.

      Never colour alone
      A red border on an invalid field is invisible to someone with red–green colour vision deficiency, which is about 8% of men. Pair every colour signal with a second channel: an icon, text, a pattern, a weight change. The quick test is a greyscale screenshot.
      APCA
      The WCAG 2 formula has known flaws — it over-rates dark backgrounds and ignores font weight and size beyond a single threshold. APCA, the candidate replacement being developed for WCAG 3, models perception far better. Use it to make good decisions; use WCAG 2 ratios for anything you must certify against today.

      Zoom, reflow and target size

      Reflow (WCAG 1.4.10)
      Content must work at 320 CSS pixels wide without horizontal scrolling — equivalent to 400% zoom on a 1280px desktop. Test it by zooming your browser to 400%, not by resizing to mobile: zoom keeps desktop media queries in play and exposes fixed widths that a narrow viewport would hide.
      Text spacing (1.4.12)
      Nothing may clip or overlap when users override line height to 1.5×, paragraph spacing to 2×, letter spacing to 0.12em and word spacing to 0.16em. Fixed-height containers around text are the usual failure.
      Target size (2.5.8)
      Minimum 24×24 CSS pixels for pointer targets, with exceptions for inline links in text. 44×44 is the practical mobile guidance. Spacing counts towards it, so a small icon with generous padding passes.
      Reduced motion
      Honour prefers-reduced-motion: reduce. Parallax, large-scale movement and auto-playing carousels can trigger genuine vestibular symptoms — nausea and dizziness, not mere annoyance. Replace movement with a fade, or remove it. Chapter 11 covers the implementation.

      Automated tools reliably detect only about 30–40% of WCAG issues, and by design they can only flag what is machine-decidable. No tool can tell you that alt="image" is a bad description or that your tab order is confusing.

      A pull-request checklist that fits in a comment

      • Every interactive thing is a <button>, an <a href>, or a real form control.
      • Every control has a visible label or an aria-label, and every image has a deliberate alt.
      • Tab through it: order matches the visual order, focus is always visible, nothing is unreachable, nothing is trapped.
      • Escape closes anything that opened; focus returns to the trigger.
      • Headings step by one; the page has one <h1> and a <main>.
      • No information conveyed by colour alone; contrast passes at AA.
      • Anything that changes without navigation is announced.
      • It still works at 400% zoom and with reduced motion on.

      9Check yourself

      Six questions.

      1. What does role="button" on a <div> give you, and what does it not?

      It changes one thing: the accessibility tree now reports the role as "button". It gives you no focusability, no keyboard activation on Enter or Space, no focus ring, no disabled state, no form association and no default styling. Worse, it now promises button behaviour to a screen-reader user, who will press Space and find nothing happens. ARIA describes; it never implements. Rule 1 applies: use <button>.

      2. A modal opens. It looks fine and Escape closes it. What three things are most likely still wrong?

      First, focus was never moved into the dialog, so a screen-reader user is still reading the page behind it and does not know anything opened. Second, focus is not trapped, so Tab walks out into the page underneath — which is still reachable and clickable. Third, on close, focus is not returned to the element that opened it, so the user is dumped at the top of the document. A fourth is common too: the background is not inert, so the virtual cursor can browse it. <dialog>.showModal() handles all four.

      3. Why is one tabindex="1" on a page a bigger problem than it looks?

      Because tab order is computed in two passes: every element with a positive tabindex first, in ascending numeric order, then everything with tabindex="0" or an implicit order in document order. A single positive value therefore jumps ahead of the whole document, so the first Tab press lands in the middle of the page. It also creates a maintenance trap — the moment a second developer adds another positive value, the two must be coordinated across files. There is essentially no problem that positive tabindex solves and DOM order does not.

      4. You add a live region that renders only when there is a message: {error && <div aria-live="polite">{error}</div>}. Nothing is announced. Why?

      The live region must be present in the accessibility tree before the content appears, so that the browser is watching it for mutations. Inserting a node that already contains the text is a single addition with no observed change inside a registered region, and most screen readers say nothing. Render the container unconditionally and empty, then set its text. The same mechanism explains why swapping the element on re-render, rather than updating its text, also loses announcements.

      5. Your design system uses a 3.8:1 grey for helper text at 13px, and the automated audit passes on the page you tested. Is it compliant?

      No. 13px is not large text — the threshold is 18.66px, or 14px if bold — so it needs 4.5:1, and 3.8:1 fails AA. If your audit passed, it was probably because the tool could not resolve the computed background (a gradient, an image, a semi-transparent overlay, or a colour set by a parent it did not evaluate) and skipped the check rather than failing it. Automated contrast checks are the most likely of all automated checks to produce a false pass; verify the values yourself for your token palette once, then trust the tokens.

      6. A single-page app changes route. What does a screen-reader user experience by default, and what do you owe them?

      By default: nothing. There is no page load, so no announcement fires; focus stays on the link they activated, which may no longer exist; and document.title is often unchanged, so the tab still says the old page. The user has no signal that navigation happened at all. The fix is three steps on every route change: update document.title, move focus to the new view's heading (given tabindex="-1") or to a dedicated skip target, and optionally announce the new page name in a polite live region. Every routing library can do this and almost none does it by default.
