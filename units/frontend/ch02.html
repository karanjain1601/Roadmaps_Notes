The network path

Everything between your keyboard and the server's disk, and back. Name resolution, connection setup, encryption, the HTTP message itself, what genuinely changed across three protocol versions, and the header set that decides whether a request happens at all.

Part 1 The platform·Reading time 45 minutes·Demos handshake cost, cache decisions·Prerequisites Chapter 1

1Round trips are the currency

The single most useful number in front-end performance, and why bandwidth is the wrong thing to optimise for.

A round trip is one packet out and one packet back. On a good fixed line it costs about 12 milliseconds. On a phone on 4G it costs 60 to 80. On a congested mobile network or a satellite link it costs 200 to 600. Everything in this chapter is an attempt to spend fewer of them.

Here is why this beats bandwidth as a mental model. Suppose you halve the size of a 60 KB stylesheet. On a 9 Mbps connection you save about 27 milliseconds of transfer. Now suppose instead you serve that stylesheet from a connection that is already open rather than a new origin. You save a DNS lookup, a TCP handshake and a TLS handshake — three round trips, 210 milliseconds on the same connection. The second change is nearly eight times more valuable and involves no compression, no tooling and no build step.

Bandwidth has improved enormously over twenty years. Latency has barely moved, because it is bounded by physics and by the number of hops between the device and the server. Light in fibre travels about 200,000 km per second; London to New York and back is 11,000 km, so 55 ms is the floor before any equipment is involved. No amount of engineering removes that.

Rule of thumb

Count round trips before counting kilobytes. A change that removes a round trip on the critical path is almost always worth more than a change that removes 30 KB, and it stays worth it as connections get faster.

2DNS: a name becomes an address

Four caches, a hierarchy, and one front-end lever.

Your code says https://api.example.com/products. The network stack needs 93.184.216.34. DNS is the distributed database that translates one into the other, and it is checked in cache order before anything touches the network:

  1. Browser cache. Chrome keeps its own DNS cache for roughly a minute. Visible at chrome://net-internals/#dns.
  2. OS cache. Then the hosts file, then the operating system's resolver cache.
  3. Router / local resolver. Home routers usually cache too.
  4. Recursive resolver. Your ISP's, or a public one like 1.1.1.1 or 8.8.8.8. If it does not have the answer, it does the walk below on your behalf.

The walk, when nothing is cached anywhere: ask a root server who handles .com; ask that TLD server who is authoritative for example.com; ask that authoritative nameserver for the api record. Three queries, though the resolver caches each level aggressively so in practice you rarely pay for all three.

The front-end lever: fewer origins, hinted early

Every distinct hostname on your page is a potential DNS lookup plus a full connection setup. A page pulling from your origin, a font CDN, an image CDN, an analytics host and a tag manager is paying that four times over. Two responses:

Resource hints, in increasing order of commitment HTML head
<!-- Resolve the name now; costs almost nothing, saves ~1 RTT later -->
<link rel="dns-prefetch" href="https://images.example-cdn.com">

<!-- Resolve AND open the TCP + TLS connection now. Use for origins you
     are certain to hit. Limit to two or three; each holds a socket open. -->
<link rel="preconnect" href="https://images.example-cdn.com" crossorigin>

<!-- Fetch this specific file now at high priority. You must get the
     `as` right or the browser will fetch it twice. -->
<link rel="preload" href="/fonts/inter.woff2" as="font"
      type="font/woff2" crossorigin>

<!-- Fetch at idle priority for a page they will probably visit next -->
<link rel="prefetch" href="/checkout" as="document">
Preload is a loaded gun

A preload with the wrong as value, or a missing crossorigin on a font, causes the browser to download the file twice — once for the hint and once for the real use, because the two requests have different credentials modes and do not match in the cache. Check the Network panel after adding one. Preloading more than a handful of things also just reshuffles the queue: everything is high priority, so nothing is.

3TCP: the reliable stream

Three packets to say hello, then a deliberately cautious ramp-up that shapes your first 14 kilobytes.

TCP gives you an ordered, reliable byte stream over an unreliable packet network. It opens with the three-way handshake — SYN, SYN-ACK, ACK — which costs one round trip before any application data can be sent.

Slow start, and why the first 14 KB is special

TCP does not know how much bandwidth is available, so it guesses conservatively and increases. The initial congestion window on most servers is 10 segments, and a segment is about 1460 bytes of payload, so roughly 14 KB can be in flight before the sender must wait for an acknowledgement. Each subsequent round trip roughly doubles the window.

The practical consequence: if your HTML document plus its inlined critical CSS fits inside about 14 KB, it arrives in a single round trip after the handshake. At 15 KB it takes two. This is the origin of the "keep your critical path under 14 KB" advice, and it is one of the few size thresholds in front-end performance that reflects a real mechanism rather than a round number.

Head-of-line blocking

Because TCP guarantees order, one lost packet stalls everything behind it until the retransmission arrives — even data that has already been received. On a clean network this is invisible. On a lossy mobile network it is the dominant cost, and it is the reason HTTP/3 abandoned TCP entirely.

4TLS: the encrypted channel

One extra round trip, one certificate chain, and two configuration mistakes that will eventually be yours to debug.

TLS does three things at once: it proves the server is who it claims to be (authentication), it hides the traffic (confidentiality), and it detects tampering (integrity). The handshake negotiates a cipher suite and agrees on session keys.

VersionHandshake costNotes
TLS 1.22 round tripsStill widely deployed. Fine, but slower to start.
TLS 1.31 round tripThe default now. Fewer negotiable options, so fewer ways to misconfigure it.
TLS 1.3 resumption1 round tripReuses a pre-shared key from a previous session.
TLS 1.3 0-RTT0 round tripsApplication data rides along with the first packet. Not replay-safe, so only for idempotent GETs.

Two things bolted onto the handshake that matter

SNI
Server Name Indication. The client states which hostname it wants before encryption is established, so one IP address can serve many certificates. It is also the reason the hostname you visit is visible to the network even over HTTPS — Encrypted Client Hello is the fix, slowly rolling out.
ALPN
Application-Layer Protocol Negotiation. The client offers h2 and http/1.1 in the handshake and the server picks. This is how HTTP/2 is selected without an extra round trip, and it is why HTTP/2 in browsers requires HTTPS in practice.

The certificate chain, and the classic failure

Your server sends a leaf certificate for your domain, signed by an intermediate certificate authority, which is signed by a root that ships in the operating system's trust store. The server must send the leaf and every intermediate. Roots come from the client.

The missing intermediate

If you forget to install the intermediate, the site works perfectly in your desktop browser and fails on some phones and most command-line clients. Desktop browsers cache intermediates they have seen before, or fetch them via the certificate's AIA extension, and so paper over the mistake. Your users' devices, and your CI pipeline's curl, do not. Always verify with a tool that starts from an empty trust cache, not with the browser you have been using all week.

Two other configuration items worth recognising when you see them in a ticket: OCSP stapling, where the server attaches a fresh proof that its certificate has not been revoked so the client does not have to make its own request to the CA; and HSTS, a response header that tells the browser to use HTTPS for this domain for the next n seconds, which removes the initial HTTP-to-HTTPS redirect on repeat visits — one more round trip saved.

5HTTP: the message

A start line, some headers, a blank line, a body. Everything else is convention.

Underneath every framework, every fetch() and every API client, HTTP is a plain text format. Being able to read it — and to type it into a terminal — makes debugging vastly faster.

Methods, and the two properties that define them

Two words come up constantly and are routinely confused. Safe means the request does not change server state, so a browser or crawler may issue it freely. Idempotent means issuing it twice has the same effect as issuing it once, which is what makes automatic retries possible.

Compression

The client advertises what it can decode with Accept-Encoding; the server picks one and says so with Content-Encoding. Text compresses dramatically — a 240 KB JavaScript bundle is typically 70 KB gzipped and 60 KB with Brotli.

AlgorithmTypical text savingNotes
gzip~70%Universal. The safe floor.
br (Brotli)~75%Better ratio, slower to compress at high levels — precompress static files at build time rather than on every request.
zstd~75%Similar ratio to Brotli with much faster compression. Growing browser support.

Never compress already-compressed formats. JPEG, PNG, WebP, AVIF, MP4 and WOFF2 gain nothing and cost CPU on both ends.

6HTTP/1.1, /2 and /3

Three versions, one problem being attacked repeatedly: too many things waiting in line.

HTTP/1.1 — one request at a time per connection

A connection carries one request/response exchange at a time. Browsers work around this by opening up to six connections per origin, and each of those pays its own TCP and TLS handshake. If your page needs 40 resources from one origin, they queue in groups of six.

The era's standard workaround was domain sharding: serve assets from static1.example.com and static2.example.com to get 12 connections instead of 6. Under HTTP/2 this is actively harmful — it forces multiple connections where one would multiplex. If you inherit a sharded setup, unsharding it is usually a free win.

HTTP/2 — multiplexing over one connection

Binary framing
Messages become frames on numbered streams instead of text separated by newlines. Parsing is unambiguous and cheap.
Multiplexing
Many requests and responses interleave over a single connection. Six-connection limits and sharding become irrelevant.
HPACK header compression
Headers repeat enormously across requests on the same page — same cookie, same user agent, same accept headers. HPACK keeps a shared table so repeats cost a few bytes. On a cookie-heavy site this saves more than you would guess.
Stream priorities
The client can express that the stylesheet matters more than the third thumbnail. Server implementations vary in how well they honour it.
Server push
Now removed from browsers. It pushed resources the client had not asked for and usually already had cached, wasting bandwidth. 103 Early Hints replaced it: the server sends a preliminary response containing Link: rel=preload headers while it is still building the real one.

What HTTP/2 did not fix: it still runs on TCP, so a single lost packet still stalls every multiplexed stream behind it. On a clean network HTTP/2 is a clear win; on a lossy one it can be worse than HTTP/1.1, because 1.1's six separate connections fail independently.

HTTP/3 — the same idea on QUIC

HTTP/3 runs over QUIC, which is built on UDP and implements its own reliability and ordering per stream. A lost packet affecting stream 4 no longer stalls streams 1, 2 and 3. It also merges the transport and cryptographic handshakes, so a cold connection costs one round trip instead of two, and a resumed one can cost zero. And because a QUIC connection is identified by a connection ID rather than an IP-and-port tuple, it survives a phone switching from wifi to cellular without re-handshaking.

Bundling everything into one file was essential under HTTP/1.1 and is a mild negative under HTTP/2 and /3, where many small cacheable files invalidate more precisely.

7Caching: the request that never happens

The fastest request is the one the browser skips entirely. Four headers decide whether it does.

Every request the browser can answer from its own disk costs zero round trips, zero bandwidth and zero server time. Getting caching right is the single highest-leverage network change available to a front-end developer, and it is almost entirely a matter of sending the correct response headers.

The two questions

When the browser needs a URL it already has a copy of, it asks two questions in order.

  1. Is my copy still fresh? Determined by Cache-Control: max-age (or the older Expires). If yes, the copy is used with no network activity at all. The Network panel calls this "(disk cache)" or "(memory cache)".
  2. If it is stale, has it actually changed? The browser sends a conditional request carrying If-None-Match (from the stored ETag) or If-Modified-Since (from Last-Modified). If the server says 304 Not Modified, no body is transferred — but a full round trip still was.
The distinction that matters

A cache hit costs nothing. A revalidation costs a round trip even when the answer is "nothing changed". On a mobile connection, revalidating twelve assets on every page view costs most of a second for zero bytes of value. Long max-age plus content-hashed filenames turns all of those into hits.

Cache-Control directives

DirectiveMeaning

ETag, Last-Modified and Vary

ETag
An opaque version identifier for the response body — usually a hash. Strong ("abc") means byte-identical; weak (W/"abc") means semantically equivalent. Precise, but each unique value costs storage on the server side of the comparison.
Last-Modified
A timestamp, one-second resolution. Cheaper but coarser. If both are present the ETag wins.
Vary
Lists the request headers that change the response, so caches key on them. Vary: Accept-Encoding is almost always correct. Vary: Cookie or Vary: User-Agent shatters your cache hit rate into thousands of variants — a common accidental performance disaster.

The pattern that works

Two rules, applied consistently, solve almost all of it server config
# 1. HTML: never cache hard. It is the index of everything else.
Cache-Control: no-cache
#    (browser revalidates; a 304 is cheap and correctness is preserved)

# 2. Everything with a content hash in the filename: cache forever.
#    /assets/app.9f3c1a2e.js  ->  a new build produces a new URL
Cache-Control: public, max-age=31536000, immutable

# API responses: short freshness plus background refresh
Cache-Control: private, max-age=30, stale-while-revalidate=300

Content hashing is what makes rule 2 safe: because the filename changes whenever the bytes change, there is no such thing as a stale copy. The HTML that references it is revalidated on every visit, so it always points at the current hash. This is why every bundler in Chapter 23 emits hashed filenames by default.

8CDNs and where the bytes come from

Moving the server closer is the only way to buy latency back.

A content delivery network is a fleet of caching servers spread geographically. A user in Jakarta hits an edge node in Jakarta rather than your origin in Frankfurt, which cuts the round-trip time from perhaps 220 ms to 15 ms — and remember that every one of the handshake round trips shrinks by the same factor.

Cache key
What the edge uses to decide whether two requests are the same. Usually the URL plus the headers named in Vary. Query strings often count, which is why appending a random cache-buster to an asset URL bypasses the CDN entirely.
Hit ratio
The fraction of requests served from the edge. The number to watch. A ratio below about 90% for static assets means something — usually a Vary header or a query string — is fragmenting the cache.
Purge / invalidation
Explicitly evicting content. Slow and rate-limited on most providers. Content hashing means you rarely need it, which is a much better position to be in.
Origin shield
A designated mid-tier cache that all edges consult before hitting your origin, so a cold cache in fifty cities does not become fifty simultaneous origin requests.
Edge compute
Running small functions at the edge — rewriting headers, A/B routing, geolocation, authentication checks. Chapter 29 covers where this fits; the Cloudflare unit goes deep on one implementation.

9Check yourself

Five questions covering the whole chapter.

1. Your team wants to speed up asset loading by splitting images across img1.example.com, img2.example.com and img3.example.com. Good idea?

It was, under HTTP/1.1, where six connections per origin was a hard limit. Under HTTP/2 or /3 it is actively harmful: each new hostname forces a fresh DNS lookup, TCP handshake and TLS handshake, and prevents the multiplexing that would have served all those images over one already-open connection. Serve from a single origin and let the protocol do the work.

2. What is the difference between Cache-Control: no-cache and no-store, and which one would you put on a logged-in user's account page?

no-cache stores the response but revalidates before reusing it — a 304 is possible and cheap. no-store never writes it to disk. For an account page containing personal data, no-store (usually with private) is right, because you do not want the response sitting in a shared computer's disk cache after logout. For your HTML shell, no-cache is right: revalidate for correctness, but a 304 saves the download.

3. A colleague adds Vary: User-Agent to speed up mobile-specific responses. What happens to the CDN?

The hit ratio collapses. User agent strings are near-unique — browser version, OS build, device model — so the edge now stores a separate copy of every response for effectively every visitor and almost never finds a match. The correct tools are client hints, or responsive images and CSS that let one response serve every device.

4. Why is "keep the critical path under 14 KB" a real threshold rather than a round number?

Because TCP slow start begins with a congestion window of about 10 segments, roughly 14 KB of payload, which is the maximum that can be sent before the server must wait for an acknowledgement. Content that fits inside that window arrives one round trip after the handshake; content that exceeds it needs at least two. On a 200 ms link that single threshold is worth 200 ms of first paint.

5. The site works in Chrome on your laptop but fails with a certificate error on a colleague's phone and in CI. What is the likely cause?

A missing intermediate certificate. Your laptop's Chrome has seen that intermediate before and cached it, or fetched it via the certificate's AIA extension, so the chain completes locally. Clients with an empty cache — a fresh phone, a container running curl — cannot complete the chain and reject the connection. Fix it on the server by sending the full chain, and verify from a clean client rather than the browser you have been testing in.
