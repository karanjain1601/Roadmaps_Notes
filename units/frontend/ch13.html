JavaScript essentials

The language itself, before any DOM and before any framework. This chapter covers the parts that actually bite: coercion, scope and closures, what this resolves to, the prototype chain under the class syntax, and the difference between copying a reference and copying a value.

1Types and coercion

Eight types, one conversion algorithm, and a small set of results everybody memorises eventually.

JavaScript has seven primitive types — string, number, bigint, boolean, undefined, symbol, null — and object, which covers arrays, functions, dates and everything else. Primitives are immutable and compared by value; objects are compared by reference.

null versus undefined

undefined
The absence of a value that was never set: a declared-but-unassigned variable, a missing property, a missing argument, a function with no return. Produced by the engine.
null
An intentional "no value". Produced by you, or by APIs that mean "we looked and there is nothing" — querySelector returns null when nothing matched.
The practical rule
Default parameters trigger on undefined only, not null. JSON.stringify drops undefined properties but keeps null. And ?? treats both as absent, which is usually what you want.

Truthiness and equality

Exactly eight values are falsy: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy — including [], {}, "0" and "false".

Equality and coercion, evaluated Every result below is computed by running the comparison, not looked up.

The == matrix. Green cells are where loose equality returns true but strict equality does not.

The rule that removes the whole problem

Use === everywhere, with one deliberate exception: x == null is a concise, idiomatic check for "null or undefined" and is worth keeping. Everything else — "" == 0, [] == false, null >= 0 being true while null > 0 is false — is a consequence of an abstract-equality algorithm you should simply never invoke.

2Scope, hoisting and closures

Where a name is visible, when it becomes usable, and what a function remembers after it returns.

KeywordScopeBefore declarationReassign / redeclare
varFunctionundefined — hoisted and initialisedBoth allowed. Avoid in new code.
letBlockReferenceError — the temporal dead zoneReassign yes, redeclare no.
constBlockReferenceErrorNeither. The binding is constant, not the value — a const object's properties are still mutable.

Hoisting is often mis-taught. Declarations are all processed before the code runs; the difference is initialisation. var is initialised to undefined, so reading it early is merely useless. let and const exist but are uninitialised, so reading them throws — the temporal dead zone, which is a feature: it turns a silent bug into an error. Function declarations are fully hoisted and callable before their definition; function expressions assigned to a variable are not.

Closures

A closure is a function together with the variables it captured from where it was defined. Not where it was called — lexical scope is fixed at authoring time.

The three closure patterns you will actually write JavaScript
// 1. Private state
function makeCounter() {
  let n = 0;                          // not reachable from outside
  return { inc: () => ++n, get: () => n };
}

// 2. Configuration captured once
const formatIn = (locale) => {
  const fmt = new Intl.NumberFormat(locale);  // built once, reused
  return (n) => fmt.format(n);
};

// 3. The classic loop trap
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));
// 3 3 3 — one function-scoped `i`, read after the loop finished

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));
// 0 1 2 — `let` creates a fresh binding per iteration
Closures are the main source of memory leaks

A closure keeps everything in its scope chain alive. An event listener that captures a large object, attached to an element that is later removed but never unbound, keeps that object in memory for the life of the page. Chapter 14 covers AbortController, which is the cleanest way to guarantee cleanup.

3Functions and this

Four ways to define one, five things this can be, and one rule that explains all five.

Forms and parameters JavaScript
function named(a, b = 1, ...rest) { }   // hoisted, has own `this`
const expr = function () { };            // not hoisted
const arrow = (a) => a * 2;               // no own `this`, no `arguments`
const obj = { method() { } };            // shorthand, has own `this`

// Defaults trigger on `undefined` only — passing null skips them
const greet = (name = 'friend') => `hi ${name}`;
greet(undefined);  // "hi friend"
greet(null);       // "hi null"

// Named parameters via destructuring, with defaults at both levels
function fetchList({ page = 1, limit = 20 } = {}) { }

The one rule for this

In a normal function, this is determined by how the function is called, not where it is defined. Arrow functions are the exception: they have no this of their own and inherit it lexically from the enclosing scope, permanently — call, apply and bind cannot change it.

this resolver Each case is executed and the result reported, not described.

4Objects, prototypes and classes

      
One inheritance mechanism, two syntaxes for it.


      
Every object has an internal link to another object — its prototype. Read a property that is not present and the engine walks that chain until it finds one or reaches null. That single mechanism is all of JavaScript inheritance; class is syntax over it.


      

        
Classes, and what they compile to conceptually JavaScript

        
class Store {
  #items = [];                    // truly private — not just a convention
  static version = '2';

  constructor(name) { this.name = name; }

  add(item) { this.#items.push(item); return this; }  // chainable
  get size() { return this.#items.length; }        // accessed as .size

  // A field holding an arrow: `this` is bound per instance.
  // Costs one function per instance; methods are shared on the prototype.
  handleClick = () => { console.log(this.name); };
}

class Cart extends Store {
  constructor(name) {
    super(name);                   // required before touching `this`
  }
}

// add() lives on Store.prototype, shared by every instance.
// name and #items live on the instance.

      


      

        
Class bodies are strict mode

        
Always, regardless of the surrounding file.

        
Private fields are real

        
#items is enforced by the engine and inaccessible from outside, unlike the _underscore convention. #x in obj is a valid brand check.

        
Methods are not bound

        
Passing obj.method as a callback loses this, because the call form changed. Bind in the constructor, use a class field holding an arrow, or wrap at the call site.

        
Prefer composition

        
Deep inheritance hierarchies are as awkward here as anywhere. Most front-end code needs plain objects, functions and modules far more often than it needs a class tree.

for…of versus for…in

        
for…of iterates values of any iterable — arrays, strings, Maps, Sets, NodeLists. for…in iterates enumerable string keys, including inherited ones, in an order you should not rely on. On an array it gives you index strings, not elements. Use for…of and entries().

        
Map versus a plain object

        
Map takes any value as a key (including objects), preserves insertion order, has a real size, and has no prototype keys to collide with. Use it for genuine lookup tables; use plain objects for records with known shapes.

        
Set

        
Unique values, O(1) membership. [...new Set(arr)] is the standard deduplication.

        
WeakMap / WeakSet

        
Keys are held weakly, so entries vanish when the key object is garbage collected. The right way to attach metadata to DOM nodes without leaking.

        
Generators

        
function* with yield produces values lazily. Rare in application code, but the mechanism behind async iteration and useful for infinite or expensive sequences.

      

    


    
    

      
6Copying, equality and immutability

      
The single most common source of "why did my state not update".


      
Objects are compared by reference: {a: 1} === {a: 1} is false. Assigning an object copies the reference, not the contents, so two variables point at one thing and mutating through either is visible through both.


      

        
Three depths of copy JavaScript

        
const a = { user: { name: 'Kim' }, tags: ['x'] };

const ref = a;                     // same object. Not a copy at all.
const shallow = { ...a };          // new top level; a.user is SHARED
const deep = structuredClone(a);   // fully independent

shallow.user.name = 'Lee';
a.user.name;                       // 'Lee' — the shared nested object changed

// structuredClone handles Date, Map, Set, ArrayBuffer and cycles.
// It cannot clone functions, DOM nodes, or class prototypes —
// you get a plain object back, not an instance.

// The old JSON trick loses undefined, Date (becomes a string),
// Map, Set, Infinity, NaN and functions. Avoid it.
const lossy = JSON.parse(JSON.stringify(a));

      


      

        
Why frameworks care

        
React, and any library using reference equality to detect change, compares old and new by identity. Mutating an object in place leaves the reference unchanged, so nothing re-renders. This is why immutable update patterns — spread, toSorted, with — matter in Chapter 19.

        
Object.freeze

        
Shallow. It prevents adding, removing or changing top-level properties, silently in sloppy mode and with a throw in strict mode. Nested objects remain mutable unless you freeze recursively.

        
Three equality functions

        
== coerces, === does not but treats NaN !== NaN and -0 === 0, and Object.is fixes both of those. React's state comparison uses Object.is.

      

    


    
    

      
7Modules

      
Static structure is the point — it is what makes tree shaking possible.


      

        
ES modules JavaScript

        
// named exports — preferred: renameable, tree-shakeable, greppable
export const parse = () => { };
export { helper as publicName };

// one default per module. Harder to search for, easy to rename
// inconsistently across a codebase.
export default class Parser { }

// imports are HOISTED and evaluated before any of this module's code
import { parse } from './parse.js';
import Parser from './parser.js';
import * as utils from './utils.js';   // namespace; blocks tree shaking

// dynamic import: returns a promise, creates a code-split point
const { Chart } = await import('./chart.js');

      


      

        
Modules are strict mode and deferred

        
<script type="module"> is deferred by default (Chapter 3), runs in strict mode, and has its own top-level scope — no accidental globals.

        
Bindings are live

        
An import is a live view of the exporter's binding, not a snapshot. If the exporting module reassigns the variable later, importers see the new value. This differs from CommonJS, which copies values at require time.

        
Single evaluation

        
A module is evaluated once per URL, however many times it is imported. That makes module scope a natural singleton — and a natural place to accidentally leak state between requests in server rendering.

        
Top-level await

        
Allowed in modules. It delays evaluation of everything that imports the module, so use it sparingly.

        
Circular imports

        
Legal but fragile: one module sees the other partially initialised. If you hit a mysterious undefined at module load, check for a cycle.

      

    


    
    

      
8Errors

      
Throw objects, catch narrowly, and never swallow.


      

        
Typed errors with a cause chain JavaScript

        
class ValidationError extends Error {
  constructor(field, message, options) {
    super(message, options);        // options.cause preserves the original
    this.name = 'ValidationError';
    this.field = field;
  }
}

try {
  await save(form);
} catch (err) {
  if (err instanceof ValidationError) {
    showFieldError(err.field, err.message);
  } else {
    // Wrap, do not discard: the stack trace of the original survives
    throw new Error('Saving the form failed', { cause: err });
  }
}

// Anything can be thrown, so a caught value is not necessarily an Error.
// Guard before reading .message.
const msg = (e) => e instanceof Error ? e.message : String(e);

      


      

        
finally always runs

        
Including after a return in the try. The place to re-enable a submit button or clear a spinner.

        
Never catch {}

        
An empty catch converts a loud failure into a silent wrong result. If you truly intend to ignore it, say so in a comment and log at debug level.

        
Global handlers

        
window.onerror and unhandledrejection catch what escaped. Wire them to your error reporter — Chapter 29 — but treat them as a net, not a strategy.

        
Errors are not control flow

        
A failed HTTP request is an expected outcome, not an exception. Chapter 16 covers returning result shapes instead of throwing for predictable failures.

      

    


    
    

      
9Check yourself

      
Six questions. Four of them are standard interview material.


      

        
1. Explain the output of both loops: for (var i=0;i<3;i++) setTimeout(()=>console.log(i)) versus the same with let.

        
        

          
var prints 3 3 3. There is one function-scoped i; all three callbacks close over that same binding, and by the time the timers fire the loop has finished and i is 3. let prints 0 1 2, because the specification creates a fresh binding for each iteration and copies the current value into it, so each closure captures a different variable. Before let, the fix was an IIFE per iteration to create that scope manually.

        

      


      

        
2. Why does const not make an object immutable?

        
        

          
Because const constrains the binding, not the value. It guarantees the variable will never be reassigned to point at something else; it says nothing about the contents of the object it points at. const a = {}; a.x = 1 is legal, while a = {} throws. For shallow immutability use Object.freeze; for deep immutability freeze recursively or use a library, and note that neither is what const is for.

        

      


      

        
3. You pass this.handleClick to addEventListener and this is wrong inside it. Why, and what are three fixes?

        
        

          
Because this in a normal function is determined by the call form, and passing the method detaches it from the object. The listener is invoked with the element as this, not your instance. Fixes: bind in the constructor (this.handleClick = this.handleClick.bind(this)); declare it as a class field holding an arrow function, which captures this lexically at construction; or pass a wrapper arrow at the call site (el.addEventListener('click', e => this.handleClick(e))). A fourth, often overlooked: stop relying on this for the element and use event.currentTarget, which is correct in all four cases.

        

      


      

        
4. What is the difference between || and ??, and when does it matter?

        
        

          
|| falls through on any falsy value; ?? falls through only on null and undefined. It matters whenever a legitimate value is falsy. opts.retries || 3 turns an explicit 0 into 3; opts.showLabel || true can never be false; input.value || 'default' replaces a deliberately empty string. Use ?? for defaults unless you specifically want every falsy value to trigger the fallback.

        

      


      

        
5. const copy = {...state} then copy.user.name = 'x', and the original changed. Explain.

        
        

          
Spread makes a shallow copy: a new top-level object whose properties hold the same references as the original's. copy.user and state.user are the same object, so mutating through either is visible through both. Only the top level is independent. Options: copy the nested level explicitly ({...state, user: {...state.user, name: 'x'}}), use structuredClone for a full deep copy, or use a library that produces immutable updates. In framework state this bug is doubly bad, because the top-level reference did change so a re-render happens — with data that has already been mutated, hiding the problem until something depends on the previous value.

        

      


      

        
6. Why does [10, 9, 1].sort() return [1, 10, 9]?

        
        

          
Because the default comparator converts each element to a string and sorts lexicographically, so "10" sorts before "9". Pass a comparator: sort((a, b) => a - b). Two related traps: sort mutates the array in place and returns the same reference, which breaks change detection in frameworks — use toSorted() — and for strings you usually want localeCompare rather than <, so that accented characters and other locales order correctly.
