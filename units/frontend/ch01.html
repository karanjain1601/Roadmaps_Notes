CHAPTER 01

What the front end owns

Before any HTML, a clear answer to what the job actually is: which artefacts you produce, what a browser does with them, where the boundary with the back end really sits, and the four constraints that make browser programming unlike anything else you will write.

Part 1 The platform·Reading time 30 minutes·Demo page-load simulator·Prerequisites none

1The job, stated precisely

"Front end" is a slippery title. Here is the version that survives contact with a real team.

A front-end developer builds the part of a system that runs on a machine you do not own, for a person you cannot see, over a connection you cannot predict. That single sentence explains almost every unusual thing about the discipline.

Server code runs on hardware you chose, with a runtime version you pinned, with memory you provisioned. If it is slow, you buy a bigger machine. Front-end code runs on a five-year-old Android phone with three other apps competing for the CPU, on a train, with a browser that shipped an update last Tuesday. You cannot pin any of it. What you can do is send less, send it in a better order, and never assume.

The deliverable

Everything a front-end developer produces ends up as one of four things arriving over the network: HTML, CSS, JavaScript, and binary assets — images, fonts, video, audio. That is the whole surface. A React component, a Sass file, a TypeScript module, a Figma export: all of them are build-time conveniences that get flattened into those four categories before a browser ever sees them.

This matters more than it sounds. When you are debugging why a page is slow, or why a style is not applying, or why a script ran twice, the question is always "what did the browser actually receive, and in what order?" — not "what does my source look like?". Chapter 23 covers the build step that sits between the two; this chapter is about what comes out the other end.

Where the boundary sits

The honest answer is that the boundary moves, and knowing where it currently sits on your project is part of the job. Three arrangements are common.

ArrangementWho renders the HTMLWhat the front end ownsTypical stack
Server-rendered pages The server, per request, from templates Templates, CSS, sprinkles of JavaScript, the whole visual layer Rails, Django, Laravel, PHP, Go templates
Single-page app The browser, after downloading a JavaScript bundle Everything visual plus routing, state, data fetching, caching, error handling React or Vue or Angular + a JSON API
Meta-framework Both — first paint on the server, then the browser takes over All of the above, plus a slice of the server: data loading, redirects, sometimes database access Next.js, Nuxt, SvelteKit, Remix, Astro

The third row is why "full stack" stopped being a useful word. A Next.js developer writing a server component that queries Postgres is doing back-end work in a front-end file.

The roadmap you are working through assumes you will end up somewhere near the second and third rows, which is why it spends so much time on frameworks, bundlers and rendering strategies. But the first row never went away — it is still the fastest, simplest way to ship a content site, and Chapter 21 makes the case for choosing it deliberately rather than by default.

What is not the job

Three things get attached to the title and should be pushed back on.

  • Design. Turning a design into code is front-end work. Deciding what the design should be is a different skill with its own roadmap. You should be able to hold an opinion — spacing, hierarchy, contrast — and you should be able to spot an inaccessible design before it ships. You should not be the only person deciding.
  • API design. You will consume APIs and you should push back hard when one is awkward, because an awkward API becomes awkward front-end code. Designing it is a shared conversation, not a handover.
  • "Making it work in IE". Browser support is a product decision with a cost. Your job is to state the cost accurately — "supporting that browser costs us container queries and roughly two weeks" — and then implement whatever is decided.
The one-sentence test

If you can explain what happens between a person pressing Enter in the address bar and the first pixel appearing, you understand the platform. Most of Part 1 is that explanation. Section 3 of this chapter is the overview; Chapters 2 and 3 are the two halves in detail.

2What the browser is handed

Four kinds of bytes, three completely different jobs, and one of them can block the other two.

A browser is a program that turns a stream of bytes into an interactive picture. It handles the four artefact types in distinct ways, and the differences are the source of most performance and correctness surprises.

HTML — structure and meaning

HTML is parsed as it arrives, incrementally, into a tree of nodes called the DOM. The parser does not wait for the whole file. This is why a slow server can still produce a fast first paint if it flushes the head early, and it is why streaming server rendering (Chapter 21) works at all.

Crucially, the parser is single-threaded and can be stopped. A <script> without defer or async halts parsing at that point in the document, downloads the script, executes it, and only then resumes. The browser mitigates this with a preload scanner — a lightweight second pass that races ahead looking for URLs to start downloading — but the DOM itself stops growing.

CSS — presentation

CSS is render-blocking. The browser will happily build a DOM without stylesheets, but it will not paint, because painting with the wrong styles and then correcting would produce a flash of unstyled content. So every <link rel="stylesheet"> in the head is a gate on first paint. Chapter 26 covers the standard escape hatches: inline the small subset needed for the visible area, load the rest asynchronously.

CSS is also, in a specific sense, script-blocking: because a script might read a computed style, a pending stylesheet delays execution of any script that follows it.

JavaScript — behaviour

JavaScript is the only one of the four that costs you twice. You pay to download it, and then you pay again to parse, compile and execute it — and that second cost lands on the CPU, which on a cheap phone is four to six times slower than your laptop. A 300 KB image and a 300 KB script are not remotely the same problem. The image decodes off the main thread; the script does not.

Binary assets — images, fonts, media

Usually the largest bytes on the page and usually the easiest win, because the fixes are mechanical: right format, right dimensions, right compression, lazy-load what is below the fold, and give the browser enough information to reserve space so the layout does not jump. Fonts are the awkward member of the family — a font request is discovered only after the CSS that references it has been downloaded and parsed, which is two round trips deep. Chapter 11 deals with that properly.

3One page load, traced end to end

Twelve steps from keystroke to interactive page. Then a simulator so you can move the pieces around.

Take an ordinary product page. Someone types the URL and presses Enter. Here is everything that happens, in order, with the front end's responsibility marked.

What the simulator is trying to teach

Four things, and they generalise well beyond this toy model.

  1. Latency dominates on mobile, not bandwidth. Switch from 4G to slow 3G and watch TTFB triple before a single byte of content moves. Doubling bandwidth on a high-latency link barely helps; removing a round trip always does. This is the entire argument for HTTP/2, connection reuse and preconnect.
  2. Render-blocking resources are a serial chain, not a parallel cost. Inlining critical CSS does not make the stylesheet smaller — it removes an entire request from the path to first paint. The gain is a round trip plus a download, not a few kilobytes.
  3. Scripts are charged twice. Turn "Defer scripts" on and first paint improves immediately, because the parser stops being blocked. But "Interactive" barely moves, because the CPU still has to execute those bytes — deferring changes when you pay, not whether.
  4. Third parties are on the critical path whether you meant them to be or not. The analytics tag is 46 KB on a different origin, which means its own DNS lookup, its own TCP and TLS handshakes, and a share of your bandwidth at the worst possible moment.
Model, not measurement

This simulator shares bandwidth equally between active downloads, treats server think time as a constant 90 ms, and prices script execution at a flat rate per kilobyte. Real browsers do priority-based scheduling, real servers vary, and real script cost depends on what the script does. Use it to build intuition about direction and magnitude, then measure your own page with the tools in Chapter 26.

4Four constraints that shape everything

Every awkward front-end practice traces back to one of these. Learn them now and the rest of the unit stops feeling arbitrary.

Constraint 1 — You do not control the runtime

There is no "supported version". At any moment your code is running on the latest Chrome, a Safari that is eighteen months behind on one specific API, a corporate Edge install with an extension injecting scripts, and a WebView inside someone's banking app. You cannot test all of it.

The practical response is progressive enhancement: build a version that works with the least, then layer on capability where it exists. A form that submits without JavaScript still submits when the bundle fails to load. A layout built on flexbox with a sensible flow fallback still reads on an ancient browser. Feature detection — asking if ('IntersectionObserver' in window) — beats browser sniffing every time, because the question you actually care about is "does this API exist", not "what does the user agent string claim".

Feature detection, not browser detection capability check
// Bad: guesses capability from a string that lies on purpose
if (navigator.userAgent.includes('Safari')) { useFallback(); }

// Good: asks the only question that matters
if ('IntersectionObserver' in window) {
  observeLazyImages();
} else {
  loadAllImages();     // slower, still correct
}

// Also good: CSS asks the same question its own way
@supports (container-type: inline-size) {
  .card { container-type: inline-size; }
}

Constraint 2 — One main thread

JavaScript execution, style calculation, layout, paint and event handling all happen on a single thread. If your code occupies it for 300 ms, the page is frozen for 300 ms: no scrolling, no hover states, no response to a tap. The user does not know your code is busy. They conclude the site is broken and tap again.

At 60 frames per second a frame is 16.7 ms, and the browser needs part of that for its own work, so a task longer than about 50 ms is officially "long". The consequences run through the whole unit: it is why Chapter 15 is about the event loop, why Chapter 18 cares how frameworks schedule updates, and why Chapter 26 measures interaction latency rather than just load time.

Constraint 3 — Everything you ship is public

Minification is not obfuscation and obfuscation is not security. Every line of your bundle, every API endpoint it calls, every key you embedded "temporarily" is one devtools panel away from any user. There is no such thing as a client-side secret and no such thing as client-side authorisation.

Client-side validation is a courtesy to the user — instant feedback instead of a round trip. Server-side validation is the actual rule. Anyone can open the console and call your API directly with whatever body they like. Chapter 27 goes through the consequences properly; the mindset to install now is that the browser is an untrusted environment that you happen to be programming.

Constraint 4 — The user is in charge

They can zoom to 400%, force a dark colour scheme, override your fonts, disable images, request reduced motion, use only a keyboard, navigate with a screen reader, block your third-party scripts and resize the window to 320 pixels wide. All of these are legitimate and several are legally protected.

The design response is to treat your layout as a set of constraints rather than a fixed drawing, and to honour the preferences the platform exposes:

Preferences the browser will tell you about, if you ask CSS media queries
@media (prefers-reduced-motion: reduce) {
  /* Someone gets motion sickness from your parallax. Believe them. */
  * { animation-duration: .001ms !important; transition-duration: .001ms !important; }
}

@media (prefers-color-scheme: dark) { /* respect the OS setting */ }
@media (prefers-contrast: more)    { /* thicker borders, stronger text */ }
@media (forced-colors: active)     { /* Windows high-contrast mode is on */ }
A useful reframe

Every one of these four constraints is also a specification. "Works on a slow phone, on one thread, with nothing secret in the bundle, under the user's preferences" is a testable definition of done. Teams that write it down ship better front ends than teams that discover it during a bug report.

The short version: a browser, an editor, a terminal, Node. Everything else is a preference.

Everything else

  • An editor. VS Code is the default and its ecosystem is genuinely the best; the JetBrains IDEs and Neovim are entirely reasonable. What matters is that it runs your formatter on save and shows TypeScript errors inline (Chapters 17 and 24).
  • Node.js. Not because you are writing servers, but because every build tool, test runner, linter and framework CLI in the ecosystem runs on it. Install the current LTS, and use a version manager (nvm, fnm, or Volta) from the start — you will need two versions within a year.
  • A terminal you are comfortable in. You do not need to be a shell expert. You do need to stop being scared of it. Chapter 24 covers the Git commands that matter.
  • A second browser. Chrome-only development produces Chrome-only sites. Keep Firefox or Safari open; Firefox's grid and flexbox inspectors are better than Chrome's and its accessibility panel is excellent.
  • A real cheap phone, if you can. CPU throttling in devtools approximates a slow device; an actual four-year-old Android tells the truth. This is the single most attitude-changing piece of equipment on the list.
What not to install yet

Not a framework, not a bundler, not a component library. Chapters 4 to 16 are all doable with a text file and a browser, and starting there means you learn what the tools are for rather than learning the tools as if they were the platform. Part 6 installs things, on purpose, with reasons.

7Check yourself

Four questions. If one is uncomfortable, the section it came from is worth a second pass.

1. A page takes 4.2 seconds to show anything on a 4G connection. Your manager asks you to "make the images smaller". Why might that not help, and what would you check first?

Images are almost never on the path to first paint — render-blocking CSS and parser-blocking scripts are. If nothing appears for 4.2 seconds, the likely causes are, in order: a slow TTFB (steps 1 to 5, before your bytes even start), a large render-blocking stylesheet, or a synchronous script in the head. Open the Network panel, sort by the start of the waterfall, and find what sits between the document arriving and the first paint marker. Images matter enormously for LCP — step 10 — which is a different number and a different fix.

2. Why is a 250 KB JavaScript bundle a bigger problem than a 250 KB hero image, even though they are the same number of bytes?

Because the script is charged twice. Both cost the same download time, but the image is then decoded on a background thread and painted, while the script must be parsed, compiled and executed on the single main thread — during which the page cannot respond to input at all. On a cheap phone that execution can take longer than the download did. This asymmetry is why "bundle size" gets its own budget separate from "page weight".

3. Your login form validates the password length in JavaScript before submitting. Is that security?

No. It is user experience — instant feedback instead of a round trip, which is worth having. Anyone can disable JavaScript, edit the DOM, or send the request directly with curl. Every rule that matters must be enforced again on the server, and the client-side copy exists purely to make the common case pleasant. Constraint 3: everything you ship is public, and nothing you ship is trusted.

4. In the simulator, switching from HTTP/1.1 to HTTP/2 helps more on slow 3G than on fibre. Why?

HTTP/1.1 opens up to six connections per origin, and each one pays a TCP handshake plus a TLS handshake before it can carry data — two round trips each. HTTP/2 multiplexes every request over a single connection, so that setup cost is paid once. On fibre a round trip is 12 ms and the saving is invisible; on slow 3G it is 200 ms per round trip, so eliminating ten of them saves two seconds. Round trips are the currency of mobile performance, which is the point Chapter 2 spends its whole length on.
