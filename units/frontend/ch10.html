CHAPTER 10

Responsive and adaptive design

Responsive design stopped being about breakpoints some years ago. The modern toolkit is components that respond to their own size, values that interpolate smoothly rather than snapping, layouts that need no breakpoints at all, and queries about what the user's input device can do rather than how wide their screen is.

Part 3 CSS·Reading time 45 minutes·Demos container queries, clamp calculator·Prerequisites Chapters 8–9

1What responsive means now

Three shifts since the original definition, and a breakpoint philosophy that survives them.

The 2010 definition was a fluid grid, flexible images, and media queries. All three still apply, but the emphasis has moved: fluid grids became intrinsic layouts that need no percentages, flexible images gained a proper mechanism, and media queries went from the primary tool to the fallback.

ThenNow
Breakpoints chosen from device widthsBreakpoints chosen from where your content stops working — measured by dragging the window, not from a device list
The page responds to the viewportComponents respond to their own container, so the same card works in a sidebar and a full-width grid
Type sizes step at each breakpointType and space interpolate continuously with clamp()
Mobile versus desktopInput capability: does this pointer hover? is it coarse? does the user want reduced motion?

Mobile-first, and why it is more than a preference

Writing the narrow layout as the base and adding complexity with min-width queries is not fashion. It produces less CSS, because the simple layout is usually the shorter one; it means an unsupported query degrades to the usable narrow version rather than a broken wide one; and it forces the content hierarchy question early, because at 360px you cannot show everything at once and must decide what matters.

Finding your breakpoints

Open the page, drag the window from wide to narrow, and note every width where something becomes ugly or unreadable. Those are your breakpoints. They will not be 768 and 1024, and they should not be — a nav bar with six items breaks at a different width from one with three. Naming them after content (--bp-nav-collapse) rather than devices keeps the reasoning visible.

2Media queries

The modern range syntax, and the feature list that goes well beyond width.

Range syntax — clearer, and no more off-by-0.02px CSS
/* Old */
@media (min-width: 48rem) and (max-width: 63.9375rem) { … }

/* New — reads as maths and the boundaries are unambiguous */
@media (48rem <= width < 64rem) { … }
@media (width >= 48rem) { … }

/* Combine and negate */
@media (width >= 48rem) and (pointer: fine) { … }
@media not (prefers-reduced-motion: reduce) { … }

/* Use rem, not px: rem respects the user's browser font-size setting,
   so a reader at 24px base gets the layout intended for that size. */

3Container queries

The feature that fixed the fundamental flaw in media-query-based components.

A media query asks about the viewport. But a card does not care how wide the window is — it cares how much room it has. Put the same card in a 220px sidebar and a 900px main column and a viewport query gives both the same layout, which is wrong in one of the two places. Container queries ask the right question.

Two steps: declare a container, then query it CSS
/* 1. The ancestor opts in. inline-size = query width only. */
.card-slot {
  container-type: inline-size;
  container-name: card;        /* optional but recommended */
  /* shorthand: container: card / inline-size; */
}

/* 2. The component queries it. Note: it queries its ANCESTOR,
      never itself — an element cannot be its own container. */
@container card (width >= 300px) {
  .card { grid-template-columns: 110px 1fr; }
}

/* Container units resolve against the nearest query container */
.card h3 { font-size: clamp(1rem, 5cqi, 1.5rem); }

inline-size versus size
inline-size applies inline-axis containment and lets you query width — the common case. size contains both axes and lets you query height too, but the container then cannot be sized by its contents and will collapse unless you give it a height. Use inline-size unless you have a specific reason.
Containment has costs
container-type implies layout, style and inline-size containment, which also creates a containing block for absolutely positioned descendants and a new formatting context. A popover that used to escape the card will now be clipped by it.
Container units
cqw, cqh, cqi (inline), cqb (block), plus cqmin and cqmax. They resolve against the nearest ancestor container, which makes truly self-scaling components possible.
Style queries
@container style(--variant: compact) queries a custom property on an ancestor instead of a size. It is how a parent can switch a child's presentation without adding a class, and it is the mechanism behind theme scoping without wrapper class names.
Naming matters
Without container-name, a query targets the nearest container of any kind, which in a nested layout is often not the one you meant. Name them.

4Fluid type and space

One line replaces four breakpoints, and there is a formula rather than trial and error.

clamp(min, preferred, max) takes a floor, a fluid middle and a ceiling. The whole technique is choosing the middle term so the value moves linearly between two viewport widths.

The derivation maths
Given: at 320px viewport we want 1.5rem; at 1200px we want 3rem.
       (working in rem, so 320px = 20rem and 1200px = 75rem)

slope     = (3 - 1.5) / (75 - 20)      = 0.02727 rem per rem of viewport
vw term   = slope × 100                = 2.727vw
intercept = 1.5 - (20 × 0.02727)       = 0.9545rem

Result:
font-size: clamp(1.5rem, 0.955rem + 2.727vw, 3rem);

Always keep a rem term in the middle
A preferred value of pure vw does not change when the user zooms text, because zoom scales the rem base but not the viewport in the same way. WCAG 1.4.4 requires text to scale to 200%; a pure-vw heading fails it. The intercept term is what makes it pass.
Space as well as type
The same technique works for section padding, gaps and container widths. A handful of fluid space tokens — --space-s through --space-xl — removes most spacing media queries from a project.
Type scales
Pick a ratio (1.2 for dense interfaces, 1.25–1.333 for editorial) and generate each step from the previous. Fluid scales usually use a smaller ratio at the narrow end and a larger one at the wide end, which is exactly what two clamp() endpoints give you.
interpolate-size: allow-keywords
Lets height: auto participate in transitions and animations — the long-standing "cannot animate to auto" problem, solved without JavaScript measuring.

5Responsive images

Two mechanisms for two different problems, and the attribute everyone gets wrong.

ProblemToolBecause
Same image, different sizessrcset + sizes on <img>The browser knows the viewport, the density and the network. Let it choose.
Different formats<picture> with <source type>You must state the fallback order; the browser takes the first it supports.
Different crops (art direction)<picture> with <source media>A wide landscape hero needs a square crop on a phone. Only you know that.
What sizes actually means HTML
<img
  srcset="card-400.jpg 400w, card-800.jpg 800w, card-1200.jpg 1200w"
  sizes="(width >= 64rem) 380px, (width >= 40rem) 50vw, 100vw"
  src="card-800.jpg" width="800" height="600"
  alt="Seedlings in a propagator">

sizes is NOT "how big is the image file". It is "how wide will this
image be laid out at each viewport width". The browser reads it during
preload scanning, BEFORE any CSS has loaded, so it cannot work this out
itself. A wrong `sizes` makes it download the wrong candidate — often
a much larger one — which is worse than no srcset at all.

Descriptors:  400w = the file is 400px wide (use with `sizes`)
              2x   = for 2× density displays (use for fixed-size images)

Modern shortcut when the layout width really is the container width:
<img sizes="auto" loading="lazy" srcset="…" …>
Format order
AVIF, then WebP, then JPEG or PNG as the <img> fallback. AVIF wins on photographs at low bitrates; WebP is safer for graphics and encodes far faster. Keep the fallback — never assume.
Always width and height
Even with srcset. They give the aspect ratio, which reserves space and prevents layout shift. Chapter 4.
object-fit and object-position
object-fit: cover plus a fixed aspect-ratio gives a consistent card image from inconsistent source dimensions, without a wrapper div and a background-image.
Loading priorities
loading="lazy" below the fold; never on the LCP image. fetchpriority="high" on the hero so it competes with the stylesheet. decoding="async" generally.
Background images
image-set() is the CSS equivalent of srcset. But remember the preload scanner cannot see CSS background images at all — anything important belongs in the markup.

6Layouts that need no breakpoints

Four patterns that adapt continuously. Between them they replace most media queries in a typical project.

The four CSS
/* 1. GRID OF CARDS — reflows from 1 to n columns with no breakpoints.
      min() guards against overflow when the viewport is narrower
      than the minimum track. */
.cards {
  display: grid;
  gap: var(--space-m);
  grid-template-columns: repeat(auto-fit, minmax(min(18rem, 100%), 1fr));
}

/* 2. SWITCHER — a row until the items would be too narrow, then a
      column. All or nothing, no in-between. The magic is that a
      negative calc() forces flex-basis huge, which forces a wrap. */
.switcher {
  display: flex;
  flex-wrap: wrap;
  gap: var(--space-m);
}
.switcher > * {
  flex-grow: 1;
  flex-basis: calc((40rem - 100%) * 999);
}

/* 3. SIDEBAR — sidebar keeps its width; content takes the rest and
      wraps below when it would be squeezed under 50%. */
.with-sidebar { display: flex; flex-wrap: wrap; gap: var(--space-m); }
.with-sidebar > .side { flex-grow: 1; flex-basis: 15rem; }
.with-sidebar > .main { flex-grow: 999; flex-basis: 0; min-inline-size: 50%; }

/* 4. CENTRED MEASURE — readable line length, gutters, no wrapper div */
.prose { inline-size: min(65ch, 100% - 2 * var(--space-m)); margin-inline: auto; }

These are sometimes called intrinsic or algorithmic layouts: instead of enumerating states, you state a rule and let the layout engine resolve it at every width, including the ones you never tested. The pay-off is real — fewer breakpoints means fewer places for a design to be subtly broken at 913 pixels.

When you still want a breakpoint

When the change is not a reflow but a genuinely different design: a horizontal nav becoming a drawer, a data table becoming a card list, a three-panel layout dropping a panel. Those are decisions, not adjustments, and a query expresses them honestly. Reach for a container query first, and a media query only if the decision really does depend on the viewport.

7Designing for input, not screen size

Screen width has never been a reliable proxy for how someone is pointing at things.

A 13-inch laptop with a touchscreen, a phone with a stylus, a TV with a remote, a tablet with a trackpad, a desktop being driven by voice. Width tells you nothing useful about any of them. Two media features do.

Query the pointer, not the pixels CSS
/* Coarse pointer = finger or stylus. Grow the targets. */
@media (pointer: coarse) {
  .btn { min-block-size: 44px; padding-inline: 1rem; }
}

/* Only attach hover-revealed affordances where hover exists.
   Without this, a touch device gets a "sticky hover" that stays on
   after the tap and needs a second tap elsewhere to clear. */
@media (hover: hover) and (pointer: fine) {
  .card:hover .actions { opacity: 1; }
}

/* any-* asks whether ANY attached input can do it — a touchscreen
   laptop matches both (hover: hover) and (any-pointer: coarse). */
@media (any-pointer: coarse) { /* someone might tap this */ }
Hover is never the only route
Anything revealed on hover must also be reachable by keyboard (:focus-within) and by touch. A "hover to reveal delete button" pattern is invisible on a phone.
Target size
24×24 CSS pixels is the WCAG 2.2 minimum; 44×44 is the practical guidance for primary touch targets. Spacing counts, so a 20px icon with 12px of padding passes.
Do not disable zoom, ever
Repeating it because it keeps happening. Chapter 4.
The 300ms tap delay is gone
Provided you have the viewport meta tag. If you are shipping a touch-action polyfill from 2014, delete it.
touch-action
Controls which gestures the browser handles versus your code. touch-action: manipulation on interactive elements removes double-tap-to-zoom handling on that element without disabling page zoom.

Device mode is a start. It is not the test.

The mobile viewport height problem

100vh on a phone is the height with the URL bar hidden, so a full-screen section is taller than the visible area and the bottom is cut off until the user scrolls. 100svh is the small viewport — always visible, safe. 100lvh is the large one. 100dvh tracks the change live, which is correct for a fixed drawer but causes reflow during scroll if used on a large layout region. Default to svh and reach for dvh deliberately.

9Check yourself

Five questions.

1. Your product card looks right on the home page grid and cramped in the 240px sidebar. It already has media queries. Why do they not help?

Because a media query asks about the viewport, and the viewport is the same in both places — the sidebar is narrow while the window is wide, so the card gets the wide layout in a narrow box. This is the exact flaw container queries were introduced to fix: put container-type: inline-size on the slot and query @container, and the component adapts to the space it actually has, in both locations, with one rule.

2. Why is font-size: clamp(1rem, 4vw, 3rem) an accessibility problem, and what fixes it?

The preferred value is pure vw, which does not respond to the user's text-size setting or to text zoom — the viewport width is unchanged by zooming text, so the middle term is frozen and the heading stays put. WCAG 1.4.4 requires text to be resizable to 200%. Including a rem term in the preferred value restores that: clamp(1rem, 0.5rem + 2.5vw, 3rem) still scales fluidly with the viewport and grows when the user increases their base font size.

3. You add srcset with three widths and the browser downloads the largest file on a phone. What is the likely cause?

A missing or wrong sizes attribute. Without it, sizes defaults to 100vw — the browser assumes the image spans the full viewport, multiplies by the device pixel ratio, and picks accordingly. On a 390px-wide phone at 3× that is 1170 CSS-pixel-equivalents, so it fetches the 1200w file even though the image is rendered at 150px in a card. The fix is a sizes value that describes the layout width at each breakpoint, or sizes="auto" with loading="lazy", which lets the browser measure the real layout first.

4. A card's dropdown menu used to overflow the card and now gets clipped. You recently added container queries. Connected?

Yes. container-type: inline-size applies layout, style and size containment to that element, which makes it a containing block for absolutely positioned descendants and establishes a new formatting context that clips overflow in the contained axis. The dropdown that used to escape now cannot. Options: move the container declaration to a different ancestor; render the menu in the top layer with the Popover API, which is immune to ancestor containment; or use CSS anchor positioning so it attaches to the trigger without being a descendant.

5. Your hero uses min-height: 100vh. On iPhone the bottom of the content is cut off. Explain and fix.

vh refers to the large viewport — the height when the browser's URL bar and toolbar are hidden. On first load they are visible, so the actual visible area is smaller than 100vh and the bottom of a full-height section sits below the fold. Use 100svh for the small viewport, which is always fully visible, or 100dvh if you genuinely want the element to resize as the bars hide — but be aware that dvh on a large layout region causes reflow mid-scroll, which is its own problem. svh is the safe default.
