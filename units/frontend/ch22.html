CHAPTER 22

Packages and dependencies

A typical front-end project has fifteen direct dependencies and twelve hundred transitive ones. Every one of them is code you ship, code you must update, and code someone else can change. This chapter is about making that a decision rather than an accident.

Part 6 The toolchain·Reading time 45 minutes·Demos semver resolver, bundle weight·Prerequisites none

1What a dependency costs

Five costs, only one of which is visible at install time.

Bytes
Whatever survives tree shaking ships to every user, and Chapter 1 established that JavaScript is charged twice — download plus parse and execute on the user's CPU.
The transitive graph
You approved one package; you installed its dependency tree. A single direct dependency commonly pulls in dozens, each with its own maintainers, release cadence and security surface.
Supply chain
Every package in that graph runs on your build machine and in your users' browsers. A compromised maintainer account somewhere five levels down is a compromise of your product. Section 7.
Maintenance
Updates, breaking changes, deprecations, and the day the package is abandoned. A dependency is a commitment to keep tracking someone else's decisions.
Coupling
The more of your code shaped around a library's API, the more expensive it is to leave. This is the cost people notice last and regret most.
The question to ask before installing

Not "is this package good?" but "what does this do that I would otherwise write, and how much of it do I need?". A date-formatting library for one toLocaleDateString call, a utility library for one debounce, a UUID package for crypto.randomUUID() — the platform has absorbed a great deal in the last few years. Equally: do not reimplement date arithmetic, internationalisation, cryptography or a rich text editor. The judgement is about how much of the library's surface you actually need, and how bad the failure mode is if you get it wrong yourself.

2Semantic versioning

Three numbers, a promise, and the range syntax that decides what you get on the next install.

PartBumped whenYou should expect
Major · 3.1.4Something breaksTo read a migration guide and change code.
Minor · 3.1.4Something is added, compatiblyTo upgrade safely and ignore the new feature.
Patch · 3.1.4Something is fixedTo upgrade without thinking.

Below 1.0.0 the rules are suspended: anything may break in any release, and ^0.3.1 therefore allows only 0.3.x. Treat pre-1.0 dependencies as pinned by default.

Semver range resolver A real range matcher — edit the range and see which published versions satisfy it.
— the version a fresh install would resolve to

^ — caret, the npm default
Allows anything that does not change the leftmost non-zero digit. ^2.3.1 means >=2.3.1 <3.0.0. This is the right default for well-behaved libraries and the reason a lockfile matters.
~ — tilde
Patches only: ~2.3.1 means >=2.3.1 <2.4.0. Reasonable for a dependency that has burned you before.
Exact
2.3.1 and nothing else. Correct for tooling where reproducibility matters more than fixes, and unnecessary for application dependencies once you have a lockfile.
Prereleases
3.0.0-beta.2 sorts before 3.0.0 and is never matched by a normal range — you must ask for it explicitly. This surprises people who expect ^3.0.0 to pick up a beta.
The uncomfortable truth
Semver is a promise made by humans. Maintainers ship accidental breaking changes in patch releases regularly — a type definition change, a stricter runtime check, a dropped Node version. That is the argument for lockfiles, for a delay before adopting new releases, and for having tests.

3Lockfiles

The difference between "it works on my machine" and "it works".

package.json records ranges. A lockfile records the exact version, integrity hash and resolved URL of every package in the entire transitive graph. Without one, two installs a week apart produce different node_modules.

Always commit it
Including for libraries. The old advice that libraries should not commit lockfiles was about not publishing them — your own CI still needs reproducible installs.
npm ci, not npm install, in CI
ci installs exactly what the lockfile says, fails if it disagrees with package.json, and deletes node_modules first. install may quietly update the lockfile, which means CI can pass on code that no longer matches what you committed. The equivalents are pnpm install --frozen-lockfile and yarn install --immutable.
Review lockfile diffs
Not line by line — but a pull request that changes one dependency and touches four hundred lockfile lines deserves a question. That diff is the only place a transitive change is visible before it ships.
Merge conflicts
Do not hand-edit. Take one side, then re-run the install to regenerate.

4The three package managers

They differ mainly in how node_modules is laid out, and that turns out to matter.

LayoutCharacter
npm Flat and hoisted: everything lifted to the top level where possible Ships with Node, works everywhere, no decision to justify. Slower and heavier on disk than the alternatives. Supports workspaces and overrides.
pnpm A content-addressed global store, symlinked into a strict nested tree Fast, and dramatically smaller on disk — one copy of a package version per machine, not per project. Its strictness is the real feature: it prevents phantom dependencies.
yarn Classic (v1) hoists like npm; Berry (v2+) can use Plug'n'Play with no node_modules at all Berry is fast and strict, with good monorepo tooling. PnP breaks tools that walk node_modules by hand, so check your stack. Classic is in maintenance.
Phantom dependencies

With a hoisted layout, a package you never declared ends up at the top of node_modules because something else depends on it — so import chalk from 'chalk' works even though chalk is nowhere in your package.json. It keeps working right up until the package that pulled it in removes it, at which point your code breaks with no change on your side. pnpm's nested layout makes those imports fail immediately, which is uncomfortable for a week and correct forever after.

Whichever you choose, choose one per repository and enforce it. Two lockfiles in one project is a guarantee that some environment is installing something different. packageManager in package.json, plus Corepack, pins the manager and its version for everyone.

5Dependency types

Five fields, and one of them is the source of the most confusing install errors.

FieldMeaning
dependenciesNeeded at runtime. For an application this distinction matters less than people think — everything is bundled anyway — but keep it honest, because tooling and audits rely on it.
devDependenciesNeeded to build or test. Not installed when your package is consumed as a dependency.
peerDependencies"I need this, but the host application must provide it." How a React plugin says it needs React without bundling a second copy. Modern npm auto-installs them, which is convenient and hides conflicts.
optionalDependenciesInstall failures are not fatal. Platform-specific binaries live here.
overrides / resolutionsForce a version somewhere deep in the tree — the escape hatch when a transitive dependency has a vulnerability and its parent has not updated. Use it, record why in a comment, and remove it when the parent catches up.
enginesDeclares the Node and package-manager versions you support. Combine with .nvmrc so everyone runs the same runtime.
The peer dependency conflict
Two plugins want incompatible versions of the same peer, and the install fails with a wall of text. The correct fix is to upgrade whichever plugin is behind. --legacy-peer-deps silences the error by ignoring peers entirely, which usually installs two copies of a framework and produces a baffling runtime bug — the classic being "invalid hook call" from two Reacts.
Duplicate copies
When two dependencies need incompatible versions of a third, both are installed and both are bundled. npm ls package-name shows the whole tree; deduplicating usually means upgrading something.

6Monorepos

Several packages in one repository, sharing one install and one commit history.

Workspaces
All three package managers support them natively: a root package.json lists the workspace globs, dependencies are installed once and hoisted, and a package can depend on a sibling by name with workspace:*. That alone is enough for a small monorepo.
Task runners
Turborepo and Nx add the part workspaces lack: a task graph, so build runs in dependency order, in parallel, and — critically — with caching, so unchanged packages are not rebuilt. On a large repo the remote cache is the difference between a two-minute and a twenty-minute CI run.
Versioning and publishing
Changesets is the common answer: contributors add a small file describing the change and its semver impact, and a release job aggregates them into version bumps and a changelog. The alternative is fixed versioning, where everything releases together at the same number.
When it is worth it
Shared code between several deployable applications, a design system consumed internally, or a team that wants atomic cross-package changes. The cost is real: build tooling, CI complexity, and slower operations as the repo grows. Two repositories and a published package is a perfectly good architecture, and often the right one.

7Supply-chain risk

The attack that does not need to find a bug in your code.

AttackHow it works
TyposquattingA package named one character away from a popular one. Read what you type, especially when copying from a blog post.
Malicious install scriptspostinstall runs arbitrary code on your machine and your CI runner, with your credentials, before you have run anything. --ignore-scripts is a real option for CI.
Compromised maintainerA legitimate package publishes a malicious version. This has happened to widely used packages more than once.
Dependency confusionA public package published under your internal package's name, resolved in preference to yours. Scope internal packages and configure the registry accordingly.
ProtestwareA maintainer deliberately sabotages their own package. Rare, and a reminder that "popular" is not "governed".
Practical defences, in order of value
Commit lockfiles and use frozen installs. Enable two-factor authentication on any registry account you own. Run npm audit in CI but treat it as a signal rather than a gate — the false-positive rate for front-end code is high, because a ReDoS in a build-time dependency is not a production vulnerability. Prefer packages with provenance attestations. Consider a minimum release age policy, so you never install a version published in the last few days — most malicious releases are caught within hours. And read the lockfile diff.
Reduce the surface
Fewer dependencies is the only defence that scales. A package with zero dependencies, a clear maintainer and a small surface is worth preferring over a more featureful one with forty.
Vendoring
For something small and stable, copying the source into your repository with attribution is a legitimate choice. You take on maintenance and remove an entire trust relationship.

Check before installing
Bundlephobia and pkg-size report minified and gzipped size plus the dependency count. It takes ten seconds and prevents the conversation where a 300 KB library is discovered three sprints later.
Prefer ESM
Tree shaking requires static import/export; a CommonJS package cannot be shaken and is included whole. Chapter 23 covers the mechanism. Check for an exports map with an import condition.
"sideEffects": false
A package field telling bundlers that importing a module has no observable effect, so unused ones can be dropped entirely. Its absence is often why a "tree-shakeable" library is not being shaken.
Import granularly
import debounce from 'lodash/debounce' or import { debounce } from 'lodash-es' pull one function; import _ from 'lodash' pulls all of it. The same applies to icon sets, chart libraries and date libraries.
The platform did some of it already
Intl.DateTimeFormat and Intl.NumberFormat for formatting, Intl.RelativeTimeFormat for "3 days ago", structuredClone for deep copies, crypto.randomUUID(), Object.groupBy, URLSearchParams, fetch, AbortController. Each of those replaced a package that many projects still ship.

9Keeping current

Little and often, automated, with tests. The alternative is a two-week upgrade project every two years.

Automate the boring ones
Renovate or Dependabot opening pull requests for patch and minor updates, grouped by ecosystem, merged automatically when CI is green. This only works if your test suite is trustworthy — Chapter 25.
Handle majors deliberately
One at a time, with the changelog open, on their own branch. Grouping four majors into one pull request means a failure tells you nothing about which caused it.
Set a delay
Configure your bot to wait a few days after publication. It costs nothing and it is the cheapest protection against both malicious releases and broken ones.
Notice abandonment
No release in two years, open issues unanswered, a deprecation notice on the registry. Plan the replacement before it becomes urgent — the worst time to migrate is when a vulnerability is announced.
Prune periodically
depcheck and knip find declared-but-unused packages, and every codebase has some. Removing one is the only dependency change with no risk attached.

10Check yourself

Six questions.

1. Your package.json says "react": "^18.2.0" and a colleague's machine installed 18.3.1 while yours has 18.2.0. What went wrong?

The lockfile was not committed, or was bypassed. package.json records a range; the caret allows any 18.x at or above 18.2.0, so two installs on different days resolve differently. The lockfile exists precisely to pin the resolved version of every package in the transitive graph, and CI must use npm ci (or the frozen-lockfile equivalent) so it installs exactly that and fails loudly on a mismatch rather than silently updating.

2. Why does ^0.4.2 not allow 0.5.0?

Because the caret allows changes that do not modify the leftmost non-zero digit, and below 1.0.0 that digit is the minor. So ^0.4.2 resolves to >=0.4.2 <0.5.0 — effectively tilde behaviour. The reasoning is that semver explicitly suspends its guarantees before 1.0.0: anything may break in any release, so npm treats each minor as potentially breaking. The practical implication is that pre-1.0 dependencies need deliberate upgrades and should not be assumed safe to bump.

3. An import works locally and fails in CI with "cannot find module", and the package is not in your package.json. Explain.

A phantom dependency. With npm's or yarn classic's hoisted layout, a transitive dependency gets lifted to the top of node_modules, so importing it resolves even though you never declared it. It breaks the moment the resolution changes — a different install order, a dependency dropping it, a different package manager, or a fresh install in CI. The fix is to declare it explicitly. The prevention is a strict layout: pnpm's symlinked tree or yarn Berry's PnP makes undeclared imports fail immediately and locally.

4. npm audit reports fourteen high-severity vulnerabilities in a front-end project. How seriously should you take it?

Seriously enough to read each one, not seriously enough to gate the build on the count. Most front-end audit findings are in build-time dependencies that never reach a browser, and many are classes of issue — regular-expression denial of service, prototype pollution reachable only from untrusted input the package never sees — that do not apply to your usage. The questions are: does this package run at build time or in the browser, is the vulnerable code path reachable from anything a user controls, and is there a fixed version. Where a transitive package is stuck, overrides forces a patched version. Treating audit as a pass/fail gate mostly teaches teams to ignore it.

5. What does --legacy-peer-deps actually do, and why is it dangerous?

It tells npm to ignore peer dependency declarations entirely, restoring pre-npm-7 behaviour. The error it silences is a real statement that two packages need incompatible versions of a shared dependency, and ignoring it typically results in two copies of that dependency being installed and bundled. With a framework that keeps module-level state — React's hook dispatcher being the famous case — two copies produce runtime failures that look nothing like a dependency problem. The correct fix is to upgrade whichever package has the outdated peer range, or to pin a compatible set with overrides and record why.

6. A teammate wants to add a 72 KB library to format three dates. What is the conversation?

Not "no libraries" — it is about matching the surface used to the surface shipped. Three date formats are Intl.DateTimeFormat, which is built in, localised, and costs nothing. If more is needed, a tree-shakeable modular library ships only the functions imported, often a couple of kilobytes, and the modern Temporal API is arriving to cover much of the rest. The general test: how much of this library will we use, is it ESM and tree-shakeable, and does the platform already do it. Reserve real dependencies for problems where getting it wrong yourself is expensive — internationalisation, cryptography, rich text, accessibility primitives.
