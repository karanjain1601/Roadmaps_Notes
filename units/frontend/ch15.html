CHAPTER 15

Async JavaScript and the event loop

One thread, an unbounded amount of waiting to do. This chapter is the scheduling model that makes that work: the loop itself, the two queues with very different priorities, promises and the syntax over them, and the difference between code that waits in sequence and code that waits at the same time.

Part 4 JavaScript in the browser·Reading time 50 minutes·Demos execution order, sequential vs parallel·Prerequisites Chapters 3, 13

1The loop

A stack, two queues, and a rendering opportunity. Everything else follows from the order.

JavaScript in a browser runs on one thread and never blocks it waiting for I/O. Instead, slow work is handed to the browser — which has other threads — and your code registers what should happen when it finishes. The event loop is the mechanism that runs those continuations.

Call stack
Where synchronous execution happens. Nothing else can run while a frame is on it. A long function on the stack is Chapter 1's Constraint 2 in action: the page is frozen.
Task queue (macrotasks)
Whole units of work: an event callback, a setTimeout, a parsed chunk of HTML, an I/O completion. One task per loop iteration.
Microtask queue
Promise continuations, queueMicrotask, MutationObserver callbacks. The entire queue is drained after every task, and microtasks added while draining are also run — before the loop moves on.
Rendering
Between tasks, if a frame is due, the browser runs requestAnimationFrame callbacks and then the style, layout, paint and composite steps from Chapter 3.
Execution order, actually run Predict the order, then reveal. The output is captured from a real run.

        Microtask starvation
        
    Because the microtask queue is drained completely, a microtask that schedules another microtask never lets the loop reach rendering. function loop() { queueMicrotask(loop); } freezes the page with no long-running function anywhere in a profile — the stack looks idle and the frame never renders. A setTimeout recursion does not do this, because each callback is a separate task with rendering in between.
    
      
    
    
    

    
    
    
      
    2Promises
    
      
    A value that is not here yet, with a fixed lifecycle and one rule about errors.
    

      
    A promise is in one of three states: pending, then either fulfilled with a value or rejected with a reason. It settles once and never changes again. Handlers registered after it settles still run — on the microtask queue, never synchronously.
    

      
    
        
    Creating, chaining, and the mistakes JavaScript
    
        
    // Only wrap a callback API. Never wrap something already a promise.
const wait = (ms) => new Promise(res => setTimeout(res, ms));

// Chaining: each .then returns a NEW promise. Returning a promise
// from inside one waits for it and unwraps the value.
fetchUser(id)
  .then(user => fetchOrders(user.id))    // returns a promise → flattened
  .then(orders => render(orders))
  .catch(err => showError(err))          // catches anything above it
  .finally(() => hideSpinner());         // runs either way, passes value through

// ✗ Forgetting to return breaks the chain: the next .then gets undefined
//   and does not wait.
.then(user => { fetchOrders(user.id); })

// ✗ The explicit-construction antipattern
function get(url) {
  return new Promise((res, rej) => {
    fetch(url).then(res).catch(rej);     // fetch is already a promise
  });
}

// ✗ .then(onOk, onErr) does NOT catch errors thrown by onOk.
//   .then(onOk).catch(onErr) does.
    
      
    

      
    
        
    An unhandled rejection is a bug
    
        
    Every chain needs a terminal catch, or to be awaited inside a try. Otherwise the failure surfaces as an unhandledrejection event and is often invisible in production. Wire that event to your error reporter regardless — Chapter 29.
    
        
    Promises are eager
    
        
    The executor runs the moment the promise is created, not when you await it. const p = fetch(url) has already sent the request. That is exactly what makes the parallel pattern in section 4 possible.
    
        
    Settling is one-way
    
        
    Calling resolve twice is a silent no-op. There is no cancellation built in — cancellation is a separate mechanism, section 6.
    
      
    

      
    The four combinators
    
      
    
        
    
          
    CombinatorSettles whenUse
    
          
            
    Promise.allAll fulfil, or the first rejectsYou need every result and any failure invalidates the lot. Note the others keep running — rejection does not cancel them.
    
            
    Promise.allSettledAll settle, whatever the outcomeIndependent operations where partial success is fine. Returns {status, value} or {status, reason} per entry.
    
            
    Promise.raceThe first to settle, fulfilled or rejectedTimeouts. The classic race([work, rejectAfter(5000)]).
    
            
    Promise.anyThe first to fulfil; rejects only if all rejectRedundant sources — try three mirrors, take whichever answers.
    
              
        
    
      
    
    
    

    
    
    
      
    3async and await
    
      
    Syntax over promises, with one performance trap that is extremely easy to write by accident.
    

      
    An async function always returns a promise. await pauses that function until the awaited value settles — but it does not block the thread: the rest of the function is registered as a microtask continuation and the loop carries on.
    

      
    
        
    Sequential versus concurrent JavaScript
    
        
    // ✗ Sequential — three round trips end to end. Each await waits for
//   the previous to finish before the next request is even sent.
const user  = await getUser(id);
const posts = await getPosts(id);
const stats = await getStats(id);

// ✓ Concurrent — all three start immediately, total time is the
//   slowest one. Correct whenever they do not depend on each other.
const [user, posts, stats] = await Promise.all([
  getUser(id), getPosts(id), getStats(id)
]);

// The same trap inside a loop — n round trips, one at a time
for (const id of ids) results.push(await load(id));

// Concurrent version
const results = await Promise.all(ids.map(load));

// …with a concurrency cap, because 500 simultaneous requests is
// its own problem. Chunk, or use a small pool.

    Error handling
    
        
    try/catch works normally around await. Note that with Promise.all one rejection loses the other results entirely — use allSettled when partial success is useful.
    
        
    The floating promise
    
        
    Calling an async function without awaiting it starts the work and discards the result and any error. If that is deliberate, say so — void doThing() — and attach a catch. TypeScript's no-floating-promises rule catches these.
    
        
    return await
    
        
    Redundant at the end of a function, except inside a try block: without the await, the promise is returned before it settles and your catch never sees the rejection.
    
        
    for await…of
    
        
    Iterates an async iterable — a paginated API, a streaming response body. Deliberately sequential, which here is the point.
    
        
    Top-level await
    
        
    Allowed in modules, and it delays every importer's evaluation. Fine for a config load at the app entry point; a hazard in a shared utility module.
    
      
    
    
    

    
    
    
      
    4Scheduling
    
      
    Seven ways to say "later", each landing in a different place in the loop.
    

      
    
        
    
          
    APIRuns asUse for
    
          
            
    queueMicrotask(fn)MicrotaskAfter the current synchronous run, before rendering. Rare in application code.
    
            
    Promise.resolve().then(fn)MicrotaskThe same thing, spelled differently.
    
            
    setTimeout(fn, 0)TaskYield to the browser: let it render and process input before continuing. The 0 is a minimum, and nesting deeper than five levels is clamped to 4ms.
    
            
    setInterval(fn, ms)Task, repeatingRarely correct: it does not wait for the previous run to finish, so slow callbacks pile up. Prefer a self-scheduling setTimeout.
    
            
    requestAnimationFrame(fn)Before renderAnything visual. Runs once per frame, and not at all in a hidden tab — which is the correct behaviour and a common source of "my timer stopped".
    
            
    requestIdleCallback(fn)Spare timeNon-urgent work: analytics, prefetching, cache warming. Give it a timeout so it eventually runs.
    
            
    scheduler.postTask(fn, {priority})Task, prioritiseduser-blocking, user-visible or background. Explicit priorities instead of hoping setTimeout(0) lands well.
    
            
    await scheduler.yield()Task, resumed earlyBreak a long job into chunks while keeping your place in the queue ahead of unrelated tasks.
    
              
        
    
      
    

      
    
        
    Splitting a long job so the page stays responsive JavaScript
    
        
    async function processAll(items) {
  let lastYield = performance.now();
  for (const item of items) {
    process(item);
    // Every 50ms, hand the thread back so input and rendering happen
    if (performance.now() - lastYield > 50) {
      await (scheduler?.yield?.() ?? new Promise(r => setTimeout(r)));
      lastYield = performance.now();
    }
  }
}
    
      
    

      
    
        Debounce and throttle, correctly
        
    Debounce waits for a pause: do it once, n milliseconds after the last call. Right for a search-as-you-type request or an autosave. Throttle enforces a maximum rate: at most once per n milliseconds. Right for scroll and resize handlers — though for those, coalescing with requestAnimationFrame is better still, because it aligns with the frame rather than an arbitrary interval, and an observer is often better than either.
    
      
    
    
    

    
    
    
      
    5Cancellation
    
      
    Promises cannot be cancelled. Signals let you stop the work behind them.
    

      
    
        
    The signal pattern, and the race condition it fixes JavaScript
    
        
    let inFlight;

async function search(term) {
  inFlight?.abort();                          // cancel the previous request
  inFlight = new AbortController();

  try {
    const res = await fetch(`/search?q=${term}`, { signal: inFlight.signal });
    render(await res.json());
  } catch (err) {
    if (err.name === 'AbortError') return;   // expected: ignore quietly
    throw err;
  }
}

// Without this, typing "cat" fires three requests and whichever
// SERVER is slowest wins the render — so results for "c" can
// overwrite results for "cat". Aborting removes the race entirely.

// Built-in helpers
AbortSignal.timeout(5000)                  // aborts itself after 5s
AbortSignal.any([userSignal, timeoutSignal]) // first to fire wins
    
      
    

      
    Signals are accepted by fetch, addEventListener, the streams APIs and an increasing number of others — and by your own functions, if you check signal.aborted in a loop and listen for the abort event. One controller per view, aborted on teardown, cleans up listeners and in-flight requests together, which is the pattern from Chapter 14.
    
    
    

    
    
    
      
    6Getting off the main thread
    
      
    Async is not parallel. When the work is CPU-bound, only a worker helps.
    

      
    The distinction matters and is often blurred. await does not make anything faster or parallel — it makes waiting non-blocking. A 400ms JSON parse, image filter or sort still occupies the main thread for 400ms whether you await it or not, and the page is frozen throughout. For that you need a second thread.
    

      
    
        
    A worker, minimally JavaScript
    
        
    // main.js
const worker = new Worker(new URL('./crunch.js', import.meta.url), { type: 'module' });
worker.postMessage({ rows });                // structured clone, not a reference
worker.onmessage = (e) => render(e.data);

// crunch.js — no DOM here, and no window
self.onmessage = (e) => {
  self.postMessage(expensiveAnalysis(e.data.rows));
};

// Transferables move ownership instead of copying — near-zero cost
// for large buffers, but the sender loses access.
worker.postMessage(buffer, [buffer]);
    
      
    

      
    
        
    What a worker cannot do
    
        
    Touch the DOM, or read window or document. It has fetch, timers, IndexedDB, WebAssembly and most of the rest.
    
        
    The message cost
    
        
    Data is copied with the structured clone algorithm, which is fast but not free — a large object graph can cost more to send than the computation saves. Use transferables for buffers, and prefer sending a summary back rather than the whole dataset.
    
        
    When it is worth it
    
        
    Parsing or transforming large data, image and video processing, cryptography, syntax highlighting, search indexing, physics. Not worth it for anything under about 50ms, where the messaging overhead dominates.
    
        
    Ergonomics
    
        
    Raw postMessage is awkward for anything beyond one call. Comlink wraps a worker in a proxy so you can await worker.analyse(rows) as if it were local.
    
        
    Other worker types
    
        
    Shared workers serve several tabs of the same origin. Service workers are a different thing entirely — a network proxy, not a compute thread — and are Chapter 28. Worklets are tiny, high-priority workers for audio and painting.
    
      
    
    
    

    
    
    
      
    7Check yourself
    
      
    Six questions. The first is asked in roughly half of all front-end interviews.
    

      
    
        
    1. What order do these log in? console.log(1); setTimeout(()=>console.log(2)); Promise.resolve().then(()=>console.log(3)); console.log(4);
    
        
        
    
          
    1, 4, 3, 2. The two synchronous logs run first, in order. Then the current task ends and the microtask queue is drained, so the promise continuation logs 3. Only then does the loop take the next task from the task queue, which is the timeout, logging 2. The rule to remember: all microtasks, then one task — a promise chain of any length still finishes before a setTimeout(…, 0) registered before it.
    
        
    
      
    

      
    
        
    2. Three independent API calls take 400, 250 and 600 milliseconds. Written with three awaits in a row, how long does the function take, and how would you fix it?
    
        
        
    
          
    1250ms — the sum, because each await prevents the next request from even being sent. Since they are independent, start them all first: await Promise.all([a(), b(), c()]) takes 600ms, the slowest one. The key insight is that promises are eager: calling the function starts the work, so const pa = a(), pb = b() followed by two awaits is also concurrent. Only the await keyword serialises, and only when it sits between the calls.
    
        
    
      
    

      
    
        
    3. A search box fires a request per keystroke. Sometimes the results shown are for a shorter prefix than what is in the box. Why, and what fixes it?
    
        
        
    
          
    A response race. Requests are sent in order but responses arrive in whatever order the server and network produce, so the reply for "c" can arrive after the reply for "cat" and overwrite it. Debouncing reduces how often it happens but does not fix it — it is still possible. Two real fixes: abort the previous request with an AbortController before starting a new one, which is the cleanest; or tag each request and discard any response that is not for the current term. Both are worth having together with a debounce, which is about reducing load rather than correctness.
    
        
    
      
    

      
    
        
    4. Does making a function async stop it blocking the page?
    
        
        
    
          
    No. async changes the return type to a promise and permits await; it does not move any code off the main thread. A function that spends 400ms sorting a large array blocks for 400ms whether or not it is declared async. What await makes non-blocking is waiting — for the network, a timer, a file — because the browser does that on other threads. For CPU-bound work the answers are a web worker, chunking the job and yielding between chunks, or doing less work.
    
        
    
      
    

      
    
        
    5. What is the difference between Promise.all and Promise.allSettled, and when does the difference bite?
    
        
        
    
          
    all rejects as soon as any input rejects, and you lose every other result even though those requests completed successfully. allSettled always fulfils, with an array of {status: 'fulfilled', value} or {status: 'rejected', reason}. It bites on a dashboard loading six independent widgets: with all, one failing endpoint blanks the whole page; with allSettled, five widgets render and one shows an error. A related subtlety: rejection in all does not cancel the other requests — they keep running and their results are discarded.
    
        
    
      
    

      
    
        
    6. Why does setInterval(poll, 1000) misbehave when poll sometimes takes two seconds?
    
        
        
    
          
    Because setInterval schedules by the clock, not by completion. It queues a task every second regardless of whether the previous one has finished, so slow runs overlap and the queue backs up — and when the tab is backgrounded and then restored, a burst of accumulated callbacks can fire at once. Use a self-scheduling timeout instead: run the work, await it, then setTimeout the next run. That guarantees a gap between runs rather than between starts, and it degrades gracefully when the work is slow.
