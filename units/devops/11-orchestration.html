Orchestration and scheduling

Every orchestrator ever built is the same loop: read the desired state, observe the actual state, do something about the difference, repeat forever. Everything else — pods, tasks, allocations, services — is vocabulary. This chapter is that loop, the placement decision it makes on your behalf, and the two numbers that control both.

The reconciliation loop

Chapter 1 promised that four questions decode any tool in this space: where is the desired state written, what compares it against reality, what does it do about a difference, and what happens when that action fails halfway. An orchestrator is the purest example.

for ever:   observe(actual)  →  diff(desired, actual)  →  act  →  sleep

The important property is that it is level-triggered, not edge-triggered. It does not react to the event "a pod died" — it repeatedly notices the condition "there are four pods and I want five". That distinction is why the system self-heals after a missed message, a controller restart or a network partition: nothing depends on having seen a particular event, only on the current difference being visible.

Desired state is declarative and stored centrally
In Kubernetes, objects in etcd behind the API server. You write what you want; you never write the steps. This is the same shape as Terraform's state file (chapter 14) and a Git repository under ArgoCD (chapter 19).
Controllers each watch one slice
The Deployment controller manages ReplicaSets; the ReplicaSet controller manages Pods; the scheduler assigns Pods to nodes; the kubelet on each node makes its assigned Pods real. No component knows the whole picture, and each is independently restartable because it derives everything from current state.
Actions are idempotent by necessity
The loop runs again in a second and must not do the same thing twice. This is chapter 3's idempotency requirement promoted from a scripting nicety to an architectural constraint.
Failure halfway is the normal case
A controller that crashes between creating a pod and recording that it did so simply observes the discrepancy on the next pass. There is no transaction and no rollback, because there is nothing to roll back to — only a difference to reduce.

How the scheduler decides

Placement is two passes over the node list, run once per pod. Filter eliminates nodes that cannot work: not enough unreserved CPU or memory, a taint the pod does not tolerate, a node selector or affinity rule that does not match, no free host port, a volume that cannot attach in that zone. Score ranks the survivors, and the pod goes to the winner.

The scoring strategy is where the interesting decision lives, because it is really a bin-packing policy — and the scheduler places pods one at a time with no lookahead, so an early policy choice can make a later pod unplaceable.

Filter, score, place — one pod at a time
Spread the eight small pods first, then try to place the 3-CPU one
Free capacity is not placeable capacity

At the defaults, spreading puts two small pods on each of four nodes. The cluster then has 8 CPU free and cannot place a 3-CPU pod, because the largest single gap is 2. The pod sits Pending with Insufficient cpu, which reads like a capacity problem and is actually a fragmentation problem — adding a node fixes it, and so would having packed differently.

Bin-packing places all nine. It pays for that by putting 4 pods on one node instead of 2, so losing that node loses twice as much. And note the third case: the same nine pods in a different order all fit even when spreading. The scheduler never revisits a placement, so outcomes depend on arrival order — which is why the descheduler exists, and why anti-affinity rules are the right way to express "these must not share a node" rather than hoping the scoring policy produces it.

Requests, limits and who gets evicted

Two numbers per resource, and they do entirely different jobs. Conflating them is the single most common source of both wasted money and surprise outages.

Requests

A reservation. The scheduler subtracts it from the node's allocatable capacity when deciding what else fits, and the kubelet uses it to set cpu.weight. Nothing enforces it at runtime — a pod may use more if the node has spare. Requests decide placement and protection.

Limits

A ceiling. CPU over the limit is throttled (chapter 9); memory over the limit is an immediate cgroup OOM kill. The scheduler ignores limits entirely. Limits decide what happens when you exceed them.

The gap between requests and actual usage is what makes a cluster affordable — you can commit 150% of a node's memory in limits because not everything peaks together. It is also precisely what creates the risk, and QoS class is how the kubelet decides who pays when the bet goes wrong.

QoS classSet byEvicted
GuaranteedRequests equal limits, for every resource in every containerLast
BurstableRequests set, limits higher or absentSecond, ordered by how far usage exceeds the request
BestEffortNeither setFirst, always, regardless of how little it is using
Memory pressure, and the order the kubelet picks
Raise the api pod's request to its usage — then set its limit equal too
Three things the eviction order teaches

BestEffort dies first even when it is tiny. The 200 MiB cache pod is evicted before a pod using 4 GB, because class outranks size. Omitting requests to "keep it simple" is opting into being killed first, every time.

Among Burstable, distance above the request decides. The api pod at 4,000 MiB against a 1,024 MiB request is 2,976 over; the worker at 1,800 against 2,048 is 248 under. The api pod goes first despite both being Burstable — requests, not raw usage, determine who is safe.

Being slightly under your request is not protection. Raise the api request to 4,096 — above its 4,000 usage — and it is still evicted second, because at 96 MiB under it is the least-under-request Burstable pod on the node. Only setting requests equal to limits moves it to Guaranteed, and then the worker is evicted instead. That is what Guaranteed is for, and it is the correct configuration for anything whose eviction would be an incident.

The position that follows

Always set memory requests, set memory limits equal to them for anything critical, and size both from observed usage plus headroom. Memory is not compressible: there is no throttling, only a kill, so the limit is doing real work. Set CPU requests, and be cautious with CPU limits for the reasons in chapter 9 — cpu.weight already prevents starvation under contention, while a limit throttles even when the node is idle. And measure: a cluster where requests are set from guesswork is either wasting most of its capacity or is one traffic spike from a cascade of evictions, and usually both on different nodes.

The three autoscalers, and why they oscillate

ScalerChangesReacts inWatch out for
HPAReplica count15 s poll, plus metric lagThe metric it scales on must actually correlate with load
VPARequests and limitsMinutesRecreates pods to apply changes; conflicts with HPA on the same metric
Cluster autoscaler / KarpenterNode countMinutes, plus boot and image pullOnly adds a node when a pod is already Pending — so it is reactive by construction

All three are feedback controllers with delay, and delayed feedback oscillates. The HPA formula is deliberately simple:

desired replicas  =  ⌈ current replicas × (current metric ÷ target metric) ⌉

With a 10% tolerance band so it ignores small deviations, a scale-up that takes effect immediately, and a five-minute stabilisation window on scale-down that makes it use the highest recommendation from the last five minutes. That asymmetry is deliberate: scaling up early is cheap and scaling down early is an outage, so the controller is biased. Without the window, the loop of "load drops, remove pods, remaining pods get busier, add pods back" runs indefinitely.

Scaling on CPU when the bottleneck is elsewhere

The default HPA metric is CPU utilisation as a percentage of the request, and it only works if CPU is what saturates. A service whose limit is a downstream connection pool, or that spends its time waiting on I/O, shows flat CPU while queueing badly — so the HPA does nothing while latency climbs, and the on-call engineer scales it by hand. Worse, a service throttled by a CPU limit (chapter 9) shows CPU pinned at the limit and scales up forever without improving, because each new replica is throttled identically. Scale on the thing that actually saturates: queue depth, requests in flight, or a latency SLO via custom metrics. And note the interaction — because utilisation is measured against the request, changing a request silently changes every HPA threshold that depends on it.

Two other patterns are worth knowing. Pod Disruption Budgets constrain what the cluster may do to you voluntarily — a node drain will block rather than take you below the budget — which is what makes cluster autoscaling and node upgrades safe. And overprovisioning with low-priority placeholder pods gives the cluster autoscaler somewhere to preempt from: real pods evict the placeholders instantly and get scheduled in milliseconds, while a new node boots in the background to replace the slack. That converts a several-minute scale-up into an immediate one, at the cost of paying for the slack.

The other orchestrators, briefly

Kubernetes is not the only implementation of the loop, and the differences are mostly in scope. Nomad does scheduling and little else, runs containers and plain binaries alike, and is a single binary — genuinely simpler, with a much smaller ecosystem. ECS is AWS-managed and integrates with the rest of AWS more cleanly than Kubernetes does, at the price of being AWS-only. Docker Swarm is the simplest and is effectively in maintenance. All four have the same reconciliation loop, a filter-and-score scheduler, and the same requests-versus-limits distinction under different names — which is the point of learning the mechanism rather than the vocabulary.

Check yourself

Self-check

  1. A pod is Pending with 0/4 nodes available: Insufficient cpu. kubectl top nodes shows every node about half idle. Explain, and give two fixes.
    Two separate things are being confused. First, scheduling uses requests, not actual usage: a node whose pods request 4 CPU is full from the scheduler's point of view even if they are using 0.2 each, so kubectl top is showing you the wrong number. Second, even genuinely free capacity may not be placeable — it has to be free on one node. Spreading eight 1-CPU pods over four 4-CPU nodes leaves 8 CPU free in the cluster and a largest single gap of 2, so a 3-CPU pod cannot be placed anywhere. Check with kubectl describe node, which prints requests rather than usage. The fixes: reduce the requests if they are set far above observed usage, which is the common case; add a node, which creates a large contiguous gap; or run the descheduler to repack. Longer term, if fragmentation is chronic, moving the scoring policy toward bin-packing helps placement at the cost of blast radius.
  2. Why can the same set of pods be schedulable in one order and not another?
    Because the scheduler places pods one at a time and never reconsiders. It has no lookahead and no notion of the pods that will arrive next, so each decision is locally optimal against the scoring function and can be globally wrong. Placing eight small pods first with a spreading policy leaves four gaps of 2 CPU and nothing can take a 3-CPU pod; placing the large pod first leaves plenty of room for the small ones and all nine fit. This is a genuine property rather than a bug — optimal bin-packing is NP-hard and a scheduler making thousands of decisions a minute cannot solve it — but it has practical consequences. Use priorityClassName so that important pods are scheduled before filler and can preempt it, express real constraints with anti-affinity or topology spread rather than hoping the scoring policy produces them, and run the descheduler if placements drift badly over time.
  3. Your smallest, least important pod has no requests or limits "to keep the manifest simple". Under memory pressure, what happens to it?
    It is evicted first, always, regardless of how little memory it is using. Omitting both requests and limits puts a pod in the BestEffort QoS class, and the kubelet's eviction ranking is by class before anything else: every BestEffort pod goes before any Burstable pod, which goes before any Guaranteed one. In the demo a 200 MiB BestEffort cache is evicted before a pod using 4 GB. There is also a second cost: with no request, the scheduler counts the pod as consuming nothing, so it will happily place it on a node that has no room for it in practice — the pod is scheduled and then killed. "Simple" here means "first to die and invisible to the scheduler", which is rarely what the author intended.
  4. Two Burstable pods on the same node. One is using 1,800 MiB, the other 4,000 MiB. Which is evicted first, and is the answer "the bigger one"?
    Not necessarily — it depends on their requests, not their usage. The kubelet ranks Burstable pods by how far usage exceeds the request. In the demo, the 4,000 MiB pod requests 1,024 and is therefore 2,976 above; the 1,800 MiB pod requests 2,048 and is 248 below. The larger one is evicted, but because it overran its reservation, not because it is larger — if the requests were reversed the answer would flip. This is the practical meaning of a request: it is a claim on protection as much as a scheduling input. Note the corollary the demo also shows: merely raising the request slightly above your usage is not enough, because you can still be the least-under-request Burstable pod on the node. To be genuinely protected, set requests equal to limits and become Guaranteed.
  5. A node is committed at 150% of its memory in limits. Is that wrong?
    No — it is the point. Overcommitting limits is what makes a cluster affordable, because workloads do not all peak simultaneously and sizing every pod for its peak would waste most of the hardware. What matters is the other number: the sum of requests must not exceed allocatable, because that is the reservation the scheduler honours, and the gap between total requests and total limits is the size of the bet you are taking. The bet fails when enough pods peak together to push actual usage past the eviction threshold, and then the QoS ranking decides who pays. So the healthy configuration is requests sized from observed usage with headroom, limits above them for burst, Guaranteed for anything whose eviction would be an incident, and monitoring on the node's actual usage against the eviction threshold rather than on the commitment ratio. A cluster at 150% limits and 60% requests is well configured; one at 150% requests is not schedulable at all.
  6. Your HPA is at maximum replicas, CPU shows 100%, and adding replicas does not reduce latency. What should you check?
    Whether CPU is actually the constraint, and specifically whether the pods are being throttled by a CPU limit. HPA utilisation is measured against the request, so a pod with a request of 200m and a limit of 500m that is throttled at the limit reports 250% utilisation and scales forever — but every new replica is throttled identically, so total useful throughput barely moves. Check container_cpu_cfs_throttled_periods_total, per chapter 9. The other possibility is that the bottleneck is downstream and shared: a connection pool, a database, a rate-limited third-party API. Adding replicas then increases contention for the same constrained resource and can make latency worse, and it is the metastable pattern from chapter 6. The fix in the first case is to raise or remove the CPU limit; in the second it is to scale on the thing that actually saturates — queue depth, in-flight requests, or a latency objective — rather than on CPU.
  7. Why does the HPA scale up immediately but wait five minutes to scale down?
    Because the two errors have very different costs and because a feedback loop with delay oscillates. Scaling up too eagerly wastes some money for a few minutes; scaling down too eagerly causes an outage. The controller is therefore deliberately asymmetric: scale-up applies at once, while scale-down uses the highest recommendation from a five-minute stabilisation window, so a brief dip in load cannot remove capacity. Without it the loop is self-sustaining — load drops, replicas are removed, the remaining replicas become busier, the metric rises, replicas are added back, load per replica drops, and it repeats indefinitely, with every cycle causing pod churn and cold starts. The same reasoning appears throughout this unit: chapter 6's jittered retry backoff and chapter 8's TTL jitter are the same idea, which is that a control loop needs damping or its corrections become the disturbance.
