Chapter 17 · Delivery

Continuous integration

Chapter 1 showed that integration cost rises with batch size and that fixed merge overhead sets the floor on how small a batch is worth making. The pipeline is that fixed overhead. Every minute it takes and every spurious failure it produces feeds directly into the branch-lifetime and deploy-cadence models — which makes CI speed and CI trustworthiness delivery decisions rather than developer conveniences.

What a pipeline is for

A CI pipeline answers one question — is this change safe to merge? — and it should answer it as cheaply and as early as it can. Everything else is arrangement.

StageAnswersTypicalNote
Lint and formatIs it written the way we write things?SecondsShould already have run as a pre-commit hook (chapter 5); here it is enforcement
Type checkIs it internally consistent?Tens of secondsCatches a large class of errors before a single test runs
Unit testsDoes each piece behave?1–3 minThe bulk of your coverage should be here, because it is the cheapest place for it
Build the artefactDoes it compile and package?1–5 minChapter 10 — cache layers and use registry-backed cache for ephemeral runners
Integration testsDo the pieces work with real dependencies?5–15 minTestcontainers or a compose file, not a shared staging database
Security and policyAny known vulnerabilities, secrets, or policy violations?1–3 minChapters 10, 14 and 21. Can run in parallel with everything above
End-to-end testsDoes a user journey work?10–30 minThe most expensive and most flaky. Keep the number small and deliberate

The ordering of that list is not decorative. A pipeline gives you no information until it finishes or fails, so the time you spend waiting for bad news depends entirely on where in the sequence the failure is caught — and the optimum ordering is a scheduling problem with a known answer.

expected time to red  =  Σ P(first failure at stage i) × (time to reach the end of stage i)

Minimised by sorting stages by duration ÷ failure probability ascending — cheapest evidence first. A stage that takes eight seconds and fails 6% of the time is worth running before one that takes twelve minutes and fails 3%, even though the second finds more serious problems, because the first buys information at a hundredth of the price.

Same stages, same failure rate, different order
Switch the ordering — the green run does not change and the wait for bad news does
Ten minutes is the number that matters

Below roughly ten minutes an engineer waits for the pipeline and stays in context. Above it they start something else, and the cost of the run is no longer the run — it is the run plus a context switch back, conventionally about fifteen minutes of re-orientation. So a 23-minute pipeline costs closer to 38 minutes of elapsed developer attention per run, and at chapter 1's fixed merge cost that pushes the optimal branch lifetime outward and the deploy cadence down. The lever is not to make everyone more patient; it is to move the long stages off the critical path — run them after merge, on a schedule, or against the merge queue rather than every push.

Making it fast

Cache the right layer, and check it is hitting
Dependency caches — ~/.npm, ~/.m2, the Go module cache — keyed on the lockfile hash so they invalidate exactly when they should. Chapter 10's registry-backed Docker layer cache, so an ephemeral runner reuses the previous build. A cache with a poor key is worse than none: it is downloaded, missed, and rebuilt anyway. Log the hit rate; almost nobody does, and a silently broken cache is common.
Parallelise, but understand the critical path
Running lint, typecheck and unit tests concurrently is nearly free and, in the demo, saves under a minute — because the long tail dominates. Sharding the slow suite across ten runners is the change that matters, and it costs ten runners.
Run only the tests that could have broken
Affected-target detection — Bazel, Nx, Turborepo, or a dependency graph you maintain — turns a monorepo's forty-minute suite into two minutes for a change touching one service. This is the single biggest lever available in a monorepo and it is why chapter 5 listed CI cost as the monorepo's characteristic failure mode.
Move the expensive stages off the blocking path
End-to-end tests, performance tests and full security scans on a merge queue or a post-merge schedule rather than on every push. The trade is real — you find out later — but "later" measured against a pipeline nobody waits for is often no worse in practice.
Fail fast, and mean it
Stop the pipeline at the first failure rather than gathering a complete report. The exception is when several independent checks each produce useful findings; then run them in parallel and collect everything, which is not the same as running them in sequence.
yaml — a pipeline shaped by the ordering above
jobs:
  quick:                                ← seconds. fails 10% of the time. runs first, always
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm                    ← keyed on the lockfile, so it invalidates exactly when it should
      - run: npm ci
      - run: npm run lint && npm run typecheck

  unit:
    needs: quick                        ← do not spend runner minutes if lint already failed
    strategy:
      matrix: { shard: [1, 2, 3, 4] }   ← sharding is what makes a slow suite fast;
    steps:                                parallelising the FAST stages barely moves the total
      - run: npm test -- --shard=${{ matrix.shard }}/4

  build:
    needs: quick                        ← parallel with unit, not after it
    steps:
      - uses: docker/build-push-action@v6
        with:
          cache-from: type=registry,ref=ghcr.io/org/app:buildcache
          cache-to:   type=registry,ref=ghcr.io/org/app:buildcache,mode=max
                                        ← chapter 10: without this an ephemeral runner has no
                                          layer cache at all and rebuilds everything every time
  integration:
    needs: build
    steps:
      - run: npm run test:integration   ← testcontainers, not a shared staging database

  e2e:
    if: github.event_name == 'merge_group'
    needs: build                        ← off the per-push path entirely. runs on the merge queue,
    steps:                                so it gates merging without making everyone wait for it
      - run: npm run test:e2e

Flaky tests, and why a tiny rate is fatal

A test that fails occasionally for reasons unrelated to the code is worse than no test. The reason is arithmetic rather than annoyance: the suite passes only if every test passes, so independent flake probabilities compound across the whole suite.

P(green | the code is fine)  =  (1 − flake rate)number of tests

At 0.05% per test — one spurious failure in every two thousand runs of a single test, which sounds like nothing — a suite of 2,000 tests passes only 36.8% of the time on perfectly good code. Nearly two runs in three go red for no reason.

A negligible flake rate, multiplied by the suite
Turn on one retry, then look at what it does to real intermittent failures
Retries fix the symptom in one step
Retrying failed tests once takes the spurious failure rate from 63% to 0.05%, because a test must now flake twice in a row. It is genuinely effective and it is why almost every large suite does it.
And they mask real failures at the same time
A genuinely broken test that fails half the time now passes on retry 25% of the time. You have not made the suite more accurate, you have made it more lenient — in both directions, and the second direction is the one that reaches production.
Fixing the tests achieves the same thing without the masking
A tenfold reduction in flake rate gets to 9.5% spurious with no retries at all. Slower to achieve and strictly better, which is the argument for retries as a stopgap with an owner rather than as a permanent setting.
There is a trust budget, and it is small
To stay under a 5% spurious rate at 0.05% per test you can have about 102 tests. Beyond that the suite goes red often enough that engineers re-run on reflex without reading the output — and once that habit forms, genuine failures are re-run too. That is the real cost of flakiness: not the wasted minutes but the loss of the signal.
The operational answer

Detect flakes automatically by re-running the suite against an unchanged commit on a schedule; anything that fails is flaky by definition. Quarantine them — keep them running but non-blocking, with the results visible — so the signal is restored immediately while the fix is pending. Give every quarantined test an owner and a deadline, because a quarantine list with no expiry is just deletion with extra steps. And track the spurious failure rate as a first-class metric: it is the accuracy of your primary safety mechanism, and it belongs on the same dashboard as chapter 1's four numbers.

What makes a build trustworthy

Pin everything, including the runner
Lockfiles for dependencies, digests for base images (chapter 10), a lock file for Terraform providers (chapter 14), and pinned action versions by commit SHA rather than by tag — a mutable tag on a third-party action is arbitrary code execution with a credential attached.
Build once, promote the artefact
Rebuilding per environment means what you tested is not what you shipped. Build one image, tag it with the commit, and promote that digest through environments. This is chapter 5's argument against long-lived environment branches, expressed as an artefact rather than a merge.
Give CI an identity, not a key
OIDC federation to a cloud role with the trust policy constrained to your repository and branch — chapter 13's confused deputy applies directly. A long-lived cloud key in CI secrets is the credential most likely to leak and least likely to be rotated.
Treat the pipeline as a supply chain
Anything CI runs has your credentials. A compromised dependency, a malicious pull request from a fork with access to secrets, or a typosquatted action are all direct paths to production. Forked pull requests must not receive secrets by default, and chapter 20 covers provenance and signing.
The merge queue, and the semantic conflict it solves

Chapter 5 described two pull requests that each pass CI and break trunk when combined — a semantic conflict no textual merge can detect. "Require branches to be up to date" solves it by forcing a rebase and a re-run before every merge, which works and serialises merging: with a twenty-minute pipeline, a busy repository can merge three times an hour. A merge queue solves the same problem without the serialisation, by speculatively testing batches of pull requests in their prospective merge order and merging the ones that pass together. When a batch fails it bisects to find the culprit. It is the right answer above a certain merge rate, and it is also where the expensive end-to-end suite belongs — gating the merge without making every push wait for it.

Check yourself

Self-check

  1. Your pipeline runs end-to-end tests first because "they catch the most important problems". What is wrong with that?
    It maximises the time you wait to be told about the cheap problems. A pipeline gives no information until it finishes or fails, so expected time-to-red is the sum over stages of the probability of first failing there multiplied by the time taken to get there — and putting the twelve-minute stage first means every lint error costs twelve minutes to discover. In the demo, reordering identical stages from slowest-first to cheapest-evidence-first takes expected time-to-red from 21 minutes to 4.3, with exactly the same total work and the same overall failure probability. The optimum is to sort by duration divided by failure probability: a stage that takes eight seconds and fails 6% of the time buys information a hundred times more cheaply than one taking twelve minutes and failing 3%, regardless of which finds the more serious problem. The serious problems are still found — just after the trivial ones have been eliminated for free.
  2. Your suite has 2,000 tests, each of which fails spuriously about one run in two thousand. How often does a good commit go red?
    About 63% of the time. The suite passes only if every test passes, so the probability is (1 − 0.0005)^2000, which is approximately e^(−1) = 36.8%. A per-test flake rate that sounds entirely negligible produces a suite that is wrong about good code nearly two runs in three, because independent probabilities compound across the whole suite. The consequence is worse than the wasted minutes: at that rate engineers stop reading failures and re-run on reflex, so genuine failures are re-run too and the suite has stopped being a signal. The trust budget is small — to stay under 5% spurious at that per-test rate you can have about 102 tests — which means any suite of realistic size needs a per-test flake rate one or two orders of magnitude lower than instinct suggests.
  3. Adding "retry failed tests once" fixes your red builds overnight. What did you also change?
    You made the suite more lenient in both directions. Spurious failures collapse — from 63% to 0.05% in the model — because a flaky test must now fail twice in a row. But a genuinely broken test that fails half the time now passes on retry 25% of the time, so real intermittent defects reach production more often than before. The retry has not improved accuracy, it has moved the threshold. It is still a reasonable stopgap and most large suites use it, provided two things are true: the retries are recorded and tracked so you can see which tests are relying on them, and there is an owner and a deadline for fixing the underlying flakiness. The alternative that has no downside is fixing the tests — a tenfold reduction in flake rate reaches 9.5% spurious with no retries at all — which is slower to achieve and strictly better.
  4. Two pull requests each pass CI and break trunk when merged together. Compare the two fixes.
    This is chapter 5's semantic conflict: each branch was tested against a base that did not contain the other, and the conflict is behavioural rather than textual, so no merge algorithm can find it. The simple fix is "require branches to be up to date before merging", which forces a rebase and a full re-run before each merge — correct, and it serialises merging, so with a twenty-minute pipeline a busy repository can merge about three times an hour. That is a hard cap on chapter 1's deploy cadence imposed by pipeline duration. A merge queue solves it without serialising: it speculatively tests batches of pull requests in their prospective merge order, merges the batch if it passes, and bisects to find the culprit when it does not. It is the right answer above a modest merge rate, and it is also the natural home for the expensive end-to-end suite, which then gates merging without making every push wait for it.
  5. Your monorepo pipeline takes forty minutes for every change, however small. What is the highest-value fix?
    Affected-target detection: work out which projects the change could possibly have affected, from the dependency graph, and run only those tests and builds. A change to one service in a monorepo of forty typically touches a handful of targets, so the pipeline goes from forty minutes to two or three. Bazel, Nx, Turborepo and Pants all do this; so does a hand-maintained mapping if the repository is simple enough. This is the specific fix for the specific problem, and chapter 5 named CI cost as the monorepo's characteristic failure mode for exactly this reason. Parallelising and caching help too but they are smaller: in the demo, running the three fast stages concurrently saves under a minute because the long tail dominates the critical path. Sharding the slow suite across runners does move the number, and it costs runners — worth doing after target detection, not instead of it.
  6. Why should CI build the artefact once rather than rebuilding it for each environment?
    Because rebuilding means what you tested is not what you shipped. Two builds of the same commit at different times can differ — a floating base image tag, an unpinned transitive dependency, a different runner image, a package published in between — so a staging test result does not transfer to production. Build once, tag with the commit, and promote that digest through environments, with configuration supplied at runtime rather than baked per environment. It is faster as well as safer, since you build once instead of three times. This is the artefact-shaped version of chapter 5's argument against long-lived environment branches: promote a thing that was tested rather than re-derive it, and it depends on chapter 10's point that a tag is a mutable pointer while a digest is not.
  7. Someone proposes running the full end-to-end suite on every push so problems are found earlier. Evaluate.
    It finds problems earlier in the pipeline and later in wall-clock time, which is usually the wrong trade. End-to-end suites are the slowest and by a wide margin the flakiest stage, so putting one on every push pushes the pipeline past the roughly ten-minute threshold at which the author stops waiting and context-switches — turning a 23-minute run into about 38 minutes of elapsed developer attention — and it multiplies the flake exposure by the number of pushes rather than the number of merges. Both effects feed straight into chapter 1's models: a higher fixed merge cost lengthens the optimal branch and lowers the deploy cadence. The better arrangement is to run the end-to-end suite on the merge queue, where it gates merging without gating iteration, keep the number of end-to-end tests small and deliberate, and push coverage down into unit and integration tests where it is cheaper and far more stable.
