Chapter 14 · Infrastructure

Infrastructure as code

Clicking in a console produces infrastructure nobody can review, reproduce or reason about six months later. Declaring it in code fixes that and introduces one genuinely new object: a state file recording what the tool believes it created. Almost everything that goes wrong with infrastructure as code is a disagreement between the code, that file, and what is actually running.

Declarative, and the loop underneath

An imperative script says create a subnet. Run it twice and you have two subnets, or an error. A declarative configuration says a subnet with this CIDR exists, and the tool works out whether that requires creating, changing or doing nothing. It is chapter 11's reconciliation loop with a human pressing the button instead of a controller running it continuously — and chapter 19 removes the human.

The tools differ in syntax and in where state lives; they do not differ in the model. Everything below is about the model.

The state file, and the three-way comparison

State exists because a cloud API cannot answer "which of these resources are mine?". It maps your resource address — aws_db_instance.main — to a provider identifier, and it caches the attributes last seen. Without it the tool could not tell a resource it created from one that already existed, and could not know which resource a renamed block refers to.

That gives plan three inputs rather than two, and the eight combinations behave differently enough that it is worth knowing them by name.

Code, state and reality — all eight cases
Try "created in the console" and then "state file lost"
The two cases that ruin an afternoon

Created out of band. A resource exists in the cloud and in your code but not in state, so the plan says create and the apply fails with "already exists". Nothing is broken; the tool simply has no way to adopt something it did not make. terraform import — or an import block, which is reviewable — attaches the existing resource to the address. If the state file is lost entirely this happens to every managed resource at once: the infrastructure is fine and the tool can no longer touch any of it without importing each one individually.

Removed from code. Deleting a block does not mean "stop managing this", it means destroy it. The two intentions look identical in a diff and have opposite consequences. If you want to stop managing something while keeping it, terraform state rm first, then remove the block — or add a removed block with destroy = false, which is reviewable rather than a local command somebody remembers to run.

The resource that is in neither code nor state

Somebody clicked something in the console two years ago. It is running, it is billed, it is reachable, and no plan will ever mention it — because a plan compares code with state, and it is in neither. This is where the surprise line items from chapter 13 come from and where the security group that is open to the world lives. The tool cannot help; the countermeasures are a service control policy that denies console writes in production accounts, and periodic reconciliation with a drift scanner such as driftctl, Cloud Custodian or the provider's own resource inventory.

Remote state with locking is not optional
Two engineers applying at once against a local file corrupts it. S3 with DynamoDB locking, Terraform Cloud, GCS, or an equivalent. The lock is what prevents two concurrent applies from interleaving; the versioning is what lets you recover a state file somebody truncated.
State contains secrets, in plaintext
Every attribute the provider returned, including generated database passwords and private keys. Encrypt the backend at rest, restrict who can read it as tightly as you restrict production itself, and never commit it. A state file in a git repository is chapter 5's secret-in-history problem with a larger radius.
Split state by blast radius, not by tidiness
One state file for the whole estate means every apply risks everything and takes minutes to refresh. Split along failure boundaries — network, data, per-service — and read across the boundary with data sources or remote state outputs rather than merging. Chapter 13's account separation argument applies here too.
refresh is what makes reality an input
Before planning, the tool queries the provider for the current attributes of everything in state. That is how console drift is detected and corrected. It also means a plan makes many API calls and can be slow on a large state — and that -refresh=false, which people reach for to make plans fast, silently removes reality from the comparison.

Update, replace, and the blast radius of one line

Some attributes can be changed on a live resource and some cannot. The provider knows which: a ForceNew attribute cannot be updated in place, so changing it means destroy and recreate. And because a recreated resource gets a new identifier, everything that referenced the old one must be recreated too. One line in a diff can propagate through a whole dependency graph.

Change one attribute, see what it takes with it
Compare the database engine version against the database identifier
The attribute decides, not the resource
On the same security group, editing an ingress rule touches one thing and renaming it replaces five — the group, the launch template, the autoscaling group, the load balancer and the database. Nothing in the diff distinguishes them; you have to read the plan.
One line can replace your database
Changing the VPC CIDR replaces all eight resources in the example and about 47 minutes of rebuild, the database included. This is the argument for reading every -/+ in a plan rather than scanning for the resource you meant to change.
create_before_destroy removes the downtime, not the churn
The same resources are replaced; the new one is created before the old is destroyed, so there is no gap. It requires that both can exist at once — which fails for anything with a unique name or a fixed address, and is exactly why so many resources take a name_prefix instead of a name.
prevent_destroy is the seatbelt
A lifecycle rule that makes any plan destroying the resource fail outright. It belongs on every database, every state bucket and anything holding data you cannot recreate. It is annoying exactly when it should be.
How to read a plan properly

The symbols carry the whole message and they are easy to skim past. + create, - destroy, ~ update in place, and -/+ destroy and recreate — the one that matters. Terraform prints # forces replacement against the specific attribute responsible, which tells you exactly which line to reconsider. Read the summary count first: if you changed one thing and the plan says "12 to add, 12 to destroy", stop. In CI, post the plan on the pull request so it is reviewed alongside the diff, and consider a policy gate — OPA, Sentinel or Checkov — that fails automatically on any unexpected destroy of a protected resource type.

Modules, and the composition that survives

A module is a reusable group of resources with inputs and outputs. The failure mode is not writing too few, it is writing one enormous module with forty variables that is harder to understand than the resources it wraps.

What a good module looks like

It owns one meaningful thing — a VPC, a service, a database with its backups and alarms. Its inputs are decisions, not passthroughs. It is versioned and referenced by a tag rather than a branch, so a change upstream cannot alter what production applies. And it is usable without reading its implementation.

What a bad one looks like

Forty variables, most of which forward directly to a resource argument, so callers must understand the resource anyway and the module. Nested three deep, so an error message points at a line nobody has ever opened. Referenced from main, so the infrastructure changes when someone else merges.

count versus for_each, which is not a style question

With count, resources are addressed by position: aws_instance.web[0], [1], [2]. Remove the first element from the list and every subsequent resource shifts down an index — so Terraform sees [0] changing identity, [1] changing identity, and one destroy at the end. Removing one item from a list of ten replaces nine resources. With for_each, resources are addressed by key: aws_instance.web["api"]. Removing one key destroys exactly one resource and leaves the rest untouched. Use for_each for anything with an identity, and reserve count for the genuinely positional case or for count = var.enabled ? 1 : 0.

The workflow that makes it safe

  1. Plan on the pull request, apply on merge. The plan output is the review artefact — a diff of HCL does not tell you that a resource will be replaced, and the plan does. Post it as a comment so the reviewer sees the consequence rather than the intention.
  2. Save the plan and apply that file. terraform plan -out=tfplan then terraform apply tfplan. Applying without a saved plan re-plans against whatever the world looks like now, so what you reviewed and what runs can differ.
  3. Gate with policy as code. OPA, Sentinel, Checkov or tfsec, running against the plan JSON. Fail on an unencrypted volume, a security group open to 0.0.0.0/0, a missing tag, or any destroy of a resource type you have marked protected. This is where a rule beats a reviewer, because it never gets tired at 6pm.
  4. Give CI a role, not a key. OIDC federation from the CI provider to a role in the target account, with the trust policy constrained to your repository and branch — chapter 13's confused deputy applies directly. A long-lived cloud key in CI secrets is the credential most likely to leak and least likely to be rotated.
  5. Pin providers and modules. A lock file for providers, tags for modules. Otherwise a provider release between your plan and your colleague's changes the behaviour of code nobody edited, which is chapter 10's argument about mutable tags in a different costume.
  6. Detect drift on a schedule. A nightly plan that alerts if anything is not a no-op. It catches console changes while someone still remembers making them, and it catches the resource somebody deleted by hand before the next real apply tries to recreate it.
Where infrastructure as code genuinely does not fit

Two honest exceptions. During an incident, a console change to restore service is correct and the reconciliation comes afterwards — a policy that forbids it will simply be violated under pressure, so the better rule is to require a follow-up pull request within a day. And for exploration, clicking is faster than writing HCL for something you may discard in ten minutes; the discipline is that the sandbox account is separate and gets emptied, so nothing exploratory becomes load-bearing by accident. What should never be manual is anything in production that is expected to persist, because the console leaves no artefact anyone can review, reproduce or explain later.

Check yourself

Self-check

  1. A colleague created a security group in the console. You add matching HCL and run apply. What happens and why?
    The plan says create and the apply fails with "already exists" or a duplicate-name error. The tool compares code with state, and the resource is in neither state nor its knowledge — a cloud API cannot answer "which of these are mine?", which is precisely why the state file exists. It has no way to recognise the existing group as the thing your block describes. The fix is terraform import, or better an import block in the code, which is reviewable and shows up in the plan rather than being a local command someone ran once. Then the plan will show any differences between the imported reality and your HCL as ordinary updates. The broader lesson is that "created out of band" is one of two states the tool handles badly, and both are avoided by denying console writes in production accounts.
  2. You delete a resource block from your Terraform because that service is now managed by another team. What does the next apply do?
    It destroys the resource. Removing a block does not mean "stop managing this", it means "this should not exist" — and since the resource is still in state, the plan reconciles by deleting it. The two intentions are indistinguishable in a code diff and have opposite consequences, which is what makes this dangerous during a reorganisation or a repository split. To hand something over while keeping it, remove it from state first with terraform state rm and then delete the block, or use a removed block with lifecycle { destroy = false }, which has the advantage of being visible in the pull request. And read the plan: this shows up as a bare -, which is exactly the symbol worth stopping on.
  3. You change engine_version on an RDS instance and the plan shows -/+. What is that symbol and what should you do?
    -/+ means destroy and recreate, not update in place — so the database will be deleted and a new empty one created, taking your data with it unless a final snapshot is configured and restored by hand. If a minor version bump is producing a replacement, something else in the same diff is a ForceNew attribute; Terraform prints # forces replacement against the specific line, so read the plan body rather than the summary. Common culprits are a changed identifier, a changed engine, or a subnet group that is itself being replaced and dragging the database with it. Never apply a -/+ on a stateful resource without understanding exactly which attribute caused it. prevent_destroy in a lifecycle block on every database makes the plan fail rather than proceed, which is the correct default for anything holding data you cannot recreate.
  4. You have ten instances defined with count and a list. You remove the second item. What does the plan show?
    Nine resources changing rather than one being destroyed. count addresses resources by position, so removing the second item shifts everything after it down an index: what was [2] is now [1], [3] becomes [2], and so on. Terraform sees each of those addresses now describing a different resource and plans updates or replacements for all of them, plus one destroy at the end. for_each over a map or set addresses by key instead — aws_instance.web["api"] — so removing one key destroys exactly that one and leaves the others untouched. This is why for_each is the default for anything with an identity, and why migrating an existing count resource usually needs terraform state mv to move each address rather than letting the plan sort it out.
  5. Your CI pipeline runs terraform apply -auto-approve after a merge. What is wrong with that even though the plan was reviewed on the pull request?
    Applying without a saved plan re-plans against the world as it is at apply time, which is not the world the reviewer saw. Between review and merge, someone may have changed something in the console, another pipeline may have applied, or a provider version may have moved — so the apply can legitimately do something nobody approved. The fix is terraform plan -out=tfplan in the pull-request job, storing that artefact, and terraform apply tfplan after merge, which either applies exactly what was reviewed or fails because the state has moved on. Two things pair with it: a policy gate running against the plan JSON so unexpected destroys and insecure configurations fail automatically, and OIDC federation instead of a static cloud key, constrained by the trust policy to your repository and branch.
  6. Why does a state file need locking, and what specifically goes wrong without it?
    Because an apply reads state, makes changes over minutes, and writes state back. Two applies running concurrently both read the same starting point and both write at the end, so the second overwrites the first's record — leaving resources that exist in the cloud and not in state, which is the "created out of band" collision from earlier in the chapter, and potentially resources destroyed by one run while the other believed they existed. Worse, the two runs can interleave actual API calls against the same resources. Locking makes the second run wait rather than proceed. In practice this means a remote backend with a lock — S3 with DynamoDB, GCS, Terraform Cloud — plus versioning on the state object so a truncated or corrupted file can be rolled back. A local state file on someone's laptop has neither, and also cannot be read by CI.
  7. A nightly drift check reports that a security group has an extra ingress rule. What are the possible causes and how do you respond?
    Someone made a console change — during an incident, or because the code path was slow, or without realising the resource was managed. The next apply will silently revert it, which is right if it was accidental and an outage if it was a deliberate fix for something still broken. So the response is to find out why before applying: if it was an incident fix, the change belongs in code as a follow-up pull request, and the code should be updated before the reconciliation reverts it. If it was accidental, applying is the correct action and the drift check has just done its job by catching it while somebody still remembers. The reason to run the check nightly rather than relying on the next apply is exactly this: the further you are from the change, the less likely anyone can explain it. Structurally, the durable fix is a service control policy denying console writes in production accounts, so the only path is the reviewed one.
