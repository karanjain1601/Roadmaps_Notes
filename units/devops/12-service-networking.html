Service networking, ingress and mesh

Pods are ephemeral and have addresses that change constantly, so something must translate a stable name into a current set of endpoints and keep that translation up to date on every node. The interesting parts are the gaps: how long the translation is wrong after a pod dies, and what happens when the thing doing the balancing is looking at connections rather than requests.

From a name to a set of endpoints

A Service is a stable name and virtual IP in front of a changing set of pods. Nothing is proxying in the usual sense — the ClusterIP does not exist on any interface. It is a rule in every node's dataplane that rewrites the destination to one of the current endpoints.

  1. A Service selects pods by label. The endpoints controller watches pods matching that selector and maintains an EndpointSlice listing the addresses that are currently ready — readiness, not liveness, and not merely running.
  2. Cluster DNS resolves the name to the ClusterIP. CoreDNS serves svc.namespace.svc.cluster.local. This is where chapter 7's ndots:5 problem lives, and it is why a fully qualified external name deserves a trailing dot.
  3. Every node's dataplane rewrites the destination. kube-proxy in iptables mode writes a chain per service that DNATs to a random endpoint; in IPVS mode it programs a kernel load balancer instead. Newer clusters may use eBPF via Cilium and skip kube-proxy entirely.
  4. The packet goes straight to the pod. There is no hop through a proxy process. The connection is client-pod to server-pod, which is why you cannot see service traffic by looking at a load balancer, and why the balancing decision is made once per connection.

How long traffic keeps arriving at a dead pod

Removing a pod from rotation is not instant, and it is not one step. The endpoints controller must notice, write an updated EndpointSlice, and then every node in the cluster must observe that change and reprogram its dataplane. Until the last node has done so, traffic still arrives.

window  =  detection  +  control-plane propagation  +  per-node dataplane sync

On a graceful deletion, detection is zero — the API server knows immediately — but propagation is not, and the pod is sent SIGTERM at the same moment the removal starts. On a crash, detection is the readiness probe: period × failureThreshold, which at the defaults of 10 seconds and 3 failures is thirty seconds before anything even begins.

Why preStop: sleep 5 appears in so many manifests

On a graceful delete, two things start at the same instant: the kubelet begins terminating the pod, and the endpoints controller begins removing it. They are not ordered. If the pod stops accepting connections before the last node has updated its rules, every request routed there in the interim fails — 240 requests at the settings above, on every pod replaced, in a routine rolling update.

A preStop hook that simply sleeps delays the SIGTERM without doing anything else, giving the removal time to propagate first. Five seconds against a 1.2-second propagation takes the failures to zero. It is not elegant and it is the standard answer; the alternative is for the application to fail its readiness probe on SIGTERM and then keep serving for a few seconds, which is chapter 6's shutdown sequence and is better if you control the code. Make sure terminationGracePeriodSeconds exceeds the sleep plus the drain, or the kubelet's SIGKILL arrives in the middle of it.

A crash is a completely different order of magnitude

Nothing tells the control plane that a pod has stopped serving; it has to be discovered. With the default probe settings — period 10 s, failureThreshold 3 — detection alone takes 30 seconds, during which the pod is still in the endpoint list and still receiving its full share. That is 6,240 failed requests at 2,000 rps across ten replicas. Tightening the probe to period 2 with threshold 2 cuts the window to 5.2 s and the failures to 1,040 — a sixfold improvement from two numbers in a manifest. The counterweight is that aggressive probes eject healthy pods during a transient blip, so the sensible landing point is a fast, cheap readiness probe that tests only the process itself, and retries on the client side or in the mesh to cover the rest.

Ingress and the Gateway API

A LoadBalancer service provisions one cloud load balancer per service, which is expensive and gives you no L7 routing. An Ingress is a single entry point that routes by host and path to many backend services — one cloud load balancer in front of an nginx or Envoy deployment inside the cluster, which is chapter 6's reverse proxy with its configuration generated from Kubernetes objects.

Ingress is limited, and its extensions are vendor-specific
The resource covers host, path and TLS. Everything else — rate limiting, header manipulation, canary weights, authentication — arrives as controller-specific annotations, so an Ingress written for the nginx controller is not portable to any other.
The Gateway API is the replacement
It splits the concern properly: GatewayClass and Gateway are owned by the platform team, HTTPRoute by the application team, and cross-namespace references are explicit. Traffic splitting by weight, header matching and request mirroring are first-class rather than annotations, which is what makes chapter 18's canary deployments declarative.
Terminate TLS at the gateway
One place for certificates, chapter 7's ACME automation, and cipher policy. cert-manager issues and renews them as Kubernetes objects, which removes the most common cause of an expired certificate — a renewal that succeeded and never reloaded anything.
externalTrafficPolicy is a real trade-off
Cluster, the default, accepts traffic on any node and forwards it to a pod possibly on another node — even balancing, one extra hop, and the client's source IP is lost to SNAT. Local only sends to pods on the receiving node — preserves the source IP and removes the hop, at the cost of uneven balancing if pods are unevenly distributed across nodes.

Why all your gRPC traffic is on one pod

The balancing decision in a plain Kubernetes Service is made once per connection, when the first packet is DNATed. With HTTP/1 and no keep-alive that is roughly once per request and the distribution is even. With HTTP/2 and gRPC — which multiplex thousands of requests over a small number of long-lived connections — the request distribution is simply whatever the connection distribution happened to be, and it never changes.

Connections are balanced; requests are not
Set 10 connections over 20 backends, then scale the backends up
With fewer connections than backends, some get nothing at all
Ten connections over twenty pods leaves about twelve pods (60%) receiving zero requests, while the busiest gets roughly 4.3× the average. You are paying for twenty replicas and running on eight.
The imbalance shrinks as connections per backend grows
At 100 connections over 20 backends the worst is 1.9× the mean; at 10,000 it is 1.08×. This is why the problem is invisible for HTTP/1 services with many short connections and severe for gRPC with a handful of pooled ones — same infrastructure, opposite outcome.
Scaling out does nothing until clients reconnect
Existing connections are pinned to the pods they were established with. Double the replica count during an incident and every new pod receives zero traffic — the classic "we scaled up and nothing improved", which then gets misdiagnosed as a downstream problem.
Three ways to fix it, in increasing order of cost

Client-side balancing over a headless Service. Set clusterIP: None so DNS returns every pod address, and let the gRPC client balance across them with round_robin. No infrastructure, and the client re-resolves as pods change. The catch is that DNS-based membership updates lag, and every client language needs the configuration.

An L7 proxy in the path. Envoy, Linkerd or an ingress controller in HTTP/2 mode balances per request rather than per connection, which removes the problem entirely and gives you chapter 6's least-connections and power-of-two-choices as well. This is one of the strongest practical arguments for a mesh.

Bound connection lifetime. max_connection_age in the gRPC server, or MAX_CONCURRENT_STREAMS tuning, forces periodic reconnection so the distribution is reshuffled and new pods are eventually discovered. A blunt instrument, but it costs one server option and it is often enough.

The service mesh: what it gives and what it costs

A mesh puts a proxy — historically a sidecar container in every pod — on both ends of every call, and controls all of them from one place. Everything it provides is something you could implement in each application; the argument is that doing it once in the infrastructure is cheaper and more consistent than doing it in five languages.

What you get

mTLS between every service with automatic certificate rotation on an hourly cycle, so chapter 7's renewal problem disappears. Per-request L7 balancing, which fixes the gRPC problem above. Retries, timeouts and circuit breaking as policy rather than library code. Traffic splitting by weight for chapter 18's canaries. And uniform golden-signal metrics and distributed traces for every call, with no application changes.

What it costs

Roughly 0.5–1 ms of added latency per hop — doubled, since the proxy is on both ends — which compounds with call depth: a five-hop chain pays it ten times. Around 50–100 MB of memory and a slice of CPU per pod, scaling with pod count rather than traffic. A control plane to run and upgrade. And a substantial increase in the number of places a request can fail, in ways that are unfamiliar during an incident.

When it is worth it, and the sidecar-less alternative

The honest test is how many of the benefits you already have and how many services you run. With five services, an L7 ingress and a shared client library get you most of the way at a fraction of the operational cost. With a hundred services in four languages and a compliance requirement for encryption in transit, implementing mTLS and consistent retry policy in every one of them is the more expensive option by a wide margin, and the mesh wins. The middle ground has changed recently: ambient or sidecar-less modes — Istio ambient, Cilium's eBPF dataplane — move mTLS and L4 policy into a per-node component and make the L7 proxy optional per workload, which removes most of the per-pod memory cost and much of the latency for services that only need encryption and identity. If you evaluated meshes a few years ago and concluded the overhead was not worth it, that arithmetic is worth redoing.

Sidecars have two operational sharp edges

Startup ordering. If the application container starts before the proxy is ready, its first outbound calls fail — which turns into a crash loop for anything that connects to a dependency at boot. Kubernetes native sidecars (an initContainer with restartPolicy: Always) fix this properly; before that it needed hold-until-ready hacks. Shutdown ordering. The mirror image: if the proxy exits first, the application's in-flight requests fail, and a Job whose sidecar never exits runs forever and never completes. Both are ordering problems around a container that was never designed to be part of your pod's lifecycle, and both are worth verifying explicitly rather than assuming.

Check yourself

Self-check

  1. Every rolling update produces a small burst of 502s even though the application handles SIGTERM correctly. Why, and what fixes it?
    Handling SIGTERM correctly is necessary and not sufficient, because the removal from the endpoint list and the SIGTERM begin at the same moment and are not ordered. The endpoints controller must write an updated EndpointSlice and then every node in the cluster must observe it and reprogram its dataplane — a second or so in a small cluster, several in a large one. If the application shuts down promptly on SIGTERM, it stops accepting before some nodes have stopped routing, and everything sent in the interim fails: about 240 requests per pod replaced at 2,000 rps across ten replicas. The standard fix is a preStop hook that sleeps for longer than the propagation delay, which delays the SIGTERM so the removal lands first. The better fix if you control the code is for the process to fail its readiness probe immediately on SIGTERM and keep serving for a few seconds before draining. Either way, terminationGracePeriodSeconds must exceed the delay plus the drain time.
  2. A pod is OOMKilled at peak. Why is the user impact so much larger than a rolling update, and what are the two numbers that control it?
    Because nothing informs the control plane that the pod has stopped serving — it must be discovered by the readiness probe. Detection therefore takes periodSeconds × failureThreshold, which at the defaults of 10 and 3 is thirty seconds, and only then does the propagation delay begin. Throughout that window the pod remains in the endpoint list and receives its full share of traffic, all of which fails: roughly 6,240 requests at 2,000 rps across ten replicas, against 240 for a graceful delete. The two numbers are the probe period and the failure threshold; tightening them to 2 and 2 cuts the window from 31 seconds to 5 and the failures to about 1,040. The counterweight is that aggressive probes eject healthy pods during a transient blip, per chapter 6, so the balance is a fast probe that tests only the process itself plus client-side or mesh retries to cover what remains.
  3. You have twenty replicas of a gRPC service. Metrics show three of them handling almost all the traffic and several handling none. Explain.
    A Kubernetes Service balances per connection, not per request: kube-proxy picks an endpoint when the connection is established and every request on that connection goes to the same pod forever. gRPC runs over HTTP/2 and multiplexes many requests over a small number of long-lived connections, so the request distribution is just the connection distribution — and with a handful of clients each holding one or two connections, most pods get none. In the model, ten connections over twenty backends leaves about twelve pods idle with the busiest at 4.3× the mean. The same infrastructure is perfectly even for HTTP/1 because those connections are short and numerous. Fixes: a headless Service plus client-side round_robin so the client balances across all pod IPs itself; an L7 proxy or mesh in the path that balances per request; or bounding connection lifetime with max_connection_age so the distribution reshuffles periodically.
  4. During an incident you double the replicas of that same gRPC service and nothing improves. Why?
    Because existing connections are pinned to the pods they were established with, and nothing moves them. New pods join the endpoint list and receive traffic only from connections established after they appeared — so if the clients are long-lived and are not reconnecting, every new pod sits at zero while the original ones stay saturated. The model shows exactly this: scaling from ten to twenty backends with 200 established connections leaves all ten new backends with no requests. It is a particularly nasty failure during an incident because the obvious action produces no effect and attention moves to the wrong place. Forcing reconnection is the immediate lever — a rolling restart of the clients, or max_connection_age on the server if it is already configured — and per-request balancing is the durable fix.
  5. Someone proposes a LoadBalancer service for each of forty microservices. What is wrong with that?
    Each one provisions a separate cloud load balancer, so it is forty billable load balancers, forty public addresses, forty places to attach a certificate and forty sets of DNS records — with no L7 routing, since the cloud LB is only forwarding to a NodePort. It is also forty separate things to keep consistent for rate limiting, TLS policy and access logging. An Ingress or Gateway is one cloud load balancer in front of a proxy deployment inside the cluster that routes by host and path to all forty services, with certificates managed once by cert-manager. The exception is a service that genuinely needs a non-HTTP protocol or its own address, where a dedicated load balancer is appropriate — but that should be an argued case rather than the default. Internal service-to-service traffic should be ClusterIP and never touch a load balancer at all.
  6. A mesh adds about 0.7 ms per proxy hop. Your architecture has a five-service call chain. What is the real latency cost and what does it imply?
    The proxy is on both ends of every call, so each hop pays it twice: roughly 1.4 ms per hop, and about 7 ms over a five-hop chain — before considering that the tail is worse than the mean, since each proxy adds its own queueing. If the chain's total budget is 50 ms that is 14% spent on infrastructure. The implication is not that meshes are bad but that call depth is the multiplier, so the mesh makes an existing architectural problem more expensive: a deep synchronous chain was already fragile, because availability multiplies and latency adds, and the mesh sharpens the incentive to flatten it. It also argues for evaluating ambient or sidecar-less modes, which keep mTLS and identity while making the L7 proxy optional per workload, so services needing only encryption stop paying the full per-hop cost.
  7. What is the practical difference between externalTrafficPolicy: Cluster and Local?
    Cluster, the default, lets any node accept the traffic and forward it to a pod anywhere in the cluster. Balancing is even regardless of how pods are distributed, at the cost of one extra network hop and — more consequentially — the loss of the client's source IP, because the forwarding node performs SNAT. That breaks IP allowlists, geolocation and per-client rate limiting, and it is why your access logs show node addresses. Local forwards only to pods on the receiving node, which preserves the source IP and removes the hop, but makes balancing depend on pod distribution: a node with three pods gets the same share of load-balancer traffic as a node with one, so those three are underused and the one is overloaded. Nodes with no pods fail the load balancer's health check and are removed, which is the mechanism that stops traffic black-holing. Use Local when you need the source IP, and pair it with a topology spread constraint from chapter 11 so pods are distributed evenly enough for the balancing to be fair.
