Chapter 10 · Containers

Building images

A Dockerfile is a cache key generator that happens to also produce a filesystem. Almost every complaint about container builds — they are slow, the images are huge, the registry bill is absurd, CI takes eleven minutes — traces back to two facts about layers that are easy to state and easy to violate. This chapter is those two facts and what follows from them.

Fact one: a layer's cache is invalid if anything above it changed

Each instruction produces a layer whose cache key is derived from the instruction itself and the key of the layer beneath it. So a cache miss is not local — once one layer misses, every layer after it rebuilds regardless of whether its own inputs changed. That single rule determines your build time, and it means the ordering of instructions is a performance decision rather than a matter of taste.

The classic mistake is one line:

The ordering that destroys the cache

COPY . . before RUN npm ci. The copy's key depends on every source file, so editing one line of application code invalidates it — and therefore invalidates the dependency install beneath it, even though no dependency changed.

The ordering that preserves it

Copy only the manifest and lockfile, install, then copy the source. Now a source edit misses only the layers after the copy, and the expensive install is a cache hit on every build where dependencies did not change — which is most of them.

Which layers rebuild, and what it costs
Change the source, then switch the ordering

The numbers are worth stating plainly. A one-line source change costs 131 seconds and pushes 370 MB in the bad ordering, against 36 seconds and 30 MB in the good one — for an identical image. Across forty builds a day that is well over an hour of CI time and thirteen gigabytes of registry traffic, every day, produced by the position of one line.

Note also what the reordering does not buy: when the dependencies themselves change, both orderings cost the same. Layer ordering is not a general optimisation, it is specifically about putting the things that change often after the things that are expensive, so the expensive work is skipped in the common case.

The rule, and the four things that violate it silently

Order instructions from least to most frequently changing. Base image, system packages, language dependencies, then application source. Everything else follows.

The silent violations: a COPY . . with no .dockerignore, so .git and node_modules are part of the cache key and every commit changes it; an ARG declared before the expensive layers, since redefining it busts everything after it; a RUN apt-get update in its own layer, which caches an ever-staler package index and then breaks the install months later; and any ADD from a URL, whose key is the URL rather than the content, so it caches something that has since changed. A .dockerignore is the highest-value file in this section and takes two minutes to write.

dockerfile — the same build, ordered properly, with BuildKit caching
# syntax=docker/dockerfile:1
FROM node:20-slim AS build
WORKDIR /app

# manifests only — this layer's key depends on two files, not on your source
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
    ← a BuildKit cache mount. the downloaded packages persist across builds
      WITHOUT becoming a layer, so even a cache MISS is fast and the image
      does not carry the npm cache

# source last: a change here misses only from this point down
COPY . .
RUN npm run build

# ---- runtime stage: nothing above this line ships ----
FROM gcr.io/distroless/nodejs20-debian12
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER nonroot
CMD ["dist/main.js"]

Fact two: deleting a file in a later layer does not remove it

Layers are stacked, not merged. Removing a file from a lower layer writes a whiteout entry in the upper one that hides it from the assembled view. The bytes remain in the image, are stored in the registry, and are transferred on every pull. So this saves nothing at all:

dockerfile — the difference is which layer the deletion lands in
# WRONG — two layers. the apt lists are in layer 1 forever; layer 2 just hides them
RUN apt-get update && apt-get install -y build-essential
RUN rm -rf /var/lib/apt/lists/*

# RIGHT — one layer. the deletion happens before the layer is committed,
# so the bytes were never written into it
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
    ← --no-install-recommends is usually worth as much again

The other half of the size story is that a build needs a compiler and a runtime does not. A multi-stage build uses one stage to compile and a second to assemble the runtime image, copying only the artefacts across. Everything in the build stage — toolchain, headers, caches, source, intermediate objects — is discarded rather than hidden.

Where the megabytes are
Move the cleanup into the same RUN, then enable multi-stage, then change the base
Same-layer cleanup saves what the caches weigh
Moving the identical rm -rf into the same RUN takes the example image from 879 MB to 760 MB. The command did not change; only the layer it landed in did.
Multi-stage saves the whole toolchain
Down to 580 MB, because compilers, headers and build caches never enter the runtime image. This is usually the single largest available reduction and it costs a few lines.
Base image choice does the rest
Onto distroless, 392 MB — 2.2× smaller than where we started, and pull time from 35 to 16 seconds. Small bases also carry fewer packages, and therefore fewer CVEs to triage.
But shared layers are only paid once
Twenty images on one host sharing a base pull it once and store it once. This is why standardising on two or three base images across an organisation reduces real bytes more than shrinking any single image, and why the number to watch is the size of the layers that are unique to your image rather than the total.
Where image size actually costs you

It is not disk, which is cheap. It is the moments when the image must move: a scale-up event during a traffic spike, where every new node pulls before it can serve; a rolling deployment across a hundred replicas; a cold node after an autoscaler event; a CI job pulling on every run. In those moments pull time is directly in your critical path — the 20-second difference above becomes several minutes of unavailable capacity when you needed it most. It is also why registry proximity matters: pulling from a registry in another region can cost more than the size reduction saves.

Choosing a base, and the alpine question

BaseSizeHasUse when
scratch0Nothing. No shell, no libc, no CA certificatesA statically linked binary — Go or Rust. You must add CA certs yourself or every HTTPS call fails
distroless~20 MBlibc, CA certs, timezone data, optionally a language runtimeThe sensible default for compiled and most interpreted apps. No shell means no shell for an attacker either
alpine~8 MBmusl libc, busybox, apkSmall and complete — but see below
debian:slim~74 MBglibc, a real shell, aptWhen you need to install system packages or debug in place. The boring, reliable choice
Language images (node:20-slim)~200 MBThe runtime, a package manager, build toolsBuild stages. Rarely the right runtime base once you have multi-stage
Alpine uses musl, and that is not a detail

Alpine is not "Debian but smaller" — it uses musl libc rather than glibc, and the difference surfaces in specific, expensive ways. Any dependency shipping a precompiled glibc binary wheel or native module will not load, so Python and Node builds fall back to compiling from source, which frequently makes the build far slower and larger than the size you saved. DNS resolution differs: musl historically did not read search domains the same way and queries A and AAAA in parallel, which interacts badly with some resolvers. And musl's malloc has markedly different performance characteristics under multi-threaded allocation-heavy load, which has produced well-documented latency regressions in real services.

None of that makes alpine wrong; it makes it a choice with consequences. If you want small, distroless gets you most of the way with glibc and no surprises. If you want alpine, adopt it deliberately, test the actual workload under load, and do not let the 8 MB number be the whole argument.

Reproducibility, and what a tag does not promise

A tag is a mutable pointer. node:20-slim means something different this month than last, and :latest means whatever was pushed most recently. Builds that pin only by tag are not reproducible, and neither are deployments.

Pin base images by digest
FROM node:20-slim@sha256:.... The tag stays for readability and the digest is what is actually resolved. Renovate or Dependabot can bump the digest in a pull request, which turns "our base image silently changed" into a reviewable event.
Deploy by digest, not by tag
Otherwise two replicas started an hour apart can be running different code with no record of it, and a rollback to :v1.4 may not return the bits that were there before. Chapter 20 makes this the basis of the whole supply-chain argument.
Pin what the build installs, too
apt-get install nginx=1.24.0-1 and a committed lockfile. Without them the same Dockerfile produces different images on different days, and a build that succeeded in CI can fail on a rebuild months later for reasons unrelated to your change.
Expect timestamps to differ
Byte-identical rebuilds need SOURCE_DATE_EPOCH and BuildKit's reproducible mode. Worth doing if you are signing images and want independent verification; not necessary for most teams, and it is fine to stop at "same inputs produce functionally identical images".
The build-time controls worth knowing

BuildKit is the default builder now and three of its features matter. Cache mounts — RUN --mount=type=cache,target=/root/.npm — persist a package cache between builds without it becoming a layer, so even a cache miss downloads little and the image stays clean. Secret mounts — RUN --mount=type=secret,id=npmrc — expose a credential to one instruction without writing it into any layer, which is the correct replacement for the ARG NPM_TOKEN pattern that leaks the token into image history forever. And registry-backed cache — --cache-from type=registry,ref=... — lets an ephemeral CI runner reuse the previous build's layers, which is what makes the ordering work in this chapter pay off in CI rather than only on a developer's laptop.

The checks worth running on every build

  1. Run as a non-root user. USER nonroot, and make sure the application does not need to write to paths it no longer owns. Combined with chapter 9's point about the missing user namespace, this is the difference between a compromise starting as root on the host and starting as nobody.
  2. Drop capabilities at run time and declare it in the manifest. --cap-drop=ALL plus whatever is genuinely needed, and no-new-privileges so a setuid binary cannot escalate.
  3. Scan for known vulnerabilities with Trivy or Grype, in CI, failing on high and critical for anything reachable. Expect noise: most CVEs in a base image are in packages your application never invokes, so triage matters more than the raw count — which is another argument for a base image that contains less.
  4. Scan for secrets in the build context and in the layers. A token in an ARG, in a copied .env, or in .git is in the image history permanently, and docker history will show it to anyone who pulls.
  5. Generate an SBOM and sign the image. docker buildx --sbom=true, then Cosign for the signature. This is what makes it possible to answer "are we affected by this CVE" in minutes rather than days, and chapter 20 covers verifying it at deployment.
  6. Add a HEALTHCHECK or its platform equivalent, and make sure it is the readiness kind from chapter 6 rather than something that queries the database.
The smallest image is also the most secure one, for a boring reason

A distroless image has no shell, no package manager, no curl and no wget. An attacker who achieves code execution in it has none of the tools that the next stage of an intrusion normally depends on — they cannot download a payload, cannot spawn a reverse shell in the usual way, and cannot install anything. It is not a boundary, and a determined attacker can bring their own tooling, but it removes a great deal of the convenience that opportunistic automated attacks rely on. The trade is that you cannot exec into it to debug either, which is a genuine cost and is what ephemeral debug containers exist to solve.

Check yourself

Self-check

  1. CI takes eleven minutes on every commit and most commits change one file. The Dockerfile does COPY . . and then RUN npm ci. What is happening and what is the fix worth?
    A layer's cache key incorporates the key of the layer beneath it, so once a layer misses, everything after it rebuilds. COPY . . has a key derived from every source file, so any commit invalidates it — and therefore invalidates the dependency install underneath, even though no dependency changed. Reordering to copy only package.json and the lockfile, install, and then copy the source means a source edit misses only the layers after the copy. In the model this takes a one-line change from 131 seconds and 370 MB pushed to 36 seconds and 30 MB, for an identical image. Across forty builds a day that is over an hour of CI time and about thirteen gigabytes of registry traffic saved daily by moving one line. Add a .dockerignore at the same time, or .git and node_modules are part of the cache key too and every commit invalidates it regardless of ordering.
  2. Your Dockerfile ends with RUN rm -rf /var/lib/apt/lists/* /tmp/build and the image is still 900 MB. Why?
    Because the deletion is in its own layer. Layers are stacked rather than merged, so removing a file that exists in a lower layer writes a whiteout entry that hides it from the assembled view — the bytes stay in the lower layer, stay in the registry, and are transferred on every pull. The image is the sum of all layers, not the size of the final filesystem. The fix is to perform the deletion in the same RUN instruction that created the files, using &&, so the files never enter a committed layer at all. In the model that single change takes the image from 879 MB to 760 MB with an identical command. For build tooling the better answer is a multi-stage build, which discards the entire build stage rather than trying to clean it up.
  3. Someone proposes moving from debian:12-slim to alpine to save 66 MB. What should you check first?
    That the workload still works and still performs, because alpine uses musl libc rather than glibc and that is a behavioural change rather than a size change. Three specific things to check: whether any dependency ships precompiled glibc binaries — Python wheels, Node native modules — since those will not load and the build will fall back to compiling from source, often making the build slower and the image larger than the saving; whether DNS resolution still behaves, since musl handles search domains and parallel A/AAAA queries differently and interacts badly with some resolvers, which matters a great deal given chapter 7's ndots discussion; and whether latency holds under realistic multi-threaded load, since musl's malloc has produced documented regressions in allocation-heavy services. If the goal is simply a small image, distroless gets you to roughly 20 MB with glibc and none of these questions. And 66 MB of a shared base layer is pulled once per host regardless, so the saving is often smaller in practice than it appears.
  4. Your build uses ARG NPM_TOKEN to install from a private registry. Why is this a problem and what replaces it?
    Build arguments are recorded in the image's layer history, so the token is visible to anyone who can pull the image — docker history prints it, and it is present in the registry permanently. Squashing does not reliably remove it and neither does deleting the file it was written to, for the whiteout reason above. The replacement is a BuildKit secret mount: RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci, where the file is available to that one instruction and never becomes part of any layer. As with chapter 5's discussion of secrets in git history, the first action if this has already been pushed is to rotate the token, because it must be assumed compromised — cleaning the image is remediation of the artefact, not of the credential.
  5. An autoscaler adds nodes during a traffic spike and it takes four minutes before they serve traffic. The image is 1.2 GB. Explain the connection and give two mitigations.
    A new node has no layers cached, so it must pull the entire image before the container can start, and that pull is directly in the critical path of adding capacity — precisely when you need capacity most. Image size is cheap on disk and expensive at exactly these moments: scale-up, rolling deployment, cold nodes, and CI. The mitigations are to shrink what is unique to the image — multi-stage to drop the toolchain, same-layer cleanup, a smaller base — and to remove the pull from the critical path, by pre-pulling images onto nodes, keeping a warm pool of nodes, or using a registry in the same region so that bandwidth is not the constraint. Worth checking too whether the size is in layers shared with other images already on the node, since those cost nothing on a warm node but everything on a cold one; the number to optimise is the unique portion.
  6. Why is pinning FROM node:20-slim insufficient, and what does pinning the digest change?
    A tag is a mutable pointer to a manifest, so node:20-slim resolves to different content over time as the upstream publishes patch updates. Two builds of the same commit, weeks apart, can therefore produce different images — with different packages, different CVEs and potentially different behaviour — and neither the Dockerfile nor the commit records which. Pinning by digest, FROM node:20-slim@sha256:..., makes the base content-addressed and therefore fixed: the same inputs give the same base every time, and an upgrade becomes an explicit change to a line in the file. That is better rather than worse for security, because updates arrive as a reviewable pull request from Renovate or Dependabot rather than silently, and you can tell exactly which builds contain which base. The same argument extends to deploying by digest rather than by tag, which chapter 20 builds on.
  7. Your scanner reports 240 vulnerabilities in the base image and nobody looks at the report any more. What went wrong and what would you change?
    The signal-to-noise ratio made the control useless — which is a worse outcome than not scanning, because it creates the appearance of coverage. Most of those CVEs are in packages the application never invokes, present only because the base image includes a full distribution userland. Two changes help. Reduce the surface: a distroless or scratch base contains a fraction of the packages and therefore a fraction of the findings, so the remaining ones are plausibly relevant — this is the strongest argument for a minimal base and it is about triage cost rather than bytes. And make the gate meaningful: fail the build only on high and critical severity with a known fix available, allow documented time-bounded exceptions, and pair it with an SBOM so that when a genuine incident happens you can answer "which of our images contain this package" in minutes. A gate that is always red teaches everyone to override it.
