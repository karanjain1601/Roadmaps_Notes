Chapter 19 · Delivery

GitOps and reconciliation

Chapter 11 described a control loop reconciling desired state against reality. Chapter 14 wrote the desired state in code and had a human run it. GitOps is the obvious remaining step: put the desired state in a repository, run the loop continuously from inside the cluster, and remove the person pressing apply. What changes is not the deployment so much as the direction the credentials point and what "drift" means.

— words— min read2 interactivesNeeds: chapters 11, 14, 18

Four properties, and one of them is the interesting one

Declarative
The whole system is described as data, not as steps. Kubernetes manifests, Helm values, Kustomize overlays — chapter 14's argument, applied to workloads rather than infrastructure.
Versioned and immutable
The description lives in git, so it has history, review, blame and revert for free. The desired state of production is a commit, which means "what was running last Tuesday" is answerable.
Pulled automatically
An agent inside the cluster fetches the description and applies it. Nothing outside needs credentials to the cluster. This is the property with the largest consequences and it is the one people notice last.
Continuously reconciled
Not applied once at deploy time but compared repeatedly, for ever. Divergence is detected and — optionally — corrected. That "optionally" turns out to matter a great deal.
The credential direction is the substantive change

In push delivery, CI holds write credentials to every cluster it deploys to. That makes the CI system the most valuable target in the organisation: compromise it and you have production, in every environment, with no further work — and chapter 17 noted that CI runs arbitrary code from pull requests. In pull delivery, the controller runs inside the cluster and reads a repository; CI's only privilege is to push an image and commit a manifest change. Nothing outside the cluster can write to it. Scaling makes the difference starker: with six clusters, push means six sets of credentials in CI and pull means zero, and the number does not grow.

From commit to running
Compare polling with a webhook — then look at what CI contributes
Polling costs about a minute and a half on average
Pull with a three-minute interval has a mean lead time of 11.8 minutes against 10.1 for push — half the interval, spent waiting for the next poll. A repository webhook takes that to 10.4 minutes, essentially matching push.
So the lead-time objection to GitOps is really an objection to polling
And it is solved by configuring a webhook, which every controller supports. A thirty-minute interval, on the other hand, makes detection 59% of the total lead time, which is a genuinely bad configuration that people arrive at by leaving the default alone in a large installation.
CI dominates either way
It is 68% of the pull lead time. If lead time is the problem, chapter 17 is where the work is, not the choice of delivery mechanism.
The interval is also the manual-change window
The same number that sets detection latency sets how long a change made directly against the cluster survives before being reverted: 90 seconds on average at a three-minute interval. That is a feature and it is deeply surprising the first time it happens during an incident.

What the controller actually does

Three settings decide the behaviour and they are independent. Conflating them is the standard misconfiguration, because their names suggest they cover each other and they do not.

SettingMeansOff means
Auto-syncApply automatically when the repository changesA human presses sync. The repository is nominally the source of truth and the cluster does not follow it
Self-healAlso correct when the cluster changesA manual edit is shown as out of sync and left alone, sometimes for months
PruneDelete resources removed from the repositoryThey stay in the cluster for ever, in no repository, invisible to every diff
Five situations, and what happens in each
Turn off self-heal and prune — the defaults — then read the manual-edit row
Auto-sync is not self-heal, and prune off recreates an old problem

With auto-sync alone — a very common configuration, and the default in several installations — commits deploy and manual edits persist. The controller only acts when the repository changes, so someone's kubectl edit during an incident survives until the next unrelated commit happens to trigger a full apply. The application shows as OutOfSync the whole time and nothing corrects it, which is the worst of both worlds: the repository is not actually the source of truth, and everybody believes it is.

Prune off is the other one. Delete a manifest and the resource stays in the cluster for ever, present in no repository and mentioned by no diff. That is exactly chapter 14's resource that is in neither code nor state — the same failure, reached from a different direction, and worth recognising as one class of problem rather than two.

Rolling back during an incident

With self-heal on, kubectl set image is reverted within a reconciliation interval — so the engineer's fix appears to work, then stops working, usually while they are explaining it to someone. The correct rollback is to change the repository: revert the commit, or set the tag back, and let the controller apply it. That is slower, which is a real cost when minutes matter. Three mitigations are worth having agreed before the incident: configure a webhook so a revert applies in seconds rather than at the next poll; document how to suspend reconciliation for one application so a manual change can hold; and use feature flags for the fastest mitigations, since chapter 18 showed they change behaviour at runtime without touching the desired state at all.

Repository structure and promotion

Separate the application repository from the configuration repository
Application code and deployment manifests have different reviewers, different change rates and different blast radii. Keeping them apart also stops the loop where a manifest bump triggers CI, which builds an image, which bumps the manifest.
Directories per environment, not branches
Chapter 5 argued against long-lived environment branches: they drift apart permanently, so what you tested is not what you shipped, and every promotion is a merge with conflicts. Directories or Kustomize overlays make the difference between environments visible in a diff instead of hidden in divergence.
Promote a digest, not a rebuild
Chapter 17's build-once-promote arrives here as a one-line change: staging references @sha256:…, production references the same digest after it has been proven. Promotion is a pull request that changes one line, which is reviewable and revertable.
Let something bump the image automatically, with care
Argo Image Updater or Flux's image automation watches the registry and commits new digests. Convenient for lower environments, and for production it removes the review step that promotion was giving you — so most teams automate the bump into staging and keep production a deliberate pull request.
yaml — an Argo CD Application with the settings that matter
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: orders-prod
spec:
  source:
    repoURL: https://github.com/org/deploy-config
    targetRevision: main                ← a branch is a moving target. a tag or commit
    path: apps/orders/overlays/prod       makes "what is deployed" exactly answerable
  destination:
    server: https://kubernetes.default.svc
    namespace: orders
  syncPolicy:
    automated:
      prune: true                       ← without this, deleting a manifest leaves an orphan
                                          in the cluster and in no repository, for ever
      selfHeal: true                    ← WITHOUT THIS, a manual kubectl edit persists.
                                          auto-sync alone only reacts to repository changes
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true         ← only touch what actually differs
    retry:
      limit: 5
      backoff: { duration: 10s, factor: 2, maxDuration: 3m }
  revisionHistoryLimit: 10              ← how far back you can roll without a git operation
  ignoreDifferences:                    ← things another controller owns. without this the
    - group: apps                         HPA and Argo fight over replicas for ever, each
      kind: Deployment                    reverting the other every reconciliation
      jsonPointers: ["/spec/replicas"]
Two controllers writing the same field is a real failure mode

The horizontal pod autoscaler from chapter 11 writes spec.replicas. So does your manifest. With self-heal on, Argo sets it back to the declared value, the HPA scales it again, and the loop runs for ever — with a sync event every few minutes, an audit log full of noise, and replica counts that oscillate under load. The fix is ignoreDifferences on that specific field, which declares that another controller owns it. The general principle is worth stating: exactly one thing may own each field, and a continuous reconciler makes any violation of that immediately and permanently visible rather than occasionally confusing.

The problem GitOps creates

If the repository is the desired state, and the desired state includes a database password, then the password is in the repository. Chapter 5 was unambiguous that a secret in git history is a secret that is gone. Four approaches resolve the contradiction and they make different trades.

ApproachIn the repositoryRead access to the repo gives an attackerRotation
Sealed SecretsCiphertext, encrypted to one cluster's public keyNothing usable — only the in-cluster controller can decryptRe-seal and commit. Per cluster, since the key is cluster-specific
SOPS + age or KMSCiphertext, decryptable by named keysNothing, unless they also hold a keyRe-encrypt and commit. Works across clusters; the key policy is the control
External Secrets OperatorOnly a reference — a path in a secret storeA map of what exists and where, which is itself useful reconnaissanceRotate in the store; nothing in git changes
Vault agent / CSI driverOnly a reference; the value is injected at pod startA map of what existsRotate in Vault, with short-lived dynamic credentials
Which to choose, and the property that decides it

The dividing question is whether a rotation should require a commit. Sealed Secrets and SOPS keep everything in the repository, which preserves the property that the repository fully describes the cluster and makes disaster recovery a clone — genuinely valuable, and it means every rotation is a code change and every emergency rotation is a pull request. The operator approaches keep only references, so rotation happens in the secret store with no deploy at all and short-lived dynamic credentials become possible — at the cost that the repository no longer contains the whole truth and a restore needs the store as well. For a small estate SOPS is hard to beat on simplicity; above a certain size, rotation frequency and dynamic credentials usually win the argument. Chapter 21 covers the stores themselves.

Check yourself

Self-check

  1. Someone argues against GitOps because "pull delivery is slower". Evaluate the claim.
    Partly true and easily fixed. Pull adds a detection step — the controller has to notice the repository changed — which with a three-minute polling interval costs half that on average, taking mean lead time from about 10.1 minutes with push to 11.8 with pull. Configure a repository webhook and it falls to 10.4, essentially matching push. So the objection is really an objection to polling, not to pull. Two things put the number in perspective. CI is 68% of the total either way, so if lead time is the actual concern the work is in chapter 17. And a long interval genuinely is bad — at thirty minutes, detection becomes 59% of lead time — which is a configuration people arrive at by leaving a default alone in a large installation rather than by choosing it. Set against that, pull removes cluster credentials from CI entirely, and that difference does not shrink with tuning.
  2. Why is having cluster credentials in CI worse than it sounds?
    Because CI is the system in your organisation that most readily executes untrusted code. It runs whatever is in a branch, often including pull requests, with whatever secrets it holds — so credentials that can write to production are one supply-chain problem or one misconfigured fork trigger away from being used. And the exposure scales: with six clusters, push means six sets of write credentials in one place, and every new environment adds another. Pull inverts the direction. The controller runs inside the cluster it manages and reads a repository, so nothing outside the cluster can write to it, and CI's only privileges are pushing an image and committing a manifest change — both of which are recoverable and both of which leave an audit trail. That is the durable argument for GitOps; the lead-time comparison is a wash once a webhook is configured.
  3. Your team enabled auto-sync. An engineer's manual fix from three weeks ago is still in the cluster. How?
    Auto-sync is not self-heal, and they are separate settings. Auto-sync means "apply when the repository changes"; self-heal means "also correct when the cluster changes". With only the first enabled, the controller never looks for divergence in the cluster — it acts on repository events — so a manual edit survives until some unrelated commit triggers a full apply that happens to overwrite it. The application shows as OutOfSync the entire time and nothing corrects it, which is the worst combination: the repository is not the source of truth and everybody believes it is. Enable self-heal, and pair it with an alert on any application that has been OutOfSync for more than a few minutes, since that condition should be transient. Also enable prune at the same time, or a resource deleted from the repository stays in the cluster indefinitely.
  4. During an incident an engineer runs kubectl set image to roll back. It works, then stops working. Explain and give the right procedure.
    Self-heal reverted it. The repository is the desired state and a continuous loop corrects anything that differs, so a direct change to the cluster is drift by definition rather than an instruction — and it is undone within one reconciliation interval, about 90 seconds on average at a three-minute setting. The correct rollback is to change the repository: revert the commit or set the image tag back, and let the controller apply it. That is genuinely slower, and three mitigations should be agreed before an incident rather than during one. Configure a repository webhook so a revert applies in seconds rather than at the next poll. Document how to suspend reconciliation for a single application, so a manual change can hold while you work. And prefer feature flags for the fastest mitigations, since chapter 18 showed they change runtime behaviour without touching the desired state at all, which means nothing reverts them.
  5. You deleted a manifest from the repository last month and the resource is still running. What setting, and why does it matter beyond tidiness?
    Prune is off. Without it, the controller applies what is in the repository and never removes what is not, so a deleted manifest leaves the resource in the cluster indefinitely. It matters because that object is now in the cluster and in no repository: it is running, it is billed, it may be exposed, and no diff will ever mention it. That is precisely chapter 14's resource that appears in neither code nor state, reached from a different direction — worth recognising as one class of problem rather than two, since both are produced by a reconciler that only knows how to add. Turning prune on is the fix; before doing so on an existing installation, run a dry run, because the first prune of a long-lived cluster can be alarming. Pair it with a resource inventory reconciled against the repository, which is the equivalent of the drift scanner in chapter 14.
  6. Your Deployment's replica count oscillates and Argo logs a sync every few minutes. What is happening?
    Two controllers own the same field. The horizontal pod autoscaler writes spec.replicas based on load; your manifest also declares it; and self-heal sets it back to the declared value on every reconciliation. The HPA scales it again, the controller reverts it, and the loop runs indefinitely — producing oscillating replica counts under load, a sync event every few minutes and an audit log full of noise. The fix is ignoreDifferences on that specific JSON pointer, which declares that another controller owns the field. Better still, remove replicas from the manifest entirely so there is nothing to fight over. The general rule is that exactly one thing may own each field, and a continuous reconciler turns any violation from an occasional confusion into a permanent visible conflict — which is arguably a feature, since the ownership problem existed either way.
  7. If the repository is the desired state, where does the database password go?
    Not in plaintext, and there are two shapes of answer. Encrypt it in the repository — Sealed Secrets, where the ciphertext can only be decrypted by a controller in one specific cluster, or SOPS with age or a cloud KMS key. Read access to the repository then yields nothing usable, and the repository still fully describes the cluster, so disaster recovery is a clone. The cost is that every rotation is a commit, including emergency ones. Or keep only a reference in the repository and have an operator fetch the value at runtime — External Secrets Operator or a Vault agent. Rotation then happens in the store with no deploy at all and dynamic short-lived credentials become possible, at the price that the repository no longer contains the whole truth and a restore needs the secret store too. The deciding question is whether a rotation should require a commit: for a small estate SOPS is hard to beat, and above a certain rotation frequency the operator approach wins.
