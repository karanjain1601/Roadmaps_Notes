Chapter 06 · Source and servers

Web servers, proxies and load balancers

Almost nothing you run is reached directly. There is a proxy in front of it terminating TLS, choosing a backend, enforcing timeouts and deciding what a failure looks like — and the configuration of that proxy determines more about your tail latency and your blast radius than the application behind it usually does. This chapter is about the choices it makes on your behalf.

What a reverse proxy is actually for

A forward proxy sits in front of clients and represents them to the internet: egress filtering, corporate web gateways, an outbound allowlist. A reverse proxy sits in front of servers and represents them to clients. Same mechanism, opposite direction, and it is the reverse case that carries almost all of your operational concerns.

It terminates TLS in one place
Certificates, renewal, cipher policy and protocol versions are configured once instead of in every service in every language. Chapter 7 covers what that configuration should contain.
It absorbs slow clients
A client on a poor mobile connection takes eight seconds to send a request body. If it talks directly to your application, one of your workers is held for those eight seconds doing nothing. The proxy buffers the whole request first and only then opens a fast local connection to the backend, so the worker is occupied for milliseconds. This one behaviour is why a proxy in front of a thread-per-request application is not optional.
It is where cross-cutting policy lives
Rate limiting, request size caps, header normalisation, compression, static file serving, access logging, IP allowlists, redirects. All things you would otherwise implement N times, inconsistently.
It decouples clients from instances
Backends can be added, removed, restarted and redeployed without any client knowing an address. This is the precondition for every deployment strategy in chapter 18.
It chooses where each request goes
Which is the interesting part, and the subject of the next two sections.

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    client_max_body_size 10m;            ← default is 1m. the cause of most unexplained 413s
    client_body_timeout 15s;

    location / {
        proxy_pass http://api;

        # without these four the backend sees nginx's IP as the client and
        # generates http:// URLs behind an https:// listener
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # keepalive to the upstream needs HTTP/1.1 and an empty Connection header.
        # omitting these two silently disables the `keepalive 32` above
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_connect_timeout 2s;        ← TCP connect. should be small; a healthy backend
                                           on the same network answers in single-digit ms
        proxy_send_timeout   10s;
        proxy_read_timeout   10s;        ← DEFAULT IS 60s. this is the number in the second demo,
                                           and leaving it at 60 is how one slow dependency
                                           consumes an entire worker pool

        proxy_next_upstream error timeout http_502 http_503;
        proxy_next_upstream_tries 2;     ← bound the retries. unbounded retry across N backends
        proxy_next_upstream_timeout 5s;    turns one slow request into N slow requests
    }

    location /healthz { access_log off; proxy_pass http://api; }
}

Load-balancing algorithms, measured

Round robin is the default nearly everywhere and it is the wrong default. Its assumption is that all backends are equally fast and all requests cost the same, and in production neither holds: one instance shares a host with a noisy neighbour, one has a cold cache after a restart, one is on older hardware, and request costs vary by an order of magnitude. Round robin cannot observe any of that, because it does not look.

Five algorithms, five backends, one of them slow
Compare round robin against least-connections at the p99

With one backend running four times slower than the others, round-robin's p99 is 12.5× that of least-connections. That is not a tuning difference, it is a different service. The mechanism is worth being precise about: round robin keeps delivering a fifth of all traffic to a node that can absorb a twentieth of it, so its queue grows without bound and every request unlucky enough to land there waits behind the whole backlog. Least-connections sees the in-flight count rising and simply stops choosing it.

Power of two choices is the one to know

True least-connections needs a single view of every backend's in-flight count, which is easy inside one nginx process and hard across a fleet of forty proxies — each sees only its own connections, and they collectively stampede whichever backend looks idle. Picking two backends at random and taking the less loaded one gets within a few per cent of least-connections in the simulation above with no shared state at all, because the second sample is enough to avoid the worst choice almost every time. It is the default in Envoy for good reason, and it is a genuinely surprising result: one extra sample removes nearly all of the penalty.

It matters even when the backends are identical

The intuition that "with homogeneous instances the algorithm does not matter" is wrong, and the simulation shows why. Even with every backend equally fast, service times vary — so a rotation that ignores load will sometimes hand a request to a node that is already working through three expensive ones. At 50% utilisation least-connections still beats round robin by 1.3× on p99; at 90% utilisation the gap widens to 2.6×, and the worst algorithm in the set (plain random, which clusters by chance as well as ignoring load) is 5.8× the best. The higher your utilisation, the more the choice costs you, which is exactly the wrong direction for a default.

Health checks, and the two kinds of "healthy"

A load balancer needs to know which backends to use, and there is a distinction that most outages in this area come from ignoring.

Liveness

"Is this process broken beyond recovery?" Failing it means restart me. Should test almost nothing — that the process can respond at all. A liveness check that queries the database will restart every instance when the database has a bad minute, turning a degradation into an outage.

Readiness

"Should this instance receive traffic right now?" Failing it means take me out of rotation, without restarting. This is where dependency checks belong, plus warm-up state and a deliberate fail during graceful shutdown.

Startup

"Has it finished booting?" A separate, more patient check that suppresses liveness until the application is up. Without it, a JVM that takes 90 seconds to start gets killed at 30 and restarts forever.

The two health-check failures that cause outages

A liveness probe with dependencies. If /healthz checks the database and the database is briefly slow, every instance fails liveness simultaneously and the platform restarts the entire fleet. You now have a cold cache, a thundering herd of reconnections, and a real outage caused by a transient blip. Liveness checks nothing but itself; readiness is where dependencies go — and even there, a shared dependency failing readiness everywhere at once removes all capacity, so prefer serving degraded to serving nothing.

Readiness not failing during shutdown. On SIGTERM the correct sequence is: fail readiness first, wait long enough for the load balancer to notice and stop sending traffic — typically two check intervals — then stop accepting and drain. Skip the wait and the balancer keeps routing to a socket that is closing, producing a burst of 502s on every single deploy. This is chapter 2's graceful shutdown contract seen from the other end, and it is why preStop: sleep 5 appears in so many Kubernetes manifests.

Beyond the probes themselves, two proxy behaviours matter. Passive checks — nginx's max_fails and fail_timeout, Envoy's outlier detection — eject a backend that is producing errors on real traffic, which catches failures an active probe misses because the probe hits a different code path. And slow start ramps a returning backend's share up gradually rather than immediately, so an instance with a cold cache is not handed a fifth of production traffic the instant it passes one check.

Ejection needs a floor, or it cascades

If a shared dependency makes every backend return errors, naive ejection removes every backend and the service goes from degraded to dead. Envoy's max_ejection_percent caps how much of the pool can be removed — 50% is a common setting — so that a systemic failure leaves you serving badly rather than not at all. Any ejection policy without such a cap has a failure mode where the health check itself is the outage, and it is worth checking whether yours has one.

Timeouts: the setting that decides your blast radius

Every worker, thread or connection slot in your service is held for the entire duration of whatever it is waiting on. Little's Law from chapter 1 applies directly and unforgivingly:

workers needed  =  arrival rate  ×  mean hold time

And the mean hold time is dominated by the slow tail rather than the common case, because the tail is where the seconds are. A service handling 200 requests a second at 20 ms needs 4 workers. Let one per cent of those requests hang until a 30-second timeout and the mean hold time becomes 320 ms — so it needs 64, which is the entire pool, consumed by one request in a hundred. Utilisation reaches 100%, and a queue at 100% utilisation has no headroom for variance at all: the average fits exactly and every burst waits.

One slow dependency against a worker pool
Set 1% hanging with a 30 s timeout, then drag the timeout down

Three conclusions come out of that model, and the third is the one that changes how you configure things.

The failure is not proportional to the fault
One per cent of requests misbehaving takes down one hundred per cent of the service. Every user sees an outage caused by traffic they have nothing to do with, which is why the incident is so confusing to diagnose from the outside: the error rate on the dependency is 1% and the error rate on your service is 100%.
Cutting the timeout fixes it with no new capacity
Dropping the same configuration from a 30-second timeout to 2 seconds takes the workers required from 64 to 8 on the identical load. The one per cent still fails — you cannot make a broken dependency work — but it now fails fast, which is the difference between one per cent of requests failing and all of them.
Adding workers works, and does not scale
Quadrupling the pool to 256 does absorb a 1% hang rate. But the hang rate is not a constant you control: at 5% the same 256 workers need 304 and saturate again, while a 2-second timeout survives 5% on the original 64 workers using only 24. The timeout scales with the failure rate; the pool does not. That is why the timeout is the lever.

Timeouts also have to be ordered. Each layer's timeout must be shorter than its caller's, or the caller gives up while the callee is still working — so you pay for the work, hold the resources and discard the result.

Retries turn a partial failure into a total one

If every layer retries twice, a request that fails at the bottom is attempted 2×2×2 = 8 times. During a partial outage — exactly when the dependency has least capacity — the offered load multiplies by eight and the thing that was recovering stops recovering. This is a metastable failure: it persists after the original trigger is gone, because the retries are now the load.

Three rules keep it bounded. Retry at one layer only, and usually the outermost one that knows whether the operation is idempotent. Use a retry budget — a cap such as "retries may not exceed 10% of requests" — rather than a per-request retry count, so that a widespread failure cannot amplify at all. And add jitter to the backoff: synchronised exponential backoff means every client retries at the same instant, converting a smooth recovery into a series of spikes.

Check yourself

Self-check

  1. One of five identical instances is on a host with a noisy neighbour and runs about four times slower. Your load balancer uses round robin and the p99 has become terrible while the mean looks acceptable. Explain the mechanism and the fix.
    Round robin sends one fifth of all traffic to a node that can absorb roughly one twentieth of it, so its queue grows without bound. The four healthy backends still serve most requests quickly, which keeps the mean respectable, but every request that lands on the slow node waits behind the entire backlog — so the damage concentrates in the tail. In the simulation this makes round-robin's p99 about 12.5 times that of least-connections. The fix is an algorithm that observes load: least-connections sees the in-flight count on that backend rising and stops choosing it, and power-of-two-choices gets within a few per cent of the same result without needing global state. Passive health checking helps too, by ejecting a backend that is timing out, but it is coarse — the point of least-connections is that it degrades the slow node's share smoothly rather than waiting for it to fail outright.
  2. Why is power-of-two-choices interesting, given that least-connections is strictly better informed?
    Because least-connections needs a single consistent view of every backend's in-flight count, and that is only available inside one proxy process. With a fleet of forty proxies each sees only its own connections; they all conclude the same backend is least loaded and stampede it, which can be worse than round robin. Power-of-two-choices samples two backends at random and takes the less loaded, requires no shared state at all, and in the simulation lands within a few per cent of true least-connections. The reason one extra sample does so much is that the failure mode you are trying to avoid is picking the worst backend, and the chance that both random samples are the worst is small. It is the default in Envoy and it is the right choice at fleet scale.
  3. Your /healthz endpoint queries the database. The database has a slow thirty seconds. Describe what happens.
    If that endpoint backs the liveness probe, every instance fails it at roughly the same moment, so the platform restarts the entire fleet at once. You now have a cold cache everywhere, a simultaneous reconnection storm against the database that was already struggling, and a real outage produced by a transient blip. If it backs the readiness probe, every instance is removed from rotation simultaneously and the load balancer has no healthy targets, so it either serves errors or — worse, in some configurations — falls back to sending traffic to everything anyway. The rule is that liveness checks nothing but the process's own ability to respond, readiness may check dependencies, and any ejection policy needs a floor such as Envoy's max_ejection_percent so that a systemic failure leaves you degraded rather than dead.
  4. A service handles 200 requests a second, each taking 20 ms, with a pool of 64 workers. It is completely healthy. A downstream dependency starts hanging on 1% of calls and the service becomes unavailable for everyone. What happened, and why is adding workers the weaker fix?
    Workers are held for the whole downstream wait, so by Little's Law the pool requirement is arrival rate times mean hold time. Healthy, that is 200 × 0.02 = 4 workers out of 64 — enormous headroom. With 1% of calls hanging until a 30-second timeout, the mean hold becomes 0.99×0.02 + 0.01×30 = 0.32 s, so the requirement becomes 200 × 0.32 = 64 workers: the entire pool, consumed by one request in a hundred. Everything else queues and the service fails for all users. Adding workers does help linearly — 256 workers absorbs a 1% hang rate — but the hang rate is not something you control, and at 5% those 256 workers need 304 and saturate again. Cutting the timeout to 2 seconds takes the requirement to 8 workers at 1% and 24 at 5%, on the original pool. The timeout scales with the failure rate; the pool does not.
  5. The client times out at 30 s, the load balancer at 60 s and the application's database call has no timeout at all. What specifically goes wrong?
    The ordering is inverted at every level. When a query is slow the client gives up at 30 s and typically retries, but the load balancer holds the original request for another 30 s and the application holds a worker and a database connection indefinitely — so the work continues, consuming resources, with nobody left to receive the result. The retry then arrives and starts a second copy of the same expensive query alongside the first, which is how a slow query becomes a saturated connection pool. Timeouts must decrease inward: client 30 s, balancer 25 s, proxy-to-app 10 s, app-to-database 3 s, and a server-side statement_timeout of 2 s as a backstop for clients that ignore their own setting. The inner deadline must always expire first, so that the layer doing the work is the one that decides to stop.
  6. Every layer in a four-layer path retries twice on failure. The bottom layer degrades to 50% success. What does the bottom layer see, and what is the correct design?
    Retries multiply rather than add: two attempts at each of three calling layers is up to 2×2×2 = 8 attempts per original request. Exactly when the dependency has least capacity, the offered load rises by up to eight times, which prevents the recovery that would otherwise happen and can keep the system down after the original trigger has cleared — a metastable failure, where the retries have become the load. The correct design retries at one layer only, normally the outermost one that knows whether the operation is safe to repeat; caps total retries with a budget such as "no more than 10% of requests may be retries", so a widespread failure cannot amplify at all; and uses exponential backoff with jitter, because synchronised backoff makes every client retry at the same instant and converts a smooth recovery into repeated spikes.
  7. Why does a reverse proxy in front of a thread-per-request application server matter more than one in front of an event-loop server?
    Because of slow clients. A thread-per-request server holds an entire thread — with its stack, and a slot in a small fixed pool — for as long as the client takes to send its request and receive its response. A client on a poor mobile link can take several seconds to upload a body, so a few hundred slow clients exhaust a pool sized for thousands of fast ones, and the server appears saturated while doing almost no work. A reverse proxy buffers the complete request before opening a fast local connection to the backend, so the expensive worker is occupied only for the actual processing time, and the cheap proxy connection absorbs the waiting. An event-loop server holds only a socket and a small amount of state per connection, so it tolerates slow clients natively and gains less from the buffering — though it still wants the proxy for TLS termination, routing, rate limiting and everything else in the first section.
