The shell and scripting

Every CI pipeline, container entrypoint, health check and deploy hook eventually bottoms out in a shell command. The shell is also the most quietly dangerous language most engineers use daily: it has no types, its default error handling is to keep going, and its most common bug — an unquoted variable — is invisible until the day the input contains a space. This chapter is about driving it deliberately.

Streams, redirection and exit codes

A Unix process starts with three file descriptors already open: 0 for standard input, 1 for standard output, 2 for standard error. That is the entire interface, and the discipline that makes the toolkit compose is that output is the data and standard error is the commentary. A program that prints its progress messages to stdout cannot be put in a pipeline; one that prints them to stderr can.

Every command returns an integer when it exits. Zero means success and anything else means a failure whose meaning is the command's own. This is inverted relative to most languages' truthiness and it catches people constantly: in the shell, 0 is true.

A container exiting 143 was asked politely to stop and complied — a normal rolling update. A container exiting 137 was killed outright: either it ignored SIGTERM through the whole grace period (chapter 2's PID 1 problem), or the cgroup OOM killer took it. Those two causes have completely different fixes and the exit code alone does not separate them; check the container's lastState.terminated.reason or the kernel log.

Strict mode, and why set -e alone is a trap

Almost every guide tells you to start scripts with set -euo pipefail. Far fewer explain what each flag does, and the gap matters because the flags interact in ways that decide whether your script stops on an error or deploys an empty artefact.

set -e — errexit
Exit immediately if a command returns non-zero. With large exceptions: it does not fire for a command in an if or while condition, for the left side of && or ||, for anything preceded by !, and — crucially — it judges a pipeline only by its final command.
set -u — nounset
Treat expansion of an unset variable as an error. This is the flag that prevents rm -rf "$PREFIX/" from becoming rm -rf /. Use ${VAR:-default} where empty is legitimate.
set -o pipefail
A pipeline's status becomes the rightmost non-zero status rather than the last command's. Without it, failing_command | tee log reports success, because tee succeeded.
set -x — xtrace
Print each command after expansion, before running it. The single best debugging tool in the shell. PS4='+ ${BASH_SOURCE}:${LINENO}: ' makes the output far more useful.

The demo below runs a small deploy script under whatever combination of flags you choose. It is worth spending a minute on, because the default combination — set -e without pipefail — produces a failure mode that looks exactly like success.

The two failures the demo is built around

A pipeline hides the failure of everything except its last stage. When curl exits 22 because the API returned 404, jq reads an empty stream and emits nothing, tee writes an empty file and exits 0 — so the pipeline's status is 0, set -e sees nothing wrong, and the script proceeds to deploy an empty version string. Adding pipefail turns that into an immediate abort. This is why the three flags are always quoted together.

An unset variable expands to nothing, silently. rm -rf "$RELEASE_DIR"/* with RELEASE_DIR unset is rm -rf /*. The quotes do not help — they prevent word splitting, not emptiness. set -u is the only thing standing between a typo in a variable name and that command. This has taken down real production systems more than once.

Where set -e quietly does not apply

Three cases are worth committing to memory because each looks protected and is not. Inside a function called in a condition — if my_func; then — errexit is disabled for the entire function body, not just the call. In local var=$(cmd) the exit status is that of local, which always succeeds, so a failing command substitution is invisible; declare and assign on separate lines. And in a command substitution used as an argument, echo "$(false)", the failure is discarded. If a script absolutely must not continue past an error, check explicitly with || exit 1 rather than relying on the flag.

Quoting, which is where most shell bugs live

After a variable is expanded, the shell performs word splitting on the result — using the characters in IFS, by default space, tab and newline — and then glob expansion on each resulting word. Both happen to the value, after substitution, and both are disabled by double quotes. That one sentence explains nearly every quoting bug.

bash — the same command, with and without quotes
file="my report.pdf"

rm $file                 ← becomes: rm my report.pdf     (TWO arguments — deletes neither,
                           or deletes a file called `my` if one exists)
rm "$file"               ← becomes: rm "my report.pdf"   (one argument) ✓

# and glob expansion, which quoting also suppresses
pattern="*.log"
ls $pattern              ← the shell expands * against the CWD before ls ever runs
ls "$pattern"            ← ls receives the literal string *.log ✓

# arrays: the difference between "$@" and "$*" is not stylistic
args=(--tag "v1.2" --note "first release")
cmd "${args[@]}"          ← 4 arguments, spaces preserved ✓
cmd "${args[*]}"          ← ONE argument: "--tag v1.2 --note first release"
cmd ${args[@]}           ← 5 arguments — "first" and "release" split apart

Run ShellCheck; it finds all of this automatically

ShellCheck is a static analyser for shell scripts and it catches unquoted expansions, useless cat, [ ] versus [[ ]] mistakes, set -e blind spots and about two hundred other patterns. It takes one line in CI and it is the single highest-return tool in this chapter. Anything in a repository that ends in .sh should be passing it before this discussion is worth having by hand.

The text-processing toolkit

The classic Unix argument is that a small set of single-purpose filters, composed with pipes, beats one large program. That is still true for the thing operators do most: turning a log file into an answer. Here is the standard set, and then a pipeline built out of it one stage at a time.

The sort | uniq -c | sort -rn idiom is worth internalising

"Count occurrences of each distinct value and show me the biggest" is the single most common question anyone asks a log file, and those three commands answer it for any data you can reduce to one item per line. Top talkers by IP, most frequent error message, busiest endpoint, most common user agent — all the same pipeline with a different field extracted. The one thing you must not omit is the first sort: uniq compares only adjacent lines, so on unsorted input it reports every run separately and the counts are silently wrong rather than obviously wrong.





bash — the same shape, applied to five different questions
# busiest endpoints
awk '{print $7}' access.log | sort | uniq -c | sort -rn | head

# top talkers, 5xx only — awk does the filtering AND the extraction
awk '$9 >= 500 {print $1}' access.log | sort | uniq -c | sort -rn | head

# status code distribution, as percentages
awk '{c[$9]++} END {for (k in c) printf "%-5s %6d %5.1f%%\n", k, c[k], 100*c[k]/NR}' access.log | sort -k2 -rn

# p95 response time, when field 11 is the duration
awk '{print $11}' access.log | sort -n | awk '{a[NR]=$1} END {print a[int(NR*0.95)]}'

# requests per minute, to find the spike
awk -F'[:[]' '{print $2":"$3":"$4}' access.log | sort | uniq -c

# the same shape over JSON logs
jq -r 'select(.status >= 500) | .path' app.jsonl | sort | uniq -c | sort -rn | head







Writing a script rather than a sequence of commands



The difference between a command history and a script is that a script has to survive being run by someone else, at an unexpected time, in a state you did not anticipate. Four constructs carry most of that weight.



bash — a script skeleton worth copying
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'                      ← removes space from the split set. Stops filenames
                                   with spaces exploding on any expansion you missed

readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly LOG_TAG="${0##*/}"

# required inputs fail loudly at the top, not halfway through
: "${TARGET_ENV:?must be set}"
readonly DRY_RUN="${DRY_RUN:-0}"

log() { printf '%s [%s] %s\n' "$(date -Is)" "$LOG_TAG" "$*" >&2; }
die() { log "FATAL: $*"; exit 1; }
run() {                          ← every mutating command goes through this.
  log "+ $*"                      DRY_RUN=1 then shows the whole plan without doing it
  [[ "$DRY_RUN" == 1 ]] || "$@"
}

# cleanup runs on ANY exit — success, failure, or Ctrl-C
readonly TMP="$(mktemp -d)"
cleanup() { rm -rf "$TMP"; }
trap cleanup EXIT
trap 'die "interrupted"' INT TERM

# refuse to run twice at once. flock is atomic; a lockfile check is not
exec 9>/var/lock/"$LOG_TAG".lock
flock -n 9 || die "another run is in progress"

main() {
  local -a targets=()
  while IFS= read -r line; do targets+=("$line"); done < "$1"
                                 ← the only correct way to read a file line by line.
                                   `for l in $(cat f)` splits on spaces and globs
  (( ${#targets[@]} )) || die "no targets"
  for t in "${targets[@]}"; do run deploy --host "$t"; done
}

main "$@"





trap … EXIT is the only reliable cleanup
It fires on normal exit, on set -e aborting, and on an explicit exit anywhere in the script. Trapping only INT TERM leaves temp directories behind whenever the script simply fails, which is most of the time.


flock rather than a lockfile
Checking whether a file exists and then creating it is two operations with a race between them, so two cron runs that start together both proceed. flock is a single kernel operation and the lock is released automatically when the process dies — including if it is killed, which a manually removed lockfile is not.


while read rather than for … in $(cat)
for over a command substitution splits on whitespace and then globs each piece, so a line containing a space becomes two items and a line containing * becomes a directory listing. while IFS= read -r preserves the line exactly; -r stops backslashes being interpreted and IFS= stops leading whitespace being trimmed.


A run() wrapper buys dry-run for free
Routing every mutating command through one function means DRY_RUN=1 prints the complete plan without executing any of it. For anything that touches production this is the difference between a review and a hope, and it costs four lines.





Idempotency is a requirement, not a nicety

Any script that a pipeline, a cron or a human might re-run must produce the same end state when run twice. That means mkdir -p rather than mkdir, ln -sfn rather than ln -s, useradd … || true guarded by an existence check, appending to a config file only after grepping for the line, and rm -f rather than rm. The test is simple and worth actually performing: run it twice in a row and diff the results. Chapter 15 makes this the central idea of configuration management, and chapter 19 builds an entire delivery model on it.









When to stop writing bash



Bash is unbeatable for gluing programs together and genuinely bad at everything else. The switching point is not a matter of taste, and there are reasonably objective signals.







Stay in bash


The script is mostly invoking other programs and wiring their streams together. It is under roughly 100 lines with no nested data. It must run somewhere with nothing else installed — a container entrypoint, a minimal image, a bootstrap on a fresh host. Or it is a thin wrapper around a CLI that already does the work.






Switch to Python or Go


You need a data structure more complicated than a flat list of strings. You are parsing JSON, YAML or XML beyond one jq expression. You need real error handling, retries with backoff, or partial-failure semantics. You want tests — bash can be tested and almost nobody does. It calls HTTP APIs and reacts to the responses. Or you are reaching for eval.







Go where the operator has to install nothing

The reason bash survives in operations is not that it is good — it is that it is already there. Any replacement inherits that requirement. Python is present on most Linux distributions but its dependencies are not, which is why operational Python should stick to the standard library or ship as a container. Go compiles to a single static binary with no runtime, which is exactly why so much of the tooling in the rest of this unit — Docker, Kubernetes, Terraform, Prometheus — is written in it.









Check yourself





Self-check


    

  1. A CI job runs set -e and then curl -sf "$URL" | jq -r .version > version.txt. The API returns 404 and the job passes. Explain, and give the one-word fix.

    A pipeline's exit status is the status of its last command. curl -sf exits 22 on a 404, but jq reads an empty stream and exits 0, so the pipeline reports 0 and set -e has nothing to act on. The job passes with an empty version.txt, and whatever consumes that file downstream now has a bug that is a long way from its cause. The fix is set -o pipefail, which makes the pipeline report the rightmost non-zero status. Belt and braces: jq -e exits non-zero when the result is null or false, so it fails on its own even without pipefail.
    2. 


  2. Why does rm -rf "$BUILD_DIR"/* not protect you when BUILD_DIR is unset, given that it is quoted?

    Quoting prevents word splitting and glob expansion of the value. It does not prevent the value from being empty. An unset variable expands to the empty string, so the argument becomes /* and the command is rm -rf /*. The only thing that stops it is set -u, which makes expanding an unset variable a fatal error, or an explicit guard such as : "${BUILD_DIR:?}" at the top of the script. Both are one line, and the difference between having them and not having them is the difference between a typo and an outage.
    3. 


  3. if grep -q ERROR log; then … is inside a script with set -e. Why does the script not exit when the pattern is absent?

    Because errexit is deliberately suppressed for commands in a condition context: an if or while test, the left operand of && or ||, and anything negated with !. If it were not, you could never test for a condition that might be false. grep exits 1 for "no match", which is a legitimate answer rather than an error, so this is the behaviour you want. The trap is the reverse case: count=$(grep -c ERROR log) outside a condition will abort the script when there are no matches, which is almost never what the author intended. Guard it with || true, or use grep -c ERROR log || echo 0.
    4. 


  4. Your pipeline is awk '{print $7}' access.log | uniq -c | sort -rn | head and the counts look implausibly fragmented. What is wrong?

    There is no sort before uniq. uniq only collapses adjacent identical lines, so on log data — where the same endpoint appears repeatedly but not consecutively — each run of identical neighbours is counted separately and one endpoint appears many times with small counts. The output is wrong rather than empty, which is what makes it dangerous: nothing errors and the numbers look like data. Insert | sort | before uniq -c. The demo above lets you toggle exactly this and shows the group count going from 8 to 12 on 12 records.
    5. 


  5. What is the difference between "${args[@]}" and "${args[*]}", and when does it break something?

    "${args[@]}" expands to one quoted word per element, preserving spaces inside each. "${args[*]}" joins every element with the first character of IFS and produces a single word. So passing "${args[*]}" to a command hands it one long argument instead of several, and the command usually reports an unrecognised option containing the entire list. Unquoted ${args[@]} is a third case: it splits on whitespace inside elements too, so an element like "first release" becomes two arguments. Use "${args[@]}" essentially always; "${args[*]}" only when you genuinely want a joined string, such as for logging.
    6. 


  6. A cron job occasionally runs twice concurrently and corrupts its output. The script already checks for a lockfile and exits if it exists. Why is that not enough?

    Because "check whether the file exists" and "create the file" are two separate operations, and two processes can both pass the check before either performs the creation. It is a classic time-of-check-to-time-of-use race, and it fires precisely when two runs start simultaneously — which is the case the lock exists for. There is a second problem: if the script is killed, the lockfile survives and every later run refuses to start. flock solves both. Acquiring the lock is a single atomic kernel operation with no window, and the kernel releases it when the file descriptor closes, including on an unexpected death.
    7. 


  7. Your container exits with code 137. What does that mean, and what are the two possible causes?

    128 + 9, so the process was terminated by SIGKILL. Two causes produce it, with different fixes. Either the cgroup OOM killer fired because the container exceeded its memory limit — check lastState.terminated.reason for OOMKilled, and the fix is to raise the limit or reduce usage — or the runtime sent SIGTERM, the process ignored it for the whole grace period, and the runtime escalated to SIGKILL. That second case means the process has no signal handler or is running behind a shell that does not forward signals, and the fix is in chapter 2. The exit code alone does not distinguish them, which is why the termination reason and the timing relative to the grace period both matter: an instant 137 is usually OOM, a 137 exactly at the grace period is usually a missing handler.
