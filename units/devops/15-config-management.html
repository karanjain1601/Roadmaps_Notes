Chapter 15 · Infrastructure

Configuration management

Chapter 14 created the machine. Something has to decide what is on it. For twenty years that meant a convergence tool repeatedly pushing a server back toward a described state — and the honest assessment now is that the whole category is being replaced by not modifying servers at all. Both halves are worth understanding, because the reasoning transfers and because plenty of estates still run on the first one.

Convergence, and the property it depends on

A configuration management tool describes a desired end state — this package installed, this file with these contents, this service running — and each run moves the machine toward it. Running twice must be indistinguishable from running once, because the tool has no idea what state it is starting from. That is chapter 3's idempotency requirement, promoted from a scripting nicety to the property the entire model rests on.

Given idempotent operations, a scheduled run repairs whatever has changed since the last one. That is the promise. Its quality depends entirely on two numbers: how often the run happens and how often it succeeds.

drifted at steady state  =  d ÷ ( 1 − (1−p)(1−d) )   where  d = 1 − e−λT

λ is how often a host drifts, T the convergence interval and p the probability a run succeeds. Drift accumulates continuously and is repaired discretely, so the fleet settles at a balance between the two — and because a failed run leaves the host drifted for another whole interval, p matters roughly as much as T.

Drift against a convergence schedule
Move the interval from daily to monthly and watch the fleet dissolve
The interval is the whole game
Daily convergence leaves 5.1% of hosts drifted at any moment. Monthly leaves 79%. The tool is identical, the playbooks are identical, and one fleet is describable and the other is two hundred individual machines.
A change takes several intervals to land everywhere
At 95% run success, reaching 99.9% of the fleet takes three runs — three days when you converge daily, 90 days when you converge monthly. The tail is set by the failure rate, not the interval, so a flaky run at 80% needs five.
Every run leaves some hosts half-applied
At 95% success across 200 hosts, about ten end each run partway through: some tasks applied, some not. That is a state neither the old nor the new configuration describes, nobody has tested, and no amount of re-running is guaranteed to reach — the next run may fail at the same task.
The half-applied host is the failure mode that has no equivalent

Everything else in this section is a tuning problem: converge more often, make runs more reliable. Partial application is different in kind. A convergence run is a sequence of operations against a live machine, and it can stop anywhere in that sequence — leaving a host with the new package and the old config file, or the new config and a service that never restarted. There is no transaction and no rollback. Replacing the machine from a tested image has no such state: the new instance either boots and passes its health check or it does not, and the old one is still there until it does. That asymmetry, more than speed or elegance, is the substantive argument in the last section of this chapter.

Push, pull, and the four tools

Where it fits nowAd-hoc operations, image building, network devices, small fleetsLarge long-lived estates that predate containersSimilar

The push/pull distinction maps directly onto the model above. A pull agent converges on its own timer, so T is small and constant and new hosts join automatically — which is why Puppet estates stay coherent. A push tool only converges when someone runs it, so T is however often that happens, which in practice is "when a change is needed" and produces the monthly column of the demo. Ansible's convenience — no agent, no server, works over SSH — is bought precisely by giving up the property that keeps the fleet converged.

Check mode is the plan step, and almost nobody uses it

ansible-playbook --check --diff reports what would change without changing it, which is the same review artefact as terraform plan from chapter 14 — and for the same reason it belongs in a pull request rather than in someone's terminal. It is imperfect: tasks using command or shell are skipped in check mode unless they declare check_mode: false, so the more escape hatches a playbook uses the less the check tells you. That is itself a useful signal about the quality of the playbook. Pair it with --diff so file changes are shown as an actual diff, and with a linter — ansible-lint — which catches the unguarded command, the missing state and the latest version pin automatically.

The argument for not modifying servers at all

Immutable infrastructure inverts the model. Instead of converging a running machine toward a description, you build a complete machine image containing everything, test it once, and replace running instances with new ones built from it. Nothing is ever modified in place; there is no drift because there is nothing to drift from.

What changes

Configuration becomes a build-time concern rather than a runtime one. The artefact is tested as a whole, once, rather than as a sequence of operations against N different starting states. Rollback is redeploying the previous image, which is a known-good thing rather than a reverse convergence nobody has rehearsed. And chapter 9's container image is exactly this idea, so most teams have already adopted it without calling it that.

What it costs

A build pipeline for images, and a few minutes of build time on every change however small. Anything genuinely stateful needs its data on a volume that survives replacement. Debugging means reproducing on a fresh instance rather than poking at the broken one. And you need a replacement mechanism — an autoscaling group, a Deployment — that can roll instances safely, which is chapter 18.

The clearest way to see the difference is at the moment it matters most: when the autoscaler needs capacity now.

Scale-up: bake it in, or install it on boot
Push the package count to 60 and look at the failed-boot count
It is faster, and that is the smaller point
190 seconds to install twenty-four packages against 30 seconds to pull a baked image — a 6.4× difference, which is three minutes of missing capacity on every node during a scale-up, exactly when chapter 11's autoscaler is trying to help.
It is also more reliable, which is not a trade
Twenty-four install steps at 0.4% failure each succeed only 90.8% of the time; sixty steps succeed 78.6%. Scaling out forty nodes therefore expects around four failed boots per event. The baked image has one step.
Every install step is a live dependency on somebody else
Installing at boot means your ability to add capacity depends on apt, npm, PyPI or Docker Hub being reachable and healthy at the exact moment you need them. That dependency is invisible in normal operation and shows up during an incident, when a package registry outage becomes your outage.
The failure moves to build time, where it is cheap
A package that fails to install fails the image build, in CI, with nobody waiting. That is the same shift as chapter 10's multi-stage build and chapter 14's plan step: find out at build time rather than at the worst possible time.
Where configuration management genuinely survives

Three places, and they are not small. Building the images themselves — Packer runs an Ansible provisioner to produce the AMI, so the playbooks live on and simply execute at build time rather than at boot, which is the best of both. Anything that cannot be replaced: network appliances, on-premise hardware, database servers with local state, developer laptops. And ad-hoc operations — running one command across three hundred hosts during an incident is what Ansible is genuinely excellent at, and no immutable model replaces it. What has gone is the specific use of a convergence tool as the continuous authority over a long-lived server's configuration, and that is because chapter 9's container image already made every workload immutable by default.

Check yourself

Self-check

  1. Your team runs Ansible manually, roughly monthly. Hosts are described as "mostly consistent". Quantify what that actually means.
    With hosts drifting about every twenty days and a 95% run success rate, a thirty-day convergence interval leaves roughly 79% of the fleet drifted at any moment — because drift accumulates continuously and is only repaired every thirty days, and a failed run pushes a host into another whole interval. Daily convergence with identical playbooks leaves about 5%. So "mostly consistent" is closer to "four hosts in five differ from the description in some way", which means the playbooks describe an aspiration rather than the fleet. It also means a change takes three runs to reach 99.9% of hosts — ninety days at monthly cadence — so at any moment several different configurations are live simultaneously. The fix is either much more frequent convergence, which usually means moving from push to a pull agent that runs on its own timer, or removing the problem by replacing hosts from images instead.
  2. Why is a failed convergence run worse than no run at all?
    Because it leaves the host partially applied: some tasks executed and some not, so it holds a state that neither the old nor the new configuration describes and that nobody has tested. A host that was never converged is at least a known previous state. In the demo, a 95% success rate across 200 hosts leaves about ten hosts in this condition after every run, and re-running is not guaranteed to fix them since the next run may fail at the same task. There is no transaction and no rollback in a convergence model — the tool is executing a sequence of operations against a live machine and can stop anywhere in it. This failure mode has no equivalent in image replacement, where the new instance either boots and passes its health check or it does not, and the old one keeps serving until it does. That asymmetry is the strongest argument for immutability, ahead of speed or elegance.
  3. What makes Ansible's agentless design attractive, and what does it cost in terms of the model in this chapter?
    Attractive because there is nothing to install and nothing to run: SSH and Python on the target are the whole requirement, so you can adopt it in an afternoon and use it on machines you do not fully control, including network devices. The cost is that convergence only happens when a human or a pipeline invokes it, so the interval T in the drift model is however often that occurs — in practice "when a change is needed", which is the monthly column. A pull-based agent converges on its own timer, so T is small and constant and, importantly, a newly built host converges without anyone remembering to include it. Ansible also scales poorly over SSH past a few hundred hosts, which pushes the interval up further at exactly the fleet size where drift is most expensive. The convenience and the drift are the same property viewed from two sides.
  4. Someone adds - name: apply schema command: /opt/app/migrate.sh to a playbook. What is wrong?
    It is not idempotent, so it runs on every convergence. Depending on what the script does that is either wasted time on every run, or repeated schema changes, or a failure that marks the whole playbook as failed and stops subsequent tasks — which produces exactly the half-applied host from earlier. Ansible cannot know whether the work is already done because command is an opaque escape hatch. Fix it with args: creates: /var/lib/app/.migrated so the task is skipped when the marker exists, or with changed_when and failed_when conditions derived from the script's output, or best of all by making the script itself idempotent and cheap to re-run. It is also worth noting that command and shell tasks are skipped in --check mode by default, so every one of them reduces how much the plan step tells you — the number of unguarded shell tasks in a playbook is a reasonable proxy for how much you can trust its dry run.
  5. Your autoscaling group installs packages on boot. Nodes take three minutes to become ready and occasionally fail. What is the argument for baking an image, beyond speed?
    Three arguments, and speed is the weakest. First, reliability: twenty-four install steps at 0.4% failure each succeed only 90.8% of the time, so a forty-node scale-up expects about four nodes that never come up — and it gets worse superlinearly with more steps. A baked image has one step. Second, dependency: installing at boot means your ability to add capacity depends on apt, npm or a container registry being reachable and healthy at the exact moment you need capacity, which is an invisible dependency that surfaces during an incident. Third, testing: the image is built and tested once as a whole, whereas on-boot configuration is executed fresh on every node and can behave differently as upstream packages move. The speed argument still matters — three minutes of missing capacity per node during a scale-up is real, and chapter 11 showed the autoscaler is already reactive — but the reliability and dependency arguments are the ones that turn a slow scale-up into a failed one.
  6. If immutable infrastructure removes the need for configuration management, why do teams still write Ansible?
    Because the playbooks moved rather than disappeared. Packer runs an Ansible provisioner to build the image, so the same roles execute at build time — in CI, once, with nobody waiting — instead of at boot on every node. That keeps the declarative descriptions and the ecosystem of modules while removing the drift and partial-application problems entirely, which is genuinely the best of both. Beyond image building, two categories remain: things that cannot be replaced, such as network appliances, on-premise hardware and stateful database servers, and ad-hoc operations, where running one command across three hundred hosts during an incident is something Ansible does very well and no immutable model addresses. What has ended is the specific use of a convergence tool as the continuous authority over a long-lived server's configuration — and largely because chapter 9's container image made every containerised workload immutable by default, without anyone framing it as an infrastructure decision.
  7. A colleague argues that immutable infrastructure is impossible for their team because their application writes files it needs later. Respond.
    The requirement is not that nothing writes anything; it is that nothing the instance writes to its own root filesystem is needed after the instance is gone. Separate the two kinds of writes. Genuinely durable data — uploads, database files, anything a user would notice losing — belongs on a volume, an object store or a managed database that outlives the instance, which chapter 9 made the same argument for with container filesystems and copy-up. Ephemeral writes — caches, temp files, logs — are fine on the instance, provided logs are shipped somewhere rather than read from disk during an incident. What usually turns out to be the real blocker is not data but state that accumulated by accident: a config file edited by hand two years ago, a certificate installed manually, a cron entry nobody remembers. Those are drift, and the fact that replacing the instance would lose them is the problem rather than the objection.
