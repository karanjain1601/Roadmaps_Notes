Glossary

Blast radius
How much breaks when one thing does. The quantity that partitioning — accounts, credentials, cells, canaries — is bought to reduce.
Burn rate
Current error rate divided by the error budget's allowance. A 10× burn consumes a month's budget in three days.
Cardinality
The number of distinct values a label can take. Series count is the product of them, so this is the cost model for metrics.
Cold start
Creating a new execution environment before a request can be served. A low-traffic, spike and deploy problem rather than a throughput one.
Content addressing
Naming a thing by the hash of its bytes, so the name cannot refer to different content later. Git objects, image digests.
Convergence
Repeatedly moving a system toward a described state. Requires idempotent operations and produces partially-applied hosts when a run fails.
Drift
Divergence between the declared state and reality. Detected by refresh, a nightly plan, or a continuous reconciler.
Envelope encryption
Encrypting data with a per-object key, and that key with a key that never leaves a hardware module. Makes every decryption an auditable API call.
Error budget
One minus the objective, as a quantity of failure you may spend. 99.9% over 30 days is 43.2 minutes.
ForceNew
An attribute that cannot be changed in place, so altering it destroys and recreates the resource — and everything referencing it.
Idempotent
Running it twice is indistinguishable from running it once. The property every retry, reconciler and at-least-once event source depends on.
Level-triggered
Reacting to a condition rather than an event. Why a controller self-heals after a missed message or a restart.
Metastable failure
A failure sustained by its own consequences, usually retries, so it persists after the original trigger clears. Fixed by shedding load, not adding capacity.
Provenance
A signed statement of which source, builder and parameters produced an artefact. The only control that detects a compromised build.
Reconciliation loop
Observe actual, diff against desired, act, repeat. The shape of every orchestrator, IaC tool and GitOps controller.
SLI / SLO / SLA
A measurement, a target on it, and a contract with consequences. Only the first two are engineering objects.
Throttling
Being descheduled on reaching a CPU quota. Happens far below the average limit because quotas are enforced per 100 ms period.
Whiteout
The overlay filesystem entry that hides a file from a lower layer. Why deleting in a later layer saves no space.

Things worth building

  1. Ship one service end to end, alone. A small HTTP service with a database, containerised, provisioned with Terraform, deployed by a pipeline you wrote, behind a proxy with TLS from ACME, with RED metrics and an SLO. Nothing exotic — the value is that every chapter's abstraction becomes a file you had to write. Budget a weekend and expect three.
  2. Break it deliberately. Kill a pod mid-request and measure the 502s (chapter 12). Set a CPU limit and watch the p99 at 40% utilisation (chapter 9). Fill the disk. Expire the certificate. Each of these is a chapter's number, reproduced on your own machine, and reproducing one is worth more than rereading three.
  3. Make the pipeline fast, then measure why it is not. Time each stage, reorder by duration ÷ failure rate, add a layer cache, and record the before and after (chapters 10 and 17). This is the single most transferable skill here and almost nobody has actually done the measurement.
  4. Do a real expand-contract migration. Rename a column across six deploys without downtime, then try the one-step version and watch it break during the rollout (chapter 18). The five reversible steps only make sense once you have seen the sixth.
  5. Instrument something you did not write. Add OpenTelemetry to an open-source service, get traces across two hops, and find a slow one. Chapter 22's ordering — metrics, then traces, then logs — is a habit rather than a fact, and it only forms with practice.
  6. Run a game day. Pick a failure, write the hypothesis, tell everyone the date, and find out how much of your runbook is fiction (chapter 23). The organisational findings will outnumber the technical ones.

The argument, in one page

What all of this was for

Chapter 1 derived it and every chapter since paid it off. Batching changes does not make you safer — it makes each failure larger and slower to isolate, because the number of defects you write does not depend on how you package them. The safe deploy frequency is a property of your release mechanism rather than your industry, so the productive work is making that mechanism cheap and reliable: automated tests that mean something, an artefact built once and promoted, a rollout that limits exposure, a reconciler that removes the human, and instrumentation that tells you within a minute rather than an hour.

Chapter 13 closed the loop from the other end. Infrastructure redundancy reaches about four nines and then stops helping, because past that the binding constraint is your own change process — and chapter 23 priced it: making each nine cheaper raises the availability worth buying. So the whole unit is one argument in different vocabularies. Small changes, shipped often, through a mechanism you trust, with the ability to see what happened and undo it. Everything else is which tool implements it.
