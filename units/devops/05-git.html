Chapter 05 · Source and servers

Version control as infrastructure

Git is not a tool you use alongside your delivery system — it is the substrate the whole thing is built on. The commit is the unit of change that chapter 1 was counting, the branch is the batch, and from chapter 19 onward the repository stops describing the software and starts being the desired state of production. That makes the object model and the branching strategy operational decisions rather than developer preferences.

Four object types, and everything else is a consequence

Git stores exactly four kinds of object, each identified by the hash of its own contents. That single design choice — content addressing — explains deduplication, why branches are free, why history cannot be quietly altered, and why the recovery story is so much better than it appears when you have just destroyed something.

blob
The contents of one file. No name, no permissions, no history — just bytes. Two files with identical contents anywhere in the repository, at any point in history, are the same blob stored once.
tree
A directory: a sorted list of names, each paired with a mode and the id of a blob or another tree. The tree is what gives a blob its filename.
commit
One tree id (the complete snapshot, not a diff), zero or more parent commit ids, author, committer, timestamp and message. A merge commit is simply one with two parents.
tag
An annotated tag object pointing at a commit, with its own message and optional signature. A lightweight tag is not an object at all — just a ref.
A ref is not an object
refs/heads/main is a file containing a commit id. That is the entire implementation of a branch: 41 bytes. Creating one is instant and costs nothing, which is why the argument against feature branches is never about the branch and always about how long it lives.
Git does not store diffs

Every commit references a complete tree of the whole project. Diffs are computed on demand, which is why git log -p is slower than git log and why git checkout of a hundred-commit-old revision is instant. The reason this does not explode on disk is deduplication: an unchanged file across a thousand commits is one blob referenced a thousand times, and packfiles later apply delta compression across objects regardless of which commit they belong to. Almost nothing is ever really lost

A destroyed branch, a bad reset --hard, a rebase that went wrong, an amended commit you needed — in every case the original objects are still in .git, merely unreachable from any ref. git reflog records where HEAD and each branch pointed after every operation, typically for 90 days, and git reset --hard HEAD@{3} puts it back. The genuinely unrecoverable cases are narrow and worth knowing precisely: work that was never committed at all, and objects removed by git gc --prune after they aged out of the reflog. Everything else is a lookup, and the first thing to do after any accident is git reflog — before anything else, because further commands can push the entry you need out of the window.

Branching strategies, priced rather than argued

The branching debate is usually conducted as a matter of taste. It is not: a branching strategy sets a hard ceiling on the deploy cadence from chapter 1, and its cost is calculable. A branch that lives for L days accumulates two things simultaneously — your changes, and everyone else's changes to the same trunk — and the chance they collide grows with the product of the two.

daily integration cost  =  (devs / L)  ×  ( fixed merge cost  +  conflict cost × conflicts(L) )

Merges happen once per branch per developer, so their number falls as 1/L — that term punishes very short branches, because each merge carries a fixed cost in CI runs, review round trips and ceremony. Conflicts grow roughly as L², because both the size of your branch and the amount of trunk drift you must reconcile against are each proportional to L. A term falling as 1/L plus a term rising as L is convex, so there is a minimum — and it is the same shape as the deploy-cadence curve in chapter 1, for the same underlying reason.

How long should a branch live?
Drop the merge cost to 0.1 h and watch the optimum move left

With a team of eight, six files each per day and a moderately automated merge, the model puts the optimum at about 1.5 days — and the shape around it matters more than the exact number. A one-day branch costs 9.2% of the team's capacity in integration and a two-day branch 8.8%, so anything in that region is fine. A ten-day branch costs 20.1% and a twenty-day branch 26.6%: at that point a quarter of the team exists to reconcile the other three quarters.

Feature flags are what make short branches possible

The obvious objection to trunk-based development is that some features take three weeks to build and cannot be released half-finished. The answer is to separate merging from releasing: merge the incomplete work behind a flag that is off, so the code is integrated continuously while the behaviour stays hidden. That keeps L small while the feature takes as long as it takes. It is not free — flags are conditional branches that need testing on both sides, and a flag left in the code for two years is technical debt with a name — so the discipline is a removal deadline written down at the moment the flag is created. Chapter 18 covers the operational side.

Merge, rebase and the shape of history

Both integrate one line of work into another; they differ in what they leave behind, and the choice has practical rather than aesthetic consequences.

Merge

Creates a commit with two parents. Preserves exactly what happened, including the fact that two lines of work existed concurrently. Never rewrites anything, so it is always safe on a shared branch. Produces a graph that is honest and can be hard to read.

Rebase

Replays your commits on top of the new base, creating new commits with new ids. Produces a linear history where every commit's parent is the state it was actually tested against. Rewrites history, so it must never be done to commits others have pulled.

Squash merge

Collapses the branch into a single commit on the target. Trunk gets one commit per unit of work, which makes git bisect and revert trivial. The intermediate commits are discarded, so the branch's development detail is lost — usually a fair trade.

Two operational consequences are worth stating plainly, because they are what makes this a delivery concern rather than a style guide.

A linear trunk makes git bisect work properly
Bisect finds the commit that introduced a defect in log₂(n) steps — twelve builds to search four thousand commits. It needs each commit to be individually buildable and testable, which a merge-heavy trunk full of half-integrated states is not. This is the same isolation cost that appears as the log₂ term in chapter 1's recovery model, and it is why "one commit per change on trunk" pays off during an incident rather than during development.
Revert is your fastest rollback, and it needs the same property
git revert <sha> produces a new commit undoing exactly one change, which can then flow through the normal pipeline. It works cleanly when trunk has one commit per unit of work and becomes an archaeology exercise when it does not. Chapter 18 treats reverting forward as a first-class deployment strategy rather than an emergency measure.
The golden rule, and the one legitimate exception

Never rewrite history that someone else has based work on. A rebase or amend of published commits gives everyone else a divergent copy, and the usual recovery — a merge — reintroduces the original commits alongside the rewritten ones, doubling the history and producing conflicts in code nobody changed.

The exception is your own unmerged branch, where rebasing onto the latest trunk before opening a pull request is exactly right: it resolves conflicts on your time rather than the reviewer's, and it means CI tested the code against the base it will actually land on. If you must force-push a shared branch, use --force-with-lease, which refuses when the remote has moved since you last fetched. Plain --force silently discards a colleague's commits.

On the protection side, four settings do most of the work: require a pull request before merging, require named status checks to pass, require the branch to be up to date with its base before merging, and forbid force-pushes and deletions. The third is the one people skip, and it is the one that prevents two branches that each pass CI independently from breaking trunk when combined — a semantic conflict that no textual merge can detect.

CODEOWNERS is the cheapest review routing there is

A CODEOWNERS file maps path patterns to teams and automatically requests review from the right people. It removes the "who should look at this?" delay, which in the chapter 1 flow model is pure queue time at the review stage. It is also how you make a monorepo navigable: /infra/ @platform, /services/payments/ @payments, *.tf @platform @security. Combined with required review from code owners, it turns an informal norm into something that cannot be forgotten at 6pm on a Friday.

Monorepo or many

This is a genuine trade-off rather than a solved question, and the deciding factor is usually not scale but how often changes need to cross a boundary.

The failure modes are mirror images

A monorepo fails by making CI slow enough that people stop trusting it — the fix is affected-target detection so a change to one service does not rebuild forty. Many repos fail by making cross-cutting change so expensive that it stops happening: a security patch to a shared library sits unapplied in eleven services for six months, and nobody can say which of them are affected. The monorepo problem is a tooling problem with known solutions. The polyrepo problem is an organisational one, and it is considerably harder to fix once it has set in.

A secret in history is a secret that is gone

This deserves its own section because the instinct is wrong. Deleting a file and committing the deletion removes it from the working tree and leaves the blob permanently in history, reachable from every earlier commit, present in every clone, and served happily by the forge's API to anyone who asks for that revision.

  1. Rotate the credential first. Before touching the repository at all. Assume it is compromised the moment it was pushed, because scanning bots find public keys within seconds and internal repositories are not much slower. Everything after this step is cleanup, not remediation — and if you do it in the other order, you spend an hour rewriting history while the live key is still valid.
  2. Then remove it from history with git filter-repo (or BFG). filter-branch is deprecated and hundreds of times slower.
  3. Force-push every branch and tag, and tell everyone to re-clone. Rewriting history changes every commit id from the touched commit forward, so anyone who pulls and merges reintroduces the old objects.
  4. Ask the forge to garbage-collect. GitHub and GitLab keep unreachable objects accessible by SHA on their servers even after your force-push; you have to open a support request to have them purged. Until then the secret is still fetchable by anyone who noted the commit id.
  5. Add the scanner so it cannot happen again — gitleaks or trufflehog, as a pre-commit hook for speed and as a required CI check for enforcement.
The real fix is that the secret should never have been committable

Every step above is expensive and none is fully reliable. The structural answer is that application configuration comes from the environment or a secret store at runtime, so there is nothing sensitive in the repository to leak — .env in .gitignore, a committed .env.example with the key names and no values, and real values injected by the platform. Chapter 21 covers the secret store; chapter 19 covers the awkward case that GitOps creates, where the desired state genuinely does live in git and therefore needs encryption at rest inside the repository.

Check yourself

Self-check

  1. A colleague argues that feature branches are fine because "branches are free in git". What is right about that and what is wrong?
    Right: creating a branch really is free — a ref is a 41-byte file containing a commit id, and no objects are copied. The cost is nothing at creation. Wrong: the cost is in the branch's lifetime, not its existence. While it lives, your changes accumulate and so does trunk drift, and the chance of collision grows with the product of the two, so conflict cost rises roughly as the square of the lifetime. The model in this chapter shows a ten-day branch consuming about 20% of a team's capacity in integration against about 9% for a one-day branch. The correct conclusion is that branching is free and not merging is expensive, which is an argument for many short branches rather than for no branches.
  2. You run git commit --amend on a commit you had already pushed, then force-push. What happened to the original commit, and what happens to a colleague who had pulled it?
    Amend does not modify anything: commit objects are immutable and identified by the hash of their content, so changing the message or the tree necessarily produces a different id. A new commit was written and the branch ref moved to it, leaving the original object present in the repository but unreachable — still recoverable from your reflog until it is pruned. A colleague who had already pulled the original now has a branch whose tip is a commit that no longer exists upstream. If they pull, git merges the two lines, and both the original and the amended commit appear in history with the same changes, producing duplicate work and conflicts in code neither of them touched. This is why history rewriting is confined to unpublished branches, and why --force-with-lease — which refuses when the remote has moved since your last fetch — is the safer force.
  3. Your team ships one release a month from a develop branch that merges to main at release time. Deployment frequency is the metric management wants improved. What is actually constraining it?
    The branching model, and no amount of pipeline automation will move it. If work is integrated into develop and only reaches main at release time, the batch size is one month of changes by definition, and chapter 1's model says the incident recovery cost scales with the log of that batch while lead time is roughly half the release interval — several weeks. You can make the deploy itself take ninety seconds and change nothing. The constraint moves only when trunk becomes releasable continuously, which means merging small changes directly into it, hiding incomplete work behind feature flags rather than behind a branch, and treating main as deployable at every commit. The pipeline work matters afterwards, because chapter 1 also shows that release-mechanism reliability is what sets the safe cadence once batch size is no longer the limit.
  4. Two pull requests each pass CI independently. Merged together, trunk breaks. Which protection setting would have caught it, and why do the others not?
    "Require branches to be up to date before merging." Each PR was tested against the base as it was when the branch was created, so neither run ever saw the other's changes — the conflict is semantic rather than textual, which is exactly the class no merge algorithm can detect: one PR renames a function, the other adds a caller of the old name, and the files may not even overlap. Requiring the branch to be current forces a rebase or merge of the latest base and a re-run of CI against the combination, so the second PR is tested against a trunk that already contains the first. Required reviews do not help because a human reading one diff cannot see the other. Required status checks do not help because they already passed — against the wrong base. The cost is a re-run per merge, which is precisely the fixed merge cost in this chapter's model, and it is why making CI fast is what makes this setting affordable.
  5. Someone reports that git reset --hard destroyed two days of committed work. Walk through the recovery, and name the case where it genuinely would be lost.
    The commits are almost certainly intact. reset --hard moves a branch ref and overwrites the working tree; it does not delete objects, so the old commits are still present and merely unreachable. git reflog lists where HEAD pointed after every operation, so find the entry from before the reset and git reset --hard HEAD@{n}, or safer, git branch recover HEAD@{n} to create a new branch without moving the current one. If the reflog entry is gone, git fsck --lost-found lists dangling commits. It is genuinely unrecoverable in two cases: changes that were never committed at all — reset --hard discards uncommitted work in the working tree and index with no record anywhere — and objects that both fell out of the reflog window, typically 90 days, and were then removed by git gc --prune. The practical lesson is to run git reflog as the very first command after any accident, before anything else pushes the entry you need out of view.
  6. A one-file change to a repository with 3,000 files adds how many objects, and why does that matter operationally?
    Three: a new blob for the changed file, a new tree for each directory on the path from the root to that file (one, in the simplest case), and the commit. Every other blob and every unaffected subtree is referenced by id and stored once. It matters because it is why a repository with a decade of history and thousands of files clones in seconds, why branching and checking out old revisions are cheap, and why the storage cost of committing frequently is close to zero — which removes the last technical argument for batching work into large commits. It also explains the opposite case: a large binary that changes every build shares nothing between versions, so each commit adds its full size permanently. That is what Git LFS exists for, and why check-added-large-files is worth having as a hook.
  7. A production API key was committed and pushed to a private repository three weeks ago. Give the order of operations.
    Rotate the key first, before touching the repository. Everything else is cleanup; until the credential is invalid you have an exposure, and history rewriting takes time you should not be spending while a live key is readable by anyone with clone access, in every existing clone, and in every CI cache and backup. Then remove the blob from history with git filter-repo, force-push all branches and tags, and have the team re-clone rather than pull — a pull would merge the old objects back in. Then ask the forge to garbage-collect: GitHub and GitLab keep unreachable objects fetchable by SHA on their side even after a force-push, so the secret remains retrievable by anyone who noted the commit id until support purges it. Finally add a scanner as both a pre-commit hook and a required CI check. Note that "private repository" changes the urgency slightly and nothing else: the credential has been readable by everyone with access, present in forks and CI logs, and it must still be treated as compromised.
