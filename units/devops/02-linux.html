The Linux machine underneath

Containers, orchestrators and cloud APIs are all abstractions over one thing: a Unix process running on a kernel that owns the memory, the disk and the clock. When something breaks at three in the morning, the abstraction is usually not where the answer is. This chapter is the layer under all of it — enough to read a machine correctly rather than guess at it.

Kernel, userspace and the line between

The kernel owns the hardware. Your process does not. It cannot read a file, open a socket, allocate memory or find out what time it is without asking, and the asking is a system call — a controlled trap into kernel mode with the arguments checked on the way in. Everything an operator cares about happens either side of that boundary, and almost every diagnostic tool is a way of watching it.

Userspace
Your processes, the shell, systemd, nginx, the container runtime, the language runtime. Isolated from each other by virtual memory. A crash here kills one process.
The syscall boundary
About 350 entry points. open, read, write, mmap, clone, execve, futex, epoll_wait. strace -c counts them per process; this is how you find out that a "slow" program is making two million stat calls.
Kernel
Scheduler, memory manager, filesystems, network stack, device drivers, namespaces and cgroups. A crash here takes the machine. Everything in chapter 9 about containers is built out of two kernel features that live at this level.
/proc is the interface, not a curiosity

Nearly every tool in this chapter — ps, top, free, uptime, ss — is a formatter over files in /proc. /proc/loadavg, /proc/meminfo, /proc/<pid>/status, /proc/<pid>/limits, /proc/<pid>/fd/, /proc/<pid>/cgroup. Knowing this matters in a minimal container image where ps is not installed but /proc always is. cat /proc/1/cgroup tells you whether you are inside a container at all.

Processes, states and signals

A new process comes from fork() — which duplicates the calling process — usually followed immediately by execve(), which replaces the duplicate's image with a different program. The copy is not a real copy: pages are marked copy-on-write and only duplicated when one side writes. This is why forking a 4 GB process is fast and why the memory accounting afterwards is confusing.

Every process is in exactly one state, and the state tells you what to do about it.

CodeStateMeaningWhat it tells you
RRunning / runnableOn a CPU, or queued waiting for oneCounts toward load. If runnable ≫ cores, you are CPU-bound
SInterruptible sleepWaiting on something, e.g. a socket or a timerThe normal state of almost everything. Does not count toward load
DUninterruptible sleepBlocked in a syscall, usually disk or NFS I/OCounts toward load, cannot be killed, ignores SIGKILL. Many D processes means storage, not CPU
ZZombieExited; exit status not yet reaped by the parentUses no memory, holds a PID. Thousands of them means a parent that never calls wait()
TStoppedSIGSTOP, or under a debuggerOften a job someone backgrounded with Ctrl-Z and forgot
IIdle kernel threadKernel worker with nothing to doIgnore. Excluded from load since 4.2

Signals are the process control interface, and three of them matter far more than the rest in operations.

PID 1 in a container does not behave like PID 1 on a host

The kernel gives PID 1 special treatment: signals with a default action are not applied to it unless it has installed a handler. On a host that is fine because PID 1 is systemd, which handles everything. In a container, PID 1 is your application — and if it has no SIGTERM handler, docker stop does nothing at all for the full grace period, then SIGKILL arrives and you lose in-flight work on every single deploy.

The second half of the problem is reaping. If your PID 1 spawns children and never calls wait(), orphaned grandchildren reparent to it and accumulate as zombies until the PID table fills. The fixes: install a real signal handler, avoid sh -c "…" as your entrypoint (the shell does not forward signals), and use --init or tini when your process is not designed to be PID 1.

bash — the graceful shutdown contract, both sides of it
# what the platform does when it wants your container gone
kill -TERM 1          ← you now have a grace period (Docker: 10s, k8s: terminationGracePeriodSeconds, default 30s)
# ...grace period elapses...
kill -KILL 1          ← unconditional. no handler, no cleanup, no flush

# what your process must do to survive that contract
#   1. stop accepting new connections / stop pulling from the queue
#   2. fail the readiness probe so the load balancer stops routing to you
#   3. finish in-flight requests, with a deadline shorter than the grace period
#   4. flush buffers, close the DB pool, exit 0

# find out whether yours does. it usually does not.
docker run -d --name t myimage
time docker stop t    ← 0.2s means it handled SIGTERM. 10s means it was killed

Load average, and what it is not

Load average is the most misread number on a Linux box. It is not CPU utilisation, it is not a percentage, and it has no upper bound. What the kernel actually does is sample, every five seconds, the count of processes that are either runnable or in uninterruptible sleep, and feed that count into three exponentially weighted moving averages with time constants of one, five and fifteen minutes.

load = load × e−5/T  +  n × (1 − e−5/T)     every 5 s, for T = 60, 300, 900 s

Where n is the instantaneous count of processes in state R or D. Two consequences fall straight out. First, the averages lag: after a step change, the 1-minute figure reaches only 63% of the new value after one minute. Second, and this is the part that catches people, D-state processes are counted — so a machine with an idle CPU and a saturated disk reports exactly the same load as a machine pinned at 100% CPU.

Load average, composed two different ways
Set CPU-bound to 0 and disk-blocked to 8 — the load is identical

The demo makes three points that are hard to get from prose alone.

Load is dimensionless until you divide by cores
A load of 8 is catastrophic on a single-core box, fully utilised on eight cores and half-idle on sixteen. The number worth alarming on is load ÷ cores, and even that only if the load is CPU-shaped. On a container, divide by the CPU limit rather than the host's core count — the host's /proc/loadavg is not namespaced, so a container sees the whole machine's load.
The three numbers are a trend, not three measurements
Their only real use is comparison. 1-minute above 15-minute means the problem is arriving; below means it is receding. One minute after a step from idle to 8 runnable, the 1-minute average reads 5.06 and the 15-minute reads 0.52 — so during a fast incident the 15-minute figure is close to meaningless, and after one it stays elevated long after recovery.
High load with idle CPUs means I/O
This is the single most useful diagnostic in the section. If uptime shows 12 and top shows the CPUs at 4%, you are looking at D-state processes queued on storage or a hung network filesystem. Confirm with ps -eo state,comm | grep ^D and iostat -x 1, and stop tuning thread pools.
Pressure stall information is the number load average should have been

Modern kernels expose /proc/pressure/{cpu,memory,io}. Each gives the percentage of wall time in which at least some tasks were stalled waiting for that resource, averaged over 10s, 60s and 300s. Unlike load average it is a bounded percentage, it separates the three resources, and some avg10 answers "is this machine short of CPU right now" directly rather than by inference. If your monitoring predates PSI, adding it is one of the highest-value small changes available.

Memory: what "free" means and who gets killed

Two facts explain nearly every memory confusion on Linux. The first is that processes see virtual memory, mapped lazily to physical pages only when touched. The second is that the kernel considers unused RAM to be wasted RAM, so it fills whatever is spare with page cache — copies of file contents it can throw away instantly if something needs the space.

NumberWhat it isUse it for
VSZTotal address space mapped, touched or not. Includes files mapped in and memory reserved but never usedAlmost nothing. A JVM with a 32 GB heap setting shows 32 GB VSZ on a 4 GB box
RSSPhysical pages currently resident for this processThe usual answer to "how much is it using", but double-counts shared pages across processes
PSSResident, with shared pages divided among the sharersThe honest per-process figure. Sums correctly across all processes. /proc/<pid>/smaps_rollup
freePhysical pages holding nothing at allNear zero on any healthy long-running machine. Alarming on it generates false pages
buff/cachePage cache and filesystem metadata — file contents kept in RAMMostly reclaimable on demand. Large is good
availableThe kernel's own estimate of what a new allocation could get without swappingThe number to alert on. Roughly free plus reclaimable cache, minus what the kernel needs to keep

When demand exceeds what is available, the kernel escalates: reclaim clean page cache, then write dirty pages out, then swap anonymous pages if there is swap, then — with nothing left — invoke the out-of-memory killer. The killer does not pick randomly and it does not pick the process that made the failing allocation. It scores every process, roughly by proportion of total memory consumed, adjusted by each process's oom_score_adj, and kills the highest.

Memory accounting and the OOM decision
Grow the JVM past the cache, then protect it with oom_score_adj and see who dies instead
Three OOM consequences people get wrong

The victim is not the culprit. A leaking sidecar can push the machine over and get postgres killed, because postgres is bigger. The kernel is minimising the number of kills, not assigning fault. Read dmesg or the journal for the full scoring table before concluding anything.

Inside a container, there are two OOM killers. The cgroup one fires when the container exceeds its own memory limit and kills only inside that cgroup — this is Kubernetes OOMKilled, exit code 137. The system one fires when the host runs out and can kill anything. They look identical from inside and have completely different fixes.

Swap does not prevent OOM, it postpones it and makes the machine unusable first. A box thrashing on swap has technically not failed, which is worse than failing: latency goes up by three orders of magnitude while every health check still passes. This is why Kubernetes historically refused to run with swap enabled at all.

Filesystems, inodes and the two ways a disk fills

A file's name and its contents are separate things. The contents, plus the metadata — size, owner, permissions, timestamps, and pointers to the data blocks — live in an inode. A directory entry is just a name paired with an inode number. That indirection explains a family of behaviours that otherwise look arbitrary.

A hard link is a second name for the same inode
There is no "original". Deleting one name decrements a reference count; the data goes when the count hits zero. Cannot cross filesystems, cannot point at a directory.
A symlink is a small file containing a path
Can cross filesystems, can dangle, resolves at access time. This is why swapping a symlink is an atomic deploy primitive and copying over a directory is not.
Deleting a file that a process still has open frees nothing
The directory entry goes, the inode's link count drops to zero, but the open file descriptor keeps it alive. df shows the space used and du cannot find it, because the file has no name any more. This is the classic "I deleted the 40 GB log and nothing happened". Find it with lsof +L1; free it by restarting the holder or truncating through /proc/<pid>/fd/<n>.
You can run out of inodes with the disk half empty
Inodes are allocated when the filesystem is created and their count is fixed. A few million tiny session files, mail-queue entries or cache fragments will exhaust them while df -h reads 45%. Writes fail with ENOSPC — "No space left on device" — which sends everyone to the wrong place. df -i is the check, and it takes two seconds.
bash — the disk-full triage sequence, in order
df -h                      ← which mount, and is it actually full
df -i                      ← inodes. do this SECOND, not last. costs nothing
du -xh --max-depth=1 / | sort -h | tail -20
                           ← -x stays on one filesystem, or you will walk /proc all night
lsof +L1                   ← deleted-but-open files. explains df and du disagreeing
journalctl --disk-usage    ← the journal is a very common answer
docker system df           ← so are dangling images and build cache

# the two immediate mitigations
truncate -s 0 /var/log/huge.log     ← keeps the inode, so an open writer keeps working.
                                      `rm` would not free the space at all while it is open
journalctl --vacuum-size=200M
Reserved blocks, and the 5% that is not missing

ext4 reserves 5% of the filesystem for root by default. On a 2 TB data volume that is 100 GB set aside so that root can still log in and clean up when a runaway process fills the disk — sensible on /, pure waste on a dedicated data volume. tune2fs -m 1 /dev/sdb1 reclaims it. It also explains why an unprivileged process gets ENOSPC while df still shows free space.

Users, permissions and capabilities

Every file has an owner, a group and nine permission bits — read, write and execute for user, group and other. The octal form is worth being fluent in because it appears in every Dockerfile, Ansible task and Kubernetes volume spec.

OctalSymbolicMeaning on a fileMeaning on a directory
644rw-r--r--Owner writes, everyone reads—
600rw-------Owner only. What every secret and private key must be—
755rwxr-xr-xExecutable by allEveryone can enter and list
700rwx------Owner-only executableOwner-only directory. ~/.ssh must be this or sshd refuses
1777rwxrwxrwt—Sticky bit: anyone writes, only the owner deletes their own. This is /tmp
4755rwsr-xr-xSetuid: runs as the file's owner regardless of who invoked it. A privilege escalation surface—

On a directory the bits mean something different from what they suggest. x is traverse — permission to reach things inside by name — while r is permission to list the names. A directory with --x lets you open /secret/known-file but not discover what is in /secret. And w on a directory permits deleting files inside it regardless of who owns them, which is why /tmp needs the sticky bit.

Capabilities replaced the root/not-root binary, and containers depend on it

Historically a process either had every privilege or none. Linux split root's powers into about forty capabilities: CAP_NET_BIND_SERVICE for ports below 1024, CAP_NET_ADMIN for interfaces and firewall rules, CAP_SYS_ADMIN for a grab-bag broad enough to be effectively root. This is what lets a container run nginx on port 80 as a non-root user — grant one capability instead of the whole set. The corresponding hardening step is --cap-drop=ALL and then adding back only what is needed, and it is one of the highest-value lines in a container spec. Chapter 10 returns to it.

systemd: what supervises everything

systemd is PID 1 on essentially every mainstream distribution. It starts services in dependency order, restarts them when they die, captures their output, applies resource limits through cgroups and handles socket activation and timers. You do not need to like it; you do need to be able to read a unit file and diagnose a service that will not start.

ini — /etc/systemd/system/api.service, annotated
[Unit]
Description=Order API
After=network-online.target postgresql.service   ← ORDERING only. does not require them
Wants=postgresql.service                         ← try to start it too; do not fail if it fails
# Requires= would make this unit stop when postgresql stops. usually too strict

[Service]

                             `simple` means "ready the instant exec returns", which is a lie
                             for anything with a warm-up, and breaks ordering downstream
ExecStart=/usr/bin/api --config /etc/api.toml
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure         ← not `always`: `always` restarts after a clean exit 0 too
RestartSec=2

Restart=always is how a crash loop becomes invisible

A service that crashes on startup and restarts every two seconds looks "active" often enough to fool a coarse health check, while filling the journal and consuming CPU. systemd has a rate limiter for exactly this — StartLimitIntervalSec and StartLimitBurst, five starts in ten seconds by default — after which the unit enters failed and stays there. That is the desired behaviour: a loudly broken service beats a quietly flapping one. Kubernetes reaches the same conclusion with CrashLoopBackOff and exponential backoff.

The USE method gives you an order to run them in

For every resource — CPU, memory, disk, network — check Utilisation, Saturation and Errors, in that order, before moving to the next resource. It is dull and it is systematic, and it beats intuition consistently because it does not let you skip the resource you happen not to be thinking about. Utilisation says how busy, saturation says how much queued work is waiting, errors say what already failed. Chapter 22 formalises this alongside its request-oriented counterpart, RED.

Check yourself

Self-check

  1. uptime reports a load average of 14.02 on an 8-core machine, and top shows all CPUs around 6% busy. What is happening, and what do you run next?
    Load counts uninterruptible (D-state) processes as well as runnable ones, so a queue of processes blocked on storage produces a high load with idle CPUs. Something is waiting on a device — a saturated disk, a degraded RAID rebuild, or a hung NFS or network mount. Confirm the state distribution with ps -eo state,comm | grep ^D, then iostat -xz 1 for %util and await per device, and check dmesg for I/O errors or mount timeouts. Tuning threads or adding CPU will do nothing.
  2. A colleague pages saying a production box is "out of memory" because free -m shows 210 MB free out of 16 GB. Are they right?
    Almost certainly not. The kernel deliberately fills unused RAM with page cache, so free tends toward zero on any machine that has been up for a while and doing I/O — that is healthy, not a fault. The number that matters is available, which estimates what a new allocation could obtain by reclaiming cache without swapping. If available is several gigabytes there is no problem. If available is also small, then there is, and the next checks are swap in/out rates in vmstat 1 and the MemAvailable trend over time rather than its instantaneous value.
  3. The OOM killer terminated postgres, but the leak was in a small sidecar. Explain why, and how you would prevent a repeat.
    Badness is scored roughly by the fraction of total memory each process holds, not by who caused the shortage. The sidecar's growth consumed the headroom; postgres, being the largest resident consumer, scored highest and was chosen. The kernel is trying to reclaim the most memory per kill, not to assign blame. Prevention has two halves: bound the culprit, by giving the sidecar its own cgroup memory limit so it hits a local OOM and dies alone, and protect the victim, by setting a negative oom_score_adj on postgres. Under Kubernetes both fall out of setting memory requests equal to limits for the critical container, which places it in the Guaranteed QoS class and makes it the last thing evicted.
  4. df says the volume is 98% full. du -sh on every directory adds up to about half that. Where is the rest?
    Most likely in files that have been deleted but are still held open by a running process. Unlinking removes the directory entry, so du — which walks names — cannot see the file, but the inode and its blocks survive until the last file descriptor closes, so df still counts them. lsof +L1 lists files with a link count of zero and the process holding each. Restart the holder, or reclaim the space in place with : > /proc/<pid>/fd/<n>. Two other candidates worth ruling out: a filesystem mounted over a directory that already contained data, which hides the underlying files from both tools, and ext4's 5% root reservation.
  5. Writes are failing with "No space left on device" but df -h shows 55% used. What is the explanation?
    Inode exhaustion. The count of inodes is fixed when the filesystem is created, so a workload producing millions of very small files — session data, mail spool, cache shards — can consume every inode while using little of the capacity. ENOSPC is returned for both conditions, which is what makes it confusing. df -i distinguishes them in two seconds. The fix is to delete the small files or move that workload to a filesystem without a fixed inode count, such as XFS; you cannot add inodes to an existing ext4 filesystem without recreating it.
  6. Your container ignores docker stop and takes the full ten seconds every time. Give two causes and their fixes.
    First, the process has no SIGTERM handler. The kernel does not apply default signal actions to PID 1, so a process that would normally die on SIGTERM simply ignores it inside a container and waits for the SIGKILL. Fix: install a handler that drains and exits. Second, the entrypoint is a shell — CMD "npm start" in shell form, or a wrapper script — and the shell receives the signal without forwarding it to the child it is waiting on. Fix: use exec form so your binary is PID 1, or exec the final command in the wrapper, or run with --init so a minimal init handles forwarding and zombie reaping. The cost of not fixing it is in-flight requests dropped on every single deployment.
  7. What does Type=notify buy over Type=simple, and when does the difference actually bite?
    With simple, systemd considers the service started the moment execve returns — before any configuration is parsed, any port is bound or any connection pool is warm. With notify, the process signals readiness explicitly over a socket, so "active" means genuinely serving. It bites whenever something is ordered After= this unit: with simple, the dependent starts against a service that is not listening yet, producing connection-refused errors on every boot that disappear on manual retry — the classic "only fails on reboot" bug. It also bites health checking and any deployment that waits for the unit to become active before shifting traffic. The same distinction reappears in Kubernetes as the difference between a container being Running and passing its readiness probe.
