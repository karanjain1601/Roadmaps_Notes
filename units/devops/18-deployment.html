Chapter 18 · Delivery

Deployment strategies

Chapter 1's model said that shipping more often does not create more failures, it creates smaller ones — and that the release mechanism's own reliability sets the safe cadence. This chapter is that mechanism. The measure that matters is not how quickly you can roll back but how many people saw the problem before you knew about it, and those two are much less related than they look.

Five ways to replace a running version

StrategyHowCapacity duringSuits
RecreateStop everything, start the new versionZero — an outage by designBatch jobs, anything where two versions must never coexist
RollingReplace a few replicas at a timeMaintained, with surgeThe default. Both versions run together, so backward compatibility is required
Blue-greenBuild a whole second environment, switch trafficFull, then fullInstant rollback matters more than cost. Doubles infrastructure during the switch
CanarySend a small share of traffic to the new version, watch, widenMaintainedAnything user-facing where exposure matters. Needs a metric to judge it by
ShadowMirror real traffic to the new version, discard the responsesMaintainedValidating performance or correctness with zero user risk. Cannot test writes without care

Comparing them by intuition produces the wrong ranking, because "rollback is instant" feels like the safety property and it is not. The quantity that matters is the integral of bad traffic over time until the problem is detected and reversed.

requests harmed  =  ∫ rate × (fraction on the bad version) × (its error rate)  dt

The fraction on the bad version is the term the strategy controls, and it is inside an integral — so keeping it small early matters far more than reversing it quickly afterwards. Detection time appears once; the fraction appears throughout.

How many people see a bad version
Compare the three, then drop the error rate to 0.1% and see the canary miss it
Canary wins by two orders of magnitude on a loud regression
540 failed requests against 36,000 rolling and 54,000 blue-green. It is caught at 1% of traffic instead of 50% or 100%, and 1% is where the integral is small.
Blue-green rolls back instantly and is still the worst
Because it puts every user on the new version from the first second, so the whole detection window is spent at 100% exposure. Fast rollback limits how long the damage lasts and does nothing about how wide it is. This is the result that contradicts the intuition, and it is the one worth remembering.
Rolling is a compromise that nobody chose deliberately
Exposure grows in steps while the alert is still gathering evidence, so it is caught somewhere in the middle — better than blue-green, far worse than canary, and it is the default in every orchestrator.
But a quiet regression escapes the canary entirely
At a 0.1% error rate the canary sees 1.8 errors in its window at 1% of traffic — indistinguishable from noise. It is promoted, and the problem is only caught at full exposure. The canary percentage has to be large enough that the error rate you care about is measurable in the detection window.
Which gives the rule for sizing a canary

Work backwards from the smallest regression you want to catch. If you need thirty errors to be confident, and you care about a 0.1% error rate, then rate × fraction × 0.001 × window ≥ 30. At 2,000 requests a second and a five-minute window that needs a fraction of about 5%, not 1%. Below that threshold the canary is theatre: it runs, it passes, and it tells you nothing. The alternatives when the traffic is not there are to hold the canary for much longer, to compare against a control group rather than a threshold so you can use a statistical test with far fewer samples, or to accept that this class of regression will be caught at full exposure and make rollback fast instead.

Separating deploy from release

Every strategy above still couples two things: putting code on a machine, and exposing behaviour to users. A feature flag separates them, which is what makes chapter 5's short branches practical — merge the incomplete work with the flag off, and turn it on when it is ready.

Release becomes a runtime decision
No deploy, no rollout, no rebuild. Turning a feature off during an incident takes seconds rather than a pipeline run, which is often the fastest mitigation available and the reason a kill switch on any risky path is worth having before you need it.
You can target as well as toggle
Internal users first, then 1%, then a region, then everyone — a canary at the feature level rather than the deployment level, and one that works even when the change is a single code path inside an otherwise unchanged service.
Every flag is a branch that must be tested both ways
Ten independent flags are 1,024 possible configurations. In practice most combinations are irrelevant, but the ones that interact are exactly the ones nobody tested — so keep the number of simultaneously live flags small.
A flag with no removal date is technical debt with a name
Write the removal ticket when you create the flag. A codebase with two hundred permanent flags has a configuration space nobody understands and a control plane that is now a production dependency — which needs its own availability story, and a default that fails safe when the flag service is unreachable.

Database changes, and why rollback stops being possible

Every strategy except recreate runs two versions of the code simultaneously. That is fine for stateless changes and it is the whole problem for schema changes, because the database is shared: every intermediate state must work for both the version being replaced and the one replacing it.

A single-step rename fails this immediately. Rename the column, deploy the new code, and while the rollout is in progress the old pods are still serving — and their column is gone. The fix is to make the change in stages where every stage is compatible with both, which is called expand and contract.

Renaming a column without an outage
Compare the big bang with the six-step plan, then look at step 6's rollback
  1. Expand. Add the new column, nullable, with no code change. The old code does not know it exists, so nothing can break. Reversible.
  2. Write both. Deploy code that writes the old and the new column and still reads the old. During this rollout the previous version and this one both run against a schema that has both columns, so both work. Reversible.
  3. Backfill. Populate the new column for existing rows, in batches, without locking the table. Nothing reads it yet, so a failure here is harmless.
  4. Read new. Deploy code that reads the new column and still writes both. If the backfill was wrong, this is where you find out — and you can still roll back, because the previous version reads the old column, which is still populated.
  5. Stop using the old. Deploy code that reads and writes only the new column. Still reversible: the old column exists and is still current.
  6. Contract. Drop the old column. This is the point of no return — the previous code version writes a column that no longer exists, so rolling back is impossible.
Five of six steps are reversible, and that is the design

The value of expand-contract is not that it avoids one outage during the rename. It is that the irreversible step is isolated, explicit, and can be deferred arbitrarily. Teams routinely leave weeks between step 5 and step 6, because until the old column is dropped every deploy in the sequence can be undone by redeploying the previous image — chapter 17's promoted artefact, unchanged. Once it is dropped, a rollback needs a database restore. Treat step 6 as a separate change with its own review, and never bundle it with the code change that stopped using the column. The same reasoning covers adding a NOT NULL constraint, changing a type, and dropping a table: expand, migrate, verify, and contract long afterwards.

The migration that locks the table

A schema change is a deployment even when no code changes. Adding a column with a non-constant default rewrites every row in older PostgreSQL versions; adding an index without CONCURRENTLY takes a write lock for the duration; and a migration that runs inside the application's start-up path means every replica tries it at once during a rolling update. Run migrations as a separate step before the deploy, with a statement timeout so a lock that cannot be acquired fails fast rather than queueing behind a long-running query and blocking every write in the meantime. The PostgreSQL unit covers the locking rules; the delivery point is that the migration needs its own place in the pipeline, not a hook inside the application.

Rollback, roll forward, and the machinery

Roll back

Redeploy the previous artefact — chapter 17's build-once-promote makes this a known-good digest rather than a rebuild. Fastest and most predictable, and it works only while every intermediate state remains compatible, which is what the migration section is protecting.

Roll forward

Fix and deploy. Necessary once an irreversible step has happened, and reasonable when the fix is trivial and the pipeline is fast — which is chapter 1's argument for why release-mechanism speed is itself a reliability property.

Revert the commit

git revert and let it flow through the normal pipeline. Slower than a redeploy but it keeps the repository as the source of truth, which matters enormously under GitOps in chapter 19 — otherwise the controller reconciles your manual rollback straight back to the broken version.

Automate the abort
A canary that requires a human to notice has a detection time measured in whatever the on-call engineer was doing. Argo Rollouts, Flagger and the equivalents watch a metric and abort automatically, which turns the detection window from an unknown into a configured number — the one in the model above.
Set maxSurge and maxUnavailable deliberately
Surge adds capacity before removing it, so throughput is maintained at the cost of briefly running more replicas. maxUnavailable: 0 with a surge is the safe default; the opposite pairing quietly reduces capacity during every deploy, which is how a routine rollout becomes an incident at peak.
Disruption budgets protect you from the platform
A PodDisruptionBudget constrains voluntary disruption — a node drain, a cluster upgrade, an autoscaler scale-down — so those operations block rather than take you below a floor. Without one, chapter 11's cluster operations are free to remove all your replicas at once, and they will.
Respect the shutdown contract
Chapter 12 measured this: a rolling update without a preStop delay drops around 240 requests per pod replaced, purely because endpoint removal and SIGTERM race. Every strategy here inherits that, and it is invisible until you look for it.

Check yourself

Self-check

  1. Your team chose blue-green because rollback is instant. Is that the safest option?
    No, and the model shows why. The quantity that matters is the integral of bad traffic over time — rate multiplied by the fraction of traffic on the bad version multiplied by its error rate, accumulated until you detect and reverse. Blue-green puts 100% of traffic on the new version from the first second, so the entire detection window is spent at full exposure: 54,000 failed requests in the demo, against 36,000 for rolling and 540 for canary. Instant rollback bounds how long the damage lasts and does nothing about how wide it is, and the width term is the one inside the integral for the whole detection window. Blue-green is still valuable where an instant, complete reversal is the requirement — a change that cannot be partially applied, or an environment you want to validate whole before switching — but it should be chosen for that property rather than for a general belief that it is the safest.
  2. Your canary sends 1% of traffic to the new version for five minutes and passes. A day later you discover the new version corrupts 0.1% of orders. Why did the canary not catch it?
    There was not enough evidence to see. At 2,000 requests a second, 1% of traffic is 20 requests a second, and a 0.1% error rate on that is 0.02 errors a second — about 1.8 errors in a 90-second window, which is indistinguishable from normal noise. The canary was promoted because nothing looked wrong, not because nothing was wrong. The rule is to size the canary backwards from the smallest regression you want to catch: if you need thirty errors to be confident about a 0.1% rate at 2,000 requests a second over five minutes, you need roughly 5% of traffic, not 1%. The alternatives when the traffic simply is not there are to hold the canary much longer, to compare against a control group with a statistical test rather than a fixed threshold, which needs far fewer samples, or to accept that this class of regression will be caught at full exposure and invest in fast detection and rollback instead.
  3. You rename a database column and deploy the matching code in the same release. What happens during the rolling update?
    Errors from every replica that has not yet been replaced. A rolling update runs both versions simultaneously by design, so the moment the schema changes, the old pods — still serving their share of traffic — query a column that no longer exists. The failure is proportional to how long the rollout takes and how many replicas are left, and it looks like an intermittent partial outage rather than a clean break, which makes it confusing to diagnose. The fix is expand and contract: add the new column, deploy code that writes both, backfill, deploy code that reads the new one, deploy code that stops using the old one, and only then drop it. Every intermediate state is compatible with both the version being replaced and the one replacing it. Note the same argument applies to blue-green and canary — anything except recreate has two versions live at once.
  4. In expand-contract, which step is irreversible and what follows from that?
    The contract — dropping the old column. Up to that point every step can be undone by redeploying the previous artefact, because the old column still exists and is still current, so the previous code version works unchanged. Once it is dropped, the previous version writes to a column that is gone and rolling back requires a database restore. What follows is that the contract should be a separate change with its own review, never bundled with the code change that stopped using the column, and deferred until the new version has been proven in production — often by weeks. Five of the six steps being reversible is the point of the pattern; avoiding one outage during the rename is a side benefit. It also explains why the sequence looks tediously long: each step exists to keep the next one reversible.
  5. Why does a rolling update produce a burst of errors even when the new version is perfectly healthy?
    Because of the endpoint propagation race from chapter 12. When a pod is deleted, the SIGTERM and the removal from the endpoint list start at the same moment and are not ordered, so the pod can stop accepting connections before every node in the cluster has updated its routing rules. Anything sent in that window fails — about 240 requests per pod replaced at 2,000 requests a second across ten replicas, so roughly 2,400 across a full rollout. It is entirely independent of whether the new version is good. The fix is a preStop hook that sleeps for longer than the propagation delay so the removal lands before the SIGTERM, or an application that fails its readiness probe on SIGTERM and keeps serving for a few seconds. Either way, terminationGracePeriodSeconds must exceed the delay plus the drain.
  6. Under GitOps, an engineer rolls back by running kubectl set image during an incident. What happens next?
    The controller reconciles it back to the broken version, usually within a minute or two, and the incident resumes with everybody confused about why the fix stopped working. Chapter 19 covers the mechanism: the repository is the desired state and a continuous loop corrects anything that differs, so a manual change to the cluster is drift by definition, not an instruction. The correct rollback is to change the repository — revert the commit, or set the image tag back in the manifest — and let the controller apply it. That is slower than a direct command, which is a genuine cost during an incident, and the mitigations are to make the reconciliation fast, to keep a documented emergency procedure that suspends the controller for the affected application first, and to prefer feature flags for the fastest mitigations since they change runtime behaviour without touching the desired state at all.
  7. Your deployment sets maxUnavailable: 25% and maxSurge: 0. What have you configured?
    A rollout that reduces capacity by a quarter for its whole duration. With no surge, new pods can only start after old ones have been removed, so at every moment up to 25% of your replicas are gone. If the service normally runs at 60% utilisation that is survivable; at 80% it is not, and the rollout itself becomes the incident — most likely at peak, because that is when someone deploys a fix. The safe default is the inverse: maxUnavailable: 0 with maxSurge: 25%, which adds new pods before removing old ones so full capacity is maintained, at the cost of briefly running 125% of the replicas and needing the cluster headroom for it. Worth pairing with a PodDisruptionBudget, which constrains what the platform may do to you voluntarily during node drains and upgrades — a different mechanism for a related risk.
