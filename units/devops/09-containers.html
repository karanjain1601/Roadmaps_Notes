Chapter 09 · Containers

Containers from first principles

There is no such thing as a container. There is a normal Linux process that has entered some namespaces, had some cgroup limits applied, and been given a root filesystem assembled from stacked read-only layers. Once you see it that way the whole model stops being magic and starts being a set of specific, inspectable decisions — including several that quietly leave you with no isolation at all.

What the container was actually invented for

Two separate problems, and it helps to keep them apart because different tools solve them and people conflate the answers.

Packaging
"It works on my machine" is a dependency statement: the machine has a particular glibc, a particular Python, a particular set of shared libraries and a particular filesystem layout. An image freezes all of that into one artefact so the thing you tested is the thing that runs. This is by far the larger of the two wins, and it is the reason containers spread through development before they spread through operations.
Density and isolation
A virtual machine duplicates an entire kernel to run one application. A container shares the host kernel and isolates only what the process can see, so it starts in milliseconds instead of tens of seconds and costs megabytes instead of gigabytes. That makes it economical to run one process per unit rather than packing several onto a machine, which is what makes per-service scaling and rolling deployment practical.

The isolation is weaker than a VM's, and being precise about how much weaker is the most useful thing in this chapter — because the difference is not fixed. It depends entirely on which of the mechanisms below you actually turned on.

Namespaces: what the process can see

A namespace wraps a global kernel resource so that processes inside it see their own instance of it. There are eight, and each one is independently entered — which is why "containerised" is not a binary state.

NamespaceIsolatesWithout it
pidThe process ID space. Your process is PID 1ps shows every host process, and /proc/<pid>/environ can leak other services' environment variables — which is where their credentials live
netInterfaces, routes, firewall rules, port numbersYou share the host's stack: can bind host ports, sniff host traffic, and reach services bound to 127.0.0.1 that believed themselves private
mntThe mount table and therefore the filesystem viewYour root filesystem is the host's
utsHostname and domain nameCosmetic — but hostname inside would change the host's
ipcSystem V IPC and POSIX message queuesShared memory segments are readable across containers
useruid and gid mappingsuid 0 inside is uid 0 on the host. Any escape lands as real root
cgroupThe cgroup hierarchy rootThe container can see the host's full cgroup tree
timeBoot and monotonic clocksRarely used; matters for checkpoint and restore

The user namespace deserves special attention because it is the one that is off by default in Docker and in most Kubernetes installations. Without it, the two senses of "root" are the same root, and every other protection is the only thing standing between a container process and the host.

Assemble a container, one mechanism at a time
Start from "nothing", then try the Docker defaults, then mount the socket
Mounting the Docker socket is equivalent to root on the host

It is extremely common — CI runners that need to build images, monitoring agents, anything doing "Docker in Docker" — and it is a complete escape with no exploit required. A process that can talk to the daemon can ask it to start a new container that is --privileged and bind-mounts /, then write to the host filesystem as root. Every namespace you carefully enabled is irrelevant, because you are not escaping the container, you are politely asking a root-privileged daemon to do the work for you. If a workload needs to build images, use a rootless builder such as Kaniko or Buildah rather than handing it the socket.

cgroups: what the process can consume

Namespaces control visibility; cgroups control resources. Under cgroup v2 each container is a directory in /sys/fs/cgroup with a handful of files that set limits and report usage.

FileControlsWhat happens at the limit
cpu.maxQUOTA PERIOD in microseconds — e.g. 50000 100000 is half a CPUThrottled: the process is descheduled until the next period. Not killed, just stopped
cpu.weightRelative share under contentionNothing. It only takes effect when the CPU is contended, which is why it is the safer control
memory.maxHard memory ceilingThe cgroup OOM killer fires inside this cgroup only. Exit code 137, Kubernetes calls it OOMKilled
memory.highSoft ceilingReclaim pressure and throttling rather than a kill. Underused, and much kinder
io.maxIOPS and bytes per second per deviceThrottled
pids.maxProcess countfork() fails. This is the cheap defence against a fork bomb, and almost nobody sets it

The CPU one is worth dwelling on, because it produces a failure that looks impossible: a container throttled hard while its average CPU usage sits comfortably below its limit. The reason is that cpu.max is not an average — it is a hard cap enforced inside every 100 ms window, and traffic does not arrive at a constant rate.

periods needed  =  ⌈ CPU the request needs ÷ quota ⌉   ·   wall time  =  (periods − 1) × period  +  remainder

A request needing 200 ms of CPU under a 50 ms quota cannot run for 200 ms. It runs for 50, stalls for 50, runs for 50, stalls for 50, and so on — finishing after 350 ms of wall time, of which 150 ms was spent descheduled doing nothing. The container used 0.2 CPU on average against a 0.5 limit the whole time.

Three consequences that change how you set limits

Throttling happens far below the average limit. At the defaults above the container runs at 40% of its CPU limit and still exhausts its quota in 8.0% of periods, because two requests fit in one quota and arrivals bunch. Every one of those periods adds up to 50 ms of pure stall to whatever was running, which lands squarely in your p99.

Raising the limit helps superlinearly. Doubling it from 0.5 to 1.0 CPU halves the utilisation but cuts throttled periods from 8.0% to 0.06% — a 135-fold reduction, not a twofold one. This is why "the CPU graph looks fine, why is p99 bad" is answered by container_cpu_cfs_throttled_periods_total rather than by the usage metric.

Parallelism drains the quota faster, it does not raise it. Splitting the same 200 ms of work across four threads should take 50 ms; under a 0.5 CPU limit it takes 313 ms, a 6.3× stretch against 1.8× for the single-threaded version. The four threads burn the quota four times faster and then all stall together. This is the mechanism behind the classic JVM problem, where a runtime that sized its thread pools from the host's core count spawns dozens of GC threads inside a half-CPU container.

The practical position on CPU limits

Set CPU requests, which reserve a share and drive scheduling. Be far more cautious with CPU limits, which throttle. Many experienced teams set requests and omit limits entirely, on the grounds that cpu.weight already prevents a noisy neighbour from starving anyone under contention, while a limit actively wastes idle capacity that nobody else wants. The counter-argument is that limits make performance predictable and stop a runaway from consuming a whole node. If you do set them, set them well above the peak rather than near the average, and alert on throttled periods. Memory is the opposite case: memory.max genuinely is necessary, because memory is not compressible and there is no equivalent of "throttling" — the alternative to a limit is the host OOM killer choosing a victim, which chapter 2 showed is not the process you would have chosen.

Union filesystems, and what an image really is

The third mechanism is the one that makes images cheap. OverlayFS presents a stack of read-only directories plus one writable directory as a single filesystem. Each image layer is a directory of files; the container gets them stacked with a thin writable layer on top.

An image is an ordered list of layer digests plus a config blob
Nothing more. The manifest names the layers by content hash and the config records the entrypoint, environment, exposed ports and so on. A tag is a mutable pointer to a manifest digest — which is why myapp:latest is not a version, and why deploying by digest is what makes a deployment reproducible.
Layers are shared across images by content
Ten images built on the same base share exactly one copy of it on disk and one pull over the network. This is why a 900 MB image is not necessarily 900 MB of new traffic, and why standardising on a small number of base images matters more than shrinking any individual image.
Writes go to the top layer, copying the whole file first
Modifying one byte of a 2 GB file in a lower layer copies the entire 2 GB into the writable layer. This copy-up cost is why databases in containers want a volume rather than the container filesystem, and why heavy write workloads on overlay storage are slow in a way that looks inexplicable.
Deleting a file from a lower layer does not remove it
It writes a whiteout entry that hides it. The bytes are still in the image and still transferred on every pull. This single fact is the most consequential thing in chapter 10.
The container's writable layer dies with the container
Which is the whole point — but it means anything you need to keep must be on a volume, and it means a container that writes logs to its own filesystem is filling the host's disk in a place nobody thinks to look.

The rule that follows from the second-to-last row

Containers isolate your workloads from each other well enough. They are not a sufficient boundary between mutually untrusted workloads, because the shared kernel means one local privilege escalation compromises every container on the host. That is why cloud providers running untrusted customer code use microVMs underneath what they present as containers — AWS Lambda and Fargate run on Firecracker — and why running arbitrary user-supplied code in a plain container on a shared node is a decision that needs a deliberate argument rather than a default. gVisor takes the other approach, intercepting syscalls in userspace to shrink the surface, at a performance cost.

Check yourself

Self-check

  1. A CI runner mounts /var/run/docker.sock so it can build images. Someone points out that the container is otherwise well hardened — all namespaces, capabilities dropped, non-root user. How much does the hardening buy?
    Essentially nothing. A process that can reach the Docker socket can instruct the daemon — which runs as root on the host — to start a new container that is --privileged and bind-mounts /, then write to the host filesystem as root. There is no exploit and no escape; it is the daemon's documented API being used as designed. Every namespace and dropped capability applies to the CI container, not to the container it asks the daemon to create. Treat socket access as equivalent to granting root on the host, and if a workload needs to build images use a rootless builder such as Kaniko or Buildah, or a remote build service, so that no process holding untrusted input ever has the socket.
  2. Your service is limited to 500m CPU. The usage graph never exceeds 250m, yet p99 latency is five times the median. Where do you look?
    At CFS throttling — container_cpu_cfs_throttled_periods_total, or nr_throttled in the cgroup's cpu.stat. The limit is not an average, it is a hard cap inside every 100 ms window, and traffic does not arrive at a constant rate. In the model above, a container at 40% of its limit still exhausts its quota in about 8% of periods simply because arrivals bunch, and each of those adds up to 50 ms of pure stall to whatever was running. Averaged over a minute the usage graph shows 250m and looks healthy; the requests unlucky enough to be running during a throttled period are the p99. The remedy is to raise the limit — which helps superlinearly, cutting throttled periods from 8% to 0.06% when doubled — or to remove the limit and rely on requests and cpu.weight for fairness.
  3. Splitting a 200 ms unit of work across four threads makes it slower inside a 0.5 CPU container. Explain.
    The quota is CPU-time per period, not CPUs. Four threads consume it four times faster in wall-clock terms: the container gets 50 ms of CPU per 100 ms period, which four parallel threads exhaust in 12.5 ms, and then all four stall for the remaining 87.5 ms. The total CPU needed is unchanged, so the number of periods needed is unchanged, but the useful fraction of each period has shrunk. The ideal wall time falls from 200 ms to 50 ms while the actual rises to about 313 ms — a 6.3× stretch against 1.8× for the single-threaded version. This is the mechanism behind the JVM case: a runtime that sizes GC threads and pools from the host's core count spawns dozens of threads inside a half-CPU container, and they all become runnable during a collection. The fixes are to make the runtime container-aware, cap its thread pools explicitly, or raise the limit so the quota is not the constraint.
  4. Why does modifying one byte of a large file inside a container sometimes take seconds?
    Copy-up. OverlayFS presents read-only image layers with one writable layer on top, and it cannot modify a file in a lower layer in place — so the first write to any such file copies the entire file into the writable layer first. One byte of a 2 GB file means a 2 GB copy before the write proceeds. It happens once per file per container lifetime, which makes it confusing: the first write is very slow and every subsequent one is normal. This is why databases and any write-heavy workload should use a volume, which bypasses the union filesystem entirely, and why an image containing large mutable files is a poor design even when its size looks acceptable.
  5. docker run --user 1000 is often described as making a container non-root. What does it and does it not achieve?
    It does achieve real defence in depth: the process starts as uid 1000, so it cannot write to root-owned paths, cannot bind ports below 1024 without CAP_NET_BIND_SERVICE, and a compromise starts from an unprivileged position. That is worth having and should be the default. What it does not achieve is a mapping between container identity and host identity. Without a user namespace, uid 1000 inside is uid 1000 on the host, and uid 0 inside would be real root on the host — so the protection depends entirely on the process never becoming root, rather than on root inside being harmless. A user namespace is what supplies the second property: it maps container uid 0 to some unprivileged host uid, so even a full escape from a root-in-container process lands as nobody. It is off by default in Docker and in most Kubernetes installations, which is why the demo flags it as an exposure in the default configuration.
  6. A container is killed with exit code 137. Give the two possible causes and how you would tell them apart.
    137 is 128 + 9, so the process received SIGKILL. Either the cgroup OOM killer fired because the container exceeded memory.max — the platform records this as OOMKilled in the termination reason, and the kernel log shows the cgroup and the chosen victim — or the runtime sent SIGTERM for a normal shutdown, the process ignored it for the entire grace period, and the runtime escalated. Timing separates them cleanly: an OOM kill happens at an arbitrary moment under load, while a grace-period escalation happens at exactly the configured grace period after a stop was requested. The fixes are unrelated: raise the limit or reduce usage in the first case, and install a working SIGTERM handler in the second, which is the PID 1 problem from chapter 2. Note also that a memory limit produces an immediate kill rather than throttling, because memory is not compressible — this asymmetry with CPU is why the advice on the two limits is opposite.
  7. Your platform team proposes running customer-supplied code in containers on shared nodes. What is the objection, and what would you propose instead?
    Containers share the host kernel, so the isolation boundary is the syscall interface — hundreds of entry points, historically a steady source of local privilege escalations. One such vulnerability compromises every container on the node, not just the one that exploited it. That is acceptable between workloads that already trust each other, since they share a blast radius anyway, and it is not acceptable between mutually untrusted tenants, because the failure mode is a cross-customer breach. The established answer is a hypervisor boundary under whatever you present as a container: microVMs such as Firecracker give a per-workload kernel with roughly 125 ms start-up and a few megabytes of overhead, which is why AWS Lambda and Fargate use them. gVisor is the alternative, intercepting syscalls in userspace to shrink the surface at some performance cost. If neither is possible, the fallback is one node per tenant — which is a real cost, and the point is to price it honestly rather than to assume the container was sufficient.
