Spring Cloud

A set of projects for running many services, most of which were designed before container platforms existed. Several now duplicate something your platform does better, and one of them makes your application unable to start when a different service is down. This chapter is as much about which pieces to leave out as how to use them.

Gateway, when you use it
Route predicates and filters in Java, so you can do things an ingress cannot: exchange an opaque session cookie for a JWT at the edge, aggregate three calls into one response, rate-limit per API key with Redis, rewrite legacy paths. Note it is reactive — built on WebFlux — so chapter 7's rule applies absolutely: one blocking call in a filter stalls the whole gateway.
Config Server and @RefreshScope
Refreshable properties sound appealing and are subtle: a @RefreshScope bean is proxied and recreated on refresh, so anything holding a reference to the old instance keeps it, and half-applied configuration is possible mid-refresh. Prefer a rolling restart, which is fast, atomic and already automated.
Tracing across services
The one distributed concern with no alternative. Micrometer Tracing propagates traceparent through RestClient, the gateway, Kafka and the scheduler — chapter 15. Without it, a request spanning five services is five unrelated log streams.
Bulkheads
A separate pool per dependency, so one slow service cannot consume all your threads. Chapter 19 of the Backend unit, and with virtual threads the semaphore bulkhead is the relevant one rather than the thread-pool variety.

Self-check

  1. Which Spring Cloud components does a Kubernetes deployment usually make redundant?
    Service discovery and client-side load balancing, because Services plus DNS already resolve a name to healthy endpoints and remove failing ones. Config Server is usually redundant too, since ConfigMaps and Secrets mount as files that chapter 3's configtree import reads directly. What remains genuinely useful is Resilience4j — because fallback behaviour is application knowledge no platform can supply — and Gateway when you need routing logic expressed in code.
  2. Why is a Config Server a different kind of dependency from the others?
    Because it is a startup dependency. Your application fetches its configuration before the context is built, so if the config server is unreachable the application does not start at all — and during an incident that turns a restart, your most reliable recovery action, into something that cannot be performed. It also means a config server outage blocks every deployment across every service. Local defaults with fail-fast: false, or mounted files, remove the coupling.
  3. Why is Spring Cloud Gateway's reactive model worth knowing about?
    Because it runs on WebFlux with a handful of event-loop threads, and chapter 7's rule applies in full: a single blocking call in a custom filter — a JDBC lookup, a synchronous SDK, a blocking cache client — stalls a large share of the gateway's total capacity. And since every request to every service passes through it, the blast radius is the whole system rather than one endpoint. Custom filters must be non-blocking or use a separate scheduler.
  4. With the default ordering, how many downstream calls does one failing request make?
    Up to the retry count, because Retry is the outermost decorator: each attempt passes through the circuit breaker separately. That is usually what you want — the breaker counts every attempt, so it sees the real load and opens quickly, and once open the remaining attempts fail fast with CallNotPermitted instead of reaching the dependency. Inverting the order makes the breaker see only one failure per request, so it takes three times as many requests to open and the dependency absorbs three times the traffic meanwhile.
  5. Why should a retry never apply to a 4xx response?
    Because it will be a 4xx next time. A bad request, an unauthorised call or a validation failure is deterministic, so retrying wastes capacity — and during an incident it wastes capacity on the service already struggling. List the retryable exceptions explicitly rather than retrying everything; and remember from chapter 5 of the Backend unit that retrying a non-idempotent operation needs an idempotency key regardless of status.
  6. Why prefer a rolling restart to @RefreshScope?
    Because a refresh is neither atomic nor complete. Refresh-scoped beans are proxies recreated on the next call, so anything that captured a reference to the previous instance keeps the old configuration indefinitely, and during the refresh some beans have new values while others still have old ones. A rolling restart replaces instances with a known, uniform configuration and is already automated, tested and observable — chapter 21 of the Backend unit.
