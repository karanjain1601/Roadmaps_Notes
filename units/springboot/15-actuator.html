Actuator and observability

One dependency gives you health checks, metrics, traces and a dozen introspection endpoints. Two of the defaults will hurt you: a health probe that restarts your pods during a database blip, and a metric tag that multiplies your time series by your user count.

Health, and the probe that restarts everything

Take a dependency down
Then put the database in the liveness group
Liveness and readiness answer different questions

Liveness: is this process broken beyond recovery? Failing it means restart the container. So it must depend on nothing external — a deadlocked thread pool or an unrecoverable internal state, and nothing else. A liveness probe that checks the database converts a thirty-second database blip into every pod restarting simultaneously, all of them cold, all of them reconnecting at once. That is chapter 19 of the Backend unit, caused by a health check.

Readiness: can this instance serve traffic right now? Failing it means stop sending requests, without restarting. This one may check the things you cannot serve without. It is also what makes a rolling deploy safe — chapter 1's startup demo showed the process existing for seconds before the port opened.

Tracing, in two properties
Add micrometer-tracing-bridge-otel and an exporter, set a sampling probability, and Boot instruments the web layer, RestClient, JDBC, Kafka and the scheduler — propagating traceparent on the way out. Chapter 20 of the Backend unit for what to do with the traces.
The one log field that matters
Put the trace id in every line. Boot's default pattern includes it once tracing is on; with structured JSON logging (logging.structured.format.console: ecs in Boot 3.4) it becomes a queryable field. One id turns a support ticket into a log query across every service the request touched.
Custom health indicators
Implement HealthIndicator and it appears as a component automatically, named from the bean. Keep them fast and give them a timeout — a health endpoint that blocks on a slow dependency is itself a availability problem.
What to alert on
Not these metrics directly. Define an SLO on http.server.requests and alert on the burn rate — chapter 20 of the Backend unit. A dashboard full of green gauges nobody looks at is not observability.

Self-check

  1. Why must a liveness probe not check the database?
    Because failing liveness means restart the container. If the probe depends on the database, a brief database problem makes every pod fail simultaneously and every pod restart together — arriving cold, with empty caches, all reconnecting at once, which is likely to keep the database struggling. A recoverable thirty-second blip becomes a full outage. Liveness should reflect only unrecoverable internal state; dependencies belong in readiness, where failing merely removes the instance from the load balancer.
  2. What does readiness do that liveness does not?
    It stops traffic without restarting the process. That is the right response to a dependency being unavailable or to an instance still starting up — chapter 1 showed the process existing for seconds before the port could serve. It is also what makes a rolling deploy safe: new instances receive traffic only once they report ready, and an instance that loses a required dependency is quietly taken out of rotation and put back when it recovers.
  3. Why is /actuator/env dangerous even though values are masked?
    Because the masking is by key name — Actuator redacts keys matching password, secret, key, token and a few more, and prints everything else in full. A property called payments.api-credential or db.connection-string is shown verbatim. It also exposes your entire configuration surface, which is a map for an attacker. Put management endpoints on a separate port that your ingress does not route.
  4. Why does a user id in a metric tag cause a problem that a user id in a log does not?
    Because metrics store one time series per unique label combination, and every series carries its own history in memory and in the metrics store. Multiplying a few hundred series by your user count produces millions, which is enormous memory in the application, enormous cardinality in Prometheus, and queries that time out. A log line is a single record where a high-cardinality field costs nothing extra. Metrics answer "how many"; logs and traces answer "which one".
  5. Why must the URI tag be the template rather than the actual path?
    Because the actual path contains identifiers, so /api/orders/{id} becomes one series per order — unbounded cardinality growing with your data. Spring tags with the matched template by default, which is correct; the failure mode is custom instrumentation using request.getRequestURI(), or an endpoint whose path variable is not part of a mapping template. The symptom is a metrics store that grows without limit and no obvious culprit.
  6. Why enable a percentile histogram instead of publishing percentiles directly?
    Because percentiles cannot be aggregated. A per-instance p99 is meaningless across a fleet — you cannot average them, as chapter 20 of the Backend unit explains. Publishing bucket counts lets Prometheus combine the underlying distributions and compute a true fleet-wide percentile at query time. Client-side percentiles are only correct for a single instance, and are actively misleading on a dashboard labelled with the service name.
