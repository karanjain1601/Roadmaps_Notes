Performance and startup

Two questions with unrelated answers. Startup time is almost entirely a function of how much is on your classpath, and there is a ladder of fixes with clear trade-offs. Request latency, once the obvious query problems are gone, usually comes down to one number: how many database connections you have.

Measure with the tools already in the application

/actuator/startup gives you a timed tree of every bean and auto-configuration — chapter 1's waterfall for your own application. /actuator/metrics/hikaricp.connections.pending tells you whether requests are queueing for connections. Hibernate's generate_statistics gives query counts per session. Beyond that, async-profiler or JFR for a flame graph. All of this takes minutes and beats any amount of reasoning about what is probably slow.

A bigger pool is usually the wrong lever

The database has fixed parallelism — a rough starting point is (cores × 2) + effective_spindles, so around twenty for an eight-core machine. Beyond that, concurrent queries contend for cores, buffers and locks and everything slows together, so raising the pool moves the queue from your application, where it is visible and boundable, into the database, where it is neither. If hikaricp.connections.pending is high, the answer is almost always fewer or faster queries — not more connections. Chapter 4 of the Backend unit.

Cache managerTrade
Caffeine — in processNanoseconds, no network. Each instance has its own copy, so eviction on one does not affect the others — fine for immutable or briefly-stale data, wrong for anything that must be consistent
Redis — sharedOne copy, evict once, works across instances. A network round trip per lookup, so it must be beating something substantially slower to be worth it
Both, layeredCaffeine in front of Redis. Fast and shared, and now with two invalidation paths and a consistency window on each instance
ConcurrentMapCacheManagerBoot's fallback when nothing else is on the classpath. No eviction, no size limit, no TTL — an unbounded memory leak with a cache-shaped API
@Async executors
Configure one. Define a ThreadPoolTaskExecutor with a bounded queue and a rejection policy, or turn on virtual threads — chapter 7. Also: an @Async method returning void swallows its exception unless you register an AsyncUncaughtExceptionHandler. Return CompletableFuture and the caller can see failures.
JVM in a container
Modern JVMs are container-aware and take 25% of the memory limit as heap by default, which is usually too little. Set -XX:MaxRAMPercentage=75. Use G1 as the default and consider ZGC only for large heaps with strict pause requirements. Never set -Xmx to the container limit — the JVM needs metaspace, code cache, thread stacks and direct buffers outside the heap.
Native images
Startup in tens of milliseconds and a fraction of the memory, in exchange for a build measured in minutes, no runtime reflection unless declared, no dynamic class loading, and libraries needing hints. Excellent for functions, CLIs and short-lived workloads; rarely worth it for a long-running service where startup happens once a day. Chapter 19.

Self-check

  1. Why is the total connection count across the fleet the number that matters?
    Because the database enforces a global limit, and every instance opens its own pool. Ten instances with a pool of twenty request two hundred connections; a Postgres configured for a hundred refuses half of them, so instances fail to fill their pools and requests error at startup or under load. Pool size has to be decided as instances × pool, with headroom left for migrations, admin sessions and monitoring — not chosen per instance in isolation.
  2. Requests are queueing for connections. Why is a bigger pool usually wrong?
    Because the database's parallelism is fixed by its cores and disks — roughly (cores × 2) + spindles. Beyond that, more concurrent queries contend for the same resources and everything slows together, so you have moved the queue out of your application, where it was bounded and visible, into the database, where it is neither. Pending connections mean too many or too slow queries; fix those and the queue disappears.
  3. Why is REQUIRES_NEW inside a transaction a pool hazard?
    Because the outer transaction is suspended but keeps its connection while the inner one takes a second, so each request in that path holds two simultaneously. The effective pool is halved — and worse, if concurrency reaches the pool size every thread can hold one connection and wait for another that will never be released, which is a genuine deadlock resolved only by the connection timeout. Chapter 11.
  4. What does spring.main.lazy-initialization cost you?
    Fail-fast behaviour. Beans are created on first use, so a misconfiguration that would have stopped the context from starting now surfaces as a 500 on the first request that touches it — possibly in production, possibly hours after the deploy. The first request to each path also pays the construction cost. It is a good development-time setting and a poor production one; excluding unused auto-configurations and trimming the classpath gives you real startup savings without moving errors to runtime.
  5. Why cache DTOs rather than entities?
    Because an entity is a managed object with lazy proxies attached to a persistence context that no longer exists by the time it is read from the cache — so touching an association throws, and the object may be stale in ways dirty checking would have caught. You are also caching far more than you need, including every mapped column. A DTO is an immutable value with no framework attachment, which is exactly what a cache should hold.
  6. Why evict a cache entry after commit rather than when the method returns?
    Because @CacheEvict fires at method exit, which is before the transaction commits. In that window the row still holds its old value, so a concurrent reader can miss the cache, read the pre-commit state and repopulate the entry — leaving a stale value with a full TTL ahead of it. A @TransactionalEventListener(phase = AFTER_COMMIT) evicts only once the new value is actually visible, which is chapter 13 of the Backend unit applied through Spring's event mechanism.
