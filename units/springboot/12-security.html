Spring Security

Add one dependency and every endpoint in the application returns 401, with a generated password printed on the console. Nothing you wrote has changed. Spring Security is a chain of servlet filters that runs entirely in front of your code, and it is comprehensible the moment you stop looking for it inside your controllers.

It is filters, all the way down

The chain Boot builds for you
Switch to a stateless JWT API and watch six filters disappear
Why security errors do not match your API's error format

Every one of those filters runs before the DispatcherServlet, so an authentication or authorisation failure is thrown outside the scope of your @ControllerAdvice — chapter 5. Spring Security has its own two hooks instead: an AuthenticationEntryPoint for 401 and an AccessDeniedHandler for 403. If you want a consistent ProblemDetail body across the whole API, you must wire both of them explicitly, and it is the step almost everyone forgets until a client complains that one endpoint returns a different error shape.

Configuration

java — a stateless JSON API, in full
@Configuration
@EnableWebSecurity
@EnableMethodSecurity                       ← enables @PreAuthorize
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .securityMatcher("/api/**")             ← this chain handles only /api.
                                                      Several chains are allowed;
                                                      the first matching one wins
            .authorizeHttpRequests(a -> a
                .requestMatchers("/api/public/**").permitAll()   ← SPECIFIC
                .requestMatchers(HttpMethod.GET, "/api/orders/**")     RULES
                    .hasAuthority("SCOPE_orders:read")               FIRST.
                .requestMatchers("/api/admin/**").hasRole("ADMIN")    Order is
                .anyRequest().authenticated())                      everything

            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))

            .sessionManagement(s -> s
                .sessionCreationPolicy(STATELESS))  ← no session, no JSESSIONID

            .csrf(AbstractHttpConfigurer::disable)  ← safe ONLY because there is
                                                      no cookie auth. See below
            .exceptionHandling(e -> e
                .authenticationEntryPoint(problemDetail401)   ← so 401 and 403
                .accessDeniedHandler(problemDetail403))         match your API
            .build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
    // stores hashes prefixed with the algorithm: {bcrypt}$2a$10$…
    // so you can migrate to Argon2 later without invalidating every
    // existing password. Chapter 14 of the Backend unit.
}
SettingWhen it is right
csrf().disable()Only when no browser-managed credential authenticates the request. A bearer token in a header is not sent automatically, so there is nothing to forge. With cookie or session auth, disabling CSRF is a vulnerability — chapter 15 of the Backend unit
WebSecurityCustomizer.ignoring()Almost never. It removes the path from the chain entirely, so no headers, no CORS, no logging — and if the pattern is wider than you meant, you have silently unprotected it. Use permitAll(), which still runs the chain
SessionCreationPolicy.STATELESSAny token-based API. Removes six filters and the session store
hasRole("ADMIN")Note it prepends ROLE_, so the authority must be ROLE_ADMIN. hasAuthority does not. Mixing them up is the most common reason a correct-looking rule denies everyone
permitAll() on actuatorNever as a blanket. /actuator/health is fine; /actuator/env and /actuator/heapdump are a credential dump — chapter 15

Authorisation, and why order decides everything

Which rule matches?
Flip the ordering and watch a rule become unreachable
java — method security, and the part it cannot do
@PreAuthorize("hasRole('ADMIN')")
void deleteAll() { … }

@PreAuthorize("#userId == authentication.name or hasRole('ADMIN')")
Profile get(String userId) { … }      ← the argument in the expression

@PostAuthorize("returnObject.ownerId == authentication.name")
Order find(UUID id) { … }
// ✗ this loads the row, then throws. The work is already done, any
//   lazy loading has happened, and in a transaction it will roll back.
//   Post-authorisation is a last resort.

// ✓ what you actually want — chapter 14 of the Backend unit:
@Query("select o from Order o where o.id = :id and o.ownerId = :owner")
Optional<Order> findOwned(UUID id, String owner);
//   scope the query. The row is never fetched, and "not yours" is
//   indistinguishable from "not there" — so return 404, not 403.

// and remember chapter 6: @PreAuthorize is a proxy. Public methods
// only, and a call from inside the same class is unchecked.
Request matchers or method security?
Matchers for coarse, path-shaped rules — everything under /api/admin needs a role. Method security for anything that depends on the arguments or the domain. Use both; they answer different questions.
Neither can enforce data ownership
A rule saying "authenticated users may read orders" does not stop user A reading user B's order. That check has to live in the query, and it is the most common serious API flaw there is.
Roles against authorities
Spring has one concept — a GrantedAuthority string. "Roles" are just authorities that start with ROLE_, and hasRole("ADMIN") adds the prefix for you while hasAuthority does not. Pick one convention per codebase and write it down.
The authentication object
SecurityContextHolder is a ThreadLocal, which is why it works in MVC, needs propagation for @Async, and does not exist at all in WebFlux — chapter 7. Prefer injecting the principal as a controller parameter over reaching for the holder.

Self-check

  1. You add the security starter and every endpoint returns 401. Why, and what created that behaviour?
    Auto-configuration. With the security classes on the classpath and no SecurityFilterChain bean of your own, @ConditionalOnMissingBean lets Boot create a default one that requires authentication for every request, enables form login and basic auth, and generates a password printed at startup. It is secure-by-default rather than a bug — and it disappears the moment you define your own chain, which is chapter 4's override mechanism.
  2. Why don't security failures go through your @ControllerAdvice?
    Because the security filters run before the DispatcherServlet, and advice lives inside it. The exception is thrown while the request is still in the filter chain, so the container's error handling deals with it and produces a body that does not match the rest of your API. Spring Security's own hooks are the answer: an AuthenticationEntryPoint for 401 and an AccessDeniedHandler for 403, both wired to emit the same ProblemDetail shape.
  3. When is csrf().disable() safe?
    When no credential is attached to the request by the browser automatically. A bearer token in an Authorization header has to be added by JavaScript, so an attacker's page cannot cause an authenticated request — there is nothing to forge. If any part of the application authenticates with a cookie or a session, disabling CSRF is a real vulnerability, and "it's a REST API" is not a defence when the session cookie is still being sent.
  4. Why does rule order matter, and what is the failure mode?
    Because matchers are evaluated top to bottom and the first match decides — no later rule is consulted. So a broad pattern placed above a specific one makes the specific one unreachable: /api/** requiring authentication above /api/public/** permitting all means the public endpoints require authentication, and nothing warns you. Always order from most specific to most general, and test the negative cases as well as the positive ones.
  5. Why is WebSecurityCustomizer.ignoring() worse than permitAll()?
    Because it removes the path from the filter chain entirely rather than allowing it through. No security headers, no CORS handling, no CSRF token, and no authentication is even attempted — so if the pattern is broader than intended you have silently unprotected real endpoints, and nothing in the chain will log that a request went by. permitAll() still runs every filter and simply authorises the request.
  6. Why can neither a request matcher nor @PreAuthorize enforce data ownership?
    Because both decide before the data is known. A matcher sees a path and a method; @PreAuthorize sees the arguments. Neither knows who owns order 7c3a until it is loaded. @PostAuthorize can check afterwards, but by then the row is fetched and the work done. The only reliable place is the query itself — scope by owner or tenant so the row is never returned, and answer 404 rather than 403 so identifiers cannot be enumerated.
