Associations and the N+1 problem

The single most common performance defect in Spring applications, and the reason is structural: JPA makes fetching a related object look exactly like reading a field. A loop over a hundred orders that touches order.getCustomer() is a hundred and one queries, and the code contains no SQL at all.

List<OrderRow> rows(Status s);
Why EAGER is not the fix

It sounds like the answer and it is not, for two reasons. It does not produce a join for query results. Hibernate runs your JPQL, gets a hundred orders, and then satisfies each one's eager association with a separate select — the same N+1, now unavoidable. And it applies everywhere, forever: every query touching that entity drags the association along, including the endpoint that only needed the id. Fetching is a property of the use case, not of the mapping. Map everything LAZY and decide per query. Note that @ManyToOne and @OneToOne default to EAGER, so you must write it out.

Bidirectional associations and cascades

java — the owning side, and keeping both sides honest
@Entity
class Order {
    @OneToMany(mappedBy = "order",       ← the INVERSE side. mappedBy means
                cascade = ALL,             "the other end owns the FK"
                orphanRemoval = true)
    private final List<OrderLine> lines = new ArrayList<>();

    // always provide these. Setting one side only means the in-memory
    // graph and the database disagree until the context is cleared.
    void addLine(OrderLine line) {
        lines.add(line);
        line.setOrder(this);            ← the side that actually writes
    }                                      the foreign key column
    void removeLine(OrderLine line) {
        lines.remove(line);
        line.setOrder(null);
    }
}

@Entity
class OrderLine {
    @ManyToOne(fetch = LAZY, optional = false)   ← the OWNING side. This
    @JoinColumn(name = "order_id")                  is the FK column
    private Order order;
}

A statement-count assertion is worth more than any of this advice

The reason N+1 ships is that it is invisible: three fixture rows in a test make three extra queries, which takes two milliseconds. Wire Hibernate's statistics or a datasource proxy into your tests and assert the count — assertThat(queryCount()).isEqualTo(2). It fails the moment somebody adds a getCustomer() call in a mapper, which is exactly when you want to know. This is the mechanical version of the advice in chapter 12 of the Backend unit, and it is the only defence that keeps working after everyone who read this chapter has left.

Self-check

  1. Why does the N+1 problem survive code review in a JPA codebase?
    Because there is no SQL in the code. order.getCustomer().getName() is syntactically identical to reading a field in memory, and the query is issued by a proxy when the getter runs — often in a mapper or a template, far from the repository call. Tests pass in milliseconds against three fixture rows. The reliable defence is mechanical: assert the statement count in a test so it fails the moment somebody adds a getter call.
  2. Why doesn't fetch = EAGER fix it?
    Two reasons. It does not produce a join for query results — Hibernate runs your JPQL, gets the root entities, then issues a separate select per row to satisfy each eager association, so the N+1 remains and is now impossible to avoid. And it applies globally: every query touching that entity drags the association along, including endpoints that only needed the id. Fetching belongs to the use case, so map LAZY and decide per query with an entity graph or a join fetch.
  3. What is MultipleBagFetchException and what causes it?
    Hibernate refusing to fetch two bags — List collections with no order column — in one query, because the cartesian product would produce duplicate elements it cannot distinguish or deduplicate. It is thrown at startup, which is merciful. Changing both to Set makes it work, at the cost of a genuine cartesian product in rows; fetching one and batch-loading the other is usually better.
  4. Why is @BatchSize often the best-value change in a JPA application?
    Because it converts N individual lazy loads into ⌈N/size⌉ queries with an in (…) predicate, without touching any calling code, without changing fetch types and without multiplying rows the way a join fetch does. Set hibernate.default_batch_fetch_size: 50 globally and every lazy association in the application improves at once. It does not eliminate the extra queries, but it turns a hundred into two.
  5. What is the difference between cascade = REMOVE and orphanRemoval = true?
    REMOVE fires only when the parent itself is deleted, cascading the delete to its children. orphanRemoval fires when a child is taken out of the collection — the row is deleted because nothing owns it any more. Most people who write cascade = ALL actually want orphan removal, since the behaviour they expect is that removing a line from an order deletes that line. Both only make sense for genuine composition.
  6. Why keep both sides of a bidirectional association in sync manually?
    Because only the owning side writes the foreign key, so setting the inverse collection alone persists nothing — and setting the owning side alone leaves your in-memory collection wrong for the rest of the transaction. The two disagree until the context is cleared and the graph is reloaded, which is why the bug appears intermittently and usually in a later method. Encapsulate it in addLine/removeLine methods and never touch the collection directly.
