The container and dependency injection

The first of the three mechanisms. You stop writing new for anything with collaborators, declare what each class needs, and a container works out the construction order and does it once at startup. Most of what follows in the unit only makes sense once this part is boring.

Beans and how they get defined

A bean is an object the container built and manages. There are exactly two ways to tell it about one, and choosing between them is the first decision in any Spring codebase.

java — the two ways, and when each is right
// ① annotate your own class, and let scanning find it
@Service
class OrderService {
    private final OrderRepository repo;
    private final Mailer mailer;

    OrderService(OrderRepository repo, Mailer mailer) {   ← constructor injection.
        this.repo = repo;                                no annotation required
        this.mailer = mailer;                            when there is one
    }                                                       constructor
}
// @Component, @Service, @Repository and @Controller are the same thing
// to the container. The difference is documentation — plus @Repository,
// which also translates persistence exceptions into Spring's hierarchy.

// ② declare a bean for a class you do not own
@Configuration
class HttpConfig {

    @Bean
    RestClient paymentsClient(PaymentProperties props) {   ← parameters are
        return RestClient.builder()                          injected too
            .baseUrl(props.baseUrl())
            .requestFactory(timeouts(props.timeout()))
            .build();
    }
}
// use @Bean for third-party types, for anything needing construction
// logic, and for several instances of one type. Use @Component for
// your own classes. Mixing them arbitrarily is the usual mess.
Injection styleVerdict
ConstructorThe right answer. Dependencies are explicit and final, the object is never in a half-built state, a missing bean fails at startup rather than at first use, and the class is trivially testable with new — no container, no reflection
SetterFor genuinely optional dependencies, and for reconfiguration after construction. Rare
Field @AutowiredAvoid. Fields cannot be final, the class cannot be constructed in a test without reflection, and — the real problem — it hides how many dependencies a class has, so a constructor that would embarrass you at eight parameters silently reaches fifteen
The argument that actually settles it

A constructor with too many parameters is useful information: it is telling you the class does too much. Field injection removes that signal, which is precisely why it feels tidier. The other benefit is subtler — with constructor injection the container cannot create a bean whose dependency is missing, so wiring errors surface during startup with a clear message. With field injection the object exists with a null field and fails later, somewhere else, under load.

Resolution, and circular dependencies

The container building your object graph
Introduce a cycle and compare the two injection styles
A circular dependency is a design message, not a configuration problem

Since Boot 2.6 circular references are rejected by default, and spring.main.allow-circular-references=true exists so you can unblock an upgrade — not so you can keep them. Two classes that each need the other are one responsibility split in the wrong place. The three honest fixes: extract the shared behaviour into a third class both depend on; invert one direction with an event, so the publisher does not know its listener (chapter 17); or merge them, because they were one thing. Injecting an ObjectProvider to defer the lookup works and leaves the cycle in place.

java — when several beans satisfy one type
// two implementations, and an injection point that cannot choose
@Service @Primary                       ← the default winner
class StripeGateway implements PaymentGateway { }

@Service @Qualifier("legacy")
class WorldpayGateway implements PaymentGateway { }

class Checkout {
    Checkout(PaymentGateway gateway,                          ← gets Stripe
             @Qualifier("legacy") PaymentGateway fallback) { }   ← gets Worldpay
}

// injecting ALL of them is often better than choosing one:
class Router {
    private final Map<String, PaymentGateway> byName;   ← keyed by bean name
    private final List<PaymentGateway> all;            ← ordered by @Order

    Router(Map<String, PaymentGateway> byName, List<PaymentGateway> all) { … }
}
// this is the strategy pattern with the registration deleted: adding a
// new gateway is a new @Service and no change to Router. It is the most
// underused feature of the container.

Singletons are shared, so they must be stateless

Every controller, service and repository in a Spring application is one object serving every concurrent request. A mutable field on a @Service is shared mutable state across threads — and it will work perfectly in development, where requests arrive one at a time. Keep per-request state in method parameters and local variables. If you genuinely need a shared mutable field, it must be thread-safe by construction: an AtomicLong, a ConcurrentHashMap, or something behind a lock.

java — the @Configuration trick worth knowing
@Configuration
class AppConfig {

    @Bean DataSource dataSource() { return buildPool(); }

    @Bean OrderRepository orderRepository() {
        return new JdbcOrderRepository(dataSource());   ← a plain method call…
    }                                                    …that does NOT build a
    @Bean AuditRepository auditRepository() {           second pool. Both get
        return new JdbcAuditRepository(dataSource());     the same singleton
    }
}
// Spring subclasses @Configuration classes with CGLIB and intercepts
// every @Bean method, so a direct call returns the container's instance
// rather than executing the method again. This is "full" mode.
//
// @Configuration(proxyBeanMethods = false) turns it off — faster startup
// and no CGLIB, at the cost of this behaviour. Boot's own auto-config
// classes all set it, and they take dependencies as method parameters
// instead. Do the same and the question stops arising.

Self-check

  1. Why is constructor injection preferred over field injection?
    Dependencies become explicit and final, the object is never half-built, and a missing bean fails at startup with a clear message rather than as a null field later. The class can also be constructed with new in a test, with no container and no reflection. The subtler benefit is that a constructor with twelve parameters is visibly wrong, which tells you the class does too much — field injection hides exactly that signal.
  2. When should you use @Bean rather than @Component?
    When you do not own the class — a third-party client, a DataSource, an ObjectMapper — since you cannot annotate it. Also when construction needs logic, when you want several beans of the same type configured differently, or when the instance depends on properties. @Component is for your own classes, where scanning can find them. Using @Bean for everything produces enormous configuration classes; using @Component where you cannot annotate is impossible.
  3. Two beans implement one interface and injection fails. What are the options?
    Mark one @Primary so it wins by default; use @Qualifier at the injection point to name a specific one; or inject them all — a List ordered by @Order, or a Map keyed by bean name. The last is usually the best answer when the choice is per-request rather than fixed: it gives you the strategy pattern with the registration step deleted, so adding an implementation requires no change to the consumer.
  4. Why does Spring reject circular dependencies by default, and what are the real fixes?
    Because with constructor injection there is no valid order — each bean needs the other completed before it can be built — and because the cycle almost always signals a misplaced boundary. allow-circular-references=true exists to unblock an upgrade, not as a solution. The genuine fixes are to extract the shared behaviour into a third class, to invert one direction using an application event so the publisher does not know its listener, or to merge the two because they were one responsibility.
  5. Why must a @Service be stateless?
    Because it is a singleton: one instance serves every concurrent request, so a mutable field is shared across threads with no synchronisation. It works flawlessly in development, where requests arrive one at a time, and corrupts data under real concurrency. Keep per-request state in parameters and locals; if a field genuinely must be shared, make it thread-safe by construction — an atomic, a concurrent collection, or something behind a lock.
  6. What happens if you inject a prototype bean into a singleton?
    You get exactly one instance — created when the singleton was constructed and kept forever. Injection happens once, so the prototype scope has no opportunity to apply, and the bean is effectively a singleton with a misleading annotation. To get a fresh instance per use you must ask the container each time: inject an ObjectProvider and call getObject(), use @Lookup, or declare a scoped proxy so each call is delegated to a new instance.
