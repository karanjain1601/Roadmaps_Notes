Transactions

One annotation with eight attributes, two of which will eventually cost you data. Chapter 10 of the Backend unit covered what transactions guarantee; this chapter is about the specific way Spring exposes them — including the default that commits your work after an exception.

— words— min read2 interactivesNeeds: chapters 06, 09 · Backend ch 10

Where the boundary goes

On the service method
One transaction per use case. It is the unit of work the business cares about, and it is the level where "all of this or none of it" is a meaningful statement.
Not on the repository
Spring Data already wraps each repository call in a transaction, so annotating them gives you one per statement — which is the opposite of what you want. Two repository calls in a service method with no boundary above them are two independent transactions.
Not on the controller
It keeps a database connection open for the whole request, including serialisation and any HTTP call the handler makes. This is what open-session-in-view does by default, and it is why the property below matters.
Remember it is a proxy
Everything in chapter 6 applies: public methods only, no self-invocation, no final, and not during construction. A @Transactional method called from within the same class does nothing at all.

Rollback rules

Does it roll back?
Try the checked exception
java — the two settings worth writing every time
// ✗ the default: unchecked exceptions and Errors roll back,
//   CHECKED exceptions commit. A rule inherited from EJB in 1999.
@Transactional
public void transfer(…) throws InsufficientFundsException { … }
//   throws → the debit is committed and the credit is not. Silently.

// ✓ say what you mean
@Transactional(rollbackFor = Exception.class)
public void transfer(…) throws InsufficientFundsException { … }

// ✓ or avoid the question: make domain exceptions unchecked. Most
//   modern Java does, and it removes the trap for everyone after you.
class InsufficientFundsException extends RuntimeException { }

// ✓ and mark every read path
@Transactional(readOnly = true)
public List<OrderRow> search(…) { … }
//   skips dirty checking and snapshots, prevents accidental writes,
//   and routes to a replica if you have one configured. Chapter 9.

Two things about REQUIRES_NEW

It uses a second connection. The outer transaction is suspended but still holds its connection, so a method using REQUIRES_NEW occupies two simultaneously. Do this in a loop and a pool of twenty deadlocks with ten concurrent requests — each holding one and waiting for another. Chapter 4 of the Backend unit.

The two cannot see each other. The inner transaction cannot read the outer's uncommitted rows, so a "log this attempt even if the operation fails" pattern works, but an inner transaction that needs to read what the outer just wrote will not find it — and may block on its locks instead.

Locking, and the connection you are holding

java — optimistic first, pessimistic when you must
// ✓ optimistic: one column, no locks held, and it catches the lost
//   update from chapter 10 of the Backend unit
@Entity
class Order {
    @Version private long version;      ← Hibernate adds it to the where
}                                         clause and increments on write

//   update orders set status=?, version=4 where id=? and version=3
//   → 0 rows updated → OptimisticLockException. Retry the whole
//     transaction; do not retry the update, because your entity is
//     now stale.

// ✓ pessimistic, when the conflict is likely and retrying is wasteful
@Lock(LockModeType.PESSIMISTIC_WRITE)         ← select … for update
@Query("select s from Stock s where s.sku = :sku")
Optional<Stock> findForUpdate(String sku);

// ✓ and best of all, where the new value is a function of the old:
@Modifying
@Query("update Stock s set s.qty = s.qty - :n where s.sku = :sku and s.qty >= :n")
int reserve(String sku, int n);
//   one atomic statement, no lock held across a round trip, no retry
//   loop, and the row count tells you whether it succeeded.
Never do these inside a transaction
  • An HTTP call. A three-second timeout on a payment gateway is three seconds holding a pooled connection and any locks you have taken. Twenty concurrent requests exhaust the pool and the whole application stops — chapter 19 of the Backend unit, arriving through JPA.
  • Publishing to a broker. If the transaction rolls back the message has already gone. Use the outbox pattern from chapter 18 of the Backend unit, or a TransactionalEventListener(phase = AFTER_COMMIT) — chapter 17.
  • Sending an email or a webhook. Same reason, and it cannot be un-sent.
  • Sleeping, or waiting on a lock or a queue. The transaction lives as long as the thread does.
LazyInitializationException
Touching a lazy association after the transaction ended. The context closed, the proxy has nothing to load from, and the throw happens wherever the getter was called — usually a mapper or a serialiser, far from any repository code.
Open-session-in-view
Boot's default binds the EntityManager to the whole request, so lazy loading keeps working in the view layer and the exception never appears. It also holds a connection for the entire request and fires unpredictable queries during serialisation. Set spring.jpa.open-in-view: false, and take the exceptions as a map of where your fetching is wrong.
Then fix them properly
Fetch what the use case needs inside the transaction — an entity graph, a join fetch or a projection — and map to a DTO before returning. Chapter 10. The lazy exception is a design signal, not an obstacle.
After-commit work
@TransactionalEventListener(phase = AFTER_COMMIT) runs only if the transaction actually committed, which is the correct place for cache invalidation, notifications and anything that must not happen on rollback. Chapter 13 of the Backend unit on invalidating after commit rather than before.

Self-check

  1. Why does a checked exception commit the transaction by default?
    Because Spring inherited the EJB convention: unchecked exceptions and Error mean "something unexpected went wrong" and roll back, while checked exceptions are treated as an anticipated outcome the caller will handle, so the work is kept. It is almost never what you want — a business rule violation should not leave a half-completed operation persisted. Either declare rollbackFor = Exception.class or make domain exceptions unchecked.
  2. Why annotate the service method rather than the repository?
    Because the transaction should span the use case. Spring Data already wraps each repository call in its own transaction, so annotating repositories gives you one per statement — and a service method calling two repositories then performs two independent transactions with a window in between where the data is inconsistent. The service method is the level at which "all of this or none of it" describes something the business would recognise.
  3. An inner REQUIRED method throws, the outer catches it and continues. What happens at commit?
    UnexpectedRollbackException. There was only ever one physical transaction, and when the inner interceptor saw the exception it marked that transaction rollback-only. Catching the exception does not clear the mark, so the outer method runs to completion, requests a commit, and gets told the transaction was already doomed. The fix is either not to catch it, or to give the inner method REQUIRES_NEW so its failure is genuinely separate.
  4. What does REQUIRES_NEW cost?
    A second connection. The outer transaction is suspended but keeps its connection, so both are held simultaneously — and a loop using REQUIRES_NEW can deadlock a pool of twenty with ten concurrent requests, each holding one and waiting for another. The two transactions also cannot see each other's uncommitted work, so an inner transaction that needs to read what the outer just wrote will not find it, and may block on its locks.
  5. Why is NESTED rarely usable in a Spring Boot application?
    Because it needs JDBC savepoints, and JpaTransactionManager — what you get with spring-boot-starter-data-jpa — does not support them. Requesting it throws NestedTransactionNotSupportedException at runtime. Savepoints do work with DataSourceTransactionManager, so plain JDBC or Spring Data JDBC can use it, but with JPA the choice is effectively between joining and starting a separate transaction.
  6. Why turn off open-session-in-view when it prevents an exception?
    Because it prevents the exception by keeping a database connection open for the entire request, including serialisation and any outbound HTTP call — so the pool is held far longer than the work requires. It also lets lazy loading fire queries during response writing, at a point where you have no visibility and no transaction boundary. Turning it off makes every place your fetching is wrong throw, which is a map of what to fix with entity graphs and projections.
