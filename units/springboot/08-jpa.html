Spring Data JPA

You declare an interface and never implement it. At startup Spring generates a class that satisfies it, parsing your method names into queries — which is delightful for the first twenty methods and then quietly becomes the thing you are fighting. This chapter is about knowing where that line is.

Repositories

A repository per aggregate, not per table

Extending JpaRepository everywhere publishes findAll(), deleteAll() and save() on every entity in the system, including the ones that should only ever be reached through their parent. An OrderLine repository is usually a mistake: lines belong to an order, and their lifecycle should be managed through it. Starting from plain Repository and adding the four methods you actually need costs nothing and keeps the aggregate boundary real — chapter 17 of the Backend unit.

When to stop deriving

The name is the query, so a complicated query becomes an unreadable name — findByStatusInAndCreatedAtBetweenAndCustomerCityIgnoreCaseOrderByTotalDesc is a real method somebody wrote, and nobody can see what it does. Two or three predicates is the practical ceiling; past that use @Query with a named query you can read, or a Specification if the predicates are genuinely dynamic. Derived methods also have no way to express a projection, a join fetch, or a window function — so as soon as performance matters you are writing the query anyway.

List<Order> findByStatus(Status s);

// ② closed interface projection — Spring generates the select list
interface OrderSummary {
    UUID getId();
    BigDecimal getTotal();
    String getCustomerName();          ← traverses the association and

List<OrderSummary> findByStatus(Status s);   ← same method, new return type

Two paging traps

Offset paging is offset paging. Pageable generates limit … offset …, so page 5,000 reads 100,020 rows to return 20, and rows shift under the user between requests. Chapter 5 of the Backend unit — keyset pagination requires a @Query with a where (createdAt, id) < (:ts, :id) predicate, and Spring Data will not derive it for you.

Paging a query with a join fetch on a collection. The join multiplies rows, so limit 20 truncates mid-entity. Hibernate detects this, logs "firstResult/maxResults specified with collection fetch; applying in memory", and then fetches the entire result set into heap and pages it there. It works, right up to the day the table is large. Chapter 10.

@Modifying queries
A bulk update or delete bypasses the persistence context entirely, so managed entities keep their stale values. Use @Modifying(clearAutomatically = true, flushAutomatically = true), and be aware that clearing detaches everything — including entities the caller is still holding.
Specification and the Criteria API
For genuinely dynamic predicates — a search screen with eight optional filters. Composable and type-checked; also verbose enough that people build a small DSL over it. QueryDSL is the nicer alternative if you can accept the code generation.
Where JPA stops
Reporting queries, window functions, CTEs, bulk upserts, anything with on conflict. Use JdbcClient (Boot 3.2) or jOOQ alongside JPA in the same transaction — they share the connection. Fighting the ORM to express a query SQL expresses cleanly is a losing trade every time.

Self-check

  1. How does a repository interface with no implementation become a working bean?
    A BeanFactoryPostProcessor runs during startup — before any bean is constructed — finds interfaces extending Spring Data's marker types, and registers a factory bean for each. That factory produces a proxy whose calls are handled by SimpleJpaRepository for the inherited methods, by a parsed query for derived methods, and by your JPQL for @Query methods. Nothing is generated at compile time and there is no implementation class to find.
  2. Why is extending JpaRepository for every entity a bad default?
    Because it publishes the full CRUD surface — including findAll, deleteAll and save — on entities that should only be reachable through their aggregate root. An OrderLine repository invites code that modifies lines without going through the order, which is precisely where invariants get broken. Starting from plain Repository and declaring the few methods you need keeps the boundary meaningful and costs nothing.
  3. What does IgnoreCase in a derived method name cost?
    The index. It generates upper(column) = upper(?), and a plain B-tree index on the column cannot satisfy a predicate on a function of it, so you get a sequential scan. The fixes are a functional index on upper(column), a case-insensitive collation, or storing a normalised copy of the column. The same applies to Containing, which produces a leading wildcard.
  4. Why is deleteByCreatedAtBefore slower than you would expect?
    Because a derived delete is not a bulk delete. Spring loads every matching entity into the persistence context and removes them one at a time, so deleting 50,000 rows is one select plus 50,000 individual deletes — and it fires lifecycle callbacks and cascades for each, which is sometimes exactly why you want it. For a genuine bulk delete write @Modifying @Query("delete from Order o where …"), and accept that callbacks and cascades will not run.
  5. What is wrong with an open interface projection using @Value?
    It cannot be pushed down into SQL. A closed projection lets Spring build a select list containing only the columns the accessors need; an open one has a SpEL expression Spring cannot translate, so it fetches the entire entity — with all its associations — and evaluates the expression in Java. You keep the narrow-looking interface and lose every benefit it appeared to give, silently.
  6. Why does paging a query with a collection join fetch misbehave?
    Because the join multiplies rows — one order with four lines is four rows — so a SQL limit would cut an entity in half. Hibernate detects the combination, warns that first/max results are being applied in memory, and then fetches the whole result set into heap to paginate there. It is correct and it does not scale; the answer is to page the root ids in one query and fetch the collections for that page in a second.
