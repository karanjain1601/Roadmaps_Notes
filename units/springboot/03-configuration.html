Configuration and profiles

One property system, a dozen sources and a defined precedence order that almost nobody can recite — which is why "it works locally" is so often a configuration question rather than a code one. This chapter is mostly about being able to answer where did that value come from in under a minute.

— words— min read2 interactivesNeeds: chapter 02

Where a value comes from

Every property is looked up across an ordered list of sources and the highest one that has it wins. The order is fixed, documented, and worth internalising once rather than rediscovering during an incident.

Rather than reasoning about the order, ask the application. /actuator/env/app.timeout returns every source that defines the property and which one won — chapter 15. In a test or a breakpoint, ((ConfigurableEnvironment) env).getPropertySources() prints the live list in order. Both take thirty seconds and remove the guesswork entirely.

Reading configuration in code

java — @Value, and the thing you should use instead
// ── @Value: fine for one-off scalars, and it scales badly ──
@Service
class PaymentClient {
    @Value("${payments.base-url}")          ← a typo here is a startup failure
    private String baseUrl;                    with a readable message, at least

    @Value("${payments.timeout:PT2S}")      ← :default after the colon
    private Duration timeout;
}
// problems: no validation, no grouping, no IDE completion, no single
// place that documents what this component needs, and field injection
// again — so the class cannot be built in a test without a container.

// ── @ConfigurationProperties: type-safe, validated, grouped ──
@ConfigurationProperties(prefix = "payments")
@Validated
record PaymentProperties(
        @NotBlank String baseUrl,          ← binds from payments.base-url
        @DefaultValue("PT2S") Duration timeout,
        @Min(1) @Max(10) int maxRetries,
        Retry retry) {
    record Retry(boolean enabled, Duration backoff) { }   ← nested groups
}

@EnableConfigurationProperties(PaymentProperties.class)   ← or @ConfigurationPropertiesScan
@Configuration
class PaymentConfig { }

// now inject it like any other bean, and an invalid value stops the
// application at startup with a message naming the field and the rule:
//   Property: payments.maxRetries   Value: 40   Reason: must be <= 10

  config.activate.on-profile: dev

# ③ profile groups — one name activating several
spring:
  profiles.group:
    prod: prod,metrics,cloud              ← activating "prod" activates all three

// ④ conditional beans
@Bean @Profile("!prod")                       ← negation, and expressions like
Mailer loggingMailer() { … }                  @Profile("prod & eu") work too

# activation, in ascending precedence:
#   spring.profiles.active in a file  <  SPRING_PROFILES_ACTIVE  <
#   -Dspring.profiles.active=prod  <  --spring.profiles.active=prod
#   and @ActiveProfiles in a test, which overrides everything
Three profile traps
  • Lists are replaced, not merged. If application.yml defines three allowed origins and application-prod.yml defines one, production has one — not four. This surprises everyone once, usually in a security setting.
  • Do not use profiles to switch between real and fake behaviour. A @Profile("!test") bean means your tests exercise a different object graph than production. Use Testcontainers and configuration values instead — chapter 14.
  • Profile count grows badly. prod, prod-eu, prod-eu-canary is a combinatorial mess. Prefer a small number of profiles plus plain properties supplied by the environment, which is what the twelve-factor argument in chapter 17 of the Backend unit is about.

Fail at startup, not at the first request

A misconfigured application should refuse to start. @Validated on your properties turns a missing or nonsensical value into an immediate, readable failure naming the property and the rule — instead of a null pointer at three in the morning, or worse, a timeout of zero silently meaning "no timeout". This matters more in a container: a pod that fails its readiness check is never sent traffic and the rollout stops on its own, so a startup failure is contained where a runtime failure is not. Self-check

  1. A property is set in application.yml and as an environment variable. Which wins?
    The environment variable. Config data files sit low in the order, and environment variables, system properties and command-line arguments all override them — deliberately, so that the same artefact can be configured per environment without rebuilding. Command-line arguments beat all three. If you need to check rather than recall, /actuator/env/{property} lists every source that defines it and which one applied.
  2. Why is @ConfigurationProperties better than a set of @Value fields?
    It groups a whole namespace into one type, supports validation that runs at startup, gets relaxed binding, handles nested objects and lists naturally, and produces IDE metadata so your own settings autocomplete. It also arrives by constructor injection, so the class is testable without a container. @Value remains useful for a single scalar and for SpEL expressions, which the binder does not support.
  3. You set payments.base-url from an environment variable and it is ignored. Why?
    Almost certainly the name. An environment variable cannot contain a dot or a dash, so relaxed binding maps PAYMENTS_BASE_URL onto payments.base-url — but payments.base-url as a literal variable name, or PAYMENTS-BASE-URL, will not bind. Use uppercase with underscores, and for list entries use an index: PAYMENTS_HOSTS_0.
  4. application.yml lists three allowed origins and application-prod.yml lists one. How many in production?
    One. Lists are replaced wholesale, not merged element by element, so the profile-specific file wins entirely. This surprises people once and it is usually in a security-relevant setting like CORS origins or permitted IPs. If you want a base plus additions, model it as two separate properties and combine them yourself, or keep the whole list in one place per environment.
  5. Why is using a profile to swap in a fake implementation for tests a bad idea?
    Because the tests then exercise a different object graph than production, so the wiring you shipped is the wiring you never tested. Profile-conditional beans quietly become the place where "works in tests, fails in production" lives. Use the real components with test configuration — Testcontainers for the database, a stubbed HTTP server for external calls — so the graph is identical and only the endpoints differ.
  6. Why should a misconfigured application refuse to start?
    Because the failure is then contained and legible. @Validated properties turn a missing or invalid value into a message naming the property and the rule, at the cheapest moment. In a container it is better still: a pod that never becomes ready is never sent traffic and the rollout halts by itself, whereas the same problem surfacing at runtime means an instance is already serving errors. A zero timeout that silently means "wait forever" is the kind of thing this catches.
