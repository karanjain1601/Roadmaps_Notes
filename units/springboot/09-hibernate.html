The persistence context

The thing that makes JPA confusing is that your objects are not just objects. Inside a transaction they are tracked, and Hibernate decides on its own when to write, what to write and whether to write at all. Almost every JPA surprise is this mechanism behaving exactly as designed.

— words— min read2 interactivesNeeds: chapter 08

Four states

Transient
A plain object you created with new. No identity, unknown to Hibernate, changes go nowhere.
Managed
Inside the persistence context. Hibernate holds it, holds a snapshot of how it looked when loaded, and will compare the two at flush. Changing a field is enough — there is no save call.
Detached
Was managed, but its context closed. It has an identity and its changes are tracked by nobody. Lazy associations now throw.
Removed
Scheduled for deletion at the next flush.
Four scenarios, and the SQL each produces
Start with the first — note what is missing from the code
Three consequences worth memorising
  • You do not need to call save() on a managed entity. Loading it inside a transaction and setting a field is enough; flush will find the change. Calling save() is harmless but misleading, because it suggests the write happens there.
  • An accidental change is still a change. A getter that normalises a string, a setter called during mapping, a lazily initialised default — Hibernate cannot tell these from a deliberate edit and will issue an UPDATE. This is where mysterious writes in read-only-looking code come from.
  • save() on a detached entity is a merge, and merge reads first. It loads the current row, copies your fields over it and returns a different, managed instance — so mutating the object you passed in does nothing from then on. Any field you left null overwrites the stored value with null.

Bulk inserts: clear as you go

Even with batching, a single transaction inserting 100,000 entities holds every one of them in the persistence context — plus a snapshot each — and dirty-checks the lot on every flush, which makes the work quadratic. The pattern is to flush and clear every batch: if (i % 50 == 0) { em.flush(); em.clear(); }. Better still, for a genuine bulk load, skip JPA entirely and use JdbcClient with a batch update or the database's native copy mechanism. The ORM is for the object graph, not for moving a million rows.

The first-level cache is per transaction
Calling findById(x) five times in one transaction produces one query and returns the identical instance each time. But a query — anything with a where clause — always goes to the database, then reconciles results against the context. That asymmetry surprises people who expect the cache to prevent all repeat reads.
readOnly = true is worth setting
It sets the flush mode to manual and marks entities read-only, so Hibernate skips dirty checking and the snapshots — measurably cheaper on large result sets, and it prevents the accidental-update problem entirely. It also routes to a replica if you have configured one.
ddl-auto
validate in every real environment, create-drop in tests if you are not using Testcontainers, and never update: it never drops or renames anything, applies changes in an order it chooses, and produces a schema that no migration file describes — so no two environments match and nothing is reproducible. Flyway or Liquibase owns the schema; Hibernate checks it.
Turn on the SQL log while learning
logging.level.org.hibernate.SQL: debug plus hibernate.format_sql: true, and add a statement counter to your tests. Nearly everything in this chapter and the next becomes obvious the first time you watch the statements go past.

Self-check

  1. You load an entity in a transaction, set a field, and never call save(). What happens?
    It is persisted. The entity is managed, so Hibernate holds a snapshot of how it looked when loaded and compares field by field at flush — finding the change and issuing an UPDATE at commit. This is the intended design and the reason save() on a managed entity is a no-op. It also means an accidental modification, such as a getter that normalises a value, produces a real write.
  2. Why does save() on a detached entity issue a SELECT first?
    Because it becomes a merge, and merge must load the current row to know what changed and to attach a managed copy. Two consequences follow: it returns a different instance, so mutating the object you passed in has no further effect; and every field you left null overwrites the stored value with null, since merge copies the whole object. If you only mean to change two columns, load the entity and set those two.
  3. Why does IDENTITY make batching impossible?
    Because the id comes from the insert itself, so Hibernate must execute each statement immediately to learn the generated key before it can return a managed entity. There is nothing to accumulate, so JDBC batching is disabled entirely and a thousand rows are a thousand round trips. A sequence with an allocation size lets Hibernate reserve a block of ids up front, assign them in memory and send inserts in batches.
  4. Why is using the generated id in equals and hashCode dangerous?
    Because the id is null until flush. Two unsaved entities both have null ids and therefore compare equal, so a Set silently keeps one. Worse, the hash code changes when the id is assigned, so an entity added to a HashSet before saving lands in the wrong bucket and can never be found again — including inside Hibernate's own collection handling. Use an immutable business key, or assign a UUID in the constructor.
  5. Why should ddl-auto: update never be used outside a laptop?
    Because it only adds. It never drops a column, never renames, never changes a type, and applies what it does apply in an order it chooses — so the resulting schema depends on the history of deploys that machine has seen. No two environments end up identical, nothing is reproducible, and there is no file describing the change. Use Flyway or Liquibase to own the schema and set validate so Hibernate verifies its mapping against it at startup.
  6. What does @Transactional(readOnly = true) actually buy?
    Hibernate sets the flush mode to manual and marks loaded entities read-only, so it skips dirty checking and does not retain loaded-state snapshots — a measurable saving on large result sets, and it makes accidental updates impossible rather than merely unlikely. It also passes the read-only hint to the driver, and with a routing datasource it can direct the transaction to a replica.
