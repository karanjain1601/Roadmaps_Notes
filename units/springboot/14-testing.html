Testing a Spring application

Two problems, both specific to Spring. The suite is slow, and the reason is almost never the tests — it is how many application contexts they force Spring to build. And some tests pass for reasons that do not hold in production, which is worse than being slow.

Constructor injection is what makes this optional

A service whose dependencies arrive through its constructor can be tested with new OrderService(fakeRepo, fakeMailer) — no annotations, no context, no reflection, and it runs in a millisecond. That is the payoff chapter 2 promised, and it is why field injection quietly costs you a fast test suite: a class with @Autowired fields cannot be constructed without a container, so every test of it becomes a Spring test. Most business logic should be tested with no Spring involved at all; slices are for the wiring, and @SpringBootTest for a handful of end-to-end paths.

// ✗ forty classes, each mocking a slightly different set → forty contexts
@SpringBootTest
class OrderServiceTest {
    @MockBean PaymentGateway gateway;      ← changes the cache key
    @MockBean Mailer mailer;
}

// ✓ one shared configuration, reused by everything
@SpringBootTest
@Import(SharedTestConfig.class)
@ActiveProfiles("test")
abstract class IntegrationTest {                ← every test extends this
    @Autowired protected MockMvcTester mvc;
}

@TestConfiguration
class SharedTestConfig {
    @Bean @Primary
    PaymentGateway gateway() { return Mockito.mock(PaymentGateway.class); }
}
// declared as a bean rather than @MockBean, so the cache key is stable.
// Reset it between tests with Mockito.reset() in an @AfterEach.

Three settings that pay for themselves immediately
  • Run tests in parallel. JUnit 5's junit.jupiter.execution.parallel.enabled=true. Contexts are shared across threads, so this is mostly free — provided your tests do not share database state, which Testcontainers plus per-test transactions handles.
  • One container for the whole suite. A static Testcontainers instance, or the singleton pattern, rather than one per class. Starting Postgres is two seconds you should pay once.
  • Never @DirtiesContext without a reason. It throws away a cached context, so the next class rebuilds it — and one carelessly placed annotation can add minutes.

Self-check

  1. Why does adding @MockBean to a test class often make the whole suite slower?
    Because the set of mocked beans is part of the context cache key. Two classes that would otherwise share a context now need two, each costing a full startup — and with forty classes each mocking a slightly different combination you get forty contexts and two minutes of pure initialisation. Declaring the fakes as @Primary beans in one shared @TestConfiguration keeps the key stable and the context reused.
  2. Why should most business logic be tested without Spring at all?
    Because it is faster, simpler and tests the same thing. A service with constructor injection is just a class — new OrderService(fake, fake) runs in a millisecond with no context, no reflection and no annotations to get wrong. Spring tests are for the wiring: that the controller binds and validates correctly, that the query works against a real database, that the security rules match. Using them for logic buys nothing and costs seconds per class.
  3. A test asserts that a duplicate key throws, and it passes — then production returns a 500. What happened?
    The test never flushed. save() only queues the insert in the persistence context; the transactional test rolls back at the end, so the statement is never sent and the unique constraint never evaluated. Whatever the test asserted, it was not the database's behaviour. Use saveAndFlush, or flush explicitly, so the constraint fires where you can see it — chapter 9.
  4. Why does lazy loading work in a @DataJpaTest and fail in production?
    Because the test method itself is the transaction, so the persistence context stays open for its whole duration and every lazy association resolves happily. In production the transaction ends at the service boundary, and the association is touched afterwards — in a mapper or during serialisation — where the context is gone. Test the mapping through the layer that actually returns the DTO, and turn off open-session-in-view so the failure is reproducible.
  5. What is wrong with testing against H2 when production is Postgres?
    It is a different database. Casts, upserts, array and JSON operators, window function edge cases, reserved words, null ordering, lock behaviour and error messages all differ, so a query that passes on H2 can fail at runtime — and the failures are found by users. Testcontainers starts the real Postgres in about two seconds, once for the whole suite, and @ServiceConnection wires it with no property plumbing. There is no longer a good reason to use H2.
  6. When is mocking a repository the wrong choice?
    Whenever the thing you care about is the query. A mocked repository returns whatever you told it to, so a derived method with a wrong predicate, a broken @Query, a missing join fetch or an N+1 all pass untouched — you have tested that your service calls a method, which was never in doubt. Mock the repository when testing branching logic above it; use a real database when testing the data access itself.
