OAuth 2.0 and JWT

Spring can play any of the four roles in an OAuth deployment, and most of the difficulty is knowing which one you are building. Once that is settled, a resource server is three lines of configuration — and the interesting question becomes what those three lines actually check.

Four roles, four dependencies

OAuth roleIsSpring artifact
Resource ownerThe user—
ClientThe application acting on the user's behalfspring-boot-starter-oauth2-client
Resource serverYour API, validating tokens someone else issuedspring-boot-starter-oauth2-resource-server — by far the most common case
Authorization serverThe thing that issues tokensspring-authorization-server, or buy it
Almost certainly you want the resource server

If tokens come from Okta, Auth0, Entra ID, Keycloak or Cognito and your job is to accept them, you need the resource server starter and nothing else. Add the client starter when your application logs users in itself or calls another API on their behalf. Running your own authorization server is a project, not a configuration — Spring Authorization Server is capable and mature, and it also means you now own key rotation, consent, token revocation, client registration and the security review for all of it.

What validation actually checks

yaml + java — a resource server
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://auth.shop.com/realms/prod    ← this one line gives you
#   at startup Spring fetches                       the whole default setup
#     {issuer-uri}/.well-known/openid-configuration
#   which yields the jwks_uri, and it caches the keys — so rotation
#   works without a redeploy, and a new kid triggers a refetch.

// map scopes and roles onto authorities. The default converter turns
// the `scope` claim into SCOPE_* authorities and nothing else — so a
// realm_access.roles claim needs this:
@Bean
JwtAuthenticationConverter converter() {
    var scopes = new JwtGrantedAuthoritiesConverter();       ← SCOPE_*
    var c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(jwt -> {
        var out = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
        Optional.ofNullable(jwt.getClaimAsMap("realm_access"))
            .map(m -> (List<String>) m.get("roles"))
            .ifPresent(rs -> rs.forEach(r ->
                out.add(new SimpleGrantedAuthority("ROLE_" + r))));  ← the prefix
        return out;                                              hasRole()
    });                                                          expects
    return c;
}

// and add the audience check, which is NOT on by default:
@Bean
JwtDecoder jwtDecoder(OAuth2ResourceServerProperties p) {
    var d = NimbusJwtDecoder.withIssuerLocation(p.getJwt().getIssuerUri()).build();
    d.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(p.getJwt().getIssuerUri()),
        new JwtClaimValidator<List<String>>("aud",
            aud -> aud != null && aud.contains("orders-api"))));
    return d;
}

Self-check

  1. Which starter do you need if tokens come from Okta and your job is to accept them?
    spring-boot-starter-oauth2-resource-server, and one property — the issuer URI. Spring fetches the discovery document at startup, learns the JWKS endpoint, caches the keys and refetches when it sees an unknown key id, so rotation works without a redeploy. The client starter is for when your application logs users in or calls another API on their behalf, which is a different job.
  2. What does PKCE prevent that TLS does not?
    Interception of the authorization code before it is exchanged. The code travels over TLS but arrives via a redirect, and on mobile a malicious app can register the same custom URI scheme, so the code can be delivered to the wrong application entirely. PKCE binds the code to a secret the legitimate client generated and never transmitted — the attacker has the code and cannot produce the matching verifier, so the exchange fails.
  3. Why is the audience check the one most often missing?
    Because Spring's defaults validate the signature, the issuer and the expiry but not the audience — so a token minted for a different service by the same authorization server is accepted. In an organisation with one identity provider and twenty APIs, that means a token for the low-privilege reporting API is valid at the payments API. It has to be added explicitly with a JwtClaimValidator on aud.
  4. Why must the algorithm be pinned rather than read from the token?
    Because the header is attacker-controlled. Historically alg: none asked the library to skip verification altogether; more subtly, switching an RS256 token to HS256 invites the server to verify an HMAC using the RSA public key as the secret — and that key is published in your JWKS. Spring's Nimbus decoder pins the expected algorithms from the JWKS metadata, which is the correct behaviour and worth knowing is happening.
  5. What is the real trade between a JWT and an opaque token?
    Revocation against latency. A JWT is verified locally with no network call, so it stays valid until it expires — a fired user or a revoked scope persists for the token's lifetime. An opaque token is checked with the authorization server on each request, so revocation is immediate, at the cost of a round trip per call. Caching introspection results brings the latency back and reintroduces a revocation window, which is why short JWT lifetimes are usually the pragmatic answer.
  6. Your rules use hasRole('ADMIN') and every request is 403 despite a token containing that role. Why?
    Because the default converter only maps the scope claim, producing SCOPE_* authorities — a role inside realm_access.roles or a custom claim is simply not read. And hasRole looks for the authority with a ROLE_ prefix, so the converter has to add it. Supply a JwtAuthenticationConverter that reads your provider's claim and prefixes it, then check with hasRole; or map without a prefix and use hasAuthority consistently.
