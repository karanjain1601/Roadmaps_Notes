What software design is for

Design is not about making code beautiful, and it is not about anticipating the future. It is about keeping the cost of the next change low, given that you cannot predict what that change will be. Everything in this unit — every principle, pattern and architecture — is an attempt to buy that one property, and every one of them charges for it.

1.1The only thing software design optimises

Software has two values. Its behaviour — it does what users need today — and its structure — it can be made to do something different tomorrow. Users pay for the first and only notice the second when it is gone. Almost every argument about design is really an argument about how much of the second to buy.

Here is the uncomfortable part. Behaviour is urgent and structure is important, and urgent always wins the calendar. A system whose behaviour is perfect and whose structure is ruined becomes a system where every change takes a month, and eventually the cheapest option is to rewrite it — which throws away the behaviour too. A system with excellent structure and wrong behaviour is one sprint from being right.

The working definition

Good design is the arrangement of code that makes the changes you will actually be asked to make local — confined to a small, obvious, testable region — without knowing in advance which changes those will be. Everything else people say about design is a technique for approximating that.

Notice what that definition rules out. It rules out "elegant". It rules out "uses design patterns". It rules out "follows the architecture diagram". None of those are the goal; at best they are tactics, and each is capable of making change harder when applied without the goal in mind. It also rules out predicting the future — which is fortunate, because nobody can, and designs built on predictions are wrong in a specific and expensive way discussed in §1.5.

1.2Why the cost of change rises

Adding a feature to a young codebase takes a day. Adding a comparable feature to the same codebase three years later takes three weeks. The feature is not more complicated; the code around it is. Four mechanisms produce that curve, and they compound.

Coupling
Changing A requires changing B. Each dependency is a path along which a change propagates, and the number of paths grows faster than the number of modules.
Understanding cost
Before you can change code you must build a mental model of it. In a well-factored system you need to understand one module; in a tangled one you need to understand how five interact, and the interaction is not written down anywhere.
Fear
Without tests, every change carries an unknown probability of breaking something unrelated. Rational engineers respond by making the smallest, most additive change possible — adding a special case rather than restructuring — which makes the next change worse. Fear is a design force, and it always pushes towards duplication.
Accumulated workarounds
Each avoided restructuring leaves a scar: a flag, a branch, a duplicated function, a comment saying "do not touch". These are individually cheap and collectively fatal.

Blast radius

How far a change travels, given how connected your modules are. The number that matters is not module count — it is dependencies per module.

1.3Coupling is the whole subject

If you take one idea from this unit, take this one: design is the management of coupling. Nearly every principle in Part 3, every pattern in Part 4 and every architecture in Part 6 is a technique for removing a dependency, weakening one, or moving one somewhere it does less damage.

Two things are coupled when a change to one forces a change to the other. That definition is sharper than it looks, because it means coupling is a property of change, not of the call graph. Module A calling module B is not necessarily coupling — if B's interface is stable, A never changes when B does. Meanwhile two modules that never reference each other can be tightly coupled through a shared database column, a shared file format, or an unwritten assumption about ordering.

Coupled to a detail
class InvoiceService {
  send(invoice: Invoice) {
    const smtp = new SmtpClient(
      "mail.acme.com", 587,
      process.env.SMTP_PASS
    );
    smtp.send(
      invoice.customerEmail,
      `Invoice ${invoice.id}`,
      renderHtml(invoice)
    );
  }
}

Invoicing now depends on SMTP, on a hostname, on an environment variable and on HTML rendering. Switching to a queue, testing without a mail server, or sending by webhook all require editing this class.

Coupled to a decision
interface Notifier {
  notify(to: Address, msg: Message): Promise<void>;
}

class InvoiceService {
  constructor(private notifier: Notifier) {}

  async send(invoice: Invoice) {
    await this.notifier.notify(
      invoice.customerAddress,
      Message.forInvoice(invoice)
    );
  }
}

Invoicing depends only on the idea "something can be notified". SMTP, queues, webhooks and a test double all satisfy it. The dependency still exists — it now points at something that will not change.

That transformation is the single most repeated move in this unit, and it is worth naming precisely: depend on the stable thing, not the volatile thing. An interface you defined is stable because you control it. A third-party client library, a wire format, a database schema and a framework are all volatile, because someone else controls them and they change on someone else's schedule.

Decoupling is not free, and it is not always right

The version on the right has one more file, one more concept and one more indirection. A reader tracing behaviour must now find the implementation. For a script that sends one email and will never change, the left version is better — it is shorter, more direct and completely obvious. The reason to introduce the interface is a specific expectation: that the notification mechanism will change, or that you need to test the invoice logic without sending mail. State that reason. "Decoupling" is not a reason; it is a cost you pay for one.

1.4The three levels of design

The same idea — manage coupling so change stays local — appears at three scales, and this unit walks up them in order.

Scale, unit of design, and what a bad decision costs
LevelUnitTechniquesCost of getting it wrong
CodeFunction, class, moduleNaming, small functions, SOLID, patternsHours to days. Refactor freely — a bad function is a local problem
ComponentPackage, library, bounded contextCohesion, dependency direction, layering, DDDWeeks. Boundaries are hard to move once code has grown across them
SystemProcess, service, datastoreThe whole of the System Design unitMonths, and sometimes never. Splitting a database is a project

That cost column is the reason for the standard advice to defer architectural decisions and be liberal with code-level ones. You can rewrite a class this afternoon; you cannot un-split a database this quarter. It also explains a common failure: teams that agonise over service boundaries while shipping functions nobody can read. The cheap decisions are the ones you make hundreds of times a day, and their aggregate matters more than any single diagram.

1.5The two ways to get it wrong

Design errors are symmetric, and both are common enough to have names.

Under- and over-engineering
Under-engineeringOver-engineering
Looks likeOne 4 000-line file, logic duplicated in six places, no seams for testingNine interfaces with one implementation each, a plugin system for one plugin, configuration for things nobody configures
Caused byDeadline pressure and no time to consolidatePredicting requirements that never arrive; applying patterns because they are patterns
SymptomEvery change touches everythingEvery change touches five files and none of them do anything
CostRises steeply over timePaid immediately and forever, in comprehension
FixRefactor towards the seams you now know you needDelete the abstraction; inline it back

Over-engineering is the more insidious of the two because it feels like diligence. The flexibility is genuinely there — it is just flexibility along axes nobody needed, purchased at the price of indirection along every axis. And it is harder to undo than under-engineering: removing an abstraction that six modules depend on is a bigger job than extracting one from a fat function.

The rule of three

Write it once. When you need it again, duplicate it — deliberately, and note that you did. When a third case arrives, you can finally see which parts genuinely vary and which are incidental, and then abstract. Two examples are not enough evidence: the abstraction you infer from two cases is usually wrong in a way you cannot detect, and a wrong abstraction is worse than duplication, because duplication is easy to remove and a wrong abstraction bends every future case to fit it.

1.6Reversibility as the real criterion

If you cannot predict what will change, the useful question is not "what is the right decision?" but "how expensive is this decision to reverse?" That reframes design as risk management, and it produces better answers than trying to be right.

  1. Cheap to reverse: just decide. Which logging library, how to name a class, whether to extract a helper. Deliberating costs more than being wrong. Decide in seconds and move.
  2. Expensive to reverse: buy information first. Data model, service boundaries, public API shape, framework. Prototype, write the interface first, or find someone who has done it. The time spent is proportional to the cost of being wrong.
  3. Make expensive decisions cheaper instead of making them better. This is the highest-leverage move available. Hide the decision behind an interface so it can be swapped. Keep the migration path in mind while writing the first version. Ship the reversible half now and the irreversible half when you know more.

Decide, or find out first?

Score a decision on the two axes that matter. The recommendation follows from where it lands.

1.7Technical debt, used precisely

The metaphor is abused into meaninglessness — "technical debt" now means any code someone dislikes. Ward Cunningham's original sense is narrower and far more useful: debt is shipping something you know is not right, deliberately, to get feedback sooner, intending to fix it once you have learned what you needed to know. Like financial debt, it is a legitimate instrument with an interest rate.

Four things people call debt
KindOriginRight response
Deliberate and prudent"Ship the simple version now, we need to learn whether anyone wants this"Actual debt. Record it, set a trigger for repayment, repay it
Deliberate and reckless"No time for design"Not debt, a choice to be slower later for no information gained
AccidentalNobody knew a better approach at the timeNot debt, ignorance. Refactor when you learn better
DriftThe code was right; the requirements movedNot debt, entropy. Continuous small realignment

Why the distinction earns its place: only the first kind has a repayment plan, and only the first is a defensible thing to argue for in a planning meeting. The others need different conversations — about standards, about learning, and about budgeting continuous refactoring rather than scheduling a "cleanup sprint" that never happens.

1.8How to read the rest of this unit

Every principle and pattern that follows is presented the same way: the problem it solves, the mechanism, and what it costs. That last part is the one usually missing, and it is the reason so much design advice does damage — a technique presented without its cost reads as an instruction, and instructions get followed in situations they do not fit.

So the test to apply throughout, and the one you should apply to this chapter: what change does this make cheaper, and what change does it make more expensive? Nothing here makes everything better. Every abstraction makes one axis of change easy and every other axis slightly harder, because it adds a thing to understand. Design is choosing which axes to favour, and choosing them on evidence rather than on habit.

The questions worth asking in any review 
1  What is likely to change here, and would that change be local?
2  What would I have to touch to add the next obvious feature?
3  Can I test this without starting a database, a server or a clock?
4  If I got this wrong, how expensive is it to undo?
5  Is this abstraction earning its keep, or is it flexibility
   along an axis nobody has asked for?
6  Would someone new understand this without asking me?
A colleague says "we should extract an interface here in case we swap the payment provider later". How do you respond?

Ask two questions. First, is there an actual expectation of swapping, or is this hypothetical? "In case" is the signature phrase of speculative generality, and the honest answer is often that nobody has ever swapped it. Second — and this is the more useful question — would you want the interface anyway for testing? Because if the payment provider makes network calls, an interface lets you test the surrounding logic without one, which is a benefit you get today rather than a bet on tomorrow. That reframes it from prediction to present value. If neither holds, the right move is to leave the concrete dependency and note that it is contained in one place, so extracting the interface later is a twenty-minute job rather than a project — which is the reversibility argument from §1.6 doing its work.

Why is a wrong abstraction worse than duplication?

Because duplication is honest and localised, and a wrong abstraction is neither. If the same logic appears in three places, you can see all three, compare them, and merge them when you understand what they share; the cost is bounded and visible. A wrong abstraction, by contrast, has already been depended on. Each new case that does not quite fit gets accommodated by adding a parameter, a flag or a branch, so the abstraction accretes conditionals until it encodes every caller's special case — at which point it is coupling all of them together through a shared implementation none of them wanted. Unwinding it means untangling every caller. Sandi Metz's formulation is the one to remember: prefer duplication over the wrong abstraction, because the cost of duplication is far less than the cost of being wrong.

Two modules never import each other. Can they still be tightly coupled?

Easily, and this is the coupling that hurts most because no tool shows it to you. They can share a database table, so a schema change breaks both. They can share a file or message format, so a field rename breaks the reader. They can depend on execution order — one must run before the other, encoded nowhere. They can share a global, a cache key format, an environment variable, or a temporal assumption about when a job runs. They can both parse the same string format with two separate parsers that must agree. Every one of these is a change that forces changes elsewhere, which is the definition of coupling, and none of them appear in a dependency graph. This is why "we have no circular imports" is a weak claim about design, and why Chapter 8's connascence vocabulary is more useful than the import graph.

Recap

  1. Design optimises the cost of the next change, not elegance and not prediction. Behaviour is what users pay for; structure is what lets you keep changing it.
  2. Coupling is the subject. Two things are coupled when changing one forces changing the other — a property of change, not of the call graph.
  3. Depend on the stable thing. An interface you own is stable; a library, schema or wire format is not.
  4. Every abstraction has a cost in indirection and comprehension. Introduce one for a stated reason, not for "decoupling".
  5. Three scales — code, component, system — with wildly different reversal costs. Be liberal at the top, careful at the bottom.
  6. Under- and over-engineering are both common; over-engineering is harder to undo and feels like diligence.
  7. Rule of three. Two examples are not enough evidence to abstract from, and a wrong abstraction is worse than duplication.
  8. Optimise for reversibility, not correctness. Cheap decisions: just decide. Expensive ones: buy information, or make them cheaper to reverse.
  9. Debt is deliberate and prudent. The other three things people call debt need different conversations.
