Enterprise patterns

The patterns that connect a domain model to a database and to the outside world. Fowler catalogued them in 2002 and almost all of them are now inside your ORM — which is exactly why they are worth knowing, because you are using them whether or not you can name them, and the ones you cannot name are the ones that surprise you in production.

~32 min read Logic organisation · mapping · unit of work · ORMs 2 interactive panels Prerequisite: chapters 14–15

16.1Three ways to organise domain logic

Before any mapping question, there is a prior one: where does business logic live? Fowler names three answers, and choosing the wrong one is the most consequential decision in this chapter.

The three, and where each fits
Transaction scriptDomain modelTable module
ShapeOne procedure per use case, start to finishA web of objects with behaviour and invariantsOne class per table, handling all rows
Reads likeA recipeA vocabularyA set of table operations
Scales withNumber of use cases — linearly, then badlyComplexity of rulesNumber of tables
Best forSimple, mostly-CRUD logic; supporting subdomainsRich rules that experts argue about; core subdomainsReport-heavy, record-set-oriented work
Fails whenRules recur across scripts and start duplicatingThere are no real rules — then it is ceremonyRules span tables
Cost of entryNoneHigh: modelling, mapping, disciplineLow
The honest guidance

Start with transaction scripts. They are simple, readable, and perfectly adequate for most of any system. Move to a domain model in the parts where rules become genuinely complicated — and let that be a small fraction of the codebase, in the core subdomain from Chapter 14. The common failure is applying a domain model uniformly, which buries a CRUD screen under aggregates and repositories; the opposite failure is keeping transaction scripts in a core domain until each is 900 lines and the same rule appears in eleven of them.

Transaction script or domain model?

The crossover depends on rule complexity and reuse, not on system size.

16.2Active record versus data mapper

Two ways to connect objects to rows, and the choice constrains everything downstream.

The two mapping strategies
Active recordData mapper
IdeaThe object knows how to save itself: order.save()A separate mapper moves data between objects and rows; the object knows nothing about storage
Object shapeMirrors the table, one class per tableFree — the model can differ from the schema entirely
Domain purityThe domain depends on persistenceThe domain has no persistence dependency at all
TestabilityNeeds a database, or heavy stubbingPure objects, testable with plain values
Speed to buildVery fastSlower — mapping is real work
FitsCRUD, supporting subdomains, small teams, Rails and Laravel conventionsRich models, core subdomains, schemas that must not dictate the model
ExamplesRails ActiveRecord, Eloquent, Django ORMHibernate/JPA, SQLAlchemy classic, Doctrine, EF Core (mostly)

The decisive question is whether you want the schema to shape the model. Active record says yes and gets enormous productivity in return; data mapper says no and pays for that freedom in mapping code. A domain model with aggregates and value objects essentially requires a data mapper, because an aggregate is not a table and a value object has no row of its own.

16.3Unit of work and identity map

Two patterns you are almost certainly using without naming, and both explain behaviour that otherwise looks like magic.

Enterprise

Unit of work

Track every object read or changed during a business transaction, then write all the changes in one commit.

What it buys
You stop writing save() calls. Change objects freely; at the end, the unit of work works out the inserts, updates and deletes, orders them to satisfy foreign keys, and commits once. That is fewer round trips and one atomic boundary.
What surprises people
Changes are written without an explicit save. In Hibernate or EF, modifying a tracked entity and committing persists it whether you meant to or not — so a "temporary" change made for a calculation goes to the database. This causes real incidents, and the defence is to keep read paths outside the tracking session.
Also
It defers writes, so constraint violations surface at commit rather than at the offending line — which makes them harder to attribute.
Enterprise

Identity map

Keep one in-memory instance per identity per session, so loading the same row twice returns the same object.

Why it matters
Without it, two loads of customer 42 give two objects, changes to one are invisible to the other, and the second write silently overwrites the first. The identity map makes object identity match database identity within a session, which is what lets == mean what you expect.
Cost
It is a cache with all a cache's problems. Data changed by another process is not seen until the session ends, and a long-lived session accumulates every object it has touched — a common memory leak in batch jobs.

16.4Lazy loading and the N+1 problem

Lazy loading is the virtual proxy applied to persistence: a collection is not fetched until touched. It is convenient and it produces the single most common performance defect in enterprise applications.

How it happens, and it always looks innocent 
const orders = await repo.findRecent();        // 1 query

for (const order of orders) {
  console.log(order.customer.name);            // 1 query EACH
  //          ^^^^^^^^^^^^^^ a proxy. Property access
  //                         is a database round trip.
}

// 200 orders → 201 queries → 201 × network latency.
// Nothing in the code says "query" and nothing looks slow.

The cost of N+1

Latency dominates, not query time — which is why this is invisible on a developer's machine and fatal in production.

The fixes, in order of preference: eager-load explicitly for the associations a use case needs (include, fetch join, selectinload); batch the loads so N queries become one WHERE id IN (…); or use a purpose-built read query returning exactly the columns the screen needs, with no entities involved. And the preventive measure that actually works: log query counts per request and fail a test when one exceeds a threshold, because N+1 is not visible in code review and is trivially visible in a counter.

16.5DTOs and mappers

A data transfer object is a flat, behaviourless structure for moving data across a boundary — to an HTTP client, into a message, between layers. Two questions come up constantly.

Why not just return the domain object?
Because your API contract would then be your internal model, and every refactoring becomes a breaking change for consumers. It also leaks fields nobody outside should see, and it forces the serialiser's constraints — no constructors with logic, no private state, no value objects — back onto the domain. A DTO decouples the wire format from the model, which is the entire point.
Is that not just boilerplate?
Some, and it buys real independence. Reduce it rather than eliminate it: generate mappers where a tool exists; define DTOs from the API contract rather than mirroring the domain; and accept that a DTO looking identical to a domain object today is fine, because the value is that they can diverge tomorrow. For internal layers where no contract is published, skipping DTOs is often correct — the pattern earns its keep at published boundaries.

Related and worth naming: a presentation model or view model, shaped for one screen rather than for the domain; and remote facade, a coarse-grained interface that batches what would otherwise be chatty calls — the pattern behind an API returning a whole page's data in one request rather than five.

16.6Use cases and the service layer

A service layer (or use-case layer, or application layer) is the set of operations the application offers, each one a complete piece of work: PlaceOrder, CancelBooking, IssueRefund. It is the boundary that transaction scripts and domain models both sit behind.

What belongs where — the division that keeps this clean 
APPLICATION SERVICE / USE CASE          orchestration, no rules
  · start a transaction
  · load aggregates through repositories
  · call domain methods
  · save, publish events
  · translate to and from DTOs
  · authorise the request

DOMAIN                                  rules, no infrastructure
  · enforce invariants
  · decide outcomes
  · emit domain events
  · know nothing about transactions, HTTP or the database

INFRASTRUCTURE                          mechanism, no rules
  · repository implementations
  · message publishing
  · external clients

A use case with an `if` about business rules has stolen from the
domain. A domain object that opens a transaction has stolen from
the application layer. Both are the usual failure.

Making each use case its own class — with one execute method, an input DTO and an output DTO — rather than grouping them into a fat OrderService has three advantages worth the extra files: dependencies are per-use-case rather than the union of a dozen, each use case is independently testable, and the list of files is the list of things the system does, which is unexpectedly good documentation.

16.7Concurrency: optimistic and pessimistic

Two ways to stop concurrent writers destroying each other's work
OptimisticPessimistic
MechanismA version column; the update asserts the version has not changed and fails if it hasA lock taken on read and held until commit
AssumesConflicts are rareConflicts are likely
On conflictThe second writer fails and must retry or mergeThe second writer waits
CostNone until a conflict; then a retry, and a user-visible decisionHeld locks, reduced throughput, deadlock risk, and it does not survive a "think time" gap
Use forAlmost everything, including anything with a human in the loopShort, hot, contended operations inside one transaction

Two practical notes. Optimistic locking is what makes the lost update problem visible instead of silent — without it, the second save simply overwrites the first and nobody finds out. And the version conflict is a domain event, not a technical one: the right response is usually to tell the user what changed and let them decide, not to retry blindly, because a blind retry re-applies an intention formed against stale data.

16.8ORMs, weighed honestly

An ORM is most of this chapter in one library: data mapper or active record, unit of work, identity map, lazy loading, query object, and often optimistic locking. It is a large amount of hard work you do not have to do — and the source of most enterprise performance problems, because it hides where the queries are.

What you get and what it costs
Gives youCosts you
Mapping, change tracking, transactions, identityQuery behaviour becomes indirect and hard to predict from the code
Portability across databases, in principlePortability you rarely use, at the price of not using each database's good parts
Migrations and schema managementA learning curve as large as SQL's, on top of SQL's
Much less boilerplate for simple casesComplex queries fight the abstraction and end up worse than SQL
A safe default against injectionN+1 and accidental full loads, invisible in review
The position that works

Use the ORM for what it is good at — writes and aggregate loading, where change tracking, identity and transactional consistency are exactly the problem — and use plain SQL or a query builder for reads, where you want specific columns, joins and aggregation with predictable cost. That split resolves most ORM complaints, because nearly all of them are about reads. It is also the minimal form of CQRS: one model for changing things, another for looking at them, with no eventual consistency and no extra infrastructure.

Your ORM is generating 400 queries for one page. What is the sequence of fixes?

First, see them: turn on query logging with the source location, and confirm the shape — one query then N similar ones is lazy loading; several hundred distinct queries is something else, usually a loop calling a service. Second, fix the immediate case by eager-loading exactly the associations that page needs, which typically collapses 400 to two or three. Third, ask whether entities were the right tool at all: a page rendering a list of orders with customer names does not need aggregates with change tracking, and a purpose-built read query returning the six columns the template uses is faster, simpler and immune to this class of bug. Fourth, prevent recurrence, because this will come back — count queries per request in tests and fail above a threshold, since N+1 is invisible in code review and glaring in a counter. What not to do: turn off lazy loading globally as a first move, because eager-everything replaces 400 small queries with one enormous join that loads the whole graph, which is often worse.

Why does a domain model essentially require a data mapper?

Because active record makes the class mirror the table, and a domain model deliberately does not. An aggregate spans several tables and presents one root; a value object has no identity and usually no row of its own, living as columns on its owner; invariants are enforced through methods rather than through settable properties; and the model wants a private constructor with named factories, which conflicts with an ORM that needs to instantiate objects from rows. Every one of those is a place the schema would otherwise dictate the model's shape — which reverses the dependency direction the whole exercise is about, since the domain would then depend on the database rather than the other way round. A data mapper absorbs the difference: the model is designed for the domain, the schema for storage, and the mapper reconciles them. The honest cost is that the mapping is real work and can be fiddly for value objects and collections — which is a good reason to reserve the domain-model approach for the core subdomain and let active record serve the rest.

Is a version-conflict error something to retry automatically?

It depends on whether the intention survives the other writer's change, and usually it does not. If two people edited a document and the second save fails on version, retrying blindly means re-applying the second person's edit on top of the first — which silently discards the first person's work, exactly the lost update the version column existed to prevent. The right response there is to surface the conflict, show what changed, and let the user decide. Automatic retry is appropriate when the operation is a function of current state rather than a snapshot of a previous one: incrementing a counter, appending to a list, or recomputing a derived value can all be reloaded and reapplied safely, and a retry loop with a small bound is correct. So the rule is to look at what the operation actually intends — a state transition can be retried, a state replacement cannot — and to structure domain methods as transitions where you can, because that turns conflicts into something the system can handle rather than something the user must.

Recap

  1. Three ways to hold logic: transaction script, domain model, table module. Start with scripts; use a domain model where rules are genuinely complex.
  2. Active record lets the schema shape the model; data mapper does not, and a real domain model needs the latter.
  3. Unit of work writes changes you did not explicitly save, which is convenient and occasionally an incident.
  4. Identity map makes object identity match row identity — and is a cache with a cache's problems.
  5. Lazy loading produces N+1, the most common enterprise performance defect. Count queries per request in tests.
  6. DTOs earn their keep at published boundaries, where the value is that the contract and the model can diverge.
  7. Use cases orchestrate and hold no rules; the domain holds rules and no infrastructure.
  8. Optimistic locking by default. A version conflict is a domain event, and only state transitions are safe to retry blindly.
  9. Use the ORM for writes and plain SQL for reads. That split resolves most ORM complaints and is CQRS at its cheapest.
