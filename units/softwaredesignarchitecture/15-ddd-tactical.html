Domain-driven design: tactical

The building blocks you use inside a bounded context. Two of them carry almost all the value — value objects, which are cheap and immediately useful anywhere, and aggregates, which are the hardest thing in this unit to get right and the thing that most determines whether a domain model stays coherent under change.

15.2Entities and value objects

The distinction is about equality. Two value objects with the same attributes are the same thing — £20 is £20, and it is meaningless to ask which £20. Two entities with the same attributes are different things if their identities differ — two customers can share a name and address and remain distinct people.

Consequences of the distinction
Value objectEntity
EqualityAll attributes matchIdentity matches; attributes irrelevant
MutabilityImmutable. Changing means a new instanceMutable — that is what having a lifecycle means

SharingFreely — it cannot be corruptedCarefully — aliasing matters

Value objects are the cheapest win in this chapter

They need no framework, no aggregate design and no DDD commitment. Replacing number with Money, string with EmailAddress, and two loose dates with DateRange eliminates a whole class of bug — adding pounds to dollars, an unvalidated email reaching the sender, an end date before its start — by making them not compile or not construct. It also gives validation one home instead of every call site, and gives behaviour somewhere to live: money.allocate(3) distributing pennies without losing one is a real algorithm that has nowhere to go if money is a number.

Primitive obsession
class Booking {
  constructor(
    public start: Date,
    public end: Date,

// All of these compile:
new Booking(dec5, dec1, -40, "GBPP", "not an email")
booking.priceAmount + otherBooking.priceAmount  // GBP + USD

Value objects
class DateRange {
  private constructor(readonly start: Date, readonly end: Date) {}
  static of(start: Date, end: Date) {
    if (end <= start) throw new InvalidRange(start, end);
    return new DateRange(start, end);
  }
  get nights() { return days(this.start, this.end); }
  overlaps(o: DateRange) { … }
}

class Money {
  private constructor(readonly cents: bigint, readonly ccy: Currency) {}
  plus(o: Money) {
    if (o.ccy !== this.ccy) throw new CurrencyMismatch();
    return new Money(this.cents + o.cents, this.ccy);
  }
  allocate(n: number): Money[] { /* splits without losing a penny */ }
}

class Booking {
  constructor(
    readonly stay: DateRange,
    readonly price: Money,
    readonly contact: EmailAddress
  ) {}
}

One caution worth stating: the entity/value distinction depends on the context, not on the thing itself. An address is a value object in shipping — two identical addresses are the same destination. It is an entity in a property register, where each address has an identity, a history and a lifecycle independent of its current text. A banknote is a value to you and an entity to the central bank tracking its serial number. Deciding requires knowing whether the domain needs to distinguish two identical-looking instances.

15.3Aggregates

An aggregate is a cluster of objects treated as a single unit for the purpose of data changes, with one entity — the root — as the only object outside code may reference. It exists to answer one question: what must be consistent, immediately, in one transaction?

The four rules 
1  ONE ENTRY POINT
   Outside code holds a reference only to the root. Internal
   objects are reached through it and never handed out mutable.

2  THE BOUNDARY IS AN INVARIANT BOUNDARY
   Everything that must be true at the end of every transaction
   is enforced inside one aggregate. Nothing else belongs in it.

3  REFERENCE OTHER AGGREGATES BY IDENTITY ONLY
   order.customerId, not order.customer. Object references across
   aggregates make the boundary meaningless and load the world.

4  ONE AGGREGATE PER TRANSACTION
   Changing two aggregates atomically means either a distributed
   transaction or a very large aggregate. Instead: change one,
   emit an event, let the other converge. Consistency between
   aggregates is EVENTUAL by design, not by accident.

Rule 2 is the one that decides everything. An invariant that spans two objects forces them into the same aggregate; an invariant that does not span them lets you keep them apart. So aggregate design is really invariant inventory: list what must always be true, then let the boundaries fall out.

Aggregate boundary designer

Select the rules that must hold immediately, in the same transaction. The boundary — and its cost — follows.

Sizing

Aggregates fail in both directions and the failures look different.

Too big and too small
Too largeToo small
SymptomLoading one thing loads thousands of rows; concurrent users constantly conflictA rule is enforced in a service rather than in an aggregate, or not at all
CauseModelling containment rather than consistency. "An order has shipments, so they are in it"Splitting along entity lines instead of invariant lines
CostContention, memory, slow loads, lock timeoutsInvariants that can be violated by concurrent transactions
FixFind which invariants genuinely need immediate consistency; the rest become eventsMerge the pieces that share an invariant

Three heuristics that resolve most cases. Prefer small. Contention scales with aggregate size and is difficult to undo later. An unbounded collection inside an aggregate is a bug — if a customer can have 40 000 orders, orders are not inside the customer. And ask whether the rule really needs to be immediate: "an order's total must equal the sum of its lines" must be; "a customer's lifetime value must equal the sum of their orders" almost certainly need not be, and treating it as eventual removes a huge boundary.

15.4Domain events

A domain event is a record that something meaningful happened, named in the past tense, carrying the facts needed to react to it: OrderPlaced, PaymentDeclined, ShipmentDispatched.

They exist because of rule 4. If one transaction may change one aggregate, everything else that must happen has to happen afterwards, driven by a fact. The event is that fact, and the pattern is uniform: the aggregate records what happened; the application publishes it after the transaction commits; subscribers in this or another context react.

Getting events right
RuleWhy
Name in the past tense, after a business factOrderPlaced, not CreateInvoiceCommand. An event states what happened; it does not instruct. Naming it as an instruction couples the emitter to the reaction
Publish after commit, not duringPublishing inside the transaction means subscribers can act on a change that then rolls back. Collect events on the aggregate and dispatch after the commit succeeds
Carry the facts, not just an idA subscriber that must call back for details creates a synchronous dependency and a race — the entity may have changed since. Include what happened, at the time it happened
Distinguish internal from publishedEvents used within a context can be rich and change freely. Events crossing a context boundary are a published language — versioned, conservative, and expensive to change
Use the transactional outbox for reliabilityWriting state and publishing an event are two systems; either can fail. Write both in one transaction and let a relay publish — the dual-write problem, covered in the System Design unit

15.5Repositories

Tactical

Repository

A collection-like interface for aggregates: you ask for one, you put one back, and nothing about storage is visible.

The rules that make it worth having
One repository per aggregate root, not per table and not per entity. It returns fully-constituted aggregates, never partial rows. Its interface is defined in the domain and phrased in the domain's language — findOverdueFor(customerId), not selectWhere(sql).
What it is not
A generic Repository<T> with save, findById, findAll and a query-builder escape hatch is a data-access object with a fashionable name. If callers can express arbitrary queries through it, the storage model has leaked and you have gained nothing but a layer.
The honest tension
Reads. A repository returning whole aggregates is right for changing things and wrong for a dashboard that needs three fields from five aggregates. Do not distort the repository to serve reads — use a separate read path with its own queries and its own DTOs. That is the practical, minimal form of CQRS, and it removes most of the pressure that deforms repositories.

15.6Domain services and factories

Domain service
A stateless operation that is genuinely part of the domain but belongs to no single entity or value: transferring money between two accounts, pricing against a promotion and a tier, checking availability across several resources. Name it after the operation in the domain's language (FundsTransfer, SeatAllocation), keep it free of infrastructure, and treat its growth as a warning — if every rule ends up here, you have rebuilt the anemic model from Chapter 5.
Distinguish it from an application service
An application service orchestrates: load the aggregate, call it, save, publish. It contains no rules. A domain service contains rules but touches no infrastructure. Conflating them is the most common structural mistake in DDD codebases, and the symptom is a "service" that both queries a repository and decides a discount.
Factory
For creation complex enough that a constructor cannot express it — building an aggregate from several inputs, reconstituting one from stored state, or enforcing creation rules that need collaborators. A static method on the root is usually enough; a separate class only when creation needs its own dependencies.

Twelve concepts. Decide before revealing — several depend on the context, and the reasoning says which.

15.8The recurring mistakes

  1. Aggregates drawn by containment instead of by invariant. "A customer has orders, so orders are in the customer aggregate" — and now loading a customer loads 40 000 rows and two users cannot place orders simultaneously. The question is never what contains what; it is what must be consistent at once.
  2. Object references across aggregate boundaries. order.customer.address.country means the boundary does not exist, the ORM loads a graph you did not ask for, and rule 4 becomes unenforceable. Reference by id and load separately.
  3. Repositories that leak queries. A repository exposing a query builder is a DAO. Keep the interface in the domain's vocabulary and put reads on a separate path.
  4. Everything an entity. Teams new to DDD produce a dozen entities and no value objects, which is exactly backwards — most concepts have no identity, and each one modelled as an entity acquires an id, a row and a lifecycle it does not need.
  5. Events named as commands. SendConfirmationEmail as an "event" means the emitter has decided what the subscriber should do, which reintroduces the coupling the event was meant to remove.
  6. Tactical patterns without strategic ones. Aggregates and repositories inside a single sprawling model, with no bounded contexts, gives you the ceremony and none of the benefit. If you adopt one half, adopt the strategic half.
Why must aggregates reference each other by identity rather than by object reference?

Four reasons, and they compound. First, it keeps rule 4 enforceable: if you hold an object reference you can modify the other aggregate in the same transaction, and nothing stops you, so the boundary stops being real. Second, loading: an object reference invites an ORM to fetch a graph, and once order.customer.orders is navigable you can accidentally load most of the database from one query — or trigger N+1 through a lazy-loading proxy. Third, it makes the boundary explicit to readers, since customerId: CustomerId says "different aggregate, load it separately if you need it" in a way that customer: Customer does not. Fourth, it is what lets aggregates eventually live in separate services or databases without a rewrite: an id crosses a process boundary and an object reference does not. The cost is real — you cannot write order.customer.name, so the application service loads both, or the read model joins them. That inconvenience is the boundary doing its job.

Your Customer aggregate contains all of a customer's orders and users are hitting lock timeouts. What is the diagnosis?

The aggregate was drawn by containment rather than by invariant, and the lock timeouts are the predictable consequence. Ask what rule requires an order and its customer to be consistent in the same instant. Usually there is none — a credit limit is the candidate, and even that is normally enforced acceptably as an eventual check with a compensating action, because businesses generally prefer occasionally exceeding a limit to blocking every concurrent order. So Order should be its own aggregate holding customerId, and the customer holds no order collection at all. Contention drops from every-order-against-every-order to per-order. If the credit limit genuinely must be immediate, the way to keep it without the big aggregate is a small dedicated aggregate — a CreditReservation per customer that orders reserve against — which confines the contention to the thing that actually needs it rather than to the entire customer. The general form: when an aggregate is too big, find the specific invariant forcing it and give that its own small aggregate.

Is Repository<T> with generic CRUD methods a repository?

Not in any sense that provides value. A repository is supposed to express the domain's retrieval needs in the domain's language and hide the storage model completely; a generic interface with save, findById, findAll and query(spec) does the opposite — it exposes a storage-shaped API to the whole application and lets any caller construct arbitrary queries, which means the storage model has leaked everywhere and cannot be changed. It also loses the two properties that matter: it operates on entities rather than aggregate roots, so nothing enforces the boundary, and it invites partial loads, so callers get objects that are not fully constituted. What a real repository looks like is a small, specific interface per aggregate root — OrderRepository with findById, findUnfulfilledFor(customerId), save(order) — where every method is a question the domain actually asks. Generic CRUD is fine as an implementation detail underneath; it is the public interface that should be domain-shaped. And the pressure that pushes people towards generic repositories is nearly always reads, which is best answered by a separate read path rather than by widening the repository.

Recap

  1. Value objects are defined by attributes and are immutable; entities are defined by identity and have lifecycles. Which one a thing is depends on the context.
  2. Most teams have too few value objects. They are the cheapest available win and need no DDD commitment.
  3. An aggregate is a consistency boundary, not a containment hierarchy. Draw it from an inventory of immediate invariants.
  4. Four rules: one entry point, invariant boundary, reference other aggregates by id, one aggregate per transaction.
  5. Prefer small aggregates. An unbounded collection inside one is a bug, and contention is hard to undo.
  6. Domain events carry the consistency that aggregates cannot. Past tense, facts not instructions, published after commit.
  7. One repository per aggregate root, phrased in the domain's language. Serve reads on a separate path.
  8. Domain services hold rules and no infrastructure; application services hold orchestration and no rules.
  9. Tactical patterns without bounded contexts give you the ceremony and none of the benefit.
