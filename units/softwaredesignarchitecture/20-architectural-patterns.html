Architectural patterns

Named structures at system scale. Two of them — CQRS and event sourcing — are almost always described together and are entirely independent, which is worth untangling because adopting the pair when you needed one is a common and expensive mistake.

20.1MVC and its relatives

Four patterns separating what is displayed from what is true, differing in who talks to whom and where the presentation state lives. The confusion between them is largely historical: MVC as implemented by a web framework is not MVC as Trygve Reenskaug described it in 1979.

What they are all actually solving

Presentation logic — formatting, enabling, showing and hiding, validation display, navigation — is real logic, and if it lives in the view it cannot be tested without rendering. Every one of these patterns exists to move that logic somewhere testable. The differences are mechanism: MVP pushes through an interface, MVVM binds, MVU derives. The failure mode is identical in all four: presentation logic leaks back into the view, and the pattern becomes decoration.

20.2Microkernel and plugin architecture

Architectural

Microkernel

A minimal core providing only the mechanism, with all features supplied as plugins registered against extension points.

Where it is right
When third parties must extend the product, or when features are genuinely independent and numerous. Editors and IDEs, browsers, CI systems, e-commerce platforms, database engines with pluggable storage.
What it demands
An extension API you are prepared to keep stable, since plugin authors depend on it — which means it is a published contract with versioning and deprecation, and getting it wrong is very expensive. Also isolation: a plugin should not be able to bring the host down, which usually means process boundaries or a sandbox.
The failure
Building a plugin system for plugins that never arrive. If you are the only author, you have paid for an API, a registry, a lifecycle and a versioning policy in exchange for indirection. This is the speculative-generality trap from Chapter 1 at its most expensive.

20.3Blackboard

Architectural · specialised

Blackboard

Several independent specialists read from and write to a shared structure, progressively refining a solution, with a controller deciding who runs next.

When it fits
Problems with no deterministic algorithm, where partial solutions from different techniques must be combined: speech recognition (its origin), sensor fusion, vehicle perception, some planning and diagnostic systems.
Why it is rare
It gives up nearly everything this unit values — the shared structure is global mutable state, control flow is opaque, and reproducing a run is difficult. That is an acceptable trade only when the alternative is having no solution at all.
Worth knowing because
Modern systems reinvent it. A pipeline of models writing enrichments into a shared record, several agents contributing to a shared context, or a rules engine with a working memory are all blackboards, and inherit its debugging difficulties.

20.4CQRS

Architectural

Command–query responsibility segregation

Use different models for changing state and for reading it.

The problem it solves
One model cannot serve both well. Writes want aggregates, invariants and normalisation; reads want denormalised, screen-shaped data with no object graph. Forcing both through one model deforms it — repositories grow query methods, aggregates grow fields nobody needs for decisions, and reads load far more than they use.
The crucial point about levels
CQRS is a spectrum, not a switch. Level 1: two models, one database, one process — the write side uses the ORM and aggregates; the read side runs SQL and returns DTOs. No new infrastructure, no eventual consistency, and this level solves most of the problem. Level 2: separate read schemas or materialised views, updated in the same transaction or by a trigger. Level 3: a separate read store updated asynchronously from events — now you have eventual consistency and everything that comes with it.
Cost, which rises steeply with level
Level 1 costs almost nothing. Level 3 costs a projection pipeline, a rebuild mechanism, monitoring for projection lag, and a user interface that can cope with a write not being visible in the next read — which is a product decision, not a technical one.
The mistake
Jumping to level 3 because the pattern is described that way. Almost everyone who needs CQRS needs level 1.

20.5Event sourcing

Architectural · high commitment

Event sourcing

Store the sequence of events that happened, rather than the current state. Current state is derived by replaying them.

What it genuinely buys
A complete, immutable audit trail that is the source of truth rather than a log written alongside it. The ability to answer questions about the past you did not know you would ask, by building a new projection over history. Temporal queries — what did this look like on 3 March. And debugging by replay.
What it costs, and this list is not optional
Event schema versioning forever — a five-year-old event must still be readable, so you need upcasting or a versioned reader. Snapshots, or replaying thousands of events per load. No easy deletes, which collides with data-protection erasure requests and usually forces crypto-shredding. Every read needs a projection, so it drags CQRS in with it. Eventual consistency between the event store and every projection. And a rebuild story for when a projection is wrong.
Where it is worth it
Domains where history is the business: accounting and ledgers, trading, insurance claims, regulated audit, anything where "why is the balance this?" must be answerable in full. In those, you were going to build an event log anyway and the pattern is a simplification.
Where it is not
Almost everywhere else, and especially as a general default. The tell is a team adopting it for auditability when a simple audit table would do — that is a fraction of the cost for most of the benefit.
CQRS and event sourcing are independent

You can have CQRS without event sourcing — two models over one ordinary database, which is the common and sensible case. You can have event sourcing without CQRS in principle, though it is awkward because reads over a raw event stream are painful, which is why the two are usually seen together. The pairing is a consequence, not a requirement, and treating them as one decision is how teams end up with a projection pipeline they never needed. Decide them separately: do reads and writes want different models (usually yes, at level 1), and is history the source of truth (usually no).

20.6The distribution patterns

Strangler fig deserves emphasis because it is the answer to the most common architectural situation: there is an existing system, it is bad, and it cannot be stopped. The alternative — a parallel rewrite — has a well-documented failure rate, because the old system keeps changing while the new one is built, and the cutover is a single enormous risk taken all at once. Strangling converts that into a sequence of small reversible steps, and the intermediate states are all shippable.

20.7Recognising the pattern from the problem

Problem to pattern

A situation; name the architectural pattern before revealing.

A team wants event sourcing for auditability. What would you suggest they check first?

Whether an audit table gives them what they need, because it usually does at a small fraction of the cost. Write an append-only table recording who did what, when, and the before and after values, and you have a queryable audit trail with no schema versioning burden, no snapshots, no projection pipeline and no eventual consistency. The questions that distinguish the two: does the audit need to be the source of truth, such that current state can be proved to derive from it — a regulator's question, and one an audit table cannot answer because state and log can drift? Do you need to reconstruct arbitrary past states, rather than just see what changed? Will you need to answer questions about history that you cannot anticipate now, which is what building a new projection over old events gives you? If all three are no, an audit table is the right answer. It is also worth naming the costs that surprise people most: an event schema must remain readable for as long as you keep events, which is forever, and deletion requests collide with immutability in a way that usually forces crypto-shredding — encrypt per subject and destroy the key.

Why does CQRS not require eventual consistency?

Because separating the models does not require separating the stores. At level 1, both sides talk to the same database in the same process: the write side loads aggregates through repositories and enforces invariants, the read side issues SQL and returns DTOs shaped for the screen. A write commits and the very next read sees it, exactly as before — the only thing that changed is that reads no longer travel through the domain model. That already solves the problem most people have, which is that repositories were being deformed into query builders and aggregates were growing fields that existed only for display. Eventual consistency enters only at level 3, when the read side moves to a separate store fed asynchronously, and that is a substantial additional commitment: projection lag to monitor, a rebuild mechanism, and a user interface that can handle a write not being visible in the next read. The rule of thumb is to adopt the model separation immediately, since it is nearly free, and to adopt the store separation only when read load or read shape genuinely demands it.

When is MVU or a unidirectional data flow worth the extra indirection over direct mutation?

When the number of ways state can change exceeds what people can hold in their heads — which arrives sooner than expected. With direct mutation, any component can set any state, so answering "why is this value wrong?" means finding every writer, and the set of writers grows quietly. MVU makes every change go through one function that takes the current state and a message and returns a new state, which gives you three things: a single place to read to know every possible transition, the ability to log the message sequence and replay it, and time-travel debugging for free because old states still exist. The costs are real — more ceremony for a simple form, a message type per interaction, and a performance consideration since a new state object is produced per change. The threshold is roughly where state is shared across several components and changed from several places; below that, local mutable state in a component is simpler and correct. It is also worth noting that most frameworks now let you mix: unidirectional flow for shared application state, local state for a text field, which is the pragmatic arrangement.

Recap

  1. The MVC family all move presentation logic somewhere testable. The failure mode in all four is the logic leaking back into the view.
  2. Microkernel needs plugin authors. Building the extension API for plugins that never arrive is speculative generality at its most expensive.
  3. Blackboard trades away reasoning for the ability to combine partial solutions, and modern pipelines reinvent it along with its debugging problems.
  4. CQRS is a spectrum. Level 1 — two models, one database, one process — costs almost nothing and solves most of the problem.
  5. Event sourcing is a large commitment whose cost list is not optional: versioning forever, snapshots, projections, rebuilds, and deletion via crypto-shredding.
  6. CQRS and event sourcing are independent decisions and should be made separately.
  7. Serverless is excellent at low and spiky volume and poor at sustained high volume; check the cost curve, not just the model.
  8. Strangler fig converts a rewrite into a sequence of reversible steps where every intermediate state ships.
