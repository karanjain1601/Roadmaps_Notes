Clean code

Code is read far more often than it is written, and most of that reading is done under pressure by someone trying to change one thing without breaking another. Clean code is not an aesthetic standard — it is a set of habits that shorten the time between opening a file and safely modifying it. This chapter is those habits, with the reasoning that makes them worth following and the limits that stop them becoming dogma.

2.1The criterion

Every rule below reduces to one measurement: how long does it take a competent stranger to correctly predict what this code does? Not to read it — to predict it, and to be right. That framing is useful because it settles most style arguments. A clever one-liner that takes forty seconds to decode is worse than four obvious lines. A 300-line function whose behaviour you can guess from the first ten lines is worse than it looks, because your guess is probably wrong.

Consistency beats correctness in style

Whether the brace goes on the same line does not matter. Whether it goes on the same line everywhere does, because inconsistency costs a reader attention on every occurrence and that attention is the scarce resource. So: adopt a formatter, run it automatically, never discuss it again. The value is not the style; it is the elimination of the decision and the diff noise. Any codebase where formatting appears in code review has a tooling problem, not a discipline problem.

2.2Naming

Naming is the highest-leverage activity in programming because a name is the only documentation that is always visible, always at the call site, and impossible to skip. Six rules cover almost everything.

Reveal intent, not implementation
userList tells you the type, which the type already told you. activeSubscribers tells you what is in it and why. If the container changes from a list to a set, the second name still works.
Make the length proportional to the scope
i is a perfect name for a three-line loop and a terrible one for a module-level variable. A name's job is to carry meaning across the distance between its definition and its use — short distance, short name.
Avoid disinformation
accountList that is actually a map. getUser() that creates one if missing. isValid() that also mutates. A misleading name is worse than a vague one, because a vague name makes you look and a misleading name stops you looking.
Use one word per concept
Pick fetch, get or retrieve and use it consistently for the same kind of operation. Three synonyms in one codebase force the reader to wonder what distinction they encode — and sometimes they encode one, which is worse.
Make names pronounceable and searchable
genymdhms cannot be discussed out loud. A bare 7 cannot be found; MAX_RETRIES can.
Prefer a better name to a comment
A comment explaining what code does is a naming failure with extra steps, and it will drift out of date because nothing enforces it. Comments earn their place when they explain why: a non-obvious constraint, a link to a bug, a rejected alternative.
Needs comments to survive
// check if user can access
function chk(u, d) {
  // 86400000 = one day
  if (Date.now() - u.ts > 86400000) {
    return false;
  }
  // 2 = admin
  return u.r === 2 || d.o === u.id;
}
Explains itself
const SESSION_LIFETIME_MS = 24 * 60 * 60 * 1000;

function canAccess(user: User, doc: Document) {
  if (sessionExpired(user)) return false;
  return user.role === Role.Admin
      || doc.ownerId === user.id;
}

const sessionExpired = (user: User) =>
  Date.now() - user.lastAuthAt > SESSION_LIFETIME_MS;

The second version has no comments and needs none. Every fact the comments carried is now in a name: the constant, the role, the extracted predicate. That is the trade to aim for — comments are a liability with an expiry date, and names are checked by the compiler and by every reader.

2.3Functions

The classic advice is "functions should be small". The reason is more useful than the rule: a function is the unit at which you can name a piece of behaviour, and naming behaviour is how a reader skips it. A well-named function is a paragraph the reader does not have to read.

One level of abstraction per function

This is the rule that actually does the work, more than any line count. A function that mixes "calculate the discount" with "iterate the array" with "append to a string buffer" forces the reader to hold three levels at once. When every statement in a function is at the same conceptual level, the function reads as a summary and each name is a link you can follow if you care.

Cyclomatic complexity

The number of independent paths through a function: one, plus one for every if, else if, case, loop, catch, ternary and short-circuit operator. It matters because it is the minimum number of test cases needed for full branch coverage, and because human working memory is small.

Reading a complexity number
ValueMeaningAction
1–4Simple, obviously testableFine
5–10Moderate; still comprehensibleFine, but watch it grow
11–20Hard to hold in your head, hard to test fullyExtract the branches that belong together
20+Effectively untestable and change-hostileSplit it. This is where bugs concentrate

A caveat worth stating: complexity that comes from genuine business rules has to live somewhere, and pushing it around does not remove it. Extracting six branches into six one-line functions reduces the number but not the difficulty. The win comes when the extraction lets each branch be named, tested and changed independently — if it does not, you have added indirection for a metric.

Guard clauses over nesting

Arrow shape, deep nesting
function pay(order) {
  if (order != null) {
    if (order.items.length > 0) {
      if (order.customer.verified) {
        if (!order.paid) {
          return charge(order);
        } else {
          throw new Error("already paid");
        }
      } else {
        throw new Error("unverified");
      }
    } else {
      throw new Error("empty");
    }
  }
  throw new Error("no order");
}
Flat, with the happy path last
function pay(order: Order) {
  if (!order)                  throw new Error("no order");
  if (order.items.length === 0) throw new Error("empty");
  if (!order.customer.verified) throw new Error("unverified");
  if (order.paid)               throw new Error("already paid");

  return charge(order);
}

Same complexity number, radically better readability: every precondition is one line, the happy path is unindented at the bottom, and adding a fifth check does not increase nesting.

Arguments

Fewer is better, and the reason is testing: each argument multiplies the combinations you must consider. Three specific argument shapes are worth avoiding outright.

Argument smell

Boolean parameters

A boolean argument means the function does two things and the caller picks which.

Why it hurts
save(user, true) is unreadable at the call site — you must open the function to learn what true means. Worse, the function necessarily contains an if on that flag, so the two behaviours are entangled and cannot be changed or tested independently.
Fix
Two functions with names: saveDraft(user) and publish(user). If they share logic, they share a private helper. If there are genuinely many options, pass a named options object so the call site reads save(user, { validate: false }).
Exception
A boolean that is genuinely data rather than a mode — setEnabled(true) — is fine, because it is not selecting between behaviours.
Argument smell

Null arguments and null returns

Null is a value that is not a value, and it type-checks everywhere.

Why it hurts
Passing null means "pretend I did not pass this", which the function handles with a branch. Returning null means every caller must remember a check the compiler will not enforce, and the one that forgets fails at a distance from the cause.
Fix
For arguments: overloads or an options object with the field absent. For returns: an explicit optional type the compiler checks, a result type carrying success or failure, an empty collection instead of null, or a null object — a real instance with neutral behaviour, such as a NoOpNotifier.
Also
Never return null from a function whose name promises a thing. findUser may return nothing; getUser should throw. Encode that distinction in the name and be consistent about it.

2.4Command–query separation

A function should either do something or answer something, never both. A query returns a value and changes nothing observable; a command changes state and returns nothing (or an acknowledgement).

Why it matters 
// Violates CQS: asks a question AND changes the world
if (user.isAuthorised(doc)) { … }    // also writes an audit row

Consequences:
  · You cannot call it twice — the second call has a different effect.
  · You cannot call it in a log line, an assertion or a debugger
    without changing program behaviour. Debugging becomes hazardous.
  · Tests of the query need to assert on the side effect too.
  · Reordering two "harmless" checks changes what happens.

// Separated
const allowed = policy.permits(user, doc);   // query: pure, repeatable
audit.record(user, doc, allowed);            // command: explicit

The point is not purity for its own sake. It is that queries become safe to call — repeatedly, out of order, in a test, in a log statement — and safety is what makes code easy to reason about. The pragmatic exceptions are well known and small: pop() on a stack, an atomic compare-and-set, a counter increment that returns the new value. Each is a case where the combination is the whole point, and each should be obvious from the name.

2.6Organise code by the actor it serves

Uncle Bob's formulation of the single-responsibility principle is about people, not about functions doing one thing: a module should have one reason to change, and a reason to change is a person or role who requests the change. Two pieces of code that serve different stakeholders should not live in the same class, even if they operate on the same data — because they will be changed at different times, by different people, for unrelated reasons, and each will risk breaking the other.

Three actors, one class
class Employee {
  calculatePay()   { … }  // finance
  reportHours()    { … }  // operations
  save()           { … }  // DBAs
}

If calculatePay and reportHours share a private helper, a finance change to overtime rules silently alters an operations report. Three unrelated groups can break each other's work through a shared file.

One actor each
class EmployeeData { … }          // the facts

class PayCalculator  { pay(e: EmployeeData) { … } }
class HoursReporter  { report(e: EmployeeData) { … } }
class EmployeeRepo   { save(e: EmployeeData) { … } }

Now shared logic must be extracted deliberately and named, rather than accidentally reused. Each class has exactly one group of people who ask for changes to it.

The same test applies to files and directories. Organising by technical layer — controllers/, services/, models/ — means a single feature change touches three directories and a single directory contains twenty unrelated features. Organising by feature — billing/, catalogue/, auth/, each containing its own controller, service and model — means a change is one directory and a deletion is one rm -rf. The second is almost always better, and it is the code-level shadow of the bounded contexts in Chapter 14.

2.7Keep the framework at arm's length

Frameworks are volatile in the sense of Chapter 1: someone else owns them and changes them on their schedule. Business rules are the most stable and most valuable thing you own. Letting the second depend on the first inverts the value.

In practice this means your domain logic should not import the web framework, the ORM's base classes, the message library's annotations, or the cloud SDK. The concrete test: could you unit-test your pricing rules without the framework on the classpath? If not, the framework has reached into the middle of your application and every upgrade is now a business risk.

The counterweight, because this one is regularly overdone: wrapping every framework call in your own abstraction is a large tax, and for a framework you will never leave — the language's standard library, the test runner — it buys nothing. Apply it where the value is highest: keep the core rules framework-free and let the edges be as frameworky as they like. That is the whole idea behind the architectures in Chapter 19.

    2.9Where clean code advice goes wrong

    1. Extracting until nothing means anything. Twelve two-line functions with names like doStepThree are harder to follow than one clear twenty-line function, because the reader now has to reassemble the story from fragments. Extract when the fragment has a name that a reader would recognise as a concept.
    2. Treating line counts as the goal. Metrics are smoke detectors, not standards. A 40-line function that reads top to bottom in one abstraction level is fine; a 12-line function with four nested closures and a mutable accumulator is not.
    3. Refactoring without tests. "Behaviour-preserving" is a claim, and without tests it is an unverified one. The order is always: get it under test, then change it. See Chapter 3.
    4. Cleaning code nobody reads. Effort should follow change frequency. A file touched weekly deserves care; a stable file that has not changed in three years is working, and rewriting it introduces risk in exchange for nothing.
    5. Making it a review battleground. Reviews that argue over naming while missing a race condition have inverted their value. Automate what can be automated, and spend human attention on correctness, boundaries and whether the change belongs where it was put.
    Why is if (user.isAuthorised(doc)) a problem if isAuthorised also writes an audit record?

    Because it breaks the reader's most basic assumption: that asking a question is safe. A reader who wants to add a second check, or log the value, or evaluate it in a debugger, will duplicate the audit record without any indication that they have. Reordering two apparently independent conditions changes what gets audited. Short-circuit evaluation means the audit sometimes does not happen at all, depending on an earlier condition. And a test of the authorisation logic now needs a working audit sink. Separating them — const allowed = policy.permits(user, doc) then audit.record(...) — makes both operations obvious at the call site, makes the query freely repeatable, and lets each be tested alone. This is command–query separation, and the value is not tidiness; it is that queries become safe.

    When is a comment the right answer rather than a better name?

    When it explains something the code cannot: why, not what. Legitimate comments include a non-obvious constraint ("the vendor's API rejects batches over 500, undocumented"), a rejected alternative and the reason ("tried a set here; ordering is load-bearing for the export"), a link to a bug or specification, a warning about a consequence ("changing this invalidates every cached token"), and a genuinely surprising performance trade-off. Illegitimate comments are the ones restating the code, marking sections that should be functions, commented-out code that version control already remembers, and changelogs at the top of the file. A good test: if renaming something would delete the comment's reason to exist, rename instead — the name is checked by every reader and the comment is checked by nobody.

    Your team has a 20-line function limit. A colleague splits a clear 35-line function into five pieces and it is now harder to read. What went wrong?

    The rule was applied instead of its reason. Small functions help when each extracted piece is a named concept a reader recognises and can then skip — the name does the summarising. If the pieces are arbitrary slices with names like processPart2, the reader gains nothing and loses the ability to read the logic in sequence; they must now jump between five locations and rebuild the order in their head. The correct question is not "how long is it" but "is every statement here at the same level of abstraction, and does each extraction have a name a domain expert would recognise?" A 35-line function that reads as a clear sequence of same-level steps is fine. The productive response is to replace the line limit with a complexity threshold plus a review question, since complexity at least correlates with test burden while line count on its own does not.

    Recap

    1. The criterion is prediction time: how long before a stranger can correctly say what this does.
    2. Consistency beats correctness in style. Automate formatting and stop discussing it.
    3. Names reveal intent, scale with scope, and never mislead. A comment describing what is a naming failure; a comment describing why earns its place.
    4. One level of abstraction per function does more work than any line limit.
    5. Cyclomatic complexity is the minimum number of tests for full branch coverage. Above ~10, split — but only if each piece becomes independently nameable and testable.
    6. Guard clauses instead of nesting; the happy path unindented at the bottom.
    7. No boolean parameters, no null arguments, no null returns. Two named functions, an options object, or an explicit optional type.
    8. Commands do, queries answer. Never both, so queries stay safe to call.
    9. Organise by actor and by feature, not by technical layer.
    10. Keep business rules free of framework imports, and spend cleaning effort where the code actually changes.
