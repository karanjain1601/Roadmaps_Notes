Layered, hexagonal, clean

Hexagonal architecture, onion architecture and clean architecture are widely presented as three competing approaches. They are three drawings of one rule — source dependencies point inwards, towards policy — with different vocabularies and slightly different emphases. Understanding that collapses a large amount of apparent complexity, and makes the real question visible: how much ceremony is the rule worth in your system.

19.1Classical layering, and why it needed fixing

The traditional stack is presentation on top, then application, then domain, then data access at the bottom, with each layer depending on the one below.

Traditional layering, and the problem in one line 
Presentation  ──►  Application  ──►  Domain  ──►  Data access
                                                       │
                                                       ▼
                                                  the database

The domain — the most valuable, most stable, most reusable part —
depends on the data access layer, which depends on a database.

Consequences:
  · The domain cannot be compiled or tested without the DAL.
  · A schema change reaches the domain.
  · The dependency points from POLICY to DETAIL, which is
    exactly backwards.

Two further problems compound it. Layer bypassing: strict layering forbids skipping a layer, which produces pass-through methods that exist only to forward a call; relaxed layering permits skipping, and then the layers stop meaning anything. And horizontal slicing: as Chapter 18 covered, features are vertical, so every feature change touches every layer.

The fix is a single move: invert the bottom dependency. Put the interface the domain needs in the domain, and let the data access layer implement it. Now the arrow points upward-inward, the domain depends on nothing, and everything else in this chapter is a way of drawing that.

19.2Hexagonal — ports and adapters

Alistair Cockburn's framing, and the most useful vocabulary of the three. The application sits inside a boundary. Anything outside talks to it only through ports — interfaces the application defines — and each external technology gets an adapter that implements or drives a port.

The two kinds of port, and the distinction that matters
Driving (primary, left side)Driven (secondary, right side)
Who initiatesThe outside world calls inThe application calls out
The port isThe application's own API — its use casesAn interface the application needs someone to satisfy
AdaptersHTTP controller, CLI, message consumer, scheduled job, test harnessPostgres repository, S3 client, email sender, payment gateway, clock
Dependency directionAdapter → port. The adapter depends on the appAdapter → port. The adapter depends on the app
NoteBoth point the same way. That is the whole idea — every adapter depends on the application, and the application depends on none of them
The symmetry is the point

Cockburn's original motivation was not database independence — it was that the application should be drivable equally by a user, a program, a test or a batch script. If the only way to invoke a use case is through an HTTP controller, then tests must go through HTTP, and the application has been shaped by its delivery mechanism. Defining the use case as a port means the HTTP controller is just one of several equal callers, and the test is another.

19.3Onion and clean

Jeffrey Palermo's onion architecture and Robert Martin's clean architecture draw the same rule as concentric circles, with dependencies pointing inwards only.

The same rule, three vocabularies
HexagonalOnionCleanWhat it actually is
DomainDomain modelEntitiesBusiness rules that would exist without this software
ApplicationDomain services + application servicesUse casesRules specific to this application; orchestration of entities
PortsInterfaces defined in the inner ringsBoundary interfacesWhat the inside needs from the outside, expressed in the inside's language
AdaptersInfrastructureInterface adaptersControllers, presenters, gateways, repositories
——Frameworks and driversThe outermost ring: the web framework, the database, the devices

The differences are real but small. Clean architecture adds an explicit outer ring for frameworks and is prescriptive about crossing boundaries with simple data structures rather than entities. Onion emphasises that the domain model is the centre and that all coupling is towards it. Hexagonal is the least prescriptive about internal structure and the most useful about the driving/driven distinction. If you understand the dependency rule, you can read all three and implement any of them.

19.5What it looks like on disk

Diagrams are easy; directory trees are where this becomes concrete. The arrangement below combines the dependency rule with the vertical-slicing conclusion from Chapter 18.

Feature at the top, layers inside 
src/
  billing/                     ← a bounded context; owns its data
    domain/                    ← entities, value objects, domain events
      Invoice.ts                 no imports outside billing/domain
      Money.ts
      InvoiceRepository.ts     ← a PORT. Interface only, defined here
    usecases/                  ← application layer
      IssueInvoice.ts            imports domain; nothing else
      VoidInvoice.ts
    adapters/                  ← everything that touches the world
      http/InvoiceController.ts       driving adapter
      persistence/PgInvoiceRepo.ts    driven adapter, implements the port
      email/SesInvoiceSender.ts
    index.ts                   ← the module's public surface. Other
                                 contexts import ONLY from here

  catalogue/  …same shape
  shipping/   …same shape

  platform/                    ← genuinely shared technical code
    http/  db/  logging/         no domain knowledge whatsoever

  main.ts                      ← composition root: the only file that
                                 constructs adapters and wires them in


THE RULES A LINTER ENFORCES
  billing/domain     may import   nothing outside itself
  billing/usecases   may import   billing/domain
  billing/adapters   may import   billing/domain, billing/usecases
  any context        may import   platform/, other contexts' index.ts
  platform/          may import   nothing from any context

Three things this arrangement gets that a purely horizontal layout does not. A feature change is one directory. Deleting a feature is one rm -rf plus removing its wiring. And the top level of src/ describes what the system does rather than what techniques it uses, which is the first thing a new person reads.

19.6What it costs, honestly

The real objections, and how much each one lands
ObjectionVerdict
"It is a lot of files for a simple operation"Fair. A create-read-update-delete endpoint may touch a controller, a use case, an entity, a port and an adapter. For genuine CRUD this is pure overhead — apply the structure in the core subdomain and let the rest be simpler
"Mapping between layers is tedious"Fair. Entity → DTO → response model is real work. Reduce it by not mapping where no contract is published, and by generating what you can
"We will never change the database"Misses the point. The benefit collected daily is testability and comprehensibility — the domain is readable and testable without infrastructure. Swappability is a side effect, not the argument
"It fights the framework"Sometimes true. Frameworks that want to own your entities (active record, annotation-driven ORMs) make this expensive. That is a real cost to weigh, not a reason to dismiss it
"Reads become awkward"True and solvable. Going through the domain to build a report is painful. Use a separate read path with its own queries — see Chapter 16
"It is over-engineering"Depends entirely on the system. For a three-month internal tool, yes. For a decade-long core domain, the alternative is worse

How much of this is worth it here?

The rule is not all-or-nothing. Four levels, each buying something specific.

19.7Applying it incrementally

The rule is not a rewrite. Four steps, each independently valuable, in order of return per unit of effort:

  1. Extract the pure decisions. Take the business logic out of the code that touches the world and make it functions over values — the functional core from Chapter 3. This alone gets most of the testability benefit and needs no new structure.
  2. Define one port. Pick the most painful infrastructure dependency, define an interface for what you need from it in your own language, and put the interface next to the code that uses it. One file.
  3. Add the import rule. A linter rule saying the domain package may not import infrastructure. This is what stops the erosion, and it is cheap.
  4. Reorganise the tree. Move to feature-first directories with layers inside. Do this last, because it is the most disruptive and the least valuable — and by this point you know where the boundaries actually are.
If you will never swap the database, is the dependency rule still worth following?

Yes, because database swappability is the least valuable thing it provides and the one always cited. What you collect daily is three other properties. Testability: the business rules run in milliseconds with no container, no fixtures and no cleanup, which changes how often people run tests and therefore how they work. Comprehensibility: the rules are readable in one place without connection handling, transaction management and serialisation interleaved, so a new person can learn what the system does by reading a small number of files. Change isolation: a schema migration, an ORM upgrade or a switch from REST to gRPC touches the adapter and stops there. Each of those pays every week; swappability might pay once, or never. It is also worth noting that the thing you actually swap is rarely the database engine — it is the ORM version, the driver, the connection pooling strategy, the addition of a read replica, or a move of one table to a different store. All of those are absorbed by the same boundary.

Where do you put a query that spans three aggregates for a dashboard?

Not through the domain. Loading three aggregates to extract six fields is slow, awkward, and distorts both the repositories and the aggregates to serve a need that has nothing to do with enforcing invariants. Put it on a separate read path: a query object or read-model service that issues SQL directly and returns a DTO shaped for the screen, living in the adapters layer and bypassing the domain entirely. That is legitimate rather than a compromise — the dependency rule exists to protect policy, and a read has no policy in it; nothing is being decided and no invariant is at risk. The two disciplines that keep it honest: the read path must be read-only, so nothing can mutate through it, and its DTOs must be defined for the view rather than reusing domain types, so the domain stays free to change. This is CQRS at its cheapest — two models, one process, one database, no eventual consistency — and it removes most of the pressure that otherwise deforms repositories into query builders.

Your team adopted clean architecture and now every simple change touches six files. What went wrong?

Most likely the structure was applied uniformly rather than where it earns its keep. The dependency rule pays in proportion to how much policy there is to protect; over a CRUD screen there is none, so a controller, request DTO, use case, entity, port, adapter and response DTO for what amounts to an insert is pure ceremony. The corrective is not to abandon it but to grade it: full structure in the core subdomain from Chapter 14, a thin use-case layer over active record in supporting areas, and something bought for generic ones. A second common cause is mapping ceremony that is not buying anything — mapping between layers matters at a published boundary where the contract must be able to diverge from the model, and internally it is often fine to pass the same type through. A third is pass-through layers: a use case that only calls a repository method is a layer with no content, and deleting it loses nothing. Count the files that made a real decision in the last change; if it is one out of six, five of them are not layers, they are forwarding.

Recap

  1. Hexagonal, onion and clean are one rule with three vocabularies: source dependencies point inwards, towards policy.
  2. Classical layering points the domain at the database, which is backwards. Inverting that one dependency is the whole fix.
  3. Ports are interfaces the application defines; adapters implement or drive them. Both driving and driven adapters depend on the application.
  4. The original motivation was drivability, not database independence — the application should be equally callable by a user, a program or a test.
  5. The rule is mechanical, so enforce it with an import linter. It erodes one import at a time.
  6. Feature at the top level, layers inside. A change is one directory and the tree describes the business.
  7. The benefit collected daily is testability and comprehensibility; swappability is a side effect.
  8. Reads go on a separate path. There is no policy in a query, so the rule does not apply to it.
  9. Apply it incrementally and unevenly: pure core first, then one port, then the linter, then the tree — and only where there is policy worth protecting.
