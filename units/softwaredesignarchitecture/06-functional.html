Functional thinking

You do not need a functional language to get most of the benefit. Purity, immutability and composition are habits, and applying them to the parts of a codebase that hold decisions produces code that is easier to test, safe under concurrency and possible to reason about locally. This chapter is the habits, the mechanics that make them affordable, and the places where they cost more than they give.

6.1Pure functions

A function is pure if it satisfies two conditions: the same inputs always produce the same output, and it has no observable effect other than returning that output. Both halves matter — a function that reads a global is impure even if it writes nothing, and a function that logs is impure even if its return value is deterministic.

The property this buys is referential transparency: any call can be replaced by its result without changing the program. That sounds theoretical and is intensely practical, because it is what makes all of the following legal without further thought.

What purity licenses
You may…Because
Test it with plain values and no doublesThere is nothing to fake — inputs in, output out
Cache or memoise the resultThe answer cannot change behind your back
Run it on any thread, in any order, in parallelNo shared state means no interleaving to get wrong
Call it in a debugger, a log line or an assertionObserving it does not change the program
Reorder, skip or repeat calls freely when refactoringOnly the value matters, not when it was computed
Reason about it without reading anything elseIts behaviour is fully described by its signature and body

Every item on that list is a property you lose the moment the function touches a clock, a database, a global or a mutable argument. That is the whole argument, and it is why the placement of impurity is a design decision rather than an implementation detail.

Purity audit

Decide before revealing. Several of these are impure in ways that are easy to miss.

6.2Immutability, and why it is affordable

The objection to immutability is always the same: copying is expensive. If updating one field in a large structure means cloning the whole thing, immutability costs O(n) per update and is unusable for anything big.

That objection assumes a deep copy, and persistent data structures do not do that. When you "change" a node, you create a new node and a new path from the root to it — every subtree not on that path is shared, not copied, because it is immutable and therefore safe to share. The cost of an update is the depth of the tree, not its size.

Structural sharing

Update one leaf. Red nodes are newly allocated; grey nodes are shared with the previous version, unchanged.

Real persistent collections use a high branching factor — 32 in Clojure's and Scala's vectors, and in Immutable.js — which makes the tree extremely shallow. A million-element vector is four levels deep, so an update allocates about four nodes and shares the rest. That is why immutability is a practical default rather than an academic preference.

The shallow copy trap

Spread syntax copies one level. { ...order } gives a new object whose items property points at the same array — so mutating copy.items mutates the original, and the code looks immutable while behaving otherwise. This is the most common immutability bug in JavaScript and TypeScript. Either use a library that does it properly, freeze in development so violations throw, or type your fields readonly so the compiler catches the mutation attempt at the point it happens.

6.3Composition over control flow

Functional style prefers building behaviour by combining small functions rather than by writing statements that step through it. The practical benefit is that each stage has a name, is testable alone, and can be reordered or removed without touching the others.

Imperative accumulation
function activeEmails(users) {
  const out = [];
  for (let i = 0; i < users.length; i++) {
    if (users[i].active) {
      if (users[i].email) {
        out.push(users[i].email.toLowerCase());
      }
    }
  }
  out.sort();
  return out;
}

Four concerns interleaved with index management and a mutable accumulator. Testing "does it lowercase" means running the whole loop.

A pipeline of named stages
const isActive   = (u: User) => u.active;
const hasEmail   = (u: User) => Boolean(u.email);
const emailOf    = (u: User) => u.email!.toLowerCase();

const activeEmails = (users: User[]) =>
  users.filter(isActive)
       .filter(hasEmail)
       .map(emailOf)
       .sort();

Each predicate is independently testable and reusable, the shape of the operation is in the method names, and there is no index to get wrong.

The loop-to-operation translation table
Loop that…IsNote
Builds a new list of the same lengthmapOne-to-one; length is preserved
Keeps some elementsfilterPredicate returns a boolean, nothing else
Accumulates a single valuereduce / foldThe most general; if it is hard to read, use an explicit loop
Checks whether any element qualifiessome / anyShort-circuits; removes a flag variable and a break
Checks whether all qualifyevery / allSame
Finds the first matchfindReturns an optional, not a sentinel index
Produces several outputs per inputflatMapThe one people reach for last and need often
Groups by a keygroupByStandard in most languages; trivially written with reduce

The counterweight: a reduce that builds a complex object while mutating an accumulator and branching three ways is less readable than the loop it replaced. The point is not to eliminate loops but to use the operation whose name states the shape. When no operation fits, a plain loop is the honest answer.

6.4Make illegal states unrepresentable

This is the highest-value idea in the chapter and it needs no functional language, only a decent type system. Rather than validating that a structure is in a legal state, arrange the types so that illegal states cannot be constructed at all. Then the check is done once by the compiler instead of defensively at every use.

Illegal states representable
interface Request {
  status: "loading" | "success" | "error";
  data?: Result;
  error?: string;
}

// All of these type-check and none should exist:
{ status: "loading", data: result, error: "oops" }
{ status: "success" }                  // no data
{ status: "error" }                    // no message

// So every reader defends:
if (r.status === "success" && r.data) { … }
//                            ^^^^^^ a check the type forced
//                                   but cannot guarantee
Only legal states exist
type Request =
  | { status: "loading" }
  | { status: "success"; data: Result }
  | { status: "error";   message: string };

// The compiler now narrows for you:
switch (r.status) {
  case "loading": return spinner();
  case "success": return view(r.data);      // data is present
  case "error":   return alert(r.message);  // message is present
}
// …and it will tell you if you add a fourth case and
// forget to handle it here.

The same technique applied at a smaller scale is the value object: instead of string for an email address, a type that can only be constructed through a function that validates. Once you hold an EmailAddress, it is valid — permanently, everywhere, with no further checks. Instead of number for money, a Money carrying a currency, so adding pounds to dollars does not compile. Chapter 15 develops this properly; the point here is that it is a functional-thinking move — pushing correctness into the type rather than into runtime checks.

6.5Errors as values

Exceptions are invisible in a signature: a function that returns User might also terminate the call stack, and nothing in its type says so. That makes error paths easy to forget and hard to see when reading. The functional alternative is to return the failure as part of the value.

Two shapes, and when each fits 
// Result / Either — the failure is part of the return type
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function parseAge(input: string): Result<number, ParseError> {
  const n = Number(input);
  if (!Number.isInteger(n))  return { ok: false, error: "not an integer" };
  if (n < 0 || n > 150)      return { ok: false, error: "out of range" };
  return { ok: true, value: n };
}

// The caller cannot ignore it — the compiler will not let them
// reach .value without checking .ok first.

USE RESULT FOR    expected, recoverable, part of the domain:
                  validation, parsing, not-found, business rule violations,
                  anything the caller will reasonably want to handle

USE EXCEPTIONS FOR  genuinely exceptional and usually unrecoverable:
                  out of memory, programmer errors, invariant violations,
                  anything where the honest response is to abort the operation

The distinction that makes this practical: if a failure is part of the domain, it belongs in the type; if it is a bug or a catastrophe, an exception is fine. "This email is already registered" is a domain outcome and should be a value the caller must handle. "The database connection pool is exhausted" is not something the pricing code can do anything about, and threading it through every signature buys nothing.

The cost of Result types in languages without built-in support is real: every call site needs unwrapping, and chains of fallible operations become nested checks unless the language offers a way to short-circuit them (Rust's ?, Kotlin's runCatching, do-notation, or a small helper). Weigh that before converting a whole codebase; the highest-value place is the boundary where inputs are validated.

6.6Functional core, imperative shell

This is the architectural pattern that packages everything above, introduced in Chapter 3 and worth stating as a rule: push side effects to the edges and keep the middle pure.

Three practical rules make it work:

  1. Pass the world in as data. Not a clock, a timestamp. Not a repository, the records already loaded. Not a random generator, a seed or the drawn value. The core should be unable to reach anything.
  2. Return decisions, not effects. The core returns "charge £40 and send a receipt" as a value; the shell performs it. This is what makes every rule testable by asserting on a returned structure.
  3. Keep the shell boring. No branching, no rules — just load, call, apply. A shell with conditionals in it has decisions that belong in the core.

The tension to be honest about: sometimes the core needs data it cannot know it needs until part-way through, and loading everything up front is wasteful. Options are to load a bit more than strictly necessary and accept it, to have the core return "I need X" as one of its outcomes and loop, or to pass in a narrowly-typed pure function that the shell has pre-populated. The first is usually right; the second is how you keep it pure when it genuinely is not.

6.7Where this costs more than it gives

Honest limits
SituationThe problemReasonable response

The version worth adopting

You do not need monads, currying or a new language. The 90% is four habits: default to immutable data; make functions pure unless they have a reason not to; separate decisions from effects; and encode constraints in types rather than in runtime checks. Every one of those is available in Java, C#, Python, Go and TypeScript, and every one of them makes code easier to test and reason about without requiring anyone to learn a new vocabulary.

Is a function that mutates a local array inside its body pure?

Yes, provided the array is created inside the function and never escapes. Purity is about observable behaviour: same inputs give the same output, and nothing outside can tell that anything happened. A local mutable accumulator is invisible to callers, so it violates nothing — and this is exactly the escape hatch that makes immutability affordable in hot code, since you can write a tight mutating loop inside a function whose contract is pure. Two ways to lose the property: returning the mutable array (callers can now modify it, and a later call might see the change if you also cached it) and mutating an array that was passed in. Return a frozen or copied result if the array leaves, and never write to an argument.

Why does "make illegal states unrepresentable" reduce code rather than add types?

Because every state a type permits must be handled somewhere, usually in several places, defensively. A Request with optional data and optional error permits eight combinations of which three are legal, so every reader writes a guard — if (r.status === "success" && r.data) — and each of those guards has a branch that cannot happen but must be written anyway, and often silently does the wrong thing. Replacing it with a discriminated union removes those five impossible combinations from existence, which removes every guard against them and every dead branch. It also converts a class of runtime bug into a compile error, and it makes exhaustiveness checking possible, so adding a fourth case produces a list of every place that must be updated instead of a silent fall-through. The type declaration is three lines longer and the code around it is considerably shorter.

Your team is sceptical of immutability because of copying costs. What is the accurate answer?

That the concern is right about deep copying and wrong about persistent data structures. Updating a persistent collection allocates only the path from the root to the changed node — everything else is shared, safely, because it cannot change. With a branching factor of 32, a million-element vector is four levels deep, so an update allocates around four nodes regardless of size. Then be honest about the two real costs: it is more allocation than in-place mutation, so it matters in genuinely hot paths, which you should measure rather than assume; and in languages without persistent collections built in, naive spread-based copying is O(n) and the shallow-copy trap is easy to hit. The practical position is immutability by default for domain data, measured mutation inside functions that stay pure at the boundary, and a library rather than hand-rolled spreads for anything large.

Recap

  1. Pure means same output for same inputs, and no observable effect. Both halves, or you lose the licences.
  2. Purity buys testability without doubles, caching, safe parallelism and local reasoning. Impurity forfeits all of them, so its placement is a design decision.
  3. Structural sharing makes immutability affordable: an update costs the depth of the tree, not its size.
  4. Spread copies one level. The shallow-copy trap is the most common immutability bug — use readonly types or a real library.
  5. Use the collection operation whose name states the shape, and fall back to a loop when none fits.
  6. Make illegal states unrepresentable. A discriminated union removes guards, dead branches and a class of bug.
  7. Domain failures are values; catastrophes are exceptions.
  8. Functional core, imperative shell: pass the world in as data, return decisions rather than effects, keep the shell free of branches.
  9. Immutability suits values, not identities. An account is an entity and should encapsulate its mutation.
  10. The four habits that carry the benefit — immutable by default, pure by default, decisions apart from effects, constraints in types — need no new language.
