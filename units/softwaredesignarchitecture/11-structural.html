Structural patterns

Seven patterns about assembling objects into larger structures. Four of them wrap another object and are constantly confused with each other, because the code looks identical and only the intent differs — which is the most useful thing this chapter can fix.

~30 min read Adapter · decorator · facade · proxy · composite 2 interactive panels Prerequisite: chapters 5, 9

11.1The four wrappers

Adapter, decorator, facade and proxy all hold a reference to something and delegate to it. In many codebases the implementations are byte-for-byte similar. They are different patterns because they answer different questions, and naming the intent correctly is what tells the next reader why the wrapper exists.

Same shape, four intents
PatternInterface of the wrapperPurposeYou have one when…
AdapterDifferent from the wrapped thingMake an incompatible interface fitYou cannot change either side and they do not match
DecoratorSame as the wrapped thingAdd behaviour, transparently and stackablyYou want retries and caching and logging, in any combination
FacadeSimpler than the subsystemHide complexity behind one entry pointCallers currently orchestrate five objects to do one thing
ProxySame as the wrapped thingControl access to it — lazily, remotely, or with a checkThe caller should not know it is not talking to the real thing
The distinguishing question for each

Adapter: did the interface change? Decorator: did behaviour get added, and can I stack another one? Facade: did several things become one? Proxy: is the wrapper deciding whether or when to call through? Decorator and proxy are the closest pair — both keep the interface identical — and the split is that a decorator augments the call while a proxy governs it. A caching wrapper is arguably either, and the honest answer is that the distinction stops paying at that point.

11.2Adapter

Structural

Adapter

Convert one interface into another so two things that were not designed together can work together.

Where it matters architecturally
This is the pattern that keeps a domain clean. Your code defines PaymentGateway in its own vocabulary; StripeAdapter translates that into Stripe's SDK. The vendor's model stops at the adapter and never enters the domain — which is also the anti-corruption layer from Chapter 14, at class scale.
Two forms
Object adapter holds an instance and delegates — the normal choice. Class adapter inherits from both, which only some languages allow and which carries the inheritance costs from Chapter 5.
Cost
A translation layer to maintain, and a leak risk: if the foreign model's concepts do not map cleanly, the adapter grows conditionals or the domain interface quietly acquires vendor-shaped methods.
Watch for
An adapter whose interface is a near-copy of the thing it adapts. That is not an adapter — it is a pass-through, and it buys nothing. The whole value is that the near side speaks your language.

11.3Decorator

Structural

Decorator

Add behaviour by wrapping, keeping the same interface, so wrappers can be stacked in any combination at runtime.

The problem it solves
The combinatorial explosion from Chapter 5. Three independent behaviours — retry, cache, log — need eight subclasses to cover every combination and three decorators to cover all of them, chosen at wiring time.
Requirement
The wrapped and wrapping types must be substitutable, so this pattern depends entirely on Liskov holding. A decorator that changes the contract is a bug that will surface at a call site that has no idea it is talking to a wrapper.
Cost
Order matters and is invisible from the call site — retry-outside-cache and cache-outside-retry behave very differently. Stack traces get deep. Debugging means knowing what the wiring built.
Where you already use it
HTTP middleware, stream wrappers, Python decorators when they wrap rather than register, and every service mesh sidecar — the same pattern, one process out.

Stacking decorators

Toggle behaviours and reorder them. The order is a design decision that the call site cannot see.

11.4Facade

Structural

Facade

One simple entry point in front of a complicated subsystem, offering the operations callers actually want.

The problem
Every caller has to know the same five-step dance: open a session, begin a transaction, resolve a policy, call three services in order, commit. That knowledge is duplicated at every call site and couples all of them to the subsystem's internals.
Mechanism
A class exposing coarse-grained operations — checkout(order) — that performs the dance internally. Callers keep the option of going underneath when they need something unusual, which distinguishes a facade from a wall.
Cost
It becomes a magnet. Every new "convenience" operation gets added until the facade is a god class knowing every subsystem, at which point it is the thing it was meant to hide. Keep it to the operations that are genuinely common.
Related
At service scale this is the API gateway and the backend-for-frontend. Same idea, one process out.

11.5Proxy

Structural

Proxy

Stand in for another object, with the same interface, to control access to it.

The four standard kinds
Virtual — defer expensive creation until first use (lazy loading; an ORM's uninitialised collection). Remote — the real object is in another process; the proxy handles the call (every RPC client stub). Protection — check authorisation before delegating. Smart reference — count references, lock, log, or cache on the way through.
The defining property
The caller believes it holds the real thing. That is the value and the hazard: a virtual proxy makes a database query on what looks like a field access, which is where the N+1 problem in ORMs comes from.
Cost
Hidden behaviour. Latency, failure and cost appear at points the code does not mark. A remote proxy makes a network call look like a method call, and that illusion is the first fallacy of distributed computing.

11.6Composite

Structural

Composite

Treat a single object and a group of objects the same way, so recursive structures need no special cases.

Mechanism
Leaf and composite both implement one interface; the composite holds children and implements each operation by delegating to them and combining the results. Client code never asks "is this one thing or many?".
Where it fits naturally
Anything genuinely tree-shaped: file systems, UI component trees, organisational hierarchies, nested permission groups, a query's boolean expression, an order with sub-orders.
Cost
The interface must be meaningful for both. A Leaf.add(child) that throws is a Liskov violation — the refused bequest from Chapter 5. Either keep child management off the shared interface, or accept that clients must check.
Watch for
Unbounded recursion depth on user-supplied structures, and operations that are O(n) over the whole tree being called in a loop.

11.7Bridge

Structural

Bridge

Separate an abstraction from its implementation so the two can vary independently — the answer when a hierarchy is trying to grow along two axes at once.

The problem
You have shapes (circle, square) and renderers (vector, raster). Inheritance forces you to pick one axis and produce VectorCircle, RasterCircle, VectorSquare, RasterSquare — the product again. Bridge makes one axis a field of the other: a Shape holds a Renderer.
Relation to strategy
Structurally identical — an object holding an interface. The distinction is intent and scope: strategy swaps one algorithm, often per call; bridge separates two hierarchies that both keep growing. If neither side is a hierarchy, you have a strategy.
Cost
Two hierarchies to navigate, and a decision at every operation about which side owns it. Only worth it when both axes genuinely vary; with one axis it is indirection for nothing.

11.8Flyweight

Structural · rarely needed

Flyweight

Share one instance of the parts that are identical across many objects, and keep only the parts that differ per object.

Mechanism
Split state into intrinsic (shared, immutable — a glyph's outline, a tile's texture, a particle's colour table) and extrinsic (per instance — position, index). Intrinsic state lives in a shared pool; extrinsic state is passed in at use.
Where it is real
Text rendering, tile maps, particle systems, and string interning — which every runtime does for you. Also every immutable value object you share rather than copy.
Cost
A pool to manage, a lookup on every access, and a hard requirement that the shared state be immutable. It is a memory optimisation and should follow a measurement, not precede one.
When it is wrong
Almost always in application code. If you are reaching for flyweight without a heap profile in front of you, you are optimising a problem you have not confirmed.

Wrappers accumulate

Each of these patterns adds a layer, and layers are individually cheap and collectively expensive: a call that passes through an adapter, two decorators, a proxy and a facade is five stack frames, five files to open while debugging, and five places a subtle contract change can hide. The specific smell is a wrapper that adds nothing — a pass-through introduced "for flexibility" that has one implementation and no behaviour. Delete those. For the rest, the useful discipline is to put the whole stack in one visible place (the composition root), so a reader can see the assembled shape rather than discovering it one go to definition at a time.

You wrap a repository to add caching. Decorator or proxy?

Both labels fit and the argument is not worth having. By the strict definitions it is a proxy — a caching proxy is one of the four canonical kinds, and the wrapper is deciding whether to call through rather than adding behaviour around a call that always happens. But if you also intend to stack it with a retrying wrapper and a logging wrapper, all sharing the interface and composable in any order, then it is functioning as a decorator and calling it one will communicate more to the next reader. The distinction that actually matters for the design is not the name: it is whether the wrapper preserves the contract. A cache that can return stale data has weakened a postcondition, which is the Liskov problem from Chapter 7 — and that is worth arguing about, because it determines whether callers can safely be given the wrapper without being told.

Why is decorator order a design decision rather than an implementation detail?

Because it changes behaviour, and the call site cannot see it. Consider retry and cache. retry(cache(db)) means a cache miss is retried, so a transient database failure is retried and the successful result is cached — usually what you want. cache(retry(db)) means the cache sits outside, so a hit skips the retry logic entirely and, more importantly, a failure that gets cached is served repeatedly without ever retrying. Add logging and the question becomes whether you want to log every attempt or only the outer call. Add a circuit breaker and the ordering determines whether retries count towards tripping it. None of that is visible at repo.find(id) — it is decided entirely by the wiring, which is a strong argument for keeping the whole stack in one readable place and for a comment stating why that order.

Your facade has grown to 40 methods. What went wrong and what do you do?

It became a magnet, which is the predictable failure of the pattern: a facade is the obvious place to add "one more convenience method", nobody is responsible for saying no, and the accumulation is invisible until it is a god class that knows every subsystem — concrete, depended on by everything, and sitting in the zone of pain from Chapter 8. The productive move is to group the 40 methods by caller rather than by subsystem, and you will usually find three or four distinct client roles each using a handful. Split along those roles, which is interface segregation applied to a facade, and each client depends only on the operations it uses. Anything left over that fits no role is usually not a facade operation at all but domain logic that drifted in, and it belongs in the domain. Finally, add the rule that a facade operation must correspond to a complete use case — if it takes a caller three facade calls to do one thing, the abstraction is at the wrong level and the dance has simply moved.

Recap

  1. Four patterns wrap something and differ only in intent: adapter translates, decorator adds and stacks, facade simplifies, proxy governs access.
  2. Adapter is what keeps a foreign model out of your domain — the anti-corruption layer at class scale. An adapter that mirrors what it adapts is a pass-through, not an adapter.
  3. Decorator turns a product of subclasses into a sum of wrappers, and depends entirely on Liskov holding.
  4. Decorator order changes behaviour and is invisible at the call site. Keep the stack in one place and say why that order.
  5. Facades become god classes. Scope them to complete use cases and split by client role when they grow.
  6. Proxies hide latency and failure behind ordinary-looking calls — the source of ORM N+1 and of the belief that remote calls are cheap.
  7. Composite needs an interface meaningful for leaves; otherwise you get refused bequest.
  8. Bridge is strategy applied to two hierarchies. With one axis you do not need it.
  9. Flyweight follows a heap profile. Reaching for it without one is optimising an unconfirmed problem.
