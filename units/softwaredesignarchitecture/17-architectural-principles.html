Architectural principles

Architecture is the set of decisions that are expensive to reverse, and the discipline is mostly about deferring them and pointing dependencies so that the expensive things depend on the cheap ones rather than the other way round. Six named principles govern how code is grouped into components and how those components may refer to each other.

~30 min read Boundaries · policy vs detail · component principles 2 interactive panels Prerequisite: chapters 7, 8

17.1What architecture is

The most useful definition is Fowler's, quoting Ralph Johnson: architecture is the decisions that are hard to change — and the corollary, that a good architect's job is to reduce the number of such decisions and postpone the rest.

That reframes the whole subject away from diagrams. The goal of an architecture is not to be correct; it is to keep as many options open for as long as possible, so that the decisions you must make are made with the most information you will ever have. A design that requires the database, the framework, the delivery mechanism and the deployment topology to be settled in week one has committed to five things while knowing least about all of them.

The test for whether a decision is architectural

Not "is it important?" but what would it cost to change in six months? Which JSON library you use is not architectural even though it appears in every file — swapping it is a search and replace. Whether the domain can be tested without a database is architectural, even though it is invisible in the running system, because reversing it is a rewrite. Chapter 1's reversibility criterion, applied at the largest scale.

17.2Boundaries

A boundary is a line across which dependencies are controlled. Drawing one costs something and buys something, and the trade differs enormously by how you draw it.

Boundary strength and what it costs to cross
KindEnforced byCrossing costWhat it buys
Convention — a directoryNothing but disciplineA function callAlmost nothing; it will be crossed
Module / packageVisibility rules, lint rules, an import checkerA function callA lot, for free — the best value on this table
Compiled component — a libraryThe build systemA function call; a build step to changeIndependent versioning and release
Process — separate deployableThe operating systemSerialisation, IPCIndependent deployment and failure isolation
Service — across a networkThe networkLatency, partial failure, versioning, operationsIndependent scaling, teams and technology

The row worth dwelling on is the second. A module boundary enforced by an import rule gives you most of the architectural benefit at nearly none of the cost. It prevents the dependency you did not want, it makes the boundary visible in the build, and moving it later is a refactoring. Teams frequently jump from "convention" straight to "service", paying network cost for a boundary they could have had by configuring a linter — and then discovering the boundary was in the wrong place, which is now a migration rather than an afternoon.

17.3Policy and detail

Every system contains policy — the business rules, the reason it exists — and details, which are the mechanisms by which policy reaches the world. The central architectural claim is that this list is all detail:

Details, every one of them 
the database          Postgres vs Mongo does not change what a
                      valid order is

the web               HTTP is a delivery mechanism. The same rules
                      could be driven by a CLI, a queue, a batch job

the framework         Spring, Rails, Django — none of them are
                      your business

the UI                one of several possible views of the policy

the message broker    a transport

the cloud provider    where the process happens to run

the file format       how bytes are arranged in transit

Policy is what remains when you remove all of them:
what is true about the business, and what must happen when.

The practical consequence is the dependency rule: source dependencies must point from detail towards policy, never the reverse. The database module imports the domain; the domain never imports the database. Everything in Chapter 19 is one way of drawing that rule.

It is worth being precise about what this claim is and is not. It does not say the database is unimportant — a wrong choice can sink a product. It says the business rules should not be written in terms of it, so that if the choice turns out wrong, changing it is a project confined to one component rather than a rewrite. The value is measured in what a change costs, not in purity.

17.4The three component cohesion principles

Given a pile of classes, which go together in one component? Robert Martin names three principles that pull in different directions, and the tension between them is the point.

Cohesion · REP

Reuse / release equivalence

The unit of reuse is the unit of release. If people are to depend on your component, it must be versioned, released and have a changelog — you cannot reuse something that is not released.

Pulls towards
Grouping classes that make sense as a coherent thing to publish and version together. It is the principle that says a component needs a name and an audience.
Cohesion · CCP

Common closure

Classes that change together belong together. A single change should ideally affect one component, not seven.

Pulls towards
Larger components, grouped by reason to change — the single-responsibility principle at component scale. This is the principle that argues against splitting by technical layer, since a feature change then touches every layer.
Cohesion · CRP

Common reuse

Classes that are not used together should not be grouped together. Depending on a component means depending on everything in it.

Pulls towards
Smaller components. It is interface segregation at component scale: if you use two classes from a component of forty, you are still coupled to the release cycle of all forty, and every change to any of them forces you to revalidate.

The cohesion tension

The three principles cannot all be maximised. Where you sit on the triangle should follow project maturity.

The resolution changes over a project's life

Early on, common closure dominates: nobody is reusing your components, so optimise for the change landing in one place. Larger, feature-shaped components are correct. Later, as external consumers appear, common reuse and release equivalence start to matter and the pressure is towards splitting. Martin's observation is that a component structure that is right at the start is usually wrong later — which is an argument for treating component boundaries as something you revisit deliberately, not as something decided once.

17.5The three component coupling principles

Coupling · ADP

Acyclic dependencies

The component dependency graph must have no cycles.

Why a cycle is fatal at this scale
Components in a cycle cannot be built, tested, versioned or released independently — they are one component pretending to be several. Changing any of them requires revalidating all of them, and a new developer cannot understand any one without understanding the whole loop.
Two ways to break one
Dependency inversion: put an interface in the component that is being depended upon backwards, and have the other implement it — the arrow flips. New component: extract the shared thing both need into a third component that both depend on.
How they appear
Never deliberately. Someone adds one import to solve a problem, and the cycle forms. The only reliable defence is a build-time check, which is cheap and catches it on the day it happens rather than a year later.

Cycle detector

Toggle dependencies between components. Cycles are found by depth-first search and highlighted.

Analysis

Coupling · SDP

Stable dependencies

Depend in the direction of stability. A component should only depend on components that are harder to change than it is.

Measured
With the instability metric from Chapter 8: I = Ce / (Ca + Ce). Every dependency edge should point from higher I to lower I.
When it is violated
A stable component depends on a volatile one, so every change to the volatile thing ripples into something many others rely on. Fix it by inverting that specific edge: define the interface in the stable component and have the volatile one implement it.
Coupling · SAP

Stable abstractions

A stable component should be abstract, so it can be extended without being modified.

The pairing
SDP says depend towards stability; SAP says stable things must be abstract, or stability becomes rigidity. Together they produce the main sequence, and the two failure corners: concrete and depended-upon is the zone of pain, abstract and unused is the zone of uselessness.

17.6Independence, and what you are actually buying

Architectural boundaries buy independence, and it is worth naming which kind, because they are separable and cost different amounts.

Four independences
IndependenceMeansCheapest boundary that gives it
DevelopabilityTeams can work without constantly collidingModule boundaries with clear ownership
TestabilityPolicy can be tested without infrastructureDependency inversion at the infrastructure edge
DeployabilityOne part can be released without releasing the restSeparate deployable units
OperabilityOne part can be scaled, restarted or fail aloneSeparate processes, usually across a network

The rows are in cost order and the first two are almost free, which produces the most useful piece of architectural advice available: take the cheap independences first, and buy the expensive ones only when you have a demonstrated need. A modular monolith with enforced module boundaries and an inverted infrastructure edge has developability and testability in full, and can be split later along boundaries that have already proved themselves.

17.7Deferring decisions

If architecture is the expensive decisions, the skill is arranging things so that fewer of them must be made early. Four techniques:

  1. Put the volatile thing behind an interface you own. The decision becomes a swap rather than a migration. This is dependency inversion used as a scheduling tool.
  2. Keep the decision out of the middle. A framework used at the edges can be replaced; a framework whose base classes your domain extends cannot.
  3. Write the policy first and the mechanism second. If the business rules exist and pass tests before a database is chosen, the choice is genuinely deferred rather than deferred in name.
  4. Prefer the reversible option when they are close. A modular monolith and a set of services may look similar in effort; one can become the other and the reverse is much harder.
And the counterweight, because this can be overdone

Deferring is not free either. An abstraction over a decision you will never revisit is over-engineering, and a system that has deferred everything has committed to nothing and can be reasoned about by nobody. The judgement is the same one from Chapter 1: how expensive is this to reverse, and how uncertain am I? Defer the expensive and uncertain. Decide the cheap ones now and stop thinking about them.

Why is a cycle between two components worse than a cycle between two classes?

Because the unit of release is the component. Two classes in a cycle are unpleasant to read and can still be compiled, tested and deployed as one unit without anyone noticing — the damage is comprehension. Two components in a cycle cannot be built independently, cannot be versioned independently, and cannot be released independently: to build A you need B, and to build B you need A, so the build must treat them as one thing. That destroys the main reason components exist. It also spreads — a cycle involving three components effectively merges all three, and each new edge into the loop enlarges the merged blob. Practically, the reason to care is that this happens by accident: nobody proposes a cycle, someone adds an import that closes one, and the cost is not felt until months later when a release cannot be cut. A build-time acyclicity check costs almost nothing and catches it on the day.

Your team wants microservices for "independence". What would you want to establish first?

Which independence they mean, because four different things travel under that word and they cost wildly different amounts. If the pain is teams colliding in the same files, that is developability and a module boundary with clear ownership fixes it — no network required. If the pain is slow tests that need a database, that is testability and dependency inversion at the infrastructure edge fixes it. Those two are nearly free. If the pain is that one team's release is blocked behind another's, that is deployability and genuinely needs separate deployable units — though separate deployables from one repository are often enough, without a network between them. Only if the pain is that one component needs to scale or fail separately from the rest does the network boundary earn its cost, and that cost is substantial: latency, partial failure, distributed tracing, versioned contracts, and an on-call burden. The productive move is to establish the module boundaries first, because they are cheap, reversible, and they tell you where the service boundaries would go — and quite often the cheap fix removes the pain that motivated the expensive one.

Is "the database is a detail" a serious claim, given how much of a system it determines?

It is a claim about dependency direction, not about importance — and read that way it holds. Nobody sensible argues that database choice is unimportant; a wrong one can be fatal, and the data model is often the most consequential decision in a system. What the principle says is narrower: your business rules should not be written in terms of the database, so that the rules remain understandable, testable and intact if the storage choice changes. In practice that means a domain that does not import the driver or the ORM's base classes, and repository interfaces defined in the domain's language rather than the schema's. Two honest caveats. First, the data model is not as deferrable as the data store — getting the entities and relationships wrong is expensive regardless of which engine holds them. Second, some systems are genuinely database-shaped: a reporting tool whose entire purpose is running queries gains little from pretending storage is an implementation detail, and forcing the rule there produces ceremony. The principle earns its keep where there is real policy to protect.

Recap

  1. Architecture is the decisions that are hard to change, and the job is to have fewer of them and postpone the rest.
  2. Module boundaries enforced by an import rule are the best value on the boundary table — most of the benefit at almost none of the cost.
  3. The database, the web, the framework and the UI are details. Source dependencies point from detail towards policy.
  4. REP, CCP and CRP pull against each other. Common closure dominates early; common reuse matters once there are external consumers.
  5. No cycles between components, or they are one component pretending to be several. Break them with dependency inversion or a new shared component.
  6. Depend towards stability, and make stable components abstract — SDP and SAP together produce the main sequence.
  7. Four independences — developability, testability, deployability, operability — in ascending cost. Take the cheap ones first.
  8. Defer expensive, uncertain decisions; decide the cheap ones immediately and stop thinking about them.
