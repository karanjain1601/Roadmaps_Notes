Object-oriented programming

Four ideas get recited — encapsulation, abstraction, inheritance, polymorphism — and three of them are routinely misunderstood in ways that produce worse code than not using objects at all. This chapter is what each one is actually for, which of them earns its place most often, and where behaviour belongs when the answer is not obvious.

5.1What objects are for

The standard explanation — objects model the real world — is where most bad object-oriented code comes from. It produces a Car with a drive() method in a system that only ever needs to price and insure cars, and it invites arguments about whether a Manager "is a" Employee in a payroll system where the distinction is a boolean.

A more useful statement: an object is a bundle of state plus the only code allowed to change it, exposed through an interface that hides how it works. Two things follow, and they are the two jobs objects do well.

  1. Protecting an invariant. Something must own the rule "a balance may never be negative" and be the only route to changing the balance. That is what a class is for, and a bag of functions over a plain record cannot do it, because anything can construct the record.
  2. Being substitutable. Several implementations satisfy one interface, so the caller depends on the idea rather than on any of them. That is what makes dependency direction controllable, per Chapter 4.

If a piece of code does neither — no invariant, no substitution — it probably does not need to be a class. A module of functions is simpler, and simpler wins by default.

5.2Encapsulation

Encapsulation is not "make fields private and add getters and setters". A class with a private field, a getter and a setter has exactly the same interface as a public field, with more typing — every caller can read it and every caller can set it to anything. Nothing is encapsulated.

The real test

Encapsulation means there is a statement about this object's state that is always true, and no caller can make it false. If you cannot name such a statement, the class is a record with ceremony. If you can name one but a caller can break it, the encapsulation is decorative.

Private fields, no encapsulation
class Order {
  private items: Item[] = [];
  private total = 0;
  private status = "draft";

  getItems()  { return this.items; }      // leaks the array
  setTotal(t: number) { this.total = t; } // anyone can lie
  setStatus(s: string) { this.status = s; }
}

// Every invariant is breakable from outside:
order.getItems().push(item);   // total is now wrong
order.setTotal(-999);          // negative total
order.setStatus("shipped");    // shipped without payment
Invariants that hold
class Order {
  private constructor(
    private readonly items: readonly Item[],
    private status: Status
  ) {}

  static draft() { return new Order([], Status.Draft); }

  add(item: Item): Order {                 // returns a new Order
    if (this.status !== Status.Draft)
      throw new IllegalTransition(this.status, "add");
    return new Order([...this.items, item], this.status);
  }

  get total(): Money {                     // derived, never stored
    return this.items.reduce((s, i) => s.plus(i.subtotal()),
                             Money.zero());
  }

  markPaid(p: Payment): Order {
    if (!p.covers(this.total)) throw new Underpaid();
    return new Order(this.items, Status.Paid);
  }
}

Four techniques did the work there, and they generalise:

Do not leak mutable internals
Returning the internal array hands out a key to the object's state. Return a copy, a read-only view, or better, do not return the collection at all — expose the operations callers actually want.
Derive rather than store
total cannot disagree with the items if it is computed from them. Every stored duplicate of derivable state is an invariant you must maintain by hand.
Model state transitions, not state
setStatus allows any transition, including nonsensical ones. markPaid, ship, cancel allow exactly the legal ones, and each can check its precondition.
Make illegal construction impossible
A private constructor plus named factory methods means an Order can only come into existence in a valid state. This is far stronger than validating afterwards.

Break the object

Two implementations of the same class. Try to put each into an illegal state.

5.3Abstraction and interfaces

An interface is a promise about behaviour with the implementation deliberately omitted. Its value is proportional to how many implementations it hides and how stable the promise is — an interface with one implementation that changes whenever that implementation changes is a second file with no benefit.

Interface or abstract class?
InterfaceAbstract class
Says"Anything that can do this""A kind of this, with some of it already written"
Carries stateNoYes
Multiple inheritanceA class can implement manyUsually one only
Coupling createdMinimal — only the signaturesStrong — subclasses depend on protected members and call order
Adding a member laterBreaks implementers, unless defaultedCan be added with a default body
Use whenDefining a capability, a boundary, a plugin point — the default choiceGenuine shared implementation between close variants, and you control all of them

A rule that avoids most trouble: the interface belongs to the caller, not the implementer. If the payment module defines PaymentGateway and the Stripe adapter implements it, the dependency points from the adapter into the domain — which is what you want. If Stripe's SDK defines the shape and your domain conforms to it, the dependency points outwards and you have coupled your rules to a vendor. Same number of files, opposite architecture. Chapter 7 calls this dependency inversion; Chapter 19 builds a whole architecture on it.

5.4Polymorphism

Polymorphism is one name doing different work depending on the receiver. Mechanically it is a table of function pointers; architecturally it is the ability to add behaviour without editing existing code, which is the open-closed principle from Chapter 7.

Conditional on type
function fee(account: Account): Money {
  if (account.kind === "basic")   return Money.of(5);
  if (account.kind === "premium") return Money.of(0);
  if (account.kind === "business")
    return account.seats > 10 ? Money.of(50) : Money.of(80);
  throw new Error("unknown kind");
}

// …and the same switch again in statementFor(),
// and in limitsFor(), and in canOverdraw().

Adding an account type means finding every one of those conditionals. Missing one is a runtime bug in an unrelated feature.

Behaviour on the type
interface Account {
  monthlyFee(): Money;
  limits(): Limits;
  canOverdraw(): boolean;
}

class BusinessAccount implements Account {
  monthlyFee() {
    return this.seats > 10 ? Money.of(50) : Money.of(80);
  }
  …
}

// Adding CharityAccount: one new file, zero edits elsewhere.
Polymorphism is not always the win

It optimises one axis — adding a type — and pessimises the other — adding an operation. With a conditional, adding taxTreatment() is one new function in one place; with polymorphism it is a change to the interface and every implementing class. This is the expression problem, and it has no free answer. Choose based on which axis actually moves: if types are stable and operations keep arriving, a conditional or a visitor is the better shape, and the switch statement everyone was taught to eliminate is correct. Note also that a single conditional appearing once is fine; the smell is the same conditional repeated across several functions.

5.5Inheritance, and what it really couples

Inheritance is the most overused feature in object orientation, because it looks like reuse and is actually the tightest coupling available. A subclass depends not just on its parent's public interface but on its protected members, its internal call sequence and its unstated assumptions — and none of that is visible from the subclass's file.

The fragile base class problem 
class Counter {
  protected n = 0;
  add(x: number)          { this.n += x; }
  addAll(xs: number[])    { for (const x of xs) this.add(x); }
}

class LoggingCounter extends Counter {
  add(x: number)       { log(x); super.add(x); }
  addAll(xs: number[]) { xs.forEach(log); super.addAll(xs); }
}

new LoggingCounter().addAll([1, 2]);
  // logs 1, 2 … then super.addAll calls this.add, which logs again.
  // Every value is logged twice.

Now the base class author "optimises" addAll to sum directly
instead of calling add. Nothing in the subclass changed.
The double logging disappears — and so does the logging in add.
The base class made no interface change, and the subclass broke.

The failure is not the double logging; it is that the subclass depended on an implementation detail of the parent — whether addAll calls add — that the parent never promised and can change at any time. Every use of inheritance carries some version of this exposure.

Composition over inheritance

The alternative is to hold the other object rather than to become it. That converts an invisible dependency on internals into a visible dependency on an interface.

Inheritance versus composition, counted

What happens to the number of classes as independent variations multiply.

When inheritance is right: when there is a genuine "is-a" relationship that satisfies the Liskov substitution principle (Chapter 7), when the hierarchy is shallow and you own every level, and when the base class is designed for extension — documented extension points, no self-calls that subclasses might override, or explicitly sealed. A template method with two or three protected hooks is a legitimate and useful pattern. A five-level hierarchy where the fourth level overrides half the third is not.

5.6Visibility is a design decision

Every public member is a promise you have to keep. The default should be the most restrictive visibility that works, widened only on demand — because widening is easy and narrowing means breaking callers.

What each level actually commits you to
VisibilityCommitmentUse for
privateNone outside this class. Change it freelyEverything, by default
package / module-privateStable within the module onlyCollaboration between closely related classes — the most underused level
protectedAn extension contract with every subclass, present and futureDeliberate template-method hooks, documented as such
publicA contract with the whole codebase, and with other teamsThe intended interface, and nothing else

Module-private is worth calling out. It lets a cluster of classes cooperate closely while presenting one small surface to the rest of the system, which is precisely the shape of a well-designed component — and it is the code-level version of the bounded context in Chapter 14. Languages without it (TypeScript, Python) approximate it with a single entry-point module that re-exports only the intended surface, and a convention that nothing imports past it.

5.7Anemic domain models

An anemic model is one where the classes hold data and nothing else — all fields, getters and setters — while every rule lives in a separate "service" class that reads the data, decides, and writes it back. Martin Fowler named it an antipattern because it takes the cost of objects and collects none of the benefit: nothing owns any invariant, so the encapsulation in §5.2 is impossible.

Anemic
class Order {                 // data only
  items: Item[];
  status: string;
  total: number;
}

class OrderService {          // all the rules, far from the data
  addItem(o: Order, i: Item) {
    if (o.status !== "draft") throw …;
    o.items.push(i);
    o.total += i.price * i.qty;   // must remember to do this
  }
}

Any code can mutate an Order without going through the service, and any new service can forget the total. The rules are advisory.

Behaviour with the data
class Order {
  add(item: Item) {
    this.guardDraft();
    this.items.push(item);
  }
  get total(): Money { /* derived */ }
  private guardDraft() { … }
}

// Services still exist — for orchestration, not for rules:
class Checkout {
  run(order: Order, payment: Payment) {
    order.markPaid(payment);
    this.repo.save(order);
    this.events.publish(new OrderPaid(order.id));
  }
}
When anemic is the right answer

The criticism only applies where there is a domain with rules. Plenty of code has none: a CRUD screen that validates a form and writes a row has no invariant beyond the database constraints, and wrapping it in a rich model is ceremony. Data transfer objects at boundaries should be anemic — they exist to carry values across a wire, and behaviour on them would be misplaced. The question is not "is this class anemic" but "are there rules here, and if so, is anything enforcing them?"

5.8Where behaviour belongs

The recurring question in object design is which class a piece of logic goes in. Three heuristics resolve most cases.

Tell, don't ask
If you find yourself pulling data out of an object to make a decision about it, the decision belongs inside. if (account.getBalance() < amount) … should be account.canWithdraw(amount) — the logic moves next to the data it needs, and the rule now exists in one place instead of at every call site.
Feature envy
A method that uses another object's data more than its own is in the wrong class. Move it to the class whose data it keeps reaching for. This is the single most productive refactoring in object-oriented code.
Information expert
Assign a responsibility to the class that already has the information needed to fulfil it. If the answer needs data from three classes, either one of them should own the others, or you need a new concept that coordinates them — often a value object or a domain service.

The counterweight, because "tell don't ask" taken absolutely produces its own problem: some logic genuinely spans several objects and belongs to none of them. Pricing an order against a promotion and a customer's tier is not the order's job, not the promotion's, and not the customer's. That is a domain service — a stateless object named after the operation, holding logic that has no natural home. It is a legitimate answer, and the mark of misuse is when every rule ends up there.

5.9Class-level smells

Recognisable shapes, and what each one is really telling you
SmellLooks likeUnderlying problem
God classOne class of 2 000 lines, imported everywhere, named Manager or Helper or UtilsNo boundaries. Several actors' concerns in one file, per Chapter 2
Data classOnly fields, getters and settersFine as a DTO; a symptom if it has rules that live elsewhere
Feature envyA method calling other.getX() five timesThe method is in the wrong class
Inappropriate intimacyTwo classes each reaching into the other's internalsThey are one concept, or the boundary is in the wrong place
Refused bequestA subclass overriding inherited methods to throw or do nothingNot an "is-a". Liskov violation — use composition
Shotgun surgeryOne conceptual change touching eleven classesA concept is scattered; it wants to be gathered into one place
Divergent changeOne class changed for three unrelated reasonsThe mirror image: one file holding three concepts
Primitive obsessionstring for an email, number for moneyMissing value objects — see Chapter 15

The last two are a matched pair and worth remembering together: shotgun surgery means a concept is too spread out; divergent change means a class is too gathered. One is fixed by moving things together, the other by splitting them apart, and both are detected by the same question — what changes together should live together.

A class has private fields and a getter and setter for each. Is it encapsulated?

No. Its interface is identical to a class with public fields — every caller can read every value and set it to anything — so nothing is hidden and no rule is protected. What you have paid for is boilerplate. The test to apply is: name a statement about this object that is always true and cannot be falsified from outside. If you cannot name one, the class is a record, and it should probably be a record — a plain data structure with no pretence. If you can name one, then work out which setter breaks it and replace that setter with an operation that expresses the legal transition and checks its precondition. Getters are less harmful than setters, but they still leak: returning a mutable collection or a mutable object hands out a route to the state regardless of the field's visibility.

When is a switch on a type field the right design rather than a missing polymorphism?

When the set of types is stable and the set of operations is not — the other half of the expression problem. If you have three payment types that have not changed in four years and you keep adding operations (settlement, refunds, reporting, reconciliation, tax treatment), polymorphism makes every new operation a change to the interface and to all three classes, while a conditional makes it one new function in one place. It is also right when the conditional appears exactly once: the smell is the same switch duplicated across functions, because that is what makes adding a type dangerous. And it is right when the behaviour does not belong to the type at all — a rendering rule for account kinds belongs in the rendering layer, not on the account, and pushing it onto the domain object to avoid a conditional couples the domain to the UI.

Your codebase has UserService, OrderService and PaymentService, each 800 lines, and the model classes are all getters and setters. What would you change first, and what would you leave alone?

First, find the invariants — the statements that ought to always be true and currently are not enforced anywhere ("an order cannot be shipped before payment", "a balance cannot go negative"). Move exactly those rules into the model classes, with operations named after the transitions rather than setters, and remove the setters that make them breakable. That is the highest-value change because it converts advisory rules into enforced ones. Leave alone: pure orchestration in the services — loading, saving, publishing events, calling other services — which is genuinely their job and should stay. Also leave alone any part of the system that has no rules; a CRUD area with only database constraints gains nothing from a rich model. The test for each candidate method is Fowler's: does this method use another object's data more than its own? If yes, move it. If the service is left with sequences of calls and no decisions, you have finished.

Recap

  1. Objects are for protecting invariants and for substitutability. Code doing neither is better as functions.
  2. Encapsulation means an unbreakable statement about state, not private fields with accessors. Do not leak mutable internals; derive rather than store; model transitions, not state.
  3. The interface belongs to the caller. Same files, opposite architecture depending on which side defines it.
  4. Polymorphism makes adding a type free and adding an operation expensive. The expression problem has no free answer — choose by which axis moves.
  5. Inheritance couples you to a parent's internals and call order, not just its interface. Prefer composition; use inheritance where substitutability genuinely holds and the base is designed for it.
  6. Visibility is a promise. Default to private; module-private is the most underused level.
  7. Anemic models are a problem only where there are rules. DTOs and CRUD are legitimately anemic.
  8. Tell don't ask, follow feature envy, assign to the information expert — with domain services for logic that genuinely spans objects.
  9. Shotgun surgery and divergent change are mirror images. What changes together should live together.
