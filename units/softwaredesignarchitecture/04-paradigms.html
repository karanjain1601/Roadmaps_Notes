The three paradigms

Structured, object-oriented and functional programming are usually taught as three toolkits you choose between. They are better understood as three restrictions: each one takes away a capability the machine offers, and gets something back in exchange. Knowing which capability each removes explains what each is for, and why every serious codebase uses all three at once.

4.1A paradigm is a discipline, not a feature

The machine will let you do anything. You can jump to any address, call through any pointer, and write to any location at any time. Every paradigm in the last sixty years has been a proposal to stop doing one of those things, on the grounds that the freedom costs more than it is worth.

Robert Martin's framing, and it is the most useful one
ParadigmRemovesIn exchange for
Structured (1968)Unrestricted goto — direct transfer of controlFunctions that can be reasoned about and decomposed independently
Object-oriented (1966)Unrestricted function pointers — indirect transfer of controlSafe polymorphism, and therefore control over the direction of dependencies
Functional (1958)Unrestricted assignment — mutationReferential transparency: code you can reason about locally, cache and parallelise

Two things follow immediately. First, no paradigm adds power — each one is strictly less capable than raw machine code, which is the point. Second, they are not alternatives. They remove different things, so you can adopt all three, and modern code does: functions instead of jumps, interfaces where you need substitutability, immutable values where you need to reason.

Why "removes a capability" is the right lens

It converts unanswerable arguments — "is OOP better than FP?" — into answerable ones: is the freedom being removed causing me problems here? If nothing in this module has aliasing bugs or concurrency, the discipline on mutation buys little. If your business rules are welded to a database driver, the discipline on indirect transfer of control buys a great deal. Each restriction has a price and a payoff, and both are situational.

4.2Structured programming

Dijkstra's argument in 1968 was not aesthetic. It was that unrestricted goto makes a program impossible to reason about, because you cannot know how control arrived at a line, so you cannot state what is true when it does. Remove the jumps and every block has a single entry and a single exit — which means you can state a precondition and a postcondition for it, and reason about the block without reading the rest of the program.

Böhm and Jacopini had shown that three constructs suffice for any computable function: sequence, selection (if/else) and iteration (loops). Everything else is convenience. That result is what made functional decomposition possible, and functional decomposition is the foundation everything else in this unit is built on — you cannot extract a function from code that can be jumped into from three places.

Unrestricted control flow
  i = 0
loop:
  if i >= n goto done
  if data[i] < 0 goto skip
  total = total + data[i]
skip:
  i = i + 1
  goto loop
done:
  print total

What is true at skip:? It depends which of two paths arrived, and the only way to know is to trace every jump. You cannot extract any part of this without reading all of it.

Single entry, single exit
const total = data
  .filter(x => x >= 0)
  .reduce((a, b) => a + b, 0);

Each stage has a stated input and output. You can name it, test it, replace it and reason about it without looking anywhere else.

The reason this paradigm feels invisible today is that it won completely — languages simply stopped offering the freedom. But the discipline still bites in modern code, in three places: deep nesting recreates the same "how did I get here" problem, which is why guard clauses help; exceptions are a controlled goto across stack frames, which is why "throw from anywhere, catch far away" is hard to follow; and unstructured concurrency — firing off tasks that outlive the function that started them — reintroduces exactly Dijkstra's problem at a larger scale, which is what structured concurrency (nurseries, scopes, errgroup) exists to fix.

4.3Object-oriented programming

The definition taught in most courses — encapsulation, inheritance, polymorphism — is a list of features, and two of the three predate OOP or are available without it. C had encapsulation via header files and opaque pointers; C had polymorphism via function-pointer tables. What object orientation added was making indirect transfer of control safe and convenient enough to use everywhere, and that is a bigger deal than it sounds.

Here is why it matters, and it is the single most important architectural idea in the paradigm. Normally, source dependencies point in the same direction as calls: if A calls B, then A's source must mention B. Polymorphism lets you break that.

So the honest one-line answer to "what is OOP for" is: it is the tool for making dependencies point where you want them to point rather than where the calls go. Encapsulation and inheritance are secondary; dependency inversion is the payoff. Chapter 5 covers the mechanics, Chapter 7 covers the principle, and Chapter 19 covers the architectures built on it.

4.4Functional programming

The restriction is on assignment. In the strictest form, a name is bound once and never rebound; a data structure, once built, never changes. What that buys is referential transparency: an expression can be replaced by its value without changing the program's meaning.

That sounds abstract until you notice how much of debugging is defeating its absence. If order.total can be mutated by anything holding a reference, then answering "what is the total here?" requires knowing everything that ran before, in what order, on which thread. If it cannot change, the answer is local — you look at where it was constructed and you are done.

What mutation costs, concretely 
// 1 · Aliasing: two names, one object
const defaults = { currency: "GBP", items: [] };
const order    = defaults;              // NOT a copy
order.items.push(item);                 // defaults is now polluted,
                                        // for every future caller

// 2 · Action at a distance
function applyDiscount(order) { order.total *= 0.9; }
applyDiscount(order);
render(order.total);   // was the discount applied once? twice?
                       // did anything else touch it in between?

// 3 · Concurrency: the interleavings are the problem
balance = balance - amount;   // read, subtract, write — three steps,
                              // and another thread can run between any two

// 4 · You cannot cache what might change
memoise(priceOf)   // safe only if priceOf depends on nothing mutable

Every one of those disappears under immutability, and none of them are exotic — items 1 and 2 account for an enormous share of ordinary bugs in ordinary code. The cost is that you must produce a new value instead of editing in place, which means allocation, and it means that updating something deep inside a nested structure is more work to express. Section 4.6 and Chapter 6 deal with both.

4.6They compose, and good code uses all three

The paradigms restrict different freedoms, so there is no conflict in adopting all of them. A well-designed modern codebase typically looks like this, and none of it is a compromise:

Where each discipline earns its place in one codebase
LayerDominant disciplineWhy
Business rules and calculationsFunctional — pure functions over immutable valuesTestable without doubles, cacheable, no ordering surprises
Domain model with invariantsObject-oriented — encapsulated state, methods that protect itInvariants need a gatekeeper; a bag of functions cannot enforce one
Boundaries to the outside worldObject-oriented — interfaces with swappable implementationsDependency inversion is exactly what interfaces are for
Orchestration and workflowsStructured — plain sequences, conditionals and loopsNothing clever needed; readability is the whole requirement
Collection processingFunctional — map, filter, reduceThe operation's shape is in the name; no index errors
Hot inner loopsProcedural — mutable buffers, explicit indicesAllocation matters here and only here; localise the ugliness
Paradigm purity is its own antipattern

Forcing everything into objects gives you DiscountCalculationStrategyFactory where a function would do. Forcing everything into pure functions gives you a monad stack to update one field, and an invariant nobody enforces because there is no object to enforce it in. Forcing everything procedural gives you the 4 000-line file. In each case the discipline was applied where the freedom it removes was not causing a problem — which means the price was paid and the payoff was not collected.

4.7The other paradigms worth naming

Not on the roadmap, but they come up
ParadigmIdeaWhere you have met it
DeclarativeState what you want, not how to get it. The engine decides the howSQL, CSS, HTML, Terraform, Kubernetes manifests, regular expressions
LogicState facts and rules; the system derives conclusionsProlog, Datalog, type checkers, constraint solvers, some policy engines
Reactive / dataflowDeclare relationships between values; changes propagate automaticallySpreadsheets, RxJS, signals in modern UI frameworks, Excel is the purest example
Data-orientedOrganise by how memory is accessed, not by conceptual entitiesEntity-component systems in games, columnar databases, SIMD-heavy code
Actor modelIsolated state, communication only by messageErlang/Elixir, Akka, and every distributed system whether it admits it or not

Two of these deserve more attention than they get. Declarative is the highest-leverage style available when a good engine exists — a SQL query you did not have to write a join algorithm for is a large amount of code you do not own. And data-oriented design is the correction to a real failure of naive OOP: an array of objects scattered across memory is dramatically slower to traverse than a few contiguous arrays of fields, and in performance-critical code that difference dwarfs everything else in this unit.

4.8Choosing per problem

The practical question is never "which paradigm is my project" but "which discipline does this piece of code need". A short decision aid:

  1. Is this a transformation from inputs to outputs? Functional. Pure function, immutable values, no reason to involve an object.
  2. Does this hold state with rules about what states are legal? Object-oriented. Something must own the invariant and reject illegal transitions.
  3. Is this a boundary to something I might replace or need to fake? Object-oriented. An interface, with the dependency pointing inwards.
  4. Is this a sequence of steps a human needs to follow? Structured. Plain, boring, readable procedure.
  5. Is this a set of relationships that must stay in sync? Reactive or declarative, if the platform offers it.
  6. Is this the 1% that is performance-critical and measured? Whatever the hardware wants, isolated behind a clean interface so the ugliness does not spread.
If each paradigm only removes capabilities, in what sense is any of them an advance?

Because the capability removed was being used to write programs nobody could reason about, and reasoning is the bottleneck. Unrestricted goto is strictly more powerful than structured control flow, and that power made it impossible to state what was true at any point in a program — so decomposition, and therefore every subsequent technique, was unavailable. The same shape recurs: unrestricted mutation is more powerful than immutability, and it is exactly what makes local reasoning, caching and safe concurrency impossible. Progress in programming has mostly consisted of giving up freedoms in return for the ability to understand what we have written, which is why a language that lets you do anything is not obviously better than one that does not.

A colleague says "we're a functional codebase, so we don't use classes". What is worth pushing back on?

Two things. First, the paradigms restrict different freedoms, so refusing one on the grounds of preferring another gives up a benefit without gaining anything — the discipline on mutation says nothing about whether you should invert a dependency. Second, and more concretely: what enforces invariants? Functional style excels at transformations, but "an account balance may never go negative" needs a gatekeeper, and a bag of exported functions over a plain record cannot be one because anything can construct the record directly. Languages with opaque types and smart constructors can achieve this without classes, which is a fine answer — but if the answer is "we just remember", the invariant is not enforced. The productive question is not which paradigm the codebase is, but where the boundaries and invariants live and what protects them.

Why is exception handling sometimes described as a controlled goto?

Because it transfers control to a location the throwing code does not name, across an arbitrary number of stack frames, skipping everything in between. That reintroduces Dijkstra's problem at a larger granularity: at the top of a catch block you cannot say what state the program is in, because you do not know which of the fifty statements in the try threw, so you do not know which side effects completed. It is controlled in that the destination is determined by the call stack rather than by an arbitrary label, and in that stack unwinding runs cleanup — which is a genuine improvement. But the design implication stands: keep try blocks small so the set of possible states at the catch is small, and prefer returning errors as values for expected failures, so the control flow stays visible in the code. That is the argument in Chapter 6.

Recap

  1. Each paradigm removes a capability and gives back the ability to reason. None of them adds power.
  2. Structured programming removes goto and makes functional decomposition possible — the foundation of everything else.
  3. Object orientation makes indirect transfer of control safe, which is what lets source dependencies point against the direction of calls. Dependency inversion is the real payoff, not encapsulation.
  4. Functional programming restricts assignment, buying referential transparency — and eliminating aliasing, action at a distance and most concurrency hazards.
  5. They compose. Pure functions for rules, objects for invariants and boundaries, plain procedure for orchestration.
  6. Paradigm purity is an antipattern: it pays a discipline's price where the freedom was causing no trouble.
  7. Declarative is the highest-leverage style when an engine exists; data-oriented is the correction when memory layout dominates.
  8. Choose per piece of code, by asking what kind of thing it is — transformation, invariant, boundary, or sequence.
