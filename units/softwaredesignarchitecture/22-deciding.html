Deciding, and recording the decision

Most of the cost of a design decision is paid by people who were not in the room when it was made. This chapter is about making those decisions well and leaving enough behind that they can be understood, challenged and reversed — and it closes the unit with three arguments worked end to end and everything on one page.

~30 min read ADRs · trade-offs · fitness functions 2 interactive panels The last chapter

22.1Why decisions get lost

Someone opens a file, finds an interface with one implementation, an odd module boundary, a service that seems unnecessary. They ask why and nobody knows. The people who decided have left or forgotten. So one of two things happens, and both are expensive.

  • It is preserved out of fear. Nobody can rule out that it matters, so it stays forever — and accumulates. Most of the inexplicable structure in an old codebase is this.
  • It is removed in ignorance. Someone tidies it away, and six weeks later the reason reappears as an incident.

What was lost is not the decision — that is visible in the code. What was lost is the context and the alternatives: what was true at the time, what else was considered, and what would have to change for the answer to be different. That is the only part worth writing down, and it is the part that never survives in a wiki page describing the current architecture.

22.2Architecture decision records

An ADR is a short document — one page, never more — capturing one decision, stored in the repository next to the code it governs, numbered and immutable once accepted.

The five sections, and what each is for
SectionContainsThe failure to avoid
ContextWhat was true when this was decided: constraints, scale, team, deadlines, what the system didWriting timeless justification. It is a snapshot, and its value is that it can become outdated visibly
DecisionOne sentence, active voice: "We will…"Hedging. If it is not a commitment it is not a decision
AlternativesWhat else was considered and why each was rejectedOmitting them. This is the most valuable section, because it stops the same option being re-proposed every year
ConsequencesWhat becomes easier, what becomes harder, what you now have to live withListing only benefits. An ADR with no downsides was not an analysis
StatusProposed / Accepted / Deprecated / Superseded by ADR-0031Editing an accepted ADR. Write a new one that supersedes it — the history is the point
Which decisions get one

The ones that are expensive to reverse and non-obvious. Not the library choice, not the naming convention. Yes to: anything that determines a boundary; anything where a reasonable person would choose differently; anything you had to argue about; anything where the reason will be invisible in the code. The practical trigger: if someone asks "why is it like this?" and the answer takes more than a sentence, write it down. A team producing more than about one a fortnight is recording too much and nobody will read them.

22.3Comparing options honestly

The usual failure in a design discussion is that options are compared on whichever criterion the loudest advocate cares about. A weighted matrix fixes that, and adds something more important than the score.

The procedure 
1  List the options, including "do nothing" and "the boring one".
2  List the criteria that actually matter for THIS decision, and
   nothing else. Five or six at most.
3  Weight the criteria BEFORE scoring the options. Doing it after
   is how the preferred answer gets reverse-engineered.
4  Score each option per criterion.
5  Compute — and then do the step everyone skips:
6  SENSITIVITY. Change the weights. Does the winner change?
   · Stable under most weightings → decide, and move on.
   · Flips easily → the options are close, so pick the
     REVERSIBLE one and write down what you were unsure about.

The sensitivity step is the part that turns the exercise from theatre into analysis. A matrix producing a clear winner across a wide range of weightings tells you the decision is robust to disagreement about priorities — which means you can stop arguing. A matrix whose winner flips when one weight moves by a point is telling you the options are equivalent and the real question is which mistake is cheaper to undo.

A real question: how to handle a growing reporting workload. Adjust the weights and watch whether the winner holds.

22.4Fitness functions

A decision that is not enforced degrades. An ADR saying the domain must not import the framework is a sentence in a file; an import-linter rule failing the build is a fact. A fitness function is an automated test of an architectural characteristic — the mechanism that keeps design decisions true.

What can actually be tested automatically
CharacteristicFitness functionWhere it runs
The dependency ruleAn import linter with layer contracts — ArchUnit, import-linter, dependency-cruiser, eslint boundariesCI, on every commit
No component cyclesThe same tools; a cycle contractCI
Domain is framework-freeForbidden-import contract on the domain packageCI
Test suite stays fastFail the build if unit tests exceed a wall-clock budgetCI
No N+1 queriesCount queries per request in integration tests; fail above a thresholdCI. See Chapter 16
Latency budgetAssert p99 in a load test; alert on the SLO in productionCI and production
Public API compatibilityContract tests or a schema-diff check against the previous versionCI
Bundle or binary sizeFail on a size regression beyond a budgetCI
No new usage of a deprecated pathRatchet: record the current count, fail if it increasesCI

The ratchet in the last row is worth adopting widely: rather than trying to reach zero violations before enforcing a rule, record today's count as the ceiling and fail the build if it rises. That lets you enforce a rule on a codebase that violates it in two hundred places, stops the problem growing immediately, and turns the cleanup into opportunistic work rather than a project.

22.5Reviewing a design

Reviews improve when the questions are known in advance, because then people prepare answers rather than defending.

The questions worth asking of any design 
CHANGE     What change is this making cheap, and which is it
           making expensive? Is the cheap one the one we expect?
           What would the next three features require?

BOUNDARY   What is inside this boundary and what is outside?
           Who owns each side? What crosses it, and in which
           direction do the dependencies point?

FAILURE    What happens when each dependency is slow, then down?
           What is the blast radius? How do we find out?

DATA       Who owns each piece of data? What must be consistent
           immediately, and what can be eventual?

REVERSAL   If this is wrong, what does it cost to undo? Can we
           make it cheaper to undo instead of trying harder to
           be right?

EVIDENCE   What are we assuming? Which assumption, if wrong,
           breaks this? Can we test that assumption cheaply now?

SIMPLER    What is the simplest thing that could work, and what
           specifically does this buy over it?

The last one deserves to be asked every time, because it is the question a design proposal is least likely to have prepared for — and because "nothing much" is a surprisingly common honest answer.

22.6Three arguments, worked

Should this new feature be its own service?

Situation: a notification system — email, SMS, push. Product wants it built. An engineer proposes a service.

The argument. Start with the question from Chapter 17: which independence is wanted? If the answer is "it feels separate", that is developability and a module gets it. Then look for a forcing reason. Notifications do have one candidate — they call slow, unreliable third parties, and a provider timing out should not consume request threads. But that argues for asynchrony, not for a separate deployable: a queue and a worker inside the same application achieve the isolation, and the worker can be extracted later if it needs to scale separately. The second candidate is scaling: notification volume can spike independently of web traffic. Real, but the worker process already separates that, and until measured it is speculation.

Decision: a notifications module with an enforced boundary, its work queued and processed by a worker in the same deployable, with providers behind an adapter per channel. What would change it: notification volume requiring different scaling from web traffic; a separate team owning it; or a compliance requirement to isolate message content. All three are observable, and the module boundary is where the service boundary would go.

Should we introduce a domain model here?

Situation: a pricing area, currently four transaction scripts of about 400 lines each, with the same discount rules appearing in three of them and diverging.

The argument. From Chapter 16, the trigger for a domain model is not size but rule duplication and complexity, and this has both — a rule existing in three places that have already drifted is one piece of knowledge with three representations, which is the DRY test from Chapter 9 answered clearly. It is also the core subdomain: pricing is what the company competes on. Against: a full model with aggregates and repositories is a large change to make while the scripts are being modified weekly.

Decision: extract the recurring rules into value objects and pure functions first — Money, DiscountPolicy, priceOrder — leaving the scripts as orchestration. That removes the duplication, makes the rules testable with plain values, and requires no new structure. Revisit aggregates when invariants that span entities appear. What would change it: a rule that must hold across several entities at commit time, which is the actual signal for an aggregate.

Should the ledger be event-sourced?

Situation: a payments ledger. Auditors ask why balances are what they are, sometimes years later.

The argument. From Chapter 20, the question is whether history is the source of truth. For a ledger it genuinely is — a balance is the sum of entries, and double-entry bookkeeping is event sourcing invented five hundred years early. So the pattern fits the domain rather than being imposed on it. The costs are real: schema versioning forever, snapshots, projections for every read, and erasure requests requiring crypto-shredding. But note that a conventional design here would need an append-only entries table, a balance derived or reconciled from it, and an audit trail — which is most of the same machinery, built ad hoc.

Decision: event-source the ledger aggregate only. Everything else — customers, products, preferences — stays conventional. What would change it: nothing likely; this is a rare case where the pattern matches the domain. The risk to manage is scope creep into aggregates that do not need it, which is why the ADR names the boundary explicitly.

Notice what the three have in common. Each identifies the forcing reason and tests whether it is real. Each takes the cheapest option that addresses it. Each names what would change the answer, so the decision can be revisited on evidence rather than re-argued from scratch.

And the one question underneath all of it

Every principle, pattern and architecture in this unit is an answer to the same question, asked at a different scale: what change is this making cheap, and what is it making expensive? Nothing here improves everything. Every abstraction favours one axis of change and taxes every other, because it adds a thing to understand. Design is choosing which axes to favour — and choosing them from the change history in front of you rather than from a prediction, a preference or a diagram.

Your team writes ADRs but nobody reads them. What is likely wrong?

Usually one of four things, and they are all fixable. They are in the wrong place — a wiki nobody opens rather than docs/adr/ in the repository, where they appear in searches and in diffs next to the code they govern. There are too many: a record for every library choice trains people to skip the directory, and the filter is whether the decision is expensive to reverse and non-obvious. They are written as justification rather than as analysis — an ADR listing only benefits reads as advocacy, and the consequences and alternatives sections are the parts that make them worth reading later. Or nothing points at them: the highest-value habit is linking the ADR from the code it explains, so a comment above the odd-looking interface says "see ADR-0014" and the question gets answered at the moment it is asked. It is also worth checking the actual usage pattern, which is not "read at leisure" — ADRs are read when someone is about to change something and wants to know why it is that way. If they cannot be found from the code, they will not be found at all.

Why is the sensitivity step of a decision matrix more useful than the score?

Because the score is only as good as the weights, and the weights are the part people disagree about and assign carelessly. Running the matrix once produces a number that looks objective and is not — it encodes one person's priorities with a veneer of arithmetic. Varying the weights tells you something the single score cannot: whether the answer is robust. If one option wins across most plausible weightings, the disagreement about priorities does not matter and you can stop having it, which is a real saving. If the winner flips when one weight moves a point, the matrix has told you the options are approximately equivalent — and that changes the question entirely, from "which is better?" to "which mistake is cheaper to undo?" That is the reversibility criterion from Chapter 1, and it usually has a clear answer where the original question did not. The other benefit is honesty: sensitivity makes it visible when someone has reverse-engineered the weights to produce a preferred conclusion, because such a matrix is always fragile.

You want to enforce the dependency rule but the codebase already violates it in 200 places. What do you do?

Ratchet. Record the current violation count as the accepted ceiling and fail the build only if it increases. That gets you the most important property immediately — the problem stops growing — without requiring a two-hundred-file cleanup before anything can be enforced, which is the requirement that stops teams enforcing anything at all. Then reduce the ceiling opportunistically: when someone touches a file with a violation, they fix it and lower the number, which is the same opportunistic principle as Chapter 21 and concentrates effort on the code that actually changes. Two refinements worth adding. Keep the violations in a checked-in baseline file rather than as a bare count, so the diff shows which ones changed and someone cannot fix one violation while adding another. And separate the rules by severity — "domain imports a framework" might be zero-tolerance from day one even while the general layer contract runs on a ratchet, because that specific violation is the one that does lasting damage.

Recap

  1. What gets lost is the context and the alternatives, not the decision — the code shows the decision.
  2. An ADR is one page: context, decision, alternatives, consequences, status. Immutable once accepted; supersede rather than edit.
  3. Record what is expensive to reverse and non-obvious. More than one a fortnight and nobody reads them.
  4. Weight the criteria before scoring the options, or the preferred answer gets reverse-engineered.
  5. Sensitivity matters more than the score. A winner that flips easily means the options are equivalent — take the reversible one.
  6. Unenforced decisions decay. Fitness functions in CI are what keep them true.
  7. Ratchet rather than waiting for zero, so a rule can be enforced on a codebase that already violates it.
  8. Name what would change the decision, so it can be revisited on evidence rather than re-argued.
  9. The question underneath everything: what change is this making cheap, and what is it making expensive?
