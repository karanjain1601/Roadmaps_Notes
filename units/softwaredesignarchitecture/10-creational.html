Creational patterns

Five patterns about the moment an object comes into existence. That moment matters more than it looks: it is where a caller becomes coupled to a concrete type, where an object's invariants are either established or missed, and where "just call the constructor" stops being adequate. This chapter is each pattern with its cost, and the modern default that has replaced two of them.

~28 min read Factory · builder · prototype · singleton 2 interactive panels Prerequisite: chapters 5, 7

10.1Why construction is a design problem

new Thing() is the tightest possible coupling: the caller names a concrete class, so it cannot be given a different one, cannot be tested without the real one, and must be edited whenever the choice changes. Most of the time that is fine — a Money, a DateRange, a local array. It stops being fine in four situations, and each creational pattern is an answer to one of them.

Four problems, four answers
ProblemPattern
The caller should not know which concrete class it getsFactory method, or dependency injection
Several related objects must come from the same familyAbstract factory
Construction takes many parameters, or happens in stepsBuilder
Creating a fresh object is expensive, and a copy would doPrototype
There must be exactly one of somethingSingleton — and usually you should not
The pattern that replaced two of these

Dependency injection — passing collaborators in through the constructor and assembling them in one place near the entry point — solves the "caller should not know the concrete class" problem more simply than a factory method does, because the caller does not create anything at all. Where the Gang of Four wrote a factory method so a subclass could decide, you now usually pass the instance in. Factories survive for the cases injection cannot cover: creating objects per call with runtime-dependent types, and creating objects whose type depends on data.

10.2Factory method

Creational

Factory method

Defer the choice of concrete class to a method, so callers depend on the interface and the decision lives in one place.

Mechanism
Classically: a base class declares createProduct() and subclasses override it. In practice more often a plain function or static method that inspects an input and returns the right implementation.
Also worth having for a much smaller reason
Named constructors. Money.fromCents(499) and Money.fromPounds(4.99) both take a number and mean different things — something a constructor overload cannot express. The name is the value.
Cost
Indirection, and one place that knows every concrete type. That place must be edited when a type is added, so the openness is partial — the factory itself is not closed to modification.
When it is wrong
When there is one implementation and no runtime choice. Then it is a function that calls a constructor.
TypeScript 
// Runtime data decides the type — injection cannot do this.
export function parserFor(contentType: string): Parser {
  switch (contentType) {
    case "application/json": return new JsonParser();
    case "text/csv":         return new CsvParser();
    case "application/xml":  return new XmlParser();
    default: throw new UnsupportedMediaType(contentType);
  }
}

// Registry variant: now adding a type is registration, not an edit.
const parsers = new Map<string, () => Parser>();
export const register = (t: string, f: () => Parser) => parsers.set(t, f);
export const parserFor2 = (t: string) =>
  (parsers.get(t) ?? fail(t))();

10.3Abstract factory

Creational

Abstract factory

One object that creates a whole family of related products, guaranteeing they are compatible with each other.

The problem it solves
Not "I need an object" but "I need three objects that must come from the same set". A Postgres Connection, Transaction and QueryBuilder must all be Postgres ones; mixing a Postgres connection with a MySQL query builder is a bug the type system would not otherwise catch.
Mechanism
An interface with several creation methods; each concrete factory returns one consistent family.
Cost
Substantial. Adding a new product type to the family means changing the factory interface and every implementation — the expression problem again, and here it bites hard because the interface is wide.
When it is wrong
Almost always, unless the family constraint is real. If the products do not actually have to match, you want several independent factories or just injection. This is the most over-applied pattern in the catalogue.

10.4Builder

Creational

Builder

Construct an object step by step, so the call site names what it is setting and the result is validated once at the end.

The problem
The telescoping constructor. With eight parameters, five of them optional, you either write dozens of overloads or you call new Report(a, null, null, true, null, 30, false, null) — unreadable, and two adjacent parameters of the same type can be swapped silently.
Mechanism
A mutable builder accumulates settings; build() validates the whole combination and returns an immutable object. The validation point matters: it can enforce rules that span fields, which a constructor with defaults cannot.
Cost
A second class to maintain in step with the first, and the object can be half-built while the builder exists. Some languages remove the need entirely — named and default parameters do most of the job.
When it is wrong
Three or four parameters that are all required. Also worth distinguishing from a fluent interface, which is a readability style and not this pattern.

Telescoping constructors versus a builder

What optional parameters do to the number of legal call shapes — and to the chance of a silent mistake.

10.5Prototype

Creational

Prototype

Create a new object by copying an existing one rather than constructing from scratch.

When it earns its place
When construction is genuinely expensive — a parsed template, a compiled regular expression set, a configured client, an object graph loaded from disk — and most instances differ from a baseline in only a few fields. Also when the concrete class is not known: you can clone something you were handed without knowing what it is.
Mechanism
A clone() method, or in immutable style a with-family: config.withTimeout(5000) returns a copy with one field changed and everything else shared.
Cost, and it is the usual bug
Shallow versus deep copy. A clone that shares a mutable child means changing the copy changes the original — the aliasing hazard from Chapter 6. Immutable objects make this free, because sharing is always safe; mutable ones require deciding, per field, and documenting it.
Modern form
In functional style this is not a pattern at all — it is how you update anything. { ...config, timeout: 5000 } is prototype, and structural sharing makes it cheap.

10.6Singleton

Creational · use with care

Singleton

Guarantee one instance and provide a global point of access — and note that those are two separate promises, only one of which is usually wanted.

What goes wrong
The global access is the problem, not the single instance. It creates connascence of identity at maximum distance (Chapter 8): any code anywhere can reach it, so the dependency does not appear in any signature, tests share state across cases, parallel test execution breaks, and initialisation order becomes a hidden constraint.
The specific symptoms
Tests that pass alone and fail together. A test that must run first. reset() methods that exist only for tests. Code you cannot reuse because it silently assumes a configured global. Two "singletons" in one process after a module bundler duplicates a file.
What to do instead
Create one instance at the composition root and inject it. You still have exactly one, and now the dependency is visible in the constructor, replaceable in a test, and impossible to reach by accident.
When it is genuinely fine
Stateless things where identity does not matter — a pure logger, a constant lookup table, a formatter. Also process-level resources where the runtime enforces it anyway. The test: does it hold mutable state? If yes, injecting it is worth the wiring.
Singleton — a hidden dependency
class Config {
  private static instance: Config;
  static get() {
    return Config.instance ??= new Config();
  }
  private values = new Map<string, string>();
  set(k: string, v: string) { this.values.set(k, v); }
  get(k: string) { return this.values.get(k); }
}

class Pricer {
  price(o: Order) {
    const rate = Config.get().get("taxRate");  // ← invisible
    …
  }
}

// The test must remember to configure a global,
// and must remember to undo it afterwards.
One instance, injected
class Pricer {
  constructor(private readonly rates: TaxRates) {}
  price(o: Order) {
    const rate = this.rates.for(o.region);      // ← declared
    …

// main.ts — the composition root, the only place
// that knows there is exactly one of anything
const rates  = new TaxRates(loadConfig());

// test — no globals, no reset, safe in parallel
new Pricer(new TaxRates({ UK: 0.20 }))

10.7Object pool, and dependency injection

Two more worth naming, neither in the original catalogue.

Object pool
Reuse expensive objects instead of creating and destroying them: database connections, threads, large buffers. Justified only when creation cost is measured and significant, because pools bring their own problems — leaked objects that are never returned, state left over from the previous user, and a sizing parameter that is wrong in both directions (see connection pool arithmetic in the System Design unit). Almost never worth hand-rolling; use the one your driver provides.
Dependency injection and the composition root
The dominant modern approach to construction: objects declare what they need in their constructors and never create their own collaborators. One place — the composition root, at the entry point — builds the object graph. The value is that every dependency is visible in a signature, every object is testable by passing doubles, and the wiring is a single readable file. Containers automate the wiring; they are optional, and a hand-written composition root of eighty lines is often clearer than a container's conventions.
Service locator is not dependency injection

A service locator — Locator.get(PaymentGateway) called from inside a class — looks like injection and behaves like a singleton. The dependency is still invisible in the signature, the class still cannot be constructed in a test without configuring a global registry, and you find out about a missing registration at runtime rather than at the composition root. It is a singleton with an extra layer, and it is worth recognising because it is frequently introduced as the fix for singletons.

10.8Choosing

Which creational approach?

Your logger is a singleton and nobody has complained. Should you change it?

Probably not, and the reason is the state test. A logger that writes to a sink configured once at startup and holds no per-caller mutable state is the case where singleton is genuinely fine: nothing can be corrupted by shared access, tests do not interfere with each other in ways that matter, and injecting it into every class in the codebase is real ceremony for no benefit. Two things would change the answer. If it accumulates state that tests assert on — captured messages, counters — then tests now share mutable state and will fail in combination or in parallel, and that is the classic symptom. And if you ever need per-request context in the log lines (a correlation id, a tenant), the global stops working, because there is no request scope in a global; at that point you need it injected or bound to a context object. The general rule: leave stateless singletons alone, and treat any singleton that grows mutable state as a bug to be fixed then rather than now.

When is a builder unnecessary?

Whenever the language gives you the same benefits for free. Builders exist to solve two problems — unreadable positional call sites and validation that spans fields — and named parameters with defaults solve the first entirely. In Python, Kotlin, C#, Swift or with a TypeScript options object, new Report({ title, from, to, includeCharts: true }) is as readable as a builder and needs no second class. What survives is the second problem: if build() must check that from < to, that a currency was set when an amount was, or that at least one of three fields is present, the builder gives you one place to do it. So the honest rule is that in Java and Go a builder is often warranted past four or five parameters, and in languages with named arguments it is warranted only when construction has cross-field rules or genuinely happens in stages across different parts of the code.

Your factory is a 300-line switch that every new type must be added to. Is that a failure of the pattern?

It is a failure of that implementation, and the fix is a registry. A switch means the factory is not closed to modification — adding a type edits a file that already works, which is what open–closed was meant to prevent. Replace it with a map from key to constructor, and let each implementation register itself at load time or be registered in the composition root. Adding a type then becomes adding a file plus one line of registration, and the registration line can live next to the new class rather than in a shared file that everyone edits and conflicts over. Two caveats: registration at import time is order-dependent and can be surprising, so prefer explicit registration in the composition root where you can see it; and a registry moves the failure from compile time to run time, so add a test that asserts every expected key resolves. The 300 lines are also worth a second look — a factory that large often means the family is too broad and should be several factories.

Recap

  1. new couples the caller to a concrete type. That is fine most of the time; the patterns are for when it is not.
  2. Dependency injection has replaced most factory use. Factories survive for per-call, data-dependent construction and for named constructors.
  3. Abstract factory is for families that must match, and is over-applied everywhere else.
  4. Builder solves telescoping constructors and cross-field validation. Named arguments remove the first reason.
  5. Prototype is ubiquitous in immutable code under the name "spread"; its bug is always shallow versus deep.
  6. Singleton's problem is the global access, not the single instance. Create one at the composition root and inject it.
  7. Service locator is a singleton wearing a disguise — the dependency is still invisible.
  8. A factory with a growing switch should be a registry, so adding a type stops editing existing code.
