Tests as design pressure

This chapter is in a design unit rather than a testing unit for a reason: the difficulty of testing a piece of code is the most reliable early signal of a design problem, and it is available before the code has caused any trouble. Tests are also the thing that makes refactoring possible at all — without them, "behaviour-preserving change" is an unverifiable claim.

3.1Testability is a design property

When a test is hard to write, the instinct is to blame the test — to reach for a heavier framework, a bigger mock, a running database. Almost always the difficulty is telling you something specific about the code, and the difficulty is the message.

What a testing difficulty actually means
Symptom in the testDesign problem it reveals
Needs a database, network or clock to test a calculationBusiness logic is tangled with I/O. The decision and the action are not separated
Needs ten lines of setup to construct the objectToo many collaborators, or the constructor is doing work. High coupling, made visible
You must reach into internals to assertThe public interface does not expose the outcome that matters — so neither does it for real callers
The test needs five mocksFive dependencies. The class is a coordinator of coordinators
You cannot test one branch without triggering othersThe branches are entangled; they should be separate functions or polymorphic cases
Test order matters, or tests interfereShared mutable state, usually a global or a singleton
The test is slowThe unit under test reaches something real. Widen your definition of "the unit" or narrow the code's reach
The reframing that makes this useful

"This is hard to test" is not a complaint about testing. It is a report that the code has too many dependencies, or the wrong ones, in the wrong place — the exact problem from Chapter 1, detected early and for free. Treat the difficulty as a design finding and the fix is usually obvious: pull the decision away from the action, inject the dependency, or narrow the interface.

3.2The shape that is easy to test

Nearly all testability comes from one structural idea, which appears under several names — functional core and imperative shell, humble object, ports and adapters. Decisions are pure; actions are trivial. Put everything interesting in code that takes values and returns values, and make the code that touches the world so simple it barely needs testing.

Decision welded to action
class SubscriptionService {
  async renew(userId: string) {
    const user = await this.db.findUser(userId);
    const sub  = await this.db.findSub(userId);

    if (sub.expiresAt < new Date()) {
      if (user.balance >= sub.price) {
        await this.db.debit(userId, sub.price);
        await this.db.extend(sub.id, 30);
        await this.mailer.send(user.email, "Renewed");
      } else {
        await this.db.cancel(sub.id);
        await this.mailer.send(user.email, "Cancelled");
      }
    }
  }
}

To test "cancels when the balance is short" you need a database, a mail server and control of the clock. Every rule change touches the same method that touches I/O.

Decision, then action
type Outcome =
  | { kind: "renew";  charge: Money; days: number }
  | { kind: "cancel" }
  | { kind: "noop" };

// pure: no db, no clock, no mailer
export function decideRenewal(
  sub: Subscription, balance: Money, now: Date
): Outcome {
  if (sub.expiresAt >= now)        return { kind: "noop" };
  if (balance < sub.price)         return { kind: "cancel" };
  return { kind: "renew", charge: sub.price, days: 30 };
}

// shell: no decisions, nothing to get wrong
async renew(userId: string) {
  const [user, sub] = await this.db.load(userId);
  const out = decideRenewal(sub, user.balance, this.clock.now());
  await this.apply(out, user, sub);
}

Every rule is testable with three plain values and no framework. The shell has no branches, so a single integration test covers it.

Notice what this buys beyond testing. The rules are now readable in one place without I/O noise; adding a rule cannot break persistence; and the outcome type is an explicit list of everything that can happen, which the compiler will make you handle. The test improvement is a side effect of a better separation, which is the point of the chapter.

3.3The pyramid is an argument about feedback loops

The test pyramid is usually presented as a rule about proportions. It is more useful as an economic argument: every test has a cost in runtime, flakiness and coupling, and a value in the bugs it can catch. The ratio differs by two orders of magnitude between levels.

The levels, honestly costed
LevelRuntimeCatchesMissesFlakiness
Unit — one function or class, no I/O< 1 msLogic errors, edge cases, branch behaviourEverything about how pieces connectEffectively zero
Integration — a component with a real dependency10–500 msWiring, SQL, serialisation, config, migrationsCross-service behaviourLow, if isolated per test
Contract — the agreement between two services10–100 msBreaking API changes, before deployWhether the behaviour is correctLow
End-to-end — the real system through the real UI5–60 s"Nobody can log in", integration of everythingEdge cases — too slow to enumerateHigh, and permanent

The pyramid's shape follows from that table rather than from tradition. You want the fast, reliable, precise tests to be numerous because they are nearly free and they point at the exact broken line. You want a small number of end-to-end tests because each one is slow, occasionally lies, and when it fails tells you only that something is wrong. Inverting the pyramid produces a suite that takes forty minutes, fails randomly twice a week, and is eventually ignored — which is the same as having no tests, at considerable cost.

The number that decides whether tests get used

Feedback latency. A suite that runs in under ten seconds gets run on every save and genuinely changes how you work — you make a small change, confirm it, continue. At a minute you run it before committing. At ten minutes you run it in CI and context-switch away, so a failure arrives after you have moved on and costs a re-entry. At forty minutes people merge and hope. The suite's runtime is not an operational detail; it determines whether the tests function as a design tool or as a compliance artefact.

3.4Test doubles, named precisely

"Mock" has become a word for any fake object, which loses a distinction that matters. Gerard Meszaros's vocabulary is worth keeping because the five kinds have different effects on coupling.

Five kinds of double
KindWhat it doesCoupling to implementation
DummyPassed to satisfy a signature, never usedNone
StubReturns canned answers to queriesLow — you specify inputs, not calls
FakeA working lightweight implementation — an in-memory repositoryLow, and it exercises real behaviour
SpyRecords what happened so you can assert afterwardsMedium
MockPre-programmed with expected calls; fails if they do not occur exactlyHigh — the test now encodes how, not what

The practical guidance follows from that last column. Prefer fakes and stubs; use mocks only at genuine boundaries where the interaction is the behaviour. Asserting that an email was sent is legitimate — sending it is the point. Asserting that a repository's findById was called exactly once is not: that is an implementation detail, and a perfectly good refactoring that adds a cache will now fail a test even though nothing observable changed.

Mock-heavy: tests the implementation
it("applies the discount", () => {
  const repo = mock<Repo>();
  const rules = mock<Rules>();
  when(repo.findCustomer("c1")).thenReturn(customer);
  when(rules.discountFor(customer)).thenReturn(0.1);

  new Pricer(repo, rules).price("c1", items);

  verify(repo.findCustomer("c1")).once();
  verify(rules.discountFor(customer)).once();
});

Asserts the sequence of internal calls. Caching the customer, or inlining the rules, breaks this test while the behaviour is unchanged — so the test punishes exactly the refactoring you want to do.

State-based: tests the outcome
it("applies the 10% loyalty discount", () => {
  const repo = new InMemoryRepo([
    aCustomer("c1", { loyaltyYears: 3 })
  ]);

  const total = new Pricer(repo, realRules).price("c1", [
    anItem({ price: 100 })
  ]);

  expect(total).toEqual(Money.of(90));
});

Asserts what a user would notice. Any internal restructuring that keeps the answer correct keeps the test green — which is what a test is for.

3.5Brittle tests, and how they get that way

A test suite that breaks constantly during honest refactoring is worse than useless: it converts every improvement into a chore, so people stop improving. Four causes, in rough order of frequency.

  1. Testing implementation instead of behaviour. The mock-heavy example above. The rule of thumb: a test should only fail if a user-visible or contract-visible behaviour changed.
  2. Reaching through the public interface. Tests that read private fields, call internal methods, or depend on the exact shape of an intermediate structure. If you must expose something for a test, that is a signal the interface is incomplete — but exposing it only for the test is a smell.
  3. Over-specified assertions. Asserting on an entire serialised object when the test is about one field. Adding an unrelated field to a response then breaks forty tests. Assert on what the test is named after.
  4. Shared fixtures that drift. A single testUser used by two hundred tests eventually has fields that seven tests depend on for contradictory reasons, and nobody can change it. Prefer builders that make each test state its own relevant facts: aUser({ verified: false }) says what this test is about and defaults everything else.
The builder pattern for test data 
// Each test declares only what it cares about. Everything else
// gets a valid default, so adding a required field to User
// changes one line in the builder rather than 200 tests.

const aUser = (overrides: Partial<User> = {}): User => ({
  id: "u1",
  email: "a@example.com",
  verified: true,
  createdAt: new Date("2026-01-01"),
  ...overrides,
});

it("rejects unverified users", () => {
  expect(canPost(aUser({ verified: false }))).toBe(false);
});
//                    ^^^^^^^^^^^^^^^^^^ the only fact that matters,
//                    and it is visible in the test that depends on it

3.6What to test, and what not to

Where test effort pays
Worth testing thoroughlyBarely worth testing
Business rules and calculations — the reason the software existsGetters, setters and pure data classes
Edge cases: empty, one, many, boundary, negative, overflowFramework behaviour — the framework has its own tests
Anything that has broken before — every bug gets a testGenerated code and simple mappings, unless the mapping is subtle
Error handling and the paths people never exercise manuallyThird-party libraries, beyond one integration test proving your usage works
Contracts between components you deploy separatelyTrivially obvious one-line delegations
Concurrency and ordering assumptionsLayout and styling, beyond a smoke check

On coverage as a target: it measures which lines were executed, not whether anything was verified. A suite can execute every line and assert nothing. It is a useful detector — a module at 5% coverage is genuinely untested, and that is worth knowing — and a bad goal, because mandating 90% produces tests written to touch lines rather than to check behaviour, and those tests are pure liability: they break during refactoring and catch nothing. Look at coverage on the modules that hold business rules; ignore the global number.

3.7Test-driven development, as a design claim

TDD is usually argued about as a testing practice. Its interesting claim is a design one: writing the test first forces you to use the interface before you build it, from the position of a caller who wants the simplest possible thing. That pressure produces smaller interfaces, fewer dependencies and fewer speculative options — because anything awkward to call is awkward to write a test for, and you feel it immediately rather than in six months.

The cycle is three steps and the third is the one people skip. Red: write a failing test for the next small behaviour. Green: the simplest change that passes, including something you know is too simple. Refactor: now that behaviour is locked down by a test, improve the structure. Skipping refactor gives you a suite of tests over code that was only ever written to pass them, which is how TDD gets a reputation for producing bad designs.

Where it works well: algorithmic code, business rules, bug fixes (write the failing test that reproduces it, then fix), and any API you will have to live with. Where it works badly: exploratory work where you do not yet know what you are building, UI layout, and integration against a system whose behaviour you are still discovering. Writing tests first for code you are about to throw away is a cost with no return — spike it, learn, delete it, then build it properly with tests.

A test needs six mocks. What is the code telling you?

That the class under test has six collaborators, which is the actual problem — the test is merely reporting it. A class with six dependencies is almost always a coordinator that has accumulated responsibilities, and it will be hard to change for the same reason it is hard to test: any of six things can force it to change. Two productive responses. First, check whether several of those dependencies are used together in one part of the class and not at all in another — that is a class trying to split into two, and the split usually falls out cleanly. Second, check whether the class is mixing decisions with actions; extracting the decision as a pure function typically removes most of the doubles at once, because pure functions need none. Adding a mocking framework that makes six mocks less tedious to write is the response that treats the symptom and preserves the disease.

Why can a test suite with 95% coverage still not support refactoring?

Because coverage measures execution, not verification, and it says nothing about coupling. A suite can execute 95% of lines while asserting on internal call sequences — in which case every refactoring breaks tests that nothing was actually wrong with, so the suite opposes restructuring rather than enabling it. It can also execute 95% of lines while asserting almost nothing, so it stays green through genuine breakage. What actually supports refactoring is a suite where tests are written against public behaviour, run fast enough to use continuously, and are reliable enough that a red result is believed. A 60% suite with those three properties is far more valuable than a 95% suite without them, and the way to tell which you have is to try a real refactoring and count how many tests broke for no behavioural reason.

Where would you draw the line between a unit test and an integration test, and why does the answer matter?

The useful line is not "one class" — that definition produces mock-heavy tests coupled to structure, because every collaborator must be doubled. Draw it at what the test touches outside the process: a unit test runs entirely in memory with no database, network, filesystem or real clock, and it may involve several collaborating classes if they form one behaviour. That definition tracks the properties you actually care about — speed and determinism — rather than an arbitrary structural boundary, and it lets you test a small cluster of classes through its natural entry point, which is precisely the level at which refactoring inside the cluster should not break tests. It matters because the "one class per test" definition is what drives teams towards strict mocks, and strict mocks are what make suites brittle.

Recap

  1. Difficulty writing a test is a design finding, available before the design has cost you anything.
  2. Pure decisions, trivial actions. A functional core with an imperative shell is where testability comes from, and it is a better separation regardless.
  3. The pyramid is an argument about cost per bug caught, not a tradition. Inverted, it produces a slow flaky suite that gets ignored.
  4. Suite runtime decides whether tests are a design tool. Under ten seconds changes behaviour; forty minutes means people merge and hope.
  5. Prefer fakes and stubs to mocks. Verify interactions only where the interaction is the behaviour.
  6. Brittleness comes from testing implementation, reaching into internals, over-specified assertions and shared fixtures.
  7. Use builders for test data so each test states only the fact it depends on.
  8. Coverage is a detector, not a target. A mandated percentage buys tests written to touch lines.
  9. TDD's real claim is about interface design — and the refactor step is the one that makes it work.
  10. Draw the unit boundary at process edges, not at class boundaries, or you will mock your way into a brittle suite.
