Patterns in perspective

Twenty-three patterns were catalogued in 1994 to describe recurring solutions in C++ and Smalltalk. Some have become language features, some were always workarounds for missing ones, and a few are as useful as they ever were. This chapter is the part usually left out of pattern teaching: which is which, what the other catalogues contain, and the specific ways enthusiasm for patterns damages code.

~24 min read PoSA · language features · over-abstraction 2 interactive panels Prerequisite: chapters 10–12

13.1What a pattern actually is

The idea came from architecture — Christopher Alexander's A Pattern Language — and the definition it brought is worth keeping: a pattern is a recurring problem in a context, a solution, and the consequences of applying it. Three parts, and the third is the one that gets dropped in retellings, which is exactly how patterns turn into templates.

So a pattern is not a piece of code and not a component. It is a named shape plus the trade-off it makes. The value of the name is coordination: "let's put a decorator around it" communicates a structure, an intent and a set of consequences in five words, to anyone who knows the vocabulary. That is a genuine benefit and it is most of what the catalogue is for.

Patterns are discovered, not invented

The Gang of Four did not design twenty-three solutions; they went looking at existing systems and wrote down what kept appearing. That origin matters, because it means the correct use is recognition — noticing that what you have arrived at is a known shape, and then benefiting from the name and the documented consequences. Starting from the catalogue and looking for somewhere to apply it inverts the method, and it is where nearly all pattern damage comes from.

13.2Patterns that became language features

A pattern is often a sign that a language is missing something. Several of the original twenty-three exist because C++ in 1994 lacked features that are now ordinary, and in a language that has them the pattern collapses to a line of code.

Where the pattern has been absorbed
PatternLanguage feature that replaces itWhat remains
StrategyFirst-class functionsThe class form, for stateful or named strategies
CommandClosures; serialisable job payloadsThe class form, where undo or introspection is needed
Iteratorfor…of, generators, yieldNothing — fully absorbed
VisitorPattern matching over sealed unions, with exhaustiveness checkingNothing, where the feature exists
SingletonModule-level values; a single instance in the composition rootNothing worth keeping
PrototypeSpread syntax, copy, with-methods, record typesNothing — it is just how you update immutables
Template methodHigher-order functions taking the varying stepsThe inheritance form, where the sequence must be locked
Abstract factoryModules as first-class values; dependency injectionWhere a family constraint is genuinely enforced
ObserverBuilt-in event emitters, signals, reactive streamsThe design questions — ordering, cascades, lifetimes — remain entirely
DecoratorMiddleware composition, function wrapping, annotationsThe pattern, but written as function composition

Peter Norvig's observation from 1996 still holds: sixteen of the twenty-three patterns are "invisible or simpler" in a sufficiently dynamic language. The useful conclusion is not that patterns are obsolete — it is that a pattern's weight should match what your language makes you write. If strategy is a parameter, use a parameter; writing an interface and two classes to achieve it is paying 1994's price with 2026's tools.

Do you need the pattern, or does your language have it?

The same intent, expressed at the weight the language requires.

13.3The other catalogues

The Gang of Four book is one of several, and it covers the smallest scale. Knowing what the others contain saves reinventing things at levels the 1994 catalogue never addressed.

Two of these deserve emphasis. PoSA's concurrency volume is the least-known and most valuable of the set — reactor and proactor describe the event loops underneath Node, nginx and every async runtime, and active object is the actor model's ancestor. And EIP is essentially the vocabulary of every message broker and integration platform built since; if you are wiring queues, its terms are the ones the tools already use.

13.4How patterns damage code

Five specific failures, in rough order of how much harm they do.

1 · Applying from the catalogue rather than recognising in the code
The inversion of the method. Starting from "where can I use a visitor?" produces abstractions serving no observed variation, and the cost — indirection, files, comprehension — is paid immediately and permanently. Every pattern should be introduced in response to a problem you can describe without naming a pattern.
2 · Pattern names as design arguments
"This should be a strategy" is a conclusion presented as a reason. The reason is the expected change: "pricing rules change per market and we have three markets coming". Without that, the discussion cannot be resolved on evidence, only on seniority.
3 · Naming classes after patterns
OrderStrategyFactoryImpl tells you the mechanism and nothing about the domain. The name should say what it does — MarketPricing, StripePayments — because a reader needs the concept far more often than the construction technique. A pattern suffix is occasionally useful at a boundary (StripeAdapter genuinely is an adapter and saying so helps); it is a smell when every class has one.
4 · Layering patterns on patterns
A factory producing a decorator wrapping a proxy over a strategy is four indirections between the call and the work. Each was locally reasonable; the aggregate is unreadable. The check is empirical: how many files must someone open to answer "what happens when I call this?" Past three, the design is costing more than it saves.
5 · Keeping a pattern after its reason expires
An abstract factory built for two database backends when the second was never delivered. A strategy interface with one implementation for six years. These are not neutral — they are ongoing comprehension cost with no remaining benefit, and they are easy to find: search for interfaces with exactly one implementor and ask why each exists.
The specific test for over-abstraction

Take any abstraction and ask: how many implementations does it have, and how many arrived after it was created? Two or more, some arriving later — it is earning its keep. Exactly one, created at the same time as the interface, with no second in prospect — it is a file with the same reasons to change as the thing it abstracts. The only good answers for keeping a one-implementation interface are the three from Chapter 7: the concrete thing is volatile, you need a test double, or it makes a dependency point the right way. "Flexibility" is not one of them.

Is this pattern earning its keep?

Score an abstraction that already exists — or one you are about to add.

13.5What patterns are still genuinely worth

The criticism above is aimed at misuse, not at the idea. Four benefits survive it, and they are the reasons to learn the catalogue.

  1. Vocabulary. Naming a structure in one word, with its consequences implied, is a real saving in design conversations and in code review. Most of the value of the GoF book is that everyone read the same one.
  2. Documented consequences. Each pattern comes with known costs — decorator ordering, visitor's difficulty adding types, singleton's test hostility. Recognising the pattern gives you the list without having to rediscover it.
  3. Recognition speed. Reading unfamiliar code is faster when the shapes are familiar. Seeing "this is a chain of responsibility" answers a dozen questions at once.
  4. They point at where variation lives. Almost every pattern is "encapsulate what varies" applied to a specific kind of variation. Knowing the catalogue is knowing the list of things that commonly vary, which is a useful prompt when you are trying to see the axis.
The workflow that avoids the failure modes

Write the simplest thing that solves the problem. When it needs to change, change it. When the second variant arrives, look at what actually differs — then check whether the shape you have arrived at has a name. If it does, adopt the name, read its consequences, and check you are not walking into a known trap. That sequence gets every benefit above and none of the costs, because the abstraction follows observed variation instead of predicting it.

Is it wrong to use a pattern name in a class name?

Not always, and the distinction is whether the pattern is the class's role in the architecture or merely its implementation technique. StripeAdapter is a good name: the class exists specifically to translate between your domain and a foreign one, "adapter" is exactly what a reader needs to know, and it signals that no Stripe concepts should escape past it. RetryingOrderRepository likewise tells you it is a decorator without saying so. The failure is when the suffix describes construction rather than purpose — PricingStrategyFactoryImpl tells you three mechanisms and no domain concept, and the reader still has to open it to learn what pricing rule it produces. A rough test: would a domain expert recognise the name? "Market pricing" yes, "pricing strategy factory" no. And if every class in a package carries a pattern suffix, the names have stopped distinguishing anything, which is the real signal.

Sixteen of the 23 GoF patterns are said to be "invisible" in dynamic languages. Does that make the book obsolete?

No, but it changes what you take from it. Norvig's point was that when a language has first-class functions, closures, dynamic dispatch and reflection, several patterns stop requiring any structure — strategy becomes a parameter, command becomes a closure, iterator becomes a generator, prototype becomes an object literal. In those cases writing the classical implementation is pure ceremony. What survives is the part the language cannot absorb: the problem statements and the consequences. A language can make observer a one-line subscription; it cannot tell you that ordering is undefined, that cascades happen, and that unsubscription is your responsibility. It can make decorator function composition; it cannot tell you that the order changes behaviour invisibly. So the book remains useful as a catalogue of recurring problems with documented trade-offs, and is much less useful as a catalogue of class diagrams — which is, unfortunately, how it is usually taught.

A codebase has interfaces with exactly one implementation everywhere. What is the argument for and against changing it?

Against changing it: consistency has value, the team may be mocking everything in tests and would need a different approach, and a mass refactoring touches a great deal of code to fix a problem that is annoying rather than dangerous. Some of those interfaces will also be legitimate under the three tests — volatile concrete thing, needed for a test double, or making a dependency point inwards — and a blanket removal would destroy those. For changing it: every one-implementation interface costs a reader a hop on every trace, and at scale the codebase becomes navigable only with an IDE's "go to implementation", which is a real accessibility cost for anyone reading it in a diff or on a web page. It also obscures the interfaces that do matter, because when everything is an interface, the boundary interfaces stop standing out. The practical middle: stop adding them by default, remove them opportunistically when touching a file for another reason, and be explicit about where the boundaries are so the remaining interfaces mean something.

Recap

  1. A pattern is problem, solution and consequences. Dropping the third turns it into a template.
  2. Patterns were discovered by observation, so the correct use is recognition rather than application.
  3. Many patterns are workarounds for missing language features. Match the weight of the implementation to what your language requires.
  4. Five catalogues cover five scales: GoF for objects, PoSA for system structure and concurrency, PoEAA for enterprise applications, DDD for modelling, EIP for messaging — plus the cloud patterns for distributed systems.
  5. The five damage modes: applying from the catalogue, using names as arguments, naming classes after mechanisms, layering patterns on patterns, and keeping a pattern after its reason expired.
  6. The over-abstraction test: how many implementations, and how many arrived after the interface.
  7. What survives the criticism: vocabulary, documented consequences, faster reading, and a list of the things that commonly vary.
  8. The workflow: simplest thing → change it when it changes → recognise the shape on the second variant → adopt the name and read the consequences.
