CHAPTER 08

File formats and columnar layout

Chapter 2 claimed columnar storage compresses about fourfold and lets a reader skip columns it does not need. Those were placeholders. This chapter runs a real encoder on real data in your browser and measures both, and the measurement turns up something the rule of thumb hides: sorting your data to improve compression can make it substantially worse.

    THE PHYSICAL ARGUMENT

    Why columns, and why only sometimes

    Row and column layouts are the same data in a different order. The order decides which queries are cheap.

    A table has to be laid out linearly on a device. Two choices:

    layout.txt
    # row-oriented: one record's fields are adjacent
1,GB,settled,1900 | 2,US,pending,450 | 3,GB,settled,7200 | ...

# column-oriented: one field's values across records are adjacent
1,2,3,...  |  GB,US,GB,...  |  settled,pending,settled,...  |  1900,450,7200,...

    Storage devices and networks are efficient at contiguous reads and terrible at scattered small ones — that was the central point of chapter 7. So the layout that puts the bytes a query needs next to each other wins, and which layout that is depends entirely on the query.

    Row layout wins when

    • You want whole records: SELECT * WHERE id = 42.
    • You write one record at a time, which is what a transactional application does.
    • You update in place — touching one row means touching one contiguous region.

    Column layout wins when

    • You want a few fields from many records: SELECT country, sum(amount) GROUP BY country.
    • You write in large batches.
    • You never update, only append and replace.

    That is the whole OLTP-versus-OLAP distinction expressed physically, and it is why chapter 10 can treat the two engine families as a consequence of layout rather than as a marketing category.

    The second, larger effect

    Skipping unwanted columns is the obvious benefit and it is not the biggest one. A column holds values of one type, from one domain, frequently with heavy repetition. That makes it enormously more compressible than a row, where an integer sits next to a country code sits next to a timestamp. Compression is where most of the win comes from, and the next section measures it.

    MEASURED, NOT ASSERTED

    The encodings, and what they actually save

    Four techniques do nearly all the work. The demo below implements them and runs them on forty thousand generated rows in the page.

    Dictionary encoding
    Replace each value with an index into a list of distinct values. A country code stored as two UTF-8 bytes plus a length prefix becomes a 4-bit index when there are only twelve countries. Effective exactly when cardinality is low relative to row count.
    Run-length encoding
    Store (value, repeat count) rather than the repeated value. Devastatingly effective on sorted low-cardinality data and useless on unsorted data, which is the whole subject of the sort-order control below.
    Delta encoding
    Store the difference from the previous value. A monotonic column — an id, an ingestion timestamp — has tiny deltas that pack into a handful of bits each instead of four or eight bytes. This is the encoding that produces the spectacular ratios, and also the one that sorting destroys.
    Bit packing
    If the values in a block need only 11 bits, use 11 bits, not 32. Applied underneath the other three rather than instead of them.

    A real Parquet writer chooses per column and per block, trying candidates and keeping the smallest. The demo does the same, and reports which one won.

    The measurement, and the correction to chapter 2

    In insertion order the encoder gets the whole table about 5.1 times smaller than CSV, not fourfold — so chapter 2's placeholder was conservative for this data. Per column the spread is enormous: a sequential id compresses about thirty-twofold under delta encoding, a four-value status column about forty-fourfold under a dictionary, and a random user id barely twofold because there is no structure to exploit.

    That spread is the real lesson. "Columnar is four times smaller" is not a property of the format, it is a property of your data's cardinality and ordering. A table of random values compresses barely at all in any format.

    Sorting to improve compression can make it worse

    Switch the sort order to country, status and watch the total grow by about a third. The mechanism is visible in the per-column table: run-length encoding on the two low-cardinality columns saves around 29 KB, and randomising the previously monotonic event_id and ts_ms columns costs around 146 KB, because their deltas stop being small. Net effect: 33% worse, on byte-for-byte identical data.

    Now switch the column selection to drop the monotonic columns and re-apply the same sort. It becomes 9% better. Whether sorting helps compression depends on which columns dominate your table, and the answer has to be measured rather than assumed.

    This matters because "sort your data for better compression" is common advice and it is only conditionally true. The good reason to choose a sort order is the next section — pruning — and its compression effect should be measured as a side effect rather than assumed as a benefit.

    SKIPPING WORK ENTIRELY

    Row groups and predicate pushdown

    The largest saving available is not reading data faster. It is proving you never needed to read it.

    A columnar file is not one long column. It is divided into row groups — horizontal slices of perhaps a hundred thousand rows — and within each row group, each column is stored as a chunk with its own footer statistics: minimum, maximum, null count, distinct count.

    Those statistics let a reader do something powerful. Given WHERE amount_cents > 400000, it inspects each row group's maximum for that column, and if the maximum is 380,000 the group cannot contain a matching row, so the reader skips it without transferring a byte. This is predicate pushdown, and combined with column projection it means a query can touch a tiny fraction of a file.

    Statistics can only ever prove absence

    A minimum and maximum can prove no row matches. They can never prove a row does match — a group whose range overlaps the predicate might contain zero matches and still has to be read. So pushdown is a filter on work, never a substitute for evaluating the predicate. This asymmetry is why pushdown effectiveness depends entirely on how well the data is physically clustered.

    Four results from the model that are worth stating explicitly.

    1. Unsorted data prunes almost nothing. With rows in insertion order, every group's amount_cents range spans nearly the whole domain, so all ten groups overlap the predicate and none can be skipped — despite only 7% of rows matching. The statistics are present and correct and completely useless.
    2. Clustering on the predicate column is what makes pushdown work. Sort by amount_cents and the same query reads one group of ten: a 90% reduction in rows touched, from physical layout alone.
    3. Clustering helps only the column you clustered on. Sort by country and the amount_cents predicate is back to reading all ten groups. You get one sort order per table, so it must be chosen for the queries that matter.
    4. Ingestion time is clustered for free. Notice that the timestamp predicate prunes to one group even in insertion order, because rows arrived in time order. This is the real reason partitioning by date is so effective and so ubiquitous — the clustering is a gift from how the data arrives, and costs nothing to maintain.

    Smaller row groups prune more precisely, and the model shows the benefit flattening: once a group is smaller than the matching region, further subdivision gains nothing while adding footer overhead and more requests. Real writers default to somewhere between 128 MB and 1 GB per row group for exactly this reason, and chapter 7's request-cost arithmetic is the other half of the argument.

    THE ACTUAL FORMATS

    Choosing between them

    Three columnar formats, one row-oriented binary format, and two text formats that will not go away.

    Formats by layout and by what they are genuinely good at

    ParquetColumnarYesEmbeddedThe default for analytical storage. Widest engine support of anything here.
    ORCColumnarYesEmbeddedTechnically comparable, with better built-in indexes. Strongest in the Hive lineage.
    AvroRowYesEmbeddedStreaming records and write-heavy landing zones, where whole records arrive one at a time.
    CSVRowYes, awkwardlyNoneInterchange with humans and spreadsheets. Never a storage layer.
    JSON linesRowYesNoneLanding semi-structured data before you know its shape.
    ArrowColumnar—EmbeddedIn-memory interchange between processes, not a storage format at all.

    Two distinctions in that table earn their place.

    Avro is row-oriented, and that is a feature. Parquet needs a whole row group in memory before it can write anything, so it is a poor fit for a stream of individual records. Avro appends one record at a time cheaply. The common pattern is therefore Avro on the way in, compacted into Parquet for the analytical layer — which is chapter 12's landing-zone design.

    Arrow is memory, not storage. Parquet is optimised for size on disk with heavy encoding; Arrow is optimised for direct CPU access with no decoding step. They are complementary, and the confusion is common enough to be worth naming: you store Parquet and process Arrow.

    Compression codec, separately from encoding

    Everything measured above was encoding — structural techniques exploiting what the data is. A general-purpose codec is then applied on top, and the choice is a straightforward speed-versus-size trade. Snappy is fast and modest, the safe default for data queried often. Zstd is now the better default in most engines: meaningfully smaller than Snappy at similar decompression speed, with a tunable level. Gzip is smaller still and slow enough to be a poor fit for interactive querying. Choose Zstd unless you have measured a reason not to.

    WHAT GOES WRONG

    Five layout mistakes

    All five are common, all five are cheap to avoid at write time and expensive to fix afterwards.

    Too many small files
    The dominant failure. Every file costs a request, a footer read and scheduler overhead, and pruning cannot help because a small file is one small row group. Chapter 7 priced this: identical bytes, tens of thousands of pounds apart. Target 128 MB to 1 GB per file and run a compaction job.
    Partitioning too finely
    Partitioning by day is usually right; by hour, or by day and country and device, produces thousands of directories holding a few kilobytes each — the small-files problem arriving through a different door. A partition should hold at least a few hundred megabytes.
    Sorting on the wrong column
    You get one physical order. Spending it on a column nothing filters by gives up all the pruning in the previous demo, as the model shows directly.
    Assuming pushdown happened
    It silently does not, for predicates the engine cannot translate: a function applied to the column, a cast, an unsupported type, statistics disabled at write time. Always check the query plan for the row-groups-scanned count rather than trusting that it worked.
    Wide tables read whole
    Columnar layout only pays if you project. SELECT * on a 300-column Parquet table forfeits the entire benefit and is slower than the row format would have been, because it pays decoding costs for columns it does not use.

    Recap

    What to take from this chapter

    1. Row and column layouts are the same data reordered. Rows win for whole-record access and in-place updates; columns win for a few fields across many records.
    2. Compression is the bigger half of the columnar benefit, because a column holds one type from one domain with heavy repetition.
    3. Measured on this data, encoded columnar is about 5.1× smaller than CSV — chapter 2's fourfold placeholder was conservative. Per column the range runs from about 1.6× to about 44×.
    4. Compression ratio is a property of your data, not of the format. Cardinality and ordering decide it; random values barely compress in anything.
    5. Sorting to improve compression can make it worse. Sorting by two low-cardinality columns saved 29 KB of run-length coding and cost 146 KB of delta coding — 33% worse overall. Drop the monotonic columns and the same sort is 9% better.
    6. Statistics can prove absence, never presence. Pushdown reduces work; it never replaces evaluating the predicate.
    7. Unsorted data prunes nothing. Every group's range spans the domain, so all groups are read even at 7% selectivity.
    8. Clustering on the predicate column cut rows touched by 90%, and clustering on a different column gave no benefit at all. One sort order per table, spent deliberately.
    9. Ingestion time is clustered for free, which is the real reason date partitioning works so well.
    10. Avro on the way in, Parquet for analytics. Row-oriented for record-at-a-time writes, columnar once compacted. Arrow is memory, not storage.
    11. Prefer Zstd over Snappy unless measurement says otherwise, and keep files between 128 MB and 1 GB.
