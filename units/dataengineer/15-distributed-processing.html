CHAPTER 15

Distributed processing

A distributed job has one interesting operation and everything else is bookkeeping. That operation is the shuffle — moving data between machines so that related rows meet — and it is where the time, the money and the failures are. Understanding it turns cluster tuning from folklore into arithmetic.

    FIRST, A CHECK

    When one machine stops being enough

    Later than almost everyone assumes, and the assumption is expensive.

    A cluster costs you more than money. It costs a scheduler, a shuffle, partial failure, serialisation, a web UI to interpret, and a class of bug that does not exist on one machine. So the first question is whether you need one, and the honest answer is frequently no.

    A single cloud instance today can have 128 cores and 2 TB of memory. Chapter 8 measured Parquet at roughly five times smaller than CSV, so a 2 TB machine comfortably holds tens of terabytes of raw-equivalent data. Single-node engines — DuckDB, Polars, a well-written pandas or Postgres query — routinely beat a small Spark cluster on datasets under a few hundred gigabytes, because they skip the coordination entirely.

    The test worth applying before reaching for a cluster

    Not "is the dataset big" but "does the working set of this particular query fit in one machine's memory?" A 40 TB table where every query touches one day and three columns has a working set of a few gigabytes, which chapter 8's pruning demo showed directly. Distributing that is paying coordination costs to process data you could have held in RAM.

    Reach for a cluster when the working set genuinely exceeds one machine, when you need more aggregate I/O bandwidth than one machine has, or when the job must finish faster than one machine's cores allow. Those are real reasons. "We have a lot of data" is not one.

    THE EXECUTION MODEL

    From MapReduce to what you use now

    One idea from 2004, and the two things later systems changed about it.

    MapReduce's contribution was not the two functions; it was noticing that if you constrain computation to a shape where every step is independent and deterministic, you get fault tolerance for free. A failed task is simply re-run, because its input still exists and its output depends on nothing else.

    model.txt
    map     each input split -> zero or more (key, value)   # independent, parallel
shuffle rows with the same key are moved to the same node   # the expensive bit
reduce  all values for one key -> output                 # independent, parallel

    Two changes since then account for most of the performance difference in modern engines.

    Stop writing to disk between every step
    MapReduce materialised to HDFS after every map and reduce, so a five-step pipeline paid five round trips to disk with triple replication. Spark keeps intermediate results in memory where it can, and chains narrow operations into one pass. This is where the often-quoted order-of-magnitude speedup came from, and it is a change in I/O rather than in algorithm.
    Plan the whole job before running it
    MapReduce ran what you wrote. A modern engine builds a logical plan, applies rules — push filters down to the scan, prune unused columns, reorder joins — and only then produces physical stages. The pruning of chapter 8 is the planner and the file format cooperating, and it is why a declarative query frequently beats hand-written code.

    The vocabulary you need to read an execution plan:

    Five words, and what each actually is
    TermWhat it isWhy it matters
    PartitionA slice of the data one task processesThe unit of parallelism, exactly as in chapter 13
    TaskOne partition being processed by one coreThe unit of scheduling and of retry
    StageA run of tasks with no shuffle between themStage boundaries are shuffle boundaries. Counting stages counts shuffles
    Narrow dependencyEach output partition reads one input partitionFree: map, filter, projection. Fused into one pass
    Wide dependencyEach output partition reads many input partitionsRequires a shuffle: groupBy, join, distinct, sort, repartition

    That last distinction is the one to internalise. Reading a plan is mostly counting wide dependencies, because each one is a full redistribution of the data across the network, and everything else is comparatively free.

    THE EXPENSIVE OPERATION

    What a shuffle costs

    Every mapper potentially writes a block for every reducer. The block count is the product, and the product gets large quickly.

    A shuffle does three things: each map task partitions its output by the shuffle key and writes those partitions to local disk; the data crosses the network; each reduce task fetches its partition from every map task. So the cost has three components — disk writes, network transfer, and a number of separate fetches equal to map tasks × shuffle partitions.

    That last number is the one people miss. The demo compares a shuffle join against the alternative that avoids it entirely.

    Shuffle join against broadcast join bytes across the network, shuffle blocks, and which constraint binds
    SHUFFLE JOIN0
    BROADCAST JOIN0
    SHUFFLE BLOCKS0
    BROADCAST CEILING0

    Two results.

    1. Shuffle blocks are the product, and the product explodes. A 500 GB fact table is 4,000 map tasks at the default block size; against 400 shuffle partitions that is 1.6 million separate fetches, and at 10,000 partitions it is 40 million. Each is a small network request with its own overhead, which is why raising the partition count past a point makes a job slower rather than faster — the same small-request penalty chapter 7 priced for object storage.
    2. Two different limits govern broadcasting, and the tighter one is memory. On network bytes alone, broadcasting beats shuffling right up to about 12.8 GB of dimension table. But every executor must hold the whole broadcast in memory, which caps it at about 6.4 GB — memory binds twice as early. That is why the automatic broadcast threshold in a real engine is set in megabytes and tied to executor memory rather than to bandwidth.
    The shuffle you can delete

    The cheapest shuffle is one that does not happen, and there are three reliable ways to remove one. Broadcast the small side of a join, as above. Filter and project before the shuffle, so you move less — a filter pushed below a join can remove most of the data. And reuse an existing partitioning: if a table is already bucketed or sorted on the join key, the engine can skip the exchange entirely, which is what bucketing is for.

    Pre-aggregation is the fourth. A groupBy that can combine on the map side sends one partial result per key per mapper rather than every row, which for a high-cardinality-reduction aggregate cuts shuffle volume by orders of magnitude.

    STRATEGIES

    How a join is actually executed

    Three physical strategies. The planner picks one, usually from statistics, and it is worth knowing when it will pick wrong.

    Broadcast hash join
    Send the small side to every executor, build a hash table, stream the large side past it. No shuffle of the big table at all. Fastest by a wide margin when the small side fits, and the memory ceiling above is the whole constraint.
    Shuffle hash join
    Shuffle both sides by the join key, then build a hash table on the smaller side of each partition pair. Needs one partition's worth of the smaller side to fit in memory, and fails or spills badly when a partition is skewed.
    Sort-merge join
    Shuffle both sides, sort each partition, then walk the two in step. No requirement that anything fits in memory, because sorting can spill to disk. The safe default for two large tables, and the reason most big joins are sort-merge.

    The planner chooses using table statistics, and the common failure is that the statistics are wrong or missing. A table written without statistics, or one whose size the planner cannot estimate through a chain of filters, gets treated as large and joined with a sort-merge when a broadcast would have been dramatically faster. This is the single most common cause of "the same query is fast on one table and slow on an identical one".

    Modern engines mitigate it with adaptive execution: run the first stage, look at the actual sizes produced, and re-plan. That converts a wrong estimate into a correct decision at the cost of one materialisation, and it is worth having enabled — it also handles the skew case in the next section.

    THE THING THAT WASTES CLUSTERS

    Skew and stragglers

    A job takes as long as its slowest task. If one partition holds a hundred times the rows of the others, you have bought a cluster and are using one core of it.

    This is the same phenomenon as the hot partition in chapter 13, appearing in a different system for the same reason: work is divided by a key, and keys are not evenly distributed. Here the consequence is measurable in money, because the idle cores are still billed.

    Skew, stragglers and cluster utilisation 2 billion rows over 200 slots, with tasks scheduled longest-first
    LONGEST TASK0
    STRAGGLER RATIO0longest over mean
    WALL CLOCK0
    CLUSTER UTILISATION0%

    The numbers are stark and they are all about the same total work.

    1. Skew converts utilisation directly into waste. With evenly distributed keys the job uses 100% of the cluster and finishes in 5 seconds. At high skew the longest task runs 608 seconds — 243 times the mean — the job takes 608 seconds, and utilisation is 1%. Identical work, two hundred times the wall clock, and you are billed for two hundred idle cores throughout.
    2. More partitions does nothing whatsoever. 400 partitions and 50,000 partitions both give a 608-second longest task, because the hottest key is one partition's worth of work by definition and cannot be divided. This is exactly the result from chapter 13, arriving through a different door.
    3. Salting is the fix that partition count is not. Splitting keys across 64 salts takes the longest task from 608 seconds to 10 and utilisation from 1% to 51%. The cost is a second aggregation pass to combine the salted groups, and — as in chapter 13 — the loss of any per-key ordering.
    Skew is invisible in the summary

    Total rows processed, total bytes shuffled and average task duration all look perfectly normal in a skewed job. The only place it shows is the distribution of task durations, which is why the first thing to open on a slow job is the task-duration histogram rather than the summary. A p50 of two seconds and a max of ten minutes is a diagnosis, not a mystery.

    The other tell is a job whose wall clock barely improves when you add executors. If utilisation is 1%, more cores are more idle cores.

    Two mitigations beyond salting. Adaptive skew join splitting detects an oversized partition at runtime and divides it across several tasks, replicating the matching side — this is automatic in current engines and handles the common case without code changes. And separating the hot key: filter it out, process it with a broadcast join or a dedicated path, and union the results. Uglier, and sometimes the only thing that works when one key is genuinely most of the data.

    DIAGNOSIS

    Four things that make a job slow

    In the order you should check them, because the order is roughly how often each is the answer.

    1. Skew
    Check the task-duration distribution first. A max far above the p95 is skew, and nothing else you do will matter until it is fixed.
    2. Small files
    One task per file means ten thousand tiny files becomes ten thousand tasks each doing almost nothing, dominated by scheduling overhead and object-store requests. Chapter 7 priced the request side; here it also costs a task launch each. The symptom is a huge task count with a tiny median duration. Compaction is the fix, and it is the same fix as chapter 7's.
    3. Spill
    A task whose partition does not fit in memory writes to disk and reads it back, which can be an order of magnitude slower. Shown explicitly as spilled bytes in the metrics. Caused by too few partitions, skew, or genuinely insufficient memory — and note the tension: too few partitions causes spill, too many causes the block explosion above.
    4. Unnecessary shuffles
    Count the stages. Each boundary is a redistribution. A repartition nobody needed, a sort before an operation that does not require order, an aggregation that could have been combined on the map side, or a broadcast the planner declined because statistics were missing.

    A useful ordering heuristic: skew and small files are data layout problems and are fixed upstream, in how the table was written. Spill and unnecessary shuffles are query problems and are fixed in the job. If several jobs over the same table are all slow, look at the table; if one job is slow over tables that serve others well, look at the job.

    Sizing, as a starting point rather than a rule

    Aim for partitions of roughly 128 MB to 1 GB after the shuffle, which usually means setting the shuffle partition count from the expected shuffle volume rather than leaving the default. Aim for files in the same range, per chapter 8. Give each executor a handful of cores rather than one or thirty — too few wastes the shared broadcast and JVM overhead, too many contend on memory. Then measure, because every one of these depends on the data.

    Recap

    What to take from this chapter

    1. Ask whether the working set fits in one machine, not whether the dataset is big. A 40 TB table queried one day at a time has a working set of gigabytes.
    2. MapReduce's real contribution was fault tolerance through determinism. Later engines changed two things: stop materialising between steps, and plan before running.
    3. Reading a plan is counting wide dependencies. Stage boundaries are shuffle boundaries; everything else is comparatively free.
    4. Shuffle blocks are map tasks times shuffle partitions, and the product explodes: 1.6 million at 400 partitions on a 500 GB table, 40 million at 10,000.
    5. Broadcasting is limited by memory long before bandwidth. Network bytes allow about 12.8 GB; executor memory allows about 6.4 GB — twice as tight, which is why thresholds are set in megabytes.
    6. The cheapest shuffle is one you delete: broadcast, filter before it, reuse an existing partitioning, or combine on the map side.
    7. Missing statistics cause the wrong join strategy, which is the usual explanation for two identical-looking tables performing differently. Adaptive execution re-plans from real sizes.
    8. Skew turns 100% cluster utilisation into 1% on identical total work — a 243× straggler, 608 seconds against 5, with two hundred cores billed and idle.
    9. More partitions does not help skew at all. 400 and 50,000 give the same 608-second task, exactly as partition count could not help a hot Kafka key.
    10. Salting is the fix: 64 salts took the longest task from 608 seconds to 10 and utilisation from 1% to 51%, at the cost of a second aggregation pass.
    11. Skew is invisible in summary metrics. Open the task-duration distribution first; a p50 of seconds with a max of minutes is a diagnosis.
    12. Check in order: skew, small files, spill, unnecessary shuffles. The first two are layout problems fixed upstream; the last two are query problems fixed in the job.

    Key skew capping throughput regardless of partition count appeared in chapter 13 for Kafka and again here for Spark. It is one property of hashing work by key, not two coincidences.

    ONE THING TO TRY

    Open the slowest stage of your slowest job and look at the task-duration histogram rather than the total. If the maximum is more than about five times the median, stop tuning anything else.
