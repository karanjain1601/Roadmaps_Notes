CHAPTER 11

Warehouses, lakes and lakehouses

Chapter 7 showed that object storage gives you cheap, durable, immutable blobs and no atomicity across them. That single missing primitive is what turned data lakes into swamps, and closing it is the entire technical content of the lakehouse. This chapter measures the gap and then measures the fix.

    THE ORIGINAL

    Warehouses, and the two schools

    A warehouse is a database tuned for analysis with the modelling discipline of chapter 9 applied to it. The long-running argument is about where that discipline is applied.

    Two architectures were proposed in the early 1990s and the disagreement has never quite ended, mostly because both are partly right.

    Inmon: normalised core first

    Integrate everything into a normalised, enterprise-wide model — the "corporate information factory" — then build dimensional marts from it. Top-down. The core is the single integrated truth; marts are derived views for particular audiences.

    Strength: genuinely consistent across the whole business. Weakness: nothing is delivered until the enterprise model exists, which historically took years and frequently never finished.

    Kimball: dimensional marts first

    Model one business process at a time as a star, and achieve consistency by sharing conformed dimensions across them. Bottom-up. The warehouse is the union of the marts, held together by shared dimensions rather than by a normalised core.

    Strength: value in weeks, and the increments are usable. Weakness: conformance requires ongoing discipline, and drifts without it.

    How this resolved in practice

    Kimball won the delivery argument and Inmon won the integration argument, and modern platforms do both in layers. The now-standard three-layer shape is recognisably a synthesis: a raw or bronze layer holding source data as it arrived, a staging or silver layer that is cleaned, conformed and lightly normalised, and a marts or gold layer of dimensional models per consumer.

    The important property is that each layer is derivable from the one before it. That is what makes a modelling mistake a rebuild rather than a data-loss event, and it is the same reasoning as the replayability requirement in chapter 12.

    What a warehouse gives you beyond a database is not one feature but a bundle: columnar storage, a planner that understands star schemas, elastic compute separated from storage, transactions over multi-table loads, time travel, and access control at column and row level. The lake story is largely the story of discovering how much of that bundle mattered.

    THE DETOUR

    The lake, and how it silted up

    The idea was excellent and the first implementation was missing four things. Naming them precisely is more useful than the swamp metaphor.

    The lake proposition was compelling around 2012. Object storage was twenty times cheaper than warehouse storage. Schema-on-write forced you to decide a schema before you knew what the data was for, and discarded anything that did not fit. So: land everything raw in cheap storage, impose schema at read time, and keep the optionality.

    All of that is sound, and the optionality argument in particular was correct. What went wrong was not the concept but four specific absences:

    No atomicity
    A write of fifty files followed by a metadata update is not one operation. Readers arriving in the middle see a partial dataset. This is the subject of the next section and it is the root cause of most of the rest.
    No schema enforcement
    Schema-on-read means nothing rejects a malformed file. Chapter 6's argument applies: with no gate, drift accumulates silently until a consumer breaks or, worse, quietly computes the wrong number.
    No efficient updates or deletes
    Objects are immutable, so "delete this customer's rows" means finding every file containing them and rewriting each whole. Which made GDPR erasure requests, when they arrived, an engineering project rather than a query.
    No usable metadata
    Finding which files belong to a table meant listing a prefix, which chapter 7 established is a slow paginated API call. At scale, query planning came to take longer than query execution. The second demo measures this.

    The consequence was predictable and widely experienced: data that nobody could be sure was complete, correct or current, in a store nobody could query quickly. The pejorative was earned, but it described an implementation gap rather than a flawed idea — which matters, because the fix turned out to be additive rather than a retreat to warehouses.

    THE MISSING PRIMITIVE

    Atomicity, measured

    Replacing a partition means several object operations. Without a commit protocol, every reader arriving during those operations sees something that was never true.

    Take a concrete case. A daily job replaces yesterday's partition: four existing files holding 250 rows each become six new files holding 200 rows each. The correct answer before the job is 1,000 rows and after it is 1,200. There is no correct answer of 250, or 2,000.

    But a reader that discovers its files by listing a directory sees whatever objects happen to exist at that instant. The demo puts readers at random moments across the operation and counts how many get an answer that was never true.

    Three results worth stating.

    1. Both non-atomic orderings fail, in opposite directions. Deleting first makes rows vanish — the worst observed error is 100%, an empty partition. Writing first makes rows duplicate — up to 120% too many. Neither is safe; the choice is only between which wrong answer you prefer.
    2. The exposure is not the whole operation, and that makes it worse. The torn window measures about 79% of the operation rather than 100%, because at the very start and the very end the file set coincidentally produces a clean-looking count. So the bug is invisible at both ends, which is exactly where a hurried test would sample.
    3. An atomic pointer swap eliminates it entirely. Zero readers out of twenty thousand see a false answer, because the pointer moves from one complete file set to another in a single operation. Every reader gets either the old snapshot or the new one, and both were true at some moment.
    Concurrent writers are the second half of the problem

    Switch to two writers. With no conflict check, both replace the partition from the same starting point and both sets of files end up present — 2,400 rows where there should be 1,200. Nothing errors; the table is simply double-counted, permanently, and neither job's logs show anything wrong.

    Turn on compare-and-swap and one writer commits while the other detects that the snapshot it started from is no longer current, and retries. That check — a conditional write on a single metadata object, which chapter 7 noted object stores now support — is the whole mechanism. It is why table formats do not need an external lock service.

    THE FIX

    Table formats

    A table format is a specification for a metadata layer over immutable files. It converts a directory of Parquet into something with transactions, schema and history.

    The shape is the same in all three implementations. Data files stay ordinary Parquet. Above them sits metadata listing exactly which files constitute the table at each version, with statistics for each. A commit writes new data files, writes new metadata, and then atomically moves a single pointer. Readers resolve the pointer first, so they always see a consistent file set — the atomic case in the demo above.

    What all three give you, and what the plain lake did not:

  1. ACID commits over many files, via the pointer swap and compare-and-swap measured above.
  2. Time travel, because old metadata versions still reference their file sets. Querying the table as of last Tuesday is a metadata lookup, not a restore.
  3. Schema evolution with the compatibility discipline of chapter 6, enforced rather than hoped for.
  4. Row-level updates and deletes, by rewriting affected files or writing delete files that readers apply — the copy-on-write and merge-on-read trade below.
  5. File-level statistics in the metadata, which extends chapter 8's row-group pruning up a level and is the subject of the next demo.
    6. Copy-on-write against merge-on-read

    Updating a row means either rewriting every file containing it (copy-on-write: expensive writes, fast reads) or writing a small delete or change file that readers merge at query time (merge-on-read: cheap writes, slower reads that degrade until compaction). This is precisely the read-write-space trade from chapter 10, reappearing one layer up. Copy-on-write for tables read far more than written; merge-on-read for streaming upserts, with compaction scheduled and monitored.

    One feature deserves calling out because it fixes a real recurring failure. Iceberg's hidden partitioning stores the partition transform in metadata rather than in the directory path. So a table partitioned by day of an event timestamp does not require the query to say WHERE dt = '2026-09-04' alongside its timestamp filter — filtering on the timestamp is enough, and the engine derives the partitions. That removes an entire class of "the query silently scanned everything because the analyst did not know about the partition column".

    THE OTHER HALF

    Metadata at scale

    Atomicity was the correctness fix. Metadata was the performance fix, and at large table counts it is the more visible one.

    Consider a table of ten years of daily partitions with twenty files each — 73,000 files — and a query wanting one week. Before any data is read, the engine has to work out which files it needs.

    A Hive-style table has to discover that by listing object keys, a thousand at a time, and then open file footers to get statistics. An Iceberg-style table reads a metadata file, then a manifest list carrying partition ranges, and reads only the manifests that can contain matching partitions.

    The number that matters is not the ratio at one size but how each scales. Raise the partition count tenfold while asking the same seven-day question: Hive-style planning goes from 213 requests to 870, because it must enumerate the whole table to find out what is in it. Manifest-based planning stays at 3, because the manifest list tells it which manifests can possibly match and it reads only those. At 50 ms a request that is roughly 11 seconds becoming 44, against 0.15 seconds staying 0.15.

    Why this was experienced as "the lake is slow"

    Planning cost is paid before a single row is read, so it is a fixed floor under every query however selective. A dashboard tile wanting one day of data waited on a full table enumeration. Teams concluded object storage was slow, when the actual problem was that they were asking the object store to serve as a catalogue — which chapter 7 explained it is structurally bad at, because directories are not real.

    There is a second effect the demo does not show: manifests carry per-file column statistics, so a table format can prune by a non-partition column too. Hive-style tables cannot, short of opening every footer, which is the expensive thing they were trying to avoid.

    THE ORGANISATIONAL LAYER

    Mesh, fabric and hub, assessed

    Three terms that get sold as architectures. One is a genuine organisational idea, one is mostly a product category, and one is a pattern.

    Data mesh
    A response to a real problem: a central data team becomes the bottleneck for every question in the company — the third row of chapter 1's maturity table. The proposal is domain ownership of data as a product, on a self-serve platform, with federated governance. It is an organisational design, not a technology, and the platform is a prerequisite rather than a consequence.
    Data fabric
    A metadata-driven integration layer that discovers, catalogues and connects data across systems, ideally with active metadata driving automation. Largely vendor-defined and vendor-shaped. The underlying capabilities — catalogue, lineage, discovery — are real and appear in chapter 21; the umbrella term adds little.
    Data hub
    A central point through which data flows between systems, with governance applied in transit. A pattern rather than a movement, and a sensible one at moderate integration counts.
    The mesh prerequisite people skip

    Domain ownership only works if a domain team can actually publish a governed, discoverable, contract-bearing dataset without needing the central team. That requires the platform — self-serve storage, orchestration, CI, contract enforcement, lineage, cost attribution — to exist and be genuinely usable first.

    Adopting the org structure before the platform gives you the same silos with new vocabulary, plus the central team's expertise dispersed. Chapter 3 listed this as a named failure: adopting a pattern without its prerequisites. If you have fewer than a few hundred engineers, the honest answer is that a central team with good self-serve tooling is almost certainly better.

    Worth being clear that the warehouse-versus-lakehouse framing is largely obsolete as a choice. Warehouses now read and write open table formats on your storage; lakehouse engines now offer SQL, governance and elastic compute. The remaining question is mostly where the authoritative copy lives and who can read it, which is a portability question rather than an architecture one.

    Recap

    What to take from this chapter

    1. Kimball won delivery, Inmon won integration, and the standard raw / staging / marts layering is the synthesis. Each layer must be derivable from the one before it.
    2. The lake concept was sound; four things were missing — atomicity, schema enforcement, efficient updates, and usable metadata.
    3. Non-atomic writes give readers answers that were never true. Deleting first makes rows vanish, up to a 100% error; writing first duplicates them, up to 120%.
    4. The torn window is about 79% of the operation, not all of it, because the very start and end coincidentally look clean — so the bug hides exactly where a quick test would sample.
    5. An atomic pointer swap eliminates it completely: zero false answers in twenty thousand readers.
    6. Concurrent writers double-count silently without a conflict check. Compare-and-swap on one metadata object is the whole mechanism, which is why no external lock service is needed.
    7. A table format is a metadata layer over ordinary Parquet giving ACID commits, time travel, enforced schema evolution, row-level deletes and file statistics.
    8. Copy-on-write against merge-on-read is chapter 10's trade one layer up. Cheap writes cost read performance until compaction runs.
    9. Hive-style planning scales with the table; manifest planning does not. Tenfold the partitions for the same seven-day query takes Hive from 213 requests to 870 while manifests stay at 3 — 11 seconds becoming 44, against 0.15 either way.
    10. Planning cost is a fixed floor under every query, which is why lakes were experienced as slow: the object store was being used as a catalogue.
    11. Mesh is an organisational design and the platform is its prerequisite. Adopting it first gives you the same silos with new vocabulary.
    12. Warehouse against lakehouse is no longer the real question. Where the authoritative copy lives and who can read it is.

    On your largest table, time a query that selects one day and compare it against one that selects a year. If the two are closer than the data volumes suggest, you are paying a planning floor.
