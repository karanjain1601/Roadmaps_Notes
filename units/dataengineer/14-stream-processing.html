CHAPTER 14

Stream processing

Batch has a luxury streaming does not: a batch job for yesterday runs when yesterday is definitively over. A streaming job has to decide, continuously and without ever being certain, that it has seen enough of a period to publish an answer. Every difficult thing in this chapter is a consequence of that one problem.

    TWO CLOCKS

    Event time and processing time

    The distinction looked pedantic in chapter 12. In streaming it is the whole subject.

    Event time is when the thing happened, recorded by whatever produced it. Processing time is when your job saw it. The gap between them is unbounded in principle and irregular in practice: a phone offline in a tunnel, a queue backlog, a retry, a third-party feed that batches hourly.

    Which clock you use decides what the answer means:

    Processing-time windows

    Group by when you saw it. Trivial to implement, never late, never incomplete — and the numbers are not reproducible. Replay the same input and a different set of events lands in each window, so the same job over the same data gives different answers.

    Fine for operational monitoring: throughput, error rates, queue depth.

    Event-time windows

    Group by when it happened. Reproducible, correct, and requires deciding when a window is finished, which you can never know for certain. Everything hard is here.

    Required for anything a business will act on: revenue per minute, sessions, conversion rates.

    The test for which you need

    Ask whether re-running the job over the same input must produce the same output. If yes — because someone will reconcile it, audit it, or compare it against a batch pipeline — you need event time, and you have signed up for watermarks. If the number is only meaningful as "what is happening right now", processing time is simpler and honest.

    Getting this wrong in the reproducible direction is the more common error: a revenue-per-minute dashboard on processing time disagrees with the warehouse every day, and nobody can say which is right.

    GROUPING

    Window types

    An unbounded stream has no end, so aggregation requires cutting it into finite pieces. Four ways.

    Tumbling
    Fixed size, non-overlapping. Every event belongs to exactly one window. The default, and the direct analogue of a batch partition — a one-day tumbling window is a daily batch job.
    Sliding (hopping)
    Fixed size, advancing by a smaller step, so windows overlap and an event belongs to several. A five-minute window every minute gives a smooth rolling average. The cost is duplication: with a size-to-slide ratio of five, every event is held in five windows and state is five times larger.
    Session
    Boundaries defined by inactivity: a window closes when no event for a key arrives within a gap. Size is data-dependent and unbounded — a user clicking every twenty seconds for four hours produces one four-hour session. The right shape for user behaviour and the most awkward operationally, because you cannot bound the state.
    Global
    One window over all time, emitting on a trigger rather than a boundary. Running totals, all-time counts. State grows forever unless you can express the aggregate incrementally.

    Two properties determine the cost of a window choice. How many windows an event belongs to multiplies state directly. And whether the aggregate is incremental — a sum or count needs one number per window, whereas a median or an exact distinct count needs every value retained, which is why streaming systems push you towards approximate sketches such as HyperLogLog.

    THE CENTRAL MECHANISM

    Watermarks

    A watermark is the system's claim that it has probably seen everything up to a point in event time. It is a heuristic, and knowing exactly how it is wrong is the point.

    The usual construction is simple: watermark = the highest event time seen so far, minus an allowed lateness. When the watermark passes a window's end, the window fires and emits its result. Anything arriving afterwards is late: dropped, or diverted to a side output, or used to update an already-emitted result if the sink supports it.

    The allowed lateness is the only real dial, and it is a direct trade between how complete the answer is and how long you wait for it.

    Three results.

    1. Completeness and latency rise together, with diminishing returns on one and none on the other. At zero allowed lateness the job emits 81.5% of each window's events after 10.8 seconds; at 40 seconds it emits 97.5% after 51 seconds; at 160 seconds it emits 100% after 171 seconds. Completeness flattens and latency does not, so there is a sensible stopping point.
    2. This is chapter 12's lookback window, paid in a different currency. Batch bought completeness with compute — reprocessing three days each night at three times the cost. Streaming buys the same completeness with latency. The lateness distribution is the same distribution, and the percentile you choose to lose is the same decision.
    3. An idle partition stalls everything. Because the watermark is the minimum across partitions — it must be, or one fast partition would advance it past data still to come from a slow one — a partition producing nothing holds the watermark still. Set the toggle and zero of sixty windows ever fire. The job is healthy by every other measure: consuming, no lag, no errors, and silently emitting nothing.
    The idle-partition failure is the classic streaming outage

    It happens whenever a topic is partitioned more finely than the data justifies, or when a key range goes quiet overnight, or after a partition count increase leaves some partitions empty. The symptom is that output stops while every dashboard says the job is fine.

    The fix is an idleness timeout: after a configured period with no data, a partition is excluded from the watermark calculation. Every serious stream processor offers this and it is off by default, because enabling it means accepting that data from a resumed partition will be late. Know which of the two failures you have chosen.

    WHERE IT GETS HARD

    State, and stream-to-stream joins

    Aggregating a stream needs a little state. Joining two streams needs a lot, and the amount is set by how long you are willing to wait.

    A stateless transformation — parse, filter, enrich from a static lookup — is easy and scales trivially. State is what makes streaming an operational discipline: it has to be checkpointed to survive a restart, redistributed when the job rescales, and kept small enough to fit.

    The hardest case is joining two streams, because neither side is complete. Joining clicks to impressions means the impression must be held in memory until its click arrives, and you have no way to know whether a click is coming.

    The shape of the trade is the important part. Recall rises with the window and flattens — 20% at ten seconds, 74% at a minute, 93% at two minutes, effectively 100% at five. State rises strictly linearly: ten times the window is exactly ten times the memory, with no flattening at all. So the marginal cost of the last few percent of recall is enormous, and the decision is where on that curve you stop.

    Why an unmatched join is worse than a slow one

    A click that arrives after its window does not merely go unjoined — depending on the join type it either disappears or emerges with null impression attributes, and either way the attribution is wrong rather than absent. With a sixty-second window, 26% of clicks are affected, and the resulting conversion rate is quietly understated by roughly that much.

    This is why an equivalent batch job over the same data frequently disagrees with the stream, and why the batch answer is usually the right one: it had the luxury of waiting.

    Two mitigations worth knowing. A stream-to-table join — enriching a stream from a slowly changing dimension held as a compacted topic or a local store — has none of this difficulty, because the table side is complete by construction. Prefer it wherever the second stream is really a lookup. And where you genuinely need the late matches, the honest pattern is a stream for the fast approximate answer and a batch job for the correct one, with the batch result treated as authoritative. That is the practical core of what used to be called a lambda architecture, and it survives because the underlying trade is real.

    CORRECTNESS

    Exactly-once, in a stream processor

    Chapter 13 said this claim is bounded by one system. Here is what the boundary looks like in practice.

    A stream processor achieves exactly-once processing by checkpointing: it periodically snapshots all operator state together with the input offsets that state corresponds to. On failure it restores the snapshot and rewinds the input to the matching offsets. State and position are always consistent, so no input is counted twice and none is skipped.

    That is genuinely exactly-once for the internal state. The boundary is the sink:

    What a checkpoint can and cannot protect
    SinkGuarantee availableMechanism
    Kafka topicExactly-onceTransactional writes committed with the checkpoint
    Table format or warehouseExactly-onceAtomic commit tied to the checkpoint — chapter 11's pointer swap
    Database with an upsert keyEffectively-onceIdempotent write, so a replay overwrites
    Append-only file or tableAt-least-onceA replay after a checkpoint duplicates rows
    HTTP call, email, paymentAt-least-onceNothing can un-send it; needs an idempotency key at the far end

    So the guarantee is a property of the whole path rather than of the processor, and it lands in the same place as chapters 5, 12 and 13: the strongest thing available end to end is an idempotent effect. Checkpointing means you get that without also having to make the internal aggregation idempotent, which is a real and substantial benefit — just not the one the marketing implies.

    Two operational consequences of checkpointing. The interval is a trade: frequent checkpoints mean less reprocessing after a failure and more steady-state overhead. And checkpoint size is state size, so a job with a large session-window state or a wide join window takes a long time to snapshot and a long time to restore — which is the same state the previous section priced, showing up as recovery time.

    THE DECISION

    When streaming earns its cost

    Streaming is strictly harder to build and operate than batch. That is worth it sometimes, and the test is narrower than enthusiasm suggests.

    Chapter 2 established the ceiling on what streaming can buy: end-to-end freshness is the sum of every stage's wait plus its runtime, and continuous stages contribute only their runtime. A stream feeding a nightly mart is a nightly pipeline with extra operational surface.

  1. Is a decision made on this data within minutes? Fraud blocking, dynamic pricing, alerting, live personalisation. If the consumer is a human reading a dashboard once a morning, the answer is no.
  2. Does the whole path support it? If any downstream stage is scheduled hourly, streaming the earlier stages changes nothing a consumer can perceive.
  3. Is the volume such that batch cannot keep up? A genuine reason, and rarer than claimed — chapter 10 noted a single machine handles a great deal.
  4. Can you operate stateful infrastructure? Checkpoint storage, rescaling, state migration on code change, replay procedures. This is the cost people underestimate, and it is ongoing.
  5. Is the answer allowed to be approximate? If the number must reconcile exactly with a batch pipeline, you are signing up to run both and explain the difference.
    6. The middle option people skip

    Micro-batching — a batch job every one to five minutes — captures most of the freshness benefit with almost none of the operational cost. No watermarks, no checkpointed state, no rescaling procedure; just chapter 12's idempotent partition write on a short schedule. Chapter 2's model puts a five-minute chain at well under half an hour of worst-case staleness, which is current enough for the large majority of things people build streaming systems for.

    Reach for genuine streaming when you need seconds, when you need session windows, or when the volume makes repeated small batches wasteful. Otherwise micro-batch and spend the saved effort on correctness.

    Recap

    What to take from this chapter

    1. Processing-time windows are simple and not reproducible; event-time windows are reproducible and require deciding when a window is done. If anyone will reconcile the number, you need event time.
    2. Window choice sets state cost. How many windows an event belongs to multiplies state; a non-incremental aggregate like an exact distinct count retains every value.
    3. Session windows are unbounded by construction, which is why they are the hardest to operate.
    4. A watermark is a heuristic: highest event time seen, minus an allowed lateness.
    5. Completeness flattens and latency does not. Measured: 81.5% complete at 10.8 s, 97.5% at 51 s, 100% at 171 s. So there is a defensible stopping point.
    6. This is chapter 12's lookback window in a different currency — batch pays in compute, streaming pays in latency, and the underlying lateness distribution is the same.
    7. An idle partition stalls the watermark completely. Zero of sixty windows fire, while the job reports healthy with no lag and no errors. An idleness timeout is the fix, and it trades the stall for late data on resume.
    8. Stream-to-stream join recall flattens while state rises strictly linearly. 20% recall at 10 s, 74% at 60 s, 93% at 120 s; ten times the window is exactly ten times the memory.
    9. A missed join is wrong, not absent. At a sixty-second window 26% of clicks are affected and the conversion rate is understated by about that much, which is why a batch equivalent disagrees.
    10. Prefer a stream-to-table join where the second side is really a lookup; it has none of the incompleteness problem.
    11. Checkpointing gives exactly-once for internal state and stops at the sink. End to end, the strongest available guarantee is still an idempotent effect.
    12. Micro-batching is the option people skip, and it captures most of the freshness with almost none of the operational cost.

    If you run a streaming job with event-time windows, check whether an idleness timeout is configured. If not, you have an outage waiting for the first quiet partition.
