CHAPTER 20

CI/CD and testing data

Nineteen chapters have introduced a specific catalogue of ways a data platform produces wrong answers. This chapter takes that catalogue and asks, for each entry, which kind of check would actually have caught it. The answer is uncomfortable in two places: unit tests catch almost none of them, and one failure is undetectable by any test at all.

    A DIFFERENT PROBLEM

    Why testing data is not testing code

    Software testing assumes the input is fixed and the code is suspect. In a pipeline both move, and usually it is the input.

    A unit test pins an input, runs the code, and asserts an output. That works because the input is under your control. A pipeline's input arrives from a system you do not own, changing in ways chapter 4 catalogued, so a passing test suite tells you the code does what it did yesterday to data that no longer looks like yesterday's.

    The two testing problems, side by side
    Testing codeTesting a pipeline
    What variesThe codeThe code and the data, and mostly the data
    When you find outAt build timeAt run time, on real input
    Failure modeAn exceptionA plausible wrong number
    DeterminismSame input, same outputYesterday's input no longer exists
    Coverage meansLines exercisedFailure modes detectable
    The consequence for where effort goes

    Testing code catches the failures that would announce themselves anyway. Chapter 4 established the asymmetry: loud breakage is cheap and silent drift is expensive. A dropped column throws an exception on the next run and costs you an hour; an enum quietly gaining a seventh value costs every decision made since.

    So the useful question is not "what percentage of lines are covered" but "which of the ways this can be wrong would we find out about, and how fast". The first demo answers that literally.

    THE LAYERS

    Four kinds of check

    They catch different things and belong at different points in the lifecycle. Most teams have the first and skip the fourth.

    Unit tests, on transformation logic
    Fixed input rows in, expected rows out, no warehouse involved. Fast, deterministic, and they run on every commit. They catch logic errors and nothing about the data. Worth having for anything with real branching — a revenue calculation with six edge cases is exactly the thing to pin.
    Contract and schema checks, in CI
    Chapter 6's compatibility rules, run against the registered schema on every pull request. The point made there stands: the same rule applied hours earlier, to someone who can still change their mind cheaply.
    Integration tests, on a real engine
    Run the transformation against a small fixed dataset in an actual warehouse or DuckDB. Catches what unit tests cannot: dialect differences, type coercion, null semantics, join behaviour. Slower, so a subset rather than everything.
    Data assertions, in production
    Checks that run against real output every time the pipeline runs: freshness, volume, uniqueness, referential integrity, distribution, reconciliation. This is the layer that catches the failures in this unit, and the one most often absent.

    The distinction worth being precise about: the first three test your code and run before deployment; the fourth tests the data and runs forever. Only the fourth can detect a source system changing behaviour, because that is not a code change at all.

    Which check catches which failure

    Four results, and the first is the one that should change what you build next.

    1. Unit tests alone catch 2 of 16. They are worth having and they are not a data quality strategy. Adding schema checks takes it to 3 — because schema checks, by design, catch the loud failures that were going to announce themselves anyway.
    2. Reconciliation against source is the single highest-value check, adding four failures on top of unit and schema tests — more than any other. It is also the one teams most often skip, because it requires counting on both sides rather than only inspecting your own output.
    3. Recomputing an old period and comparing is the second. It is the only thing that detects late-data incompleteness and SCD misattribution, both of which produce output that is internally consistent and wrong.
    4. With every check enabled, 15 of 16 are covered — and one is not. Two teams defining a metric differently is undetectable by any test, because there is no defect in the data. Both numbers are correct computations of different things. That is why chapter 17's answer was a semantic layer rather than an assertion.
    The pattern across the uncaught ones

    Work through the failures that survive a typical check set — freshness, volume, uniqueness — and they have a family resemblance. The cold-row corruption from chapter 5, the SCD misattribution from chapter 9, the late-data gap from chapter 12: in each case the row count is right, the schema is right, the freshness is right, and the values are wrong.

    Structural checks verify structure. Only comparing against something independent — the source, or the same period recomputed later — verifies content. That is the gap, and it is why the two highest-value checks are both comparisons.

    What the assertions look like

    assertions.sql
    -- freshness: did it run, and is the newest row recent enough?
SELECT max(loaded_at) > now() - interval '3 hours' AS ok FROM fct_order;

-- volume: is today's count within a plausible band of the trailing median?
SELECT count(*) BETWEEN 0.7 * :median AND 1.4 * :median AS ok
FROM   fct_order WHERE dt = :run_date;

-- uniqueness: the grain declared in chapter 9, enforced
SELECT count(*) = count(DISTINCT order_line_id) AS ok FROM fct_order_line;

-- referential integrity: no orphaned facts after a join
SELECT count(*) = 0 AS ok
FROM   fct_order f LEFT JOIN dim_customer d USING (customer_key)
WHERE  d.customer_key IS NULL;

-- reconciliation: does the source agree?
SELECT abs(:source_count - count(*)) <= 0.001 * :source_count AS ok
FROM   fct_order WHERE dt = :run_date;

    Two design notes. Bands, not equality — a volume check asserting an exact count fails on every normal day, and one asserting "more than zero" catches nothing. And assertions belong in the DAG as tasks, per chapter 16, so a failure stops the graph before the bad data reaches a consumer rather than alerting after it has.

    BEFORE IT SHIPS

    What runs on a pull request

    A budget of about ten minutes. Spend it on the checks that need a human to still be paying attention.

  1. Lint and compile. Does the SQL parse, do the model references resolve, is the DAG acyclic. Seconds, and it catches the most common mistake.
  2. Unit tests on transformation logic with fixed fixtures.
  3. Schema compatibility against the registry, per chapter 6, failing the build on a breaking change.
  4. Build the changed models and their children into a scratch schema. The environment pattern from chapter 19: real data, real engine, isolated namespace. This catches dialect and type problems that fixtures cannot.
  5. Run the assertions against that build, so a change that would break uniqueness or referential integrity fails before merge rather than at 2am.
  6. Diff the output against production. The highest-value and least common step, below.
    7. Data diffing is the review tool this discipline was missing

    Build the changed models on real data, then compare row counts, column distributions and a sample of changed rows against the current production output. Post it on the pull request.

    This converts an unanswerable review question — "does this SQL change do what the author intended?" — into a factual one: this change alters 0.3% of rows, all in the EMEA region, and shifts the revenue total by £12,400. A reviewer can evaluate that. Nobody can evaluate a forty-line SQL diff by reading it, which is why data pull requests are so often approved without real scrutiny.

    What should not run on every pull request: the full pipeline, anything taking more than about ten minutes, and anything that touches production tables. Build only the changed models and their descendants — every serious transformation tool can work out that subgraph — and keep the full run for a scheduled job.

    SHIPPING IT

    Deploying a pipeline

    Deploying code is solved. Deploying a change that alters historical data is not, and the difference is worth naming.

    A pipeline deployment has two parts that people conflate. The code change is ordinary: version it, deploy it, roll it back if needed. The data change is not: if the new logic produces different values, existing history is now inconsistent with new output unless you backfill, and a rollback of the code does not roll back the data.

    Three kinds of change, and what each requires
    ChangeCodeDataRollback
    Add a columnDeployBackfill if history is wantedDrop the column
    Fix a bug in a measureDeployBackfill the affected periodCode reverts; data needs a second backfill
    Change a definitionDeployBackfill, and tell the consumersHard — downstream may have acted on it

    The third row is the one that causes arguments. A definition change makes today's number incomparable with last month's, and if nobody is told, somebody will present a trend line across the discontinuity. Treat a definition change as a release with an announcement, not a deployment — and where possible, publish both definitions in parallel for a period so consumers can migrate deliberately, which is the compatibility discipline of chapter 6 applied to semantics rather than schema.

    For the mechanics, the safest pattern is the one chapter 11 and chapter 12 both arrived at: build the new version alongside the old, verify it, then swap atomically. Blue-green for tables. It gives you a real rollback target, which the table on the right-hand column above shows you otherwise do not have.

    AFTER IT SHIPS

    Thresholds, and the limit nobody models

    A check that fires too often is worse than no check, because it consumes the attention the real failures needed.

    Every assertion needs a threshold, and the instinct is to make it sensitive so nothing is missed. On one metric that is right. Across a platform monitoring hundreds of tables and columns, it produces a volume of alerts nobody can work through — and alerts nobody reads detect nothing.

    The model below simulates a check on a metric with natural variance, scaled across however many series you monitor, and caps how many alerts a team can actually investigate in a week.

    The result is worth sitting with. At one series, the most sensitive threshold is best: 1.5 sigma detects 93% of problems and generates about one alert a week. At three hundred series the same threshold generates 328 alerts a week, a team that can work through five reads 2% of them, and the platform detects 1.4% of its real problems despite a raw recall of 93%.

    The best achievable threshold moves with the number of series — 1.5 sigma at one, 2.5 at twenty, 4 at three hundred — and the best achievable detection rate collapses from 93% to 8%. Monitoring more things with the same sensitivity makes you find fewer real problems.

    Which means threshold tuning is the wrong lever

    The model shows the optimum moving, and it also shows the ceiling falling however you move it. Raising capacity from 5 to 40 alerts a week lifts the best achievable detection from 8% to 50% — a far larger effect than any threshold change. So the levers that matter are the ones that change volume or capacity, not sensitivity:

    Monitor fewer things, chosen deliberately. Every table does not need a distribution check. The ones feeding decisions do.

    Group related alerts. One upstream failure firing forty downstream checks should be one incident, not forty. Alerting on the root of the lineage graph rather than every node is the single biggest volume reduction available.

    Separate blocking from informational. An assertion that stops the DAG needs a person. A distribution shift worth reviewing does not need to page anyone; it needs a dashboard somebody looks at weekly.

    Alert on the SLA, not on every failure — chapter 16's rule. A check that failed and passed on retry is not an incident.

    Recap

    What to take from this chapter

    1. Testing code assumes the input is fixed; a pipeline's input is the thing that changes. Coverage should mean failure modes detectable, not lines exercised.
    2. Four layers: unit tests, contract checks, integration tests, and data assertions in production. Only the fourth detects a source system changing behaviour.
    3. Unit tests alone catch 2 of the 16 failure modes in this unit; adding schema checks reaches 3, because schema checks catch the loud failures that would announce themselves anyway.
    4. Reconciliation against source is the highest-value single check, adding four failures on top of unit and schema tests.
    5. Recomputing an old period is the second, and the only thing that catches late-data gaps and SCD misattribution.
    6. With every check enabled, 15 of 16 are covered. The exception — two teams defining a metric differently — is not a data defect, which is why chapter 17's answer was a semantic layer.
    7. The uncaught failures share a shape: right row count, right schema, right freshness, wrong values. Structure checks verify structure; only comparison verifies content.
    8. Use bands, not equality, and put assertions in the DAG so a failure stops the graph.
    9. Data diffing on a pull request converts an unanswerable review question into a factual one, and it is the review tool this discipline was missing.
    10. A code rollback does not roll back data. Definition changes are releases with announcements, not deployments.
    11. At 300 monitored series, a 1.5-sigma threshold produces 328 alerts a week and detects 1.4% of real problems despite 93% raw recall.
    12. The best threshold moves with the number of series and the ceiling falls anyway. Capacity from 5 to 40 alerts a week lifts achievable detection from 8% to 50% — far more than any threshold change.
    13. Monitor fewer things, group by lineage root, and separate blocking from informational.
