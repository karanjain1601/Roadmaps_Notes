CHAPTER 18

Serving ML and applications

A dashboard reads what is true now. A model has to be trained on what was true at some moment in the past and then scored on what is true at some moment in the future, and the two must be computed identically. Almost every serious machine learning data bug is a violation of one of those two requirements.

    A DIFFERENT CUSTOMER

    What a model team needs that a dashboard team does not

    Four requirements, all of which are easy to serve badly without anybody noticing until the model underperforms in production.

    History as it was, not as it is
    A dashboard wants the customer's current segment. A model trained on last March needs the segment they were in last March. That is exactly the type-2 dimension of chapter 9, and where it was skipped, training data is quietly wrong.
    The same computation twice
    Features must be computed identically for training, over months of history in batch, and for scoring, for one entity in milliseconds. Two code paths for one definition is the default outcome and the second-largest source of failure here.
    Low-latency lookup
    Scoring a request needs a few hundred feature values in single-digit milliseconds. A warehouse cannot do that — chapter 10 put columnar last on point lookups — so a second store is not optional.
    Reproducibility
    Retraining next quarter must be able to rebuild the exact training set, or you cannot tell whether a change in performance came from the model or the data.
    The framing that makes this tractable

    A model is not a consumer of your data in the way a dashboard is. It is a consumer of a function: "the value of feature F for entity E as of time T". Training calls that function for millions of (E, T) pairs in the past; serving calls it for one entity at the present moment. Everything in this chapter is about making one function answer both calls consistently.

    THE FIRST REQUIREMENT

    Point-in-time correctness

    Joining features to labels without respecting time lets the future leak into the past, and the resulting model looks excellent right up until it is deployed.

    The setup is ordinary. You have labelled examples — customer 4182 churned on 12 March — and you want features for them. The obvious join is against your customer table, which holds current values. That join is wrong, and wrong in the direction that flatters you: today's values for customer 4182 reflect everything that happened after March, including things caused by the churn itself.

    Take a concrete leak. Support tickets tend to spike after a customer decides to leave. A feature counting support tickets, built from a full history, is therefore an excellent predictor of churn in your training data and worthless at decision time, because at the moment you need a prediction those tickets have not been filed.

    The shape of the result is worse than "the model is not as good as it looked".

    1. Offline evaluation reports a near-perfect 1.000 once the model leans on the leaked feature. Every offline check passes: held-out test set, cross-validation, all of it, because the leak is in the data rather than in the split.
    2. In production it collapses to 0.513 — barely better than a coin toss — because the feature it relies on carries no information at decision time.
    3. The point-in-time model scores 0.882 both offline and in production. So the leaky model does not merely disappoint; it is substantially worse than the honest one it beat in evaluation. Leakage does not just inflate a number, it causes you to ship the wrong model.
    Why cross-validation cannot catch this

    Every offline validation technique splits the examples. Leakage is a property of how each example's features were constructed, so it is present in the training fold and the test fold equally. A perfectly executed cross-validation over leaked data reports a perfectly consistent, perfectly wrong number.

    The only reliable defence is structural: build features with an as-of join and verify that no feature value used a row written after the label timestamp. And the loudest warning sign is a model that performs far better than the problem should allow. An AUC of 0.99 on churn is not a triumph, it is a bug report.

    The as-of join

    The correct join takes each labelled example's timestamp and asks for the feature value as it stood at that moment:

    as_of_join.sql
    -- for every label, the most recent feature row written strictly before it
SELECT l.entity_id,
       l.label_ts,
       l.churned,
       f.tickets_30d,
       f.orders_90d
FROM   labels l
LEFT JOIN LATERAL (
  SELECT *
  FROM   feature_history f
  WHERE  f.entity_id  = l.entity_id
    AND  f.valid_from <= l.label_ts        -- nothing from the future
  ORDER BY f.valid_from DESC
  LIMIT  1
) f ON true;

    Two things that join needs, and both are chapters you have already read. It needs feature_history to exist at all, which is chapter 9's type-2 dimension — a type-1 table has overwritten the past and cannot answer the question. And it needs the timestamps to be trustworthy, which is chapter 4's warning that updated_at is application convention rather than a guarantee.

    There is a subtler version worth guarding against: a feature that is technically point-in-time correct but was not available at that moment. A daily aggregate stamped with the start of the day is correct as of midnight and was not computed until 02:00, so a model scoring at 00:30 will not have it. The rule is to join on when the value became available, not on when it became true.

    THE INFRASTRUCTURE

    Feature stores

    Two stores, one definition. Most of the value is in the "one definition" half, which is also the half teams skip.

    A feature store has an offline store — historical values with validity ranges, in your warehouse or lakehouse, supporting as-of joins over millions of rows — and an online store, a low-latency key-value store holding the current value per entity for millisecond lookups at scoring time. Redis, DynamoDB and similar, for exactly the reason chapter 10 gave: point lookups are what key-value stores are for and what columnar stores are worst at.

    The part that matters is that both are populated from one feature definition. Write the transformation once; a batch job materialises history into the offline store and a streaming or scheduled job pushes current values into the online store. That single-definition property is what prevents the skew in the next section, and it is the reason to adopt a feature store rather than building two pipelines.

    The two stores, and what each is for
    Offline storeOnline store
    Used byTraining and batch scoringReal-time scoring
    Query shapeAs-of join over millions of rowsGet a few hundred values by key
    Latency targetMinutesSingle-digit milliseconds
    HoldsFull history with validity rangesCurrent value only
    Typical technologyWarehouse or lakehouse tableRedis, DynamoDB, Cassandra
    You may not need the product

    A feature store is a real category with real tools, and for one or two models it is straightforwardly more machinery than the problem justifies — chapter 3's arithmetic again. What you cannot skip are the properties: one definition, history retained, an as-of join, and a low-latency read path.

    Those are achievable with a type-2 table in the warehouse, a scheduled job pushing current values into Redis, and the discipline of generating both from the same SQL. Adopt the product when you have enough models and teams that discovery and reuse become the bottleneck, which is the problem it is genuinely best at.

    THE SECOND REQUIREMENT

    Training-serving skew

    The same feature name computed two ways gives two distributions, and the model was fitted to one of them.

    Skew is any systematic difference between a feature's value at training time and at serving time. It comes from four places, and the fourth is the one this unit has already measured:

    Where it comes from

    • Two code paths. SQL for training, Python in the service. They diverge on nulls, rounding, timezones and edge cases.
    • Different windows. "Last 30 days" from midnight in batch, from now in serving.
    • Different null handling. Batch fills a missing value with the median; the service sends zero.
    • Incomplete data at serving. The batch job had the benefit of a lookback window; the online store does not.

    Why it is hard to see

    • Nothing errors — the feature has a plausible value.
    • Offline metrics are unaffected, because training used the training version.
    • The model degrades gradually rather than failing.
    • It is attributed to "drift" and answered with a retrain, which does not fix it.

    The demo takes the fourth cause and prices it, using the exact completeness figures chapter 12 measured. The feature is "orders in the last thirty days"; the batch path enjoys a lookback window and sees nearly everything, while the online path sees only what has arrived.

    At chapter 12's one-day lookback — 76.2% completeness, which sounds tolerable — the mean feature value drops from 5.47 to 4.18 and 8.8% of threshold decisions flip. Every one of those is a model making a different call than it would have on training-quality data, and there is no error anywhere in the system to notice it.

    The three defences, in order

    One definition, executed twice. Generate both paths from one specification, which is the feature store's core benefit and removes the first three causes entirely.

    Log what you actually served. Record the feature vector used for each prediction. This gives you the serving distribution to compare against the training distribution — and, more valuable, it gives you the correct training data for the next model, because it is by construction exactly what will be available at decision time.

    Compare the distributions automatically. A scheduled check on mean, variance and null rate per feature, training against serving, alerting on divergence. This is the only defence that catches the fourth cause, because incompleteness is a property of the data rather than of the code.

    A NEWER SHAPE

    Embeddings and vector serving

    Semantic search and retrieval-augmented generation put a new store in the platform, with familiar problems underneath.

    An embedding is a fixed-length vector of floats representing a piece of content, positioned so that similar things sit near each other. Serving them means answering "which stored vectors are nearest to this one", which needs an approximate nearest-neighbour index — HNSW or IVF — because exact search over millions of vectors is too slow.

    From a data engineering standpoint this is a pipeline like any other, with four properties worth planning for:

    Re-embedding is a full rebuild
    Change the embedding model and every stored vector is invalid, because vectors from different models are not comparable. That is a complete reprocessing of the corpus, which is chapter 12's backfill with a GPU bill attached. Version the model with the vectors, and plan the migration before you need it.
    Chunking is a modelling decision
    How you split documents determines what can be retrieved. Too large and the relevant sentence is diluted; too small and context is lost. It is not a preprocessing detail, it is the grain decision of chapter 9 in another form, and it deserves the same deliberateness.
    Freshness applies as it always did
    A vector index built nightly answers yesterday's questions. The freshness arithmetic of chapter 2 is unchanged: worst case is the sum of every wait plus every run, and an embedding step is just another stage.
    Recall is a tuning parameter with a cost
    Approximate search trades accuracy for speed, and the index parameters set where you sit. That is the same recall-against-resources curve as the stream join in chapter 14, and it should be measured rather than defaulted.

    Worth noting that a dedicated vector database is frequently unnecessary. Postgres with pgvector, or the vector support now in most warehouses and search engines, handles corpora of a few million vectors comfortably — and chapter 3's build-against-buy arithmetic applies exactly as it did to every other store in this unit.

    THE STRICTEST CONSUMER

    Serving data back into applications

    When a pipeline output appears in a product, the obligations change and usually nobody says so out loud.

    A recommendation on a page, a risk score in a checkout, a personalised feed: these are pipeline outputs on a user-facing path. The differences from a dashboard are large.

    What changes when the consumer is the product
    DashboardApplication
    Latency budgetSecondsTens of milliseconds
    ConcurrencyTensThousands per second
    Availability needBusiness hoursWhatever the product promises
    Missing dataAn empty tileA broken page, unless there is a fallback
    Wrong dataA confused analystA customer-visible error
    RollbackRerun the jobNeeds a version to roll back to
    Always define the degraded path

    The single most important design decision on an application-serving path is what happens when the data is absent, stale or clearly wrong. Serve a default? A cached previous value? Hide the feature entirely? Every one of those is a legitimate answer and no answer is not, because the failure will happen and the behaviour will then be decided by whatever the code does by accident.

    The corollary is that these paths need a staleness check at read time, not just an alert on the pipeline. A consumer that can tell the data is four hours old can degrade deliberately; one that cannot will serve four-hour-old prices with complete confidence.

    Two other things follow from the table. You need a rollback target, which means the serving store should hold at least the previous version rather than being overwritten in place — the atomic pointer swap of chapter 11, applied to a Redis key or a served index. And the pipeline now inherits the product's availability promise, which is a genuine on-call obligation and should be agreed explicitly rather than discovered during an incident.

    Recap

    What to take from this chapter

    1. A model consumes a function, not a table: the value of feature F for entity E as of time T, called for millions of past pairs at training and for one entity now at serving.
    2. Joining features to labels without respecting time lets the future leak in, and it flatters you.
    3. Offline AUC of 1.000, production 0.513, honest model 0.882 both. The leaky model is not merely disappointing — it is worse in production than the model it beat in evaluation, so leakage makes you ship the wrong one.
    4. Cross-validation cannot catch leakage, because it splits examples while leakage is a property of how each example was constructed.
    5. Performance far better than the problem allows is a bug report, not a result.
    6. An as-of join needs type-2 history and trustworthy timestamps — chapters 9 and 4. And it should join on when a value became available, not when it became true.
    7. A feature store is two stores and one definition, and the single definition is the part that matters. The properties are achievable without the product; adopt it when discovery and reuse become the bottleneck.
    8. Skew comes from two code paths, different windows, different null handling and incomplete serving data.
    9. Chapter 12's one-day lookback, 76.2% complete, moves the mean feature from 5.47 to 4.18 and flips 8.8% of decisions — with no error anywhere.
    10. Log the feature vector you actually served. It gives you the serving distribution and, better, correct training data for the next model.
    11. Re-embedding is a full corpus rebuild, and chunking is a grain decision rather than preprocessing.
    12. Application paths need a defined degraded behaviour, a read-time staleness check and a rollback target. The failure will happen; the only question is whether the response was designed.

    Take any model in production and ask whether its training features were built with an as-of join. If the answer is that they were joined against current dimension tables, the offline metric is not measuring what you think.
