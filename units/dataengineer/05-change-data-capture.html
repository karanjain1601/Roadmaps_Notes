CHAPTER 05

Change data capture

Chapter 4 ended on a problem with no good solution inside the query model: you cannot reliably infer change by asking a database what it looks like now. CDC escapes the problem entirely by reading the log the database was already writing. The idea is elegant; the two places it goes wrong are the initial handover and the assumption that a stream arrives in order.

    THE CORE IDEA

    The log was always there

    Every durable database already maintains an ordered record of every change it has made. CDC is the observation that this is exactly what you wanted.

    A database cannot acknowledge a write until that write survives a crash. Writing the row to its final location on disk is too slow to do synchronously, so instead it appends a compact description of the change to a sequential file and forces that to disk. Only then does it acknowledge. The row itself is updated in memory and written out later, lazily.

    That file is the write-ahead log — the WAL in Postgres, the binary log in MySQL, the transaction log in SQL Server, the redo log in Oracle. Three of its properties are what make CDC work:

    It is complete
    Every committed change is in it, including deletes. There is no such thing as a change the database made without logging it, because a change that is not logged cannot be acknowledged.
    It is in commit order
    Entries appear in the order transactions committed, not the order statements ran. This is the precise thing the timestamp query in chapter 4 could not observe, and it is why late-committing transactions cannot slip past a log reader.
    It shows intent, not just outcome
    The log distinguishes an insert from an update from a delete, and typically carries both the old and new versions of the row. Querying state can only ever show you the outcome.
    Why this reframes chapter 4's problem

    Timestamp-based extraction asks "which rows look like they changed?" and has to infer the answer from mutable state. CDC asks "what changed?" and reads the answer from a record the database keeps for its own reasons. The first question is unanswerable in general; the second is a file read. Every guarantee in this chapter descends from that difference.

    The mechanism is not new or exotic. This is the same log the database uses for crash recovery and for streaming replication to a replica. CDC tools connect as if they were a replica, which is why they are usually low-impact on the source: the database was already producing this data for somebody.

    THE OPTIONS

    Four ways to capture change

    Log-based is the right answer at scale, but the other three exist for reasons and two of them are sometimes correct.

    Capture mechanisms compared on the properties that matter
    MechanismHowDeletesLoad on sourceNeeds source changeLatency
    Query-based Poll on updated_at No A query per poll Needs the column maintained One poll interval
    Trigger-based Database triggers write to an audit table Yes Adds work to every write Yes, invasive One poll interval
    Log-based Read the WAL as a replica Yes, explicitly Minimal Config only Sub-second
    Application events The app publishes a domain event Yes, if modelled None on the database Yes, significant Sub-second

    Two of these deserve a fairer hearing than they usually get.

    Trigger-based capture is widely dismissed as legacy, and it is genuinely the worst option on performance — it puts synchronous extra work inside every transaction, so a write-heavy table pays for it forever. But it works on databases where you cannot get logical log access at all, which includes plenty of managed and older systems, and it captures deletes correctly. If the alternative is query-based polling on a table where deletes matter, triggers are the better wrong answer.

    Application events are, in an important sense, the best option and not a form of CDC at all. Instead of inferring meaning from row changes, the application publishes what actually happened: OrderCancelled rather than orders.status changed from 2 to 5. CDC gives you the database's internal representation, which is a private implementation detail of another team's service — every schema change is your problem, and you have to reverse-engineer business meaning from column mutations. Domain events invert both. The catch is that they require the owning team to build and maintain them, which is an organisational commitment rather than a configuration change.

    The pragmatic sequence

    CDC is frequently the right first move precisely because it needs nothing from the source team, and it buys you a working pipeline while you make the longer argument for domain events on the interfaces that matter most. Treating CDC as permanent architecture for a service you do not own is how you end up coupled to somebody else's column names indefinitely.

    MECHANICS

    How log-based capture actually works

    Four concepts, and one of them will page you at 3am if you do not understand it.

    Take Postgres as the worked example; MySQL and the others differ in naming more than in shape.

    Logical decoding
    The raw WAL is physical — it describes byte changes to disk pages, which is useless to a consumer. Logical decoding is a plugin layer that translates those page changes back into row-level operations with column names and values. In Postgres this is pgoutput or wal2json; MySQL's binlog in ROW format is already close to logical.
    Replication slot
    A named, server-side bookmark recording how far a particular consumer has read. It is what makes the stream resumable: disconnect for an hour, reconnect, and you continue from where you stopped rather than losing the interval.
    LSN, the log sequence number
    A monotonically increasing position in the log. It is the only genuinely reliable ordering you have — more reliable than any timestamp, because it is assigned by the log rather than by a clock. Almost every correctness technique later in this chapter uses it.
    Publication
    Which tables the stream includes. Worth being deliberate about: capturing every table because it was easier is how you end up owning a dependency on every table.
    The replication slot is a disk-space bomb

    A slot guarantees the server retains WAL until the consumer has confirmed reading it. That guarantee has no expiry by default. If your connector crashes on a Friday and nobody notices, the primary retains every byte of WAL over the weekend until the disk fills, at which point the database stops accepting writes and you have taken down the application you were carefully reading from a replica to avoid disturbing.

    This is the single most common CDC production incident. Mitigate on both sides: monitor slot lag as a first-class alert, and set max_slot_wal_keep_size (Postgres 13 and later) so the server drops the slot rather than the database. Dropping a slot means a re-snapshot, which is painful; a full primary is worse.

    One consequence worth stating plainly: logical decoding only emits committed transactions, and it emits them at commit time, in commit order. A transaction open for ten minutes produces nothing for ten minutes and then appears atomically. This is the correct behaviour and it means CDC latency has a floor set by your longest transaction, not by the connector.

    THE FIRST HARD PART

    The snapshot handover

    The stream only tells you what changed since it started. You need the state before that, and joining the two is where the bugs are.

    The log has finite retention, so it does not contain the row inserted three years ago that has never been touched since. Every CDC deployment therefore has two phases: an initial snapshot of current state, and the ongoing stream. The interesting question is what happens to writes that occur during the snapshot, which for a large table can take hours.

    The obvious approach — snapshot the table, then start streaming from the moment the snapshot finished — is wrong, and the model below shows how wrong along with something less obvious about why it is so hard to detect.

    Four handover strategies against ground truth simulated writes during a snapshot, reconstructed state compared row by row
    1 · SNAP THEN STREAM0rows wrong
    2 · MARK LSN FIRST0rows wrong
    3 · LOCKED SNAPSHOT0rows wrong
    4 · CHUNKED SNAPSHOT0rows wrong
    CORRUPTED AT HANDOVER0before self-repair

    The four strategies

    1. Snapshot, then stream from the end. Rows read early in the snapshot and updated later in it fall into a blind gap: too late for the snapshot, too early for the stream. Broken.
    2. Note the log position first, then snapshot, then replay from that position. Correct. You deliberately re-apply changes already reflected in the snapshot, which is harmless provided the apply is idempotent — an absolute "set this row to these values" is fine, an increment is not.
    3. Lock the table for the snapshot. Correct and simple, and it blocks writes for the whole duration. Fine for a small table at 4am, unacceptable for a large one.
    4. Chunked snapshot interleaved with the stream. Read the table in key ranges, tracking a low watermark per chunk, and let stream events for already-snapshotted ranges apply normally. Correct with no lock. This is Debezium's incremental snapshot, following the DBLog design, and it is what you want for anything large.
    The finding that makes this bug hard to catch

    Set the write volume to a hot table and watch the two right-hand tiles diverge. At 10,000 writes, roughly 184 of 200 rows are corrupted at handover — and essentially none are still wrong at the end, because a later write to the same row overwrites the stale value with a correct one.

    The corruption is real, and busy rows repair themselves. So the surviving errors concentrate entirely in cold rows: reference data, dormant accounts, historical records that nobody updates. Those are frequently the rows whose correctness matters most, and they are the last place anyone looks. Row counts reconcile, spot checks on active records pass, and a handful of rows are permanently wrong with no signal at all.

    Notice also that raising the chunk count reduces the buffered-and-superseded work without ever compromising correctness — that is the whole argument for chunking, and the reason chunk size is a tuning parameter rather than a correctness one.

    WHAT ARRIVES

    The shape of a change event

    A CDC event carries more than the new row, and the extra fields are what make correct application possible.

    event.json
    {
  "op": "u",
  "before": { "id": 42, "status": "pending", "total": 1900 },
  "after":  { "id": 42, "status": "paid",    "total": 1900 },
  "source": {
    "table": "orders",
    "lsn": 24019576,
    "txId": 998812,
    "ts_ms": 1717243310221,
    "snapshot": "false"
  },
  "ts_ms": 1717243310318
}
    op
    c create, u update, d delete, r read (a row from the initial snapshot rather than a live change). The r distinction matters: snapshot reads are not events that happened at that moment.
    before and after
    The row either side of the change. before requires the source to log full row images — Postgres needs REPLICA IDENTITY FULL, MySQL needs binlog_row_image=FULL. Without it you get only the primary key on a delete, which is enough to apply but not enough to audit what was lost.
    lsn and txId
    Position and transaction. The LSN is your ordering key and your deduplication key. The transaction id lets you group changes that committed together, which matters if a consumer needs transactional consistency across tables rather than per-row correctness.
    Two timestamps
    source.ts_ms is when the database committed it; the outer ts_ms is when the connector processed it. The difference is your capture lag, and it is worth monitoring directly rather than inferring.

    Tombstones, and why there are two delete messages

    A delete produces an event with op: "d", an after of null, and the old row in before. Connectors then usually emit a second message for the same key with a null value entirely — a tombstone.

    The reason is log compaction. On a compacted Kafka topic the broker retains only the most recent message per key, so the topic converges to a snapshot of current state. A null value is the signal that permits the broker to eventually remove the key altogether. Without a tombstone, a deleted row's last known state is retained forever in the compacted topic.

    Two consumer bugs that come from this

    First: a consumer that deserialises without null-checking the value crashes on every tombstone, so deletes take down the pipeline while inserts and updates work perfectly. Second, and worse: a consumer that treats a tombstone as "no change" and skips it will apply the op: "d" event correctly but, on a compacted topic replayed after retention has removed the delete event, resurrect the row. Handle both messages explicitly and test deletion paths — deletes are the least-exercised branch in most consumers.

    THE SECOND HARD PART

    Applying the stream

    The stream is correct. Whether your copy ends up correct depends on three properties of how you apply it.

    Two facts about delivery are true of essentially every message system and are covered properly in chapter 13. Delivery is at-least-once, so duplicates happen whenever a consumer crashes between processing and committing its offset. And ordering is guaranteed only within a partition, so if two changes to the same row land in different partitions they can be applied in either order.

    That second one is a configuration decision people make casually. Partition by primary key and all changes to a row are ordered relative to each other. Partition round-robin for even load and they are not.

    Applying a change stream to a target table partitioning, duplicates and delete handling against ground truth
    EVENTS DELIVERED0including duplicates
    OUT OF ORDER0per-key inversions
    ROWS WRONG0against source
    RESURRECTED0deleted rows still present

    The demo isolates three independent failure modes, and the combination that is actually safe is narrow.

    1. Duplicates are harmless if the apply is idempotent. An absolute upsert applied twice gives the same result. Turn off the LSN guard while partitioning by key and duplicates still cost nothing.
    2. Reordering is not fixed by idempotency. Partition round-robin and an older change can arrive after a newer one, overwriting good data with stale data. Because the apply is idempotent, nothing errors — the row is simply wrong.
    3. The LSN guard fixes reordering. Store the LSN alongside each row and ignore any event whose LSN is not greater. This makes the apply order-insensitive as well as idempotent, which is the property you actually want. It costs one column.
    4. Skipping deletes resurrects rows. Predictably, but note that nothing else degrades — every present row is correct, the table just contains rows that no longer exist upstream. Aggregates over it are wrong in a way no row-level check detects.
    The rule worth memorising

    Make the apply idempotent and order-insensitive, then delivery guarantees stop mattering. An upsert keyed on the primary key, guarded by a stored LSN, handling tombstones explicitly, is correct under duplicates, reordering and replays alike. Once you have that, a full stream replay from the beginning of retention is a safe operation rather than a frightening one — and being able to replay safely is what makes CDC operable.

    RUNNING IT

    Operating CDC

    Four things that will happen, in roughly the order they will happen to you.

    Slot lag grows and nobody notices
    Covered above and worth repeating because it is the incident. Alert on replication slot lag in bytes, with a threshold well below your WAL disk headroom, and treat it as a page rather than a ticket.
    The source changes its schema
    An ALTER TABLE appears in the stream as a schema change event. Your consumer now needs a policy: fail closed, or evolve. This is exactly the problem chapter 6 solves with a registry and compatibility rules, and CDC is the strongest argument for having one, because the change arrives with no warning at all.
    Someone runs a bulk update
    A migration touching ten million rows produces ten million change events in a few seconds. Your connector is fine; your downstream consumer, your topic retention and your warehouse merge costs may not be. Ask the owning team to tell you before large migrations, and size the pipeline for the burst rather than the average.
    You need to re-snapshot
    Because a slot was dropped, a table was added to the publication, or a consumer bug corrupted the target. This should be a routine, documented operation rather than a crisis, which means the incremental snapshot from the demo needs to be something you have actually run before you need it.

    A closing note on what CDC does and does not give you. Per-row, you get every change in commit order — that is solid. Cross-table transactional consistency is a different and harder property. If an order and its line items are written in one transaction, the events arrive with the same txId but may be spread across partitions and applied at different moments, so a consumer reading the target mid-apply can see the order without its items. If you need transactional consistency downstream you must buffer by transaction id and apply atomically, which most pipelines do not do and most consumers do not realise.

    Recap

    What to take from this chapter

    1. CDC works by reading a log the database already keeps. It is complete, in commit order, and distinguishes inserts, updates and deletes — the three things querying state cannot give you.
    2. Log-based capture is low-impact because it impersonates a replica. The database was already producing this stream for somebody else.
    3. Domain events published by the application are better than CDC, because CDC couples you to another team's private schema. CDC is the right first move precisely because it needs nothing from them.
    4. The replication slot will fill your primary's disk. A stalled connector makes the server retain WAL indefinitely. Alert on slot lag; set a retention cap so the server sacrifices the slot rather than the database.
    5. Snapshot-then-stream is broken. Rows read early and updated during the snapshot fall into a blind gap. Correct options: mark the LSN first and replay, lock the table, or take a chunked incremental snapshot.
    6. Handover corruption is masked by write volume. On a hot table almost every corrupted row is repaired by a later write, so the surviving errors sit entirely in cold reference rows where nobody checks. Reconciliation looks fine.
    7. A delete emits two messages. The op: "d" event and a null-valued tombstone for log compaction. Consumers that ignore either one crash on deletes or resurrect rows.
    8. Partition by primary key. Ordering holds only within a partition; round-robin partitioning lets a stale change overwrite a newer one silently.
    9. Make the apply idempotent and order-insensitive. Upsert on the key, guarded by a stored LSN, tombstones handled. Then duplicates, reordering and full replays are all safe.
    10. Per-row ordering is guaranteed; cross-table transactional consistency is not. Same transaction, different partitions, different apply moments.

    If you run CDC, check whether your target table stores the source LSN. If not, your apply is order-dependent and you are relying on partitioning you may not have verified.
