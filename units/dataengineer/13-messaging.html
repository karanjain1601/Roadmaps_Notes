CHAPTER 13

Messaging and streaming logs

Two things get called message brokers and they are structurally different: a queue hands work out and forgets it, a log records events and remembers them. Confusing the two is the source of most surprise in this area, along with a persistent misunderstanding of what exactly-once delivery can possibly mean.

    THE DISTINCTION

    Queues and logs

    Both move messages between systems. What happens after a message is read is completely different, and it determines what each is good for.

    A queue distributes work

    A message is delivered to one consumer, acknowledged, and deleted. The queue is a work list: its natural length is zero, and a growing queue means you are falling behind. Consumers are interchangeable workers and messages need not be ordered relative to each other.

    RabbitMQ, SQS, Celery, most job systems.

    A log records history

    A message is appended to an ordered, immutable sequence and retained for a configured period. Reading does not consume it. Each consumer tracks its own position, so several independent consumers read the same messages, and a consumer can rewind.

    Kafka, Kinesis, Pulsar, and the write-ahead logs of chapter 5.

    Why data engineering mostly wants a log

    The replay row decides it. A pipeline whose input is deleted on read has no recovery path when the transformation turns out to be wrong — which is chapter 12's argument for a landing zone, and a log is a landing zone with an ordering guarantee. Adding a new consumer that can read history is the other decisive property: with a queue, a new use case starts from today.

    Queues remain the right answer for actual work distribution: send this email, resize this image, charge this card. If the message is a task rather than a fact, you want a queue.

    THE MODEL

    Partitions, offsets and consumer groups

    Four concepts. Everything else about operating a log follows from how they interact.

    Topic and partition
    A topic is a named stream, divided into partitions. A partition is the unit of ordering and the unit of parallelism, and those two facts being the same fact is the central design tension of the whole system. Each partition is an append-only sequence on disk.
    Offset
    A message's position within its partition. Monotonic, per-partition, and assigned by the broker — the same role the LSN played in chapter 5. A consumer's progress is entirely described by one offset per partition.
    Consumer group
    A set of consumers sharing the work of a topic. The coordinator assigns each partition to exactly one member. Different groups are independent, each with its own offsets, which is how one topic feeds a warehouse loader, a fraud model and a search indexer without them interfering.
    Retention
    How long messages are kept: by time, by size, or by compaction, which retains only the most recent message per key. Compaction is what makes a topic converge to a snapshot of current state, and it is why the tombstones of chapter 5 exist.

    The consequence that catches people is stated plainly: a partition goes to exactly one consumer in a group. So a group can never have more useful consumers than there are partitions, and ordering only holds within a partition. Both halves of that are the subject of the next section.

    WHERE THROUGHPUT GOES

    Keys, partitions and skew

    A message's key decides its partition, which decides its ordering and which consumer handles it. Choose the key badly and no amount of scaling helps.

    A producer with a key hashes it and takes the modulus of the partition count, so all messages with the same key land in the same partition and are therefore ordered relative to each other. That is exactly the property chapter 5 required for a CDC stream: partition by primary key and a row's changes stay in order.

    The cost is that load follows the key distribution rather than being balanced by the system. The demo hashes real keys into partitions and works out where the throughput ceiling actually sits.

    Four results, and the third is the one worth remembering.

    1. Consumers beyond the partition count do nothing. Twelve partitions and twenty-four consumers leaves twelve sitting idle, holding a group membership and consuming no messages. Scaling a consumer deployment past the partition count is a no-op that looks like capacity.
    2. More partitions balance worse for a fixed number of keys. With a thousand uniform keys the skew is 1.06 at four partitions, 1.19 at twelve, 1.60 at sixty-four and 2.56 at two hundred and fifty-six — because fewer keys per partition means less averaging. Over-partitioning is not free.
    3. Partition count cannot fix key skew. Set the keys to eight and the skew high, so one key carries about 76% of the traffic. The busiest partition holds 76,486 messages at four partitions and 76,066 at every count from twelve upward — the hot key itself is the floor. The hot key is a hard floor, because a key cannot be split across partitions without giving up the ordering that was the reason for keying in the first place.
    4. The ceiling is set by the busiest consumer, not the average. Throughput is total work divided by the slowest member's share, so a single hot partition caps the whole group however much you add elsewhere.
    What to do about a hot key

    There is no configuration fix; the options all involve giving something up. Salt the key — append a random suffix from a small range — which spreads the load and destroys per-key ordering. Split by a compound key if a finer grain still satisfies your ordering requirement. Handle the hot key separately with a dedicated consumer and a different code path. Or accept it and size that one partition's consumer for the peak.

    Deciding requires knowing what the ordering guarantee is actually for. If nothing downstream depends on per-key order, you should not have been keying at all.

    One operational note that follows from the modulus. Changing the partition count re-maps every key, because hash(key) % 12 and hash(key) % 24 put the same key in different places. Messages already written stay where they are, so for a period the same key exists in two partitions with no ordering between them. Partition counts can be increased and are painful to change; choose with headroom.

    THE CLAIMS

    Delivery semantics, precisely

    Three phrases, one of which is routinely oversold. The difference between them is entirely about when you record your progress.

    A consumer does two things: process a message, and record that it has done so by committing an offset. The order of those two operations is the whole subject.

    At-most-once
    Commit the offset first, then process. A crash between the two means the message is never processed and never redelivered, because the offset has already moved past it. Loses messages, never duplicates.
    At-least-once
    Process first, then commit. A crash between the two means the message is redelivered and processed again. Duplicates messages, never loses them. The sane default, and what essentially every system gives you unless you work at it.
    Exactly-once
    Neither loss nor duplication. Achievable, with conditions that matter, and discussed below.

    The demo makes the trade concrete and then makes the escape visible. At-most-once loses 160 of 2,000 messages and duplicates none. At-least-once duplicates 240 and loses none. A deduplication store covering 200 message ids gives neither — but a window of 20 ids against batches of 100 leaks all 240 duplicates straight through, because the redelivery span is wider than the memory.

    What exactly-once actually means

    Two genuinely different things are sold under the phrase.

    Exactly-once processing within one system. Kafka transactions let a consumer read, process and write — to Kafka — atomically, committing the output and the offset together. This is real and it works. Its boundary is the system: as soon as your side effect is a database write, an HTTP call or an email, the transaction cannot cover it.

    Effectively-once end to end, which is at-least-once delivery plus an idempotent consumer. This is the only thing available when the side effect leaves the broker, and it is what the dedup column in the demo models. It is also exactly the LSN-guarded upsert from chapter 5 and the atomic partition write from chapter 12 — the same answer arriving for the third time.

    So the practical instruction is the one this unit keeps repeating: stop trying to make delivery exact and make the effect idempotent. A dedup store then becomes an optimisation rather than a correctness requirement, which matters because a dedup store is a stateful component with a retention window that will eventually be too short.

    The unfashionable answer that is often right

    Under a few thousand messages a second, a table in the database you already run is a perfectly good queue, and it has one property no broker can offer: the enqueue is in the same transaction as the data change that caused it. That eliminates the dual-write problem entirely — the situation where you commit a row and then fail to publish the event, leaving the two permanently disagreeing. Reaching for Kafka to avoid a database table frequently introduces that problem in exchange for scale you do not need.

    The pattern that solves it properly when you do need a broker is the transactional outbox: write the event to a table in the same transaction as the data, and have a separate process ship the table to the broker. Which is CDC, applied to your own outbox.

    RUNNING IT

    Four things you will have to manage

    Consumer lag
    The gap between the latest offset and the consumer's committed offset, in messages and in time. The single most important metric on a log, and it should be alerted on in seconds behind rather than message count, because message count is meaningless across a volume change. Lag rising steadily means throughput is insufficient; lag sawtoothing means a batch or rebalance pattern.
    Retention against replay need
    Retention is your recovery window. Seven days of retention means you can rebuild a consumer's state from up to seven days ago and no further, so a bug found on day eight is unrecoverable from the log. Set retention from the recovery you want, not from disk convenience — and note that compacted topics keep the latest value per key indefinitely, which is a different guarantee.
    Rebalancing
    When a consumer joins, leaves or is presumed dead, partitions are reassigned and consumption pauses. A consumer whose processing occasionally exceeds the poll timeout is declared dead, triggering a rebalance, which slows everyone, which causes more timeouts. Cooperative and static assignment exist specifically to limit this; if you see repeated rebalances, look at processing time per poll before anything else.
    Poison messages
    A message that always fails will be retried forever and block its partition, since offsets advance in order. A dead-letter topic with a bounded retry count is not optional. Attach the original topic, partition, offset and the error, or triage is guesswork.

    Backpressure deserves a note because logs and queues handle it oppositely. A queue applies backpressure by growing until the producer notices or is throttled. A log does not push back at all — it accepts writes at broker speed and lets the consumer fall behind, which is a feature: a traffic spike becomes lag rather than a rejected write. The failure mode is that lag exceeds retention, at which point the consumer's next read fails because the data it wanted has been deleted, and it has silently skipped a gap. Alert on lag approaching retention, not just on lag.

    Recap

    What to take from this chapter

    1. A queue distributes work and deletes it; a log records history and retains it. Data engineering usually wants a log, because replay and independent consumers are the properties that matter.
    2. A partition is both the unit of ordering and the unit of parallelism, and that coincidence is the source of most difficulty.
    3. Consumers beyond the partition count are idle. Twenty-four consumers on twelve partitions leaves twelve doing nothing.
    4. More partitions balance worse for a fixed key count — skew 1.06 at four partitions rising to 2.56 at two hundred and fifty-six, with a thousand uniform keys.
    5. Partition count cannot fix key skew. With one key holding 76% of traffic, the busiest partition holds 76,486 messages at four partitions and 76,066 at every count from twelve to 1,024. The hot key is a hard floor.
    6. Throughput is set by the busiest consumer, so one hot partition caps the whole group.
    7. Changing the partition count re-maps every key, so the same key temporarily lives in two partitions with no ordering between them.
    8. At-most-once loses and never duplicates; at-least-once duplicates and never loses. Measured: 160 lost against 240 duplicated on the same 2,000 messages.
    9. A dedup store only works within its window. Twenty ids against batches of a hundred leaked every one of the 240 duplicates.
    10. Exactly-once is two claims. Transactional processing within one system is real and bounded by that system; end to end you get at-least-once plus an idempotent consumer, which is the same answer as chapters 5 and 12.
    11. A database table is a legitimate queue at modest volume, and uniquely lets the enqueue share a transaction with the data change. Otherwise use a transactional outbox.
    12. Alert on lag in seconds, and on lag approaching retention. Exceeding retention means the consumer silently skips a gap.

    ONE THING TO TRY

    On your busiest topic, compare messages per partition rather than the total. If the ratio between the busiest and the mean is above about two, you have key skew and adding consumers will not help.
