CHAPTER 02

The lifecycle end to end

Every data platform ever built has the same five stages, whether or not anyone named them. Learning the stages is not the point — the point is that each one imposes a cost on the ones after it, and two of those costs, freshness and the price of being wrong, are set by decisions made long before anyone notices them.

    THE SPINE

    Five stages

    Generation, ingestion, storage, transformation, serving. The vocabulary is worth adopting because it gives you a shared name for where a problem lives.

    The framing below is the one popularised by Fundamentals of Data Engineering, and it has displaced the older ETL-centred description of the field for a good reason: ETL describes one implementation choice, whereas the lifecycle describes the problem independent of how you solve it.

    1. Generation
    Data comes into existence in a source system: a row is inserted, a user taps a button, a sensor reports, a third party updates a record in their own database. You do not control this stage and mostly cannot change it. Your only real lever is the contract you negotiate with whoever does. Chapter 4.
    2. Ingestion
    Getting data out of the source and into your platform. This is where most operational pain lives, because it is the boundary between a system you own and one you do not. The decisions here are batch against stream, push against pull, and full against incremental. Chapters 12 and 13.
    3. Storage
    Not a stage that happens once but a substrate the whole lifecycle sits on: data is stored on the way in, between transformations, and on the way out. The choices — object store or warehouse, what file format, partitioned by what — quietly determine the cost and speed of everything else. Chapters 7 to 11.
    4. Transformation
    Turning data that reflects how a source system happens to work into data that reflects how the business thinks. Joining, aggregating, deduplicating, conforming, applying the definition of revenue. This is where correctness is won or lost. Chapter 9 and 15.
    5. Serving
    Delivering the result to whoever needs it, in the shape they need: a BI tool, a model's feature store, an API, a file for a partner, a row pushed back into a CRM. Data that is never served has cost money and returned nothing. Chapters 17 and 18.
    The stages are not a project plan

    A common misreading is to build them in order: a year on ingestion and storage, then transformation, then finally serving. This reliably fails, because until something is served nobody can tell you whether what you ingested was the right thing. Build a thin path through all five stages for one real use case, then widen it. The lifecycle is a map of concerns, not a sequence of phases.

    A useful property of the framing: any incident can be located. "The number is wrong" is not actionable, but "the number is wrong because ingestion silently dropped rows with null timezones" names a stage, an owner and a class of fix. Most of the value of a shared vocabulary is speed of triage.

    WHAT RUNS UNDERNEATH

    The undercurrents

    Six concerns that are not stages because they apply to all of them at once. These are what separate a platform from a pile of scripts.

    Security

    Who can read what, encryption in transit and at rest, least privilege, and the fact that a copy of production data in a development environment is still production data. Chapter 23.

    Data management

    Governance, catalogues, lineage, quality definitions, ownership, retention. Unfashionable and the first thing regulators ask about. Chapter 21.

    DataOps

    Applying operational discipline to data: version control, CI, tests, monitoring, incident response, SLAs. Chapters 20 and 22.

    Data architecture

    The shape of the whole thing and how it is allowed to change. Mostly the discipline of keeping decisions reversible. Chapter 3.

    Orchestration

    Something has to decide what runs, in what order, after what, and what happens when a step fails. Absent an orchestrator you have written one badly in cron. Chapter 16.

    Software engineering

    Testing, packaging, modularity, review, dependency management. SQL and YAML are code and go rotten the same way when treated as configuration.

    These get skipped early for an understandable reason: none of them delivers a number to anybody this week. The consequence is equally predictable. A platform without orchestration works until two pipelines need ordering; without tests it works until a source changes; without lineage it works until someone asks which dashboards depend on a table you want to delete.

    The order these become urgent

    Roughly: orchestration first, because dependency chaos arrives almost immediately. Then software engineering practice, once more than one person edits the pipelines. Then DataOps, at the first incident nobody noticed for a week. Security and data management are usually forced by an external event — an audit, a customer contract, a breach — which is a bad way to be forced, since retrofitting access control across an existing platform is considerably more expensive than starting with it.

    THE FIRST COMPOUNDING COST

    Where latency accumulates

    End-to-end data age is not the slowest stage. It is the sum of every wait and every run along the path, and waits dominate.

    Ask how fresh a dashboard is and you will usually be told how often the last job runs. That answer is wrong in an interesting way, and the error is almost always an underestimate.

    Consider one record moving through a scheduled chain. It is created at some arbitrary moment — the source system does not consult your schedule. It then waits until the ingestion job next runs. In the worst case it just missed a run, so it waits a full interval; on average it waits half. Then the job takes some time to complete. Then the same thing happens at the next stage, and the next. Each scheduled hop contributes both a wait and a run:

    freshness.txt
    # worst case a record can be, arriving at the end of the chain
worst = sum(interval_i + duration_i for i in stages)

# average case, assuming arrival is uniform within each interval
average = sum(interval_i / 2 + duration_i for i in stages)

    The consequence is that four hourly stages produce data that is up to four hours and change old, not one hour old. Set the intervals below and watch which stage is actually responsible.

    Three lessons fall out of this model, and all three are things people get wrong in planning meetings.

    1. Waiting dominates running. With every stage hourly, the runs contribute half an hour in total and the waits contribute four. Optimising job runtime — the thing engineers enjoy — is attacking the small term. Shortening intervals attacks the large one.
    2. The chain is as stale as its slowest scheduler. Leave one stage at daily and every other stage can run every five minutes without materially improving the result. Try it: set marts to 24 hours and then make everything else continuous.
    3. Continuous stages contribute only their runtime. That is the real argument for streaming, and also its limit — a stream feeding a nightly mart is a nightly pipeline with extra operational complexity.
    Promising average freshness

    Teams quote the average because it sounds better, then get judged on the worst case, because the complaint always arrives on the bad day. Publish the worst case. If the worst case is unacceptable, the fix is a schedule change, not a rewording.

    THE SECOND COMPOUNDING COST

    What it costs to be wrong

    Every pipeline eventually produces bad output for a period of time. The bill for fixing it is set by a storage decision made months earlier.

    This is the scenario, and it is not hypothetical — it happens to everyone. A transformation has a bug. It was deployed two weeks ago. It has been quietly writing incorrect values since. Somebody notices. You fix the code in ten minutes.

    Now you have to fix the data, which means reprocessing every affected day. What that costs depends almost entirely on whether the table you are rewriting can be addressed by day, and whether the engine can read only the columns it needs.

    Unpartitioned, row-oriented
    One large table with no physical divisions, stored as CSV, JSON lines or uncompressed database pages. To correct fourteen days you must rewrite the whole object, because there is no way to replace part of it. You scan all history to fix two weeks of it.
    Date-partitioned, row-oriented
    Physically separate files or partitions per day. You replace fourteen of them and leave the rest untouched. This single decision is usually the difference between a routine fix and an incident.
    Date-partitioned, columnar
    As above, but stored in Parquet or ORC. Two further savings compound: columnar data compresses far better because a column holds one type with repeated values, and the reader can skip columns the job never mentions. Chapter 8 measures both properly.

    The gap between the first and last layout is routinely three or four orders of magnitude, and none of it comes from writing better code. It comes from two choices — partition by ingestion date, store columnar — that cost nothing at design time and are expensive to retrofit once a table has years of history in it.

    The question to ask at design time

    Not "how fast is this pipeline" but "if this has been wrong for a month, what does it cost me to fix?" A design where the answer is "a few minutes and a few pounds" is a fundamentally different thing to operate from one where the answer is "a weekend and a conversation about budget", even when both produce identical output on a good day.

    Two related properties matter as much as the layout and are covered later. A pipeline is idempotent if re-running it for the same day produces the same result rather than duplicating rows — without that, backfilling is unsafe at any cost. And a replayable pipeline retains its raw input, so you can recompute from source rather than from a derived table you no longer trust. Both are in chapter 12.

    THE SAME LIFECYCLE, THREE SIZES

    Three reference architectures

    All five stages, all six undercurrents, at wildly different levels of machinery. Each is correct at its scale and wrong at the others.

    The lifecycle instantiated at three scales
    StageSmall: one databaseMid: managed warehouseLarge: lakehouse and streams
    Generation One app database App databases, a dozen SaaS tools, event tracking Many services, event topics per domain, partner feeds
    Ingestion Read replica, queried directly Managed connectors plus log-based CDC Kafka as the ingestion backbone, connectors onto it
    Storage The replica itself Cloud warehouse, columnar internally Object storage with an open table format; warehouse for serving
    Transformation Scheduled SQL views SQL models under version control, tested SQL for batch, Spark or Flink for scale and streams
    Serving A BI tool on the replica BI on marts, a semantic layer, reverse ETL BI, feature store, low-latency APIs, data products
    Orchestration Cron, honestly labelled Airflow or Dagster Orchestrator plus event-driven and data-aware triggers
    People Nobody full time One to four Multiple teams plus a platform team
    Worst-case freshness Seconds, and it is hurting the app Hours Minutes on the streaming path, hours on the batch one

    Read the first column carefully before dismissing it. A company whose entire platform is a read replica, six scheduled views and a BI tool has all five stages and can be entirely well run. It will have a freshness problem and a metric-definition problem before it has a scale problem, and both are addressed with a warehouse and a transformation tool rather than a distributed compute engine.

    The migration that actually happens

    Almost nobody moves from column one to column three. They move to column two and stay there for years, which is the correct outcome — a managed warehouse with tested SQL models serves the large majority of companies indefinitely. Column three is driven by a specific forcing function: data volumes that a warehouse prices badly, genuine sub-minute latency requirements, or organisational scale that demands domain ownership. Absent one of those, it is cost without benefit.

    Recap

    What to take from this chapter

    1. Five stages: generation, ingestion, storage, transformation, serving. Their value is diagnostic — they let you say where a problem lives and who owns it.
    2. Six undercurrents run beneath all five. Security, data management, DataOps, architecture, orchestration and software engineering practice. Orchestration becomes urgent first; security and governance are usually forced by an external event, which is the expensive way to arrive at them.
    3. Build a thin slice through all five stages, not one stage at a time. Until data is served, nobody can confirm you ingested the right thing.
    4. Freshness is a sum, not a maximum. Every scheduled hop adds a wait plus a run, so four hourly stages give roughly four hours of staleness. Waits dominate runs, which means schedule intervals matter far more than job optimisation.
    5. One slow scheduler caps the whole chain. A streaming ingestion feeding a nightly mart is a nightly pipeline.
    6. Quote worst-case freshness, never average. You will be judged on the bad day.
    7. Reprocessing cost is decided by layout, not by code. Partitioning by date and storing columnar routinely separate a several-hour, expensive backfill from a several-second, negligible one.
    8. Ask the design-time question: if this has been wrong for a month, what does the fix cost? Two designs with identical happy-path output can be completely different things to operate.

    WHERE THIS GETS PRECISE

    The freshness model here assumes independent schedules. Chapter 16 covers what changes when the orchestrator triggers stages on completion rather than on a clock, which removes most of the waiting term.

    ONE THING TO TRY

    Take one dashboard you rely on and add up the intervals of every stage behind it. Compare that number to what its users believe. The gap is nearly always larger than anyone expects.
