CHAPTER 07

Storage foundations

One economic fact reorganised this entire field: storage on a remote object store became so cheap, so durable and so elastic that keeping compute and storage in the same box stopped making sense. Almost every architecture in the rest of this unit is a consequence of that, so it is worth understanding what object storage actually gives you and what it charges for.

    ORDERS OF MAGNITUDE

    The hierarchy, in numbers worth memorising

    Every storage decision is a trade between latency, throughput, durability and cost. The ratios between the levels are large enough that intuition is useless without the figures.

    Approximate figures for a 2020s server and cloud. Orders of magnitude matter, not the digits
    LevelLatencyThroughputCost per TB-monthSurvives
    CPU cache~1 nsTB/s—Nothing
    RAM~100 ns~50 GB/s~£3,000Nothing
    Local NVMe SSD~100 µs~3 GB/s~£100Process crash
    Network block store~1 ms~0.5 GB/s~£80Instance loss
    Object storage~50–200 msUnlimited in parallel~£20Datacentre loss
    Archive tierMinutes to hoursThrottled~£2Datacentre loss

    Three things in that table drive most of the rest of the unit.

    Object storage latency is terrible and its throughput is unlimited. A single read takes 50 to 200 milliseconds, which is a thousand times slower than local disk — so object storage is hopeless for one small random read and superb for a thousand concurrent large ones. The design consequence is everywhere in this unit: read big contiguous chunks in parallel, never small scattered ones. That single sentence explains file formats, partitioning strategy, and why the small-files problem in chapter 15 is so damaging.

    RAM is roughly 150 times the price of object storage and about 30 times the price of SSD. This is why the "just keep it in memory" instinct is expensive at scale, and equally why a machine with 512 GB of RAM can hold a dataset most people would reach for a cluster to process.

    The archive tier is ten times cheaper and comes with a latency of minutes. That is not a small inconvenience; it changes what the data can be used for, which is the subject of the second demo.

    THE THREE ABSTRACTIONS

    Block, file, object

    These are not three products. They are three different things you are allowed to say to a storage system, and the vocabulary determines what is possible.

    Block storage
    A flat array of fixed-size blocks, addressed by number. It has no idea what a file is. You get to overwrite block 4,182 in place, which is what a database needs to update a page. Attached to exactly one machine at a time. Examples: a disk, an EBS volume, a Persistent Disk.
    File storage
    Directories, filenames, byte ranges, permissions, and the ability to append to or seek within a file. Mountable by many machines at once, which is its point. Examples: NFS, EFS, HDFS. Convenient and, over a network, hard to scale — the directory tree is shared mutable state.
    Object storage
    A flat key-value store where the values are large blobs of bytes and the keys are strings. No directories — the slashes in events/2026/09/04/part-0001.parquet are just characters in the key, and the "folder" is a prefix rather than a thing. Objects are immutable: you replace one whole, you do not edit it. Examples: S3, GCS, Azure Blob.
    Immutability is the constraint that buys everything else

    Because an object cannot be partially modified, the system never has to coordinate concurrent writers to a byte range, never needs a distributed lock manager, and can replicate freely without worrying about a replica being mid-edit. That is what makes object storage scale to exabytes at that price with those durability guarantees.

    It is also the source of every awkward thing about working with it. You cannot append a row to a Parquet file. You cannot update one record. Deleting "a directory" means listing and deleting every key with that prefix. The table formats in chapter 11 exist entirely to reconstruct mutability on top of an immutable substrate.

    One practical trap that follows from "directories are not real": listing a prefix with millions of keys is a paginated API call returning a thousand at a time, not a directory read. A job that begins by listing a large prefix can spend minutes doing so before reading a byte, which is why mature table formats keep their own file manifests rather than asking the store what exists.

    THE ECONOMIC SHIFT

    Why this restructured the field

    Separating storage from compute is the single most consequential architectural change in data engineering, and it is a consequence of pricing rather than of cleverness.

    The older model — Hadoop, and every shared-nothing database — put data on the disks of the machines that processed it. This was correct when networks were slow relative to disks: you moved the computation to the data because moving the data was prohibitive. It produced a hard coupling. Needing more storage meant buying more compute, and needing more compute meant rebalancing data across new nodes.

    Two things changed. Datacentre networks got fast enough that reading from a remote store at 10 Gbit/s stopped being the bottleneck, and object storage got cheap enough that keeping one authoritative copy there beat replicating it across compute nodes.

    What separation buys

    • Scale storage and compute independently, which is what you actually want since they grow at different rates.
    • Compute becomes disposable: start a cluster, run a job, destroy it. You pay for the minutes.
    • Many engines over one copy of the data — SQL, Spark, Python, all reading the same files.
    • No rebalancing. Adding capacity is not a data-movement project.

    What it costs

    • Every read crosses a network with 50–200 ms of latency, so small reads are punished severely.
    • You must think about file layout yourself, because the engine no longer owns the storage.
    • Request charges become a real line item, sometimes the dominant one.
    • Transactions, updates and deletes have to be rebuilt in a layer above.

    Note that this is a genuine trade rather than a free win, and the industry re-learned the cost side the hard way. The first generation of data lakes put files in object storage and discovered they had lost transactions, schema enforcement and efficient updates — producing the "data swamp" of the mid-2010s. The lakehouse table formats were the correction, and they are the subject of chapter 11.

    THE HEADLINE NUMBER

    Durability, and why erasure coding wins

    Eleven nines is a real claim with real arithmetic behind it. Working through it explains why nobody serious uses three-way replication any more.

    First, two words people use interchangeably and should not:

    Durability
    The probability that data you stored still exists. Losing it is permanent and unrecoverable. Quoted in nines: eleven nines means a one in a hundred billion annual chance of losing a given object.
    Availability
    The probability that you can reach it right now. An outage is temporary and annoying. Object stores typically offer four nines of availability alongside eleven of durability — roughly an hour of unreachability a year, and effectively never losing anything.

    The mechanism is redundancy, and there are two ways to buy it. Replication keeps n whole copies. Erasure coding splits an object into k data shards, computes m parity shards, and can reconstruct the original from any k of the k+m — the same idea as RAID, generalised.

    The model below uses the standard first-order approximation: one disk fails, and loss requires enough further failures to land inside the repair window before the system has rebuilt.

    The result is the one that matters: erasure coding is simultaneously more durable and cheaper than replication. At a 2% failure rate and a six-hour repair, three-way replication gives about eleven nines for 3.00× the raw bytes, while 10+4 erasure coding gives about seventeen nines for 1.40×. That is six extra nines at less than half the storage cost, which is why every large object store uses erasure coding internally and why the "just keep three copies" heuristic is obsolete.

    What the repair window does, and what the arithmetic ignores

    Move the repair slider: 6 hours to 72 hours costs 10+4 coding several nines, because a longer rebuild leaves a wider period of reduced redundancy. This is why a store's rebuild speed is as important as its coding scheme, and why a nearly-full system is dangerous — there is nowhere to rebuild into.

    The model also assumes independent failures, and the real risks are correlated: a firmware bug across a whole batch of drives, a datacentre losing power, a botched software deploy, or an engineer running a delete with the wrong prefix. Eleven nines describes hardware failure only. It offers no protection whatsoever against the most common cause of real data loss, which is somebody deleting it on purpose. That is what versioning, object locks and a separate backup account are for — see chapter 22.

    A HISTORICAL TRAP

    Consistency, and one piece of stale advice

    A large body of writing about data lakes is built on a limitation that no longer exists, and following it now costs you real complexity.

    Until December 2020, S3 offered only eventual consistency for some operations: you could write an object, immediately list its prefix, and not see it. Whole layers of software existed to work around this — S3Guard kept a consistent file index in DynamoDB, and much advice about "commit protocols" for Spark descends from it.

    S3 now provides strong read-after-write consistency for PUTs, DELETEs and LISTs, at no cost and with no configuration. GCS and Azure Blob offer the equivalent. So the workaround layers are unnecessary on new systems, and advice recommending them should be read with its date in mind.

    What remains true

    Strong consistency for a single object is not transactional consistency across many. Writing fifty Parquet files and then a manifest is still not atomic: a reader can arrive between file forty and the manifest and see a partial dataset. Every object store has this property, and closing that gap is precisely what the table formats in chapter 11 do, by making the final act of a write a single atomic pointer swap.

    Two other properties worth knowing. Versioning retains previous versions of a key, converting an overwrite or delete into something recoverable — the single most valuable protective setting on a bucket, and it costs storage for the retained versions. And conditional writes (write only if the key does not exist, or only if the ETag matches) give you enough primitive to build a compare-and-swap, which is how modern table formats commit without an external lock service.

    THE BILL

    The cost model, and the number people forget

    Everyone compares price per terabyte. On a real workload it is frequently not the largest line, and the thing that decides is average object size.

    An object store charges on four axes: bytes stored per month, requests made, bytes transferred out of the cloud, and for cold tiers, bytes retrieved. Only the first is what people compare, and requests are charged per object regardless of size — so the same volume of data costs wildly different amounts depending on how it is chopped up.

    Three conclusions, each of which has cost somebody a great deal of money.

    1. Small files are the expensive failure. Ten terabytes in 128 MB objects costs a few hundred pounds a month, essentially all storage. The same ten terabytes in 4 KB objects costs tens of thousands, essentially all requests. The stored bytes are identical. This is the strongest argument for the compaction jobs in chapter 16, and it is a cost argument before it is a performance one.
    2. Archive tiers are cheap to hold and expensive to read. Move the tier to archive with several reads a month and watch retrieval overtake the storage saving. Archive is for data you are keeping because you must, not data you query occasionally.
    3. Egress dominates everything once it appears. At roughly four times the monthly storage price per gigabyte moved, sending data out of the cloud is the most expensive thing on the bill, and it is the mechanism behind the data lock-in priced in chapter 3.

    Recap

    What to take from this chapter

    1. Object storage has terrible latency and unlimited parallel throughput. Read big contiguous chunks concurrently; never small scattered ones. Most of this unit's file-layout advice follows from that one sentence.
    2. Objects are immutable, and that constraint buys the scale. No byte-range coordination, no distributed locks, free replication — at the cost of not being able to append or update anything.
    3. Directories are not real. A prefix is a string match, and listing a large one is a slow paginated API call, which is why table formats keep their own manifests.
    4. Separating storage from compute followed from pricing, not cleverness, and it is a trade: independent scaling and disposable clusters, paid for in latency, request charges and having to rebuild transactions above.
    5. Erasure coding beats replication on both axes. Roughly seventeen nines at 1.40× overhead for 10+4, against eleven nines at 3.00× for triple replication.
    6. The repair window is a first-class durability parameter. Six hours to seventy-two costs several nines, which is why rebuild speed and spare capacity matter.
    7. Nines describe uncorrelated hardware failure only. They say nothing about a bad deploy or a mistaken delete, which is what versioning and object locks are for.
    8. S3 has been strongly consistent since 2020. Advice about consistency workarounds predates that. Cross-object atomicity is still absent, which is what table formats provide.
    9. Average object size can dominate your bill. The same ten terabytes costs a few hundred pounds in 128 MB objects and tens of thousands in 4 KB objects, because requests are priced per object.
    10. Egress is the most expensive line on the bill, at several times the monthly storage price per gigabyte moved.
