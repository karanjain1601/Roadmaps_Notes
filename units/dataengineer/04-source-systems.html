CHAPTER 04

Source systems

This is the stage you do not control, and the one that will hurt you most. The central result of this chapter is uncomfortable: the incremental extraction pattern that almost every team writes first — select rows where updated_at is greater than last time — loses data silently, and no amount of care in the code that follows can recover it.

    WHAT YOU WILL MEET

    Five shapes of source

    Almost everything you ingest is one of these, and the shape determines which extraction problems you inherit.

    Transactional databases
    Postgres, MySQL, SQL Server, Oracle and their managed equivalents behind an application. Rich, authoritative, current — and mutable, which is the source of every difficulty in this chapter. A row can change or vanish with no record that it ever looked different.
    APIs
    Third-party SaaS, internal services, partner endpoints. You get whatever the vendor decided to expose, paginated, rate-limited, and occasionally changed without notice. The second demo shows why the rate limit rather than the data volume usually decides whether an ingestion is even feasible.
    Event streams and logs
    Clickstream, application logs, message topics, IoT telemetry. Structurally the nicest source you will ever get: append-only, immutable, ordered within a partition. Nothing is ever updated, so there is nothing to miss. High volume and frequently low quality, but the extraction problem is close to trivial.
    Files
    CSVs on SFTP, exports dropped in a bucket, spreadsheets emailed monthly. Universally derided and universally present. The characteristic problems are schema drift with no announcement, partial or duplicated deliveries, and encoding.
    Third-party and public data
    Data vendors, open government data, scraped sources. You control neither the schema, the schedule, the quality nor the availability, and the terms of use are a genuine constraint rather than a formality.
    The distinction that matters more than the list

    Sources divide into mutable state and immutable events. A database table is state: it tells you what is true now and forgets what was true before. An event log is history: it tells you what happened and never changes. Every hard extraction problem in this chapter comes from state, and every one of them disappears if the source emits events instead. That is the deep reason change data capture works — it converts state back into the event log the database was keeping anyway.

    READ THE SMALL PRINT

    What each source actually promises

    Most ingestion bugs are a mismatch between what you assumed a source guaranteed and what it does.

    Two rows in that table cause a disproportionate share of real incidents.

    "Only if the app maintains it". An updated_at column is application convention, not a database guarantee. It is set correctly by the ORM on normal writes, and then somebody runs a bulk correction with raw SQL, or a migration touches a million rows, or a trigger updates a denormalised counter without touching the timestamp. Every one of those rows is now invisible to timestamp-based extraction, permanently. Ask whether the column is maintained by a database trigger rather than by application code; the answer changes how much you can trust it.

    "By commit, not by timestamp". This is the subtle one, and it is the subject of the next section. The order in which rows become visible to a reader is not the order of their timestamps, because a transaction that started earlier can commit later. Every timestamp-based incremental extraction assumes those two orders agree, and they do not.

    THE CENTRAL RESULT

    Why incremental extraction loses rows

    Not an edge case, not a misconfiguration. A structural property of reading committed state with a timestamp filter.

    Here is the pattern nearly everyone writes first, and it is entirely reasonable on inspection:

    incremental.sql
    -- run every 60 seconds, remembering the previous high-water mark
SELECT *
FROM   orders
WHERE  updated_at > :last_watermark
  AND  updated_at <= :now;

-- then: last_watermark := :now

    Now consider what a database actually does. A transaction sets updated_at at the moment the statement runs. The row does not become visible to any other reader until the transaction commits, which may be milliseconds later, or seconds, or — if the transaction is doing other work, waiting on a lock, or blocked on a slow external call — minutes later.

    So a row can have updated_at = 10:00:59 and become visible at 10:01:30. The extraction that ran at 10:01:00 could not see it: uncommitted. The extraction that runs at 10:02:00 will not look for it: its watermark has already advanced past 10:01:00. The row is never extracted, by any run, ever. It is not late; it is gone.

    Rows lost by timestamp-based incremental extraction simulated writes with realistic commit delay, evaluated against four strategies
    ROWS WRITTEN0committed in window
    COMMIT AFTER WINDOW0at risk
    LOST FOREVER0timestamp incremental
    LOG-BASED CDC0lost
    LOSS RATE0%silently wrong

    Work through the controls in this order, because each one isolates a separate lesson.

    1. Set the transaction duration to zero. Loss goes to zero. If every transaction committed instantly the pattern would be correct, which is precisely why it survives code review — it is correct in the mental model where writes are instantaneous.
    2. Raise it to 20 seconds against a 60-second interval. Roughly a third of rows are lost. Not delayed. Lost.
    3. Add a lookback window. Re-reading the previous couple of minutes recovers nearly everything, because it gives late-committing rows a second and third chance to be selected. This is the standard mitigation and it works.
    4. Now add deletes. Watch what the lookback does: nothing. A query filtering on updated_at cannot return a row that is no longer in the table, at any lookback, ever. Set the lookback to ten minutes and the deletes are still all lost.
    The three ways this stays hidden

    Row counts look plausible, because you are losing a small percentage rather than a block. Every individual row present is correct, so spot checks pass. And the loss is not reproducible — re-running the pipeline over the same period recovers nothing, because the watermark has moved and the rows were never marked as missing. Teams typically discover it when a total fails to reconcile against the source and somebody counts both sides.

    The four strategies, honestly compared

    Extraction strategies against correctness and cost
    StrategyLoses late commitsSees deletesCost per runLoad on source
    Full snapshotNoYes, by absenceWhole table, every timeHeavy, and grows forever
    Incremental, no lookbackYesNoChanged rows onlyLight
    Incremental with lookbackMostly noNoChanged rows plus overlapLight
    Log-based CDCNoYes, explicitlyChanges only, no queriesMinimal — reads the log

    The full snapshot is worth defending, because it is unfashionable and frequently correct. It is trivially right, it handles deletes, it needs no state, and for a table of a few million rows it costs almost nothing. A great deal of complexity has been added to platforms in pursuit of incremental extraction for tables that could simply be copied whole every night. Reach for incremental when the snapshot genuinely stops fitting in its window, not before.

    Log-based CDC is the correct answer at scale, and it works precisely because it stops asking the question this chapter is about. Rather than querying state and inferring change, it reads the database's own write-ahead log in commit order. Late commits cannot be missed because the log is the commit order, and deletes appear as explicit events. Chapter 5 is entirely about it.

    A DIFFERENT CONSTRAINT

    APIs, pagination and the catch-up trap

    With an API the binding constraint is usually not data volume or network speed. It is the vendor's rate limit, and it can make an ingestion mathematically impossible.

    An API extraction is a loop: request a page, get some records, follow the cursor, repeat. The arithmetic is simple and the conclusion is often surprising, because the failure is not "slow" but "never finishes".

    There are two independent ceilings. The rate ceiling is requests per minute the vendor allows. The latency ceiling is how fast you can issue requests given round-trip time and how many you run in parallel. Your throughput is the lower of the two, and which one binds determines what to do about it — parallelism helps only if latency is binding, and a larger page size helps in both cases.

    API backfill feasibility rate limit against concurrency, and whether incremental loading can keep up
    REQUESTS NEEDED0including retries
    BINDING LIMIT—
    BACKFILL TIME0wall clock
    DAILY LOAD—against 24 h

    The last tile is the one that matters operationally. A backfill that takes a week is annoying but survivable — you run it once. A daily incremental load that takes more than a day is a platform that can never be current, and will fall further behind every day it runs. That is a design error rather than a performance problem, and no amount of tuning fixes it; you need a larger page size, a higher rate limit, a bulk export endpoint, or a different integration entirely.

    Ask for the bulk endpoint before building the loop

    Many vendors offer a bulk or export API, an S3 drop, or a webhook subscription alongside the paginated REST interface, and it is frequently undocumented or buried. A bulk export sidesteps the rate ceiling completely. It is worth one email to the vendor before writing several weeks of pagination and retry logic.

    Two more API realities worth building for from the start. Rate limits are usually enforced with 429 responses, and the correct response is exponential backoff with jitter, honouring Retry-After when present — retrying immediately turns a slowdown into a ban. And cursor pagination is safe where offset pagination is not: with LIMIT 100 OFFSET 5000, rows inserted or deleted during your walk shift the window, so you silently skip and duplicate records. If a vendor offers a cursor or a keyset, use it.

    DOING IT SAFELY

    Reading from production without causing an incident

    Chapter 1 showed what analytical load does to a transactional database. Here is the practical version.

    Never read from the primary
    Read from a replica. It is the single highest-value thing on this list, it is usually a configuration change rather than a project, and it converts a potential outage into a lag problem.
    Know your replica's lag, and that it is not constant
    Replication lag is small until the primary is under load, at which point it grows — exactly when your data matters most. A watermark taken from the replica's clock while reading lagged data is a subtle way to lose rows for the same reason as the section above.
    Prefer a snapshot to a long-running query
    On Postgres, a long analytical read holds back vacuum and can bloat the primary even from a replica, depending on configuration. Exporting to object storage and querying there is kinder and usually faster.
    Bound everything
    Statement timeouts, row limits, a separate connection pool with a low ceiling and its own credentials. If the extraction misbehaves it should fail rather than consume the database.
    Read from the fewest tables you can
    Every table you extract is a dependency on someone else's schema, and chapter 1 showed what that costs. Extract what a consumer actually needs, not the whole schema because it was easier to write.
    Talk to the owning team before you start
    Unglamorous and the highest-leverage item here. Teams generally do not mind being read from; they mind finding out during an incident. This conversation is also where the data contract in chapter 6 begins.

    WHAT CHANGES UNDERNEATH YOU

    Drift, and which kinds hurt

    The source will change. Sorting changes by whether they are detectable and whether they are breaking tells you where to spend defensive effort.

    Classes of upstream change, ordered by how much trouble they cause
    ChangeBreaks the pipelineHow you find outDanger
    Column addedNoNever, unless you lookLow — you miss new data, nothing is wrong
    Column renamed or droppedYesNext run, loudlyLow — loud failures are cheap
    Type widened, int to bigintSometimesOn overflow, possibly months laterMedium
    Meaning changed, same typeNoA human noticesSevere
    Enum gains a valueNoRows fall through a CASE into a defaultSevere
    Timezone or precision changeNoAggregates shift slightlySevere
    Soft delete introducedNoDeleted rows keep appearingSevere
    Backfill run upstreamNoVolume spike, or nothing at allMedium

    The pattern is consistent with the blast-radius result in chapter 1 and worth stating as a rule: the changes that break loudly are the safe ones. A pipeline that fails on a dropped column has cost you an hour. A pipeline that keeps running while an enum quietly gains a seventh value that your CASE statement buckets as "other" has cost you every decision made on that number since.

    This is why the defensive work in this unit concentrates on the silent classes: schema registries and compatibility rules in chapter 6, distribution and volume tests in chapter 20, and freshness and anomaly monitoring in chapter 21. None of those catch a dropped column, because a dropped column does not need catching.

    Recap

    What to take from this chapter

    1. Sources are either mutable state or immutable events. Every hard extraction problem comes from state; event logs have almost none of them.
    2. Timestamp-based incremental extraction loses rows permanently. A transaction sets updated_at when the statement runs but becomes visible at commit. Rows committing after the watermark advances are never selected by any run. At a 20-second mean transaction against a 60-second interval, roughly a third are lost.
    3. A lookback window fixes late commits and nothing else. Re-reading the previous few minutes recovers almost all of them, for the cost of some duplicate reads.
    4. No lookback recovers a delete. A query filtering on updated_at cannot return a row that is gone. If deletes matter you need snapshots or CDC; there is no third option.
    5. updated_at is application convention, not a guarantee. Bulk updates, migrations and triggers routinely bypass it. Ask whether a database trigger maintains it.
    6. Full snapshots are underrated. Trivially correct, delete-aware, stateless. Use them until they genuinely stop fitting the window.
    7. For APIs the rate limit usually binds, not the volume. Parallelism helps only when latency is the ceiling; page size helps either way.
    8. If a daily load takes more than a day, it is a design error. No tuning fixes a pipeline that falls further behind every time it runs.
    9. Use cursor pagination, never offset. Concurrent writes shift an offset window, so you skip and duplicate rows.
    10. Loud breakage is cheap; silent drift is expensive. A dropped column costs an hour. A new enum value bucketed as "other" costs every decision since.
