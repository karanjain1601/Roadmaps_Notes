Orchestration

Chapter 2 found that 89% of a pipeline's worst-case staleness was waiting for a scheduler rather than computing. This is the chapter that reclaims it — and shows that the obvious way to reclaim it, staggering cron jobs so each starts when the last usually finishes, is silently wrong the first time a stage runs long.

    WHAT IT IS FOR

    The problem an orchestrator solves

    Not "running things on a schedule". Cron does that. The orchestrator exists for what happens between and after.

    The reason teams end up with one is always the same sequence. First a script on a cron. Then a second script that must run after the first, so the cron times are staggered. Then a third that depends on both. Then one fails at 3am and the two downstream jobs run anyway, producing wrong numbers from stale input, and nobody notices for two days.

    What is actually needed is a system that knows the dependency graph rather than a set of independent times:

    Dependencies
    Run B after A succeeds, and if A fails do not run B at all. This alone is most of the value.
    Retries with policy
    Retry a transient failure a bounded number of times with backoff, and escalate when the budget is spent. The second demo shows why this is not optional on any graph of real width.
    Backfill as a first-class operation
    Re-run a range of historical periods, with the same code, at controlled concurrency. Chapter 12's procedure needs a system that supports it.
    Observability of runs
    What ran, when, for how long, with what code version, and what the logs said. This is where incident response starts.
    A place to attach everything else
    SLAs, alerts, data quality gates, lineage. The orchestrator is where the pipeline becomes a system you can reason about rather than a collection of scripts.
    The honest version of "you might not need one"

    Below about ten tasks with a simple linear dependency, cron plus a wrapper script that exits non-zero and pages you is genuinely adequate, and chapter 3's arithmetic applies to orchestrators as much as to anything else. The threshold is not task count but whether you can still hold the dependency graph in your head. The moment somebody has to ask "what does this table depend on?" and the answer requires reading three cron files, you have already needed one for a while.

    THE STRUCTURE

    DAGs, tasks and runs

    Three words, and one distinction that causes more confusion than the rest of the vocabulary combined.

    A DAG is the dependency graph: tasks as nodes, "must run after" as directed edges, and no cycles — a cycle would be a task that must run before itself. A task is a unit of work. A run is one execution of the DAG for one logical period.

    The confusion is between the period a run is for and the time it executes. A daily run covering the twenty-fourth of the month starts after the twenty-fourth is over — so the run labelled with one date executes on the next. Airflow's historical naming of this as the "execution date" when it means the period start has probably cost the field thousands of hours; it now calls it the logical date, which is what it always was.

    The rule that follows

    Every task should take its period as a parameter and process exactly that period, never "now" and never "yesterday" computed inside the task. A task that calls current_date - 1 internally cannot be backfilled, cannot be re-run for a specific day, and will process the wrong period if it is retried after midnight. Parameterising the period is what makes the idempotent partition write of chapter 12 usable at all.

    One design question worth settling early: how much work belongs in a task? Too fine and the graph becomes unreadable and the scheduler overhead dominates. Too coarse and a failure means re-running an hour of work that mostly succeeded. A workable rule is that a task should be the smallest unit you would ever want to retry independently — usually one table's worth of transformation.

    THE FRESHNESS QUESTION

    Three ways to decide when to run

    Chapter 2 measured the cost of getting this wrong. This is the fix, and the near-miss that looks like the fix.

    Recall the chain from chapter 2: four stages with run durations of 6, 12, 8 and 4 minutes. On independent hourly crons the worst-case data age was 270 minutes, of which 240 was waiting. Three ways to schedule the same chain:

    Independent clocks
    Every stage has its own cron. Each contributes a full interval of waiting. Simple, robust, and slow.
    Staggered clocks
    Each stage is scheduled at an offset chosen so it starts just after the previous one usually finishes. Nearly as fast as anything else, and it is the obvious optimisation.
    Completion-triggered
    A stage starts when its upstream finishes. This is what an orchestrator is for, and it removes the waiting entirely except for the first stage's interval.

    The three models separate on two axes, and the second is the one that matters.

    1. Completion-triggering takes 270 minutes to 90. All the waiting except the first stage's interval disappears, because nothing sits idle after its input is ready. This is chapter 2's 89% figure being reclaimed.
    2. Staggered clocks get almost the same number and are silently wrong. 94 minutes against 90 — practically identical. But the offsets were sized for normal durations, so the first time the core transform takes three times as long, stage 3 starts on schedule and reads yesterday's output. No error, no alert, no failed task. A complete, plausible, wrong result.
    3. Completion-triggering degrades honestly. The same overrun makes it slower — 114 minutes instead of 90 — and it cannot produce a wrong answer, because stage 3 does not exist until stage 2 has finished.
    Why staggered cron is the most dangerous of the three

    It is the configuration a competent engineer arrives at by reasoning, it performs beautifully in testing, and its failure mode is the silent-wrongness class from chapter 1: correct types, plausible row counts, freshness checks passing, wrong numbers. It also fails intermittently, only on days when a stage runs long, which makes it maddening to diagnose.

    If you take one operational thing from this chapter: any dependency expressed as a time offset rather than as an actual dependency is a bug waiting for a slow day.

    There is a fourth model worth naming. Data-aware or asset-based scheduling triggers on the materialisation of a dataset rather than the completion of a task: stage 3 runs when the partition it needs exists. It behaves like completion-triggering for freshness, and adds two things — a task can wait on a specific partition rather than on the most recent run, and an external producer can trigger downstream work without being part of your DAG. That is the model Dagster is built around and which Airflow added as datasets.

    WHY GRAPHS NEED RETRIES

    Failure across width

    A one-percent chance of failure is negligible for one task and near-certain across two hundred. The arithmetic is unforgiving and the fix is cheap.

    Tasks fail transiently for reasons that have nothing to do with your code: a spot instance reclaimed, a network blip, a warehouse queue timeout, a rate limit, a brief credential refresh. Say each task has a 1% chance of hitting one. Across a graph of N tasks the probability that all succeed is 0.99^N, which falls fast.

    The headline is that a 200-task DAG with a 1% per-task failure rate succeeds only 13% of the time without retries — so 87% of nightly runs fail, and somebody is woken up almost every night for something that would have worked on a second attempt. Three retries take the effective per-task failure to one in a hundred million, and the run succeeds essentially always.

    Retries are only safe if tasks are idempotent

    Set the idempotency control to no. The arithmetic is unchanged — the run still succeeds — but each retry of a partially-completed task duplicates whatever it had already written, which is precisely chapter 12's append case ending at 2,600 rows against a correct 1,000.

    So retries and idempotency are one feature, not two. An orchestrator that retries non-idempotent tasks is a machine for corrupting data politely. Getting the write strategy right is what makes the retry policy usable.

    Two refinements worth configuring rather than accepting the defaults. Exponential backoff with jitter, because retrying immediately against a rate limit or an overloaded warehouse makes the outage worse, and retrying on a fixed interval synchronises every failed task into a thundering herd. And distinguishing retryable from terminal failures: a timeout deserves a retry, a syntax error or a missing column does not, and retrying it five times just delays the alert by twenty minutes.

    The pairing that covers most cases

    An orchestrator for everything plus dbt for transformation is the most common working arrangement, and it is a good one. The orchestrator handles ingestion, external dependencies, retries and scheduling; dbt owns the SQL layer, where it derives the dependency graph from the queries themselves rather than making you declare it — which eliminates the entire class of bug where the declared order and the actual order disagree.

    The failure to avoid is running dbt as a single orchestrator task. A one-task DAG that internally runs four hundred models gives you no per-model retry, no per-model timing, and no useful failure message. Expose the models as tasks.

    PRACTICE

    Patterns worth adopting, and four to avoid

    Adopt

    • Parameterise the period. Every task takes its logical date and processes exactly that.
    • One task per retryable unit. Usually one table.
    • Quality gates as tasks. A failing assertion should stop the graph before the bad data reaches a consumer, which is chapter 20.
    • Separate backfill concurrency. Chapter 12's rule, enforced by the scheduler.
    • Alert on the SLA, not the failure. A run that failed and was retried successfully is not an incident; a run that has not produced data by 07:00 is.

    Avoid

    • Time-offset dependencies. The staggered-cron failure, in any disguise.
    • Sensors that poll forever. A sensor with no timeout occupies a worker slot indefinitely and can deadlock the pool. Bound them, and prefer event triggers.
    • Business logic in the orchestrator. It should decide what runs when, not compute anything. Logic in a DAG file is untestable and runs on the scheduler.
    • One giant DAG. Split by domain and connect across with dataset dependencies, or every team waits on every other team's failures.

    A note on the sensor point, because it is the most common self-inflicted outage in Airflow specifically. A sensor waiting for a file occupies a worker slot while it waits. Twenty sensors on a pool of sixteen workers means all sixteen slots are held by tasks doing nothing, and the tasks that would satisfy them cannot start. The pool is deadlocked and the graph is stalled with no failure anywhere. Deferrable or reschedule-mode sensors exist precisely for this and should be the default.

    Recap

    What to take from this chapter

    1. An orchestrator is for dependencies, retries, backfills and observability, not for running things on a schedule. The threshold for needing one is when the graph no longer fits in your head.
    2. The period a run is for is not the time it executes. Parameterise the period into every task; a task computing "yesterday" internally cannot be backfilled or safely retried.
    3. Completion-triggering takes chapter 2's 270 minutes to 90, reclaiming almost all the waiting.
    4. Staggered cron gets 94 minutes and is silently wrong. When a stage overruns, the next starts on schedule and reads the previous day's output — no error, no alert, plausible numbers.
    5. Completion-triggering degrades honestly: the same overrun makes it slower, 114 minutes, and it cannot produce a wrong answer.
    6. Any dependency expressed as a time offset is a bug waiting for a slow day.
    7. Data-aware scheduling is the fourth model: trigger on a partition existing rather than a task finishing, which lets external producers drive your graph.
    8. A 200-task DAG at 1% per-task failure succeeds 13% of the time without retries. Three retries take effective failure to one in a hundred million.
    9. Retries and idempotency are one feature. Retrying a non-idempotent task is chapter 12's append case: the run goes green and the data is wrong.
    10. Back off exponentially with jitter, and do not retry terminal errors — that only delays the alert.
    11. Orchestrator plus dbt is the common pairing, but expose the models as tasks rather than running dbt as one.
    12. Alert on the SLA, not on the failure. A retried-and-recovered run is not an incident.
    13. Bound your sensors. Polling sensors holding worker slots is the classic self-inflicted stall.
