CHAPTER 06

Data contracts and schema evolution

Chapter 4 showed that the dangerous upstream changes are the quiet ones, and chapter 5 arranged for those changes to arrive with no warning whatsoever. This chapter is the defence: a machine-checkable agreement about shape, and a small set of compatibility rules precise enough that a build can reject a breaking change before it ships.

    WHY THIS EXISTS

    The gap a contract closes

    The producer of data and its consumers have no shared artefact describing what passes between them. Everything else follows from that.

    An application team owns a table. They understand it as internal state, because that is what it was built as. Downstream, four pipelines, nine dashboards and a churn model depend on its exact shape. Nobody told the application team that, and there is no document anywhere recording the dependency. So they rename a column during a refactor, entirely reasonably, and something breaks in a team they have never met.

    Notice this is not a technical failure. Both teams behaved correctly given what they knew. The failure is the absence of an interface: something that says this is what we promise, this is what you may rely on, and this is how it will change. Every other engineering discipline has this. Data mostly does not.

    What makes a contract different from documentation

    Documentation describes what a thing currently is; a contract constrains what it is allowed to become. The distinguishing feature of a useful contract is that a machine can reject a violation before it reaches production. A wiki page recording the schema of a table is genuinely helpful and will not stop a single incident, because nothing checks it. The compatibility rules in this chapter matter precisely because they are decidable.

    CONTENTS

    What a contract contains

    Schema is the part people implement. It is roughly half of what makes the agreement useful.

    Schema
    Field names, types, nullability, and which fields are required. The mechanically checkable core, and the subject of the rest of this chapter.
    Semantics
    What the fields mean. That total_cents excludes shipping, that status has exactly six legal values, that created_at is UTC. This is where the disagreements from chapter 1 get settled, and it cannot be inferred from types.
    Guarantees
    Freshness, completeness, uniqueness, ordering. "Available within fifteen minutes of the event", "primary key is unique", "no more than 0.1% of rows have a null customer". These are the assertions that become the tests in chapter 20.
    Ownership
    A named team, a channel to reach them, and an escalation path. A contract with no owner is a wiki page.
    Change policy
    The compatibility level enforced, notice required for a breaking change, and how long old versions are supported. This is what makes the contract a contract rather than a snapshot.

    The schema half is where nearly all tooling investment goes, because it is the half a computer can check. That is a good reason to start there and a bad reason to stop there — the expensive incidents from chapter 4 were semantic drift, and no schema language will catch a field whose meaning changed while its type did not.

    THE LANGUAGES

    Avro, Protobuf and JSON Schema

    Three serious options with genuinely different trade-offs. The compatibility rules that follow are Avro's, because they are the most fully specified.

    Schema languages compared on what matters for a data platform

    The row that decides most choices is field identity. Avro matches fields by name, so renaming is a breaking change unless you declare an alias. Protobuf matches by tag number, so renaming a field is free — the wire format never contained the name — while reusing a retired tag number is catastrophic. These produce opposite habits: Avro teams are careful about names, Protobuf teams are careful about numbers and mark retired tags reserved.

    Practical guidance

    If your data flows through Kafka into analytics, Avro with a registry is the well-trodden path and everything in the next section applies directly. If your organisation already runs gRPC, use Protobuf and inherit the schemas the services already have rather than translating them. JSON Schema is the right answer for HTTP APIs and for validating files, and the wrong answer for a high-volume event pipeline — the encoding overhead is large and the compatibility story is weak.

    THE DECIDABLE PART

    Compatibility, and which deploy order it permits

    Two directions, four classes, and one consequence that most explanations leave out.

    Get the definitions exactly right, because they are easy to say backwards:

    Backward compatible
    A reader using the new schema can read data written with the old one. New code copes with old data. Permits: upgrade consumers first.
    Forward compatible
    A reader using the old schema can read data written with the new one. Old code copes with new data. Permits: upgrade producers first.
    Fully compatible
    Both. Deploy in any order, which in a real distributed system with a rolling deploy is the only genuinely comfortable position.
    Incompatible
    Neither. There is no deploy order that works, so it needs a coordinated change: a new schema version consumed in parallel, or dual-writing during a migration window.

    That last column is the part usually omitted, and it is the part you need on the day. Pick a change below and the demo works out both directions from the actual Avro resolution rules, then tells you what you are allowed to do with it.

    Three results are worth pulling out because they contradict common intuition.

    1. Adding a field is not automatically safe. With a default it is fully compatible; without one it is forward-compatible only, so a new reader hitting old data has no value to use and no default to fall back on. The default is what makes the change safe, not the addition.
    2. Widening a type is only safe in one direction. Promoting int to long is backward compatible — a long reader handles int data — but not forward compatible, because an old int reader cannot hold a long. So a change that feels purely additive still constrains your deploy order.
    3. An alias buys backward compatibility only. Aliases are declared on the reader schema, so a new reader can resolve an old field name. An old reader has no alias for the new name and cannot resolve it. Renaming is therefore never fully compatible in Avro, however carefully you do it.
    Which level to enforce in the registry

    The common default is BACKWARD, and for a Kafka topic feeding analytics it is usually right: it lets producers evolve while requiring consumers to be upgraded first, which is the order you can actually control. But if you do not control your consumers — other teams, third parties, a dashboard someone built and forgot — FULL is the honest setting, because BACKWARD quietly assumes a coordination you do not have.

    WHY ORDER MATTERS

    What a rolling deploy does to a one-way change

    Compatibility is not an abstract property. It decides how many messages break during the window when both versions are running.

    In a real deployment there is no instant when versions swap. For minutes or hours you have a mixture: some producers on the new schema, some consumers still on the old. Every message crosses one of four pairings, and two of them are where compatibility gets tested for real.

    pairings.txt
    old writer -> old reader   always fine
new writer -> new reader   always fine
new writer -> old reader   needs FORWARD compatibility
old writer -> new reader   needs BACKWARD compatibility

    So a backward-compatible change survives a deploy that upgrades consumers first, and breaks if a producer gets there before them. Set the change class and the deploy order below and watch what happens to the broken-message count.

    The model makes three practical points. A fully compatible change is genuinely free — zero broken messages in any order, which is why it is worth paying the small design cost of always supplying a default. A one-way change is free if you deploy in the matching order and expensive otherwise, so the compatibility class is really an instruction about sequencing. And an incompatible change breaks messages under every order, at a volume proportional to how long the deploy takes, which is why the answer there is never "deploy carefully" but "do not do this as a deploy".

    The rollback trap

    Deploy order also governs rollback, in reverse. If you upgraded consumers first for a backward-compatible change and then need to roll the producers back, you are fine. If you upgraded producers first for a forward-compatible change and need to roll consumers back, you are fine. Mismatch it and your rollback is the breaking direction — so you have an outage during the recovery from an outage. Decide the rollback order at the same time as the deploy order, not during the incident.

    ENFORCEMENT

    The registry, and where the check belongs

    Rules nobody enforces are documentation. The value is entirely in the rejection.

    A schema registry is a small service holding schemas by subject and version, assigning each an id, and — the part that matters — refusing to register a new version that violates the configured compatibility level for that subject.

    The runtime path is straightforward. A producer registers its schema, gets an id, and prefixes each message with that id rather than the whole schema, which is what keeps the encoding compact. A consumer reads the id, fetches and caches the schema, and resolves the writer's schema against its own.

    Move the check left

    A registry rejecting a bad schema at runtime means the producer deploys and then fails, which is a production incident with extra steps. The valuable configuration is a CI check: on every pull request touching a schema, test the proposed version against the registered one and fail the build. The same rules, applied hours earlier, to the person who can still change their mind cheaply. That single job prevents more incidents than the registry itself.

    Two things a registry does not do, worth being clear about. It does not know your semantics — nothing stops total_cents silently becoming tax-inclusive, since the type is unchanged. And it does not cover tables, only serialised messages, so a warehouse table has no registry unless you build the equivalent yourself with schema tests in your transformation tool.

    THE HARDER HALF

    Getting a contract agreed

    The technology has been solved for a decade. Adoption is where this fails, and it fails for a predictable reason.

    From the producing team's chair, a data contract is pure cost. They gain a constraint on their own schema, a CI check that can block their deploy, and an obligation to a team whose roadmap they do not share. Presented as a governance requirement, it will be resisted, and the resistance is rational.

    What works is inverting the framing so the contract is something they receive rather than something imposed:

  1. Start where it already hurt. One interface, chosen because a real incident happened there. A contract that visibly prevents a recurrence is an easier sell than a policy covering forty tables.
  2. Give them the blast radius. The lineage from chapter 1 turns "please be careful" into "this column has fourteen downstream dependencies across three teams". Most people are perfectly willing to be careful once they can see what they are being careful about.
  3. Supply the check, do not request compliance. Write the CI job, open the pull request, make it green. Adoption cost near zero beats adoption benefit argued in the abstract.
  4. Offer something back. Ownership metadata, a schema they can validate against in their own tests, freedom from ad-hoc data questions because consumers now read the contract. Reciprocity, not compliance.
  5. Make the contract narrower than the table. Promising three columns is a small commitment; promising a whole table forbids all internal change. A deliberately minimal contract is far easier to agree and far more likely to hold.

    6. That last point is the one most worth internalising, because it is where enthusiasm usually overreaches. A contract covering every column of every table is a freeze on someone else's codebase, and it will be either refused or quietly ignored. Promise little, enforce it properly, and expand only where a real consumer needs more.

    Recap

    What to take from this chapter

    1. A contract differs from documentation because a machine can reject a violation. A wiki page recording a schema prevents nothing.
    2. Schema is about half of it. Semantics, guarantees, ownership and a change policy are the rest, and semantic drift is the class that caused the expensive incidents in chapter 4.
    3. Field identity decides your habits. Avro matches by name, so renames break and aliases are needed. Protobuf matches by tag, so renames are free and reusing a retired tag is catastrophic.
    4. Backward means new code reads old data and permits upgrading consumers first. Forward means old code reads new data and permits upgrading producers first. Full permits any order.
    5. Adding a field is only fully compatible with a default. Without one it is forward-compatible only.
    6. Widening int to long is backward but not forward compatible. An apparently additive change still dictates deploy order.
    7. Aliases give backward compatibility only, because they live on the reader schema. Renaming is never fully compatible in Avro.
    8. A rolling deploy tests compatibility for real. One-way changes cost nothing in the matching order and break messages in the wrong one, proportionally to the deploy window.
    9. Plan the rollback order with the deploy order. Mismatched, your recovery is the breaking direction.
    10. Enforce in CI, not at runtime. Same rules, hours earlier, to someone who can still change their mind cheaply.
    11. Promise less than the whole table. A narrow contract gets agreed and holds; a total one gets refused or ignored.

    ONE THING TO TRY

    Take the most important table you consume and write the narrowest contract you would actually be happy with: three columns, their types, one freshness guarantee, one owner. If that document does not exist, it is an hour's work and the start of the conversation.
