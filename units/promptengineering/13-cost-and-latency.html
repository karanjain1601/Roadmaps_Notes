Optimising cost and latency

Prompt work usually optimises for quality alone, then someone looks at the invoice. The levers here are ordered by return per hour of effort, and the first two are free — they are layout decisions you should have made anyway.

caching length routing output limits

Know which half you are paying for

Output tokens typically cost three to five times input tokens. A prompt of 2,000 input tokens producing 400 output tokens is often majority-output cost, which surprises people who spend their optimisation effort on the prompt.

the arithmetic worth doing before optimising anything
IN, OUT, CACHED = 3.00, 15.00, 0.30      # $ per million, illustrative

def breakdown(tokens_in: int, tokens_out: int, cached: int, calls_per_day: int):
    fresh = tokens_in - cached
    c_in     = fresh  / 1e6 * IN
    c_cached = cached / 1e6 * CACHED
    c_out    = tokens_out / 1e6 * OUT
    per = c_in + c_cached + c_out
    return {
        "per_call": per,
        "monthly": per * calls_per_day * 30,
        "share_input":  (c_in + c_cached) / per,
        "share_output": c_out / per,
    }

breakdown(tokens_in=2000, tokens_out=400, cached=0, calls_per_day=20_000)
# per_call $0.0120 — input 50%, output 50%

breakdown(tokens_in=2000, tokens_out=400, cached=1600, calls_per_day=20_000)
# per_call $0.0072 — input 17%, output 83%
#
# Note what caching did: it cut the bill 40% AND changed which half to optimise.
# Do this calculation first, or you will spend a day shortening a prompt that
# accounts for a sixth of the cost.

Lever 1 — cache-aware layout

Free, and usually the largest single reduction. Chapter 3 covered the mechanism; the operational points are what matter here.

  • Everything stable comes first, byte-identical on every request. System prompt, tool schemas, examples.
  • Nothing variable above the line. Dates, names, session ids, A/B flags, feature toggles — all below.
  • Whitespace is part of the bytes. A template that sometimes emits an extra newline halves your hit rate silently. Test for it (chapter 11).
  • Never rewrite the prefix mid-conversation. Appending a reminder at the end is free; editing the system prompt invalidates everything after it.
  • Check the minimum cacheable length. Providers have a floor — a 300-token prefix may not be cached at all.
  • Watch the TTL. Low-traffic endpoints may never hit a warm cache; the discount assumes requests arrive close together.
  • Monitor the hit rate as a first-class metric. A collapse is the earliest signal that someone put something variable in the prefix.

Lever 2 — the output

The most under-attacked cost, because prompt length is visible in the editor and output length is not.

TechniqueEffect
State a length limit and mean it"Under 80 words" cuts typical output by half against no limit. Assert on it in evals
A schema instead of proseStructured output is dramatically shorter than the equivalent explanation
Drop the preamble"Reply with the answer only, no preamble" removes "Certainly! Here's a summary of…" from every response
Strip the reasoningIf working goes in <scratch> tags you still pay for it. Consider whether the task needs it at all (chapter 7)
Set max_tokens to a real ceilingProtection against runaway generation, and it makes cost predictable
Stop sequencesStop the moment the useful part ends rather than letting it trail into a closing paragraph
Output length is also latency

Tokens are generated sequentially at a roughly fixed rate, so 400 output tokens is several seconds regardless of how fast your prompt prefills. Halving the output halves the visible wait. This makes output reduction the only lever that improves cost and latency together — and it is why "be concise" as an enforced numeric limit is worth more than any infrastructure change.

Lever 3 — prune the prompt

Chapter 3 argued that deletion is a prompt-engineering technique. It is also a cost technique, and the two motivations point the same way.

an ablation sweep — which parts are earning their tokens?
SECTIONS = ["role", "rules_6_to_12", "examples_3_and_4", "edge_cases", "voice_notes"]

def ablate(prompt, cases):
    base = run(prompt, cases)
    print(f"full: {base['pass_rate']:.3f}  {base['tokens_in']} tokens")

    for s in SECTIONS:
        trimmed = prompt.without(s)
        r = run(trimmed, cases)
        delta = r["pass_rate"] - base["pass_rate"]
        saved = base["tokens_in"] - r["tokens_in"]
        verdict = ("DELETE"  if delta >= -0.01 else
                   "review"  if delta >= -0.03 else "keep")
        print(f"-{s:<18} {r['pass_rate']:.3f} ({delta:+.3f})  -{saved} tokens  {verdict}")

Run the ablation before you optimise anything else

Prompts grow by accretion and nobody ever measures what the accreted parts contribute. An afternoon of ablation routinely finds a quarter of the prompt doing nothing measurable — and that quarter has been billed on every request since it was added. It also frequently improves quality, because the surviving instructions stop competing for attention. This is the highest return per hour in the chapter.

Lever 4 — routing

route.py — classify, then escalate only what needs it
async def answer(q: str, ctx) -> Answer:
    difficulty = await classify(q)                # small model, ~80ms, negligible cost

    if difficulty == "simple":
        r = await call(PROMPT_SHORT.render(q=q), model=SMALL)
        if looks_uncertain(r):                    # hedging, refusal, low confidence
            metrics.incr("router.escalated")
            r = await call(PROMPT_FULL.render(q=q), model=MID)
        return r

    return await call(PROMPT_FULL.render(q=q),
                      model=LARGE if difficulty == "hard" else MID)

# Two things to track:
#   escalation rate  — above ~15% the classifier is mis-routing and you are
#                      paying for two calls to do one job
#   quality by route — the small-model path must be evaluated separately, or a
#                      regression there hides inside a healthy overall average
#
# A cheaper variant that often works as well: skip the classifier entirely, try
# the small model first, and escalate on low confidence. One fewer call on the
# happy path, at the cost of a slower tail.

Lever 5 — batch what can wait

Most providers offer an asynchronous batch endpoint at roughly half price with a delivery window measured in hours. Anything not on a user's critical path belongs there: back-classification of a backlog, nightly summarisation, eval runs, dataset generation, re-processing after a prompt change.

Eval runs in particular are worth moving. A 500-case suite at three repeats is 1,500 calls, run on every prompt change, and none of it is latency-sensitive.

Automatic prompt optimisation

Use a model to improve the prompt: generate candidate variants, score them against your eval set, keep the best, iterate. It works, with real caveats.

optimise.py — search over prompts, scored by your evals
REWRITE = """Here is a prompt and the cases it currently fails.

{prompt}
{failures}

Propose 4 revised prompts, each targeting a different hypothesis about the cause.
Change one thing per variant. Keep the output contract identical. Return JSON:
[{{"hypothesis": "...", "prompt": "..."}}]"""

def optimise(prompt, cases, rounds: int = 3, holdout: list = None):
    best = (prompt, run(prompt, cases)["pass_rate"])

    for _ in range(rounds):
        fails = failing_cases(best[0], cases)
        variants = structured_call(list[Variant], REWRITE.format(
            prompt=best[0].source(), failures=render(fails[:8])))

        for v in variants:
            score = run(v.prompt, cases)["pass_rate"]
            if score > best[1] + 0.01:            # require a real margin
                best = (v.prompt, score)

    # The step that makes this trustworthy: confirm on data the search never saw.
    held = run(best[0], holdout)["pass_rate"]
    print(f"train {best[1]:.3f}  holdout {held:.3f}")
    return best[0], held
Optimised prompts overfit, and they get long

The search will happily find a prompt that scores 0.96 on your 60 cases and 0.84 on anything else — it has learned your eval set, not your task. Always hold out cases the search never sees, and judge only on those. Second problem: candidate variants tend to grow, because adding is easier than removing. Cap the length in the rewrite instruction, and run an ablation on the winner. And read the result — an automatically-generated prompt nobody understands is a maintenance liability regardless of its score.

Measure before optimising, then measure after

Every change here trades against quality, and the trade is only visible if you run the eval set on both sides. A prompt pruned by 30% that loses two points of accuracy might be an excellent trade or a terrible one depending on what an error costs you (chapter 9's demo). Record cost, p95 latency and pass rate together in every eval report, and make the trade explicitly rather than discovering it later.

The short version

  1. Compute the input/output split first. Output usually costs 3–5× input per token, and caching changes which half to attack.
  2. Cache-aware layout is free and usually the largest single reduction. Whitespace counts; monitor the hit rate.
  3. Output length is the only lever that improves cost and latency together. Enforce a numeric limit and assert on it.
  4. Run an ablation. An afternoon routinely finds a quarter of the prompt contributing nothing — and deleting it often helps quality too.
  5. Routing halves cost on mixed traffic. Watch the escalation rate and evaluate each route separately.
  6. Batch anything off the critical path, starting with your own eval runs.
  7. Automatic optimisation works but overfits and inflates. Hold out cases, cap length, ablate the winner, and read it.
  8. Record cost, p95 latency and pass rate together, so every trade is made deliberately.
