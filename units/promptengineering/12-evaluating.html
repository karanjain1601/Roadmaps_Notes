Evaluating a prompt

Without measurement, prompt work is a series of confident opinions about a non-deterministic system. This chapter is the smallest amount of apparatus that lets you say "version 4 is better than version 3" and be right.

eval set checks judges significance

Start smaller than you think

Twenty cases in a JSONL file, run from a script, beats a sophisticated platform you will set up next quarter. The failure mode is not a bad eval system — it is not having one, and discovering three months in that nobody can say whether last week's change helped.

evals/run.py — a complete eval harness, forty lines
import json, asyncio, statistics
from collections import Counter

async def run(prompt, cases: list[dict], repeats: int = 3) -> dict:
    sem = asyncio.Semaphore(8)

    async def one(case, attempt):
        async with sem:
            out = await call(prompt.render(**case["input"]), **prompt.meta["params"])
        return {"id": case["id"], "attempt": attempt, "category": case.get("category","-"),
                "output": out.text, "tokens": out.usage.total_tokens,
                "cost": out.cost_usd, "checks": check(case, out.text)}

    rows = await asyncio.gather(*[one(c, i) for c in cases for i in range(repeats)])

    passed = [r for r in rows if not r["checks"]]
    by_case = Counter(r["id"] for r in passed)

    return {
        "prompt_hash": prompt.hash,          # chapter 11 — the join key
        "pass_rate":   len(passed) / len(rows),
        "solid":       sum(1 for c in cases if by_case[c["id"]] == repeats) / len(cases),
        "flaky":       [c["id"] for c in cases if 0 < by_case[c["id"]] < repeats],
        "cost":        sum(r["cost"] for r in rows) / len(rows),
        "tokens_p95":  pct([r["tokens"] for r in rows], 95),
        "rows":        rows,
    }

# The two numbers to watch are pass_rate and solid. A case that passes two runs
# out of three is not passing — it is telling you the prompt is under-specified
# on that input, and that is more actionable than the average.
Run every case three times

Chapter 2 established that even temperature 0 is not deterministic. One run of a case is a sample, not a result, and a prompt change that "fixed" a case may simply have got lucky. Three repeats costs three times as much and is the difference between measurement and anecdote. Track the flaky list separately from the pass rate — flaky cases are usually the most informative thing in the report.

Cheap checks first

A surprising amount is measurable with string operations — deterministic, instant, free, and never disagreeing with itself. Exhaust these before reaching for a judge.

check.py — the assertions that catch most regressions
def check(case: dict, out: str) -> list[str]:
    fails = []

    if case.get("schema"):
        try:
            parsed = SCHEMAS[case["schema"]].model_validate_json(out)
        except ValidationError as e:
            return [f"schema: {e.errors()[0]['msg']}"]       # nothing else is meaningful
        for field, want in case.get("expect", {}).items():
            got = getattr(parsed, field)
            if got != want:
                fails.append(f"{field}: expected {want!r}, got {got!r}")

    for s in case.get("must_contain", []):
        if s.lower() not in out.lower():
            fails.append(f"missing: {s!r}")
    for s in case.get("must_not_contain", []):
        if s.lower() in out.lower():
            fails.append(f"present but forbidden: {s!r}")

    if case.get("expect_behaviour") == "refuse" and not is_refusal(out):
        fails.append("answered an unanswerable case")

    # Grounding: every figure in the output must appear in the input.
    src = " ".join(str(v) for v in case["input"].values())
    for n in re.findall(r"\b\d[\d,.]*\b", out):
        if n not in src:
            fails.append(f"fabricated number: {n}")

    return fails
Exact-figure assertions catch the subtlest regressions

Case t-018 above asserts "48.00" present and "£48 " absent. That looks pedantic until a prompt edit causes the model to start rounding, and every downstream reconciliation breaks two weeks later with no obvious cause. Numbers, dates, references and units are where quiet regressions live, and they are the cheapest possible thing to assert on.

Validate the judge before you trust a single number from it

Label fifty outputs yourself, run the judge on the same fifty, and measure agreement. Below roughly 80%, the judge is measuring something other than what you care about, and every decision made from its numbers is noise dressed as data. When you disagree with the judge, the rubric is nearly always the problem — it is ambiguous in exactly the way your instructions to a new colleague would be, which makes fixing it useful twice.

Comparing two versions

Is that difference real? Two prompt versions, two pass rates. Check whether the gap survives the noise before shipping on it.

paired comparison — the version that needs fewer cases
# Comparing two independent pass rates wastes information: both versions ran on
# the SAME cases, so compare them case by case.

def paired(a: Report, b: Report) -> dict:
    ids = set(a.case_ids) & set(b.case_ids)
    b_better = sum(1 for i in ids if b.passes(i) > a.passes(i))
    a_better = sum(1 for i in ids if a.passes(i) > b.passes(i))
    same     = len(ids) - b_better - a_better

    n = b_better + a_better                    # ties carry no signal
    if n == 0:
        return {"verdict": "identical", "changed": 0}

    # Sign test: under the null, each discordant case is a coin flip.
    p = binom_test(b_better, n, 0.5)
    return {
        "b_better": b_better, "a_better": a_better, "unchanged": same,
        "p_value": p,
        "verdict": "b wins" if p < 0.05 and b_better > a_better
                   else "a wins" if p < 0.05
                   else "not distinguishable",
    }

# The paired test detects real differences with far fewer cases, and it hands you
# something more useful than a p-value: the LIST of cases that changed. Read them.
# A version that fixes four cases and breaks three is not an improvement, even
# when the aggregate went up.

Slicing

One number hides everything worth knowing

"Pass rate: 0.84" is not actionable. Always break it down — by category, by input length, by language, by whether the case is an edge case. A uniform 0.84 and an 0.84 that is 0.96 on common inputs and 0.31 on the unanswerable slice are completely different situations, and only the second tells you what to do next. Most prompt improvements are concentrated in one slice, and most regressions hide in another.

the report that gets read
def summarise(rep: dict) -> str:
    lines = [f"prompt {rep['prompt_hash']}  pass {rep['pass_rate']:.2f}  "
             f"solid {rep['solid']:.2f}  ${rep['cost']:.4f}/call"]
    for cat in sorted({r["category"] for r in rep["rows"]}):
        rows = [r for r in rep["rows"] if r["category"] == cat]
        ok = sum(1 for r in rows if not r["checks"])
        lines.append(f"  {cat:<16} {ok/len(rows):.2f}  ({len(rows)} runs)")
    if rep["flaky"]:
        lines.append(f"  flaky: {', '.join(rep['flaky'][:8])}")
    top = Counter(c.split(":")[0] for r in rep["rows"] for c in r["checks"])
    for reason, n in top.most_common(5):
        lines.append(f"  fail cause: {reason} ×{n}")
    return "\n".join(lines)

In CI

gate.py — tolerance on quality, none on safety
TOLERANCE = 0.03

def gate(curr: dict, base: dict) -> None:
    fail = []
    if curr["pass_rate"] < base["pass_rate"] - TOLERANCE:
        fail.append(f"pass rate {base['pass_rate']:.2f} → {curr['pass_rate']:.2f}")

    # No tolerance for these two.
    if slice_of(curr, "adversarial")["pass_rate"] < 1.0:
        fail.append(f"adversarial: {failed_ids(curr, 'adversarial')}")
    if slice_of(curr, "regression")["pass_rate"] < 1.0:
        fail.append(f"previously-fixed cases broke: {failed_ids(curr, 'regression')}")

    # Efficiency regressions count too.
    if curr["cost"] > base["cost"] * 1.3:
        fail.append(f"cost +{curr['cost']/base['cost']-1:.0%}")
    if curr["tokens_p95"] > base["tokens_p95"] * 1.3:
        fail.append(f"p95 output +{curr['tokens_p95']/base['tokens_p95']-1:.0%}")

    if fail:
        raise SystemExit("Prompt eval gate failed:\n  " + "\n  ".join(fail))
  • Full suite on prompt, example, schema or model changes. All four alter behaviour and only the last is obvious.
  • Fast subset on every commit — twenty cases, one repeat, adversarial included. Under two minutes.
  • Store the report against the prompt hash (chapter 11). Reports without a hash are numbers with no provenance.
  • Keep every report. Six months of history is how you answer "when did this get worse, and what shipped that week?"
  • Read twenty failures in full, monthly. Patterns invisible in aggregates are obvious in the actual text.
  • Gate on cost and output length, not only quality. A change that adds three points and doubles the bill is a decision.

The short version

  1. Twenty cases in a file today beats a platform next quarter. Forty lines is a complete harness.
  2. Three repeats per case. One run is a sample; the flaky list is often the most informative output.
  3. Every production failure becomes a permanent case — that is what keeps the set honest.
  4. Exhaust deterministic checks first. Exact figures, forbidden strings and fabricated numbers catch the quietest regressions.
  5. Judges need named criteria, quoted failures and a different model family — and validation against your own labels before you trust them.
  6. Compare versions with a paired test: fewer cases needed, and it hands you the list of cases that changed.
  7. Always slice. A single pass rate hides the one category carrying all the failure.
  8. Gate CI on regression with zero tolerance for adversarial and previously-fixed cases, and on cost as well as quality.
