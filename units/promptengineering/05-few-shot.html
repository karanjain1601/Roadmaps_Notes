Few-shot examples

An example is the strongest conditioner available, because it does not describe the pattern — it is the pattern. That strength is also the danger: examples transmit everything about themselves, including the parts you did not mean to teach.

how many selection ordering leakage

Why examples work so well

Chapter 1's demo made this visible: two examples in a numbered-list format pushed "1" from a marginal token to the dominant one, with no instruction saying "use a numbered list". A description of a format is text about a pattern. An example instantiates the pattern, and instantiation is a far stronger conditioner.

This is why few-shot reliably outperforms elaborate instructions for anything with a consistent shape — classification, extraction, format conversion, tone matching. It is also why examples are the first thing to try when a zero-shot prompt has plateaued.

Diversity matters more than count

Four examples covering four distinct situations beat twelve variations on the same one, at a third of the cost. Before adding a fifth example, ask what it demonstrates that the existing four do not. If the answer is "the same thing again, slightly differently", it is buying you nothing but tokens and the risk of over-narrowing. The count is a consequence of the coverage you need, not a target.

Which examples

Choose deliberately. A set of examples is a specification of the task, so what it omits is as informative as what it includes.

  • One from the common case. The boring majority. It anchors the default behaviour.
  • One from each distinct class or branch, if the task has them. The model infers the label set from what it sees.
  • One genuinely hard case — ambiguous, or requiring the rule you keep having to restate.
  • One refusal or empty case. Almost always the highest-value example, because declining is a behaviour that instructions convey poorly and demonstrations convey well.
  • Real examples, not invented ones. Invented inputs are cleaner than reality — better punctuated, better spelled, more complete — and they teach the model to expect that.
  • Correct examples. An error in an example is taught with full force. Have someone else check them.

Format leakage

The characteristic few-shot failure. Examples transmit everything about themselves, and some of that is accidental.

LeakSymptomFix
ContentOutputs mention Northwind, or order NW-8842, for unrelated inputsVary the entities across examples; never reuse one identifier
LengthEvery output is the length of your examples, regardless of inputInclude a short one and a long one
Label distributionThree of four examples are "high" severity, so everything becomes highBalance the classes, or over-represent the rare ones deliberately
Order effectsThe last example's class is over-predictedDo not put all of one class together; end on the common case
Incidental formattingTrailing full stops, capitalisation, key order in JSON — all copiedMake examples byte-consistent with what you want
Reasoning styleIf examples show reasoning, the model reasons; if not, it will notDeliberate either way — see chapter 7
Never reuse an identifier across examples

If NW-8842 appears in two of your four examples, it becomes a strongly conditioned token, and the model will emit it for inputs that contain no order reference at all. This produces exactly the kind of confident, well-formatted wrong answer that survives review. Use a different, obviously-distinct identifier in every example — and if you validate outputs, assert that any reference returned actually appears in the input.

Ordering

Recency dominates
The last example is the most influential. End on the case that best represents your typical input, not on the exotic one.
Do not cluster classes
Three "billing" examples followed by one "delivery" teaches a run, not a distribution. Interleave.
Order sensitivity is a diagnostic
If shuffling your examples changes accuracy noticeably, the task is under-specified — the model is relying on the arrangement rather than the pattern. Add an explicit rule or a clearer contract.
Keep the order stable in production
For caching (chapter 3) and for reproducibility. Shuffle only when testing sensitivity.

Dynamic selection

Instead of a fixed set, retrieve the examples most similar to the current input. Genuinely powerful when you have a large labelled pool and the task has many distinct sub-cases.

dynamic_examples.py — nearest neighbours, with diversity
def select_examples(query: str, pool: list[Example], k: int = 4) -> list[Example]:
    q = embed(query)
    scored = sorted(pool, key=lambda e: -cosine(q, e.vector))

    picked: list[Example] = []
    for e in scored:
        # Skip near-duplicates of something already chosen: four examples that
        # are all the same case teach one thing at four times the cost.
        if any(cosine(e.vector, p.vector) > 0.92 for p in picked):
            continue
        picked.append(e)
        if len(picked) == k - 1:
            break

    # Always keep one refusal/empty example, regardless of similarity, or the
    # model stops believing declining is an option.
    picked.append(REFUSAL_EXAMPLE)

    # Most similar LAST: recency dominates, so the closest match should be the
    # final thing read before the input.
    picked.reverse()
    return picked
Dynamic selection costs you the cache

Examples that change per request cannot sit in the cacheable prefix, so you lose the discount from chapter 3 on that whole block. On a high-volume endpoint that can outweigh the accuracy gain. Measure both: if dynamic selection buys two points of accuracy and triples your input bill, that is a decision to make deliberately rather than a straightforward improvement. A middle path that often works: a fixed cached set of three, plus one dynamically retrieved example appended after the cached region.

for ex in EXAMPLES:
    messages += [{"role": "user", "content": ex.input},
                 {"role": "assistant", "content": ex.output}]
messages.append({"role": "user", "content": ticket})

# Both are cacheable; both are byte-stable. The difference is small and
# model-dependent, which means it is exactly the kind of thing to settle with
# your eval set rather than an opinion (chapter 12).

Maintaining an example set

  • Store examples as data, not embedded in a string. A JSON or YAML file, versioned with the prompt, renderable into either placement.
  • Never let an example duplicate an eval case. Testing on what you demonstrated measures memorisation, not generalisation.
  • Re-check them when the schema changes. An example emitting a retired field teaches the model to emit it.
  • Review after every model upgrade. Examples that were compensating for a weakness may now be dead weight — try removing them and re-measuring.
  • Track which failures each example was added for. Otherwise nobody will ever dare remove one.

The short version

  1. An example is the pattern rather than a description of it, which is why it conditions so much more strongly than an instruction.
  2. Diversity matters more than count. Four covering four situations beat twelve covering one.
  3. Include the common case, each distinct class, one hard case, and — most valuable — one refusal or empty case.
  4. Use real examples. Invented ones are cleaner than reality and teach the model to expect that.
  5. Examples leak content, length, class balance and incidental formatting. Never reuse an identifier across them.
  6. Recency dominates: end on the case that best represents typical input, and do not cluster classes.
  7. Order sensitivity is a diagnostic — if shuffling changes accuracy, the task is under-specified.
  8. Dynamic selection buys accuracy and costs you the cache. Measure both before adopting it.
