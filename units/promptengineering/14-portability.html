Across models and modalities

A prompt is tuned against one model's particular tendencies, which means part of what you built is compensation for quirks the next model does not have. Portability is mostly about knowing which part that is.

portability reasoning models multimodal upgrades

What transfers and what does not

Transfers well

  • Clear task definition and audience
  • Output contracts and schemas
  • Well-chosen examples
  • Edge-case handling
  • Section ordering and delimiters
  • Grounding rules and refusal wording

Transfers badly

  • Phrasings that worked around one model's quirk
  • Chain-of-thought instructions
  • Rules restated three times because one model ignored them
  • Exact tone calibration
  • Assumptions about default verbosity
  • Sampling parameters — the scales differ
  • Provider-specific features: prefill, JSON mode, tag conventions

Notice the pattern: structural things transfer, compensatory things do not. That is a useful test when auditing a prompt for portability — for each rule, ask whether it describes the task or patches a behaviour. The patches are the risk.

Portability audit Describe what is in your prompt. The output is a migration plan, not a score.

Reasoning models

Models trained to think before answering change the advice in chapter 7 rather than extending it. Most of what you would add, you should now remove.

STANDARD = """Determine whether this return is accepted.

Work through it in :
1. What was bought, and when?
2. Was it a sale item? Is it marked final sale?
3. Is it faulty, or a change of mind?
4. Which policy section applies given 2 and 3?
5. What is the window, and who pays postage?
Then answer in ."""

# For a reasoning model: supply the goal and the constraints, not the steps.
REASONING = """Determine whether this return is accepted, and who pays postage.

Constraints:
- Use only the policy text provided; quote the clause you rely on.
- Faults are governed by the faulty-items rule regardless of discount.
- If the policy does not cover the case, say so rather than inferring.

Answer in under 80 words, citing the clause."""

# The second is shorter, does not prescribe a decomposition that might be wrong,
# and states the one domain rule that is genuinely non-obvious. Everything else
# the model works out for itself — which is what you are paying it for.
Prompts for reasoning models get shorter, not longer

The instinct is that a more capable model deserves a more elaborate prompt. The opposite holds: specify the objective, the constraints and the output contract, then get out of the way. Over-specified method instructions fight the model's own process and reliably make things worse. If migrating, the first thing to try is deleting every "how" instruction and keeping only the "what".

The unreadable-fields pattern

A required field with no escape hatch produces confabulation — chapter 9's point, and it bites hardest on documents. Adding unreadable_fields: list[str] gives the model a legitimate place to express uncertainty about a smudged total instead of inventing a plausible one. Pair it with an arithmetic cross-check in code and you have converted a silent data-corruption risk into a routing decision.

1 · Run the existing prompt unchangedGet the baseline on the new model before touching anything. Sometimes it is already better
↓
2 · Read twenty failuresThey cluster. Usually two or three causes, not twenty
↓
3 · Delete the compensations firstRepeated rules, CoT instructions, quirk workarounds. Re-measure after each
↓
4 · Fix provider-specific mechanicsPrefill, JSON mode, tag conventions, sampling parameter scales
↓
5 · Re-run the adversarial sliceSafety behaviour differs between models, in both directions
↓
6 · Compare cost and latency, not just qualityThe new model may be better and slower, or worse and a third of the price
An upgrade within the same family is still a migration

Teams treat a point release as a config change. It is not: verbosity, refusal thresholds, format adherence, tool-calling eagerness and reasoning depth all move between versions, none of it in the release notes. Run the full eval suite including the adversarial slice, compare cost and p95 latency, and roll out behind a flag. Pin versions in production (chapter 11) so this happens when you choose rather than when the provider retires an alias.

Writing portably from the start

  • Separate the task from the mechanics. Task definition, contract and examples in the prompt file; prefill, JSON mode and sampling in the adapter.
  • Keep a model matrix. The same eval set against two or three models, run monthly. It costs little and it means a migration decision takes an hour instead of a fortnight.
  • Annotate compensations. A comment marking "rule 9 exists because model X drops the second clause" tells the next person exactly what to try deleting.
  • Avoid depending on defaults. State the length, the format and the register rather than relying on a model's habits.
  • Prefer structural constraints to stylistic ones. A schema transfers; "be concise" is interpreted differently by every model.
  • Re-run the ablation after switching. Sections that earned their tokens on the old model may now be dead weight (chapter 13).

Where this unit ends

Fourteen chapters from one claim: the model is continuing your text, not obeying it. Everything since has been a consequence — examples beat descriptions because an example is the pattern; negations misfire because there is no "not" operator; structure beats adjectives because structure conditions and adjectives mostly do not; and a prompt cannot supply knowledge, capability or guarantees because it only ever moves probability around.

The techniques will date. Reasoning models have already inverted half of chapter 7, and the next generation will invert something else. What will not date is the habit the later chapters are really about: treating a prompt as a production artefact with a version, a test suite, a cost and a measured failure rate. That is what separates prompt engineering from prompt opinions, and it is entirely independent of which model you are pointed at.

The next step is not more reading. Take one prompt you already run, write twenty cases against it, and find out what its actual pass rate is. Most people are surprised, and the surprise is where the work starts.

The short version

  1. Structural things transfer; compensations do not. For each rule, ask whether it describes the task or patches a behaviour.
  2. Prompts for reasoning models get shorter. Delete the "how", keep the "what" — over-specified method fights the model.
  3. Smaller models need more examples, flatter schemas, one task per call — and a re-test of the refusal path, which degrades silently.
  4. Multimodal: evidence first, question last, label multiple images, and never trust a chart value or a count above five.
  5. Give the model an unreadable-fields escape hatch, and cross-check arithmetic in code.
  6. Migrate by running unchanged first, then deleting compensations before adding anything.
  7. A point release is a migration. Full suite, adversarial slice, cost and latency, behind a flag.
  8. Write portably: task in the prompt file, mechanics in the adapter, and keep a model matrix so the next decision takes an hour.
