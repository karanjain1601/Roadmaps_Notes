Chapter 08 · Reliable output

Structured output

The moment a model's output is consumed by code rather than read by a person, "usually well-formatted" stops being good enough. Getting from a tendency to a guarantee is a stack of four techniques, and only the top one is actually a prompting technique.

schemas json mode constrained decoding repair

Four levels of guarantee

LevelMechanismGuaranteesTypical failure rate
1 · Ask nicely"Reply with JSON matching this shape"Nothing. A strong tendency1–8%, and it spikes on unusual inputs
2 · Ask nicely, plus a prefillStart the assistant turn with {Still nothing, but far fewer preambles0.5–3%
3 · JSON modeProvider constrains output to valid JSONIt parses. Not that it matches your schemaParse: ~0. Schema: 1–5%
4 · Constrained decodingTokens outside the grammar are masked at each stepStructurally valid against your schemaStructure: ~0. Content still needs checking
Note what none of these guarantee: that the values are correct. Level 4 stops the model returning "severity": "quite bad". It does not stop it returning "high" when the answer was "low".
Use the strongest level available, then validate anyway

Constrained decoding is a solved problem where your provider or serving stack supports it — take it. But every level still needs a validation step in your code, because structural validity and semantic correctness are different things, and the second is where your bugs will be. The prompt work in this chapter is about making the content right; the mechanism handles the shape.

the same schema, three ways
from pydantic import BaseModel, Field
from typing import Literal

class TicketLabel(BaseModel):
    category: Literal["billing.duplicate_charge", "billing.refund_delay",
                      "delivery.not_received", "delivery.damaged",
                      "product.fault", "account.access",
                      "feedback.praise", "other.unintelligible"]
    severity: Literal["none", "low", "medium", "high"]
    order_ref: str | None = Field(default=None, pattern=r"^NW-\d{4}$",
        description="Only if a reference appears verbatim in the ticket. Never infer one.")
    reasoning: str = Field(max_length=200,
        description="One sentence naming the evidence for the category.")

# A. Schema enforced by the provider — strongest, use where available.
resp = client.responses.parse(model=MODEL, input=messages, text_format=TicketLabel)
label = resp.output_parsed

# B. JSON mode — valid JSON guaranteed, schema is not.
resp = client.chat.completions.create(model=MODEL, messages=messages,
                                      response_format={"type": "json_object"})
label = TicketLabel.model_validate_json(resp.choices[0].message.content)

# C. Local model with a grammar — same guarantee as A, self-hosted.
resp = llm(prompt, extra_body={"guided_json": TicketLabel.model_json_schema()})

Field design is prompt engineering

The schema is part of the prompt. Field names, types, descriptions and ordering all condition the output, and most structured-output problems are schema problems wearing a costume.

RuleInstead ofPrevents
Enums over free stringscategory: strEleven spellings of the same label. This is the single biggest win

Reasoning before the answer

Field order matters because generation is sequential. If category comes before reasoning, the model commits to a label and then writes a justification for it — and the justification will be fluent whether or not the label was right. Put the reasoning first and it genuinely informs the choice.

the ordering that costs nothing and helps measurably
# Weaker: label first, rationalisation after.
class Bad(BaseModel):
    category: Literal[...]
    reasoning: str

# Better: evidence, then conclusion. The category token is now generated in a
# context that already contains the analysis.
class Good(BaseModel):
    evidence: str = Field(max_length=200,
        description="Quote the phrase in the ticket that determines the category.")
    category: Literal[...]
    severity: Literal[...]

# Requiring a QUOTE rather than a summary is what makes this work. A summary can
# be written to fit any label; a quotation has to actually exist in the input,
# which you can then verify in code.

Validate, then repair

extract.py — the loop that handles the tail
def extract(ticket: str, max_attempts: int = 2) -> TicketLabel:
    messages = build(ticket)

    for attempt in range(max_attempts + 1):
        raw = call(messages, temperature=0)

        try:
            label = TicketLabel.model_validate_json(raw)
        except ValidationError as e:
            if attempt == max_attempts:
                metrics.incr("extract.gave_up")
                return TicketLabel.fallback(reason="unparseable")
            # Feed the actual error back. The model fixes what it can see.
            messages += [{"role": "assistant", "content": raw},
                         {"role": "user", "content":
                          f"That did not validate: {summarise(e)}. "
                          f"Return corrected JSON only, no commentary."}]
            metrics.incr("extract.structural_retry")
            continue

        # Structure is fine. Now check the things a schema cannot express.
        problems = semantic_checks(label, ticket)
        if not problems:
            return label
        if attempt == max_attempts:
            metrics.incr("extract.semantic_gave_up")
            return label.flagged(problems)
        messages += [{"role": "assistant", "content": raw},
                     {"role": "user", "content":
                      "Problems with that answer: " + "; ".join(problems) +
                      ". Return corrected JSON only."}]
        metrics.incr("extract.semantic_retry")

    return TicketLabel.fallback(reason="exhausted")


def semantic_checks(label: TicketLabel, ticket: str) -> list[str]:
    out = []
    # The check that catches the most damaging error: an invented reference.
    if label.order_ref and label.order_ref not in ticket:
        out.append(f"order_ref {label.order_ref} does not appear in the ticket")
    if label.evidence and label.evidence.strip('"') not in ticket:
        out.append("evidence is not a verbatim quotation from the ticket")
    if label.category == "other.unintelligible" and len(ticket.split()) > 30:
        out.append("a 30+ word ticket is unlikely to be unintelligible; re-read it")
    if label.severity == "high" and label.category.startswith("feedback."):
        out.append("feedback cannot be high severity")
    return out
The repair rate is a metric, not a solution

A repair loop hides failures, which is exactly the danger. If 15% of calls need a retry, you are paying 15% more, adding latency to that tail, and — more importantly — the prompt has a problem the loop is papering over. Alert on the rate. A sudden rise usually means a model version changed, an input distribution shifted, or someone edited the schema. Treat the repair loop as a safety net, and treat needing it often as a bug.

What a schema cannot express

These all need code. They are also where the errors that reach production live, because everything structural was caught upstream.

CheckExample
GroundingEvery identifier, figure and quotation must appear in the input
Cross-field consistencyseverity: high is incompatible with category: feedback.praise
ArithmeticLine items must sum to the stated total
Referential integrityThe order id exists, and belongs to this customer
PlausibilityA date in 2029, a refund larger than the order value
CompletenessThe ticket mentions three issues and only one was captured

Streaming structured output

ApproachTrade-off
Do not streamSimplest, and usually right. Structured output is consumed by code, which cannot use a partial object
Stream, buffer, parse at the endYou get a progress signal without partial-parse complexity
Incremental parsingRender fields as they complete. Needs a tolerant parser and careful UI. Worth it only when a human is watching
Split the callStream the prose the user reads; make a separate structured call for the data your code needs. Often the cleanest answer

When not to use a schema

Structure hurts when

  • The output is genuinely prose a person reads
  • The schema is so elaborate the model spends its attention on shape rather than content
  • You are forcing categorical answers onto something genuinely continuous
  • Every field is optional — that is not a schema, it is a suggestion
  • You added a field "just in case" and nothing consumes it

Structure helps when

  • Code consumes the output
  • You need to evaluate it automatically (chapter 12)
  • The task has a fixed set of outcomes
  • You want a place for uncertainty to live
  • You need to constrain what an injected instruction could produce (chapter 10)
Every field should have a consumer

Schemas grow the same way prompts do — by accretion. Someone adds sentiment because it might be useful, nothing ever reads it, and now every request pays tokens to produce it and every eval has to account for it. Once a quarter, grep for each field name in your codebase. Fields with no consumer get deleted. This usually shortens the schema by a third and measurably improves the fields that remain, because there is less to get right.

The short version

  1. Four levels of guarantee. Use the strongest your stack supports, and validate anyway — structure and correctness are different things.
  2. The schema is part of the prompt. Field names, types, descriptions and order all condition the output.
  3. Enums over free strings is the single biggest win.
  4. Put evidence before the answer, and require a verbatim quotation so you can verify it.
  5. Give the model an explicit place to be unsure, or it will confabulate to fill a required field.
  6. The grounding check — every identifier and figure must appear in the input — catches the most damaging errors.
  7. Alert on the repair rate. A loop that fires often is hiding a prompt problem.
  8. Prune the schema quarterly. Every field should have a consumer.
