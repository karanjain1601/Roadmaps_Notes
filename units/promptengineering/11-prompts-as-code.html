Prompts as code

A prompt is a production artefact with no type system, no compiler and no linter, whose behaviour changes when a dependency you do not control ships an update. That combination argues for more process around it than ordinary code, not less — and most teams give it none.

templates versioning review deployment

The three places prompts live, and two of them are wrong

LocationReality
An f-string in the middle of a functionWhere most start. No version, no diff that reads well, no way to test it independently, and impossible to find. Fine for a spike
A row in a database, edited through a UINon-engineers can change production behaviour with no review, no test run and no rollback. This causes incidents
Files in the repository, loaded at startupThe right answer for nearly everyone. Diffs, review, CI, rollback and blame all work exactly as they do for code
If it can change production behaviour, it goes through review

The argument for a prompt-editing UI is that non-engineers should be able to iterate. That is a good goal and it is achievable without giving them a direct write path to production: let them edit in a playground, run the eval set, and open a pull request. The friction people object to is mostly the review, and the review is the part that catches the change that quietly broke the refusal path.

Layout

prompts/ — a structure that scales past three prompts
prompts/
  ticket_triage/
    v3.md                 # the current prompt, plain markdown
    v2.md                 # kept: you will want to compare, or revert
    examples.yaml         # few-shot examples as data, not embedded in the string
    schema.py             # the Pydantic model, next to the prompt that produces it
    meta.yaml             # model, sampling params, owner, changelog
    evals/
      cases.jsonl         # golden set for this prompt specifically
      adversarial.jsonl   # injection and abuse cases, zero tolerance
  reply_draft/
    ...
  registry.py             # loads, validates and hashes everything above
meta.yaml — everything needed to reproduce a result
id: ticket_triage
version: 3
owner: support-platform
model: provider:model-name-2026-01-15      # pinned. never a floating alias
params:
  temperature: 0
  max_tokens: 400
schema: schema.TicketLabel
examples: examples.yaml
eval_threshold:
  accuracy: 0.91
  refusal_accuracy: 0.95
  adversarial: 1.0                          # no tolerance
changelog:
  - v3: added the unintelligible example; accuracy 0.89 -> 0.93 on the golden set
  - v2: moved the date into the user turn; cache hit rate 0.11 -> 0.78
  - v1: initial

The changelog is the part people skip and later need most. Six months on, nobody remembers why the date moved, and someone will helpfully move it back — into the system prompt, where it reads more naturally and costs thousands (chapter 3). One line per version prevents that.

Templating

registry.py — strict rendering, stable hashing
import hashlib, yaml
from jinja2 import Environment, StrictUndefined, FileSystemLoader

env = Environment(
    loader=FileSystemLoader("prompts"),
    undefined=StrictUndefined,      # a missing variable raises, never renders "None"
    trim_blocks=True,
    lstrip_blocks=True,
    keep_trailing_newline=True,     # whitespace stability matters for caching
)

class Prompt:
    def __init__(self, pid: str):
        self.meta = yaml.safe_load(open(f"prompts/{pid}/meta.yaml"))
        self.template = env.get_template(f"{pid}/v{self.meta['version']}.md")
        self.examples = yaml.safe_load(open(f"prompts/{pid}/{self.meta['examples']}"))
        self.raw = self.template.render.__self__.source if False else None
        self.hash = self._hash(pid)

    def _hash(self, pid: str) -> str:
        """Hash the template, examples and params together. Two prompts with the
        same hash produced the same behaviour; that is what makes eval results
        comparable across runs and across months."""
        h = hashlib.sha256()
        h.update(open(f"prompts/{pid}/v{self.meta['version']}.md","rb").read())
        h.update(yaml.safe_dump(self.examples, sort_keys=True).encode())
        h.update(yaml.safe_dump(self.meta["params"], sort_keys=True).encode())
        h.update(self.meta["model"].encode())
        return h.hexdigest()[:12]

    def render(self, **vars) -> str:
        return self.template.render(examples=self.examples, **vars)


PROMPTS = {pid: Prompt(pid) for pid in discover("prompts")}   # validated at startup
StrictUndefined is not optional

Default Jinja renders a missing variable as an empty string. Your prompt then says Answer using only the sources below: followed by nothing, and the model — reasonably — answers from general knowledge. The output is fluent, plausible and completely ungrounded, and nothing in your logs indicates a bug. StrictUndefined turns that silent failure into an exception at render time. It is one constructor argument and it prevents a category of incident that is otherwise very hard to detect.

Reviewing a prompt change

Review checklist Tick what applies to the change in front of you. The verdict is about what could break, not about whether the wording reads well.

What makes prompt diffs hard

A one-word change can shift behaviour more than a hundred-line refactorEval results in the PR description, always. The diff is not the evidence
Prose diffs read as trivial even when they are notRequire the author to state the failing case that motivated the change

serving a version, and recording which one ran
def triage(ticket: str, ctx: RequestContext) -> TicketLabel:
    version = flags.variant("prompt.ticket_triage", ctx.user_id)   # "v2" | "v3"
    prompt = PROMPTS["ticket_triage"].at(version)

    result = call(prompt.render(ticket=ticket), **prompt.meta["params"])

    # Every log line and trace carries the prompt hash. Without it you cannot
    # attribute a quality change to a deploy, and you will spend a day guessing.
    log.info("triage",
             prompt_id="ticket_triage", prompt_version=version,
             prompt_hash=prompt.hash, model=prompt.meta["model"],
             tokens_in=result.usage.input_tokens,
             tokens_out=result.usage.output_tokens,
             cached=result.usage.cached_tokens,
             finish_reason=result.finish_reason)
    return parse(result)
The prompt hash is the join key

Put it on every log line, every trace and every eval report. It is what lets you ask "what changed on the 14th?" and get an answer in one query rather than a git archaeology session. It also makes eval results honest: two runs with the same hash are comparable, two with different hashes are not, and a report without a hash is a number with no provenance.

Testing

tests that need no model at all
def test_renders_with_all_variables():
    """StrictUndefined catches missing variables — make sure the set is right."""
    out = PROMPTS["ticket_triage"].render(ticket="test")
    assert "{{" not in out and "{%" not in out

def test_prefix_is_stable():
    """Two renders with different inputs must share a byte-identical prefix,
    or prompt caching silently stops working."""
    a = PROMPTS["ticket_triage"].render(ticket="first")
    b = PROMPTS["ticket_triage"].render(ticket="second")
    prefix = os.path.commonprefix([a, b])
    assert len(prefix) > 1500, f"cacheable prefix collapsed to {len(prefix)} chars"

def test_no_secrets():
    for p in PROMPTS.values():
        body = p.source()
        assert not re.search(r"sk-|api[_-]?key|password|BEGIN PRIVATE", body, re.I)

def test_examples_validate_against_schema():
    """An example emitting a retired field teaches the model to emit it."""
    for ex in PROMPTS["ticket_triage"].examples:
        TicketLabel.model_validate_json(ex["output"])

def test_examples_are_not_in_the_eval_set():
    """Testing on what you demonstrated measures memorisation, not generalisation."""
    ex_inputs = {e["input"] for e in PROMPTS["ticket_triage"].examples}
    for case in load_cases("ticket_triage"):
        assert case.input not in ex_inputs

All five run in milliseconds with no API calls, and each catches a real failure that would otherwise surface in production. The prefix-stability test in particular has saved teams from silently losing a cache discount they were still budgeting for.

Ownership

  • Every prompt has a named owner in its metadata, and that person reviews changes to it.
  • Non-engineers propose, engineers merge. A playground that opens a PR with eval results attached gets you both iteration speed and a gate.
  • Model upgrades are prompt changes. Run the full suite; expect to adjust. A prompt tuned around one model's quirks may be actively counterproductive on the next.
  • Deprecate old versions deliberately. Keep two back for comparison and rollback; delete the rest, or the directory becomes a graveyard nobody trusts.
  • Review the whole prompt quarterly, not just the diff. Accretion is invisible in diffs and obvious when you read the thing from the top.
  • Record what you tried and rejected. Otherwise the same idea gets re-proposed every six months and re-tested at full cost.

The short version

  1. Prompts belong in files in the repository — so diffs, review, CI, rollback and blame all work as they already do.
  2. A prompt-editing UI is fine for iteration; it must not be a direct write path to production.
  3. StrictUndefined always. A missing variable rendering as empty produces confident ungrounded answers with no error.
  4. Hash the template, examples, params and model together. That hash is the join key for every log and eval report.
  5. The diff is not the evidence — eval results go in the PR, and the author states the failing case that motivated the change.
  6. Annotate each rule with its origin, or nobody will ever dare delete one.
  7. Serve prompt versions behind a flag so rollback is a config change, and test that it works.
  8. Five model-free tests — renders, stable prefix, no secrets, examples validate, examples not in the eval set — catch real production failures in milliseconds.
