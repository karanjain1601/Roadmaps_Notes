A calculator, and two failed validations

Two attempts that proved nothing

The first raced each selector against a reference of known specificity, #r1#r2#r3. Every single race came back a win — which should have been the tell, because an element can only have one id, so that selector can never match anything. The reference rule never applied, so the test selector won by default every time and the validation was vacuous.

The second raced selectors pairwise, which is the right idea, against a fixture where they matched different elements: #i matched the wrapping div and p matched the paragraph, so 63 of 130 pairs "disagreed" for reasons that had nothing to do with specificity. That is exactly the mistake chapter 2 made when it first raced :not(#t) against an element with id="t", and the fix is the same: assert element.matches() before racing anything. With every selector matching one target, 132 of 132 ordered pairs agree.

What the unit measured about measuring

Roughly a third of the chapters contain a correction, and the pattern in them is consistent. A single observation is a hypothesis. Chapter 22's content-visibility reveal produced two different wrong conclusions from single readings before twenty runs per condition settled it. A test that always passes is broken. This chapter's first validation won every race because the reference selector could not match anything. Check that the thing you are measuring is the thing you think. Chapter 12's line-height inheritance test was defeated by the harness's own reset; chapter 23's colour scale read oklch numbers as RGB. And an unsupported declaration measures exactly like one with no effect — chapter 10's fit-content(300px) looked like a wrong answer until CSS.supports said it was never valid. None of these was found by inspection. All were found by a result that did not fit, and then taken seriously.

Check yourself

Self-check

  1. Why did the first specificity validation prove nothing?
    Because the reference selector was #r1#r2#r3, and an element can only have one id — so it could never match, the reference rule never applied, and every test selector won by default. All twelve races came back a win, which should itself have been the tell: a validation where nothing can fail is not a validation. The second attempt raced pairs, which is the right shape, against a fixture where the selectors matched different elements, so 63 of 130 pairs disagreed for reasons unrelated to specificity. The fix for both is one line: assert element.matches() before racing. Chapter 2 learned the same lesson when it first raced :not(#t) against an element with id="t".
  2. Why validate a calculator by ordering rather than by value?
    Because ordering is what specificity actually decides. A three-number tuple is an implementation detail of the comparison; what a browser does with it is pick a winner between two declarations. Racing every ordered pair — 132 of them for twelve selectors — tests the thing that matters, and it tests the tie-breaking rule at the same time, since equal specificity must go to whichever rule is written later. It also catches classes of error a value check misses: a calculator could be consistently wrong in a way that preserves ordering, which would be harmless, or right on individual values and wrong about how :is() composes, which would not. The pairwise sweep found zero disagreements, so the calculator can be trusted on a stylesheet it has never seen.
  3. What does a specificity distribution tell you that a total does not?
    Whether there is a ladder to climb. Measured on this unit's own stylesheet: 216 selectors, of which 35 are type-only, 112 sit at exactly one class, 67 use two or more, and 2 use an id. A file shaped like that has no escalation, so changing something means writing a rule later in the file rather than writing a more specific one — which is the property that keeps a stylesheet editable after a year. A total, by contrast, tells you almost nothing: a thousand selectors all at one class is healthy and fifty selectors with ids and !important is not. The useful follow-up question is where the outliers are, which is why the audit lists the two id selectors by name rather than just counting them.
  4. The two id selectors are both #prog. Is that a problem?
    No — it is the one case where an id is defensible. #prog is the reading-progress bar, a genuine singleton that exists exactly once per page and has no variants. The argument against ids in stylesheets is not aesthetic: an id is (1,0,0), which no number of classes can outrank, so any rule wanting to override it must also use an id or !important. That is a real cost when the element might be reused or themed, and no cost at all when it cannot be. The measurement is what makes the judgement possible: knowing there are exactly two, and that both are the same singleton, is a different situation from knowing there are forty spread across components — and both would report as "uses ids" in a lint rule.
  5. What would you check first in an unfamiliar stylesheet?
    The specificity distribution and the !important count, because together they say whether the file has been fought with. A long tail of high-specificity selectors and a pile of important declarations means past authors could not get their rules to apply and escalated — so any change you make will need to escalate too. After that: whether layers are used, since chapter 20 measured that layer order beats specificity entirely and unlayered styles beat every layer, which means an unlayered file cannot be lowered in priority without moving it into one. Then whether custom properties are used semantically or as raw values, which chapter 23 covered, because that determines whether theming is a variable change or a rewrite.
  6. What is the single most useful habit this unit demonstrates?
    Turning a claim into a question with an answer the browser can give. "Layout was skipped" becomes "does the section report 200px or 400px". "This selector is more specific" becomes "which colour wins when both rules are present". "This is hidden from screen readers" becomes "is it in the accessibility tree". Each substitution replaces a judgement with a reading, and the readings are repeatable where the judgements are not. The second habit is treating a surprising result as information rather than as noise: chapter 3's getComputedStyle().width, chapter 20's !important inversion and chapter 6's containing-block resolution all began as failed assertions where the measurement was right and the expectation was wrong.
  7. What does the unit's correction rate suggest about writing CSS from memory?
    That it is unreliable in a specific way: the wrong beliefs are confident, plausible and rarely contradicted by everyday work. Roughly a third of these chapters contain a correction, and none of the corrected beliefs was exotic — that a percentage line-height inherits relatively, that !important unlayered beats !important layered, that an absolute element positions inside the padding, that fit-content() works as a width. Each is the kind of thing that produces a slightly wrong layout you then work around, rather than an error you notice. The practical conclusion is not to memorise more but to keep the cost of checking low: a scratch file, a devtools panel and the habit of asking rather than assuming turns a half-hour of confusion into a ten-second reading.
