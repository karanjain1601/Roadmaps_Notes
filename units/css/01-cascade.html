How a declaration wins

Two rules both set color. Exactly one applies. The browser decides by asking five questions in a fixed order, and specificity — the thing everyone reaches for first — is only the fourth. Getting the order right explains almost every "why is this not applying" moment.

The five questions

How this unit measures

Every figure in this unit was produced by loading real markup into Chromium 141 and reading getComputedStyle or an element's actual box. Nothing is quoted from a specification without being run. One honest limit, stated once and repeated where it matters: only Chromium is installed here, so these are Chromium measurements rather than cross-engine ones. The cascade, specificity and the box model are areas where engines agree closely; where a property is known to differ, the chapter says so rather than implying the measurement settles it.

!important and the escalation it starts

Reaching for !important works, which is the problem: it moves the declaration into a higher band where only another !important can reach it, so the next person to need an override has exactly one tool. A codebase with a hundred of them has effectively re-created the cascade one band up, with all the same conflicts and none of the structure. Two better instruments now exist. @layer lets you say "theme beats base" once, structurally, so a low-specificity theme rule can override a high-specificity base one without any importance at all — measured above. And :where(), from chapter 2, contributes zero specificity, so a library can ship defaults that anything at all can override. The legitimate uses of !important are narrow: utility classes whose whole purpose is to win, and overriding a third-party stylesheet you cannot edit.

Check yourself

Self-check

  1. In what order does the browser decide which declaration applies?
    Five questions, asked in this order. First origin and importance together — user-agent, user and author stylesheets, with the important variants of each ranked in reverse. Then cascade layer. Then specificity. Then source order. And finally, only if nothing matched at all, inheritance from the parent. The thing worth internalising is that specificity is the fourth question, not the first — measured, p { color: red !important } beat #t { color: green }, a type selector defeating an id, because importance was settled before specificity was consulted. The same happens with layers: a type selector in a later layer beat an id in an earlier one. So "the more specific rule wins" is only true when everything above specificity is equal, which in a codebase using layers or importance is often not the case.
  2. Why does !important invert the layer order?
    So that a base layer can force something a later layer cannot override. Measured: with two !important declarations in different layers, the one in the earlier layer won — the exact opposite of the normal rule, where a later layer beats an earlier one. It sounds perverse until you see the purpose. Layers are ordered from "most overridable" to "least", so a reset layer comes first and a theme layer last, and normal declarations let the theme win. But if the reset genuinely must not be overridden — an accessibility rule, a safety constraint — marking it important should make it stronger, not weaker, and inverting the order is what achieves that. The same inversion applies across origins for the same reason: a user's important stylesheet beats an author's important one, so a reader who needs larger text gets it.
  3. Unlayered styles and layered styles compete. Which wins?
    Unlayered, always — measured, a plain p selector beat an #t rule inside a layer. Unlayered author styles behave as though they were in a final layer added after every named one, so they are the most powerful normal author declarations available. This is a deliberate migration path: you can adopt @layer for a design system or a third-party stylesheet without touching your existing CSS, and your existing CSS keeps winning. It is also a trap in the other direction, because it means putting some of your styles in layers quietly demotes them beneath everything you did not move. The practical advice is to be wholehearted — either layer everything, with an explicit @layer reset, base, components, utilities; declaration at the top establishing the order, or layer only vendor CSS you are trying to tame.
  4. Two rules have identical specificity. What decides?
    Source order — the later one wins. Measured: .a { color: red } then .b { color: green } gave green, and reversing the two gave red, with the element carrying both classes. This is the last question, so it only comes up on an exact tie, but exact ties are extremely common in class-based CSS where nearly everything is (0,1,0). It has one consequence people trip over: the order of your @import or bundler entries changes which of two equally-specific rules applies, so a build that reorders files can change the rendering without any CSS having changed. Note that the order that matters is the order in the final stylesheet, not the order of the classes in the HTML class attribute — that has no effect whatsoever, which is a common misconception.
  5. How does inheritance differ from the cascade?
    It is a fallback rather than a competitor. Inheritance applies only where the cascade produced nothing at all for that element and property, so it never beats a matching declaration however weak — a * selector setting color defeats inheritance everywhere, which is why the universal selector is a blunt instrument. Only some properties inherit, and the split is roughly text against box: measured, color on a parent gave the child red, while border on a parent left the child's border at 0px. Text-ish properties — color, font-family, line-height, visibility, cursor — inherit; box-ish ones — border, padding, margin, display, background — do not. You can force either way with the global keywords, and inherit works on any property including non-inheriting ones.
  6. What do unset and revert do?
    unset means "inherit if this property inherits, otherwise use its initial value" — so it restores whichever default behaviour the property naturally has, which is usually what you want when clearing something. revert is different and more subtle: it rolls the property back to the value it would have had from the previous origin, so in author CSS it gives you the user-agent stylesheet's value rather than the property's spec initial. That distinction matters for elements the browser styles heavily. display: revert on a div gives block, because that is what the user-agent stylesheet says, while display: initial gives inline, because that is the property's spec initial — and inline is almost never what you meant. The blunt form is all: unset, most useful on button, where the user-agent stylesheet is opinionated enough to fight.
  7. When is !important actually the right tool?
    Two cases. Utility classes whose entire purpose is to win — a .hidden { display: none !important } that must work regardless of what a component sets — and overriding a third-party stylesheet you cannot edit. Everything else has a better instrument now. @layer expresses "theme beats base" structurally, once, so a low-specificity theme rule can override a high-specificity base rule with no importance at all, which the measurements above confirm. And :where() from chapter 2 contributes zero specificity, so a library can ship defaults that anything overrides trivially. The reason to care is escalation: an !important moves a declaration into a band where only another !important can reach it, so the next person needing an override has exactly one tool, and a codebase with a hundred of them has rebuilt the cascade one level up with none of the structure.
