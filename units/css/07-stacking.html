Stacking contexts and z-index

An element with z-index: 9999 can lose to one with z-index: 1, and adding zeros will never fix it. The reason is that z-index values are only ever compared within a stacking context — and ten ordinary declarations create one, several of which you would never suspect.

What creates one

Measured by hit-testing, not by looking

Every result below comes from document.elementFromPoint(60, 60) in a real browser — the same call the browser uses to decide what a click lands on, so it reports what is genuinely painted on top rather than what ought to be. The setup: a parent carrying the declaration under test contains a child with z-index: 9999; a sibling later in the DOM has z-index: 1. If the parent created a stacking context the child is trapped inside it, and the sibling wins.

The escalation, and why the ceiling is not the problem

Something is behind something else, so you write z-index: 10. It still loses, so 100. Then 9999. Then 999999. If the second attempt did not work, no further zeros ever will — the values are not being compared, because the two elements are in different stacking contexts and the comparison is happening one level up between their ancestors. Measured, a 9999 child lost to a 1 sibling in eight of ten configurations. The diagnosis is to walk up from the element to the root looking for any of those ten declarations, which is quicker than it sounds because most are visible in devtools' computed styles. The fix is to raise the ancestor that owns the context, not the element; or, better, to sidestep the whole question with the top layer, where a <dialog> or [popover] renders above the entire document with no z-index at all.

Check yourself

Self-check

  1. How can z-index: 9999 lose to z-index: 1?
    If they are in different stacking contexts. z-index values are only ever compared between siblings within the same context, so a child at 9999 inside a context is trapped there — the browser compares the whole context as one unit against its siblings, using the context-creating ancestor's own z-index. Measured by hit test: with a parent creating a context, a z-index: 9999 child lost to a z-index: 1 sibling in eight of the ten configurations tested. The practical consequence is that adding zeros never helps: if 10 did not work, 999999 will not either. The diagnosis is to walk up the tree looking for a context-creating declaration, and the fix is to raise the ancestor that owns the context rather than the element inside it.
  2. position: relative and position: relative; z-index: 0 — what is different?
    The second creates a stacking context and the first does not — measured, and it is the least intuitive pair in CSS. With no z-index the computed value is auto, which participates in its parent's context without creating one; with z-index: 0 it creates its own. The two are identical for every positioning purpose and differ entirely for stacking. This causes a specific and common bug: someone adds z-index: 0 to a card "just to be safe", and every absolutely positioned dropdown inside it is now trapped. The same goes the other way — removing an apparently pointless z-index: 0 can fix a layering problem three levels down. If you want a context deliberately, isolation: isolate says so explicitly and has no other effect at all.
  3. Which stacking-context triggers have nothing to do with layering?
    Most of them. Measured as creating a context: opacity below 1, transform, filter, will-change, mix-blend-mode and contain: paint — none of which mentions stacking. That is what makes this class of bug so hard to trace: a fade-in animation setting opacity: 0.99 mid-transition, an animation library adding will-change, or a card with a drop-shadow filter, all silently change how every descendant's z-index is compared. It overlaps heavily with chapter 6's containing-block list and is not identical: transform, filter and will-change do both, while opacity creates a stacking context and not a containing block, and position: relative does the reverse. Knowing which list a symptom belongs to — where something is, or what it is on top of — narrows the search quickly.
  4. What happens to z-index on a static element?
    Nothing at all. Measured: a static box with z-index: 9999 lost to a positioned box with z-index: 1. The property applies only to positioned elements — and, since a later addition to the specification, to flex and grid items, which is a genuine exception worth knowing because it means a flex child can use z-index without being positioned. Everywhere else it is a silent no-op, like chapter 6's offsets on a static element: valid syntax, correct property for the element, computes fine, does nothing. The fix is to add position: relative, which changes nothing visually but makes the element positioned — though note that combination then also creates a stacking context if the z-index is anything other than auto.
  5. Two elements overlap and neither has a z-index. Which is on top?
    It depends on the band before it depends on document order. Within one stacking context the painting order runs roughly: the context's own background, then negative z-index, then in-flow block boxes, then floats, then inline content, then positioned elements with z-index: auto, then positive z-index. Only within a band does document order decide. So two static blocks give the later one — measured, b on top — but a positioned element beats a later static one, measured as a on top even though b came second in the markup. No amount of DOM reordering fixes that, because they are in different bands. And a float paints above a static block's background, which is exactly why wrapped text sits beside a floated image rather than under it.
  6. You add z-index: 10, then 100, then 9999, and it still does not work. What now?
    Stop adding zeros — if the second value did not help, no larger one will, because the numbers are not being compared. Walk up from the element to the root looking for any of the ten context-creating declarations, which is quicker than it sounds since most show up in devtools' computed styles. Then fix it at the right level: raise the ancestor that owns the context rather than the element, so .card.is-open { z-index: 10 } instead of putting a large number on the dropdown inside. If the ancestor's context is genuinely needed, the element has to leave the subtree — historically by portalling it to document.body with JavaScript, and now by using the top layer instead, where a <dialog> or a [popover] renders above the whole document with no z-index involved at all.
  7. How should a codebase manage z-index values?
    With a small named scale and deliberate isolation. Define the layers once as custom properties — --z-dropdown: 10; --z-sticky: 20; --z-modal: 30; --z-toast: 40 — so the ordering is written down in one place and a new value is a decision rather than a guess. Values in the single or double digits are plenty, because z-index only compares siblings; anything larger is a sign that someone was fighting a stacking context. Then use isolation: isolate on self-contained widgets on purpose, so their internal layering cannot leak upward and nothing outside can slip between their parts — it creates a context with no other effect, which is precisely what you want. And for anything that must sit above everything — modals, toasts, tooltips — use the top layer instead of a number.
