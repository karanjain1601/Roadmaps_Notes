Chapter 10 · Layout systems

Sizing and intrinsic dimensions

Underneath every layout system are three questions about content: how narrow can this get, how wide would it like to be, and what should it settle for. min-content, max-content and fit-content answer them by name — and one of the five values tested here turned out to be silently dropped.

The sizing keywords

Support was checked before the width was measured

An unsupported declaration is dropped and the element sizes as auto — which measures identically to several of the values below and looks exactly like a wrong answer. So every value was passed through CSS.supports first. That caught one: fit-content(300px) is not valid as a width in Chromium 141, though it is valid as a grid track size. Without the check it would have appeared in this chapter as a value that mysteriously does nothing.

.cell  { width: min-content }        /* as narrow as the content allows        */

width: clamp(20ch, 50%, 60ch);       /* min, preferred, max — chapter 19  */

One rule, three syntaxes

The automatic minimum size has now appeared three times in three chapters, and it is worth naming as a single idea: CSS will not let content be crushed smaller than it can render, unless you say so explicitly. A flex item stayed 617px in a 300px container until min-width: 0. A grid track took 308px of a 400px grid until minmax(0, 1fr). An aspect-ratio box grew to 400px tall until overflow: hidden. Different properties, different syntax, one behaviour — and in every case the fix is either an explicit zero minimum or an overflow other than visible, because a scroll container is expected to clip rather than to be sized by its content. Recognising the pattern turns three separate memorised workarounds into one rule with three spellings.

Check yourself

Self-check

  1. What are min-content, max-content and fit-content?
    Three answers to three questions about the same content. min-content is the narrowest the box can be without its content overflowing — measured at 328px, which is exactly the width of the one long unbreakable word in the test string. max-content is how wide the content would like to be with no wrapping at all — measured at 520px, overflowing the 500px parent, because it ignores the available space entirely. fit-content is min(max-content, available) — measured at 500px, wanting 520 and settling for what there was. That last one is the "shrink to fit" behaviour a float, an inline-block or a flex item already has by default, which is why the keyword mostly appears when you want that behaviour on a block-level element.
  2. Why did fit-content(300px) measure 500px?
    Because it is not a valid width value in Chromium 141 — CSS.supports("width", "fit-content(300px)") returns false, the declaration is dropped, and the element sizes as auto, which for a block is 500px. The bare keyword fit-content is supported for width, and the function form with an argument is supported as a grid track size, where grid-template-columns: fit-content(300px) 1fr works exactly as you would expect. The reason this is worth its own answer is the failure mode: a silently dropped declaration measures identically to a value that has no effect, so it looks like a CSS bug rather than an unsupported syntax. Checking CSS.supports before measuring is what distinguished the two, and it is a habit worth having whenever a declaration appears to do nothing.
  3. auto gave 500px here. Is that always what it means?
    No — auto means two different things depending on the box. On a block-level element in normal flow it fills the container, which is what produced the measured 500px. On a float, an inline-block, an absolutely positioned element or a flex item, auto behaves like fit-content: shrink to fit, capped by the available space. Same keyword, two rules, chosen by context — which is a large part of why display changes feel like they change sizing "for no reason". Chapter 4 measured the pair directly: a block with width: auto came out at 500px and an inline-block at 10px, its content width. The practical takeaway is that if you want shrink-to-fit on a block, say fit-content rather than relying on a display change to get it as a side effect.
  4. aspect-ratio: 16/9; width: 300px; height: 100px. What happens?
    The ratio is ignored and the box is 300×100 — measured. aspect-ratio computes whichever dimension you did not specify: with only a width it gave 300×169, and with only a height it gave 178×100. Given both, there is nothing left to compute, and the explicit values win. That is the sensible design, and it makes the property easy to use in one direction — set a width, get the height — while quietly doing nothing if a stylesheet elsewhere also sets a height, which is a plausible way to be confused by it. The related thing worth knowing is that it replaces the old padding-top percentage hack entirely, and unlike that hack it works on the block axis as well, so height: 200px; aspect-ratio: 1 gives a square 200px wide.
  5. Content taller than the ratio stretched the box to 400px. Why, and how do you stop it?
    Because aspect-ratio is a suggestion, not a constraint: the automatic minimum size means a box will not be smaller than its content can render, so a 400px child stretched a 300×169 box to 300×400. Measured. overflow: hidden restored the ratio to 300×169, and min-height: 0 would too. That is the third appearance of the same rule in three chapters — chapter 8's flex item stayed 617px in a 300px container until min-width: 0, and chapter 9's grid track took 308px of a 400px grid until minmax(0, 1fr). Three properties, three syntaxes, one behaviour: CSS refuses to crush content below what it can render unless you say so explicitly, and the escape is always either an explicit zero minimum or a non-visible overflow.
  6. Where are the sizing keywords most useful?
    In grid track lists, where they replace guesswork with a statement of intent. grid-template-columns: max-content 1fr gives a first column exactly as wide as its longest row needs and no wider, which is what a label column or an icon column actually wants — and it adapts when the content changes, where a hard-coded 140px does not. min-content is useful for a column that should be as tight as possible, and fit-content(300px) — valid here even though not as a width — caps a content-sized track. Outside grid the most common use is width: max-content on a tag or badge so it never wraps however narrow its container, and width: fit-content with margin-inline: auto to centre a block that should be only as wide as its content.
  7. How do vh, dvh, svh and lvh differ?
    They differ in what they do about mobile browser toolbars that appear and disappear as you scroll. lvh is the largest viewport, with the toolbars retracted; svh is the smallest, with them showing; dvh is dynamic and tracks the current state; and vh is defined as equal to lvh, which is why height: 100vh on a mobile hero has always been slightly too tall and hidden the bottom of the content behind the toolbar. So 100dvh is usually what people meant, at the cost that it changes as the user scrolls and can cause a reflow — which is why a fixed 100svh is sometimes better for anything that must not move. The same four exist for every viewport unit, and there are logical equivalents in dvi and dvb for writing-mode-relative sizing.
