Backgrounds, borders and shadows

Decoration divides cleanly into two groups: things that are part of the box and things that are only painted. Six of the eight declarations measured here changed nothing about the layout at all — and one of them, border-radius, changed where a click lands.

background-clip: padding-box   /* stop the background under a dashed border */
background-clip: text          /* gradient text, with -webkit- for older engines */

/* a shadow with no blur is a second border that costs no layout */
box-shadow: 0 0 0 2px var(--ring);
box-shadow: inset 0 1px 0 #fff3;              /* inner highlight */

/* the two shadows differ in what they follow */
box-shadow:      0 2px 8px #0003;   /* the BORDER BOX, rounded corners and all */
filter: drop-shadow(0 2px 8px #0003); /* the ALPHA SHAPE — use for PNGs and SVGs */

/* elliptical corners, and the safe pill */
border-radius: 50% / 20%;      /* horizontal / vertical radii */
border-radius: 9999px;         /* clamped — see the measurements */

border-radius, measured by hit test

Why hit-testing

A rounded corner is a shape rather than a style, and the way to measure a shape is to ask what is inside it. Each row below applies a radius to a 200×200 box and then calls document.elementFromPoint at two places: the very corner at (4, 4), and a point at (20, 20) that is inside a gently rounded rectangle and outside a circle inscribed in the box. The browser's own hit-testing answers both.

The corners are scaled proportionally, all at once
If the sum of two adjacent radii exceeds the side, every radius is reduced by the same factor — so a box never ends up with corners that overlap.
Two shadows that are not interchangeable

box-shadow follows the border box, rounded corners included — so it draws a rectangle-shaped shadow behind a transparent PNG rather than following the artwork. filter: drop-shadow() follows the alpha shape, so it traces the actual silhouette of an image, an SVG icon or a clipped element, which is the only way to get a correct shadow on a non-rectangular thing. Both were measured as paint-only, so neither costs layout. They differ in what they cost to render: a filter processes the element's rasterised pixels and forces it onto its own compositing layer, which chapter 22 measures, while a plain unblurred box-shadow is close to free. The practical rule is box-shadow for boxes and drop-shadow for silhouettes, and if you find yourself wanting both on the same element, the element is probably two elements.

Check yourself

Self-check

  1. Which of border, outline and box-shadow affect layout?
    Only border, and even that depends on box-sizing. Measured, the element following the box stayed at exactly 40px for outlines, both shadow kinds and a transform — six of the eight declarations tested changed nothing about the layout at all. And under border-box the border took its space from the content rather than from outside, so offsetWidth also stayed at 100px, which is chapter 3's measurement seen from another angle. The practical consequence is the reason focus indicators use outline: a ring drawn with border shifts everything around it when focus arrives, and one drawn with outline cannot. outline-offset lets you push it away from the edge, still without touching layout.
  2. What does transform: scale(2) do to the two width readings?
    It splits them. Measured, getBoundingClientRect().width came back as 200px and offsetWidth as 100px — the visual box doubled and the layout box did not. Everything around the element behaved as though nothing had happened, which the measurement confirms: the following element stayed at 40px. That is by design, and it is what makes transforms cheap to animate, since nothing has to be laid out again — chapter 22. It also means a scaled element overlaps its neighbours rather than pushing them, and that any code measuring "how wide is this" needs to know which question it is asking. Chapter 3 listed four width readings; this is the case where the difference between two of them is unmissable.
  3. Why is (4, 4) outside a rounded element?
    Because border-radius changes the element's shape, and hit testing follows the shape rather than the bounding rectangle. Measured with document.elementFromPoint: with any radius applied, the point at (4, 4) resolved to body rather than to the element — so a click in the very corner passes through to whatever is behind. That is correct and occasionally surprising: a rounded button has a slightly smaller clickable area than its box, and stacking a rounded card over an interactive element leaves four small holes at the corners. It also means hit testing is a legitimate way to measure a shape, which is how every row in that demo was produced — the browser's own answer to "what is here", rather than an inspection of the style.
  4. What happens to border-radius: 9999px on a 200px box?
    It is clamped to a circle — measured, 200px, 50% and 9999px all produced the identical shape, with both probe points giving the same answers. The specification says that if the sum of two adjacent radii would exceed the length of the side, every radius on the box is reduced by the same factor, so corners can never overlap and the box never becomes a strange shape. Reducing all of them by one factor rather than clamping each individually is what keeps an asymmetric radius looking deliberate rather than broken. The practical payoff is that border-radius: 9999px is a safe idiom for a pill of unknown height: it gives fully rounded ends at any size and cannot overshoot, which a computed half-height value would have to be recalculated for.
  5. When do you need filter: drop-shadow() rather than box-shadow?
    When the thing is not a rectangle. box-shadow follows the border box — rounded corners included — so on a transparent PNG or an SVG icon it draws a rectangular shadow around the whole image rather than tracing the artwork. drop-shadow follows the alpha shape, so it traces the actual silhouette, which is the only way to get a correct shadow on a clipped element or a non-rectangular graphic. Both were measured as paint-only, so neither costs layout. They differ in rendering cost: a filter works on the element's rasterised pixels and promotes it to its own compositing layer, where an unblurred box-shadow is nearly free — chapter 22. The rule of thumb is box-shadow for boxes and drop-shadow for silhouettes.
  6. In what order do multiple backgrounds paint?
    The first listed is on top, which is the opposite of the intuition most people bring from layer panels in design tools. So background: url(badge.svg), linear-gradient(#fff, #eee) puts the badge over the gradient. Only the last layer can have a background-color, because the colour always paints at the very bottom regardless of where you write it. Two related properties are worth knowing together: background-clip decides which box the background is painted within — padding-box stops it showing through the gaps in a dashed border, and text gives you gradient text — while background-origin decides which box the background is positioned against. They are easy to confuse and they answer different questions, one about the visible extent and one about the coordinate origin.
  7. How do you draw a second ring around an element without affecting layout?
    A box-shadow with no blur and a spread: box-shadow: 0 0 0 2px var(--ring) draws a solid 2px ring that follows the border radius exactly and costs no layout — measured, the following element did not move. Shadows stack, so 0 0 0 2px white, 0 0 0 4px blue gives the two-tone focus ring that stays visible on any background, which is chapter 21's recommended pattern. The alternative for a single ring is outline with outline-offset, which is also layout-free and which modern browsers now draw following the border radius too — historically outlines were always rectangular, which is why the shadow trick became common. Use outline for focus specifically, since some assistive and high-contrast modes preserve outlines and discard shadows.
