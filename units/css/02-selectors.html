Selectors and specificity

Anyone who has written "specificity 011 beats 100" has the wrong model, and it will mislead them exactly once per project.

Fifteen selectors, raced

How each weight was established

Not looked up — raced. Each selector was written first in the stylesheet against a rival written second, so if the first still won it is strictly more specific. Two rivals were used: .a.b[data-x] at (0,3,0) and #t at (1,0,0). Every selector was also checked with element.matches() first, because a selector that does not match tells you nothing — the first version of this table raced :not(#t) against a target with id="t", which it cannot match, and the result was meaningless. All fifteen results agree exactly with the three-number comparison.

The mental model to discard

Specificity is often taught as a three-digit number — "an id is 100, a class is 10, an element is 1, add them up". That model gives the right answer almost always, which is what makes it dangerous: it fails exactly when you have more than nine of something, and at that point it says (0,11,0) is 110 and therefore beats an id's 100. Measured, it does not, in either source order. The correct model is a tuple compared left to right, like version numbers — and thinking of it as 1.0.0 against 0.11.0 makes the answer obvious, since nobody expects version 0.11.0 to be newer than 1.0.0. Fifteen selectors were checked against that model here and all fifteen agreed. The practical consequence is the same either way: if you are counting past three, the problem is the architecture, not the arithmetic.

Check yourself

Self-check

  1. Eleven classes against one id. Which wins, and why?
    The id — measured, in both source orders. Specificity is three independent numbers compared left to right, not a score: (0,11,0) against (1,0,0) is decided in the first column, where 0 is less than 1, and the eleven is never looked at. The three-digit mental model — "an id is 100, a class is 10, add them up" — gives the right answer almost always, which is exactly what makes it dangerous, because it fails at ten of anything and says 110 beats 100. Thinking of specificity as a version number makes it obvious: nobody expects 0.11.0 to be newer than 1.0.0. The practical consequence is the same either way. If you are counting past three, the problem is the architecture rather than the arithmetic, and chapter 1's layers are the structural fix.
  2. What counts in each of the three columns?
    Ids in the first. Classes, attribute selectors and pseudo-classes in the second — so .a, [data-x], :hover and :first-child all weigh the same, which the measurements confirmed. Type selectors and pseudo-elements in the third, so div and ::before are equal. And nothing else counts at all: the universal selector * is (0,0,0), and so are the combinators >, +, ~ and descendant space — which is why div p and div > p have identical weight at (0,0,2). The single-versus-double-colon distinction is worth remembering because it is the one place the syntax tells you the column: one colon is a pseudo-class in the middle column, two is a pseudo-element in the last.
  3. What does :where() do, and when would you use it?
    It contributes zero specificity, always, whatever is inside it — measured, :where(#t, p) lost to three classes and to an id despite containing an id. It is the only way to write a selector with no weight. The use is defaults that should be trivially overridable: a component library writing :where(.btn) { padding: 8px } ships a sensible default that any single class in consuming code can override without a fight, which is a much better contract than !important or than hoping consumers out-specify you. It also solves the grouped-selector problem — :where(h1, h2, h3) > p keeps the weight at (0,0,1) rather than inheriting the heaviest branch. Its sibling :is() is the same syntax with the opposite rule: it takes its most specific argument, so :is(#t, p) weighs (1,0,0), which the measurement confirmed.
  4. How much specificity does :not(.a) contribute?
    The specificity of its most specific argument — so (0,1,0) for :not(.a), and (1,0,0) for :not(#zzz), which the measurement confirmed by beating three classes. The :not() itself adds nothing; only what is inside it counts. That is worth knowing because it makes :not() a quiet source of weight: .card:not(#modal) looks like a class selector and weighs as much as an id. It is also the basis of a known hack — .btn:not(#\9) adds one id of weight deliberately, matching everything since no element has that id — which you will see in older codebases and should recognise rather than imitate. Modern :not() accepts a list, and the rule still applies: the heaviest argument sets the weight.
  5. Two rules both have specificity (0,1,0). What decides?
    Source order — the later one wins, which is chapter 1's fourth question. Measured: .a then .b gave green, and reversing them gave red, on an element carrying both classes. The important corollary is that the order of the classes in the HTML class attribute has no effect whatsoever, which is a common misconception — class="b a" and class="a b" render identically. Only the order in the stylesheet matters. This is more consequential than it sounds in class-based CSS, where nearly everything is (0,1,0) and therefore nearly every conflict is settled by file order. A bundler that reorders imports, or a lazily-loaded stylesheet arriving later than expected, can change the rendering with no CSS having changed — which is one of the arguments for cascade layers.
  6. Why do design systems usually ban ids for styling?
    Because an id creates a weight nothing below it can reach. Once a rule is (1,0,0), no amount of classes will override it — measured, eleven classes lost — so a consumer's only remaining options are another id, an inline style, or !important, all of which escalate. Since ids must be unique in a document anyway, an id selector can only ever style one element, so it buys nothing that a class does not, and it costs the ability to override. The related habit is to keep selectors flat: a single class per rule, at (0,1,0), so that everything is comparable and source order or layers do the arbitration. Ids remain the right tool for their actual jobs — fragment links, label for, ARIA references, and JavaScript hooks — none of which involve the stylesheet.
  7. You need to override a third-party stylesheet you cannot edit. What are the options, best first?
    Put the vendor CSS in a cascade layer and yours outside it, which chapter 1 measured as beating every named layer regardless of what is inside — @import "vendor.css" layer(vendor); is one line and settles it permanently. Failing that, if you control load order, match their specificity and load later, since a tie falls through to source order. Then out-specify them by the smallest possible margin, adding one class rather than three, so the next person has room to move. And only then !important, which works and starts an escalation where the next override has exactly one available tool. Worth checking first whether the library exposes custom properties, since chapter 18's variables let you change values without competing on specificity at all — that is increasingly how well-built libraries expect to be themed.
