Typography

line-height: 1.5 and line-height: 150% compute to the same value on the element you write them on, and behave completely differently on its children — measured, 60px against 30px on a child with twice the font size. It is the clearest case in CSS of a unit changing what inherits.

What line-height inherits

A note on how this was measured

The setup is a parent at font-size: 20px containing a child at font-size: 40px, with the line-height set only on the parent. The first version of this test reported 60px for all four cases, because the harness's universal reset included font: 16px/1.5 — which sets line-height on every element directly and so defeats inheritance entirely. An inheritance test cannot use a reset that touches the property under test, which is obvious in hindsight and was not obvious while writing it.

Three of the four give the child 30px
All four give the parent 30px
1.5 × 20, 30px literal, 150% of 20, and 1.5em of 20. Identical on the element you write them on.
Only the unitless form recomputes for the child
Measured 60px — the child inherits the number 1.5 and multiplies by its own 40px font.
The other three inherit the computed length
All measured 30px on a 40px font, so the lines overlap. 150% and 1.5em behave exactly like 30px.
Which is why the advice is always "unitless"
A percentage looks relative and is resolved once, at the point of declaration. Nothing about the syntax warns you.
css — a typography baseline worth starting from
body {
  font-family: system-ui, sans-serif;
  line-height: 1.5;                    /* unitless, so headings recompute */
  text-wrap: pretty;                   /* no orphans in body copy         */
}
h1, h2, h3 { line-height: 1.15; text-wrap: balance }   /* even lines in headings */
p { max-width: 65ch }                                   /* measure tracks the font */

/* loading a webfont without a flash of invisible text */
@font-face {
  font-family: "Body"; src: url(body.woff2) format("woff2");
  font-display: swap;                  /* show the fallback immediately   */
  size-adjust: 105%;  ascent-override: 90%;   /* match metrics → no reflow */
}

/* the properties that actually improve readability */
hyphens: auto   ·   text-wrap: pretty   ·   font-variant-numeric: tabular-nums
letter-spacing: -0.01em    /* tighten large text, never small text */

The font-relative units

Measured at font: 32px Georgia, root 16px
Two of them look alike and are not
em is 32px and rem is 16px
The element's font size against the root's. The difference compounds when ems nest, which is the whole reason rem exists.
ch measured 16px — the advance of the digit zero
Which makes max-width: 60ch a measure that tracks the actual font rather than a pixel guess.
ex is 14.7px and cap is 21px
The x-height and the cap height, read from the font's own metrics. Both change with the typeface at the same font size.
lh is 37px — one line box
Useful for spacing that should align to the text's own rhythm, such as an inline icon or a vertical rule beside a quote.
Fonts and layout shift

A webfont is loaded after the first paint, so text is laid out twice: once in the fallback and once in the real font. font-display: swap makes the first paint visible rather than blank, which is nearly always right — but it means the reflow is visible too, and if the two fonts have different metrics every line rewraps and the page jumps. The fix is not to hide the text, it is to make the fallback measure the same: size-adjust, ascent-override and descent-override on an @font-face block for the fallback family let you match the webfont's metrics closely enough that swapping causes no shift at all. Tools generate the numbers by comparison. The other half is loading: <link rel=preload as=font crossorigin> for the one or two faces above the fold, subsetted, in WOFF2, and nothing else — every additional weight is another file blocking the same moment.

Check yourself

Self-check

  1. line-height: 1.5 against line-height: 150% — what is the difference?
    Nothing on the element you write them on, and everything on its children. Measured with a 20px parent, both computed to 30px there. On a 40px child, the unitless form gave 60px and the percentage gave 30px — text at double the size crammed into the original line box, so the lines overlap. A unitless value inherits as a number and each element multiplies it by its own font size; every other form inherits the computed length, resolved once at the point of declaration. 1.5em and a literal 30px behaved identically to the percentage, all three measuring 30px on the child. Nothing in the syntax warns you, and a percentage in particular looks relative, which is why the universal advice is to use unitless and why it is worth knowing the reason rather than the rule.
  2. Why do the lines overlap when a heading inherits a length line-height?
    Because the line box stays at the inherited size while the glyphs grow. Measured: a 40px child inheriting 30px gets a 30px line box for 40px text, so consecutive lines are closer together than the letters are tall and the descenders of one line collide with the ascenders of the next. It shows up most obviously on a heading that wraps, which is exactly where it is least acceptable. The value is not clamped or corrected — CSS lets the content overflow its line box, which is the same "content is never crushed but boxes can be smaller than content" territory as chapter 10's automatic minimum, seen from the other side. A unitless 1.5 on body avoids it everywhere at once, and headings usually want an explicit tighter value like 1.15 anyway.
  3. What does 1ch actually measure?
    The advance width of the digit zero in the current font — measured at 16px for 32px Georgia, exactly half the em. Not the average character width, and not the width of a typical letter, which is why 60ch is a rough proxy for sixty characters rather than a promise. In a monospace font it is exact, since every glyph has the same advance. What makes it valuable is that it tracks the font: max-width: 60ch gives roughly the same visual measure whether the typeface is narrow or wide, where max-width: 600px gives a different number of characters per line for each. Typography research generally puts comfortable body measure somewhere between 45 and 75 characters, so a ch-based cap encodes the intent rather than a guess.
  4. When would you use em rather than rem?
    When something should scale with its local text rather than the page. Measured, 1em was 32px and 1rem was 16px on the same element — the element's own font size against the root's. The classic em case is padding inside a button: padding: 0.5em 1em keeps the proportions right whether the button is small or large, with no size variants needed. The classic rem case is layout spacing and type scales, where you want one consistent rhythm regardless of local font size. The reason rem became the default is compounding: nested em-sized elements multiply, so three levels of 0.9em gives 73% and nobody intended that. And because the root size is what a reader's browser font setting changes, rem-based type respects that preference where px does not.
  5. What is font-display: swap trading away?
    Visual stability, in exchange for text being readable immediately. Without it the browser hides text for up to three seconds waiting for the webfont — a flash of invisible text, which is worse than the alternative on a slow connection. With it, the fallback paints straight away and is replaced when the real font arrives, so the reflow is visible: if the two fonts have different metrics, every line rewraps and the page jumps, which is a layout-shift problem as well as an ugly one. The fix is not to hide the text but to make the fallback measure the same, using size-adjust, ascent-override and descent-override on an @font-face block for the fallback family. Tools compute the numbers by comparing the two fonts, and a well-matched fallback makes the swap essentially invisible.
  6. What do text-wrap: balance and text-wrap: pretty do?
    Both improve line breaking, in opposite parts of the page. balance evens out the line lengths across a short block, so a three-line heading does not end with one word — it is intended for headings and pull quotes, and browsers cap it at a small number of lines because the algorithm is expensive. pretty is for body copy: it avoids orphans and improves the last few lines without rebalancing the whole paragraph, so it scales to long text. The practical pairing is text-wrap: balance on headings and text-wrap: pretty on body. Neither changes the content or the layout box, so both degrade to nothing where unsupported, which makes them safe to add unconditionally. They are worth mentioning alongside hyphens: auto, which helps most in narrow columns and in languages with long compounds.
  7. What should a typography baseline contain?
    Four things, all set once. A unitless line-height on body — measured above as the only form that recomputes for children — usually around 1.5 for body text, with headings tightened to about 1.15. A measure cap in ch, so line length tracks the font rather than a pixel guess. A font stack beginning with system-ui if you can accept it, since the fastest webfont is the one you do not load. And a scale rather than ad-hoc sizes, in rem so it respects the reader's browser font setting. Beyond that, text-wrap: pretty on body and balance on headings cost nothing and degrade cleanly, and font-variant-numeric: tabular-nums is worth remembering for anything showing figures in a column.
