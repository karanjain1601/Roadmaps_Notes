Display and normal flow

Set width: 100px on a <span> and nothing happens. Not a cascade problem, not a typo — an inline box discards width and height by definition. That single fact is behind a large share of "my CSS is not applying", and this chapter measures it alongside the five display values that behave differently.

Block formatting contexts

A container with one floated child
Six ways to fix it, five with side effects
A plain block collapses to zero around a floated child
Measured: an 80px float inside an ordinary div left the container at 0px tall. Floats are taken out of normal flow, so nothing measures them.
Establishing a block formatting context contains it
All six triggers measured 80px. A BFC is a self-contained layout region: floats inside it are measured by it, and margins do not collapse through it — chapter 5.
flow-root is the one with no side effect
It exists for exactly this. overflow: hidden also clips; display: flex also relays out the children; position: absolute also removes the container from flow.
Which is why the clearfix hack is obsolete
A pseudo-element with clear: both solved this for a decade. One declaration replaces it.
The inline-block gap, measured at 10px

Two inline-block boxes with a newline between them in the HTML sit 10px apart — measured, with the parent at font: 16px monospace. There is no margin anywhere; the gap is a space character, because whitespace between inline-level boxes is content, and its width is whatever a space is in the parent's font. Setting font-size: 0 on the parent closed it to 0px exactly, which is the fix that was standard for years and which breaks the moment a child inherits that zero. The other historical fixes were equally unpleasant: removing the newlines from the HTML, or commenting them out with </li><!--. The real answer is that this is a layout problem being solved with a text mechanism. Use display: flex and gap, where whitespace between children is ignored entirely and the spacing is a number you control.

Check yourself

Self-check

  1. You set width: 100px on a <span> and nothing happens. Why?
    Because a <span> is display: inline, and an inline box discards width and height by definition — measured, width: 100px; height: 40px produced a box 10px wide and 19px tall, exactly the size of its one character of text. An inline box is sized by its content and its font, because it participates in a line box alongside text rather than forming a rectangle of its own. This is the single commonest cause of "my CSS is not applying", and the tell is that the element is a span, an a, an em or a label. The fix is display: inline-block if it should still sit in a line, or block if it should not — and both honoured the same declarations in the measurement.
  2. An inline element has padding: 30px 0. What happens?
    It paints but does not push. Measured, the span drew 79px tall while its parent's line stayed 24px — so the padding renders, complete with background colour, and overlaps whatever is above and below rather than moving it. Horizontal padding on an inline box behaves normally and does affect layout; only the block direction is ignored. The same asymmetry applies to margins: margin-left and margin-right work on an inline box, margin-top and margin-bottom do nothing. The practical consequence is that a link styled as a button with generous vertical padding will overlap the lines around it in a paragraph, which looks like a broken layout and is correct behaviour. inline-block fixes it, at the cost of introducing the whitespace gap.
  3. What is the difference between block and inline-block when no width is set?
    A block fills its line; an inline-block shrinks to fit. Measured in a 500px container with width: auto, block came out at 500px and inline-block at 10px — the width of its content. That is the whole difference in the outer behaviour, and it is why a heading is full-width by default and a button is not. Both honour an explicit width identically. The two-value display syntax makes the underlying idea explicit: inline-block is really inline flow-root, meaning "behave as inline on the outside, lay out children as a self-contained block on the inside". Once you see it that way, display: block is block flow and display: flex is block flex — the outer and inner behaviours were always two separate choices sharing one property.
  4. Why does a container collapse to zero height around a floated child?
    Because a float is taken out of normal flow, so its parent does not measure it — measured, an 80px floated child left an ordinary div at 0px tall. That was deliberate in the original design, where floats existed to let text wrap around an image and the image was not supposed to stretch the paragraph. It became a problem the moment floats were repurposed as a layout system, which is what CSS did for roughly fifteen years. The fix is to make the container establish a block formatting context, a self-contained layout region that measures its own floats. Measured, six different declarations all achieved it and produced 80px: flow-root, overflow: hidden, overflow: auto, display: flex, position: absolute and float: left on the container itself.
  5. Which BFC trigger should you use, and why?
    display: flow-root, because it exists for exactly this and has no other effect. Every other trigger does something else as well, and that something is the cost. overflow: hidden also clips, so any child that meant to escape — a dropdown, a tooltip, a focus ring — is cut off, and it can also introduce scroll containers you did not intend. overflow: auto adds scrollbars. display: flex or grid relays out every child. position: absolute removes the container itself from flow. float: left moves the problem up a level. All six were measured as working, so the choice is entirely about side effects. And flow-root replaces the clearfix pseudo-element hack that solved this for a decade — one declaration instead of five, with no extra element in the box tree.
  6. Two inline-block boxes have a 10px gap and no margin. Where does it come from?
    From a space character. Whitespace between inline-level boxes is content, so the newline separating the two elements in the HTML renders as a space, and its width is whatever a space measures in the parent's font — 10px here at 16px monospace. Setting font-size: 0 on the parent closed it to exactly 0px, which was the standard fix for years and breaks the moment a child inherits that zero and has no size of its own. The other historical workarounds were removing the newlines or commenting them out with </li><!--, both of which make the markup worse to read. The real diagnosis is that this is a layout problem being solved with a text mechanism. display: flex with gap ignores whitespace between children entirely and makes the spacing a number you set.
  7. What are the differences between display: none, visibility: hidden and opacity: 0?
    How much of the element survives. display: none removes it from the box tree entirely — no space, no paint, and it is removed from the accessibility tree so screen readers do not announce it. visibility: hidden keeps the box and its space, paints nothing, and is also hidden from assistive technology; crucially it inherits, which chapter 1 measured, so a child can set visibility: visible and reappear inside a hidden parent — something impossible with display. opacity: 0 keeps everything: the space, the layout, the hit target and the accessibility tree, so the element is invisible but still clickable and still read out, which is a real bug when used for hiding. And none of the three is what you want for content that should be available to screen readers but not shown — that is the .visually-hidden pattern in chapter 21.
