The maths functions

clamp(200px, 50%, 400px) replaces two media queries with one declaration, and its behaviour is exactly max(min, min(preferred, max)) — measured at four container widths. The wider point is that CSS does real unit algebra: a length times a length is an area, and it is rejected rather than coerced.

css — where the functions earn their place

/* the responsive container, with no breakpoint */
width: min(100% - 2rem, 65ch);

Fluid type, and the accessibility trap in it

The obvious fluid-type expression is font-size: clamp(1rem, 2vw, 1.4rem), and the middle term is the problem. A pure viewport unit does not respond to the reader's browser zoom or default font size: someone who has set 24px as their base, or zoomed to 200%, still gets text sized by the window. Between the two clamp bounds the text is effectively unzoomable, which fails WCAG's requirement that text can be resized to 200%. The fix is to include a relative unit in the preferred value — clamp(1rem, 0.9rem + 0.5vw, 1.4rem) — so the expression still scales with the viewport and also scales with the reader's settings. The same caution applies to any vw-driven spacing that a reader might need to enlarge.

Check yourself

Self-check

  1. clamp(200px, 50%, 400px) in a 300px container. What width?
    200px — the minimum. Fifty per cent of 300 is 150, which is below the floor, so the floor applies. Measured across four containers the results were 200, 250, 400, 400 at 300, 500, 800 and 1000px: the minimum, then the preferred value, then the maximum twice. clamp(a, b, c) is defined as exactly max(a, min(b, c)), so it is a convenience rather than a new capability, and understanding it that way makes the argument order memorable. The value is continuous, which is the real advantage over a media query — there is no breakpoint at which the layout jumps, and no set of widths at which someone forgot to add a rule.
  2. What happens if the minimum exceeds the maximum?
    The minimum wins — measured, clamp(400px, 50%, 200px) in a 1000px container gave 400px. That follows directly from the definition: max(400px, min(50%, 200px)) evaluates the inner min to 200px and then the outer max raises it to 400. It is the same precedence chapter 3 measured for the separate properties, where width: 300px; min-width: 400px; max-width: 200px produced 400px, and for the same underlying reason: the minimum is applied last. Worth knowing because a reversed clamp is a plausible typo that produces a plausible-looking result rather than an error, and because it means a clamp built from variables can silently invert if the variables change.
  3. Why is calc(1px * 1px) invalid?
    Because a length times a length is an area, and CSS has no type for that — so the expression is rejected at parse time rather than coerced into something. Measured, CSS.supports returns false for it, as it does for calc(10 / 2px), which would be a per-length quantity. The operations that are allowed follow the same dimensional logic: length ÷ number is a length, length × number is a length, and length ± length is a length. This is real unit algebra rather than string manipulation, which is also why calc(100% - 20px) works even though the two terms cannot be resolved until layout — the types are compatible, and the resolution is deferred. It is worth remembering that a rejected declaration is silently dropped, so the symptom is a property that appears to do nothing.
  4. What does round(23px, 10px) give, and what is it for?
    20px by default, and 30px with the up keyword — both measured. The second argument is the interval to round to, so the function snaps a value to a grid in a single expression, and the direction keywords are nearest, up, down and to-zero. The obvious use is aligning to a spacing scale or a baseline grid when a value comes from a variable or a container query and cannot be written literally. Its companions are mod() and rem(), which both gave 3px for (15px, 4px) and differ on negative inputs — mod takes the sign of the divisor and rem takes the sign of the dividend, which is the same distinction most programming languages draw and get wrong equally often.
  5. How would you place items around a circle in CSS alone?
    With the trigonometric functions and a per-item index. Give each item --i, compute its angle as calc(var(--i) * 360deg / var(--n)), and then translate by calc(100px * cos(var(--a))) and calc(100px * sin(var(--a))). Measured, calc(100px * sin(30deg)) gives exactly 50px, so the arithmetic is genuinely available rather than approximate. The multiplication by a length is what gives the result a unit, since sin() returns a plain number — the same reason calc(1px * pow(2, 5)) is written that way and gives 32px. Combining this with @property from chapter 18 makes the angle animatable, which is how CSS-only radial menus and progress rings are built.
  6. What is wrong with font-size: clamp(1rem, 2vw, 1.4rem)?
    The middle term ignores the reader. A pure viewport unit does not respond to browser zoom or to a changed default font size, so between the two bounds the text is effectively unzoomable — someone who has set 24px as their base still gets text sized by the window. That fails WCAG's requirement that text can be resized to 200% without loss of content or function, and it is a genuine accessibility defect rather than a stylistic preference. The fix is to include a relative unit in the preferred value: clamp(1rem, 0.9rem + 0.5vw, 1.4rem) still scales with the viewport and also scales with the reader's settings, because the rem component grows when they change their base size. The same caution applies to vw-driven spacing and line heights.
  7. When is min() better than max-width?
    When you want the cap and the gutter in one declaration. width: min(100% - 2rem, 65ch) says "as wide as 65 characters, but always leave a rem of space each side", which with the separate properties needs width: 100%; max-width: 65ch; padding-inline: 1rem and a border-box assumption, or a wrapper element. Reading them aloud helps keep them straight: min() caps a value, because the result can never exceed the smallest argument, and max() sets a floor. That is the opposite of the intuition the names suggest, which is why min() behaving like max-width reads oddly at first. Both accept any number of arguments and nest freely, so min(90%, max(300px, 50vw)) is legal — though at that point clamp usually says it more clearly.
