The individual properties

The same two operations, four ways to write them
Two of the four are identical
The individual properties ignore declaration order
Measured: translate then rotate and rotate then translate both landed at 240, 140. They are always applied translate, then rotate, then scale.
The shorthand does not
The same two operations written as a transform list gave 240, 140 one way and 211, 211 the other.
Which is what makes them independently animatable
Two animations can move translate and rotate at once without composing into one list and fighting over the order.
They compose with transform too
If both are present, the individual properties apply first and the transform list is applied after them.
The three properties that break position: fixed

Worth restating here because this is where people write them. Chapter 6 measured that transform, filter and perspective each make an element the containing block for a position: fixed descendant — so a fixed header inside a transformed wrapper stops being fixed to the viewport and starts scrolling. Chapter 7 measured that the same three also create a stacking context, so a z-index that used to work can stop working. And a no-op value counts: translateX(0) and blur(0px) both did it. The individual properties behave identically — translate: 0 is still a transform for these purposes. None of this is a reason to avoid transforms; it is a reason to recognise the symptom, because the cause is usually several levels up the tree from the element that looks broken.

Check yourself

Self-check

  1. translate(100px) rotate(45deg) against rotate(45deg) translate(100px) — what is the difference?
    Where the element ends up. Measured on an 80×80 box positioned at 100, 100: the first gave a centre at 240, 140 and the second at 211, 211. Transform functions are applied left to right, and each one moves the coordinate system the next one operates in. So translating first moves the box right and then spins it in place; rotating first turns the axes, so the subsequent 100px translation travels along a diagonal. The same non-commutativity applies to scale: measured, translate(100px) scale(2) put the centre at 240 and scale(2) translate(100px) at 340, because the scale also multiplies the distance the translation covers. Matrix multiplication is not commutative, and this is that fact showing through.
  2. Why does rotating an element not move its centre?
    Because the default transform-origin is 50% 50% — the centre of the border box — and a rotation about a point leaves that point where it is. Measured, an 80×80 box at 100, 100 kept its centre at 140, 140 under rotate(45deg). Change the origin and the same rotation becomes a swing: with transform-origin: 0 0 the centre moved to 100, 157, and with 100% 100% to 180, 123. That makes the origin the right tool for hinge-like motion — a door opening, a menu unfolding from a corner — where the shorthand alternative would be a translate before and after the rotation. Worth knowing that SVG defaults differently, using the user coordinate system rather than the element box, and transform-box: fill-box makes it behave like HTML.
  3. Why do translate: 100px; rotate: 45deg and the reverse give the same result?
    Because the individual properties are applied in a fixed order — translate, then rotate, then scale — regardless of the order you declare them in. Measured, both orderings landed at 240, 140, while the equivalent transform shorthand gave 240, 140 one way and 211, 211 the other. That fixed order is the point of the feature. It means two separate animations can drive translate and rotate simultaneously without composing into one list and overwriting each other, which with the shorthand requires a single keyframe track containing every function. If both a shorthand and the individual properties are present, the individual ones apply first and the transform list is applied on top.
  4. Does a transform affect layout?
    No — chapter 14 measured that directly: with transform: scale(2), the element following it did not move, staying at exactly the same position as with no transform at all. The element's visual box changed and its layout box did not, which showed up as getBoundingClientRect().width reporting 200px while offsetWidth reported 100px. Two consequences follow. A transformed element overlaps its neighbours rather than pushing them, so hover effects that scale a card will cover the cards beside it. And because nothing needs laying out again, transforms are among the two things cheapest to animate — chapter 22 — which is why the standard advice is to animate transform and opacity rather than width, top or margin.
  5. What does a transform do to position: fixed descendants?
    It captures them. Chapter 6 measured that transform, filter, will-change, contain and perspective all make an element the containing block for a position: fixed descendant, so a fixed header inside a transformed wrapper stops being fixed to the viewport and scrolls with the page instead. A no-op value is enough: measured, translateX(0) and blur(0px) both did it, because it is the presence of the property that matters rather than its effect. The individual properties behave the same way — translate: 0 still counts. Chapter 7 measured that the same declarations also create a stacking context, so a working z-index can break at the same moment. The symptom usually appears several levels away from the declaration that caused it.
  6. What do you need for a 3D transform to look three-dimensional?
    A perspective, and it goes on the parent. Without one, rotateY(45deg) is an orthographic projection — the element simply gets narrower, with no sense of depth, because there is no vanishing point. perspective: 800px on the containing scene sets how far the viewer is from the plane: smaller values give a more dramatic, wide-angle effect and larger ones flatten it. There is also a perspective() function usable inside a transform list, which applies per element rather than to a shared scene, so several children each get their own vanishing point and a row of cards will not look coherent. The companions are transform-style: preserve-3d, needed for children to keep their own 3D position rather than being flattened into the parent's plane, and backface-visibility: hidden for the classic card flip.
  7. When should you use the individual properties over the shorthand?
    Whenever more than one thing is animating, or whenever different rules want to change different parts. The shorthand is a single value, so a hover rule that sets transform: scale(1.05) silently wipes out a base rule's transform: translateY(-2px) — a real and common bug that the individual properties remove entirely, since scale and translate are separate properties that cascade separately. The same applies to animation: two keyframe tracks can drive them independently. Use the shorthand when you need an order the fixed one does not give you — anything requiring rotate before translate, or several rotations about different origins — and when you need functions with no individual equivalent, such as skew or matrix. Mixing both is legal, with the individual properties applying first.
