Design tokens

A nine-step colour scale looks like nine colours you can use. Measured against WCAG, four work as text on white, five work as a surface under dark ink, and none does both. A scale is not a palette — most of it exists to be borders, backgrounds and hover states.

A scale, scored

How these numbers were produced

Nine steps of one hue at fixed chroma — oklch(L 0.14 250) — converted to sRGB by the browser and scored with the WCAG formula against white and against #111. Converting needed care: chapter 13 measured that oklch keeps its space in the computed value, so reading getComputedStyle().color returns oklch numbers. The first run of this harness read those three numbers as if they were RGB and produced a scale of identical blues. Wrapping each value in rgb(from … r g b) forces the conversion.

css — the three tiers, and why each exists
:root {
  /* 1. primitives — raw values, no meaning. Never used directly. */
  --blue-50: oklch(.97 .14 250);   --blue-500: oklch(.50 .14 250);
  --blue-600: oklch(.40 .14 250);  --space-3: .75rem;

  /* 2. semantic — meaning, no component. This is the theming layer. */
  --surface: #fff;        --text: var(--blue-600);
  --accent: var(--blue-500);  --border: var(--blue-50);
}
.dark { --surface: #16202b; --text: #eef3f7 }   /* one class, whole subtree */

/* 3. component — bound to one thing, and always reads a semantic token */
.btn { --btn-bg: var(--accent); background: var(--btn-bg); padding: var(--space-3) }

/* register anything that must animate or must not inherit — chapter 18 */
@property --accent { syntax: '<color>'; inherits: true; initial-value: #06c }

/* a fluid step, capped at both ends — chapter 19 */
--step-2: clamp(1.1rem, 1rem + .4vw, 1.5rem);

What to test about a token system

Tokens invite a particular failure: the system looks consistent because everything is a variable, and nothing checks whether the combinations are usable. Three tests are worth automating, and all three are computations rather than opinions. Contrast across every theme — every semantic text token against every semantic surface token, in each theme, which is the scale measurement above applied to real pairs. Every token is reachable — a component token pointing at a primitive that was renamed fails silently, because chapter 18 measured that an undefined variable makes the declaration invalid at computed-value time and the element quietly inherits. And the scale has no gaps or duplicates: two steps that round to the same rendered value are a maintenance cost with no benefit. None of these needs a visual review, which is what makes them worth putting in CI.

Check yourself

Self-check

  1. Why can no step of the measured scale be both text and a surface?
    Because the two roles pull in opposite directions and the thresholds do not overlap. Measured across nine steps of oklch(L 0.14 250): four steps at L 0.5 and below pass AA as text on white, five steps at L 0.6 and above pass as a surface under #111 ink, and the crossover falls cleanly between them, so none does both. That is not a flaw in the scale — it is what a scale is for. Roughly half of it exists to be borders, dividers, hover states, focus rings and disabled text, roles that either have a 3:1 bar or no contrast requirement at all. Treating all nine steps as interchangeable "brand blues" is the mistake, and it is invisible until someone computes the numbers.
  2. What went wrong converting oklch to sRGB the first time?
    The harness read the computed value with a numeric regex and got the oklch numbers, then treated them as RGB — producing a scale of nine nearly identical blues. The cause is a measurement from chapter 13: modern colour functions keep their authored space in the computed value, where legacy formats like hsl() resolve to rgb(). So getComputedStyle(el).color on an oklch value returns oklch(…), and any code assuming three numbers means red, green and blue is silently wrong. Wrapping the value as rgb(from … r g b) forces the conversion. It is a good illustration of why the chapters build on each other: the fix was already measured eleven chapters earlier, and not applying it produced plausible-looking nonsense rather than an error.
  3. What are the three token tiers, and why not two?
    Primitive values with no meaning (--blue-500, --space-3), semantic tokens with meaning and no component (--surface, --text, --accent), and component tokens bound to one thing (--btn-bg). The middle tier is the one people skip and the one that does the work: it is where theming happens, because a component referencing --surface re-themes for free while one referencing --blue-50 does not. Skipping it means every theme change is a search for every place a primitive leaked into a component. The third tier earns its place differently — it gives a component one documented override point, so a variant can set --btn-bg without knowing anything about the component's internals.
  4. How does adding one class re-theme a whole subtree?
    Because custom properties inherit and resolve per element — chapter 18's central measurement. Adding .dark to the root redefines --surface, --text and --muted for everything below it, and every component that reads those tokens picks up the new values wherever it happens to sit. Measured, one class changed all four computed readings — a panel's background and colour, a muted note, and a button's background — with no rule anywhere mentioning dark mode. The same mechanism means scoping is free: put the class on a subtree instead of the root and only that subtree changes, so an inverted panel inside a light page needs no new rules at all. That is the property a preprocessor variable cannot have, since it is substituted at build time.
  5. What should be automated about a token system?
    Three checks, all computations rather than opinions. Contrast across every theme: each semantic text token against each semantic surface token, in every theme — the scale measurement in this chapter applied to the real pairs, which catches a dark theme where a muted colour tuned for light backgrounds has quietly stopped passing. Reachability: a component token pointing at a renamed primitive fails silently, because chapter 18 measured that an undefined variable leaves the declaration invalid at computed-value time and the element simply inherits — no error, no warning, just a wrong colour. No duplicate or missing steps: two scale entries rounding to the same rendered value are pure maintenance cost. None requires a visual review, which is what makes all three suitable for CI.
  6. When should a token be registered with @property?
    When it must animate, when it must not inherit, or when a missing value would be dangerous. Chapter 18 measured all three: an unregistered custom property produced no transition at all where a registered <color> produced one; a child read the parent's value when unregistered and the declared initial-value when registered with inherits: false; and a registered property has a guaranteed value, so var() never resolves to nothing. That last one matters most for tokens, because it converts the silent inherit-from-nowhere failure into a defined fallback. The cost is verbosity, so the sensible rule is to register the semantic tier — the tokens components actually consume — and leave raw primitives unregistered.
  7. What is the difference between a token and a variable?
    A token is a variable with a contract. --x: 4px is a variable; --space-2: 4px as part of a documented scale, with a name meaning something to a designer, is a token. The practical difference is what happens when someone needs a value that is not in the scale: with variables they add one, and with tokens they have to justify it, which is the whole mechanism by which a system stays consistent. That also means the naming is the design work, not the values — a name that says what a thing is for survives a redesign, while one that says what it looks like does not, which is why --surface-raised outlasts --grey-100. And a token system with no rule about adding to it is just variables with longer names.
