The box model

width: 120px with 10px padding and a 5px border measures 150px on screen by default, and 120px under border-box. Four different ways of asking "how wide is it" give four different numbers, and knowing which one you are reading is most of debugging a layout.

What width means

css — the reset almost everyone uses, and why
*, *::before, *::after { box-sizing: border-box }

/* because this is the thing you actually want: */
.col { width: 50%; padding: 16px }     /* content-box → 50% + 32px → overflows */
                                        /* border-box  → exactly 50%           */

/* percentages resolve against the containing block's CONTENT box */
#parent { width: 400px; padding: 50px }  /* occupies 500px on screen */
#child  { width: 50% }                   /* → 200px, not 250px       */

/* height: 100% needs a DEFINITE parent height, or it resolves to auto */
html, body { height: 100% }              /* the old chain. Prefer: */
.hero { min-height: 100dvh }             /* dvh handles mobile toolbars */

min-width, width, max-width

Six combinations in a 600px container
The fourth one has min and max contradicting
Resolve width, then clamp with max-width, then clamp with min-width
Three steps, in that order. Each one can override the previous.
Which means min-width wins when they contradict

Either works without a width at all

Four ways to ask how wide something is

They disagree, and the disagreement is the useful part. getComputedStyle(el).width echoes your declared value in whatever box model is in effect — measured at 120px under both settings, so it cannot tell you which. offsetWidth is the border box: content plus padding plus border, and it includes a scrollbar if there is one. clientWidth is the padding box: it drops the border and excludes any scrollbar, so offsetWidth − clientWidth is a decent scrollbar-width probe. getBoundingClientRect().width is the border box after transforms, so a scaled element reports its visual size there and its layout size in offsetWidth — chapter 15. And none of them include margin. To get the content width you subtract padding from clientWidth yourself, which under border-box gave 90px.

Check yourself

Self-check

  1. width: 120px; padding: 10px; border: 5px solid — how wide on screen?
    150px by default, and 120px under box-sizing: border-box — both measured. In content-box, which is the initial value, width sets the content width and padding and border are added outside it: 120 + 10·2 + 5·2 = 150. In border-box, width is the width of the whole box up to and including the border, so the content shrinks to fit: 120 − 20 − 10 = 90. Margin is outside the box in both models — measured, adding margin: 20px to the border-box case still drew 120px. This is why nearly every codebase starts with *, *::before, *::after { box-sizing: border-box }: it makes width: 50% mean 50% even when the element has padding, which is almost always what you meant.
  2. Which of the four width readings tells you what box-sizing is in effect?
    None of them — which corrected an expectation while writing this chapter. getComputedStyle(el).width came back as 120px under both settings, because it reports the value in whichever box model is in effect rather than normalising to content width. The four readings under border-box were 120, 120, 110, 90: computed, offsetWidth (the border box), clientWidth (the padding box), and content, which you have to compute yourself by subtracting padding from clientWidth. Each has a use. offsetWidth includes a scrollbar and clientWidth does not, so their difference is a scrollbar probe. And getBoundingClientRect().width is the border box after transforms, so a scaled element reports its visual size there and its layout size in offsetWidth.
  3. A parent is width: 400px; padding: 50px. A child is width: 50%. How wide is the child?
    200px — measured. A percentage width resolves against the containing block's content box, which is 400px here, not the 500px the parent occupies on screen. That distinction catches people whenever a padded container holds percentage-sized children, and it is one more reason border-box on the parent helps: with border-box the parent's content box would be 300px and the child 150px, which at least matches what you see. Two related rules worth carrying. Percentage padding and margin resolve against the containing block's width, even vertically — so padding-top: 50% is half the width, which is the old aspect-ratio hack, now replaced by the aspect-ratio property. And height: 100% needs a definite parent height or it resolves to auto.
  4. width: 300px; min-width: 400px; max-width: 200px. What happens?
    The element is 400px — measured. The order is: resolve width, then clamp with max-width, then clamp with min-width. So 300 becomes 200 under the maximum, and then 200 becomes 400 under the minimum, because the minimum is applied last and therefore wins any contradiction. That is specified rather than accidental, and it is the sensible choice — a minimum usually encodes something that must not break, like a control staying tappable, while a maximum usually encodes a preference. The same ordering applies on the block axis with min-height and max-height. Each also works alone: measured, max-width: 200px with no width capped an auto width to 200, and min-width: 400px alone left it at 600, since the auto width already exceeded the minimum.
  5. Why is width: 100%; max-width: 60ch a good responsive default?
    Because it fills a narrow viewport and caps on a wide one with no media query at all. The width: 100% takes whatever is available, and max-width clamps it down once available exceeds the cap — which the clamping order makes reliable, since maximum is applied after width. Using ch ties the cap to the font rather than to a pixel guess, and 45–75 characters is the range typography research generally supports for readable body text, so 60ch lands in the middle. The pattern generalises: width: 100%; max-width: 1200px; margin-inline: auto is the standard page container. Worth knowing that min-width: 0 is the counterpart fix inside flex and grid, where an item's automatic minimum size stops it shrinking — chapter 8 measures that.
  6. What does height: 100% need to work?
    A parent with a definite height. A percentage height resolves against the containing block's height, and if that height is itself auto — determined by its contents — there is nothing to take a percentage of, so the declaration is ignored and the element falls back to auto. That is why the old idiom starts html, body { height: 100% }, establishing a definite chain from the viewport down. Modern CSS has better answers: min-height: 100dvh sizes against the viewport directly, and the dvh unit tracks mobile browser toolbars appearing and disappearing where vh does not. Inside a flex or grid container the rule changes again — an item can stretch to fill without any percentage, which is usually the cleaner solution and one reason full-height layouts got much easier.
  7. What does the difference between offsetWidth and clientWidth tell you?
    The border widths plus any scrollbar. offsetWidth is the border box, clientWidth is the padding box, so subtracting gives left border + right border + the vertical scrollbar's width if one is present. With no borders that makes it a reliable scrollbar-width probe, which is how libraries measure the value to compensate for layout shift when a modal locks scrolling — though scrollbar-gutter: stable is the modern answer to that specific problem. Measured here with a 5px border and no scrollbar, the difference was exactly 10px in both box-sizing modes, because borders are the same either way — box-sizing changes what width means, not what the box is made of. The related pair is scrollWidth, the full content extent including overflow, which is how you detect that text has been truncated.
