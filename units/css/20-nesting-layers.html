Nesting, layers and scope

Nesting compiles to :is(parent) child, which has a consequence nobody expects: adding one unrelated selector to a parent list silently raises the specificity of every rule nested inside it. Measured here by racing the nested rule against a later plain one.

— words— min read2 interactivesNeeds: chapters 01, 02

What a nested selector costs

The measurement

Each row writes a green rule one way and then a plain .x .p { color: red } — specificity (0,2,0) — after it. If red wins, the green rule was also (0,2,0) and lost on source order. If green wins despite being written first, its specificity must be higher. One comparison, and it distinguishes the two competing accounts of what nesting does.

Five ways of writing the same match
Two of them win, three lose
A single-class parent behaves exactly like a descendant selector
.x { & .p {} } lost to the later plain rule — so both are (0,2,0).
A parent list containing an id does not
.x, .y#z { & .p {} } won despite being written first, so its specificity is (1,2,0) — the id counts even though the element matched via .x.
Because nesting is defined as :is(parent)
The hand-written :is(.x, .y#z) .p measured identically. :is() takes the specificity of its most specific argument.
:where() is the escape hatch
It matches the same elements and contributes zero specificity, so nesting inside it costs nothing.

Layers and scope

Four layer arrangements, and a scope donut
!important reverses everything
Layer order beats specificity entirely
A p selector in a later layer beat an #id selector in an earlier one.
Unlayered author styles beat every named layer
Which makes layers a way to lower the priority of imported CSS rather than to raise your own.
!important inverts the whole ordering
Including the unlayered position: measured, an important rule inside a layer beat an important unlayered one. That corrected an expectation while writing this.
@scope … to … makes a donut

css — the shapes worth knowing
/* declare the layer order once, at the top — the order here is what counts */
@layer reset, base, components, utilities;
@import url(normalize.css) layer(reset);

/* nesting: `&` is optional before a compound selector, required otherwise */
.card {
  padding: 1rem;
  .title { font-weight: 600 }        /* = :is(.card) .title */
  &:hover { background: #f6f6f6 }     /* `&` REQUIRED here    */
  &.is-open { border-color: blue }    /* and here             */
  @container (min-width: 30rem) { display: grid }
}

/* keep nesting from inflating specificity */
:where(.a, .b#c) { .p { … } }        /* the parent contributes zero */

/* scope: a root, and optionally a limit */
@scope (.card) to (.content) { p { color: … } }
@scope (.theme) { :scope { background: … } }    /* the root itself */
Two things about nesting worth knowing before adopting it

& is optional in some places and required in others. Before a compound selector — .title, p, > li — it can be omitted and the rule still means a descendant. Before a pseudo-class or an appended class it is required, because :hover { } nested inside would mean "a descendant that is hovered" rather than "this element hovered", and .is-open would mean a descendant with that class rather than this element also having it. That is a silent difference in meaning rather than an error, which makes it the easiest nesting mistake to ship.

Depth is the real cost. Every level adds to the selector, and the specificity measurement above shows it can add more than it looks like. Two levels is usually fine; four means the CSS mirrors the markup, and the rules break the moment the markup is refactored — the same problem deeply nested preprocessor code always had, now available natively.

Check yourself

Self-check

  1. What specificity does .x, .y#z { & .p { } } give the nested rule?
    (1,2,0) — the id counts, even when the element matched via .x and has no id at all. Measured by racing it against a later .x .p rule at (0,2,0): the nested rule won despite being written first, which it could only do with higher specificity. The single-class version .x { & .p { } } lost the same race, confirming it is (0,2,0). The mechanism is that nesting is defined as :is(parent) child, and :is() takes the specificity of its most specific argument — the hand-written :is(.x, .y#z) .p measured identically. So adding one selector to a parent list silently changes the priority of everything nested inside, which is a real maintenance hazard in a long stylesheet.
  2. How do you nest without inflating specificity?
    Wrap the parent in :where(), which matches the same elements and contributes zero specificity — so :where(.a, .b#c) { .p { … } } gives the nested rule the specificity of .p alone. That is the standard technique for anything meant to be easily overridden: a reset, a base layer, a library's defaults. Chapter 2 measured the pair directly, with :is(#t, p) at (1,0,0) and :where(#t, p) at (0,0,0). The alternative for the same goal is @layer, which sidesteps specificity altogether by making layer order the deciding factor — and for a whole stylesheet that is usually the better tool, with :where() reserved for individual selectors.
  3. When is & required in a nested rule?
    Before anything that is not a compound selector start — most importantly before a pseudo-class or an appended class. &:hover means this element hovered; :hover nested alone means a descendant that is hovered, which is a different rule that will match sometimes and confuse you the rest of the time. Likewise &.is-open means this element also carrying that class, while .is-open means a descendant with it. Before a plain compound selector — .title, p, > li — the & is optional and the rule means a descendant either way. Because both forms are valid, the mistake produces a silent change in meaning rather than an error, which makes it the easiest nesting bug to ship. Writing & always is a defensible habit.
  4. Does a later layer beat a higher specificity?
    Yes — measured, a plain p selector in a later layer beat an #id selector in an earlier one. Layer order is checked before specificity in the cascade, so once two declarations are in different layers their selectors stop mattering. That is the point of the feature: it lets you say "these styles always lose to those" structurally, rather than by escalating selectors. The order is set by the first @layer statement that names them, which is why the convention is to declare it once at the top of the entry stylesheet — @layer reset, base, components, utilities; — before anything else. Layers declared later without a prior statement are appended in first-appearance order, which makes the ordering depend on import order and is worth avoiding.
  5. Where do unlayered styles sit?
    Above every named layer — measured, an unlayered p rule beat an #id rule inside a layer. That surprises people who expect unlayered to mean "first" or "default", and it is deliberate: it means adding @layer to a project is safe, because existing unlayered CSS keeps winning and nothing changes until you move it in. The practical consequence is that layers are a tool for lowering the priority of things — a vendor stylesheet imported with @import url(x.css) layer(vendor) now loses to all your own code, with no selector rewriting. Trying to use layers to raise the priority of your own styles above unlayered code does not work, and is a sign the unlayered code should be in a layer instead.
  6. What does !important do to layer order?
    It reverses it completely — and this corrected an expectation while writing the chapter. Measured, an important declaration in the first layer beat one in the last, which is the inversion most people know about. What is less known, and what the measurement caught, is that the inversion covers the unlayered position too: an important rule inside a layer beat an important unlayered rule, the exact opposite of the normal case. The logic is consistent once stated — the whole ordering is mirrored, so whatever normally wins normally, loses when everything is important. The practical reading is that !important in a layered codebase is even harder to reason about than usual, and that a reset layer using it will override everything, which is occasionally what a reset wants.
  7. What does @scope (.card) to (.content) match?
    Everything from .card down, stopping at .content — a donut. Measured with three paragraphs: one directly inside .card matched, one inside .content did not, and one outside .card did not. That lower boundary is the genuinely new capability, because a descendant selector can only say "inside X" and has no way to say "but not past Y". The case it exists for is a component that may contain slotted or user-supplied content it must not restyle — a card whose own paragraphs should be styled but whose embedded article should be left alone. @scope also adds a proximity tiebreak, so when two scoped rules of equal specificity both match, the one whose root is nearer the element wins.
