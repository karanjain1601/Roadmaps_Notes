Chapter 17 · Motion

Animations

An animation that snaps back at the end is not broken — it is animation-fill-mode: none, the default, doing exactly what it says. The four modes are measured here by seeking the animation to an exact time rather than waiting for one, which turns a flaky test into an exact reading.

— words— min read2 interactivesNeeds: chapters 15, 16

Fill modes

Seeking, not waiting

The setup is animation: fade 1s linear 1s — a one-second delay, then a one-second animation from opacity: .2 to opacity: .8 — on an element whose own rule says opacity: 1. Rather than sleeping and hoping, each reading calls element.getAnimations()[0], pauses it, and sets currentTime to the exact moment of interest: 500ms for the middle of the delay and 2000ms for past the end. Two readings, no timing flake, and the same technique works for any moment in any animation.

Four fill modes, read at two moments
The two ends are independent
none leaves the element's own value at both ends
Measured 1 during the delay and 1 after the end. The animation only applies while it is running, which is why things snap back.
backwards fills the delay with the first keyframe
Measured 0.2 during the delay and 1 after. It fixes the flash before a delayed animation starts.
forwards holds the last keyframe after the end
Measured 1 during and 0.8 after. This is the one people usually mean.
both does each
0.2 then 0.8. Two independent behaviours in one keyword, which is why the names never quite stick.

Scroll-driven animations

A progress bar with no duration
Its progress is the scroll position
The animation has no duration at all
Measured: progress 0, 0.5 and 1 at the three scroll positions, with scaleX matching exactly. The timeline is the scroll.
scroll() tracks a scroll container; view() tracks an element
Both supported here. view() is the one for reveal-on-scroll, since it measures an element's progress through the viewport.
No scroll listener, and no main-thread work
Which is the reason to do it in CSS at all: a JavaScript scroll handler runs on the main thread and competes with everything else.
animation-range chooses which part counts
entry 0% cover 50% and similar keywords let a reveal finish before the element is fully on screen.
css — the shapes worth knowing
@keyframes fade { from { opacity: 0 } to { opacity: 1 } }
.thing { animation: fade .4s ease-out both }     /* `both` far more often than none */

/* a reading-progress bar, no JavaScript */
.bar { animation: grow linear; animation-timeline: scroll(root);
       transform-origin: 0 50% }

/* reveal each card as it enters the viewport */
.card { animation: fade linear both;
        animation-timeline: view();
        animation-range: entry 0% cover 40% }

/* multiple animations on one element, comma-separated and independent */
animation: slide .3s ease-out, fade .5s linear;

/* and the guard that is close to mandatory — chapter 11 */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: .01ms !important;
                           animation-iteration-count: 1 !important }
}
Animation or transition?

A transition needs a state change to react to and interpolates between two values — the old one and the new one. An animation needs no trigger at all, can define any number of intermediate steps, can repeat, and can run in reverse or alternate. The practical division: use a transition when something changes because of an interaction, because the reverse direction comes free and interruption is handled sensibly — a half-open menu being closed again animates from where it actually is. Use an animation when there is no state change to hang it on (a loading spinner, an entrance on page load), when you need more than two points, or when it should loop. Chapter 16's @starting-style narrowed the gap considerably, since entrances used to be the main reason to reach for a keyframe animation, and both share getAnimations() as the way to find out what is actually running.

Check yourself

Self-check

  1. Your animation snaps back to its original value at the end. Why?
    Because animation-fill-mode defaults to none, which means the animation only applies its values while it is running. Measured: with none, the computed opacity was 1 — the element's own declared value — both during the delay and after the end, even though the animation's last keyframe says 0.8. Add forwards and the last keyframe is held: measured 0.8 after the end. This is one of the most common CSS animation surprises, and the fix is usually to write both rather than forwards, since the same problem exists at the other end — a delayed animation shows the element's own value until it starts, which produces a visible flash.
  2. What does backwards fill, and when do you need it?
    It fills the delay with the animation's first keyframe. Measured with a one-second delay: backwards gave 0.2 during the delay — the from value — where none gave the element's own 1. You need it whenever an animation has a delay and its first keyframe differs from the element's normal state, which is exactly the staggered-entrance case: five cards each fading in from opacity: 0 with increasing delays will all be fully visible until their turn arrives, then blink to invisible and fade in. Writing both covers this end and the other in one keyword, which is why both is the value worth defaulting to. The four modes are two independent behaviours, and the names describe which end rather than what happens.
  3. How do you read an animation's value at an exact moment?
    Seek it rather than waiting for it. element.getAnimations()[0] returns the running animation, .pause() stops the clock, and setting .currentTime to a number of milliseconds moves it to any point — after which getComputedStyle reads the exact value there. Every figure in this chapter's first demo came from two such readings, at 500ms for the middle of the delay and 2000ms for past the end. The alternative — sleeping for roughly the right duration and hoping — is flaky in a way that produces intermittent failures rather than clear ones. The same object exposes effect.getComputedTiming(), whose progress field is how the scroll-driven measurements in the second demo were taken.
  4. What is the timeline of a scroll-driven animation?
    The scroll position itself — the animation has no duration. Measured at three points down a 3000px page, the animation's progress read 0, 0.5 and 1, with the element's scaleX matching exactly. animation-timeline: scroll() ties progress to a scroll container's position, and view() ties it to an element's own progress through the viewport, which is the one for reveal-on-scroll effects. animation-range then selects which part of that journey counts, so entry 0% cover 40% finishes the reveal before the element is fully visible. The reason to do this in CSS rather than with a scroll listener is that a listener runs on the main thread and competes with everything else, where these run off it.
  5. When should you use a transition rather than an animation?
    Whenever there is a state change to react to. A transition interpolates between the old value and the new one, so the reverse direction is free — you write the hover state once and both directions work — and interruption is handled sensibly, since a half-open menu being closed again animates from where it actually is rather than jumping to the end first. An animation needs no trigger, which makes it right for anything with nothing to react to: a loading spinner, an entrance on page load, an attention loop. It also handles more than two points, repetition, and reversing. Chapter 16's @starting-style narrowed the gap, because entrances used to be the main reason to reach for keyframes; the remaining clear cases for animation are loops and multi-step sequences.
  6. What does animation: fade .4s ease-out both mean, in order?
    Name, duration, timing function, fill mode — and the shorthand's ordering rules are less strict than they look. The first <time> is the duration and the second is the delay, so 1s 2s means a one-second animation delayed by two; everything else is matched by type, so the name, timing function, fill mode, direction, iteration count and play state can appear in any order. The traps are that a bare number is read as iteration-count, and that the shorthand resets every property it does not mention — so a later animation: fade .4s silently clears a both set earlier. As with transition, the longhands are worth using when a rule is only adjusting one part.
  7. How should an animation respect prefers-reduced-motion?
    By removing the movement while keeping the meaning. The blanket reset — setting animation-duration to a near-zero value and animation-iteration-count to 1 inside @media (prefers-reduced-motion: reduce) — is a sound safety net, and setting iteration-count matters because an infinite animation with a tiny duration is worse than one with a long one. The better treatment is per-effect: a spinner can become a static indicator, a parallax section can hold still, a card entrance can fade rather than slide. What must survive is the communication — someone who has asked for reduced motion still needs to know the panel opened or the content loaded. Scroll-driven animations deserve particular care, since they move continuously with input and are among the most likely to cause discomfort.
