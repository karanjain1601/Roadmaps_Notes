Position and containing blocks

Every offset is measured from something, and position chooses what. Five values, five different answers — plus a genuinely surprising one: five ordinary-looking declarations, transform chief among them, silently capture a fixed element and make it scroll with the page.

— words— min read2 interactivesNeeds: chapters 03, 04

Five values

The ancestor everything is measured against

A position: relative box with margin: 100px, a 5px border and 20px padding, so its three edges sit at 100 (border box), 105 (padding box) and 125 (content box). Those three numbers are what make the difference visible: a static child starts at 125, and an absolute child with left: 10px landed at 115 — measured — which tells you it resolved against the padding box.

Where the box ends up, and what it leaves behind
Two of the five stop taking up space
static ignores the offsets entirely
Measured at 125px — the content edge — with top and left having no effect at all. Setting offsets without setting position is a common silent no-op.
relative moves visually and keeps its space
135px: its normal position plus 10. Nothing else shifted, so it can overlap its neighbours while they lay out as though it had not moved.
absolute resolves against the padding box
115px = 105 + 10. Inside the border, outside the padding — so a padded container's absolute children start at its border, not at its content.
fixed went to the viewport at 10px
Ignoring the positioned ancestor completely — unless one of the five declarations in the next demo is present.
css — the patterns worth knowing
.parent { position: relative }        /* establishes the reference */
.badge  { position: absolute; top: 0; right: 0 }

/* opposite offsets STRETCH rather than move */
.overlay { position: absolute; inset: 0 }        /* all four sides */
.overlay { position: absolute; top:0; right:0; bottom:0; left:0 }   /* same */

/* sticky needs a threshold and a scrolling ancestor that is tall enough */
.head { position: sticky; top: 0 }    /* with no `top` it never sticks */

/* and the modern replacement for most tooltip positioning: */
.tooltip { position: absolute; position-anchor: --btn; top: anchor(bottom) }
[popover] { }                          /* the top layer — above everything, no z-index */

What captures a fixed element

Eight declarations on an ancestor
Five of them break position: fixed
position: relative captures absolute and not fixed
Measured — the ordinary, expected split, and the one most people know.
But transform, filter, will-change, contain and perspective capture both
All five measured as containing a fixed descendant. A transform: translateX(0) anywhere above turns a fixed header into one that scrolls away.
Even a no-op value does it
translateX(0), blur(0px) and perspective: 1px all captured. It is the presence of the property, not its effect.
opacity: 0.99 is the near-miss
It creates a stacking context — chapter 7 — but not a containing block, so a fixed descendant still used the viewport. The two concepts overlap and are not the same.
The commonest "my fixed header does not stay fixed"

An animation library adds will-change: transform to a wrapper. A card gets transform: translateY(0) to promote it to its own layer. A parent gets filter: drop-shadow(…). Any of these, anywhere between the fixed element and the root, silently changes what position: fixed is fixed to — measured, all five captured a fixed descendant — and it starts scrolling with the page. The symptom appears far from the cause, and nothing in devtools flags it directly, though inspecting the element and seeing its offsets resolve against something other than the viewport is the giveaway. Two defences. Keep fixed elements as direct children of body, outside any transformed subtree. Or use the top layer instead: a [popover] element or a <dialog> shown with showModal() escapes the containing-block question entirely, and escapes z-index with it.

Check yourself

Self-check

  1. An ancestor has a 5px border and 20px padding. Where does an absolute child with left: 10px land?
    At the ancestor's border-box left plus 5 plus 10 — measured at 115px with the ancestor's border box at 100. An absolutely positioned element resolves against its containing block's padding box, whose left edge sits inside the border and outside the padding. The three edges in that measurement were 100 (border box), 105 (padding box) and 125 (content box), and a static child started at 125 — so the same "top left corner" means two different places depending on positioning, differing by exactly the padding. That catches people building a badge in the corner of a padded card: top: 0; left: 0 puts it against the border rather than against the content, which is usually what you wanted but rarely what you expected.
  2. What is the difference between relative and absolute in terms of flow?
    relative keeps its space; absolute does not. Measured, the element following a relative box stayed where it was, while the element following an absolute box moved up to fill the gap. So a relatively positioned element moves visually while everything else lays out as though it had not — which means it can overlap its neighbours, and which is why position: relative with no offsets is such a common and harmless declaration: it establishes a containing block for absolute children and changes nothing else. An absolute element is removed from normal flow entirely, so it contributes no height to its parent, which is the same removal that makes floats collapse their containers in chapter 4.
  3. Why does top: 10px sometimes do nothing?
    Because the element is position: static, which is the initial value, and static boxes ignore the offset properties completely — measured, the element sat at 125px exactly as if top and left had not been written. It is a silent no-op with no warning anywhere, so the usual experience is writing offsets, seeing nothing move, and adding more offsets. The fix is to set a position other than static; relative is the usual choice because it changes nothing else. The related silent no-op is z-index, which is also ignored on static elements — chapter 7. Both are cases where a property is valid, applies to the element, computes fine, and simply has no effect in the current state, which is a category of bug CSS has rather a lot of.
  4. Which declarations capture a fixed descendant?
    Measured, five: transform, filter, will-change: transform, contain: paint and perspective. Any of these on any ancestor makes it the containing block for a position: fixed descendant, so the element becomes fixed to that box and scrolls with the page. Notably a no-op value is enough — translateX(0), blur(0px) and perspective: 1px all captured, because it is the presence of the property rather than its effect. position: relative is the one that behaves as expected: it captures absolute and does not capture fixed. This is the commonest cause of a fixed header that will not stay put, and the symptom appears far from the cause — an animation library adding will-change three levels up is enough.
  5. opacity: 0.99 did not capture a fixed element. What does it do?
    It creates a stacking context but not a containing block. Measured, a fixed descendant still resolved against the viewport. The two concepts are often conflated because their trigger lists overlap heavily — transform, filter and will-change create both — but they answer different questions. A containing block determines what offsets are measured from; a stacking context determines how z-index values are compared and which is chapter 7's subject. opacity below 1 creates only the second, which is why it can break a z-index that used to work while leaving positioning alone. Knowing which list a property is on saves a lot of guessing: the practical test is to check whether the symptom is about where something is or about what it is on top of.
  6. What does position: sticky need in order to stick?
    A threshold and room to move. It needs at least one of top, right, bottom or left — with none, it behaves exactly like relative and never sticks, which is the commonest reason it "does not work". It also sticks only within its parent, so it stops at the parent's bottom edge; if the parent is only as tall as the sticky element there is nowhere to travel and nothing appears to happen. And it needs an actual scrolling ancestor, which is where the third common failure comes from: any ancestor with overflow: hidden or overflow: auto becomes the scroll container, so a sticky element inside one sticks relative to that box rather than to the page. Unlike fixed, sticky keeps its space in flow — measured — so nothing jumps when it engages.
  7. How would you avoid the containing-block question entirely for a modal?
    Use the top layer. A <dialog> opened with showModal(), or any element with the popover attribute, is rendered in a separate layer above the entire document — so it is unaffected by ancestor transforms, unaffected by overflow: hidden clipping, and unaffected by z-index anywhere in the page. That removes three whole categories of bug at once: the transform capture measured here, the clipping from chapter 4, and the stacking-context traps in chapter 7. It also brings behaviour you would otherwise write by hand — a backdrop via ::backdrop, focus trapping, dismissal on Escape, and light-dismiss for popovers. The older answer was to portal the element to document.body with JavaScript, which every component library implemented; the platform now does it, and the markup stays where it belongs.
