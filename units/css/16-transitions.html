Transitions

A transition that does nothing looks exactly like a transition that is too fast to see. This chapter asks the browser directly — getAnimations() reports whether a transition object was created — and three of seven ordinary-looking changes produced none at all.

Which changes transition

Asking the browser instead of watching

Every row below applies a change and then calls element.getAnimations(), which returns a live list of the animations and transitions currently running on that element. A transition object exists, or it does not — no timing, no screenshots, no guessing whether something moved. That distinguishes the two failures that look identical from the outside: a transition that ran instantly, and a transition that was never created.

One negative result, and how it was settled

An early probe reported interpolate-size as not working, and the guess at the time was that the element had no content for auto to resolve to. That guess was wrong. A controlled sweep across three variables — the keyword present or absent, transition: height against transition: all, and content against an empty element — found the keyword to be the only factor: all three configurations with it transitioned and both without it did not. Content made no difference at all. The original probe differed from the working ones in several ways at once, which is precisely why it could not be diagnosed by inspection. The general lesson is worth more than the specific one: a single negative result is a hypothesis, and the way to turn it into a finding is to vary one thing at a time.

css — the patterns worth having
/* name the properties: `all` transitions things you did not mean to */
transition: opacity .2s, transform .2s;

/* the two cheap ones — chapter 22 */
transition: transform .2s ease-out, opacity .2s;

/* animating in from nothing needs a starting point to come FROM */
@starting-style { .toast { opacity: 0; translate: 0 -8px } }
.toast { opacity: 1; translate: 0; transition: opacity .3s, translate .3s }

/* a fade-out that ends hidden, entirely in CSS */
.panel {
  transition: opacity .3s, display .3s allow-discrete;
  opacity: 1; display: block;
}
.panel[hidden] { opacity: 0; display: none }

/* and the query that is close to mandatory — chapter 11 */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { transition-duration: .01ms !important }
}

Check yourself

Self-check

  1. Your transition does nothing. How do you tell why in one step?
    Call element.getAnimations(). It returns a live list of the animations and transitions currently running on that element, so an empty array means no transition was ever created — which is a completely different problem from one that ran too fast to see, and the two look identical from the outside. Measured across seven ordinary-looking changes, three produced nothing at all: height → auto, width → auto and display → none. Once you know it is a "never created" failure, the causes are a short list: the property is discrete, one end of the change is a keyword like auto, the element was only just inserted so there was no previous value, or the transition property does not name the property that changed.
  2. Why does height: 40px → auto not transition?
    Because auto is not a number, so there is nothing to interpolate towards — measured, no transition object was created at all, and the height simply jumped. The same happened for width → auto. This is the single most common animation frustration in CSS and the reason for a generation of JavaScript workarounds that measured the natural height and then animated to an explicit pixel value. Two modern fixes now exist and both were measured as working: interpolate-size: allow-keywords on an ancestor makes keyword values interpolable throughout that subtree, and calc-size(auto, size) does it for a single declaration. It is opt-in rather than default because making auto suddenly animate everywhere would change the behaviour of existing pages.
  3. What does transition-behavior: allow-discrete change?
    It lets discrete properties — ones with no in-between values, such as display and content-visibility — flip at the correct end of a transition rather than immediately. Measured, adding it made display → none produce a transition list that included display, where without it there was nothing. What that buys is a fade-out that actually ends hidden, in CSS alone: the element stays display: block for the duration of the opacity transition and switches to none at the end, which previously required a transitionend listener. Going the other way it flips at the start, so the element is visible before it fades in. One caution the measurement surfaced: with transition: all the browser also picked up font-feature-settings, so naming properties explicitly is worth the extra characters.
  4. Why does an element added to the page not transition in?
    Because a transition needs a previous value to move from, and a newly inserted element has none — its first computed style is its only style, so there is no change to animate. The traditional workaround was to insert the element, force a style read, and then add the class in a requestAnimationFrame, which is fiddly and easy to get wrong. @starting-style replaces it: the rule inside declares what the element's values should be considered to be before its first style resolution, so the transition has somewhere to come from. It is also what makes the popover and dialog entry animations work, since those elements go from display: none to visible and hit both this problem and the discrete-property one at once — which is why the two features shipped together.
  5. Which properties are cheap to transition, and why?
    transform and opacity, because neither requires layout or paint to be redone — chapter 22 measures the categories. Chapter 14 measured the layout half of that directly: a transform: scale(2) left the following element exactly where it was and changed only the visual box, so nothing around it needs recomputing. Animating width, height, top, margin or padding forces layout on every frame, and on a complex page that is where dropped frames come from. The practical translation: move things with translate rather than top or margin, resize with scale rather than width where the distortion is acceptable, and fade with opacity rather than visibility. The FLIP technique exists to express a layout change as a transform for exactly this reason.
  6. What is wrong with transition: all?
    It transitions things you did not intend, and the measurement here shows it concretely: with allow-discrete added, the transition list came back as display, font-feature-settings — a property nobody asked to animate. In real code the effects are worse: a rule elsewhere changing background-color on hover suddenly animates over your duration, a class toggle that alters border-width becomes a slow reflow, and every one of those is a layout or paint animation you did not budget for. It also makes the intent unreadable, since the declaration says nothing about what is expected to move. Naming properties costs a few characters and documents the animation: transition: opacity .2s, transform .2s. The one place all is defensible is a quick prototype you intend to tighten.
  7. How should a page respect prefers-reduced-motion?
    By removing the motion, not the feedback. The blunt version — setting transition-duration and animation-duration to a near-zero value inside @media (prefers-reduced-motion: reduce) — is a reasonable safety net and is what most resets do. But the better treatment is per-effect: a modal that slides in can simply fade instead, a parallax section can become static, and a loading spinner can become a progress bar. What matters is that the state change is still communicated, because someone who has asked for reduced motion still needs to know the panel opened. The preference reports an operating-system setting made by people who experience nausea or vertigo from large movement, so honouring it is closer to a correctness requirement than a nicety — chapter 21 treats it as one.
