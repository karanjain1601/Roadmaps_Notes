Performance

Rendering cost is hard to measure and easy to assert, so this chapter uses two things that are neither. A height reading that proves the browser skipped layout — and a timing comparison where the effect is roughly 27×, far larger than the noise around it.

Proving that work was skipped

A height reading as evidence

Claiming a browser "skipped layout" usually means quoting a profiler. There is a more direct test: a section containing 400px of content, with contain-intrinsic-size: auto 200px as its placeholder. If it reports 200px, its contents were never laid out. If it reports its real height, they were. The number itself is the proof, and it needs no timing at all.

The measurement that needed twenty runs

The first attempt read the height immediately and got 200px for an on-screen section, which looked like a finding. Adding one requestAnimationFrame gave 432px — so the conclusion written down was "the reveal takes one rendering frame". Sweeping the frame count destroyed that: the values came back 432, 200, 432, 432 for zero, one, two and three frames, which is not a function of anything. Running each condition twenty times settled it: at two frames the answer was 432 in 20 of 20, at zero frames it was 200 in 17 of 20, and successive reads within a single task gave [200, 200, 432, 432, 432, 432]. So it settles after two frames, and one frame lands in the unsettled window where either value can appear. Two wrong conclusions came from single observations before repetition produced the right one — which is the general hazard with anything timing-adjacent.

Which is why the guidance is "batch, then read"
Every framework's scheduling layer exists partly to enforce this ordering.
the three categories, and what triggers each
/* LAYOUT — geometry recomputed, then paint, then composite */
width  height  padding  margin  top  left  font-size  display

/* PAINT — pixels redrawn, no geometry change */
color  background  box-shadow  border-radius  visibility

/* COMPOSITE — handled by the compositor, no layout, no paint */
transform  opacity  filter*      /* *filter promotes to its own layer */

/* the properties that let you opt out of work */
content-visibility: auto;  contain-intrinsic-size: auto 200px;
contain: layout paint;     /* promise nothing escapes this subtree */
will-change: transform;    /* a hint — remove it when idle        */

/* the read/write ordering that avoids the 27× */
for (const e of els) e.style.width = w + 'px';   /* all writes  */
for (const e of els) read(e.offsetWidth);        /* then reads  */
will-change is a hint, and it is not free

It tells the browser to prepare for a change, usually by promoting the element to its own compositing layer — which costs memory and can make text rendering subtly worse, since a promoted layer may be composited rather than subpixel-antialiased. Applying it to many elements, or leaving it on permanently, can be slower than not using it. The intended pattern is to add it shortly before the change and remove it afterwards. And it has two side effects measured earlier in this unit that have nothing to do with performance: chapter 6 found it creates a containing block, capturing position: fixed descendants, and chapter 7 found it creates a stacking context. Both are silent, and both appear far from the declaration.

Check yourself

Self-check

  1. How can a height reading prove that layout was skipped?
    Because contain-intrinsic-size supplies a placeholder that is only used when the real contents were not laid out. A section holding 400px of content, marked content-visibility: auto with contain-intrinsic-size: auto 200px, reported 200px while offscreen and 432px once on screen. The 200 could not appear if the contents had been measured, so the number itself is the evidence — no profiler, no timing, no noise. The page's scrollHeight tells the same story from the other end. This is worth generalising: when a performance claim can be turned into a question about a value rather than a duration, the measurement becomes deterministic and repeatable instead of statistical.
  2. Why does content-visibility: auto need contain-intrinsic-size?
    Because without it a skipped element has no size at all — measured, the section reported 0px. That makes the page shorter than it really is, so the scrollbar is wrong and jumps as sections are revealed and their real heights appear, which is a worse experience than the rendering cost the property was added to avoid. contain-intrinsic-size gives the browser a guess to use in the meantime, and the auto keyword makes it remember the real size once measured, so the estimate only matters the first time. The two are effectively one feature. It is worth choosing a placeholder close to the typical real height, since the total error across many sections is what determines how much the scrollbar moves.
  3. What is layout thrashing, and how large is the effect?
    Reading a layout property after writing one, repeatedly — which forces the browser to recompute layout synchronously each time instead of once at the end. Measured over 400 elements: interleaved writes and reads took a median of 113.5ms, and the identical work with all writes first and all reads after took 4.2ms — roughly 27×. The reason is that offsetWidth and its relatives must return a correct answer, so a pending style change has to be resolved before they can. Batching means one layout serves 400 reads. This is what framework scheduling layers exist partly to enforce, and it is the most common performance bug that is invisible in the source: each individual line looks harmless.
  4. Why did writing transform cost nothing measurable?
    Because a transform is not a layout property, so reading offsetWidth afterwards has nothing pending to resolve — measured at 7.7ms against 113.5ms for the same pattern with width. Chapter 14 measured the underlying fact directly: with transform: scale(2), the element that followed did not move at all, and offsetWidth reported the layout box while the bounding rect reported the visual one. That is the whole reason the standard advice is to animate transform and opacity: they are handled by the compositor, so a change skips both layout and paint. Expressing a layout change as a transform is what the FLIP technique does — measure the start and end positions once, then animate between them with transforms.
  5. What are the three rendering categories?
    Layout, paint and composite, and each is a superset of the next in cost. Changing width, height, padding, margin, top, font-size or display forces layout, then paint, then composite — everything. Changing color, background, box-shadow or border-radius skips layout but still repaints. Changing transform or opacity skips both and is handled by the compositor alone, which is why those two are the ones to animate. Chapter 14's measurement supports the categories from a different direction: six of eight decorative declarations left the following element exactly where it was, so they cannot have triggered layout. Knowing the category of a property is most of knowing what it costs.
  6. When is will-change worth using?
    Shortly before a change you know is coming, and removed once it is done. It hints that the browser should prepare, usually by promoting the element to its own compositing layer — which costs memory and can make text rendering subtly worse, since a promoted layer may lose subpixel antialiasing. Applied to many elements, or left on permanently, it can be slower than omitting it. It also carries two side effects measured earlier in this unit that have nothing to do with performance: chapter 6 found it creates a containing block, so a position: fixed descendant becomes fixed to it instead of the viewport, and chapter 7 found it creates a stacking context, so a working z-index can stop working. Both are silent and both appear far from the declaration.
  7. What does the two-frame settling result say about measuring performance?
    That single observations of timing-adjacent behaviour are worth very little. Reading the height immediately gave 200px and looked like a finding; adding one frame gave 432px and produced the conclusion "it takes one rendering frame". Sweeping the frame count gave 432, 200, 432, 432 — not a function of anything, so both conclusions were wrong. Twenty runs per condition settled it: two frames gave 432 in 20 of 20, zero frames gave 200 in 17 of 20, and successive reads in one task gave [200, 200, 432, 432, 432, 432]. The same discipline applies to the thrashing figures, which is why they are reported as a median of seven runs with the range shown — the ratio is stable at roughly 27× while the milliseconds move by a factor of two.
