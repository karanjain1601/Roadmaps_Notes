Accessibility

Four ways of hiding something look identical on screen and are completely different to a screen reader. This chapter reads the browser's own accessibility tree rather than describing it — and opacity: 0 leaves a button fully present in it: announced, focusable, clickable.

Seven ways to hide something

Reading the real tree

These are not descriptions. Each row puts a button on a page with one hiding technique applied and then asks the browser for its accessibility tree — the same structure assistive technology consumes. A button either appears in it or it does not, which turns a topic usually taught as folklore into a table of measurements.

The same button, hidden seven ways
Three stay in the tree
display: none, visibility: hidden and [hidden] remove it entirely
Measured: none of the three appeared in the tree. They are the correct choice when the content should be gone for everyone.
opacity: 0 leaves it fully present
Still announced, still focusable, still clickable — an invisible button that a keyboard user will land on and a screen reader will read out.
.visually-hidden is invisible and announced
Which is the entire point of it: skip links, labels for icon-only buttons, live-region status text.
aria-hidden="true" is the exact inverse
Removed from the tree while remaining visible and clickable — right for decorative icons, wrong for anything focusable.
css — the utility, and why each line is there
.visually-hidden {
  position: absolute;          /* out of flow, so no space is taken   */
  width: 1px; height: 1px;     /* not 0 — a 0×0 box is dropped        */
  overflow: hidden;
  clip-path: inset(50%);       /* hides the 1px without removing it   */
  white-space: nowrap;         /* stop long text wrapping to nothing  */
}
/* and let it reappear on focus, for skip links */
.visually-hidden:focus-visible { position: static; width: auto; height: auto;
  overflow: visible; clip-path: none }

/* focus: style it, never remove it */
:focus-visible { outline: 3px solid var(--ring); outline-offset: 2px }
:focus:not(:focus-visible) { outline: none }   /* only if you must */

/* a ring visible on any background — chapter 14 measured shadows as free */
box-shadow: 0 0 0 2px #fff, 0 0 0 5px #0a6;

Three CSS features that change what is announced

Visual order is not reading order. order in flexbox, row-reverse, and grid placement all change where things appear without changing the DOM — so tab order and screen-reader order still follow the markup. A visually reordered form can be tabbed in a sequence that makes no sense, and the specifications are explicit that these properties are for visual reordering only. Fix the markup, not the CSS.

Generated content is sometimes read out. Text in a content property can be announced, so an icon inserted with content: "★" may be read as "black star". Use content: "" / "" — the second string is an explicit empty alternative — or put decorative glyphs in an aria-hidden element. And forced-colors mode replaces your palette entirely: backgrounds, borders and shadows are overridden, so anything conveying meaning purely through colour or a background image disappears. @media (forced-colors: active) is where you restore it, usually by adding a border.

Check yourself

Self-check

  1. Which hiding techniques remove an element from the accessibility tree?
    Measured against the browser's own tree: display: none, visibility: hidden and the hidden attribute all remove it, and opacity: 0, .visually-hidden and a plain button all leave it present. aria-hidden="true" also removes it while leaving the element visible and clickable. The four visual results are indistinguishable and the four accessible results are not, which is why this is worth measuring rather than remembering. The practical mapping: use display: none or [hidden] when the content should be gone for everyone, .visually-hidden when it should be announced but not seen, and aria-hidden only on decorative things that are not focusable.
  2. Why is opacity: 0 a bug when used to hide something?
    Because it hides the element from sighted users and from nobody else. Measured, an opacity: 0 button is still in the accessibility tree — announced by a screen reader — and it also still takes up space, still receives focus when tabbed to, and still responds to clicks. So a keyboard user tabs into a control they cannot see, and a screen-reader user hears a button that visually is not there. It is a common shortcut precisely because it is animatable where display is not, which is the real motivation — and chapter 16 measured the modern fix: transition-behavior: allow-discrete lets a fade-out end in display: none, giving the animation and the correct end state together.
  3. What does each line of the .visually-hidden utility do?
    position: absolute takes it out of flow so it occupies no space. width: 1px; height: 1px keeps it non-zero — a 0×0 box is treated as having nothing to render and some engines drop it from the tree, which defeats the purpose. overflow: hidden plus clip-path: inset(50%) hides that remaining pixel without removing the element. And white-space: nowrap stops long text wrapping inside a 1px box, which in some engines collapses it to nothing. Measured, the result is present in the accessibility tree — invisible and announced, which is the entire point. It is worth pairing with a :focus-visible rule that restores the element, since the classic use is a skip link that must appear when tabbed to.
  4. What is the difference between :focus and :focus-visible?
    Whether the browser judges a visible indicator to be warranted. Measured: after a mouse click the element matched :focus and not :focus-visible; after pressing Tab it matched both. The element is genuinely focused in both cases — only the second pseudo-class is heuristic. That heuristic is exactly the judgement developers used to make badly: focus rings appeared on mouse clicks, which looked untidy, so people wrote outline: none and removed the indicator for keyboard users too. :focus-visible is the platform making the call properly, taking input modality and element type into account — a text input gets a ring on click, because you may be about to type.
  5. Why is outline: none the canonical accessibility mistake?
    Because it removes the only signal a keyboard user has about where they are, and it is usually done for a cosmetic reason that :focus-visible now solves properly. If the default ring does not suit the design, replace it rather than delete it — and chapter 14 measured that an outline costs no layout at all, so a replacement cannot shift the page. A ring that survives any background is box-shadow: 0 0 0 2px #fff, 0 0 0 5px #0a6, two stacked shadows giving a light halo inside a dark ring. Two further points: outline-offset pushes the ring clear of the border without affecting layout, and modern outlines follow border-radius, which removed the last practical reason people reached for shadows instead.
  6. #767676 passes AA and #777777 fails. What does that tell you?
    That the boundary is sharp, arbitrary-looking and invisible to the eye. Measured, the two give 4.54 and 4.48 against white, either side of the 4.5 threshold for body text, and one hex step separates them. Two consequences follow. First, contrast has to be computed rather than judged — no designer can see the difference, and neither can you. Second, the thresholds themselves are a step function over a continuous quantity, so a value of 4.51 is not meaningfully better than 4.49 and both are worse than 7. The other numbers worth carrying: black on white is exactly 21, the formula's maximum; large text needs only 3; and non-text elements such as focus rings and input borders also need 3.
  7. Why does order in flexbox create an accessibility problem?
    Because it changes visual order and nothing else. Tab order and screen-reader order follow the DOM, so a form whose fields are visually rearranged with order is tabbed in the original sequence — which can mean focus jumping from the top of the form to the bottom and back. The same applies to flex-direction: row-reverse and to grid placement. The specifications are explicit that these are for visual reordering only and that the source should be in a logical order, which in practice means: if the visual order is the correct order, change the markup. The legitimate use is responsive rearrangement where both orders are sensible — and even then it is worth tabbing through the result at each breakpoint.
