Custom properties

Write color: red; color: var(--c) with --c holding nonsense, and the element does not fall back to red. It inherits its parent's colour — measured — throwing the red away entirely. That one behaviour explains most of the confusing failures custom properties produce.

When the value is wrong

A green parent, a child with color: red; color: var(--c)
Three of the four end up green
An invalid value makes the property inherit

Because substitution happens before parsing
A custom property is a token stream. By the time the browser discovers notacolour is not a colour, the cascade has already picked a winner, and the only remaining option is unset.
The var() fallback does not rescue it

css — the patterns worth having
@property --angle {
  syntax: '<angle>'; inherits: false; initial-value: 0deg;
}
.card { background: conic-gradient(from var(--angle), …);
        transition: --angle 1s }        /* now animatable */

/* theming: define once at the root, override anywhere down the tree */
:root       { --surface: #fff; --text: #111 }
.dark       { --surface: #111; --text: #eee }   /* a subtree, not a rebuild */
@media (prefers-color-scheme: dark) { :root { --surface: #111; --text: #eee } }

/* the space-toggle idiom: a variable used as a switch */
--on: initial;                 /* "false" — makes the declaration invalid */
--on: ;                        /* "true"  — an empty value is valid       */
.thing { --border: var(--on) 1px solid red }

/* reading and writing from script */
getComputedStyle(el).getPropertyValue('--c')
el.style.setProperty('--c', 'blue')
Custom properties resolve at computed-value time

This is the rule the whole chapter follows from, and it has two consequences worth stating plainly. First, a custom property is inherited by default and resolves per element, so --gap: 1rem on a container is visible to every descendant — which is what makes theming work, and what makes an accidental variable name collision reach further than expected. Second, resolution happens after the cascade has chosen a winner, which is why an invalid value cannot fall back to a losing declaration: that declaration is already gone. The same timing explains why a variable can hold a value that is invalid for one property and fine for another, and why var() cannot be used in a property name or a selector — those are decided long before values are computed.

Check yourself

Self-check

  1. color: red; color: var(--c) where --c: notacolour. What colour is the element?
    Its parent's colour — measured as rgb(0, 128, 0), the green the parent declared. The color: red is thrown away entirely. The mechanism is that custom properties are substituted before the value is parsed, so the cascade picks color: var(--c) as the winner while --c is still just a token stream. Only afterwards does the browser discover that notacolour is not a valid colour, and by then the losing declaration is gone — the specification calls this "invalid at computed-value time" and says the property becomes unset, which for an inherited property such as color means inherit. On a non-inherited property it would be the initial value instead, which is usually just as surprising.
  2. Does a var() fallback protect against that?
    No — measured, var(--c, orange) with --c: notacolour still produced the inherited green. The fallback is used when the variable is missing, not when its value turns out to be invalid for the property it is used in. That distinction catches almost everyone, because the fallback looks like a safety net and is really a default. So var(--c, orange) covers the case where nobody defined --c, and covers nothing at all when someone defined it badly — including the common real-world version, where a value that is perfectly valid in one context is meaningless in another. The genuine protection is @property with a declared syntax and initial-value, which makes the browser validate assignments and fall back to the initial value.
  3. Why can an invalid value not fall back to the previous declaration?
    Because the cascade has already finished by the time the value is checked. Ordinary invalid CSS is discarded at parse time, before the cascade runs, which is why color: notacolour written literally is simply ignored and an earlier color: red survives. A var() reference cannot be checked then, because the variable's value is not known until computed-value time, per element. So the declaration is treated as valid, wins the cascade, and only then fails — at which point there is no losing declaration left to fall back to. The same timing explains two other things: a variable can hold something valid for one property and invalid for another, and var() cannot appear in a selector or a property name, since both are resolved long before values are.
  4. What does @property registration make possible?
    Three things, all measured. It makes the property animatable: getAnimations() returned [] for an unregistered variable and ["--c"] for one registered with syntax: '<color>', because without a declared type there is nothing to interpolate and the value simply jumps. It allows inheritance to be turned off: a child read 3 from an unregistered parent variable and 7, the declared initial value, when registered with inherits: false. And it guarantees a value, so var() never resolves to nothing and the invalid-value failure above becomes a defined fallback. Registration also normalises the computed value — the registered property computed to rgb(255, 0, 0) where the unregistered one stayed the literal token.
  5. Why can you animate a conic gradient's angle only with @property?
    Because gradients themselves are not interpolable, but a registered <angle> is. Declaring @property --angle { syntax: '<angle>'; inherits: false; initial-value: 0deg } and then writing conic-gradient(from var(--angle), …) means the thing being animated is the angle — a single typed number — and the gradient is simply recomputed from it. Without registration the variable is an untyped token stream, so the browser has no notion of a halfway point between 0deg and 360deg and the value jumps. The same trick works for any effect built from a typed value: animated borders, progress rings, spotlight cursors. It is worth knowing this repaints on every frame, so it is not one of the cheap animations from chapter 22.
  6. How do custom properties differ from preprocessor variables?
    They exist at runtime and participate in the cascade, where a preprocessor variable is substituted at build time and then gone. That difference is the whole value: a custom property is inherited and resolves per element, so setting --surface on .dark restyles that entire subtree without any rules being rewritten, and a media query or a container query can change one variable rather than duplicating declarations. Script can read and write them with getPropertyValue and setProperty. The costs are the flip side: they resolve at computed-value time, which produces the invalid-value behaviour measured here, and they cannot appear where a preprocessor variable can — in a selector, a property name, or an @media condition, all of which are decided before values are computed.
  7. What is the "space toggle" idiom, and should you use it?
    A way to build conditional CSS out of the invalid-value behaviour. Setting a variable to initial makes any declaration using it invalid at computed-value time, so the declaration effectively disappears; setting it to an empty value makes the declaration valid, so it applies. That gives a boolean switch — --on: ; for true and --on: initial; for false — usable in any property, which was genuinely the only way to do conditional styling for a while. It is clever and it is very hard to read, since the mechanism is invisible in the declaration and the failure mode is silence. It is worth recognising in someone else's code and mostly worth avoiding in new code, because @container style() queries and if() express the same intent directly.
