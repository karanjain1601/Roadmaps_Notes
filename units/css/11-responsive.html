Media and container queries

A media query asks how wide the window is. That was the only question available for fifteen years, and it is the wrong one for a component that appears in both a sidebar and a main column. Measured here: the same markup in a 300px slot and a 600px slot, at one viewport, laid out identically under a media query and correctly under a container query.

Which is the whole argument
A component reusable in a sidebar and a main column cannot be styled by viewport. Before container queries the answer was a modifier class passed down from whoever placed it.
css — the query types worth knowing
/* container queries: mark the container, then ask about it */
.slot { container-type: inline-size; container-name: card }
@container card (min-width: 400px) { .card { flex-direction: row } }

/* the modern range syntax reads like the comparison it is */
@media (400px <= width <= 900px) { }        /* not min- and max- */
@media (width >= 400px) { }

/* the queries that ask about the PERSON, not the device */
@media (prefers-reduced-motion: reduce) { *, *::before { animation: none !important } }
@media (prefers-color-scheme: dark) { }
@media (prefers-contrast: more) { }
@media (prefers-reduced-transparency: reduce) { }
@media (pointer: coarse) { .hit { min-height: 44px } }   /* touch, not width */

/* and style queries — asking about a custom property */
@container style(--variant: featured) { }

The two limits worth knowing before you commit

A container cannot query itself. The element carrying container-type is queried by its descendants, not by its own rules — so the usual pattern is a wrapper around the component rather than the component itself. Forgetting this produces a query that silently never matches, which looks identical to unsupported syntax.

Containment is not free. container-type creates a containment context, which also establishes a containing block for absolutely positioned descendants — chapter 6's list, again — so a tooltip positioned against a far ancestor will suddenly position against the container instead. And size additionally makes the box not sized by its contents at all, which is a much larger change than the name suggests. Neither is a reason to avoid container queries; both are reasons to reach for inline-size on a dedicated wrapper rather than adding it to an existing layout element.

Check yourself

Self-check

  1. Why did the media query fire in a 300px slot?
    Because it asked about the viewport, which was 900px, and had no way to know the component was sitting in a 300px column. Measured: flex-direction came out as row in both slots under @media (min-width: 400px), and as column then row under the equivalent @container rule — same markup, same stylesheet, same viewport. That is the whole case for container queries. A card that appears in a sidebar and in a main column has two correct layouts and one viewport, so no media query can express it. Before container queries the workaround was a modifier class passed down by whoever placed the component, which pushes knowledge of the layout into every call site and breaks the moment someone reuses it somewhere new.
  2. What is cqw, and how does it differ from vw?
    1cqw is 1% of the query container's inline size, where 1vw is 1% of the viewport's. Measured, width: 50cqw gave 150px inside a 300px container and 300px inside a 600px one, from the identical declaration. It is the unit equivalent of the query: where @container lets you switch layouts at a threshold, cqw lets you scale continuously with the slot. The family is cqw, cqh, cqi and cqb for inline and block, plus cqmin and cqmax. The most useful application is fluid type inside a component — font-size: clamp(1rem, 4cqi, 2rem) scales with the container rather than the window, which is what a card in a resizable panel actually wants.
  3. Your container query does nothing. What are the two likely causes?
    A missing container-type, or querying the wrong element. Measured, container-type: normal — the default — is not a query container at all, so the @container rule simply did not match; you have to opt in explicitly. The second cause is subtler: a container is queried by its descendants, never by its own rules, so putting container-type on the component and then writing @container rules for that same component silently never matches. The usual pattern is a dedicated wrapper around the component. Both failures look identical to unsupported syntax, which makes them frustrating to diagnose — the quick check is to give the container an obvious temporary outline and confirm in devtools that it is listed as a container.
  4. What does container-type: size do that inline-size does not?
    It applies containment on the block axis too, so the container stops being sized by its content. Measured, a container with an 80px child collapsed to 0px tall under size and stayed at 80px under inline-size. That is a much larger change than the name suggests, and it is why inline-size is nearly always the right choice: it contains only the inline axis, which is enough to answer width questions, and leaves the height following its content as normal. Reach for size only when the container already has an explicit height and you genuinely need to query the block axis — a fixed-height panel deciding whether to show a summary or a detail view, for instance. Both also establish a containing block for absolutely positioned descendants, which is chapter 6's list appearing again.
  5. Which media queries ask about the person rather than the device?
    The preference queries, and they are the more valuable half of the feature. prefers-reduced-motion reports an operating-system setting for people who get motion sickness from parallax and large transitions, and honouring it is close to mandatory — chapter 17 treats it as such. prefers-color-scheme gives dark mode without a toggle. prefers-contrast and prefers-reduced-transparency cover low-vision needs. And pointer: coarse asks whether the primary input is a finger, which is a far better test for enlarging hit targets than guessing from width — a touchscreen laptop is wide and needs big targets, and a small window on a desktop is narrow and does not. Guessing capability from width has always been a proxy; these queries ask directly.
  6. What is wrong with min-width and max-width in media queries?
    Mostly that they read badly and overlap by one pixel. @media (max-width: 399px) and @media (min-width: 400px) is the correct pairing, but 399 is a fractional-pixel hazard on zoomed or high-density displays, and writing 400 in both creates a range where both rules apply. The range syntax says what you mean: @media (width >= 400px), or @media (400px <= width < 900px) for a band, with no off-by-one and no ambiguity about which end is inclusive. It is supported across current browsers and reads like the comparison it is. The related habit worth adopting is mobile-first — write the narrow layout unprefixed and add @media (width >= …) for wider ones — so the base stylesheet works when a query fails to match for any reason.
  7. Should container queries replace media queries?
    No — they answer different questions and both remain useful. Container queries are right for components: anything reusable in more than one slot should size itself against its slot, which the measurement here makes concrete. Media queries remain right for anything genuinely about the viewport or the device: the page-level layout that creates the slots in the first place, print styles, and every preference query, none of which has a container equivalent. A good rule of thumb is that the page shell uses media queries to decide how many columns exist, and everything inside uses container queries to decide how to fill whatever column it landed in. The two compose cleanly, and the practical migration is to move component-level breakpoints to @container and leave the shell alone.
