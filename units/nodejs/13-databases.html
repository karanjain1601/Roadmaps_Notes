Databases and pooling

Node's data layer is unusually unopinionated: no equivalent of JPA, no single default, and a spectrum from raw SQL to full ORM that you pick a point on. Two things go wrong regardless of the point you pick, and both are about which connection your query ran on.

The Node-specific observation

There is no persistence context here — nothing like the machinery in chapters 9 to 11 of the Spring Boot unit. No dirty checking, no lazy proxies, no LazyInitializationException, and no accidental UPDATE from touching a field. What you send is what runs. That removes a whole category of confusion, and it removes the automatic identity map too, so N+1 is entirely yours to avoid — usually by writing the join, or by batching ids with DataLoader. Chapter 12 of the Backend unit still applies; you just have fewer tools doing it accidentally on your behalf.

import { Pool } from "pg";

export const pool = new Pool({
  max: 10,                          ← × workers × instances. See above.
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 3_000,   ← how long a request waits for a
                                       connection before failing. Must be
                                       well under your request timeout
  maxLifetimeSeconds: 1_740,         ← 29 min: retire connections before a
                                       proxy or the database drops them,
  statement_timeout: 10_000,           or you will meet ECONNRESET
  query_timeout: 10_000,
});

// ✱ the one everybody forgets. An idle pooled connection that errors
//   emits on the POOL, and chapter 5 applies: unhandled, it ends the
//   process — during a database failover, on every instance at once.
pool.on("error", (err) => logger.error({ err }, "idle client error"));

// ── parameterised, always. Backend chapter 15. ──
await pool.query("select * from orders where id = $1", [id]);   ✓
await sql`select * from orders where id = ${id}`;                  ✓ postgres.js —
//   the tagged template CANNOT interpolate; it always parameterises
await pool.query(`select * from orders where id = '${id}'`);      ✗

// ── and note what you cannot parameterise: identifiers ──
//   order by $1  does not work. If a sort column comes from the
//   client, validate it against an allow-list — there is no other way.

Transactions, and which client ran your query

One line in the wrong place
Look at what survives the rollback
javascript — the shape that cannot go wrong
// ✓ a helper, so nobody writes BEGIN by hand again
export async function transaction(fn) {
  const client = await pool.connect();
  try {
    await client.query("begin");
    const out = await fn(client);      ← the callback receives the client,
    await client.query("commit");        so there is nothing else to use
    return out;
  } catch (err) {
    await client.query("rollback").catch(() => {});   ← swallow, or a
    throw err;                                         failed rollback
  } finally {                                            masks the real
    client.release();       ← ALWAYS. In finally, unconditionally.
  }                           Miss this on the error path and the pool
}                             drains one connection per failed request.

// used like this, and the wrong-client bug becomes unwritable:
await transaction(async (tx) => {
  const order = await tx.query(INSERT_ORDER, [...]);
  await tx.query(INSERT_AUDIT, [order.rows[0].id]);
});
// postgres.js and Kysely both provide this shape natively:
//   await sql.begin(async (tx) => { … })
//   await db.transaction().execute(async (trx) => { … })

// ✱ and never await something slow inside a transaction — an HTTP
//   call, a hash, a queue publish. The connection and any locks are

Migrations, as a pipeline step
Not on application startup — several instances would race, and a failed migration would stop every one of them from booting. Chapter 19. Any of node-pg-migrate, Kysely's migrator, Drizzle Kit or Prisma Migrate; what matters is that the files are checked in, forward-only, and backwards compatible with the running version.
Prepared statements and PgBouncer
In transaction-pooling mode, a prepared statement created on one server connection may not exist on the next, so drivers relying on them break. Use session pooling, or turn off prepared statements in the driver. This bites the first time you put a pooler in front of an existing service.
Read replicas
Two pools and an explicit choice per query, not automatic routing — because read-your-writes will break the moment something reads after writing. Chapter 11 of the Backend unit.
N+1 is yours to avoid
With no identity map and no lazy loading, an ORM will not accidentally fire a hundred queries — and it also will not batch them for you. A loop calling findById is a hundred round trips exactly as written. Write the join, or use DataLoader to batch ids within a tick.

Self-check

  1. Why does cluster multiply your connection count?
    Because each worker is a separate process with its own module instances, so each one creates its own pool with its own maximum. Eight workers with a pool of ten is eighty connections per instance, not ten — and multiplied by instances it reaches the database's limit very quickly. The pool size has to be divided by the worker count, or the pool moved outside the process into a pooler like PgBouncer.
  2. What goes wrong when a pool.query appears inside a transaction?
    It runs on a different connection. BEGIN was issued on one pooled client, and pool.query checks out whichever client is free — so that statement executes outside the transaction and autocommits immediately. If the transaction later rolls back, everything issued through the client is undone and the one issued through the pool survives. Nothing errors, and the data is left in a state the code says is impossible.
  3. Why must client.release() be in a finally?
    Because otherwise the error path leaks the connection. Every failed request removes one client from the pool permanently, so a pool of ten survives ten failures and then every subsequent request waits for a connection that will never be returned — until the connection timeout fires and everything starts failing. The symptom is a service that works, degrades over hours in proportion to the error rate, and recovers on restart.
  4. Why is a tagged-template driver safer by construction?
    Because the template tag receives the static strings and the interpolated values as separate arguments, so the values cannot become part of the SQL text — parameterisation is not something you remember to do, it is the only thing the syntax can express. With a plain query(string) API, the safe and unsafe forms look almost identical and differ by a backtick.
  5. What can you not parameterise?
    Identifiers — table names, column names, and the direction in an ORDER BY. Placeholders are for values, and the database plans the statement before it sees them, so a column name cannot arrive that way. If a sort column or a filter field comes from the client, map it through an allow-list to a known-good literal. There is no escaping approach that is as safe as a lookup table.
  6. Why does putting PgBouncer in front sometimes break a working service?
    Transaction pooling. Server connections are handed out per transaction rather than per session, so anything with session state — prepared statements, temporary tables, SET settings, advisory locks held across statements — may find itself on a different connection than the one that created it. Drivers that prepare statements by default are the usual casualty. Use session pooling, or disable prepared statements in the driver.
