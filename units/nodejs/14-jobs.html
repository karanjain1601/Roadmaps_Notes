Caching and background jobs

Two ways to get work off the request path. Node has one genuinely elegant advantage here — a pending promise is already a deduplication primitive, so single-flight is four lines — and one recurring trap, which is that a worker's concurrency setting cannot buy what the single thread does not have.

javascript — single-flight, and why it is so short in Node
const inflight = new Map();

export function once(key, fn) {
  let p = inflight.get(key);
  if (!p) {
    p = fn().finally(() => inflight.delete(key));   ← finally, so a
    inflight.set(key, p);                             rejection does not
  }                                                   cache forever
  return p;
}
// ✱ the insight: a pending promise IS the deduplication. Every caller
//   awaiting the same promise gets the same result from one execution.
//   No mutex, no condition variable, no double-checked locking — the
//   single thread means Map.get and Map.set cannot interleave.

const cached = async (key) => {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);
  return once(key, async () => {
    const v = await db.expensiveQuery(key);
    await redis.set(key, JSON.stringify(v), "EX", jitter(300));
    return v;                                       ↑ jitter the TTL,
  });                                  or a thousand keys written together
};                                     will expire together

// ── and the version that survives many processes ──
//   ① serve the stale value immediately
//   ② one holder of a short Redis lock refreshes in the background
//   ③ everyone else gets stale data and nobody waits
// store { value, expiresAt } and treat "expired" as "refresh soon",
// not "the answer is gone". Backend chapter 11.

import { Queue, Worker } from "bullmq";

const queue = new Queue("emails", { connection });

await queue.add("welcome", { userId }, {
  jobId: `welcome:${userId}`,      ← the queue's idempotency: adding the
                                  same jobId twice is a no-op
  attempts: 5,
  backoff: { type: "exponential", delay: 1_000 },
  removeOnComplete: { age: 3600, count: 1000 },   ← or Redis grows
  removeOnFail: { age: 86_400 },                  without limit
});

const worker = new Worker("emails", async (job) => {
  await send(job.data);      ← must be idempotent. At-least-once
}, {                            delivery means this WILL run twice
  connection,                   eventually — Backend chapter 18

  await worker.close();     ← stops taking new jobs, finishes current

Scheduling across instances
Four instances with a setInterval or a node-cron job means the job runs four times. Use the queue's own repeatable jobs, which are scheduled centrally in Redis, or take a distributed lock. This is the same problem as chapter 17 of the Spring Boot unit, and it is discovered the same way — by someone receiving four identical emails.
Which Redis client
ioredis for cluster support and because BullMQ requires it; node-redis otherwise. Either way: set a maxRetriesPerRequest, attach an error listener, and remember that a blocking command such as BRPOP occupies its connection entirely — a worker needs its own.
Don't cache in the process
A module-level Map is not shared between instances or cluster workers and is lost on every deploy, so hit rates are divided by the process count and invalidation is impossible. It is fine for something derived and immutable — a compiled schema, a parsed config. It is not a cache of your data.
Queue or event log
BullMQ is a work queue: a job is delivered to one consumer and removed. If several independent consumers need the same event, or you need to replay history, that is a log — Redis Streams or Kafka. Chapter 18 of the Backend unit.

Self-check

  1. Why is single-flight so short in Node compared with a threaded runtime?
    Because a pending promise already is the deduplication: every caller that awaits the same promise receives the same result from one execution. And because there is one thread, the check-then-set on the map cannot interleave — nothing can run between Map.get returning nothing and Map.set storing the promise. In a threaded runtime that same pattern needs a lock or a concurrent map with atomic computeIfAbsent semantics.
  2. What does in-process single-flight not solve?
    Anything beyond the process. The map is per-process, so eight instances collapse their own stampedes and still send eight queries — and with cluster workers it is eight per instance. It turns a hundred queries into one locally, which is usually the bulk of the benefit, but for a genuinely expensive query across a large fleet you need a shared lock and, better, stale-while-revalidate so nobody waits at all.
  3. Why jitter a cache TTL?
    Because keys written together expire together. A deploy that warms a thousand keys, or a batch job that populates them in one pass, creates a synchronised expiry that produces a burst of misses at the same instant — and single-flight does not help, since the keys are all different. A random spread of ten or twenty per cent over the TTL turns a spike into a smooth trickle for the cost of one function call.
  4. Does raising a worker's concurrency help a CPU-bound job?
    No. Concurrency lets the worker have n jobs in flight on one thread, which only helps while those jobs are waiting — for a network call, a database query, an API. CPU work does not overlap with anything, so ten concurrent hash jobs take exactly as long as ten sequential ones and simply make each individual job's latency worse. For CPU-bound work you need more threads or more processes, which is chapter 15.
  5. Why must a job handler be idempotent?
    Because delivery is at-least-once. A worker that crashes after doing the work but before acknowledging will have the job redelivered, and a retry after a timeout may run alongside an attempt that is still going. So the handler will eventually run twice for the same job, and it must produce the same outcome — through a natural key, an upsert, or a processed-ids table. The jobId option deduplicates at enqueue time, which is a different problem.
  6. What happens with a setInterval job on four instances?
    It runs four times, once per process — and with cluster workers, once per worker. Nothing coordinates them, so a nightly report is generated four times and a reminder email is sent four times. Use the queue's repeatable jobs, which are scheduled centrally in Redis and delivered to exactly one worker, or take a distributed lock around the body. It is almost always found in production rather than in review.
