Cluster, workers and child processes

Three ways to escape the single thread, and they are not interchangeable. Two of them multiply your processes and therefore everything a process owns — connection pools, in-memory state, cron timers. The third keeps one process and charges you for every byte that crosses the boundary.

What cluster silently breaks
  • Connection pools. Eight workers with a pool of ten is eighty connections from one instance — chapter 13's demo.
  • In-memory anything. A rate-limit counter, a session store, a cache, a WebSocket registry: each worker has its own, so a limit of 100 is really 100 × workers and a socket registered on worker 3 is invisible to worker 5.
  • Timers. A setInterval or node-cron job runs once per worker. Chapter 14.
  • Sticky sessions. Round-robin means consecutive requests from one client land on different workers, which breaks anything holding per-connection state — and WebSockets need a sticky strategy or a shared adapter.
  • Metrics. Each worker exposes its own /metrics, so a scrape gets one worker's view. You need an aggregator.

javascript — a worker pool, and the three ways to pass data
// ── use piscina rather than writing a pool. It handles queueing,
//    idle timeouts, crashed workers and abort signals. ──
import Piscina from "piscina";
import os from "node:os";

const pool = new Piscina({
  filename: new URL("./resize-worker.js", import.meta.url).href,
  maxThreads: os.availableParallelism() - 1,   ← leave one for the
  idleTimeout: 30_000,                          main thread
});

// ① structured clone — the default. COPIES, on the main thread.
await pool.run({ buf });                ← buf is duplicated: ~2.5 ms/MB
                                          of blocking, before any work

// ② transferList — MOVES the memory. Nearly free.
await pool.run({ buf }, { transferList: [buf.buffer] });
//   the ArrayBuffer is detached here and owned there. Touching it
//   afterwards throws — which is the point: no copy, no sharing bug.

// ③ SharedArrayBuffer — both threads see the same memory.
const shared = new SharedArrayBuffer(size);
//   zero copy either way, and now you have real shared mutable state:
//   coordinate with Atomics, or corrupt it. Reach for this last.

// ── inside the worker ──
export default async function ({ buf }) {
  return resize(buf);       ← piscina makes it a plain function
}
// ✱ a worker has its own module graph, so every import is loaded
//   again per thread — chapter 1's startup cost, multiplied. Keep
//   worker files small; do not import your whole application.
// ✱ AsyncLocalStorage does NOT cross the boundary. Pass the request
//   id in the message — chapter 5.
Start with more containers
Your orchestrator already restarts, schedules, limits and load-balances processes. cluster reimplements a worse version of that inside one container, and then you own the supervision. If you can add replicas, do that first and read the rest of this chapter only if you cannot.
availableParallelism(), not cpus().length
In a container with a CPU limit of one, os.cpus().length reports the host's core count — often 64 — so a worker-per-core pool creates 64 threads fighting over one core's worth of quota. os.availableParallelism() respects the cgroup. Chapter 19.
Workers are not free to create
Each one is a fresh V8 isolate with its own heap and its own module graph, so spawning costs tens of milliseconds and tens of megabytes. Always a pool, never one per request.
The honest default
Most Node services need none of this. If the event loop lag from chapter 3 is low, adding threads adds complexity and no capacity. Measure first — chapter 16 — and reach for a worker pool only when a specific, bounded computation is provably the constraint.

Self-check

  1. Why is "more containers" usually a better answer than cluster?
    Because the orchestrator already does everything cluster does, and does it better: restarts on crash, schedules across hosts, applies memory and CPU limits per process, and load-balances with health checks. cluster reimplements supervision inside one container, and it multiplies everything a process owns — pools, caches, timers, rate-limit counters — which is a set of bugs you did not have. The parallelism is identical either way.
  2. What does a worker-thread pool give that cluster does not?
    One process. So one connection pool, one in-memory cache, one set of cron timers, one metrics endpoint, and one WebSocket registry — none of the multiplication problems. The main thread stays free to serve requests while the threads compute. The trade is that nothing is shared automatically: data crosses by message, and the boundary has a cost proportional to the payload.
  3. When does offloading to a worker make things worse?
    When the structured clone costs more main-thread time than the work you moved. Cloning is a copy performed on the calling thread, at roughly two and a half milliseconds a megabyte, so handing a forty-megabyte buffer to a worker blocks the main thread for about a hundred milliseconds — and if the job itself was twenty milliseconds you have made the loop block five times longer for no gain. Use a transfer list, or keep it inline.
  4. What does a transfer list do differently?
    It moves the memory instead of copying it. The ArrayBuffer is detached from the sending thread and adopted by the receiving one, so the cost is constant rather than proportional to size — and touching the buffer afterwards throws, which is a feature: the ownership transfer is enforced rather than assumed. It is the right default for any sizeable binary payload.
  5. Why is os.cpus().length the wrong number in a container?
    Because it reports the host's cores, not your cgroup quota. On a 64-core host with a CPU limit of one, it returns 64 — so a worker-per-core pool spawns 64 threads and tens of gigabytes of intent, all contending for one core's worth of scheduling. Every one of them is slower than a single thread would have been. os.availableParallelism() reads the limit and is the number to use.
  6. Why must worker files stay small?
    Because each worker has its own module graph and loads every import independently. Importing your application's root from a worker means resolving and compiling the whole dependency tree once per thread — chapter 1's startup cost multiplied by the pool size, in both time and heap. A worker should import the two or three things the computation needs and nothing else.
