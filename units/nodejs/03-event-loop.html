The event loop

The most important chapter in the unit. Almost every confusing Node behaviour — a timer that fired late, an await that did not yield where you expected, one endpoint making every endpoint slow — is this loop doing precisely what it is specified to do.

nextTick against a promise, and why it matters

Both are microtask-like and drain between callbacks, but the nextTick queue drains entirely first — and it is drained again after each microtask batch. So a recursive process.nextTick starves the loop completely: no timers, no I/O, nothing, forever, with the process at 100% CPU and no error. A recursive setImmediate is the well-behaved equivalent, because check is a phase the loop passes through once per iteration rather than a queue it must empty. The practical rule: use setImmediate to yield, and reach for nextTick almost never — its remaining legitimate use is deferring something to just after the current operation, and even then queueMicrotask is usually clearer.

// ── ① chunking: buys FAIRNESS, not capacity ──
async function hashAll(items) {
  let since = performance.now();
  for (const it of items) {
    hash(it);
    if (performance.now() - since > 5) {          ← every 5 ms of work,
      await new Promise(setImmediate);              hand the loop back
      since = performance.now();
    }
  }
}
// the total CPU is identical. What changes is that a health check no
// longer waits behind the whole job — it waits at most one chunk.

setTimeout(fn, 0) is not zero
Node clamps it to 1 ms, and the callback runs in the next timers phase — which is whenever the loop gets there. Under load that can be tens of milliseconds. Timers are a floor, never a guarantee, and a long-running callback delays every other timer behind it.
Why the process exits, or does not
The loop runs while any handle is active. An open server, a pending timer or a live socket keeps the process alive; unref() tells the loop to ignore a handle for that purpose, which is what you want on a metrics interval or a shutdown deadline so it cannot hold the process open.
Synchronous APIs
readFileSync, execSync, crypto.pbkdf2Sync, zlib.gzipSync and JSON.parse on a large payload all block the loop for their whole duration. They are fine at startup and in a CLI; in a request handler each one is a bomb whose size is the input's size.
Where await actually yields
await yields at the point the awaited value is pending. Awaiting an already-resolved promise still defers the continuation to the microtask queue, but no loop phase runs in between — so await inside a tight computational loop does not let other requests through. Only a macrotask boundary such as setImmediate does that, which is why the chunking pattern above uses it.

Self-check

  1. Why does process.nextTick run before a resolved promise's .then?
    Because Node drains the nextTick queue completely before touching the promise microtask queue, and drains it again after each microtask batch. It is a Node-specific queue with higher priority than the language's microtasks. The practical consequence is that a recursive nextTick starves everything — no timers, no I/O, no other callbacks — at full CPU and with no error.
  2. Why does setImmediate run after a setTimeout(fn, 0) at the top level but before one registered inside an I/O callback?
    Because of where the loop is when each is registered. At the top level, the loop's first iteration reaches timers before check, so the timeout wins. Inside an I/O callback the loop is already in the poll phase, and check comes next in the same iteration while timers is not visited again until the following one — so the immediate wins. Same two calls, opposite order, entirely determined by phase position.
  3. Why is setImmediate the right way to yield and nextTick the wrong one?
    Because check is a phase the loop passes through once per iteration, so scheduling into it lets a full iteration run in between — timers fire, I/O callbacks run, other requests progress. The nextTick queue must be emptied before the loop advances at all, so recursively adding to it means the loop never moves. Yielding with setImmediate gives other work a turn; yielding with nextTick gives it nothing.
  4. Twelve milliseconds of CPU per request at sixty requests a second. Why is the health check at risk?
    Because utilisation is 72%, and at that level queueing is substantial — a request arriving must wait for whatever is already executing plus whatever is queued ahead of it, and the health check queues like everything else. It needs no CPU of its own and still waits tens of milliseconds. Push utilisation towards 100% and the wait grows without bound, the probe times out, and the orchestrator restarts a process that was merely busy.
  5. Does chunking with setImmediate increase throughput?
    No. The total CPU work is identical, so capacity is unchanged — if arrivals exceed capacity the queue still grows without bound. What chunking changes is fairness: the longest single block drops from the whole job to one chunk, so short requests and health checks are no longer stuck behind a long one. It converts "the service is down" into "the service is slow", which is a real improvement and not a capacity fix. Only another thread or another process adds capacity.
  6. Why doesn't await inside a computational loop let other requests through?
    Because awaiting an already-resolved value only defers the continuation to the microtask queue, and microtasks drain before the loop advances a phase. No timer fires and no I/O callback runs in between, so from the loop's point of view you are still in one long callback. To actually yield you need a macrotask boundary — await new Promise(setImmediate) — which lets a full loop iteration happen.
