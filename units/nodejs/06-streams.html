Streams and backpressure

Node takes streams more seriously than most runtimes, and the reason is chapter 3: with one thread and no per-connection memory, the only way to move data larger than your heap is to move it in pieces. Backpressure is the part that makes that safe, and the part people skip.

javascript — three ways to move a file, only one of them safe
// ✗ ① buffer the whole thing. Fine for a 4 KB config, fatal for a
//      2 GB upload — and the size is decided by whoever uploads.
const buf = await readFile(src);
await writeFile(dst, buf);
//    also blocks: JSON.parse on 200 MB is chapter 3's problem too.

// ✗ ② write in a loop, ignoring the return value
for await (const chunk of source) {
  out.write(chunk);              ← write() returns false when the
}                                  internal buffer is over its
//    the loop keeps going, so every chunk    highWaterMark. Ignoring
//    the destination has not drained yet     that IS the leak.
//    accumulates in memory.

// ✓ ③ pipeline. Honours backpressure, propagates errors, destroys
//      every stream on failure.
import { pipeline } from "node:stream/promises";
await pipeline(
  createReadStream(src),
  createGzip(),
  createWriteStream(dst),
);
//    memory stays at roughly highWaterMark per stream — 64 KB each
//    by default — regardless of whether the file is 2 MB or 2 TB.

// and if you must write manually, this is the contract:
if (!out.write(chunk)) {
  await once(out, "drain");      ← wait, then continue
}

Why .pipe() is effectively deprecated for real use

.pipe() forwards data and does nothing else. It does not forward errors, and it does not destroy the other streams when one fails. So a destination that errors leaves the source open, reading, buffering and holding a file descriptor — and an 'error' event with no listener is chapter 5's process-killing throw.

pipeline() was added precisely for this: it wires up error propagation, destroys every stream in the chain on any failure, and with the node:stream/promises version gives you an awaitable that rejects. The rule is simple — use pipeline, always, and treat a bare .pipe() in a code review as a defect.

javascript — the patterns worth having to hand
// ── line by line, with constant memory, over a 40 GB log ──
import { createInterface } from "node:readline";
for await (const line of createInterface({ input: createReadStream(p) })) {
  if (line.includes("ERROR")) count++;
}
//   note: `for await` honours backpressure automatically, because the
//   loop body must finish before the next chunk is requested.

// ── a transform, as an async generator. Far nicer than subclassing. ──
async function* toJsonl(rows) {
  for await (const row of rows) yield JSON.stringify(row) + "\n";
}
await pipeline(db.queryStream(sql), toJsonl, createWriteStream(out));
//   pipeline accepts async generators directly — no Transform class,
//   no _transform callback, no push().

// ── streaming a large export to the client: constant memory, and
//    the first byte arrives immediately ──
app.get("/export", async (req, res) => {
  res.setHeader("content-type", "application/x-ndjson");
  try {
    await pipeline(db.queryStream(sql), toJsonl, res,
                   { signal: AbortSignal.timeout(300_000) });
  } catch (err) {
    // ✱ headers are already sent, so you cannot change the status.
    //   Log it, destroy the response, and accept a truncated body —
    //   which is why NDJSON beats a single JSON array here: the client
    //   can tell it was cut off.
    if (!res.headersSent) res.writeHead(500);
    res.destroy(err);
  }
});
Web Streams as well
Node also implements the ReadableStream from the web platform, which is what fetch bodies are. Readable.fromWeb and Readable.toWeb convert between the two. Use Node streams inside Node, and convert at the edges rather than mixing them in one pipeline.
When not to stream
When the payload is small and bounded, or when you need the whole value before you can act — parsing JSON you must validate as a unit, for instance. Streaming a 2 KB response adds complexity and no benefit. The question is whether the size is bounded by you or chosen by the client.
Object mode's highWaterMark is 16
Sixteen objects, not sixteen kilobytes — and an object can be a megabyte. A pipeline of object-mode transforms over large records can therefore buffer far more than you expect while every stream reports itself as within its limit.
Always handle 'error'
On every stream you hold a reference to. Chapter 5: an EventEmitter 'error' with no listener is thrown, and a thrown error from an I/O callback ends the process. pipeline handles this for the chain; a stream you keep outside one still needs it.

Self-check

  1. What does write() returning false mean, and what happens if you ignore it?
    It means the writable's internal buffer has passed its highWaterMark and you should stop until it emits 'drain'. Ignoring it does not lose data — everything is queued — which is exactly the problem: the queue is your heap. With a source faster than the destination, memory grows at the difference between the two rates until the process is killed. That is the backpressure signal, and honouring it is the whole mechanism.
  2. Why does a 90 MB/s source and a 12 MB/s destination end in a crash without backpressure?
    Because 78 MB a second has nowhere to go but the writable's buffer. Memory climbs linearly, and with a 512 MB heap the process is killed in under seven seconds — sooner if anything else is allocated. With backpressure the source is simply throttled to the destination's rate: the transfer takes as long as the slow end needs, and memory stays at roughly the high-water mark regardless of total size.
  3. Why is .pipe() unsafe for anything that can fail?
    Because it only forwards data. It does not forward errors and it does not destroy the other streams when one fails, so a destination that errors — a client disconnecting, most commonly — leaves the source open, reading and holding a file descriptor. The leak accumulates per request, and an unattached 'error' on any of those streams is a thrown error from an I/O callback, which ends the process. pipeline exists to fix exactly this.
  4. What eventually happens to a server leaking one descriptor per aborted download?
    It hits the process limit and every subsequent operation fails with EMFILE — not just file reads, but accepting sockets, so the server stops serving entirely while looking healthy by most measures. Memory climbs alongside, since each abandoned stream keeps its buffers. The clue in the logs is EMFILE or ENFILE appearing on unrelated operations, and the fix is a single word.
  5. Why is object mode's default highWaterMark a trap?
    Because it counts objects rather than bytes — sixteen of them, whatever they weigh. Sixteen database rows is nothing; sixteen parsed multi-megabyte documents is hundreds of megabytes, and every stream in the chain reports itself as comfortably within its limit. If your object-mode chunks are large, set the high-water mark explicitly and low, or the backpressure mechanism is measuring the wrong thing.
  6. You are streaming an export and the query fails halfway. What can you do about the status code?
    Nothing — the headers went out with the first chunk, so a 200 is already committed and the connection can only be truncated. That is the trade for streaming, and it is why a line-delimited format is better than one large JSON array for exports: the client can detect an incomplete stream. Log the failure, destroy the response so the client sees an aborted transfer rather than a hang, and consider a trailing sentinel record the client can check for.
