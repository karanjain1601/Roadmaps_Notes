Testing

Node's test tooling got quietly good: there is a runner in the standard library, and Vitest made the fast path pleasant. The harder question is unchanged — a test that passes tells you nothing about production unless the thing it replaced behaves like the thing it replaced.

The runners

Note
node:testBuilt in since Node 18, stable since 20. No dependency, no config, real ESM, --test --watch and coverage included. The right default for a backend service
VitestFast, Vite-powered, excellent watch mode, Jest-compatible assertions, first-class TypeScript. Worth it if you want browser-style mocking or share config with a front end
JestEnormous ecosystem and the assertions everyone knows. Its ESM support is still awkward, and its module registry per file is where much of the slowness comes from
Assertionsnode:assert/strict — deepStrictEqual, rejects, throws. Adequate, and one fewer dependency
HTTP testsFastify's app.inject() needs no socket at all; supertest for Express; or fetch against a server on port 0
Containerstestcontainers for a real Postgres or Redis in a globalSetup. The single highest-value change to most Node suites

import { test, before, after, mock } from "node:test";
import assert from "node:assert/strict";

// ── globalSetup: ONE container for the whole suite ──
import { PostgreSqlContainer } from "@testcontainers/postgresql";

export default async function setup() {
  const pg = await new PostgreSqlContainer("postgres:16-alpine")
    .withReuse()                       ← keeps it alive between local runs.
    .start();                            Turns 9 s of startup into 0.2 s
  process.env.DATABASE_URL = pg.getConnectionUri();
  await runMigrations();               ← the real migrations, so the schema
  return () => pg.stop();                is the one you ship
}

// ── isolate with a transaction, not by truncating ──
test("rejects a duplicate order reference", async (t) => {
  await withRollback(async (tx) => {          ← begin, run, always rollback:
    await orders.create(tx, { ref: "A-1" });    fast, and tests cannot
    await assert.rejects(                       see each other's rows
      () => orders.create(tx, { ref: "A-1" }),
      (e) => e.code === "23505",             ← the REAL constraint fired.
    );                                          A mock could not have
  });                                           told you this
});

// ── HTTP without a socket, with Fastify ──
test("GET /orders/:id returns 404 for an unknown id", async () => {
  const res = await app.inject({ method: "GET", url: "/orders/" + uuid() });
  assert.equal(res.statusCode, 404);
  assert.equal(res.json().type, "https://api.shop/problems/not-found");
});
// exercises the whole lifecycle from chapter 10 — hooks, validation,

Why the suite is slow

Where the wall time goes
Per-file setup is the multiplier
90
4
Each test file gets a fresh module registry
Vitest and Jest run files in worker processes with isolated module graphs, so module-level code runs once per file — a pool created at import, a config parse, a client construction. That is the Node analogue of Spring's context cache, and it is why moving expensive setup into globalSetup is usually the largest single win available.
Isolate with a transaction
Begin before each test and roll back after. Faster than truncating, and it means tests cannot see each other's rows, so they can run in parallel against one database. The exception is anything that must observe a real commit — a trigger, a NOTIFY, or code that opens its own connection.
Fix flakiness, never retry it
A retried test is a test you no longer believe. In Node the usual causes are narrow: a real timer somewhere, an unawaited promise, a shared module-level variable between files, or ordering assumptions about a Map. Run with --detectOpenHandles and fix what it names.
Coverage measures execution, not verification
A test that calls a function and asserts nothing gives full coverage of it. Useful as a floor and as a way to find whole files nobody exercises; useless as a quality target. Chapter 14 of the Spring Boot unit makes the same argument.

Self-check

  1. Why does a mocked repository hide a whole class of bug?
    Because the mock implements what you believe the database does, not what it does. Unique constraints, foreign keys, check constraints, NOT NULL, default values, cascade behaviour, type coercion and isolation semantics are all in the database and absent from the mock. So the test proves the handler calls the repository correctly and says nothing about whether the write can succeed — and duplicate submissions are precisely the case nobody thinks to mock.
  2. How can fake timers hide a missing timeout?
    Because the stubbed call resolves immediately, so the absence of a deadline is unobservable. fetch has no default timeout — chapter 4 — and a test where the response is instant never waits, never hangs and never fails. In production the same code against a server that accepts the connection and never replies waits forever, holding the request and whatever it holds. Assert on the timeout: stub a call that never resolves and check the handler rejects.
  3. What does in-memory SQLite fail to reproduce?
    Most of what you rely on. Different type affinity, different NULL and case-sensitivity behaviour, no ILIKE, different JSON functions, no real concurrency, weaker constraint enforcement and entirely different isolation and locking. So a suite passes against SQLite and the same query fails or returns different rows against Postgres. A real container in globalSetup costs seconds and removes the whole category.
  4. What does a suite passing only with --forceExit tell you?
    That the process has handles still open when the tests finish — a timer, a socket, a pool, a subscription — which means your production code is failing to clean something up. The flag hides it, the suite goes green, and the same leak in a long-lived process is chapter 16's growth curve or a container that will not shut down. Run --detectOpenHandles and fix what it names, rather than forcing the exit.
  5. Why is per-file setup the dominant cost in a slow Node suite?
    Because test files run in isolated worker processes with their own module registries, so anything at module level executes once per file. Ninety files each starting a container, or each building a pool and parsing config, is ninety times a cost you meant to pay once — and it dwarfs the actual test execution. Moving it to globalSetup makes it a single fixed cost, which is usually a five- to twentyfold improvement.
  6. Why isolate with a transaction rather than truncating tables?
    Because a rollback is far cheaper than deleting and re-seeding, and because uncommitted rows are invisible to other connections — so tests cannot observe each other and can safely run in parallel against one database. The exception is anything that must see a real commit: a trigger firing on commit, a NOTIFY, or code that opens its own connection and therefore cannot see your open transaction.
