Files, processes and CLIs

The parts of Node that talk to the operating system. Two of them are also the two places where user input most easily becomes code execution, so this chapter spends its interactives on those rather than on the API surface, which the documentation covers better than prose can.

The filesystem

javascript — three read patterns, and when each is right
import { readFile, writeFile, rename, mkdir } from "node:fs/promises";
import { createReadStream } from "node:fs";      ← streams live in node:fs,
                                                      promises in the subpath
// ① whole file — when the size is bounded BY YOU
const cfg = JSON.parse(await readFile(p, "utf8"));

// ② stream — when the size is chosen by someone else. Chapter 6.
await pipeline(createReadStream(p), parse, out);

// ③ line by line — logs, CSV, anything newline-delimited
for await (const line of createInterface({ input: createReadStream(p) })) …

// ✱ never the *Sync variants in a request path. Chapter 3: they
//   block the loop for the whole syscall, so their cost is the
//   file's size. Fine at startup, fine in a CLI.

// ── an atomic write, which most code gets wrong ──
const tmp = `${path}.${process.pid}.tmp`;
await writeFile(tmp, data);
await rename(tmp, path);        ← rename within a filesystem is atomic,

Things that also matter about child processes
  • Always handle 'error'. A missing binary emits ENOENT on the child object, and chapter 5 applies: unhandled, it ends the process.
  • close is not exit. exit fires when the child ends; close when its stdio has also been fully consumed. If you are reading output, wait for close.
  • Kill the tree, not the child. Killing a shell does not kill its grandchildren. Use detached: true plus process.kill(-child.pid), or avoid the shell entirely and there is no tree.
  • Set a timeout and a maxBuffer. A child that never exits, or produces 900 MB of output, is your problem to bound.
  • Pass an explicit env for anything untrusted. The child inherits your whole environment by default, including every secret.

The process, and a CLI that behaves

javascript — a well-behaved CLI, with no dependencies
import { parseArgs } from "node:util";        ← built in since Node 18

const { values, positionals } = parseArgs({
  options: {
    out:     { type: "string",  short: "o" },
    verbose: { type: "boolean", short: "v", multiple: true },
    help:    { type: "boolean", short: "h" },
  },
  allowPositionals: true,
});

if (values.help) { process.stdout.write(USAGE); process.exit(0); }

// ① data to stdout, everything else to stderr. This is what makes a
//    tool composable: `mytool | jq` must not see your log lines.
process.stderr.write("scanning…\n");
process.stdout.write(JSON.stringify(result) + "\n");

// ② colour and progress only when a human is watching
if (process.stdout.isTTY) renderProgressBar();

// ③ set exitCode, do not call exit() — exit() truncates pending
//    writes to stdout, which is a real and confusing data loss
process.exitCode = failures ? 1 : 0;

// ④ honour the conventions people expect
//    NO_COLOR set → no ANSI codes at all
//    a broken pipe (EPIPE) → exit quietly; `mytool | head` is normal
//    exit codes: 0 success, 1 failure, 2 usage error

// ── signals, and why they need handling ──
for (const s of ["SIGTERM", "SIGINT"]) process.on(s, shutdown);
//   SIGTERM  — the polite stop. Containers send this. Default action
//              is immediate termination, so you MUST handle it.
//   SIGINT   — Ctrl-C.
//   SIGKILL  — cannot be caught. Nothing you write runs.
//   SIGUSR2  — free for you: dump a heap snapshot or a report.
// chapter 19 covers the shutdown sequence and its deadline.
process.env is strings, always
process.env.PORT is "3000", and process.env.DEBUG === false is never true because "false" is a truthy string. Parse and validate configuration once at startup into a frozen object, and fail to start if something required is missing — the same argument as chapter 3 of the Spring Boot unit.
--env-file instead of dotenv
node --env-file=.env app.js, built in since Node 20. One fewer dependency, and it loads before your code rather than partway through it.
process.cwd() is not your file's directory
It is wherever the process was started, so a path relative to cwd breaks the moment someone runs your tool from elsewhere. Use import.meta.dirname for files that ship with your code and cwd only for things the user is pointing at.
The permission model
Node 20 added --permission with --allow-fs-read, --allow-fs-write and --allow-child-process. Worth knowing about for running untrusted code or plugins; it is a real reduction in blast radius, and it is not a substitute for the two demos above.

Self-check

  1. Why does path.join(base, userInput) not protect against traversal?
    Because join normalises the path, which means it resolves the .. segments rather than rejecting them — join("/srv/uploads", "../../etc/passwd") is /etc/passwd, cleanly and with no error. It was never a security function; it is string handling that knows about separators. The containment check has to be explicit and separate.
  2. Why is path.resolve(base, userInput) worse than join here?
    Because resolve processes its arguments right to left and stops at the first absolute one, so an input of /etc/passwd discards the base entirely and returns /etc/passwd. join at least keeps the base as a prefix before normalising. Neither is a guard — resolve is the right tool for producing an absolute path, and the containment check is what you compare it against.
  3. Why does a prefix check still not stop a symlink?
    Because the resolved path is inside the base directory — the link itself lives there. Only following it reveals that the target does not. realpath resolves every symlink in the chain, so checking the real path against the base catches it. This matters wherever users can create entries in the directory, including an upload folder if archive extraction ever preserves links.
  4. What does exec do that execFile does not?
    It runs the command through a shell, so the whole string is parsed for metacharacters — semicolons, pipes, backticks, $(), && — and any of them in interpolated input becomes command execution. execFile and spawn pass an argument array directly to the operating system with no shell involved, so a semicolon is just a character in an argument. It is the same distinction as parameterised SQL against string concatenation.
  5. Why is spawn(cmd, args, { shell: true }) a trap?
    Because it looks like the safe form and behaves like the unsafe one. The argument array is joined into a single string and handed to a shell, so every metacharacter is interpreted again — the array gives no protection at all. It is usually added to make a pipe or a glob work, and the correct fix is to do that in Node: spawn the two processes and pipe the streams, or use fs.glob.
  6. Why set process.exitCode rather than call process.exit()?
    Because exit() terminates immediately and pending writes to stdout can be truncated — a real and very confusing data loss when the output is piped, since writes to a pipe are asynchronous. Setting exitCode lets the event loop drain naturally and the process exits with that code once there is nothing left to do. Reserve exit() for a fatal path where you have already given up on flushing.
