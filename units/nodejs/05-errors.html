Errors and diagnostics

Node has more ways to lose an error than any runtime should, and several of them end with the process gone. The distinction that organises all of it is old and still the most useful one available: is this a failure the program should expect, or a bug in the program?

— words— min read2 interactivesNeeds: chapters 03, 04

Two kinds of error

Operational errors
Things that go wrong in a correct program: a socket reset, a timeout, a 404 from a dependency, a validation failure, a disk that is full. Handle these. Retry, degrade, return a 4xx or a 5xx — chapter 5 of the Backend unit. They are part of the design.
Programmer errors
Bugs: reading a property of undefined, passing a string where a number was required, an unhandled state. Do not handle these. There is no recovery, because you do not know what invariants have already been broken. Log with full context and let the process die, then let the supervisor restart it.
Why the distinction matters practically
A try/catch that swallows both leaves you running on top of a broken invariant, and the visible symptom appears somewhere else entirely — usually as corrupted data rather than an error. Catching narrowly, by error code, is how you keep the two apart.
javascript — errors worth throwing
// ✓ a code, not a message. Callers branch on code; messages change.
class AppError extends Error {
  constructor(code, message, { status = 500, cause, ...meta } = {}) {
    super(message, { cause });      ← error.cause, standard since Node 16.
    this.name = "AppError";           Keeps the original stack attached
    this.code = code;                 instead of stringifying it away
    this.status = status;
    this.meta = meta;               ← structured context for the log,
  }                                     never interpolated into the message
}

throw new AppError("ORDER_NOT_FOUND", "Order does not exist",
                    { status: 404, orderId });

// ✓ catch narrowly, by code — this is an operational error
try {
  await writeFile(path, data);
} catch (err) {
  if (err.code === "ENOSPC") return spillToS3(data);
  throw err;                      ← anything else is not yours to handle
}

// ✗ and the pattern that hides bugs for months:
try { await doEverything(); } catch { return null; }
//   a TypeError from a refactor now silently returns null, and the
//   symptom surfaces three layers away as missing data.

Where does a thrown error actually go?

Eight throw sites, four outcomes
Three of these take the process with them
javascript — the two process-level handlers, done correctly
// These are for OBSERVING a fatal error, not for recovering from one.

process.on("uncaughtException", (err, origin) => {
  logger.fatal({ err, origin }, "uncaught — exiting");
  // flush what you can, then go. The state is unknown.
  server.close();
  setTimeout(() => process.exit(1), 2000).unref();
});

process.on("unhandledRejection", (reason) => {
  logger.fatal({ err: reason }, "unhandled rejection — exiting");
  throw reason;                  ← promote it, so uncaughtException
});                                  handles the shutdown in one place

// ✱ NEVER swallow and continue:
//     process.on("uncaughtException", err => logger.error(err));
//   the process now runs with a half-completed operation, a lock
//   still held, a transaction never rolled back. It will produce
//   wrong answers instead of stopping, which is strictly worse.

// ✱ and the flag that makes this explicit either way:
//     node --unhandled-rejections=strict app.js   (the default since 15)

Carrying context across await

A log line without a request id is nearly useless in a concurrent server. The obvious way to keep one fails in a way that is easy to miss and impossible to debug from the logs it produces.

Three interleaved requests
Watch the request ids in the log
javascript — AsyncLocalStorage, in full
import { AsyncLocalStorage } from "node:async_hooks";
export const ctx = new AsyncLocalStorage();

// one middleware, at the very top of the stack
app.use((req, res, next) => {
  ctx.run({ requestId: req.headers["x-request-id"] ?? randomUUID(),
            userId: null },
          next);                     ← everything called from `next`,
});                                    synchronously or across any number
                                       of awaits, sees this store
// anywhere at all, with no plumbing:
export function log(level, msg, meta) {
  logger[level]({ ...ctx.getStore(), ...meta }, msg);
}
// this is what makes chapter 18's traceId-on-every-line practical
// without threading a context object through forty function
// signatures — and it is how every Node tracing library works.

// caveats worth knowing:
//   · the store does NOT cross a worker_threads or child_process
//     boundary. Pass the id in the message. Chapter 15.
//   · a callback registered ONCE and invoked many times keeps the
//     context from registration — an EventEmitter listener attached
//     at startup has the startup context, not the request's.
//   · it has a small but real cost, historically more than now.
//     Measure rather than assume; it is almost always worth it.

Self-check

  1. What is the difference between an operational and a programmer error, and why act differently?
    An operational error is a failure a correct program should expect — a timeout, a reset connection, a full disk, a validation failure — and it should be handled: retried, degraded, or turned into a status code. A programmer error is a bug, and there is no recovery, because you cannot know which invariants have already been broken. Handling it leaves the process running on top of a corrupted state and producing wrong answers instead of stopping, which is worse than crashing.
  2. Why does throwing inside a fs.readFile callback crash the process?
    Because the callback runs in the poll phase of the event loop, on a fresh stack — there is no try/catch anywhere above it, and the code that called readFile returned long ago. The throw propagates to the top of that stack and becomes an uncaughtException, which by default terminates the process. This is precisely the problem promises solved: a rejection has somewhere to go.
  3. Why did an async route handler crash Express 4 but not Express 5?
    Because Express 4 predates promises in its design and ignores the value a handler returns, so a rejected promise is floating — nothing observes it, and Node reports an unhandled rejection and exits. Express 5 and Fastify await the handler and route a rejection into their error pipeline. On Express 4 the fix is to wrap every async handler in a helper that catches and calls next(err), or to use try/catch in every one.
  4. Why should an uncaughtException handler exit?
    Because by definition something unexpected escaped every boundary, and the process state is unknown — a lock may be held, a transaction not rolled back, a data structure half-updated. Logging and continuing means running on a broken invariant, and the eventual symptom is wrong data rather than an error. The handler's job is to record the failure with full context, flush, and exit so a supervisor can start a clean process.
  5. Why does tracking the current request in a module-level variable fail?
    Because there is one variable and many overlapping requests. Request A sets it and awaits; request B arrives and overwrites it; A resumes and reads B's value. Every log line, audit record and error report from that point on is attributed to the wrong request, and the logs give no hint that anything is wrong — they are internally consistent and simply false. It never reproduces under single-request testing.
  6. What does AsyncLocalStorage not cover?
    Boundaries where the async context does not follow. It does not cross into a worker thread or a child process, so the request id has to travel in the message. And a callback registered once but invoked many times — an EventEmitter listener attached at startup — keeps the context from the moment it was registered, not from whatever triggered it. Both surprise people, and both are visible as log lines with a missing or stale id.
