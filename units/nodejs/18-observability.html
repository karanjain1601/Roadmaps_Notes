The gaps in a trace

A waterfall shows what the request did. On a single-threaded runtime the more useful question is often what it did not do, and for how long.

Liveness and readiness are different questions
Liveness: is this process wedged and unable to recover? It must not check dependencies — a database outage would otherwise cause every instance to be restarted, which helps nobody. Readiness: should traffic come here now? This one may check dependencies, and may go false during a shutdown drain. Chapter 19.
Cardinality is the metrics bill
A label with unbounded values — a user id, an order id, a raw URL with parameters in it — creates a new time series per value. Label with the route template (/orders/:id), the method and the status class, and nothing else. Route templates come from the framework; raw paths come from req.url, which is why the wrong one is easier to reach for.
cluster breaks the metrics endpoint
Each worker serves its own /metrics, so a scrape hits whichever worker the round-robin picks and you see one worker's counters. prom-client's AggregatorRegistry collects across workers. Chapter 15 — one more thing multiplied.
Sample traces, keep all errors
Head sampling at a few per cent for successful requests, and everything that errored or exceeded a latency threshold. Full tracing at volume costs real money and mostly records requests you will never look at.

Self-check

  1. Why is a template-string log line so much less useful than the same information as JSON?
    Because you cannot query it. Order 4821 failed for user 91 after 1832ms requires a regular expression to extract anything, breaks the moment someone rewords the message, and cannot be aggregated — no percentile, no group-by, no filter. The same fields as JSON keys are queryable, aggregatable and stable across rewordings. The message becomes a label rather than the data.
  2. What does AsyncLocalStorage add that structured logging alone does not?
    Correlation. Without it, each line has its own fields and nothing ties the twelve lines from one request together — so you can find that an error happened but not what led to it. A store bound to the async context puts the same requestId on every line from that request, across every await and every layer, with nothing threaded through the function signatures. Chapter 5's demo is the mechanism.
  3. Why must redaction be configured on the logger rather than at each call site?
    Because the leak happens where nobody was thinking about it — someone logs a whole request object, an error with a config attached, or a user record to debug something, and a token or an email address goes to a log store with a long retention and broad access. Call-site discipline fails once; a redaction path list on the logger applies to every line anyone writes, including in code added later by someone who has not read this.
  4. What does an unexplained gap in a Node trace usually mean?
    That the continuation was queued behind other work on the event loop. Spans measure operations; the space between the end of one and the start of the next is time when this request's callback existed and could not run. On a threaded runtime that gap is usually the scheduler and is small; on Node under load it can be most of the request. Which is why loop lag belongs on the same dashboard as latency — it converts "the trace does not add up" into a number.
  5. Why is labelling a metric with the raw URL a problem?
    Because every distinct value creates a time series. /orders/7c3a… with a UUID in it means one series per order, so a few million orders is a few million series — which is a storage and cost failure in the metrics backend, not in your service. Use the route template the framework already knows, plus method and status class. The trap is that req.url is the easier thing to reach for.
  6. Why must a liveness probe not check the database?
    Because it asks whether this process is wedged, and a database outage does not make the process wedged. If the probe reports unhealthy, the orchestrator restarts every instance simultaneously — so a recoverable dependency failure becomes a total outage with a cold fleet and no capacity when the database returns. Dependency checks belong in readiness, which removes an instance from the load balancer instead of killing it.
