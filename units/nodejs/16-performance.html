Performance and memory

The chapter that should be read before chapter 15. Almost every Node performance problem is a slow query, a missing batch, or a synchronous computation — and almost every memory problem is one of four shapes. The skill is measuring in the right order rather than knowing more tricks.

Event loop lag is the first metric, always
It answers the only question that changes what you do next: is the process busy or waiting? Low lag with high latency means you are waiting on something — a query, an API, a lock — and no amount of CPU work will help. High lag means the loop is blocked, and a profile will tell you by what.
V8 optimises hot functions, so warm up before you measure
The first few hundred calls run in the interpreter. A benchmark that runs a function twice measures the interpreter; one that runs it a million times measures optimised code that may have been inlined out of existence. Neither is your production behaviour, which is why a load test against a warm process beats a microbenchmark almost every time.
rss is not the heap
Buffer, ArrayBuffer and native addon memory are external — outside V8's heap and outside --max-old-space-size. So a leak of buffers grows rss and external while heapUsed stays flat, the heap snapshot looks clean, and the container is killed anyway. Watch both numbers.
Compare three snapshots, never read one
A single snapshot tells you what is on the heap, which is a large and unhelpful list. Two snapshots either side of load, or three, let you sort by delta and see what only ever grows — and the Retainers pane then names the exact variable holding it. That is the whole technique.

Self-check

  1. Why is event loop lag the first thing to measure?
    Because it distinguishes busy from waiting, and that determines everything you do next. Low lag with high latency means the process is idle and waiting on something external, so a CPU profile will show nothing and more threads will add nothing — go and look at the query or the downstream call. High lag means the loop is genuinely blocked, and a profile will name the function. Measuring it first prevents most misdirected optimisation.
  2. Why do the last two fixes in the ladder do so little on their own?
    Because they address costs that are tiny next to the ones above them. Outbound keep-alive saves about a hundred milliseconds and a larger pool reduces queueing — both real, and both invisible while a missing index is costing nine hundred milliseconds per request. Worse, pool queueing is caused by slow service time, so fixing the query reduces the wait on its own. Fixing in the wrong order means measuring an improvement you cannot see and concluding it did not work.
  3. What does rss include that heapUsed does not?
    External memory: Buffer, ArrayBuffer and anything a native addon allocates. Those live outside the V8 heap, so they are not counted in heapUsed and not bounded by --max-old-space-size. A buffer leak therefore shows a flat heap graph and a rising rss, the snapshot looks clean, and the container is OOM-killed while every heap metric says the process is fine.
  4. Why must --max-old-space-size be set in a container?
    Because V8 derives its default heap ceiling from the host's memory, not your cgroup limit. On a large host with a 512 MB container limit, V8 believes it may grow to several gigabytes — so rather than running a major collection as it approaches your limit, it grows past it and the kernel kills the process. Set it to roughly 75% of the container limit and V8 will collect instead of dying.
  5. How do you find which variable is holding a leak?
    Three heap snapshots — baseline, after load, after more load — compared in DevTools, sorted by delta. Whatever grows monotonically is the leak, and selecting an instance shows the Retainers path: the chain of references from a root to that object, which names the module, the closure or the array holding it. Reading a single snapshot instead gives you a large list of everything alive and no signal.
  6. Why is a microbenchmark of a Node function often misleading?
    Because V8's behaviour depends on how often the code has run. The first few hundred calls are interpreted; after that a function may be optimised, inlined, or — if the benchmark discards the result — eliminated entirely. So a tight loop measures either cold interpretation or an optimisation that will not apply in a handler where the function is called with varying shapes. A load test against a warmed process is closer to the truth.
