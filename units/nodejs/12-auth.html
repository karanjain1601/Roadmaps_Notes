Authentication and security

Chapter 14 of the Backend unit covered the concepts. Two things are specifically Node's problem: password hashing is deliberately expensive CPU work and you have one thread for it, and the cookie flags that carry a session are the kind of detail that is either exactly right or a vulnerability.

Password hashing meets the single thread

A password hash is supposed to cost tens of milliseconds of CPU. On a runtime with one thread for your code, that is not a detail — it is a capacity decision.

Verifying a webhook signature in Node

Two things go wrong specifically here. First, you must hash the raw body bytes, and your framework has usually already parsed and re-serialised them — key order and whitespace change, and the signature will never match. Capture the raw buffer in a pre-parsing hook (chapter 10) for that route only. Second, compare with crypto.timingSafeEqual rather than ===, and check the timestamp inside the signed payload so an old delivery cannot be replayed. Chapter 18 of the Backend unit.

Self-check

  1. Why is password hashing a capacity decision in Node specifically?
    Because a hash is deliberately expensive CPU work — tens of milliseconds by design — and Node has one thread for your code. A synchronous hash blocks the entire process for its full cost, so twenty logins a second at sixty milliseconds each is more than a whole thread and every other request queues behind them. The mitigations are real but bounded: the native async implementations use libuv's thread pool, which has four threads by default and is shared with your file and DNS work.
  2. What is wrong with bcrypt.hashSync in a login handler?
    It blocks the event loop for the entire hash. Nothing else in the process runs — not another request, not a timer, not the health check — so the login endpoint's cost becomes every endpoint's latency. It also makes login a denial-of-service primitive against your own CPU, since an attacker only has to send requests. Use the async form, which moves the work to the thread pool, and rate-limit the endpoint regardless.
  3. Why does raising UV_THREADPOOL_SIZE help hashing, and what does it cost?
    Because the native async hash functions run on that pool, so its size is your hashing concurrency — four threads at sixty milliseconds each is about 66 hashes a second and no more. Raising it increases that ceiling. The cost is that the pool is shared: filesystem operations, DNS lookups and zlib use the same threads, so hashing at capacity starves them, and a larger pool means more threads contending for the same cores. A dedicated worker pool separates the two concerns properly.
  4. Why verify the password even when the user does not exist?
    Because otherwise the response time tells an attacker which addresses are registered — a hit costs sixty milliseconds and a miss costs one. Verify against a fixed dummy hash so both paths cost the same, and return one message for both cases. It is a small thing that turns a user-enumeration oracle into no information at all, and it is easy to lose in a refactor that adds an early return.
  5. What does the __Host- prefix do?
    It makes the browser refuse the cookie unless it is Secure, has Path=/ and has no Domain attribute — which means it is locked to the exact host that set it. A compromised or taken-over subdomain therefore cannot set a cookie your main site will accept, which is otherwise a real and often-missed path to session fixation. It costs a naming convention and is enforced by the browser rather than by you.
  6. Why is per-instance rate limiting misleading?
    Because each instance counts independently, so a limit of 100 requests a minute across ten instances is really 1,000 — and with cluster, each worker within an instance counts separately too. The limit you configured is not the limit you have. Use a shared store such as Redis so the counter is global, and remember that any per-IP limit is only as trustworthy as the X-Forwarded-For handling above it.
