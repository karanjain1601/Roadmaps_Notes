Modules: CommonJS, ESM and interop

Node shipped a module system in 2009, the language standardised a different one in 2015, and both are still here. The mechanics of each are simple; the seam between them is where an afternoon disappears. This chapter is about knowing which side of the seam you are on.

Two systems

javascript — the same module, twice
// ── CommonJS. Every file is wrapped in a function before it runs: ──
//   (function (exports, require, module, __filename, __dirname) { … })

// ── ESM. Statically analysed before any code runs: ──

                                                first line of this file
export { list };

const cfg = await load();     ← top-level await. Only in ESM, and it
                                  delays every importer of this module

The seam

Which direction works, and what you get
Click a cell, then change the Node version
The three errors you will actually see
  • ERR_REQUIRE_ESM — a CommonJS file tried to require an ESM-only package. On Node 22 and later this often just works; before that, the fixes are dynamic import(), converting the file to ESM, or pinning the last CJS version of the dependency.
  • ERR_MODULE_NOT_FOUND for a file you can see — you omitted the extension in ESM. ./orders must be ./orders.js, and in TypeScript that means writing .js in the import even though the file on disk is .ts.
  • ERR_PACKAGE_PATH_NOT_EXPORTED — you imported a deep path the package's exports map does not list. That is the package author enforcing its public surface, and it is usually correct even when it is inconvenient.
Circular imports differ between the systems
CommonJS hands the requiring module a partially populated exports object — so a function attached later is undefined at that moment, and the failure is a runtime TypeError in unrelated-looking code. ESM hoists declarations, so mutually recursive functions work; a const read before its module finished evaluating throws a clear ReferenceError. Either way, a cycle is a design signal — chapter 2 of the Spring Boot unit makes the same argument.
The node: prefix, always
import "node:fs" rather than "fs". It cannot be shadowed by a package of the same name, it is unambiguous to readers and tooling, and it makes a typo a resolution error rather than a silent load of something from node_modules.
The module cache
Both systems cache by resolved path, so a module's top-level code runs once per process — which is what makes module-level state behave like a singleton. Two consequences: the same file reached by two different paths (a symlink, a dual package) is two modules; and there is no supported way to clear the ESM cache, so hot reloading needs a loader hook or a fresh process.
TypeScript, briefly
Set "module": "nodenext" and write the runtime specifier — ./orders.js, not ./orders. Everything above then applies unchanged, because the compiler is emitting the module system Node will actually see. Fighting this with bundler-style resolution works until something loads at runtime.

Self-check

  1. Where do require, module and __dirname come from in CommonJS?
    Node wraps every CommonJS file in a function whose parameters are exports, require, module, __filename and __dirname, so they look like globals and are actually locals. That is also why they do not exist in ESM — there is no wrapper. Use import.meta.dirname on Node 21 and later, or derive it from import.meta.url.
  2. Why can CommonJS not be tree-shaken but ESM can?
    Because module.exports is an ordinary mutable object assigned at runtime — a file can add exports in a loop, or conditionally, so no tool can know the export set without executing it. ESM's imports and exports are declarations analysed before any code runs, so a bundler can prove a binding is never used and drop it. That static analysability is also what makes named imports from a CJS module unreliable.
  3. Why does import "./orders" fail when require("./orders") works?
    Because CommonJS resolution probes extensions — it tries the literal path, then .js, .json and .node, then treats it as a directory. ESM does none of that: the specifier is resolved as a URL and must name the file exactly. It is deliberate, since probing costs several filesystem calls per import and makes resolution ambiguous, and it is the most common error when migrating.
  4. What is the dual-package hazard?
    A package shipping both CJS and ESM builds can have both loaded in one process — one dependency requires it, another imports it — giving two copies with separate module-level state and separate class identities. A singleton is no longer single, a cache is duplicated, and instanceof fails across the boundary in ways that are very hard to diagnose. Avoid module-level state in dual packages, or ship one format.
  5. Why is the node: prefix worth using consistently?
    Because a bare "fs" could resolve to a package in node_modules named fs, while node:fs can only ever be the builtin. It makes the intent explicit to readers and tools, and it turns a typo into a resolution error rather than a silent load of something unexpected. It is also the only form some newer builtins accept.
  6. How do circular imports behave differently in the two systems?
    CommonJS returns whatever the partially-executed module has attached to exports so far, so a function added after the cycle is undefined — and the error appears later as a confusing TypeError. ESM hoists declarations, so mutually recursive functions work fine, and reading a const before its module finished evaluating throws a clear ReferenceError. ESM fails better; neither makes the cycle a good idea.
