Controlling the results

A distributed search cannot know which ten documents rank highest without asking every shard for its own top ten. That one fact explains why deep pagination is expensive, why there is a hard limit on it, and why the fix is a cursor rather than a page number.

Why deep paging is expensive

query then fetch, in two phases
You ask for results 10,000 to 10,010 across an index with 5 shards.

QUERY PHASE
  The coordinating node sends the query to all 5 shards.
  Each shard must return its own top 10,010 — because any of them could
  hold all of the globally top-ranked documents.
  Each returns 10,010 (doc id, score) pairs.

  The coordinating node now holds 50,050 entries. It sorts them, discards
  50,040, and keeps 10.

FETCH PHASE
  It asks the relevant shards for the _source of those 10 documents.
  Those come back and are returned to you.

THE COST OF PAGE N IS PROPORTIONAL TO N × SHARDS, and all of it lands in
memory on ONE node — the coordinating node. Ten users deep-paging
simultaneously is a coordinated attack on a single JVM heap.

That is why:
  index.max_result_window: 10000          # the default hard limit
  # from + size > 10000 -> 400 Bad Request

RAISING IT IS THE WRONG FIX. The limit exists to stop a query taking down
a node, and a cluster where it has been raised to 1,000,000 is a cluster
with an outage scheduled for whenever someone builds a link to page 50,000.

WHAT DOES NOT HAVE THIS PROBLEM: aggregations, which are computed per shard
and combined, and search_after, which carries a position rather than an
offset.

search_after, the one to use
# 1. Open a point in time — a frozen view of the index, so the results are
#    consistent even as documents are written underneath you
POST /products/_pit?keep_alive=2m
# -> { "id": "46ToAwMDaWR5..." }

# 2. First page. The sort MUST be a total order — include a tiebreaker
POST /_search
{ "size": 20,
  "pit": { "id": "46ToAwMDaWR5...", "keep_alive": "2m" },
  "query": { "match": { "name": "wireless" } },
  "sort": [ { "price": "asc" }, { "_shard_doc": "asc" } ] }

#    _shard_doc is a free implicit tiebreaker available with a PIT. Without
#    one, documents with equal sort values can appear on two pages or on
#    none, because the order between them is undefined.

# 3. Every subsequent page: pass the LAST hit's sort values back
POST /_search
{ "size": 20,
  "pit": { "id": "46ToAwMDaWR5...", "keep_alive": "2m" },
  "query": { "match": { "name": "wireless" } },
  "sort": [ { "price": "asc" }, { "_shard_doc": "asc" } ],
  "search_after": [ 349.99, 4294967298 ] }

DELETE /_pit  { "id": "46ToAwMDaWR5..." }

# EACH SHARD NOW SKIPS DIRECTLY to its position in the sorted term data and
# returns only `size` results. The cost is CONSTANT per page, whether it is
# page 2 or page 20,000.
#
# WHAT YOU GIVE UP: you cannot jump to an arbitrary page. You can only go
# forward one page at a time, because the cursor IS the previous page's last
# row. That is why infinite scroll is the natural interface for it and
# numbered pagination is not.
#
# WITHOUT A PIT it still works, and results can shift as the index changes —
# a document indexed between two page requests can push things across the
# boundary. Use a PIT whenever consistency matters.
Nobody visits page 500

Deep pagination is almost always a symptom rather than a requirement. When a user is on page 40 of search results, the search failed — they should have refined it, and the interface should have helped. The three legitimate needs are export, migration and background processing, and all three want search_after or a scroll rather than page numbers, because they read everything in order and never jump. If a product requirement genuinely demands numbered pages into the tens of thousands, the honest response is that Elasticsearch is being asked to be a paginated table and something with a stable ordered index — a relational database with a keyset cursor — is a better fit for that specific screen.

Sorting

and what it costs you
{ "sort": [
    { "price": { "order": "asc" } },
    { "released": { "order": "desc" } },
    "_score",                                   # relevance as a tiebreaker
    { "_doc": "asc" }                           # cheapest possible tiebreak
]}

# SORTING TURNS OFF SCORING unless _score is in the sort list. That is a
# small performance win and a real behavioural change — track_scores: true
# brings the scores back if you need to display them.

# ARRAYS need a mode, since a document has several values:
{ "sort": [ { "prices": { "order": "asc", "mode": "min" } } ] }
#   min | max | sum | avg | median

# MISSING VALUES:
{ "sort": [ { "price": { "order": "asc", "missing": "_last" } } ] }
#   _last | _first | a literal value

# NESTED FIELDS need the path, or you sort on an unrelated element:
{ "sort": [ { "members.joined": {
    "order": "asc",
    "nested": { "path": "members",
                "filter": { "term": { "members.role": "admin" } } } } } ]}

# YOU CANNOT SORT ON A text FIELD. Use the .keyword sub-field. The error
# suggests enabling fielddata; do not (chapter 3).

# GEO DISTANCE:
{ "sort": [ { "_geo_distance": {
    "location": { "lat": 51.5, "lon": -0.12 },
    "order": "asc", "unit": "km" } } ]}

# INDEX SORTING — pre-sort the segments on disk at index time:
PUT /events { "settings": { "index": {
    "sort.field": [ "@timestamp" ],
    "sort.order": [ "desc" ] }}}
# Queries sorted the same way can stop early instead of scanning every
# matching document, which on a large time-series index is a very large win.
# The cost is slower indexing. For append-mostly log data it is usually
# worth it, and it must be set at index creation.

What comes back

source filtering, fields, and highlighting
# RETURN ONLY WHAT YOU RENDER. _source is fetched and decompressed per hit,
# so returning a 40 KB document to display a title is real, avoidable cost.
{ "_source": [ "name", "price", "thumbnail" ] }
{ "_source": { "includes": [ "user.*" ], "excludes": [ "user.internal_*" ] } }
{ "_source": false }                       # ids and scores only

# THE fields PARAMETER — formatted values, and it understands runtime fields
# and multi-fields in a way _source does not:
{ "fields": [ "name", "price", { "field": "released", "format": "yyyy-MM-dd" } ],
  "_source": false }
# _source gives you what was SENT. fields gives you what was INDEXED, after
# coercion and formatting. For dates and numbers that distinction matters.

# HIGHLIGHTING — the matched fragments, marked up
{ "highlight": {
    "pre_tags":  [ "" ],
    "post_tags": [ "" ],
    "fields": {
      "name": {},
      "description": { "fragment_size": 150, "number_of_fragments": 3 }
    }
}}

#   THREE HIGHLIGHTERS, and the default is usually right:
#     unified   default. Uses the Lucene highlighter, handles most cases
#     plain     re-analyses the field at query time. Accurate, slow on big
#               fields, and the one to avoid on large documents
#     fvh       fast vector highlighter. Needs term_vector: with_positions_offsets
#               in the mapping, which costs index size. Worth it only for
#               genuinely large fields you highlight constantly
#
#   Highlighting reads _source and re-analyses by default, so it is one of
#   the more expensive things you can add to a search. Measure it.

# COLLAPSE — one result per group, without an aggregation
{ "collapse": {
    "field": "brand",
    "inner_hits": { "name": "top_3", "size": 3, "sort": [ { "price": "asc" } ] }
}}
# "show the best match per brand, with three examples each". Far cheaper
# than a terms aggregation with top_hits, and it paginates properly —
# which top_hits does not.
Scroll is legacy, and still the right answer occasionally

scroll holds a search context open on every shard for the duration, pinning the segments so the view stays consistent. That is expensive — open scrolls prevent segment merges from freeing space, and a forgotten scroll with a long keep_alive quietly holds disk and memory until it expires. Elastic's own documentation now recommends search_after with a point in time for deep pagination, and PIT is genuinely lighter. Scroll remains reasonable for one case: a single-pass export of an entire index where you want slice to parallelise across workers, and you control the lifetime. Anything user-facing should be search_after.

Three settings that make searches predictable

"timeout": "2s" on the request bounds how long each shard may spend, returning partial results rather than hanging — and note it is per shard, not per request. "terminate_after": 1000 stops each shard after collecting that many matches, which is a blunt instrument that turns an unbounded scan into a bounded one when you only need "are there some of these". And "allow_partial_search_results": false makes a search fail when a shard is unavailable instead of quietly returning fewer documents — the default is true, which means a yellow cluster silently returns incomplete results, and for anything where correctness matters more than availability that default is wrong.

The short version

  1. Every shard returns from + size results, and the coordinating node sorts and discards. Deep paging costs memory on one node.
  2. max_result_window is 10,000 for a reason. Raising it schedules an outage.
  3. search_after with a PIT is the answer — constant cost per page, forward only.
  4. Always include a tiebreaker in the sort, or documents appear twice or not at all. _shard_doc is free with a PIT.
  5. Sorting disables scoring unless _score is in the sort list.
  6. Index sorting lets time-series queries stop early, at the cost of slower indexing. Set at creation.
  7. Return only the fields you render. _source is fetched and decompressed per hit.
  8. collapse beats a terms aggregation with top_hits for one-result-per-group, and it paginates.
