Chapter 02 · The model

Cluster, nodes and shards

An index is not a thing on disk. It is a name for a set of shards, each of which is a complete Lucene index, distributed across machines and replicated. Almost every capacity and availability question in this unit is really a question about that number.

shards replicas node roles quorum

Four layers

Cluster
One or more nodes sharing a cluster.name, holding one shared view of where everything is. One node is a valid cluster.
Node
One running Elasticsearch process. Usually one per machine, because it wants the whole machine's memory and page cache.
Index
A named, logical collection of documents — articles, logs-2026.03. Roughly a table, and unlike a table it is only a name and a mapping. The data is in the shards.
Shard
A complete, independent Lucene index. This is the unit that actually holds documents, gets allocated to a node, gets copied, and gets searched.

Below shards there is one more layer that matters operationally: a shard is made of segments, which are immutable files. Writing a document does not modify a segment; it creates a new one, and background merging combines them. That immutability is inherited from Lucene and it explains updates, deletes, refresh behaviour and a good deal of the disk I/O (chapters 6 and 14).

Where a document goes

the routing formula
    shard = hash(_routing) % number_of_primary_shards

_routing defaults to the document's _id.

Three consequences follow immediately, and they are the whole reason shard
count is a serious decision:

1. THE SHARD COUNT IS IN THE FORMULA. Change it and every document hashes
   somewhere new, so the existing data is in the wrong place. This is why
   number_of_shards cannot be changed on a live index — you reindex into a
   new one instead (chapter 6).

2. DISTRIBUTION IS AUTOMATIC AND YOU CANNOT STEER IT. A hash of an id
   spreads documents evenly, which is what you want and means you cannot
   co-locate related documents by default.

3. UNLESS YOU OVERRIDE _routing:

     PUT /orders/_doc/8842?routing=customer-41
     GET /orders/_search?routing=customer-41

   Now every document for that customer is on one shard, and a search
   restricted to that routing value touches ONE shard instead of all of
   them. On a large cluster that is a very large difference.

   The cost is skew: a customer with a hundred times more orders than the
   others makes one shard a hundred times larger. Same trade as a hash tag
   in Redis Cluster, and the same failure mode.

READS go to any copy — primary or replica, chosen adaptively. WRITES always
go to the primary, which then replicates to its replicas synchronously
before acknowledging. That last point is a real difference from Redis and
from MongoDB's default: an Elasticsearch write is not acknowledged until
the in-sync replicas have it.

Primaries are permanent, replicas are free to change

number_of_shards is fixed at index creation and cannot be altered afterwards, because it is in the routing formula. number_of_replicas can be changed at any moment with one call, and the cluster will create or drop copies to match. That asymmetry is worth committing to memory: the decision you must get right at creation time is the primary count; the replica count is a dial you can turn later. It is also why the common advice for a bulk load is to set replicas to 0, index everything, then set them back — you avoid replicating every document as it arrives, and the copies are built from the finished shards instead.

How many shards

the guidance, and why it is what it is
TARGET 10-50 GB PER SHARD. Up to 50 GB for search workloads, and time-series
data is routinely run larger. Below about 10 GB you are usually paying more
in overhead than you gain in parallelism.

WHY THERE IS AN UPPER BOUND: a shard is the unit of recovery and relocation.
A 200 GB shard has to be copied in full when a node fails or the cluster
rebalances, which is slow and saturates the network. It is also the unit of
parallelism — one shard is searched by one thread, so an oversized shard
makes a single query slow with no way to speed it up.

WHY THERE IS A LOWER BOUND: every shard costs memory for its own Lucene
index structures, file handles, and a slot in the cluster state. A query
against an index fans out to every shard and the coordinating node merges
the results, so 200 tiny shards means 200 requests and 200 result sets to
merge for every search.

THE HEAP RULE: aim for UNDER 20 SHARDS PER GB OF HEAP on each node. A node
with 30 GB of heap should hold at most ~600 shards, and comfortably fewer.
Clusters that ignore this develop slow cluster-state updates, long recovery
times and mysterious master instability.

  ------------------------------------------------------------------
  A WORKED EXAMPLE
    200 GB of data, expected to reach 400 GB
    400 GB / 40 GB per shard = 10 primary shards
    with 1 replica       = 20 shard copies, 800 GB of disk
    across 5 data nodes  = 4 copies per node. Comfortable.
  ------------------------------------------------------------------

FOR TIME-SERIES DATA, do not agonise. Use a data stream with rollover
(chapter 15) — each backing index is small, you set a size threshold, and
the shard count per index can be 1. The problem solves itself.

FOR SEARCH DATA, size for the data you will have in a year, not today. You
cannot change it later without a reindex, and a reindex of a live search
index is a project.
Oversharding is the most common self-inflicted Elasticsearch problem

The instinct is that more shards means more parallelism means faster, so people create 20 shards for 5 GB of data. What actually happens: every search fans out to 20 shards and merges 20 result sets, cluster state grows, recovery gets slower, heap fills with per-shard overhead, and the master node starts struggling to propagate updates. The symptoms appear months later and look like general cluster sickness rather than a configuration mistake, which is why it is so persistent. Elasticsearch's default was reduced from 5 primaries to 1 in version 7 precisely because the old default was oversharding almost everybody.

Split brain, and why it is solved

the historical problem and the current answer
THE PROBLEM. A network partition splits a cluster. Each side notices the
master is gone and elects its own. Both sides accept writes. When the
partition heals, two divergent cluster states must be reconciled — and one
side's writes are discarded.

BEFORE VERSION 7 you prevented this by hand:

    discovery.zen.minimum_master_nodes: 2      # (N/2)+1, set MANUALLY

Setting it wrong — or forgetting to update it when adding nodes — caused
real, well-documented data loss. It was the single most common serious
Elasticsearch misconfiguration.

SINCE VERSION 7 the setting is gone. Elasticsearch uses a proper consensus
algorithm with an explicit VOTING CONFIGURATION that the cluster maintains
itself. A master can only act if it holds a majority of votes, and the
minority side of a partition cannot elect one — it goes read-only and waits.

    GET /_cluster/state/metadata?filter_path=metadata.cluster_coordination

WHAT YOU STILL HAVE TO GET RIGHT:

  * an ODD NUMBER of master-eligible nodes. Three is the standard answer.
    Two is worse than one, because two cannot form a majority when one
    fails — exactly the arithmetic from Redis Cluster and MongoDB
  * master-eligible nodes on SEPARATE failure domains — different hosts,
    ideally different racks or zones
  * on very large clusters, DEDICATED masters, so a heavy query on a data
    node cannot destabilise cluster coordination
  * do not run exactly two master-eligible nodes and then wonder why a
    single failure takes the cluster read-only. It is doing what it should

Note this protects CLUSTER STATE, not documents. A partition can still lose
in-flight writes on the minority side. Elasticsearch's consistency model
(chapter 6) is not a transactional database's, and no amount of correct
quorum configuration changes that.
Index templates, so the settings apply to indices that do not exist yet

Shard count and mappings are set at index creation, and for time-series data the indices are created automatically as data arrives — which means there is no moment at which you could set them by hand. An index template attaches settings and mappings to a name pattern in advance, so logs-2026.03.15 is created with your configuration the first time a document for that day is written. This is not an advanced feature to defer: any index created implicitly by an incoming document gets whatever the defaults are, dynamic mapping and all, and by the time you notice, you have a month of indices with the wrong shard count and inferred field types (chapters 4 and 15).

The short version

  1. An index is a name for a set of shards. Each shard is a complete, independent Lucene index.
  2. shard = hash(_routing) % primaries, which is why the primary count cannot change on a live index.
  3. Custom routing co-locates related documents and turns an all-shard search into a one-shard search, at the cost of skew.
  4. Yellow means you lost redundancy, red means you lost access. A single node with replicas is permanently yellow and that is correct.
  5. Target 10–50 GB per shard, and under 20 shards per GB of heap per node.
  6. Oversharding is the common self-inflicted problem, and its symptoms show up months later as general cluster sickness.
  7. Replicas can be changed any time. Set them to 0 for a bulk load and back afterwards.
  8. Odd number of master-eligible nodes, three by default. Version 7 removed the setting that used to cause split-brain data loss.
