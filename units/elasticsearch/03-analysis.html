Chapter 03 · The model

Analysis and the inverted index

Elasticsearch never searches your text. It searches the terms your text was reduced to at index time, by a process you can configure and mostly did not. Nearly every baffling search result in this unit traces back to this chapter.

analyzers tokenizers text vs keyword _analyze

The chain

When a document with an analysed field is indexed, the value passes through three stages before anything is stored.

Character filters
Operate on the raw string before tokenisation. Strip HTML, replace characters, apply regular expressions. Zero or more, in order.
Tokenizer
Splits the string into tokens. Exactly one. The standard tokenizer splits on word boundaries following the Unicode segmentation rules, which is why it handles most languages sensibly.
Token filters
Transform, add or remove tokens. Lowercase, stem, remove stopwords, expand synonyms, fold accents. Zero or more, in order.

What comes out is the list of terms that go into the inverted index. Those terms are what exists as far as searching is concerned; the original text is kept separately in _source for display, and is never consulted during matching.

The same analyzer runs on your query

This is the mechanism that makes search work, and the one that makes term queries fail. A match query analyses your search string with the field's analyzer before looking anything up, so "Foxes" becomes fox and finds the document whose "foxes" also became fox. A term query does not analyse — it looks up your string in the term dictionary exactly as given. On an analysed field that almost always means looking up something that was never stored. The rule that follows: match for text fields, term for keyword fields, and if a query mysteriously returns nothing, check that pairing first (chapter 8).

PUT /products
{ "mappings": { "properties": {
    "name": {
      "type": "text",                       # searchable prose
      "fields": {
        "keyword": {                        # AND exact, for sorting and facets
          "type": "keyword",
          "ignore_above": 256
        }
      }
    }
}}}

# You now have two fields backed by one source value:
GET /products/_search
{ "query": { "match": { "name": "wireless headphones" } } }        # text
{ "query": { "term":  { "name.keyword": "Sony WH-1000XM5" } } }    # exact
{ "aggs":  { "models": { "terms": { "field": "name.keyword" } } } }# facet
{ "sort":  [ { "name.keyword": "asc" } ] }                         # sort

# This is a MULTI-FIELD, and dynamic mapping creates exactly this shape for
# every string it sees — which is why so much works by accident and why
# mapping sizes balloon (chapter 4).
#
# ignore_above: 256 means values longer than 256 characters are not indexed
# in the keyword sub-field at all. That is a sensible default: a 4 KB
# product description has no meaningful exact-match or facet value, and
# indexing it as a keyword wastes space and can blow up a terms aggregation.
# The value is still in _source and still returned.

# THE DECISION, in one line: will a human ever type PART of this value and
# expect to find it? If yes, text. If it is a code, a status or an id that is
# only ever matched whole, keyword — and keyword-only is meaningfully cheaper.

The built-in analyzers

what each one does to "The Quick-Brown Foxes jumped!"
standard    [the, quick, brown, foxes, jumped]
            Unicode word boundaries, lowercased. No stopword removal by
            default, no stemming. THE DEFAULT and a good one.

english     [quick, brown, fox, jump]
            Adds English stopwords and stemming. "foxes" and "fox" both
            become "fox", so either query finds either document.

simple      [the, quick, brown, foxes, jumped]
            Splits on anything that is not a letter. Drops numbers entirely,
            which surprises people.

whitespace  [The, Quick-Brown, Foxes, jumped!]
            Splits on whitespace only. No lowercasing, punctuation retained.

keyword     [The Quick-Brown Foxes jumped!]
            Does nothing. One token, the whole string. This is what the
            keyword FIELD TYPE uses.

pattern     splits on a regular expression you provide
stop        like simple, plus stopword removal
fingerprint sorts, deduplicates and concatenates tokens — for near-duplicate
            detection

LANGUAGE ANALYZERS exist for around thirty languages: french, german,
spanish, cjk, arabic and so on. Each brings stemming and stopwords for that
language. If your content is not English, using the right one is one of the
highest-value changes available — English stemming applied to German is
worse than no stemming at all.

TRY THEM. This API needs no index and no data:

  POST /_analyze
  { "analyzer": "english", "text": "The Quick-Brown Foxes jumped!" }

  POST /_analyze
  { "tokenizer": "standard",
    "filter": ["lowercase", "porter_stem"],
    "text": "The Quick-Brown Foxes jumped!" }

  POST /products/_analyze
  { "field": "name", "text": "Sony Headphones" }   # what THIS field does
_analyze is the debugging tool for the whole unit

When a search does not return what you expect, the question is almost never "is my query wrong" — it is "what terms actually exist". Run the field's analyzer over the document value, run it over the query string, and compare the two lists. If they do not overlap, there is your answer, and you now know whether the fix is in the mapping or the query. This one API resolves more Elasticsearch confusion than any other, and the field-specific form (POST /index/_analyze with "field") is the one to reach for, because it uses the analyzer actually configured rather than the one you think is configured.

Custom analyzers

assembled from parts, defined at index creation
PUT /articles
{
  "settings": { "analysis": {

    "char_filter": {
      "strip_html": { "type": "html_strip" }
    },

    "filter": {
      "en_stop":     { "type": "stop", "stopwords": "_english_" },
      "en_stem":     { "type": "stemmer", "language": "english" },
      "my_synonyms": { "type": "synonym_graph",
                       "synonyms": [ "laptop, notebook, portable computer",
                                     "tv, television" ] },
      "edge_ngram":  { "type": "edge_ngram", "min_gram": 2, "max_gram": 15 }
    },

    "analyzer": {
      "article_body": {
        "type": "custom",
        "char_filter": [ "strip_html" ],
        "tokenizer":   "standard",
        "filter":      [ "lowercase", "asciifolding", "en_stop", "en_stem" ]
      },
      "autocomplete": {
        "type": "custom",
        "tokenizer": "standard",
        "filter": [ "lowercase", "edge_ngram" ]
      }
    }
  }},

  "mappings": { "properties": {
    "body":  { "type": "text", "analyzer": "article_body" },
    "title": { "type": "text",
               "analyzer": "autocomplete",          # index time: n-grams
               "search_analyzer": "standard" }      # search time: whole words
  }}
}

# THE SEPARATE search_analyzer IS THE POINT OF THAT LAST ONE. Index "keyboard"
# as [ke, key, keyb, keybo, ...] so a prefix matches; but analyse the QUERY
# with standard, so searching "key" looks up the single term "key" rather
# than expanding into n-grams of itself. Using the n-gram analyzer on both
# sides produces a flood of irrelevant matches — this is the classic
# autocomplete mistake.
#
# ORDER MATTERS IN THE FILTER LIST. Stemming before lowercasing gives
# different results from lowercasing before stemming, because most stemmers
# expect lowercase input. Put lowercase first.
#
# ANALYSIS SETTINGS CANNOT BE CHANGED ON AN OPEN INDEX. Close it, update,
# reopen — and existing documents keep their OLD terms until reindexed,
# which means the index is now inconsistent with itself. In practice,
# changing analysis means reindexing (chapter 6).

The trade-offs worth understanding

Stemming and stopwords help

  • Stemming collapses inflections so "running", "runs" and "ran" all find each other. Recall goes up substantially on natural prose.
  • Stopword removal drops "the", "and", "of" — a smaller index and less noise.
  • ASCII folding makes "cafe" find "café", which users expect.
  • Synonyms bridge vocabulary gaps between how you describe things and how people search for them.

And each has a cost

  • Stemming loses precision. "university" and "universe" both stem to "univers" under Porter, so they match each other.
  • Stopwords break phrases. Remove "to" and "be" and the phrase "to be or not to be" cannot be searched at all.
  • Folding merges distinct words. In some languages the accent is the difference between two meanings.
  • Synonyms are one-way trouble. Defined at index time they need a reindex to change; at search time they slow queries.
Normalizers, for keyword fields that need one small transformation

A common need: a status or tag field that must be exact-matchable and aggregatable — so keyword — but where "ACTIVE" and "active" should be the same thing. Making it text to get lowercasing breaks aggregations and sorting; leaving it keyword means the case must match exactly. The answer is a normalizer: a restricted analyzer for keyword fields that may only use character filters and token filters that produce a single token — lowercase, asciifolding, trim. It gives you a keyword field that is still one term, still sortable and aggregatable, but case-insensitive. This is not obscure, and people spend a surprising amount of effort working around not knowing about it.

What is actually stored

four structures per field, and they cost different things
INVERTED INDEX     term -> [doc ids, positions, frequencies]
                   Built for any field with "index": true. This is what
                   makes matching fast.

DOC VALUES         doc id -> value, a columnar layout on disk
                   Built for any field with "doc_values": true, which is the
                   default for everything except analysed text. This is what
                   makes SORTING, AGGREGATING and scripting fast — the
                   inverted index is the wrong shape for "give me the value
                   of this field for these 10,000 documents".

_source            the original JSON, stored verbatim
                   Returned in search hits, and required for reindexing,
                   updates and highlighting. Disabling it saves space and
                   costs you the ability to reindex, which is a bad trade
                   for almost everyone.

STORED FIELDS      individual fields kept separately from _source
                   Rarely needed now that _source exists.

WHY text FIELDS CANNOT BE SORTED OR AGGREGATED: they have no doc values,
because doc values on an analysed field would mean storing every term for
every document in columnar form — enormous, and semantically useless, since
"the value" of an analysed field is a list of stems.

  "Fielddata is disabled on [name] in [products]. Text fields are not
   optimised for operations that require per-document field data..."

That error means: you tried to sort or aggregate on a text field. The
suggested fix in the message is to enable fielddata, which builds the
structure IN HEAP at query time and is a well-known way to run a cluster out
of memory. DO NOT DO IT. Add a .keyword sub-field and use that instead.

  GET /products/_disk_usage?run_expensive_tasks=true

  ^ breaks disk usage down per field and per structure. When an index is
    twice the size you expected, this tells you which field and which of the
    four structures is responsible.

The short version

  1. Analysis happens at index time: character filters, then one tokenizer, then token filters. The output terms are what exists.
  2. The same analyzer runs on your query in a match, which is why it works — and a term query skips it, which is why it does not.
  3. text for prose, keyword for identifiers, and a multi-field for both. Dynamic mapping does this automatically.
  4. _analyze resolves more confusion than any other API. Compare the document's terms with the query's terms.
  5. Use the right language analyzer. English stemming on German is worse than none.
  6. A separate search_analyzer is what makes edge n-gram autocomplete work instead of flooding you with matches.
  7. Normalizers give keyword fields lowercasing without losing sortability or aggregatability.
  8. Never enable fielddata. The error message suggests it; add a .keyword sub-field instead.
