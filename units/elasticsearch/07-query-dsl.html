The Query DSL

Two distinctions carry the whole query language. Leaf queries match; compound queries combine. And every clause runs in either query context, where it is scored, or filter context, where it is merely true or false — which is both a correctness decision and the biggest performance lever you have.

bool filter must should

The bool query

four clause types, and they do not mean what their names suggest
GET /products/_search
{ "query": {
    "bool": {

      "must": [                         # must match, AND CONTRIBUTES TO SCORE
        { "match": { "name": "wireless headphones" } }
      ],

      "filter": [                       # must match, SCORE IGNORED, CACHEABLE
        { "term":  { "brand": "sony" } },
        { "range": { "price": { "lte": 400 } } },
        { "term":  { "in_stock": true } }
      ],

      "should": [                       # optional. Matching RAISES the score
        { "match": { "description": "noise cancelling" } },
        { "term":  { "features": "bluetooth" } }
      ],

      "must_not": [                     # must NOT match. Filter context too
        { "term": { "discontinued": true } }
      ],

      "minimum_should_match": 0         # how many `should` are REQUIRED
    }
}}

# THE NAMES ARE MISLEADING and this is worth being precise about:
#
#   must     = AND, scored
#   filter   = AND, not scored
#   must_not = NOT, not scored
#   should   = OR, scored — but only when it is the ONLY thing there
#
# THE `should` RULE, which trips up everyone:
#   * if the bool has NO must and NO filter, then at least one should must
#     match. It behaves as OR
#   * if the bool HAS a must or a filter, then should becomes purely
#     optional — zero of them may match and the document still qualifies.
#     They only affect ranking
#
# Set minimum_should_match explicitly whenever you care. Relying on the
# implicit behaviour produces queries whose meaning changes when someone
# later adds a filter clause.

If the answer is yes or no, it belongs in filter

A clause in filter context skips scoring entirely and — for clauses used repeatedly — its result is cached as a bitset of matching documents in the node query cache. Reusing that bitset is close to free, so a filtered search is often an order of magnitude cheaper than the same conditions expressed as must. It is also more correct: a category, a status, a boolean or a date range has no meaningful relevance contribution, and putting it in must lets an arbitrary BM25 number for "is this in the audio category" perturb the ranking of your actual search. The rule is mechanical — does this condition have degrees of matching? If not, filter.

what caching actually does here
THE NODE QUERY CACHE holds, per segment, a bitset of which documents match a
filter clause. It caches clauses that are used often enough to be worth it —
Elasticsearch tracks frequency and only caches after a clause has been seen
several times, and only on segments above a size threshold.

  { "term": { "status": "published" } }

Once cached, applying that filter is a bitwise AND over a bitset. No term
lookup, no scoring, no document access.

WHAT IS NOT CACHED:
  * anything in query context, because the score depends on the query
  * range queries on a field with very high cardinality, sometimes
  * "now"-relative date ranges, because the value changes every millisecond

    { "range": { "@timestamp": { "gte": "now-1h" } } }     # never cacheable

  ROUND IT and it becomes cacheable:

    { "range": { "@timestamp": { "gte": "now-1h/m" } } }   # rounded to minute

  That single character is a large win on a dashboard that runs the same
  time-window filter hundreds of times a minute.

GET /_nodes/stats/indices/query_cache
#   hit_count, miss_count, cache_size, evictions

THE SHARD REQUEST CACHE is different and also worth knowing: it caches the
whole response for size=0 requests — which is to say, aggregations. A
dashboard that repeatedly runs the same aggregation over an index that has
not changed gets the entire result back for free.

  GET /logs/_search?request_cache=true
  index.requests.cache.enable: true          # default true for size=0

It is invalidated on refresh, so it only helps on indices that are not being
written to — which describes yesterday's log index perfectly.

dis_max, and why summing scores is usually wrong
# Searching "quick fox" across title and body with a bool should:

{ "bool": { "should": [
    { "match": { "title": "quick fox" } },
    { "match": { "body":  "quick fox" } } ]}}

# The scores are SUMMED. A document with "quick" in the title and "fox" in
# the body — two mediocre partial matches — can outrank a document with
# "quick fox" as its exact title.
#
# That is almost never what you want. dis_max takes the single best field's
# score instead:

{ "dis_max": {
    "queries": [
      { "match": { "title": "quick fox" } },
      { "match": { "body":  "quick fox" } } ],
    "tie_breaker": 0.3 } }

# tie_breaker adds a fraction of the OTHER matching clauses' scores, so
# matching in several fields is still slightly better than matching in one.
# 0.3 is the conventional starting point.

# YOU WILL RARELY WRITE dis_max BY HAND, because multi_match wraps it:

{ "multi_match": {
    "query":  "quick fox",
    "fields": [ "title^3", "body" ],     # ^3 boosts the title
    "type":   "best_fields",             # DEFAULT — this is dis_max
    "tie_breaker": 0.3 } }

#   best_fields     dis_max. For "find the one field that matches well"
#   most_fields     sum. For the same text analysed several ways
#   cross_fields    treats the fields as one big field. For names, addresses
#   phrase          best_fields with match_phrase
#   bool_prefix     the last term is a prefix — for search-as-you-type
#
# best_fields is the default and the right default. Choose most_fields when
# you have deliberately indexed one value multiple ways — a title field with
# a stemmed version and an exact version, say.
must_not is filter context, and that is occasionally surprising

Clauses inside must_not are never scored — there is nothing sensible to score, since you are asking for the absence of a match. That is fine and expected. What catches people is the combination with should: a bool containing only must_not and should clauses still requires one should to match, because must_not does not count as a "must or filter" for the purposes of that rule. Meanwhile a bool containing only must_not matches every document that is not excluded, which is a legitimate and occasionally expensive way to select almost your entire index. When a bool query behaves unexpectedly, count which clause types are present — the semantics genuinely depend on the combination rather than on each clause in isolation.

Structure that scales

the shape most real search queries end up in
GET /products/_search
{
  "query": {
    "bool": {
      "must": {                                    # WHAT the user searched
        "multi_match": {
          "query": "wireless noise cancelling",
          "fields": [ "name^3", "description", "brand^2" ],
          "type": "best_fields",
          "fuzziness": "AUTO",
          "minimum_should_match": "75%"
        }
      },
      "filter": [                                  # WHAT THEY NARROWED TO
        { "terms": { "category": [ "audio", "accessories" ] } },
        { "range": { "price": { "gte": 50, "lte": 400 } } },
        { "term":  { "in_stock": true } }
      ],
      "should": [                                  # WHAT WE PREFER
        { "term": { "featured": { "value": true, "boost": 2 } } },
        { "range": { "released": { "gte": "now-6M", "boost": 1.5 } } }
      ],
      "must_not": [
        { "term": { "discontinued": true } }
      ]
    }
  },
  "size": 20,
  "from": 0,
  "_source": [ "name", "brand", "price", "thumbnail" ],
  "track_total_hits": 1000
}

# THE DISCIPLINE: user intent in must, user-selected facets in filter,
# business preferences in should, exclusions in must_not. Once a codebase
# follows that convention consistently, a query is readable at a glance and
# the performance characteristics are predictable.

# NOTE track_total_hits. Since version 7 the total is only counted exactly
# up to 10,000 by default, because counting every match on a large index is
# expensive and nobody reads page 500. Setting it to a number caps the count
# there; true forces an exact count and costs real time.
#
#   "hits": { "total": { "value": 10000, "relation": "gte" } }
#
# That "relation": "gte" is Elasticsearch telling you the number is a floor,
# not a total. Applications that display it as an exact count are lying to
# users, and this is a very common bug in search interfaces.
Two APIs that answer "why did this happen"

GET /index/_validate/query?explain=true tells you whether a query is syntactically valid and shows the Lucene query it compiles to — useful when a DSL query is silently doing something other than what you wrote, which happens most often with misspelled field names, since an unknown field is simply a clause that matches nothing rather than an error. GET /index/_explain/{id} takes a query and one document id and returns the full scoring breakdown for that pairing, including whether it matched at all. Between them they answer both halves of the usual question: why did this document not appear, and why did that one rank above it (chapter 10).

The short version

  1. bool is the workhorse. must is scored AND, filter is unscored AND, must_not is NOT, should is OR-or-boost.
  2. should means OR only when there is no must or filter; otherwise it is purely a ranking boost. Set minimum_should_match explicitly.
  3. If the answer is yes or no, use filter — cacheable, faster, and it keeps meaningless scores out of your ranking.
  4. Round your now-relative ranges to make them cacheable. One character, large win on dashboards.
  5. dis_max takes the best field's score, not the sum, which is what you want across fields — and multi_match wraps it.
  6. Structure the query by role: intent in must, facets in filter, preferences in should.
  7. track_total_hits defaults to 10,000, and "relation": "gte" means the total you are showing users is a floor.
  8. _validate/query and _explain answer why a document did not match and why one outranked another.
