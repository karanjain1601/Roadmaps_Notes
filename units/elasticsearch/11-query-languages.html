The other query languages

Elasticsearch accepts five query languages, which sounds like abundance and is mostly history. Each was added for a different audience, only one of them is the general answer for application code, and knowing which is which saves a lot of confusion when reading documentation.

ES|QL, the one that is new

a piped query language, introduced in 8.11
POST /_query
{ "query": """
FROM logs-*
| WHERE @timestamp > NOW() - 1 hour AND level == "ERROR"
| EVAL is_slow = duration_ms > 1000
| STATS count = COUNT(*), p95 = PERCENTILE(duration_ms, 95) BY service, is_slow
| WHERE count > 10
| SORT count DESC
| LIMIT 20
""" }

# READ IT LEFT TO RIGHT. Each pipe takes a table and produces a table, which
# is the significant difference from both the DSL and SQL — you can filter
# AFTER aggregating, compute a field and then group by it, and chain
# transformations without nesting anything.
#
# In the DSL that query is a bool filter, a terms aggregation, a nested
# percentiles aggregation, a bucket_selector pipeline aggregation and a
# bucket_sort — four levels of nesting and roughly forty lines of JSON.

# THE COMMANDS worth knowing:
#   FROM        source indices, patterns and aliases
#   WHERE       filter. Can appear anywhere in the pipeline
#   EVAL        compute new columns
#   STATS ... BY   aggregate
#   SORT, LIMIT, KEEP, DROP, RENAME
#   DISSECT, GROK   parse text into fields, mid-query
#   ENRICH      look up values from an enrich policy — the closest thing to
#               a join that Elasticsearch offers
#   LOOKUP JOIN a left join against a lookup index (added in 8.18/9.0;
#               check your version before relying on it)

# WHAT IT IS NOT GOOD AT: relevance. ES|QL is built for analytics, and
# although it has gained text-matching functions, ranked full-text search
# with BM25 scoring, boosting and highlighting is Query DSL territory. Use
# ES|QL to compute over your data and the DSL to search it.

# ALSO WORTH KNOWING: it returns COLUMNAR results —
#   { "columns": [ { "name": "service", "type": "keyword" }, ... ],
#     "values":  [ [ "checkout-api", 412 ], [ "auth", 88 ] ] }
# which is compact and is not the hits array your existing code expects.
The Query DSL is still the answer for application search

ES|QL is genuinely good and it has not displaced the DSL. Everything relevance-related lives in the DSL: BM25 scoring, field boosts, function_score, rescore, highlighting, collapse, suggest, and the full range of query types from chapter 8. The DSL is also what every client library, every ORM-ish wrapper and every piece of documentation assumes. The clean division of labour is DSL for search, ES|QL for analytics — a product search box uses the DSL, a dashboard computing p95 latency by service uses ES|QL, and reaching for the wrong one means fighting the language.

KQL and Lucene syntax

the two text-box languages, which are frequently confused
KQL — Kibana Query Language. The default in Kibana's search bar.

  level:ERROR and service:checkout-api
  response:>=400
  message:*timeout*
  user.name:(alice or bob)
  not tags:test
  service:* and not level:DEBUG

  Readable, forgiving, and NOT AN ELASTICSEARCH FEATURE. Kibana parses KQL
  in the browser and sends the Query DSL to Elasticsearch. There is no KQL
  endpoint, and you cannot send KQL from your application.

LUCENE SYNTAX — what query_string accepts. Kibana can also use it.

  level:ERROR AND service:checkout-api
  response:[400 TO 599]
  title:"exact phrase"~2
  name:wireles~                     fuzzy
  title:consensus^3 OR body:raft    boosts
  _exists_:discount
  /err(or|ors)/                     regular expressions

  More powerful, more punctuation, and it THROWS on a syntax error. That
  last point is why it does not belong in a public search box — an
  unmatched quote returns a 400 rather than results (chapter 8).

  { "query_string": { "query": "level:ERROR AND service:checkout-api",
                      "default_field": "message" } }

  { "simple_query_string": { "query": "wireless +headphones -wired",
                             "fields": [ "name", "description" ] } }
  # simple_query_string supports + | - " * and NEVER throws. If you want
  # operator syntax in front of users, this is the one.

THE PRACTICAL POINT: KQL and Lucene syntax look similar and behave
differently — KQL's `and` is case-insensitive and Lucene's `AND` is not,
KQL has no boosting, Lucene has no `not` in lowercase. Documentation and
Stack Overflow answers routinely mix them up, and a query copied from a
Kibana screenshot into query_string may parse and mean something else.

SQL and EQL

two narrow tools, each excellent in its lane
-- SQL: for BI tools and people who already know SQL
POST /_sql?format=txt
{ "query": """
    SELECT service, AVG(duration_ms) AS avg_ms, COUNT(*) AS n
    FROM "logs-*"
    WHERE level = 'ERROR'
    GROUP BY service
    HAVING COUNT(*) > 10
    ORDER BY avg_ms DESC
    LIMIT 20
""" }

--  format: txt | json | csv | tsv | yaml | cbor | smile
--  and a JDBC and ODBC driver, which is the actual reason it exists —
--  Tableau and Power BI can point at Elasticsearch directly.

--  WHAT IT CANNOT DO:
--    * joins between indices
--    * full-text relevance ranking, except via a MATCH() function that
--      escapes into the DSL
--    * nested documents, cleanly
--    * most of the interesting aggregation types
--
--  It translates to the DSL underneath, and you can see the translation:
POST /_sql/translate
{ "query": "SELECT service FROM logs WHERE level = 'ERROR'" }
--  This is a genuinely useful learning tool: write what you mean in SQL and
--  read the DSL it produces.

-- ================================================================

-- EQL: Event Query Language. For ORDERED SEQUENCES, which nothing else here
-- can express.
POST /logs-endpoint/_eql/search
{ "query": """
    sequence by user.name with maxspan=5m
      [ authentication where event.outcome == "failure" ] with runs=3
      [ authentication where event.outcome == "success" ]
      [ process where process.name == "net.exe" ]
""" }

--  "three failed logins, then a success, then this process — all by the
--   same user, within five minutes"
--
--  THAT IS NOT EXPRESSIBLE IN THE DSL. The DSL matches documents
--  independently; it has no concept of one document following another. EQL
--  is built for exactly this and it is why security detection rules use it.
--
--  sequence by    correlate on a shared value
--  with maxspan=         a time window for the whole sequence
--  until [ ... ]         cancel the sequence if this happens first
--  runs=N                repetition
--  sample by      unordered co-occurrence, when order does not matter
--
--  If you are not doing security analytics you will never need it. If you
--  are, it is the reason to choose Elasticsearch over alternatives.
Every one of these compiles down to the same engine

ES|QL, SQL, KQL and Lucene syntax are all translated into operations against the same shards, the same inverted indices and the same doc values. That has a reassuring consequence and a limiting one. The reassuring one: performance intuition transfers. A filter is cheap in every language, a leading wildcard is expensive in every language, and deep pagination hurts regardless of syntax. The limiting one: no language can do what the engine cannot. SQL cannot join because Elasticsearch cannot join; ES|QL's ENRICH is a lookup against a pre-built enrich index rather than a real join. A friendlier syntax over the same constraints is still the same constraints, and expecting SQL to make Elasticsearch relational is the commonest disappointment here.

Which to learn, in order

Query DSL first, and properly. It is the native interface, it is what every client library and every piece of documentation assumes, and the other languages are best understood as translations of it — which is why _sql/translate is such a good learning tool. ES|QL second, if you do analytics or build dashboards; it makes queries that are forty lines of nested JSON in the DSL into six readable lines, and it is where Elastic is investing. KQL by osmosis from using Kibana — there is nothing to study. SQL only if a BI tool needs it. EQL only if you do security analytics, in which case it is the whole reason you are here.

The short version

  1. Query DSL is the native interface and the right default for application search. Everything relevance-related lives only here.
  2. ES|QL is piped and reads left to right, so you can filter after aggregating. Analytics and dashboards.
  3. KQL is a Kibana feature, not an Elasticsearch one. There is no endpoint; Kibana translates it in the browser.
  4. Lucene syntax throws on a parse error. Use simple_query_string for anything user-facing.
  5. KQL and Lucene syntax look alike and differ in case sensitivity and features. Documentation mixes them up constantly.
  6. SQL exists for JDBC and ODBC. It cannot join, and _sql/translate is a good way to learn the DSL.
  7. EQL expresses ordered sequences, which nothing else here can. Security analytics, or never.
  8. All of them compile to the same engine. A friendlier syntax over the same constraints is still the same constraints.
