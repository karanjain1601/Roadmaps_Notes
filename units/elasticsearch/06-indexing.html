Indexing documents

A write returns success roughly a second before it is searchable, an update is really a delete and an insert, and a delete does not free any space. All three follow from one Lucene property: segments are immutable.

bulk refresh translog versioning

The operations

CRUD, and the distinctions that matter
# CREATE OR REPLACE at a known id
PUT /articles/_doc/1
{ "title": "Consensus", "views": 0 }

# CREATE ONLY — fails with 409 if the id exists
PUT /articles/_create/1
{ "title": "Consensus" }

# CREATE with a generated id
POST /articles/_doc
{ "title": "Consensus" }

# GET BY ID. Real-time — bypasses search entirely and always sees the
# latest version, even before a refresh
GET /articles/_doc/1
GET /articles/_source/1
HEAD /articles/_doc/1

# PARTIAL UPDATE
POST /articles/_update/1
{ "doc": { "views": 42 } }

# SCRIPTED UPDATE — atomic read-modify-write on the shard
POST /articles/_update/1
{ "script": { "source": "ctx._source.views += params.n", "params": { "n": 1 } } }

# UPSERT
POST /articles/_update/1
{ "script": { "source": "ctx._source.views += 1" },
  "upsert": { "title": "Consensus", "views": 1 } }

DELETE /articles/_doc/1

# WHAT AN UPDATE ACTUALLY IS: Elasticsearch fetches _source, applies your
# change in memory, and reindexes the WHOLE DOCUMENT. There is no partial
# write to disk, because segments are immutable. A "partial update" is a
# convenience in the API, not an optimisation in the engine — and it needs
# _source enabled, which is one of several reasons not to disable it.
#
# A DELETE is a tombstone. The document is marked deleted in a bitset and
# skipped in results; the terms and doc values stay on disk until a merge
# rewrites that segment without it. Deleting a million documents frees
# nothing immediately, and GET /_cat/indices shows docs.deleted alongside
# docs.count so you can see how much dead weight a shard is carrying.

Where a write goes

The write path Step through what happens between your request and a searchable document.

Durable and searchable are different moments

Elasticsearch acknowledges a write once it is in the in-memory buffer and the translog, and the translog is fsynced by default — so the write survives a crash immediately. It becomes searchable only at the next refresh, which turns the buffer into a new segment and by default happens once per second. That gap is why Elasticsearch is described as "near real time" rather than real time, and why a write-then-search in a test suite fails intermittently. A GET by id has no such gap — it reads the translog too and is always current, which is a genuinely useful asymmetry: if you need read-your-writes, read by id.

refresh, flush and merge — three different things
# REFRESH — buffer becomes a searchable segment. Cheap-ish, frequent.
PUT /logs/_settings { "index": { "refresh_interval": "30s" } }
POST /articles/_refresh                     # force one, manually

PUT /articles/_doc/1?refresh=true           # refresh NOW, then return.
                                            # Creates a tiny segment. Fine in
                                            # tests, terrible in a hot loop
PUT /articles/_doc/1?refresh=wait_for       # wait for the NEXT scheduled
                                            # refresh. No extra segments —
                                            # the right choice in production
PUT /articles/_doc/1?refresh=false          # default. Return immediately

# FLUSH — commit segments to disk and clear the translog. Automatic.
POST /articles/_flush
# You should essentially never call this. Elasticsearch flushes when the
# translog reaches index.translog.flush_threshold_size (512mb default).

# MERGE — combine small segments into bigger ones, dropping deleted docs.
# Continuous, in the background, and the main consumer of background I/O.
POST /articles/_forcemerge?max_num_segments=1
# ONLY on an index that will never be written to again. On a live index it
# produces one enormous segment that the merge policy will never reconsider,
# and deleted documents in it are then stuck there permanently.

# THE TRANSLOG, which is what makes the acknowledgement safe:
"index.translog.durability": "request"      # DEFAULT — fsync per request
"index.translog.durability": "async"        # fsync every sync_interval (5s)
"index.translog.sync_interval": "5s"
# async is a real throughput gain for log ingestion where losing five
# seconds of data on a hard crash is acceptable. It is the wrong choice for
# anything you cannot re-send.

Bulk indexing

the only sane way to load data
POST /_bulk
{ "index":  { "_index": "articles", "_id": "1" } }
{ "title": "Consensus", "views": 0 }
{ "create": { "_index": "articles", "_id": "2" } }
{ "title": "Raft" }
{ "update": { "_index": "articles", "_id": "1" } }
{ "doc": { "views": 5 } }
{ "delete": { "_index": "articles", "_id": "3" } }

# NDJSON: one action line, one source line, newline-delimited, and the file
# MUST end with a newline. The format is deliberately dumb so that the
# coordinating node can split it without parsing the whole body.

# CHECK THE RESPONSE. This is the mistake that matters:
#
#   { "took": 30, "errors": true, "items": [ ... ] }
#
# The HTTP status is 200 even when individual documents failed. A bulk
# request is not atomic — some documents succeed, some fail, and the only
# place that is recorded is the per-item status inside the body. Client
# libraries that ignore "errors" silently drop data, and this is the single
# most common way an Elasticsearch load loses documents.

# SIZING:
#   * 5-15 MB per request is the usual sweet spot. Measure — the right
#     number depends on document size and cluster shape
#   * document COUNT is the wrong unit; bytes is the right one
#   * too large and you hit http.max_content_length (100mb) or push the
#     coordinating node into a circuit breaker

# FOR A LARGE INITIAL LOAD:
PUT /articles/_settings
{ "index": { "refresh_interval": "-1",        # no refreshes at all
             "number_of_replicas": 0 } }      # do not replicate per document
# ... load everything ...
PUT /articles/_settings
{ "index": { "refresh_interval": "1s", "number_of_replicas": 1 } }
POST /articles/_forcemerge?max_num_segments=1
#
# Replicas built afterwards are copied from finished shards rather than
# constructed document by document, which is dramatically faster. This
# combination routinely doubles or triples load throughput.

# LET ELASTICSEARCH GENERATE IDS when you can. A supplied id forces a check
# for an existing document with that id before writing; an auto-generated
# one is known to be new, so the check is skipped.

# HANDLE 429 PROPERLY. TOO_MANY_REQUESTS means the write queue is full, and
# it is backpressure rather than an error. Retry with exponential backoff;
# do not treat it as a failure and do not retry immediately in a tight loop.
A bulk response of 200 does not mean the data arrived

It is worth repeating on its own because it costs people real data. _bulk returns HTTP 200 as long as the request itself was well-formed; individual documents can fail for mapping conflicts, version conflicts, circuit breakers or rejected queue slots, and each failure appears only as a status inside its own items entry. Every bulk client must check response["errors"] and, when true, walk the items array. The official language clients mostly do this for you if you use their bulk helpers — and mostly do not if you call the raw endpoint yourself, which is exactly what a hand-rolled ingestion script does.

Concurrency

optimistic concurrency control
GET /articles/_doc/1
# { "_seq_no": 41, "_primary_term": 1, "_source": { "views": 42 } }

PUT /articles/_doc/1?if_seq_no=41&if_primary_term=1
{ "views": 43 }
# 409 if anything changed the document since you read it

# There are no transactions and no locks. This is the compare-and-swap
# primitive, and it is the only concurrency control available.
#
# _seq_no    increments per operation on a shard
# _primary_term increments when a shard's primary changes, so a write from a
#               client that was talking to a stale primary is rejected
#
# The pair is what makes the check correct across a failover — the older
# ?version= parameter was not.

# FOR EXTERNAL SYSTEMS OF RECORD, use your own version number:
PUT /articles/_doc/1?version=7&version_type=external
{ "title": "Consensus" }
# Rejected if the stored version is >= 7. This makes out-of-order delivery
# safe: replaying an old change from a queue is a no-op rather than a
# regression, which is exactly what you want when Elasticsearch holds a
# derived copy of data owned elsewhere (chapter 1).

# UPDATE BY QUERY AND DELETE BY QUERY — batch operations, and they take a
# snapshot at the start, so documents changed underneath cause conflicts:
POST /articles/_update_by_query?conflicts=proceed&wait_for_completion=false
{ "query": { "term": { "status": "draft" } },
  "script": { "source": "ctx._source.status = 'archived'" } }
# -> { "task": "node-1:12345" }

GET /_tasks/node-1:12345
POST /_tasks/node-1:12345/_cancel

# ALWAYS use wait_for_completion=false for anything touching more than a few
# thousand documents. Otherwise the HTTP connection has to stay open for the
# duration, and a client timeout does NOT cancel the work — it just leaves
# you with no way to observe it.

Reindexing

the operation you will need eventually
# Changing a field type, changing an analyzer, changing the shard count —
# all of these mean building a new index and copying into it.

PUT /articles-v2 { "mappings": { ... }, "settings": { ... } }

POST /_reindex?wait_for_completion=false&slices=auto
{
  "source": {
    "index": "articles",
    "size": 5000,
    "query": { "range": { "published": { "gte": "2020-01-01" } } }
  },
  "dest": { "index": "articles-v2", "op_type": "create" },
  "script": {
    "source": "ctx._source.total = (ctx._source.remove('amount') ?: 0) / 100.0"
  }
}

# slices=auto parallelises across the source shards. On a large index this
# is the difference between hours and a coffee break.
#
# op_type: create makes the reindex idempotent — re-running it will not
# overwrite documents already copied, so a failed run can be resumed.

# THE ALIAS SWAP, which is why you always read through an alias:
POST /_aliases
{ "actions": [
    { "remove": { "index": "articles",    "alias": "articles-live" } },
    { "add":    { "index": "articles-v2", "alias": "articles-live" } } ]}
# Atomic. No window where the alias points at nothing.

# HANDLING WRITES DURING THE REINDEX is the hard part, and _reindex does not
# solve it for you. Three approaches:
#   1. accept the downtime — stop writes, reindex, swap
#   2. dual-write to both indices during the migration, then swap
#   3. reindex, then catch up with a second pass filtered on a timestamp,
#      then swap. Requires an updated_at field you can trust
#
# Plan this before you need it. The reindex itself is the easy half.
Ingest pipelines do the transformation before the document lands

Rather than cleaning data in your application or standing up Logstash, a pipeline runs inside Elasticsearch on the ingest node: PUT /_ingest/pipeline/logs with processors like grok, date, convert, rename, set, geoip and user_agent. Attach it with ?pipeline=logs, or set index.default_pipeline so every write to the index goes through it whether the client knows or not. Test with POST /_ingest/pipeline/logs/_simulate, which runs your documents through and shows the output without indexing anything — the same debugging role _analyze plays for text. For a great many deployments this removes the need for a separate ingestion service entirely.

The short version

  1. Segments are immutable. An update reindexes the whole document; a delete is a tombstone that frees nothing until a merge.
  2. Durable and searchable are different moments. The translog makes it safe immediately; a refresh makes it findable, ~1s later.
  3. GET by id is always current. If you need read-your-writes, read by id.
  4. ?refresh=wait_for, not ?refresh=true — the latter creates a tiny segment per call.
  5. Bulk returns 200 with failures inside. Check errors and walk the items, or you will silently lose documents.
  6. For a big load: refresh_interval: -1, replicas 0, then restore both and force-merge.
  7. if_seq_no and if_primary_term are the only concurrency control. There are no transactions.
  8. Use wait_for_completion=false for reindex and update-by-query, and read through an alias so the swap is atomic.
