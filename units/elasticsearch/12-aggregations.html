Aggregations

The half of Elasticsearch that has nothing to do with search, and arguably the reason it displaced dedicated analytics databases for log data. It also produces numbers that are approximate by design, in ways that are easy to miss and awkward to explain afterwards.

terms metrics nesting cardinality

Buckets and metrics

two kinds, and they nest
GET /orders/_search
{
  "size": 0,                              # no documents, just the numbers
  "query": { "range": { "placed_at": { "gte": "now-30d/d" } } },
  "aggs": {

    "by_country": {                       # BUCKET agg — splits documents up
      "terms": { "field": "country", "size": 10 },

      "aggs": {                           # nested inside each bucket
        "revenue":  { "sum": { "field": "total" } },      # METRIC agg
        "avg_order": { "avg": { "field": "total" } },
        "customers": { "cardinality": { "field": "customer_id" } },

        "by_month": {                     # buckets inside buckets
          "date_histogram": { "field": "placed_at", "calendar_interval": "month" },
          "aggs": { "revenue": { "sum": { "field": "total" } } }
        }
      }
    }
  }
}

# size: 0 is important. It says "return no hits", which makes the response
# far smaller AND makes the request eligible for the shard request cache —
# so a dashboard re-running the same aggregation over an unchanged index
# gets the whole response back for free (chapter 7).

# THE MENTAL MODEL: a bucket aggregation partitions documents into groups; a
# metric aggregation computes a number over a group. Nesting a bucket inside
# a bucket subdivides; nesting a metric inside a bucket computes per group.
#
# AGGREGATIONS RUN OVER DOC VALUES, the columnar structure from chapter 3 —
# which is why text fields cannot be aggregated and .keyword sub-fields can.

Where the numbers go wrong

Why a terms aggregation can return the wrong top N Each shard sends its own top results. The coordinating node never sees the rest.
—doc_count_error_upper_bound
—top N correct?
—memory cost
Three numbers in the response tell you whether to trust it

doc_count_error_upper_bound is the maximum amount by which any returned bucket's count could be understated. sum_other_doc_count is how many documents fell outside the returned buckets — if that is large relative to your total, the buckets you are showing are a small slice. And on a cardinality aggregation, the value is a HyperLogLog++ estimate, exact only below precision_threshold (default 3000, maximum 40000) and typically within a few percent above it. All three are in every response and almost universally ignored, which is how approximate numbers end up in board reports. Read them, and if doc_count_error_upper_bound is non-zero on a number that matters, raise shard_size until it is not.

pipeline aggregations — computing on the results
# Pipeline aggregations take the OUTPUT of other aggregations as input. They
# are how you express "moving average", "difference from last month" and
# "only buckets where X" — none of which the normal aggregations can do.

{ "size": 0,
  "aggs": {
    "monthly": {
      "date_histogram": { "field": "placed_at", "calendar_interval": "month" },
      "aggs": {
        "revenue": { "sum": { "field": "total" } },

        "growth": { "derivative": { "buckets_path": "revenue" } },
        "smoothed": { "moving_fn": {
            "buckets_path": "revenue", "window": 3,
            "script": "MovingFunctions.unweightedAvg(values)" } },
        "cumulative": { "cumulative_sum": { "buckets_path": "revenue" } }
      }
    },

    "best_month": { "max_bucket": { "buckets_path": "monthly>revenue" } },
    "total":      { "sum_bucket": { "buckets_path": "monthly>revenue" } }
  }
}

# THE ONE YOU WILL WANT MOST — bucket_selector, which is HAVING:
{ "aggs": { "by_service": {
    "terms": { "field": "service", "size": 100 },
    "aggs": {
      "errors": { "filter": { "term": { "level": "ERROR" } } },
      "enough": { "bucket_selector": {
          "buckets_path": { "n": "errors._count" },
          "script": "params.n > 10" } }
    }
}}}

# And bucket_sort, which sorts and paginates buckets AFTER computing them:
{ "aggs": { "by_service": {
    "terms": { "field": "service", "size": 100 },
    "aggs": {
      "p95": { "percentiles": { "field": "duration_ms", "percents": [95] } },
      "worst": { "bucket_sort": {
          "sort": [ { "p95.95": { "order": "desc" } } ], "size": 10 } }
    }
}}}
# Note the two-step shape: ask terms for 100 buckets, compute p95 in each,
# then sort by p95 and keep 10. You cannot sort a terms aggregation by a
# metric it has not computed yet, so this is the pattern — and it is why
# ES|QL's flat pipeline reads so much better for this kind of query
# (chapter 11).
Nesting multiplies, and there is a limit for a reason

A terms aggregation with size: 1000 containing another with size: 1000 asks for up to a million buckets, and every one is built in heap on the coordinating node before anything is returned. This is the classic way to make a node unresponsive with a single well-formed request, and it is why search.max_buckets exists — 65,536 by default, and a rejected request is very much better than an out-of-memory node. Two habits avoid the problem: set size to what you will actually display, since a chart showing ten bars does not need a thousand buckets, and reach for composite when you genuinely need to enumerate everything, because it paginates instead of materialising the whole set at once.

composite, for enumerating everything
GET /orders/_search
{ "size": 0,
  "aggs": { "all_customers": {
      "composite": {
        "size": 1000,
        "sources": [
          { "customer": { "terms": { "field": "customer_id" } } },
          { "month":    { "date_histogram": { "field": "placed_at",
                                              "calendar_interval": "month" } } }
        ]
      },
      "aggs": { "spend": { "sum": { "field": "total" } } }
  }}
}

# -> "after_key": { "customer": "c-4192", "month": 1740787200000 }

# Pass it back to continue:
{ "composite": { "size": 1000, "after": { "customer": "c-4192", "month": 1740787200000 },
                 "sources": [ ... ] } }

# THIS IS THE search_after OF AGGREGATIONS (chapter 9): a cursor rather than
# an offset, so the cost per page is constant and memory is bounded.
#
# Use it for: export, reconciliation, feeding a downstream system, anything
# that must see every bucket. Do NOT use it for a dashboard — it is slower
# per bucket than terms and it cannot be sorted by a metric.

# TRANSFORMS are the persistent version of this. Instead of computing the
# pivot on every request, a transform materialises it into a real index,
# either once or continuously:
PUT /_transform/customer_summary
{ "source": { "index": "orders" },
  "dest":   { "index": "customer_summary" },
  "pivot": {
    "group_by": { "customer": { "terms": { "field": "customer_id" } } },
    "aggregations": { "total_spend": { "sum": { "field": "total" } },
                      "order_count": { "value_count": { "field": "order_id" } } }
  },
  "sync": { "time": { "field": "placed_at", "delay": "60s" } },
  "frequency": "5m"
}
POST /_transform/customer_summary/_start

# The destination is an ordinary index you can search, sort and paginate
# normally — including by total_spend, which you cannot do to a terms
# aggregation of a million customers. For "entity-centric" views this is
# the right tool, and it is much less known than it should be.
#   latest transforms keep only the most recent document per group, which
#   is the other common shape: current state per device, per user, per host.
Two smaller traps worth knowing

avg of an avg is not the average. Nesting an average inside buckets and then taking avg_bucket across them weights every bucket equally regardless of size, so a bucket with three documents counts as much as one with thirty thousand. Compute sum and value_count and divide, or use weighted_avg. And calendar_interval is not fixed_interval. A month is not 30 days, a day is not always 24 hours where daylight saving exists, and asking for fixed_interval: "30d" when you meant months produces buckets that drift out of alignment with the calendar — visible as a chart where the monthly peaks slowly slide. Pass "time_zone" too, or your daily buckets are split at UTC midnight rather than the user's.

The short version

  1. Bucket aggregations partition, metric aggregations compute, and they nest arbitrarily.
  2. Always set size: 0 when you only want numbers — smaller response, and eligible for the request cache.
  3. terms is approximate. Each shard sends its own top results, so the global top N can be wrong.
  4. Read doc_count_error_upper_bound and sum_other_doc_count. They are in every response and always ignored.
  5. cardinality and percentiles are estimates — HyperLogLog++ and t-digest respectively.
  6. Nesting multiplies buckets, all built in heap. search.max_buckets is 65,536 for good reason.
  7. composite paginates where terms materialises, and bucket_selector is HAVING.
  8. Transforms materialise a pivot into a real index, which you can then sort and paginate normally.
