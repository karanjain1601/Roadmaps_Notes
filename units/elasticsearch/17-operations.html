Operating it

Elasticsearch tells you a great deal about itself through one family of endpoints, and almost every incident is diagnosable in four commands. The skill is knowing which four, and knowing that a yellow cluster is a warning rather than an emergency.

cat api health circuit breakers upgrades

The first four commands

before forming a theory
# 1. WHAT COLOUR, AND WHY
GET /_cluster/health
GET /_cluster/health?level=indices          # per index
GET /_cluster/allocation/explain            # WHY is that shard unassigned
#    ^ the single most useful diagnostic in Elasticsearch. It answers in
#      plain English: disk watermark, no matching node attributes, too many
#      copies for the node count, an allocation filter, a failed recovery.

# 2. WHAT IS THE CLUSTER DOING RIGHT NOW
GET /_cat/nodes?v&h=name,node.role,heap.percent,ram.percent,cpu,load_1m,disk.avail
GET /_cat/tasks?v&detailed              # long-running operations
GET /_cat/pending_tasks?v               # cluster-state updates queued —
                                        # a growing queue means the master
                                        # is struggling
GET /_cat/recovery?v&active_only=true   # shards being copied

# 3. WHERE IS THE DATA
GET /_cat/indices?v&s=store.size:desc
GET /_cat/shards?v&s=store:desc
GET /_cat/allocation?v                  # disk per node
GET /_cat/thread_pool/search,write?v&h=node_name,name,active,queue,rejected

# 4. WHAT IS UNDER PRESSURE
GET /_nodes/stats/breaker               # circuit breaker trips
GET /_nodes/stats/jvm                   # heap used, GC counts and durations
GET /_nodes/stats/indices/search,indexing,merges,refresh

# THE HEALTH REPORT API, which is newer and underused:
GET /_health_report
# It runs the diagnostics itself and returns findings with symptoms,
# impacts and suggested actions — including the specific documentation link.
# Start here before the manual dig; it often names the problem outright.

Yellow is not an outage

It is worth being emphatic because the colour causes more unnecessary alarm than any other signal in the product. Yellow means every primary shard is assigned and at least one replica is not. Every document is readable, every document is writable, every search returns complete results. What you have lost is redundancy — the next failure might hurt — and Elasticsearch will usually rebuild the missing copies by itself within minutes. A single-node cluster with the default one replica is permanently yellow and entirely healthy. Alert on red, and on yellow that persists beyond the time a recovery should take; paging on yellow itself trains people to ignore the alert.

the disk watermarks, since they cause the scariest failure
cluster.routing.allocation.disk.watermark.low: 85%
#   no NEW shards allocated to this node
cluster.routing.allocation.disk.watermark.high: 90%
#   Elasticsearch starts MOVING shards off this node
cluster.routing.allocation.disk.watermark.flood_stage: 95%
#   every index with a shard on this node is set to read-only-allow-delete

# THE FLOOD STAGE IS THE ONE THAT HURTS. It applies an index block:
#   "index.blocks.read_only_allow_delete": true
# and your application starts getting:
#   "cluster_block_exception: index [logs-000042] blocked by:
#    [TOO_MANY_REQUESTS/12/disk usage exceeded flood-stage watermark,
#    index has read-only-allow-delete block];"
#
# THE BLOCK IS NOT REMOVED AUTOMATICALLY IN OLDER VERSIONS. Free the disk,
# then clear it explicitly:
PUT /_all/_settings
{ "index.blocks.read_only_allow_delete": null }
# Newer versions release it once usage falls below the high watermark, but
# check rather than assume — this has caught many people mid-incident,
# having freed space and wondered why writes were still failing.

# ALSO WORTH KNOWING: the watermarks are evaluated per node, so ONE full
# node can make EVERY index that has a shard there read-only. A single
# unbalanced node takes down writes cluster-wide.

# EMERGENCY SPACE:
DELETE /logs-2025.11.*                  # oldest indices first
POST /logs-000041/_forcemerge?max_num_segments=1    # reclaims deleted docs
PUT /_cluster/settings
{ "transient": { "cluster.routing.allocation.disk.watermark.flood_stage": "97%" } }
#   ^ buys minutes, not a fix. Set it back.

Upgrades

a rolling upgrade, and the rules
THE COMPATIBILITY RULES:
  * rolling upgrades work between minor versions, and from the LAST minor
    of one major to the next major (7.17 -> 8.x, 8.19 -> 9.x)
  * an index created two majors ago cannot be read. You must reindex it, or
    restore it from a snapshot taken by a version that can read it
  * you cannot downgrade. Ever. A node that has started on a newer version
    has upgraded its data directory
  * snapshots restore forward, generally one major version, never backward

THE PROCEDURE, per node:
  1. GET /_cluster/health          — must be green before starting
  2. disable shard allocation, so a stopped node does not trigger a full
     rebalance of its shards onto everything else:
       PUT /_cluster/settings
       { "persistent": { "cluster.routing.allocation.enable": "primaries" } }
  3. stop indexing if you can, and flush:
       POST /_flush
  4. stop the node, upgrade it, start it
  5. re-enable allocation:
       PUT /_cluster/settings
       { "persistent": { "cluster.routing.allocation.enable": null } }
  6. WAIT FOR GREEN before touching the next node
  7. repeat

  Upgrade MASTER-ELIGIBLE NODES LAST. A newer node can join a cluster
  whose master is older; an older node cannot join one whose master is
  newer.

BEFORE ANY OF IT:
  * take a snapshot, and confirm it completed
  * read the breaking changes and the deprecation log:
      GET /_migration/deprecations
    This endpoint tells you what in YOUR configuration will break, which is
    far more useful than reading the release notes cold
  * upgrade Kibana AFTER Elasticsearch, and clients after that
  * test on a restored snapshot in a scratch cluster first, on real data.
    Mapping and query incompatibilities show up there and not in the notes
Two settings that will save an incident

cluster.routing.allocation.enable: primaries before any planned node restart. Without it, stopping a node for sixty seconds makes the cluster decide its shards are gone and begin copying every one of them onto the remaining nodes — hundreds of gigabytes of network and disk I/O that becomes wasted work the moment the node returns. Related: index.unassigned.node_left.delayed_timeout (one minute by default) is what stops a brief network blip from triggering the same storm, and raising it to five minutes is reasonable on a cluster where restarts are routine. And action.destructive_requires_name: true, which refuses wildcard deletes — it is the setting that stands between a fat-fingered DELETE /logs-* and a very bad afternoon.

What to have in place beforehand

  • The metrics table above as a time series, with a year of history. Nearly everything in _cat and _nodes/stats is a point-in-time reading and the useful signal is the trend.
  • Shard count and index count trended — they predict the oversharding wall months before it arrives.
  • Slow logs enabled for search, fetch and indexing, shipped somewhere searchable (chapter 14).
  • Deprecation logging on, and read before every upgrade.
  • Index templates in version control, so "what changed" has an answer.
  • A restore test, dated, with its duration recorded (chapter 15). That duration is your real recovery time.
  • An ILM policy on every time-series index, and an alert for indices with no policy.
  • _cluster/allocation/explain in your runbook, because it answers the question you will have at 3am.
  • A scratch cluster you can restore a snapshot into. It is where upgrades and mapping changes get tested.
Do not run _forcemerge, _flush or _cache/clear as a reflex

All three appear in Stack Overflow answers as fixes and all three are usually wrong. _forcemerge on a live index creates one enormous segment the merge policy will never reconsider, so deleted documents in it are stuck permanently (chapter 14) — it belongs in ILM's warm phase, on read-only indices. _flush commits the translog, which Elasticsearch already does on its own schedule; calling it manually achieves nothing except during a planned shutdown. _cache/clear discards the caches that were making your queries fast, so throughput gets worse for the next several minutes. The reflex worth building instead is GET /_cluster/allocation/explain and GET /_health_report, both of which are read-only and frequently name the problem outright.

The short version

  1. Four commands first: cluster health, allocation/explain, _cat/nodes, and the thread pools.
  2. _cluster/allocation/explain is the best diagnostic in the product — it says in plain English why a shard is unassigned.
  3. _health_report runs the diagnosis for you and is underused.
  4. Yellow is not an outage. Alert on red, and on yellow that persists.
  5. The flood-stage watermark makes indices read-only at 95%, and one full node can block writes cluster-wide.
  6. Disable allocation before a planned restart, or you trigger a pointless rebalance of every shard on that node.
  7. Rolling upgrades: masters last, green between nodes, and check _migration/deprecations first.
  8. Do not force-merge, flush or clear caches reflexively. All three usually make things worse.
