The queries you will use

There are around forty query types and you will use eight. The one thing worth being precise about for each: whether it analyses your input. Every "why does this return nothing" question in Elasticsearch is that question in disguise.

The table you should memorise

Analysed — match, match_phrase, multi_match, match_bool_prefix, query_string, simple_query_string. Your input goes through the field's analyzer, so it matches the way the document was indexed. Not analysed — term, terms, prefix, wildcard, regexp, fuzzy, range, exists. Your input is looked up in the term dictionary exactly as written. Pair an unanalysed query with a text field and it will usually find nothing, because the terms stored are lowercased and stemmed while your input is not. The single most common Elasticsearch bug is term on a text field, and the fix is almost always to query field.keyword instead.

The eight

with the options that actually matter
# 1. MATCH — the default full-text query
{ "match": { "name": {
    "query": "wireless noise cancelling",
    "operator": "or",                  # DEFAULT. "and" requires every term
    "minimum_should_match": "75%",     # better than either extreme
    "fuzziness": "AUTO"                # typo tolerance, see below
}}}

# 2. MATCH_PHRASE — terms adjacent and in order
{ "match_phrase": { "name": {
    "query": "noise cancelling",
    "slop": 1                          # allow 1 position of movement
}}}
# Uses the POSITIONS stored in the inverted index. "cancelling noise" needs
# slop 2 to match, because swapping two terms costs two moves.

# 3. TERM — exact, unanalysed. For keyword, numeric, boolean, date fields
{ "term": { "status": "published" } }
{ "term": { "status": { "value": "published", "case_insensitive": true } } }

# 4. TERMS — several exact values, OR'd
{ "terms": { "status": [ "published", "featured" ] } }
{ "terms": { "user_id": { "index": "admins", "id": "1", "path": "user_ids" } } }
#          ^ TERMS LOOKUP: fetch the list from another document. This is how
#            you filter by a set that lives elsewhere without two round trips

# 5. RANGE — numbers, dates, IPs
{ "range": { "price": { "gte": 50, "lt": 400 } } }
{ "range": { "@timestamp": { "gte": "now-7d/d", "lte": "now/d" } } }
#   date maths: now-1h  now+2d  now-1M/M  ||/d  and /d /M /y to round
#   ROUND IT so the filter is cacheable (chapter 7)

# 6. PREFIX — terms starting with. Not analysed
{ "prefix": { "name.keyword": "Sony" } }
# Slow on high-cardinality fields: it must enumerate every matching term.
# For autocomplete use index_prefixes or an edge n-gram field (chapter 3)

# 7. WILDCARD — * and ?. Not analysed. Genuinely dangerous
{ "wildcard": { "sku": "WH-*-BLK" } }
# A LEADING wildcard scans the entire term dictionary. On a large index that
# is a query that can take a shard offline. allow_expensive_queries: false
# disables this whole family at the cluster level, and that is a reasonable
# production setting

# 8. EXISTS — the field has a non-null value
{ "exists": { "field": "discount" } }
{ "bool": { "must_not": { "exists": { "field": "discount" } } } }   # IS NULL
# Note: a field set to null, or to [], does not exist. There is no
# distinction between "absent" and "explicitly null" — chapter 4's rule that
# null creates no field, seen from the query side

Typo tolerance

fuzziness, and its limits
{ "match": { "name": { "query": "wirelss", "fuzziness": "AUTO" } } }

# Fuzziness is LEVENSHTEIN EDIT DISTANCE: insertions, deletions,
# substitutions, and transpositions of adjacent characters.
#
#   AUTO   0 edits for terms of 1-2 characters
#          1 edit  for 3-5
#          2 edits for 6+
#   1, 2   a fixed number. 2 is the maximum Lucene supports
#
# AUTO is right. A fixed fuzziness of 2 on short words makes "cat" match
# "dog"-adjacent nonsense, which is why the length scaling exists.

  "prefix_length": 1        # first N characters must be exact. Big speedup,
                            # and typos in the first letter are rare
  "max_expansions": 50      # cap on how many term variants to consider

# WHAT FUZZINESS DOES NOT DO:
#   * phonetic matching. "Smith" does not match "Smyth" via edit distance in
#     the way a phonetic analyzer would
#   * word-order or missing-word tolerance
#   * anything across term boundaries — "head phones" and "headphones" are
#     one edit apart as strings and completely different as TERM SEQUENCES,
#     so fuzziness will not bridge them. That needs a shingle or compound
#     word filter at index time

# THE COST IS REAL. A fuzzy query expands into many term lookups, so it is
# meaningfully slower. The usual production pattern is a bool that prefers
# exact matches and falls back:

{ "bool": { "should": [
    { "match": { "name": { "query": "wirelss", "boost": 3 } } },
    { "match": { "name": { "query": "wirelss", "fuzziness": "AUTO" } } }
]}}
# Exact matches score three times higher, and fuzzy matches still appear
# below them rather than being mixed in at the same weight.
Do not put query_string in front of users

query_string parses Lucene syntax — AND, OR, NOT, field:value, wildcards, regular expressions, fuzzy operators, boosts. That is genuinely useful in Kibana, where the person typing is an operator debugging something. Exposed to end users it is two problems: a syntax error throws a 400, so a search box that accepts an unmatched quote returns an exception rather than results, and a user can write *:* or a leading-wildcard regular expression and make one shard do an enormous amount of work. Use simple_query_string if you want operator syntax in a public search box — it supports +, |, - and quotes, and it never throws, silently ignoring anything malformed.

Searching several fields

multi_match, and picking the type
{ "multi_match": {
    "query":  "sony wireless headphones",
    "fields": [ "name^3", "brand^2", "description" ],
    "type":   "best_fields",
    "tie_breaker": 0.3,
    "minimum_should_match": "75%"
}}

# best_fields   the best-matching field's score wins (dis_max). DEFAULT.
#               For "one of these fields should match this well"
# most_fields   scores are summed. For ONE value indexed several ways —
#               a title with a stemmed analyzer and an exact analyzer
# cross_fields  treats the fields as one combined field, matching terms
#               across them. THE RIGHT ANSWER FOR NAMES AND ADDRESSES:
#               "sony headphones" where "sony" is in brand and "headphones"
#               is in name. best_fields handles that badly because neither
#               field matches the whole query
# phrase        best_fields, but each field uses match_phrase
# bool_prefix   the final term is treated as a prefix. Search-as-you-type

# FIELD PATTERNS work:
"fields": [ "name", "name.*", "*_text" ]

# BOOSTS ARE MULTIPLIERS on the score, not priorities. name^3 means a match
# there scores three times what the same match scores in an unboosted field.
# They are worth tuning empirically and worth NOT over-tuning: boosts above
# about 10 usually mean the field should have been a separate should clause
# or the ranking problem is not really about field weights (chapter 10).

# THE SEARCH-AS-YOU-TYPE SHORTCUT, which saves defining n-grams by hand:
PUT /products { "mappings": { "properties": {
    "name": { "type": "search_as_you_type" } }}}

{ "multi_match": {
    "query": "wirel",
    "type":  "bool_prefix",
    "fields": [ "name", "name._2gram", "name._3gram" ] }}
# The field type creates the shingle sub-fields for you. For most
# autocomplete needs this is enough and considerably less work than a
# hand-rolled edge n-gram analyzer.
When a search returns nothing, check in this order

One: does the field name exist? A misspelled field is not an error — it is a clause that matches nothing, silently. GET /index/_mapping. Two: are you using an unanalysed query on an analysed field? That is term, prefix, wildcard or fuzzy against a text field; try field.keyword. Three: what terms actually exist? Run POST /index/_analyze with "field" over the document value and over your query string and compare (chapter 3). Four: is minimum_should_match or "operator": "and" excluding it? Five: GET /index/_explain/{id} with your query, which states plainly whether that document matched and why. Working the list takes two minutes and beats guessing every time.

The short version

  1. Analysed: match, match_phrase, multi_match, query_string. Not analysed: term, terms, prefix, wildcard, fuzzy, range.
  2. term on a text field is the most common bug. Query field.keyword instead.
  3. match_phrase uses stored positions, and slop allows movement — a swap costs two.
  4. Round date ranges so the filter is cacheable.
  5. Leading wildcards scan the whole term dictionary. allow_expensive_queries: false is a reasonable production setting.
  6. fuzziness: "AUTO", and it will not bridge term boundaries — "head phones" and "headphones" need index-time help.
  7. simple_query_string for user input; query_string throws on a syntax error.
  8. cross_fields for names and addresses, best_fields for everything else.
