Data lifecycle

Deleting old documents from a big index is one of the worst things you can ask Elasticsearch to do. The whole lifecycle apparatus — data streams, rollover, tiers, ILM — exists so that you can delete a whole index instead, which is nearly free.

ilm rollover data streams snapshots

Why one big index is the wrong shape

the problem, stated plainly
You have a `logs` index. It grows. After a year you want to delete anything
older than 90 days.

    POST /logs/_delete_by_query
    { "query": { "range": { "@timestamp": { "lt": "now-90d" } } } }

WHAT THAT ACTUALLY DOES: marks several hundred million documents as deleted,
one at a time, writing a tombstone for each. Nothing is freed. The disk
space comes back only as background merges rewrite the affected segments
without those documents — which is an enormous amount of I/O, competing with
your live indexing and searching, for hours or days.

And you get to do it again next week.

ALSO WRONG WITH ONE BIG INDEX:
  * the shard count was fixed when it was small, and cannot be changed
  * every search touches all of it, including data nobody is querying
  * yesterday's data and last year's data sit on the same expensive disks
  * you cannot force-merge it, because it is still being written to
  * a mapping change requires reindexing the whole thing

THE ANSWER: write to a NEW INDEX periodically. Then "delete old data" is
DELETE /logs-2025.11.01, which unlinks some files. Instant, no merge storm,
no tombstones.

Every capability in this chapter is built on that one idea.

Data streams

the modern shape for append-only time-series data
# A data stream is a name you write to, backed by hidden indices that roll
# over automatically. You index into `logs-app-prod`; Elasticsearch writes
# into .ds-logs-app-prod-2026.03.14-000042 and manages the rest.

# 1. A component template for the mapping
PUT /_component_template/logs-mappings
{ "template": { "mappings": {
    "properties": {
      "@timestamp": { "type": "date" },
      "message":    { "type": "text" },
      "service":    { "type": "keyword" },
      "level":      { "type": "keyword" }
    }
}}}

# 2. A component template for the settings
PUT /_component_template/logs-settings
{ "template": { "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1,
    "refresh_interval": "30s",
    "index.lifecycle.name": "logs-policy"
}}}

# 3. An index template that declares a data stream
PUT /_index_template/logs-template
{ "index_patterns": [ "logs-*" ],
  "data_stream": { },
  "composed_of": [ "logs-mappings", "logs-settings" ],
  "priority": 200 }

# 4. Just write. The stream and its first backing index appear.
POST /logs-app-prod/_doc
{ "@timestamp": "2026-03-14T09:12:44Z", "message": "...", "level": "ERROR" }

GET /_data_stream/logs-app-prod
POST /logs-app-prod/_rollover                    # force one manually

# WHAT A DATA STREAM GIVES YOU OVER A PLAIN ALIAS:
#   * @timestamp is required, and the stream knows its time range, so a
#     query with a date filter can SKIP backing indices entirely
#   * writes always go to the newest backing index automatically
#   * append-only by default — updates and deletes by id are rejected,
#     which is a feature for logs and a blocker for anything mutable
#   * rollover, ILM and tier movement are wired in
#
# THE CONSTRAINT WORTH KNOWING: because it is append-only, you cannot use a
# data stream for data you need to update in place. Use an alias with
# rollover instead, which gives you most of the same benefits and permits
# updates.

the policy itself
PUT /_ilm/policy/logs-policy
{ "policy": { "phases": {

  "hot": {
    "actions": {
      "rollover": {
        "max_primary_shard_size": "40gb",     # THE ONE TO USE
        "max_age": "1d",
        "max_docs": 200000000
      },
      "set_priority": { "priority": 100 }     # recovery order after restart
    }
  },

  "warm": {
    "min_age": "7d",
    "actions": {
      "allocate": { "number_of_replicas": 1,
                    "require": { "data": "warm" } },
      "forcemerge": { "max_num_segments": 1 },   # safe — no longer written to
      "shrink": { "number_of_shards": 1 },       # fewer, larger shards
      "readonly": { },
      "set_priority": { "priority": 50 }
    }
  },

  "cold": {
    "min_age": "30d",
    "actions": {
      "searchable_snapshot": { "snapshot_repository": "s3-backups" },
      "set_priority": { "priority": 0 }
    }
  },

  "frozen": {
    "min_age": "90d",
    "actions": { "searchable_snapshot": { "snapshot_repository": "s3-backups" } }
  },

  "delete": {
    "min_age": "365d",
    "actions": { "delete": { } }
  }
}}}

GET /logs-app-prod/_ilm/explain          # WHERE IS EACH INDEX, AND WHY
POST /_ilm/stop  |  POST /_ilm/start
POST /logs-000042/_ilm/retry             # after fixing whatever failed

# min_age IS MEASURED FROM ROLLOVER, not from index creation and not from
# the age of the documents inside. An index that stayed hot for three days
# before rolling over enters the warm phase three days later than you might
# expect. This is the commonest source of "why is this index still hot".

# ROLL OVER BY max_primary_shard_size, not max_size or max_docs. It targets
# the thing that actually matters — shard size (chapter 14) — and it adapts
# automatically when your volume changes. Combine it with max_age so that a
# quiet period does not leave one index open for months.

# ILM RUNS ON A POLL INTERVAL, ten minutes by default. Nothing is instant,
# and an index sitting one step behind is usually just waiting for the poll.
indices.lifecycle.poll_interval: 10m
The tiers are a cost decision, and searchable snapshots are the interesting one

Hot takes the writes and wants fast SSDs. Warm is read-only, force-merged and shrunk, on cheaper disks. Cold and frozen use searchable snapshots — the data lives in object storage and the node holds only a cache, so you are paying S3 prices for storage while the index remains queryable. Frozen goes further, keeping almost nothing locally and fetching on demand, which makes queries much slower and storage nearly free. That is the shape of the trade: each tier down is roughly an order of magnitude cheaper and correspondingly slower, and for log data where 95% of queries touch the last three days, moving the other 97% of the bytes to cold storage is one of the largest cost reductions available in the whole product.

Snapshots

the only actual backup Elasticsearch has
# 1. Register a repository
PUT /_snapshot/s3-backups
{ "type": "s3",
  "settings": { "bucket": "my-es-backups", "region": "eu-west-1",
                "base_path": "prod", "compress": true } }
# types: s3, gcs, azure, fs (a shared filesystem), hdfs, url (read-only)

# 2. Take one
PUT /_snapshot/s3-backups/snapshot-2026-03-14?wait_for_completion=false
{ "indices": "logs-*,products", "include_global_state": true }
#   include_global_state captures templates, ILM policies, pipelines and
#   cluster settings. Without it you restore data into a cluster that does
#   not know how to handle it — a genuinely unpleasant discovery

# 3. Automate with SLM, which is the part people skip
PUT /_slm/policy/nightly
{ "schedule": "0 30 2 * * ?",
  "name": "",
  "repository": "s3-backups",
  "config": { "indices": [ "*" ], "include_global_state": true },
  "retention": { "expire_after": "60d", "min_count": 10, "max_count": 100 } }

POST /_slm/policy/nightly/_execute          # test it now
GET /_slm/policy/nightly                    # last success AND last failure
GET /_slm/stats

# 4. Restore
POST /_snapshot/s3-backups/snapshot-2026-03-14/_restore
{ "indices": "products",
  "rename_pattern": "(.+)",
  "rename_replacement": "restored-$1",       # do not clobber the live index
  "index_settings": { "index.number_of_replicas": 0 } }

GET /_snapshot/s3-backups/_all
GET /_cat/recovery?v&active_only=true

# SNAPSHOTS ARE INCREMENTAL AT THE SEGMENT LEVEL. A second snapshot only
# uploads segments that did not exist before, so nightly full snapshots are
# far cheaper than they sound. Deleting a snapshot only removes segments no
# other snapshot references.
#
# YOU CANNOT RESTORE INTO AN OLDER CLUSTER, and there are version-skew
# limits going forward — generally one major version. Snapshots are not an
# archive format you can sit on indefinitely and read in five years.
#
# AND A REPLICA IS NOT A BACKUP. It faithfully applies your DELETE within
# milliseconds. Same argument as every other unit.
Restore-test on a schedule, and time it

A backup nobody has restored is a hope. The specific failure modes here are worth knowing because they are all silent until the day you need them: a snapshot taken without include_global_state, so the templates and ILM policies are missing and restored indices behave nothing like the originals; a repository whose credentials expired months ago, with the SLM failure buried in a stats endpoint nobody reads; a restore that works and takes eleven hours, which nobody knew until it mattered. Restore into a scratch cluster quarterly, check a document count and a sample query, and record how long it took — that duration is your actual recovery time objective, and it grows with your data.

Two conveniences worth knowing

shrink, split, and DSL
# SHRINK — fewer shards, for an index that is no longer written to. The
# original shard count must be a multiple of the new one.
POST /logs-000042/_shrink/logs-000042-shrunk
{ "settings": { "index.number_of_shards": 1,
                "index.number_of_replicas": 1,
                "index.codec": "best_compression" } }
# Requires the source index to be read-only and all its shards on one node.
# ILM's shrink action handles both prerequisites for you, which is a good
# reason to let ILM do it.

# SPLIT — more shards. Also requires read-only, and the target must be a
# multiple of the source.
POST /products/_split/products-bigger
{ "settings": { "index.number_of_shards": 6 } }
# This is the closest thing to changing the shard count without a full
# reindex, and the multiple-of constraint means planning ahead: an index
# created with 1 shard can be split to any number, one created with 5 can
# only go to 10, 15, 20.

# index.codec: best_compression uses DEFLATE instead of LZ4 for _source.
# Roughly 15-25% smaller, slightly slower to fetch. For warm and cold data
# that is an easy win, and ILM's forcemerge is the natural place to apply
# it since the index is being rewritten anyway.

# DATA STREAM LIFECYCLE (DSL) — the simpler alternative to ILM, for data
# streams only:
PUT /_data_stream/logs-app-prod/_lifecycle
{ "data_retention": "90d" }
# One setting: how long to keep it. Elasticsearch handles rollover and
# deletion, and manages downsampling and merging itself.
#
# No tiers, no phases, no actions. If your requirement genuinely is "keep
# 90 days of logs and then delete them", this is the whole configuration
# and ILM is more machinery than the problem needs. Reach for ILM when you
# actually want tier movement or per-phase actions.
Downsampling, for metrics you keep for years

Time-series metrics have an awkward property: you want per-second resolution for the last day and nobody needs it for data from eighteen months ago — but the storage cost is dominated by the old data precisely because there is so much of it. Downsampling replaces an index with a smaller one holding statistical aggregates over a coarser interval: POST /metrics-000012/_downsample/metrics-000012-1h with {"fixed_interval": "1h"} turns per-second samples into hourly min, max, sum, value count and average. The reduction is often 20–50×, the data stays queryable through the same data stream, and it can be an ILM action so it happens on schedule. For a metrics cluster this is frequently a larger saving than tier movement, and it is much less known.

The short version

  1. delete_by_query on a large index is a merge storm. Write to periodic indices so deletion means dropping an index.
  2. Data streams are the modern shape for append-only time-series data — and they reject updates, which is a feature or a blocker.
  3. Roll over by max_primary_shard_size, with max_age as a backstop.
  4. ILM's min_age is measured from rollover, not from index creation. This is the usual "why is it still hot".
  5. Each tier down is ~10× cheaper and slower. Searchable snapshots put cold data in object storage while keeping it queryable.
  6. Snapshots are the only real backup, incremental at the segment level, and useless without include_global_state.
  7. Restore-test quarterly and record the duration. That number is your actual recovery time.
  8. Data stream lifecycle is one setting where ILM is five phases. Use ILM only when you need tiers or per-phase actions.
