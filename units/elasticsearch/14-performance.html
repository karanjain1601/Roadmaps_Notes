Performance and sizing

Most Elasticsearch performance problems are capacity problems wearing a disguise, and most capacity problems come from three decisions: how many shards, how much heap, and how often to refresh. All three are easier to get right at the start than to fix later.

The heap rules, which have not changed in a decade

Half of RAM, and never above about 31 GB. Half, because Lucene needs the other half for the filesystem cache — segments are memory-mapped files and the page cache is what makes searching them fast, so a node with all its memory in heap is a node doing disk I/O for every query. And below 32 GB because the JVM uses compressed object pointers under that threshold; crossing it makes every reference larger, so a 32 GB heap holds less usable data than a 31 GB one. If you have a 128 GB machine, run 31 GB of heap and let Lucene use the rest, or run two nodes on it. Then the shard count rule: aim below 20 shards per GB of heap, which puts a 30 GB node at 600 shards maximum and comfortably fewer in practice.

Indexing throughput

the levers, in order of effect
# 1. BULK, and size it in bytes. 5-15 MB per request (chapter 6)
# 2. RAISE THE REFRESH INTERVAL. Each refresh makes a segment, and segments
#    must be merged. 1s is for search freshness you probably do not need
PUT /logs/_settings { "index": { "refresh_interval": "30s" } }

# 3. FOR A BULK LOAD: no refreshes, no replicas, then restore both
PUT /logs/_settings
{ "index": { "refresh_interval": "-1", "number_of_replicas": 0 } }

# 4. LET ELASTICSEARCH GENERATE IDS. A supplied id forces a lookup to check
#    whether that document already exists; a generated one is known to be new

# 5. INDEX LESS. The largest wins are usually in the mapping (chapter 4):
"index": false          # not searchable — for fields you only display
"doc_values": false     # not sortable or aggregatable
"norms": false          # no length normalisation
"_source": { "excludes": [ "huge_blob" ] }
#    Check what is actually costing you:
GET /logs/_disk_usage?run_expensive_tasks=true

# 6. INDEX BUFFER, shared across all shards on the node
indices.memory.index_buffer_size: 10%      # default. 512mb+ helps heavy loads

# 7. MULTIPLE CLIENT THREADS. One bulk stream will not saturate a cluster.
#    Increase concurrency until you see 429s, then back off one step. The
#    429 is the signal that you have found the ceiling — it is backpressure,
#    not an error, and should be retried with backoff

# WHAT TO WATCH:
GET /_nodes/stats/thread_pool
#   thread_pool.write.rejected      rising = you are past capacity
#   thread_pool.write.queue
GET /_cat/thread_pool/write?v
GET /_nodes/stats/indices/indexing
#   index_total, index_time_in_millis -> ms per document

# TWO THINGS THAT DO NOT HELP AS MUCH AS PEOPLE EXPECT:
#   * more shards. Indexing is already parallel across shards; beyond one
#     per node you are adding overhead rather than throughput
#   * faster CPUs. Indexing is usually bound by disk and by merge I/O.
#     Fast local SSDs are the hardware that matters

Merging

the background process that explains a lot of I/O
Every refresh creates a segment. Segments are immutable, so deletes and
updates accumulate as tombstones inside them (chapter 6). Merging combines
small segments into larger ones and drops the deleted documents on the way.

WHY IT MATTERS:
  * a search must visit EVERY segment in a shard, so hundreds of tiny
    segments is hundreds of times the per-segment overhead
  * deleted documents occupy disk and are scanned until a merge removes them
  * merging is the single largest consumer of background disk I/O, and it
    competes directly with indexing and searching

  GET /_cat/segments/logs?v
  GET /_cat/indices/logs?v&h=index,docs.count,docs.deleted,store.size
  #   docs.deleted large relative to docs.count = dead weight

  GET /_nodes/stats/indices/merges
  #   current, total_time_in_millis, total_throttled_time_in_millis
  #   THROTTLED TIME RISING means merges cannot keep up with indexing, and
  #   segment count will grow until searches slow down

  indices.store.throttle / index.merge.scheduler.max_thread_count
  #   defaults are tuned for SSDs. On spinning disks set max_thread_count
  #   to 1 — concurrent merges on a single spindle are pathological

FORCE MERGE, and the trap:
  POST /logs-2026.03.14/_forcemerge?max_num_segments=1

  ONLY on an index that will never be written to again. On a live index it
  produces one enormous segment that the merge policy will never select
  again — so any documents deleted from it afterwards are stuck there
  permanently, and the shard carries that dead weight forever.
  This is the right thing to do to yesterday's log index as part of ILM
  (chapter 15), and the wrong thing to do to a live search index.

  Note vector indices merge much more slowly, because HNSW graphs must be
  rebuilt rather than concatenated (chapter 13).

the three caches, and what invalidates each
# 1. NODE QUERY CACHE — per-segment bitsets for filter clauses
indices.queries.cache.size: 10%            # of heap
GET /_nodes/stats/indices/query_cache
#   hit_count, miss_count, evictions
#   Only caches clauses used repeatedly, on segments above a size threshold

# 2. SHARD REQUEST CACHE — whole responses for size=0 requests
index.requests.cache.enable: true          # default true for size=0
indices.requests.cache.size: 1%            # of heap
GET /_nodes/stats/indices/request_cache
#   Invalidated on REFRESH, so it only helps indices that are not being
#   written to. Which describes yesterday's log index perfectly, and is why
#   dashboards over historical data are so much faster than over today's

# 3. THE FILESYSTEM CACHE — the operating system's page cache
#   Not an Elasticsearch feature and by far the most important. Segments are
#   memory-mapped files; if they are in the page cache, searching them is
#   memory speed, and if not, it is disk speed.
#
#   THIS IS THE REASON FOR THE HALF-OF-RAM HEAP RULE. Every GB you give the
#   JVM is a GB Lucene cannot use for caching segments.

GET /_stats/fielddata?fields=*              # should be near zero
GET /_nodes/stats/breaker
#   Circuit breakers: parent, fielddata, request, in_flight_requests
#   A tripped breaker returns a 429 or 503 rather than an OOM. Rising trip
#   counts mean queries are asking for more memory than is available —
#   usually a huge aggregation or an unbounded terms size (chapter 12)

# PROFILE A SLOW QUERY — per-shard, per-clause timing:
GET /logs/_search
{ "profile": true, "query": { ... } }
# Verbose, and it tells you exactly which clause and which phase cost the
# time. Use it on one slow query rather than guessing.

# SLOW LOGS, which are off by default and worth turning on:
PUT /logs/_settings
{ "index.search.slowlog.threshold.query.warn": "5s",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.indexing.slowlog.threshold.index.warn": "10s" }
Watch the fetch phase separately from the query phase

A search has two phases (chapter 9) and they fail for different reasons. A slow query phase means the matching itself is expensive — an unbounded aggregation, a leading wildcard, too many shards, a heavy scoring function. A slow fetch phase means the matching was fine and retrieving the documents is the problem: large _source, highlighting over big fields, or too many hits requested. The distinction matters because the fixes have nothing in common, and the slow log threshold is configured separately for each. When a search is slow and the query looks cheap, check indices.search.fetch_time_in_millis against query_time_in_millis before optimising the wrong half.

Hardware

what to spend money on, in order
1. FAST LOCAL SSDs. NVMe if possible. Elasticsearch is I/O bound far more
   often than CPU bound, and network-attached storage adds latency to every
   segment read. If you are on cloud block storage, provision IOPS
   deliberately and watch for burst-credit exhaustion — a cluster that was
   fine for three weeks and then was not is very often this.

2. RAM. Half for heap (capped near 31 GB), half for the page cache. More RAM
   means more of your index is served from memory.

3. CPU. Matters for indexing, aggregations and vector search. Rarely the
   first bottleneck.

4. NETWORK. Matters during recovery and rebalancing, when whole shards move
   between nodes. A 200 GB shard on a 1 Gbps link is a long recovery.

  ------------------------------------------------------------------
  ALSO:
    * bootstrap.memory_lock: true, and set the ulimit to match. A swapped
      heap is catastrophic — GC pauses of tens of seconds
    * set -Xms and -Xmx to the SAME value. A growing heap causes pauses
    * do not disable swap without also setting memory_lock; do both
    * vm.max_map_count = 262144. Elasticsearch memory-maps every segment
      file and will refuse to start without enough map entries
    * one node per machine unless the machine is large enough to justify
      two, in which case configure them not to hold copies of the same shard
  ------------------------------------------------------------------

MANY SMALL NODES OR FEW LARGE ONES? Prefer a moderate number of moderate
nodes. Very large nodes hold too many shards and recover slowly; very small
ones spend a disproportionate fraction of their memory on per-shard
overhead and cluster state. Three to ten data nodes covers a great many
production deployments, and going wider should be a response to a measured
limit rather than an assumption.
Benchmark with your own data, and with Rally

Every number in this chapter is a starting point that your workload will contradict. Rally is Elastic's own benchmarking tool and the same one they use to test releases: it drives a defined workload — including your own indices and queries — and reports indexing throughput, query latency percentiles and resource usage, so you can compare configurations rather than argue about them. The specific things worth measuring before committing: refresh interval against indexing throughput, shard count against query latency at your real concurrency, and heap size against GC behaviour under load. An afternoon with Rally on representative data settles questions that otherwise get decided by whichever blog post was read most recently.

The short version

  1. Target 10–50 GB per shard, sized for the data you will have in a year, and under 20 shards per GB of heap.
  2. Half of RAM for heap, never above ~31 GB. Above 32 GB the JVM loses compressed pointers and a bigger heap holds less.
  3. The filesystem cache is the most important cache, and it is the other half of your RAM.
  4. Raise the refresh interval. Each refresh makes a segment, and segments must be merged.
  5. Merging is the largest background I/O consumer. Rising throttled time means it cannot keep up.
  6. Force-merge only read-only indices, or deleted documents are stuck in one giant segment forever.
  7. Separate the query phase from the fetch phase when diagnosing; the fixes have nothing in common.
  8. Spend on SSDs first, RAM second. Elasticsearch is I/O bound far more often than CPU bound.
