Vector and semantic search

BM25 matches words. Embeddings match meaning. Neither is strictly better, they fail in different directions, and the interesting result of the last few years is that combining them beats either — which is why hybrid retrieval, not vector search, is the thing to build.

knn hnsw elser hybrid

The two failure modes are complementary, which is the whole argument

BM25 fails on vocabulary mismatch. A query using different words from the document finds nothing, because there is no shared term to match — "something to carry my computer" against a document that says "laptop bag" scores zero. Embeddings fail on exact tokens. A part number, a SKU, a proper noun or a rare technical term gets embedded into roughly the same region as similar-looking strings, so a search for WH-1000XM5 returns plausible-looking wrong products. Since the failures do not overlap, combining the two rankings recovers most of both — and that is a stronger and more reliable result than either method tuned in isolation.

Dense vectors and kNN

the mapping and the query
PUT /products
{ "mappings": { "properties": {
    "name": { "type": "text" },
    "name_vector": {
      "type": "dense_vector",
      "dims": 384,                       # must match your model exactly
      "index": true,                     # build an HNSW graph for fast ANN
      "similarity": "cosine",            # cosine | dot_product | l2_norm |
                                         # max_inner_product
      "index_options": {
        "type": "int8_hnsw",             # quantisation — see below
        "m": 16,                         # graph connections per node
        "ef_construction": 100           # build-time search breadth
      }
    }
}}}

# APPROXIMATE kNN — uses the HNSW graph. This is what you want.
GET /products/_search
{ "knn": {
    "field": "name_vector",
    "query_vector": [0.12, -0.03, ...],
    "k": 10,                             # results to return
    "num_candidates": 100,               # per shard. Higher = better recall,
                                         # slower. 100 is a reasonable start
    "filter": { "term": { "in_stock": true } }
}}

# EXACT kNN — brute force over every vector, via a script_score query
{ "query": { "script_score": {
    "query": { "term": { "category": "audio" } },
    "script": { "source": "cosineSimilarity(params.qv, 'name_vector') + 1.0",
                "params": { "qv": [ ... ] } } }}}
# Exact and O(documents). Fine over a few thousand pre-filtered candidates,
# hopeless over millions.

# THE FILTER IS PRE-FILTERED, and this matters. Elasticsearch applies the
# filter DURING the graph traversal rather than after it, so a restrictive
# filter still returns k results. Systems that post-filter return fewer than
# k — sometimes zero — when the filter is selective, which is a common and
# nasty surprise in other vector stores.
#
# The caveat: a very restrictive filter degrades the graph search toward
# brute force, because the traversal keeps hitting excluded nodes. Elastic-
# search will fall back to exact search when the filtered set is small
# enough, which is the right behaviour.
what HNSW costs, and quantisation
HNSW is a layered proximity graph. Search starts at a sparse top layer,
descends greedily toward the query point, and refines at the bottom. That
gives you logarithmic-ish search instead of linear — and it requires the
graph to be resident in memory to be fast.

  THE MEMORY ARITHMETIC, which is the thing to plan around:

    raw float32 vectors:  dims × 4 bytes × documents
    plus the graph:       roughly dims × 4 × m × 2 (small by comparison)

    1 million docs × 384 dims × 4 bytes  ≈  1.5 GB
    10 million   × 768 dims × 4 bytes    ≈  30 GB

  And that wants to be in the page cache OR the JVM heap depending on
  version and configuration — either way it is real memory that competes
  with everything else on the node.

QUANTISATION is the answer, and it is unusually effective:

  int8_hnsw    4× smaller. Recall loss is typically small enough to be
               invisible after rescoring. THE SENSIBLE DEFAULT, and it
               became the default for float vectors in recent versions
  int4_hnsw    8× smaller. More loss, still often acceptable
  bbq_hnsw     Better Binary Quantisation — ~32× smaller. Available in
               newer 8.x/9.x versions. Needs oversampling and rescoring to
               recover recall, and the trade is often excellent
  flat / *_flat  no graph. Exact brute force, for small collections

  Quantised vectors are searched approximately and then RESCORED against
  higher-fidelity values for the top candidates, which is how the recall
  loss is largely recovered. Check the exact options and defaults for your
  version — this area has moved quickly.

TWO OTHER COSTS worth knowing:
  * indexing is slower. Building graph connections is real work
  * MERGING is much slower, because segments' graphs must be rebuilt rather
    than concatenated. A vector index does noticeably more background I/O
    than an equivalent text index (chapter 14)

Hybrid retrieval

RRF, via the retrievers API
GET /products/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": {                        # the lexical side
            "query": { "multi_match": {
                "query": "wireless noise cancelling",
                "fields": [ "name^2", "description" ] } } } },
        { "knn": {                             # the semantic side
            "field": "description_vector",
            "query_vector_builder": {
              "text_embedding": {
                "model_id": "sentence-transformers__all-minilm-l6-v2",
                "model_text": "wireless noise cancelling" } },
            "k": 50, "num_candidates": 200 } }
      ],
      "rank_window_size": 50,
      "rank_constant": 20
    }
  },
  "size": 10
}

# RECIPROCAL RANK FUSION combines rankings by POSITION, not by score:
#
#     rrf_score(d) = Σ over retrievers  1 / (rank_constant + rank(d))
#
# That is the key property. BM25 scores are unbounded and corpus-dependent;
# cosine similarities live in [-1, 1]. There is no principled way to add
# them, and normalising them requires knowing the distributions. RRF sidesteps
# the problem entirely by throwing the scores away and keeping only the order.
#
# A document ranked 1st and 5th beats one ranked 3rd and 3rd — appearing
# near the top of EITHER list counts for a lot, which is exactly the
# behaviour you want given the complementary failure modes.
#
# rank_constant dampens the contribution of top ranks. Higher values flatten
# the curve so lower-ranked results matter more. 20 is the usual default and
# 60 appears in the original paper; it is worth trying both.

# THE RETRIEVERS API also composes other stages:
#   standard    a normal query
#   knn         vector search
#   rrf         fusion
#   text_similarity_reranker   a cross-encoder or reranking service over the
#                              top N — a second-stage reranker, which is
#                              usually the largest single quality win after
#                              hybrid itself
#   rule        pinned or excluded documents, for merchandising

# The retrievers API arrived in 8.14 and has been evolving since. Check what
# your version supports before designing around a particular stage.

{ "service": "elasticsearch",
  "service_settings": { "num_allocations": 1, "num_threads": 1,
                        "model_id": ".elser_model_2" } }

# 2. A semantic_text field
PUT /articles
{ "mappings": { "properties": {
    "body": { "type": "text" },
    "body_semantic": { "type": "semantic_text", "inference_id": "my-elser" }
}}}

# 3. Index normally. Chunking and inference happen automatically.
PUT /articles/_doc/1
{ "body": "...", "body_semantic": "..." }

# 4. Query with natural language
GET /articles/_search
{ "query": { "semantic": { "field": "body_semantic",
                           "query": "how do distributed systems agree" } } }

# WHAT IT HANDLES FOR YOU: chunking long text into passages, running
# inference at index time and query time, storing the vectors, and matching
# at the chunk level while returning whole documents.
#
# Chunking is the part people underestimate. An embedding of a 5,000-word
# document is a vector representing the average of everything in it, which
# is close to useless — the signal is diluted to nothing. Passage-level
# chunking with overlap is what makes semantic search over long documents
# work at all, and getting it right by hand is fiddly.

# ELSER SPARSE VECTORS, if you want the model without semantic_text:
PUT /articles { "mappings": { "properties": {
    "body_expanded": { "type": "sparse_vector" } }}}
# ELSER expands text into weighted TERMS rather than a dense vector, so
# matching uses the inverted index. That means it works with the existing
# machinery, it is interpretable — you can see which terms it added — and it
# does not need an HNSW graph in memory. The cost is longer posting lists
# and slower queries than dense kNN, plus the licence tier.
The model is now part of your index format

An embedding is only comparable with embeddings from the same model. Change the model — a new version, a different provider, a switch from 384 to 768 dimensions — and every vector in the index is invalid and must be regenerated. That is a full reindex plus the inference cost of re-embedding your entire corpus, which for millions of documents is a real bill and a real amount of time. Two habits make it survivable: record the model id and version in the index name or metadata, so you always know what generated what, and read and write through an alias (chapter 4) so the swap to a re-embedded index is atomic. This is the operational cost that separates a semantic search demo from a semantic search system, and it is rarely mentioned in the demo.

Is it worth it

Semantic earns its place

  • Question-shaped queries — "how do I cancel my order" against documentation that never uses those words
  • RAG retrieval, where the query is a user's sentence rather than keywords
  • Vocabulary gaps between how you write and how users search
  • Multilingual, with a multilingual model — genuinely hard to do lexically
  • Images, audio, recommendations — anywhere there are no words to match
  • Long-tail queries nobody wrote a synonym rule for

BM25 is still better, or enough

  • Identifiers — SKUs, part numbers, error codes, names
  • Keyword search where users already type the domain's vocabulary
  • Filtered navigation, which is filters and facets, not retrieval
  • When the corpus is small — a good analyzer and synonyms will beat a mediocre embedding setup
  • When you have not tuned BM25 yet — see below
  • When latency and memory are tight; kNN costs both
Tune BM25 before you reach for vectors

The commonest sequence is: search quality is poor, vector search is the current answer to poor search quality, so vectors get added — and the result is a system that is more expensive, slower, harder to operate and only slightly better. Meanwhile the lexical side still has no synonyms, the wrong analyzer for the content's language, no field boosts, minimum_should_match untouched, and identifiers indexed as text. Those fixes are hours of work with no ongoing cost, and they frequently close most of the gap (chapters 3, 8 and 10). Build a rank_eval set first so you can measure what each change is worth. Then add hybrid retrieval, which is a genuine improvement — and you will be able to prove it rather than hope.

The short version

  1. BM25 fails on vocabulary mismatch; embeddings fail on exact tokens. The failures are complementary, which is why hybrid works.
  2. Approximate kNN over an HNSW graph is the practical form. Exact kNN is for small pre-filtered candidate sets.
  3. Filters are applied during traversal, so you still get k results — unlike post-filtering systems.
  4. Vectors are a memory-planning problem. Quantisation is unusually effective; int8 is the sensible default.
  5. RRF fuses by rank, not score, because BM25 scores and cosine similarities are not on comparable scales.
  6. semantic_text handles chunking, which is the part people underestimate — embedding a whole long document dilutes the signal to nothing.
  7. The model becomes part of your index format. Changing it means re-embedding everything.
  8. Tune BM25 first. Synonyms, the right analyzer and field boosts are free and often close most of the gap.
