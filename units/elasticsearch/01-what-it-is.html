What Elasticsearch is

One data structure explains almost everything about it. Understand the inverted index and you understand why Elasticsearch is astonishingly fast at some questions, structurally bad at others, and not a place to keep your only copy of anything.

search engine inverted index elk use cases

The idea

A relational database stores rows and, when you ask it to find something, walks an index from value to row. That works beautifully when you know the value: WHERE id = 41, WHERE created_at > '2026-01-01'. It works badly when the question is "which of these ten million documents mention distributed consensus, ranked by how relevant they are".

The reason is that LIKE '%consensus%' cannot use a B-tree index. A B-tree is sorted by the whole value, so it can find things that start with a prefix and nothing else — a substring in the middle means reading every row. Ten million rows, every query.

An inverted index turns the problem inside out. Instead of mapping document to contents, it maps term to the documents containing it.

The index does not grow with the corpus, in the way that matters

Finding a term in an inverted index is one lookup in a sorted dictionary of terms, then reading a list of document ids. The cost is proportional to how many documents match, not to how many documents exist. A corpus of ten documents and a corpus of ten million both answer "which documents contain consensus" in roughly the time it takes to read the matching list. That single property is why search engines exist as a separate category of software, and it is worth holding onto — most of Elasticsearch's design decisions, including the ones that look strange, are protecting it.

What you give up to get it

Relational databaseElasticsearch
ACID transactions across rowsAtomic per document. Nothing across documents
Joins at query timeNo joins. Denormalise, or use limited alternatives (chapter 5)
Read-your-writesNear-real-time — a write is searchable after a refresh, ~1s by default (chapter 6)
Constraints, foreign keys, uniquenessNone. Nothing stops you writing contradictory data
Schema enforced on writeSchema inferred on first write, then fixed and mostly unchangeable (chapter 4)
Exact countsApproximate above a threshold, on purpose (chapter 12)
Rows found by valueDocuments found by relevance, scored and ranked
Query planner does the thinkingYou choose the access path, in the query itself

Read that table as a trade rather than a list of deficiencies. Every row on the right is a consequence of the same decision: precompute an index over the contents of documents so that content-based questions are cheap. Transactions across documents would require coordination that makes indexing slow. Joins would require touching two indexes at query time, which is exactly the cost the design removes. Immediate visibility would mean writing to disk per document instead of batching into segments.

It is not a system of record

This is the single most consequential thing to internalise, and it comes up in almost every later chapter. Elasticsearch has no transactions across documents, no referential integrity, a mapping you largely cannot change after the fact, and a history of upgrades that require reindexing. The standard architecture is that a database owns the data and Elasticsearch holds a derived, searchable copy — one you can throw away and rebuild. Teams that skip the database and make Elasticsearch the only copy generally discover why over the following eighteen months, and the discovery is expensive because by then the reindex-from-source path does not exist.

What it is actually good at

Full-text search
The obvious one. Ranked results, stemming, synonyms, typo tolerance, phrase matching, highlighting. This is what the inverted index was built for.
Log and event analytics
Enormous volumes of append-only, time-stamped, semi-structured records that you query by any field at all. This is arguably the larger use case now, and the reason for the ELK stack.
Faceted navigation
An e-commerce sidebar showing every brand with counts, filtered live. Aggregations compute this in one request over the whole result set (chapter 12).
Aggregations over big data
The half of Elasticsearch nobody mentions. Grouping, statistics, histograms, percentiles across billions of documents, fast.
Geospatial queries
Points, shapes, distance sorting, bounding boxes — genuinely strong, and rarely the reason people adopt it.
Vector and semantic search
kNN over embeddings, and hybrid retrieval combining it with BM25 (chapter 13). A large part of why the tool is in AI stacks.

The stack around it

ELK, Elastic Stack, and what the pieces do
ELASTICSEARCH   the search and analytics engine. The only mandatory piece.
KIBANA          the UI — dashboards, Dev Tools console, index management,
                and the visualisation layer most people actually interact with
LOGSTASH        an ingestion pipeline: read from anywhere, transform, write to
                Elasticsearch. Powerful, heavy, and increasingly optional
BEATS           lightweight shippers that run on the source machine.
                Filebeat for logs, Metricbeat for metrics, and others
ELASTIC AGENT   the newer single agent that replaces the individual Beats,
                managed centrally through Fleet

"ELK" originally meant Elasticsearch + Logstash + Kibana. Beats arrived and
the acronym stopped working, so the marketing name became "the Elastic Stack".
Both names still circulate and mean roughly the same thing.

INGEST PIPELINES run inside Elasticsearch itself and handle most of what
Logstash used to: parsing, enrichment, field manipulation. For a lot of
deployments they remove the need for Logstash entirely, which is worth
knowing before you deploy a JVM-based pipeline service you do not need.

YOU DO NOT NEED THE STACK. A great many Elasticsearch deployments are one
cluster, an application writing to it, and no Kibana in production. The
stack is the log-analytics product; the engine is a general-purpose one.

GET /

# Create a document. The index is created implicitly if it does not exist.
PUT /articles/_doc/1

  "body":  "Raft and Paxos solve the same problem differently.",

# Read it back by id — this bypasses search entirely and is immediately

# Search it
GET /articles/_search
{ "query": { "match": { "body": "raft" } } }

# What did it infer about my fields?
GET /articles/_mapping

# How is this index doing?
GET /articles/_stats
GET /_cluster/health

# Delete the lot
DELETE /articles

# THE CONVENTIONS, once you see them:
#   /_something        a cluster-level API      (/_search, /_cluster/health)
#   /index/_something  an index-level API       (/articles/_search)
#   /index/_doc/id     a specific document
#   underscore prefix  means "this is an API, not an index name"
#
# The Kibana Dev Tools console understands this abbreviated form directly.

Getting one running

A single node in Docker is one command: docker run -p 9200:9200 -e "discovery.type=single-node" docker.elastic.co/elasticsearch/elasticsearch:8.15.0. Since 8.0 security is on by default, so it will print an elastic user password and a CA fingerprint on first start — that is the change that fixed the long-standing problem of clusters exposed to the internet with no authentication (chapter 16). For learning, Kibana's Dev Tools console is worth the extra container: it autocompletes the DSL, formats responses, and means you are not fighting curl quoting while trying to understand a query.

Where it came from, briefly

Elasticsearch is a distributed layer around Apache Lucene, the Java search library that has been the de facto standard since 1999. Lucene provides the inverted index, the analysis chain, the scoring, the segment format — genuinely most of what makes search work. Elasticsearch provides sharding, replication, cluster coordination, the JSON API and the aggregation framework on top.

That inheritance shows up constantly. Segments are immutable because Lucene's are. The scoring is BM25 because Lucene's is. Some error messages are Lucene's. Solr, the other major search server, is built on the same library — which is why the two have such similar capabilities and such different operational characters.

"It is like a NoSQL database" is a misleading way in

Elasticsearch stores JSON documents without a fixed schema, so the comparison to MongoDB is natural and it leads people astray. MongoDB is a general-purpose document database that happens to have text search; Elasticsearch is a search engine that happens to store documents. The differences that follow are not cosmetic: Elasticsearch has no transactions across documents, no read-your-writes, no cheap document updates — an update deletes and reinserts, because segments are immutable — and a mapping you mostly cannot change. If you approach it as "MongoDB with better search", the first three months are a sequence of unpleasant discoveries. Approach it as an index over data that lives elsewhere and everything fits.

The short version

  1. The inverted index maps terms to documents, so finding by content costs what the results cost, not what the corpus costs.
  2. Everything else is the price of that. No joins, no cross-document transactions, no immediate visibility, no changing your mind about the schema.
  3. It is not a system of record. A database owns the data; Elasticsearch holds a derived copy you can rebuild.
  4. Two large use cases: full-text search, and log and event analytics. The second is now arguably bigger.
  5. Aggregations are half the product and are barely mentioned in the marketing.
  6. The stack is optional. Ingest pipelines inside Elasticsearch replace much of what Logstash did.
  7. Everything is HTTP and JSON. Underscore-prefixed paths are APIs, not indices.
  8. It is Lucene, distributed. Segment immutability, analysis and BM25 all come from there.
