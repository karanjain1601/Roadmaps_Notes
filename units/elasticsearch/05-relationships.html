Objects, nested and relationships

Elasticsearch has no joins, which everyone knows. What catches people is subtler: an array of objects is silently flattened at index time, so a query that looks obviously correct returns documents that do not match it — with no error, ever.

nested object join denormalisation

The flattening trap

Lucene has no concept of an object. A document is a flat set of field-to-terms mappings, so when Elasticsearch indexes nested JSON it flattens the structure into dotted paths. For a single object that is harmless. For an array of objects it destroys the association between fields.

There is no error. That is the whole problem.

Every other modelling mistake in this unit announces itself — a rejected document, a mapping conflict, an empty result set that makes you look. This one returns plausible extra results, forever, silently. A permissions check written this way grants access to people who should not have it; a product filter shows items that do not match; a compliance report includes records it should exclude. If your document contains an array of objects and you query two of their fields together, you need nested — and the time to discover that is now rather than during an audit.

what nested actually does
PUT /projects
{ "mappings": { "properties": {
    "name":    { "type": "text" },
    "members": {
      "type": "nested",                 # <- the whole fix
      "properties": {
        "name": { "type": "keyword" },
        "role": { "type": "keyword" }
      }
    }
}}}

# Nested objects are indexed as SEPARATE HIDDEN LUCENE DOCUMENTS, stored
# adjacent to their parent in the same segment and joined at query time.
# Each one keeps its own field associations intact.

GET /projects/_search
{ "query": {
    "nested": {
      "path": "members",
      "query": {
        "bool": { "must": [
          { "term": { "members.name": "Alice" } },
          { "term": { "members.role": "admin"  } }
        ]}
      },
      "inner_hits": {}                  # WHICH member matched — very useful
    }
}}

# THE COSTS, and they are real:
#
#  * A document with 50 members is 51 Lucene documents. Your doc count in
#    _cat/indices is the visible one; the internal count is much higher and
#    it is what actually consumes resources
#  * Updating ANY field of the parent reindexes the parent and every nested
#    child. A document with a large nested array is expensive to touch
#  * Queries are slower — a join, even a cheap one
#  * index.mapping.nested_objects.limit defaults to 10,000 per document and
#    index.mapping.nested_fields.limit to 50 per index. Both exist because
#    unbounded nesting is a reliable way to exhaust heap
#
# So: use nested where you must, and notice when the array is unbounded and
# growing. An array of a few sizes or a handful of variants is fine; an
# array of every event that ever happened to an order is a different index.

parent/child, and why it is a last resort
PUT /blog
{ "mappings": { "properties": {
    "relation": {
      "type": "join",
      "relations": { "post": "comment" }
    },
    "title": { "type": "text" },
    "body":  { "type": "text" }
}}}

PUT /blog/_doc/1?refresh
{ "title": "Consensus", "relation": { "name": "post" } }

PUT /blog/_doc/c1?routing=1&refresh          # routing is MANDATORY
{ "body": "Great post", "relation": { "name": "comment", "parent": "1" } }

GET /blog/_search
{ "query": { "has_child": { "type": "comment",
    "query": { "match": { "body": "great" } } } } }

GET /blog/_search
{ "query": { "has_parent": { "parent_type": "post",
    "query": { "match": { "title": "consensus" } } } } }

# THE CONSTRAINTS:
#   * parent and children MUST live on the same shard, which is what the
#     routing parameter enforces. Forget it and the relationship breaks
#   * one join field per index, one level of hierarchy in practice
#   * has_child and has_parent queries are SLOW — Elastic's own guidance is
#     roughly 5-10× slower than the equivalent nested query
#   * scoring across the join is limited and awkward
#
# WHEN IT IS NEVERTHELESS RIGHT: a parent with thousands of children that
# change constantly. Nested would reindex the entire parent document on
# every child change; join lets a child be written on its own.
#
# WHEN IT IS NOT: almost everything else. If you are reaching for join
# because the data is relational, the honest answer is that the data is
# relational and Elasticsearch is holding a derived copy of it (chapter 1) —
# so denormalise the copy and let the database own the relationships.
Denormalisation is the intended answer, and it is a real commitment

The Elasticsearch-shaped solution to "I need data from two places" is to write it into one document at index time. A product document carries its category name, its brand name and its supplier name as fields, not as ids. Searches are then a single-shard-local operation with no join at any level, which is exactly the performance the design exists to deliver. The commitment is that when a brand is renamed, you must find and rewrite every document that mentions it — an update_by_query, or more often a reindex from the source database. That is fine when it happens monthly and unworkable when it happens hourly. The question to ask before denormalising is not "does this fit" but "how often does the copied field change, and what rewrites it when it does".

Choosing

a decision procedure
1. IS IT A SINGLE OBJECT, not an array?
      { "customer": { "id": ..., "email": ... } }
   -> object. There is no trap. Nothing to think about.

2. IS IT AN ARRAY OF OBJECTS?
   -> Will you ever query TWO of their fields together and require both to
      match the SAME element?

      NO   -> object. Cheaper, simpler, and correct for this usage.
              e.g. an array of tags with a count you only ever display
      YES  -> nested. This is the flattening trap and there is no other fix.

3. DOES THE RELATED DATA CHANGE MUCH MORE OFTEN THAN ITS PARENT,
   AND ARE THERE MANY OF THEM?
   -> join, reluctantly, and measure the query cost before committing.

4. OTHERWISE
   -> denormalise, and write down what rebuilds the copies.

A FIFTH OPTION PEOPLE FORGET: two indices and two queries. Search the child
index, collect the parent ids, fetch the parents by id. Two round trips,
no join machinery, no nested overhead, and it scales predictably. For a
lot of "I need a join" situations this is both faster and simpler than
making Elasticsearch do it, and it keeps each index simple enough to
reason about.

AND A SIXTH, WHICH IS OFTEN CORRECT: do the join in the database that owns
the data, and index the result. If the relational shape matters to your
queries, the relational store should be answering them — Elasticsearch is
holding a derived copy, and a derived copy can be pre-joined.

Nested aggregations, briefly

the same trap, in the analytics half
# Aggregating a nested field requires the nested aggregation, and forgetting
# it produces numbers that are wrong in the same silent way as the query.

GET /projects/_search
{ "size": 0,
  "aggs": {
    "members": {
      "nested": { "path": "members" },
      "aggs": {
        "by_role": { "terms": { "field": "members.role" } }
      }
    }
}}

# And to get back to the parent's fields from inside a nested aggregation:
{ "aggs": { "members": {
    "nested": { "path": "members" },
    "aggs": { "admins": {
      "filter": { "term": { "members.role": "admin" } },
      "aggs": { "back_to_parent": {
        "reverse_nested": {},
        "aggs": { "projects": { "terms": { "field": "name.keyword" } } }
      }}
    }}
}}}

# reverse_nested is the escape hatch: "having found the matching members,
# now group by something on their PARENT documents". It is the answer to
# "which projects have an admin", asked as an aggregation.

# NOTE THE COUNTS MEAN SOMETHING DIFFERENT. Inside a nested aggregation,
# doc_count counts NESTED DOCUMENTS, not parents. A count of 500 admins
# across 200 projects is 500 member-records, not 500 projects — and people
# report the wrong number to stakeholders on the strength of that confusion
# more often than they discover it.
Check whether you have the bug already

The flattening trap is worth actively auditing for, because nothing will tell you. Look for indices whose mapping contains an object field — meaning no explicit "type", which is how objects appear — that receives arrays, and then grep your query code for bool queries combining two of that object's sub-fields. GET /index/_mapping shows the structure; the array-ness only shows in the data, since Elasticsearch does not record whether a field held one value or many. A quick empirical test: index a document you know should not match, run the query, and see whether it comes back. That five-minute check has found real bugs in permission filters and pricing rules, and it is cheaper than finding them the other way.

The short version

  1. Lucene has no objects. Nested JSON is flattened into dotted paths at index time.
  2. An array of objects loses the association between fields, so a two-field query matches documents that should not match.
  3. There is no error and no warning. The results are plausible and wrong.
  4. nested fixes it by indexing each element as a separate hidden document, at the cost of size, update expense and query speed.
  5. Denormalisation is the intended answer — and the commitment is knowing what rewrites the copies when the source changes.
  6. join is a last resort: same-shard routing, one level, and 5–10× slower than nested.
  7. Two indices and two queries is often better than making Elasticsearch join at all.
  8. Nested aggregations count nested documents, not parents. Use reverse_nested to get back.
