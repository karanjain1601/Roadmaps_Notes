Security

For most of Elasticsearch's history security was an optional paid add-on that was off by default, and the internet accumulated a great many open clusters as a result. Version 8 changed the default, which is the most consequential security decision in the product's history.

rbac api keys tls dls

The history, because it explains the internet

how thousands of clusters ended up public
Before 6.8   Security was Shield, then X-Pack — a commercial plugin. A
             default installation had NO authentication, NO TLS, and bound
             to 0.0.0.0 in many packagings.

6.8 / 7.1    The basic security features became free: authentication, TLS,
             role-based access control. Still OFF by default.

8.0          SECURITY IS ON BY DEFAULT. A new cluster generates a password
             for the `elastic` user, generates certificates, enables TLS on
             the transport layer, and prints an enrolment token on first
             start. You have to work to make it insecure.

THE CONSEQUENCE OF THE FIRST TWENTY YEARS: tens of thousands of
Elasticsearch clusters were exposed to the internet with no authentication.
Shodan indexed them, researchers reported them, and a long series of data
breaches traced back to exactly this. The "Elasticsearch database left
exposed" news story was a genre.

AND A SPECIFIC ONE STILL WORTH KNOWING: an anonymous user who can write to
your cluster can usually do more than corrupt data. Scripting, snapshot
repositories pointing at local paths, and ingest pipelines have all been
avenues for escalation at various versions. Treat unauthenticated write
access as full compromise of the host, not as a data problem.

IF YOU RUN 7.x, TURN IT ON:
  xpack.security.enabled: true
  xpack.security.transport.ssl.enabled: true
  xpack.security.http.ssl.enabled: true
  bin/elasticsearch-setup-passwords interactive

IF YOU RUN 8.x OR 9.x, DO NOT TURN IT OFF. The temptation appears during
local development, and the habit of "we disable security in dev" is how
insecure configuration reaches production.

{

    { "names": [ "products", "products-*" ],
      "privileges": [ "read", "view_index_metadata" ] }

POST /_security/role/ingest-writer
{ "cluster": [ "monitor" ],
  "indices": [
    { "names": [ "logs-*" ],
      "privileges": [ "create_doc", "create_index", "auto_configure" ] }
  ]
}
# create_doc allows indexing NEW documents and not overwriting existing ones,
# which is the right privilege for an append-only log shipper. `write`
# includes update and delete; `index` includes overwriting. Pick the
# narrowest that works.

POST /_security/user/log-shipper
{ "password": "...", "roles": [ "ingest-writer" ], "full_name": "Filebeat" }

GET /_security/role/app-search
GET /_security/user/log-shipper
POST /_security/user/log-shipper/_password { "password": "..." }
GET /_security/_authenticate                   # who am I, and what can I do
POST /_security/user/_has_privileges { ... }   # can I do this specific thing

# THE PRIVILEGE VOCABULARY worth knowing:
#   cluster: monitor, manage, manage_index_templates, manage_ilm, all
#   index:   read, write, index, create_doc, delete, create_index, manage,
#            view_index_metadata, monitor, all
#
# BUILT-IN ROLES: superuser, kibana_admin, monitoring_user, viewer, editor,
# and a set of specific ones for Beats and APM. `viewer` and `editor` are
# reasonable starting points for people; the service roles are usually
# better replaced with narrow custom ones.

Field and document level security

the feature that makes multi-tenancy possible
POST /_security/role/analyst
{ "indices": [
    { "names": [ "employees" ],
      "privileges": [ "read" ],

      "field_security": {                     # FLS — which fields are visible
        "grant":  [ "*" ],
        "except": [ "salary", "ssn", "home_address" ]
      },

      "query": {                              # DLS — which documents
        "term": { "department": "engineering" }
      }
    }
]}

# FLS strips the fields from _source and makes them unsearchable and
# unaggregatable for this role. A query on `salary` returns no matches rather
# than an error, which is the correct behaviour — an error would confirm the
# field exists.
#
# DLS applies the query as an invisible filter to every search this role
# performs. The user cannot see, count, aggregate over or retrieve by id any
# document that does not match.

# MULTI-TENANCY, which is the main reason to use DLS:
POST /_security/role/tenant_template
{ "indices": [
    { "names": [ "shared-data" ],
      "privileges": [ "read" ],
      "query": { "template": {
          "source": "{\"term\":{\"tenant_id\":\"{{_user.metadata.tenant}}\"}}" } }
    }
]}
POST /_security/user/acme-app
{ "password": "...", "roles": [ "tenant_template" ],
  "metadata": { "tenant": "acme" } }

# ONE role, N tenants, enforced by Elasticsearch rather than by your
# application remembering to add a filter. That difference matters: an
# application-level tenant filter is one forgotten WHERE clause away from a
# cross-tenant data leak, and this is not.

# THE COSTS, and they are real:
#   * FLS and DLS are a paid tier (Platinum). Not available on Basic
#   * DLS disables the shard request cache for those requests, because the
#     result now depends on who is asking. Dashboards get slower
#   * FLS interacts badly with some aggregations and with highlighting
#   * neither hides the INDEX. A user who cannot see any documents can still
#     see that the index exists and read its mapping, unless you also
#     restrict view_index_metadata
API keys, not shared passwords

A user with a password is the wrong credential for a service. It cannot be scoped more narrowly than the user's roles, it cannot be given an expiry, and rotating it means coordinating with everything that uses it. An API key can do all three: it is created by a user, it can only ever have a subset of that user's permissions, it takes an expiration, and it is revoked individually without touching anything else. POST /_security/api_key with a role_descriptors block and "expiration": "90d" gives a service exactly the access it needs for a bounded period, and the response is the only time the key is shown. For anything automated — a shipper, a batch job, a microservice — this is the credential to use, and GET /_security/api_key plus DELETE is a real inventory you can audit.

API keys, concretely
POST /_security/api_key
{ "name": "checkout-service-2026-03",
  "expiration": "90d",
  "role_descriptors": {
    "read-products": {
      "cluster": [ ],
      "indices": [ { "names": [ "products" ], "privileges": [ "read" ] } ]
    }
  },
  "metadata": { "service": "checkout", "owner": "payments-team" }
}
# -> { "id": "VuaC...", "api_key": "ui2lp...",
#      "encoded": "VnVhQ2ZHY0JDZGJrU..." }        # shown ONCE

Authorization: ApiKey VnVhQ2ZHY0JDZGJrU...

GET /_security/api_key?name=checkout-service-*
DELETE /_security/api_key { "ids": [ "VuaC..." ] }
POST /_security/api_key/_query
{ "query": { "range": { "expiration": { "lte": "now+7d" } } } }
#   ^ keys expiring in the next week. Worth running on a schedule.

# THE SUBSET RULE: a key created by a user can never have more privileges
# than that user. So a key created by `superuser` can do anything, and a key
# created by a narrowly-scoped service account cannot exceed it. Create keys
# from restricted accounts, not from an admin session.

# CROSS-CLUSTER API KEYS are a separate type, for cross-cluster search and
# replication, with their own privilege model.

Transport and authentication realms

elasticsearch.yml
xpack.security.enabled: true

# TRANSPORT TLS — node-to-node. NOT OPTIONAL on a multi-node cluster.
# Without it, anything that can reach the transport port (9300) can join
# the cluster and read everything. Certificate verification is what stops
# an attacker's node from enrolling.
xpack.security.transport.ssl.enabled: true
xpack.security.transport.ssl.verification_mode: full
xpack.security.transport.ssl.keystore.path: certs/node.p12
xpack.security.transport.ssl.truststore.path: certs/node.p12

# HTTP TLS — client-to-cluster
xpack.security.http.ssl.enabled: true
xpack.security.http.ssl.keystore.path: certs/http.p12

# AUTHENTICATION REALMS, checked in order
xpack.security.authc.realms:
  native.native1:      { order: 0 }              # users stored in ES itself
  ldap.ldap1:          { order: 1, url: "ldaps://...", ... }
  saml.saml1:          { order: 2, idp.metadata.path: ..., ... }
  oidc.oidc1:          { order: 3, ... }
  kerberos.krb1:       { order: 4, ... }
  pki.pki1:            { order: 5, ... }
#   native and file are free. LDAP, SAML, OIDC, Kerberos and PKI are paid
#   tiers. Role MAPPING connects external groups to Elasticsearch roles:
POST /_security/role_mapping/ldap-analysts
{ "roles": [ "analyst" ], "enabled": true,
  "rules": { "field": { "groups": "cn=analysts,ou=groups,dc=example,dc=com" } } }

# ANONYMOUS ACCESS — exists, and should not
xpack.security.authc.anonymous.roles: [ ]        # leave empty

# THE SECURE SETTINGS KEYSTORE, for anything secret:
bin/elasticsearch-keystore add s3.client.default.access_key
bin/elasticsearch-keystore add xpack.security.transport.ssl.keystore.secure_password
#   Never put credentials in elasticsearch.yml. It gets committed.

# AUDIT LOGGING — a paid tier, and the thing you will want after an incident
xpack.security.audit.enabled: true
xpack.security.audit.logfile.events.include: [ access_denied, authentication_failed,
                                               run_as_denied, tampered_request ]
Kibana is a second front door

Everything above secures Elasticsearch, and Kibana sits in front of it with its own service account, its own session handling and its own exposure. Three things follow. Kibana's own connection to Elasticsearch must use TLS and a scoped service account, not the elastic superuser — which is what a quickstart configuration will have. Kibana spaces and its own privilege model control what users see inside it, and they are separate from Elasticsearch roles, so a user restricted in Elasticsearch may still see dashboard definitions and saved objects referencing data they cannot read. And a Kibana instance exposed to the internet is an interactive query console pointed at your cluster; if it must be public, put it behind an authenticating proxy and configure server.publicBaseUrl, session timeouts and CSP properly.

The checklist

  • Security enabled, and TLS on both the transport and HTTP layers.
  • The elastic superuser is not used by any application. One scoped account or API key per service.
  • Bind to specific interfaces, never 0.0.0.0 on a reachable network, and firewall 9200 and 9300 to known sources.
  • API keys with expiry for automation, and a scheduled check for keys expiring soon.
  • Narrowest privileges that work — create_doc rather than write, named indices rather than *.
  • No anonymous access, and _has_privileges used in tests to assert what a role cannot do.
  • Secrets in the keystore, not in elasticsearch.yml.
  • Snapshot repositories credentialled separately, and the repository itself access-controlled — a snapshot is a full copy of your data.
  • Audit logging on if your tier allows it, shipped somewhere you can search.
  • Scripting restricted. Painless is sandboxed; inline scripts from user input are still a bad idea.
Test what a role cannot do

Permission bugs are almost always too much access rather than too little, because too little fails loudly in development and too much fails silently forever. POST /_security/_has_privileges answers "can this user do X" as a boolean, which makes it usable in an automated test — and the tests worth writing are the negative ones. Assert that the application's role cannot delete an index, cannot read the logs index, cannot see another tenant's documents, and has no cluster privileges. Those four assertions take ten minutes, run in CI, and catch the class of change where somebody widens a role's index pattern to fix an unrelated problem. Nothing else in the security configuration gives you that kind of regression protection.

The short version

  1. Security is on by default since 8.0, and was an off-by-default paid add-on before 6.8. That history is why so many clusters were public.
  2. Unauthenticated write access is host compromise, not just a data problem.
  3. Transport TLS is not optional on a multi-node cluster — without it, anything reaching port 9300 can join.
  4. API keys, not passwords, for services — scoped to a subset, given an expiry, revoked individually.
  5. Pick the narrowest privilege: create_doc for an append-only shipper, not write.
  6. DLS enforces multi-tenancy in the cluster rather than in your application's WHERE clause. It disables the request cache.
  7. Kibana is a second front door with its own service account, privilege model and exposure.
  8. Write negative permission tests with _has_privileges. Too much access fails silently.
