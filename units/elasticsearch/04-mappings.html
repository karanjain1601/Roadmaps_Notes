Mappings and field types

Elasticsearch will happily accept a document it has never seen and invent a schema for it. That is a wonderful feature for the first afternoon and the source of a specific set of production problems from the second week onwards.

THE SINGLE MOST CONSEQUENTIAL RULE: every string becomes text AND keyword.
That doubles the index size for every string field and is why dynamic
mapping is so expensive at scale — you are paying to make every log message
aggregatable, including the ones nobody will ever group by.

A MAPPING IS ALMOST IMMUTABLE. You can ADD a new field to an existing
mapping. You cannot change an existing field's type, its analyzer, or
whether it is indexed. The reason is physical: the terms are already on
disk in the old form, and changing the definition would make the index
disagree with itself.

  PUT /orders/_mapping
  { "properties": { "discount_code": { "type": "keyword" } } }   # fine

  PUT /orders/_mapping
  { "properties": { "total": { "type": "double" } } }            # rejected
  # "mapper [total] cannot be changed from type [long] to [double]"

Changing a field type means creating a new index and reindexing (chapter 6).
On a large index that is a project, which is why the first document you send
matters more than it looks like it should.
The first document defines the index

Whichever document happens to arrive first sets the type of every field in it, permanently. If your test data had "quantity": 1 the field is a long, and the production document with "quantity": 1.5 will be rejected — or worse, silently truncated depending on your settings. If a field was empty in the first batch and a string in the second, its type is whatever the second batch happened to contain. The fix is to define the mapping before any data arrives, via an explicit index creation or an index template. This is not a nicety for later; it is the difference between a schema you chose and a schema that was chosen by whatever your ingest pipeline emitted on a Tuesday.

an explicit mapping, with the decisions visible
PUT /orders
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
  },
  "mappings": {
    "dynamic": "strict",              # reject unknown fields — see below
    "properties": {

      "order_id":  { "type": "keyword" },
      "status":    { "type": "keyword" },

      "customer_note": {              # prose, searched AND faceted
        "type": "text",
        "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } }
      },

      "total": {                      # money: never a float
        "type": "scaled_float",
        "scaling_factor": 100
      },

      "quantity": { "type": "integer" },
      "placed_at": {
        "type": "date",
        "format": "strict_date_optional_time||epoch_millis"
      },

      "internal_ref": {               # stored and returned, never searched
        "type": "keyword",
        "index": false
      },

      "tags": { "type": "keyword" },  # arrays need no special declaration

      "customer": {                   # an object, single-valued: fine
        "properties": {
          "id":    { "type": "keyword" },
          "email": { "type": "keyword" },
          "name":  { "type": "text" }
        }
      }
    }
  }
}

# FOUR SETTINGS THAT SAVE REAL SPACE, per field:
#   "index": false          not searchable. Still in _source and returned
#   "doc_values": false     not sortable/aggregatable. Saves the columnar copy
#   "norms": false          drops length normalisation — fine for keyword-like
#                           text you match but do not need scored well
#   "ignore_above": 256     do not index keyword values longer than this
#
# On a large log index, turning off doc_values for fields you never aggregate
# and norms for fields you never score can cut the index size substantially.
# Check with GET /index/_disk_usage?run_expensive_tasks=true first.

Controlling dynamic behaviour

four settings, and dynamic templates
"dynamic": true        # DEFAULT. Add new fields to the mapping automatically
"dynamic": "runtime"   # add them as RUNTIME fields — queryable, not indexed.
                       # A very good middle ground: nothing is lost, nothing
                       # is silently indexed, and you can promote a field to
                       # a real one later if it earns it
"dynamic": false       # ignore new fields. They stay in _source and are
                       # returned, but are NOT searchable. Silent, and the
                       # cause of "the data is there but I cannot find it"
"dynamic": "strict"    # REJECT the document with an error

# For anything with a known shape, "strict" is the right choice. A rejected
# document is a bug report; a silently unindexed one is a mystery in three
# months. For log-shaped data where fields genuinely vary, "runtime" is the
# modern answer.

# DYNAMIC TEMPLATES apply rules to fields you have not seen yet, matched by
# name or by inferred type:

PUT /logs
{ "mappings": {
    "dynamic_templates": [

      { "ids_as_keyword": {
          "match": "*_id",
          "mapping": { "type": "keyword" } } },

      { "strings_keyword_only": {
          "match_mapping_type": "string",
          "mapping": { "type": "keyword", "ignore_above": 1024 } } },

      { "metrics_as_float": {
          "path_match": "metrics.*",
          "mapping": { "type": "float", "index": false } } }
    ]
}}

# That second rule alone — every string becomes keyword-only instead of
# text-plus-keyword — is the standard fix for log indices. Log messages are
# filtered and aggregated far more often than they are searched as prose, and
# you have just halved the string overhead across the whole index.

# RUNTIME FIELDS deserve their own mention. They are computed at query time
# from _source or other fields:
PUT /logs/_mapping
{ "runtime": {
    "response_bucket": {
      "type": "keyword",
      "script": "emit(doc['status'].value < 400 ? 'ok' : 'error')"
    }
}}
# No reindex, no disk cost, slower to query. Perfect for a field you need
# occasionally, or for fixing a mapping mistake without rebuilding the index.
Mapping explosion

Every field in every index is held in the cluster state, which lives in memory on every node and is propagated to all of them on every change. A few hundred fields is nothing. Tens of thousands of fields makes cluster-state updates slow, node joins slow, and the master unstable — and the cluster degrades in ways that look like a performance problem rather than a modelling one. The classic cause is dynamic mapping over user-controlled keys: a document with {"attributes": {"colour": "red"}} creates attributes.colour, and if the key is whatever the customer typed, each new key is a permanent new field. The index.mapping.total_fields.limit setting defaults to 1000 and exists to stop this. Raising it because you hit it is almost always the wrong response; the right one is a flattened field.

flattened — one field for an entire unpredictable object
PUT /events
{ "mappings": { "properties": {
    "custom_attributes": { "type": "flattened" }
}}}

PUT /events/_doc/1
{ "custom_attributes": {
    "campaign": "spring-sale",
    "variant":  "b",
    "referrer": "newsletter",
    "anything_at_all": "the customer decided this key name"
}}

# ONE field in the mapping, regardless of how many keys arrive. Every leaf
# value is indexed as a keyword.

GET /events/_search
{ "query": { "term": { "custom_attributes.campaign": "spring-sale" } } }
{ "query": { "term": { "custom_attributes": "spring-sale" } } }   # any key

# WHAT YOU GIVE UP:
#   * everything is a keyword. No numbers, no dates, no full-text
#   * no per-field analysis, no per-field boosting
#   * limited aggregation support compared with real fields
#
# WHAT YOU GET: an index whose field count is bounded by your schema rather
# than by your users' imagination. For the "arbitrary tags" or "custom
# properties" problem this is the correct answer, and it is under-used
# because people do not know the type exists.

# TO CHANGE A TYPE, reindex into a correctly-mapped index and swap an alias:
PUT /orders-v2  { "mappings": { ... } }

POST /_reindex
{ "source": { "index": "orders" },
  "dest":   { "index": "orders-v2" } }

POST /_aliases
{ "actions": [
    { "remove": { "index": "orders",    "alias": "orders-live" } },
    { "add":    { "index": "orders-v2", "alias": "orders-live" } } ]}

# ALWAYS READ AND WRITE THROUGH AN ALIAS, from day one. It costs nothing and
# it turns "we need to change the mapping" from an outage into an atomic
# swap. An application that names a concrete index cannot be reindexed
# without a deployment; one that names an alias can be reindexed at 3pm on a
# Tuesday. This is the single cheapest piece of Elasticsearch hygiene there
# is, and the one most often skipped.
Index templates make the mapping arrive before the data

For anything created automatically — logs, metrics, events, any time-series index named by date — there is no moment at which you could apply a mapping by hand, because the index springs into existence the instant a document arrives. An index template binds settings, mappings and aliases to a name pattern in advance: PUT /_index_template/logs with "index_patterns": ["logs-*"], and every index matching that pattern is born correct. Component templates let you compose them from reusable pieces, so a shared set of standard fields can be defined once and included everywhere. Without this, every new index gets full dynamic mapping and you find out a month later.

The short version

  1. The first document defines the index. Field types are set by whatever arrived first and mostly cannot be changed.
  2. Every string becomes text plus keyword under dynamic mapping, which doubles the cost of every string field.
  3. Numbers are always long or float. Declaring smaller types is real disk savings.
  4. Use scaled_float for money, never double.
  5. "dynamic": "strict" for known shapes, "runtime" for varying ones. false silently loses searchability.
  6. Dynamic templates fix the string default — keyword-only for log data is the standard win.
  7. flattened is the answer to user-controlled keys, and mapping explosion is what happens without it.
  8. Read and write through an alias from day one. It turns a reindex from an outage into a swap.
