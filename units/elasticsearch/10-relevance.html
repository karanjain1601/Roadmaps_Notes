Relevance and BM25

The number in _score is not arbitrary and it is not comparable between queries. It comes from three quantities — how often the term appears, how rare the term is, and how long the field is — combined by a formula worth understanding, because tuning relevance without it is guesswork.

bm25 scoring boosting explain

The formula

BM25, for one term in one field
                            tf × (k1 + 1)
  score = IDF  ×  ───────────────────────────────────
                  tf + k1 × (1 − b + b × dl / avgdl)

  where

    tf     term frequency — occurrences of the term IN THIS FIELD
    dl     the length of this field, in terms
    avgdl  the average field length across the index
    IDF    inverse document frequency = ln(1 + (N − n + 0.5) / (n + 0.5))
             N = documents in the index
             n = documents containing the term
    k1     1.2  — how fast term frequency saturates
    b      0.75 — how much field length matters

  A multi-term query sums the per-term scores. A multi-field query combines
  them with dis_max or a sum depending on type (chapter 7).

THREE INTUITIONS, and they are the whole thing:

  MORE OCCURRENCES IS BETTER, WITH DIMINISHING RETURNS. The tf term
  saturates: going from 1 to 2 occurrences helps a lot, 20 to 21 barely at
  all. That is the "25" refinement over classic TF-IDF, where frequency
  contributed linearly and a page repeating a word 400 times won.

  RARE TERMS MATTER MORE. IDF rises as fewer documents contain the term. A
  match on "quixotic" says far more than a match on "the", and this is
  computed from your actual corpus rather than a stopword list.

  SHORTER FIELDS MATCHING IS STRONGER. A term in a 4-word title is a bigger
  fraction of that field than the same term in a 4,000-word body. The b
  parameter controls how hard this applies.

Scores are not comparable across queries, and not a percentage

_score is meaningful only as an ordering within one result set. It has no upper bound, no unit and no absolute interpretation — a score of 8.4 for one query and 8.4 for another say nothing about each other, because IDF depends on the corpus and the number of clauses affects the sum. That has two practical consequences. Never threshold on a raw score (min_score: 5) and expect it to mean the same thing next month, because as the index grows the IDF values shift. And never show it to users as a relevance percentage — dividing by max_score gives you a number where the top hit is always 100%, whether it was a perfect match or the least-bad of a bad set.

IDF is computed per shard, so scores differ across shards

Each shard computes N and n from its own documents, because gathering global statistics before scoring would mean an extra round trip on every search. With a large, evenly distributed index the per-shard values approximate the global ones closely enough that nobody notices. With a small index, or unevenly distributed data — a shard where a term is rare and another where it is common — the same document can score differently depending on which shard it landed on, and near-identical documents can rank in a surprising order. Two remedies: ?search_type=dfs_query_then_fetch gathers global term statistics first at the cost of a round trip, and using fewer shards makes the problem smaller. It is also the reason relevance testing on a three-document index produces nonsense.

The levers, weakest to strongest

field boosts, then query boosts, then functions
# 1. FIELD BOOSTS — a multiplier on that field's contribution
{ "multi_match": { "query": "sony", "fields": [ "name^3", "brand^2", "body" ] } }

# 2. CLAUSE BOOSTS — the same idea on a whole clause
{ "bool": { "should": [
    { "match": { "name":  { "query": "sony", "boost": 3 } } },
    { "match": { "body":  { "query": "sony", "boost": 1 } } } ]}}

# Both are just numbers multiplied into the score, which means their effect
# depends on what the scores already are. A boost of 3 on a field whose
# scores are around 0.5 is worth less than a boost of 1.2 on a field whose
# scores are around 8. This is why boost tuning feels unscientific — it is
# arithmetic on quantities you have not looked at. Look at them first with
# _explain.

# 3. FUNCTION_SCORE — modify the score with a function of field values
{ "function_score": {
    "query": { "match": { "name": "headphones" } },
    "functions": [
      { "field_value_factor": {
          "field": "sales_rank_inverse",
          "modifier": "log1p",              # tame the distribution
          "factor": 1.2,
          "missing": 1 } },
      { "gauss": {                          # decay by recency
          "released": { "origin": "now", "scale": "180d", "decay": 0.5 } } },
      { "filter": { "term": { "featured": true } }, "weight": 1.5 }
    ],
    "score_mode": "sum",                    # combine the functions
    "boost_mode": "multiply",               # combine with the query score
    "max_boost": 5
}}

#   score_mode  multiply | sum | avg | first | max | min
#   boost_mode  multiply | replace | sum | avg | max | min
#
#   DECAY FUNCTIONS: gauss, exp, linear. Each takes origin, scale, offset,
#   decay — and they work on dates, numbers and geo_points, which makes them
#   the right tool for "nearer is better" and "newer is better".

# 4. DISTANCE FEATURE — cheaper than function_score for the common cases,
#    and it can be used as a should clause so it only boosts:
{ "bool": { "should": [
    { "distance_feature": {
        "field": "released", "pivot": "180d", "origin": "now" } } ]}}
# Designed to be efficient enough to use on every query, unlike
# function_score which scores every matching document.

# 5. RESCORE — re-rank only the top N with an expensive query
{ "query": { "match": { "name": "wireless headphones" } },
  "rescore": {
    "window_size": 100,
    "query": {
      "rescore_query": { "match_phrase": { "name": { "query": "wireless headphones", "slop": 2 } } },
      "query_weight": 0.7, "rescore_query_weight": 1.3 }
}}
# THE MOST UNDERUSED FEATURE HERE. A phrase query over the whole index is
# expensive; over the top 100 candidates it is free. This is how you get
# "documents where the terms are adjacent rank higher" without paying for
# positional matching across millions of documents.

Precision and recall

Recall too low — results are missing

  • Loosen minimum_should_match, or drop "operator": "and"
  • Add fuzziness: "AUTO" for typos
  • Add a stemming analyzer, or the right language one (chapter 3)
  • Add synonyms for vocabulary the corpus does not use
  • Search more fields with multi_match
  • Check for the term-on-text bug first (chapter 8)

Precision too low — results are junk

  • Tighten minimum_should_match to "75%" or higher
  • Move exact conditions into filter (chapter 7)
  • Use match_phrase, or rescore with one
  • Reduce over-aggressive stemming or synonyms
  • Boost the fields that indicate real relevance
  • Check that should clauses are not letting junk qualify
Tune against a judgement list, not against your own intuition

Relevance tuning by trying a query, looking at the results and adjusting a boost is a process that converges on the queries you happen to try. It very reliably makes some other query worse without telling you. The alternative is a ranking evaluation set: a list of queries with the documents that should be in their top results, from analytics, from support tickets, or from asking colleagues. Elasticsearch has an API for exactly this — POST /products/_rank_eval with your queries and their expected hits, returning precision, recall, mean reciprocal rank or NDCG. Run it before and after every change. It turns "this feels better" into a number, and it is the difference between tuning relevance and fiddling with it.

        { "_index": "products", "_id": "1204", "rating": 2 },

# -> { "metric_score": 0.812, "details": { per-query breakdown } }

#   precision_at_k         fraction of the top k that are relevant
#   recall_at_k            fraction of relevant documents in the top k
#   mean_reciprocal_rank   how high the FIRST relevant result appears
#   dcg (normalize: true)  NDCG — graded relevance, position-discounted.
#                          The right default when your ratings have degrees

#
# THIRTY QUERIES WITH RATINGS is enough to catch most regressions and is a
# couple of hours of work. It is the highest-value hour anyone spends on
# search quality, and it is skipped almost universally.
Tuning BM25 itself is almost never the answer

k1 and b are configurable per field via a custom similarity, and the defaults of 1.2 and 0.75 are the product of a great deal of information-retrieval research on general text. The honest guidance is to leave them alone. Two exceptions worth knowing: for a field where length carries no information — a tag list, a set of identifiers, a product code — b: 0 disables length normalisation and is a genuine improvement, since a document with four tags is not more relevant than one with eight. And for short, uniform fields where repetition is meaningless, k1: 0 makes term frequency irrelevant so any occurrence counts once. Both are narrow, structural cases. If your ranking problem is "the wrong documents are winning", the answer is in the query, the mapping or the analysis — not in these two constants.

The short version

  1. BM25 combines term frequency, inverse document frequency and field length with two constants, k1 and b.
  2. Term frequency saturates — that is the improvement over TF-IDF, where a page repeating a word 400 times won.
  3. Scores are not comparable across queries and are not percentages. Do not threshold on them; do not show them.
  4. IDF is per shard, so small or skewed indices score oddly. That is why testing relevance on three documents is meaningless.
  5. _explain answers "why", and the differing leaf between two documents is almost always dl or n.
  6. Boosts are multipliers on numbers you have not looked at. Look at them with _explain before tuning.
  7. rescore is the most underused feature here — an expensive phrase query over 100 candidates instead of millions.
  8. Tune against a rank_eval judgement list. Thirty rated queries catches most regressions.
