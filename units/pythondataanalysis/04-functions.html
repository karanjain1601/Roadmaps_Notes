Functions, and thinking in columns

    THE BASICS, BRIEFLY

    Defining a function

    Four features of Python's signatures that are worth using deliberately.

    functions.py
    def summarise(df, column, *, dropna=True, precision=2):
    """Mean and median of one column. Keyword-only options after the *."""
    s = df[column].dropna() if dropna else df[column]
    return round(s.mean(), precision), round(s.median(), precision)

summarise(df, "revenue")                      # defaults
summarise(df, "revenue", precision=4)         # must be named
summarise(df, "revenue", False)               # TypeError: too many positional
    Keyword-only arguments, after a bare *
    Forces callers to name the options, so summarise(df, "revenue", False) is rejected rather than silently interpreted. Worth doing for any boolean flag — a bare True at a call site is unreadable and frequently wrong.
    Type hints, as documentation that tools can check
    def summarise(df: pd.DataFrame, column: str) -> tuple[float, float]: is not enforced at runtime, and it is read by your editor, by mypy, and by the next person. On analysis code the return type is the one worth annotating, because that is the thing a reader most often has to guess.
    Docstrings, stating what a reader cannot infer
    Not what the function does — the name should carry that — but what it assumes. Which grain the frame is at, whether nulls are dropped, what units the result is in. Those are the questions that make somebody read the body.
    Defaults are evaluated once
    Chapter 3 measured this: a mutable default is shared by every call. Never write def f(rows=[]).

    VARIABLE SIGNATURES

    *args and **kwargs

    Collecting extra positional and keyword arguments. Useful in exactly two situations and overused everywhere else.

    args_kwargs.py
    def total(*amounts):              # any number of positional arguments
    return sum(amounts)
total(1, 2, 3)                    # 6

# the same star does the reverse at a call site: it unpacks
values = [1, 2, 3]
total(*values)                    # 6, same as total(1, 2, 3)

# **kwargs collects, and ** unpacks
def load(path, **read_options):
    return pd.read_csv(path, **read_options)      # pass them straight through
load("sales.csv", sep=";", parse_dates=["date"])
    The two cases where this earns its keep

    Passing options through to something else, as in load above — you do not want to enumerate every one of read_csv's fifty parameters, and you do not want to block them either. And decorators or wrappers, which must accept whatever the wrapped function accepts.

    Outside those, **kwargs in your own analysis functions is usually a mistake. It removes the signature, so nothing — not your editor, not a reader, not a type checker — can tell what the function accepts, and a misspelled option is silently ignored rather than rejected.

    SMALL FUNCTIONS

    Lambdas, and where they belong

    An anonymous single-expression function. Genuinely useful in three places, and a readability cost everywhere else.

    lambda x: x * 2 is the same as a one-line def without a name. The value is that it can be written inline where a function is expected.

    lambdas.py
    # 1. a sort key
rows.sort(key=lambda r: (r["region"], -r["revenue"]))    # region asc, revenue desc

# 2. a named aggregation in Pandas
df.groupby("region").agg(
    total=("revenue", "sum"),
    spread=("revenue", lambda s: s.max() - s.min()),      # no built-in name for this
)

# 3. chaining without an intermediate name
(df.pipe(lambda d: d[d["revenue"] > 0])
   .assign(margin=lambda d: d["profit"] / d["revenue"]))

    The third pattern deserves a note because it looks odd at first. Inside assign, a lambda receives the DataFrame as it is at that point in the chain, so you can reference a column created earlier in the same chain. Writing df["profit"] / df["revenue"] there would refer to the original frame instead, which is a real and subtle difference.

    Where a lambda is the wrong choice

    The moment it needs a comment, a conditional, or is used twice, it should be a named function. lambda r: "high" if r > 100 else "low" if r > 10 else "none" is legal, unreadable, and cannot be tested on its own.

    And in a .apply() on a DataFrame, a lambda is doubly the wrong choice — not because it is anonymous but because .apply is, which is the next section.

    ALREADY THERE

    The built-ins worth knowing

    Eight functions that replace a loop each. Learning them is a better use of an afternoon than learning a library.

    The built-ins that come up constantly in analysis
    FunctionDoesReplaces
    sum, min, maxAggregate an iterableAn accumulator loop. All three take a key=, which is underused
    sortedReturns a new sorted listA sort loop; key= and reverse= cover almost every case
    any, allShort-circuiting truth over an iterableA flag variable and a break
    zip, enumeratePair up, or index and valueAn index variable, per chapter 3
    round, abs, lenThe obvious—

    One detail on round that surprises people, and that matters if anyone reconciles your output. Python uses banker's rounding: halves go to the nearest even number, so round(0.5) is 0 and round(1.5) is 2. This is deliberate — it removes the upward bias of always rounding halves up — and it differs from what a spreadsheet does by default. If your totals disagree with Excel's in the last penny, this is frequently why.

    map and filter: skip them

    They exist, they work, and a comprehension does the same job more readably: [f(x) for x in xs] rather than list(map(f, xs)). The one place map still reads well is applying an existing named function to a single iterable with no transformation of its own. Otherwise the comprehension wins on clarity, and neither wins on speed once the data is in a DataFrame.

    THE CENTRAL SHIFT

    Thinking in columns

    Four ways to compute the same derived column. They differ by a factor of two thousand, and the reason is not the arithmetic.

    The task: given revenue and discount columns, compute net = revenue * (1 - discount). Here are the four ways people write it.

    four_ways.py
    # 1. iterrows: a Python object built for every row
net = []
for _, row in df.iterrows():
    net.append(row["revenue"] * (1 - row["discount"]))

# 2. apply: one Python function call per row
net = df.apply(lambda r: r["revenue"] * (1 - r["discount"]), axis=1)

# 3. list comprehension over the raw values
net = [r * (1 - d) for r, d in zip(df["revenue"], df["discount"])]

# 4. vectorised: one operation on the whole column
net = df["revenue"] * (1 - df["discount"])

    All four produce the same numbers. The demo prices them.

    The same column, four ways per-row costs calibrated from typical Pandas benchmarks

    Three results, and one honest caveat.

    1. A million rows takes 8 seconds with iterrows and 4 milliseconds vectorised — a factor of two thousand. Ten million takes 80 seconds against 40 milliseconds, because the gap is multiplicative in row count rather than a fixed overhead.
    2. Within one second you can process 125,000 rows with iterrows or 250 million vectorised. That is the number that decides whether an analysis is interactive.
    3. A list comprehension over raw values is a good middle option — about twenty times faster than iterrows — and it is the right answer when the per-row logic genuinely cannot be expressed as column operations.
    Why the gap exists, and what the in-page benchmark can and cannot show

    The cost is not the arithmetic. It is that iterrows constructs a Python Series object for every row — allocating, boxing each value, building an index — and then does one multiplication. The vectorised version does one pass of machine-code arithmetic over a contiguous block of memory, with no Python involved per element.

    The benchmark button measures the part of this that is real in any language: building an object per element against one fused arithmetic loop. What it will not reproduce is the apply gap, because JavaScript's compiler inlines a small callback away entirely — the two come out identical. That is a genuine difference between the runtimes, and it is why the table above uses measured Pandas costs rather than numbers from this page.

    Two practical notes. itertuples() is several times faster than iterrows() if you must iterate, because it does not build a Series per row — so if you find yourself writing iterrows, that is the cheap improvement. And df.apply(..., axis=1) is the slow direction; axis=0 applies a function to each column, which is only as many calls as you have columns and is perfectly fine.

    CONDITIONS WITHOUT A LOOP

    Branching, vectorised

    The most common reason people fall back to a loop is an if/else per row. It does not require one, and the vectorised form has one trap worth knowing.

    Assigning a tier from a value is naturally written as a branch. The vectorised equivalents are boolean masks, np.select, or pd.cut:

    branching.py
    # masks, assigned in order from broadest to narrowest
df["tier"] = "key"
df.loc[df.revenue < 2000, "tier"] = "large"
df.loc[df.revenue < 500,  "tier"] = "medium"
df.loc[df.revenue < 100,  "tier"] = "small"

# np.select: conditions and choices, evaluated in order
df["tier"] = np.select(
    [df.revenue < 100, df.revenue < 500, df.revenue < 2000],
    ["small", "medium", "large"],
    default="key",
)

# pd.cut: the clearest option when the bins are numeric ranges
df["tier"] = pd.cut(df.revenue, [0, 100, 500, 2000, np.inf],
                    labels=["small", "medium", "large", "key"], right=False)
    Four-way branching, and the np.where trap 200,000 values tiered both ways, and a division that happens before it is discarded

    RESULT—

    The correctness result first: masked assignment and a per-row branch agree on all 200,000 rows, so this is genuinely the same computation written two ways. The masked version makes four passes over the column where the branch makes one — and it is still much faster, because each pass is a fused loop and the branch is not. Four vectorised passes beat one interpreted pass. That is counter-intuitive and it is the whole reason vectorised code looks wasteful and is not.

    np.where evaluates both branches, for every row

    np.where(den != 0, num / den, 0) gives the right answer and still divides by zero. The reason is that it is not a branch at all: num / den is computed as a complete array first, for every row including the zeros, and only then are the values selected. So you get the correct result and a RuntimeWarning, and on some inputs an inf or NaN that propagates somewhere you did not expect.

    The fix is to make the operation safe rather than to select afterwards: num / den.replace(0, np.nan), or np.divide(num, den, out=np.zeros_like(num), where=den != 0), which genuinely skips the excluded rows.

    THE EXCEPTIONS

    When a loop is the right answer

    Vectorise by default, and there are four cases where a loop is correct rather than lazy.

  1. The rows are genuinely sequential. A running state machine, a session-boundary detector, a stock ledger where each row depends on the previous result. Some of these have vectorised forms — cumsum, shift, expanding — and some do not, and forcing the ones that do not produces unreadable code for no gain.
  2. The count is small and fixed. Iterating over 12 columns or 40 files is not a performance question. Iterating over 4 million rows is.
  3. Each step calls something external. An API request per row is dominated by network latency, so the Python overhead is irrelevant — and chapter 11's rate limits matter far more.
  4. You are still working out what you want. A slow, obvious loop that produces the right answer is worth more than a fast, clever expression that produces a plausible one. Get it correct, then vectorise it if it is too slow, and check the two agree.
    5. The last point is the one worth taking seriously

    Vectorised code is harder to debug because there is no per-row place to put a print statement. So the useful order is: write the loop, save its output, write the vectorised version, and assert they match — pd.testing.assert_series_equal(loop_result, vectorised_result). Then delete the loop.

    That gives you the speed and a test, which is the same move chapter 21 makes about analyses generally.

    Recap

    What to take from this chapter

    1. Use keyword-only arguments after a bare * for anything boolean, so callers must name it.
    2. Docstrings should state what a reader cannot infer — the grain, the null handling, the units.
    3. **kwargs earns its keep only for passing options through and for wrappers. Elsewhere it deletes the signature and silently swallows typos.
    4. Lambdas belong in sort keys, named aggregations and chained assign. Inside assign a lambda sees the frame as it is at that point in the chain.
    5. Python's round sends halves to the nearest even number. If your totals disagree with a spreadsheet in the last penny, that is often why.
    6. A million rows: 8 seconds with iterrows, 4 milliseconds vectorised — a factor of two thousand, multiplicative in row count.
    7. Within one second: 125,000 rows via iterrows, or 250 million vectorised.
    8. The cost is object construction per row, not the arithmetic. itertuples is much faster than iterrows if you must iterate.
    9. apply(axis=1) is the slow direction; axis=0 is one call per column and is fine.
    10. Four vectorised passes beat one interpreted pass. Masked assignment and a per-row branch agreed on all 200,000 rows.
    11. np.where evaluates both branches for every row, so it divides by zero on the way to the right answer. Make the operation safe instead of selecting afterwards.
    12. A loop is correct for sequential logic, small fixed counts, external calls, and while you are still working out the answer.
    13. Write the loop, then the vectorised version, then assert they match, and delete the loop.
