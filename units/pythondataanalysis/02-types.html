CHAPTER 02

Types, operators and numeric surprises

A tour of Python's types would be dull and you can read one anywhere. This chapter covers instead the specific places where an analyst's arithmetic is not what it appears to be: floats that do not sum to what you asked for, integers that stop being exact, and a revenue column read as text whose top ten shares four entries with the truth.

    THE FOUR THAT MATTER

    The types you will actually meet

    Python has many types. Four of them carry almost all analytical data, and each has one property worth knowing.

    The four scalar types, and the thing to remember about each
    TypeExampleThe property that matters
    int42Unbounded in pure Python — but not in NumPy or Pandas, where it is a fixed-width machine integer that overflows
    float3.14A 64-bit binary approximation. Most decimal values cannot be represented exactly
    str"1000"Compares and sorts character by character, which is the subject of the second demo
    boolTrueA subclass of int, so True + True == 2 — which is genuinely useful for counting
    The bool-is-an-int fact is worth using deliberately

    (df["amount"] > 100).sum() counts the rows over 100, because each True contributes 1. And (df["amount"] > 100).mean() gives the proportion over 100, which is one of the most useful two-character idioms in Pandas. Both work because a boolean is an integer.

    The first row deserves emphasis because it catches people who learned Python before NumPy. A pure Python int grows without limit — 2 ** 200 is fine. A NumPy int64 does not: it wraps around silently at about 9.2 × 1018, and a sum over a large integer column can overflow into a negative number with no warning. If you are summing large integers, cast to float or to Python objects first.

    THE ONE EVERYONE MEETS

    Floating point

    A float is a binary fraction. One tenth is not a binary fraction, so it is stored as the nearest available value, and the error compounds.

    The demonstration is famous and worth doing once properly: 0.1 + 0.2 is 0.30000000000000004, so 0.1 + 0.2 == 0.3 is False. This is not a Python bug — it is IEEE 754 double-precision arithmetic, and every language using it gives the same answer, including the one this page is written in.

    What matters for analysis is not the single addition but what happens when you do it a million times.

    Accumulated error, and why summation order changes the total real IEEE 754 arithmetic, computed in the page
    NAIVE SUM0
    ERROR0against the exact value
    ORDER CHANGES THE TOTAL BY0same values, different order
    THIS ORDER0

    Three results, and the third is the one that changes how you write code.

    1. Error grows with the number of additions. Ten additions of 0.1 are off by about 10-14 pennies; a million are off by 10-4. Still tiny, and worth knowing the direction.
    2. Addition is not associative. The same 200,000 values summed smallest-first and largest-first give different totals. Not different roundings of one total — genuinely different numbers, because precision is lost when a small value is added to a large running sum.
    3. Compensated summation fixes it, and you already have it. math.fsum in the standard library, and NumPy's pairwise summation in .sum(), are both far more accurate than a Python loop. Which is one more reason not to write the loop.
    The honest scope of this problem

    For most analysis, float error does not matter: an error in the fourteenth decimal place will not change a conclusion about revenue trends. Being alarmed about it is as unhelpful as being unaware of it.

    It matters in exactly four situations. Equality comparisons — never write x == 0.3; use np.isclose or compare within a tolerance. Money, where a reconciliation must balance to the penny, so work in integer pennies or use decimal.Decimal. Iterative algorithms, where error feeds back into the next step. And subtracting two close large numbers, which can destroy every significant digit at once.

    floats.py
    0.1 + 0.2 == 0.3                 # False
np.isclose(0.1 + 0.2, 0.3)       # True  <- compare like this

sum([0.1] * 1_000_000)           # 100000.00000133288
math.fsum([0.1] * 1_000_000)     # 100000.0            <- exact
np.array([0.1] * 1_000_000).sum()# 100000.00000000001  <- pairwise, close

# money: work in integer pennies, or be explicit
from decimal import Decimal
Decimal("0.1") + Decimal("0.2") == Decimal("0.3")   # True

    THE LIMIT PEOPLE FORGET

    When an integer stops being exact

    A float can hold integers exactly, up to a point. Past that point it silently cannot, and the failure looks like nothing.

    A 64-bit float represents integers exactly up to 253 − 1, which is 9,007,199,254,740,991. Beyond that, consecutive integers are no longer distinguishable, so:

    big_ints.py
    9007199254740992 + 1 == 9007199254740992     # True, as a float
2**53 + 1                                     # fine as a pure Python int

# but read a big ID column and Pandas may give you float64:
pd.read_csv("events.csv")["user_id"].dtype    # float64 if any value is missing
# -> two different users can collapse to the same ID
    Where this actually bites: identifier columns

    Snowflake IDs, some database bigints and many timestamps in nanoseconds exceed 253. If a column of them is read as float — which Pandas will do automatically if a single value is missing, since the classic integer dtype cannot hold NaN — distinct identifiers can become equal, and a join or a distinct count is then quietly wrong.

    The fix is to read identifiers as strings: pd.read_csv(path, dtype={"user_id": "string"}). You are not doing arithmetic on an ID, so nothing is lost, and chapter 9 makes the general case for declaring dtypes rather than letting them be guessed.

    Two operators worth being precise about while we are here. / is always true division and always returns a float, so 4 / 2 is 2.0. // is floor division, and it floors toward negative infinity: -7 // 2 is -4, not -3. And % follows the same convention, so -7 % 2 is 1. If you are bucketing signed values, that is the behaviour you get.

    THE EXPENSIVE ONE

    A numeric column read as text

    Strings compare character by character, so "9" sorts above "1000". When the column is revenue, the top-ten list is wrong and looks fine.

    This is the most common serious type error in practice, because it arrives by accident: a CSV column containing "1,200" or "N/A" or a currency symbol cannot be parsed as a number, so the whole column becomes text. Nothing errors. Every operation still works — it just works on strings.

    The same column sorted as numbers and as text 400 revenue values spanning four orders of magnitude
    TOP LIST OVERLAP0
    TRUE MAXIMUM0sorted numerically
    MAXIMUM AS TEXT0what max() returns
    ROWS OUT OF PLACE0

    The small version everybody recognises once they see it:

    text_numbers.py
    sorted([9, 100, 25, 1000, 7])                  # [7, 9, 25, 100, 1000]
sorted(["9", "100", "25", "1000", "7"])        # ['100', '1000', '25', '7', '9']

max(["9", "100", "25", "1000", "7"])           # '9'   <- not 1000
sum(...)                                        # TypeError, or concatenation

# and the diagnosis, which takes one line
df.dtypes                                       # object where you expected int64
df["revenue"].str.contains(r"[^0-9.]").sum()   # how many values block parsing
    Why max is the sneakiest of these

    A sort that puts 100 before 9 looks obviously wrong the moment you glance at it. max returning '9' does not — it returns a plausible-looking number, of the right kind, in the right units. It is simply the wrong one, and a summary table containing it gives no hint.

    Worse, df.describe() silently omits text columns entirely, so the column you most need to check is the one missing from the summary you would check it with. Look at df.dtypes as a matter of routine, not describe.

    The fix is pd.to_numeric with a deliberate choice about what to do with the values that will not parse:

    fix_numeric.py
    # strip the things that block parsing, then convert
clean = df["revenue"].str.replace(r"[£$,]", "", regex=True).str.strip()
df["revenue"] = pd.to_numeric(clean, errors="coerce")   # unparseable -> NaN

# then look at what you just discarded, rather than assuming it was nothing
print(df["revenue"].isna().sum(), "values could not be parsed")

    errors="coerce" turns the failures into NaN, which is usually right and is only safe if you then look at how many there were. Silently coercing a third of a column to missing and carrying on is how chapter 12's problems begin.

    CONDITIONS

    Truthiness, and where it misfires

    Python treats empty things as false. That is convenient in scripts and dangerous with data.

    0, 0.0, "", [], {} and None are all falsy. So if value: is not a test for whether a value exists — it also fails for a legitimate zero, which in analytical data is a real measurement rather than an absence.

    truthy.py
    discount = 0          # a real value: no discount applied
if discount:          # False! treats a genuine zero as missing
    apply(discount)
if discount is not None:   # what you actually meant
    apply(discount)

# NaN is the opposite trap: it is truthy, and never equal to itself
float("nan") == float("nan")     # False
bool(float("nan"))               # True
pd.isna(float("nan"))            # True   <- the only reliable test

    Two Pandas-specific consequences follow, and both produce errors people find baffling the first time.

    A Series has no single truth value
    if df["x"] > 0: raises the truth value of a Series is ambiguous, because the comparison produced a whole column of booleans and Python does not know which you meant. You wanted .any(), .all(), or — most often — to use the boolean column as a filter: df[df["x"] > 0].
    and and or do not work element-wise
    They evaluate truthiness of whole objects, so combining conditions on columns needs the bitwise operators: df[(df.a > 0) & (df.b < 5)]. The parentheses are not optional — & binds tighter than >, so without them the comparison happens last and the error is obscure.

    CONVERTING

    Casting, and its four failure modes

    Every conversion either succeeds, fails loudly, or fails quietly. Only the last one is a problem.

    What each cast does when the input is not what you expected
    CastOn good inputOn bad inputRisk
    int("42")42ValueErrorNone — fails loudly
    int(3.7)3—Truncates toward zero, does not round
    float("1,200")—ValueErrorNone — fails loudly
    pd.to_numeric(s)numeric SeriesValueError, or NaN with coerceQuiet data loss with coerce
    astype(int)int SeriesError on NaNTruncates floats, overflows silently
    astype(str)text Series—Turns NaN into the string "nan"

    Two rows are worth dwelling on. int(3.7) gives 3 and int(-3.7) gives -3 — it truncates toward zero rather than rounding, so casting a column of averages to integers biases them downward in magnitude. Use round() if you meant to round.

    And astype(str) converting NaN to the four-character string "nan" is a genuinely nasty one, because pd.isna() then reports the column as having no missing values. A count of missing data taken after that cast is wrong, and it will agree with itself every time you check.

    The habit that prevents most of this chapter

    Declare the dtypes you expect when you read the data, rather than inspecting what you were given. pd.read_csv(path, dtype={"user_id": "string", "revenue": "float64"}) fails immediately if revenue contains something unparseable — which is the loud failure you want, arriving at the point where you can still do something about it.

    This is the same argument the Data Engineer unit makes about schema contracts, at the scale of one analysis: a check that runs earlier is worth more than a check that runs at all.

    Recap

    What to take from this chapter

    1. A bool is an int, so (df.x > 100).sum() counts and .mean() gives the proportion.
    2. Pure Python ints are unbounded; NumPy int64 is not, and overflows silently at about 9.2×1018.
    3. 0.1 + 0.2 is 0.30000000000000004. Never compare floats with ==; use np.isclose.
    4. Float error grows with the number of additions — about 10-14 pennies over ten, 10-4 over a million.
    5. Addition is not associative: the same 200,000 values summed smallest-first and largest-first give different totals.
    6. math.fsum and NumPy's .sum() are both more accurate than a Python loop — one more reason not to write the loop.
    7. Float error matters in exactly four places: equality tests, money, iterative algorithms, and subtracting close large numbers.
    8. Floats hold integers exactly only to 253−1. Read identifier columns as strings, since you will never do arithmetic on them.
    9. // floors toward negative infinity, so -7 // 2 is -4.
    10. A numeric column read as text shares only 4 of its top 10 with the truth, and max returns '9' rather than 1000 — a plausible wrong number.
    11. describe() omits text columns, so the column you need to check is missing from the summary you would check it with. Look at dtypes.
    12. A genuine zero is falsy, so if value: is not a test for existence. Use is not None.
    13. NaN is truthy and never equal to itself. pd.isna() is the only reliable test — and astype(str) turns it into "nan", after which nothing looks missing.
    14. Declare dtypes when reading so a bad value fails immediately rather than becoming a silent string column.
