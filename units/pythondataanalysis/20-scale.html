CHAPTER 20

When pandas stops

Tuning buys you roughly one order of magnitude and changing engine buys the next. But the result worth the chapter is this: a filter selecting one row in ten thousand from unsorted Parquet reads every byte of the file, however good the predicate pushdown, and sorting the data is what fixes it.

    Two things that follow, and they are the chapter's practical summary

    Tuning is worth roughly a doubling and costs one line. Declaring dtypes and reading only the columns you need takes pandas from 71 million rows to 149 million on the same machine, which is the difference between "this does not fit" and "this is fine" for a great many datasets.

    Beyond that, the choice is about memory model rather than speed. Chunked pandas, streaming Polars and DuckDB all have bounded peak memory, so their ceiling is disk rather than RAM. They differ in how pleasant they are to write and how fast they run, not in whether they work.

    One caveat on the numbers above: the ×2.5 multiplier for naive pandas is a rule of thumb rather than a law, because it depends on how many intermediate copies your operations create. A single groupby is cheap; a chain of merges and sorts can be far worse. The reliable version is to measure it — df.memory_usage(deep=True).sum() for the frame and the operating system's own figure for the process.

    FIRST

    Making pandas go further

    Five changes, in order of return. Most "we need Spark" conversations end here.

  1. Read fewer columns. usecols= is the largest single win, because it avoids reading rather than shrinking, and chapter 9 measured 40 columns down to 4 as 107 MB against 5,096.
  2. Declare dtypes. int32 instead of int64, category for repetitive text — chapter 5 measured 66× on a low-cardinality column. Watch for the silent overflow that chapter also measured.
  3. Store Parquet, not CSV. Types preserved, 5–10× smaller, and column selection happens in the reader rather than after parsing.
  4. Filter early. If the analysis only needs last quarter, do not load three years. Obvious, and routinely not done because the file is already there.
  5. Aggregate before joining. A groupby that turns 40 million rows into 12,000 before a merge avoids the row explosion of chapter 8 and most of the memory pressure with it.
    6. The question to ask before switching tools

    How much of this data does the answer actually depend on? A monthly revenue summary from three years of transactions needs a few thousand numbers, and moving 60 GB into a distributed engine to produce them is solving the wrong problem — chapter 10 measured that as a 44-million-fold difference in bytes moved.

    The honest ordering is: reduce the data, then reach for a better engine, then reach for more machines. Skipping to the third is common and expensive, and it usually makes the analysis harder to write as well.

    THE MECHANISM

    Lazy evaluation, and what an optimiser can do

    The reason Polars and DuckDB win is not that their loops are faster. It is that they see the whole query before running any of it.

    Pandas is eager: each line executes when written, so pd.read_parquet(path) reads everything and the filter on the next line discards most of it. A lazy engine builds a plan, rewrites it, and then executes — pushing the filter and the column selection down into the file scan.

    lazy.py
    import polars as pl

# eager: reads every column and every row, then throws most of it away
df = pl.read_parquet("events.parquet")
out = df.filter(pl.col("date") >= "2024-07-01") \
        .group_by("region").agg(pl.col("revenue").sum())

# lazy: the filter and the columns are pushed into the scan
out = (pl.scan_parquet("events.parquet")
         .filter(pl.col("date") >= "2024-07-01")
         .group_by("region")
         .agg(pl.col("revenue").sum())
         .collect())                       # nothing runs until here

# and you can read the plan it chose
print(pl.scan_parquet("events.parquet").filter(...).explain())
    Projection pushdown
    The engine works out which columns the query needs and reads only those. With 40 columns and a query using 3, that is most of the win, and it happens without usecols because the optimiser can see what you used.
    Predicate pushdown
    The filter is applied during the scan rather than after, so non-matching rows are never materialised. This is the same argument as chapter 10's, applied to a local file instead of a database.
    Streaming
    Processing in batches so peak memory is bounded regardless of file size. collect(engine="streaming") in Polars; the default in DuckDB. This is chunked pandas with the chunking written for you.
    explain() before optimising anything
    Both engines will show you the plan they chose. If the plan does not mention your filter as part of the scan, the pushdown did not happen — usually because the predicate references a computed column or a Python function the optimiser cannot see through.

    THE LIMIT OF PUSHDOWN

    Why sort order decides whether pruning works

    Predicate pushdown lets the reader skip row groups. Whether there are any it can skip depends entirely on how the data was written.

    A Parquet file is divided into row groups, each with min and max statistics per column. A filter can skip a group whose range excludes the value. That works beautifully when matching rows are clustered together, and not at all when they are scattered.

    On unsorted data the pruning does nothing at any of those selectivities. Even a filter selecting one row in ten thousand reads all four thousand row groups — every byte of the file — because almost every group happens to contain at least one matching row.

    The rule, and it is a formula rather than a heuristic

    A row group is skipped only when it contains no matching row. With R rows per group and selectivity s, the expected number of matches per group is s × R, and pruning starts working only when that falls well below one — so selectivity must be under about 1/R.

    At 100,000 rows per group that threshold is 0.001%. Measured: at 0.01% selectivity (ten matches expected per group) 100% of groups are read; at 0.001% (one match per group) 63.2%; at 0.0001% (a tenth of a match) 9.5%. Analytical filters are almost never that tight.

    Which means sorting is the change that matters, and tuning the row-group size is not. Smaller groups shift the threshold proportionally and cost you metadata overhead and worse compression, so they help a little and never enough.

    layout.py
    # sort by whatever you filter on most, once, when writing
df.sort_values("event_date").to_parquet("events.parquet", row_group_size=100_000)

# or partition, which is pruning by directory and needs no statistics at all
df.to_parquet("events/", partition_cols=["event_date"])
# -> events/event_date=2024-07-01/part-0.parquet

# then a filter on the partition column skips whole directories
pl.scan_parquet("events/**/*.parquet").filter(pl.col("event_date") >= "2024-07-01")

    Partitioning is the stronger version of the same idea: the filter column becomes a directory name, so the reader skips files without opening them and no statistics are involved. The cost is that you must choose the partition column when writing, and choosing one with too many distinct values produces thousands of tiny files — which is its own performance problem, and one the Data Engineer unit treats properly.

    THE OPTIONS

    Polars, DuckDB, Dask, PySpark

    What each is for
    ModelGood atThe catch
    PolarsLazy DataFrame, one machineEverything pandas does, faster, with a stricter APIA new API to learn; a smaller ecosystem
    DuckDBSQL, one machine, out of coreAggregation, joins, querying files in placeYou write SQL; less natural for row-level work
    DaskParallel pandasReusing pandas code across cores or machinesLeaky abstraction; debugging is genuinely harder
    PySparkDistributed clusterTerabytes, and existing Spark infrastructureLarge fixed overhead in setup and in latency
    The order to consider them

    DuckDB if the work is aggregation and joins, which most analytical work is. It queries Parquet and pandas objects in place, needs no server, and SQL is often the clearer language for a complicated group-and-aggregate anyway.

    Polars if the work is DataFrame-shaped and you want to stay in Python expressions. The API is stricter than pandas in ways that prevent several of this unit's bugs outright — there is no ambiguous index, and no chained-assignment problem.

    Dask if you have a large pandas codebase that must keep working. The appeal is not rewriting; the cost is that failures happen inside a scheduler rather than in your code.

    PySpark if you already run Spark, or the data genuinely exceeds one machine's disk. A single machine now holds terabytes of SSD and hundreds of gigabytes of RAM, so that threshold is higher than most people assume.

    One note on Polars that matters for this unit: it has no index. Everything chapter 7 measured about automatic alignment — the fifteen-row result from two ten-row inputs, the twenty rows silently assigned the wrong values — cannot happen, because there is nothing to align on. That is a real reduction in the number of ways to be wrong, and it is worth weighing against the cost of learning a second API.

    IN PRACTICE

    A decision procedure

  6. Compute the raw size first. Rows × columns used × 8 bytes. If that is comfortably inside RAM, the problem is not size and switching tools will not help.
  7. Then apply usecols and dtypes and recompute. This alone doubles what fits, and it is the cheapest step available.
  8. If it still does not fit, ask how much the answer depends on. An aggregate over three years is a small result from a large input, and chapter 10's pushdown argument applies directly.
  9. Then reach for DuckDB or Polars streaming. Both bound peak memory, both run on the machine you have, and both take an afternoon rather than a project.
  10. Only then consider a cluster — and if you do, check the data layout first, because the row-group result above says an unsorted file makes every engine read everything.
    11. The most expensive mistake in this chapter

    Moving to a distributed engine while leaving the data layout alone. A Spark cluster reading unsorted Parquet with a 0.01% filter reads the whole file, exactly as pandas would — it just does it on more machines and bills you for them.

    Sorting the file and adding a partition column is usually a smaller change than adopting a new engine, and it frequently removes the need for one. Layout before infrastructure.

    Recap

    What to take from this chapter

    1. Compute the raw size before choosing a tool: rows × columns used × 8 bytes.
    2. Naive pandas peaks at about 2.5× the raw data, giving 71 million rows in 16 GB with twelve columns in use.
    3. Dtypes and usecols take that to 149 million — a doubling, for one line.
    4. Chunked pandas, streaming Polars and DuckDB all bound peak memory, so their ceiling is disk rather than RAM.
    5. Five cheap wins first: fewer columns, declared dtypes, Parquet, filter early, aggregate before joining.
    6. Ask how much of the data the answer depends on. A monthly summary from three years is a small result from a large input.
    7. Lazy engines win by seeing the whole query, pushing the filter and the column list into the scan.
    8. Run explain(). If the plan does not show your filter in the scan, the pushdown did not happen.
    9. On unsorted Parquet, a 0.01% filter reads all 4,000 row groups — every byte — because nearly every group holds a matching row.
    10. A group is skipped only if it contains no match, so unsorted pruning needs selectivity below about 1/rows-per-group.
    11. Measured: 10 expected matches per group reads 100% of groups; 1 reads 63.2%; 0.1 reads 9.5%.
    12. Sorting is the fix; row-group size is not. Smaller groups shift the threshold and cost metadata and compression.
    13. Partitioning is pruning by directory, and needs no statistics — at the cost of choosing the column when writing.
    14. DuckDB for aggregation and joins, Polars for DataFrame work, Dask to keep pandas code, PySpark if you already run it.
    15. Polars has no index, so chapter 7's alignment and chained-assignment failures cannot occur.
    16. Layout before infrastructure. A cluster reading an unsorted file reads all of it, on more machines.
