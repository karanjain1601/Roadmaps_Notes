CHAPTER 08

Grouping, reshaping and joining

Most analysis is three verbs: group things, change their shape, and join them to something else. The first two are straightforward once you know which function preserves the row count. The third has a failure mode where every individual row is correct and the total is wrong, and it is worth the second half of this chapter.

    THE MODEL

    Split, apply, combine

    Three steps, and naming them makes the API predictable rather than something you look up each time.

    Split the frame into groups by one or more keys. Apply a function to each group. Combine the pieces back into a result. Every groupby operation is those three steps, and the only real question is what the combine step produces.

    groupby.py
    df.groupby("region")["revenue"].sum()          # a Series, one row per region
df.groupby(["region", "month"])["revenue"].sum()   # a MultiIndex Series

# named aggregation: several outputs, explicitly named. The readable form.
df.groupby("region").agg(
    total=("revenue", "sum"),
    orders=("order_id", "count"),
    customers=("customer_id", "nunique"),
    biggest=("revenue", "max"),
)

# as_index=False keeps the keys as columns rather than moving them to the index
df.groupby("region", as_index=False)["revenue"].sum()
    Two defaults that will surprise you once each

    Grouping keys become the index. That is why so much Pandas code ends in .reset_index(). Use as_index=False if you want a flat frame, which for further merging or plotting you usually do.

    Rows with a missing key are dropped. groupby excludes NaN keys by default, so a total over groups can be less than the total over the frame, silently. dropna=False keeps them as their own group, and comparing the two totals is a five-second check worth making when the numbers do not tie out.

    One more distinction: count counts non-missing values, size counts rows. On a column with nulls they differ, and which you want depends on whether you are asking "how many orders" or "how many orders have a recorded value". They are quietly different questions and the two method names do not make that obvious.

    THE DISTINCTION

    agg, transform and filter

    Three combine steps with different output shapes. Choosing wrongly is the most common groupby mistake, and the shapes make it obvious once you look.

    What each returns
    MethodReturnsUse when you want
    aggOne row per groupA summary table
    transformOne row per original rowA group statistic broadcast back onto every row
    filterA subset of the original rowsTo keep or drop whole groups by a condition
    applyWhatever the function returnsNothing else fits. Slow, and the shape is unpredictable
    agg against transform, and the invariant that proves it 5,000 rows across seven groups, with each group's shares checked
    INPUT ROWS0
    OUTPUT ROWS0
    SHAPE—
    INVARIANT—

    The third setting is the reason the distinction matters. Computing each row's share of its group's total needs the group total on every row, which is exactly what transform produces. The check that it is right is a real invariant: every group's shares must sum to exactly 1, and all 5,000 shares must total exactly the number of groups. The demo verifies both.

    transform.py
    # share of the group total — one row per original row
df["share"] = df["revenue"] / df.groupby("region")["revenue"].transform("sum")

# rank within the group, and distance from the group mean
df["rank_in_region"] = df.groupby("region")["revenue"].rank(ascending=False)
df["vs_region_mean"] = df["revenue"] - df.groupby("region")["revenue"].transform("mean")

# filter: keep whole groups, by a property of the group
big_regions = df.groupby("region").filter(lambda g: g["revenue"].sum() > 100_000)

# the alternative to transform is a merge back, which is longer and equivalent
totals = df.groupby("region", as_index=False)["revenue"].sum().rename(
    columns={"revenue": "region_total"})
df = df.merge(totals, on="region", validate="m:1")     # note the validate
    Prefer transform to the merge-back

    Both give the same answer and transform cannot go wrong. The merge version introduces a join, which introduces the cardinality question the second half of this chapter is about — and if the aggregated frame has a duplicate key for any reason, it multiplies your rows.

    Reach for the merge when you need the group statistic in a separate table anyway, and add validate="m:1" when you do.

    CHANGING SHAPE

    Long and wide

    The same data in two layouts. Long is better for storage and computation; wide is better for reading. Converting between them is four functions.

    Long (tidy)

    One row per observation, one column per variable. region, month, revenue. Easy to filter, group and extend — adding a month adds rows, not columns. This is the shape to compute in.

    Wide (pivoted)

    One row per entity, one column per value of some key. region, Jan, Feb, Mar. Easy to read across, and it is what people want in a report. Adding a month changes the schema.

    reshape.py
    # long -> wide
wide = df.pivot(index="region", columns="month", values="revenue")
# pivot() REQUIRES the index/columns pair to be unique. If it is not, use:
wide = df.pivot_table(index="region", columns="month", values="revenue",
                      aggfunc="sum", fill_value=0, margins=True)

# wide -> long
long = wide.reset_index().melt(id_vars="region", var_name="month",
                               value_name="revenue")

# the index-level versions of the same idea
df.stack()      # columns -> an index level (wide to long)
df.unstack()    # an index level -> columns (long to wide)
    pivot raises where pivot_table silently aggregates

    If two rows share the same index-and-column pair, pivot raises a ValueError and pivot_table quietly applies its aggfunc — which defaults to mean, not sum. So the same duplicate that stops one function produces an averaged number from the other, and nothing tells you an aggregation happened.

    Use pivot when you believe the pair is unique, precisely because it will tell you if you are wrong. Use pivot_table when you intend to aggregate, and always pass aggfunc explicitly rather than accepting the default.

    Two smaller notes. pivot_table(margins=True) adds row and column totals, which is what turns a pivot into something you can paste into a report. And after unstacking or a multi-column aggregation you often end up with a MultiIndex on the columns; df.columns = ["_".join(c) for c in df.columns] flattens it, which is nearly always what you want before writing the frame out.

    THE FAILURE WORTH KNOWING

    Merge cardinality

    A join with a duplicated key on the right multiplies rows. Every row remains individually correct, and every total computed afterwards is inflated.

    The intent is ordinary: attach each order's customer region. One row per order in, one row per order out. That holds exactly as long as the customer table has one row per customer — and a customer table can acquire a duplicate from a bad load, a slowly changing dimension, or a filter somebody forgot.

    What a duplicated join key does to a total 1,000 orders merged to a customer table, with revenue summed before and after
    ROWS IN0one per order
    ROWS OUT0
    REVENUE INFLATED0
    validate="m:1"—

    Three results.

    1. A clean many-to-one merge is exactly row-preserving. 1,000 orders in, 1,000 out, revenue total identical to the penny. That is the property you are relying on, usually without stating it.
    2. One duplicated key in five inflates revenue by 20.6%. 1,204 rows out, and a total of 305,864 where the truth is 253,582. No error, no warning, and every individual row shows the correct revenue for a real order.
    3. The inflation is the revenue-weighted multiplicity, not the plain mean. Measured: 1.2062 against a plain mean of 1.2040. So dividing the total by the average duplication rate does not undo it — a fact worth knowing before somebody proposes exactly that as a fix.
    Why this is hard to spot after the fact

    Inspect any row of the merged frame and it is correct: a real order, its real revenue, its real region. The defect exists only in the relationship between rows, so no row-level check finds it — and describe() shows a plausible distribution because the duplicated rows are drawn from the same distribution as the rest.

    The only cheap checks are structural. Compare the row count before and after, which takes one line and catches it immediately. Or let Pandas do it: validate="m:1" raises a MergeError at the join, naming the problem, before any total is computed.

    merge.py
    merged = orders.merge(customers, on="customer_id", how="left",
                      validate="m:1",        # many orders to one customer
                      indicator=True)        # adds a _merge column

merged["_merge"].value_counts()
# both          9_840     matched
# left_only       160     orders whose customer is missing
# right_only        0

# validate accepts: "1:1", "1:m", "m:1", "m:m"
# and the assertion that costs nothing:
assert len(merged) == len(orders), "the join changed the row count"

    THE OTHER PARAMETERS

    How, on, and concat

    Four join types, three ways to specify the key, and the function people reach for when they meant something else.

    Join types, and what each does with unmatched rows
    how=KeepsUnmatched becomeUse for
    "left"All left rowsNaN in the right columnsEnriching a table. The default to reach for
    "inner"Only matchesDropped, silentlyWhen unmatched rows are genuinely irrelevant
    "outer"EverythingNaN on either sideReconciling two sources against each other
    "cross"Every pair—Deliberate cartesian products, such as a date scaffold

    how="inner" deserves a warning of its own: it drops unmatched rows with no indication of how many. An inner join on a key with a formatting mismatch — trailing whitespace, different case, one side zero-padded — can return almost nothing, and it looks exactly like a legitimately small result. Use how="left" with indicator=True while you are still checking, then switch if you are sure.

    concat is not a join

    pd.concat stacks frames — vertically by default, horizontally with axis=1. Vertically it aligns on column names, so a typo in one frame's column silently produces two columns each half full of NaN. Horizontally it aligns on the index, which brings chapter 7's alignment behaviour with all of its consequences.

    Two habits: pass ignore_index=True when stacking frames whose indexes are meaningless, so you do not end up with duplicate labels. And when concatenating horizontally, ask whether you actually wanted a merge on a key — usually you did.

    THE ROUTINE

    Four checks around a join

    Each is one line, and between them they catch every failure in this chapter.

  1. Row count before and after. assert len(merged) == len(left) for a many-to-one join. This catches the row explosion in the second it happens rather than in a total three steps later.
  2. validate= on every merge. It costs nothing, documents your assumption in the code, and turns a silent multiplication into a MergeError naming the duplicated key.
  3. indicator=True while developing. The _merge column tells you how many rows matched. A left join that matched 3% of rows is a key-formatting problem, and without the indicator it looks like a lot of NaN.
  4. Check the key's dtype on both sides. An int64 key will not match a string key containing the same digits, and the result is zero matches with no error — chapter 2's problem arriving at a join.
    5. The same result, from two directions

    The row explosion here is the analyst-side view of what the Data Engineer unit measures as grain fan-out: joining a coarse-grain measure to a finer grain multiplies it by the row count. That unit found the inflation to be the measure-weighted mean line count rather than the plain mean, and this chapter measures the same thing — 1.2062 against 1.2040 — from the other end of the pipeline.

    It is one property of joining on a non-unique key, not two coincidences, and the defence is the same in both places: state the expected cardinality and have something check it.

    Recap

    What to take from this chapter

    1. Every groupby is split, apply, combine. The only real question is what the combine step produces.
    2. Grouping keys become the index unless you pass as_index=False, which is why so much code ends in reset_index().
    3. Rows with a missing key are dropped silently. dropna=False keeps them, and comparing the two totals is a five-second check.
    4. count counts non-missing values; size counts rows. Different questions, similar names.
    5. agg gives one row per group; transform gives one row per original row. Measured: 7 against 5,000.
    6. A share of the group total needs transform, and the invariant proving it is right is that every group's shares sum to exactly 1.
    7. Prefer transform to a merge-back, which introduces a join and therefore a cardinality question.
    8. pivot raises on a duplicate pair; pivot_table silently averages. Pass aggfunc explicitly.
    9. A clean many-to-one merge is exactly row-preserving: 1,000 in, 1,000 out, revenue identical.
    10. One duplicated key in five inflated revenue by 20.6% — 1,204 rows and a total of 305,864 against a true 253,582, with no error.
    11. The inflation is the revenue-weighted multiplicity, not the plain mean (1.2062 against 1.2040), so dividing by the average duplication rate does not undo it.
    12. No row-level check finds it, because every individual row is correct. Only row counts and validate= do.
    13. how="inner" drops unmatched rows silently. Develop with how="left" and indicator=True.
    14. concat aligns on column names vertically and on the index horizontally, and is not a join.
    15. Four checks: row count, validate=, indicator=True, and the key's dtype on both sides.
