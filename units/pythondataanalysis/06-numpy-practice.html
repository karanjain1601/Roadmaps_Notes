    THE VOCABULARY

    Universal functions

    A ufunc is an operation that applies element-wise to a whole array in compiled code. Learning that they exist is most of the benefit.

    Every arithmetic operator on an array is a ufunc, and so is every mathematical function NumPy exposes. The practical point is that if you are about to write a loop to apply a mathematical function, there is a ufunc for it, and it will be hundreds of times faster.

    ufuncs.py
    np.sqrt(a)          np.exp(a)         np.log(a)        np.log1p(a)
np.abs(a)           np.sign(a)        np.round(a, 2)   np.clip(a, 0, 100)
np.maximum(a, b)    np.minimum(a, b)  np.floor(a)      np.ceil(a)

# they broadcast, so this centres and scales in one expression
z = (a - a.mean()) / a.std()

# and they write into an existing array if you ask, avoiding an allocation
np.sqrt(a, out=a)                     # in place
    Three that are easy to miss and solve real problems

    np.clip(a, lo, hi) caps values at both ends in one call, which is the honest way to handle the outliers of chapter 13 when you want to limit their influence rather than remove the rows.

    np.log1p(a) computes log(1 + a) accurately for small a, where np.log(1 + a) loses precision because adding 1 to a tiny number throws away its digits — chapter 2's floating-point problem in a specific form. Its inverse is np.expm1.

    np.maximum(a, b) is element-wise across two arrays; np.max(a) reduces one array to a scalar. The names are close and the operations are unrelated, and this is a common source of a confusing shape error.

    THE RULE

    Aggregating along an axis

    The single most guessed-at parameter in NumPy and Pandas. There is a rule, it is one sentence, and it settles every case.

    The axis you name is the one that disappears. That is all of it. axis=0 on a 2-D array collapses the row dimension, so you get one value per column. axis=1 collapses the column dimension, so you get one value per row.

    Two things the demo establishes.

    1. The shape rule generalises. A (4, 3) array with axis=0 gives shape (3,); with axis=1 it gives (4,). A three-dimensional (2, 4, 3) array with axis=1 gives (2, 3) — remove the named position from the shape tuple and you have the answer.
    2. Both partial sums add to the same grand total. That is the check worth running when you are unsure you picked the right axis: sum the result and compare against aggregating with no axis at all. If they match, the axis collapsed something rather than losing something.
    The mnemonic that survives contact with Pandas

    In Pandas, axis=0 is also called axis="index" and axis=1 is axis="columns", and using the names is worth the extra characters because they say which dimension you are operating along — which is the opposite framing to "which disappears" and is where the confusion originates.

    Both readings are correct and describe the same thing: df.sum(axis="index") walks down the index and returns one value per column. If you find yourself guessing, write axis="columns" instead of axis=1 and the ambiguity goes away.

    keepdims=True is the third control, and it exists for exactly one reason: broadcasting the result back. A (4, 3) array reduced along axis=1 gives shape (4,), which will not broadcast against the original — chapter 5's alignment-from-the-right problem. With keepdims=True you get (4, 1), which does. Turn it on in the demo and watch the shape change.

    REPRODUCIBILITY

    Random numbers, and why seeding is not enough

    np.random.seed(42) is what nearly everyone writes and it does not make an analysis reproducible. The reason is worth understanding rather than working around.

    The legacy functions — np.random.rand, np.random.choice, np.random.shuffle — all draw from one global stream of numbers. Seeding sets that stream's starting point. Every subsequent draw, anywhere in the program, advances it.

    So your results depend not on your seed but on every draw that happened before them, including draws made by libraries you did not write, in code you did not read, that may be added in a version you did not choose.

    The measured result is stark. On a shared global stream, inserting three unrelated draws between the two analyses changes all five of the second analysis's values. With each analysis holding its own generator, none of them change.

    Why this is a real reproducibility failure and not a hypothetical

    You seed at the top of a notebook, run a train/test split, and get a result. Six weeks later you add a cell above it that samples some rows to look at, re-run, and the split is different — so the model metric moves and you cannot tell whether your change caused it. The seed is still 42. Nothing in the code looks different.

    The fix is the modern API, and it is a one-line habit: rng = np.random.default_rng(42), then rng.integers(...), rng.choice(...), rng.normal(...). The generator holds its own state, so nothing outside it can perturb your draws.

    random.py
    # the legacy API: one shared stream, order-dependent
np.random.seed(42)
np.random.rand(5)

# the modern API: independent state
rng = np.random.default_rng(42)
rng.random(5)                  # floats in [0, 1)
rng.integers(0, 100, size=5)   # note: high is EXCLUSIVE, unlike randint
rng.normal(loc=0, scale=1, size=5)
rng.choice(df.index, size=100, replace=False)
rng.shuffle(a)                 # in place

# and pass it explicitly where it matters, rather than relying on global state
train, test = train_test_split(df, test_size=0.2, random_state=42)
    Two things a seed does not buy you

    Cross-version reproducibility. The same seed can produce different numbers under a different NumPy version if the underlying generator changed. This is why chapter 1 asked you to record library versions alongside results — the seed and the version together are what reproduce a number, not the seed alone.

    Parallel independence. Seeding several workers identically gives every one of them the same "random" numbers, which silently ruins a bootstrap or a simulation. rng.spawn(n) produces properly independent child generators; copying the same seed into each worker does not.

    MISSING VALUES

    NaN, and the functions that ignore it

    One NaN in a column makes every ordinary aggregation over it NaN. That is deliberate, and there is a parallel set of functions for when you want it ignored.

    np.mean of an array containing a single NaN is NaN. This is the right default — it tells you that the answer is not knowable from the data you have, rather than quietly answering a different question. But when you have decided to ignore missing values, the nan-prefixed variants do so.

    Ordinary and NaN-aware aggregations
    OrdinaryNaN-awareWhat the NaN-aware one does
    np.sumnp.nansumTreats NaN as zero. An all-NaN array sums to 0, which is rarely what you want
    np.meannp.nanmeanAverages over the present values only, so the denominator shrinks
    np.stdnp.nanstdSame, and note that dropping values usually reduces the spread
    np.maxnp.nanmaxIgnores NaN; warns and returns NaN if everything is missing
    np.argmaxnp.nanargmaxPosition of the maximum among present values
    Pandas and NumPy disagree here, and it matters

    Pandas skips missing values by default: df["x"].mean() is NumPy's nanmean, not its mean. NumPy propagates by default. So the same conceptual operation gives different answers depending on which library you called it through, and that difference is silent.

    Neither default is wrong, and being unaware of which one you are getting is. Pandas' skipna=False gives you NumPy's behaviour when you want to be told that data is missing rather than have it quietly excluded — which chapter 12 shows can move a mean by a great deal.

    Two further points. np.isnan(a) is the only reliable test, because a == np.nan is always False — NaN is not equal to itself, per chapter 2. And np.isnan fails on an object-dtype or integer array, where pd.isna works on anything, so pd.isna is the safer habit when you are not certain of the dtype.

    ENOUGH TO READ THE FIELD

    Linear algebra, briefly

    Four operations that appear constantly in analytical and machine-learning code. You do not need the theory to recognise them.

    linalg.py
    A @ B                 # matrix multiplication — the @ operator, not *
A * B                 # element-wise! a common and silent bug
A.T                   # transpose

np.linalg.inv(A)      # inverse — rarely what you actually want
np.linalg.solve(A, b) # solve Ax = b — what you want instead, and more stable
np.linalg.norm(v)     # length of a vector
np.linalg.eig(A)      # eigenvalues and eigenvectors
np.linalg.svd(A)      # singular value decomposition, behind PCA
    @ against *
    The most common mistake here. A * B multiplies element by element and, if the shapes happen to broadcast, it succeeds and returns nonsense. A @ B is the matrix product. If a linear-algebra result looks wrong and no error was raised, check this first.
    solve rather than inv
    Computing an inverse and then multiplying is both slower and numerically worse than solving the system directly. np.linalg.solve(A, b) is the right call almost every time — and chapter 2's point about subtracting close numbers is exactly why the difference in accuracy is real.
    The dot product is a weighted sum
    weights @ values is the entire content of a weighted average, a linear model's prediction, and a portfolio return. Recognising that one pattern demystifies a lot of code that looks mathematical.
    SVD is behind more than it looks
    Principal component analysis, low-rank approximation, recommender systems and pseudo-inverses are all singular value decomposition wearing different names. Worth knowing the term even if you never call it directly.

    FIVE THINGS

    Gotchas worth reading once

  1. np.arange with a float step can produce an unexpected length. np.arange(0, 1, 0.1) giving 10 or 11 elements depends on floating-point rounding at the endpoint. Use np.linspace(0, 1, 11) when the count is what you care about, which is usually.
  2. Comparison chains do not work on arrays. 0 < a < 10 raises the ambiguous-truth-value error from chapter 2. Write (a > 0) & (a < 10).
  3. An empty aggregation is not zero. np.mean([]) returns NaN with a warning, and np.max([]) raises. Guard aggregations over filtered arrays that might select nothing — a filter matching no rows is a normal occurrence, not an exceptional one.
  4. Integer division of arrays follows Python's flooring. np.array([-7]) // 2 is −4, not −3, per chapter 2. Consistent, and surprising if you expected truncation.
  5. np.array on ragged input no longer silently works. Building an array from lists of differing lengths used to produce an object array; it now raises. That is an improvement, and if you meant ragged data you want a list or a DataFrame.
    6. When to use NumPy directly at all

    Most analytical work belongs in Pandas, which is built on NumPy and gives you labels, alignment and missing-value handling for free. Reach for NumPy directly in three cases: numeric work with no labels such as a simulation or a matrix computation; a performance-critical inner step where Pandas' overhead per operation matters; and reading other people's code, since scikit-learn, SciPy and most modelling libraries accept and return arrays rather than frames.

    That last one is the most common reason to understand this chapter even if you never write import numpy yourself.

    Recap

    What to take from this chapter

    1. If you are about to loop to apply a mathematical function, there is a ufunc for it.
    2. np.clip, np.log1p and np.maximum are the three easy to miss — and np.maximum (element-wise, two arrays) is not np.max (reduce one array).
    3. The axis you name is the one that disappears. A (4, 3) array with axis=0 gives (3,); with axis=1 it gives (4,).
    4. Remove the named position from the shape tuple and you have the result shape: (2, 4, 3) with axis=1 gives (2, 3).
    5. Both partial sums add to the same grand total. That is the check when you are unsure you picked the right axis.
    6. Write axis="columns" rather than axis=1 in Pandas and the ambiguity disappears.
    7. keepdims=True exists for broadcasting the result back, turning (4,) into (4, 1) so it aligns with the original.
    8. The legacy random functions share one global stream, so your results depend on every draw made before them, including in code you did not write.
    9. Measured: inserting three unrelated draws changed all five downstream values on a shared stream, and none with per-analysis generators.
    10. Use rng = np.random.default_rng(42) and call methods on it. And note rng.integers excludes its upper bound where randint did not.
    11. A seed does not give cross-version reproducibility, which is why library versions belong next to results; and identical seeds across parallel workers give identical draws, not independent ones. Use rng.spawn.
    12. NumPy propagates NaN; Pandas skips it by default. The same operation gives different answers through the two libraries, silently.
    13. np.nansum of an all-NaN array is 0, which is rarely what you want.
    14. A * B is element-wise and A @ B is the matrix product. Check that first when linear algebra silently returns nonsense, and prefer solve over inv.
    15. Use linspace when the count matters, since arange with a float step has a rounding-dependent length.
