CHAPTER 10

Databases and SQL from Python

The question this chapter answers is where the work happens. The same analysis can move twelve gigabytes across a network and filter it in pandas, or move twelve rows — and the difference is which clauses you put in the SQL rather than anything about your Python.

    THE ALTERNATIVE TO EXPORTING

    Why query rather than download

    A CSV export is a snapshot with no schema, taken at a time you did not record, by a query you no longer have.

    The common workflow is: somebody runs a query, exports a CSV, and you analyse the CSV. That works, and it loses four things worth having.

    Types
    The database knew that order_id was a bigint and created_at was a timestamp with a timezone. The CSV does not, so chapter 9's entire inference problem is reintroduced at every read — including the identifier collision that merged 16,575 values into 470.
    Freshness
    A query re-runs. An export is as old as whenever somebody last made it, and nothing in the file says when that was.
    The definition
    A query in your code is a reviewable statement of what you counted, including which rows were excluded. An export is a result whose filters live in somebody's memory.
    The database's engine
    Indexes, join algorithms and parallel aggregation, all of which are better at filtering and grouping large tables than pandas is. Exporting means declining to use any of it, which is the next section.
    When the export is genuinely the right answer

    Three cases. You do not have access, which is a permissions conversation rather than a technical one. The data must be frozen for an audit or a published figure, where re-running and getting a different number is the problem rather than the point. And the query is expensive and you will iterate on the analysis many times — in which case run it once and save Parquet, per chapter 9, rather than working from CSV.

    CONNECTING

    sqlite3, SQLAlchemy and connection strings

    Two layers, and you usually want the second even for one query.

    connect.py
    import sqlite3, pandas as pd
from sqlalchemy import create_engine

# sqlite3: in the standard library, no server, a file on disk
con = sqlite3.connect("sales.db")
df = pd.read_sql("SELECT * FROM orders LIMIT 5", con)

# SQLAlchemy: one interface over every database, and what pandas prefers
engine = create_engine("postgresql+psycopg://user:pass@host:5432/dbname")
engine = create_engine("mysql+pymysql://user:pass@host/dbname")
engine = create_engine("sqlite:///sales.db")

with engine.connect() as con:
    df = pd.read_sql("SELECT * FROM orders WHERE region = :r",
                     con, params={"r": "North"})

df.to_sql("results", engine, if_exists="replace", index=False)

    Use SQLAlchemy rather than a raw driver connection, even for one query. Pandas supports both and increasingly expects an engine; the interface is identical across databases, so switching from SQLite to Postgres changes one string; and connection pooling comes free, which matters as soon as you make more than a handful of queries.

    Credentials do not belong in the notebook

    A connection string with a password in a committed notebook is the most common way credentials leak, and it happens because it is the path of least resistance while you are getting something working.

    create_engine(os.environ["DATABASE_URL"]) costs nothing and removes the problem. Keep the value in an environment variable or a .env file that is in .gitignore, and note that a notebook stores its output too — so printing a connection string commits it just as surely as writing it.

    THE DECISION THAT MATTERS

    Push the work down

    Every clause you move from pandas into SQL removes data from the network. The reductions multiply, and the total is larger than people expect.

    Consider a genuine analytical question: monthly revenue by region for last quarter, from a table of forty million orders with forty columns. The filter selects 2% of rows, the answer needs three columns, and it aggregates to twelve groups. There are four places to stop pushing.

    Three things to take from it. The reductions multiply rather than adding — 50 from the filter, 13 from the projection, 66,667 from the aggregate. Each is a clause, not a rewrite. And the last row is the whole point: if the answer is twelve numbers, move twelve numbers.

    When to pull the rows out instead

    This is not an argument for putting everything in SQL. Pull the rows into pandas when you need row-level exploration — looking at distributions, plotting, checking individual records — because that is what pandas is for and SQL is bad at it. When the logic is genuinely easier in Python, which regex work and anything iterative often is. And when you will ask many questions of the same subset, where pulling it once beats twenty round trips.

    The rule that follows: push the filtering and the shrinking, then explore locally. Reduce forty million rows to eight hundred thousand in the database, and do the interesting part in pandas.

    A THIRD OPTION

    DuckDB

    An analytical database with no server, that queries your files and DataFrames directly. It changes the shape of this chapter's advice.

    SQLite is transactional and row-oriented; it is excellent at looking up individual records and slow at aggregating large tables. DuckDB is columnar and built for aggregation, runs in-process like SQLite, and will query CSV, Parquet and pandas objects without loading them first.

    duckdb_.py
    import duckdb

# query a Parquet file on disk without loading it
duckdb.sql("""
    SELECT region, date_trunc('month', order_date) AS month, sum(revenue) AS revenue
    FROM 'sales/*.parquet'
    WHERE order_date >= '2024-07-01'
    GROUP BY 1, 2
""").df()                       # -> a pandas DataFrame

# query a DataFrame already in memory, by variable name
duckdb.sql("SELECT region, count(*) FROM df GROUP BY 1").df()

# and it reads what pandas would struggle with
duckdb.sql("SELECT * FROM read_csv_auto('messy.csv') LIMIT 5").df()
    Why this matters for the previous section

    Pushing work down usually means having a database and a query you are allowed to run. DuckDB gives you the same benefit with no database at all — the pushdown happens against files on your own disk. A directory of Parquet files becomes something you can aggregate with SQL, reading only the columns and row groups the query needs.

    So the honest version of chapter 9's advice is: convert the awkward CSV to Parquet once, then use DuckDB to query it. You get types, column pruning and a real query engine, and you have not installed a server.

    Two practical notes. DuckDB and pandas share memory through Arrow, so .df() on a result is close to free rather than a serialisation step. And SQL is frequently the clearer language for the group-and-aggregate part of an analysis even when the data is already in a frame — duckdb.sql("... FROM df ...") is a legitimate way to write a complicated aggregation, and reads better than a chain of five pandas calls.

    NEVER FORMAT SQL

    Parameters

    Two problems with one fix. The security one gets the attention and the everyday one is the apostrophe in a customer's name.

    Building SQL by interpolating a value into a string means the value becomes part of the query's syntax. That fails in two ways, and the demo runs both against a real 501-row table.

    String formatting against a parameter the same three inputs, both ways, with rows returned
    ROWS RETURNED0
    CORRECT—
    WHAT WENT WRONG—
    THE VALUE IS—

    Three results, and the middle one is the reason to build the habit.

    1. An ordinary value works either way. One row, both times. Which is why the bad version survives testing indefinitely.
    2. A legitimate apostrophe breaks the formatted query. O'Brien terminates the string literal early and the database reports a syntax error. This is not an attack — it is a customer, and it will happen.
    3. A hostile value returns the entire table. ' OR 1=1 -- closes the literal, adds a condition that is always true, and comments out the rest. All 501 rows come back where one was intended. Parameterised, the same input matches nothing, because it is treated as a name to look for rather than as syntax.
    The distinction that makes this click

    With formatting, the value becomes part of the query. With a parameter, the query is parsed first and the value is bound to a placeholder afterwards — so it can never be interpreted as SQL, whatever characters it contains.

    That is also why parameters handle types correctly. A Python date, a None, a Decimal all pass through with the right semantics, where formatting requires you to produce the right literal syntax for each database yourself — and None formatted into a string becomes the word None, which matches nothing and does not error.

    params.py
    # named parameters, which pandas and SQLAlchemy both accept
pd.read_sql(text("SELECT * FROM orders WHERE region = :r AND date >= :d"),
            con, params={"r": region, "d": start_date})

# a list of values needs expanding, and this is the one awkward case
from sqlalchemy import bindparam
stmt = text("SELECT * FROM orders WHERE region IN :regions").bindparams(
    bindparam("regions", expanding=True))
pd.read_sql(stmt, con, params={"regions": ["North", "South"]})

# table and column NAMES cannot be parameters — validate against a whitelist
assert col in {"revenue", "quantity", "discount"}     # then interpolate safely

    That last line is worth stating because it is the one genuine limitation. Parameters bind values, not identifiers, so a dynamic column or table name has to be interpolated — and the only safe way to do that is to check it against a set of names you control before it goes anywhere near a query.

    LARGE RESULTS

    Reading more than fits

    If pushing the work down still leaves too much, the same chunking idea from chapter 9 applies to a cursor.

    chunks.py
    # an iterator of frames, so peak memory is one chunk
totals = []
for chunk in pd.read_sql(query, con, chunksize=100_000):
    totals.append(chunk.groupby("region")["revenue"].sum())
result = pd.concat(totals).groupby(level=0).sum()

# writing back, in chunks, and without the index
df.to_sql("results", engine, if_exists="append",
          index=False, chunksize=10_000, method="multi")
    chunksize bounds memory, not work
    Exactly as in chapter 9: peak memory becomes one chunk and the total processed is unchanged. Sums and counts combine trivially across chunks; medians and exact distinct counts do not, and pushing those into SQL is the better answer.
    index=False on to_sql
    Otherwise pandas writes the index as a column, which for a default index is a meaningless 0, 1, 2 column in your table. Almost never what you want, and the default is to include it.
    method="multi" for writes
    Batches rows into multi-row inserts rather than one statement each. On a remote database this is the difference between minutes and seconds, since each round trip has latency — and it is off by default.
    Server-side cursors, where available
    Some drivers buffer the whole result on the client before chunksize can help, which defeats the point. Postgres needs stream_results=True on the connection for genuinely streaming reads.
    The order to try things

    If a query result does not fit: push the aggregation down first, since that is the 44-million-fold reduction from the demo. Then select fewer columns. Then filter to a narrower period and loop over periods, which is often more natural than row chunks and lets you cache each period's result. Then chunk the cursor.

    Chunking last, because it is the only one of the four that changes how the analysis is written rather than what the query returns.

    Recap

    What to take from this chapter

    1. A CSV export loses types, freshness, the definition and the database's engine. Chapter 9's inference problem is reintroduced at every read.
    2. Use SQLAlchemy rather than a raw driver, even for one query: one interface, pooling, and a one-string switch between databases.
    3. Credentials belong in an environment variable, and printing a connection string commits it as surely as writing it.
    4. Pushing work into SQL multiplies: 50× from the filter, 13× from the projection, 66,667× from the aggregate.
    5. Forty million rows: 12,207 MB and two minutes as SELECT *, or 288 bytes as an aggregate — 44,444,444× less data.
    6. If the answer is twelve numbers, move twelve numbers.
    7. Push the filtering and the shrinking, then explore locally. Row-level exploration is what pandas is for.
    8. DuckDB gives you pushdown with no database — it queries Parquet, CSV and DataFrames in place, and shares memory with pandas through Arrow.
    9. Never format values into SQL. An ordinary value works either way, which is why the bad version survives testing.
    10. A legitimate apostrophe breaks a formatted query. O'Brien is a customer, not an attack.
    11. A hostile value returned all 501 rows where one was intended; parameterised, it matched nothing.
    12. Parameters bind values, not identifiers. A dynamic column name must be checked against a whitelist you control.
    13. index=False on to_sql, or you write a meaningless counter column into the database.
    14. method="multi" is off by default and is the difference between minutes and seconds on a remote write.
    15. Order for a result that does not fit: aggregate down, fewer columns, narrower period, then chunk.
