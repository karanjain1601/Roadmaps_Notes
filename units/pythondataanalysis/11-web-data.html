    BEFORE YOU START

    The order to try things

    Four ways to get data off the web, in decreasing order of how much you will regret it.

    Try these in order, and stop at the first one that works
    SourceEffortStabilityLook for
    A bulk fileLowestHighestA downloads page, an S3 bucket, a data portal, a GitHub release
    A documented APILowHigh/api, developer docs, an OpenAPI spec
    An undocumented APIMediumMediumThe browser's network tab — the page's own JSON calls
    HTML scrapingHighestLowestLast resort, and it breaks on the next redesign
    The third row is the one people skip

    Most pages that look like they need scraping are rendering data fetched from their own JSON endpoint. Open the browser's developer tools, go to the network tab, filter to XHR or Fetch, and reload the page. What you frequently find is a clean JSON API with pagination parameters — which is a hundred times less work than parsing the HTML and does not break when somebody changes a CSS class.

    It is undocumented, so it can change without notice, and that is still a far better position than parsing rendered markup.

    One more before any of these: ask. A surprising number of organisations will give you a data extract or an API key if asked, and it takes an email. The reflex to scrape rather than ask is usually about avoiding a conversation rather than about the data being unavailable.

    THE CLIENT

    requests, and four things to always set

    The default call works and omits four things that will each cost you an afternoon.

    requests_basics.py
    import requests

session = requests.Session()                  # 1. reuse the connection
session.headers.update({                      # 2. identify yourself
    "User-Agent": "research-bot (you@example.org)",
    "Accept": "application/json",
})

r = session.get(url, params={"page": 1, "per_page": 500},
                timeout=(5, 30))              # 3. connect, read — ALWAYS set this
r.raise_for_status()                          # 4. do not silently accept a 500
data = r.json()

df = pd.json_normalize(data["results"])       # chapter 9's flattening
    Session, not bare requests.get
    Reuses the TCP connection and TLS handshake across calls, which on a thousand-page crawl is a large fraction of the total time. It also carries headers and cookies for you.
    A real User-Agent with a contact address
    The default announces you as a Python script. A named agent with an email is how a site operator contacts you before blocking you, and it is the single cheapest piece of good citizenship available.
    timeout, always
    Without it, requests waits forever — a hung connection stops your loop with no error and no output. This is the omission most likely to produce a notebook that has been "running" for six hours. Pass a tuple: connect timeout and read timeout.
    raise_for_status()
    A 500 or a 404 still returns a response object, and r.json() on an error page raises something confusing about a token in position 0. Checking the status turns that into an accurate exception at the point of failure.
    Read the response headers before writing any pagination logic

    print(dict(r.headers)) on the first call usually tells you everything you need: X-RateLimit-Limit and X-RateLimit-Remaining, a Link header with the next page's URL, Retry-After on a 429, and a total count. Guessing at pagination when the server is telling you the answer is a common waste of an hour.

    THE FEASIBILITY QUESTION

    Pagination, and what actually limits it

    Two independent bounds on how fast you can fetch, and which one binds decides whether concurrency is worth writing.

    Fetching two million records at five hundred per page is four thousand requests. How long that takes depends on two things that do not interact the way people expect: the latency bound — how long each request takes, divided by how many you run at once — and the rate bound, which concurrency cannot touch at all.

    Which bound binds latency against rate limit, with the crossover computed
    REQUESTS NEEDED0
    TOTAL TIME0
    BOUND BY—
    USEFUL WORKERS0beyond this, only 429s

    Three results, and the first is smaller than anyone expects.

    1. The crossover is at two workers. One worker takes 720 seconds and is latency-bound; two takes 360 seconds of latency against a 400-second rate floor, so the rate limit already binds. Every worker past the second earns nothing but 429 responses.
    2. Past the crossover, concurrency does literally nothing. Sixty-four workers and two workers finish at the same time, because the limit is on requests rather than on connections.
    3. Page size is the lever that works. Going from 100 to 1,000 records per page is exactly ten times faster when rate-bound, because it divides the request count. Concurrency cannot do that and page size costs one parameter.
    The order to try, therefore

    Maximise the page size first — check the documentation for the maximum, and check whether it is honoured, since some APIs silently cap it lower than they claim. Then filter server-side, which is chapter 10's pushdown argument at a different protocol: a since= parameter that halves the records halves the requests. Then add concurrency, up to the crossover and no further.

    And compute the total before you start. Twenty million records at 600 requests a minute is a four-thousand-second floor, and knowing that in advance turns "why is this still running" into a decision about whether to do it at all.

    paginate.py
    def fetch_all(url, per_page=500, max_pages=None):
    """Cursor pagination where available; page numbers otherwise."""
    frames, page, cursor = [], 1, None
    while True:
        params = {"per_page": per_page}
        if cursor: params["cursor"] = cursor
        else:      params["page"] = page

        r = session.get(url, params=params, timeout=(5, 30))
        r.raise_for_status()
        body = r.json()

        rows = body["results"]
        if not rows: break                       # the only reliable stop condition
        frames.append(pd.json_normalize(rows))

        cursor = body.get("next_cursor")
        page += 1
        if cursor is None and not body.get("has_more"): break
        if max_pages and page > max_pages: break

    return pd.concat(frames, ignore_index=True)

    Two notes on that. Prefer a cursor to a page number where the API offers one: page-number pagination over a table that is being written to will skip and duplicate rows as items shift between pages, and a cursor is stable against that. And an empty page is the only reliable stop condition — a total count in the response can be stale, and has_more is sometimes wrong on the last page.

    WHEN IT FAILS

    Retries, and the thundering herd

    Everyone knows to retry with exponential backoff. The measurement shows that exponential backoff alone does not help at all — and what does.

    Forty concurrent workers hit a limit of ten requests a second. Thirty are rejected. They all retry. The question is when, and the answer people reach for turns out not to address the problem.

    Forty rejected workers, three retry strategies arrivals per second, wasted 429s, and total wall clock
    BUSIEST SECOND0
    WASTED 429s0rejected again
    WALL CLOCK0
    SPREAD NEEDED0for zero rejections

    The measured comparison is more interesting than the folklore.

    1. Fixed and exponential backoff waste exactly the same number of requests — 60 rejected 429s each. Both send every worker at the same instant, so the same thirty are turned away every round. Exponential is not better; it merely waits longer while being equally wrong, taking 15 seconds against 4.
    2. Jitter helps, and not because it is random. It wastes 40 rather than 60. But with a one-second spread over forty pending workers, the busiest second still sees all forty arrivals — identical to fixed backoff. The improvement comes entirely from the spread widening across rounds.
    3. There is a formula. Zero rejections requires the spread to be at least pending / limit seconds wide — four seconds here. At 2 seconds, twenty are rejected; at 4 seconds, none are. That is a number you can compute rather than a constant you pick and hope about.
    A narrow jittered window is still a thundering herd

    This is the part the usual advice omits. "Exponential backoff with jitter" is repeated as a phrase, and the jitter only works if its range is wide enough to bring the arrival rate inside the limit. Randomising forty retries across one second when ten a second are allowed changes nothing about the first round.

    So the useful version of the rule is: spread the retries over at least as long as it would take to serve them. If forty requests are pending and ten a second are permitted, four seconds is the floor, and anything narrower guarantees another round of rejections.

    retries.py
    from urllib3.util.retry import Retry
from requests.adapters import HTTPAdapter

retry = Retry(
    total=5,
    backoff_factor=1,               # 1s, 2s, 4s, 8s…
    backoff_jitter=1.0,             # full jitter — needs urllib3 >= 2.0
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET"],        # only retry what is safe to repeat
    respect_retry_after_header=True,   # obey the server if it tells you
)
session.mount("https://", HTTPAdapter(max_retries=retry))

    Two parameters there deserve attention. respect_retry_after_header matters because a server sending Retry-After: 30 is telling you the answer, and your backoff calculation is guessing at something it already knows. And allowed_methods restricts retries to methods that are safe to repeat — retrying a POST that timed out may create a second record, which is the idempotency argument arriving over HTTP.

    LAST RESORT

    Parsing HTML

    Two functions cover most of it, and one of them people never try first.

    html_parse.py
    # try this FIRST — it handles a genuine <table> in one line
tables = pd.read_html(html)          # a list of DataFrames
df = tables[2]

# and only then reach for a parser
from bs4 import BeautifulSoup
soup = BeautifulSoup(html, "lxml")               # lxml is faster than html.parser

soup.select("table.results tr")                  # CSS selectors: the readable way
soup.select_one("h1.title").get_text(strip=True)
[a["href"] for a in soup.select("a[href^='/product/']")]

rows = [{"name": tr.select_one(".name").get_text(strip=True),
         "price": tr.select_one(".price").get_text(strip=True)}
        for tr in soup.select("tbody tr")]
df = pd.DataFrame(rows)
    pd.read_html before BeautifulSoup

    If the data is in an actual HTML table, this is one line and it is done — including the header row and the column names. People routinely write forty lines of BeautifulSoup for something read_html handles, because they reached for the parser without checking.

    It fails when the "table" is a grid of <div> elements, which is common in modern layouts, and that is when the parser is the right tool.

    Three things that will break your selectors

    • JavaScript rendering. If the data is not in r.text, it was fetched after page load — and the network tab will show you the endpoint, which is the first section's advice.
    • Generated class names. css-1x2y3z changes on every deploy. Anchor on structure or on text instead.
    • Inconsistent markup. A missing element makes select_one return None, and .get_text() on None raises. Handle it per row rather than letting one bad row end the crawl.

    Two habits that make it survivable

    • Save the raw HTML to disk before parsing. Then iterating on your selectors costs nothing and re-fetches nothing, which is both faster and politer.
    • Assert the shape. assert len(rows) > 20 catches a silently emptied selector after a redesign, which is otherwise a crawl that reports success and returns nothing.

    BEFORE YOU RUN IT

    When scraping is the wrong tool

    A short section with real consequences. I am not a lawyer and this is not legal advice — it is the set of questions worth answering before starting, and some of them need someone who is.

  1. Read robots.txt and the terms of service. The first tells you what the operator asks automated clients not to do. The second may prohibit automated access entirely, and whether that is enforceable varies by jurisdiction — which is a question for your organisation's counsel rather than for a chapter.
  2. Rate-limit yourself even where nothing forces you to. One request a second is invisible; two hundred a second is an attack on somebody's server regardless of intent, and it is how you get blocked and remembered.
  3. Never scrape personal data without a lawful basis. Names, emails, profiles and reviews attached to identifiable people fall squarely under the data-protection obligations that the Data Engineer unit covers, and "it was publicly visible" is not a lawful basis.
  4. Do not evade access controls. Logging in to scrape, defeating a CAPTCHA, or rotating addresses to avoid a block moves this from an etiquette question to a different category entirely.
  5. Cache aggressively. Every page fetched twice is a request that did not need to exist. Save the raw response and re-parse locally.
    6. The question worth asking first

    Would you be comfortable explaining this crawl to the person who runs the site? That single test catches most of the genuinely problematic cases, and it usually points at the alternative — which is emailing them.

    The technical version of the same test: a crawl you would be happy to identify yourself in the User-Agent for is almost certainly fine. One where you would rather not be identifiable is telling you something.

    Recap

    What to take from this chapter

    1. Try in order: a bulk file, a documented API, the page's own undocumented JSON, then HTML. The third is the one people skip, and the network tab reveals it in seconds.
    2. Ask first. Many organisations will supply an extract if emailed.
    3. Always set a timeout. Without one, requests waits forever, which is the notebook that has been running for six hours.
    4. Use a Session, a real User-Agent with a contact address, and raise_for_status().
    5. Read the response headers before writing pagination logic. Rate limits, the next page and the total are usually right there.
    6. Two independent bounds: latency and rate. Concurrency touches only the first.
    7. The crossover is at two workers for 4,000 pages at 180 ms against 600 requests a minute. Everything past that earns only 429s.
    8. Page size is the lever. 100 to 1,000 records per page is exactly ten times faster when rate-bound.
    9. Prefer a cursor to a page number, and treat an empty page as the only reliable stop condition.
    10. Fixed and exponential backoff waste identically — 60 rejected requests each — and exponential merely takes 15 seconds instead of 4 while doing it.
    11. A narrow jittered window is still a thundering herd. Forty retries across one second, against a limit of ten a second, is no better than no jitter at all.
    12. The spread must be at least pending / limit seconds. Four seconds here gives zero rejections; two gives twenty.
    13. Respect Retry-After, and restrict retries to methods that are safe to repeat.
    14. Try pd.read_html before BeautifulSoup, and save the raw HTML to disk so iterating on selectors re-fetches nothing.
    15. Assert the row count so a redesign that empties your selector fails loudly.
    16. Would you explain this crawl to the site's operator? That test catches most of the problematic cases.

    ONE THING TO TRY

    Take an API you fetch from and compute its rate floor: pages divided by the limit. If that number is larger than your patience, no amount of concurrency will fix it and the page size is where to look.
