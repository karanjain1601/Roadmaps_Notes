CHAPTER 05

NumPy: the array model

Chapter 4 established that whole-column operations are two thousand times faster than row-at-a-time ones. This is why: an array is a single typed block of memory rather than a collection of objects. That one design decision explains the speed, the memory savings, the silent integer overflow, and the aliasing bug that catches everybody once.

    THE ONE IDEA

    Why an array is fast

    A Python list of a million numbers is a million objects with a million pointers. A NumPy array of a million numbers is eight megabytes.

    A Python int is an object. It has a type pointer, a reference count, and its value — around 28 bytes for a small integer, plus 8 more for the pointer the list holds. So a list of a million integers is roughly 36 MB scattered across the heap, and iterating it means following a million pointers to a million separate places.

    A NumPy array of a million int64 values is one contiguous 8 MB block. Every element is at a computable offset, so the CPU can prefetch, the values fit in cache lines, and the whole array can be handed to a compiled loop that never touches a Python object.

    The three consequences worth carrying

    One dtype for the whole array is the price of contiguity, and it is why mixing types forces the array into object dtype — at which point you have a list again with extra steps, and none of the speed.

    Fixed size is the other price. There is no cheap append: np.append allocates a new array and copies everything. Building an array by appending in a loop is quadratic. Collect into a Python list, then convert once.

    Every element is at a computable offset, which is what makes views possible — and views are the subject of the second demo.

    THE TYPE DECISION

    dtype: what it saves and what it costs

    Choosing a narrower type can cut memory by a factor of eight. Choosing one too narrow corrupts your data silently, and the corruption looks like a number.

    An array's dtype fixes how many bytes each element occupies. int64 is the default on most platforms and handles anything; int8 is eight times smaller and holds values from −128 to 127. Pandas will happily downcast for you if you ask, and will not check whether your values fit.

    Two results.

    1. The savings are large and exactly proportional. Ten million rows across eight columns is 610 MB at int64 and 76 MB at int8 — an exactly eight-fold reduction, which is often the difference between fitting in memory and chapter 20.
    2. Integer overflow wraps around silently. Three billion downcast to int32 becomes −1,294,967,296. Forty thousand in int16 becomes −25,536. No exception, no warning, and a sum over that column is meaningless. float32 fails differently — 1,234,567,891 becomes 1,234,567,936, losing precision rather than sign.
    The check to run before any downcast

    The safe target is the smallest dtype whose range covers the column's observed minimum and maximum — and observed is doing work in that sentence, because next month's data may exceed today's. pd.to_numeric(s, downcast="integer") does this check for you and picks a safe type; a bare astype("int32") does not.

    Which is a specific instance of the general rule: a cast that cannot fail is safe, and a cast that can fail should be one that fails loudly.

    Text columns, and the one that actually saves memory

    A string column has no fixed-width dtype, so Pandas stores it as object: a pointer per row to a Python string object. That is roughly 60 bytes per row regardless of how short the string is. A category dtype stores a small integer code per row plus the distinct values once.

    The demo's text panel makes the trade concrete: a million-row column with twelve distinct values costs 63 MB as object and 1.0 MB as a category — 66 times smaller. With fifty thousand distinct values the saving falls to 13×, and with almost every value distinct a category can cost more than the object column, because you pay for both the codes and the dictionary. Categories pay off in proportion to how repetitive the column is.

    DIMENSIONS

    Shape, reshape and strides

    The block of memory is one-dimensional. Shape is metadata that says how to read it.

    shape.py
    a = np.arange(12)              # [0 1 2 ... 11], shape (12,)
b = a.reshape(3, 4)            # 3 rows of 4 — the SAME memory, read differently
b.shape                        # (3, 4)
b.strides                      # (32, 8): 32 bytes to the next row, 8 to the next column

a.reshape(3, -1)               # -1 means "work it out": gives (3, 4)
b.T                            # transpose: shape (4, 3), still the same memory
b.ravel()                      # back to 1-D, a view where possible

    Strides are how many bytes to step to reach the next element along each axis, and they are what makes reshaping and transposing free. Transposing a 10,000 × 10,000 array does not move 800 MB — it swaps two numbers in the metadata. The data stays exactly where it is and is simply read in a different order.

    Why a transposed array can be slower to work with

    Free to create, not always free to use. After a transpose, walking along what is now a row means jumping through memory in large steps rather than reading consecutively, so you lose the cache locality that made the array fast in the first place. On a large array, an operation on a transposed view can be several times slower than on a contiguous one.

    np.ascontiguousarray(b.T) pays the copy once to get the locality back. Worth it if you are about to do many operations; not worth it for one.

    Two shape conventions worth internalising, because they show up constantly. A shape of (n,) is one-dimensional and is not the same as (n, 1) or (1, n) — the first is a bare sequence, the others are a column and a row of a 2-D array. Many broadcasting confusions are this distinction. And a trailing -1 in reshape means "infer this from the total", which is the readable way to write reshapes whose length you do not want to hard-code.

    THE ALIASING BUG

    Views against copies

    Some operations give you a window onto the original memory. Mutating that window mutates the original, and nothing tells you which kind you have.

    This is chapter 3's aliasing story, made sharper by strides. Because every element is at a computable offset, a slice does not need to copy anything — it can be described as "the same memory, starting later, with these strides". That is a view. Other operations cannot be described that way and must copy.

    The rule that emerges is learnable, and it is the one worth memorising from this chapter.

    Views — mutating them changes the original

    • Basic slicing: arr[2:5]
    • Strided slicing: arr[::2]
    • reshape and transpose
    • ravel() where it can

    Cost: nothing. Just new metadata.

    Copies — independent of the original

    • Fancy indexing: arr[[1, 3, 5]]
    • Boolean masks: arr[arr > 40]
    • Arithmetic: arr * 2
    • .copy(), and flatten() always

    Cost: a new allocation the size of the result.

    Why this is a real bug and not a curiosity

    The pattern that produces it is ordinary. You take a slice to work on a subset, modify it, and the original silently changes underneath you — so a later computation on the full array uses values you thought were confined to the subset. Nothing errors. The numbers change.

    Two defences. Call .copy() when you intend to modify a subset independently, which costs an allocation and buys certainty. And check with arr.base is not None, which is True for a view — useful when debugging a number that changed for no visible reason.

    In Pandas this same distinction is the source of the SettingWithCopyWarning that everybody meets, and chapter 7 takes it apart properly.

    SHAPES THAT DIFFER

    Broadcasting

    Operating on arrays of different shapes without writing a loop or copying data. Two rules, applied right to left.

    arr * 2 works because the scalar is broadcast across every element. The same mechanism handles arrays: NumPy compares shapes from the trailing dimension backwards, and two dimensions are compatible if they are equal or if one of them is 1.

    broadcast.py
    a = np.ones((3, 4))          # 3 rows, 4 columns

a + 10                       # (3,4) with a scalar     -> (3,4)
a + np.array([1, 2, 3, 4])   # (3,4) with (4,)          -> (3,4)   one value per column
a + np.array([[1], [2], [3]])# (3,4) with (3,1)         -> (3,4)   one value per row
a + np.array([1, 2, 3])      # (3,4) with (3,)          -> ValueError

# the classic use: centre every column on its own mean
centred = a - a.mean(axis=0)             # (3,4) - (4,)  -> (3,4)
# and centre every ROW instead, which needs the extra dimension
centred = a - a.mean(axis=1, keepdims=True)   # (3,4) - (3,1) -> (3,4)
    Shapes compared from the right, and the result
    FirstSecondResultWhy
    (3, 4)()(3, 4)A scalar broadcasts to anything
    (3, 4)(4,)(3, 4)Trailing dimensions match; the missing one is treated as 1
    (3, 4)(3, 1)(3, 4)4 against 1 — the 1 stretches
    (3, 4)(3,)ErrorCompared from the right, 4 against 3
    (5, 1, 3)(4, 3)(5, 4, 3)Both stretch, in different dimensions
    The failure that confuses everyone, and its fix

    The fourth row is the one people hit. You have a (3, 4) array and a per-row vector of 3 values, and adding them fails — because broadcasting aligns from the right, so it compares your 3 against the 4 columns.

    The fix is keepdims=True on the aggregation that produced the vector, or an explicit [:, None] to add the missing dimension. Both turn (3,) into (3, 1), which broadcasts correctly. If you remember one thing here: a reduction that you intend to broadcast back should keep its dimensions.

    One caution about memory. Broadcasting itself allocates nothing — that is the point — but the result is a full array. a[:, None] - b[None, :] on two vectors of 50,000 elements produces a 50,000 × 50,000 result, which is 20 GB at float64. The expression is three characters longer than the one that works; the memory is five orders of magnitude larger. Pairwise-distance calculations are where this bites.

    SELECTING

    Boolean masks and fancy indexing

    Two ways to select a subset, both of which return copies, and both of which replace a loop.

    indexing.py
    arr = np.array([10, 20, 30, 40, 50, 60])

# boolean mask: a same-shaped array of True/False
arr > 35                     # [False False False  True  True  True]
arr[arr > 35]                # [40 50 60]
(arr > 35).sum()             # 3      — counting, per chapter 2
(arr > 35).mean()            # 0.5    — the proportion

# combining masks needs the bitwise operators and parentheses
arr[(arr > 20) & (arr < 50)]        # [30 40]
arr[~(arr > 35)]                    # [10 20 30]   ~ is "not"

# fancy indexing: an array of positions, in any order, with repeats
arr[[4, 0, 4]]                      # [50 10 50]

# and both work for assignment, which is how vectorised branching is written
arr[arr > 35] = 0                   # in place, no loop

    Three notes on this. The mask must be the same shape as the axis it indexes, which is why a mask built from one column can filter another — that is the whole basis of df[df.revenue > 100]. Use &, | and ~ rather than and, or, not, and parenthesise, per chapter 2. And np.where gives you the positions when you need indices rather than values: np.where(arr > 35) returns (array([3, 4, 5]),).

    Assignment through a mask is the vectorised if

    arr[arr < 0] = 0 is a conditional replacement with no loop and no branch, and it is the form chapter 4's tiering demo used four times in a row. It is also in-place, so it mutates rather than returning a new array — which, given the previous section, is worth being deliberate about.

    Recap

    What to take from this chapter

    1. An array is one contiguous typed block; a list is a million pointers to a million objects. 8 MB against roughly 36 MB for the same million integers.
    2. The price of contiguity is one dtype for the whole array and a fixed size. There is no cheap append — collect into a list and convert once.
    3. Narrower dtypes save exactly proportionally: 10 million rows × 8 columns is 610 MB at int64 and 76 MB at int8.
    4. Integer overflow wraps around silently. 3,000,000,000 in int32 becomes −1,294,967,296; 40,000 in int16 becomes −25,536. No warning.
    5. float32 fails by losing precision instead: 1,234,567,891 becomes 1,234,567,936.
    6. Downcast with pd.to_numeric(downcast=...), which checks the range, rather than a bare astype, which does not.
    7. A text column with 12 distinct values is 63 MB as object and 1.0 MB as a category — 66× — but only 13× at 50,000 distinct values, and a loss when almost all are distinct.
    8. Shape and strides are metadata, so reshape and transpose are free — though a transposed view loses cache locality and can be several times slower to use.
    9. (n,) is not (n, 1). Most broadcasting confusion is this distinction.
    10. Basic slicing, reshape and transpose give views; fancy indexing, masks and arithmetic give copies. Mutating a view changes the original, with no warning.
    11. arr.base is not None tells you it is a view, which is the debugging tool when a number changes for no visible reason.
    12. Broadcasting aligns shapes from the right, and a dimension of 1 stretches. A reduction you intend to broadcast back should use keepdims=True.
    13. Broadcasting allocates nothing; the result does. Two 50,000-element vectors crossed pairwise is 20 GB.
    14. Assignment through a mask is the vectorised if, and it is in place.
