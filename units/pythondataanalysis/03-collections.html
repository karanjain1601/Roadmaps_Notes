    THE FOUR

    What each container is for

    They are not interchangeable, and the difference is not style. Each makes a different operation cheap.

    The four built-in containers, and the operation each is built for
    ContainerWrittenOrderedMutableCheap operation
    list[1, 2, 3]YesYesAppend, index by position, iterate in order
    tuple(1, 2, 3)YesNoSame as a list, plus it can be a dict key
    dict{"a": 1}Insertion orderYesLook up by key
    set{1, 2, 3}NoYesMembership, and set algebra

    Two of these rows are the ones that matter for analysis.

    A tuple is not just an immutable list
    Because it cannot change, it can be hashed, which means it can be a dictionary key or a set member. That is why a multi-column grouping key is a tuple, and why chapter 7's MultiIndex levels come back to you as tuples. Immutability is also a signal to a reader: this collection is a fixed record, not a growing list.
    Sets and dicts are hash tables, and lists are not
    Checking whether something is in a set is a single hash lookup regardless of size. Checking whether it is in a list scans the list. For a hundred items nobody notices; for a filter against fifty thousand identifiers the difference is the demo below.
    Set algebra is underused

    Comparing two collections of identifiers is a routine analytical task and reads terribly as loops. As sets it is one line each: a - b for what is only in the first, a & b for the overlap, a ^ b for the symmetric difference. Reconciling two systems' customer lists — which is exactly the reconciliation check Data Engineer argues for — is three lines of set algebra.

    THE DECISION WITH A PRICE

    Membership, and the one-word fix

    Filtering rows against a collection of allowed values is one of the most common things an analyst writes. Whether that collection is a list or a set changes the work by a factor of the collection's size.

    The pattern is familiar: you have a list of identifiers of interest, and you want the rows matching them. Written as if row_id in allowed, the cost depends entirely on what allowed is.

    Three results.

    1. The penalty is the container's size, not a constant factor. Five thousand items at a 50% hit rate averages 3,750 comparisons per lookup. Fifty thousand items averages 37,500. The gap grows as your data grows, which is why this bites in production and not in testing.
    2. Misses are the worst case. A hit stops the scan early — on average halfway. A miss has to compare every element before concluding it is absent, so a filter that mostly excludes rows pays the full n every time.
    3. The fix is one word. allowed = set(allowed) before the loop. Building the set costs one pass; every lookup afterwards is a single hash.
    membership.py
    # the version people write
allowed = load_ids()                    # a list of 50,000 ids
rows = [r for r in data if r["id"] in allowed]      # scans 50,000 per row

# the version that is 37,500 times less work
allowed = set(load_ids())               # one pass to build
rows = [r for r in data if r["id"] in allowed]      # one hash per row

# in Pandas, the same idea has its own method
df[df["id"].isin(allowed)]              # hash-based, and vectorised

    The last line is the one to reach for once the data is in a DataFrame. isin is both hash-based and vectorised, so it avoids this problem and chapter 4's problem at the same time.

    THE IDIOM

    Comprehensions

    A comprehension is a loop that builds a collection, written as one expression. Faster than the loop, and clearer up to a point that is easy to overshoot.

    comprehensions.py
    squares = [x**2 for x in values]                    # list
evens   = [x for x in values if x % 2 == 0]         # with a filter
lookup  = {r["id"]: r["name"] for r in rows}        # dict comprehension
seen    = {r["region"] for r in rows}               # set comprehension

# a generator: computes lazily, holds one item at a time
total = sum(r["amount"] for r in rows)              # no list is ever built

    Three things worth knowing about them.

    They are genuinely faster than the equivalent loop
    Not because the iteration is different, but because append is not looked up and called on every pass. The gain is real and modest — roughly two to four times — and it is nothing like the gain from chapter 4's vectorisation, so do not reach for a comprehension as a performance fix on a DataFrame.
    The generator form matters for memory
    sum([x for x in rows]) builds the whole list first; sum(x for x in rows) never builds it. On a large file that is the difference between fitting in memory and not, which is chapter 20's subject. Drop the brackets when you are only consuming the result once.
    Nesting is where readability dies
    Two clauses is usually fine. Three, or a conditional expression inside a nested comprehension, is write-only code. The rule that works: if you cannot read it aloud as a sentence, make it a loop or a named function.
    The nesting order catches everyone once

    In [x for row in table for x in row], the clauses read left to right in the same order you would write the nested loops — outer first. It looks like it should be the other way round because the expression comes first, and getting it backwards produces a NameError that seems to make no sense. Write the loops out, then collapse them.

    THE CONFUSING ONE

    Mutability, aliasing and copies

    Assignment in Python binds a name to an object. It does not copy. Almost every surprise in this section follows from that one sentence.

    Two names can refer to the same list, so mutating through one is visible through the other. That is straightforward once stated. What is not obvious is that a function's default value is also an object, created once when the function is defined — so a mutable default is shared by every call for the lifetime of the program.

    The measured result is unambiguous. With acc=[], four calls return lists of length 1, 2, 3, 4 — each call sees everything the previous ones added. With acc=None and acc = acc if acc is not None else [] inside, every call returns length 1.

    Why this is worse than it looks in analysis code

    The bug does not surface on the first call, so it survives testing on a single example. It surfaces when a helper is applied to several groups — and then the second group's output silently contains the first group's rows too. Totals are inflated, nothing errors, and the numbers look plausible.

    The rule has no exceptions worth learning: never use a mutable object as a default argument. Use None and create it inside. This applies to lists, dicts, sets and DataFrames alike.

    The copy control demonstrates the other half. b = a is an alias, so b sees everything. b = a.copy() makes a new outer list whose elements are the same objects — so mutating an inner list is visible through both, and the demo reports all three inner objects shared. Only copy.deepcopy gives an independent structure.

    copies.py
    import copy

a = [[1, 2], [3, 4]]
alias   = a                    # same object
shallow = a.copy()             # new outer list, same inner lists
deep    = copy.deepcopy(a)     # fully independent

a[0].append(99)
alias[0]      # [1, 2, 99]   sees it
shallow[0]    # [1, 2, 99]   sees it too
deep[0]       # [1, 2]       does not

# Pandas is the same story, and defaults to a copy
df2 = df.copy()          # deep by default: safe
df2 = df                 # an alias: chapter 7's SettingWithCopyWarning starts here

    WORTH KNOWING

    Five idioms that replace a loop

    Each of these removes an index variable, and an index variable is where off-by-one errors live.

    idioms.py
    # 1. enumerate: index and value together
for i, name in enumerate(columns):
    print(f"{i}: {name}")

# 2. zip: walk two collections in step
for name, dtype in zip(columns, dtypes):
    ...
# zip stops at the shorter one, silently. If that is a bug, say so:
for a, b in zip(xs, ys, strict=True):    # raises if the lengths differ
    ...

# 3. unpacking: name the parts
first, *rest = row              # rest is a list
region, total = group_key       # a tuple from groupby

# 4. dict.get with a default, instead of a key check
label = mapping.get(code, "unknown")

# 5. dict.items to iterate keys and values
for code, label in mapping.items():
    ...
    strict=True on zip is worth the habit

    By default zip stops at the shortest input without complaint. Zipping a list of 50 column names against a list of 48 dtypes silently drops the last two columns, and you get a result rather than an error. Since Python 3.10, strict=True turns that into an exception, which is what you want — the loud failure at the point of the mistake rather than a quiet one later.

    THE BOUNDARY

    When to stop using these

    Everything above is the right tool for a few thousand records. Past that, and for anything tabular, it is the wrong one.

    A list of dictionaries is a perfectly reasonable way to hold tabular data, right up until you want to do something to a whole column. Then every operation is a loop, every aggregation is manual, and every one of them pays Python's per-element cost.

    The same three tasks, in plain Python and in Pandas
    TaskPlain PythonPandas
    Mean of a columnsum(r["x"] for r in rows) / len(rows)df["x"].mean()
    Total per groupA loop with a defaultdictdf.groupby("g")["x"].sum()
    Rows matching a setThe membership demo abovedf[df["id"].isin(ids)]

    The Pandas column is shorter, and — more importantly — it is executed by compiled code over the whole column rather than by Python one element at a time. That is the entire subject of the next chapter.

    Where plain containers still win

    Three cases, and they are common enough to name. Configuration and mappings — a dict of region codes to labels is a dict, not a DataFrame. Streaming a file too large to load, where a generator processes one line at a time and never holds the whole thing. And genuinely non-tabular data, like a nested JSON response before you have flattened it, which chapter 9 covers.

    The signal to switch is not size but shape: as soon as you are thinking in columns, you want a DataFrame.

    Recap

    What to take from this chapter

    1. Each container makes one operation cheap: lists for order and position, tuples for fixed records that can be keys, dicts for key lookup, sets for membership.
    2. A tuple's real advantage is that it can be hashed, which is why grouping keys are tuples.
    3. Set algebra replaces reconciliation loops: a - b, a & b, a ^ b.
    4. Membership in a list costs the container's size, not a constant: 5,000 items averages 3,750 comparisons per lookup, 50,000 averages 37,500.
    5. Misses are the worst case, because a miss must compare every element before concluding absence.
    6. The fix is set(...) before the loop, or isin once the data is in a DataFrame.
    7. Comprehensions are two to four times faster than the loop — real, modest, and nothing like vectorisation.
    8. Drop the brackets for a generator when consuming once; it never builds the list.
    9. Assignment binds a name, it does not copy. Everything in the mutability section follows from that.
    10. A mutable default argument is created once at definition and shared by every call: four calls returned lengths 1, 2, 3, 4. Use None and create it inside.
    11. A shallow copy shares every inner object. Only deepcopy gives independence.
    12. zip stops at the shortest input silently. Use strict=True so a length mismatch fails loudly.
    13. Switch to a DataFrame when you start thinking in columns, not at a particular size.
