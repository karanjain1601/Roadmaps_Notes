CHAPTER 01

Setup that will not fight you

Two things in this chapter cost analysts more time than any technique in the rest of the unit. A shared Python installation that cannot satisfy every project at once, and a notebook whose result depends on the order somebody happened to click. Both are avoidable, and both are worth understanding as arithmetic rather than as folklore.

    WHY THIS LANGUAGE

    What Python is actually good at here

    Not speed, and not elegance. Two other things, and knowing which they are tells you when to reach for something else.

    Python is a slow language wrapped around fast libraries. Nearly every operation in this unit that matters — a column multiplied by a scalar, a group-by, a correlation matrix — is executed by compiled C or Rust while Python does the arranging. That is why chapter 4 spends its time on the difference between looping over rows and operating on whole columns: the first pays Python's speed, the second does not.

    What Python contributes is two things:

    One language across the whole path
    Loading, cleaning, statistics, charts, modelling and a web dashboard in one place. The alternative is usually SQL for the data, a spreadsheet for the exploration and a BI tool for the chart, with a manual export between each — and every one of those handoffs is a place for a number to change.
    Readable analysis
    An analysis is an argument, and somebody has to check it. Python that reads like a sequence of stated steps is reviewable in a way that a chain of spreadsheet formulas is not, which is most of why it displaced them for anything consequential.
    When not to use it

    If the work is a single aggregate over a large table, SQL in the database is faster to write, faster to run and easier to review — chapter 10 makes that case properly. If the deliverable is a recurring formatted report for people who live in Excel, fighting them costs more than it returns. And if the dataset comfortably fits a spreadsheet and the question is asked once, a spreadsheet is the right tool.

    Python earns its place when the analysis will be repeated, checked, or built on.

    THE FIRST DECISION

    Why one shared installation stops working

    Not because Python is fragile, but because a single environment can hold exactly one version of each package, and projects do not agree.

    The failure is specific. Project A pins pandas==1.5.* because a colleague's script depends on a behaviour that changed. Project B needs a library that requires pandas>=2.1. One installation cannot hold both, so installing for B breaks A, silently, until A is next run.

    Most requirements are permissive — pandas>=1.5 accepts anything recent — which is why a shared install works fine for a while. Conflict comes from the minority that pin. The demo models exactly that.

    Three things the model shows.

    1. It is fine, and then it is not. Two projects conflict 10% of the time; three 29%; five 62%; eight 93%. The curve is steep, which is why a shared install feels perfectly workable right up to the point where every install breaks something.
    2. The driver is pinning, not project count. At eight projects, 15% pinned requirements conflict 41% of the time and 60% pinned conflict 100%. So the practice that causes this is pinning tightly by default, which people do out of caution.
    3. Isolation is always satisfiable, and the cost is disk. Eight environments at 420 MB is 3.3 GB — genuinely nothing against the hours a broken install costs.

    THE TOOLS

    pip, venv, conda, uv

    Four names that solve overlapping problems. Knowing which problem each solves stops the choice being cargo cult.

    What each tool actually does
    ToolJobInstallsReach for it when
    pipInstalls Python packagesPython packages onlyAlways. It is the installer, not the isolator.
    venvCreates an isolated environmentNothing — it makes a place for pip to install intoThe standard-library answer to the previous section. Built in, no install.
    condaBoth, plus non-Python dependenciesPython packages, compilers, CUDA, R, system librariesYou need a compiled library that pip struggles with, or GPU tooling.
    uvBoth, very fast, with a lockfilePython packages, and Python itselfThe current default worth learning. Orders of magnitude faster and it resolves properly.
    setup.sh
    # the standard-library route, available everywhere
python -m venv .venv
source .venv/bin/activate        # .venv\Scripts\activate on Windows
pip install pandas numpy matplotlib seaborn jupyterlab
pip freeze > requirements.txt

# the same thing with uv, faster and with a real lockfile
uv init
uv add pandas numpy matplotlib seaborn jupyterlab
uv run jupyter lab              # no activation step needed
    The distinction worth internalising

    pip freeze records what you happen to have installed, including transitive dependencies at whatever versions resolution picked that day. A lockfile records a resolved, reproducible set: same inputs, same versions, on any machine. That difference is why requirements.txt so often fails to reproduce an environment months later, and it is the main practical reason to prefer uv or Poetry over bare pip for anything that has to be re-run.

    If you are stuck with requirements.txt, pin exact versions in it and regenerate deliberately rather than continuously.

    One note on conda specifically. It solves a real problem — installing compiled and non-Python dependencies — and it is slower and heavier for the case where you do not have that problem. If pip installs what you need, you do not need conda. If you are fighting a compiler error installing a geospatial or GPU library, conda is the shortcut, and conda-forge is the channel to use.

    THE SECOND DECISION

    Notebooks, and the order problem

    A notebook's result depends on the order cells were run, not the order they appear. That is a genuine hazard and it is measurable.

    Notebooks are excellent for exploration: you see intermediate output, you iterate on one step without re-running the rest, and the narrative and the code live together. They also have one structural problem, which is that the visible order of cells and the order they executed are different things.

    Take five cells that load, drop missing values, scale a column, filter out large values and take a mean. Read top to bottom they are unambiguous. The demo runs every possible execution order and classifies the outcome.

    Every execution order of a five-cell notebook all 120 permutations run against real data, and classified
    ERRORED0on an undefined name
    RIGHT ANSWER0
    RAN CLEANLY, WRONG0no error at all
    RESULT0

    The classification is the point. Of 120 orderings, 96 fail loudly on an undefined name — those are harmless, because you find out immediately. Four reproduce the intended answer. Twenty run without a single error and give a different answer, and there is nothing in the output to distinguish them from the correct ones.

    The everyday version is worse than the permutation

    Nobody runs cells in a random order. What people do constantly is re-run one cell — tweak the scaling factor, run it again, see the output. Switch the demo to that scenario.

    Running the scaling cell twice gives a mean of 104.00 against the correct 102.67. That looks like a rounding difference and it is not: the row count went from 12 to 6, because the doubled values pushed half the data past the filter. The summary statistic barely moved while half the dataset vanished, which is precisely why nobody notices.

    Four habits remove most of this, and none of them requires giving up notebooks.

  1. Restart and run all before believing a result. If it does not survive that, it was never a result. This is the single highest-value habit in the chapter.
  2. Make cells idempotent where you can. df2 = df.assign(x=df.x * 2) can run twice harmlessly; df["x"] *= 2 cannot. New name rather than in-place mutation is the whole trick, and it is the same argument the Data Engineer unit makes about pipeline writes.
  3. Keep the load cell cheap or cached, because "restart and run all" only becomes a habit if it takes seconds rather than minutes.
  4. Move settled code into a module and import it. Then the notebook holds the narrative and the logic is testable, which is chapter 21.

    5. WHERE TO WORK

    JupyterLab, Colab and VS Code

    Three environments with genuinely different trade-offs, and it is normal to use more than one.

    JupyterLab

    Local, runs on your machine and your data. Best notebook experience, and the standard for exploratory work. No setup beyond a pip install, and the data never leaves your laptop — which is sometimes the deciding factor.

    Google Colab

    Nothing to install, free compute including GPUs, trivially shareable. Excellent for learning and for anything you want somebody else to be able to run. Its costs are real: your data goes to Google, sessions expire and lose state, and the installed package versions are not yours to control.

    VS Code

    Runs notebooks and ordinary Python side by side, with a debugger, git integration and a proper editor. The best answer once an analysis stops being exploratory, and the natural home for chapter 21's move from notebook to module.

    Two things worth checking before using a hosted notebook for work

    Whether your organisation permits the data to leave its own systems, which is frequently a firm no for anything containing personal or commercial data. And whether the analysis needs to be reproducible — a hosted environment whose package versions change underneath you cannot give you the same answer next quarter, which matters as soon as anyone acts on the result.

    GETTING GOING

    A working setup in five commands

    If you take nothing else operational from this chapter, take this.

    first_project.sh
    mkdir sales-analysis && cd sales-analysis   # one directory per analysis
uv init                                      # or: python -m venv .venv
uv add pandas numpy matplotlib seaborn jupyterlab
uv run jupyter lab                           # opens in the browser
# commit pyproject.toml and uv.lock; do not commit .venv

    And the first cell of any new notebook, which saves more time than it looks like it should:

    cell_one.py
    import pandas as pd
import numpy as np
import matplotlib.pyplot as plt

# make the environment reproducible and the output readable
pd.set_option("display.max_columns", 50)
pd.set_option("display.width", 160)
rng = np.random.default_rng(42)      # seeded, so results repeat

print(pd.__version__, np.__version__)   # record what actually ran

    The last line is the one people leave out. Recording the library versions the analysis ran under turns "this used to give a different number" from a mystery into a two-minute check — and chapter 6 makes the case for the seeded generator properly.

    Recap

    What to take from this chapter

    1. Python is a slow language around fast libraries. Everything in chapter 4 about whole-column operations follows from that.
    2. Its real contributions are one language across the whole path, and reviewable analysis. For a single aggregate over a large table, SQL is better.
    3. One shared install can hold one version of each package, and projects disagree. Two projects conflict 10% of the time, five 62%, eight 93%.
    4. Pinning is the driver, not project count. At eight projects, 15% pinned requirements conflict 41% of the time and 60% pinned conflict 100%.
    5. Isolation is always satisfiable and costs disk. Eight environments at 420 MB is 3.3 GB.
    6. pip installs, venv isolates, conda handles non-Python dependencies, uv does both quickly with a lockfile.
    7. A lockfile is not pip freeze. One records a resolved reproducible set; the other records what you happen to have.
    8. Of 120 notebook orderings, 96 error, 4 are right and 20 run cleanly with a wrong answer. The silent twenty are the problem.
    9. Re-running one mutating cell changed the mean from 102.67 to 104.00 and the row count from 12 to 6. The statistic barely moved while half the data vanished.
    10. Restart and run all before believing a result, and prefer a new name over an in-place mutation so cells can run twice safely.
    11. Record the library versions the analysis ran under. It converts a future mystery into a two-minute check.
