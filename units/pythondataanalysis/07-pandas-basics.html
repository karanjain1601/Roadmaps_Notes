CHAPTER 07

Pandas: Series, DataFrame and the index

A NumPy array is values. A Pandas Series is values with labels, and every operation respects the labels. That is the whole difference, it is why Pandas exists, and it is the source of both the most useful behaviour in this unit and the two most confusing ones.

    TWO OBJECTS

    Series and DataFrame

    One is a labelled column. The other is a set of labelled columns sharing one index. Everything else follows.

    objects.py
    s = pd.Series([10, 20, 30], index=["a", "b", "c"], name="revenue")
s["b"]          # 20      by label
s.iloc[1]       # 20      by position
s.index         # Index(['a', 'b', 'c'])
s.values        # array([10, 20, 30])   the underlying NumPy array

df = pd.DataFrame({"revenue": [10, 20, 30], "region": ["N", "S", "N"]})
df["revenue"]   # a Series, sharing df's index
df.dtypes       # revenue int64, region object
df.shape        # (3, 2)

    Three structural facts worth stating explicitly, because a lot of confusion downstream is really confusion about these.

    A DataFrame is columns, not rows
    Each column is a separate typed array. That is why a column has a dtype and a row does not, why selecting a row gives you a Series of mixed types, and why chapter 4's apply(axis=1) is slow — it has to build a mixed-type object for every row from columns stored separately.
    All columns share one index
    The index is a property of the frame, not of each column. So df["a"] + df["b"] is guaranteed to align, and a Series from somewhere else is not.
    Underneath, it is still NumPy
    .values or .to_numpy() gives you the array, and chapter 5's dtype and view rules apply unchanged. Dropping to NumPy is the escape hatch when you want positional semantics and no alignment.

    THE DISTINCTIVE PART

    The index is a real object

    Not a row number. A labelled axis that operations respect, that persists through filtering, and that can be almost anything.

    By default the index is 0, 1, 2, …, which makes it look like a row number and encourages people to treat it as one. It is not. It is a set of labels that happen to be integers, and the difference shows the moment you filter.

    index.py
    big = df[df["revenue"] > 100]
big.index          # [3, 7, 11, ...]  — the ORIGINAL labels, with gaps

big.iloc[0]        # the first row of the filtered frame
big.loc[3]         # the row labelled 3
big.loc[0]         # KeyError — label 0 was filtered out

big = big.reset_index(drop=True)      # renumber 0..n-1, discarding the old labels
big = big.reset_index()               # or keep them as a column called "index"

df = df.set_index("order_id")         # use a meaningful column as the index
df.set_index(["region", "month"])     # a MultiIndex, one level per column
    When to set a meaningful index, and when not to

    Set one when the label is what you look things up by — a date for a time series, an identifier you join on repeatedly, a two-level region-and-month key. Lookups become fast and alignment becomes automatic and correct.

    Leave the default for ordinary tabular analysis. A meaningful index makes groupby, merge and reset_index calls slightly more awkward, and if you are not exploiting the labels you are paying that cost for nothing.

    The one thing not to do is rely on the default index meaning row position, because the next section shows what that costs.

    Two properties worth knowing about. An index need not be unique — df.index.is_unique tells you, and a duplicated index makes .loc return multiple rows where you expected one, which is a genuinely baffling bug the first time. And a sorted index enables fast lookups and slicing by range: df.loc["2024-03":"2024-06"] works on a sorted DatetimeIndex and is a performance cliff on an unsorted one.

    THE BEHAVIOUR THAT DEFINES PANDAS

    Automatic alignment

    Arithmetic between two Series matches them on the index, not on position. This is a feature, and it is the source of the NaNs that appear from nowhere.

    Add two NumPy arrays and element 0 meets element 0. Add two Series and label "a" meets label "a", wherever each of them sits. Where a label exists in one and not the other, the result is NaN.

    MISSING0NaN in the result
    CORRECT VALUES0
    VERDICT—

    The three scenarios cover the three ways this shows up, and they are not equally dangerous.

    1. Offset indexes: loud. Two ten-element Series indexed 0–9 and 5–14 produce a fifteen-row result with 5 valid values and 10 NaN. Alarming, obvious, and easy to fix once seen.
    2. Shuffled order: alignment saving you. The same labels in a different order give a perfect result — index 0 gets 110, which is 10 + 100, proving it matched by key rather than position. This is the behaviour you want and would have to write by hand otherwise.
    3. Assigning into a filtered frame: silent. Twenty rows, twenty values land, zero NaN — and zero correct. Because the filtered frame's index was reset to 0–19, every row aligned against the wrong original row. Nothing is missing, so nothing signals it.
    The third case is the one that costs you

    The pattern is ordinary: filter a frame, reset the index because the gaps look untidy, then assign a Series computed from the original. Every row receives a plausible number and every one of them belongs to a different row.

    Two habits prevent it. Do not reset the index unless you have a reason — the gaps are information, and they are what makes the assignment correct. And when you intend positional assignment, say so with .values, which strips the labels and makes the intent explicit rather than accidental.

    A useful diagnostic: after any operation combining two objects, result.isna().sum() costs nothing and catches the loud version immediately. And a.index.equals(b.index) answers the question directly before you combine them at all.

    SELECTING

    loc, iloc and the bracket

    Three ways to select, with different rules. Using the right one deliberately removes a whole category of bug.

    What each accessor does, and its one surprise
    WrittenSelects bySlice endSurprise
    df["col"]Column name—A single bracket takes a column, but df[0:3] takes rows
    df.loc[rows, cols]LabelInclusivedf.loc[2:5] returns six rows, not four
    df.iloc[rows, cols]PositionExclusiveIgnores the index entirely, like a NumPy array
    df.at[row, col]Label, single cell—Much faster than loc for one scalar
    selecting.py
    df.loc[3, "revenue"]                 # label 3, column revenue
df.loc[df["region"] == "N", ["revenue", "date"]]     # mask + column list
df.iloc[0]                           # the first row, whatever its label
df.iloc[-1]                          # the last row — loc cannot do this
df.loc[:, "revenue":"date"]          # a slice of columns, inclusive at both ends

# the bracket is inconsistent, which is why loc and iloc exist
df["revenue"]        # a column
df[0:3]              # three ROWS — the same syntax, a different axis
df[["a", "b"]]       # two columns
df[df.x > 5]         # rows matching a mask
    The two rules that settle it

    Inclusive label slicing is deliberate and correct. df.loc["2024-01":"2024-03"] including March is what you want from a date range; excluding the endpoint would be surprising. It is only jarring because integer labels look like positions.

    Use loc and iloc explicitly, and reserve the bare bracket for selecting columns. df[0:3] silently means rows while df["a"] means a column, and mixing the two in one notebook is how you end up reading code you cannot predict.

    THE WARNING EVERYBODY IGNORES

    Chained assignment

    SettingWithCopyWarning is telling you that your assignment did nothing. It is worth reading once.

    This is chapter 5's view-against-copy distinction, arriving where it actually bites. A boolean mask returns a copy. So df[df.x > 5] is a new object, and assigning into it writes into a temporary that is discarded a moment later.

    Three ways to write the same assignment 2,000 rows, and how many actually change
    ROWS MATCHING0meant to change
    ROWS THAT CHANGED0
    WARNING RAISED—
    RESULT—

    The measurement is unambiguous. With a threshold of 5, 875 rows match and 0 change under either chained form. Under .loc, all 875 change. The chained versions are silent no-ops, and the only signal is a warning that scrolls past.

    The rule, and what changed recently

    One indexing operation, not two. df.loc[mask, "col"] = value is a single operation on df itself, so Pandas knows what you meant. df[mask]["col"] = value is two operations: produce a copy, then assign into it.

    Historically this was worse than a no-op, because whether it worked depended on internal memory layout — it might modify the original, and might not. Copy-on-write, the default from Pandas 3.0, makes it deterministic: chained assignment now reliably does nothing and raises a ChainedAssignmentError. Deterministically failing is a large improvement over intermittently working.

    And when you genuinely want an independent subset, say so: sub = df[df.x > 5].copy(). Then modifying sub is correct, intended, and warning-free.

    FIRST FIVE MINUTES

    Inspecting a frame you have just loaded

    Six calls, in order. This is the routine that catches most of the problems the rest of the unit is about.

    inspect.py
    df.shape                       # 1. how much is here?
df.dtypes                      # 2. object where a number belongs? — chapter 2
df.head(), df.sample(5)        # 3. sample, not just head: the top is often unusual
df.isna().sum()                # 4. missing, per column — chapter 12
df.describe(include="all")     # 5. include="all" or text columns are omitted
df.memory_usage(deep=True)     # 6. deep=True or object columns are undercounted
    dtypes before anything else
    Chapter 2 measured what an object dtype does to a numeric column: a top-ten list sharing four entries with the truth, and a max that returns a plausible wrong number. This is a five-second check that catches it.
    sample rather than head
    The first rows of a file are frequently unrepresentative — a header artefact, the oldest records, a test account. A random sample shows you the middle of the distribution, which is what you are about to analyse.
    include="all" on describe
    Without it, text and categorical columns are silently omitted, so the columns most likely to have a type problem are the ones missing from your summary. With it you also get count, unique, top and frequency, which is exactly what you want for a categorical.
    deep=True on memory_usage
    Without it, an object column reports only the pointer array — 8 bytes a row rather than the ~60 the strings actually cost. Chapter 5 measured a 66-fold saving from converting such a column to a category, and you cannot see the opportunity without deep=True.
    One more worth adding to the routine

    df.index.is_unique. A duplicated index makes .loc return several rows where you expected one, makes alignment behave in ways that look random, and turns a later merge into chapter 8's row explosion. It is one boolean and it saves an afternoon.

    Recap

    What to take from this chapter

    1. A DataFrame is columns, not rows. That is why a column has a dtype, a row does not, and apply(axis=1) is slow.
    2. All columns share one index, so columns of the same frame always align and a Series from elsewhere may not.
    3. The index is labels, not row numbers, and the difference shows the moment you filter.
    4. Set a meaningful index when you look things up by it; otherwise leave the default and do not rely on it meaning position.
    5. Check index.is_unique. A duplicated index makes .loc return several rows and turns a merge into a row explosion.
    6. Arithmetic aligns on labels. Two ten-element Series indexed 0–9 and 5–14 give fifteen rows: 5 valid, 10 NaN.
    7. Alignment is usually saving you. The same labels shuffled give a perfect result, matched by key rather than position.
    8. The dangerous case is silent: assigning into a reset-index filtered frame filled all 20 rows with 0 correct and 0 NaN. Nothing missing, everything wrong.
    9. Do not reset the index without a reason, and use .values when you mean positional.
    10. loc is by label and inclusive at both ends; iloc is by position and exclusive. Reserve the bare bracket for columns.
    11. Chained assignment is a silent no-op: 875 rows matched, 0 changed. df.loc[mask, "col"] = value changed all 875.
    12. Copy-on-write makes it deterministically fail rather than intermittently work, which is an improvement. Use .copy() when you want an independent subset.
    13. Six inspection calls: shape, dtypes, sample, isna, describe with include="all", memory_usage with deep=True.
