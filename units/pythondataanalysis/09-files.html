CHAPTER 09

Files and formats

CSV has no type system, so every column's dtype is a guess made from the characters in it. Most of the time the guess is right. This chapter is about the times it is not, including a single missing value in an identifier column that merged 16,575 distinct entities into 470.

    THE FORMAT

    CSV, and what it does not specify

    Universally supported, and it defines almost nothing. Every one of these has to be inferred or told.

    What a CSV file does not tell you
    UnspecifiedCommon valuesHow to say it
    TypesAnythingdtype={"id": "string"}
    SeparatorComma, semicolon, tab, pipesep=";" or sep=None to sniff
    EncodingUTF-8, Latin-1, Windows-1252encoding="latin-1"
    Decimal markPoint or commadecimal=","
    Missing markersEmpty, NA, -, NULL, 999na_values=["-", "999"]
    Date formatAnyparse_dates=, date_format=
    QuotingVaries, and often brokenquotechar, escapechar
    The habit that removes most of this chapter

    Declare what you expect rather than inspecting what you were given:

    pd.read_csv(path, dtype={"user_id": "string", "revenue": "float64"}, parse_dates=["order_date"])

    If revenue contains something unparseable, this raises at the point of reading — which is the loud failure you want, arriving where you can still do something about it. Without the declaration you get a silent object column and chapter 2's consequences: a top-ten list sharing four entries with the truth and a max that returns a plausible wrong number.

    One note on the European decimal comma, because it is the trap that catches people working across regions. A file with 1.234,56 read with default settings gives an object column, and read with decimal="," but no thousands="." gives 1.23456 — a number, of the right kind, off by a factor of a thousand. Both arguments or neither.

    THE GUESSING

    How type inference fails

    Pandas scans a column's values and picks a dtype. There are four distinct ways that goes wrong, and only one of them warns you.

    THE FIX—

    Four failure modes, in increasing order of how much they cost you.

    1. Promotion to float. One missing value in an integer column makes it float64, because the classic integer dtype cannot hold NaN. Usually harmless — unless the column is an identifier.
    2. Falling back to object. A thousand separator, a currency symbol, or an NA marker pandas does not recognise. Note that "N/A" is in pandas' default list and "unknown" is not, so two columns with identical intent get different dtypes.
    3. Silent truncation. "007" parses cleanly as 7. Nothing warns, because nothing went wrong — the zeros were simply never data as far as the parser was concerned.
    4. Identifier collision. The expensive one. Twenty thousand large identifiers promoted to float64 collapsed from 17,045 distinct values to 470, because past 253 consecutive integers are no longer distinguishable — chapter 5's limit, arriving through a single blank cell.
    Chunked inference: why the same column can have two dtypes

    Pandas reads large files in blocks and infers per block. Turn chunking on in the demo and put the awkward value late: nine blocks infer int64 and one infers object, so the resulting column holds a mixture and the DtypeWarning appears. Operations on that column then behave differently depending on which rows they touch.

    low_memory=False reads the whole column before deciding, which is why it fixes this — and it is a memory trade rather than a free win, which is the next section. Declaring the dtype outright avoids both.

    BEFORE THE TYPES

    Encodings, separators and line endings

    Three problems that stop a file loading at all, which is preferable to the ones above.

    Encoding
    A UnicodeDecodeError means the file is not UTF-8. Almost always it is cp1252 (Windows) or latin-1, and encoding="latin-1" never fails because every byte is a valid character in it — which is both convenient and a warning, since it will happily produce mojibake rather than an error. Prefer encoding="utf-8-sig" first, which handles the byte-order mark Excel writes.
    Separator
    A file loading as a single column means the separator is wrong. sep=None, engine="python" sniffs it, which is convenient for exploration and worth replacing with the actual value once you know it, because sniffing can differ between files.
    Embedded newlines
    A quoted field containing a line break is legal CSV and breaks naive line-splitting. Pandas handles it correctly; the reason to know is that a row count from wc -l will disagree with len(df), and that disagreement is information rather than a bug.
    Look at the bytes before debugging the parser

    Two minutes with the raw file answers most loading questions faster than any argument to read_csv:

    with open(path, "rb") as f: print(f.read(400))

    Reading as bytes shows you the actual separator, whether there is a BOM (\xef\xbb\xbf at the start), what the line endings are (\r\n or \n), and whether the first line is really a header. Guessing at parser arguments without looking is slower than looking.

    FITTING IT IN

    Memory, and four ways to use less

    A CSV on disk is text. In memory it is typed, indexed and sometimes far larger. The strategies for reducing that solve two different problems.

    Peak memory under five reading strategies 8 million rows, 40 columns, six of them text
    TOTAL FOOTPRINT0if held at once
    PEAK MEMORY0the number that matters
    AGAINST NAIVE0peak reduction
    FITS IN BUDGET—

    The result worth understanding is that these are two different wins, not a ranking. Reading 8 million rows naively takes 5,096 MB. Declaring narrower dtypes gets it to 4,059 MB and converting text to categories to 1,129 MB — both reduce the footprint of what you hold. Chunking does something different: it bounds peak memory to a single chunk, 14 MB, while the total you process is unchanged. And usecols reduces the total to 107 MB by never reading the other columns at all.

    Which to reach for, in order

    usecols first. It is the only strategy that avoids reading data rather than making it smaller, and analyses typically need a handful of the columns available. It also speeds up parsing, which none of the others do.

    Then dtype and category, which shrink what you kept. Chapter 5 measured a 66-fold saving on a low-cardinality text column, and this is where you collect it.

    Then chunksize, when the data genuinely does not fit however small you make it. It changes how you write the analysis — you aggregate per chunk and combine — so it is a larger change than the others and worth avoiding until needed.

    They compose. Combining chunking with usecols is better than either, and the demo's last option shows it.

    TWO OTHER SOURCES

    Excel and JSON

    Both arrive constantly and both have one characteristic problem.

    excel_json.py
    # Excel: name the sheet, and skip the decoration
pd.read_excel(path, sheet_name="Q3 Data", skiprows=3, usecols="B:H")
pd.read_excel(path, sheet_name=None)      # a dict of every sheet
pd.ExcelFile(path).sheet_names            # look before you read

# JSON: flat records
pd.read_json(path)                        # works only if it is already tabular

# nested JSON needs explicit flattening
pd.json_normalize(records,
    record_path=["orders", "lines"],      # the list to explode into rows
    meta=["customer_id", ["address", "city"]])   # fields to carry down

    Excel: the layout is not a table

    Title rows, merged cells, blank spacer columns, totals rows in the middle of the data, and a footnote at the bottom. skiprows and usecols handle the top and sides; a totals row inside the data has to be filtered out, and it will otherwise be double-counted in every aggregate.

    Also: Excel dates. A column of dates can arrive as serial numbers, and a column of numbers can arrive as dates because somebody's locale reformatted it. Always check dtypes.

    JSON: the shape is not flat

    read_json works only for already-tabular JSON. Anything nested needs json_normalize, and the decision you are making there is chapter 8's grain question: exploding a list of order lines gives one row per line, so any order-level measure carried down is now repeated and will inflate if summed.

    That is the same fan-out the previous chapter measured, arriving from a file rather than a join.

    The totals-row problem is worth checking for explicitly

    A spreadsheet exported by a human frequently contains subtotal rows, because they were useful to the person reading it. Loaded into a frame they are ordinary rows, and every sum you compute afterwards is inflated by roughly a factor of two — enough to notice, and not obviously enough to be sure.

    The cheap test: does the column total equal twice a plausible number? And does any row have a null in the identifier column? Subtotal rows usually do.

    THE ALTERNATIVE

    Parquet, and why to switch

    Everything in this chapter is a consequence of CSV having no schema. Parquet has one, and that removes the whole category.

    CSV against Parquet, for the same data
    CSVParquet
    TypesInferred, per readStored in the file
    Size on diskBaselineTypically 5–10× smaller
    Reading four of forty columnsParses all fortyReads only four
    Read speedBaselineOften 10× faster or more
    Categories, timezones, nullable intsLost on writePreserved
    Human-readableYesNo
    Opens in ExcelYesNo
    parquet.py
    df.to_parquet("sales.parquet")                     # types preserved
pd.read_parquet("sales.parquet", columns=["date", "revenue"])   # reads two columns

# the pattern worth adopting: parse the CSV once, work from Parquet after
raw = pd.read_csv("sales.csv", dtype=SCHEMA, parse_dates=["date"])
raw.to_parquet("sales.parquet")        # everything below is now fast and typed
    The habit, not the format

    Parse the awkward file once, deliberately, and save the result. Do the encoding argument, the dtype declaration and the date parsing a single time, write Parquet, and every subsequent read is fast, correctly typed and free of everything in this chapter.

    Keep CSV for what it is genuinely good at: handing data to a person, or to a system whose capabilities you do not know. Those are real requirements and they are not a reason to re-parse a 4 GB file on every run.

    Two smaller notes. Parquet needs pyarrow installed, which is one pip install and is worth it regardless — pandas increasingly uses Arrow internally. And Feather is worth knowing for the narrow case of caching an intermediate result between steps of your own analysis: faster still, and not intended as a storage format.

    Recap

    What to take from this chapter

    1. CSV specifies types, separator, encoding, decimal mark, missing markers, dates and quoting: none of them. Declare what you expect rather than inspecting what you got.
    2. decimal="," without thousands="." turns 1.234,56 into 1.23456 — a plausible number off by a thousand.
    3. One missing value promotes an integer column to float64, because the classic int dtype cannot hold NaN.
    4. "N/A" is in pandas' default NA list and "unknown" is not, so two columns with identical intent get different dtypes.
    5. "007" parses cleanly as 7. Nothing warns, because as far as the parser is concerned nothing went wrong.
    6. 20,000 large identifiers promoted to float collapsed to 470 distinct values — 16,575 collisions, from one blank cell.
    7. Chunked inference gives one column two dtypes: nine blocks int64 and one object. low_memory=False fixes it at a memory cost; declaring the dtype avoids both.
    8. Read the first 400 bytes before debugging the parser. It shows the separator, the BOM, the line endings and whether the header is real.
    9. usecols first, then dtype and category, then chunksize. Only usecols avoids reading data rather than shrinking it.
    10. Chunking bounds peak memory (14 MB) while usecols reduces the total (107 MB). Different wins, and they compose.
    11. Excel arrives with title rows, merged cells and subtotal rows in the middle of the data, which inflate every aggregate. Check for nulls in the identifier column.
    12. Exploding nested JSON is a grain decision, and carrying a parent-level measure down repeats it — chapter 8's fan-out from a file rather than a join.
    13. Parse the awkward file once and write Parquet. Types preserved, 5–10× smaller, column selection on read.

    ONE THING TO TRY

    Take the CSV you read most often and add a dtype= declaration for its identifier columns as "string". If anything downstream changes, it was wrong before.
