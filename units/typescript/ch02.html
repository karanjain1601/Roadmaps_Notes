CHAPTER 02

Setting it up, and the flags that matter

There are over a hundred compiler options and about a dozen that change how you write code. This chapter is those, one at a time, with the code each one rejects — because strict: true is eight separate decisions and knowing which is which is what lets you adopt them on an existing codebase.

1A config worth starting from

Short, opinionated, and every line has a reason.

tsconfig.json JSON
{
  "compilerOptions": {
    // What the output must run on. Sets the available library
    // types and how much gets downlevelled.
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],

    // Modern module resolution. "bundler" if a bundler resolves
    // for you; "nodenext" for Node. Both understand package
    // exports maps, which the legacy "node" mode does not.
    "module": "ESNext",
    "moduleResolution": "bundler",

    // The eight flags in section 2, plus the two in section 3
    // that ought to be in strict and are not.
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,

    // Correctness of the module graph, not of your types.
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,

    // Tidiness. Errors rather than warnings, so CI catches them.
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,
    "noImplicitOverride": true,

    // If a bundler emits and tsc only checks:
    "noEmit": true
  },
  "include": ["src"]
}
skipLibCheck is a pragmatic lie
It stops the compiler type-checking .d.ts files in node_modules. Strictly you are skipping real checks; practically two dependencies with incompatible library types produce errors you cannot fix, and everyone turns it on. Know that you have.
verbatimModuleSyntax earns its place
It requires import type for type-only imports and then emits imports exactly as written. That removes a whole class of confusion about which imports survive erasure — Chapter 1's demo — and makes single-file transpilers correct by construction.
Do not set target to ESNext casually
It means "whatever this compiler version thinks is newest", so an upgrade can silently change your output. Name a year.
Extend a base if you would rather not decide
The @tsconfig/* packages publish maintained bases per target and runtime. "extends": "@tsconfig/node22/tsconfig.json" and then override.

The adoption order that works

On an existing untyped codebase, turning on strict at once produces thousands of errors and gets reverted. Do it in this order instead: noImplicitThis and alwaysStrict first, because they usually produce almost nothing; then noImplicitAny, which is a lot of work and mostly mechanical; then strictNullChecks, which is the big one and the one worth the effort — it is where the real bugs are. strictFunctionTypes, strictBindCallApply and strictPropertyInitialization tend to be small. Keep each step a separate pull request.

3Two flags outside strict that belong on

Both close holes described in Chapter 1. Neither is in strict, for compatibility reasons.

What they change TypeScript
// noUncheckedIndexedAccess — index access might miss
const names: string[] = ['ada'];
const first = names[0];
//    off: string          — and names[99] is "string" too, and it is not
//    on:  string | undefined  — which is the truth

const byId: Record<string, User> = {};
byId['nope'].name;
//    off: compiles, throws at runtime
//    on:  Object is possibly 'undefined'

// exactOptionalPropertyTypes — optional means absent
interface Opts { retries?: number }
const o: Opts = { retries: undefined };
//    off: allowed — so "retries" in o is true, with no value
//    on:  rejected — write { retries?: number | undefined } if
//         you genuinely mean "may be present and undefined"
Why noUncheckedIndexedAccess is not in strict
It is noisy in loops where you know the index is valid, and adding it to strict would have broken vast amounts of code. It is nonetheless the single most honest flag available: array and record access genuinely can miss, and the default type says otherwise. Turn it on for new projects and accept the occasional non-null assertion in a loop.
exactOptionalPropertyTypes matters when you diff objects
Without it, "not set" and "set to undefined" are the same type and different at runtime — 'retries' in o distinguishes them, and Object.keys sees a difference. Any code that spreads, merges or serialises options is affected.
Do not turn on noImplicitAny's cousin by accident
useUnknownInCatchVariables is inside strict and makes catch (e) give you unknown rather than any. That is correct — a thrown value can be anything — and it means you must narrow before using it. Chapter 3.

Pick by who resolves at runtime
"bundler" if a bundler does — Vite, esbuild, webpack, a framework. "nodenext" if Node does. Those two are the only current answers; "node" is the pre-2015 CommonJS algorithm and cannot see exports maps, which is the cause of most "this package has no types" reports about packages that do.
nodenext requires extensions in relative imports
import './util.js' — with .js, from a .ts file, because that is what will exist at runtime. It looks wrong and is correct. allowImportingTsExtensions lets you write .ts instead, but only with noEmit.
Path aliases are a compiler fiction
paths tells the type checker how to resolve @/lib/x. It does not rewrite the emitted import, so your bundler or runtime needs the same aliases configured independently. Mismatched alias config is a common and confusing failure.
Dual-package hazard is real
A package shipping both CommonJS and ESM can end up loaded twice, giving you two copies of a class and instanceof checks that fail. Chapter 19 has more; the mitigation is to prefer one format per dependency tree.

5How to actually run it

Four arrangements, and the distinction that matters in all of them.

Transpiling is not checking

Every fast tool — esbuild, SWC, Vite, Node's own type stripping — deletes the types without reading them. That is why they are fast. It also means your development server happily runs code with type errors in it, and nothing tells you until you run the checker. Treat tsc --noEmit as a separate mandatory job, in your editor and in CI. This is the most common way a team ends up believing they have types and shipping without them.

ArrangementNotes
tsc emitsSimplest and slowest. Right for a published library, where you need .d.ts files anyway. Add declaration and declarationMap.
Bundler emits, tsc --noEmit checksThe common arrangement. Fast rebuilds, and checking is a parallel job. Set noEmit so the two cannot fight.
tsx or ts-nodeRunning a script directly. tsx uses esbuild and does not check.
Node running .ts directlyRecent Node versions strip types natively. Convenient, zero checking, and it restricts you to syntax that can be erased without knowing types — so no enum, no namespace, no parameter properties. Chapter 1's demo shows exactly why those three are the exceptions.

6Check yourself

Five questions.

1. Why does strict: true being eight flags matter?

Because it lets you adopt it gradually on a codebase where turning it all on produces thousands of errors and gets reverted. Each flag is independent, so you can sequence them: noImplicitThis and alwaysStrict first since they usually produce almost nothing, then noImplicitAny which is a lot of mechanical work, then strictNullChecks which is the large one and the one carrying nearly all the value — it is where the actual bugs are. The remaining three are typically small. One flag per pull request keeps each review comprehensible, which is what makes the migration finish.

2. What is wrong with the type of names[99] by default?

It is string, and the value is undefined. Index access on an array or a Record is typed as the element type with no allowance for the index missing, which is one of the deliberate unsoundnesses from Chapter 1 — so byId['nope'].name compiles and throws. noUncheckedIndexedAccess makes it string | undefined, which is the truth. It is not part of strict because it is noisy inside loops where the index is provably valid and would have broken enormous amounts of existing code, but for a new project it is the single most honest flag available.

3. Your dev server runs the app and CI fails with type errors. How?

Because the dev server transpiles rather than checks. esbuild, SWC, Vite and Node's native type stripping all delete annotations without reading them — that is precisely why they are fast — so code with type errors runs perfectly locally. Type checking is a separate job: tsc --noEmit, in your editor and as a required CI step. This is the commonest way a team ends up believing it has types and shipping without them, and the symptom is exactly this: everything works until someone runs the checker.

4. Which moduleResolution should you use, and why does "node" cause trouble?

"bundler" if a bundler resolves at runtime, "nodenext" if Node does. Those are the only current answers. "node" is the pre-2015 CommonJS algorithm and cannot read a package's exports map, so a modern package that publishes its types through exports appears to have none — which produces a stream of "could not find a declaration file" errors about packages that ship perfectly good types. One related surprise worth knowing: under nodenext, relative imports need the .js extension even from a .ts file, because that is what exists at runtime.

5. What do paths aliases not do?

They do not rewrite the emitted import. paths tells the type checker that @/lib/x means src/lib/x, and nothing more — the output still says @/lib/x, so whatever loads that code needs the same alias configured independently, whether that is your bundler, a runtime loader, or Node's own resolution. A mismatch is confusing precisely because the types are all correct and the editor is happy: the failure is at run time with a module-not-found. Frameworks that generate both configs from one source hide this, until you step outside them.
