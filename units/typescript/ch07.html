CHAPTER 07

Type predicates and assertion functions

Chapter 6's narrowing all came from checks the compiler recognises. Move a check into a function and it stops recognising anything — so you tell it what the function proves. And then it believes you, without ever looking at the body.

1The problem

A perfectly good check, extracted into a function, stops working.

Same logic, different outcome TypeScript
// Inline: the compiler reads the check and narrows.
if (typeof v === 'string') v.toUpperCase();      // fine

// Extracted: it sees a function returning boolean and learns nothing.
function isString(x: unknown) { return typeof x === 'string'; }
if (isString(v)) v.toUpperCase();                // error — v is still unknown

// The fix: declare what a true result proves.
function isString2(x: unknown): x is string {
  return typeof x === 'string';
}
if (isString2(v)) v.toUpperCase();               // fine

// Read `x is string` as: "if this returns true, treat x as string".
// The parameter named before `is` must be one of this function's
// own parameters — you cannot make a claim about anything else.
It narrows in both directions
A false result narrows the else branch too, removing string from the union — the same as the negated discriminant in Chapter 6.
Methods can be predicates
isValid(): this is ValidForm narrows this, which is occasionally very tidy on a class.
Modern inference sometimes does it for you
Recent compiler versions can infer a predicate from a simple function whose body is a single narrowing check on a parameter. Useful, and worth writing the annotation anyway: it documents the intent and it does not silently stop working when the body grows.

2The compiler never reads the body

Verdict—

A wrong predicate is worse than a wrong cast

An as assertion is visible at the site where the lie is told, and a reader knows to be suspicious of it. A predicate hides the lie inside a function with a reassuring name, and then every call site inherits it — so one careless return true unchecks a dozen places, none of which look wrong. Predicates are a genuine hole in the type system, the same category as as in Chapter 21, and they deserve the same scrutiny: review the body, and prefer delegating to something that actually validates.

3Assertion functions

Narrowing that persists after the call, rather than only inside a branch.

Two forms, and the declaration requirement TypeScript
// asserts x is T — throws if not, and narrows everything AFTER.
function assertIsUser(v: unknown): asserts v is User {
  if (!isUser(v)) throw new Error('not a user');
}

assertIsUser(data);
data.name;                     // User from here on — no if, no block

// asserts x — the truthiness version, for non-null assertions
function assert(cond: unknown, msg?: string): asserts cond {
  if (!cond) throw new Error(msg ?? 'assertion failed');
}

assert(user, 'user is required');
user.name;                     // user is no longer possibly undefined

// THE CATCH that costs people an hour: an assertion function
// must have an EXPLICIT type annotation at every reference.
// This does not work:
const assert2 = (c: unknown): asserts c => { … };   // error
// Assertions require every identifier they are called through to
// have an explicit type, so a plain arrow-function const fails.
// Use a function declaration, or annotate the const:
const assert3: (c: unknown) => asserts c = (c) => { … };   // fine
Predicate or assertion?
A predicate when both outcomes are normal and you want to branch. An assertion when the wrong type is a bug and continuing is meaningless — which reads better than if (!isUser(x)) throw repeated at every entry point.
Assertions are erased, like everything else
The throw is real and the narrowing is not. So an assertion function is the honest version of a non-null assertion: same compile-time effect, plus an actual runtime check and a message.
Node has one built in
node:assert's ok is typed as an assertion, so assert.ok(x) narrows. Handy, and it throws an AssertionError which you may not want in production paths.

4Four helpers worth having

Small, reusable, and each solves something you will otherwise write badly.

The standard set TypeScript
// 1. Remove null and undefined from a collection, with the type
//    following along. The single most useful predicate there is.
export function isDefined<T>(v: T | null | undefined): v is T {
  return v != null;
}
const users = maybeUsers.filter(isDefined);        // User[], not (User|null)[]

// 2. Narrow unknown to something indexable, so you can look inside
//    without reaching for `any`.
export function isRecord(v: unknown): v is Record<string, unknown> {
  return typeof v === 'object' && v !== null && !Array.isArray(v);
}

// 3. Prove a key exists, keeping the key's literal type.
export function hasKey<K extends string>(
  v: unknown, k: K
): v is Record<K, unknown> {
  return isRecord(v) && k in v;
}

// 4. Chapter 6's exhaustiveness check, named.
export function assertNever(x: never): never {
  throw new Error('unhandled variant: ' + JSON.stringify(x));
}

// And a caution on (1): the null-check version is sound. A version
// written as `return !!v` is NOT — it would also drop '' and 0,
// which are perfectly good values. That bug is invisible at the
// call site, which is section 2's whole argument.

6When a predicate is the wrong tool

Three cases, and in two of them something better exists.

When a discriminant would do
If you control the type, add a literal kind field and Chapter 6's narrowing works with no function and no possibility of lying. A predicate to distinguish your own union members usually means the union should have been discriminated.
When you are validating external data
A hand-written predicate over an API response is a validator you have to keep in step with the type by hand, and it will drift. Derive both from a schema so they cannot — Chapter 20. The schema library's own guard is a predicate too, and it is one that was generated from the type.
When the check is expensive and repeated
A predicate is called every time you branch. Validate once at the boundary, convert to a well-typed value, and stop checking — which is a design point rather than a performance one: repeated validation deep in a program usually means the boundary was in the wrong place.
And a note on the alternative that is not one
Reaching for as instead avoids writing a predicate and tells the same lie with less ceremony. If you are going to be unsound, at least be unsound in one reviewable place — which is the argument for the delegating version in section 2.

7Check yourself

Five questions.

1. Why does extracting typeof x === 'string' into a function stop it narrowing?

Because the compiler narrows by reading the check itself, and once it is behind a function call all it sees is something returning boolean — a true result tells it nothing about the argument. Declaring the return type as x is string restores it: read that as "if this returns true, treat x as a string". The parameter named before is must be one of the function's own parameters, so you cannot make a claim about anything else. It narrows in both directions, so the else branch has string removed from the union as well.

2. What does the compiler check about a predicate's body?

Nothing relevant. It checks the body is a valid function returning boolean, and it does not verify that a true result actually implies the claimed type — function isUser(v: unknown): v is User { return true } compiles. That makes a predicate a genuine hole in the type system, and a worse one than as: an assertion is visible where the lie is told and a reader knows to be suspicious, whereas a predicate hides it behind a reassuring name and every call site inherits it. Review predicate bodies with the same suspicion you would give a cast, and prefer delegating the check to something that really validates.

3. When would you use an assertion function rather than a predicate?

When the wrong type is a bug rather than a case to handle. A predicate gives you a branch; an assertion throws and then narrows everything after the call, so you write assertIsUser(data) once and use data as a User for the rest of the function, with no block. That reads far better than if (!isUser(x)) throw repeated at each entry point. One practical catch worth remembering: an assertion function must have an explicit type annotation at every reference, so a plain arrow-function const fails to compile — use a function declaration or annotate the const explicitly.

4. Why does arr.filter(x => x !== null) not remove null from the type?

Because the callback is typed as returning boolean, and filter's ordinary signature returns the same element type it was given — the compiler has no way to know that a true result means the element was not null. filter has a second overload taking a type predicate, and that is the one that narrows, which is why arr.filter(isDefined) gives you User[]. This is the clearest practical demonstration of what a predicate buys. Note the trap in writing the helper: return !!v would also discard '' and 0, and the resulting bug is invisible at every call site.

5. You are writing a predicate for an API response. What should you do instead?

Derive both the type and the check from a single schema, so they cannot drift. A hand-written predicate over external data is a validator you have to maintain in step with a type declared separately, and the day someone adds a field to the type without updating the predicate, it starts claiming things it does not check — silently, at every call site. Schema libraries invert this: you write the schema, infer the type from it, and the guard the library gives you is a predicate that was generated from the thing it validates. Chapter 20 covers the boundary properly.

Carry forward

The compiler never reads a predicate's body — it takes your word and every call site inherits it. Use an assertion when the wrong type is a bug. filter(isDefined) rather than an inline arrow. If you control the type, a discriminant beats a predicate; if the data is external, a schema does.
