CHAPTER 18

Classes

The one construct where TypeScript's type system and JavaScript's runtime semantics are genuinely entangled — some of what you write is erased, some of it emits code, and the word private means something quite a lot weaker than it appears to.

Part 5 Meeting the real world·Reading time 35 minutes·Demos four kinds of privacy, the implements trap·Prerequisites Chapters 1, 5

1What a class adds

Three things an interface cannot do, and one thing it does better.

A class declares a type and a value
class User {} introduces the type User (instances) and the value User (the constructor). That is why typeof User is the constructor type and User alone is the instance type — the one piece of syntax where the two namespaces meet visibly.
It carries an implementation
Methods, field initialisers, a constructor. An interface describes; a class does.
It can be nominal
A class with a private or #private member is not structurally compatible with anything else, even an identical class. The only exception in an otherwise structural language, and section 2's demo shows why it happens.
But an interface is better for data
If the thing has no behaviour, it is a shape, and a class buys you a constructor call and a prototype in exchange for nothing. Most "model" classes in a TypeScript codebase should be interfaces plus functions — Chapter 5's argument, and Chapter 17's branded types are usually the better tool for the invariant you were reaching for.

3Members, and the shorthand

Parameter properties, plus three modifiers with runtime consequences.

The compressed form, and what it expands to TypeScript
// PARAMETER PROPERTIES: a modifier on a constructor parameter
// declares and assigns the field. This is TypeScript-only syntax
// that emits real code — one of the few things in Chapter 1's list.
class Point {
  constructor(
    public readonly x: number,
    public readonly y: number,
    private label?: string
  ) {}
}
// expands to the field declarations plus `this.x = x` and so on.

// STATIC members belong to the constructor, not to instances.
class Counter {
  static instances = 0;
  static { /* static initialisation block, runs once */ }
  constructor() { Counter.instances++; }
}

// readonly is compile-time only — assignable in the constructor,
// erased entirely afterwards. `Object.freeze` if you need it real.

// GETTERS AND SETTERS may differ in type since TS 4.3, which is
// the idiomatic way to accept a wide input and expose a narrow one:
class Box {
  private _v = 0;
  get value(): number { return this._v; }
  set value(v: number | `${number}`) { this._v = Number(v); }
}

// And note useDefineForClassFields (on by default with modern
// targets): field initialisers now use [[Define]] semantics, which
// means a field declared without an initialiser OVERWRITES an
// inherited value with undefined. `declare x: number` opts out.

4this types

Three distinct features that share a keyword.

Polymorphic this, this parameters, this-based guards TypeScript
// 1. POLYMORPHIC this — the return type follows the subclass,
//    which is what makes fluent builders inherit correctly.
class Query {
  where(c: string): this { …; return this; }
}
class UserQuery extends Query {
  byEmail(e: string): this { …; return this; }
}
new UserQuery().where('x').byEmail('y');
// works — where() returned UserQuery, not Query

// 2. A this PARAMETER — declares what `this` must be at the call
//    site. Erased; costs nothing; catches detached methods.
function render(this: HTMLElement, ev: Event) { this.classList.add('on'); }
// with strictBindCallApply, .call/.bind/.apply are checked against it

// 3. A this-based TYPE GUARD — narrows the receiver itself.
class Result<T> {
  constructor(private v?: T, private e?: Error) {}
  isOk(): this is { value: T } { return this.e === undefined; }
}
if (r.isOk()) r.value;      // narrowed — and see Chapter 7 on
                           // why the compiler trusts you here

6Abstract classes and constructor types

Typing the thing that makes the thing.

Factories, mixins, and the abstract new constraint TypeScript
abstract class Shape {
  abstract area(): number;
  describe() { return `area ${this.area()}`; }   // concrete, inherited
}

// A CONSTRUCTOR TYPE. Note `abstract new` — without it the
// constraint rejects abstract classes, which is usually not
// what a factory wants.
type Ctor<T> = abstract new (...args: never[]) => T;

function register<T extends Shape>(c: Ctor<T>, name: string) { … }

// InstanceType goes the other way (Chapter 14):
type S = InstanceType<typeof Circle>;      // Circle

// MIXINS — a function returning a class expression. The awkward
// `new (...args: any[]) => {}` constraint is required because a
// mixin must call super() with unknown arguments.
type Constructor = new (...args: any[]) => {};

function Timestamped<B extends Constructor>(Base: B) {
  return class extends Base {
    createdAt = new Date();
  };
}
class Doc extends Timestamped(Base) {}      // Doc has createdAt

// Mixins are the one place `any` in a constraint is conventional
// rather than lazy — `never[]` breaks the super() call.

8Check yourself

Five questions.

1. What is the difference between private x and #x?

private is a compile-time check only: the field is an ordinary property at runtime, so it appears in Object.keys, it serialises with JSON.stringify, and (obj as any).x reaches it. #x is a JavaScript language feature enforced by the engine: it is genuinely inaccessible from outside the class, it does not enumerate, it does not serialise, and no cast reaches it. Both make the class nominal for assignability purposes. Prefer #x unless you need the field to be visible to a subclass, since # has no protected equivalent.

2. Why does a class with a private field stop being structurally compatible?

Because a private member is identified by its declaration site, not by its name and type. Two identical classes each declaring private id: string have members that originate in different declarations, so neither is assignable to the other — and that is deliberate, because structural compatibility would let you pass one class's instance to code that will use it as the other's and reach a private field it has no right to. It is the single exception to structural typing in the language, and it is also the cheapest way to get nominal behaviour out of a class when you want it.

3. What does implements not do?

It does not type the class. implements is a one-way check that the class satisfies the interface; it does not contextually type the members, so a method parameter with no annotation is an implicit any rather than inheriting the interface's parameter type — and under noImplicitAny that is an error, which is at least loud, but with an annotation of the wrong type it silently passes because a wider parameter is still assignable (Chapter 8's contravariance). It also does not bring across optionality or privacy. If you want the interface to drive the types, annotate the value instead: const x: Iface = { … }, or annotate each member explicitly.

4. Why abstract new (...args: never[]) => T for a constructor constraint?

abstract so the constraint accepts abstract classes, which a plain new signature rejects — usually not what a registry or factory wants, since abstract base classes are exactly the things you want to accept references to. And never[] for the parameters because of contravariance (Chapter 11's recipe): a parameter list of never[] is compatible with every parameter list, so the constraint accepts any constructor without falling back to any. The one exception is mixins, where any[] is conventional because the class expression must call super(...args) and never[] makes that call impossible.

5. When should a class be an interface plus functions instead?

When it has no behaviour worth encapsulating — which covers most "model" classes. If the thing is a bag of data that gets constructed, passed around and serialised, a class buys you a constructor call, a prototype, and a value that does not survive JSON.parse intact, in exchange for nothing the type system was not already giving you. Classes earn their place when there is real invariant-maintaining behaviour, when you want the nominal typing a private field provides, or when a framework requires them. For the invariant case specifically, Chapter 17's branded types are usually the better tool: same guarantee, no runtime object.
