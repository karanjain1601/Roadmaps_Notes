CHAPTER 20

Validation at the boundary

Every guarantee in this unit rests on the types being true, and at four specific places in every program they simply are not. What you write there decides whether a bad payload fails immediately with a precise message or four layers later with a confusing one — and in one case, whether it fails at all.

Part 5 Meeting the real world·Reading time 35 minutes·Demos where the failure surfaces, schema drift·Prerequisites Chapters 3, 7

1Where types stop

Four places, and they are the same four in every program.

BoundaryWhat the compiler believes, and why it is wrong
Network responsesres.json() returns any in older lib versions and Promise<any> still in most. Whatever you assert about it is an assumption about a server you do not control, on a deploy schedule you do not share.
StorageJSON.parse(localStorage.getItem(k)) — written by a version of your app that may be three releases old, still running in a tab someone left open.
The environmentprocess.env.X is typed string | undefined, and every augmentation that says otherwise is Chapter 19's lie.
User inputForm values, URL parameters, file contents. Typed as strings at best, and shaped by whoever is typing.

A fifth, less obvious one: any dependency without real types. A declare module 'x' stub makes every value from that library an any flowing into your program, which is the same problem wearing different clothes — Chapter 19, section 2.

The shape of it, with the type derived TypeScript
import { z } from 'zod';

const UserSchema = z.object({
  id:        z.string().uuid(),
  email:     z.string().email(),
  role:      z.enum(['admin', 'member']),
  createdAt: z.coerce.date(),           // parses the ISO string
  total:     z.number().int().nonnegative()
});

// ONE source of truth. The type is derived, so it cannot drift.
export type User = z.infer<typeof UserSchema>;

export async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new HttpError(res.status);
  return UserSchema.parse(await res.json());
  //               ↑ throws with a path and an expectation
}

// Note z.coerce.date(): the boundary is also the right place to
// convert representations. The wire has strings; your domain has
// Dates; the parser is where one becomes the other, once.

4Choosing one

Four reasonable options, and what actually differs between them.

LibraryIts argument
ZodThe default. Largest ecosystem, best documentation, integrates with everything. Version 4 substantially reduced the bundle and compile-time cost that were the main objections to version 3.
ValibotModular, so tree-shaking removes what you do not use — meaningfully smaller in a browser bundle. The API is functions rather than methods, which reads less fluently and composes more predictably.
ArkTypeSchemas written as TypeScript-like strings, with very fast validation. The most impressive type-level work of the four and the one whose error messages will most surprise you when something goes wrong.
TypeBoxProduces JSON Schema, which matters if you also need OpenAPI documents or server-side JSON Schema validation. Otherwise heavier than necessary.

The choice matters much less than making one. Any of these turns the failure in section 2 from a confusing symptom into a precise message at the boundary, and the differences between them are bundle size and taste. What matters more is the direction: the schema is the source of truth and the type is derived from it. A hand-written type validated by a hand-written guard has the drift problem in section 3 regardless of which library is absent.

5Where to validate, and where not

Once, at the edge. The temptation is to do it everywhere, and that is a different mistake.

Validate at every entry point, exactly once
One parse per boundary crossing. After that the value has a type that is actually true, and the rest of the program can rely on it — which is the whole point, and re-validating internally says you do not believe your own boundary.
Do not validate between your own functions
If formatTotal receives a User from your own code, checking it again is noise. The type system already covers that path; validation is for the places it cannot.
Parse outbound data too, in one specific case
When you are the server. Validating your own response against the schema you publish catches the moment your implementation drifts from your contract, and it is cheap in a test rather than in production.
Consider being lenient about extra fields
Most schema libraries strip unknown keys by default, which is usually right: a server adding a field should not break your client. Strict mode is for the cases where an unexpected field means something has gone genuinely wrong.
And validate the shape, not the business rules
"total is a non-negative integer" belongs in the schema. "total matches the sum of the line items" is a domain invariant and belongs in your code, where the error can say something useful.

6The environment, specifically

The boundary people most often paper over, and the cheapest one to fix properly.

Twelve lines that turn a 3am incident into a startup failure TypeScript
// src/env.ts — imported for side effect at the very top of main
import { z } from 'zod';

const EnvSchema = z.object({
  NODE_ENV:     z.enum(['development', 'test', 'production']),
  DATABASE_URL: z.string().url(),
  PORT:         z.coerce.number().int().default(3000),
  LOG_LEVEL:    z.enum(['debug', 'info', 'warn']).default('info')
});

const parsed = EnvSchema.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid environment:', z.prettifyError(parsed.error));
  process.exit(1);
}

export const env = parsed.data;      // PORT is a number here

// Everything downstream imports `env`, never `process.env`. An
// ESLint rule banning `process.env` outside this file makes that
// stick. The payoff: a missing variable stops the process at
// startup with its name, instead of surfacing as a connection
// error under load an hour later.

7Check yourself

Five questions.

1. What does await res.json() as User check?

Nothing. An assertion is a statement to the compiler, not a runtime operation, and it is erased along with every other type (Chapter 1). What it actually does is decide where you find out: the value flows into your program wearing a type it may not have, and the failure surfaces at whatever line first does something the real value cannot support — typically several layers away, with a message about a missing method rather than about a bad payload. Parsing at the boundary moves the failure to the boundary and makes the message name the field and the expectation.

2. Which kind of bad payload never produces a runtime error at all?

An unexpected value in a union — a role of 'superadmin' where the type says 'admin' | 'member'. Every operation on it succeeds, because it is a perfectly good string; it just falls through every branch that was written to be exhaustive. The switch hits its default, or the permission check returns false, or the UI renders an empty state, and nothing anywhere throws. Chapter 6's never exhaustiveness check gives you a compile-time guarantee that all declared members are handled, and it cannot tell you that the declaration matches reality. Only a runtime parse can.

3. Why derive the type from the schema rather than writing both?

Because two descriptions of the same shape drift, and nothing checks them against each other. Rename a field and update the type, and the hand-written guard still checks the old name — so it passes, the value is typed as the new shape, and the property is undefined at runtime with no error anywhere. The compiler cannot help, because a guard's return type is a claim it takes on trust (Chapter 7). With z.infer<typeof Schema> there is exactly one place that describes the shape, so there is nothing to keep in step: the type is a projection of the validator rather than a parallel assertion about it.

4. Where should validation happen, and where should it not?

Once at every entry point — network, storage, environment, user input — and nowhere else. After the boundary the value has a type that is genuinely true, which is the entire return on the exercise; re-checking it between your own functions is noise that says you do not believe your own parser. Two refinements: if you are the server, validating your outbound responses against your published schema catches implementation drift cheaply, ideally in a test. And validate shape, not business rules — "a non-negative integer" belongs in the schema, "matches the sum of the line items" belongs in your code where the error can say something useful.

5. What is wrong with augmenting ProcessEnv?

It asserts rather than checks. Declaring DATABASE_URL: string tells the compiler the variable is present and typed, and nothing verifies that — so a missing variable is undefined at runtime while every use site believes it has a string, and the failure appears wherever the value is eventually used, usually as a connection error under load rather than at startup. Twelve lines parsing process.env against a schema at the top of main converts that into a process that refuses to start and names the missing variable. Export the parsed object, import it everywhere, and consider an ESLint rule banning process.env outside that one file.
