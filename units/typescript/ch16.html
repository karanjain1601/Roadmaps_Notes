CHAPTER 16

Recursion, and when to stop

A type may refer to itself, which makes the type system Turing-complete and gives you a budget of about fifty instantiations to work with — unless you write the recursion in one particular shape, in which case you get twenty times as many. Knowing which shape, and knowing when to put the whole thing down, is most of the skill here.

1The shape of it

A conditional type that names itself in one branch. Everything else follows.

Base case, recursive case, and the thing that terminates it TypeScript
// The canonical shape: split, process, recurse on the remainder.
type Length<T extends readonly unknown[]> =
  T extends [unknown, ...infer Rest]
    ? [unknown, ...Rest]['length']     // (a tuple knows its own length — Ch 9)
    : 0;

// Three requirements, and all three are easy to get wrong:
//   1. A BASE CASE the recursion can reach.
//   2. Each step must make PROGRESS — the argument to the
//      recursive call must be strictly smaller.
//   3. The compiler must be able to SEE the progress. A recursion
//      on `string` rather than on a literal never terminates,
//      because `string` is not getting shorter.

// Fail any of them and you get:
//   Type instantiation is excessively deep and possibly infinite.
// which is the compiler refusing to loop forever on your behalf.

What makes a type-level recursion tail-recursive

The recursive reference must be the entire body of its branch — nothing wrapped around it. ? Params<Tail> qualifies; ? Name | Params<Tail> and ? [Head, ...Reverse<Tail>] do not, because the compiler must hold the surrounding construction while the inner call resolves. The transformation is the same one you would apply in a value-level language: add an accumulator parameter and build the answer on the way down rather than on the way back up. The compiler recognises the shape and reuses one frame, which raises the practical ceiling from roughly 45 instantiations to just under 1,000.

4Recursive object types

A different and much cheaper kind of recursion, plus the one that bites.

Lazy versus eager recursion TypeScript
// This is fine, and costs nothing. A self-referential INTERFACE
// is resolved lazily — the compiler does not expand it until
// something asks about a specific path.
type Json =
  | string | number | boolean | null
  | Json[]
  | { [key: string]: Json };

interface TreeNode { value: string; children: TreeNode[]; }

// So is this — recursion through a mapped type over a concrete
// object is bounded by the object's actual depth.
type DeepReadonly<T> =
  T extends (...a: never[]) => unknown ? T
  : T extends readonly (infer E)[] ? readonly DeepReadonly<E>[]
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;

// THE ONE THAT BITES: DeepReadonly on a type that refers to
// itself. TreeNode.children is TreeNode[], so the recursion has
// no bottom and the compiler reports excessive depth. Nothing in
// the definition is wrong; the input is circular.
type Bad = DeepReadonly<TreeNode>;

// Two ways out. Either add a depth counter:
type DeepReadonlyN<T, D extends number[] = []> =
  D['length'] extends 6 ? T
  : T extends object ? { readonly [K in keyof T]: DeepReadonlyN<T[K], [...D, 0]> }
  : T;

// … or declare the readonly version by hand, which for a handful
// of recursive shapes is less code and infinitely more readable.

5The cost, and how to see it

Recursive types are the commonest cause of a slow project, and the tooling for it is good.

tsc --diagnostics --extendedDiagnostics
Instantiation count, check time and memory. A healthy medium project sits in the low millions of instantiations; tens of millions means something recursive is being asked a question it should not be.
tsc --generateTrace ./trace
Writes a trace loadable in Chrome's profiler viewer, which shows which type is expensive rather than only that something is. The single most useful diagnostic in the language, and almost nobody knows it exists.
Watch the editor, not the build
The language server does the same work on every keystroke. A type that adds two seconds to a build adds two seconds to every hover, which is a much worse experience than the build number suggests.
Cache with an alias, sometimes
Assigning a computed type to a named alias lets the compiler reuse the resolution across uses. It is not a general fix — the alias is still expanded in error messages (Chapter 15) — but it helps when the same expensive type is referenced in many places.
The blunt instrument works
If a recursive type is costing seconds, write out the concrete result and add a type-level test asserting the two agree. You keep the guarantee and lose the cost. Chapter 12's Expect<Equal<…>> is exactly for this.

6When not to

Four honest signals, from someone who has written the clever version.

SignalWhat to do instead
The recursion exists to validate a formatA pattern type (Chapter 15) for the shape, and a runtime schema for the rest. A type that parses a date string to check the month is in range is a monument, not a tool.
Nobody on the team can modify itWrite the concrete type. A guarantee that cannot be maintained is a liability with a nice error message.
The error messages are unreadableReduce the type's ambition until they are not. Colleagues will hit these messages far more often than you will hit the bugs the type prevents.
It works but the editor got slowerMeasure with --generateTrace, then decide honestly. Latency on every keystroke is a real cost paid continuously; the bug prevented is a hypothetical cost paid rarely.

None of this argues against learning it. The mechanisms in Part 4 are how the standard library is built, how good library types are built, and how you read someone else's clever type when it breaks. The argument is only about where the code you maintain should sit — and the answer for most application code is: use the clever types that libraries ship, and write plain ones yourself.

7Check yourself

Five questions.

1. What makes a type-level recursion tail-recursive, and why does it matter?

The recursive reference must be the entire body of its branch, with nothing wrapped around it. ? Go<Tail, [...Acc, X]> qualifies; ? [Head, ...Reverse<Tail>] does not, because the compiler has to hold the surrounding tuple construction while the inner call resolves. It matters because the compiler recognises the tail shape and reuses a single frame, raising the practical ceiling from around 45 instantiations to just under 1,000 — a twentyfold difference that decides whether a type works on real input. The transformation is the familiar one: add an accumulator and build the answer on the way down.

2. Why does recursing on string never terminate?

Because there is no progress the compiler can see. A pattern match like `${infer H}${infer T}` against a string literal shortens the tail by one character each step, so the recursion visibly approaches its base case. Against string, both captures are string — the tail is exactly as large as the input was, the base case is never nearer, and the compiler reports excessive depth rather than looping forever. It is the same requirement as at the value level, with the twist that "smaller" has to be evident to the type checker rather than merely true at runtime.

3. Why is a self-referential interface free while DeepReadonly of one explodes?

Because a self-referential interface is resolved lazily — the compiler stores the reference and expands it only when something asks about a specific path, so interface TreeNode { children: TreeNode[] } costs nothing. A mapped type over it is eager: it walks every property and recurses into each one, and since children is TreeNode[] there is no bottom to reach. Nothing about the DeepReadonly definition is wrong; the input is circular. The fixes are a depth counter using a tuple's length, or writing the readonly version by hand — which for a handful of shapes is less code and far more readable.

4. How do you find out which type is making a project slow?

tsc --generateTrace ./trace, then open the output in Chrome's profiler viewer. It shows which specific type instantiations are expensive rather than only that checking is slow, and it is the most useful diagnostic in the language despite being almost unknown. --extendedDiagnostics is the cheaper first look: it prints total instantiations, check time and memory, and a project in the tens of millions of instantiations has something recursive being asked a question it should not be. Watch the editor rather than the build, though — the language server repeats that work on every keystroke.

5. When should you write out the concrete type instead?

When the recursion is validating a format rather than deriving a fact — that is a pattern type plus a runtime schema. When nobody else on the team can modify it, because a guarantee that cannot be maintained is a liability. When the error messages have become unreadable, since colleagues meet those far more often than they meet the bugs the type prevents. And when the editor has got slower, which is a cost paid on every keystroke against a bug prevented rarely. In several of those cases you can keep the guarantee and drop the cost: write the concrete type and add Expect<Equal<Concrete, Computed>> as a type-level test.
