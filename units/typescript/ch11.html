CHAPTER 11

Constraints, defaults and inference sites

A constraint says what a type parameter must be assignable to. It does not say what the parameter is — and that distinction produces the single most confusing error message in the language, along with the reason you cannot build a value of your own type parameter.

Part 3 Generics·Reading time 35 minutes·Demos why the constraint is not the type, the keyof toolkit·Prerequisites Chapter 10

1extends means assignable to

Not inheritance. Not equality. Assignability, in the Chapter 3 sense.

Four things a constraint can be TypeScript
// A shape: any type with at least these members.
function save<T extends { id: string }>(x: T): T { … }

// A union: T must be one of these (or a subset of them).
function route<T extends 'home' | 'about'>(p: T): T { … }

// A primitive: T must be a string, possibly a literal one.
function tag<T extends string>(t: T): T { … }

// Another parameter — the pattern that does the most work.
function get<T, K extends keyof T>(o: T, k: K): T[K] { … }

// And note: `extends` here is unrelated to class inheritance.
// `T extends string` does not mean T is a subclass of anything; it
// means every value of T is assignable to string. Which is why
// `T extends string` is satisfied by 'a', by 'a' | 'b', and by
// string itself.

The rule underneath all of it

T extends C means every T is a C. It does not mean every C is a T — so you can read everything the constraint guarantees, and you cannot construct a T, because the caller's actual type may require members you have never heard of. The signature <T extends C>(x: T): T is a promise to return the caller's own type, and the only way to keep it is to return something that came from the caller. If you find yourself needing to build one, the honest signature returns C rather than T.

4Defaults

A fallback for when nothing can be inferred, and three rules about them.

Where defaults help and where they mislead TypeScript
// The genuine use: a type parameter nobody usually needs to name.
interface Result<T, E = Error> {
  ok: boolean; value?: T; error?: E;
}
type A = Result<User>;              // E is Error
type B = Result<User, HttpError>;   // E is HttpError

// Rule 1: parameters with defaults must come last.
interface Bad<T = string, U> {}          // error

// Rule 2: a default may reference earlier parameters.
interface Store<T, K extends keyof T = keyof T> {}

// Rule 3 — the one that misleads: on a FUNCTION, a default is used
// only when inference produces nothing at all. It is not a hint.
declare function make<T = string>(x?: T): T[];
make();                              // string[] — nothing to infer
make(42);                            // number[] — the argument wins

// So a default cannot rescue a bad inference (Chapter 10's demo).
// If inference keeps picking something too wide, the answer is a
// constraint, an explicit argument, or `const T` — section 5.

5Steering inference

Four tools, in order of how often you should reach for them.

When the compiler picks the wrong thing TypeScript
// The problem: a fallback parameter pollutes the inference.
declare function pick<T>(items: T[], fallback: T): T;
pick([1, 2], 'none');            // T = string | number. Compiles. Wrong.

// 1. NoInfer — mark the site that should NOT contribute.
//    The precise fix, and the one to reach for first.
declare function pick2<T>(items: T[], fallback: NoInfer<T>): T;
pick2([1, 2], 'none');           // error, at the fallback — exactly right

// 2. An explicit type argument — stops inference entirely.
//    Good at a call site, no help to other callers.
pick<number>([1, 2], 'none');     // error, correctly

// 3. A const type parameter — preserves literals without asking
//    every caller to write `as const`.
declare function routes<const T extends readonly string[]>(r: T): T;
routes(['home', 'about']);        // readonly ['home', 'about']

// 4. A separate parameter with a constraint — when the two things
//    are genuinely allowed to differ.
declare function pick3<T, F extends T>(items: T[], fallback: F): T | F;

// The thing NOT to do: `as` at the call site. It silences the
// symptom and leaves the signature wrong for everyone else.

6Constraint recipes

Seven that come up repeatedly.

ConstraintSays
T extends objectAny non-primitive. Rarely what you want — Record<string, unknown> is usually more accurate (Chapter 3).
T extends unknown[] / readonly unknown[]Any array or tuple. Use the readonly form so tuples and readonly arrays both satisfy it — Chapter 9.
T extends (...args: never[]) => unknownAny function. never[] rather than any[] for the parameters, because contravariance means never accepts every parameter list — Chapter 8.
K extends keyof TA real key of T. The workhorse.
T extends stringA string, possibly a literal one — which is what makes template literal types work on it (Chapter 15).
T extends PropertyKeystring | number | symbol. For anything used as an index.
T extends abstract new (...args: never[]) => unknownAny constructor, including an abstract class. For mixins and factories — Chapter 18.

Two notes on the third and last rows. Using never[] for a "any function" constraint is a small piece of variance cleverness worth understanding rather than copying blindly: a parameter list of never[] is contravariantly compatible with every parameter list, so the constraint accepts any function without resorting to any. And unknown rather than any as the return keeps the constraint honest.

7Check yourself

Five questions.

1. Why does function f<T extends { id: string }>(x: T): T { return { id: x.id }; } fail?

Because the constraint is not the type. T extends { id: string } means every T is assignable to { id: string }, not the reverse — so the caller may have passed { id: string; name: string; role: Role }, and the object you built has none of those. The signature promised to return the caller's own type, and the only way to keep that promise is to return something that came from the caller. If you genuinely need to construct the value, the honest signature returns { id: string } rather than T, and the caller loses the extra members — which is the truthful outcome.

2. What can you do with a constrained T inside the body?

Read anything the constraint guarantees, and assign to a property whose type the constraint pins down. So with T extends { id: string; n: number } you may read x.id, write x.n = 1, pass x anywhere the constraint is accepted, and spread it. What you cannot do is construct a T, assign a constraint-typed value into a T-typed slot, or inspect what T actually is — it is opaque and erased. Everything in that list follows from one fact: the caller's type may have members you have never heard of.

3. Why does <T, K extends keyof T>(o: T, k: K): T[K] beat (o: object, k: string): unknown?

Two reasons, and they are separate. The constraint K extends keyof T rejects a key that is not on the object, so a typo fails at the call site instead of silently returning undefined. And the return type T[K] is an indexed access, so reading 'age' from { id: string; age: number } gives you number — not string | number | boolean, and certainly not unknown. The naive version accepts every string and tells you nothing about the result, which means every call site needs a narrowing step or a cast.

4. Why can a default not rescue a bad inference?

Because on a function, a default is consulted only when inference produces nothing at all. If any argument position contributes a candidate, the candidate wins and the default is ignored — so declare function make<T = string>(x?: T): T[] gives string[] for make() and number[] for make(42). A default is a fallback, not a hint or a preference. When inference keeps choosing something too wide, the tools are a constraint, an explicit type argument at the call site, a const type parameter to preserve literals, or NoInfer to exclude a specific site from contributing.

5. What does NoInfer solve?

A parameter that should be checked against T but should not determine it. The classic case is a fallback: pick<T>(items: T[], fallback: T) lets the fallback contribute a candidate, so pick([1,2], 'none') quietly infers string | number and compiles — Chapter 10's third row. Wrapping the fallback as NoInfer<T> removes it from inference while still checking it, so T comes from the array alone and the bad call is rejected at the fallback, where the mistake is. It is the precise fix; an explicit type argument works at one call site and leaves the signature wrong for everyone else.
