Classes and decorators

The least JavaScript-like part of the language and the part that emits the most code. Most of it is ordinary and two pieces are not: private, which is a compile-time promise rather than privacy, and decorators, of which there are two mutually incompatible systems in current use.

private is not private

It is erased, so obj["secret"] reads it at runtime and any JavaScript consumer sees it in Object.keys and in a JSON serialisation. Its two real properties are that the compiler stops you touching it, and — from chapter 1 — that it makes two structurally identical classes incompatible, which is TypeScript's oldest branding mechanism. JavaScript's #private is genuinely inaccessible at runtime and gives the same nominal behaviour, so use #private unless you need the field visible to a test or a serialiser.

implements checks once and confers nothing
It verifies the class body against the interface at the declaration and has no effect on assignability afterwards — chapter 1's structural rule still governs. So a class with the right shape satisfies the interface whether or not it says implements, and the keyword's value is that the error appears on the class rather than at some distant call site.
abstract is compile-time only
An abstract class emits an ordinary class; only the new check and the unimplemented members are enforced by the compiler. Abstract members cannot be private, and an abstract class can still be instantiated by JavaScript consumers.
Most of the time you want a function and an object
Classes earn their place where identity, lifecycle or genuine polymorphism is involved — an entity with invariants, a connection, a state machine with behaviour. A class whose methods never touch this, or which exists only to group functions, is a module with extra ceremony. Chapter 3's discriminated unions replace most of the inheritance you would otherwise reach for.
Getters and setters are typed as one member
Since TypeScript 4.3 a getter and setter may have different types — set size(v: string | number) with get size(): number — which is useful at a boundary. The setter's type must be assignable from the getter's.

Self-check

  1. What does private actually guarantee?
    That the compiler will stop you accessing the member from outside the class, and that two structurally identical classes with private members are not assignable to each other. Nothing at runtime — the field is an ordinary property, readable through a string index, visible in Object.keys and included in JSON.stringify. Use #private for real inaccessibility; it gives the same nominal behaviour and is enforced by the engine.
  2. What do parameter properties emit?
    Assignments at the top of the constructor. constructor(private db: Db) becomes constructor(db) { this.db = db; } — one of the four non-erasing features from chapter 1. It removes the drift between field declarations and constructor arguments, and it is not JavaScript, so the code cannot be understood without knowing the rule. It is also the shape every dependency-injection framework expects.
  3. What does useDefineForClassFields change?
    Whether a field initialiser is an assignment or a defineProperty. With define semantics — the standard, and the default when target is ES2022 or later — a subclass field shadows a base class accessor rather than calling its setter, so the setter silently stops running. That breaks a pattern several older libraries rely on, which is why the flag exists and why the emitted code differs so much between the two settings.
  4. Why do two decorator systems exist?
    TypeScript implemented decorators years before the ECMAScript proposal stabilised, and the final standard has different semantics — a decorator returns a replacement rather than mutating a descriptor, and the context object is a different shape. TypeScript 5.0 shipped the standard version alongside the legacy one. They are not interchangeable, and a library written for one fails under the other, usually at runtime rather than with a type error.
  5. Why can NestJS not simply move to standard decorators?
    Because it depends on emitDecoratorMetadata, which emits the runtime types of constructor parameters so the injector can resolve dependencies from them. That is the single place TypeScript emits type information, it exists only in the legacy system, and the standard proposal has no equivalent. Moving would mean changing how injection is expressed — explicit tokens rather than inferred parameter types.
  6. When is a class the wrong tool?
    When there is no identity, no lifecycle and no polymorphism — a class whose methods never touch this, or one that exists to group related functions, is a module written with extra ceremony. And where you were reaching for a hierarchy to model variants, a discriminated union from chapter 3 usually does it better: exhaustiveness checking, no inheritance, and each variant carrying exactly the fields its state has.
