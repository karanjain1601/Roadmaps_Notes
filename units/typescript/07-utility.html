Utility and mapped types

A mapped type is a for loop over an object's keys, and every built-in utility is one. Once you can read the four-token syntax you stop looking them up and start writing the one you actually needed — which is usually a filter, and there is no built-in for that.

Writing your own

The whole syntax is { [K in Keys]: Value }, plus three optional pieces: a modifier on readonly or ?, an as clause to rename the key, and a conditional to compute the value.

A key remapped to never disappears
That is the entire mechanism behind filtering. [K in keyof T as Cond extends true ? K : never] keeps or removes each key, which gives you PickByValue, OmitByValue, "only the methods", "only the optional fields" and every variant you will ever need — none of which is built in.
Omit is not key-safe
Omit<Order, "totl"> compiles happily and removes nothing, because Omit's second parameter is keyof any rather than keyof T. So a renamed field leaves a stale Omit silently doing nothing. Pick is constrained and will error. If it matters, write a constrained wrapper.
Mapped types over unions distribute per member
Applying Partial to a discriminated union gives a union of partials — which usually destroys the discriminant, since the tag becomes optional and narrowing stops working. Map the variants individually, or reach for a distributive conditional (chapter 8) instead.
Homomorphic mapping preserves the original's modifiers
A mapping written exactly as [K in keyof T] keeps readonly and ? from the source unless you override them; add an as clause or map over a different key set and that preservation is lost. It explains most "why did my optional field become required" surprises.
When not to compute a type

A derived type cannot drift from its source, which is the argument for computing. Against it: hovers become expressions rather than names, error messages expand to the full structure, "go to definition" leads to a mapped type rather than the field you wanted, and every layer costs the checker something — chapter 19. The rule that holds up: derive when the source genuinely is the source of truth — a Record<Status, …> that must cover every status, a DTO that must track an entity. Write the type out when it is a real, independent contract, even if it looks like a duplicate today. A public API type derived from an internal one couples them permanently, and the first breaking change you did not intend will be exactly there.

Self-check

  1. What is the minimal mapped type syntax, and what are the optional pieces?
    { [K in Keys]: Value } — a key variable, a set of keys to iterate, and the value type for each. The three additions are a modifier (readonly, ?, or either with a - to remove), an as clause to rename or filter the key, and a conditional in the value position. Every built-in utility is one of these.
  2. How do you remove a key in a mapped type?
    Remap it to never in the as clause — [K in keyof T as Cond extends true ? K : never]. A key of type never is dropped from the result, and that single behaviour gives you every filtering utility: pick by value type, keep only methods, keep only optional fields. None of them ships in the standard library, which makes this the most valuable thing in the chapter.
  3. Why is Omit less safe than Pick?
    Its second parameter is constrained to keyof any rather than keyof T, so Omit<Order, "totl"> compiles and removes nothing. That makes it silently wrong after a rename: the field comes back into the type and nobody is told. Pick is constrained to keyof T and errors on a bad key. Where it matters, wrap Omit in a version with the tighter constraint.
  4. What goes wrong applying Partial to a discriminated union?
    The mapping distributes over the members, so you get a union of partials — and each variant's discriminant is now optional. Narrowing on the tag stops working, because the compiler can no longer use it to select a member, and every field becomes optional in every branch. Map the variants individually, or use a distributive conditional that only touches the payload.
  5. What does "homomorphic" buy, and how do you lose it?
    A mapping written literally as [K in keyof T] preserves the source's readonly and ? modifiers, and passes arrays and tuples through as arrays and tuples rather than flattening them to objects. Adding an as clause, or iterating a different key set such as Exclude<keyof T, "id">, breaks that — which is why a renaming map turns optional fields required unless you add ? back explicitly.
  6. When should you write a type out instead of deriving it?
    When it is an independent contract rather than a projection. A public API type derived from an internal entity couples them permanently: the next internal rename becomes a breaking change you did not intend, and nothing in the diff says so. Derive when the source genuinely is the source of truth — a lookup that must cover every union member, a patch type over an entity — and write it out when the two are allowed to diverge, even if today they look identical.
