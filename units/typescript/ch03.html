CHAPTER 03

The primitives, the top and the bottom

Seven primitives, which are easy, and then five types people reach for interchangeably — any, unknown, never, void and object. They behave nothing alike, and two of them sit at opposite ends of the whole system.

Part 1 The shape of the type system·Reading time 35 minutes·Demos what you may do with a value, the assignability matrix·Prerequisites Chapters 1–2

1The primitives

Seven of them, all lower-case, and three notes worth having.

TypeNotes
stringNo separate char. Template literals are string unless you use the literal types in Chapter 15.
numberOne numeric type — no int, no float, no i32. It is a double, so 0.1 + 0.2 !== 0.3 and integers above 253 lose precision, and the type system will not warn you about either.
bigintSeparate, and deliberately not mixable — 1n + 1 is an error at both levels. For money and ids beyond safe integer range.
booleanExactly true | false, which is why narrowing on a boolean works so cleanly.
symbolAnd unique symbol for a specific one, which is the only nominal-ish primitive the language has.
null, undefinedDistinct types, and only meaningful with strictNullChecks. Without it they are assignable to everything and the distinction is decorative.

Always the lower-case names. String, Number and Boolean are the wrapper object types — they exist, they are almost never what you want, and a lint rule should ban them. new String('a') === 'a' is false.

any is not a type, it is an off switch
It means "stop checking this expression". Every property access, call and index succeeds, and the result is any again — which is the contagion. One any at the top of a data pipeline silently unchecks everything downstream.
unknown is the honest top type
Every value is assignable to it and it is assignable from nothing but itself and any. So you must narrow before use, which is exactly what you should be doing with a value of unknown provenance.
Use unknown everywhere you were going to write any
API responses, JSON.parse, catch variables, function parameters you have not typed yet. It costs you a narrowing step and buys you a compiler that is still working.
Explicit beats implicit
If you truly need any, write it. An implicit any from a missing annotation is the same hole with nothing marking it — which is what noImplicitAny is for.

3never

The bottom type: no value has it. Four places it turns up, and one behaviour that surprises everyone.

Where never comes from TypeScript
// 1. A function that does not return — not "returns nothing"
function fail(msg: string): never { throw new Error(msg); }
function forever(): never { while (true) {} }

// 2. An exhausted narrowing — the exhaustiveness check
function area(s: Circle | Square) {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'square': return s.side ** 2;
    default:
      const _exhaustive: never = s;   // add a third shape and this errors
      throw new Error('unreachable');
  }
}

// 3. An impossible intersection
type Nope = string & number;          // never

// 4. Filtering everything out of a union (Chapter 12)
type Gone = Exclude<'a', 'a'>;         // never

// AND THE SURPRISE: never disappears from a union.
type T = string | never;              // string — never is the identity for |
// which is why a conditional type that returns never for some
// members of a union removes them rather than producing
// "string | never". Chapter 12 depends on this.
The exhaustiveness pattern is the reason to care

Assigning the narrowed value to a never-typed variable in the default branch means that adding a new member to the union breaks the build at every switch that does not handle it. That single line converts "we forgot to handle the new payment method" from a production incident into a compiler error, and it is the most valuable four words in this chapter. Chapter 6 has the full treatment.

5void against undefined

Not synonyms, and the difference is load-bearing.

The asymmetry, and what it is for TypeScript
// undefined is assignable to void. void is NOT assignable to undefined.
const a: void = undefined;        // fine
const b: undefined = a;            // error

// The point: a void RETURN means "I will ignore whatever you
// return", so any function is assignable to it.
type Cb = () => void;
const ok: Cb = () => 42;             // allowed — the number is discarded

// Which is exactly why this works and is a classic bug:
const ids: number[] = [];
[1, 2, 3].forEach(n => ids.push(n));   // push returns number; fine

// …and why THIS silently does nothing useful:
[1, 2, 3].forEach(async n => { await save(n); });
// forEach's callback returns void, so the Promise is discarded and
// nothing waits for the saves. The types permit it because void
// means "ignored". Use a for-of loop, or Promise.all(map(…)).

// A void PARAMETER is different and rare — it means "pass nothing":
declare function f(x: void): void;
f();                                // fine
Use void for return types you ignore
Which is the vast majority of callbacks. It is deliberately permissive so that () => someExpression works without a block body.
Use undefined when the value genuinely is undefined
A property that may be absent, a function that returns nothing and whose result you check. string | undefined, never string | void.
The floating-promise problem is worth a lint rule
no-misused-promises and no-floating-promises catch the forEach case above and its relatives. The type system permits them by design, so this is one of the places a linter is doing genuine type-aware work the compiler will not.

6object, Object and {}

Three things that look like they mean the same and mean three different things.

MeansAccepts
objectAny non-primitiveObjects, arrays, functions, class instances. Not string, number, boolean, symbol, null, undefined.
{}Anything except null and undefinedEverything else including primitives — const x: {} = 'hello' compiles. It does not mean "empty object"; it means "has at least no required properties", which everything satisfies.
ObjectThe interface of Object.prototypeEffectively the same as {}. Avoid it; a lint rule should flag it alongside String and Number.
Record<string, unknown>An object with string keys and unknown valuesWhat people almost always mean when they write one of the above. Use this.

The {} confusion is worth internalising because it appears in error messages and in library types. When you see {} in a constraint — T extends {} — it is being used to mean "not null or undefined", which is a real and useful thing to say, and nothing to do with emptiness.

7Literal types, and what to use instead of enum

The most useful type in the language is a string with one possible value.

A union of literals beats an enum TypeScript
// A literal type has exactly one member.
type Open = 'open';
let s: Open = 'open';        // the only legal value

// A union of them is a closed set the compiler can exhaust.
type Status = 'open' | 'closed' | 'pending';

// The const-object pattern, when you also want the values at runtime:
const STATUS = { open: 'open', closed: 'closed' } as const;
type Status2 = typeof STATUS[keyof typeof STATUS];   // 'open' | 'closed'

// Why not enum:
//   • it emits runtime code (Chapter 1's demo) — the only
//     type-position construct that adds to your bundle
//   • a numeric enum accepts any number, which is a real hole
//   • enum members are nominal, so two structurally identical
//     enums are incompatible — surprising in a structural language
//   • it does not work under type-stripping runtimes (Chapter 2)
// A union of string literals has none of those problems and
// narrows better.

8Check yourself

Five questions.

1. What is the difference between any and unknown?

Both accept every value. The difference is what you may then do. any permits every operation and yields any back — so property access, calls and indexing all succeed unchecked, and the result is unchecked too, which is the contagion: one any at the top of a pipeline silently unchecks everything downstream. unknown permits almost nothing until you narrow it, and is assignable to nothing but itself and any. Practically: write unknown wherever you were about to write any — API responses, JSON.parse, catch variables — because it costs one narrowing step and keeps the compiler working.

2. Why does type T = string | never equal string?

Because never is the empty type — no value has it — so it is the identity element for union: adding "nothing" to a set of possibilities changes nothing. This is not a curiosity; Chapter 12 depends on it. A conditional type that maps some union members to never and others to themselves acts as a filter, because the never results vanish from the resulting union rather than appearing in it. That is precisely how Exclude and Extract work, and why they are one-liners.

3. What is the exhaustiveness pattern and why is it valuable?

In the default branch of a switch over a discriminated union, assign the narrowed value to a variable typed never. If every case is handled, the value has been narrowed to never and the assignment is legal. Add a new member to the union and it no longer narrows to never, so every switch that fails to handle the new case becomes a compile error naming the file and line. That turns "we forgot to handle the new payment method" from an incident into a build failure, and it is the highest-value use of never by a wide margin.

4. Why does [1,2,3].forEach(async n => { await save(n) }) type-check and not work?

Because forEach's callback is typed as returning void, and void in a return position means "whatever you return will be ignored" — so any function is assignable, including one returning a promise. The promises are created and discarded, forEach returns immediately, and nothing waits for the saves. This permissiveness is deliberate: it is what lets you write () => array.push(x) without a block body. Use for...of with await for sequential work, or Promise.all(items.map(...)) for parallel, and turn on no-floating-promises and no-misused-promises — this is a case where a type-aware linter catches what the compiler permits by design.

5. Does {} mean "empty object"?

No — it means "anything except null and undefined", and that includes primitives, so const x: {} = 'hello' compiles. Read it as "has no required properties", which every non-nullish value satisfies. This matters because {} shows up in library types and error messages, usually in a constraint like T extends {} where the author means "not nullish". The type you almost always actually want is Record<string, unknown>; object means "non-primitive" and excludes strings and numbers; and Object is the wrapper interface and should be banned by a lint rule alongside String and Number.
