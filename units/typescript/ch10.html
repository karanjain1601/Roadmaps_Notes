CHAPTER 10

Generics from first principles

A type parameter is a hole in a type, filled in later by whoever uses it. That is the whole idea, and there is one rule that catches almost every misuse of it — including the very common case of a generic that should never have been a generic at all.

1What a type parameter is

A placeholder, and a promise about how the placeholder is used.

The smallest possible example, and what it buys TypeScript
// Without a parameter, you must choose — and lose information.
function firstAny(xs: any[]): any { return xs[0]; }
const a = firstAny([1, 2]);            // any — checking is now off (Ch 3)

function firstUnknown(xs: unknown[]): unknown { return xs[0]; }
const b = firstUnknown([1, 2]);        // unknown — safe, and useless to the caller

// With one, the caller's type flows through and comes back out.
function first<T>(xs: readonly T[]): T | undefined { return xs[0]; }
const c = first([1, 2]);               // number | undefined
const d = first(['a']);                // string | undefined

// The parameter is a RELATIONSHIP: "whatever you put in, that is
// what comes out". It is not a way of saying "some type" — that is
// what `unknown` is for, and confusing the two is section 2.
Read a generic as a claim about connections
<T>(xs: T[]) => T says the return is the element type. <T>(x: T) => void says nothing at all, because T appears once and connects nothing.
The parameter belongs to the caller, not to you
Inside the function body T is opaque — you know nothing about it beyond its constraint. If you find yourself wanting to inspect it, you probably wanted a union or an overload (Chapter 8).
Erased, like everything
There is no T at runtime, so you cannot do new T() or typeof T. Chapter 1. Passing a constructor as a value is the workaround, which is what Chapter 8's construct signatures are for.

2The golden rule

The rule, stated once

A type parameter must appear at least twice — otherwise it is not relating anything, and you have written a more complicated way to say unknown. The two appearances can be a parameter and the return, two parameters, or a parameter and a constraint on another parameter. If T appears only in a parameter position, replace it with unknown or a union. If it appears only in the return position, you have written a disguised type assertion and the caller can ask for anything they like.

Explicit arguments override everything
pick<string>(xs, f) stops inference and checks the arguments against string. Useful when inference picks something wider than you wanted, and a sign the signature may need a constraint.
Return positions do not drive inference
The compiler infers from arguments, not from what you assign the result to — with the exception of contextual typing through a callback parameter, which does flow inward (Chapter 4).
Defaults are a fallback, not a hint
<T = string> is used only when nothing can be inferred at all. If an argument provides a candidate, the default is ignored.
const type parameters preserve literals
<const T>(x: T) infers as if the argument had as const, which removes a great deal of as const from call sites. Modern, and worth knowing about for configuration-shaped APIs.

4Relating several parameters

Where generics stop being decorative and start preventing bugs.

Four signatures worth being able to write from memory TypeScript
// 1. Key must be a key of the object, and the return follows.
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
get({ id: 'a', n: 1 }, 'n');       // number — not string | number
get({ id: 'a' }, 'nope');          // error, at the call site

// 2. Two collections whose element types must agree.
function zip<A, B>(as: readonly A[], bs: readonly B[]): [A, B][] { … }

// 3. A transform, where the output type is the callback's return.
function mapValues<T, R>(
  obj: Record<string, T>,
  fn: (v: T) => R
): Record<string, R> { … }

// 4. A parameter constrained by ANOTHER parameter — the pattern
//    that catches mismatched pairs.
function setState<S, K extends keyof S>(s: S, k: K, v: S[K]): S { … }
setState({ n: 1 }, 'n', 'oops');     // error — v must be number

// Notice what all four have in common: every parameter appears
// more than once, and the extra appearances are where the checking
// happens. That is section 2's rule doing real work.

5When not to

Five signals that a generic is the wrong tool.

SignalWhat you wanted instead
T appears onceunknown, or a union. Section 2.
T appears only in the return typeNothing — that signature lets the caller name any type and get it unchecked, which is a type assertion with extra steps.
You want to branch on T inside the bodyOverloads (Chapter 8), or a discriminated union parameter. T is opaque at runtime and the body cannot see it.
The constraint is so tight only one type satisfies itThat type, written directly.
Every call site passes the type argument explicitlyInference is not working, which usually means the parameter is not connected to anything the caller passes — section 2 again, or a missing constraint.

And one anti-signal worth resisting: adding a type parameter because a function "might need to be more general one day". A generic with one caller is a guess about the future paid for in every reader's attention. Add it when the second caller arrives.

6Check yourself

Five questions.

1. What is wrong with function log<T>(x: T): void?

T appears once, so it relates nothing — it is a more complicated way of writing unknown. A type parameter expresses a connection: "whatever comes in is what goes out", or "this key belongs to that object". With a single occurrence there is no connection to express, and the signature is longer, harder to read, and behaves identically to (x: unknown): void. The mechanical test is worth applying whenever you write one: count the occurrences, and if there is only one, delete the parameter.

2. Why is function parse<T>(s: string): T dangerous?

Because T appears only in the return position, so nothing constrains it and the caller names whatever they like: parse<User>(s) yields a User with no checking of any kind. It is a type assertion wearing a function's clothing — worse, actually, because the lie is inside a shared helper that every call site inherits, which is exactly Chapter 7's argument about predicates. The honest signature returns unknown and makes the caller narrow or validate, which is Chapter 20's boundary work.

3. Where does the compiler get candidates for T?

From the argument positions where T appears — each one contributes a candidate, and the compiler picks a best common type from the set. It does not infer from what you assign the result to; return positions do not drive inference, the one exception being contextual typing flowing into a callback parameter (Chapter 4). Two related facts: an explicit type argument stops inference entirely and checks the arguments against it; and a default like <T = string> is only used when nothing can be inferred at all, so it is a fallback rather than a hint.

4. Why does get<T, K extends keyof T>(obj: T, key: K): T[K] beat get(obj: object, key: string): unknown?

Because it checks the relationship and preserves the answer. The key is constrained to be a real key of the object, so a typo fails at the call site rather than returning undefined; and the return is T[K], so getting 'n' from { id: string; n: number } gives you number and not string | number. Both type parameters appear more than once, and the extra appearances are precisely where the checking happens — which is section 2's rule doing something useful rather than just being satisfied.

5. You want the function body to behave differently depending on T. What should you write?

Not a generic. T is erased and opaque — the body cannot inspect it, so there is nothing to branch on. What you want is either overloads, where each declared signature pairs an argument type with its return type and the body narrows a union parameter (Chapter 8), or a discriminated union parameter so the branch is on a real runtime value (Chapter 6). If you reach for a generic plus a conditional return type, note what Chapter 8's demo showed: the body cannot be checked against a conditional return, so you end up with as any inside and an unverified implementation.
