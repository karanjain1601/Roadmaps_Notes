Types are not validation

Chapter 1's erasure, cashed out. A type is a claim the compiler tries to verify about your code; data that entered from outside has been verified by nobody. Every real TypeScript failure in production is somewhere on the line between those two sentences.

Where does the boundary go?

Six functions, one parse
Drag it as early as it will go
nowhere
Validate at the edge, and only at the edge
One parse where data enters the process, and everything inside is typed. Re-validating in the service layer is duplicated logic that will diverge; not validating at all pushes the check into every reader. The edges are: HTTP handlers, queue consumers, file and config loads, and any third-party response you act on.
Do not validate your own function arguments
Inside the boundary the compiler has already checked them, and a runtime check there is noise that also implies the types cannot be trusted. The exception is a published library, whose callers may not be using TypeScript at all.
Database rows are a boundary too, and an easy one to miss
A query builder's row type comes from your schema definition, not from the database — so a column changed by a migration you did not run, a NULL where the type says string, or a numeric arriving as a string from the driver all pass silently. Parse at least the rows whose shape you do not fully control.
The schema is the source of truth, not the type
Derive the type from the schema with z.infer and never write both. Two hand-maintained declarations of the same shape will disagree, and the disagreement will be silent because only one of them runs.

Self-check

  1. Why does a typed parameter guarantee nothing about incoming data?
    Because the type is erased and the check happened at the call sites the compiler could see. Data from outside the program has no call site it verified — it arrived as bytes. So function handle(o: Order) means "every caller I can see passes an Order", and an HTTP body cast to Order is not a caller the compiler checked. The annotation is a claim about your code, not a gate on your data.
  2. What is the difference between validating and parsing?
    Validation returns a boolean and leaves you holding the same unverified value, so the knowledge that the check passed lives only in your head and in control flow that the next function cannot see. Parsing returns a new value of a narrower type, so the type system carries the fact that the check happened — and every function downstream receives a real guarantee rather than a convention. Only the second one composes across module boundaries.
  3. Why derive the type from the schema rather than writing both?
    Because two hand-maintained declarations of the same shape will diverge, and the divergence is silent — only the schema runs, so the type quietly starts describing something that is not what gets checked. z.infer<typeof Order> makes one of them a consequence of the other, so a field added to the schema appears in the type and a field removed breaks the code that read it.
  4. Why is declaring ProcessEnv a lie?
    Because declare namespace NodeJS { interface ProcessEnv { PORT: string } } asserts the variable exists and is a string, and nothing checks either claim — a missing variable is undefined with a type of string, which is chapter 9's laundering in its purest form. Parse process.env at boot instead: a missing variable becomes a process that refuses to start, which is a deployment failure rather than a runtime one.
  5. Why not validate in the service layer as well?
    Because it is the same logic in two places and it will diverge — and the presence of a second check implies the first one is not trusted, which encourages a third. One parse at the edge, then types all the way down. The genuine exception is a published library: its callers may not be using TypeScript, so its public entry points are boundaries even though they look internal.
  6. Why are database rows a boundary?
    Because the row type comes from your schema definition, not from the database itself. A migration someone else ran, a nullable column the type says is string, or a driver returning numeric as a string all produce values that do not match the declared type, and nothing checks. It is the boundary people forget precisely because the types look like they came from the database — they came from a file describing it.
