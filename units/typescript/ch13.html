CHAPTER 13

Mapped types and key remapping

A loop over the keys of a type, with the option to change each key's name, its modifiers and its value type. Together with Chapter 12 that is the entire type-level toolkit — and there is one special case, with a name, that explains several otherwise baffling behaviours.

Part 3 Generics·Reading time 35 minutes·Demos build a mapped type, homomorphic behaviour·Prerequisites Chapter 12

1The syntax

Four movable parts, and the demo below drives all of them.

Every position labelled TypeScript
type Mapped<T> = {
  //  ↓ modifiers        ↓ the key variable   ↓ what to iterate
  readonly [K in keyof T as NewKey<K>]?: T[K]
  //                     ↑ remap clause      ↑ the value type
};

// The minimal identity mapping — and it is not quite the identity,
// which is section 6:
type Id<T> = { [K in keyof T]: T[K] };

// You can iterate anything that is a union of keys, not only keyof:
type Flags = { [K in 'read' | 'write']: boolean };
// { read: boolean; write: boolean }

// Which is all Record is:
type Record<K extends PropertyKey, V> = { [P in K]: V };

3Modifiers, added and removed

Four operations, and one of them does more than it says.

WrittenDoes
?:Makes every mapped property optional. Same as +?.
-?:Removes optionality — and removes undefined from the value type, which is the part people miss. That is why Required<{ a?: string }> is { a: string } rather than { a: string | undefined }.
readonly [K in …]Makes every mapped property readonly.
-readonly [K in …]Removes it. This is Mutable<T>, which is not in the standard library and probably should be.

Modifiers are only preserved from the source when the mapping is homomorphic — section 6. Add an as clause and every property comes out with whatever modifiers you wrote and nothing else, which is the root of Omit's problems in Chapter 14.

4Key remapping with as

Rename keys, or drop them, using the machinery from Chapter 12.

Three things the clause is for TypeScript
// 1. RENAME, with a template literal type (Chapter 15)
type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
};
// { id: string } → { getId: () => string }
// note `string & K` — keyof T may include number and symbol,
// and Capitalize only accepts strings

// 2. FILTER, by mapping unwanted keys to never
type OnlyStrings<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K]
};
// A key remapped to never is dropped entirely — the same
// never-vanishes rule as Chapter 12, applied to keys.

// 3. SPLIT one key into several, by remapping to a union
type Events<T> = {
  [K in keyof T as `on${Capitalize<string & K>}Change` | `${string & K}Dirty`]: boolean
};

// THE COST: adding an `as` clause makes the mapping
// non-homomorphic, so source modifiers are NOT preserved. If you
// remap keys and want to keep readonly and optional, you have to
// write them yourself — and you cannot preserve them per property.

5Homomorphic mapped types

A word worth learning, because it explains five otherwise arbitrary behaviours.

A mapped type is homomorphic when it iterates keyof T directly for a type parameter T — written exactly as [K in keyof T], with no as clause. The compiler then treats it as "the same type, adjusted" rather than "a new object type", and gives it four special behaviours that a non-homomorphic mapping does not get.

The four special behaviours

1 · Modifiers are preserved. A source readonly or ? survives unless you explicitly change it. 2 · Arrays and tuples stay arrays and tuples rather than becoming objects with numeric keys. 3 · It distributes over unions, so Partial<A | B> is Partial<A> | Partial<B>. 4 · Primitives pass through unchanged, so Partial<string> is string. Every one of those is lost the moment you add an as clause — which is why Pick and Omit behave differently from Partial and Readonly, and Chapter 14 is largely about that difference.

6Recipes worth knowing

Five that come up, all built from these two chapters.

Composing conditional and mapped types TypeScript
// 1. Keys whose values match a type — Chapter 11's preview, now
//    fully explicable. Map, filter to never, then index to collapse.
type KeysOfType<T, V> = {
  [K in keyof T]-?: T[K] extends V ? K : never
}[keyof T];

// 2. Make selected keys optional, leaving the rest alone.
type SetOptional<T, K extends keyof T> =
  Omit<T, K> & Partial<Pick<T, K>>;

// 3. Recursive, for nested config objects. Note the array guard —
//    without it, arrays become objects (section 5, behaviour 2).
type DeepPartial<T> =
  T extends (...a: never[]) => unknown ? T
  : T extends readonly (infer E)[] ? readonly DeepPartial<E>[]
  : T extends object ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

// 4. Flatten an intersection so the editor shows it readably.
type Prettify<T> = { [K in keyof T]: T[K] } & {};

// 5. Remove readonly. Absent from the standard library.
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

7Check yourself

Five questions, closing Part 3.

1. What does -? do beyond removing optionality?

It also removes undefined from the value type. That is why Required<{ a?: string }> is { a: string } and not { a: string | undefined } — the modifier and the union member are removed together, which is almost always what you wanted. It matters in two places: when you write your own Required-like mapping and are surprised the type got narrower, and in the KeysOfType recipe, where -? is needed so that optional keys do not contribute undefined and defeat the filter.

2. How do you drop a key in a mapped type?

Remap it to never in the as clause: [K in keyof T as Cond extends true ? K : never]. A key remapped to never is dropped from the resulting type entirely, which is the same never-vanishes rule from Chapter 12 applied to keys rather than to union members. It is how you filter by value type, by name pattern, or by anything else a conditional type can express. The cost is that adding an as clause at all makes the mapping non-homomorphic, so you lose the source's modifiers and the array, union and primitive special cases.

3. What does "homomorphic" mean here, and what does it buy?

A mapped type is homomorphic when it iterates keyof T directly for a type parameter T, written exactly as [K in keyof T] with no as clause. The compiler then treats it as the same type adjusted rather than a fresh object type, and grants four behaviours: source readonly and ? modifiers are preserved; arrays and tuples stay arrays and tuples instead of becoming objects with numeric keys; it distributes over unions; and primitives pass through unchanged. Add one as K clause — a no-op rename — and all four disappear.

4. Why is Partial<string> equal to string?

Because Partial is homomorphic, and one of the four special behaviours is that primitives pass through a homomorphic mapping unchanged. It looks like a bug and it is what makes utilities like DeepPartial possible without a primitive guard at every level — the recursion can hand a string to Partial and get a string back rather than an object with the keys of String.prototype made optional. The non-homomorphic version does exactly that instead, which is one of the rows in the demo and a good illustration of how much the special-casing is doing.

5. Why does DeepPartial need an array branch?

Because the recursion is not a plain homomorphic mapping — it wraps the map in a conditional type, and once you route through T extends object ? { [K in keyof T]?: … } the mapping is still homomorphic at each level, but you need to decide what happens to arrays before you get there. Without an explicit array branch, an array's element type ends up mapped as if the array were an object of properties, so DeepPartial<{ items: User[] }> produces something with optional numeric keys and optional array methods rather than readonly DeepPartial<User>[]. Also worth a branch: functions, which should pass through untouched rather than having their properties made optional.
