Errors, results and exhaustiveness

TypeScript has no checked exceptions, so a function's signature says nothing about how it fails. What it does have is never — which turns "did I handle every case?" from a question you ask yourself into one the compiler answers, but only if you set it up beforehand.

What breaks when the union grows

Exhaustiveness is a property you only ever benefit from in the future. Here is the same union, six call sites, and one new member.

Add a fourth status
Three sites tell you; three do not
typescript — the helper, and where to put it
// one function, once, in a utilities module
export function exhaustive(x: never, msg = "unhandled"): never {
  throw new Error(`${msg}: ${JSON.stringify(x)}`);
}
// ① the parameter is `never`, so passing anything is an error —
//    and in a default branch where every case is handled, the
//    variable HAS narrowed to never, so it compiles. Chapter 2.
// ② it also throws, so the runtime is covered if a value arrives
//    from outside the type system. Chapter 13 — it will.

switch (order.status) {
  case "pending":  return …;
  case "paid":     return …;
  case "refunded": return …;
  default:          return exhaustive(order.status);
}

// ── narrowing a caught error ──
try { … } catch (err) {          ← unknown, with
  if (err instanceof HttpError) return reply(err.status);
  if (err instanceof z.ZodError) return reply(422, err.issues);
  throw err;                       ← anything you did not
}                                       recognise is not yours
// ✱ instanceof breaks across realms and after some bundling, and
//   it fails for a subclass whose prototype was not restored when
//   targeting ES5. A `code` property you set yourself is more

Exceptions or results?

What does the caller know?
Only one style puts failure in the signature
never is a proof, and only in a default branch
The helper works because control-flow narrowing has eliminated every union member by the time the default is reached — so the variable really is never, and nothing else is assignable to never. Add a member and one branch no longer eliminates it, the variable is that member, and the call fails to compile. Chapter 2's lattice doing real work.
An if / else if chain is not exhaustive
Even with a final else that throws, the compiler does not narrow the final branch to never unless every preceding condition was a discriminant comparison it could follow — and in practice people write conditions it cannot. A switch narrows reliably; prefer it whenever the value is a discriminated union.
Errors are values, and TypeScript will not help you
There is no throws clause, so a function's signature is silent about failure and the only way to know what a call can throw is to read it and everything it calls. That is the argument for Result, and the argument against is that it is ceremony on every call in a codebase where most failures are genuinely unrecoverable.
Do not make every error a Result
A bug — a null dereference, a broken invariant, an out-of-memory — has no useful handling and should propagate. Chapter 5 of the Node unit calls these programmer errors. Result earns its place for the expected failures a caller must decide about: a card declined, a name taken, a file absent.

Self-check

  1. How does exhaustive(x: never) work?
    By the time control reaches the default branch, narrowing has eliminated every union member the earlier cases handled — so if they covered all of them, the variable's type is never, and never is the only thing assignable to a never parameter. Add a member and one case no longer eliminates it: the variable is now that member, which is not assignable, and the call fails to compile at every switch that needs updating.
  2. Why is exhaustiveness only valuable in the future?
    Because when you write the switch you already know the cases — the compiler is telling you something you just decided. The value arrives months later when someone adds a variant: with the helper, every site that needs attention becomes a build error and the change is a checklist; without it, the sites silently take a fallback branch and the failure is a wrong answer in production. It is a refactoring property, not a correctness property.
  3. Why does a Record<Status, string> break but a plain object literal not?
    Because Record's keys are exactly the union, so a missing key is a missing required property and an error. A plain object literal is inferred from what you wrote — its type simply becomes an object with three keys, and nothing relates it to the union at all. Annotating the lookup is what turns it into an exhaustiveness check, and it is one of the highest-value annotations available.
  4. Why is a caught error unknown?
    Because JavaScript lets you throw anything — a string, a number, an object with no message, undefined. So typing it Error would be a lie and any would be chapter 9's hole. useUnknownInCatchVariables, on under strict, makes it unknown and forces a narrowing. Re-throw anything you do not recognise, rather than converting it into something you do.
  5. When is Result worth the ceremony?
    For expected failures the caller must decide about — a declined card, a taken username, a missing file — where putting the failure in the signature means the compiler enforces handling. It is not worth it for bugs, which have no useful handling and should propagate to a top-level handler that logs and exits. The mixed approach is what most codebases converge on, and it works because the two categories really are different.
  6. What is the risk of a Result type without a linter?
    That the return value is ignored. await charge(card) compiles perfectly as a statement, so the failure case you carefully encoded in the type is discarded and the code continues as though it succeeded — the exact bug Result was adopted to prevent, now silent instead of loud. A no-floating-promises-style rule or a linted "must-use" convention is not optional here; it is what makes the pattern work.
