Chapter 09 · Escape hatches

any, unknown and assertions

Every escape hatch is the same trade: you assert something the compiler cannot verify, in exchange for getting on with your day. They differ enormously in how much they switch off and how far the consequences travel — and the worst of them is also the easiest to type.

How far does an any travel?

One unchecked value, six lines later

Where any comes from, when you did not write one
  • JSON.parse returns any, and so does response.json(). Both are the front door for untyped data.
  • A caught error is any unless useUnknownInCatchVariables is on — which it is under strict, and which many older configs disable.
  • An untyped dependency. No @types package and no bundled declarations means every import from it is any, silently, unless noImplicitAny catches the module.
  • A wrong @types package. Hand-written, sometimes stale, and an any in one signature spreads into your code with nothing to indicate it — chapter 16.
  • Implicit parameters in a callback the compiler cannot contextually type. noImplicitAny is the flag, and it is the highest-value one in the whole config.

unknown costs one narrowing and buys everything
The complaint against it is that you have to check before use. That is the feature: the check is where the knowledge actually enters the program, and after it every downstream line is verified rather than assumed. One typeof, one predicate or one schema parse — chapter 13.
An assertion is a claim about now
order as OrderDto is true when you write it and says nothing about the shape after someone adds a field. Assertions do not resurvive refactoring, and nothing re-checks them, so each one is a small permanent liability rather than a one-off shortcut.
Prefer a predicate to an as
Both are assertions the compiler trusts. The difference is that a predicate puts the claim in a named, testable function used in many places, while an as scatters unverifiable claims across call sites. One thing to review and test beats thirty things to grep.
Make the hatches visible
Lint rules that ban bare any, flag unsafe member access on any, and require a comment on every suppression. The goal is not zero escape hatches — it is that each one is deliberate, explained and countable, so the number can go down.

Self-check

  1. What does any actually disable?
    Every check on the value and on everything derived from it. Property access, calls, arithmetic and assignment are all permitted, and each result is itself any — so the absence of checking propagates outward through inference rather than staying where it was introduced. It is also assignable to every type, which means an unchecked value can be handed to a parameter promising a great deal, with no cast and no complaint.
  2. Why is unknown better than any for a parsed value?
    Because it accepts anything and permits nothing until narrowed, so the compiler forces the check to exist at the point the data enters. With any every subsequent line compiles and the failure surfaces far from the source — typically as a runtime TypeError in a function that had nothing to do with the parsing. The cost is one narrowing; the benefit is that every line after it is verified.
  3. What rule does a plain as follow, and why is it not much protection?
    The types must overlap in one direction — one has to be assignable to the other — so "paid" as number is rejected. It is not much protection because as unknown as number launders anything through the top type in two steps, and everyone learns that immediately. The one genuine benefit is that the double form is conspicuous and greppable, which makes it reviewable in a way an implicit any never is.
  4. Why is a type predicate preferable to scattered assertions?
    Because it concentrates the unverifiable claim in one named function that can be reviewed and unit-tested, and then reused everywhere. Both are assertions the compiler takes on trust — chapter 3 — but one of them is a single testable thing and the other is thirty as expressions across the codebase, each of which was true when written and may not be now.
  5. Why @ts-expect-error rather than @ts-ignore?
    Because it fails if the next line stops producing an error. So a suppression added for a genuine upstream bug cannot outlive the fix — the build tells you to remove it. @ts-ignore is silent forever, including after the dependency is updated, and it also hides any new error on that line, which is how a suppression added for one reason ends up concealing something else entirely.
  6. Which flag stops the most any from arriving?
    noImplicitAny. Without it, an unannotated parameter the compiler cannot contextually type, and every import from a dependency with no declarations, become any silently — so a codebase can be substantially unchecked while reporting zero errors. It is part of strict and it is the flag to turn on first when migrating, because it makes the remaining work visible. Chapters 11 and 17.
