CHAPTER 19

Declaration files and module augmentation

Most of the types in your project were written by someone else, and eventually one of them will be wrong, missing, or not quite what you need. This is how to read them, how to add the ones that are absent, and why the augmentation you wrote is being silently ignored.

Part 5 Meeting the real world·Reading time 35 minutes·Demos typing an untyped dependency, why augmentation fails·Prerequisites Chapters 2, 5

1What a .d.ts is

Types with the implementation removed. Nothing more exotic than that.

The same module, as source and as a declaration TypeScript
// ---- src/parse.ts — what you wrote
export interface Options { strict?: boolean }
export function parse(s: string, o?: Options): unknown {
  return JSON.parse(s);
}

// ---- dist/parse.d.ts — what `tsc --declaration` produced
export interface Options { strict?: boolean }
export declare function parse(s: string, o?: Options): unknown;
//     ↑ `declare` means: this exists, I am not telling you how

// Three places your types come from:
//   1. BUNDLED — the package ships .d.ts files and points at
//      them from package.json. The best case.
//   2. DEFINITELYTYPED — `npm i -D @types/foo`. Community
//      maintained, sometimes behind, occasionally wrong.
//   3. YOURS — a .d.ts in your project. Section 3.

// A file with no top-level import or export is a SCRIPT, and
// everything in it is GLOBAL. A file with either is a MODULE.
// That single distinction causes most of section 4's problems.

The four rules

1 · The file must be a module. It needs a top-level import or export, or your declare module 'x' is read as declaring a brand new ambient module rather than adding to an existing one. 2 · The specifier must match exactly what consumers import — 'express', not 'express/index'. 3 · Only interfaces and namespaces merge. A type alias cannot be reopened, which is Chapter 5's difference finally mattering. 4 · The file must be included by tsconfig — inside include, or listed in types/files. A .d.ts nobody loads is inert.

4Global augmentation

Same rules, one extra keyword, and one strong recommendation about process.env.

Extending the global scope from inside a module TypeScript
// src/globals.d.ts
export {};                      // ← makes this a module. Without it,
                                //   the declarations below are already
                                //   global and `declare global` errors.

declare global {
  interface Window {
    __APP_VERSION__: string;
  }

  // Non-standard but occasionally necessary:
  interface Array<T> {
    at(i: number): T | undefined;
  }
}

// The popular one, and the one to think twice about:
declare global {
  namespace NodeJS {
    interface ProcessEnv {
      DATABASE_URL: string;      // ← a lie
      PORT?: string;
    }
  }
}
// It is a lie because nothing checks it. If DATABASE_URL is
// missing, the type says `string` and the value is `undefined`,
// and you find out in a stack trace somewhere else. This is
// exactly Chapter 20's argument — parse the environment once at
// startup and export the result, rather than asserting its shape.

5Shipping types with your own package

Four lines of configuration, and the one that people get wrong.

package.json, for a package with both module formats JSON
{
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
Both keys, not one
"types" at the top level is the legacy lookup; the "types" condition inside "exports" is what modern resolution uses. Ship both, because you do not control which resolution mode your consumers set — this is the exact failure Chapter 2's demo showed as "the package has no types".
"types" must come first in the condition object
Conditions are matched in declaration order. Put it after "import" and it will never be reached.
Generate, do not hand-write
declaration: true in tsconfig. Hand-written declarations for your own package drift from the implementation within a release or two, and nothing checks them against it.
Verify with a tool
@arethetypeswrong/cli checks a packed tarball against every resolution mode and reports which consumers will fail. Two minutes, and it catches the class of problem that produces confused issue reports.
Ship declarationMap too
It lets "go to definition" land in your source rather than in a .d.ts, which is a considerable kindness to anyone debugging through your package.

A general diagnostic worth knowing: tsc --traceResolution prints every path the compiler tried for every import. It is extremely verbose and it answers "why is it not finding this" definitively, which no amount of guessing at tsconfig will.

7Check yourself

Five questions.

1. What makes a .d.ts file a module rather than a script?

A top-level import or export. Without one, everything declared in the file is global, and declare module 'express' { … } is read as declaring a brand new ambient module called 'express' rather than adding to the real one — which means your augmentation quietly does nothing, or worse, shadows the real types entirely. Adding export {} at the top is the conventional fix and costs nothing. The same distinction is why declare global requires a module: from a script you are already in the global scope, so the compiler rejects it with a message that names the rule.

2. Why can you augment an interface but not a type?

Because declaration merging is a property of interfaces (and namespaces): two interface declarations with the same name in the same scope combine into one. A type alias is a single binding — declaring it twice is a duplicate identifier error, not a merge. This is Chapter 5's difference finally having a practical consequence, and it is the reason libraries meant to be extended by their users declare their extension points as interfaces. If a library exposes something as a type alias and you need to add to it, you cannot; the options are a wrapper type of your own or a pull request.

3. Why is declare global { namespace NodeJS { interface ProcessEnv { DATABASE_URL: string } } } a lie?

Because nothing checks it. You have told the compiler that process.env.DATABASE_URL is a string, and if the variable is absent the value is undefined — so the type is wrong and the failure appears wherever the value is eventually used, with a message about the consequence rather than the cause. It is a type assertion spread across the whole program. The alternative is Chapter 20's: parse process.env once at startup against a schema, fail immediately and loudly if something is missing, and export the parsed object so every consumer receives a value whose type is actually true.

4. When is a stub .d.ts better than @types or full types?

When you use a small, stable part of a library and no maintained types exist. A stub covering the three functions you call takes ten minutes, gives real checking at every call site, and — importantly — fails loudly if a major upgrade changes those signatures, which declare module 'x' would not. The honest caveat is that a stub is unchecked against reality: nothing verifies it matches the library, so it can be confidently wrong. Keep it minimal for that reason, and prefer describing what you observe over what you assume.

5. Why ship both "types" and an "exports" types condition?

Because you do not control your consumers' moduleResolution. The top-level "types" field is the legacy lookup used by node resolution; the "types" condition inside "exports" is what node16, nodenext and bundler consult. Ship only the modern one and consumers on legacy resolution report that your package has no types; ship only the legacy one and modern consumers hit the same thing. Two extra lines avoids both. Order matters as well — conditions match in declaration order, so "types" must come before "import" and "require", and @arethetypeswrong/cli will tell you if it does not.
