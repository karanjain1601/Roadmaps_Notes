CHAPTER 08

Functions, overloads and variance

Typing a function is easy. Working out whether one function is assignable to another is where the type system stops feeling intuitive — because returns behave the way you expect and parameters behave in exactly the opposite direction, for a reason that is obvious once you see it.

Why parameters go backwards

Ask what the target's users are entitled to do. If the target is (x: Animal) => void, callers will pass any animal — a cat, a dog, anything. So a function that only handles dogs cannot stand in for it: it would receive a cat. A function that handles any animal, however, can — it copes with everything the callers might send. So the substitute's parameter must be at least as general as the target's. Returns are the opposite because the flow is opposite: the target's users expect at least an Animal back, and getting a Dog is more than enough. Accept more, return less.

3The method exception

Why strictFunctionTypes deliberately does not apply to methods.

Two ways to declare the same thing, checked differently TypeScript
interface A { cb: (x: Animal) => void }     // property syntax — CONTRAVARIANT
interface B { cb(x: Animal): void }        // method syntax — BIVARIANT

const a: A = { cb: (d: Dog) => d.bark() };   // error, correctly
const b: B = { cb: (d: Dog) => d.bark() };   // allowed — unsound, on purpose

// Why the hole exists: the standard library is full of methods
// whose sound typing would be unusable. Array is the canonical
// example — with fully sound method parameters, `Dog[]` would not
// be assignable to `Animal[]`, because push would accept a Cat.
// Every codebase would need casts everywhere.

// The practical rule:
//   • prefer PROPERTY syntax for callbacks you declare, so
//     strictFunctionTypes actually checks them
//   • use METHOD syntax when you want the looseness, or when
//     matching an existing interface's shape
//   • and remember Chapter 1's list — this is one of the
//     enumerable places a type-checking program can still throw

4Overloads, unions, or a generic

One requirement, three implementations, and they give the caller quite different things.

A function taking a string or a number and returning an array of the same Judge each on what the caller gets, not on how it looks.
Caller's return type—
Mixed call rejected—
Error quality—
Implementation cost—

The implementation signature is not callable
With overloads, only the declared overloads are visible to callers. The implementation's signature must be compatible with all of them and is invisible — which is why it is usually the widest and often needs a cast inside.
Overloads are tried top to bottom
So put the most specific first. A broad overload above a narrow one shadows it and the narrow one is unreachable.
Prefer a union parameter when the return does not depend on it
Overloads exist to express a correlation between argument and return type. If there is no correlation, one signature with a union parameter is simpler and gives better errors.

6Four assignability gotchas

All four are deliberate, and all four surprise people.

This is allowedBecause
arr.map(x => x) where map passes three argumentsA function with fewer parameters is assignable where more are expected. Ignoring arguments is always safe, and requiring you to declare unused ones would be miserable.
const f: () => void = () => 42A void return means "the result is ignored" (Chapter 3), so any return type is assignable. This is what makes the async forEach bug compile.
const f: (x: number, y: number) => void = (x: number) => {}Same rule as the first row — but note the reverse is not allowed: a function requiring more parameters than the target provides is correctly rejected.
const f: (x?: number) => void = (x: number) => {}Rejected, actually — an optional parameter means the target's callers may pass nothing, and the source demands a number. The mirror image is allowed. This is contravariance again, applied to optionality.

7Check yourself

Five questions.

1. Why must a substitute function's parameter be more general than the target's?

Because the target's callers get to pass anything the target's parameter type allows. If the target is (x: Animal) => void, someone will pass a cat — so a function that only handles dogs cannot stand in for it, because it would receive a cat and break. A function handling any animal can stand in, because it copes with everything callers might send. Returns work the opposite way for the same reason read in the other direction: the target's callers expect at least an Animal back, so returning a Dog is more than sufficient. The slogan is accept more, return less.

2. Why does strictFunctionTypes not apply to methods?

Because sound method parameters would make the standard library unusable. The canonical example is arrays: with fully contravariant method parameters, Dog[] would not be assignable to Animal[], since push on the target accepts a Cat — and virtually every codebase relies on that assignment. So method-syntax parameters remain bivariant on purpose, and it is one of the enumerable holes from Chapter 1. The practical consequence: prefer property syntax — cb: (x: Animal) => void — for callbacks you declare yourself, because that is the form the flag actually checks.

3. When do overloads beat a single union signature?

When the return type is correlated with the argument type. A single signature (x: string | number): string[] | number[] forces every caller to narrow a result they already know the type of, which is the real cost. Overloads give each call site the specific return type, and they also reject nonsensical mixed calls. If there is no correlation — the return type is the same whatever you pass — one signature with a union parameter is simpler and gives clearer errors, because a failed overload resolution reports every candidate and is genuinely hard to read.

4. Why is arr.map(x => x) legal when map passes three arguments?

Because a function with fewer parameters is assignable where more are expected. Ignoring arguments is always safe — the extra ones are simply not read — and requiring every callback to declare an index and an array it does not use would be miserable. The reverse is correctly rejected: a function demanding more parameters than the target supplies would read undefined. A related case that catches people is optionality: a target with an optional parameter cannot accept a source that requires it, because the target's callers may pass nothing. That is contravariance again, applied to whether an argument is provided at all.

5. What is the implementation signature of an overloaded function?

The one attached to the actual body, and it is not callable — only the declared overloads are visible to callers. It must be compatible with all of them, which in practice means it is the widest of the set, and because it is wider than any individual overload the body usually needs a cast or a narrowing check inside. Two related rules: overloads are resolved top to bottom, so the most specific must come first or a broader one above will shadow it and make it unreachable; and if you find the implementation signature is doing real work for callers, you probably wanted a union parameter or a generic instead.
