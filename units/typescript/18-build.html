Building and shipping

The compiler does two unrelated jobs — checking types and producing JavaScript — and almost every modern setup takes the second one away from it. That is the right call, and it means one thing must be true: something still has to run the checker, because the tool now emitting your code is not looking at types at all.

Who does what

Five setups, six responsibilities
One of them checks nothing at all
What a single-file transpiler cannot do

esbuild, SWC and Babel each see one file at a time and never build a program. So three things are impossible for them by construction: type checking, which needs the whole graph; declaration emit, which needs inferred types; and any feature whose output depends on another file — const enum inlining, and re-exporting a name without knowing whether it is a type.

isolatedModules is the flag that makes the compiler refuse the constructs those tools cannot handle, so your code stays portable between them. Turn it on before you swap the transpiler, not after — the errors it produces are all real and all small.

What a consumer actually gets

Your package, four ways
Try each against the three resolution modes
isolatedDeclarations, and why it is worth the annotations
It requires an explicit type on everything exported, so a .d.ts can be produced from one file without consulting the rest of the program. That makes declaration emit parallelisable and available to tools other than tsc — and it gives you chapter 5's benefit for free: your public contracts become decisions rather than inferences, so an internal change cannot silently alter your published API.
Ship source maps, and the sources with them
sourceMap plus declarationMap lets a consumer step into your code and use "go to definition" on your types. inlineSources avoids shipping a separate directory. It costs bytes nobody downloads at runtime and saves the person debugging your library an afternoon.
incremental and tsBuildInfoFile
Writes a cache of the last build so an unchanged file is not re-checked. Nearly free, substantial on a second run, and the file belongs in .gitignore and in your CI cache. composite implies it, and is what project references need — chapter 19.
Verify the published shape rather than assuming it
arethetypeswrong checks your tarball against every resolution mode a consumer might use and reports the specific failure — masquerading types, a missing condition, resolution that only works under node10. Run it in CI before publishing; the failures it catches are invisible from inside your own repository.

Self-check

  1. Why can esbuild not type-check?
    Because it transforms one file at a time and never builds a program. Type checking needs the whole import graph — the type of a value in another module, the declarations of every dependency, the inference that flows between them. esbuild simply deletes the type syntax, which is why it is so fast and why tsc --noEmit has to run somewhere as well. The two facts are the same fact.
  2. What does isolatedModules forbid, and why?
    Constructs whose correct output depends on another file: re-exporting a name without saying whether it is a type, and const enum, whose values must be inlined from a declaration elsewhere. A per-file transpiler cannot know either, so it would emit something wrong. The flag makes the compiler reject them, keeping your code portable between tsc and every fast transpiler.
  3. What does isolatedDeclarations require, and what does it buy?
    Explicit types on everything exported, so a declaration file can be generated from one file alone. That makes declaration emit parallelisable and available to tools other than tsc, which matters on a large library. It also has chapter 5's benefit built in: an inferred public API can be widened or narrowed by an unrelated internal change, and an annotated one cannot.
  4. Why does a dual package need types per condition?
    Because the ESM and CommonJS builds have genuinely different shapes — default export interop differs, and so does whether named exports exist — so one declaration file cannot describe both. Under nodenext the compiler picks the condition matching how the consumer's file will be loaded, and if you only supplied one set of types, half your consumers get declarations for the other format. The errors that produces are about default imports and make no sense in context.
  5. Why run arethetypeswrong in CI?
    Because the failures are invisible from inside your own repository — your tests import from source, not from the tarball, so a broken exports map or a missing types condition passes everything you run. The tool resolves your published package the way each consumer configuration would and reports the specific breakage. It is a few seconds in CI and it catches a whole class of bug you would otherwise learn about from an issue.
  6. Where should type checking happen if the bundler emits?
    In CI as a required step, and in the editor. The bundler will happily build code full of type errors, so a repository with no tsc --noEmit in its pipeline has a type checker that runs only on the machines of people who happen to have the editor open. Add it as a separate job — it is the cheapest gate you have and it runs in parallel with everything else.
