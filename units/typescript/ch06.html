CHAPTER 06

Unions and narrowing

A union says a value is one of several things. Narrowing is the compiler reading your ordinary JavaScript checks and working out which one it must be. Together they do more useful work than any other feature in the language, and there are six places the narrowing silently evaporates.

Part 2 Composing types·Reading time 40 minutes·Demos the narrowing engine, where narrowing is lost·Prerequisites Chapters 3, 5

1A union is a set of possibilities

Which means you may only do what is valid for every member.

The members are alternatives, not a combination
A | B is "one of these", so the operations available are the intersection of what A and B allow. That inversion — a union of types gives an intersection of capabilities — is worth sitting with, because it explains every "property does not exist on type" error you will get from a union.
Which is why narrowing exists
The union is the honest description of what you have. Narrowing is how you get from there to something you can actually use, and the compiler does it from checks you were going to write anyway.
Unions of object types are the interesting case
Reading a property that exists on all members works and gives you a union of its types. Reading one that exists on only some is an error until you narrow.
never is the empty union
Chapter 3. Narrowing away every member leaves never, which is exactly what the exhaustiveness check in section 5 exploits.

2Discriminated unions

One shared literal-typed field, and the whole pattern falls out.

The shape, and why it is worth restructuring code to get TypeScript
// A common property with a distinct LITERAL type per member.
type Result =
  | { status: 'loading' }
  | { status: 'ok'; data: User[] }
  | { status: 'error'; message: string; retryable: boolean };

// Checking the discriminant narrows to exactly one member.
function render(r: Result) {
  if (r.status === 'ok') return list(r.data);        // data exists here
  if (r.status === 'error') return err(r.message);   // message exists here
  return spinner();                                // r is { status: 'loading' }
}

// Compare the version people write first, and what it permits:
type Bad = {
  loading: boolean;
  data?: User[];
  error?: string;
};
// This type says { loading: true, data: […], error: 'x' } is valid.
// Eight combinations, five of them nonsense, and every consumer
// must defend against all of them. The discriminated version makes
// those states unrepresentable — Chapter 17's whole subject.
Requirements for the pattern to work

The discriminant must be a literal type, not string — which is why as const and Chapter 4 matter here. It must be present on every member, with a different value on each. And it should be a single property; the compiler can discriminate on several, but the errors get much harder to read. A boolean discriminant works and reads worse than 'ok' | 'error', because it cannot grow to a third case.

5Exhaustiveness that fails the build

Four words that convert a class of production incident into a compiler error.

Three ways, in order of preference TypeScript
// 1. A never-typed assignment in the default branch.
function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'square': return s.side ** 2;
    default: {
      const _never: never = s;      // add Triangle and THIS line errors
      throw new Error('unhandled: ' + JSON.stringify(s));
    }
  }
}

// 2. A helper, so the intent is named and reusable.
function assertNever(x: never): never {
  throw new Error('unhandled variant: ' + JSON.stringify(x));
}

The compile-time check protects your code; the runtime throw protects you from data that does not match your types at all — a payload from an API with a status you never modelled. Chapter 20.

7Check yourself

Five questions.

1. Why can you not read .length on a string | number?

Because a union is a set of alternatives, so the operations available are those valid for every member — and numbers have no length. A union of types gives you an intersection of capabilities, and that inversion explains essentially every "property does not exist on type" error you will meet from a union. It is not the compiler being unhelpful: the value genuinely might be a number, and reading .length would give undefined. Narrowing is the way out, and the point is that it uses checks you were going to write anyway.

2. What makes a union discriminated, and what must the discriminant be?

A property present on every member, with a distinct literal type on each. The literalness is the requirement people get wrong: if the field is typed string rather than 'ok' | 'error', checking it narrows nothing, which is why Chapter 4's widening rules matter here directly — an object built without as const or a matching annotation will have a widened discriminant and the pattern silently stops working. It should also be a single property; the compiler can discriminate on several but the errors become very hard to read.

3. Name three places narrowing is silently lost.

Inside a callback, because the compiler cannot know when it runs, so narrowing established outside does not apply within. After any function call, if the narrowed thing is a mutable property — the call might have reassigned it. And on a let that is reassigned in between. Two more worth knowing: narrowing a property of an object does not survive passing the object somewhere; and destructuring before the check loses the connection between the discriminant and the fields. The usual fix for all of them is the same: pull the narrowed value into a const immediately after the check and use that.

4. What does the exhaustiveness check buy you?

Adding a member to a union produces a compile error at every switch that does not handle it, naming the file and line. Assigning the narrowed value to a never-typed variable in the default branch works because a fully-handled union has narrowed to never there; add a case and it has not, so the assignment fails. Without it the new variant falls quietly to default and you learn about it from a user. It costs four words and it is the highest-value use of never in the language. Pair it with a runtime throw that stringifies the value, because data from outside your program need not match your types at all.

5. Why prefer a union of objects to an object with optional fields?

Because the optional-fields version permits states that make no sense. { loading: boolean; data?: T; error?: string } allows eight combinations of which five are nonsense — loading and errored simultaneously, ok with no data — and every consumer must defend against all of them, typically with a non-null assertion that is really a comment saying "this cannot happen". A union of three concrete members permits exactly the three real states. The test to apply: count the states the type allows against the states that are meaningful, and when they differ, the difference is work you have pushed onto every reader.
