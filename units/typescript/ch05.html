A rule you can actually apply

Use type by default. It does everything interface does for object shapes, plus unions, tuples, mapped types, conditional types and primitive aliases — so you never have to convert one into the other halfway through. Reach for interface in two situations: when you need declaration merging, which is the only way to augment a third-party module's types (Chapter 19); and on a large, widely-implemented public shape, where the compiler's caching and the named-type error messages are measurably better. Everything else is preference, and consistency within a file matters more than which one you picked.

2Excess property checks

The rule that looks inconsistent, is inconsistent, and is worth having anyway.

Structural typing says extra properties are fine — a value with more than the target requires still satisfies it (Chapter 1). But an object literal written directly at an assignment gets an additional check: unexpected properties are an error. The reasoning is that a surplus property in a freshly-written literal is almost always a typo or a misremembered API, and never intentional. That extra check applies only to fresh literals, which is where the confusion starts.

3Optional, undefined, and absent

Three states, two syntaxes, and one flag that separates them properly.

The distinction, and when it bites TypeScript
interface A { x?: number }              // may be absent
interface B { x: number | undefined }   // must be present, may be undefined
interface C { x?: number | undefined }  // either

const a: A = {};                        // fine
const b: B = {};                        // error — x is required

// Without exactOptionalPropertyTypes (Chapter 2), A and C are the
// same type — so this compiles:
const a2: A = { x: undefined };
// …and now these disagree, at runtime:
'x' in a2                                // true
Object.keys(a2)                            // ['x']
a2.x === undefined                       // true, for both {} and { x: undefined }

// Which matters the moment you merge or serialise:
{ ...defaults, ...a2 }                     // x: undefined WINS and clobbers the default
JSON.stringify(a2)                         // '{}' — the key is dropped
JSON.stringify({ x: null })              // '{"x":null}' — null survives
The spread clobber is the practical bug
An options object where a caller passed { timeout: undefined } explicitly will override your default with undefined, because spread copies present keys regardless of value. exactOptionalPropertyTypes makes that a type error instead of a support ticket.
Pick one convention for absence
undefined for "not provided" and null for "explicitly empty" is the common split, and it only works if the whole codebase agrees. Mixing them produces checks like x != null everywhere, which works and hides which case you meant.
Optional methods are usually a smell
onDone?: () => void is fine. save?(): void on an interface means every caller must check, and a no-op default is nearly always better.

4readonly

A compile-time promise, one level deep, and not a barrier to assignment.

Three things to know TypeScript
interface P { readonly id: string; readonly tags: string[] }

const p: P = { id: 'a', tags: [] };
p.id = 'b';          // error
p.tags.push('x');    // FINE — readonly is shallow. The reference is
                       // frozen, the array is not. Use readonly string[].

// 2. readonly does not stop you assigning it somewhere mutable
//    — for OBJECT properties. This is a known unsoundness:
interface Q { id: string }
const q: Q = p;          // allowed
q.id = 'b';              // and now p.id is 'b'

// 3. Arrays are the exception — readonly arrays are NOT assignable
//    to mutable ones, which is the behaviour you would expect:
const ro: readonly string[] = ['a'];
const mut: string[] = ro;     // error — correctly rejected

// And it emits nothing (Chapter 1). For real immutability:
const frozen = Object.freeze({ id: 'a' });   // also shallow, but real

5Index signatures

For objects whose keys you do not know, and the two rules that trip people.

Signatures, Record, and the conflict rule TypeScript
// An index signature says "any key of this kind maps to this type"
interface Counts { [key: string]: number }

// RULE 1: every declared property must be compatible with it.
interface Bad {
  [key: string]: number;
  name: string;      // error — string is not assignable to number
}
interface Good {
  [key: string]: number | string;
  name: string;      // fine — and now every read is number | string
}

// RULE 2: a numeric index must be assignable to the string index,
// because JavaScript object keys are strings anyway.

// Record is the same thing, more readable, and it accepts a union
// of keys — which an index signature cannot express:
type Counts2 = Record<string, number>;
type ByStatus = Record<'open' | 'closed', number>;   // exhaustive!

// The trap worth knowing: an index signature turns off excess
// property checking entirely, because every key is expected.
// And reading a missing key is typed as present unless you set
// noUncheckedIndexedAccess (Chapter 2):
const c: Counts = {};
c.nope.toFixed(2);   // compiles, throws

6Intersections, and what happens on conflict

& combines requirements. When they cannot both hold, the two syntaxes behave differently.

The difference that decides which to use TypeScript
// Compatible members: intersection is just "both".
type WithId = { id: string };
type WithTime = { at: Date };
type Event1 = WithId & WithTime;        // { id: string; at: Date }

// CONFLICTING members — here they diverge:
type T1 = { x: string } & { x: number };
// no error here. T1['x'] is string & number, which is never
// (Chapter 3) — so the type is silently unsatisfiable and you
// find out when you try to build one.

interface I1 { x: string }
interface I2 extends I1 { x: number }
// ERROR, immediately, at the declaration:
//   Interface 'I2' incorrectly extends interface 'I1'.
// The interface tells you at the point of the mistake.

// This is the strongest argument for interface on shapes you
// expect others to extend: the failure is reported where the
// error was made rather than where someone tries to use it.

7Declaration merging

Interfaces with the same name combine. Occasionally essential, mostly a hazard.

The one case that justifies it TypeScript
// Two declarations of the same interface merge into one.
interface User { id: string }
interface User { name: string }
// User is { id: string; name: string }
// A type alias declared twice is an error instead, which for
// your own code is the behaviour you want.

// Where merging is the only tool: adding to somebody else's types.
declare module 'express' {
  interface Request {
    user?: AuthUser;        // your middleware puts this here
  }
}

// And for globals:
declare global {
  interface Window { __APP_VERSION__: string }
}

// The hazard: within your own codebase, two interfaces of the
// same name in the same scope merge SILENTLY. A duplicated name
// after a refactor does not error — it produces a type with the
// members of both, which then fails somewhere else entirely.
// One more reason to default to `type`. Chapter 19 has the rest.

8Check yourself

Five questions.

1. Give two things only type can do and one thing only interface can do.

type only: unions, tuples, mapped types, conditional types, primitive aliases, and template literal types — anything that is not an object shape. interface only: declaration merging, which is the sole mechanism for adding members to a third-party module's types or to a global such as Window. The practical rule that follows is to default to type, because it covers every object shape as well and you will never have to convert one halfway through a refactor, and reach for interface when you need merging or when a large widely-extended public shape would benefit from its better error messages and compiler caching.

2. Why does the excess property check exist if structural typing says extra properties are fine?

Because a surplus property in an object literal written directly at an assignment is almost never intentional — it is a typo, a misremembered option name, or a leftover from a rename. Structural typing is still the underlying rule; the excess check is an extra pass applied only to fresh object literals, on the reasoning that when you have just written the object out you presumably meant every key in it. That freshness condition is where the apparent inconsistency comes from: the identical object assigned through a variable is accepted, because at that point it is a value with a type rather than a literal you are writing.

3. Which is worse: { x?: number } or { x: number | undefined }?

Neither is worse; they say different things. The first means the key may be absent; the second means the key must be present and may hold undefined. Without exactOptionalPropertyTypes the compiler treats them as interchangeable, and that is where trouble comes from — because at runtime they are not. 'x' in obj and Object.keys distinguish them, JSON.stringify drops an undefined value entirely, and most consequentially a spread copies a present-but-undefined key and clobbers your default. Turn the flag on and the compiler enforces the distinction you were relying on anyway.

4. What does readonly not protect you from?

Three things. It is shallow, so readonly tags: string[] freezes the reference and not the array — p.tags.push(x) is legal, and you want readonly string[]. It does not prevent assignment to a mutable type for object properties: a value with readonly properties is assignable to an interface without them, and the recipient can then write through it, which is a documented unsoundness. And it emits nothing, so it is a compile-time promise only and anyone with an as any can ignore it. Arrays are the pleasing exception: a readonly array is correctly rejected where a mutable one is expected.

5. What two things does an index signature quietly do to your type?

It turns off excess property checking entirely, because every key is now expected — so the typo protection from section 2 disappears from that type. And it makes reads of missing keys type as present, so counts.nope.toFixed(2) compiles and throws, unless you have turned on noUncheckedIndexedAccess. There is also the constraint rule worth remembering: every declared property must be assignable to the index signature's value type, so adding name: string to [key: string]: number is an error, and widening the signature to accommodate it makes every read a union. Prefer Record with a union of keys where you can, since that stays exhaustive.
