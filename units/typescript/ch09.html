Why this is not a bug

A sound type system would make Dog[] unassignable to Animal[], because a mutable array's element type appears in both a read position and a write position — so it can be neither covariant nor contravariant. Every function taking Animal[] would then reject every concrete array you have, and real codebases would be full of casts. TypeScript chose the useful behaviour. The mitigation is readonly: a readonly Animal[] parameter has no write position, so covariance is genuinely safe there — which is why declaring array parameters as readonly T[] is the single best habit in this chapter.

3Tuples

Fixed length, positional types, and four features people miss.

Labels, optionality, rest elements TypeScript
// Positional, with a literal length type
type Pair = [string, number];
const p: Pair = ['a', 1];
p.length;                          // 2 — a literal type, not number

// 1. LABELS. No effect on the type; large effect on tooling — the
//    editor shows the names in hints and destructuring suggestions.
type Range = [start: number, end: number];

// 2. OPTIONAL elements, which must come last
type Point = [x: number, y: number, z?: number];
// length is 2 | 3

// 3. REST elements, in any single position
type Row = [id: string, ...cells: number[]];
type Tail = [...init: number[], last: string];   // leading rest also works

// 4. Tuples are what a PARAMETER LIST is. This is the connection
//    that makes Chapter 14's Parameters<T> possible:
type Args = Parameters<(a: string, b: number) => void>;   // [a: string, b: number]
function call(...args: Args) {}                        // and back again

// The hole worth knowing: push works on a tuple.
p.push('oops');                    // compiles. p.length still says 2.
// A tuple's array methods are typed against the union of its
// element types, so mutating methods are not constrained by the
// fixed length. `readonly [string, number]` removes them entirely.

4Variadic tuple types

Spreading a type parameter into a tuple. The mechanism behind most well-typed utility functions.

Three things it unlocks TypeScript
// 1. Concatenation that keeps every position
function concat<A extends readonly unknown[], B extends readonly unknown[]>(
  a: A, b: B
): [...A, ...B] {
  return [...a, ...b];
}
concat(['a'] as const, [1, true] as const);
// ['a', 1, true] — not (string | number | boolean)[]

// 2. Partial application, typed exactly
function partial<H extends readonly unknown[], R extends readonly unknown[], Ret>(
  fn: (...args: [...H, ...R]) => Ret,
  ...head: H
): (...rest: R) => Ret {
  return (...rest) => fn(...head, ...rest);
}

// 3. Wrapping a function while preserving its whole signature —
//    the pattern behind every well-typed decorator and middleware
function logged<F extends (...args: any[]) => any>(fn: F): F {
  return ((...args: Parameters<F>) => {
    console.time(fn.name);
    try { return fn(...args); } finally { console.timeEnd(fn.name); }
  }) as F;
}

// Note the `as F` — same category as Chapter 8's conditional
// return: the compiler cannot verify a body against a generic
// signature it has not resolved. One reviewable cast.

5readonly collections

Which direction they assign, and the habit worth adopting.

The assignability direction is the useful one
T[] is assignable to readonly T[]; the reverse is not. So a readonly T[] parameter accepts both mutable and readonly arrays — it is strictly more permissive to callers and strictly safer inside. There is almost no reason to declare a mutable array parameter unless you intend to mutate it.
Three syntaxes, two meanings
readonly T[] and ReadonlyArray<T> are the same. Readonly<T[]> is not — it maps the properties of the array object, which happens to produce something similar and is not the idiom.
It is shallow, as always
readonly User[] stops you replacing elements and does nothing about mutating a user inside. Chapter 5.
Maps and Sets have readonly forms too
ReadonlyMap, ReadonlySet. Same reasoning, same habit for parameters.
And it costs nothing at runtime
Chapter 1. If you need a collection that genuinely cannot be mutated, freeze it or copy on read.

6Iterables

What for...of needs, and why it sometimes complains about a Set.

The types, and the two flags TypeScript
// Accept anything iterable rather than requiring an array — the
// same argument as readonly parameters, one level more general.
function firstOf<T>(xs: Iterable<T>): T | undefined {
  for (const x of xs) return x;
}
firstOf([1, 2]); firstOf(new Set([1])); firstOf(map.values());   // all fine

// Generators are typed with three parameters:
//   Generator<Yield, Return, Next>
function* ids(): Generator<string, void, undefined> { yield 'a'; }

// Two configuration notes that cause real confusion:

//     ES2015+ you do not need it.

7Check yourself

Five questions, closing Part 2.

1. Why is Dog[] assignable to Animal[] when that is unsound?

Because a mutable array's element type appears in both a read position and a write position, so it can be neither covariant nor contravariant — and a sound rule would make Dog[] unassignable to Animal[], which would reject essentially every array you ever pass to a general-purpose function. TypeScript took the useful behaviour and accepted the hole: you can pass a Dog[] as an Animal[], that function can push a Cat, and reading it back as a Dog gives you something with no bark. The mitigation is readonly — a readonly Animal[] has no write position, so covariance is genuinely safe there.

2. Why declare array parameters as readonly T[]?

Because the assignability runs the helpful way: T[] is assignable to readonly T[] and not the reverse. So a readonly parameter accepts both mutable and readonly arguments — strictly more permissive to callers — while preventing your function from mutating something the caller still holds, which closes the covariance hole for that parameter. It also documents intent: a mutable array parameter now means "this function mutates it", which is information. There is almost no reason to write the mutable form unless you genuinely intend to modify the caller's array.

3. What can you do to a tuple that its type says you cannot?

push. A tuple's array methods are typed against the union of its element types, so mutating methods are not constrained by the fixed length: const p: [string, number] = ['a', 1]; p.push('oops') compiles, and p.length still reports the literal type 2 while the array has three elements. It is the same category of documented hole as array covariance and it has the same fix — readonly [string, number] removes the mutating methods entirely. Worth knowing because a tuple's whole appeal is the fixed shape, and that guarantee is weaker than it looks.

4. What is the connection between tuples and function parameters?

A parameter list is a tuple, as far as the type system is concerned. That is why Parameters<F> gives you a labelled tuple, why you can spread a tuple type into a rest parameter with (...args: Args), and why variadic tuple types can express things like partial application and signature-preserving wrappers. It is the single idea that makes most well-typed utility functions possible: [...H, ...R] as a parameter list lets you split a signature in two and keep both halves exact, which is how a typed partial or a middleware wrapper works.

5. Why does for...of over a Set sometimes fail to compile?

Because lib does not include a modern enough ES target, so the compiler's declaration of Set has no [Symbol.iterator] and it reports that the value is not an array type and has no iterator. It is a configuration problem rather than a code problem — Chapter 2 — and the fix is lib, not a cast. The related flag is downlevelIteration, needed to spread or iterate an arbitrary iterable when targeting ES5, and it emits a runtime helper. Targeting ES2015 or later removes the need for it. Separately, prefer Iterable<T> to T[] for parameters you only iterate — the same generosity argument as readonly.
