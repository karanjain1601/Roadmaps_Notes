The whole implementation TypeScript
// One declaration, reusable for every id type in the codebase.
declare const brand: unique symbol;
export type Brand<T, B extends string> = T & { readonly [brand]: B };

export type UserId  = Brand<string, 'UserId'>;
export type OrderId = Brand<string, 'OrderId'>;
export type Cents   = Brand<number, 'Cents'>;
export type Email   = Brand<string, 'Email'>;

// A `unique symbol` key means the brand cannot be written by
// accident and cannot collide across modules — and since it is
// declared, never defined, the property does not exist at runtime.

// The ONE place a cast is correct, because it is the one place
// the invariant is actually established:
export function toEmail(s: string): Email {
  if (!s.includes('@')) throw new Error(`not an email: ${s}`);
  return s as Email;      // checked immediately above
}

// Everything downstream now receives an Email and needs no
// further checking. That is the pattern in section 4.

3State machines

Section 1 applied to something that changes over time, and the payload travels with the state.

An order lifecycle where the wrong field cannot be read TypeScript
type Order =
  | { status: 'draft';     items: Item[] }
  | { status: 'placed';    items: Item[]; placedAt: Date; total: Cents }
  | { status: 'shipped';   items: Item[]; placedAt: Date; total: Cents;
                            tracking: string }
  | { status: 'cancelled'; items: Item[]; reason: string };

// A draft has no total, so `order.total` on an unnarrowed Order is
// a compile error rather than `undefined` reaching a currency
// formatter. That is the entire value proposition.

// Transitions, typed as functions from one member to another:
type OrderOf<S extends Order['status']> = Extract<Order, { status: S }>;

function place(o: OrderOf<'draft'>, total: Cents): OrderOf<'placed'> {
  return { ...o, status: 'placed', placedAt: new Date(), total };
}
// place(shippedOrder, …) does not compile. The set of legal
// transitions is now in the type system rather than in a comment.

// Note Extract from Chapter 14 doing the work — pulling one member
// out of a union by its discriminant is most of what it is for.

4Parse, don't validate

The principle that ties sections 1 to 3 together, in one sentence.

A validator answers a question and throws the answer away: isEmail(s) returns a boolean, and the string is still a string afterwards, so the next function has to ask again. A parser returns a value whose type records what was learned: toEmail(s) returns an Email, and nothing downstream can forget. The whole of this chapter is that idea applied at different scales — a branded type records a checked invariant about a primitive, a discriminated union records which fields are meaningful, and a state machine records which transitions are legal.

5How much of Part 4 belongs in application code

An opinionated answer, offered as one reasonable position rather than the only one.

Discriminated unions — everywhere, without hesitation
No advanced machinery, enormous return. If you take one thing from this unit, take section 1.
Branded types — for identifiers and checked primitives
Ten lines total, zero runtime cost, and they catch the class of bug that is hardest to find by testing. The cost is one as in each constructor function, in the one place where the cast is honest.
satisfies, as const, Extract, Pick — freely
These are load-bearing and readable. Chapters 4 and 14.
Mapped and conditional types — when deriving one shape from another
Deriving a form's field types from its model, or an API client's methods from a route table, is worth it because the alternative is two things that must be kept in step by hand. Two or three in a codebase is healthy.
Recursive type-level computation — almost never
Chapter 16's section 6. Use the ones your libraries ship; do not write them. The exception is a library author, whose users pay nothing and benefit a great deal.
And a test for the whole question
If the type would take longer to explain to a colleague than the bug it prevents would take to find, write the simpler type. That is not an argument against expressiveness — it is a reminder that a type is read far more often than it is written.

6Check yourself

Five questions, closing Part 4.

1. What is wrong with { isLoading: boolean; data: T | null; error: Error | null }?

It can describe eight states, of which four are nonsense — loading with data, loading with an error, data and an error together, and all three at once. Every one of those is representable, so every consumer has to decide what to do about combinations that should never occur, usually by checking the fields in a particular order and hoping everyone else picked the same order. The discriminated union describes exactly four states and no invalid ones, which means the "what if both are set" question disappears rather than being handled. Adding a fifth field to the flat version doubles the nonsense; adding a fifth state to the union adds one state.

2. Why does type UserId = string catch nothing?

Because a type alias is a name, not a type — UserId and string are the same type, so every string is a UserId and an OrderId passes anywhere a UserId is expected. This is structural typing working exactly as designed (Chapter 1), and the alias is documentation that the compiler does not read. A brand adds a phantom property that only the constructor function can produce, which makes the type genuinely distinct while remaining a string at runtime and costing nothing.

3. Why a unique symbol for the brand key rather than a string?

Two reasons. It cannot be written by accident — nobody can construct a value satisfying { [brand]: 'UserId' } without access to the declared symbol, so the only route to a UserId is your constructor function. And it cannot collide: two modules that both brand with a string key called __brand produce types that are structurally compatible, which quietly defeats the whole exercise. The symbol is declared and never defined, so the property does not exist at runtime and the brand is erased along with every other type.

4. Where is an as cast the right answer?

In the constructor of a branded type, immediately after the check that establishes the invariant: if (!s.includes('@')) throw; return s as Email. The cast is honest because the line above it is the reason it is true, the two cannot drift apart, and the assertion is confined to about four lines that a reviewer can verify at a glance. Compare with an as at a call site, which asserts something the surrounding code does not demonstrate and cannot be checked by anyone reading it later. Chapter 21 makes this argument in general; this is its clearest instance.

5. Which techniques from Part 4 belong in ordinary application code?

Discriminated unions everywhere, without hesitation — no advanced machinery, enormous return. Branded types for identifiers and checked primitives, because they are ten lines with no runtime cost and they catch the bug class that testing finds worst. satisfies, as const, Extract and Pick freely. Mapped and conditional types when you are deriving one shape from another and the alternative is two things kept in step by hand — two or three per codebase is healthy. Recursive type-level computation almost never: use what your libraries ship. The test is whether the type takes longer to explain than the bug it prevents takes to find.
