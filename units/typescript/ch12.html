CHAPTER 12

Conditional types and infer

A ternary that operates on types, plus an operator that reads a type apart and captures a piece of it. Between them they produce every utility type in the standard library — and one behaviour that surprises everyone, exactly once, memorably.

Part 3 Generics·Reading time 40 minutes·Demos distribution on and off, where infer may appear·Prerequisites Chapters 3, 11

1The operator

Same shape as a ternary, and extends means the same thing it meant in Chapter 11.

Reading one TypeScript
type IsString<T> = T extends string ? true : false;

type A = IsString<'hello'>;      // true
type B = IsString<number>;       // false

// Read as: "if T is assignable to string, then true, else false".
// Not equality — assignability, so 'hello' passes and so does
// string itself.

// They nest, and this is how a lookup table is written at the
// type level:
type TypeName<T> =
  T extends string   ? 'string'
  : T extends number ? 'number'
  : T extends boolean? 'boolean'
  : 'object';

// And they are LAZY — an unresolved conditional stays unresolved,
// which is why a conditional inside a generic function body cannot
// be checked (Chapter 8's `as any` caveat).
type Deferred<T> = T extends string ? string[] : number[];
// inside `function f<T>(): Deferred<T>`, the compiler knows
// nothing about which branch applies until T is supplied.

The two rules

A conditional type distributes when the checked type is a naked type parameter. The union is split, the conditional is applied to each member separately, and the results are unioned back together. That is why Exclude works, and why T extends string ? true : false on string | number gives boolean rather than false. Wrapping either side in a tuple stops it — [T] extends [string] checks the whole union at once. And the special case worth memorising: never is the empty union, so a distributive conditional over never evaluates zero branches and returns never, which is not what most people expect the first time.

4The standard library, rebuilt

Six utility types, each one or two lines, all from the two mechanisms above.

These are close to the real definitions TypeScript
// Distribution + never-as-filter. The whole of Exclude.
type Exclude<T, U> = T extends U ? never : T;
type Extract<T, U> = T extends U ? T : never;

// Which makes this a one-liner:
type NonNullable<T> = T & {};      // the modern definition — {} excludes
                                       // null and undefined (Chapter 3)

// infer in a return position:
type ReturnType<T extends (...a: never[]) => unknown> =
  T extends (...a: never[]) => infer R ? R : never;

// infer in a parameter position — captured as a tuple (Chapter 9):
type Parameters<T extends (...a: never[]) => unknown> =
  T extends (...a: infer P) => unknown ? P : never;

// Recursive, to unwrap nested promises:
type Awaited<T> = T extends PromiseLike<infer U> ? Awaited<U> : T;

// Note `(...a: never[])` in the constraints. Chapter 11's recipe:
// never in a parameter position is contravariantly compatible with
// every parameter list, so the constraint accepts any function
// without using `any`.

5Three never behaviours to keep straight

All three come from never being the empty union, and they pull in different directions.

1 · In a result, it filters
T extends U ? never : T removes matching members, because a never result disappears when the branches are unioned back together. This is Exclude, and it is the useful one.
2 · As the input, it short-circuits
Exclude<never, 'a'> is never — not because the branch was taken but because there were no members to iterate. A distributive conditional over never evaluates nothing at all, which means a check like T extends never ? 'yes' : 'no' returns never rather than 'yes'. Wrap it: [T] extends [never].
3 · In a constraint, it is the bottom
T extends never is satisfied only by never. Combined with rule 2, this makes "is this type never" the single most awkward question to ask, and [T] extends [never] ? true : false the standard answer.
And a fourth, adjacent
any distributes to both branches: T extends string ? 'y' : 'n' with T = any gives 'y' | 'n'. Worth knowing when a conditional type mysteriously returns a union — an any has leaked in somewhere upstream.

6Debugging one

Four techniques, because the error messages are the worst in the language.

Making an unresolved type visible TypeScript
// 1. Force the compiler to show you a type, by asserting equality.
type Expect<T extends true> = T;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends
  (<T>() => T extends B ? 1 : 2) ? true : false;

type _test = Expect<Equal<Exclude<'a' | 'b', 'a'>, 'b'>>;
// A red squiggle here IS the failing test. Type-level tests cost
// nothing at runtime and catch exactly this class of mistake.

// 2. Expand an object type so the editor stops showing the alias.
type Pretty<T> = { [K in keyof T]: T[K] } & {};
type Readable = Pretty<SomeAwfulIntersection>;

//    bug is visible the moment T is a concrete type.

//    did not expect, or `never` where you expected a value, the

7Check yourself

Five questions.

1. Why is IsString<string | number> equal to boolean?

Because the conditional distributes. The checked type is a naked type parameter, so the union is split, the conditional is applied to each member separately — string gives true, number gives false — and the results are unioned back together as true | false, which is boolean. It is not that the compiler decided the union "is not a string". If you wanted the whole union tested at once, wrap both sides in a tuple: [T] extends [string] ? true : false gives false, because the union as a unit is not assignable to string.

2. How does Exclude work?

T extends U ? never : T, and it needs both of this chapter's mechanisms. Distribution splits the union so each member is tested individually; and never in a result disappears when the branches are unioned back together, because never is the identity for union (Chapter 3). So the members matching U become never and vanish, and the rest come through unchanged. Extract is the same line with the branches swapped. That is genuinely the whole implementation — one of the pleasing moments in the language, and the reason those two utilities are one-liners.

3. Why does T extends never ? 'yes' : 'no' give never when T is never?

Because never is the empty union, and a distributive conditional iterates the members of a union. With no members there is nothing to iterate, so zero branches are evaluated and the result is the union of nothing, which is never — the 'yes' branch is never reached, not because the check failed but because the check never ran. This is the single most counter-intuitive behaviour in the chapter. To ask the question you actually meant, switch distribution off: [T] extends [never] ? 'yes' : 'no'.

4. Where can infer appear?

Only inside the extends clause of a conditional type, in a position where the compiler is matching a pattern — a function's return type, a parameter list captured as a tuple, a generic type argument such as PromiseLike<infer U>, an array's element type, a tuple position, or a property type. It cannot appear in the true or false branches, in a type alias outside a conditional, or in a constraint. Several infers in one pattern are fine and often useful — capturing a tuple's head and tail together, for instance. If the same name appears in more than one position, the results are combined rather than conflicting.

5. A conditional type unexpectedly returns a union of both branches. What happened?

Either the input was a union and the conditional distributed — the ordinary case, fixed by wrapping in tuples if you wanted the whole thing tested at once — or an any has leaked in upstream. any is special-cased to distribute to both branches, so T extends string ? 'y' : 'n' with T = any gives 'y' | 'n'. That second cause is worth knowing because it points somewhere else entirely: the conditional is fine and something above it lost its type, usually a JSON.parse or an untyped dependency (Chapter 3). Write a type-level test with Expect<Equal<…>> to pin the behaviour once you have fixed it.

Carry forward

A naked type parameter distributes; a tuple-wrapped one does not. never in a result filters, and never as the input evaluates nothing at all. Exclude is one line that needs both facts. An unexpected union of both branches means distribution or a leaked any.
