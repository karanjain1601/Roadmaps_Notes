CHAPTER 04

Inference, widening and as const

Most types in a well-written codebase are never written down. The compiler works them out — and then deliberately makes some of them less specific than they could be, which is the single most confusing thing about it until you know why.

1Four things the compiler infers

And the direction each one flows in, which turns out to be the whole story.

From an initialiser, outward
const n = 3 gives n a type from the value. Information flows from the expression to the name.
Return types, outward
A function's return type comes from its return statements. You almost never need to write it, and section 6 explains the one case where you should.
Contextual typing, inward
This is the one that goes the other way. When an expression sits in a position whose type is already known, that type flows into it — which is why a callback's parameters need no annotations. Section 3.
Generic type arguments, from the call
identity(3) infers T = number from the argument. Chapter 11 covers where the compiler looks and how to steer it.

Why widening exists

Because the type of a variable has to accommodate every value it might hold later. If let s = 'open' inferred the type 'open', then s = 'closed' would be an error and let would be useless. So the compiler widens a literal to its base type for anything mutable, and keeps the literal type for anything that cannot change. That is the entire rule: widening is about mutability, not about literals. Which is also why as const works by making things readonly — the narrow type is a consequence.

3Contextual typing

Information flowing inward, and the reason your callbacks have no annotations.

The type comes from the position TypeScript
// No annotations here, and n is number, i is number.
// The type flowed IN from map's signature.
[1, 2, 3].map((n, i) => n * i);

// Same mechanism, and it is why this compiles with no ceremony:
const handler: (e: MouseEvent) => void = (e) => e.clientX;
//                                                 ↑ e is MouseEvent

// And why an object literal in an argument position keeps its
// narrow types WITHOUT as const — the expected type provides them:
declare function request(o: { method: 'GET' | 'POST' }): void;
request({ method: 'GET' });          // fine, no widening

// …but not once it goes through a variable, because there is no
// longer a context to type it from. That is section 5.
const o = { method: 'GET' };            // { method: string }
request(o);                            // error

// Contextual typing also explains this asymmetry, which looks
// like a bug and is not:
const f: () => string = () => 'a';      // returns string
const g = () => 'a';                    // returns string too — return
                                       // positions widen as well
Annotate the variable, not the function
const f: Handler = (e) => … gives the parameters their types for free. const f = (e: Event) => … makes you write them and does not check the shape of the whole function against anything.
It is why satisfies is useful
An annotation provides context and therefore replaces the inferred type. satisfies provides context for checking and keeps the inferred type. Section 5, and Chapter 17.
It does not reach through a variable
Once a value is bound to a name with no annotation, its type is fixed by widening, and the eventual use site has no say. That single fact causes most of the confusion in section 5.

4What as const actually does

Two things, one of which people rely on without noticing.

Readonly, deeply, and therefore narrow TypeScript
const a = { id: 1, tags: ['new'] };
// { id: number; tags: string[] }

const b = { id: 1, tags: ['new'] } as const;
// { readonly id: 1; readonly tags: readonly ['new'] }
//   ↑ readonly           ↑ literal        ↑ tuple, not array

// Three consequences worth separating:
//   1. every property becomes readonly, recursively
//   2. every literal keeps its literal type
//   3. arrays become readonly TUPLES — fixed length, positional
//
// (3) is the one people use without realising. It is what makes
// this work:
const ROUTES = ['home', 'about'] as const;
type Route = typeof ROUTES[number];      // 'home' | 'about'

// It emits nothing (Chapter 1) — the object is fully mutable at
// runtime. readonly is a compile-time promise only:
(b as any).id = 99;                     // works, silently

// And it is not the same as Object.freeze, which is real:
const c = Object.freeze({ id: 1 });   // readonly AND actually frozen

6When to annotate

One rule, and three exceptions to it.

Annotate the inputs and the boundaries. Infer everything else.

Function parameters always, because nothing else can determine them and they are your contract. Everything a consumer outside the module can see. And nothing else — local variables, return types, intermediate values — because an annotation there is a second source of truth that can drift from the code, and the compiler is better at it than you are.

Exception 1: a public API's return type
Annotating it means a change inside the function that alters the return type fails there rather than at every call site. On an exported function that is worth the duplication; on a local one it is noise.
Exception 2: when inference gives you something worse
An empty array infers any[]. An accumulator in a reduce often needs help. A recursive function cannot always infer its own return type. Annotate and move on.
Exception 3: when the annotation is the check
const config: Config = { … } verifies the object against Config. Note that this is the section 5 trade — you get the check and lose the precise types. satisfies is usually what you wanted.
And an anti-pattern worth naming
Annotating something with the type it already has. const n: number = 3 adds nothing and will be wrong the day the initialiser changes.

7Where inference misleads

Five cases where the inferred type is legal and unhelpful.

CodeWhat you get, and the fix
const xs = []any[] — and every push is unchecked. Annotate: const xs: string[] = []. Under noImplicitAny this is an error only in some positions, so it slips through.
let x = nullnull, so nothing else can be assigned. Usually you meant let x: string | null = null.
arr.reduce((a, b) => …, {})The accumulator infers {} from the seed and then rejects every property you set. Pass the type argument: reduce<Record<string, number>>(…).

A useful habit: hover the things you did not annotate. Any time the answer is any, any[], {} or never[], inference has given up and you are no longer being checked. That hover is the cheapest audit available.

8Check yourself

Five questions.

1. Why does let s = 'open' infer string rather than 'open'?

Because s can be reassigned, and the type has to accommodate every value it might hold. If it inferred 'open' then s = 'closed' would be an error and let would be almost unusable. A const cannot be reassigned, so the literal type is kept. The rule to remember is that widening is about mutability, not about literals — which is also why as const achieves narrow types by making things readonly. The narrowness is a consequence of the immutability, not a separate feature.

2. Why does request({ method: 'GET' }) compile when request(o) does not?

Contextual typing. In the first case the object literal sits in an argument position whose expected type is known, so that type flows inward and 'GET' keeps its literal type. In the second, const o = { method: 'GET' } was typed on its own with no context available, so method widened to string — and by the time the value reaches the call site its type is already fixed. Contextual typing does not reach through a variable. That single fact is behind most of the confusion in this chapter, and the fix is one of the four in section 5.

3. What are the three things as const does?

Every property becomes readonly, recursively; every literal keeps its literal type rather than widening; and arrays become readonly tuples — fixed length, positional types. The third is the one people rely on without noticing: it is what makes typeof ROUTES[number] produce a union of the actual strings rather than just string. Two caveats: it emits nothing, so the object is entirely mutable at runtime and readonly is a compile-time promise only; and it is therefore not Object.freeze, which is real but only shallow.

4. Annotating versus satisfies — what is the difference?

An annotation replaces the inferred type with the declared one: const c: Config = {...} checks the object and then c.method is 'GET' | 'POST', because that is what Config says — you have lost the knowledge that it is specifically 'GET'. satisfies checks against the type and keeps the inferred type, so c.method stays 'GET'. It also still catches excess properties and missing required ones. That combination — verified against a contract, precise about the actual value — is what you almost always wanted, which is why it is worth reaching for by default on configuration objects.

5. Name two places inference gives you something legal and useless.

const xs = [] infers any[], so every subsequent push is unchecked and the array's contents are never verified. And JSON.parse(s) returns any, which contaminates every value derived from it — Chapter 3's contagion, arriving through the front door of every application that talks to an API. Two more worth knowing: let x = null infers null and accepts nothing else, and a reduce with {} as its seed infers an accumulator that rejects every property you try to set. The general audit: hover anything you did not annotate, and if the answer is any, any[], {} or never[], inference has given up.
