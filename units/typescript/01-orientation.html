What TypeScript actually is

A static checker that runs over JavaScript and then deletes itself. Nothing it knows survives into the program, and it compares types by shape rather than by name. Those two facts are not trivia — they are the reason for almost every surprise in the next nineteen chapters.

Erasure

The compiler's output is JavaScript with the types removed. Almost everything you write in the type language leaves no trace — and the handful of exceptions are worth knowing precisely, because they are the features that behave unlike the rest of the language.

The sentence to remember

A type is a claim about your code, never a check on your data. function f(x: number) does not verify that x is a number — it asserts that every call site the compiler can see passes one. Data arriving from outside the program has been checked by nobody: a request body, a JSON file, a message from a queue, a value from a library whose types are wrong. Chapter 13 is entirely about that seam, and chapter 11 of the Node unit is the same argument from the runtime's side.

Where it sits, and what it is not

TypeScript is a superset of JavaScript — valid JavaScript is valid TypeScript, and every JavaScript feature is available. It adds no runtime library, no standard collections, no operator overloading and no reflection. There is nothing to import at runtime, because there is no runtime.

Which means the version you care about is two versions: the TypeScript version, which decides what type syntax you may write; and the target and lib settings, which decide what JavaScript is emitted and which built-ins the compiler believes exist. Chapter 11.

Self-check

  1. What does it mean that TypeScript is erased?
    The compiler checks your code and then emits JavaScript with all type syntax removed. No annotation, interface, alias or generic exists at runtime, so nothing can be inspected, reflected over or validated against. A type is a claim the compiler tries to verify at the call sites it can see — not a guard that runs when your program does.
  2. Which TypeScript features do not erase?
    The four that emit runtime code: enum (which becomes an object), parameter properties in a constructor (which become assignments), decorators (which become function calls), and namespace (which becomes an IIFE). They are the least JavaScript-like parts of the language, and each is worth avoiding or using deliberately rather than by accident — chapter 12.
  3. Why are two interfaces with identical members interchangeable?
    Because TypeScript compares types structurally: a type is assignable if it has the required members with compatible types, regardless of its name or where it was declared. That matches how JavaScript actually works, since nothing in JavaScript tracks which interface an object was meant to satisfy, and it makes typing existing code far more practical than a nominal system would.
  4. Why does an object literal with an extra property fail when a variable of the same type does not?
    Excess property checking, which applies only to fresh object literals assigned directly to a typed target. The reasoning is that a literal written on the spot with an unexpected key is almost always a typo or a misunderstanding, whereas a value that came from elsewhere may legitimately carry extra members. It is a deliberate exception to structural assignability, and it disappears the moment the literal is put in a variable first.
  5. Why do UserId and OrderId need branding?
    Because if both are aliases for string they are the same type, so passing one where the other is expected compiles cleanly — and a function like cancel(orderId, userId) can be called with the arguments reversed with no complaint. A brand adds a phantom property that makes them structurally distinct while erasing to nothing at runtime, so the mistake becomes a compile error at zero cost.
  6. Why is TypeScript deliberately unsound?
    Because a sound type system for JavaScript would reject an enormous amount of correct, existing code — and TypeScript's purpose was to type the JavaScript people already write. So it accepts known holes: as, any, unchecked array indexing, bivariant method parameters, and every declared type for data crossing the program boundary. Knowing where they are is more useful than wishing they were closed, because each one is a place a runtime failure can originate.
