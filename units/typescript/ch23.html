CHAPTER 23

Compiler performance and project structure

Type checking gets slow for a small number of specific reasons, almost none of which is "the project is large". The number that matters is type instantiations rather than files, and there is a profiler that will tell you exactly which type is responsible.

Part 6 At scale·Reading time 30 minutes·Demos the usual causes, what a change forces you to recheck·Prerequisites Chapters 2, 16

1What is actually slow

Not the file count. Not the line count.

The compiler's work is dominated by type instantiations — each time a generic type is applied to concrete arguments, a new type is constructed and cached. A project with 3,000 files and simple types checks faster than one with 300 files and a deeply generic component library, because the second one asks the compiler to build hundreds of thousands of intermediate types that the first never needs. That is why the useful diagnostic is a count of instantiations rather than anything about your source.

tsc --extendedDiagnostics
The first look. Reports files, lines, instantiations, memory, and time split across parse, bind, check and emit. A healthy medium project is in the low millions of instantiations; tens of millions means something specific is wrong and it is findable.
tsc --generateTrace ./trace
The one that answers the question. It writes a trace loadable in Chrome's profiler viewer showing which types and which files consumed the time. Almost nobody knows it exists and it is the difference between guessing and knowing.
Measure the editor, not the build
The language server repeats this work as you type. A type that adds two seconds to a build adds a pause to every hover and completion, which is a much worse experience than the build number suggests. The TypeScript extension's Open TS Server Log command shows what it is doing.
And measure before changing anything
Every recommendation in this chapter is worth reversing if your trace says something else. Performance advice ages badly, and the profiler does not.

{
  "compilerOptions": {

4Separate the check from the build

The single biggest win available to most projects, and it is a config change.

Do not use tsc to produce your bundle
esbuild, SWC and Vite transpile file-by-file without type checking and are one to two orders of magnitude faster. Type checking becomes a separate parallel job — tsc --noEmit — that runs in CI and in your editor, where it belongs.
Which requires isolatedModules: true
It rejects the handful of constructs a single-file transpiler cannot handle correctly: re-exporting a type without export type, const enum across modules, and a few others. Turn it on regardless — it costs nothing and it keeps your options open.
And verbatimModuleSyntax, ideally
Makes import elision explicit: an import without type is always emitted, one with it is always erased. Removes a whole class of confusion about why a side-effecting import disappeared from the output.
incremental: true for the check itself
Writes a .tsbuildinfo so subsequent tsc --noEmit runs only redo what changed. Cache it in CI keyed on the lockfile and it is close to free.
And skipLibCheck: true, with one eye open
Skips checking .d.ts files, which is often a large fraction of the total. The cost is that a genuinely broken declaration file in a dependency goes unreported. Nearly everyone runs it; know that you are trading a real check for real time.

5A checklist

In order. Stop when it is fast enough.

#DoWhy
1Run --extendedDiagnostics, write down the instantiation countEverything else is guessing without it.
2Turn on skipLibCheck and incrementalTwo lines, frequently a large fraction of the total.
3Move emit to esbuild or SWC; tsc --noEmit for checkingThe biggest single win in most projects.
4Run --generateTrace and look at the top ten typesNow you know rather than suspect.
5Fix or delete the worst two or threeUsually a recursive utility or an over-generic component. Chapter 16, section 6.
6Add explicit return type annotations on exported functionsStops the compiler re-deriving large inferred types at every call site, and improves error locality besides.
7Only then consider project referencesReal benefit at real scale, real complexity at any scale.

Step 6 deserves a word, because it is the one that sounds like busywork and is not. An exported function with an inferred return type forces every consumer to re-derive that type, and if the inferred type is a large intersection or a conditional, that derivation is repeated across the whole project — and it lands in the .d.ts too, where it is re-read by every downstream package. One annotation makes it a name.

6Check yourself

Five questions.

1. Why is file count a poor predictor of check time?

Because the work is dominated by type instantiations, not by parsing. Each application of a generic type to concrete arguments constructs and caches a new type, so 300 files using a deeply generic component library can ask the compiler to build far more intermediate types than 3,000 files of straightforward code. That is why --extendedDiagnostics reports instantiations as a headline number and why it is the one to write down before changing anything: it correlates with time in a way that lines of source does not.

2. What does --generateTrace give you that --extendedDiagnostics does not?

Attribution. --extendedDiagnostics tells you that checking took eleven seconds and made forty million instantiations; the trace tells you which types and which files those were. Load the output in Chrome's profiler viewer and the top few entries are usually the whole answer — a recursive utility being instantiated thousands of times, or one over-generic component. It is the difference between knowing you have a problem and knowing where it is, and it turns a day of bisecting into ten minutes.

3. Why separate type checking from emitting?

Because they have wildly different costs and only one of them blocks you. Transpiling is a per-file transformation that esbuild or SWC does one to two orders of magnitude faster than tsc; type checking is a whole-program analysis that has to be slow. Splitting them means your dev server and build stop waiting for the checker, and tsc --noEmit runs in parallel in CI and continuously in your editor. The requirement is isolatedModules: true, which rejects the few constructs a single-file transpiler cannot handle correctly — worth enabling regardless.

4. What is the trade with project references?

Referenced projects are consumed through their emitted .d.ts files rather than their source, so a change in a dependency is not visible to its dependents until that dependency is rebuilt. That indirection is exactly what buys the speed — tsc --build can skip any project whose inputs are unchanged — and it is also what confuses people on the first day, when an edit appears to have no effect. Add declarationMap so go-to-definition still lands in source, and expect to reach for --build --clean occasionally when a .tsbuildinfo goes stale.

5. Why annotate return types on exported functions?

Because an inferred return type has to be re-derived at every consumer, and if it is a large intersection or a conditional type, that derivation is repeated across the whole project — and written into the .d.ts, where every downstream package re-reads it. An explicit annotation turns the computation into a name that is looked up once. It also improves error locality: a mistake inside the function is reported at the function rather than at whichever call site first noticed the return type was wrong. It sounds like busywork and it is one of the higher-value items on the checklist.
