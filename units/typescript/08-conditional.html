Conditional and template literal types

A conditional type asks whether one type is assignable to another and picks a branch — and when the thing being asked about is a naked type parameter, it asks once per union member and unions the answers. That distribution is the feature, and it is also where every confusing result comes from.

— words— min read2 interactivesNeeds: chapters 06, 07

Distribution

One conditional, once per member
Then wrap it in a tuple and step again
The three rules that explain every surprise
  • Distribution needs a naked type parameter on the left of extends. T extends X ? … : … distributes; [T] extends [X] ? … : … and T[] extends X[] ? … : … do not. Wrapping in a one-element tuple is the standard way to turn it off.
  • never is the empty union, so a distributive conditional over never runs zero times and returns never — even when both branches would have produced something. This is the single most common "why is my type never".
  • any takes both branches and unions them, because it is assignable to everything and nothing at once. boolean distributes as true | false, which occasionally matters.

typescript — template literals, and recursion with a floor
// ── patterns, checked at compile time ──
type Route   = `/${string}`;
type EventOf<T extends string> = `on${Capitalize<T>}`;
type CssVar  = `--${string}`;

const r: Route = "orders";    ✗ not assignable — no leading /
const r: Route = "/orders";   ✓
// the four intrinsics: Uppercase, Lowercase, Capitalize,
// Uncapitalize. They are compiler built-ins, not TypeScript code.

// ── extracting path parameters, which is the real payoff ──
type Params<P extends string> =
  P extends `${string}:${infer Name}/${infer Rest}`
    ? { [K in Name | keyof Params<Rest>]: string }
  : P extends `${string}:${infer Name}`
    ? { [K in Name]: string }
  : {};

type P = Params<"/orders/:orderId/items/:itemId">;
//   { orderId: string; itemId: string }   ← from the string alone.
//   This is how every modern router types its params, and it is
//   the clearest case where type-level code pays for itself.

// ── recursion, and its ceiling ──
type Split<S extends string, D extends string, Acc extends string[] = []> =
  S extends `${infer H}${D}${infer R}`
    ? Split<R, D, [...Acc, H]>      ← tail position: the compiler
    : [...Acc, S];                       can iterate rather than nest
// ✱ tail-recursive conditionals get ~1,000 iterations; a nested
//   one gets ~50 before "Type instantiation is excessively deep".
//   Accumulate into a parameter and recurse in the tail. Ch 19.
extends here means assignable, not inherits
The check is ordinary assignability, so "paid" extends string is true, string extends "paid" is false, and {a:1,b:2} extends {a:number} is true. Reading it as "is a subtype of" gets you most of the way; reading it as class inheritance will mislead you constantly.
Distribution is what overloads cannot do
Chapter 5's demo: a conditional return type handles a union argument by evaluating per member, where overload resolution has to pick one signature for the whole thing. That is the whole reason to prefer a generic with a conditional return when the return genuinely depends on the input.
Conditional returns are not verified against the body
The checker cannot prove your implementation satisfies T extends string ? number : string, so the body needs an as or an internal overload signature. The safety is entirely at the call sites, which is usually where you wanted it — but it is worth knowing the implementation is unchecked.
Name your intermediate types
An inlined three-level conditional appears in full in every hover and every error message that touches it. Aliasing each step gives the reader a name to hold and gives the compiler something to cache — the same argument as chapter 4's error legibility, and chapter 19's performance one.

Self-check

  1. When does a conditional type distribute?
    When the type being tested is a naked type parameter on the left of extends. Then the conditional is evaluated once per union member and the results are unioned. Wrap either side in anything — most conventionally a one-element tuple, [T] extends [X] — and it is evaluated once against the whole union instead.
  2. Why does a distributive conditional over never produce never?
    Because never is the empty union, so distributing over it means running the conditional zero times and unioning zero results — which is never, regardless of what either branch would have produced. It is the commonest cause of an unexpected never in a type, and the fix when you want the branch evaluated is to wrap in a tuple so distribution does not happen.
  3. What does any do to a conditional?
    It takes both branches and unions them, because any is simultaneously assignable to the check and not — the compiler cannot pick, so it returns both. So a conditional meant to discriminate produces a useless union the moment an any reaches it, which is one of the quieter ways an any from a dependency spreads through your own types. Chapter 9.
  4. What is infer doing?
    Declaring a type variable inside the pattern on the right of extends, to be filled in if the match succeeds. It is pattern matching: T extends Promise<infer U> ? U : never says "if T is a promise of something, call that something U". The variable is only in scope in the true branch, which is why the false branch is almost always never.
  5. Why does tail position matter for a recursive conditional?
    Because the compiler can iterate rather than nest. A conditional whose recursive call is the whole result of a branch is unrolled in a loop with a limit around a thousand; one that recurses inside a larger expression builds nested instantiations and fails at roughly fifty with "Type instantiation is excessively deep". So you accumulate results into an extra type parameter and recurse in the tail — the same transformation as in ordinary tail-call optimisation.
  6. Why name intermediate conditional types?
    Because an inlined multi-level conditional is expanded into every hover and every error message that touches it, so a small mistake produces forty lines about a structure nobody named. Aliasing each step gives the reader a name and the compiler a caching point, which improves both legibility and check time. It is the cheapest thing you can do to make type-level code maintainable by someone else.
