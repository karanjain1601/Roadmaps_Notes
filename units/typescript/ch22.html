CHAPTER 22

Reading an error

A TypeScript error is not a sentence, it is a proof trace — the compiler showing every step it took while comparing two types until it found the one thing that did not line up. Once you know that, the twelve-line messages stop being intimidating and start being a map with an X on the last line.

Part 6 At scale·Reading time 30 minutes·Demos reading bottom-up, the error catalogue·Prerequisites Chapters 3, 8

1Why they are long

Structural typing means the comparison is recursive, and the error is the recursion.

In a nominal language, "expected User, got Admin" is the whole error, because names either match or they do not. TypeScript compares structure (Chapter 1), so when two object types disagree the compiler walks in — property by property, then into their properties, then into function parameters and return types — until it reaches something primitive that cannot be reconciled. Each indented line is one step of that walk, and the last one is the actual mismatch. The lines above it are the path to it, which is genuinely useful information presented in an order nobody wants.

The habit

Read the last line first. It names the two primitive types that failed to match. Then read the first line, which tells you which assignment triggered the whole thing. The middle is the path between them, and you only need it when the leaf is ambiguous — which happens when the same property name appears at several depths, or when the mismatch is inside a function parameter and the direction matters.

4Isolating a mismatch

Five techniques, in the order you should try them.

1 · Hover the subexpression, not the statement
Assign the awkward part to an intermediate const and hover it. Most confusing errors are one inference gone wrong three subexpressions ago, and splitting the line shows you exactly where the type stopped being what you expected.
2 · Annotate to bisect
Add the type you think the value has. If the annotation errors, the value is wrong; if it passes and the original error remains, the problem is downstream. Two minutes, and it halves the search space — the same move as narrowing a bug with a print statement.
3 · Prettify the type
type Prettify<T> = { [K in keyof T]: T[K] } & {} from Chapter 14. An error mentioning Omit<A, 'x'> & Partial<B> becomes an error mentioning actual properties, which is frequently the whole fix.
4 · Assert what you expect, at the type level
type _ = Expect<Equal<Computed, WhatIThink>> (Chapter 12). When a generic or conditional type is involved, this tells you which of the two is wrong, which the error message will not.
5 · Check for any upstream
If an error is bizarre — a conditional returning both branches, a union where you expected one member, a method that should not exist — look for an any that leaked in from an untyped dependency or a JSON.parse. The type-aware no-unsafe-* lint rules find these, and Chapters 3 and 21 explain why nothing else does.

5When the error is not where the mistake is

Three patterns where the reported location is genuinely misleading.

At a call site, complaining about your argumentSometimes in the signature: an over-narrow parameter type, or contravariance rejecting something that ought to be fine (Chapter 8). Check whether the argument is genuinely wrong before changing it.

6Check yourself

Five questions.

1. Why are TypeScript's errors so much longer than a nominal language's?

Because the comparison is structural and therefore recursive. In a nominal system, "expected User, got Admin" is complete — names match or they do not. TypeScript walks into the two types property by property, then into their properties, then into function parameters and return types, until it reaches primitives that cannot be reconciled. Each indented line is one step of that walk. The message is a proof trace rather than a sentence, which is why the useful part is at the bottom and the framing is at the top.

2. Which line of a nested error should you read first?

The last. It names the two primitive types that actually failed to match — Type 'string' is not assignable to type 'number' — and in most errors that is the entire answer. Read the first line second, since it tells you which assignment triggered the comparison. The middle lines are the path between the two and you only need them when the leaf is ambiguous: when the same property name occurs at several depths, or when the mismatch is inside a function parameter, where the direction of the comparison is flipped and matters.

3. What does Types of parameters 'x' and 'y' are incompatible usually mean?

That the comparison has descended into a function type and reversed direction. Parameters are contravariant (Chapter 8), so at that point the compiler is checking whether the expected parameter type is assignable to yours, not the other way round — which is why the leaf underneath often reads backwards from what you expect and looks like a compiler bug. It is not: a callback that accepts fewer kinds of value than the caller may pass is genuinely unsafe. The usual fix is to widen your parameter, not narrow the expectation.

4. An error is bizarre — a conditional type returning both branches, or a method appearing that should not exist. What do you check?

Whether an any has leaked in upstream. any distributes to both branches of a conditional type, satisfies every property access, and propagates silently through everything derived from it — so a strange error is often correct reasoning applied to a value that lost its type several steps earlier, typically from an untyped dependency or a JSON.parse. noImplicitAny cannot see it because nothing was implicit; the type-aware no-unsafe-assignment family can. Assign the suspect subexpression to a const and hover it — if it says any, that is your bug.

5. An error appears in a file you did not touch, after an unrelated change. Where do you look?

At what is in scope rather than at the code. That pattern almost always means a declaration merge or a configuration change altered the global or module environment — a new dependency shipping an ambient declaration, a lib or types change, or a .d.ts that has started being included. Chapter 19's four preconditions are the checklist, and tsc --traceResolution or bisecting the tsconfig will find it considerably faster than re-reading a file that has not changed. Reading the code is the instinct and it is the wrong first move here.
