CHAPTER 01

What TypeScript is, and is not

A checker that runs before your code does and then removes itself entirely. Three properties follow from that, and each one explains a class of confusion: nothing survives to runtime, types describe shapes rather than names, and the checker is unsound on purpose in a small number of well-chosen places.

Part 1 The shape of the type system·Reading time 30 minutes·Demos what erasure removes, structural compatibility·Prerequisites JavaScript

1Everything is erased

The single most useful fact about TypeScript, and the source of most beginner surprises.

TypeScript compiles to JavaScript by deleting the types. There is no runtime library, no type registry, no reflection. A .ts file becomes the .js file you would have written yourself, minus the annotations. Everything else follows from this.

        The rule this gives you
        
If a question can only be answered by looking at a value while the program is running, types cannot answer it. You cannot ask whether a value is a User, iterate an interface's fields, switch on a type parameter, or validate an API response against a type. Chapter 20 is entirely about that boundary. Everything you can do at runtime — typeof, instanceof, checking a property exists — is ordinary JavaScript, and the compiler is simply clever about reading it.

A class is a shape too

        
A plain object with the right members satisfies a class type, without ever having been constructed by it. That is often useful — you can pass a test double — and occasionally alarming.

        
Which is why two unrelated ids interchange freely

        
type UserId = string and type OrderId = string are the same type, so passing one where the other is expected compiles silently. Chapter 17's branded types are the answer.

        
Excess properties are a special case

        
Assigning an object literal with unexpected members is an error, even though the same object through a variable is fine. That inconsistency is deliberate and Chapter 5 explains what it is for.

        
Nominal typing is available, sort of

        
Not natively, but a private field or a brand gives you the effect. Chapter 17 and Chapter 18.

      

    


    
    

      
3Unsound on purpose

      
A sound type system would reject correct programs. TypeScript chose otherwise, in a handful of specific places.


      

        

          
HoleWhat it permits, and why it exists

          
            
anyAssignable to and from everything. It exists so that untyped JavaScript can be adopted gradually. It is the largest hole and it spreads — Chapter 3.

            
Type assertionsas tells the compiler you know better and it stops arguing. Necessary at genuine boundaries, ruinous when used to silence a real error — Chapter 21.

            
Array covarianceDog[] is assignable to Animal[], which lets you push a Cat into an array of dogs. Sound systems forbid this; it would make most real code painful.

            
Method parameter bivarianceMethod parameters are checked leniently, which is what makes DOM event handlers and array callbacks usable. strictFunctionTypes tightens function properties but deliberately not methods — Chapter 8.

            
Optional property accessIndex signatures and array access return the value type, not T | undefined, so arr[99] type-checks and is undefined. noUncheckedIndexedAccess fixes it and is off by default — Chapter 2.

            
Declaration merging on any-typed modulesAn untyped dependency becomes any, and every value derived from it stops being checked without warning.

          
        

        
These are engineering decisions rather than bugs, and knowing the list is what separates trusting the compiler from understanding it. The practical consequence: a program that type-checks can still throw, and the places it can are mostly enumerated above.

      

    


    
    

      
4What it does not do for you

      
Worth stating plainly, because a lot of disappointment comes from expecting these.


      

        
It does not validate data

        
A type on a fetch result is a claim, not a check. If the API sends something else, nothing notices until the value is used. Chapter 20.

        
It does not make code faster

        
The output is the same JavaScript. Annotations do not help the engine — the JIT works out shapes at runtime regardless.

        
It does not catch logic errors

        
a - b where you meant b - a type-checks perfectly. Types constrain shape, not meaning. Chapter 17's branded types push a little of the meaning into the type, and only a little.

        
It does not prove absence of exceptions

        
There are no checked exceptions and no Result type. A function typed as returning User may throw instead, and its signature will not say so.

        
It does not fix bad design

        
An awkward abstraction gets awkward types. When a type is genuinely hard to write, the usual cause is that the thing being modelled is confused, and the type is telling you.

      


      

        What it does do, which is a great deal
        
It catches every misspelled property, every argument in the wrong position, every undefined you forgot could occur, every case you did not handle in a union, and every call site you failed to update after a rename. It makes editors able to answer "what can I do with this value" reliably. And it turns a refactor across two hundred files from an act of faith into a list of compiler errors. That is worth the ceremony.

      

    


    
    

      
5The honest cost

      
Four costs, and where each one actually lands.


      

        
A build step, and its speed

        
Type checking is separate from transpiling. Modern tools strip types very fast and do not check them, so checking becomes a parallel job you must remember to run — Chapter 23. Node can now run TypeScript directly by ignoring the types, which is convenient and checks nothing.

        
Dependency types you do not control

        
A library with wrong or missing types is a real cost, and the workaround is module augmentation or a declaration file — Chapter 19.

        
The temptation to be clever

        
The type system is expressive enough to be a programming language, and treating it as one produces types nobody can read and errors nobody can decipher. Chapter 16 is largely a plea for restraint.

        
The pressure to lie

        
When the compiler is wrong and you are in a hurry, as any is right there. Every one of those is a place the type system has stopped helping, and they accumulate quietly — Chapter 21.

      

    


    
    

      
6Check yourself

      
Five questions.


      

        
1. Why can you not write if (value is User) at runtime?

        
        

          
Because types are erased. The compiled JavaScript contains no record that User ever existed — no registry, no metadata, no runtime library — so there is nothing to compare a value against. What you can do is check the things JavaScript can see: typeof, instanceof for classes, whether a property is present, or the value of a discriminant field. The compiler is good at reading those checks and narrowing the type accordingly (Chapter 6), and you can package one up as a type predicate (Chapter 7) — but the check itself is always ordinary JavaScript that you wrote.

        

      


      

        
2. What does structural typing mean, and what does it cost you?

        
        

          
Compatibility is decided by shape, not by declared name: any object with the required members of the right types is assignable, regardless of what it was declared as or whether the two types know about each other. That is mostly a benefit — it makes test doubles trivial and means you can accept a value from anywhere that happens to fit. The cost is that types which are conceptually distinct but structurally identical interchange silently. type UserId = string and type OrderId = string are literally the same type, so passing one where the other belongs compiles without complaint. Chapter 17's branded types are how you get the distinction back.

        

      


      

        
3. Give two places TypeScript is deliberately unsound.

        
        

          
Array covariance — Dog[] is assignable to Animal[], so you can hand it to something that pushes a Cat in — and index access, where arr[99] is typed as the element type rather than possibly undefined. Also any, type assertions, and method parameter bivariance which is what makes event handlers and array callbacks usable. None of these are bugs: a sound system would reject a great deal of correct, ordinary code, and the language chose usability. The practical takeaway is that a program that type-checks can still throw, and the ways it can are largely on that list.

        

      


      

        
4. You typed a fetch result as User[] and got a runtime error reading .name. What happened?

        
        

          
The type was a claim about the data, not a check on it. response.json() returns any (or unknown), and annotating the variable simply told the compiler to stop asking questions — the API sent something else and nothing verified it. This is the single most consequential gap in practice, because the failure appears far from its cause and only in production, where the real data lives. The fix is a runtime check at the boundary: validate the response against a schema and derive the type from the schema rather than declaring it separately, so the two cannot drift. Chapter 20.

        

      


      

        
5. Does TypeScript make code faster?

        
        

          
No. The output is the same JavaScript you would have written, with the annotations deleted, so the engine sees no difference and the JIT works out object shapes at runtime exactly as it always did. Types are for people and tools. Where TypeScript does affect performance is indirectly and in both directions: it makes some optimisations easier to do safely because you can refactor with confidence, and the type checker itself costs build time, which is Chapter 23's subject. Anyone claiming a speed-up from adding annotations is describing something else, usually a rewrite that happened at the same time.
