Assertions and escape hatches

Seven ways to tell the compiler it is wrong. All of them are sometimes correct, none of them checks anything, and the difference between a defensible one and a liability turns out to be less about which you chose than about how far it sits from the thing that justifies it.

2What as can and cannot do

There is a check. It is much weaker than people assume, and there is a well-known way round it.

The overlap rule, and the double assertion TypeScript
// `as` requires the two types to OVERLAP — one must be
// assignable to the other. So this is rejected:
const a = 'hello' as number;
// Conversion of type 'string' to type 'number' may be a mistake

// But the check is one-directional and very permissive
// downward, so ALL of these are accepted:
const b = {} as User;                    // no properties at all
const c = { id: 'x' } as User;             // missing everything else
const d = JSON.parse(s) as User;           // any → anything

// And the escape from the escape: `unknown` overlaps with
// everything, so a double assertion defeats the rule entirely.
const e = 'hello' as unknown as number;    // accepted

// WHAT `as` NEVER DOES:
//   • convert a value — no code is emitted at all (Chapter 1)
//   • check anything at runtime
//   • warn you later if the target type changes shape

// That last one is the quiet cost. Rename a field on User and
// every `as User` keeps compiling, because the object it is
// applied to was never checked against User in the first place.

And a caution — ! is nearly invisible in review and hard to grep for reliably, which is why @typescript-eslint/no-non-null-assertion earns its place even if you sometimes disable it inline.

4Assertion functions

The one hatch that actually checks something, plus its awkward requirement.

asserts x is T, and why the call site sometimes errors TypeScript
// Narrows by throwing. The compiler trusts the signature the
// same way it trusts a predicate (Chapter 7) — but here there
// is a real runtime check backing it up, if you write one.
function assertIsUser(v: unknown): asserts v is User {
  if (typeof v !== 'object' || v === null || !('id' in v)) {
    throw new TypeError('not a user');
  }
}

const data: unknown = await res.json();
assertIsUser(data);
data.id;                     // narrowed from here on

// The plain form, for invariants:
function assert(c: unknown, msg?: string): asserts c {
  if (!c) throw new Error(msg ?? 'assertion failed');
}

// THE AWKWARD BIT. Assertions are only applied when the thing
// being called has an explicit type annotation, so this fails:
const check = assertIsUser;      // inferred
check(data);                    // error: Assertions require every name
                                // in the call target to be declared with an
                                // explicit type annotation.

const check2: typeof assertIsUser = assertIsUser;   // fine

// Worth knowing because the message is genuinely opaque, and
// it appears whenever an assertion function is imported through
// a barrel file or destructured out of an object.

6Containing them

Five practices, in order of return on effort.

Prefer @ts-expect-error to @ts-ignore, always
It errors when the error it was suppressing goes away, so it deletes itself when the underlying problem is fixed. There is no situation where @ts-ignore is better; the ESLint rule ban-ts-comment can enforce the swap and require a description.
Require a reason, mechanically
ban-ts-comment with descriptionFormat makes every suppression carry a sentence. It converts "someone silenced this" into "someone silenced this because", which is the difference between an archaeology project and a decision you can re-evaluate.
Put the unavoidable ones behind a function
A branded constructor, a parser, one getOrThrow. The cast stops being scattered and becomes a small reviewed surface — section 5's argument, applied deliberately.
Turn on the type-aware lint rules
no-unsafe-assignment, no-unsafe-member-access, no-unsafe-call, no-unsafe-return. These catch any spreading from an untyped dependency, which is the leak that noImplicitAny cannot see because nothing was implicit — Chapter 3.
Count them, occasionally
A grep for as [A-Z], @ts- and : any across the codebase, recorded once a quarter. Not a gate, and not a target — just a number that tells you whether the escape hatches are a considered part of the design or an accumulating tax.

7Check yourself

Five questions, closing Part 5.

1. What does as check, and how do you defeat it?

It checks that the two types overlap — one must be assignable to the other — so 'hello' as number is rejected. The check is very permissive downward, though: {} as User and { id: 'x' } as User are both accepted, because an object with fewer properties is a supertype. And as unknown as T defeats it entirely, since unknown overlaps with everything. Worth being explicit that a double assertion is not a clever workaround but a signal: it is the language saying the two types have nothing to do with each other, and you saying you know better.

2. Why is @ts-expect-error always better than @ts-ignore?

Because it errors when there is no error to suppress. That makes it self-cleaning: fix the underlying problem, upgrade the dependency that finally shipped types, and the comment itself becomes a build failure telling you to delete it. @ts-ignore stays forever, silently, and also silences any new error that appears on that line later — so a suppression added for one reason can hide a completely different bug six months on. There is no case where @ts-ignore is the better choice, which is unusual enough among these trade-offs to be worth stating plainly.

3. Why does any have a worse blast radius than as?

An as lies about one value at one point, and everything downstream is still checked against the type you claimed. any disables checking for the value and everything derived from it — its properties, its method results, whatever it is assigned to — so a single any at the top of a call chain can silently untype a large region with no error anywhere. That is why the type-aware lint rules exist as a separate family: noImplicitAny cannot help, because nothing was implicit. Prefer unknown and narrow, which is Chapter 3's argument and the single highest-value habit in that chapter.

4. What makes one cast defensible and an identical cast not?

Distance from its justification. return s as Email on the line after if (!s.includes('@')) throw is verifiable at a glance and breaks visibly if someone edits either line. The same cast in a different file, relying on a convention about what callers pass, cannot be checked by any reader and will keep compiling forever after the convention changes. The cast is identical; what differs is whether a reviewer can confirm it and whether an edit that invalidates it produces any signal. That is also the argument for confining unavoidable casts to small constructor functions — it collapses the distance to zero deliberately.

5. When is an assertion function better than a type predicate?

When failure is a bug rather than a branch. A predicate returns a boolean and asks the caller to handle both cases; an assertion throws, so the code after it reads linearly and the failure path is one place rather than every call site. Use a predicate when both outcomes are normal — filtering a list, deciding which UI to render — and an assertion when the false case means something is broken. Both are trusted by the compiler on the strength of their signature (Chapter 7), so both can lie; the assertion at least has a runtime check in it by construction. Its one wrinkle is the requirement that the call target have an explicit type annotation, which produces an opaque error whenever one is imported through a barrel file.

Carry forward

None of these check anything at compile time except as's weak overlap rule. @ts-expect-error is self-cleaning and @ts-ignore never is. any's blast radius is everything downstream. A cast's honesty is its distance from its justification — so put the unavoidable ones inside small functions.
