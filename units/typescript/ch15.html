CHAPTER 15

Template literal types

String types the compiler can build and take apart. They produce some of the most satisfying APIs in the language and some of the worst error messages, and the difference between those two outcomes is mostly about how many members you asked for.

Part 4 The type-level toolkit·Reading time 35 minutes·Demos expansion and patterns, a route parser·Prerequisites Chapters 12–13

1The syntax, and the two behaviours

Backticks in a type position. What happens next depends entirely on what you interpolate.

Expansion or pattern — the distinction the whole chapter turns on TypeScript
// Interpolate a UNION of literals → you get every combination.
type Size = 'sm' | 'lg';
type Class = `btn-${Size}`;      // 'btn-sm' | 'btn-lg'

// Interpolate `string` → you get a PATTERN, not an expansion.
type Handler = `on${string}`;      // matches any string starting 'on'
const a: Handler = 'onClick';      // fine
const b: Handler = 'click';        // error

// This is a genuinely different kind of type: it has infinitely
// many inhabitants and the compiler checks membership by matching
// rather than by looking it up in a list. It stays cheap.

// number and bigint interpolate too, as patterns:
type Px = `${number}px`;              // '4px', '-2.5px', …

// And multiple slots multiply. Three unions of three members
// each is 27 members, computed eagerly and held in memory.
type Boom = `${A}-${B}-${C}`;

4The four intrinsics

The only utility types that cannot be written in the type system.

TypeBehaviour
Uppercase<S>'get' → 'GET'. On string it returns string.
Lowercase<S>'GET' → 'get'.
Capitalize<S>'get' → 'Get'. The one you reach for in key remapping.
Uncapitalize<S>'Get' → 'get'.

Two practical notes. Each is declared in the standard library as intrinsic — implemented inside the compiler, because character-level case conversion is not expressible in the type system. And they only accept strings, so in a key remapping you need Capitalize<string & K> rather than Capitalize<K>: keyof T may include number and symbol, and the intersection filters them out.

5Where they pay for themselves

Five uses that justify the complexity, and what each buys.

Event maps
on<Event> handler names derived from a union of event names, so adding an event adds its handler and misspelling one is a compile error. The pattern that makes typed emitters pleasant.
Route parameters
The demo above. navigate('/users/:id', { id: '4' }) checking the params object against the path string is the single most impressive thing template literals do, and several routers now ship it.
Getters and setters from a data shape
Chapter 13's remapping, with Capitalize. Generates an accessor interface that cannot drift from the model.
Object paths
'user.address.city' as a type, with the value type looked up recursively. Useful for form libraries and translation keys — and the first thing on this list where the cost starts to show, because the union of all paths through a deep object grows fast.
Units and formats
`${number}px`, `#${string}`, ISO date shapes. These are patterns rather than expansions, so they stay cheap and they are the best value on the list. They do not validate — '99999px' passes and so does '#zzz' — but they catch the common mistake of passing a bare number.

6The costs, stated plainly

Three of them, and they arrive in this order.

CostWhat it looks like
Compile timeThe first thing you notice. A large expansion is computed eagerly and cached, so a few hundred thousand members turns editor responsiveness noticeably worse before anything errors.
The 100,000 member capExpression produces a union type that is too complex to represent. A hard limit, and hitting it means redesigning rather than tuning.
Error messagesThe worst cost, and the one that lands on your colleagues. A mismatch against a 4,000-member union prints a substantial fraction of it. Wrapping the type in an alias does not help, because the compiler expands it anyway.

The mitigation for all three is the same: prefer a pattern to an expansion wherever the check can be structural rather than exhaustive. `${string}-${string}` costs nothing and catches the shape error; enumerating every valid pair costs a lot and catches slightly more. Reach for the expansion when the finite list is genuinely the point — a set of routes, a set of events — and not when you are merely validating a format.

7Check yourself

Five questions.

1. What is the difference between `on${'Click' | 'Focus'}` and `on${string}`?

The first is an expansion: the compiler materialises 'onClick' | 'onFocus', a two-member union it holds in memory and can enumerate. The second is a pattern: it has infinitely many inhabitants and membership is checked by matching rather than by lookup. That difference is the whole cost model of the chapter — expansions grow multiplicatively across slots and eventually hit a hard 100,000-member cap, while patterns stay cheap no matter how permissive they are. Prefer the pattern whenever the check can be structural; reach for the expansion when the finite list is genuinely the point.

2. Why Capitalize<string & K> rather than Capitalize<K>?

Because keyof T is string | number | symbol, and Capitalize is constrained to string. Intersecting with string filters the other two out: string & 'name' is 'name', while string & symbol is never and disappears from the union. It reads like a cast and it is not — it is an ordinary intersection doing exactly what intersections do. This appears in almost every real key-remapping type, and forgetting it produces an error about symbol not being assignable to string that looks unrelated to what you wrote.

3. How does a template pattern with infer split a string?

The compiler matches the string against the template as a pattern and binds each infer to the corresponding span. 'a-b-c' extends `${infer H}-${infer T}` gives H = 'a' and T = 'b-c' — the match is non-greedy at the first delimiter, so the head is the shortest possible prefix and the tail takes the rest. That is what makes recursion work: split once, process the head, recurse on the tail. Two consequences worth knowing: a pattern with two adjacent infers and no delimiter between them cannot split meaningfully, and matching against string rather than a literal gives you string for every capture.

4. Why is a large expansion bad for your colleagues specifically?

Error messages. When a value fails to match a 4,000-member union, the compiler prints a substantial fraction of that union, and the actual mistake — usually a single typo — is buried in it. Wrapping the type in a named alias does not help, because the compiler expands the alias when reporting. So the person who pays the cost is not the author, who knows what the type means, but whoever next mistypes a string and receives several screens of output. This is a real reason to prefer patterns, and a real reason to keep expansions to a size you would be happy to read printed out.

5. When is `${number}px` the right tool, and what does it not do?

It is right when you want to catch the shape mistake cheaply — passing a bare number where a CSS length string is expected, or forgetting the unit. It is a pattern, so it costs nothing regardless of how many values match. What it does not do is validate: '99999px' passes, '-0px' passes, and `#${string}` happily accepts '#zzz'. Template patterns check format, not plausibility. If the value needs real validation you are at Chapter 20's boundary problem, and a schema at runtime is the answer — the type can express the shape and never the range.
