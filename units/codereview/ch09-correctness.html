Correctness and edge cases

Three real bugs, planted in three real functions. Random testing finds two of them almost every time and the third never — not in ten tests, not in a hundred, not ever. A seven-item checklist finds all three.

The third bug is unreachable, not unlikely

It needs lo == hi. The random generator draws hi = lo + at least 1, so that input is not merely rare — it cannot be produced. Ten random tests find it 0% of the time and so do a hundred, and so would a million.

That is the general shape. Random testing samples where inputs are common; bugs live where inputs are rare. And a generator written by the same person who wrote the code inherits its blind spots — the assumption that a range has width is in both.

The other two bugs are reachable, so more tests help: fifty random tests find the binary-search bug 100% of the time. The difficulty is that you cannot tell which case you are in without looking at the boundary — which is the reviewer's job, not the generator's.

Coverage of the input space is the wrong measure

The seven checklist inputs cover 0.0038% of the normalise function's input space — and find the bug that a hundred random draws cannot. Bugs are not uniformly distributed. They cluster at the edges of the logic, which is a much smaller set than the edges of the data.

Error paths

An error path is code that never runs in development. It is the least-exercised code in the change and it reliably gets the least attention in review.

The question is not "is the error handled"

In the demo it is handled — the exception propagates cleanly, nothing is swallowed, and any reviewer scanning for a bare except would pass it. Thirty units still vanish.

The question is "what is true after it?" That is answerable by reading, and it is the one nobody asks.

The fourth row deserves separate attention. A function that returns null for both "no such user" and "the database is down" has collapsed two very different situations into one value, and every caller now guesses. That is a correctness bug that will never appear in a stack trace.

The third is the one that generalises furthest. "What happens on the second call?" catches an entire class that boundary values do not: a function that mutates its argument, a cache that is never invalidated, a generator consumed twice. None of those are edge cases of the input — they are edge cases of the sequence.

Chapter 1 put concurrency at 5%

Races are the class review is worst at, and reading harder does not fix it. What does help is a single narrow question: which of these lines assume nothing happened in between?

Check-then-act is the pattern to recognise — if not exists: create, read; modify; write, if balance >= amount: deduct. You will not catch most races, but you can catch the shape, and the shape is visible in a diff.

The first is worth stating as a rule. A green test suite tells you the bugs it can reach are absent. It says nothing at all about the region its generators do not visit, and the boundary is usually in that region — because the same person wrote both.

Check yourself

Random testing finds two of the three planted bugs easily. Why not the third?

Because it is unreachable, not unlikely. The normalise bug needs lo == hi, and the generator draws hi = lo + at least 1 — so that input cannot be produced at all. Ten random tests find it 0% of the time, and so do a hundred, and so would a million. The other two are reachable, so more tests do help: fifty random tests find the binary-search bug 100% of the time.

Why do random generators miss boundaries so reliably?

Because random testing samples where inputs are common and bugs live where inputs are rare — and because the generator is usually written by the same person who wrote the code, so it inherits the same blind spots. The assumption that a range has non-zero width was in both the function and its test generator here. That is not a coincidence; it is the normal case.

Is input-space coverage a good measure of a test suite?

No. The seven checklist inputs cover 0.0038% of the normalise function's input space and find the bug that a hundred random draws cannot. Bugs are not uniformly distributed — they cluster at the edges of the logic, which is a far smaller set than the edges of the data. Seven chosen inputs beat a hundred arbitrary ones for that reason.

Which input classes should you check first, and why those?

Empty, one, two — in that order, before anything else. They are where loop and index logic differs from the general case, they are cheap to check by reading rather than running, and between them they covered two of the three planted bugs. The rest of the list — at limit, over limit, degenerate range, absent, duplicate, negative — comes after.

A transfer raises cleanly on a frozen account. Is the error handled correctly?

The error is handled — it propagates cleanly, nothing is swallowed, and a reviewer scanning for bare except blocks would pass it. Thirty units still vanish, because the source was debited before the check and nothing put them back. The right question is not "is the error handled" but "what is true after it?" — and that is answerable by reading.

What is wrong with returning null for both "not found" and "database down"?

Two very different facts have been collapsed into one value, so every caller now guesses which happened. "No such user" is a normal outcome to display; "the database is down" is an incident to retry or escalate. Conflating them is a correctness bug that will never appear in a stack trace, which is why it belongs on an error-path checklist rather than left to be noticed.

What does "what happens on the second call?" catch that boundary values do not?

Edge cases of the sequence rather than the input: a function that mutates its argument, a cache never invalidated, a generator consumed twice, accumulated state that was fine once. None of these are extreme inputs, so no boundary checklist reaches them — and they are visible from a diff if you think to ask.

Ten things to carry forward

  1. One of three planted bugs was unreachable by random testing at any sample size.
  2. Generators inherit the blind spots of whoever wrote the code.
  3. Seven chosen inputs beat a hundred random ones at 0.0038% coverage.
  4. Coverage of the input space is the wrong measure.
  5. Empty, one, two — first, always. They covered two of three bugs.
  6. A green suite says the bugs it can reach are absent. Nothing more.
  7. "Is the error handled" is the wrong question; ask what is true after it.
  8. One value for two situations makes every caller guess.
  9. Ask what happens on the second call — sequence bugs beat input bugs.
  10. You will not spot races. Spot check-then-act instead.
