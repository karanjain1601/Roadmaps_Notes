Formatters: the only free one

A formatter is a function of the abstract syntax tree. Whitespace is not in the tree, so it cannot influence the output — which gives three properties you can rely on absolutely.

Measured using Python's ast.unparse as the formatter

Two differently-formatted sources with the same ASTFormat identically
format(format(x))Equals format(x) — idempotent
Behaviour after formattingUnchanged

Idempotence is the one that matters operationally. A formatter that is not idempotent creates diffs in files nobody edited, and that is the failure mode which makes teams turn it off.

The point is a shorter diff, not tidier code

Measured on a change with one real edit and a lot of reformatting: the raw diff shows 8 changed lines and the formatted diff shows 2 — the actual edit and nothing else. A fourfold reduction in what the reviewer must read.

Every reformatted line in a diff is attention spent proving that nothing happened. That is the cost a formatter removes, and it is much larger than the cost of style comments it also removes.

Which style the formatter picks is nearly irrelevant, and the argument about it is the most reliable waste of time in this chapter. Any consistent choice gets you both properties; no choice gets you neither.

Linters, and why precision collapses

A linter examines constructs and flags suspicious ones. It has a recall (how often it catches a real problem) and a false-positive rate (how often it flags a clean one). Both sound like they should be roughly equally important. They are not.

You need a 500-fold reduction to get usable precision

Going from 5% to 0.01% false positives — a factor of 500 — is what it takes to move precision from 0.5% to 73%. That is the base rate at work: real defects are rare and the clean majority is enormous, so a rule firing on a tiny fraction of clean code still buries the signal.

This predicts what actually happens. Teams do not tune noisy linters; they disable them. Any rule you cannot get to near-zero false positives is a rule that will be switched off within a quarter.

Auto-fix escapes the analysis entirely

All of the above assumes each finding costs a human some attention. A rule that can auto-fix costs zero attention no matter how often it fires — a wrong fix simply shows up in the diff, where the reviewer was looking anyway.

So the useful question about a lint rule is not "how accurate is it" but "can it fix what it finds?". An auto-fixing rule at 5% false positives is nearly free; a flag-only rule at 5% is 1,499 units of attention per ten thousand lines.

Type checkers pay back quadratically

Gradual typing lets you annotate some of a codebase and check what you annotated. The natural assumption is that annotating half gets you half the benefit. It does not.

Type errors visible against annotation coverage
AnnotatedErrors caught
25%6.2%
50%25%
75%56.2%
90%81%
100%100%
Why it squares

A call site has two ends. A type error is visible only when the caller's argument type and the callee's parameter type are both known — one unannotated side is a hole. So the fraction of checkable boundaries is the annotation fraction squared.

The adoption consequence is concrete: going from 50% to 90% coverage more than triples the catch rate. Annotating one module fully beats annotating every module a bit, which is the opposite of how teams usually roll it out.

And there is a ceiling. Six common defect sources sit entirely outside the type system: value ranges, None arriving from an external call, dictionary key presence, units and dimensions, ordering assumptions, and resource lifetimes. A fully-typed codebase still has all of them.

The bill

Every automated check has a setup cost, an upkeep cost, and a flake rate. Only one of them has zeroes in the last two columns.

Modelled cost per tier
TierSetupUpkeepFlake rate
Formatter2 h00%
Linter8 h30 min/wk0%
Type checker40 h60 min/wk0%
Unit tests—90 min/wk2%
End-to-end tests24 h120 min/wk15%

That gives the adoption order directly: formatter first because it is free forever, then linter, then types. End-to-end tests last.

A flaky check is worse than no check

Fifty CI runs a week at a 15% flake rate, twenty minutes to investigate each, is 150 minutes — more than the 120 minutes of upkeep already budgeted for the suite. The flakiness costs more than the maintenance.

And the money is the smaller half. A flaky check trains the team to ignore a red build, which is the one signal you cannot afford to devalue. Fixing flakiness is not tidying; it is protecting everything else.

The last is the one this chapter exists to set up. Automating everything automatable moves the bottom three layers off the reviewer's plate — and chapter 1 measured that the two layers left are where the irreversible decisions live. Automation does not shrink the job; it concentrates it.

Check yourself

What does a formatter actually guarantee?

Three things, because it is a function of the abstract syntax tree and whitespace is not in the tree. Two differently-formatted sources with the same AST format identically; format(format(x)) equals format(x); and behaviour is unchanged. All three were measured using Python's ast.unparse as a real formatter. Idempotence is the operationally important one — a non-idempotent formatter creates diffs in files nobody edited, which is what makes teams disable it.

What is the main benefit of a formatter — fewer style comments?

No, a shorter diff. Measured on a change with one real edit buried in reformatting: the raw diff shows 8 changed lines and the formatted diff shows 2, the actual edit and nothing else. Every reformatted line in a diff is attention spent proving that nothing happened, and that cost is considerably larger than the style comments the formatter also removes.

Why does a 5% false-positive rate produce a useless linter?

Base rates. Real defects are rare — one per thousand lines here — and clean constructs are not, so a rule firing on 5% of the clean majority produces 1,499 false alarms against 8 real findings across ten thousand lines: 0.5% precision. It takes a 500-fold reduction, down to 0.01%, to reach 73% precision. This predicts what teams do: they do not tune noisy linters, they disable them.

What is the right question to ask about a lint rule?

Not "how accurate is it" but "can it fix what it finds?". The whole precision analysis assumes each finding costs a human attention — an auto-fixing rule costs zero regardless of how often it fires, because a wrong fix simply appears in the diff where the reviewer was already looking. An auto-fixing rule at 5% false positives is nearly free; a flag-only rule at 5% is 1,499 units of attention per ten thousand lines.

You annotate half your codebase. How much of the benefit do you get?

A quarter, not a half. A call site has two ends, and a type error is visible only when the caller's argument type and the callee's parameter type are both known — one unannotated side is a hole. So checkable boundaries go as the annotation fraction squared: 25% coverage catches 6%, 50% catches 25%, 90% catches 81%. Going from 50% to 90% more than triples the catch rate.

What does that imply about how to roll out type checking?

A fully-typed codebase still has all of them.

And the time is the smaller half: a flaky check trains the team to ignore a red build, devaluing the one signal you cannot afford to lose. Ten things to carry forward

  1. A formatter is a function of the AST, so style cannot survive it.
  2. Idempotence is the property that matters — otherwise it diffs files nobody touched.
  3. The benefit is a shorter diff: 8 changed lines became 2.
  4. 5% false positives gives 0.5% precision — 1,499 false against 8 real.
  5. You need a 500-fold reduction to make a flag-only rule usable.
  6. Ask whether a rule can auto-fix, not how accurate it is.
  7. Type coverage squares: half annotated catches a quarter.
  8. Type one module fully rather than every module thinly.
  9. The formatter is the only tier with zero upkeep and zero flake. Adopt in that order.
  10. A flaky check costs 150 min/week and devalues the red build.
