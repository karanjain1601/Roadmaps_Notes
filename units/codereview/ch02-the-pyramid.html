Two orderings, pointing opposite ways

The pyramid is built from one observation: rank the five layers by how automatable they are, then rank them by how reversible a mistake is, and the two orderings run in opposite directions.

Why API semantics is the top

It is the only layer whose cost to change depends on how successful the code has been. Everything else is bounded by the size of the change itself; an API decision is bounded by adoption, which grows.

Modelled at 35% monthly growth: after 24 months a style fix still costs 1 and an API fix costs 1,343. A style comment you skip today costs the same to fix in two years. An API decision you skip today may be unfixable in two years.

With a single caller the API change costs less than the implementation change — which is exactly why the pyramid is advice about public interfaces and internal code that is on its way to becoming one, not about every function you write.

The layer that is drawn in the wrong place

"Tests" sits second from the bottom because CI can check them: do they exist, do they pass, is coverage above the line. All three are automatable, so the layer looks safely delegated.

Here is a subject and two test suites.

the subject, and two suites that both pass
def classify(n):
    if n < 0:  return "negative"
    if n == 0: return "zero"
    if n < 10: return "small"
    return "large"

# suite A — executes everything, asserts nothing
for n in (-1, 0, 5, 50):
    classify(n)

# suite B — the same inputs, with assertions
assert classify(-1) == "negative"
assert classify(0)  == "zero"
assert classify(5)  == "small"
assert classify(50) == "large"

Both execute 7 of 8 lines. Both pass. A coverage gate cannot distinguish them, and neither can any other automated check in normal use.

Zero against two, on identical coverage

Suite A kills 0 of 3 mutants. Suite B kills 2 of 3. Same lines executed, same green tick. CI can check that tests exist and pass; it cannot check that they assert anything, and a suite that asserts nothing satisfies every automated gate there is.

So the layer splits. Test existence and test passing are automatable and belong at the bottom. Whether a test would catch a regression is a human judgement and belongs near the top, next to implementation semantics.

The survivor is the useful part

Suite B has one case per branch, four assertions, and complete coverage — and still leaves one mutant alive. It is the one that changes n < 10 to n <= 10, and it differs from the original on exactly one input: n = 10.

Adding that single assertion takes the mutation score from 67% to 100%.

What the tool told the reviewer

Not "add more tests". Not "coverage is 88%". It said: here is the exact input your tests do not distinguish. That is a far more useful review comment than any percentage, and it is the form the question should take even when no tool is producing it.

The reviewer's question about tests is therefore not "are there tests" and not "is coverage high", but "which change to this code would these tests not notice?" — which you can ask by reading, and which chapter 12 turns into a habit.

Using the pyramid

It is a prioritisation device, and the way to apply it is as an order of passes rather than a checklist.

What to spend attention on, in order
Ask firstBecause
Is this the right interface?The only decision whose cost grows with success
Would these tests catch a regression?No tool checks this; coverage does not measure it
Is the implementation comprehensible?Costs a bounded amount to fix, but you pay it repeatedly
Is the documentation right?Cheap to fix, cheap to skip, worth one pass
Is the formatting consistent?A machine already answered this

Read the top three questions before you read the diff line by line. Chapter 5 makes that concrete as an order of passes, and the reason it works is that the first question is often answerable from the pull request description alone — before you have spent any attention at all.

What the pyramid does not model

Four concerns the five layers cannot express
ConcernWhy it does not fit
SecurityNot a layer — it cuts across all five
Data migrationsIrreversible in a way even API changes are not
PerformanceInvisible in a diff — chapter 1 put it at 10% caught
DependenciesA decision whose cost lands on someone else, later
Data migrations sit above the top

You can deprecate an API and support both for a year. You cannot un-drop a column once the data is gone. On the reversibility axis a destructive migration is strictly worse than anything the pyramid contains, and it does not appear on it — which is exactly the kind of gap a model produces when you treat it as a checklist.

The pyramid is a model of one axis pair: automatability against reversibility. It is genuinely useful and it is not complete. Chapter 13 handles the four above on their own terms.

Traps

Where the pyramid gets misused
TrapWhy

Assuming reversibility is fixedAn internal API becomes a public one by being used

The last one is the subtle one. Nothing about the code changes when the fifth team starts calling it — but its position on the pyramid does, and nobody sends a notification. The question "how many callers will this have in a year?" is worth asking at review time precisely because it is unanswerable later.

Check yourself

What are the two orderings the pyramid is built from?

How automatable a layer is, and how reversible a mistake in it is — and they run in opposite directions. Style is 100% automatable and costs one file to fix; API semantics is 0% automatable and costs every caller. The layers a tool can check are the ones you can change freely, and the layers no tool can check are the ones you often cannot change at all.

Why is API semantics at the top rather than implementation?

Because it is the only layer whose cost to change depends on how successful the code has been. Everything else is bounded by the size of the change itself; an API decision is bounded by adoption, which grows. Modelled at 35% monthly growth: after 24 months a style fix still costs 1 and an API fix costs 1,343. With a single caller the API change is actually the cheaper of the two — which is why this is advice about public interfaces, not every function.

Two suites have identical coverage and both pass. Are they equivalent?

No. Measured with a real mutation run on the same subject: the suite with no assertions kills 0 of 3 mutants and the one with assertions kills 2 of 3. Both execute 7 of 8 lines, both go green. CI can check that tests exist and that they pass; it cannot check that they assert anything, and a suite asserting nothing satisfies every automated gate there is.

So where does the "tests" layer actually belong?

In two places. Test existence and test passing are fully automatable and belong at the bottom with style. Whether a test would catch a regression is a human judgement no tool performs by default, and belongs near the top beside implementation semantics. Drawing it as one low layer is what licenses "there are tests, approved" — which the mutation numbers show is not the same statement.

A suite with one case per branch and full coverage still leaves a mutant alive. Which?

The one changing n < 10 to n <= 10. It differs from the original on exactly one input: n = 10 — the boundary, which no test used. Every branch is covered, every assertion passes, and the behaviour is wrong. Adding that single assertion takes the mutation score from 67% to 100%.

What question should a reviewer ask about tests?

Not "are there tests" and not "is coverage high", but "which change to this code would these tests not notice?" That is what the mutation tool answers, and its output is a specific input rather than a percentage — "here is the exact value your tests do not distinguish" is a far more useful comment than "coverage is 88%". You can ask it by reading, without any tool.

Where does a destructive database migration sit on the pyramid?

Above the top, and it is not on the diagram. You can deprecate an API and support both for a year; you cannot un-drop a column once the data is gone. On the reversibility axis it is strictly worse than anything the five layers contain. Security, performance and dependency choices are similarly off-model — the pyramid captures one axis pair well and is not a checklist, which is the main way it gets misused.

Ten things to carry forward

  1. Automatability and reversibility run in opposite directions. That inversion is the pyramid.
  2. API semantics is the only layer whose cost grows with success — 1,343 against 1 after two years.
  3. With one caller the ordering does not hold; this is advice about public interfaces.
  4. Identical coverage, 0 mutants killed against 2. No gate distinguishes them.
  5. CI checks that tests exist and pass, never that they assert anything.
  6. The tests layer splits: existence at the bottom, usefulness near the top.
  7. Full coverage still missed the boundary at n = 10.
  8. One extra assertion took 67% to 100%.
  9. Ask which change these tests would not notice, not whether coverage is high.
  10. Security, migrations, performance and dependencies are off-model. It is not a checklist.

About the mutation figures

The mutation tester is real — it parses the subject, swaps one comparison operator per mutant, and runs each suite against each mutant. The 0-against-2 result and the surviving n = 10 case are outputs of that run, not illustrations.
