One boundary, not many

"Defence in depth" is usually read as "check it everywhere". For independent controls that is right. For the same check repeated it is exactly backwards.

The same (1 − p)N compounding as chapter 12's flake and chapter 10's Hyrum's Law. Twenty copies of a rule is twenty chances to get the rule wrong, and a gap becomes near-certain.

Parse, don't validate

Turn the untrusted string into a typed value once, at the edge. Every downstream site is then correct by construction rather than by discipline — 95% regardless of how many sites use the result, which beats validating at twenty of them by 59 points.

The reviewable version: when you see a check repeated, ask whether it could instead be a type that cannot hold the invalid case.

One new resource is 20 new decisions and one new role is 40 — and none of them appear in the diff that created them. That is why "we check authorisation" does not scale as a review practice: the thing to review is not in front of you.

Deny by default converts silent leaks into noisy failures

The same 2% miss rate that leaves 16 gaps leaves zero leaks when unlisted combinations fail closed. It produces 16 support tickets instead.

That is the whole value: a 403 someone complains about beats a 200 nobody notices. And it makes the review question tractable — not "is this endpoint authorised" but "what happens to a request that matches no rule?" One question, covering the entire product.

Migrations: the irreversible layer

Eight migrations by reversibility

Add a nullable columnYesDrop it

Rename a columnNoOld code breaks immediately
Change a column typeNoNarrowing loses data
Drop a columnNoThe data is gone

Five of eight are irreversible, and the two worst are data destruction. Chapter 2 ranked the pyramid's layers by reversibility — a dropped column sits above the top of it. You can support two API versions for a year; you cannot un-drop a column.

The honest accounting: it is more expensive when nothing goes wrong

Modelled with a four-hour incident, direct costs 32 expected minutes and expand-and-contract costs 81 — 2.5× more.

It is bought as insurance, and the case for it lives in the tail. Raise the incident to eighty hours — a dropped column with no usable backup — and the ordering flips: direct becomes 260 and expand 104.

Which makes the review question concrete. Not "is this migration correct", but "if this is wrong, how do we find out and what do we do?" Reversibility is the answer to the second half, and it is the half nobody plans.

What leaks

Six routes, and half are not the API
ChangeExposes
A field added to a shared responseEvery consumer of that response now receives it
An error message containing a querySchema and data reach the client
A log line with a request bodyThe log store now holds whatever the body held
A sequential idThe count and the ordering become public
A timing differenceExistence becomes observable
A debug endpoint left enabledEverything the endpoint returns

Three of six leak through channels nobody thinks of as an interface — errors, logs, debug output. Chapter 10's point applies directly: the observable surface is much larger than the documented one.

Two habits that cover most of it

For any new field: where else is this response returned? A field added for one caller arrives at every caller of the same serialiser.

For any new log line: what is in the object being logged? log.info("failed", user) writes whatever user holds into a store with different retention, different access control, and often a different jurisdiction.

What review can and cannot do here
ConcernWho catches it
A credential in the diffA scanner, better than a human — chapter 3's auto-fix tier
A credential in the git historyA scanner over history; a reviewer sees only the diff
A secret in a config file that is now committedA reviewer — the file is new, the secret is not
A secret passed as a command-line argumentA reviewer — it lands in the process table and shell history
A secret in an error message or logA reviewer — no scanner reads it as a secret
Rotation that nothing implementsA reviewer — absence is invisible to tools

The split is the same as everywhere else in this unit. Anything a scanner can pattern-match belongs to a scanner; what is left for the reviewer is where the secret goes, which is a semantic question and the reason this row sits in Part 3 rather than chapter 3.

And the fourth row is worth remembering because it is invisible in review unless you know to look: an argument on a command line is readable by every process on the machine, and lands in shell history besides.

The fifth is the most common and the least discussed. A migration and the code that needs it shipped together look tidy in one pull request — and that tidiness is precisely what removes the rollback point. Two boring pull requests are safer than one coherent one, which is the opposite of how review usually rewards changes.

Check yourself

Is validating in more places safer?

Not for the same check. At 95% correct per site, twenty sites means a 64% chance at least one gets the rule wrong — the same (1 − p)N compounding as suite flakiness. Defence in depth is right for independent controls; twenty copies of one rule is twenty chances to get that rule wrong.

What is the alternative?

Parse, don't validate. Turn the untrusted string into a typed value once at the edge, so every downstream site is correct by construction rather than by discipline — 95% regardless of how many sites use it, beating twenty validating sites by 59 points. In review: when a check is repeated, ask whether it could be a type that cannot hold the invalid case.

Why does "we check authorisation" stop working as the system grows?

Because the surface is a product: resources × actions × roles. Ten resources, four actions and five roles is 200 decisions; one new resource adds 20 and one new role adds 40. None of them appear in the diff that created them, so the thing you would need to review is not in front of you.

What makes that reviewable again?

Deny by default. The same 2% miss rate that leaves 16 gaps across 800 decisions leaves zero leaks when unlisted combinations fail closed — it produces 16 support tickets instead. A 403 someone complains about beats a 200 nobody notices. And it reduces the review question to one: what happens to a request that matches no rule?

Where do migrations sit on chapter 2's pyramid?

Above the top of it, and off the diagram. Five of eight common migrations are irreversible and the two worst are data destruction. You can deprecate an API and support both versions for a year — the whole subject of chapter 10 — but you cannot un-drop a column. That is a strictly lower reversibility than anything the pyramid contains.

Is expand-and-contract worth it?

Not in the normal case — modelled with a four-hour incident it costs 81 expected minutes against 32 for a direct migration, 2.5× more. It is bought as insurance, and the case lives in the tail: raise the incident to eighty hours and the ordering flips to 104 against 260. What it actually buys is three rollback points instead of zero, and a schema change decoupled from a code deploy.

What leaks that nobody treats as an interface?

Half of the common routes: error messages containing queries, log lines containing request bodies, and debug endpoints left enabled. The observable surface is much larger than the documented one — chapter 10's point again. Two habits cover most of it: for a new field ask where else is this response returned, and for a new log line ask what is in the object being logged, since the log store has different retention and access control from the API.

Ten things to carry forward

  1. Twenty validating sites gives a 64% chance of a gap.
  2. Parse, don't validate — one typed boundary beats twenty checks by 59 points.
  3. Your own database is untrusted unless every write path ever was.
  4. The authorisation surface is a product: one role adds 40 decisions.
  5. Deny by default turns silent leaks into support tickets.
  6. Ask what happens to a request matching no rule. One question, whole product.
  7. Five of eight migrations are irreversible; two destroy data.
  8. Expand-and-contract costs 2.5× more when nothing goes wrong. It is insurance.
  9. Ask how you would undo it, not whether it is correct.
  10. Half of all leaks are logs, errors and debug output.

About the models

All three are structural rather than empirical: compounding validation error, the multiplicative authorisation surface, and migration cost with a tail. Their parameters are sliders, and the conclusions hold across the ranges rather than at the specific numbers.

The scope of this chapter

This is defensive review guidance — where to put checks, what to ask about a migration, what a diff can and cannot tell you. It is deliberately about structure rather than about specific attacks.
