What an assertion actually pins down

Chapter 2 left a question open: not "are there tests" but which change to this code would these tests not notice? Here it is measured, on five real mutations of one real function.

Asserting one field is worth a quarter of asserting the result

Checking total alone catches 1 of 5. Checking the whole structure catches 4. The three mutations it adds all change count or average while leaving total at 30 — which is exactly the kind of thing a partial assertion is blind to by construction.

The habit worth forming: assert the whole result, not a field of it, unless you have a reason the rest is genuinely unspecified.

The survivor needs a different input, not a stronger assertion

One mutation survives even the full-structure assertion: raising the filter threshold from > 0 to > 5. Both amounts in the test data are above 5, so the change is invisible — no assertion on that input could catch it.

Adding a single row with amount 3 kills it. Which gives the two failure modes to check separately:

Tests need both, and reviewers habitually check neither. The second is chapter 9's lesson arriving from the tests' side: a row chosen to sit between the plausible thresholds is worth more than a dozen arbitrary ones.

The refactor tax

The same function, rewritten with a comprehension instead of a loop, returns identically — verified. Which of its tests survive?

The rule, and the review question

A test that breaks when behaviour did not change is testing the implementation. It will break again, every time, and it never catches a bug.

So the question to ask of any test in a diff: if I rewrote the body of this function keeping the same behaviour, would this test still pass? If not, the test is pinned to the wrong thing.

The cost is not abstract. On a 200-test suite refactored four times a year at eight minutes a fix, three years of that tax is 214 hours at 67% coupling and 32 hours at 10% — a 6.7-fold difference from a property nobody measures.

Flake compounds

Chapter 3 costed a flaky end-to-end suite at 150 minutes a week. That treated flakiness as a per-test problem. Across a suite it is worse, and for the same reason Hyrum's Law was worse than it looked.

"Only a bit flaky" is not a local judgement

The budget is divided across the whole suite. For a 99% green rate, a 200-test suite allows 0.005% per test, a 1,000-test suite allows 0.001%, and a 5,000-test suite allows 0.0002%.

Those numbers are far below what anyone intuitively calls flaky. A test that fails one run in a thousand sounds negligible and blows the budget of a thousand-test suite by a factor of a thousand.

And at 60% green, red carries almost no information. That is the arithmetic behind chapter 3's claim that a flaky check devalues the red build: the team is not being lazy when it re-runs rather than investigates — it is being correct, because most red runs really are false.

The fourth deserves its own note. Mocking a collaborator is often right; mocking the thing you are testing is a way of asserting that the implementation calls what you expected it to call — which is the definition of an implementation-coupled test, arrived at by a route that feels like good practice.

Check yourself

How much does assert result is not None pin down?

Nothing. Measured against five real mutations of a real function, it kills 0 of 5 — and so do isinstance(result, dict) and asserting the set of keys. All three pass on every mutation. They are not weak tests; on this function they are not tests at all, and they satisfy every coverage gate.

Is asserting one field good enough?

It catches a quarter of what the full result catches — 1 of 5 against 4 of 5. The three mutations it misses all change count or average while leaving total at 30, which is exactly what a partial assertion is blind to by construction. Assert the whole result unless you have a reason the rest is genuinely unspecified.

One mutation survives even the strongest assertion. What fixes it?

A different input, not a stronger assertion. Raising the filter threshold from > 0 to > 5 is invisible because both amounts in the test data are above 5 — no assertion on that data could catch it. Adding one row with amount 3 kills it. Weak assertions miss what the input exposed; weak inputs miss what no assertion could catch, and reviewers check neither.

How do you tell an implementation-coupled test from a behaviour test?

Ask: if I rewrote the body of this function keeping the same behaviour, would this test still pass? Measured against a real behaviour-preserving rewrite, four of six test styles break — log assertions, loop counts, helper calls, intermediate variables — while return-value and error-message assertions survive. A test that breaks when behaviour did not change is testing the implementation, will break again every time, and never catches a bug.

What does that coupling cost?

On 200 tests refactored four times a year at eight minutes a fix, three years is 214 hours at 67% coupling and 32 hours at 10% — a 6.7-fold difference from a property nobody measures. Which is why counting tests is the wrong metric: the number tells you nothing about whether the suite is an asset or a tax.

Your tests each flake one run in a thousand. Is that fine?

Not at scale. Every test must pass for the run to be green, so the rates multiply: 500 tests at 0.1% each is green 60.6% of runs, and 2,000 tests is green 13.5%. For a 99% green rate a 1,000-test suite allows 0.001% per test — a thousandfold tighter than "one run in a thousand". The budget is divided across the whole suite, so "only a bit flaky" is never a local judgement.

Why do teams re-run red builds instead of investigating?

Because at a 60% green rate they are correct to. Most red runs really are false, so re-running has a better expected payoff than investigating — the behaviour is rational and the process is broken. That is the arithmetic behind chapter 3's claim that a flaky check devalues the red build: red stops carrying information, and it is the one signal you cannot afford to lose.

Ten things to carry forward

  1. Not null, is a dict, has the keys: 0 of 5 mutants killed.
  2. One field catches a quarter of what the whole result catches.
  3. Assert the whole result unless the rest is genuinely unspecified.
  4. Some survivors need a new input, not a stronger assertion.
  5. Weak assertion and weak input are different failures. Check both.
  6. Four of six test styles break on a behaviour-preserving rewrite.
  7. Ask whether the test would survive a rewrite of the body.
  8. 67% coupling costs 214 hours over three years; 10% costs 32.
  9. 500 tests at 0.1% flake are green 60% of runs.
  10. A 1,000-test suite's per-test budget is 0.001%.

About the assertion figures

Five real mutations of a real function, each executed against each assertion. The 0-of-5 results are outcomes of running them, and the surviving mutation genuinely produces an identical result on the test data.

The same factor again

Suite flakiness is (1 − p)^N — the complement of chapter 10's Hyrum's Law. One saturates towards certainty and the other towards zero, from the same shape.
