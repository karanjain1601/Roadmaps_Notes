Reading a diff

Edit 40% of a file while renaming it and the diff shows 80 lines. Edit 60% and the same operation shows 200 — because rename detection is a threshold, and crossing it silently reclassifies a move as a deletion plus an addition.

Five passes, three of them before the code

What each pass is asking
PassReadQuestion
1The descriptionIs this the right problem?
2The testsWhat does the author think this does?
3The interfacesWhat did this promise?
4The diff, line by lineIs the implementation right?
5What is missingWhich case is not handled?
The first three can reject the change without reading it

Finding out at pass 1 that the problem is wrong costs a minute. Finding out after a line-by-line read costs an hour, and you have spent your attention establishing that code you are about to discard is correct.

Reading the tests before the implementation is the pass people skip and the highest-value one. The tests state what the author believed the change does — so you can check that belief against the description before checking the code against the belief.

The ordering also protects something measurable, which is the subject of section three: attention decays as a review goes on, and spending the early, sharp part of it on the wrong change is the most expensive mistake available.

The rename cliff

Git does not record renames. It infers them by comparing content: if a deleted file and an added file are similar enough — 50% by default — it reports a rename. Otherwise it reports both operations in full.

The crossing point is at 51% of lines edited, which is exactly git's -M50 default. It is a cliff, not a gradient: one line either side of it, the same change presents as twice as much code with none of it marked as moved.

And by chapter 4's model that is not merely cosmetic. 80 diff lines is reviewed at a 100% catch rate and 200 at 80% — twenty points of detection lost to a display decision the author did not know they were making.

Rename in one commit. Edit in another.

The reviewer then sees a rename with zero content change — which needs no reading at all — followed by an edit on the new path, at its true size. It costs the author one extra commit and it is the single highest-leverage habit in this chapter.

The last files in a pull request are reviewed markedly less carefully than the first, and nothing about their content caused it. Over eight files, the first three supply 49% of the findings from 38% of the files.

Two consequences, both actionable

Put the file that matters first. Most tools order alphabetically, which is arbitrary — and the model says position is worth up to 9.8× in how hard a file gets looked at. Saying "start with auth.py" in the description is free.

Splitting resets the curve. Eight files as one review yields 14.7 findings; as two reviews of four it yields 18.2 — a 24% improvement from nothing but restarting attention. That is a second argument for splitting, independent of chapter 4's: smaller diffs have fewer defects to miss and each new review begins at full attention.

The code that is not in the diff

You are reviewing a change to a function. Its callers are almost certainly not on screen.

Modelled: a six-file diff in an 800-file repository, a function with 20 callers. The expected number of those callers visible in the diff is 0.15. You are reviewing a signature change with 99% of its blast radius off-screen.

What covers the gap, and what does not

For a signature change in a typed language, the compiler covers it — every caller either updates or fails to build. That is a real safety net and it is why chapter 3's type-coverage section matters here.

For a semantic change that keeps the signature, nothing covers it. The caller still compiles and now means something different.

Five changes no compiler notices
Change
A unit changed — seconds to milliseconds
A default changed
An error is now raised instead of returned
An ordering guarantee dropped
None became a valid return

So the reviewer's question is not "is this code correct" — which you can answer from the diff — but "what did this code promise, and does it still promise it?" That question is also answerable from the diff, which is what makes it the right one. The caller list is not.

When the answer is "the promise changed", the follow-up is mechanical: search for callers, and say so in the review rather than assuming the author did.

The last one has a corollary worth stating: a reviewer who stops halfway through has lost far less than half the value, because the half they did was the sharp half. Stopping and returning tomorrow is better than finishing tired, and saying "I have reviewed the first four files" is a legitimate review state.

Check yourself

What should you read before the diff itself?

The description, the tests, and the interfaces — in that order. All three can reject the change without reading the implementation, and finding out at pass 1 that the problem is wrong costs a minute where finding out afterwards costs an hour. Reading the tests before the code is the pass people skip and the highest-value one: they state what the author believed the change does, so you can check that belief against the description before checking the code against the belief.

Why does renaming a file sometimes double the diff?

Because git does not record renames — it infers them by content similarity, defaulting to 50%. Editing 40% of a renamed 100-line file gives 60% similarity and shows as a rename plus 80 diff lines; editing 60% gives 40% similarity and shows as a delete plus an add at 200 lines. The crossing point measured at 51% of lines edited. It is a cliff, not a gradient.

Is that cliff just cosmetic?

No — it moves the change along chapter 4's detection curve. 80 diff lines is reviewed at a 100% catch rate and 200 at 80%, so twenty points of detection are lost to a display decision the author did not know they were making. The fix costs one commit: rename in one, edit in another. The reviewer then sees a rename with zero content change followed by an edit at its true size.

Does file position affect how carefully a file is reviewed?

Substantially. Modelled attention decay gives the first file 2.70 findings and the last 1.17 over eight files — a 2.3× difference — rising to 9.8× over twenty. Nothing about the content caused that. Over eight files the first three supply 49% of the findings from 38% of the files, so the file that matters should be first, and most tools order alphabetically instead.

Chapter 4 said splitting helps. Does this chapter add anything?

A second, independent effect. Chapter 4's argument was that smaller diffs have fewer defects to miss. This one is that each new review restarts attention at full: eight files as one review yields 14.7 findings, and as two reviews of four it yields 18.2 — a 24% improvement from resetting the curve alone, before any of chapter 4's effect. The two compound.

How much of a function's blast radius is visible while you review it?

Almost none. Modelled with a six-file diff in an 800-file repository and 20 callers, the expected number of callers visible is 0.15 — you are reviewing with 99% of the blast radius off-screen. For a signature change in a typed language the compiler covers it. For a semantic change that keeps the signature, nothing does: the caller still compiles and now means something else.

What question should you ask instead of "is this correct"?

"What did this code promise, and does it still promise it?" A unit changing from seconds to milliseconds, a default changing, an error being raised instead of returned, an ordering guarantee dropped, None becoming a valid return — none of these are visible to a compiler and all are visible in the diff. That is what makes it the right question: it is answerable from what is on screen, and the caller list is not.

Ten things to carry forward

  1. Five passes; three of them before reading code. They can reject the change for free.
  2. Read the tests before the implementation — they state the author's intent.
  3. Rename detection is a cliff at 51% edited, not a gradient.
  4. Crossing it turns 80 diff lines into 200 and costs 20 points of catch rate.
  5. Rename in one commit, edit in another.
  6. The first file gets 2.3× the attention of the eighth, 9.8× of the twentieth.
  7. Put the file that matters first; alphabetical is arbitrary.
  8. Splitting resets attention — 24% more findings on top of chapter 4's effect.
  9. 99% of a function's callers are off-screen while you review it.
  10. Ask what the code promised, not whether it is correct.

About the rename figures

The detector is real — it computes content similarity with difflib.SequenceMatcher, the same idea git uses, and reports a rename above the threshold. The 51% crossing point is the output of a binary search over edit fractions, not a quoted default.

The models

Attention decay and caller visibility are models, stated as such, each implemented and asserted. Their parameters are visible in the demos so you can see how much the conclusions depend on them.
