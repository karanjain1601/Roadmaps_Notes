Chapter 10 · What to look for

API semantics

Of eleven ways to change an API, eight are breaking — and the compiler catches four. Half of all breaking changes reach production compiling cleanly, and every one of them is a change to what a function means rather than how it is called.

Everything observable acquires a dependent

Hyrum's Law says that with enough users, every observable behaviour of your system is depended on by somebody — regardless of what you documented. It is usually quoted as a maxim. It is also a probability, and worth computing.

It takes 693 users for a coin-flip chance and 2,995 for 95%. And an ordinary function has around eight observable behaviours — iteration order, error message text, exception type, whether a field is present when null, timing, sort stability, output whitespace, the case of enum strings. At a thousand users, the chance that none of the eight has a dependent is 0.03%.

So "nobody uses that" is not a claim you can make

It is a claim about a probability that goes to zero as adoption rises. The useful question is not whether someone depends on the behaviour but whether you are willing to break them — which is a decision, and can be made deliberately.

The four silent ones share a property

None of them touches the signature. They change what a function means without changing how it is called — so every caller still builds, still passes its tests, and is now wrong.

That is the whole reason API semantics sits at the top of the pyramid. The four the compiler catches need no reviewer; the four it misses need one, and there is no other line of defence.

It also gives you a concrete thing to search for in a diff, which is more useful than "think about the API". Find every change where the signature is untouched but the behaviour is not — that is the whole class, and it is visible in the lines in front of you.

How long to support both

You have decided to break something. Supporting the old and new versions together costs upkeep every week; dropping the old one strands whoever has not migrated. Those two curves cross.

The cheapest window is 23 weeks — a 3.8-fold saving against breaking immediately, and cheaper than a year of dual support too. It is longer than most teams pick and considerably shorter than "forever".

The window is set by the migration rate, not by your release cadence

With a 3-week half-life the optimum is 14 weeks; with a 12-week half-life it is 34. Choosing "two releases" without reference to how fast callers actually migrate is choosing at random.

And one thing beats choosing well

Ship a migration script. Quadrupling the migration rate moves the optimum to 9 weeks and the total cost to 435 minutes — a 2.9-fold saving against the best window without one.

A codemod changes the curve; picking a window only chooses a point on it. That is worth more than any amount of deliberation about release counts, and it is the thing to ask for in review when someone deprecates an API with many callers.

Names are the API

A name is written once and read every time anyone touches a caller. Modelled at three edits per caller per year, four reads per edit, over three years:

At twenty callers that is a 720-to-1 read-to-write ratio. A bad name is not a one-off cost — it is a small tax on every read, and reads outnumber writes by nearly three orders of magnitude. That is why naming belongs in this chapter rather than in the style layer at the bottom of the pyramid.

The test that works

Can a caller predict the behaviour from the name without reading the body? If not, the name is wrong — however accurate it may be.

getUser that also creates one, validate that mutates, size that is O(n): each is defensible and each fails the test, because the caller who trusted the name wrote a bug.

The fifth is the one nobody asks and the one that decides the rest. Nothing about the code changes when the fifth team starts calling it — but its position on the pyramid does, and no notification is sent. The moment to ask is while it is cheap to answer.

That may be exactly what you want, and it is a decision about blame rather than about risk. Worth being clear which one you are buying.

Check yourself

How many users before a quirk becomes load-bearing?

At one in a thousand users depending on any given observable behaviour: 693 for a coin flip, 2,995 for 95%, and effectively certain by twenty thousand. An ordinary function has around eight observable behaviours, so at a thousand users the chance that none of them has a dependent is 0.03%. "Nobody uses that" is a claim about a probability that goes to zero.

What counts as an observable behaviour?

Far more than the return value: iteration order, error message text, the exact exception type, whether a field is present when null, timing and latency, sort stability, whitespace in output, the case of enum strings. Anything a caller can detect, someone eventually detects and relies on — which is why the count of eight per function is conservative rather than pessimistic.

Can you rely on the build to catch breaking changes?

For half of them. Of eleven kinds of API change, eight are breaking, and the compiler catches four: adding a required parameter, renaming a method, widening a return type, narrowing an accepted type. The other four — changing a default, changing units, raising instead of returning null, dropping an ordering guarantee — compile cleanly and pass every test.

What do the four silent breaking changes have in common?

None of them touches the signature. They change what a function means without changing how it is called, so every caller still builds and is now wrong. That gives a concrete thing to search a diff for, rather than a vague instruction to think about the API: find every change where the signature is untouched but the behaviour is not.

How long should a deprecation window be?

Set by the migration rate, not the release cadence. Upkeep rises linearly and breakage falls exponentially, so there is a minimum: with 40 callers and a 6-week half-life it sits at 23 weeks, costing 1,257 minutes against 4,800 for breaking immediately. A 3-week half-life moves it to 14 weeks and a 12-week half-life to 34 — so "two releases" chosen without reference to migration speed is chosen at random.

What beats picking the window well?

Shipping a migration script. Quadrupling the migration rate moves the optimum to 9 weeks and the total cost to 435 minutes — 2.9× cheaper than the best window without one. A codemod changes the curve; choosing a window only picks a point on it. It is the thing to ask for in review when someone deprecates an API with many callers.

Why is naming an API concern rather than a style one?

Because of the read-to-write ratio. A name is written once and read every time anyone touches a caller — at twenty callers, roughly 720 reads over three years. A bad name is a small tax on each of them. The working test is whether a caller can predict the behaviour from the name without reading the body: getUser that also creates one fails it, however defensible the name is.

About the models

Hyrum's Law here is 1 − (1−p)^N with p as a slider, so you can see how little the conclusion depends on the exact rate. The deprecation curve has three parameters — upkeep, breakage cost and migration half-life — all visible in the demo.
