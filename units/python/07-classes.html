Classes and objects

A class is an object holding a dictionary, and an instance is another object holding another dictionary. Attribute access searches those dictionaries in a defined order, and self is just the first parameter. Nearly everything that surprises people about Python classes — shared state between instances, super() going somewhere unexpected — follows from those two sentences.

The mechanics

python
class Account:
    currency = "GBP"                # class attribute — ONE object, shared by every instance

    def __init__(self, owner, balance=0):
        self.owner = owner          # instance attributes — created here, per instance
        self.balance = balance

    def deposit(self, amount):      # `self` is the first parameter, nothing more
        self.balance += amount
        return self.balance

    @classmethod
    def zero(cls, owner):           # receives the CLASS. The idiom for alternative constructors,
        return cls(owner, 0)        # and cls means a subclass gets a subclass back

    @staticmethod
    def is_valid(code):             # receives nothing. A plain function that lives here for tidiness
        return len(code) == 3

# a.deposit(50) is exactly Account.deposit(a, 50) — the dot does the binding
a = Account("ada")
a.deposit(50) == Account.deposit(a, 50)
Why self is explicit

It is not ceremony. a.deposit produces a bound method — an object pairing the function with a — and calling it inserts a as the first argument. Because the mechanism is visible rather than magic, a method is an ordinary function you can pass around, store in a dictionary, or call on the class with an explicit instance. It also means there is no ambiguity between a local variable and an attribute: balance and self.balance are unmistakably different, which removes a whole category of bug that languages with an implicit this have to work around with naming conventions.

Where an attribute comes from

Reading obj.x searches the instance dictionary, then the type, then each class in the MRO, and finally calls __getattr__ if one exists. Writing obj.x = ... does something different: it always writes to the instance.

Attribute lookup, step by step
Compare "assign an int" with "mutate a list"
Assignment never touches the class
a.total += 1 reads the class attribute, adds one, and stores the result on the instance. Afterwards a.total is 1, b.total is 0, Account.total is 0, and 'total' has appeared in a.__dict__. The class attribute was read and then shadowed.
Mutation does the opposite
a.items.append("x") never assigns anything, so it reaches the one list on the class — and a.items is b.items is True. Every instance sees the change. This is chapter 5's mutable default in a different costume: one object created once at class-definition time and shared by everyone.
A data descriptor is the documented exception
A property lives on the type and wins over the instance dictionary. Assigning to a read-only property raises AttributeError, and even smuggling a value directly into c.__dict__["x"] does not help — c.x still returns the property. That inversion is what makes properties reliable.
__getattr__ is the last resort
It runs only when the normal search has already failed, so it cannot shadow a real attribute. __getattribute__ is the one that intercepts everything, and is almost always the wrong tool — it is very easy to write an infinite recursion in it.
The shared class attribute

Writing class Cart: items = [] and then self.items.append(x) gives every cart in the process the same contents. It usually survives testing because a test creates one instance, and it fails in production where several exist. The rule is simple: class attributes are for values shared by design — constants, defaults, counters you actually want shared — and anything mutable and per-instance belongs in __init__. If you want the terse form, a @dataclass with field(default_factory=list) gives you a fresh list per instance and refuses outright if you try to use a mutable literal as a default, which is the linting Python does not do elsewhere.

Inheritance, the MRO, and super()

The most common misconception in Python OOP is that super() means "the parent class". It does not. It means "the next class in the MRO of the object's actual type" — which can be a class the current one has never heard of.

The same super() call, two different destinations
Switch between calling on a D and calling on a B
D.__mro__ is D B C A object
Computed by C3 linearisation, which preserves each class's own order and guarantees a class appears before all of its bases. You can print it on any class.
The same line resolves differently per instance
super().who() inside B reaches C when called on a D, and reaches A when called on a B. B has no relationship with C whatsoever. That is the whole point of cooperative inheritance and the reason the "parent class" model breaks.
Which means every class must call super()
One class in the chain that does not is enough to skip everything after it — ['L', 'Broken'] instead of ['L', 'Broken', 'R', 'Base']. There is no error and no warning; the class is simply never reached.
An impossible order is rejected at class creation
class C(A, B) where B already inherits from A fails immediately with TypeError: Cannot create a consistent method resolution order (MRO) for bases A, B. Better to find out at import time than at call time.
Composition first, and mixins with care

Multiple inheritance is worth understanding and worth using sparingly. It works well for genuine mixins — small, orthogonal, cooperative classes that each add one capability and each call super() — and badly for modelling "is a" relationships from two directions at once, which is where the MRO stops being predictable to a reader. Two practical guards: give mixin methods distinctive names so they cannot silently collide, and accept *args, **kwargs in any cooperative __init__ so a class further along the MRO still receives what it needs. If you find yourself drawing the diagram to work out what will run, composition — holding an object rather than inheriting from it — is usually the clearer design.

class Point:
    x: float
    y: float

                                                     # the one place Python enforces it

# a __hash__ as well. `slots=True` removes __dict__, which makes instances

# a property turns an attribute into computed behaviour without changing callers
class Circle:
    def __init__(self, r): self._r = r

    @property
    def area(self): return 3.14159 * self._r ** 2   # c.area, not c.area()

    @property
    def r(self): return self._r

    @r.setter
    def r(self, value):                              # validation at the boundary
        if value <= 0: raise ValueError("radius must be positive")
        self._r = value
Defining __eq__ silently removes hashability

Add an __eq__ to a class and Python sets __hash__ = None, so instances can no longer go in a set or be used as dict keys — TypeError: unhashable type. That is deliberate rather than an oversight: two objects that compare equal must hash equally, and Python cannot guess how, so it refuses rather than letting you corrupt a dict. If the object is immutable, define __hash__ over the same fields __eq__ uses. If it is mutable, leaving it unhashable is the correct outcome — a mutable key whose hash changes while it sits in a dict becomes permanently unreachable, which chapter 4 described from the container's side. A frozen dataclass handles both halves for you.

Check yourself

Self-check

  1. class Cart: items = [] and every cart shows the same contents. Explain, and fix it.
    The list is a class attribute — one object, created once when the class statement executed, shared by every instance. self.items.append(x) never assigns anything, so the lookup finds the single list on the class and mutates it; a.items is b.items is True. It survives testing because a test usually creates one instance. The fix is to create the list per instance in __init__: self.items = []. Note the contrast that makes the rule feel inconsistent: a.total += 1 on a class attribute does not affect other instances, because += is an assignment and assignment always writes to the instance dictionary, shadowing the class attribute. Read-and-mutate reaches the class; read-and-rebind creates an instance attribute. This is exactly chapter 5's mutable default in different clothing — one object created once at definition time and shared by everyone.
  2. What is super() in a class B actually referring to?
    The next class after B in the MRO of type(self) — not B's parent. With class D(B, C) where both B and C inherit from A, D.__mro__ is D B C A object. So super().who() written inside B goes to C when called on a D instance, and to A when called on a B instance — the same line of code, two destinations, and B has no static relationship with C at all. That is what makes cooperative multiple inheritance work: each class delegates to whatever comes next without knowing what that is. The practical consequence is that every class in the chain must call super(), because one that does not silently truncates the rest — you get ['L', 'Broken'] instead of ['L', 'Broken', 'R', 'Base'], with no error. And any cooperative __init__ should accept *args, **kwargs so the classes after it still receive their arguments.
  3. Why can't a property be shadowed by setting the attribute on the instance?
    Because a property is a data descriptor — it defines __set__ (or __delete__) as well as __get__ — and data descriptors on the type take priority over the instance dictionary. That is the documented exception to the instance-first rule. Assigning to a read-only property raises AttributeError: property 'x' of 'C' object has no setter, and even writing directly into c.__dict__["x"] does not help: the lookup checks the type for a data descriptor first, finds the property, and returns its computed value while the smuggled entry sits there unused. The inversion is what makes properties trustworthy — a computed attribute cannot be accidentally overwritten. Note the contrast with a non-data descriptor such as a plain function: those lose to the instance dictionary, which is why you can shadow a method by assigning to it on an instance.
  4. You add __eq__ to a class and it can no longer be a dict key. Why?
    Defining __eq__ sets __hash__ to None, so instances become unhashable and raise TypeError: unhashable type. It is deliberate. The contract is that objects comparing equal must hash equally, and once you have redefined equality Python has no way to know which fields the hash should use — so rather than let you build a dict that silently loses keys, it refuses. If the object is immutable, define __hash__ over the same fields __eq__ compares, typically hash((self.a, self.b)). If it is mutable, unhashable is the right answer: chapter 4 described the container's side of this, where a key whose hash changes after insertion is stored in one bucket and looked up in another, becoming permanently unreachable. @dataclass(frozen=True) generates both correctly and is usually the right choice.
  5. What does @classmethod give you that a plain function would not?
    It receives the class as its first argument, and crucially the actual class rather than the one it was defined in. That makes it the correct way to write an alternative constructor: @classmethod def from_json(cls, data): return cls(**data) returns a SubAccount when called on SubAccount, whereas hard-coding Account(...) would always return the base type and silently break every subclass. The standard library uses this everywhere — dict.fromkeys, datetime.fromtimestamp. Compare @staticmethod, which receives nothing and is just a function namespaced inside the class; it is fine for a helper that logically belongs with the class but touches neither instance nor class state, though a module-level function is often clearer. If you find yourself writing a static method that takes the instance as an explicit argument, you wanted a normal method.
  6. What does slots=True on a dataclass change?
    It removes the per-instance __dict__ and stores attributes in a fixed array instead. Two consequences follow. Memory drops substantially — often around half for a small object — and attribute access gets slightly faster, which matters when you have millions of instances. And you can no longer set an attribute that was not declared: p.z = 1 raises AttributeError, which catches typos that would otherwise silently create a new attribute nobody reads. The costs are real but narrow: you cannot attach arbitrary attributes at runtime, multiple inheritance from two slotted classes with overlapping slots is an error, and anything relying on __dict__ — some serialisers, some mocking — needs adjusting. For a value object created in bulk it is close to free improvement; for a rich object with a handful of instances it makes no measurable difference.
  7. When should you reach for inheritance rather than composition?
    When the subclass genuinely satisfies the base's contract everywhere the base is used — so any caller holding a base reference can be handed the subclass without knowing. That is a stronger requirement than "shares some code", which is the usual reason people inherit and is better served by composition or a module-level function. Two specific cases where inheritance earns its place: implementing a framework's interface, where the base defines the protocol and you fill in the methods; and small orthogonal mixins that each add one capability and each call super() cooperatively. What it handles badly is modelling from two directions at once, where the MRO stops being obvious to a reader — and the diagnostic is simple: if you have to draw the diagram to work out which method runs, the design is doing something a reader cannot follow. Holding an object as an attribute and delegating explicitly is nearly always easier to change later.
