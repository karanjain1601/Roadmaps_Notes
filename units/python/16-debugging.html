Debugging and profiling

Two skills that look different and are the same one: finding out what the program is actually doing rather than what you believe it is doing. A traceback already contains most of the answer, a debugger costs less than the print statements you were about to write, and a profiler routinely contradicts the guess you were about to act on.

Reading a traceback

Bottom-up. The last line is what escaped, the frame above it is where, and each block above that is a cause. Most of the frames in between are irrelevant library internals.

A real chained traceback
Step from the bottom and watch which line matters
Start at the bottom
RuntimeError: row 41 is malformed is what escaped. The File …, line 10, in main immediately above it is where. Everything higher is how you got there.
Then find your deepest frame
In a real traceback most frames belong to a framework. The last one whose path is inside your project is almost always where the fix goes.
Two tracebacks means a chained exception
The upper block is the original ValueError; the lower is what was raised while handling it. Chapter 8's distinction shows up in the wording — "direct cause" for raise … from e, "During handling of the above exception, another occurred" for a bare raise inside an except.
And that wording is a signal
"Direct cause" means someone deliberately translated the error. "During handling" often means a second, accidental bug in the error path — an AttributeError in the handler that is now hiding the real failure.
python — getting more out of a failure
import traceback, logging

logging.exception("import failed")   # inside an except block: message + full
                                      # traceback, at ERROR. Never log str(e) alone —
                                      # "invalid literal for int()" without a frame
                                      # is nearly useless

traceback.print_exc()                 # when you have no logger yet

python -X dev script.py               # development mode: extra warnings and checks
python -m pdb -c continue script.py   # drop into pdb at the point of an uncaught
                                      # exception, with the frame still alive

When a print is genuinely better

A debugger is the wrong tool when the bug is in the shape of the data over time rather than at one moment — an accumulating error, a value that is wrong on the four hundredth iteration, anything concurrent where stopping changes the behaviour. There, printing or logging in a loop and reading the sequence is faster and does not perturb the timing. The upgrade over a bare print(x) costs nothing: print(f"{x=} {y=}") prints both the expression and its value, so you never end up with a column of unlabelled numbers. For anything you might want twice, use logging.debug instead, which you can leave in place and switch on with a configuration change rather than an edit.

python — logging, set up once at the entry point
import logging
logger = logging.getLogger(__name__)      # module-level, named for the module

logging.basicConfig(                       # ONLY in main() / __main__ — never in a
    level=logging.INFO,                    # library, which should only ever get a
    format="%(asctime)s %(name)s %(levelname)s %(message)s",  #  logger
)

logger.info("processed %d rows", n)        # %s style, NOT an f-string: the formatting
                                            # is skipped entirely if the level is off
logger.exception("row %d failed", i)        # inside except: adds the traceback

# and the reason to bother at all: a library that adds a NullHandler and logs to
# its own named logger lets the APPLICATION decide the level, format and
# destination — which print() takes away from it permanently
logging.getLogger("mylib").addHandler(logging.NullHandler())

Profiling before optimising

Where the time actually goes
Look at fast_part: 0% by one measure, 18% by the other
tottime is time in the function's own code; cumtime includes everything it calls
main has cumtime 0.105 s — the entire run — and tottime 0.008 s. It is 100% of the program and 0% of the work. Sort by tottime to find hot code, by cumtime to find the hot path.
Which is why fast_part is the interesting row
tottime 0.000 s and cumtime 0.019 s. Its own bytecode does nothing; the work happens inside the C sum() it calls, which the profiler bills to sum. By tottime it looks free. By cumtime it is 18% of the run.
Amdahl sets the ceiling before you start
slow_part is 59% of the run, so making it infinitely fast caps out at 2.44×, and a realistic 2× improvement buys 1.42×. The same effort on helper at 15% buys 1.08×.
So measure first, and measure the right thing
Profiling adds overhead and distorts short functions, so use it to find where and timeit to measure how much. And profile something the size of real work — a hot spot at production data volumes is often not the one in your test fixture.
bash / python
python -m cProfile -s tottime script.py | head -20
python -m cProfile -o out.prof script.py    # then: snakeviz out.prof

python -m timeit -s "setup" "statement"     # microbenchmarks, auto-repeats

# line-level, when the function is hot but you cannot see which line:
#   pip install line_profiler, then @profile and kernprof -l -v

# memory rather than time — stdlib, no install:
import tracemalloc
tracemalloc.start()
...
for stat in tracemalloc.take_snapshot().statistics("lineno")[:10]:
    print(stat)

Check yourself

Self-check

  1. A traceback is forty lines of framework internals. Which line do you read?
    Two. The last line, which names the exception type and message and tells you what actually escaped; and the deepest frame whose file path is inside your project, which is almost always where the fix goes. Everything between them is the framework doing its job. The order confuses people because it is chronological rather than by relevance — "most recent call last" means the bottom is nearest the failure, so read upwards. Two habits make this fast: configure your editor or a tool such as rich or pytest --tb=short to trim library frames, and never catch an exception only to log str(e), which throws away every frame and leaves you with a message like "invalid literal for int()" and no idea where. logging.exception inside the except block keeps the whole thing.
  2. What does "During handling of the above exception, another occurred" tell you?
    That a second exception was raised inside an except block, and nobody linked the two deliberately. Python attaches the original as implicit context, which is chapter 8's __context__. The wording matters because it is different from raise … from e, which produces "The above exception was the direct cause of the following exception" — that phrasing means a developer deliberately translated one error into another and the chain is intentional. "During handling" is frequently a second bug, in the error path: an AttributeError or KeyError in the handler that is now obscuring the real failure, often because the handler assumed something about the error state that was not true. So when you see it, read the upper traceback first — that is the original problem — and treat the lower one as a bug in your error handling.
  3. Your function shows 0.000 s of tottime. Can you ignore it?
    No — check its cumtime first. In the measured example, fast_part has tottime 0.000 s and cumtime 0.019 s, which is 18% of the whole run. Its own bytecode does almost nothing; the work happens inside the C sum() it calls, and the profiler bills that time to sum rather than to its caller. So by tottime it looks free and by cumtime it is a meaningful chunk of the program. The two columns answer two different questions. tottime bounds what you can gain by rewriting the code inside the function; cumtime bounds what you gain by removing the call and everything beneath it. Sort by tottime to find hot code you can edit, and by cumtime to find an expensive path you might avoid entirely — caching a result, or not making the call at all, is often the larger win.
  4. A function is 15% of runtime. You make it twice as fast. What happens?
    The program gets about 1.08× faster — roughly a 7% saving. Amdahl's law: the improvable part shrinks by half and the other 85% is untouched, so the total goes from 1.0 to 0.848 + 0.076 = 0.924. For comparison, the same 2× improvement applied to the 59% function in the measured example gives 1.42×, and even making the 15% function infinitely fast caps out at 1.18×. Two conclusions follow. First, the ceiling is set before you write a line, so calculate it from the profile and decide whether the work is worth doing. Second, if the ceiling on every individual function is low, the answer is not micro-optimisation — it is an algorithmic change, doing less work, or moving the work somewhere else. That is a decision the profile can prompt and a micro-benchmark never will.
  5. Why logger.info("processed %d rows", n) rather than an f-string?
    Because the formatting only happens if the message is actually emitted. With an f-string the interpolation runs before logger.info is even called, so a debug line in a hot loop costs its formatting on every iteration even when the level is set to WARNING and nothing is written. With %s-style arguments, logging holds the format string and the values and only combines them if a handler wants them. Two secondary benefits. Log aggregation systems can group messages by their format string, so every "processed %d rows" is one event type with a varying parameter rather than thousands of distinct strings. And a value that raises when formatted — a broken __repr__ — degrades to a logging error rather than taking down the code path that was trying to log. The cost is a slightly less natural syntax, which is why the rule is easiest applied as a lint rule rather than remembered.
  6. Why should a library never call logging.basicConfig?
    Because it configures the root logger, which belongs to the application. A library that calls it decides the level, format and destination for every log line in the whole process, including code it knows nothing about — and since basicConfig does nothing if handlers already exist, the outcome depends on import order, which makes it intermittent. What a library should do is get a named logger with logging.getLogger(__name__), log to it, and attach a NullHandler so that a message produces no output and no "no handlers could be found" warning when the application has not configured anything. The application then calls basicConfig or builds handlers once at its entry point, and can set your library's verbosity independently with logging.getLogger("mylib").setLevel(...). The same reasoning is the real argument against print in library code: it takes that choice away permanently.
  7. You profile a function and it is fast. In production it is slow. What might differ?
    Most often the data. An algorithm that is quadratic looks fine on the hundred-row fixture and dies on the million-row table, so profile at something like production volume or the profile is answering a different question. Beyond size: the cache is warm locally and cold in production; the database is on localhost rather than across a network, which turns an N+1 query pattern from invisible into dominant; concurrency means your function is competing for a GIL or a connection pool that does not exist on your machine, which chapter 14 covered. Two measurement traps as well. cProfile adds per-call overhead, so it exaggerates functions called very often and can point at the wrong one — cross-check a candidate with timeit. And it measures CPU work in the calling thread, so time spent waiting on I/O or blocked on a lock barely registers; for those, wall-clock timing around the suspicious block tells you far more than the profile does.
