The one number worth memorising
At 1,000 items, x in list took 9,892 ns and x in set took 33 ns — 299×. This is the most common performance bug in Python and the easiest to fix.
Growing 1,000 → 8,000 separates O(n) from O(1)
The list scan got 7.9× slower — very nearly the 8× the size grew — and the set lookup 1.00×. Complexity classes, measured rather than asserted.
list.insert(0, x) is O(n)
6,052 ns against 20 ns for append, because everything shifts. If you are adding at the front, collections.deque does it in 25 ns.
And the ordering caveat from chapter 4
Dicts preserve insertion order and sets do not. If you need distinctness and order, use dict.fromkeys(items), not set.

The pattern in the red column

Nearly every entry marked as a problem is a case where Python does something reasonable that is not what you expected, and says nothing. That is the through-line of the whole unit: the language very rarely stops you, so the discipline has to come from elsewhere — from a linter for the things that are statically visible, a type checker for the contracts, tests that assert values rather than absence of exceptions, and a measurement rather than a memory when performance matters. None of the four is optional, because each is blind to what the others catch.

Check yourself

Self-check

  1. You have a list of 8,000 IDs and check membership in a loop. What do you change, and what do you gain?
    Convert it to a set once, before the loop. Measured at 1,000 items, x in list took 9,892 ns and x in set took 33 ns — 299×. And the gap widens with size: growing from 1,000 to 8,000 made the list scan 7.9× slower, almost exactly the 8× the collection grew, while the set lookup stayed at 1.00×. That is the difference between O(n) and O(1) appearing as a measurement rather than a claim. Two caveats worth carrying. The conversion itself is O(n), so it pays only if you check more than a handful of times — inside a loop, always; for one check, never. And sets do not preserve insertion order, so if you also need order use dict.fromkeys(items), which gives O(1) membership and keeps the sequence.
  2. Which single measurement in this unit best argues for running a linter?
    The undefined name in a cold branch. The file compiles, imports, and runs the hot path returning exactly the right answer — NameError arrives only when that branch executes, which for an error handler may be weeks later at an unhelpful hour. So byte-compiling passes, importing passes, and the test suite passes unless it specifically exercises that path, which error paths notoriously lack. A linter finds it statically in milliseconds without running anything. The unused import makes the complementary case from the other side: it passes every execution-based gate and always will, because it is not a behaviour difference at all — it is a cost, and only static analysis addresses that category. Together they show the four tools partition the space rather than overlapping, which is why "the tests pass" is not an argument against the other three.
  3. Name two pieces of common Python advice this unit found to be wrong.
    First, hoisting m = obj.method out of a loop. It measured 0.95× — no gain, marginally negative — because since 3.11 the specialising interpreter (PEP 659) caches the attribute lookup inline, doing by itself what the hoist did by hand. Second, that a misspelled mock assertion passes silently: modern unittest.mock guards assertion-shaped names, so assert_called_onec and called_once both raise AttributeError. Only names that do not look like assertions, such as was_called, still slip through as truthy Mocks. A third if you want it: comprehensions as a performance fix, measured at 1.14× over an append loop. The pattern is that each was true when written and describes an interpreter or a library that has since changed, which is the argument for measuring on the version you actually run rather than remembering.
  4. A colleague reports a bug that only happens twice a year. What are the likely candidates from this unit?
    Daylight saving. Adding a timedelta to an aware datetime does wall-clock arithmetic, so three hours added across a spring-forward elapses only two real hours — the fields advance by three and an hour did not exist. The autumn case is worse because both answers are valid: the two 01:30s compare equal to each other while mapping to UTC instants an hour apart, so sorting by local time interleaves them and a range query returns the wrong set. Both are invisible for about 363 days a year, which is precisely what makes them expensive: the code looks correct, passes review and passes tests written on an ordinary date. The fix is structural rather than defensive — store UTC, compute in UTC, convert only for display — and if you genuinely need recurring local times, store a zone name rather than an offset and recompute, because a zone's offset is a function of the date.
  5. What is the honest limit of the concurrency and gate-ordering measurements here?
    Both hit the ceiling of the machine rather than of the idea. The concurrency chapter ran on a single CPU, so it could measure that threads give no CPU speedup (1.15×, the GIL) and that processes give none either on one core (1.04×) — but it could not demonstrate the multi-core process speedup at all, so above one core the demo models it and labels the row. The tooling chapter tried to measure "cheapest gate first" and got the opposite: byte-compiling cost 26 ms above interpreter startup while running the test file cost 10 ms, because py_compile loads its own machinery and the test was two assertions. On a one-file project each gate's fixed overhead swamps its work. Both are reported as what they are. The general lesson is the one chapter 16 opened with: a measurement answers the question you actually asked, and knowing which question that was is most of the skill.
  6. Where would you start on an existing untyped, untested codebase?
    In roughly this order, because each step makes the next cheaper. Add a formatter and commit the reformat separately, which costs nothing and ends a category of review argument. Add ruff with F and B selected — those are the rules that find real bugs, and the first run on a codebase that has never had one usually turns up several. Then write a regression test at the moment you next fix a bug, rather than attempting coverage as a project. Then annotate boundaries only — public functions, data models, anything crossing a module edge — and turn on disallow_untyped_defs per module as each is done, so the checked area can only grow. What not to do is set a coverage target, which chapter 15 measured producing a suite with 100% coverage and zero of six bugs caught. The gate you can satisfy without doing the work is the gate that gets satisfied without doing the work.
  7. What single habit would have prevented most of the defects in this unit?
    Checking the value rather than the absence of an exception. The suite with 100% line coverage caught none of six bugs because it asserted is not None; the same coverage asserting actual values caught five, and the sixth was an equivalent mutant no test could kill. The pattern repeats across chapters: the annotation violation and the wrong result never raise, they return a wrong answer; the mutable default returns 1, 2, 3 across identical calls and looks perfect on the first; the flat-layout wheel imports the source tree and passes. In every one, something ran without error and was wrong. The habit has a cheap version that needs no tooling: after writing a test, go and break the code it covers — flip a comparison, change a constant — and confirm the test fails. If it does not, you have learnt something no coverage report would have told you.
