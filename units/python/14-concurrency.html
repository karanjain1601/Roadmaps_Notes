Concurrency and async

Python has three concurrency models and picking the wrong one gives you the overhead without the benefit. The choice is decided almost entirely by one question — whether your program is waiting or computing — and by one implementation detail, the global interpreter lock, which is less mysterious than its reputation.

— words— min read2 interactivesNeeds: chapters 08, 09

The GIL, precisely

One lock in the interpreter, held by whichever thread is currently executing Python bytecode. It is released on I/O, released periodically so other threads get a turn, and released by C extensions that do not touch Python objects — which is why NumPy is not affected the way pure Python is.

What it prevents
Two threads running Python bytecode simultaneously. So threads give no speedup on CPU-bound Python work, however many cores you have.
What it does not prevent
Concurrency during I/O — the lock is released while a thread waits on a socket, a file or a subprocess, so other threads run. That is why threads work well for I/O.
What it does not give you
Thread safety. The lock guarantees each bytecode is atomic, not that your operation is. counter += 1 is several bytecodes and can interleave, so you still need a Lock.
And it is on its way out, slowly
3.13 ships an optional free-threaded build (PEP 703). It is not the default, extension support is incomplete, and single-threaded code is somewhat slower — worth watching, not yet worth planning around.
Which model for which workload
Switch the workload — the ranking inverts completely
The measurements, and what this machine could not show

The one-core figures were measured on the machine that built this page. CPU-bound, four tasks: sequential 0.67 s, threads 0.58 s (1.15×), processes 0.65 s (1.04×). I/O-bound, twenty 100 ms waits: sequential 2.00 s, threads 0.10 s (19.5×), asyncio 0.10 s (19.7×).

That machine had one CPU, so it cannot demonstrate the multiprocessing speedup — with no second core, four processes just add spawn and pickling overhead. Above one core the demo therefore models the process case rather than reporting a measurement: measured per-task work, divided across the cores you select, plus the measured process overhead. The thread and asyncio curves stay measured, because the GIL makes them independent of core count.

The event loop

python
import asyncio

async def fetch(session, url):        # a coroutine — calling it runs NOTHING,
    async with session.get(url) as r:  # exactly like chapter 9's generator
        return await r.json()

async def main():
    async with aiohttp.ClientSession() as s:
        results = await asyncio.gather(*(fetch(s, u) for u in urls))

    # …all tasks are complete here          ExceptionGroup (chapter 8)

asyncio.run(main())                    # one loop, at the top, once

sem = asyncio.Semaphore(20)

    async with sem:
        return await fetch(s, u)

async with asyncio.timeout(5):         # 3.11+
    await fetch(s, url)
What blocks the loop
One line's difference, ten times the wall clock
Ten tasks, 100 ms each: 0.101 s or 1.002 s
Awaiting asyncio.sleep finishes in one interval; calling time.sleep takes the full ten. One line's difference, and the concurrency is gone.
Because the loop is a single thread
While a blocking call holds it, nothing else runs — not the other tasks, not the timers, not the server accepting connections. The program is not slow, it is serialised.
asyncio.to_thread restores it
0.201 s at ten tasks: the blocking work moves to a thread pool and the loop stays free. That is the correct wrapper for any synchronous library you cannot replace.
Which is why one sync driver undoes a whole framework
A synchronous database call inside an async request handler blocks every concurrent request on that worker. The framework's benefit is entirely contingent on nothing in the request path blocking.

Getting it wrong

Forgetting await
Calling a coroutine without awaiting it does nothing at all and returns a coroutine object — like calling a generator function, from chapter 9. Python emits RuntimeWarning: coroutine was never awaited, which is easy to miss in a busy log. Run with -W error::RuntimeWarning in tests.
Fire-and-forget tasks that vanish
asyncio.create_task returns a task the loop holds only weakly, so a task nobody keeps a reference to can be garbage-collected mid-flight. Keep the reference, or use a TaskGroup, which is one of several reasons to prefer it.
Assuming the GIL makes you thread-safe
It does not. counter += 1 is a read, an add and a write, and the lock can be released between them — so a hundred threads incrementing a shared counter reliably lose updates. Use a Lock, or a queue.Queue, which is designed for it.
Sharing state between processes
Processes have separate memory, so a global modified in a worker is invisible to the parent. Everything crossing the boundary is pickled, which means arguments must be picklable — a lambda is not — and large arguments cost real time to copy.
The colour problem

An async function can only be awaited from another async function, so a single async call deep in a call stack forces every caller above it to become async too. That is why adopting asyncio tends to convert a whole codebase rather than a corner of it, and why many libraries maintain two parallel APIs. Two escape hatches, both with costs: asyncio.run() starts a loop to call async code from sync, but cannot be called from inside a running loop; asyncio.to_thread() goes the other way and costs a thread. If you are choosing at the start of a project, concurrent.futures.ThreadPoolExecutor handles a great deal of I/O concurrency with none of this, and is genuinely the right answer more often than its reputation suggests — asyncio's advantage appears at thousands of concurrent connections, not dozens.

Check yourself

Self-check

  1. You move CPU-bound work into four threads and it does not get faster. Why?
    The global interpreter lock. Only one thread executes Python bytecode at a time, so four threads doing arithmetic take the same wall-clock time as doing it four times in a row — measured at 0.67 s sequential against 0.58 s with threads, which is within noise of no improvement. The lock is released on I/O and released periodically to let other threads have a turn, but that only reorders the work, it does not parallelise it. For CPU-bound Python the answer is ProcessPoolExecutor, which sidesteps the lock by using separate interpreters — at the cost of process spawn time and pickling everything that crosses the boundary, so it only pays for tasks large enough to amortise that. Two important exceptions: C extensions such as NumPy release the lock while computing, so threads do help there; and 3.13's optional free-threaded build removes the lock entirely, though it is not the default yet.
  2. An async endpoint calls a synchronous database driver. What happens to the other requests?
    They stop. The event loop is a single thread, so while a blocking call holds it nothing else progresses — not the other in-flight requests, not the timers, not the socket accepting new connections. The measurement is stark: ten tasks each waiting 100 ms take 0.101 s when they await properly and 1.002 s when they call time.sleep instead. One line's difference, and the concurrency is entirely gone. The service is not slow in the usual sense; it is serialised, and it will look fine under single-request testing and collapse under load. The fix is either an async driver, or wrapping the synchronous call in asyncio.to_thread, which moved the same workload back to 0.201 s by keeping the loop free. This is why one synchronous dependency in the request path can cost more throughput than the entire framework gained.
  3. Does the GIL make your code thread-safe?
    No, and this is the most consequential misunderstanding of it. The lock guarantees that a single bytecode instruction is atomic — it does not guarantee that your operation is. counter += 1 compiles to a load, an add and a store, and the interpreter can release the lock between them, so two threads can both read 5, both compute 6, and both write 6: one increment is lost. With enough threads and iterations this is not theoretical, it is reliable. You still need a threading.Lock around any read-modify-write on shared state, or better, a design that avoids shared mutable state at all — queue.Queue is built for handing work between threads safely, and having each thread own its data and return a result is simpler than locking. The rule of thumb: if you would need a lock in a language without a GIL, you need one in Python.
  4. When is asyncio genuinely better than a thread pool?
    At high connection counts, and when you need fine control over cancellation and timeouts. The measurements make the point about the ordinary case: twenty concurrent 100 ms waits took 0.10 s with threads and 0.10 s with asyncio — identical, because both simply wait. The difference is cost per unit of concurrency. A thread carries an OS stack, typically a megabyte of reserved address space, and every switch goes through the kernel; an asyncio task is a Python object of a few hundred bytes and switches are function calls. So a few dozen concurrent operations are equally well served by ThreadPoolExecutor, and tens of thousands of open sockets are practical only with asyncio. Against that, asyncio brings the colour problem, requires async-native libraries throughout, and makes a single blocking call catastrophic rather than merely slow. For most applications a thread pool is the right answer and the boring one.
  5. Why might a task created with asyncio.create_task never finish?
    Because the event loop keeps only a weak reference to it, so if you do not keep the returned task somewhere it can be garbage-collected mid-flight — the work simply stops, usually with no error anywhere. The documented fix is to store tasks in a set and discard them in a done-callback, which is tedious enough that the real answer is asyncio.TaskGroup from 3.11: it holds its tasks, waits for them all at the end of the async with block, and cancels the remainder if one fails, delivering an ExceptionGroup that chapter 8's except* can pick apart. That failure behaviour is the second reason to prefer it over gather, where by default one exception propagates while the other tasks keep running unsupervised. If you do use gather, return_exceptions=True at least makes the outcomes explicit rather than partial.
  6. You pass a lambda to ProcessPoolExecutor.map and get a pickling error. Why?
    Because processes have separate memory, so everything crossing the boundary is serialised with pickle, and a lambda has no importable qualified name to pickle by reference. The same applies to nested functions, most closures, open file handles and locks. Use a module-level function, and functools.partial to bind arguments — that pickles fine. The wider point is that the process boundary is a copy, not a share: a global modified in a worker is invisible to the parent, and large arguments cost real time to serialise, transfer and deserialise, which is why process pools only pay for tasks big enough to amortise it. That cost is exactly what the one-core measurement showed — four processes were 1.04× against sequential, meaning the overhead ate the entire benefit when there was no second core to exploit.
  7. Your program prints RuntimeWarning: coroutine 'fetch' was never awaited. What did you do?
    Called an async function without awaiting it. Calling a coroutine function runs none of its body — it builds a coroutine object, exactly as calling a generator function builds a generator in chapter 9 — so the work never happens and the return value is the coroutine rather than the result. Common shapes: forgetting await on a call whose result you discard, passing a coroutine where a value was expected, or calling one inside a synchronous callback that cannot await. The warning is easy to lose in a busy log, so run tests with -W error::RuntimeWarning to turn it into a failure. Note the related case that produces no warning at all: asyncio.gather(*(fetch(u) for u in urls)) is correct because gather awaits them, while forgetting the await on gather itself leaves everything unstarted — and a type checker with async support will catch that one where the runtime will not.
