Functions

Python's argument handling is the most flexible of any mainstream language, which is a real benefit and the reason its two most famous traps exist. Both of them — the mutable default and the closure that captured the wrong value — turn out to be the same question asked twice: when is this expression evaluated?

How arguments bind

A parameter list can constrain how each argument may be passed, not only what it is called. Two markers do the work, and both look like punctuation errors until you know them.

python — the two markers
def f(a, b, /, c, d, *, e, f):
      └─────┘  │  └────┘  │  └────┘
      positional  │  either  │  keyword-only
      only        │          │
           everything BEFORE / is positional-only
                        everything AFTER * is keyword-only

# positional-only frees you to rename the parameter later without breaking callers,
# which is why most builtins use it: len(obj) has no keyword form
def clamp(value, /, lo=0, hi=1): ...

# keyword-only forces the call site to be readable. Compare:
resize(img, 800, 600, True, False)          # what are the booleans?
resize(img, 800, 600, keep_ratio=True, upscale=False)

# *args and **kwargs are just "collect the rest" — the names are convention
def log(level, *parts, **fields): ...
log("warn", "disk", "full", host="db1")     # parts=("disk","full"), fields={"host":"db1"}

# and the mirror image at the call site: * and ** UNPACK
args = (800, 600); opts = {"keep_ratio": True}
resize(img, *args, **opts)
Which call works against which signature
Try f(a, /, b) called with f(a=1, b=2)
/ makes a parameter unreachable by name
f(a=1, b=2) against def f(a, /, b) raises 'a' parameter is positional only, but was passed as a keyword. That is the point: the name becomes an implementation detail you can change.
* makes a parameter unreachable by position
f(1, 2) against def f(a, *, b) raises too many positional arguments, even though there are exactly two parameters.
*args absorbs surplus positionals; **kw does not
f(1, 2, 3) against def f(a, *args) binds args=(2, 3). The same call against def f(a, **kw) is still a TypeError — **kw only catches surplus keywords.
Defaults are filled in at bind time
f(1) against def f(a, b=2) binds a=1, b=2. Which raises the question of when that 2 was evaluated — and that is the next section.

When is it evaluated?

Python's two most-reported gotchas are usually taught as unrelated oddities. They are the same rule seen from two sides: a default is evaluated once, when the def executes; a closed-over name is looked up every time the function is called. Get that pair straight and both stop being surprises.

Evaluated at def, or at call?
Step through the mutable default, then switch to the closure
The default list is one object, created once
add("a") returns ['a'], then add("b") returns ['a', 'b']. And add("a") is add("b") is True — there is only ever one list. You can read it directly off the function: add.__defaults__ is (['a', 'b'],).
Any expression in a default is frozen at def time
Set limit = 10, define def f(n=limit), then set limit = 99. f() still returns 10. This bites with configuration read at import time and with datetime.now() as a default, which returns the time the module was loaded for ever after.
A closure looks the name up at call time
[lambda: i for i in range(5)] gives five functions that all return 4, because they share one i and read it when called — by which time the loop has finished. The functions are correct; the expectation was wrong.
Both fixes work by forcing evaluation at the other moment
lambda i=i: i makes the default do the capturing, evaluated at def time — giving [0, 1, 2, 3, 4]. functools.partial does the same thing more explicitly. The trap and the fix are the same mechanism pointed in opposite directions.
The mutable default is not always a bug

A shared object created once at def time is exactly what a memoisation cache wants — def fib(n, _cache={}): is a real idiom, though functools.cache is clearer. What makes the classic case a bug is that the caller cannot see it: the signature says bucket=[], which reads as "an empty list each time". Use None as the sentinel whenever the default is mutable and the sharing is not the point, and write the intent out: if bucket is None: bucket = []. Linters flag [], {} and set() defaults for this reason; they cannot flag datetime.now(), which has the same problem and no warning.

Scope, and the rule that catches everyone once

Name lookup walks four scopes in order — Local, Enclosing, Global, Built-in. What surprises people is that whether a name is local is decided by the compiler, statically, for the whole function.

python
count = 0

def bump():
    count += 1          # UnboundLocalError: cannot access local variable 'count'
                        # the ASSIGNMENT makes count local for the whole function,
                        # so the read on the right-hand side finds nothing

def show():
    print(count)        # fine — no assignment, so count stays global

def bump_ok():
    global count        # "this name refers to the module-level one"
    count += 1

def outer():
    total = 0
    def inner():
        nonlocal total  # "the one in the ENCLOSING function, not global"
        total += 1
    inner(); inner()
    return total        # 2

# the same rule explains this one:
def f():
    print(x)            # UnboundLocalError, not NameError — because of the line below
    x = 1
Mutating is not assigning

This is why the rule feels inconsistent. count += 1 on a global integer fails, but items.append(x) on a global list works perfectly — because append is a method call on an object the name already refers to, not a rebinding of the name. Chapter 2's model makes this exact: global and nonlocal are about which name a binding writes to, and they have nothing to say about mutating the object a name points at. If you find yourself reaching for global, the usual better answer is to return the value, or to hold the state on an object.

Functions are objects

python
def greet(name): return f"hi {name}"

greet.__name__          # 'greet'
greet.__defaults__      # the tuple of default values — inspectable, and mutable
greet.__doc__           # the docstring
greet.calls = 0         # yes, you can attach attributes to a function

handlers = {"greet": greet}          # store them
sorted(users, key=lambda u: u.age)   # pass them

# lambda is a single EXPRESSION, and that is its whole limitation.
# If you are naming one, write a def — the name is the only thing a def adds,
# and it is what appears in the traceback
f = lambda x: x * 2     # linters object, and they are right
def f(x): return x * 2  # same thing, better traceback

from functools import partial, cache
int2 = partial(int, base=2)          # fix an argument, get a new callable
int2("1011")                          # 11

@cache                                # memoise on the arguments. Chapter 10 explains the @
def fib(n): return n if n < 2 else fib(n-1) + fib(n-2)
Type hints belong on the signature

def resize(img: Image, width: int, *, keep_ratio: bool = True) -> Image: costs nothing at runtime — annotations are stored in __annotations__ and not checked — and it is the single highest-return documentation you can write, because a reader learns the contract without reading the body and a type checker can verify the callers. Chapter 11 covers the type system properly. The one runtime caveat worth knowing now: a default is still evaluated at def time whatever its annotation says, so items: list = [] is the same trap wearing a hint.

Check yourself

Self-check

  1. def add(item, bucket=[]) — what does the third call return, and why?
    ['a', 'b', 'c'], because all three calls share one list. The default expression is evaluated exactly once, when the def statement executes, and the resulting object is stored on the function — you can see it with add.__defaults__, which after two calls reads (['a', 'b'],). Every call that omits the argument gets that same object, so add("a") is add("b") is True. The fix is a sentinel: def add(item, bucket=None) and if bucket is None: bucket = [], which creates a fresh list per call. Worth knowing that the sharing is occasionally what you want — _cache={} is a real memoisation idiom — and that what makes the classic case a bug is that the signature reads as "a new empty list each time" while doing the opposite. Linters flag [] and {} defaults; they cannot flag datetime.now(), which has exactly the same problem.
  2. [lambda: i for i in range(5)] — what do the five functions return?
    All five return 4. A closure captures the variable, not the value, and looks it up when called — by which time the comprehension has finished and i is 4. The functions are behaving correctly; the expectation was wrong. Two fixes, and both work by forcing evaluation at the other moment. lambda i=i: i uses a default argument, which is evaluated at def time, so each function captures the value of i as it was — giving [0, 1, 2, 3, 4]. functools.partial(lambda i: i, i) does the same thing more explicitly and without the odd-looking parameter. Note that this is the mutable-default trap from the other side: a default is evaluated once at definition, a closed-over name is looked up on every call, and both classic gotchas fall out of that single pair of rules.
  3. You set limit = 10, write def f(n=limit), then set limit = 99. What does f() return?
    10. The default expression is evaluated when the def runs, so the function holds the value 10, not a reference to the name limit. Rebinding limit afterwards has no effect on it. This matters more than it looks in two situations. Configuration read at import time is frozen at whatever it was then, so a default of n=settings.TIMEOUT ignores anything that changes the setting later. And def log(msg, when=datetime.now()) stamps every message with the moment the module was imported, which looks correct in a short test and is obviously wrong after a day of uptime — with no warning from any linter. If the default needs to be computed per call, use None and compute it in the body.
  4. Why does count += 1 raise UnboundLocalError when count is a module-level variable?
    Because the compiler decides scope statically for the whole function. An assignment to count anywhere in the body makes count local everywhere in that function, including on lines above the assignment — so the read on the right-hand side of += looks for a local that has not been assigned yet. Note the error is UnboundLocalError rather than NameError, which tells you exactly this: the name is known to be local and simply has no value yet. Just reading count in a function with no assignment works fine, which is what makes the rule feel inconsistent. Declare global count to write to the module-level name, or nonlocal for an enclosing function's. And note the related asymmetry: items.append(x) on a global list works without any declaration, because a method call mutates the object rather than rebinding the name.
  5. What does the / in def clamp(value, /, lo=0, hi=1) do, and why would you want it?
    Everything before the / is positional-only, so clamp(value=5) raises 'value' parameter is positional only, but was passed as a keyword. The reason to want it is that a parameter name only becomes part of your public API if callers can use it — so marking it positional-only lets you rename it later without breaking anyone. That is why most builtins work this way: len(obj) has no keyword form. It also prevents a name collision with **kwargs, which is why it was added to the language in 3.8 for pure-Python functions. The mirror image is *, after which parameters are keyword-only, used to force readability at the call site — resize(img, 800, 600, True, False) tells the reader nothing, and keyword-only parameters make the second form the only one possible.
  6. def f(a, **kw) called as f(1, 2, c=3). Does it work?
    No — TypeError, because **kw only collects surplus keyword arguments and the 2 is a surplus positional one. The parameter list accepts exactly one positional argument. To absorb both you need both markers: def f(a, *args, **kw), which binds a=1, args=(2,) and kw={'c': 3}. The symmetric case is worth checking too: def f(a, *args) called as f(1, b=2) also fails, because *args does not collect keywords. The two markers are independent and each catches exactly one kind of surplus.
  7. When is a lambda the right choice over a def?
    When it is short, passed immediately as an argument, and never named — sorted(users, key=lambda u: u.age) is the canonical case, where naming the function would add a line and no information. The moment you assign one to a name, write a def instead: the two are otherwise identical, and the def gives the function a real __name__, which is what appears in tracebacks and in debugger output. A lambda assigned to f shows up as <lambda> in the stack, which is exactly the information you wanted at that moment. The other constraint is structural: a lambda body is a single expression, so it cannot contain a statement — no try, no assignment, no early return — which is a reasonable proxy for "this is too big to be a lambda anyway".
