Performance

Chapter 16 found where the time goes. This one is about what to do with that, in a strict order: the data structure, then the idiom, then leaving Python. Every figure here was measured on the machine that built the page, and one of them contradicts advice you have almost certainly been given.

5.05×, because each += builds a new string and copies everything so far. CPython has an optimisation that sometimes mutates in place, which is why this is not quadratic in practice — but it is fragile and does not apply if any other name refers to the string.
Comprehensions are barely faster than loops now
1.14×. They are worth writing for clarity, and reaching for one as a performance fix is not worth the rewrite.
And the famous one has stopped working
Hoisting m = obj.method out of a loop measured 0.95× — no gain, marginally negative. Confirmed on a 200,000-iteration loop at 0.97×. Since 3.11 the specialising interpreter caches attribute lookups inline, so the advice is obsolete.
Which is why you re-measure rather than remember

Most Python performance folklore was true when it was written and describes an interpreter that no longer exists. PEP 659's specialising adaptive interpreter, which landed in 3.11, quietly invalidated a whole category of it: hoisting attribute lookups, avoiding method calls in loops, preferring map over comprehensions for speed. Some old advice is still right — the data-structure choices, and str.join — and the only way to tell them apart is timeit on the version you actually run. Two minutes of measurement beats any amount of remembering, and the measurement is also what stops you shipping a rewrite that made the code worse.

One problem, five versions

Counting occurrences of 4,000 items drawn from 500 distinct keys — the shape of a great many real jobs. Each version produces byte-identical output, which was checked before any of the timings were taken.

The naive version drops to 910 µs — a 2.7× gap rather than 69×, because scanning a nine-element list is cheap. The right structure depends on the data, so profile with data the size of the real thing.
The order to work in

Do less work first: cache a repeated computation, avoid recomputing inside a loop, stop fetching rows you discard, break out early. Then fix the data structure, which is where the 194× and the 69× in this chapter both came from — chapter 4 is the reference. Then move the loop into C by using a built-in or a library function that does the whole job. Only then reach for idiom-level rewrites, which are worth single-digit multiples at best and cost readability. And measure between each step, because the profile changes as you go: the function that was 59% of the run may not be after you fix the first thing.

The costs nobody mentions in the benchmark

Every row above buys speed with something. A Rust or Cython extension needs a compiler in your build, wheels for every platform you support, and a second language in the review path — and it is very hard to remove once it exists. NumPy is only fast if the work stays vectorised; a Python loop over a NumPy array is slower than the same loop over a list, which is a common and demoralising discovery. PyPy has a warm-up period that makes it a poor fit for short-lived processes, and its C-extension support has always been the sticking point. Caching trades correctness risk for speed and needs an invalidation story before it needs a benchmark. The question is never just how much faster — it is how much faster, for how much permanent complexity, on a path that actually matters.

Check yourself

Self-check

  1. Why is hoisting m = obj.method out of a loop no longer worth doing?
    Because since 3.11 the specialising adaptive interpreter (PEP 659) caches the attribute lookup inline. The bytecode observes that the same type appears at the same location each time and rewrites itself into a specialised form that skips the general lookup path — which is exactly what hoisting did by hand. Measured here, the hoisted version came out at 0.95×, and on a 200,000-iteration loop at 0.97×: no gain, marginally negative, because you have added a local assignment for nothing. The broader lesson matters more than this one case. A lot of Python performance folklore was accurate against an interpreter that no longer exists, and the specialising interpreter invalidated a whole category of it at once. Some old advice survives — the data-structure choices, str.join — and timeit on the version you actually run is the only way to tell which is which.
  2. You can make one change. The data structure or the idiom?
    The data structure, and it is not close. In this chapter's measurements, swapping a list for a set in a membership test was 194×; the largest idiom-level win among five was str.join at 5.05×, and most were under 1.2×. The optimisation ladder shows the same shape from the other direction: moving from a list scan to a dict was worth 69×, and dict.get, defaultdict and Counter combined took it a further 1.8×. That is a different category of change, not a bigger one — the first fixes an O(n) lookup inside an O(n) loop, and the rest shave constants. So the working order is: do less work, then fix the structure, then push the loop into C via a built-in, then consider idioms. Reversing that order is how people spend an afternoon on a rewrite worth 4%.
  3. defaultdict measured slower than dict.get. Should you stop using it?
    No — but stop describing it as an optimisation. It came in at 414 µs against 345 µs, so it is about 20% slower here while being the more readable of the two for accumulate-into-a-collection patterns. That is a perfectly good reason to use it; it just is not a performance reason, and the distinction matters because "faster" is how the choice usually gets justified in review. The honest framing is that at this scale all three dict-based versions are within a factor of two of each other and any of them is fine, while the version they replaced was seventy times slower. Once you are in the right complexity class, pick for clarity. The exception is when the profile from chapter 16 has already told you this specific loop is the hot spot — then measure the alternatives rather than reasoning about them, because as this chapter keeps showing, the reasoning is often out of date.
  4. Your optimisation is 122× faster on test data and no faster in production. Why?
    Almost certainly the data has a different shape. The clearest illustration is in this chapter's own ladder: with 500 distinct keys the naive list scan is 27,271 µs and the dict version is 69× faster, and with only 9 distinct keys the naive version is 910 µs and the gap collapses to 2.7×. The linear scan only hurts when the list it scans is long, so a fixture with a handful of unique values hides the entire problem — or, in the reverse direction, makes a fix look transformative when production has different cardinality. Other common mismatches: the test data fits in cache and the real data does not; the hot path in production is I/O-bound and no amount of CPU work helps; the real workload is concurrent and contends for something your benchmark had to itself. The remedy is the same in every case, which is to profile against something the size and shape of the real thing.
  5. When is NumPy the wrong answer?
    When the work will not stay vectorised. NumPy is fast because a single operation on a whole array runs one C loop over contiguous memory; a Python for loop over a NumPy array is slower than the same loop over a list, because every element access has to box a scalar into a Python object. So code that reads element by element, branches per element, or calls back into Python gets the overhead and none of the benefit. It is also the wrong answer for small arrays, where the per-call overhead dominates, and for heterogeneous or ragged data that does not fit a rectangular typed array at all. The general form of the question applies to every row of the table above: each option buys speed with permanent complexity — a compiler in your build, wheels per platform, a second language in review, a cache-invalidation story — so the decision is how much faster, for how much complexity, on a path that the profile says matters.
  6. Why does Counter beat a hand-written dict loop?
    Because the loop itself runs in C. Counter(text) measured 223 µs against 345 µs for the tightest Python loop, and the difference is not a cleverer algorithm — both are a single pass building a hash map. It is that the Python version pays interpreter overhead per element: fetch the next item, look up the name, dispatch the operation, store the result. Counter's fast path hands the whole iterable to C and pays that overhead once. This generalises into the most reliable optimisation available in the language: if a built-in or standard-library function does the entire loop for you, it will beat the loop you write, and it is usually shorter too. sum, min, max, any, all, sorted, str.join, Counter, itertools and the bytes methods are all cases of this, and reaching for them is the one optimisation that costs no readability.
  7. What should you measure, and with what?
    Use the profiler to find where and timeit to measure how much, because they are bad at each other's jobs. cProfile adds per-call overhead, so it exaggerates functions called very often and can point at the wrong one — but it is the only thing that shows you the shape of the whole program. timeit runs a statement many times and reports the minimum of several repeats, which is the right statistic for a microbenchmark because it filters out scheduler noise, and it is useless for finding a hot spot you have not guessed. Three habits that prevent wasted work: measure before and after every change rather than at the end, so you know which one helped; check the ceiling with Amdahl's law before starting, since a 15% function caps at 1.18×; and keep a correctness check alongside the benchmark — every timing in this chapter was taken only after verifying all five versions produce identical output.
