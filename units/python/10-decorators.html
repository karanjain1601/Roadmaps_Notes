Decorators and descriptors

A decorator looks like special syntax and is not: @d above a def means f = d(f), using chapter 5's closures and nothing else. Descriptors are the other half of the same story — the mechanism property, classmethod and every method you have ever called are built on.

— words— min read2 interactivesNeeds: chapters 05, 07

What decoration replaces

python — the syntax is the only new part
def timed(fn):                        # takes a function…
    def wrapper(*args, **kwargs):     # …and closes over it (chapter 5)
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:                       # chapter 8: runs even if fn raises
            print(f"{fn.__name__} took {time.perf_counter() - t0:.3f}s")
    return wrapper                     # …and returns a replacement

@timed
def load(path): ...

# is EXACTLY this, and nothing more:
def load(path): ...
load = timed(load)

That last line is the whole feature. The name load now refers to wrapper — a different object, with different metadata — and everything confusing about decorators follows from that substitution being invisible at the call site.

What the decorator did to your function
Compare "no wraps" with "functools.wraps"
Without wraps, four things are lost
__name__ becomes "wrapper", __doc__ becomes None, the signature reads (*a, **k), and there is no way back to the original. Tracebacks, help(), API documentation generators and anything dispatching on the name all see the wrapper.
functools.wraps restores all four
__name__ is base again, the docstring is back, and inspect.signature recovers (x: int, y: str = 'd') -> bool. It does that last one by setting __wrapped__, which inspect knows to follow.
Identity is not restored, and should not be
decorated is base is False — it is a different object doing different work. But decorated.__wrapped__ is base is True, which is how a test can reach the undecorated function to call it without the caching, retrying or logging.
So @wraps is not optional politeness
It is the line that keeps a decorated function introspectable. Any decorator without it degrades every tool that reads function metadata, and the failure appears far away — a framework that routes on __name__ suddenly seeing five endpoints all called wrapper.

Decorators that take arguments

A decorator taking arguments is one more layer: a function that returns a decorator, which returns a wrapper. The reason is mechanical — @retry(3) means f = retry(3)(f), so retry(3) must evaluate to something that can decorate.

python — three levels, and how to avoid needing them
import functools, time

def retry(attempts=3, delay=0.5, on=(OSError,)):
    def decorator(fn):                                # ← this is the actual decorator
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for n in range(1, attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except on as e:                        # chapter 8: catch narrowly
                    if n == attempts:
                        raise
                    time.sleep(delay * 2 ** (n - 1))   # back off
        return wrapper
    return decorator

@retry(attempts=5, on=(TimeoutError,))
def fetch(url): ...

# the three-level nesting is why decorators feel hard. A class avoids it,
# at the cost of having to implement __call__ and handle methods yourself:
class Retry:
    def __init__(self, attempts=3): self.attempts = attempts
    def __call__(self, fn):
        @functools.wraps(fn)
        def wrapper(*a, **k): ...
        return wrapper

# and the ones you should reach for before writing your own:
@functools.cache                 # memoise. Unbounded — see the warning below
@functools.lru_cache(maxsize=1024)
@functools.singledispatch        # dispatch on the first argument's type
@contextlib.contextmanager       # a generator becomes a `with` block
@dataclasses.dataclass           # chapter 7
@cache on a method leaks memory for the life of the process

The cache lives on the function, which is a class attribute shared by every instance — and its keys include self. So every instance ever passed in is held by a strong reference in a dictionary that is never trimmed, and none of them can be garbage-collected. The object looks like it is being freed and the memory graph says otherwise. Use functools.cached_property for a per-instance computed value, which stores the result in the instance's own __dict__ and dies with it. If you genuinely want a cache keyed on arguments across instances, make it a module-level function and pass what it needs, or use lru_cache(maxsize=...) and accept that self is part of the key.

Two orders, and they are opposite

Stacked decorators are applied bottom-up and entered top-down. Both follow from the same nesting, and confusing them is the usual reason a stack behaves unexpectedly.

@A over @B over @C
Step through definition, then through the call
Applied C, B, A — bottom-up
Because @A @B @C def f means f = A(B(C(f))) and the innermost call is evaluated first. Anything a decorator does at decoration time — registering a route, validating a signature, printing — happens in this order.
Entered A, B, C — top-down
Because A's wrapper ended up outermost, so it is the one the caller reaches first. Anything a decorator does per call — timing, caching, authentication — happens in this order, and the reverse on the way out.
Which is why order changes behaviour
@cache above @timed measures only the misses, because the cache short-circuits before the timer is reached. @timed above @cache measures every call including the hits. Neither is wrong; they answer different questions.
And why @staticmethod goes on top
It must be the outermost, because it produces a descriptor rather than a function and most decorators expect a plain callable. Putting it underneath was a TypeError before 3.10 and merely confusing since.

Descriptors: what a method really is

Chapter 7 noted that a property beats the instance dictionary because it is a data descriptor. Here is the mechanism, and the reason it explains something you use constantly without noticing.

python — the protocol, and the thing it explains
class Positive:
    def __set_name__(self, owner, name):      # 3.6+: told its own attribute name
        self.attr = "_" + name

    def __get__(self, obj, objtype=None):     # obj is None on class access
        if obj is None: return self
        return getattr(obj, self.attr)

    def __set__(self, obj, value):            # defining __set__ makes it a DATA descriptor,
        if value <= 0:                        # which beats the instance __dict__
            raise ValueError(f"must be positive, got {value}")
        setattr(obj, self.attr, value)

class Order:
    quantity = Positive()                      # validation, reusable across classes
    price = Positive()

# ─────────────────────────────────────────────────────────────────
# and now the thing you use every day. A plain function is a NON-data
# descriptor: it defines __get__ and not __set__.

class C:
    def method(self): ...

C.method            # the plain function
C().method          # a BOUND METHOD — created by function.__get__(instance)

# that is where `self` comes from. The dot triggers __get__, which returns an
# object pairing the function with the instance. `property`, `classmethod` and
# `staticmethod` are all descriptors too — none of them is special syntax
DefinesPriorityExamples
Data descriptor__set__ or __delete__Beats the instance __dict__property, a validator like the one above
Non-data descriptorOnly __get__Loses to the instance __dict__Functions, staticmethod, classmethod, cached_property
Why cached_property is a non-data descriptor on purpose

It computes the value on first access and writes it into the instance's __dict__. Because it is a non-data descriptor, the instance dictionary wins from then on — so every subsequent access skips the descriptor entirely and costs an ordinary attribute lookup. If it defined __set__ it would win every time and the caching would be pointless. That single design choice is the whole implementation, and it is a good demonstration that the data/non-data distinction is a feature rather than an accident. It also explains the limitation: cached_property does not work on a class using __slots__, because there is no __dict__ to write into.

Check yourself

Self-check

  1. Your web framework now shows five endpoints all named wrapper. What happened?
    A decorator was written without functools.wraps. @d above a def means f = d(f), so the name now refers to the wrapper function — a different object with its own metadata. __name__ becomes "wrapper", __doc__ becomes None, and inspect.signature reports (*a, **k). Anything reading function metadata sees the wrapper: tracebacks, help(), documentation generators, and frameworks that route or register on __name__. Adding @functools.wraps(fn) to the wrapper copies the name, docstring, module and annotations across, and sets __wrapped__ to the original — which is what lets inspect.signature see through the wrapper and recover the real signature. It is not politeness; it is the line that keeps a decorated function introspectable, and the failure it prevents always appears somewhere far from the decorator.
  2. @A @B @C def f. In what order do the decorators run, and in what order do the wrappers run?
    Opposite orders, and both follow from the same nesting. The stack means f = A(B(C(f))), so at definition the innermost is evaluated first: C, B, A — bottom-up. Anything a decorator does at decoration time, such as registering a route or validating a signature, happens in that order. But the result is that A's wrapper is outermost, so a call reaches A, then B, then C, then the body — top-down, and the reverse on the way back out. Anything per-call, such as timing or caching or authentication, happens in that order. This is why order changes behaviour rather than just style: @cache above @timed times only the misses, because the cache returns before the timer is reached, while @timed above @cache times every call including hits.
  3. Why does a decorator taking arguments need three levels of nesting?
    Because the syntax forces it. @retry(3) above a def means f = retry(3)(f) — so retry(3) is evaluated first and whatever it returns must itself be capable of decorating f. That gives you three functions: the outer one taking the configuration, the middle one taking the function, and the inner wrapper taking the call's arguments. Each level closes over the level above, which is chapter 5's closures doing all the work. Two ways to reduce the pain: write the decorator as a class with __init__ and __call__, which flattens it to two levels at the cost of having to handle the descriptor protocol yourself if it is used on methods; or use functools.partial to support both @retry and @retry(attempts=5), which is a common convenience and worth doing when the arguments all have defaults.
  4. Why does @cache on a method leak memory?
    Because the cache is attached to the function, which is a class attribute shared by every instance, and the cache key includes self. So every instance ever passed to the method is held by a strong reference in a dictionary that is never trimmed — functools.cache is unbounded by definition — and none of them can be collected. Nothing in the code looks like it retains anything, and the object appears to go out of scope normally. The fix depends on what you wanted. For a value computed once per instance, use functools.cached_property, which stores the result in the instance's own __dict__ and therefore dies with the instance. For a genuine argument-keyed cache shared across instances, make it a module-level function taking only the values it needs. And if you must cache a method, lru_cache(maxsize=N) at least bounds the damage — though self is still part of the key and still held.
  5. What is a bound method, mechanically?
    The result of the descriptor protocol running on a plain function. A function defines __get__, which makes it a non-data descriptor; when you write obj.method, the attribute lookup finds the function on the class, sees that it is a descriptor, and calls its __get__ with the instance — which returns a bound-method object pairing the function with obj. Calling that object inserts obj as the first argument. So self is not special syntax and not a keyword: it is the first parameter, and the dot is what supplies it. Two consequences worth holding onto. C.method gives you the plain function, so C.method(instance) is exactly equivalent to instance.method(). And because a function is a non-data descriptor, you can shadow a method by assigning to it on an instance — obj.method = something puts it in the instance dictionary, which wins.
  6. Why is cached_property a non-data descriptor rather than a data one?
    Because that is what makes the caching work. On first access the descriptor computes the value and writes it into the instance's __dict__. A non-data descriptor loses to the instance dictionary, so every subsequent access finds the stored value and never reaches the descriptor at all — the cache costs one ordinary attribute lookup after the first call. If it defined __set__ it would be a data descriptor, would win on every access, and the stored value would be permanently ignored. That one design choice is essentially the whole implementation. It also explains the documented limitation: a class using __slots__ has no __dict__ to write into, so cached_property raises. The contrast with property is instructive — property is a data descriptor precisely so that a computed attribute cannot be accidentally overwritten, which chapter 7 showed from the lookup side.
  7. When should you write a decorator rather than just calling a function?
    When the behaviour is genuinely cross-cutting and you want it applied uniformly and visibly at the definition site — retrying, caching, timing, authentication, registration, logging entry and exit. The value is that the concern is declared where the function is defined rather than repeated at every call site, and that it can be removed by deleting one line. Where they cost more than they give: when the wrapper changes the signature or the return type, so callers cannot tell what they are calling; when several stack up and the resulting order matters but is not obvious; and when the behaviour needs configuration per call rather than per definition, where an argument or a context manager is clearer. The practical test is whether a reader who has not seen the decorator can still predict what the function does — @retry(3) passes that easily and @transform does not.
