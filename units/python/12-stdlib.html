The standard library

Two hundred modules ship with Python and about thirty are worth knowing by name. This chapter maps those, and then goes carefully through the two that are most often used incorrectly — datetime, where the arithmetic is not what it looks like, and json, where a round trip quietly changes your data.

python — pathlib, which replaces most of os.path
from pathlib import Path

p = Path("data") / "raw" / "events.jsonl"     / is the join operator, and it is
                                               platform-correct without thinking
p.stem, p.suffix, p.parent, p.name             # 'events', '.jsonl', Path('data/raw'), …
p.exists(), p.is_file(), p.stat().st_size
p.read_text(encoding="utf-8")                  # always pass encoding — see below
p.with_suffix(".gz")
p.parent.mkdir(parents=True, exist_ok=True)    # the idiom, and exist_ok avoids a race

for f in Path("logs").rglob("*.log"): ...      # recursive, lazy (chapter 9)

# and the one that catches people: Path is not a str, so an API expecting a str
# may reject it. Most of the stdlib accepts it; some third-party code does not
open(p)          # fine — anything using os.fspath works
"prefix" + p     # TypeError. Use str(p) or an f-string
Always pass encoding

open(p) and read_text() use the platform default, which on Windows has historically been the system code page rather than UTF-8. So code that works on your machine mangles non-ASCII characters on someone else's, and the failure appears as corrupted text or a UnicodeDecodeError in a place unrelated to the file. Pass encoding="utf-8" every single time. Python 3.15 will change the default to UTF-8, and until then -X warn_default_encoding or the PYTHONWARNDEFAULTENCODING environment variable will show you every call site that has not been fixed.

datetime, and the arithmetic that is not arithmetic

Adding a timedelta to a timezone-aware datetime does wall-clock arithmetic, not elapsed-time arithmetic. Most of the year the two agree, which is exactly what makes the disagreement expensive.

Three hours later, twice
Compare the elapsed times — the field values both advanced by three
Three hours added, two hours elapsed
From 2024-03-30T23:30+00:00, adding timedelta(hours=3) gives 2024-03-31T02:30+01:00 — the fields advanced by three, and only 2:00:00 of real time passed, because 01:00 to 02:00 never existed. Converting to UTC first, adding, and converting back gives 03:30+01:00 and exactly 3:00:00.
The autumn version is worse, because both answers are valid
01:30 on 27 October occurs twice. fold=0 maps to 00:30 UTC and fold=1 to 01:30 UTC — and the two datetimes compare equal to each other while representing instants an hour apart. Sorting by local time silently interleaves them.
Naive and aware refuse to mix
Subtracting one from the other raises TypeError. That is the one place Python protects you; everywhere else a naive datetime is silently assumed to be local time, by whoever happens to interpret it.
So: store UTC, do arithmetic in UTC, convert for display
datetime.now(timezone.utc) rather than the deprecated utcnow(), which returned a naive datetime holding UTC — the worst of both, and the source of a great many bugs.
When wall-clock arithmetic is the correct answer

"Every morning at 09:00" means 09:00 local, whatever the offset — so a daily alarm genuinely wants the wall-clock behaviour, and converting to UTC would drift by an hour twice a year. "Retry in three hours" means three hours of elapsed time and wants UTC. The rule is to decide which one you mean and be explicit: schedule recurring local events by storing a local time plus a zone name and recomputing, and do durations in UTC. What you must not do is store an offset — +01:00 — and expect it to remain correct, because a zone's offset is a function of the date, which is why zoneinfo takes a name like Europe/London rather than a number.

What survives a JSON round trip

json.loads(json.dumps(x)) == x?
Three different ways for this to go wrong
Silent type changes
A tuple comes back a list. Integer dict keys come back as strings — {1: 'a'} becomes {"1": "a"} — and so does None, which becomes the key "null". No error, no warning, and == against the original is False.
Loud refusals
A set, a date and bytes all raise TypeError: Object of type X is not JSON serializable. These are the good ones: you find out immediately, and the fix is a default= function or a schema library.
Output that is not valid JSON
json.dumps(float('nan')) emits the bare token NaN, and inf emits Infinity. Python's own loads accepts them; the JSON specification does not, and a strict parser at the other end rejects the whole document. allow_nan=False turns it into a ValueError at your end instead, which is where you want it.
And one that survives here and breaks elsewhere
2**70 round-trips through Python perfectly. JSON has a single number type and JavaScript parses it as a double, so a consumer silently loses precision above 2⁵³. Serialise large integers as strings if anything outside Python will read them.
Never unpickle anything you did not create

pickle handles all the types JSON refuses, which makes it tempting as a cache or a message format. It is also a code-execution format: unpickling constructs arbitrary objects by calling arbitrary callables, so a malicious payload runs code with your process's privileges before you can inspect it. There is no safe mode and no validation step that helps. Use it only for data your own process wrote and can trust — a local cache — and for anything crossing a boundary use JSON with an explicit schema, or a binary format designed for the job such as msgpack or protobuf. The same applies to yaml.load without SafeLoader, for exactly the same reason.

Check yourself

Self-check

  1. You add timedelta(hours=3) to an aware datetime and three hours do not pass. How?
    Adding a timedelta to an aware datetime does wall-clock arithmetic: it advances the field values and then re-derives the offset for the new local time. Starting at 2024-03-30T23:30+00:00 in London and adding three hours gives 2024-03-31T02:30+01:00 — the fields moved by three, and only two hours of real time elapsed, because the hour from 01:00 to 02:00 did not exist that night. To get elapsed-time arithmetic, convert to UTC, add, and convert back: that gives 03:30+01:00 and exactly three hours. Most of the year both approaches agree, which is what makes the disagreement expensive — it appears twice a year, in production, in a scheduler nobody has looked at since. The rule is to store and compute in UTC and convert only for display.
  2. Two datetimes both read 01:30 on 27 October and compare equal. Are they the same instant?
    No. The clocks went back that morning, so 01:30 local occurred twice — once at 00:30 UTC and again an hour later at 01:30 UTC. The fold attribute distinguishes them: fold=0 is the first occurrence and fold=1 the second. But fold is deliberately excluded from equality comparison for backwards compatibility, so the two datetimes compare equal to each other while astimezone(utc) shows they are an hour apart. The practical consequences are nasty and quiet: sorting events by local time interleaves that hour arbitrarily, deduplicating by timestamp merges distinct events, and a "between these two times" query returns the wrong set. The fix is the same as the previous answer — store UTC, where the ambiguity does not exist at all.
  3. What is wrong with datetime.utcnow()?
    It returns a naive datetime whose fields happen to hold UTC — so it carries no timezone information while looking authoritative. Anything that later interprets it assumes local time, because that is what a naive datetime means by convention, so a UTC value gets treated as local and shifted by the offset. It also cannot be compared or subtracted against a correctly aware datetime, which raises TypeError — the one place Python does protect you. Use datetime.now(timezone.utc), which is aware and unambiguous; utcnow() and utcfromtimestamp() are deprecated since 3.12 for exactly this reason. The general rule follows: a datetime crossing any boundary — a database, an API, a log, another function — should be aware, and naive datetimes should exist only briefly and locally where you have just parsed one and are about to attach a zone.
  4. Your API sends {1: "a"} as JSON and the consumer reports a key of "1". Bug or not?
    Not a bug — JSON object keys are strings by definition, so json.dumps coerces yours and loads has no way to know they were ever integers. The round trip is therefore lossy and silent: json.loads(json.dumps({1: "a"})) == {1: "a"} is False with no error anywhere. The same coercion applies to None, which becomes the key "null", and to True, which becomes "true" — and if a dict happens to contain both 1 and "1", one silently overwrites the other. Either use string keys deliberately so the round trip is exact, or restructure as a list of objects with an explicit id field, which is usually clearer for a consumer anyway. json.dumps(..., sort_keys=True) helps with reproducibility but does nothing about this.
  5. A downstream service rejects your JSON as malformed and you cannot reproduce it locally. What might it be?
    A NaN or an infinity in the payload. json.dumps emits the bare tokens NaN, Infinity and -Infinity, which are not in the JSON specification — Python's own loads accepts them, so a Python-to-Python round trip works perfectly and you cannot reproduce the failure, while a strict parser in another language rejects the entire document. The fix is json.dumps(data, allow_nan=False), which raises ValueError at your end where the bad value can be traced, rather than producing output that fails somewhere else. Worth checking the neighbouring case at the same time: a Python integer larger than 2⁵³ round-trips exactly through Python and silently loses precision in a JavaScript consumer, because JSON has one number type and JS parses it as a double. Serialise large integers as strings if anything outside Python will read them.
  6. Why should pickle never touch data from outside your process?
    Because unpickling is not parsing, it is execution. The format contains instructions to construct objects by calling callables, so a crafted payload can run arbitrary code with your process's privileges — before you have any opportunity to inspect what arrived. There is no safe mode, no validation step and no subset of the format that avoids it; the design assumes the data is trusted. So it is fine for something your own process wrote and will read back, such as a local cache, and unacceptable for a message queue, an upload, a cookie or anything crossing a network. For those, use JSON with an explicit schema, or a binary format designed for untrusted input such as msgpack or protobuf. The identical warning applies to yaml.load without SafeLoader, which can instantiate arbitrary Python objects for the same reason.
  7. Why does the encoding argument to open() matter when your code works fine?
    Because "fine" means "on your machine". Without an explicit encoding, Python uses the platform default, which on Linux and macOS is usually UTF-8 and on Windows has historically been the system code page — so the same code reading the same file produces different text on a colleague's machine or in a container with a different locale. The failure is either a UnicodeDecodeError in a place unrelated to the file, or worse, silently mangled characters that propagate into a database. Pass encoding="utf-8" on every open and read_text, without exception. Python 3.15 makes UTF-8 the default, and until then you can find every unfixed call site by running with -X warn_default_encoding or setting PYTHONWARNDEFAULTENCODING=1, which is worth doing once across a codebase.
