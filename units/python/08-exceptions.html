Errors and exceptions

Python uses exceptions for ordinary control flow, not only for disasters — a for loop ends on one. That makes catching them a design decision rather than damage control, and it makes two details worth knowing precisely: exactly which block runs on which path, and what the hierarchy you are catching actually contains.

Which block runs, and when

Four clauses, and the two people skip are the two worth having. else runs only when nothing was raised; finally runs on every path, including the one where an exception is on its way out.

try / except / else / finally
Compare the last two — a return in finally changes the outcome
else is the "nothing went wrong" block
It runs after try only when no exception was raised, and it exists so the try can hold just the line that might fail. That matters: a wide try can catch an exception from code you never meant to guard, and else is how you keep the guarded region narrow without giving up the follow-on logic.
finally runs on every path
Including when the exception is uncaught and about to propagate — the sequence is try, finally, then the exception reaches the caller. Including on a return from try: the return value is computed, then finally runs, then the function actually returns.
A return inside finally discards the exception
Completely and silently. The ValueError never reaches the caller and the function returns normally. There is no warning, and nothing in the traceback, because there is no traceback.
And it overrides a return from try
The try block said "from try"; the caller received "from finally". The same applies to break and continue inside finally. Treat any control-flow statement in a finally block as a bug unless you can explain exactly this.
Prefer with to finally

Most finally blocks exist to release something, and a context manager does that better: the cleanup lives next to the acquisition rather than at the far end of the function, it cannot be forgotten by an early return, and it is reusable. with open(p) as f: rather than f = open(p) and a finally: f.close(). Write your own with @contextlib.contextmanager — a generator that yields once, with the cleanup after the yield in its own finally. contextlib.suppress(FileNotFoundError) is the readable form of a try/except/pass, and ExitStack handles a variable number of resources.

What you are actually catching

Exceptions form a class hierarchy, and an except clause catches its class and every subclass. Two things about the shape of that hierarchy matter in practice.

Which clause catches which exception
Look at the KeyboardInterrupt row under except Exception
except Exception does not catch KeyboardInterrupt
Nor SystemExit, nor GeneratorExit. All three derive from BaseException directly, above Exception, precisely so that a broad handler in a retry loop cannot swallow your Ctrl-C or a sys.exit(). That is a feature, and it is the reason to write except Exception rather than a bare except:.
The intermediate classes are the useful ones
LookupError covers KeyError and IndexError. ArithmeticError covers ZeroDivisionError, OverflowError and FloatingPointError. OSError absorbed the old IOError, socket.error and friends in 3.3, and its subclasses — FileNotFoundError, PermissionError, TimeoutError — replaced the errno checks people used to write.
Clause order matters and nothing warns you
The first matching clause wins, so except Exception: written above except KeyError: silently makes the second unreachable. Specific first, general last.
A bare except: catches BaseException
Which means it catches Ctrl-C and turns your program into something that cannot be stopped normally. There is essentially never a reason to write it; except Exception: says the same thing without that.

try:
    config = json.loads(raw)
except json.JSONDecodeError as e:
    raise ConfigError(f"{path} is not valid JSON") from e
    #                                            ^^^^^^
    # sets __cause__ AND __suppress_context__ = True, which is what changes
    # the traceback wording to "The above exception was the direct cause of…"

# raising inside an except block WITHOUT `from` still keeps the original:
#   __context__ is set automatically, and you get
#   "During handling of the above exception, another exception occurred"
# which reads like a bug report, because usually it is one

raise ConfigError(...) from None    # hides the original in the traceback,
                                    # but keeps __context__ for a debugger

# 3.11+: several failures at once, from concurrent work or a batch
raise ExceptionGroup("import failed", [ValueError("row 3"), KeyError("row 9")])

try:
    process_batch()
except* ValueError as eg:           # except* handles the matching SUBSET
    log(eg.exceptions)               # and lets the rest keep propagating

# 3.11+: add context to an exception in flight without replacing it
try:
    parse(row)
except ValueError as e:
    e.add_note(f"while parsing row {n}")
    raise

Designing exceptions worth catching

Ask forgiveness, not permission
try: return d["k"] except KeyError: beats if "k" in d: for two reasons. It is faster when the key is usually present, since the check costs nothing on the happy path. And it has no race: between the check and the use, another thread — or the filesystem — can change the answer, which is why os.path.exists followed by open is a genuine bug and try: open(...) except FileNotFoundError: is not.
Catch narrowly, at the level that can act
A handler that cannot do anything useful should not exist. Most code should let exceptions pass and let one place near the top decide — log it, return a 500, retry, show a message. Catching in the middle to log and re-raise produces the same error logged five times.
Give the library one base class
class ConfigError(Exception) with everything specific inheriting from it lets a caller write except ConfigError and be sure they have covered you, whatever you add later. Deriving from the closest built-in as well — class ConfigKeyError(ConfigError, KeyError) — lets existing generic handlers keep working.
Put the values in the message
ValueError("port must be 1–65535, got 70000") against ValueError("invalid port"). The first is debuggable from a log line alone; the second sends someone to the source. This is the cheapest quality improvement available in any codebase.
Three ways to lose an error entirely

except Exception: pass discards the exception and everything about it. If you genuinely want to ignore a specific failure, say so: contextlib.suppress(FileNotFoundError) names exactly what is being ignored and cannot expand to cover something you did not intend.

except Exception: raise MyError("failed") without from e keeps the original in __context__, so it does appear — under "During handling of the above exception, another exception occurred", which reads like a bug in your handler. Use from e to say the relationship was deliberate.

And return inside finally, from the first demo, which discards the in-flight exception with no trace at all. The first two are visible in review; the third looks like tidy cleanup code.

Check yourself

Self-check

  1. A function raises ValueError inside try, and the finally block contains return "ok". What does the caller see?
    "ok", and no exception at all. A return executed in a finally block discards whatever was in flight — the ValueError never reaches the caller, there is no traceback, and nothing is logged. It also overrides a return from the try block: if try returned "from try" and finally returned "from finally", the caller gets the second. The same applies to break and continue inside finally. Treat any control-flow statement in a finally as a bug unless you can explain precisely this behaviour, because the code looks like ordinary cleanup and the failure mode is a silently swallowed error. Most finally blocks are better written as a context manager anyway, which puts the cleanup next to the acquisition and removes the temptation.
  2. Why does except Exception not catch KeyboardInterrupt?
    Because KeyboardInterrupt derives from BaseException directly, one level above Exception, and so do SystemExit and GeneratorExit. The hierarchy is shaped that way deliberately: a broad except Exception in a retry loop or a worker thread should not be able to swallow your Ctrl-C or a sys.exit(), because a program you cannot stop is worse than one that crashes. This is the concrete reason to prefer except Exception: over a bare except: — the bare form catches BaseException and does exactly what the hierarchy was designed to prevent. The narrow legitimate use of catching BaseException is a top-level handler that needs to run cleanup on shutdown, and it should re-raise afterwards.
  3. What is the else clause on a try for?
    It runs after try only if no exception was raised, and its purpose is to keep the guarded region narrow. Without it you either put the follow-on code inside the try — where an unrelated exception from it will be caught by your handler, which is a real and common bug — or after the whole statement, where it also runs when the exception was caught. else is the block that means "the risky bit worked, now do the rest, and do not guard the rest". So try: row = fetch() / except NotFound: return None / else: return transform(row), where a NotFound raised by transform is genuinely different from one raised by fetch and should not be swallowed. The same clause exists on for and while, meaning "no break" — on try the word is a better fit.
  4. Your handler raises a new exception. What is the difference between doing it with and without from e?
    Both keep the original — an exception raised inside an except block automatically gets the one being handled as its __context__. The difference is what the traceback says and what you are claiming. Without from, you get "During handling of the above exception, another exception occurred", which reads as though your handler itself failed unexpectedly — and often it means exactly that. With from e, Python sets __cause__ as well and flips __suppress_context__ to True, which changes the wording to "The above exception was the direct cause of the following exception" — a deliberate translation from a low-level failure to a domain-level one. Use from e whenever the new exception is a translation of the old, which is nearly always. from None suppresses the display entirely while keeping __context__ for a debugger, which is right when the internal detail would only mislead a caller.
  5. Which is better, if key in d: or try: d[key] except KeyError:?
    The try form, in most cases, for two reasons. Performance: setting up a try costs essentially nothing when no exception occurs, so the happy path is cheaper than a membership test plus a lookup — and the exception only costs when the key is genuinely missing, which by assumption is rare. Correctness: the check-then-use form has a race, because anything can change between the two operations. That is mostly theoretical for a local dict and entirely real for a filesystem, which is why os.path.exists(p) followed by open(p) is a genuine bug and try: open(p) except FileNotFoundError: is not. The exception is when the failure is common rather than exceptional — a lookup that misses half the time is better served by d.get(key), which avoids both the test and the exception.
  6. Why does clause order matter, given that Python does not warn about it?
    Because the first matching clause wins, and matching means "is an instance of". So except Exception: written above except KeyError: catches the KeyError and the second clause becomes unreachable — with no error, no warning, and no visible symptom other than the specific handling never happening. Write clauses from most specific to most general. The same reasoning applies to your own hierarchy: if ConfigKeyError inherits from ConfigError, the specific one has to come first. It is worth noting the related surprise: catching a tuple, except (ValueError, TypeError):, matches either, but except ValueError, TypeError: was Python 2 syntax for binding the exception to a name and is a syntax error now — one of the few places where the 2-to-3 change removed a real footgun.
  7. When should a library define its own exception classes?
    Whenever callers might want to distinguish your failures from anyone else's, which is nearly always. Define one base — class ConfigError(Exception) — and derive everything specific from it, so a caller can write except ConfigError and be certain they have covered your library including whatever you add in a later version. Where a built-in genuinely describes the failure, inherit from both: class ConfigKeyError(ConfigError, KeyError) means existing generic handlers keep working while callers who care can be specific. What to avoid is raising bare Exception, which forces every caller into except Exception and therefore into catching everything, and raising a built-in for a domain failure, which makes your errors indistinguishable from a genuine bug in the caller's own code. And put the values in the message — "port must be 1–65535, got 70000" is debuggable from a log line, "invalid port" is not.
