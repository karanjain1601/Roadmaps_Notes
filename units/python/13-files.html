Files, text and encodings

A str is a sequence of code points and a bytes is a sequence of bytes, and the only way between them is an encoding you name. Python 3 made that boundary explicit, which is why the errors are loud — except for the one case where they are silent, and that case is the reason this chapter exists.

— words— min read2 interactivesNeeds: chapters 02, 12

Two types, one boundary

python
s = "café"              str  — a sequence of CODE POINTS. No encoding. Not bytes
b = s.encode("utf-8")   bytes — b'caf\xc3\xa9'. Now it has an encoding
b.decode("utf-8")       # back to 'café'

# they do not mix, and that is the design:
"a" + b"b"              # TypeError — Python 2 allowed this, and it was the bug
len(s), len(b)          # 4 and 5. Different questions, different answers

# open() in text mode decodes for you; binary mode does not
open(p, encoding="utf-8").read()   # str  — decoded on the way in
open(p, "rb").read()               # bytes — exactly what is on disk

# the rule that makes all of this manageable:
#   decode at the boundary, work in str, encode on the way out.
#   bytes should exist only where you are actually talking to a socket,
#   a file handle or a wire protocol
The same string, different encodings
Encode as utf-8, then read it back as latin-1
Encoding fails loudly when it cannot represent something
"café".encode("ascii") raises UnicodeEncodeError. ascii covers 128 code points, latin-1 covers 256, and utf-8 covers everything — at a variable width: ASCII is one byte, é is two, 日 is three, 👍 is four.
Decoding as latin-1 never fails, which is the problem
It maps all 256 byte values to code points, so any byte sequence decodes to something. b'caf\xc3\xa9' read as latin-1 gives 'cafÃ©' — no exception, no warning, corrupted text that flows into your database. A wrong encoding that raises is a good day.
The error handlers are not equivalent
ignore deletes the character with no record — b'caf 10'. replace substitutes ?, which at least marks the loss. backslashreplace gives b'caf\\xe9 \\u20ac10' and is the only one that is reversible. strict is the default and almost always right.
Except for filenames, where surrogateescape exists
A filesystem can hold a name that is not valid UTF-8. surrogateescape smuggles the undecodable bytes into reserved code points so that b'file\xff.txt' decodes and re-encodes to exactly the same bytes. That is how os.listdir() can hand you a broken name without losing it.

How long is a string?

Four defensible answers, and len() gives one of them. Which one you need depends on the question, and the mismatch is where the bugs live.

Four ways to measure the same text
Compare the two cafés, then look at the family emoji
Two identical-looking cafés with different lengths
"caf\u00e9" is 4 code points; "cafe\u0301" — e plus a combining acute — is 5. They render identically, they are not equal, and neither is wrong. unicodedata.normalize("NFC", s) on both before comparing is what makes the comparison mean anything.
Python counts code points; JavaScript counts UTF-16 units
"👍" is 1 in Python and 2 in JavaScript, because it is outside the Basic Multilingual Plane and needs a surrogate pair. Neither language is wrong — a length limit enforced in one and validated in the other will disagree.
And a user counts neither
"👨‍👩‍👧" is one thing on screen, 5 code points — three people joined by two zero-width joiners — and 18 UTF-8 bytes. len() counts none of the three things a person means by "how long".
Which is why slicing by index cuts emoji in half
family[:2] gives '👨\u200d' — one person and a dangling joiner. For anything user-facing you need grapheme clusters, which the standard library does not provide; the regex module's \X or the grapheme package does.
A VARCHAR(20) that rejects a 15-character name

The classic shape of this bug. The form validates len(name) <= 20 in Python — code points. The database column counts bytes, or UTF-16 units, or characters depending on the engine and the collation. So a name with accents or emoji passes validation and is truncated or rejected on insert, and the error message is about the database rather than the input. Decide which unit the limit is in, enforce it in that unit everywhere, and normalise to NFC first so the composed and decomposed forms of the same name do not disagree by three. The same reasoning applies to a Twitter-style character count, a filename length limit, and any protocol field with a declared size.

Files, modes and newlines

python
from pathlib import Path

Path(p).read_text(encoding="utf-8")             # small files, whole thing
with open(p, encoding="utf-8") as f:             # large files, one line at a time
    for line in f: ...                            # chapter 9 — lazy, never loads it all

# text mode also translates newlines. Reading, \r\n and \r both become \n;
# writing, \n becomes os.linesep. Usually helpful, occasionally not:
open(p, "w", newline="")                          # REQUIRED for the csv module,
                                                  # which does its own \r\n handling
open(p, "rb")                                     # binary: no decoding, no newline translation

# writing safely: write to a temp file in the same directory, then rename.
# rename is atomic on the same filesystem, so a reader sees old or new, never half
tmp = p.with_suffix(p.suffix + ".tmp")
tmp.write_text(data, encoding="utf-8")
tmp.replace(p)

# and the one to know for logs and pipes:
print(x, flush=True)                              # stdout is block-buffered when not a tty,
                                                  # so output can vanish on a crash
Three file defaults that differ between machines

Encoding. Chapter 12's point, repeated because it is the most common of the three: without an explicit encoding, Python uses the platform default. Pass encoding="utf-8" every time, and use PYTHONWARNDEFAULTENCODING=1 to find the call sites you have missed.

Newlines. Text mode translates them, which is what you want for ordinary text and wrong for CSV — the csv module emits \r\n itself, so without newline="" you get \r\r\n on Windows and blank lines between rows.

Buffering. stdout is line-buffered to a terminal and block-buffered to a pipe or a file. So a script that prints progress looks fine interactively and produces nothing for minutes when redirected to a log — and loses the last buffer entirely if it is killed. flush=True, or python -u, or PYTHONUNBUFFERED=1 in a container.

Check yourself

Self-check

  1. A file of UTF-8 text is read as latin-1. What happens?
    It succeeds, and every non-ASCII character is corrupted. latin-1 maps all 256 possible byte values to code points, so no byte sequence can fail to decode — b'caf\xc3\xa9' becomes 'cafÃ©', with no exception and no warning. That is the single most dangerous property in this chapter: a wrong encoding that raises UnicodeDecodeError is a good outcome, because you find out immediately. latin-1 gives you silent corruption that flows into your database and is very hard to reverse once mixed with correct data. Two defences. Always name the encoding explicitly rather than relying on a platform default. And never reach for latin-1 as a way to "make the error go away" — if you genuinely need to survive undecodable bytes, errors="surrogateescape" preserves them losslessly and round-trips exactly, which latin-1 does not once the text has been through any transformation.
  2. Two strings render identically as "café", compare unequal, and have lengths 4 and 5. Explain.
    One uses the single code point U+00E9 for é; the other uses e followed by U+0301, a combining acute accent. Both are valid Unicode, both render the same, and Python compares strings by code point sequence — so they are not equal and their lengths differ by one. This arrives in real systems all the time: macOS filesystems historically stored decomposed forms while most other sources produce composed ones, so the same filename from two places does not match. The fix is normalisation: unicodedata.normalize("NFC", s) on both before comparing, hashing, or storing. NFC composes where possible and is the right default for storage and comparison; NFD decomposes and is occasionally useful for stripping accents. The rule is to normalise at the boundary, once, and store one form — comparing unnormalised text from two sources is a bug waiting for a name with an accent in it.
  3. len("👨‍👩‍👧") returns 5. What are the five, and what should you use instead?
    Three person emoji joined by two zero-width joiners (U+200D), which is how the family is composed from its parts. It is one thing on screen, 5 code points and 18 UTF-8 bytes, so len() counts none of the three things a person means by "how long". The consequence is that slicing by index cuts it up: family[:2] gives '👨\u200d', a person and a dangling joiner, which renders as a person and an invisible character. For anything user-facing — a character limit, a truncation, a cursor position — you need grapheme clusters, and the standard library does not provide them. The regex module's \X pattern matches one grapheme, and the grapheme package wraps it. For a storage limit, count bytes in the encoding the storage uses. The important step is deciding which unit the requirement is actually in.
  4. Your form validates len(name) <= 20 and the database rejects a 15-character name. Why?
    Because the two are counting different things. Python's len counts code points; the column may count bytes, UTF-16 units, or characters depending on the engine and collation. A name of 15 characters containing accents or emoji can be 20 or more bytes in UTF-8 — 👍 alone is four — so it passes your check and overflows the column, with an error message about the database rather than about the input. Decide which unit the limit is genuinely in and enforce it in that unit at every layer: if the column is VARCHAR(20) counting bytes, validate len(name.encode("utf-8")) <= 20. And normalise to NFC before measuring, or the composed and decomposed forms of the same name will disagree — which turns this from a reproducible bug into an intermittent one depending on which client submitted it.
  5. Your script prints progress and shows nothing when redirected to a file. Why?
    stdout is line-buffered when it is a terminal and block-buffered — typically 8 KB — when it is a pipe or a file. So interactively each line appears immediately, and redirected the output accumulates until a buffer fills, which for a progress line can be minutes. Worse, if the process is killed or crashes, the unflushed buffer is lost entirely, so the log ends before the interesting part. Three fixes depending on scope: print(x, flush=True) per call, python -u for the whole process, or PYTHONUNBUFFERED=1 in the environment, which is worth setting by default in any container. Note that stderr is unbuffered, which is one good reason for progress and diagnostics to go there rather than to stdout — and it keeps them out of the pipeline when someone pipes your output into something else.
  6. What is surrogateescape for?
    Round-tripping bytes that are not valid in the declared encoding, without losing them. A filesystem can contain a filename that is not valid UTF-8 — the kernel stores bytes, not text — so os.listdir() has to return something. With errors="surrogateescape", each undecodable byte is mapped into a reserved surrogate code point, and encoding back with the same handler produces exactly the original bytes: b'file\xff.txt' decodes to a string and re-encodes to b'file\xff.txt'. That is what lets you list a directory, pass the name to open(), and have it work. The limits are worth knowing: such a string is not valid Unicode, so it will raise if you try to encode it with any other handler, print it to a strict stream, or send it over a protocol. It is a transport mechanism for bytes wearing a string's clothes, and it should not travel far from the filesystem call that produced it.
  7. Why does the csv module require newline=""?
    Because the CSV format specifies \r\n as its line terminator and the module emits that itself — so if text mode also translates \n to the platform line ending, you get \r\r\n on Windows, which readers see as a blank line between every row. Passing newline="" disables the translation and lets the module control the terminator, which is why the documentation specifies it for both reading and writing. On reading it matters for a different reason: a quoted field may legitimately contain an embedded newline, and text-mode translation would rewrite it inside the data. This is a good illustration of the general principle — text mode's newline handling is helpful for ordinary human-readable text and wrong for any format that specifies its own line endings, which includes CSV and most wire protocols. When the format defines the bytes, take the translation out of the way.
