Chapter 18 · Craft

Packaging

Packaging has quietly become good. One pyproject.toml replaces four legacy files, and the remaining sharp edges are two: a project layout that decides whether your tests can notice a broken build, and version constraints that admit more than you think.

One file

pyproject.toml
[build-system]                          # who builds it. Required; without this you
requires = ["setuptools>=68"]           # get legacy setup.py behaviour
build-backend = "setuptools.build_meta" # or hatchling, flit_core, pdm-backend

[project]                               # PEP 621 — the same keys whatever backend
name = "mypkg"
version = "0.3.1"                       # or: dynamic = ["version"] to read it from
description = "Does the thing"          #      the package itself
readme = "README.md"
requires-python = ">=3.10"              # pip will refuse to install on 3.9 —
license = "MIT"                         #   worth setting honestly, it is load-bearing
dependencies = [
    "httpx>=0.27,<1",
    "pydantic~=2.6",
]

[project.optional-dependencies]         # pip install mypkg[dev]
dev = ["pytest>=8", "mypy"]

[project.scripts]
mypkg = "mypkg.cli:main"                # creates the `mypkg` command on install

[tool.setuptools.packages.find]
where = ["src"]                         # see the next section — this line matters

[tool.ruff]                             # tool config lives here too, so one file
line-length = 100                       # covers build, deps and tooling
sdist and wheel are different things
A wheel is the built artefact — unzip and it works, no build step, so it installs fast. An sdist is the source, and installing one runs a build on the target machine. Publish both: the wheel for everyone, the sdist for anyone on a platform you did not build for.
Add a py.typed marker if you ship annotations
An empty file inside the package, listed in the package data. Without it, PEP 561 says a type checker must ignore your annotations entirely, so chapter 11's work is invisible to your users.
Applications pin, libraries constrain
A library with narrow pins makes itself uninstallable alongside anything else, so give ranges. An application should lock exact versions of everything, in a lockfile, which is a separate artefact from pyproject.toml.
uv is worth knowing about
A drop-in replacement for pip and virtualenv that is dramatically faster and handles locking. It reads the same pyproject.toml, so trying it costs nothing.

Why the layout matters

Both projects below have the same bug: a module that never made it into the wheel. One test suite notices and one does not, and the only difference is which directory the package sits in.

The same broken wheel, two layouts
Both wheels are broken — only one test says so
Flat layout: the test passes and the wheel is unusable
Python puts the script's directory on sys.path, so running the tests from the project root makes demo/ importable directly. import demo finds the source tree, the missing file is present there, and the suite is green while the published artefact cannot be imported by anyone.
src layout: the test fails, correctly
With the package under src/, the project root contains no importable demo, so the only candidate is the installed one. ModuleNotFoundError: No module named 'demo.helper' — the truth, at the earliest possible moment.
Verified by building and installing both
These are not illustrations. Two real projects were built into wheels, the module was removed from each wheel, both were installed, and the suites were run.
The general shape
Any missing packaging metadata behaves like this — a forgotten subpackage, data files not declared, an entry point that is never exercised. A flat layout tests your working copy; a src layout tests what you would ship.
The layout, concretely

Move the package into src/, point the backend at it with where = ["src"] under [tool.setuptools.packages.find] — or nothing at all for hatchling, which finds it — and install the project in editable mode with pip install -e . so your changes still take effect immediately without the root being importable. That last part is the bit people expect to lose and do not: editable installs work fine with src layout, and you get the safety for free. The cost is one extra directory level and a small amount of confusion the first time. If you have an existing flat project, the migration is a git mv and one config line.

What a constraint admits

Version specifiers, resolved
Every result computed with the packaging library
~=1.2 and >=1.2,<2 are the same thing
Both admit 1.2.0, 1.2.5, 1.4.0 and 1.9.9. The compatible-release operator lets the last component vary, so ~=1.2 allows any 1.x from 1.2 and ~=1.2.0 allows only 1.2.x.
>=1.2 alone will accept 3.0.0
No upper bound means the next major release installs itself into your project on a routine pip install -U. For an application, a lockfile makes this moot; for a library, an unbounded dependency is a promise you cannot keep.
Prereleases are excluded by the resolver, not by the arithmetic
2.0.0rc1 does satisfy >=1.2 numerically, and a resolver still will not choose it unless you opt in. Two different questions, and the surprising one is that Version(…) in SpecifierSet(…) answers the first while .filter() answers the second.
But <2 excludes 2.0.0rc1 regardless
Even though it sorts below 2.0.0. PEP 440 requires an exclusive <V to reject prereleases of V itself, which is what you want and is not obvious — it is why >=1.2,<2 is safer than it looks.
A conflict a resolver cannot solve

If one dependency requires >=1.2,<2 and another requires >=2.0, the number of versions satisfying both is zero. No amount of backtracking finds a solution, and pip's long "ResolutionImpossible" message naming both packages is the tool telling you a human decision is needed: upgrade the first, pin the second back, or drop one. Two things make these easier to live with. Keep your own constraints as loose as you can honestly support, because every narrow pin in a library is a future conflict for somebody. And when you do hit one, read which packages are named rather than reaching for --force-reinstall or --no-deps, both of which produce an environment that installs and then fails at import time.

Check yourself

Self-check

  1. Your tests pass and users cannot import your package. What is the most likely cause?
    A flat layout hiding a broken build. Python puts the script's directory on sys.path, so running tests from the project root makes the source mypkg/ importable directly — and import mypkg finds the source tree rather than the installed package. If a module, subpackage or data file never made it into the wheel, the source copy is still there, so the suite is green while the published artefact is unusable. This was verified by building both layouts, deleting a module from each wheel, installing them and running the suites: the flat one passed, the src one failed with ModuleNotFoundError: No module named 'demo.helper'. Moving the package under src/ fixes it by making the source unimportable from the root, so tests can only reach what was actually installed. Editable installs still work, so the safety is close to free.
  2. What is the difference between an sdist and a wheel?
    A wheel is the built artefact: a zip with a defined layout that pip unpacks into place, with no build step, no compiler and no arbitrary code executed at install time. An sdist is the source, and installing one runs the build backend on the target machine — which is slower, needs a toolchain for anything with C extensions, and can fail in ways you never see locally. Publish both. The wheel covers almost everyone and makes installs fast and reproducible; the sdist is the fallback for a platform or architecture you did not build a wheel for, and it is what distributions and auditors want because it contains the actual source. For a pure-Python project one py3-none-any wheel covers every platform, so the whole thing is python -m build and done. For compiled extensions you need a wheel per platform and Python version, which is what cibuildwheel exists to automate.
  3. ~=1.4.2 — which versions does it allow?
    1.4.2 and any later 1.4.x, but not 1.5.0. The compatible-release operator lets the last specified component vary and pins everything above it, so ~=1.4.2 means >=1.4.2, ==1.4.*. Contrast ~=1.4, which lets the second component vary: >=1.4, ==1.*, so it admits 1.9.9 and not 2.0. The measured comparison in this chapter makes the equivalence concrete — ~=1.2 and >=1.2,<2 select exactly the same releases from the same list. Which to write is mostly taste, though the explicit two-clause form is harder to misread and does not require the reader to remember which component varies. What matters more than the syntax is having an upper bound at all in a library: >=1.2 alone will accept 3.0.0 on a routine upgrade.
  4. Does 2.0.0rc1 satisfy >=1.2?
    Arithmetically yes, and a resolver still will not install it. These are two separate rules that get conflated. The version comparison is straightforward — 2.0.0rc1 is greater than 1.2 — and Version("2.0.0rc1") in SpecifierSet(">=1.2") returns True. But installers exclude prereleases by default unless the constraint itself mentions one or you pass --pre, which in the library is SpecifierSet.filter() rather than in. So the practical answer to "will pip pick it" is no. There is a second, subtler rule worth knowing alongside it: <2 excludes 2.0.0rc1 even though it sorts below 2.0.0, because PEP 440 requires an exclusive <V to reject prereleases of V itself. That is almost always what you meant, and it is the reason >=1.2,<2 is safer than the ordering alone would suggest.
  5. Should a library pin its dependencies?
    No — constrain, do not pin. A library pinned to httpx==0.27.1 is uninstallable alongside anything else that wants a different 0.27.x, and since your users have no way to override it, every narrow pin you publish becomes somebody's ResolutionImpossible. Give the widest range you can honestly support, usually a lower bound for the features you use and an upper bound at the next major version. Applications are the opposite case: they are the top of the dependency tree, nothing has to be compatible with them, and reproducible deploys matter — so lock exact versions of everything, including transitive dependencies, in a lockfile. Note that the lockfile is a separate artefact from pyproject.toml: the file declares intent as ranges, the lock records one resolved solution. Tools such as uv, Poetry and pip-tools all keep that distinction.
  6. What does an empty py.typed file do?
    It tells type checkers that your package's annotations are intended to be used. PEP 561 says a checker must ignore inline annotations in an installed third-party package unless that marker is present, so without it every annotation from chapter 11 is invisible to your users and their mypy treats your entire API as Any — which then propagates through their code, silently disabling checking downstream of every call into your library. The file is empty; what matters is that it ships, so it must be inside the package directory and included as package data ([tool.setuptools.package-data], or automatically with hatchling). It is worth verifying it made it into the wheel, which is exactly the class of packaging bug the src layout catches — unzip the wheel and look, or install it into a clean environment and run a checker against a file that imports you.
  7. pip reports ResolutionImpossible. What is it telling you?
    That no single version of some package satisfies every constraint on it, so there is no solution to find. If one dependency requires >=1.2,<2 and another requires >=2.0, the overlap is empty and no amount of backtracking helps. The message is long because it lists the chain of requirements that produced the conflict, and that chain is the useful part: read which packages are named and which constraint each contributes. The resolution is a human decision — upgrade the package holding the old bound, pin the other back, or drop one. What not to do is reach for --force-reinstall or --no-deps, which both produce an environment that installs successfully and then fails at import or at runtime, converting a clear message at install time into a confusing one in production. Loose constraints in your own packages are the main thing that makes these rare.
