Built-in data structures

Four structures cover almost everything, and choosing between them is the single easiest large performance win available in Python — a membership test against a set instead of a list is around a thousand times faster on a realistic size, for a one-word change. This chapter is about which to reach for and what each one is doing underneath.

A tuple is not a frozen list

The conventional distinction is mutability; the useful one is meaning. A list is a variable number of the same kind of thing — the elements are homogeneous and their positions are incidental. A tuple is a fixed number of different things where position is the meaning: (x, y), (name, age, email), a row from a database. That is why for item in my_list reads naturally and for item in my_point does not. Immutability follows from the meaning rather than the other way round, and it is what makes a tuple hashable and therefore usable as a dict key — but only if everything inside it is hashable too, so (1, [2]) will refuse.

The cost of choosing wrong

Membership: 1,000 lookups against 10,000 items
A list performs about 5,000,000 comparisons; a set performs 1,000 hashes. Measured on this machine that is 33.7 ms against 0.035 ms — roughly 950×, which is less than the 5,000× comparison ratio because an integer comparison is cheaper than a hash.
Inserting at the front: 20,000 times
list.insert(0, x) takes 118 ms; deque.appendleft(x) takes 0.6 ms — 187×, because a list must shift every existing element one place right, every time.
The fix is almost always a one-word change
if x in big_list → build the set once, then if x in big_set. lst.insert(0, x) → from collections import deque. Neither restructures anything.
But only if the collection is stable
Building a set costs O(n), so converting inside the loop makes it worse. Build once outside, or keep the set alongside the list if you need both order and membership.

How a list and a dict actually grow

Both are contiguous blocks that cannot be resized in place, so growing means allocating a bigger block and copying. If they grew by one element at a time, building a list of n items would copy about n²/2 elements. They over-allocate instead, which is what makes append amortised O(1) rather than actually O(1).

new_capacity  =  size + (size >> 3) + 6,  rounded down to a multiple of 4

CPython's growth rule — roughly 12.5% headroom plus a small constant, so the capacity sequence from empty is 4, 8, 16, 24, 32, 40, 52, 64. You can watch it happen with sys.getsizeof, and the demo below is checked against exactly that.

A dict resizes when it is two-thirds full
Over 100 inserts it grows at n = 1, 6, 11, 22, 43, 86 — six times, ending at a capacity of 256. The new table is sized from the count before the insert, which is why capacities double rather than quadruple.
And a rule of thumb that has quietly expired
Comprehensions were once several times faster than the equivalent append loop. Measured on 3.12 with min-of-nine repeats, 100,000 elements takes 2.83 ms as a loop and 2.51 ms as a comprehension — 1.13×. The specialising interpreter added in 3.11 closed most of the gap. Prefer the comprehension for readability, not for speed.
Insertion order was a side effect that became a promise

The compact dict layout introduced in 3.6 stores entries in a dense insertion-ordered array with a sparse index table pointing into it. Preserving order was a consequence of the design rather than its goal — the goal was memory, and it made dicts about 20% smaller. In 3.7 the ordering became a language guarantee, which is why **kwargs, __dict__ and JSON round-trips all preserve order now. Two things follow: collections.OrderedDict is still not redundant, because it compares order-sensitively in == and has move_to_end; and set made no such promise, so set iteration order is arbitrary and will change between runs for strings, since string hashing is randomised per process.

Reaching past the built-ins

python — collections, and what each one removes
from collections import defaultdict, Counter, deque, namedtuple, ChainMap

# defaultdict — removes the setdefault dance
groups = defaultdict(list)
for user in users:
    groups[user.team].append(user)      # no key check, no setdefault

# Counter — removes the counting dance, and sorts for you
counts = Counter(words)
counts.most_common(3)                    # [('the', 812), ('a', 401), ('of', 388)]

# deque — the O(1) ends, and a bounded buffer for free
recent = deque(maxlen=100)               # appending past 100 drops from the other end

# namedtuple — a tuple whose positions have names. Tiny, and still a tuple
Point = namedtuple("Point", "x y")

# and for anything with behaviour, a dataclass instead
from dataclasses import dataclass
@dataclass(frozen=True, slots=True)      # frozen → hashable; slots → no __dict__
class Point:
    x: float
    y: float
defaultdict creates keys just by looking at them

Reading a missing key from a defaultdict inserts it with the default value. So if groups["nonexistent"]: leaves an empty list behind, and a loop that checks a few thousand candidate keys quietly grows the dict by a few thousand entries — which then shows up as a memory question, or as a later iteration finding keys nobody added. Use .get(k) or k in d when you are only asking, and reserve the subscript for when you intend to write. The same caution applies to __missing__ on a dict subclass, which is the mechanism underneath.

Sorting, and the two mistakes

sorted(x) returns a new list; x.sort() sorts in place and returns None. So items = items.sort() silently sets items to None, which then fails somewhere else entirely. The same shape catches list.reverse, list.append and dict.update — the convention is that mutating methods return None on purpose, precisely so this cannot be chained by accident.

And the key function is called once per element, not once per comparison, so sorted(users, key=lambda u: expensive(u)) costs n calls rather than n log n. Python's sort is stable, which means you can sort by several fields by sorting by the least significant first — or just use a tuple key, key=lambda u: (u.team, -u.score), which is clearer.

Check yourself

Self-check

  1. A function checks if item_id in known_ids: against a 10,000-element list, a thousand times. What does it cost and what is the fix?
    About 5,000,000 comparisons, because in on a list scans linearly and finds the item after n/2 elements on average — measured at roughly 34 ms on this machine. Converting known_ids to a set makes it 1,000 hash operations, measured at about 0.035 ms, so around 950× faster. Note that the measured ratio is well below the 5,000× comparison ratio, because an integer comparison is cheaper than computing a hash — the asymptotic difference is what matters and the constant factor works slightly against the set. The important caveat is that building the set is itself O(n), so this only pays if you build it once outside the loop. If you need both order and fast membership, keep both: the list for order, a set alongside for the test. And if the collection is genuinely tiny — a handful of elements — the list is fine and possibly faster.
  2. Why is list.insert(0, x) slow, and what should you use instead?
    A list is a contiguous array of pointers, so inserting at the front means moving every existing element one position right before writing the new one. That is O(n) per insert, and it gets worse as the list grows: 20,000 front-inserts into a 10,000-element list took 118 ms, against 0.6 ms for deque.appendleft — about 187×. A collections.deque is a doubly-linked list of blocks, so both ends are O(1). The trade is that indexing into the middle of a deque is O(n) rather than O(1), and it does not support slicing, so it is the right structure for a queue or a sliding buffer and the wrong one for random access. deque(maxlen=100) is also the neatest way to keep the last N of something, since appending past the limit drops from the other end automatically.
  3. Why is append described as amortised O(1) rather than O(1)?
    Because most appends are O(1) and occasional ones are O(n). A list is a contiguous block that cannot be extended in place, so when it fills, CPython allocates a larger block and copies everything across. It over-allocates using roughly size + (size >> 3) + 6, giving about 12.5% headroom, so the capacity sequence from empty is 4, 8, 16, 24, 32, 40, 52, 64 — visible directly through sys.getsizeof. Building a 199-element list therefore reallocates 15 times and copies 964 elements in total, against 19,701 for a structure that grew by one each time. Averaged over all the appends the cost per append is constant, which is what "amortised" means — but any individual append can be the expensive one, which matters if you are writing something latency-sensitive rather than throughput-sensitive.
  4. Your dict has grown to 100 keys. How many times did it resize?
    Six, at n = 1, 6, 11, 22, 43 and 86, which you can watch through sys.getsizeof. CPython resizes once the table is about two-thirds full, and grows to roughly three times the number of used entries rounded up to a power of two. The two-thirds load factor is a deliberate trade: a fuller table means more hash collisions and slower lookups, an emptier one means more wasted memory. The same reasoning explains why the compact layout introduced in 3.6 was a memory optimisation first — a dense insertion-ordered entry array plus a sparse index table made dicts about 20% smaller, and preserving insertion order was a side effect that became a language guarantee in 3.7. If you know the size in advance, building from a comprehension or dict(zip(...)) avoids some of the incremental resizing.
  5. What is wrong with items = items.sort()?
    list.sort() sorts in place and returns None, so this discards the list and binds items to None. The failure appears later, somewhere else, as a TypeError about NoneType. Use items.sort() on its own line to sort in place, or items = sorted(items) to get a new list. The convention is deliberate and consistent: methods that mutate return None — append, extend, reverse, update — specifically so they cannot be chained as if they returned the object, which would make it ambiguous whether the original had changed. Two related points on sorting: the key function is called once per element rather than once per comparison, so an expensive key costs n calls not n log n; and the sort is stable, so a tuple key like (u.team, -u.score) is the clean way to sort by several fields.
  6. Reading a missing key from a defaultdict has a side effect. What is it?
    It inserts the key with the default value. groups["nobody"] does not raise — it calls the factory, stores the result, and returns it, so the dict now contains a key nobody deliberately added. In a loop that checks a few thousand candidate keys, that quietly grows the dict by a few thousand empty entries, which surfaces later as unexplained memory use or as an iteration finding keys that should not exist. Use d.get(k) or k in d when you are only asking, and reserve the subscript for when you intend to write. The mechanism underneath is __missing__, so any dict subclass implementing it behaves the same way. Counter is the exception worth knowing: it returns 0 for a missing key without inserting it.
  7. Why can a tuple be a dict key but a list cannot?
    Because a dict key must be hashable, and hashability requires that the hash never changes for the life of the object — otherwise the key would be stored in one bucket and looked up in another after a mutation, and would simply vanish from the dict. A list is mutable, so no stable hash is possible and Python refuses to define one. A tuple is immutable, so it can hash, but only if everything inside it is hashable too: (1, 2) works and (1, [2]) raises TypeError, because the tuple's hash is derived from its contents. The same rule explains frozenset existing alongside set, and why a @dataclass(frozen=True) gets a generated __hash__ while a mutable one does not. Chapter 2's identity-versus-equality material is the other half of this: a dict compares keys with == after matching the hash, so a class overriding __eq__ without __hash__ becomes unhashable on purpose.
