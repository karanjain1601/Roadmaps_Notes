Tooling and CI

Four tools, each catching a class of problem the others cannot see. This chapter starts by measuring which gate actually catches what — including one defect that compiles, imports and runs correctly right up until a cold branch executes — and then wires them into pre-commit and CI.

— words— min read2 interactivesNeeds: chapters 11, 15

Which gate catches what

Six defects, four gates
The third one is why linters exist
An undefined name compiles, imports, and runs the happy path
It raises NameError only when the branch containing it executes. So a test suite that never exercises that branch is green, the deploy succeeds, and the failure arrives in production at whatever hour that condition first occurs. A linter finds it in milliseconds without running anything.
An unused import passes every gate there is
It compiles, imports, and produces exactly correct behaviour forever. No amount of testing can find it, because it is not a bug — it is a cost, in import time and in the reader's attention, and only a linter addresses that category.
Two of the six never crash at all
The annotation violation and the wrong result return an incorrect value without raising. Nothing that merely runs the code finds them — you need a value-asserting test or a type checker, which is chapter 15's point about assertions arriving from another direction.
And the mutable default needs more than one call
Three identical calls return 1, 2, 3. A test that calls the function once passes, because the bug is state across calls. Chapter 5 explained the mechanism; here it is the gate analysis that matters.

Ordering the checks, and why this section is a model

The rule everyone gives is "cheapest gate first", so a broken build fails in seconds rather than after a ten-minute suite. It is good advice and this chapter could not demonstrate it. Measured on a one-file project: byte-compiling cost 26 ms above interpreter startup while running the test file cost 10 ms, because python -m py_compile loads its own machinery and the test is two assertions. The intuitive ordering came out backwards.

What that means is that every gate has a fixed overhead — loading its own tooling — which dominates until the project is large enough for the work to matter. The shape is what generalises: linting is roughly linear in files, type checking builds a whole-program model, and a test suite runs your code. On any real codebase they separate by orders of magnitude. But the honest instruction is to time your pipeline rather than assume the order, because the fixed costs are specific to your tools.

The two settings that cause arguments, resolved

Auto-fixing in pre-commit. --fix modifies files during the commit, which means the commit aborts and you stage again — mildly annoying and much better than the alternative of a CI failure for a missing blank line. Keep it, and keep the formatter's output non-negotiable so nobody spends review time on it.

Coverage gates. A minimum coverage percentage in CI reliably produces the suite from chapter 15 — the one with 100% coverage that caught zero of six bugs — because the cheapest way to satisfy the gate is tests that execute code without checking it. If you want a gate, gate on coverage not decreasing for changed files, which pushes toward testing new code without rewarding assertion-free tests. And remember that pre-commit is a convenience, not a control: it runs on the developer's machine and can be skipped with --no-verify, so anything that must hold has to run in CI as well.

Check yourself

Self-check

  1. A misspelled function name inside an except block ships to production. Which gate should have caught it?
    A linter, and only a linter, among the gates that run automatically. Measured: a file containing an undefined name in a rarely-taken branch compiles, imports, and runs the hot path returning exactly the right answer — it raises NameError only when that branch executes. So byte-compiling passes, importing passes, and a test suite passes unless it specifically exercises the error path, which error paths notoriously lack. Ruff's F rules find it statically in milliseconds without running anything. This is the single strongest argument for a linter: not style, but the class of defect that is invisible to execution-based gates until the exact condition arises. It is also an argument for testing error paths, since the reason this hides so well is that the branch never runs — chapter 15's advice to write a regression test at the moment you fix a bug applies with particular force to handlers.
  2. What can no amount of testing find?
    Anything that is not a behaviour difference. An unused import is the clearest case: it compiles, imports, and produces exactly correct results forever, so every execution-based gate passes and always will. It is not a bug, it is a cost — in import time, in the reader's attention, and occasionally in a dependency you no longer need but still install. The same applies to dead code, a stale # type: ignore, an unreachable branch, and a variable assigned and never read. These are precisely the categories a linter exists for, which is why "the tests pass" is not an argument against running one. The reverse also holds and is worth stating: a linter cannot tell you the answer is wrong. The four tools partition the space, and the reason to run all of them is that each is blind to what the others catch.
  3. Two of the six defects never raise. Why does that matter?
    Because a gate that only runs the code cannot see them. The annotation violation and the wrong result both return an incorrect value without crashing, so compiling, importing and executing all succeed — the program simply produces the wrong answer, quietly, for as long as nobody checks. Catching those needs something that compares against an expectation: a value-asserting test, or a type checker for the subset that is a type error. This is chapter 15's finding arriving from another direction. There, a suite with 100% line coverage caught zero of six injected bugs because its assertions only checked is not None; here, the same distinction appears as the difference between a defect that crashes and one that lies. The practical consequence is that "it ran without errors" is evidence of very little, and smoke tests that only check for absence of exceptions are close to worthless.
  4. Your test calls the function once and passes. The function has a mutable default argument. Explain.
    The default list is created once, when the def executes, and shared by every call that does not supply its own — so the bug is state across calls and a single call cannot reveal it. Measured: three identical calls to run(mode, seen=[]) return 1, 2, 3. The first call sees an empty list and behaves exactly as intended, which is why this survives both casual testing and code review. Chapter 5 covered the mechanism and the fix — default to None and build the list inside. What this chapter adds is the gate analysis: no execution-based gate reliably catches it, because catching it requires calling twice and comparing, which a test only does if its author already suspected the problem. A linter flags it on sight from the syntax alone (ruff's bugbear B006), which is the whole reason static analysis earns its place alongside tests.
  5. Why does this chapter not measure the "cheapest gate first" rule?
    Because on a one-file project the measurement contradicts the rule, and reporting it as support would be dishonest. Byte-compiling cost 26 ms above interpreter startup while running the test file cost 10 ms — the intuitive ordering backwards — because python -m py_compile loads its own machinery and the test was two assertions. Every gate carries a fixed overhead for loading its tooling, and until the project is large enough that the actual work dominates, that overhead decides the ranking. The advice is still right at real scale, where linting is roughly linear in files, type checking builds a whole-program model, and a suite runs everything, so they separate by orders of magnitude. But the honest instruction is to time your own pipeline: the fixed costs belong to your specific tools, and the one thing you can be confident of without measuring is that a gate which cannot catch a given defect should not be blocking it.
  6. Should CI fail the build if coverage drops below 80%?
    Be careful, because that gate has a cheap and bad solution. Chapter 15 measured a suite with 100% line coverage that caught zero of six injected bugs — assertions of is not None over every branch. A percentage target rewards exactly that shape, because executing code is much easier than checking it, and once the number is a gate somebody under deadline will find the shortest path through it. If you want a gate, gate on coverage not decreasing for the files a change touches: that pushes toward testing new code without paying for assertion-free tests on old code, and it fails for a reason the author can act on. Better still, treat the coverage report as a map rather than a score — uncovered code is definitely untested and worth looking at, which is real information the percentage throws away. And spend the enforcement budget on things with no cheap workaround, such as --strict-markers and filterwarnings = ["error"].
  7. Pre-commit runs the checks. Why run them in CI too?
    Because pre-commit is a convenience, not a control. It runs on the developer's machine, it has to be installed there, it can be bypassed entirely with git commit --no-verify, and it operates by default only on staged files — so a change that breaks something elsewhere passes locally. It also runs against whatever versions that machine has, which may not be the ones you support. CI is the enforcement point: it runs on every commit regardless of local setup, on a clean checkout, across the version matrix, on the whole codebase. The right division is to run fast checks in both — the same ruff configuration, so results agree — and reserve CI for what cannot run locally: the full suite, the type checker over the whole project, the OS and Python version matrix, dependency auditing, and the build itself. Pre-commit exists to make CI failures rare, not to replace them.
