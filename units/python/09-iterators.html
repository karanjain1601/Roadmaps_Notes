Iterators and generators

Chapter 3 showed that a for loop is a protocol rather than a counter. This is what you can build once you implement that protocol yourself: functions that produce values on demand, pipelines that never materialise an intermediate list, and computations over data larger than memory. The syntax is one keyword.

Implementing it by hand, then not doing that

python — the same thing three ways
# 1. the protocol, written out. Two dunder methods, per chapter 7
class Countdown:
    def __init__(self, n): self.n = n
    def __iter__(self):    return self          # "here is an iterator"
    def __next__(self):                          # "here is the next value"
        if self.n <= 0: raise StopIteration
        self.n -= 1
        return self.n + 1

# 2. a generator function. `yield` anywhere in the body changes what def MEANS:
#    calling it returns a generator instead of running the body
def countdown(n):
    while n > 0:
        yield n
        n -= 1

# 3. a generator expression, for anything that fits on a line
countdown_gen = (n for n in range(5, 0, -1))

# the class version returns SELF from __iter__, so it is one-shot like a generator.
# Returning a fresh iterator instead makes it re-iterable:
class Deck:
    def __init__(self, cards): self.cards = cards
    def __iter__(self): return iter(self.cards)   # a NEW iterator each time
What yield actually does to a function

It is not a fancy return. The presence of yield anywhere in the body makes the whole function a generator function, so calling it runs none of the body — it builds a generator object holding a frozen stack frame. Each next() thaws that frame, runs to the next yield, and freezes it again with all local variables intact. That is why a generator can hold state between values without a class, and why a generator can be infinite: nothing is ever computed until something asks.

Lazy against eager

The two benefits are usually stated together and are actually separate: memory, because nothing is stored, and latency, because nothing is computed until it is needed. The second is often the larger.

The same pipeline, materialised or streamed
Ask for the first match, then ask for all of them
Memory: 8,448,728 bytes against 192
A list of a million integers is about 8.4 MB for the pointer array alone; the equivalent generator is 192 bytes, a factor of 44,000. And the list figure understates it, because each integer beyond CPython's cached −5 to 256 range is a separate 28-byte object the array points at.
Latency: 63.5 ms against 0.014 ms
Time to the first result through a three-stage pipeline over 200,000 rows. The eager version builds every stage in full before the next begins, so it does all the work for every row to answer a question about one. That is a 4,400× difference and it has nothing to do with memory.
But laziness is not free speed
Consume everything and the two are within a few per cent — 10.1 ms against 11.4 ms for a full sum. There is no work avoided when you need every element, and generators add a small per-item overhead that roughly cancels the allocation the list would have done.
And you can only do it once
A generator is exhausted after one pass. If the answer needs two passes, materialise it — the list is the correct choice and the generator is a bug waiting for a second loop.

The four states, and the trap

A generator's lifecycle
Watch when the body first runs, then try to iterate it twice
Calling the function runs nothing
g() returns a generator in state GEN_CREATED with the body untouched. Nothing executes until the first next(). So a generator that validates its arguments does so far too late — the usual fix is a plain function that validates and then returns the generator.
A generator is its own iterator
iter(g) is g is True, so there is nothing to restart. sum(g), sum(g) gives 3 0 — the second pass sees nothing, silently. A list is re-iterable precisely because iter() on it returns a fresh iterator every time.
send() makes yield an expression
x = yield total receives whatever the caller sent. Prime with next(), then send(10) → 10, send(5) → 15. This is the coroutine mechanism that async was built on, and worth understanding once even if you never write one directly.
yield from delegates and returns
yield from inner() forwards every value, and the inner generator's return value becomes the value of the whole expression — [1, 2, 'done'] in the demo. It also forwards send, throw and close correctly, which is the part that is tedious to write by hand.
The exhausted generator that fails silently

The dangerous version is not two obvious loops — it is a function that accepts an iterable and passes over it twice. def report(rows): print(len(list(rows))); return [r for r in rows if ...] works perfectly when handed a list and returns an empty result when handed a generator, with no error. If a function needs more than one pass, either say so in the signature by taking a Sequence, or materialise defensively at the top with rows = list(rows). And note that len() does not work on a generator at all, which at least fails loudly.

Pipelines and itertools

python — each stage is lazy, so the whole chain is
def read(path):
    with open(path) as f:
        yield from f                                 # one line at a time

def parse(lines):
    for line in lines:
        yield json.loads(line)

def errors_only(events):
    for e in events:
        if e["level"] == "ERROR":
            yield e

# nothing has run yet — this only wires the stages together
pipeline = errors_only(parse(read("app.log")))

for event in pipeline:      # NOW rows are pulled one at a time, all the way through
    alert(event)

# the file stays open for the life of the generator, which is a real gotcha:
# abandon the pipeline half-way and the `with` only closes at garbage collection

from itertools import islice, chain, groupby, count, tee, batched

islice(pipeline, 10)        # the first ten, without consuming the rest
chain(a, b, c)              # concatenate without building a combined list
batched(rows, 100)          # 3.12+: fixed-size chunks, for bulk inserts
count(1)                    # an infinite counter — fine, because nothing materialises
groupby(sorted(rows, key=k), key=k)   # NOTE: only groups ADJACENT items, so sort first

a, b = tee(gen)             # two independent passes over one generator —
                            # but it BUFFERS whatever the slower one has not read yet
Two itertools functions that look like their SQL namesakes and are not

groupby groups consecutive equal keys, not all equal keys. Unsorted input gives you the same key several times in separate groups, which looks like data corruption. Sort by the same key first, every time — and note the group it yields is itself an iterator that is invalidated as soon as you advance to the next group, so list(items) inside the loop if you need to keep them.

tee gives you two independent iterators over one source, which sounds free and is not: it buffers every item one iterator has consumed and the other has not. Read one to the end before touching the other and you have materialised the whole thing in memory, having written code that reads as though you did not.

Check yourself

Self-check

  1. Your function takes an iterable, calls len(list(rows)) to log a count, and then filters it. It works in tests and returns nothing in production. Explain.
    The tests pass a list and production passes a generator. A generator is its own iterator — iter(g) is g is True — so the first pass exhausts it and the second sees nothing, silently and with no error. A list is re-iterable because iter() on it returns a fresh iterator each time, which is why the test never caught it. This is the dangerous form of the exhaustion trap, because the two passes are not adjacent and neither looks like a loop over the same object. Two fixes. Say what you need in the signature by accepting a Sequence rather than an Iterable, so a type checker rejects the generator at the call site. Or materialise defensively at the top: rows = list(rows), which costs the memory you were avoiding but is honest about needing two passes.
  2. Why is a lazy pipeline 4,400× faster to the first result but no faster overall?
    Because laziness avoids unneeded work, not work. An eager pipeline materialises each stage completely before the next begins, so asking for the first match over 200,000 rows parses all 200,000 and filters all 200,000 — 63.5 ms — to answer a question that needs about seven of them. The lazy version pulls one row through all three stages, finds a match, and stops: 0.014 ms. But when you genuinely need every element, nothing is skipped, and the two land within a few per cent of each other — 10.1 ms against 11.4 ms for a full sum, where the generator's per-item overhead roughly cancels the list's allocation. So the decision rule is about the shape of the consumption rather than a general preference: use a generator when you might stop early, when the data does not fit in memory, or when it is unbounded, and use a list when you need every element, more than one pass, random access, or a length.
  3. What does calling a generator function actually do?
    Nothing, other than construct a generator object. The presence of yield anywhere in the body changes what def means: calling it does not run the body, it creates an object in state GEN_CREATED holding a frozen stack frame. The first next() thaws that frame and runs to the first yield. You can watch this directly — a print at the top of the body does not appear until the first next(). The practical consequence is that a generator which validates its arguments validates them far too late, typically inside somebody else's for loop where the traceback is confusing. The standard fix is a plain function that validates eagerly and then returns the generator from a nested generator function, so the error surfaces at the call site where it belongs.
  4. What is the difference between return and yield in a generator?
    yield produces a value and suspends, keeping every local variable alive for the next resume. return ends the generator, which raises StopIteration at the consumer — and if it returns a value, that value is attached to the exception rather than being yielded, so a for loop never sees it. The place it becomes visible is yield from: result = yield from inner() binds result to whatever inner returned, which is how you get [1, 2, 'done'] from a generator that yields 1 and 2 and returns 'done'. That mechanism is what made yield from the basis of coroutines before async/await got dedicated syntax. Worth knowing the related rule: raising StopIteration inside a generator is converted into a RuntimeError since 3.7, because the old behaviour silently truncated the generator instead.
  5. Why does groupby return the same key several times?
    Because it groups consecutive equal keys rather than all equal keys — it is closer to Unix uniq than to SQL's GROUP BY. Unsorted input produces a new group every time the key changes, so a key appearing in three separate runs yields three groups. Sort by the same key function first, every time. There is a second trap in the same function: the group it hands you is an iterator into the underlying stream, and it is invalidated as soon as you advance to the next group — so {k: list(g) for k, g in groupby(...)} works while {k: g for k, g in groupby(...)} leaves you a dictionary of empty iterators. Both behaviours follow from groupby being lazy and making a single pass, which is also why it can group a stream larger than memory.
  6. What does itertools.tee cost?
    Memory, proportional to how far apart the two iterators drift. tee gives you independent iterators over one source, which it achieves by buffering every item that one has consumed and the other has not — so if you read the first to the end before touching the second, you have materialised the entire sequence, having written code that reads as though you avoided doing so. It is the right tool when the two consumers advance roughly together, and the wrong one otherwise; if you need two full independent passes, list() is clearer and no more expensive. There is also a correctness note: once you have teed an iterator you must not use the original, because the tee'd ones own it.
  7. A generator reads a file with with open(path) as f: yield from f. What is the risk?
    The file stays open for as long as the generator is alive, and if the consumer stops early the with block never reaches its exit normally — it runs when the generator is garbage-collected, which on CPython is usually immediate through reference counting but is not guaranteed and is not immediate on other implementations. So a pipeline abandoned half-way can hold a file handle, and a program that does this in a loop can exhaust the file descriptor limit while appearing to close everything. Two mitigations: call close() on the generator explicitly, or wrap it in contextlib.closing, which makes the lifetime a block rather than a hope. The more robust design is to keep the resource management at the caller — open the file in a with block and pass the open file to a generator that only transforms — so the lifetime is lexically obvious.
