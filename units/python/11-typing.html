Type hints

Annotations are data attached to a function, and the interpreter does not read them. That one fact explains everything else: why a checker is a separate program, why hints cost nothing at runtime, and why the libraries that do read them at runtime have a whole category of failure the rest of your code does not.

What Python checks

Nothing. It is worth being precise about this before anything else, because a great deal of confusion comes from expecting otherwise.

Six annotated functions, all wrong
Only one of them fails, and not because of the annotation
Five of the six run without complaint
A str passed where int is declared returns 'hello'. A function declared -> int returns 'not an int'. Even def f(x: "a totally invalid type") -> 42 runs, because the annotation is never examined.
The one failure has nothing to do with the annotation
return x + 1 with a string argument raises TypeError: can only concatenate str — that is the + operator refusing, exactly as it would with no annotations at all. The hint played no part.
A bare class annotation creates no attribute
class C: name: str gives hasattr(C, "name") == False and an entry in C.__annotations__. This is what lets a dataclass declare fields without values — and it is why a typo'd attribute name in a class body is silent.
So hints cost nothing and prove nothing on their own
The value comes entirely from running a checker — mypy, pyright, pyre — as a separate step, in CI alongside the tests. Hints without a checker in the pipeline are documentation that drifts.

The syntax worth using

python — modern forms, and what they replaced
def parse(raw: str, limit: int = 10) -> list[dict[str, int]]: ...
#                                      ^^^^ builtin generics since 3.9 —
#                                      no more typing.List, typing.Dict

name: str | None = None            # 3.10+. Replaces Optional[str], and reads better
value: int | float                 # replaces Union[int, float]

from collections.abc import Iterable, Callable, Sequence, Mapping
def total(rows: Iterable[int]) -> int: ...      # accept the WIDEST thing that works
def apply(fn: Callable[[int, str], bool]): ...  # args in a list, then the return

type UserId = int                  # 3.12: a real type alias statement
type Rows = list[dict[str, str]]

def first[T](items: Sequence[T]) -> T | None:   # 3.12 generic syntax — no TypeVar
    return items[0] if items else None

from typing import Literal, Final, TypedDict, NewType
Mode = Literal["r", "w", "a"]                   # only these three strings
MAX: Final = 100                                # reassignment is an error
UserId = NewType("UserId", int)                 # an int a plain int cannot satisfy

class Row(TypedDict):                           # a dict with a known shape,
    id: int                                      # for JSON you do not control
    name: str
Accept broadly, return specifically

The most useful rule in the whole system. A parameter should be annotated with the widest type your function actually handles — Iterable[int] rather than list[int], Mapping[str, int] rather than dict[str, int] — so callers can pass a generator, a tuple, or anything else that works. A return type should be as specific as you can make it, because that is what the caller has to work with: return list[str], not Iterable[str], unless it really is lazy. Chapter 9's exhaustion trap has a typing form here: if your function iterates its argument twice, annotate it Sequence and a checker will reject the generator at the call site.

Why list[Dog] is not a list[Animal]

It looks like it should be, and accepting it would be unsound: a function taking list[Animal] is entitled to append a Cat, which would corrupt your list of dogs. So mutable containers are invariant — the element type must match exactly. Read-only ones are not: Sequence[Dog] is a Sequence[Animal], because you cannot add to it. This is the concrete reason the rule above matters. Annotating a parameter Sequence[Animal] or Iterable[Animal] accepts a list of dogs; annotating it list[Animal] rejects one, and the error message about invariance is the single most confusing thing a new user of a type checker encounters.

Annotations at runtime

Ignored by the interpreter, but not invisible: they are stored, and a growing number of libraries read them. Dataclasses, pydantic, FastAPI, attrs and SQLAlchemy all build behaviour from annotations at import time — which means how they are stored suddenly matters.

What __annotations__ actually contains
Try the TYPE_CHECKING case — the annotation is fine and resolving it is not
Plain annotations are evaluated at definition time
def f(x: int, y: "SomeClass") stores {'x': <class 'int'>, 'y': 'SomeClass'} — the bare name was evaluated to the class object, the quoted one stayed a string. So an annotation naming a class defined later is a NameError unless you quote it.
from __future__ import annotations stores the source text
Everything becomes a string: {'x': 'int', 'y': "'SomeClass'", 'return': 'bool'}. Note the doubly-quoted one — the already-quoted annotation kept its own quotes, which is redundant and harmless. Forward references then work with no quoting at all.
get_type_hints() turns the strings back into objects
Resolving each in the defining module's namespace. That is what dataclasses and pydantic call, and it is where the trap lives.
A TYPE_CHECKING import is not importable at runtime
The annotation stores fine — {'x': 'Decimal'} — and get_type_hints() raises NameError: name 'Decimal' is not defined. Chapter 6 introduced TYPE_CHECKING for breaking import cycles; this is the cost, and it only appears when something reads the annotations.
Which is why TYPE_CHECKING and pydantic need care together

Anything that builds behaviour from annotations resolves them, so a type hidden behind if TYPE_CHECKING: fails at model-construction time with a NameError that names the type and not the import. Three ways out: import the type properly and break the cycle a different way, per chapter 6's advice to extract a third module; call the library's own rebuild step after the type is available, such as pydantic's model_rebuild(); or keep TYPE_CHECKING imports for things that genuinely are checker-only — a return type on an internal function, a variable annotation — and never for a field on a model.

Structural typing

python — typing duck typing
from typing import Protocol, runtime_checkable

class SupportsClose(Protocol):
    def close(self) -> None: ...

def shut(thing: SupportsClose) -> None:      # accepts ANYTHING with close(),
    thing.close()                             # with no inheritance and no registration

# which is what makes it right for Python: a file, a socket, a connection pool
# and your own class all satisfy it without importing your protocol

@runtime_checkable                            # adds isinstance() support…
class Sized(Protocol):
    def size(self) -> int: ...

isinstance(thing, Sized)                      # …but see below
runtime_checkable checks names, not signatures

A class whose size is the string "not callable" passes isinstance(c, Sized). The runtime check only asks whether an attribute of that name exists — it cannot verify arity, argument types or the return type, because none of that exists at runtime. So runtime_checkable is a coarse filter and not a guarantee, and if you are relying on it to validate untrusted input you are not getting what the annotation promises. The static check is the real one; the runtime version exists mainly so protocols work with isinstance at all.

Adopting types on an existing codebase

Gradual typing works because unannotated code is treated as Any and Any is compatible with everything — so a partly-annotated codebase checks cleanly. That is also the failure mode: one Any in the wrong place silently disables checking for everything downstream of it, and the checker will not tell you unless you ask. The practical route is to start with mypy on new files only, turn on disallow_untyped_defs per-module as each is done, run --strict on the newest code, and use --warn-return-any and --disallow-any-explicit to see where the holes are. Annotating the boundaries first — public functions, data models, anything crossing a module edge — gets most of the value for a fraction of the work.

Check yourself

Self-check

  1. def f(x: int) -> int: return x called as f("hello"). What happens?
    It returns 'hello'. The interpreter never examines annotations, so nothing checks the argument on the way in or the return value on the way out. The same function with return x + 1 would raise TypeError: can only concatenate str (not "int") to str — but that is the + operator refusing, exactly as it would with no annotations present, and the hint played no part. Even a syntactically valid but meaningless annotation such as def f(x: "a totally invalid type") -> 42 runs fine. The consequence is that hints are worth exactly what you spend on checking them: they cost nothing at runtime and prove nothing on their own, and the value comes entirely from running mypy or pyright as a separate step in CI alongside the tests. Hints without a checker in the pipeline are documentation that silently drifts out of date.
  2. Why is list[Dog] not acceptable where list[Animal] is expected?
    Because a function accepting list[Animal] is entitled to append a Cat to it, which would leave you holding a list of dogs containing a cat. Allowing the substitution would be unsound, so mutable containers are invariant: the element type must match exactly. Read-only ones are not — Sequence[Dog] is acceptable where Sequence[Animal] is expected, because there is no way to add to it. This is the concrete reason for "accept broadly, return specifically": annotating a parameter Iterable[Animal] or Sequence[Animal] accepts a list of dogs, while list[Animal] rejects it. The invariance error is the single most confusing message a new type-checker user meets, and it almost always means the parameter annotation is too narrow rather than the argument being wrong.
  3. What does from __future__ import annotations change?
    Annotations stop being evaluated at definition time and are stored as their source text instead. So def f(x: int, y: "SomeClass") -> bool stores {'x': 'int', 'y': "'SomeClass'", 'return': 'bool'} — everything a string, including the already-quoted one, which keeps its own quotes redundantly but harmlessly. Three consequences. Forward references work with no quoting, because nothing is looked up. Import time is marginally faster and annotations referencing expensive types cost nothing. And anything that reads annotations at runtime must call typing.get_type_hints() to resolve the strings back into objects, rather than reading __annotations__ directly. That last point is why the flag is not simply free: it moves a class of failure from definition time to resolution time, which is later and further from the cause.
  4. Your pydantic model fails with NameError: name 'Decimal' is not defined, but the import is right there. Explain.
    The import is inside if TYPE_CHECKING:, so it does not exist at runtime. The annotation itself stores fine — it is just the string 'Decimal' — and the failure comes when pydantic calls get_type_hints() to resolve it, which evaluates the string in the module's namespace and finds nothing. Chapter 6 introduced TYPE_CHECKING as the clean way to break an import cycle that exists only for annotations, and this is its cost: it is only safe for annotations nothing reads at runtime. Three ways out. Import the type properly and break the cycle by extracting a shared third module, which is usually the right fix. Call the library's rebuild step once the type is available — model_rebuild() in pydantic. Or keep TYPE_CHECKING imports for genuinely checker-only annotations such as an internal return type, and never for a field on a model that a library will introspect.
  5. What can runtime_checkable actually verify?
    Only that an attribute of the right name exists. A class whose size attribute is the string "not callable" passes isinstance(c, Sized) against a protocol declaring def size(self) -> int. It cannot check arity, parameter types or the return type, because none of that information exists on the object at runtime — signatures are a static-only guarantee. So runtime_checkable is a coarse filter suitable for dispatching between a few known shapes, and not a validation mechanism for untrusted input. The static check is the real one; the runtime version exists mainly so protocols work with isinstance at all. If you need genuine runtime validation, a library that builds validators from the annotations — pydantic, attrs with validators — is doing something categorically different and far more expensive.
  6. Why does adding one Any sometimes stop the checker finding anything?
    Because Any is compatible with everything in both directions, so it propagates. A function returning Any makes its result usable as any type, which makes the next call's arguments unchecked, which makes that result Any too — and the silence spreads downstream without any diagnostic, since from the checker's point of view nothing is wrong. That compatibility is deliberate: it is what makes gradual typing possible, because unannotated code is implicitly Any and a partly-annotated codebase therefore checks cleanly. The way to see the holes is to ask: --warn-return-any flags functions leaking it, --disallow-any-explicit flags the ones you wrote deliberately, and reveal_type(x) in the source prints what the checker actually believes at that point, which is the fastest way to find where inference gave up.
  7. Where do type hints pay off most, if you can only annotate part of a codebase?
    The boundaries: public functions, data models, and anything crossing a module edge. Those are the places where a reader has no other way to learn the contract, where a mistake is made by someone who did not write the code, and where a checker has the most information to work with. Internal helpers within a well-factored module get much less benefit, because the caller is three lines away. Two specific high-value cases worth naming. Anything returning X | None, because forgetting the None case is the single most common Python bug a checker catches. And anything whose argument is iterated more than once, where annotating Sequence rather than Iterable turns chapter 9's silent exhaustion bug into a rejected call site. The practical route is disallow_untyped_defs per-module, turned on as each module is done, so the annotated area can only grow.
