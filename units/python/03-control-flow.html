Control flow

The syntax here takes ten minutes. What takes longer is the model underneath: a for loop is not a counter, it is a protocol, and knowing that explains why mutating a list while looping over it silently skips elements. The chapter ends on match, which is genuinely new and has one trap that will catch you exactly once.

Conditionals

No parentheses, no braces, no switch until 3.10. Indentation is the block structure, which means a misplaced indent is a logic error rather than a syntax error — the one real cost of the design.

python
if status >= 500:
    retry()
elif status == 429:
    back_off()
else:
    accept()

# a conditional EXPRESSION, which has a value. Note the order: value, condition, value
label = "error" if status >= 400 else "ok"

# chained comparison — evaluates `age` once, and reads as it would in maths
if 18 <= age < 65:
    ...

# chapter 2's truthiness: empty containers are falsy, so this covers None AND []
if not results:
    return

# the walrus assigns AND evaluates, which keeps a value you would otherwise recompute
if (n := len(results)) > 100:
    print(f"{n} results, truncating")
Two conditionals that do not mean what they look like

if x == None: should be if x is None:. None is a singleton, so identity is both correct and faster — and a class that overrides __eq__ can make == None return anything it likes. The same applies to True and False: write if flag:, not if flag == True:, which is additionally wrong for any truthy non-boolean.

if x == 1 or 2: is always true. It parses as (x == 1) or 2, and 2 is truthy. What you meant is if x in (1, 2):. This one has no error and no warning, so it survives until someone notices the branch never fails.

Loops, and the protocol underneath

Python has no C-style for. A for statement takes an iterable, calls iter() on it to get an iterator, and calls next() until StopIteration. That is the whole mechanism, and everything else follows from it.

python — what `for x in things:` actually does
it = iter(things)          # calls things.__iter__()
while True:
    try:
        x = next(it)       # calls it.__next__()
    except StopIteration:
        break
    ...                    # the loop body

# so anything with __iter__ works, including things with no length and no end
for line in open("app.log"):   # a file is its own iterator — no read into memory
    ...

# and `range` is not a list. It is an object that computes values on demand
range(10**12)              # instant, and about 48 bytes

# iterating indices is a C habit. Iterate the thing itself
for i in range(len(names)): print(names[i])   # works, reads badly
for name in names: print(name)                # do this
for i, name in enumerate(names, start=1): ... # when you genuinely need the index
for name, score in zip(names, scores, strict=True): ...  # 3.10+: raises if lengths differ

For a list, the iterator holds an index into the live list rather than a snapshot. That single fact produces the most common silent bug in beginner Python.

Removing items while looping over them
Mark two adjacent items for removal and step through

The iterator index advances every pass, removal or not
Remove the item at index 2 and everything after it shifts left, so the item that was at index 3 is now at index 2 — and the loop has already moved on to index 3. It is never visited.
Adjacent removals are the failure
Removing b and c from abcdef visits only five of six items and leaves c behind. Removing b and e — separated — appears to work perfectly.
Which is exactly why it reaches production
The bug is data-dependent. It passes every test whose fixture happens to have non-adjacent matches, and fails on the customer's data. There is no exception, no warning and no wrong type.
The fix is a comprehension
items = [x for x in items if not doomed(x)] builds a new list and rebinds. Iterating a copy (items[:]) also works, and so does iterating in reverse, but the comprehension says what it means.
Dictionaries and sets refuse instead

Adding or deleting a key while iterating a dict or a set raises RuntimeError: dictionary changed size during iteration. That is a strictly better design than the list's silent skipping — you find out immediately rather than in production. Note the exact condition, though: it triggers on a size change, so reassigning an existing key inside the loop is allowed. To delete while iterating, build the key list first: for k in list(d): ..., which materialises the keys before the loop starts.

python — break, continue, and the else nobody uses
for item in haystack:
    if matches(item):
        found = item
        break
else:
    # runs only if the loop finished WITHOUT hitting break.
    # read it as "no break", not as "otherwise" — the keyword is badly chosen
    raise LookupError("nothing matched")

# the alternative people write instead, which needs a flag and is easy to get wrong
found = None
for item in haystack:
    if matches(item):
        found = item
        break
if found is None:
    raise LookupError("nothing matched")   # breaks if None is a legitimate match

while chunk := f.read(8192):   # the walrus makes a read loop read well
    process(chunk)

Comprehensions

A comprehension is the idiomatic way to build a collection from another. It is also slightly faster than the equivalent append loop — though far less so than it used to be, which chapter 4 measures.

python
squares  = [x * x for x in range(10)]              # list
evens    = [x for x in nums if x % 2 == 0]         # with a filter
lookup   = {u.id: u for u in users}                # dict
unique   = {w.lower() for w in words}              # set
lazy     = (x * x for x in big)                    # GENERATOR — computes nothing yet

# nested: the clauses read in the same order you would write the nested loops
flat = [cell for row in grid for cell in row]

# the ternary goes BEFORE the for, because it is part of the expression;
# the filter goes AFTER, because it is a clause. This is the most common confusion
labels = ["big" if n > 100 else "small" for n in nums]        # transform every item
big    = [n for n in nums if n > 100]                          # select some items

# a comprehension has its OWN scope, so this does not leak (unlike Python 2)
[x for x in range(3)]
x  # NameError
When to stop

A comprehension is better than a loop when it fits on one line and does one thing. Two for clauses and a condition is the point at which most readers slow down; three is the point at which a plain loop is clearly better. And a comprehension whose only purpose is a side effect — [print(x) for x in items] — is a loop written to build a list you throw away, which is both slower and misleading. The generator form (x for x in big) is the one to reach for when the result feeds straight into sum, any, max or another loop, since it never materialises the intermediate list; chapter 9 covers what it actually creates.

match, and the one trap

Added in 3.10. It is not a switch — it is structural pattern matching, which destructures the subject and binds parts of it. That makes it genuinely useful for parsing shapes of data, and it has one behaviour that surprises everyone exactly once.

Which patterns match which subjects
Look at the STATUS row, then read the note
A bare name captures — it never compares
case STATUS: does not test whether the subject equals your STATUS constant. It matches anything and rebinds the name to the subject. Every row in the demo matches.
CPython catches half of it for you
If any case follows the bare name, the compiler refuses: SyntaxError: name capture 'STATUS' makes remaining patterns unreachable. That is an unusually good error message and it is the reason this bug is rarer than it should be.
But as the final pattern it compiles silently
And then matches everything, binds your constant to the subject, and looks like it works. The fix is a dotted name — case HTTP.NOT_FOUND: — because only a bare name captures.
Sequences need the exact length; mappings do not
[x, y] matches a two-element sequence and nothing else. {"role": r} matches any mapping containing that key, extra keys included — which is usually what you want when matching JSON.
python — the patterns worth knowing
match event:
    case {"type": "click", "pos": [x, y]}:      # mapping + nested sequence, binds x and y
        handle_click(x, y)
    case {"type": "key", "code": code} if code < 32:   # a guard, checked after the match
        handle_control(code)
    case Point(0, y):                            # positional, via __match_args__
        on_axis(y)
    case [first, *rest]:                         # star captures the remainder
        head_tail(first, rest)
    case str() | bytes() as raw:                 # alternatives, then bind the whole
        parse(raw)
    case _:                                      # the wildcard. `_` binds nothing
        raise ValueError(event)

# str, bytes and bytearray are DELIBERATELY excluded from sequence patterns —
# otherwise `case [x, y]:` would match every two-character string

# and the trap, one more time:
NOT_FOUND = 404
match status:
    case NOT_FOUND:   # matches ANY status and rebinds NOT_FOUND. Use HTTP.NOT_FOUND
        ...
When match earns its place

Not as a replacement for if/elif on a scalar — that is longer and no clearer. It earns its place when you are matching the shape of data and want the parts: parsing a message protocol, walking an abstract syntax tree, handling a JSON payload with several possible forms. In those cases the alternative is a stack of isinstance checks and index lookups that can each fail separately, and match replaces the lot with one declarative block that either binds everything or moves to the next case.

Check yourself

Self-check

  1. You loop over a list and remove matching items. Tests pass; production leaves some behind. Why?
    A list iterator holds an index into the live list, and it advances on every pass whether or not you removed something. So removing the item at index 2 shifts everything left — what was at index 3 is now at index 2 — while the loop moves on to index 3, skipping an item entirely. Removing b and c from abcdef visits five of six items and leaves c. The reason tests pass is that the bug is data-dependent: separated matches like b and e work perfectly, so any fixture without adjacent matches looks fine. There is no exception and no warning. Fix with a comprehension that rebinds — items = [x for x in items if not doomed(x)] — or iterate a copy with items[:]. Dicts and sets handle this better by raising RuntimeError on a size change during iteration.
  2. Why does for line in open("big.log"): not load the file into memory?
    Because for works on the iteration protocol rather than on a sequence. It calls iter() on the object and then next() repeatedly until StopIteration, and a file object is its own iterator whose __next__ reads and returns one line at a time. Nothing ever holds the whole file. The same mechanism is why range(10**12) is instantaneous and about 48 bytes — it computes values on demand rather than storing them — and why a generator can be infinite. It also explains a common surprise: an iterator is consumed, so looping over the same file object twice gives you nothing the second time, and you need f.seek(0) or a fresh open. A list is re-iterable because iter() on it returns a fresh iterator each time; a file is not, because it returns itself.
  3. What does else on a for loop do?
    It runs when the loop completes without hitting break. Read it as "no break" rather than "otherwise" — the keyword is genuinely badly chosen and is the reason the feature is so rarely used. It is exactly right for search loops: iterate looking for something, break when found, and put the not-found handling in the else. The alternative needs a sentinel flag, which introduces its own bug when None or False is a legitimate result. The same clause exists on while, with the same meaning, and on try, where it means "no exception was raised" — which is a more defensible use of the word.
  4. if x == 1 or 2: never takes the false branch. Why?
    It parses as (x == 1) or 2. When x is not 1, the left side is False, so or evaluates and returns 2 — which is truthy, so the branch is always taken. There is no error, no warning and no type problem, which is why it survives review and tests that only ever pass 1 or 2. What you meant is if x in (1, 2):. The underlying rule is chapter 2's: or returns one of its operands rather than a boolean, and every non-zero integer is truthy. The same shape appears as if name == "a" or "b":, where the non-empty string is the truthy value doing the damage.
  5. You write case NOT_FOUND: to match your constant. What happens?
    It depends on whether another case follows it. If one does, CPython refuses to compile the module: SyntaxError: name capture 'NOT_FOUND' makes remaining patterns unreachable. If it is the last pattern, it compiles and matches everything — a bare name in a pattern is a capture, not a comparison, so it binds the subject to NOT_FOUND and succeeds regardless of the value. Your constant is now overwritten with whatever came in. The fix is a dotted name: case HTTP.NOT_FOUND: compares, because only a bare name captures. A literal such as case 404: compares too. This is the single trap in the whole feature, and the compiler catches the more dangerous half of it.
  6. When does a comprehension stop being the right choice?
    Three points. When it no longer fits on one line and does one thing — two for clauses plus a condition is where most readers slow down and three is where a plain loop is clearly better. When the body needs a statement rather than an expression: a try, an assignment to something else, an early return. And when it exists only for a side effect, like [print(x) for x in items], which builds and discards a list of None — slower than a loop and misleading about intent. Worth correcting a stale rule of thumb, though: comprehensions were once several times faster than the equivalent append loop, and on 3.12 the difference for 100,000 elements is about 1.13× — the specialising interpreter added in 3.11 closed most of the gap. Prefer a comprehension for readability rather than for speed. And when the result feeds straight into sum, any or another loop, the generator form (x for x in ...) avoids materialising the list at all.
  7. Why does {"role": r} match a dict with five keys, while [x, y] rejects a three-element list?
    Deliberate asymmetry, and both choices are the useful one. A mapping pattern matches on a subset of keys because that is nearly always what you want when handling JSON or a message payload: you care that the keys you named are present with the right shape, not that no others exist. A sequence pattern requires the exact length because position carries meaning in a sequence, so a three-element list genuinely is a different shape from a two-element one — and if you want "at least two", the star pattern [x, y, *rest] says so explicitly. Worth knowing the related design decision: str, bytes and bytearray are excluded from sequence patterns entirely, even though they are sequences, because otherwise case [x, y]: would match every two-character string and no one would ever expect it.
