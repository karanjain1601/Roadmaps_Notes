Chapter 15 · Craft

Testing

A test suite is worth exactly the bugs it would catch, which is not the same as the lines it runs. This chapter starts with a measurement of that gap — a suite with complete line coverage that catches none of six real bugs — and then goes through pytest and the ways a mock quietly agrees with whatever you assert.

What a suite actually catches

The honest way to measure a test suite is to break the code on purpose and see whether anything notices. Here is one small function, six realistic single-character bugs, and three suites.

python — the function under test
def shipping(weight, express=False, country="UK"):
    if weight <= 0:
        raise ValueError("weight must be positive")
    base = 3.0 if country == "UK" else 8.0
    if weight > 10:
        base = base + (weight - 10) * 0.5
    if express:
        base = base * 2
    return round(base, 2)
Coverage against bugs caught
Look at "every line" — 100% coverage, nothing caught
100% line coverage, 0 of 6 bugs caught
The "every line" suite runs every executable line of the function and asserts only is not None. Coverage tools report it as complete. Every one of the six mutations survives it.
Because coverage measures execution, not checking
A line that ran with nobody looking at the result is covered and untested. The number is a useful floor — uncovered code is definitely untested — and it is not a measure of quality.
The suite that asserts values catches 5 of 6
Same 100% coverage, entirely different value. The difference is not more tests, it is assertions that pin down the answer instead of its type.
And the sixth is not a gap
Changing weight > 10 to >= 10 is an equivalent mutant: at exactly 10 the added term is (10 - 10) * 0.5, which is zero, so both versions agree on every input. No test can kill it, which is why a mutation score of 100% is not a realistic target.
How to use this in practice

You do not need a mutation-testing tool to get the benefit, though mutmut and cosmic-ray exist and are worth an afternoon on a critical module. The cheap version is a habit: after writing a test, go and break the code it covers — flip a comparison, change a constant — and confirm the test fails. If it does not, the test is not testing what you think. This is also the fastest way to check a test you have just fixed: a test that passes both before and after your change was never exercising the bug.

pytest

python — test_shipping.py
import pytest
from shipping import shipping

def test_base_rate():
    assert shipping(5) == 3.0        # plain assert. pytest rewrites it so a
                                      # failure shows both sides, not just "False"

@pytest.mark.parametrize("weight,expected", [
    (5, 3.0), (10, 3.0), (10.5, 3.25), (20, 8.0),   # 4 separate tests, named
])                                                    # individually in the output
def test_weight_bands(weight, expected):
    assert shipping(weight) == expected

def test_rejects_zero():
    with pytest.raises(ValueError, match="must be positive"):
        shipping(0)                   # match= guards against passing for the
                                      # WRONG ValueError — worth always adding

@pytest.fixture
def db():                             # setup before the yield, teardown after,
    conn = connect(":memory:")        # and teardown runs even if the test fails
    yield conn
    conn.close()

@pytest.fixture(scope="session")      # function (default) · class · module · session
def app():                            # wider scope = fewer setups = faster, and
    return build_app()                # state leaks between tests if it is mutable

def test_query(db):                   # request a fixture by naming it as a parameter
    assert db.execute("select 1").fetchone() == (1,)
-x stop at the first failure, --lf re-run only last-failed
The pair that makes a red suite tractable. --lf -x is the tight loop while fixing.
-k "name and not slow"
Select by substring. -m slow selects by marker, which you register in pyproject.toml so a typo'd marker is an error rather than silence.
conftest.py
Fixtures defined there are available to every test in that directory and below, with no import. Also where you put hooks and shared configuration.
-p no:randomly, and test independence
Tests that only pass in a particular order are broken tests. Running with pytest-randomly occasionally is how you find them before CI does.
What to test, when there is never enough time

In rough order of return: anything with a boundary or a branch, because that is where the bugs measured above lived; anything that has broken before, as a regression test written at the moment you fix it; and the seams where your code meets something you do not control. Below that, pure functions are cheap to test and rarely wrong, and glue code that only wires two things together is better covered by one integration test than by mocking both sides. The shape that pays worst is a unit test that mocks so much of its surroundings that it only asserts the code calls the mocks it was written to call — it will pass forever, including after the real thing changes underneath it.

How a mock passes

Four tests that pass and should not
The patch-target case is the one that bites everyone
Patch where the name is looked up, not where it is defined
app.py does from dep import fetch, which binds a new name in app. Patching dep.fetch then changes nothing app can see — the test runs the real function and passes. patch("app.fetch") works. This follows directly from chapter 6: from X import y copies a reference.
A plain Mock accepts any call at all
m.charge(1, 2, 3, 4, 5) is fine even though the real function takes three arguments. create_autospec or autospec=True raises TypeError: too many positional arguments, and catches the case where the real signature changed and your test did not.
Every attribute of a Mock is a new truthy Mock
So assert mock.was_called passes regardless of what happened, and bool(mock.anything.at.all) is True. Modern unittest.mock does guard names that look like assertions — assert_called_onec, called_once — and raises AttributeError, so the old folklore that all typos pass silently is out of date. Anything not shaped like an assertion still slips through.
spec= closes the rest
With Mock(spec=real_charge), an attribute the real object does not have raises AttributeError at the point you touch it. Habit worth forming: never construct a bare Mock() for something that has a real counterpart.
Mock the boundary, not your own code

The useful rule for deciding. Mock things you do not own and cannot make fast or deterministic: a network call, the clock, a payment provider, a random source. Do not mock your own functions to test the function that calls them — that couples the test to the current call structure, so any refactor breaks a test that has found no bug, and the test stops noticing when the real function's behaviour changes. If your code is hard to test without mocking your own internals, that is usually a design signal rather than a testing problem: passing the dependency in as an argument, which chapter 5 called for other reasons, makes the test a matter of passing a different value rather than patching a name.

Check yourself

Self-check

  1. Your suite has 100% line coverage. What does that guarantee?
    That every line ran. Nothing more — in particular, not that anything checked the result. The measurement in this chapter makes the point concretely: a suite calling shipping four different ways and asserting only is not None reaches complete line coverage and catches zero of six injected single-character bugs. A second suite with identical coverage, asserting actual values, catches five. Coverage is a useful floor, because uncovered code is definitely untested and the number tells you where to look. It is not a measure of quality, and a team targeting it as a goal will reliably produce the first suite rather than the second. The honest check is to break the code deliberately — flip a comparison, change a constant — and confirm a test fails. If none does, you have learnt something the coverage number could not tell you.
  2. What is an equivalent mutant, and why does it matter?
    A deliberate change to the code that cannot alter its behaviour, so no test can possibly detect it. In this chapter's function, changing if weight > 10 to >= 10 is one: at exactly 10 the extra term is (10 - 10) * 0.5, which is zero, so both versions produce identical output for every input. It matters for two reasons. Practically, it means a mutation score of 100% is not achievable or worth chasing — a surviving mutant needs judging, not automatically fixing, and time spent writing a test for an equivalent one is entirely wasted. Conceptually, it is a reminder that these tools measure your tests against the code's behaviour, not its text, which is the right thing to measure and the reason mutation testing tells you more than coverage does.
  3. app.py has from dep import fetch. Why does patch("dep.fetch") not work?
    Because from dep import fetch binds a new name fetch in app's namespace, pointing at the function object. Replacing the fetch attribute on the dep module afterwards does not change app's separate binding, so app.run() calls the real function and the test passes having patched nothing — measurably: it returns 'REAL' rather than 'FAKE'. The fix is patch("app.fetch"), patching where the name is looked up rather than where it is defined. This is chapter 6's point about from X import y copying a reference, arriving with consequences. Note the corollary: had app.py written import dep and called dep.fetch(), the lookup would happen at call time and patching dep.fetch would work — which is one small argument for importing modules rather than names.
  4. Your test asserts mock.was_called and always passes. What is happening?
    Attribute access on a Mock creates a new child Mock on demand, and every Mock is truthy — so assert mock.was_called asserts a freshly invented object exists, which it now does. The real attribute is mock.called, or better mock.assert_called_once_with(...). Worth knowing what modern unittest.mock does protect: names that look like assertions are guarded, so assert_called_onec, assret_called_once and called_once all raise AttributeError rather than passing silently — the widely repeated claim that any typo slips through is out of date. But a plausible name that does not look like an assertion, such as was_called or verify, still returns a truthy Mock. The general fix is spec=: with Mock(spec=real_thing), any attribute the real object lacks raises immediately.
  5. What does autospec=True buy you?
    Signature checking. A plain Mock accepts any call whatsoever — m.charge(1, 2, 3, 4, 5) against a three-parameter function is fine — so a test can keep passing long after the real function's signature has changed, which is precisely when you needed it to fail. With create_autospec or patch(..., autospec=True), the same call raises TypeError: too many positional arguments, and the mock also carries the real object's attributes so a typo on one raises. The cost is that it inspects the real object, so it is slower and occasionally awkward with heavy metaprogramming or dynamically created attributes. For anything with a stable signature it is the better default, and the case it earns its keep is exactly the one unit tests are otherwise bad at: a change somewhere else in the codebase that your isolated test cannot see.
  6. When should you not mock something?
    When you own it and it is fast and deterministic. Mocking your own functions to test their caller couples the test to the current call structure, so a refactor that changes nothing observable breaks tests that have found no bug — and worse, the test stops noticing when the real function's behaviour changes, which is the failure mode it was supposed to guard. Mock the boundary instead: things you do not control and cannot make fast or repeatable — a network call, the system clock, a payment provider, a random source. If the code seems untestable without mocking its own internals, that is usually a design signal. Passing the dependency in as an argument turns the test into a matter of supplying a different value rather than patching a name, which is simpler, faster, and does not break when you move the function.
  7. Why register pytest markers in configuration rather than just using them?
    Because an unregistered marker is a silent no-op waiting to happen. @pytest.mark.slow works whether or not slow means anything, so @pytest.mark.slwo also "works" — it attaches a marker nobody selects on, and -m "not slow" quietly includes the test you meant to exclude. Declaring markers under [tool.pytest.ini_options] markers = [...] plus --strict-markers turns the typo into a collection error. The same reasoning covers a related setting worth turning on: filterwarnings = ["error"] promotes warnings to failures, which is how you catch chapter 14's RuntimeWarning: coroutine was never awaited and every deprecation before the upgrade that removes it. Both are cases of making a silent condition loud, which is most of what test configuration is for.
