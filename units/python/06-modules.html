Modules and packages

A module is a file that has been executed once and cached. Almost every confusing import error — the circular one, the file that shadows the standard library, the relative import that works under one command and not another — follows directly from that sentence and from one detail of the order things happen in.

— words— min read2 interactivesNeeds: chapters 02, 05

What import does

Six steps, and the surprising one is fourth.

import greet, stepped
Run it a second time, then look at step 4
A module body runs exactly once
Three import greet statements execute the file once. Everything after that is a dictionary lookup in sys.modules. So module-level code is initialisation, and a module that is expensive to import is expensive exactly once per process.
The module object exists before its body has finished
Step 4 inserts a partially built module into sys.modules, then step 5 executes the body. Checking 'm' in sys.modules from inside m.py returns True. That ordering is what stops a circular import from looping for ever — and it is why some circular imports work and others do not.
import x and from x import y differ only at the end
Both load and execute the module identically. import x binds the module object to the name x; from x import y then reads the attribute y off it and binds that instead. That final attribute read is the entire difference, and the entire cause of the circular-import asymmetry.
sys.path[0] is the script's own directory
Searched before the standard library. A file called random.py next to your script is random as far as Python is concerned, and the error you get — usually AttributeError: module 'random' has no attribute 'randint' — never mentions your file.
The shadowing error names the wrong thing

Name a file random.py, string.py, types.py, email.py or test.py and it silently replaces the standard-library module for anything run from that directory — including libraries you did not write, which is why the failure often appears somewhere unrelated. The diagnosis is import random; print(random.__file__), which shows the path immediately. Note the second casualty: a stale __pycache__/random.cpython-312.pyc can keep shadowing after you rename the file, so delete it too. This is also a reason to put your code in a package directory rather than loose at the top level, since a package name has to collide as a whole to cause the same trouble.

Packages, and how to run them

a package on disk
myapp/
├── __init__.py        # runs when the package is imported. Often empty, and that is fine
├── __main__.py        # runs on `python -m myapp`
├── config.py
├── cli.py
└── store/
    ├── __init__.py
    └── db.py          # myapp.store.db

# absolute — from the top of the package. Unambiguous, and the default choice
from myapp.store.db import connect

# relative — one dot is this package, two is the parent. Only legal INSIDE a package
from .config import SETTINGS       # in myapp/cli.py → myapp/config.py
from ..config import SETTINGS      # in myapp/store/db.py → myapp/config.py

# __init__.py can define the package's public surface
from .store.db import connect      # now `from myapp import connect` works
__all__ = ["connect"]              # what `from myapp import *` exports
python myapp/cli.py and python -m myapp.cli are not the same command

Run the file directly and Python sets sys.path[0] to myapp/, so myapp itself is not on the path and is not a package as far as that process is concerned. Every relative import then fails with ImportError: attempted relative import with no known parent package. Run it with -m from the project root and sys.path[0] is the current directory, myapp is importable, and the relative imports resolve.

Both forms also set __name__ to "__main__" for the entry file, which is what the if __name__ == "__main__": guard tests. The guard is not decoration: without it, importing a module runs its script body, and under multiprocessing on Windows and macOS the child process re-imports the main module — so a missing guard spawns processes recursively. Use -m, and put a console-script entry point in your packaging metadata for anything users will run (chapter 18).

__init__.py is optional now, and still worth having
Since 3.3 a directory without one is a namespace package, which allows a single package to be split across several directories on the path. Useful for plugin systems and confusing everywhere else — a typo'd directory name silently becomes an empty namespace package instead of an ImportError. Keep the file.
Prefer absolute imports
They read the same wherever the file is, they survive moving the module, and they make the dependency visible. Relative imports earn their place inside a package that may be renamed or vendored, where from .config import X keeps working and from myapp.config import X would not.
import * is for the interactive prompt
In a module it makes the source of every name unknowable and lets a dependency's new export silently shadow one of yours. __all__ limits the damage without making it a good idea.

Circular imports: which forms survive

Two modules that import each other is not automatically an error. Whether it works depends on what you import and when, and the reason traces back to step 4 above: the module goes into sys.modules half-built, so the second import gets a real module object that is missing most of its attributes.

Four ways to write the same cycle
Compare the first two — the only difference is the import form
import b works; from b import NAME does not
The first binds the module object, which exists from step 4 onward even though it is empty — and the attribute is only read later, when the function runs, by which time b is complete. The second needs the attribute to exist now, and it does not.
The error names the situation precisely
ImportError: cannot import name 'NAME' from partially initialized module 'b' (most likely due to a circular import). It is one of the better error messages in the language and it tells you both the cause and the fix.
Moving the import into the function always works
By the time the function is called, both modules are fully loaded. It costs one dictionary lookup per call — sys.modules is already populated — so the performance objection is not real. It is a legitimate fix, and also a signal.
The signal is usually a missing third module
If a and b genuinely need each other, the shared part often wants to be c, which both import. A cycle broken by a function-level import still couples the two modules; extracting the shared piece removes the cycle instead of deferring it. TYPE_CHECKING imports are the exception — a cycle that exists only for type annotations is real but harmless.
python — the type-annotation cycle, which is not a real one
# models.py needs Order for a type hint, and orders.py needs User. A real cycle,
# except that neither is needed at RUNTIME — only by the type checker
from __future__ import annotations   # annotations become strings, not evaluated
from typing import TYPE_CHECKING

if TYPE_CHECKING:                     # False at runtime, True for mypy and friends
    from .orders import Order

class User:
    def latest(self) -> Order | None: # fine: never evaluated at runtime
        ...

Check yourself

Self-check

  1. You import the same module in five different files. How many times does its body run?
    Once, per process. The first import executes the file and stores the resulting module object in sys.modules; every later import of the same name finds it there and skips straight to binding the name. That is why module-level code is initialisation rather than something that happens per user, and why an expensive import — a large library, a file read, a network call — costs you once at startup rather than repeatedly. Two consequences worth holding onto. Module-level mutable state is effectively a singleton shared by everything that imports it, which is the mechanism behind both the configuration-module pattern and a whole category of test-isolation problems. And editing a module while a process is running has no effect, because the cached object is not reloaded — importlib.reload exists but is deliberately awkward, since anything holding a reference to the old objects keeps them.
  2. Your program fails with AttributeError: module 'random' has no attribute 'randint'. What happened?
    There is a file called random.py in the script's own directory. sys.path[0] is that directory and it is searched before the standard library, so your file is the random module for that process — and it does not define randint. The error never mentions your file, which is what makes it confusing, and the failure often appears inside a library you did not write, because that library also imports random. Diagnose with import random; print(random.__file__), which shows the path immediately. Rename the file, and delete __pycache__ too, since a stale .pyc can keep shadowing after the rename. The names that bite most often are random, string, types, email, test and logging. Putting your code inside a package directory rather than loose at the top level largely avoids the whole class.
  3. Two modules import each other. Why does import b work where from b import NAME fails?
    Because of when the attribute is read. The import machinery puts a module object into sys.modules before executing its body, so when b imports a partway through a's execution, it gets a real but half-built module. import b only binds that object to a name, and any attribute access happens later — typically inside a function, by which time both modules are complete. from b import NAME has to read the attribute immediately, and it does not exist yet, so you get ImportError: cannot import name 'NAME' from partially initialized module 'b' (most likely due to a circular import). That message is unusually good: it names the cause and implies the fix. Three fixes work — switch to import b and use b.NAME, move the import inside the function, or extract the shared part into a third module that both import, which is usually the right one.
  4. Why does python myapp/cli.py break relative imports when python -m myapp.cli does not?
    Because they set sys.path[0] differently. Running the file directly puts myapp/ on the path, so cli.py is a top-level module with no parent package — and a relative import has nothing to be relative to, giving ImportError: attempted relative import with no known parent package. Running with -m from the project root puts the current directory on the path, so myapp is importable as a package, cli is myapp.cli, and from .config import X resolves. Use -m for anything inside a package. For something users will run, define a console-script entry point in your packaging metadata so they get a command rather than a path, which sidesteps the question entirely. Worth noting that both forms set __name__ to "__main__" for the entry file, so the guard behaves the same either way.
  5. What is if __name__ == "__main__": actually protecting against?
    A module's body running when it is imported rather than executed. __name__ is "__main__" only for the file Python was told to run; for an imported module it is the module's own name. So without the guard, any script-level code — parsing arguments, starting a server, running a job — fires the moment someone imports the file to reuse one function from it. That makes the module untestable, since importing it in a test runs it. There is a sharper failure too: multiprocessing on platforms using the spawn start method, which is Windows and now macOS by default, re-imports the main module in each child process. Without the guard, the child re-runs the code that created the pool, which spawns more children, recursively. The guard turns that from an infinite process explosion into normal behaviour.
  6. Is a circular import ever acceptable?
    Yes, in one clear case and one pragmatic one. The clear case is a cycle that exists only for type annotations: put the import under if TYPE_CHECKING:, which is False at runtime and True for type checkers, and add from __future__ import annotations so the annotations are stored as strings rather than evaluated. The cycle then does not exist at runtime at all, and the checker still sees both sides. The pragmatic case is a function-level import to break an otherwise awkward dependency — it always works, since both modules are fully loaded by call time, and it costs one dictionary lookup because sys.modules is already populated. But treat it as a signal rather than a solution: if a and b genuinely need each other, the shared part usually wants to be a third module that both import. That removes the cycle instead of deferring it, and the resulting layering is nearly always easier to follow.
  7. Why should you keep writing __init__.py when it is optional?
    Because a directory without one is a namespace package, and namespace packages fail quietly. They exist so a single logical package can be split across several directories on the path — genuinely useful for plugin systems and for large namespaced distributions — but the consequence is that any directory matching an import name becomes an importable empty package. A typo in a directory name, or a stray folder that happens to match, gives you a successful import of nothing rather than an ImportError, and the failure then surfaces later as a missing attribute. With __init__.py present, only real packages import. It also gives you somewhere to define the public surface — re-exporting the handful of names callers should use, with __all__ to say so — which is what lets consumers write from myapp import connect instead of reaching three levels into your internals.
