Constraints and integrity

A rule enforced in application code holds until someone writes a second service, runs a migration by hand, or forgets. A rule in the database holds always. This chapter is about moving invariants to where they cannot be bypassed.

keys unique check cascade

Why the database and not the application

Application-level validation

  • Bypassed by a second service, a background job, a console session, a migration
  • Racy — two requests both pass the check, both write (chapter 10)
  • Drifts between codebases and languages
  • Silent when it fails

Database-level constraints

  • Hold for every writer, including the ones that do not exist yet
  • Atomic — the check and the write happen under one lock
  • Document the rule where the data lives
  • Fail loudly, with an error naming the constraint
  • Let the planner optimise using the guarantee
Both, not either

Application validation gives good error messages and catches problems before a round trip. Database constraints guarantee the invariant actually holds. You want both: validate in the application for the user experience, constrain in the database for correctness. The failure mode to avoid is having only the first and believing it is sufficient — every table with duplicate rows that "cannot happen" is that belief being wrong.

UNIQUE, and the NULL surprise

a "unique" column that permits a thousand duplicates
CREATE TABLE users (email text UNIQUE);
INSERT INTO users VALUES (NULL), (NULL), (NULL);   -- all three succeed

-- Standard SQL treats NULLs as distinct for uniqueness, because NULL = NULL is
-- UNKNOWN rather than true (chapter 3). Every NULL is "possibly different".
-- If the column must be unique AND present, that is two constraints:
CREATE TABLE users (email text UNIQUE NOT NULL);

-- Postgres 15+ can invert the behaviour when NULL genuinely means "one of these":
CREATE UNIQUE INDEX ON users (email) NULLS NOT DISTINCT;

-- SQL Server is the outlier: its unique index allows only ONE NULL, which is
-- neither the standard behaviour nor usually what anyone wants.
partial unique indexes — conditional uniqueness
-- "One active subscription per customer, but any number of cancelled ones."
-- A plain UNIQUE on customer_id would forbid the history.
CREATE UNIQUE INDEX one_active_sub
    ON subscriptions (customer_id)
    WHERE status = 'active';

-- "Emails unique among live users, but soft-deleted rows may reuse them."
CREATE UNIQUE INDEX unique_live_email
    ON users (lower(email))
    WHERE deleted_at IS NULL;

-- Note lower(email): case-insensitive uniqueness needs the expression in the
-- index, or 'A@x.com' and 'a@x.com' are both allowed. Postgres and SQLite
-- support partial indexes; SQL Server calls them filtered indexes; MySQL has
-- no equivalent and needs a generated column plus a trigger.
The partial unique index is the most underused feature here

Nearly every "only one of these at a time" rule — one default address, one primary contact, one active subscription, one open shift per employee — is a partial unique index. Most codebases enforce these with application checks that race under concurrency, and the fix is one line of DDL that cannot be bypassed. When you next see a comment saying "there should only ever be one of these", that is what it is asking for.

Foreign keys

the referential actions, and choosing between them
CREATE TABLE orders (
    customer_id bigint NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    address_id  bigint          REFERENCES addresses(id) ON DELETE SET NULL,
    ...
);

-- ON DELETE:
--   RESTRICT / NO ACTION  refuse the delete if children exist  <- safe default
--   CASCADE               delete the children too
--   SET NULL              null the reference (column must be nullable)
--   SET DEFAULT           set it to the column default
--
-- ON UPDATE takes the same actions, and matters only if you allow the parent
-- key to change — which is an argument for surrogate keys (chapter 4).
UseWhen the child isExample
RESTRICTIndependently meaningfulOrders for a customer. Deleting the customer should fail loudly
CASCADEGenuinely part of the parentLine items of an order. Meaningless without it
SET NULLAn optional referenceAn order's delivery address, kept as a snapshot elsewhere
Two things foreign keys will do that surprise people

They do not create an index on the child. PostgreSQL, SQL Server and Oracle index the parent's key and not the referencing column, so every parent delete scans the child table to check the constraint, and every join across it is a scan. MySQL/InnoDB is the exception. This is the single most common missing index (chapter 5). And cascades compound: deleting one customer can remove orders, then their line items, then shipments — millions of rows and a long exclusive lock from a statement that looked trivial. Follow the graph and count before deleting from a parent table in production.

deferrable constraints — for the chicken-and-egg cases
-- Two tables that reference each other, or a bulk load that must insert
-- children before parents.
ALTER TABLE orders
    ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id)
    REFERENCES customers(id) DEFERRABLE INITIALLY IMMEDIATE;

BEGIN;
SET CONSTRAINTS orders_customer_fk DEFERRED;   -- check at COMMIT, not per row
INSERT INTO orders …;                          -- customer does not exist yet
INSERT INTO customers …;                       -- now it does
COMMIT;                                        -- constraint verified here

-- Use sparingly. A deferred constraint means the database is inconsistent for
-- the duration of the transaction, and the error arrives at COMMIT where it is
-- harder to attribute to a particular statement.

CHECK constraints

the rules a type cannot express
ALTER TABLE orders
  ADD CONSTRAINT amount_positive  CHECK (amount > 0),
  ADD CONSTRAINT currency_iso     CHECK (currency ~ '^[A-Z]{3}$'),
  ADD CONSTRAINT status_valid     CHECK (status IN ('pending','paid','shipped',
                                                    'cancelled','refunded')),
  -- cross-column rules
  ADD CONSTRAINT ships_after_placed
      CHECK (shipped_at IS NULL OR shipped_at >= placed_at),
  ADD CONSTRAINT discount_within_total
      CHECK (discount IS NULL OR discount <= amount),
  -- keep a status column and its timestamps from drifting apart
  ADD CONSTRAINT status_matches_timestamps
      CHECK ((status = 'shipped')   = (shipped_at   IS NOT NULL)
         AND (status = 'cancelled') = (cancelled_at IS NOT NULL));

-- Remember chapter 3: CHECK rejects only FALSE, so UNKNOWN passes. Every one
-- of these accepts a NULL in the tested column. If the value is mandatory,
-- that is a separate NOT NULL — the CHECK will not do it for you.
A CHECK must be deterministic and row-local

It cannot reference other rows, other tables, or anything that changes — no subqueries, no now(), no user-defined function that reads a table. The reason is that constraints are re-verified when a table is rewritten or a dump is restored, and a rule depending on external state would fail then. CHECK (placed_at <= now()) looks reasonable and will reject your own backup during restore. For cross-row rules use an exclusion constraint, a trigger, or accept that it belongs in application code.

Exclusion constraints

preventing overlaps — the constraint UNIQUE cannot express
-- "No two bookings for the same room may overlap in time."
-- UNIQUE cannot say this: the rule is about ranges intersecting, not values
-- being equal. An exclusion constraint generalises UNIQUE to any operator.
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE bookings (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL,
    during  tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
    --                          equal        overlaps
);

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-03-01 09:00, 2026-03-01 11:00)');   -- ok
INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-03-01 10:00, 2026-03-01 12:00)');   -- ERROR: conflicts

-- Without this, preventing double-booking needs a SELECT to check for overlaps
-- followed by an INSERT — which is a race (chapter 10), and the failure mode
-- is a customer arriving to find their room occupied.
-- PostgreSQL only. Elsewhere: SERIALIZABLE plus retry, or an explicit lock.

Adding constraints to a table that already has data

without locking the table for an hour
-- The naive version scans the whole table under an ACCESS EXCLUSIVE lock:
ALTER TABLE orders ADD CONSTRAINT amount_positive CHECK (amount > 0);

-- Two-step. Step 1 takes a brief lock and does NOT scan; new and updated rows
-- are checked from this moment on.
ALTER TABLE orders ADD CONSTRAINT amount_positive CHECK (amount > 0) NOT VALID;

-- Step 2 verifies the existing rows under a weaker lock that permits reads
-- and writes. Slow, and it does not block anything.
ALTER TABLE orders VALIDATE CONSTRAINT amount_positive;

-- Same pattern for foreign keys. And for NOT NULL on a large table, add a
-- CHECK (col IS NOT NULL) NOT VALID, validate it, then convert:
--   Postgres 12+ recognises the validated CHECK and skips the scan when you
--   SET NOT NULL.

-- Fix the offending rows BEFORE validating. VALIDATE fails on the first bad
-- row and you have to start again.
Find the violations before you add the constraint

Run the negation as a query first: SELECT count(*) FROM orders WHERE NOT (amount > 0) — and remember to handle NULLs separately, since NOT (NULL > 0) is UNKNOWN and will not appear in that count. Knowing the number changes the plan: zero means you can add the constraint immediately, a handful means fix them by hand, and thousands means you have a data-quality project rather than a migration, and probably a bug still producing them.

Triggers, and when to resist them

Reasonable uses

  • Maintaining updated_at
  • Append-only audit logging
  • Maintaining a denormalised counter or search vector
  • Enforcing a cross-row rule no constraint can express

Why they are a last resort

  • Invisible — code runs that nobody reading the application can see
  • Hard to test, hard to debug, hard to version
  • Fire on bulk operations, turning one statement into millions of function calls
  • Can cascade into other triggers
  • Order between triggers on the same event is often undefined
the one nearly everyone should have
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER orders_updated_at
    BEFORE UPDATE ON orders
    FOR EACH ROW
    WHEN (OLD.* IS DISTINCT FROM NEW.*)   -- skip no-op updates entirely
    EXECUTE FUNCTION set_updated_at();

-- The WHEN clause matters: without it, an UPDATE that changes nothing still
-- bumps the timestamp, which breaks any consumer using updated_at to detect
-- real changes — including incremental syncs and cache invalidation.

A checklist for a new table

  • Primary key — surrogate, bigint or UUID v7 (chapter 4).
  • NOT NULL on every column that has no meaningful absent state. Default to it and justify exceptions.
  • A unique constraint on the natural key, even though the primary key is a surrogate.
  • Foreign keys with an explicit action, and an index on each referencing column.
  • A CHECK for every enum-like column, and for every numeric range that has one.
  • Cross-column checks where two columns must agree — status and its timestamps especially.
  • Partial unique indexes for every "only one of these at a time" rule.
  • created_at and updated_at, both timestamptz NOT NULL.
  • Named constraints — the auto-generated names appear in error messages and are useless.

The short version

  1. Application validation for the error message; database constraints for the guarantee. Both, not either.
  2. UNIQUE permits unlimited NULLs, because NULL is never equal to NULL. Add NOT NULL if you meant both.
  3. Partial unique indexes are the answer to nearly every "only one at a time" rule, and they cannot be raced.
  4. Foreign keys do not create an index on the child in most engines — the commonest missing index there is.
  5. Cascades compound. Follow the graph and count before deleting from a parent in production.
  6. CHECK must be deterministic and row-local — no now(), no subqueries, or restores will fail.
  7. Exclusion constraints generalise UNIQUE to overlap and other operators. No booking system should be without one.
  8. On a live table, add constraints NOT VALID then VALIDATE, and find the violations first.
