Indexes

An index is a sorted copy of some columns with pointers back to the rows. Everything else — which ones to create, what order the columns go in, why the one you added did nothing — follows from taking that description literally.

b-tree column order covering write cost

What an index is

A B-tree index holds the indexed columns in sorted order, in a shallow tree, with each leaf entry pointing at a row in the table. Because it is sorted, the database can binary-search it — a few page reads instead of scanning every row.

Everything a B-tree index can do is a consequence of sorted order. If an operation cannot be expressed as "find a position in a sorted list", the index cannot help.
Two lookups, not one

An index scan usually costs two reads per row: find the entry in the index, then follow the pointer to fetch the row itself. That second step is random I/O, and it is why the planner sometimes refuses your index — if a query will return 30% of the table, doing 30% of the rows as random reads is slower than reading the whole thing sequentially. A sequential scan is often the correct plan, and seeing one is not automatically a problem.

the left-prefix rule
CREATE INDEX ON orders (customer_id, status, placed_at);

-- An index on (a, b, c) is sorted by a, then b within equal a, then c within
-- equal (a, b). So it can serve any LEFT PREFIX of the columns:
--     (customer_id)                         yes
--     (customer_id, status)                 yes
--     (customer_id, status, placed_at)      yes
--     (status)                              NO — the index is not sorted by
--                                           status at the top level
--     (status, placed_at)                   NO
--
-- Think of a phone book sorted by surname, then first name. You can find every
-- "Okafor", and every "Okafor, Amara". You cannot find every "Amara" without
-- reading the whole book.

-- One consequence: an index on (a, b) makes a separate index on (a) redundant.
-- Extra single-column indexes on the leading column are pure write cost.
A range on an earlier column stops the later ones being useful

With (customer_id, placed_at, status) and a query filtering customer_id = 42 AND placed_at > X AND status = 'paid', the index seeks to customer 42, then scans forward through the date range — but within that range the rows are ordered by placed_at, not by status, so the status filter cannot be a seek. It becomes a filter applied to every row scanned. Put equality columns first, range columns last. One range column can be used efficiently; anything after it in the index is only a filter.

the ordering rule, stated fully
-- For a query with:  a = ?  AND  b = ?  AND  c > ?  ORDER BY d
-- the ideal index is: (a, b, c, d)   -- equality, then range, then sort
--
-- Rules of thumb, in priority order:
--   1. Equality predicates first
--   2. Then the column you ORDER BY (if the range allows it)
--   3. Then range predicates
--   4. Among equality columns, most selective first is a weak preference —
--      it barely matters for seeks, and matters for which other queries the
--      index can also serve
--
-- Rule 4 is the one people over-think. Choosing the order so that ONE index
-- serves THREE queries is worth more than optimising the selectivity of one.

Covering indexes

avoiding the second lookup entirely
-- This query needs amount, which is not in the index, so every matching entry
-- requires a trip to the table.
SELECT sum(amount) FROM orders WHERE customer_id = 42 AND status = 'paid';

-- Put amount in the index and the query never touches the table: an
-- index-only scan.
CREATE INDEX ON orders (customer_id, status) INCLUDE (amount);

-- INCLUDE columns are stored in the leaf pages but are NOT part of the sort
-- key, so they do not affect ordering, cannot be searched, and make the index
-- only slightly larger. Postgres 11+, SQL Server.
-- Elsewhere, append them to the key columns: (customer_id, status, amount).

-- Caveat in PostgreSQL: an index-only scan still consults the visibility map
-- to check whether a row is visible to your transaction. On a table with heavy
-- recent writes the map is stale and the scan falls back to fetching rows —
-- so index-only scans work best on tables that are vacuumed regularly.

Partial and expression indexes

indexing less, and indexing something else
-- PARTIAL: index only the rows you query. If 2% of jobs are pending, this
-- index is 2% of the size, stays in memory, and is not touched when the other
-- 98% are written.
CREATE INDEX ON jobs (created_at) WHERE status = 'pending';
-- The planner uses it only when it can prove the WHERE clause is implied by
-- the query's predicate — so the query must also say status = 'pending'.

-- EXPRESSION: index the value you actually search by.
CREATE INDEX ON users (lower(email));
-- Now WHERE lower(email) = 'a@b.com' can seek. Without it, the function must
-- be evaluated for every row and no index applies.

-- The general rule this illustrates:
--     WHERE f(col) = value      cannot use an index on col
--     WHERE col = g(value)      can
-- Keep the column bare on one side of the comparison. This is called making
-- the predicate SARGable, and it is the single most common reason an index
-- that "should" be used is not.

What indexes cost

the write amplification nobody accounts for
-- Every INSERT writes the row plus one entry per index.
-- Every DELETE removes the row plus one entry per index.
-- Every UPDATE that changes an indexed column updates that index; in
-- PostgreSQL a non-HOT update rewrites entries in ALL indexes on the table.
--
-- A table with 8 indexes does roughly 9 units of write work per insert.
-- Indexes also consume memory that would otherwise cache table pages, and
-- they lengthen every VACUUM and every backup.

-- Find the ones nobody uses (PostgreSQL):
SELECT schemaname, relname, indexrelname,
       idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan < 50                         -- nearly never used
  AND indexrelid NOT IN (SELECT conindid FROM pg_constraint)  -- keep constraints
ORDER BY pg_relation_size(indexrelid) DESC;

-- Find duplicates and redundant prefixes: an index on (a) is redundant when
-- (a, b) exists. Drop the narrower one.
Unused indexes are pure cost

They slow every write, consume memory that could cache real data, lengthen maintenance, and give the planner more options to consider. Check idx_scan on a production replica after a full business cycle — a month, so that monthly reports are included — and drop the ones nobody touches. On a mature schema this routinely removes a third of the indexes with no measurable read regression. Drop them one at a time, and keep the DDL to recreate them.

Creating indexes on live tables

without blocking writes
-- Plain CREATE INDEX takes a lock that blocks all writes for the duration.
-- On a large table that is an outage.
CREATE INDEX ON orders (customer_id, status);

-- CONCURRENTLY does two passes and never blocks writes. Slower, and worth it.
CREATE INDEX CONCURRENTLY idx_orders_customer_status ON orders (customer_id, status);

-- Three things to know:
--   * it cannot run inside a transaction, so most migration frameworks need
--     an explicit escape hatch for it
--   * if it fails it leaves an INVALID index behind, which is not used by the
--     planner but is still maintained on every write. Check for these:
--       SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
--     then DROP INDEX CONCURRENTLY and try again
--   * DROP INDEX CONCURRENTLY exists too, and should be your default

-- MySQL: most index changes are online since 5.6. SQL Server: ONLINE = ON,
-- Enterprise edition only.

Index the query, not the column

The habit that separates useful indexing from cargo cult. Instead of asking "should I index status?", take an actual slow query and design one index that serves the whole of it — its equality predicates, its sort, its range, and if worthwhile its output columns. One well-shaped composite index frequently replaces four single-column ones and does more. And it starts from evidence: the slow query log, not intuition about which column "feels" searched.

The short version

  1. An index is a sorted copy with pointers back. Everything it can do follows from sorted order.
  2. An index scan is usually two reads per row, which is why a sequential scan is often the correct plan.
  3. Left-prefix rule: an index on (a, b, c) serves a, (a, b), (a, b, c) — never (b) alone.
  4. Equality columns first, range columns last. A range stops later columns being seekable.
  5. Keep the column bare in a predicate. WHERE f(col) = x cannot use an index on col.
  6. Partial indexes are small, stay cached, and are untouched by writes to the rows they exclude.
  7. Every index taxes every write and consumes cache. Audit idx_scan and expect to drop a third.
  8. On a live table, CREATE INDEX CONCURRENTLY — and check afterwards for invalid indexes.
