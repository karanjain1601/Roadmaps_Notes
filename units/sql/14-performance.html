Chapter 14 · Making it fast

Performance patterns

Chapters 12 and 13 covered indexes and plans. This one is the rest: the query shapes that scale badly no matter how you index them, and the honest question of whether the query was ever the problem.

pagination n+1 materialised views what to measure

Start by finding out what is actually slow

the query that tells you where to look
-- PostgreSQL, with pg_stat_statements enabled (turn it on; it costs almost
-- nothing and you will need it at some point).
SELECT
    calls,
    round(total_exec_time::numeric)              AS total_ms,
    round(mean_exec_time::numeric, 2)            AS mean_ms,
    round((100 * total_exec_time /
           sum(total_exec_time) OVER ())::numeric, 1) AS pct_of_total,
    rows / greatest(calls, 1)                    AS rows_per_call,
    left(query, 90)                              AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- Order by TOTAL time, not mean. A 4ms query called two million times an hour
-- costs far more than a 30-second report run once a night, and it is the one
-- worth fixing. Sorting by mean_exec_time is the commonest mistake here and it
-- reliably points you at the wrong query.
Total time, then rows per call

Two columns do most of the work. Total time tells you which query is consuming the database. Rows per call tells you why: a query returning 40,000 rows per call is being used to fetch data that will be filtered or aggregated in application code, which is chapter 1's mistake showing up in the statistics. Together they usually identify the fix before you look at a single plan.

why OFFSET degrades, and the fix
-- OFFSET does not skip rows cheaply. The database must PRODUCE every skipped
-- row — read it, sort it if needed — and then discard it.
SELECT * FROM orders ORDER BY placed_at DESC, id DESC LIMIT 20 OFFSET 100000;
-- reads 100,020 rows to return 20

-- KEYSET (also called seek, or cursor) pagination: remember where you stopped
-- and ask for what comes after it. Constant time at any depth.
SELECT * FROM orders
WHERE (placed_at, id) < ('2026-02-14 09:31:00', 88213)   -- the last row you saw
ORDER BY placed_at DESC, id DESC
LIMIT 20;

-- The row-comparison syntax (a, b) < (x, y) is the tidy way to express
-- "earlier date, or same date and lower id". The expanded form works
-- everywhere and matches a composite index on (placed_at DESC, id DESC):
WHERE placed_at < '2026-02-14 09:31:00'
   OR (placed_at = '2026-02-14 09:31:00' AND id < 88213)

The correctness point in row four is underrated: with OFFSET, a row inserted at the top while a user pages through pushes everything down one, so page 2 repeats an item from page 1. Keyset pagination is immune.

N+1, and its cousins

three shapes of the same mistake
-- 1. The classic (chapter 1): one query per parent row.
--    Fix: a join, or a single IN query.
SELECT * FROM line_items WHERE order_id = ANY($1);   -- one round trip
-- then group in application code by order_id.

-- 2. The lazy-loading N+1 that ORMs produce. The loop is invisible in the
--    source, because it happens when a property is accessed.
--    Fix: eager loading — select_related / joinedload / include / with().

-- 3. The hidden N+1: a correlated subquery in a SELECT list over many rows,
--    or a user-defined function called per row.
SELECT o.id, expensive_lookup(o.customer_id) FROM orders o;   -- runs per row
--    Fix: join to a pre-computed set, or mark the function STABLE so the
--    planner may cache repeated calls within one statement.
Count the queries per request in development

Every framework can log query counts per request; turn it on and put a threshold in CI. A page issuing 340 queries is not something anyone notices by reading code — it looks like ordinary property access — and it is invisible locally because a round trip to a database on the same machine costs microseconds rather than half a millisecond. A simple assertion that a given endpoint issues fewer than ten queries catches the entire category before it ships.

Counting

exact counts are expensive; usually you do not need one
-- In PostgreSQL this reads the whole table or a whole index, every time,
-- because MVCC means visibility is per-transaction and there is no stored count.
SELECT count(*) FROM orders;                     -- seconds on a large table

-- Estimate from the statistics. Milliseconds, accurate to a few percent.
SELECT reltuples::bigint FROM pg_class WHERE relname = 'orders';

-- Estimate for an arbitrary filtered query, by asking the planner:
EXPLAIN (FORMAT JSON) SELECT * FROM orders WHERE status = 'paid';
-- read "Plan Rows" out of the JSON

-- "More than 1,000" is usually enough for a UI, and it is cheap:
SELECT count(*) FROM (SELECT 1 FROM orders WHERE … LIMIT 1001) t;

-- If you truly need an exact live count, maintain it — a counter table
-- updated by a trigger, or a periodic refresh. Do not compute it per request.
"1–20 of 4,182,993" costs more than the page it decorates

A paginated list that shows a total row count runs two queries: the cheap page, and a count over the entire filtered set. The second is frequently ten times the cost of the first, and nobody uses the number. Replace it with "showing 20 results" plus a next button, or with an estimate, or with a capped count. This is one of the few performance fixes that is purely a product decision — and product will usually agree once they see the figure.

materialised views, and the refresh detail that matters
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', placed_at) AS day,
       region,
       count(*)    AS orders,
       sum(amount) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY 1, 2;

-- A plain refresh takes an exclusive lock: readers BLOCK for the duration.
REFRESH MATERIALIZED VIEW daily_revenue;

-- CONCURRENTLY does not block readers. It requires a unique index on the view,
-- and it is slower — an excellent trade for anything users query.
CREATE UNIQUE INDEX ON daily_revenue (day, region);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;

-- The limitation: a refresh recomputes EVERYTHING. If yesterday's numbers
-- never change, recomputing three years of history nightly is waste. At that
-- point a summary table you update incrementally is the better structure:
INSERT INTO daily_revenue_tbl
SELECT date_trunc('day', placed_at), region, count(*), sum(amount)
FROM orders
WHERE status = 'paid' AND placed_at >= current_date - 1
GROUP BY 1, 2
ON CONFLICT (day, region) DO UPDATE
   SET orders = EXCLUDED.orders, revenue = EXCLUDED.revenue;

the OR rewrite, which surprises people
-- Two indexed columns, and the planner frequently gives up and scans.
SELECT * FROM users WHERE email = $1 OR phone = $2;

-- Two seeks and a concatenation. Often orders of magnitude faster.
SELECT * FROM users WHERE email = $1
UNION
SELECT * FROM users WHERE phone = $2;

-- Use UNION here rather than UNION ALL only because a row could match both
-- and you want it once. If the columns are mutually exclusive, UNION ALL and
-- skip the dedup sort.
--
-- Postgres can sometimes do this itself with a BitmapOr, so check the plan
-- before rewriting — chapter 13. The rewrite is worth knowing for when it
-- does not.

Connection pools: more is not better

A database with 8 cores does not go faster with 500 connections — it goes slower, because each one consumes memory and the scheduler thrashes between them. The usual guidance is a pool of roughly (cores × 2) + effective spindles, which for modern hardware lands somewhere between 10 and 40 for most applications, not the hundreds people configure. Put a pooler in front (PgBouncer, or your framework's) and keep the database-side count small. Teams routinely "fix" a slow database by raising the pool size and make it measurably worse.

Partitioning

what it does and does not buy
CREATE TABLE events (
    id bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    payload jsonb
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_03 PARTITION OF events
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

-- What it genuinely buys:
--   * DROP TABLE events_2025_01  -- instant retention, no DELETE, no bloat
--   * partition pruning: a query with a date filter reads only relevant
--     partitions
--   * maintenance per partition — vacuum, reindex, backup one at a time
--
-- What it does NOT buy:
--   * faster lookups by primary key. A B-tree on a big table is already only
--     a couple of levels deeper than one on a small table
--   * anything at all if queries do not filter on the partition key — they
--     now scan every partition instead of one table, which is worse
--
-- The rule: partition when you have a RETENTION policy or a natural time
-- dimension every query filters on. Not because the table is large.

Set a budget before you start

"Make it faster" has no stopping condition, and optimisation without one consumes weeks. Decide the number first — this endpoint's p95 must be under 200ms — then stop when you reach it. It also settles the arguments: an index that takes you from 800ms to 180ms is done, and the further rewrite that would reach 40ms is not worth the correctness risk of a denormalised column. Most of the harm from performance work comes from continuing past the point where it mattered.

The short version

  1. Order pg_stat_statements by total time, not mean — and read the rows-per-call column next to it.
  2. OFFSET is linear in the offset and also produces duplicates when rows are inserted. Keyset pagination is constant and stable.
  3. Count queries per request in CI. N+1 is invisible in source and invisible locally.
  4. Exact counts are expensive. Estimate, cap, or drop the total from the UI — nobody uses it.
  5. Know the shapes that scale badly: deep OFFSET, OR across columns, leading-wildcard LIKE, huge IN lists, needless UNION.
  6. When everything is slow at once, the query is not the problem — look at locks, pools, bloat and replica lag.
  7. Bigger connection pools make things worse. Tens, not hundreds.
  8. Partition for retention and pruning, not because a table is large. Pre-compute last, and set a budget before you start.
