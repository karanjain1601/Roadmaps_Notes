Chapter 09 · Changing data

Writing data

Reads that go wrong give you a wrong number. Writes that go wrong give you wrong data, permanently, and often across tables that were consistent five minutes ago. This chapter is about the habits that make that unlikely.

INSERT

the forms worth knowing
-- Always name the columns. Without them, adding or reordering a column in the
-- table silently changes what your INSERT means.
INSERT INTO orders (customer_id, amount, status)
VALUES (42, 129.99, 'pending');

-- Multi-row: one statement, one round trip, one parse. Dramatically faster
-- than a loop of single inserts — this is the N+1 of writes.
INSERT INTO orders (customer_id, amount, status)
VALUES (42, 129.99, 'pending'),
       (43,  59.00, 'pending'),
       (44, 210.50, 'paid');

-- From a query: the whole point of a set-based language.
INSERT INTO order_archive (id, customer_id, amount)
SELECT id, customer_id, amount FROM orders WHERE placed_at < '2020-01-01';

-- RETURNING gives back generated values without a second query.
INSERT INTO orders (customer_id, amount)
VALUES (42, 129.99)
RETURNING id, placed_at;
-- Postgres, SQLite 3.35+, MariaDB. SQL Server uses OUTPUT INSERTED.*.
-- MySQL has LAST_INSERT_ID(), which returns only the first id of a batch.
Bulk loading: COPY, not INSERT

For anything over a few thousand rows, the bulk-load path is an order of magnitude faster than even multi-row inserts — COPY in PostgreSQL, LOAD DATA INFILE in MySQL, BULK INSERT in SQL Server. It bypasses much of the per-statement machinery. If you are loading a million rows and it is taking twenty minutes, this is almost always the answer, and it is usually a one-line change in the driver.

Upserts

"Insert it, or update it if it already exists." The obvious implementation is a race condition, and this is one of the few places where dialects differ so much it is worth memorising all three.

the broken version, and why
-- BROKEN. Two concurrent requests can both pass the check, then both insert.
if not db.query("SELECT 1 FROM prefs WHERE user_id = ?", uid):
    db.execute("INSERT INTO prefs (user_id, theme) VALUES (?, ?)", uid, theme)
else:
    db.execute("UPDATE prefs SET theme = ? WHERE user_id = ?", theme, uid)

-- The window between the SELECT and the INSERT is small and it is not zero.
-- Under load it is hit regularly, and the symptom is a unique-violation error
-- in a code path that "cannot" produce one — or duplicate rows if there is no
-- constraint, which is worse.
--
-- No isolation level fixes this by itself (chapter 10). It needs a single
-- atomic statement.
the atomic version, per dialect
-- PostgreSQL / SQLite
INSERT INTO prefs (user_id, theme, updated_at)
VALUES (42, 'dark', now())
ON CONFLICT (user_id) DO UPDATE
    SET theme = EXCLUDED.theme,           -- EXCLUDED = the row you tried to insert
        updated_at = EXCLUDED.updated_at
    WHERE prefs.theme IS DISTINCT FROM EXCLUDED.theme;   -- skip no-op writes
-- The WHERE is worth adding: without it, an unchanged value still writes a new
-- row version, bloats the table and fires triggers for nothing.

-- ON CONFLICT DO NOTHING when you only want the insert to be idempotent:
INSERT INTO events (id, payload) VALUES (…) ON CONFLICT (id) DO NOTHING;

-- MySQL / MariaDB
INSERT INTO prefs (user_id, theme) VALUES (42, 'dark')
ON DUPLICATE KEY UPDATE theme = VALUES(theme);

-- SQL Server, Oracle: MERGE. Powerful, verbose, and historically bug-prone
-- under concurrency in SQL Server — read your version's guidance before
-- relying on it for high-contention keys.
MERGE prefs AS t
USING (VALUES (42, 'dark')) AS s (user_id, theme) ON t.user_id = s.user_id
WHEN MATCHED THEN UPDATE SET theme = s.theme
WHEN NOT MATCHED THEN INSERT (user_id, theme) VALUES (s.user_id, s.theme);
An upsert needs a unique constraint to conflict against

ON CONFLICT (user_id) requires a unique index or constraint on user_id. Without one there is nothing for the database to detect, and the statement errors. This is a feature: it forces you to declare the uniqueness rule you are relying on, which means it also holds for every other code path — including the migration script someone runs by hand. If you find yourself wanting an upsert on a column with no unique constraint, the missing constraint is the actual bug.

UPDATE and DELETE

the discipline that prevents the worst incident in this unit
-- 1. ALWAYS write the SELECT first and look at the rows.
SELECT * FROM orders WHERE status = 'pending' AND placed_at < now() - interval '30 days';

-- 2. Then convert it. Same WHERE, no edits.
UPDATE orders
SET status = 'expired', updated_at = now()
WHERE status = 'pending' AND placed_at < now() - interval '30 days';

-- 3. Check the row count against what the SELECT returned. If they differ,
--    something is wrong and you want to know now, not tomorrow.

-- In a console, wrap it. The transaction is your undo.
BEGIN;
UPDATE orders SET status = 'expired' WHERE …;
-- UPDATE 1,284      <- expected ~1,280. Close enough.
SELECT count(*) FROM orders WHERE status = 'expired';   -- sanity check
COMMIT;   -- or ROLLBACK if the number is wrong
A missing WHERE updates every row

UPDATE users SET is_admin = true is valid SQL, runs instantly, and affects the entire table. There is no confirmation and no undo outside a transaction. Two protections worth having: run your console in a mode that requires an explicit COMMIT (\set AUTOCOMMIT off in psql, --safe-updates in the MySQL client, which refuses unqualified updates entirely), and give production credentials to as few humans as possible. Most people who have done this did it once.

UPDATE from another table
-- PostgreSQL
UPDATE orders o
SET region = c.region
FROM customers c
WHERE c.id = o.customer_id
  AND o.region IS DISTINCT FROM c.region;    -- skip rows already correct

-- MySQL uses a join in the UPDATE clause instead:
UPDATE orders o JOIN customers c ON c.id = o.customer_id
SET o.region = c.region
WHERE o.region <=> c.region IS NOT TRUE;

-- Note IS DISTINCT FROM rather than <>: with a plain <>, rows where either
-- side is NULL evaluate to UNKNOWN and are skipped — so a NULL region never
-- gets filled in, and the backfill silently does nothing for exactly the
-- rows that needed it most. Chapter 3.

Bulk changes without an outage

One big UPDATE, or many small ones The total work is the same. What differs is how long anything else has to wait.

batched backfill — the pattern to keep in a snippet file
-- Each batch is its own transaction, so locks are released between them and
-- other work proceeds. Keyset iteration, not OFFSET (chapter 14).
DO $$
DECLARE
    last_id bigint := 0;
    n       int;
BEGIN
    LOOP
        WITH batch AS (
            SELECT id FROM orders
            WHERE id > last_id AND region IS NULL
            ORDER BY id
            LIMIT 10000
            FOR UPDATE SKIP LOCKED          -- do not block on rows others hold
        )
        UPDATE orders o
        SET region = c.region
        FROM batch b JOIN customers c ON c.id = o.customer_id
        WHERE o.id = b.id;

        GET DIAGNOSTICS n = ROW_COUNT;
        EXIT WHEN n = 0;

        SELECT max(id) INTO last_id FROM (
            SELECT id FROM orders WHERE id > last_id ORDER BY id LIMIT 10000) t;

        COMMIT;                              -- release locks
        PERFORM pg_sleep(0.05);              -- let replication and autovacuum breathe
    END LOOP;
END $$;

-- The three things that make this safe:
--   * bounded batch size, so no lock is held long
--   * a commit between batches, so waiters get through
--   * resumable — it can be killed and restarted, because the WHERE clause
--     only matches rows not yet done
Make bulk operations resumable and idempotent

Write the WHERE clause so that already-processed rows no longer match — WHERE region IS NULL rather than a row range. Then killing the job halfway and restarting it is safe, running it twice is harmless, and you can stop it when the on-call alert fires without having to reason about where it got to. This one property turns a scary operation into a routine one, and it costs nothing to design in.

deleting most of a table
-- Deleting 95% of 100 million rows: slow, bloats the table, and the space is
-- not returned to the OS without a rewrite.
DELETE FROM events WHERE created_at < now() - interval '90 days';

-- Faster: keep the 5% and swap. One brief exclusive lock at the rename.
BEGIN;
CREATE TABLE events_new (LIKE events INCLUDING ALL);
INSERT INTO events_new SELECT * FROM events
  WHERE created_at >= now() - interval '90 days';
ALTER TABLE events RENAME TO events_old;
ALTER TABLE events_new RENAME TO events;
COMMIT;
DROP TABLE events_old;    -- after you have confirmed the swap

-- Better still: partition by month from the start and DROP the old partition.
-- Instant, no bloat, no rewrite. If a table has a retention policy, it should
-- probably be partitioned (chapter 16).
Cascading deletes can be much bigger than they look

ON DELETE CASCADE is convenient and it means one DELETE can touch tables you were not thinking about, several levels deep. Deleting one customer might remove their orders, then the line items of those orders, then the shipments — millions of rows and a long lock from a statement that looked like it affected one row. Before deleting from a parent table in production, follow the foreign keys and count what will actually go. Chapter 11 covers choosing between CASCADE, RESTRICT and SET NULL.

Writing safely from application code

  • Parameterise everything. Never build SQL by string concatenation — chapter 15.
  • Check the affected row count. An UPDATE that matched zero rows usually means someone else changed the row first, and silence is the wrong response.
  • Use RETURNING rather than a follow-up SELECT — one round trip, and no race in between.
  • Make retries safe. Network timeouts mean you do not know whether a write landed. An idempotency key plus ON CONFLICT DO NOTHING makes the retry harmless.
  • Do not read-modify-write. UPDATE t SET n = n + 1 is atomic; reading n and writing back n+1 loses updates under concurrency (chapter 10).
  • Batch multi-row writes. One statement with a thousand rows, not a thousand statements.
  • Keep transactions short. Never hold one open across a network call to another service.
the lost-update bug, and the one-line fix
-- BROKEN under concurrency. Two requests read 10, both write 11, one increment
-- is lost. Nothing errors.
n = db.query("SELECT stock FROM products WHERE id = ?", pid)
db.execute("UPDATE products SET stock = ? WHERE id = ?", n - 1, pid)

-- Atomic: the database reads and writes under one lock.
UPDATE products SET stock = stock - 1
WHERE id = 42 AND stock > 0
RETURNING stock;
-- Zero rows returned means it was already out of stock — the check and the
-- decrement happen together, so there is no window between them.

The short version

  1. Always name the columns in an INSERT, and batch multi-row writes into one statement.
  2. For bulk loads use COPY or the equivalent, not inserts.
  3. Check-then-insert is a race condition. Use an atomic upsert, which requires the unique constraint you should have anyway.
  4. Write the SELECT first, convert it to the UPDATE without editing the WHERE, and check the row count.
  5. Use IS DISTINCT FROM in backfills, or NULL rows are silently skipped.
  6. Batch large changes, commit between batches, and make the WHERE clause resumable and idempotent.
  7. Deleting most of a table? Keep the survivors and swap, or partition and drop.
  8. Never read-modify-write. SET n = n - 1 WHERE n > 0 RETURNING n does the check and the change atomically.
