NULL and three-valued logic

NULL is not a value. It is the absence of one, and SQL handles it with a third truth value that quietly changes the meaning of every comparison it touches. More production reports are wrong because of this chapter than because of anything else in the language.

unknown three-valued logic not in aggregates

NULL means "unknown"

Not zero. Not an empty string. Not false. It means there is no value here, and the crucial consequence is that you cannot compare it to anything — including itself. Two unknowns are not known to be equal, so the comparison is not true. It is also not false. It is UNKNOWN.

the results that surprise people
SELECT NULL = NULL;          -- NULL, not true
SELECT NULL <> NULL;         -- NULL, not true
SELECT NULL = 0;             -- NULL
SELECT NULL + 1;             -- NULL — arithmetic propagates it
SELECT 'abc' || NULL;        -- NULL — so does concatenation
SELECT NULL IS NULL;         -- TRUE  ← the only way to test for it

-- Which is why this returns nothing, ever, regardless of the data:
SELECT * FROM orders WHERE discount_code = NULL;

-- And this is what you meant:
SELECT * FROM orders WHERE discount_code IS NULL;
WHERE keeps only TRUE

This is the rule that generates every surprise in the chapter. WHERE returns rows where the condition is TRUE. Rows where it is FALSE are dropped, and rows where it is UNKNOWN are also dropped. So a filter that looks like it excludes nothing can silently remove every row with a NULL in the compared column — and nothing in the output indicates it happened.

The two asymmetries worth memorising

FALSE AND UNKNOWN is FALSE, because false wins regardless of what the unknown turns out to be. TRUE OR UNKNOWN is TRUE, for the same reason in reverse. Everything else involving UNKNOWN stays UNKNOWN. Those two shortcuts are why an AND chain can survive a NULL and an OR chain can too — and why removing a seemingly redundant condition can change a query's results.

NOT IN, the classic

the bug that returns zero rows and looks like a data problem
-- Intent: customers who have never ordered.
SELECT * FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);

-- If ANY row in orders has a NULL customer_id, this returns NOTHING. Ever.
-- Here is why. NOT IN expands to a chain of inequalities:
--     id <> 1 AND id <> 7 AND id <> NULL AND ...
-- That last term is UNKNOWN for every id, and TRUE AND UNKNOWN is UNKNOWN,
-- so the whole condition is UNKNOWN and WHERE drops the row. Every row.

-- Fix 1 — NOT EXISTS. Not affected, and usually the better plan anyway.
SELECT * FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

-- Fix 2 — exclude the NULLs explicitly.
SELECT * FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);

-- Fix 3 — anti-join. Same result, sometimes a better plan (chapter 5).
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

Note that plain IN is safe: id IN (1, 7, NULL) is TRUE when id is 1, and UNKNOWN otherwise — which behaves like false and gives the answer you wanted. The asymmetry between IN and NOT IN is exactly the OR/AND asymmetry above, and it is why this bug is so hard to spot by reading.

Prefer NOT EXISTS as a habit

It is NULL-safe, it expresses the intent more directly, and on most planners it produces the same or a better plan than NOT IN. There is essentially no case where NOT IN against a subquery is the better choice. Making this a reflex removes a whole category of bug you will otherwise meet once every few years, always at an inconvenient moment.

CHECK is the inverse of WHERE, and it catches people out

WHERE keeps only TRUE; CHECK rejects only FALSE. So CHECK (discount >= 0) happily accepts a NULL discount, because the condition is UNKNOWN rather than false. If the column must have a value, that is a separate NOT NULL — the check constraint will not do it for you, and the table will quietly fill with NULLs that were supposed to be impossible.

Aggregates and the average that is wrong

four counts, four different numbers
-- Table: 10 rows, 3 of which have rating IS NULL, 2 duplicates among the rest.

SELECT count(*)                 FROM reviews;   -- 10  rows
SELECT count(rating)            FROM reviews;   --  7  non-NULL ratings
SELECT count(DISTINCT rating)   FROM reviews;   --  5  distinct non-NULL values
SELECT sum(rating) / count(*)   FROM reviews;   -- WRONG: divides by 10
SELECT avg(rating)              FROM reviews;   -- divides by 7 — the non-NULL count

-- Which is right depends entirely on what you meant:
--   "average rating given"           -> avg(rating), divide by 7
--   "average treating unrated as 0"  -> avg(coalesce(rating, 0)), divide by 10
--
-- Those are different questions with different answers, and a report that
-- silently picks one has silently made a business decision.
the empty-table case
SELECT count(*) FROM orders WHERE 1 = 0;    -- 0
SELECT sum(amount) FROM orders WHERE 1 = 0; -- NULL, not 0

-- sum() over no rows is NULL. If that feeds into arithmetic, everything
-- downstream becomes NULL and a dashboard shows a blank rather than a zero.
SELECT coalesce(sum(amount), 0) AS revenue FROM orders WHERE 1 = 0;   -- 0

-- The habit worth forming: wrap any sum() that could see zero rows.
-- count() never needs it; sum(), max(), min() and avg() all do.

the ones worth knowing by name
-- coalesce: first non-NULL wins. Types must be compatible.
SELECT coalesce(nickname, first_name, 'there') AS greeting FROM users;

-- nullif: the standard divide-by-zero guard.
SELECT revenue / nullif(order_count, 0) AS avg_order FROM daily;
-- order_count = 0 becomes NULL, and x / NULL is NULL rather than an error.

-- IS DISTINCT FROM: comparison that treats NULL as a value.
-- Essential for change detection, where "was NULL, now has a value" counts.
SELECT * FROM staging s
JOIN target t ON t.id = s.id
WHERE s.email IS DISTINCT FROM t.email          -- catches NULL -> 'x' and 'x' -> NULL
   OR s.phone IS DISTINCT FROM t.phone;

-- With plain <> those changes are UNKNOWN and the row is skipped, so a sync
-- job silently stops propagating any field that was previously empty.

Should the column allow NULL at all?

Most NULL bugs are downstream of a schema that permits NULL where it has no meaning. The cheapest fix is upstream.

NULL is meaningful when

  • The value genuinely does not exist yet — shipped_at on an unshipped order
  • It does not apply — cancellation_reason on a live subscription
  • It is genuinely unknown — a legacy record imported without an email
  • An outer join produced it (chapter 5)

NULL is a mistake when

  • It means zero — use 0 with NOT NULL DEFAULT 0
  • It means empty — use '', and pick one of the two consistently
  • It means false — use false
  • It encodes a state — use an enum with an explicit value
  • Nobody can say what it means. That is the real test
Default to NOT NULL

Make nullability a decision you justify rather than a default you inherit. For each column, ask: what does it mean when this is absent, and is that different from any value it could hold? If there is no good answer, add NOT NULL with a sensible default. This eliminates the bugs in this chapter before they can occur, and it is far cheaper than adding the constraint later against a table that has already accumulated NULLs nobody can now interpret.

Empty string and NULL are both "no email", and now you have two

The commonest schema smell in this area. Some rows have '', others have NULL, both mean the same thing, and every query has to handle both — which most do not. Pick one representation, add a CHECK (email <> '') to forbid the other, and clean up the existing rows. Doing this once is a morning's work; not doing it is a permanent tax on every query that touches the column.

Reviewing for NULL bugs

  • Every NOT IN against a subquery — can the subquery produce NULL? Rewrite as NOT EXISTS regardless.
  • Every <> or != — is the column nullable? If so it excludes NULLs, which is probably not what "everything except" meant.
  • Every sum() — can the group be empty? Wrap in coalesce(…, 0).
  • Every avg() — should NULLs be excluded from the denominator or counted as zero? Say which.
  • Every count(col) — did you mean count(*)? They differ exactly when the column is nullable.
  • Every division — nullif(divisor, 0).
  • Every inner join on a nullable column — rows with a NULL key disappear entirely.
  • Every CHECK — it permits NULL. Add NOT NULL separately if you need it.

The short version

  1. NULL means unknown, not zero and not empty. It is not equal to anything, including itself.
  2. WHERE keeps only TRUE — UNKNOWN is dropped just like FALSE. That is the source of every surprise here.
  3. Two asymmetries: FALSE AND UNKNOWN is FALSE, TRUE OR UNKNOWN is TRUE. Everything else stays unknown.
  4. NOT IN with a NULL in the subquery returns nothing at all. Use NOT EXISTS as a reflex.
  5. CHECK is the inverse of WHERE: it rejects only FALSE, so it accepts NULL.
  6. Aggregates skip NULLs, so avg divides by the non-NULL count — and sum() over no rows is NULL, not 0.
  7. IS DISTINCT FROM is the NULL-safe comparison, and change-detection queries need it.
  8. Default to NOT NULL, and never let empty string and NULL both mean "absent" in the same column.
