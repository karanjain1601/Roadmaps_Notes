Aggregation and GROUP BY

Grouping changes the shape of a result: many rows become one, and the individual rows stop being addressable. Almost every confusion about GROUP BY — and the worst reporting bug in SQL — follows from that one change.

group by having counting double counting

Grouping changes the shape

Before GROUP BY, the result has one row per source row. After it, one row per group. A column that had one value per row now has many values per output row — so you can only reference it through a function that reduces many values to one.

the error everyone meets first
SELECT customer_id, status, sum(amount)
FROM orders
GROUP BY customer_id;
-- ERROR: column "orders.status" must appear in the GROUP BY clause
--        or be used in an aggregate function

-- The message is precise. This customer's group holds three orders with three
-- different statuses. Which one should the single output row show? There is no
-- answer, so the database refuses rather than guessing.

-- Three legitimate resolutions, depending on what you meant:
SELECT customer_id, status, sum(amount)
FROM orders GROUP BY customer_id, status;        -- finer groups

SELECT customer_id, max(status), sum(amount)
FROM orders GROUP BY customer_id;                -- pick one deterministically

SELECT customer_id,
       string_agg(DISTINCT status, ', ' ORDER BY status) AS statuses,
       sum(amount)
FROM orders GROUP BY customer_id;                -- collapse them into one value
The rule, and why it is not arbitrary

Every column in the SELECT list must either appear in GROUP BY or be wrapped in an aggregate. This is not a syntax quirk to be worked around — it is the database telling you that your question is ambiguous. When you hit this error, the useful move is to decide what you actually want for that column, not to reach for whatever makes the error go away.

MySQL used to guess, and plenty of code still relies on it

Older MySQL allowed the first query above and returned an arbitrary status from each group — no error, no warning, and a different answer if the plan changed. ONLY_FULL_GROUP_BY is on by default in MySQL 5.7+ and disables it, but legacy code and older tutorials are full of the pattern. If a query works in MySQL and errors in Postgres, this is usually why. MySQL also offers ANY_VALUE(col) to say "I genuinely do not care", which at least documents the intent.

conditional aggregation — one pass, many answers
-- The pattern that replaces running four separate queries.
SELECT
    date_trunc('month', placed_at)                          AS month,
    count(*)                                                AS orders,
    count(*) FILTER (WHERE status = 'paid')                 AS paid,
    count(*) FILTER (WHERE status = 'refunded')             AS refunded,
    coalesce(sum(amount) FILTER (WHERE status = 'paid'), 0) AS revenue,
    round(100.0 * count(*) FILTER (WHERE status = 'refunded')
                / nullif(count(*), 0), 1)                   AS refund_pct
FROM orders
GROUP BY 1
ORDER BY 1;

-- FILTER is standard SQL and supported by Postgres and SQLite. The portable
-- version, which works everywhere:
--     count(CASE WHEN status = 'paid' THEN 1 END)
--     sum(CASE WHEN status = 'paid' THEN amount ELSE 0 END)
--
-- Note the two different ELSE choices: count() needs NULL for non-matches
-- (so no ELSE), sum() needs 0. Writing count(CASE ... ELSE 0 END) counts
-- every row, and the number looks plausible.
--
-- Note also nullif(count(*), 0) guarding the division, and 100.0 rather
-- than 100 to force floating-point division — integer division silently
-- truncates to 0 in most engines.
Percentiles, not averages, for latency

avg(duration_ms) is the wrong summary for anything with a long tail, which is every latency distribution. One 30-second request among a thousand fast ones moves the average and tells you nothing about what users experience. Use percentile_cont(0.5) and percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms). The syntax is awkward and the number is worth it.

The double-counting bug

Join then aggregate Three orders, with line items and shipments. Add each join and watch the revenue total inflate.
—rows before grouping
—sum(o.amount)
—true revenue
—error
This is the most damaging bug in this unit

It does not error, it does not look wrong, and the number it produces is plausible enough to survive review and reach a board deck. The mechanism is chapter 5's fan-out: the join multiplies rows, then sum() faithfully adds the duplicates. Every aggregate in the query is affected — revenue, counts, averages — and DISTINCT fixes only the visible duplication while leaving the numbers wrong. Any time you aggregate over a join, check the pre-grouping row count against what you expect.

three ways to aggregate safely across a one-to-many
-- 1. Pre-aggregate each side to one row per key, then join. Clearest, and
--    usually the best plan because each subquery groups independently.
SELECT o.id, o.amount, coalesce(li.qty, 0) AS qty, coalesce(s.n, 0) AS shipments
FROM orders o
LEFT JOIN (SELECT order_id, sum(quantity) AS qty
           FROM line_items GROUP BY order_id) li ON li.order_id = o.id
LEFT JOIN (SELECT order_id, count(*) AS n
           FROM shipments  GROUP BY order_id) s  ON s.order_id  = o.id;

-- 2. Correlated scalar subqueries. Fine for two or three columns; verbose
--    beyond that, and each one is a separate lookup.
SELECT o.id, o.amount,
       (SELECT coalesce(sum(quantity), 0) FROM line_items li
        WHERE li.order_id = o.id) AS qty
FROM orders o;

-- 3. count(DISTINCT ...) as a rescue when you cannot restructure. Works for
--    counts, does NOT work for sums — there is no sum(DISTINCT row).
SELECT o.id,
       count(DISTINCT li.id) AS line_items,
       count(DISTINCT s.id)  AS shipments,
       min(o.amount)         AS amount      -- min() over identical copies
FROM orders o
LEFT JOIN line_items li ON li.order_id = o.id
LEFT JOIN shipments  s  ON s.order_id  = o.id
GROUP BY o.id;
-- The min(o.amount) trick works because every duplicate row carries the same
-- amount. It is correct and it is a smell — option 1 says what you mean.

WHERE against HAVING

not interchangeable, and the difference is the answer
-- WHERE drops ROWS before grouping. HAVING drops GROUPS after aggregating.
SELECT customer_id, count(*) AS n, sum(amount) AS total
FROM orders
WHERE status = 'paid'          -- unpaid orders never enter a group
GROUP BY customer_id
HAVING count(*) >= 3;          -- customers with fewer than 3 PAID orders go

-- Move the status test into HAVING and it is a different question entirely:
HAVING count(*) FILTER (WHERE status = 'paid') >= 3
-- now all orders form the groups, and the threshold counts only paid ones.
-- A customer with 2 paid and 8 refunded orders is excluded by the first and
-- also by the second — but their 'total' differs, because the first summed
-- only paid amounts and the second summed everything.

-- Rule of thumb: if the condition is about ONE ROW, it belongs in WHERE.
-- If it is about the GROUP as a whole, it belongs in HAVING. Putting a
-- row-level condition in HAVING also costs performance — you grouped rows
-- you were always going to discard.

the missing-zeros problem
-- A month with no orders produces no row. The chart then draws a straight line
-- between the surrounding months and nobody notices the gap.
SELECT date_trunc('month', placed_at) AS month, count(*)
FROM orders GROUP BY 1 ORDER BY 1;

-- Generate the axis, then LEFT JOIN the data onto it.
SELECT m.month, count(o.id) AS orders          -- count(o.id), not count(*):
FROM generate_series(                          -- count(*) would return 1 for
        date_trunc('month', current_date - interval '11 months'),
        date_trunc('month', current_date),     -- an unmatched month, because
        interval '1 month') AS m(month)        -- the LEFT JOIN produced a row
LEFT JOIN orders o
       ON date_trunc('month', o.placed_at) = m.month
GROUP BY m.month
ORDER BY m.month;

-- The count(o.id) detail is the point. On a LEFT JOIN with no match there is
-- still one output row, so count(*) says 1 and count(o.id) says 0. The second
-- is what you meant, and this is the commonest way a zero becomes a one.

Grouping sets, rollup and cube

subtotals without unions
-- ROLLUP adds progressively coarser subtotals plus a grand total.
SELECT region, product, sum(amount)
FROM sales
GROUP BY ROLLUP (region, product);
--  by (region, product), then by (region), then the overall total.
--  The rolled-up columns are NULL in subtotal rows.

-- CUBE gives every combination: (region, product), (region), (product), ().
SELECT region, product, sum(amount) FROM sales GROUP BY CUBE (region, product);

-- GROUPING SETS lets you name exactly the ones you want.
SELECT region, product, sum(amount)
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());

-- Distinguishing a subtotal's NULL from a real NULL in the data:
SELECT
    CASE WHEN grouping(region) = 1 THEN 'ALL REGIONS' ELSE region END AS region,
    sum(amount)
FROM sales GROUP BY ROLLUP (region);
-- grouping() returns 1 when the column was rolled up. Without it, a genuine
-- NULL region and the grand-total row are indistinguishable.

Check every aggregate query against a known number

The habit that catches all of this: before shipping a report, verify one figure you can compute another way. Total revenue for one small customer, order count for one day, a single group you can check by eye. Aggregates fail silently — no error, plausible output — so the only reliable defence is an independent check. Doing it once per query, at the time you write it, is the difference between a report you trust and one you merely hope about.

The short version

  1. Grouping changes the shape: many rows become one, and non-grouped columns stop being addressable.
  2. The "must appear in GROUP BY" error means your question is ambiguous — decide what you want, do not silence it.
  3. sum() over zero rows is NULL, and count(*) over a LEFT JOIN with no match is 1. Both turn into wrong dashboard numbers.
  4. Aggregating over a one-to-many join double-counts, plausibly and silently. Pre-aggregate each side, then join.
  5. count() wants NULL for non-matches and sum() wants 0 — getting that backwards counts every row.
  6. WHERE for row conditions, HAVING for group conditions. Wrong choice, wrong answer and slower.
  7. GROUP BY cannot produce a group with no rows — generate the axis and left-join onto it.
  8. Verify one figure independently before trusting any aggregate query. There is no other defence against silent failure.
