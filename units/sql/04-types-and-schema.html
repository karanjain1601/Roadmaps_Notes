Types and schema design

The schema is the one part of a system that outlives every rewrite. Application code gets replaced; the data stays, and so does every decision encoded in the columns holding it. This chapter is about the decisions that are cheap now and expensive later.

types keys normalisation reversibility

A type is a constraint

Its job is not to store your data — it is to refuse data that should not exist. A column typed date cannot hold "next Tuesday", and that rejection is the feature. Every value the type excludes is a class of bug that can never reach production.

Never store money in a float

Binary floating point cannot represent 0.10 exactly. Sum enough of them and the total drifts, comparisons that should be equal are not, and a reconciliation report is off by pennies in a way nobody can explain. Use numeric/decimal with an explicit scale, or store integer minor units — 1099 rather than 10.99 — and format at the edge. This is a one-line decision at table-creation time and a multi-week migration afterwards.

the timestamp decision, which is really a timezone decision
-- timestamptz stores an absolute instant (as UTC) and converts on the way out.
-- timestamp stores wall-clock digits with no zone — two different events at
-- the same "time" are indistinguishable, and DST makes some values ambiguous.
CREATE TABLE events (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at  timestamptz NOT NULL DEFAULT now(),   -- an instant
    local_date   date        NOT NULL                  -- a calendar day
);

-- Use timestamptz for anything that happened. Use date for anything that is
-- genuinely a calendar concept — a birthday is the same date everywhere, and
-- storing it as an instant introduces a timezone question that has no answer.
--
-- MySQL: DATETIME has no zone; TIMESTAMP converts but has a 2038 limit.
-- SQL Server: datetimeoffset is the closest equivalent to timestamptz.
-- SQLite: no date types at all — store ISO 8601 text or Unix epoch integers.
varchar(255) is cargo cult

The number comes from old MySQL index-prefix limits and means nothing today. In PostgreSQL varchar(n) and text have identical performance, and a length limit chosen arbitrarily will eventually reject a legitimate value — a German company name, a long address, an email at the RFC limit. Use text, and add a CHECK (length(col) <= n) only where the limit is a genuine business rule. That way the limit is documented, intentional, and changeable without rewriting the column.

Keys

Choosing a primary key The trade-offs are real and they pull in different directions. Pick your constraints and see what falls out.

Random UUIDs and index locality

A sequential key means every insert goes into the rightmost index page, which stays in memory — cheap. A random UUID v4 means every insert goes to a random page, so a large table's index cannot be cached and each write becomes a disk read. On a table of tens of millions of rows this is a measurable throughput difference, and it is the main technical argument against v4. UUID v7 fixes it by putting a timestamp in the high bits, giving you distributed generation with sequential locality. If you want UUIDs, want v7.

Surrogate primary key plus a unique constraint on the natural one

The usual right answer. A stable, meaningless id is what foreign keys point at, so nothing breaks when a business value changes. A UNIQUE constraint on the natural key still enforces the real rule. You get referential stability and data integrity, and the two concerns stay separate — which is what makes each of them changeable.

Normalisation, to the point it helps

The formal normal forms are worth knowing once and rarely worth reciting. In practice three rules cover the value.

RuleMeansViolation looks like
1NFOne value per celltags holding 'red,blue,green'; phone1, phone2, phone3
2NFNon-key columns depend on the whole keyIn a table keyed by (order_id, product_id), a customer_name column
3NFNon-key columns depend on nothing but the keycity and country alongside postcode, which determines both
The single test that catches most of it: can the same fact be stored in two places and disagree? If yes, it is not normalised, and eventually it will disagree.
what denormalisation actually costs
-- Denormalised: the customer's name copied onto every order.
CREATE TABLE orders (
    id             bigint PRIMARY KEY,
    customer_id    bigint NOT NULL,
    customer_name  text   NOT NULL,      -- a copy
    amount         numeric(12,2) NOT NULL
);

-- Reads are faster: no join to show an order list. The costs:
--   * a name change must update every order, in one transaction
--   * miss one and the same customer has two names in your data
--   * "which is right" now has no answer the database can give
--   * every consumer must know which copy is authoritative
--
-- Sometimes correct anyway. Two cases where it genuinely is:
--   1. The copy is a HISTORICAL RECORD, not a cache — an invoice should show
--      the name and address as they were at the time. That is not duplication;
--      it is a different fact that happens to look similar.
--   2. Measured performance requires it, the source of truth is unambiguous,
--      and the copy is maintained by a trigger or a materialised view rather
--      than by whichever application code remembers.
"Denormalise for performance" is usually premature

A join on an indexed foreign key is fast — often faster than people assume, because the index is small and cached. Denormalise when you have measured a specific query, tried an index, and found the join genuinely dominant. Doing it upfront trades a certain, permanent correctness risk against a speculative performance gain, and that is a bad trade at design time. Chapter 14 covers the cases where it is the right answer.

The patterns that go wrong

Entity-attribute-value
A generic (entity_id, attribute, value) table so "we can add fields without migrations". You lose types, constraints, indexes, foreign keys and readable queries, and every read becomes a pivot. Where genuine flexibility is needed, a jsonb column gives it with far less damage.
Comma-separated lists
tags = 'red,blue'. Cannot be indexed usefully, cannot be joined, cannot be constrained, and every query needs string splitting. Use a join table, or an array or jsonb column if the engine supports one properly.
Numbered columns
phone1, phone2, phone3. The moment someone needs a fourth, you are altering the table. It is a one-to-many relationship pretending not to be.
Nullable columns encoding a state
Where "if cancelled_at is NULL and shipped_at is not NULL then…" becomes the business logic. An explicit status column with a CHECK makes the state machine visible and constrainable.
Booleans that become three states
is_approved works until you need "pending". Now it is nullable and NULL means pending — undocumented, and chapter 3 applies. An enum from the start costs nothing.
Soft deletes everywhere
A deleted_at column means every query in the system must remember to filter it, and one that forgets shows deleted data. If you need it, enforce it with a view or row-level security rather than discipline.
a table that constrains itself
CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  bigint      NOT NULL REFERENCES customers(id),
    status       text        NOT NULL DEFAULT 'pending',
    amount       numeric(12,2) NOT NULL,
    currency     char(3)     NOT NULL DEFAULT 'GBP',
    placed_at    timestamptz NOT NULL DEFAULT now(),
    shipped_at   timestamptz,
    cancelled_at timestamptz,

    CONSTRAINT status_valid CHECK (
        status IN ('pending','paid','shipped','cancelled','refunded')),
    CONSTRAINT amount_positive CHECK (amount > 0),
    CONSTRAINT currency_iso    CHECK (currency ~ '^[A-Z]{3}$'),

    -- Cross-column rules the type system cannot express:
    CONSTRAINT shipped_after_placed CHECK (shipped_at IS NULL OR shipped_at >= placed_at),
    CONSTRAINT cancelled_xor_shipped CHECK (
        NOT (cancelled_at IS NOT NULL AND shipped_at IS NOT NULL)),
    CONSTRAINT status_matches_timestamps CHECK (
        (status = 'shipped')   = (shipped_at   IS NOT NULL) AND
        (status = 'cancelled') = (cancelled_at IS NOT NULL))
);

-- Every one of these is a bug that can now never reach the table, from any
-- code path, including a migration script someone runs by hand at 2am.
-- Note the last constraint in particular: it stops status and timestamps
-- drifting apart, which is the failure mode of the two-representations design.

Which decisions are expensive to reverse

Cheap to change later

  • Adding a nullable column
  • Adding an index
  • Widening a type — int to bigint is still a rewrite, but a mechanical one
  • Adding a constraint, if the data already complies
  • Adding a table

Expensive, or effectively permanent

  • The primary key type, once other tables reference it
  • Splitting one table into two, once code depends on the shape
  • Changing what a column means without renaming it
  • Adding NOT NULL to a column that already has NULLs nobody can interpret
  • Removing a denormalised copy that consumers now read
  • Timezone semantics, once data is stored ambiguously
Spend the design time on the right-hand column

You do not need the schema to be perfect. You need the irreversible parts to be right, and everything else can be iterated on. Before creating a table, look only at the second list: is the key type right, is the timezone semantics unambiguous, does every column mean exactly one thing? Get those, and the rest is ordinary maintenance rather than an archaeology project.

The short version

  1. A type's job is to refuse data that should not exist. Every value it excludes is a bug that cannot happen.
  2. Never money in a float. numeric with an explicit scale, or integer minor units.
  3. timestamptz for instants, date for calendar days. A birthday is not an instant.
  4. varchar(255) is cargo cult. Use text plus a CHECK where the limit is a real rule.
  5. Surrogate key plus a unique constraint on the natural key — referential stability and integrity, kept separate.
  6. bigint, not int. If you want UUIDs, want v7, because random keys destroy index locality.
  7. The normalisation test that matters: can the same fact be stored twice and disagree?
  8. Spend design time only on the irreversible decisions — key type, timezone semantics, what each column means.
