Chapter 05 · Combining data

Joins

A join is not "looking up related rows". It is a filtered Cartesian product, and holding that definition explains the two things people get wrong: why row counts multiply, and why moving a condition between ON and WHERE changes the answer.

inner and outer fan-out on vs where anti-joins

The definition that explains everything else

Conceptually, a join pairs every row of the left table with every row of the right table, then keeps the pairs where the condition holds. Real engines never do this — they use indexes, hashes and merges (chapter 13) — but the semantics are defined this way, and the semantics are what surprises you.

the same query, three spellings
-- Cross join: every pair. 4 customers × 900 orders = 3,600 rows.
SELECT * FROM customers CROSS JOIN orders;

-- Inner join: every pair, filtered. This is literally the definition.
SELECT * FROM customers c CROSS JOIN orders o WHERE o.customer_id = c.id;

-- Which is what this means. Same result, and the planner treats them alike.
SELECT * FROM customers c JOIN orders o ON o.customer_id = c.id;

-- The old comma syntax. Identical to an inner join, and best avoided: leave
-- out the WHERE and you get a silent cross join rather than a syntax error.
SELECT * FROM customers c, orders o WHERE o.customer_id = c.id;

ON against WHERE

For an inner join they are interchangeable. For an outer join they mean completely different things, and this is the single most common way an outer join silently becomes an inner one.

the difference, spelled out
-- Intent: every customer, with their PAID orders. Customers with no paid
-- orders should still appear, with nothing attached.

-- CORRECT: the condition is part of what counts as a match.
SELECT c.name, o.id, o.amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid';

-- WRONG: the join happens, then WHERE filters the result. For a customer with
-- no paid orders, the LEFT JOIN produced a row with o.status = NULL — and
-- NULL = 'paid' is UNKNOWN, so WHERE drops it (chapter 3).
SELECT c.name, o.id, o.amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';                 -- silently an INNER JOIN

-- The rule:
--   ON    = what counts as a match          (runs during the join)
--   WHERE = which result rows to keep       (runs after)
-- Any WHERE condition on the OUTER side of an outer join destroys the outerness,
-- unless it explicitly allows NULL:
--   WHERE o.status = 'paid' OR o.id IS NULL      -- keeps the unmatched rows
The test for a broken outer join

If a LEFT JOIN query has any WHERE condition on a right-side column that does not account for NULL, it is an inner join wearing a costume. Reviewing for this is quick and catches a lot: find each outer join, then check every WHERE reference to that table. The exception is deliberate — WHERE o.id IS NULL is the anti-join idiom, and it works precisely because it selects the unmatched rows.

Fan-out: the bug that inflates every number

how a total triples
-- An order has 3 line items and 2 shipments.
-- Joining both multiplies: 1 × 3 × 2 = 6 rows for one order.

SELECT o.id,
       o.amount,               -- repeated 6 times
       sum(li.quantity),       -- each line item counted twice  (× shipments)
       count(DISTINCT s.id)    -- this one is fine
FROM orders o
JOIN line_items li ON li.order_id = o.id
JOIN shipments  s  ON s.order_id  = o.id
GROUP BY o.id, o.amount;

-- sum(o.amount) across orders would be TRIPLED here, and nothing in the output
-- says so. The number is plausible, the query runs, the report is wrong.

-- Fix 1 — aggregate before joining. Usually the clearest.
SELECT o.id, o.amount, li.qty, s.n
FROM orders o
LEFT JOIN (SELECT order_id, sum(quantity) AS qty
           FROM line_items GROUP BY order_id) li ON li.order_id = o.id
LEFT JOIN (SELECT order_id, count(*) AS n
           FROM shipments GROUP BY order_id)  s  ON s.order_id  = o.id;

-- Fix 2 — correlated scalar subqueries. Fine for a handful of columns.
SELECT o.id, o.amount,
       (SELECT sum(quantity) FROM line_items li WHERE li.order_id = o.id) AS qty,
       (SELECT count(*)      FROM shipments  s WHERE s.order_id  = o.id) AS n
FROM orders o;

-- Fix 3 — LATERAL, when the subquery needs more than one column back.
DISTINCT does not fix fan-out

The instinct on seeing duplicate rows is to add DISTINCT. It removes the visible duplication and leaves every aggregate wrong, because sum() already consumed the multiplied rows. Worse, it makes the symptom disappear so nobody investigates. If you added DISTINCT to a query with a join and an aggregate, you probably have a fan-out bug. Count the rows before grouping and see whether the number matches what you expect — that check takes ten seconds and is the fastest way to find it.

the ten-second check
-- Before trusting any aggregate over a join, run the ungrouped version:
SELECT count(*) FROM orders o
JOIN line_items li ON li.order_id = o.id
JOIN shipments  s  ON s.order_id  = o.id;
-- 4,182 -- but there are only 900 orders. Something multiplied by ~4.6.

-- Then narrow it down one join at a time:
SELECT count(*) FROM orders o JOIN line_items li ON li.order_id = o.id;  -- 2,700
SELECT count(*) FROM orders o JOIN shipments  s  ON s.order_id  = o.id;  -- 1,400
-- Both fan out. Together they multiply.

EXISTS is a join that cannot multiply
-- WRONG for "customers who have ordered": one row per order, not per customer.
SELECT c.* FROM customers c JOIN orders o ON o.customer_id = c.id;

-- Right, and no DISTINCT needed. EXISTS stops at the first matching row.
SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- The reflex worth building: if you are joining ONLY to test existence, and
-- selecting nothing from the joined table, use EXISTS. It says what you mean
-- and it structurally cannot fan out.

Self-joins and LATERAL

a table joined to itself
-- Each employee with their manager. Same table, two roles, two aliases.
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;    -- LEFT keeps the CEO

-- Self-joins used to be how you compared a row to its neighbours. Window
-- functions (chapter 8) have replaced most of those, and are usually clearer
-- and faster because they need only one pass.
LATERAL — the right side sees the left
-- Each customer's three most recent orders. A plain join cannot express this,
-- because the subquery needs to know which customer it is running for.
SELECT c.name, o.id, o.placed_at, o.amount
FROM customers c
CROSS JOIN LATERAL (
    SELECT id, placed_at, amount
    FROM orders
    WHERE customer_id = c.id        -- c is visible here; that is the whole point
    ORDER BY placed_at DESC
    LIMIT 3
) o;

-- LEFT JOIN LATERAL (...) ON true keeps customers with no orders.
-- SQL Server spells this CROSS APPLY / OUTER APPLY. MySQL 8.0.14+ supports
-- LATERAL. It is the cleanest top-N-per-group when the N is small and there
-- is an index on (customer_id, placed_at DESC).

Practical notes

Index every foreign key

Worth stating on its own because the omission is so common. Creating a foreign key constraint does not create an index in PostgreSQL, SQL Server or Oracle — MySQL/InnoDB is the exception. Without one, every join across it is a full scan of the child table, and every DELETE on the parent scans the child to check the constraint. Adding the index is one line and frequently the largest single performance win available on a schema nobody has tuned.

The short version

  1. A join is a filtered Cartesian product. That definition explains fan-out and the ON/WHERE distinction.
  2. ON defines what matches; WHERE filters the result. For outer joins these are not interchangeable.
  3. Any WHERE condition on the outer side of a LEFT JOIN silently makes it an inner join unless it allows NULL.
  4. Fan-out multiplies rows and corrupts every aggregate, plausibly and silently. Two one-to-many joins multiply each other.
  5. DISTINCT hides fan-out; it does not fix it. Count rows before grouping to detect it.
  6. Joining only to test existence? Use EXISTS — it says what you mean and cannot fan out.
  7. LATERAL is the clean answer to top-N-per-group, because the right side can see the left.
  8. Index every foreign key. Most engines do not do it for you, and it is the commonest missing index there is.
