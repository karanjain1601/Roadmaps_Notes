Subqueries and CTEs

Chapter 1 said every operation returns a relation, so a query can go anywhere a table can. This chapter is that closure property cashed in — and the one place where a readability tool can quietly cost you a hundredfold in performance.

the same question, four ways
-- "Customers who have placed a paid order."

-- IN — fine, and reads well for a short list of values.
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE status = 'paid');

-- EXISTS — the reflex to build. NULL-safe, stops at the first match,
-- and cannot fan out.
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.customer_id = c.id AND o.status = 'paid');

-- JOIN — WRONG here: one row per matching order, not per customer.
SELECT c.* FROM customers c
JOIN orders o ON o.customer_id = c.id AND o.status = 'paid';   -- duplicates

-- JOIN with DISTINCT — works, and does more work than EXISTS: it materialises
-- every match and then deduplicates, instead of stopping at the first.
SELECT DISTINCT c.* FROM customers c
JOIN orders o ON o.customer_id = c.id AND o.status = 'paid';
EXISTS says what you mean

SELECT 1 inside an EXISTS is idiomatic and the column list is genuinely ignored — the engine only checks whether a row was produced. The reason to prefer it over a join is not usually performance (planners often produce the same semi-join either way) but intent: it states that you are testing for existence and not retrieving anything, which means it cannot accidentally multiply rows the way a join can.

Correlated subqueries

A subquery that references a column from the outer query is correlated: conceptually it re-runs for every outer row. That is the readable version and also the dangerous one.

readable, and potentially N executions
-- Correlated: `c.id` comes from the outer query.
SELECT c.name,
       (SELECT count(*) FROM orders o WHERE o.customer_id = c.id) AS n_orders,
       (SELECT max(placed_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c;

-- Two scalar subqueries, each conceptually running once per customer. With an
-- index on orders(customer_id) and a few thousand customers this is fine —
-- planners frequently rewrite it into a hash join anyway. Without the index,
-- it is two full scans of orders per customer.

-- The equivalent that groups once and joins once. Usually the better plan on
-- large tables, and it computes both values in a single pass:
SELECT c.name, coalesce(o.n, 0) AS n_orders, o.last_order
FROM customers c
LEFT JOIN (
    SELECT customer_id, count(*) AS n, max(placed_at) AS last_order
    FROM orders GROUP BY customer_id
) o ON o.customer_id = c.id;
Two or three scalar subqueries is fine; six is a rewrite

Correlated scalar subqueries are the clearest way to attach one or two derived values to each row, and modern planners handle them well when the inner table is indexed on the correlation column. Past about three, you are scanning the same table repeatedly to compute things that one GROUP BY could produce together — and the query becomes harder to read as well as slower. Check the plan (chapter 13); if you see the same table appearing several times, consolidate.

Common table expressions

the same logic, nested and named
-- Nested derived tables. Read from the inside out, which nobody enjoys.
SELECT region, avg(total) FROM (
    SELECT c.region, o.customer_id, sum(o.amount) AS total
    FROM orders o
    JOIN customers c ON c.id = o.customer_id
    WHERE o.status = 'paid'
      AND o.placed_at >= date_trunc('year', current_date)
    GROUP BY c.region, o.customer_id
) t
WHERE total > 500
GROUP BY region;

-- The same thing as named steps. Read top to bottom.
WITH paid_this_year AS (
    SELECT customer_id, amount
    FROM orders
    WHERE status = 'paid'
      AND placed_at >= date_trunc('year', current_date)
),
by_customer AS (
    SELECT c.region, p.customer_id, sum(p.amount) AS total
    FROM paid_this_year p
    JOIN customers c ON c.id = p.customer_id
    GROUP BY c.region, p.customer_id
)
SELECT region, avg(total) AS avg_value
FROM by_customer
WHERE total > 500
GROUP BY region;

Same result, same plan on most engines, dramatically easier to review — each step has a name that says what it is, and you can run any prefix of the query to see intermediate output while debugging.

The optimisation-fence trap

Historically PostgreSQL materialised every CTE: it computed the whole thing, stored it, and could not push a filter from the outer query down into it. A CTE producing ten million rows that the outer query filters to fifty would compute all ten million first. That changed in PostgreSQL 12 — CTEs referenced once are now inlined by default — but older versions, and other engines with the same behaviour, are still in service. If a CTE-based query is unexpectedly slow, rewrite one step as a derived table and compare; that is the fastest way to identify the fence.

controlling it explicitly
-- Postgres 12+: force the old behaviour when you want it.
WITH expensive AS MATERIALIZED (
    SELECT customer_id, sum(amount) AS total
    FROM orders GROUP BY customer_id
)
SELECT * FROM expensive e1 JOIN expensive e2 ON …;
-- Worth forcing when the CTE is referenced several times and is expensive to
-- compute — otherwise it may be evaluated once per reference.

WITH cheap AS NOT MATERIALIZED (…)
-- Forces inlining, letting the planner push filters down. The default for a
-- single-reference, side-effect-free CTE.

Recursive CTEs

A recursive CTE, one iteration at a time Walking an org chart. Step through and watch the working table feed itself.
the shape of every recursive CTE
WITH RECURSIVE subordinates AS (
    -- ANCHOR: the starting rows. Runs once.
    SELECT id, name, manager_id, 1 AS depth, name::text AS path
    FROM employees
    WHERE id = 1

    UNION ALL

    -- RECURSIVE TERM: joins the previous iteration's output to the table.
    -- Runs repeatedly until it produces no new rows.
    SELECT e.id, e.name, e.manager_id, s.depth + 1, s.path || ' > ' || e.name
    FROM employees e
    JOIN subordinates s ON e.manager_id = s.id      -- s = the working table
    WHERE s.depth < 20                              -- always bound the depth
)
SELECT repeat('  ', depth - 1) || name AS org, depth, path
FROM subordinates
ORDER BY path;

-- How it actually runs:
--   1. evaluate the anchor -> working table
--   2. evaluate the recursive term against the working table
--   3. append the results, and make them the new working table
--   4. repeat until step 2 returns nothing
--
-- "subordinates" inside the recursive term does NOT mean everything found so
-- far. It means only the rows the PREVIOUS iteration produced. That is the
-- single most misunderstood part, and the demo above shows it directly.
UNION ALL, and always bound the depth

Use UNION ALL, not UNION: the deduplication that UNION performs is usually unnecessary and always expensive. But that means a cycle in the data — an employee who is transitively their own manager, a category loop from a bad import — produces an infinite loop that consumes memory until something dies. Two defences: a depth < n guard, which is cheap and catches everything, and a path array with NOT (e.id = ANY(path)), which detects genuine cycles precisely. Use the depth guard always; add the path check when cycles are plausible.

cycle-safe, and walking upward
-- Detecting cycles rather than merely surviving them.
WITH RECURSIVE tree AS (
    SELECT id, name, manager_id, ARRAY[id] AS path, false AS cycle
    FROM employees WHERE manager_id IS NULL

    UNION ALL

    SELECT e.id, e.name, e.manager_id, t.path || e.id, e.id = ANY(t.path)
    FROM employees e
    JOIN tree t ON e.manager_id = t.id
    WHERE NOT t.cycle                       -- stop expanding once one is found
)
SELECT * FROM tree WHERE cycle;             -- report the loops

-- Walking UP instead of down: swap which side of the join is correlated.
WITH RECURSIVE chain AS (
    SELECT id, name, manager_id FROM employees WHERE id = 7
    UNION ALL
    SELECT e.id, e.name, e.manager_id
    FROM employees e
    JOIN chain c ON c.manager_id = e.id     -- note: reversed
)
SELECT * FROM chain;                        -- Rossi, their manager, and so on

Adjacency lists are not the only option

manager_id pointing at the parent is simple and makes insertion trivial, but every ancestor or descendant query needs recursion. If your workload is read-heavy over deep hierarchies, consider a materialised path (a text or array column holding the full ancestry, indexed for prefix search) or a closure table (one row per ancestor-descendant pair). Both make subtree queries a simple indexed lookup and make writes more expensive. Recursion is the right default; these are what you reach for when the profile says so.

Data-modifying CTEs

multiple statements, one atomic pass
-- Postgres: move rows to an archive and delete them, in one statement.
WITH moved AS (
    DELETE FROM orders
    WHERE placed_at < now() - interval '7 years'
    RETURNING *
)
INSERT INTO orders_archive SELECT * FROM moved;

-- Two things to know:
--   * all sub-statements see the SAME snapshot of the database, so a later
--     one does not observe an earlier one's changes
--   * execution order between them is not guaranteed, so do not write two
--     that modify the same rows and expect a particular sequence
--
-- Supported in PostgreSQL. SQL Server has OUTPUT clauses; MySQL has neither.

The short version

  1. A subquery can go anywhere a relation can — SELECT, FROM, WHERE, JOIN LATERAL, HAVING.
  2. EXISTS over a join when you are only testing existence: it states the intent and cannot multiply rows.
  3. A correlated subquery references the outer row and conceptually runs per row. Two or three is fine; six is a rewrite.
  4. CTEs are for readability — named steps, top-to-bottom, debuggable a step at a time.
  5. Watch the optimisation fence: on older PostgreSQL and some engines a CTE is materialised and filters cannot be pushed into it.
  6. A recursive CTE is anchor UNION ALL recursive term, and the recursive term sees only the previous iteration's rows.
  7. Always bound the depth. UNION ALL plus a cycle in the data is an infinite loop.
  8. Adjacency lists need recursion; materialised paths and closure tables trade write cost for cheap subtree reads.
