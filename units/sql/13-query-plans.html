Reading a query plan

Chapter 1 said you describe the result and the planner chooses the route. This is how you find out what it chose, and — more usefully — where its estimate of your data diverged from reality.

explain analyze node types estimates

EXPLAIN and EXPLAIN ANALYZE

the two commands, and the difference that matters
-- EXPLAIN: the plan, with estimates. Does not run the query. Instant and safe.
EXPLAIN SELECT …;

-- EXPLAIN ANALYZE: RUNS the query and reports actual timings and row counts.
-- This is the one you want, and it really does execute — including writes.
EXPLAIN ANALYZE SELECT …;

-- Always wrap a write in a transaction you roll back:
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'expired' WHERE …;
ROLLBACK;

-- The full form, worth using by default:
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT) SELECT …;
--   ANALYZE   actual rows and time
--   BUFFERS   pages read from cache vs disk  <- the most under-used option
--   VERBOSE   output columns per node
--   SETTINGS  non-default planner settings, which explain odd choices

-- MySQL: EXPLAIN ANALYZE (8.0.18+), or EXPLAIN FORMAT=JSON.
-- SQL Server: SET STATISTICS IO, TIME ON, plus the actual execution plan.
Estimated against actual is the whole skill

Plain EXPLAIN shows what the planner believes. EXPLAIN ANALYZE shows what happened. The gap between them is where nearly every bad plan comes from: the planner estimated 12 rows, got 400,000, and chose a nested loop that would have been perfect for 12. Find the node with the largest ratio between estimated and actual rows — that is almost always the cause, and fixing the estimate fixes the plan without you having to outsmart the optimiser.

-- Reading rules:
--   * the MOST INDENTED nodes run FIRST; results flow upward
--   * cost=A..B  A is the startup cost, B the total. Arbitrary units
--   * rows= is per LOOP, not in total. Multiply by loops for the real figure
--   * actual time=A..B  A is time to the first row, B to the last
--   * a node's time INCLUDES its children, so subtract to get its own cost
--   * "Rows Removed by Filter" is often the most informative line in the plan

A nested loop with a bad estimate is the classic catastrophic plan

The planner estimates 5 outer rows and chooses a nested loop: 5 index lookups, microseconds. The real answer is 500,000 rows, so it performs 500,000 index lookups and the query takes twenty minutes. The plan is not wrong for the data the planner expected — it is wrong about the data. This is why the estimate/actual ratio is the first thing to look at: a nested loop with loops=500000 where rows=5 was estimated is the signature, and it is visible at a glance once you know to look.

CauseSymptomFix

Correlated columnsEstimate is the product of two independent selectivities, but they are not independentCREATE STATISTICS … (dependencies) in Postgres 10+
Skewed distributionFine for most values, terrible for the one that is 40% of the tableRaise the statistics target on that column
ExpressionsNo statistics exist for lower(email)Create an expression index — it carries statistics too
Function calls in predicatesThe planner assumes a fixed selectivityMark functions STABLE, or restructure
Parameter sniffingA prepared plan built for one parameter value, reused for a very different oneForce a re-plan, or use a generic plan
correlated columns — the estimate bug worth knowing
-- The planner assumes columns are independent, so it multiplies selectivities:
--     P(city = 'Manchester') × P(postcode LIKE 'M1%')
-- But postcode DETERMINES city, so the true selectivity is the smaller of the
-- two, not the product. The estimate comes out ~1000× too low, and a nested
-- loop is chosen for what is actually a large result.

CREATE STATISTICS addr_stats (dependencies, ndistinct)
    ON city, postcode FROM addresses;
ANALYZE addresses;

-- Common correlated pairs worth checking: (country, city), (status,
-- cancelled_at), (product, category), (year, quarter). Anywhere one column
-- functionally determines another, the default estimate is wrong.

A method for a slow query

1 · EXPLAIN (ANALYZE, BUFFERS)Twice — the first run warms the cache and its timings mislead
↓
2 · Find the node with the most time of its ownSubtract children's time. Not the top node — that one includes everything
↓
3 · Check its estimated against actual rowsA ratio over ~100 means the plan was chosen for imaginary data
↓
4 · Look for rows discarded"Rows Removed by Filter" points straight at a missing index column
↓
5 · Check buffersHeavy read rather than hit means the working set does not fit in memory
↓
6 · Change one thing, re-run, compareAn index, an ANALYZE, a rewritten predicate. One at a time
Paste the plan into a visualiser

Text plans are hard to read past about fifteen nodes, and the arithmetic of subtracting child times is tedious and error-prone. Tools like explain.depesz.com and explain.dalibo.com take the raw output and highlight the expensive node, the bad estimates and the discarded rows automatically. Use one. Reading plans by eye is a skill worth having and not a skill worth demonstrating on a fifty-node plan at midnight. Do sanitise first if the plan contains real values.

Nudging the planner

Fix the cause

  • ANALYZE the table
  • Raise the statistics target on a skewed column
  • Create extended statistics for correlated columns
  • Add the index the plan is asking for
  • Rewrite a predicate to be SARGable (chapter 12)
  • Raise work_mem for the session running a big sort

Force the outcome

  • SET enable_nestloop = off — a sledgehammer, and session-wide
  • Optimiser hints (MySQL, Oracle, and via pg_hint_plan)
  • OFFSET 0 or a CTE as an optimisation barrier
  • Freezing a plan

All of these work and all of them mean the plan stops adapting when your data changes. Use them to confirm a diagnosis, then fix the cause.

Test on production-shaped data

A plan built against ten thousand development rows tells you almost nothing about a hundred million production rows: the planner's choices are driven by table sizes and value distributions, and both are different. Sequential scans that are correct locally become disasters at scale, and indexes that look pointless locally are essential. Where you cannot use production data, at least generate the right volumes and the right skew — a column where one value is 40% of the table behaves nothing like a uniformly distributed one.

The short version

  1. EXPLAIN shows beliefs; EXPLAIN ANALYZE shows what happened. It really runs the query — wrap writes in a rollback.
  2. Read the tree innermost first. Times include children, and rows= is per loop.
  3. The first thing to look at is the ratio of estimated to actual rows. That gap is where bad plans come from.
  4. A nested loop with a huge loops= is the classic catastrophic plan, and it is a data-estimate problem, not a join-type problem.
  5. "Rows Removed by Filter" points straight at a missing index column, and is often the most useful line in a plan.
  6. A sequential scan is frequently correct. Judge it by selectivity and table size, not by reflex.
  7. Estimates go wrong from stale statistics, correlated columns and skew — all fixable without touching the query.
  8. Fix the cause, do not force the plan. Forced plans stop adapting the moment your data changes.
