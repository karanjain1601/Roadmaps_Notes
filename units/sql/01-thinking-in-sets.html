Thinking in sets

Almost everyone learns SQL as syntax bolted onto programming habits they already have, and then hits a ceiling. The ceiling is not knowledge of clauses — it is still thinking in loops. This chapter is the shift.

declarative relations sets not loops what to expect

You describe the result, not the route

In most languages you write the steps. In SQL you write a description of the answer, and a query planner decides how to get it — which indexes to use, which table to read first, whether to sort or hash. The same query can execute completely differently on Tuesday than it did on Monday because the data changed shape.

Imperative

total = 0
for order in orders:
  if order.status == 'paid':
    total += order.amount

You specified the loop, the order, the accumulator. The machine does exactly that.

Declarative

SELECT sum(amount)
FROM orders
WHERE status = 'paid';

You specified the answer. Whether it scans, seeks an index, or runs across eight cores is not your decision.

The practical consequence

Because you do not control execution, you cannot optimise SQL by rewriting it the way you would rewrite a loop. Two queries that look very different often produce identical plans, and two that look nearly identical can differ by a factor of a thousand. The only way to know is to ask the planner — which is chapter 13, and which is why that chapter exists at all.

What a relation actually is

A table is an unordered set of rows, each row a set of named, typed values. Three words in that sentence do real work.

PropertyConsequence
UnorderedThere is no "first row" and no natural order. A query without ORDER BY may return rows in any order, and that order can change between runs with no schema change
Named columnsYou address data by name, not position. SELECT * breaks this and is why it is discouraged in application code
TypedThe database rejects values that do not fit. This is a feature — chapter 4
Set-valuedEvery operation takes relations and returns a relation. That closure is what lets queries nest arbitrarily
There is no default order, and relying on one is a bug that waits

A query without ORDER BY frequently returns rows in insertion order on a small table, because a sequential scan happens to read them that way. Then the table grows, the planner switches to an index scan or a parallel scan, and the order changes — in production, months later, with no code change. If order matters, say so. Every time.

Strictly, SQL tables are multisets rather than true sets: duplicate rows are allowed unless a constraint forbids them. That divergence from the pure relational model is the source of several oddities later — notably why UNION and UNION ALL are different operations, and why COUNT(DISTINCT x) exists.

N+1 is the loop habit, wearing a costume

Fetch a list, then loop over it fetching one related row at a time. One hundred orders becomes one hundred and one queries. Each is fast; the round trips are not. At 0.5ms of network latency per call, a page that should take 2ms takes 50ms, and at a thousand rows it takes half a second. This is the most common performance problem in application code that talks to a database, it is invisible in local development where latency is near zero, and it is entirely a symptom of thinking in loops. Chapter 14 covers the fixes; the cure starts here.

The operations, and why they compose

Every SQL operation takes one or more relations and returns a relation. Nothing else. That closure property is what allows a subquery anywhere a table can go, and it is worth seeing the operations named plainly.

OperationDoesSQL
SelectionKeeps some rowsWHERE
ProjectionKeeps some columns, or computes new onesThe SELECT list
JoinCombines two relations on a conditionJOIN … ON
AggregationCollapses groups of rows into one row eachGROUP BY
Union, intersect, exceptSet arithmetic on two relations of the same shapeUNION, INTERSECT, EXCEPT
OrderingImposes an order on the outputORDER BY — the one operation that leaves the relational model
Six operations. Everything in chapters 2 through 8 is a combination of these, and the closure property is why they combine without limit.
closure in practice — a relation wherever a table can go
-- A subquery in FROM: the inner query produces a relation, so it can be joined.
SELECT c.name, r.total
FROM customers c
JOIN (
    SELECT customer_id, sum(amount) AS total
    FROM orders
    WHERE status = 'paid'
    GROUP BY customer_id
) r ON r.customer_id = c.id;

-- Exactly the same thing, named up front. Easier to read, easier to extend,
-- and on most planners identical in performance. Chapter 7.
WITH revenue AS (
    SELECT customer_id, sum(amount) AS total
    FROM orders
    WHERE status = 'paid'
    GROUP BY customer_id
)
SELECT c.name, r.total
FROM customers c
JOIN revenue r ON r.customer_id = c.id;

The dialects

SQL is a standard that every implementation deviates from. The core — SELECT, joins, aggregation, window functions — is portable. The edges are not, and knowing which is which saves time.

AreaPortable?Note
SELECT, WHERE, JOIN, GROUP BYYesLearn once
Window functions, CTEsMostlyWidely supported now; recursive CTE syntax varies slightly
UpsertNoON CONFLICT in Postgres, ON DUPLICATE KEY in MySQL, MERGE elsewhere

LIMITNoLIMIT, TOP, FETCH FIRST — three spellings

The single question that changes how you write SQL

Before writing a loop that touches the database, ask: "can this be one statement?" Usually it can. Deduplicating records, backfilling a column, finding rows in one table missing from another, computing a per-group ranking — all of these are commonly written as a fetch-and-loop and all are a single query. Getting into the habit of asking is worth more than memorising any particular clause.

Where SQL is the wrong tool

An honest chapter has to include this, because the reverse enthusiasm is also a failure mode.

Do not push into the database

  • Business logic that changes weekly — it is harder to test and deploy than application code
  • Anything genuinely procedural, with loops and branching over external state
  • Calling out to other services
  • Heavy computation that would occupy a shared resource everything else depends on
  • Logic that needs to be readable by people who do not write SQL

Do push into the database

  • Filtering, joining, sorting, aggregating — always
  • Invariants that must hold regardless of which service writes
  • Anything that would otherwise transfer rows you will discard
  • Set-shaped work: deduplication, backfills, reconciliation
  • Anything correctness-critical under concurrency

The short version

  1. SQL is declarative: you describe the result and a planner chooses the route. You cannot optimise it by rewriting it like a loop.
  2. A table is an unordered multiset of typed, named rows. Every word there has consequences.
  3. There is no default row order. Relying on one is a bug that surfaces months later.
  4. Six operations — selection, projection, join, aggregation, set arithmetic, ordering — and every one returns a relation, which is why they nest without limit.
  5. N+1 is the loop habit in disguise, invisible locally and expensive in production.
  6. The core language is portable; upserts, string and date functions, LIMIT and isolation behaviour are not.
  7. Before writing a loop against the database, ask "can this be one statement?" Usually it can.
  8. Push set-shaped work and invariants into the database. Keep volatile business logic out of it.
