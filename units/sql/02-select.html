SELECT and the order things happen

SQL is written in one order and evaluated in another. That single fact explains a whole cluster of apparent inconsistencies people work around for years without ever seeing the pattern.

clauses logical order aliases distinct

Written order against logical order

You write SELECT first. It is evaluated almost last. Here are both orders side by side — the right-hand column is the one that explains SQL's behaviour.

You writeIt happensWhat that step does
1. SELECT5Computes expressions, applies column aliases
2. FROM / JOIN1Assembles the source rows
3. WHERE2Discards rows, before any grouping
4. GROUP BY3Collapses rows into groups
5. HAVING4Discards groups, after aggregation
6. ORDER BY7Sorts the output — after aliases exist
7. LIMIT / OFFSET8Takes a slice of the sorted result
(DISTINCT)6Removes duplicate output rows, after SELECT
This is the logical order — the semantics the language guarantees. The planner is free to execute in any order that produces the same answer, and usually does (chapter 13).

What the order explains

four rules that look arbitrary and are not
-- 1. You cannot use a SELECT alias in WHERE. WHERE runs at step 2, the alias
--    is created at step 5, so it does not exist yet.
SELECT amount * 1.2 AS gross
FROM orders
WHERE gross > 100;                      -- ERROR: column "gross" does not exist

SELECT amount * 1.2 AS gross
FROM orders
WHERE amount * 1.2 > 100;               -- repeat the expression, or use a subquery


-- 2. You CAN use it in ORDER BY. That runs at step 7, after the alias exists.
SELECT amount * 1.2 AS gross
FROM orders
ORDER BY gross DESC;                    -- fine


-- 3. WHERE cannot reference an aggregate. Aggregates are computed at step 3;
--    WHERE ran at step 2.
SELECT customer_id, sum(amount)
FROM orders
WHERE sum(amount) > 500                 -- ERROR: aggregate not allowed here
GROUP BY customer_id;

SELECT customer_id, sum(amount)
FROM orders
GROUP BY customer_id
HAVING sum(amount) > 500;               -- HAVING is step 4 — after aggregation


-- 4. WHERE filters rows, HAVING filters groups — and the difference is not style.
SELECT customer_id, sum(amount) AS total
FROM orders
WHERE status = 'paid'                   -- drops unpaid ROWS before summing
GROUP BY customer_id
HAVING sum(amount) > 500;               -- drops small-total GROUPS after summing
-- Swap those conditions and you get a different, wrong answer.
One diagram, four rules, no memorisation

Every one of those is the same fact: a clause can only see what earlier steps have produced. Once you hold the logical order, you stop looking these up. It also tells you where to put a condition — if it concerns individual rows, it belongs in WHERE; if it concerns a group's aggregate, it belongs in HAVING; and putting it in the wrong one is usually a correctness bug rather than a syntax error.

MySQL is more permissive, and that is not a kindness

MySQL allows a SELECT alias in HAVING, and historically allowed GROUP BY queries selecting columns that are neither grouped nor aggregated — returning an arbitrary value from the group with no warning. Modern versions disable that by default via ONLY_FULL_GROUP_BY, but plenty of legacy code depends on it and plenty of tutorials still teach it. If a query works in MySQL and errors in Postgres, this is usually why — and Postgres is usually right.

CASE — the conditional you will use constantly
SELECT
    id,
    CASE
        WHEN amount >= 1000 THEN 'enterprise'
        WHEN amount >= 100  THEN 'standard'
        ELSE 'small'
    END AS tier,
    -- CASE inside an aggregate is the idiom for conditional counting.
    -- count() ignores NULL, so the ELSE arm is deliberately omitted.
    count(*) FILTER (WHERE status = 'paid') AS paid_count      -- Postgres
FROM orders
GROUP BY id, amount;

-- The portable version of FILTER, which works everywhere:
SELECT
    count(CASE WHEN status = 'paid'     THEN 1 END) AS paid,
    count(CASE WHEN status = 'refunded' THEN 1 END) AS refunded,
    sum(CASE WHEN status = 'paid' THEN amount ELSE 0 END)      AS paid_revenue
FROM orders;

-- Note the difference between the two aggregates: count() needs NULL for the
-- non-matching case (so no ELSE), sum() needs 0. Getting that backwards is a
-- common quiet bug — count(CASE ... ELSE 0 END) counts every row.

SELECT *

Fine for

  • Exploring a table interactively
  • EXISTS subqueries, where the columns are never read
  • count(*), which does not read columns at all

A problem in application code

  • Transfers columns you do not need, including large text and JSON
  • Prevents index-only scans — the index no longer covers the query (chapter 12)
  • Breaks when someone adds or reorders a column
  • Hides which columns a query actually depends on, making schema changes risky
  • Ambiguous column names after a join

DISTINCT

what DISTINCT is, and what it usually means
-- DISTINCT applies to the WHOLE row of the output, not to one column.
SELECT DISTINCT customer_id, status FROM orders;
-- distinct PAIRS, not distinct customers.

-- DISTINCT is not a function, so this does not mean what it looks like:
SELECT DISTINCT (customer_id), status FROM orders;   -- identical to the above;
                                                     -- the parens do nothing

-- Postgres has DISTINCT ON: first row per group, by the ORDER BY.
SELECT DISTINCT ON (customer_id) customer_id, id, amount
FROM orders
ORDER BY customer_id, amount DESC;      -- each customer's largest order

-- Portable equivalent, and usually clearer (chapter 8):
SELECT customer_id, id, amount FROM (
    SELECT *, row_number() OVER (PARTITION BY customer_id
                                 ORDER BY amount DESC) AS rn
    FROM orders
) t WHERE rn = 1;
DISTINCT is usually a symptom, not a solution

When you add DISTINCT to make duplicates go away, stop and ask where they came from. Nine times in ten the answer is a join that multiplied rows (chapter 5), and DISTINCT is hiding the multiplication rather than fixing it. That matters because the same multiplication is silently corrupting any sum() or count() in the query, and DISTINCT will not save those. Find the join, fix the join.

ORDER BY, LIMIT and the trap in between

non-deterministic pagination
-- BROKEN: if several orders share a created_at, their relative order is
-- undefined — so a row can appear on both page 1 and page 2, and another
-- can appear on neither.
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 20;

-- FIXED: break every tie with something unique.
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 20;

-- Two more things about this query, both covered later:
--   * OFFSET makes the database produce and discard the skipped rows, so
--     page 5000 is slow. Keyset pagination fixes it (chapter 14).
--   * NULLs sort last by default in Postgres for DESC and first for ASC.
--     Other engines differ. Say NULLS FIRST or NULLS LAST if it matters.

Writing queries people can read

the conventions worth adopting
SELECT
    c.id                                AS customer_id,
    c.name,
    count(*)                            AS order_count,
    sum(o.amount)                       AS lifetime_value,
    max(o.created_at)                   AS last_order_at
FROM customers        AS c
JOIN orders           AS o  ON o.customer_id = c.id
WHERE o.status = 'paid'
  AND o.created_at >= date_trunc('year', current_date)
GROUP BY c.id, c.name
HAVING count(*) >= 3
ORDER BY lifetime_value DESC
LIMIT 50;

-- What is doing the work here:
--   * one clause per line, so a diff shows what actually changed
--   * conditions on their own lines with the AND leading, so adding or
--     commenting out one is a single-line edit
--   * table aliases that mean something (c, o) rather than t1, t2
--   * every column qualified once there is more than one table — otherwise
--     adding a column to either table can make the query ambiguous overnight
--   * aliases on every computed column, because the consumer needs a name
Qualify columns as soon as there are two tables

An unqualified status works fine until someone adds a status column to the other table, at which point the query either errors or — worse, in some engines — silently resolves to the other one. Qualifying every column costs two characters and removes a whole class of future breakage. It also makes the query readable by someone who does not know the schema, which is usually you in six months.

The short version

  1. SQL is written SELECT … FROM … WHERE and evaluated FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
  2. That single order explains why aliases work in ORDER BY and not in WHERE, and why aggregates need HAVING.
  3. WHERE filters rows before grouping; HAVING filters groups after. Choosing wrong is a correctness bug, not a style one.
  4. Inside aggregates, count() wants NULL for non-matches and sum() wants 0 — getting that backwards counts every row.
  5. SELECT * is fine interactively and a liability in application code: wasted transfer, no index-only scans, breaks on schema change.
  6. DISTINCT is usually a symptom of a join that multiplied rows — and it will not fix the aggregates that multiplication corrupted.
  7. Always break ties in ORDER BY, or paginated results duplicate and drop rows.
  8. Qualify every column once there are two tables, and put one clause per line.
