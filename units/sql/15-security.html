Security

Injection has a complete, well-understood fix that costs nothing, and it remains one of the most exploited vulnerabilities in software. This chapter is about applying it properly, and about the layers that limit the damage when something else goes wrong.

parameterisation least privilege row-level security sensitive data

Why injection happens

The same reason as chapter 10 of the prompt-engineering world: code and data share one channel. When you build a query by concatenating strings, the database receives one blob of text and has no way to know which parts you intended as instructions and which as values.

the mechanism, schematically
# Vulnerable: the value becomes part of the query text.
q = "SELECT * FROM users WHERE email = '" + user_input + "'"

# The database parses one string. If user_input contains a quote character,
# the value ends early and everything after it is parsed as SQL — a new
# condition, a chained statement, whatever the attacker wrote. The engine is
# behaving correctly; it was handed a different query from the one intended.

# Safe: the value travels in a separate channel and is never parsed as SQL.
cur.execute("SELECT * FROM users WHERE email = %s", (user_input,))

# The driver sends the query text and the parameters separately. The database
# plans the statement first, then binds the value into a placeholder. There is
# no string in which a quote could terminate anything, so there is nothing to
# escape and nothing to get wrong.
Parameterisation is a structural fix, not a filter

This is the distinction that matters. Escaping and input validation try to detect dangerous content — and detection can always be wrong, because the space of encodings, character sets and edge cases is unbounded. Parameterisation removes the possibility: the value is never part of the parsed statement, so there is nothing for it to break out of. It is not a mitigation that reduces risk; it eliminates the class. That is why "we sanitise inputs" is not an acceptable answer and "we use parameterised queries everywhere" is.

Identifiers cannot be parameters, and this is where injection survives

A placeholder stands in for a value. It cannot stand in for a table name, a column name, or the direction of a sort, because those are part of the query's structure and the statement must be parsed before values are bound. So dynamic sorting and dynamic table selection cannot be parameterised — and that is exactly where injection lives in codebases that otherwise use placeholders correctly. The fix is an allowlist: map the user's input to a fixed set of known-good identifiers in your code, and reject anything else. Never pass the string through, even quoted.

the allowlist pattern
SORTABLE = {
    "date":     "o.placed_at",
    "amount":   "o.amount",
    "customer": "c.name",
}
DIRECTIONS = {"asc": "ASC", "desc": "DESC"}

def list_orders(sort: str, direction: str, status: str, limit: int):
    # Look up, never interpolate. An unknown key falls back to a default
    # rather than reaching the database.
    col = SORTABLE.get(sort, "o.placed_at")
    dir_ = DIRECTIONS.get(direction, "DESC")
    limit = min(max(int(limit), 1), 200)          # clamp, do not trust

    sql = f"""
        SELECT o.id, o.amount, c.name
        FROM orders o JOIN customers c ON c.id = o.customer_id
        WHERE o.status = %s
        ORDER BY {col} {dir_}, o.id DESC
        LIMIT {limit}
    """
    return cur.execute(sql, (status,))

# The f-string is safe here ONLY because col, dir_ and limit can no longer be
# arbitrary strings — they are dictionary values and a bounded integer. The
# status value still goes through a placeholder, because it can be anything.
#
# Reviewing rule: an f-string in a query is not automatically wrong, but every
# interpolated name must be traceable to a literal in your source.

optional filters without string-building values
def search(status=None, min_amount=None, since=None):
    clauses, params = ["1 = 1"], []

    if status is not None:
        clauses.append("status = %s");       params.append(status)
    if min_amount is not None:
        clauses.append("amount >= %s");      params.append(min_amount)
    if since is not None:
        clauses.append("placed_at >= %s");   params.append(since)

    sql = "SELECT * FROM orders WHERE " + " AND ".join(clauses) + " ORDER BY id DESC"
    return cur.execute(sql, params)

# The query TEXT is assembled from literals in this file. Only values go into
# params. That is the invariant to hold, and it is easy to check in review:
# no variable ever appears inside the SQL string itself.

Least privilege

the application should not own its schema
-- Most applications connect as the user that owns every table, which means a
-- successful injection can DROP them. Separate the roles.

CREATE ROLE app_owner NOLOGIN;                   -- owns the schema
CREATE ROLE app_rw LOGIN PASSWORD '…';           -- what the application uses
CREATE ROLE app_ro LOGIN PASSWORD '…';           -- reports, analytics, replicas

ALTER SCHEMA public OWNER TO app_owner;

GRANT USAGE ON SCHEMA public TO app_rw, app_ro;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_rw;
GRANT SELECT                          ON ALL TABLES IN SCHEMA public TO app_ro;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_rw;

-- Future tables too, or the next migration silently creates something the
-- application cannot read.
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO app_ro;

-- Revoke the default that surprises people: PUBLIC can create objects in the
-- public schema on older Postgres versions.
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- Migrations run as app_owner, from CI, with credentials the application
-- never has. Then no injection, however severe, can alter the schema.

Row-level security

multi-tenancy the database enforces
-- The usual approach is "every query includes WHERE tenant_id = ?" — which
-- holds until one query forgets, and then one customer sees another's data.
-- RLS moves the rule below the application, where it cannot be forgotten.

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
    USING       (tenant_id = current_setting('app.tenant_id')::bigint)  -- reads
    WITH CHECK  (tenant_id = current_setting('app.tenant_id')::bigint); -- writes

-- Set the tenant per connection, per request, as a parameterised call:
SET LOCAL app.tenant_id = '42';     -- LOCAL = resets at end of transaction

-- Now every query on orders is filtered automatically. A query that forgets
-- its tenant filter returns nothing rather than everything, which is the
-- correct direction for that mistake to fail in.

-- Two things to get right:
--   * WITH CHECK as well as USING, or a tenant can INSERT rows attributed to
--     another tenant even though they cannot read them
--   * the table owner BYPASSES RLS by default. The application must connect
--     as a role that is not the owner, or FORCE ROW LEVEL SECURITY
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
RLS with a connection pool needs care

SET LOCAL is scoped to the transaction, which is what makes it safe with pooling — the setting cannot leak to the next request that borrows the connection. Plain SET persists for the session and will leak, giving one tenant another's context. If you use RLS behind PgBouncer in transaction mode, verify this explicitly with a test that runs two requests for different tenants through the same pooled connection. It is exactly the kind of bug that never appears in development, where the pool has one connection per request.

a redacting view, so analysts get data without identities
CREATE VIEW customers_safe
WITH (security_barrier = true) AS      -- stops predicate pushdown leaking rows
SELECT
    id,
    region,
    created_at,
    -- keep the shape, lose the identity
    left(md5(email), 12)          AS email_hash,
    substring(postcode from 1 for 3) AS postcode_area,
    date_trunc('year', birth_date)   AS birth_year
FROM customers;

REVOKE ALL ON customers      FROM analyst;
GRANT SELECT ON customers_safe TO analyst;

-- The analyst can group, join and count. They cannot read an email address,
-- and no query they write — however creative — can, because the grant does
-- not exist. This is stronger than a policy document.
--
-- Postgres 15+ also has native dynamic masking via RLS column policies in
-- some distributions; the view approach works everywhere.
Errors and logs leak too

A database error returned to the user reveals table names, column names and sometimes values — everything an attacker needs to make the next attempt more precise. Catch database exceptions at the boundary, log the detail with a correlation id, and return something generic. Separately: check that your query logs and your APM traces are not recording parameter values, or every password reset token and personal detail that passed through a query is now in a log aggregator with much weaker access control than the database.

The rest of the surface

  • TLS on every connection, including inside the private network. sslmode=verify-full, not require — the weaker setting encrypts without authenticating the server.
  • No database on a public address. Private networking or a bastion, and a firewall that defaults to deny.
  • Rotate credentials, and prefer short-lived ones issued by a secrets manager or IAM.
  • Separate credentials per service, so a compromise is scoped and an audit log identifies the source.
  • Encrypt backups, and test restoring them. An untested backup is a hope.
  • Audit privileged access. Who connected as an admin role, when, and what they ran.
  • Patch. Database CVEs are less frequent than application ones and considerably more serious.
  • Statement timeouts (chapter 10) also limit how much damage a hostile query can do.
Assume the application will be compromised

Every control after parameterisation exists for the case where something else failed — a dependency, a deserialisation bug, a leaked credential, an insider. The question to design against is not "can they inject SQL" but "if they can run arbitrary queries as the application, what do they get?" With an owner-level connection: everything, including the ability to destroy it. With a restricted role, RLS, hashed tokens and no card data, the same compromise yields a much smaller incident. That difference is the whole return on this chapter's second half.

The short version

  1. Injection exists because code and data share one channel. Parameterisation separates them structurally.
  2. Parameterisation eliminates the class; escaping only reduces it. "We sanitise inputs" is not an answer.
  3. Identifiers cannot be parameters — sort columns, table names, directions. Use an allowlist that maps input to literals in your source.
  4. The reviewable invariant: no variable ever appears inside the SQL string itself, only in the parameter list.
  5. The application should not own its schema. Migrations run as a separate role from CI.
  6. RLS moves tenant isolation below the application, so a forgotten filter returns nothing rather than everything. Use SET LOCAL, and FORCE it for the owner.
  7. Hash tokens and passwords; do not store card numbers; give analysts a redacting view rather than a policy.
  8. Design for the compromise: "if they can run any query as the app, what do they get?"
