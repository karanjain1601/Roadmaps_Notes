Chapter 08 · Combining data

Window functions

The one feature that most changes what you can express cleanly. A window function computes across a set of related rows while keeping every row — which removes most self-joins, most correlated subqueries, and a great deal of application code.

over partition by ranking frames

Aggregate without collapsing

GROUP BY reduces many rows to one. A window function computes the same kind of thing and attaches the answer to every row. That is the whole idea, and it is what makes "each row alongside its group's total" a single clause rather than a join.

the difference in one comparison
-- GROUP BY: 4 rows out, one per customer. Individual orders are gone.
SELECT customer_id, sum(amount) FROM orders GROUP BY customer_id;

-- Window: every order still there, each carrying its customer's total.
SELECT id, customer_id, amount,
       sum(amount) OVER (PARTITION BY customer_id) AS customer_total,
       amount / sum(amount) OVER (PARTITION BY customer_id) AS share
FROM orders;

-- Without windows, that second query needs a self-join or a correlated
-- subquery, and both scan the table twice:
SELECT o.id, o.customer_id, o.amount, t.total
FROM orders o
JOIN (SELECT customer_id, sum(amount) AS total
      FROM orders GROUP BY customer_id) t ON t.customer_id = o.customer_id;
The signal that you want a window function

Any sentence of the form "each row, compared to…" — compared to its group's total, to the previous row, to the group's maximum, to its rank within the group. If you find yourself joining a table to itself, or writing a correlated subquery against the same table you are already selecting from, stop: it is almost certainly a window function, it will be shorter, and it will need one pass instead of two.

The anatomy of OVER

three independent parts
function(args) OVER (
    PARTITION BY  ...      -- 1. split rows into independent groups
    ORDER BY      ...      -- 2. order within each group
    ROWS/RANGE    ...      -- 3. which rows within the group to include
)

-- Omit PARTITION BY -> the whole result is one partition.
-- Omit ORDER BY     -> no order, and the default frame is the entire partition.
-- Add ORDER BY      -> the default frame becomes "start of partition to
--                      CURRENT ROW", which is why running totals work with
--                      no frame clause at all.

-- That default is the single most surprising thing about window functions:
sum(amount) OVER (PARTITION BY customer_id)                     -- group total
sum(amount) OVER (PARTITION BY customer_id ORDER BY placed_at)  -- RUNNING total
-- Adding ORDER BY silently changed what the function computes.

last_value does not do what it looks like

With an ORDER BY and no explicit frame, the default frame ends at the current row — so last_value() returns the current row's own value, every time. It is the single most reported "window functions are broken" bug and it is the default frame doing exactly what it says. The fix is to state the frame: last_value(x) OVER (ORDER BY y ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING). Or avoid it — first_value(x) OVER (ORDER BY y DESC) is clearer and needs no frame clause.

Frames

ROWS against RANGE, and why it matters
-- ROWS counts physical rows. Predictable, and almost always what you want.
sum(amount) OVER (ORDER BY placed_at ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
-- a 7-row moving window

-- RANGE works on VALUES of the ORDER BY column. Rows with the same value are
-- all included together, which changes the answer when there are ties.
sum(amount) OVER (ORDER BY placed_at RANGE BETWEEN
                  INTERVAL '6 days' PRECEDING AND CURRENT ROW)
-- a genuine 7-DAY window, regardless of how many orders fall in it

-- The default frame when ORDER BY is present is:
--     RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
-- Note RANGE, not ROWS. With ties in the ORDER BY column, a "running total"
-- jumps by the whole tied group at once rather than one row at a time.
-- If that matters, say ROWS explicitly:
sum(amount) OVER (ORDER BY placed_at
                  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

The patterns worth memorising

top-N per group — the most useful one
-- Each customer's 3 largest orders. Window functions cannot go in WHERE
-- (they are computed at step 5, after WHERE at step 2 — chapter 2), so the
-- ranking goes in a subquery or CTE and the filter goes outside it.
SELECT * FROM (
    SELECT o.*,
           row_number() OVER (PARTITION BY customer_id
                              ORDER BY amount DESC, id) AS rn
    FROM orders o
) t
WHERE rn <= 3;

-- Use row_number() for "exactly 3", rank() for "3 places, ties included".
-- Note the tie-break on id: without it, two equal amounts get an arbitrary
-- order and the query returns different rows between runs.
period-on-period, running totals, moving averages
WITH monthly AS (
    SELECT date_trunc('month', placed_at) AS month, sum(amount) AS revenue
    FROM orders WHERE status = 'paid' GROUP BY 1
)
SELECT
    month,
    revenue,
    lag(revenue) OVER (ORDER BY month)                       AS prev_month,
    revenue - lag(revenue) OVER (ORDER BY month)             AS change,
    round(100.0 * (revenue - lag(revenue) OVER (ORDER BY month))
          / nullif(lag(revenue) OVER (ORDER BY month), 0), 1) AS pct_change,
    sum(revenue) OVER (ORDER BY month)                       AS running_total,
    avg(revenue) OVER (ORDER BY month
                       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM monthly
ORDER BY month;

-- Repeating the same OVER clause is noisy. Name it once with WINDOW:
SELECT month, revenue,
       lag(revenue) OVER w                       AS prev_month,
       sum(revenue) OVER w                       AS running_total
FROM monthly
WINDOW w AS (ORDER BY month)
ORDER BY month;
deduplication — keep one row per key
-- Find the duplicates.
SELECT * FROM (
    SELECT id, email,
           row_number() OVER (PARTITION BY lower(email) ORDER BY created_at) AS rn
    FROM users
) t WHERE rn > 1;

-- Delete them, keeping the earliest of each group.
DELETE FROM users WHERE id IN (
    SELECT id FROM (
        SELECT id, row_number() OVER (PARTITION BY lower(email)
                                      ORDER BY created_at, id) AS rn
        FROM users
    ) t WHERE rn > 1
);
-- Run the SELECT version first, always. Then add the UNIQUE constraint that
-- should have prevented this (chapter 11), or it happens again next quarter.
gaps and islands — the clever one
-- Find runs of consecutive active days per user.
-- Trick: for consecutive dates, (date − row_number()) is CONSTANT within a run,
-- so it works as a group key for the run itself.
WITH numbered AS (
    SELECT user_id, activity_date,
           activity_date - (row_number() OVER (PARTITION BY user_id
                                               ORDER BY activity_date))::int
               AS run_key
    FROM daily_activity
)
SELECT user_id,
       min(activity_date) AS streak_start,
       max(activity_date) AS streak_end,
       count(*)           AS streak_days
FROM numbered
GROUP BY user_id, run_key
HAVING count(*) >= 3
ORDER BY streak_days DESC;

-- Worth understanding rather than memorising: consecutive dates increase by 1
-- and so does row_number(), so their difference stays put. A gap makes the
-- difference jump, which starts a new group.

Where window functions can and cannot go

ClauseAllowed?Because
SELECT listYesStep 5, after grouping
ORDER BYYesStep 7
WHERENoStep 2 — the window has not been computed yet
GROUP BYNoStep 3, same reason
HAVINGNoStep 4, same reason
Nested inside an aggregateNosum(count(*) OVER ()) is invalid
An aggregate inside a windowYessum(count(*)) OVER () is valid and useful with GROUP BY
All of these follow from chapter 2's execution order. To filter on a window result, compute it in a subquery or CTE and filter outside.
a window over an aggregate — legal and useful
-- Each region's revenue, and its share of the overall total, in one pass.
SELECT
    region,
    sum(amount)                        AS revenue,
    sum(sum(amount)) OVER ()           AS grand_total,
    round(100.0 * sum(amount) / sum(sum(amount)) OVER (), 1) AS pct
FROM orders
GROUP BY region;

-- The nesting reads oddly and is correct: the inner sum() aggregates within
-- each group, then the window sums those group totals across all groups.
-- Windows are evaluated AFTER grouping, so they see the grouped rows.

Support is universal now

Window functions are in PostgreSQL (since 8.4), MySQL 8.0, MariaDB 10.2, SQLite 3.25, SQL Server and Oracle. If you learned SQL when they were a Postgres-and-Oracle luxury, that constraint is gone — and a large amount of self-joining, correlated-subquery SQL written under it is now worth rewriting. This is the highest-leverage modernisation available on an old codebase's queries.

The short version

  1. A window function computes across related rows without collapsing them. That is the whole feature.
  2. The signal is any "each row, compared to…" requirement, and any self-join against the table you are already selecting from.
  3. OVER has three parts: partition, order, frame. Adding ORDER BY changes the default frame — and turns a group total into a running total.
  4. last_value() returns the current row unless you state the frame. It is the default frame, not a bug.
  5. row_number for exactly N, rank for ties-with-gaps, dense_rank for ties-without. Always add a tie-break to the order.
  6. Windows cannot go in WHERE, GROUP BY or HAVING — compute in a subquery, filter outside.
  7. Learn four patterns: top-N per group, period-on-period with lag, running totals, and deduplication.
  8. Functions sharing an OVER clause share one sort. Name it with WINDOW.
