Transactions and isolation

A transaction promises that a group of changes happens completely or not at all. Isolation is the harder half of the promise — what your transaction sees while others are running — and the default in most databases permits several anomalies that will eventually cost you money.

Atomicity and durability are largely handled for you. Isolation is a spectrum you choose a point on — usually by accident, since almost nobody changes the default.

The same level name means different things

PostgreSQL defaults to READ COMMITTED, and its READ UNCOMMITTED is identical to it — dirty reads are simply not possible. Its REPEATABLE READ uses snapshot isolation, which prevents phantoms (stricter than the standard requires) but still allows write skew. MySQL/InnoDB defaults to REPEATABLE READ and uses gap locking, which prevents phantoms in a different way and has its own locking consequences. Oracle has no REPEATABLE READ at all. SQL Server defaults to READ COMMITTED with locking rather than versioning, so readers can block writers unless you enable RCSI. Read your engine's documentation on this specific point — the standard's names are not portable behaviour.

Lost updates, the one you will actually meet

three fixes, in order of preference
-- The bug, from chapter 9: read 10, both write 11, one decrement vanishes.

-- FIX 1 — atomic statement. Best when expressible. No transaction needed.
UPDATE products SET stock = stock - 1
WHERE id = 42 AND stock > 0
RETURNING stock;
-- Zero rows back means it was already out of stock.

-- FIX 2 — pessimistic lock. When you must compute in application code.
BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;   -- blocks other writers
-- ... application logic ...
UPDATE products SET stock = 7 WHERE id = 42;
COMMIT;
-- Correct, and it serialises everything touching that row. Keep it short.

-- FIX 3 — optimistic lock. Best under low contention and across requests.
UPDATE products SET stock = 7, version = version + 1
WHERE id = 42 AND version = 3;
-- Zero rows means someone else changed it since you read it. Re-read and retry.
-- This is the only one that works when the user thinks between the read and
-- the write, because it holds no lock while they do.
READ COMMITTED does not prevent lost updates

Worth stating plainly, because it is the default nearly everywhere and it is widely assumed to be safe. Two transactions can both read a row, both compute a new value from it, and both write — the second overwrites the first, no error, no warning. Isolation level alone will not save you; you need one of the three patterns above. This is the most consequential thing in the chapter.

Write skew, and why SERIALIZABLE exists

the anomaly no lower level catches
-- Rule: at least one doctor must remain on call.
-- Two doctors, both on call, both try to go off at the same moment.

-- Transaction A                          -- Transaction B
BEGIN;                                    BEGIN;
SELECT count(*) FROM shifts               SELECT count(*) FROM shifts
 WHERE on_call = true;   -- 2              WHERE on_call = true;   -- 2
-- "2 > 1, safe to go off"                -- "2 > 1, safe to go off"
UPDATE shifts SET on_call = false         UPDATE shifts SET on_call = false
 WHERE doctor = 'A';                       WHERE doctor = 'B';
COMMIT;                                   COMMIT;
-- Now nobody is on call. Both transactions were individually correct.

-- Note that they never touched the same ROW, so row locks do not help and
-- REPEATABLE READ does not help. Each read a set, made a decision about that
-- set, and wrote something that invalidated the other's decision.

-- FIX A — SERIALIZABLE. The database detects the conflict and aborts one.
BEGIN ISOLATION LEVEL SERIALIZABLE;
...
COMMIT;   -- may raise serialization_failure; the caller MUST retry

-- FIX B — materialise the conflict so a lock exists to take.
SELECT * FROM shifts WHERE on_call = true FOR UPDATE;   -- lock the rows you read
-- Now both transactions contend on the same rows and one waits.

-- FIX C — express the rule as a constraint the database enforces (chapter 11).
-- Usually the most robust: no application code can bypass it.
SERIALIZABLE requires retry logic, and without it you have made things worse

Serialisable isolation does not make conflicts wait — it detects them and aborts one transaction with a serialisation failure. If your application does not catch that and retry, you have converted a rare silent corruption into a frequent user-visible error. The retry loop is not optional: catch the specific error code, back off briefly, and re-run the whole transaction from the beginning. Under heavy contention the abort rate can be high enough that throughput collapses, which is the real cost of the level.

the retry wrapper that makes SERIALIZABLE usable
import random, time
import psycopg

SERIALIZATION_FAILURE = "40001"
DEADLOCK_DETECTED     = "40P01"

def in_serializable(fn, attempts: int = 5):
    for i in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
                return fn(conn)
        except psycopg.errors.OperationalError as e:
            if e.sqlstate not in (SERIALIZATION_FAILURE, DEADLOCK_DETECTED):
                raise
            if i == attempts - 1:
                raise
            time.sleep((2 ** i) * 0.01 * (0.5 + random.random()))  # jitter
    raise RuntimeError("unreachable")

# Two requirements the wrapper imposes on fn:
#   * it must be safe to run more than once (no side effects outside the
#     transaction — no emails sent, no payments taken mid-way)
#   * it must re-read everything; using values from the failed attempt
#     defeats the point entirely

the FOR UPDATE variants that matter
-- Wait for the lock (default). Fine when contention is rare.
SELECT * FROM jobs WHERE id = 7 FOR UPDATE;

-- Fail immediately rather than queueing. Good for interactive paths where a
-- fast error beats a slow success.
SELECT * FROM jobs WHERE id = 7 FOR UPDATE NOWAIT;

-- Skip rows someone else holds. The queue-worker idiom: several workers can
-- each grab different jobs with no coordination and no contention.
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;

-- SKIP LOCKED is the single most useful of the three. It turns a table into a
-- work queue that scales with the number of workers, and it is why "just use
-- your database as the queue" is reasonable advice far more often than people
-- assume.

Deadlocks

the cause, and the fix
-- Transaction A            Transaction B
UPDATE accounts             UPDATE accounts
  SET … WHERE id = 1;         SET … WHERE id = 2;      -- each holds one lock
UPDATE accounts             UPDATE accounts
  SET … WHERE id = 2;         SET … WHERE id = 1;      -- each wants the other's
-- Circular wait. The database detects it and kills one with a deadlock error.

-- FIX: acquire locks in a consistent order, everywhere in the codebase.
-- Sorting by primary key is the standard convention and costs nothing.
UPDATE accounts SET … WHERE id = least(from_id, to_id);
UPDATE accounts SET … WHERE id = greatest(from_id, to_id);

-- Or lock both up front, ordered:
SELECT * FROM accounts WHERE id IN (from_id, to_id) ORDER BY id FOR UPDATE;
CauseFix
Inconsistent lock orderingAlways lock in primary-key order. The most common cause by far
Long transactions holding many locksShorten them; do less inside
Escalation from row to table locksSmaller batches (chapter 9)
Foreign keys locking parentsIndex the foreign key; consider deferrable constraints
Upserts under contentionON CONFLICT rather than check-then-insert
Deadlocks are normal; retry them

A deadlock is not a bug to be eliminated so much as a condition to be handled — the database detected a circular wait and resolved it by killing the cheaper victim, which is the correct behaviour. Any code path that writes should be wrapped in the same retry logic as serialisation failures, since the error codes and the correct response are identical. Then reduce the rate by fixing lock ordering, and alert if it climbs.

Keeping transactions short

Never inside a transaction

  • An HTTP call to another service
  • Waiting for user input
  • Sending an email or a webhook
  • A long computation you could do before BEGIN
  • Sleeping, for any reason

Why it matters more than it looks

  • Locks are held for the whole transaction, not the statement
  • Long transactions prevent vacuum from cleaning dead rows, and the table bloats
  • Replicas can fall behind or cancel queries
  • Connection pools fill with transactions that are doing nothing
  • The rollback after a failure costs as much as the work did
Set a statement timeout, and an idle-in-transaction timeout

SET statement_timeout = '30s' stops one runaway query taking the system with it. idle_in_transaction_session_timeout is the one people forget, and it is arguably more important: it kills sessions that opened a transaction and then went away — a crashed worker, a developer's abandoned psql window — which otherwise hold locks and block vacuum indefinitely. Both are one line of configuration and both have prevented real outages.

The short version

  1. Atomicity and durability are handled for you. Isolation is a choice, and almost nobody makes it deliberately.
  2. READ COMMITTED — the default nearly everywhere — permits lost updates. That is the most consequential fact here.
  3. Fix lost updates with an atomic statement, FOR UPDATE, or an optimistic version column — in that order of preference.
  4. Write skew needs no shared row, so row locks and REPEATABLE READ do not catch it. SERIALIZABLE, an explicit lock, or a constraint.
  5. SERIALIZABLE aborts rather than waits. Without retry logic you have made things worse, not better.
  6. FOR UPDATE SKIP LOCKED turns a table into a work queue that scales with workers.
  7. Deadlocks come from inconsistent lock ordering. Lock in primary-key order, and retry the ones that happen anyway.
  8. Never hold a transaction across a network call, and set both statement and idle-in-transaction timeouts.
