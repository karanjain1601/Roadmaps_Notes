Chapter 16 · In production

Migrations and operations

Every schema change is a deployment against a running system holding data you cannot recreate. This chapter is the set of habits that make that routine rather than frightening — and the short list of things worth knowing before the alert fires.

The lock is the whole problem

Chapter 10 introduced ACCESS EXCLUSIVE — the lock that blocks everything including reads. Most schema changes take one. The question for every migration is not "how long does this take" but "what does it block, and for how long".

The lock queue is worse than the lock

The failure that actually causes outages is not a long migration — it is a short one that has to wait. ALTER TABLE requests an ACCESS EXCLUSIVE lock, and if a long-running SELECT holds a weaker lock, the ALTER waits. Every subsequent query then queues behind the ALTER, because lock requests are ordered. A one-millisecond migration blocks the entire table for as long as that one slow report takes to finish. Always set lock_timeout before DDL — a few seconds — so the migration fails fast and retries instead of taking the site down.

the preamble every migration should have
SET lock_timeout = '3s';        -- fail fast rather than queueing behind a
                                -- long query and blocking everything after it
SET statement_timeout = '60s';  -- do not let a rewrite run unbounded

ALTER TABLE orders ADD COLUMN region text;

-- If the lock cannot be acquired in 3 seconds the statement errors, nothing
-- is blocked, and you retry in a moment. Make your migration runner catch
-- the timeout and retry with backoff — that turns the riskiest class of
-- migration into a non-event.

Expand and contract

The pattern behind every zero-downtime schema change. Never change a thing; add the new one, migrate to it, then remove the old one — with a deploy between each step, so that at every moment the running code and the current schema are compatible.

renaming a column without downtime
-- A RENAME is instant and it is NOT safe: the old code is still running during
-- the deploy and refers to the old name. Every request from an old instance
-- errors until the rollout finishes.

-- Migration 1 — expand
ALTER TABLE customers ADD COLUMN full_name text;

-- Deploy A — write both, read the old
--   customer.name = value; customer.full_name = value

-- Migration 2 — backfill, batched (chapter 9)
UPDATE customers SET full_name = name
WHERE full_name IS NULL AND id BETWEEN … AND …;

-- Deploy B — read the new, still write both
-- Deploy C — write only the new

-- Migration 3 — contract, a few days later
ALTER TABLE customers DROP COLUMN name;

-- Six steps for a rename. That is the actual cost of zero downtime, and it is
-- why "can we just take two minutes of downtime at 4am" is sometimes the right
-- engineering answer rather than a failure of ambition.
Every migration must be safe with the previous version still running

This is the rule that generates the whole pattern. During any rollout, old and new application code run simultaneously against one schema — so the schema must satisfy both. It rules out renames, type narrowing, adding NOT NULL to a column old code does not populate, and dropping anything still referenced. Check each migration against the question directly: if the deploy stalls halfway for an hour, does everything still work?

Migration hygiene

  • Versioned files in the repository, applied in order, recorded in a table. Never hand-run DDL in production.
  • Forward-only. Down-migrations are rarely tested and rarely correct; roll forward with a new migration instead.
  • One logical change per migration, so a failure has an obvious blast radius.
  • Never mix DDL and a large backfill in one transaction — the DDL lock is then held for the whole backfill.
  • Run against a production-sized copy first. A migration that takes 40ms on 10,000 rows can take 40 minutes on 50 million.
  • lock_timeout on every migration, with retry.
  • CREATE INDEX CONCURRENTLY cannot run in a transaction — most frameworks need an explicit escape hatch.
  • Review migrations more carefully than code. Code can be reverted; a dropped column cannot.

a view as a migration shim
-- Splitting one table into two, without breaking every existing query.
-- Old code keeps working against a view with the original shape.
CREATE VIEW customers AS
SELECT c.id, c.name, c.created_at,
       a.line1, a.city, a.postcode
FROM customers_core c
LEFT JOIN customer_addresses a ON a.customer_id = c.id AND a.is_primary;

-- Writes need rules or an INSTEAD OF trigger, which is where this gets
-- involved — so use it for a read-mostly transition period, and set a date to
-- remove it. A compatibility view that survives two years is a second schema
-- nobody documented.

The two that quietly kill a PostgreSQL instance

Transaction id wraparound: if autovacuum cannot freeze old rows fast enough, the database refuses new writes to protect itself. It is preventable, it is visible for weeks in age(datfrozenxid), and it is almost always caused by a long-running transaction or a stuck replication slot blocking vacuum. An abandoned replication slot: an inactive slot makes the primary retain WAL indefinitely, and the disk fills. Both have taken down real systems, both are on the dashboard above, and neither is difficult to avoid once you know the name.

When the alert fires

the queries worth having saved
-- What is running right now, longest first.
SELECT pid, now() - query_start AS runtime, state, wait_event_type, wait_event,
       left(query, 100) AS query
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY query_start;

-- Who is blocking whom. The single most useful query in an incident.
SELECT blocked.pid       AS blocked_pid,
       blocked.query     AS blocked_query,
       blocking.pid      AS blocking_pid,
       blocking.query    AS blocking_query,
       now() - blocking.query_start AS blocking_for
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- Transactions left open and idle — the classic cause of everything stopping.
SELECT pid, now() - state_change AS idle_for, left(query, 80)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY state_change;

-- Cancel a query (polite), or terminate the connection (not polite).
SELECT pg_cancel_backend(12345);
SELECT pg_terminate_backend(12345);

Test the restore, not the backup

Backups that have never been restored fail at a remarkable rate — wrong permissions, missing extensions, an unnoticed error in the nightly job, a retention policy that quietly deleted everything older than the corruption you need to recover from. Restore to a scratch instance on a schedule, verify a row count and a checksum, and record the time it took: that duration is your actual recovery objective, whatever the policy document says. Most teams discover theirs is four hours rather than the twenty minutes they assumed, and they discover it during an incident.

Where this unit ends

Sixteen chapters from one claim: SQL is declarative, and the unit of work is a set rather than a row. Nearly everything since followed from taking that seriously. Joins multiply because they are filtered Cartesian products. Aggregates double-count because the multiplication happened first. Window functions exist because sometimes you want the group's answer without losing the rows. Indexes work because sorted order permits binary search. Query plans are readable because the planner is choosing between a small number of physical strategies for the same declarative request.

The chapters that will matter most in practice are probably not the ones that felt hardest. NULL, because it produces wrong answers rather than errors. Fan-out, because the wrong number is plausible. Lost updates, because the default isolation level permits them and almost nobody knows. Foreign key indexes, because they are missing nearly everywhere. Those four are worth re-reading; the rest you will look up when you need them, which is fine.

The next step is not more reading. Open the slowest query in something you already run, put EXPLAIN (ANALYZE, BUFFERS) in front of it, and find out what it is actually doing. It will not be what you expected, and that gap is where the learning is.

The short version

  1. For every migration, ask what it locks and for how long — not how long it takes.
  2. The lock queue is worse than the lock. Set lock_timeout and retry, always.
  3. Expand and contract: add, dual-write, backfill, switch reads, stop writing, drop. Six steps, and that is the real cost of zero downtime.
  4. Every migration must be safe with the previous version still running. If the deploy stalls for an hour, does everything work?
  5. Forward-only migrations, one logical change each, tested against production-sized data.
  6. Monitor connections, replication lag, longest transaction, bloat, disk and transaction id age — the last two kill instances quietly.
  7. Keep the blocking-pid query saved. In an incident it is the one that identifies the culprit in seconds.
  8. Test the restore. Its duration is your real recovery objective, whatever the document says.
