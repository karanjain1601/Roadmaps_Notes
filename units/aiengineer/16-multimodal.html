Multimodal: vision, audio, video

Images, audio and video enter and leave the same models you already call. The API shape barely changes; what changes is how you count tokens, where latency comes from, and a set of failure modes that text work never taught you to expect.

vision image gen speech to text tts documents voice agents

Images in

A multimodal model accepts image blocks in the same message array as text. The image is divided into patches, encoded, and consumes tokens exactly like text does — which is where the cost surprises come from.

python — an image and a question in one message
import base64

def as_block(path: str, media_type: str = "image/jpeg") -> dict:
    with open(path, "rb") as f:
        return {"type": "image",
                "source": {"type": "base64", "media_type": media_type,
                           "data": base64.b64encode(f.read()).decode()}}

resp = client.messages.create(
    model=MODEL, max_tokens=1024,
    messages=[{"role": "user", "content": [
        as_block("receipt.jpg"),
        {"type": "text", "text": "Extract the line items, totals and VAT as JSON."}]}])

Resize before you upload

Sending a 4,000-pixel photograph when 1,000 pixels would do can cost four times as much for identical accuracy, because most providers cap the useful resolution anyway and downscale server-side — you pay for the upload and often for the tokens. Resize client-side so the longest edge is around 1,000–1,500 pixels, unless you are reading small text, in which case crop to the region of interest rather than sending the whole page at full resolution.

Documents: the highest-value vision use case

Chapter 11 mentioned this in passing; it deserves its own treatment because it is where vision models earn most of their commercial keep. PDFs with complex layouts — tables spanning pages, multi-column text, forms, scanned handwriting — defeat traditional extraction, and a vision model reading a rendered page often does substantially better.

extract.py — page images to structured data, with validation
import fitz                                   # PyMuPDF
from pydantic import BaseModel, Field

class LineItem(BaseModel):
    description: str
    quantity: float
    unit_price: float
    total: float

class Invoice(BaseModel):
    invoice_number: str
    issue_date: str = Field(description="ISO 8601")
    supplier: str
    currency: str = Field(description="ISO 4217, e.g. GBP")
    line_items: list[LineItem]
    subtotal: float
    tax: float
    total: float
    unreadable_fields: list[str] = Field(
        description="Fields you could not read confidently. Do not guess.")

def page_images(pdf: str, dpi: int = 150) -> list[bytes]:
    doc = fitz.open(pdf)
    return [p.get_pixmap(dpi=dpi).tobytes("png") for p in doc]

def extract(pdf: str) -> Invoice:
    blocks = [image_block(png) for png in page_images(pdf)]
    inv = structured_call(Invoice, blocks + [
        {"type": "text", "text":
         "Extract this invoice. Copy figures exactly as printed; never compute a "
         "missing value. If a field is unreadable, list it in unreadable_fields."}])

    # Arithmetic is the cheapest confidence check you will ever write.
    computed = round(sum(li.total for li in inv.line_items), 2)
    if abs(computed - inv.subtotal) > 0.02:
        inv.unreadable_fields.append(f"subtotal mismatch: items sum to {computed}")
    if abs(round(inv.subtotal + inv.tax, 2) - inv.total) > 0.02:
        inv.unreadable_fields.append("total does not equal subtotal + tax")
    return inv

Two design choices carry most of the reliability. The unreadable_fields list gives the model a legitimate way to express uncertainty rather than inventing a number — without it, models fill gaps confidently. And the arithmetic cross-check catches misreads automatically: if the line items do not sum to the subtotal, something was misread, and you route that document to a human instead of into your ledger.

Before shipping generated imagery: check the provider's terms on commercial use and ownership; do not generate in the style of a named living artist for commercial work; do not generate identifiable real people; preserve or add provenance metadata such as C2PA where available; and disclose AI generation where your users or regulators expect it. These are product decisions with legal consequences, not implementation details — settle them before the feature ships, not after.

Audio out: text to speech

Voice selection
Preset voices are safe. Cloned voices need documented consent from the speaker and are regulated in some jurisdictions.
Streaming
Essential for conversation. Streamed TTS starts speaking in a few hundred milliseconds; batch TTS makes you wait for the whole utterance.
Control
Some engines accept SSML or style instructions for pace, emphasis and pauses. Numbers, dates, currency and abbreviations are where naive TTS embarrasses itself — normalise them in text first.
Caching
Fixed phrases — greetings, hold messages, confirmations — should be synthesised once and cached, not regenerated per call.

Building a voice agent

The classic pipeline chains three models, and its latency is the sum of every stage. Getting the total under the roughly 800 milliseconds at which conversation feels natural is the entire engineering problem.

Voice activity detection → end of turn~100–300ms. Deciding the user has stopped is the hardest and most latency-critical judgement in the system
↓
Streaming ASR~100–200ms after end of speech, if transcription has been running live
↓
LLM, first token~300–600ms. The dominant term. Prompt caching and a smaller model both help
↓
Streaming TTS, first audio~150–300ms once the first sentence is available
  • Stream everything, everywhere. Start TTS on the first complete sentence rather than the full response. This alone can halve perceived latency.
  • Handle barge-in. Users interrupt. Detect speech during playback, stop audio immediately, and truncate the assistant message to what was actually heard — otherwise the model believes it said things the user never heard.
  • Use filler intelligently. A short "let me check that" while a tool call runs is far better than silence, provided it is not used every turn.
  • Write prompts for speech. No markdown, no bullet lists, no long paragraphs. Short sentences. Spell out numbers and dates the way a person would say them.
  • Consider speech-to-speech models where available: one model, lower latency, and prosody carries through. The trade-off is less control over the intermediate text and harder logging.
  • Log the transcript, not the audio, unless you have a specific reason and consent for the latter.

Video

Video understanding is mostly frame sampling plus audio. Sample one frame every second or two — or on scene changes — transcribe the audio, and give the model both with timestamps. Native video models exist and handle temporal reasoning better, but frame sampling covers most practical needs at a fraction of the cost.

python — scene-change sampling beats fixed intervals
import cv2, numpy as np

def key_frames(path: str, threshold: float = 0.35, max_frames: int = 40) -> list:
    cap, frames, prev = cv2.VideoCapture(path), [], None
    fps = cap.get(cv2.CAP_PROP_FPS) or 25
    idx = 0
    while True:
        ok, frame = cap.read()
        if not ok:
            break
        if idx % int(fps) == 0:                       # consider one frame per second
            small = cv2.resize(frame, (64, 64)).astype(np.float32) / 255
            if prev is None or np.abs(small - prev).mean() > threshold:
                frames.append((idx / fps, frame))     # (timestamp, image)
                prev = small
        idx += 1
    cap.release()
    return frames[:max_frames]

# Then: transcribe the audio track separately and interleave by timestamp, so the
# model sees "[00:14]   [00:14] speaker: and here's the billing screen…"

Video generation is advancing quickly but remains slow, expensive and hard to control precisely. Treat it as an asynchronous creative tool rather than a component in a request path.

The short version

  1. Images are tokens. Resize before uploading — most of the cost surprises are unnecessary resolution.
  2. Put the image before the question, and never trust a precise number the model read off a chart or a count above five.
  3. Document extraction is the highest-value vision use case. Give the model a way to say "unreadable" and cross-check the arithmetic.
  4. Extract once at ingest and store the result — vision per query is expensive.
  5. For transcription, the prompt parameter biases vocabulary, and confidence fields let you flag low-quality segments.
  6. Voice agents live or die on latency. Stream every stage, handle barge-in, and write prompts meant to be spoken.
  7. Video is frame sampling plus audio with timestamps, until you specifically need temporal reasoning.
  8. Media is untrusted input and often personal data. Moderate both directions, strip EXIF, decide retention early.
