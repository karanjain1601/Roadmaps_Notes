Talking to a model in code

The request itself is ten lines. The other ninety are conversation state, streaming, timeouts, retries, finish reasons and the seam that stops you rewriting everything when you change provider. Those ninety are the chapter.

message roles streaming retries finish reasons conversation state provider seam

The request shape

Every text model API is the same idea with different spelling: a list of messages, each with a role, plus generation settings. The provider returns a message from the assistant, a reason it stopped, and a token usage record.

python — the whole idea, once
response = client.chat.completions.create(
    model="provider/workhorse-v2-2026-05-20",
    messages=[
        {"role": "system", "content": "You classify support tickets. Reply with one word."},
        {"role": "user",   "content": "My card was charged twice for the same order."},
    ],
    temperature=0,
    max_tokens=8,
)

print(response.choices[0].message.content)   # "billing"
print(response.choices[0].finish_reason)     # "stop"
print(response.usage.prompt_tokens,          # 34
      response.usage.completion_tokens)      # 2

The roles, and what each is for

RoleContainsNotes
system (sometimes developer)Instructions, persona, rules, output contract, static reference materialHighest-priority text in the request. Anthropic passes it as a separate top-level parameter rather than a message. Keep it stable — a stable prefix is what prompt caching keys on.
userThe end user's input, plus anything you retrieved on their behalfTreat everything here as untrusted, including retrieved documents (chapter 17).
assistantWhat the model said previously, and any tool calls it requestedYou can also write these yourself to prefill a response or to demonstrate desired behaviour.
tool (or function)The result of a function the model asked you to runMust reference the call id the model issued. Chapter 7.

Modern APIs allow a message's content to be a list of typed blocks rather than a plain string — text, image, document, tool use, tool result, and sometimes a thinking block. This is how multimodal input arrives (chapter 16) and how tool calls come back (chapter 7).

Conversation state is yours

The API is stateless. A conversation exists because you store the messages and re-send them. That means three decisions are yours: where history lives, what you trim, and what you never send again.

conversation.py — history with a token budget
from dataclasses import dataclass, field

@dataclass
class Conversation:
    system: str
    messages: list = field(default_factory=list)
    max_history_tokens: int = 12_000

    def add(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})

    def build(self, counter) -> list:
        """Newest-first walk, keeping whole turns, until the budget is spent."""
        kept, used = [], 0
        for m in reversed(self.messages):
            cost = counter(m["content"])
            if used + cost > self.max_history_tokens:
                break
            kept.append(m)
            used += cost
        kept.reverse()

        # Never drop the first user turn: it usually contains the actual task.
        if self.messages and kept and kept[0] is not self.messages[0]:
            first = self.messages[0]
            if first["role"] == "user":
                kept.insert(0, first)

        return [{"role": "system", "content": self.system}] + kept

Three strategies for long conversations, in increasing order of effort:

StrategyHowCostLoses
Sliding windowKeep the last N turnsFreeAnything established early — the user's name, the constraint they gave in turn two
Window plus pinned factsKeep last N turns and a small structured summary you maintain (order id, chosen plan, language)One cheap extraction call per few turnsNuance, but rarely anything that matters
Rolling summaryWhen history exceeds a threshold, summarise the oldest half into one assistant-visible note and drop itOne summarisation call occasionallyDetail, progressively — and summarisation errors compound over a very long session
Store the raw exchange separately from the prompt

Keep an append-only log of exactly what the user said and what the model returned, including token counts, model version and latency. What you send is a derived, trimmed view. Conflating the two makes it impossible to replay an incident or build an eval set from real traffic.

Streaming

Streaming does not make the response faster. It makes the wait visible, which is a different and much larger UX win: a first token in 400ms with tokens arriving steadily feels dramatically better than silence for six seconds followed by everything at once.

typescript — server-sent events to the browser
// Server (any Node framework). Note: disable proxy buffering, or nothing arrives until the end.
export async function GET(req: Request) {
  const encoder = new TextEncoder();
  const body = new ReadableStream({
    async start(controller) {
      const stream = await llm.stream({ model: MODEL, messages });
      try {
        for await (const chunk of stream) {
          controller.enqueue(encoder.encode(`data: ${JSON.stringify({ t: chunk.text })}\n\n`));
        }
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ done: true })}\n\n`));
      } catch (err) {
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ error: String(err) })}\n\n`));
      } finally {
        controller.close();
      }
    },
    cancel() { /* user navigated away: abort upstream so you stop paying for tokens */ }
  });

  return new Response(body, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      "Connection": "keep-alive",
      "X-Accel-Buffering": "no",
    },
  });
}

The four things that bite you when streaming

  • Proxies buffer. Nginx, some CDNs and some serverless platforms will hold your chunks until the response completes, which silently converts streaming back into buffering. Set X-Accel-Buffering: no, disable compression on the route, and test through your real edge, not localhost.
  • Partial JSON is not JSON. If the model is emitting a structured object you cannot parse mid-stream with JSON.parse. Either buffer structured responses and stream only prose, or use a streaming-tolerant parser and render fields as they complete. Chapter 7.
  • Errors arrive mid-stream. A 200 response can still fail halfway. You have already sent a partial answer to the user, so you need a UI state for "this got cut off" rather than an exception page.
  • Cancellation must propagate. When the user closes the tab, abort the upstream request. Otherwise you keep generating and paying for tokens nobody will read. Wire an AbortController through every layer.

Finish reasons: check them, always

The most common silent bug in LLM code is treating a truncated response as a complete one. The text looks fine. It just stops.

ReasonMeansYour code should
stop / end_turnThe model finished naturallyProceed
length / max_tokensIt hit your output cap mid-sentenceNever parse the result as complete. Either raise, or continue generation, or re-run with a higher cap. Log it — a rising rate means your cap is wrong.
tool_calls / tool_useIt wants you to run a functionExecute the tool and loop (chapter 7). This is not an answer.
content_filter / refusalBlocked by a safety system, yours or theirsShow a specific message, do not retry identically, and log it for review
pause_turn and similarA long server-side operation pausedContinue the request as documented rather than treating it as finished
python — a guard that has saved a lot of incidents
class Truncated(Exception): ...

def text_of(response) -> str:
    choice = response.choices[0]
    reason = choice.finish_reason
    if reason == "length":
        raise Truncated(f"hit max_tokens ({response.usage.completion_tokens} generated)")
    if reason == "content_filter":
        raise Blocked(choice.message.content or "")
    if reason == "tool_calls":
        raise ToolRequested(choice.message.tool_calls)
    return choice.message.content or ""

Failure and retries

Model APIs fail more often than the databases you are used to, and in more interesting ways. Handle each class deliberately.

StatusCauseRetry?Handling
400Malformed request, or context length exceededNoA bug or an oversized prompt. Count tokens before sending (chapter 5) and fail with a clear internal error.
401 / 403Bad key, no access to that modelNoConfiguration. Fail loudly at startup, not per request — validate model access on boot.
408 / client timeoutSlow generation, long promptCarefulRetrying a slow request usually produces another slow request. Prefer a shorter prompt, a smaller model, or streaming.
429Rate limit — requests or tokens per minuteYesHonour retry-after if present, otherwise exponential backoff with jitter. Also queue and smooth your own traffic.
500 / 503 / 529Provider trouble or overloadYesBackoff, then fall back to a second model or provider (chapter 19).
Empty or malformed outputThe model did something unhelpfulYes, onceRetry with the validation error appended to the messages. A second attempt fixes most format failures (chapter 7).
retry.py — backoff with jitter and a hard deadline
import random, time

RETRYABLE = (RateLimited, Overloaded, ServerError, ConnectionError)

def with_retries(fn, *, attempts=4, base=0.7, cap=12.0, deadline_s=45.0):
    started = time.monotonic()
    last = None
    for i in range(attempts):
        try:
            return fn()
        except RETRYABLE as e:
            last = e
            retry_after = getattr(e, "retry_after", None)
            wait = retry_after if retry_after else min(cap, base * (2 ** i))
            wait *= 0.5 + random.random()               # full jitter: do not stampede
            if time.monotonic() - started + wait > deadline_s:
                break                                   # never blow the user's latency budget
            time.sleep(wait)
        except Exception:
            raise                                       # non-retryable: fail fast
    raise last
Retries are not free

A retried request is charged again, and a naive retry loop across a whole fleet during a provider incident turns a partial outage into a self-inflicted one. Always set a total deadline, always use jitter, and put a circuit breaker in front of the provider so that when it is clearly down you fail fast to your fallback rather than queueing thousands of doomed calls.

Concurrency, timeouts and budgets

Model calls are slow I/O, so throughput comes from concurrency, and safety comes from bounding it.

  • Set an explicit timeout on every call. SDK defaults are often a minute or more. Decide per call site: an interactive answer might get 20 seconds, a background enrichment job 120.
  • Bound your concurrency with a semaphore sized to your rate limit, not to your CPU. Exceeding token-per-minute limits produces 429s that cost you latency and retries.
  • Give each user request a token budget and a wall-clock budget that all its internal calls share. Agent loops without a budget are the classic way to discover a five-figure bill.
python — bounded fan-out over many documents
import asyncio

async def classify_all(docs, concurrency=8):
    sem = asyncio.Semaphore(concurrency)          # sized to your rate limit

    async def one(doc):
        async with sem:
            try:
                return await asyncio.wait_for(classify(doc), timeout=20)
            except asyncio.TimeoutError:
                return {"id": doc.id, "error": "timeout"}

    return await asyncio.gather(*(one(d) for d in docs))

The seam

Put one interface between your application and any provider. Not a framework, not an abstraction over every feature — a narrow surface that covers what you actually use, with an adapter per provider behind it.

llm.py — small enough to read, big enough to matter
from dataclasses import dataclass
from typing import Protocol, Iterator, Any

@dataclass
class Completion:
    text: str
    tool_calls: list[dict]
    finish_reason: str
    input_tokens: int
    output_tokens: int
    cached_input_tokens: int
    model: str
    latency_ms: int

class LLM(Protocol):
    def complete(self, *, system: str, messages: list, model: str,
                 temperature: float = 0.0, max_tokens: int = 1024,
                 tools: list | None = None, schema: dict | None = None,
                 timeout: float = 30.0) -> Completion: ...

    def stream(self, **kwargs) -> Iterator[str]: ...


class OpenAIAdapter:
    def complete(self, *, system, messages, model, **kw) -> Completion:
        t0 = time.perf_counter()
        r = self._client.chat.completions.create(
            model=model,
            messages=[{"role": "system", "content": system}, *messages],
            temperature=kw.get("temperature", 0),
            max_tokens=kw.get("max_tokens", 1024),
            tools=kw.get("tools"),
            timeout=kw.get("timeout", 30.0),
        )
        c = r.choices[0]
        return Completion(
            text=c.message.content or "",
            tool_calls=[t.model_dump() for t in (c.message.tool_calls or [])],
            finish_reason=c.finish_reason,
            input_tokens=r.usage.prompt_tokens,
            output_tokens=r.usage.completion_tokens,
            cached_input_tokens=getattr(r.usage, "prompt_tokens_details", {}).get("cached_tokens", 0),
            model=r.model,
            latency_ms=int((time.perf_counter() - t0) * 1000),
        )


class AnthropicAdapter:
    def complete(self, *, system, messages, model, **kw) -> Completion:
        r = self._client.messages.create(
            model=model, system=system, messages=messages,           # system is separate here
            max_tokens=kw.get("max_tokens", 1024),
            temperature=kw.get("temperature", 0),
            tools=kw.get("tools"),
        )
        text = "".join(b.text for b in r.content if b.type == "text")
        return Completion(
            text=text,
            tool_calls=[b.model_dump() for b in r.content if b.type == "tool_use"],
            finish_reason=r.stop_reason,
            input_tokens=r.usage.input_tokens,
            output_tokens=r.usage.output_tokens,
            cached_input_tokens=getattr(r.usage, "cache_read_input_tokens", 0),
            model=r.model,
            latency_ms=...,
        )

What this buys you, concretely: one place to add retries, one place to log every call for tracing, one place to enforce timeouts and budgets, one place to swap a model, and a test double that makes your business logic testable without a network.

Do not build a mega-abstraction

The failure mode at the other extreme is a framework-shaped layer that supports every provider's every option through a lowest-common-denominator interface. You lose prompt caching, structured-output guarantees and provider-specific tool features — precisely the things that make a system cheap and reliable. If a feature exists on one provider only and you need it, let that adapter expose it and branch at the call site.

Making it testable

Business logic that calls a model should be testable without a network, without cost and without flakiness. Two techniques cover almost everything.

tests — a scripted fake and recorded fixtures
class ScriptedLLM:
    """Deterministic double. Assert on what your code DOES with a response."""
    def __init__(self, replies): self.replies, self.calls = list(replies), []

    def complete(self, **kw):
        self.calls.append(kw)
        return self.replies.pop(0)

def test_refund_requires_confirmation():
    llm = ScriptedLLM([Completion(text="", tool_calls=[{"name": "refund",
                                  "arguments": {"order_id": "A-1", "amount": 40.0}}],
                                  finish_reason="tool_calls", **ZERO_USAGE)])
    result = handle("refund my order A-1", llm=llm)

    assert result.status == "awaiting_confirmation"     # policy, not model behaviour
    assert result.pending.name == "refund"
    assert "You are a support agent" in llm.calls[0]["system"]


# For prompt-quality changes, record real responses once and replay them:
#   pytest --record   -> hits the provider, writes tests/fixtures/*.json
#   pytest            -> replays, so CI is fast, free and deterministic

Note what the test asserts: that a refund goes to a confirmation state, not that the model produced particular words. Tests cover your logic. Model behaviour is covered by evals, which are a different mechanism with a pass rate rather than a boolean, and they live in chapter 18.

A checklist for every call site

  • An explicit model version from your central model file, never a floating alias.
  • An explicit max_tokens, and a check of the finish reason before using the text.
  • An explicit timeout suited to this call, not the SDK default.
  • Retries with jitter and a total deadline, applied only to retryable errors.
  • Token counts, latency, model version and cost logged for every call.
  • A correlation id threaded through so one user request is one trace.
  • Cancellation propagated from the client all the way to the provider.
  • Temperature set deliberately — zero unless you have a reason.

The short version

  1. The API is stateless. Conversation, trimming and summarisation are your code's job, and they are where token cost quietly grows.
  2. Streaming does not reduce total time; it removes dead air. Watch for buffering proxies, mid-stream errors and partial JSON.
  3. Always check the finish reason. Treating a truncated answer as complete is the most common silent bug in this field.
  4. Retry only what is retryable, with jitter, a deadline and a circuit breaker. Retries cost money and can amplify an outage.
  5. Bound concurrency to your rate limit, and give every user request a token and time budget.
  6. One thin seam per provider gives you logging, retries, testing and migration for almost no design cost.
