Vector databases and search

Finding the nearest vectors among millions, fast, while also filtering by tenant and date, and without missing the one document that used the exact term the user typed. The index is the easy part; the interesting decisions are filtering, hybrid retrieval and reranking.

hnsw recall vs latency filtering bm25 fusion reranking

Start by asking whether you need one

Exact nearest-neighbour search over 50,000 normalised vectors is a single matrix multiply. On a laptop that is a few milliseconds, with perfect recall, no index to tune and no service to operate.

python — perfectly adequate for most corpora
import numpy as np

V = np.load("vectors.npy")          # (50_000, 768) float32, already normalised — 150 MB
scores = V @ query                  # ~4 ms, exact
top = np.argpartition(-scores, 20)[:20]
top = top[np.argsort(-scores[top])]

You need a real vector store when one of these is true: the corpus is large enough that a scan is too slow or too big for memory; you need filtered search with correct results; you need concurrent writes and deletes with visibility guarantees; or you need it to survive a restart without a rebuild. Below roughly a hundred thousand chunks, "a numpy array plus a JSON file" is a legitimate architecture and a lot of teams over-engineer past it.

How approximate search works

Above a few hundred thousand vectors, exact search stops being viable and you accept approximation: an index that finds most of the true nearest neighbours, much faster. The measure of "most" is recall@k — the proportion of the true top k the index actually returned.

The three knobs of HNSW

M
Neighbours per node in the graph. Higher means better recall and more memory. 16 is a common default; 32–48 for high-dimensional or hard corpora.
ef_construction
How hard the builder searches when inserting. Higher gives a better graph and a slower build. 128–200 is typical. Build time is one-off; recall is forever.
ef_search
How hard a query searches. The one you tune at runtime: raise it for recall, lower it for latency. Must be at least k, and is usually 2–8× k.
The recall–latency trade-off Illustrative curves for a one-million-vector HNSW index. The shape is what matters: recall is cheap up to about 95% and expensive after.

Measure recall, do not assume it

Take 200 sample queries, run them against a brute-force scan to get ground truth, then compare with your index. If recall@10 is 0.86, roughly one in seven relevant passages never reaches the model — and you will misdiagnose that as a prompting problem for weeks. This measurement takes an hour and should be a scheduled job, because recall drifts as the corpus grows.

Filtering, and why it is the hard part

Real queries are almost never "nearest neighbours in the whole corpus". They are "nearest neighbours within this tenant, in English, published after January, excluding archived documents". How the store implements that determines whether your results are correct.

StrategyHowProblem
Post-filterFetch top 100 by vector, then discard non-matchingIf the tenant is 0.1% of the corpus, you get zero results. Silent, common, and disastrous in multi-tenant systems
Pre-filterFind matching ids first, then search only thoseCorrect, but if the subset is large you are back to brute force
Filtered graph traversalApply the predicate during the walk, skipping non-matching nodesThe good answer, and what mature stores do. Can degrade when the filter is very selective and the graph becomes disconnected
PartitioningA separate index (namespace, collection, partition) per tenantCorrect and fast, with strong isolation. Costs overhead per partition, so it does not suit a hundred thousand tiny tenants
Multi-tenancy is a correctness requirement

Never rely on post-filtering for tenant isolation. Use a native partition or namespace per tenant where the store supports it, and enforce the filter server-side — never from a value the client sends. A retrieval bug that returns another customer's document is a data breach, not a relevance problem, and it will not show up in your quality metrics.

Hybrid search

Chapter 9 listed what embeddings miss: exact identifiers, rare jargon, product codes, error strings, names. Keyword search catches exactly those and misses everything vector search is good at. Running both and combining is not a refinement — on most real corpora it is worth more than any other single retrieval change.

BM25 (keyword)

Ranks by term overlap, weighting rare terms higher and normalising for document length.

  • Finds NW-8842, ERR_TLS_CERT, "Vollkornbrot"
  • Zero results when vocabulary differs
  • No training, no embedding cost, instantly updatable

Vector (semantic)

Ranks by meaning in embedding space.

  • Finds "billed twice" for "charged two times"
  • Blind to negation, numbers and exact strings
  • Needs an embedding pass and an index

Combining them: reciprocal rank fusion

The two score scales are incomparable — BM25 is unbounded, cosine sits in a narrow band — so do not add them. Fuse the ranks instead. Reciprocal rank fusion is three lines, has one parameter that barely matters, and is remarkably hard to beat.

fusion.py — RRF, and why it works
def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """rankings: several ordered lists of document ids, best first."""
    scores: dict[str, float] = {}
    for ranking in rankings:
        for position, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + position + 1)
    return sorted(scores.items(), key=lambda kv: -kv[1])


vector_hits  = [h.id for h in vector_search(query, limit=50)]
keyword_hits = [h.id for h in bm25_search(query,  limit=50)]
fused = rrf([vector_hits, keyword_hits])[:20]

# k=60 flattens the difference between ranks 1 and 2 so that a document
# appearing at rank 5 in BOTH lists outranks one that is first in only one.
# That consensus behaviour is the entire value of the method.
postgres — hybrid search in one query, no extra services
WITH semantic AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> :qvec) AS rank
  FROM chunks
  WHERE tenant_id = :tenant AND lang = :lang AND NOT archived
  ORDER BY embedding <=> :qvec
  LIMIT 50
),
keyword AS (
  SELECT id, ROW_NUMBER() OVER (
           ORDER BY ts_rank_cd(tsv, websearch_to_tsquery('english', :q)) DESC) AS rank
  FROM chunks
  WHERE tenant_id = :tenant AND lang = :lang AND NOT archived
    AND tsv @@ websearch_to_tsquery('english', :q)
  LIMIT 50
)
SELECT c.id, c.text, c.source, c.updated_at,
       COALESCE(1.0 / (60 + s.rank), 0) + COALESCE(1.0 / (60 + k.rank), 0) AS score
FROM chunks c
LEFT JOIN semantic s ON s.id = c.id
LEFT JOIN keyword  k ON k.id = c.id
WHERE s.id IS NOT NULL OR k.id IS NOT NULL
ORDER BY score DESC
LIMIT 20;

That query is worth studying because it is a complete production retrieval layer in one place: tenant isolation in the WHERE clause of both arms, vector and keyword retrieval, and rank fusion — with transactional consistency between your documents and your vectors, which a separate vector service cannot give you.

Reranking

Retrieval is a recall problem: cast a wide net, get the right passage somewhere in the top 50. Reranking is a precision problem: take those 50 and order them properly before the top 5 go into the prompt.

The difference in mechanism is the reason it works so well. An embedding model is a bi-encoder — it encodes query and document separately, so nothing about the query can influence how the document is read. A reranker is a cross-encoder: it reads the query and the document together in one pass and outputs a relevance score. That is far more accurate and far too slow to run over a whole corpus, which is exactly why it belongs in a second stage over a shortlist.

python — reranking, hosted or local
# Hosted rerank endpoint
ranked = cohere.rerank(model="rerank-v3.5", query=query,
                       documents=[c.text for c in candidates], top_n=5)
best = [candidates[r.index] for r in ranked.results if r.relevance_score > 0.3]

# Or locally, with a small cross-encoder - a few hundred MB, runs on CPU
from sentence_transformers import CrossEncoder
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3", max_length=512)
scores = reranker.predict([(query, c.text) for c in candidates])
best = [c for _, c in sorted(zip(scores, candidates), key=lambda p: -p[0])[:5]]
Where reranking actually earns its keep

Unlike embedding similarity, a reranker sees both texts at once, so it handles negation, qualifiers and specificity — it can tell that "refunds are not available on sale items" does not answer "can I refund a sale item?". Adding a reranker is typically the single largest quality jump available to an existing RAG system, and it costs about 100ms and a fraction of a cent.

The honest default: if you run Postgres, start with pgvector. Keeping vectors in the same transaction as the documents they came from removes an entire category of consistency bug — no dual-write problem, no "the document was deleted but its chunks are still being retrieved". Move to a specialist store when you have measured a specific limit, not in anticipation of one.

postgres — a schema that will not need re-ingesting
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id            bigserial PRIMARY KEY,
  tenant_id     uuid        NOT NULL,
  document_id   uuid        NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  chunk_index   int         NOT NULL,
  text          text        NOT NULL,
  token_count   int         NOT NULL,
  content_hash  text        NOT NULL,          -- skip re-embedding unchanged chunks
  embedding     vector(768) NOT NULL,
  embed_model   text        NOT NULL,          -- what needs rebuilding when you switch
  lang          text        NOT NULL,
  source_url    text,
  section_path  text,                          -- "Billing > Refunds > Sale items"
  updated_at    timestamptz NOT NULL DEFAULT now(),
  archived      boolean     NOT NULL DEFAULT false,
  tsv           tsvector GENERATED ALWAYS AS (to_tsvector('english', text)) STORED
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 128);
CREATE INDEX ON chunks USING gin  (tsv);
CREATE INDEX ON chunks (tenant_id, document_id, chunk_index);

-- Per query: SET LOCAL hnsw.ef_search = 100;   -- tune recall per request, not globally

Operating it

  • Measure recall against brute force on a sample, on a schedule. It drifts as the corpus grows.
  • Track p50 and p99 query latency separately from the LLM call, so you know which half of a slow response to fix.
  • Plan for rebuilds. Changing the embedding model, the dimensions or the chunking means a full re-index. Build behind a version field and swap atomically rather than mutating in place.
  • Handle deletes properly. Most graph indexes only mark deletions; without compaction, removed documents keep consuming memory and can still be traversed.
  • Keep the source of truth outside the index. The vector store should be rebuildable from your documents at any time. Treat it as a derived cache, not a database of record.
  • Log every retrieval — query, filters, candidate ids, scores, what survived reranking. Without this, debugging a bad answer is guesswork (chapter 13).

The short version

  1. Under about a hundred thousand vectors, a brute-force scan is exact, fast and simpler than any index.
  2. HNSW is the default approximate index. ef_search is the runtime knob; recall is cheap to about 95% and expensive after.
  3. Measure recall against ground truth. Missing passages get misdiagnosed as prompting problems.
  4. Filtering strategy decides correctness. Never post-filter for tenant isolation — use native partitions and enforce server-side.
  5. Hybrid search beats either half. Fuse ranks with RRF rather than trying to reconcile incompatible score scales.
  6. A cross-encoder reranker over the top 50 is usually the single biggest quality win available, for 100ms.
  7. If you already run Postgres, start with pgvector. Keep the index rebuildable and treat it as derived data.
