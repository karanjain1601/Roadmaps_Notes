Chapter 20 · Taking it to production

The AI-assisted development workflow

You are building with these models; you are also building using them. The engineers who get the most out of coding assistants are not the ones who accept the most suggestions — they are the ones who have worked out what to delegate, what to specify precisely, and what to never stop reading carefully.

Three modes, three uses

ModeWhat it isBest atWorst at
Inline completionSuggestions as you type, from surrounding codeBoilerplate, repetitive structures, the obvious next line, test cases following a patternAnything requiring a decision. It will confidently complete a wrong approach
Chat in the editorConversation with file and selection contextExplaining unfamiliar code, targeted refactors, debugging with a stack trace, writing a function to a clear specChanges spanning many files; anything needing to run the code
Agentic CLI or IDE agentAn agent with file, shell and test access working a task to completionMulti-file changes, migrations, "make the failing tests pass", scaffolding, mechanical refactors at scaleAmbiguous requirements, architectural decisions, anything where being 80% right is worse than not starting
Match the mode to how well you can specify the outcome

The strongest predictor of a good result is whether you could have written a precise ticket for it. "Add pagination to the orders endpoint following the pattern in products.py, with tests" is a well-specified task and an agent will do it well. "Make the checkout flow better" is not a task, and no amount of model capability rescues it. When you cannot specify it, that is a signal to think, not to prompt.

Context is the whole game

Every one of these tools is a model with a context window, and everything from chapters 05 and 06 applies. A coding agent that produces code inconsistent with your conventions is almost always an agent that was never shown your conventions.

The project context file

Most agentic tools read a project-root instruction file — CLAUDE.md, AGENTS.md, .cursorrules, or an equivalent — on every session. It is the highest-leverage file in the repository, and the one people write once and never revisit.

CLAUDE.md — specific enough to change behaviour
# Northwind API

Python 3.12, FastAPI, Postgres via SQLAlchemy 2.0 async, pytest.
Package management with uv. Never edit `uv.lock` by hand.

## Commands
- Install: `uv sync`
- Test: `uv run pytest` (a single file: `uv run pytest tests/test_orders.py -x`)
- Lint and format: `uv run ruff check --fix && uv run ruff format`
- Types: `uv run mypy src/`
- Migrations: `uv run alembic revision --autogenerate -m "..."`

## Conventions
- Async everywhere. No sync database calls in request handlers.
- Pydantic models in `schemas/`, ORM models in `models/`. Never return an ORM
  object from a route; always map to a schema.
- Custom errors subclass `AppError` and are handled centrally. Do not add
  try/except in route handlers.
- Tests use factories in `tests/factories.py`, never raw fixtures.
- Structured logging via `log.info("event_name", key=value)`. No f-strings in logs.

## Do not
- Do not add dependencies without asking. We have a review process.
- Do not modify `alembic/versions/*` once merged.
- Do not use `datetime.now()` — use `now_utc()` from `src/clock.py` so tests
  can freeze time.
- Do not write new code in `legacy/`. It is being retired.

## Where things are
- Routes: `src/api/routes/`      - Business logic: `src/services/`
- DB access: `src/repositories/` - Background jobs: `src/workers/`
What earns its placeWhy
Exact commandsOtherwise the agent guesses pytest when you use uv run pytest, and wastes turns discovering that
Conventions that are not inferableThe model reads your code and infers most patterns. Write down what it cannot see: the rule you enforce in review but that older files violate
Explicit prohibitionsThe highest-value section. "Do not" instructions are followed well and prevent whole categories of unwanted change
A map of the codebaseSaves exploratory turns and improves the odds that new code lands in the right place
GotchasThe test that needs a database, the service that must start first, the migration that cannot be autogenerated
Update it when you correct the same thing twice

The context file should grow from friction. Any time you tell the agent something you have told it before — in this session or a previous one — that instruction belongs in the file. This is the single habit that separates people who find these tools transformative from people who find them mildly useful. Keep it under a page or two; a bloated file dilutes attention exactly as chapter 06 describes.

Working with an agentic tool

1 · Plan before codeAsk for an approach first. Reading a plan costs thirty seconds; reviewing the wrong implementation costs thirty minutes
↓
2 · Small, verifiable unitsOne coherent change per session. Long sessions accumulate context and drift
↓
3 · Give it a feedback loopA failing test, a type error, a reproduction script. An agent that can run something converges; one that cannot, guesses
↓
4 · Commit at every working stateClean checkpoints make it safe to let the agent try something ambitious and safe to discard it
↓
5 · Review as if from a strangerBecause it is. Confident, fluent, unfamiliar with your intent
Delegate, pair, or do it yourself? The judgement that matters most. Describe the task honestly.

Reviewing generated code

Generated code has a distinct risk profile. It is syntactically clean, plausibly structured, and confident — which defeats the pattern-matching that ordinary code review relies on. Sloppy human code announces itself; generated code does not.

CheckWhy it is specific to generated code
Does the dependency exist?Models invent plausible package names. Attackers register those names — "slopsquatting" is a real supply-chain attack. Verify every new import
Does the API exist, in this version?Method signatures from a different major version look completely correct and fail at runtime
Are the error paths real?A bare except: pass, or a handler that logs and continues into a broken state. Very common, very quiet
Is the security thinking present?String-interpolated SQL, missing authorisation checks, secrets in code, permissive CORS. Models reproduce the average of their training data, and the average has vulnerabilities
Are the tests real tests?Generated tests often assert that mocks were called rather than that behaviour is correct. A test that cannot fail is worse than no test
Is it duplicating something?Agents write new helpers rather than finding existing ones. Watch for a fourth date-formatting utility
Is it more complex than the problem?Models tend toward elaborate general solutions — abstract base classes and configuration for a case with one caller
Does it handle the boring cases?Empty list, null, unicode, timezone, concurrent access. Happy paths are generated flawlessly; the edges get less attention
Never merge code you have not read and understood

This is not conservatism — it is the ownership boundary. Once it is merged it is your team's code, and "the model wrote it" is not an answer during an incident. If a change is too large to review properly, it was too large to generate in one go; break the task down and generate it in reviewable pieces. The failure mode to avoid is a codebase nobody on the team can explain.

Where it genuinely shines

Explaining unfamiliar code
Possibly the highest-value use overall. Paste a function nobody understands and ask what it does and why. Onboarding to a legacy codebase went from weeks to days.
Tests for existing code
Behaviour is already defined, so the specification problem disappears. Review that the assertions test behaviour rather than implementation.
Mechanical refactors at scale
Renaming across a hundred files, migrating a pattern, updating call sites for a changed signature. Tedious, well-specified, verifiable.
The first draft of anything unfamiliar
A Terraform module, a GitHub Actions workflow, a regex, a shell pipeline. You get 80% of something you would have spent an hour researching, and you know enough to check it.
Debugging with a stack trace
Paste the error, the relevant code and what you expected. Strong at narrowing the search space, even when it does not find the bug.
Translation between languages and formats
JSON to a typed schema, a curl command to code, one framework's config to another's.
Documentation and commit messages
Reliable, and it removes a task most people postpone.
Code review, as a first pass
Catches the obvious before a human looks. It complements review; it does not replace it.

The habits worth keeping

  • Ask for a plan first on anything non-trivial. It surfaces misunderstandings before they become diffs.
  • Give it something to run. Tests, a type checker, a linter, a reproduction script. Verification is what turns guessing into converging.
  • Commit often, in small pieces. Cheap to revert means safe to experiment.
  • Start a fresh session for a new task. Stale context from a previous problem degrades results and costs tokens.
  • Correct once, then write it down. The second correction belongs in the context file.
  • Say what you do not want as clearly as what you do. Prohibitions are followed well.
  • Keep reading the code. Skill atrophies without use, and your judgement is the thing that makes the tool safe.
  • Watch what it costs. Agentic sessions consume a lot of tokens; know your usage before the invoice tells you.
  • Do not paste secrets or customer data into any assistant whose retention terms you have not read.

Where this unit ends

Twenty chapters ago the question was what an AI engineer actually does. The answer that has accumulated: you take a probabilistic component with no guarantees and build a system around it that has some — through constrained outputs, retrieval you can verify, tools with real authorisation, budgets that hold, evaluation that tells you the truth, and containment for the day something goes wrong.

None of that is model expertise. It is ordinary engineering judgement applied to an unusual component. The models will keep improving and several specifics in these chapters will date; the shape of the work will not, because it comes from the properties of the component rather than from any particular version of it.

The next thing to do is not read more. Pick one of the demos in this unit, rebuild it properly against a real API, put an eval set behind it, and ship it to five people who will tell you when it is wrong.

The short version

  1. Three modes — completion, chat, agent — and the right one depends on how precisely you can specify the outcome.
  2. If you cannot write the ticket, you are not ready to prompt. That is a thinking signal, not a model limitation.
  3. The project context file is the highest-leverage file in the repository. Grow it from friction; keep it short.
  4. Explicit prohibitions work better than almost anything else you can write in it.
  5. Give the agent something it can run. Verification is what separates converging from guessing.
  6. Review generated code for invented dependencies, wrong API versions, fake tests and missing security thinking — its risks differ from human code.
  7. Never merge what you have not understood. Too large to review means it was too large to generate at once.
  8. Delegate the mechanical, pair on the uncertain, and keep your own hands in the code.
