Chapter 18 · Taking it to production

Evaluation and observability

Without evaluation you cannot tell improvement from regression, and every change becomes an argument about vibes. This is the discipline that separates teams who ship AI features from teams who demo them — and it is mostly unglamorous infrastructure built early.

eval sets metrics llm judge tracing monitoring feedback

Why this is harder than testing software

Ordinary softwareLLM application
Same input, same outputSame input, different output — even at temperature 0, because of batching and hardware non-determinism
Correct or incorrectA spectrum: correct, correct but unhelpful, helpful but unfaithful, right answer badly formatted
Assertions are exactExact matching fails on valid paraphrases
Behaviour changes when you change codeBehaviour changes when the provider updates a model you did not touch
Fast and free to runSlow and metered; a thousand-case suite costs real money and minutes

The consequence is that you build a measurement system, not a test suite. It gives you numbers with uncertainty attached, and you make decisions from trends and comparisons rather than from pass/fail.

The three layers

Unit — deterministic assertionsSchema validates, required fields present, forbidden content absent, citations resolve. Milliseconds, free, run on every commit
↓
Offline — the eval set100–500 cases with graded outputs. Minutes and dollars. Run before merge and before any model change
↓
Online — production signalsUser feedback, implicit behaviour, sampled human review. Continuous. The only measure of reality
Start at the top and go down, but start today

Twenty cases in a JSONL file with three assertions each, run from a script, is worth more than a sophisticated evaluation platform you will set up next quarter. The most common failure is not a bad eval system — it is not having one, and discovering three months in that nobody can say whether last week's prompt change helped.

Building the eval set

Where cases come fromPriority
Production failuresHighest. Every bug becomes a permanent case. This is how the suite stays relevant instead of drifting into synthetic irrelevance
Real user inputsHigh. Sample from logs across the actual distribution, including the boring majority
Edge cases you thought ofMedium. Empty input, enormous input, wrong language, mixed languages, emoji, malformed data
Adversarial casesHigh. From chapter 17. Injection, extraction, abuse — treated as regression tests
Synthetic generationLow. Useful for volume and coverage, but systematically easier and cleaner than reality. Always human-reviewed

Choosing metrics that mean something

TaskMeasure
ClassificationAccuracy, and per-class precision and recall. A confusion matrix tells you which pairs the model conflates — usually two adjacent categories, fixable by rewriting their descriptions
ExtractionField-level precision and recall. Distinguish "wrong value" from "missed entirely" — they have different fixes
RAGRetrieval recall, faithfulness, correctness, refusal accuracy (chapter 13)
AgentsTask completion, steps to completion, tool-selection accuracy, cost per completed task, unsafe-action rate
GenerationRubric-based judging plus deterministic constraints on length, format and forbidden content
Everythingp50 and p95 latency, cost per request, error rate, refusal rate
One number hides everything interesting

"Quality: 0.84" tells you nothing actionable. Always slice: by category, by input length, by language, by user segment, by whether retrieval fired. A uniform 0.84 and an 0.84 that is 0.95 on the common path and 0.35 on a segment representing your most valuable customers are entirely different situations, and only the slice reveals which you have.

LLM-as-judge, properly

judge.py — a rubric with explicit criteria beats a vague score
class Judgement(BaseModel):
    criteria: dict[str, bool]        # each rubric point, individually decided
    failures: list[str]              # what specifically went wrong
    verdict: Literal["pass", "partial", "fail"]

JUDGE = """Assess the RESPONSE against each criterion. Decide each independently.

{question}
{response}
{reference}

Criteria:
- factually_matches_reference: no contradictions with the reference
- complete: covers every part of the question
- grounded: no claims beyond the reference
- correct_format: {format_requirement}
- appropriate_tone: professional, direct, no filler

Decide each true or false. List specific failures. Then give an overall verdict.
Judge only what is present. Do not reward length or confidence."""

j = structured_call(Judgement, JUDGE.format(...), model=JUDGE_MODEL, temperature=0)
BiasCountermeasure
Prefers longer answersRubric criteria rather than holistic scores; an explicit instruction not to reward length
Prefers its own family's outputsJudge with a different model family than the one generating
Position bias in comparisonsRandomise order; run both directions and keep only consistent verdicts
Clusters scores in the middleBinary or three-way verdicts. Never a 1–10 scale
Rewards confident phrasingRequire it to cite the specific text supporting each judgement
Drifts when the judge model updatesPin the judge model version; re-validate against human labels after any change
Validate the judge before you trust it

Label fifty cases by hand, run the judge on the same fifty, and measure agreement. Below about 80% agreement, the judge is measuring something other than what you care about, and every decision you make from its numbers is noise. When you disagree with the judge, the rubric is usually the problem — it is ambiguous in exactly the way your instructions to a new colleague would be.

Tracing

A trace is the complete record of one request: every model call, every tool invocation, every retrieval, with inputs, outputs, timings, token counts and costs. It is the single highest-value piece of infrastructure in an LLM application, and it must go in early, because you cannot reconstruct it after the fact.

trace.py — what a span must carry
@dataclass
class Span:
    trace_id: str
    span_id: str
    parent_id: str | None
    kind: Literal["llm", "retrieval", "tool", "embedding", "judge"]
    name: str
    started_at: float
    duration_ms: float

    # For llm spans - store the LITERAL strings sent and received.
    model: str | None = None
    prompt_version: str | None = None
    messages: list[dict] | None = None
    output: str | None = None
    tokens_in: int = 0
    tokens_out: int = 0
    cached_tokens: int = 0
    cost_usd: float = 0.0
    finish_reason: str | None = None
    temperature: float | None = None

    # For retrieval spans
    query: str | None = None
    filters: dict | None = None
    result_ids: list[str] | None = None
    scores: list[float] | None = None

    # Correlation
    user_id_hash: str | None = None       # hashed, never raw
    session_id: str | None = None
    release: str | None = None            # which deploy produced this
    error: str | None = None
  • Store the literal prompt. Not the template, not the variables — the exact string. Half of all debugging ends the moment you read it.
  • Version your prompts and record the version on every span. Otherwise you cannot correlate a quality change with a deploy.
  • Redact before writing. Traces are the biggest accidental PII store in most AI systems (chapter 17).
  • Sample intelligently. Full traces on 100% of errors, 100% of thumbs-down, and 1–5% of successes. Storage is not free and errors are what you need.
  • Link the trace id to the user-visible response so a support report maps to a trace in one lookup.
  • Use OpenTelemetry conventions if you already have tracing. LLM spans in the same system as your HTTP and database spans is worth more than a separate specialised tool.

Operational monitoring

Alongside quality, watch the things that page you at night: p50/p95/p99 latency by stage, error and timeout rate by provider, tokens per request, cost per request and per day, rate-limit rejections, refusal rate, moderation-flag rate, and cache hit rate. Sudden movement in refusal rate or output length is often the first sign that a provider silently updated a model.

Alert on distributions, not just failures

The failures that hurt most are not errors. Average output length dropping 30%, refusal rate doubling, cache hit rate collapsing after a prompt edit, a retrieval score distribution shifting — none of these throw exceptions, and all of them mean something changed. Set alerts on the shape of these distributions, not only on 500s.

↓

↓

↓
5 · It ships behind a flagSmall traffic slice, online metrics compared, then rolled out or rolled back
ci.py — the gate that stops silent regression
TOLERANCE = 0.02          # allow for run-to-run noise

def gate(current: Report, baseline: Report) -> None:
    failures = []

    for metric in ["accuracy", "faithfulness", "refusal_accuracy"]:
        if current[metric] < baseline[metric] - TOLERANCE:
            failures.append(f"{metric}: {baseline[metric]:.3f} → {current[metric]:.3f}")

    # Adversarial cases are not subject to tolerance. They must all pass.
    if current.slice(tag="adversarial").pass_rate < 1.0:
        failures.append(f"adversarial failures: {current.slice(tag='adversarial').failed_ids}")

    # A previously-fixed bug reappearing is always a blocker.
    if current.slice(tag="regression").pass_rate < 1.0:
        failures.append(f"regressions: {current.slice(tag='regression').failed_ids}")

    if current.p95_latency_ms > baseline.p95_latency_ms * 1.25:
        failures.append(f"p95 latency +{current.p95_latency_ms/baseline.p95_latency_ms-1:.0%}")
    if current.cost_per_request > baseline.cost_per_request * 1.3:
        failures.append(f"cost +{current.cost_per_request/baseline.cost_per_request-1:.0%}")

    if failures:
        raise SystemExit("Eval gate failed:\n  " + "\n  ".join(failures))

The short version

  1. You are building a measurement system, not a test suite. Decisions come from trends and comparisons, not pass/fail.
  2. Three layers: deterministic assertions, an offline eval set, online signals. Start with twenty cases in a file today.
  3. Every production failure becomes a permanent case. That is what keeps the suite honest.
  4. Never report one number. Slice by category, length, language and segment — the average hides the problem.
  5. LLM judges work with a rubric of independent criteria, a different model family, and validation against human labels.
  6. Tracing is the highest-value infrastructure you will build. Store the literal prompt; version it; redact before writing.
  7. Check whether a difference is larger than the noise before shipping on it. Small eval sets produce confident illusions.
  8. Gate CI on regression against a baseline, with zero tolerance for adversarial and previously-fixed cases.
