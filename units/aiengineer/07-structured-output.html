Structured output and tool calling

The moment a model's output has to be consumed by code rather than read by a person, prose becomes a liability. Schemas turn a fuzzy generator into a typed function — and the same mechanism, pointed the other way, is how a model calls into your systems.

json schema constrained decoding validation tool loop tool design failure modes

Three levels of guarantee

There are three ways to get JSON out of a model, and they are not equivalent. Know which one you are using, because the failure rate differs by orders of magnitude.

LevelMechanismGuaranteesFailure rate
1. Ask nicely"Return JSON matching this shape" in the promptNothing1–10% depending on model and input weirdness. Markdown fences, preambles, trailing commentary, invented fields
2. JSON modeA provider flag that forces syntactically valid JSONIt parsesNear zero parse failures, but the shape is still unconstrained: missing fields, extra fields, wrong types
3. Constrained decodingA schema supplied to the API; the sampler is restricted at each token to only those that can still satisfy itIt parses and matches the schemaEffectively zero structural failures. Semantic errors remain — a valid schema can hold a wrong answer
Level 3 goes by names like structured outputs, strict schema, or response format with a JSON schema. On open models the same effect is achieved with grammar-constrained sampling (chapter 8).
The distinction that matters

Constrained decoding removes an entire class of production bug: you will never again see a 3am page for a trailing comma. It does not make the content correct. A schema guarantees {"refund_amount": 40000.00} is well-formed; only validation, business rules and evals catch that it should have been 40.00.

from typing import Literal
from pydantic import BaseModel, Field

class TicketAnalysis(BaseModel):
    reasoning: str = Field(description="One sentence of justification. Written FIRST so "

Designing a schema the model can actually fill

A schema that is valid JSON Schema can still be one the model fills badly. These rules come from watching extraction tasks fail.

RuleWhy
Make every uncertain field nullable, and say when null is correctThe single biggest cause of invented data. A non-nullable order_id forces the model to produce something; it will produce a plausible-looking reference number
Use enums, not free strings, wherever the set is closedConstrained decoding then makes an out-of-set value impossible, rather than merely unlikely
Put reasoning fields before the fields they justifyGeneration is sequential: a field can only be conditioned on what precedes it. reasoning after category is post-hoc rationalisation and does not improve accuracy
Keep it shallowDeeply nested objects have higher error rates and are harder to validate meaningfully. Two levels is usually plenty; flatten or split into two calls
Write real descriptionsField descriptions are part of the prompt. "amount" versus "the refund amount in the order's original currency, as a decimal number, without a currency symbol" is a large accuracy difference
Name fields for meaning, not storagedelivery_estimate_days beats val2. The name is a hint the model reads
Avoid unions and polymorphismSupport varies, error rates rise, and validation gets complicated. Prefer a discriminator field plus optional fields
Bound your arraysAn unbounded list invites a model to keep going. State a maximum in the description and enforce it in validation
Numbers as numbers, dates as strings with a stated formatAsk for ISO-8601 explicitly. "Next Tuesday" is a legitimate string and a useless date

When it is still wrong: validate and repair

Even with constrained decoding you need a validation layer, because business rules are not expressible in a schema. Give the model the validation error and let it try once more — this fixes the large majority of remaining failures.

repair.py — one retry, with the error as feedback
from pydantic import ValidationError

def extract(text: str, *, attempts: int = 2) -> TicketAnalysis:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user",   "content": text}]

    for attempt in range(attempts):
        raw = llm.complete(messages=messages, schema=TicketAnalysis, temperature=0)
        try:
            parsed = TicketAnalysis.model_validate_json(raw.text)
            check_business_rules(parsed, text)          # raises ValueError
            return parsed
        except (ValidationError, ValueError) as e:
            if attempt == attempts - 1:
                metrics.increment("extract.unrecoverable")
                raise
            metrics.increment("extract.repaired")
            messages += [
                {"role": "assistant", "content": raw.text},
                {"role": "user", "content":
                    f"That response was rejected:\n{e}\n\n"
                    f"Return a corrected version. Change only what the error names."},
            ]

def check_business_rules(a: TicketAnalysis, source: str):
    # Things a schema cannot express, and where hallucination actually hides.
    if a.order_id and a.order_id not in source:
        raise ValueError(f"order_id {a.order_id!r} does not appear in the ticket text")
    if a.refund_requested and a.category == "technical":
        raise ValueError("refund_requested is true but category is technical; re-check")

That order_id not in source check is worth dwelling on. It is a two-line grounding test that catches invented identifiers with complete reliability, and the same pattern — does this extracted value literally appear in the input? — applies to dates, amounts, names and reference numbers. It is the cheapest hallucination detector you will ever write.

Track your repair rate

Count first-attempt successes, repairs and unrecoverable failures as separate metrics. A repair rate creeping from 2% to 15% is an early warning of a model change, a prompt regression or a shift in your input distribution — long before users complain.

Streaming structured output

You cannot JSON.parse a half-finished object. Three workable approaches:

  • Do not stream it. For a small object, buffer and parse. The user waits 800ms for a form to populate — acceptable.
  • Split the response. Stream the prose field as text, and return the structured fields at the end. Works well when there is one long human-readable field and several small machine ones.
  • Use an incremental parser. Libraries that tolerate truncated JSON let you render fields as they complete. Useful for long arrays where each element can appear as it finishes.

Tool calling: the same mechanism, reversed

Instead of constraining the model's output to your data shape, you describe a set of functions and let it produce a structured request to call one. Your code executes it and hands the result back. The model never runs anything — it only asks.

1 · You sendMessages, plus a list of tool definitions with JSON-schema parameters
›
2 · Model replies with a tool callStop reason is tool_calls, not stop. It contains a name, arguments and a call id
›
3 · You executeValidate the arguments, check permissions, run your own function. This is ordinary code you own
›
4 · You append the resultA tool message referencing the call id, containing the output as a string
›
5 · Call againThe model either answers, or asks for another tool. Loop until it stops or you hit your cap

tools.py — definitions and the loop
TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_order",
        "description": ("Look up one order by its reference. Use this whenever the customer "
                        "mentions an order number, before making any claim about its status. "
                        "Returns status, dates, items and totals. Read-only."),
        "parameters": {
            "type": "object",
            "properties": {
                "order_id": {"type": "string",
                             "description": "Reference exactly as the customer wrote it, e.g. NW-8842"}
            },
            "required": ["order_id"],
            "additionalProperties": False,
        },
    },
}]

REGISTRY = {"get_order": get_order_impl}          # name -> callable
MAX_STEPS = 6

def run(user_message: str) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user",   "content": user_message}]

    for step in range(MAX_STEPS):
        r = client.chat.completions.create(model=MODEL, messages=messages,
                                           tools=TOOLS, temperature=0, max_tokens=800)
        msg = r.choices[0].message
        messages.append(msg)                       # keep the assistant turn verbatim

        if r.choices[0].finish_reason != "tool_calls":
            return msg.content or ""

        for call in msg.tool_calls:                # may be several, issued in parallel
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,           # must match, or the API rejects it
                "content": execute(call),
            })

    return "I wasn't able to complete that. Let me pass you to a colleague."


def execute(call) -> str:
    """Never trust the arguments. Validate, authorise, bound the output."""
    fn = REGISTRY.get(call.function.name)
    if fn is None:
        return json.dumps({"error": f"unknown tool {call.function.name}",
                           "available": list(REGISTRY)})
    try:
        args = ToolArgs[call.function.name].model_validate_json(call.function.arguments)
    except ValidationError as e:
        return json.dumps({"error": "invalid arguments", "detail": str(e)})

    if not authorised(current_user, call.function.name, args):
        return json.dumps({"error": "not permitted for this user"})

    try:
        out = fn(**args.model_dump())
    except Exception as e:
        log.exception("tool failed")
        return json.dumps({"error": type(e).__name__, "detail": str(e)[:200]})

    return truncate_json(out, max_tokens=1500)     # a big result will eat your window

Four details in that code are load-bearing and frequently omitted.

  • The assistant message is appended verbatim, including its tool calls. Reconstructing it loses the call ids and the API rejects the follow-up.
  • Errors are returned to the model as tool results, not raised. A well-worded error is information the model can act on — "invalid arguments: order_id must match NW-\d+" often produces a corrected call on the next step. Raising just ends the request.
  • Authorisation is checked in your code, per call, against the real user. The model's opinion about what it should be allowed to do is not an authorisation decision.
  • Results are truncated. An API returning 200,000 tokens of JSON straight into the context is a real and expensive incident.

Designing tools the model uses correctly

Tool-use failures are overwhelmingly caused by tool design, not by model weakness. Treat a tool definition as a user interface whose user happens to be a language model.

PrincipleBadGood
Few tools40 fine-grained tools; selection accuracy collapses and schemas eat 4,000 tokens5–15 well-scoped tools. If you need more, group them behind a router or split into sub-agents (chapter 15)
Unambiguous namessearch, lookup, find all presentsearch_help_articles, get_order, find_similar_tickets
Descriptions say when, not just what"Gets an order""Look up one order by reference. Use before making any claim about order status. Read-only."
Narrow parameters{"query": "any SQL you like"}{"status": enum, "since": date, "limit": int ≤ 50}
Compact resultsThe raw upstream payload with 60 fieldsThe 6 fields that matter, renamed for clarity, dates formatted
Teaching errors{"error": "400"}{"error": "no order NW-884; references look like NW-8842. Ask the customer to confirm."}
Idempotent where possiblecharge_card with no key — a retry double-chargescharge_card(idempotency_key=...), so a repeat is a no-op
Separate read from writeOne tool that reads or updates depending on argumentsDistinct tools, with writes requiring confirmation
Read your tool schemas as a prompt

Serialise your full tool list and read it as if it were the only instruction you received. Would you know which one to reach for, when, and with what arguments? Count the tokens too — it is common for tool definitions to be a third of a system prompt, cached or not.

guards worth having from day one
seen: set[str] = set()

def guard(call, step: int):
    sig = f"{call.function.name}:{call.function.arguments}"
    if sig in seen:
        return json.dumps({"error": "you already made this exact call in this conversation; "
                                    "use the earlier result or try a different approach"})
    seen.add(sig)

    if call.function.name in DESTRUCTIVE:
        # Do not execute. Return a proposal for a human to approve.
        raise NeedsConfirmation(call)

    if step >= MAX_STEPS - 1:
        return json.dumps({"error": "step budget exhausted; give your best answer now"})
    return None
Tools are an authorisation boundary

A tool call is an instruction from an untrusted source — the model may be repeating something a user, a retrieved document or a web page told it to do. Every tool must authorise against the real user's permissions, validate its arguments, run with the narrowest possible scope, and never interpolate model output into SQL, a shell, or a URL without escaping. Chapter 17 covers the attacks in detail.

Model Context Protocol, briefly

MCP is an open protocol for exposing tools, resources and prompts to any model client over a standard interface, so a tool server you write once can be used by different applications without bespoke glue. Practically, it means "connect this assistant to our issue tracker" becomes a configuration step rather than an integration project.

It does not change any of the above: the schemas, the loop, the truncation and the authorisation are all still your responsibility, and a remote MCP server is a third party with access to your model's context. Chapter 15 covers using and writing MCP servers; chapter 17 covers trusting them.

The short version

  1. Three levels of guarantee. Use constrained decoding with a schema whenever your provider offers it — it deletes a whole class of bug.
  2. A schema guarantees shape, never correctness. Keep a validation layer for business rules and check extracted values actually appear in the source.
  3. Design schemas for the generator: nullable uncertain fields, enums, reasoning first, shallow, described.
  4. Feed validation errors back and retry once. Track the repair rate as a leading indicator of regression.
  5. Tool calling is the same mechanism reversed: the model asks, your code executes, authorises and truncates.
  6. Most tool failures are tool design failures. Few tools, clear names, descriptions that say when, narrow parameters, teaching errors.
  7. Cap the steps, detect repeats, and require human confirmation for anything irreversible.
