Open weights and local inference

Running the model yourself buys privacy, offline capability, version stability and — sometimes — a much lower bill. It costs GPUs, an upgrade treadmill and a quality gap you have to measure honestly. This chapter is the decision and the mechanics.

"Open" means several different things

Almost no widely used model is open source in the sense the term means for software. What you usually get is open weights: the trained parameters are downloadable, the training data and code are not, and a licence governs use.

CategoryWhat you getWhat to check

Fine-tunes inherit licences

A model fine-tuned from a restricted base carries the base licence's obligations, and derived datasets generated by a commercial API may carry contractual restrictions on training competing models. Before shipping a fine-tune, trace the lineage: base model licence, dataset licence, and the terms of any API used to generate synthetic data. Get legal to read it once; it is a short document.

Should you self-host at all?

Genuine reasons

  • Data cannot leave your infrastructure. A hard regulatory or contractual constraint, not a preference.
  • Offline or edge. On-device, air-gapped, or a factory with no reliable link.
  • Very high, steady volume of a task a small model handles well — classification, extraction, reranking, embeddings.
  • Version permanence. Nobody deprecates your weights on 60 days' notice.
  • Deep customisation. Full fine-tuning, unusual sampling, logit access, custom grammars.

Reasons that do not survive contact

  • "It'll be cheaper." Only above a utilisation threshold you should calculate first — see below.
  • "We'll avoid lock-in." You trade vendor lock-in for a GPU fleet, an ops burden and a model you must keep upgrading yourself.
  • "No content restrictions." You still need moderation, and now you own the whole problem.
  • "It's more private." Only if your own infrastructure and access controls are actually better than the provider's. Often they are not.

The break-even arithmetic

An always-on GPU costs the same whether it serves one request an hour or a thousand. A hosted API costs nothing when idle. So the question is never "which is cheaper per token" but "at what utilisation does the fixed cost amortise".

How the memory number is built

sizing.py — the estimate the calculator is doing
def vram_gb(params_b: float, bytes_per_param: float,
            ctx_tokens: int, concurrency: int,
            n_layers: int = 32, n_kv_heads: int = 8, head_dim: int = 128) -> dict:

    weights = params_b * 1e9 * bytes_per_param / 1e9

    # KV cache: 2 (K and V) x layers x kv_heads x head_dim x 2 bytes, per token, per request.
    per_token = 2 * n_layers * n_kv_heads * head_dim * 2 / 1e9
    kv = per_token * ctx_tokens * concurrency

    overhead = (weights + kv) * 0.15 + 1.0        # activations, fragmentation, CUDA context

    return {"weights": weights, "kv": kv, "total": weights + kv + overhead}

# 8B at 4-bit, 8k context, 16 concurrent:  4.4 + 2.1 + 2.0 = ~8.5 GB   -> one 24GB card, comfortably
# 70B at 4-bit, 8k context, 16 concurrent: 38.5 + 4.2 + 7.4 = ~50 GB   -> 2x 40GB or 1x 80GB

Two things this makes obvious. The KV cache, not the weights, is what limits concurrency — which is why long-context serving is so much more expensive than the parameter count suggests. And grouped-query attention (few key-value heads) is a huge practical win: it is the difference between serving eight concurrent requests and eighty on the same card.

Quantisation

Storing weights at lower numeric precision shrinks memory and increases speed, at some quality cost. It is what makes useful local models possible on ordinary hardware.

PrecisionBytes/param8B modelQuality impactUse
fp16 / bf16216 GBReferenceTraining, fine-tuning, quality baselines
fp818 GBVery smallModern server GPUs, good throughput win
int818 GBSmall, usually not user-visibleA safe default when memory is tight
4-bit (Q4_K_M, AWQ, GPTQ)~0.554.4 GBModest; noticeable on hard reasoning and long chainsThe workhorse of local inference. Where most people should start
3-bit and below~0.423.4 GBClear degradation; instruction-following gets brittleOnly when memory is the binding constraint
The rule that decides most local setups

A larger model at 4-bit almost always beats a smaller model at 16-bit for the same memory. A 4-bit 13B model outperforms an fp16 7B model on nearly every task while using less VRAM. Choose the biggest model that fits at 4-bit, then measure — do not assume the quantisation cost is negligible for your task, especially structured output and multi-step tool use, which degrade earlier than chat quality does.

The Hugging Face Hub

The registry for open models, datasets and demos. Learn to read it properly; it is the difference between picking a good model in ten minutes and a bad one in three days.

Model card
Licence, intended use, training data notes, evaluation results and limitations. Read the licence and the limitations sections specifically.
Tasks
The Hub is organised by task — text generation, embeddings, reranking, speech recognition, image captioning. Filtering by task is how you discover the small specialist models that beat a general LLM at a fraction of the cost.
Files tab
Tells you the real story: format, shard sizes, whether quantised variants exist. Prefer .safetensors over .bin — pickle-format weights can execute code on load.
Gated models
Some require accepting terms before download. Automate this properly; a CI job that silently fails to fetch weights is a fun outage.
Community quantisations
Popular models get third-party GGUF and AWQ builds within days. Convenient, and an unverified binary from a stranger — check the uploader's track record.
Inference providers
Hosted endpoints for Hub models, either serverless for experimentation or dedicated for production. A good middle path: open weights without running GPUs.
python — from the Hub, three ways
# 1. Local, with transformers — full control, most memory
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_id = "mistralai/Mistral-7B-Instruct-v0.3"
tok = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype=torch.bfloat16,
                                             device_map="auto")

messages = [{"role": "user", "content": "Summarise this incident in two sentences: ..."}]
ids = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt")
out = model.generate(ids.to(model.device), max_new_tokens=200, do_sample=False)
print(tok.decode(out[0][ids.shape[-1]:], skip_special_tokens=True))

# 2. Hosted inference, no GPU of your own
from huggingface_hub import InferenceClient
client = InferenceClient(model=model_id, token=HF_TOKEN)
print(client.chat_completion(messages, max_tokens=200).choices[0].message.content)

# 3. A small specialist model instead of an LLM - often 100x cheaper and better
from transformers import pipeline
ner = pipeline("token-classification", model="dslim/bert-base-NER", aggregation_strategy="simple")
print(ner("Order NW-8842 from Anna Weber shipped from Hamburg on Tuesday."))
Do not use an LLM for a solved task

Named-entity recognition, language identification, sentiment, toxicity classification, translation, embeddings, speech transcription and reranking all have small purpose-built models that run in milliseconds on a CPU and beat a general LLM on accuracy and cost. Before writing a prompt, search the Hub for the task.

Ollama: local development and small deployments

The easiest way to run a model on your own machine. It wraps llama.cpp, manages downloads, and exposes both its own API and an OpenAI-compatible one, so your existing client code works unchanged.

bash — from nothing to a local endpoint
ollama pull llama3.1:8b-instruct-q4_K_M      # tag encodes size and quantisation
ollama run  llama3.1:8b-instruct-q4_K_M      # interactive
ollama ps                                    # what is loaded, and how much memory it holds

# OpenAI-compatible endpoint on :11434 — point your existing client at it
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"llama3.1:8b-instruct-q4_K_M",
       "messages":[{"role":"user","content":"Classify: card charged twice"}],
       "temperature":0}'
Modelfile — bake a system prompt and parameters into a named model
FROM llama3.1:8b-instruct-q4_K_M

PARAMETER temperature 0
PARAMETER num_ctx 8192
PARAMETER stop "</answer>"

SYSTEM """
You classify support tickets. Reply with exactly one of:
billing, shipping, technical, account, other.

Ollama is excellent for development, prototypes, desktop applications and internal tools. It is not built for high-concurrency serving — for that, use vLLM.

Serving properly: vLLM and friends

Production inference servers exist to solve one problem: keeping an expensive GPU busy. The techniques that matter are continuous batching — new requests join the batch as others finish, rather than waiting for a whole batch to complete — and paged attention, which manages KV cache memory in pages so it does not fragment and waste capacity. Together they are worth an order of magnitude in throughput over a naive loop.

bash — an OpenAI-compatible server in one command
pip install vllm

python -m vllm.entrypoints.openai.api_server \
  --model mistralai/Mistral-7B-Instruct-v0.3 \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --api-key "$LOCAL_KEY"

# Now identical to any OpenAI-compatible client:
#   base_url="http://gpu-node:8000/v1"

Structured output on open models

You do not lose schema enforcement by leaving hosted APIs — you gain a stricter version of it. Grammar-constrained sampling masks the token distribution at each step so only tokens that keep the output valid can be chosen.

python — guaranteed JSON from a local model
from pydantic import BaseModel
import requests, json

class Ticket(BaseModel):
    category: str
    urgency: str
    order_id: str | None

r = requests.post("http://localhost:8000/v1/chat/completions", json={
    "model": MODEL,
    "messages": [{"role": "user", "content": ticket}],
    "temperature": 0,
    "guided_json": Ticket.model_json_schema(),   # vLLM: sampling is masked to the schema
})
ticket = Ticket.model_validate_json(r.json()["choices"][0]["message"]["content"])

What self-hosting actually costs you

Beyond the GPU bill, budget for these. They are the reasons self-hosting projects stall.

  • Capacity planning. Peak concurrency, KV cache headroom, what happens when a burst arrives. Queue rather than fail, and load-shed rather than time out.
  • Upgrades. A better open model appears every few months. Someone must evaluate it, migrate prompts and re-run evals — the same treadmill you avoided with a hosted API, now yours.
  • Evaluation. Hosted providers do a lot of quiet quality work. On your own weights, your eval suite is the only thing standing between you and a silent regression.
  • Safety. No built-in moderation. You need your own input and output filtering (chapter 17), and open models are generally easier to jailbreak.
  • Observability. Token throughput, queue depth, cache hit rate, GPU utilisation and memory — plus the application metrics you would have anyway.
  • On-call. A GPU node that OOMs at 2am is now your page.
The hybrid that usually wins

Self-host the high-volume, low-difficulty work — classification, extraction, reranking, embeddings — on one modest GPU, and call a hosted frontier model for the small fraction of requests that need real capability. You capture most of the cost saving and almost none of the quality risk, and the routing logic is twenty lines (chapter 19).

The short version

  1. "Open" usually means open weights under a licence, not open source. Read the licence, and trace it through fine-tunes.
  2. Self-host for privacy, offline, permanence or genuine high steady volume — not to avoid lock-in or to save money by default.
  3. Memory is weights plus KV cache, and the KV cache is what caps concurrency. Long contexts are expensive in a way parameter counts hide.
  4. A bigger model at 4-bit beats a smaller model at fp16 for the same memory. Measure quantisation loss on your own task, especially structured output.
  5. Search the Hub by task: a small specialist model often beats an LLM at a hundredth of the cost.
  6. Ollama for development, vLLM for serving. Both speak the OpenAI API, so the swap is a base URL.
  7. The real cost is the ops and evaluation treadmill. A hybrid — small models local, hard requests hosted — usually beats either extreme.
