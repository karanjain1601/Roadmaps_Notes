Chapter 14 · Adaptation and autonomy

Fine-tuning and other adaptations

Fine-tuning is the most over-requested and least often necessary technique in the field. It is also genuinely the right answer for a specific, recognisable class of problem. This chapter is mostly about telling those apart, and then about doing it properly when the answer is yes.

when not to datasets lora sft dpo distillation

The one thing to understand first

Fine-tuning teaches behaviour, not facts. It shifts the model's distribution toward a style, a format, a way of reasoning about your domain. It is a poor and expensive way to install knowledge, and every project that starts with "we'll fine-tune it on our documentation" ends by rebuilding it as RAG six weeks later.

Fine-tuning is good at

  • A consistent output format or house style
  • A specialised classification or extraction task
  • Domain tone and vocabulary
  • Making a small model imitate a big one on one narrow task
  • Reducing prompt length — the instructions become the weights
  • Latency and cost, via a smaller model that now performs well enough

Fine-tuning is bad at

  • Teaching facts that change (use RAG)
  • Teaching facts at all, reliably — it learns the shape more than the content
  • Anything needing citations or verifiability
  • Broad general capability — it usually narrows the model
  • Fast iteration — every change is a training run
  • Small data. Fifty examples will not do it
The ladder, in order

Work down this list and stop at the first rung that solves the problem. 1. Better prompt. 2. Few-shot examples in the prompt. 3. Retrieval. 4. Tool use. 5. A better model. 6. Decomposition into several calls. 7. Then fine-tuning. Most teams that fine-tune successfully did steps 1–6 first, which is also how they got the dataset: the logs of the prompted system are the training data.

When the answer is genuinely yes

SituationWhy fine-tuning wins
A large model works, but costs too muchDistil it. Use the big model's outputs to train a small one on your single task. 10–50× cheaper inference at comparable quality on that task
Format compliance is imperfectWhen structured output and prompting still leave a few percent of malformed responses, training on 1,000 correct examples usually eliminates the tail
Your prompt is 4,000 tokens of instructionsThose instructions can move into weights. Latency and per-request cost both fall sharply
The task is genuinely unusualClassifying internal ticket taxonomies, extracting fields from a proprietary document format, writing in a specific regulated register
A specialised domain vocabularyMedical, legal or industrial language where general models consistently misread terms
Latency floorA fine-tuned small model running locally answers in tens of milliseconds. No API can
Should you fine-tune? Answer honestly. The recommendation includes the break-even arithmetic, which is usually the deciding factor.

The dataset is the entire project

Everyone focuses on the training run. The training run is a command you type. The dataset is where success is decided, and it takes ninety percent of the effort.

RequirementDetail
Quantity500–1,000 examples for a narrow format or classification task. 5,000–10,000 for anything nuanced. Below 100, use few-shot prompting instead — you cannot beat it
Quality over quantity500 carefully checked examples beat 5,000 scraped ones, consistently. The model learns your mistakes as diligently as your successes
ConsistencyThe single most important property. If two examples handle the same situation differently, you are teaching the model to be inconsistent. Have one person, or one rubric, own the labels
DiversityCover the real input distribution: edge cases, malformed inputs, ambiguous cases, and the boring majority in proportion
Match production exactlySame system prompt, same input formatting, same field order as you will use at inference. A mismatch between training and serving formats degrades results in ways that are very hard to diagnose
Held-out split10–20% never seen in training, used only for evaluation. And an entirely separate golden set for end-to-end comparison against the prompted baseline
Negative and refusal casesInclude examples of declining, of asking for clarification, of handling input the task does not cover. Otherwise the model learns that it must always answer

Your best dataset already exists in your logs

If a prompted system has been running, you have thousands of real inputs with real outputs. Filter to the ones that succeeded — where the user did not rephrase, the structured output validated, the human reviewer approved — and you have a distilled dataset drawn from exactly the production distribution. This is why fine-tuning is usually a step 7 activity: doing steps 1–6 generates the training data as a side effect.

Distillation, concretely

distil.py — big model teaches small model
import json, asyncio

async def build_dataset(inputs: list[str], out: str = "train.jsonl"):
    """Generate with the strong model, keep only what passes checks."""
    sem = asyncio.Semaphore(8)
    kept = dropped = 0

    async def one(text: str):
        nonlocal kept, dropped
        async with sem:
            resp = await strong_model(SYSTEM, text, temperature=0)
        try:
            parsed = TicketLabel.model_validate_json(resp)     # schema must hold
        except ValidationError:
            dropped += 1
            return None
        if parsed.order_ref and parsed.order_ref not in text:  # grounding check
            dropped += 1
            return None
        kept += 1
        return {"messages": [
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": text},
            {"role": "assistant", "content": parsed.model_dump_json()}]}

    rows = [r for r in await asyncio.gather(*(one(t) for t in inputs)) if r]
    with open(out, "w") as f:
        for r in rows:
            f.write(json.dumps(r) + "\n")
    print(f"kept {kept}, dropped {dropped} ({dropped/(kept+dropped):.1%})")

# The filtering is the point. An unfiltered teacher's mistakes become the
# student's permanent behaviour, and you have no way to unlearn them later.

How the training actually works

Full fine-tuning versus LoRA

Full fine-tuning updates every weight: for a 7-billion-parameter model that means optimiser state for 7 billion values, roughly 60–80 GB of GPU memory, and a new full-size model per task.

LoRA (low-rank adaptation) freezes the base model and trains small rank-decomposition matrices injected into the attention layers. You update perhaps 0.1–1% of the parameters, memory drops by an order of magnitude, and the result is an adapter file of tens of megabytes that you load on top of the shared base model. Multiple adapters can be served from one base model, swapped per request.

Full fine-tuneLoRA / QLoRA
Trainable parametersAll of them0.1–1%
GPU memory (7B model)~70 GB+~16 GB (LoRA), ~8 GB (QLoRA)
Artefact sizeFull model, 14 GB+Adapter, 10–200 MB
ServingOne deployment per variantMany adapters on one base
QualitySlightly higher ceilingWithin a point or two for most tasks
Catastrophic forgettingReal riskMuch lower — base weights untouched
QLoRA quantises the frozen base to 4-bit while training the adapter in higher precision, which is what makes fine-tuning a 7B model on one consumer GPU possible. Use LoRA unless you have a measured reason not to.
train_lora.py — a realistic starting configuration
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer, SFTConfig

lora = LoraConfig(
    r=16,                      # rank: 8-16 for style, 32-64 for harder tasks
    lora_alpha=32,             # conventionally 2 × r
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",     # attention
                    "gate_proj", "up_proj", "down_proj"],       # and MLP: better results
)

args = SFTConfig(
    output_dir="out/ticket-classifier-v3",
    num_train_epochs=3,               # 2-4. More overfits fast on small data
    learning_rate=2e-4,               # LoRA wants ~10x a full fine-tune's LR
    lr_scheduler_type="cosine",
    warmup_ratio=0.03,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,    # effective batch 16
    max_seq_length=2048,
    bf16=True,
    gradient_checkpointing=True,      # trades ~20% speed for a lot of memory
    logging_steps=10,
    eval_strategy="steps",
    eval_steps=50,
    save_strategy="steps",
    load_best_model_at_end=True,      # keep the best checkpoint, not the last
)

trainer = SFTTrainer(model=base, args=args, peft_config=lora,
                     train_dataset=train, eval_dataset=held_out)
trainer.train()
trainer.save_model()                  # ~40 MB adapter, not a 14 GB model

Reading the loss curves

Training loss falls, eval loss falls
Working. Keep going.
Training loss falls, eval loss rises
Overfitting. Stop at the point eval loss bottomed out — this is why load_best_model_at_end matters. Fewer epochs, more data, or more dropout.
Neither moves
Learning rate too low, rank too small, or the task is not learnable from this data. Check the data first — usually the labels are inconsistent.
Loss spikes or goes to NaN
Learning rate too high, or a precision problem. Lower the LR, add warmup, verify bf16 support.
Loss looks great, outputs are worse
Train/serve mismatch: different system prompt, different formatting, or a chat template applied in training but not at inference. Check the literal tokenised strings on both sides.

Beyond supervised tuning

MethodWhat it needsWhat it is for
SFT — supervised fine-tuningInput → ideal output pairsThe default. Teaching a task, a format, a style
DPO — direct preference optimisationInput + preferred output + rejected outputTeaching preferences that are easy to compare but hard to specify: tone, helpfulness, "not like that". Simpler and more stable than RLHF, and now the standard choice
ORPO / KTOPreference data, sometimes unpairedVariants that fold preference learning into a single stage, or work with thumbs-up/down rather than paired comparisons — useful because that is the data products actually collect
RLHF / PPOA trained reward model, plus RL infrastructureWhat frontier labs use. Powerful, unstable, expensive. Rarely the right call for an application team
Continued pre-trainingLarge volumes of raw domain textAdapting a model to a genuinely different domain or language. Needs billions of tokens; a research-scale undertaking
preferences.jsonl — DPO wants three fields, not two
{"prompt": "Customer asks why their refund is late, 9 working days after return.",
 "chosen": "Your refund was issued on 3 March and typically reaches the account within 5-10 working days, so it should arrive by 17 March. If it hasn't by then, reply here with your order number and I'll chase the payment provider directly.",
 "rejected": "Refunds take 5-10 working days. Please wait."}

Note what the pair teaches: not facts, but a manner — specificity, a concrete date, an explicit next step. That is exactly the kind of thing preference tuning does well and prompting does inconsistently. The data comes naturally from an editing workflow: whenever a human corrects a draft, you have a rejected/chosen pair.

Costs, honestly

ItemReality
Dataset constructionThe dominant cost. Days to weeks of human effort. Budget for it explicitly or the project stalls here

Self-hosted inferenceCheap per token, but you are now operating a GPU service (chapter 08)
MaintenanceThe hidden one. Every base model upgrade means retraining and re-evaluating. Your fine-tune is frozen against a model that keeps improving without you
The maintenance trap

A fine-tuned model is a fork. Six months later the base has improved substantially and your fine-tune has not. You must periodically re-run the whole exercise on the new base and re-evaluate against the prompted baseline — and quite often you will find the new base model, simply prompted, now beats your fine-tune. That is a good outcome, but only if you check. Schedule the comparison; do not let the fork ossify.

The workflow, end to end

1 · Establish the baselineBest prompted version, measured on a golden set. If you cannot state this number, stop
↓
2 · Build and clean the datasetFrom logs where possible. Check consistency. Hold out 15%
↓
3 · Train small first500 examples, 2 epochs, small rank. Confirm the pipeline works before spending
↓
4 · Evaluate against the baselineSame golden set, same metrics. Also check it did not lose general ability
↓
5 · Scale what workedMore data before more epochs; more rank only if underfitting
↓
6 · Ship behind a flagRoute a slice of traffic. Compare online. Keep the prompted path warm as a fallback
  • Test for regression, not just improvement. A model fine-tuned to classify tickets may have lost the ability to refuse, to handle another language, or to follow safety guidelines. Run a general-capability set as well as the task set.
  • Version everything — dataset hash, base model, hyperparameters, adapter — and record which produced which evaluation number.
  • Keep the prompted path. It is your fallback, your comparison and your escape route when the base model is upgraded.
  • Watch for safety drift. Fine-tuning on narrow data can weaken alignment behaviours; re-test refusals explicitly (chapter 17).
  • Do not fine-tune on model output you have not filtered. Errors compound silently across generations.

The short version

  1. Fine-tuning teaches behaviour, not facts. For facts, use retrieval — every time.
  2. Work the ladder: prompt, few-shot, retrieval, tools, better model, decomposition. Fine-tuning is step seven, and those steps generate the dataset.
  3. The clearest win is distillation: a small fine-tuned model matching a large prompted one on one narrow task, far cheaper.
  4. The dataset is the project. Consistency matters more than volume; 500 clean examples beat 5,000 scraped ones.
  5. Training and serving formats must match exactly — the commonest cause of "loss looked fine, outputs got worse".
  6. Use LoRA unless measurement says otherwise: 1% of the parameters, an adapter you can swap, far less forgetting.
  7. DPO for preferences you can compare but not specify. The data falls out of any human editing workflow.
  8. Fine-tuning creates a fork. Re-run the comparison against a plain prompt on each new base model — sometimes you get to delete the fine-tune.
