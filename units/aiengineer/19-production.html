Shipping and running it

Everything to this point was about making the model do the right thing. This chapter is about the system around it: the architecture, the caching, the fallbacks, and the operational habits that keep a feature working on a Tuesday afternoon when a provider is having a bad day.

The gateway is the piece teams most often skip and most often regret. Every model call in your codebase going through one component means provider switching, fallbacks, cost tracking, caching and rate limiting are each implemented once. Without it they are implemented never, or eleven times inconsistently.

gateway.py — the seam everything else depends on
@dataclass
class Route:
    primary: str                       # "anthropic:claude-x"
    fallbacks: list[str]               # tried in order on failure
    max_retries: int = 2
    timeout_s: float = 30.0
    cache: Literal["none", "exact", "semantic"] = "exact"

ROUTES = {
    "classify":  Route("openai:small",  ["anthropic:small"], cache="exact"),
    "answer":    Route("anthropic:mid", ["openai:mid", "local:llama"], cache="semantic"),
    "summarise": Route("openai:small",  ["local:llama"], cache="exact"),
    "judge":     Route("anthropic:mid", [], cache="none"),      # never cache judging
}

async def complete(task: str, messages: list[dict], ctx: RequestContext, **kw):
    route = ROUTES[task]
    if route.cache != "none" and (hit := await cache_get(task, messages, route)):
        metrics.incr("llm.cache_hit", task=task)
        return hit

    last_error = None
    for model_id in [route.primary, *route.fallbacks]:
        for attempt in range(route.max_retries + 1):
            try:
                with trace.span("llm", model=model_id, task=task) as span:
                    result = await providers[model_id].complete(
                        messages, timeout=route.timeout_s, **kw)
                    span.record(result)
                budget.charge(ctx, result.cost_usd)
                await cache_put(task, messages, route, result)
                return result
            except RateLimited as e:
                await asyncio.sleep(e.retry_after or backoff(attempt))
                last_error = e
            except (Timeout, ServerError) as e:
                last_error = e
                if attempt == route.max_retries:
                    break                       # move to the next model
            except BadRequest:
                raise                           # our bug: do not retry, do not fail over
    raise AllProvidersFailed(task) from last_error
Fail over on the right errors only

Retry and fall back on rate limits, timeouts and 5xx responses. Do not retry a 400 — a malformed request will be malformed at the next provider too, and you will have burned the fallback budget hiding your own bug. Context-length errors are their own case: shorten the input rather than switching model, unless the fallback has a larger window, in which case switching is exactly right.

Caching, in four layers

LayerMechanismTypical effect
Prompt prefix cacheProvider-side, on the stable start of your prompt (chapter 05)Large cost and latency reduction on long system prompts. Nearly free to adopt
Exact response cacheHash of model + parameters + full message array → responseExcellent for classification and extraction, where inputs repeat. Useless for open chat
Semantic cacheEmbed the query; serve a stored answer if similarity exceeds a thresholdReal savings on FAQ-shaped traffic, and a real risk of serving a subtly wrong answer. Threshold high, scoped per tenant, never for personalised replies
Derived-artefact cacheStore the output of expensive one-off work: document extraction, summaries, embeddingsThe biggest saving of all, and the most often missed. Never recompute what has not changed
cache.py — exact caching, with the keys that matter
def cache_key(task: str, messages: list[dict], model: str, params: dict) -> str:
    payload = json.dumps({
        "task": task, "model": model, "messages": messages,
        "temperature": params.get("temperature"),
        "prompt_version": PROMPT_VERSIONS[task],   # invalidates on prompt change
        "schema": params.get("schema_hash"),
    }, sort_keys=True)
    return "llm:" + hashlib.sha256(payload.encode()).hexdigest()

# Cache only where it is safe:
#   temperature > 0        -> caching removes variety users may expect
#   personalised content   -> never cache across users
#   time-sensitive answers -> short TTL, or do not cache
#   tool-calling turns     -> do not cache; the world may have changed

Streaming, and the UX around it

Streaming does not make anything faster. It changes a four-second blank screen into visible progress starting at 700 milliseconds, which users experience as a different product.

  • Stream by default for anything conversational or long. Skip it for structured output the user never sees.
  • Show stage progress in multi-step flows: "searching the documentation", "reading three sources". A spinner for eight seconds feels broken; labelled progress does not.
  • Make it interruptible. A stop button that actually cancels the upstream request — and stops billing for the tokens you no longer want.
  • Handle mid-stream failure. Errors can arrive after tokens have already rendered. Decide whether to keep partial output or replace it, and be consistent.
  • Watch the proxy layer. Buffering proxies and some serverless platforms defeat streaming entirely; test the real deployed path, not localhost.
  • Render markdown incrementally without flicker, and hold back partial links, code fences and tables until they close.
  • For long jobs, use a queue. Anything beyond about thirty seconds should be a background job with a progress channel, not a held-open request.

Failure modes and their responses

FailureResponse
Provider rate limitRespect retry-after, back off with jitter, then fail over. Track headroom against your quota as a metric
Provider outageFail over to a second provider. This is the main reason to keep the gateway abstraction honest — and to test the fallback path deliberately
Elevated latencyCircuit-break after N slow responses and route elsewhere. A slow provider is worse than a failed one, because it ties up your capacity
Context length exceededTruncate history, drop the lowest-ranked retrieved passages, or route to a larger-window model. Never just error
Malformed structured outputRetry once with the validation error fed back; then fall back to a simpler schema or a default (chapter 07)
Content filteredA clear message, not a stack trace. Log the category; watch the rate
Retrieval emptySay so honestly rather than answering unsourced (chapter 12)
Budget exhaustedDegrade to a cheaper model or a non-AI path. Decide in advance whether the feature fails closed or degrades
Test the fallback path on purpose

A fallback that has never executed is not a fallback; it is untested code with a comforting name. Force it in staging — block the primary provider, exhaust a quota, inject timeouts — and confirm the second path produces acceptable output. Different providers have different tokenisers, different tool-calling formats and different behaviour on the same prompt. Discovering that during an outage is the wrong time.

Controlling spend

ControlDetail
Per-request capA hard token and cost ceiling on every request. Especially for agents, which can loop
Per-user quotasDaily or monthly limits by plan tier. Without these, one user can cost more than a hundred others combined
Global circuit breakerAn automatic stop if daily spend exceeds a threshold. The protection against a deploy that accidentally loops
Model routing by difficultyClassify the request, send the easy majority to a small model, escalate the rest. Often halves cost with no measurable quality loss
Batch what can waitOvernight work at roughly half price through batch endpoints
Attribute costTag every call with feature, tenant and user. "We spend $9,000 a month on LLMs" is not actionable; "$6,200 of it is document summarisation for three enterprise accounts" is
Alert on rate of changeCost per request doubling matters more than absolute spend, and shows up sooner
router.py — difficulty routing, with a verification pass
async def answer(question: str, ctx: RequestContext) -> Answer:
    difficulty = await classify_difficulty(question)        # small model, ~80ms

    if difficulty == "simple":
        result = await complete("answer", build(question), ctx, model_hint="small")
        if await looks_uncertain(result):                   # hedging, refusal, low confidence
            metrics.incr("router.escalated")
            result = await complete("answer", build(question), ctx, model_hint="mid")
        return result

    return await complete("answer", build(question), ctx,
                          model_hint="large" if difficulty == "hard" else "mid")

# mis-routing and you are paying for two calls to do one job.

Deployment habits

  • Pin model versions. Never point production at a floating alias. A silent model update will change your outputs, your latency and your costs on a schedule you do not control.
  • Version prompts and deploy them like code — reviewed, versioned, rolled back. A prompt edit is a production change with no type checking, which makes review more important, not less.
  • Feature-flag every AI feature for percentage rollout and instant disable. The kill switch is the most important operational control you have.
  • Run evals in CI against a baseline, with zero tolerance on adversarial and regression cases (chapter 18).
  • Shadow-test model upgrades. Run the new model on live traffic without serving its output, compare on your eval set and on real distributions, then switch.
  • Keep a non-AI path where you can. Search that still works, a form that still submits, a human who can be reached.
  • Document the runbook: how to disable the feature, how to switch providers, who to contact, what the budget alerts mean.

The pre-launch list

Correctness

  • Eval suite passing against a baseline
  • Adversarial suite at 100%
  • Refusal behaviour verified
  • Citations verified where applicable

Resilience

  • Fallback path exercised for real
  • Timeouts and retries on every call
  • Context-overflow path tested
  • Kill switch tested in production

Safety

  • Tools scoped to the session user
  • Output sanitised before render
  • PII redacted from logs
  • Moderation both directions

Operations

  • Tracing on, sampled, redacted
  • Cost attribution and alerts
  • Latency dashboards by stage
  • Runbook written and findable

The short version

  1. Put every model call behind one gateway. Routing, retries, fallbacks, caching and cost accounting are then implemented once.
  2. Fail over on rate limits, timeouts and 5xx — never on your own malformed requests.
  3. Four caching layers. The most valuable and most forgotten is caching derived artefacts: never recompute what has not changed.
  4. Streaming does not make it faster; it makes it feel like a working product. Show stage progress and allow interruption.
  5. A fallback path that has never run is not a fallback. Force it in staging.
  6. Cost control is per-request caps, per-user quotas, a global breaker and difficulty routing — plus attribution, so the number is actionable.
  7. Pin model versions, version prompts like code, and flag every feature for instant disable.
  8. Keep a non-AI path. Some days the model is not available, and the product should still be.
