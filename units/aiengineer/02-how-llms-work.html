Inside the model

You do not need to be able to build a transformer. You do need an accurate picture of what happens between your request and the text that comes back, because almost every expensive mistake in this field traces back to a wrong belief formed here.

The one-sentence model

A large language model is a function that takes a sequence of tokens and returns a probability distribution over what the next token should be. That is the entire mechanism. Everything else — conversation, reasoning, code, tool use — is that function applied over and over, each time with its own previous output appended to the input.

Three consequences follow immediately, and they explain a surprising amount of day-to-day behaviour:

  • Generation is sequential. Token 500 cannot be computed before token 499. This is why output length dominates latency, why streaming is possible at all, and why "just make it shorter" is a real performance optimisation.
  • The model has no memory between calls. Every request is stateless. A conversation exists only because your code re-sends the whole history each time. Chapter 4 makes this concrete; chapter 5 makes the cost of it concrete.
  • The model never looks anything up. Unless you gave it a tool or put the text in the prompt, it is producing likely continuations from patterns in its weights. That is the root of hallucination, and no amount of asking it to be accurate changes the mechanism.

Tokens

Models do not see characters or words. They see tokens: sub-word units produced by a learned vocabulary, typically 50,000 to 200,000 entries. A common English word is usually one token. A rare word, a name, a number or a non-English word splits into several.

Rules of thumb for English: ~4 characters or ~0.75 words per token. Code is denser in tokens than prose; JSON is denser still because of punctuation.

Why an engineer should care, beyond billing:

  • Character-level tasks are unnaturally hard. "How many r's in strawberry", reversing a string, counting words — the model sees str·aw·berry, not letters. Do these in code, not in the model.
  • Arithmetic is unreliable for the same reason. Numbers fragment inconsistently, so digit alignment is not something the model can rely on. Give it a calculator tool (chapter 7).
  • Non-English costs more. The same paragraph in Thai or Japanese can be three times the tokens of the English, which is a real cost and context-window issue for international products.
  • Formatting choices have a price. Deeply indented pretty-printed JSON in a prompt can cost 20–30% more tokens than the compact form for identical information.
Check, don't guess

Every provider publishes a tokeniser, and they differ. tiktoken for OpenAI models, the transformers tokeniser for open weights, a count-tokens endpoint for Anthropic and Google. Chapter 5 has the code and an interactive estimator.

Training and inference are different worlds

People conflate these constantly and it causes real confusion in planning meetings.

Training — done once, by someone else

  • Pre-training: predict the next token across trillions of tokens of text. Months, thousands of GPUs, tens of millions of dollars. Produces a model that can continue text but is not helpful or safe.
  • Supervised fine-tuning: train on curated instruction-and-response pairs so it answers questions instead of continuing them.
  • Preference tuning (RLHF, DPO and relatives): train on human or AI comparisons of two answers, so it prefers helpful, harmless, correctly formatted responses.

The result is a fixed set of weights with a fixed knowledge cutoff.

Inference — what you do, thousands of times a day

  • Prefill: the whole input is processed in parallel. Fast per token, and this is what prompt caching optimises.
  • Decode: tokens are produced one at a time. This is where the wall-clock time goes.

Weights never change. Nothing you send is learned. "The model remembered what I told it" always means your code re-sent it, or a memory feature stored it somewhere and re-sent it.

The prefill/decode split explains the two latency numbers you will care about: time to first token, which is dominated by prompt length and queueing, and tokens per second, which is dominated by model size and hardware. A 20,000-token prompt with a 50-token answer feels slow to start and then finishes instantly. A 200-token prompt with a 2,000-token answer starts immediately and then trickles.

What the forward pass is doing

You can build good products with the mechanism above and no further detail. But two internals leak into practice often enough to be worth understanding.

Attention, and why it matters to you

Each layer of a transformer lets every token look at every earlier token and pull in what is relevant. That is attention. The consequences that reach the application layer:

  • Cost grows super-linearly with context. Attention compares tokens pairwise, so doubling the prompt more than doubles the compute. This is why long-context requests are slow and why providers price and rate-limit them the way they do.
  • Position matters. Information at the very start and the very end of a long context is used more reliably than information in the middle — the widely reproduced "lost in the middle" effect. Put your instructions and the most important retrieved passage at the edges, not buried at 60% depth.
  • More context is not free quality. Stuffing thirty retrieved passages in when three were relevant measurably degrades answers as well as costing more. Chapter 12 covers packing the context deliberately.

The KV cache, and why the first token is slow

During decoding, the model caches the intermediate representations of every previous token so it does not recompute them. That cache is why generation is feasible at all — and it is also memory that scales with context length and concurrent users, which is the main constraint when you self-host (chapter 8). Prompt caching, offered by every major provider, is this cache made durable across requests so a stable prefix is not re-processed. It is the single biggest cost lever in most applications and it is covered in chapter 5.

Sampling: turning scores into text

The forward pass produces a score (a logit) for every token in the vocabulary. Softmax turns those into probabilities. Then a sampling strategy picks one. The parameters you set on the API are all controls on that pick, and understanding them is the difference between "the model is being weird" and "I configured it to be weird".

Temperature 0 is not determinism

It is greedy decoding — always take the top token — which removes sampling randomness but not batching non-determinism on GPUs, silent model updates behind a version alias, or differences between hardware in a provider's fleet. Treat it as "much more consistent", pin explicit model versions, and never write a test that asserts exact string equality on model output.

The context window

The context window is the maximum number of tokens the model can consider at once, and on most APIs it is shared between input and output. A 200,000-token window with a 16,000-token maximum output means your prompt plus history plus retrieved documents plus the answer must fit inside 200,000.

Four things people get wrong:

  • Big windows are not a replacement for retrieval. Putting a thousand-page manual into every request is technically possible and financially absurd: you pay for all of it, on every turn, and quality drops relative to sending the five right pages. Retrieval is a cost and quality optimisation, not a workaround for small windows.
  • Conversations grow quadratically in cost. Turn n re-sends turns 1 through n−1. A long chat becomes expensive on its own, which is why you need trimming or summarisation strategies (chapter 4).
  • Advertised length is not usable length. Effective recall across the full window varies by model and degrades before the hard limit. Benchmarks like needle-in-a-haystack tests measure this; treat the last 20% of any window as a place you would rather not rely on.
  • Overflow behaviour is a design decision. Some SDKs truncate silently, which is the worst option — you lose the system prompt and never know. Count before you send and decide explicitly what gets dropped.

Why models make things up

Hallucination is not a bug that a future release will patch out. It is the direct consequence of the mechanism: the model produces plausible continuations, and a plausible-looking citation, case number, API method or statistic is exactly what the pattern calls for even when no true value is available. Fluency and factuality are separate axes, and training optimises fluency far more directly.

It is worth separating the causes, because they have different fixes.

The engineering stance

You cannot eliminate hallucination. You can make it detectable — by grounding answers in text you supplied and can check, by requiring citations that resolve, by validating against schemas, and by measuring faithfulness on a fixed test set. Design for detection, not for perfection.

Reasoning models

A newer class of model is trained to produce an extended internal chain of thought before its visible answer, and to spend more compute at inference time on harder problems. You will see them exposed as separate models or as an effort/thinking setting on a standard one.

Good atExtraction, classification, drafting, chat, summarisation, most retrieval answeringMulti-step maths, hard debugging, planning, complex constraint satisfaction, code architecture

The practical rule: default to a fast model, and route to a reasoning model only for the requests that need it. A router that sends 5% of traffic to the expensive model gets most of the quality benefit at a fraction of the cost and latency. Chapter 19 covers routing.

The vocabulary, defined precisely

These words are used loosely everywhere. Here is what each one actually means, so the rest of the unit is unambiguous.

Token
A sub-word unit from the model's vocabulary. The atomic thing that gets processed, counted and billed.
Parameters / weights
The learned numbers inside the model, usually quoted in billions. Bigger is roughly more capable and definitely more expensive to run.
Inference
Running a trained model to get an output. What every API call does.
Context window
Maximum tokens the model can attend to in one request, input and output together.
Knowledge cutoff
The date after which the training data stops. Anything later must be supplied by you, via retrieval or a tool.
Embedding
A fixed-length vector representing the meaning of a piece of text, produced by a different, smaller model. Chapter 9.
Vector database
A store that finds the nearest vectors to a query vector quickly. Chapter 10.
RAG
Retrieval-augmented generation: fetch relevant text, put it in the prompt, answer from it. Chapters 11–13.
Prompt engineering
Designing the instructions, examples and structure of the input to get reliable behaviour. Chapter 6.
Fine-tuning
Continuing training on your own examples to change behaviour. Changes style and format well; adds facts badly. Chapter 14.
Tool / function calling
Giving the model a set of callable functions with schemas, so it can request one instead of guessing. Chapter 7.
Agent
A loop in which the model repeatedly chooses a tool, sees the result, and decides what to do next until the task is done. Chapter 15.
Multimodal
Handling images, audio or video as well as text. Chapter 16.
Quantisation
Storing weights at lower numeric precision so a model fits in less memory, at some quality cost. Chapter 8.
AGI
A hypothetical system matching or exceeding human ability across essentially all cognitive tasks. Not a category of product you can buy, and not a useful planning assumption.

The short version

  1. The model predicts the next token, repeatedly. It is stateless, sequential, and it never looks anything up unless you make it.
  2. Everything is measured in tokens, which is why character-level tasks and arithmetic are weak spots and why non-English text costs more.
  3. Prefill is parallel, decode is serial. Prompt length drives time-to-first-token; output length drives everything after that.
  4. Sampling settings are yours to control. Temperature 0 for anything with a right answer, and it is consistency rather than determinism.
  5. Bigger context windows do not replace retrieval, and quality falls before the hard limit does.
  6. Hallucination is inherent to the mechanism. Engineer for detection — grounding, citations, schemas, evals — not elimination.
