AI agents

An agent is a loop: the model chooses a tool, something runs it, the result goes back into the conversation, repeat until done. That is the whole idea, and it fits in forty lines. Everything difficult about agents is what happens when the loop does not terminate, or terminates having done the wrong thing to production.

the loop react tools memory mcp multi-agent

What makes something an agent

The distinction that matters in practice is who decides what happens next.

PatternControl flowUse when
Single callYou call the model onceClassification, extraction, generation. Most production LLM work
ChainYou call it several times in a fixed orderSummarise then translate; extract then validate. Predictable, testable, cheap
RouterThe model picks one of N fixed branches, you execute itIntent classification into handlers. Bounded and safe
AgentThe model decides what to do next, repeatedly, until it decides to stopOpen-ended tasks where the steps cannot be enumerated in advance
Prefer the least agentic thing that works

Agency buys flexibility and costs determinism, latency, money and debuggability. A chain that handles 90% of your cases in two predictable calls beats an agent that handles 95% in an unpredictable number of them. Reach for an agent when the sequence of steps genuinely depends on what earlier steps discover — research, triage across systems, multi-step repair — and not merely because the task has several steps.

agent.py — the entire mechanism, with the guards that make it survivable
import json, time
from dataclasses import dataclass, field

@dataclass
class Budget:
    max_steps: int = 12
    max_tokens: int = 120_000
    max_seconds: float = 90.0
    max_cost_usd: float = 0.50
    started: float = field(default_factory=time.monotonic)
    used_tokens: int = 0
    used_cost: float = 0.0

    def exceeded(self, step: int) -> str | None:
        if step >= self.max_steps:                        return "step limit"
        if self.used_tokens > self.max_tokens:            return "token limit"
        if time.monotonic() - self.started > self.max_seconds: return "time limit"
        if self.used_cost > self.max_cost_usd:            return "cost limit"
        return None


def run_agent(goal: str, ctx: RequestContext, budget: Budget | None = None) -> Result:
    budget = budget or Budget()
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user",   "content": goal}]
    trace = []

    for step in range(budget.max_steps + 1):
        if (reason := budget.exceeded(step)):
            return Result(status="halted", reason=reason, trace=trace,
                          text=summarise_progress(messages))

        resp = call_model(messages, tools=TOOL_SCHEMAS, temperature=0)
        budget.used_tokens += resp.usage.total_tokens
        budget.used_cost   += resp.cost_usd
        messages.append(resp.message)

        if not resp.tool_calls:                             # the model is done
            return Result(status="ok", text=resp.text, trace=trace, steps=step)

        for call in resp.tool_calls:                        # may be several, in parallel
            observation = execute(call, ctx, trace)
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": observation})

    return Result(status="halted", reason="loop fell through", trace=trace)


def execute(call, ctx, trace) -> str:
    """Every failure mode here is returned as text, never raised."""
    tool = REGISTRY.get(call.name)
    if tool is None:
        return f"Error: no tool named {call.name}. Available: {', '.join(REGISTRY)}"

    try:
        args = tool.schema.model_validate_json(call.arguments)
    except ValidationError as e:
        return f"Error: invalid arguments. {e.errors()[0]['msg']}. Fix and retry."

    if not authorised(tool, args, ctx):                     # never trust the model
        return f"Error: not permitted for this user."

    try:
        result = tool.fn(args, ctx)
    except Exception as e:                                  # tools fail; agents must cope
        trace.append(("error", call.name, str(e)))
        return f"Error running {call.name}: {e}. Consider a different approach."

    trace.append(("ok", call.name, args.model_dump()))
    return truncate(json.dumps(result), max_tokens=1500)    # protect the context

Four things in that code are the difference between a demo and something you can run: a budget with four independent limits, errors returned as observations rather than raised (the model can recover from text; it cannot recover from a stack trace), authorisation checked in your code rather than requested in the prompt, and truncation of tool results so one verbose API response does not consume the context window.

ReAct, and why the model narrates

ReAct — reason, act — is the observation that interleaving explicit reasoning with tool calls works better than tool calls alone. Modern models with native tool calling do this implicitly, but making the reasoning explicit still helps on hard tasks and helps enormously when debugging.

Thought: The user says order NW-8842 was charged twice. I need the order first.

Observation: {"id":"NW-8842","total":48.00,"status":"shipped","customer":"c_991"}

Action: list_payments({"order_id": "NW-8842"})
Observation: [{"id":"p_1","amount":48.00,"status":"captured","at":"2026-03-02T10:14Z"},
              {"id":"p_2","amount":48.00,"status":"captured","at":"2026-03-02T10:16Z"}]

Thought: Confirmed - two captures two minutes apart, almost certainly a double

Action: propose_action({"type":"refund","payment_id":"p_2","amount":48.00,
                        "reason":"duplicate capture 2 minutes apart"})
Observation: {"status":"awaiting_human_approval","ticket":"AP-2210"}

Thought: I have confirmed the problem and queued the fix. Time to answer.
Answer: Order NW-8842 was charged twice — two £48 captures at 10:14 and 10:16 on

should reach the card within 5-10 working days once approved.

Notice the third thought. The agent recognised a destructive action, checked it against a threshold, and proposed rather than executed. That behaviour comes from the system prompt and is enforced in execute — belt and braces, because the prompt alone is not a control.

Designing the tools

Chapter 07 covered the mechanics of tool calling. Agents raise the stakes, because tool descriptions are now the model's entire map of what it can do, and errors compound across steps rather than surfacing immediately.

PrincipleIn practice
Few tools, well describedSelection accuracy falls sharply past roughly 15–20 tools. If you have 40, group them behind a smaller set or route to a subset per request
Task-shaped, not API-shapedfind_customer_orders(email) beats exposing three CRUD endpoints and hoping the model composes them correctly
Descriptions written for a strangerSay when to use it and when not to. "Use for orders in the last 90 days; older orders are only in search_archive"
Return what helps the next decisionNot the raw 40-field API response. Summarise, flatten, and include the identifiers the model will need to act next
Errors that suggest a recovery"No customer with that email. Try search_customers with a partial name." The model will follow that advice
Idempotent where possibleAgents retry. A tool that double-charges on retry is a production incident waiting for a timeout
Separate read from writeReads run freely. Writes go through confirmation, an allowlist, or a proposal queue
guards.py — the checks that stop the common disasters
DESTRUCTIVE = {"refund", "cancel_order", "delete_record", "send_email", "update_address"}

def guard(call, ctx, trace) -> str | None:
    """Return an observation to short-circuit with, or None to proceed."""

    # 1. The same call three times means the model is stuck in a groove.
    signature = (call.name, call.arguments)
    if [t for t in trace if t[:2] == signature[:2]].__len__() >= 2:
        return ("You have already called this with these arguments and got the same "
                "result. Try a different approach or explain what is blocking you.")

    # 2. Destructive actions need explicit authority, never the model's own judgement.
    if call.name in DESTRUCTIVE:
        if ctx.mode == "read_only":
            return f"Error: {call.name} is not available in read-only mode."
        if not ctx.auto_approve_limit or amount_of(call) > ctx.auto_approve_limit:
            queue_for_human(call, ctx)
            return f"Queued for human approval (limit £{ctx.auto_approve_limit})."

    # 3. Alternating between two tools without progress: a known oscillation.
    recent = [t[1] for t in trace[-4:]]
    if len(recent) == 4 and recent[0] == recent[2] and recent[1] == recent[3]:
        return "You are alternating between two tools without progress. Stop and summarise."

    return None

Memory

"Agent memory" covers four genuinely different things that get conflated.

Working memory
The messages array in the current run. Bounded by the context window, gone when the run ends. Managed by truncation, summarisation and result compaction.
Session memory
The conversation across turns with one user. Usually the last N turns plus a rolling summary of what came before.
Long-term memory
Facts persisted across sessions — preferences, prior decisions, learned corrections. A database with an explicit write path, retrieved into the prompt when relevant. Not magic: it is RAG over things the agent chose to remember.
Episodic memory
Records of past runs — what was attempted, what worked. Useful for "you tried this last week and it failed for reason X".
memory.py — long-term memory as an explicit tool, not an ambient mechanism
REMEMBER = {
  "name": "remember",
  "description": ("Store a durable fact about this user for future conversations. "
                  "Use for stable preferences and decisions, e.g. 'prefers email over "
                  "phone', 'account is on the legacy billing plan'. Do NOT store "
                  "transient details, anything about the current task, or any payment "
                  "card, password or identity document number."),
  "parameters": {"type": "object", "required": ["fact", "category"],
    "properties": {
      "fact": {"type": "string", "maxLength": 200},
      "category": {"enum": ["preference", "account", "history", "constraint"]}}}
}

def remember(args, ctx) -> dict:
    if contains_pii(args.fact):                      # a hard gate, not a prompt rule
        return {"stored": False, "reason": "contains sensitive data"}
    vec = embed_passage(args.fact)
    existing = memory_store.search(ctx.user_id, vec, limit=3)
    if existing and existing[0].score > 0.93:        # deduplicate, or memory fills with restatements
        memory_store.touch(existing[0].id)
        return {"stored": False, "reason": "already known"}
    memory_store.insert(ctx.user_id, args.fact, args.category, vec)
    return {"stored": True}

# At the start of a run, retrieve rather than dump:
relevant = memory_store.search(ctx.user_id, embed_query(goal), limit=5)
system += "\n\nWhat you know about this user:\n" + "\n".join(f"- {m.fact}" for m in relevant)
Memory needs forgetting, or it poisons itself

An agent that stores everything accumulates contradictions, stale facts and near-duplicates, and eventually retrieves the wrong one confidently. Build in expiry by category, deduplication on write, an update path so a new fact supersedes an old one, and a way for the user to see and delete what is stored. The last one is a legal requirement in several jurisdictions and a trust requirement everywhere.

Planning

PatternHow it worksTrade-off
Implicit (ReAct)Decide the next step each iteration, no plan up frontAdaptive and simple; can wander on long tasks
Plan then executeWrite the full plan first, then execute stepsCoherent and inspectable; brittle when reality diverges from the plan
Plan, execute, replanPlan, execute a step, revise the plan with what was learnedThe practical middle. Costs an extra call per revision
Task decompositionBreak into subtasks, run each in its own context, combineKeeps contexts small and parallelises well; needs careful result merging
ReflectionAfter producing output, critique it and revise onceReal quality gains on writing and code; roughly doubles cost. One round helps, three do not
A visible plan is a debugging tool

Even when the agent replans constantly, having it emit a plan first gives you something to show the user (progress is legible instead of a spinner), something to log, and something to diff when a run goes wrong. It also lets you insert a human approval point between planning and execution — often the difference between an agent you can deploy and one you cannot.

MCP: tools as infrastructure

The Model Context Protocol standardises how applications expose tools, resources and prompts to models. Instead of every application writing bespoke integrations for every system, a system publishes one MCP server and any MCP-capable client can use it.

ConceptWhat it is
HostThe application the user interacts with — an editor, a chat client, your own agent
ClientThe connection the host maintains to one server
ServerA process exposing capabilities over the protocol. Local (stdio) or remote (HTTP)
ToolsFunctions the model can invoke — the same shape as chapter 07
ResourcesReadable content the host can pull in: files, records, query results
PromptsReusable templates the server offers the host, surfaced as slash commands or similar
An MCP server is arbitrary code with your credentials

Installing one is closer to installing a browser extension than adding a library. Review what it does, run it with the narrowest credentials that work, prefer read-only scopes, and treat everything it returns as untrusted input that may contain prompt injection (chapter 17). A tool description fetched from a remote server is text the model will read and may obey — this is a real attack surface, not a theoretical one.

Multi-agent, and when it is worth it

PatternShapeHonest assessment
SupervisorOne coordinator delegates to specialists and assembles resultsThe most useful pattern. Each specialist gets a small tool set and a focused prompt, which is where the gain comes from
PipelineFixed sequence of specialists, each handing to the nextNot really multi-agent — it is a chain, and better for it: testable and predictable
Parallel workersFan out independent subtasks, mergeGenuinely valuable for research and broad search. Contexts stay small, wall-clock time drops
Debate / criticOne produces, another critiques, iterateWorks for writing and code review. Costs at least double; one round of critique captures most of the benefit
Autonomous swarmPeers negotiating freelyImpressive in demonstrations, extremely hard to make reliable or debug. Avoid in production

The real reason multi-agent helps is not "collaboration" — it is context isolation. A specialist with six tools and a focused prompt makes better decisions than a generalist with forty. If you can get that isolation with a router and separate prompts, do that instead; it is cheaper and far easier to test.

How agents fail

Looping
The same call repeated with the same arguments. Fix with a repeat guard and a hard step limit.
Oscillating
Alternating between two tools without progress. Detect the pattern and force a summary.
Context exhaustion
Tool results accumulate until the window overflows mid-run. Truncate results, summarise old steps, keep only the last few observations in full.
Wrong tool, confidently
Usually a description problem, not a model problem. Rewrite the description to say when not to use it.
Fabricated arguments
Inventing an order id rather than looking one up. Validate arguments against reality — does that id exist? — before executing.
Premature success
Declaring the task done having achieved something adjacent. Add an explicit completion criterion and verify it in code.
Silent partial failure
Three of five subtasks failed; the summary mentions none of it. Aggregate statuses in code and report them, never leave it to the summary.
Runaway cost
A long loop over an expensive model. Four independent budget limits, and alerting on runs that approach them.

What to build first

  • Write the loop yourself before adopting a framework. Forty lines, and you will understand every abstraction you later choose. Frameworks are useful for the surrounding machinery — tracing, retries, streaming state — not for the loop.
  • Start read-only. An agent that can look things up and propose actions is useful and safe. Add write access one tool at a time, each behind confirmation.
  • Log the full trace — every message, tool call, argument, result, token count and timing. Agent debugging is impossible without it, and chapter 18 depends on it.
  • Set all four budgets from day one. Steps, tokens, time, money.
  • Show progress to the user. Streaming each step as it happens turns a 40-second silence into something legible, and lets them interrupt.
  • Evaluate on trajectories, not just outcomes. A right answer reached by six wasteful steps is fragile; measure step count, tool-selection accuracy and cost per completed task.

The short version

  1. An agent is a loop — reason, act, observe, repeat — and it fits in forty lines. Write those lines yourself.
  2. Prefer the least agentic design that works. Chains and routers are cheaper, faster and testable.
  3. Return tool errors as observations, never as exceptions. The model can recover from text.
  4. Enforce authorisation and destructive-action limits in your code. A prompt rule is not a control.
  5. Tool descriptions are the model's map. Few tools, task-shaped, with guidance on when not to use them.
  6. Memory is four different things. Long-term memory needs deduplication, expiry and a user-visible delete path.
  7. Multi-agent helps because of context isolation, not collaboration. Get the isolation the cheapest way you can.
  8. Set four budgets — steps, tokens, time, cost — log the full trace, and evaluate trajectories as well as answers.
