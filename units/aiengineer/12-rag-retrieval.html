RAG part two: retrieval and generation

The query the user typed is rarely the query you should run, and the passages you retrieved are rarely in the order or the shape the model reads best. This is the request path: seven stages between a question and a grounded, citable answer.

Stage 1 — the query is not the query

Users type "what about sale items?" as the third turn of a conversation. Embedding that string retrieves nothing useful, because everything it means lives in the preceding turns.

TechniqueWhat it doesCost
History condensationRewrite the follow-up into a standalone question using the conversation so far. Mandatory for any multi-turn RAG — nothing else matters if you skip itOne small-model call, ~200ms
Multi-query expansionGenerate 3–4 paraphrases, retrieve for each, fuse the results. Covers vocabulary the user did not useOne call plus parallel retrievals
DecompositionSplit a compound question ("how do returns and refund timing work for sale items?") into sub-questions retrieved separatelyOne call; more retrievals
HyDEAsk the model to write a hypothetical answer, then embed that instead of the question. Answers look like answers, so they match passages betterOne call, ~400ms. Strong on jargon-heavy corpora, weak when the model hallucinates a wrong-shaped answer
Filter extractionPull structured constraints out of natural language — "last quarter", "for the EU" — into metadata filtersOne structured-output call (chapter 07)
Intent routingDecide whether this needs retrieval at all. "Thanks!" and "write me a poem" should not hit the indexA classifier or a small model; saves latency and money on a surprising share of traffic
query.py — condensation and filter extraction in one structured call
from pydantic import BaseModel, Field
from typing import Literal

class QueryPlan(BaseModel):
    needs_retrieval: bool = Field(description="False for greetings, thanks, chit-chat")
    standalone_question: str = Field(description="Self-contained, with pronouns resolved")
    paraphrases: list[str] = Field(max_length=3, description="Alternative phrasings")
    product: str | None = None
    after_date: str | None = Field(default=None, description="ISO date, if the user implied recency")
    intent: Literal["factual", "procedural", "comparison", "chitchat"]

PLAN_PROMPT = """Rewrite the user's latest message as a standalone search query.

{history}
{question}

Rules:
- Resolve every pronoun and ellipsis using the conversation.
- Do not answer the question. Do not add facts that are not implied.
- Paraphrases must use different vocabulary, not reordered words."""

plan = structured_call(QueryPlan, PLAN_PROMPT.format(history=history, question=q))

if not plan.needs_retrieval:
    return direct_answer(q)                    # skip the whole pipeline
Use a small, fast model here

Query rewriting sits on the critical path of every request, so it must be cheap and quick. A small model does it perfectly well — the task is close to mechanical. Run it concurrently with nothing else and it adds 150–300ms; skip it and multi-turn accuracy falls off a cliff. If latency is critical, condense only when the message contains a pronoun, an ellipsis, or fewer than four words.

Stages 2–4 — retrieve, fuse, rerank

Chapter 10 covered the mechanics. What matters here is the funnel shape: wide then narrow. Retrieve 50 per arm because recall is the only thing you can never recover later; rerank down to 5 because precision is what the model actually consumes.

retrieve.py — the full funnel, concurrent where it can be
import asyncio

async def retrieve(plan: QueryPlan, ctx: RequestContext) -> list[Chunk]:
    filters = {
        "tenant_id": ctx.tenant_id,                    # never from the client payload
        "acl_groups": {"$overlaps": ctx.user_groups},
        "archived": False,
        **({"product": plan.product} if plan.product else {}),
        **({"updated_at": {"$gte": plan.after_date}} if plan.after_date else {}),
    }

    queries = [plan.standalone_question, *plan.paraphrases]
    vectors = await embed_many([f"query: {q}" for q in queries])

    rankings = await asyncio.gather(
        *[vector_search(v, filters, limit=50) for v in vectors],
        *[bm25_search(q, filters, limit=50)   for q in queries],
    )

    fused = rrf([[h.id for h in r] for r in rankings])[:60]
    candidates = await fetch_chunks([doc_id for doc_id, _ in fused])

    scores = await rerank(plan.standalone_question, [c.text for c in candidates])
    ranked = [c for s, c in sorted(zip(scores, candidates), key=lambda p: -p[0])]

    keep = [c for c, s in zip(ranked, sorted(scores, reverse=True)) if s > RERANK_FLOOR]
    return keep[:TOP_K] or ranked[:2]        # never return nothing without saying so
Handle "nothing relevant found" explicitly

If every reranker score is below the floor, the honest answer is "I could not find this in the documentation." Returning the top 5 regardless — which is the default behaviour of every framework — guarantees the model is handed irrelevant context and invents something plausible from it. An explicit low-confidence path is worth more to user trust than any amount of prompt tuning.

Stage 5 — packing the context

You have five good passages. How you arrange them changes the answer.

Context packing Five retrieved chunks, one budget. Adjust and watch what reaches the model — and where in the window it lands.

How many chunks3–8 after reranking. More is not better: past about eight, precision falls and the model starts averaging across sources rather than answering from the best one
OrderingModels attend most reliably to the start and end of the context. Put the strongest passage first and the second-strongest last
DeduplicationOverlapping chunks from the same section repeat text. Merge adjacent chunks from one document rather than sending both

CachingRetrieved context changes per request, so it cannot be cached — put it after the stable system prompt so the prefix cache still hits (chapter 05)

Six of those seven rules exist because of a specific, observed failure mode. Rule 3 stops the model quietly answering from pre-training when retrieval fails — the single most damaging RAG bug, because the answer looks grounded. Rule 4 handles superseded policies. Rule 5 stops "within 14 days" becoming "within two weeks" and then "within a fortnight or so". Rule 6 is prompt-injection defence, and it matters enormously when your corpus contains user-submitted content (chapter 17).

Citations that actually verify

verify.py — check the citations before the user sees them
import re

CITE = re.compile(r"\[S(\d+)\]")

def verify(answer: str, sources: list[Source]) -> VerifyResult:
    ids = {int(m) for m in CITE.findall(answer)}
    valid = {i + 1 for i in range(len(sources))}

    problems = []
    if ids - valid:
        problems.append(f"cited non-existent sources: {sorted(ids - valid)}")

    # Any sentence making a factual claim should carry a citation.
    for sentence in re.split(r"(?<=[.!?])\s+", answer):
        if len(sentence) > 40 and not CITE.search(sentence) \
           and not sentence.startswith("I couldn't find"):
            problems.append(f"uncited claim: {sentence[:60]}…")

    # Numbers in the answer must appear in a cited source.
    for number in re.findall(r"\b\d[\d,.]*\b", answer):
        if not any(number in sources[i - 1].text for i in ids if i in valid):
            problems.append(f"number not present in cited sources: {number}")

    return VerifyResult(ok=not problems, problems=problems)

The number check is worth its weight. Hallucinated figures are the most damaging RAG failure and the easiest to detect mechanically. When verification fails, you have options in ascending order of cost: strip the offending sentence, retry once with the problems fed back, or return the low-confidence response. Log every failure — the rate is a headline quality metric in chapter 13.

Show the sources in the interface, always

Rendering citations as clickable links to the source document does three things at once: it lets users verify, it makes hallucinations obvious rather than invisible, and it converts every user into an evaluator. Teams that ship citations find their quality problems in days. Teams that ship bare prose find them in support tickets, months later.

Variants worth knowing

Parent–child (small-to-big)
Embed 200-token chunks, return the 1,500-token section they belong to. Precision of small chunks with the context of large ones. The highest value-to-effort variant; adopt it early.
Sentence window
Embed single sentences, return the sentence plus its neighbours. Excellent for dense reference material where the answer is one line.
Self-query
The model writes the metadata filter itself from natural language, then retrieval runs against the filtered subset. Powerful over well-structured catalogues; validate the generated filter against an allowlist before executing it.
Corrective RAG
Grade retrieved passages for relevance; if they fail, rewrite the query and retry, or fall back to web search. Adds a round trip but rescues bad first attempts.
Agentic RAG
Retrieval becomes a tool the model can call repeatedly, deciding what to look up next based on what it has read (chapter 15). Far better on multi-hop questions; slower, costlier, harder to evaluate.
Graph RAG
Build an entity-and-relationship graph at ingest, retrieve subgraphs, and answer over them. Strong for "how does X relate to Y across many documents"; ingestion is expensive and the graph needs maintaining.
Multi-index routing
Separate indexes per corpus — policies, code, tickets — with a router choosing which to query. Better filtering, better recall per index, and cheaper than one enormous index.
Add these one at a time, with measurement between

Every variant on that list makes the system slower and harder to debug. Teams routinely stack HyDE, multi-query, corrective retrieval and an agentic loop, then cannot say which part helps. The order that actually pays: hybrid search → reranking → query condensation → parent–child. Those four are most of the available gain. Everything else is a targeted fix for a failure you have measured, and chapter 13 is how you measure it.

A well-built RAG response starts streaming in about one second. If yours takes five, the profile above tells you which stage to attack — and it is usually reranking a too-large candidate set, or a condensation call on a big model.

The short version

  1. Rewrite the query before retrieving. Multi-turn RAG without history condensation does not work, and nothing downstream compensates.
  2. Wide then narrow: retrieve 50 per arm for recall, rerank to 5 for precision. Recall lost at stage 2 cannot be recovered later.
  3. Handle "nothing relevant found" explicitly. Returning the top 5 regardless is how confident hallucinations happen.
  4. Packing matters: strongest passage first, second-strongest last, deduplicate, expand to parents, and put context after the cacheable prefix.
  5. The grounded prompt needs a citation contract, a refusal path, a recency rule and an injection rule — each one earns its place.
  6. Verify citations mechanically before returning. Numbers not present in cited sources are the cheapest hallucination check you will ever write.
  7. Show sources in the UI. It turns every user into an evaluator.
  8. Adopt variants in order — hybrid, rerank, condense, parent–child — and measure between each.
