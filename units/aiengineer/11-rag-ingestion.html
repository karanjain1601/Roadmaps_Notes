Chapter 11 · Knowledge and retrieval

RAG part one: getting your data in

Retrieval-augmented generation is the most common thing AI engineers build, and almost every failure traces back to ingestion. The quality ceiling of the entire system is set here — before a single query is ever run.

parsing chunking metadata contextualisation incremental

What RAG is, and what it is not

The model does not know your company's refund policy. Three ways to fix that: fine-tune it in (expensive, slow to update, and it teaches style better than facts — chapter 14), put everything in the prompt (works beautifully up to a point, then costs too much and dilutes attention), or look up the relevant parts at query time and put those in the prompt. That third option is RAG.

Ingest — offline, once per document changeLoad → parse → chunk → enrich → embed → index
↓
Retrieve — online, once per queryRewrite query → hybrid search → rerank → pack context
↓
Generate — onlineGrounded prompt → answer with citations → verify

This chapter is the top box. Chapter 12 is the other two, chapter 13 is how you tell whether any of it works.

Long context has not made RAG obsolete

A million-token window tempts you to skip retrieval and paste everything. Sometimes you should — if your whole corpus is 30 pages, retrieval is pointless complexity. But at scale you still want RAG, for four reasons that do not go away: cost (you pay per token, on every request), latency (prefill time scales with input), accuracy (models genuinely degrade at locating one fact in a haystack), and permissions (you cannot paste a corpus that different users are allowed different slices of). Long context changes the ideal chunk size and how much you retrieve — it does not remove the need to retrieve.

Step one: loading and parsing

This is unglamorous and it is where most of the real engineering time goes. A PDF is not text; it is drawing instructions. Getting clean text out of the formats real organisations use is the difference between a system that works and one that retrieves navigation menus.

SourceApproachWhat goes wrong
Plain text, MarkdownRead it. Keep the heading structure — it is free metadataNothing. Be grateful
HTMLExtract the main content region, drop nav, footers, cookie banners, sidebars. Convert to Markdown to preserve headings, lists and tablesBoilerplate dominates the index; the same nav bar embeds into every chunk and matches everything

Read fifty parsed chunks with your own eyes

Before building anything downstream, dump a random sample of parsed chunks and read them. Not summary statistics — the actual text. You will find repeated page headers, broken tables, navigation menus, and passages that were split mid-sentence. Every one of those defects is about to be embedded and retrieved for the rest of the system's life. This half-hour is the highest-leverage half-hour in the whole project.

Vision models as parsers

For complex layouts — financial reports, forms, scientific papers with figures — rendering each page to an image and asking a multimodal model to transcribe it into Markdown now often beats traditional extraction, especially for tables. It costs a few cents a page and is slow, so it is a one-off ingestion cost rather than a per-query one. Chapter 16 covers the mechanics.

Step two: chunking

Chunks are the unit of retrieval. Too large and you retrieve one relevant sentence wrapped in 900 tokens of noise, diluting both the embedding and the model's attention. Too small and you retrieve a sentence that has lost the context needed to interpret it.

The strategies, in order of how often they are right

StrategyHow it worksUse when
StructuralSplit on the document's own boundaries — headings, sections, list items, slides — then subdivide anything still too largeAlmost always, when structure exists. Markdown, HTML, Confluence, docs sites. Sections were written as coherent units by a human; respect that
Recursive characterTry to split on \n\n, then \n, then . , then space, taking the largest break that fits the size limitThe workhorse default for prose without reliable structure. Cheap, deterministic, rarely cuts mid-sentence
Fixed sizeEvery N characters or tokens, with overlapRarely the right answer, but a reasonable baseline and it never fails on weird input
Sentence windowEmbed single sentences; at retrieval time return the sentences either side tooPrecise retrieval over dense reference material. Excellent precision, more storage
Parent–childEmbed small chunks; return the larger parent section they belong toWhen small pieces retrieve well but the model needs surrounding context to answer. Very effective, and my usual recommendation after structural
SemanticEmbed sentences, split where consecutive similarity drops — a topic changeUnstructured transcripts and long narrative text. Costs an embedding pass over every sentence; measure before assuming it beats recursive
AgenticAsk an LLM where the natural boundaries areSmall, high-value, awkward corpora. Too slow and expensive at volume
chunk.py — structural first, recursive as the fallback
import re
from dataclasses import dataclass, field

TARGET = 500          # tokens, not characters
OVERLAP = 75
HARD_MIN = 40         # below this, merge forward rather than index noise

@dataclass
class Chunk:
    text: str
    section_path: str                       # "Returns > Sale items"
    index: int
    meta: dict = field(default_factory=dict)


def split_by_headings(markdown: str) -> list[tuple[str, str]]:
    """Returns (section_path, body) preserving the heading hierarchy."""
    sections, stack, buf = [], [], []
    for line in markdown.splitlines():
        m = re.match(r"^(#{1,6})\s+(.*)", line)
        if m:
            if buf:
                sections.append((" > ".join(stack), "\n".join(buf).strip()))
                buf = []
            level = len(m.group(1))
            stack = stack[: level - 1] + [m.group(2).strip()]
        else:
            buf.append(line)
    if buf:
        sections.append((" > ".join(stack), "\n".join(buf).strip()))
    return [(p, b) for p, b in sections if b]


def recursive_split(text: str, target: int, overlap: int) -> list[str]:
    """Take the largest separator that keeps pieces under target."""
    for sep in ["\n\n", "\n", ". ", "; ", " "]:
        parts = text.split(sep)
        if len(parts) == 1:
            continue
        out, cur = [], ""
        for p in parts:
            candidate = (cur + sep + p) if cur else p
            if count_tokens(candidate) > target and cur:
                out.append(cur)
                tail = cur[-overlap * 4:]                  # ~4 chars per token
                cur = tail + sep + p
            else:
                cur = candidate
        if cur:
            out.append(cur)
        if all(count_tokens(o) <= target * 1.3 for o in out):
            return out
    return [text[i:i + target * 4] for i in range(0, len(text), target * 4)]


def chunk_document(markdown: str, doc_meta: dict) -> list[Chunk]:
    chunks: list[Chunk] = []
    for path, body in split_by_headings(markdown):
        pieces = ([body] if count_tokens(body) <= TARGET
                  else recursive_split(body, TARGET, OVERLAP))
        for piece in pieces:
            if count_tokens(piece) < HARD_MIN and chunks:
                chunks[-1].text += "\n" + piece          # absorb orphans
                continue
            chunks.append(Chunk(text=piece.strip(), section_path=path,
                                index=len(chunks), meta=dict(doc_meta)))
    return chunks

Sizing, concretely

ContentChunk sizeOverlapWhy
FAQ, knowledge base articles200–400 tokens0 — split per Q&AEach entry is already an atomic answer
Policy and reference docs400–800 tokens10–15%Sections are self-contained; overlap saves boundary-straddling rules
Long-form prose, books600–1,000 tokens15%Argument needs room to develop
Technical documentation500–1,000 tokens10%Keep a code example with its explanation, never apart
Source codeOne function or classsignature + docstringSyntactic units are the only sensible boundary

Start at 500 tokens with 15% overlap and a structural splitter. Then change it based on evaluation numbers (chapter 13), not on taste.

Step three: enrich before you embed

A raw chunk from the middle of a document is often uninterpretable on its own. "This does not apply to items marked final sale." What does not apply? The embedding has no idea, so it matches poorly and the model receives a fragment it cannot use.

Contextual prefixing

Prepend the document title and section path to the chunk text before embedding it. This one change routinely produces double-digit percentage improvements in retrieval accuracy and costs nothing.

Embedded as-is

"This does not apply to items marked final sale. Postage is not refunded."

Matches queries about postage. Loses to any chunk that says "returns" for a returns query.

Contextually prefixed

"Northwind Returns Policy › Refunds › Exceptions — This does not apply to items marked final sale. Postage is not refunded."

Now matches "can I return sale items?" and the model knows which policy it is reading.

python — three levels of enrichment
# Level 1 - free, do this always.
embed_text = f"{doc.title} › {chunk.section_path}\n\n{chunk.text}"

# Level 2 - cheap, generate once per document at ingest.
embed_text = f"{doc.title} › {chunk.section_path}\n{doc.one_line_summary}\n\n{chunk.text}"

# Level 3 - "contextual retrieval": an LLM writes a bespoke situating sentence per
# chunk. Costly at volume, but prompt caching makes it viable because the document
# is the cached prefix and only the chunk changes.
SITUATE = """{doc}
Here is a chunk from that document:
{chunk}
Write one short sentence situating this chunk within the document, to improve
search retrieval. Answer with the sentence only."""

context = llm(SITUATE.format(doc=doc.text, chunk=chunk.text), max_tokens=80)
embed_text = f"{context}\n\n{chunk.text}"

# Note what is stored where:
#   embed_text -> the vector          (enriched, for matching)
#   chunk.text -> shown to the model  (clean, for reading)
# Keeping them separate matters. Do not put the situating sentence in the prompt.

Generated questions

The mismatch from chapter 9 — questions do not look like answers — has a direct fix. At ingest, ask a cheap model to write three questions each chunk answers, and index those alongside. Now query embeddings are compared against question embeddings, which is a like-for-like comparison.

Step four: metadata

Metadata is what lets you filter, cite, permission and expire. It is also the thing people under-invest in and then have to re-ingest a corpus to add. Decide it before the first full run.

FieldWhy you will need it
tenant_id, acl_groupsCorrectness and security. Filter at query time, always server-side (chapter 10)
source_url, page, section_pathCitations. Users trust an answer they can click through and verify; without this you cannot offer that
updated_at, effective_from/toRecency boosting, and excluding superseded policies. The most common cause of confidently wrong answers is retrieving last year's document
doc_type, lang, productRouting and filtering. Users usually mean one product area, not all of them
content_hashSkip re-embedding unchanged chunks on re-ingest. Turns a four-hour job into four minutes
embed_model, chunker_versionKnowing what is stale when you change either. You will change both
token_countPacking the context window without a second tokenisation pass at query time
Permissions must be enforced at retrieval, not by the model

Never retrieve documents the user cannot see and instruct the model to ignore them. That is not a security boundary — it is a suggestion to a text generator, and prompt injection defeats it trivially (chapter 17). Apply access control as a filter in the query, derived from the session's identity, before any vector is compared.

Step five: the pipeline that survives contact with reality

Ingestion is not a script you run once. Documents change, parsers get fixed, models get swapped. Build it to be re-runnable from the start.

ingest.py — incremental, idempotent, resumable
import hashlib

PIPELINE_VERSION = "2026-04-parser3-chunk500-bge768"

def hash_text(s: str) -> str:
    return hashlib.sha256(s.encode()).hexdigest()

def ingest(source_doc) -> dict:
    raw = load(source_doc)                      # bytes -> text/markdown
    doc_hash = hash_text(raw)

    existing = db.get_document(source_doc.id)
    if existing and existing.doc_hash == doc_hash \
                and existing.pipeline_version == PIPELINE_VERSION:
        return {"status": "unchanged"}          # the common case; costs nothing

    chunks = chunk_document(raw, doc_meta=source_doc.meta)

    # Re-embed only what actually changed. A typo fix in paragraph 40 of a
    # 200-chunk manual should not re-embed 200 chunks.
    old = {c.content_hash: c for c in db.get_chunks(source_doc.id)}
    to_embed, reused = [], []
    for c in chunks:
        h = hash_text(c.text + c.section_path)
        c.content_hash = h
        (reused if h in old else to_embed).append(c)

    if to_embed:
        vectors = embed_texts([enrich(c) for c in to_embed])
        for c, v in zip(to_embed, vectors):
            c.embedding = v
    for c in reused:
        c.embedding = old[c.content_hash].embedding

    with db.transaction():                      # atomic swap: never a half-indexed doc
        db.delete_chunks(source_doc.id)
        db.insert_chunks(chunks)
        db.upsert_document(source_doc.id, doc_hash=doc_hash,
                           pipeline_version=PIPELINE_VERSION,
                           chunk_count=len(chunks))

    return {"status": "reindexed", "embedded": len(to_embed), "reused": len(reused)}
  • Deletions propagate. When a source document disappears, its chunks must go. A cascade foreign key does this for free in Postgres; a separate vector store needs explicit handling and it is the most commonly forgotten path.
  • Re-indexing is a blue-green operation. Changing the embedding model or chunker means building a new index version and swapping, not mutating live data. Users should never see a half-rebuilt corpus.
  • Failures are per-document. One malformed PDF must not abort the run. Record the failure, continue, report at the end.
  • Log the funnel. Documents in, parsed, chunks produced, chunks embedded, failures by reason. When retrieval quality drops, this is where you look first.
  • Alert on shape changes. A parser regression usually shows up as chunk count per document tripling, or median chunk length collapsing — long before anyone complains about answers.

Ingestion smells

Every chunk starts with the same 40 words
You are indexing page headers or navigation. Strip boilerplate in the parser.
Median chunk is 60 tokens
The splitter is fragmenting on formatting artefacts. Merge orphans forward.
Tables retrieve but are unreadable
Convert tables to Markdown, or serialise each row as a sentence with column names.
Retrieval returns the table of contents
Index-like pages match everything weakly. Exclude them by structure or by a length-versus-link-density heuristic.
Answers cite documents from 2019
No recency handling. Add effective_to and filter, or boost by updated_at.
Correct fact exists but is never retrieved
Usually a chunking boundary splitting the fact from its heading. Check the specific chunk containing it.

The short version

  1. RAG's quality ceiling is set at ingestion. Long context does not remove the need for it — cost, latency, accuracy and permissions all still apply.
  2. Parsing is most of the real work. Read fifty parsed chunks by hand before building anything downstream.
  3. Split on the document's own structure first, recursive splitting second. Fixed-size windows are a baseline, not a plan.
  4. Start at 500 tokens with 15% overlap, then change it because of evaluation numbers.
  5. Prefix chunks with title and section path before embedding. Free, and one of the largest wins available.
  6. Embed the enriched text; show the model the clean text. They are not the same string.
  7. Decide metadata before the first full run — tenancy, citations, recency, hashes and versions — or you will re-ingest to add them.
  8. Make the pipeline incremental, idempotent and atomic. You will run it hundreds of times.
