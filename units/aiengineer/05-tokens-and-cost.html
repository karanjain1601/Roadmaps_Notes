Tokens, context and money

Token accounting is the closest thing this field has to a performance profiler. It tells you what a feature costs, why a request is slow, why a prompt fails at the boundary, and which optimisation is worth doing. Most teams learn it after their first surprising invoice.

counting context budget prompt caching batch API unit economics rate limits

How you are billed

Almost every provider charges per million tokens, with four different rates:

RateApplies toTypical multiple
InputEverything you send: system prompt, history, retrieved documents, tool schemas, images1×
Cached inputA repeated prefix the provider has already processed0.02–0.25× of input
Cache writeEstablishing that cached prefix, on some providers1.25× of input, once
OutputTokens the model generates, including reasoning tokens you never see3–5× of input
Some providers also charge a premium above a context-length threshold, and offer a discount for asynchronous batch jobs.

Two implications that shape design. Output is the expensive direction, so asking for less is a real optimisation: "reply with one word" versus "explain your reasoning then answer" can be a tenfold cost difference on a classification task. And cached input is nearly free, so a stable prompt prefix is worth engineering for.

Counting before you send

Guessing token counts leads to two failures: requests rejected at the context boundary, and budget planning built on fiction. Count properly.

python — exact counts, three ways
# 1. OpenAI-family models, offline and instant
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o-mini")
n = len(enc.encode("The deployment failed because the readiness probe timed out."))

# 2. Any open-weight model, from its own tokeniser
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("mistralai/Mistral-7B-Instruct-v0.3")
n = len(tok.encode(text))

# 3. Providers that do not publish a local tokeniser expose an endpoint
n = client.messages.count_tokens(model=MODEL, system=SYSTEM, messages=msgs).input_tokens
Message overhead is real

Counting only the content undercounts. Each message carries structural tokens for its role and boundaries, tool schemas are serialised into the prompt and charged, and images are converted to a token count based on their dimensions. Budget a few tokens per message plus the full serialised size of your tool definitions — a rich tool set can be 1,500 tokens before the user has said anything.

Budgeting the context window

Treat the window like a fixed memory allocation and give every consumer an explicit share. Without this, retrieval quietly grows until one long conversation with five documents blows the limit in production and nowhere else.

AllocationShare of a 128k windowNotes
System prompt and rules1,500Stable, cacheable, worth keeping tight anyway — long prompts dilute attention
Tool schemas1,500Grows fast. Ten tools with rich descriptions is easily 3,000
Few-shot examples2,000Cacheable if fixed. Drop first if you are tight
Retrieved passages8,000A hard cap, enforced by the retriever, not a hope
Conversation history12,000Trimmed or summarised to fit (chapter 4)
Reserved for output4,000Must be subtracted from the window before you fill anything else
Safety margin10%Your counter is an estimate; the provider's is authoritative
That is under 30k of a 128k window. Using far less than the maximum is normal and usually produces better answers.
budget.py — enforce it rather than hoping
class ContextBudget:
    def __init__(self, window: int, reserve_output: int, margin: float = 0.10):
        self.available = int((window - reserve_output) * (1 - margin))
        self.spent = {}

    def take(self, name: str, text: str, counter) -> str:
        n = counter(text)
        if self.remaining < n:
            raise ContextOverflow(f"{name} needs {n}, only {self.remaining} left: {self.spent}")
        self.spent[name] = n
        return text

    def fit(self, name: str, chunks: list[str], counter, cap: int) -> list[str]:
        """Take chunks in order until the section cap or the window is reached."""
        out, used = [], 0
        for c in chunks:
            n = counter(c)
            if used + n > min(cap, self.remaining):
                break
            out.append(c); used += n
        self.spent[name] = used
        return out

    @property
    def remaining(self): return self.available - sum(self.spent.values())

Prompt caching

This is the highest-leverage cost optimisation available, and it is nearly free to adopt. The provider keeps the processed representation of a prompt prefix; when your next request starts with the identical prefix, that part is not recomputed and is billed at a fraction of the rate. It also cuts time to first token substantially.

Stable prefixSystem prompt, tool schemas, few-shot examples, a fixed document
›
Cache hitCharged at ~10% of input, and not re-processed
›
Variable suffixRetrieved passages, conversation, this turn's question
›
Full priceThe only part you pay properly for

The rules that decide whether it works:

  • Matching is on an exact prefix, byte for byte, from the very start of the request. One changed character anywhere in the prefix invalidates everything after it.
  • Order your prompt from most stable to least. System rules, then tool definitions, then examples, then retrieved context, then history, then the current question. This ordering is the entire technique.
  • Remove volatility from the prefix. A timestamp, a request id, a user name or a randomly ordered set of tools at the top of your system prompt reduces your hit rate to zero. Move them below the cached boundary.
  • There is a minimum length — often around 1,000 tokens — below which caching does nothing.
  • Entries expire, typically after a few minutes of inactivity, with longer options sometimes available. Bursty per-user traffic caches well; one request per user per hour does not.
  • Some providers require explicit markers on the block you want cached; others cache automatically. Check, because the automatic ones still need the ordering discipline.
python — explicit cache markers and a cache-friendly layout
messages = [
    # --- stable prefix: identical on every request, marked for caching -------
    {"role": "system", "content": [
        {"type": "text", "text": SYSTEM_RULES},                     # ~1,200 tokens
        {"type": "text", "text": FEW_SHOT_EXAMPLES,
         "cache_control": {"type": "ephemeral"}},                   # ~2,000 tokens, cached
    ]},
    # --- variable suffix: changes per request, paid in full -----------------
    {"role": "user", "content": f"CONTEXT:\n{passages}\n\nQUESTION: {question}"},
]

# Verify it is working. If cache_read stays at 0, your prefix is not stable.
r = client.messages.create(model=MODEL, messages=messages, max_tokens=800)
log.info("cache_write=%s cache_read=%s uncached=%s",
         r.usage.cache_creation_input_tokens,
         r.usage.cache_read_input_tokens,
         r.usage.input_tokens)
Worked example

A support assistant with a 3,200-token stable prefix, 6,000 tokens of retrieved context and 350 tokens of output, at $1/$5 per million, costs $0.0110 per request uncached. With the prefix cached at 0.1×, it costs $0.0081 — a 26% saving for a change in prompt ordering and one parameter. On a million requests a month that is roughly $2,900. The estimator above will do this arithmetic for your numbers.

Batch processing

If a workload does not need an answer within seconds — nightly enrichment, back-filling classifications, generating embeddings for an existing corpus, running an eval suite — providers offer an asynchronous batch mode at roughly half price with a turnaround measured in hours.

python — submit a batch, collect later
import json

with open("batch.jsonl", "w") as f:
    for doc in documents:                       # one request per line
        f.write(json.dumps({
            "custom_id": doc.id,                # how you match results back
            "method": "POST",
            "url": "/v1/chat/completions",
            "body": {"model": MODEL, "temperature": 0, "max_tokens": 200,
                     "messages": [{"role": "system", "content": SYSTEM},
                                  {"role": "user", "content": doc.text}]},
        }) + "\n")

up  = client.files.create(file=open("batch.jsonl", "rb"), purpose="batch")
job = client.batches.create(input_file_id=up.id, endpoint="/v1/chat/completions",
                            completion_window="24h")

# Poll, then stream the results file. Handle per-line failures: a batch can
# partially succeed, and a missing custom_id is a silent data-quality bug.

Rules of thumb: batch anything offline, never batch anything a user is waiting for, and always reconcile the returned custom_ids against what you submitted.

The cost levers, in order of payoff

#LeverTypical savingEffortRisk

Where the surprise bills come from

In roughly this order: an agent loop with no iteration cap; a retry loop with no deadline during a provider incident; a tool returning a 200,000-token API response straight into the context; an unauthenticated endpoint that proxies to a model; re-embedding an entire corpus after a chunking change; and a conversation feature with no history trimming. Every one is a bug in your code, not a pricing problem.

Unit economics

Convert cost per request into cost per user per month before you commit to a pricing model. The arithmetic is simple and the conclusions are often uncomfortable.

python — the number your finance team will ask for
cost_per_request   = 0.0081                       # from the estimator above
requests_per_user  = 40                           # per month, from your analytics
heavy_user_factor  = 6                            # p95 users, not the mean

typical = cost_per_request * requests_per_user            # $0.32 / user / month
heavy   = typical * heavy_user_factor                     # $1.94 / user / month

price   = 20.00
print(f"gross margin, typical user: {(price - typical) / price:.1%}")   # 98.4%
print(f"gross margin, heavy user:   {(price - heavy)   / price:.1%}")   # 90.3%
print(f"break-even requests/month:  {price / cost_per_request:,.0f}")   # 2,469

Three things this exercise reveals:

  • Plan by the tail, not the mean. Usage of AI features is heavily skewed. A small proportion of users can account for most of the spend, and averages hide it entirely.
  • Unlimited plans need a limit somewhere. Either a soft cap with a friendly message, a hard cap, degradation to a cheaper model, or usage-based pricing above a threshold. Decide before launch, not during an incident.
  • Free tiers are an attack surface. An unauthenticated or trivially registered endpoint that proxies to a model is a way for strangers to spend your money — sometimes deliberately, by reselling access. Rate-limit per account and per IP, require verification, and alert on anomalies.

Rate limits

Limits are usually expressed as requests per minute and tokens per minute, per model, per account tier. Tokens per minute is the one that surprises people: a job sending 30 requests a minute with 20,000-token prompts is consuming 600,000 tokens a minute and will be throttled long before the request limit matters.

python — a token-aware limiter that keeps you under TPM
import time, threading

class TokenBucket:
    """Admit work only when the projected token spend fits the per-minute budget."""
    def __init__(self, tokens_per_minute: int):
        self.rate = tokens_per_minute / 60.0
        self.capacity = tokens_per_minute
        self.tokens = float(tokens_per_minute)
        self.updated = time.monotonic()
        self.lock = threading.Lock()

    def acquire(self, estimated: int, timeout: float = 60.0):
        deadline = time.monotonic() + timeout
        while True:
            with self.lock:
                now = time.monotonic()
                self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
                self.updated = now
                if self.tokens >= estimated:
                    self.tokens -= estimated
                    return
            if time.monotonic() > deadline:
                raise TimeoutError("token budget unavailable")
            time.sleep(0.05)

# Estimate before the call, reconcile after it with the real usage figure.

Beyond a limiter: keep a queue for bulk work so it cannot starve interactive traffic, request a limit increase well before you need it (approval is not instant), and spread heavy jobs across a longer window rather than firing them all at midnight.

Instrumenting spend

Log usage on every call, in one place — the seam you built in chapter 4 — with enough dimensions to answer the questions you will be asked.

the fields that make cost questions answerable
log.info("llm_call", extra={
    "trace_id":       trace_id,          # one user request may make many calls
    "feature":        "support_answer",  # which product surface
    "step":           "generate",        # which step within it
    "tenant_id":      tenant.id,         # who to bill or investigate
    "model":          spec.id,           # exact pinned version
    "input_tokens":   u.input_tokens,
    "cached_tokens":  u.cached_input_tokens,
    "output_tokens":  u.output_tokens,
    "cost_usd":       cost(u, spec),     # computed once, centrally
    "latency_ms":     latency,
    "finish_reason":  finish,
    "retry_count":    retries,
    "cache_hit_rate": u.cached_input_tokens / max(1, u.input_tokens),
})

With those fields you can answer, without a new deploy: which feature costs the most, which tenant is anomalous, whether caching is actually working, how much of the bill is retries, and what a 10× growth in users would cost. Without them, cost work is archaeology.

The short version

  1. Output tokens cost several times input tokens. Asking for less is a first-class optimisation.
  2. Count tokens with the real tokeniser, and remember message overhead, tool schemas and images.
  3. Give the context window an explicit budget per section and enforce it. Reserve output space first.
  4. Order the prompt stable-to-variable and turn on caching. It is the cheapest large saving available.
  5. Model routing beats every other lever: most calls in a mature system should be going to a small model.
  6. Compute cost per user per month at the p95, not the mean, and cap something before launch.
  7. Log tokens, cost, cache hit rate and model version on every call, with a feature and tenant dimension.
