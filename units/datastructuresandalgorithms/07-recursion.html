Recursion

A function that calls itself is not a trick — it is what you write when a problem contains a smaller copy of itself. Trees, graphs, nested structures and every divide-and-conquer algorithm in this unit are built on it, and the whole thing rests on one machine-level mechanism: the call stack.

— words— min read2 interactivesNeeds: chapters 02, 05

The shape of a recursive function

Two parts, and both are compulsory. A base case that returns without recursing, and a recursive case that calls itself on a strictly smaller input. Omit the first and it never stops; omit the second's shrinking and it also never stops.

python
def factorial(n):
    if n <= 1:            # ① base case — stops the recursion
        return 1
    return n * factorial(n - 1)   # ② recursive case — n strictly decreases
Trust the recursion

The hardest habit to build is refusing to trace the calls in your head. Assume factorial(n-1) already returns the correct answer, and ask only whether you combine it correctly. That is all a proof by induction does — verify the base case, then verify the step assuming the previous one holds. People who find recursion hard are usually trying to simulate the whole stack mentally, which is both exhausting and unnecessary.

The call stack

factorial(5), frame by frame
Nothing multiplies until the base case returns

Every call allocates a frame holding its arguments, locals and the address to return to. Frames stack up on the way down and unwind on the way back, which has two consequences you will meet constantly:

Recursion costs memory
Depth d means d frames alive at once, so space is O(d) even if the function allocates nothing. This is why chapter 2 insisted on counting depth rather than total calls.
There is a hard limit
CPython raises RecursionError at about 1,000 frames. A recursive algorithm on a million-element list will crash regardless of how efficient it is.

The recursion tree

When a function makes more than one recursive call, the calls form a tree rather than a chain. Drawing that tree is how you work out the complexity — and how you see immediately why some recursive solutions are catastrophic.

Fibonacci, with and without a cache
The same function, two very different trees

python
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)      # O(2ⁿ) — fib(50) would take days

from functools import lru_cache
@lru_cache(maxsize=None)
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)      # O(n) — one decorator, exponential to linear

def fib(n):                          # O(n) time, O(1) space, no stack at all
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

The fix generalises: whenever a recursion tree contains the same subproblem more than once, caching results collapses it from a tree to a graph, and the cost drops from the number of nodes to the number of distinct nodes. That observation is the whole of chapter 20.

Recursion and iteration

Every recursive function has an iterative equivalent, because you can always manage the stack yourself. Sometimes that is worth doing.

python — the same traversal, three ways
# ① recursive — clearest
def walk(node):
    if not node: return
    visit(node)
    walk(node.left)
    walk(node.right)

# ② iterative with an explicit stack — same order, no depth limit
def walk(root):
    if not root: return
    stack = [root]
    while stack:
        node = stack.pop()
        visit(node)
        if node.right: stack.append(node.right)   # right first —
        if node.left:  stack.append(node.left)    # so left pops first

# ③ tail-recursive — and Python will NOT optimise it away
def count(node, acc=0):
    if not node: return acc
    return count(node.next, acc + 1)   # still O(n) stack frames in Python
Tail-call optimisation

A tail call is a recursive call that is the last thing a function does — nothing remains to compute with its result. Such a call can reuse the current frame instead of allocating a new one, making recursion depth O(1). Scheme, Scala and most functional languages do this; Python, Java and JavaScript engines generally do not. Guido van Rossum has explicitly declined it for Python, partly because it destroys tracebacks. So in Python, tail recursion buys you nothing over ordinary recursion — write a loop.

Prefer recursion whenPrefer iteration when
The data is recursive — trees, graphs, nested JSON, file systemsThe structure is a flat sequence
Divide and conquer, or backtrackingDepth could exceed the stack limit
The recursive version is dramatically clearerThe call overhead matters in a hot loop
Depth is logarithmic — a balanced tree of a billion nodes is only 30 deepDepth is linear in the input size

The templates

python — divide and conquer
def solve(problem):
    if is_trivial(problem):          # ① base case
        return direct_answer(problem)
    left, right = split(problem)     # ② divide
    a = solve(left)                  # ③ conquer the parts
    b = solve(right)
    return combine(a, b)            # ④ combine

# mergesort, quicksort, binary search, closest pair, fast exponentiation,
# and most tree algorithms are all this shape.

#   two halves, O(n) to combine  →  T(n) = 2T(n/2) + O(n)  →  O(n log n)
python — backtracking, and the pattern chapter 19 expands
def backtrack(state, choices, results):
    if is_complete(state):
        results.append(state.copy())     # copy — state keeps mutating
        return
    for choice in choices:
        if not is_valid(state, choice):
            continue                     # prune — this is where the speed comes from
        state.append(choice)             # make the choice
        backtrack(state, choices, results)
        state.pop()                      # UNDO it — the defining move

# subsets, permutations, N-queens, sudoku, word search: all this shape
python — three habits worth adopting
# ① pass indices, never slices
def bad(a):  return bad(a[1:])                # O(n) copy per call → O(n²)
def good(a, i=0): return good(a, i + 1)      # O(1) per call

# ② use a helper when the signature would otherwise be ugly
def depth(root):
    def go(node, d):
        if not node: return d
        return max(go(node.left, d+1), go(node.right, d+1))
    return go(root, 0)              # callers see a clean interface

# ③ raise the limit only when you know the depth is bounded
import sys
sys.setrecursionlimit(10000)         # the C stack can still overflow and crash

Self-check

  1. Why is naive recursive Fibonacci exponential when it only makes two calls?
    Because each call makes two more, so the number of calls doubles at each level of the tree — about 2ⁿ nodes for depth n. The deeper problem is that the same subproblems recur: fib(3) is computed five times inside fib(6). There are only n distinct subproblems, so caching collapses the tree to a chain and the cost to O(n). Toggle memoisation in the demo and watch the node count fall.
  2. A recursive function makes 2ⁿ calls but is only n deep. What is its space complexity?
    O(n), from the call stack. Only the frames along the current root-to-leaf path exist at once — completed branches have already returned and released theirs. Time is O(2ⁿ), space is O(n). Depth, not call count, determines stack usage, and this distinction applies to every tree and backtracking algorithm in the unit.
  3. Your recursion works on small inputs and raises RecursionError on large ones. What are the options?
    Convert to iteration with an explicit stack, which removes the limit entirely and is the right answer for linear-depth recursion over sequences or degenerate trees. Alternatively restructure so the depth becomes logarithmic — a balanced tree of a billion nodes is only 30 deep. Raising sys.setrecursionlimit is a last resort: the interpreter's guard exists to prevent a hard C-stack overflow, which crashes the process rather than raising an exception.
  4. Why does f(arr[1:]) quietly ruin a recursive function?
    Slicing copies. Each call allocates and copies an array one element shorter, so n calls copy n + (n−1) + … = O(n²) elements — the copying dominates whatever the algorithm was doing. Pass the original array plus an index instead, making each call O(1) in setup. The same applies to concatenating strings or dictionaries into recursive calls.
  5. What makes a call a tail call, and why does it not help in Python?
    A tail call is a recursive call that is the very last operation — its result is returned directly, with nothing left to compute. A compiler can therefore reuse the current stack frame instead of pushing a new one, making depth O(1). Python does not implement this, deliberately: it would destroy tracebacks, which are considered more valuable. So in Python a tail-recursive function still uses O(n) stack, and if depth is the problem you should write a loop.
