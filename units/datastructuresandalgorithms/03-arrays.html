Arrays and dynamic arrays

The simplest structure and the one you should reach for first. Its single design decision — store elements next to each other in memory — buys constant-time indexing, forces linear-time insertion, and produces a cache advantage large enough to overturn complexity tables.

— words— min read2 interactivesNeeds: chapter 02

Contiguous memory

An array is a block of memory holding elements of equal size, one after another. That is the entire definition, and every property follows from it.

$$\text{address}(i) = \text{base} + i \times \text{element size}$$

One multiplication and one addition. The hardware does this in a single instruction, and the cost does not depend on i — reaching element 1,000,000 is exactly as fast as reaching element 0. That is what O(1) random access means, and it is the reason arrays underpin almost everything else in this unit.

Two consequences come immediately:

Elements must be the same size
Otherwise the arithmetic does not work. Languages with typed arrays store the values directly; Python's list stores pointers, which are all 8 bytes, so the array of pointers is uniform even when the objects are not.
The block must be contiguous
Which means growing it may require finding a new, larger block and copying everything across. There is no way to extend a block in place if something else already occupies the next address.

The distinction between length and capacity is what makes dynamic arrays work. A list of 5 elements might own a block with room for 8; appending writes into a spare slot with no allocation at all. When the spares run out, a bigger block is allocated and everything is copied — the expensive event that chapter 2's amortised analysis showed is rare enough not to matter.

The cache advantage

Complexity analysis says an array scan and a linked list traversal are both O(n). On real hardware the array can be ten times faster, and the reason is the one thing Big-O deliberately cannot see.

Memory is not accessed a byte at a time. When the processor needs an address, it loads an entire cache line — typically 64 bytes, so 8 or 16 array elements — into fast on-chip memory. If the next thing you touch is in that line, it is essentially free. If it is somewhere else, you wait, and the wait is on the order of a hundred times longer than the arithmetic you were trying to do.

        total += grid[r][c]

# identical operation count, identical O(rows × cols),
# and the second can be several times slower on a large grid
Why this matters beyond loops

This effect is why an array of structs often beats a linked list even for insertion-heavy workloads, why NumPy operations are fast, why C-order versus F-order matters in scientific code, and why "just use a list" is usually correct advice. When two structures have the same complexity, the contiguous one wins. Chapter 4 returns to this when comparing arrays with linked lists honestly.

Array techniques worth knowing early

python
# ── in-place reversal: two pointers walking inward ──
def reverse(a):
    i, j = 0, len(a) - 1
    while i < j:
        a[i], a[j] = a[j], a[i]
        i += 1; j -= 1
    # O(n) time, O(1) space — chapter 19 generalises this pattern

# ── prefix sums: pay O(n) once, answer any range sum in O(1) ──
def build_prefix(a):
    p = [0] * (len(a) + 1)
    for i, x in enumerate(a):
        p[i+1] = p[i] + x
    return p

def range_sum(p, lo, hi):      # sum of a[lo:hi]
    return p[hi] - p[lo]        # O(1) — chapter 18 builds on this

# ── rotate left by k, in place, using three reversals ──
def rotate(a, k):
    k %= len(a)
    a.reverse()                  # the classic trick:
    a[:len(a)-k] = reversed(a[:len(a)-k])   # reverse all, then reverse each part
    a[len(a)-k:] = reversed(a[len(a)-k:])

# ── the two-pass idiom: filter in place without a second array ──
def remove_value(a, val):
    w = 0                        # write pointer trails the read pointer
    for x in a:
        if x != val:
            a[w] = x; w += 1
    del a[w:]
    # O(n) time, O(1) extra space, order preserved
Building a list by inserting at the front

A loop doing result.insert(0, x) n times is O(n²) — every insertion shifts everything. Append and reverse at the end, or use collections.deque which has O(1) appendleft. This appears constantly in code that builds a result while walking backwards through something, and it is invisible until the input grows.

A Python list of a million integers holds a million 8-byte pointers plus a million separate integer objects — roughly 36 MB. The equivalent NumPy array is 8 MB in one contiguous block, and iterating it touches a fraction of the cache lines. That difference is why numeric Python moves to NumPy rather than optimising the loop.

When an array is the wrong choice
  • Frequent insertion or deletion at the front or middle — a deque or a linked structure avoids the shifting.
  • Lookup by key rather than position — a hash table, chapter 6.
  • You need the minimum repeatedly — a heap, chapter 13.
  • Sorted order must be maintained under insertion — a balanced tree, chapter 12, or bisect.insort if insertions are rare enough that O(n) shifting is acceptable.
  • The data does not fit in memory — a B-tree on disk, chapter 12.

Self-check

  1. Why is indexing an array O(1) but indexing a linked list O(n)?
    Because an array computes the address directly: base + i × element size, one multiplication and one addition regardless of i. A linked list stores each node wherever memory was available, with only a pointer to the next, so reaching element i means following i pointers. Contiguity is what buys the arithmetic, and it is the only thing that does.
  2. A list has length 5 and capacity 8. What happens on the next three appends?
    The first three each write into a spare slot and increment the length — O(1), no allocation. The fourth would find length equal to capacity, so it allocates a larger block (typically 1.5× or 2×), copies all 8 elements, frees the old block, then writes. That one call is O(n); spread across the sequence it is O(1) amortised, as the demo in chapter 2 showed.
  3. Two loops over the same 2D grid have identical operation counts, but one is four times slower. Why?
    Cache lines. The grid is laid out row by row in memory, so a row-wise loop touches consecutive addresses and each 64-byte line loaded serves 8 or 16 elements. A column-wise loop jumps a full row between accesses, so nearly every access needs a fresh line, and if the cache cannot hold a whole column's worth of lines they are evicted before being reused. Big-O cannot see this because it counts operations, not memory hierarchy behaviour.
  4. How would you remove every occurrence of a value from a list in O(n) with no extra array?
    Two pointers: a read pointer walks the whole list, and a write pointer trails behind. Whenever the read value should be kept, write it at the write pointer and advance it. At the end, truncate to the write pointer's position. One pass, O(1) extra space, order preserved. The naive alternative — calling remove in a loop — is O(n²) because each removal shifts the tail.
  5. When would you use array.array or NumPy instead of a list?
    When the data is large and numerically homogeneous. A list stores pointers to separate integer objects — around 36 bytes per element in total — while both alternatives store raw values contiguously at 4 or 8 bytes each. That is roughly 4× less memory and dramatically better cache behaviour, and NumPy additionally lets you replace the Python loop with a vectorised operation running in C.
