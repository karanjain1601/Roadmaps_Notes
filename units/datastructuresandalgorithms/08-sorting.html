Sorting

You will almost never implement a sort. You will constantly rely on one, choose between them, and be asked to explain them — and the six classic algorithms are the clearest worked examples of the design ideas in this unit: incremental construction, divide and conquer, and using a data structure to do the work for you.

The properties that distinguish them

Stable
Equal elements keep their original relative order. This matters more than it sounds: it lets you sort by one key, then another, and have the first act as a tie-breaker. Sort by name, then by department, and each department's names remain alphabetical.
In place
Uses O(1) or O(log n) extra memory rather than a second copy of the data. Decisive when the array is large.
Adaptive
Runs faster on partly sorted input. Insertion sort is O(n) on nearly-sorted data; mergesort does the same work regardless.
Comparison-based
Learns about the data only by asking "is a before b?". This restriction is what makes O(n log n) a hard floor — and sidestepping it is how the linear-time sorts work.

The simple three

python
def bubble_sort(a):
    for i in range(len(a)):
        swapped = False
        for j in range(len(a) - i - 1):
            if a[j] > a[j+1]:
                a[j], a[j+1] = a[j+1], a[j]
                swapped = True
        if not swapped:               # already sorted → O(n) best case
            break

def selection_sort(a):
    for i in range(len(a)):
        m = min(range(i, len(a)), key=lambda j: a[j])
        a[i], a[m] = a[m], a[i]        # exactly n−1 swaps, always ⚠ not stable

def insertion_sort(a):
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0 and a[j] > key:  # strictly greater keeps it STABLE
            a[j+1] = a[j]
            j -= 1
        a[j+1] = key                # O(n) on nearly-sorted input
Insertion sort is not a toy

It is the only one of the three used in production. It is stable, in place, adaptive, and has a very small constant — so real library sorts switch to it for subarrays below roughly 16–32 elements. Bubble sort's single virtue is being easy to explain; selection sort's is doing the minimum possible number of swaps, which matters only when writes are far more expensive than reads.

The efficient three

python — mergesort: divide, sort, merge
def merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    left  = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    return merge(left, right)

def merge(l, r):
    out, i, j = [], 0, 0
    while i < len(l) and j < len(r):
        if l[i] <= r[j]:            # <= keeps it stable — < would not
            out.append(l[i]); i += 1
        else:
            out.append(r[j]); j += 1
    out.extend(l[i:]); out.extend(r[j:])
    return out

# T(n) = 2T(n/2) + O(n)  →  O(n log n) in every case
# O(n) extra space, which is its one real drawback
python — quicksort: partition, then recurse
import random

def quick_sort(a, lo=0, hi=None):
    if hi is None: hi = len(a) - 1
    if lo >= hi: return
    p = partition(a, lo, hi)
    quick_sort(a, lo, p - 1)
    quick_sort(a, p + 1, hi)

def partition(a, lo, hi):                 # Lomuto scheme
    k = random.randint(lo, hi)              # randomise — this is what kills the worst case
    a[k], a[hi] = a[hi], a[k]
    pivot = a[hi]
    i = lo - 1                             # boundary of the "≤ pivot" region
    for j in range(lo, hi):
        if a[j] <= pivot:
            i += 1
            a[i], a[j] = a[j], a[i]
    a[i+1], a[hi] = a[hi], a[i+1]        # pivot into its final position
    return i + 1
One partition step
Two pointers, and the pivot lands in its final position

Heapsort is the third: build a max-heap from the array in O(n), then repeatedly swap the root to the end and sift down. O(n log n) in every case and fully in place — the only one of the three with both guarantees. Its weakness is memory access: sifting jumps around the array, so it loses badly to quicksort on cache behaviour. Chapter 13 builds the heap; the sort is four lines once you have one.

Why O(n log n) is a floor

No comparison-based sort can do better, and the proof is a counting argument you can reconstruct from memory.

Any comparison sort is a decision tree: each internal node asks "is a[i] < a[j]?", each branch is an answer, and each leaf is one possible ordering of the input. To sort correctly the tree must have a leaf for every permutation, so at least n! leaves. A binary tree with L leaves has height at least log₂L, and the height is the number of comparisons in the worst case:

$$h \ge \log_2(n!) \approx n\log_2 n - 1.44n = \Omega(n\log n)$$

None of these contradicts the bound, because none of them is a comparison sort — they use the value of a key to compute where it goes, exactly as a hash table does. Which is the general lesson: a lower bound constrains a model of computation, and the way past it is to change the model.

Timsort
Python's sorted and Java's object sort. Finds existing sorted runs, extends short ones with insertion sort, and merges them. Stable, adaptive, and O(n) on already-sorted input — which real data very often nearly is.
Introsort
C++ std::sort. Runs quicksort, switches to heapsort if recursion gets too deep, and finishes with insertion sort on small ranges. Quicksort's speed with heapsort's worst-case guarantee.
External sorting
When the data exceeds memory: sort chunks that fit, write them out, then k-way merge the sorted runs. Mergesort is the natural fit because merging is sequential — chapter 12's B-trees exist for the same reason.
python — what you will actually write
people.sort(key=lambda p: p.age)              # in place, stable, Timsort
ordered = sorted(people, key=lambda p: p.age)   # returns a new list

# descending
people.sort(key=lambda p: p.age, reverse=True)

# multiple keys — tuple, and the second breaks ties in the first
people.sort(key=lambda p: (p.dept, p.name))

# mixed directions: exploit stability by sorting twice, LEAST significant first
people.sort(key=lambda p: p.name)                  # ② then this, ascending
people.sort(key=lambda p: p.age, reverse=True)   # ① this wins, ties keep name order

# don't sort when you only need the top k — O(n) instead of O(n log n)

Self-check

  1. Why does stability matter?
    Because it lets you build a multi-key ordering from single-key sorts. Sort by name, then by department: with a stable sort, each department block stays alphabetical by name, so two simple passes produce a compound ordering. It also matters whenever equal-comparing records are not identical — sorting a table by one column should not scramble rows that tie. Quicksort and heapsort are not stable; mergesort, insertion sort and Timsort are.
  2. Quicksort's worst case is O(n²). Why is it still the default in most libraries?
    Because its average case has the best constant factors of any comparison sort — it works in place with sequential memory access, which the cache rewards heavily — and randomising the pivot makes the worst case require an adversary who knows your random seed. Libraries hedge anyway: introsort detects excessive recursion depth and switches to heapsort, giving quicksort's speed with an O(n log n) guarantee.
  3. Reconstruct the argument that comparison sorting cannot beat O(n log n).
    Model any comparison sort as a decision tree: internal nodes are comparisons, branches are the two answers, leaves are output orderings. Correctness requires a distinct leaf for each of the n! permutations. A binary tree with n! leaves has height at least log₂(n!), which by Stirling is about n log₂ n. Height equals the number of comparisons in the worst case, so no comparison sort can do better than Ω(n log n).
  4. How do counting and radix sort beat that bound?
    They are not comparison sorts, so the bound does not apply. Counting sort uses the key's value as an array index — the same trick as a hash table — and radix sort applies that repeatedly, one digit at a time, relying on stability to preserve the work of earlier passes. They buy this by assuming something extra about the keys: a small known range, or fixed width. Lower bounds constrain a model, and changing the model is the way past them.
  5. You need the 10 largest of a million values. Sort and slice?
    No. Sorting is O(n log n) to produce an ordering you throw away. A heap of size 10 scanned across the input is O(n log k) — effectively O(n) for constant k — and uses almost no memory. heapq.nlargest(10, data) does exactly this. Chapter 13 covers the mechanism; the general point is that "sort then take a bit" is usually a sign of a cheaper algorithm.
  6. When would you deliberately choose insertion sort?
    On small arrays — below roughly 16 to 32 elements, where its tiny constant beats the overhead of divide and conquer, which is why production sorts switch to it for small subranges. Also on nearly-sorted data, where it is O(n) with very few writes, and in streaming situations where elements arrive one at a time and must be placed into an already-sorted result.
