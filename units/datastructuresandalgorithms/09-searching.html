Chapter 09 · Recursion and sorting

Searching

Binary search is four lines that almost nobody writes correctly the first time. It is also far more general than "find a value in a sorted array" — the real technique is searching a space where a yes/no question flips exactly once, and that shape appears in problems that look nothing like searching.

— words— min read2 interactivesNeeds: chapters 02, 08

Linear search, and when it is right

Walk the collection, compare each element. O(n), no preconditions, five seconds to write. It is the correct choice more often than people admit:

Use linear search whenReason
The data is unsorted and you search onceSorting costs O(n log n) — more than the single scan you were trying to avoid
n is smallBelow roughly 50 elements the sequential scan's cache behaviour often beats binary search's jumping
The data changes constantlyMaintaining sorted order costs more than scanning
You need every match, not the firstYou are traversing anyway

The crossover: if you will perform k searches, sorting first pays off when k · n exceeds n log n + k log n — roughly when k grows past log n. One search, scan. Thousands of searches, sort first or build a hash table.

Binary search

Halve the search space on every comparison. A million elements takes 20 comparisons; a billion takes 30. That is the whole appeal, and it costs you one precondition: the data must be sorted.

Binary search
Half the remaining range disappears at every step
python — the version to memorise
def binary_search(a, target):
    lo, hi = 0, len(a) - 1          # INCLUSIVE bounds
    while lo <= hi:                    # so <=, not <
        mid = lo + (hi - lo) // 2      # avoids overflow in fixed-width languages
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1                # the +1 and −1 are what guarantee progress
        else:
            hi = mid - 1
    return -1
The four ways it breaks
  1. Infinite loop. Writing lo = mid instead of lo = mid + 1. When hi = lo + 1, mid equals lo, and the range never shrinks. Every iteration must exclude mid.
  2. Off-by-one at the boundary. Mixing inclusive bounds with while lo < hi, so the last element is never examined. Pick one convention — inclusive with <=, or half-open with < — and keep it consistent.
  3. Overflow. (lo + hi) // 2 overflows for large indices in C, C++ and Java. The bug survived in the JDK's own binary search for nine years. Python's integers make it harmless, but the habit is free.
  4. Unsorted input. Returns a plausible wrong answer rather than an error, which is the worst failure mode there is.

The variants that actually get used

python
# first index where a[i] >= target  — "lower bound" / bisect_left
def lower_bound(a, target):
    lo, hi = 0, len(a)              # half-open: hi is one PAST the end
    while lo < hi:                  # so <, not <=
        mid = (lo + hi) // 2
        if a[mid] < target: lo = mid + 1
        else:               hi = mid       # mid stays in the range — it may be the answer
    return lo                       # == len(a) if every element is smaller

# first index where a[i] > target  — "upper bound" / bisect_right
def upper_bound(a, target):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] <= target: lo = mid + 1   # the ONLY difference: <= instead of <
        else:                hi = mid
    return lo

# everything follows from these two
count_of_x   = upper_bound(a, x) - lower_bound(a, x)
first_occurrence = lower_bound(a, x)          # if a[i] == x
last_occurrence  = upper_bound(a, x) - 1
insertion_point  = lower_bound(a, x)          # keeps the array sorted

# and the standard library has both
from bisect import bisect_left, bisect_right, insort
i = bisect_left(a, x)
insort(a, x)                                  # O(log n) to find, O(n) to shift
The mental model that fixes the off-by-ones

Stop thinking "find the target" and start thinking "find the boundary where a condition flips". Every binary search maintains an invariant: everything left of lo fails the condition, everything at or right of hi satisfies it. The loop shrinks the unknown middle until it is empty, and lo is the boundary. Written that way, lower bound and upper bound differ by one character, and "does the target exist" becomes a check afterwards rather than a special case inside.

Binary search on the answer

The generalisation that makes this chapter worth more than its length suggests. If you can check an answer more easily than you can compute it, and the check is monotone — false, false, false, true, true, true — then binary search the answer space.

Searching a space of answers
"What is the smallest ship capacity that delivers all packages in 3 days?"
python — the template
def min_capacity(weights, days):
    def feasible(cap):                 # ① can we finish within `days` at this capacity?
        need, load = 1, 0
        for w in weights:
            if load + w > cap:
                need += 1; load = 0
            load += w
        return need <= days            # O(n) — much easier than computing the answer

    lo, hi = max(weights), sum(weights)  # ② bound the answer space
    while lo < hi:                       # ③ standard lower-bound search
        mid = (lo + hi) // 2
        if feasible(mid): hi = mid       #    mid works — but something smaller might too
        else:             lo = mid + 1   #    mid fails — so does everything below it
    return lo
    # O(n log(sum − max)) instead of trying every capacity
ProblemThe answer spaceThe predicate
Minimum ship capacity in D daysmax weight … total weightCan we finish in D days at this capacity?

Square root to 6 decimal places0 … nIs mid² ≤ n?
Largest square of 1s in a grid0 … min(rows, cols)Does a square of this size exist?
Minimum time for k workers0 … worst caseCan k workers finish within this time?

The signal is a problem phrased as "minimise the maximum", "maximise the minimum", or "the smallest X such that Y is possible". Direct computation is usually hard; checking a candidate is usually a simple greedy pass. When you notice that asymmetry, you have found a binary search.

Self-check

  1. Why does lo = mid instead of lo = mid + 1 cause an infinite loop?
    When the range is two elements, integer division makes mid equal to lo. Setting lo = mid leaves the range unchanged, so the loop repeats forever with identical state. Every iteration must strictly shrink the range, which means excluding mid from at least one side. The half-open form hi = mid is safe precisely because hi is exclusive, so the range still shrinks.
  2. What do bisect_left and bisect_right return, and how do they differ?
    bisect_left returns the first index where the element is ≥ target; bisect_right returns the first index where it is strictly greater. For a value present once they differ by one; for a value absent they return the same insertion point. Their difference gives the count of occurrences, and bisect_right − 1 gives the last occurrence. In the implementation they differ by a single character: < versus <=.
  3. Why is (lo + hi) // 2 a bug in C but not in Python?
    In fixed-width integer languages, lo + hi can exceed the maximum int and wrap to a negative value, producing an out-of-bounds index. lo + (hi − lo) // 2 is mathematically identical and cannot overflow. Python's integers are arbitrary precision so the bug cannot occur — but the habit costs nothing and the original form survived undetected in the JDK for nine years, which is a reasonable argument for writing it the safe way everywhere.
  4. What tells you a problem wants binary search on the answer?
    Two things together: the phrasing is "minimise the maximum", "maximise the minimum", or "the smallest X such that Y is possible"; and checking a candidate answer is much easier than computing the answer directly — usually a single greedy pass. The check must be monotone, so that if a candidate works, every larger one works too. Then you binary search the answer range with the check as the predicate.
  5. You have an unsorted array of a million elements and need to answer 5 membership queries. Sort first?
    No. Sorting is about 20 million comparisons; five linear scans are five million element visits with excellent cache behaviour. The crossover is around k > log n queries, so with 5 queries scanning wins and with 5,000 it does not. If queries keep arriving, build a hash set instead — O(n) once and O(1) per query, which beats sorting for membership.
