Linked structures

Taught immediately after arrays as the natural alternative, and in application code almost never the right answer. Worth understanding precisely — because the ideas underpin trees, graphs and half of what follows — and worth being sceptical about as a choice.

nodes and pointers singly and doubly the honest verdict techniques

The structure

A node holds a value and a reference to the next node. That is all. The nodes can live anywhere in memory; the chain is made of pointers rather than adjacency.

a singly linked list, complete
class Node:
    __slots__ = ("value", "next")          # avoids a per-node dict; still not cheap
    def __init__(self, value, nxt=None):
        self.value, self.next = value, nxt

class LinkedList:
    def __init__(self):
        self.head = None
        self.size = 0

    def push_front(self, v):               # O(1) — the operation it exists for
        self.head = Node(v, self.head)
        self.size += 1

    def pop_front(self):                   # O(1)
        if self.head is None: raise IndexError("empty")
        v, self.head = self.head.value, self.head.next
        self.size -= 1
        return v

    def find(self, v):                     # O(n) — no shortcuts available
        node = self.head
        while node:
            if node.value == v: return node
            node = node.next
        return None

    def insert_after(self, node, v):       # O(1) — but only if you HOLD the node
        node.next = Node(v, node.next)
        self.size += 1

    def delete_after(self, node):          # O(1), same caveat
        if node.next:
            node.next = node.next.next
            self.size -= 1

    def __iter__(self):
        node = self.head
        while node:
            yield node.value
            node = node.next
The caveat that undoes most of the advantage

"O(1) insertion and deletion" is true and almost always quoted without its condition: you must already hold a reference to the node. If you have to find it first, that is O(n), and the O(1) splice afterwards is noise. Since finding is the common case, the headline advantage evaporates in most real usage — and this is the single most misleading thing in the standard presentation of linked lists.

the doubly-linked unlink — the operation that justifies the extra pointer
def unlink(node):                          # O(1), given only the node itself
    if node.prev: node.prev.next = node.next
    if node.next: node.next.prev = node.prev
    node.prev = node.next = None

# A singly linked list cannot do this. To remove a node you need the one before
# it, so you either walk from the head — O(n) — or keep the predecessor around,
# which is what makes singly-linked deletion awkward in practice.
#
# This one operation is why an LRU cache uses a doubly linked list plus a hash
# map: the map finds the node in O(1), and unlink moves it in O(1). Neither
# structure can do it alone.

Even "insert in the middle" usually goes to the array

This is the case the textbook gives to the linked list, and it is the one most often wrong. Inserting at index i in an array shifts the tail — but that shift is a single contiguous memmove, which modern hardware does at many gigabytes per second. The list avoids the shift and pays instead for walking i pointers, each potentially a cache miss at roughly 80ns. For collections up to several thousand elements the array is routinely faster despite doing "more work". The list only wins when you already hold the node and never had to walk to it.

Where linked structures genuinely win

LRU caches
A hash map to find a node in O(1), a doubly linked list to move it to the front in O(1). Neither structure can do both; the combination is why this pairing is everywhere.
Intrusive lists in systems code
The link pointers live inside the object itself, so an object can be on several lists at once with no allocation. Kernel schedulers, allocators and drivers use this heavily.
Free lists in allocators
The free blocks store the next-pointer in their own unused memory. Zero overhead, because the space was free anyway.
Persistent and functional structures
Prepending to an immutable list shares the entire tail — O(1) and no copying. An immutable array cannot do that.
Splicing whole sublists
Joining or cutting sequences in O(1) by rewiring a few pointers. Rope structures for text editors build on this.
Unstable references
A pointer to an array element is invalidated by a resize. A pointer to a list node stays valid forever, which matters when other structures hold references into it.
lru.py — the canonical justified use of a doubly linked list
class LRUCache:
    """Hash map for O(1) find; doubly linked list for O(1) reorder."""

    def __init__(self, capacity: int):
        self.cap = capacity
        self.map: dict = {}                          # key -> node
        # Sentinel head and tail remove every null check from the link code.
        self.head, self.tail = Node(None), Node(None)
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n

    def get(self, key):
        n = self.map.get(key)
        if n is None: return None
        self._unlink(n); self._push_front(n)         # mark as recently used, O(1)
        return n.value

    def put(self, key, value):
        if key in self.map:
            n = self.map[key]
            n.value = value
            self._unlink(n); self._push_front(n)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev                     # least recently used
            self._unlink(lru)
            del self.map[lru.key]
        n = Node(value); n.key = key
        self.map[key] = n
        self._push_front(n)

# Every operation is O(1). An array cannot do the reorder; a hash map has no
# order. This is the shape to remember: a list for order, a map for lookup.
Sentinel nodes

Notice the empty head and tail nodes above. They exist so that _unlink and _push_front never need to check for null — every real node always has a predecessor and a successor. This removes the entire class of edge-case bug that makes linked-list code notoriously fiddly: first element, last element, single element, empty list. Two wasted nodes for a large reduction in defects is an excellent trade, and it is the standard technique.

The techniques worth knowing

Linked lists are over-represented in interviews, and these four cover most of what is asked. They also transfer — the two-pointer idea reappears in chapter 17.

reverse in place — the one everybody is asked
def reverse(head):
    prev, node = None, head
    while node:
        nxt = node.next        # remember where we were going
        node.next = prev       # flip the pointer
        prev, node = node, nxt # advance both
    return prev                # new head

# O(n) time, O(1) space. The whole trick is holding three references: the one
# behind, the current one, and the one ahead — because flipping the pointer
# destroys your only route forward.
fast and slow pointers — middle, cycle, and nth from the end
def middle(head):                       # slow arrives at the midpoint
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    return slow

def has_cycle(head):                    # Floyd's algorithm
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast: return True    # a faster runner on a loop laps a slower one
    return False

def cycle_start(head):                  # where the loop begins
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            slow = head
            while slow is not fast:     # both move one step; they meet at the entry
                slow, fast = slow.next, fast.next
            return slow
    return None

def nth_from_end(head, n):              # a gap of n, then walk both to the end
    lead = head
    for _ in range(n):
        if not lead: return None
        lead = lead.next
    trail = head
    while lead:
        lead, trail = lead.next, trail.next
    return trail

# All four are O(n) time and O(1) space, and all four are the same idea:
# maintain two references with a controlled relationship between them.
Why cycle_start works

Worth understanding rather than memorising. Let the tail before the loop have length a, and let the meeting point be b steps into a loop of length c. When they meet, slow has walked a + b and fast has walked twice that, so fast has gone a + b + kc for some whole number of laps k. Setting those equal gives a = kc − b. That is exactly the distance from the meeting point back round to the loop entry — so a pointer starting at the head and one starting at the meeting point, both moving one step, arrive together at the entry. It is a small piece of arithmetic and it turns an unmemorable trick into an obvious one.

The verdict

Do not reach for a linked list because

  • "Insertion is O(1)" — only if you hold the node
  • "Arrays have to resize" — amortised O(1), and the copy is fast
  • "It saves memory" — it usually costs 2–3× more for small values
  • "It avoids shifting" — the shift is a memmove and it is very fast
  • You need a queue — use a deque (chapter 5)

Do reach for one when

  • You hold node references and splice at them — LRU, schedulers
  • References must stay valid across mutation
  • You are joining or cutting whole sequences
  • The structure must be immutable and share tails
  • You are writing an allocator or a kernel data structure
  • You are building a tree or a graph — which are linked structures
The real reason to learn this chapter

Not so you will use linked lists. So you will recognise them: a tree is a linked structure with several next-pointers, and a graph is one with no constraints on where they point. Pointer manipulation, traversal, cycle detection and sentinel handling all reappear in chapters 7 through 13. This is the chapter where those ideas are simple enough to see clearly.

The short version

  1. A node holds a value and a reference. Nodes live anywhere; the chain is pointers, not adjacency.
  2. "O(1) insertion" requires already holding the node. If you must find it first, the advantage disappears.
  3. Iteration is O(n) for both, and the array is 5–20× faster on constants because of the cache.
  4. Even middle insertion usually goes to the array: a memmove beats a pointer chase at realistic sizes.
  5. The genuine wins are held-node splicing, stable references, O(1) joins and persistent sharing — LRU caches being the canonical case.
  6. Sentinel nodes remove the entire class of first/last/empty edge-case bugs.
  7. Reverse, fast-and-slow, cycle detection and nth-from-end are all two references in a controlled relationship.
  8. Learn it because trees and graphs are linked structures, not because you will choose a list.
