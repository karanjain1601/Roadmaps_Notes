Chapter 11 · Trees

Binary search trees

Binary search made structural. One ordering rule turns a tree into a searchable collection that also supports insertion, deletion, ordered iteration and range queries — and the same rule, met with sorted input, degrades the whole thing into a linked list.

— words— min read2 interactivesNeeds: chapters 09, 10

The property

The BST invariant

For every node: every value in its left subtree is smaller, and every value in its right subtree is larger. Not just its immediate children — the entire subtree. That distinction is the source of the most common bug in BST validation code.

The payoff is that a single comparison eliminates an entire subtree. Searching becomes exactly the halving from chapter 9, except that the structure encodes the halving instead of arithmetic doing it.

python
class Node:
    __slots__ = ("val", "left", "right")
    def __init__(self, val):
        self.val, self.left, self.right = val, None, None

def search(node, target):
    while node:
        if target == node.val: return node
        node = node.left if target < node.val else node.right
    return None                       # O(h) — h is the HEIGHT, not log n

def insert(root, val):
    if not root: return Node(val)
    if val < root.val:  root.left  = insert(root.left, val)
    elif val > root.val: root.right = insert(root.right, val)
    return root                       # duplicates ignored; new nodes always become leaves
Build one, then search it
The insertion order decides everything
Every cost is O(h), not O(log n)

Textbooks quote O(log n) for BST operations, and that is only true when the tree is balanced. Insert sorted data into a plain BST and every value goes to the right of the last, producing a chain of height n — search, insert and delete all become O(n), and a recursive traversal overflows the stack. Sorted input is not exotic: it is what you get from a database, a log file, or anything already ordered. Chapter 12 is the fix.

Deletion — the interesting one

Search and insert are a few lines each. Deletion has three cases, and the third is where BSTs stop being obvious.

The three deletion cases
Removing a node must leave the ordering intact
python
def delete(node, val):
    if not node: return None
    if val < node.val:
        node.left = delete(node.left, val)
    elif val > node.val:
        node.right = delete(node.right, val)
    else:
        # ① no children — just vanish
        # ② one child — the child takes this node's place
        if not node.left:  return node.right
        if not node.right: return node.left
        # ③ two children — replace with the in-order SUCCESSOR:
        #    the smallest value in the right subtree, which is the only
        #    value that can sit here without breaking the ordering
        succ = node.right
        while succ.left:
            succ = succ.left
        node.val = succ.val
        node.right = delete(node.right, succ.val)   # and remove it from below
    return node

# the successor always has at most one child — it cannot have a left child,
# or it would not be the smallest — so the recursive call hits case ① or ②
Why the successor is the only valid replacement

The removed node sits between everything in its left subtree and everything in its right. Whatever takes its place must satisfy the same constraint, so it must be greater than every value on the left and smaller than every value on the right. Exactly two values qualify: the largest on the left (the predecessor) and the smallest on the right (the successor). Either works, and implementations that always pick the same one gradually skew the tree — some alternate between them for that reason.

What a tree gives you that a hash table cannot

If you only need lookup by key, use a hash table — it is O(1) and simpler. The reason to accept O(log n) is that hashing destroys ordering, and a tree keeps it.

python
# ── in-order traversal emits sorted values, for free ──
def inorder(node, out):
    if not node: return
    inorder(node.left, out); out.append(node.val); inorder(node.right, out)

# ── floor and ceiling: nearest value at or below / above ──
def floor(node, x):
    best = None
    while node:
        if node.val == x: return x
        if node.val < x:
            best = node.val; node = node.right    # candidate — but try for closer
        else:
            node = node.left
    return best

# ── range query: every value in [lo, hi], pruning whole subtrees ──
def range_query(node, lo, hi, out):
    if not node: return
    if node.val > lo: range_query(node.left, lo, hi, out)
    if lo <= node.val <= hi: out.append(node.val)
    if node.val < hi: range_query(node.right, lo, hi, out)
    # O(log n + k) for k results — the two guards skip entire subtrees

# ── validation: the range travels DOWN, the verdict comes UP ──
def is_bst(node, lo=float("-inf"), hi=float("inf")):
    if not node: return True
    if not (lo < node.val < hi): return False
    return (is_bst(node.left,  lo, node.val) and
            is_bst(node.right, node.val, hi))
    # ✗ comparing only against immediate children passes invalid trees

Choosing between them

Lookup only, no ordering → hash table. Ordered operations with frequent insertions → balanced tree. Ordered operations on data that rarely changes → sorted array with binary search, which beats a tree on cache behaviour and memory. In Python there is no built-in balanced tree: use bisect on a list when writes are rare, sortedcontainers.SortedList when they are not, or a heap if you only ever want the extreme.

Self-check

  1. Why is checking only against immediate children the wrong way to validate a BST?
    Because the property constrains entire subtrees, not parent-child pairs. A tree with root 10, left child 5, and 5's right child 12 satisfies every local comparison — 5 < 10, 12 > 5 — yet 12 sits in the left subtree of 10, which is invalid. Correct validation passes a permitted range downward, narrowing it at each step, so every node is checked against every ancestor's constraint at once.
  2. Deleting a node with two children — why the in-order successor?
    Because the replacement must be greater than everything in the left subtree and smaller than everything in the right, and only two values satisfy that: the largest on the left, or the smallest on the right. The successor is the latter. It conveniently has no left child — otherwise it would not be the smallest — so removing it from its old position hits the easy one-child or no-child case.
  3. You insert 1 through 1000 in order into a plain BST. What have you built?
    A linked list. Every value is larger than the current node, so each becomes the right child of the previous — height 1000, all operations O(n), and a recursive traversal overflows the stack. The tree is not incorrect, just useless. This is why self-balancing variants exist, and why sorted input is the case you must assume rather than the case you hope to avoid.
  4. When is a hash table the wrong choice despite being O(1)?
    Whenever you need order: minimum or maximum, the nearest key above or below a value, all keys in a range, or iteration in sorted sequence. Hashing deliberately scatters keys, so all of those become O(n) scans. A balanced tree gives O(log n) lookup and keeps every ordered operation cheap — that is exactly what you are paying the logarithm for.
  5. Why does a range query cost O(log n + k) rather than O(n)?
    Because the ordering lets you prune. If a node's value is below the range's lower bound, its entire left subtree is too, and you skip it without looking — likewise on the right. The traversal descends to the range's boundaries, which is O(log n) in a balanced tree, and then visits only the k nodes actually inside it. The two guard conditions in the code are what cut off the rest.
