Range queries

"What is the sum of elements 3 through 900?" asked a million times, on data that keeps changing. Scanning is O(n) per query; precomputing everything makes updates O(n). The structures here find the middle, and all of them are the same idea — store partial answers over nested intervals.

Prefix sums: the static answer

If the data never changes, one pass is enough. Store the running total, and any range sum becomes a subtraction.

p = [0] * (len(a) + 1)          # the leading 0 removes every edge case
for i, x in enumerate(a):
    p[i+1] = p[i] + x

range_sum = p[hi] - p[lo]        # sum of a[lo:hi] — O(1)

The segment tree

Build a binary tree over the array where each node stores the answer for its interval. Any query range decomposes into at most 2 log n of those precomputed intervals.

class SegTree:
    def __init__(self, a):
        self.n = len(a)
        self.t = [0] * (4 * self.n)     # 4n is always enough for any n
        self._build(a, 1, 0, self.n - 1)

    def _build(self, a, node, lo, hi):
        if lo == hi:
            self.t[node] = a[lo]; return
        mid = (lo + hi) // 2
        self._build(a, 2*node,     lo,      mid)
        self._build(a, 2*node + 1, mid + 1, hi)
        self.t[node] = self.t[2*node] + self.t[2*node + 1]   # O(n) total

    def query(self, l, r, node=1, lo=0, hi=None):
        if hi is None: hi = self.n - 1
        if r < lo or hi < l:  return 0          // no overlap → identity element
        if l <= lo and hi <= r: return self.t[node]   # fully inside → use the stored answer
        mid = (lo + hi) // 2                     # partial → split and recurse
        return (self.query(l, r, 2*node,     lo,      mid) +
                self.query(l, r, 2*node + 1, mid + 1, hi))

    def update(self, i, val, node=1, lo=0, hi=None):
        if hi is None: hi = self.n - 1
        if lo == hi:
            self.t[node] = val; return
        mid = (lo + hi) // 2
        if i <= mid: self.update(i, val, 2*node,     lo,      mid)
        else:        self.update(i, val, 2*node + 1, mid + 1, hi)
        self.t[node] = self.t[2*node] + self.t[2*node + 1]   # repair the path up
Change the operator, keep everything else

Nothing in the structure cares that the operation is addition. Replace + with min and you have range minimum; with max, range maximum; with gcd, range gcd. The only requirement is associativity — the combine must not care how the interval was split — plus an identity element for the empty case. That generality is why a segment tree is worth learning once and a Fenwick tree, which is tied to invertible operations, is not a full substitute.

Lazy propagation

Point updates are easy. Range updates — "add 5 to everything between 100 and 900" — would touch O(n) leaves. The trick is to stop at the nodes that fully cover the range, record the pending change there, and push it down only when a later query needs to look inside.

python — the idea in outline
def push(self, node, lo, hi):
    if not self.lazy[node]: return
    self.t[node] += self.lazy[node] * (hi - lo + 1)   # apply to this node
    if lo != hi:                                       # and defer to the children
        self.lazy[2*node]   += self.lazy[node]
        self.lazy[2*node+1] += self.lazy[node]
    self.lazy[node] = 0

# every query and update calls push() on the way down, so a node's
# stored value is always correct by the time it is read.
# range update becomes O(log n) instead of O(n).

The Fenwick tree

Also called a binary indexed tree. It answers the same prefix-sum question with a fraction of the code and memory, using nothing but a single array and the lowest set bit of an index.

Which cells hold what

python — the entire structure
class Fenwick:
    def __init__(self, n):
        self.t = [0] * (n + 1)          # 1-indexed — the arithmetic needs it

    def add(self, i, delta):          # i is 1-based
        while i < len(self.t):
            self.t[i] += delta
            i += i & -i                # move to the next cell covering i

    def prefix(self, i):              # sum of the first i elements
        s = 0
        while i > 0:
            s += self.t[i]
            i -= i & -i                # strip the lowest set bit
        return s

    def range_sum(self, l, r):
        return self.prefix(r) - self.prefix(l - 1)

# i & -i isolates the lowest set bit: 12 = 1100 → 4, 13 = 1101 → 1.
# cell i stores the sum of the (i & -i) elements ending at i, so the
# cells visited on the way down partition the prefix exactly once.

Sparse tables

For data that never changes and an operation where overlapping is harmless — min, max, gcd — you can precompute the answer for every interval whose length is a power of two, then answer any query with two lookups.

$$\text{min}(l,r) = \min\big(\, \text{table}[k][l],\; \text{table}[k][r-2^k+1] \,\big), \qquad k = \lfloor \log_2(r-l+1) \rfloor$$

The two intervals overlap, which is fine because taking the minimum twice changes nothing. It would not be fine for sums — which is exactly why sparse tables are limited to idempotent operations.

Do the cheap thing first

These structures are satisfying and mostly unnecessary. If the data is static, prefix sums answer the question in O(1) with four lines. If there are only a few hundred queries, a plain scan is fine. If you need range sums with updates, the ten-line Fenwick tree covers it. A full segment tree with lazy propagation earns its complexity only when you need range updates and range queries on a non-invertible operation — which is common in competitive programming and rare elsewhere.

Self-check

  1. Why do prefix sums fail once the data can change?
    Because changing element i invalidates every prefix sum from i onward, so an update is O(n). Prefix sums push all the cost into preprocessing, which is exactly right when preprocessing happens once. Fenwick and segment trees rebalance that trade: both query and update become O(log n), so no single operation is catastrophic.
  2. Why is a range query on a segment tree O(log n) rather than O(n)?
    Because the query range decomposes into a small number of precomputed intervals. At each level of the tree at most two nodes are partially overlapped by the range — one at each end — and everything between them is fully covered and taken whole. With log n levels that is at most 2 log n nodes touched. Drag the range in the demo and watch the covering-node count stay tiny while the number of array elements grows.
  3. What must an operation satisfy to work in a segment tree?
    Associativity, plus an identity element for empty ranges. The tree combines a node's two children without knowing how the interval was originally split, so the result must not depend on the grouping. Sum, min, max, gcd, bitwise and, matrix product all qualify. Subtraction and average do not, since they are not associative — though average can be handled by storing sum and count and dividing at the end.
  4. What does i & -i compute, and why does the Fenwick tree need it?
    It isolates the lowest set bit of i — 12 is 1100 so it gives 4; 13 is 1101 so it gives 1. Cell i stores the sum of exactly that many elements ending at i. Subtracting the low bit walks a prefix through cells whose ranges partition it precisely once; adding it walks up through every cell whose range contains i. Both loops run once per bit, giving O(log n).
  5. Why can a sparse table do min in O(1) but not sum?
    Because it covers the query with two power-of-two intervals that overlap in the middle, and min is idempotent — including an element twice changes nothing. Summing would double-count the overlap. Any idempotent associative operation works: min, max, gcd, bitwise and or or. For sums you need a non-overlapping decomposition, which is what prefix sums and segment trees provide.
  6. Static data, ten million range-sum queries. What do you use?
    Prefix sums. One O(n) pass, then every query is a single subtraction — O(1), no tree, four lines of code, and perfect cache behaviour on one contiguous array. A Fenwick tree would answer each query in O(log n) for no benefit, and a segment tree would be slower still with far more code. Only reach for the trees when the data changes.
