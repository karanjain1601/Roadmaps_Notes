Trees and traversal

A tree is a linked structure with more than one next-pointer and a rule against cycles. That rule buys hierarchy, and hierarchy is what lets you discard half the possibilities at every step — which is where logarithmic time comes from.

Height is the only number that matters

Nearly every tree operation walks one root-to-leaf path, so cost is O(height). With n nodes, height can be anywhere from ⌊log₂ n⌋ (perfectly balanced) to n − 1 (a straight line). That range — from 20 steps to a million — is the entire subject of chapter 8. Whenever you read "O(log n)" about a tree, it silently assumes balance, and that assumption is exactly what an unbalanced tree violates.

The binary search tree

One invariant, applied at every node: everything in the left subtree is smaller, everything in the right subtree is larger. That is what makes search logarithmic — each comparison discards an entire subtree.

bst.py — search, insert and the delete case people get wrong
class Node:
    __slots__ = ("key", "val", "left", "right")
    def __init__(self, key, val):
        self.key, self.val = key, val
        self.left = self.right = None

def search(node, key):                      # O(height)
    while node:
        if   key < node.key: node = node.left
        elif key > node.key: node = node.right
        else: return node
    return None

def insert(node, key, val):                 # returns the (possibly new) subtree root
    if node is None: return Node(key, val)
    if   key < node.key: node.left  = insert(node.left, key, val)
    elif key > node.key: node.right = insert(node.right, key, val)
    else: node.val = val                    # key already present: update
    return node

def delete(node, key):
    if node is None: return None
    if   key < node.key: node.left  = delete(node.left, key);  return node
    elif key > node.key: node.right = delete(node.right, key); return node

    # Found it. Three cases, and only the third is interesting.
    if node.left  is None: return node.right     # 0 or 1 child: promote it
    if node.right is None: return node.left

    # Two children: replace this node's contents with its in-order successor —
    # the smallest key in the right subtree — then delete that successor.
    # The successor has at most one child by construction, so the recursion
    # bottoms out immediately.
    succ = node.right
    while succ.left: succ = succ.left
    node.key, node.val = succ.key, succ.val
    node.right = delete(node.right, succ.key)
    return node
Why the successor, specifically

Deleting a node with two children leaves a hole that must be filled by a key which is still larger than everything on the left and smaller than everything on the right. Exactly two keys qualify: the in-order predecessor (largest on the left) and the in-order successor (smallest on the right). Either works. The successor is conventional, and the reason it terminates cleanly is that the smallest node in a subtree cannot have a left child — so the recursive delete hits one of the easy cases immediately.

all four, and the one that is different
def in_order(n, out):
    if not n: return
    in_order(n.left, out); out.append(n.key); in_order(n.right, out)

def pre_order(n, out):
    if not n: return
    out.append(n.key); pre_order(n.left, out); pre_order(n.right, out)

def post_order(n, out):
    if not n: return
    post_order(n.left, out); post_order(n.right, out); out.append(n.key)

# The first three differ by ONE LINE'S POSITION. All three are depth-first and
# all three use the call stack implicitly.

from collections import deque
def level_order(root):
    if not root: return []
    out, q = [], deque([root])
    while q:
        n = q.popleft()                     # a QUEUE, not the call stack
        out.append(n.key)
        if n.left:  q.append(n.left)
        if n.right: q.append(n.right)
    return out

# Level-order is structurally different: it cannot be expressed by moving one
# line, because it is breadth-first. This is chapter 5's point again — the
# container choice IS the algorithm.
In-order on a BST is sorted, and that is the whole reason BSTs exist

A hash table beats a BST on lookup, insert and delete — better constants, simpler code. What it cannot do is produce keys in order, answer "what is the next key after X", or return everything between two bounds. Those all fall directly out of the in-order property. When you choose a tree over a hash table, this is what you are buying, and if you never use it you have chosen the wrong structure.

Iterative traversal

Recursion is clearer, but it consumes stack proportional to height — and on a degenerate tree that is O(n) frames and a real overflow risk on untrusted input.

making the stack explicit
def pre_order_iter(root):                   # easiest: push right first, so left pops first
    out, stack = [], [root] if root else []
    while stack:
        n = stack.pop()
        out.append(n.key)
        if n.right: stack.append(n.right)
        if n.left:  stack.append(n.left)
    return out

def in_order_iter(root):                    # the one worth memorising
    out, stack, n = [], [], root
    while stack or n:
        while n:                            # descend left, remembering the path
            stack.append(n); n = n.left
        n = stack.pop()                     # leftmost unvisited node
        out.append(n.key)
        n = n.right                         # then its right subtree
    return out

# Note what in_order_iter is: a manual reconstruction of exactly what the call
# stack was doing. Converting recursion to iteration is always this — you are
# writing down the frames yourself (chapter 14).
Morris traversal — O(1) space, by temporarily vandalising the tree
def morris_in_order(root):
    out, n = [], root
    while n:
        if n.left is None:
            out.append(n.key); n = n.right
        else:
            # Find the in-order predecessor: rightmost node of the left subtree.
            pred = n.left
            while pred.right and pred.right is not n:
                pred = pred.right
            if pred.right is None:
                pred.right = n              # thread a temporary link back up
                n = n.left
            else:
                pred.right = None           # undo it; the subtree is done
                out.append(n.key); n = n.right
    return out

# No stack and no recursion — the tree carries the return path in unused right
# pointers, then repairs itself. Rarely needed, genuinely clever, and a good
# illustration that "O(n) space for traversal" was never a law.

The recursive shape

Almost every tree question is the same three lines: handle the empty case, recurse into both children, combine. Recognising that is worth more than memorising the individual answers.

one template, six problems
def height(n):
    if not n: return -1                         # empty tree: height -1, so a leaf is 0
    return 1 + max(height(n.left), height(n.right))

def count(n):
    return 0 if not n else 1 + count(n.left) + count(n.right)

def mirror(n):
    if not n: return None
    n.left, n.right = mirror(n.right), mirror(n.left)
    return n

def is_same(a, b):
    if not a and not b: return True
    if not a or not b:  return False
    return a.key == b.key and is_same(a.left, b.left) and is_same(a.right, b.right)

def is_balanced(n):
    def h(node):
        if not node: return 0
        l, r = h(node.left), h(node.right)
        if l < 0 or r < 0 or abs(l - r) > 1: return -1    # -1 propagates failure up
        return 1 + max(l, r)
    return h(n) >= 0

def lowest_common_ancestor(n, a, b):            # on a BST, use the ordering
    while n:
        if   a < n.key and b < n.key: n = n.left
        elif a > n.key and b > n.key: n = n.right
        else: return n                          # the split point is the LCA
    return None
Validating a BST — the trap everyone falls into

Checking only that each node is greater than its left child and smaller than its right child is wrong. It passes trees where a node deep in the left subtree is larger than an ancestor — locally correct, globally invalid. The invariant is about entire subtrees, not immediate children, so validation must carry bounds down the recursion.

two correct validations
def is_bst(n, lo=float("-inf"), hi=float("inf")):
    if not n: return True
    if not (lo < n.key < hi): return False
    return (is_bst(n.left,  lo, n.key) and      # bounds narrow as you descend
            is_bst(n.right, n.key, hi))

# Or exploit the in-order property directly: a valid BST's in-order traversal
# is strictly increasing. This version is shorter and often clearer.
def is_bst_inorder(root):
    prev = None
    for key in in_order_gen(root):
        if prev is not None and key <= prev: return False
        prev = key
    return True

Sorted input is the common case, not the adversarial one

The degenerate case for a plain BST is inserting keys in order — which is what happens when you load rows from a database ordered by id, or replay events by timestamp, or ingest anything already sorted. The structure silently becomes a linked list with extra memory overhead, and every operation becomes O(n). This is not a contrived worst case; it is the most likely shape of real data, and it is precisely why nobody ships a plain BST. Chapter 8 is the fix.

Trees that are not binary search trees

Heaps
A complete binary tree with a weaker invariant — parent beats child, with no ordering between siblings. Stored in an array with no pointers at all. Chapter 9.
Tries
One child per possible character; the path from the root spells the key. Chapter 18.
B-trees
Many keys and many children per node, sized to a disk page. What databases actually use. Chapter 8.
Expression trees
Operators as internal nodes, operands as leaves. Post-order traversal evaluates them, which is why post-order and reverse Polish notation are the same idea.
Parse and syntax trees
Every compiler and every JSON parser builds one. Pre-order serialises it; post-order evaluates it.
Merkle trees
Each node hashes its children. Git commits, blockchains and content-addressed stores are built on this, and it makes "did anything change" a single comparison.
Filesystem hierarchies
A tree with arbitrary branching. du is post-order — a directory's size needs its children's sizes first.

The short version

  1. A tree is a linked structure with several next-pointers and no cycles. Height is the only number that matters.
  2. The BST invariant is about entire subtrees, not immediate children — which is why naive validation is wrong.
  3. Deleting a node with two children: replace with the in-order successor, which by construction has at most one child.
  4. The three depth-first orders differ by one line's position. Level-order differs by using a queue instead of the stack.
  5. In-order on a BST is sorted order, and that property is the entire reason to choose a tree over a hash table.
  6. Iterative traversal is just writing the call stack down yourself. Morris traversal shows even that is not required.
  7. Most tree problems are one template: empty case, recurse both sides, combine.
  8. A plain BST degenerates to a list on sorted input — which is the most likely shape of real data, not an adversarial one.
