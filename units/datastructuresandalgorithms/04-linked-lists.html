Linked lists

The opposite design decision to chapter 3: store elements wherever memory is free and connect them with pointers. That buys O(1) insertion anywhere you already stand, costs you indexing and cache locality, and produces the pointer manipulations that make up a surprising share of interview questions.

— words— min read2 interactivesNeeds: chapter 03

Nodes and pointers

A node holds a value and a reference to the next node. The list is a reference to the first node. There is no block, no capacity, and no address arithmetic — you find element i by starting at the head and following i pointers.

python
class Node:
    __slots__ = ("val", "next")          # saves memory; nodes are numerous
    def __init__(self, val, nxt=None):
        self.val, self.next = val, nxt

# build 1 → 2 → 3
head = Node(1, Node(2, Node(3)))

# traverse — the fundamental loop
cur = head
while cur:
    print(cur.val)
    cur = cur.next                    # O(n), and each step may miss the cache

# insert after a node you already hold — this is the whole selling point
def insert_after(node, val):
    node.next = Node(val, node.next)  # O(1), nothing shifts

# delete the node after one you hold
def delete_after(node):
    if node.next:
        node.next = node.next.next    # O(1)
The crucial qualifier

Insertion and deletion are O(1) given a reference to the position. Finding that position is O(n). So "linked lists have O(1) insertion" is true and routinely misapplied: inserting at index 5,000 costs 5,000 pointer hops plus one constant-time splice. The structure only wins when you are already standing where the change happens — which is exactly the situation in an LRU cache, an iterator, or a free-list allocator.

The honest verdict

In practice, arrays win far more often than this table suggests. A linked list traversal chases pointers into scattered memory, so it can be an order of magnitude slower than an array scan doing the same number of operations — chapter 3's cache demo, applied to the worst case. Copying a few thousand contiguous bytes is often cheaper than one cache miss. Reach for a linked list when you need O(1) splicing at held positions, when elements are large, or when you cannot tolerate the copy pause of a resize. Otherwise use a dynamic array or a deque.

python — why a sentinel is worth one wasted node
# without a sentinel: the head is a special case everywhere
def remove_value(head, target):
    while head and head.val == target:   # special case ①
        head = head.next
    cur = head
    while cur and cur.next:              # special case ②: cur might be None
        if cur.next.val == target:
            cur.next = cur.next.next
        else:
            cur = cur.next
    return head

# with a sentinel: one loop, no special cases
def remove_value(head, target):
    dummy = Node(None, head)
    cur = dummy
    while cur.next:
        if cur.next.val == target:
            cur.next = cur.next.next
        else:
            cur = cur.next
    return dummy.next                   # the head may have changed; this handles it

Reversing a list in place

The canonical linked-list exercise, and worth doing slowly once. Three pointers, four statements, and every one of them is necessary — remove any and the list either breaks or becomes unreachable.

In-place reversal
One statement at a time
python
def reverse(head):
    prev = None
    cur = head
    while cur:
        nxt = cur.next        # save the rest of the list before we lose it
        cur.next = prev       # flip this node's pointer backwards
        prev = cur            # prev advances
        cur = nxt             # cur advances into the saved rest
    return prev              # cur is None; prev is the new head
    # O(n) time, O(1) space

The pointer patterns

Fast and slow pointers

Advance one pointer twice as fast as the other. Two classic results follow immediately: when the fast pointer reaches the end, the slow one is at the middle; and if there is a cycle, they must eventually meet.

Floyd's cycle detection
Tortoise and hare, then the second phase that finds where the loop starts
python — the four classics
# ── middle of the list, one pass ──
def middle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    return slow

# ── cycle detection, and where the cycle starts ──
def cycle_start(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:                # they met — there is a cycle
            slow = head
            while slow is not fast:      # now both move one step at a time
                slow, fast = slow.next, fast.next
            return slow                  # the node where the cycle begins
    return None

# ── nth node from the end, one pass ──
def nth_from_end(head, n):
    lead = head
    for _ in range(n):
        lead = lead.next                # open a gap of n
    trail = head
    while lead:
        lead, trail = lead.next, trail.next   # move together
    return trail

# ── merge two sorted lists ──
def merge(a, b):
    dummy = tail = Node(None)
    while a and b:
        if a.val <= b.val: tail.next, a = a, a.next
        else:              tail.next, b = b, b.next
        tail = tail.next
    tail.next = a or b                # attach whatever remains — O(1), no copying
    return dummy.next
Why Floyd's second phase works

Let the tail before the cycle have length a, and let the pointers meet b steps into a cycle of length c. When they meet, slow has travelled a + b and fast has travelled exactly twice that; the difference must be a whole number of laps, so a + b is a multiple of c. That makes the distance from the meeting point onward to the cycle start equal to a — the same distance as from the head. So moving one pointer back to the head and advancing both one step at a time makes them meet precisely at the cycle's first node. Watch the demo run it.

In Python specifically

There is no built-in singly linked list, and you rarely want one. collections.deque covers the "fast at both ends" case with far better constants. Implement nodes by hand when a problem hands you a linked list — which interviews do constantly, because pointer manipulation is hard to fake — and otherwise use a list or a deque. If you build a long chain of nodes, be aware that deleting the head can trigger a cascade of recursive deallocations deep enough to crash CPython; production code unlinks iteratively.

Self-check

  1. Why is "linked lists have O(1) insertion" misleading?
    Because it is O(1) only once you hold a reference to the insertion point, and getting there is O(n). Inserting at index k costs k pointer hops plus a constant-time splice. The structure wins when you are already at the position — an iterator mid-traversal, a node found through a hash map, the head or tail — not when position is expressed as an index.
  2. Which statement can you not remove from the reversal loop, and what breaks?
    All four are needed, but nxt = cur.next is the one whose necessity is least obvious. The very next line overwrites cur.next, so without saving it first the remainder of the list becomes unreachable and the loop cannot advance. Everything after the current node would be lost. Step the demo to that statement and watch the forward arrow disappear.
  3. Why must fast and slow pointers meet if a cycle exists?
    Once both are inside the cycle, the fast pointer gains exactly one position on the slow pointer per step. The gap therefore decreases by one each step, modulo the cycle length, so it must reach zero within at most one cycle's worth of steps — they cannot step past each other, because the gap changes by exactly one. If there is no cycle, fast simply runs off the end.
  4. You need frequent insertion and removal at both ends of a sequence. Array, linked list or deque?
    A deque. It gives O(1) at both ends like a linked list, but stores elements in contiguous blocks, so traversal keeps most of an array's cache advantage and the per-element memory overhead is far lower. A plain array is O(n) at the front; a plain linked list gives the right complexity with poor constants. This is the common case where the textbook answer and the practical answer differ.
  5. Why is a doubly linked list required for an O(1) LRU cache?
    Because on a cache hit you must move an arbitrary node to the front, which means unlinking it from its current position. Unlinking requires knowing the predecessor — instant with a prev pointer, O(n) without one. The hash map gives you the node in O(1), and the backward pointer is what lets you detach it in O(1). Neither structure alone suffices.
