Chapter 20 · Problem solving

Dynamic programming

The topic with the worst reputation, mostly because it is usually taught as a list of tricks. It is one idea: if a recursive solution solves the same subproblem more than once, remember the answers. Everything difficult about it is choosing what a subproblem is.

— words— min read2 interactivesNeeds: chapter 07

The two conditions

Overlapping subproblems
The same smaller question is asked repeatedly. Chapter 7's Fibonacci tree computed fib(3) five times inside fib(6); caching collapsed exponential to linear. Without overlap, caching gains nothing — mergesort's subproblems are all distinct, which is why it is divide and conquer rather than DP.
Optimal substructure
An optimal solution is built from optimal solutions to subproblems. True for shortest paths: the best route through a midpoint uses the best route to that midpoint. False for longest simple paths, where the best route to a midpoint may consume vertices the rest of the journey needed — which is why that problem is NP-hard and this one is not.
The honest description

Dynamic programming is recursion plus a cache. Write the brute-force recursion first, confirm it is correct, then notice it recomputes things and add memoisation. Every DP solution can be reached that way, and doing it in that order is far more reliable than trying to write a table directly. The elegant bottom-up loop is an optimisation of the recursive version, not a different idea.

python — the same problem three ways
# ① brute force — correct, and exponential
def rob(h, i=0):
    if i >= len(h): return 0
    return max(h[i] + rob(h, i+2),      # take this house, skip the next
               rob(h, i+1))              # skip this one

# ② memoised — one decorator, O(n)
from functools import lru_cache
def rob(h):
    @lru_cache(None)
    def go(i):
        if i >= len(h): return 0
        return max(h[i] + go(i+2), go(i+1))
    return go(0)

# ③ tabulated, then space-optimised — O(n) time, O(1) space
def rob(h):
    take, skip = 0, 0                # only two values are ever needed
    for x in h:
        take, skip = skip + x, max(skip, take)
    return max(take, skip)

Designing the state

This is the whole difficulty. Once the state is right the recurrence usually writes itself; when a DP problem feels impossible it is almost always because the state is missing a dimension.

  1. What decision am I making at each step? Take this item or not. Match these characters or not. Cut here or there.
  2. What do I need to know to make it? That answer is the state. Remaining capacity. Position in both strings. Whether I already sold a stock today.
  3. What does the state mean? Write the sentence down: "dp[i][w] is the best value using the first i items with capacity w." Vague definitions produce off-by-one errors that are almost impossible to debug.
  4. What is the recurrence? Express dp[state] in terms of smaller states — usually a max or min over the available decisions.
  5. What are the base cases? Empty input, zero capacity, index past the end.
  6. In what order can it be filled? Every state must come after everything it depends on.
0/1 knapsack, cell by cell
Each cell asks one question: take this item, or not?
python — 0/1 knapsack
def knapsack(items, cap):        # items = [(weight, value), …]
    n = len(items)
    # dp[i][w] = best value using the first i items with capacity w
    dp = [[0] * (cap + 1) for _ in range(n + 1)]

    for i in range(1, n + 1):
        wt, val = items[i-1]
        for w in range(cap + 1):
            dp[i][w] = dp[i-1][w]                    # skip item i
            if wt <= w:                              # or take it, if it fits
                dp[i][w] = max(dp[i][w], dp[i-1][w-wt] + val)
    return dp[n][cap]
    # O(n · cap) time and space — "pseudo-polynomial": linear in the
    # capacity's VALUE, exponential in the number of bits used to write it

# space-optimised: only the previous row is ever read
def knapsack(items, cap):
    dp = [0] * (cap + 1)
    for wt, val in items:
        for w in range(cap, wt - 1, -1):    # BACKWARDS — forwards would let one
            dp[w] = max(dp[w], dp[w-wt] + val)   # item be taken twice
    return dp[cap]

Edit distance, and the alignment it hides
Fill the table, then walk backwards to recover what was done
python — edit distance
def edit_distance(a, b):
    m, n = len(a), len(b)
    # dp[i][j] = edits needed to turn a[:i] into b[:j]
    dp = [[0] * (n+1) for _ in range(m+1)]
    for i in range(m+1): dp[i][0] = i      # delete everything
    for j in range(n+1): dp[0][j] = j      # insert everything

    for i in range(1, m+1):
        for j in range(1, n+1):
            if a[i-1] == b[j-1]:
                dp[i][j] = dp[i-1][j-1]        # characters match — free
            else:
                dp[i][j] = 1 + min(
                    dp[i-1][j],                # delete a[i−1]
                    dp[i][j-1],                # insert b[j−1]
                    dp[i-1][j-1],              # substitute
                )
    return dp[m][n]                       # O(m·n)

# and fuzzy search. Walking back from dp[m][n] recovers the operations.
Two habits that make DP tractable

Write the state's meaning as a sentence, in a comment, before any code. "dp[i][j] is the minimum edits to turn the first i characters of a into the first j of b." Half of all DP bugs are a definition that shifted silently between the base cases and the loop.

Compute the complexity as states × transitions. Knapsack has n·cap states and O(1) work each. Edit distance has m·n states and O(1) each. Matrix-chain has n² states and O(n) each, hence O(n³). If that product is too large for the constraints, the state has a dimension it does not need — or the problem wants something else entirely.

Self-check

  1. What are the two conditions a problem must satisfy for DP to apply?
    Overlapping subproblems — the same smaller question arises repeatedly, so caching pays — and optimal substructure, meaning an optimal solution is composed of optimal solutions to subproblems. Mergesort has the second but not the first, so it is divide and conquer. Longest simple path has the first but not the second, because the best route to a midpoint may use up vertices the remainder needed, and it is NP-hard as a result.
  2. Why should you write the recursion before the table?
    Because the recursion is easy to get right and easy to verify against brute force, and the table is neither until you already know the recurrence and the dependency order. Adding a cache to a correct recursion gives a correct DP immediately; converting to a bottom-up table afterwards is a mechanical optimisation. Attempting to write the table directly means designing the state, the recurrence and the fill order simultaneously, which is where most people get stuck.
  3. In the space-optimised knapsack, why must the inner loop run backwards?
    Because the single row is being updated in place. Iterating forwards, dp[w - wt] may already have been updated with the current item, so taking it again would let one item be used twice — that is the unbounded knapsack, a different problem. Going backwards guarantees dp[w - wt] still holds the previous row's value, which is what the 0/1 recurrence requires. Exactly one character differs between the two problems.
  4. Your DP is correct on small inputs and wrong on large ones. What is the likely cause?
    A missing state dimension. Two genuinely different situations are mapping to the same cache key, so a value computed for one is reused for the other — and with small inputs the collision may never occur. Ask what else you needed to know to make the decision: a remaining count, a previous choice, whether some resource has been used. Anything a decision depends on must appear in the state.
  5. How do you compute a DP's complexity?
    Number of states multiplied by the work per transition. Knapsack: n·capacity states, O(1) each. Edit distance: m·n states, O(1) each. Matrix-chain multiplication: n² states with an O(n) loop inside, hence O(n³). Doing this early tells you whether the design fits the constraints before you write it, and if the product is too large the state usually has a dimension that can be dropped or compressed.
  6. Why is knapsack called "pseudo-polynomial" when it runs in O(n·capacity)?
    Because it is polynomial in the capacity's numeric value but exponential in its input size. A capacity written with 64 bits can be around 10¹⁹, so the table is astronomically large even though the input is tiny. Genuine polynomial complexity is measured against the number of bits needed to write the input. This is why subset sum is NP-complete despite having an apparently efficient DP.
