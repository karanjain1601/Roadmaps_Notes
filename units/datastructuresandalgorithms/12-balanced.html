Balanced trees and B-trees

Chapter 11 ended with a search tree collapsed into a linked list. The repair is a single primitive — the rotation — applied automatically whenever the shape drifts. And then a twist: the fastest tree on a disk is not binary at all.

— words— min read2 interactivesNeeds: chapter 11

The rotation

One local rearrangement that changes a subtree's shape while leaving its in-order sequence untouched. Every self-balancing tree is built from it.

Rotation
Shape changes; the sorted order does not
python — six lines, and both are mirror images
def rotate_right(y):
    x = y.left
    y.left  = x.right      # x's right subtree moves across to y's left
    x.right = y            # y becomes x's right child
    return x               # x is the new root of this subtree

def rotate_left(x):
    y = x.right
    x.right = y.left
    y.left  = x
    return y

# why the ordering survives: in the "before" tree the in-order sequence is
#   [x.left]  x  [x.right]  y  [y.right]
# and after the rotation it is exactly the same sequence — the subtree that
# moved (x.right) sits between x and y both before and after.
Why rotations are safe

A rotation only ever moves the middle subtree — the one between the two nodes being swapped — and that subtree lies between them in sorted order either way. Everything else keeps its relative position. So a rotation is a pure reshaping: no comparisons, no reordering, O(1) work, and the BST property is preserved by construction. That is what makes it a usable repair operation.

AVL trees

The first self-balancing BST, from 1962. It maintains one invariant: for every node, the heights of its two subtrees differ by at most 1. That difference is the node's balance factor, and it must stay in {−1, 0, +1}.

The zig-zag cases need two rotations because a single one just moves the imbalance to the other side. The rule for spotting which case applies: compare the direction of the heavy child with the direction of the heavy grandchild. Same direction is a single rotation; opposite is a double.

python — AVL insertion
def h(n):  return n.height if n else 0
def bf(n): return h(n.left) - h(n.right) if n else 0
def fix(n): n.height = 1 + max(h(n.left), h(n.right))

def insert(node, val):
    if not node: return Node(val)
    if   val < node.val: node.left  = insert(node.left, val)
    elif val > node.val: node.right = insert(node.right, val)
    else: return node
    fix(node)
    b = bf(node)
    if b >  1 and val < node.left.val:            # Left-Left
        return rotate_right(node)
    if b < -1 and val > node.right.val:           # Right-Right
        return rotate_left(node)
    if b >  1:                                    # Left-Right
        node.left = rotate_left(node.left)
        return rotate_right(node)
    if b < -1:                                    # Right-Left
        node.right = rotate_right(node.right)
        return rotate_left(node)
    return node
    # at most 2 rotations per insertion, all O(1) — so insertion stays O(log n)
$$h \le 1.44 \log_2(n+2) - 0.33$$

The worst-case AVL height, about 44% above the theoretical minimum. Deletion is harder than insertion: rebalancing one node can unbalance its parent, so up to O(log n) rotations may cascade up the tree — still O(log n) overall.

Red-black trees

The variant your standard library almost certainly uses. Instead of tracking heights, each node carries one bit of colour, and five rules keep the tree roughly balanced:

  1. Every node is red or black.
  2. The root is black.
  3. Every leaf (the null sentinels) is black.
  4. A red node's children are both black — no two reds in a row.
  5. Every path from a node down to a leaf contains the same number of black nodes.

Rules 4 and 5 together bound the height: the longest path can be at most twice the shortest, because the extra length has to come from red nodes and they cannot be adjacent. That gives h ≤ 2 log₂(n+1) — looser than AVL, and enough.

B-trees: when the memory hierarchy takes over

Every structure so far assumed each node access costs the same. On a disk it does not — and that single change makes binary trees the wrong answer.

A disk read fetches a whole page, typically 4 KB, and costs on the order of a hundred microseconds on an SSD or ten milliseconds on a spinning disk. A binary tree of a billion keys is 30 levels deep, so a lookup is 30 page reads to retrieve 30 individual keys — almost all of each page thrown away.

The B-tree trade

Stop making nodes small. Fill each node with as many keys as fit in one page — hundreds of them — so each expensive read yields hundreds of comparisons' worth of progress. With a fanout of 200, a billion keys fit in four levels: 200⁴ is 1.6 billion. Four page reads instead of thirty. The binary tree was optimising the wrong thing, because it was counting comparisons when the real cost was page fetches.

Structure
A node of order m holds up to m−1 keys in sorted order and up to m child pointers, with the children interleaved between the keys. Search means a binary search within the node, then descending through the correct gap.
Always balanced
All leaves sit at the same depth, maintained by splitting a full node on insert and merging or borrowing on delete. Growth happens at the root, upward — which is why the tree never becomes lopsided.
B+ tree
The variant databases actually use: all data lives in the leaves, internal nodes hold only keys for routing, and the leaves are linked together. Internal nodes therefore hold more keys, and a range scan becomes a descent followed by a walk along the leaf chain — which is what makes WHERE x BETWEEN a AND b fast.
Where you meet them
Every relational database index, MongoDB, and the filesystems NTFS, ext4, Btrfs and HFS+. If you have used an index, you have used a B-tree.
The same argument applies in RAM

Cache lines are pages in miniature — chapter 3's demo, at a different scale. A binary tree pointer-chase misses the cache at almost every level, so in-memory B-trees with a fanout of 16 or 32 routinely beat red-black trees despite doing more comparisons. This is the recurring lesson of the unit: when two structures have the same complexity, the one that respects the memory hierarchy wins.

Self-check

  1. Why does a rotation preserve the BST property?
    Because it only moves the subtree that lies between the two rotated nodes in sorted order, and that subtree sits between them either way. Writing out the in-order sequence before and after gives the identical list. Nothing is compared and nothing is reordered — the rotation is a pure reshaping, which is exactly why it is a safe repair primitive.
  2. Why do the Left-Right and Right-Left cases need two rotations?
    Because the imbalance zig-zags. In a Left-Left case the heavy path goes left then left again, so one right rotation lifts the middle node and evens both sides. In Left-Right the heavy path goes left then right, and a single right rotation would simply move the same imbalance to the other side. Rotating the child first converts the zig-zag into a straight line, and then the single rotation works. The test: heavy child and heavy grandchild in the same direction means one rotation, opposite means two.
  3. Why do most standard libraries use red-black trees rather than AVL?
    Because they rebalance less aggressively. AVL keeps a tighter height bound and so has slightly faster lookups, but it performs more rotations on insertion and deletion. Red-black trees guarantee at most two rotations on insert and three on delete, which makes mixed read-write workloads faster overall — and one colour bit per node is cheaper to store than a height. For read-heavy workloads AVL is the better choice.
  4. Why is a B-tree faster than a red-black tree on disk despite doing more comparisons?
    Because comparisons are not the cost — page reads are, by four or five orders of magnitude. A binary tree with a billion keys needs about 30 page reads, each yielding one useful key. A B-tree with fanout 200 needs 4, each yielding a page full of keys that are then searched in memory for free. The B-tree deliberately does more comparisons in order to do far fewer I/O operations, which is the correct trade when one operation dominates the other so heavily.
  5. What does a B+ tree add over a plain B-tree?
    All records live in the leaves, with internal nodes holding only routing keys, and the leaves are linked in a chain. Two consequences: internal nodes fit more keys, so the fanout rises and the tree gets shallower; and a range scan becomes one descent followed by a sequential walk along the leaf chain rather than a repeated traversal. That is precisely what makes range predicates in SQL efficient, which is why it is the standard database index structure.
  6. Your data arrives sorted and you need ordered operations. What do you use?
    Not a plain BST — sorted input is its worst case and produces a linked list. Options: a self-balancing tree, which handles the order automatically; or, since the data is already sorted, simply keep it in an array and use binary search, which is faster than any tree for lookups and range scans and uses less memory. Only move to a balanced tree if insertions and deletions are frequent enough that the array's O(n) shifting becomes the bottleneck.
