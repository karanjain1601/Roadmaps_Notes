Trees and traversal

A tree is a linked structure with no cycles and one path between any two nodes. That constraint is what allows recursion to work cleanly on it — and it is where the logarithms in the rest of this unit come from, because a balanced tree of a billion nodes is only thirty levels deep.

Where the logarithm comes from

Each level of a binary tree can hold twice as many nodes as the one above, so n nodes fit into about log₂n levels — if they are spread evenly. A perfect tree of height 30 holds over a billion nodes. Every O(log n) claim about trees in this unit is really a claim that the tree is balanced, and every one of them fails on a degenerate tree. That single sentence is why chapter 12 exists.

The four traversals

Depth-first has three variants, and they are not three algorithms — they are one walk with the visit happening at a different moment. Watching that is the fastest way to stop confusing them.

Traversal orders
Same walk, different moment of visiting
python — one function, three visit points
def walk(node):
    if not node: return
    visit(node)          # ← here makes it PRE-order
    walk(node.left)
    visit(node)          # ← here makes it IN-order
    walk(node.right)
    visit(node)          # ← here makes it POST-order

# breadth-first is structurally different — a queue, not recursion
from collections import deque
def level_order(root):
    if not root: return
    q = deque([root])
    while q:
        n = len(q)                     # capture the level size FIRST —
        for _ in range(n):            # this is how you process level by level
            node = q.popleft()
            visit(node)
            if node.left:  q.append(node.left)
            if node.right: q.append(node.right)
OrderSequenceUse it for
Pre-ordernode, left, rightCopying or serialising a tree; you need the parent before the children
In-orderleft, node, rightOn a BST this emits the values in sorted order — chapter 11
Post-orderleft, right, nodeAnything computed bottom-up: height, size, deletion, evaluating an expression tree
Level-orderby depth, left to rightShortest path in an unweighted tree; anything grouped by level; printing a tree
Choosing the order is usually the whole problem

"Delete a tree" must be post-order — free the children before the parent, or you lose the pointers to them. "Compute each node's height" must be post-order, because a node's answer depends on its children's. "Print a directory listing" wants pre-order. "Find the shallowest leaf" wants level-order, which can stop early. Getting these right is mostly a matter of asking: does this node need its children's answers, or do the children need something from it?

Computing up the tree

Most tree algorithms are one post-order traversal where each node combines what its children returned. Once you see that shape, a long list of problems becomes the same problem with a different combine step.

Values returning up the tree
Each node waits for its children, then combines
python — the same shape, five times
def height(node):
    if not node: return -1                 # empty = −1 so a leaf comes out 0
    return 1 + max(height(node.left), height(node.right))

def size(node):
    if not node: return 0
    return 1 + size(node.left) + size(node.right)

def total(node):
    if not node: return 0
    return node.val + total(node.left) + total(node.right)

def is_balanced(node):                    # returns height, or −2 to signal failure
    if not node: return -1
    l, r = is_balanced(node.left), is_balanced(node.right)
    if l == -2 or r == -2 or abs(l - r) > 1:
        return -2                          # O(n): one pass, not height() at every node
    return 1 + max(l, r)

def diameter(root):                       # longest path between any two nodes
    best = 0
    def go(node):
        nonlocal best
        if not node: return -1
        l, r = go(node.left), go(node.right)
        best = max(best, l + r + 2)         # the path THROUGH this node
        return 1 + max(l, r)               # the height returned UPWARD
    go(root)
    return best
    # note the two different quantities: one tracked globally, one returned
The accidental quadratic

A common way to check balance is: at every node, call height(left) and height(right) and compare. That is O(n) work at each of n nodes — O(n²), or O(n log n) if balanced. The fix is to return the height and the verdict from a single traversal, as above. The general principle: if a recursive function calls another recursive function on the same subtree, you are probably recomputing something. Return a tuple instead.

Passing down versus returning up

Two directions of information flow, and most confusion about tree recursion is confusing them. Information that flows down — the depth so far, the running path, the allowed value range — travels as an extra parameter. Information that flows up — height, size, whether a target was found — travels as a return value. Some problems need both, like validating a BST: the permitted range comes down, the verdict goes up. When a tree problem feels stuck, ask which direction the missing information is travelling.

Self-check

  1. Pre-, in- and post-order differ only in one respect. Which?
    When the node is visited relative to its recursive calls — before both, between them, or after both. The traversal path through the tree is identical in all three cases; each node is passed three times, and the order determines which pass counts as the visit. Seeing this collapses three things to memorise into one, and the demo shows the same walk with the visit moved.
  2. Why must deleting a tree use post-order?
    Because you need the parent's pointers to reach the children. Free the parent first and the children become unreachable — a memory leak in a manually managed language, and in a garbage-collected one simply the wrong order to do any cleanup that must cascade. Post-order guarantees both subtrees are finished before the node itself is touched.
  3. Why does in-order traversal of a BST produce sorted output?
    Because the BST property says everything in the left subtree is smaller than the node and everything in the right subtree is larger. In-order visits left, then node, then right — so by induction it emits all smaller values, then the node, then all larger values, at every level. This is also the cheapest way to check whether a tree is a valid BST: traverse in order and verify the sequence increases.
  4. Checking balance by calling height() at every node is O(n²). What is the fix?
    Return both pieces of information from one traversal. Have the recursive function return the height, and use a sentinel value — or a tuple — to signal that some subtree was already unbalanced. Each node is then visited once, making it O(n). The general symptom: a recursive function calling another recursive function on the same subtree usually means recomputation, and the cure is returning a tuple.
  5. A tree of a billion nodes. How deep is it?
    About 30 levels if it is balanced, since 2³⁰ is just over a billion — so any root-to-leaf operation is 30 steps and recursion depth is trivial. If it is degenerate, it is a billion levels deep, every operation is O(n), and any recursive traversal overflows the stack. Same node count, same code, completely different behaviour, which is why chapter 12 spends its length on keeping trees balanced.
  6. Which traversal finds the shallowest leaf fastest?
    Level-order. It examines nodes in increasing order of depth, so the first leaf it encounters is the shallowest and it can stop immediately — potentially after examining very few nodes. Any depth-first order might descend the deepest branch first and must explore the whole tree before it can be sure. The same reasoning makes BFS the right choice for shortest paths in unweighted graphs, in chapter 14.
