Complexity analysis

How to say what an algorithm costs, in a way that does not depend on your laptop. This chapter is short on mathematics and long on the reasoning you will use every time you read code: what grows, how fast, and whether that is going to matter.

Counting operations, not seconds

Seconds are useless for comparing algorithms — they depend on the machine, the language, the compiler, what else is running and how warm the cache is. So we count operations as a function of input size, and we ask how that count grows.

python
def total(nums):          # n = len(nums)
    s = 0                  # 1 operation
    for x in nums:          # n iterations…
        s += x              # …each doing 1 operation
    return s               # 1 operation
                            # total ≈ n + 2  →  O(n)

def pairs(nums):
    out = []
    for i in range(len(nums)):        # n iterations…
        for j in range(i+1, len(nums)):  # …each doing up to n more
            out.append((nums[i], nums[j]))
    return out             # n(n−1)/2 = ½n² − ½n  →  O(n²)

def halve(n):
    steps = 0
    while n > 1:            # n halves each time: n → n/2 → n/4 → …
        n //= 2
        steps += 1
    return steps           # log₂n iterations  →  O(log n)

Why constants and lower terms are dropped

The second function does exactly \(\tfrac{1}{2}n^2 - \tfrac{1}{2}n\) operations, and we call it O(n²). Two simplifications happen there, and both are justified:

Lower-order terms vanish
At n = 1,000 the n² term is 500,000 and the n term is 500 — a tenth of a percent. At n = 1,000,000 it is a ten-thousandth of a percent. The largest term wins, and it wins by more as n grows.
Constants are machine-dependent
Whether each iteration takes 3 or 30 nanoseconds depends on the language and hardware, not the algorithm. A constant factor of 10 is a faster computer; a factor of n is a better algorithm, and no computer closes that gap.
Which does not mean constants are irrelevant

O(n) with a constant of 500 loses to O(n²) with a constant of 1 until n reaches 500. Real sort implementations switch to insertion sort below about 50 elements for exactly this reason. Big-O answers "how does this scale?" — a different question from "which is faster on my data?", and you need both.

Beyond some input size, f never exceeds g scaled by a constant. The "for large enough n" is what licenses ignoring small-input behaviour, and the constant is what licenses ignoring machine speed.

The two mistakes everyone makes

1. Confusing O with worst case. These are unrelated ideas. Big-O bounds a function; best, average and worst case describe which input you are analysing. You can state a big-O bound on the best case perfectly well. Insertion sort is O(n) in the best case, O(n²) in the worst — both are big-O statements.

2. Using a loose bound. Binary search is technically O(n²) — the definition is satisfied, since it grows no faster than that. It is a true statement and a useless one. Say the tightest bound you can, which is why Θ is what people usually mean even when they write O.

A rule of thumb for feasibility

Competitive programming assumes roughly 10⁸ simple operations per second as a safe budget. That gives usable ceilings: n ≤ 10 tolerates O(n!) · n ≤ 25 tolerates O(2ⁿ) · n ≤ 500 tolerates O(n³) · n ≤ 5,000 tolerates O(n²) · n ≤ 10⁶ needs O(n log n) · n ≤ 10⁸ needs O(n) or better. Reading the input size in a problem statement therefore tells you which complexity you must reach — which is often the strongest hint available about the intended solution.

The hidden-cost checklist
  • list.insert(0, x) and list.pop(0) are O(n) — everything shifts. Use a deque.
  • x in some_list is O(n). Inside a loop over n items, that is a quadratic algorithm hiding in one innocuous line.
  • String concatenation in a loop is O(n²) in most languages, because strings are immutable.
  • Slicing copies: arr[1:] is O(n), so a recursive function that slices each call is doing far more work than the recursion suggests.
  • sorted() inside a loop is O(n² log n). Sort once, outside.

The pattern behind the fourth line is worth internalising because it recurs everywhere: if you split the problem in half each time, there are log n levels; if each level does O(n) total work, the answer is O(n log n). Mergesort, quicksort, and most divide-and-conquer algorithms are that sentence.

Amortised analysis

Some operations are usually cheap and occasionally expensive. Quoting the worst case for every call would be misleading, so instead we ask what a sequence of operations costs on average — which is a different thing from average-case analysis, because it involves no probability at all.

The accounting argument

Charge every cheap append three units instead of one: one for the write, and two saved. When a resize happens, the saved units from the previous half of the array exactly pay for copying all n elements. Nothing is ever short, so the total cost of n appends is at most 3n — which is O(n) for the sequence, and therefore O(1) each. The trick is that doubling makes resizes exponentially rarer as the array grows, so the expensive events are always spread over exponentially more cheap ones.

Space complexity

The same analysis applied to memory. Usually we mean auxiliary space — extra memory beyond the input itself — because the input has to exist regardless.

python
def total(nums):
    s = 0
    for x in nums: s += x
    return s                       # O(1) auxiliary — one accumulator

def doubled(nums):
    return [x * 2 for x in nums]      # O(n) — a whole new list

def countdown(n):
    if n == 0: return
    countdown(n - 1)              # O(n) — n stack frames alive at once ⚠

def binary_search_rec(a, lo, hi, t):
    ...                             # O(log n) space — the recursion depth
                                    # the iterative version is O(1)
Recursion is not free

Every pending call holds a stack frame with its local variables and return address. A recursion depth of n means O(n) memory even if the function allocates nothing itself — and Python raises RecursionError at about 1,000 frames by default. Depth is what matters, not the total number of calls: a balanced tree traversal makes n calls but is only O(log n) deep, whereas a degenerate one is O(n) deep and will overflow.

What the notation hides

Constant factors
Two O(n log n) sorts can differ by 5× in practice. Big-O deliberately cannot see this.
Memory locality
A linear scan of an array can be 10× faster than the same number of operations chasing pointers, because the cache prefetches contiguous memory. Chapter 3 covers why this makes arrays beat linked lists far more often than the complexity table suggests.
The size of n
Asymptotic statements are about large n. If n is 12, the analysis is irrelevant and you should choose whatever is clearest.
Which operation is being counted
"O(n) comparisons" and "O(n) swaps" are different claims. When comparisons are expensive — sorting long strings, say — count those specifically.

Self-check

  1. What is the complexity of this, and what is the trap?
    python
    def has_common(a, b):
    for x in a:
        if x in b:
            return True
    return False
    O(n·m) if b is a list, because x in b is a linear scan — the loop hides a second loop. If b is a set it is O(n), since membership is O(1). One line of setup, b = set(b), changes the complexity class, and nothing in the syntax of the loop tells you which version you are looking at. This is the single most common accidental quadratic in real code.
  2. Why is O(n²) with a small constant sometimes better than O(n log n)?
    Because asymptotic notation discards the constant, and for small n the constant dominates. Insertion sort does very little work per element and accesses memory sequentially, so it beats mergesort below roughly 50 elements — which is why production sorts such as Timsort and introsort switch to it for small subarrays. The crossover point is where the classes actually change places, and it is not always small.
  3. Explain amortised O(1) for array append without using the word "average".
    Any sequence of n appends costs at most c·n operations in total, so the cost per operation across the sequence is bounded by a constant. Individual appends can cost O(n) when a resize copies everything, but because capacity doubles, resizes happen at 1, 2, 4, 8… and the copies sum to 2n across the whole sequence. It is a guarantee about the total, not a probabilistic statement — which is what distinguishes amortised from average-case analysis.
  4. A recursive function makes 2ⁿ calls but is only n deep. What is its space complexity?
    O(n) auxiliary, from the call stack. Only the frames on the current path from the root to the active call exist simultaneously; completed branches have already returned and released their frames. Time is O(2ⁿ), space is O(n). Depth, not call count, determines stack usage — the distinction matters for every tree and backtracking algorithm in this unit.
  5. Is it correct to say quicksort is O(n²)?
    Yes, and it is misleading without qualification. Its worst case is Θ(n²), so O(n²) is a true upper bound; its average case is Θ(n log n), which is what determines its behaviour in practice, especially with a randomised pivot. The precise statement names the case: worst Θ(n²), average Θ(n log n). Stating a bound without saying which case you mean is where most confusion in this area comes from.
  6. A problem gives n ≤ 10⁵ and a one-second limit. What complexities are viable?
    O(n), O(n log n) and O(n√n) are comfortable — around 10⁵ to 10⁷ operations. O(n²) is 10¹⁰ and far too slow. The input bound is effectively telling you the intended solution is roughly linearithmic, which usually means sorting, a hash-based pass, a heap, or a single traversal of a graph. Reading n before thinking about the algorithm is a genuinely useful habit.
