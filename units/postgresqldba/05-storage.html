Chapter 05 · Storage and access

Physical storage

Everything is 8 KB pages. Knowing what fits in one, what happens when a value does not, and when an update can stay inside one explains a surprising amount of performance behaviour — including why some tables bloat far faster than others.

pages toast fillfactor hot updates

The page

8192 bytes, laid out from both ends
┌─────────────────────────────────────────────┐  offset 0
│ PageHeader (24 bytes)                       │  LSN, checksum, free space
├─────────────────────────────────────────────┤  pointers
│ ItemId array →→→→→                          │  4 bytes each, one per tuple
│                                             │
│              free space                     │  ← this is what fillfactor
│                                             │     reserves
│                          ←←←←← Tuples       │  grow backwards from the end
│ tuple 3 │ tuple 2 │ tuple 1                 │
└─────────────────────────────────────────────┘  offset 8191

-- Pointers grow forward from the header; tuple data grows backward from the
-- end. They meet in the middle, and the gap is the page's free space.
--
-- The ItemId indirection is why a tuple can move within its page without
-- invalidating anything: a ctid of (4, 2) means page 4, item 2, and item 2
-- points at wherever the tuple currently sits. That is what makes in-page
-- compaction possible during vacuum.

CREATE EXTENSION pageinspect;
SELECT * FROM page_header(get_raw_page('orders', 0));
SELECT lp, lp_off, lp_len, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('orders', 0));
A tuple cannot span pages

The largest tuple that fits in an 8 KB page is roughly 8 KB minus the header, and Postgres will not split one across pages. That constraint is the entire reason TOAST exists, and it is also why a row with many wide columns can fail to insert with "row is too big" even though each individual value looks reasonable. The per-tuple overhead is about 23 bytes of header plus alignment padding, which matters when rows are small — a table of two integers is mostly header.

Column order affects table size

alignment padding, and the free win
-- Fixed-width types must start at an aligned offset, so Postgres inserts
-- padding bytes. Declaration order therefore changes the size on disk.

CREATE TABLE bad (              -- 24 bytes of data per row
    a boolean,                  --  1 byte  + 7 padding
    b bigint,                   --  8 bytes
    c boolean,                  --  1 byte  + 3 padding
    d integer                   --  4 bytes
);                              -- 24 bytes

CREATE TABLE good (             -- 16 bytes for the same data
    b bigint,                   --  8 bytes
    d integer,                  --  4 bytes
    a boolean,                  --  1 byte
    c boolean                   --  1 byte  + 2 padding at the end
);                              -- 16 bytes

-- One third smaller, for free. The rule: declare widest fixed-width first
-- (bigint, timestamptz, double), then narrower (integer, date), then
-- single-byte (boolean, char), then all variable-length (text, jsonb, numeric).
--
-- On a hundred-million-row table this is gigabytes and a materially better
-- cache hit ratio. On a small table it does not matter at all — so apply it
-- to your largest tables and ignore it elsewhere.

-- What it costs you now:
SELECT pg_column_size(ROW(true, 1::bigint, true, 1::integer));

TOAST

The Oversized-Attribute Storage Technique. When a row will not fit in a page, Postgres compresses wide values and, if still too large, moves them to a side table in chunks.

what happens to a large value
-- The sequence, when a row exceeds ~2 KB (TOAST_TUPLE_THRESHOLD):
--   1. compress the widest eligible column
--   2. if the row still does not fit, move that column out of line into the
--      TOAST table, leaving an 18-byte pointer in its place
--   3. repeat with the next widest until the row fits

-- Every table with a toastable column gets a hidden companion:
SELECT c.relname, t.relname AS toast_table,
       pg_size_pretty(pg_relation_size(c.oid))  AS main,
       pg_size_pretty(pg_relation_size(t.oid))  AS toast
FROM pg_class c JOIN pg_class t ON t.oid = c.reltoastrelid
WHERE c.relname = 'documents';

-- Per-column storage strategy:
ALTER TABLE documents ALTER COLUMN body SET STORAGE EXTERNAL;
--   PLAIN     never compressed or moved (only for non-toastable types)
--   EXTENDED  compress, then move out of line   (default for text, jsonb)
--   EXTERNAL  move out of line, do NOT compress
--   MAIN      compress, avoid moving out if possible

-- EXTERNAL is worth knowing: it makes substring() and jsonb field access on
-- large values much faster, because those can read a slice of an uncompressed
-- out-of-line value without decompressing the whole thing. The cost is disk.
TOAST is why a "small" table can be enormous

pg_relation_size reports only the main table and excludes TOAST, so a table showing 40 MB can occupy 12 GB once its TOAST table is counted. Always use pg_total_relation_size, which includes TOAST and indexes. Related: a SELECT * on a table with a large jsonb column pays to fetch and decompress every TOASTed value, even for columns you never read — which is one of the more expensive versions of the SQL unit's argument against SELECT *.

HOT updates

Heap-only tuple updates Whether an update can stay inside its page decides how much work it really does. Two conditions, and both are under your control.
—HOT possible?
—writes per update
—WAL per second
—index entries / sec
the two conditions, and why it matters so much
-- An update is HOT — heap-only tuple — when BOTH hold:
--   1. no INDEXED column changed
--   2. the new tuple fits on the SAME PAGE as the old one
--
-- When it is HOT:
--   * the old tuple gets a pointer to the new one, forming a HOT chain
--   * NO index entries are written — indexes still point at the old ctid and
--     the chain is followed to reach the current version
--   * dead tuples in the chain can be cleaned up by a cheap "page prune"
--     during any read, without waiting for vacuum
--
-- When it is not:
--   * every index on the table gains an entry
--   * cleanup requires a full vacuum pass over the table AND every index
--
-- On a table with six indexes, that is the difference between one write and
-- seven, and between cheap opportunistic cleanup and an expensive vacuum.

-- Measure it:
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 10000
ORDER BY n_tup_upd DESC;

-- hot_pct below ~50% on an update-heavy table is worth investigating. The
-- usual causes are an index on a frequently-changing column, or fillfactor
-- 100 leaving no room on the page for the new version.
Two changes that raise the HOT rate

Drop the index on the column you keep updating. An index on updated_at or last_seen_at on a hot table is unusually expensive — it disqualifies every update from HOT, on a column whose value changes constantly. Check whether anything actually queries by it. Lower fillfactor on update-heavy tables to 70–90, so each page keeps room for new versions. It costs disk and reduces how many rows fit per page for scans; on a queue or session table it is nearly always worth it. Both are one line, and together they routinely take a table from 20% HOT to 90%.

fillfactor
-- The percentage of a page that INSERTs may fill. The rest is reserved for
-- future updates to rows already on that page.
ALTER TABLE sessions SET (fillfactor = 80);
VACUUM FULL sessions;    -- or pg_repack; existing pages are not rewritten
                         -- by the ALTER alone

-- Guidance:
--   100  the default. Right for append-only and read-mostly tables
--   90   mild update traffic
--   70-85 heavily updated tables: queues, sessions, counters, state machines
--   below 70 rarely pays — you are trading a lot of scan efficiency
--
-- Index fillfactor exists too and defaults to 90 for B-trees. Leave it unless
-- you have a specific reason; the default already accounts for page splits.

The free space map is why deleted space is reused, not returned

Chapter 3's point, from the storage side. Vacuum records reclaimed space in the FSM, so the next insert finds a page with room and fills the gap. The file never shrinks — which is correct for a table with ongoing inserts, and unhelpful after a one-off deletion of 90% of the rows. That is the case where VACUUM FULL or pg_repack earns its lock. Note also that the FSM is only updated by vacuum, so a table where autovacuum is starved will keep extending the file even though free space exists inside it.

Measuring what a table costs

the size query worth saving
SELECT
    c.relname,
    pg_size_pretty(pg_total_relation_size(c.oid))                   AS total,
    pg_size_pretty(pg_relation_size(c.oid))                         AS heap,
    pg_size_pretty(pg_indexes_size(c.oid))                          AS indexes,
    pg_size_pretty(coalesce(pg_total_relation_size(c.reltoastrelid), 0)) AS toast,
    round(100.0 * pg_indexes_size(c.oid) /
          nullif(pg_total_relation_size(c.oid), 0), 1)              AS pct_indexes,
    c.reltuples::bigint                                             AS est_rows,
    pg_size_pretty((pg_relation_size(c.oid) /
                    nullif(c.reltuples, 0))::bigint)                AS bytes_per_row
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname = 'public'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;

-- What the columns tell you:
--   pct_indexes above ~50%   more index than data. Audit them (SQL ch 12)
--   toast much larger than heap   wide values dominate; check SELECT * usage
--   bytes_per_row far above the sum of column widths   bloat, or padding

Checksums and corruption

turn them on, and know how to check
SHOW data_checksums;         -- on / off

-- Checksums detect silent corruption from failing storage — a bit flip that
-- would otherwise be read back as plausible data and propagate into backups
-- and replicas before anyone notices.
--
-- They cost a few percent of CPU and they are OFF by default when a cluster is
-- created with initdb without --data-checksums. Most managed services enable
-- them; many self-managed clusters do not, because nobody chose either way.
--
-- Enabling on an existing cluster requires downtime:
--   pg_checksums --enable -D $PGDATA        (cluster must be stopped)
--
-- Verify an offline cluster or a restored backup:
--   pg_checksums --check -D $PGDATA
--
-- Corruption in the log looks like:
--   WARNING:  page verification failed, calculated checksum 21023 but expected 15118
--   ERROR:  invalid page in block 8213 of relation base/16384/16401
-- Do not "fix" this by setting ignore_checksum_failure. Take a copy, work out
-- which relation and which rows, and restore from backup.
Check whether checksums are on before you need them

Without them, a failing disk corrupts a page, Postgres reads it back happily, and the bad data flows into your replicas and your backups. By the time a query returns something impossible, every copy you have is contaminated and you cannot tell when it started. With them, the read fails loudly at the moment of corruption and your backups from before that point are known good. It is one flag at cluster creation and a painful migration afterwards — so check SHOW data_checksums on every cluster you own, today.

The short version

  1. Everything is 8 KB pages, with pointers growing forward and tuples backward. A tuple cannot span pages.
  2. Column order changes table size through alignment padding — widest fixed-width first. Free, and worth doing on large tables.
  3. TOAST compresses and relocates wide values. Use pg_total_relation_size, or you will not see it.
  4. A HOT update writes no index entries — but only if no indexed column changed and the new tuple fits on the same page.
  5. An index on a constantly-updated column disqualifies every update from HOT. Check whether anything queries by it.
  6. Lower fillfactor to 70–90 on update-heavy tables so there is room on the page for new versions.
  7. Track n_tup_hot_upd as a percentage. Below 50% on a hot table is worth investigating.
  8. Check data_checksums today. Without them, corruption propagates silently into replicas and backups.
