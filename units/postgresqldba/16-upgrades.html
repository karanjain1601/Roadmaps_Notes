Upgrades

Minor upgrades are a package update and a restart. Major upgrades are a project — and the cost of putting one off is that the next one is worse, until you are running an unsupported version and the decision has been made for you.

minor pg_upgrade logical extensions

Minor upgrades

16.2 to 16.6 — do these promptly
# The on-disk format never changes within a major version, so a minor upgrade
# is: install the new binaries, restart. Typically under a minute of downtime.

apt-get install --only-upgrade postgresql-16
systemctl restart postgresql@16-main

# On a replicated cluster, upgrade standbys first, then switch over, then
# upgrade the old primary. Downtime is one planned switchover (chapter 14):
patronictl switchover --leader node1 --candidate node2

# Minor releases are bug and security fixes only — no new features, no
# behaviour changes. The project ships them quarterly and they routinely
# include data-corruption fixes.
#
# Read the release notes anyway. Occasionally a fix requires action, such as
# reindexing indexes built by a version with a known bug. That instruction
# appears in the notes and nowhere else, and skipping it leaves you with
# indexes that silently return wrong results.

SELECT version();
SHOW server_version_num;    -- 160006
Never skip minor releases

The changelog for a typical minor version includes fixes for crashes, wrong query results and index corruption. Running six months behind means running with known, published, exploitable-or-corrupting bugs that someone has already written a patch for. The upgrade is a restart and it is compatible in both directions. Apply them within a few weeks, and automate it if you can — the risk of applying them is far lower than the risk of not.

pg_upgrade

the standard route
# 1. Install the new major version alongside the old. Both must be present.
apt-get install postgresql-17

# 2. CHECK MODE. Runs against the live cluster, changes nothing, and reports
#    every problem — missing extensions above all. Run this weeks ahead.
/usr/lib/postgresql/17/bin/pg_upgrade \
    --old-datadir=/var/lib/postgresql/16/main \
    --new-datadir=/var/lib/postgresql/17/main \
    --old-bindir=/usr/lib/postgresql/16/bin \
    --new-bindir=/usr/lib/postgresql/17/bin \
    --check

# 3. Stop both clusters. This is where downtime begins.
systemctl stop postgresql@16-main postgresql@17-main

# 4. Run it. --link uses hard links instead of copying, so the time depends on
#    the number of relations rather than the volume of data.
/usr/lib/postgresql/17/bin/pg_upgrade … --link --jobs=8

# 5. Start the new cluster, then IMMEDIATELY rebuild statistics. pg_upgrade
#    does not carry them across, so the planner starts blind — this is the
#    classic "the upgrade made everything slow" incident.
systemctl start postgresql@17-main
vacuumdb --all --analyze-in-stages --jobs=8

# --analyze-in-stages runs three passes of increasing accuracy, so you get
# rough statistics in seconds rather than waiting for a full analyse.

# 6. Once satisfied:
./delete_old_cluster.sh
--link means you cannot start the old cluster again

Hard links make the upgrade fast — minutes rather than hours, because no data is copied — and the two clusters now share the same files on disk. The moment the new cluster writes anything, the old data directory is corrupt from the old version's point of view. There is no rollback after startup. Your fallback becomes a restore from backup, so take one immediately before, verify it, and know how long the restore takes (chapter 12). If you cannot accept that, use copy mode or logical replication instead — both keep the old cluster intact and startable.

The logical replication route

near-zero downtime, at the cost of complexity
-- Because logical replication decodes WAL into row changes (chapter 13), the
-- subscriber can be a DIFFERENT major version. That is what makes this work.

-- 1. Build a new cluster on the new version. Copy the schema across.
pg_dump --schema-only -d orders | psql -h newhost -d orders

-- 2. Publish and subscribe. copy_data does the initial sync.
--    On the old primary (needs wal_level = logical — a RESTART, so check
--    this before you need it):
CREATE PUBLICATION upgrade_pub FOR ALL TABLES;

--    On the new cluster:
CREATE SUBSCRIPTION upgrade_sub
    CONNECTION 'host=old dbname=orders user=replicator password=…'
    PUBLICATION upgrade_pub WITH (copy_data = true, streaming = on);

-- 3. Wait for the initial copy, then for lag to reach near zero.
SELECT * FROM pg_stat_subscription;

-- 4. THE CUTOVER. This is the only downtime, and it is seconds:
--      a. stop writes to the old cluster
--      b. confirm the subscriber has caught up completely
--      c. advance every sequence — logical replication does NOT copy them
--      d. point the application at the new cluster
--      e. drop the subscription

-- Step (c) is the one that gets forgotten, and the symptom is duplicate-key
-- errors on the new cluster from the first insert onward:
SELECT 'SELECT setval(' || quote_literal(seq) || ', ' || last_value || ');'
FROM (SELECT sequencename AS seq,
             pg_sequence_last_value(sequencename::regclass) AS last_value
      FROM pg_sequences WHERE schemaname = 'public') s;
-- Run that output on the new cluster, with a safety margin added.

Practise the cutover, then practise rolling back

The logical route's real advantage is not the low downtime — it is that the old cluster is untouched and still running. If something is wrong ten minutes after cutover, you point the application back. Make that genuinely available by setting up reverse replication before you switch: publish from the new cluster, subscribe on the old, so writes that land on the new one flow back. Then rolling back is a configuration change rather than a data-loss event. This is what turns a major upgrade from a one-way door into a reversible decision.

the collation problem, which is worse than it sounds
-- Text indexes are ordered according to the operating system's collation
-- rules. If glibc changes those rules — which happened significantly in
-- glibc 2.28, shipping in RHEL 8, Debian 10 and Ubuntu 18.10 — then existing
-- B-tree indexes on text are ordered by rules the server no longer uses.
--
-- The symptoms are appalling: queries silently miss rows that exist, unique
-- constraints stop detecting duplicates, and nothing errors.

SELECT datname, datcollate, datctype, datcollversion FROM pg_database;
SELECT collname, collversion, pg_collation_actual_version(oid)
FROM pg_collation WHERE collprovider <> 'c';
-- A mismatch between collversion and the actual version is the warning.

-- If the OS collation changed, REINDEX every text index:
REINDEX DATABASE CONCURRENTLY orders;      -- PG12+
ALTER DATABASE orders REFRESH COLLATION VERSION;

-- Avoiding it in future, in order of preference:
--   1. ICU collations (PG15+ can use ICU as the default provider). ICU
--      versions its collations explicitly, so a change is detectable
--   2. C collation for columns that only need byte ordering — identifiers,
--      codes, hashes. Faster too, and it never changes
--
-- This is not strictly an upgrade issue: it bites whenever the OS changes,
-- including a base image bump. But a major upgrade is usually when the OS
-- changes, which is why it belongs here.

The upgrade is not finished when the server starts

Two things routinely make a technically successful upgrade look like a disaster. Statistics are gone, so until you analyse, every plan is built for a table the planner believes is empty — run vacuumdb --analyze-in-stages as the very next command, not as a follow-up task. And plans change: a new version's planner is generally better and occasionally worse for a specific query. Having the pre-upgrade pg_stat_statements snapshot is what lets you identify a regression in minutes rather than argue about whether things feel slower.

Keeping current

PracticeWhy
Upgrade one major version a yearEach release is supported for five years. Upgrading annually means never being close to the edge
Do not wait for a compelling featureThe reason to upgrade is that skipping accumulates risk, not that 17 has a nice feature
Run --check quarterlyFree, safe, and it tells you which extension is about to become a problem
Treat extension choice as an upgrade decisionChapter 10 — an extension that lags releases pins your cluster
Rehearse against production dataThe only way to know the duration and to find the surprises
Track the end-of-life dateAn unsupported version stops receiving security fixes, and then the upgrade is an emergency
Falling behind is the actual risk

Every skipped year makes the next upgrade harder: more extension churn, more collation drift, a bigger jump in planner behaviour, more accumulated schema that nobody understands, and less institutional memory of how the last one went. Teams that upgrade annually find it routine. Teams that have not upgraded in four years find it a quarter-long project with real risk — and they are usually forced into it by an end-of-life date rather than choosing the timing. The best upgrade strategy is doing them regularly enough that each one is boring.

The short version

  1. Minor upgrades are a restart. Never skip them — they contain crash, wrong-result and corruption fixes.
  2. Read the minor release notes anyway; occasionally one requires a reindex, and that instruction appears nowhere else.
  3. pg_upgrade --check is safe on a live cluster. Run it weeks ahead and quarterly thereafter.
  4. --link is fast and one-way. After the new cluster starts, your rollback is a restore from backup.
  5. Logical replication gives near-zero downtime and a real rollback — set up reverse replication before cutover.
  6. Advance the sequences at cutover. Logical replication does not copy them, and the symptom is duplicate keys immediately.
  7. Collation changes silently corrupt text indexes. Check datcollversion, and prefer ICU or C where you can.
  8. Statistics do not survive. vacuumdb --analyze-in-stages is the next command after starting the new cluster.
