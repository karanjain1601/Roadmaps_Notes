Chapter 08 · Configuring

Memory and resource configuration

There are about fifteen settings worth changing from their defaults, and roughly two hundred that are not. This chapter is the fifteen, with the reasoning attached — because a number you cannot justify is a number you cannot adjust when the workload changes.

shared_buffers work_mem timeouts defaults

Why the defaults are what they are

PostgreSQL ships with settings that will start on almost any machine, including a small container or an old laptop. They are startup-safe, not sensible, and a freshly installed cluster on a 128 GB server is using 128 MB of shared buffers and assuming 4 GB of cache exists. Every managed service overrides them; a self-managed cluster frequently does not, because nobody chose either way.

shared_buffers

25%, and when it is wrong
shared_buffers = '8GB'      -- 25% of 32GB. Requires a restart.

-- Why not more? Postgres reads through the OS page cache as well, so a hot
-- page is often cached twice. Beyond about 25-40% you are mostly buying
-- duplication, and you make checkpoints write more dirty pages at once.
--
-- Reasons to go HIGHER (40%+):
--   * write-heavy workload — keeping pages dirty in shared_buffers longer
--     means fewer writes overall, because repeated modifications coalesce
--   * a dedicated machine where nothing else wants the memory
--   * the working set is just above 25% and just below 40%
--
-- Reasons to go LOWER:
--   * the application runs on the same box
--   * many connections each needing work_mem
--   * a small container where the OS cache matters proportionally more

-- Is it big enough? Measure the hit ratio rather than guessing:
SELECT sum(heap_blks_hit) AS hits, sum(heap_blks_read) AS reads,
       round(100.0 * sum(heap_blks_hit) /
             nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0), 2) AS hit_pct
FROM pg_statio_user_tables;
-- Above 99% on an OLTP system is normal. Sustained below ~95% means the
-- working set does not fit — though note "read" counts include pages served
-- from the OS cache, so this understates the true hit rate.

CREATE EXTENSION pg_buffercache;   -- what is actually IN the cache right now
Huge pages are the free win nobody enables

With 8 GB of shared buffers and 4 KB pages, the kernel manages two million page-table entries per backend. Huge pages (2 MB each) cut that by a factor of 512, reducing TLB misses and page-table memory measurably — typically a few percent of throughput on a large instance, for no downside. Set huge_pages = try and configure vm.nr_hugepages in the kernel to cover shared_buffers plus a margin. Use try rather than on so the server still starts if the reservation fails, and check SHOW huge_pages_status afterwards to confirm it actually got them.

work_mem

the setting that is per node, not per query
-- Chapter 1 and chapter 7 both flagged this; here is the sizing.
-- Worst case ≈ max_connections × nodes_per_query × parallel_workers × work_mem

work_mem = '16MB'                 -- modest global default
maintenance_work_mem = '2GB'      -- vacuum, CREATE INDEX, ALTER TABLE
autovacuum_work_mem = '1GB'       -- separate, so autovacuum workers do not
                                  -- each grab maintenance_work_mem

-- Per role is nearly always better than one global compromise:
ALTER ROLE reporting SET work_mem = '512MB';
ALTER ROLE app       SET work_mem = '8MB';

-- Or per transaction, for a specific known-heavy statement:
BEGIN; SET LOCAL work_mem = '1GB'; SELECT … ; COMMIT;

-- Is it big enough? Sorts that spill to disk are the symptom:
SELECT temp_files, pg_size_pretty(temp_bytes) AS temp
FROM pg_stat_database WHERE datname = current_database();

-- And find WHICH queries, so you can raise it for those rather than globally:
--   log_temp_files = '10MB'   -- log any temp file over this size
-- Then look for "temporary file: path ... size ..." in the log.
A hash join spilling is worse than a sort spilling

When a sort exceeds work_mem it switches to an external merge, which is slower but degrades gracefully. When a hash join exceeds it, Postgres splits into batches and may have to re-read both inputs several times — a much sharper cliff. So if EXPLAIN ANALYZE shows Batches: 17 on a Hash node, that one query is worth a session-level work_mem increase far more than a sort showing external merge Disk: 40MB. Look at the batch count first.

Timeouts

the four that prevent incidents
-- 1. Stop one runaway query taking the system with it. Set per role, not
--    globally — a nightly report legitimately runs for an hour.
ALTER ROLE app SET statement_timeout = '30s';
ALTER ROLE reporting SET statement_timeout = '30min';

-- 2. THE MOST IMPORTANT ONE. Kill sessions that opened a transaction and
--    went away — a crashed worker, an abandoned psql window. These hold
--    locks and block vacuum indefinitely (chapters 2 and 3).
ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';

-- 3. Fail fast on DDL rather than queueing behind a long query and blocking
--    everything after it (SQL chapter 16). Set it in your migration runner.
SET lock_timeout = '3s';

-- 4. Reap connections a pooler or a crashed client left behind (PG14+).
ALTER SYSTEM SET idle_session_timeout = '1h';
-- Careful with this one if clients rely on long-lived idle connections;
-- most poolers handle reconnection fine.

-- Also worth setting, and easy to forget:
ALTER SYSTEM SET tcp_keepalives_idle = 60;   -- detect dead peers, so a
ALTER SYSTEM SET tcp_keepalives_interval = 10; -- network partition does not
ALTER SYSTEM SET tcp_keepalives_count = 6;   -- leave backends hanging forever
Set idle_in_transaction_session_timeout today

If you take one action from this chapter, this is it. A session sitting idle inside a transaction holds its snapshot, which holds back vacuum for every table in the cluster (chapter 2), and holds any locks it acquired. The causes are mundane — a worker that crashed after BEGIN, a developer's terminal, an ORM that opened a transaction and then made a slow HTTP call. Five minutes is generous for almost every legitimate workload, and it converts a class of silent cluster-wide degradation into a clear error in one application.

Disk and the kernel

the settings outside postgresql.conf
# /etc/sysctl.d/30-postgresql.conf

# Do not overcommit. The OOM killer choosing the postmaster takes the whole
# cluster down and forces crash recovery; better to fail an allocation.
vm.overcommit_memory = 2
vm.overcommit_ratio  = 80

# Make the kernel flush dirty pages earlier and in smaller batches, so a
# checkpoint does not collide with a huge accumulated writeback.
vm.dirty_background_bytes = 67108864      # 64 MB
vm.dirty_bytes            = 536870912     # 512 MB

# Do not swap out a database. Reclaim cache instead.
vm.swappiness = 1

# Huge pages: enough to cover shared_buffers, in 2 MB units.
vm.nr_hugepages = 4500                    # ≈ 8.8 GB

# Transparent huge pages: turn them OFF. The defragmentation stalls they
# cause show up as unexplained latency spikes, and they are not the same
# thing as the explicit huge pages above.
#   echo never > /sys/kernel/mm/transparent_hugepage/enabled

# Filesystem: mount with noatime. ext4 or xfs are both fine and both are
# used at scale; the choice matters far less than the mount options.

Logging

what to log, and what to leave off
-- A prefix that makes every line attributable. Without this, log analysis is
-- guesswork, and pgBadger cannot parse timings at all.
log_line_prefix = '%m [%p] %q%u@%d %a %h '
--   %m timestamp  %p pid  %u user  %d database  %a application_name  %h host

log_min_duration_statement = '1s'   -- log slow queries. Start here
log_checkpoints = on                -- PG15+ default; keep it
log_autovacuum_min_duration = '1s'  -- chapter 3
log_lock_waits = on                 -- log anything waiting past deadlock_timeout
log_temp_files = '10MB'             -- work_mem is too small for these queries
log_connections = off               -- noisy behind a pooler
log_disconnections = off

-- Leave OFF unless you are actively debugging:
--   log_statement = 'all'      logs every statement including parameters,
--                              which is a volume problem AND a data-protection
--                              problem — passwords and personal data end up in
--                              a log aggregator with weaker access control
--                              than the database (SQL chapter 15)

-- Set application_name from every service. It costs nothing and it is the
-- difference between "some backend is doing this" and knowing which
-- deployment to roll back.

How to change a setting safely

1 · Measure firstKnow the number you expect to move, and its current value
↓
2 · Change one thingTwo at once and you learn nothing from the result
↓
3 · Prefer the narrowest scopeSession, then role, then database, then cluster
↓
4 · Reload rather than restart where possiblepg_settings.context tells you which is needed
↓
5 · Wait a full cycleA day, including the nightly jobs. Some effects only appear under the weekly peak
↓
6 · Write down whyThe next person needs the reasoning, not the number
Configuration generators are a starting point, not an answer

Tools like PGTune and the demo above produce a reasonable baseline from RAM, cores and a workload label — and they cannot know your working-set size, your query shapes, your connection pattern or your write rate. Use one to escape the defaults, then measure and adjust. The failure mode is treating the generated file as finished: a cluster configured for "OLTP, 32 GB" two years ago is now running a workload nobody re-examined, with a work_mem that made sense at the time.

The short version

  1. The defaults are startup-safe, not sensible. A fresh cluster on a large server is using 128 MB of buffers.
  2. shared_buffers at 25% of RAM, higher for write-heavy, lower if the app shares the box.
  3. work_mem is per node per worker. Keep the global modest and raise it per role.
  4. A hash join spilling to batches is worse than a sort spilling — check the batch count first.
  5. Huge pages are a free few percent that almost nobody enables. Transparent huge pages should be off.
  6. Set idle_in_transaction_session_timeout today. It is the highest-value single change in this chapter.
  7. Set vm.overcommit_memory = 2 so the OOM killer never chooses the postmaster.
  8. Decide max_connections, shared_buffers, wal_level and huge_pages before going live — changing them later needs a restart.
