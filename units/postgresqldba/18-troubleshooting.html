Troubleshooting

Everything so far, arranged by symptom. Twelve failures account for most Postgres incidents, and for each one there is a query that identifies the cause in seconds — provided you have it to hand rather than reconstructing it at 3am.

The first five minutes

four queries, in this order, before forming a theory
-- 1. What is running, longest first.
SELECT pid, now() - query_start AS runtime, state,
       wait_event_type, wait_event, left(query, 90)
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY query_start;

-- 2. Who is blocking whom. THE most useful query in an incident.
SELECT blocked.pid          AS blocked_pid,
       blocked.usename      AS blocked_user,
       left(blocked.query, 60)  AS blocked_query,
       blocking.pid         AS blocking_pid,
       blocking.state       AS blocking_state,
       now() - blocking.xact_start AS blocking_for,
       left(blocking.query, 60) AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- 3. Connections, by state.
SELECT state, count(*), max(now() - state_change) AS longest
FROM pg_stat_activity WHERE backend_type = 'client backend' GROUP BY state;

-- 4. Disk and WAL.
SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();
-- plus df on the data directory

-- Keep these four in a file. Reconstructing pg_blocking_pids from memory at
-- 3am is not a skill worth developing.
Ask whether it is the database at all

Before diagnosing Postgres, check the two things that make it look guilty when it is not. Connection pool saturation — if the pool is full, every request queues and the symptom is total unavailability while the database sits at 10% CPU (chapter 9). A dependency — an application holding transactions open across a slow HTTP call produces long-running transactions, exhausted pools and blocked vacuum, all originating outside the database. Both look exactly like "the database is slow" and neither is fixed by touching the database.

The playbook

Symptom to cause Pick what you are seeing. The query identifies which cause it is; the fix depends on that answer.

Locks

the full picture, when the blocking query is not enough
SELECT l.pid, l.locktype, l.mode, l.granted,
       CASE l.locktype
            WHEN 'relation' THEN l.relation::regclass::text
            WHEN 'transactionid' THEN l.transactionid::text
            ELSE coalesce(l.objid::text, '')
       END AS target,
       now() - a.xact_start AS txn_age,
       a.state, left(a.query, 70)
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE NOT l.granted OR l.mode LIKE '%Exclusive%'
ORDER BY l.granted, a.xact_start;

-- Lock modes, in increasing strength:
--   ACCESS SHARE            SELECT. Conflicts only with ACCESS EXCLUSIVE
--   ROW EXCLUSIVE           INSERT, UPDATE, DELETE
--   SHARE                   CREATE INDEX (blocks writes)
--   SHARE ROW EXCLUSIVE     ADD FOREIGN KEY
--   EXCLUSIVE               REFRESH MATERIALIZED VIEW
--   ACCESS EXCLUSIVE        most ALTER TABLE, DROP, VACUUM FULL.
--                           Blocks EVERYTHING including reads

-- Resolve, least violent first:
SELECT pg_cancel_backend(12345);      -- cancel the query, keep the connection
SELECT pg_terminate_backend(12345);   -- kill the connection entirely
-- Cancel first. Terminate only if cancel does not work, and never blindly —
-- read the query before killing it.
The lock queue is why one slow query stops everything

Lock requests are ordered. A migration requests ACCESS EXCLUSIVE, waits behind one long-running SELECT, and every query that arrives afterwards queues behind the migration — including ordinary reads that would not have conflicted with the SELECT at all. One slow report plus one ALTER TABLE equals a total outage on that table. This is the single most common "the database froze for no reason" cause, and lock_timeout on every DDL statement prevents it entirely (SQL chapter 16).

Recovering from a full disk

the awkward one, because you cannot write
# Postgres has stopped accepting writes. Do NOT delete anything in pg_wal by
# hand — removing unarchived segments breaks recovery and replication both.

# 1. Buy space from outside the data directory.
rm /var/log/postgresql/*.gz            # old logs
#    Or extend the volume, which is usually fastest in cloud.

# 2. Find why WAL is being retained (chapters 4, 12, 13).
psql -c "SELECT slot_name, active, wal_status,
         pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
         FROM pg_replication_slots ORDER BY 4 DESC;"
psql -c "SELECT failed_count, last_failed_time FROM pg_stat_archiver;"

# 3. Fix the cause, then WAL is recycled at the next checkpoint.
psql -c "SELECT pg_drop_replication_slot('dead_standby');"
#    or repair archive_command, then:
psql -c "CHECKPOINT;"

# If it will not start at all, Postgres reserves a small emergency file
# precisely for this. If even that is exhausted, create space and start it in
# single-user mode:
postgres --single -D $PGDATA postgres

# Afterwards, prevent the recurrence:
#   max_slot_wal_keep_size = '100GB'
#   alerts on pg_wal size and pg_stat_archiver.failed_count

↓

↓
pg_cancel_backendCancels the statement, keeps the connection. Almost always sufficient
↓
pg_terminate_backendKills the connection. Uncommitted work rolls back
↓
Never kill -9 a backendThe postmaster restarts the whole cluster to protect shared memory
↓
Then prevent itA per-role statement_timeout is the fix, not vigilance
A rollback can take as long as the work did

Terminating a backend halfway through a large UPDATE does not free things instantly. The transaction must roll back, and on a statement that has modified millions of rows that takes real time — during which the locks are still held and the situation looks unchanged. People terminate again, then start killing processes, and make things considerably worse. Watch pg_stat_activity after terminating; if the backend is still there in state idle with no query, it is rolling back and the correct action is to wait.

Corruption

stop, take a copy, then investigate
-- ERROR: invalid page in block 8213 of relation base/16384/16401
-- WARNING: page verification failed, calculated checksum 21023 but expected 15118

-- 1. STOP. Take a filesystem-level copy of the data directory before doing
--    anything else. Every subsequent action can make recovery harder.

-- 2. Identify what is affected.
SELECT relname FROM pg_class WHERE relfilenode = 16401;

-- 3. Check the extent, with amcheck.
CREATE EXTENSION amcheck;
SELECT bt_index_check(index => c.oid, heapallindexed => true)
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE c.relam = (SELECT oid FROM pg_am WHERE amname = 'btree')
  AND c.relpersistence = 'p';

-- 4. If it is only an INDEX, that is recoverable: REINDEX rebuilds it from
--    the heap. If the HEAP is corrupt, restore from backup.

-- Do NOT reach for ignore_checksum_failure or zero_damaged_pages to make the
-- error go away. They let you read past the damage, silently discarding data,
-- and they turn a contained problem into an unknown one.

-- Causes, in rough order: failing storage, a kernel or filesystem bug, a
-- volatile write cache that lied about fsync, and operator error such as
-- copying a data directory from a running server.
--
-- And note the point from chapter 5: WITHOUT checksums enabled, none of these
-- errors appear at all. The corruption is read back as plausible data and
-- propagates into every replica and every backup before anyone notices.

SymptomActual cause
Total unavailability, low database CPUConnection pool exhausted (chapter 9)

Intermittent timeouts, no slow queriesNetwork, or DNS resolution on connect
Slow every hour on the hourA cron job competing for I/O
Slow for one customer onlyData skew — that tenant has 40× the rows
Latency spikes with no query causeTransparent huge pages, or a noisy neighbour (chapter 8)
Everything slow after a deploy, queries unchangedA new index, a plan change, or a config change
Reads stale or wrongReading from a replica (chapter 13)

Working an incident

  • Write down what you run and what it returned. In the incident channel, as you go — reconstructing it afterwards is guesswork and the post-mortem needs it.
  • Change one thing at a time. Two simultaneous changes and you will not know which helped, or which caused the next problem.
  • Prefer reversible actions. Cancelling a query is reversible; a config change needing a restart is not, mid-incident.
  • Do not restart to "clear things up". It discards the evidence and starts crash recovery, which can take longer than the incident.
  • Take a copy before destructive steps — a snapshot of the volume, or a copy of the data directory.
  • Know when to fail over and when not to. A slow primary usually stays slow after promotion (chapter 14).
  • Capture the state before fixing it. pg_stat_activity, pg_locks, the plan — once resolved, they are gone.
The queries in this chapter belong in a file

Not in your memory, and not in a wiki page nobody can find. A ~/pg-incident.sql checked into the ops repository, with the four opening queries and the twelve diagnostic ones, is worth more during an incident than any amount of remembered detail. Add to it every time you work something out the hard way. That file, and the history from chapter 17, are the two things that turn a two-hour investigation into a ten-minute one.

Where this unit ends

Eighteen chapters from five design decisions. A process per connection, so pooling is mandatory. MVCC by tuple versioning, so readers never block writers and dead rows accumulate. Vacuum as a separate process, so bloat and wraparound are things you operate rather than things that happen. Write-ahead logging, which turns out to provide durability, replication and point-in-time recovery from one mechanism. And extensibility deep enough to add index types, which is why "just use Postgres" is a serious architectural position rather than a slogan.

Almost everything operational in this unit traces back to one of those. The bloat is MVCC. The wraparound alarm is MVCC. The idle-in-transaction timeout matters because one snapshot holds the cleanup horizon for the whole cluster. The disk fills because a replication slot is retaining WAL, and WAL exists because of the write path. The connection pooler exists because a connection is a process. Once the five are internalised, the rest is consequence — which is why the first four chapters are the ones worth rereading.

Three things are worth doing this week, whatever else you take from this. Set idle_in_transaction_session_timeout. Check SHOW data_checksums. And run a restore, end to end, and time it. Each takes under an hour and each addresses a failure that is otherwise silent until it is not.

The short version

  1. Four queries first: what is running, who blocks whom, connections by state, disk. Keep them in a file.
  2. Ask whether it is the database at all. Pool exhaustion and application-held transactions both look exactly like this.
  3. The lock queue is why one slow query plus one ALTER TABLE freezes a table entirely.
  4. Cancel before terminate, never kill -9, and expect a rollback to take as long as the work did.
  5. On a full disk, never delete WAL by hand — find the slot or the failing archive command.
  6. On corruption: copy the data directory first, and do not silence the error to make it go away.
  7. Capture state before fixing it. Once resolved, the evidence is gone.
  8. Set idle_in_transaction_session_timeout, check data_checksums, and time a real restore.
