The planner and statistics

The SQL unit covered reading a plan. This one covers where the numbers in it come from — the cost constants, the statistics behind every row estimate, and the small number of settings that legitimately change the planner's mind rather than overriding it.

cost model statistics extended statistics settings

Cost is a made-up unit

Every plan node gets a cost in arbitrary units, defined relative to one constant: reading a page sequentially costs 1.0. Everything else is calibrated against that, and the planner picks the cheapest total. The units mean nothing on their own; only the ratios matter.

ConstantDefaultMeaningUsually set to
seq_page_cost1.0Read one page sequentiallyLeave at 1.0 — it is the reference
random_page_cost4.0Read one page randomly1.1 on SSD or cloud storage
cpu_tuple_cost0.01Process one rowLeave
cpu_index_tuple_cost0.005Process one index entryLeave
cpu_operator_cost0.0025Evaluate one operator or functionLeave
parallel_setup_cost1000Start a parallel queryLeave
effective_cache_size4GBHow much cache the planner may assume50–75% of RAM
Two settings are wrong on most installations

random_page_cost = 4.0 encodes the seek time of a spinning disk: random reads were genuinely four times a sequential read. On SSD or cloud block storage the real ratio is close to 1, so leaving the default makes the planner systematically pessimistic about index scans and it chooses sequential scans it should not. Set it to 1.1. Meanwhile effective_cache_size defaults to 4 GB regardless of your machine, so on a 128 GB server the planner assumes almost nothing is cached and reaches the same wrong conclusion from a different direction. These two are the highest-value planner changes available and both are one line.

the sequential scan formula, in full
Seq Scan cost = (pages × seq_page_cost)
              + (rows  × cpu_tuple_cost)
              + (rows  × cpu_operator_cost × number_of_filter_conditions)

For a 1M-row table in 10,000 pages with one WHERE condition:
    10,000 × 1.0     = 10,000     page reads
 + 1,000,000 × 0.01  = 10,000     processing each row
 + 1,000,000 × 0.0025 = 2,500     evaluating the filter
                      ────────
                        22,500

Note that the CPU terms dominate here — more than half the cost is touching
rows, not reading pages. That is why a filter that is expensive to evaluate
(a function call, a regex) shifts the balance noticeably.

Where statistics come from

ANALYZE samples; it does not scan
-- ANALYZE reads a random sample of 300 × default_statistics_target rows —
-- 30,000 by default — and derives four things per column, stored in pg_stats.

SELECT attname, null_frac, n_distinct, correlation,
       most_common_vals, most_common_freqs, histogram_bounds
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

--   null_frac          fraction of NULLs
--   n_distinct         distinct values. NEGATIVE means a ratio to row count:
--                      -1 = every value unique, -0.5 = half as many distinct
--   most_common_vals   the top N values and their frequencies (the MCV list)
--   histogram_bounds   equal-frequency buckets covering everything else
--   correlation        how well physical order matches value order (chapter 6)

-- Selectivity for an equality predicate is then:
--   value in the MCV list  ->  use its exact recorded frequency
--   otherwise              ->  (1 - sum(mcv_freqs) - null_frac) / n_distinct_remaining
--
-- This is why estimates are excellent for common values and rougher for rare
-- ones — and why a skewed column with more distinct values than the MCV list
-- can hold produces poor estimates for everything outside it.
raising the statistics target where it matters
-- Global default is 100 (so 100 MCVs, 100 histogram buckets, 30,000 sampled).
SHOW default_statistics_target;

-- Per column, which is nearly always the right scope:
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;                    -- required; the setting alone does nothing

-- Raise it when a column is:
--   * heavily skewed — one value is 40% of the table and others are rare
--   * used in predicates whose estimates are visibly wrong in EXPLAIN ANALYZE
--   * a join key on a large table
--
-- The cost is a slower ANALYZE and a larger pg_statistic. Raising the GLOBAL
-- target to 1000 makes every ANALYZE ten times more expensive across every
-- column of every table, which is rarely what you want. Target the columns.
n_distinct is sampled, and it is often badly wrong

Estimating the number of distinct values from a sample is a genuinely hard statistical problem, and Postgres frequently underestimates it on large tables — sometimes by orders of magnitude. The symptom is a group-by or a join that the planner thinks produces a hundred rows and actually produces a million. When you know the truth, tell it directly: ALTER TABLE t ALTER COLUMN c SET (n_distinct = -0.8) fixes the estimate permanently and survives ANALYZE. This is one of the few places where overriding a statistic rather than improving it is the right answer.

Extended statistics

the fix for correlated columns
-- The planner assumes columns are INDEPENDENT, so for two predicates it
-- multiplies their selectivities. When one column determines another, the
-- true selectivity is the smaller of the two, not the product — and the
-- estimate comes out orders of magnitude too low.
--
--   P(city = 'Manchester') = 0.02
--   P(postcode LIKE 'M1%') = 0.01
--   assumed together: 0.0002    actual: 0.01     50x too low
--
-- A 50x underestimate is exactly what produces the catastrophic nested loop
-- from the SQL unit's chapter 13.

CREATE STATISTICS addr_stats (dependencies, ndistinct, mcv)
    ON city, postcode FROM addresses;
ANALYZE addresses;

--   dependencies  functional dependencies: postcode determines city
--   ndistinct     the number of distinct COMBINATIONS, for GROUP BY estimates
--   mcv           most common combinations — the most powerful, PG12+

SELECT * FROM pg_stats_ext WHERE tablename = 'addresses';

-- Pairs worth checking in almost any schema:
--   (country, city)        (status, cancelled_at)
--   (product, category)    (year, quarter)
--   (tenant_id, anything)  in a multi-tenant schema, everything correlates
--                          with the tenant
statistics on an expression
-- No statistics exist for an expression, so the planner falls back to a
-- fixed guess — usually 0.5% selectivity, which is wrong in both directions.
SELECT * FROM orders WHERE date_trunc('month', placed_at) = '2026-03-01';

-- Two ways to give it real numbers:
CREATE INDEX ON orders (date_trunc('month', placed_at));   -- index + stats
CREATE STATISTICS ON date_trunc('month', placed_at) FROM orders;  -- PG14+,
                                                                  -- stats only
ANALYZE orders;

-- The second is useful when you want the estimate corrected but do not want
-- to pay for an index on every write.

Join planning

the combinatorial problem, and the escape hatch
-- The planner considers join orders exhaustively, which is factorial in the
-- number of tables. Past a threshold it switches to a genetic algorithm.

SHOW join_collapse_limit;      -- 8  — flatten explicit JOINs up to this many
SHOW from_collapse_limit;      -- 8  — same, for subqueries in FROM
SHOW geqo_threshold;           -- 12 — above this, use the genetic optimiser

-- Symptoms of hitting these on a 15-table query:
--   * planning time in the hundreds of milliseconds
--   * the SAME query producing different plans between runs, because the
--     genetic optimiser is non-deterministic
--
-- Options:
--   raise geqo_threshold      exhaustive search, slower planning, stable plans
--   set geqo = off            never use the genetic optimiser
--   lower join_collapse_limit force the planner to respect your written order
--   restructure the query     usually the real answer

-- Check planning time separately from execution — EXPLAIN reports both, and
-- on a short OLTP query 200ms of planning is the whole problem.

Parallel workers multiply work_mem

Each worker gets its own work_mem for each sort or hash node it runs. A query with two hash joins running four workers can allocate 2 × 5 × work_mem — counting the leader. This is chapter 1's warning in its sharpest form, and it is why raising both work_mem and max_parallel_workers_per_gather together on an OLTP system is a reliable way to meet the OOM killer. Also worth knowing: Workers Planned: 4 / Workers Launched: 0 in a plan means the pool was exhausted by other queries, and the plan's cost estimate no longer bears any relation to what happened.

Settings that change the planner's mind

Legitimate, permanent

  • random_page_cost = 1.1 on SSD
  • effective_cache_size to 50–75% of RAM
  • default_statistics_target, or per column
  • CREATE STATISTICS for correlated columns
  • ALTER TABLE … SET (n_distinct = …) when you know better
  • ALTER FUNCTION … STABLE so calls can be cached

Diagnostic only

  • SET enable_seqscan = off
  • SET enable_nestloop = off
  • SET enable_hashjoin = off
  • pg_hint_plan

These do not disable anything — they add a cost of 10 billion, so the plan is still chosen if nothing else is possible. Use them to confirm "would the other plan be faster", then fix the estimate that caused the wrong choice.

the diagnostic loop
-- 1. Confirm the alternative would be better.
SET enable_nestloop = off;
EXPLAIN ANALYZE SELECT …;        -- 220ms instead of 18s: yes, it would
RESET enable_nestloop;

-- 2. Find why the planner did not choose it. Look for the node where
--    estimated and actual rows diverge most (SQL chapter 13).
--       Seq Scan on events  (rows=12) (actual rows=456213)

-- 3. Fix the estimate, not the plan.
CREATE STATISTICS ev_stats (mcv) ON source, region FROM events;
ANALYZE events;

-- 4. Re-check. The planner now chooses the hash join by itself, and it will
--    keep choosing correctly as the data changes — which a forced plan
--    would not.
EXPLAIN ANALYZE SELECT …;
auto_explain gives you plans you did not think to capture

The hardest plans to debug are the ones from queries that were slow at 3am and are fast now. auto_explain logs the plan of any query exceeding a threshold, automatically, with actual row counts if you enable it. Set auto_explain.log_min_duration = '1s', log_analyze = on and log_nested_statements = on. The log_analyze option adds measurable overhead to every query it triggers on, so start with a high threshold — but having the plan of the incident query, rather than a reconstruction, is worth a great deal.

Keeping statistics fresh

the three cases where statistics are stale and it matters
-- 1. Immediately after a bulk load. Autoanalyze has not run yet, so the
--    planner thinks the table is empty and picks plans for zero rows.
COPY orders FROM …;
ANALYZE orders;              -- always, explicitly, as part of the load

-- 2. Immediately after a major upgrade. pg_upgrade does NOT carry statistics
--    across, so the new cluster starts with none. This is the classic
--    "the upgrade made everything slow" incident.
--    (PostgreSQL 18 improves this; on earlier versions run it yourself.)
vacuumdb --all --analyze-in-stages --jobs=4

-- 3. On a table whose distribution shifts faster than autoanalyze notices.
--    The scale factor is 0.1 by default — 10% of rows changed. On a large
--    append-only table with a moving date range, that is far too slow.
ALTER TABLE events SET (autovacuum_analyze_scale_factor = 0.005);

-- What was analysed and when:
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC
LIMIT 20;

The short version

  1. Cost is arbitrary units anchored to seq_page_cost = 1.0. Only ratios matter.
  2. random_page_cost = 4.0 is a spinning-disk number. Set 1.1 on SSD — the single highest-value planner change.
  3. effective_cache_size defaults to 4 GB regardless of your machine. Set it to 50–75% of RAM. It allocates nothing.
  4. Statistics come from a sample: MCV list, histogram, n_distinct and correlation.
  5. n_distinct is often badly underestimated, and overriding it directly is legitimate.
  6. CREATE STATISTICS for correlated columns — the planner multiplies selectivities and gets it wrong by orders of magnitude.
  7. Parallel workers multiply work_mem, per worker per node.
  8. Use enable_* settings to confirm a diagnosis, then fix the estimate — a forced plan stops adapting.
