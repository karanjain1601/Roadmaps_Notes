Chapter 04 · The engine

The write path

One mechanism — the write-ahead log — provides crash recovery, replication and point-in-time recovery all at once. It also explains why a commit is fast, why checkpoints cause I/O spikes, and why your disk filled up.

wal checkpoints fsync durability

Write to the log, not to the table

The rule is in the name: a change is recorded in the WAL and flushed to disk before the modified data page is. The data page can then be written whenever convenient, because if the server crashes the log has enough information to redo the change.

1 · Modify the page in shared_buffersIn memory. The page is now "dirty"
↓
2 · Append a WAL record to the WAL bufferSequential, tiny, cheap
↓
3 · On COMMIT, flush the WAL to disk and fsyncThis is the only synchronous disk wait in the whole path
↓
4 · Tell the client it committedThe data page is still dirty in memory and that is fine
↓
5 · Later: the checkpointer writes dirty pages to diskBatched, spread out, asynchronous to any client
Why this is fast

A commit writes a small record to the end of one file — sequential I/O, which even on spinning disks is orders of magnitude faster than random writes. Without WAL, committing would mean fsyncing every modified page to its scattered location. Instead, one sequential flush covers arbitrarily many page changes, and the random writes happen later in bulk when the checkpointer can order them sensibly. WAL turns many random synchronous writes into one sequential one.

where the log is, and how to read its position
-- WAL lives in $PGDATA/pg_wal as 16 MB segment files with hex names.
-- A position — an LSN, log sequence number — is a byte offset into that stream.
SELECT pg_current_wal_lsn();              -- 3/A82C4F18
SELECT pg_walfile_name(pg_current_wal_lsn());

-- LSNs subtract, which is how every lag and volume metric in this unit works:
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '3/A0000000'));

-- How much WAL a workload generates, measured directly:
SELECT pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), :start_lsn)) AS wal_written;
-- Capture :start_lsn before a batch job and compare. Useful when a nightly
-- job is quietly producing 200 GB of WAL and filling the archive.

Checkpoints

A checkpoint writes every dirty buffer to disk and records a position in the WAL, saying: everything before here is safely in the data files. Recovery then only needs to replay from the last checkpoint, which bounds how long a crash restart takes.

Checkpoint tuning The trade is between recovery time and how much I/O the checkpointer inflicts. Both ends are unpleasant.
—checkpoint every
—triggered by
—write I/O during spread
—worst-case recovery
the settings, and what each actually controls
checkpoint_timeout = '15min'            -- default 5min; 15-30min is common
max_wal_size = '8GB'                    -- default 1GB; the soft ceiling that
                                        -- triggers a checkpoint when exceeded
min_wal_size = '2GB'                    -- keep this many segments for reuse
checkpoint_completion_target = 0.9      -- default since PG14; spread writes
                                        -- over 90% of the interval
checkpoint_warning = '30s'              -- log if checkpoints come closer

-- The two triggers:
--   TIME     checkpoint_timeout elapsed
--   VOLUME   WAL since the last checkpoint exceeded max_wal_size
--
-- Volume-triggered checkpoints are the ones to avoid. They arrive whenever
-- the write rate says so, they are not spread over a predictable interval,
-- and they mean the settings are fighting the workload.

-- Which trigger is firing:
SELECT checkpoints_timed, checkpoints_req,
       round(100.0 * checkpoints_req /
             nullif(checkpoints_timed + checkpoints_req, 0), 1) AS pct_forced,
       buffers_checkpoint, buffers_clean, buffers_backend,
       checkpoint_write_time, checkpoint_sync_time
FROM pg_stat_bgwriter;
-- (PG17 splits this into pg_stat_checkpointer and pg_stat_bgwriter.)
--
-- pct_forced above ~10% means raise max_wal_size.
-- buffers_backend high means backends are flushing their own pages because
-- the background writer cannot keep up — that cost lands on user queries.
Full-page writes make the first write after a checkpoint expensive

The first time a page is modified after a checkpoint, Postgres writes the entire 8 KB page into the WAL, not just the change. This protects against torn pages — a partial page write during a crash, which the WAL delta alone could not repair. The consequence is that WAL volume spikes immediately after every checkpoint, and frequent checkpoints multiply the effect. It is also why lengthening checkpoint_timeout often reduces total WAL volume substantially, which surprises people who expect the opposite. Do not turn full_page_writes off unless your storage genuinely guarantees atomic 8 KB writes; almost none do.

synchronous_commit off is the one safe speed knob

It is the only durability setting where the failure mode is losing recent commits rather than corrupting the database. On a crash you lose up to a few hundred milliseconds of transactions; everything that survives is consistent. That is an entirely reasonable trade for analytics loads, bulk imports, session tables and audit trails — and it can be set per transaction, so the payment write stays durable while the page-view insert does not. fsync = off is a different category and belongs only in throwaway test environments.

per-transaction durability
-- Global default stays safe.
-- Relax it only where losing a few hundred ms of writes is acceptable.
BEGIN;
SET LOCAL synchronous_commit = off;
INSERT INTO page_views (…) SELECT … FROM staging;   -- 50k rows
COMMIT;   -- returns without waiting for the WAL flush

-- Or per role, which is usually cleaner:
ALTER ROLE etl SET synchronous_commit = off;

-- With synchronous replication configured (chapter 13) there are more levels:
--   off          do not wait for the local flush
--   local        wait for the local flush only
--   remote_write wait for a standby to receive it
--   on           wait for a standby to flush it
--   remote_apply wait for a standby to APPLY it — read-your-writes on replicas,
--                and the slowest by a wide margin

Crash recovery

what happens when it starts after a crash
LOG:  database system was not properly shut down; automatic recovery in progress
LOG:  redo starts at 3/A82C4F18
LOG:  invalid record length at 3/AB19C220: wanted 24, got 0
LOG:  redo done at 3/AB19C1F8 system usage: CPU 4.12s elapsed 38.44s
LOG:  database system is ready to accept connections

-- What it did:
--   1. read the last checkpoint record to find the redo start position
--   2. replayed every WAL record from there forward, reapplying changes to
--      pages whose on-disk version is older than the record
--   3. stopped at the first invalid record — that is the crash point, and the
--      "invalid record length" line is expected, not an error
--   4. rolled back anything left uncommitted, lazily, via MVCC (chapter 2):
--      those tuples are simply never visible and vacuum removes them later
--
-- "elapsed 38.44s" is your recovery time, and it is bounded by how much WAL
-- accumulated since the last checkpoint. That is the whole reason
-- checkpoint_timeout is a trade rather than a free knob.

WAL retention: the thing that fills your disk

four reasons WAL is not being removed
-- Normally WAL older than the last checkpoint is recycled. It is retained if:

-- 1. A REPLICATION SLOT is holding it. The single most common cause, because
--    an inactive slot retains WAL forever and nothing complains until the
--    disk is full.
SELECT slot_name, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;
-- active = false with gigabytes retained: a replica that was decommissioned
-- and whose slot nobody dropped. Set max_slot_wal_keep_size (PG13+) so the
-- slot is invalidated instead of taking the primary down.

-- 2. archive_command is FAILING. Postgres will not recycle unarchived WAL.
SELECT archived_count, last_archived_wal, last_archived_time,
       failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;
-- A rising failed_count with a stale last_archived_time is a ticking clock.

-- 3. wal_keep_size is set high (or wal_keep_segments on old versions).

-- 4. A checkpoint has not happened yet — rare, and self-resolving.

-- Alert on pg_wal size as a percentage of the filesystem. A full pg_wal
-- stops all writes, and recovering from it is unpleasant precisely because
-- you cannot write.
An abandoned replication slot is the classic 3am page

A standby is removed, or a logical subscriber stops consuming, and its slot stays behind. The primary keeps every WAL segment since that slot's position — forever — because as far as it knows a consumer will return. Disk usage climbs steadily for days with no other symptom, then the filesystem fills and the database stops accepting writes. Put pg_replication_slots on your dashboard, alert on any slot with active = false, and set max_slot_wal_keep_size so Postgres invalidates a runaway slot rather than sacrificing the primary for it.

reducing WAL volume, in order of effect
-- 1. Longer checkpoint interval  -> far fewer full-page images
checkpoint_timeout = '30min';  max_wal_size = '16GB';

-- 2. Compress the full-page images that remain
wal_compression = 'lz4';       -- or 'pglz'; lz4 is faster, PG15+

-- 3. Drop indexes you do not use (SQL chapter 12). Each one is WAL per write.

-- 4. Unlogged tables for genuinely disposable data
CREATE UNLOGGED TABLE import_staging (…);
-- No WAL, so no replication and no crash survival — the table is TRUNCATED
-- after an unclean shutdown. Correct for staging and scratch; never for
-- anything you would miss.

-- 5. Update fewer columns and fewer rows. The cheapest WAL is the record you
--    never wrote, and chapter 5's HOT updates make some updates much cheaper.
The same WAL powers three features

Crash recovery replays it locally. Streaming replication ships it to a standby that replays it continuously (chapter 13). Point-in-time recovery archives it alongside a base backup so you can replay to any moment (chapter 12). This is why the WAL settings appear in all three chapters, and why wal_level is a restart-only setting you want right from the beginning — discovering you need logical after the cluster is in production means a restart you have to schedule.

The short version

  1. WAL turns many random synchronous writes into one sequential flush. That is why commits are fast.
  2. A commit's only disk wait is the WAL fsync; data pages are written later by the checkpointer.
  3. Checkpoints trade recovery time against I/O spikes. Volume-triggered checkpoints mean max_wal_size is too small.
  4. Full-page writes mean WAL spikes after every checkpoint — so a longer interval often reduces total WAL.
  5. synchronous_commit = off loses commits, not consistency, and can be set per transaction or per role. fsync = off corrupts.
  6. Recovery replays from the last checkpoint; uncommitted work is discarded lazily via MVCC.
  7. WAL not being recycled means a replication slot, a failing archive command, or wal_keep_size.
  8. An inactive replication slot will fill your disk and stop all writes. Alert on it and set max_slot_wal_keep_size.
