Replication

Chapter 4's write-ahead log, shipped somewhere else and replayed. That one sentence covers streaming replication entirely — and the interesting decisions are all about what you give up in exchange for how much durability.

setting up a streaming replica
# On the primary — postgresql.conf
wal_level = replica                 # the default; 'logical' also works
max_wal_senders = 10
max_replication_slots = 10
# pg_hba.conf — note DATABASE is the literal word `replication` (chapter 11)
#   hostssl  replication  replicator  10.0.9.0/24  scram-sha-256

CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '…';

# On the standby — one command builds the whole thing
pg_basebackup \
    -h primary.internal -U replicator \
    -D /var/lib/postgresql/16/main \
    -Fp -Xs -P -R \
    --slot=standby1 --create-slot

#   -R  writes standby.signal and the primary_conninfo setting for you
#   --create-slot  creates a replication slot on the primary, so it retains
#                  WAL this standby has not yet received

# Then just start it. It connects, streams, and catches up.
pg_ctl -D /var/lib/postgresql/16/main start

Synchronous commit

Durability against latency Every level buys a stronger guarantee and pays for it on every single commit.
—added commit latency
—data lost if the primary dies
—max commits/sec per session
—read-your-writes on the replica
configuring it, and doing so per transaction
-- On the primary. The standby names come from their application_name,
-- set in primary_conninfo.
synchronous_standby_names = 'ANY 1 (standby1, standby2)';
synchronous_commit = 'on';

--   FIRST 1 (a, b)   wait for a; fall back to b — a strict priority order
--   ANY 1 (a, b)     wait for whichever responds first — usually what you want
--   ANY 2 (a, b, c)  wait for any two

-- The setting is per transaction, which is the important part: pay for
-- durability where it matters and not everywhere.
BEGIN;
SET LOCAL synchronous_commit = 'remote_apply';
INSERT INTO payments …;          -- must survive, and must be readable
COMMIT;

ALTER ROLE analytics_writer SET synchronous_commit = 'off';   -- disposable

SELECT application_name, state, sync_state, sync_priority,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
--   sync_state: sync | potential | async | quorum
One synchronous standby is a single point of failure for writes

With synchronous_standby_names = 'standby1' and that standby down, every commit on the primary blocks indefinitely. The primary is healthy, the disk is fine, and the application is completely stalled — waiting for acknowledgement from a machine that is gone. This surprises people badly the first time, because they configured synchronous replication for safety and got an outage. Use ANY 1 (a, b) with at least two candidates, so losing one standby degrades nothing. And have the runbook step written down: ALTER SYSTEM SET synchronous_standby_names = '' plus a reload releases the writes immediately, at the cost of the guarantee.

Replication slots

the guarantee, and the hazard
-- A slot records how far a consumer has got, and the primary retains WAL
-- until that position. That is what stops a standby falling irrecoverably
-- behind after a network blip.
--
-- It is also chapter 4's disk-filling hazard: an INACTIVE slot retains WAL
-- forever, because as far as the primary knows the consumer will come back.

SELECT slot_name, slot_type, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
           AS wal_retained,
       age(xmin) AS xmin_age
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

--   active = false with gigabytes retained: a decommissioned replica whose
--            slot nobody dropped. This is the classic 3am page.
--   xmin_age climbing: a LOGICAL slot also holds back vacuum, cluster-wide,
--            exactly like a long transaction (chapters 2 and 3)

-- The safety valve. Postgres invalidates a runaway slot rather than letting
-- it take the primary down:
ALTER SYSTEM SET max_slot_wal_keep_size = '100GB';   -- PG13+

-- Set it. Without it, the trade is "lose one standby" against "lose the
-- primary", and the default picks wrong.

SELECT pg_drop_replication_slot('old_standby');

Reading from replicas

what changes when the read is not on the primary
-- 1. Reads are stale by the replay lag. Usually milliseconds; occasionally
--    much more. Read-your-writes breaks: a user saves a form, the redirect
--    reads from a replica, and their change is not there.
--    Route reads that follow a write to the primary, or use remote_apply
--    for that specific transaction.

-- 2. Long queries on the standby conflict with replay. The standby must
--    apply changes that would remove rows the query is still reading, and
--    something has to give:
max_standby_streaming_delay = '30s';   -- pause replay for up to 30s...
--    ...then CANCEL the query:
--      ERROR: canceling statement due to conflict with recovery

--    Or make the standby tell the primary what it needs kept:
hot_standby_feedback = on;
--    Now the primary will not vacuum rows the standby's queries need — which
--    stops the cancellations AND causes bloat on the primary, driven by
--    queries running on a different machine. Both settings are a trade
--    between the two problems; pick deliberately.

-- 3. No writes at all, including temporary tables and sequence nextval().
--    An ORM that writes a session row on every request cannot use a replica.

SELECT now() - pg_last_xact_replay_timestamp() AS replay_lag;
SELECT pg_is_in_recovery();      -- true on a standby — useful for routing
Read replicas are not free capacity

They are frequently proposed as a way to scale reads, and they solve a narrower problem than that. Every write still happens on every replica, so a write-heavy workload gains nothing. Reads are stale, so anything that needs its own writes back must go to the primary. Long analytical queries either get cancelled or cause bloat on the primary. What replicas are genuinely good for: an analytics workload that tolerates staleness and would otherwise evict the OLTP working set from the primary's cache, taking backups without touching the primary, and being ready to promote. That is a real set of wins — just not "add a replica and double your throughput".

Logical replication

publish and subscribe
-- Publisher: wal_level = logical  (a RESTART — decide this before go-live)
CREATE PUBLICATION orders_pub FOR TABLE orders, line_items;
CREATE PUBLICATION everything FOR ALL TABLES;
CREATE PUBLICATION eu_only FOR TABLE customers WHERE (region = 'eu');  -- PG15+

-- Subscriber: a normal, writable database
CREATE SUBSCRIPTION orders_sub
    CONNECTION 'host=primary dbname=orders user=replicator password=…'
    PUBLICATION orders_pub
    WITH (copy_data = true, streaming = on);

SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_replication_slots WHERE slot_type = 'logical';

-- Every replicated table needs a REPLICA IDENTITY so updates and deletes can
-- identify the row. A primary key provides it automatically. Without one:
ALTER TABLE t REPLICA IDENTITY USING INDEX some_unique_index;
ALTER TABLE t REPLICA IDENTITY FULL;   -- the whole old row as the key.
                                       -- Works, and is expensive
-- A table with no primary key and no replica identity silently replicates
-- INSERTs and fails on UPDATE and DELETE. Check before you rely on it.
Logical replication does not replicateConsequence
DDLApply schema changes on the subscriber first, then the publisher
Sequence valuesAdvance them manually before promoting a subscriber
TRUNCATEReplicated since PG11, but only if included in the publication
Large objectsNot supported at all
Rows from other subscribersNo cascading by default — watch for loops in bidirectional setups
Logical replication holds back vacuum on the publisher

A logical slot keeps an xmin, so it holds the cleanup horizon exactly like a long transaction (chapter 2). If a subscriber falls behind or stops consuming, the publisher accumulates dead tuples across every table while nothing looks wrong on that side. It also retains WAL. So a broken subscriber produces two slow-motion failures on a machine that is not the one with the problem — bloat and a filling disk. Monitor pg_replication_slots.xmin_age and wal_retained on the publisher, not just subscription health on the subscriber.

Monitoring lag

from both ends, because they answer different questions
-- On the PRIMARY: per-standby, in bytes and in time
SELECT client_addr, application_name, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn))   AS pending,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn))             AS to_apply,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

--   write_lag   time until the standby wrote it
--   flush_lag   ...flushed it to disk
--   replay_lag  ...made it visible to queries    <- what readers experience

-- On the STANDBY: how stale am I, in seconds
SELECT CASE WHEN pg_is_in_recovery()
            THEN coalesce(extract(epoch FROM now() - pg_last_xact_replay_timestamp()), 0)
            ELSE 0 END AS lag_seconds;

-- One caveat that causes false alarms: on an IDLE primary this number grows
-- steadily, because there is nothing new to replay and the timestamp of the
-- last replayed transaction keeps getting older. Alert on byte lag as well,
-- or the pager fires every quiet Sunday.

-- Why a standby is behind, when it is:
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE backend_type = 'startup' GROUP BY 1,2;
-- Replay is single-threaded, so a standby on slower storage than the primary
-- will fall behind under sustained write load and never catch up.

Choosing a topology

NeedSetup
Survive losing the machineOne async streaming standby, same region, plus WAL archiving (chapter 12)
Survive it with zero data lossTwo standbys, ANY 1 synchronous — never a single sync standby
Survive losing the regionAn async standby in another region; accept the extra RPO
Offload analyticsAn async standby with hot_standby_feedback = on and a long max_standby_streaming_delay, accepting bloat on the primary
Catch a destructive mistakeA delayed standby: recovery_min_apply_delay = '1h'
Upgrade across major versionsLogical replication (chapter 16)
Feed another systemLogical replication, or a change-data-capture tool reading the slot
Write in two placesGenuinely hard. Conflict resolution is your problem — think very carefully first
A delayed standby is cheap insurance

recovery_min_apply_delay = '1h' makes a standby stay deliberately one hour behind. When someone runs a DELETE without a WHERE, or a migration corrupts a column, you have an hour to notice — and the correct data is sitting on a running server you can query immediately, rather than at the end of a multi-hour restore. It costs one extra machine and nothing else. It is not a backup and it does not replace one; it is the fastest possible recovery for the specific, common failure of a human destroying data.

Timelines

why an old primary cannot just rejoin
When a standby is promoted it starts a new TIMELINE — an identifier that
distinguishes "the WAL stream after this promotion" from "the WAL stream that
would have continued on the old primary".

    timeline 1  ────────────●───────────  old primary kept writing here
                            │              (these changes are now orphaned)
    timeline 2              └───────────   new primary, after promotion

The old primary may have committed transactions after the last one the
standby received. Those changes exist only on the old primary and diverge
from the new history — so it cannot simply reconnect as a standby.

Options:
  pg_rewind    rewinds the old primary to the divergence point and lets it
               follow the new one. Requires wal_log_hints = on or data
               checksums, and it DISCARDS those diverged transactions
  rebuild      pg_basebackup from the new primary. Slow, always correct

Set wal_log_hints = on now — it is a restart-only setting, and without it
pg_rewind is unavailable exactly when you want it. Data checksums (chapter 5)
satisfy the same requirement, which is another reason to have them.

The short version

  1. Streaming replication is chapter 4's WAL, shipped and replayed. Logical decodes it into row changes instead.
  2. Never a single synchronous standby. If it goes down, every commit blocks. Use ANY 1 with two candidates.
  3. synchronous_commit is per transaction — pay for durability where it matters.
  4. An inactive replication slot retains WAL forever. Set max_slot_wal_keep_size.
  5. Replicas are not free read capacity: stale reads, no writes, and long queries either get cancelled or bloat the primary.
  6. Logical replication does not replicate DDL, and its slot holds back vacuum on the publisher.
  7. Time-based lag grows on an idle primary. Alert on byte lag too, or the pager fires every Sunday.
  8. Set wal_log_hints = on now — it is restart-only, and without it pg_rewind is unavailable when you need it.
