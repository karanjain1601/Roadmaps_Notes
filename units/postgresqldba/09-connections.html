Connections and pooling

Because a connection is an operating-system process, adding more of them past a point makes the database slower rather than faster. That fact makes pooling a requirement rather than an optimisation, and it is the most common thing to get wrong on a growing system.

The knee Throughput rises with concurrency until the cores are busy, then falls. Latency does the opposite of what people expect.

More connections is not more capacity

Eight cores can execute eight things at once. Beyond enough concurrency to keep them busy through I/O waits, extra connections do not add throughput — they add context switching, lock contention, cache pressure and memory use. Throughput falls past the knee and latency climbs sharply. The standard starting formula is cores × 2 + effective_spindles, which for modern hardware usually lands between 10 and 40 active connections, not the several hundred people configure. If the database is slow and the pool is saturated, the fix is very rarely a bigger pool.

Application pools multiply

The arithmetic that catches teams during a scale-up: twenty application instances, each with a framework connection pool of twenty, is four hundred connections — and the number grows every time you add a pod. Autoscaling makes it worse, because the peak instance count is exactly when the database is already busy. Either size the per-instance pool so that instances × pool stays under your target, which is fragile as the instance count changes, or put a pooler in front and let it enforce one number. The second is the only version that survives autoscaling.

listen_addr = 0.0.0.0

pool_mode = transaction          ; the whole point

max_client_conn = 2000           ; how many CLIENTS may connect to pgbouncer
default_pool_size = 25           ; backends per (database, user) pair
min_pool_size = 5                ; keep a few warm
reserve_pool_size = 5            ; emergency headroom
reserve_pool_timeout = 3

server_idle_timeout = 600
server_lifetime = 3600           ; recycle backends so memory does not creep
query_wait_timeout = 30          ; fail rather than queue forever

ignore_startup_parameters = extra_float_digits,options

; max_client_conn is the number that lets you accept a burst; default_pool_size
; is the number that protects the database. Those are different problems, and
; separating them is the main thing a pooler buys you.

What transaction mode breaks

anything that assumes the same backend next time
-- In transaction mode, consecutive statements from one client may land on
-- DIFFERENT backends. Anything that lives in session state is unreliable.

-- BROKEN: the SET may apply to one backend and the query run on another.
SET work_mem = '256MB';
SELECT …;

-- FINE: SET LOCAL is scoped to the transaction, so it travels with it.
BEGIN;
SET LOCAL work_mem = '256MB';
SELECT …;
COMMIT;

-- Also affected:
--   session-level advisory locks   -> use transaction-level: pg_advisory_xact_lock()
--   LISTEN / NOTIFY                -> needs session mode, or a separate connection
--   WITH HOLD cursors              -> not usable
--   temporary tables               -> may not exist on the next backend
--   PREPARE / EXECUTE              -> PgBouncer 1.21+ handles protocol-level
--                                     prepared statements; older versions need
--                                     the driver's prepared statements disabled
--   SET ROLE, and RLS via SET      -> use SET LOCAL (SQL chapter 15)

-- The RLS case deserves emphasis: plain SET app.tenant_id persists on the
-- backend and WILL leak to the next client that borrows it. SET LOCAL resets
-- at COMMIT and is safe. Test it explicitly with two tenants through one
-- pooled connection — it never fails in development, where each request gets
-- its own connection.
Prepared statements and PgBouncer

Historically the sharpest edge. Many drivers use protocol-level prepared statements by default, and in transaction mode the PREPARE happened on one backend while the EXECUTE landed on another — producing "prepared statement does not exist" errors that appear only under load, only in production, and only sometimes. PgBouncer 1.21 added proper support and this is largely solved on current versions. On anything older, disable driver-side prepared statements: prepareThreshold=0 for JDBC, prepare_threshold=None for psycopg, statement_cache_size=0 for asyncpg.

Choosing a pooler

OptionNotes
PgBouncerSingle-threaded, tiny, extremely well proven. The default choice. Run several instances behind a load balancer if one CPU becomes the bottleneck
pgcatMulti-threaded, adds load balancing across replicas and sharding. Younger, actively developed
OdysseyMulti-threaded, from Yandex. Good at scale, smaller community
SupavisorElixir, built for very large client counts and multi-tenant hosting
Application-side poolNecessary and not sufficient — it cannot coordinate across instances
Managed service poolerRDS Proxy, Cloud SQL and others. Convenient; check which pool mode and which features are supported
You want both pools, doing different jobs

The application-side pool avoids a TCP connect and a round trip per request — real latency, worth keeping. The server-side pooler enforces one global limit on actual backends regardless of how many instances exist. They are not alternatives. The usual configuration is a small per-instance pool (5–10) pointing at PgBouncer, with PgBouncer's default_pool_size set to the number the database can actually use well. Clients connect instantly, and the database sees a stable, small number of backends.

Monitoring the pool

PgBouncer's admin console, and the columns that matter
psql -p 6432 -U pgbouncer pgbouncer

SHOW POOLS;
--  cl_active  clients currently attached to a backend
--  cl_waiting WAITING FOR ONE   <- the number to alert on
--  sv_active  backends in use
--  sv_idle    backends free
--  maxwait    seconds the longest-waiting client has waited  <- and this one
--
-- cl_waiting consistently above zero with maxwait climbing means the pool is
-- saturated. Before raising default_pool_size, check WHY: usually queries got
-- slower, or a transaction is being held open across a network call.

SHOW STATS;      -- queries and transactions per second, average times
SHOW SERVERS;    -- individual backend connections and their state
SHOW CLIENTS;    -- who is connected, and what they are waiting for

-- From the database side, the corresponding view:
SELECT state, count(*), max(now() - state_change) AS longest
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state;
-- A large "idle in transaction" count here is the classic cause of pool
-- exhaustion: those backends are checked out and doing nothing (chapter 8).

When the pool saturates, look at query duration first

A saturated pool is nearly always a symptom. Backends are held for as long as each transaction runs, so if transactions got slower — a missing index after a deploy, a plan change, a lock wait, a transaction holding open across an HTTP call — the same traffic now needs more concurrent backends. Raising the pool size treats the symptom and usually makes it worse, because more concurrency past the knee reduces throughput further. Check pg_stat_statements for what changed, and check for idle in transaction, before touching the pool.

Reserve connections

so you can still log in when it is on fire
-- max_connections includes everything. Reserve slots so an incident does not
-- also lock you out of the database.
max_connections = 200
superuser_reserved_connections = 5        -- always available to superusers
reserved_connections = 10                 -- PG16+, for a designated role
max_wal_senders = 10                      -- replication uses connection slots
                                          -- and is counted separately

-- Grant the monitoring role pg_monitor so it can read the statistics views
-- without being a superuser, and give it its own reserved capacity:
CREATE ROLE monitoring LOGIN;
GRANT pg_monitor TO monitoring;
ALTER ROLE monitoring CONNECTION LIMIT 5;

-- Per-role and per-database limits are a useful blunt instrument:
ALTER ROLE batch_jobs CONNECTION LIMIT 10;
ALTER DATABASE analytics CONNECTION LIMIT 40;
-- One misbehaving service then cannot consume every slot.

The short version

  1. A connection is an OS process. Past the knee, more connections means less throughput and more latency.
  2. Start at cores × 2 — usually 10 to 40 active backends, not hundreds.
  3. Application pools multiply across instances. Only a server-side pooler enforces one global limit.
  4. Transaction mode is the point of PgBouncer. Session mode mostly just saves the fork cost.
  5. Transaction mode breaks session state: use SET LOCAL, transaction-level advisory locks, and no session temp tables.
  6. SET for RLS tenant context will leak through a pooled connection. SET LOCAL will not — test it with two tenants.
  7. Prepared statements work in transaction mode from PgBouncer 1.21; disable driver-side prepares on older versions.
  8. Alert on cl_waiting and maxwait — and when the pool saturates, check query duration before raising it.
