Partitioning

Splitting one logical table into many physical ones. It is frequently proposed as a fix for "the table is large", which is the wrong reason — the right reasons are retention and pruning, and getting the key wrong makes everything slower.

declarative pruning retention choosing a key

What it actually buys

Genuine wins

  • Instant retention — DROP TABLE on an old partition, no DELETE, no bloat, no vacuum
  • Pruning — a query filtered on the key reads only the relevant partitions
  • Per-partition maintenance — vacuum, reindex and analyse one at a time
  • Bulk load and detach — build a partition offline, attach it in one operation
  • Smaller indexes — one B-tree per partition rather than one enormous one

Not wins

  • Lookups by primary key. A B-tree on 1 billion rows is barely deeper than on 100 million
  • Queries that do not filter on the partition key — now they scan every partition
  • Anything requiring uniqueness across partitions on a different column
  • Write throughput, in itself
  • "The table is too big" as a general complaint
Partition for retention and pruning, not for size

The test: does nearly every query filter on the same column, and do you delete old data by that column? If yes — events, logs, metrics, orders by date, anything with a time dimension — partitioning is excellent and you should do it early. If no, it will make most queries slower by turning one index lookup into a lookup per partition, and add operational work for nothing. A large table is not by itself a reason.

Setting it up

declarative partitioning
CREATE TABLE events (
    id          bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    device_id   bigint      NOT NULL,
    payload     jsonb,
    PRIMARY KEY (id, occurred_at)      -- the key MUST include the
) PARTITION BY RANGE (occurred_at);    -- partition column

CREATE TABLE events_2026_03 PARTITION OF events
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
CREATE TABLE events_2026_04 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

-- A catch-all, so an out-of-range insert does not error. Mixed blessing:
-- it prevents errors and it hides the fact that you stopped creating
-- partitions. Monitor its row count if you use one.
CREATE TABLE events_default PARTITION OF events DEFAULT;

-- Indexes created on the parent are created on every partition automatically
-- and on every new one:
CREATE INDEX ON events (device_id, occurred_at DESC);
CREATE INDEX ON events USING brin (occurred_at);   -- tiny (chapter 6)

-- Three strategies:
--   RANGE  time, id ranges — by far the most common
--   LIST   discrete values: region, tenant, status
--   HASH   even distribution when there is no natural grouping.
--          Note HASH gives you NO pruning benefit for range queries and no
--          cheap retention — it mostly just spreads writes
Every unique constraint must contain the partition key

This is the constraint that most often makes partitioning impossible, and it is worth checking before you commit. Postgres cannot enforce uniqueness across partitions without a global index, which it does not have — so a primary key on id alone is rejected and you need (id, occurred_at). That is fine until something references the table by id alone: foreign keys pointing at a partitioned table need the full key, so a child table must carry the partition column too. Work through your foreign keys before partitioning, not after.

Automating partition management

pg_partman, because doing this by hand fails eventually
CREATE EXTENSION pg_partman;

SELECT partman.create_parent(
    p_parent_table => 'public.events',
    p_control      => 'occurred_at',
    p_interval     => '1 month',
    p_premake      => 4                  -- keep 4 future partitions ready
);

UPDATE partman.part_config
SET retention = '12 months',
    retention_keep_table = false,        -- actually drop them
    infinite_time_partitions = true
WHERE parent_table = 'public.events';

-- Run maintenance on a schedule — pg_cron, or an external scheduler
SELECT partman.run_maintenance('public.events');

-- Doing it manually is a cron job that creates next month's partition. It
-- works for a year and then fails at 2am on the first of the month because
-- the disk was full or the job host was rebuilt — and every insert starts
-- landing in the default partition or erroring outright.
--
-- Monitor either way:
SELECT count(*) FROM events_default;      -- should be 0
SELECT max(relname) FROM pg_class
WHERE relname LIKE 'events_2%';           -- should be several months ahead

Retention, which is the main reason

instant, versus hours of damage
-- Unpartitioned: deleting 100 million rows.
DELETE FROM events WHERE occurred_at < now() - interval '12 months';
--   * hours of work, generating WAL for every row
--   * 100 million dead tuples for vacuum to process (chapter 3)
--   * every index rewritten
--   * the table does not shrink; the space is only marked reusable
--   * replicas replay all of it

-- Partitioned: the same outcome.
DROP TABLE events_2025_03;
--   * instant. A catalogue change and an unlink
--   * no dead tuples, no WAL for rows, no vacuum work
--   * the space is returned to the filesystem immediately

-- Or keep the data and take it out of the live table:
ALTER TABLE events DETACH PARTITION events_2025_03 CONCURRENTLY;
-- Now an ordinary standalone table: archive it, move it to cheap storage,
-- or attach it again later. CONCURRENTLY avoids the exclusive lock (PG14+).

-- Attaching validates that every row satisfies the bound, which means a scan.
-- Add a matching CHECK constraint first and the scan is skipped:
ALTER TABLE events_2026_05 ADD CONSTRAINT ck
    CHECK (occurred_at >= '2026-05-01' AND occurred_at < '2026-06-01');
ALTER TABLE events ATTACH PARTITION events_2026_05
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');   -- no scan
If a table has a retention policy, it probably wants partitioning

The strongest single signal. Any table where you periodically delete old rows — events, logs, metrics, sessions, audit trails, notifications — is paying an enormous recurring cost for a job that partitioning makes free. And it compounds: the mass DELETE creates bloat, the bloat needs vacuum, the vacuum competes with your workload, and the table never actually shrinks. Set this up before the table is large, because converting a big table to partitioned is real work (below).

Choosing the key

QuestionWhy it decides things
Do nearly all queries filter on it?Without this, pruning never happens and every query touches every partition
Does retention follow it?The main operational win
Is it immutable?Updating the key moves the row between partitions — allowed since PG11 and expensive
Does it appear in every unique constraint?It must. Check your foreign keys first
Are the partitions evenly sized?One partition holding 90% of the data gives you the costs without the benefits
How many will there be?Aim for tens to low hundreds, not thousands
Do not create thousands of partitions

Planning has to consider each one, and every partition a query touches takes a lock — so a query against a table with 5,000 partitions can exhaust max_locks_per_transaction and fail with "out of shared memory". Even with pruning, planning time grows and pg_class becomes large enough to slow catalogue lookups. Postgres 12 improved this enormously and it is not free even now. Tens to low hundreds is the comfortable range: monthly partitions with a few years of retention, or daily for a few months. Daily partitions kept for five years is 1,800 tables and a bad time.

Pruning in detail

two stages, and what defeats each
-- PLAN-TIME pruning: the planner excludes partitions using constant values in
-- the query. The excluded ones never appear in the plan at all.
EXPLAIN SELECT * FROM events WHERE occurred_at >= '2026-03-01';

-- RUN-TIME pruning: for parameters and subquery results, values are not known
-- until execution. The plan shows all partitions, and the executor skips them.
EXPLAIN (ANALYZE) SELECT * FROM events WHERE occurred_at >= $1;
--   Append  (actual rows=…)
--     Subplans Removed: 9        <- run-time pruning worked
SET enable_partition_pruning = on;   -- default; only turn off to diagnose

-- What defeats pruning:
--   a function on the column      date_trunc('month', occurred_at) = …
--   a cast                        occurred_at::date = '2026-03-14'
--   a join to the key             ON d.day = events.occurred_at::date
--   no predicate at all           the commonest reason by far
--
-- The fix is almost always to write a plain range on the bare column:
WHERE occurred_at >= '2026-03-14' AND occurred_at < '2026-03-15'
-- rather than a function that computes the same thing. This is the SARGability
-- argument from the SQL unit, with partitions as the stake instead of an index.

-- Partitionwise operations — off by default because planning gets expensive:
SET enable_partitionwise_join = on;      -- join partition to partition
SET enable_partitionwise_aggregate = on; -- aggregate per partition, then combine
-- Worth enabling for analytics workloads on partitioned tables; leave off
-- for OLTP.

Converting an existing table

without a long outage
-- There is no ALTER TABLE ... PARTITION BY. You build a new structure and
-- move the data, which is why doing this early is much cheaper.

-- 1. New partitioned table, same columns.
CREATE TABLE events_new (LIKE events INCLUDING ALL)
    PARTITION BY RANGE (occurred_at);
-- (adjust the primary key to include occurred_at)

-- 2. Create partitions covering all existing data plus the near future.

-- 3. Attach the OLD table as one partition covering everything historical.
--    Add the CHECK first so the attach does not scan it.
ALTER TABLE events ADD CONSTRAINT ck_hist
    CHECK (occurred_at < '2026-04-01');
ALTER TABLE events_new ATTACH PARTITION events
    FOR VALUES FROM (MINVALUE) TO ('2026-04-01');

-- 4. Swap the names in one transaction.
BEGIN;
ALTER TABLE events     RENAME TO events_hist;
ALTER TABLE events_new RENAME TO events;
COMMIT;

-- 5. New rows now land in proper partitions. Migrate the history in batches
--    at your leisure, or leave it as one large partition and let retention
--    eventually drop it.

-- The alternative — copy every row into the new structure, then swap — is
-- simpler and needs double the disk plus a way to catch up the writes that
-- arrived during the copy. Logical replication to a partitioned subscriber
-- is the clean version of that, and it works across the swap.

Operating a partitioned table

  • Monitor the default partition. Rows landing there mean partition creation has stopped. It should always be empty.
  • Keep several future partitions ready. p_premake = 4 or equivalent, so one failed maintenance run is not an incident.
  • Autovacuum works per partition, which is good — but per-table settings must be applied to the partitions, not only the parent.
  • Statistics are per partition, plus optional parent-level ones. Run ANALYZE on the parent after big changes.
  • Watch max_locks_per_transaction if partition counts grow.
  • Indexes created on the parent propagate to new partitions automatically. Ones created directly on a partition do not.
  • Check pruning is happening with EXPLAIN after any query change — losing it is silent and expensive.
Partitioning and BRIN together

On an append-only time-series table these compose unusually well. Partitioning restricts the query to the relevant months; within a partition, a BRIN index on the timestamp narrows it to the right block ranges — and the BRIN index is a few kilobytes rather than gigabytes (chapter 6). Correlation stays near perfect because each partition is written in time order. The result is a table that scales to billions of rows with tiny indexes, instant retention and no vacuum crisis. It is the standard shape for this workload and worth reaching for deliberately.

The short version

  1. Partition for retention and pruning, not because a table is large.
  2. The test: do nearly all queries filter on the same column, and does deletion follow it?
  3. Every unique constraint must include the partition key — check your foreign keys before committing to this.
  4. DROP TABLE on a partition is instant; the equivalent DELETE is hours of work and bloat.
  5. Tens to low hundreds of partitions. Thousands means lock exhaustion and slow planning.
  6. A function or cast on the key defeats pruning, and losing it is silent.
  7. Monitor the default partition — rows in it mean partition creation has stopped.
  8. Set it up before the table is large. Converting later is real work.
