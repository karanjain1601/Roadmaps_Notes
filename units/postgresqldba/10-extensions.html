Extensions

Chapter 1 called extensibility one of the five design decisions. In practice it means the difference between Postgres and a stack of four specialist systems — and it means a handful of extensions you should install before you need them.

day one evaluating operations upgrades

Install these before you need them

the day-one set
-- 1. pg_stat_statements — query statistics. Needs shared_preload_libraries
--    and therefore a RESTART, which is exactly why you want it configured
--    before the incident rather than during it.
--    postgresql.conf:  shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION pg_stat_statements;

-- 2. auto_explain — plans for slow queries, logged automatically (chapter 7).
--    Also preload-only.
--    shared_preload_libraries = 'pg_stat_statements,auto_explain'
--    auto_explain.log_min_duration = '3s'
--    auto_explain.log_analyze = on          (has overhead; start high)
--    auto_explain.log_nested_statements = on

-- 3. pg_buffercache — what is actually in shared_buffers right now.
CREATE EXTENSION pg_buffercache;

-- 4. pgstattuple — real bloat measurement rather than an estimate (chapter 3).
CREATE EXTENSION pgstattuple;

-- 5. pg_trgm — substring and fuzzy search. You will want it eventually
--    and adding it later means an index build (chapter 6).
CREATE EXTENSION pg_trgm;

-- 6. btree_gist — scalars inside GiST indexes, which is what exclusion
--    constraints need (SQL chapter 11).
CREATE EXTENSION btree_gist;

-- Available on this server, and what is already installed:
SELECT name, default_version, installed_version, comment
FROM pg_available_extensions
WHERE installed_version IS NOT NULL OR name IN ('pg_stat_statements','pg_trgm')
ORDER BY installed_version NULLS LAST, name;
The preload-only ones are the argument for doing this on day one

pg_stat_statements and auto_explain both require shared_preload_libraries, which means a restart. The moment you actually want them is during an incident, when a restart is the last thing you can do — and even after restarting you have no history, only whatever accumulates from that point. Their overhead is small and well understood. Configure them when the cluster is created, and you will have months of query history the first time someone asks what changed.

pg_stat_statements

the single most useful extension there is
-- Normalises queries by replacing literals with placeholders, then aggregates
-- statistics per normalised query. One row per query SHAPE, not per execution.

SELECT
    calls,
    round(total_exec_time::numeric)                        AS total_ms,
    round(mean_exec_time::numeric, 2)                      AS mean_ms,
    round(stddev_exec_time::numeric, 2)                    AS stddev_ms,
    rows / greatest(calls, 1)                              AS rows_per_call,
    round(100.0 * shared_blks_hit /
          nullif(shared_blks_hit + shared_blks_read, 0), 1) AS cache_pct,
    round(total_exec_time::numeric /
          sum(total_exec_time) OVER () * 100, 1)           AS pct_of_total,
    left(query, 90)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- Order by TOTAL, not mean (SQL chapter 14). Then read three more columns:
--   stddev_ms high relative to mean  ->  unstable plan, or parameter sniffing
--                                        (chapter 1), or lock waits
--   rows_per_call very high          ->  fetching rows to filter in the app
--   cache_pct low                    ->  this query is going to disk

-- Settings worth knowing:
--   pg_stat_statements.max = 10000     how many query shapes to track
--   pg_stat_statements.track = top     top-level only, or 'all' for nested
--   pg_stat_statements.track_utility = off   ignore DDL and VACUUM

SELECT pg_stat_statements_reset();     -- before a load test, or after a fix
Snapshot it, do not just query it

The view holds cumulative totals since the last reset, so "what got slower last Tuesday" is unanswerable from a single read. Capture the whole view into a table on a schedule — every fifteen minutes is plenty — and you can diff any two points in time. That turns it from a leaderboard into a time series, and it is the difference between "this query is slow" and "this query became slow at 14:20 on the day of the deploy". Several monitoring tools do this for you; a cron job and an INSERT … SELECT also works.

Evaluating one

  • Is it available where you run? Managed services allow a fixed list. Check before designing around it — this is the constraint that catches people, and it can force a migration.
  • Does it require shared_preload_libraries? Then adding it needs a restart, and so does removing it.
  • How does it affect major upgrades? A C extension must be compiled for the new major version and available before you can upgrade (chapter 16). An extension that lags Postgres releases pins your cluster.
  • Who maintains it? Check the commit history and whether it supports the current major version. An extension abandoned two releases ago is a future upgrade blocker.
  • What is the licence? Some widely-used extensions are not open source in the way people assume, and some have changed licence.
  • What does it cost at runtime? Background workers, WAL volume, shared memory, per-query overhead.
  • Can you remove it? An extension that owns a column type is very hard to drop once data uses it.
Extensions are the main thing that blocks a major upgrade

Upgrading from 15 to 16 requires every installed extension to have a build for 16 on the new server before pg_upgrade will proceed. A popular extension usually ships within weeks; a niche or abandoned one may never. Teams discover this when they are already behind on versions and now cannot move at all without removing a dependency that is embedded in the schema. Before adopting an extension, check how quickly it supported the last two major releases. That number predicts your upgrade freedom for years.

Managing them

install, version, schema, remove
-- Put extensions in their own schema so they do not clutter public and are
-- easy to see in a dump.
CREATE SCHEMA IF NOT EXISTS ext;
CREATE EXTENSION pg_trgm WITH SCHEMA ext;
-- then add ext to search_path, or qualify calls

-- Extensions have their own versions, independent of the server version:
SELECT extname, extversion FROM pg_extension;
ALTER EXTENSION pg_stat_statements UPDATE;            -- to the latest available
ALTER EXTENSION pg_stat_statements UPDATE TO '1.10';  -- to a specific one

-- Installing the binary does NOT enable it in a database. CREATE EXTENSION is
-- per database, which is why a new database created later is missing it.
-- Add it to template1 so every future database inherits it:
\c template1
CREATE EXTENSION pg_stat_statements;

-- What an extension owns, before you try to drop it:
SELECT classid::regclass, objid::regclass
FROM pg_depend
WHERE refobjid = (SELECT oid FROM pg_extension WHERE extname = 'pg_trgm');

DROP EXTENSION pg_trgm;            -- fails if anything depends on it
DROP EXTENSION pg_trgm CASCADE;    -- drops the indexes and columns too.
                                   -- Read the notice output before confirming

The real comparison is not feature for feature

A dedicated system usually wins on its own axis, and that is not the whole comparison. A second datastore means another thing to back up, monitor, upgrade, secure and page someone about at 3am — plus a consistency boundary where the two can now disagree, and code to reconcile them. One database you understand deeply beats four you understand partially, especially with a small team. Add the specialised system when the Postgres answer has been measured and found wanting for your data, not when a comparison table says it would be.

the queue, since it is the most common case
CREATE TABLE jobs (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind        text        NOT NULL,
    payload     jsonb       NOT NULL,
    run_after   timestamptz NOT NULL DEFAULT now(),
    attempts    int         NOT NULL DEFAULT 0,
    locked_at   timestamptz
) WITH (fillfactor = 70);            -- heavy updates: help HOT (chapter 5)

CREATE INDEX ON jobs (run_after) WHERE locked_at IS NULL;   -- partial: tiny

-- Each worker claims a batch. SKIP LOCKED means workers never contend.
WITH claimed AS (
    SELECT id FROM jobs
    WHERE locked_at IS NULL AND run_after <= now()
    ORDER BY run_after
    LIMIT 10
    FOR UPDATE SKIP LOCKED
)
UPDATE jobs j SET locked_at = now(), attempts = attempts + 1
FROM claimed c WHERE j.id = c.id
RETURNING j.*;

-- Why this is genuinely good: the job and the business data commit in ONE
-- transaction, so you cannot enqueue work for a row that then rolls back —
-- the dual-write problem that a separate queue always has.
--
-- Two things to watch: this table churns hard, so give it aggressive
-- autovacuum settings (chapter 3), and delete or archive completed rows
-- rather than letting it grow forever.
pg_cron runs on the primary, and that matters at failover

Jobs are scheduled on whichever node is the primary. After a failover the new primary must have pg_cron configured with the same schedule, or your nightly work silently stops — and if the old primary comes back as a standby with cron still enabled, you can get duplicate runs. Configure it identically on every node, make every job idempotent, and add a check that each scheduled job actually ran. The same reasoning applies to any background worker: ask what happens to it during a failover, because chapter 14 is going to move the primary.

The short version

  1. Install pg_stat_statements and auto_explain on day one — they need a restart, which you cannot do during an incident.
  2. Order pg_stat_statements by total time, then read stddev, rows-per-call and cache hit rate.
  3. Snapshot the view on a schedule so you can diff two points in time. Cumulative totals cannot answer "what changed on Tuesday".
  4. CREATE EXTENSION is per database — add it to template1 so new databases inherit it.
  5. Extensions are the main thing that blocks a major upgrade. Check how fast one supported the last two releases before adopting it.
  6. pg_repack instead of VACUUM FULL; hypopg to test an index without building it.
  7. "Just use Postgres" is often right — a second datastore is another thing to back up, monitor, upgrade and reconcile.
  8. Ask what happens to every background worker at failover, pg_cron especially.
