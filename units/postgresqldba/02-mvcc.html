Chapter 02 · The engine

MVCC

Postgres never overwrites a row in place. An update writes a new version and marks the old one dead, and every transaction sees whichever version was current when it started. That single mechanism gives you lock-free reads — and produces the bloat, the long-transaction problems and the wraparound alarm in the next chapter.

tuple versions xmin and xmax snapshots visibility

Rows are versions

What Postgres stores is not a row but a tuple — one version of a row. Every tuple carries two hidden system columns that say which transactions bracket its life.

the hidden columns you can select
SELECT xmin, xmax, ctid, * FROM accounts WHERE id = 1;

--  xmin  | xmax |  ctid  | id | balance
-- -------+------+--------+----+---------
--   4812 |    0 | (0,1)  |  1 |   100
--
--   xmin  the transaction that CREATED this version
--   xmax  the transaction that DELETED or superseded it; 0 means still live
--   ctid  physical location: (page number, item number within the page)

UPDATE accounts SET balance = 150 WHERE id = 1;
SELECT xmin, xmax, ctid, * FROM accounts WHERE id = 1;

--  xmin  | xmax |  ctid  | id | balance
-- -------+------+--------+----+---------
--   4813 |    0 | (0,2)  |  1 |   150      <- a NEW tuple at a new location
--
-- The old tuple at (0,1) is still on disk, now with xmax = 4813. It is invisible
-- to new transactions and it still occupies space until vacuum reclaims it.
-- An UPDATE in Postgres is physically an insert plus a mark.
Every consequence in this unit starts here

An UPDATE writes a whole new tuple, even if you changed one boolean. That means: updates are as expensive as inserts; every index on the table may need a new entry (chapter 5's HOT updates are the exception); the table grows until vacuum reclaims the dead versions; and a DELETE frees no space immediately. If you internalise one thing from this chapter, make it that a row's history is physically present in the table until something cleans it up.

Snapshots and visibility

the visibility rule, in full
A tuple is VISIBLE to a snapshot if:

    xmin is committed
    AND xmin is not still in progress according to the snapshot
    AND (xmax is 0, OR xmax aborted, OR xmax is still in progress /
         started after the snapshot)

A snapshot is three things captured when the statement (or transaction, under
REPEATABLE READ) begins:

    xmin       the oldest transaction still running
    xmax       the next xid to be assigned
    xip_list   the transactions in progress right now

Anything with an xid below the snapshot's xmin is settled — committed or
aborted, and everyone agrees. Anything at or above xmax started later and is
invisible. The in-progress list handles the middle.

    SELECT pg_current_snapshot();     -- 4812:4820:4815,4817
    --                                    xmin:xmax:xip_list
READ COMMITTED takes a new snapshot per statement

Under READ COMMITTED — the default — each statement gets a fresh snapshot, which is exactly why the SQL unit's non-repeatable read is possible: two identical queries in one transaction can see different data. Under REPEATABLE READ the snapshot is taken once at the first statement and held for the whole transaction, so the transaction sees one consistent instant. That difference is the entire implementation of the isolation levels — the same visibility rule, applied against a snapshot taken at a different moment.

Readers do not block writers

What MVCC buys

  • A SELECT never waits for an UPDATE, and never blocks one
  • A long analytical query sees a consistent instant without holding read locks
  • Rollback is nearly free — the new tuples are simply never visible
  • No read locks to escalate, and no lock-manager contention on reads
  • Consistent backups without stopping writes (chapter 12)

What it costs

  • Dead tuples accumulate and must be cleaned up (chapter 3)
  • Tables and indexes bloat, and bloat is not automatically reclaimed to the OS
  • UPDATE writes a full new tuple, and often new index entries
  • count(*) cannot read a stored counter — visibility is per transaction
  • Long transactions hold back cleanup for the entire cluster
  • Transaction ids are finite, so freezing is mandatory
One long transaction degrades everything

Vacuum may only remove a dead tuple once no running transaction could still need to see it — so the oldest open transaction in the cluster sets the horizon for cleanup everywhere. A session left idle in transaction for two hours means two hours of dead tuples on every busy table, in every database, accumulating with nothing able to reclaim them. A forgotten psql window, a crashed worker, an analytics query with no timeout: any of them is enough. This is the single most common cause of sudden unexplained bloat, and chapter 3 is largely about detecting it.

finding the transaction holding everything back
SELECT pid,
       now() - xact_start        AS transaction_age,
       now() - state_change      AS in_state_for,
       state,
       backend_xmin,
       left(query, 80)           AS query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC
LIMIT 10;

-- The top row is the one holding the horizon. Note that "idle in transaction"
-- is as damaging as a running query — the snapshot is held either way, and
-- the session is not even doing anything with it.

-- Two settings that prevent this entirely:
--   idle_in_transaction_session_timeout = '5min'
--   statement_timeout                   = '60s'    (per role, not globally)
--
-- Replication slots and long-running queries on a hot standby with
-- hot_standby_feedback = on hold the horizon back too. Chapter 13.

Transaction ids are 32 bits

the finite counter, and how it is made to work
-- xids are 32-bit, so there are about 4.2 billion of them and they WRAP.
-- Comparison is modular: for any xid, half the space is "in the past" and half
-- is "in the future". If a tuple's xmin fell more than 2 billion transactions
-- behind, it would suddenly appear to be in the future and become invisible —
-- data loss, silently.
--
-- The fix is FREEZING. Vacuum marks tuples old enough that everyone can see
-- them as frozen, and a frozen tuple is visible to all transactions
-- regardless of xid comparison. Its xmin no longer matters.

SELECT datname,
       age(datfrozenxid)                        AS xid_age,
       2000000000 - age(datfrozenxid)           AS xids_remaining,
       round(100.0 * age(datfrozenxid) / 2000000000, 1) AS pct_to_limit
FROM pg_database
ORDER BY xid_age DESC;

-- Postgres warns from about 200 million behind autovacuum_freeze_max_age,
-- and at 3 million remaining it REFUSES NEW WRITES to protect itself.
-- That is a full outage, and it is entirely preventable — the number above
-- climbs visibly for weeks first.
--
-- 64-bit xids have been under discussion for years and are not here yet.
-- Chapter 3 covers keeping this number down.

Row locks live in the tuple

why Postgres never runs out of row locks
-- Locking a row sets xmax on the tuple with a flag saying "locked, not
-- deleted". The lock is stored IN THE ROW, so there is no lock table to size
-- and no escalation from row locks to a table lock.
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- Consequences:
--   * you can lock ten million rows without exhausting anything
--   * lock waits are per row, resolved by the waiter examining the tuple
--   * SELECT FOR UPDATE writes to the page, so it dirties buffers and
--     generates WAL — a "read-only" query that is not read-only
--   * several sessions holding FOR SHARE on one row need a multixact, an
--     extra structure that has its own wraparound to worry about
--
-- TABLE-level locks are different: they live in shared memory, sized by
-- max_locks_per_transaction × max_connections. A transaction touching
-- thousands of partitions can exhaust that, and the error names it directly.

The counting consequence

why count(*) is not free, and what to do
-- There is no stored row count, because "how many rows" has no single answer:
-- it depends on the asking transaction's snapshot. So count(*) must examine
-- every candidate tuple and test its visibility.
SELECT count(*) FROM orders;              -- scans the table or an index

-- An index-only scan helps, and only when the visibility map says a page is
-- all-visible — otherwise the heap must be consulted anyway (chapter 3).
-- Which is why an aggressively vacuumed table counts much faster than a
-- neglected one, and why the same query can be fast on Monday and slow on
-- Friday with no change to the data volume.

-- The estimate, accurate to a few percent and instant:
SELECT reltuples::bigint FROM pg_class WHERE relname = 'orders';

-- Nearly always sufficient. Chapter 14 of the SQL unit covers the rest.

How other databases do it

SystemApproachTrade
PostgreSQLOld versions kept in the table itselfCheap rollback and fast reads; bloat and vacuum
MySQL / InnoDBOld versions in a separate undo logTables stay compact; rollback is expensive and long readers make undo grow
OracleUndo tablespaceSimilar to InnoDB; the classic "snapshot too old" error when undo is recycled
SQL ServerLocking by default; versions in tempdb with RCSI enabledReaders block writers unless you opt in; tempdb becomes a bottleneck when you do
Every design has a bill. Postgres's is paid by vacuum; InnoDB's is paid by the undo log and by rollback cost. Neither is a mistake, and knowing which bill you are paying is what makes the operational advice make sense.
The practical rules that follow from this chapter

Keep transactions short — the oldest one holds back cleanup cluster-wide. Update fewer columns and fewer rows, because every update writes a new tuple. Set idle_in_transaction_session_timeout, today, on every cluster. Batch bulk changes (SQL chapter 9) so no single statement creates millions of dead tuples at once. Watch age(datfrozenxid). Everything in chapter 3 is the enforcement of these.

The short version

  1. Postgres stores tuples, not rows — versions bracketed by xmin and xmax.
  2. An UPDATE is physically an insert plus a mark. The old version stays on disk until vacuum removes it.
  3. A snapshot is xmin, xmax and the in-progress list; the isolation levels differ only in when it is taken.
  4. Readers never block writers — which is what MVCC buys — and dead tuples are what it costs.
  5. The oldest open transaction in the cluster holds back cleanup everywhere. idle in transaction is as damaging as a running query.
  6. Transaction ids are 32-bit and wrap. Freezing prevents it, and neglect causes a full write outage.
  7. Row locks live in the tuple, so they never run out — but FOR UPDATE writes to the page.
  8. There is no stored row count because visibility is per transaction. Estimate from reltuples.
