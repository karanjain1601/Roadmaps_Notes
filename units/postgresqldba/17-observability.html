Postgres exposes an unusual amount about itself through ordinary SQL. The problem is not access to data — it is knowing which dozen numbers predict trouble, and having them recorded before the trouble arrives.

the progress views, which are underused
-- "Is this vacuum going to finish?" — answerable, rather than a guess.
SELECT p.pid, c.relname, p.phase,
       pg_size_pretty(p.heap_blks_total * 8192)      AS total,
       pg_size_pretty(p.heap_blks_scanned * 8192)    AS scanned,
       round(100.0 * p.heap_blks_scanned /
             nullif(p.heap_blks_total, 0), 1)        AS pct,
       p.index_vacuum_count
FROM pg_stat_progress_vacuum p JOIN pg_class c ON c.oid = p.relid;

-- index_vacuum_count above 1 means maintenance_work_mem was too small to
-- track all the dead tuples in one pass, so it is walking every index
-- repeatedly. That single number often explains a vacuum taking hours
-- (chapters 3 and 8).

SELECT * FROM pg_stat_progress_create_index;   -- CREATE INDEX / REINDEX
SELECT * FROM pg_stat_progress_copy;           -- bulk loads
SELECT * FROM pg_stat_progress_basebackup;     -- backups
SELECT * FROM pg_stat_progress_cluster;        -- CLUSTER / VACUUM FULL
SELECT * FROM pg_stat_progress_analyze;
Counters are cumulative, so record them over time

Nearly every statistic here is a total since the last reset. A single reading of n_dead_tup or checkpoints_req tells you almost nothing; the rate of change is the signal. Scrape these into a time-series system on a schedule — Prometheus with postgres_exporter is the common answer — and suddenly "when did this start" becomes answerable. Without history, every incident begins with reconstructing what normal looked like, from memory, under pressure.

Wait events

not "what is slow" but "what is it waiting for"
SELECT wait_event_type, wait_event, state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
GROUP BY 1,2,3
ORDER BY count(*) DESC;

--  wait_event_type    means
--  ---------------    -----------------------------------------------
--  (null)             actually running on CPU
--  Lock               waiting for a heavyweight lock — another transaction
--  LWLock             internal contention, often buffer or WAL related
--  IO                 reading or writing. DataFileRead is the common one
--  Client             waiting for the application  <- ClientRead while
--                     'idle in transaction' is the classic problem
--  IPC                waiting for another backend, e.g. a parallel worker
--  Timeout            deliberate sleeping, e.g. vacuum's cost delay
--
-- Sampling this every second and aggregating gives you a poor man's
-- always-on profiler. It answers "the database was slow at 14:20 — doing
-- what?" which no other view does.
--
-- pg_wait_sampling does this properly if you can install it; a cron job
-- inserting the query above into a table works and costs nothing.

Logging

a configuration that is useful and not overwhelming
# Without a proper prefix, log analysis is guesswork and pgBadger cannot
# parse timings at all. This is the single most important logging setting.
log_line_prefix = '%m [%p] %q%u@%d %a %h '

log_min_duration_statement = '1s'      # slow queries
log_checkpoints = on                   # PG15+ default
log_autovacuum_min_duration = '1s'     # chapter 3
log_lock_waits = on                    # anything waiting past deadlock_timeout
log_temp_files = '10MB'                # work_mem too small for these queries
log_connections = off                  # noisy behind a pooler
log_disconnections = off

log_destination = 'stderr'
logging_collector = on
log_rotation_age = '1d'
log_rotation_size = '500MB'

# Or, for anything feeding a log aggregator:
log_destination = 'jsonlog'            # PG15+, structured and parseable

# LEAVE OFF unless actively debugging:
#   log_statement = 'all'
# It logs every statement including parameter values — a volume problem and a
# data-protection problem both, since passwords and personal data end up in a
# system with weaker access control than the database (SQL chapter 15).
Set application_name from every service

It costs nothing, it appears in pg_stat_activity and in every log line if your prefix includes %a, and it converts "some backend is running this query" into "the orders API is running this query" — which tells you what to roll back. Set it in the connection string (application_name=orders-api) or the PGAPPNAME environment variable. During an incident it is frequently the difference between a five-minute diagnosis and an hour of asking around.

Log analysis

pgBadger, and what to look at first
pgbadger -j 4 -o report.html /var/log/postgresql/postgresql-*.log

# It produces an HTML report with, in rough order of usefulness:
#   * slowest queries, normalised and ranked
#   * queries by total time — the same argument as pg_stat_statements
#   * temp file usage per query        -> work_mem candidates (chapter 8)
#   * lock waits, with the blocking query
#   * checkpoint behaviour over time   -> max_wal_size (chapter 4)
#   * autovacuum activity per table    -> tuning candidates (chapter 3)
#   * error and connection distribution by hour
#
# Run it nightly and keep the reports. It is complementary to
# pg_stat_statements rather than a replacement: pg_stat_statements aggregates
# everything cheaply, pgBadger shows individual slow executions WITH their
# parameter values and the surrounding context.
#
# Incremental mode, for a continuously updated report:
pgbadger --incremental --outdir /var/www/pgbadger /var/log/postgresql/*.log

Alert on causes with lead time, not only on symptoms

"The database is down" is a symptom, and by the time it fires you have an outage. Nearly every failure in this unit is preceded by a metric moving in one direction for days: transaction id age climbing, pg_wal growing, a slot retaining more each hour, bloat increasing, backup age advancing. Those give you days of warning and they are trivially cheap to watch. A dashboard of twelve leading indicators, reviewed weekly, prevents more incidents than any amount of alerting on the outage itself.

What to record before you need it

  • pg_stat_statements snapshotted every 15 minutes into a table, so you can diff two points in time (chapter 10).
  • Wait events sampled every second, or as close as you can manage.
  • The twelve dashboard metrics, as a time series with at least a year of history.
  • Plans for your critical queries, captured before every upgrade and every major deploy.
  • Table and index sizes weekly, so growth is a trend rather than a surprise.
  • Configuration in version control, so "what changed" has an answer.
  • Restore test duration, trended (chapter 12).
  • Failover test results, dated (chapter 14).
The question you will be asked is "when did this start"

Almost every serious investigation reduces to it, and answering requires history you were recording before anyone knew there was a problem. Everything in the list above is cheap to set up on a quiet afternoon and impossible to obtain retroactively. The single highest-value item is the pg_stat_statements snapshot: with it, "which query changed behaviour on Tuesday" is one query against your own table. Without it, it is guesswork and a deploy log.

The short version

  1. Twelve metrics predict nearly every incident in this unit. Watch causes with lead time, not just the outage.
  2. Counters are cumulative. Scrape them into a time series or a single reading tells you nothing.
  3. Wait events answer "waiting for what", which no other view does. Sample them continuously.
  4. The progress views turn "will this vacuum ever finish" into a number — and index_vacuum_count often explains why it is slow.
  5. log_line_prefix is the most important logging setting. Without it, log analysis is guesswork.
  6. Set application_name everywhere. It converts "some backend" into "which service to roll back".
  7. Keep log_statement = 'all' off — a volume problem and a data-protection problem.
  8. Snapshot pg_stat_statements on a schedule. "When did this start" is the question you will be asked.
