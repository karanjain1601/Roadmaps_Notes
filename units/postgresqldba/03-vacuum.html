Vacuum, bloat and freezing

Vacuum is the bill for chapter 2. It does three separate jobs that people conflate, it is the most common thing to be misconfigured on a busy cluster, and neglecting one of its jobs will eventually stop your database accepting writes.

dead tuples autovacuum visibility map wraparound

Three jobs, not one

JobWhat it doesIf it falls behind
Reclaim dead tuplesMarks space from dead versions as reusable within the tableBloat: the table grows, scans read more pages, cache holds less real data
Update the visibility mapMarks pages where every tuple is visible to everyoneIndex-only scans stop being index-only; vacuum itself gets slower
Freeze old tuplesMarks tuples as visible to all, independent of xid comparisonTransaction id wraparound. Eventually a forced shutdown
Also: it refreshes the free space map, and ANALYZE — a separate but co-scheduled task — updates the planner's statistics. A table nobody vacuums also has stale statistics, so bad plans and bloat usually arrive together.
Vacuum does not return space to the operating system

The most consistently misunderstood point. Plain VACUUM marks dead tuples' space as reusable by that table, so the file stays the same size and future inserts fill the gaps. It only shrinks the file if the dead space happens to be at the very end. To actually return space you need VACUUM FULL — which rewrites the whole table under an ACCESS EXCLUSIVE lock and needs room for a second copy — or pg_repack, which achieves the same without the long lock. For a table with steady write traffic, reusable space is the right outcome and shrinking is pointless; it will simply grow back.

Autovacuum, and why it falls behind

the trigger, and the problem with it
-- Autovacuum wakes a table when:
--   dead_tuples > autovacuum_vacuum_threshold
--                 + autovacuum_vacuum_scale_factor × reltuples
--
-- Defaults: threshold = 50, scale_factor = 0.2
--
--   10,000-row table  ->  vacuum at ~2,050 dead tuples.   Fine.
--   100M-row table    ->  vacuum at ~20,000,050 dead.     Not fine.
--
-- The scale factor is a PERCENTAGE, so the threshold grows with the table.
-- On a large busy table it means vacuum runs rarely and then has an enormous
-- amount to do — the opposite of what you want.

-- The standard fix: a small scale factor and a fixed threshold on big tables.
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,   -- 1% instead of 20%
    autovacuum_vacuum_threshold     = 1000,
    autovacuum_analyze_scale_factor = 0.005,
    autovacuum_vacuum_cost_delay    = 0       -- PG12+ default; do not raise it
);

-- PostgreSQL 13+ also vacuums on INSERTS alone, which finally handles
-- append-only tables that previously never got vacuumed and then hit
-- wraparound years later:
--   autovacuum_vacuum_insert_scale_factor, ..._insert_threshold

Measuring bloat

the first query to run on an unfamiliar cluster
SELECT
    schemaname || '.' || relname                       AS table,
    n_live_tup,
    n_dead_tup,
    round(100.0 * n_dead_tup /
          nullif(n_live_tup + n_dead_tup, 0), 1)       AS dead_pct,
    pg_size_pretty(pg_total_relation_size(relid))      AS total_size,
    last_autovacuum,
    last_autoanalyze,
    autovacuum_count
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 20;

-- What to look for:
--   dead_pct above ~20%          vacuum is not keeping up on this table
--   last_autovacuum NULL or old  it is not running at all — find out why
--   autovacuum_count = 0 on a busy table   check per-table settings, and
--                                          check for a long transaction
--
-- pg_stat_user_tables counters reset when the stats are reset or the cluster
-- is recreated, so check pg_stat_get_db_stat_reset_time() before concluding
-- that a table has "never" been vacuumed.
If vacuum is running and dead tuples are not falling, look for a long transaction

This is the signature of chapter 2's warning, and it confuses people because the logs show vacuum running normally and completing. It cannot remove tuples that a running transaction might still need, so it does its full scan, reports success, and reclaims nothing. Check pg_stat_activity for the oldest backend_xmin, check for abandoned replication slots (which hold the horizon just as effectively and are easier to forget), and check for prepared transactions left in doubt — SELECT * FROM pg_prepared_xacts is a table that should almost always be empty.

Index bloat

indexes bloat too, and they are worse
-- Every non-HOT update writes new index entries; vacuum removes the dead ones
-- but the B-tree pages stay half-empty. Over time an index can become several
-- times larger than it needs to be, and unlike a table it is not naturally
-- refilled by inserts unless the new keys happen to land in the gaps.

SELECT
    schemaname || '.' || indexrelname                  AS index,
    pg_size_pretty(pg_relation_size(indexrelid))       AS size,
    idx_scan
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;

-- Rebuild without a long lock (PG12+):
REINDEX INDEX CONCURRENTLY idx_orders_customer_status;
REINDEX TABLE CONCURRENTLY orders;         -- every index on the table

-- Before PG12, the equivalent was: CREATE INDEX CONCURRENTLY a new one,
-- DROP the old, rename. REINDEX CONCURRENTLY does exactly that internally,
-- and leaves an _ccnew index behind if it fails — check for those afterwards.

-- A rebuilt index on a heavily-updated table often halves in size, which
-- means it fits in cache again. This is one of the highest-return pieces of
-- routine maintenance available, and almost nobody schedules it.

The visibility map

two bits per page that decide index-only scans
-- The visibility map holds, per 8 KB page, two flags:
--   all-visible   every tuple on this page is visible to every transaction
--   all-frozen    every tuple is frozen (used to skip pages when freezing)
--
-- Consequences:
--   * an INDEX-ONLY SCAN can skip the heap only for all-visible pages.
--     Otherwise it must fetch the row to check visibility — which is why
--     EXPLAIN shows "Heap Fetches: 483920" on an index-only scan and the
--     query is not fast at all
--   * vacuum can SKIP all-frozen pages entirely, which is what makes
--     repeated vacuums on a mostly-static table cheap

SELECT relname,
       pg_size_pretty(pg_relation_size(oid))          AS heap,
       (pg_stat_get_live_tuples(oid))                 AS live,
       (SELECT count(*) FROM pg_visibility_map(oid) WHERE all_visible)
                                                      AS visible_pages
FROM pg_class WHERE relname = 'orders';   -- needs the pg_visibility extension

-- The practical rule: an index-only scan with high Heap Fetches means the
-- table needs vacuuming, not a different index.

Freezing and wraparound

the alarm that gives you weeks of warning
SELECT
    c.relname,
    age(c.relfrozenxid)                              AS xid_age,
    round(100.0 * age(c.relfrozenxid) /
          current_setting('autovacuum_freeze_max_age')::numeric, 1) AS pct_to_forced,
    pg_size_pretty(pg_total_relation_size(c.oid))    AS size
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','m','t') AND n.nspname NOT IN ('pg_catalog','information_schema')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 20;

-- The thresholds, in order:
--   autovacuum_freeze_max_age (default 200M)
--       an ANTI-WRAPAROUND autovacuum starts, and unlike a normal one it
--       cannot be cancelled by a conflicting lock request — it will block
--       your ALTER TABLE and there is nothing to do but wait
--   ~40M remaining
--       loud warnings in the log on every commit
--   3M remaining
--       the database REFUSES NEW WRITES and must be brought up in single-user
--       mode to vacuum. This is a multi-hour outage on a large cluster.
--
-- It is preventable, it is visible for weeks, and the causes are always the
-- same three: a long transaction, an abandoned replication slot, or
-- autovacuum too slow to keep up on a large table.
Anti-wraparound vacuum is not politely cancellable

A normal autovacuum yields when another session requests a conflicting lock — which is why your ALTER TABLE usually succeeds even while a vacuum is running. An anti-wraparound vacuum does not yield, because the alternative is the cluster shutting down. So it will hold its lock through your migration window, on your largest table, for hours. This is how a wraparound problem first announces itself to most teams: not as an alarm, but as a deploy that mysteriously hangs. Watch age(relfrozenxid) and it never gets that far.

Per-table settings beat global ones

Most clusters have a handful of hot tables and hundreds of quiet ones. Tuning globally for the hot tables makes autovacuum thrash the quiet ones; tuning for the quiet ones lets the hot ones bloat. Set aggressive per-table storage parameters on the specific tables that need them — a queue table, a session table, anything with high churn — and leave the global defaults reasonable. ALTER TABLE … SET (autovacuum_vacuum_scale_factor = 0.01) is a targeted fix that does not affect anything else.

checking whether autovacuum is actually keeping up
-- Is it running right now, and on what?
SELECT pid, now() - xact_start AS running_for, query
FROM pg_stat_activity
WHERE query LIKE 'autovacuum:%'
ORDER BY xact_start;

-- "(to prevent wraparound)" in that query text is the signal to pay attention.

-- Turn on logging so you have history, not just a snapshot:
--   log_autovacuum_min_duration = '1s'
-- Then every vacuum taking over a second is in the log with its page counts,
-- its tuple counts, and — the useful part — how many dead tuples it could NOT
-- remove, which points straight at a long transaction.

-- Never do this:
--   autovacuum = off
-- It is occasionally suggested for bulk loads. Turning it off cluster-wide
-- and forgetting is one of the reliable routes to a wraparound outage.

The four things to do on any cluster you inherit

One: run the bloat query above and note anything over 20% dead. Two: run the relfrozenxid query and note anything over 100 million. Three: set log_autovacuum_min_duration = '1s' so you have history. Four: check for abandoned replication slots — SELECT slot_name, active, age(xmin) FROM pg_replication_slots — because an inactive slot silently holds back both vacuum and WAL cleanup, and it is the single most commonly forgotten cause of both bloat and a full disk.

The short version

  1. Vacuum does three separate jobs: reclaim dead tuples, maintain the visibility map, and freeze.
  2. Plain vacuum does not return space to the OS — and for a table with steady writes, reusable space is the right outcome.
  3. The default scale_factor of 0.2 is a percentage that scales the wrong way. Set 0.01 on large hot tables.
  4. Vacuum running but dead tuples not falling means a long transaction, a replication slot, or a prepared transaction.
  5. Indexes bloat too, and REINDEX CONCURRENTLY is high-return maintenance almost nobody schedules.
  6. An index-only scan with high Heap Fetches means the table needs vacuuming, not a different index.
  7. Anti-wraparound vacuum cannot be cancelled, and will hold its lock through your migration window.
  8. Prefer per-table settings for hot tables over global tuning that is wrong for everything else.
