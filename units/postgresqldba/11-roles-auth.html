Roles and authentication

Two separate systems that people conflate: pg_hba.conf decides whether you may connect at all, and the privilege system decides what you may do once inside. Getting the first wrong locks you out; getting the second wrong is quieter and worse.

pg_hba roles privileges ssl

pg_hba.conf

Host-based authentication. A list of rules matched top to bottom, first match wins — and if the matched rule rejects you, Postgres does not continue looking for a later rule that would have let you in.

Which rule matches A realistic pg_hba.conf. Describe a connection attempt and see which line decides it — and why the order matters.

—matched line
—method
the format, and the methods worth using
# TYPE  DATABASE  USER  ADDRESS         METHOD          [OPTIONS]
local   all       all                   peer
hostssl orders    app   10.0.1.0/24     scram-sha-256
host    all       all   0.0.0.0/0       reject

# TYPE:
#   local     Unix socket
#   host      TCP, with or without TLS
#   hostssl   TCP, TLS required          <- use this, not `host`
#   hostnossl TCP, TLS forbidden
#
# METHOD:
#   scram-sha-256  the default and correct choice for passwords
#   md5            legacy, weak. Migrate off it
#   peer           local only: the OS username must match the database role
#   cert           client TLS certificate. Strong, more to manage
#   ldap / gss     enterprise directory integration
#   trust          NO AUTHENTICATION AT ALL
#   reject         refuse, and stop matching

SELECT * FROM pg_hba_file_rules;    -- the parsed file, with any errors
SELECT pg_reload_conf();            -- reload; no restart needed
Two entries to check on every cluster you inherit

trust means anyone who can reach the port becomes any role they name, with no password. It appears in default configurations for local connections and in a great many Docker images and quickstart guides, and it survives into production more often than anyone would like. md5 is the old password method and is weak by modern standards; scram-sha-256 has been the default since PostgreSQL 14 and migrating requires each user to set their password again after changing password_encryption. Grep for both, today.

Roles

there are no users, only roles
-- CREATE USER is CREATE ROLE ... LOGIN. That is the only difference.
-- A role with LOGIN is what you might call a user; one without is a group.

CREATE ROLE readonly NOLOGIN;                          -- a group
CREATE ROLE analyst LOGIN PASSWORD '…' IN ROLE readonly;

GRANT USAGE ON SCHEMA public TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;

-- The pattern worth adopting: grant privileges to GROUP roles, and grant
-- group membership to login roles. Then onboarding is one GRANT and
-- offboarding is one REVOKE, rather than an audit of every table.

-- Attributes:
--   LOGIN / NOLOGIN         may connect
--   SUPERUSER               bypasses all permission checks. Almost never
--   CREATEDB / CREATEROLE   CREATEROLE was dangerously broad before PG16
--   REPLICATION             may start a replication connection
--   BYPASSRLS               ignores row-level security policies
--   CONNECTION LIMIT n      cap concurrent connections (chapter 9)
--   VALID UNTIL '2026-12-31'  password expiry

-- Predefined roles, which remove most reasons to hand out SUPERUSER:
--   pg_monitor            read all the statistics views
--   pg_read_all_data      SELECT on everything (PG14+)
--   pg_write_all_data     INSERT/UPDATE/DELETE on everything
--   pg_signal_backend     cancel and terminate other backends
--   pg_maintain           VACUUM, ANALYZE, REINDEX (PG17+)
GRANT pg_monitor TO monitoring;
The application should not own its schema

The SQL unit made this point; here is the Postgres-specific reason it matters. The role that owns a table can DROP it, ALTER it and change its permissions — and most applications connect as the owner because that is what the quickstart did. Separate them: an owner role that runs migrations from CI, and a read-write role the application uses which has SELECT, INSERT, UPDATE, DELETE and nothing else. Then no injection, no compromised dependency and no accidental script can alter the schema, and the blast radius of an application compromise is bounded by DML.

The default privileges trap

why the grant you ran last month does not cover the new table
-- This grants on tables that exist RIGHT NOW. It is not a standing rule.
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;

-- The next migration creates a table, and readonly cannot see it. The symptom
-- is a permission error in production hours after a deploy, on one endpoint.

-- The standing rule. Note FOR ROLE: default privileges apply to objects
-- created BY A PARTICULAR ROLE, so this must name whoever runs migrations.
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO readonly;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO app_rw;

-- Getting FOR ROLE wrong is the commonest mistake here: the defaults are
-- recorded against the creating role, so a rule set without FOR ROLE applies
-- only to objects YOU create.
SELECT * FROM pg_default_acl;

-- And the one people miss entirely: on PostgreSQL 14 and earlier, PUBLIC can
-- CREATE objects in the public schema. Anyone who can connect can create a
-- table there. Fixed by default in PG15; revoke it explicitly on older ones.
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON DATABASE orders FROM PUBLIC;

What a role can actually do

auditing privileges, which is harder than granting them
-- Everything a role has been granted, transitively through group membership:
SELECT table_schema, table_name, privilege_type
FROM information_schema.table_privileges
WHERE grantee = 'analyst'
ORDER BY table_schema, table_name;

-- Ask directly, which accounts for inheritance and is the reliable check:
SELECT has_table_privilege('analyst', 'orders', 'SELECT');
SELECT has_schema_privilege('analyst', 'public', 'USAGE');
SELECT pg_has_role('analyst', 'readonly', 'MEMBER');

-- Who is a member of what:
SELECT r.rolname AS role, m.rolname AS member_of
FROM pg_auth_members am
JOIN pg_roles r ON r.oid = am.member
JOIN pg_roles m ON m.oid = am.roleid
ORDER BY 1, 2;

-- Roles with attributes worth reviewing:
SELECT rolname, rolsuper, rolcreaterole, rolcreatedb,
       rolreplication, rolbypassrls, rolconnlimit, rolvaliduntil
FROM pg_roles
WHERE rolsuper OR rolcreaterole OR rolreplication OR rolbypassrls
ORDER BY rolname;
-- Run this quarterly. Superuser and BYPASSRLS accumulate quietly.

\du+       -- the psql shorthand for the same overview
Schema USAGE is a separate privilege and it is easy to miss

GRANT SELECT ON ALL TABLES is not enough on its own. Without USAGE on the containing schema the role cannot reach the tables at all, and the error — "permission denied for schema" — reads like a table problem to anyone in a hurry. The same applies to sequences: a role with INSERT on a table using an identity column also needs USAGE on its sequence, or every insert fails. Both are one extra GRANT, and both are the reason a permissions change "did not work".

TLS

encrypt everything, and verify the server
# postgresql.conf
ssl = on
ssl_cert_file = '/etc/ssl/certs/server.crt'
ssl_key_file  = '/etc/ssl/private/server.key'
ssl_ca_file   = '/etc/ssl/certs/ca.crt'      # required for client certs
ssl_min_protocol_version = 'TLSv1.2'

# pg_hba.conf — hostssl, so a plaintext attempt is refused rather than allowed
hostssl  orders  app  10.0.1.0/24  scram-sha-256

# Client side, and this is the part that is usually wrong:
#   sslmode=disable      no TLS
#   sslmode=allow        TLS only if the server insists
#   sslmode=prefer       DEFAULT — TLS if available, silently falls back
#   sslmode=require      TLS, but the certificate is NOT checked
#   sslmode=verify-ca    checks the certificate chain
#   sslmode=verify-full  checks the chain AND the hostname   <- use this
#
# `require` encrypts against passive eavesdropping and does nothing against an
# active attacker, because it accepts any certificate. Only verify-full
# authenticates the server you are actually talking to.

SELECT ssl, version, cipher, client_dn
FROM pg_stat_ssl JOIN pg_stat_activity USING (pid)
WHERE backend_type = 'client backend';
-- Anything with ssl = false is a client to fix.
sslmode=require is not verification

It is the setting most people reach for and it stops at encryption: the client accepts whatever certificate it is offered, so anything that can intercept the connection can present its own and read everything. verify-full checks the chain against a CA and that the hostname matches. The reason require is so common is that verify-full fails loudly when the CA bundle is not configured, and require does not — so it gets chosen to make an error go away. Configure the CA bundle and use verify-full, including inside your private network.

Passwords and rotation

managing credentials without downtime
-- Make sure new passwords use SCRAM before you set any.
SHOW password_encryption;                 -- want scram-sha-256
ALTER SYSTEM SET password_encryption = 'scram-sha-256';
SELECT pg_reload_conf();
-- Existing md5 passwords stay md5 until each is set again:
ALTER ROLE app PASSWORD 'new-password';

-- Find who is still on the old scheme:
SELECT rolname, CASE WHEN rolpassword LIKE 'SCRAM-SHA-256%' THEN 'scram'
                     WHEN rolpassword LIKE 'md5%' THEN 'md5' ELSE 'none' END
FROM pg_authid WHERE rolcanlogin;

-- Never type a password into psql: it lands in ~/.psql_history and in the
-- server log if statement logging is on. Use \password, which computes the
-- hash client-side and sends only the hash:
\password app

-- Zero-downtime rotation, since ALTER ROLE ... PASSWORD takes effect at once
-- and breaks anything still holding the old one:
--   1. create app_v2 with the new password, IN ROLE the same groups
--   2. roll the application over to app_v2
--   3. confirm no sessions remain as app in pg_stat_activity
--   4. DROP ROLE app
-- Better still: short-lived credentials from a secrets manager, or IAM
-- authentication where your platform supports it — then rotation is automatic
-- and there is no long-lived secret to leak.

-- Expiry, so a forgotten credential does not live forever:
ALTER ROLE contractor VALID UNTIL '2026-06-30';

A working role layout

the whole thing, in one place
-- Groups: privileges attach here.
CREATE ROLE app_owner NOLOGIN;                 -- owns the schema
CREATE ROLE app_rw    NOLOGIN;                 -- DML only
CREATE ROLE app_ro    NOLOGIN;                 -- SELECT only

-- Logins: no privileges of their own, only membership.
CREATE ROLE svc_orders  LOGIN PASSWORD '…' IN ROLE app_rw;
CREATE ROLE svc_reports LOGIN PASSWORD '…' IN ROLE app_ro;
CREATE ROLE migrations  LOGIN PASSWORD '…' IN ROLE app_owner;
CREATE ROLE monitoring  LOGIN PASSWORD '…';
GRANT pg_monitor TO monitoring;

-- Ownership and grants.
ALTER SCHEMA public OWNER TO app_owner;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON DATABASE orders FROM PUBLIC;

GRANT USAGE ON SCHEMA public TO app_rw, app_ro;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_rw;
GRANT SELECT                          ON ALL TABLES IN SCHEMA public TO app_ro;
GRANT USAGE, SELECT ON ALL SEQUENCES  IN SCHEMA public TO app_rw;

-- The standing rules, so tomorrow's tables are covered.
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO app_ro;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO app_rw;

-- Per-role settings, which is the right scope for most of chapter 8.
ALTER ROLE svc_orders  SET statement_timeout = '30s';
ALTER ROLE svc_reports SET statement_timeout = '30min';
ALTER ROLE svc_reports SET work_mem = '256MB';
ALTER ROLE monitoring  SET CONNECTION LIMIT 5;

A review checklist

  • No trust in pg_hba.conf, including for local connections.
  • No md5; password_encryption = scram-sha-256 and every password reset.
  • hostssl, not host, and clients using verify-full.
  • A final reject rule, so an unmatched connection is refused explicitly rather than by luck.
  • The application does not own its schema, and migrations run as a different role from CI.
  • ALTER DEFAULT PRIVILEGES … FOR ROLE set, naming whoever runs migrations.
  • REVOKE CREATE ON SCHEMA public FROM PUBLIC on anything before PostgreSQL 15.
  • Superuser, CREATEROLE, REPLICATION and BYPASSRLS audited quarterly.
  • Monitoring uses pg_monitor, not superuser.

The short version

  1. pg_hba.conf is matched top to bottom, first match wins — a matching reject stops the search.
  2. Grep for trust and md5 today. Both survive from quickstarts into production.
  3. There are no users, only roles. Privileges on groups, membership on logins.
  4. The application should not own its schema. Migrations run as a separate role from CI.
  5. GRANT … ON ALL TABLES covers today's tables. ALTER DEFAULT PRIVILEGES … FOR ROLE covers tomorrow's.
  6. Schema USAGE and sequence USAGE are separate grants, and their absence looks like a table problem.
  7. sslmode=require does not verify anything. Use verify-full, including internally.
  8. Rotate by creating a new role and switching, not by changing a password in place.
