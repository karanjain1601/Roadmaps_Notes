Backup and recovery

The only property of a backup that matters is whether you have restored from it. Everything else in this chapter — the tools, the schedules, the retention — is in service of making that restore fast enough and recent enough when you need it.

logical vs physical pitr rpo and rto testing

Two kinds, for two different jobs

What it isSQL statements or a custom archiveA byte copy of the data directory
Restore granularityA single table, or one databaseThe whole cluster only

Most production clusters want both: physical for recovery, and periodic logical dumps for the case where someone dropped one table and you would rather not roll the whole cluster back.
What your strategy actually gives you RPO is how much data you lose; RTO is how long you are down. Pick a strategy and see both.

Logical backups

pg_dump, with the options that matter
# Custom format. Compressed, and restorable selectively — always use -Fc or -Fd
# rather than plain SQL, unless you specifically need a readable file.
pg_dump -Fc -Z 6 -d orders -f orders.dump

# Directory format allows PARALLEL dump and restore. On a large database this
# is the difference between hours and minutes.
pg_dump -Fd -j 8 -d orders -f /backup/orders/

# Restore, also parallel, into a fresh database
createdb orders_restored
pg_restore -d orders_restored -j 8 /backup/orders/

# Restore ONE table out of a full dump — the thing physical backups cannot do
pg_restore -d orders -t line_items /backup/orders/

# See what is in an archive without restoring it
pg_restore -l /backup/orders/ | less

# Roles and tablespaces are CLUSTER-wide and are NOT in pg_dump. Without this
# your restore has no users and every GRANT fails:
pg_dumpall --globals-only -f globals.sql
pg_dump holds a long transaction

It takes a snapshot at the start and holds it for the entire dump, so that the output is consistent. On a 500 GB database that is hours — during which vacuum cannot remove any tuple dead after the snapshot began, anywhere in the cluster (chapters 2 and 3). Overnight dumps of large databases are a common and completely unsuspected cause of daytime bloat. Run them from a replica if you can, or accept the cost knowingly and watch the dead-tuple counts afterwards.

Physical backups and PITR

1 · Base backupA byte copy of the data directory, taken while the server runs
↓
2 · WAL archivingEvery WAL segment copied off as it fills — this is what makes PITR possible
↓
3 · Restore the base backupCopy it into place on the target machine
↓
4 · Replay WAL forwardFrom the backup's position to any moment you choose
↓
5 · Stop at the target and promoteA timestamp, an LSN, a named restore point, or a transaction id
the built-in tools
# postgresql.conf
#   wal_level = replica
#   archive_mode = on
#   archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
#   archive_timeout = '300s'    # force a segment switch, so RPO is bounded
#                               # even when write traffic is light

# A base backup
pg_basebackup -D /backup/base -Ft -z -Xs -P -c fast

#   -Ft  tar format      -z  compress
#   -Xs  stream WAL alongside, so the backup is self-consistent on its own
#   -c fast  checkpoint immediately rather than waiting for the spread

# Restore to a point in time:
#   1. stop the server, move the old data directory aside
#   2. unpack the base backup into $PGDATA
#   3. postgresql.conf:
#        restore_command = 'cp /archive/%f %p'
#        recovery_target_time = '2026-03-14 09:15:00+00'
#        recovery_target_action = 'promote'
#   4. touch $PGDATA/recovery.signal        # PG12+; recovery.conf is gone
#   5. start, and watch the log replay forward

# Name a point before a risky operation, so you can target it exactly:
SELECT pg_create_restore_point('before_the_big_migration');
#   recovery_target_name = 'before_the_big_migration'
Use a backup tool, not scripts

pg_basebackup plus cp works and it gives you no incremental backups, no parallelism, no compression tuning, no retention policy, no verification, and an archive_command that fails silently the first time the disk fills. pgBackRest and Barman handle all of it: parallel backup and restore, incremental and differential, checksum verification, retention, and PITR to a timestamp with one command. The setup cost is an afternoon. Rolling your own is one of those decisions that looks fine until the first real restore.

pgBackRest, since it is the usual answer
# /etc/pgbackrest/pgbackrest.conf
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2
repo1-retention-diff=6
repo1-cipher-type=aes-256-cbc          # encrypt the repository
process-max=8
compress-type=zst
start-fast=y

[orders]
pg1-path=/var/lib/postgresql/16/main

# postgresql.conf
#   archive_command = 'pgbackrest --stanza=orders archive-push %p'

pgbackrest --stanza=orders stanza-create
pgbackrest --stanza=orders check              # verifies archiving works NOW
pgbackrest --stanza=orders backup --type=full
pgbackrest --stanza=orders backup --type=incr
pgbackrest --stanza=orders info

# Point-in-time restore, in one command
pgbackrest --stanza=orders restore \
    --type=time --target="2026-03-14 09:15:00+00" --target-action=promote

# `check` is the important one. Run it on a schedule: it confirms the archive
# command actually works and the repository is reachable, which is exactly
# what silently stops being true.

Monitoring backups

the things that fail quietly
-- Is WAL archiving working? A rising failed_count with a stale
-- last_archived_time means WAL is accumulating on the primary and your
-- recovery window stopped advancing (chapter 4).
SELECT archived_count, last_archived_wal, last_archived_time,
       failed_count, last_failed_wal, last_failed_time,
       now() - last_archived_time AS since_last
FROM pg_stat_archiver;

-- How much WAL is waiting to be archived
SELECT count(*) AS pending
FROM pg_ls_dir('pg_wal/archive_status') f
WHERE f LIKE '%.ready';

-- Alert on all four of these:
--   backup age            > 1 day
--   last_archived_time    > 15 minutes ago
--   failed_count          rising at all
--   last successful RESTORE TEST  > 1 month ago
--
-- The fourth is the one nobody has a metric for, and it is the one that
-- decides whether the other three mattered.
A failing archive_command has two separate consequences

Your recovery point stops advancing — everything since the last successful archive is unrecoverable if the primary dies. And Postgres refuses to recycle unarchived WAL, so pg_wal grows until the filesystem fills and the database stops accepting writes. One failure, two outages, and the only symptom in between is a counter nobody is watching. Alert on failed_count and on pg_wal size as a percentage of the disk.

Testing the restore

automate it, or it will not happen
#!/usr/bin/env bash
set -euo pipefail
# Weekly, in CI, against a scratch instance.

START=$(date +%s)

pgbackrest --stanza=orders --delta \
    --pg1-path=/scratch/pgdata restore

pg_ctl -D /scratch/pgdata -o "-p 5433" -w start

# 1. It starts and accepts connections.
psql -p 5433 -d orders -c 'SELECT 1' > /dev/null

# 2. The data is actually there — compare against known figures.
psql -p 5433 -d orders -tAc \
  'SELECT count(*) FROM orders' | tee /tmp/count

# 3. Structural integrity, not just "the server started".
psql -p 5433 -d orders -c 'CREATE EXTENSION IF NOT EXISTS amcheck'
psql -p 5433 -d orders -tAc "
  SELECT bt_index_check(index => c.oid, heapallindexed => true)
  FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
  WHERE c.relam = (SELECT oid FROM pg_am WHERE amname='btree')
    AND c.relpersistence = 'p'" > /dev/null

pg_ctl -D /scratch/pgdata stop

echo "restore verified in $(( $(date +%s) - START ))s"
# Record that duration as a metric. It IS your recovery time objective,
# whatever the policy document claims — and it grows as the database does.
The restore duration is your real RTO

Not the number in the runbook. Measure it every week and trend it, because it grows with the database and one day it crosses the threshold that the business agreed to without anyone noticing. Teams routinely discover during an incident that their four-hour restore is now eleven hours — and that is the moment they find out, because it is the first time anyone ran it end to end. An untested backup is a hope, and an untimed restore is an unknown outage length.

What backups do not cover

RiskWhy a backup does not helpWhat does
Logical corruption from a bugThe bad data is faithfully backed up tooPITR to before the deploy; retention long enough to notice
Silent page corruptionPropagates into backups and replicasChecksums (chapter 5), and amcheck on restores
Ransomware or a malicious insiderBackups reachable from the compromised host get encrypted tooImmutable or write-once storage; separate credentials
Losing the whole regionBackups in the same region are goneCross-region replication of the repository
Losing the encryption keyThe backup exists and is unreadableKey escrow, and testing a restore with the recovery key
Dropping one tablePhysical restore rolls back the entire clusterA logical dump alongside, or restore to a scratch instance and copy
A replica is not a backup

Streaming replication copies everything faithfully, including the DELETE that removed a million rows — usually within a second. It protects against hardware failure and nothing else. Delayed replicas (recovery_min_apply_delay = '1h') give you a window to catch a destructive mistake before it propagates, which is genuinely useful, and they are still not a substitute for backups you can restore to an arbitrary point weeks ago. Keep both, and be clear which risk each one addresses.

Retention

a schedule that covers the realistic cases
Full backup           weekly
Incremental           daily
WAL archiving         continuous, with archive_timeout = 5min

Retain:
  7 days    of full PITR capability     — the common case: a bad deploy
  4 weeks   of weekly fulls             — "this has been wrong for a while"
  12 months of monthly fulls            — compliance, and audits
  Off-site or cross-region copy of everything

Why the middle tier exists: logical corruption is often discovered long after
it started. A seven-day window is useless if the bug shipped three weeks ago,
and the monthly archive is what lets you extract the correct values for the
affected rows rather than guess them.

Also worth writing down, once, and reviewing yearly:
  * the agreed RPO and RTO, and who agreed them
  * where the decryption key lives, and who can get it
  * the runbook, tested by someone who did not write it

The short version

  1. Logical for granularity and version moves; physical for disaster recovery. Most clusters need both.
  2. pg_dump holds a long transaction and blocks vacuum cluster-wide. Run it from a replica.
  3. Base backup plus WAL archiving is what gives point-in-time recovery — the only thing that undoes a bad deploy.
  4. Use pgBackRest or Barman. Hand-rolled scripts lack verification, retention and incrementals, and fail silently.
  5. A failing archive_command costs you both your recovery window and eventually your disk.
  6. Test the restore weekly, automatically, and check integrity with amcheck rather than just that it started.
  7. The restore duration is your real RTO. Trend it — it grows with the database.
  8. A replica is not a backup. It replicates your mistakes within a second.
