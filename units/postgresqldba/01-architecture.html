What makes Postgres Postgres

Five design decisions account for most of what is distinctive about running PostgreSQL — the good parts and the operational sharp edges alike. Learn them once and the rest of this unit is largely consequences.

The process model

MySQL uses a thread per connection. SQL Server uses a scheduler over a thread pool. PostgreSQL forks a separate operating-system process for every connection — a decision from the 1980s that has survived because it buys real isolation: a crash in one backend cannot corrupt another's memory, and the postmaster can restart cleanly.

A connection is not free, and this is why

Each backend is a fork with its own memory: several megabytes of private allocation before it does anything, a catalogue cache that grows as it touches tables, and a slot in shared memory. Establishing one costs single-digit milliseconds. So a thousand idle connections is a gigabyte of memory and a scheduler full of processes, and the fix is never to raise max_connections — it is a connection pooler in front (chapter 9). This one decision explains why Postgres advice about connections differs so sharply from MySQL advice.

work_mem is the setting most often misread

It is not per connection and not per query — it is per sort, hash join, or hash aggregate node in a plan, and a parallel query multiplies it again by the number of workers. A query with three hash joins and two sorts running with two parallel workers can allocate fifteen times work_mem. Set it conservatively as a global, and raise it per session for the specific reports that need it. This is why the demo above shows a worst case that startles people the first time they compute it.

Double caching

Postgres reads through the operating system's page cache rather than using direct I/O, so a hot page frequently exists twice: once in shared_buffers and once in the kernel's cache. That sounds wasteful and is mostly deliberate.

why shared_buffers is not simply "all of RAM"
-- The conventional starting point is 25% of RAM, and the reasoning is:
--   * the OS cache is also caching your data, and it is good at it
--   * a large shared_buffers makes checkpoints write more at once (ch 4)
--   * Postgres's own cache management is simpler than the kernel's
--   * memory left free is available for work_mem, backends and the OS
--
-- Going higher can help on write-heavy workloads where you want pages to stay
-- dirty in Postgres's cache longer. Going higher on a machine that also runs
-- the application is usually a mistake.
--
-- effective_cache_size tells the PLANNER how much cache it can assume in
-- total, including the OS. It allocates nothing. Set it to roughly 50-75%
-- of RAM; too low and the planner avoids index scans it should choose.
SHOW shared_buffers;         -- actual memory
SHOW effective_cache_size;   -- a hint to the planner, not an allocation
effective_cache_size allocates nothing

Worth stating plainly because the name suggests otherwise. It is purely an input to the cost model: it tells the planner how likely a page is to be found in cache, which shifts the balance between index scans and sequential scans. Setting it too low makes the planner pessimistic about repeated index lookups and pushes it toward sequential scans on tables that are entirely cached. It is free to set correctly and it is left at the tiny default on a remarkable number of installations.

How a query travels

1 · ParseText to a parse tree. Syntax errors surface here
↓
2 · AnalyseResolve names against the catalogue. "Column does not exist" comes from this stage
↓
3 · RewriteExpand views and apply rules and row-level security policies
↓
4 · PlanEnumerate strategies, estimate costs from statistics, pick the cheapest (chapter 7)
↓
5 · ExecutePull rows through the plan tree, reading pages via shared_buffers
two things this pipeline explains
-- 1. A view is expanded at REWRITE, before planning. So a view is not an
--    optimisation barrier and its predicates merge with yours — which is why
--    a well-written view usually costs nothing.

-- 2. Prepared statements skip parse and analyse on reuse, and after five
--    executions Postgres may switch to a GENERIC plan that ignores the actual
--    parameter values.
PREPARE p AS SELECT * FROM orders WHERE status = $1;
EXECUTE p('pending');    -- rare value: an index scan is right
EXECUTE p('paid');       -- 40% of the table: a seq scan is right
-- One plan cannot be right for both. If a prepared statement is intermittently
-- slow, this is usually why. Control it explicitly:
SET plan_cache_mode = 'force_custom_plan';   -- re-plan every time

Extensibility

The system catalogue is itself a set of tables, and almost everything is registered in it — types, operators, functions, index access methods, procedural languages. That is what makes an extension able to add a genuinely new index type rather than a wrapper.

Types and operatorsNew data types with full operator supportinet, ranges, PostGIS geometry

"Just use Postgres" is an architectural argument

Full-text search, JSON documents, geospatial queries, time-series, vector similarity, message queues and cron scheduling all have credible extension-based answers. Each is weaker than the dedicated system it competes with, and each removes an entire operational surface — another cluster to run, another backup regime, another consistency boundary between two stores that can disagree. One database you understand deeply beats four you understand partially. Reach for a specialised system when the Postgres answer has been measured and found wanting, not before.

Configuration

where a setting came from, and how to change it
-- Settings have scopes. Some need a restart, most need only a reload.
SELECT name, setting, unit, context, source, sourcefile, pending_restart
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','max_connections','wal_level');

-- context tells you what a change requires:
--   internal    fixed at compile time
--   postmaster  RESTART   (shared_buffers, max_connections, wal_level)
--   sighup      RELOAD    (most things, including autovacuum settings)
--   superuser   SET, by a superuser
--   user        SET, by anyone, per session

SELECT pg_reload_conf();                       -- apply sighup-level changes
ALTER SYSTEM SET work_mem = '16MB';            -- writes postgresql.auto.conf
ALTER DATABASE reports SET work_mem = '256MB'; -- per database
ALTER ROLE analyst SET work_mem = '256MB';     -- per role — often the best answer
SET LOCAL work_mem = '512MB';                  -- one transaction only

-- The per-role and per-database scopes are underused. A reporting role with a
-- large work_mem and a long statement_timeout, alongside an application role
-- with small values, is far better than one global compromise.
ALTER SYSTEM writes a file that overrides your config management

postgresql.auto.conf is read after postgresql.conf, so anything set with ALTER SYSTEM wins — including over the value your Ansible or Terraform run just deployed. The result is a setting that reverts every deploy and a setting that never takes effect, and hours spent finding out why. Pick one mechanism per cluster. If you manage configuration as code, use ALTER SYSTEM only for emergencies and reset it afterwards with ALTER SYSTEM RESET name.

The short version

  1. Five decisions explain most of Postgres's behaviour: process per connection, MVCC, vacuum, WAL, extensibility.
  2. A connection is an operating-system process costing megabytes. Pooling is mandatory, not an optimisation.
  3. work_mem is per sort or hash node, multiplied again by parallel workers — not per query and not per connection.
  4. effective_cache_size allocates nothing. It is a planner hint, and it is left at the default far too often.
  5. Views are expanded before planning, so they are not optimisation barriers.
  6. Prepared statements can switch to a generic plan after five executions — a common cause of intermittent slowness.
  7. Extensibility reaches down to index access methods and types, which is why "just use Postgres" is often a serious answer.
  8. ALTER SYSTEM overrides your configuration management. Pick one mechanism per cluster.
