Chapter 06 · Storage and access

Index types in depth

The SQL unit covered what indexes do in general. Postgres has six built-in access methods and an extension mechanism for more, and reaching for the right one is frequently the difference between a query that is impossible and one that is instant.

GIN

the inverted index — one entry per element, not per row
-- A B-tree indexes the whole value. GIN indexes each ELEMENT inside a value
-- and stores the list of rows containing it — an inverted index. That is what
-- makes "which rows contain this tag" a lookup rather than a scan.

CREATE INDEX ON articles USING gin (tags);                    -- text[]
CREATE INDEX ON events   USING gin (payload jsonb_path_ops);  -- jsonb
CREATE INDEX ON docs     USING gin (to_tsvector('english', body));
CREATE INDEX ON users    USING gin (name gin_trgm_ops);       -- pg_trgm

SELECT * FROM articles WHERE tags @> ARRAY['postgres'];
SELECT * FROM events   WHERE payload @> '{"type":"signup"}';
SELECT * FROM users    WHERE name ILIKE '%okaf%';   -- trigram index applies

-- jsonb_ops (the default) vs jsonb_path_ops:
--   jsonb_ops       indexes keys AND values; supports ?, ?|, ?& as well as @>
--   jsonb_path_ops  indexes only key/value PATHS; ~3x smaller and faster,
--                   supports only @>
-- If you only ever use @>, use jsonb_path_ops. Most people only use @>.
GIN writes are slow, and the pending list is the reason it seems fine

Inserting one row with ten tags means ten index entries, each needing its posting list updated. To hide this, GIN batches new entries into a pending list and merges them in bulk later — during vacuum, or when the list exceeds gin_pending_list_limit. The consequences: inserts look cheap until a merge, which is a latency spike; and queries must scan the pending list linearly, so a large one makes reads slow too. On a write-heavy GIN index, keep gin_pending_list_limit modest and let autovacuum run often. Setting fastupdate = off makes writes uniformly slower and removes the spikes, which is sometimes the better trade.

BRIN

the tiny index for enormous tables
-- BRIN stores, for each BLOCK RANGE (128 pages by default), the minimum and
-- maximum value found there. A query for a value outside a range skips those
-- 128 pages entirely without reading them.
--
-- An index on a billion-row table can be a few megabytes.

CREATE INDEX ON events USING brin (occurred_at);
CREATE INDEX ON events USING brin (occurred_at) WITH (pages_per_range = 32);

-- It works ONLY when values correlate with physical order. On an append-only
-- table with a timestamp, correlation is near 1 and BRIN is superb. On a
-- randomly-ordered column it is worthless — every block range covers the
-- whole value space and nothing can be skipped.

SELECT attname, correlation
FROM pg_stats
WHERE tablename = 'events' AND attname = 'occurred_at';
-- correlation near 1.0 or -1.0: BRIN is a good fit
-- correlation near 0:            use a B-tree

-- Rough comparison on a billion-row time-series table:
--   B-tree on occurred_at    ~21 GB, meaningful write cost
--   BRIN   on occurred_at    ~3 MB, negligible write cost
-- BRIN returns more false positives, so it reads more heap pages than a
-- B-tree would — but on a table where the B-tree does not fit in memory,
-- BRIN wins by a wide margin.
BRIN is the most under-used index type in Postgres

Every append-only table with a timestamp — events, logs, metrics, audit trails, orders — is a candidate, and these are exactly the tables that grow to hundreds of gigabytes and where a B-tree becomes a problem. The index is so small it stays in memory permanently and the write cost is close to zero. Check correlation in pg_stats first; if it is above about 0.9, try BRIN before adding another B-tree. Note that a CLUSTER or a bulk reorganisation resets correlation, and updates that move rows degrade it over time.

GiST and SP-GiST

GiST — a framework, not one structure
-- GiST is a generalised search tree: a template that an operator class fills
-- in. That is why it supports such different things.

-- Range overlap — the exclusion constraint from the SQL unit
CREATE EXTENSION btree_gist;
CREATE INDEX ON bookings USING gist (room_id, during);
ALTER TABLE bookings ADD EXCLUDE USING gist (room_id WITH =, during WITH &&);

-- Geometry, via PostGIS
CREATE INDEX ON places USING gist (geom);
SELECT * FROM places WHERE ST_DWithin(geom, :point, 1000);

-- Nearest-neighbour: GiST can return rows in distance order, so ORDER BY
-- distance LIMIT 10 becomes an index scan rather than sorting everything.
SELECT * FROM places ORDER BY geom <-> :point LIMIT 10;
-- This "KNN-GiST" capability is unique among the access methods and is
-- the reason GiST is the answer for anything spatial.

-- SP-GiST: space-partitioned, for structures that are naturally unbalanced
CREATE INDEX ON networks USING spgist (addr inet_ops);
SELECT * FROM networks WHERE addr >>= '192.168.1.42';   -- containment
-- Radix trees over text prefixes and quadtrees over points are the other
-- classic uses. Rarely the first thing to reach for; excellent when it fits.

Hash

finally usable, still rarely the answer
CREATE INDEX ON sessions USING hash (token);

-- Before PostgreSQL 10, hash indexes were not WAL-logged: they did not
-- survive a crash and could not be replicated, so the advice was simply
-- "never use them". That was fixed in 10, and a great deal of writing online
-- still repeats the old advice.
--
-- Even so, a B-tree does equality nearly as fast AND supports ranges,
-- ordering, multi-column keys and uniqueness. The narrow case for hash is a
-- very wide key — a long token or URL — where the hash index is materially
-- smaller than the B-tree because it stores a 4-byte hash rather than the
-- value.
--
-- If you are considering it, measure both. Usually the B-tree wins on
-- flexibility for a size difference that does not matter.

Operator classes

the same index type, taught a different comparison
-- An operator class tells an access method how to handle a particular type.
-- Choosing the right one is often the difference between an index that is
-- used and one that is not.

-- text_pattern_ops: makes LIKE 'prefix%' indexable in non-C locales.
-- The default operator class uses locale collation, and LIKE does not.
CREATE INDEX ON files (path text_pattern_ops);
SELECT * FROM files WHERE path LIKE '/var/log/%';    -- now uses the index

-- gin_trgm_ops / gist_trgm_ops: substring and similarity search
CREATE EXTENSION pg_trgm;
CREATE INDEX ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%okaf%';
SELECT * FROM users WHERE name % 'Okafor' ORDER BY similarity(name, 'Okafor') DESC;

-- jsonb_path_ops: smaller jsonb GIN, @> only
CREATE INDEX ON events USING gin (payload jsonb_path_ops);

-- What is available for a type:
SELECT am.amname, opc.opcname, opc.opcdefault
FROM pg_opclass opc JOIN pg_am am ON am.oid = opc.opcmethod
WHERE opc.opcintype = 'text'::regtype;
text_pattern_ops is the fix people spend hours not finding

LIKE 'prefix%' should be indexable, and on a database created with a non-C locale it is not — because the default B-tree operator class orders by locale collation rules while LIKE compares byte by byte. The plan shows a sequential scan on a column that obviously has an index, and nothing in the query looks wrong. Adding a second index with text_pattern_ops fixes it. (If the database was created with C collation the default index already works, which is why the problem appears inconsistent across environments.)

pgvector, since it is why many people arrive here
CREATE EXTENSION vector;
ALTER TABLE documents ADD COLUMN embedding vector(1536);

-- HNSW: better recall and query speed, slower to build, more memory
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- IVFFlat: faster to build, smaller, needs the data present before building
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 1000);      -- roughly rows/1000 for under 1M rows

SET hnsw.ef_search = 100;     -- raise for better recall, at query cost
SELECT id, embedding <=> :query AS distance
FROM documents ORDER BY embedding <=> :query LIMIT 10;

-- Both are APPROXIMATE: they trade recall for speed, and the operator class
-- must match the distance function you query with (cosine, L2 or inner
-- product). A mismatch silently returns wrong neighbours with no error —
-- the query works, the results are just not the nearest ones.

Check the plan actually uses it

Creating an index is not evidence that it is used. The operator in your query has to be one the operator class supports — @> works with jsonb_path_ops and ? does not; LIKE needs text_pattern_ops in a non-C locale; a cast on the column disables everything. After creating any index other than a plain B-tree, run EXPLAIN on the query you built it for and confirm the node type. A GIN index that is never used is one of the more expensive mistakes available, because it taxes every write for nothing.

The short version

  1. Six access methods. B-tree is right about 90% of the time; the skill is recognising the rest.
  2. GIN indexes elements, not values — arrays, jsonb, full text, trigrams. Writes are expensive.
  3. GIN's pending list hides write cost until a merge, and a large one slows reads too.
  4. BRIN is the most under-used type in Postgres. Tiny, nearly free to maintain, and perfect for append-only timestamped tables — check correlation first.
  5. GiST does overlap, containment and nearest-neighbour, which no other method offers.
  6. Hash indexes have been crash-safe since PostgreSQL 10, and are still rarely better than a B-tree.
  7. text_pattern_ops is what makes LIKE 'prefix%' indexable in a non-C locale.
  8. After creating any non-B-tree index, run EXPLAIN and confirm it is used. An unused GIN index is pure write cost.
