PostgreSQL

Almost everything surprising about running Postgres — the bloat, the wraparound alarm, why one long transaction stops the world, why you cannot just raise max_connections — follows from a handful of design decisions made deliberately. This unit starts with those decisions and derives the operational behaviour from them.

How to use this

This unit assumes the SQL unit, or equivalent knowledge — joins, aggregation, transactions, indexes and query plans in the abstract. It deliberately does not repeat any of that. What it covers is PostgreSQL specifically: how the engine is built, what that implies, and how to run it.

Chapters 1–4 are the engine — the process model, MVCC, vacuum and the write path. Nearly every operational surprise traces back to one of these four, so they are worth reading in order even if the rest is reference. Chapters 5–7 cover storage, the index types and the planner. Chapters 8–10 are configuration. Chapters 11–14 are running it in production. Chapters 15–18 are scale and the things that go wrong.

Demos model real mechanisms — you can watch tuple versions accumulate, see a checkpoint spread its writes, and price a vacuum against a growing table. Examples target PostgreSQL 16 and note where behaviour changed in recent versions, because a great deal of the advice online is describing Postgres 9.

Two commitments

Mechanism before advice

"Set shared_buffers to 25% of RAM" is a rule you cannot reason about. Knowing what the buffer cache does, and how it interacts with the operating system's cache, tells you when 25% is wrong. Every recommendation here comes after the thing it depends on.

Version-aware

Postgres has changed enormously. Adding a column with a default was a full rewrite until 11; partitioning was barely usable before 12; logical replication has improved every release since 10. Where advice has expired, this unit says so rather than repeating it.
