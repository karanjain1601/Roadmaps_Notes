Chapter 14 · Running it

High availability and failover

Postgres has no built-in automatic failover, and that is a deliberate omission rather than a gap. Deciding that a primary is dead — rather than briefly unreachable — is a distributed consensus problem, and getting it wrong loses data in ways a database cannot repair.

consensus patroni split-brain clients

The hard part is not promoting

Promoting a standby is one command. The hard part is the question before it: is the primary actually dead, or can I merely not reach it? Those look identical from a single observer, and answering wrong produces two primaries accepting writes.

Two nodes cannot do this

With a primary and one standby, a network partition between them is indistinguishable from the primary having died — from the standby's point of view those are the same observation. Promote and you may have two primaries; do not promote and you have no automatic failover. There is no configuration that resolves it, because the information genuinely is not there. You need a third voter: a third database node, or — cheaper and usually sufficient — a third member of the consensus store on a separate machine. This is why every serious HA setup has an odd number of somethings.

Patroni

patroni.yml — the parts that matter
scope: orders-cluster
name: node1

etcd3:
  hosts: [10.0.1.10:2379, 10.0.1.11:2379, 10.0.1.12:2379]   # THREE

bootstrap:
  dcs:
    ttl: 30                    # leader key lifetime; a dead leader is
                               # detected after this
    loop_wait: 10              # how often each node checks in
    retry_timeout: 10          # tolerance for a slow DCS before demoting
    maximum_lag_on_failover: 1048576   # 1 MB — a laggier standby is not
                                       # eligible, which bounds data loss
    synchronous_mode: true             # do not promote a standby that might
                                       # be missing committed transactions
    postgresql:
      use_pg_rewind: true
      parameters:
        wal_log_hints: 'on'            # chapter 13 — required for pg_rewind
        max_wal_senders: 10

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.1.10:5432
  data_dir: /var/lib/postgresql/16/main
  authentication:
    replication: {username: replicator, password: '…'}
    superuser:   {username: postgres,   password: '…'}

# The mechanism: the leader holds a key in etcd with a TTL and refreshes it
# every loop_wait. If it stops refreshing, the key expires and the remaining
# nodes race to take it — etcd's consensus guarantees exactly one wins.
# A node that cannot reach etcd DEMOTES ITSELF, which is the fencing.
Self-demotion is the whole trick

The behaviour that makes Patroni safe is not the promotion, it is what a node does when it cannot reach the consensus store: it demotes itself, immediately, without needing to be told. A partitioned primary therefore stops accepting writes on its own, before any standby is promoted — so even if both sides act, only one is ever writable. This is the correct shape for any failover system, and it is exactly what hand-rolled scripts using a health check and a promote command do not do.

operating it
patronictl -c /etc/patroni.yml list
# + Cluster: orders-cluster ------+---------+---------+----+-----------+
# | Member | Host      | Role    | State   | TL | Lag in MB |
# +--------+-----------+---------+---------+----+-----------+
# | node1  | 10.0.1.10 | Leader  | running | 12 |           |
# | node2  | 10.0.1.11 | Replica | running | 12 |         0 |
# | node3  | 10.0.1.12 | Replica | running | 12 |         0 |

patronictl switchover --leader node1 --candidate node2   # PLANNED. No loss
patronictl failover --candidate node2                    # forced; may lose data
patronictl pause                                         # maintenance mode:
                                                         # no automatic action
patronictl resume
patronictl reinit node3                                  # rebuild from the leader

# switchover and failover are different operations and the distinction matters:
#   switchover  waits for the candidate to catch up fully, then swaps cleanly
#   failover    promotes now, accepting whatever the candidate is missing
# Use switchover for every planned change — upgrades, maintenance, rebalancing.

# ALWAYS pause before manual maintenance. Otherwise Patroni sees the node you
# just stopped, decides it has failed, and fails over in the middle of your
# planned work.

postgresql://a.db,b.db,c.db/orders?target_session_attrs=read-write
postgresql://a.db,b.db,c.db/orders?target_session_attrs=prefer-standby  # reads

# The driver tries each host and asks whether it accepts writes. On failover
# the connection breaks, the driver reconnects, and it lands on the new
# primary. Supported by libpq 10+, JDBC, psycopg, Npgsql, Go pgx and others.

# 2. HAProxy in front, health-checking Patroni's REST API.
listen postgres_primary
    bind *:5432
    option httpchk GET /primary          # 200 only on the leader
    http-check expect status 200
    default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions
    server node1 10.0.1.10:5432 check port 8008
    server node2 10.0.1.11:5432 check port 8008
    server node3 10.0.1.12:5432 check port 8008

listen postgres_replicas
    bind *:5433
    option httpchk GET /replica
    balance roundrobin
    server node1 10.0.1.10:5432 check port 8008
    ...

# on-marked-down shutdown-sessions is the important flag: it kills existing
# connections to a demoted node rather than leaving them attached to a server
# that is now read-only and will fail every write.
Failover is not transparent to the application

Whatever the routing, in-flight transactions are lost and open connections break. The application sees connection errors for a few seconds, and if it does not retry, users see errors even though failover worked perfectly. Three things are needed on the client side: connection-level retry with backoff, idempotent writes so a retry after an ambiguous failure is safe (SQL chapter 9), and a short connection timeout so a dead host is abandoned quickly rather than hanging for the operating system's default. Teams build an excellent HA setup and then discover their failover is thirty seconds because a JDBC socket timeout was never configured.

Split-brain

how it happens, and what it costs
1. The network partitions. The primary is isolated; standbys and the DCS are
   on the other side.
2. The primary is fine and keeps accepting writes from any clients that can
   still reach it.
3. The standbys see no leader, elect one, and promote it.
4. Two primaries. Both accept writes. Both are internally consistent.
5. The partition heals.

Now there are two divergent histories with no automatic reconciliation. Both
sets of transactions are real, both were acknowledged to clients, and no tool
can merge them — you choose one and manually extract what you can from the
other, if the data even permits it.

Preventing it — in order of importance:
  * SELF-DEMOTION. A node that cannot reach the DCS stops being primary.
    This alone prevents the scenario above
  * A majority requirement, so the minority side can never elect
  * Fencing: STONITH, a cloud API call to stop the instance, or revoking
    its storage access
  * synchronous_mode, so a standby missing committed transactions is not
    promoted at all
  * Routing that actively rejects the demoted node, rather than relying on
    it to stop answering
A clean shutdown is not fencing

Asking the old primary to stop assumes you can reach it — and in a network partition, by definition, you cannot. Real fencing does not require the failing node's cooperation: a cloud API call that stops the instance, a management-controller power-off, or revoking its access to shared storage. In the common cloud setup Patroni's self-demotion covers the realistic cases, because the node fences itself when it loses the DCS. If you are relying on something reaching in and stopping it, test that path — it is the one that fails exactly when it is needed.

Automatic failover is not obviously worth it

It adds a distributed system whose failure modes include causing outages — an unnecessary failover triggered by a network blip, a promotion to a lagging standby, a DCS problem that demotes a healthy primary. Before adopting it, work out honestly how often the primary actually fails, and what a paged engineer following a runbook would cost in minutes. For many systems the answer is that fifteen minutes of downtime a few times a year is acceptable, and a well-tested manual runbook is more reliable than automation nobody exercises. Automate failover when the availability requirement genuinely demands it, and then test it monthly — untested automatic failover is worse than none.

what to measure during a test
-- Run a write loop from a client throughout, and record:
--   t0  the failure is injected
--   t1  the failover system notices               (ttl + loop_wait)
--   t2  a new primary is promoted
--   t3  routing points at it
--   t4  the client's first successful write        <- the number that matters
--
-- t4 − t0 is your real recovery time. It is nearly always longer than the
-- promotion itself, and the gap is usually routing and client retry — the
-- two parts nobody tests.

-- Afterwards, confirm nothing was lost that was acknowledged:
SELECT count(*), max(id) FROM write_test;      -- against the client's log
SELECT pg_last_wal_replay_lsn(), pg_current_wal_lsn();

-- And that the old node rejoined rather than sitting broken:
--   patronictl list        all members running, same timeline (TL), lag 0

The short version

  1. Promoting is easy. Deciding the primary is dead rather than unreachable is the hard part, and it needs consensus.
  2. Two nodes cannot do automatic failover safely. You need a third voter — a node, or a third DCS member.
  3. Self-demotion is the mechanism that prevents split-brain: a node that cannot reach the DCS stops being primary on its own.
  4. switchover is planned and lossless; failover is forced and may lose data. Pause before manual maintenance.
  5. Routing needs a stable endpoint — multi-host connection strings or HAProxy against Patroni's REST API.
  6. Failover is not transparent. Clients need retry, idempotent writes and short timeouts, or your HA works and users still see errors.
  7. A clean shutdown is not fencing. Real fencing does not need the failing node's cooperation.
  8. Automatic failover adds failure modes. Adopt it when the requirement demands it, then test it monthly — including a network partition.
