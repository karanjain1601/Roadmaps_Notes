Designing an HTTP API

An API is a contract you will be living with for years and cannot unilaterally change. Most of the decisions are cheap to get right at the start and expensive afterwards — which makes this one of the few areas where thinking ahead genuinely pays. This chapter is the decisions, in the order you will face them.

~32 min read Resources · pagination · idempotency · errors 2 interactive panels Prerequisite: chapter 3

5.1Resources

The core REST idea is that your API exposes things, identified by URLs, that you act on with a small set of methods — rather than exposing operations. The value is not purity; it is that the small set of methods have properties (Chapter 3) that caches, proxies and retry logic already understand.

URL conventions worth following, because consistency is most of the benefit

When the thing is not a resource

Some operations genuinely are not create-read-update-delete on a noun: refund this payment, retry this job, publish this draft, search. Two honest answers. Model the action as a resource — POST /payments/p_1/refunds creates a refund, which is a real thing with an identity and a status, and this is usually the better design because it gives you somewhere to record the outcome. Or accept a verb sub-resource: POST /jobs/j_1/retry. What is not worth doing is contorting a genuine action into a PATCH on a status field so the API looks RESTful — PATCH {"status":"refunded"} hides a significant operation behind an innocuous-looking write, and gives you no place to put the refund's own id, amount or failure reason.

5.2Pagination

Every collection endpoint needs pagination from day one, because retrofitting it is a breaking change and because an unpaginated endpoint is an outage waiting for a customer with a lot of data. There are two mechanisms and they are not equivalent.

Offset versus cursor, while the data changes

A user reads page by page. Meanwhile rows are being inserted and deleted. Watch what each mechanism does.

The two queries

Choosing
Offset / page numberCursor / keyset
Stable while data changesNo — duplicates and skipsYes
Deep-page performanceDegrades linearly — the database counts and discards every skipped rowConstant — an index seek
Jump to page 500TrivialNot possible
Total countNaturalExpensive; usually omitted or estimated
ImplementationOne lineNeeds a stable sort key and tie-breaking
Use forSmall admin tables where a page picker is genuinely wantedAnything large, anything a client iterates, anything public

The cursor should be opaque — base64 of the sort key plus a tie-breaker — so that clients cannot construct one and you can change the encoding later. Always include a unique tie-breaker in the sort: ordering by created_at alone is ambiguous when two rows share a timestamp, and the ambiguity produces exactly the duplicate-and-skip behaviour cursors were meant to eliminate.

5.3Filtering, sorting, sparse fields

Conventions that stay readable as they grow 
GET /orders
  ?status=paid,shipped          repeated values as a comma list
  &created_after=2026-01-01     explicit operator in the NAME,
  &total_gte=5000                not a mini query language
  &sort=-created_at,id          leading "-" for descending
  &fields=id,total,status       sparse fieldsets
  &expand=customer              inline a related resource
  &limit=50&cursor=eyJ…

RULES THAT SAVE YOU LATER
  · Reject unknown parameters with 400 rather than ignoring
    them. A silently-ignored typo in a filter returns the
    wrong data and looks like it worked.
  · Cap the page size server-side. limit=1000000 must not
    be honoured, whatever the client asks.
  · Only allow sorting on indexed columns, or an innocent
    ?sort=notes becomes a table scan for every caller.
  · Do not invent a query DSL in the query string. Once you
    need real query expressions you want a POST /search with
    a body, or GraphQL — chapter 6.

5.4Idempotency keys

The problem from Chapter 3: a client sends POST /payments, the payment succeeds, and the response is lost. The client cannot tell that from the request never arriving. Retrying risks charging twice; not retrying risks a lost payment the customer believes they made.

An idempotency key gives POST the safety that PUT and DELETE have by construction. The client generates a unique key per logical operation and sends it with every attempt at that operation; the server guarantees the operation happens at most once and returns the same response to every retry.

The protocol, including the parts that are easy to get wrong 
CLIENT
  key = uuid()                     once per logical operation,
  POST /payments                   NOT once per attempt
  Idempotency-Key: {key}
  → on timeout or 5xx, retry with the SAME key

SERVER, on receiving a request with a key
  1  Try to INSERT (key, request_fingerprint, state='in_progress')
     Use a unique constraint on the key. The insert IS the lock —
     doing a SELECT then an INSERT has a race between them.

  2  If the insert succeeded → this is the first attempt.
     Do the work. Then, IN THE SAME TRANSACTION as the side
     effect, store the response and set state='complete'.
     ← this atomicity is the whole point. Storing the response
       afterwards leaves a window where the charge happened and
       the record says it did not.

  3  If the insert conflicted → we have seen this key.
     state='complete'    → return the STORED response verbatim
     state='in_progress' → return 409, the client should retry
                           shortly; do not run it concurrently

  4  If the fingerprint differs from the stored one → 422.
     The same key with a different body is a client bug, and
     silently honouring it would be worse.

  5  Expire keys after 24 h. Long enough for any retry, short
     enough that the table does not grow forever.

WHAT ELSE NEEDS THIS
  Any POST with an external side effect: payments, emails,
  provisioning, outbound webhooks, message publication.

5.5Versioning

Four approaches
ApproachLooks likeForAgainst
URL path/v1/ordersObvious, visible in logs, trivially routable, easy to test in a browserStrictly, the same resource now has two URLs
Media typeAccept: application/vnd.shop.v2+jsonURLs stay stable; the purist's answerInvisible in logs and dashboards, awkward to test, and clients forget it
HeaderX-API-Version: 2026-06-01Flexible; supports date-based pinningSame invisibility problem
Date-pinned per accountVersion recorded at signup; overridable per requestClients never break; you can ship changes continuously. Stripe's modelYou maintain transformation layers for every version, forever
The strategy that beats all four

Do not version. Change additively. A new optional field, a new endpoint, a new enum value the client is told to ignore if unrecognised — none of these break anyone, and none require a version. Reserve versioning for genuinely breaking changes, which are rarer than they seem: removing a field, renaming one, changing a type, changing the meaning of a value, or making an optional field required. When you must break, use parallel change — support both shapes, migrate consumers, instrument the old path, and remove it only when the usage counter has read zero for longer than your longest client refresh cycle.

5.5bErrors

Error responses are the part of an API most often designed by accident, and they are what a client integrator spends their time on. RFC 9457 (which supersedes RFC 7807) defines a standard shape, and adopting it costs nothing.

application/problem+json 
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://api.shop.com/problems/insufficient-stock",
  "title":    "Insufficient stock",
  "status":   422,
  "detail":   "Only 2 units of SKU-4471 remain; 5 were requested.",
  "instance": "/orders/o_9f21",

  "sku": "SKU-4471",           ← extension members are allowed
  "requested": 5,                and are where the machine-readable
  "available": 2,                detail belongs
  "requestId": "8c2e-4d1a-…"
}

type      a STABLE identifier clients switch on. Never change it.
          A URL by convention; it need not resolve, but if it
          does, put the documentation there.
title     short, human, and the same for every occurrence
detail    specific to THIS occurrence, and safe to show a user
instance  which resource this was about
extensions  everything a client needs to act programmatically

FOR VALIDATION, one problem with a list beats many problems:
  "errors": [
    { "pointer": "/lines/0/quantity", "detail": "must be ≥ 1" },
    { "pointer": "/address/postcode", "detail": "not recognised" }
  ]
Returning only the first error means a form takes six round
trips to fill in correctly.

NEVER include: stack traces, SQL, internal hostnames, or
whether an account exists. An error is an information leak
if you let it be one.                              → ch 14

5.6Rate limiting

Rate limits protect you from a client's bug, a client's success, and abuse — usually in that order of frequency. The algorithm you choose determines how the limit behaves at its edges, and the differences are larger than they look.

Four rate-limiting algorithms on identical traffic

Same limit, same arrivals. Watch how many requests each actually admits in the worst window.

Whatever you choose, tell the client the budget. A client that can see its remaining quota can slow down; a client that only discovers the limit by being rejected will hammer you and then retry immediately.

The headers to send on every response, not just rejections 
RateLimit-Limit: 100
RateLimit-Remaining: 43
RateLimit-Reset: 27                seconds until the budget refills

…and on a rejection:
HTTP/1.1 429 Too Many Requests
Retry-After: 27                    seconds, or an HTTP-date

Limit per API KEY, not per IP — several users share an IP and
one user has several. Consider a separate, tighter limit for
expensive endpoints, because 100 searches and 100 exports are
not the same load.

5.7Long-running operations

Some work cannot finish inside a request: generating a report, transcoding a video, running an import. Holding the connection open is wrong — it consumes a worker, times out at proxies, and gives the client nothing to reconnect to. The pattern:

202 and a resource to watch 
POST /exports                      client asks for the work
→ 202 Accepted
  Location: /exports/e_7c31
  { "id":"e_7c31", "status":"queued" }

GET /exports/e_7c31                client polls, or is told by a
→ 200 { "status":"running",        webhook when it is done
        "progress": 0.42 }

→ 200 { "status":"succeeded",
        "resultUrl": "/exports/e_7c31/download" }
→ 200 { "status":"failed",
        "error": { …problem+json… } }

NOTE
  · 202 means accepted, NOT done. Do not return 200.
  · The job is a real resource with an id, so it can be
    listed, cancelled and audited.
  · Include Retry-After on the polling response to control
    how often clients ask.
  · Offer a webhook as well as polling — a client that polls
    every second for a ten-minute job is a load problem you
    created.                                        → ch 15

5.8Documentation as a contract

An OpenAPI document is worth writing not for the rendered page but because it becomes machine-readable: request validation, client generation, mock servers, and — most valuable — a breaking-change check in CI that diffs the specification against the previous version and fails the build on an incompatible change. That single check catches more integration breakage than any amount of review.

Write the specification first where you can. Designing the interface before the implementation forces you to think as a caller, which is the same argument test-first design makes; and it lets consumers start against a mock while you build.

Why does offset pagination get slower on later pages even with a perfect index?

Because OFFSET n does not skip rows — it fetches and discards them. ORDER BY created_at LIMIT 20 OFFSET 100000 requires the database to walk the index and produce 100,020 rows in order, throw away the first 100,000, and return the last 20. The work is linear in the offset, so page 5,000 costs 5,000 times what page 1 does, and the query gets slower the deeper a client goes — which is exactly backwards from what anyone expects. Keyset pagination replaces the offset with a WHERE clause: WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20. That is a single index seek to the starting position followed by a scan of 20 entries, and it costs the same on page 5,000 as on page 1. The two things to get right are including a unique tie-breaker in both the ordering and the comparison — otherwise rows sharing a timestamp are skipped or repeated — and using a row-value comparison rather than created_at < $1 AND id < $2, which is a different and wrong condition.

A client retries a payment with the same idempotency key while the first attempt is still running. What should happen?

Return 409 Conflict and let the client retry shortly — do not execute it concurrently and do not block waiting for the first one. The reason the key record is inserted before the work starts, with a state of in_progress, is precisely to detect this: the unique constraint on the key means the second request's insert fails, and the existing row tells you an attempt is in flight. Executing concurrently defeats the entire purpose, since both could charge. Blocking until the first finishes is tempting but holds a worker for the duration and turns a retry storm into resource exhaustion. Two details that matter. The insert must be the lock — a SELECT followed by an INSERT has a race between the two statements, and under retry pressure that race is hit routinely. And the completed response must be stored in the same transaction as the side effect; if you charge the card and then write the record separately, a crash in between leaves a charged customer and a record saying the operation never happened, so the next retry charges again. Where the side effect is external and cannot join your transaction, the outbox pattern in Chapter 15 is the standard answer.

Why is a fixed-window rate limiter often the wrong choice?

Because it permits up to twice the limit across a window boundary. A limit of 100 per minute implemented as a counter that resets on the minute allows 100 requests in the last second of one minute and another 100 in the first second of the next — 200 requests in a two-second span, which is 60 times the intended rate. That is not a corner case: clients naturally align to clock boundaries because cron jobs, scheduled syncs and retry backoffs all round to the minute, so the boundary is exactly where bursts arrive. It also means the limiter fails to protect you at the precise moment protection matters. The alternatives fix it differently. A sliding window log is exact but stores a timestamp per request. A sliding window counter weights the previous window's count by how much of it remains in view, which is an approximation accurate to within a few percent for a fraction of the storage. A token bucket refills continuously and allows a configurable burst, which is usually what you actually want — it smooths traffic while still permitting a legitimate short spike, and it is cheap to implement atomically in Redis.

Recap

  1. Expose things, not operations — and when something genuinely is an action, model it as a resource rather than contorting a PATCH.
  2. Paginate from day one. Cursors for anything large or public; offsets only for small admin tables that want a page picker.
  3. Offset pagination duplicates and skips while data changes, and degrades linearly with depth.
  4. Reject unknown query parameters and cap page size server-side.
  5. Idempotency keys give POST the safety PUT has. The insert is the lock, and the response must be stored atomically with the side effect.
  6. Change additively and avoid versioning; when you must break, use parallel change and instrument the old path.
  7. RFC 9457 problem+json, with a stable type, machine-readable extensions and all validation errors at once.
  8. Fixed-window limiters allow 2× the limit at the boundary. Token bucket is usually what you want.
  9. Always send the rate-limit budget, not just the rejection.
  10. 202 plus a job resource for long work, with a webhook as well as polling.
