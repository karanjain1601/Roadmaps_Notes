Authentication and authorisation

Two different problems that share a prefix and get confused constantly. One asks who you are and is solved once at the edge; the other asks what you may do and must be answered at every single operation. Most real breaches are failures of the second, in code that got the first entirely right.

~34 min read Passwords · sessions · JWT · OAuth · RBAC 2 interactive panels Prerequisite: chapters 3, 5

7.1The distinction

Why keeping them separate matters
AuthenticationAuthorisation
QuestionWho are you?May you do this, to this?
WhenOnce per session or request, at the edgeAt every single operation, on every object
Failure code401, with WWW-Authenticate403 — or 404, to avoid confirming existence
Where the code livesMiddlewareIn the domain, next to the data. Not in middleware
Typical bugWeak or misused tokensForgetting to check on one endpoint out of two hundred
Authorisation cannot live in middleware alone

Middleware sees a route and a user; it does not see which object is being touched. GET /orders/o_9f21 passes any route-level check a signed-in user could pass — the question of whether this user owns that order can only be answered after loading it. That gap is insecure direct object reference, and it is consistently the most common serious API vulnerability, because the code looks complete: there is an auth check, it runs, and it checks the wrong thing. The structural defence is to make ownership part of the query — WHERE id = $1 AND customer_id = $2 — so a wrong owner returns nothing rather than relying on a check somebody has to remember to write.

7.2Passwords

If you store passwords, you will one day be judged on how. The rules are short and non-negotiable.

What to use, and why the obvious answers are wrong 
NEVER  plaintext, encryption (reversible = the key leaks too),
       MD5, SHA-1, SHA-256, or any general-purpose hash

WHY NOT SHA-256?  It is designed to be FAST. A modern GPU does
       billions per second, so a leaked table of SHA-256 hashes
       is a list of passwords by tomorrow. You want SLOW.

USE    Argon2id      preferred; memory-hard, so GPUs and ASICs
                     lose their advantage
       scrypt        also memory-hard, widely available
       bcrypt        fine; note the 72-byte input truncation
       PBKDF2        acceptable where compliance demands it,
                     weakest of the four

ALWAYS · a unique random salt per password — the library does
         this and stores it in the output string
       · a work factor tuned so hashing takes 100–500 ms on
         YOUR hardware, re-tuned as hardware improves
       · re-hash on successful login when the stored work
         factor is below current policy
       · a constant-time comparison, which the library provides

AND    · no maximum length below 64 characters, and no
         character-class rules — length beats composition
       · check against a breached-password list; this catches
         far more real attacks than complexity rules
       · rate limit and lock out by ACCOUNT and by IP
       · never reveal whether an address is registered, in
         login, signup or password reset — all three must
         behave identically

What a work factor buys

Time to crack one password from a leaked hash, against attacker hardware.

7.3Sessions versus tokens

Once someone has proved who they are, subsequent requests need to carry that fact. There are two mechanisms and the choice is more consequential than it looks.

The trade
Server-side sessionSelf-contained token (JWT)
What the client holdsAn opaque random idSigned claims — the data itself
Server lookup per requestYes — a cache or database readNo — verify the signature
RevocationImmediate. Delete the recordNot possible without a lookup, which removes the advantage
Changing permissionsTakes effect on the next requestStale until the token expires
Size on the wire~32 bytes300 bytes to several KB, on every request
Cross-serviceNeeds shared session storageAny service with the public key can verify
Leak consequenceValid until deletedValid until it expires, and you cannot stop it
Good forA first-party web application — the common caseService-to-service, and short-lived access tokens in OAuth
JWTs are the wrong default for web sessions

The pitch is "stateless, no database lookup". The trap is that you almost always need revocation — a logout, a password change, a disabled account, a permission removed, a stolen token — and the moment you add a revocation list you are doing a lookup on every request, which is exactly what a session does, only now with a larger cookie and a token that stays valid until expiry anyway. A session id in an HttpOnly; Secure; SameSite=Lax cookie with the record in Redis is simpler, smaller, immediately revocable, and the lookup costs well under a millisecond. Use JWTs where their actual advantage applies: a token passed between services that each need to verify it without calling an auth service, and short enough that expiry is an adequate substitute for revocation.

7.4JWT, when you do use one

Structure, and every sharp edge 
header.payload.signature      three base64url segments, dot-separated

{ "alg":"RS256", "kid":"2026-06" }          header
{ "sub":"u_44b1", "iss":"https://auth.shop.com",
  "aud":"api.shop.com", "exp":1780003600,
  "iat":1780000000, "jti":"9f2c…" }         payload — NOT encrypted,
                                             only signed. Anyone can
                                             read it. Put nothing
                                             secret in it.

THE SHARP EDGES, IN ORDER OF HOW OFTEN THEY BITE

1  alg confusion. A verifier that trusts the header's alg can be
   handed alg:"none" (accept unsigned) or an RS256 public key
   used as an HS256 secret. PIN the expected algorithm in your
   verification call; never read it from the token.

2  Not verifying at all. Decoding is not verifying, and the two
   functions in most libraries differ by one word.

3  Missing claim checks. Verify exp, and also iss and aud — a
   valid token issued for a different audience is still a valid
   signature. Allow only small clock skew.

4  No revocation. Keep access tokens SHORT — 5 to 15 minutes —
   and put the long life in a refresh token you can revoke,
   because that one is checked against storage anyway.

5  Size. Claims accumulate. Past 4 KB a cookie is rejected
   outright, and every request carries the whole thing.

6  Storage in the browser. localStorage is readable by any
   injected script, so one XSS bug exfiltrates every token.
   An HttpOnly cookie is not — which is why the "JWTs avoid
   cookie problems" argument usually ends with a cookie.

7  Key rotation. Publish a JWKS endpoint, put a kid in the
   header, and support two keys at once during a rotation.

7.5OAuth 2 and OpenID Connect

The two are constantly conflated. OAuth 2 is delegated authorisation — letting an application act on a user's behalf against another service without holding their password. OIDC is an identity layer on top of it, adding an ID token that says who the user is. "Log in with Google" is OIDC; "let this app read your Google Calendar" is OAuth.

The flows that remain in OAuth 2.1

Authorization code + PKCEEverything with a user: web apps, mobile, single-page appsThe default, and now required for all client types. PKCE is no longer only for public clients

Device codeDevices with no browser or keyboard — TVs, CLIsThe "go to this URL and enter this code" pattern

Implicit—Removed. Tokens in the URL fragment leak through history, referrers and logs
Password grant—Removed. It requires the app to handle the user's password, which is what OAuth exists to avoid
Authorization code with PKCE, and what each step defends against

3  User authenticates there. Your app never sees the password.

4  Redirect back with a one-time code.
   Intercepting the code is not enough on its own…

5  App exchanges code + VERIFIER at the token endpoint.
   The server hashes the verifier and compares to the stored
   challenge. An attacker with the code but not the verifier

REFRESH TOKEN ROTATION
  Each use returns a NEW refresh token and invalidates the old
  one. If an old one is ever presented again, that means it was
  stolen and replayed — revoke the entire family immediately.
  This turns silent theft into a detectable event.

7.7Authorisation models

Four models, in increasing order of what they can express
ModelRule shapeGoodLimit
OwnershipYou may act on rows you ownCovers most of a typical application, and is enforceable in the queryCannot express sharing or delegation
RBACRoles hold permissions; users hold rolesSimple, auditable, easy to explain to an auditorRole explosion once rules depend on the object, not just the user
ABACRules over attributes of user, resource, action and contextExpresses "managers may approve expenses under £5 000 in their own department during business hours"Hard to reason about, hard to answer "who can see this?"
ReBACPermissions derive from a graph of relationshipsNatural for sharing, folders, teams and inheritance. The Google Zanzibar modelNeeds a dedicated service; a graph traversal per check

The practical path: start with ownership plus a small set of roles, because that covers most applications and both are checkable inside the database query. Add attribute conditions where a specific rule needs them, rather than adopting a whole policy engine. Reach for a relationship-based service only when you genuinely have nested sharing — documents in folders in teams with inherited access — which is a real problem and a genuinely hard one to bolt on later.

Two rules regardless of model. Deny by default: a new endpoint with no policy must be inaccessible, not open, which means the framework should require an explicit decision rather than allowing an omission. And decide in one place: a single authorisation function called from every use case, so a new rule is one change and an audit is one file — rather than a check scattered across two hundred handlers where the missing one is invisible.

Why is SHA-256 unsuitable for passwords when it is a strong hash?

Because "strong" here means collision-resistant and one-way, and neither is the property you need — the property you need is slow. SHA-256 is designed to be fast so that it can hash gigabytes, which means a single modern GPU computes billions per second and a rack of them computes trillions. Against that, the entire space of eight-character passwords is exhausted in a matter of hours, so a leaked table of SHA-256 hashes is a list of plaintext passwords very shortly afterwards. Salting fixes a different problem: it stops one precomputed rainbow table cracking every account at once and forces the attacker to attack each hash separately, but each individual attack is still billions per second. Password hashes must be deliberately expensive — bcrypt, scrypt and Argon2 have a tunable work factor, so you set it such that one hash takes a few hundred milliseconds on your server, which is imperceptible at login and reduces an attacker's rate from billions per second to a few thousand. Argon2 and scrypt go further by being memory-hard, requiring tens of megabytes per hash, which removes the massive parallelism advantage of GPUs and custom hardware since memory bandwidth rather than arithmetic becomes the constraint.

You adopt JWTs to avoid database lookups, then add a revocation list. What have you actually built?

A session, with extra steps. The entire performance argument for a self-contained token is that verification is local — a signature check, no round trip. A revocation list reintroduces exactly the lookup you were avoiding, on every request, so you now pay the same cost as a session while carrying a token that is several hundred bytes to several kilobytes instead of thirty-two, and which remains cryptographically valid until it expires regardless of what your list says. You have also inherited a set of problems a session does not have: algorithm confusion, claim validation, key rotation, and the fact that anyone can read the payload. Two honest resolutions. If you need immediate revocation for a first-party web application, use a server-side session in an HttpOnly; Secure; SameSite cookie — it is simpler, smaller, and the Redis lookup is well under a millisecond. If you need offline verification across services, keep the JWT but make the access token very short-lived, five to fifteen minutes, and accept expiry as your revocation mechanism, putting the long-lived, revocable state in a refresh token that is checked against storage anyway. What does not work is the middle position, which is where most JWT implementations end up.

Your API checks authentication in middleware on every route. Why is that not enough?

Because middleware answers the wrong question. It knows the route and the authenticated user, so it can enforce "you must be signed in" and even "you must have the admin role for routes under /admin" — but it cannot know whether this user is entitled to that specific object, because the object has not been loaded yet. So GET /orders/o_9f21 passes every middleware check a signed-in user could pass, and returns another customer's order. This is broken object-level authorisation, and it is consistently the most commonly found serious API flaw, precisely because the code looks complete: there is an auth layer, it runs on every request, and it checks something real. Three defences that work together. Push ownership into the query — WHERE id = $1 AND customer_id = $2 — so a mismatched owner returns no rows and there is no check to forget. Use opaque, non-sequential identifiers, which does not fix the flaw but removes trivial enumeration. And test it structurally: for every endpoint that takes an id, have a test where user A requests user B's object and asserts a 404, because a per-endpoint manual check is exactly the thing that gets missed on endpoint 187 of 200.

Recap

  1. Authentication happens once at the edge; authorisation happens at every operation on every object.
  2. Authorisation cannot live in middleware alone — put ownership in the query so there is no check to forget.
  3. Password hashes must be slow and memory-hard. Argon2id, scrypt or bcrypt, tuned to a few hundred milliseconds.
  4. Length beats composition, and a breached-password check catches more real attacks than complexity rules.
  5. Sessions beat JWTs for first-party web apps. Adding a revocation list to a JWT rebuilds a session with a bigger cookie.
  6. Pin the algorithm, verify exp, iss and aud, keep access tokens short, and publish a JWKS with a kid.
  7. Authorization code with PKCE for everything with a user; implicit and password grants are gone.
  8. Rotate refresh tokens and detect reuse — that turns silent theft into a detectable event.
  9. Start with ownership plus roles; deny by default, and decide in one place.
  10. Test broken object-level authorisation structurally, because the endpoint that forgets is invisible in review.
