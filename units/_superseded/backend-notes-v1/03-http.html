HTTP

The protocol every backend speaks, and the one most people know 20% of. That 20% is enough until something behaves strangely — a browser refusing a request that curl accepts, a proxy caching a response it should not have, a form submitted twice. This chapter is the rest of it, organised by what actually causes those problems.

3.1The message

HTTP is text-shaped, even when HTTP/2 and /3 encode it in binary. Every exchange is a request with a method, a target and headers, and a response with a status and headers. Both may carry a body.

Two properties shape everything built on it. HTTP is stateless — the server is not required to remember anything between requests, which is what allows any process to serve any request (Chapter 1). And it is request–response, initiated only by the client, which is why pushing data to a browser requires the workarounds in Chapter 6.

3.2Methods, and the three properties that matter

The method is not decoration. Caches, proxies, browsers and retry logic all behave differently based on it, and getting it wrong produces failures far from the code.

Why idempotency is the important column

Networks fail in a specific, awkward way: the request arrives and the response is lost. The client cannot distinguish that from the request never arriving, so it must choose between retrying — risking a duplicate — and not retrying — risking a lost operation. If the method is idempotent, retrying is free and the choice disappears. That is the entire reason the property matters, and it is why a payment endpoint needs an idempotency key to buy the same guarantee for a POST. Chapter 5 works through the protocol.

Two consequences people learn the hard way. A GET that changes state will eventually be triggered by something that assumes it is safe — a link prefetcher, a crawler, a browser preloading on hover, a monitoring probe. There is a well-known genre of incident where a crawler followed every "delete" link on an admin page. And PATCH is not idempotent unless you make it so: {"op":"increment","by":1} applied twice is different from applied once, whereas {"quantity":5} is not.

The distinction worth internalising is 401 versus 403, because the names are misleading. 401 says "I do not know who you are — authenticate and try again", and must include a WWW-Authenticate header. 403 says "I know exactly who you are and you may not do this", and retrying with the same credentials is pointless. Returning 403 for an expired token sends clients into a loop; returning 401 for a permissions failure makes them re-authenticate for no reason.

Vary

If a response differs depending on a request header — the Accept-Language, the Accept-Encoding, whether an Authorization header was present — the response must say so with Vary. Otherwise a shared cache stores one variant and serves it to everyone: the French page to English users, a gzipped body to a client that cannot decompress it, or in the worst case one user's personalised response to another. Vary omissions are the mechanism behind most cache-poisoning incidents, and the failure is invisible in development because there is no shared cache in front of your laptop.

3.5Cookies

A cookie is a small value the server asks the browser to store and send back on subsequent requests to the same site. The attributes are the whole security story.

Two practical notes. Cookies are sent on every matching request including images and scripts, so a large cookie is a per-request tax — keep them small, and put bulk state server-side keyed by an identifier. And the 4 KB per-cookie limit is real and is the reason JWT-in-a-cookie schemes fail once claims accumulate.

3.6CORS

The rule the browser enforces: a page from origin A may not read a response from origin B unless B says it may. An origin is scheme, host and port together, so https://shop.com and https://api.shop.com are different origins, and so are ports 3000 and 8080 on localhost.

Two things people misunderstand, and both cause wasted debugging. First, CORS is enforced by the browser, not by the server — the request often reaches your server and executes; the browser simply refuses to let the page read the response. Second, CORS is not a defence against anything. It protects users from malicious pages, not your API from malicious clients: curl, a mobile app and a server-side script ignore it entirely. Authorisation is a separate job (Chapter 7).

3.7Content negotiation

The client says what it can accept and the server chooses. Accept: application/json, text/html;q=0.8 means "JSON preferred, HTML acceptable" — the q value is a preference weight from 0 to 1, defaulting to 1.

In practice most APIs do very little of this: they serve JSON and ignore Accept. That is a defensible simplification, with two exceptions worth honouring. Accept-Encoding should be respected, because compression is a large win and clients genuinely differ. And if you serve more than one representation, you must send Vary: Accept or a shared cache will serve the wrong one.

A related use is versioning by media type — Accept: application/vnd.shop.v2+json — which keeps URLs stable at the cost of being invisible in logs and awkward to test from a browser. Chapter 5 weighs it against the alternatives.

The property that matters most is multiplexing. Under HTTP/1.1 a connection carries one request at a time, so browsers opened six connections per host and developers concatenated files, sprited images and sharded across domains to work around it. HTTP/2 makes all of that unnecessary and in some cases counterproductive — bundling everything into one file defeats granular caching when the protocol no longer penalises multiple requests.

HTTP/2's remaining weakness is that TCP still delivers bytes in order, so one lost packet stalls every multiplexed stream even though only one needed it. QUIC fixes this by tracking streams independently. The other QUIC benefit is connection migration: because a connection is identified by an id rather than by an IP-and-port tuple, moving from wifi to cellular does not break it — which matters a great deal for mobile clients and not at all for server-to-server traffic.

Why does returning 403 for an expired access token cause problems?

Because 403 tells the client "you are authenticated and this is not permitted", so a well-behaved client will not attempt to refresh — it will surface a permissions error to the user, who is confused because they have the right permissions and were working a minute ago. An expired token is an authentication failure, which is 401, and the client's refresh logic is keyed on exactly that status. Send 401 with a WWW-Authenticate header, the client exchanges its refresh token, retries, and the user notices nothing. The mirror-image mistake is equally common: returning 401 when an authenticated user lacks a permission, which sends the client into a refresh loop — it gets a new token, retries, gets 401 again, refreshes again — and eventually logs the user out for no reason. The clean rule is that 401 is about the credential and 403 is about the subject: if presenting a different or renewed credential could succeed it is 401, and if no credential this user could hold would succeed it is 403. There is one legitimate deviation, which is returning 404 instead of 403 to avoid confirming that a resource exists to someone not permitted to see it.

Your API works from Postman and fails from the browser with a CORS error. What is actually happening?

Nothing is wrong with the API, and Postman is not a useful test. CORS is enforced entirely by the browser: Postman, curl and any server-side client ignore it and will always succeed, so their working tells you nothing. What the browser is doing is one of two things. If the request is "simple" — a GET or a form-encoded POST with no custom headers — it was sent, your server responded, and the browser refused to let the page read the response because the Access-Control-Allow-Origin header was missing or did not match the page's origin. Note that the request ran, so any side effects happened. If the request is not simple — a JSON POST, a PUT or DELETE, or one with an Authorization header — the browser first sent an OPTIONS preflight, and that failed or was not answered, so the real request was never sent at all. The diagnostic is to open the network tab and look for the OPTIONS request: if it is there and failed, fix the preflight response (allow the method, allow the headers, respond 204); if there is no OPTIONS, fix the Access-Control-Allow-Origin on the actual response. And if the request sends cookies, remember that the wildcard * is not permitted with credentials — you must echo the specific origin and add Access-Control-Allow-Credentials: true.

A shared cache is serving one user's data to another. What header was probably missing?

Vary, or Cache-Control: private — and often both. A shared cache keys its entries on the method and URL. If a response differs based on a request header the cache does not know about, it stores whichever variant it saw first and serves it to everyone hitting that URL. For personalised responses the header that varies is Authorization or Cookie, so the first authenticated user's response gets served to the next. The correct fix is not Vary: Authorization, which technically works but produces a cache entry per user and defeats the point; it is Cache-Control: private for browser-only caching, or no-store for anything genuinely sensitive. Vary is the right answer for the non-personalised cases — Vary: Accept-Encoding when you serve gzip and brotli, Vary: Accept-Language when you serve translations. Two things make this dangerous in practice: it is invisible in development because there is no shared cache in front of a laptop, and once a wrong entry is stored it keeps being served until it expires, so the blast radius is everyone who requests that URL rather than one unlucky person.

Recap

  1. HTTP is stateless and client-initiated, which is what allows interchangeable processes and what makes server push awkward.
  2. Safe, idempotent, cacheable are properties infrastructure acts on. A GET that changes state will eventually be triggered by a crawler.
  3. Idempotency exists because responses get lost, not requests. It removes the retry dilemma.
  4. 401 is about the credential, 403 is about the subject. Confusing them produces refresh loops or false permission errors.
  5. 422 for semantic validation failures, 409 for state conflicts, 429 with Retry-After.
  6. Vary is the header people forget, and omitting it is how shared caches serve the wrong response to the wrong person.
  7. Cookie attributes are the security story: HttpOnly limits XSS damage, SameSite structurally blocks CSRF, Secure prevents plain-text leakage.
  8. CORS is browser-enforced and protects users, not your API. Non-simple requests preflight; credentials forbid the wildcard.
  9. HTTP/2 multiplexes and removes the reason for bundling; HTTP/3 removes TCP head-of-line blocking and survives a network change.
