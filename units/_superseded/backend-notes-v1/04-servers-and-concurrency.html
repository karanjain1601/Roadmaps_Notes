Servers, proxies and concurrency

Between the socket and your route handler sit two things that determine your capacity ceiling: a reverse proxy doing work your application should not, and a concurrency model deciding how many requests can be in flight at once. Most "we need more servers" conversations are actually about one of the numbers in this chapter.

~32 min read Proxies · concurrency models · pools 2 interactive panels Prerequisite: chapters 1–3

4.1What is listening

A server binds a socket to a port and calls accept(). Every connection that arrives is a file descriptor the process must do something with, and the something is the concurrency model. Everything else in this chapter follows from that one decision.

In production there are almost always at least two processes in the path: a reverse proxy facing the internet and your application behind it. Occasionally they are the same thing, and it is nearly always a mistake — the proxy is optimised for many slow connections and your application is optimised for executing your code, and those are different problems.

Buffering is the one that saves you

Without a buffering proxy, a client on a poor connection uploading a 5 MB file holds an application worker for the entire upload — thirty seconds of a worker doing nothing but receiving bytes. A hundred such clients exhausts a hundred-worker pool and the service is down, with the CPU idle. With buffering, the proxy absorbs the slow read into memory or disk and hands your application a complete request it can process in milliseconds. The same applies in reverse for slow readers. This is also the defence against Slowloris, the attack that consists entirely of being slow on purpose.

4.3Three concurrency models

Given a connection, the question is what resource handles it. There are three answers in wide use, and each has a characteristic shape under load.

The models, honestly

The decisive variable is how much of a request is waiting. From Chapter 1, a typical request spends 2% of its time computing and 98% waiting on the network and disk. A thread-per-request server holds a megabyte of stack and a scheduler slot for the whole 98%, which is why its ceiling is low. The other two models release the resource during the wait, which is the entire point of both.

One blocking call in an event loop

An event loop is a single thread running a queue of callbacks. Any operation that does not yield — a synchronous file read, a CPU-heavy JSON parse of a large payload, a bcrypt hash, a regular expression that backtracks — occupies that thread and every other in-flight request stops. A 200 ms synchronous call in a server handling 500 requests a second delays roughly a hundred of them. The failure is not a crash; it is a latency graph with unexplained spikes, and the cause is invisible in the code because the offending line looks ordinary. Move CPU work to a worker pool, and treat any synchronous library call as a defect.

Concurrency models under load

The same workload through each model. Throughput is capped by whichever resource runs out first.

4.4Little's Law

The most useful formula in capacity planning, and it is one line:

L = λ × W 
concurrency  =  arrival rate  ×  time in system

600 req/s × 84 ms  =  50.4 requests in flight at any moment

So you need at least 51 of whatever unit handles a request —
threads, goroutines, pool slots. Fewer and a queue forms.

It works in every direction:
  · How many threads do I need?        L = λW
  · What arrival rate can N threads take?   λ = L / W
  · What latency does my concurrency imply? W = L / λ

And it holds regardless of distribution, scheduling policy or
what the system is doing internally. It is an identity, not a
model — which is why it is worth memorising.

Two applications worth having at hand. Sizing: if you know your traffic and your p50 latency, you know your required concurrency, and if your thread pool is smaller than that number you are queueing by construction. Diagnosis: if concurrency is pinned at exactly the pool size, the pool is the bottleneck; if it is well below and latency is still high, the bottleneck is downstream.

4.5Connection pools

Your application does not open a database connection per request — a connection costs a TCP handshake, TLS, authentication and server-side memory, several milliseconds and a few megabytes each. Instead a fixed set is opened at start and borrowed.

Which makes pool size a real decision, and the intuition is backwards. A bigger pool is usually slower. Each connection is a server-side process or thread doing work; past the point where the database's cores and disks are saturated, adding connections adds context switching and lock contention without adding throughput — while every client thinks it is making progress.

Pool sizing, with the queueing maths

An M/M/c queue — c servers, Poisson arrivals. The Erlang C formula gives the probability of waiting and the average wait.

The rule of thumb, and why it is so small

A well-known starting formula for a database pool is connections = ((core_count × 2) + effective_spindle_count), which for a modern 8-core server on SSDs gives about 17 — far smaller than most people set. The reasoning: a query is either using a core or waiting for I/O, and once you have enough connections to keep every core busy plus a few to cover I/O waits, more connections only add contention. The counter-intuitive part is that reducing an over-sized pool usually improves throughput and latency at the same time, because the queue moves from inside the database, where it causes contention, to inside the application, where it is just a wait. Also multiply by your instance count before comparing against max_connections — that arithmetic is what an autoscaler quietly breaks.

4.6Timeouts, and the budget that shrinks

From Chapter 1: every remote call needs a timeout. The refinement is that timeouts must form a budget that shrinks as you go deeper, or the outer call gives up while inner calls keep holding resources.

A worked timeout budget 
User's patience                       3000 ms
  Proxy read timeout                  2500 ms   ← always shorter
    Application request deadline      2200 ms
      Payment provider call            800 ms   ← + 1 retry = 1600
      Database query                   250 ms
      Cache lookup                      50 ms
      Connection acquisition           100 ms

WRONG, and extremely common:
  proxy 30 s, app no deadline, db 30 s, http client default (none)

  A dependency stalls. Every layer waits. Workers fill. The
  health check queues behind them and fails. The load balancer
  removes the instance. Traffic moves to the others, which fill
  the same way. One slow dependency, total outage.

RULES
  · Each layer's timeout < its caller's remaining budget.
  · Pass the deadline down, do not re-derive it per layer.
  · Budget for retries: 800 ms × 2 attempts needs 1600 ms.
  · Connection acquisition needs its OWN timeout, separate from
    the query timeout — otherwise "the database is slow" and
    "the pool is empty" look identical and have opposite fixes.

4.7Graceful shutdown

A deployment replaces every process. Done carelessly, each replacement drops in-flight requests, and with a dozen deploys a day that is a steady trickle of errors nobody can reproduce. The sequence that avoids it:

  1. Receive SIGTERM. The orchestrator sends this and starts a countdown to SIGKILL — usually 30 seconds by default.
  2. Fail the readiness probe immediately, but keep serving. The load balancer needs a few seconds to notice and stop sending new work; until it does you must still answer.
  3. Wait out the propagation delay — typically 5–15 seconds, and this step is the one people omit. Closing the listener the instant SIGTERM arrives drops every request the balancer sends in the interval.
  4. Stop accepting new connections, and finish the in-flight ones.
  5. Drain background work: stop consuming from queues, let current jobs finish or return them for redelivery.
  6. Close pools and flush telemetry, then exit — before the SIGKILL deadline, or you get killed mid-request anyway.

The two constraints that must line up: your shutdown must complete faster than the orchestrator's grace period, and your grace period must exceed your longest legitimate request. If a request can take 60 seconds and the grace period is 30, you will drop requests on every deploy no matter how correct the sequence is.

4.8Backpressure and shedding

When arrivals exceed capacity, something must give. There are exactly three options and you are choosing one whether or not you decide to.

What happens when you are overloaded
OptionMechanismResult
QueueAccept everything and let it waitLatency grows without bound; memory grows; clients time out but the work is still queued and gets done for nobody. The default, and the worst
ShedReject beyond a threshold with 429 or 503Some requests fail fast and the rest are served normally. Almost always correct
Push backSlow the producer down — TCP flow control, bounded queues, rate limits at the edgeBest where the producer is under your control

The insight that makes shedding obvious once seen: an unbounded queue converts an overload into an outage. If clients time out at 3 seconds and your queue holds 10 seconds of work, every request you are processing is for a client that has already given up — you are at 100% CPU with a 0% success rate, and the only escape is to stop accepting. A bounded queue with fast rejection keeps the success rate at whatever your actual capacity is, which is the best achievable outcome.

Practically: cap the accept queue, cap the pool wait, return 429 with Retry-After rather than hanging, and prefer to shed the lowest-value traffic first — a health check and a batch export are not equally important. The System Design unit covers prioritised shedding and deadline-aware rejection.

Your Node.js service has p50 latency of 12 ms and occasional p99 spikes of 400 ms with no corresponding database slowness. What would you look for?

Something blocking the event loop. In a single-threaded runtime, any operation that does not yield stops every in-flight request, so the victims are not the request doing the work — they are the ones that happened to be queued behind it, which is why the spike appears on unrelated endpoints and correlates with nothing downstream. The usual culprits: JSON.parse or JSON.stringify on a large payload, synchronous filesystem calls (readFileSync in a request path, often inside a library), crypto.pbkdf2Sync or a bcrypt call with a high work factor, a regular expression that backtracks catastrophically on certain inputs, and large synchronous loops over arrays. The diagnostic is an event-loop lag metric — sample the delay on a fixed-interval timer and you will see the lag spike exactly when the latency does. Then find it with a CPU profile taken during the spike, or with --prof. The fixes are to move the work to a worker thread, stream rather than buffer, use the async variant, or precompute. Note that adding instances does not help: each one has the same single loop, so the spike simply follows the traffic.

Why can reducing your connection pool from 100 to 20 make the application faster?

Because the database is the constrained resource, not the pool, and a large pool moves the queue to the worst possible place. A database server has a fixed number of cores and a fixed disk; it can genuinely execute only so many queries at once. With 100 connections all issuing work, the server is context-switching between 100 backends, contending on shared buffers and locks, and each individual query takes longer — so the same total throughput arrives with much worse per-query latency, and lock contention can reduce throughput outright. With 20 connections the server runs near its actual parallelism, each query completes quickly, and the excess demand waits in the application's pool queue instead. Total throughput is the same or better, per-query latency is dramatically better, and the waiting is now visible as a pool-acquisition metric you can alert on rather than hidden as generalised slowness. The counter-intuitive summary is that the queue has to exist somewhere, and it is cheaper outside the database than inside it. This is also why a connection proxy such as PgBouncer helps: it lets many application instances share a small number of real backends.

You deploy twelve times a day and see a handful of 502s each time. What is the likely cause?

Almost certainly the propagation gap during shutdown — the process closes its listener as soon as it receives SIGTERM, while the load balancer is still sending it traffic. Health-check propagation is not instantaneous: the balancer polls every few seconds and usually requires two or three consecutive failures, so there is a window of five to fifteen seconds after SIGTERM in which requests are still arriving at a process that has stopped accepting them, and each one becomes a 502. The fix is the sequencing in §4.7: on SIGTERM, immediately fail the readiness probe but keep serving, sleep for longer than the propagation window, and only then stop accepting and drain. Two adjacent causes worth ruling out. If the numbers are larger, check that the grace period exceeds your longest request — a 30-second grace with a 60-second export means the export is killed every time. And check the proxy's upstream keep-alive: if the proxy holds an idle connection to a process that exits, the next request on that connection fails, which is fixed by having the application's keep-alive timeout be shorter than the proxy's so the application always closes first.

Recap

  1. A buffering reverse proxy absorbs slow clients, so a 30-second upload costs a proxy connection rather than an application worker.
  2. The concurrency ceiling follows from what a waiting request holds. A thread holds a megabyte; a goroutine holds a few kilobytes.
  3. One synchronous call stalls an entire event loop, and the symptom is latency spikes on unrelated endpoints.
  4. L = λW. Concurrency equals arrival rate times latency, always, and it sizes every pool you have.
  5. A bigger connection pool is usually slower, because the queue moves into the database where it causes contention.
  6. Multiply pool size by instance count before comparing with max_connections — this is what autoscaling breaks.
  7. Timeouts must shrink with depth, and connection acquisition needs its own, separate from the query timeout.
  8. Graceful shutdown needs a deliberate wait after failing the readiness probe, or you drop what the balancer sends in the gap.
  9. An unbounded queue converts overload into an outage. Shed early and fast.
