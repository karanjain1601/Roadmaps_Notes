Orientation: what a container is

There is no container. There is a process, and a set of kernel features that lie to it about what machine it is on. Every surprising thing Docker does — why your app sees 64 CPUs it cannot use, why a file written inside vanishes, why ps shows PID 1 — follows from that single fact, and this chapter establishes it before any command appears.

A container is not a small virtual machine

The most useful thing to unlearn first.

A virtual machine emulates hardware. It boots a second kernel, which manages its own memory, schedules its own processes, and talks to virtual disks and virtual network cards that a hypervisor presents to it. Two kernels are running, and the guest genuinely does not know it is a guest.

A container does none of that. Your containerised process is scheduled by the host kernel, appears in the host's process table, and its memory is host memory. What differs is only what it is allowed to see and consume:

MechanismRestrictsExample
NamespacesWhat the process can seeA process table with 3 entries instead of 400
cgroupsWhat the process can consume512 MB of memory and half a CPU
Capabilities, seccomp, LSMsWhat the process may doNo loading kernel modules, no changing the clock

That is the entire trick, and chapter 2 takes each apart. Everything else Docker provides — images, registries, Compose — is packaging and ergonomics around those three.

The consequence you will meet within a week

The kernel is shared. An Alpine container on an Ubuntu host is not running Alpine's kernel — it is running the host's kernel with Alpine's userspace files. So a container cannot use a kernel feature the host lacks, cannot load a kernel module of its own, and cannot run a Linux image on a Windows kernel without a Linux VM underneath. It is also why "it works in the container" is a much weaker guarantee than people assume when the hosts differ.

One process, two views

The same running program, seen from inside and outside.

Start a container and look at the process from both sides. It is one process; the numbers differ because the container is looking through a PID namespace.

Host view versus container view

One nginx process, observed from the host and from inside the container
on the host — ps -ef
inside the container — ps -ef

prove it yourself in three commands
$ docker run -d --name web nginx
$ docker exec web ps -ef | head -3        # nginx is PID 1 in here
$ ps -ef | grep '[n]ginx: master'          # ...and PID 48213 out here
$ docker inspect -f '{{.State.Pid}}' web   # the host PID, straight from the daemon
$ sudo ls -l /proc/$(docker inspect -f '{{.State.Pid}}' web)/ns    # its namespaces

Nothing is hidden here. The container's files are on the host's disk, its process is in the host's scheduler, and the /proc/<pid>/ns directory lists exactly which namespaces it was placed in. A container is a view, and the host has the unrestricted one.

They compose, and in practice they do

This is not a three-way choice. Nearly every container you run in a cloud is inside a virtual machine: the VM provides the hard boundary between customers, and containers provide density and packaging within one customer's slice. Docker Desktop on macOS and Windows does the same thing locally — a Linux VM you mostly do not notice, which is why bind-mount performance and file watching behave oddly there (chapter 11).

What problem containers actually solve

Two problems, and only one of them is about running things.

The packaging problem is the bigger one. Before containers, "deploy this application" meant reproducing an environment: the right runtime version, the right system libraries, the right locale, the right directory layout — described in a wiki page that was wrong. An image is that environment, captured as a file, byte-identical everywhere it runs.

ProblemPre-container answerContainer answer
"Works on my machine"A runbook, and hopeShip the userspace with the app
Two apps needing different library versionsTwo servers, or careful painTwo images on one host
Bringing a new developer upA day of setupdocker compose up
Identical staging and productionAspirationalThe same digest in both
Scaling a stateless serviceProvision a VMStart another process

And where they are the wrong tool

  • A single-machine hobby app. A systemd unit and a package is less machinery, and easier to debug at 2am.
  • Untrusted multi-tenant code. Shared kernel means the boundary is thinner than a VM's. Use a VM, or a sandboxed runtime like gVisor or Kata (chapter 21).
  • Stateful systems you have not thought about. Databases in containers are fine, and are also how people lose data by not reading chapter 11 first.
  • Desktop GUI applications. Possible, unpleasant, and rarely worth it.
  • Anything needing the host kernel changed — custom modules, some eBPF work, kernel debugging.

Docker, containerd, runc and OCI

Four names for four different layers, routinely confused for each other.

"Docker" is a product built on a stack of smaller pieces, most of which are standardised and replaceable. Knowing which layer a term belongs to makes the ecosystem legible:

LayerPieceDoes
You typedocker CLISends HTTP requests to a daemon over a socket
DaemondockerdBuilds images, manages networks and volumes, exposes the API
Runtime managercontainerdPulls images, manages container lifecycle and snapshots
Shimcontainerd-shimOne per container, so the daemon can restart without killing it
Low-level runtimeruncActually calls clone(), sets up namespaces and cgroups, and executes your process

The OCI — Open Container Initiative — publishes the three specifications that make those layers interchangeable:

SpecificationDefinesSo that
Runtime specA filesystem bundle plus config.json, and what a runtime must do with itrunc, crun, gVisor and Kata are drop-in alternatives
Image specLayers, manifests, image configuration, digestsAn image built by Docker runs under Podman or Kubernetes
Distribution specThe registry HTTP APIDocker Hub, GHCR, ECR and a self-hosted registry all speak the same protocol
Why this matters practically

Because of these specifications, almost nothing you learn here is Docker-specific. Your images are OCI images; Kubernetes runs them without Docker installed anywhere (it dropped the Docker shim in 1.24 and talks to containerd directly); Podman runs them with no daemon at all. When someone says "we are moving off Docker", they usually mean replacing the daemon and CLI while keeping every image and registry unchanged.

What adding yourself to the docker group means

Membership of the docker group is equivalent to root on that machine, and not approximately — anyone who can talk to the daemon socket can start a container that mounts / and writes to it. Convenient on your laptop, unacceptable on a shared server. Rootless mode (chapter 18) exists precisely to remove this, and it is what to reach for on anything multi-user.

check what you are actually running
$ docker version                # client and server versions, separately
$ docker info                    # storage driver, cgroup version, runtimes, rootless?
$ docker info -f '{{.CgroupVersion}} {{.Driver}} {{.DefaultRuntime}}'
$ docker context ls              # which daemon is this CLI talking to?

Two lines of that output matter later: the cgroup version (v2 changes how limits are expressed — chapter 10) and the storage driver (overlay2 almost everywhere, and the subject of chapter 3).

Your first minute, explained

Six commands, and what each one really did.

an annotated first session
$ docker run --rm -it alpine sh
#   pull alpine if absent, create a container from it, give it namespaces
#   and cgroups, run `sh` as PID 1, attach your terminal, delete it on exit

/ # ls /                 # alpine's filesystem, not yours
/ # ps -ef               # two processes in the entire world
/ # hostname             # a random hex string — the UTS namespace
/ # cat /proc/version    # ...the HOST kernel. Look closely at this one
/ # exit

$ docker ps -a           # nothing: --rm deleted it
$ docker images          # alpine is still cached locally

cat /proc/version is the line worth pausing on. Inside an Alpine container on an Ubuntu host it reports the Ubuntu kernel, because there is only one kernel. That single output disproves the small-virtual-machine model more efficiently than any diagram.

FlagMeans
--rmDelete the container when it exits. Without it, exited containers accumulate
-iKeep stdin open — otherwise an interactive shell exits instantly
-tAllocate a pseudo-terminal, so you get a prompt and line editing
-dDetach: run in the background and print the container id
--nameA stable name, instead of nostalgic_hopper

-it is one of the most-typed strings in the industry and almost nobody separates the two flags in their head. -i connects stdin; -t makes it look like a terminal. You need both for a shell, only -i to pipe data in, and neither for a service.

The short version

Chapter 1 in seven lines

  • A container is a process with a restricted view, produced by namespaces (what it sees), cgroups (what it consumes) and capabilities (what it may do).
  • The kernel is shared. An Alpine container on an Ubuntu host runs the Ubuntu kernel with Alpine's files.
  • The process exists in the host's process table with a different PID; docker inspect -f '{{.State.Pid}}' shows it.
  • VMs isolate with hardware virtualisation and boot a second kernel; containers are cheaper, start in milliseconds, and have a thinner security boundary.
  • The bigger problem containers solve is packaging, not running — the environment becomes a file.
  • Docker is a stack: CLI → dockerd → containerd → shim → runc, standardised by the OCI runtime, image and distribution specifications.
  • Membership of the docker group is equivalent to root on that host.

Check yourself

Someone says "we run Alpine containers, so we get Alpine's kernel and its security patches". Correct them.

There is no Alpine kernel involved. The image supplies userspace — libc, busybox, the package manager — and every process in it is executed by the host kernel. So kernel CVEs are patched by updating the host, not by rebuilding the image; and conversely a kernel feature the host lacks is unavailable no matter what the image contains. cat /proc/version inside the container reports the host kernel, which is the fastest way to demonstrate it.

Why can a container start in 50 ms when a VM takes 30 seconds?

Because nothing boots. Starting a container is roughly: unpack or reuse the image layers as a filesystem, create the namespaces, write the cgroup limits, and exec the process — all operations on an already-running kernel. A VM must initialise virtual hardware, boot a kernel, run an init system and start services before your process exists. The demo above models the same difference for memory: a VM pays a full guest OS per instance, a container pays almost nothing.

A colleague proposes running customers' submitted code in containers on a shared host. What is your concern, and what would you propose?

The isolation boundary is the kernel, and it is shared with every other tenant — so a kernel vulnerability or one misconfigured flag (a mounted Docker socket, an added capability, --privileged) is a full compromise rather than a contained one. Containers are designed to isolate your own workloads from each other, not to defend against hostile code. Propose one VM per tenant with containers inside it, or a sandboxed runtime such as gVisor or Kata that puts a real boundary under the container. Chapter 18 covers hardening if the design stands regardless.

Kubernetes "removed Docker support" in 1.24. Do your images still work, and why?

Yes, unchanged. What was removed was dockershim — the adapter letting Kubernetes drive dockerd — and Kubernetes now talks to containerd (or CRI-O) directly through the CRI. Your images are OCI images, and both runtimes consume that format, so nothing about building or publishing changes. This is the practical payoff of the OCI specifications: the daemon is replaceable while the artefacts and registries stay put.
