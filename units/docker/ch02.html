Namespaces, cgroups and capabilities

Three kernel mechanisms, each answering a different question. Namespaces: what can this process see? cgroups: how much may it use? Capabilities: what is it allowed to do? Docker is a convenient way to set all three at once — and when a container behaves strangely, the useful first question is which of the three is responsible.

The namespaces

Each one virtualises a single global kernel resource.

A namespace wraps one class of system resource so that processes inside it see their own instance of it. There are eight, added to Linux over eighteen years, and Docker uses six of them by default.

NamespaceVirtualisesDocker default
mntThe mount table — which filesystems exist and wherenew
pidProcess IDs. The first process becomes PID 1new
netInterfaces, addresses, ports, routes, firewall rulesnew
utsHostname and NIS domain namenew
ipcSystem V IPC and POSIX message queuesnew
cgroupThe visible cgroup hierarchy rootnew
userUID and GID mappingsshared — see below
timeOffsets for the monotonic and boot clocksshared
The one Docker does not use by default

Without a user namespace, UID 0 in the container is UID 0 on the host — the same credential, merely restricted by capabilities and seccomp. That is why a bind-mounted host directory is writable by a container running as root, and why an escape from a root container is an escape to host root. Enabling user namespaces (userns-remap) or rootless mode maps container root to an unprivileged host UID instead, and chapter 18 covers both.

lrwxrwxrwx 1 root root 0 … uts    -> 'uts:[4026532504]'

$ lsns -p $PID                       # the same information, readably
$ sudo nsenter -t $PID -n ip addr    # enter just its network namespace
$ unshare --pid --fork --mount-proc ps -ef    # build a PID namespace by hand

The inode numbers are the namespaces' identities: two processes with the same number are in the same namespace. Note user matching the host's — that is the default sharing described above, visible in one command.

Sharing on purpose: the pod model

--net=container:web puts a second container in the first one's network namespace, so both see the same interfaces and can talk over localhost. This is exactly what a Kubernetes pod is: several containers sharing a network and IPC namespace while keeping separate mount namespaces. Knowing it is just a namespace flag makes the pod concept much less mysterious when you meet it in chapter 22.

cgroups: how much it may use

Namespaces do not limit consumption at all. A container without cgroup limits can exhaust the host.

Control groups organise processes into a tree and attach resource controllers to each node. Version 2 — the unified hierarchy, the default on every current distribution — exposes them as plain files under /sys/fs/cgroup:

cgroup v2 fileDocker flagMeaning
memory.max-m / --memoryHard limit. Exceed it and something in the group is OOM-killed
memory.high--memory-reservationSoft limit: reclaim aggressively above this, but do not kill
memory.swap.max--memory-swapSwap allowance, counted separately in v2
cpu.max--cpusquota period in microseconds. 50000 100000 is half a CPU
cpu.weight--cpu-sharesRelative share, and only meaningful when CPUs are contended
cpuset.cpus--cpuset-cpusWhich physical CPUs it may run on
pids.max--pids-limitProcess count cap — cheap protection against a fork bomb
io.max--device-write-bpsBlock device throughput limits
read the limits the kernel actually applied
$ docker run -d --name app --memory 512m --cpus 1.5 nginx
$ CG=$(docker inspect -f '{{.HostConfig.CgroupParent}}' app)
$ cat /sys/fs/cgroup/system.slice/docker-*.scope/memory.max
536870912
$ cat /sys/fs/cgroup/system.slice/docker-*.scope/cpu.max
150000 100000

$ docker stats --no-stream            # live usage against those limits
$ cat /sys/fs/cgroup/.../cpu.stat      # nr_throttled, throttled_usec
$ cat /sys/fs/cgroup/.../memory.events  # oom, oom_kill counters

cpu.stat is the file that settles arguments. If nr_throttled is climbing, your container is hitting its quota and being stopped mid-work — regardless of whether the host looks busy.

Limits, throttling and the OOM killer

Two failure modes, and the trap that causes most of them.

--cpus does not change what nproc reports

A CPU quota is enforced by the scheduler; it does not alter /proc/cpuinfo or the process's CPU affinity mask. So nproc, os.cpus().length and runtime.NumCPU() all still report the host's CPU count, and a runtime that sizes its thread pool from that will create sixteen worker threads to share half a CPU. The result is heavy throttling and latency that looks like a mysterious GC problem. --cpuset-cpus does change the affinity mask, so it is visible to those APIs — which is why pinning sometimes fixes a problem that quota alone made worse.

RuntimeRespects --cpus quota?What to do
JVM 10+ (and 8u191+)yes — reads the cgroupLeave UseContainerSupport on; tune with -XX:MaxRAMPercentage
Node.jsnoSet UV_THREADPOOL_SIZE; do not trust os.cpus() for pool sizing
Gono — affinity onlySet GOMAXPROCS explicitly from the limit
Python (multiprocessing)noPass the worker count in; os.cpu_count() is the host's
nginx worker_processes autonoSet an explicit number

Exit code 137, and how to confirm it

was it the OOM killer?
$ docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' app
137 true

# 137 = 128 + 9, i.e. killed by SIGKILL. 143 = 128 + 15, a clean SIGTERM.
$ dmesg | tail                                  # the kernel's own record
$ cat /sys/fs/cgroup/.../memory.events           # oom_kill counter
$ docker events --filter event=oom               # watch for it live

An important subtlety: the limit counts page cache as well as anonymous memory. A process that reads a large file can push the group to its limit through cache alone — but cache is reclaimable, so the kernel evicts it rather than killing. This is why memory.current often sits suspiciously close to memory.max on a healthy container, and why that is not itself a problem.

Capabilities: what it may do

Root in a container is a partial root, and knowing which parts matters.

Linux splits root's powers into about forty capabilities. Docker grants a small subset by default, so a container's UID 0 can chown files and bind port 80 but cannot load a kernel module, change the system clock, or mount a filesystem.

Kept by default (the useful ones)Allows
CHOWN, FOWNER, FSETID, DAC_OVERRIDEIgnore file ownership and permission checks
SETUID, SETGID, SETPCAPDrop privileges — which well-behaved images do at startup
NET_BIND_SERVICEBind ports below 1024
NET_RAWRaw sockets — ping, and also packet spoofing
KILL, SYS_CHROOT, MKNOD, AUDIT_WRITESignal any process in the container, chroot, make device nodes
Dropped by defaultWould allow
SYS_ADMINMounting filesystems, and so much else that it is effectively root
SYS_MODULELoading kernel modules — a straight escape
SYS_TIMEChanging the host clock, since the time namespace is shared
NET_ADMINReconfiguring interfaces and firewall rules
SYS_PTRACEInspecting other processes' memory
SYS_BOOTRebooting the host
the pattern worth adopting
# start from nothing and add only what the app needs
$ docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx

$ docker run --rm --cap-drop=ALL alpine ping -c1 1.1.1.1
ping: permission denied (are you root?)          # NET_RAW is gone. Correct.

$ docker run --rm -it alpine sh -c 'apk add -q libcap; capsh --print' | head -3
$ docker run --security-opt no-new-privileges …   # block setuid escalation
--privileged is not "a bit more access"

It grants every capability, exposes all host devices, and disables seccomp and AppArmor. A privileged container can mount the host's disk and edit anything on it, so it is equivalent to handing over the machine. It appears in tutorials because it makes a problem go away; the fix is almost always one specific capability or one device, and chapter 18 shows how to find which.

Beyond capabilities sit two more layers: the default seccomp profile, which blocks several dozen syscalls outright, and an AppArmor or SELinux profile restricting file and capability access further. All three are on by default and all three are switched off by --privileged.

What none of this isolates

Worth knowing before you rely on the boundary.

Shared regardlessConsequence
The kernelA kernel vulnerability affects every container on the host
Kernel parameters (sysctl)Mostly host-wide; only a few are namespaced
The system clockSame time everywhere — the time namespace is unused by default
Page cache and memory bandwidthA noisy neighbour degrades others without exceeding any limit
CPU caches and hardware side channelsNot addressable at this layer at all
/proc entries that are not namespaced/proc/cpuinfo, /proc/meminfo report the host's figures

That last row is the origin of the nproc trap above, and of the same problem for memory: a JVM without container support reads /proc/meminfo, sees 64 GB, sizes its heap accordingly, and gets OOM-killed at 512 MB. The tool for making the container's view honest is lxcfs, but the practical answer is to pass limits into the application explicitly.

Assembling a container by hand

Ten minutes that make the rest of the unit obvious.

Nothing about a container requires Docker. With a root filesystem and three commands you can build one, and doing it once converts the model from something read into something operated:

a container with no Docker involved
# 1. a root filesystem: borrow one from an image
$ mkdir -p /tmp/rootfs && docker export $(docker create alpine) | tar -C /tmp/rootfs -x

# 2. a cgroup with limits
$ sudo mkdir -p /sys/fs/cgroup/handmade
$ echo '100000 100000' | sudo tee /sys/fs/cgroup/handmade/cpu.max     # one CPU
$ echo 268435456        | sudo tee /sys/fs/cgroup/handmade/memory.max  # 256 MB

# 3. namespaces, the new root, and the process
$ sudo unshare --pid --net --mount --uts --ipc --fork --mount-proc=/tmp/rootfs/proc \
    chroot /tmp/rootfs /bin/sh
/ # hostname handmade && ps -ef        # PID 1, own hostname, own mounts

That is a container: a chroot for the filesystem view, unshare for the namespaces, a cgroup for the limits. What Docker adds is images, layer caching, networking, volumes, a registry protocol and a coherent CLI — enormous convenience over exactly this.

Why chroot is not enough on its own

chroot changes the apparent root directory and nothing else: the process keeps the host's PID view, network, hostname and full resource access, and a process with SYS_CHROOT can escape a chroot with a few lines of C. Real containers use pivot_root inside a mount namespace, which detaches the old root entirely rather than merely stepping past it.

The short version

Chapter 2 in eight lines

  • Namespaces = visibility, cgroups = consumption, capabilities = permission. Ask which one is responsible before debugging.
  • Docker creates six namespaces by default and shares the user namespace, so container root is host root restricted by capabilities.
  • ls -l /proc/<pid>/ns shows the namespace inode numbers; matching numbers mean the same namespace.
  • --net=container:other shares a network namespace — that is precisely what a Kubernetes pod is.
  • Namespaces limit nothing. Without cgroup limits one container can exhaust the host.
  • --cpus sets a scheduler quota and does not change nproc; --cpuset-cpus does, because it changes the affinity mask.
  • Exit code 137 means SIGKILL, usually the OOM killer; confirm with State.OOMKilled and memory.events.
  • --privileged grants all capabilities, all devices, and disables seccomp and AppArmor — it is equivalent to giving away the host.

Check yourself

A Node service given --cpus=0.5 has terrible tail latency, and the host is idle. What is happening?

Quota throttling. --cpus=0.5 sets cpu.max to 50000 100000: the container may use 50 ms of CPU per 100 ms period, and once it is spent every thread is stopped until the next period — producing latency spikes even on a completely idle host. Node makes it worse because os.cpus() still reports every host CPU, so libraries size worker pools from that and oversubscribe the quota. Check nr_throttled in cpu.stat to confirm, then either raise the quota or cap concurrency (UV_THREADPOOL_SIZE, explicit worker counts) to match what the container actually has.

Why is a file created by a root container in a bind-mounted host directory owned by host root?

Because there is no user namespace by default, so container UID 0 and host UID 0 are the same credential — the kernel records the write as root's. It is not a translation or a coincidence. Consequences: the file may be unreadable by your normal user afterwards, and an escape from that container is an escape to host root. Fixes are to run as a non-root UID matching the host user (--user $(id -u):$(id -g)), or to enable user namespace remapping so container root maps to an unprivileged host UID.

docker run --rm --cap-drop=ALL alpine ping 1.1.1.1 fails with permission denied, running as root. Why?

ping needs raw sockets, which requires CAP_NET_RAW — normally granted by default and removed here by --cap-drop=ALL. This is the clearest demonstration that container root is a partial root: the UID is 0, the capability set is nearly empty, and the kernel checks capabilities rather than the UID. Adding --cap-add=NET_RAW restores it, and the fact that you had to name it is the point of the drop-all-then-add pattern.

A container has -m 512m, and memory.current sits at 508 MB constantly. Is it about to be killed?

Probably not. The limit counts page cache as well as anonymous memory, and cache is reclaimable — so a process reading files will fill the group to near its limit and the kernel will simply evict cache as needed. What indicates real trouble is the anonymous portion approaching the limit, or a rising oom_kill counter in memory.events. Read memory.stat to separate anon from file before concluding anything from memory.current alone.
