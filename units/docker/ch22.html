Chapter 22Beyond Docker

Kubernetes, from here

Kubernetes runs the same containers, built from the same Dockerfiles, pulled from the same registries — chapter 21 established that the bottom of the stack is identical. What it adds is a scheduler and a set of control loops, and almost everything that surprises a Docker user comes from two specific additions: the Pod, and the split between requests and limits.

The framing that helps most: Kubernetes is a distributed scheduler with an extensible API, not a bigger Docker. Every object is a record of intent, and a controller loop works continuously to make reality match. That is why kubectl apply feels different from docker run — you are not starting a container, you are recording that one should exist.

The Pod

The one concept with no Docker equivalent — except the one you already met.

A Pod is a group of containers sharing a network namespace, an IPC namespace and a lifecycle. You have seen this: docker run --network container:api in chapter 12 shares exactly that, and Podman's pods in chapter 21 are the same idea. Inside a Pod, containers reach each other on localhost, and the Pod has one IP address.

what the shared namespace buys you

Init containers are the answer to depends_on

Chapter 13 established that depends_on waits only for a container to start, and that service_healthy plus application retries is the real fix. Kubernetes has no depends_on at all — the equivalents are an init container that blocks until a dependency answers, and readiness probes that keep a Pod out of the load balancer until it can serve. The conclusion is the same one chapter 13 reached: the application must retry, because nothing above it can guarantee ordering after start-up.

Requests and limits

The split that has no Docker equivalent, and the thing most often got wrong.

Chapter 10's --memory and --cpus are limits. Kubernetes adds requests, which are what the scheduler uses to decide where a Pod fits — and the relationship between the two decides your QoS class, and therefore what gets killed when a node runs short.

CPU limits and memory limits fail in opposite ways

CPU is compressible: exceeding a CPU limit means throttling, so the Pod gets slower and survives — chapter 10's latency cliff, unchanged. Memory is not compressible: exceeding a memory limit means an OOM kill, exit 137, exactly as in chapters 10 and 19. That asymmetry drives the usual advice: set memory requests equal to limits, and be cautious with CPU limits, because a CPU limit buys predictability at the cost of throughput you already paid for.

Probes

One HEALTHCHECK becomes three, and they do different jobs.

ProbeOn failureUse for
startupKeeps trying; blocks the other twoSlow boots — a JVM, a large cache warm-up

the shape that behaves well
      startupProbe:                     # up to 60 × 2s = two minutes to boot
        httpGet: { path: /healthz, port: 3000 }
        periodSeconds: 2
        failureThreshold: 60

      readinessProbe:                   # checks dependencies — safe to fail
        httpGet: { path: /readyz, port: 3000 }
        periodSeconds: 5
        failureThreshold: 2

      livenessProbe:                    # checks ONLY this process — no dependencies
        httpGet: { path: /healthz, port: 3000 }
        periodSeconds: 10
        failureThreshold: 3
A liveness probe that checks the database turns an outage into an outage plus a restart storm

If /healthz queries the database and the database becomes briefly unavailable, every replica fails its liveness probe simultaneously and every one is restarted — so when the database recovers there is no warm capacity, connection pools are cold, and the restarts continue while the Pods boot. The rule is a hard one: liveness checks only this process; readiness may check dependencies. A readiness failure removes the Pod from the load balancer and leaves it running, which is recoverable; a liveness failure destroys it.

The distinction that matters most

Using Kubernetes and operating Kubernetes are different jobs, and conflating them is where the "too complex" reputation comes from. A managed cluster hands you the API and takes the control plane, etcd, upgrades and node management away — which removes most of the operational burden while keeping the model. Self-hosting is a legitimate choice with an entirely different staffing requirement. Decide which one you are signing up for before deciding whether it is complex.

The short version

Chapter 22 in eight lines

  • Kubernetes is a distributed scheduler with control loops. The container layer underneath is what chapter 21 described.
  • kubectl apply records intent; a controller makes reality match. That is the whole mental shift.
  • A Pod shares a network and IPC namespace — the same thing as --network container: from chapter 12.
  • There is no depends_on: init containers, readiness probes, and the application retrying.
  • Requests schedule; limits enforce. Their relationship sets the QoS class and therefore eviction order.
  • Exceeding a CPU limit throttles; exceeding a memory limit is an OOM kill. Set memory requests equal to limits.
  • Liveness checks only this process. A liveness probe that checks the database restarts every replica during an outage.
  • The drain problem persists: terminationGracePeriodSeconds must exceed the drain time, or a green rollout still drops requests.

Check yourself

Your database has a 90-second blip. Every API pod restarts, and recovery takes twenty minutes rather than ninety seconds. What did you configure wrongly?

A liveness probe that checks the database. Every replica failed it at once, so every container was restarted — and when the database came back there was no warm capacity: cold connection pools, caches empty, and pods still booting while traffic arrived. That is why recovery took far longer than the outage. The fix is the rule: liveness tests only this process (can it serve a trivial request?), while readiness may test dependencies — a readiness failure pulls the pod out of the Service and leaves it running, so it rejoins immediately when the database returns. Nothing is destroyed.

A pod has requests: { memory: 256Mi } and limits: { memory: 2Gi }. What QoS class, and what is the risk?

Burstable, because a request is set and does not equal the limit. Two risks follow. The scheduler places it using the 256Mi request, so a node can accept many such pods whose limits sum far above its capacity — legitimate overcommit until they all grow. And under node memory pressure, Burstable pods are evicted in order of how far usage exceeds requests, so a pod using 1.5Gi against a 256Mi request is near the front of the queue. For anything whose memory use is predictable, set requests equal to limits and get Guaranteed. The model above shows the eviction ordering.

What in Kubernetes replaces depends_on: { db: { condition: service_healthy } }?

Nothing, directly — and that is deliberate, because ordering guarantees at start-up do not survive anything restarting later. The pieces: an init container that blocks until the database answers, so the app container does not start prematurely; a readiness probe that keeps the pod out of the Service until it can serve; and most importantly, connection retries with backoff in the application. Chapter 13 reached the same conclusion from the Compose side — service_healthy fixes only the cold start, and the 3am database restart needs the application to cope.

A colleague says containerising the app was the hard part and Kubernetes will be easy from here. Assess that.

Half right, and the useful half. Everything about the artefact transfers: images, Dockerfiles, digest pinning, layer caching, the capability set, resource limits, logging to stdout. What does not transfer is a set of genuinely new concepts — the Pod, requests versus limits and QoS, three kinds of probe, controllers and reconciliation, Services and Ingress, and NetworkPolicy replacing per-network isolation. That is a real learning curve, though a much smaller one than starting from scratch. And the honest question first is whether it is needed at all: two hosts and a load balancer removes the single point of failure without any of it.
