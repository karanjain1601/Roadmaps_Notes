Observability and debugging

A container is a process you cannot easily see. Its logs vanish with it, its filesystem may have no shell, and its exit code is often the only evidence you get — so the work is in arranging beforehand that there will be something to look at, and in reading the little you have properly when there is not.

The logging contract

Write to stdout. Let the platform decide where it goes.

Chapter 9 noted that docker logs only ever shows what PID 1 wrote to stdout and stderr. That is not a limitation to work around — it is the contract. A container that writes to a file inside itself has produced logs that no aggregator can collect and that disappear with the container.

Existing containers keep the driver they were created with, so this only affects new ones — after changing it, recreate everything or the old containers keep growing. The local driver is the better default: it rotates and compresses out of the box, and docker logs still works.

Delivery mode

The default couples your application's availability to your log backend.

mode=blocking (default)mode=non-blocking
When the backend is slowThe application's writes blockBuffered, then dropped

choosing to lose logs rather than requests
$ docker run --log-driver fluentd \
    --log-opt fluentd-address=logs.internal:24224 \
    --log-opt mode=non-blocking \
    --log-opt max-buffer-size=8m \
    --log-opt fluentd-async=true \
    app
A log aggregator outage taking down the application

With a remote driver in blocking mode, a write to stdout is a write to a socket that the daemon is trying to deliver — so when the aggregator is unreachable or slow, the container's own write() calls block and the application stops serving. This produces one of the most confusing incidents available: every service degrades simultaneously, nothing in the application changed, and the cause is a logging system nobody considers part of the request path. For a remote driver, set mode=non-blocking and accept the possibility of dropped lines.

Debugging an image with no shell

Chapter 7 removed the shell on purpose. Here is the replacement.

a debug container sharing the target's namespaces
# the network namespace: see exactly what it sees (chapter 12)
$ docker run --rm -it --network container:api nicolaka/netshoot
  ss -tlnp; dig db; curl -v http://db:5432; tcpdump -i eth0 -n

# the PID namespace: see its processes, and reach its filesystem through /proc
$ docker run --rm -it --pid container:api --cap-add SYS_PTRACE alpine sh
/ # ps aux
/ # ls /proc/1/root/app          # the target's filesystem, via its PID
/ # cat /proc/1/environ | tr '\0' '\n'

# or from the host, into the namespaces directly
$ PID=$(docker inspect -f '{{.State.Pid}}' api)
$ sudo nsenter -t $PID -n -p ss -tlnp
$ sudo ls /proc/$PID/root/app

/proc/<pid>/root is the trick worth remembering

Every process's root filesystem is reachable through /proc, so a debug container sharing the PID namespace can read a distroless container's files without that container having any tooling at all. It works because the mount namespace is visible through /proc even when the target has no shell, no ls and no package manager — which is exactly the situation chapter 7's small images create.

In production

Making a container's output attributable to a service.

labels as the join key
services:
  api:
    labels:
      com.acme.service: api
      com.acme.version: "2.4.1"
      com.acme.team: platform
    logging:
      driver: local
      options: { max-size: 20m, max-file: "5" }
ProblemFix
Logs identified only by a container IDLabels, and a shipper configured to attach them
A restarted container looks like a new serviceJoin on the service label, not the container ID
Cannot correlate a request across containersA trace ID propagated in headers and logged
Log volume costs more than the computeSample debug lines; keep errors; shorten retention
Metrics disappear when a container is replacedScrape by label; keep series across container identity

The recurring theme is that container identity is not service identity. A container ID changes on every deploy and every restart, so anything keyed on it fragments — logs, metrics, dashboards and alerts all need to key on a label you control. Set the labels once in Compose and the rest of the stack has something stable to join on.

The short version

Chapter 19 in eight lines

  • Write to stdout and stderr. Logs in a file inside the container cannot be collected and die with it.
  • The default json-file driver has no rotation — a chatty container fills the host disk.
  • The local driver rotates and compresses by default and still supports docker logs. Prefer it.
  • Changing the daemon default only affects new containers.
  • A remote driver in blocking mode couples your uptime to the log backend. Use mode=non-blocking.
  • Watch anon memory, nr_throttled and RestartCount — not total memory and not CPU average.
  • The healthcheck's recorded output is a diagnostic channel, not just a status.
  • For an image with no shell, share its namespaces from a toolbox container and read /proc/<pid>/root.

Check yourself

A host runs out of disk. /var/lib/docker/containers is 340 GB. Diagnose and fix, including for containers already running.

The json-file driver with no max-size, which is the default — logs grow without limit until the disk fills, and one chatty container can do it alone. Immediate relief: find the largest files under /var/lib/docker/containers/*/​*-json.log and truncate them (: > file rather than deleting, since the daemon holds the handle). Then set log-driver: local with max-size and max-file in daemon.json — and note that this applies only to new containers, so everything running must be recreated or it keeps growing. The model above shows how quickly it accumulates at a given rate.

Your log aggregator has an outage and every service starts timing out. Nothing about the applications changed. Explain.

A remote logging driver in the default blocking mode. Each write to stdout is a write the daemon must deliver, so when the aggregator is unreachable those writes block, and the applications stall inside their own logging calls. Everything degrades at once, which is what makes it look like an infrastructure-wide failure rather than a logging one. Fix by setting mode=non-blocking with a max-buffer-size: you then lose log lines during an outage instead of losing the service. That is the right trade for almost every workload.

A distroless container is misbehaving. No shell, no ls, and you cannot rebuild it. How do you look inside?

Bring the tooling in a second container that shares its namespaces. For network questions: docker run --rm -it --network container:api nicolaka/netshoot, which sees exactly the interfaces, routes and DNS the target sees. For the filesystem: share the PID namespace and read the target's root through /proc/1/root/…, which works because /proc exposes the mount namespace regardless of what tooling the target has. Also useful without any of that: docker cp api:/path -, docker diff api, and docker inspect. If you can restart it, the :debug variant of the distroless base adds busybox.

A container exits with 137 and OOMKilled: false. What are the two candidate explanations, and how do you tell them apart?

137 means SIGKILL, and OOMKilled: false rules out this container's memory limit. Either a docker stop exceeded its grace period — the process ignored SIGTERM, so the daemon killed it (chapter 9) — or something else sent SIGKILL, most often the host OOM killer selecting this container as a victim. Distinguish by the uptime: a stop timeout produces an exit at almost exactly the --stop-timeout value, which is a suspiciously round number. Confirm with dmesg for a kernel OOM naming a different cgroup, and with docker events for a preceding kill signal=15. The diagnoser above keys on exactly this pair of fields.
