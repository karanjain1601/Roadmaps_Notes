Containers in CI

A container pipeline has one rule and everything else is optimisation. Build the image once, and carry its digest through every later job — because the moment a stage rebuilds, the thing you tested and the thing you deploy are different artefacts, and no amount of green ticks tells you so.

Build once, pass the digest

The rule, and the three ways to implement it.

the build job publishes a digest
jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: build
        uses: docker/build-push-action@v6
        with:
          context: .
          target: runtime
          push: true
          tags: ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: mode=max
          sbom: true

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: |
          docker run --rm \
            ghcr.io/${{ github.repository }}@${{ needs.build.outputs.digest }} \
            npm test

Pushing before the tests pass is fine

The instinct is to withhold the push until everything is green, which forces either a rebuild or a tarball. Push immediately under a per-commit tag instead (sha-<commit>, chapter 15) — an image in a registry is not deployed just because it exists, and a retention rule can expire unpromoted commit tags. Promotion, not pushing, is the gate. That inversion is what makes build-once practical.

Cache on ephemeral runners

Chapter 6's cache, on a machine that is deleted after every job.

BackendWhere it livesNotes
type=ghaThe Actions cache serviceEasiest on GitHub. Branch-scoped and size-capped — see below
type=registryA tag in your registryPortable across CI systems and shareable between repositories
type=s3A bucket you ownNo size cap, and you control retention
type=localA directoryOnly useful with a persistent runner
type=inlineEmbedded in the pushed imageSimple, but mode=max is unavailable
registry cache, which works anywhere
$ docker buildx build \
    --cache-from type=registry,ref=ghcr.io/acme/api:buildcache \
    --cache-to   type=registry,ref=ghcr.io/acme/api:buildcache,mode=max \
    -t ghcr.io/acme/api:sha-$GIT_SHA --push .
Two things about the GitHub Actions cache

It is branch-scoped: a pull request branch can read the default branch's cache but cannot write into it, and sibling branches cannot see each other's. So the first build on a new branch warms nothing for anyone else, and a long-lived branch drifts. It is also size-capped per repository with least-recently-used eviction, so a mode=max cache for several large images can evict itself and produce mysteriously variable build times. When either bites, move to type=registry, which has neither property.

mode=max caches intermediate stages as well as the final one, which matters for multi-stage builds because it lets a later run reuse the deps stage (chapters 6 and 7). It also stores considerably more, which is what interacts badly with a capped cache.

Multi-arch in CI

Chapter 8's choice, expressed as jobs.

native runners per platform, then one merge
jobs:
  build:
    strategy:
      matrix:
        include:
          - { platform: linux/amd64, runner: ubuntu-latest }
          - { platform: linux/arm64, runner: ubuntu-24.04-arm }
    runs-on: ${{ matrix.runner }}
    steps:
      - uses: docker/build-push-action@v6
        id: build
        with:
          platforms: ${{ matrix.platform }}
          outputs: type=image,name=ghcr.io/acme/api,push-by-digest=true,name-canonical=true
          cache-from: type=gha,scope=${{ matrix.platform }}
          cache-to: type=gha,mode=max,scope=${{ matrix.platform }}

  merge:
    needs: build
    steps:
      - run: |
          docker buildx imagetools create \
            -t ghcr.io/acme/api:sha-${{ github.sha }} \
            ghcr.io/acme/api@${{ needs.build.outputs.digest-amd64 }} \
            ghcr.io/acme/api@${{ needs.build.outputs.digest-arm64 }}

Each platform builds natively and pushes by digest only, with no tag; the merge job then assembles those digests into one index under the real tag (chapters 3 and 8). Two details make it work: a per-platform cache scope, since otherwise the two jobs fight over one cache key, and imagetools create, which builds the index server-side without moving layers.

When a single QEMU job is the better answer

If your CI provider has no native ARM runners, or the build is not compilation-heavy — an interpreted application with no native modules — a single job with docker/setup-qemu-action and --platform linux/amd64,linux/arm64 is far less YAML and the emulation penalty is small (chapter 8's model prices it). Reach for the matrix when the penalty is real.

CI security

A pipeline with registry credentials is a production credential holder.

PracticeWhy
OIDC rather than stored tokensShort-lived credentials minted per job; nothing to leak or rotate (chapter 15)
Least-privilege permissions:Default to contents: read and grant packages: write only in the job that pushes
Never expose secrets to fork pull requestsA PR can change the workflow it runs
Avoid pull_request_target with a checkout of the PR headIt runs untrusted code with secrets. A well-known escalation
Pin actions by commit SHAA tag on a third-party action can be repointed — chapter 15's mutability, applied to your pipeline
Secrets via --mount=type=secretNot --build-arg, which lands in history and provenance (chapter 8)
A pull request from a fork must not build with your credentials

If a fork's pull request can trigger a workflow that has registry write access, whoever opened it can push whatever they like to your registry — because the workflow file itself is part of the changes under review. The safe split is: run tests on untrusted pull requests with no secrets and no push, and build-and-push only from branches in your own repository, after review. This is the same trust boundary chapter 18 draws around the Docker socket, one layer up.

A worked pipeline

Everything above, in one file.

.github/workflows/ci.yaml
name: ci
on:
  push: { branches: [main] }
  pull_request:

permissions: { contents: read }

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write, id-token: write }
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: build
        uses: docker/build-push-action@v6
        with:
          context: .
          target: runtime
          push: true
          tags: ${{ env.IMAGE }}:sha-${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: mode=max
          sbom: true

  unit:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build --target test --cache-from type=gha .

  integration:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          docker compose -f compose.test.yaml run --rm test
          docker compose -f compose.test.yaml down -v
        env:
          IMAGE_REF: ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}

  scan:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}
          severity: CRITICAL,HIGH
          exit-code: "1"
          ignore-unfixed: true

  promote:
    needs: [unit, integration, scan]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { packages: write, id-token: write }
    steps:
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Tag the tested digest as staging
        run: |
          docker buildx imagetools create \
            -t ${{ env.IMAGE }}:staging \
            ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}
      - uses: sigstore/cosign-installer@v3
      - run: cosign sign --yes ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}

Every job after build refers to the image by digest, so all of them examine the same bytes. promote moves a tag onto that digest rather than rebuilding, and signs the digest rather than the tag. Nothing in the pipeline can produce a situation where the scanned image and the shipped image differ.

The short version

Chapter 16 in eight lines

  • Build once and pass the digest. Every later job refers to the same bytes, or your tests do not apply to what you ship.
  • Push immediately under a per-commit tag; make promotion the gate rather than pushing.
  • Ephemeral runners have no local cache, so a cache backend is not optional — type=gha to start, type=registry when it stops fitting.
  • The Actions cache is branch-scoped and size-capped, which produces both cold branches and self-evicting caches.
  • Prefer Compose for integration tests, because the same file runs on a laptop.
  • Mounting the Docker socket into a job is root-equivalent on the host; DinD needs --privileged.
  • Multi-arch: native runners per platform pushing by digest, then one imagetools create to build the index.
  • Untrusted pull requests get no secrets and no push. Pin third-party actions by SHA.

Check yourself

Your pipeline builds in the test job and again in the deploy job, from the same commit. Name the failure mode.

They are different images. Between the two builds the base image may have been republished under its tag, dependency resolution may pick a newer patch, and timestamps differ — so the digests differ and possibly the contents (chapter 8). The tests passed against an artefact that was then thrown away, and something never tested was deployed. The vulnerability scan has the same problem, only worse, because its report names an image nobody runs. Build once, and reference the digest everywhere downstream; the tracer above shows the digests diverging.

Builds on main take two minutes; the first build on any new branch takes eleven. Both use cache-from: type=gha.

The Actions cache is branch-scoped. A new branch can read the default branch's cache but writes into its own scope, so it warms on first use and shares nothing back — and if the branch was created before the last main build, it may miss the newest entries entirely. Options: accept it, since the second build on that branch is fast; or move to type=registry, where one cache ref is shared by every branch with no scoping. The second also avoids the size cap that can silently evict a mode=max cache.

Why push a per-commit tag before the tests have passed, rather than after?

Because the alternative is worse. Withholding the push means either rebuilding after the tests (which changes the artefact) or shipping the image around as a tarball artefact (which costs an upload and download of the whole thing per job). An image sitting in a registry under sha-<commit> is not deployed — nothing references it — so pushing early costs only storage, which a retention rule handles by expiring unpromoted commit tags (chapter 15). Make promotion the gate instead: the tag that means "deployable" is only moved when everything is green.

A colleague suggests mounting /var/run/docker.sock into the test job so Testcontainers works. What do you say?

That it grants the job root-equivalent control of the host: anything that can talk to the daemon can start a privileged container mounting the host filesystem (chapter 18). On a hosted ephemeral runner that is destroyed after the job it may be an acceptable trade, since the "host" is disposable and already runs your build. On a shared self-hosted runner it is not, because a compromised dependency in one repository's tests can reach every other job on that machine. Safer options: rootless DinD, a remote BuildKit or Docker endpoint scoped to the job, or Compose-managed services instead of Testcontainers.
