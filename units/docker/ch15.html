Registries and distribution

A registry is a content-addressed blob store with an HTTP API and a mutable name index bolted on the front. Everything difficult about distribution comes from that last part — tags move, so the thing you deployed is not necessarily the thing you can go back to, and the fix is to treat digests as the real identifiers and tags as labels for humans.

The protocol

Two endpoints, and chapter 3's objects moving over HTTP.

what a pull is, in requests
# 1. resolve the tag to a manifest (or an index, for multi-arch)
GET /v2/library/nginx/manifests/1.27-alpine
    Accept: application/vnd.oci.image.index.v1+json, …
→   Docker-Content-Digest: sha256:41523187cf…

# 2. fetch the config blob named in that manifest
GET /v2/library/nginx/blobs/sha256:2b8b1b3a5c…

# 3. fetch each layer blob it does not already have
GET /v2/library/nginx/blobs/sha256:63ca1fbb43…      # "Already exists" if cached

That is the whole distribution specification: /v2/<name>/manifests/<reference> and /v2/<name>/blobs/<digest>, plus an upload flow for pushing. Because blobs are named by digest, a registry deduplicates across every image and a push only uploads layers it does not have — which is why pushing a rebuilt application image transfers a few megabytes rather than the whole base (chapter 3).

poking at it directly
$ docker run -d -p 5000:5000 --name reg registry:2      # a real registry, locally
$ docker tag nginx:alpine localhost:5000/nginx:alpine
$ docker push localhost:5000/nginx:alpine
$ curl -s localhost:5000/v2/_catalog
{"repositories":["nginx"]}
$ curl -s localhost:5000/v2/nginx/tags/list
{"name":"nginx","tags":["alpine"]}

# and the useful one: inspect a remote image without pulling it
$ docker buildx imagetools inspect nginx:1.27-alpine --raw | head -20
Retag without pulling anything

docker buildx imagetools create -t ghcr.io/acme/api:prod ghcr.io/acme/api@sha256:4152… creates a new tag pointing at an existing manifest entirely server-side — no layers move, and it works on multi-arch indexes without flattening them. That is the correct mechanism for promotion, and it is much faster and safer than docker pull + docker tag + docker push, which round-trips gigabytes and can accidentally promote a single platform.

Image references

There is a precise parsing rule, and it produces one genuine surprise.

Reference resolver

What Docker actually resolves your image name to

RuleEffect
The first component is a registry if it contains a . or a :, or is exactly localhostOtherwise it is part of the repository name
No registryDefaults to docker.io
No namespace on Docker Hublibrary/ is inserted — nginx is docker.io/library/nginx
No tag and no digest:latest is assumed
Both a tag and a digestThe digest wins; the tag is documentation
A registry hostname without a dot is not a registry

Name an internal registry registry or myregistry and docker pull myregistry/api does not talk to it — the first component has no dot and no colon, so Docker reads it as a Docker Hub namespace and tries docker.io/myregistry/api. The error is a confusing "repository does not exist" or "unauthorized" from Docker Hub about an image you have never heard of. Use a fully-qualified name (registry.internal.acme.com/api) or a port (registry:5000/api), both of which contain a disambiguating character.

Authentication

And where your credentials are actually stored.

logging in
$ echo "$TOKEN" | docker login ghcr.io -u acme --password-stdin   # never as an argument
$ cat ~/.docker/config.json
{
  "auths": { "ghcr.io": { "auth": "YWNtZTpnaHBfeDdLZOKApg==" } }
}
$ echo 'YWNtZTpnaHBfeDdLZOKApg==' | base64 -d
acme:ghp_x7Kd…                       # base64, not encryption
config.json stores credentials in plain text

The auth field is base64-encoded, which is an encoding rather than a protection — anyone who can read the file has your registry token. Configure a credential store so it goes to the OS keychain instead: "credsStore": "osxkeychain" on macOS, "wincred" on Windows, "pass" or "secretservice" on Linux. And on a server, prefer a short-lived token minted per job (chapter 8's OIDC) over a long-lived one on disk at all.

~/.docker/config.json — the shape you want
{
  "credsStore": "osxkeychain",
  "credHelpers": {
    "123456789012.dkr.ecr.eu-west-1.amazonaws.com": "ecr-login",
    "europe-docker.pkg.dev": "gcloud"
  }
}

A credential helper mints a token on demand from cloud credentials you already have, so nothing registry-specific is stored at all — docker-credential-ecr-login uses your IAM identity, gcloud uses your Google session. This is the right answer for cloud registries and removes an entire class of expired-token incident.

in CI, with no stored secret at all
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}     # scoped, and expires with the job

Tagging and promotion

The section that decides whether you can roll back.

the pattern: build once, tag by commit, promote by digest
# build once, and record what came out
$ docker buildx build -t ghcr.io/acme/api:sha-$GIT_SHA --push .
$ DIGEST=$(docker buildx imagetools inspect ghcr.io/acme/api:sha-$GIT_SHA \
             --format '{{json .Manifest.Digest}}' | tr -d '"')

# promote by pointing a tag at that exact digest — nothing is rebuilt
$ docker buildx imagetools create -t ghcr.io/acme/api:staging ghcr.io/acme/api@$DIGEST
$ docker buildx imagetools create -t ghcr.io/acme/api:prod    ghcr.io/acme/api@$DIGEST

# deploy the digest, not the tag
$ echo "image: ghcr.io/acme/api@$DIGEST" >> deploy.yaml
Build once, promote many

If staging and production are separate builds of the same commit, they are separate images — different digests, possibly different base layers, and the thing you tested is not the thing you shipped (chapter 8's reproducibility problem). Building once and moving a pointer removes that gap entirely, and makes a rollback a matter of pointing at the previous digest rather than rebuilding an old commit and hoping.

Pull limits

The 429 that appears the week your CI gets busy.

Docker Hub throttles pulls — by IP for anonymous clients and by account for authenticated ones. The specific figures have been revised several times, so check the current policy rather than a number in a tutorial; what matters is the shape: anonymous pulls from a shared CI IP exhaust an allowance quickly, and the failure is toomanyrequests: You have reached your pull rate limit partway through a build.

MitigationEffectEffort
Authenticate in CILimits count against your account rather than a shared IPOne step in the workflow
A pull-through cacheOne upstream pull per image, then local hitsA registry to run
Mirror base images into your own registryNo Hub dependency in the build path at allA sync job, and you own the updates
Cache layers in CIFewer builds pull anything (chapter 6)Already worth doing
Pin by digestDoes not reduce pulls, but removes surprise base changesFree
a pull-through cache
$ docker run -d -p 5000:5000 --name mirror \
    -e REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io \
    registry:2

# point the daemon at it: /etc/docker/daemon.json
{ "registry-mirrors": ["http://mirror.internal:5000"] }
$ sudo systemctl restart docker

Note the mirror is transparent: image references stay unchanged and the daemon consults the mirror first. That makes it the least invasive of the mitigations, and the one that also speeds up cold CI runners on a shared network.

Storage and retention

Deleting a tag frees nothing.

Because blobs are content-addressed and shared, removing a tag only removes a name. The manifest becomes untagged, its blobs become unreferenced if nothing else needs them, and the space is reclaimed when garbage collection runs — which on a self-hosted registry is a command you must schedule yourself.

reclaiming space
# self-hosted registry:2 — deletion must be enabled first
$ docker exec mirror registry garbage-collect /etc/docker/registry/config.yml --dry-run

# ECR: a lifecycle policy, evaluated automatically
{
  "rules": [{
    "rulePriority": 1,
    "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed",
                   "countUnit": "days", "countNumber": 14 },
    "action": { "type": "expire" }
  }]
}
KeepExpire
Anything a running deployment references by digestUntagged manifests older than a fortnight
Every release tag, indefinitely — they are cheapPer-commit tags from merged pull requests
The last several images per branch, for rollbackBranch builds for deleted branches
An expiry policy can delete what production is running

If you deploy by digest and the tag has since been expired by a retention rule, the manifest may be garbage-collected — and then a node that needs to pull it during a scale-up or a restart cannot. Retention rules must exclude anything currently deployed, which in practice means keeping a durable tag on every promoted digest rather than relying on the digest alone to protect it.

Signing

Provenance says how it was built; a signature says nobody swapped it since.

cosign, keyless
# sign the DIGEST — signing a tag is meaningless, because tags move
$ cosign sign --yes ghcr.io/acme/api@sha256:41523187cf…

# verify, pinning who was allowed to sign it and which issuer vouched for them
$ cosign verify ghcr.io/acme/api@sha256:41523187cf… \
    --certificate-identity-regexp '^https://github\.com/acme/api/\.github/workflows/.+$' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com

$ cosign tree ghcr.io/acme/api@sha256:41523187cf…      # signatures and attestations

Keyless signing uses the CI job's OIDC identity, so there is no key to store or rotate: the signature records which workflow in which repository produced the image, and verification asserts that. Combined with chapter 8's provenance attestation, you can require that a deployed image was built from your source by your pipeline — and that requirement is only meaningful if it is enforced at deploy time by an admission policy rather than checked by hand (chapters 17 and 22).

Docker Content Trust is the older answer

DOCKER_CONTENT_TRUST=1 uses Notary v1 and a key you manage, and it predates the Sigstore ecosystem. It still works, and new work should use cosign: keyless identities remove the key-management problem that stopped most teams adopting signing at all.

The short version

Chapter 15 in eight lines

  • A registry is /v2/<name>/manifests/<ref> plus /v2/<name>/blobs/<digest>. Content addressing is why pushes and pulls transfer so little.
  • The first component of a reference is a registry only if it contains a . or :, or is localhost — otherwise it is a Docker Hub namespace.
  • A reference with both a tag and a digest resolves by digest; the tag is documentation.
  • ~/.docker/config.json holds credentials base64-encoded, not encrypted. Use a credential store or helper.
  • docker buildx imagetools create retags server-side — no layers move, and multi-arch indexes survive.
  • Build once, tag by commit, promote by digest. Rebuilding per environment means the thing you tested is not the thing you shipped.
  • Deleting a tag frees no space until garbage collection; retention rules must exclude anything deployed.
  • Sign the digest, keylessly, and enforce verification at deploy time or it proves nothing.

Check yourself

docker pull registry/api:2.4 against your internal registry called registry fails with "unauthorized". Why?

It never contacted your registry. The first component has no dot and no colon and is not localhost, so Docker parsed registry as a Docker Hub namespace and asked docker.io/registry/api:2.4 — hence an authorization error about an image you do not own. Give the host a fully-qualified name (registry.internal.acme.com/api:2.4) or include the port (registry:5000/api:2.4); either adds the character the parser needs. The resolver above shows the fully-qualified form for any reference you type.

Production deploys api:latest. A release breaks things at 2am. Walk through the rollback.

There is nothing to roll back to. latest now points at the broken image, and the previous one may have no tag at all — so the only route is to find the old digest in a deploy log or a node's local image cache, if either still exists. With per-commit tags you would name the previous one directly; with promotion by digest you would repoint prod at the previous digest, which is exact and takes one command. The simulator above makes the difference concrete: the same three releases are recoverable under one strategy and not the other.

Why promote by moving a tag to an existing digest rather than rebuilding from the same commit?

Because rebuilding produces a different image. The base image may have been republished under its tag, dependency resolution may pick newer patch versions, and timestamps differ — so the staging artefact you tested and the production artefact you shipped have different digests and possibly different contents (chapter 8). Promotion by digest guarantees they are byte-identical, is instant because imagetools create is server-side, and gives a rollback target that is exactly what previously worked.

CI starts failing with toomanyrequests halfway through builds. Two fixes, and which you would do first.

Authenticate to Docker Hub in the workflow, so the allowance counts against your account rather than the runner's shared IP — that is one step and usually resolves it immediately. Then, if base-image pulls are still on the critical path, run a pull-through cache and add it to registry-mirrors, which is transparent to every image reference and also speeds up cold runners. The heavier option is mirroring base images into your own registry, which removes the dependency entirely at the cost of owning the update cadence. Layer caching (chapter 6) helps too, by reducing how often anything is pulled at all.
