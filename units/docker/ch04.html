The CLI and the object model

The docker command does almost nothing. It is an HTTP client for a daemon that holds all the state, which is why it can drive a machine on the other side of the world with one environment variable, and why a hundred commands turn out to be four object types and a lifecycle. This chapter also covers the two flags — --format and --filter — that turn the CLI into something scriptable.

Client and daemon

Two programs, one socket, and a security consequence.

docker run does not create a container. It sends POST /containers/create followed by POST /containers/{id}/start to dockerd, which does the work described in chapters 1 to 3. You can send those requests yourself:

talking to the daemon directly
$ curl -s --unix-socket /var/run/docker.sock http://localhost/v1.45/version | head -c 120
$ curl -s --unix-socket /var/run/docker.sock http://localhost/v1.45/containers/json

$ docker version -f '{{.Client.Version}} → {{.Server.Version}}'
27.3.1 → 27.3.1                       # they can differ; the API negotiates

Because the client is thin, "where does this command run" is entirely a matter of which daemon it reaches — and there are three ways to change that:

pointing the CLI somewhere else
$ docker -H ssh://deploy@build-01 ps          # one command, over SSH
$ export DOCKER_HOST=ssh://deploy@build-01     # this shell
$ docker context create build --docker host=ssh://deploy@build-01
$ docker context use build                      # persistent, and named
$ docker context ls                              # which one am I on?
NAME       DESCRIPTION                    DOCKER ENDPOINT
default *  Current DOCKER_HOST based       unix:///var/run/docker.sock
build                                      ssh://deploy@build-01
The socket is the machine

Anything that can write to /var/run/docker.sock can start a container with --privileged and -v /:/host, which is unrestricted root on that host — no exploit required, just the API. That is why the docker group is root-equivalent (chapter 1), and why mounting the socket into a container to "let it manage containers" is the most consequential single line in many compose.yaml files. Chapter 18 covers the alternatives.

The objects

Four types you manage, plus two you mostly ignore.

ObjectIsLives until
ImageRead-only layers plus a config (chapter 3)You delete it, or prune removes it as dangling
ContainerAn image plus a writable layer, plus runtime configurationdocker rm — stopping is not removing
VolumeA directory managed by Docker, outside any imagedocker volume rm. Survives container removal
NetworkA virtual bridge plus DNS for the containers attacheddocker network rm
Build cacheBuildKit's record of previous build stepsdocker builder prune only
ContextA named daemon endpoint, stored in your home directoryIt is client-side config, not daemon state

Every one of these has the same shape of commands — ls, inspect, rm, prune — which is the clearest argument for using the management form of the CLI:

the two spellings
# the old top-level commands, kept for compatibility
$ docker ps          $ docker images        $ docker rmi        $ docker rm

# the management form: predictable, and discoverable with --help
$ docker container ls    $ docker image ls    $ docker image rm    $ docker container rm
$ docker volume ls       $ docker network ls  $ docker system df   $ docker builder prune
Names, IDs and prefixes

Every object has a 64-character ID and accepts any unambiguous prefix, so docker stop 3f9c works. Containers also get a random two-word name unless you pass --name, and that name is what other containers resolve over DNS on a user-defined network (chapter 12) — which is the practical reason to always name them.

Reading docker inspect

Three hundred lines of JSON, or one line of Go template.

docker inspect returns everything the daemon knows about an object. Piping it to grep works badly; the --format flag takes a Go template and is the difference between reading output and using it:

Inspect template playground

A real container's inspect output, and a working subset of Go templates

the one-liners worth keeping
$ docker inspect -f '{{.State.Pid}}' web                    # host PID (ch. 1)
$ docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' app   # why it died (ch. 2)
$ docker inspect -f '{{.NetworkSettings.IPAddress}}' web
$ docker inspect -f '{{range .Mounts}}{{.Source}}:{{.Destination}}{{println}}{{end}}' db
$ docker inspect -f '{{json .Config.Env}}' web
$ docker inspect -f '{{.HostConfig.Memory}}' app             # 0 means unlimited
$ docker inspect -f '{{index .Config.Cmd 0}}' web

# it works across several objects at once
$ docker inspect -f '{{.Name}} {{.State.Status}}' $(docker ps -aq)
Where the fields differ from what you set

.Config holds what came from the image plus your overrides; .HostConfig holds the runtime flags you passed (limits, mounts, restart policy); .State is live. So "why is this container using the wrong command" is a .Config.Entrypoint and .Config.Cmd question, while "why is it being killed" is .HostConfig.Memory and .State. Knowing which of the three to look in saves most of the scrolling.

the piping patterns these enable
$ docker rm $(docker ps -aq --filter status=exited)          # tidy up
$ docker rm -f $(docker ps -aq --filter label=stack=dev)      # everything in a stack
$ docker stop $(docker ps -q --filter ancestor=node:22)
$ docker image rm $(docker images -q --filter dangling=true)

# -q prints IDs only, which is what makes all of the above work.
# Guard against an empty list, or the outer command errors:
$ ids=$(docker ps -aq --filter status=exited); [ -n "$ids" ] && docker rm $ids

The container lifecycle

Six states, and the transitions people get wrong.

StateMeansReached by
createdExists, never started — writable layer allocated, no processdocker create
runningThe main process is alivedocker start / run
pausedFrozen by the cgroup freezer; still holds memorydocker pause
restartingBetween attempts, under a restart policyThe process exited and the policy says try again
exitedThe process finished. The writable layer still existsProcess exit, or docker stop
deadRemoval failed partway — rare, and needs cleanupDaemon or storage trouble
lifecycle commands
$ docker create --name web nginx        # created, not running
$ docker start -a web                    # start and attach to its output
$ docker stop -t 30 web                   # SIGTERM, then SIGKILL after 30s
$ docker kill -s HUP web                   # send any signal
$ docker restart web
$ docker pause web && docker unpause web
$ docker wait web                           # block, then print the exit code
$ docker rm web                              # now the writable layer is gone

$ docker update --memory 1g --cpus 2 web    # change limits without recreating
$ docker rename web api
Stopped is not removed, and it costs you disk

docker stop ends the process; the container object and its writable layer remain, which is why docker ps -a fills up and docker system df shows containers consuming gigabytes. docker start then resumes the same container with its filesystem changes intact — genuinely useful for debugging, and the reason --rm exists for everything else.

Restart policies

PolicyRestarts whenUse for
no (default)NeverOne-shot jobs
on-failure[:N]Non-zero exit, up to N timesJobs that should retry but not loop forever
unless-stoppedAlways, unless you stopped it explicitlyLong-running services on a single host
alwaysAlways, including after a daemon restartSame, but it comes back even after you stopped it

A restart policy is per-container state, not a supervisor: the daemon applies backoff and there is no notion of health, dependency order or a maximum restart budget beyond on-failure:N. That gap is most of the argument for an orchestrator (chapter 20).

Getting inside a running container

And the four commands that inspect its filesystem.

exec, logs, cp, diff
$ docker exec -it web sh                    # a NEW process in its namespaces
$ docker exec -u root -it web sh             # ...as a different user
$ docker exec -e DEBUG=1 web env             # with extra environment

$ docker logs -f --tail 100 --timestamps web
$ docker logs --since 10m web

$ docker cp web:/etc/nginx/nginx.conf .      # works on stopped containers too
$ docker cp ./nginx.conf web:/etc/nginx/

$ docker diff web                             # what changed vs the image
C /run
A /run/nginx.pid
C /etc/nginx
A /etc/nginx/conf.d/extra.conf

docker diff is a direct window onto chapter 3's upper layer: A added, C changed, D deleted, all relative to the image. It is the fastest way to answer "what has this container written", which matters because all of it disappears on docker rm.

CommandProducesNote
docker commitA new image from a container's current stateWorks, and produces an image nobody can rebuild. For debugging only
docker exportA tar of the filesystem, flattenedNo layers, no config, no history
docker saveA tar of an image — layers, config, manifestThe one that round-trips through docker load
docker top / statsProcesses; live resource usagestats shows usage against the cgroup limits
docker exec does not run in the same process tree position

exec starts a new process inside the container's namespaces — it is not a shell attached to PID 1. So environment variables set by the entrypoint script are absent, the working directory is the image's, and killing your shell does not affect the service. Also: on a distroless or scratch image there is no shell to exec at all, which is chapter 19's problem to solve.

The short version

Chapter 4 in seven lines

  • The CLI is an HTTP client; dockerd holds all the state. DOCKER_HOST or a context repoints it at another machine.
  • Write access to the daemon socket is root on that host — no exploit needed, just the API.
  • Four objects: images, containers, volumes, networks. Each has ls, inspect, rm, prune.
  • --format takes a Go template. .Config is image plus overrides, .HostConfig is your runtime flags, .State is live.
  • --filter plus -q is what makes the CLI scriptable — and guard against an empty list before piping into docker rm.
  • Stopped is not removed: an exited container keeps its writable layer, and its disk, until docker rm.
  • docker exec starts a new process in the container's namespaces, so entrypoint-set environment variables are absent.

Check yourself

docker system df reports 12 containers using 240 MB, but only 2 are running. Where is the space?

In the writable layers of the ten exited containers. Stopping a container ends its process and leaves the container object and its upper overlay directory intact — which is what makes docker start able to resume with the filesystem changes still there. docker container prune removes all stopped containers and reclaims it; --rm on docker run prevents the accumulation in the first place. Note this is separate from the build cache, which docker image prune does not touch either.

You need the host PID and exit code of every container, in one command. Write it.

docker inspect -f '{{.Name}} {{.State.Pid}} {{.State.ExitCode}}' $(docker ps -aq). Two things make it work: inspect accepts many objects and applies the template to each, and -q gives it bare IDs to consume. If the list can be empty, guard it — the command substitution collapses to nothing and docker inspect errors on no arguments. The playground above evaluates this template subset against a real inspect payload.

An entrypoint script exports APP_TOKEN. Why is it missing when you docker exec in and echo it?

Because exec starts a brand-new process from the image's configured environment, not a shell inside the existing process. Variables exported by the entrypoint exist only in PID 1's environment and its children, and your exec'd shell is a sibling rather than a descendant. To see them, read PID 1's environment directly — docker exec web cat /proc/1/environ | tr '\0' '\n' — or pass what you need with docker exec -e. This also explains why a WORKDIR change made at runtime by the script does not apply to your shell.

A colleague proposes docker commit to capture a fix made inside a running container. What do you say?

It works and produces an image nobody can reproduce: there is no Dockerfile, no record of what changed beyond docker diff, and the next person who needs the same fix has to repeat the archaeology. Use it as a diagnostic — commit the broken container so you can poke at a copy — and then encode the actual fix in the Dockerfile. The related trap is docker export, which flattens the filesystem and discards layers, config and history; docker save is the one that round-trips an image intact.
