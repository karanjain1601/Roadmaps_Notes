Multi-stage builds and small images

A compiler, a package manager, header files and your source code are all things you need to build an application and none of them are things you need to run it. Multi-stage builds separate the two, and once they are separated the question of which base image to ship becomes interesting — with a real trade behind every megabyte you remove.

What is in a naive image

Mostly things you would be alarmed to find in production.

Three separate costs follow. Transfer: every node pulls it on every deploy. Attack surface: every package is a package that can have a CVE, and a shell plus a package manager is what turns a code-execution bug into a foothold (chapter 18). Noise: a scanner reporting 240 vulnerabilities in build tooling you do not run makes it impossible to see the two that matter (chapter 17).

Multi-stage builds

Several FROMs in one file. Only the last one ships.

the same application, staged
# syntax=docker/dockerfile:1

FROM node:22-alpine AS base
WORKDIR /app

FROM base AS deps
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM base AS prod-deps
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM deps AS build
COPY . .
RUN npm run build

FROM deps AS test
COPY . .
RUN npm test

FROM base AS runtime
ENV NODE_ENV=production
COPY --from=prod-deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

Six stages, one shipped image. The runtime stage contains production dependencies and compiled output and nothing else — no source, no dev dependencies, no build toolchain. And because stages form a graph rather than a sequence, a stage nothing depends on is never built:

A test stage costs a production build nothing

Because unreferenced stages are skipped, adding AS test and AS lint stages gives CI a single-command entry point (docker build --target test .) without adding a second to the image build — the demo above shows exactly which stages each target pulls in. It also means the tests run in an environment identical to the one that produced the artefact, which is the property a separate CI test job does not give you.

Alpine, musl, and the cost nobody mentions

Alpine is not simply a smaller Debian.

Alpine uses musl rather than glibc. It is a legitimate, standards-conformant C library, and it is a different one — which matters because the pre-built binaries the ecosystem ships are usually compiled against glibc:

EffectWhat happens
Python wheelsPyPI's manylinux wheels are glibc. On Alpine, pip needs musllinux wheels or it compiles from source — turning a 20-second install into ten minutes plus a build toolchain
Node native modulesPrebuilt binaries often miss, so node-gyp runs and needs python3, make and g++ in the image
DNS resolutionmusl's resolver historically differs from glibc's over search domains and parallel queries; Kubernetes DNS setups have been bitten by it
Allocation-heavy workloadsmusl's allocator has different performance characteristics; some workloads measurably regress
Debugging toolsDifferent ldd, different stack traces, different core-dump tooling than most guides assume
The Alpine Python trap, with numbers

A python:3.12-alpine image looks 90 MB smaller than python:3.12-slim. Then a dependency without a musllinux wheel forces a source build, so the Dockerfile grows gcc, musl-dev, libffi-dev and friends — and either the final image is bigger than the slim one, or you need a multi-stage build to get rid of them again, with the added risk that a compiled-from-source extension behaves subtly differently. For Python, -slim is usually the better default, and the size difference is not worth the build time. For Go and Rust the calculus flips entirely, because a static binary does not care what libc the base has.

Static binaries and scratch

Where the two-megabyte image is genuinely available.

Go to a near-empty image
# syntax=docker/dockerfile:1

FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/server ./cmd/server

FROM gcr.io/distroless/static:nonroot
COPY --from=build /out/server /server
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/server"]

CGO_ENABLED=0 is the line that makes this work for Go: it forces a pure-Go build with no dynamic linking, so the binary needs no libc at all. If you need cgo — SQLite, some crypto bindings, os/user — you need distroless/base or a static build against musl instead. For Rust, the equivalent is the x86_64-unknown-linux-musl target.

Prefer distroless/static over bare scratch

It is about two megabytes and it already contains the CA certificates, timezone database and a non-root user entry that you would otherwise assemble by hand and get subtly wrong. scratch is the right answer when you genuinely want nothing, and the wrong answer when what you actually wanted was "very small".

Two things that do not work as advertised

Layer count is not size. Merging every RUN into one giant instruction to "reduce layers" makes the cache useless (chapter 6) and saves nothing, because size is the sum of the content, not a per-layer overhead. Combine instructions when they share a cleanup, not to hit a number. And --squash flattens history into one layer, which destroys layer sharing between images (chapter 3) — so the registry stores your base again for every image. It has been experimental for years; multi-stage builds are the supported answer.

That inverted form — exclude everything, then re-include explicitly — is stricter than a deny list and worth the extra thought on anything that handles credentials. A deny list silently ships whatever you forgot to name; an allow list fails the build instead, which is the failure you want.

The short version

Chapter 7 in eight lines

  • Multi-stage builds ship the artefact and discard the toolchain — the single biggest size win, and it makes every other technique cheaper.
  • Stages form a graph, not a sequence: unreferenced stages are never built, and independent ones build in parallel.
  • So a test or lint stage costs a production build nothing, while giving CI one command that runs in the real build environment.
  • COPY --from= takes a stage name, a stage index, or any image.
  • Base image sizes buy capabilities: slim loses docs, distroless loses the shell and package manager, scratch loses everything including CA certs.
  • Alpine means musl, so prebuilt glibc wheels and native modules may compile from source — often making a Python image slower to build and no smaller.
  • For Go and Rust, a static binary (CGO_ENABLED=0) plus distroless/static gives a genuinely tiny image; prefer it to bare scratch.
  • Layer count is not size, and --squash destroys layer sharing. Neither is a slimming technique.

Check yourself

Your Dockerfile has stages base, deps, build, test, lint and runtime. What does a plain docker build . build?

Only the stages the final one transitively depends on: runtime, plus whatever it copies from — typically build, and deps and base beneath it. test and lint are not built at all, because nothing references them. That is what makes them free to keep in the file, and it is why docker build --target test . is a good CI entry point: it builds the same deps layers the production build uses, so the tests run against the real dependency set. The demo above shows the dependency closure for each target.

A team switches a Python image from slim to alpine. The image is 40 MB smaller and builds take eleven minutes instead of forty seconds. Explain.

Alpine uses musl, and PyPI's prebuilt wheels are mostly manylinux — compiled against glibc. Any dependency without a musllinux wheel is built from source, so pip is now invoking a compiler for packages that previously arrived as binaries; the Dockerfile also has to install gcc and the relevant -dev headers, which partly cancels the size saving. For Python, -slim is usually the better default. If Alpine is required, use a multi-stage build so the toolchain does not ship, and expect to maintain the list of build dependencies.

A Go binary works in golang:alpine and exits immediately with no output on scratch. Diagnose it.

It is dynamically linked and scratch has no libc, so the loader fails before main runs — which is why there is no output. It happens when cgo is enabled, either explicitly or by importing a package that needs it (net with the default resolver, os/user, SQLite bindings). Build with CGO_ENABLED=0 for a pure-Go static binary, or ship on distroless/base, which has glibc. Once it starts, the next two failures are usually missing CA certificates on outbound HTTPS and a missing /etc/passwd if you used a named USER — all three of which distroless/static:nonroot already solves.

A colleague merges twelve RUN instructions into one to "reduce layers and shrink the image". Assess it.

It will not shrink the image, because size is the sum of the content — there is no meaningful per-layer overhead. It will destroy the build cache: twelve cache boundaries become one, so any change to any of those commands reruns all twelve (chapter 6). The genuine reason to combine instructions is different and narrower: when a later command removes what an earlier one created, they must share a layer or the bytes remain (chapter 3). So combine apt-get update && install && rm -rf /var/lib/apt/lists/*, and leave unrelated steps apart.
