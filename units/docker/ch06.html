The build cache

Two Dockerfiles can produce the same image and differ by a minute per build. The difference is where you put COPY. The cache rule is simple — once a step misses, every step after it misses — and it turns instruction order from a matter of taste into the main performance decision in the file.

How the cache works

Each step gets a key, and the key includes its parent's key.

For every instruction the builder computes a cache key. If a previous build produced a result under the same key, that result is reused and the instruction does not run. The key is built from the parent step's key plus something about this step:

InstructionKey includesConsequence
FROMThe resolved base image digestA new base invalidates the whole file
RUNThe command string, and nothing elseDocker never inspects what the command did — see the trap below
COPY / ADDA checksum of the copied files' contents and modesEditing a copied file invalidates from there down
ENV, LABEL, USER, …The instruction textCheap to run, but still a cache boundary
ARGThe value, for instructions that use itChanging an unused ARG invalidates nothing
--mount=type=cacheNot part of any keyPersists across builds and invalidates nothing
The rule that follows from parent keys

A cache miss cascades downward and never upward. If step 4 misses, steps 5 to 12 also miss even though nothing about them changed — their keys depend on step 4's result. Nothing above step 4 is affected. That single asymmetry is why the ordering advice in this chapter works, and it is the same reasoning as chapter 3's digest chain: identity depends on everything beneath you.

RUN apt-get update in its own instruction

The cache key for a RUN is the literal command text, so RUN apt-get update stays cached for months while the package lists it wrote go stale. A later RUN apt-get install -y curl then fails with "404 Not Found" for a version that no longer exists — a build that worked yesterday, broken by a cache hit. Always combine them: RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*. One instruction, one cache key, no stale window — and the cleanup is in the same layer, per chapter 3.

Ordering is the whole game

Stable instructions at the top, volatile ones at the bottom.

the pattern, per ecosystem
# Node
COPY package*.json ./
RUN npm ci
COPY . .

# Python
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# Go
COPY go.mod go.sum ./
RUN go mod download
COPY . .

# Rust — cargo needs a dummy source to resolve dependencies alone
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo 'fn main(){}' > src/main.rs && cargo build --release && rm -rf src
COPY . .

# Java / Maven
COPY pom.xml ./
RUN mvn -B dependency:go-offline
COPY . .

Every one of these is the same shape: copy the file that lists dependencies, install them, then copy the source. Dependency manifests change weekly; source changes hourly. Putting the expensive step between them means it only reruns when it genuinely needs to.

What COPY actually hashes

Contents, not timestamps — with a few things that catch people anyway.

BuildKit hashes the contents and modes of the files being copied, so touching a file without changing it does not invalidate the cache. What does invalidate it, sometimes surprisingly:

CauseWhyFix
COPY . . with no .dockerignoreAny file in the tree is part of the checksum — including .git, which changes on every commitA real .dockerignore (chapter 5)
Build output in the contextdist/ changes on every local build, invalidating the copyIgnore it
A file mode changeMode is part of the hash, so chmod +x countsNothing — it is genuinely a change
Generated files with embedded timestampsContent differs each time even with identical inputsGenerate inside the build, or make it reproducible
Editor swap and lock filesThey appear and vanish inside the contextIgnore *.swp, .DS_Store, *~

Cache mounts

A package manager's cache that survives builds and never lands in the image.

Ordering fixes "do not rerun npm ci unnecessarily". Cache mounts fix the harder case: when it does rerun, it should not re-download everything. A --mount=type=cache directory is provided by the builder, persists between builds, and is not part of any layer:

cache mounts, per ecosystem
# syntax=docker/dockerfile:1

# Node
RUN --mount=type=cache,target=/root/.npm npm ci

# Python
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# Go — the module cache and the build cache
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /app ./cmd/server

# Debian/Ubuntu — needs the auto-clean hook disabled first
RUN rm -f /etc/apt/apt.conf.d/docker-clean
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt/lists,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends curl

# Alpine
RUN --mount=type=cache,target=/var/cache/apk apk add --no-cache curl
OptionMeans
target=Where to mount it inside the build step. The only required option
id=Names the cache, so different targets can share or stay separate
sharing=shared (default)Concurrent builds use it simultaneously
sharing=lockedConcurrent builds wait — required for apt, which is not concurrency-safe
sharing=privateEach concurrent build gets its own copy
uid=, gid=, mode=Ownership, for when the build step does not run as root
Two properties worth stating separately

The cache mount is not in the image. A package cache mounted this way never becomes a layer, so chapter 3's "clean up in the same RUN" problem disappears — there is nothing to clean up. And its contents are not part of the cache key, so a warm cache mount neither invalidates a step nor makes one hit. It only makes the step faster when it does run.

And one thing it is not

A cache mount is not a build secret and not a way to share files into the image. Anything the step writes to target= is discarded from the layer, so RUN --mount=type=cache,target=/app/node_modules npm ci produces an image with no node_modules — a genuinely common mistake. Cache the package manager's download cache, never the installed output.

Cache in CI

A fresh runner has no cache at all, and that is a solvable problem.

Every local speed-up in this chapter assumes a builder that remembers the previous build. CI runners are usually clean, so the cache has to be imported from somewhere:

CI cache backend model

Which backend, what it restores, and what the transfer costs — assumptions listed underneath
backend
the change

the flags
# registry-backed, exporting every intermediate stage
$ docker buildx build \
    --cache-from type=registry,ref=ghcr.io/acme/api:buildcache \
    --cache-to   type=registry,ref=ghcr.io/acme/api:buildcache,mode=max \
    -t ghcr.io/acme/api:$GIT_SHA --push .

# inline: cache metadata travels inside the image itself. Simple, min mode only
$ docker buildx build --cache-to type=inline --cache-from type=registry,ref=… .

# GitHub Actions cache backend
$ docker buildx build --cache-from type=gha --cache-to type=gha,mode=max .

# local directory, for a self-hosted runner with persistent disk
$ docker buildx build --cache-to type=local,dest=/var/cache/buildkit,mode=max \
                       --cache-from type=local,src=/var/cache/buildkit .
BackendStoresBest for
inlineCache metadata inside the pushed image. Final stage onlySingle-stage builds; zero extra setup
registry, mode=minLayers in the final image, as a separate tagSame coverage as inline, but does not bloat the image
registry, mode=maxEvery intermediate stageMulti-stage builds — the usual right answer
ghaGitHub's own cache serviceGitHub Actions, subject to the repository cache quota
localA directory on the builderSelf-hosted runners with persistent disk
s3, azblobObject storageLarge teams wanting one shared cache
mode=min and multi-stage builds do almost nothing

min exports only the layers that ended up in the final image — and in a multi-stage build the expensive steps (npm ci, compilation) happen in a builder stage whose layers are not in the final image. So the cache restores the cheap final layers and rebuilds everything that mattered. mode=max exports the intermediate stages too, which is what actually helps; it costs more upload and more registry storage, and that trade is nearly always worth it.

Busting the cache deliberately

Sometimes you need a miss, and there are precise ways to get one.

from broadest to narrowest
$ docker build --no-cache .                       # everything
$ docker build --no-cache-filter deps .            # one named stage only
$ docker build --pull .                             # re-resolve the base image tag

# a cache-busting ARG: change the value to invalidate from that point down
$ docker build --build-arg CACHEBUST=$(date +%s) .
and in the Dockerfile
# everything below this line rebuilds when CACHEBUST changes
ARG CACHEBUST=1
RUN git clone --depth 1 https://github.com/acme/plugins.git /opt/plugins

That pattern exists because of the RUN key rule: a git clone of a moving branch is cached forever otherwise. It is a workaround rather than a design — pinning a commit or a release tarball with a checksum is better, because then a cache hit is correct rather than merely fast.

inspecting and pruning the cache
$ docker builder du                              # how big is it, by record
$ docker builder du --verbose | head -30          # per-step, with last-used times
$ docker builder prune --filter until=168h        # older than a week
$ docker builder prune --keep-storage 20GB         # bound it instead
$ docker buildx du --builder default

The build cache is invisible to docker image prune and grows without limit by default, so it is the usual answer to "the disk filled up and I deleted all my images and it did not help" (chapter 3).

The short version

Chapter 6 in eight lines

  • Each step's cache key includes its parent's key, so a miss cascades downward and never upward.
  • A RUN's key is the command text only — Docker never looks at what it did.
  • Hence apt-get update alone caches stale package lists and breaks a later install. Combine them into one RUN.
  • COPY hashes file contents and modes, so ordering dependency manifests before source is what makes the expensive step cacheable.
  • An unused ARG invalidates nothing; a used one invalidates from that instruction down.
  • --mount=type=cache persists between builds, never becomes a layer, and is not part of any cache key.
  • Never cache-mount the installed output (node_modules) — only the package manager's download cache.
  • In CI, mode=max is what caches a multi-stage build; mode=min and inline restore only the final image's layers.

Check yourself

A build that worked last month now fails at apt-get install -y libpq-dev with a 404. Nothing in the Dockerfile changed.

RUN apt-get update is a separate instruction and its cache key is just that text, so it has been a cache hit for weeks while the package lists it produced went stale. The distribution has since published new package versions and removed the old files, so the install requests a URL that no longer exists. Fix by combining them in one RUN with &&, which gives the pair a single cache key — and add rm -rf /var/lib/apt/lists/* to the same instruction so the lists do not ship in the layer (chapter 3).

Local builds take 4 seconds; CI takes 90 every time, with --cache-from type=registry configured. What is likely wrong?

Almost certainly mode=min on the --cache-to side — the default. It exports only the layers present in the final image, and in a multi-stage build the expensive steps live in a builder stage that contributes no layers to the final image. So CI restores the cheap tail and rebuilds the dependency install every run. Switch to mode=max. If that is already set, check whether the cache is being written at all: a fork or a pull request often lacks registry push permission, so --cache-to silently fails while --cache-from keeps finding nothing.

Why does RUN --mount=type=cache,target=/app/node_modules npm ci produce a broken image?

Because a cache mount is not part of the resulting layer. Everything npm ci writes to /app/node_modules goes into the builder's cache directory and is discarded when the step finishes, so the image ships with an empty node_modules and the application cannot start. Cache mounts are for the package manager's download cache — /root/.npm — which is a pure accelerator that nothing at runtime needs. The installed output must be a real layer.

Your first COPY misses on every build even when you change nothing. How do you find out why?

Look at the context size with docker build --progress=plain — if "transferring context" is tens of megabytes, something volatile is in it. The usual culprit is .git, whose contents change on every commit and every git status, followed by a local dist/ or node_modules. Since COPY hashes contents and modes, any of those makes the checksum differ. Write a .dockerignore, re-run, and watch both the transfer size and the cache behaviour change. A chmod counts too, because mode is part of the hash.
