Scanning and the supply chain

A scanner tells you which packages are present and which have published advisories. It does not tell you whether any of it matters. The gap between those two things is where most container security effort is wasted — and closing it is mostly about rebuild cadence, not about the scanner.

What a scanner actually does

Two lists and a join.

It enumerates the packages in the image — from the OS package database and from language manifests — and joins that inventory against vulnerability databases. That is genuinely useful and it is also the whole mechanism, which explains the blind spots exactly.

Scan the digest, not the tag

Chapter 16 made this point about pipelines; it applies to every scan. A report against api:staging describes whatever that tag pointed at when the scan ran, which may not be what is deployed by the time anyone reads it. Scan @sha256:… so the report and the artefact are permanently linked, and store the report alongside the digest.

Reading a scan honestly

Severity is a property of the vulnerability. Risk is a property of your deployment.

Triage funnel

What each policy layer blocks, and how much of it is noise

SignalTells you
CVSS severityHow bad it is if exploited in a worst-case deployment. Not a priority
A fix existsWhether you can do anything today. --ignore-unfixed filters on this
ReachabilityWhether the vulnerable code path is loaded at all
EPSSEstimated probability of exploitation soon. Most CVEs score very low
CISA KEVKnown to be exploited in the wild. The strongest single signal
Shipped or notA dev dependency in a build stage never reaches production (chapter 7)
"Critical" in NVD, "not affected" in Debian

Distributions frequently backport a security fix without changing the upstream version number, so a naive version comparison against NVD reports a vulnerability the package no longer has. Distro-aware scanners consult the distribution's own security tracker and get this right; version-matching tools and homegrown checks do not. The corollary matters more: when a scanner and a distribution disagree, the distribution is usually right about its own package. The persistent false-positive source is elsewhere — vendored binaries and language dependencies with no manifest.

Base image currency

The single biggest lever, and it is not a security tool.

Most findings in a typical image come from the base, not from your code — so the highest-value action is usually rebuilding on a fresh base, which fixes dozens of advisories without a line of application change. That makes vulnerability count a function of two things you control: how much surface the base has, and how old your build is.

Pinning by digest and staying current are the same problem

Chapter 3 argued for pinning FROM by digest, and a pinned digest by definition never picks up a patched base. The resolution is not to unpin — it is to make the pin move on a schedule, visibly, through review. A bot raising a weekly pull request that bumps the digest gives you reproducibility and currency at once, with a commit recording each change. Unpinned tags give you currency and no record of what changed or when.

SBOM in practice

The point is not the document; it is the query.

generating and querying
# at build time (chapter 8), or after the fact
$ docker buildx build --sbom=true --provenance=mode=max -t ghcr.io/acme/api:x --push .
$ syft ghcr.io/acme/api@sha256:4152… -o spdx-json > sbom.json
$ trivy image --format cyclonedx --output sbom.cdx.json ghcr.io/acme/api@sha256:4152…

# the question you actually need answered, at 9am, about 200 images
$ jq -r '.packages[] | select(.name=="log4j-core") | .versionInfo' sbom.json
$ trivy sbom sbom.cdx.json --severity CRITICAL      # rescan without the image
Because you stored SBOMsOtherwise
"Which images contain this package?" — a query, secondsPull and scan every image, hours to days
Rescan old images against today's database without rebuildingThe image may no longer build at all
Answer a customer's licence question from a recordReconstruct it by hand
Diff two releases' dependency setsGuess from the changelog

Store the SBOM as an attestation attached to the image digest, so it travels with the artefact rather than living in a CI log that expires. The value is entirely in being able to ask a question across the fleet at the moment an advisory lands — which is a storage and indexing problem, not a scanning one.

A gate everyone bypasses is worse than no gate.

an exception list that expires

# call the affected iconv path. Reviewed 2026-08-14 by @karan.

# CVE-2025-30412 — in a build stage only, never shipped (multi-stage, ch. 7).
CVE-2025-30412 exp:2026-10-01
The failure mode is social, not technical

A policy that fails builds on every high-severity finding produces a list nobody can act on, and within a fortnight someone adds a blanket ignore or an || true — after which the gate reports nothing and everybody believes it is working. Block on the small set that is genuinely actionable (fixed, shipped, reachable, or known-exploited), warn on the rest, and require every exception to carry a justification and an expiry date. A gate that blocks three things a month gets respected; one that blocks ninety gets disabled.

Delta scanning is the other half: comparing this build against the previous release separates what this change introduced from the inherited backlog. Developers can act on the former immediately, and the latter belongs on a currency schedule rather than in a pull request review.

All of chapters 8, 15 and 16 produce evidence — provenance, SBOMs, signatures — and none of it does anything unless something refuses to run an image that fails verification. On a single host that is a deploy script check; on a cluster it is an admission controller (chapter 22). Evidence without enforcement is documentation.

What scanning cannot cover

And the cheap things that do.

The ordering is worth stating plainly. A container built on a current slim base, running as a non-root user with a read-only filesystem, no capabilities and no outbound access it does not need, is in far better shape than one with a clean scan and none of that. Scanning tells you about known problems in known packages; the hardening in chapter 18 limits what any problem can do.

The short version

Chapter 17 in eight lines

  • A scanner joins a package inventory against advisory databases. It cannot see vendored code, your own bugs, or misconfiguration.
  • Severity describes the vulnerability; risk depends on your deployment. Fix availability, reachability, KEV and shipped-or-not are the useful filters.
  • NVD and a distribution can legitimately disagree, because distros backport without bumping versions.
  • Base currency is the biggest lever — most findings come from the base, and a rebuild clears them with no code change.
  • Pin by digest and move the pin on a schedule through review. That is reproducibility and currency together.
  • SBOMs are worth storing for the query, not the document: "which of our images has this package" in seconds.
  • Block on the actionable few, warn on the rest, and give every exception a justification and an expiry.
  • Provenance, SBOMs and signatures do nothing unless something refuses to deploy on failure.

Check yourself

A scan of your image reports 187 vulnerabilities, 34 of them high or critical. Where do you start?

Not with the list. First filter to what is actionable: has a fix, is in a shipped layer rather than a build stage, and is in something the application actually loads — then sort what remains by whether it is in the KEV catalogue and by EPSS rather than by CVSS. That usually leaves a handful. Second, check base currency: if the image is built on a base that is months old, rebuilding on a fresh one probably clears most of the 187 at once with no code change. Third, set a policy that blocks only the actionable set, so the number stays small enough to act on. The triage funnel above shows the ratios.

You pin FROM debian:12-slim@sha256:… for reproducibility. A colleague says this guarantees you never get security patches. Are they right?

Right about the mechanism, wrong about the conclusion. A pinned digest cannot change, so a patched base will never arrive on its own — but unpinning trades that for a base that changes silently, with no record of when or to what, which breaks reproducibility (chapter 8) and makes an incident harder to investigate. The answer is to keep the pin and automate moving it: a bot raises a weekly pull request bumping the digest, so every change is a reviewed commit. Add a scheduled rebuild so a patched base reaches production without waiting for a code change.

Your build fails on 40 high-severity findings, none with fixes available. What is the least-bad policy?

Do not block on unfixed findings — there is no action a developer can take, so the gate only teaches people to bypass it. Warn on them, record them with a review date, and revisit when fixes appear. Meanwhile check whether a smaller base removes most of them outright (chapter 7): 40 unfixed findings in a full Debian base often becomes two or three on slim or distroless, because the packages are simply absent. Then block on the categories that are actionable — fixed, shipped, or known-exploited — so the gate keeps its credibility.

Your pipeline produces provenance, an SBOM and a cosign signature for every image. What does that prevent today?

By itself, nothing — it produces evidence, and evidence prevents nothing until something checks it. What it enables: verifying at deploy that an image was built by your pipeline from your source, and answering fleet-wide questions when an advisory lands. Both require enforcement — a deploy-time cosign verify that fails closed, or an admission controller rejecting unsigned images (chapter 22). Until that exists, the attestations are a good audit trail and not a control. Worth adding in that order, though: you cannot enforce what you do not produce.
