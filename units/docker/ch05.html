Dockerfiles: every instruction

Eighteen instructions, and two of them cause most of the confusion in the industry. ENTRYPOINT and CMD are not alternatives — they combine, and whether you wrote them in shell form or exec form decides whether your process is PID 1, whether it receives SIGTERM, and whether docker stop takes fifty milliseconds or ten seconds.

The context is sent first, and that matters more than people expect.

The final . is the build context: that directory is archived and sent to the builder before any instruction runs. A 48 MB context on a project with 2 MB of source means node_modules, .git or a build output directory is being shipped for no reason — and it is paid on every build.

The # syntax line on the first line pins the Dockerfile frontend, which is how you get newer instruction features (COPY --link, heredocs, --mount) without upgrading Docker itself. It is worth having on every Dockerfile.

ENTRYPOINT, CMD, and PID 1

The most consequential four lines of configuration in a Dockerfile.

Both instructions contribute to one command line. ENTRYPOINT is the part that always runs; CMD is the default arguments, and docker run replaces them. Each can be written in exec form (a JSON array) or shell form (a bare string), and the form decides what happens to signals.

Why shell form makes docker stop take ten seconds

Shell form wraps your command in /bin/sh -c, so sh is PID 1 and your application is its child. docker stop sends SIGTERM to PID 1; sh does not forward signals while waiting on a child, so your application never hears about it. Ten seconds later Docker sends SIGKILL, the container dies with exit code 137, and in-flight requests are dropped. Exec form fixes it — with one further wrinkle in the next paragraph.

PID 1 ignores signals it has no handler for

The kernel does not apply default signal actions to PID 1 — a normal process without a SIGTERM handler is terminated, but PID 1 without one simply ignores it. So exec form alone is not enough: the application must actually handle SIGTERM. If it cannot (many scripts, some runtimes), docker run --init inserts a tiny init process as PID 1 that forwards signals and reaps zombies. The demo above shows all four combinations of form and handler.

the entrypoint script pattern that works
#!/bin/sh
set -e
# do setup that needs the runtime environment
: "${DATABASE_URL:?DATABASE_URL is required}"
./wait-for-db.sh

# exec REPLACES the shell, so the app becomes PID 1 and gets signals directly
exec "$@"

Paired with ENTRYPOINT ["/entrypoint.sh"] and CMD ["node", "server.js"], that gives you both: a place for startup logic, and an application that is genuinely PID 1. The exec on the last line is the entire trick, and forgetting it is the most common version of this bug.

COPY, ADD, and the path rules

Two instructions, and a set of path behaviours worth memorising once.

FormResult
COPY file.txt /app/Trailing slash means destination is a directory — /app/file.txt
COPY file.txt /app/renamed.txtNo trailing slash with a single file means rename
COPY src/ /app/The contents of src, not the directory itself
COPY . .Everything not excluded by .dockerignore, into WORKDIR
COPY package*.json ./Globs; multiple sources require a directory destination
COPY --from=build /app/dist ./distFrom an earlier stage rather than the context
COPY --chown=node:node . .Ownership set as the files are written — avoids the copy-up cost of a later chown -R (ch. 3)
ADD https://example.com/f.tar.gz /tmp/Downloads it — and does not extract a remote archive
ADD local.tar.gz /app/Extracts a local archive automatically

The rule of thumb: use COPY. ADD's two extra behaviours are surprising in opposite directions — local archives extract, remote ones do not — and a URL fetch bypasses the layer caching and checksum discipline you would get from doing it inside a RUN with a verification step.

the caching-friendly ordering, which is chapter 6's whole subject
# dependency manifests first: they change rarely
COPY package*.json ./
RUN npm ci

# source last: it changes on every commit
COPY . .

--build-arg is not a secret mechanism

Docker's own documentation is explicit: build-argument values are visible to anyone with the image via docker history. And even without that, a token used inside a RUN can end up in a layer — in a config file, a lockfile, or a package manager's cache. If ENV is worse (it is in the runtime environment of every container), ARG is not safe either. The correct tool is a build secret mount, which never lands in a layer at all, and chapter 8 covers it:

the safe version
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npmtoken \
    NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
and how it is invoked
$ docker build --secret id=npmtoken,env=NPM_TOKEN .
$ docker build --secret id=npmtoken,src=./token.txt .

$ docker history --no-trunc my-app | grep -i token     # nothing. That is the point.

HEALTHCHECK

Cheap, underused, and the thing Compose dependencies actually wait on.

syntax and states
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:3000/healthz || exit 1

# exit 0 = healthy, exit 1 = unhealthy. Anything else is also unhealthy.
# HEALTHCHECK NONE disables one inherited from the base image.
OptionMeans
--intervalHow often to run it (default 30s)
--timeoutHow long to wait before calling that attempt a failure
--start-periodGrace window during which failures do not count — for slow starters
--retriesConsecutive failures before the state becomes unhealthy

The status appears in docker ps and in .State.Health, and is filterable with --filter health=unhealthy (chapter 4). Two practical notes: the check runs inside the container, so curl must exist in the image — a distroless image needs a static binary or a language-native check instead; and an unhealthy container is not restarted by Docker on its own, which is another gap orchestrators fill (chapter 20).

A checklist for reviewing someone's Dockerfile

Is the base pinned? Are dependency manifests copied before the source? Is cleanup in the same RUN? Is there a USER? Is ENTRYPOINT in exec form? Is anything secret in ARG or ENV? Is there a .dockerignore? Seven questions, and they catch nearly everything that matters.

The short version

Chapter 5 in eight lines

  • The build context is archived and sent before any instruction runs — write .dockerignore first.
  • ENTRYPOINT and CMD combine. ENTRYPOINT always runs; CMD is default arguments that docker run replaces.
  • Shell form wraps in /bin/sh -c, making sh PID 1 — so SIGTERM never reaches your app and docker stop takes the full timeout, then SIGKILL and exit 137.
  • A shell-form ENTRYPOINT ignores CMD and run-time arguments entirely.
  • Even in exec form, PID 1 ignores signals it has no handler for. Use --init, or handle SIGTERM.
  • An entrypoint script must end with exec "$@", or the shell stays PID 1.
  • Use COPY: ADD extracts local archives and does not extract remote ones. COPY --chown avoids a later chown -R.
  • ARG is build-time and per-stage; ENV persists into the image. Neither is safe for secrets — use --mount=type=secret.

Check yourself

ENTRYPOINT python app.py — a deploy drops connections and every stop takes ten seconds. Diagnose and fix.

Shell form, so the container runs /bin/sh -c "python app.py": sh is PID 1 and Python is its child. docker stop SIGTERMs PID 1, sh does not forward it, and after the ten-second grace period Docker SIGKILLs everything — hence dropped connections and exit 137. Fix with exec form, ENTRYPOINT ["python", "app.py"], so Python is PID 1. Then make sure Python actually installs a SIGTERM handler, because PID 1 ignores signals with no handler; if it cannot, add --init.

An image has ENTRYPOINT ["node"] and CMD ["server.js"]. What runs for docker run img --version?

node --version. Run-time arguments replace CMD and are appended to ENTRYPOINT, so server.js is dropped and --version takes its place. This is exactly the intended design: ENTRYPOINT fixes what the image is (a Node runtime), CMD supplies a sensible default, and the user can override the default without losing the entrypoint. To bypass node altogether you need --entrypoint, for instance docker run --entrypoint sh -it img.

A second build stage uses $BUILD_ENV and gets an empty string, though --build-arg BUILD_ENV=production was passed and it worked in stage one. Why?

ARG is scoped to a single stage. Declaring it in stage one does not make it available in stage two — each stage must re-declare ARG BUILD_ENV (no default needed) to receive the value. The related rule: an ARG before the first FROM is available to FROM lines but not inside any stage unless re-declared there. The demo above shows both cases, including what happens when you forget.

A colleague passes an npm token with --build-arg NPM_TOKEN=…, noting it is not an ENV so it will not be in the image. Are they right?

No. Build-argument values are recorded in the image's build metadata and Docker documents them as visible via docker history, so anyone who can pull the image can recover the token. Separately, the token may have been written into a layer by whatever consumed it — an .npmrc, a lockfile, a package cache. The fix is RUN --mount=type=secret, which exposes the value on a tmpfs during that one instruction and never commits it to a layer. And regardless of the mechanism, a token that has been in a build should be rotated.
