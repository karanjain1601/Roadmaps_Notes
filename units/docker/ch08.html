BuildKit, multi-arch and provenance

Chapters 5 to 7 were about what a Dockerfile says. This one is about the machine that reads it. BuildKit is why stages run in parallel, why cache mounts and build secrets exist, and why one command can produce an arm64 image on an x86 laptop — though how it does that is a decision worth making rather than accepting, because the wrong choice is ten times slower.

BuildKit has been the default since Docker 23, so docker build already uses it. docker buildx build is the extended CLI: it accepts everything docker build does plus the multi-platform, cache-export and attestation flags, and it can drive builders that are not the local daemon.

The default driver is the one that surprises people

--platform linux/amd64,linux/arm64 fails on a fresh install with "multiple platforms feature is currently not supported for docker driver". Nothing is wrong with your command — the default driver cannot do it. Create a docker-container builder once and the same command works.

Building for another architecture

Three approaches with very different costs.

Chapter 3 introduced the image index: one tag pointing at several per-platform manifests, so the same name works on an ARM laptop and an x86 server. Producing one means building the image once per platform, and there are three ways to do that:

ApproachHowCost
EmulationQEMU runs the foreign binaries via binfmt_miscWorks for anything; 5–20× slower for compilation
Cross-compilationBuild natively, targeting the other architectureFast, and only possible if the toolchain supports it
Native buildersOne real machine per architectureFast and universal; you have to run the machines

--load and multi-platform do not mix

A multi-platform build produces an index, and the classic Docker image store cannot hold one — so --load fails and you must --push, or build a single platform locally. Two workarounds: build --platform linux/arm64 --load for the one you want to test, or enable the containerd image store in Docker Desktop, which can hold an index. Either way, "why can I not see my multi-arch image in docker images" has this answer.

The cross-compilation pattern

Two predefined build args, and a large speed-up.

BuildKit supplies the platform as build arguments. BUILDPLATFORM is the machine doing the building; TARGETPLATFORM is what you are building for. Pinning the build stage to BUILDPLATFORM makes it run natively while still producing a foreign binary:

Go — no emulation anywhere
# syntax=docker/dockerfile:1

FROM --platform=$BUILDPLATFORM golang:1.23-alpine AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /out/server ./cmd/server

FROM gcr.io/distroless/static:nonroot
COPY --from=build /out/server /server
ENTRYPOINT ["/server"]
Predefined ARGExample value
BUILDPLATFORM, BUILDOS, BUILDARCHlinux/amd64, linux, amd64
TARGETPLATFORM, TARGETOS, TARGETARCHlinux/arm64, linux, arm64
TARGETVARIANTv7 for linux/arm/v7, empty otherwise

They must be declared with ARG inside the stage that uses them (chapter 5's scope rule), but need no default and no --build-arg — BuildKit supplies the values.

Which runtimes can do this

Go and Rust cross-compile natively, so the pattern above is close to free. Interpreted languages have nothing to compile, so a Node or Python image is mostly a fast file copy under emulation — unless it has native modules or C extensions, which must be built for the target and therefore need emulation or a native builder. JVM languages produce architecture-independent bytecode, so only the base JRE differs. The demo above prices each case.

Build secrets and other mounts

Chapter 5 established that ARG is not safe. This is what is.

the four mount types
# syntax=docker/dockerfile:1

# a secret: a tmpfs file, present only during this instruction
RUN --mount=type=secret,id=npmtoken,required=true \
    NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci

# an SSH agent socket, for private git dependencies
RUN --mount=type=ssh git clone git@github.com:acme/private-lib.git /lib

# files from another stage or image, without copying them into a layer
RUN --mount=type=bind,from=schema,source=/schema,target=/schema \
    ./generate --from /schema

# scratch space that is never committed
RUN --mount=type=tmpfs,target=/tmp/work ./big-extract.sh
supplying them
$ docker build --secret id=npmtoken,env=NPM_TOKEN .
$ docker build --secret id=npmtoken,src=./token.txt .
$ docker build --ssh default .                      # forward your agent

$ docker history --no-trunc my-app | grep -i token   # nothing
$ docker save my-app | tar -xO --wildcards '*/layer.tar' | grep -a npmtoken   # nothing

Provenance is another place build args show up

Attestations record how the image was built, and that record includes the build arguments. So a token passed with --build-arg is now recoverable from two places rather than one — docker history and the provenance attestation. This makes the chapter 5 advice stronger rather than weaker: use a secret mount, and treat any token that has been through a --build-arg as compromised.

Provenance and SBOM

Two machine-readable answers to "where did this image come from and what is in it".

producing and reading them
$ docker buildx build --provenance=mode=max --sbom=true \
    -t ghcr.io/acme/api:2.4.1 --push .

$ docker buildx imagetools inspect ghcr.io/acme/api:2.4.1 \
    --format '{{json .Provenance.SLSA.invocation.configSource}}'
$ docker buildx imagetools inspect ghcr.io/acme/api:2.4.1 \
    --format '{{range .SBOM.SPDX.packages}}{{.name}} {{.versionInfo}}{{println}}{{end}}' | head
AttestationRecordsAnswers
ProvenanceThe Dockerfile, source repository and commit, base image digests, build arguments, builder identity, timestampsWas this image built from the code we think, by the pipeline we think?
SBOMEvery package the scanner detected, with versions and licencesAre we affected by the CVE announced this morning?

mode=min records the essentials; mode=max adds the full build definition and the source materials. The practical payoff arrives with the next emergency: when a widely used library has a critical CVE, an SBOM query across your registry answers "which of our 200 images contain it" in seconds rather than a week of rebuilding and grepping. Chapter 17 covers acting on that answer.

Signing is the missing third piece

Provenance says how an image was built; it does not prove nobody replaced it afterwards. Signing does — cosign sign with a keyless OIDC identity, verified in an admission policy, so only images built by your pipeline can be deployed. Chapter 15 covers it alongside registries, and chapter 17 covers the policy side.

Reproducible builds

Building the same source twice and getting the same digest is harder than it sounds.

Digest reproducibility

Real SHA-256: build the same source twice, an hour apart, and compare
build A — 09:14
build B — 10:22, same commit

the flags that help
# pin every timestamp in the image to a fixed point, usually the commit date
$ export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
$ docker buildx build --output type=image,name=app,rewrite-timestamp=true .

# and pin the base by digest rather than by tag (chapter 3)
FROM node:22-alpine@sha256:41523187cf…

Full bit-for-bit reproducibility is achievable and demanding: every timestamp fixed, every dependency pinned by hash, every base pinned by digest, and no build step that embeds the clock or a random value. Most teams do not need it. What every team does need is the weaker property — that the image running in production corresponds to a known commit — and that is what pinning bases by digest plus recording provenance gives you, at almost no cost.

Building several images at once

buildx bake, for when one docker build is no longer the unit of work.

docker-bake.hcl
variable "TAG" { default = "dev" }

group "default" { targets = ["api", "worker"] }

target "common" {
  context    = "."
  platforms  = ["linux/amd64", "linux/arm64"]
  cache-from = ["type=registry,ref=ghcr.io/acme/cache"]
  cache-to   = ["type=registry,ref=ghcr.io/acme/cache,mode=max"]
}

target "api" {
  inherits   = ["common"]
  dockerfile = "docker/api.Dockerfile"
  tags       = ["ghcr.io/acme/api:${TAG}"]
}

target "worker" {
  inherits   = ["common"]
  dockerfile = "docker/worker.Dockerfile"
  tags       = ["ghcr.io/acme/worker:${TAG}"]
}
using it
$ docker buildx bake --print                  # resolve and show the plan, build nothing
$ docker buildx bake                           # the default group
$ docker buildx bake api --set api.tags=…      # one target, with an override
$ TAG=2.4.1 docker buildx bake --push

The value is that build configuration stops living in a shell script full of repeated flags: platforms, cache settings and tags are declared once and inherited, and --print gives you a reviewable plan. It is also what CI should call, so local and CI builds cannot drift apart.

The short version

Chapter 8 in eight lines

  • BuildKit is the default builder; buildx is the CLI exposing multi-platform, cache export and attestations.
  • The default docker driver cannot build multi-platform — create a docker-container builder once.
  • Three ways to build for another architecture: emulation (universal, 5–20× slower for compilation), cross-compilation (fast, toolchain permitting), native builders (fast, but you run the machines).
  • FROM --platform=$BUILDPLATFORM plus ARG TARGETOS TARGETARCH is the cross-compile pattern, and it is close to free for Go and Rust.
  • Multi-platform builds produce an index, which the classic image store cannot hold — so --push, not --load.
  • --mount=type=secret is the only mechanism here that leaves nothing in a layer, in history, or in provenance.
  • Provenance records build arguments, so a secret in --build-arg is now recoverable from two places.
  • Pinning the base by digest plus recording provenance gets you the property you actually need; bit-for-bit reproducibility is a further, much larger job.

Check yourself

Your CI arm64 build takes 24 minutes; the amd64 build takes 90 seconds. Same Dockerfile, a Go service. What is happening and what do you do?

The arm64 build is running under QEMU emulation, so the Go compiler is executing as translated instructions — a 10-to-20-fold slowdown on a CPU-bound workload. Because it is Go, you do not need emulation at all: pin the build stage with FROM --platform=$BUILDPLATFORM, declare ARG TARGETOS TARGETARCH, and pass them as GOOS and GOARCH. The compiler then runs natively and emits an arm64 binary, bringing the arm64 leg back to roughly the amd64 time. If the image needed cgo, cross-compilation gets harder and a native arm64 builder is the better answer.

docker buildx build --platform linux/amd64,linux/arm64 --load . fails. Two reasons it might.

First, the default docker driver does not support multi-platform builds at all — the fix is a docker-container builder. Second, even with the right driver, a multi-platform build produces an image index and the classic Docker image store cannot represent one, so --load has nowhere to put it; use --push, build a single platform with --load, or enable the containerd image store. The two failures look similar and the error messages differ, so read them rather than assuming.

Why is --build-arg GITHUB_TOKEN=… worse now than it was before attestations existed?

Because there is a second copy. It was already visible via docker history, which Docker documents. Provenance attestations additionally record the build invocation including its arguments, so an image built with --provenance=mode=max carries the token in its attestation as well — and attestations are designed to be published and queried, which is the opposite of what you want for a credential. Use --mount=type=secret, which appears in none of the three places, and rotate anything already exposed.

Two builds of the same commit produce different digests. Name three plausible causes, in order of likelihood.

First, the base image was pinned by tag and resolved to a different digest between the two builds — a moving tag makes every layer above it differ (chapter 3). Second, file timestamps: layer tarballs record modification times, so files created during the build carry the clock unless SOURCE_DATE_EPOCH and rewrite-timestamp are set. Third, unpinned dependencies: an install that resolves a floating version range fetches different bytes. Beyond those: a label containing the build date, a generated file embedding a UUID, or non-deterministic ordering in an archive. The demo above isolates each factor so you can see which one moves the digest.
