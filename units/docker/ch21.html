Chapter 21Beyond Docker

Podman, containerd and the OCI

Everything in the previous twenty chapters is portable, because almost none of it is really about Docker. Images, the runtime contract and the registry API are all standards — so the images you built will run under Podman, containerd or Kubernetes unchanged, and what actually differs between the tools is narrower and more interesting than the marketing suggests.

The three OCI specifications

Chapter 1 mentioned them. Here is what each one actually fixes in place.

SpecificationDefinesWhich is why
image-specThe manifest, the config blob, layer media types, and the index for multi-platform (chapter 3)Any tool can read any image
runtime-specA filesystem bundle plus a config.json, and the lifecycle: create, start, kill, deleteAny runtime can run any bundle
distribution-specThe /v2/ HTTP API for manifests and blobs (chapter 15)Any client can push to any registry
the runtime contract, in the raw
# a "container" at the lowest level is a directory and a JSON file
$ mkdir -p bundle/rootfs && cd bundle
$ docker export $(docker create alpine) | tar -C rootfs -xf -
$ runc spec                                    # writes config.json
$ sudo runc run demo                            # and that is a container
/ # exit
$ sudo runc list

That is the whole runtime abstraction: a root filesystem and a specification of namespaces, cgroups, capabilities, seccomp and the process to run. Everything from chapters 2, 10 and 18 appears in that config.json — which is what Docker, Podman and Kubernetes are all ultimately generating.

Why live-restore can work at all

Container processes are children of a shim, one per container, not of the daemon — so restarting dockerd does not orphan or kill them (chapter 20). The shim also holds the container's stdio and reports its exit status, which is how the exit code survives a daemon that was not running when the process died. That architecture is the reason a daemon is less of a single point of failure than it appears.

The differences that actually bite

Rootless Podman cannot bind ports below 1024 without a sysctl change, so -p 80:80 fails where Docker succeeds. On SELinux systems, bind mounts need :z or :Z far more often (chapter 11). --privileged is privileged only within your user namespace, which is a feature and surprising the first time. And rootless networking runs in userspace, so throughput is lower and the source address a container sees may be rewritten. None of these is a defect — they are the visible cost of not having a root daemon.

The namespace detail explains a common confusion: an image pulled by Docker is invisible to Kubernetes on the same machine even though both use the same containerd, because they live in different namespaces. ctr -n moby images list and ctr -n k8s.io images list return different sets.

Low-level runtimes

Swappable, and one of them changes the security model entirely.

RuntimeIsolationCostUse when
runcNamespaces and cgroups — the defaultEssentially noneAlmost always
crunThe same, implemented in CLower memory, faster startVery high container density
youkiThe same, in RustComparable to crunCuriosity, mostly
runsc (gVisor)A userspace kernel intercepting syscallsSyscall overhead; some incompatibilityRunning untrusted code
KataA lightweight VM per containerMemory and boot overheadHardware-level isolation between tenants
registering and using one
# /etc/docker/daemon.json
{ "runtimes": { "runsc": { "path": "/usr/local/bin/runsc" } } }

$ docker run --rm --runtime=runsc alpine dmesg | head -3
[    0.000000] Starting gVisor…              # not the host kernel

$ docker run --rm --runtime=runsc alpine uname -r
4.4.0                                          # gVisor's reported version

The distinction that matters: runc, crun and youki are interchangeable implementations of the same isolation model, so switching between them is a performance decision. gVisor and Kata change the model — the container no longer talks to the host kernel directly, which is the only thing on this page that meaningfully alters chapter 18's escalation analysis. Both cost real performance, and both are the right answer when you are running code you did not write.

Buildah's scriptable form, which has no Dockerfile equivalent
$ ctr=$(buildah from gcr.io/distroless/static:nonroot)
$ buildah copy $ctr ./server /server
$ buildah config --entrypoint '["/server"]' --user 65532 $ctr

That is the same image a multi-stage Dockerfile would produce, assembled by a shell script instead — occasionally useful when the build logic is genuinely dynamic, and worse than a Dockerfile whenever it is not, because you have traded a declarative artefact for imperative code.

The standards are why this is a small decision

Because image-spec, runtime-spec and distribution-spec are settled, switching container tooling is closer to changing shell than changing database. Nothing you learned in chapters 3 to 20 becomes wrong — the layer model, the cache behaviour, the capability set, the digest discipline all transfer intact. What changes is which process holds your containers and whether it runs as root, and that is worth choosing deliberately rather than by default.

The short version

Chapter 21 in eight lines

  • Three OCI specifications — image, runtime, distribution — make images, runtimes and registries interchangeable.
  • A container at the lowest level is a root filesystem plus a config.json, and runc will run one directly.
  • Container processes are children of a per-container shim, not of the daemon. That is why live-restore works.
  • Podman has no daemon and is rootless by default; containers are held by a conmon per container.
  • Podman adds pods and Kubernetes YAML generation, and manages services with systemd rather than restart policies.
  • containerd partitions by namespace, so Docker's images (moby) are invisible to Kubernetes (k8s.io).
  • runc, crun and youki are performance choices; gVisor and Kata change the isolation model.
  • Migration cost is near zero for images and Dockerfiles; the real cost is rootless assumptions.

Check yourself

You pull nginx:alpine with Docker on a Kubernetes node, and the kubelet still pulls it again. Both use containerd. Why?

containerd partitions its content and images by namespace. Docker operates in moby; the kubelet operates in k8s.io. They share the same containerd process and the same on-disk content store, but the image references live in separate namespaces, so a pull in one is not visible to the other. Confirm with ctr -n moby images list against ctr -n k8s.io images list. It is also why docker images on a Kubernetes node shows almost nothing of what the node is actually running.

A team moves to rootless Podman. -p 80:80 now fails and a bind-mounted directory is unreadable. Explain both.

Both come from not being root. Binding a port below 1024 is a privileged operation, and a rootless process does not have it — the fixes are to publish a high port and let a proxy front it (chapter 20), or lower net.ipv4.ip_unprivileged_port_start. The unreadable mount is usually SELinux: Podman is common on RHEL-family systems where a bind mount needs a :z or :Z label, and separately the UID mapping means the container's user is not the directory's owner (chapter 11). Neither is a Podman defect; they are what chapter 18 called the visible cost of the structural fix.

Would switching from runc to crun change your answer to chapter 18's escalation analysis?

No. crun is a different implementation of the same runtime specification, so the isolation is identical — namespaces, cgroups, capabilities and seccomp behave the same way, and every path in that tracer stays exactly as open or closed as before. It is a performance and memory choice, worth making at high container density. The runtimes that do change the analysis are gVisor, which puts a userspace kernel between the container and the host so most syscalls never reach the real kernel, and Kata, which puts a VM boundary there. Both cost measurable performance in exchange.

Your CI runs in Kubernetes with no Docker socket, and you need to build images. What are the options?

A daemonless builder. BuildKit as a pod, addressed as a remote builder (chapter 8) — the closest to what you already do, and it keeps the cache backends. Kaniko, which executes a Dockerfile in userspace inside an ordinary container. Buildah, rootless, accepting the same Dockerfiles. For Go or Java specifically, ko and Jib skip the Dockerfile entirely. What you should not do is mount the node's socket or run privileged Docker-in-Docker to avoid the question, for the reasons in chapters 16 and 18.
