Chapter 9Running containers

docker run, end to end

Starting a container is easy and stopping one is where the bugs live. A deploy that drops connections, a crash loop that reports itself as healthy, a container that takes exactly ten seconds to die every single time — all three are the same small set of mechanics, and all three are visible on a timeline once you know what the daemon is actually doing.

What docker run actually does

Two API calls, and about nine steps between them.

The interesting part is the order. Create allocates everything; start runs the process. Between them the image layers are mounted as an overlay (chapter 3), the writable layer is allocated, the network endpoint is created and attached (chapter 12), volumes are mounted (chapter 11), the cgroup is written (chapter 10) and the namespaces are set up (chapter 2). Only then does runc execute your entrypoint.

Exit codeMeans
0Clean exit
1–124The application's own exit code

The three codes worth memorising

137 is SIGKILL — either the OOM killer (chapter 10) or a stop that timed out, and State.OOMKilled distinguishes them. 143 is SIGTERM, meaning the container was asked to stop and did. 125 means the container never ran at all, so stop reading your application logs and read the Docker error instead.

Stopping, in slow motion

docker stop is a two-phase operation with a deadline.

The sequence is: send STOPSIGNAL (SIGTERM unless the image says otherwise) to PID 1, wait up to stop-timeout (10 seconds by default), then send SIGKILL, which cannot be caught. Everything interesting is in what your process does with that window.

A service that takes 25 seconds to finish long-lived requests, behind a default 10-second timeout, has 15 seconds of work killed on every single deploy — quietly, because the container does exit and the exit code is buried. Set --stop-timeout above your worst-case drain, make the application's own graceful timeout slightly lower than that, and check the exit code is 0 rather than 137 after a deploy. Restart policies and backoff

There is an exponential backoff, and almost nobody knows its rules.

Docker's restart manager waits before each retry: 100 ms, doubling each time, capped at one minute. The delay resets to 100 ms once the container has run for more than 10 seconds. Those two numbers produce very different behaviour depending on how fast your container fails:

seeing a crash loop for what it is
$ docker ps
CONTAINER ID   IMAGE     STATUS                          NAMES
7d6c5b4a3928   api:2.4   Restarting (1) 34 seconds ago   api      <- not "Up"

$ docker inspect -f '{{.RestartCount}} {{.State.Status}} {{.State.ExitCode}}' api
47 restarting 1

$ docker events --filter container=api --filter event=restart
$ docker logs --tail 20 api                  # the same startup error, 47 times
always plus a fast crash is an outage that looks like a running service

After a dozen failures the delay reaches a minute, so the container spends most of every minute stopped while docker ps shows Restarting rather than Exited. Nothing alerts, because from the daemon's point of view the policy is working. The two things that turn this into a visible failure are a HEALTHCHECK (chapter 5) and alerting on RestartCount — and the reason orchestrators exist is that they treat a crash loop as a state to report rather than a policy to honour (chapter 20).

Why docker logs sometimes shows nothing

It replays what the daemon captured from PID 1's stdout and stderr, so anything the application wrote to a file inside the container is invisible to it. That is the single most common logging misconfiguration in containers: a framework defaulting to /var/log/app.log produces an empty docker logs and a log file that vanishes with the container. Log to stdout and let the platform route it (chapter 19).

One-shot containers

The underused half of Docker: containers as commands.

tools you never install
$ docker run --rm -v "$PWD:/w" -w /w node:22-alpine npm ci
$ docker run --rm -i alpine sh -c 'apk add -q jq && jq .' < data.json
$ docker run --rm -v "$PWD:/w" -w /w hadolint/hadolint hadolint Dockerfile
$ docker run --rm -it --network container:web nicolaka/netshoot   # ch. 12, ch. 19

# an alias that behaves like a local binary
$ alias aws='docker run --rm -it -v ~/.aws:/root/.aws -v "$PWD:/w" -w /w amazon/aws-cli'
exit codes as job status
$ docker run --rm migrate-image ./migrate up && echo "migrated"
$ docker create --name job batch-image ./process
$ docker start job && docker wait job          # prints the exit code
0
$ docker logs job && docker rm job

docker wait blocks until the container exits and prints its exit code, which makes a container a usable unit of work in a shell script or a CI step. Pair it with --rm for anything you do not need to inspect afterwards, since an exited container keeps its writable layer until removed (chapter 4).

Passing configuration

Four sources, one precedence order, and one parsing surprise.

precedence, lowest to highest
# 1. ENV in the image           (chapter 5)
# 2. --env-file, in file order
# 3. -e NAME=value
# 4. -e NAME                     (inherits the value from your shell)

$ docker run -e NODE_ENV=staging --env-file base.env --env-file prod.env app
#   -e wins over both files; later files win over earlier ones
--env-file is not a shell script

Docker parses it literally: KEY=value per line, no interpolation, no export, and quotes are part of the value. So PASSWORD="hunter2" sets a password including the quote characters, and URL=$HOST/api sets the literal string $HOST/api. A line with just KEY and no = means "take it from my environment", which is occasionally useful and often an accident. Verify with docker run --rm --env-file x.env alpine env before debugging anything else.

Kind of configurationPass it asWhy
Non-secret settings-e or --env-fileSimple, visible in inspect, which is fine
SecretsA mounted file, read at startupEnvironment variables appear in docker inspect, in crash dumps and in child processes
Large config filesA read-only bind mount or volumeChapter 11
Anything differing per environmentNever baked into the imageOne image, promoted between environments (chapter 15)

The last row is the principle worth holding onto: the image is the same in staging and production and the configuration is not. An image with the staging database URL compiled in cannot be promoted, so every environment needs its own build, and now the thing you tested is not the thing you shipped.

The short version

Chapter 9 in eight lines

  • Create allocates, start runs. Layers, writable layer, network endpoint, volumes, cgroup and namespaces are all set up before your process exists.
  • 137 is SIGKILL (OOM or a stop that timed out), 143 is SIGTERM, 125 means the container never ran.
  • docker stop sends STOPSIGNAL, waits --stop-timeout (10s default), then SIGKILL — which cannot be caught.
  • Set the stop timeout above your worst-case drain time, and the application's own graceful timeout slightly below it.
  • Restart backoff is 100 ms doubling to a 1-minute cap, resetting once the container survives 10 seconds.
  • So a fast crash loop settles into one attempt per minute while docker ps reports Restarting — an outage that raises no alarm.
  • attach connects to PID 1 (Ctrl-C stops the container); exec starts a new process; logs only ever shows what PID 1 wrote to stdout and stderr.
  • --env-file is parsed literally: quotes become part of the value and nothing is interpolated.

Check yourself

Every deploy shows a spike of 502s, and containers exit with 137 after exactly ten seconds. What is the fix, in two parts?

The application is not finishing its shutdown inside the default ten-second grace period, so SIGKILL arrives mid-request. Part one: raise --stop-timeout above the worst-case drain time. Part two — and this is the part usually missed — make the application actually drain: install a SIGTERM handler that stops accepting new connections, waits for in-flight requests, then exits, with its own graceful timeout set slightly below the Docker timeout so it exits by choice rather than by SIGKILL. If the process cannot be made to handle signals, add --init. Verify by checking the exit code is 0 rather than 137 after a stop.

A container with --restart always has RestartCount of 340 and reports Restarting. Users say the service is down. Reconcile those.

It is down, and the restart policy is hiding it. The container fails immediately on start, so the backoff has grown to its one-minute cap: it spends nearly every minute stopped, briefly starts, fails, and waits again. docker ps says Restarting rather than Exited, so nothing looks broken to the daemon — the policy is working as designed. Read the logs for the repeated startup error, and add a HEALTHCHECK plus alerting on RestartCount so the next one is visible. The simulator above shows the delay sequence.

Why does a container that crashes after 15 seconds hammer the host, while one that crashes instantly does not?

Because the backoff resets once the container has run for more than 10 seconds. A container living 15 seconds each time satisfies that threshold on every attempt, so the delay never grows past 100 ms — it restarts roughly four times a minute forever, and each attempt does whatever expensive startup work it does. The instant-crash case backs off to a one-minute cap and becomes cheap, if invisible. It is a genuinely counter-intuitive result: failing slightly slower makes the loop far more expensive, and it is why restart budgets belong in an orchestrator rather than in a doubling timer.

docker logs is empty but the application is clearly running and writing logs. Where are they?

In a file inside the container. docker logs replays only what the daemon captured from PID 1's stdout and stderr, so a framework configured to write /var/log/app.log produces nothing there — and that file lives in the writable layer, so it disappears when the container is removed. Find it with docker exec ls /var/log or docker diff (chapter 4), then reconfigure the application to log to stdout. A related case: logs written by a child process that redirected its own output, which is one more reason to make the real application PID 1.
