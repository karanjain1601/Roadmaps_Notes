The development loop

Containers make an environment reproducible and, done naively, make the edit-to-result loop forty times slower. The fix is not one technique but matching the technique to the change — a source edit and a dependency bump want completely different handling, and the tools that feel magical are the ones that let you say so.

24 min2 demos8 sections4 self-checks

The loop is the metric

Everything else in this chapter is about one number.

The only measure that matters for development tooling is how long from saving a file to seeing the result. Under a second and you stay in flow; ten seconds and you check your messages; a minute and you batch changes, which is how five small bugs become one large one.

you changed

The result that matters: no single approach is right for every change. A live-reload approach — bind mount or sync — turns a source edit into a second or two and is simply wrong for a dependency bump, because the container's node_modules never gets updated. Which of the two live approaches is faster depends on the platform: on Linux a bind mount has no overhead and wins narrowly, while across the Docker Desktop VM boundary sync wins clearly. That is why the good tools take a list of rules rather than a single mode.

Bind mount plus a watcher

The classic approach, and its three failure modes.

compose watch

Rules per path, which is what the loop-time model asked for.

the develop section
services:
  api:
    build: .
    develop:
      watch:
        - path: ./src
          action: sync            # copy the file in; the watcher reloads
          target: /app/src
        - path: ./public
          action: sync
          target: /app/public
        - path: ./package.json
          action: rebuild          # a dependency change needs a real build
        - path: ./config
          action: sync+restart     # config is read at boot, so restart
          target: /app/config
      ignore:
        - node_modules/
        - "*.test.ts"
ActionDoesRight for
syncCopies changed files into the running containerSource that a watcher inside will reload
rebuildRebuilds the image and recreates the containerDependency manifests, the Dockerfile itself
sync+restartCopies, then restarts the containerConfig read only at startup
sync+execCopies, then runs a command insideRegenerating something after a sync — migrations, codegen
running it
$ docker compose watch                 # start everything and watch
$ docker compose up --watch             # same, with logs interleaved
Why sync beats a bind mount on macOS and Windows

A bind mount makes every file read cross the VM boundary, forever. A sync copies the changed file into the container's own filesystem, so reads afterwards are native — you pay a one-off transfer per edit rather than a permanent tax on every access. On Linux a bind mount is already native and the difference is small; on Docker Desktop it is the difference between a usable and an unusable loop. The demo above shows both.

Attaching a debugger

Two things to get right: the port, and the path mapping.

exposing the debug port
# Node — bind 0.0.0.0, or nothing outside the container can attach
$ node --inspect=0.0.0.0:9229 src/server.js

# Python
$ python -m debugpy --listen 0.0.0.0:5678 --wait-for-client manage.py runserver

# Go — delve needs extra privileges to ptrace
$ docker run -p 2345:2345 --cap-add=SYS_PTRACE --security-opt seccomp=unconfined \
    app dlv exec --headless --listen=:2345 --api-version=2 /app/server

# Java
$ java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar

The port is the easy half. The half that consumes an afternoon is that your editor knows about /Users/you/proj/src/index.ts and the runtime knows about /app/src/index.ts, and until something translates between them your breakpoints stay unbound.

Tests in the image you ship

The strongest argument for containerising the test run.

$ docker build --target test .                    # one command, real environment
$ docker compose run --rm api npm test             # with dependencies started
$ docker compose run --rm --no-deps api npm run lint    # without them

Tests on the CI runnerThe runner's toolchain and librariesLogic bugs. Misses environment differences entirely
--target testThe same base image and dependency tree you shipVersion skew, missing system libraries, locale and timezone issues

integration tests against a real database
# compose.test.yaml
services:
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: test }
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
      retries: 15
    tmpfs: [/var/lib/postgresql/data]      # RAM-backed: fast, and disposable

  test:
    build: { context: ., target: test }
    depends_on:
      db: { condition: service_healthy }
    environment:
      DATABASE_URL: postgres://postgres:test@db:5432/postgres

Two details make that pattern good. The database's data directory is a tmpfs, so it is fast and leaves nothing behind. And the dependency is gated on service_healthy (chapter 13), so the suite does not fail on a cold start — which is otherwise the flakiest thing in any containerised test setup.

the whole run, exit code and all
$ docker compose -f compose.test.yaml run --rm --build test; ec=$?
$ docker compose -f compose.test.yaml down -v
$ exit $ec

Development hygiene

Four habits that prevent the usual annoyances.

  • A separate override for development, not a modified base file. compose.yaml stays production-shaped; compose.override.yaml adds the mounts, the dev command and the debug port — and it is picked up automatically, so nobody has to remember a flag.
  • Match your UID. user: "${UID:-1000}:${GID:-1000}" with UID and GID exported from your shell profile, so files created in a bind mount belong to you (chapter 11).
  • Prune on a schedule. A month of development leaves tens of gigabytes in the build cache and dangling images — docker system df then docker image prune and docker builder prune. Never --volumes without checking.
  • Keep .dockerignore honest. It is what keeps the context small and the cache stable (chapters 5 and 6), and in development it also stops your local .env from being copied into an image.
a weekly clean-up that is safe to run
$ docker system df
$ docker container prune -f              # stopped containers
$ docker image prune -f                   # dangling images only
$ docker builder prune -f --filter until=168h
$ docker volume ls -f dangling=true       # look before you prune these

The short version

Chapter 14 in eight lines

  • The metric is save to result. Under a second keeps you in flow; a minute changes how you work.
  • No single approach fits every change. Live reload makes a source edit near-instant; syncing a dependency manifest does nothing useful at all.
  • Bind mount plus a watcher is the classic approach; on Docker Desktop it needs polling and an anonymous volume over node_modules.
  • Never npm install on the host if you bind-mount the project — the host's binaries shadow the container's.
  • compose watch takes rules per path: sync for source, rebuild for manifests, sync+restart for config.
  • Sync copies into the container's own filesystem, so subsequent reads are native — the reason it beats a bind mount across a VM boundary.
  • Debuggers need the port bound to 0.0.0.0 and a path mapping; without the mapping, breakpoints stay unbound.
  • Run tests with --target test so they execute in the image you ship, with dependencies gated on service_healthy.

Check yourself

A colleague adds a dependency, and their container still cannot import it — though the file change is clearly synced. Why?

Syncing package.json copies the file into the container and nothing else: no install runs, so node_modules is unchanged. A dependency change needs the image rebuilt (or at minimum an install executed inside), which is exactly why compose watch distinguishes sync from rebuild and why the rules are per path. The same applies to a bind-mount setup — the mount makes the manifest visible instantly and installs nothing. Add a rebuild rule for the manifest, or run compose up --build after dependency changes.

Hot reload works on your Linux machine and not on a colleague's Mac, with the same Compose file. Explain, and give two fixes.

Docker Desktop runs a Linux VM, and inotify events from the macOS host do not reliably propagate across that boundary — so the watcher inside the container never learns the file changed. On Linux the bind mount is a native mount and events arrive normally. Fixes: enable polling in the watcher (CHOKIDAR_USEPOLLING, --legacy-watch, usePolling), which costs CPU but works; or switch to compose watch with a sync rule, where Compose itself detects the change on the host and pushes the file in, sidestepping inotify entirely. The second is better, and also faster to read from afterwards.

Your debugger attaches but every breakpoint shows as unbound. The port is published and the process has --inspect. What is missing?

The path mapping. Your editor identifies the file as /Users/you/proj/src/index.js; the runtime reports /app/src/index.js. Without a translation the debugger cannot match them, so it accepts the connection and binds nothing — which is why it looks like a connection problem and is not. Set localRoot to the workspace folder and remoteRoot to the container's working directory (or pathMappings for debugpy). If only a subdirectory is mounted, the roots are the mounted pair, not the project root — and with a build step in between you also need source maps, or you are mapping to files the runtime never executes.

Why run the test suite with docker build --target test rather than on the CI runner directly?

Because it runs against the same base image, system libraries and dependency tree you are about to ship, so it catches the class of failure that only appears in the deployed environment: a missing shared library, a different OpenSSL, a locale or timezone difference, a version of the runtime the runner does not have. Testing on the runner validates your logic against the runner's environment, which is not the artefact. It also reuses the cached dependency layers from the build (chapter 6), so it is usually no slower — and it gives you one command that behaves identically on a laptop and in CI.
