Docker Compose

Everything in Parts 1 to 3 was a flag on a command nobody can remember. Compose is that command written down and committed — one file describing several containers, their network, their volumes and the order they come up in. The two things worth learning properly are what depends_on actually waits for, and how four layers of configuration resolve into one value.

What Compose is

A declarative file, and a CLI that reconciles reality with it.

compose.yaml
name: acme

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/pg
    secrets: [pg]
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s
    networks: [backend]

  api:
    build:
      context: .
      target: runtime
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgres://postgres@db:5432/app
    networks: [backend, frontend]
    restart: unless-stopped

  web:
    image: nginx:1.27-alpine
    ports: ["127.0.0.1:8080:80"]
    depends_on: [api]
    networks: [frontend]

volumes:
  pgdata:

networks:
  frontend:
  backend:
    internal: true

secrets:
  pg:
    file: ./secrets/pg_password

That file is chapters 5, 9, 11 and 12 in one place: a build, a healthcheck, resource limits, a named volume, two networks with the tiered pattern, and a loopback-bound published port. docker compose up -d creates all of it; docker compose down removes it.

The project name is why down sometimes removes nothing

Compose finds its containers by a project label, and the project defaults to the directory name. Run up from ~/work/api and down from a copy at ~/work/api-2 and the second command finds nothing to remove, because it is looking for a different project. Set name: in the file and this class of confusion disappears.

The deploy key was originally Swarm-only, and most of it still is — but resources.limits is honoured by plain docker compose up, which is why memory and CPU limits live several levels deeper than every other runtime setting. Everything else under deploy (replicas, placement, update policy) is silently ignored outside Swarm.

Startup order and depends_on

The most misunderstood key in the file.

depends_on: [db] waits for the database container to be created and started. It does not wait for Postgres to finish initialising, accept connections, or be ready in any sense — so an API that connects on boot will reliably fail on a cold start and succeed on every subsequent one, which is exactly the pattern that makes people blame the network.

    build: .
    depends_on:
      db: { condition: service_healthy }
      migrate: { condition: service_completed_successfully }
And make the application retry anyway

service_healthy fixes the cold start; it does nothing for the database restarting at 3am while the API keeps running. A connection retry with backoff in the application is the only thing that survives both, and it makes the Compose ordering an optimisation rather than a requirement. This is the same conclusion chapter 9 reached about restart policies: ordering helps, resilience is the application's job.

Interpolation and environment

Four layers, two different jobs, and a name collision between them.

The confusion is that .env and env_file sound like the same thing and are not. .env substitutes variables into the Compose file itself, before anything runs. env_file passes variables into the container at runtime, and Compose never reads their values.

the four layers
# 1. .env in the project directory — interpolated into THIS FILE
#    TAG=2.4.1
#    DB_PORT=5432

services:
  api:
    image: ghcr.io/acme/api:${TAG:-latest}        # <- interpolation
    ports:
      - "${DB_PORT:?DB_PORT is required}:5432"     # <- fails if unset

    # 2. env_file — read by the CONTAINER, not by Compose
    env_file:
      - ./config/base.env
      - ./config/prod.env

    # 3. environment — highest priority of the container's own layers
    environment:
      NODE_ENV: production
      LOG_LEVEL: ${LOG_LEVEL:-info}                # interpolation works here too
      PASSTHROUGH:                                  # no value: take it from my shell
SyntaxMeans
${VAR}Substitute, or empty if unset
${VAR:-default}Default if unset or empty
${VAR-default}Default only if unset — an empty value stays empty
${VAR:?message}Fail with that message if unset or empty
$$A literal $ — needed for shell variables inside command
The shell always wins over .env

For interpolation the order is: shell environment, then .env. So an exported TAG left over in your terminal silently overrides the file, and docker compose config shows a value nobody wrote down. For the container's environment the order is different again: environment: beats env_file:, and later env_file entries beat earlier ones. When something is not the value you expect, docker compose config resolves everything and prints the answer — it is faster than reasoning about it.

Override files and merging

One base file plus environment-specific deltas — with merge rules worth knowing exactly.

how files combine
# automatic: compose.yaml plus compose.override.yaml, if present
$ docker compose up

# explicit, in order — later files override earlier ones
$ docker compose -f compose.yaml -f compose.prod.yaml up -d
$ COMPOSE_FILE=compose.yaml:compose.prod.yaml docker compose up -d

# always check the result before trusting it
$ docker compose -f compose.yaml -f compose.prod.yaml config

ports appends, and that surprises people

Adding ports: ["8080:80"] in an override does not replace the base file's ports — it adds to them, so you end up publishing both and the second binding fails with "port is already allocated". To genuinely replace a sequence you must set it to an empty list in the override first (ports: !reset [] in recent Compose), or restructure so the base file does not publish at all. The mapping keys behave the way you expect; the sequences do not.

Profiles

Optional services in the same file, off by default.

profiles
services:
  api: {}                          # no profile: always started

  mailhog:
    image: mailhog/mailhog
    profiles: [dev]

  seed:
    build: .
    command: ["./seed"]
    profiles: [tools]              # only ever run explicitly
using them
$ docker compose up                        # api only
$ docker compose --profile dev up           # api + mailhog
$ COMPOSE_PROFILES=dev,tools docker compose up
$ docker compose run --rm seed              # a profiled service runs on demand

A service with no profiles key always starts; one with a profile starts only when that profile is active. It is the clean answer to "one file per environment" — a single file with the optional extras behind profiles, rather than four files that drift apart.

Beyond up and down.

run and exec are different in a way that matters

exec enters the running container. run creates a new one from the same service definition — with its dependencies started, but without its published ports unless you pass --service-ports. So compose run api sh gives you a clean container that cannot be reached on port 8080, which is usually what you want for a shell and confusing the first time you try to debug a port with it.

The short version

Chapter 13 in eight lines

  • Compose is the docker run flags from Parts 1–3, written down. Nearly every service key maps to a flag you know.
  • The project name — from name:, -p or the directory — labels every resource and decides what down can find.
  • depends_on alone waits only for the container to start, which is why cold starts fail and warm ones do not.
  • condition: service_healthy is the fix, and it requires a healthcheck on the dependency.
  • Make the application retry anyway — ordering does nothing when the database restarts at 3am.
  • .env interpolates into the Compose file; env_file passes variables into the container. The shell beats .env.
  • Override merging: scalars replace, mappings merge by key, ports and other sequences append, and command is replaced wholesale.
  • docker compose config resolves the lot and prints it. Use it before reasoning about any of the above.

Check yourself

Your API crashes on docker compose up from clean, but works when you re-run it immediately. It already has depends_on: [db].

depends_on in list form means service_started: it waits for the database container to start, not for Postgres to accept connections. On a cold start the API dials a database still initialising and dies; on the second run the database is already up, so it works — which is what makes this look intermittent. Fix by giving db a healthcheck and using condition: service_healthy. Then add a connection retry in the application, because the Compose condition does nothing if the database restarts later.

An override file adds ports: ["8080:80"] and up now fails with "port is already allocated". Why?

Because ports is a sequence that concatenates across files rather than replacing. The base file's mapping is still there and yours was appended, so Compose tries to publish both — and if they collide on the host port, the second binding fails. Mappings like environment merge key by key as you would expect; sequences do not. Either reset the list in the override, or restructure so the base file publishes nothing and each environment file adds what it needs. docker compose config shows the merged result before you run it.

.env contains TAG=2.4.1 but Compose keeps using 2.3.0. Where is it coming from?

Your shell. For interpolation into the Compose file the precedence is shell environment first, then .env — so an exported TAG from an earlier command silently wins, and nothing in the repository explains the value. Check with echo $TAG and docker compose config | grep image. This is deliberate, because it lets CI set values without editing files, and it is a frequent source of "it works on my machine" when a stale export is involved.

Why does docker compose run api curl localhost:8080 fail when the service works in a browser?

Two reasons, both about run. It creates a new container rather than entering the running one, and that new container does not publish the service's ports unless you pass --service-ports — so there is nothing listening on 8080 in it. And localhost inside a container is that container's own loopback, not the host's, so even with ports published it would be the wrong address. Use compose exec api … to enter the running container, and address the other service by its Compose service name (chapter 12) rather than localhost.
