Storage: volumes, binds and tmpfs

Everything a container writes goes into a scratch layer that is deleted with it. Mounts are how you opt out of that — and the three kinds behave differently enough that choosing wrongly produces either data loss, a directory your process cannot write to, or a development setup that is mysteriously slow on one colleague's laptop.

The ephemeral writable layer

Chapter 3 built it. Here is what it costs you.

Writes from a running container land in its upper overlay directory. That layer has three properties worth stating plainly: it is deleted with the container, it is not shared with any other container, and it is slow for rewrites because of copy-up.

seeing it
$ docker run -d --name t alpine sh -c 'dd if=/dev/zero of=/data.bin bs=1M count=200; sleep 999'
$ docker diff t
A /data.bin
$ docker ps -s --filter name=t
CONTAINER   SIZE
t           210MB (virtual 217MB)      # 210MB of writable layer

$ docker rm -f t          # and it is gone, with no warning
Copy-up makes the container layer wrong for write-heavy work

Modifying a file that came from an image layer copies the whole file up first (chapter 3), so a database rewriting pages inside its image directory pays a duplication cost on the first write to every file, then loses everything on docker rm. A volume bypasses the overlay entirely — writes go straight to the host filesystem — which is why the official database images declare their data directory as a mount point and why you should give them a real one.

Mount spec resolver

What Docker infers from your flag, and what it does with the path

the two syntaxes
# short form: compact, and the type is inferred from the source
$ docker run -v pgdata:/var/lib/postgresql/data postgres:16
$ docker run -v /srv/conf:/etc/nginx/conf.d:ro nginx
$ docker run -v /var/cache nginx                       # anonymous volume

# long form: explicit, validates, and the only way to set some options
$ docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres:16
$ docker run --mount type=bind,source=/srv/conf,target=/etc/nginx/conf.d,readonly nginx
$ docker run --mount type=tmpfs,target=/tmp,tmpfs-size=64m app
The difference that matters: a missing host path

With -v /srv/typo:/data, Docker creates /srv/typo as an empty directory owned by root and mounts it — so the container starts, finds no data, and initialises an empty database while your real data sits untouched one typo away. With --mount type=bind,source=/srv/typo,target=/data, Docker refuses to start. That single behavioural difference is the strongest argument for --mount in anything automated.

Named volumes

Docker manages the location so you do not have to.

managing them
$ docker volume create pgdata
$ docker volume ls
$ docker volume inspect pgdata -f '{{.Mountpoint}}'
/var/lib/docker/volumes/pgdata/_data

$ docker volume ls -f dangling=true          # attached to nothing
$ docker volume prune                         # remove those. Reads: deletes data
$ docker run --rm -v pgdata:/d alpine du -sh /d      # how big is it?
backup and restore, the portable way
# back up: mount the volume plus a host directory, tar between them
$ docker run --rm -v pgdata:/from:ro -v "$PWD:/to" alpine \
    tar czf /to/pgdata-$(date +%F).tgz -C /from .

# restore into a fresh volume
$ docker volume create pgdata-restored
$ docker run --rm -v pgdata-restored:/to -v "$PWD:/from:ro" alpine \
    tar xzf /from/pgdata-2026-09-03.tgz -C /to

For a database, prefer its own dump tool — pg_dump, mysqldump — over a filesystem tar of a running data directory, which can capture a torn state. Stop the container first if you must copy the files.

VOLUME in a Dockerfile is usually a mistake

It forces an anonymous volume at that path on every run, whether or not the user wanted one. Those volumes are invisible in docker volume ls until you look for dangling ones, they accumulate silently, and they cannot be overridden away — a later RUN writing to that path in a derived image has its writes discarded. Declare nothing, document the path, and let the operator mount what they choose. The official database images use it, which is why docker volume ls on a development machine is full of unnamed volumes containing old databases.

Bind mounts

A host path, straight through — with two platform caveats.

the forms and the flags
$ docker run -v "$PWD:/app" -w /app node:22-alpine npm run dev   # absolute paths only
$ docker run -v /srv/conf:/etc/app:ro app                          # read-only
$ docker run -v /srv/data:/data:z app                               # SELinux: shared label
$ docker run -v /srv/data:/data:Z app                               # SELinux: private label

# mount a single file — the container sees exactly that file
$ docker run -v /etc/localtime:/etc/localtime:ro app
CaveatWhereEffect
Crosses a VM boundaryDocker Desktop on macOS and WindowsFile operations are much slower than native; node_modules and large repositories feel it most
File watching is unreliableSameInotify events may not propagate; hot reload needs polling
SELinux denies accessFedora, RHEL, CentOSPermission denied despite correct modes — needs :z or :Z
Single-file mounts do not survive replacementEverywhereAn editor that writes a new file and renames breaks the mount; mount the directory
The development pattern that avoids the slow case

Bind-mount the source but keep the dependency directory inside the container, by layering an anonymous volume over it: -v "$PWD:/app" -v /app/node_modules. Your edits appear instantly, while the thousands of small dependency files stay on the container's own filesystem where access is native. It also stops a host node_modules built for macOS from shadowing the Linux one built inside the image.

The UID mismatch

The single most common storage failure, and it is pure arithmetic.

There is no user namespace by default (chapter 2), so the UID inside the container is a UID on the host. A container running as UID 10001 writing to a directory owned by host UID 1000 gets whatever the other permission bits allow — usually nothing.

It works, and it makes the directory writable by every user and every container on the host, permanently, including anything that later escapes a neighbouring container. Finding the list is empirical: run with --read-only, watch it fail, add a tmpfs, repeat. Two or three iterations usually suffice, and the result is a container that cannot be modified at runtime — which removes a large class of persistence techniques an attacker would otherwise use (chapter 18).

Databases in containers

Fine, with three rules.

the shape that works
$ docker volume create pgdata
$ docker run -d --name db \
    -v pgdata:/var/lib/postgresql/data \
    -e POSTGRES_PASSWORD_FILE=/run/secrets/pg \
    -v /srv/secrets/pg:/run/secrets/pg:ro \
    --shm-size 256m \
    --stop-timeout 60 \
    -m 2g --cpus 2 \
    postgres:16

When not to

A production database on a single Docker host gives you containerisation's packaging benefits and none of its scheduling benefits, while adding a storage layer between the process and the disk. That is a reasonable trade for a small deployment and a poor one at scale, where a managed service or a dedicated host usually wins. In development, containerised databases are unambiguously correct — a disposable, version-pinned Postgres per project is one of the best things containers do.

The short version

Chapter 11 in eight lines

  • The writable layer is deleted with the container, shared with nothing, and slow to rewrite because of copy-up.
  • Named volume for data the app owns, bind mount for source and config you own, tmpfs for scratch and secrets.
  • A named volume that is empty is populated from the image, ownership included. A bind mount shadows whatever was there.
  • -v with a missing host path creates it as root-owned; --mount refuses to start. Prefer --mount in automation.
  • VOLUME in a Dockerfile forces an anonymous volume on every run and cannot be overridden away.
  • There is no user namespace by default, so container UID is host UID — and permission is decided by ordinary POSIX bits.
  • Fix the mismatch with --user, a named volume, or matching ownership. chmod 777 is not a fix.
  • --read-only plus tmpfs for /tmp and /run costs two iterations and removes a whole class of persistence.

Check yourself

You mount -v /srv/pgdata:/var/lib/postgresql/data and Postgres initialises an empty database. The data is definitely at /srv/pg-data. What happened?

The hyphen. -v silently created /srv/pgdata as an empty root-owned directory and mounted it, so Postgres saw an empty data directory and did what it does with one: initialised a fresh cluster. Your real data is untouched at /srv/pg-data. Two defences: use --mount type=bind,source=…, which errors on a missing source instead of inventing it, and prefer named volumes for database data so there is no host path to mistype.

An image runs as UID 10001. A bind-mounted host directory owned by 1000:1000 with mode 755 gives "permission denied" on write. Give three fixes and say which you would pick.

The container's UID matches neither owner nor group, so it falls to the other bits — r-x, no write. Fixes: chown -R 10001:10001 the host directory; run with --user "$(id -u):$(id -g)" so the process is the directory's owner; or replace the bind mount with a named volume, which is populated with the image's own ownership and therefore writable. On a server I would chown the directory, since it has one purpose; in development I would use --user; for anything the application alone owns I would use a volume. Not chmod 777.

Why does a named volume "just work" for Postgres while a bind mount to an empty directory often does not?

Because an empty named volume is populated from the image at that path on first use, including ownership — so the directory arrives owned by the postgres user the image expects. A bind mount does the opposite: it shadows whatever the image had there, so the container sees a host directory with host ownership and no initialisation. That single asymmetry explains most of the difference in how the two feel. Note it only applies while the volume is empty; once it has content, nothing is copied.

A colleague's npm run dev in a bind-mounted container is ten times slower on their MacBook than on your Linux box, and hot reload does not fire. Explain both.

Docker Desktop runs a Linux VM, so a bind mount crosses a boundary between the host filesystem and the VM. Every file operation pays that crossing, which is why a directory of thousands of small dependency files is dramatically slower — and why inotify events from the host may not reach the container, so watchers see nothing. Fixes: keep node_modules inside the container with an anonymous volume layered over the bind mount, and configure the watcher to poll. Neither is needed on Linux, where a bind mount is just a mount.
