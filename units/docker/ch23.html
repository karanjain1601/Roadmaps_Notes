The first two are different in kind from the rest

Numbers 3 to 15 are things that will eventually hurt you. Numbers 1 and 2 mean there is no boundary at all — no capability set, filesystem mode or read-only flag changes what they grant, so every other control on the list is decoration while either is in place. If you only ever act on one page of this unit, make it those two rows.

The short version

Chapter 23 in eight lines

  • Order build instructions by change frequency, and ship an artefact rather than a toolchain.
  • Exec form and a drain handler — the two lines that decide whether deploys are quiet.
  • Limits on everything, so a bug takes down one container rather than the host.
  • Build once, promote by digest, deploy the digest. Everything downstream depends on this.
  • Rebuild on a schedule. Currency fixes more findings than any scanner setting.
  • The two anti-patterns in a different class: the Docker socket and --privileged. Nothing else compensates.
  • A gate that blocks the actionable few gets respected; one that blocks everything gets disabled.
  • An unrehearsed restore is not a backup, and a scan is not a safety assessment.

Check yourself

You inherit a service with all fifteen anti-patterns. You have one afternoon. What do you do?

Remove the socket mount and --privileged first — those are not risks that materialise later, they mean no boundary exists now, and neither takes long. Then set memory and CPU limits, which is one line per service and converts "the host died" into "one container restarted". Then stop deploying a mutable tag: pin the digest currently running so a rollback target exists. Then rotate logs on the daemon, because a full disk is the most common single-host outage. That is an afternoon, and it addresses the four highest-damage rows. The build-side items — cache ordering, multi-stage, exec form — matter and can wait for a normal working day.

The reviewer flags your Dockerfile for COPY . . before npm ci. Explain the cost in your own terms.

Cache invalidation cascades downward (chapter 6). COPY . . changes whenever any file changes, so the layer digest changes, so every instruction after it reruns — including the dependency install, which is usually the slowest step in the build. Copying the manifest and lockfile first, installing, and only then copying the source means an ordinary code change reuses the install layer entirely. On a typical Node project that is the difference between a five-second and a fifty-second rebuild, repeated every time anyone edits anything.

Why do the checklists separate "before the first deploy" from "before calling it production"?

Because they answer different questions. The first is "will this work correctly and can I debug it" — exec form, drain handling, limits, logs to stdout, data in a volume. The second is "what happens when something goes wrong or someone attacks it" — capability dropping, no socket, firewall placement, digest deploys, a rehearsed restore, alerting. A service can pass the first list and be entirely reasonable for internal use, and the second list is what you owe anything carrying real traffic. Separating them also stops the second list from blocking the first, which is how checklists get abandoned.

A colleague says the reviewers here are just a linter and they already run hadolint. Fair?

Largely fair, and worth doing both. A dedicated linter has more rules, better parsing, and runs in CI where it belongs — these reviewers are a teaching device that happens to be usable. What they add is the reasoning: each finding links to the chapter explaining the mechanism, so "avoid shell form" arrives with the signal-delivery matrix behind it rather than as a rule to satisfy. The right end state is a linter in CI plus an understanding of why each rule exists, because the second is what lets you judge the exceptions.
