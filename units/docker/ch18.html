Chapter 18Security and operations

Hardening

Chapter 17 was about knowing which packages have known problems. This chapter is about making it not matter very much. A container is a process with restrictions, and the restrictions are all optional — which means the interesting question is not "is my container secure" but "what exactly can this process do, and what would it take to get out".

The root problem

There is no user namespace by default, so container root is host root.

Chapters 2 and 11 established the mechanism; here is the consequence. A container running as UID 0 is running as the host's UID 0, restricted only by the capability set, seccomp profile and namespaces it happens to have. Remove any of those restrictions and root in the container is root on the machine.

what root in a container still cannot do — by default
$ docker run --rm -it alpine sh
/ # id
uid=0(root) gid=0(root)
/ # mount -t tmpfs none /mnt
mount: permission denied                      # no CAP_SYS_ADMIN, and seccomp blocks mount
/ # sysctl -w kernel.hostname=x
sysctl: error setting key: Read-only file system
/ # touch /proc/sysrq-trigger
touch: /proc/sysrq-trigger: Read-only file system

$ docker run --rm -it --privileged alpine sh
/ # mount -t tmpfs none /mnt                  # works. And so does everything else
/ # fdisk -l                                   # the host's disks
running as a non-root user, properly
# create the user at build time, own what it needs, then switch
RUN addgroup -g 10001 app && adduser -u 10001 -G app -S -H app
COPY --from=build --chown=10001:10001 /out/app /app/
USER 10001:10001                    # numeric, so it works on scratch too (ch. 7)
Why non-root matters even with capabilities dropped
A kernel vulnerability reachable only by UID 0 becomes unreachable
Files written to bind mounts belong to a real user, not host root (chapter 11)
Container-internal escalation via setuid binaries needs somewhere to escalate from
Most platform policies (Kubernetes runAsNonRoot) simply require it

Capabilities

Docker grants fourteen by default. Most workloads need none of them.

Capability audit

What your workload actually needs, and the flags that follow

inspecting and restricting
$ docker run --rm alpine sh -c 'apk add -q libcap; capsh --print | head -3'
$ docker run --rm --cap-drop ALL alpine sh -c 'apk add -q libcap; capsh --print | head -3'

# drop everything, then add back only what is proven necessary
$ docker run --cap-drop ALL --cap-add NET_BIND_SERVICE nginx
$ docker inspect -f '{{.HostConfig.CapDrop}} {{.HostConfig.CapAdd}}' web
NET_BIND_SERVICE is usually avoidable

It exists to bind ports below 1024, and there is rarely a reason for a container to do so: listen on 8080 inside and publish it as 80 outside (-p 80:8080), and the capability becomes unnecessary. Official images increasingly ship unprivileged variants that do exactly this. The general principle: a capability you need because of a configuration choice is a capability you can remove by changing the configuration.

--privileged is not "a few more capabilities"

It grants every capability, exposes all host devices under /dev, and disables the seccomp and AppArmor profiles entirely. A privileged container is a root shell on the host with extra steps. The legitimate uses are narrow — Docker-in-Docker, some storage and networking tooling — and each has a narrower alternative: specific --cap-add flags, a single --device, or rootless DinD.

seccomp

A syscall filter, on by default, that quietly does a lot of work.

Docker's default seccomp profile blocks roughly forty of the several hundred available syscalls — the ones with no legitimate use inside a container and a history of vulnerabilities. It is applied unless you turn it off, and it is a large part of why root in a container is less dangerous than root on the host.

mount, umount2, pivot_rootFilesystem manipulation is the classic escape primitive

a custom profile, and turning it off (do not)
$ docker run --security-opt seccomp=./profile.json app
$ docker run --security-opt seccomp=unconfined app         # only to diagnose
$ docker info --format '{{.SecurityOptions}}'               # is it even on?

Custom profiles are rarely worth writing by hand — the default is well-tuned, and a bespoke allow-list breaks on the next runtime upgrade. The exception is a narrow, long-lived workload where you can enumerate its syscalls; tools exist to record a profile from a running process, and the result needs re-recording whenever the application changes.

Debuggers are why people disable seccomp, and they should not

Delve and gdb need CAP_SYS_PTRACE, and the common advice is --security-opt seccomp=unconfined --privileged, which removes every syscall restriction to solve a capability problem. --cap-add SYS_PTRACE alone is usually sufficient (chapter 14), and it belongs in a development override rather than the production compose file.

A second, path-based layer that most people never touch.

Both are disabled by --privileged, which is worth restating because it is the least visible thing that flag does. If you are on a distribution where one of these is active, leave it active and fix the denial rather than switching it off — the SELinux bind-mount case in particular has a one-character fix that people replace with --privileged.

The Docker socket

The single most dangerous thing you can mount.

what "just for monitoring" actually grants
$ docker run -it -v /var/run/docker.sock:/var/run/docker.sock alpine sh
/ # apk add -q docker-cli
/ # docker run -v /:/host --privileged -it alpine chroot /host sh
# whoami
root                     # on the host. Game over.

Access to the socket is access to the daemon's API, and the daemon runs as root and can start any container with any configuration. There is no read-only mode, no scope, and no capability set you can drop inside the mounting container that changes this — the escalation happens in a new container the daemon creates on your behalf.

Instead of mounting the socketUse
A container that needs container metadataA socket proxy allow-listing specific read-only endpoints

Testcontainers in CIRootless DinD, or Compose-managed services
A reverse proxy discovering containersA proxy with the socket, on its own network, nothing else on it
MonitoringThe metrics endpoint, or a read-only socket proxy

Rootless Docker

The structural fix for the root problem, with real costs.

Rootless mode runs the daemon and containers inside a user namespace as your unprivileged user, so container UID 0 maps to a high, harmless host UID. An escape lands you as a normal user, not as root — which changes the severity of every path in the demo above.

setting it up
$ dockerd-rootless-setuptool.sh install
$ export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
$ docker info -f '{{.SecurityOptions}}'
[name=rootless name=seccomp,profile=builtin ...]

# the middle ground: keep the root daemon, remap container UIDs
# /etc/docker/daemon.json
{ "userns-remap": "default" }
Rootless costsDetail
Privileged portsCannot bind below 1024 without extra configuration
NetworkingUserspace networking (slirp4netns or pasta) is slower; source IPs may be rewritten
Storage driversFewer options; overlay2 needs a recent kernel
Some resource limitscgroup delegation must be configured for memory and CPU limits to apply
--privilegedStill exists, but is now privileged only within your user namespace

userns-remap is the compromise: the daemon stays root, but containers get a UID mapping, so container root is an unprivileged host UID. It breaks fewer things than rootless and gives most of the benefit. Podman takes the rootless approach as its default, which is the main structural difference between the two tools (chapter 21).

The short version

Chapter 18 in eight lines

  • Container root is host root, restricted only by capabilities, seccomp and namespaces — all of which are optional.
  • Docker grants 14 capabilities by default and most workloads need none. Drop all, add back what breaks.
  • NET_BIND_SERVICE is usually avoidable: listen on 8080 and publish it as 80.
  • --privileged grants every capability, exposes all devices, and disables seccomp and AppArmor.
  • The default seccomp profile blocks about forty syscalls and does much of the real work. Do not disable it to fix a capability problem.
  • Mounting the Docker socket is unconditional host root. No capability set inside the container changes that.
  • Rootless mode or userns-remap makes container root an unprivileged host UID — the structural fix.
  • Order of value: no socket, no privileged, non-root, drop caps, no-new-privileges, read-only.

Check yourself

A monitoring agent needs the Docker socket "read only" — -v /var/run/docker.sock:/var/run/docker.sock:ro. Is that safe?

No. The :ro applies to the socket file, not to the API reachable through it — writes to a socket are how you send requests, so every endpoint remains available. Anything that can talk to the daemon can create a privileged container mounting the host filesystem, which is root on the machine. The mitigation is a socket proxy that allow-lists specific read-only endpoints and refuses container creation, placed on its own network with only the agent attached. Better still, use whatever metrics endpoint the thing actually needs.

A colleague fixes "operation not permitted" from Delve by adding --privileged --security-opt seccomp=unconfined. What is wrong, and what is right?

They removed every syscall restriction and every capability limit, plus AppArmor, to solve a single missing capability. Delve needs CAP_SYS_PTRACE; --cap-add SYS_PTRACE is almost always sufficient, and ptrace is permitted by the default seccomp profile precisely so debuggers work. The wider problem is where the flags live: this belongs in a development override (chapter 14), not in the file that also describes production — because --privileged added "temporarily" is how it reaches a server.

Your container runs as non-root with cap_drop: [ALL] and a read-only filesystem. It also has pid: host. What did you lose?

Visibility isolation, and possibly more. With the host PID namespace the container sees every process on the machine, so it can read command lines and environment from /proc — which is where secrets passed as environment variables end up (chapter 9). It also makes host processes targetable if the container ever gains CAP_SYS_PTRACE or runs as root. The other controls are still worth having and they do not compensate: a namespace you share is a boundary you removed, and no capability set restores it. The tracer above shows which paths open when you toggle it.

You have limited time. Rank: drop all capabilities, run rootless, switch to distroless, enable a custom seccomp profile.

Drop all capabilities first — one line, no behaviour change for most workloads, and it closes every capability-gated primitive. Rootless (or userns-remap) second: it is structural, making container root harmless, and worth the configuration cost. Distroless third — it removes the shell and package manager an attacker would use, and reduces the scan surface (chapters 7 and 17), but it changes your debugging story. A custom seccomp profile last: the default already blocks the dangerous syscalls, and a bespoke allow-list is high-effort, brittle across upgrades, and adds little over the first three.
