Networking

A container gets its own network stack — its own interfaces, routes and firewall rules — and Docker wires that stack to the outside with a virtual cable and a NAT rule. Two consequences catch nearly everyone: containers on the default bridge cannot resolve each other by name, and publishing a port can walk straight through your host firewall.

The wiring

A network namespace, a virtual cable, and a bridge.

Chapter 2 established that a container gets its own net namespace: its own interfaces, IP addresses, routing table and iptables rules, all separate from the host's. Docker connects that namespace to the world with a veth pair — a virtual cable with one end inside the container as eth0 and the other end plugged into a bridge on the host.

both ends of the cable
$ docker run -d --name web nginx
$ docker exec web ip -br addr
lo     UNKNOWN  127.0.0.1/8
eth0   UP       172.17.0.2/16              # inside

$ ip -br link | grep -E 'docker0|veth'
docker0        UP      172.17.0.1/16       # the bridge, and the container's gateway
veth3f9c2a1@if7 UP                          # the host end of the same cable

$ docker exec web ip route
default via 172.17.0.1 dev eth0             # everything leaves via the bridge
172.17.0.0/16 dev eth0 scope link

Outbound traffic is masqueraded: a NAT rule rewrites the container's source address to the host's, so the wider network sees traffic from the host and never learns the container exists. Inbound is the reverse and does not happen unless you ask for it, which is what publishing a port means.

what Docker wrote into iptables
$ sudo iptables -t nat -S | grep -E 'MASQUERADE|DOCKER'
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE      # outbound
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 8080 \
   -j DNAT --to-destination 172.17.0.2:80                        # -p 8080:80

creating and using networks

Create a network. Always.

The default docker0 bridge exists for backwards compatibility and behaves worse in every respect: no DNS between containers, every container on the host shares one flat network, and the only way to link two was the deprecated --link flag. A user-defined bridge costs one command, gives you name resolution, and isolates its members from containers on other networks. Compose creates one per project automatically, which is a large part of why Compose feels easier than raw docker run.

DNS between containers

An embedded resolver at a fixed address.

On a user-defined network, Docker runs a DNS server at 127.0.0.11 inside each container's namespace. It answers for container names, network aliases, and forwards anything else to the host's resolvers.

seeing it work
$ docker network create app
$ docker run -d --name db --network app postgres:16
$ docker run --rm --network app alpine cat /etc/resolv.conf
nameserver 127.0.0.11
options ndots:0

$ docker run --rm --network app alpine nslookup db
Name: db
Address: 172.18.0.2

# aliases, for when the name your code expects differs from the container name
$ docker run -d --name pg-primary --network app --network-alias db postgres:16
$ docker run -d --name pg-primary --network app --network-alias postgres postgres:16

DNS names are not the same as reachability

Name resolution and connectivity are separate. A container can resolve a name it cannot reach — for instance a stale DNS entry after a container was recreated with a new IP, which is why long-lived connection pools sometimes keep dialling an address that no longer exists. Applications that cache DNS results indefinitely (some JVM configurations, by default) are the classic victim. And on an --internal network, public names still resolve while nothing outside is reachable at all.

Publishing ports

The one place a Docker default is genuinely dangerous.

Port publishing resolver

Where it listens, who can reach it, and whether your firewall gets a say

FormBinds
-p 80Container port 80 to a random host port on all interfaces
-p 8080:80Host 8080 on every interface — including the public one
-p 127.0.0.1:8080:80Loopback only. Reachable from the host, nowhere else
-p 8080:80/udpUDP rather than TCP; both need publishing separately
-p 8000-8010:8000-8010A range, one rule per port
-PEvery EXPOSEd port to random high ports
Docker publishes past ufw and firewalld

Published ports are implemented as DNAT rules in the nat table, so the traffic is rewritten in PREROUTING and then traverses FORWARD — while ufw and most firewalld setups filter INPUT. The packet never passes the chain your rules are in. So a host with "deny incoming" configured, running -p 5432:5432, has an open database on the public internet and a firewall that reports everything is blocked. Two fixes: bind to loopback (-p 127.0.0.1:5432:5432) so nothing leaves the machine, or put your rules in the DOCKER-USER chain, which Docker evaluates first and never overwrites.

filtering that Docker respects
# DOCKER-USER is evaluated before Docker's own rules and survives restarts
$ sudo iptables -I DOCKER-USER -i eth0 ! -s 10.0.0.0/8 -j DROP

# check what is actually published, and on which address
$ docker port web
80/tcp -> 0.0.0.0:8080
$ sudo ss -tlnp | grep docker-proxy
$ sudo iptables -t nat -S DOCKER

Note that publishing has nothing to do with container-to-container traffic. Two containers on the same network reach each other on every port, published or not — publishing is exclusively about access from outside the Docker network. A database that needs to serve only the API container should publish nothing at all.

The tiered pattern this makes possible

Put db on backend only, web on frontend only, and api on both. The API can reach the database; the web tier cannot, no matter what it tries, because there is no route between the two networks. That is real network segmentation from three docker network commands, and it is what a Compose file with two networks is quietly doing.

Debugging

Most network problems are one of five things.

a toolbox container, sharing the target's namespace
# netshoot joins the container's network namespace, so it sees exactly what it sees
$ docker run --rm -it --network container:api nicolaka/netshoot
  ip addr; ss -tlnp; dig db; curl -v http://db:5432; tcpdump -i eth0 -n

$ sudo nsenter -t $(docker inspect -f '{{.State.Pid}}' api) -n ss -tlnp

Binding to localhost inside a container publishes nothing

A development server defaulting to 127.0.0.1:3000 is bound to the container's loopback, which nothing outside that namespace can reach — so -p 3000:3000 forwards to a port that refuses connections. The fix is in the application, not in Docker: bind 0.0.0.0. Frameworks that do this by default include Flask, Rails and Vite, and it is the single most common "my container will not respond" question.

Beyond one host

And two configuration issues that bite in corporate networks.

NeedApproach
Containers across several hostsoverlay with Swarm, or an orchestrator's own network (chapter 22)
A container with a real LAN addressmacvlan — it gets its own MAC and DHCP lease
IPv6Enable in daemon.json and give the network a v6 subnet
Fixed addresses--ip on a network with a defined --subnet
/etc/docker/daemon.json — the two settings worth knowing
{
  "default-address-pools": [
    { "base": "10.201.0.0/16", "size": 24 }
  ],
  "mtu": 1400
}

Address pools matter because Docker's defaults (172.17.0.0/16 onward) collide with plenty of corporate VPN ranges — and when they do, the symptom is that the VPN works until you start Docker, then a whole subnet becomes unreachable. MTU matters for the opposite reason: a VPN or overlay reduces the usable packet size, and a container still using 1500 sends packets that are silently dropped. Small requests succeed, large responses hang forever, and nothing logs an error.

The short version

Chapter 12 in eight lines

  • Each container gets a network namespace joined to a bridge by a veth pair; outbound traffic is masqueraded to the host's address.
  • Create a user-defined network. The default bridge has no DNS between containers and no isolation.
  • DNS is an embedded resolver at 127.0.0.11 answering for container names and --network-alias.
  • -p 8080:80 binds every interface; -p 127.0.0.1:8080:80 binds loopback only.
  • Published ports bypass ufw and firewalld, because DNAT sends traffic through FORWARD rather than INPUT. Use loopback binding or the DOCKER-USER chain.
  • Publishing is only about access from outside — containers on one network already reach each other on every port.
  • Put a container on two networks to bridge tiers; that is real segmentation for three commands.
  • An app bound to 127.0.0.1 inside a container is unreachable however you publish it. Bind 0.0.0.0.

Check yourself

A server has ufw with "deny incoming" and one container run with -p 5432:5432. Is the database exposed?

Yes, to the entire internet. Docker implements publishing as a DNAT rule in the nat table, so the packet is rewritten in PREROUTING and then traverses the FORWARD chain — while ufw's rules live in INPUT. The firewall is not wrong, it is simply not in the path. Fix by binding to loopback (-p 127.0.0.1:5432:5432) if only the host needs it, or by adding rules to DOCKER-USER, which Docker evaluates before its own and does not overwrite. Best of all, publish nothing: if only the API container talks to it, being on the same network is sufficient.

docker run --name api app cannot resolve db, though both containers are running. Why, and what is the one-line fix?

They are on the default bridge, which has no DNS between containers — a deliberate legacy behaviour, previously worked around with --link. They can reach each other by IP address, which is why "ping the IP works but the name does not" is the signature. The fix is to create a user-defined network and put both on it: docker network create app and --network app on each. Compose does this automatically for every project, which is most of why service names simply work there.

Your API container reaches the database fine; the web container must not. Describe the setup.

Two networks. db joins backend only, web joins frontend only, and api joins both — so the API bridges the tiers while the web container has no route to the database at all, regardless of credentials or configuration. Add --internal to backend and the database also loses outbound internet access, which is usually correct for a database. This is ordinary routing rather than a policy engine: without a shared network there is simply no path.

A container serves small API responses correctly but hangs on any large file. Same image works on another host.

An MTU mismatch, almost certainly a VPN or overlay on the failing host reducing the usable packet size below 1500. Small responses fit in one packet and succeed; a large transfer produces full-size packets that are dropped silently, so the connection stalls rather than failing — which is why nothing appears in the logs. Confirm with ping -M do -s 1400 from inside the container, then set the MTU on the Docker network or globally in daemon.json. The related corporate-network problem is a Docker subnet colliding with a VPN route, fixed with default-address-pools.
