Images, layers and content addressing

An image is not a disk snapshot. It is an ordered list of tarballs, plus a JSON file describing how to start a process, all addressed by the SHA-256 of their own contents. That structure explains layer caching, registry deduplication, why tags are untrustworthy, and the single most common reason images are far larger than they need to be.

What an image actually is

Four kinds of object, and one of them is the name you type.

ObjectIsAddressed by
LayerA tarball of filesystem changes — files added, modified, deletedSHA-256 of the blob
ConfigJSON: the ordered layer list, plus Env, Cmd, Entrypoint, User, architectureSHA-256 of the JSON — this is the image ID
ManifestJSON: pointers to the config and the layers, with sizesSHA-256 of the JSON — the digest in image@sha256:…
IndexJSON: one manifest per platform, for multi-arch imagesSHA-256 of the JSON
TagA mutable name in a registry pointing at a manifest or indexNothing — it is just a label

Because the config lists the layers, and the manifest names the config, changing any byte of any layer changes the config, which changes the manifest. It is a Merkle tree — the same structure Git uses for commits and trees, and it gives the same properties: content that is identical is stored once, and an identifier fixes the entire contents transitively.

look at a real one
$ docker pull nginx:1.27-alpine
$ docker image inspect nginx:1.27-alpine -f '{{.Id}}'
sha256:2b8b1b3a5c…                      # the CONFIG digest = the image ID

$ docker image inspect nginx:1.27-alpine -f '{{range .RootFS.Layers}}{{println .}}{{end}}'
sha256:63ca1fbb43…                      # diff_ids: the UNCOMPRESSED layer digests
sha256:8a3d5a0d3f…

$ docker image inspect nginx:1.27-alpine -f '{{index .RepoDigests 0}}'
nginx@sha256:41523187cf…                # the MANIFEST digest — what to pin in production

$ docker buildx imagetools inspect nginx:1.27-alpine    # the index, per platform
Three different digests, and people conflate them constantly

The image ID is the config digest, computed locally. The repository digest is the manifest digest, assigned by the registry. And each layer has two digests: its diffID (SHA-256 of the uncompressed tar, used locally) and its blob digest (SHA-256 of the compressed blob, used for transfer). They are all different numbers for the same image, and only the manifest digest is what you pin with image@sha256:….

Notice what lives in the config rather than in a layer: environment variables, the entrypoint, the working directory, the user. Those instructions create no filesystem layer at all — they only edit this JSON, which is why docker history shows them as 0 B.

How the layers become one filesystem

overlay2, and the two mechanics that decide your image size.

The layers are stacked by an overlay filesystem. Read-only layers are the lower directories, the container's writable layer is the upper directory, and the process sees a single merged view:

the actual mount
$ docker inspect -f '{{.GraphDriver.Data.LowerDir}}' web | tr ':' '\n' | head -3
/var/lib/docker/overlay2/9f8e…/diff        # topmost read-only layer
/var/lib/docker/overlay2/7d6c…/diff
/var/lib/docker/overlay2/5b4a…/diff        # the base

$ mount | grep overlay
overlay on /var/lib/docker/overlay2/3f9c…/merged type overlay
  (lowerdir=…9f8e/diff:…7d6c/diff:…5b4a/diff,
   upperdir=…3f9c/diff, workdir=…3f9c/work)
MechanicWhat happensCost
LookupTopmost layer containing the path winsFree
Copy-upWriting to a file from a lower layer copies the whole file up firstThe file's full size, every time
WhiteoutDeleting a lower-layer file writes a marker (.wh.<name>) in the upper layerNothing is reclaimed — the bytes stay below
Opaque directoryDeleting a whole directory writes .wh..wh..opq, hiding everything beneath itSame — hidden, not removed
Copy-up and whiteouts are the two facts that explain image bloat

A later layer can never make an image smaller. RUN rm -rf /var/lib/apt/lists/* in its own instruction adds whiteout markers on top of the layer that still contains every one of those files, so the image grows slightly. And RUN chown -R app /app after copying 200 MB of dependencies copies all 200 MB into a new layer, doubling it. The demo below prices both.

Reading an image you did not build

Where the size went, and what is in there.

layer by layer
$ docker history --no-trunc --human my-app:latest
IMAGE          CREATED BY                                      SIZE
<missing>      RUN npm ci                                      241MB
<missing>      COPY package*.json ./                           412kB
<missing>      ENV NODE_ENV=production                         0B      <- config only
<missing>      /bin/sh -c #(nop) CMD ["node" "server.js"]      0B

$ docker image inspect my-app -f '{{.Size}}'            # total, in bytes
$ docker system df -v                                    # per-image, shared vs unique
$ docker save my-app | tar -tv | head                     # the raw structure

<missing> is not an error: intermediate image IDs are not retained for pulled images, so only the layer sizes and the instruction that produced them survive. The 0 B rows are the config-only instructions — proof of the split described above.

Use dive once on your worst image

dive my-app:latest shows each layer's file tree with the bytes it contributed, and flags files that are added and later deleted — the exact waste the demo above models. It takes two minutes and usually finds something embarrassing: a cache directory, a .git folder, a 200 MB test fixture.

Why pulls are usually fast

Content addressing means the same layer is stored and transferred once.

Because a layer is named by its own digest, two images built FROM node:22-alpine share those base layers on disk and in the registry. A pull fetches only the digests you do not already have:

what a pull is really doing
$ docker pull my-app:v2
63ca1fbb43: Already exists          # base layers, shared with every other image
8a3d5a0d3f: Already exists
c41a2f0e77: Pull complete            # only the layers that changed
Digest: sha256:41523187cf…
Status: Downloaded newer image for my-app:v2

This is why instruction order in a Dockerfile is a deployment-speed decision, not a style preference: put the layers that rarely change underneath, and a new release ships only the top few megabytes. Chapter 6 is entirely about arranging that deliberately.

Sharing is by digest, not by name

Two layers are shared only if their contents hash identically. RUN apt-get update in two images produces two different layers, because the package lists differ by timestamp — so they cannot be shared even though the instruction is the same. Building both FROM the same pinned base image is what actually produces sharing.

Tags versus digests

A tag is a mutable pointer. In production that matters.

FROM nginx@sha256:41523187cf…   # 1.27-alpine

$ docker pull nginx@sha256:41523187cf…      # cannot possibly get anything else
"It worked yesterday" and the moving tag

A build that says FROM node:22 is a build whose base changes underneath it without a commit, a review or a notification — so a failure appearing overnight with no code change is usually this. The same reasoning applies to your own images: deploying my-app:latest means your rollback target is whatever latest happens to point at now, which may be the broken build. Digests in production, tags for humans; chapter 15 covers the tagging strategy that gives you both.

Multi-arch, in one paragraph

nginx:1.27-alpine usually resolves to an index, not a manifest — a list of per-platform manifests, and your client picks the one matching its architecture. That is why the same tag works on an ARM laptop and an x86 server, and why docker pull of an image with no linux/arm64 entry fails with a platform error rather than running slowly. Chapter 8 covers building these.

Where all of this lives

And how to reclaim the space it takes.

accounting for the disk
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          47        6         18.2GB    14.1GB (77%)
Containers      12        2         240MB     198MB (82%)
Local Volumes   9         3         3.4GB     2.1GB (61%)
Build Cache     312       0         6.8GB     6.8GB

$ docker system df -v                      # itemised, per image and volume

$ docker image prune                        # dangling images only — safe
$ docker builder prune --keep-storage 10GB   # bound the build cache
$ docker system prune                        # containers, networks, dangling images
$ docker system prune -a --volumes           # ...and everything unused. Reads volumes too
--volumes deletes data

docker system prune -a --volumes removes every volume not attached to a running container — which includes the database volume of anything you have merely stopped. There is no undo. Run docker volume ls and docker system df -v first, and prefer the narrower commands: docker image prune and docker builder prune reclaim most of the space with none of the risk.

The build cache is usually the biggest surprise in that table. It is not part of any image, it grows without bound by default, and docker image prune does not touch it — docker builder prune is the one that does.

The short version

Chapter 3 in eight lines

  • An image is ordered layers + a config JSON, described by a manifest, all named by the SHA-256 of their own contents — a Merkle tree.
  • The image ID is the config digest; the repository digest is the manifest digest; layers have both an uncompressed diffID and a compressed blob digest.
  • ENV, CMD, ENTRYPOINT, USER and WORKDIR create no filesystem layer — they edit the config, hence 0 B in docker history.
  • Layers stack with an overlay filesystem: topmost match wins, upper layer is writable.
  • Copy-up: modifying a lower-layer file copies the whole file up — so a later chown -R can double your image.
  • Whiteouts: deleting a lower-layer file only hides it. A later RUN rm never shrinks an image; combine cleanup into the same instruction.
  • Identical layers are stored and transferred once, so instruction order determines how much a release actually ships.
  • Tags are mutable pointers; only image@sha256:… is immutable. Pin digests in production.

Check yourself

Your Dockerfile ends with RUN rm -rf /root/.cache/pip and the image is unchanged in size. Why, and what is the fix?

Because that RUN is its own layer, and a layer cannot remove bytes from the layers beneath it — it writes whiteout markers that hide the cache while every file remains in the earlier layer, so the image gets marginally larger. Fix: do the cleanup in the same instruction that created the files (RUN pip install … && rm -rf /root/.cache/pip), so the cache never gets committed to a layer at all. Better still, use --mount=type=cache (chapter 6) so it is never in the build context, or a multi-stage build (chapter 7) so only the artefact is copied forward.

Two teams build images FROM python:3.12-slim. Do they share layers on disk? What if both run RUN apt-get update?

The base layers are shared, because they are byte-identical and therefore hash identically — stored once, and reported by docker system df -v as shared. The apt-get update layers are not shared: the package lists they write differ (timestamps, mirror state), so the tarballs hash differently even though the instruction text is the same. Sharing is a property of content, never of instructions — which is also why the build cache and the on-disk layer store are two separate things.

A colleague asks why ENV NODE_ENV=production shows 0 B while COPY package.json . shows 412 kB.

Because they change different objects. COPY writes files, so it produces a layer — a tarball with a digest and a size. ENV changes only the image config JSON, so there is no tarball and nothing to measure; the history entry exists to record the instruction. The same is true of CMD, ENTRYPOINT, WORKDIR, USER, EXPOSE and LABEL. It also means changing an ENV invalidates the build cache from that point on (chapter 6) while adding no bytes.

Production runs my-app:latest. A deploy breaks things and you need to roll back. What is the problem?

There is nothing to roll back to: latest now points at the broken image, and the previous one may have no tag at all. Tags are mutable pointers, so latest records only the most recent push rather than a history. What you want instead is an immutable reference per release — a digest, or a tag containing the commit SHA or version — recorded in whatever deploys the service, so rolling back is naming the previous one. Chapter 15 covers the strategy; the digest is what makes it reliable, because a digest cannot be repointed.
