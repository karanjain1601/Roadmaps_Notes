Chapter 20Security and operations

Production on one host

A single machine running Compose serves a great many real businesses, and does it with a fraction of the operational surface of a cluster. What it does not give you for free is a deploy without downtime, or a restore you can rely on — and both are achievable on one host if you build them deliberately.

When one host is the right answer

And the specific things that end that.

One host is fine whenYou need more when
The load fits comfortably in one machine, with headroomYou have outgrown the largest sensible instance
A few minutes of downtime for host maintenance is tolerableAn availability target rules that out
One or two people operate itMany teams deploy independently and need isolation
Services are stable in number — tens, not hundredsServices and their dependencies change constantly
Traffic is predictable, or absorbed by headroomLoad varies enough to need autoscaling
You can restore from backup within your recovery targetLosing the host must not lose the service

Modern hardware is the reason this remains reasonable: a single machine with 64 cores and 256 GB is unremarkable, and it will run a workload that would have needed a rack a decade ago. The honest limit is not throughput — it is that the host is a single point of failure, and no amount of configuration on that host changes it. Everything below is about making the failure modes you can control behave well.

The intermediate step people skip

The gap between one host and an orchestrator is usually filled by two hosts and a load balancer — the same Compose files deployed to both, with the database on one and a replica on the other. That removes the single point of failure for the stateless tier at a fraction of the complexity of a cluster, and it is where most "we need Kubernetes" conversations should actually start (chapter 22 covers when they should not).

Deploying without downtime

The default has downtime. Here is what each alternative costs.

Deployment strategy timeline

Downtime, dropped requests, peak resources and rollback
strategy

what the default actually does
$ docker compose up -d
 ⠿ Container acme-api-1  Recreate      # stop the old one…
 ⠿ Container acme-api-1  Started       # …then start the new one. That gap is downtime.

# a blue-green switch behind a proxy, by hand
$ docker compose up -d --scale api=2 --no-recreate       # new alongside old
$ docker compose ps --format json | jq -r 'select(.Health=="healthy")'
$ docker compose stop --timeout 30 api-old               # drain and remove the old one
"Zero downtime" still drops requests if the drain is wrong

A proxy that switches instantly to a healthy new container gives zero downtime, and the old container is still holding in-flight requests when it is asked to stop. If its drain takes longer than the stop timeout, those requests are killed exactly as in chapter 9 — so the deploy reports success and a slice of users saw an error. The stop timeout must exceed the drain time, and the proxy must stop sending new requests before the drain begins. Both demos on this page are about the same lesson: the mechanism is only as good as its timings.

The reverse proxy

TLS, routing and the health-aware switch.

Caddy — automatic TLS in four lines
# Caddyfile
api.acme.com {
    reverse_proxy api:3000 {
        health_uri /healthz
        health_interval 5s
        lb_try_duration 5s
    }
}
and the service it fronts
services:
  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data          # the certificates live here — back this up
    networks: [edge]
    restart: unless-stopped

  api:
    image: ghcr.io/acme/api@sha256:41523187cf…
    networks: [edge, backend]
    expose: ["3000"]              # not published: only the proxy reaches it (ch. 12)
    stop_grace_period: 30s
    healthcheck:
      test: ["CMD", "/app/healthcheck"]
      interval: 5s
      start_period: 20s
    restart: unless-stopped

And the proxy's certificate volume is real state: losing it means re-issuing certificates, which rate limits will make slow at exactly the wrong moment.

Daemon upgrades and reboots

live-restore, and what it does not cover.

upgrading Docker without stopping containers
# with "live-restore": true, containers survive a daemon restart
$ sudo systemctl restart docker
$ docker ps                       # still running, uptime unbroken

$ docker events --since 5m --filter type=daemon
live-restore coversIt does not cover
A daemon restart or upgradeA host reboot — that is what restart policies are for
Containers keeping their processes and connectionsChanges to the daemon's bridge or address pools
Patch upgrades of the daemonSwarm mode, which is incompatible with it
—The window where the API is unavailable, so no deploys mid-restart

For a host reboot, the combination that works is restart: unless-stopped on every service plus the Docker service enabled at boot — containers then come back in dependency order as Compose recorded it. Verify it rather than assuming: a planned reboot is the cheapest possible test of your restart configuration, and far better than discovering it during an unplanned one.

# yes: the proxy's certificate volume, and your Compose files (in git)
# no:  images. They are reproducible from a digest and a registry (chapter 15)
# no:  container writable layers. If they hold anything you need, that is the bug
A tar of a running database directory may not restore

Copying data files while the engine is writing captures a torn state — some pages from before a checkpoint, some after — and the result can fail to start or, worse, start and be subtly corrupt. Use the database's own tool (pg_dump, mysqldump, mongodump), or stop the container first, or use a filesystem snapshot that is atomic. The model above prices this as a consistency risk because it is the difference between a backup and a file.

The short version

Chapter 20 in eight lines

  • One host is a legitimate production choice; its honest limit is being a single point of failure, not throughput.
  • The step people skip is two hosts and a load balancer, not a cluster.
  • Put /var/lib/docker on its own filesystem, set log rotation, and firewall via DOCKER-USER.
  • docker compose up -d stops before it starts — the default deploy has real downtime.
  • Blue-green behind a proxy removes the downtime and costs double the resources during the switch.
  • Zero downtime still drops requests unless the stop timeout exceeds the drain time.
  • live-restore survives a daemon restart; a host reboot needs restart policies instead.
  • Back up dumps and volumes, not images. An unrehearsed restore is not a backup.

Check yourself

Your deploy is git pull && docker compose up -d. Users report brief errors on every release. Why, and what is the smallest fix?

Compose recreates a changed service by stopping the old container and then starting the new one, so there is a gap covering the stop, the start and the time until the new process is actually serving — commonly ten to thirty seconds. The smallest real fix is a reverse proxy in front plus a blue-green switch: start the new container alongside, wait for its healthcheck, switch the proxy, then drain and stop the old one. That costs double the resources briefly and no downtime. Make sure the old container's stop timeout exceeds its drain time, or you have moved the errors rather than removed them.

You back up a Postgres volume nightly with tar while the container runs. Assess this.

It is a file, not necessarily a backup. Tarring a data directory under active writes captures a torn state — pages from either side of a checkpoint — so the archive may refuse to start or start and be quietly corrupt, which is worse. Use pg_dump, which produces a consistent snapshot by design, or stop the container first, or take an atomic filesystem snapshot. Then rehearse the restore: the failure mode here is discovering at recovery time that months of archives were never usable, and only a drill finds that.

Docker needs a security update. How do you apply it with the least disruption, and what still stops?

With "live-restore": true in daemon.json, systemctl restart docker upgrades the daemon while containers keep running — their processes and connections survive, because containerd and the container processes are not children of the daemon in the way that would kill them. What stops is the API: for the restart window you cannot deploy, exec or read logs, and any daemon-level networking change is not covered. A kernel update is different — that needs a reboot, which means restart policies plus a drain, and it is the case worth rehearsing.

Your recovery target is one hour. Daily backups of 200 GB, restored over a 50 MB/s link. Do you meet it?

No, on both numbers. Transferring the stored archive is roughly 40 minutes at that link speed, and once you add noticing the failure, provisioning, verifying and starting up, the total lands over an hour — so the recovery time misses even before anything goes wrong. And with daily backups the recovery point is up to 24 hours of data loss, which a one-hour target almost certainly does not permit either. Fix the two separately: cadence drives data loss (more frequent backups, or continuous archiving such as WAL shipping), and bandwidth plus volume drive downtime (keep a copy nearer the host, or restore incrementally). The model above separates them precisely because they need different fixes.
