Resource limits and the OOM killer

Chapter 2 showed the kernel mechanisms. This chapter is about using them without producing either a container that dies at 3am or a host that falls over because nothing was limited at all. Two things cause most of the confusion: memory accounting counts things you did not expect, and CPU shares do nothing at all most of the time.

Measure before you limit

A limit chosen from intuition is a scheduled outage.

# the peak, which is what actually matters for sizing
$ cat /sys/fs/cgroup/system.slice/docker-*.scope/memory.peak
ColumnRead it as
CPU %Percentage of one CPU, so 142% means 1.42 cores. It can exceed 100%
MEM USAGEmemory.current minus inactive file cache — not the raw cgroup figure
MEM %That figure against the limit; without a limit it is against host memory and meaningless

Size from the peak under realistic load, not the steady state. A service idling at 180 MB that reaches 430 MB during a batch import needs a limit above 430, and memory.peak is the honest number — docker stats samples, so it misses spikes shorter than its interval.

The limit counts more than your heap, and that is fine until you misread it.

Memory accounting explorer

What the kernel counts, what docker stats reports, and when the OOM killer fires

Why a container sits at 99% of its memory limit and is perfectly healthy

File cache counts toward memory.current and the kernel has no reason to evict it until the limit is reached — so a process that reads files will always drift up to the limit and stay there. That is the cache doing its job, not a leak. The number that predicts an OOM kill is the anonymous portion, which is what docker stats approximates by subtracting inactive file cache. Read memory.stat to separate them before concluding anything.

the fields that matter in memory.stat
$ CG=/sys/fs/cgroup/system.slice/docker-3f9c2a….scope
$ grep -E '^(anon|file|kernel|slab|sock|shmem|inactive_file|active_file) ' $CG/memory.stat
anon           314572800      # the heap. This is what can OOM you
file           188743680      # page cache. Reclaimable
inactive_file  132120576      # what docker stats subtracts
shmem            8388608      # tmpfs and /dev/shm. NOT reclaimable
$ cat $CG/memory.current $CG/memory.max $CG/memory.peak
$ cat $CG/memory.events            # low high max oom oom_kill counters

The --memory-swap table

The most confusing flag in Docker, because it is a total rather than an amount.

--memory--memory-swapSwap available
512munset512 MB — the default is twice the memory value in total
512m512mNone. Equal values disable swap — the usual production choice
512m1g512 MB (the total minus the memory limit)
512m-1Unlimited, up to what the host has
unsetanythingRejected — swap cannot be set without a memory limit

Swap turns a fast, obvious OOM kill into slow, mysterious latency, which is why most production setups disable it inside containers and let the process die honestly. Keep it if the workload has genuinely cold pages and you would rather be slow than dead.

--oom-kill-disable is almost never what you want

It does not give the container more memory; it makes the kernel pause the offending process instead of killing it when the limit is hit. The container then hangs forever — no logs, no exit, no restart, and the only cure is killing it from the host. Use it only with a memory limit set and a plan for who notices, which in practice means: do not.

nr_periods 5821  nr_throttled 1204  throttled_usec 18442000
Throttling is a latency problem, not a throughput problem

When a container exhausts its quota the scheduler stops every thread until the next 100 ms period begins. Average CPU usage looks fine and the host looks idle; what you see is a tail-latency cliff, because unlucky requests wait out the remainder of a period. If nr_throttled is climbing, raise the quota or reduce concurrency — and consider a shorter --cpu-period, which spreads the same allowance into smaller, more frequent slices.

Telling the application about its limits

Chapter 2's trap, with the specific fixes.

RuntimeSet thisBecause
GoGOMEMLIMIT=450MiB, GOMAXPROCSThe GC otherwise assumes host memory and collects too late; NumCPU ignores quota
JVM-XX:MaxRAMPercentage=75, -XX:ActiveProcessorCount=NContainer-aware since 8u191, but the default heap fraction is conservative and the CPU count still reads affinity
Node.js--max-old-space-size=384, UV_THREADPOOL_SIZEV8 sizes the heap from host memory; os.cpus() reports host CPUs
PythonExplicit worker countsos.cpu_count() is the host's
nginxworker_processes 2;auto means one per host CPU
Postgresshared_buffers, max_connectionsDefaults are tuned for a dedicated machine
the pattern: derive the app's limits from the container's
#!/bin/sh
# entrypoint.sh — read the cgroup and configure the runtime from it
LIMIT=$(cat /sys/fs/cgroup/memory.max 2>/dev/null || echo max)
if [ "$LIMIT" != "max" ]; then
  export GOMEMLIMIT=$(( LIMIT * 90 / 100 ))          # 90% of the hard limit
fi
QUOTA=$(cut -d' ' -f1 /sys/fs/cgroup/cpu.max)
PERIOD=$(cut -d' ' -f2 /sys/fs/cgroup/cpu.max)
[ "$QUOTA" != "max" ] && export GOMAXPROCS=$(( (QUOTA + PERIOD - 1) / PERIOD ))
exec "$@"

Leave headroom below the hard limit. A Go service with GOMEMLIMIT equal to --memory will still be OOM-killed, because the limit also counts stacks, the page cache and kernel memory that the GC does not manage. Ninety percent is a reasonable starting point, and the same reasoning applies to MaxRAMPercentage and --max-old-space-size.

The other limits

Three that are only noticed when they bite.

--shm-size64 MBChrome and Puppeteer crash; Postgres parallel workers fail

--ulimit nofileInherited from the daemon"Too many open files" under load at a suspiciously round number

setting them
$ docker run --shm-size 1g --pids-limit 512 \
    --ulimit nofile=65536:65536 \
    --device-write-bps /dev/sda:50mb app

The 64 MB /dev/shm default is the one worth remembering, because the failure it produces looks like anything but a memory limit — a headless browser exiting with a cryptic renderer crash, hours before anyone checks the shared-memory size. It also counts toward --memory, since tmpfs is memory.

Diagnosing an OOM kill

A short, ordered checklist.

was it the OOM killer, and whose?
# 1. confirm
$ docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' api
137 true

# 2. the cgroup's own counter — did it happen more than once?
$ cat /sys/fs/cgroup/…/memory.events
oom 3
oom_kill 3

# 3. the kernel's record, which names the process and the cgroup
$ dmesg -T | grep -i -A3 'killed process'

# 4. how close was it, historically?
$ cat /sys/fs/cgroup/…/memory.peak

# 5. watch for the next one
$ docker events --filter event=oom
FindingMeansDo
OOMKilled: trueThe container exceeded its own limitRaise the limit, or find why it grew
OOMKilled: false, exit 137A stop timed out (chapter 9), or something else sent SIGKILLCheck the stop timeout and the shutdown path
Kernel OOM naming a different cgroupThe host ran out; your container was collateralLimit everything, and stop overcommitting
anon rising steadily across restartsA genuine leakProfile the application; a bigger limit only delays it
anon flat, file at the limitNormal cache behaviourNothing
Unlimited containers are how a single bug takes down a host

Without --memory, a container can consume all host memory, and the kernel's OOM killer then picks a victim by score across the whole machine — frequently not the container at fault, and sometimes the database or the daemon. Setting a limit on everything converts "the host died" into "one container died and restarted", which is the entire point. The sum of limits may exceed host memory (overcommit is normal), but each individual limit must exist.

The short version

Chapter 10 in eight lines

  • Size limits from memory.peak under load, not from the steady state and not from intuition.
  • memory.current counts anonymous memory, file cache, kernel memory and tmpfs — so sitting near the limit is usually the cache working.
  • docker stats shows memory.current minus inactive file cache, so it and the cgroup file disagree on purpose.
  • The number that predicts an OOM kill is the anonymous portion, from memory.stat.
  • --memory-swap is a total, not an amount: equal to --memory means no swap; unset means an equal amount of swap.
  • --cpus is a ceiling that always applies; --cpu-shares is a weight that applies only under contention.
  • Throttling shows up as tail latency, not as high load — watch nr_throttled.
  • /dev/shm defaults to 64 MB and counts toward the memory limit.

Check yourself

docker stats shows 38% memory while memory.current is at 99% of the limit. Which is wrong?

Neither — they measure different things deliberately. memory.current includes file cache, and the kernel fills cache up to the limit because there is no reason not to; docker stats subtracts inactive file cache to approximate "memory that would be hard to reclaim". The container is healthy: 38% is anonymous plus active cache, and the remaining 61% is evictable. Confirm by reading anon and inactive_file in memory.stat. What would worry you is anon alone approaching the limit, or a rising oom_kill counter in memory.events.

A container has --cpu-shares 2048 and still runs slowly, on a host that is 90% idle. Explain.

Shares only take effect when the CPUs are contended — they divide contested time proportionally. On an idle host every container gets whatever it asks for, so doubling the weight changes nothing. If it is slow anyway, the cause is elsewhere: a --cpus quota (which applies regardless of contention), a --cpuset-cpus pinning it to two busy cores, single-threaded application code, or I/O rather than CPU. Check nr_throttled in cpu.stat first — if it is climbing, it is quota, not shares.

A Go service with --memory 512m and GOMEMLIMIT=512MiB is still OOM-killed. Why?

Because GOMEMLIMIT governs only the memory the Go runtime manages, while the cgroup limit counts everything: goroutine stacks beyond the heap, the page cache from files the process reads, socket buffers, and anything in /dev/shm. Setting them equal leaves the GC no reason to collect until the container is already at its hard limit. Set GOMEMLIMIT to roughly 90% of the container limit so the GC works harder before the kernel intervenes — and the same reasoning applies to MaxRAMPercentage and Node's --max-old-space-size.

A headless-Chrome container crashes under load with no useful error, well below its 2 GB memory limit. First thing to check?

--shm-size. Chrome puts renderer shared memory in /dev/shm, which Docker defaults to 64 MB regardless of the container's memory limit — so it exhausts a limit that has nothing to do with the one you set, and the renderer dies with a message that names neither. Raise it (--shm-size 1g) or run Chrome with --disable-dev-shm-usage so it uses /tmp instead. Note the raised /dev/shm is tmpfs and therefore counts toward --memory, so budget for both.
