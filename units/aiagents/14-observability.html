Tracing and debugging a run

When an agent does something inexplicable, you have one artefact to work from. If it does not contain the literal prompt, the exact arguments and the raw observations, you are guessing — and guessing about a non-deterministic system is not debugging.

spans what to capture replay sampling workflow

The questions a trace must answer

Design the trace backwards from the questions you will ask it at 3am. There are seven, and if any of them requires opening a database by hand, the trace is incomplete.

QuestionNeeds
What did the model actually see at step 7?The literal message array sent, not the template
Why did it pick that tool?The reasoning text, and the tool set that was available at that moment
What did the tool really return?The raw result, plus the truncated version the model received — both
Where did the time go?Per-span duration, split into model, tool and framework overhead
What did this cost?Tokens in and out per call, cached tokens, cost, running total
Did a guard fire?Guard events as spans, with which detector and why
What changed in the world?Every write, with its idempotency key and result
Store the rendered prompt, not the ingredients

Almost every framework logs the template and the variables. That is not the same thing, and the difference is exactly where the bugs live: a variable that rendered as None, a list that serialised to [object Object], a truncation that cut mid-JSON, a system prompt that a mid-run edit invalidated. Store the exact string. It is large, so sample it — but never lose it on the runs that failed.

Span structure

An agent run is a tree, and mapping it onto ordinary distributed-tracing spans means your agent shows up next to your HTTP and database spans rather than in a separate tool.

agent.runThe whole task. Holds goal, budget, final status, totals
↓
agent.stepOne iteration. Parent for the model call and any tool calls it triggered
↓
llm.call · tool.execute · guard.fire · subagent.runThe leaves, each with its own attributes
tracing.py — OpenTelemetry spans with agent attributes
from opentelemetry import trace
tracer = trace.get_tracer("agents")

def run_agent(goal, ctx, tools, budget):
    with tracer.start_as_current_span("agent.run") as run_span:
        run_span.set_attributes({
            "agent.name":          ctx.agent_name,
            "agent.version":       ctx.agent_version,      # prompt + tool set version
            "agent.model":         ctx.model_id,           # pinned, exact
            "agent.goal":          redact(goal),
            "agent.tools":         ",".join(sorted(tools)),
            "agent.budget.steps":  budget.max_steps,
            "agent.budget.usd":    budget.max_cost_usd,
            "session.id":          ctx.session_id,
            "user.id_hash":        ctx.user_id_hash,       # hashed, never raw
            "tenant.id":           str(ctx.tenant_id),
            "deploy.release":      RELEASE,
        })

        for n in range(1, budget.max_steps + 1):
            with tracer.start_as_current_span("agent.step") as step_span:
                step_span.set_attribute("agent.step.n", n)

                with tracer.start_as_current_span("llm.call") as llm_span:
                    reply = model.complete(messages, tools=schemas)
                    llm_span.set_attributes({
                        "llm.model":            ctx.model_id,
                        "llm.tokens.in":        reply.usage.input_tokens,
                        "llm.tokens.out":       reply.usage.output_tokens,
                        "llm.tokens.cached":    reply.usage.cached_tokens,
                        "llm.cost_usd":         reply.cost_usd,
                        "llm.finish_reason":    reply.finish_reason,
                        "llm.tool_calls":       len(reply.tool_calls),
                        "llm.reasoning":        reply.text[:2000],
                        # The big ones go to blob storage, keyed by span id.
                        "llm.prompt_ref":       blobs.put(run_span, n, messages),
                    })

                for call in reply.tool_calls:
                    with tracer.start_as_current_span("tool.execute") as t:
                        t.set_attributes({
                            "tool.name":        call.name,
                            "tool.args":        redact_json(call.arguments),
                            "tool.consequence": tools[call.name].consequence,
                        })
                        out = execute(call, ctx, tools, steps)
                        t.set_attributes({
                            "tool.ok":            out.ok,
                            "tool.result_ref":    blobs.put_result(t, out.raw),
                            "tool.observation":   out.observation[:1000],
                            "tool.truncated":     out.truncated,
                            "tool.idempotency":   out.key,
                        })
                        if not out.ok:
                            t.set_status(trace.StatusCode.ERROR, out.observation[:200])
Attributes for querying, blobs for reading

Trace backends index attributes and choke on 40KB strings. Put the small, queryable facts on the span — tool name, tokens, cost, ok — and push prompts and raw results into object storage with a reference. You can then ask "show me every run where list_payments returned ok=false and cost exceeded £0.20" in a query, and only pull the heavy content for the handful you open.

The debugging workflow

Diagnose from a trace A real-shaped run that went wrong. Work down it — the answer is visible in the numbers before you read any prose.
1 · Find the runTrace id from the response, or query by user, time and status
↓
2 · Read the shape before the contentStep count, durations, costs, which spans errored. The anomaly is usually visible here
↓
3 · Open the step where it went wrongNot step 1. Find the first step whose reasoning stops making sense
↓
4 · Read the literal prompt for that stepHalf of all investigations end here
↓
5 · Compare the raw result with the observationTruncation, shaping and error-formatting bugs live in this gap
↓
6 · Replay with a changeSame inputs, one difference. Confirm the fix before shipping it
↓
7 · Add it to the eval suiteWith fixtures reproducing the world state (chapter 13)

Replay

A trace that can be replayed turns debugging from archaeology into experiment. The recorded observations become a scripted environment, so you can change one thing and see what the model does differently — deterministically, offline, for the price of the model calls.

replay.py — the trace becomes the test fixture
class RecordedTools:
    """Replays observations from a trace. Unknown calls are surfaced, not faked."""
    def __init__(self, trace: Trace, strict: bool = True):
        self.by_sig = {(s.tool, s.arg_sig): s.raw_result
                       for s in trace.tool_spans()}
        self.strict = strict
        self.novel: list[tuple[str, dict]] = []

    def execute(self, call, ctx, tools, steps):
        key = (call.name, sig(call.name, call.arguments))
        if key in self.by_sig:
            return Outcome(render(self.by_sig[key]), True, {})
        self.novel.append((call.name, call.arguments))
        if self.strict:
            # The model diverged. That is the finding, not an error to paper over.
            raise Diverged(call.name, call.arguments)
        return Outcome(f"[not recorded: {call.name}]", False, {})


def replay(trace_id: str, **changes) -> Run:
    trace = traces.load(trace_id)
    cfg = trace.config.with_changes(**changes)      # prompt version, model, tool set…
    return run_agent(trace.goal,
                     ctx=trace.ctx.with_tools(RecordedTools(trace)),
                     tools=tools_for(cfg), budget=trace.budget)

# Uses that pay for themselves:
#   replay(id)                              -> is it deterministic?
#   replay(id, model="next-version")        -> does the upgrade change behaviour?
#   replay(id, prompt_version="v9")         -> did my fix work on the real case?
#   replay(id, tools=narrowed)              -> was the tool set the problem?
#
# Divergence is informative: the point where the model asks for something the
# original run never called is usually the point your change took effect.

Sampling and redaction

ContentRetainNote
Span attributes (all runs)100%, 30–90 daysSmall and queryable. This is your metrics substrate
Prompts and raw results — failed runs100%, 30 daysNever sample away a failure. These are what you actually open
Prompts and raw results — unsafe attempts or guard fires100%, 90 daysSecurity-relevant; longer retention
Prompts and raw results — successes1–5%, 7 daysEnough to spot drift and build fixtures. Cheap to keep small
Runs flagged by a user100%, until resolvedLink the trace id to the feedback record
Traces are the biggest accidental PII store you will build

Tool observations contain customer records in full. Prompts contain the user's own words. Arguments contain email addresses and order references. Redact before writing, not on read — a redaction applied at display time still leaves the raw data in storage and in every backup. Hash user identifiers, drop or tokenise structured identifiers, and set retention deliberately per category rather than accepting a default. Then check what you actually stored, by reading some.

The silent regressions are distributional

None of the failures that matter most throw an exception. Average step count creeping from 4 to 6, cached-token ratio quietly falling after a prompt edit, one tool's error rate rising from 0.2% to 3% — all invisible in an error dashboard, all expensive. Alert on the shape of these distributions, and re-baseline deliberately after every model or prompt change so you notice when the new normal is worse than the old one.

The short version

  1. Design the trace backwards from the seven questions you will ask it during an incident.
  2. Store the rendered prompt, not the template and variables. That gap is where the bugs live.
  3. Model the run as agent.run → agent.step → llm.call / tool.execute / guard.fire, in your existing tracing system.
  4. Attributes for querying, blobs for reading. Keep spans small and indexable; push heavy content to object storage.
  5. Debug by shape before content: durations, costs and error spans usually locate the problem before you read any prose.
  6. Replay turns a trace into a fixture. Change one variable, rerun offline, and treat divergence as the finding.
  7. Sample successes, never sample away failures, and redact before writing rather than on read.
  8. The regressions that hurt are distributional, not exceptional. Alert on shape and re-baseline after every change.
