What an agent actually is

The word has been stretched to cover everything from a chatbot with a search box to a fleet of processes rewriting a codebase overnight. One distinction survives all that marketing and is the only one worth building around: who decides what happens next.

autonomy control flow use cases step reliability when not to

The definition that does work

In ordinary software you write the control flow. The program does what you wrote, in the order you wrote it. In an agent, a model chooses the next action at runtime, repeatedly, and decides when to stop. Your code executes those choices and enforces limits on them.

That is the whole distinction, and everything difficult follows from it. You have given up determinism in exchange for handling tasks whose steps you could not enumerate in advance. Whether that trade is worth making is the subject of this chapter.

The autonomy spectrum

Most production systems marketed as agents are level 3. That is not a criticism — level 3 is reliable, fast, cheap and testable, and it covers a great deal of useful work.
Move up a level only when forced

Each level buys flexibility and costs determinism, latency, money and debuggability. The right question is never "could this be an agent?" — nearly anything could. It is: can I enumerate the steps in advance? If yes, write them. A chain that handles 90% of cases in two predictable calls beats an agent that handles 95% in an unpredictable number of them, because you can test the chain, price it, and explain it when it goes wrong.

The arithmetic nobody puts on the slide

Agents fail in a way that is easy to state and easy to forget. If each step succeeds with probability p, and the task needs n sequential steps that each depend on the last, the run succeeds with probability pn. Ninety-five per cent per step sounds excellent. Over twelve steps it is 54%.

Two things move that number, and neither is "use a better model". The first is recoverability: if a failed step returns an error the model can read and act on, many failures cost a step rather than the run. The second is verifiable checkpoints: if the agent can run the tests, re-read the file it just wrote, or check that the record it created exists, errors are caught near where they happened instead of propagating.

This is why coding agents work better than most

A coding agent has a compiler, a type checker and a test suite. Every step produces a signal that is objectively right or wrong, immediately, for free. Agents in domains without that — writing a strategy document, triaging a nuanced complaint — have no such ground truth, and their per-step errors accumulate silently. Before building an agent, ask what its compiler is. If there is no answer, expect to supply verification yourself or to keep the loop very short.

And where they do not

Symptoms you built the wrong thing

  • The trace is the same five tools in the same order, every run — that is a chain
  • You added an agent so the model could "decide" between two options — that is a router
  • Latency went from 2s to 40s and quality is unchanged
  • You cannot write down what "done" means
  • Every run needs a human to check it anyway

Symptoms it was the right call

  • Step count varies genuinely between runs
  • Traces show the agent changing approach after an observation
  • It solves cases your previous fixed flow could not express
  • There is an objective check it can run
  • The alternative was a human doing lookups for ten minutes

A worked example, to fix the idea

One task, four ways to build it. The task: a customer writes in saying they were charged twice.

four designs for the same problem
# Level 0 - single call. Cheap, instant, and often enough.
label = classify(ticket)                       # -> "billing.duplicate_charge"
route_to_queue(label)

# Level 1 - chain. Still fully predictable.
label   = classify(ticket)
order   = orders.find(extract_order_ref(ticket))
draft   = compose_reply(ticket, label, order)
queue_for_agent_review(draft)

# Level 3 - tool-augmented single turn. The model picks the lookups it needs,
# once, and then answers. Bounded: one round of tool calls, no loop.
resp = model.complete(ticket, tools=[find_order, list_payments])
draft = resp.text

# Level 4 - agent loop. Needed only if the investigation genuinely branches:
# no order reference in the message, so search by email; two accounts match, so
# disambiguate by postcode; payments look fine, so check the refund ledger; and
# so on. You cannot write this sequence in advance because it depends on data.
result = run_agent(goal=ticket, tools=SUPPORT_TOOLS, budget=Budget(max_steps=10))

Most teams should ship the level-3 version and see how far it gets. Its trace tells you exactly which cases it could not close, and those cases are the specification for the level-4 version — if you still need one.

The demo-to-production gap is wider here than anywhere else

Agents demo extraordinarily well. The happy path is genuinely impressive and takes an afternoon. The gap to production is not incremental polish; it is the twelve chapters after this one — permissioning, budgets, context management, failure detection, evaluation, tracing. Plan for that gap explicitly, because stakeholders who saw the demo will not have. A useful framing when asked for a date: the demo is roughly 10% of the work, and the remaining 90% is entirely about the cases the demo did not show.

What to hold on to

  • Agency is a cost, not a feature. Justify each level you climb.
  • Per-step reliability compounds. Shorten the loop before improving the model.
  • Find the verifier. An agent that can check its own work is a different class of system from one that cannot.
  • Start read-only. An agent that investigates and proposes is useful and nearly harmless. Chapter 15 is about what changes when it can act.
  • Build the level-3 version first. Its failures are the requirements document for the level-4 version.

The short version

  1. An agent is a system where the model chooses the next action at runtime and decides when to stop. Everything else follows from that.
  2. There is a spectrum from single call to open loop. Most production "agents" are level 3 — tool-augmented single turns — and that is fine.
  3. Success compounds downward: 95% per step is 54% over twelve steps.
  4. Recoverable errors and verifiable checkpoints are what rescue that arithmetic — not a bigger model.
  5. Ask what the agent's compiler is. Coding agents work well because they have one.
  6. Agents earn their place when the next step genuinely depends on the last result. Otherwise you have written a chain with extra latency.
  7. The demo is about 10% of the work. Say so early.
