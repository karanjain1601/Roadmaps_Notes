Chapter 07 · Context and memory

Context engineering

At step one the model sees a clean prompt and a question. At step nine it sees that plus eight rounds of tool output, most of which no longer matters. Managing what occupies that window is the difference between an agent that gets sharper as it learns and one that gets vaguer as it fills.

What is in there

Five components, with very different growth behaviour. Knowing which is which tells you where to intervene.

Why bigger windows did not solve this

A million-token window removes the hard failure — the run no longer crashes at step fourteen. It does not remove the soft one. Three things degrade well before you hit the limit:

Attention dilutes
The rule you wrote in the system prompt now competes with 40,000 tokens of tool output for the model's attention. Instruction adherence measurably falls with context depth, and it falls fastest for constraints stated once, early.
Stale facts persist
Step three found a draft record; step nine updated it. Both are in the context, both look equally authoritative, and nothing marks the first as superseded.
Cost and latency scale with it
Prefill time and price grow with every token you carry. A 200k-token context on step twenty of a run you resend each step is expensive in both.
Treat the window as a working set, not a log

The instinct is to preserve everything in case the model needs it. The better instinct is the opposite: the context should hold what is needed to decide the next action, and nothing else. Everything else belongs in storage the agent can query. A tidy 12,000-token context beats a complete 90,000-token one on accuracy, latency and cost simultaneously — which is a rare combination and worth exploiting.

Truncating observations

The first and cheapest intervention. Most tool results contain far more than the next decision requires.

truncate.py — cut with a marker, never silently
def truncate(text: str, max_tokens: int, hint: str | None = None) -> str:
    n = count_tokens(text)
    if n <= max_tokens:
        return text

    # Keep the head and a little of the tail: structure lives at the start,
    # totals and conclusions often at the end.
    head = take_tokens(text, int(max_tokens * 0.8))
    tail = take_tokens_from_end(text, int(max_tokens * 0.15))
    return (f"{head}\n\n…[truncated: {n:,} tokens, showing first {int(max_tokens*0.8):,} "
            f"and last {int(max_tokens*0.15):,}"
            + (f". {hint}" if hint else "") + "]\n\n" + tail)


# Row-oriented results deserve a better cut than character truncation.
def truncate_rows(rows: list[dict], max_rows: int, total: int, hint: str) -> str:
    shown = rows[:max_rows]
    body = "\n".join(compact_row(r) for r in shown)
    if total > max_rows:
        body += f"\n…[{total:,} rows total, {max_rows} shown. {hint}]"
    return body

# Used as:
truncate_rows(orders, 20, 147, "Narrow with since= or status= to see the rest.")

Compaction

When truncation is not enough, replace old detail with a summary. The critical design decision is what the summary must never lose.

compact.py — summarise the middle, preserve the ends
COMPACT_AT = 0.70          # fraction of the working budget

COMPACT_PROMPT = """Summarise this portion of an in-progress investigation so it
can replace the original messages. You are writing for yourself, to continue the
work with less context.

Preserve exactly and completely:
- Every concrete fact established, with its identifiers, figures and dates
- Every tool call made and what it returned, in one line each
- Anything that failed, and why — so it is not retried
- Open questions and what was about to be tried next

Discard: reasoning that led nowhere, restatements, formatting, pleasantries.
Never invent, round, or generalise a specific value. Under 400 words."""

def maybe_compact(messages: list[dict], budget: Budget) -> list[dict]:
    used = count_messages(messages)
    if used < budget.max_tokens * COMPACT_AT:
        return messages

    head = messages[:2]                      # system + goal: never touch
    tail = messages[-6:]                     # recent steps: keep verbatim
    middle = messages[2:-6]
    if not middle:
        return messages

    # Do not split a tool call from its result, or the next request is invalid.
    middle, tail = realign_tool_pairs(middle, tail)

    summary = model.complete(
        [{"role": "user", "content": COMPACT_PROMPT + "\n\n" + render(middle)}],
        tools=None, max_tokens=600, temperature=0).text

    log.info("compacted", run=budget.run_id, from_tokens=used,
             replaced_messages=len(middle))

    return head + [{"role": "assistant",
                    "content": f"[Earlier steps, compacted]\n{summary}"}] + tail
Compaction destroys your prompt cache

Rewriting the middle of the array changes the prefix, so every cached token after that point is invalidated and the next call pays full price. That is usually still worth it — you are trading one expensive step for many cheaper ones — but it means compaction should happen rarely and decisively, not incrementally every step. Compact once at 70% rather than trimming continuously, and expect a visible cost spike on that step.

Realign tool pairs or the next call fails

If your slice leaves an assistant message containing tool calls in the summarised region while its matching tool results are in the kept region — or vice versa — the provider rejects the request. This is the single most common bug in home-grown compaction, and it appears only on long runs, which means it appears in production. Slice on step boundaries, never on message indices.

Externalising state

The strongest technique, and the least used. Instead of carrying findings in the conversation, have the agent write them somewhere and carry only a reference.

a scratchpad turns context pressure into a storage problem
NOTES = {
  "name": "record_finding",
  "description": ("Record an established fact so you do not need to keep it in mind. "
                  "Use after any tool call that produced something you will need later. "
                  "Findings persist for the whole task and are shown to you in summary. "
                  "Retrieve full detail with read_finding(key)."),
  "input_schema": {"type":"object","required":["key","fact"],"properties":{
      "key":  {"type":"string","pattern":"^[a-z0-9_]{3,40}$"},
      "fact": {"type":"string","maxLength":500},
      "source": {"type":"string","description":"Which tool call established this"}}}
}

# The system prompt then carries a compact index that is rebuilt each step:
#
#   Findings so far:
#   - duplicate_captures: two £48 captures on NW-8842, 10:14 and 10:16 (list_payments)
#   - policy_threshold: refunds over £25 need agent approval (search_policy)
#   - customer_id: c_991 (find_orders)
#
# Three lines instead of three full tool observations. The agent can read any of
# them back in full if it needs to, and the working set stays small.

This is what long-running coding agents do with files: the repository is the memory, and the context holds only the current working set plus a map. It generalises well beyond code — a findings table, a scratch document, a task list the agent maintains.

Ordering within the window

Position matters, and you control it. Three rules, in tension, resolved in this order:

1 · Stable first, for cachingSystem prompt, then tool schemas. Byte-identical across every step of the run
↓
2 · Goal early and restated lateModels drift from the objective on long runs. A one-line restatement in the last user turn is cheap insurance
↓
3 · Most recent observations lastNatural ordering, and the end of the context is where attention is strongest
restating the objective without breaking the cache
# WRONG: editing the system prompt invalidates the cache for the rest of the run.
messages[0]["content"] = SYSTEM + f"\n\nREMINDER: the goal is {goal}"

# RIGHT: append at the end, where nothing downstream is cached anyway.
if step > 6 and step % 4 == 0:
    messages.append({"role": "user", "content":
        f"Reminder — the objective is: {goal}. "
        f"You have {budget.max_steps - step} steps left. "
        f"If you cannot complete it, say what you established and stop."})

# Note this also arrives at the position the model attends to most strongly,
# which is why it works better than the version that feels more correct.

Not the summary, not the trace view — the literal string that went to the model on a real long run. It is a striking exercise. You will find a 3,000-token HTML dump nobody needed, the same customer record fetched three times, a tool schema for something that was never going to be called, and a critical constraint buried 40,000 tokens from the decision it was meant to govern. Every one of those is a fix you can make this afternoon, and together they usually matter more than any architectural change.

The short version

  1. Five components; only observations grow without bound. Almost all context work is observation work.
  2. Big windows removed the crash, not the decay: attention dilutes, stale facts persist, cost scales.
  3. Treat the window as a working set, not a log. Tidy and small beats complete and large on accuracy, latency and cost at once.
  4. Cap every tool result, and truncate with a marker that says how much is missing and how to get it.
  5. Compact rarely and decisively at a threshold — it resets your prompt cache, so incremental trimming is the wrong shape.
  6. Realign tool pairs when slicing, or long runs fail with a confusing provider error.
  7. Externalising findings to a scratchpad is the most scalable technique and the least used.
  8. Restate the objective in a late turn, never by editing the system prompt.
