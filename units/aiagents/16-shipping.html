Shipping an agent

Agents break the assumptions your web stack was built on: requests that run for minutes, work that must survive a deploy, costs that vary by an order of magnitude between two users on the same plan. This chapter is the operational shape that accommodates that.

Pick queued earlier than feels necessary

The migration from "hold the connection open" to "durable job with progress" is disruptive: it changes the API shape, the client, the error handling and the tests. Doing it before launch costs a couple of days. Doing it after, because a customer's run reliably takes ninety seconds and your gateway caps at sixty, costs a sprint and an incident. If there is any realistic path to runs exceeding thirty seconds, start queued.

api.py — the shape that scales in both directions
@app.post("/runs")
async def create_run(req: RunRequest, ctx: RequestContext = Depends(session)):
    if not quota.allow(ctx.user_id, ctx.tenant_id):
        raise HTTPException(429, "daily agent quota reached")

    run_id = uuid7()
    await runs.create(run_id, goal=req.goal, status="queued",
                      authority=ctx.authority.restrict(tools=toolset_for(req.kind)),
                      budget=budget_for(ctx.plan, req.kind))
    await queue.enqueue("agent.run", run_id=run_id)
    return {"run_id": run_id, "status": "queued",
            "events": f"/runs/{run_id}/events"}


@app.get("/runs/{run_id}/events")
async def events(run_id: str, ctx = Depends(session)):
    run = await runs.get(run_id)
    authorise_read(run, ctx)                       # never trust the id alone

    async def gen():
        # Replay anything that already happened, so a reconnect is seamless.
        for e in await runs.events_since(run_id, 0):
            yield sse(e)
        async for e in runs.subscribe(run_id):
            yield sse(e)
            if e.kind in ("done", "error", "cancelled"):
                return

    return StreamingResponse(gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache, no-transform",
                 "X-Accel-Buffering": "no"})       # or nginx buffers it away


@app.post("/runs/{run_id}/cancel")
async def cancel(run_id: str, ctx = Depends(session)):
    await runs.request_cancel(run_id)              # the worker checks this each step
    return {"status": "cancelling"}

Replaying stored events before subscribing is the small detail that makes reconnection work. A user switching networks, closing a laptop lid, or refreshing gets the whole run so far and then continues live — rather than a blank screen for work that is already half done.

Interruption and resumption

worker.py — cancellable, resumable, deploy-safe
async def worker(run_id: str):
    run = await runs.get(run_id)
    state = run.state or initial_state(run)          # resume mid-run if state exists

    for n in range(state.step, run.budget.max_steps + 1):
        if await runs.cancel_requested(run_id):
            await runs.finish(run_id, status="cancelled",
                              text=wrap_up(state.messages, "cancelled by user"))
            return
        if shutting_down.is_set():                   # SIGTERM during a deploy
            await runs.checkpoint(run_id, state)     # persist and requeue
            await queue.enqueue("agent.run", run_id=run_id, delay=5)
            return

        result = await do_step(state, run)
        state = result.state
        await runs.checkpoint(run_id, state)         # after every step, not at the end
        await runs.emit(run_id, result.event)

        if result.awaiting_approval:
            await runs.pause(run_id, pending=result.pending)
            return                                   # resumed by the approval webhook
        if result.done:
            await runs.finish(run_id, status="completed", text=result.text)
            return

    await runs.finish(run_id, status="halted",
                      text=wrap_up(state.messages, "step limit"))
  • Checkpoint after every step, not at the end. A step is the natural transaction boundary and losing one is cheap.
  • Handle SIGTERM. Deploys happen mid-run. Persist, requeue, exit — do not fight the shutdown.
  • Cancel must reach the model call. Pass a cancellation token into the provider client so an in-flight request aborts and stops billing.
  • Version the state. A checkpoint written by yesterday's code will be resumed by today's; either migrate it or fail it cleanly with a clear message.
  • Expire paused runs. A run waiting on an approval nobody gives should time out, notify, and release its budget.
  • Make resumption idempotent. A requeued job must not re-execute the write that was already committed (chapter 5).

Budgets and quotas

Agent cost per user varies far more than in a single-call product. One user asking hard questions can cost more than a thousand asking easy ones, and the difference does not show up in your plan tiers unless you put it there.

budget_for — derive limits from the plan and the task
def budget_for(plan: Plan, kind: str) -> Budget:
    base = TASK_BUDGETS[kind]              # a quick lookup differs from a deep investigation
    return Budget(
        max_steps   = min(base.steps, plan.max_steps),
        max_tokens  = min(base.tokens, plan.max_tokens),
        max_seconds = base.seconds,
        max_cost_usd= min(base.cost, plan.remaining_today()),
    )

Rolling it out

1 · ShadowRun on real traffic, serve nothing. Compare trajectories and cost against the human or the old path
↓
2 · InternalYour own support team uses it. They will find things no eval set contains
↓
3 · AssistedAgent drafts and proposes; a human approves everything. Measure approval and edit rates
↓
4 · Narrow autonomyAuto-approve the safest class of action below a low threshold. Watch the reversal rate
↓
5 · Widen deliberatelyOne action class or one threshold at a time, with a week of data between changes

Stage three is the one to linger in. Approval rate tells you whether the agent is right; edit rate tells you whether it is useful. An agent whose drafts are approved 95% of the time but edited heavily is doing the easy half of the job — and the traces of those edits are the best specification you will get for what to fix next.

The kill switch must be tested in production

Feature-flag the agent so it can be disabled — entirely, or just its write tools — without a deploy. Then actually flip it in production, during business hours, and check three things: runs in flight terminate gracefully with a useful message, the non-agent path still works, and nothing 500s. An untested kill switch is a comforting name for code that has never run, and you will discover which it is at the worst possible moment.

Before launch

Correctness

  • Eval suite passing against a baseline
  • Adversarial slice at 100%, zero unsafe attempts
  • Unanswerable tasks refused cleanly
  • Degraded-tool tasks report the gap

Control

  • All four budgets enforced per run
  • Per-user quota and a global breaker
  • Guards wired with metrics on each
  • Kill switch flipped in production once

Safety

  • Authority scoped to the session, narrowing only
  • Consequential actions gated
  • Egress allowlisted, output sanitised
  • Trifecta reviewed across the whole session

Operations

  • Tracing on, sampled, redacted before write
  • Cost attributed by tenant and task kind
  • Alerts on distributions, not just errors
  • Runbook written and findable

Where this unit ends

Sixteen chapters ago the claim was that an agent is a loop that fits in forty lines. That is still true, and it is still the least interesting part. What the rest of the unit added is the machinery that makes those forty lines safe to leave running: tools described well enough to be chosen correctly, execution gates that hold when the prompt does not, a context that stays a working set, detectors for the dozen ways runs go wrong, evaluation that distinguishes a good run from a lucky one, traces that answer the question at 3am, and an authority model that can only shrink.

None of that is specific to any model generation. The models will get better at picking tools and knowing when to stop, and several specifics here will date. The reason the machinery still matters is that it does not derive from the model's weaknesses — it derives from the fact that you have wired a probabilistic component to real systems, and that arrangement needs the same guarantees whether the component is right 80% of the time or 99%.

The useful next step is not more reading. Take the loop from chapter 2, give it three tools and a read-only credential, put twenty golden tasks behind it, and point it at something real. The failures you get in the first week will make every chapter here concrete in a way this text cannot.

The short version

  1. Choose queued earlier than feels necessary. Migrating from a held-open connection after launch costs a sprint.
  2. Replay stored events before subscribing so reconnection is seamless.
  3. Emit a labelled event within a second, in domain language, never raw arguments.
  4. Checkpoint after every step, handle SIGTERM, version the state, keep resumption idempotent.
  5. Cancel must reach the model call and stop billing — not just close the tab.
  6. Budget at four levels: per run, per user, per tenant, globally. Alert on rate of change.
  7. Roll out through shadow → internal → assisted → narrow autonomy, and linger at assisted: edit rate is the honest signal.
  8. Flip the kill switch in production once, before you need it.
