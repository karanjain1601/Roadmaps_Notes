How agents fail

Agents fail in a small number of recognisable ways, over and over, across every domain. Each has a cheap mechanical detector and a known recovery. Building those in from the start is the difference between a system you can operate and one that produces incident reports.

Detect in code, recover through the model

The pattern that works throughout this chapter: your code notices the failure deterministically, then injects an observation telling the model what happened and what to do differently. Detection must not be the model's job — it is inside the failure. Recovery usually should be the model's job, because it has the context to choose a different approach. Halting is the fallback when recovery does not take.

The guard function

One place, called before every tool execution, holding every cheap detector. This is guard() from chapters 2 and 5, written out.

guards.py — mechanical detection, model-side recovery
import json, hashlib
from collections import Counter

def sig(name: str, args) -> str:
    return name + ":" + hashlib.sha1(
        json.dumps(args, sort_keys=True, default=str).encode()).hexdigest()[:12]

def guard(call, args, ctx, steps: list[Step]) -> str | None:
    """Return an observation to short-circuit with, or None to proceed."""
    history = [(s.tool, s.arg_sig) for s in steps if s.tool]
    this = (call.name, sig(call.name, args.model_dump()))

    # 1. Exact repeat — the same call with the same arguments.
    if history.count(this) >= 2:
        return ("You have already called this twice with these exact arguments and "
                "received the same result both times. It will not change. Either try "
                "a different tool or different arguments, or stop and report what you "
                "have established and what is blocking you.")

    # 2. Oscillation — A, B, A, B with no new information.
    recent = [t for t, _ in history[-4:]]
    if len(recent) == 4 and recent[0] == recent[2] and recent[1] == recent[3] \
       and recent[0] != recent[1]:
        return (f"You are alternating between {recent[0]} and {recent[1]} without making "
                f"progress. Neither is answering the question. Summarise what you know "
                f"and state what information you are missing.")

    # 3. Per-tool call cap within one run.
    used = sum(1 for t, _ in history if t == call.name)
    if used >= ctx.limits.per_tool.get(call.name, 8):
        return (f"You have used {call.name} {used} times in this run, which is the limit. "
                f"Work with what you already have.")

    # 4. Fabricated references — the identifier was never seen.
    for field, kind in TOOL_REFS.get(call.name, {}).items():
        ref = getattr(args, field, None)
        if ref and not seen_reference(steps, ctx, kind, ref):
            return (f"The {kind} reference '{ref}' has not appeared in any tool result "
                    f"in this conversation and was not provided by the user. Do not "
                    f"guess identifiers — look it up first with {LOOKUP_TOOL[kind]}.")

    # 5. Cost trajectory — projected overrun, caught early rather than at the wall.
    if steps and ctx.budget.projected_cost(len(steps)) > ctx.budget.max_cost_usd:
        return ("This run is on track to exceed its cost budget. Stop exploring and "
                "produce the best answer you can from what you already have.")

    return None

Detector four is worth dwelling on. Checking that every identifier the model passes has actually appeared in a previous observation or in the user's message catches fabrication before it reaches a database — and it converts a whole class of confident-wrong-answer bugs into a single recoverable step.

Premature success

The most damaging failure, because it looks like a completed run. The agent did something plausible, decided that was the task, and returned a fluent answer. Nothing in the trace is obviously wrong.

completion.py — check the claim before returning it
class Completion(BaseModel):
    criterion_met: bool
    evidence: list[str] = Field(description="Specific tool results supporting this")
    unmet: list[str] = Field(description="Parts of the request not addressed")

CHECK = """The agent claims this task is complete. Decide whether it is, using only
the tool results in the transcript.

{goal}
{criterion}
{steps}
{answer}

For each part of the original request, was it actually addressed by a tool result —
not merely asserted in the answer? List anything unaddressed."""

def verify_completion(run: Run, goal: str, criterion: str) -> Run:
    v = structured_call(Completion, CHECK.format(...), temperature=0)
    if v.criterion_met:
        return run

    metrics.incr("agent.premature_completion")
    if run.budget.remaining_steps() >= 2:
        return continue_run(run, nudge=(
            f"Before finishing: these parts of the request are not yet addressed by "
            f"any tool result: {'; '.join(v.unmet)}. Handle them or explain why you "
            f"cannot."))

    return run.with_caveat(f"Incomplete: {'; '.join(v.unmet)}")

# The cheaper version, where you can write it: a deterministic check.
#   "a refund proposal exists for this order"  ->  db query, no model needed
# Always prefer the deterministic check. Use the judge only where you cannot.

Silent partial failure

aggregate statuses in code, never in a prompt
# WRONG: hoping the summary mentions it.
system += "If any sub-task failed, say so in your answer."

# RIGHT: the caller owns the truth about what happened.
results = await asyncio.gather(*workers, return_exceptions=True)

succeeded = [r for r in results if not isinstance(r, Exception) and r.status == "completed"]
failed    = [(s, r) for s, r in zip(sources, results)
             if isinstance(r, Exception) or r.status != "completed"]

answer = compose(succeeded)
if failed:
    answer.caveat = (f"{len(failed)} of {len(results)} sources could not be checked: "
                     + ", ".join(s for s, _ in failed) + ".")
    answer.confidence = "partial"

# The caveat is attached by your code to the response object. It appears in the
# UI whether or not the model mentioned it, and it is queryable in your metrics.
Never let the model be the only reporter of its own failures

A model summarising a run it partly failed will produce a fluent, complete-sounding answer far more often than it will volunteer the gap. This is not deception — the failed branches are just less salient than the successful ones in a long context. Any status that matters must be computed by your code from what actually happened and attached to the response independently.

Goal drift and sycophancy

Drift

By step twelve the objective is buried under forty thousand tokens of observations, and the agent is answering a related, easier question.

Fix: restate the goal and remaining budget in a late user turn every few steps (chapter 7). Cheap, and it works.

Sycophancy

The agent established that two captures exist. The customer says "no, I was only charged once." The agent apologises and agrees.

Fix: an explicit rule that tool results outrank assertions, and a re-check rather than a capitulation.

the system-prompt clause that handles disagreement
When someone contradicts something a tool established:
- Do not change your finding on assertion alone. Say what the tool returned and
  when it was checked.
- Re-run the relevant lookup once. If it now returns something different, say
  that it changed and give both values.
- If it returns the same thing, state that plainly and offer to escalate to a
  human who can look further. Being wrong is possible; agreeing without evidence
  is not helpful.

Instrumenting the failures

Each detector should emit a metric. The rates tell you where to spend effort, and the trends tell you when something upstream broke.

MetricHealthyWhat a rise means
repeat_blocked_rate< 3% of runsA tool returns results that do not read like answers — check its return shape
oscillation_rate< 1%Two tool descriptions are not distinguishable. Find the pair
fabricated_ref_rate< 1%A lookup path is missing, so the model invents rather than searches
premature_completion_rate< 5%The completion criterion is vague, or the task is under-specified
budget_halt_rate< 10%Tasks are harder than the budget assumes, or a tool got slower
partial_result_rateTrack, no targetUpstream reliability. This is a dependency dashboard, not an agent problem
steps_p95StableA jump usually means a model version changed or a tool started failing quietly
Read ten failed traces a week

Metrics tell you the rate; only the traces tell you the cause, and the cause is almost always something you would never have guessed — a tool returning an empty list rather than an error, a date format the model keeps misreading, a description whose second sentence contradicts its first. Half an hour a week of reading actual failures will produce more improvement than any amount of prompt tuning done from imagination.

The short version

  1. Agents fail in a dozen recognisable ways, each with a cheap detector and a known recovery.
  2. Detect in code, recover through the model. Detection cannot be the model's job — it is inside the failure.
  3. One guard() function before every execution holds repeats, oscillation, per-tool caps, reference validation and cost projection.
  4. Validate identifiers against what has actually been seen. It stops fabrication before it reaches a database.
  5. Premature success is the most damaging failure because the run looks complete. Check the criterion — deterministically where you can.
  6. Aggregate sub-task statuses in code. A model is not a reliable reporter of its own partial failures.
  7. Restate the goal periodically for drift; give the agent an explicit rule for disagreement so it re-checks rather than capitulates.
  8. Emit a metric per detector, and read ten failed traces a week.
