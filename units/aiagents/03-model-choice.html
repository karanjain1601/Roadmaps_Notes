Choosing a model for agentic work

The model that writes the best prose is not necessarily the one that reliably picks the right tool on step nine of eleven. Agentic selection turns on a different set of properties from single-call selection, and almost none of them appear on a leaderboard.

What actually matters

The AI Engineer unit covers general model selection. For agents, reweight it heavily toward these seven properties, in roughly this order.

Benchmarks measure the wrong thing for this

Public leaderboards mostly test single-turn reasoning and knowledge. A model can be excellent at those and mediocre at maintaining a tool-calling contract over eleven turns with 40k tokens of accumulated observations. Agentic benchmarks exist and are better, but they use their tools, not yours — and tool-calling accuracy is strongly sensitive to how tools are described. The only measurement that predicts your production behaviour is your own tools on your own tasks. Chapter 13 builds that harness; it takes a day and it is the highest-value day in the project.

Reasoning models in a loop

Models that think before answering behave differently inside an agent, and the trade is not obvious.

Where they win

  • Planning the overall approach at step 1
  • Deciding what to do after a surprising observation
  • Tasks where a wrong turn is expensive to unwind
  • Knowing that the task is actually complete
  • Recognising an impossible request instead of flailing

Where they cost you

  • Mechanical steps — "now read the file I just found"
  • Latency: seconds of thinking per step, multiplied by steps
  • Reasoning tokens are billed and often invisible
  • Some over-deliberate and take more steps, not fewer
  • Reasoning traces bloat the context you resend

The pattern that works in practice is asymmetric: a reasoning model for the first step and for any step following an error or an unexpected result; a fast standard model for the mechanical majority. Most agent steps are mechanical.

step_model.py — choose per step, not per agent
def model_for_step(n: int, steps: list[Step], budget: Budget) -> str:
    if n == 1:
        return "reasoning"                       # plan the approach properly
    last = steps[-1] if steps else None
    if last and not last.ok:
        return "reasoning"                       # something failed: think about why
    if last and looks_surprising(last.observation):
        return "reasoning"                       # empty result, conflict, unexpected shape
    if budget.cost > budget.max_cost_usd * 0.7:
        return "small"                           # running low: finish cheaply
    return "standard"

# Roughly 70-80% of steps in a typical investigative run are mechanical.
# Routing those to a cheaper, faster model usually halves cost and cuts
# wall-clock time by more, with no measurable drop in completion rate.
# Measure that claim on your own tasks before believing it.

The cost curve is quadratic

Chapter 2 showed why: the whole message array is resent on every step. A run of n steps does not cost n times one call — it costs roughly the sum of a growing array, which is proportional to n².

Prompt caching matters more for agents than for anything else

In a chat application the cacheable prefix is the system prompt. In an agent, everything before the current step — the system prompt, the tool definitions, and every previous message — is a stable prefix that will be resent unchanged. That is exactly what prefix caching is designed for, and it turns the quadratic term into a much smaller one. To get it: keep the system prompt and tool schemas byte-identical between steps, and never insert anything at the front of the array mid-run. Rewriting the system prompt on step 5 to "remind" the model of a rule invalidates the entire cache for the rest of the run.

A 10-step run at 3s per step is 30 seconds. That is acceptable if the user can see progress and unacceptable if they cannot — which is a UX decision, not a model one (chapter 16).

Open-weight models as agents

The gap between hosted frontier models and open weights has narrowed considerably for generation quality. It has narrowed less for agentic reliability, because tool calling is a specifically trained behaviour and the long tail of getting it right — nested schemas, parallel calls, recovering from a validation error, refusing to invent a tool — is where the difference still shows.

  • Check the tool-calling format explicitly. Some open models emit a provider-compatible structure; others need a special template, and a serving stack that supports it. Verify end to end before designing around it.
  • Prefer constrained decoding where your server supports it. Forcing the output to match the tool schema eliminates malformed-argument failures entirely, which is the single biggest reliability gap.
  • Test at depth, not at step one. Smaller models degrade faster as the context fills — the metric to watch is adherence at step 10, not step 2.
  • Consider a hybrid. A hosted model for planning and a local model for the mechanical steps captures most of the cost saving with much less risk.
  • Weigh the operational cost honestly. Agents are bursty and long-running; the utilisation maths differs from single-call serving. The AI Engineer unit has the break-even model.

Measuring it yourself

bakeoff.py — the harness that decides the question
import asyncio, statistics
from collections import Counter

CANDIDATES = ["provider-a:mid", "provider-b:mid", "provider-b:reasoning", "local:open-32b"]

async def evaluate(model_id: str, tasks: list[Task]) -> dict:
    runs = await asyncio.gather(*[run_agent(t.goal, ctx_for(t), TOOLS,
                                            budget=Budget(max_steps=12),
                                            model=model_id) for t in tasks])

    invalid = wrong_first = repeats = 0
    for task, run in zip(tasks, runs):
        for s in run.steps:
            if s.tool and not s.ok and "invalid arguments" in (s.observation or ""):
                invalid += 1
        first = next((s.tool for s in run.steps if s.tool), None)
        if task.expected_first_tool and first != task.expected_first_tool:
            wrong_first += 1
        sigs = Counter((s.tool, json_key(s.args)) for s in run.steps if s.tool)
        repeats += sum(c - 1 for c in sigs.values() if c > 1)

    completed = [r for r in runs if r.status == "completed"]
    correct = [r for r, t in zip(runs, tasks) if t.check(r)]

    return {
        "model": model_id,
        "task_success":       len(correct) / len(tasks),
        "completed":          len(completed) / len(tasks),
        "invalid_call_rate":  invalid / sum(len(r.steps) for r in runs),
        "wrong_first_tool":   wrong_first / len(tasks),
        "repeat_calls":       repeats / len(runs),
        "median_steps":       statistics.median(len(r.steps) for r in completed) if completed else None,
        "p95_seconds":        pct([r.seconds for r in runs], 95),
        "cost_per_success":   sum(r.cost for r in runs) / max(1, len(correct)),
    }

# cost_per_success is the number to decide on. A cheap model that completes 60%
# of tasks can easily cost more per finished job than an expensive one at 90%,
# once you count the retries and the human who cleans up after the failures.
Pin the version, and re-run when it moves

Point production at a specific model version, never a floating alias. Agentic behaviour is unusually sensitive to model updates: a change that improves general quality can alter how eagerly a model calls tools, how many steps it takes, or when it decides it is finished — none of which appear in release notes. Your bake-off harness is also your upgrade harness. Run it against the new version, compare on completion rate, step count and cost per success, then switch deliberately.

The short version

  1. Agentic selection weights differently: tool-call validity, selection accuracy and adherence at depth beat prose quality.
  2. Leaderboards do not predict this. Measure with your own tools on your own tasks — it takes a day.
  3. Reasoning models earn their cost at step one and after surprises, not on mechanical steps.
  4. Cost is quadratic in run length because the array is resent each step. Prompt caching is the main defence and agents benefit from it more than anything else.
  5. Never rewrite the system prompt mid-run — it invalidates the cache for the rest of the run.
  6. Open weights have closed the quality gap faster than the tool-calling reliability gap. Use constrained decoding and test at step 10.
  7. Decide on cost per success, not cost per call.
  8. Pin the version, and re-run the bake-off on every upgrade.
