Chapter 05 · Tools and actions

Executing tools safely

Between the model asking for a tool call and something happening in the world sits your dispatch code. It is the only place in an agent where you have complete control, which makes it the right place to put every guarantee the system needs.

validation authorisation idempotency sandboxing approval

The execution pipeline

Seven gates, in this order. Order matters: cheap rejections first, side effects last.

1 · ResolveDoes this tool exist and is it in this request's toolset?
↓
2 · ValidateArguments against the schema. Reject before anything is touched
↓
3 · GuardRepeats, oscillation, per-run call limits
↓
4 · AuthoriseMay this session's user do this, to this object? Server-side, from the session
↓
5 · Gate consequencesDestructive or costly? Approval, dry-run or a proposal record
↓
6 · ExecuteWith a timeout, an idempotency key and a circuit breaker
↓
7 · Shape and truncateRender for the model, cap the tokens, log the full thing separately
execute.py — the pipeline, complete
from dataclasses import dataclass

@dataclass
class Outcome:
    observation: str          # what the model sees
    ok: bool
    audit: dict               # what the log sees — never the same object

def execute(call, ctx: RequestContext, tools: dict, steps: list) -> Outcome:
    # 1. resolve
    tool = tools.get(call.name)
    if tool is None:
        return Outcome(f"Error: no tool called '{call.name}'. "
                       f"Available: {', '.join(sorted(tools))}.", False,
                       {"event": "unknown_tool", "requested": call.name})

    # 2. validate
    try:
        args = tool.model.model_validate_json(call.arguments)
    except ValidationError as e:
        err = e.errors()[0]
        field = ".".join(str(p) for p in err["loc"])
        return Outcome(f"Error: invalid arguments for {call.name}. "
                       f"Field '{field}': {err['msg']}. Fix and call again.", False,
                       {"event": "invalid_args", "tool": call.name, "field": field})

    # 3. guard
    if (blocked := guard(call, args, ctx, steps)):
        return Outcome(blocked, False, {"event": "guarded", "tool": call.name})

    # 4. authorise — from the session, never from args
    decision = authorise(tool, args, ctx)
    if not decision.allowed:
        return Outcome(f"Error: not permitted. {decision.reason}", False,
                       {"event": "denied", "tool": call.name, "reason": decision.reason})

    # 5. gate consequences
    if tool.consequence != "none":
        gate = consequence_gate(tool, args, ctx)
        if gate.hold:
            return Outcome(gate.observation, True,
                           {"event": "held", "tool": call.name, "ref": gate.ref})

    # 6. execute
    key = idempotency_key(ctx.run_id, call.id, tool.name, args)
    try:
        result = tool.fn(args, ctx, idempotency_key=key, timeout=tool.timeout_s)
    except ToolTimeout:
        return Outcome(f"Error: {call.name} timed out after {tool.timeout_s}s. "
                       f"It may have partially completed — do not retry it. "
                       f"Verify the current state before continuing.", False,
                       {"event": "timeout", "tool": call.name, "key": key})
    except UpstreamUnavailable:
        breaker.record_failure(tool.name)
        return Outcome(f"Error: the {tool.upstream} service is unavailable. "
                       f"Continue without it, or tell the user what is blocked.", False,
                       {"event": "upstream_down", "tool": call.name})
    except Exception as e:
        log.exception("tool_failed", tool=call.name, run=ctx.run_id)
        return Outcome(f"Error running {call.name}: {type(e).__name__}. "
                       f"Consider a different approach.", False,
                       {"event": "error", "tool": call.name, "type": type(e).__name__})

    # 7. shape
    rendered = tool.render(result)
    return Outcome(truncate(rendered, tool.max_observation_tokens), True,
                   {"event": "ok", "tool": call.name, "args": redact(args),
                    "result_bytes": len(rendered)})

Authorisation

This is the gate that matters most and the one most often implemented wrongly. Two rules, both absolute.

Never

  • Take identity from a tool argument
  • Run tools with a service account that can see everything
  • Instruct the model in the prompt to only access permitted records
  • Filter results after fetching them broadly
  • Trust an id the model produced without checking it belongs to this session

Always

  • Derive identity from the session, server-side
  • Scope every query by that identity in the WHERE clause
  • Check object-level ownership, not just tool-level permission
  • Return "not permitted" identically to "not found"
  • Log every denial — a pattern of them is a signal
authorise.py — tool-level and object-level, both
def authorise(tool, args, ctx) -> Decision:
    # Tool-level: is this capability available to this role, in this mode?
    if tool.name not in ROLE_TOOLS[ctx.role]:
        return Decision(False, "this capability is not available for your role")
    if ctx.mode == "read_only" and tool.consequence != "none":
        return Decision(False, "this session is read-only")

    # Object-level: does the thing being acted on belong to this session?
    # This is the check that stops a persuasive ticket reaching another
    # customer's data, and it cannot be skipped for "internal" tools.
    for field, kind in tool.object_refs.items():          # {"order_id": "order"}
        ref = getattr(args, field, None)
        if ref is None:
            continue
        if not owns(ctx, kind, ref):
            log.warn("object_denied", run=ctx.run_id, kind=kind, ref=ref)
            # Deliberately indistinguishable from not-found: never confirm
            # that an id exists to someone not entitled to see it.
            return Decision(False, f"no {kind} with that reference is available")

    return Decision(True, None)
The model is not a security boundary

Anything you ask the model to enforce is a suggestion. "Only access records for the current customer" is a sentence that competes with every other sentence in a context window that includes text an attacker may have written. The only enforcement that holds is the one in authorise(), running in your process, using an identity the model never touches. Put the instruction in the prompt as well — it improves behaviour — but never rely on it.

Idempotency

Agents retry. They retry after timeouts, after ambiguous errors, and sometimes simply because the observation did not read like success. A tool that is not idempotent will eventually do its thing twice.

idempotency, from the run identity rather than the clock
import hashlib, json

def idempotency_key(run_id: str, call_id: str, tool: str, args) -> str:
    """Stable across retries of the SAME logical action, distinct across different ones."""
    payload = json.dumps({"run": run_id, "tool": tool,
                          "args": args.model_dump()}, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()[:32]

# Note the key uses run_id + args, NOT call_id. If the model retries the same
# refund with identical arguments after a timeout, the provider sees the same
# key and returns the original result rather than issuing a second refund.
# Including call_id would defeat that, because the retry has a new call id.

def issue_refund(args, ctx, idempotency_key: str, timeout: float):
    return payments.refund(payment_id=args.payment_id, amount=args.amount,
                           idempotency_key=idempotency_key, timeout=timeout)
Timeouts are the dangerous case, not errors

A clean error means nothing happened. A timeout means you do not know. The agent will be tempted to retry, and if the first call actually succeeded you now have two refunds, two emails, two tickets. The observation text above is written deliberately: it may have partially completed — do not retry it, verify the state first. Pair that with an idempotency key so that if it retries anyway, nothing bad happens. Belt and braces, because the model will occasionally ignore the belt.

Gating consequences

Classify every tool by what it can do. This one field drives most of the safety machinery.

ClassExamplesTreatment
none — read-onlyget_order, search_policy, list_paymentsRun freely. Rate-limit only
reversibleadd_note, set_tag, create_draftRun, but log and make undo easy
externalsend_email, post_message, call_webhookApproval, or a strict recipient allowlist. Cannot be unsent
financialrefund, charge, adjust_creditThreshold-based approval, idempotency, full audit
destructivedelete_record, cancel_order, revoke_accessSoft delete plus approval. Never a hard delete from an agent
Consequence gate One proposed action, several policies. See what reaches the world and what the agent is told.
consequence_gate — proposals are first-class objects
def consequence_gate(tool, args, ctx) -> Gate:
    if ctx.mode == "auto" and tool.consequence in ("none", "reversible"):
        return Gate(hold=False)

    if tool.consequence == "financial":
        amount = float(getattr(args, "amount", 0))
        if ctx.mode == "auto" and amount <= ctx.auto_approve_limit:
            return Gate(hold=False)

    proposal = proposals.create(
        run_id=ctx.run_id, tool=tool.name, args=args.model_dump(),
        requested_by=ctx.user_id, rationale=recent_reasoning(ctx),
        expires_at=now_utc() + timedelta(hours=24),
    )
    return Gate(hold=True, ref=proposal.ref, observation=(
        f"Queued for human approval as {proposal.ref}. It has NOT been executed. "
        f"Do not attempt this action again. Continue with anything else you can "
        f"do, then report what is pending."))

Three details in that observation carry weight. It says the action has not happened, so the agent does not report success. It says not to retry, which prevents a loop. And it tells the agent to continue with other work, so a single held action does not waste the remaining budget.

Sandboxing code execution

A code-execution tool is the most powerful thing you can hand an agent and the one with no partial measures. If generated code runs anywhere your application code can reach, you have no security model.

def run_code(args, ctx, idempotency_key=None, timeout=20) -> dict:
    with sandbox.session(
        image="python-sandbox:3.12-slim",
        network="none",
        readonly_root=True,
        writable=["/work"],
        user="nobody",
        memory_mb=512, cpus=0.5, pids_max=64,
        env={},                          # deliberately empty
        timeout_s=timeout,
    ) as box:
        box.put("/work/main.py", args.code)
        for f in ctx.attached_files:     # only files this session already owns
            box.put(f"/work/{f.name}", f.bytes)
        r = box.run(["python", "/work/main.py"], cwd="/work")

    return {
        "exit_code": r.exit_code,
        "stdout": truncate_chars(r.stdout, 4000),
        "stderr": truncate_chars(r.stderr, 2000),
        "files_written": [f.name for f in r.new_files][:20],
        "_note": "No network access. Output truncated at 4000 characters.",
    }
Code produced by an agent is untrusted input

It does not matter that the model is helpful and the user is legitimate. The code may have been shaped by text the model read from a document, a web page or a ticket — the injection path in chapter 15. Treat every execution as if it were written by an anonymous stranger on the internet, because in the adversarial case it effectively was.

Reliability details that bite later

  • Per-tool timeouts, not one global value. A database lookup gets 3 seconds; a report build gets 60. A single global timeout is either too short for the slow tool or too long for a stuck one.
  • Circuit-break flaky upstreams. After N failures, stop calling and return "unavailable" immediately. An agent burning eight steps retrying a dead service is worse than one told plainly it is down.
  • Cache read-only calls within a run. Agents re-read the same record repeatedly. A per-run cache keyed on tool plus arguments removes those steps and costs nothing.
  • Rate-limit per run, not just per user. A single run should not be able to make ninety search calls.
  • Truncate at the token level, with a marker. "…[truncated, 340 of 2,100 rows shown — narrow with since=]" tells the model both that there is more and how to get it.
  • Keep the audit record separate from the observation. The model sees a shaped summary; the log keeps the full call, arguments and result, redacted per chapter 15.
  • Make tools testable in isolation. Every tool should have unit tests that never involve a model. Most tool bugs are ordinary bugs.

The short version

  1. Dispatch is the one place with full control. Seven gates: resolve, validate, guard, authorise, gate consequences, execute, shape.
  2. Authorisation is object-level, from the session, in your code. The model is never a security boundary.
  3. Return "not permitted" indistinguishably from "not found".
  4. Agents retry. Idempotency keys derived from run and arguments make that survivable.
  5. Timeouts are more dangerous than errors — tell the agent not to retry, and make retrying harmless anyway.
  6. Classify every tool by consequence. Proposals are first-class records, and the observation must say the action did not happen.
  7. Code execution: container, no network, read-only root, non-root user, hard limits, no secrets. No partial measures.
  8. Per-tool timeouts, circuit breakers, per-run caching and truncation markers — the unglamorous parts that decide reliability.
