Multi-agent systems

Multi-agent architectures are usually explained as collaboration — specialists conferring, dividing labour, checking each other. The mechanism that actually produces the gains is duller and more useful to understand: each sub-agent gets a smaller context and fewer tools.

supervisor parallel handoff isolation cost

Why it works, when it works

A single agent with thirty tools and a forty-thousand-token context makes worse decisions than one with six tools and eight thousand tokens. Chapters 4 and 7 established both halves of that. A sub-agent is a way to buy both at once: a focused prompt, a small tool set, and a context containing only what its subtask requires.

What you actually gain

  • Context isolation — the sub-run's intermediate noise never enters the parent's window
  • Tool-set reduction — selection accuracy rises sharply
  • Parallelism — independent subtasks run at once
  • Separable permissions — the researcher cannot send email
  • Independent evaluation — each specialist has its own golden tasks

What you pay

  • Every sub-run re-reads a system prompt and tool schemas
  • Information is lost at every handoff boundary
  • Debugging spans several traces instead of one
  • Failure modes multiply — partial failures, orphaned sub-runs
  • Latency, unless the work is genuinely parallel
Get the isolation the cheapest way you can

If a router plus three separate prompts and tool sets gives you the same focus as three agents, build that — it is cheaper, faster, and testable with ordinary tests. Reach for real sub-agents when the subtask needs its own loop: several steps, unpredictable in number, producing intermediate results the parent should never see.

Supervisor, concretely

sub-agents exposed to the supervisor as ordinary tools
# The cleanest implementation: a sub-agent IS a tool. The supervisor does not
# need a new concept, and everything from chapter 5 — validation, authorisation,
# budgets, timeouts — applies unchanged.

def make_subagent_tool(name: str, description: str, spec: AgentSpec):
    class Args(BaseModel):
        task: str = Field(description="A complete, self-contained instruction. "
                                      "The sub-agent cannot see this conversation.")
        context: str = Field(default="", max_length=2000,
                             description="Facts it needs that it cannot look up itself.")

    def call(args: Args, ctx: RequestContext) -> dict:
        sub = run_agent(
            goal=args.task,
            ctx=ctx.restricted(tools=spec.tools, mode=spec.mode),   # narrower, never wider
            tools={t: REGISTRY[t] for t in spec.tools},
            budget=Budget(max_steps=spec.max_steps,
                          max_cost_usd=ctx.remaining_budget() * 0.4),
        )
        # Return a summary, never the sub-run's transcript. That is the isolation.
        return {
            "status": sub.status,
            "result": sub.text,
            "steps_used": len(sub.steps),
            "unresolved": sub.reason,
            "trace_id": sub.trace_id,        # for debugging, not for the model
        }

    return Tool(name=name, description=description, model=Args,
                fn=call, consequence="none", timeout_s=90)


BILLING = make_subagent_tool(
    "investigate_billing",
    ("Delegate a billing investigation. Use for anything involving charges, refunds, "
     "invoices or payment failures. Give it the customer reference and the specific "
     "question. It can read orders, payments and policy, and it can propose refunds "
     "but not issue them. Returns a summary of findings, not its working."),
    AgentSpec(tools=["get_order","list_payments","get_refunds","search_policy",
                     "propose_refund"],
              mode="assisted", max_steps=8))

Two details do most of the work. The sub-agent's context is ctx.restricted(...) — permissions can only narrow, never widen, so a compromised sub-run cannot escalate. And the return value is a summary, not a transcript: if you pass the sub-run's full message history back to the supervisor you have paid for the extra runs and kept none of the isolation.

One agent or several? The same twelve-step task, arranged three ways. Context, cost and wall-clock time are all affected differently.

Handoff

Delegation returns; handoff does not. The specialist takes over the conversation, and the question becomes what it inherits.

handoff.py — an explicit brief, not a raw transcript
class Handoff(BaseModel):
    to: Literal["billing", "shipping", "technical", "human"]
    reason: str = Field(description="Why this needs the other specialist")
    established: list[str] = Field(description="Facts you have confirmed, with references")
    attempted: list[str] = Field(description="What you already tried, so it is not repeated")
    open_question: str = Field(description="The specific thing that still needs answering")

def handoff(args: Handoff, ctx) -> dict:
    if args.to == "human":
        return escalate_to_human(args, ctx)

    brief = (f"You are taking over a conversation.\n"
             f"Reason: {args.reason}\n"
             f"Established:\n" + "\n".join(f"- {f}" for f in args.established) + "\n"
             f"Already attempted (do not repeat):\n" + "\n".join(f"- {a}" for a in args.attempted) + "\n"
             f"Open question: {args.open_question}")

    return run_agent(goal=brief, ctx=ctx.for_specialist(args.to),
                     tools=TOOLSETS[args.to], budget=Budget(max_steps=8))

# Passing the raw transcript instead of a structured brief is the common shortcut.
# It loses the isolation benefit, costs the tokens, and gives the receiving agent
# a wall of text in which the important facts are no more prominent than the
# dead ends. The brief is worth the extra structured call.
Handoff loops

Billing decides it is a shipping problem, shipping decides it is billing, and the customer watches the same two specialists pass them back and forth. Guard it in code: cap total handoffs per conversation at two, record the handoff chain, and make a second transfer to an already-visited specialist impossible — it must escalate to a human instead. This is the multi-agent version of the oscillation failure in chapter 12, and it is far more visible to users because it happens in front of them.

Shared state

Sub-agents need to communicate more than a return value, and the mechanism you choose determines how debuggable the system is.

parallel workers with a shared, conflict-aware findings store
async def research(question: str, sources: list[str], ctx) -> Report:
    findings = FindingsStore(run_id=ctx.run_id)

    async def worker(source: str):
        return await run_agent(
            goal=f"Answer this using only {source}: {question}. "
                 f"Record each finding with record_finding, including the exact "
                 f"quotation and its location. If {source} does not address it, say so.",
            ctx=ctx.restricted(tools=SOURCE_TOOLS[source] + ["record_finding"]),
            budget=Budget(max_steps=6, max_cost_usd=0.10))

    results = await asyncio.gather(*[worker(s) for s in sources],
                                   return_exceptions=True)

    # Partial failure is the normal case, not the exception. Report it.
    failed = [s for s, r in zip(sources, results) if isinstance(r, Exception)]
    conflicts = findings.detect_conflicts()      # same claim, different values

    return compose(
        findings=findings.all(),
        conflicts=conflicts,                     # surfaced, never silently resolved
        incomplete=failed,
    )
Never let the summary hide a partial failure

Three of five workers succeeded, and the final answer reads as though all the evidence is in. This is the most damaging multi-agent failure because it is invisible: the output is fluent, complete-looking and quietly missing two sources. Aggregate statuses in your code — not in a prompt asking the model to mention failures — and put "2 of 5 sources unavailable" in the response itself.

What it costs to debug

The operational cost is the part that gets underestimated. A single-agent run is one trace you read top to bottom. A supervisor with three sub-runs is four traces, and the interesting question — why did the supervisor delegate that task with that phrasing — lives in the gap between them.

  • One trace id for the whole task, with sub-runs as child spans. If they are separate traces, correlating them is manual and you will not do it (chapter 14).
  • Record the delegation itself — the exact task string, the tool set granted, and the budget. Most supervisor bugs are badly phrased sub-tasks.
  • Budget top-down. The parent holds the total; each sub-run gets a slice. Otherwise five sub-agents each with a "reasonable" budget cost five times what you intended.
  • Time-box sub-runs and treat a timeout as a normal outcome the supervisor must handle, not an exception that kills the task.
  • Evaluate specialists separately from the whole. A supervisor that scores 70% might have one specialist at 40% and two at 95%.
  • Cap depth at two. Sub-agents spawning sub-agents produces cost and traces nobody can follow, for benefits nobody has demonstrated.

The short version

  1. The gain is context isolation and tool-set reduction, not collaboration. Buy those the cheapest way available.
  2. A router with separate prompts often gets you the same focus. Use real sub-agents when the subtask needs its own loop.
  3. Implement a sub-agent as a tool — then validation, authorisation, budgets and timeouts all apply unchanged.
  4. Sub-agent permissions narrow, never widen. Return a summary, never the transcript.
  5. Handoff needs a structured brief — established facts, what was already tried, the open question — not a raw transcript.
  6. Cap handoffs at two and escalate to a human rather than looping between specialists in front of the customer.
  7. Partial failure must appear in the output. Aggregate statuses in code, not by asking the model nicely.
  8. One trace id across the whole task, budget top-down, cap depth at two, and avoid autonomous swarms in production.
