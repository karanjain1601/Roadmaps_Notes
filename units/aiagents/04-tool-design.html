Chapter 04 · Tools and actions

Designing tools

Tool definitions are the agent's entire model of what it can do. When an agent behaves stupidly, the cause is a badly described tool far more often than a weak model — and unlike the model, the description is something you can fix this afternoon.

descriptions schemas granularity return shapes tool count

What the model actually sees

Tool schemas are serialised into the prompt on every step. That has two consequences people forget: they cost tokens continuously, and they are read as instructions. A tool definition is a piece of prompt engineering that happens to have a JSON body.

one tool, as the model receives it
{
  "name": "find_orders",
  "description": "Find a customer's orders. Use this when you have a customer email or ID but no order reference. Returns the 20 most recent orders, newest first. For a specific order you already have a reference for, use get_order instead — it returns more detail. Orders older than 24 months are not here; use search_archive.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email":       {"type": "string", "format": "email",
                      "description": "Customer email exactly as they gave it"},
      "customer_id": {"type": "string", "pattern": "^c_[0-9]+$",
                      "description": "Internal customer id, e.g. c_991"},
      "status":      {"type": "string", "enum": ["any","pending","shipped","delivered","cancelled"],
                      "default": "any"},
      "since":       {"type": "string", "format": "date",
                      "description": "ISO date. Omit for no lower bound."}
    },
    "oneOf": [{"required": ["email"]}, {"required": ["customer_id"]}]
  }
}

Roughly 180 tokens. With fifteen tools that is 2,700 tokens on every step of every run — worth writing well, and worth keeping tight.

The description is the important field

Four things belong in it, in this order. Most descriptions in the wild contain only the first.

ElementExampleWhy
What it does"Find a customer's orders."The obvious part
When to reach for it"Use this when you have an email or ID but no order reference."Turns a capability list into a decision rule
When not to"For a specific order you already have a reference for, use get_order instead."The highest-value sentence. Disambiguates against neighbouring tools, which is where selection errors concentrate
What comes back and its limits"Returns the 20 most recent, newest first. Nothing older than 24 months."Stops the model concluding a customer has no old orders when it simply cannot see them

What most tools look like

"description": "Search orders"

The model cannot tell this from get_order, list_orders or search_archive. It will pick by name similarity to the user's phrasing, which is roughly a coin toss.

What they should look like

"Find a customer's orders. Use when you have an email or ID but no order reference. For a known reference use get_order. Returns 20 most recent; nothing older than 24 months."

Now selection is a rule, not a guess, and the model knows what silence means.

Task-shaped, not API-shaped

The instinct is to expose your existing endpoints. Resist it. Your API was designed for a programmer who reads documentation and holds the whole model in their head. A tool is designed for something that sees only the description, at the moment of choosing.

the same capability, two ways
# API-shaped: four tools, and the agent must compose them correctly.
GET  /customers?email=          -> customer_id
GET  /customers/{id}/orders     -> order ids
GET  /orders/{id}               -> order
GET  /orders/{id}/payments      -> payments

# Four round trips, four chances to pass the wrong id, ~2,400 tokens of
# intermediate observations the model must carry, and a composition the model
# has to rediscover on every run.

# Task-shaped: one tool that answers the question people actually ask.
{
  "name": "get_billing_picture",
  "description": "Everything needed to investigate a billing complaint for one customer: their recent orders, the payments against each, and any refunds already issued. Use this first for any billing question. Identify the customer by email or customer id.",
  "input_schema": {...}
}
# One round trip, one shaped result, no composition to get wrong.
Design tools around questions, not resources

Look at the ten things people most often ask your agent to do. Each of those is a candidate tool. If answering one of them requires the agent to chain four calls in a fixed order every single time, that chain is the tool — you have discovered it, so encode it. Reserve the loop's flexibility for the parts that genuinely vary.

Granularity, and the tool-count cliff

Selection accuracy degrades as the tool list grows. The exact numbers depend on the model and on how distinct your descriptions are, but the shape is consistent: comfortable to about ten, noticeably worse past twenty, poor past thirty.

SituationFix
Fewer than 5 toolsUsually fine. Check none is a god-tool with a mode parameter selecting between unrelated behaviours — split those
5–15 toolsThe sweet spot. Spend the effort on disambiguating descriptions between neighbours
15–30 toolsGroup them. Either route to a subset per request, or introduce a two-level scheme where a category tool reveals its members
30+ toolsRestructure. Sub-agents with focused tool sets (chapter 10), or progressive disclosure via search
two ways to keep the visible list short
# 1. Route to a subset. Cheap, effective, and usually enough.
TOOLSETS = {
    "billing":  ["get_billing_picture", "list_payments", "propose_refund", "search_policy"],
    "shipping": ["track_parcel", "get_order", "reschedule_delivery", "search_policy"],
    "account":  ["get_customer", "update_contact", "reset_password", "search_policy"],
}

def tools_for(goal: str, ctx) -> dict:
    area = classify_area(goal)                       # small model or classifier, ~80ms
    names = TOOLSETS.get(area, TOOLSETS["billing"])
    return {n: REGISTRY[n] for n in names if ctx.may_use(n)}


# 2. Progressive disclosure. For very large or open-ended tool sets.
FIND_TOOL = {
  "name": "find_tool",
  "description": ("Search for a capability you need but do not currently have. "
                  "Describe what you want to do in plain words. Returns matching "
                  "tools with full schemas, which then become available to you."),
  "input_schema": {"type":"object","required":["need"],
                   "properties":{"need":{"type":"string"}}}
}
# The agent starts with 6 core tools plus find_tool, and pulls in specialists
# on demand. Costs a step when it is needed; saves tokens on every step it is not.

Schema rules that prevent whole error classes

RuleInstead ofPrevents
Enums over free stringsstatus: string"Shipped", "SHIPPED", "in transit", "dispatched"
Patterns on identifiersorder_id: stringFabricated references. ^NW-[0-9]{4}$ rejects invention at validation
Formats on datessince: string"last Tuesday", "03/04/26" with ambiguous ordering
Flat over nestedThree levels of objectsStructural errors. Models get objects wrong more often the deeper they go
Required means requiredEverything optionalUnder-specified calls that return everything or nothing

Descriptions on every fieldBare typesThe wrong value in the right field — the hardest error to spot

Never let the model supply identity

No tool should take user_id, tenant_id, role or an API key as a parameter. Those come from the session, resolved server-side, and are injected by your dispatch code. A tool schema that accepts tenant_id is one persuasive sentence in a support ticket away from being a cross-tenant data breach — and it will look like a perfectly reasonable tool call in the trace. This is chapter 15's central point, and it is prevented here, at design time.

Return shapes

What a tool returns matters as much as what it accepts, because it becomes context for every subsequent step — permanently, and at growing cost.

shaping a result for the next decision
# Raw upstream response: 41 fields, 2,100 tokens, mostly irrelevant.
{"id":"NW-8842","customer":{"id":"c_991","email":"...","created_at":"...",
 "marketing_consent":true,"segment":"retail","lifetime_value":481.20, ...},
 "line_items":[{"sku":"...","name":"...","variant_id":"...","warehouse":"...",
 "tax_class":"...","supplier_ref":"...", ...}], "shipping_method_internal_code":"...", ...}

# Shaped for an agent: 180 tokens, and every field earns its place.
def render_order(o) -> dict:
    return {
        "order_id":   o.id,
        "placed":     o.created_at.date().isoformat(),
        "status":     o.status,
        "total":      f"{o.currency} {o.total:.2f}",
        "items":      [f"{li.quantity}× {li.name}" for li in o.line_items],
        "customer":   {"id": o.customer.id, "email": o.customer.email},
        # Identifiers the agent will need for its NEXT call:
        "payment_ids": [p.id for p in o.payments],
        # Say what is not here, so absence is not read as evidence:
        "_note": "Refund history not included. Use get_refunds(order_id) for that.",
    }
  • Include the identifiers the next step will need. An order result without payment ids forces another lookup.
  • State what is missing. "Refund history not included" prevents "there were no refunds".
  • Say when a result is truncated and how to get more: "showing 20 of 147; pass since= to narrow".
  • Prefer compact readable text over deep JSON for prose-like results. Models read both, but text costs fewer tokens and is easier to summarise later.
  • Keep formatting stable. Consistent shapes across calls make the accumulated context easier for the model to scan at step ten.
  • Never return raw HTML or an entire file. Extract, then truncate with a marker (chapter 7).

Iterating on a tool set

1 · Read traces for wrong-tool stepsEvery one is a description defect until proven otherwise
↓
2 · Identify the confusion pairWhich tool did it pick, and which should it have picked?
↓
3 · Add the negative clause to both"For X, use the other one." Cross-reference in both directions
↓
4 · Re-run the golden tasksMeasure top-1 tool accuracy specifically, not just task success
Write descriptions for a competent new starter

The useful test: could someone who joined last week, with no access to your codebase, pick the right tool from your descriptions alone? If they would have to ask a colleague which of two tools to use, the model will guess. Write the answer to that question into both descriptions — and note that this is also a genuinely good onboarding document, which makes it easier to justify the time.

The short version

  1. Tool definitions are prompt engineering with a JSON body, resent on every step and paid for every step.
  2. The description needs four parts. The one everyone omits — when not to use it — prevents most selection errors.
  3. Build task-shaped tools, not API wrappers. If the agent chains the same four calls every run, that chain is the tool.
  4. Selection accuracy falls past about fifteen tools. Route to a subset or use progressive disclosure.
  5. Schemas prevent error classes: enums, patterns on identifiers, formats, flat structures, real descriptions.
  6. Identity never comes from the model. No tenant_id parameters, ever.
  7. Shape returns for the next decision: include the ids it will need, and state what is absent.
  8. Treat every wrong-tool step in a trace as a description bug, and fix it in both tools of the confusion pair.
