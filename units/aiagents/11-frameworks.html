Frameworks, and whether to use one

The loop is forty lines, so the question is never "do I need a framework to write an agent?" It is: which of the fifteen surrounding problems do I want to solve myself, and what does accepting somebody else's answer cost me when I disagree with it later?

what they give you landscape build vs buy the seam migration
This chapter dates faster than the rest

The agent-framework space moves quickly and the specifics below will drift. What holds is the taxonomy — the categories of thing a framework can be, and the questions to ask of any candidate. Use those to evaluate whatever exists when you read this, rather than trusting any named comparison here. Check current documentation before committing.

What is actually on offer

Separate the loop from everything around it. The loop is the part you should understand and the part frameworks add least value to. The surrounding machinery is where the real work is, and where buying can genuinely pay.

The line, stated once

Buy the machinery. Own the behaviour. Persistence, tracing, streaming state and human-in-the-loop are undifferentiated infrastructure — take the best available. The loop, the prompts, the tool definitions and the control decisions are your product; if those live inside a framework's abstractions, you will spend your time debugging the framework rather than your agent, which is a strictly harder problem with a smaller community.

What do you actually need? Answer for the system you are building, not the one you might build. The recommendation is a category, not a product.

Questions to ask of any candidate

  • Can I see the literal prompt? If getting the exact string sent to the model requires monkey-patching, walk away. This is the single most important debugging affordance and chapter 14 depends on it.
  • Where does state live, and can I read it? Checkpoints should be inspectable rows or documents, not an opaque blob.
  • What happens on a tool error? Does it raise and kill the run, or become an observation the model can recover from? Chapter 2 argues for the latter; frameworks differ.
  • How do I enforce budgets? Steps, tokens, wall clock and cost, all four. If it only offers a step cap, you are building the rest anyway.
  • Can I intervene mid-run? Inject an observation, block a call, force termination — from my code, deterministically.
  • What does it do that I cannot see? Hidden retries, silent prompt rewriting and automatic summarisation all change behaviour and cost in ways that will surprise you at 3am.
  • How is it tested? Can I run a whole agent against a scripted fake model, with no network? If not, your test suite will be slow, flaky and expensive.
  • What is the upgrade story? Look at the last few releases. Frequent breaking changes in a dependency this central is a real ongoing cost.

Keep the seam

Whatever you choose, put a boundary between your product's logic and the framework's. It costs an afternoon and it is what lets you change your mind in a year without rewriting the application.

agent/interface.py — the contract your application depends on
from typing import Protocol, Callable, Iterator

@dataclass
class AgentRequest:
    goal: str
    ctx: RequestContext
    tools: list[str]
    budget: Budget
    resume_from: str | None = None

@dataclass
class AgentEvent:
    kind: Literal["step", "tool", "awaiting_approval", "done", "error"]
    payload: dict

class AgentRunner(Protocol):
    def run(self, req: AgentRequest) -> Run: ...
    def stream(self, req: AgentRequest) -> Iterator[AgentEvent]: ...
    def resume(self, run_id: str, decision: Decision) -> Run: ...

# Two implementations, one interface.
class NativeRunner:      # chapter 2's loop
    ...
class FrameworkRunner:   # whatever you adopted
    ...

# Everything else in the application — routes, jobs, tests, the UI — depends on
# AgentRunner and never imports the framework. Swapping is then a config change
# plus one new class, and you can run both in parallel behind a flag to compare.

Your tools should sit outside the framework too. A tool is a validated function with an authorisation gate (chapter 5); registering it with a framework should be a one-line adapter, not a rewrite. If you find yourself writing framework-specific tool classes, the seam has leaked.

The prototype-to-production trap

Role-based crew frameworks get you something demonstrable in an afternoon, which is genuinely valuable for learning what to build. The trap is that the demo becomes the plan, and six weeks later you need per-tool authorisation, a step budget, a trace that explains a bad run, and deterministic tests — and each of those is a fight against abstractions designed for the demo. Prototype freely; be explicit with yourself and your team that the prototype is a spike, and be prepared to throw it away.

Migrating later

What moves easilyWhat does not
Tool functions and schemas, if they are plainPersisted state in a framework-specific checkpoint format
Prompts, if they are data rather than codeControl flow expressed as the framework's graph primitives
Eval sets — they test behaviour, not implementationTraces already stored in a proprietary shape

Before adopting anything, ask what leaving would cost. If the answer is "rewrite the orchestration", that is acceptable. If it is "rewrite the tools and re-record every trace", negotiate that down first.

A defensible default

Start with chapter 2's loopAn hour. You now understand every abstraction you will later evaluate
↓
Add libraries, not a frameworkPydantic or Zod for schemas, your existing tracing, your existing job queue
↓
Adopt when you hit a real wallDurable multi-hour runs, mid-run human interrupts, or a control flow that is honestly a graph
↓
Adopt behind the seamOne class implementing AgentRunner. The rest of the application never knows

Teams that follow that order tend to end up with less code than teams that started with a framework, because they only ever adopted the parts they had a demonstrated need for. Teams that start with a framework often carry orchestration machinery for a control flow that turned out to be a loop with six tools.

The short version

  1. Buy the machinery, own the behaviour. Persistence, tracing, streaming and human-in-the-loop are worth buying; the loop, prompts and tools are your product.
  2. Evaluate categories, not products — the landscape shifts faster than any comparison stays accurate.
  3. The first question of any candidate: can I see the literal prompt? If not, walk away.
  4. Check what it does that you cannot see — hidden retries, silent summarisation, prompt rewriting.
  5. Insist on deterministic tests against a scripted model, offline.
  6. Keep the seam. One AgentRunner interface, framework behind it, tools outside it.
  7. Crew frameworks are excellent spikes and poor foundations. Prototype knowingly.
  8. Default order: loop, then libraries, then a framework when you hit a real wall — and adopt it behind the seam.
