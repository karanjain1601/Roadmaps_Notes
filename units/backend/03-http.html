HTTP in depth

Most people know enough HTTP to send a request. Rather less common is knowing what the protocol promises — which methods may be retried safely, which responses may be cached and for how long, and why the browser sent an OPTIONS request nobody asked for. Those promises are what the rest of the stack is built on.

Safe and idempotent are not the same, and both are promises to strangers

Safe means no observable change. Idempotent means doing it twice has the same effect as doing it once. DELETE is not safe — it destroys something — but it is idempotent, because deleting an already-deleted thing leaves the world in the same state.

These are not academic labels. Browsers prefetch links, proxies retry failed GETs, load balancers replay requests when a backend disappears mid-flight, and monitoring tools poll endpoints. All of that assumes the promises hold. An endpoint that mutates data behind a GET will be triggered by something you did not write — the classic case being a crawler that follows every /delete?id=… link on an admin page.

Status codes

The class matters more than the number: 2xx worked, 3xx go elsewhere, 4xx you made a mistake, 5xx we made a mistake. Within that, a dozen carry information worth getting right.

Status code reference

The single most common API mistake

Returning 200 OK with {"success": false, "error": "..."} in the body. It breaks every layer that reads status codes rather than bodies: retry logic, circuit breakers, error-rate dashboards, alerting, CDN caching, and the client library's own exception handling. Your error rate graph shows a flat zero while the product is broken. Use the status line for what went wrong and the body for the detail — RFC 7807 problem details is a ready-made shape for that body, covered in chapter 5.

Caching and conditional requests

HTTP has a caching model built in, and it is the cheapest performance work available — a header change with no application logic. Most APIs do not use it at all.

Six requests, four strategies
Watch the bytes and the origin hits
http — the headers that do the work
# ── a public, immutable asset: cache it forever ──
Cache-Control: public, max-age=31536000, immutable
# safe only if the URL changes when the content does — /app.4f2a1b.js

# ── a list that changes occasionally ──
Cache-Control: public, max-age=60, stale-while-revalidate=300
ETag: "a4f2c9"
# fresh for 60s; for the next 5 minutes serve the stale copy INSTANTLY
# while revalidating in the background. Users never wait for the check.

# ── personalised: never store in a shared cache ──
Cache-Control: private, no-cache
# "no-cache" does NOT mean do not cache. It means revalidate before
# each use. "no-store" is the one that means do not keep a copy.

# ── anything with a token or a session ──
Cache-Control: no-store
Vary: Authorization
# Vary tells caches the response depends on that header — without it a
# shared cache can serve one user's data to another. A real breach,
# caused by a missing header.

Cookie or Authorization header?

Cookies are automatically attached by the browser, which is convenient and is precisely why CSRF exists — the browser will attach them to a request your site did not initiate. Authorization headers must be added deliberately by your code, so they are immune to CSRF but must be stored somewhere, and every storage option in a browser is readable by JavaScript and therefore by an XSS payload. For a browser-facing application, an HttpOnly cookie with SameSite=Lax is usually the safer default; for mobile clients and service-to-service calls, a bearer token in a header. Chapter 14 takes this apart properly.

CORS

The rule browsers enforce is the same-origin policy: a page from one origin may not read a response from another. CORS is the mechanism by which a server opts out of that restriction for specific callers.

http — a preflight, and the response that satisfies it
# the browser sends this BY ITSELF before the real request, because the
# request is not "simple" — it has a JSON content type and a custom header
OPTIONS /v1/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

# the server must answer this, not just the real request

Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400        # cache the preflight for a day

CORS is not a security control for your API

It protects users of browsers from having their credentials used by a malicious page. It does nothing about anyone with a terminal, since a non-browser client simply ignores the headers. Setting Access-Control-Allow-Origin: * does not expose an otherwise-protected API — but it does mean any website can make authenticated-looking requests using a visitor's cookies, which is why the specification forbids combining it with credentials. Your actual authorization lives in chapter 14; CORS is a browser policy, not a firewall.

What this means for you, concretely
  • Turn HTTP/2 on at the edge and stop thinking about it. It is a load-balancer configuration line. Almost nothing in your application changes.
  • Domain sharding and asset concatenation are now harmful. Both existed to work around HTTP/1.1's six-connection limit; under multiplexing they add handshakes and defeat caching.
  • Server push is dead. It was HTTP/2's headline feature, browsers removed support, and 103 Early Hints replaced it. Do not build on it.
  • HTTP/3 matters most on lossy networks. On mobile the removal of head-of-line blocking is a substantial real-world win; on a wired connection to a nearby datacentre it is a rounding error.
  • Internal service-to-service traffic often still runs HTTP/1.1, and on a reliable low-latency network that is entirely fine.

Self-check

  1. DELETE is idempotent but not safe. Explain both halves.
    Not safe, because it observably changes the world — something is gone afterwards. Idempotent, because deleting an already-deleted resource leaves the same end state, so a client that retries after a timeout causes no additional harm. That distinction is what lets infrastructure retry a DELETE automatically when a backend disappears mid-request, and it is why the two words are not interchangeable.
  2. Why is returning 200 with an error in the body a real problem rather than a style preference?
    Because everything between your code and the client reads the status line, not the body: retry logic, circuit breakers, CDN caching rules, error-rate metrics, alerting thresholds and client library exception handling. All of them conclude the request succeeded. The practical result is a dashboard showing a zero per cent error rate while the product is broken, and no alert firing. The status line is a machine-readable contract with infrastructure you did not write.
  3. What is the difference between no-cache and no-store?
    They are almost opposites of what the names suggest. no-cache permits storing the response but requires revalidation with the origin before each use — so you still get the bandwidth saving of a 304 when nothing changed. no-store forbids keeping any copy at all, which is what you want for anything containing credentials or personal data. If you meant "do not keep this", you meant no-store.
  4. What does Vary: Authorization prevent?
    A shared cache serving one user's personalised response to another. Without it, a CDN sees two requests for the same URL, considers them identical, and returns the cached copy — which contains the first user's data. It is a genuine data breach produced by a missing header. The stronger protection for anything user-specific is Cache-Control: private or no-store, with Vary as a backstop.
  5. Your API works from curl but the browser reports a CORS error. What does that tell you?
    That the API itself is fine and the problem is the browser's same-origin policy, which curl does not enforce. Check whether the failing request triggers a preflight — a JSON content type or a custom header does — and whether your framework actually answers OPTIONS rather than returning 404 or 405. Then check that the returned origin, methods and headers cover what the browser asked for, and that credentials are handled with a specific origin rather than a wildcard.
  6. Why did concatenating JavaScript files into one bundle stop being good advice?
    It was a workaround for HTTP/1.1's roughly six connections per origin, which made each additional file a real cost. HTTP/2 multiplexes many requests over one connection, so the cost largely disappears — and one large bundle is worse for caching, because changing a single line invalidates the whole thing rather than one small file. Domain sharding went the same way: it now adds DNS lookups and handshakes to defeat a limit that no longer exists.
