Scaling and resilience

Two problems that look separate and are the same one. Scaling is about handling more; resilience is about handling less than you expected from something you depend on. Both come down to the same question: what does this system do when a resource runs out?

— words— min read2 interactivesNeeds: chapters 04, 17

Scaling

Vertical first, and further than you think
A single machine with 128 cores and a terabyte of memory is available for a few thousand a month, and it needs no distributed anything. Most systems that adopted horizontal scaling did not need it — and vertical scaling is one line of configuration against months of engineering.
Horizontal requires statelessness
Any instance must serve any request. In-memory sessions, local file uploads, in-process caches, scheduled jobs that assume they are the only one — each pins a request to an instance and has to be moved to a backing service before scaling out means anything.
The database is the hard part
Application instances scale trivially; the shared database does not. Read replicas handle reads, and writes remain on one primary until you shard. Almost every "we need microservices to scale" conversation is really about the database.
Sharding is the last resort
It removes cross-shard joins, transactions, unique constraints and simple aggregation. Exhaust caching, read replicas, better indexes, archiving old data and a larger machine first — genuinely, in that order.

When a dependency gets slow

Not down — slow. A dependency that fails immediately is a minor inconvenience; one that takes eight seconds to answer will take your service down with it, and it will do so through a mechanism that has nothing to do with the dependency itself.

            return fn()

How a cascade actually happens

One dependency slows to three seconds. Your service has no timeout, so each request holds a worker for three seconds instead of fifty milliseconds — a sixtyfold drop in throughput. Requests queue; the queue is unbounded, so it grows. Every endpoint on the instance is now slow, including ones that never touch that dependency, because they are waiting for a worker. The health check times out. The load balancer removes the instance and sends its traffic to the others, which are in the same state and now receive more. Clients time out and retry, tripling the load. The dependency, now receiving three times the traffic, gets slower.

Note that nothing in this chain is a bug. Every component behaved as designed. The cascade is an emergent property of unbounded waiting, and a timeout on that one call would have stopped it at the first step.

Capacity, briefly

Measure the throughput of one instance under realistic load, note the utilisation at which latency starts climbing — usually 70–80%, for the queueing reasons in chapter 4 — and size for peak traffic at that utilisation, plus headroom for one availability zone failing. Then check the numbers that do not scale with instances: database connections (instances × pool size), third-party rate limits, and licence or quota ceilings. Autoscaling is not a capacity plan; it reacts over minutes to spikes that arrive in seconds, and it cannot scale the database at all.

Self-check

  1. Why is a slow dependency more dangerous than a dead one?
    Because a dead one fails immediately — connection refused, worker released, error returned in a millisecond. A slow one holds a worker for the whole of its latency, so throughput collapses in proportion, requests queue, and every other endpoint on the instance degrades even though they never touch that dependency. Failing fast is a mild, contained event; failing slowly consumes the resource that everything else needs.
  2. Trace how a single slow dependency becomes a full outage.
    No timeout means each call holds a worker far longer than usual, so throughput drops sharply. The queue grows without bound, latency rises across every endpoint on the instance, and the health check itself times out. The load balancer removes the instance and redistributes its traffic to others already in the same state. Clients time out and retry, multiplying load on the dependency, which slows further. Every step is a component working as designed; the emergent behaviour is the outage, and a timeout at step one prevents all of it.
  3. What does a circuit breaker do that a timeout does not?
    A timeout bounds each individual call but you still pay it on every request — with a 500 ms timeout and 200 requests per second you are still spending 100 worker-seconds a second on calls you know will fail. A breaker notices the pattern and stops calling altogether, so requests fail in about a millisecond and workers stay free for everything else. It also relieves the struggling dependency, giving it room to recover, and probes periodically so recovery is detected automatically.
  4. Why must retry backoff include jitter?
    Because clients that failed together will retry together. A dependency blip fails a thousand requests at the same instant, and with deterministic backoff all thousand return exactly one second later — a synchronised spike that re-breaks whatever was recovering, causing another synchronised retry. Randomising the delay spreads the returns across the interval and converts a spike into a ramp. It is one line and it is the difference between recovery and a self-sustaining outage.
  5. Why is an unbounded queue a delayed crash?
    Because it converts an overload you could have detected into one you cannot. If arrivals exceed capacity, the queue grows, latency grows with it, and every item eventually completes after the client has given up — so you are doing full work for results nobody will read, while memory climbs until the process is killed. A bounded queue makes the overload visible immediately: it fills, and you reject with 503 or apply backpressure upstream. Rejecting early is a decision; running out of memory is not.
  6. Sharding is proposed because the database is at capacity. What comes first?
    Fix the queries — indexes and N+1 problems routinely yield an order of magnitude for a day's work. Then cache what is expensive and repeated, then move to a larger machine, which is a configuration change and often gives 4–8×. Then read replicas if the load is read-heavy, archiving old data to shrink the working set, and moving high-volume writes like events and metrics out of the transactional store. Sharding is last because it permanently removes joins, transactions, unique constraints and simple aggregation across the whole dataset.
