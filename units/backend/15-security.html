Injection

Every injection flaw has the same shape: data crosses into a place where it is read as instructions. SQL is the famous case; the pattern is identical for shell commands, template engines, LDAP filters and log formats.

A login query, built two ways
Pick a payload, then flip to parameterised
python — the same pattern in four languages of its own
# ── SQL ──
cur.execute(f"SELECT * FROM users WHERE email = '{email}'")   # ✗
cur.execute("SELECT * FROM users WHERE email = %s", (email,))   # ✓
# the driver sends the query and the values separately. The database
# parses the query BEFORE it sees the data, so data can never become
# syntax. This is why parameterisation is a guarantee, not a filter.

# ── shell ──
os.system(f"convert {path} out.png")                 # ✗ path="a; rm -rf /"
subprocess.run(["convert", path, "out.png"])         # ✓ no shell involved

# ── identifiers, which parameters CANNOT cover ──
cur.execute("SELECT * FROM users ORDER BY %s", (col,))   # ✗ won't work
if col not in {"created_at", "email", "name"}:            # ✓ allow-list
    raise BadRequest()
cur.execute(f"SELECT * FROM users ORDER BY {col}")
# table and column names are syntax, not data. The ONLY safe approach
# is an allow-list of permitted values — never an escaping function.

# ── NoSQL is not immune ──
db.users.find({"email": request.json["email"]})     # ✗ {"$ne": null}
db.users.find({"email": str(request.json["email"])})  # ✓ coerce the type

XSS, CSRF and SSRF

XSS — someone else's script in your page
The defence is contextual output encoding, applied where the value is rendered rather than where it is stored. HTML body, attribute, URL and JavaScript contexts each need different escaping, which is why sanitising on input does not work — you do not yet know the context. Modern template engines escape by default; the bugs live in the places that opt out: innerHTML, dangerouslySetInnerHTML, |safe, and building URLs from user input.
CSP — the second line
A strict Content-Security-Policy turns an XSS bug from a compromise into a blocked console message. script-src 'self' 'nonce-…'; object-src 'none'; base-uri 'none' is the shape to aim for. Avoid unsafe-inline, which removes most of the value.
CSRF — your user's browser, someone else's page
An attacker's page issues a request to your site, and the browser helpfully attaches the cookies. SameSite=Lax is now the browser default and stops the cross-site POST case, which is most of it. Add a synchroniser token for anything sensitive, and never make a state-changing endpoint respond to GET — chapter 3's safety promise is load-bearing here.
SSRF — your server, someone else's target
You fetch a URL the user supplied, and they point it at 169.254.169.254 to read cloud instance credentials, or at an internal service with no authentication because it is "on the private network". Underrated and severe.
python — SSRF is harder to prevent than it looks
# ✗ a blocklist of hostnames. Defeated by a DNS name that resolves to
#   a private address, by decimal or IPv6-mapped notation, by a redirect
#   to an internal host, or by DNS rebinding between check and fetch.

# ✓ resolve first, validate the ADDRESS, then connect to that address
def safe_fetch(url):
    parsed = urlparse(url)
    if parsed.scheme not in ("http", "https"):
        raise BadRequest()
    ips = [ipaddress.ip_address(ai[4][0]) for ai in
           socket.getaddrinfo(parsed.hostname, None)]
    for ip in ips:
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            raise BadRequest("internal address")     ← 169.254.169.254 is
    return httpx.get(url, timeout=5,                       link-local: covered
                     follow_redirects=False)          ← redirects bypass the
                                                          check. Handle each hop
# the robust answer at scale is an egress proxy with an allow-list, so
# the application simply has no route to internal addresses at all.

Protection against brute force, scraping, runaway clients and cost. The algorithm choice looks like a detail and produces a threefold difference in what actually gets through.

Rate limiting in practice
  • Limit by the right key. Per IP catches crawlers and punishes offices behind one NAT. Per account is the meaningful unit for an authenticated API. Per endpoint matters because a login attempt and a health check are not comparable. Usually you need several limits at once.
  • Return the headers. RateLimit-Remaining on successful responses lets a well-behaved client slow down; Retry-After on a 429 tells it when to come back. Omitting them turns a limit into a retry storm — chapter 5.
  • Distributed counters need shared state. Per-instance limits multiply by your instance count. Redis with an atomic script is the standard answer.
  • Fail open or closed, deliberately. If the limiter's Redis is unreachable, do you admit everything or reject everything? Both are defensible; having no answer is not.

                         object-src 'none'; base-uri 'none'; frame-ancestors 'none'

   the browser refuses plain HTTP for this domain, closing the downgrade

   stops the browser guessing a content type and executing your uploaded
   "image" as a script.

   third parties through the Referer header.

   disables browser capabilities the application does not use, so an
   injected script cannot reach them either.
The two habits worth more than the rest of this chapter

Validate at the boundary, with an allow-list. Define what is acceptable — types, lengths, ranges, permitted values — and reject everything else at the edge of the system, before any business logic runs. A schema validator that rejects unknown fields also prevents mass assignment for free. Denylists fail because attackers find inputs you did not think of; allow-lists fail closed.

Make the safe way the easy way. If avoiding a vulnerability depends on every developer remembering something, it will eventually not be remembered. A query builder that cannot concatenate, a template engine that escapes by default, a repository layer where every query takes a tenant id, a linter that rejects innerHTML — these remove whole classes of bug structurally. Security that relies on vigilance is security that expires with the next hire.

Self-check

  1. Why does parameterisation prevent SQL injection when escaping does not reliably?
    Because it removes the possibility rather than filtering for it. The driver sends the query text and the values on separate channels, so the database parses and plans the statement before it has seen any user data — the data can never be interpreted as syntax, whatever it contains. Escaping tries to neutralise dangerous characters, which depends on getting the character set, the quoting style and every edge case right. One is a structural guarantee; the other is a filter you have to keep winning.
  2. Parameters cannot be used for a column name in ORDER BY. What is the safe approach?
    An allow-list. Identifiers are syntax rather than data, so the placeholder mechanism does not apply — check the supplied value against a fixed set of permitted column names and reject anything else before interpolating. Do not reach for an escaping or quoting helper; the correct mental model is that you are choosing between a handful of pre-approved queries, not passing a value. The same applies to table names, sort directions and anything else that is part of the statement's structure.
  3. Why is escaping on input the wrong place to prevent XSS?
    Because the correct escaping depends on where the value ends up, and at input time you do not know. HTML body, an HTML attribute, a URL, a JavaScript string and a CSS value each need different treatment, and a value escaped for one is wrong — sometimes still dangerous, usually visibly mangled — in another. Store the raw value and encode at the point of rendering, in the context it is being rendered into, which is what modern template engines do by default.
  4. What makes SSRF hard to prevent with a blocklist?
    Because the check and the connection are separate events, and the attacker controls what happens between them. A hostname can resolve to a private address; an address can be written in decimal, octal or IPv6-mapped form; a permitted host can redirect to an internal one; and DNS rebinding can return a public address to your validator and a private one to your HTTP client moments later. The robust answer is to resolve the name, validate the resulting addresses, connect to that address specifically, and refuse to follow redirects — or better, give the service no network route to internal addresses at all.
  5. What is wrong with a fixed-window rate limiter?
    The boundary. A limit of 100 per minute permits 100 requests in the final second of one window and 100 more in the first second of the next — 200 in two seconds, twice the intended rate, at exactly the moment an attacker is most likely to be probing. Sliding windows track a moving interval and do not have the seam; a token bucket permits a bounded burst on purpose and then enforces the average, which is usually the behaviour you actually want from an API.
  6. Why is "make the safe way the easy way" better advice than a security checklist?
    Because checklists rely on people remembering, and over a codebase's lifetime and a team's turnover, something will not be remembered. Structural defences do not decay: a query interface that cannot concatenate, a template engine that escapes by default, a data layer where every query requires a tenant id, a schema validator that rejects unknown fields. Each removes an entire class of bug regardless of who writes the next endpoint, which is the only kind of security that survives contact with a growing team.
