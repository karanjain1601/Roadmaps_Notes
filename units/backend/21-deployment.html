Deployment and delivery

Chapter 1 ranked "a change that was deployed" as the most common cause of production incidents. That does not argue for deploying less often — it argues for deploying in a way where a bad change reaches a small number of people and can be undone in seconds.

— words— min read2 interactivesNeeds: chapters 08, 20

Build once, deploy many

One artefact, every environment
The image that reaches production is byte-identical to the one tested in staging. If a build runs per environment, you have not tested what you shipped — and the difference will be found in production.
Configuration comes from outside
Environment variables and mounted secrets, never baked in. An artefact that contains a database URL is an artefact that can only run in one place.
A release is an artefact plus a config
Both versioned. Rolling back means selecting the previous release, which is a fast, boring operation rather than a rebuild from an old commit.
Immutable, and tagged by content
Tag by commit SHA, never latest. A mutable tag means two instances running "the same version" may not be, which is a debugging experience nobody should have.

Every strategy except recreate runs two versions simultaneously

This is the constraint that makes deployment a design problem rather than an operations one. Both versions read and write the same database, consume the same queues and serve the same clients — so every change must be compatible with the version before it. That is chapter 8's expand-and-contract for schemas, chapter 18's schema versioning for events, and additive-only changes for API responses. A change that requires all instances to switch at once has only one safe strategy, and it involves downtime.

How long must a canary bake?

A one per cent canary limits the blast radius to one per cent — and gives you one per cent of the data, so it takes a hundred times longer to notice anything. The two effects pull against each other and the balance is arithmetic rather than taste.

What to compare, and what to compare it against

Compare the canary to the baseline running at the same moment, not to yesterday's numbers — traffic mix, time of day and a neighbouring incident all move the absolute figures, and only a simultaneous comparison controls for them. Compare error rate, latency percentiles and business metrics such as conversion, since a change can be technically clean and commercially disastrous. And route by a stable hash of the user rather than randomly per request, so an individual gets a consistent experience instead of alternating between versions mid-journey.

Flags, migrations and rollback

Deploy is not release
A feature flag lets code reach production while switched off, so deployment becomes routine and enabling the feature becomes the risky, reversible, separately-timed event. It also makes rollback instantaneous for that feature alone, without touching anything else that shipped in the same build.
Flags are debt
Each one doubles the paths through that code, and combinations multiply. Give every flag an owner and a removal date, and delete it once the feature is permanent — a codebase with two hundred stale flags is untestable in any meaningful sense.
Migrations run separately from deploys
As their own pipeline step, before the code that needs them, and always backwards compatible — chapter 8. Coupling them to the application's startup means a failed migration takes down every instance trying to boot.
Rollback beats roll forward, usually
Reverting to a known-good release is fast and predictable; fixing forward under pressure is writing untested code during an incident. The exception is a change that cannot be reversed — anything that has already altered data — which is precisely why irreversible steps are separated and deferred.

The counter-intuitive finding

Deploying more often makes systems more stable, not less. It sounds backwards and the mechanism is simple: frequent deploys are necessarily small, small changes are easy to reason about and to revert, and the machinery required to deploy safely — tests, progressive rollout, fast rollback, good signals — is exactly the machinery that limits the damage when something does go wrong. Teams that deploy monthly have large, risky releases and a rollback procedure nobody has rehearsed. The safety comes from the batch size and the practice, not from the caution.

Self-check

  1. Why must the artefact deployed to production be identical to the one tested?
    Because otherwise you tested something else. A rebuild can pick up a different base image, a newer transitive dependency, a different compiler or a changed build environment, and any of those differences is untested by definition. Build once, tag by commit, promote the same image through each environment, and supply everything that varies as external configuration. It also makes rollback a selection rather than a rebuild.
  2. Why do rolling, blue-green and canary all constrain what changes you may make?
    Because all three run two versions at once against the same database, queues and clients, so every change has to be compatible with the version before it. That means expand-and-contract for schema changes, versioned and additive event payloads, and API responses that only gain fields. A change requiring every instance to switch simultaneously is incompatible with zero-downtime deployment, and needs either a compatibility shim or a maintenance window.
  3. A 1% canary limits exposure to 1%. Why is that not automatically safest?
    Because it also gives you 1% of the observations, so detecting a regression takes roughly a hundred times longer than at full traffic. For a rare error the bake can run for hours, during which the bad version is live — and the total number of affected requests can end up similar to, or worse than, a larger canary caught quickly. The right share depends on your traffic and the size of the regression you need to catch: high volume permits a small canary, low volume does not.
  4. Why compare a canary against a simultaneous baseline rather than yesterday's metrics?
    Because everything else moves too. Traffic mix, time of day, a marketing campaign, a slow dependency or an unrelated incident all shift the absolute numbers, so a comparison across time confounds your change with all of them. Running both versions at once and comparing them directly controls for every shared factor, which is the only way a small difference becomes attributable. It is the same reasoning as a control group in an experiment.
  5. How do feature flags change the risk profile of a deployment?
    They separate deploying code from activating behaviour. The code ships inert, so the deploy itself is low-risk and can happen often, and the feature is enabled later as its own reversible decision — for a percentage of users, and switched off in seconds without a redeploy. The cost is that every flag doubles the paths through that code and combinations multiply, so flags need owners and removal dates or the codebase becomes untestable.
  6. Why does deploying more often improve stability?
    Because frequency forces small batches. A small change has few suspects when something breaks, is easy to reason about and can be reverted without taking anyone else's work with it. Frequency also requires the machinery — fast tests, progressive rollout, one-command rollback, good signals — and that machinery is precisely what contains a failure. Infrequent deployment produces large releases, unrehearsed rollbacks and a longer time to restore, which is why the DORA metrics move together rather than trading off.
