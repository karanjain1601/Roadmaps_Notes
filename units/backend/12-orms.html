ORMs and data access

The layer nearly everyone reaches the database through, and the source of the single most common performance bug in web applications — one that is invisible in development, because in development the list has four rows in it.

— words— min read2 interactivesNeeds: chapter 09

What an ORM actually does

Mapping rows to objects is the advertised feature and the least interesting one. The machinery underneath is where both the value and the surprises come from.

Identity map
Within one session, the same row is always the same object. Load user 7 twice and you get one instance — which prevents a whole class of bug where two copies of a record drift apart in memory.
Unit of work
Changes accumulate and are written in one flush at the end, in dependency order, inside one transaction. You stop writing INSERT statements and start assigning attributes.
Change tracking
The ORM knows which fields you modified and writes only those. Useful, and the reason an innocuous attribute assignment can produce an UPDATE you did not expect.
Lazy loading
Related objects are fetched on first access, transparently. This is the convenience that causes N+1, and it is on by default in most ORMs.
Migrations
Schema changes derived from model definitions, versioned and ordered. Genuinely valuable, and often the strongest single argument for adopting one.
An ORM is worth it forAnd costs you
CRUD, which is most of the queries in most applicationsA layer between you and the SQL, so performance problems are one step removed

The rule that resolves most ORM arguments

Use the ORM for the eighty per cent of queries that are loading and saving records, and drop to SQL for the twenty per cent that are reports, bulk operations and anything with a window function. Both are correct tools; the mistake is insisting on one. The corollary matters more: you must be able to see the SQL your ORM generates. Turn on query logging in development, and put a query counter in your test suite. An ORM you cannot see through is not an abstraction, it is a blindfold.

python — the bug, and the three ways out
# ── the bug. Nothing in this code mentions a query. ──
orders = session.query(Order).limit(50).all()      # 1 query
for o in orders:
    print(o.customer.name)                          # 50 more, one per loop
#   ↑ attribute access. It looks free and it is a network round trip.

# ── ① join: one query, one round trip ──
orders = (session.query(Order)
          .options(joinedload(Order.customer))
          .limit(50).all())
#   best for many-to-one. Beware for collections — see the next demo.

# ── ② select-in: two queries, no row multiplication ──
orders = (session.query(Order)
          .options(selectinload(Order.items))
          .limit(50).all())
#   issues  SELECT … WHERE order_id IN (…)  — the right default for
#   collections, and what GraphQL's DataLoader does by hand.

# ── ③ do not load objects at all ──
rows = session.query(Order.id, Order.total, Customer.name) \
              .join(Customer).limit(50).all()
#   if you are rendering a table, you want rows, not an object graph.
#   no identity map, no lazy loading, no surprises.
Why it survives review and testing

The loop contains no SQL, so nothing looks like a database call. The test fixture has three orders, so the endpoint responds in four milliseconds. The code reads beautifully. It reaches production, the list grows to two hundred rows, and the endpoint starts taking a quarter of a second — then the traffic doubles and the connection pool from chapter 4 is exhausted, because each request now holds a connection for two hundred sequential round trips. The single most effective defence is a test that asserts the query count: render the page with two records, then with ten, and fail if the number of queries changed.

The other direction: joining too much

Having learned that N+1 is fixed by eager loading, the next mistake is eager-loading everything with joins. Joining two collections multiplies them.

python — a query-count assertion, which catches N+1 before production
def test_order_list_does_not_scale_with_rows(client, db):
    make_orders(2)
    with count_queries(db) as few:
        client.get("/v1/orders")

    make_orders(20)
    with count_queries(db) as many:
        client.get("/v1/orders")

    assert few.count == many.count, (
        f"query count grew from {few.count} to {many.count} — N+1")
# ten times the data must not mean ten times the queries. This one
# assertion catches the bug at the moment it is introduced, which is
# the only time it is cheap to fix.
Query builders, and the repository question

Query builders — SQLAlchemy Core, Knex, jOOQ, Kysely — sit between an ORM and raw strings. You compose SQL programmatically with type safety and parameterisation, and get no identity map, no lazy loading and no surprises. For read-heavy services and reporting they are often the better fit, and they compose far more naturally than ORM query APIs do.

The repository pattern — wrapping data access behind an interface — is worth it when it hides genuinely complex queries behind a domain-meaningful name, and not worth it when it is a thin passthrough that reimplements the ORM's API with worse ergonomics. The usual justification, swapping the database later, almost never happens; the real benefit is having one place where the queries live, so N+1 problems and missing indexes are findable.

Self-check

  1. Why does N+1 survive code review?
    Because the loop contains no SQL. o.customer.name is attribute access, syntactically identical to reading a field already in memory, and lazy loading makes it a network round trip instead. Reviewers see clean code, tests pass in milliseconds against three fixture rows, and the cost only appears when a real list has two hundred. The reliable defence is mechanical rather than human: assert that the query count does not grow with the number of records.
  2. Why is a JOIN the wrong way to eager-load two collections?
    Because joining two one-to-many relations produces their cartesian product. Twenty orders each with eight items and five tags returns 800 rows to convey 280 facts, and each row repeats the full order columns — so the bytes multiply worse than the row count. The ORM deduplicates it correctly in memory, which hides the problem entirely. Load collections with select-in, which issues one extra query per relation and returns each row once.
  3. Why does LIMIT 20 behave unexpectedly with a joined collection?
    Because the limit applies to the joined result rows, not to the parent entities. Twenty rows of an order-joined-items result might be three orders, so you get three orders rather than twenty. ORMs work around this by wrapping the parent query in a subquery and joining against that, which is why joined eager loading with a limit produces surprising SQL — and another reason select-in is the safer default for collections.
  4. You need to mark ten thousand rows as archived. Why is a loop of loaded objects wrong?
    Because it fetches ten thousand rows into memory, constructs ten thousand objects, tracks changes on each and issues ten thousand UPDATE statements — when the database can do the whole thing in one statement without materialising anything. Bulk work does not need objects. Use UPDATE … WHERE, and if the set is very large, batch it as chapter 8 describes so no single transaction holds locks for minutes.
  5. When should you drop to raw SQL?
    Reports and aggregations, anything with window functions, recursive CTEs, bulk operations, and any query where you have read the generated SQL and it is wrong. The ORM is genuinely good at loading and saving records, which is most of an application; it is poor at analytical queries, and fighting its API to express one costs more than writing the SQL. Mixing the two is normal practice, not a failure.
  6. What is the strongest argument for a repository layer, and the weakest?
    Strongest: it gives complex queries a domain-meaningful name and one home, so data access is findable, testable, and reviewable — which is where N+1 problems and missing indexes get spotted. Weakest: "so we can swap the database later", which essentially never happens and would not survive contact with engine-specific SQL anyway. If the repository is a thin passthrough that renames the ORM's methods, it is adding indirection without adding meaning.
