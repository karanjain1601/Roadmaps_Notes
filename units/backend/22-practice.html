The slow endpoint nobody can explain

  1. Confirm it is slow, and for whom. Look at p95 and p99, not the average, and check whether it is all users or one tenant with far more data than the rest.
  2. Find where the time goes before touching anything. A trace, or curl -w for the transport breakdown. The answer is rarely where you would guess.
  3. Count the queries. One request issuing two hundred is the single most common cause, and it is invisible in every metric except the query count.
  4. Read the plan for the slowest query. EXPLAIN (ANALYZE, BUFFERS). Look for a sequential scan with a selective filter, and for estimated rows disagreeing with actual by an order of magnitude.
  5. Check the queue, not just the work. If service time is 20 ms and latency is 200 ms, the request spent 180 ms waiting — for a connection, a worker or a lock.
  6. Look at what it calls. A dependency's p99 becomes your p99, and several in sequence add up. Is there a timeout at all?
  7. Only now consider the code. Serialisation of a large response, an accidental sort, a regex compiled per request.
  8. Fix one thing and measure again. Two changes at once means you learn nothing about either.

    Things worth building

    A URL shortener that survives

    Trivial to start and it touches everything: a hot read path that must be cached, an ID scheme that resists enumeration, rate limiting, analytics as an event stream, and a redirect budget measured in milliseconds. Take it to a thousand requests per second on one machine and you will have used chapters 9, 13, 15 and 19 in anger.

    A job queue you wrote yourself

    SELECT … FOR UPDATE SKIP LOCKED, visibility timeouts, retries with backoff, a dead-letter table, and idempotent handlers. A weekend's work, and afterwards every managed queue's documentation reads differently because you know what each option is protecting against.

    A multi-tenant API

    Where tenant isolation is structural rather than remembered — row-level security or a data layer that cannot issue an unscoped query. Then try to break it. This is chapter 14's hardest idea and the one most often got wrong in real systems.

    Something with an outbox

    Two services, one event, a deliberately unreliable broker, and a consumer you restart at random moments. Prove to yourself that no event is lost and none is applied twice. Chapter 18 becomes concrete in about an hour of doing this.

    Break your own system

    Add a proxy that injects 3-second delays into one dependency and watch chapter 19 happen live. Then add a timeout, then a breaker, then a fallback, measuring each time. This is the single most instructive afternoon in the unit.

    Instrument something properly

    OpenTelemetry traces, RED metrics, structured logs with trace ids, one SLO with a burn-rate alert. Then deliberately introduce an N+1 and find it from the trace alone. Chapter 20 is the hardest to appreciate without doing it.

    Where to go from here

    Read one book properly

    Kleppmann's Designing Data-Intensive Applications is the one. It goes deeper than this unit on every data topic and is worth a slow read rather than a skim.

    Go wider

    The System Design unit for what happens past one machine, DevOps for the infrastructure beneath all of this, and the Data Structures & Algorithms unit for the costs underneath the costs.

    Read production code

    Postgres's planner, Redis's eviction, an HTTP framework's routing. The structures in this unit make far more sense once you have seen them earning their keep in something that is deployed.

    Be on call

    Nothing teaches operability like owning the pager for a service you built. Every chapter in the last third exists because someone learned it that way.

    The short version of the whole unit
    1. Almost none of the difficulty is in the code you write.
    2. Measure before optimising; the time is never where you guess.
    3. The schema outlives the service. Constraints are guarantees; application checks are hopes.
    4. An index is the difference between two million rows and forty.
    5. The default isolation level prevents one of five anomalies. Know which four remain.
    6. Cache what is expensive, not what is frequent — and know your uncached numbers.
    7. Authenticate at the edge; authorize in the query.
    8. Every network boundary costs availability, latency and a new failure mode.
    9. Two writes to two systems are not atomic. Use an outbox.
    10. A timeout on every outbound call is the highest-value line of code in the unit.
    11. You cannot operate what you cannot see.
    12. Deploy small, deploy often, and make rollback one command.

    That is the unit. Twenty-two chapters, from a single request's waterfall to the pipeline that ships the change. The remaining distance is closed by building and operating something real, not by reading more chapters.
