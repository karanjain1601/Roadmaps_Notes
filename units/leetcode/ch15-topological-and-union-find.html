Ordering under dependencies

"Finish all the courses given their prerequisites" is asking for a topological order: a sequence where every edge points forwards. Kahn's algorithm produces one by repeatedly taking a node with nothing left blocking it.

Demo 1 — peel off the unblocked nodes

Each round takes every node whose in-degree has reached zero. The result is checked edge by edge.

Kahn's algorithm
indeg[v] = number of edges INTO v
queue = every node with indeg 0

while (queue not empty) {
    u = queue.pop()
    order.push(u)
    for (v of adj[u])
        if (--indeg[v] === 0) queue.push(v)
}

if (order.length < n) // everything left is inside a cycle
Ordering and cycle detection are the same algorithm

If Kahn's emits fewer than n nodes, every node it could not reach has an unresolved prerequisite — which means it sits in or behind a cycle. You get the order and the cycle check from one pass, and Course Schedule I (can it be done?) and II (in what order?) are literally the same code with a different return statement.

Verified on 2,000 random DAGs: every order produced respects every edge.

Why cycle detection needs three colours

The DFS alternative to Kahn's is to look for a back edge. The version everyone writes first uses a single visited set, and it is wrong.

The diamond breaks it

Take 0→1, 0→2, 1→3, 2→3. Depth-first from 0: visit 1, visit 3, come back, visit 2, and 2 points at 3 — which is already in the visited set. A single-colour check calls that a cycle. There is no cycle: 3 was finished, not on the current path.

Across 3,000 random directed graphs the two-colour version disagrees with the truth on 1,828 of them — 61%. Every single error is a false cycle; it never misses a real one, which is exactly why the bug survives: the code looks conservative and is in fact useless.

the three states, and what each means
WHITE — not visited yet
GREY  — on the current recursion path
BLACK — fully explored, and everything below it too

go(u):
    colour[u] = GREY
    for (v of adj[u]) {
        if (colour[v] === GREY)  return true     // back edge: a real cycle
        if (colour[v] === WHITE && go(v)) return true
    }                                        // BLACK is fine — already done
    colour[u] = BLACK
    return false

The three-colour version is correct on all 3,000. In practice Kahn's count is simpler still and needs no colours at all — so reach for the DFS version only when you also need the order the recursion produces.

One thing this does not transfer to: in an undirected graph the same "already visited" encounter is normal, because every edge appears in both directions. There the fix is to skip the edge you arrived on, and chapter 14's component traversal already does exactly that.

Union-find

A forest where each tree is one connected component. find(x) walks to the root; union(a, b) points one root at the other. Two elements are connected exactly when they share a root.

Unioning 0–1, then 1–2, then 2–3 with no rank builds a linked list 19,999 deep, and every subsequent find walks the whole thing. Either optimisation collapses it: union by rank never puts a taller tree under a shorter one, and path compression flattens every path it walks.

Compression costs more hops than rank, and is still worth it

Path compression measures 59,995 hops against union by rank's 19,999 — three times more, which surprised me. The reason is that compression walks each path twice: once to find the root and once to rewrite the pointers behind it. That is a one-off cost that makes every later find on those elements free, so the extra hops here are an investment the single measured pass does not get to recover.

Together the two give the famous inverse-Ackermann bound — effectively constant for any input that fits in a computer. In an interview, implement both and say that; implement neither and a chained input is quadratic.

Verified against BFS component counts on 2,000 random graphs.

The one-line idiom

union returning false IS cycle detection
for ([a, b] of edges)
    if (!union(a, b)) return [a, b]     // they were already connected

// on [[1,2],[1,3],[2,3]] this returns [2,3] — the edge that closes
// the cycle. it is also how Kruskal's algorithm rejects edges.

That is the whole of Redundant Connection, and it is the reason union-find appears in minimum-spanning-tree algorithms: an edge is safe to add exactly when its endpoints are in different components.

What union-find can and cannot do
CanCannot
Answer "are these connected" in near-constant timeList a component's members without a full pass
Merge components incrementallyRemove an edge
Count components as edges arriveGive you distances or paths

The middle row is the real constraint. Union-find is incremental only — the structure has no way to undo a merge. A problem that removes edges over time is usually solved by running it backwards, processing removals in reverse as additions, which is the trick behind problems like Last Day Where You Can Still Cross.

Choosing between them

Three tools, three situations
SituationUse
Directed dependencies, an ordering is requiredTopological sort
Directed, only "is it possible"Topological sort, and check the count
Undirected, edges arriving over time, many queriesUnion-find
Undirected, one pass over a fixed graphJust BFS or DFS

The last row matters because union-find is over-applied. Counting islands once on a static grid does not need it — chapter 14 measured DFS, BFS and union-find as equivalent there, and the traversal is shorter to write. Union-find pays off when connectivity queries are interleaved with edge additions, so no single traversal can answer them all.

Check yourself

How does Kahn's algorithm detect a cycle?

By counting. It repeatedly emits nodes whose in-degree has reached zero; if it emits fewer than n, every node left has an unresolved prerequisite, which means it sits in or behind a cycle. That makes ordering and cycle detection literally the same pass — Course Schedule I and II differ only in what they return. No colours, no recursion, no stack depth to worry about.

Why does a single "visited" set fail for directed cycle detection?

Because re-encountering a visited node is not the same as finding a cycle. On the diamond 0→1, 0→2, 1→3, 2→3, depth-first from 0 reaches 3 via 1, backtracks, then reaches 3 again via 2 — and a one-colour check calls that a back edge. There is no cycle; 3 was finished, not on the current path. Measured on 3,000 random directed graphs, the two-colour version is wrong on 1,828 of them, 61%.

All the two-colour errors are false positives. Does that make it safe?

No — it makes it useless while looking conservative. A checker that never misses a real cycle but invents one 61% of the time rejects almost every valid input. And the failure mode is the wrong way round for intuition: people assume a too-eager cycle detector is "erring on the safe side", when in a scheduling problem it means refusing to run a schedule that is perfectly fine. The fix is one extra state: grey for on-the-current-path, black for finished.

What does naive union-find cost on a chained input?

Quadratic. Unioning 0–1, then 1–2, then 2–3 with no rank builds a linked list — 20,000 elements gives a tree 19,999 deep — and one find per element then costs 199,990,000 pointer hops. Either optimisation collapses it: union by rank never puts a taller tree under a shorter one, path compression flattens every path it walks, and both bring the same workload under 60,000 hops with a depth of 1.

Path compression measured more hops than union by rank. Is it worse?

No — 59,995 against 19,999 on that measurement, three times more, because compression walks each path twice: once to find the root and once to rewrite the pointers behind it. That is a one-off investment that makes every later find on those elements free, and a single measured pass does not get to recover it. Over a realistic workload with repeated queries the ordering reverses. Implement both; together they give the inverse-Ackermann bound, which is effectively constant.

What can union-find not do?

Remove edges. The structure merges and has no way to undo a merge, so it is incremental only — a problem that deletes edges over time is normally solved by processing it backwards, turning removals into additions. It also cannot list a component's members without a full pass, and it gives no distances or paths. If you need "how far apart are these", you need BFS, not union-find.

Counting islands on a static grid. Union-find?

No — just DFS or BFS. Chapter 14 measured all three as equivalent for counting components, and the traversal is shorter to write with no auxiliary structure. Union-find earns its place when connectivity queries are interleaved with edge additions, so that no single traversal can answer them all: "after each of these connections, how many components are there?" is its problem, and "how many are there now" is not.

Ten things to carry forward

  1. Kahn's peels off nodes with no remaining prerequisites, one round at a time.
  2. Emitting fewer than n nodes is exactly a cycle, so ordering and detection are one pass.
  3. Directed cycle detection needs three colours. Grey is on the path; black is finished.
  4. Two colours is wrong on 61% of directed graphs, always with a false cycle.
  5. In an undirected graph the fix is different — skip the edge you arrived on.
  6. Naive union-find is quadratic on a chain — 199,990,000 hops and a depth of 19,999.
  7. Either optimisation collapses it; both together are effectively constant.
  8. Compression costs more hops up front because it rewrites the path it walked.
  9. union() returning false is cycle detection for undirected graphs, in one line.
  10. Union-find cannot remove edges, so run those problems backwards in time.
