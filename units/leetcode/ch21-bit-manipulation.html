Bit manipulation

Enumerating every submask of every mask over n bits takes exactly 3n steps — not approximately, exactly. There is a one-line reason, and knowing it turns a family of problems from intractable into routine.

XOR, and why it cancels

Three properties, verified on thousands of random values: x ^ x === 0, x ^ 0 === x, and XOR is commutative and associative.

Together they mean order does not matter and duplicates vanish

Fold XOR across an array where every value appears twice except one, and the pairs annihilate regardless of how they are arranged — leaving the lone value. Verified on 3,000 shuffled inputs, in Θ(1) space where a hash map needs Θ(n).

Missing Number also has a sum-formula solution, and both agree on 2,000 random inputs. The XOR version has one concrete advantage: the sum can overflow a fixed-width integer and the XOR never can, because it never grows.

Counting set bits, three ways

Brian Kernighan's trick
while (n) { n &= n - 1; count++ }

// subtracting 1 flips the lowest set bit to 0 and everything below
// it to 1. ANDing clears exactly that bit and leaves the rest alone,
// so the loop runs once per SET bit rather than once per position.

Verified on 2,000 random values: the loop count equals the population count exactly, while the shift-and-test loop runs once per bit position. On 2³⁰ the naive loop runs 31 times and Kernighan's runs once.

And a third way, which is chapter 18 in disguise

For "count the bits in every number from 0 to n", the answer is dp[i] = dp[i >> 1] + (i & 1) — one operation per value, because i >> 1 has already been computed. Verified against a reference for all 100,001 values up to 100,000.

That is overlapping subproblems arriving in a bit-manipulation costume: i and i>>1 share all but one bit, so the work is shared too.

Subsets by counting, and submasks in 3n

Chapter 17 enumerated subsets by recursion. There is a shorter way: count from 0 to 2n−1 and read each integer's bits as a membership vector. No recursion, no unchoose step, and it is trivially resumable.

for (s = mask; ; s = (s - 1) & mask) {
    use(s)
    if (s === 0) break
}
// (s-1) borrows through the zero bits and the & mask discards them,
// so it lands on the next smaller submask every time.
Exactly 3n, and here is why

Summed over every mask, the loop takes 3n steps — measured as 27, 729, 19,683 and 531,441 for n = 3, 6, 9 and 12, which are 3³, 3⁶, 3⁹ and 3¹².

The reason is one sentence: each bit is independently in both mask and submask, in the mask only, or in neither — three states per bit, so 3n (mask, submask) pairs, and the loop visits each exactly once.

The naive alternative — testing every candidate against every mask — is 4n. At n = 12 that is 16,777,216 against 531,441, a 32-fold gap that grows as (4/3)n.

This is what makes set-partition DP feasible: iterating over all splits of all subsets is 3n, not 4n, which is the difference between n = 16 being fine and being hopeless.

Bitmask DP

When the DP state is "which subset have I used", the subset is an integer. That is the whole idea, and it turns a factorial search into an exponential one.

Travelling salesman with dp[mask][last], verified against exhaustive permutation search on 200 random graphs. At 10 cities the DP does 9,225 transitions and brute force evaluates 362,880 tours — a 39-fold reduction. The formulas say 2n·n² against n!, which at n = 15 is a factor of 177,365.

The practical consequence: masks above 31 bits need BigInt or a pair of numbers, and >>> is what you want when treating a value as an unsigned bit pattern.

Precedence: & binds looser than ===

x & 1 === 1 parses as x & (1 === 1). It compiles, it runs, and it returns a number where you expected a boolean — for x = 5 it gives 1 rather than true. Always write (x & 1) === 1.

This one is worth flagging because it does not throw, and in a truthiness context it usually produces the right answer anyway — until the day a value's low bit is 0 and you compare the result against true.

Check yourself

Which three XOR properties make Single Number work?

x ^ x === 0, x ^ 0 === x, and commutativity with associativity. Together they mean the order of a XOR fold is irrelevant and every duplicated value annihilates itself — so folding across the array leaves exactly the value that appears once, regardless of how the input is shuffled. Verified on 3,000 shuffled inputs, in Θ(1) space where a hash map needs Θ(n).

Missing Number has a sum solution and an XOR solution. Any reason to prefer one?

Both are one pass and both agree on 2,000 random inputs. The XOR version has one concrete advantage: the sum can overflow a fixed-width integer for large n, and XOR never can, because it never grows beyond the width of its inputs. In a language with 32-bit integers that is a real constraint rather than a stylistic preference.

Why does n &= n - 1 count set bits faster?

Because subtracting 1 flips the lowest set bit to 0 and everything below it to 1; ANDing then clears exactly that bit and leaves the rest alone. So the loop runs once per set bit rather than once per bit position — verified on 2,000 random values, where the loop count equals the population count exactly. On 2³⁰ the naive shift loop runs 31 times and Kernighan's runs once.

Why is submask enumeration exactly 3n and not approximately?

Because each of the n bits is independently in one of three states across a (mask, submask) pair: in both, in the mask only, or in neither. That gives 3n pairs, and the loop visits each exactly once. Measured: 27, 729, 19,683 and 531,441 for n = 3, 6, 9 and 12 — 3³, 3⁶, 3⁹ and 3¹². The naive alternative of testing every candidate against every mask is 4n, a gap growing as (4/3)n.

When should the DP state be a bitmask?

When the state is "which subset have I used" — because a subset is an integer. TSP with dp[mask][last] does 9,225 transitions at 10 cities where brute force evaluates 362,880 tours, and the formulas 2n·n² against n! give a factor of 177,365 at n = 15. Chapter 1's table points here directly: n ≤ 20 with a set-shaped state, because 2²⁰ is a million and 20! is not iterable.

What is 1 << 31 in JavaScript?

−2147483648, because bitwise operands coerce to 32-bit signed integers. Related: 1 << 32 is 1, since the shift count is taken mod 32; −8 >> 1 is −4 because arithmetic shift preserves the sign; and −8 >>> 1 is 2147483644 because logical shift fills with zeros. Masks above 31 bits need BigInt or a pair of numbers, and >>> is what you want for unsigned bit patterns.

What does x & 1 === 1 evaluate to?

Not what you meant. & binds looser than ===, so it parses as x & (1 === 1) — for x = 5 that is 1, a number rather than a boolean. It compiles, it runs, it does not throw, and in a truthiness context it often produces the right answer anyway, which is what makes it dangerous. Always write (x & 1) === 1.

Ten things to carry forward

  1. XOR cancels duplicates in any order — three properties, one Θ(1)-space trick.
  2. XOR cannot overflow; the sum-formula alternative can.
  3. n & (n-1) clears the lowest set bit, so Kernighan's loop runs once per set bit.
  4. n & -n isolates it, which is how you partition on a differing bit.
  5. The power-of-two test needs n > 0, or zero passes.
  6. Counting bits 0..n is dp[i>>1] + (i&1) — overlapping subproblems in disguise.
  7. Submask enumeration is exactly 3n, because each bit has three states.
  8. That beats the naive 4n by (4/3)n — 32× at twelve bits.
  9. A subset is an integer, which is what makes bitmask DP work at n ≤ 20.
  10. JavaScript's bitwise ops are 32-bit signed, and & binds looser than ===.
