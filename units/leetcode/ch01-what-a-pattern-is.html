Chapter 1 · Recognising the shape

What a coding pattern is

"Find two numbers that sum to a target" and "find two numbers in a sorted array that sum to a target" are different questions with different answers. One word moved the solution from Θ(n) extra space to Θ(1). Reading for words like that one is the whole skill.

Why the problems repeat

An interviewer has forty-five minutes and needs a problem with a clean brute-force solution, a clean optimal solution, and a gap between them that can be reasoned about out loud. That is a narrow specification, and it does not admit many distinct answers.

So the same twenty or so structures come round again and again, dressed differently. A problem about scheduling meetings, a problem about merging DNA read ranges and a problem about CPU time slices are the same interval problem. Recognising that is not a trick; it is the thing being tested.

A pattern is a triple

Not just an algorithm. A pattern is a recognisable signal in the problem statement, a template that solves it, and a complexity you can state before writing code. Learning the template alone is what produces the candidate who can write a sliding window perfectly and cannot tell when a problem wants one.

Reading for signals

A signal is a phrase that constrains which pattern can apply. Some rule things in, some rule things out, and the useful ones do both.

Try the first two presets in order. "Find a pair summing to a target" alone leaves a genuine tie between a hash map and two pointers, and both are correct — the hash map is Θ(n) time and Θ(n) space, two pointers needs a sort. Add "the array is sorted" and two pointers pulls ahead, because the sort is already paid for and the space drops to Θ(1). One adjective, a different answer.

The most valuable word in the language: contiguous

"Contiguous subarray" and "subsequence" look almost the same and share no candidate patterns at all. Contiguous means a window can slide, so you are in sliding-window or prefix-sum territory at Θ(n). A subsequence may skip elements, so there are 2n of them and you are almost certainly in dynamic programming. Misreading this one word sends you to the wrong half of the unit, and it is the single most common misread there is.

Notice too that "contiguous" alone is ambiguous — the demo ties sliding window with prefix sums. It takes a second signal to break it: "longest range satisfying a condition" picks sliding window, and "sums to exactly k" picks prefix sums. Genuine ambiguity is information, not a failure of the method; it tells you which further question to ask the interviewer.

The constraints are a hint, and they are not subtle

Every problem states its input bounds. Most candidates skip them. They are, in practice, the interviewer telling you the intended complexity.

Read the table in reverse and it becomes a diagnostic. If n ≤ 20, an exponential search is not a fallback, it is the plan — stop trying to find a polynomial algorithm that probably does not exist. If n is a billion, no algorithm that touches every element can pass, so the answer is binary search or closed-form arithmetic, and you should be looking for the monotonic property rather than the clever loop.

Say the budget out loud

"n is up to 10⁵, so I'm aiming for n log n or better" is one sentence, takes four seconds, and does three things: it shows you read the constraints, it commits you to a target that rules out the wrong approaches, and it invites the interviewer to correct you before you have written anything. Candidates who do this almost never spend twenty minutes optimising an approach that was never going to fit.

Hard problems are two patterns, not one exotic one

Load the Word Search II preset in demo 1 and the classifier returns three candidates rather than a winner: graph traversal, a trie, and dynamic programming. That is not the table failing. The problem genuinely needs a backtracking search over a grid with a trie pruning it, and the reason it is rated hard is precisely that it is two patterns composed.

It also explains why grinding hard problems before the easy ones does not work — the composition is unlearnable until the components are automatic.

Always start from brute force

The instinct under pressure is to reach for the clever answer immediately. That is backwards, for four reasons that all pay off in the room.

  1. It is always available. A working Θ(n²) beats a broken Θ(n), and interviewers say so explicitly.
  2. It defines the target. "This is Θ(n²); the constraints want n log n; so I need to remove a factor of n" turns a vague search into a specific one.
  3. The optimisation is usually visible from it. Look at what the brute force recomputes. Recomputing a sum over a shifting range is a sliding window. Recomputing the same subproblem is memoisation. Rescanning for a value you have seen is a hash map.
  4. It is the oracle. Chapter 2 makes this concrete: the brute force is what you test the fast version against, and every demo in this unit does exactly that.
the same problem, brute force then optimised — and what changed
// brute force: for each i, scan the rest for the complement
for (i = 0; i < n; i++)
    for (j = i+1; j < n; j++)
        if (a[i] + a[j] === target) return [i, j]      // Θ(n²)

// what is being recomputed? the inner loop re-asks "have I seen
// target - a[i] anywhere?" — a membership question, over and over.
// a membership question with a fast answer is a hash set.

seen = {}
for (i = 0; i < n; i++) {
    if (seen.has(target - a[i])) return [seen.get(target - a[i]), i]
    seen.set(a[i], i)                                    // Θ(n)
}

That question — what is the inner loop recomputing? — resolves a surprising fraction of optimisation steps in this unit. It is the closest thing to a general method that exists here.

The goal is a named reflex

You are not trying to memorise solutions. You are trying to reach the point where "return all valid combinations" produces the thought backtracking, choose-explore-unchoose, prune on the constraint before you have consciously decided anything. Chapter 2 is about how that reflex is actually built, and the answer is not "do more problems".

Check yourself

A problem says "find a pair summing to a target". What do you need to know next?

Whether the array is sorted, and whether you may modify it. Unsorted, the answer is a hash map: one pass, Θ(n) time and Θ(n) space. Sorted, two pointers from the ends is Θ(n) time and Θ(1) space. If it is unsorted but you may sort it, you are choosing between Θ(n) time with extra space and Θ(n log n) time with none — a real trade the interviewer probably wants you to name. The demo shows this as a genuine tie that one adjective resolves.

Why is "contiguous" the most important word in a problem statement?

Because it decides which half of the unit you are in, and the two halves share no candidate patterns. Contiguous means the elements are adjacent, so a window can slide and you are looking at sliding window or prefix sums, typically Θ(n). A subsequence may skip elements, so there are 2n candidates and you are in dynamic programming, typically Θ(n²) or worse. "Longest increasing subarray" and "longest increasing subsequence" are one word apart and completely different problems.

The constraints say n ≤ 20. What does that tell you?

That an exponential solution is intended. 2²⁰ is about a million operations, which is instant; 2⁴⁰ would not be. When n is capped at 20 or so, the interviewer is signalling subsets, bitmasks or permutation search, and time spent hunting for a polynomial algorithm is usually time spent looking for something that does not exist — several of these problems are NP-hard in general. Small bounds are permission, not a warning.

n can be 10⁹. What is ruled out, and what does that leave?

Everything that touches each element is ruled out, including Θ(n) — a billion operations will not fit a one-second budget, and the input could not even be transmitted. That leaves Θ(log n) or Θ(1): binary search over the answer space, closed-form arithmetic, or a mathematical property. The tell is that the input is usually not an array at all but a few numbers describing one, which is itself the hint. Chapter 8 is where this becomes concrete.

Why start with brute force when you can already see the optimal answer?

Four reasons, and the third is the one people miss. It guarantees you have something working; it fixes the target by making the current complexity explicit; it shows you what to optimise, because the improvement is almost always "stop recomputing this"; and it gives you an oracle to test against. Stating the brute force takes thirty seconds and costs nothing — and if you cannot state one, you have not understood the problem yet, which is much better to discover at minute two than at minute thirty.

The classifier returns three patterns with equal scores. Has it failed?

No — that is information. Sometimes the problem is genuinely ambiguous and the tie tells you exactly which clarifying question to ask: "contiguous" alone ties sliding window with prefix sums, and asking whether you need the longest range satisfying a condition or a range summing to exactly k resolves it. Other times, as with Word Search II, the answer is that you need both patterns composed. Hard problems are usually two ordinary patterns together rather than one exotic one.

You recognise the pattern immediately. What should you do first?

Still restate the problem and confirm the edge cases — empty input, one element, duplicates, negative numbers, whether the input may be modified. Jumping straight to the template looks impressive for about ninety seconds and then costs you when it turns out duplicates were allowed and your set-based approach silently drops them. The pattern tells you the shape of the solution; the clarifications tell you which variant of it, and they take one minute against the twenty a wrong assumption costs.

Ten things to carry forward

  1. Interview problems repeat because the format is narrow, not because the field is small.
  2. A pattern is a signal, a template and a complexity — learning only the template is what leaves you unable to recognise it.
  3. Signals constrain. "Sorted" turns a hash-map problem into a two-pointer one and drops the space to Θ(1).
  4. "Contiguous" and "subsequence" share no patterns. One word, opposite halves of the unit.
  5. Ambiguity is information. A tie in the candidates tells you which question to ask next.
  6. The constraints state the intended complexity. n ≤ 20 means exponential is the plan.
  7. Say the budget out loud before writing anything — it takes four seconds and prevents the twenty-minute mistake.
  8. Hard problems are two patterns composed, which is why the components have to be automatic first.
  9. Start from brute force, then ask what the inner loop is recomputing. That question drives most optimisations here.
  10. The goal is a named reflex, not a memorised solution set.
