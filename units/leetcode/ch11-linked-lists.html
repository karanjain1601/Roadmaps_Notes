Linked lists and fast-slow pointers

Two pointers walk a list, one twice as fast. When they meet, that node is not where the cycle starts — and the distance from it back to the start happens to equal the distance from the head. That coincidence has a one-line proof and is the whole trick.

What you get and what you lose

Linked lists appear in interviews far more than in production code, and it is worth being clear about why: they are a pointer-manipulation exercise. The problems test whether you can hold three references straight in your head, not whether you know a fast data structure.

Why it works: every node gets a predecessor

Deleting a node means rewriting its predecessor's pointer, and the head is the one node that has none. A dummy gives it one. Removal at the front, in the middle, at the end, of every element, and from an empty list all become the same three lines.

Measured across 3,000 random removals: the dummy version executes zero head-handling branches and the version without executes 826. Both are correct — the difference is entirely in how many ways there are to get it wrong.

Use it whenever the head might change: removal, merging two lists, partitioning, inserting before the first element, removing the nth from the end. If you find yourself writing if (head === null) as the first line of a list function, a dummy probably deletes that line and two others.

Reversal, and the pointer you must save

the three-pointer dance
prev = null, cur = head
while (cur) {
    next = cur.next        // SAVE first — the next line destroys it
    cur.next = prev        // flip
    prev = cur             // advance
    cur = next
}
return prev                // cur is null; prev is the new head

Line one is the whole difficulty. Overwrite cur.next before saving it and the pointer you needed to walk forward along has already been redirected backwards — the loop runs once and returns a one-element list, silently discarding the rest.

Verified against an array reverse on 2,000 random lists, and it takes exactly n steps with Θ(1) extra space.

Which middle?

The fast-slow pair also finds the middle, and the initialisation decides which middle on an even-length list.

Verified on every length from 1 to 12. For splitting a list you usually want fast = head.next, so that the left half is the shorter one and mid.next cleanly begins the right half. Choosing the other one is an off-by-one you will discover three functions later.

Floyd's algorithm, and the part everyone gets wrong

Move slow one step and fast two. If there is a cycle, fast gains one position per step on slow inside it, so it must eventually land exactly on it. If there is no cycle, fast falls off the end. That part is easy.

The meeting point is not the cycle start

With a tail of 3 and a cycle of 5, the pointers meet at node 5 and the cycle begins at node 3. Returning the meeting point is the single most common bug in this problem, and it passes any test where the tail happens to be empty — because then, and only then, the two coincide.

phase two, and why three lines find the entrance
a = head, b = meetingPoint
while (a !== b) { a = a.next; b = b.next }
return a

// let T = tail length, C = cycle length. slow walked T + k steps,
// fast walked 2(T + k), and fast is exactly one lap ahead:
//     2(T + k) - (T + k) = mC     so     T + k = mC
// the distance from the meeting point onward to the entrance is
// C - k, and (T + k) mod C = 0 means C - k = T mod C.
// so both pointers need T steps. they arrive together.

Checked exhaustively on all 168 combinations of tail length 0–12 and cycle length 0–12: Floyd agrees with a visited-set on every one, the entrance step lands on the true start every time, and the meeting point sits at index T + ((C − T mod C) mod C) exactly as the algebra predicts.

The point is the memory

A visited-set finds cycles in three lines and is easier to write. On 100,000 nodes it holds 100,000 node references; Floyd holds two. That is the entire reason the harder algorithm exists, and it is the same shape of argument as chapter 10's heap merge — a space result, not a speed one. If the interviewer has not said "O(1) space", offer the set first and then the improvement.

Check yourself

What does a dummy head actually buy?

A predecessor for the head. Deleting a node means rewriting its predecessor's pointer, and the head is the one node without one — so every list function that might remove or replace the first element needs special handling for it. A dummy makes removal at the front, in the middle, at the end, of everything, and from an empty list all the same three lines. Measured over 3,000 random removals: zero head-handling branches with a dummy, 826 without. Both versions are correct; the difference is how many ways there are to get it wrong.

Why must you save cur.next before flipping the pointer?

Because the flip destroys it. cur.next = prev overwrites the only reference you have to the rest of the list, so if you have not saved it you cannot advance. The loop runs exactly once and returns a one-element list, silently discarding everything else. That is why the reversal is a three-pointer dance rather than two: prev, cur, and a temporary next whose entire purpose is to survive the assignment on the line below.

fast = head or fast = head.next?

It decides which middle you get on an even-length list. fast = head lands on index ⌊n/2⌋ — the second middle, 3 in [1,2,3,4]. fast = head.next lands on ⌊(n−1)/2⌋ — the first, 2. On odd lengths they agree. For splitting a list you usually want the first middle, so the left half is the shorter one and mid.next cleanly starts the right half. Picking the other is an off-by-one you discover three functions later.

Why is Floyd's meeting point not the cycle entrance?

Because the pointers meet wherever fast happens to catch up, which depends on both the tail and cycle lengths. With tail 3 and cycle 5 they meet at node 5 while the cycle starts at node 3. The meeting point sits at index T + ((C − T mod C) mod C), verified across all 168 tail/cycle combinations. Returning it as the answer is the most common bug in the problem, and it passes any test with an empty tail — the one case where they coincide.

Why does resetting one pointer to the head find the entrance?

Let T be the tail length and C the cycle length. Slow walked T + k steps to the meeting point and fast walked twice that, with the difference being whole laps: 2(T+k) − (T+k) = mC, so T + k is a multiple of C. The remaining distance from the meeting point round to the entrance is C − k, which therefore equals T mod C. Both pointers need T steps, so moving them one at a time from the head and from the meeting point makes them arrive together.

A visited-set finds cycles in three easy lines. Why bother with Floyd?

Memory. On 100,000 nodes the set holds 100,000 references and Floyd holds two pointers. That is the entire justification — the same shape of argument as chapter 10's k-way merge, where the naive method was faster and held 500× more. If the interviewer has not required O(1) space, offer the set first, state that it is Θ(n) memory, and then present Floyd as the improvement. That sequence demonstrates more than jumping straight to the clever answer.

Your palindrome check works. What is still wrong with it?

It probably left the caller's list reversed from the middle onwards. Reversing the second half in place is what makes the check Θ(1) space, and most published solutions stop once they have the answer — leaving a mangled list behind. Reversing it back costs three lines and one more pass. It matters because a function that silently destroys its input is a bug even when its return value is right, and saying so unprompted in an interview is a cheap way to demonstrate care.

Ten things to carry forward

  1. Linked-list problems test pointer manipulation, not knowledge of a fast structure.
  2. A dummy head gives the head a predecessor, and every edge case disappears with it.
  3. 826 special-case branches against zero, for one line and one allocation.
  4. Save cur.next before flipping, or the loop runs once and loses the list.
  5. fast = head gives the second middle; fast = head.next gives the first.
  6. Use while (fast && fast.next), in that order, or you dereference null.
  7. The meeting point is not the cycle entrance unless the tail is empty.
  8. Reset one pointer to the head and step both — they meet at the entrance, and there is a proof.
  9. Floyd exists for the memory: two pointers against 100,000 set entries.
  10. Restore what you reversed. A correct return value from a function that mangles its input is still a bug.
