The condition: overlapping subproblems

Chapter 17 ended by saying that if n is large you are in the wrong chapter. This is the right one, and the precise condition is that the recursion tree revisits the same subproblem on different branches.

At n = 30 the naive recursion makes 2,692,537 calls and the memoised version makes 59 — a 45,636-fold reduction. The naive count follows 2·fib(n+1)−1 exactly; the memoised one follows 2n−1.

Backtracking's tree branches; DP's tree overlaps

That is the whole distinction. Chapter 17's subsets never revisit a subproblem — each branch explores a genuinely different set of choices, so there is nothing to cache and the exponential cost is irreducible. Here fib(20) is computed thousands of times, and caching it collapses the tree into a line.

The diagnostic when you are stuck: draw two levels of the recursion tree and look for a repeated argument. If you find one, memoise. If every node is distinct, you are backtracking and the constraints had better be small.

The state sentence

Write down what dp[i] means, in one English sentence, before writing any code.

That sentence is the algorithm. Once it is precise the recurrence follows mechanically, and if you cannot write it precisely the recurrence will be wrong in a way that is hard to debug.

LIS is the one where the natural sentence — "the longest increasing subsequence in the first i elements" — produces a recurrence you cannot write, because knowing the best length so far tells you nothing about whether the next element can extend it. Pinning the state to sequences ending at i makes the recurrence possible, at the cost of needing a final max over the whole table.

When a recurrence refuses to come out, the state is usually the problem, not your algebra.

House Robber verified against exhaustive search over all non-adjacent subsets on 3,000 random inputs. On 100,000 houses it does 100,000 operations in Θ(1) space.

Write the memoised version first — it is the recurrence with a cache bolted on, so it is the one you can derive under pressure. Convert to tabulation if the recursion depth is a problem, and roll the array only once it works and only if the space matters.

The rolling cut is available whenever the recurrence reaches back a fixed distance. Fibonacci and House Robber need two previous values, so the table collapses from n+1 slots to 2. What you lose is the ability to reconstruct which houses were robbed — the table is the record, and discarding it discards the path.

Why not greedy?

Coin Change is the standard demonstration. With coins 1, 2 and 5, taking the largest first is optimal and the DP is unnecessary. With coins 1, 3, 4 it is not: greedy makes 6 as 4+1+1, three coins, where 3+3 needs two.

Across the first 100 amounts with those coins, greedy is wrong on 24 of them.

The coin system decides, not the algorithm

Greedy works for coin systems with a particular structure — real currencies are designed to have it — and fails for systems that do not. An interviewer choosing 1, 3, 4 is choosing a system without it, deliberately. Since you cannot tell by looking, and the DP is six lines, take the DP.

Chapter 20 covers the exchange argument that would let you prove a greedy correct. Absent that proof, the measured 24% failure rate is what you are gambling on.

One thing worth noticing about the DP's cost: with amount 100,000 and three coins it does 300,000 operations — amount × coins. That is linear in the target value, not in the input size, which is the pseudo-polynomial behaviour that makes Coin Change tractable at amount 10⁴ and hopeless at amount 10⁹.

The loop-order trap

"How many ways can you make amount n?" has two nested loops, and their order silently decides which question you answered.

the same four lines, in two orders
// coins OUTER -> combinations. each coin is fully considered before
// the next, so a multiset is built in one fixed order only.
for (coin of coins)
    for (a = coin; a <= amount; a++) dp[a] += dp[a - coin]

// amount OUTER -> permutations. every coin is tried at every amount,
// so 1+2 and 2+1 are reached separately.
for (a = 1; a <= amount; a++)
    for (coin of coins) if (coin <= a) dp[a] += dp[a - coin]
Coins 1, 2, 5 making 5
Loop orderCountsAnswer
Coins outerCombinations — order ignored4
Amount outerPermutations — order matters9

The four combinations are 5, 1+1+1+2, 1+2+2 and 1+1+1+1+1. The nine permutations are the same multisets, but 1+2+2, 2+1+2 and 2+2+1 now count separately. Both loop orders were verified against exhaustive counts on 2,000 random inputs, and they disagree on 1,113 of 2,000.

Both answers are plausible positive integers

Nothing errors, nothing looks suspicious, and the number you get is a perfectly reasonable count of something. This is the same failure profile as the unit's preconditions, arriving from a new direction: not a missing check, but two indistinguishable-looking lines that mean different things.

The fix is the state sentence again. "Ways to make amount a using only the first k coin types" is a two-dimensional state that the coins-outer loop collapses correctly; "ways to make amount a" with no coin restriction is the permutation count. Decide which one the problem wants before writing the loops.

When the DP is not the best algorithm

Longest Increasing Subsequence has the clean Θ(n²) DP in the table above, and a Θ(n log n) alternative that is not a DP at all: maintain an array of the smallest possible tail for each length, and binary-search each new value into it.

On 5,000 values the quadratic DP does 12,497,500 operations and patience with binary search does 31,935 — a 391-fold reduction. Both match brute force on 2,000 random inputs.

The tails array is not the subsequence

Patience gives the correct length, and its tails array is very often not a valid increasing subsequence of the input at all — it is a record of the best tail seen per length, assembled from different positions. Reconstructing the actual sequence needs predecessor links threaded through, which the quadratic DP has for free in its table.

So the choice is not simply "faster is better". If the problem asks for the length, take patience. If it asks for the subsequence, the quadratic version is less work overall.

Check yourself

What exactly distinguishes a DP problem from a backtracking problem?

Whether the recursion tree revisits the same subproblem on different branches. Chapter 17's subsets never do — each branch explores a genuinely different set of choices, so there is nothing to cache and the exponential cost is irreducible. Fibonacci recomputes fib(20) thousands of times, and caching collapses 2,692,537 calls into 59. The diagnostic is to draw two levels of the tree and look for a repeated argument.

What should you write before any code?

The state sentence: what dp[i] means, in one precise English sentence. That sentence is the algorithm — once it is exact the recurrence follows mechanically, and if you cannot state it precisely the recurrence will be wrong in a way that is hard to debug. When a recurrence refuses to come out, the state is almost always the problem rather than the algebra.

Why is LIS's state "ending at i" rather than "in the first i"?

Because the natural sentence produces a recurrence you cannot write. Knowing the longest increasing subsequence among the first i elements tells you nothing about whether element i+1 can extend it — you would need to know what that subsequence ends with. Pinning the state to sequences ending at i makes the recurrence possible, at the cost of a final max over the whole table rather than reading dp[n−1].

Memoisation, tabulation or rolling array?

Write the memoised recursion first — it is the recurrence with a cache bolted on, so it is the version you can derive under pressure, and it only computes states you actually need. Convert to tabulation if recursion depth is a concern or the iteration order is clearer that way. Roll the array only once it works and only if the space matters, because rolling discards the table and with it the ability to reconstruct which choices produced the answer.

Coins 1, 3, 4 making 6. Greedy or DP?

DP. Greedy takes 4+1+1 for three coins where 3+3 needs two, and across the first 100 amounts with those coins it is wrong on 24. Greedy works only for coin systems with a particular structure — real currencies are designed to have it, and an interviewer picking 1, 3, 4 is deliberately picking one that does not. You cannot tell by looking, the DP is six lines, and chapter 20's exchange argument is what a proof would require.

Two nested loops, coins and amounts. Does the order matter?

Enormously. Coins outer counts combinations — each coin is fully considered before the next, so a multiset is built in one fixed order — and gives 4 for coins 1, 2, 5 making 5. Amount outer counts permutations, because every coin is tried at every amount, and gives 9. They disagree on 1,113 of 2,000 random inputs, nothing errors, and both answers are plausible positive integers. Decide which question you are answering, via the state sentence, before writing the loops.

LIS in Θ(n log n) is 391× faster. Always use it?

Only if the problem asks for the length. The patience method's tails array is a record of the best tail seen per length, assembled from different positions — it is frequently not a valid subsequence of the input at all. Reconstructing the actual sequence needs predecessor links threaded through, which the quadratic DP has for free in its table. Faster is not automatically better when the fast version discards what you were asked for.

Ten things to carry forward

  1. DP applies when subproblems overlap — backtracking's tree branches, DP's revisits.
  2. 2,692,537 calls become 59 the moment the repeated argument is cached.
  3. Write the state sentence first. It is the algorithm, and a vague one produces a wrong recurrence.
  4. "Ending at i" is often the state that works, at the cost of a final max.
  5. Memoise first, tabulate second, roll last — and only roll once it works.
  6. Rolling discards the path, so keep the table if you must reconstruct the answer.
  7. Greedy is wrong on 24% of amounts with coins 1, 3, 4, and you cannot tell by looking.
  8. Coin change is linear in the TARGET, not the input — fine at 10⁴, hopeless at 10⁹.
  9. Coins outer counts combinations; amount outer counts permutations. 4 against 9.
  10. They disagree on more than half of random inputs, silently, with both answers plausible.
