Two pointers

The same Θ(n) as chapter 3's hash map, with zero extra memory. The price is a precondition, and when the precondition is not met the algorithm does not crash — it returns a plausible wrong answer, on about one input in five.

Two indices instead of two loops

A nested loop examines every pair: n²/2 of them. Two pointers examine a carefully chosen path through the pairs — one that provably contains the answer — and each step advances at least one pointer, so the whole thing is one pass.

Two arrangements, two families of problem
ArrangementPointersLoop invariantProblems
ConvergingOne at each end, moving inwardThe answer, if any, lies between themTwo Sum II, Valid Palindrome, Container With Most Water, Trapping Rain Water

Both arrangements share the thing that makes the pattern work: every step eliminates candidates without examining them. The whole design problem is justifying that elimination.

the template, and the deduction that justifies it
lo = 0, hi = n - 1
while (lo < hi) {
    s = a[lo] + a[hi]
    if (s === target) return [lo, hi]
    if (s < target) lo++          // a[lo] is too small to pair with ANYTHING
    else              hi--         // remaining, since a[hi] is the largest left
}

// the deduction: if a[lo] + a[hi] is too small and a[hi] is the
// LARGEST value remaining, then a[lo] cannot reach the target with
// any of them. one comparison discards a whole row of the matrix.

On 2,000 sorted values with no valid pair, the pointers take 1,999 steps and brute force takes 1,999,000 — a thousandfold reduction, and unlike chapter 3's hash it uses no memory at all. That is the whole argument for the pattern when the input is already sorted.

The precondition fails silently

Run the same code on [2, 9, 6, 7] with target 11 and it returns null. But 2 + 9 = 11, sitting at indices 0 and 1. Nothing crashes; you get a confident wrong answer.

Measured across 100,000 small unsorted inputs, converging pointers disagree with exhaustive search 18.7% of the time. That frequency is the dangerous part: often enough to be a genuine bug, rare enough that four or five hand-written test cases will very likely all pass. Load the "unsorted trap" preset and untick Sort first to watch it happen.

When the move is a greedy choice

Two Sum's move is forced by arithmetic. Some problems need a genuine argument about which pointer to advance, and getting it wrong produces something that looks right on small examples.

Container With Most Water: the area between two walls is width × min(left, right). Move the shorter wall inward.

why moving the shorter wall discards nothing
area(lo, hi) = (hi - lo) x min(h[lo], h[hi])

suppose h[lo] < h[hi]. consider any pair (lo, j) with j < hi:
    width is SMALLER          (j - lo < hi - lo)
    height is at most h[lo]   (min(h[lo], h[j]) <= h[lo])

so every remaining pair using lo is no better than the one we just
measured. lo can be discarded. moving the TALLER wall has no such
argument — the shorter wall might pair better with something inside.

Verified against exhaustive search on 400 random arrays, the greedy matches every time. The plausible-looking alternative — always advance the left pointer — fails on 198 of the same 400. On [23, 25, 26, 18, 24, 5, 24, 20, 4] the true answer is 140 and always-left gives 32.

The same shape solves Trapping Rain Water: advance whichever side is shorter, tracking the running maximum behind each pointer. Water above a cell is min(maxLeft, maxRight) − height, and the shorter side's maximum is the binding one, so it can be committed without looking ahead. On 3,000 values it does 2,999 operations in Θ(1) space; the prefix-array version does 8,998 across three passes and allocates 6,000 slots for the same answer.

The test for a greedy pointer move

Before writing the loop, complete this sentence: "I can discard this pointer because every remaining pair using it is provably no better than the one I just measured." If you cannot complete it, you do not have a two-pointer solution — you have a guess that will pass the examples in the problem statement. Both greedy moves above have a two-line proof, and the wrong version has none.

Same direction: read and write

The second arrangement is not about pairs at all. One pointer reads every element; the other marks where the next kept element goes. Everything before the write pointer is finished.

one template, many problems
w = 0
for (r = 0; r < n; r++)
    if (keep(a[r]))
        a[w++] = a[r]
// a[0..w) is the answer; w is its length

// change keep() and you change the problem:
//   a[r] !== 0                  -> move zeroes
//   w === 0 || a[r] !== a[w-1]  -> remove duplicates from a sorted array
//   a[r] !== val                -> remove element
//   a[r] < pivot                -> the partition step of quicksort

The saving is in writes, and it is larger than the operation count suggests. Over 1,000 values that are 40% zeroes, the read/write pass writes exactly 1,000 times — once per slot. The naive approach of shifting everything left on each removal writes 203,751 times: a 204-fold difference for the same output.

That matters beyond the operation count. On flash storage a write costs far more than a read and consumes endurance; in a copy-on-write structure a write allocates; in a database a write takes a lock. "Same complexity, far fewer writes" is a real argument that a plain Θ() comparison hides.

The naive version has a bug people reproduce faithfully

Writing the shifting version, the natural loop is for i in 0..n: if a[i] === 0 then shift left. It is wrong: after shifting, the value now at position i may also be zero, and advancing past it leaves it in place. Fix that by not advancing after a shift, and it never terminates, because the zero you pushed to the end gets found again. You need both fixes — hold position and shrink the boundary. Getting the slow version right is harder than getting the fast version right, which is a reasonable argument for the fast one.

Three Sum: sorting, nesting, and the three skips

The step up from two pointers to three: sort, fix an anchor, and run converging pointers over the rest. Θ(n²) instead of Θ(n³).

and the deduplication, which is where it goes wrong
sort(a)
for (i = 0; i < n - 2; i++) {
    if (i > 0 && a[i] === a[i-1]) continue          // skip 1: the anchor
    lo = i + 1, hi = n - 1
    while (lo < hi) {
        s = a[i] + a[lo] + a[hi]
        if (s < 0) lo++
        else if (s > 0) hi--
        else {
            record(a[i], a[lo], a[hi])
            while (lo < hi && a[lo] === a[lo+1]) lo++      // skip 2: the second
            while (lo < hi && a[hi] === a[hi-1]) hi--      // skip 3: the third
            lo++; hi--
        }
    }
}

Sorting is what makes the inner pointers valid — the same precondition as section two — and it also makes deduplication possible, because equal values are now adjacent. Verified against exhaustive Θ(n³) search on 300 random inputs, the version above matches every time.

Remove the skips and it disagrees on 198 of the same 300. On [-1, 0, 1, 2, -1, -4] it reports three triplets where there are two. On four zeroes it reports two copies of [0,0,0]. Those are three separate guards — anchor, second, third — and omitting any one of them leaks duplicates of a different kind.

Why not just use a set at the end?

You can, and it is worth saying so in an interview: collect every triplet, serialise each as a sorted key, and dedupe. It is correct and costs Θ(n²) extra space in the worst case. The skip version is the same answer in Θ(1) space, and — more usefully in the room — it demonstrates you understood why duplicates arise rather than papering over them. Offer both, implement the skips.

Two of those — the precondition and the unjustified greedy — share a property worth naming: they produce plausible output. Nothing throws, the shape of the answer is right, and only comparison against a slow reference reveals the problem. That is the argument for writing the brute force even when you already know the fast solution, which chapter 1 made and chapter 2 turned into a habit.

Check yourself

Why can converging pointers discard a whole row of pairs in one comparison?

Because the array is sorted, so a[hi] is the largest value remaining. If a[lo] + a[hi] < target, then a[lo] paired with anything still in range is also below the target — every one of those pairs is provably not the answer, so lo can advance without examining them. That single deduction turns n²/2 pair checks into n steps: on 2,000 values with no valid pair, 1,999 operations against 1,999,000.

Two pointers and a hash map are both Θ(n) here. Why prefer two pointers?

Memory. The hash needs n slots; converging pointers need none, which is what "O(1) extra space" in a problem statement is asking for. The catch is that the pointers require sorted input: if it is already sorted, take the pointers; if you must sort it yourself, you have paid Θ(n log n) and destroyed the original indices, at which point the hash is usually better. The deciding question is whether sortedness was given to you or has to be bought.

What happens if you run converging pointers on unsorted input?

It returns a wrong answer without any error. On [2, 9, 6, 7] with target 11 it reports "no pair" while 2 + 9 sits at indices 0 and 1. Measured across 100,000 small unsorted inputs it disagrees with exhaustive search 18.7% of the time — frequent enough to be a real bug, and rare enough that four or five hand-written test cases can all pass. Silent wrongness at that rate is worse than an outright crash.

In Container With Most Water, why move the shorter wall?

Because every remaining pair that uses the shorter wall is provably no better than the one just measured. Area is width × min(left, right); moving inward from the shorter wall's side reduces the width, and the height can never exceed that shorter wall, so nothing using it can beat the current area. Moving the taller wall has no such argument — the shorter one might pair better with something further in. Verified on 400 random arrays the correct greedy matches exhaustive search every time; "always move the left pointer" fails on 198 of them, returning 32 where the answer is 140.

What is the sentence you must be able to complete before writing a greedy pointer move?

"I can discard this pointer because every remaining pair using it is provably no better than the one I just measured." Both correct moves in this chapter have a two-line proof of exactly that, and the wrong version has none. If you cannot complete the sentence you do not have a two-pointer solution — you have a heuristic that will satisfy the examples in the problem statement and fail on half of all random inputs, which is the worst possible failure profile because it looks like success.

The read/write pattern has the same complexity as shifting. Why is it better?

Writes. Over 1,000 values that are 40% zeroes, the read/write pass writes exactly 1,000 times — once per slot — while shifting on each removal writes 203,751 times, a 204-fold difference for identical output. Complexity notation hides this because it counts operations without pricing them, and a write is not a read: on flash it consumes endurance, in a copy-on-write structure it allocates, in a database it takes a lock. The naive version is also genuinely harder to write correctly — it needs both a hold-position fix and a shrinking boundary, or it either skips zeroes or never terminates.

Three Sum needs three separate duplicate skips. What does each one prevent?

The anchor skip stops the same first element being used twice, which would repeat every triplet it participates in. The second and third skips advance past runs of equal values after recording a match, so the same triplet is not re-found from a different index pair. They are independent: omitting any one leaks duplicates of a different kind. Verified against exhaustive search, the full version matches on all 300 random inputs and the version without skips disagrees on 198 — reporting three triplets for [-1,0,1,2,-1,-4] where there are two, and two copies of [0,0,0] for four zeroes.

Ten things to carry forward

  1. Two pointers walk a chosen path through the pairs and eliminate the rest without examining them.
  2. Converging needs sorted input; same-direction does not, because it is not about pairs.
  3. Same Θ(n) as a hash, with zero memory — 1,999 steps against 1,999,000, and no allocation.
  4. The precondition fails silently on 18.7% of unsorted inputs. No error, plausible answer.
  5. Move the shorter wall, because everything remaining that uses it is provably no better.
  6. The wrong greedy fails on half of all random inputs and passes the example in the problem.
  7. Complete the discard sentence before writing the loop, or you have a guess rather than an algorithm.
  8. Read/write partitioning is one template — change keep() and you change the problem.
  9. It writes 204× less than shifting, which complexity notation cannot show you.
  10. Three Sum needs three independent skips, and omitting any one leaks a different kind of duplicate.
