Choose, explore, unchoose

Backtracking is depth-first search over a tree of decisions. What makes it a distinct pattern is the third step: the state is shared across branches, so you must put it back the way you found it.

the template, and the line people delete
go(state):
    if (complete) { record(path); return }
    for (choice of options(state)) {
        if (!valid(choice)) continue       // prune
        path.push(choice)                  // CHOOSE
        go(next(state, choice))            // EXPLORE
        path.pop()                         // UNCHOOSE — restores shared state
    }
What "forgot to unchoose" actually looks like

On [1,2,3] the correct enumeration gives eight subsets. Without the pop it still returns eight results — so the count looks right — and the last one is [3,2,3,1,3,2,3]. Only 3 of the 8 are valid subsets at all.

The failure mode is worth noting: the result count is unaffected, because the tree shape has not changed. Only the contents are wrong, so a test that checks the length passes.

The single distinguishing line is what the loop iterates over. for i from start gives combinations and subsets, because you can never go back and pick something earlier — which is exactly what prevents [1,2] and [2,1] both appearing. for i from 0, skipping used gives permutations, because order is now significant.

Measured: the include-or-exclude formulation of subsets visits 2,047 nodes for 10 elements — exactly 2n+1−1 — recording a result only at the leaves. The from start formulation in the demo visits 2n nodes instead, because it records a subset at every node. Both enumerate the same 1,024 subsets; they differ in where the result is emitted, which is worth noticing when you compare node counts between implementations.

Permutations of 8 visit 109,601 nodes for 40,320 results. All counts verified against 2n, n! and C(n,k) for every size tested.

Duplicates in the input

[1,2,2] has six distinct subsets, not eight. The naive enumeration produces eight, with [2] and [1,2] each appearing twice — once for each of the identical 2s.

sort, then skip repeats at the same level
sort(a)                                    // step 1, and it is not optional
go(start):
    record(path)
    for (i = start; i < a.length; i++) {
        if (i > start && a[i] === a[i-1]) continue
        //  ^^^^^^^^^ not i > 0
        path.push(a[i]); go(i + 1); path.pop()
    }

Verified on 3,000 random inputs with repeated values: sort-and-skip is correct every time. No deduplication at all is wrong on 2,075 of them, and — the part worth pausing on — the skip without sorting first is wrong on 1,218.

Two conditions, both load-bearing

Sorting is part of the fix, not a convenience. The skip compares a[i] with a[i−1], which only identifies duplicates when equal values are adjacent. On an unsorted array it removes the wrong elements — the demo's third preset, 2 1 2, shows it directly.

The guard is i > start, not i > 0. The first occurrence at each level must be allowed through; only repeats within the same loop are duplicates. Using i > 0 on [1,1] yields 2 subsets where the answer is 3 — it loses [1,1] itself, because at the deeper level the second 1 is a legitimate first choice.

The same two lines handle Subsets II, Permutations II and Combination Sum II. For permutations the skip additionally requires that the previous equal element is unused, which enforces a fixed relative order among identical values.

Pruning

The template's if (!valid) continue is where the pattern earns its name. Rejecting a partial solution discards its entire subtree unexamined.

Why the ratio grows so fast

Rejecting a placement at row 2 discards every arrangement of rows 3 through 8 beneath it — 86 = 262,144 arrangements, unexamined. The higher in the tree a rejection happens, the more it saves, which is why ordering the choices so that failures surface early is worth more than any micro-optimisation inside the loop.

A pruning claim I could not support

The standard advice for Combination Sum is to sort the candidates and break rather than continue when one exceeds the remaining target — since everything after it is larger too. I set out to measure that saving and found the node counts identical: 672 either way.

The meter was wrong, not the advice

The recursion only descends on candidates that fit, so rejected candidates never become nodes. A node count cannot see this saving at all — it happens entirely in loop iterations.

Counting those instead: on a candidate list where most values are too large, break rejects 5 candidates and continue rejects 30, six times more. The advice is sound and the improvement is real; I was measuring the wrong thing, which is worth as much as the result.

The general lesson is the one chapter 3 reached from the other direction: a counter measures what it counts. Operation counts hid a constant-factor difference there; node counts hide a loop-iteration difference here. Decide what the saving is before choosing how to measure it.

The second is the most immediately baffling. If you push path itself into the results rather than path.slice(), every entry is the same array object, and by the time the search finishes they are all empty. Ten seconds of confusion, every time.

The last one matters more. Chapter 1's constraint table said n ≤ 20 means exponential is intended. If n is 1,000 and you are enumerating, you are in the wrong chapter — the problem almost certainly wants dynamic programming, which is what happens when the subtrees you are exploring turn out to overlap.

Check yourself

What does the "unchoose" step actually do?

It restores the shared state so the next branch starts clean. Backtracking uses one path array across the whole search rather than allocating a new one per branch, which is what makes it cheap — and the price is that every choice must be undone on the way back up. Omitting it on [1,2,3] still returns eight results, so a length check passes, but the last is [3,2,3,1,3,2,3] and only 3 of the 8 are valid subsets.

What single line separates subsets from permutations?

What the loop iterates over. for i from start gives subsets and combinations, because you can never pick something earlier than your last choice — which is exactly what prevents [1,2] and [2,1] both appearing. for i from 0, skipping used gives permutations, because order is now significant. Everything else in the template is the same, and the counts follow: 2n against n!.

Why must you sort before skipping duplicates?

Because the skip compares a[i] with a[i−1], which only identifies duplicates when equal values are adjacent. On an unsorted array it removes the wrong elements — measured wrong on 1,218 of 3,000 random inputs. Sorting is part of the fix rather than a tidying step, and the demo's 2 1 2 preset shows the failure directly: the two 2s are not neighbours, so neither gets skipped and the middle 1 is compared against the wrong thing.

Why i > start rather than i > 0?

Because the first occurrence at each level must be allowed through — only repeats within the same loop are duplicates. With i > 0, the second 1 in [1,1] is skipped even at the deeper level where it is a legitimate first choice, so you get 2 subsets where the answer is 3: [1,1] itself disappears. One character, and it removes a correct result rather than a duplicate one.

How much does pruning save on n-queens?

At n = 8, 2,057 nodes against 19,173,961 — a 9,321-fold reduction — and the unpruned search reaches 16,777,216 leaves while the pruned one reaches 92, arriving only at complete solutions. The ratio grows with n because rejecting a placement high in the tree discards more: a rejection at row 2 throws away 86 = 262,144 arrangements unexamined. Ordering choices so failures surface early is worth more than anything inside the loop.

Sorting candidates and using break instead of continue — how much does it save?

Nothing measurable in node counts: 672 either way, because the recursion only descends on candidates that fit, so rejected ones never become nodes. The saving is entirely in loop iterations — on a list where most values exceed the target, break rejects 5 candidates and continue rejects 30, six times more. The advice is sound; a node counter simply cannot see it, which is a reminder that a meter measures what it counts.

Your backtracking solution is too slow and n is 1,000. What now?

Change chapter. Chapter 1's constraint table says n ≤ 20 or so means exponential search is intended; at n = 1,000 it is not, and no amount of pruning closes a gap that large. The usual answer is that the subtrees you are exploring overlap — the same subproblem reached by different paths — which is precisely the condition for dynamic programming. Chapters 18 and 19 are the continuation.

Ten things to carry forward

  1. Choose, explore, unchoose. The third step exists because the state is shared.
  2. Forgetting it keeps the result count right and corrupts the contents, so length tests pass.
  3. Record path.slice(), or every result is the same array object.
  4. One line separates the shapes: from start for subsets, from 0 skipping used for permutations.
  5. Sort before skipping duplicates — unsorted, the skip removes the wrong things.
  6. The guard is i > start, or you lose legitimate results like [1,1].
  7. Pruning is the whole point: 2,057 nodes against 19 million at n = 8.
  8. A rejection high in the tree saves more — 262,144 arrangements per rejection at row 2.
  9. A meter measures what it counts. Node counts cannot see a loop-iteration saving.
  10. If n is large, you are in the wrong chapter. Overlapping subtrees mean dynamic programming.
