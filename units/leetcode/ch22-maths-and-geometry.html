Maths and geometry

In JavaScript, (a * b) % 1000000007 gives the wrong answer for 79% of random inputs — and which ones is unpredictable. That is worse than failing every time, because it means your test passed.

The limit you will hit

JavaScript numbers are 64-bit floats, so integers are exact only up to 2⁵³ − 1 = 9,007,199,254,740,991. Past that, distinct integers collide: 2⁵³ === 2⁵³ + 1 is true.

Two values near 10⁹ multiply to 10¹⁸, well past 2⁵³. The product is rounded before the modulo is applied, so the modulo runs on the wrong number. Measured across 5,000 random pairs mod 10⁹+7: wrong on 3,927 of them.

79% wrong is worse than 100% wrong

If it failed every time you would notice immediately. Failing on four out of five means small test inputs pass, the submission fails, and nothing in the code looks suspicious. Verified: with both factors under about 94 million, the plain form is correct on all 5,000 trials.

The fix is BigInt for the multiply, or keeping intermediate values small enough that the product stays under 2⁵³.

Modular arithmetic

Problems say "return the answer modulo 10⁹+7" because the true answer overflows. The modulus is prime, which matters for division — but the first thing to get right is when to reduce.

What survives the modulo and what does not
OperationWorks?
(a + b) % mYes — reduce as you go
(a − b + m) % mYes, with the + m to avoid a negative
(a × b) % mMathematically yes; in JavaScript, no
(a ÷ b) % mNo — needs the modular inverse, b^(m−2) mod m
fast exponentiation, by squaring
result = 1
while (e > 0) {
    if (e & 1) result = mulMod(result, b, m)
    b = mulMod(b, b, m)
    e = Math.floor(e / 2)
}
// each squaring doubles the exponent covered, so the loop runs
// ceil(log2(e)) times rather than e times.

Verified: naive exponentiation to 1,000 does 1,000 multiplications and the fast version does 10. At exponent 10⁹ the fast version does 30, exactly ⌈log₂(10⁹)⌉. Both agree on 2,000 random exponents.

That is also where the division rule comes from: since the modulus is prime, Fermat's little theorem gives b⁻¹ ≡ bm−2, so dividing means one fast exponentiation.

Euclid, and a worst case that surprised me

two lines, and the LCM that avoids overflow
gcd(a, b) = b === 0 ? a : gcd(b, a % b)

lcm(a, b) = a / gcd(a, b) * b        // divide FIRST
// a * b / gcd(a,b) overflows where a / gcd(a,b) * b does not

Verified as a true greatest common divisor on 3,000 random pairs — dividing both inputs by it leaves them coprime every time.

Consecutive Fibonacci numbers are the worst case, and subtraction ties there

Lamé's theorem says Euclid's worst case is consecutive Fibonacci numbers, and I expected to show the subtraction-based GCD collapsing on them. It does not: on F₃₁ and F₃₀ both take 29 steps.

The reason is the theorem itself. Fibonacci pairs are the worst case precisely because each modulo reduces to a single subtraction — there is nothing for % to skip. The two algorithms are identical on exactly the inputs where Euclid is slowest.

Where subtraction really collapses is a lopsided pair: gcd(1000000, 1) takes Euclid 1 step and subtraction 999,999.

The step count on Fibonacci pairs is k−1 for Fk+1 and Fk — linear in the number of digits, not the value, which is what makes Euclid fast on numbers of any size.

Below 100,000 there are 9,592 primes. The sieve does 193,078 operations and trial division does 2,745,694 — a 14-fold difference.

The i × i start saves less than expected

Every multiple of i below i² already has a smaller prime factor and was crossed off earlier, so starting at i² rather than 2i is free correctness-wise. I assumed it was a large saving; measured below 10,000 it is 16,981 crossings against 17,991 — about 6%.

The reason is that most crossings happen for small primes, where i² is small and there is little to skip. Still worth doing — it costs nothing — but it is not where the sieve's advantage comes from.

The sieve's real advantage is structural: trial division tests each number independently, while the sieve lets every prime it has already found do work for it.

Never divide in a geometry predicate

"Are these three points collinear?" has an obvious answer — compare the slopes — and a correct one.

the cross product
cross(a, b, c) = (b.x - a.x) * (c.y - a.y) - (b.y - a.y) * (c.x - a.x)

// zero     -> collinear
// positive -> c is counter-clockwise from ab
// negative -> clockwise
// integers in, integer out. no division, no rounding, no NaN.
The slope version fails, and sometimes works by luck

On the vertical line (0,0) (0,1) (0,2) both slopes come out +Infinity, and Infinity === Infinity is true — so it passes by accident. Change the third point to (0,−2) and one slope is +Infinity and the other −Infinity: it now reports "not collinear" for three points on the same vertical line. A repeated point gives 0/0 = NaN, and NaN !== NaN.

Measured over 5,000 random triples, the slope version disagrees with the truth on 171 — 3%, every failure on a vertical or degenerate case. Low, silent, and structural: exactly the profile this unit keeps running into.

The cross product's sign answers three questions with one expression, which is why convex-hull algorithms are built on it — and why "compare slopes" never appears in a serious geometry library.

Coordinate tricks

Rotating a matrix 90° clockwise decomposes into two easy steps: transpose, then reverse each row. Verified against the direct index formula result[i][j] = m[n−1−j][i] on 1,000 random matrices, and four rotations return the original. Anticlockwise is transpose then reverse the columns.

The general habit: when an index formula is hard to get right, look for a decomposition into two operations you cannot get wrong.

The third catches people who learnt modulo from mathematics rather than from C. JavaScript's % is a remainder, so it takes the sign of the dividend: -1 % 5 is -1. For a true modulo, write ((a % m) + m) % m.

Check yourself

Why is (a * b) % 1000000007 wrong in JavaScript?

Because integers are exact only to 2⁵³ − 1, and two factors near 10⁹ produce a product near 10¹⁸. The product is rounded before the modulo is applied, so the modulo runs on the wrong number. Measured on 5,000 random pairs it is wrong on 3,927 — 79%. With both factors under about 94 million it is correct on every trial. Fix with BigInt for the multiply, or keep intermediates small.

Is 79% wrong better or worse than 100% wrong?

Worse. Failing every time gets noticed on the first test; failing four times in five means small inputs pass, the submission fails, and nothing in the code looks suspicious. It is the same profile as chapter 20's low-rate greedy failures and chapter 16's Dijkstra with negative edges — silently and unpredictably wrong is the hardest thing to catch.

How many multiplications does 3^(10⁹) mod p take?

Thirty. Fast exponentiation squares the base and halves the exponent each round, so the loop runs ⌈log₂(e)⌉ times — measured as exactly 10, 20 and 30 for exponents 10³, 10⁶ and 10⁹. The naive version does e multiplications, which at 10⁹ is minutes. Both agree on 2,000 random exponents, and the fast version still needs the BigInt multiply at every step.

Euclid's worst case is consecutive Fibonacci numbers. Does subtraction collapse there?

No — they tie, at 29 steps each on F₃₁ and F₃₀. And that is not a coincidence: Fibonacci pairs are the worst case precisely because each modulo reduces to a single subtraction, so there is nothing for % to skip. The two algorithms are identical on exactly the inputs where Euclid is slowest. Where subtraction really collapses is a lopsided pair: gcd(1000000, 1) is 1 step against 999,999.

Why does the sieve start crossing off at i² rather than 2i?

Because every multiple of i below i² already has a smaller prime factor and was crossed off earlier. It is free correctness-wise — but measured below 10,000 the saving is only 6% (16,981 crossings against 17,991), much less than I assumed, because most crossings happen for small primes where i² is small. Still worth doing since it costs nothing, but it is not where the sieve's 14× advantage over trial division comes from.

What is wrong with checking collinearity by comparing slopes?

Division. On the vertical line (0,0) (0,1) (0,2) both slopes are +Infinity and it passes by luck; change the third point to (0,−2) and the signs differ, so three points on one vertical line are reported non-collinear. A repeated point gives 0/0 = NaN, which is not equal to itself. Measured over 5,000 triples it is wrong on 171 — 3%, every failure vertical or degenerate. Use the cross product: integers in, integer out, no division at all.

Rotate a matrix 90° clockwise, in place.

Transpose, then reverse each row. Verified against the direct formula result[i][j] = m[n−1−j][i] on 1,000 random matrices, and four rotations return the original. Anticlockwise is transpose then reverse the columns. The general habit is worth more than the specific trick: when an index formula is hard to get right, look for a decomposition into two operations you cannot get wrong.

Ten things to carry forward

  1. JavaScript integers are exact to 2⁵³ − 1, and 2⁵³ === 2⁵³ + 1.
  2. (a*b) % m is wrong on 79% of large inputs, unpredictably.
  3. Unpredictably wrong is worse than always wrong.
  4. Reduce as you go for + and −; use BigInt for ×; use Fermat for ÷.
  5. Fast exponentiation is ⌈log₂ e⌉ steps — 30 at exponent 10⁹.
  6. Write LCM as a / gcd * b, dividing first.
  7. Fibonacci pairs are Euclid's worst case because each modulo is one subtraction.
  8. The sieve's i² start saves 6%, not the large fraction usually implied.
  9. Never divide in a geometry predicate. Cross products stay in integers.
  10. Slope comparison sometimes works by luck, which is why it survives testing.
