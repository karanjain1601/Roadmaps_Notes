The shape of the question

A design problem gives you an interface and a complexity requirement, usually O(1). The requirement is the whole puzzle: it rules out every single structure, so the answer has to be a composition.

Why the doubly linked list, and why the map

The list gives O(1) removal — but only if you already hold the node, since finding it would be O(n). The map is what puts the node in your hand. Neither structure solves the problem; each covers exactly the other's weakness.

It has to be doubly linked because unlinking a node needs its predecessor, and chapter 11 established that a singly linked node does not have one. Sentinel head and tail nodes then remove every edge case, which is chapter 11's dummy head applied twice.

Verified against an array-based reference on 2,000 random operation sequences, comparing the full ordering after every single operation. On 20,000 operations at capacity 2,000: the linked-list version takes 49,782 steps — about 2.5 per operation, constant — and the array version takes 62,939,265, averaging 3,147. A 1,264-fold difference that grows with capacity.

Min stack, and one character

Two implementations, both O(1) per operation. Store (value, min-so-far) pairs, or keep an auxiliary stack that records only new minimums.

the auxiliary-stack version
push(v):
    stack.push(v)
    if (!mins.length || v <= mins.top()) mins.push(v)
    //                    ^^ <= not <

pop():
    v = stack.pop()
    if (v === mins.top()) mins.pop()
    return v
Using < loses the minimum on duplicates

Push 1, then 1 again. With < the second is not recorded, so mins holds a single entry — and the first pop removes it, leaving the surviving 1 unguarded. min() then returns null when the true minimum is still 1.

Measured over 3,000 random push/pop sequences, the <= version is correct every time and the < version is wrong on 2,566 — 86%. That rate is high because a small value range makes duplicate minimums common; with a wide range the bug is rarer and exactly as real, because it is the duplicate that triggers it rather than the sequence.

Which of the two implementations?

The pair version always stores 2n values. The auxiliary version stores n plus however many new minimums appeared — measured, 1,001 for 1,000 ascending pushes, and 2,000 for 1,000 descending ones.

So the auxiliary stack wins when new minimums are rare and ties in the worst case. It is never worse, which makes it the right default, and the pair version is easier to explain — a legitimate reason to pick it under pressure.

remove in O(1)
remove(v):
    i = idx.get(v)
    last = arr[arr.length - 1]
    arr[i] = last
    idx.set(last, i)      // THE LINE. without it the map still claims
    arr.pop()             // `last` lives at the end, which it no longer does
    idx.delete(v)

Removing from the middle of an array is O(n) because everything after it shifts; removing from the end is O(1). So move the doomed element to the end first. Measured over 8,000 operations: swap-with-last takes exactly 8,000 steps — one per operation — and splice takes 12,066,092, a 1,508-fold difference.

Forgetting idx.set(last, i)

The array looks right immediately afterwards, so the bug is invisible until the moved element is itself removed — at which point the map points at the wrong slot and the wrong value gets overwritten. Measured over 3,000 random sequences, this omission produces a wrong answer on 1,968 of them, 66%.

This is the consistency cost the first section warned about. Two structures mean two things to update, and the second one is easy to forget because the first one already looks correct.

The array is not an optimisation; it exists solely so getRandom can pick an index, because a hash map offers no O(1) random access. Verified uniform: 100,000 draws from a 5-element set land within 800 of the expected 20,000 each.

LFU is the one worth attempting after LRU, because it is the same idea one level deeper: the frequency map replaces the single list, and the extra bookkeeping is a counter tracking which frequency bucket is currently lowest. Everything that makes LRU work — sentinels, O(1) unlinking, a map to find the node — carries straight over.

The sixth is worth stating because it passes casual testing: a get that returns the right value but does not move the node to the front turns your LRU into a FIFO queue. Every lookup succeeds, every value is correct, and the eviction order is wrong — which only shows up when the cache is full.

Check yourself

What is the single question that solves a design problem?

Which operation is slow, and what structure makes that one fast? Then keep both and pay the cost of keeping them consistent. The O(1) requirement in the prompt is the whole puzzle, because it rules out every single structure — so the answer is always a composition where each half covers exactly the other's weakness. All the bugs live in the consistency work.

Why does an LRU cache need both a map and a doubly linked list?

The list gives O(1) removal, but only if you already hold the node — searching for it would be O(n). The map is what puts the node in your hand. And it must be doubly linked because unlinking needs the predecessor, which chapter 11 established a singly linked node does not have. Measured: 2.5 steps per operation against the array version's 3,147, a 1,264-fold difference at capacity 2,000.

Min stack: why <= rather than <?

Because < skips duplicate minimums. Push 1 then 1 again: only one entry lands in mins, and the first pop removes it — leaving the surviving 1 unguarded, so min() returns null when the true minimum is still 1. Measured over 3,000 random sequences, the <= version is correct every time and < is wrong on 2,566, 86%.

Pair-storing or auxiliary stack for the min stack?

The auxiliary stack, on space. Pairs always store 2n values; the auxiliary version stores n plus the number of new minimums — measured at 1,001 for 1,000 ascending pushes and 2,000 for 1,000 descending. So it wins when minimums are rare and ties in the worst case, never losing. The pair version is easier to explain, which is a legitimate reason to reach for it under pressure.

How do you remove from a set in O(1) while keeping random access?

Swap the doomed element with the last one, then pop. Removing from the middle of an array is O(n) because everything after it shifts; removing from the end is O(1). Measured over 8,000 operations, swap-with-last takes exactly 8,000 steps — one per operation — against splice's 12,066,092, a 1,508-fold difference. The array exists solely so getRandom can pick an index, since a map has no O(1) random access.

What is the one line people forget in the randomised set?

idx.set(last, i) — reindexing the element you just moved. Without it the map still claims that element lives at the end of the array, which it no longer does. The array looks correct immediately afterwards, so the bug is invisible until the moved element is itself removed and the wrong slot gets overwritten. Measured wrong on 1,968 of 3,000 random sequences, 66%.

Your LRU passes every test but evicts the wrong key when full. Why?

Almost certainly get returns the value without moving the node to the front. Every lookup succeeds, every value is correct, and the structure has quietly become a FIFO queue — least recently inserted rather than least recently used. It only shows up once the cache fills, which is why it survives small tests. The reorder on read is not an optimisation; it is the policy.

Ten things to carry forward

  1. Ask which operation is slow and what makes it fast. Then keep both structures.
  2. The O(1) requirement is the puzzle — it rules out every single structure.
  3. The map puts the node in your hand; the list unlinks it in O(1).
  4. Doubly linked, because unlinking needs a predecessor.
  5. Sentinels remove every edge case — chapter 11's dummy head, twice.
  6. <= in the min stack, or duplicates lose the minimum on 86% of sequences.
  7. The auxiliary stack ties in the worst case and wins otherwise.
  8. Swap with the last, then pop — removing from the end is the only O(1) removal.
  9. Reindex the moved element, or you are wrong on 66% of sequences, silently.
  10. A get that does not reorder is a FIFO queue wearing an LRU's interface.
