Prefix sums and difference arrays

Chapter 5's window gave up when the values could be negative. This is where that problem gets solved — and the reason it works is a property the window never had: subtraction undoes addition.

Precompute once, answer instantly

Store the running total up to each index. Then the sum of any range is the difference of two of them — one subtraction, regardless of how long the range is.

the whole idea
p[0] = 0
p[i+1] = p[i] + a[i]                // Θ(n) once

sum(i..j) = p[j+1] - p[i]           // Θ(1) forever after

// the off-by-one guard: make p one longer than a, with p[0] = 0.
// then sum(0..j) needs no special case, which is where the bugs are.

On 10,000 values with 1,000 range queries: building costs 10,000 operations and each query costs exactly 1, for 11,000 total. Scanning each range costs 2,370,787 — a 216-fold difference.

The build is a fixed cost, so count your queries

With one query, scanning is cheaper: you pay n to build and then answer one question. In the measurement above the average range spans 2,371 elements, so the build pays for itself after about 5 queries. Prefix sums are for the "many queries" case, and the giveaway in a problem statement is the word queries, plural, or an input that contains a list of ranges.

Subarray sum equals k — the case the window could not do

Chapter 5 ended with a failure: with negative values allowed, a sliding window reports the wrong answer on about a quarter of inputs, because shrinking is no longer monotonic. Prefix sums make no monotonicity assumption at all.

Demo 1 — prefix sums against the window that failed

seen = {0: 1}                       // one empty prefix, before anything
sum = 0, count = 0
for (v of a) {
    sum += v
    count += seen[sum - k] || 0     // how many earlier prefixes leave exactly k?
    seen[sum] = (seen[sum] || 0) + 1
}

// sum(i..j) === k  is the same statement as  p[j+1] - p[i] === k,
// which rearranges to  p[i] === p[j+1] - k.  that is a MEMBERSHIP
// question about values already seen — chapter 3's hash map.

That rearrangement is the whole trick, and it explains why negatives are irrelevant: nothing here assumes the running sum increases. Verified on 3,000 random inputs containing negatives, the prefix version matches exhaustive search every time, while chapter 5's window is wrong on 1,564 of them.

The one-line bug: seen[0] = 1

The map must start with a single empty prefix recorded. Without it, every subarray that starts at index 0 is missed: on [3, 4] with k = 3 the correct answer is 1 and you get 0. It is a single line, it produces answers that are plausible and slightly too small, and it is the most common mistake in this pattern. Test it with a target that is satisfied by the first element alone.

Difference arrays: the same trick, backwards

A prefix sum makes range queries constant-time. A difference array makes range updates constant-time. They are inverses, and the second is much less well known.

add v to every element of a[i..j]
d[i]   += v          // "from here on, add v"
d[j+1] -= v          // "from here on, stop"

// after all updates, one prefix-sum pass reconstructs the array:
run = 0
for (k = 0; k < n; k++) { run += d[k]; a[k] = run }

// d needs n+1 slots, so an update ending at the last index has
// somewhere to put its cancelling mark.

On 10,000 slots with 2,000 range updates, applying them directly costs 5,055,310 operations; the difference array costs 14,000 — two marks per update plus one pass. A 361-fold reduction, and it is exact rather than asymptotic hand-waving.

The pattern shows up wherever ranges are added rather than queried: booking systems, the Car Pooling and Corporate Flight Bookings problems, meeting-room overlap counting, and any "how many intervals cover each point" question. It is also the discrete version of the sweep line that chapter 7 uses for intervals.

Two dimensions: inclusion–exclusion

The same idea in a grid, with one wrinkle. Building the table needs an extra subtraction, because the two strips you add overlap in a corner.

build, then query any rectangle in four lookups
// build: everything above and to the left
P[r+1][c+1] = g[r][c] + P[r][c+1] + P[r+1][c] - P[r][c]
                                              // ^ the overlap, added twice

// query the rectangle (r1,c1)..(r2,c2):
sum = P[r2+1][c2+1]     // everything up to the far corner
    - P[r1][c2+1]       // minus the strip above
    - P[r2+1][c1]       // minus the strip to the left
    + P[r1][c1]         // plus the corner removed twice

Verified against brute force on 500 random rectangles over a 200×200 grid. Building costs R×C = 40,000; the 500 queries cost 500 lookups against 1,133,956 cell reads for scanning. Every query is exactly four array accesses no matter how large the rectangle.

Draw the four rectangles

The sign pattern is impossible to remember and trivial to re-derive. Sketch the big rectangle from the origin, cross out the strip above, cross out the strip to the left, and notice you have crossed the top-left corner out twice — so add it back. Ten seconds on a whiteboard, and it generalises: three dimensions needs eight terms with alternating signs, by the same argument.

Which operations admit this at all

The requirement is precise and it is not "the operation is associative". It is that the operation has an inverse, so that range(i, j) can be recovered from prefix[j+1] and prefix[i] alone.

XOR works because it is its own inverse: x ^ y ^ y === x, the same cancellation subtraction gives. That makes prefix-XOR the tool for "count subarrays with XOR equal to k", solved exactly like the sum version.

Why range-minimum has no prefix trick, proved in one example

Take [3, 1, 4]. Its prefix minima are [∞, 3, 1, 1]. Now ask for the minimum of range (2,2) — that is 4 — and of range (1,2) — that is 1. Both would have to be computed from p[3] = 1 and p[2] = 1: identical inputs, different required outputs. No function of two prefix values can produce both, so no inverse exists and no formula can.

This is not a limitation to work around, it is a signpost. Range minimum and maximum need a sparse table for static data or a segment tree when it changes. If you find yourself trying to build a prefix-min, stop — you are in the wrong chapter.

Product of Array Except Self is the classic problem that looks like it wants division and must not use it. On [1, 2, 0, 4], dividing the total product by each element gives [0, 0, NaN, 0] where the answer is [0, 0, 8, 0] — wrong at exactly the position the zero occupies, which is the one position with a non-zero answer. The fix is two passes: a running product of everything before each index, then a running product of everything after, multiplied. Exactly 2n operations, no division, no special case.

Check yourself

Why does prefix + hash solve "subarray sum equals k" when a sliding window cannot?

Because it makes no monotonicity assumption. sum(i..j) === k is the same statement as p[j+1] − p[i] === k, which rearranges to p[i] === p[j+1] − k — a membership question about prefixes already seen, answered by a hash map. Nothing there requires the running sum to increase, so negatives are irrelevant. Verified on 3,000 random inputs containing negatives it is correct every time, while chapter 5's window is wrong on 1,564 of them.

What breaks if you omit seen[0] = 1?

Every subarray that starts at index 0 is missed, because there is no recorded "empty prefix" for it to match against. On [3, 4] with k = 3 the answer should be 1 and you get 0. It is one line, the failure is silent, and the answers come out plausibly slightly too small — which is the worst combination. Test it deliberately with a target satisfied by the first element alone.

Prefix sums make queries Θ(1). What makes updates Θ(1)?

A difference array, which is the same trick inverted. To add v across a[i..j], write d[i] += v and d[j+1] −= v — two numbers instead of touching the range — and reconstruct with a single prefix-sum pass at the end. On 10,000 slots with 2,000 updates that is 14,000 operations against 5,055,310 for applying them directly, a 361-fold reduction. The array needs n+1 slots so an update reaching the last index has somewhere to put its cancelling mark.

Why does the 2-D build subtract P[r][c]?

Because the strip above and the strip to the left overlap in the rectangle up-and-left of the current cell, so adding both counts it twice. Subtracting it once fixes the double count. The query formula is the same argument in reverse: take everything up to the far corner, remove the strip above, remove the strip to the left, then add back the corner you just removed twice. Sketch the four rectangles rather than memorising the signs — it re-derives in ten seconds and generalises to eight terms in three dimensions.

Prefix sums work for sums and XOR. Why not for minimum?

Because the technique needs an inverse, and minimum has none. Concretely: [3, 1, 4] has prefix minima [∞, 3, 1, 1]. The minimum of range (2,2) is 4 and of range (1,2) is 1, but both would have to be computed from p[3] = 1 and p[2] = 1 — identical inputs, different required outputs. No function can do that, so no formula exists. XOR works precisely because x ^ y ^ y === x makes it its own inverse. Range minimum needs a sparse table or a segment tree.

Why can't Product of Array Except Self just divide the total by each element?

Zeros. On [1, 2, 0, 4] the total product is 0, so dividing gives [0, 0, NaN, 0] while the answer is [0, 0, 8, 0] — wrong at exactly the one position whose answer is non-zero. Two zeros makes it worse. Even without zeros, integer division loses information. The fix is prefix and suffix products: a running product of everything before each index, then everything after, multiplied together. Exactly 2n operations, no division, no special cases.

When is building a prefix array not worth it?

When you have very few queries. The build is a fixed Θ(n) cost, so with one query you have paid n to answer one question that a scan would have answered in the length of the range. In the measured example — 10,000 values, average range 2,371 — the build pays for itself after about five queries. The signal in a problem statement is the plural: "answer the following queries", or an input that includes a list of ranges. A single range means just add it up.

Ten things to carry forward

  1. Store running totals; a range is the difference of two. Θ(n) once, Θ(1) forever.
  2. Make the prefix array n+1 long with p[0] = 0 and the off-by-one cases disappear.
  3. The build is a fixed cost — worth it after about five queries, not for one.
  4. sum(i..j) === k rearranges to a membership question, which is why negatives stop mattering.
  5. seen[0] = 1 is not optional — without it every subarray starting at index 0 is dropped.
  6. A difference array inverts the trick: mark both edges, sweep once, 361× fewer operations.
  7. Two dimensions is inclusion–exclusion. Draw the four rectangles; do not memorise the signs.
  8. The requirement is an inverse, not associativity. Sum and XOR have one; min and max do not.
  9. Prefix-min is impossible, and one three-element example proves it. Use a sparse table.
  10. Product except self needs two passes, not division — zeros break the division shortcut exactly where it matters.
