Arrays and hashing

Two thousand distinct values, checked for duplicates: 1,999,000 comparisons and no memory, or 2,000 comparisons and 2,000 slots. That is the entire pattern. Everything else in this chapter is about what you put in the map and what you look up.

The trade

A nested loop asks the same question over and over: have I seen this before? A hash table answers that question in constant time, so the inner loop disappears. That is the pattern, and it accounts for a large fraction of every "easy" and "medium" problem list.

Chapter 1 gave the diagnostic — what is the inner loop recomputing? — and here the answer is always a membership or a count.

With no duplicate — the case that bounds you — brute force does n(n−1)/2 = 1,999,000 comparisons on 2,000 values and the hash does 2,000: a thousandfold reduction, paid for with 2,000 slots of memory.

A lucky input is not evidence

Move the duplicate to the first two slots and brute force finishes in one operation while the hash takes two. Brute force is genuinely faster there. That does not make it a better algorithm — it makes that input unrepresentative. When you compare approaches, compare on the case that has no early exit, because that is the one the complexity describes and the one an adversarial test will use.

Notice the third option in the demo, which people routinely forget: sort, then scan adjacent pairs. It costs Θ(n log n) rather than Θ(n), but it needs no extra memory if the sort is in place. When a problem says "O(1) extra space", that is often the intended answer.

Three shapes, and how to tell them apart

The distinction matters because it decides what the map can answer. A set can tell you a value appeared; only an index map can tell you where, which is what Two Sum needs to return. Choosing a set and then discovering you need indices is a common five-minute detour.

The complement trick

the move that turns Θ(n²) into Θ(n)
// instead of asking "does some LATER element complete this pair?"
// ask "did some EARLIER element complete it?" — which you can answer
// from what you have already stored.

seen = new Map()
for (i = 0; i < n; i++) {
    need = target - a[i]
    if (seen.has(need)) return [seen.get(need), i]
    seen.set(a[i], i)                // store AFTER checking, or a[i]
}                                    // pairs with itself when 2*a[i] === target

The inversion is the whole idea: a question about the future becomes a question about the past, and the past is something you can afford to remember. On 1,000 values with no valid pair, brute force does 499,500 operations and the hash does 1,000 — a 500-fold reduction in the case that actually bounds you.

Store after checking, not before

If you insert a[i] into the map before testing for its complement, then when 2·a[i] === target the element pairs with itself and you return [i, i]. It passes the naive test cases and fails on [3, 2, 4], target 6. One line's ordering, and it is the single most common Two Sum bug.

When two pointers is better

If the array is sorted, two pointers from the ends solves the same problem in Θ(n) with zero extra space — 471 operations against the hash's 551 on the same data, and no map at all. But it returns indices into the sorted array. If the problem wants original indices, sorting has destroyed them unless you carried them along in pairs, and that bookkeeping usually costs more than the map you were avoiding.

Frequency maps, and the bucket trick

Counting is the second shape, and it is nearly always one line. The interesting part is what you do with the counts.

"Return the k most frequent elements" looks like it needs a sort or a heap — Θ(d log d) over the distinct values. But a count cannot exceed n, so you can index an array by count and read it from the top: no comparisons at all, Θ(n). Measured over 20,000 values across 500 distinct ones, bucketing does 20,505 operations against sorting's 23,696.

bucket by count — the same idea as counting sort
counts  = frequency map of the values                    // Θ(n)
buckets = array of n+1 empty lists                       // a count can't exceed n
for ([value, c] of counts) buckets[c].push(value)      // Θ(distinct)

// read from the top until you have k
for (i = n; i >= 0 && out.length < k; i--)
    for (v of buckets[i]) out.push(v)                  // Θ(n) total

The reasoning generalises: whenever the values you are sorting by are bounded small integers, you can index instead of compare. Chapter 10 covers the heap version, which wins when k is tiny and the stream is unbounded.

Canonical keys

"Group the anagrams together" is the archetype of a whole family: you need a key such that two inputs share a key if and only if they are equivalent. Both halves matter, and the second is where it goes wrong.

Why summing fails, concretely

abc is 97 + 98 + 99 = 294. aad is 97 + 97 + 100 = 294. They are not anagrams, and the demo shows the sum key collecting them into one group — 5 groups where the truth is 6. Summing satisfies "equivalent implies same key" and fails "same key implies equivalent", and only the first half is easy to notice. Every group looks plausible until you check one.

The test to apply to any canonical key: can two different things collide? Addition loses order and multiplicity together; sorting and counting lose only order, which is exactly what an anagram should lose.

The prime-product key is correct — unique factorisation guarantees it — and is a good example of a right answer that is wrong in practice: with 12-letter words the product exceeds a 64-bit integer and silently wraps, at which point collisions return. It works in the demo only because JavaScript's BigInt is arbitrary precision. Mention it in an interview as an idea; do not ship it.

When hashing is the wrong answer

Hashing destroys order by design. The moment a problem mentions order, ranking, ranges or nearness, a hash table cannot answer it and you need chapter 8's binary search or chapter 10's heap.

Questions a hash set cannot answer
QuestionNeeds
What is the smallest element?A heap, or a sorted structure
How many values fall between a and b?A sorted array plus binary search
What is the next value above x?A balanced tree
Give me everything in orderAnything but a hash table
And below about ten elements, do not bother

Hashing has a real constant factor — computing the hash, probing, allocating. Over 200,000 runs on a five-element array, the brute-force scan took 18 ms and the hash set took 81 ms: the hash did half the operations and 4.6 times the work.

This is also the limit of the operation counter this unit uses everywhere. Counting operations treats "compare two integers" and "hash a value, probe a bucket, maybe allocate" as one unit each, and they are not. The counts are the right tool for showing an asymptotic gap; they are the wrong tool at n = 5, and knowing which regime you are in is part of the skill.

The other trap is mutable keys. Store an object or array as a key, mutate it, and the entry is unreachable while still occupying the map — because the hash was computed from the old contents. In JavaScript this bites differently: objects are keyed by identity, so two structurally identical arrays are two different keys. Serialise to a string, or use a genuine canonical key as above.

Check yourself

What exactly is being traded when you replace a nested loop with a hash map?

Memory for time, in a specific ratio. On 2,000 distinct values, brute force does n(n−1)/2 = 1,999,000 comparisons and no allocation; the hash does 2,000 and holds 2,000 entries. A thousandfold reduction in operations for linear memory. There is a third option people forget — sort and scan adjacent pairs — which is Θ(n log n) but needs no extra space, and is usually the intended answer when the problem says "O(1) extra space".

Brute force finds the duplicate in one operation and the hash takes two. What does that prove?

That the input had an early exit, and nothing about the algorithms. Put the duplicate in the first two slots and brute force genuinely wins; put it nowhere and brute force does a thousand times the work. Complexity describes the case with no early exit, which is also the case an adversarial test will choose. When comparing approaches, compare on the input that forces both to finish — that is why the demo defaults to "no duplicate at all".

Why must you store a[i] after checking for its complement?

Because otherwise an element can pair with itself. If you insert first and then look up target − a[i], then whenever 2·a[i] === target the map already contains the answer and you return [i, i]. On [3, 2, 4] with target 6, storing first returns [0, 0] — the 3 matched itself — where the answer is [1, 2]. It passes most hand-written test cases, which is what makes it the most common Two Sum bug.

The array is sorted. Hash map or two pointers?

Two pointers, unless you need the original indices. It is Θ(n) time like the hash but with zero extra space — 471 operations against 551 on the same data, and no allocation at all. The catch is that if you had to sort the array yourself, the indices you return are positions in the sorted copy, not the input. Carrying (value, index) pairs through the sort fixes it and usually costs more than the map you were trying to avoid, so on unsorted input with index output, take the hash.

Top k frequent elements. Why is a sort or a heap not the best answer?

Because a count is bounded by n, so you can index by it instead of comparing. Build the frequency map, allocate n+1 buckets, drop each value into the bucket for its count, then read from the top until you have k — no comparisons anywhere, Θ(n). Measured over 20,000 values across 500 distinct, bucketing does 20,505 operations against 23,696 for sorting by count. The general rule: when the thing you are ordering by is a bounded small integer, index rather than compare.

Is "sum of the character codes" a valid key for grouping anagrams?

No. abc = 97+98+99 = 294 and aad = 97+97+100 = 294, so they land in the same group without being anagrams — 5 groups where the truth is 6. A canonical key needs two inputs share a key if and only if they are equivalent, and summing satisfies only the easy half. Sorting the letters and a 26-slot count vector both work; counting is Θ(k) against sorting's Θ(k log k), which is why it is the intended answer.

Five elements. Hash set or nested loop?

Nested loop, and the operation counter will tell you the opposite. Over 200,000 runs on a five-element array the brute-force scan took 18 ms and the hash took 81 ms — the hash did half the operations and 4.6× the work, because computing a hash, probing a bucket and possibly allocating are not one unit of cost. This is worth knowing as a limit of the method used throughout this unit: operation counts show asymptotic gaps honestly and mislead badly at small n.

Ten things to carry forward

  1. The pattern is "what is the inner loop recomputing?" and for this chapter the answer is a membership or a count.
  2. 1,999,000 comparisons against 2,000 is the trade, and it costs 2,000 slots.
  3. Compare on the input with no early exit. A duplicate in slot two makes brute force look excellent.
  4. Sort-and-scan is the forgotten third option and is usually what "O(1) extra space" is asking for.
  5. Set, frequency map, index map — pick by what you need to return, not by what you need to check.
  6. The complement trick inverts the question: not "will something later complete this?" but "did something earlier?"
  7. Store after checking, or an element pairs with itself when 2·a[i] === target.
  8. When the sort key is a bounded integer, index instead of comparing — that is the bucket trick.
  9. A canonical key must collide if and only if the inputs are equivalent. Summing character codes fails the second half.
  10. Hashing destroys order and has a real constant factor — 4.6× slower than a scan at n = 5.
