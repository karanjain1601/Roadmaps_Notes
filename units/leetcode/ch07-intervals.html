Intervals

Merging sorts by start. Selecting sorts by end. Use the wrong one and nothing errors — merge-by-end is wrong on 493 of 2,000 random inputs, and select-by-start on 321. Almost every interval problem is decided before you write the loop.

The first question is always the convention

Before anything else: does a meeting ending at 10 conflict with one starting at 10? One sentence, and it decides every comparison in the problem.

The two conventions, and where they differ
Half-open [s, e)Closed [s, e]
Overlap testa.s < b.e && b.s < a.ea.s <= b.e && b.s <= a.e
[1,2] and [2,3]do not overlapdo overlap
Natural forTime ranges, array slicesInclusive numeric ranges

The two agree on every case except the touching one, which is exactly why it is easy to miss: your test cases pass, and the boundary input fails. Meeting-room problems are almost always half-open — a room freed at 10 can be booked at 10 — and this chapter uses that convention throughout.

merge, and the reason the sort key is start
sort by START
out = [first]
for (iv of rest) {
    last = out[out.length - 1]
    if (iv.start <= last.end) last.end = max(last.end, iv.end)
    else                      out.push(iv)
}

// sorting by start guarantees that anything overlapping the current
// run has ALREADY BEGUN, so comparing against the one interval behind
// you is enough. sorted by end, an interval that starts earlier can
// arrive later, and the single backward comparison misses it.

Verified on 2,000 random inputs, merging by start is correct every time and merging by end is wrong on 493 of them. The demo's second preset is one: [[6,8],[1,6],[3,4],[7,12]] merges to [[1,12]], and end-sorting produces [[3,12]] — it lost the interval starting at 1.

Insert Interval is the same problem when the list is already sorted, and it needs no sort at all: everything strictly before, then everything overlapping collapsed into one, then everything after. Three phases, Θ(n).

Selecting: sort by end

"Keep the largest set of non-overlapping intervals" — equivalently, "remove the fewest to eliminate all overlaps" — is the classic activity-selection problem, and its greedy key is the opposite one.

why earliest-finishing-first is optimal
sort by END
count = 0, lastEnd = -infinity
for ([s, e] of sorted)
    if (s >= lastEnd) { count++; lastEnd = e }

// exchange argument: take any optimal solution. its first interval
// ends no earlier than the greedy choice, since the greedy one ends
// earliest of all. swap it for the greedy choice — still valid, still
// the same size. repeat. so greedy is at least as good as optimal.
Three plausible greedy keys, checked against exhaustive search on 2,000 inputs

Earliest-start fails for an obvious reason — one long early interval blocks everything behind it. Shortest-first is the interesting one: it sounds careful, it is wrong far less often, and it is still wrong. On [[1,7],[6,10],[4,7],[4,8],[7,12],[10,14],[1,6],[5,8]] it picks 2 where 3 is possible.

Merge sorts by start; select sorts by end

Same data, same shape of loop, opposite keys — and each key is wrong for the other problem. This is the single most useful thing to memorise about intervals, and the reason is worth holding onto rather than the rule: merging needs to know what has already begun, so it orders by beginnings; selection wants to leave as much room as possible for what follows, so it orders by endings.

The rarity of shortest-first's failures is its own lesson. A heuristic wrong on 1.8% of inputs passes every example in the problem statement and most hand-written tests. Chapter 4 asked you to justify a greedy move before writing it; the exchange argument above is what that justification looks like, and shortest-first has none.

The sweep line

"How many meeting rooms do I need?" is asking for the maximum number of intervals overlapping at any point. You do not need the intervals for that — only their endpoints, as a stream of +1 and −1 events.

the sweep, and the comparator that matters
events = []
for ([s, e] of intervals) { events.push([s, +1]); events.push([e, -1]) }

events.sort((a, b) => a[0] - b[0] || a[1] - b[1])
//                                    ^^^^^^^^^^^
// -1 sorts before +1, so an END at coordinate 10 is processed before
// a START at 10. that is what makes a room freed at 10 reusable at 10.

cur = 0, best = 0
for ([, delta] of events) { cur += delta; best = max(best, cur) }
One comparator character, one extra room

Reverse that tie-break and [[0,10],[10,20],[20,30]] — three back-to-back meetings that fit in one room — reports 2. Across 2,000 random inputs the correct ordering is right every time and starts-first is wrong on 584 of them.

It is worth noticing that this is the same question as section one's convention. Half-open intervals mean touching does not conflict, which means ends must be processed before starts. If the problem uses closed intervals, flip it deliberately — do not leave the comparator to chance.

The sweep line is chapter 6's difference array with the indexing removed. A difference array marks +1 and −1 at integer positions and sweeps by walking the array; a sweep line marks the same deltas at arbitrary coordinates and sweeps by sorting them. Use the difference array when coordinates are small integers, the sweep when they are not.

The alternative implementation is a min-heap of end times: for each interval in start order, pop everything that has finished, push this one, and the heap size is the concurrency. Same answer, Θ(n log n) either way — the sweep does 2n event steps against the heap's n interval steps with a log factor inside each.

The last one is the subtlest. When you absorb an overlapping interval you must take max(last.end, iv.end), not iv.end — otherwise a fully contained interval shrinks the run it was supposed to disappear into. The demo's "nested" preset is that case.

Check yourself

What is the first question to ask about any interval problem?

Whether a meeting ending at 10 conflicts with one starting at 10 — the half-open versus closed convention. Under half-open [s, e) the overlap test is a.s < b.e && b.s < a.e; under closed it is <= in both places. They agree on everything except the touching case, which is precisely why it slips through: ordinary test cases pass and the boundary input fails. It also determines the sweep-line tie-break, so answering it once settles two decisions.

Why does merging sort by start rather than end?

Because sorting by start guarantees that anything overlapping the current run has already begun, so comparing against the single interval behind you is sufficient. Sorted by end, an interval that starts earlier can arrive later in the order, and the one backward comparison misses it. Verified on 2,000 random inputs, merge-by-start is correct every time and merge-by-end is wrong on 493 — for instance [[6,8],[1,6],[3,4],[7,12]] gives [[3,12]] instead of [[1,12]], having lost the interval starting at 1.

For maximum non-overlapping intervals, why is earliest-finish optimal?

By an exchange argument. Take any optimal solution; its first interval ends no earlier than the greedy choice, because the greedy one finishes earliest of all available. Swap it for the greedy choice — the result is still valid and still the same size. Repeat down the list, and greedy is at least as good as optimal. Choosing earliest start instead is wrong on 321 of 2,000 random inputs, because one long early interval blocks everything behind it.

Picking the shortest interval first sounds careful. Is it correct?

No — it is wrong on 36 of 2,000 random inputs, about 1.8%. On [[1,7],[6,10],[4,7],[4,8],[7,12],[10,14],[1,6],[5,8]] it selects 2 where 3 is achievable. The rarity is the danger: a heuristic that fails on under 2% of inputs passes every example in the problem statement and most hand-written tests. It also has no exchange argument, which is the check chapter 4 asked for — earliest-finish has a two-line proof and shortest-first has none.

In the sweep line, why must ends be processed before starts at the same coordinate?

Because under half-open intervals a room freed at 10 is available at 10. If the start is processed first, the counter momentarily includes both meetings and reports one room too many. On [[0,10],[10,20],[20,30]] — three back-to-back meetings needing one room — starts-first reports 2. Across 2,000 random inputs the correct ordering is right every time and starts-first is wrong on 584. It is one character in the comparator, and it is the same question as the convention from section one.

How is a sweep line related to chapter 6's difference array?

It is the same technique with the indexing removed. A difference array marks +1 where a range starts and −1 just past where it ends, then reconstructs by walking the array — which requires the coordinates to be small integers you can index by. A sweep line marks the identical deltas at arbitrary coordinates and reconstructs by sorting the marks instead. That costs Θ(n log n) rather than Θ(n + range), which is the right trade when the coordinates are sparse, large, or not integers at all.

[[1,10],[2,3]] merges to [1,3]. What went wrong?

The extension used last.end = iv.end instead of last.end = max(last.end, iv.end). [2,3] is fully contained in [1,10], so absorbing it should change nothing — but assigning directly shrinks the run to the nested interval's end. It only shows up when one interval strictly contains another, which many test sets do not include, and the answer stays superficially well-formed. Always take the maximum.

Ten things to carry forward

  1. Decide the convention first. Does a meeting ending at 10 conflict with one starting at 10?
  2. The two conventions differ only on touching intervals, which is why the bug survives testing.
  3. Merge sorts by start, because then anything overlapping has already begun.
  4. Selection sorts by end, because finishing early leaves the most room for what follows.
  5. Each key is wrong for the other problem — 493 and 321 failures out of 2,000.
  6. Shortest-first is wrong on 1.8% of inputs, which is rare enough to pass every test you write.
  7. Justify the greedy with an exchange argument, or you have a heuristic.
  8. A sweep line is +1 and −1 events, sorted and summed.
  9. Ends before starts at a shared coordinate, or you buy a room you do not need.
  10. The sweep is chapter 6's difference array without the indexing, which is what buys arbitrary coordinates.
