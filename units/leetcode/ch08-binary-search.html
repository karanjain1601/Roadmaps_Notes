Chapter 8 · Ordering and search

Binary search on the answer

It finds a boundary, not an element

Everyone learns binary search as "find x in a sorted array", and that framing is what makes the variants painful. The useful framing is:

Given a predicate that is false, false, …, false, true, true, …, true — find the boundary.

Finding an element is then a special case. "Is x present?" becomes "find the first index where a[i] >= x, then check whether that element equals x". The variants that used to need their own template — first occurrence, last occurrence, insertion point, count of a value — are all the same search with a different predicate.

The one rule that prevents every infinite loop

The surviving range must always shrink. When hi − lo === 1, a rounding-down mid equals lo. So if the false branch writes lo = mid, nothing moves and the loop spins forever — the demo's broken variant runs past 100,000 iterations without converging.

The pairing is fixed: if hi = mid then lo must become mid + 1. If instead you want last true and write lo = mid, then mid must round up — lo + ceil((hi − lo) / 2) — or that version hangs for the mirrored reason. Both failures are verified here.

The probe count is exactly ⌈log₂ n⌉ — 10 for a thousand, 20 for a million, 30 for a billion — verified at all four scales.

One more detail, invisible in JavaScript and fatal in C or Java: write lo + (hi − lo) / 2 rather than (lo + hi) / 2. The second overflows a signed 32-bit integer once lo and hi are both large, and the bug sat in the JDK's own binary search for nine years.

Searching the answer space

The precondition: monotonicity

This is the third chapter running with a silent precondition, and by now the shape should be familiar. Chapter 4 needed sortedness, chapter 5 needed a monotonic shrink condition, and binary search needs a monotonic predicate: once feasible(x) is true, feasible(x+1) must also be true.

What a non-monotonic predicate does

Run the boundary template over 0…99 with the predicate i % 7 < 3, which is true in patches rather than in one run. It reports the first true index as 42. The real answer is 0. No error, no warning — the search discarded a half that contained the answer, because "false here" no longer implies "false everywhere below".

The check takes one sentence: if this candidate works, must every larger candidate also work? For Koko, a faster monkey never needs more hours, so yes. If you cannot answer yes, there is no boundary to find and binary search is the wrong tool regardless of how sorted anything looks.

Sortedness of the input is a special case of this, not a separate requirement — "is a[i] >= x" is monotonic precisely because the array is sorted. Seeing it that way is what lets you apply the pattern to problems with no array in them.

Rotated arrays, and where duplicates ruin it

A rotated sorted array is not sorted, so the predicate is not monotonic — but at every probe at least one half is still sorted, and you can tell which by comparing a[lo] with a[mid].

decide which half is sorted, then decide whether the target is in it
if (a[lo] <= a[mid]) {                    // left half is sorted
    if (a[lo] <= t && t < a[mid]) hi = mid - 1
    else                          lo = mid + 1
} else {                                 // right half is sorted
    if (a[mid] < t && t <= a[hi]) lo = mid + 1
    else                          hi = mid - 1
}

Verified on all 70 combinations of rotation and target for a seven-element array, and 100,000 elements takes 16 probes.

Duplicates break the argument, and there is no fix

When a[lo] === a[mid] === a[hi] you cannot tell which half is sorted — both look flat. The only safe move is to shrink by one from each end, and the worst case becomes Θ(n).

Measured: 2,001 near-identical elements with the outlier buried in the middle takes 501 probes where a clean binary search would take 11 — 46 times more. Note what triggers it: the outlier has to be hidden between equal endpoints. Put it at the end and the search still halves in 10 probes. That is exactly the input an adversarial test constructs, and it is why the LeetCode problem with duplicates is a separate, harder problem rather than a footnote.

Get either wrong and the boundary is outside the range you searched.

Check yourself

What does binary search actually find?

A boundary in a predicate that is false, false, …, false, true, true, …, true. Finding an element is a special case: "is x present" is "find the first index where a[i] >= x, then check that element". Reframing this way collapses first-occurrence, last-occurrence, insertion point and count-of-a-value into one template with different predicates, and it is what lets the technique apply to problems containing no sorted array at all.

Why does lo = mid cause an infinite loop?

Because when hi − lo === 1, a rounding-down mid equals lo — so assigning lo = mid changes nothing and the loop spins. The rule is that the surviving range must always shrink: if hi = mid then lo must become mid + 1. If you genuinely want lo = mid — for a last-true search — then mid must round up instead, or you get the mirrored hang. The demo runs both broken variants past 100,000 iterations without convergence.

Why write lo + (hi − lo) / 2 rather than (lo + hi) / 2?

Because lo + hi can overflow a fixed-width signed integer when both are large, producing a negative mid and an out-of-bounds access. The subtraction form never exceeds hi. This is not a theoretical concern: the bug sat in the JDK's own Arrays.binarySearch for about nine years before Joshua Bloch wrote it up in 2006. JavaScript's doubles hide it until 2⁵³, so it will not bite in this unit's demos — and it will in an interview conducted in Java or C++.

The array isn't sorted and there's nothing to search. When is binary search still the answer?

When the problem asks for a minimum or maximum value satisfying some condition, and you can check one candidate cheaply. The candidate answers form a range of integers, which is sorted by construction, so you binary-search that instead of the input. Three questions: what is the range of possible answers, can I check one candidate in linear time, and is the check monotonic? On 1,000 piles with answers up to a million that turns 338,660 probes into 20.

What happens if the predicate isn't monotonic?

You get a wrong answer with no error. Running the template over 0…99 with i % 7 < 3 — true in patches — reports the first true index as 42 when it is 0. The search discarded a half containing the answer, because "false here" stopped implying "false everywhere below". The check is one sentence: if this candidate works, must every larger candidate work too? Sortedness of an input array is just the special case where a[i] >= x is monotonic.

In a rotated sorted array, how do you know which half to keep?

At least one half is always still sorted, and a[lo] <= a[mid] tells you which. If the left half is sorted you can test whether the target lies inside it by two comparisons and discard the other half; if not, the right half is sorted and you do the mirrored test. The array is not sorted, so the predicate is not monotonic — but each probe restores enough local order to make a decision. Verified on all 70 rotation-and-target combinations of a seven-element array, and 100,000 elements takes 16 probes.

Why are duplicates in a rotated array a genuinely harder problem?

Because when a[lo] === a[mid] === a[hi] both halves look flat and you cannot tell which is sorted. The only safe move is shrinking by one from each end, so the worst case is Θ(n) and no fix exists. Measured: 2,001 near-identical elements with the outlier buried in the middle takes 501 probes against 11 for a clean search — 46× more. The trigger is specific: the outlier must sit between equal endpoints. Put it at the end and the search still halves in 10, which is why casual testing misses this entirely.

Ten things to carry forward

  1. Binary search finds a boundary in a monotonic predicate, not an element in an array.
  2. All the variants are one template with a different predicate — first, last, insertion point, count.
  3. The surviving range must always shrink, which is the whole termination argument.
  4. hi = mid pairs with lo = mid + 1; lo = mid requires a mid that rounds up.
  5. Use lo + (hi − lo) / 2, the form that cannot overflow.
  6. Probes are exactly ⌈log₂ n⌉ — 20 for a million, 30 for a billion.
  7. Search the answer space when the input has no order — 338,660 probes become 20.
  8. Three questions: what range, can I check one candidate, is the check monotonic?
  9. A non-monotonic predicate returns 42 where the answer is 0, quietly.
  10. Duplicates in a rotated array cost 46× more probes when the outlier hides between equal ends.
