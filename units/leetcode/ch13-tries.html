Chapter 13 · Linked structures

Tries

A trie is worse than a hash set at deciding whether a word is in a dictionary. It uses more memory and answers no faster. Knowing precisely what it is good at is most of what this chapter is for.

One node per distinct prefix

Each edge is a character, each path from the root is a prefix, and a boolean marks which paths are complete words. Words sharing a prefix share the nodes for it.

car, cat, cart, dog, do hold 15 characters between them and build 9 nodes.

The end flag is not optional

do is a word and dog continues past it, so "has no children" cannot mean "is a word". Without a separate boolean, every prefix that happens to be a word becomes invisible. This is the first bug people hit, and it shows up as a dictionary that mysteriously forgets its shorter entries.

What it is not for

A hash set is better at exact lookup

Both answer "is this word in the dictionary" correctly. The hash set hashes the key in Θ(m) and probes in Θ(1); the trie walks Θ(m) nodes, chasing a pointer per character with terrible cache behaviour, and uses far more memory. There is no version of this comparison the trie wins.

Reaching for a trie because the problem mentions words is the mistake this section exists to prevent. The question to ask is whether anything prefix-shaped is being asked.

The second row is the real argument. A failing prefix costs the trie one character comparison — the first letter is not in the root's children and the answer is no. The scan pays full price whether or not anything matches, and its cost grows with the dictionary while the trie's does not.

So the signal is: autocomplete, "all words with prefix P", "does any word start with", counting shared prefixes, and pattern matching with wildcards. Exact membership is a hash set.

Wildcards

Design Add and Search Words allows . to match any single character. The recursion is three lines and the cost analysis is the interesting part.

a literal follows one edge; a dot follows all of them
go(node, i):
    if (i === word.length) return node.isWord
    ch = word[i]
    if (ch === ".")
        return any(child => go(child, i + 1)) for child of node.children
    return node.children.has(ch) && go(node.children.get(ch), i + 1)

Verified against brute-force matching on 3,000 random patterns. Measured on the 5,000-word dictionary, the pattern "ba" visits 3 nodes and ".." visits 33 — because a dot branches into every child at that depth. A pattern of all dots is a full traversal of every node at that level, so the worst case is Θ(n) rather than Θ(m).

Word Search II, and a result I got backwards

Chapter 1 named this as the archetypal two-pattern composition: backtracking over a grid, with a trie pruning it. The usual explanation is that the trie lets you walk the board once instead of once per word, following every candidate down the same shared path.

The trie alone loses

On a 10×10 board over a 3-letter alphabet with 205 words, measured cell visits were: searching once per word, 2,945. A trie without pruning, 8,637 — nearly three times worse. A trie with pruning, 1,005.

I expected the trie to win on its own and it does not. Per-word search exits the instant it finds each word, while an unpruned trie keeps exploring branches whose words were all found long ago. The shared-prefix saving is real and it is smaller than the cost of not knowing when to stop.

the two lines that make it work
if (next.isWord) { found.add(word); next.isWord = false }   // 1. never find it twice

// ... after exploring all four directions ...
if (next.children.size === 0 && !next.isWord)
    node.children.delete(ch)                            // 2. delete the dead branch

Clearing the flag stops the same word being rediscovered from every path that spells it. Deleting childless nodes means the trie shrinks as words are found, so later starting cells explore a smaller structure. Together they turn 8,637 visits into 1,005 — an 8.6-fold saving — and only then does the trie approach beat per-word search, by 2.9×.

The lesson generalises beyond this problem: a shared data structure is a saving only if it also tells you when to stop. The trie's job here is not primarily to share prefixes; it is to know that a branch is exhausted.

Implementation choices

How to store the children
RepresentationPer nodeGood when
Array of 2626 slots alwaysLowercase only, dense tries
Hash mapOne entry per real childSparse tries, unknown alphabet
Sorted arrayOne entry per childYou need children in order

The array of 26 is the standard interview answer because indexing is ch.charCodeAt(0) − 97 and there is no hashing at all. It wastes badly on a sparse trie — most nodes near the leaves have one child and carry 25 nulls — which is what a radix tree fixes by collapsing single-child chains into one edge holding a whole substring.

Two extras worth knowing. Storing a count at each node instead of a boolean lets you answer "how many words share this prefix" in Θ(m). And deletion is the fiddly operation: you must remove the word flag, then walk back up deleting nodes only while they have no children and are not themselves words.

Check yourself

Why does a trie node need a boolean as well as its children?

Because a word can be a prefix of another word. do and dog share a path, and the node for do has a child — so "no children" cannot mean "end of word". Without a separate flag, every entry that happens to be a prefix of a longer entry becomes invisible, and the bug presents as a dictionary that mysteriously forgets its shorter words. The structure stores prefixes; being a word is separate information.

Should you use a trie to check whether a word is in a dictionary?

No. A hash set hashes the key in Θ(m) and probes in Θ(1); the trie walks Θ(m) nodes, chasing a pointer per character with poor cache behaviour, and uses substantially more memory. There is no version of that comparison the trie wins. Reaching for a trie because the problem involves words is the common mistake — the question to ask is whether anything prefix-shaped is being requested.

What is a trie actually better at?

Prefix questions. On a 5,000-word dictionary, finding the 233 words starting with "ba" costs the trie 593 steps and a linear scan 6,668. Better still, a prefix with no matches costs the trie one character comparison against the scan's 10,002 — and the trie's cost does not grow with the dictionary while the scan's does. Autocomplete, "does any word start with", counting shared prefixes and wildcard matching are all the same shape.

Why is a leading . expensive in wildcard search?

Because a literal character follows one edge and a dot follows all of them. On the same dictionary, the pattern "ba" visits 3 nodes and ".." visits 33. A pattern of all dots is a complete traversal of every node at that depth, so the worst case is Θ(n) in the size of the trie rather than Θ(m) in the pattern length. Dots early in the pattern cost far more than dots late in it, because the branching happens before the tree has narrowed.

Does a trie make Word Search II faster on its own?

No — measured, it makes it slower. On a 10×10 board over a 3-letter alphabet with 205 words: searching once per word costs 2,945 cell visits and a trie without pruning costs 8,637, nearly three times worse. Per-word search exits the instant it finds each word, while an unpruned trie keeps exploring branches whose words were all found long ago. The shared-prefix saving is real and smaller than the cost of not knowing when to stop.

So what makes the trie approach win?

Pruning, in two lines. Clearing the word flag once a word is found stops it being rediscovered from every path that spells it. Deleting nodes that have no children and are not words makes the trie shrink as words are found, so later starting cells explore a smaller structure. Together they take 8,637 visits down to 1,005 — an 8.6× saving — and only then does the approach beat per-word search, by 2.9×. A shared structure helps only if it also tells you when to stop.

Array of 26 or a hash map for the children?

Array of 26 when the alphabet is known-small and the trie is dense: indexing is charCodeAt(0) − 97 with no hashing at all, which is why it is the standard interview answer. It wastes badly on sparse tries, where most nodes near the leaves have one child and carry 25 nulls — a radix tree fixes that by collapsing single-child chains into one edge holding a whole substring. Use a hash map when the alphabet is large, unknown, or Unicode.

Ten things to carry forward

  1. One node per distinct prefix — 15 characters become 9 nodes, and 63% is saved on a real dictionary.
  2. The end flag is separate from having children, or do disappears inside dog.
  3. A hash set beats a trie at exact lookup, on both time and memory.
  4. The win is prefix questions — 593 steps against 6,668, and 1 against 10,002 when nothing matches.
  5. The trie's cost does not grow with the dictionary; the scan's does.
  6. A dot branches into every child, so early wildcards cost far more than late ones.
  7. A trie alone makes Word Search II slower — 8,637 visits against per-word search's 2,945.
  8. Pruning is what wins: 8,637 becomes 1,005, an 8.6× saving.
  9. A shared structure helps only if it tells you when to stop.
  10. Array of 26 for dense lowercase, a map for anything else, and a radix tree when chains are long.
