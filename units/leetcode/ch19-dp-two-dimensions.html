Two-dimensional DP

One character — j-- instead of j++ — turns 0/1 knapsack into unbounded knapsack. Both are correct algorithms solving real problems, and only one of them is yours. It changes the answer on 69% of inputs.

Unique Paths has a closed form — C(m+n−2, m−1) — and the DP matches it for every grid up to 10×10. The DP earns its place the moment obstacles appear, where no formula survives; verified against exhaustive path enumeration on 2,000 random grids.

A 100×100 grid has 2.28 × 10⁵⁸ paths. Enumerating them is impossible; filling 10,000 cells is instant. That gap is the pattern in one line.

String pairs

The most common 2-D shape: dp[i][j] compares the first i characters of one string with the first j of another. The recurrence always has the same skeleton — do the characters match? — and differs only in what happens when they do not.

Same table, three problems
ProblemCharacters matchThey do not
Edit distancedp[i-1][j-1]1 + min of all three neighbours
LCSdp[i-1][j-1] + 1max(dp[i-1][j], dp[i][j-1])
Common supersequencedp[i-1][j-1] + 11 + min(dp[i-1][j], dp[i][j-1])

The three neighbours have names worth knowing: dp[i-1][j-1] is replace, dp[i-1][j] is delete from the first string, and dp[i][j-1] is insert. Once you see the table as three moves rather than three subscripts, the recurrence stops needing to be memorised.

Verified against the naive recursion on 1,500 random string pairs, and LCS against exhaustive subsequence search on another 1,500.

A speedup I overstated

I expected the naive edit-distance recursion to be catastrophically slower than the table. On intention versus execution it makes 1,709 calls against the table's 81 cells — a 21-fold difference, not the thousands I had assumed.

The reason is that when characters match, the recursion takes a single branch instead of three, and those two strings share several matching runs. The exponential blow-up is real for strings that share little, and modest for strings that share a lot — which are exactly the pairs you tend to test with.

Knapsack, and the direction of the inner loop

The 2-D form is unambiguous: dp[i][j] is the best value using the first i items within capacity j. Since each row only reads the row above, it collapses to a single array — and the collapse introduces the trap.

the same line, two directions
// 0/1 — each item at most once
for (i of items)
    for (j = cap; j >= w[i]; j--)          // BACKWARDS
        dp[j] = max(dp[j], dp[j - w[i]] + v[i])

// unbounded — each item any number of times
for (i of items)
    for (j = w[i]; j <= cap; j++)          // FORWARDS
        dp[j] = max(dp[j], dp[j - w[i]] + v[i])
Why the direction decides it

dp[j - w] must hold the value from before this item was considered. Going backwards, the lower index has not been touched yet this round, so it still holds the previous row — one use of the item. Going forwards, dp[j - w] has already been updated with this item, so it gets taken again.

That is not a bug so much as a knob. Forwards is exactly correct for unbounded knapsack, verified on 1,500 inputs. The danger is that it is a knob nobody realises they are setting.

Measured across 3,000 random instances, the 2-D and backwards-1-D versions match exhaustive subset search every time, and the forwards version differs on 2,067 of them — 69%.

My first example did not show the bug

I picked weights 1, 3, 4, 5 with capacity 7 — a standard textbook instance — and both loop directions returned 9. Reusing an item simply does not help there, so the trap is invisible. The demo keeps that preset alongside one where reuse pays, because "my test passed" is precisely how this bug survives.

Recovering the answer, not just its value

Most DP problems ask for a number and most solutions stop there. When the problem wants the actual subsequence, path or item set, the table already contains it — you walk backwards through the decisions that produced each cell.

reconstructing the LCS from its table
i = m, j = n
while (i > 0 && j > 0)
    if (a[i-1] === b[j-1]) { out.push(a[i-1]); i--; j-- }   // diagonal: IN the answer
    else if (dp[i-1][j] >= dp[i][j-1]) i--                    // move toward the larger
    else j--
return reverse(out)

Every reconstruction over 1,500 random pairs came out the right length and a valid subsequence of both inputs — the length alone would not have caught an ordering error.

The knapsack version is the same idea: if dp[i][j] !== dp[i-1][j] then item i was taken, so record it and reduce j by its weight. On the demo's default that recovers both items, weighing 2 + 3 = 5 for value 3 + 4 = 7.

Rolling and reconstruction are mutually exclusive

A 200×200 LCS table needs 40,401 slots; two rows need 402, a hundredfold saving. But the table is the record of how each value was reached, and two rows retain only the last step of it.

So decide what the problem asks before optimising space. Length or count: roll it. Sequence, path or item set: keep the table. Doing both requires storing a separate parent pointer per cell, which costs the space you were trying to save.

Recognising a 2-D problem

What the second dimension usually is
SignalStateExamples
Two sequencesposition in eachEdit Distance, LCS, Interleaving String
A gridrow and columnUnique Paths, Minimum Path Sum, Maximal Square

A range of the inputleft and right endpointBurst Balloons, Palindromic Substrings, Matrix Chain
A mode or flagposition and current modeBest Time to Buy and Sell Stock with Cooldown

The fourth row is worth flagging as the hardest family. Interval DP iterates by increasing range length rather than by index, because dp[i][j] depends on shorter ranges inside it. If a natural row-by-row loop produces a table that reads cells it has not filled, the iteration order is the thing to change.

Chapter 1's constraint table converts directly: n ≤ 500 with a 2-D DP means Θ(n³) is affordable, which is exactly the interval-DP budget. n ≤ 5,000 means Θ(n²), which is the string-pair budget.

The third causes more lost time than any of the others. The table is one larger than the strings in each direction so that row 0 and column 0 can hold the empty-string base cases — which means dp[i][j] compares a[i-1] with b[j-1]. Writing a[i] is off by one everywhere and still produces a plausible number.

Check yourself

When does the DP state need two indices?

When one cannot express it. "Ways to reach cell (i, j)" plainly needs both coordinates; "the best using the first i items within capacity j" needs both the item index and the remaining budget. The state sentence from chapter 18 is still the tool — you are just checking how many variables it takes to write it precisely, and the answer is the table's dimensionality.

What are the three neighbours in the edit-distance recurrence?

Three moves, not three subscripts. dp[i-1][j-1] is replace, dp[i-1][j] is delete from the first string, and dp[i][j-1] is insert. When the characters match, no edit is needed and the answer is dp[i-1][j-1] with no +1. Naming the moves is what stops the recurrence needing to be memorised — and it is the same table for LCS and for the shortest common supersequence, differing only in what happens on a mismatch.

Why must the 1-D knapsack loop run backwards?

Because dp[j - w] must hold the value from before this item was considered. Iterating backwards, the lower index has not been touched yet this round, so it still holds the previous row — one use of the item. Iterating forwards, dp[j - w] has already been updated with this item, so it is taken again. One character, and it changes the answer on 69% of random inputs.

So is the forwards version simply a bug?

No — it is exactly correct for unbounded knapsack, where each item may be used any number of times, verified on 1,500 inputs. The direction of the inner loop is the choice between "each item once" and "each item any number of times". That reframing is more useful than memorising which way to go, because it turns an arbitrary rule into a knob you set on purpose — and the danger is only that most people do not realise they are setting it.

You tested the knapsack and both loop directions gave the same answer. What does that tell you?

That reusing an item does not help on that instance, not that your code is right. Weights 1, 3, 4, 5 with capacity 7 — a standard textbook example — returns 9 either way. To exercise the trap you need an instance where repeating an item beats using distinct ones: weights 2 and 3 with capacity 6 gives 7 for 0/1 and 9 for unbounded, because three copies of the weight-2 item fit exactly.

The problem wants the actual subsequence, not its length. Now what?

Walk backwards through the table from dp[m][n]. A diagonal step where the characters matched means that character is in the answer; otherwise move toward whichever neighbour holds the same value. The table already records how each cell was reached — you are just replaying it. Checking only the length would not catch an ordering error, so verify that the result really is a subsequence of both inputs.

Can you roll the table to two rows and still reconstruct the answer?

Not without giving the space back. A 200×200 LCS table needs 40,401 slots and two rows need 402 — a hundredfold saving — but the table is the record of how each value was reached, and two rows retain only the last step. Storing parent pointers per cell restores reconstruction at exactly the cost you were avoiding. Decide first: a length or count can roll, a sequence or path cannot.

Ten things to carry forward

  1. Two indices when one cannot express the state — the sentence tells you the dimensionality.
  2. A 100×100 grid has 2.28 × 10⁵⁸ paths and 10,000 cells. That gap is the pattern.
  3. String-pair tables are three moves: replace, delete, insert.
  4. The table is one larger than the strings, so dp[i][j] uses a[i-1].
  5. Backwards inner loop gives 0/1 knapsack; forwards gives unbounded.
  6. It changes the answer on 69% of inputs — and both answers are correct, to different problems.
  7. A textbook instance can hide the trap entirely, which is how it survives testing.
  8. The table contains the answer, not just its value. Walk backwards to recover it.
  9. Rolling to two rows saves 100× and destroys the path.
  10. Interval DP iterates by range length, not by index, or it reads unfilled cells.
