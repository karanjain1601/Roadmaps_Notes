Stacks and monotonic stacks

A descending array is brute force's worst case — 199,990,000 comparisons — and the monotonic stack's cheapest, because it never pops at all. The stack does 20,000 operations on the same input. Understanding why is the same argument chapter 5 made, in a different structure.

Matching: why a counter is not enough

Valid Parentheses looks like it needs a counter, and with one bracket type it does. With several types it needs a stack, and the reason is exact.

A counter knows how many are open; a stack knows which

([)] has two openers and two closers in the right quantity, so a counter accepts it. A stack rejects it, because when ) arrives the top of the stack is [. Crossing is only detectable if you know the order, and order is precisely what a counter throws away.

Across 5,000 random bracket strings the counter disagrees with the stack on 283 of them, and it agrees perfectly whenever only one bracket type is present. That is the shape of the whole family: a stack is what you reach for when the most recent unresolved thing is what matters.

The same shape covers evaluating expressions, decoding nested strings, simplifying paths, and the undo stack in every editor. If the problem contains the word nested, or "the most recent", a stack is almost certainly involved.

The monotonic stack

The second use is less obvious and much more useful in interviews. Keep the stack sorted — pop anything that violates the order before pushing — and each pop answers a question about the element being popped.

next greater element, and the four variants
st = []
for (i = 0; i < n; i++) {
    while (st.length && a[st.top] < a[i])
        ans[st.pop()] = i          // a[i] is the answer for the popped index
    st.push(i)
}

// two knobs, four problems:
//   comparison < or >      -> greater or smaller
//   answer at pop, or at    -> NEXT (to the right) or
//     push from the new top     PREVIOUS (to the left)

All four variants were checked against brute force on 2,000 random arrays and agree every time. Notice that next problems record the answer when an element is popped, and previous problems record it when an element is pushed — reading whatever survives beneath it.

Daily Temperatures is next-greater with one change: return the distance i − j instead of the index i. Same stack, different arithmetic at the pop.

Why it is linear

There is a while inside a for again, and again it is not quadratic. The argument is the twin of chapter 5's.

Each element is pushed exactly once and popped at most once. Total stack work is therefore at most 2n, however the pops are distributed.

The worst cases are opposite

Look at the first and last rows. A descending array is brute force's disaster — every element scans to the end of the array, n(n−1)/2 = 199,990,000 comparisons — and the stack's easiest case, because nothing is ever greater so nothing ever pops. That is 10,000 times less work on the input brute force finds hardest.

An ascending array reverses it: brute force answers each element in one comparison, and the stack pops on almost every step. Even then the stack does 39,999 operations, which is still under the 2n bound. That is the point — the bound holds regardless of input, while brute force swings across four orders of magnitude.

Largest rectangle in a histogram

The hardest common monotonic-stack problem, and it is next-smaller in both directions at once. A bar of height h can extend left until something shorter blocks it, and right until something shorter blocks it — so the rectangle it anchors is h × (distance between those two blockers).

Without the trailing zero, bars still on the stack are never measured

The loop only measures a bar when something shorter arrives to pop it. Anything still on the stack when the input runs out was never measured at all — and on an increasing histogram that is every single bar. [1,2,3,4,5] returns 0 instead of 9.

Across 3,000 random histograms, omitting the sentinel is wrong on 1,427 of them — nearly half. A height of 0 is shorter than everything, so appending one forces the stack to flush and every remaining bar to be measured. Untick the checkbox in the demo and load the increasing preset.

On 5,000 bars the stack does 10,001 operations against brute force's 12,502,500 comparisons — a 1,250-fold reduction — and the stack version was checked against exhaustive search on 3,000 random histograms.

Recognising it

Phrasings that mean monotonic stack
The problem saysYou need
"next greater / warmer / larger element"Decreasing stack, answer at pop
"how many days until…"The same, returning a distance
"previous smaller element"Increasing stack, answer at push
"largest rectangle / maximal area"Next smaller both ways, plus a sentinel
"remove k digits to make the smallest number"Increasing stack, popping while beneficial
"the span of consecutive days below today"Previous greater, returning a distance

The underlying signal is that for each element, you want the nearest element in one direction satisfying a comparison. If you catch yourself writing a nested loop that scans outward from each position looking for the first bigger or smaller thing, that is the pattern.

The related structure is the monotonic deque, which is what Sliding Window Maximum needs: a monotonic sequence that also drops elements leaving the window at the front. Chapter 5 flagged that problem as a composition, and this is the second half of it.

The second is the one worth internalising as a habit: push indices, not values. You can always read the value with a[i], and you cannot recover the index from a value. Every width, distance and span in this chapter needs the index.

Check yourself

Valid Parentheses with only ( and ). Does it need a stack?

No — a counter is enough and uses Θ(1) space: increment on open, decrement on close, fail if it ever goes negative, and require zero at the end. Add a second bracket type and the counter breaks, because it records how many are open and not which. ([)] has the right quantities and is invalid, and only a stack can see that. Across 5,000 random bracket strings the counter disagrees with the stack on 283 of them.

Why is a monotonic stack linear despite the inner while?

Because each element is pushed exactly once and popped at most once, so total stack work is bounded by 2n however the pops are distributed. The inner loop can pop many elements on one iteration, but those elements can never be popped again. This is chapter 5's amortised argument in a different structure — there the left pointer only moved forward, here each element only leaves the stack once, and both give a total rather than a product.

Which input is worst for a monotonic stack, and which is worst for brute force?

They are opposite, which is the useful part. A descending array is the stack's cheapest case — nothing is ever greater, so nothing ever pops, 20,000 operations for 20,000 elements — and brute force's disaster, since every element scans to the end: n(n−1)/2 = 199,990,000 comparisons, ten thousand times more. An ascending array reverses it: brute force answers each element in one comparison and the stack pops on nearly every step, still finishing in 39,999 operations. The stack's cost barely moves; brute force's swings across four orders of magnitude.

What are the two knobs that turn one template into four problems?

The comparison direction — < gives next/previous greater, > gives smaller — and where you record the answer. Recording at the pop, using the element that caused it, gives you the next qualifying element to the right. Recording at the push, reading whatever survives beneath the new element, gives you the previous one to the left. All four combinations were checked against brute force on 2,000 random arrays and agree every time.

Why does Largest Rectangle need a trailing zero?

Because a bar is only measured when something shorter arrives to pop it, so anything still on the stack when the input ends was never measured. On an increasing histogram that is every bar — [1,2,3,4,5] returns 0 instead of 9. A sentinel height of 0 is shorter than everything, so it forces the stack to flush and every remaining bar to be measured against its true right boundary. Across 3,000 random histograms, omitting it is wrong on 1,427 — nearly half.

Why push indices rather than values?

Because you can always recover the value with a[i] and can never recover the index from a value. Every width, distance and span in this chapter needs the index: Largest Rectangle computes i − left − 1, Daily Temperatures computes i − j, and span problems need the gap to the previous greater element. Pushing values works for Valid Parentheses, where there is no arithmetic, and stops working the moment a problem asks "how far".

"Find the largest element to the right of each position." Monotonic stack?

No. The pattern answers nearest questions — the first element in some direction satisfying a comparison — and "largest to the right" is not a nearest question. It is a suffix maximum: one backward pass keeping a running maximum, Θ(n) and much simpler. Reaching for a stack here produces code that works and is harder than it needs to be. The tell for a genuine monotonic-stack problem is the word next, previous, or nearest.

Ten things to carry forward

  1. A counter knows how many are open; a stack knows which, which is why crossing needs a stack.
  2. A monotonic stack answers "nearest element satisfying a comparison" for every position at once.
  3. Two knobs, four problems: the comparison direction, and whether you record at pop or at push.
  4. Record at pop for next, at push for previous.
  5. Each element is pushed once and popped at most once, so total work is bounded by 2n.
  6. That is chapter 5's argument in another structure — a total, not a product.
  7. Descending input is the stack's cheapest case and brute force's worst, by a factor of 10,000.
  8. Largest rectangle is next-smaller in both directions, and needs a sentinel.
  9. Without the sentinel it is wrong on 48% of histograms and returns 0 for an increasing one.
  10. Push indices, never values. You can recover a value from an index and not the reverse.
