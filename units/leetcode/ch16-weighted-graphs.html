Weighted graphs in interviews

There are two versions of Dijkstra in circulation. One breaks on negative edges and the other does not — because the one that survives has quietly stopped being Dijkstra.

BFS answers the wrong question

Chapter 14 established that BFS gives shortest paths on unweighted graphs. The moment edges have different costs, "fewest hops" and "lowest cost" become different questions.

The error rate is low and the overshoot is not

Across 6,355 reachable pairs in random weighted graphs, BFS's route costs more than the optimum on 217 of them — only 3%, because a small random graph usually has one obvious route. But when it is wrong it is badly wrong: the worst case found reported 14 where the answer is 3, 4.7× too expensive.

That combination — rarely wrong, badly wrong when it is — has appeared in every part of this unit. It is the profile that survives testing.

Dijkstra

the version with a finalised set
dist[src] = 0
heap.push([0, src])
while (heap not empty) {
    [d, u] = heap.pop()          // the closest unfinalised node
    if (done[u]) continue
    done[u] = true              // FINALISED — never reconsidered
    for ([v, w] of adj[u])
        if (!done[v] && d + w < dist[v]) {
            dist[v] = d + w
            heap.push([dist[v], v])
        }
}
The invariant, and where it comes from

When a node is popped it is the cheapest unfinalised node in the graph. Any other route to it would have to pass through some node that is at least as expensive, so no cheaper route can exist — and it can be finalised.

That argument uses one assumption: extending a path never makes it cheaper. Which is to say, all weights are non-negative. Everything Dijkstra does rests on that single line, and section four is what happens when it is false.

Verified against Bellman-Ford on 3,000 random non-negative graphs — identical distances every time. On 2,000 nodes and 20,000 edges, Dijkstra performs 19,936 relaxations, about one per edge, against Bellman-Ford's 239,400 — a twelvefold difference that grows with the graph.

Negative edges, and the two Dijkstras

Take 0→1 costing 1, 0→2 costing 2, and 2→1 costing −2. Dijkstra pops node 1 at cost 1 and finalises it. Later it examines 2→1, which would give cost 0 — but node 1 is already done, so the edge is ignored. It answers 1; the truth is 0.

The version that survives has stopped being Dijkstra

Many implementations use a lazy heap instead: no done array, just a check that a popped entry is not stale. That version gets the right answer here, and on all 3,599 negative-weight graphs tested it disagrees with Bellman-Ford zero times.

This is not a fix. Without the finalised set, a node can be re-pushed every time its distance improves — so the algorithm keeps correcting itself and has silently become Bellman-Ford with a heap, losing the complexity guarantee that made Dijkstra worth using. On a graph engineered to keep improving distances it can re-push exponentially often. If you rely on the lazy version to handle negatives, say so deliberately rather than discovering it by accident.

The measured failure rate for the finalised version on random negative-weight graphs is 27 of 3,599 — under 1%, because the failure needs the negative edge to be discovered after its target is locked in, and random graphs rarely arrange that. On the three-node graph above it fails every time. Rare on random input, certain on an adversarial one, which is exactly the pattern to distrust.

Bellman-Ford

Relax every edge, n−1 times. That is the whole algorithm, and it needs no assumption about signs — after k rounds, every shortest path using at most k edges has been found.

It also detects what Dijkstra cannot express: run one extra round, and if anything still improves there is a negative cycle, meaning no shortest path exists at all because you can loop forever getting cheaper.

When the problem has two quantities

Cheapest Flights Within K Stops asks for the cheapest route using at most k stops. That is not a shortest-path problem, because the cheapest route may use too many hops and the shortest-hop route may be too expensive.

Checked against exhaustive search on 3,000 random cases, the k-round version is correct every time. Plain Dijkstra ignoring the limit is wrong on 205 of them, and the version that relaxes in place — omitting the snapshot — is wrong on 111.

Why the snapshot matters

Relaxing in place lets a value updated this round be used again in the same round, chaining two edges into one iteration. That silently permits more hops than k, so the answer comes out too cheap. One array copy per round fixes it, and its absence is invisible in a code review.

The general move: put the constraint in the state

When a problem constrains something besides cost, that constraint becomes part of the vertex. You are no longer finding shortest paths over nodes but over (node, hops used) pairs — and once you see it that way, Dijkstra works again, on the expanded graph.

The same reframing handles fuel limits, keys collected, moves remaining, and "at most k obstacles removed". The state space multiplies by the constraint's range, which the input bounds will tell you is affordable.

0-1 BFS is the one people forget. With weights of only 0 and 1, push zero-cost neighbours to the front of a deque and unit-cost ones to the back — the deque then behaves as a two-bucket priority queue and you get Dijkstra's answer in linear time with no heap. It is the right tool for "minimum obstacles removed" and "minimum flips" problems.

Chapter 1's constraint table applies here too. V ≤ 400 with all-pairs distances wanted is Floyd-Warshall's 64 million operations; V ≤ 10⁵ with weights is Dijkstra; a stated hop or fuel limit means the state has an extra dimension.

Check yourself

Why can't you use BFS once edges have weights?

Because BFS optimises the number of edges, which equals cost only when every edge costs the same. On 0→1 at 10, 0→2 at 1 and 2→1 at 1, BFS takes the single-edge route for 10 where the answer is 2. Measured across 6,355 reachable pairs it is wrong on only 3% — a small random graph usually has one obvious route — but the worst case found was 14 against 3, 4.7× too expensive. Rarely wrong and badly wrong is the profile that survives testing.

What is Dijkstra's invariant, and what does it assume?

When a node is popped it is the cheapest unfinalised node, so any other route to it must pass through something at least as expensive — therefore no cheaper route exists and it can be finalised. That argument rests on one assumption: extending a path never makes it cheaper, which is to say all weights are non-negative. Everything Dijkstra does follows from that one line, and it is exactly what a negative edge violates.

Your Dijkstra gives the right answer on a graph with negative edges. Is it correct?

Probably you wrote the lazy version — no done array, just a staleness check on popped entries. It keeps re-pushing nodes whenever their distance improves, so it corrects itself, and on 3,599 random negative-weight graphs it disagrees with Bellman-Ford zero times. But that is not Dijkstra any more: without the finalised set it has become Bellman-Ford with a heap and lost the complexity guarantee, and on a graph engineered to keep improving distances it can re-push exponentially often. Relying on it is fine if deliberate and a trap if accidental.

The textbook Dijkstra is wrong on under 1% of random negative-weight graphs. Reassuring?

No — 27 of 3,599, and the low rate is because the failure needs a specific ordering: the negative edge must be discovered after its target is finalised. Random graphs rarely arrange that. On the three-node graph 0→1:1, 0→2:2, 2→1:−2 it fails every time, answering 1 where the truth is 0. Rare on random input and certain on adversarial input is the same pattern as chapter 4's unsorted two pointers and chapter 15's two-colour cycle check.

Why doesn't plain Dijkstra solve Cheapest Flights Within K Stops?

Because the problem has two quantities and shortest-path algorithms optimise one. The cheapest route may use more hops than allowed, and Dijkstra will happily return it — wrong on 205 of 3,000 random cases. The fix is Bellman-Ford stopped after k+1 rounds, since after round i the table holds the cheapest route using at most i+1 edges. Equivalently, make the vertex a (node, hops used) pair, at which point Dijkstra works again on the expanded graph.

Why must each Bellman-Ford round use a snapshot?

Because relaxing in place lets a value updated this round be used again in the same round, chaining two edges into one iteration — which silently allows more hops than k and produces an answer that is too cheap. Wrong on 111 of 3,000 random cases, and completely invisible in a code review: the loop looks identical. One array copy per round fixes it. For unbounded Bellman-Ford it does not matter, which is why the habit does not transfer.

All the weights are 0 or 1. Dijkstra?

You can, but 0-1 BFS is better: push zero-cost neighbours to the front of a deque and unit-cost ones to the back. The deque then acts as a two-bucket priority queue and you get the same answer in Θ(V + E) with no heap at all. It is the right tool for "minimum obstacles removed", "minimum flips" and similar problems, and it is the case people most often over-engineer with a full Dijkstra.

Ten things to carry forward

  1. BFS optimises hops, not cost, and the two coincide only with equal weights.
  2. Wrong on 3% of pairs and 4.7× too expensive at worst — the profile that survives testing.
  3. Dijkstra's invariant rests on non-negative weights, and nothing else.
  4. The finalised-set version is the real Dijkstra, and negative edges break it.
  5. The lazy version survives negatives by becoming Bellman-Ford and losing the guarantee.
  6. Bellman-Ford needs no sign assumption and detects negative cycles with one extra round.
  7. A hop limit is a second quantity, so shortest-path alone cannot answer it.
  8. Put the constraint in the state: the vertex becomes (node, hops used).
  9. Snapshot each Bellman-Ford round, or two edges chain into one iteration.
  10. Weights of 0 and 1 want a deque, not a heap.
