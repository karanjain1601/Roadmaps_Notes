Tree patterns

The obvious way to validate a binary search tree — check each node against its children — accepts trees that are not search trees. When it says "valid" it is wrong 12% of the time, which is precisely when you were relying on it.

Which way does information flow?

Almost every tree problem is decided by one question: does the recursive call need something from its parent, or does the parent need something from it?

two directions, same answer
// top-down: carry state DOWN as an argument, write to an outer variable
function go(node, depth) {
    if (!node) return
    best = max(best, depth)              // outer
    go(node.left, depth + 1)
    go(node.right, depth + 1)
}

// bottom-up: return state UP, no outer variable at all
function height(node) {
    if (!node) return 0
    return 1 + max(height(node.left), height(node.right))
}

Both make the same number of calls and agree on all 1,500 random trees tested. Bottom-up is usually preferable because it needs no mutable outer state — but the interesting case is the one that needs both.

Diameter: return one thing, track another

The longest path between any two nodes may not pass through the root, so no single return value works. The resolution is that the recursion returns the height — what the parent needs — and tracks the best diameter in an outer variable, which is what you actually want.

That split is why Diameter of Binary Tree feels harder than its Θ(n) solution looks. Once you have seen it, the same shape solves Binary Tree Maximum Path Sum, Longest Univalue Path, and House Robber III: the answer you want is not the answer the parent needs.

The cost of recomputing

"Is this tree balanced?" has an obvious solution: at every node, compute both subtree heights and compare. It is correct and it recomputes the same heights repeatedly.

I expected to write "quadratic" here and the measurement says otherwise. The ratios — 3.2, 5.1, 7.0, 9.0, 11.0, 13.0 for heights 4 through 14 — are each the height minus one. Recomputing the height at every node costs a factor of h, so the naive version is Θ(n·h). On a balanced tree that is Θ(n log n); it degrades to genuinely quadratic only on a skewed tree.

Which is still worth fixing, and the fix is a sentinel: have the height function return −1 to mean "a subtree below here was already unbalanced", and propagate it. One bottom-up pass computes the height and detects the imbalance.

The general principle is chapter 1's diagnostic applied to recursion: what is this call recomputing? If a child's result is needed by more than one ancestor, return it once rather than asking for it again.

Why the local check is wrong

On [5,1,6,null,null,4,7]: node 4 sits below node 6, and 4 < 6, so the parent-child test passes. But 4 is in the right subtree of 5 and must therefore exceed 5. It does not. An inorder walk gives 1 5 4 6 7 — not sorted.

A BST constraint is inherited from every ancestor, not just the parent. Each node lives inside a range narrowed by every turn taken to reach it, and only a check that carries those bounds down can see it.

Measuring the failure honestly

Across 4,000 random trees the local check disagrees with the truth on only 7. That number badly understates the problem, because most random trees are invalid for reasons the local check does catch — so the denominator is full of easy cases.

The number that matters is conditional: of the trees the local check accepts, how many are actually BSTs? Measured over 200,000 trees, it accepts 5,807 and 719 of those are not search trees — a 12% error rate on exactly the verdict you were relying on. A validator is only consulted when you expect a yes, so that is the rate that describes its usefulness.

two correct validators
// carry the bounds down, narrowing at every step
valid(node, lo, hi):
    if (!node) return true
    if (lo !== null && node.val <= lo) return false
    if (hi !== null && node.val >= hi) return false
    return valid(node.left,  lo, node.val)      // tighten the upper bound
        && valid(node.right, node.val, hi)      // tighten the lower bound

// or, simpler: walk inorder and check the sequence is strictly increasing

Both were checked against each other on thousands of random trees and agree. The inorder version is easier to get right; the range version generalises to problems where you need the bounds for something else.

Lowest common ancestor, and what ordering buys

In a general binary tree, LCA is a neat postorder recursion: if a node is one of the targets, return it; otherwise recurse both ways and return this node if both sides found something.

In a BST you can do much better, and it needs no recursion at all:

the split point
while (node) {
    if (p.val < node.val && q.val < node.val) node = node.left
    else if (p.val > node.val && q.val > node.val) node = node.right
    else return node        // they diverge here — this is the LCA
}

Measured on a 63-node BST over 60 random pairs: the general version visits 4,542 nodes and the BST version visits 95 — a 48-fold reduction, Θ(height) instead of Θ(n). Both match brute force on every pair.

That gap generalises. The same substitution — use the ordering rather than searching — turns Θ(n) into Θ(height) for search, insert, delete, kth-smallest, floor, ceiling, and range queries. When a problem says "binary search tree" rather than "binary tree", the word is doing work.

BFS or DFS?

Choose by what you need, then by shape
Use BFS whenUse DFS when
The problem mentions levels, rows or depthYou need root-to-leaf path information
You want the shallowest answerYou are aggregating subtree results
The tree is deep and narrowThe tree is wide and shallow

The memory argument is concrete. A complete tree of 1,023 nodes has ten levels and its widest holds 512 nodes — BFS queues all of them at once, while DFS holds one path of ten. A left spine of 800 reverses it: 800 levels of one node each, so BFS holds one node and DFS recurses 800 deep and may overflow the stack.

The practical rule is that BFS costs Θ(width) and DFS costs Θ(height), and you should know which of those is large before choosing.

The fifth is worth pinning down before you write anything: is depth measured in nodes or edges? A single-node tree has depth 1 in nodes and 0 in edges, and diameter is conventionally counted in edges while depth is conventionally counted in nodes. Decide, say it out loud, and stay consistent.

Check yourself

Why does checking each node against its children fail to validate a BST?

Because the constraint is inherited from every ancestor, not just the parent. On [5,1,6,null,null,4,7], node 4 is less than its parent 6 so the local test passes — but 4 sits in the right subtree of 5 and must exceed 5. Inorder gives 1 5 4 6 7, not sorted. Every node lives inside a range narrowed by each turn taken to reach it, so a correct check either carries those bounds down or walks inorder and verifies the sequence increases.

The local check disagrees with the truth on 7 of 4,000 random trees. Is that reassuring?

No, and the number is misleading. Most random trees are invalid for reasons the local check does catch, so the denominator is stuffed with easy cases. The meaningful rate is conditional: of the trees it accepts, how many are actually BSTs? Measured over 200,000 trees it accepts 5,807 and 719 of those are not — a 12% error rate on precisely the verdict you were relying on. A validator is only consulted when you expect a yes.

Top-down or bottom-up?

Ask which way the information flows. If a call needs something from its parent — the depth so far, the path so far, the allowed range — pass it down as an argument and write results to an outer variable. If the parent needs something from the call — a height, a sum, a count — return it and use no outer state at all. Bottom-up is usually cleaner because it avoids mutable state, and both make the same number of calls.

Why is Diameter of Binary Tree harder than its solution looks?

Because the answer you want is not the answer the parent needs. The longest path may not pass through the root, so no single return value works. The resolution is that the recursion returns the height — what a parent can use — while tracking the best diameter in an outer variable. Once you have seen that split, the same shape solves Binary Tree Maximum Path Sum, Longest Univalue Path and House Robber III, which is why it is worth naming rather than memorising.

How much does recomputing subtree heights actually cost?

A factor of the height, not of n. Measured on perfect trees, the naive balance check does 3.2×, 7.0×, 11.0× and 13.0× the visits of a one-pass version at heights 4, 8, 12 and 14 — each ratio is the height minus one, so it is Θ(n·h). On a balanced tree that is Θ(n log n) rather than the quadratic people usually claim; it becomes genuinely quadratic only on a skewed tree. The fix is a sentinel: return −1 for "already unbalanced" and propagate it in one bottom-up pass.

What does knowing it is a BST buy you for LCA?

A factor of 48, measured. The general recursion visits every node — 4,542 across 60 queries on a 63-node tree — while the BST version walks down from the root, going left when both targets are smaller, right when both are larger, and stopping at the first node where they diverge: 95 visits. That is Θ(height) instead of Θ(n), and it needs no recursion at all. When a problem says "binary search tree", the word is doing work.

BFS or DFS on a complete tree of a million nodes?

DFS, on memory grounds, unless you need level information. BFS costs Θ(width) and a complete tree's widest level holds half its nodes — for 1,023 nodes that is 512 queued at once against DFS's path of 10. A left spine reverses it completely: 800 levels of one node each, so BFS holds one node while DFS recurses 800 deep and risks a stack overflow. Know which of width and height is large before choosing.

Ten things to carry forward

  1. Inorder on a BST yields sorted output, and that single fact solves half the BST problems.
  2. Ask which way information flows — down as an argument, or up as a return value.
  3. Some problems need both: return the height, track the diameter.
  4. Recomputing subtree heights costs a factor of h, not of n — 13× at height 14.
  5. A −1 sentinel turns two passes into one and detects the failure on the way up.
  6. A BST constraint is inherited from every ancestor, not just the parent.
  7. The local check is wrong on 12% of the trees it approves, which is the rate that matters.
  8. Carry bounds down, or walk inorder. Both are correct; inorder is easier.
  9. LCA in a BST is the first node where the targets diverge — 48× fewer visits.
  10. BFS costs Θ(width), DFS costs Θ(height). Know which is large.
