Sliding window

There is a while loop inside a for loop and the whole thing is Θ(n). Over 20,000 characters the two pointers move 39,998 times between them — never more than twice per element. Understanding why is the chapter.

A window is a contiguous range you maintain rather than rebuild

Chapter 1 named contiguous as the most valuable word in a problem statement, and this is why. If the thing you are looking for is a contiguous range, you never need to re-examine its contents: you update as it grows and shrinks.

Fixed windows: add one, subtract one

The maximum sum of k consecutive values does not need the window re-summed at each position. Add the element entering, subtract the one leaving.

the rolling update
sum = a[0] + ... + a[k-1]
best = sum
for (i = k; i < n; i++) {
    sum += a[i] - a[i - k]        // one add, one subtract
    best = max(best, sum)
}

On 5,000 values with k = 250, rolling does 5,000 operations and rescanning does 1,187,750. The ratio is k, because rescanning re-reads the whole window every time — measured at 10×, 98× and 800× for k of 10, 100 and 1,000.

Variable windows: the shrink condition

Most window problems do not tell you the size. Instead they give a condition the window must satisfy, and the algorithm is: grow on the right always; shrink from the left while the condition is violated.

the template every variable window shares
lo = 0
for (hi = 0; hi < n; hi++) {
    add(a[hi])                              // window grows right

    while (violated())                      // shrink until legal again
        remove(a[lo++])

    record(hi - lo + 1)                     // every window here is valid
}

// three things to decide, and they are the whole problem:
//   what state does add/remove maintain?  (a count map, a sum, a set)
//   what does violated() test?
//   do you record on every step, or only when legal?

Verified against exhaustive search on 500 random strings, the window matches every time. The interesting question is not whether it is correct but why it is fast.

Why the nested loop is not quadratic

A while inside a for usually means Θ(n²). Here it does not, and the reason is worth stating precisely because it is the argument you will be asked for.

The amortised argument, in one sentence

The left pointer only ever moves forward, so across the entire pass it takes at most n steps in total — no matter how they are distributed. The inner loop can run 500 times on one iteration of the outer loop, but then it cannot run on 500 others. Total work is right-advances plus left-shrinks: at most 2n.

Measured over 20,000 characters: 20,000 advances and 19,998 shrinks, 39,998 pointer moves, right at the bound. Brute force on the same input does 70,064 operations, and if the left pointer reset to zero each step the cost would be n(n+1)/2 = 200,010,000 — five thousand times more. Monotonicity of the left pointer is the entire difference.

The practical test: when you write the inner while, check that lo only ever increases and never resets. If your logic ever needs to move it backwards, you do not have a sliding window and the analysis does not hold.

The precondition, again

Chapter 4's converging pointers needed sortedness. A shrinking window needs its own guarantee, and it is easy to miss because the code looks the same either way.

Minimum Size Subarray Sum — the shortest contiguous run summing to at least a target — is a classic window. On 400 random all-positive inputs it matches brute force every time. Allow negative values and it is wrong on 1,228 of 5,000 inputs. On [-2, 5, -1, 5, 3] with target 8 it reports a length of 4; the answer is 2.

Why negatives break it

The shrink condition assumes that removing an element from the left can only make the window worse — smaller sum, fewer characters, less coverage. That is what licenses "shrink while the condition still holds, and stop when it breaks".

With a negative value in the window, removing it increases the sum. Growing the window can also decrease the sum, so the sum is no longer monotonic in the window's endpoints, and "I stopped shrinking here" no longer means "this is the shortest valid window ending here". The code runs happily and answers wrongly, on about a quarter of inputs. When negatives are allowed, the answer is prefix sums with a hash map — chapter 6.

The generalisation: a sliding window works when the condition is monotonic in the window — once adding elements makes it true it stays true, and once removing them makes it false it stays false. Check that before writing the loop, the same way chapter 4 asked you to complete the discard sentence.

At most, at least, exactly

Three phrasings that look interchangeable and are not.

Which phrasing admits a window
PhrasingDirect window?Approach
At most kYesShrink while the count exceeds k
At least kYesShrink while still satisfied, recording as you go
Exactly kNoatMost(k) − atMost(k−1)

"Exactly k" has no monotonic shrink condition — a window with too few distinct values is fixed by growing, one with too many by shrinking, and there is no single direction to move. But it is the difference of two problems that do have one.

counting subarrays with exactly k distinct values
exactly(k) = atMost(k) - atMost(k - 1)

// on [1,2,1,2,3]:  atMost(2) = 12,  atMost(1) = 5,  so exactly(2) = 7
// verified against exhaustive search on 400 random inputs

// and inside atMost, the counting line is the subtle part:
total += hi - lo + 1     // EVERY window ending at hi is valid,
                         // not just the longest one

That last line catches people. Once the window [lo, hi] is legal, so is every window ending at hi that starts later — there are hi − lo + 1 of them, and they all get counted at once. Adding 1 instead counts only the longest and undercounts badly.

Minimum Window Substring is the hardest common instance, and it is the same template with a richer state: a count map of what is still needed and a single missing counter so the condition is Θ(1) to test rather than Θ(alphabet). Verified against brute force on 300 random inputs, and over 5,000 characters its total pointer movement stays under 2n, exactly as the argument predicts.

Check yourself

There is a while inside the for. Why is it not Θ(n²)?

Because the left pointer only ever moves forward, so across the whole pass it takes at most n steps in total — however they are distributed. The inner loop can run 500 times on one outer iteration, but then it cannot run on 500 others. Total work is advances plus shrinks, bounded by 2n. Measured over 20,000 characters: 20,000 advances and 19,998 shrinks, 39,998 moves. If the left pointer reset to zero each step the cost would be n(n+1)/2 ≈ 200 million — five thousand times more.

What is the practical check that your window really is linear?

That lo only ever increases and never resets. If your logic needs to move the left pointer backwards — because a later element made an earlier position valid again — the amortised argument does not hold and you do not have a sliding window. That usually means the condition is not monotonic, which is the same diagnosis as the negative-numbers case, and the fix is normally prefix sums or dynamic programming rather than a smarter window.

Why does Minimum Size Subarray Sum break when negative values are allowed?

Because the shrink condition assumes that removing a left element can only make the window worse. With a negative in the window, removing it increases the sum, and growing the window can decrease it — so the sum is no longer monotonic in the endpoints and "I stopped shrinking here" no longer means "this is the shortest valid window ending here". It is wrong on 1,228 of 5,000 random inputs with negatives: on [-2, 5, -1, 5, 3] with target 8 it reports 4 where the answer is 2. Nothing errors. With negatives, use prefix sums plus a hash map.

Rolling sum versus rescanning the window. How much does it save?

A factor of k, because rescanning re-reads the whole window at every position. On 5,000 values with k = 250, rolling does 5,000 operations and rescanning does (n−k+1)·k = 1,187,750 — a 238-fold difference, and the measured ratios for k of 10, 100 and 1,000 are 10×, 98× and 800×. The window's contents never need re-reading: add the element entering, subtract the one leaving.

"Count subarrays with exactly k distinct values." Why is there no direct window?

Because there is no monotonic shrink condition. Too few distinct values is fixed by growing, too many by shrinking, so there is no single direction the left pointer can move — and monotonicity is exactly what the pattern requires. The fix is that "exactly" is the difference of two problems that do have one: atMost(k) − atMost(k−1). On [1,2,1,2,3] that is 12 − 5 = 7, which matches exhaustive search, as it does on all 400 random inputs tested.

Inside atMost, why is the counting line hi − lo + 1 rather than 1?

Because once the window [lo, hi] is valid, every window ending at hi that starts later is also valid — a subrange of a valid range cannot have more distinct values. There are hi − lo + 1 of them and they are all counted in one step. Adding 1 counts only the longest window at each position and undercounts badly. This is the single most common bug in counting-window problems, and it produces answers that look plausible on tiny inputs.

Your "at most k distinct" window is accepting too-wide ranges. What is the likely bug?

You are decrementing counts on shrink but not deleting the key when the count reaches zero. map.size then counts characters that have already left the window, so the condition silently becomes "at most k ever seen" rather than "at most k currently present" — and since that is a weaker condition, the window grows too far. It is invisible in the code, because the decrement looks complete. Delete the key at zero, or track a separate distinct counter you adjust explicitly.

Ten things to carry forward

  1. A window is maintained, not rebuilt — which is why "contiguous" is the word that triggers it.
  2. Fixed windows roll: add the entering element, subtract the leaving one, and save a factor of k.
  3. Variable windows grow right always and shrink left while violated. One template, three decisions.
  4. The nested while is not quadratic because the left pointer only moves forward — at most 2n total.
  5. 39,998 pointer moves over 20,000 characters, against 200 million if the left pointer could reset.
  6. Check that lo never decreases. If it must, you do not have a window.
  7. The condition has to be monotonic. Negatives break Minimum Size Subarray Sum on a quarter of inputs.
  8. At most and at least admit windows; exactly does not — use atMost(k) − atMost(k−1).
  9. Count hi − lo + 1, not 1, because every shorter window ending here is valid too.
  10. Delete zero-count keys, or size reports characters that have already left.
