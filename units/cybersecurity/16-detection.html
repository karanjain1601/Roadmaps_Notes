Detection engineering

Turning telemetry into something that tells you when to act. The discipline is younger than the tooling suggests, and its central insight is that a detection is a piece of software with a lifecycle — it is written, tested, deployed, measured, tuned, and eventually retired — rather than a rule you buy and switch on.

16.1Four ways to detect

Each finds a different kind of thing
ApproachFindsFails on
Signature / indicatorKnown-bad hashes, addresses, domains, stringsAnything new. Bottom of the pyramid of pain — ch 4
Behavioural ruleTechniques: a process tree, a command-line pattern, a sequenceThe workhorse. Fails on techniques nobody has characterised yet
Anomaly / baselineStatistical deviation — a user, host or account behaving unlike itselfNoisy. "Unusual" and "malicious" overlap far less than vendors imply
DeceptionInteraction with something that should never be touchedNear-perfect precision, low volume — ch 12

Most of a good programme is behavioural rules with a layer of signatures underneath for cheap known-bad coverage and a sprinkling of deception for high-precision catches. Anomaly detection has a real place — impossible travel, a service account suddenly interactive, a host resolving ten thousand unique subdomains — but the general form of "alert me when anything is unusual" fails on the base rates from Chapter 12, because most unusual things are benign and there are a great many of them.

16.2Writing a detection that survives

Anatomy of a rule worth deploying 
NAME       what it detects, in plain words
TECHNIQUE  the ATT&CK reference, so coverage can be mapped
LOGIC      the query, expressed against normalised fields
DATA       which sources it needs — and therefore what breaks
           it if one goes quiet
SEVERITY   what the analyst should do, not how bad it sounds
CONTEXT    the fields an analyst needs to triage without
           running four more queries
FALSE POSITIVES
           the known-benign causes, written down BEFORE
           deployment, with what to check for each
RESPONSE   the first three steps. A rule with no runbook
           becomes a rule that gets ignored
TESTS      an execution that should fire it, and one that
           should not. Run both when anything changes.

WRITE FOR THE TECHNIQUE, NOT THE PROCEDURE
  ✗  command line equals "powershell -enc SQBFAFgA"
  ✓  powershell with an encoded-command flag AND a hidden
     window AND a parent that is not an administrative tool
  The first catches one campaign. The second catches a class,
  and keeps working when the payload changes.

PREFER A JOIN OVER A THRESHOLD
  A single suspicious event is usually ambiguous. Two
  correlated ones rarely are: an encoded PowerShell command
  is common; an encoded PowerShell command from a document
  process on a host that has never run PowerShell before is
  not. Correlation buys precision without losing recall,
  which is the only free lunch in this chapter.
Detection as code

Rules belong in version control, in a portable format such as Sigma, with review, tests and a deployment pipeline — for the same reasons application code does. It gives you history when a rule stops firing, review before something noisy reaches production, the ability to test a change against recorded data before deploying it, and portability if you change platform. The common alternative — rules edited directly in a console by whoever is on shift, with no record of why — produces a ruleset nobody understands, containing exclusions added years ago for reasons nobody remembers, which is how detections quietly stop covering what they were written for.

16.3The tuning lifecycle

Is this rule worth keeping?

A new rule is deployed. Tuning improves precision each round — but only if the false positives are systematic.

Exclusions are where detections go to die

Every tuning round adds an exclusion, and exclusions accumulate silently. A rule that excludes a directory, then a service account, then a subnet, then a parent process, eventually excludes exactly the conditions an attacker will operate under — and the excluded path is one an attacker can deliberately choose, because exclusion lists leak through helpdesk tickets and are guessable from what an environment looks like. Three habits that keep this honest: exclude narrowly, matching several fields together rather than one broad path; date every exclusion with an owner and a reason, and review them; and prefer risk-scoring over exclusion, so a known-benign pattern lowers the score rather than disappearing entirely, which keeps it visible when it combines with something else.

16.4Hunting

Detection rules find what you have characterised. Hunting is the deliberate search for what you have not — a structured investigation starting from a hypothesis rather than an alert.

The loop 
1  HYPOTHESIS
   Specific and falsifiable, from a technique, a threat
   report, an architectural weakness or an anomaly.
   ✗ "look for anything odd in the proxy logs"
   ✓ "an attacker using DNS tunnelling would produce a
      host with an unusually high count of unique
      subdomains under one parent domain"

2  FIND THE DATA
   Which source would show it, and do we have it, with the
   right fields, for long enough? Very often the hunt ends
   here — and THAT IS A RESULT: a documented visibility gap
   is more valuable than an inconclusive search.

3  SEARCH, and expect to find benign explanations
   Most hunts find no attacker and several surprises: a
   forgotten service, a misconfiguration, shadow IT, a
   backup job nobody documented.

4  WHATEVER YOU FIND, PRODUCE AN ARTEFACT
   Found an intrusion    → incident response
   Found a benign oddity → fix it, or document it
   Found nothing         → write the detection anyway if the
                           technique is relevant, or log the
                           visibility gap
   A hunt that produces no artefact was entertainment.

5  AUTOMATE WHAT REPEATS
   Anything you hunt for twice should be a scheduled rule.
   The hunting function should be continuously converting
   itself into detection engineering.

Hunting cadence and time to discovery

Rules catch what they cover, immediately. Hunting catches the rest, on average halfway through the interval.

When should you delete a detection rule rather than tune it?

When the remaining false positives are not systematic, or when the cost of the queue exceeds the value of the catch. Tuning works by finding structure in the noise — a service account that always triggers it, a backup job, a directory a legitimate tool writes to — and each exclusion removes a whole cause. If several rounds of tuning have removed the structured causes and the rule still fires on scattered one-off benign activity, further tuning has nothing to grip on and each round buys progressively less. At that point compute the arithmetic honestly: alerts per month times minutes to triage gives the cost, against a true positive rate that may be well under one a year, and if the rule has never fired truly in its lifetime that is evidence too. Three refinements before deleting. Demote rather than delete — move it from an alert to a scheduled report or a risk-score contribution, so the signal still exists and combines with others without consuming triage. Check whether the rule is wrong or the data is, since a noisy rule is sometimes a correctly-written detection against a source with poor field quality, and fixing the source fixes several rules at once. And check whether it is duplicating another rule that catches the same thing more precisely. What matters most is the cultural point: a programme that never deletes accumulates rules nobody trusts, and an untrusted queue is worse than a smaller trusted one, because analysts learn to dismiss rather than investigate — so retiring rules should be a tracked, celebrated activity rather than an admission of failure.

A hunt finds nothing. Was it wasted?

Only if it produced no artefact, and a hunt that finds no attacker usually produces two other things worth more than the search. The first is a visibility finding: very often the hunt cannot be completed because the data does not exist, the field is not populated, retention is too short, or a subset of hosts do not report. That is a concrete, actionable gap that would otherwise have been discovered during an incident, at the worst possible moment, and documenting it is a better outcome than a clean negative result. The second is a detection: if the technique is relevant to your environment, the query you just wrote is most of a rule, and turning it into a scheduled detection means you never have to hunt for that particular thing again. There is also a reliable third category — hunts routinely surface benign oddities that matter operationally: a forgotten server still running, a service account with unexpected permissions, an unapproved tool in wide use, a misconfiguration nobody had noticed. Two cautions to keep it honest. A negative result is only meaningful if you can state what it covered — "no evidence of this technique across hosts reporting Sysmon over the last thirty days" is a claim; "we looked and found nothing" is not, because the coverage and the window are exactly what a reader needs. And hunting should be converting itself into detection engineering over time; if the same hunts keep being run manually, the programme is not compounding, and the measure of a mature hunting function is how much of it has been automated away.

Why does correlating two weak signals beat lowering the threshold on one?

Because it improves precision without sacrificing recall, which nothing else in detection does. Lowering a threshold moves you along a single trade-off curve: you catch more real events and you catch proportionally more benign ones, so the alert volume rises faster than the true positives and precision falls — and at security base rates, where benign events outnumber malicious ones by six orders of magnitude, a small threshold relaxation can multiply the queue while adding a fraction of a true positive. Correlation changes the curve instead of moving along it. If two conditions are individually common but rarely co-occur in benign activity, requiring both multiplies their false positive rates while leaving the true positive rate nearly intact, because a real attack tends to produce both. An encoded PowerShell command line is common in administration; a parent process that is a document application is common; both together on a host that has not run PowerShell before is essentially never benign. The practical guidance follows: prefer joins across sources, because signals from different telemetry are more likely to be independent than two fields from the same event; add temporal proximity, since "within five minutes" is a strong constraint that costs almost no recall; and add rarity, since first-time-seen behaviour for a given host or account is a cheap and powerful second condition. Two limits worth knowing. Correlation requires both sources to be present and time-synchronised, so it inherits the fragility of whichever source is weakest — and it fails silently if one goes quiet, which is why source-silence alerting from Chapter 15 underpins it. And an attacker who knows the correlation can break it by separating the actions in time, which is an argument for varying the window rather than publishing it.

Recap

  1. Behavioural rules are the workhorse, with signatures beneath for cheap coverage and deception above for precision.
  2. "Alert me when anything is unusual" fails on base rates. Most unusual things are benign.
  3. Write for the technique, not the procedure, so the rule survives the payload changing.
  4. Prefer a correlation over a lower threshold — it buys precision without costing recall.
  5. A rule needs documented false positives and a runbook before deployment, or it gets ignored.
  6. Detection as code: version control, review, tests, and a record of why each exclusion exists.
  7. Exclusions accumulate into blind spots an attacker can deliberately occupy. Date them and review them.
  8. Delete rules when the noise stops being systematic. A programme that never retires anything is untrusted.
  9. A hunt that finds nothing should still produce an artefact — a detection or a documented visibility gap.
  10. Measure precision, time to detect, tested coverage and the share of incidents found internally.
