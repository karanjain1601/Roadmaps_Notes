Logging and telemetry

Detection, investigation and proof all rest on the same foundation: a record of what happened. The uncomfortable part is that the record is decided long before the incident, mostly by defaults nobody examined — and the question you cannot answer at 3am is the one whose log source was switched off eighteen months earlier for storage reasons.

The most useful telemetry is off by default

Windows does not log process creation until you enable it, and even then omits the command line unless you enable that separately — which means the single most valuable field for detection, the arguments a process was started with, is absent from most estates. PowerShell script block logging, module logging and transcription are all off. Linux distributions ship with auditd rules that log almost nothing useful. DNS query logging on a resolver is off, or on and discarded. Cloud data-plane logging is separate from control-plane logging and usually disabled for cost. The pattern is consistent: vendors default to low volume, and low volume means low visibility. Auditing what you actually collect against what the platform can emit is a short exercise that routinely finds the most important sources missing.

15.2Log quality

Collecting a log is not the same as being able to use it. Five properties decide whether a source is worth what you pay to store it.

What makes a log usable 
TIMESTAMPS THAT AGREE
  Everything in UTC, with sub-second precision, from a common
  time source. Correlation across sources is impossible if
  clocks differ, and an attacker who can shift time on a host
  can reorder your reconstruction. NTP is a security control
  for this reason alone.                              → ch 9

IDENTITY THAT RESOLVES
  A log saying "10.4.7.22 did X" is nearly useless three
  months later unless you can map that address, at that
  moment, to a machine and a person. DHCP leases, VPN session
  records and directory data are what make network logs
  investigable. Keep them as long as the logs they explain.

CONSISTENT FIELDS
  Normalise at ingestion — one field name for source address,
  one for username, one for hostname — or every query has to
  know each source's idiosyncrasies. This is unglamorous and
  it is most of the value a SIEM adds.

ENOUGH CONTEXT TO DECIDE
  "Process created" is nearly useless. "Process created, this
  binary, this command line, this parent, this user, this
  hash, this directory" is a detection. The extra fields cost
  little and change everything.

COMPLETENESS YOU CAN VERIFY
  Monitor for sources going quiet. A host that stops sending
  logs looks identical to a host with nothing to report, and
  silencing telemetry is an early attacker action — so
  absence of events must itself raise an alert.

15.3Volume, cost and retention

Every logging decision is a budget decision, and the constraint is real — telemetry at full fidelity across a large estate costs more than most security teams spend on everything else. The question is where to spend it.

Retention against dwell time

Retention shorter than dwell time means the start of the intrusion is already gone when you begin looking.

Retention must exceed dwell time plus investigation time

If an intrusion goes unnoticed for three weeks and you keep two weeks of logs, then on the day you detect it the evidence of how it began no longer exists — you can see the current activity and not the entry point, which means you cannot establish scope, cannot know what else was touched, and cannot state with confidence that you have removed the attacker. The arithmetic is simple and frequently unmet: retention ≥ dwell time + investigation duration, and since many intrusions are found by a third party months later, a meaningful archive tier matters even when hot search is short. Tiering is how this is affordable — recent data hot and searchable, older data in cheap object storage you can rehydrate when needed.

15.4Deciding what to collect

A sequence that gets the most value soonest 
1  AUTHENTICATION, everywhere
   Identity provider, VPN, domain controllers, cloud, SaaS.
   Cheap, usually already emitted, and it covers the
   techniques the perimeter and endpoint controls miss.

2  CLOUD CONTROL PLANE
   Low volume, irreplaceable, and shipped to a separate
   account so an attacker cannot delete it.

3  PROCESS CREATION WITH COMMAND LINE
   The highest-value endpoint source. Enable it and the
   command-line field, or deploy Sysmon with a curated
   configuration. Filter noisy known-good at the agent
   rather than paying to ingest and then ignore it.

4  DNS
   Per-client resolution logs. Excellent value; catches
   tunnelling, algorithmically generated domains, and
   newly registered domains.

5  EMAIL GATEWAY
   Delivery records, so a phishing report can be scoped to
   everyone else who received it, within minutes.

6  APPLICATION ACCESS LOGS for the systems holding your
   most sensitive data. Nothing at the infrastructure layer
   can tell you which records were read, and that is exactly
   the question a regulator asks.

FILTER AT THE EDGE, NOT IN THE QUERY
  The cheapest event is the one you never ingest. Drop
  known-good high-volume noise at the agent or forwarder —
  but keep a sample, and write down what you dropped, because
  the exclusion list is the first thing to review when a
  detection mysteriously never fires.

Logs are a data protection liability too

Log stores accumulate things nobody intended to keep: passwords typed into a username field, tokens in URLs, personal data in request payloads, full email addresses, and occasionally card numbers. That makes the log platform a high-value target and a regulatory obligation in its own right — it is subject to the same retention limits, access controls and deletion requests as any other system holding personal data. Two practical consequences: scrub or hash sensitive fields at ingestion rather than after, and remember that "we keep everything forever" is a compliance problem as well as a cost one.

Why is process creation logging with the command line so much more valuable than without?

Because the binary name is almost never the interesting part, and the arguments almost always are. powershell.exe ran is unremarkable — it runs constantly for legitimate management. powershell.exe -nop -w hidden -enc SQBFAFgA… is an encoded, hidden, profile-free command, which is not what administration looks like. The same holds throughout: rundll32.exe is normal and rundll32.exe javascript:… is not; certutil.exe is a certificate utility and certutil -urlcache -f http://… is a downloader; wmic is administrative and wmic process call create from a document is not. Since modern intrusions deliberately use legitimate signed binaries (chapter 3), the command line is frequently the only field that distinguishes an attack from routine work, and without it your detections are reduced to noticing that a normal program ran normally. Two adjacent points. The parent process is nearly as valuable, because it encodes context the binary cannot — Word spawning a shell is the detection, and neither Word nor the shell is suspicious alone. And this is precisely the field that is off by default on Windows: process creation auditing must be enabled, and the command-line inclusion is a separate setting that is disabled even when auditing is on, so a great many organisations believe they have process logging and do not have the field that makes it useful. Sysmon with a curated configuration gives all of it plus hashes and network attribution, and filtering the known-good at the agent keeps the volume manageable.

Your SIEM licence is capped and you must cut ingestion by a third. What do you cut?

Cut by volume-per-value, not by source, and do the filtering as far upstream as possible. The largest volumes are usually firewall and flow logs, verbose web server access logs, and high-frequency endpoint events like file-system writes to temporary directories — and much of that is known-good noise that nobody has ever queried. Start by measuring which sources and which event types actually appear in searches and detections over the last few months: it is routine to find that a source consuming a quarter of the licence has never been used in an investigation. Then filter at the agent or forwarder rather than at ingestion, because the cheapest event is the one you never send, and keep a sampled subset of what you drop so you can still see the shape of it. Three things not to cut. Authentication logs, which are low volume and cover exactly the techniques the network and endpoint controls miss. Cloud control plane, for the same reason. And process creation with command lines, which is the highest-value endpoint source — if it is too voluminous, filter noisy known-good parent-child pairs rather than dropping the source. Two structural alternatives worth considering before cutting anything: tiering, where full-fidelity data goes to cheap object storage and only the searchable subset is licensed, which often removes the constraint entirely; and pushing detection to the source, since some events can be evaluated at the agent and only the matches forwarded. Finally, write down what you excluded and review it whenever a detection unexpectedly never fires, because a forgotten filter is indistinguishable from a broken rule.

Why alert when a log source goes quiet?

Because absence of events and absence of activity look identical, and only one of them is good news. A host that has stopped forwarding logs produces exactly the same view as a host on which nothing has happened — an empty result — so every detection you have silently stops applying to it and nobody notices, sometimes for months. The causes are mostly mundane: an agent crashed, a certificate expired, a forwarder's disk filled, a firewall rule changed, a machine was rebuilt without the agent, a licence cap started dropping events. Each of those quietly removes coverage while the dashboards continue to look healthy, which is the worst kind of failure because it degrades your detection without degrading your confidence. It is also a deliberate attacker action: stopping the agent, clearing the log, or reconfiguring forwarding is a standard early step, and in a cloud account disabling the audit trail is a single API call. So silence carries information in both cases and should be treated as an event. Practically this means maintaining an expected-sources inventory and alerting when a source's event rate drops materially below its own baseline rather than to zero, since a partial failure is more common than a total one and harder to spot. Two refinements: baseline per source and per hour, because a workstation legitimately goes quiet overnight and a server does not; and reconcile the reporting inventory against an independent list of assets, because a machine that never sent logs at all will never trigger a "stopped sending" alert.

Recap

  1. Authentication, DNS and process creation are the highest value per unit of effort.
  2. The most useful telemetry is off by default, and the Windows command-line field is a separate setting from process auditing.
  3. Application access logs are the usual gap — no infrastructure source shows which records were read.
  4. Timestamps must agree, which makes NTP a security control.
  5. Identity must resolve. Keep DHCP and VPN session data as long as the logs they explain.
  6. Retention ≥ dwell time + investigation duration, or the entry point is already gone when you look.
  7. Tiering is what makes long retention affordable — hot search short, archive long.
  8. Filter at the edge, keep a sample, and write down what you dropped.
  9. Logs must leave the host fast, be write-once, and sit in a separate trust boundary.
  10. A source going quiet is a signal. Alert on it, and reconcile against an independent inventory.
