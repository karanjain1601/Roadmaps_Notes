Digital forensics

Establishing what actually happened, in a way that survives scrutiny. Most of the difficulty is not analysis but sequence: evidence disappears in a predictable order, and the decisions made in the first ten minutes determine which questions remain answerable.

~28 min read Volatility · acquisition · timelines · custody 2 interactive panels Prerequisite: chapters 3, 17

18.1Order of volatility

The governing principle, from RFC 3227: collect evidence in order of how quickly it disappears. Everything you do to a machine changes it, so the sequence is not a preference but a constraint.

What each action costs you

A responder arrives at a suspect machine. Choose what they do, and see what survives.

Memory first, and it is not close

A memory image contains things that exist nowhere else: running processes including ones hidden from the operating system's own APIs, network connections, injected code, decrypted configuration, credentials and keys in cleartext, command history, and the contents of files that were only ever opened and never written to disk. Against a fileless intrusion — which describes a large share of modern activity — memory is frequently the only place the malicious code exists at all. It is also the first thing to vanish: powering off destroys it entirely, and even leaving the machine running degrades it as pages are reused. Capturing it takes minutes with a tool prepared in advance, and the preparation is the hard part, because nobody wants to be downloading an acquisition tool onto a compromised host.

The rules that make evidence hold up 
WORK ON COPIES. Hash the original, hash the copy, prove they
match, and analyse the copy. The original is never touched
again.

USE A WRITE BLOCKER for physical disks. Simply attaching a
disk to a running system modifies it — timestamps update,
recovery files are written, indexing starts.

DOCUMENT EVERYTHING as you go: what you ran, when, on which
system, under whose account, and what it returned. An action
you cannot account for casts doubt on everything else.

CHAIN OF CUSTODY, unbroken: who had the evidence, when, and
what they did with it. A gap is the first thing challenged.

RECORD YOUR OWN FOOTPRINT. You WILL change the system by
investigating it. That is fine and expected; what is not
fine is being unable to distinguish your changes from the
attacker's afterwards.

TIME: record the system's clock AND the true time, and note
the offset and the timezone. Every timeline depends on it,
and a machine with a wrong clock will silently misplace
every event you correlate against it.

18.3Building a timeline

The core analytical product. Nearly every question an incident asks — when did this start, what did they touch, is this the entry point — is answered by putting events from many sources onto one ordered list.

Which artefacts answer which question

Different sources survive different actions and cover different windows.

Timestamps lie, in several different ways

A file has multiple times — modified, accessed, created, and metadata-changed — and they behave differently: copying a file gives it a new creation time later than its modification time, which is a well-known tell but also a source of honest confusion. Timestamps can be set deliberately to arbitrary values, a technique called timestomping, and a common signature is a file whose recorded times are impossibly precise or predate the operating system's installation. Access times are frequently disabled for performance, so their absence means nothing. And the file system may record times the operating system's API does not show, which is why some tools disagree — a discrepancy between the two is itself evidence. The practical response is to corroborate across independent sources: a file timestamp on its own is weak, and the same event appearing in a log, a registry key, a journal entry and a memory artefact is strong.

The pattern worth extracting: anti-forensics removes specific artefacts and rarely removes the fact that something happened. A cleared log leaves a clearing event and a gap; a wiped file leaves an execution record for the wiper; a disabled agent leaves silence where there was telemetry. Investigations frequently pivot on those absences, which is why the strongest single defence against anti-forensics is having the evidence somewhere the attacker cannot reach — centralised logs, immutable storage, and a separate trust boundary.

Two preparations pay for themselves entirely. Set instances to be preserved rather than terminated on a security event — an autoscaling group that replaces a compromised instance destroys the evidence automatically and looks like healthy self-healing. And enable and export the audit trail before you need it, because unlike a disk you cannot retrospectively acquire a log that was never written.

Why capture memory before doing anything else, even before isolating the host?

Because memory is the most volatile source and contains things that exist nowhere else, and every action degrades it. A memory image holds the running process list including entries hidden from the operating system's own APIs by a rootkit, active network connections and the processes owning them, code injected into legitimate processes, decrypted malware configuration and command-and-control addresses, credentials and encryption keys in cleartext, command history, and the contents of files that were opened but never written to disk. For a fileless intrusion, which describes a large share of modern activity, the malicious code exists only there — image the disk and you will find nothing at all. Powering off destroys it completely and instantly; even leaving the machine running degrades it steadily as pages are reused, so the delay before someone acts is itself a loss. As for isolating first: network isolation via an EDR agent is generally safe to do alongside capture and does not destroy memory, so in practice the two are near-simultaneous — the ordering that matters is memory before anything that reboots, shuts down, or writes substantially to the system. The genuine exception is full-disk encryption where the key exists only in memory: powering off in that state can render the disk unreadable entirely, which makes memory capture not merely the first priority but a prerequisite for the disk being useful at all. The practical constraint is preparation: capture takes minutes with a tool staged in advance and is close to impossible if you are downloading one onto a compromised host at 2am.

An attacker cleared the Windows event logs. Is the investigation over?

No, and in some ways the clearing helps you. First, the clearing itself is recorded — Windows writes an event for the log being cleared, and its timestamp bounds the activity you are looking for, so you have gained a fact rather than only lost one. Second, if logs were being forwarded centrally in near real time, as they should be, the copies already left the host and clearing the local ones achieves nothing except to tell you which host to look at closely. Third, event logs are only one of many artefact sources on a Windows system: execution evidence persists in prefetch files, shimcache and amcache, in the registry, in scheduled task definitions, in service configurations and in userassist entries; file system journals record changes independently of the event log; browser and application data survive; and the memory image, if captured, is untouched by log clearing entirely. Fourth, other hosts saw this one — authentication attempts appear on domain controllers, network flows appear at the firewall, DNS queries appear at the resolver, and none of those are on the machine the attacker controlled. The general principle is the one from §18.4: anti-forensics removes specific artefacts and rarely removes the fact that something happened, and the resulting gap is itself an indicator that narrows your search. What clearing does genuinely cost you is precision and time, and the defence that makes it nearly irrelevant is architectural rather than investigative — forward logs off the host immediately, to a separate trust boundary with write-once retention, so the copy that matters was never the attacker's to delete.

Why does chain of custody matter if you have no intention of prosecuting anyone?

Because the audiences who will scrutinise your findings extend well beyond a criminal court, and most incidents involve at least one of them. A regulator deciding whether your breach notification was accurate will ask how you established what data was accessed. An insurer assessing a claim will ask how you know the sequence of events you have described. A customer under contract, or their auditor, may require evidence that you determined scope properly. A civil action can arrive years later from a party you have not thought about, and by then nobody remembers who had which disk image. And internally, a retrospective that leads to significant change — or to someone's dismissal — needs findings that hold up to challenge from people with an interest in disputing them. In all of those, the question is the same: can you demonstrate that the evidence you analysed is what it purports to be, and that it was not altered? That means hashing at acquisition and being able to prove the copy matches, an unbroken record of who held it and what they did, working on copies rather than originals, and documenting your own actions so your changes can be distinguished from the attacker's. There is also a practical benefit that has nothing to do with defensibility: incidents run for weeks with people rotating in and out, and rigorous documentation is what stops the team re-deriving the same conclusions, contradicting each other in a status update, or discovering on day twelve that the image everyone has been analysing came from the wrong host. The discipline costs very little at the time and is impossible to reconstruct afterwards.

Recap

  1. Collect in order of volatility. Memory first, and it is not close.
  2. Memory holds what exists nowhere else — hidden processes, injected code, decrypted configuration, keys.
  3. With full-disk encryption, powering off can make the disk unreadable, so memory is a prerequisite not a preference.
  4. Work on hashed copies, with a write blocker, and never touch the original again.
  5. Record your own footprint, so your changes can be distinguished from the attacker's.
  6. Note the clock offset. Every correlation depends on it.
  7. Corroborate timestamps across independent sources, because a single file time is weak evidence.
  8. Anti-forensics removes artefacts, not the fact that something happened, and the gap is itself an indicator.
  9. Cloud makes acquisition easy and memory hard. Preserve instances rather than terminating them.
  10. Chain of custody matters for regulators, insurers and auditors, not only for courts.
