CHAPTER 14

Images, fonts and scripts

Three asset types Next gives you a component for, because all three are easy to get wrong in ways that cost either a great many bytes or a visibly jumping page. The components help; two of them need one prop set correctly to help at all.

Part 4 The product layer·Reading time 35 minutes·Demos which image the browser picks, measured font swap·Prerequisites Chapter 13

1next/image

Six things it does, and the two ways to tell it about size.

What you get
Resizing to the sizes actually needed, format negotiation to AVIF or WebP, lazy loading below the fold, a reserved box so nothing shifts, an optional blurred placeholder, and caching of the derived variants.
Two sizing modes
Intrinsic — a static import, or explicit width and height, giving the aspect ratio so the space can be reserved. Fill — fill on an absolutely-positioned image in a container you have sized, with object-fit. Use fill when the dimensions are only known from CSS.
A static import is the easiest correct thing
import hero from './hero.jpg' gives Next the real dimensions at build time, so you cannot get the aspect ratio wrong and a blur placeholder is generated for free.
priority for the one above the fold
It disables lazy loading and preloads the image. Set it on your LCP image and on nothing else — marking several defeats the purpose, since everything is then competing.
Remote images need allow-listing
images.remotePatterns in next.config. This is a security boundary, not an inconvenience: without it your optimiser would resize arbitrary URLs on request.
When not to use it
SVG icons — inline them or use a plain <img>; there is nothing to optimise and rasterising is a downgrade. And a fully static export has no optimiser, so it needs unoptimized or a third-party loader.

2The sizes prop

The most misunderstood prop in the component, and getting it wrong wastes most of the benefit.

It describes layout, not the image

sizes tells the browser how wide the image will be at a given viewport width, so it can choose a candidate before any CSS has been applied. It is not the image's dimensions and it is not a resize instruction. Get it wrong and the browser picks using its default assumption — that the image is the full viewport width — and downloads something far larger than the slot it lands in.

Writing it for a real grid JSX
// The grid: 1 column on mobile, 2 on tablet, 4 on desktop,
// inside a container capped at 1200px with 24px gaps.
<Image
  src={product.image}
  alt={product.name}
  width={600} height={600}
  sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 300px"
/>

// Read it as: below 640px the image fills the viewport; below
// 1024px it is half; otherwise it is 300px wide because the
// container stops growing. The last value has no media query and
// is the fallback — it must come last.
//
// With `fill`, sizes is effectively required: there is no width to
// infer anything from, so without it the browser assumes 100vw.

3next/font

Four things, and the fourth is the one nothing else gives you.

Google and local fonts TypeScript
import { Archivo } from 'next/font/google';
import localFont from 'next/font/local';

const sans = Archivo({
  subsets: ['latin'],            // only the glyphs you need
  display: 'swap',
  variable: '--font-sans'          // expose it as a custom property
});

const brand = localFont({
  src: [{ path: './Brand-Variable.woff2', weight: '100 900' }],
  display: 'swap', variable: '--font-brand'
});

// app/layout.tsx
<html className={`${sans.variable} ${brand.variable}`}>

/* globals.css — now usable from anywhere, including Tailwind's config */
body { font-family: var(--font-sans), system-ui, sans-serif; }
1 · Self-hosted at build time
Google fonts are downloaded during the build and served from your own domain. No request to a third party at runtime, no extra DNS lookup and connection, and no dependency on their availability.
2 · Subsetted
Declaring subsets strips glyphs you will never render, which for a Latin-only site removes most of a large font file.
3 · A variable font is one file
Rather than four static weights. Prefer them where available and stop enumerating weights.
4 · Fallback metrics, automatically
This is the part worth understanding. Next computes size-adjust, ascent-override and related descriptors so the fallback font occupies almost exactly the same space as the real one — so when the swap happens, nothing moves. Section 4 measures it.

Verdict—

display: 'swap' is the right default
Text is readable immediately in the fallback and swaps when the real font arrives. block hides text until the font loads, which is invisible text rather than shifted text — usually worse. optional gives up on the swap entirely if the font is slow, which is defensible for body text on a very slow connection.
Choose a fallback with similar metrics
The override can only stretch so far. A condensed sans against a wide serif fallback will still move. Pair like with like and the correction is small.
Two families is usually plenty
Each additional family is another file on the critical path. A variable font with a wide weight range replaces several static ones.

5next/script

Four strategies. Picking the wrong one is how a tag manager ends up delaying your first paint.

StrategyLoadsUse for
beforeInteractiveBefore any hydration, blockingAlmost nothing. A consent manager or a bot-detection script that must run first. Everything here delays your page.
afterInteractiveRight after hydration (default)Analytics, tag managers, anything that should run early but need not block.
lazyOnloadDuring browser idle timeChat widgets, support bubbles, social embeds, heat mapping. Most third-party scripts belong here.
workerIn a web workerExperimental, via Partytown. Genuinely promising for analytics, and check its status for your version before relying on it.
And the case for loading it on interaction instead JSX
<Script src="https://widget.example/chat.js" strategy="lazyOnload" />

// Better still for a chat widget: do not load it at all until
// somebody wants it. A 240 kB bundle that 2% of visitors open is
// 240 kB wasted on 98% of them.
'use client';
const [open, setOpen] = useState(false);
return (
  <>
    <button onClick={() => setOpen(true)}>Need help?</button>
    {open && <Script src="https://widget.example/chat.js" />}
  </>
);
Third-party scripts are usually the largest thing on the page
Bigger than your own JavaScript, on many sites. They also run on the main thread, so they compete directly with your interactivity — Chapter 26 of the Front-end unit covers measuring this.
Audit them by asking who owns each one
Every tag was added for a reason that may no longer apply. A script nobody can name an owner for is a script to remove.
next/third-parties for the common ones
Wrappers for Google Analytics, Tag Manager, YouTube embeds and Google Maps with sensible loading behaviour already applied. Cheaper than getting the strategy right yourself.

6Check yourself

Five questions.

1. What does sizes actually tell the browser?

How wide the image will be laid out at a given viewport width — not the image's own dimensions, and not a resize instruction. The browser needs that before any CSS has been applied, because it wants to start the download early, so you are describing your layout in advance. Omit it and the browser assumes the image is the full viewport width, then multiplies by the device pixel ratio and picks a candidate on that basis, which on a four-column grid means downloading something several times larger than the slot. With fill it is effectively required, since there is no width to infer anything from.

2. Why is a static image import the easiest correct option?

Because import hero from './hero.jpg' gives Next the real intrinsic dimensions at build time. You cannot get the aspect ratio wrong, the space is reserved exactly so nothing shifts, and a blur placeholder is generated for free with no extra work. With a remote URL you must supply width and height yourself — or use fill inside a sized container — and a wrong ratio there produces either a distorted image or reserved space that does not match, which reintroduces the layout shift the component exists to prevent.

3. What does next/font do that a Google Fonts stylesheet link does not?

Four things. It downloads the font at build time and serves it from your own domain, removing a third-party DNS lookup, connection and dependency. It subsets to the character ranges you declare, which for Latin-only text removes most of the file. It prefers a single variable font over several static weights. And — the part nothing else gives you — it computes size-adjust and related descriptors for the fallback font so that the fallback occupies nearly the same space as the real one, which means the swap does not move the page. The demo measures that last effect from real rendered geometry.

4. Which script strategy for a chat widget, and is there something better?

lazyOnload, so it loads during idle time rather than competing with your own hydration. But better still is not loading it until somebody wants it: render a button and only mount the <Script> when it is pressed. A 240 kB widget that two per cent of visitors open is 240 kB wasted on the other ninety-eight, and it runs on the main thread where it competes with your interactivity. The general principle applies to most third-party scripts: lazyOnload as the default, on-interaction where possible, and beforeInteractive reserved for the rare thing that genuinely must run first, such as a consent manager.

5. Why set priority on exactly one image?

Because it works by removing lazy loading and preloading the image, and preloading is a way of saying "this matters more than the other things competing for bandwidth". Mark one image — your largest above-the-fold one, usually the LCP element — and it gets a genuine head start. Mark six and you have told the browser nothing, because they now compete with each other and with your CSS and fonts, and the LCP can end up slower than with no priority at all. The corollary is that images below the fold should keep the default lazy behaviour, which is where most of the byte saving comes from.
