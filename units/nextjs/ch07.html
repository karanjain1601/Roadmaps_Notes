CHAPTER 07

Middleware

One function that runs before a request reaches any route. It is the earliest and cheapest place to make a decision, which makes it valuable — and it runs on every matching request in a constrained environment, which makes it easy to misuse.

Part 2 Routing·Reading time 35 minutes·Demos the request pipeline, how much auth·Prerequisites Chapters 4–5

1What it is

A single file at the project root, and a single exported function.

middleware.ts TypeScript
import { NextResponse, type NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const session = request.cookies.get('session');

  if (!session) {
    const url = new URL('/login', request.url);
    url.searchParams.set('from', request.nextUrl.pathname);   // come back after
    return NextResponse.redirect(url);
  }

  const response = NextResponse.next();
  response.headers.set('x-request-id', crypto.randomUUID());
  return response;
}

export const config = {
  matcher: ['/dashboard/:path*', '/orders/:path*']
};

// One file, one function, at the project root — not inside app/.
// It runs before routing, before rendering, before any cache is
// consulted. Return nothing (or next()) to let the request continue.
Four things it can return
NextResponse.next() to continue, optionally with added headers or cookies. NextResponse.redirect() to send the user elsewhere, visibly. NextResponse.rewrite() to serve different content at the same URL, invisibly. Or a Response of your own, to answer without touching a route at all.
Redirect and rewrite are not the same
A redirect changes the URL in the address bar and costs another round trip. A rewrite keeps the URL and serves other content — which is how locale prefixes, A/B splits and proxying are done.
It runs on the edge runtime by default
Close to the user, fast to start, and with a restricted API surface. Section 3 is the list of what that costs.

2The matcher

Without one, your middleware runs on every request in the application, including every image.

Narrow it deliberately TypeScript
// Include what you mean:
matcher: ['/dashboard/:path*', '/orders/:path*', '/api/private/:path*']

// Or exclude the things that should never pay for it:
matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\\\..*).*)']

// Conditional matching, for finer control:
matcher: [{
  source: '/dashboard/:path*',
  missing: [{ type: 'header', key: 'next-router-prefetch' }]   // skip prefetches
}]

// Matchers must be statically analysable — no variables, no
// computed values. They are read at build time.
Middleware runs on prefetches too

Every Link in the viewport triggers a prefetch, and each of those is a request your matcher may catch. On a page with forty links that is forty middleware invocations before the user has clicked anything. If your middleware does real work — and especially if it makes a network call — that cost is multiplied by every link on every page. The missing matcher above is how you opt prefetches out.

3What you cannot do

Read this before designing around middleware, not after.

LimitationConsequence
No Node APIs on the edge runtimeNo fs, no net, no native modules. Many database drivers and ORMs simply will not run. Node runtime support for middleware has been arriving, but check it for your version rather than assuming.
No React, no renderingYou cannot render a component or return JSX. It is request plumbing, not a view layer.
The body is effectively off limitsReading it consumes the stream, so the route receives an empty body. Body-dependent logic belongs in a route handler.
Everything is on the critical pathEvery millisecond here is added to every matching request, before anything can be cached or streamed. A 60ms token lookup makes the whole site 60ms slower.
Size and time limitsThe bundle is constrained, and pulling in a large library can push you over. There are execution time limits too, which vary by host.
It cannot see the route's dataIt runs before rendering, so it knows nothing about what the page will fetch. Decisions needing that belong in the layout or page.

The arrangement to copy TypeScript
// middleware.ts — CHEAP and OPTIMISTIC. Does the cookie exist and
// is the signature valid? No database, no network.
export async function middleware(request: NextRequest) {
  const token = request.cookies.get('session')?.value;
  const ok = token && await verifyJwtSignature(token);   // local, ~1ms
  if (!ok) return NextResponse.redirect(new URL('/login', request.url));
}

// The page or the data layer — AUTHORITATIVE. Is this session still
// valid, is the account still active, may THIS user see THIS record?
export default async function OrderPage({ params }) {
  const user = await requireUser();                // hits the database
  const { id } = await params;
  const order = await getOrder(id, user.orgId);      // scoped by owner
  if (!order) notFound();
  return <Order order={order} />;
}

// Middleware improves the EXPERIENCE — no flash, one redirect,
// nothing wasted. The page provides the SECURITY. Never the reverse:
// a matcher that misses one path is a hole, and a server action or a
// route handler is reachable without ever passing through middleware.

5Rewrites, locales and experiments

Three jobs middleware does uniquely well, all of them variations on one trick.

Serving different content at the same URL TypeScript
// Locale from the Accept-Language header, kept out of the URL
const locale = pickLocale(request.headers.get('accept-language'));
return NextResponse.rewrite(new URL('/' + locale + request.nextUrl.pathname, request.url));

// A/B split, sticky per visitor via a cookie
let bucket = request.cookies.get('bucket')?.value;
if (!bucket) bucket = Math.random() < 0.5 ? 'a' : 'b';
const res = NextResponse.rewrite(new URL('/home-' + bucket, request.url));
res.cookies.set('bucket', bucket, { maxAge: 60 * 60 * 24 * 30 });
return res;

// Passing something computed here down to the route
const headers = new Headers(request.headers);
headers.set('x-org-id', orgId);
return NextResponse.next({ request: { headers } });   // read with headers()
Rewrites are invisible
Which is the point, and also the risk: a rewrite that goes wrong shows the wrong page at a URL that looks right, and nothing in the address bar hints at it.
A rewrite makes the route dynamic
You are deciding per request, so the result cannot be a prerendered static file. That is an acceptable cost for a personalised experiment and a poor one for something that could have been static — Chapter 8.
Header injection is the clean way to pass context
NextResponse.next({ request: { headers } }) lets a page read a value middleware computed, via headers(). Do not use it for anything security-relevant, since the page cannot tell your header from a forged one unless middleware ran — and see the previous section on why that is not guaranteed.

7Debugging it

Middleware is invisible by design, which makes a few habits worth having.

Log the decision, not the entry
"Middleware ran" tells you nothing on a site making forty prefetches a page. Log the path and the branch taken — redirected, rewritten, passed — and you can actually read it.
Set a header rather than reasoning about it
Adding x-middleware-decision to the response makes the branch visible in your browser's network panel for every request. Cheap, and it removes most of the guesswork.
Check the matcher first
When middleware "does not run", the matcher is the cause far more often than the logic. Note that matchers are statically analysed at build time, so a computed pattern silently does not work.
Watch out for redirect loops
Redirecting to /login without excluding /login from the matcher is the classic. The browser reports too many redirects and the middleware looks correct in isolation.
Measure it in production
Locally it looks free. Under real traffic it is a fixed tax on every matching request, and the number to watch is its p99 rather than its average — a token check that occasionally takes 200ms is a slow site occasionally, which is much harder to diagnose than a consistently slow one.

8Check yourself

Five questions, closing Part 2.

1. Why is a full database session check in middleware a bad design?

Because it is on the critical path of every matching request, including every prefetch, and it usually cannot run there anyway. A database round trip is added to every page load before anything can be cached or streamed, and a page with forty links generates forty prefetches that each pay it. On the edge runtime most drivers will not even load. The arrangement that works is optimistic-then-authoritative: middleware does a cheap local check — does the cookie exist, is the signature valid — to avoid a flash of protected content and a wasted render, and the page or data layer does the real verification against the database, scoped to the specific record.

2. Why can middleware not be your security boundary?

Because not everything passes through it. A matcher that misses one path is a hole, and matchers are easy to get subtly wrong. More importantly, server actions and route handlers are reachable in ways that do not necessarily traverse your matcher, and a page's own data fetching happens after middleware has finished and knows nothing about it. Middleware also cannot answer the question that actually matters — may this user see this record — because it runs before any data is loaded. So treat it as an experience optimisation: fewer wasted renders, no flash, one clean redirect. The authorisation must live where the data is read.

3. What is the difference between a rewrite and a redirect?

Visibility and cost. A redirect sends a 3xx, so the browser makes a second request and the address bar changes — the user can see where they ended up. A rewrite keeps the URL exactly as the user typed it and serves different content behind it, in the same round trip. That is what makes rewrites right for locale prefixes, A/B splits and proxying, where the URL should stay stable. The trade-offs: a rewrite is invisible, so a mistake shows the wrong page at a URL that looks correct with no clue in the address bar, and because the decision is per request the route can no longer be served as a prerendered static file.

4. Your middleware seems not to run. What do you check first?

The matcher, before the logic — that is the cause far more often. Three specific things: the pattern itself, since /dashboard does not match /dashboard/settings without :path*; whether the matcher is statically analysable, because a computed or variable pattern is read at build time and silently fails; and whether the file is in the right place, at the project root rather than inside app/. If the matcher is right, add a response header recording the branch taken so the decision becomes visible in the network panel for every request, which removes most of the remaining guesswork.

5. Where should a permanent URL change live, and why not middleware?

In next.config's redirects. It resolves before middleware in the pipeline, costs nothing at runtime because it is not your code executing, and emits a 308 so search engines transfer the old URL's standing to the new one. Middleware would work but is strictly worse here: you are paying a function invocation on every matching request to express something entirely static, and you have moved a piece of routing configuration into imperative code where the next person will not look for it. Keep middleware for decisions that genuinely depend on the request — a session, a locale, an experiment bucket.
