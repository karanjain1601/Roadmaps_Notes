Server actions and mutations

A function you call from a component that only ever runs on the server. It removes the API layer, the fetch, the serialisation boundary and most of the form state — and it is an HTTP endpoint that anyone can call with anything, which the syntax does an excellent job of hiding.

Part 3 Rendering and data·Reading time 40 minutes·Demos the attack surface, a working form·Prerequisites Chapters 9–10

1What one is

A directive, and a build step that turns your function into an endpoint plus a client stub.

Two ways to declare, three ways to call TypeScript
// actions.ts — file-level: every export is an action
'use server';

export async function addComment(formData: FormData) { … }

// or inline, inside a server component:
export default async function Page() {
  async function save(formData) {
    'use server';
    …
  }
  return <form action={save}>…</form>;
}

// Calling it:
//   1. <form action={addComment}>        — works before hydration
//   2. useActionState(addComment, {})     — result + pending
//   3. await addComment(fd) in a handler  — programmatic, from a
//                                           client component

// What the build produces: an HTTP endpoint at a generated URL, and
// a stub the client calls. That is the whole mechanism, and it is
// why section 3 exists.
It can be passed to a client component
Functions cannot normally cross the boundary (Chapter 9), and a server action is the deliberate exception — React sends a reference rather than the code.
Arguments are serialised
Same rules as props: primitives, plain objects, arrays, Date, Map, Set, FormData. Not closures, not class instances.
They run in sequence per client
Actions from one browser are queued rather than run concurrently, which avoids a class of race but means a slow action delays the next one.
They are not only for forms
Any mutation: a toggle, a reorder, a delete button. The form integration is the most convenient path, not the only one.

The five guards, in order TypeScript
'use server';

export async function updateOrder(formData: FormData) {
  // 1. Authenticate — who is this?
  const session = await auth();
  if (!session) return { error: 'Not signed in' };

  // 2. Validate — never trust the shape or the types
  const parsed = orderSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { errors: parsed.error.flatten().fieldErrors };

  // 3. Authorise — may this ROLE do this at all?
  if (!can(session.user, 'order:update')) return { error: 'Not permitted' };

  // 4. Check ownership — may they touch THIS record?
  //    Scope the query rather than checking afterwards.
  const order = await db.order.findFirst({
    where: { id: parsed.data.id, orgId: session.user.orgId }
  });
  if (!order) return { error: 'Not found' };   // not "forbidden" — do not confirm it exists

  // 5. Rate limit — an endpoint anyone can call in a loop
  if (await tooManyRequests(session.user.id)) return { error: 'Slow down' };

  await db.order.update({ where: { id: order.id }, data: parsed.data });
  revalidateTag(tags.order(order.id));
  return { ok: true };
}
Three things that are not protection

Middleware. Chapter 7 — an action's generated endpoint is not reliably behind your matcher, and middleware cannot know which record is being touched.

The page already checked. The page render and the action are separate requests. Nothing the page verified is carried into the action.

TypeScript. Types are erased. The id: string in your signature is a comment as far as the request is concerned.

3Returning errors people can use

Actions return values, which is the whole reason form state gets simple.

One schema, field errors, values preserved TypeScript
export async function save(prev: State, formData: FormData): Promise<State> {
  const raw = Object.fromEntries(formData);
  const parsed = schema.safeParse(raw);

  if (!parsed.success) {
    return {
      errors: parsed.error.flatten().fieldErrors,
      values: raw            // ← send them back, or the form clears
    };
  }
  await db.profile.update(…);
  revalidateTag('profile');
  return { ok: true };
}

// In the component — no useState, no loading boolean
const [state, formAction, isPending] = useActionState(save, {});

<form action={formAction}>
  <input name="email" defaultValue={state.values?.email}
         aria-invalid={!!state.errors?.email}
         aria-describedby={state.errors?.email ? 'email-err' : undefined} />
  {state.errors?.email && <p id="email-err">{state.errors.email[0]}</p>}
  <SubmitButton />      {/* uses useFormStatus — no prop needed */}
</form>
Return expected failures, throw unexpected ones
A validation error or a permission refusal is a return value the form renders. A database being down is an exception for error.tsx. Throwing for validation loses the field detail and shows an error page for a typo.
Send the values back
Without them an uncontrolled form clears on failure, which is the worst outcome in Chapter 14 of the React unit and equally true here.
The accessibility work is unchanged
aria-invalid, aria-describedby, an error summary that receives focus. The framework improved the plumbing, not the announcement.

4Revalidation, redirects, and one trap

Two lines at the end of most actions, and one of them will silently not run if you get this wrong.

redirect() inside a try block does nothing

It works by throwing a special signal that Next catches. Your own catch catches it first, swallows it, and the redirect silently does not happen — while the mutation succeeded, so the user sees a form that appears to have done nothing. Put the redirect after the try block, in the success path.

The ending most actions want TypeScript
try {
  await db.order.create({ data });
} catch (e) {
  return { error: 'Could not create the order' };
}

revalidateTag(tags.orders());        // shared — everyone sees it (Chapter 10)
redirect('/orders/' + order.id);      // OUTSIDE the try

5Optimistic updates

A working form, with a failure switch, so you can watch the rollback happen.

Right for cheap, likely, reversible things
A like, a toggle, adding a comment, reordering a list. The user is almost certainly going to succeed, and undoing it costs nothing.
Wrong for anything consequential
A payment, an irreversible delete, a booking. Showing success before it is true is worse than a spinner, because the user acts on it.
Rollback is automatic
useOptimistic discards the optimistic value when the action settles and the real state arrives. You do not write the revert — which is the main advantage over hand-rolling it.
Say something on failure
A row silently disappearing is not an error message. Pair the rollback with a live region so the user learns why.

6Working before hydration

Why the API is shaped around FormData rather than arbitrary arguments.

What you get free
<form action={serverAction}> posts natively if the JavaScript has not arrived yet — on a slow connection, during a deploy, with a blocked bundle, or in a browser where something failed. The mutation still happens.
What it requires of you
A real <form> with named inputs. The moment you collect values into an object and call the action programmatically, the enhancement is gone.
What does not survive
Optimistic updates, isPending, and anything relying on useActionState's returned value — all of those need the client runtime. Design so the form works without them and feels better with them.
Worth caring about?
For a public sign-up, a search form or a checkout, yes. For an internal tool behind a login, it is a nice property rather than a requirement — and it costs you nothing to have, since a real form is what you wanted anyway.

7When an action is the wrong tool

Four cases, mirroring Chapter 4's table from the other side.

SituationUse instead
Something outside your app calls itA route handler. Third parties, webhooks and mobile clients cannot invoke a server action.
Reading data for displayAwait it in the server component. An action for a read is a needless round trip and gives up caching.
Long-running workA queue. An action holds the request open, and hosts have execution limits.
Streaming a responseA route handler returning a ReadableStream.

And one honest caveat: many actions in sequence from one client are queued, so a page firing an action per keystroke will feel worse than a debounced client fetch. Actions are for mutations, not for a general-purpose RPC layer.

8Check yourself

Five questions, closing Part 3.

1. Why does every server action need its own authentication?

Because the build turns it into an HTTP endpoint at a generated URL, and anyone can send anything to it at any time. The fact that your interface only invokes it from behind a permission check is irrelevant — the request does not come from your interface. Three things that feel like protection and are not: middleware, because the generated endpoint is not reliably behind your matcher and middleware cannot know which record is involved; the page having already checked, because the render and the action are separate requests carrying nothing between them; and TypeScript, because types are erased and the signature is a comment as far as the wire is concerned.

2. What are the five guards, and why is ownership separate from authorisation?

Authenticate, validate, authorise, check ownership, rate limit. Authorisation asks whether this role may perform this kind of operation at all; ownership asks whether this particular user may touch this particular record. They are genuinely different, and conflating them is the classic multi-tenant hole: a legitimate manager with full order:update permission passing another organisation's order id. The robust form is to scope the lookup rather than check afterwards — findFirst({ where: { id, orgId: session.user.orgId } }) — so an id from elsewhere simply does not resolve. Return "not found" rather than "forbidden", so you do not confirm the record exists.

3. Your action redirects on success, but nothing happens. What is wrong?

redirect() is inside a try block. It works by throwing a signal that Next catches, so your own catch intercepts it first and swallows it. The mutation succeeded and the navigation silently did not, leaving the user with a form that appears to have done nothing at all — and no error anywhere, because your catch handled it. Move the redirect after the try block, in the success path. The same applies to permanentRedirect() and to notFound(), which use the same mechanism, and it is worth a lint rule if your codebase has many actions.

4. When is an optimistic update the wrong choice?

When being wrong is expensive for the user. A payment shown as complete, a booking shown as confirmed, an irreversible delete shown as done — if any of those roll back, the user has already acted on false information, and a spinner would have been kinder. Optimism suits cheap, likely-to-succeed, easily-reversed operations: a like, a toggle, adding a comment, reordering. Two supporting points: useOptimistic handles the rollback for you, which is its main advantage over hand-rolling; and a rollback must be announced, because a row quietly disappearing is not an error message.

5. What does a real <form> with a server action give you that a programmatic call does not?

It works before hydration. A form whose action is a server action posts natively if the JavaScript has not arrived — a slow connection, a deploy in progress, a blocked bundle — and the mutation still happens. That is the reason the API is shaped around FormData rather than arbitrary arguments, and it disappears the moment you gather values into an object and call the action from a handler. What does not survive is the enhancement layer: optimistic updates, isPending, and useActionState's return value all need the client runtime. Design so the form works without them and feels better with them.
