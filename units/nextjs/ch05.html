CHAPTER 05

Navigation and prefetching

Next intercepts your links and takes over navigation. Done well that makes moving around feel faster than a page load; done carelessly it silently drops the five things the browser was handling for you.

Part 2 Routing·Reading time 35 minutes·Demos prefetch timeline, which API·Prerequisites Chapters 3–4

1Link is a real anchor

Which matters more than it sounds, because the alternatives quietly break things.

What it renders and what it adds JSX
import Link from 'next/link';

<Link href="/orders/4182">Order 4182</Link>
// renders  <a href="/orders/4182">  — a genuine anchor.

// So all of this still works, for free:
//   middle-click and cmd-click open a new tab
//   right-click gives "copy link address"
//   the status bar shows the destination on hover
//   a crawler follows it
//   it works before hydration
//
// And Next adds: click interception, prefetching, and a client-side
// transition that keeps the layouts above the change mounted.

<Link href="/orders" prefetch={false} replace scroll={false}>
Three ways to get this wrong

<div onClick={() => router.push('/x')}> is not a link: no new tab, no copy, no keyboard activation, invisible to crawlers, and needs its own role, tabIndex and Enter handler to be usable at all.

<a href="/x"> without Link works but does a full page reload — losing every layout's state and re-downloading everything. Correct for an external URL, wrong for your own routes.

Wrapping a <button> in a Link produces invalid, confusingly-announced markup. If it navigates it is a link; if it acts it is a button.

When it happens
In production only — prefetching is disabled in development, which is why navigation feels slower locally than it will in production. A Link prefetches when it enters the viewport, and again on hover.
Static and dynamic routes prefetch different amounts
A static route can be prefetched completely, because its output already exists. A dynamic route cannot — it has not been rendered for this user yet — so by default Next prefetches the route's code and whatever shared layout output it can, and leaves the rest for the click. That is the gap the demo shows between the second and third modes.
prefetch={true} forces the full payload
Which does render the route on the server ahead of the click. Worth it for the one destination you are confident about; wasteful across a list of fifty rows.
prefetch={false} is a real option
For a long list, a rarely used footer, or an expensive destination. The tile on the right of the demo is the cost: prefetching a route nobody visits is a render and a payload paid for nothing.

3Navigating from code

Five methods, and one of them is the answer to a question people ask constantly.

useRouter — client components only JSX
'use client';
import { useRouter } from 'next/navigation';   // NOT next/router

const router = useRouter();

router.push('/orders/4182');      // adds a history entry
router.replace('/orders?page=2');  // swaps the current one — for filters and typing
router.back();                     // history.back()
router.prefetch('/checkout');     // warm a destination you expect
router.refresh();                  // re-fetch the current route's server output
refresh() is the one worth understanding
It re-runs the current route's server components and updates the page without losing client state — an open dialog stays open, an input keeps its value, scroll position holds. That makes it the right tool after a client-side change that the server render depends on.
And it is not revalidatePath
refresh() runs in the browser and affects this user's view now. revalidatePath runs on the server and invalidates the shared cache for everyone. A mutation usually wants the second; a client-only situation wants the first. Chapter 10 draws the line properly.
replace for continuous changes
A filter that updates as the user types will otherwise put twenty entries in the history and make the back button useless. Chapter 15 of the React unit; the same rule.
Prefer Link where you can
router.push in a click handler gives up the anchor semantics from section 1. Use it for genuine programmatic cases — after a submit, on a timeout, from a keyboard shortcut.

4Honest pending states

A navigation that fetches takes time. The user should know, without the screen going blank.

ToolFor

The principle from React Chapter 12 holds: dim the old content rather than replacing it. A navigation that blanks the screen for 200ms feels worse than one that leaves the previous page visible and slightly faded. Next already helps here — navigations run in a transition, which suppresses Suspense fallbacks for content that is already on screen.

5Scroll and focus

Next handles the first. You are responsible for the second.

Scroll, mostly done for you
A navigation scrolls to the top; back and forward restore the previous position. scroll={false} on a Link, or { scroll: false } on push, suppresses it — which is what you want when only a filter changed and the user is halfway down a list.
Scrolling containers need checking
Restoration works on the window. If your layout scrolls an inner div instead, verify it yourself; this is the most common way scroll behaviour ends up broken.
Hash links work
href="/docs#install" scrolls to the element with that id, and honours scroll-margin-top for a sticky header.
Focus is not done for you
After a client navigation, focus stays on the link that no longer exists. A keyboard user's next Tab starts at the top of the document, and a screen-reader user gets no signal that anything happened. Give the new view's heading tabIndex={-1} and focus it, and pair that with a polite live region announcing the page. React Chapter 15 lists all five obligations; this is the one Next does not cover.

8Check yourself

Five questions.

1. Why does Link render a real <a> rather than intercepting a div?

Because a large amount of behaviour comes attached to an anchor and none of it comes attached to a div. Middle-click and cmd-click open a new tab, right-click offers "copy link address", the status bar shows the destination on hover, keyboard activation works, crawlers follow it, and it functions before hydration. A div with an onClick has to reimplement the role, the tab index and the Enter handler just to be operable, and still cannot open in a new tab. The mirror-image mistake is a plain <a> to an internal route: it works, but triggers a full reload that discards every layout's state and re-downloads the application.

2. Why does prefetching help less for a dynamic route?

Because there is nothing finished to fetch. A static route's output already exists, so it can be prefetched in full and the click costs essentially nothing. A dynamic route has not been rendered for this request yet — it may depend on cookies, search params or live data — so by default Next prefetches only what it safely can: the route's code and whatever shared layout output is available, leaving the per-request render for the click. You can force the whole payload with prefetch={true}, which does render it on the server ahead of time; that is worth it for one likely destination and wasteful across a list of fifty rows.

3. What is the difference between router.refresh() and revalidatePath()?

Scope and location. router.refresh() runs in the browser and re-fetches the current route's server output for this user, right now, preserving client state — an open dialog stays open, inputs keep their values. revalidatePath() runs on the server and marks the shared cache stale for everyone, so the next visitor gets fresh output. A mutation almost always wants the second, because the data really did change for all readers; the first is for situations that are local to one browser, such as a client-side auth change that the server render depends on. Using refresh() where you needed revalidatePath() produces the classic "works for me, stale for everyone else".

4. Which of the five navigation obligations does Next not handle?

Focus. Next resets scroll on forward navigation and restores it on back, updates the document title from your metadata exports, and cancels in-flight work for a route you navigated away from. It does not move focus — after a client-side navigation, focus remains on the link that no longer exists in the tree, so a keyboard user's next Tab starts from the top of the document and a screen-reader user gets no announcement that the page changed. The fix is small and entirely yours: give the new view's heading tabIndex={-1} and focus it, paired with a polite live region. Also worth verifying scroll restoration if your layout scrolls an inner element rather than the window.

5. Why should an auth redirect not live in an effect?

Because the protected page renders first. The component mounts, returns its markup, the browser paints, and only then does the effect run and navigate away — so there is a real frame in which unauthorised content is on screen, and any data fetching inside it has already started. It is also React Chapter 9's pattern: an effect reacting to something already known before render. Do it earlier instead: middleware for a whole section, or a check in a server layout or page that calls redirect() before returning anything. One caveat with redirect() — it works by throwing, so calling it inside a try block lets your own catch swallow it.

Carry forward

If it navigates it is a link. Static routes prefetch fully, dynamic ones do not. refresh() is this browser; revalidatePath is everyone. Move focus yourself. Never redirect inside a try.
