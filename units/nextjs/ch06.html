CHAPTER 06

Parallel and intercepting routes

Two features with intimidating names that solve very ordinary problems: showing several independent sections on one screen, and making a modal behave like a real place you can link to. Both are worth knowing and neither should be your first idea.

Part 2 Routing·Reading time 35 minutes·Demos slots and default.tsx, the modal problem·Prerequisites Chapters 3–5

1The problem parallel routes solve

One screen, several regions that should load, fail and stream independently.

A dashboard shows a team panel and an analytics panel. Each queries something different, at a different speed, and either can fail on its own. In a single page.tsx you can achieve that with Suspense and error boundaries — but the two panels are then just markup, with no route of their own, no independent URL state, and no way to swap one for something else.

A slot is a folder starting with @ Structure
app/dashboard/
  layout.tsx
  page.tsx            // arrives as the `children` prop
  @team/
    page.tsx          // arrives as the `team` prop
    loading.tsx       // its own fallback
    error.tsx         // its own boundary
  @analytics/
    page.tsx
    loading.tsx

// The layout receives each slot as a named prop.
export default function Layout({ children, team, analytics }) {
  return (
    <div className="grid">
      <section>{children}</section>
      <aside>{team}{analytics}</aside>
    </div>
  );
}

// @folders contribute NOTHING to the URL. /dashboard renders all
// three. They are a way to compose independently-routed regions.
What you gain over plain components
Each slot is a real route subtree, so it gets its own loading.tsx, error.tsx and layout, and it can have nested routes of its own — meaning one region can navigate while the others stay put.
Every slot must be rendered
A slot the layout does not render simply does not appear, with no warning. Same failure mode as forgetting children.
children is an implicit slot
It is the unnamed one. You do not create an @children folder.

2default.tsx, and the trap

The thing everyone hits on the first hard reload, and it looks like a bug.

Why the two differ

On a soft navigation Next keeps each slot's previously active state, because it still knows what was there — the router has that in memory. On a hard reload there is no memory: the server is asked for /dashboard/settings, and any slot with no route matching that URL has nothing to render. default.tsx is what you supply for that case. Without one, the whole page 404s — which is why this presents as "it works until I refresh".

3Intercepting routes

Show a different route's content in the current context, while keeping the real URL.

Four conventions, borrowed from relative paths Structure
(.)folder      // intercept a route at the SAME level
(..)folder     // one level up
(..)(..)folder // two levels up
(...)folder    // from the app root

// Note: the levels are counted in ROUTE segments, not filesystem
// folders — so route groups and slots do not count. This is the
// single most common reason an interception silently does not fire.

app/
  @modal/
    (.)photos/[id]/page.tsx   // intercepts /photos/[id]
    default.tsx               // null, when nothing is intercepted
  photos/
    [id]/page.tsx             // the real page, for direct visits
  page.tsx                    // the grid

The pieces, and the one that is easy to forget JSX
// app/layout.tsx — render the slot
export default function Root({ children, modal }) {
  return <html><body>{children}{modal}</body></html>;
}

// app/@modal/default.tsx — nothing intercepted, render nothing
export default function Default() { return null; }

// app/@modal/(.)photos/[id]/page.tsx — the modal itself
'use client';
export default function PhotoModal({ params }) {
  const router = useRouter();
  // closing means going back — the modal IS a history entry
  return <Dialog open onClose={() => router.back()}>…</Dialog>;
}

// And it still needs the real page for direct visits and for
// anyone arriving from a shared link: app/photos/[id]/page.tsx
Closing is router.back()
Not setting state. The modal exists because the URL changed, so it closes when the URL changes back — which also makes the browser's back button close it, for free and correctly.
You must still build the full page
app/photos/[id]/page.tsx handles a direct visit, a shared link and a reload. It is not optional, and it should be a good page rather than an afterthought — that is the URL people will send each other.
Accessibility is not included
Routing gets the URL right. Focus trapping, returning focus to the trigger, aria-modal, Escape handling and inert background content are all still yours. Use a dialog primitive (React Chapter 16).

5Conditional routes

The same URL rendering genuinely different trees.

One URL, two experiences JSX
app/dashboard/
  @admin/page.tsx
  @member/page.tsx
  layout.tsx

export default async function Layout({ admin, member }) {
  const role = await getRole();
  return role === 'admin' ? admin : member;
}

// Both slots have their own loading and error states, and neither
// tree is downloaded by a user who cannot see it.
//
// Worth being clear: this is a rendering decision, not a security
// boundary. Whatever each slot fetches must still authorise on its
// own — the layout choosing a slot proves nothing to the server.

6When not to reach for these

Both features cost more than they look, and there are usually simpler answers.

You wantTry first
Independent loading states on one page<Suspense> around each region inside one page.tsx. Chapter 11. Reach for slots only when a region needs its own routing.
A modal that need not be linkablePlain client state. A confirmation dialog, a settings popover, an image zoom nobody shares — none of it wants a URL, and a URL brings history entries you then have to reason about.
TabsA search param, or nested routes. Slots are heavier than either.
Role-based screensTwo routes and a redirect is usually clearer than one URL with conditional slots, unless the URL genuinely must be shared between roles.

The honest cost: @ folders and (.) prefixes are unfamiliar to most people reading your repository, default.tsx is a requirement nothing warns you about, interception counts route segments rather than folders, and debugging a slot that silently renders nothing is unpleasant. Use them where they solve a real problem — a genuinely shareable modal is a real problem — and not because they are the most interesting tool available.

7Check yourself

Five questions.

1. What does an @folder contribute to the URL?

Nothing. It is a named slot, delivered to the enclosing layout as a prop with that name, and it is invisible to the URL entirely — /dashboard renders page.tsx, @team/page.tsx and @analytics/page.tsx together. The value over plain components is that each slot is a real route subtree: it gets its own loading.tsx, error.tsx and layout, and it can contain nested routes so one region navigates while the others stay put. Two consequences: children is the implicit unnamed slot, and a slot the layout forgets to render simply does not appear with no warning at all.

2. Everything works until you press reload, then the page 404s. Why?

A slot has no route matching the current URL and no default.tsx. On a soft navigation the router remembers what each slot was showing and keeps it, so nothing appears wrong. A hard reload has no such memory — the server is asked for that URL, and a slot with nothing to match it has nothing to render, which fails the whole page. default.tsx is what you supply for exactly that case: often returning null, sometimes an empty state, sometimes the slot's own index view. It presents as "it works until I refresh", which is a confusing symptom for a missing file that nothing warned you about.

3. Why does a client-state modal fail on refresh and a plain route fail differently?

They fail at opposite ends. A client-state modal has no URL, so a refresh loses it, the back button does not close it, and there is nothing to share — the state exists only in that tab. A plain route fixes all of that but throws away the context: navigating to /photos/4 replaces the grid entirely, so the user loses their scroll position and the sense of being inside a gallery, and closing means a navigation rather than a dismissal. An intercepted route gets both: the URL changes so it is shareable, refreshable and back-button-correct, while the grid stays underneath because the modal renders into a slot rather than replacing the page.

4. Your (.)photos/[id] interception silently does not fire. What is the likely cause?

You counted filesystem folders instead of route segments. The (.), (..) and (...) markers are relative to the route structure, and route groups in parentheses and slots beginning with @ contribute no segments — so a folder that looks one level up may be zero levels up in routing terms. That mismatch is the most common reason an interception does nothing, and it fails quietly: the real route renders instead, which looks like the feature simply not working. Count segments as they appear in the URL, not directories on disk. The second candidate is a missing default.tsx in the slot, which breaks it a different way.

5. When should a modal not be a route?

When nobody would want to link to it. A delete confirmation, a settings popover, a filter panel, an inline image zoom — none of those are places, and giving them URLs adds history entries you then have to reason about, plus a slot, a default.tsx and an interception folder to maintain. Plain client state is the right answer and is not a lesser one. Make it a route when the content genuinely is a destination someone would share or return to — a photo, a product, a profile — where refresh-survival and the back button matter. The test is a question about the product, not about the framework.
