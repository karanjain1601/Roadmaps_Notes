CHAPTER 10

The caching layers

Four caches, each with its own scope, lifetime and way of being cleared, and not one of them appears in your browser's network panel. Almost every "my change is not showing" is one of them, and knowing which requires knowing all four.

Part 3 Rendering and data·Reading time 50 minutes·Demos which cache lied, what an invalidation clears·Prerequisites Chapters 8–9

1Why this is genuinely hard

Not because caching is conceptually difficult. Because four of them overlap invisibly.

They have different scopes
One is per browser tab. Two are shared across every visitor. One lasts a single render. A change that looks fixed in your window may be stale for everyone else, and the reverse.
They have different lifetimes
Seconds, a configured window, until a deployment, or until you explicitly clear it. Nothing is uniform.
They are invalidated by different things
A time window, a tag, a path, a client-side call, a deployment. Calling the wrong one produces no error and no effect.
None of them is visible
The network panel shows a 200 whether the response came from a shared route cache, a data cache, or a real render. There is no column for "which layer answered this".
And the defaults have moved
Between major versions, notably for fetch and for the client router cache. Advice written eighteen months ago may describe behaviour your version no longer has — section 7.

2The four layers

Learn this table. Everything else in the chapter refers back to it.

LayerWhereScopeHolds, and what clears it
1 · Request memoisationServer, in memoryOne render Identical fetch calls within a single request. Discarded when the render ends. Nothing to invalidate — this is the one that never causes a bug. Chapter 9.
2 · Data CacheServer, persistentShared The results of individual fetch calls, and of unstable_cache wrappers. Survives deployments. Cleared by revalidateTag, revalidatePath, or its revalidate window.
3 · Full Route CacheServer / CDNShared The rendered HTML and payload of a static route. Cleared by a deployment, by revalidatePath, or by revalidating any data it depends on.
4 · Router CacheThe browserOne tab Route payloads for recently visited and prefetched routes. Short-lived, cleared by router.refresh(), by a server action, or by a hard reload. Invisible to the server entirely.

Two things worth reading twice. The Data Cache survives deployments — shipping new code does not clear it, which surprises people who expect a deploy to fix staleness. And the Router Cache lives in one browser tab, so a user reporting stale data may not have made a request at all.

Where each belongs TypeScript
// In a server action or route handler — shared, everyone sees it
revalidateTag('orders');              // every fetch tagged 'orders'
revalidatePath('/orders/4182');      // that route's cached render + its data
revalidatePath('/orders', 'layout');  // and everything nested below it

// As a route export — a time window rather than an event
export const revalidate = 3600;

// In a client component — THIS TAB ONLY
router.refresh();

// The one people miss: a server action that sets a cookie also
// clears the router cache, because the session may have changed.

5Tags are the part to design

React Chapter 13's key hierarchy, on the server.

One place, so they cannot drift TypeScript
// lib/tags.ts — general to specific, exactly like query keys
export const tags = {
  orders: () => 'orders',
  ordersList: (status: string) => 'orders:list:' + status,
  order: (id: string) => 'orders:' + id,
  orderEvents: (id: string) => 'orders:' + id + ':events'
};

// Tag every cached read with everything it belongs to — tags are a
// SET, not a hierarchy, so list them explicitly. This is the crucial
// difference from a query key: there is no prefix matching here.
await fetch(url, { next: { tags: [tags.orders(), tags.order(id)] } });

// Then a mutation invalidates precisely what it affected:
export async function updateOrder(id, data) {
  await db.order.update({ where: { id }, data });
  revalidateTag(tags.order(id));      // the detail
  revalidateTag(tags.orders());       // every list that includes it
}
Tags do not prefix-match

This is the difference from React Chapter 13's query keys, and it catches people who arrive from TanStack Query. revalidateTag('orders') clears entries tagged exactly 'orders' — it does not clear 'orders:4182'. So a cached read must carry every tag it belongs to, including the broad one. Tag generously; it costs nothing and it is the difference between an invalidation that works and one that half-works.

6Rules that hold across versions

Seven habits that survive the defaults changing under you.

1 · Be explicit on every cached read
Write the cache or revalidate option even when it matches the current default. This is the single highest-value habit in the chapter, because it makes intent survive an upgrade.
2 · Every mutation ends with an invalidation
Make it part of the shape of a server action, the way a mutation in a query library ends with invalidating keys. A write with no invalidation is a bug you will find later.
3 · Tag generously, from one file
Section 5. Cheap, and the alternative is enumerating affected paths at every call site and missing one.
4 · Prefer tags to paths
A path says "this URL is stale". A tag says "this data is stale", which is what you actually know after a write, and it reaches every route that used the data including ones you have forgotten about.
5 · Never rely on a deployment to clear anything
The Data Cache survives deploys. If your fix depends on shipping, it is not a fix.
6 · refresh() is not invalidation
It updates one browser. Reaching for it after a mutation gives you "works for me, stale for everyone else" — the hardest kind of report to act on.
7 · Check freshness in a private window
It removes layer 4 from the picture in one step, which is the fastest way to tell a shared-cache problem from a local one.

7Version drift, handled honestly

This part of Next has changed more than any other, and it will change again.

What has moved
fetch's default has been both cached and uncached. The client router cache's default staleness has changed and became configurable. unstable_cache has been renamed and reshaped. Partial prerendering has moved through flags. An explicit-caching model (use cache and similar directives) has been arriving to replace implicit defaults.
What has not moved
The four layers, their scopes, and the fact that tags beat paths. That is why this chapter is organised around scope rather than around API names.
How to verify your version in five minutes
Run a build and read the symbol column (Chapter 8). Add a timestamp to a cached read and reload repeatedly to see whether it moves. Open a private window to remove the browser cache from consideration. Then check the documentation for your version rather than a blog post.
The stance to take
Do not learn the defaults; learn the layers, and state your intent explicitly at every call site. Code written that way did not break across any of the changes above, and code that relied on a default did.

8Check yourself

Five questions.

1. Name the four layers and the scope of each.

Request memoisation — server, one render, deduplicating identical fetch calls within a single request. Data Cache — server, shared across all visitors, holding individual fetch results, and it survives deployments. Full Route Cache — server or CDN, shared, holding the rendered output of static routes. Router Cache — the browser, one tab, holding recently visited and prefetched route payloads. Scope is the useful thing to memorise because it determines who sees the staleness and therefore what could possibly fix it: two are shared, one is local to a tab, and one cannot cause a bug at all.

2. A user says their edit is not showing, but it looks correct to you. Where do you start?

Ask whether it appears after a hard reload, and check in a private window. If a hard reload fixes it for them, it is the Router Cache — their browser answered from memory without making a request at all, which is why nothing you do on the server helps. If it persists across a reload and in a private window, it is shared: the Full Route Cache or the Data Cache, meaning something is missing an invalidation. The reason to start with these two observations rather than with the code is that they split the problem cleanly between "local to one browser" and "shared by everyone", and those have completely different fixes.

3. Why does revalidateTag('orders') not clear an entry tagged 'orders:4182'?

Because tags are matched exactly — there is no prefix matching, unlike query keys in React Chapter 13. 'orders:4182' is simply a different string. This catches everyone arriving from TanStack Query, where an array key gives you hierarchy for free. The fix is to tag every cached read with the whole set it belongs to: tags: ['orders', 'orders:4182'], so the broad invalidation reaches it and the narrow one still works. Tag generously from a single exported factory — it costs nothing, and the alternative is an invalidation that appears to work while quietly leaving detail pages stale.

4. Why will a deployment not fix a stale value?

Because the Data Cache persists across deployments. Shipping new code clears the Full Route Cache — rendered output is rebuilt — but the cached results of individual fetch calls survive, so a route rebuilt from stale data produces stale output again. That is deliberate: it means a deploy does not stampede your database or your upstream APIs. It also means "we redeployed and it is still wrong" is expected rather than mysterious. If a fix depends on shipping, it is not a fix; invalidate the tag or the path, and if the data was cached with no tag and no window, that is the thing to change.

5. Why prefer tags to paths for invalidation?

Because after a write you know which data changed, not which URLs displayed it. A path invalidation requires you to enumerate every route that showed that record — the detail page, three list views with different filters, a dashboard widget, an export — and you will miss one, and the one you miss will be the one someone reports. A tag says "this data is stale" and reaches every cached read that declared it belonged to that set, including routes added after you wrote the mutation. Paths remain useful for genuinely path-shaped invalidation, such as after a content edit where the URL is the natural unit.
