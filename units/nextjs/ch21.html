Deploying

Four shapes, chosen by what your application actually does rather than by preference. And one thing that catches nearly everyone who self-hosts behind more than one instance: the caches from Chapter 10 are per instance unless you make them otherwise.

2Static export, and its exact cost

The most attractive option and the one whose limits are least often read in advance.

Not available with output: 'export'Because
Dynamic rendering of any kindThere is no server. Every route must be prerenderable, so cookies(), headers() and searchParams on the server are out.
Route handlersNothing to execute them. An API must live elsewhere.
Server actionsSame. Mutations go to an external endpoint from the client.
MiddlewareNo request-time layer at all.
Image optimisationNo optimiser process; use unoptimized or a third-party loader (Chapter 14).
Revalidation and the Data CacheContent changes when you rebuild, and only then (Chapter 10).
generateStaticParams fallbacksEvery path must be enumerated at build time; there is nothing to render an unlisted one.

What you get in exchange is genuinely valuable: files on any static host, no runtime to operate or pay for, no cold starts, and effectively unlimited scale. For documentation, a marketing site or a blog it is an excellent fit. The trap is choosing it early and discovering the list above at the point you need a contact form.

3Standalone output and Docker

The self-hosting path, and the one setting that makes the image reasonable.

A multi-stage build Dockerfile
# next.config.ts:  output: 'standalone'
# — traces exactly the files needed and writes a self-contained
#   server, so the image does not carry all of node_modules.

FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:22-alpine AS run
WORKDIR /app
ENV NODE_ENV=production
RUN addgroup -S app && adduser -S app -G app
COPY --from=build /app/.next/standalone ./
COPY --from=build /app/.next/static ./.next/static
COPY --from=build /app/public ./public
USER app
EXPOSE 3000
CMD ["node", "server.js"]

# Two things people get wrong:
#   • forgetting to copy .next/static and public — the app boots
#     and every asset 404s
#   • assuming NEXT_PUBLIC_ variables can be set at runtime. They
#     are inlined at BUILD time (Chapter 19), so one image cannot
#     serve two environments with different public values.

4The caches, across instances

The chapter's most important section. Chapter 10 assumed one server; production usually is not.

Three instances behind a load balancer, one revalidateTag The instance that handled the mutation clears. The others do not know.
Instances cleared—
Still serving stale—
Users affected—
Reproducible—

The default cache is on local disk
Which is per instance, per container, and lost on restart. With one instance that is invisible; with three it means an invalidation reaches a third of your traffic.
Use a shared cache handler
cacheHandler in next.config, pointed at Redis or another shared store, makes the Data Cache and Full Route Cache genuinely shared. Managed platforms do this for you, which is a large part of what you are paying for.
Then set cacheMaxMemorySize: 0
Otherwise an in-memory layer sits in front of your shared store per instance and reintroduces the same divergence, more subtly.
Pin the build id for consistency
generateBuildId returning your commit SHA means every instance of a deployment agrees on cache keys. Without it, instances built separately can disagree.

5Previews and staging

Useful, and three ways to embarrass yourself with them.

Block indexing, on the environment not the branch
A robots.ts returning disallow: '/' when the environment is not production, plus robots: { index: false } in metadata. Preview URLs get indexed and outrank the real site more often than you would think.
Never point a preview at production data
A preview is a place people click "delete" to see what happens. Seed a separate database, and if you must use production data, anonymise it.
NEXT_PUBLIC_ values are baked per build
Chapter 19. So a preview needs its own build with its own public URL, not a runtime override. This is the one that surprises people promoting an image between environments.
Draft mode for content previews
draftMode() lets an editor see unpublished content on the real site. It makes the route dynamic (Chapter 8), which is correct here — it is only for authenticated editors.

6Rollback

Two things that make it work and one that makes it not.

Reverting code does not revert the Data Cache
Chapter 10, and it matters most here: rolling back leaves cached data from the bad release in place. Plan an invalidation as part of the rollback, not after someone notices.
Database migrations are the real constraint
Code rolls back in seconds; a schema does not. Write migrations so the previous release still runs against the new schema — add columns before using them, remove them a release later. This is what makes rollback a real option rather than a theoretical one.
Deterministic build ids
The commit SHA as the build id means you can identify precisely what is deployed and attribute an error spike to a release (Chapter 19).

Fourteen items, each pointing at the chapter that explains it.

8Check yourself

Five questions.

1. You self-host behind three instances and an edit only appears sometimes. Why?

Because the default cache lives on each instance's local disk, so revalidateTag clears only the instance that handled the mutation. The other two keep serving output rendered from their own stale copies, and which one you reach depends on the load balancer — so the same URL is correct on one refresh and stale on the next, from the same browser. It is maddening to reproduce and completely deterministic once you know. The fix is a shared cacheHandler pointed at Redis or similar, plus cacheMaxMemorySize: 0 so a per-instance memory layer does not reintroduce the same divergence more subtly.

2. What exactly do you give up with output: 'export'?

Everything that needs a server at request time: dynamic rendering of any kind, so no cookies(), headers() or server-side searchParams; route handlers; server actions; middleware; image optimisation; revalidation and the Data Cache, so content changes only when you rebuild; and generateStaticParams fallbacks, since every path must be enumerated at build time. In exchange you get files on any static host, nothing to operate, no cold starts and effectively unlimited scale — an excellent fit for documentation, a blog or a marketing site. The trap is choosing it early and meeting that list when someone asks for a contact form.

3. Why can one Docker image not serve staging and production?

Because NEXT_PUBLIC_ variables are inlined into the client bundle at build time (Chapter 19), so the public site URL, analytics key and error-tracking DSN are literal strings baked into the JavaScript. Setting a different value in the container's environment at runtime changes nothing in the already-built bundle. Each environment therefore needs its own build. Server-only variables are read at runtime and can differ per container, so the split is exactly along the public prefix. This is the detail that surprises people setting up an image-promotion pipeline.

4. What makes rollback actually possible?

Backwards-compatible migrations. Code reverts in seconds and a schema does not, so if the new release dropped a column the old one reads, rolling back gives you a broken application rather than the previous one. Write migrations in two steps: add a column before anything uses it, and remove one a release after nothing does. Two supporting pieces: a deterministic build id from the commit SHA so you can identify and attribute what is deployed; and remembering that reverting code does not revert the Data Cache, so an invalidation belongs in the rollback procedure rather than in the incident review afterwards.

5. Why block indexing on previews, and how?

Because preview URLs get discovered and indexed, and duplicate content on a preview domain can outrank the real site — which is a difficult thing to explain and slow to undo. Use a robots.ts that returns disallow: '/' whenever the environment is not production, and add robots: { index: false } to the metadata as a second layer. Key it on the environment rather than the branch name, so a preview from any branch is covered by default. Two related habits: never point a preview at production data, since a preview is where people click "delete" to see what happens; and use draftMode() for genuine content previews on the real site.
