CHAPTER 09

Fetching data

Server components can await data directly, which removes the API layer and the client waterfall in one move. It also introduces a new way to be slow: four queries that could have run at once, running one after another because that is what await on consecutive lines means.

Part 3 Rendering and data·Reading time 40 minutes·Demos the waterfall, request memoisation·Prerequisites Chapters 3, 8

1Where to fetch

Four places, and the first covers most cases.

PlaceWhen
The server component that displays itThe default, and usually correct. No endpoint, no loading state, no client cache, the query runs next to the database. Colocated with the thing that needs it.
A shared function called from several componentsWrapped in cache() so the duplicate calls are free. This is how a layout and its page can both need the same record (Chapter 3).
A client componentOnly when the data depends on interaction: polling, infinite scroll, a search-as-you-type box, anything after hydration. Section 6.
A route handlerOnly when something outside your React tree needs a URL. Chapter 4's table.
The shape that replaces an API layer JSX
export default async function OrderPage({ params }) {
  const { id } = await params;
  const order = await db.order.findUnique({ where: { id } });
  if (!order) notFound();
  return <Order order={order} />;
}

// No useEffect, no loading boolean, no error state to wire up, no
// endpoint, no client cache, and no serialisation boundary in the
// middle where the types could drift.

2fetch, extended

Next replaces the global fetch with one that also caches. That is a much larger change than it sounds.

The caching options TypeScript
// Cached until you invalidate it
await fetch(url, { cache: 'force-cache' });

// Never cached — and this makes the route dynamic (Chapter 8)
await fetch(url, { cache: 'no-store' });

// Cached, refreshed in the background after 60 seconds
await fetch(url, { next: { revalidate: 60 } });

// Cached and TAGGED, so a mutation can invalidate it precisely
await fetch(url, { next: { tags: ['orders', 'order:' + id] } });
// later, from a server action:  revalidateTag('orders')

// IMPORTANT: the default has changed between major versions — it has
// been cached-by-default and uncached-by-default at different times.
// Do not rely on the default. State what you mean, per call.
Tags are the part worth adopting early
They give you Chapter 13-of-React's key hierarchy on the server: tag a fetch with what it represents, and a mutation can invalidate exactly the affected set. Without tags your only options are a time window or invalidating a whole path.
A database query is not a fetch
So none of the above applies to it. Wrap it in React's cache() for per-request deduplication, and in unstable_cache (or whatever your version calls it) for persistent caching with tags. This asymmetry surprises people who assume the caching is about data rather than about fetch.
Be explicit, always
The single most useful habit in this chapter: never let a caching default decide something important. Write the option, even when it matches the default, because the default has moved and will move again.

3Request memoisation

Why "just fetch it again" is genuinely the right answer to Chapter 3's layout problem.

The same data needed in four places Count the calls, then count the network requests.
Where it is calledCache keyResult
Calls made—
Actual round trips—
Time cost—
Prop drilling needed—

Scope: one render pass
Memoisation lasts for the duration of a single request's render, then is discarded. It is not a cache in the Chapter 10 sense — it exists so that components can state their own data needs without coordinating.
The key is the URL and options for fetch
Which means a different header or method is a different call. For cache() the key is the arguments, so pass primitives — a fresh object argument defeats it exactly as it defeats memo in React Chapter 10.
What this buys architecturally
No prop drilling for data, and no context for data. Every component asks for what it needs and the framework deduplicates. That is a genuinely better arrangement than passing a record down five levels, and it is why the Chapter 3 answer is not a workaround.

4Parallel, sequential, streamed

The one performance mistake almost everyone makes in a server component.

A page needing four independent queries Same four queries every time. Only the arrangement changes.
First byte—
Everything visible—
Round trips in series—
Time blocked—

The three fixes JSX
// ✗ Four round trips in series. Nothing about this code says
//   the queries depend on each other — but await does.
const order = await getOrder(id);
const customer = await getCustomer(id);
const events = await getEvents(id);
const related = await getRelated(id);

// ✓ One round trip, for anything genuinely independent
const [order, customer, events, related] = await Promise.all([
  getOrder(id), getCustomer(id), getEvents(id), getRelated(id)
]);

// ✓ The preload pattern — start it before you need it.
//   Useful when a child will await something the parent does not.
function preload(id) { void getRelated(id); }   // fire, do not await
preload(id);                                 // memoised, so the child's
const order = await getOrder(id);            // await is already warm

// ✓ Stream the slow one instead of waiting for it
<Suspense fallback={<RelatedSkeleton />}>
  <Related id={id} />      {/* awaits inside, off the critical path */}
</Suspense>

5When to fetch on the client

Server components remove most client fetching. Not all of it.

CaseWhy the server cannot do it
Polling live dataIt changes after the render. Use an interval, or better, server-sent events through a route handler.
Infinite scrollDriven by the user's scroll position, which the server never sees.
Search as you typeEvery keystroke would be a navigation. Debounce and fetch client-side, or use search params with a transition if the URL should reflect it.
Optimistic UI needing a re-readThe mutation happened in the browser; useOptimistic plus a server action is usually better than fetching.
Data only some users requestAn expensive panel behind a "show details" toggle should not be in every response.

For these, a client cache library still earns its place — TanStack Query or SWR alongside server components, not instead of them. The pattern that works: the server component provides the initial data, and the client library takes over for interaction-driven updates. Do not put server-rendered data into a client cache just to have it there.

6Keeping the server's data on the server

Everything you pass to a client component is in the response the browser receives.

The leak that looks like nothing

<UserCard user={user} /> where UserCard is a client component sends the whole user record to the browser — the password hash, the internal notes, the Stripe customer id, the flags — because props crossing the boundary are serialised into the payload. It renders correctly and shows only the name, and everything else is in the page source. Pass the fields you need, not the record you have.

Three defences TypeScript
// 1. Pass fields, not records. The dullest and most effective fix.
<UserCard name={user.name} avatarUrl={user.avatarUrl} />

// 2. Make the mistake a build error.
import 'server-only';   // at the top of a module holding secrets —
                       // importing it from a client component now fails

// 3. Taint values you must never send.
import { experimental_taintObjectReference as taint } from 'react';
taint('Do not pass the whole user to the client', user);

// And the environment variable rule: anything prefixed
// NEXT_PUBLIC_ is inlined into the client bundle. Everything else
// is server-only — so a secret with that prefix is a published
// secret, and it will not warn you.

7The states people forget

Awaiting directly removes the loading boolean, and it does not remove the other three states.

Not found is not an error
notFound() gives a 404 and renders not-found.tsx. Returning your own "no such order" markup gives a 200, which tells crawlers the page exists and will keep them coming back.
Empty is not not-found
A successful query returning zero rows is a fourth state and the one most often skipped. "You have no orders yet" with a call to action is a design job, not an edge case.
A thrown error hits error.tsx
Which is why every route with data wants one, and why it must be trivial enough not to throw itself (React Chapter 18).
Partial failure is a real design decision
With four sections streaming independently, one can fail while three succeed. Each Suspense boundary should be paired with an error boundary so a broken recommendations panel does not remove the order details.

8Check yourself

Five questions.

1. Four consecutive awaits for four independent queries. What is wrong and what is the fix?

They run in series, so the page takes the sum of the four latencies rather than the largest — and nothing in the code says the queries depend on each other, which is exactly why it is easy to write. await means "wait for this before continuing", and consecutive awaits therefore serialise things that had no relationship. Wrap them in Promise.all and the same four queries take one round trip. Two related tools: the preload pattern, where you start a promise without awaiting it so a child component's await is already warm; and a Suspense boundary around a genuinely slow section, which takes it off the critical path entirely rather than making it faster.

2. Why is fetching the same record in a layout and its page not wasteful?

Because of request memoisation. Within a single render pass, identical fetch calls — same URL, same options — are deduplicated, so the second one never reaches the network. For a database query, which is not a fetch, you get the same behaviour by wrapping the function in React's cache(), keyed on its arguments. The architectural payoff is what matters: every component can state its own data requirement without prop drilling or a context, and the framework collapses the duplicates. That makes Chapter 3's "just fetch it in both places" a genuinely good answer rather than a workaround for a missing prop channel.

3. Why should you always state the caching option on a fetch?

Because the default has changed between major versions — it has been cached-by-default and uncached-by-default at different times — so code that relied on the default behaved differently after an upgrade, silently. Writing cache: 'force-cache' or next: { revalidate: 60 } explicitly, even when it matches the current default, makes the intent survive the upgrade and makes it readable to the next person. It also has a Chapter 8 consequence worth knowing: no-store makes the whole route dynamic, so an absent-minded default is not just a caching question but a rendering one.

4. What is wrong with <UserCard user={user} /> when UserCard is a client component?

The entire user record is serialised into the response the browser receives — password hash, internal notes, billing ids, feature flags — because that is how props cross the server-client boundary. The component renders correctly and displays only the name, so nothing looks wrong; the rest is simply in the page source for anyone who looks. The fix is unglamorous: pass the fields you need rather than the record you have. Two supporting defences are worth adopting — import 'server-only' at the top of modules holding secrets, which turns the mistake into a build error, and React's taint APIs for objects that must never cross. And remember that any environment variable prefixed NEXT_PUBLIC_ is inlined into the bundle.

5. Server components can await data. When do you still fetch on the client?

When the data depends on something that happens after the render: polling live values, infinite scroll driven by scroll position, search-as-you-type where a navigation per keystroke would be absurd, and expensive panels only some users open. For those, a client cache library such as TanStack Query or SWR still earns its place — alongside server components, with the server providing the initial data and the client library taking over for interaction-driven updates. What you should not do is push server-rendered data into a client cache for the sake of uniformity; that reintroduces the loading states and the serialisation boundary you had just removed.
