CHAPTER 11

Streaming and Suspense

Streaming means the response leaves in pieces: a usable shell immediately, then each slow region as it resolves. Adding a boundary is one line, and there are five ordinary things that quietly stop it working at all.

Part 3 Rendering and data·Reading time 35 minutes·Demos what blocks the stream, measured layout shift·Prerequisites Chapters 3, 8–9

1What is actually sent

Not a loading spinner feature. A chunked HTTP response.

Without streaming, the server renders the whole tree, then sends it. With streaming it sends the shell — everything outside any Suspense boundary — with the fallback markup in place, keeps the connection open, and appends each region's real markup as its data resolves, along with a small script that swaps it into position. The browser is painting the first chunk while the server is still working on the third.

The user-visible consequence
First paint stops depending on the slowest query on the page. That is the whole benefit, and it is large: a 1.5-second recommendations query no longer decides when the header appears.
It does not reduce work
The same queries run and the page still finishes at the same time. What changes is that the user is looking at something usable for most of it.
It works without JavaScript for the first paint
The shell is real HTML. The swap-in mechanism needs a small inline script, but a crawler or a reader with scripting disabled still gets the shell, and Next also renders the resolved content in the stream rather than only client-side.
Two ways to declare a boundary
loading.tsx for a whole segment, or <Suspense> inline for one region. Chapter 3 covered the difference; this chapter is about what to do with it.

2Designing the shell

The first chunk is a design decision, not a technical leftover.

Belongs in the shellBelongs behind a boundary
Header, navigation, footer. The page title and any static copy. The primary content if it is fast — a product's name, price and images. Anything the user needs in order to decide what to do next. Personalised sections. Anything querying a slow or third-party service. Recommendations, related items, activity feeds, review aggregates. Anything below the fold.

The test: could a user start doing something useful with only this? A shell that is a header and four skeletons is technically streaming and experientially a loading screen. A shell containing the product and its buy button is a page that works, with extras arriving.

3What silently stops it working

"I added Suspense and nothing changed" is a common report, and it usually has one of five causes.

An await above the boundary
The most common. If the page or layout awaits something before returning the JSX containing the boundary, the shell cannot be sent until that resolves. The boundary is fine; it just never gets a chance.
A dynamic API outside any boundary
Chapter 8. Not fatal to streaming, but it removes the static shell, so the shell is now rendered per request rather than served from the CDN.
generateMetadata awaiting something slow
Metadata goes in the document head, which precedes everything, so a slow generateMetadata holds the entire response. Easy to miss because it is in a different export from the component you were optimising.
A proxy or host that buffers
Some reverse proxies and CDN configurations buffer the whole response before forwarding it, which converts streaming back into blocking with no code change and no error. If streaming works locally and not in production, check this before your code.
Boundaries in the wrong place
A boundary around the entire page content streams nothing useful — the shell becomes a header and a skeleton. Section 2.

Size the fallback to the content
Not approximately — measure the real thing and match it. A skeleton with the right number of rows at the right height produces no shift at all, which is the difference between a page that assembles and a page that jumps.
Reserve space even when you cannot match exactly
A min-height on the container bounds the shift. Better than nothing by a wide margin.
Skeletons over spinners for anything large
A spinner is a small element standing in for a big one, so it guarantees a shift. It also communicates less: a skeleton tells the user what is coming.
Do not animate aggressively
A shimmering skeleton for 1.5 seconds is fine; one for 80 milliseconds is a flash. Consider a small delay before showing a fallback for regions that are usually fast, and respect prefers-reduced-motion.

5Streaming and crawlers

A frequent worry, with a more reassuring answer than people expect.

The streamed content is in the HTML
Not fetched later by JavaScript. It arrives in the same response, appended as it resolves, so a crawler reading the full response body sees it. This is materially different from client-side fetching.
Metadata is never streamed late
Titles, descriptions and canonical URLs come from your metadata exports and are in the head before any body content. That is also why a slow generateMetadata blocks everything — section 3.
The practical caution is time, not mechanism
A crawler will not wait indefinitely. If something important is behind a boundary that takes four seconds, the risk is the timeout rather than the streaming. Keep anything that must be indexed in the shell or in a fast boundary.
Verify rather than assume
curl the URL and read the whole body, or use a search console's rendering tool. Two minutes, and it settles the question for your actual setup — including whether a proxy is buffering.

6Pair every boundary with an error boundary

Streaming makes partial failure possible, which is a feature and a design obligation.

The arrangement JSX
<ErrorBoundary fallback={<RecsUnavailable />}>
  <Suspense fallback={<RecsSkeleton />}>
    <Recommendations productId={id} />
  </Suspense>
</ErrorBoundary>

// Error boundary OUTSIDE, so a rejection can escape the Suspense
// boundary and be caught. Both fallbacks occupy the same footprint
// as the content, so neither loading nor failing shifts the page.
//
// At route level, error.tsx and loading.tsx give you this pairing
// for free — which is a good reason to use them where the whole
// segment genuinely waits together.

Once four regions stream independently, one can fail while three succeed, and that is a much better outcome than one failure taking the page down. It only works if each region has somewhere to put its error — otherwise a rejected promise inside a boundary propagates upward until it finds one, which may be the root.

7Check yourself

Five questions.

1. What does streaming actually change?

When bytes leave the server, not how much work happens. Without it the server renders the whole tree and then responds; with it the shell — everything outside any Suspense boundary — is sent immediately with fallback markup in place, the connection stays open, and each region's real markup is appended as its data resolves. So the first paint stops depending on the slowest query on the page. The same queries still run and the page still finishes at the same moment; the difference is that the user has something usable for most of that time rather than a blank screen.

2. You added a Suspense boundary and the page still blocks. What is the likely cause?

Something above the boundary is awaited, so the shell containing it cannot be sent yet. If the page or a layout does await getSomething() before returning the JSX, the boundary is correct and simply never gets a chance to help. The second candidate is generateMetadata awaiting something slow: metadata goes in the head, which precedes all body content, so it holds the entire response — and it is easy to miss because it lives in a different export from the component you were optimising. The third, if it works locally but not in production, is a proxy or host buffering the whole response before forwarding it.

3. What belongs in the shell?

Whatever lets a user start doing something useful. Header, navigation, the page title, and the primary content if it is fast — a product's name, price and images, or an order's details. Behind boundaries go personalised sections, third-party or slow queries, recommendations, activity feeds, and anything below the fold. The test is worth applying literally: a shell that is a header and four skeletons is technically streaming and experientially a loading screen, whereas a shell containing the product and its buy button is a working page with extras arriving. The boundary placement is a design decision about what waits together.

4. Why is a spinner a poor fallback for a large region?

Because it is a small element standing in for a big one, so it guarantees a layout shift: everything below jumps by the difference when the content arrives. The demo measures that from real geometry — a 34-pixel spinner replaced by a 260-pixel table moves everything below it by more than 200 pixels, and it moves twice if the region is also above other content. A skeleton sized to the real content produces no shift at all, and it communicates more, because it shows the shape of what is coming. When you cannot match exactly, a min-height on the container at least bounds the movement.

5. Does streaming hurt search indexing?

Not mechanically. The streamed content arrives in the same HTTP response, appended as it resolves, rather than being fetched later by JavaScript — so a crawler reading the full body sees it, which is materially different from client-side fetching. Metadata is never late either: it comes from your metadata exports and sits in the head before any body content. The real caution is time rather than mechanism: a crawler will not wait indefinitely, so anything that must be indexed should be in the shell or behind a fast boundary rather than a four-second one. Verify with curl on your actual deployment, which also catches a buffering proxy.
