Styling

Most of what you know about CSS applies unchanged. Three things do not: which approaches survive the server boundary, why your stylesheet order is decided by your import order, and why the theme flashes on first load.

1What works across the boundary

One table, and one row that decides most projects.

The last-but-one row is the one that matters. Runtime CSS-in-JS is not merely slower here — it is structurally incompatible, because a server component has no client runtime and no React context. You can still use it inside client components behind a provider, and many teams do during a migration, but every styled component then becomes a client component and Chapter 19 of the React unit explains what that costs.

2CSS Modules

The quiet default: real CSS, scoped by the build, nothing at runtime.

Scoped by compilation, not convention CSS
/* Button.module.css */
.btn { display: inline-flex; padding: 8px 16px; border-radius: 6px; }
.solid { background: var(--action-bg); color: white; }

/* composes pulls in another class — no duplication, still scoped */
.primary { composes: btn solid; font-weight: 600; }

// Button.tsx — works in a server component
import s from './Button.module.css';
<button className={s.primary}>Save</button>

// compiles to  class="Button_primary__a3f1"  — collision-proof,
// and deleting the component deletes its styles with it.
Colocate the file with the component
Chapter 2 — a .module.css inside a route folder is not a route, so it can sit beside its component.
:global() is the escape hatch
For styling a third-party component's class names you do not control. Use it sparingly and it stays readable; use it freely and you have global CSS with extra steps.
Custom properties are not scoped
Which is the point — they inherit, so tokens defined globally reach into every module. That is how theming works in section 7.

3Tailwind, and its one real trap

It fits Next well. The failure mode is specific and produces styles that vanish in production.

The scanner only sees literal strings

Tailwind generates its stylesheet by scanning your source for class names it recognises. A class name assembled at runtime does not exist in the source, so it is never generated — and because development often builds a broader set, this frequently works locally and disappears in production.

// ✗ never generated — the scanner sees no such string
className={`text-${colour}-600 p-${size}`}

// ✓ complete class names, present in the source
const TONE = { danger: 'text-red-600', ok: 'text-green-600' };
className={TONE[tone]}
Why it suits Next particularly
Build-time, so it works in server components; the output is one cached CSS file; and unused utilities cannot accumulate, because the stylesheet is derived from what is actually in your source.
Forward and merge className
React Chapter 16's argument. twMerge so a caller's px-8 genuinely beats your px-4, since Tailwind utilities all share one specificity and source order would otherwise decide.
It does not replace tokens
Point the Tailwind theme at your CSS custom properties rather than duplicating colours in the config. Then section 7's theming works for Tailwind classes too, with no extra machinery.

Where global CSS goes
Import it once, in the root layout. Importing the same global sheet from several components is how the ordering above becomes unpredictable, because the order then depends on which route was compiled.
Keep global CSS to genuinely global things
Resets, custom properties, base typography, @font-face. Component styles belong in modules or utilities, where the cascade cannot surprise you.
Cascade layers make it explicit
@layer reset, base, components, utilities; declares the precedence you want, so import order stops mattering. Well supported now and the cleanest fix.

/* globals.css — semantic tokens, reassigned per theme */
:root { --surface: white; --text: #16232F; }
[data-theme="dark"] { --surface: #101820; --text: #E7EDF3; }

// app/layout.tsx — set the attribute BEFORE first paint.
// One of the few legitimate blocking inline scripts.
<head>
  <script dangerouslySetInnerHTML={{ __html: `
    try {
      var t = localStorage.getItem('theme') ||
        (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
      document.documentElement.dataset.theme = t;
    } catch (e) {}
  ` }} />
</head>

// No JavaScript at all, if you accept the OS preference:
:root { color-scheme: light dark; --surface: light-dark(white, #101820); }
Theme in CSS, preference in React
React Chapter 16's rule. Putting the values in context re-renders every consumer on a toggle and does not work in a server component; setting data-theme on <html> is one attribute write and no re-render.
The cookie approach has a real cost
Reading the theme from a cookie on the server removes the flash without any inline script — and reading cookies() makes the route dynamic (Chapter 8), so a static marketing page stops being static. Usually the inline script is the better trade.
Components use semantic tokens only
var(--surface), never var(--grey-900). A component naming a primitive cannot be themed.

6Check yourself

Four questions.

1. Why can runtime CSS-in-JS not be used in a server component?

Because it needs things a server component does not have: a client runtime to generate class names and inject stylesheets while rendering, and React context to reach the theme provider. This is an incompatibility rather than a performance preference — the library cannot function there at all. You can still use it inside client components behind a provider, which is what most migrations do, but every styled component then becomes a client component and drags its imports into the bundle. If you are starting fresh, CSS Modules or Tailwind are the straightforward answers, and a zero-runtime tool such as Panda or vanilla-extract keeps the typed-authoring experience with real CSS output.

2. A Tailwind class works in development and vanishes in production. Why?

The class name is assembled at runtime, so the scanner never saw it. Tailwind generates its stylesheet by looking for recognisable class names as literal strings in your source, and `text-${colour}-600` is not one — there is no such string anywhere. It often appears to work locally because development builds a broader set. The fix is to write complete class names and select between them: a lookup object mapping your variant to 'text-red-600' or 'text-green-600'. It is also worth adding to a code review checklist, because it fails silently and only in the environment that matters.

3. Two CSS Modules set the same property at the same specificity. What decides the winner?

Their order in the compiled stylesheet, which follows your import order — so the winner depends on which file was imported first, which is not information anybody has in mind while writing components. The demo shows the button actually changing colour when the two imports swap. Two fixes: keep global CSS to a single import in the root layout so the order is stable, and use cascade layers — @layer reset, base, components, utilities; — to declare the precedence you want explicitly, after which import order stops mattering. The underlying point is that equal specificity plus incidental ordering is not a design; it is a coin toss you have not noticed yet.

4. Why does a dark-mode user see a flash of white, and what fixes it?

Because the saved preference lives in localStorage, which the server cannot read, so the HTML is generated with the default theme and only corrected after the bundle has loaded and hydrated — a real interval, sometimes several hundred milliseconds, of the wrong colours. The fix is a small blocking inline script in the head that reads storage and sets data-theme on <html> before the first paint; this is one of the few legitimate blocking scripts. The alternative is storing the theme in a cookie the server can read, which also works and makes the route dynamic (Chapter 8) — so it costs you static rendering, which is usually the worse trade.
