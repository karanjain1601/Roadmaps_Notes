CHAPTER 16

Internationalisation

Next has no built-in i18n in the App Router, which sounds like an omission and is really a set of decisions handed to you. Four of them, and the first one — where the locale lives — determines most of the rest.

Part 4 The product layer·Reading time 35 minutes·Demos routing strategies, what actually ships·Prerequisites Chapters 4, 7–8

1Four decisions

Answer them in this order, because each constrains the next.

1 · Where does the locale live?
In the URL path, in the domain, or nowhere visible. Section 2, and it is the consequential one — it decides whether each language is indexable and shareable.
2 · How is it chosen the first time?
From the Accept-Language header, from the domain, or not at all. Section 4, along with the rule that matters more than the mechanism.
3 · Where do the translations live, and who loads them?
On the server, or in the bundle. Section 5, and the difference is measured in kilobytes per visitor.
4 · What else changes with the language?
Dates, numbers, currency, plural rules, sort order, text direction, and sometimes the layout itself. Section 6 — this is the part scoped as "just translate the strings" and then discovered later.

3The [locale] segment

The whole implementation of the path-prefix strategy, which is less code than it sounds.

One dynamic segment at the top Structure
app/
  [locale]/
    layout.tsx          // sets <html lang> and dir
    page.tsx
    blog/[slug]/page.tsx
  middleware.ts         // redirects a bare / to a locale

// The layout — note lang and dir come from the segment
export async function generateStaticParams() {
  return [{ locale: 'en' }, { locale: 'fr' }, { locale: 'ar' }];
}

export default async function Layout({ children, params }) {
  const { locale } = await params;
  return (
    <html lang={locale} dir={locale === 'ar' ? 'rtl' : 'ltr'}>
      <body>{children}</body>
    </html>
  );
}

// Because locale is a param rather than a cookie, every language of
// every page can still be prerendered — generateStaticParams
// multiplies out with the slugs. That is the whole reason to put it
// in the path rather than reading cookies() (Chapter 8).
Validate the segment
/xx/blog is a valid URL shape. If xx is not a known locale, call notFound() rather than rendering with missing translations — otherwise you have generated an indexable page of untranslated keys.
lang and dir are not decoration
They drive screen-reader pronunciation, hyphenation, quotation marks, and the entire mirrored layout for right-to-left languages. Setting them in the locale layout is the single highest-value line in this chapter.
Keep the URL structure identical across locales
Translating path segments as well as content — /fr/blogue/ — is possible and doubles your routing complexity. Worth it for a marketing site where the URL is a keyword; rarely worth it otherwise.

4Detection, and the rule that matters

The mechanism is easy. The policy is where sites go wrong.

Negotiate once, then never override TypeScript
// middleware.ts
export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  // Already has a locale? Leave it completely alone.
  if (LOCALES.some(l => pathname === '/' + l || pathname.startsWith('/' + l + '/'))) return;

  // An explicit previous choice wins over any header.
  const chosen = request.cookies.get('locale')?.value;
  const locale = (chosen && LOCALES.includes(chosen))
    ? chosen
    : negotiate(request.headers.get('accept-language'), LOCALES, 'en');

  return NextResponse.redirect(new URL('/' + locale + pathname, request.url));
}

export const config = { matcher: ['/((?!_next|api|.*\\\\..*).*)'] };
Never redirect away from a locale the user is already on

Somebody sends a French colleague a link to /en/pricing. If your middleware sees a French Accept-Language and redirects to /fr/pricing, you have broken a shared link and overridden a deliberate act — and there is now no way to read the English page without fighting you. Detect only when there is no locale in the URL. This is the single most common i18n complaint about real sites, and it looks like helpfulness in the code.

Store the choice, but only when explicit
When someone uses your language switcher, set a cookie. Do not set it from a header guess, or the guess becomes sticky and the user cannot tell why.
Use a real negotiation library
Accept-Language has quality values, region subtags and wildcards. @formatjs/intl-localematcher plus negotiator handles it; parsing it yourself gets fr-CA against fr wrong.
Redirecting the root is fine; redirecting everything is not
A crawler following / should land somewhere sensible. A crawler following /en/pricing should get that page with a 200, not a redirect chain.
Always offer a visible switcher
Detection is a guess. The switcher is the correction, and it should be findable without scrolling to the footer.

Server-side loading, and the client island TypeScript
// dictionaries.ts — a dynamic import per locale, so only the
// requested one is ever loaded, and none of it reaches the browser.
import 'server-only';

const dictionaries = {
  en: () => import('./dict/en.json').then(m => m.default),
  fr: () => import('./dict/fr.json').then(m => m.default)
};
export const getDictionary = (locale) => dictionaries[locale]();

// A server component just awaits it
const t = await getDictionary(locale);
return <h1>{t.home.heading}</h1>;

// A client component needs the strings as PROPS — pass only the
// namespace it uses, not the whole dictionary.
<SearchBox labels={t.search} />   // 0.4 kB, not 24 kB
Namespace the dictionary
Grouping by feature is what makes passing a slice possible. One flat object of 800 keys leaves you handing the whole thing across the boundary because nothing smaller is meaningful.
Interpolation is not string concatenation
Word order differs between languages, so a template with named placeholders — "{count} items left" — is required, not a nicety. Concatenating fragments produces sentences that cannot be translated correctly.
Keys, not English
Using the English string as the key means every copy edit is a key change across every locale file. Use stable identifiers.

6Everything that is not a string

Where a translated site becomes a localised one, and it is mostly built into the platform.

Intl does most of this TypeScript
new Intl.DateTimeFormat(locale, { dateStyle: 'long' }).format(d);
new Intl.NumberFormat(locale, { style: 'currency', currency: 'GBP' }).format(n);
new Intl.RelativeTimeFormat(locale).format(-3, 'day');
new Intl.ListFormat(locale).format(['twine', 'labels', 'trowel']);
new Intl.Collator(locale).compare(a, b);        // sorting — not <
new Intl.PluralRules(locale).select(1);         // 'one' | 'other' | …

// Plurals are not two cases. Arabic has six categories, Polish
// four, Japanese one. A dictionary entry needs a case per category
// the locale actually uses — which is what ICU message format is
// for, and why libraries in section 8 are worth having.
Sorting with < is wrong
It compares code points, so accented characters sort after z and Swedish, German and Turkish all disagree with it. Intl.Collator is one line and correct.
Right-to-left is a layout change, not a text change
Set dir="rtl" and use logical CSS properties — margin-inline-start, padding-inline, inset-inline-end — rather than left and right. Then the mirroring happens for free. Icons indicating direction need flipping; a clock does not.
Text expands
German and Finnish run considerably longer than English, and some languages much shorter. A button sized to its English label breaks. Test with the longest locale you support, not with placeholder text.
Server and client must agree
Formatting a date on the server in the server's timezone and again on the client in the user's produces a hydration mismatch. Pass an ISO string and format in one place, or set the timezone explicitly.

7hreflang and metadata

Chapter 15's alternates, doing the job it exists for.

Declaring the alternates TypeScript
export async function generateMetadata({ params }) {
  const { locale, slug } = await params;
  return {
    alternates: {
      canonical: '/' + locale + '/blog/' + slug,
      languages: {
        'en-GB': '/en/blog/' + slug,
        'fr-FR': '/fr/blog/' + slug,
        'x-default': '/en/blog/' + slug      // for unmatched languages
      }
    },
    openGraph: { locale: locale.replace('-', '_') }
  };
}

// Two rules: the set must be reciprocal — every alternate lists all
// the others, including itself — and each locale's canonical points
// at itself, not at the English version. Pointing every language's
// canonical at English tells search engines the others should not be
// indexed, which is the opposite of the intention.

8Libraries

Three worth knowing, and the case for none of them.

Character
next-intlBuilt for the App Router: server and client components, ICU message format, routing helpers, typed message keys. The default recommendation for a real multilingual product.
next-i18next / i18nextEnormous ecosystem, plugins for everything, familiar to many teams. Heavier, and its App Router story arrived later.
LinguiCompiles messages at build time and extracts them from source, so keys can be the source text without the maintenance cost. Good tooling.
NothingGenuinely fine for two or three locales with simple strings: a dictionary per locale, dynamic imports, Intl for formatting, and about forty lines of your own. What you give up is ICU plurals, message extraction and translator tooling — all of which matter at scale and none of which matter at two locales.

9Check yourself

Five questions.

1. Why is a cookie-only locale a poor choice for a public site?

Because the language is invisible to everything except that one browser. Each language has no URL of its own, so a crawler cannot index the French content at all, a shared link arrives in whatever language the recipient's cookie says, and hreflang is impossible because there are no alternate URLs to declare. It also makes the route dynamic, since deciding the language means reading cookies(), so nothing can be prerendered (Chapter 8). It is a reasonable choice for an application entirely behind a login, where none of those consequences apply. For anything public, put the locale in the path.

2. Why does putting the locale in the path keep pages static?

Because it becomes a route param rather than request state. app/[locale]/blog/[slug]/page.tsx has an enumerable set of paths — locales multiplied by slugs — so generateStaticParams can return all of them and every language of every page is prerendered and served from a CDN. Reading the locale from a cookie or an Accept-Language header instead means reading the request, which tips the route dynamic and costs you a render per visit. That is the concrete reason to prefer the path prefix, quite apart from the indexing and sharing arguments.

3. What is wrong with redirecting a French-speaking visitor from /en/pricing to /fr/pricing?

It overrides a deliberate act. Somebody chose or was sent that specific URL, and redirecting away from it breaks shared links and leaves the visitor no way to read the English page — every attempt bounces them back. It also creates redirects on URLs that crawlers expect to serve a 200. Detection should apply only when there is no locale in the URL: a bare / is a reasonable place to guess, and /en/anything is not. Store an explicit choice from your language switcher in a cookie, never a header guess, or the guess becomes sticky for reasons the user cannot see.

4. How do translations reach a client component without shipping the whole dictionary?

As props, and only the namespace that component uses. A server component awaits the dictionary — loaded through a dynamic import so only the requested locale is read, and marked server-only so it cannot leak — then passes labels={t.search} rather than the whole object. That is a fraction of a kilobyte instead of twenty-four. This is what makes namespacing structural rather than cosmetic: with one flat object of 800 keys there is no meaningful slice to pass, so you end up handing the entire dictionary across the boundary, and the demo shows what that costs when multiplied by every visitor.

5. Name three things beyond strings that change with the locale.

Sort order — < compares code points, so accented characters sort after z and Swedish, German and Turkish all disagree; use Intl.Collator. Plural categories — not two cases but up to six, so Arabic and Polish need entries English does not have, which is what ICU message format exists for. And text direction, which is a layout change rather than a text change: set dir="rtl" and use logical CSS properties so the mirroring happens for free. Two more worth planning for: text expansion, since German and Finnish run much longer than English and break buttons sized to their English label; and date formatting done consistently on one side of the boundary, or you get a hydration mismatch.
