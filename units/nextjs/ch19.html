1next.config

There are dozens of options. These are the ones a real project uses.

A realistic configuration TypeScript
import type { NextConfig } from 'next';

const config: NextConfig = {
  images: {
    remotePatterns: [{ protocol: 'https', hostname: 'cdn.northwind.example' }]
  },

  redirects: async () => [
    { source: '/old-pricing', destination: '/pricing', permanent: true }
  ],

  headers: async () => [{
    source: '/:path*',
    headers: [
      { key: 'X-Content-Type-Options', value: 'nosniff' },
      { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
      { key: 'Strict-Transport-Security', value: 'max-age=63072000' }
    ]
  }],

  experimental: { optimizePackageImports: ['lucide-react'] },   // Chapter 18
  output: undefined,          // 'standalone' for Docker, 'export' for static
  poweredByHeader: false
};

export default config;

// Two settings to be suspicious of:
//   typescript: { ignoreBuildErrors: true }
//   eslint: { ignoreDuringBuilds: true }
// Both exist for genuine migration emergencies and both become
// permanent. If they are in your config, put a dated comment
// saying why and who is removing them.
Headers here, not in middleware
Static security headers are declarative, cost nothing at runtime, and live where the next person will look. Middleware is for headers that depend on the request.
Redirects here, not in middleware
Chapter 7's pipeline: config redirects resolve before your code runs. A permanent URL change is not a decision, so it does not need a function.
A content security policy is worth the effort
It is the one header that genuinely needs a nonce per request, so it belongs in middleware. Start in report-only mode, read the reports for a week, then enforce.

2Environment variables

One prefix, one rule, and a mistake that is impossible to take back.

NEXT_PUBLIC_ means published

Any variable with that prefix is inlined into the client bundle at build time — its value becomes a literal string in the JavaScript every visitor downloads. That is exactly what it is for. It also means a secret given that prefix is not a secret any more, and nothing warns you: the build succeeds, the app works, and the key is in your page source. If it has ever been deployed, rotate it — you cannot un-publish it.

Validate at boot, not at first use TypeScript
// env.ts — imported by instrumentation.ts, so a missing variable
// fails the build or the boot rather than a request at 3am.
import { z } from 'zod';

const server = z.object({
  DATABASE_URL: z.string().url(),
  STRIPE_SECRET_KEY: z.string().startsWith('sk_'),
  SESSION_SECRET: z.string().min(32)
});

const client = z.object({
  NEXT_PUBLIC_SITE_URL: z.string().url()
});

export const env = {
  ...client.parse(process.env),
  ...(typeof window === 'undefined' ? server.parse(process.env) : {})
};

// The file precedence, highest first:
//   .env.local  (never committed)  → .env.development / .env.production
//   → .env  → the real environment. Commit a .env.example listing
//   the NAMES with no values, so a new joiner knows what is needed.

4Cold starts

The cost of a route that has not run recently, and four ways to reduce it.

Keep module scope cheap
Code at the top level of a route module runs on every cold start. Creating a database pool, reading a large JSON file or initialising an SDK there is paid before your handler begins. Do it lazily, memoised.
Smaller bundles start faster
Chapter 18's work helps here too, on the server side: less to load and parse before the first request is served.
Static routes have no cold start at all
They are files. This is one more argument for Chapter 8's containment work — a route that never runs cannot be slow to start.
Connection pooling needs thought in serverless
Each instance holding its own connections multiplies against your database's limit. A pooler such as PgBouncer, or a driver designed for the model, is not optional at scale.

5Instrumentation

Two files, both easy to overlook and both worth having on day one.

Server startup and error reporting TypeScript
// instrumentation.ts — at the project root, runs once per server start
export async function register() {
  await import('./env');                    // fail fast on bad config
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    await import('./tracing');              // OpenTelemetry setup
  }
}

// onRequestError — server-side errors, including ones no error
// boundary sees (Chapter 18 of the React unit)
export async function onRequestError(err, request, context) {
  await reportToTracker(err, {
    path: request.path,
    routerKind: context.routerKind,
    renderSource: context.renderSource,
    revalidateReason: context.revalidateReason
  });
}
Trace across the boundary
Next emits OpenTelemetry spans for rendering, fetching and route resolution. Connecting them to your database spans turns "the page is slow" into "this query takes 600ms", which is the difference between guessing and knowing.
Client vitals separately
useReportWebVitals in a small client component sends the real field metrics from real devices. Chapter 18's argument about the p75.
Log the release
Attach a build id to every error and metric. Attributing a spike to a deployment is the single most useful thing observability gives you, and it is one field.

6Tooling and the custom server

Briefly, and one warning worth its own paragraph.

Type checking is not part of the build
Next runs tsc during next build by default, which is more than a bare bundler does — but if you have set ignoreBuildErrors, nothing is checking. Run tsc --noEmit in CI regardless. React Chapter 17.
Lint rules worth enforcing
The hooks rules as errors, and eslint-plugin-react-hooks's compiler diagnostics. Next's own config also catches things like a plain <img> where next/image was intended, and synchronous script tags.
A custom server disables a great deal
Running Next behind your own Express or Fastify server turns off automatic static optimisation and most platform integrations. Almost every reason people want one — headers, redirects, rewrites, proxying, auth — is better served by config or middleware. Reach for it only for something genuinely outside HTTP request handling, such as a websocket server sharing the process, and know what you are giving up.

7Check yourself

Five questions.

1. What does the NEXT_PUBLIC_ prefix actually do?

It inlines the variable's value into the client bundle at build time, so it becomes a literal string in the JavaScript every visitor downloads. That is the intended behaviour for things that must reach the browser: a publishable payment key, a public site URL, an error-tracking DSN. It also means giving that prefix to a secret publishes the secret, with no warning at any point — the build succeeds and the application works. Two consequences: never add the prefix to reach something in a client component without asking whether it should be public, and if a secret has been deployed with it, rotate the credential, because you cannot retract a value already in someone's cache.

2. Why validate environment variables at boot rather than where they are used?

Because otherwise a missing or malformed variable surfaces as a confusing runtime failure on whichever request happens to touch that code path first — possibly a rarely used route, possibly at three in the morning, and with an error that names a database client rather than the configuration. Parsing the whole environment with a schema in a module imported from instrumentation.ts means a bad deployment fails at start-up with the variable named. It also gives you a typed env object rather than process.env.THING! assertions scattered around, and it documents what the application requires.

3. When is the edge runtime the right choice?

When all of four things hold: the work is small — a redirect, a rewrite, a token signature check, a geolocation lookup, a light proxy; nothing needs a Node API or a native module; physical closeness to the user is worth something; and a fast cold start matters because the route is hit infrequently. That describes middleware and a handful of route handlers. For nearly everything else, Node: the moment you touch a database with a normal driver, read a file, or want a larger bundle, edge is either impossible or awkward. The specific trap worth remembering is that Chapter 17's content index calls readFile, so an MDX route cannot be edge — which catches people who set edge as a project-wide default.

4. Why do static security headers belong in next.config rather than middleware?

Because they do not depend on the request, so there is nothing to decide. Declaring them in config costs no runtime execution, applies before any of your code runs, and lives somewhere declarative that the next person will look for it. Putting them in middleware means paying a function invocation on every matching request — including every prefetch (Chapter 7) — to emit constants, and moving routing configuration into imperative code. The one exception is a content security policy with a per-request nonce, which genuinely needs to be generated per request and therefore does belong in middleware.

5. What does a custom server cost you?

Automatic static optimisation and most platform integrations. Running Next inside your own Express or Fastify process means the framework can no longer make its own decisions about how routes are served, so the static and revalidated rendering from Chapter 8 stops applying — which is a large loss for a small amount of control. And almost every motivation people have for one is better served elsewhere: headers and redirects in config, request-dependent logic in middleware, proxying with a rewrite, authentication in middleware plus the page. The remaining legitimate case is something genuinely outside HTTP request handling, such as a websocket server sharing the process — and even then, running it as a separate service is usually simpler.
