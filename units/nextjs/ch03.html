CHAPTER 03

Layouts, templates and the route tree

A URL does not select a page. It selects a chain of layouts with a page at the end, and the layouts above the change stay mounted. That single fact is what makes navigation in a Next application feel like moving around inside something rather than loading documents.

Part 1 Foundations·Reading time 35 minutes·Demos what persists, boundary placement·Prerequisites Chapter 2

1A URL selects a stack

Every layout.tsx on the path from app/ to the matched page contributes a layer.

Three layouts and a page JSX
app/layout.tsx              // root: html, body, fonts, providers
app/(app)/layout.tsx        // signed-in shell: header, sidebar
app/(app)/orders/layout.tsx // orders shell: filters, tabs
app/(app)/orders/[id]/page.tsx

// Visiting /orders/4182 composes:
<RootLayout>
  <AppLayout>
    <OrdersLayout>
      <OrderPage params={{ id: '4182' }} />
    </OrdersLayout>
  </AppLayout>
</RootLayout>

// Every layout must accept and render children. Forgetting to
// render them produces a blank page with no error, which is a
// surprisingly common ten minutes.
export default function OrdersLayout({ children }) {
  return <div className="orders"><Filters />{children}</div>;
}

Layouts persist within their subtree
Moving from /orders/4182 to /orders/4183 keeps the root layout, the app shell and the orders layout mounted. Their state, scroll positions and any data they loaded are all untouched, and their server components are not re-rendered.
Leaving the subtree unmounts them
Going from /orders/4182 to /customers keeps the root and app layouts but discards the orders layout — the filters close, its state is gone.
The page is reused when the component is the same
Two order ids render the same page.tsx in the same position, so React reuses the instance and its client state — the selected tab stays selected even though the order changed. That is React Chapter 4's identity rule, and it is usually right. When it is not, key the offending component on the id.
A hard reload resets everything
Persistence is a property of client-side navigation. Pressing the browser's reload button rebuilds the whole stack, which is why a layout is the wrong place to keep anything the user would be annoyed to lose.

3Layout or template

One file differs from the other in exactly one way, and that way decides everything.

layout.tsxtemplate.tsx
On navigation within its subtreeStays mountedUnmounts and remounts
StatePreservedReset
EffectsRun onceRun on every navigation
Position in the treeOutside the templateInside the layout, outside the page
Use forAlmost everything: shells, navigation, providers, persistent panelsEnter animations, per-view analytics, deliberately resetting a form or a scroll container on each visit

Default to a layout. Reach for a template only when you specifically want the remount — and note that both can exist at the same level, with the template nested inside the layout, which is occasionally exactly what you want: a persistent sidebar and an animating content area.

4The root layout

Required, unique, and constrained in five ways worth knowing before you fight one of them.

The one layout you cannot omit JSX
import { Inter } from 'next/font/google';
const inter = Inter({ subsets: ['latin'] });

export const metadata = { title: { default: 'Northwind', template: '%s — Northwind' } };

export default function RootLayout({ children }) {
  return (
    <html lang="en" className={inter.className}>
      <body>{children}</body>
    </html>
  );
}
It must render <html> and <body>
No other layout may. This is also why global-error.tsx has to supply its own — the thing that would have provided them is what failed.
It never unmounts
Nothing in it is discarded by navigation, which makes it the right home for providers, fonts and anything global. It also means a mistake there is permanent for the session.
Keep it a server component
It can be marked 'use client', and doing so pulls your entire application into the client bundle (React Chapter 19). If a provider needs to be a client component, wrap only the provider — export a small Providers client component and render it here.
Route groups can each have one
If app/layout.tsx does not exist, every top-level route group must supply a root layout of its own. That is how a marketing site and an application can have genuinely separate shells, including different fonts and different <body> classes.
Metadata is exported, not rendered
Do not write <title> or <meta> tags by hand. Export a metadata object and let Next place and deduplicate them. Chapter 15.

loading.tsx covers the segment below it
Placed in app/orders/, it wraps everything from app/orders/page.tsx downwards — but not the orders layout itself, which renders immediately alongside the fallback. That is usually what you want: the filters appear straight away and only the results wait.
For finer control, use Suspense directly
loading.tsx is a whole-segment boundary. When only one panel is slow, wrap that panel in <Suspense> inside the page instead, and let the rest of the page render immediately. Chapter 11.
error.tsx works the same way, one level off
It covers the segment below it, so it cannot catch a throw in its own layout — Chapter 2's demo. A boundary protects what is beneath it, and a layout is never beneath its own segment's boundary.
Size the fallback like the content
A spinner replacing a 600-pixel table moves everything below it twice. A skeleton with the same footprint moves nothing.

6Data between a layout and its page

There is no prop channel, and the workaround is better than a prop channel.

A layout cannot pass data to its page

Layouts render children, and children is an already-created element — the layout cannot add props to it. There is also no shared context between server components. So if a layout fetches an order and the page needs the same order, the layout cannot hand it over.

Just fetch it in both places
This sounds wasteful and is not. Within a single request, identical fetch calls are memoised, so the second one does not hit the network at all — and with a database client you can wrap the query in React's cache() for the same effect. Chapters 9 and 10.
A layout does not receive searchParams
Only params. This is deliberate: layouts are not re-rendered on navigation, so a search-param value would go stale immediately. If a layout genuinely needs them, that part belongs in a client component reading useSearchParams.
Shared client state goes in a client provider
Rendered inside the layout, wrapping children. The layout stays a server component; the provider is a small client island.
Request-scoped values come from the request
cookies(), headers() and your auth helper are available anywhere on the server, so a page does not need a layout to pass the session down. Note the cost: reading them makes the route dynamic, which Chapter 8 covers.

7Five layout mistakes

All of them produce confusing symptoms rather than errors.

MistakeSymptom
Not rendering childrenA blank content area, no error, no warning. Check this first.
'use client' in the root layoutEverything works, and the bundle triples. Wrap the provider instead.
Expecting a layout to re-run on navigationData fetched in a layout looks stale after a client-side navigation, because the layout never re-rendered. Move it into the page, or into a segment whose position changes.
Reading cookies() in the root layoutEvery route in the application becomes dynamic, and nothing is static any more. The build output is where you notice.
Putting a form's state in a layoutIt survives navigation, which sounds good until the user goes to a different order and finds the previous one's draft.

8Check yourself

Five questions, closing Part 1.

1. Navigating from /orders/4182 to /orders/4183, what re-renders?

Only the page, and even that is reused rather than remounted. Every layout on the path — root, app shell, orders — stays mounted with its state, scroll position and loaded data untouched, and their server components are not re-rendered. The page component is the same component in the same position with a different params.id, so React reuses the instance: its client state, such as a selected tab, persists across the change. That is normally desirable, and when it is not — a form that must reset per order — you give the component a key tied to the id so it remounts cleanly.

2. When is template.tsx the right choice over layout.tsx?

When you specifically want the remount. A template unmounts and remounts on every navigation within its subtree, so its state resets and its effects re-run — which is exactly right for an enter animation that should play each time, for per-view analytics, or for deliberately clearing a scroll container or a draft on each visit. For everything else a layout is better, because persistence is the feature. They can also coexist at one level, with the template nested inside the layout, giving you a persistent sidebar around an animating content area.

3. Why should the root layout stay a server component?

Because 'use client' marks a boundary that everything below it crosses — the module and its entire import graph become client code (React Chapter 19). At the root, that is your whole application: every component ships to the browser, every server-only dependency comes with it, and no route can query a database directly any more. Nothing errors; the bundle simply triples. When a provider genuinely needs to be a client component, extract a small Providers component marked 'use client' and render it inside the server root layout, so the boundary sits around the provider rather than around everything.

4. A layout fetches an order and the page needs it too. How do you share it?

You do not — you fetch it again in both places. A layout renders children, which is an already-created element it cannot add props to, and server components share no context, so there is no channel. Fetching twice is not the waste it appears to be: within a single request, identical fetch calls are memoised so the second never reaches the network, and a database query can be wrapped in React's cache() for the same deduplication. The result is arguably better than prop passing, because each component states its own data requirement instead of depending on an ancestor to have loaded it.

5. Where should a loading.tsx go if only one panel on a page is slow?

Nowhere — use <Suspense> around that panel inside the page instead. loading.tsx is a whole-segment boundary, so putting one in app/orders/ replaces the entire page content with a fallback even though the header, the gallery and the order details were ready immediately. An inline boundary lets everything else paint at once and streams only the slow panel into place. The rule that follows: loading.tsx when the whole segment genuinely waits together, inline Suspense when one region is the problem — and in both cases the fallback should occupy the same space as the content it replaces.
