CHAPTER 01

What Next.js is for

React renders components and deliberately declines to say where or when. A framework answers those two questions, and every feature in this unit is a consequence of one of them. Knowing which question a feature answers is most of understanding it.

Part 1 Foundations·Reading time 35 minutes·Demos first-paint timeline, is it a fit·Prerequisites React components and hooks

1The two questions React leaves open

Where the code runs, and when. Everything else follows.

A React application built with Vite answers both questions the same way for everything: in the browser, after the bundle arrives. That is a coherent and often correct answer. It is also the only answer available, and it has consequences — the first paint waits for JavaScript, every byte of every dependency ships to every user, and a crawler or a link preview sees an empty document.

Where
Build machine, server, edge, or browser. Next lets each route — and, with server components, each part of a route — pick. That is what makes a database query in a component possible and a markdown parser free.
When
At build time, on each request, or once and then periodically. This is the axis people mean by "static versus dynamic", and it is decided per route rather than per project.
And then a third question nobody expected
Once the answer to when can be "earlier, and reused", you have a cache. Then several. Chapter 10 is the longest in this unit for that reason, and the difficulty is genuine rather than accidental.

3What Next actually gives you

Nine things, and the point is that they are integrated rather than assembled.

ConcernWhat you would otherwise assemble
RoutingA router, plus code splitting per route, plus a convention for where data loading lives. Next derives all three from the filesystem.
Server renderingA server that renders React to a stream, a hydration entry point, and matching of the two so they do not disagree.
Server componentsNot assemblable. It needs a bundler that understands the client boundary and a runtime that can stream the payload — which is why Chapter 19 of the React unit only exists inside a framework.
Data and mutationsAn API layer, or server actions that remove the need for one.
CachingSeveral layers, hand-rolled, incorrectly. This is the largest thing Next does for you and the largest thing to understand.
AssetsImage resizing and format negotiation, font subsetting without layout shift, script loading strategies.
MetadataPer-route titles, descriptions, canonical URLs and generated social preview images.
BuildA bundler configured for two environments, environment variable handling, and a production output that a host understands.
ConventionsThe genuinely underrated one. Any Next developer can open your repository and know where things are.

4App Router and Pages Router

Two frameworks in one package. This unit teaches the first; here is enough about the second to read old code.

They can coexist in one project during a migration, which is the intended path for a large application. New work should use app/. And note the honest trade in the last row: the Pages Router was easier to reason about, and a good deal of this unit exists because the App Router is not.

5What it costs

Stated plainly, because the alternative is finding out in month three.

A server to run
Unless every route is static, something must execute per request. That is a deployment target, a cold-start characteristic, a bill, and someone to own it.
Two mental models at once
Server and client components have different capabilities, and the error messages are not always clear about which side you are on. Chapter 19 of the React unit is a prerequisite for a reason.
Caching you must learn
The defaults are aggressive by design and have changed between major versions. "My change does not appear" is the single most common complaint, and it is almost never a bug.
Ecosystem friction
Any library needing a context provider or a browser API needs a client wrapper. Runtime CSS-in-JS does not work in server components at all.
Conventions you cannot easily leave
File-based routing, the special filenames and the caching directives are Next-shaped. Your components and logic are portable; that layer is not.
An upgrade cadence
Next moves quickly. Falling two majors behind turns one upgrade into three interacting ones.

7The model to hold

Four sentences that make the rest of the unit easier.

Carry these forward

1. The filesystem is the configuration. A folder is a URL segment; a specially named file is a behaviour. There is no route table to read, which is either elegant or disorienting depending on the day.

2. Server is the default. A component runs on the server unless something marked 'use client' pulled it across. You opt into the browser, not out of it.

3. A route is a stack, not a page. Nested layouts persist across navigation; only the innermost changed segment re-renders. Chapter 3.

4. Assume something is cached. When output is stale, the question is not whether a cache is involved but which. Chapter 10.

8Check yourself

Four questions.

1. Which two questions does a React framework answer that React does not?

Where the code runs and when it runs. React renders components and has no opinion about either, so a plain client-side application answers both the same way for everything: in the browser, after the bundle arrives. Next lets each route — and with server components, each part of a route — choose a place (build machine, server, edge, browser) and a time (build, per request, or once and then periodically). A third question then appears uninvited: once work can happen earlier and be reused, you have a cache, and then several. That is why the caching chapter is the longest in this unit.

2. Where does a client-rendered page actually lose time, and does server rendering fix all of it?

It loses time twice. First the browser gets an effectively empty document, so nothing is visible until the bundle has downloaded and executed. Then the application starts its data request — which could not begin earlier, because the code that knows about it had not arrived. Server rendering fixes the first problem completely: markup with real content arrives in the first response, and the data query happens on the server next to the database. It does not fix interactivity, because the bundle must still download and hydrate before anything responds to a click. That is the gap the demo shows between the first two tiles, and it is why reducing client JavaScript matters even with server rendering.

3. Why is the App Router harder to reason about than the Pages Router?

Because it is more capable in exactly the ways that add invisible state. Data loading moved from one explicit function per page to await anywhere in the tree, which is more flexible and much harder to see at a glance. Components are split across a server-client boundary that is not visible in the file you are reading. And caching went from mostly explicit to several layers with defaults, none of which appear in the browser's network panel. The capability is real — nested persistent layouts, streaming, server components — but the trade is genuine, and pretending otherwise is why people are surprised in production.

4. Give a case where Next.js is the wrong choice.

An application entirely behind a login with no SEO requirement, no first-paint pressure and nobody to operate a server — an internal dashboard, an admin tool, an editor. Every page is personalised, so nothing can be static or cached; there is no crawler to serve; and you have taken on a server, a second component model and a caching system in exchange for very little. Vite plus React Router, with a query library for data, is faster to develop, deployable as static files, and has less to unlearn. The other clear misfits are a canvas or editor application where almost everything is client state, and a small embedded widget where the framework outweighs the product.
