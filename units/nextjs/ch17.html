MDX and content

Markdown with components in it, compiled at build time. Excellent for documentation and engineering blogs, actively bad for content a marketing team edits weekly — and the difference is entirely about who writes it, not about the technology.

Part 4 The product layer·Reading time 35 minutes·Demos the pipeline stages, frontmatter validation·Prerequisites Chapters 4, 8

1Where content can live

Decide by who edits it and how often, not by which is more elegant.

OptionSuits
MDX in the repositoryDevelopers writing docs, changelogs, engineering blogs. Version controlled, reviewable in a pull request, deployed with the code, and components can be embedded inline. Requires a commit and a build to publish.
A headless CMSNon-technical authors, frequent edits, scheduled publishing, previews, localised content, media libraries. Sanity, Contentful, Payload, Strapi. You gain a whole editing product and take on an integration and a service.
Markdown from a databaseUser-generated content, or an author interface you already own. Compiled at request time rather than build time, so section 5's warning applies.
Git-backed CMSThe middle ground: a web editor writing MDX back to the repository. Sensible when a small non-technical team edits developer-owned content.

The honest test: will someone without a Git account need to publish a correction on a Friday afternoon? If yes, MDX in the repository is the wrong home however pleasant it is to work with, and you will end up as the bottleneck for typo fixes.

2Setting it up

Two arrangements: MDX files as routes, or MDX compiled from a string.

The file-based route, and shared component mapping TypeScript
// next.config.ts
import createMDX from '@next/mdx';
const withMDX = createMDX({ options: { remarkPlugins: [], rehypePlugins: [] } });
export default withMDX({ pageExtensions: ['ts', 'tsx', 'mdx'] });

// mdx-components.tsx at the project root — maps markdown elements
// to your own components, for every MDX file at once.
export function useMDXComponents(components) {
  return {
    h2: (p) => <h2 className="sec" {...p} />,
    a: (p) => <Link {...p} href={p.href} />,
    img: (p) => <Image {...p} sizes="(max-width: 720px) 100vw, 680px" />,
    Callout,                       // available in MDX without importing
    ...components
  };
}

// Then app/blog/hello/page.mdx is a route. Simple, and it means one
// folder per post — which is why most projects instead keep MDX in
// a content/ directory and compile it from a [slug] route.
File-as-route or content directory
page.mdx is the least configuration and gives you no index, no sorting and no tags. A content/ directory read by app/blog/[slug]/page.tsx costs a little setup and gives you section 6 — which almost every real blog needs.
Compiling from a string
next-mdx-remote or @mdx-js/mdx when the source is a database or a CMS. Note that MDX is executable — it compiles to JSX — so never compile MDX submitted by users. For untrusted input, use plain markdown with a sanitising pipeline.
Rendering happens on the server
An MDX document is a server component by default, so it can embed components that query a database. Only the interactive parts need 'use client', which keeps a documentation site's bundle very small.

const frontmatter = z.object({
  title: z.string().min(1),
  date: z.coerce.date(),                  // YAML gives you a string
  tags: z.array(z.string()).default([]),

4remark and rehype

Two plugin families operating on two different trees. Knowing which is which explains every plugin name you will meet.

One paragraph of markdown through the pipeline Toggle plugins and watch which stage each one changes.

FamilyOperates onTypical plugins
remarkThe markdown tree (mdast) — headings, lists, links as markdown concepts remark-gfm for tables, strikethrough and task lists. remark-frontmatter. Anything changing the meaning of the document.
rehypeThe HTML tree (hast) — elements and attributes rehype-slug for heading ids. rehype-autolink-headings. rehype-pretty-code or rehype-shiki for highlighting. Anything changing the output markup.

The rule that follows: if it is about what the document says, it is remark; if it is about the HTML you get, it is rehype. Order matters within each family — rehype-autolink-headings needs rehype-slug to have run first, or there are no ids to link to.

5Syntax highlighting at build time

The difference between a documentation site that is instant and one that ships a parser.

There is no real argument for the second column in a Next project. The code is known at build time, so highlight it then: the output is plain styled markup, nothing is downloaded, and it matches what the author saw while writing. Shiki also supports dual light and dark themes in one pass via CSS variables, so it works with Chapter 13's theming.

6The content index

The thing file-as-route does not give you, and every blog needs.

Read once, cache, derive everything TypeScript
import 'server-only';
import { cache } from 'react';

export const getAllPosts = cache(async () => {
  const files = await readdir('content/blog');
  const posts = await Promise.all(files.map(async (f) => {
    const raw = await readFile(join('content/blog', f), 'utf8');
    const { data, content } = matter(raw);
    return { slug: f.replace(/\.mdx$/, ''), ...frontmatter.parse(data), content };
  }));
  return posts
    .filter(p => process.env.NODE_ENV === 'development' || !p.draft)
    .sort((a, b) => b.date.getTime() - a.date.getTime());
});

// Which then feeds everything:
export async function generateStaticParams() {
  return (await getAllPosts()).map(p => ({ slug: p.slug }));
}
// … and the listing page, the tag pages, the sitemap (Chapter 15),
// the RSS feed, and "related posts" by shared tags. One source.
cache() matters here
The index is read by the listing page, generateStaticParams, generateMetadata, the sitemap and the feed. Wrapping it deduplicates within a request rather than reading the directory five times.
Drafts visible in development only
One line, and it makes writing pleasant without risking a publish. Pair it with robots: { index: false } on any preview deployment.
Node APIs mean the Node runtime
readdir and readFile do not exist on the edge, so a route reading content from disk needs runtime = 'nodejs' — Chapter 19. This surprises people who set edge as a default.
Consider a content layer at scale
Once you have hundreds of documents, tools that precompute a typed index at build time save real time. The pattern above is the same idea, hand-rolled, and it stays readable to a few hundred files.

7When MDX is the wrong answer

Four signals, and the first is decisive on its own.

Non-developers publish
A commit, a review and a deploy to fix a typo is a workflow that will be worked around rather than followed. You become the bottleneck for corrections, which is nobody's intention and everyone's outcome.
The content is structured, not prose
Products, events, team members, pricing tiers. Those want typed fields and relationships, not a document with a heading convention. A CMS or a database models them properly; frontmatter with twelve keys is a database schema in disguise.
Publishing needs scheduling, previews or workflow
Embargoed posts, review states, a preview URL for a stakeholder. All buildable, none of it worth building.
Content changes far more often than code
Every edit triggering a deployment couples two things with very different cadences, and it makes your deploy pipeline a publishing bottleneck.
Where it genuinely excels

Documentation written by the people who wrote the code — reviewable alongside it, versioned with it, and able to embed live components and runnable examples inline. Changelogs. Engineering blogs. Anything where the author is comfortable with a pull request and the value of embedding real components is high. For those it is not a compromise; it is better than a CMS.

8Check yourself

Four questions, closing Part 4.

1. What decides whether MDX is the right home for content?

Who edits it and how often — not the technology. If publishing requires a commit, a review and a deploy, then anyone without a Git account is dependent on a developer to fix a typo, and that workflow gets worked around rather than followed. MDX excels where the author is the developer: documentation reviewable alongside the code it describes, changelogs, engineering blogs, anything benefiting from embedded live components. It is the wrong home for content a marketing team edits weekly, for structured records like products or events that want typed fields and relationships, and for anything needing scheduling, previews or an approval workflow.

2. What is the difference between remark and rehype?

The tree they operate on. remark plugins transform the markdown syntax tree, where the nodes are markdown concepts — headings, lists, emphasis, tables — so anything changing what the document says is remark: remark-gfm adding tables and task lists, remark-frontmatter handling the metadata block. rehype plugins transform the HTML tree after conversion, where the nodes are elements and attributes, so anything changing the markup you get is rehype: rehype-slug adding heading ids, rehype-autolink-headings, syntax highlighting. Order matters within each family — autolink needs slug to have run, or there are no ids to link to.

3. Why highlight code at build time rather than in the browser?

Because the code is already known, so there is nothing to decide at runtime. Build-time highlighting with Shiki produces plain styled markup: no library and no language grammars downloaded, no flash of unstyled code, it works with JavaScript disabled, and the fidelity is higher because it uses the same TextMate grammars as your editor rather than regular expressions. A runtime highlighter ships a parser plus a grammar per language to every reader in order to re-derive something that was static. Shiki also emits dual light and dark themes via CSS variables in one pass, so it fits the theming from Chapter 13 without a second build.

4. Why validate frontmatter with a schema?

Because YAML is untrusted input and gives you strings for everything, so a mistyped date, a missing title or tags written as a single string rather than a list will otherwise flow into your templates and produce a broken page — or a broken sitemap entry, or an invalid datetime attribute. Parsing at build time turns a malformed post into a failed build with the file named, which is the right moment to find out. It also gives you the TypeScript type by inference, so the type cannot drift from the rules, and coercion in one place — z.coerce.date() — rather than scattered through the components that read it.

Carry forward

Choose by who publishes, not by elegance. remark is meaning, rehype is markup. Highlight at build time, always. Validate frontmatter so a bad post fails the build. Never compile user-submitted MDX.
