CHAPTER 02

Project anatomy and file conventions

There is no route table. The folder structure is the routing configuration and a dozen reserved filenames are the behaviour. That is either elegant or opaque, and which one it feels like depends almost entirely on whether you know the dozen.

public/ is not processed
Files are served from the root exactly as they are, with no hashing, so they cannot be cached aggressively and must not be renamed casually. Put anything that needs optimisation through next/image or next/font instead (Chapter 14), and remember that everything in here is public — the folder name is doing its job.
The @/* alias
tsconfig.json maps it to the project root or src/. Use it — @/components/Button rather than four levels of ../ — because relative imports break the moment a route moves, which in a filesystem router happens often.

2Folders make segments, files make routes

Two rules, and the second one is the surprise.

The whole routing model

1. Each folder inside app/ is one URL segment, nested exactly as the folders nest.

2. A folder is only reachable if it contains a page.tsx or a route.ts. Without one it contributes a path segment for its children and cannot be visited itself.

That second rule is what makes colocation safe: you can put components, tests, helpers and even whole folders next to a route and none of them become URLs.

3The reserved filenames

Eleven of them. Learn what each guarantees, not just what it renders.

FileWhat it is, and what it guarantees
page.tsxMakes the segment reachable and renders its content. Receives params and searchParams. Exactly one per route.
layout.tsxWraps this segment and everything below it, and persists across navigation within its subtree — it does not re-render or lose state when a child route changes. Must render its children.
template.tsxLike a layout but remounts on every navigation. For enter animations and per-view effects. Rarely what you want; Chapter 3.
loading.tsxSugar for a Suspense boundary around the segment. Its presence is what makes the segment's data streamable.
error.tsxAn error boundary around the segment. Must be a client component — it needs state and a reset handler. Does not catch errors in its own layout.
global-error.tsxThe last resort, wrapping the root layout. Must render its own <html> and <body>, because the root layout is what failed.
not-found.tsxRendered for an unmatched URL, and for anything that calls notFound().
route.tsA plain HTTP handler — GET, POST and so on. Cannot coexist with page.tsx in the same folder. Chapter 4.
default.tsxA fallback for an unmatched parallel-route slot, usually on a hard reload. Chapter 6.
middleware.tsRuns before a request reaches any route. Lives at the project root, not in app/. Chapter 7.
instrumentation.tsServer startup hooks, for tracing and monitoring. Chapter 19.

Also file-based but for output rather than routing: sitemap.ts, robots.ts, opengraph-image.tsx, icon.tsx and manifest.ts — Chapter 15.

4Folders that are not segments

Three naming conventions that let structure and URLs disagree on purpose.

Parentheses, underscore, at-sign Structure
app/
  (marketing)/          // route GROUP — organises and can hold its own layout,
    layout.tsx          //   but contributes NOTHING to the URL
    page.tsx            //   → /
    pricing/page.tsx    //   → /pricing        (not /marketing/pricing)
  (app)/
    layout.tsx          // a completely different shell for signed-in users
    dashboard/page.tsx  //   → /dashboard

  _lib/                 // PRIVATE folder — opted out of routing entirely,
    queries.ts          //   even if someone puts a page.tsx inside it

  dashboard/
    @analytics/         // a named SLOT for parallel routes — Chapter 6
    @activity/
Route groups earn their place for one reason
They let two parts of a site have genuinely different root-level shells — a marketing layout and an application layout — without a URL prefix nobody asked for. Using them merely to tidy files is fine but rarely worth the indirection.
Two groups can both define the same route
And that is a build error, not a silent precedence rule. Worth knowing because the message points at two files that look unrelated.
The underscore is a hard opt-out
Useful when a folder name would otherwise collide with a route, or to make it obvious that a directory is internal. To use a literal leading underscore in a URL, write %5F.

5Colocation, and where other code lives

Because nothing is routable without page or route, you have real freedom here.

A route folder that holds its own world Structure
app/orders/[id]/
  page.tsx              // the only routable file here
  loading.tsx
  error.tsx
  OrderHeader.tsx       // not a route — just a component next to its user
  OrderHeader.test.tsx
  actions.ts            // server actions for this route (Chapter 12)
  queries.ts

// Shared across routes — outside app/, or in a private folder:
components/ui/          // design system
features/orders/        // domain logic, per React Chapter 23
lib/                    // db client, formatting, fetch wrapper
Colocate what one route uses; share what several do
A component used by exactly one page belongs next to that page. The moment a second route imports it, it moves out. This is React Chapter 23's feature-folder argument, and file-based routing makes it easier rather than harder.
app/ is for routing, not for everything
Domain logic, the database client and the design system have no reason to live under app/. Putting them there invites accidental route creation and makes the routing structure harder to read.
Where server-only code goes
Anywhere, but mark it: the server-only package makes importing a module from a client component a build error rather than a runtime leak. Worth using for anything holding secrets or a database connection.

7Check yourself

Five questions.

1. You add app/orders/OrderTable.tsx. Is /orders/OrderTable now a URL?

No. Only a page.tsx or a route.ts makes something reachable, and a component file is neither. Folders build path segments and files with reserved names attach behaviour; everything else is inert. That is precisely what makes colocation safe — you can keep components, tests, helper modules and query functions inside a route folder without accidentally publishing them as URLs. Note the related rule: even app/orders/table/ with no page.tsx inside it is not visitable, though it still contributes /orders/table/... as a prefix for any child that does have one.

2. What does a route group in parentheses change about the URL?

Nothing — that is the entire point. app/(marketing)/pricing/page.tsx serves /pricing, not /marketing/pricing. The value is that a group can hold its own layout.tsx, so two parts of a site can have genuinely different top-level shells — a marketing layout and a signed-in application layout — without inventing a URL prefix for the distinction. One consequence worth knowing: if two groups both define the same resulting route, that is a build error rather than a precedence rule, and the message names two files that look unrelated.

3. Why must error.tsx be a client component, and what can it not catch?

Because an error boundary needs state to record that something failed and a handler to reset itself, and neither is available in a server component — so the file requires 'use client'. What it cannot catch is an error thrown in its own segment's layout, because that layout sits above the boundary in the composed tree. To cover a layout you need an error.tsx in the parent segment, and to cover the root layout you need global-error.tsx, which is why that file has to render its own <html> and <body> — the elements that would normally provide them are the thing that broke.

4. What does adding a loading.tsx actually do?

It wraps the segment in a Suspense boundary with that file's output as the fallback. The consequence is bigger than "a spinner appears": its presence is what makes the segment streamable, so Next can send the surrounding shell immediately and stream this part in when its data resolves, rather than holding the whole response until everything is ready. Where you place it therefore decides how much of the page waits together — the same boundary-placement decision as React Chapter 12, expressed as a filename. Chapter 11 covers designing them.

5. A route you expected to be static shows ƒ in the build output. What does that mean?

It is being rendered per request rather than prerendered at build time, because something in it read request-specific information — cookies(), headers(), searchParams, or a fetch marked not to cache. One such call anywhere in the route's tree, including in a shared component, tips the whole route over. This matters because it silently changes the cost and speed profile of a page you thought was free from a CDN, and the build output is the only place it is visible. Chapter 8 covers exactly what triggers it and how to keep the dynamic part contained rather than letting it spread.
