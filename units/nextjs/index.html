Next.js

Next.js takes React and answers the questions React deliberately leaves open — where code runs, when it runs, and what gets cached. Most of the difficulty is in that third question. Twenty-two chapters, each one a page you can read end to end.

·How to use this unit

Next.js is easy to use and hard to reason about. This unit is aimed squarely at the reasoning.

Every chapter is one HTML page in this folder. Nothing loads from a server and nothing loads from a parent directory. The demos run real code: several of them implement the mechanism being described, so when a chapter says a request was answered by the router cache without touching the network, there is a control that lets you cause it and watch where the request stopped.

Assumed knowledge
React, to roughly the level of the React unit — components, state, effects, Suspense, and especially server components and the client boundary. This unit does not re-teach them; it shows what a framework does with them.
The App Router only
The Pages Router is covered in Chapter 1 for orientation and then set aside. It still works and large applications still run on it, but it is not what a new project should adopt, and covering both would double the length while teaching half as much.
Version drift, honestly
Next changes faster than most of what this catalogue covers, and caching defaults in particular have shifted between major versions. Chapters name the behaviour and the direction of travel rather than pinning to a release, and Chapter 10 tells you how to verify what your version actually does.
Where to start
Part 1 if you are new to the App Router. Part 3 if you have shipped something and it is behaving strangely — the caching chapter is the one people need and rarely read first.

·Contents

Five parts. Cards without a link are not written yet.

·The shape of the argument

What each part is for, in a sentence.

Part 1 · Foundations
What problem the framework solves, what the file conventions actually mean, and how a URL becomes a stack of layouts. Almost every later confusion traces back to one of these three.
Part 2 · Routing
Dynamic segments, route handlers, navigation and prefetching, the two advanced patterns worth knowing, and middleware — including what middleware genuinely cannot do.
Part 3 · Rendering and data
The core of the unit. What makes a route dynamic, where to fetch, the four caching layers and what invalidates each, streaming, and mutations through server actions.
Part 4 · The product layer
The parts that make a real site: styling, images and fonts, metadata and social previews, more than one language, and content.
Part 5 · Production
Bundle and performance, configuration and the two runtimes, testing, deployment on and off Vercel, and a practice chapter with a checklist, a symptom lookup, a glossary and a quiz.

Companion units in the catalogue: React for the component model this builds on, and Front-end Developer for the browser mechanics underneath both. They are named rather than linked so that this folder keeps working on its own — reach them through the catalogue.

How a unit works

One folder, one contents page, one page per chapter, one assets/. Copy the folder anywhere and it still opens — no server, no build, no siblings.

What is inside a chapter

Intuition first, then the mechanism, then real configuration. Comparison tables for decisions, and interactive demos wired to the actual logic so you can break them deliberately.

Keeping this current

The sidebar and these cards are generated from one manifest in assets/unit.js. A chapter appears here when its number is added to the LIVE set.
