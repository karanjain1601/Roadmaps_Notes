CHAPTER 15

Metadata and SEO

Titles, descriptions, canonical URLs and social previews, declared as data rather than written as tags. It composes down the route tree, which is convenient and occasionally surprising — and one part of it can hold your entire response.

Part 4 The product layer·Reading time 35 minutes·Demos how metadata resolves, social previews·Prerequisites Chapters 3, 11

1Two ways to declare it

A static object when you know the values, a function when they depend on the route.

Export, do not render TypeScript
// Static — for anything known at build time
export const metadata: Metadata = {
  title: 'Pricing',
  description: 'Plans from £9 a month.'
};

// Dynamic — receives the same params as the page
export async function generateMetadata({ params }): Promise<Metadata> {
  const { slug } = await params;
  const post = await getPost(slug);      // memoised with the page's own fetch
  if (!post) return { title: 'Not found' };
  return {
    title: post.title,
    description: post.excerpt,
    alternates: { canonical: '/blog/' + post.slug },
    openGraph: { images: [post.cover] }
  };
}

// Never write <title> or <meta> by hand. Next places and
// deduplicates them, and hand-written tags bypass all of that.
// Use only one of the two per file — both is an error.

2How it composes

Values inherit down the tree, some fields replace and some do not, and the title template is its own rule.

Three files contributing to one page's head Toggle what each level declares and watch the resolved output.

Resolved <head>

inherited from a layout overridden by the page title template applied

Inheritance is per field, not per object
A page that sets only title keeps the layout's description, its robots, its openGraph.siteName. You do not restate everything.
But nested objects replace rather than merge deeply
This is the trap. A page setting openGraph: { title: 'X' } replaces the whole openGraph object from the layout — so the site name, the locale and the default image all vanish. If you set one Open Graph field, set the ones you need alongside it.
The title template applies to descendants only
title: { default: 'Northwind', template: '%s — Northwind' } in a layout formats titles set below it, not the layout's own. title: { absolute: 'X' } in a page opts out of the template entirely.
metadataBase makes relative URLs work
Set it once in the root layout. Without it, relative canonical and image paths cannot be resolved to absolute URLs, which social platforms require — and you get a build warning that is easy to ignore.

Generating the image, per route JSX
// app/blog/[slug]/opengraph-image.tsx
import { ImageResponse } from 'next/og';

export const size = { width: 1200, height: 630 };
export const contentType = 'image/png';

export default async function Image({ params }) {
  const post = await getPost(params.slug);
  return new ImageResponse(
    (
      <div style={{ display: 'flex', flexDirection: 'column', justifyContent: 'center',
                   width: '100%', height: '100%', padding: 64, background: '#0C1D30' }}>
        <div style={{ fontSize: 64, color: 'white' }}>{post.title}</div>
        <div style={{ fontSize: 28, color: '#93AABF' }}>northwind.example</div>
      </div>
    ), size
  );
}

// Only flexbox and a subset of CSS — no grid, no floats. Fonts must
// be supplied explicitly as ArrayBuffers. The file convention wires
// the og:image tags up for you; you do not add them by hand.

5File conventions

Five more special files, all producing output rather than routes.

FileProduces
icon.tsx / .pngFavicons at the sizes needed, with the link tags. apple-icon for the touch icon.
opengraph-image.tsxThe preview image and its tags, per route. twitter-image if you need a different one.
sitemap.ts/sitemap.xml from an exported function. Generate it from your data rather than maintaining a list, and split it if you exceed the per-file entry limit.
robots.ts/robots.txt, including the sitemap reference. Remember to block staging environments here.
manifest.tsThe web app manifest, for installability.

All of these can be dynamic, which is the point of the .ts variants: a sitemap generated from the database cannot go stale, and a robots file can differ per environment from an environment variable.

6Structured data

The one thing you do render as a tag, and it is safe to.

JSON-LD in a server component JSX
export default async function ProductPage({ params }) {
  const product = await getProduct((await params).id);

  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'Product',
    name: product.name,
    offers: { '@type': 'Offer', price: product.price, priceCurrency: 'GBP',
              availability: product.inStock ? 'InStock' : 'OutOfStock' }
  };

  return (
    <>
      <script type="application/ld+json"
              dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }} />
      <Product product={product} />
    </>
  );
}

// JSON.stringify escapes the content, so this is safe — but it must
// describe what is actually on the page. Structured data claiming a
// price or a rating the page does not show is a manual-action risk,
// not a clever trick.

7generateMetadata blocks everything

Chapter 11's point, repeated here because this is where it bites.

Metadata precedes the body

Titles and meta tags go in the document head, which comes before any body content — so nothing can be streamed until generateMetadata resolves. A slow lookup there holds your whole response, including a shell that was otherwise ready in fifty milliseconds. It is easy to miss because it lives in a different export from the component you were optimising.

It shares memoisation with the page
If generateMetadata and the page both call getPost(slug), the second is free within that request (Chapter 9). So fetching the same thing twice costs nothing — and fetching something different and slow costs you the whole page.
Cache the read
The metadata lookup is a good candidate for a tagged cache entry: titles change rarely, and the cost falls on every request.
Return early on the cheap path
If the slug does not resolve, return a minimal object rather than doing more work. And do not put analytics, feature flags or anything incidental in there.

8Check yourself

Five questions.

1. A page sets openGraph: { title: 'X' } and the site name disappears from previews. Why?

Because nested objects replace rather than merge deeply. Top-level fields inherit individually — a page setting only title keeps the layout's description and robots — but the moment you declare openGraph, your object replaces the layout's entire openGraph object, taking siteName, locale and the default image with it. Nothing warns you; previews simply get worse. The fix is to restate the fields you need alongside the one you are changing, or to build the object from a shared helper so the defaults are always included.

2. How does the title template work, and how do you opt out?

A layout declares title: { default: 'Northwind', template: '%s — Northwind' }. The default is used when a descendant sets no title of its own; the template formats titles that descendants do set, so a page with title: 'Pricing' resolves to "Pricing — Northwind". Two details worth knowing: the template applies only to routes below the layout, never to the layout's own title, so the home page shows the default rather than a doubled name. And a page can opt out entirely with title: { absolute: 'X' }, which is what you want for a landing page whose title should stand alone.

3. Why is canonical the highest-value field on a content or commerce site?

Because the same content is usually reachable through several URLs — tracking parameters, sort and filter combinations, trailing-slash variants, a print view, the same product under two categories — and without a canonical each of those competes with the others rather than accumulating together. Declaring one authoritative URL consolidates that. It also protects against a genuine class of accident: a filtered listing generating thousands of near-duplicate URLs. Pair it with robots on the routes that should not be indexed at all, such as search-result pages and anything paginated beyond the first page.

4. Why can a slow generateMetadata ruin a page you carefully made stream?

Because metadata goes in the document head, which precedes all body content — so nothing at all can be sent until it resolves, including a shell that was ready in fifty milliseconds and every Suspense boundary you placed carefully. It is a different export from the component you were optimising, which is why it gets missed. Two mitigations: it shares request memoisation with the page, so fetching the same record in both is free; and the metadata lookup is a good candidate for a tagged cache entry, since titles change rarely and the cost falls on every request. Return a minimal object early on the failure path rather than doing more work.

5. Why should you not write <meta> tags by hand?

Because Next owns the head: it resolves your metadata exports through the whole route tree, applies title templates, deduplicates tags, and resolves relative URLs against metadataBase. Hand-written tags bypass all of that, so you get duplicates where a layout and a page both declare something, no template applied, and relative image paths that social platforms cannot resolve. The one exception is JSON-LD structured data, which has no metadata-API equivalent and is rendered as a script tag — safely, because JSON.stringify escapes the content. And it should describe what is genuinely on the page.
