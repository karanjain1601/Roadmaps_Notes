CHAPTER 18

Performance and the bundle

Four separate costs, each with its own lever, and the common mistake is pulling the wrong one — spending a week on bundle size when the problem was a 600ms database query, or vice versa. This chapter is about telling them apart.

Part 5 Production·Reading time 40 minutes·Demos what you ship, where the time goes·Prerequisites Chapters 8–11

1Four costs, four levers

Name the cost before choosing the fix.

CostShows up asLever
Server workSlow time to first byteCaching (Chapter 10), parallel queries (Chapter 9), streaming (Chapter 11). Not bundle size.

A useful diagnostic: if the page is slow to appear, look at the first two. If it appears quickly and does not respond, look at the last two. Section 8's demo maps every lever against the metric it actually moves.

Read the build output every build
Chapter 2. The First Load JS column is what a visitor downloads before the page is interactive, and the shared figure at the bottom is what every route pays. A jump in the shared number is the most important regression this chapter is about.
Then look at the analyser
@next/bundle-analyzer gives you a treemap. The useful question is not "what is biggest" but "what is in here that I did not expect" — that is where the barrel-file imports and the accidentally-client components show up.
Enforce a budget in CI
A number that fails the build. Without one, the bundle grows by two kilobytes per pull request and nobody is ever responsible for it. This is the cheapest performance work available.

3The biggest lever is the client boundary

Everything else in this chapter is smaller than this.

One directive can double your bundle

'use client' is an entry point, and everything it imports transitively becomes client code (Chapter 19 of the React unit, Chapter 8 here). A provider added to the root layout, a hook needed in a shared component, a UI library imported at the top of a shell — each pulls a subtree into the browser. Nothing errors; the shared First Load JS figure simply rises, and it rises for every route at once.

Push the directive to the leaves
The interactive carousel, the basket button, the filter dropdown. Not the page, not the layout, not the shell.
Wrap providers, do not mark layouts
Export a small Providers client component and render it inside a server root layout. Chapter 3.
Compose with children rather than importing
A client component receiving a server component as children keeps that subtree on the server. This is the single most useful structural habit in a Next codebase.
Audit it as a number
Count the 'use client' files in your repository and look at the largest. It is a better proxy for bundle health than any lint rule.

4Barrel files and package imports

Why importing one icon can cost 180 kB, and the two ways to stop it.

The same icon, three ways TypeScript
// The package's index re-exports 1,400 modules. Tree shaking can
// often remove them — but every one is still parsed and traversed
// at build time, and anything with a side effect survives.
import { ChevronDown } from 'icon-library';

// Per-path: the bundler visits one module.
import ChevronDown from 'icon-library/dist/ChevronDown';

// Or let Next rewrite the barrel import to the per-path one:
// next.config.ts
experimental: { optimizePackageImports: ['icon-library', '@acme/ui'] }

// It is applied automatically to many well-known packages already.
// The build-time saving is often larger than the bundle saving —
// barrel imports are a common cause of slow builds and slow
// development refreshes.
Do not create your own barrels for large sets
An index.ts re-exporting your whole design system is convenient and turns every import of one button into a traversal of everything. React Chapter 23 said the same thing from the architecture side; this is the cost.
Watch for side effects
A module that runs code on import — registering something, polyfilling, injecting a stylesheet — cannot be tree-shaken away. "sideEffects": false in a package's manifest is what tells the bundler it is safe; packages lacking it cannot be shaken at all.
Prefer platform APIs where they exist
Chapter 16's Intl replaces a formatting library entirely, at zero bytes. That is the best kind of optimisation because there is nothing left to maintain.

5Lazy loading

Useful, over-applied, and occasionally harmful.

next/dynamic, and when it earns its place JSX
const Chart = dynamic(() => import('./Chart'), {
  loading: () => <ChartSkeleton />,
  ssr: false          // only when the component genuinely cannot render on the server
});

// Worth it: a heavy library used by a minority of visitors, or
// below the fold, or behind an interaction.
//   ✓ a rich text editor opened by a button
//   ✓ a charting library on a tab nobody clicks
//   ✓ a map that appears after "show on map"
//
// Not worth it, and often worse:
//   ✗ a 3 kB component — you added a request to save nothing
//   ✗ anything above the fold — you delayed the thing people
//     came to see, and introduced a layout shift
//   ✗ dozens of tiny lazy chunks — they compress badly and each
//     costs a round trip

The honest ordering: remove it, then move it to the server, then lazy-load it. Lazy loading is the last resort of the three, because the code still exists and still runs — it has only moved later, and "later" sometimes means "while the user is waiting".

6The server side

Where a Next app is usually slow, and where bundle work does not help at all.

Caching is the biggest lever by far
A static route costs nothing per visit. A revalidated one costs a render occasionally. A dynamic one costs a render and every query, every time. Moving a route from dynamic to revalidated is worth more than any amount of bundle work — Chapters 8 and 10.
Then query shape
Chapter 9's waterfall. Consecutive awaits cost the sum; Promise.all costs the maximum. And the classic database problems apply unchanged: missing indexes, N+1 queries, selecting columns you do not use.
Then streaming
It does not make anything faster, and it stops the slowest query deciding when the page appears (Chapter 11).
Cold starts
A serverless function that has not run recently pays initialisation. Keeping the bundle small helps, and so does not connecting to a database at module scope in a route that rarely runs. The edge runtime starts faster and can do less — Chapter 19.
Measure the server separately
Time to first byte is a server metric. If it is 800ms, no amount of JavaScript removal will help, and every hour spent on the bundle is an hour not spent on the actual problem.

8Check yourself

Five questions.

1. Time to first byte is 800ms. Will reducing the bundle help?

No, not at all. Time to first byte is entirely server-side: it is your render plus your queries plus any cold start, and it is over before a single byte of JavaScript has been requested. The levers for it are caching — moving the route from dynamic to revalidated or static is the largest single change available — then query shape, since consecutive awaits cost the sum rather than the maximum, then streaming so the shell is not held by the slowest query. Bundle work moves interactivity and paint on constrained devices, which are real problems, just not this one. Naming the cost before choosing the fix is the whole point of the chapter's first table.

2. What is the single biggest lever on bundle size in a Next app?

Where the client boundary sits. 'use client' is an entry point, so that module and everything it imports transitively ships — which means one directive in a shared layout can pull most of your application into the browser, and it raises the shared First Load JS figure that every route pays. Nothing errors, so it is invisible unless you read the build output. The three habits that follow: push the directive to interactive leaves, wrap providers in a small client component rather than marking a layout, and compose with children so a client component can hold a server subtree without importing it.

3. Why can importing one icon from a package cost far more than the icon?

Because the package's index re-exports everything, so the bundler has to visit and analyse every module even if it can eventually drop most of them. Two consequences: anything with a side effect at import time cannot be shaken out and stays, and the build itself gets slow — barrel imports are a common cause of sluggish builds and development refreshes, often a bigger day-to-day cost than the bytes. Fixes: import per path, or list the package in optimizePackageImports so Next rewrites the barrel import for you. And do not build your own barrel over a large design system, which recreates the problem locally.

4. When is next/dynamic the wrong tool?

When the thing is small, when it is above the fold, or when you are applying it broadly. A 3 kB component behind a dynamic import trades nothing for an extra round trip. Something above the fold gets delayed, along with a layout shift as its fallback is replaced — you have made the thing people came for arrive later. And dozens of tiny chunks compress worse than one and each costs a request. The right ordering is remove it, then move it to the server, then lazy-load it: lazy loading is the last resort of the three because the code still exists and still runs, just later — and later sometimes means while the user is waiting.

5. Why is Lighthouse on your laptop insufficient?

Because it measures your laptop. Parse and execute cost scales with device speed, so a bundle that is unremarkable on a development machine can be several times more expensive on a mid-range phone, and worse again on a cheap one — the demo's device selector shows that multiplier directly. You need field data from real users, via useReportWebVitals or your host's analytics, and you should read the 75th percentile rather than the average, since Core Web Vitals are assessed there and averages hide the users you are failing. Also remember prefetching is disabled in development, so local navigation feels slower than production and should not be tuned against.
