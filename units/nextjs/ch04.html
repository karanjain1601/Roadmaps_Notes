CHAPTER 04

Dynamic routes and route handlers

Most routes are not known in advance. Square brackets in a folder name turn a segment into a variable, and three bracket styles cover every shape of URL you are likely to need — provided you know which one wins when two of them could match.

Part 2 Routing·Reading time 35 minutes·Demos route matching, prerendering·Prerequisites Chapters 2–3

1Dynamic segments

A folder in brackets becomes a parameter, delivered to the page.

Three bracket styles Structure
app/blog/[slug]/page.tsx          // /blog/hello   → { slug: 'hello' }
app/docs/[...path]/page.tsx       // /docs/a/b     → { path: ['a','b'] }
app/shop/[[...filters]]/page.tsx  // /shop         → { filters: undefined }
                                  // /shop/red     → { filters: ['red'] }

// params is a promise in current versions — await it.
export default async function Post({ params, searchParams }) {
  const { slug } = await params;
  const { page } = await searchParams;
  const post = await getPost(slug);
  if (!post) notFound();          // renders the nearest not-found.tsx
  return <Article post={post} />;
}
Everything arrives as a string
Or an array of strings for a catch-all. A numeric id is "4182", and a URL is user input, so validate it — the same schema doing its third job (React Chapters 14 and 17).
Nested dynamic segments are fine
app/[org]/orders/[id]/page.tsx gives you both keys. Layouts on the path receive params too, though only the parts above them.
Reading searchParams makes the route dynamic
Unlike params, which is part of the path and therefore knowable at build time, search params are per-request. Touching them means the route can no longer be prerendered — Chapter 8.
notFound() is the right failure
It throws a special signal that renders the nearest not-found.tsx with a 404 status. Returning your own "not found" markup gives a 200, which tells crawlers the page exists.

3generateStaticParams

Telling the build which dynamic URLs exist, so they can be prerendered.

Prerendering a known set JSX
export async function generateStaticParams() {
  const posts = await getAllPostSlugs();
  return posts.map(p => ({ slug: p.slug }));    // keys match the folder name
}

// Default: anything NOT in that list is rendered on first request
// and then cached. Set this to make unknown params 404 instead:
export const dynamicParams = false;

// For a catch-all, return arrays:
return [{ path: ['guides', 'install'] }, { path: ['api'] }];

4Route handlers

A file that answers HTTP directly, for the cases where a page is the wrong shape.

app/api/orders/route.ts TypeScript
import { NextRequest } from 'next/server';

export async function GET(request: NextRequest) {
  const status = request.nextUrl.searchParams.get('status');
  const orders = await getOrders({ status });
  return Response.json(orders, {
    headers: { 'Cache-Control': 's-maxage=60, stale-while-revalidate=300' }
  });
}

export async function POST(request: NextRequest) {
  const parsed = orderSchema.safeParse(await request.json());
  if (!parsed.success) return Response.json({ errors: parsed.error.flatten() }, { status: 400 });
  const order = await createOrder(parsed.data);
  return Response.json(order, { status: 201 });
}

// GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
// route.ts and page.tsx cannot share a folder.
// Handlers are dynamic by default — nothing is cached unless you
// say so with headers or a route segment config.
Request and Response are the web standards
request.json(), request.formData(), request.headers, Response.json(). NextRequest adds conveniences — nextUrl, cookies — and is otherwise a Request. Knowledge here transfers to Cloudflare Workers, Deno and Bun.
Streaming works
Return a ReadableStream for server-sent events or a proxied AI response. This is one of the clearest cases where a handler beats anything else.
Dynamic segments work the same way
app/api/orders/[id]/route.ts receives { params } as a second argument, and params is a promise as it is in pages.
CORS is yours
A handler called from another origin needs the headers set explicitly, including an OPTIONS export for the preflight. Nothing is added for you.

5When a handler is the wrong tool

The most common unnecessary code in a new Next application.

You probably do not need an API route

The reflex from client-rendered React is: component needs data, so write an endpoint, then fetch it. In the App Router a server component can query the database directly, and a server action can write to it — so the endpoint is a round trip through your own server for no reason. It also loses type safety at the boundary, adds a place for the shapes to drift, and forces you to reimplement auth checks the page already did.

You want toUse
Show data on a pageQuery it in the server component. No endpoint.
Submit a form and update the pageA server action (Chapter 12).
Fetch more data after an interactionA server action returning data, or a handler if a client cache library needs a URL.
Receive a webhookA handler. Something external needs a URL and a raw body.
Serve a public APIA handler. Third parties cannot call a server action.
Stream somethingA handler returning a ReadableStream.
Proxy a third-party API to hide a keyA handler, or a server action if only your own client calls it.
Return a non-HTML fileA handler — a CSV export, an image, an ICS calendar feed.
Handle auth callbacksA handler, usually supplied by your auth library.

The pattern in every "yes": something outside your React tree needs a URL. If the only caller is your own application, you probably want a server component or an action.

6Check yourself

Five questions.

1. Why does /docs return a 404 when you have app/docs/[...path]/page.tsx?

Because a catch-all requires at least one segment to fill it. [...path] matches /docs/a and /docs/a/b/c but not the bare parent path, which has nothing for path to be. Two fixes: add app/docs/page.tsx for the index, which is usually what you want because a documentation home page rarely looks like an article; or switch to an optional catch-all, [[...path]], which matches zero or more segments and then hands you path: undefined for the parent. Note that it is undefined, not an empty array, which catches people writing path.length.

2. Both app/blog/new/page.tsx and app/blog/[slug]/page.tsx exist. What serves /blog/new?

The static one. Precedence runs most specific first: a fully literal path, then a dynamic segment, then a catch-all, then an optional catch-all — so new/ wins and [slug] never sees it. This is usually convenient, and it is worth knowing because it means a slug that collides with a real folder name becomes unreachable through the dynamic route. If a post were genuinely slugged new, it would serve the editor instead. The related rule: two patterns that resolve to the same route are a build error rather than a silent precedence decision.

3. What does generateStaticParams do, and what happens to a URL it does not return?

It tells the build which values of a dynamic segment exist, so those URLs are prerendered at build time and served as static files. By default anything not in the list still works: it is rendered on the first request and then cached, so a post published after the build appears without a rebuild. Setting export const dynamicParams = false changes that to a 404, which is right when the set is genuinely closed — a fixed list of countries, say — and wrong for a blog. The demo shows the third case too: with no generateStaticParams at all, nothing is prerendered and every URL renders on demand, which is fine but gives up the free CDN delivery.

4. Why does reading searchParams change how a page is rendered, when params does not?

Because params comes from the path, and the set of paths can be known at build time — that is exactly what generateStaticParams enumerates. Search params cannot be enumerated: ?page=2&sort=price is unbounded and arrives with the request, so a page that reads them cannot have been rendered in advance and Next marks the route dynamic. The practical consequence is that one component reading searchParams tips the whole route from a static file to per-request rendering, and the build output is where you notice. Chapter 8 covers how to contain that rather than let it spread.

5. When do you actually need a route handler?

When something outside your React tree needs a URL. Webhooks, a public API for third parties, streaming responses, proxying a third-party service to keep a key server-side, non-HTML files such as a CSV export or a calendar feed, and auth callbacks. What you do not need one for is your own application fetching its own data: a server component can query the database directly and a server action can write to it, so an endpoint in between is a round trip through your own server that loses type safety, duplicates auth checks and adds a place for shapes to drift. Writing an API layer out of habit is the most common unnecessary code in a new Next project.
