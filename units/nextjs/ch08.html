CHAPTER 08

Static, dynamic and the boundary

Every route is produced either once at build time or freshly on each request, and you do not choose directly — you choose by what your code reads. One line in one component decides it for the whole route, which is why pages people expected to be free turn out not to be.

And a third, newer one that mixes them.

Neither is better. What matters is that a route is dynamic on purpose rather than by accident — and accidents are the normal case, because the trigger is a single function call somewhere in the tree.

3It spreads upward, not sideways

The propagation rule, and the trap that follows from it.

Anything in the tree tips the whole route

A dynamic API called in a deeply nested component makes the route dynamic, not just that component. There is no partial answer in the classic model: the route either has a prebuilt output or it does not, and it cannot have one if any part of it needs the request.

The trap that follows: reading cookies() in the root layout makes every route in your application dynamic. Nothing is prerendered any more, your CDN stops helping, and the only visible sign is that every line in the build output has changed symbol. Auth helpers are the usual culprit, because putting one in the root layout looks like good centralisation.

Siblings are unaffected
/orders being dynamic says nothing about /pricing. It is per route, and the route includes every layout above it.
Which is why layout placement matters so much
A dynamic API in a route group's layout affects that group. In the root layout it affects everything. Push it as far down as it will go.
Suspense changes the picture
With partial prerendering, a dynamic API inside a Suspense boundary no longer tips the whole route — the shell is prerendered and that boundary becomes a hole filled per request. Sections 5 and 6.

4Saying it explicitly

Route segment configuration, for when you want to decide rather than discover.

Exports that configure a page, layout or handler TypeScript
export const dynamic = 'auto';
// 'auto'           default — static unless something tips it
// 'force-static'   prerender regardless; dynamic APIs return empty
//                  values rather than throwing. Read that twice:
//                  cookies() gives you nothing, silently.
// 'force-dynamic'  never prerender
// 'error'          prerender, and FAIL the build if anything tips it
//                  — the useful one, because it turns an accident
//                  into a build error

export const revalidate = 3600;   // seconds; false = never, 0 = always fresh
export const dynamicParams = true; // Chapter 4
export const runtime = 'nodejs';   // or 'edge'; Chapter 19
export const fetchCache = 'auto';  // override the default fetch caching

// Config on a LAYOUT applies to everything below it, which is the
// same propagation problem as section 3 — with the same fix.
dynamic = 'error' is underused
It says "this route must stay static, and I want to know at build time if that stops being true". On a marketing or documentation route that is exactly the guarantee you want, and it converts the silent regression in section 3 into a failed build.
force-static is sharper than it looks
It does not error on a dynamic API — it makes the call return an empty value. So a page reading a session cookie prerenders happily and renders as though nobody is signed in, which is a much worse outcome than a build failure.

5Partial prerendering

The feature that dissolves the all-or-nothing choice this chapter is otherwise about.

The classic model forces one decision per route, and real pages are mixed: a product page is identical for everyone except the basket count and a "recently viewed" strip. Partial prerendering renders the static shell at build time and leaves each Suspense boundary containing a dynamic API as a hole, streamed in per request.

What the user gets
The shell arrives from the CDN immediately — header, layout, product details — with skeletons where the personalised parts go, and those stream in behind it. Static first paint and personalised content, rather than choosing.
What you have to do
Wrap each dynamic region in <Suspense> with a sensible fallback. That is genuinely the whole API — the boundary is the declaration of where a hole goes.
What it does not fix
A dynamic API called outside any boundary still tips the whole route, because there is no hole to put it in. And the work is not reduced — the personalised query still runs on every request, it just no longer delays the shell.
Check your version
This has moved through experimental flags and configuration names. Verify the behaviour on the version you are on rather than trusting a blog post — which is the standing advice for anything in this part of the unit.

Push the dynamic API down, then wrap it
Move cookies() out of the page and into the smallest component that needs it, then put a Suspense boundary around that component. The route keeps its static shell and gains one hole.
A client component is a legitimate third option
Fetching the personalised bit after hydration keeps the whole route static with no holes at all. The cost is that it appears later and needs its own loading state — fine for a basket count, wrong for anything above the fold that matters.
Some personalisation is not worth a dynamic route
A greeting, a basket badge, a "you viewed this" strip. Ask whether it needs to be in the first byte at all. Often the honest answer is no, and the page becomes free.

7Reading the build output properly

Two minutes per build, and it catches the regression in section 3 the day it happens.

Read the symbol column, not the sizes
A route that was ○ last week and is ƒ now is the signal. Sizes creep slowly; this changes in one commit.
Ask why, not whether
Next will tell you which dynamic API tipped a route if you look — the build log names the call and the file. That is usually enough to find the auth helper somebody added to a shared component.
Assert it in CI
dynamic = 'error' on the routes that must stay static turns this from a habit into a guarantee. If your marketing pages are a business concern, this is the cheapest protection available.
Compare against the previous build
Storing the output and diffing it in CI makes an accidental change visible in the pull request rather than a month later when someone notices the bill.

8Check yourself

Five questions.

1. Name four things that make a route dynamic.

Reading cookies() or headers(); reading searchParams; a fetch marked cache: 'no-store'; and export const dynamic = 'force-dynamic'. Also connection() and draftMode(), a middleware rewrite targeting the route, and awaiting an uncached data source such as a bare database query. The list is closed, which is useful — nothing else does it — and any single item is enough. Note the one that is not on it: params, because the set of paths can be enumerated at build time, which is exactly what generateStaticParams does.

2. Why is cookies() in the root layout so damaging?

Because the effect propagates upward through the route, and the root layout is part of every route — so one call there makes the entire application dynamic. Nothing is prerendered, the CDN stops serving anything, every visit pays a render, and your marketing pages are now as expensive as your dashboard. The only visible sign is that every line in the build output changed symbol, which is easy to scroll past. It happens because centralising an auth helper in the root layout looks like good practice. The fix is to push the call down to the smallest component that needs it and wrap that in a Suspense boundary.

3. What does partial prerendering change about the choice in this chapter?

It stops the choice being per route. Classically a route either had a prebuilt output or it did not, so one personalised element forced the whole page to be rendered per request. With partial prerendering the static shell is built ahead of time and each Suspense boundary containing a dynamic API becomes a hole streamed in per request — so the user gets a CDN-fast first paint and personalised content. The API is just the boundary. Two limits: a dynamic API outside any boundary still tips the whole route, because there is nowhere to put the hole; and the work is not reduced, only moved off the critical path.

4. Why is force-static risky?

Because it does not object to dynamic APIs — it makes them return empty values. A page reading a session cookie under force-static prerenders without complaint and renders as though nobody is signed in, so the failure is silent and shipped rather than loud and caught. That is strictly worse than a build error. Use dynamic = 'error' instead when you want a route to stay static: it prerenders and fails the build if anything tips it, converting the accidental regression into something the pull request tells you about. Reserve force-static for cases where you have verified nothing in the tree reads the request.

5. A product page needs a basket count in the header. What are your options?

Three, in rough order of preference. Wrap it in Suspense so the count becomes a partial-prerendering hole: the whole page ships from the CDN and the badge streams in. Make it a client component that fetches after hydration, which keeps the route entirely static at the cost of the number appearing a little later — usually fine for a badge. Or accept a dynamic route, which is the honest choice if the page is genuinely personalised throughout. What you should not do is read the cookie at the top of the page or in a shared layout, which converts a free page into a per-request render for the sake of one number.
