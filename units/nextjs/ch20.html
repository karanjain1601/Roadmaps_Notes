CHAPTER 20

Testing a Next application

Server components sit awkwardly with the usual component-testing tools, which turns out to matter less than it sounds — because the answer is to stop putting logic in components. What is left is a clear division of labour between four levels and a build-time check.

Part 5 Production·Reading time 35 minutes·Demos which level catches what, what a suite costs·Prerequisites Chapters 9, 12

1What is actually different

One awkward fact, and why it costs less than people expect.

An async server component is not renderable by a component test
Testing Library renders in a DOM environment with the client React runtime; an async component that awaits a database does not fit that model. Support has improved and remains partial — check the current state for your versions rather than trusting a blog post.
But there should be very little in there worth testing
A server component that awaits a query and maps it to markup has almost no behaviour. The interesting parts — the query, the authorisation, the formatting, the derived state — belong in functions you can test directly. That is section 2, and it is the whole answer to this chapter's premise.
The client boundary is now also a testing boundary
Client components are ordinary React and test exactly as they always did (React Chapter 22). Server actions are ordinary async functions. Route handlers are request-to-response functions. Three of the four levels are unremarkable.
Some bugs are not test-shaped at all
A 'use client' in the wrong place, a wrong sizes prop, a route that quietly went dynamic. Section 3's demo has a column for these, because pretending a unit test will catch them is how they ship.

2Get the logic out of the component

The highest-value habit in the chapter, and it is not really about testing.

Before and after TypeScript
// ✗ Everything in the component. Nothing here is testable without
//   rendering an async server component against a real database.
export default async function OrdersPage({ searchParams }) {
  const sp = await searchParams;
  const status = sp.status ?? 'open';
  const page = Math.max(1, parseInt(sp.page ?? '1', 10) || 1);
  const rows = await db.order.findMany({ where: { status }, skip: (page - 1) * 20 });
  const total = rows.reduce((a, r) => a + r.total, 0);
  return <table>…</table>;
}

// ✓ Three plain functions and a component that only arranges markup.
export function parseOrderQuery(sp: Record<string, string>) { … }   // pure
export function summarise(rows: Order[]) { … }                   // pure
export const getOrders = cache(async (q: OrderQuery) => { … });     // one seam

export default async function OrdersPage({ searchParams }) {
  const q = parseOrderQuery(await searchParams);
  const rows = await getOrders(q);
  return <OrdersTable rows={rows} summary={summarise(rows)} />;
}
Pure functions are where the bugs live
Query parsing, pagination arithmetic, permission predicates, currency rounding, date bucketing, tag construction. Every one is a plain function with obvious edge cases and a two-line test.
One seam per data source
All reads through a small module means one place to stub. Scattering db. calls through components means there is nowhere to stand.
This is good design regardless
The same extraction makes the code readable, reusable between a page and an action, and cheap to change. Testability is the symptom, not the goal.

4Testing server actions

They are async functions, so this is the cheapest high-value testing in a Next codebase.

Testing the guards from Chapter 12 TypeScript

vi.mock('next/cache');        // so revalidateTag is observable

test('rejects an unauthenticated caller', async () => {
  vi.mocked(auth).mockResolvedValue(null);
  const r = await updateOrder(fd({ id: '1', status: 'shipped' }));
  expect(r.error).toBeDefined();
});

test('refuses another organisation’s order', async () => {
  vi.mocked(auth).mockResolvedValue(sessionFor({ orgId: 'org-a' }));
  const r = await updateOrder(fd({ id: orderIn('org-b'), status: 'shipped' }));
  expect(r.error).toBe('Not found');      // not "forbidden"
});

test('invalidates BOTH tags after a write', async () => {
  await updateOrder(validFormData);
  expect(revalidateTag).toHaveBeenCalledWith('orders:4182');
  expect(revalidateTag).toHaveBeenCalledWith('orders');   // Chapter 10
});

// That last test is the one nobody writes and it catches the most
// common cache bug in the unit: an invalidation that half-works.
Test the refusals, not the happy path
The happy path is exercised by every end-to-end test you have. The five guards from Chapter 12 are exercised by nothing unless you write these.
Assert the invalidation
Mocking next/cache and asserting which tags were cleared turns Chapter 10's silent half-failure into a red test.
Redirects throw
Which means you can assert them — and a test that fails because a catch swallowed the redirect is exactly the Chapter 12 trap, caught.

5What only end-to-end can reach

A short, specific list — which is also the argument for keeping it short.

Hydration mismatches
They require real server HTML being hydrated by the real client runtime. Nothing below this level sees them. Fail the test on a console error and you have a genuine safety net.
Navigation, prefetching and cache behaviour
Chapters 5 and 10. Whether an edit is visible after a client-side navigation is a question about four caches interacting, and only a real browser answers it.
Streaming and boundary placement
That the shell appears before the slow section, and that a failing region does not remove the rest (Chapter 11).
The document head
Chapter 15's metadata resolution — including the nested-object replacement that silently drops your Open Graph image.
Progressive enhancement
Run one test with JavaScript disabled and assert the form still submits. That is the only way to verify Chapter 12's claim holds in your application.
Accessibility in the composed page
An axe scan on the assembled route catches contrast, landmark and labelling problems that component tests miss because they render one piece.
Two practical Playwright habits TypeScript
// 1. Sign in once, reuse the state — turns a 40-test suite from
//    minutes into seconds.

// playwright.config.ts

// 2. Fail on console errors — the hydration net
test.beforeEach(async ({ page }) => {
  page.on('console', (m) => {
    if (m.type() === 'error') throw new Error('console: ' + m.text());
  });
});

7What not to test

Four things that generate maintenance and no confidence.

The framework
That Link navigates, that generateStaticParams produces routes, that revalidateTag clears a cache. Test your usage, not their implementation.
A server component's markup structure
Asserting which element wraps which is a snapshot of a design decision, and it fails on every legitimate change. Assert what a user can find and do.
Implementation details of your own components
React Chapter 22's argument, unchanged: query by role and label, not by test id or internal state.
Every route end to end
The cost demo above is the argument. Cover the critical journeys and the things only that level can reach; use cheaper levels for the rest.

8Check yourself

Five questions.

1. Server components are awkward to unit test. Why does that matter less than it sounds?

Because a well-structured server component has almost no behaviour to test — it awaits a query and arranges markup. The parts worth testing are the parts that should not be inside it: query parsing, pagination arithmetic, permission predicates, currency rounding, tag construction. Extracting those into plain functions gives you cheap, thorough tests and better code at the same time, so testability is the symptom rather than the goal. One further seam helps: routing all data access through a small module means there is exactly one place to stub, whereas scattered db. calls in components leave nowhere to stand.

2. Which bugs can only an end-to-end test catch?

Hydration mismatches, because they need real server HTML being hydrated by the real client runtime. Cache and navigation behaviour, because whether an edit is visible after a client-side navigation is a question about four caches interacting. Streaming order and partial failure. The composed document head, including Chapter 15's silently-dropped Open Graph image. Progressive enhancement, which needs one test run with JavaScript disabled. And accessibility of the assembled page, since component tests only see one piece. That list is short deliberately — it is both the argument for having end-to-end tests and the argument for not having many.

3. What is the most valuable server action test, and why does nobody write it?

Asserting the invalidation: mock next/cache and check that the write cleared both the specific tag and the broad one. Nobody writes it because the mutation appears to work — the record changes, the page the developer is looking at refreshes — and the failure is that some other view stays stale for everyone else. That is Chapter 10's half-working invalidation, and it is exactly the kind of thing a test turns from an eventual support ticket into a red line in CI. The related habit: test the refusals rather than the happy path, since the happy path is covered by every end-to-end test and the five guards from Chapter 12 are covered by nothing.

4. Why must the end-to-end suite run against a production build?

Because the development server behaves differently in ways the tests are supposed to be checking. Prefetching is disabled in development (Chapter 5), so navigation timing and cache-hit behaviour differ. Caching behaves differently across the board (Chapter 10), so a test asserting that content is fresh or stale may pass locally and fail in production or the reverse. Static and dynamic rendering decisions are only real after a build (Chapter 8). A suite run against the dev server is testing an artefact you never deploy, which is worse than a smaller suite testing the real one.

5. Which bugs are not test-shaped at all?

The ones that are about the shape of the build rather than the behaviour of the code. A 'use client' added to a shared layout produces correct output and a much larger bundle for every route. A route that quietly went dynamic renders identically and costs a render per visit. A wrong sizes prop downloads an oversized image and displays it perfectly. None of those fail an assertion, because nothing is wrong with the result. They are caught by build-output assertions in CI: a bundle budget, dynamic = 'error' on routes that must stay static, and a diff of the build output against the previous run.
