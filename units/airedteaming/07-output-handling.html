Insecure output handling

The cheapest high-severity findings in this unit are here, because the vulnerabilities are thirty years old and the developers treating model output as trusted are not making a subtle mistake. They are making an understandable one about provenance.

Model output is a laundering path for user input

The mistake is understandable and worth naming precisely. A developer reasons: this text came from our model, running on our infrastructure, so it is our content. But the model is a function of its context, and its context contains the user's message and whatever was retrieved — so an attacker's string can enter as a question and leave as your application's markup, having passed through a component that the developer thinks of as a source rather than a transformation. The framing that fixes every row in that table is one sentence: model output is untrusted input to whatever consumes it. Encode it, parameterise it, validate it, never execute it. This is not a new class of vulnerability and it does not need new controls — it needs the existing controls applied at a boundary nobody drew.

The rendering case, in detail

markdown is not a safe subset
Most AI applications render responses as markdown, because models produce
markdown well and it looks better than plain text. Markdown feels safe. It
is not, and there are four separate issues.

  1. RAW HTML PASSTHROUGH. Many markdown renderers permit embedded HTML by
     default, or permit it unless explicitly configured otherwise. If yours
     does, you are rendering model output as HTML and every ordinary XSS
     concern applies unchanged.
       -> configure the renderer to strip HTML, then sanitise the result
          anyway with a maintained library. Do not write your own.

  2. IMAGE TAGS ARE AN EXFILTRATION CHANNEL, and this is the one people
     miss. A markdown image reference causes the BROWSER TO FETCH A URL
     when the response renders. No click required, no script required.
     If the model can be induced to include an image whose URL contains
     data from the conversation, that data has left your system — appearing
     in the attacker's server logs.
       -> this defeats "we stripped all script tags" entirely
       -> a content security policy restricting img-src to your own origin
          is the control, and it is a one-line header

  3. LINKS. Similar, with a click required, and correspondingly less
     severe — but a plausible link with data in its query string is a
     realistic phishing and exfiltration path, especially where the link
     text is chosen by the model to look legitimate.
       -> restrict schemes to http and https, strip javascript: and data:,
          and consider showing the true destination

  4. STREAMED PARTIAL OUTPUT. If you render tokens as they arrive, you may
     be rendering a partial document — and an output-side classifier that
     inspects the complete response has not run yet. A control that
     evaluates the finished text does nothing for content already painted
     on screen.
       -> buffer before rendering, or accept that output moderation does
          not apply to a streaming interface and say so in the design

THE COMPOSITE FINDING that combines this chapter with chapter 5: content
writable by an attacker reaches the model's context, the model's response
renders unencoded in a different user's browser, and the response can
include an image reference. That is stored cross-site scripting with
data exfiltration, reached without the attacker touching the victim's
session, and every component behaved as designed.

Structured output is not validation

the gap between "it is JSON" and "it is safe to act on"
# A common pattern: the model returns JSON, the application acts on it.
resp = model.generate(prompt, response_format={"type": "json_object"})
action = json.loads(resp)
execute(action["operation"], action["target"], action["amount"])   # <- no

# JSON MODE GUARANTEES SYNTAX, NOT SEMANTICS. You get well-formed JSON;
# you do not get values within an allowed set, an operation you support,
# a target this user may touch, or an amount within a limit.
#
# So the parse succeeded and nothing was validated.

# WHAT ACTUALLY VALIDATES — a schema with enumerated values and bounds,
# then an authorisation check that does not consult the model:
from pydantic import BaseModel, Field
from typing import Literal

class Action(BaseModel):
    operation: Literal["refund", "annotate", "escalate"]     # enumerate
    target_id: str = Field(pattern=r"^ord_[0-9a-f]{12}$")    # constrain
    amount:    int = Field(ge=0, le=50_000)                  # bound
    reason:    str = Field(max_length=200)                   # cap

action = Action.model_validate_json(resp)          # raises on anything else

# AND THEN — the part that is not about the schema at all:
require_permission(user, action.operation, action.target_id)   # not the model
if action.operation == "refund" and action.amount > 5_000:
    require_human_confirmation(action)

# THREE PRINCIPLES:
#
#   ENUMERATE, DO NOT VALIDATE. A Literal of three operations is a
#   different kind of control from a regex checking for dangerous strings.
#   The first cannot be bypassed by an operation you did not think of.
#
#   NO FREE-TEXT FIELD MAY REACH AN INTERPRETER. `reason` is capped and
#   goes to a log and a UI, both of which encode it. It never reaches a
#   query, a template, or another model's instruction channel — that last
#   one being the case that reopens chapter 5's dual-model pattern.
#
#   AUTHORISATION IS EVALUATED AGAINST THE USER, ALWAYS. The model
#   proposed an action; the application decides whether this user may take
#   it. If that check reads anything the model produced other than the
#   enumerated operation and the id, it is not an authorisation check.
Generated code that anything executes is remote code execution

Products that write and run code — data analysis, chart generation, notebook assistants — have made the model's output reachable by an interpreter, and the model's output is a function of untrusted input. Treat it accordingly: the sandbox is the entire control, and the question is what the code can reach. No network egress, no credentials in the environment, no writable mount that outlives the call, hard CPU and memory limits, and — specifically — no access to cloud instance metadata, which is the standard route from code execution to cloud credentials and is blocked by a single network rule. A container running with the application's own service account is not a sandbox; it is the application with extra steps. And review what the interpreter has installed: a Python environment with the cloud SDK and a mounted config directory hands over the account.

Find these by grepping, not by prompting

This is the one chapter where the fastest route to findings is reading code rather than testing the model. Search for the sinks and check what reaches them: innerHTML, dangerouslySetInnerHTML, v-html, template rendering with autoescape disabled, string-formatted SQL, subprocess with shell=True, eval and exec, os.system, requests.get with a variable URL, file operations with a variable path. Then trace backwards: does any of those receive a value that came, however indirectly, from a model response? An afternoon of that on a moderately sized AI application typically produces two or three real findings, all of them mechanically fixable and none of them dependent on a jailbreak working — which also makes them the findings that survive a model update.

The short version

  1. Model output is untrusted input to whatever consumes it, because it is a transformation of user input and retrieved content.
  2. Markdown is not a safe subset. Renderers often pass raw HTML, and image references fetch URLs with no click.
  3. Image tags are an exfiltration channel that defeats "we stripped all script tags". A CSP img-src rule is the control.
  4. Streaming defeats output moderation. A classifier on the finished text does nothing for pixels already painted.
  5. JSON mode guarantees syntax, not semantics. Enumerate allowed values; do not validate against a blocklist.
  6. Authorise against the user, never against the model's output. The model proposes; the application decides.
  7. Generated code that runs is RCE. The sandbox is the control — no egress, no credentials, no instance metadata.
  8. Grep for the sinks. An afternoon of code reading beats a week of prompting, and the findings survive model updates.
