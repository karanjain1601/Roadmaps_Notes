Testing methodology

The hardest question in an AI engagement is not how to attack the system. It is how to decide you have finished, given that the input space is unbounded and a failed attempt proves nothing.

Ask for grey box, and take white box if offered

Black-box testing of an AI system is a poor use of an engagement. The realistic attacker frequently has grey-box capability for free — the model family is discoverable from responses, the system prompt is usually extractable, and transferability means an open-weights proxy substitutes for gradients (chapter 8) — so testing blind simulates an adversary weaker than the real one while spending your budget on reconnaissance. More importantly, the highest-severity findings in this unit come from reading an architecture, not from probing an interface: tool permissions, whose credentials a tool uses, whether retrieval filters by entitlement, what the load path executes. None of those is efficiently discoverable from outside, and all are answerable in an hour with the engineers. Reserve black-box work for validating that a specific control holds from where an attacker actually stands.

The productive relationship is sequential rather than either-or: manual work discovers a mechanism, automation measures its rate and turns it into a regression test (chapter 16). An engagement that produces only manual findings leaves nothing that runs next month. One that produces only automated results has tested the attacks somebody already published, which is a floor and not coverage (chapter 6).

the order that produces the most per day
DAY 1 — ARCHITECTURE, WITH THE ENGINEERS. Not testing. Produce:
  * the tool table: what each does, whose credential, what it can reach,
    reversible, can it send data out, whose permissions are checked (13)
  * the content sources table: every input reaching the context, with who
    can write to it (chapter 5)
  * the output sinks list: everything that consumes model output (7)
  Those three artefacts determine what the rest of the engagement is for,
  and they frequently contain the headline finding before any testing.

DAY 2 — THE MECHANICAL CONTROLS. Yes-or-no questions with durable answers:
  retrieval entitlement filtering, tool authorisation against the actor,
  output encoding at each sink, untrusted content escaped at assembly,
  cache keys, rate limits, spend cap, artefact load path. Grep, read, ask.

THEN — REACHABILITY. Plant benign unique markers in each candidate source
  and check which reach the context. This is the half most teams have never
  tested and where the surprises are (chapter 5).

THEN — INFLUENCE AND CONSEQUENCE. Demonstrate control using benign but
  observable effects. Measure rates over 20+ trials. Trace each to a
  consequence from the day-one artefacts.

THEN — SAFETY COVERAGE, if in scope. The matrix from chapter 6: policy
  category × mechanism family × context position, with a rate per cell.

LAST — NOVEL EXPLORATION. Genuinely open-ended probing. Valuable, and it
  goes last because it is unbounded and the earlier steps have known ends.

WHAT THIS ORDERING BUYS: if the engagement is cut short — and it will be —
you have lost the least valuable part. Reverse the order and a shortened
engagement delivers anecdotes.
One success is a finding; twenty failures are not a clearance

This asymmetry has to be built into how results are recorded, or the report will overclaim. A technique that worked once out of thirty attempts is a real finding — it demonstrates the control does not hold, and an attacker gets thirty attempts for free. A technique that failed thirty times establishes that that technique failed thirty times, at that model version, in that configuration. So every result needs a trial count, and a negative result needs its confidence interval stated: zero successes in twenty trials is consistent with a true rate as high as roughly 14%, which is not a clearance and reads like one when written as "did not succeed". The practical consequence for scoping is that negative results are expensive — establishing that something reliably does not happen takes far more trials than demonstrating that it can (chapter 16).

When to stop

four defensible stopping conditions
You cannot cover the input space, so "we tested everything" is never
available. These are the conditions that produce a defensible report.

1. THE ARTEFACTS ARE COMPLETE. Every tool, content source and output sink
   is enumerated, and each mechanical control has a yes-or-no answer with
   evidence. This is a finite task and it is the deliverable that survives.

2. EVERY IDENTIFIED PATH IS RESOLVED. For each attacker-controlled input
   with a route to a consequence: either demonstrated with a rate, or
   shown blocked by a named mechanical control. No path left "probably
   fine".

3. THE COVERAGE MATRIX IS POPULATED. Each cell of policy category ×
   mechanism family × context position has a rate and a trial count, or an
   explicit note saying why it was not tested.

4. NEW EFFORT STOPS PRODUCING NEW MECHANISMS. Not new instances — new
   MECHANISMS. Three days of work yielding only variants of what you
   already found is diminishing returns, and worth saying so in the
   report rather than padding.

WHAT THE REPORT THEN CLAIMS, and it is narrower than clients expect:
  * these paths exist, at these rates
  * these controls hold, verified this way
  * these areas were not covered, for these reasons
  * this is the residual risk

NOT "the system is secure", and not "we found no issues in area X" unless
you can state the trial count and the interval behind that sentence
(chapter 17).

AND SAY WHAT WOULD CHANGE THE ANSWER: a model version update, a new tool,
a change to who can write to a content source. Each of those invalidates
part of the assessment, and naming them converts a point-in-time report
into something the team can reason about later.
Keep a lab log with exact conditions

Probabilistic findings are unreproducible without their configuration, and "it worked when I tried it" is the least useful sentence in a report. Log, for every attempt: the model identifier and version, temperature and sampling settings, the full assembled context if you can obtain it, the timestamp, the trial number, and the outcome under an explicit criterion decided in advance. Two things follow from this that are hard to get any other way. A finding becomes re-verifiable by the client after a fix, which is the difference between a report they can act on and one they argue with. And the log is the seed corpus for the regression harness — the difference between an engagement that ends and one that leaves a suite behind (chapter 16). A spreadsheet is adequate; the discipline is what matters.

The short version

  1. Ask for grey box at minimum. The realistic attacker has it for free, and blind testing wastes budget on reconnaissance.
  2. The best findings come from reading an architecture, not probing an interface. Spend day one with the engineers.
  3. Produce three artefacts first: the tool table, the content-source table, the output-sink list.
  4. Order the work so a shortened engagement loses the least. Novel exploration goes last, not first.
  5. Manual finds mechanisms; automation measures rates and becomes the regression suite.
  6. One success is a finding. Twenty failures is not a clearance — zero in twenty allows a true rate near 14%.
  7. Negative results are expensive. Proving something reliably does not happen takes far more trials.
  8. Name what would invalidate the assessment: a model update, a new tool, a change to a write path.
