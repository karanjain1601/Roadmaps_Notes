Threat modelling an AI system

Ordinary threat modelling works here, with one adjustment that changes most of the answers: a component in the middle of your architecture will follow instructions from anything that reaches its context, so the usual assumption that data flows are inert does not hold.

The question that reorders every AI threat model

Conventional threat modelling asks, at each boundary, what data crosses and could it be malformed? For a system containing a language model there is a second question that matters more: could the content crossing this boundary be interpreted as an instruction, and if it were followed, what could the model then do? Those two halves are separate. The first is about the injection reaching the model, which is usually easy and often unavoidable. The second is about consequences, and it is where the design work is — because it is determined entirely by what capability the model has been given, not by anything about the model itself. A model that can only return text has a bounded worst case regardless of what it is told. A model holding a database credential does not.

STRIDE, applied to the model as a component
SPOOFING
  * an injected instruction impersonating the operator ("system override")
  * a poisoned retrieval document presenting itself as authoritative
  * an agent's tool calls indistinguishable from a legitimate user's
  -> the model cannot authenticate the origin of anything in its context

TAMPERING
  * poisoning training data or a fine-tuning set (chapter 9)
  * poisoning the knowledge base, which is far cheaper than the above
  * a backdoored model from a public hub (chapter 12)
  -> integrity of inputs is the weakest link, and write paths are the audit

REPUDIATION
  * probabilistic behaviour makes "the model did X" hard to establish
  * without logging the exact prompt, retrieved context and tool calls,
    an incident is unreconstructible
  -> log the assembled context, not just the user message (chapter 17)

INFORMATION DISCLOSURE
  * system prompt extraction; training data memorisation (chapter 10)
  * retrieval returning documents the user is not entitled to
  * cross-tenant leakage through shared caches or history
  * the model summarising data it was given but should not reveal
  -> retrieval must apply the USER's permissions, not the service's

DENIAL OF SERVICE
  * resource-exhausting inputs; long-context amplification
  * agent loops that consume budget until a limit is hit
  * DENIAL OF WALLET, which is the version that actually happens
  -> metered inference makes availability a cost problem (chapter 14)

ELEVATION OF PRIVILEGE
  * the confused deputy: untrusted content directing a privileged tool
  * the model reasoning its way around an application-layer check
  -> the only reliable control is that the model HAS no privilege to
     elevate. Authorise the user at the tool, not at the prompt.

The final line of each block is the one to keep. In every category the
useful control is at the boundary around the model rather than inside it.

MITRE ATLAS

the ATT&CK equivalent for AI, and how to use it
ATLAS — Adversarial Threat Landscape for AI Systems — is MITRE's
knowledge base of adversary tactics and techniques against ML systems,
structured like ATT&CK: tactics as columns, techniques as cells, with
real-world case studies attached.

THE TACTICS, roughly in kill-chain order:

  RECONNAISSANCE            find out what model, what version, what
                            framework. Model responses leak this readily
  RESOURCE DEVELOPMENT      obtain the model, build a proxy, prepare a
                            poisoned dataset or a backdoored artefact
  INITIAL ACCESS            reach the model — the app, the API, a
                            supply-chain artefact, a poisoned document
  ML MODEL ACCESS           query access, weights access, or access to the
                            training pipeline. These are very different
  EXECUTION                 code execution via deserialisation, via a tool,
                            via generated code that something runs
  PERSISTENCE               a backdoor in weights, in the knowledge base,
                            or in the agent's stored memory
  PRIVILEGE ESCALATION      the confused deputy, tool chaining
  DEFENCE EVASION           evading a moderation or detection model
  CREDENTIAL ACCESS         extracting secrets from context or from tools
  DISCOVERY                 mapping the system through its own responses
  COLLECTION                extraction, inversion, membership inference
  EXFILTRATION              output channels, tool side effects, encoding
                            data into innocuous-looking responses
  IMPACT                    integrity loss, availability loss, cost, harm

HOW TO ACTUALLY USE IT — the same way ATT&CK is used, as a coverage
checklist rather than a curriculum:

  1. list the techniques applicable to your architecture. Many are not:
     if you consume a hosted API you have no weights to steal and no
     training pipeline to poison, and half the matrix is out of scope
  2. for each applicable one, name the control and whether it is tested
  3. the gaps are your engagement scope (chapter 15) and your harness
     backlog (chapter 16)

TWO OTHER FRAMEWORKS WORTH KNOWING, and they answer different questions:
  OWASP TOP 10 FOR LLM APPLICATIONS  — application-developer facing, and
    the right list to hand an engineering team. Prompt injection, insecure
    output handling, supply chain, excessive agency and the rest
  NIST AI RMF  — organisational governance: govern, map, measure, manage.
    Not a technical control set; the right artefact for a risk function
    and for the AI Act mapping (chapter 18)
Model your data flows by trust, not by component

The diagram people draw has boxes for the app, the model, the vector store and the tools, with arrows between them — and it hides the thing that matters, because two arrows into the same box can carry entirely different trust levels. Redraw it with the prompt context as the centre and label every inbound arrow with who controls that content: the operator writes the system prompt, the user writes their message, an unknown third party wrote the retrieved document, an external service produced the tool result, and a past version of any of them produced the conversation history. Once the diagram is drawn that way, the questions answer themselves: which of these can an attacker influence, and what is downstream of the context. Most AI threat models fail at the diagram stage rather than the analysis stage.

The three questions that get you most of the way

Before any tooling or framework, ask these of any AI system and write the answers down. One: what can the model cause to happen? Enumerate every tool, every write path, every downstream consumer of its output — this bounds the worst case and it is the single most informative artefact in the model. Two: whose content reaches its context? Every source, with who controls it, including sources that feel internal like a wiki anyone can edit. Three: whose permissions apply when it acts? If the answer is "the service's" rather than "the requesting user's", you have found the confused deputy before writing a single test. Those three answers determine which of the following chapters matter to you and in what order, and they usually take an afternoon with the engineers who built the thing.

The short version

  1. Ask not just whether data could be malformed but whether it could be read as an instruction, and what would follow.
  2. Consequence is determined by capability, not by the model. A model that only returns text has a bounded worst case.
  3. The system prompt is not a secret. Assume it is public and design so that it does not matter.
  4. Tool credentials are the highest-severity asset in most agentic systems.
  5. Retrieval must apply the user's permissions, not the service's, or the vector store becomes a bypass.
  6. Log the assembled context, not just the user message, or incidents are unreconstructible.
  7. Use ATLAS as a coverage checklist. Half the matrix is out of scope if you consume a hosted API.
  8. Redraw the diagram by trust level, with the context at the centre. Most AI threat models fail at the diagram.
