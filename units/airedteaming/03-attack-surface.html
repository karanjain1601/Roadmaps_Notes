The attack surface

Six layers, and which of them you can be attacked at depends almost entirely on how you obtained your model. A team consuming a hosted API has three layers to worry about; a team training its own has six. Knowing which you are is the first act of scoping.

Everyone has layers 3, 4 and 6. Almost nobody has layer 1.

The literature on adversarial ML is dominated by training-time attacks — poisoning, backdoors, adversarial examples against classifiers — because that is where the research is. The literature on incidents is dominated by layers 3, 4 and 6: prompt injection reaching a tool, output rendered as script, an API with missing authorisation, a model file that executed on load. If you consume a hosted model, you cannot be poisoned and your weights cannot be stolen, and roughly half the adversarial ML canon is out of scope — which is worth establishing on day one of an engagement, because it redirects effort from the interesting layers to the ones you actually have. The exception that catches people: fine-tuning gives you layer 1 back, and a retrieval index gives you a poisoning surface that behaves like layer 1 at a fraction of the cost.

the three access levels an attacker might have
Which attacks are available depends less on the layer than on what the
attacker can reach. Three levels, and the difference between them is large.

BLACK BOX — query access only, through your application.
  available:  prompt injection, jailbreaks, system-prompt extraction,
              output-path attacks, tool abuse, membership inference (with
              effort), model extraction (with a lot of queries), transferred
              adversarial examples
  not:        weight theft, poisoning (unless there is a training feedback
              loop), white-box adversarial example generation
  this is the realistic external attacker, and it is where most
  engagements sit

GREY BOX — knowledge of the architecture, the model family, the prompt
structure, or the ability to query the same base model directly.
  adds:       far more efficient adversarial example generation against a
              proxy model, targeted extraction, better-informed injection
  how it happens: the model family is usually discoverable from responses,
  the system prompt is usually extractable, and open-weights models mean
  an attacker can hold a local copy of the same base model

WHITE BOX — weights, gradients, architecture, and possibly training data.
  adds:       gradient-based adversarial examples, precise extraction,
              inversion, and the ability to search for inputs that produce
              a chosen behaviour
  who has it: anyone who downloaded your open-weights model. If you
  self-host a public checkpoint, assume every attacker is white box on
  the BASE model even if not on your fine-tune

THE PRACTICAL POINT: transferability means grey-box capability is often
available for free. Adversarial inputs and elicitation techniques
developed against one model frequently work against others, because the
models share architectures, training data and objectives (chapter 8). So
"our model is private" is a weaker defence than it sounds.
A retrieval index is a poisoning surface at a hundredth of the cost

Training-data poisoning requires influence over a training run — expensive, slow, and unavailable to most attackers. A retrieval index requires influence over one document, and the effect is immediate, targeted and persistent until someone notices. The threat models are analogous and the economics are not remotely comparable. Then consider who can write to a typical index: employees via an internal wiki, customers via support tickets and uploads, the open web via a scraping pipeline, and whoever ran the last ingestion job. This is the single most under-modelled surface in production AI systems, because retrieval is thought of as a read path and its write path is nobody's security responsibility. Auditing who can add a document to your index is an afternoon's work and it routinely produces the highest-severity finding in an engagement.

What escalates

the combinations that turn a text problem into a breach
Individual findings at layer 3 are usually low severity on their own — the
model said something it should not, to the person who asked for it. What
raises severity is a path from layer 3 to a layer with consequences.

  INJECTION + TOOL ACCESS
    untrusted content directs a privileged action. The single most
    important escalation in this unit (chapter 13)

  INJECTION + OUTPUT RENDERED AS HTML
    the model's response becomes script in another user's browser. Now the
    attack crosses users, which changes severity entirely (chapter 7)

  INJECTION + AN OUTBOUND CHANNEL
    anything that can send data out — an email tool, a webhook, a fetched
    URL, even an image whose src the renderer resolves — turns a
    disclosure into an exfiltration (chapters 7 and 13)

  RETRIEVAL WITHOUT PER-USER PERMISSIONS + ELICITATION
    the index holds documents this user cannot read, and the model will
    summarise what it was given. The access control was bypassed by the
    architecture rather than broken (chapter 14)

  SHARED CONTEXT + MULTI-TENANCY
    conversation history, caches or memory crossing between users. Turns
    any disclosure into a cross-tenant disclosure (chapter 14)

  TRAINING FEEDBACK LOOP + ANY WRITE PATH
    production interactions reaching a fine-tuning set gives an attacker
    layer 1 access from layer 3 (chapter 9)

THE PATTERN: severity comes from the combination, not the component. So the
useful engagement output is not a list of things the model said — it is a
set of PATHS, each running from an attacker-controlled input to a
consequence, with the control that would break each path named.

That is also the reason chapter 2's three questions come first. What can
the model cause to happen, whose content reaches its context, and whose
permissions apply when it acts — the answers tell you which of these
combinations exist in the system before you test anything.
Draw the surface before testing it

An hour with a whiteboard and the engineers who built the system produces a better engagement than a day of probing. Enumerate: every tool with its credential and permissions; every source that reaches the context with who controls it; every consumer of the output with how it is treated; and whether retrieval and history are scoped per user. That artefact does three things. It bounds the worst case, so you know what is worth pursuing. It identifies the escalation paths above, which are where the real findings are. And it survives the engagement — it is the thing the team keeps, updates when the architecture changes, and hands to the next reviewer. Reports get filed; a surface map gets maintained, and it is the more valuable deliverable (chapter 17).

The short version

  1. Six layers: training data, the artefact, the prompt context, the output path, tools, infrastructure.
  2. How you obtained the model decides your surface. A hosted API removes roughly half the adversarial ML canon.
  3. Everyone has layers 3, 4 and 6, and that is where incidents actually cluster.
  4. Fine-tuning gives layer 1 back, and a training feedback loop gives an attacker a path into it.
  5. A retrieval index is a poisoning surface at a fraction of the cost, and its write path is usually unaudited.
  6. Transferability makes grey-box capability free. "Our model is private" is a weak defence.
  7. Severity comes from combinations, not components — injection plus tools, plus rendering, plus an outbound channel.
  8. Deliver a surface map, not just a report. It bounds the worst case and it is the artefact that gets maintained.
