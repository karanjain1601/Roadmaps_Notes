What AI red teaming is

Two established disciplines already cover most of this ground — penetration testing knows how to attack systems, and model evaluation knows how to measure behaviour. AI red teaming exists because there is a gap between them where a specific class of failure lives.

Most of what is called AI security is ordinary security

Working through that list, a majority of the findings are authentication, authorisation, output encoding, deserialisation and rate limiting — things a competent application security review has covered for twenty years, appearing in a new context because the component is new. Being precise about which findings are genuinely novel is the single most useful analytical habit in this field, because it determines who should be doing the work. Conflating the two produces two bad outcomes: teams hire specialist AI red teamers to find missing authorisation checks, and teams assume their existing appsec programme covers prompt injection. The genuinely new territory is narrow — the instruction channel, training-time attacks, extraction, and agent tool use — and everything else is your existing programme applied to a new service.

the two properties that make this its own discipline
1. FINDINGS ARE PROBABILISTIC.

   A SQL injection either works or it does not. An elicitation technique
   works 30% of the time, and a variant works 60% of the time, and after a
   model update the first works 5% and the second works 80%.

   Consequences that follow, and they reach into everything:
     * a single successful attempt is a finding, not a fluke — you cannot
       dismiss it as noise
     * a failed attempt is not evidence of safety, only of that attempt
     * severity has to incorporate reliability, which conventional scoring
       systems have no field for (chapter 17)
     * a fix must be verified statistically rather than by re-running the
       original input once (chapter 16)
     * regression is continuous, because the model changes underneath you

2. THE BOUNDARY BETWEEN INSTRUCTION AND DATA IS NOT ENFORCED.

   In conventional software, code and data are separated by mechanisms that
   the machine enforces — parameterised queries, output encoding, memory
   protection, type systems. Injection vulnerabilities are the class where
   that separation fails, and the fix is always to restore it.

   A language model has one channel. The system prompt, the user's message,
   a retrieved document and a tool result all arrive as tokens in the same
   context, and the model's disposition to follow instructions applies to
   all of them. There is no parameterised-query equivalent (chapter 4).

   So prompt injection is not a bug of the same kind as SQL injection. It
   is the absence of the boundary whose failure defines that bug class, and
   that is why the mitigations in chapter 5 are architectural containment
   rather than input sanitisation.

THE PRACTICAL UPSHOT: treat the model as an untrusted component that
produces useful output. Not as a trusted decision-maker with a filter on
the front. Every recommendation in this unit is downstream of that stance.

Authorisation, before anything else

Everything in penetration testing ethics applies unchanged. Written

The Cyber Security unit covers rules of engagement properly.

FIVE THINGS THAT ARE SPECIFIC TO AI ENGAGEMENTS:

  1. THE MODEL PROVIDER'S TERMS ARE A SEPARATE AUTHORISATION. If the system
     is built on a third-party API, adversarial testing may breach that
     provider's acceptable use policy — the client cannot authorise you to
     violate an agreement they are a party to. Read the terms; many
     providers have an explicit research or red-teaming allowance and a
     process for it. Check before, not after.

  2. YOU WILL GENERATE PROHIBITED CONTENT. That is the point of some of
     the work. Decide in advance where it is stored, who can see it, how
     long it is retained, and how it is destroyed. Treat the artefacts of
     a safety engagement with the handling rules of the worst thing in
     them, and write that into the engagement agreement.

  3. SOME CATEGORIES ARE OUT OF SCOPE REGARDLESS OF AUTHORISATION.
     Material whose creation is itself illegal in your jurisdiction — child
     sexual abuse material being the unambiguous case — is not testable by
     producing it, and no client authorisation changes that. Test the
     control differently: with benign proxies, with classifier-level
     testing, or by reviewing the control's design. Agree these boundaries
     in writing before the engagement.

  4. TESTING COSTS MONEY, MEASURABLY. Automated adversarial testing against
     a metered API can generate a large bill quickly, and an aggressive
     harness can look exactly like an attack to the provider's abuse
     systems. Agree budget and rate limits; notify the provider if the
     volume is unusual.

  5. FINDINGS MAY NOT BE THE CLIENT'S TO FIX. If a jailbreak works against
     the underlying model rather than the client's system, the client can
     add mitigations and cannot fix the cause. That changes the report:
     what the client owns, what needs disclosing upstream, and what has to
     be contained architecturally (chapter 17).
"We red-teamed it" is not a security claim

The phrase has become a badge, and it is doing a lot of work with very little behind it. Red teaming establishes that specific attempts, by specific people, over a specific period, did or did not succeed. It cannot establish absence — a failed attack is evidence about that attack, not about the system — and the search space of natural-language inputs is not enumerable, so no amount of effort covers it. This is a weaker guarantee than a penetration test provides, and penetration tests are already weaker guarantees than people believe. The defensible statements are specific: what was tested, how, with what coverage, what was found, and what the residual risk is. Chapter 15 is about making that specificity possible and chapter 17 about writing it down honestly.

The two red teams

Security red teaming

Confidentiality, integrity and availability. Can an attacker read data they should not, cause the system to act against its owner's interest, or take it down? The adversary is external and hostile, the harm falls on the operator, and the output is a vulnerability report. This is where chapters 5, 7, 10, 12, 13 and 14 sit, and it is continuous with existing appsec practice.

Safety red teaming

Harmful, biased or dangerous output. Can the system be made to produce content that damages users or third parties? The adversary may be an ordinary user, the harm often falls outside the operator, and the output is an evaluation of policy coverage. Chapters 6 and 16 sit here, and the discipline draws more on evaluation methodology than on security.

They overlap, they are frequently done by the same people, and they answer to different stakeholders with different definitions of success. Being explicit about which one an engagement is scoped for prevents the common outcome where a security team delivers a report about offensive content to an audience that wanted to know about data exfiltration, or the reverse.

Start where the impact is, not where the novelty is

The temptation on a first AI engagement is to go straight for the interesting part — elicitation techniques, novel jailbreaks, the things that make good conference talks. The findings that matter are usually duller and arrive faster. Check what the model is allowed to do before checking what it can be made to say: which tools it can call, with whose credentials, against which systems, and whether the blast radius of a fully-compromised model is bounded (chapter 13). Then check output handling, then authorisation, then the supply chain. A system where the model has read access to one index and can return text is a fundamentally different risk from one where it can execute queries with a service account — and the second finding is worth more than a dozen elicitation results.

The short version

  1. Most "AI security" findings are ordinary security in a new context. Being precise about which are novel determines who should do the work.
  2. Findings are probabilistic. One success is a finding; a failure is evidence about that attempt only.
  3. The instruction/data boundary is not enforced, which is why prompt injection is not a bug of the same kind as SQL injection.
  4. Treat the model as an untrusted component that produces useful output, not a trusted decision-maker with a filter.
  5. The provider's terms are a separate authorisation the client cannot grant on your behalf.
  6. Plan for handling the content you generate, and agree the categories that are out of scope regardless of authorisation.
  7. "We red-teamed it" is not a security claim. Absence cannot be established; specificity is the only honest output.
  8. Check what the model can do before what it can say. Bounded blast radius beats a dozen elicitation findings.
