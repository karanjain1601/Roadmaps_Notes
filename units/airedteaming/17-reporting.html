Reporting and disclosure

Conventional severity scoring has no field for "works 30% of the time" and no field for "the cause is in a third party's training". Both are normal here, and a report that ignores them produces either panic or dismissal.

Reliability affects urgency, not severity

The tempting move is to discount a finding that only works some of the time, and it is usually wrong, because an attacker gets unlimited attempts and pays almost nothing per attempt. A technique succeeding 5% of the time succeeds within twenty tries, and twenty tries is a script. So the severity is set by the consequence and by who can reach it; reliability belongs in the urgency and remediation-sequencing discussion, where it genuinely matters — a 95% technique against a live system needs a same-day mitigation, a 3% one against the same system needs a fix this quarter. Report the rate and the trial count in every finding, and say explicitly which of the two things it is informing. Otherwise a reader will use it to dismiss the finding, and that is the interpretation the number invites.

What a finding needs

a template that survives a model update
TITLE — the path, not the technique.
  "Support-ticket attachments reach the assistant's context unescaped, and
   the assistant can email external addresses using a service credential"
  not "prompt injection in the chatbot"

THE PATH, as facts each independently verifiable:
  1. content writable by       any authenticated customer
  2. reaches the context via   ticket attachment ingestion, nightly
  3. the model can then        call send_email
  4. using                     a service credential with no recipient
                               restriction
  5. authorisation checked     at the prompt only

  This is the part that ages well. Each line is checkable by inspection,
  none depends on a particular string working, and a model update does not
  invalidate any of them.

DEMONSTRATION — reproducible, with conditions:
  model and version, sampling parameters, exact inputs, the assembled
  context if obtainable, trial count and success count, the success
  criterion decided in advance (chapter 15)

CONSEQUENCE — what an attacker achieves, concretely. Not "could lead to
  data loss" but "the contents of any ticket the assistant can read, sent
  to an address the attacker controls".

REMEDIATION — ordered, with the mechanical option first:
  1. scope send_email to the requesting user's own address domain
  2. require confirmation showing the recipient for external addresses
  3. escape untrusted content at prompt assembly
  4. restrict who can write ticket attachments
  Each independently reduces or removes the path. Say which are sufficient
  alone and which are defence in depth.

RESIDUAL RISK — what remains after remediation, honestly. Usually: prompt
  injection is not fixed, and the consequence is now bounded.

VERIFICATION — how the client confirms the fix, and how it stays fixed.
  Ideally a layer-1 assertion in their CI (chapter 16).
Split what the model did from what the system allowed

A single finding often contains two problems with different owners, and conflating them produces a report that reads as an indictment of the model and gives the engineering team nothing to do. Write them as separate statements. "The underlying model can be induced to produce X, at approximately this rate, which we have disclosed to the provider and cannot be fixed here" — that is context and residual risk. "In this system, content of that kind reaches the user unmoderated and renders as HTML, which is fixable here" — that is the finding, with an owner and a verification. The second sentence is what generates work and what someone can confirm was completed. Reports that only contain the first kind get filed, and the team's reasonable reading is that nothing they control was wrong.

Disclosing upstream

when the cause is in someone else's model
WHERE TO SEND IT. Most major model providers run a security or safety
disclosure programme, and several run bug bounties covering model-level
issues. Check the provider's security page for the current process rather
than guessing — and note that safety issues and security vulnerabilities
often have different intake routes at the same organisation.

WHAT TO INCLUDE, in addition to the usual:
  * the model identifier and version, and whether you tested others
  * the sampling parameters
  * the success rate over a stated number of trials — providers deal in
    rates, and a single transcript is much weaker evidence
  * whether it transfers to other providers' models, if you checked. This
    is genuinely useful to them and distinguishes a model-specific issue
    from a general one
  * the mechanism family, not just the instance (chapter 6)

WHAT NOT TO DO:
  * publish before the provider has had reasonable time, on the argument
    that "it is only a jailbreak". Elicitation findings can have real
    third-party consequences
  * include material whose creation or distribution is itself illegal.
    Describe the category and the mechanism; do not attach the artefact
  * assume the client can authorise your testing of the provider's model.
    They cannot — that is a separate agreement (chapter 1)

THE THREE-PARTY PROBLEM. Your client operates a system built on a
provider's model, and you have found something in the model. The client
needs to know their residual risk, the provider needs the technical
detail, and neither disclosure is quite the other. Agree in the engagement
contract, in advance, who discloses upstream and on what timeline —
otherwise it happens late, or twice, or not at all.

AND FOR ORDINARY VULNERABILITIES in AI tooling — an inference server, an
orchestrator, an MCP server — this is normal coordinated disclosure with
normal timelines. The ML ecosystem's projects are often small and
volunteer-run, so expect slower responses and be proportionate.
Deliver the artefacts, not just the report

The report gets read once and filed. The things that keep working are the tool table, the content-source table, the output-sink list and the harness (chapters 13, 15, 16) — because those get maintained, and a team that updates the tool table when it adds a tool has internalised the chapter-13 review rather than remembering that someone once wrote a document about it. So structure the engagement to produce them as deliverables in their own right, hand them over in a form the team can edit, and say in the report which of them needs updating on which trigger: a new tool, a new content source, a new output sink, a model version change. An assessment is a point-in-time claim; the artefacts are what let the team re-derive the claim themselves, which is the difference between an engagement and a capability.

The short version

  1. Reliability affects urgency, not severity. An attacker gets unlimited attempts at almost no cost.
  2. Report the rate and trial count, and say which of urgency or severity it informs — otherwise it reads as a discount.
  3. Title the finding as a path, not a technique. A path survives a model update; a prompt does not.
  4. Split what the model did from what the system allowed. The second has an owner and a verification.
  5. Order remediations with the mechanical option first, and say which are sufficient alone.
  6. State the residual risk honestly — usually that injection is not fixed and the consequence is now bounded.
  7. Agree upstream disclosure in the contract, in advance. Providers want rates and mechanisms, not transcripts.
  8. Deliver the artefacts and the harness. The report is filed; those get maintained.
