The AI supply chain

Downloading model weights is running untrusted code, and almost nobody treats it that way. The vulnerability class is thirty years old; what is new is that the delivery mechanism looks like fetching a data file.

Prefer formats that cannot execute, and check what you actually load

The single highest-value control in this chapter is format choice. Safetensors, GGUF and similar tensor-only containers are parsed rather than deserialised — there is no mechanism by which loading them runs code — whereas pickle-based formats execute during deserialisation by design, because that is what pickle is for. The trap is that "we use safetensors" is often true of the main weights file and not of everything the loader touches: a tokeniser configuration, a custom code module the repository ships, a processor definition, a cached auxiliary file. Several loader APIs will fetch and execute repository-provided Python when a flag permits it, and that flag is sometimes set in example code that gets copied. Audit what your load path actually reads, not what the model card says the weights are.

The layers of the chain

everything between a paper and your production process
MODEL WEIGHTS. The artefact itself. Format risk as above, plus the
  possibility of a backdoor in the weights that no format check finds
  (chapter 9). Provenance is the only real control.

REPOSITORY-SHIPPED CODE. Many hubs allow a model repository to include
  Python that the loader will run — custom architectures, processors,
  tokenisers. This is a straightforward code-execution path that is opt-in
  by a flag and frequently opted into by copied example code.

TOKENISERS AND CONFIGS. Small files, easily overlooked, and some formats
  among them are deserialised rather than parsed. A malicious tokeniser is
  a viable delivery mechanism.

DATASETS. Loading scripts, in some ecosystems, are executable. And the data
  itself is chapter 9's problem.

PYTHON DEPENDENCIES. The ordinary problem, with an unusually deep and
  fast-moving tree. Typosquatting on ML package names is documented and
  the naming space is crowded — many plausible variants of any given
  library name are unclaimed.

BASE CONTAINER IMAGES. CUDA images are large, versioned confusingly, and
  frequently pinned by tag rather than digest, so the contents change.

INFERENCE SERVERS AND FRAMEWORKS. Network-facing services with their own
  vulnerability history. Several have had serious remote-code-execution
  issues, and they are often deployed inside a trusted network on the
  assumption that they are internal tooling rather than exposed services.

MCP SERVERS AND AGENT PLUGINS. Newer, less mature, and they run with
  whatever privileges you gave the agent (chapter 13). A plugin is a
  dependency with credentials.

THE PATTERN: every layer is a conventional supply-chain problem, and the ML
ecosystem's norms are less mature than package managers' — less signing,
less pinning, more copying of example code, and a strong cultural habit of
downloading artefacts from strangers because that is how the field works.

Provenance you can actually verify

what to record and what to check
FOR EVERY MODEL ARTEFACT IN PRODUCTION, record:

  * the source URL and the specific revision — a commit hash, not a branch
    or a tag, because both move
  * a content hash of every file you load, verified at load time
  * the format, and whether it can execute
  * the licence, which is a separate compliance question and is frequently
    unclear on community re-uploads
  * who approved it, and when
  * whether it was scanned, with what, and what the result was

THAT LIST IS AN AI-BSOM, whatever you call it. CycloneDX has model-card
fields and there is active standards work here; the important part is
having the inventory rather than the format it is in.

THE LOAD-TIME CHECK IS THE ONE THAT MATTERS. Recording a hash and never
verifying it is documentation. Verifying it at load turns a substituted
artefact into a startup failure:

    expected = MANIFEST[path]
    actual   = sha256_of(path)
    if actual != expected: raise

Cheap, mechanical, and it converts the entire class of "someone replaced
the file" into a loud error.

MIRROR RATHER THAN FETCH. Pull artefacts once, scan them, store them in
your own registry, and have production load only from there. That removes
a runtime dependency on an external service, prevents an upstream
re-upload from changing what you run, and gives you a single place to
enforce the checks above. It is the same argument as an internal package
mirror and it is standard practice there for the same reasons.

SCANNING: tools exist that inspect serialised artefacts for dangerous
opcodes and suspicious imports — the major hubs run scanners, and
open-source options are available. Worth running, and understand the
limit: a scanner detects known-dangerous DESERIALISATION patterns. It does
not and cannot detect a backdoor in the weights (chapter 9). Two different
threats, one of which has a tool.
Inference servers are network services, not internal tooling

Model-serving frameworks and vector databases are frequently deployed with the mental model of a library rather than a service: bound to all interfaces, no authentication, on a network someone described as internal. Several inference servers have had serious remote-code-execution vulnerabilities, and some expose management endpoints that permit loading a model from an arbitrary path or URL — which is a code-execution primitive by way of the deserialisation problem above. Treat every one of these as an exposed service: authenticated, firewalled to known callers, patched on a schedule, and with any model-loading endpoint disabled or restricted in production. The same applies to the ML tooling nobody thinks of as production — a notebook server, an experiment-tracking UI, a pipeline orchestrator's web interface. Each has been an initial-access route in real incidents.

Whatever else you do, this one control catches the entire on-load class and costs a CI job: before an artefact is admitted to your registry, load it in a container with no network egress, no credentials, no mounted volumes and a short timeout, and observe. A deserialisation payload fires at load time by construction, so it fires there, where it reaches nothing — and any attempt at network egress or file access is a clear signal rather than an inference. Combine it with a scanner in the same job and record the result in the artefact's manifest entry. This is a strictly better position than trusting a hub's scanner, because it tests the specific artefact you are about to run in an environment you control, and it produces an auditable record that someone checked.

The short version

  1. Downloading weights is running untrusted code in pickle-based formats. The vulnerability class is old; the delivery route is new.
  2. Prefer tensor-only formats. Safetensors and GGUF are parsed, not deserialised — no mechanism executes.
  3. Audit the whole load path, not the weights file. Tokenisers, configs and repository-shipped code are all in it.
  4. Never set flags that permit executing repository code, and check that copied example code has not set them for you.
  5. Pin by revision hash and verify content hashes at load. A recorded hash never checked is documentation.
  6. Mirror to an internal registry, scanning on the way in. Same argument as a package mirror.
  7. A scanner finds dangerous serialisation, not backdoored weights. Two threats, one tool.
  8. Inference servers are exposed services. Authenticate them, and disable model-loading endpoints in production.
