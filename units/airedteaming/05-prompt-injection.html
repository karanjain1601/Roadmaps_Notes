Chapter 05 · The prompt layer

Prompt injection

Untrusted content reaches the model's context and is acted on as instruction. It is the defining vulnerability class of AI systems, it has no clean fix, and the useful engineering response is to make the consequences bounded rather than to try to stop the injection.

Indirect injection is the serious form, and for three reasons

Direct injection — a user instructing the model in their own message — is bounded: the attacker is authenticated, rate-limited, attributable, and can generally only affect their own session. Their worst outcome is usually that they see something they should not have seen, which they asked for. Indirect injection is different in kind. The payload is planted once and fires later, for a different user, with no authenticated party to attribute it to; it executes with the victim's session and permissions rather than the attacker's; and it scales, because one poisoned document can affect everyone who retrieves it. When an engagement finds both, the indirect finding is the one that matters, and the write paths into every content source the system reads are the audit that produces it.

THE LAST GROUP IS WORTH DWELLING ON. A human reviewing a document sees the
rendered result; an ingestion pipeline extracts the text. Anything the
extractor reads and the reviewer does not is an unreviewed channel, and
"we have a human approve every document" does not cover it.

THE AUDIT QUESTION, per source: who can write here, and is that set
smaller than "anyone"? If the answer is no, the content is untrusted, and
the design has to hold on that basis.

the architectural pattern worth knowing
The strongest available answer is to separate the component that READS
untrusted content from the component that ACTS.

  UNPRIVILEGED READER            PRIVILEGED PLANNER
  sees untrusted content         never sees untrusted content
  has no tools                   has tools
  returns structured data        acts on structured data only
  ------------------------------------------------------------------
  reads the document      ->     receives {summary, entities, no free text}
  reads the web page      ->     receives a schema-validated object
  reads the email         ->     receives extracted fields

The reader's output must pass through a SCHEMA — enumerated fields, typed
values, bounded lengths, no free-form strings that reach the planner's
instruction channel. Then a document's injected instruction can at most
influence the VALUES the reader extracts, not the ACTIONS the planner
takes, because the planner never receives natural language from the
document.

This is the dual-LLM pattern (Willison), and variants appear in research
as CaMeL and similar capability-based designs. It is genuinely stronger
than filtering, and it is not free:

  * it constrains what the system can do — anything requiring the planner
    to reason over the document's actual prose is out
  * the schema is the security boundary, so a permissive schema with a
    "notes" string field reopens the channel entirely
  * two model calls per step, so latency and cost roughly double

WHERE IT FITS: any flow where an agent must read attacker-influenceable
content AND take consequential action. That combination is exactly the
high-severity case in chapter 13, so if you have it, this pattern is the
thing to reach for before more filtering.

WHERE IT DOES NOT: a system whose value IS reasoning over untrusted prose —
a general research assistant, a document Q&A tool. There the honest answer
is that the model is not a trust boundary, and the design must assume the
untrusted content controls the model's behaviour.
The one prompt-layer control that is actually mechanical

Almost everything at this layer is statistical, with one exception worth implementing today: escape untrusted content when you assemble the prompt. If a document can contain text resembling a role marker, a turn boundary, or your own delimiter convention, then it can attempt to close your data section and open a new instruction section — and whether that succeeds is a tokeniser detail rather than a judgement call. Escaping or stripping those sequences at assembly time is deterministic: it does not depend on the model's disposition, it cannot be argued around, and it costs a few lines. This is the closest thing at this layer to output encoding, and it is skipped in most implementations because prompt assembly is usually an f-string that nobody reviewed as a security-relevant code path.

Testing for it

what to test, and what a result means
THE WRONG TEST: put an instruction in a message, see if the model follows
it, report a finding. That establishes almost nothing — you have shown that
a model follows instructions, which is its function.

THE RIGHT TEST is per PATH, and each path has three parts to verify:

  1. REACHABILITY. Can content you control actually get into the context?
     Plant a benign, uniquely identifiable marker — a nonsense token — in
     each candidate source and check whether it appears in the assembled
     prompt or influences output. This is the half that most teams have
     never checked, and it is where the surprises are: sources they did
     not know were ingested, metadata fields the extractor reads.

  2. INFLUENCE. Does content in that position change behaviour? Test with
     benign but observable requests — ask the model to include a specific
     word, to reorder its output, to call a harmless tool. You do not need
     a harmful payload to demonstrate control, and using a benign one
     makes the finding reportable without handling problems (chapter 1).

  3. CONSEQUENCE. What is downstream? This is the part that determines
     severity, and it is answered from the surface map rather than by
     testing (chapter 3).

RELIABILITY IS PART OF THE FINDING. Run each successful case 20 or more
times and report the rate. "Succeeds 3 times in 20" and "succeeds 19 times
in 20" warrant different responses, and a single anecdote supports neither
(chapter 17).

AND TEST THE CONTROLS SEPARATELY FROM THE MODEL. The questions that produce
durable findings are not about the model at all:
  * does retrieval filter by the requesting user's permissions?
  * is the tool's authorisation check evaluated against the user, or the
    service account?
  * is untrusted content escaped at assembly?
  * is output encoded at every render point?
  * can any single tool call cause an irreversible effect without
    confirmation?
Each of those has a yes-or-no answer, is stable across model updates, and
is fixable. Findings about the model's disposition are none of those.
Write the finding as a path, not as a prompt

An injection finding that consists of a prompt and a screenshot ages badly: the model updates, the prompt stops working, and the team concludes the issue is fixed. A finding written as a path survives — "content writable by any authenticated customer, via support ticket attachments, reaches the model's context unescaped, in a system where the model can call a tool that emails external addresses using a service credential" names four facts, each independently verifiable, none dependent on a particular string working. The remediation follows from it directly: escape at assembly, scope the email tool to the requesting user, require confirmation for external recipients, or restrict who can write attachments. That is a report a team can act on and re-verify after a model change, which is the actual test of whether a finding was written well (chapter 17).

The short version

  1. Indirect injection is the serious form: unattributable, fires for another user with their permissions, and scales.
  2. Inventory every source of untrusted content, including document metadata, alt text and hidden layers that an extractor reads and a reviewer does not.
  3. The consequence, not the injection, is what you can control. Bound it with least privilege and per-user retrieval permissions.
  4. Escaping untrusted content at assembly is mechanical — the one deterministic control at this layer, and usually absent.
  5. Separate the reader from the planner, with a schema between them. The strongest architectural answer, and it costs capability.
  6. A permissive schema reopens the channel. A free-text notes field defeats the whole pattern.
  7. Test reachability first with a benign marker. Most teams have never checked which sources actually reach the context.
  8. Write findings as paths, not prompts. A path survives a model update; a prompt does not.
