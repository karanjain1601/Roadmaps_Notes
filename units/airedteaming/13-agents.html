Chapter 13 · Systems and agents

Agentic systems

Everything in the prompt layer is a text problem until the model can act. Then it is a security problem, and the severity is determined by one thing: what the credentials behind the tools can reach.

The combination to avoid

Removing any one leg is the whole mitigation

This framing — sometimes called the lethal trifecta — is the most useful defensive idea in agent design, because it converts an unsolvable problem into a design choice. Prompt injection has no reliable fix (chapter 5), so an agent exposed to untrusted content will sometimes follow instructions in it. That is survivable if the agent cannot reach private data, or cannot send anything outward. The three capabilities are individually safe and jointly equivalent to handing an attacker a read of your data with an exfiltration channel — and no component has a bug, which is why code review does not find it and why the finding has to come from an architecture review. When an agent needs all three, split it into separate agents with separate credentials rather than granting one everything.

What counts as an outbound channel

broader than people assume, and this is where the finding usually is
The obvious ones get restricted. The subtle ones are why the trifecta keeps
being present in systems whose designers believed they had closed it.

  OBVIOUS
    send an email, post a message, create a ticket, call a webhook,
    write to a shared document, commit to a repository

  LESS OBVIOUS
    fetch a URL — the request itself carries data in the path or query,
      and the attacker reads their own access log
    render an image — the browser fetches the URL (chapter 7), so
      markdown image output is an outbound channel with no click
    a link the user might click, with data in the query string
    a DNS lookup, which leaks the queried name even when the connection
      is refused
    write to any store an attacker can later read — a shared index, a
      cache, an audit log they have access to, a public bucket
    an error message returned to the caller
    a filename, in a system where filenames are visible to others

  ALMOST INVISIBLE
    timing, and the number of tool calls, as a low-bandwidth channel
    a search query submitted to an external engine
    a calendar invitation, which notifies an attendee
    updating a record another party monitors

THE PRACTICAL TEST, and it is more useful than an allowlist:

  Can this agent cause any observable effect outside the trust boundary,
  in a way an attacker can measure?

If yes, that is the outbound leg, whatever it is called in your
architecture diagram. Egress filtering to an allowlist of hosts closes most
of these at once, and it is the single highest-value network control for an
agent — considerably more valuable than filtering the agent's text.

The confused deputy, precisely

and why authorising at the prompt is not authorising
An agent holds a credential. Untrusted content in its context directs a
tool call. The credential is used as designed, the tool behaves correctly,
and an action occurs that the credential's owner did not intend.

That is a confused deputy, which is a fifty-year-old problem in access
control, and it has a fifty-year-old answer: THE DEPUTY'S AUTHORITY MUST BE
SCOPED TO THE REQUESTER'S.

CONCRETELY, THE SHAPE THAT WORKS:

    def refund(order_id: str, amount: int, *, actor: User) -> Result:
        order = orders.get(order_id)
        require(order.customer_id == actor.customer_id)   # not the model
        require(actor.has_permission("refund"))
        require(amount <= order.total)
        require(amount <= actor.refund_limit)
        ...

Every check reads the ACTOR and the stored record. None reads anything the
model produced except the enumerated operation and the id. So an injected
instruction can at most cause the user to do something they were already
entitled to do — which is a much smaller finding, and often not one.

THE QUESTION TO ASK OF ANY AGENT: if the model were fully controlled by an
attacker, what could it do? If the answer is "whatever the user could do",
the design is sound and the residual risk is bounded. If the answer is
"whatever the service account can do", that is the finding, and it is
worth more than any number of elicitation results (chapter 1).
Human confirmation degrades to a rubber stamp unless it shows the effect

"Require approval for consequential actions" is the standard mitigation and it fails in a specific, predictable way. A dialogue saying the assistant would like to send an email — approve? gets approved, every time, within a week, because it appears constantly and the cost of reading it exceeds the perceived risk. Confirmation is only a control when it shows the actual effect and the user can evaluate it: the recipient address, the amount, the record being changed, the file being deleted — rendered plainly, with the unusual part highlighted. And the frequency has to be low enough that attention survives, which means confirming only genuinely consequential and irreversible actions rather than everything above a threshold. A confirmation on every tool call trains the user to click through the one that mattered.

agent-specific failure modes worth testing for
MEMORY POISONING. An instruction that reached the context once is written
  into stored memory and re-enters every later session. A single successful
  injection becomes a durable compromise of the account, and it looks like
  ordinary stored state.
  -> do not write memory automatically from model output; summarise into a
     schema, or require the user to confirm. Make memory inspectable and
     clearable by the user.

TOOL CHAINING. No single tool is dangerous; a sequence is. Read a file,
  encode it, put it in a search query. Each call is individually
  reasonable.
  -> review the tool set as a SET, and ask what compositions exist. This is
     the review that finds the real problems, and it cannot be done one
     tool at a time.

TOOL SHADOWING AND DESCRIPTION INJECTION. Tool descriptions enter the
  model's context, so a maliciously described tool — from a third-party
  plugin or MCP server — can influence how other tools are used. A
  description is untrusted content if you did not write it.
  -> pin and review third-party tool definitions; treat a plugin as a
     dependency with credentials (chapter 12).

MULTI-AGENT LAUNDERING. Agent A reads untrusted content and passes a
  summary to agent B, which has tools. By the third hop nobody can say
  which content came from where.
  -> a schema between agents, with no free-text field crossing into an
     instruction channel (chapter 5). A "notes" string defeats it.

CONFIRMATION FATIGUE. Covered above, and it is the most reliable way a
  designed control stops working in production.

UNBOUNDED LOOPS. An agent retrying, re-planning and re-calling until a
  budget is exhausted. A cost attack, and sometimes an availability one.
  -> hard call budgets, and alert on tasks that approach them.

DELEGATED AGENTS INHERITING PERMISSIONS. A sub-agent spawned for a subtask
  receiving the parent's full credential set.
  -> scope the sub-agent's tools to the subtask, explicitly.
The artefact to produce first

Before testing anything, build a table with one row per tool and these columns: what it does, which credential it uses, what that credential can reach, whether the action is reversible, whether it can send data outward, and whose permissions are checked. An afternoon with the engineers produces it, and it does three things no amount of probing does. It bounds the worst case, so you know what is worth pursuing. It makes the trifecta visible immediately — private data, untrusted input and an outbound channel are columns in that table. And it makes tool composition reviewable, which is where the real findings are, because you can read down the outbound column and ask what could reach it. Reports get filed; this table gets maintained and updated when a tool is added, which makes it the more valuable deliverable (chapters 3 and 17).

The short version

  1. Private data, untrusted content and an outbound channel — safe individually, equivalent to exfiltration together.
  2. Removing any one leg is the mitigation. Prompt injection has no fix, so make it not matter.
  3. Outbound is broader than it looks: a fetched URL, a rendered image, a DNS lookup, a shared write path.
  4. Egress filtering is the highest-value network control for an agent — worth far more than filtering its text.
  5. Authorise at the tool against the requesting user, never at the prompt and never against a service account.
  6. Ask what a fully-controlled model could do. "Whatever the user could" is sound; "whatever the service account could" is the finding.
  7. Confirmation must show the actual effect, and be rare enough that attention survives.
  8. Review the tool set as a set. Composition is where the findings are, and per-tool review misses it.
