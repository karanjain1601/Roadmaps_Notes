A spend cap is the only control that bounds the loss

A conventional denial-of-service attack exhausts capacity, and you notice because the service degrades. A denial-of-wallet attack exhausts budget, and the service works perfectly right up until the invoice arrives or the provider cuts you off mid-month. Rate limits reduce the rate; they do not bound the total, so a limit permitting a modest sustained load still permits a large monthly figure. A hard spend cap, with alerting at fractions of it and a defined degraded mode for what happens when it is hit, is the only control that puts a ceiling on the loss — and it is the one most often absent, because it reads as a finance concern rather than a security one. Decide in advance whether hitting the cap means the feature degrades, queues or fails. The alternative is discovering that answer during an incident.

Tenancy in a stateful conversation

the shared state that each needs scoping
Multi-tenancy is well understood for stateless CRUD. An AI feature adds
several pieces of shared, stateful infrastructure, and each has been a real
leak somewhere.

  CONVERSATION HISTORY. Keyed by a session id. If that id is guessable, or
    the lookup does not verify ownership, one user reads another's whole
    conversation. An ordinary object-reference bug on an object that
    contains everything.

  THE RETRIEVAL INDEX. The important one. If retrieval runs with the
    service's permissions and returns global top matches, a question can
    pull documents the user is not entitled to, and the model summarises
    them helpfully. Filter by entitlement BEFORE ranking — post-filtering
    leaks through result counts and latency, and degrades relevance.

  PROMPT AND RESPONSE CACHES. A cache keyed on prompt content alone serves
    one tenant's response to another whose prompt matches. Include the
    tenant in the cache key, always.

  VECTOR STORES. Namespaces and metadata filters are usually available and
    usually optional. An optional isolation control is one somebody forgot.

  LONG-TERM MEMORY. Per-user by intent; the write path and the read path
    both need the check. Workspace-shared memory is a feature in some
    products and an accident in others.

  FINE-TUNED WEIGHTS. Not scopeable at all. Do not fine-tune across a
    tenancy boundary — memorisation is retrievable by any tenant
    (chapter 10). Use retrieval, where the boundary is mechanical.

  QUOTA STATE. A shared limit lets one tenant exhaust another's capacity.

  LOGS AND TRACES. A second copy of everything, with looser access control
    and longer retention than the primary store.

The provider key in a client bundle is a recurring find

Calling a model API from a browser or mobile client requires the key to be in the client, and a key in a client is public — extractable from a bundle, visible in network inspection, recoverable from a decompiled app. The consequence is not just cost: an extracted key is usually organisation-scoped, so it grants access to every model and every capability your account has, billed to you, from anywhere. The fix is architectural rather than obfuscation: proxy through your own backend, where the key stays server-side, the request is authenticated as your user, per-account limits apply, and you can log what was asked. Client-side key handling has no safe version — key rotation, obfuscation and remote configuration all still put the key on the device. If a design requires direct client-to-provider calls, that requirement is the finding.

rate limiting that actually constrains
Rate limiting appears in three earlier chapters as the control that matters
— against extraction (10), against black-box adversarial search (8), and
against agent loops (13). It is worth being specific about what works.

  PER ACCOUNT, NOT PER IP. IP rotation is cheap and residential proxy
    services are a commodity. Per-IP limiting stops accidents.

  LIMIT TOKENS, NOT JUST REQUESTS. One request with a 200k-token context
    costs more than a hundred short ones. A request-count limit leaves
    the expensive axis unbounded.

  MULTIPLE WINDOWS. A per-minute limit permits a large daily total; a
    daily limit permits a burst. Use both, plus a monthly spend cap.

  LIMIT THE EXPENSIVE OPERATIONS SEPARATELY. Tool calls, code execution,
    long-context requests and retrieval queries have different unit costs
    from a short completion.

  RETURN 429 AND MEAN IT. A limit that queues instead of rejecting turns
    a cost attack into a latency attack for everyone else.

  ALERT ON APPROACH, NOT ON BREACH. An account at 80% of an unusual limit
    is the signal; at 100% you are already paying.

AND THE CALCULATION WORTH DOING ONCE, because it tells you whether your
limits are controls or decoration:

  at my per-account limit, how long would an attacker need to
  (a) distil the model, (b) run a black-box search, (c) exhaust the
  monthly budget — and would anyone be alerted before they finished?

If the answer is "three days, and no", the limit is not a control.
The ML tooling nobody thinks of as production

Experiment-tracking UIs, notebook servers, pipeline orchestrator dashboards, vector database admin consoles, model-serving management endpoints, annotation tools. Each is a web application, several have had serious vulnerabilities, and they are routinely deployed with the mental model of internal tooling — no authentication, bound to all interfaces, on a network someone described as private. Every one of these has been an initial-access route in real incidents, and they are attractive targets precisely because they sit close to the data and the credentials. Enumerate them as part of the engagement: list every AI-adjacent service with a network listener, check what authenticates it, and check whether any of them exposes a model-loading or code-execution endpoint (chapter 12). This is unglamorous and it is where the fast findings are.

The short version

  1. Denial of wallet is the availability attack that matters — the service works perfectly until the invoice arrives.
  2. Rate limits reduce the rate; only a spend cap bounds the total. Define the degraded mode in advance.
  3. Limit per account, not per IP, and limit tokens rather than only requests.
  4. Filter retrieval by entitlement before ranking. Post-filtering leaks through counts and latency.
  5. Put the tenant in every cache key. A prompt-hash key serves one tenant's response to another.
  6. Do not fine-tune across a tenancy boundary. Weights hold no per-tenant boundary; retrieval does.
  7. A provider key in a client bundle is public. Proxy through your backend; obfuscation has no safe version.
  8. ML tooling is production infrastructure. Notebooks, tracking UIs and serving endpoints are exposed services.
