Chapter 04 · The prompt layer

Why guardrails are soft

One structural fact explains prompt injection, jailbreaks, system-prompt extraction and most of what follows: a language model receives instructions and data on the same channel, and has no mechanism for telling them apart. Not a weak mechanism — none.

There is no parameterised-query equivalent

Every injection class in conventional software has a fix that restores a boundary the machine enforces. SQL injection is fixed by parameterised queries, where the database receives the query structure and the values through separate channels and no value can become structure. XSS is fixed by contextual encoding. Command injection is fixed by passing an argument vector rather than a shell string. In each case the fix is mechanical — it does not depend on the input being benign, and it does not degrade under a cleverer attacker. No such mechanism exists for a language model, because the model's function is to interpret natural language, and "interpret this text as inert data" is itself an instruction expressed in that same text. Role markers, delimiters and priority hints all help statistically and none is enforced. That is why chapter 5's mitigations are architectural containment rather than a fix.

What the role markers do and do not do

system, user, assistant, tool
Modern chat models are trained on a structured format with role markers,
and the API presents them as separate fields:

    [{"role": "system",    "content": "..."},
     {"role": "user",      "content": "..."},
     {"role": "assistant", "content": "..."},
     {"role": "tool",      "content": "..."}]

WHAT THAT GENUINELY BUYS YOU. The model has been trained so that system
content carries more weight than user content, and providers have invested
heavily in this — instruction hierarchies, priority training, and specific
work on resisting attempts to override higher-priority instructions. It is
a real and improving mitigation. A system instruction is meaningfully
harder to override than it was three years ago.

WHAT IT DOES NOT BUY YOU. The distinction is LEARNED, not enforced. The
roles are tokens in a sequence; the model's adherence to the hierarchy is
a behavioural tendency with a probability attached, and probabilities under
adversarial pressure are not guarantees. Contrast with a memory protection
bit, where the hardware refuses regardless of how the instruction is
phrased.

Consequences that matter for a defender:

  * PUTTING SOMETHING IN THE SYSTEM PROMPT IS NOT AN ACCESS CONTROL.
    "Never reveal account numbers" is a strong hint. A query filtered by
    the authenticated user's id is a control. Do not confuse them.

  * THE SYSTEM PROMPT IS NOT A SECRET. It is in the model's context, the
    model discusses its context, and extraction is routinely successful.
    Design so that its disclosure is uninteresting: no credentials, no
    internal URLs, no unreleased feature names, nothing whose secrecy the
    system depends on.

  * RETRIEVED CONTENT AND TOOL RESULTS ARE FREQUENTLY PLACED IN A USER OR
    TOOL ROLE, which means third-party text sits at a similar priority to
    the actual user's request. Structuring the assembly so untrusted
    content is clearly demarcated as data helps. It does not resolve.

  * THE ROLES CAN BE DESCRIBED IN CONTENT. Nothing prevents text inside a
    document from resembling a role marker or a system instruction. Whether
    that works varies by model and tokeniser, and defending against it is
    a matter of escaping content at assembly time — which is a real,
    cheap control and one of the few mechanical ones available.

Why alignment training is not a boundary

what safety training is, in security terms
Safety behaviour in a model comes from training — supervised fine-tuning on
demonstrations, reinforcement learning from human or AI feedback,
constitutional methods, adversarial training against known attacks. The
result is a model that reliably declines a very wide range of requests.

IN SECURITY TERMS, that is a DETECTIVE control implemented by a classifier
with a soft decision boundary — not a preventive control implemented by a
reference monitor. Three consequences follow, and they shape how you test.

  1. IT GENERALISES, WHICH IS THE POINT AND THE PROBLEM. The model declines
     things nobody enumerated, which is why safety training beats a
     blocklist. The same generality means the boundary is fuzzy: inputs
     near it behave inconsistently, and an adversary searching near the
     boundary will find inconsistencies. That is a property of learned
     decision boundaries, not a training defect.

  2. IT IS A DISTRIBUTION, NOT A RULE. The same input can be declined and
     accepted across samples, at different temperatures, in different
     languages, with different framing, at different context lengths. So a
     single failed attempt is weak evidence, and a single success is a
     finding (chapter 1).

  3. IT COMPETES WITH OTHER TRAINED OBJECTIVES. Models are also trained to
     be helpful, to follow instructions, to complete patterns, and to
     maintain coherence. Attack families work by putting these in tension
     with the safety objective, which is why the taxonomy in chapter 6 is
     organised by which objective is being leveraged rather than by
     surface form.

WHAT THIS MEANS FOR THE ARCHITECTURE — and it is the whole argument of the
unit:

    Do not build a system whose security depends on the model refusing.

    Build one where the model refusing is a useful additional layer, and
    the boundary that actually holds is somewhere the machine enforces it:
    at the tool's authorisation check, at the output encoder, at the
    retrieval permission filter, at the sandbox.

A useful reframing when reading a finding: ask whether it describes the
model doing something it should not, or the SYSTEM allowing something it
should not. The first is a model-provider concern and a mitigation
opportunity. The second is your bug, and it is fixable.
Guardrail products are filters, and filters are models too

The standard mitigation offered is a separate classifier on the input, the output, or both — a moderation endpoint, an injection detector, a policy model. These are worth deploying and worth understanding precisely. A guardrail is itself a model with a soft boundary, so it inherits every property above: it can be evaded, it produces false positives that degrade the product, and its coverage is whatever its training covered. Layering two soft controls gives you a better probability, not a guarantee, and the composite failure rate is the one to measure rather than each in isolation. Two specific traps. A detector evaluated only on published attack corpora reports excellent numbers and tells you nothing about novel input. And an output filter that inspects text cannot see an action already taken — if a tool call happened before the filter ran, filtering the response is theatre (chapter 13).

What is actually enforceable

Mechanical — holds regardless of input

  • Authorisation at the tool, against the requesting user's identity
  • Retrieval filtered by the user's permissions before documents reach the context
  • Output encoding at every render point
  • Parameterised queries for anything the model influences
  • Sandboxing of generated code, with no network and no credentials
  • Escaping untrusted content at prompt-assembly time
  • Rate and spend limits, enforced outside the model
  • Human confirmation for consequential actions

Statistical — helps, does not hold

  • System-prompt instructions about what not to do
  • Role markers and delimiters
  • Input injection detectors
  • Output moderation classifiers
  • Asking the model to check its own output
  • Instructing the model to treat a section as data
  • Refusal training in the base model
  • Keyword and pattern blocklists

Both columns belong in a real system. The error is not deploying the right-hand column — it is counting on it: designing a system where the only thing standing between an untrusted input and a consequence is an item from the right, and then describing that as a control in a design document.

The design question that resolves most arguments

When someone proposes a prompt-layer mitigation, ask: if the model ignored this instruction entirely, what would happen? If the answer is "the request would be refused by the tool's authorisation check" or "the output would be encoded and render as text", the mitigation is a defence-in-depth improvement on a system that is already sound. If the answer is "the data would be disclosed" or "the action would execute", then the instruction is the control, and the system's security rests on a probability. That question moves the conversation from prompt wording — which is unfalsifiable and endless — to architecture, which is testable. It is also the fastest way to triage a list of proposed guardrails into the ones that matter and the ones that are reassurance.

The short version

  1. Instructions and data arrive on one channel with no enforced separation. Everything in this part follows.
  2. There is no parameterised-query equivalent, because "treat this as data" is itself an instruction in the same text.
  3. Role markers are learned, not enforced. A real and improving mitigation, and a probability rather than a guarantee.
  4. The system prompt is not a secret and not an access control. Design so its disclosure is uninteresting.
  5. Safety training is a detective control with a soft boundary, competing with helpfulness and instruction-following.
  6. Guardrails are models too, so they inherit every one of these properties. Measure the composite failure rate.
  7. Escaping untrusted content at assembly time is one of the few mechanical controls available at this layer.
  8. Ask what happens if the model ignores the instruction. That moves the argument from wording to architecture.
