CHAPTER 01

Why models are hard to ship

Six things have to line up to rebuild a model, each of them individually fine, and the product is 7.1%. Then CI runs when code changes — and two of the three inputs to a model are not code, so a system where nothing is broken and no test failed spends 45.5% of its days running a combination nobody has tested.

    THE PREMISE

    A model is not a service

    Everything in software delivery assumes the artefact is code. A model is code plus data plus an environment, and the three do not behave alike.

    Why the usual practices do not transfer cleanly
    A serviceA model
    The artefactA binary built from sourceWeights built from source and data
    CorrectnessTests pass or they do notA number that is better or worse than another number
    Rebuilding itDeterministicFrequently not
    What triggers a releaseA commitA commit, a data refresh, or nothing at all
    FailureLoud — errors, timeoutsSilent — predictions get worse
    RollbackRedeploy the previous versionRedeploy which previous version, trained on what?
    The two rows that generate the rest of this unit

    Failure is silent. A service that breaks pages someone. A model that degrades keeps returning well-formed responses at normal latency, and the only symptom is that they are worse. Every monitoring chapter here exists because of that row.

    The artefact has three parents. Code, data and environment, each with its own lifecycle and its own release cadence. The next two demos are about what that costs.

    THE FIRST COST

    Rebuilding the same model twice

    Reproducibility is a conjunction, not a budget

    No single component is the culprit. The worst one — the random seed — still matches 45% of the time on its own. And the product of six such components is 7.1%.

    Fixing only the worst one takes you from 7.1% to 15.7%. Still a coin flip you lose, roughly five times in six.

    This is exactly unlike an error budget, where the largest variance source dominates and the rest barely matter. Here everything must hold simultaneously, so there is no highest-leverage fix — there is only the full set or a lottery.

    Which is why the answer is mechanical rather than careful

    You do not achieve this by being disciplined. You achieve it by making the unpinned state impossible to reach: a lockfile rather than a requirements list, a content hash rather than a table name, a container rather than a machine, a seed set in the pipeline rather than in a notebook cell.

    The target is not "we usually get the same model". It is a rebuild that fails loudly when an input has moved, which is a different and much more achievable goal — and it is what chapter 2 is about.

    THE SECOND COST

    What is actually running

    Continuous integration fires on a commit. Two of the three inputs to a model do not involve one.

    180 days. CI runs on every code change and pins the combination present at that moment
    What movesDays on an untested combinationLongest such run
    Code only0.0%0.0 days
    Code and data35.5%14.1 days
    Code, data and environment45.5%15.3 days
    Slow releases, live data75.3%48.7 days
    The first row is the service case, and it works

    When code is the only moving input, CI covers it completely — 0.0% of days on an untested combination. That is not a coincidence; it is what continuous integration was designed for, and on a normal service it succeeds.

    Add a data source that refreshes on its own schedule and it becomes 35.5%. Add an environment that updates independently and it becomes 45.5%. Nothing is broken. No test failed. CI simply was not triggered, because nobody committed anything.

    And releasing less often makes it worse

    The last row drops the code-change rate and keeps the data live: 75.3% of days on an untested combination, with runs of up to 49 consecutive days.

    That inverts the usual intuition. Shipping code is what re-tests the combination, so a quiet quarter on a model-backed system is a risky one rather than a safe one. The team that has not deployed since March is not stable; it is running something last verified in March against data from this morning.

    You cannot test your way out of it

    Over 180 days, code alone reaches about 37 distinct combinations. All three moving reaches about 7,030 — a 190-fold increase — while CI tested about 37 of them.

    So the response is not more test coverage. It is to make the untested state detectable: validate the data at the pipeline boundary (chapter 6), record which combination produced each prediction (chapter 11), and monitor the model rather than only the service (chapter 16).

    THE SHAPE OF THE WORK

    What sits between a notebook and production

    The stages this unit works through, and what each one is actually for.

    Reproducibility — chapters 2 and 3
    Being able to rebuild the artefact, and knowing which artefact you have. Everything downstream assumes this, and the demo above is why it comes first.
    Pipelines — chapters 4 to 8
    Turning a script that a person runs into a job that a scheduler runs. Orchestration, data contracts, features and training, each as a step that can fail and be retried on its own.
    Tracking and registry — chapters 9 to 11
    Answering "what is running, what produced it, and how does it compare to the last one" without an archaeology project.
    Serving — chapters 12 to 15
    Getting predictions to the thing that needs them, inside a latency budget and a cost budget. This is where most of the surprising arithmetic lives.
    Operating — chapters 16 to 19
    Monitoring, retraining, incidents, and the platform underneath. The longest phase of a model's life and the least discussed.
    What this unit assumes and does not repeat

    Containers, CI/CD mechanics, cloud infrastructure and Kubernetes are covered in DevOps, Docker and Kubernetes. Pipelines, warehouses and streaming are in Data Engineer. The algorithms are in Machine Learning.

    This unit covers what is different when the thing being deployed is a model, and cross-references rather than duplicating. The closest neighbour is AI & Data Scientist chapter 22, which measured the statistics of drift; here the concern is the system that detects and responds to it.

    CALIBRATION

    How much of this you actually need

    The full apparatus is wrong for most teams. Here is what scales with what.

    What to have at each stage, and what is premature
    SituationWorth havingPremature
    One model, retrained by handPinned environment, versioned data, a README that worksA feature store, a registry
    One model, retrained on a scheduleA pipeline, experiment tracking, basic monitoringStreaming features, multi-region serving
    Several models, several peopleA registry, data contracts, shared servingA bespoke platform
    Models as a product surfaceThe lot, plus cost attribution and governance—
    The one thing worth doing on day one

    Of everything in this unit, the highest return at the smallest cost is recording which code, data and environment produced each deployed model. It is a few lines in the training job and a column in a table.

    It does not prevent the 45.5% or the 7.1%. It makes both of them visible, which converts a class of unexplainable incidents into a lookup — and it is the thing teams most often wish they had started with.

    JUDGEMENT

    Five questions for an existing ML system

    Answerable in an afternoon, and the answers locate everything else in this unit.

  1. Could you rebuild the currently deployed model? Not approximately — bit-for-bit, or with a documented reason why not. The 7.1% is the default answer.
  2. What triggers a retrain, and what tests it? If the answer is "a person, when they remember", the 75.3% row applies.
  3. How would you know the model had degraded? Silent failure is the defining property; a dashboard of request counts does not answer this.
  4. Which data produced the model that made yesterday's prediction? If this needs an investigation, lineage is missing.
  5. What is the rollback procedure, and when was it last used? A procedure that has never been run is a hypothesis.

    6. Recap

    What to take from this chapter

    1. A model is code plus data plus an environment, and the three have different lifecycles.
    2. Model failure is silent — well-formed responses at normal latency that happen to be worse.
    3. Six components each mostly fine multiply to 7.1% odds of an identical rebuild.
    4. The worst single component still matches 45% of the time, so there is no single culprit.
    5. Fixing only the worst takes 7.1% to 15.7%. Reproducibility is a conjunction, not a budget.
    6. Pinning everything gives 91.3%, or roughly one differing rebuild in eleven.
    7. The fix is mechanical, not careful: make the unpinned state impossible to reach.
    8. CI fires on commits, and two of the three inputs are not commits.
    9. Code alone: 0.0% of days on an untested combination. That is the service case, and it works.
    10. Add data: 35.5%. Add the environment: 45.5%. Nothing broken, no test failed.
    11. Releasing less often makes it worse — 75.3% of days, with runs up to 49 days.
    12. So a quiet quarter on a model-backed system is a risky one.
    13. Three moving inputs reach 7,030 combinations against code's 37, and CI tested about 37.
    14. You cannot test your way out; make the untested state detectable instead.
    15. Most teams need far less than the full apparatus, and it scales with model count and headcount.
    16. Record which code, data and environment produced each deployed model. Day one, few lines.
