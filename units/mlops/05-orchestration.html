Orchestration

    THE MODEL

    A graph, not a schedule

    The distinction sounds pedantic and it decides how the system behaves under failure.

    Two ways to run the same six steps
    Six cron entriesOne DAG
    OrderingImplied by clock timesDeclared by dependencies
    If a step runs lateThe next starts anyway, on stale inputThe next waits
    If a step failsDownstream runs on yesterday's outputDownstream does not run
    Rerunning one stepManual, and you must know what followsThe graph knows
    BackfillA bespoke scriptA parameterised rerun
    The third row is the one that costs money

    Cron has no concept of failure propagating. A feature job that fails silently leaves yesterday's feature table in place, and the training job that follows at 03:00 trains happily on it — producing a model that is quietly a day stale, with nothing in any log to say so.

    That is chapter 1's silent failure arriving through the scheduler. A DAG turns it into a loud one: the downstream task is marked upstream-failed and does not run.

    PARALLELISM

    The critical path

    Adding workers helps until you hit the longest chain, and then it stops helping entirely.

    The ceiling is 1.45×, and three workers reach it

    The critical path is ingest_a → clean_a → join → features_3 → assemble → train → evaluate, which totals 135 minutes. No amount of parallelism gets below that, because those seven tasks must run in order.

    So 196 minutes of work has a maximum speedup of 1.45×, and it is reached at three workers. The ninth through twelfth workers contribute nothing but 1,424 idle worker-minutes of billing.

    This is worth computing before provisioning. A pipeline dominated by one long serial step — which any pipeline containing training is — has almost no parallelism to exploit, and the instinct to scale the cluster is answering the wrong question.

    Optimising off the critical path saves exactly nothing

    Halving features_1 — a twenty-minute task, a real piece of engineering work — saves 0.0 minutes. So does halving ingest_b. Halving train saves thirty.

    And the path is not the list of longest tasks. features_1 at 20 minutes is longer than evaluate at 8, and speeding up the shorter one helps while the longer one does not. The critical path is the longest chain, which you cannot read off a task list — it has to be computed from the dependencies.

    It also moves. Make training four times faster and the critical path drops to 90 minutes, at which point the next bottleneck is somewhere else and the whole calculation has to be redone.

    FAILURE

    What a retry actually buys

    Retry policies are designed for independent failures. Most real ones are not.

    A task fails 30% of the time. Sometimes that is transient — a flaky connection, a preempted node. Sometimes it is an outage: the upstream service is down, the cluster is full, the credential expired, and every attempt in the next twenty minutes will fail for the same reason.

    The right-hand column stops moving

    Under independent failure, retries work exactly as advertised: three of them take 70.6% to 99.2%, and the problem is solved.

    With one failure in five being an outage, the same three retries reach 79.1%, and the fifth adds 0.1 points. The sequence stalls just under 80% — which is precisely the ceiling set by how often the failure is an outage at all. Retrying into an outage is not a recovery strategy; it is load, applied to the thing that is already failing.

    The wasted-compute column keeps climbing while the success column does not. That is the definition of a policy that has stopped working.

    Backoff works, and only once it has waited long enough

    At five retries backoff reaches 98.2% against immediate retry's 79.6%, because the cumulative wait outlasts the outage. It costs elapsed time — 20.3 minutes against 10.2 — and essentially no extra compute, which is the right trade against a shared dependency.

    But look at the three-retry row: backoff gives 79.1%, identical to immediate. Its cumulative 12.8 minutes is still inside the 20-minute outage, so it has bought nothing at all.

    The parameter that matters is the total time spanned, not the number of retries. A policy of "three attempts with backoff" against a twenty-minute outage is a policy that fails, and it fails while looking like best practice.

    And backoff is not a general improvement

    With purely independent failures, backoff gives 99.2% against immediate retry's 99.2% — no benefit — while still costing elapsed time.

    So "always use exponential backoff" is advice with a missing condition. It is a fix for correlated failure specifically. If your failures are genuinely independent it buys you nothing but latency, and if they are correlated the thing to size is the window, not the count.

    WHEN TO RUN

    Schedules, sensors and events

    Three ways to start a pipeline, with different failure modes.

    A schedule
    Runs at a time. Simple, predictable, and it assumes the data arrived. When the upstream is late the pipeline runs on yesterday's data and succeeds — which is the silent failure again.
    A sensor, polling for readiness
    Waits for a file, a partition, a row count. Correct, and it occupies a worker slot while waiting. A pipeline with several sensors can deadlock itself by holding every slot waiting for things that need a slot to produce.
    An event
    The upstream signals completion. Best when you control the upstream and awkward when you do not, since a missed event means the pipeline simply never runs — a failure with no failed task to alert on.
    Whatever you choose, add a deadline
    "This should have completed by 06:00" catches all three failure modes above, including the one where nothing ran at all. It is the only alert that fires on absence, and absence is the failure mode a task-level alert cannot see.
    Idempotence is what makes any of this safe

    Chapter 4's requirement returns here with teeth. A scheduler retries, backfills, and occasionally runs the same interval twice after a restart. Every one of those is a rerun, and on a non-idempotent step each turns a recoverable failure into duplicated data.

    The practical form: a task takes its interval as a parameter, derives its output location from it, and overwrites rather than appends. Then a rerun is free and a backfill is the same code.

    HISTORY

    Backfills

    Reprocessing the past is where orchestration earns its keep, and where it most often goes wrong.

  1. A backfill is a resource event, not a data event. Thirty days of a pipeline that normally runs once a day is thirty times the load, arriving at once. Cap the concurrency or it competes with the live run for the same cluster.
  2. Backfill in reverse order when the recent data matters more. If someone is waiting on the output, yesterday first is usually worth more than a month ago first.
  3. Beware point-in-time correctness. Reprocessing an old interval with today's feature code and today's upstream tables does not reconstruct what that day looked like — it produces something that never existed. Chapter 7 is about this specifically.
  4. A backfill writing to the same place as the live run is a race. Write to a separate location and swap, which is the same discipline as an idempotent step.
  5. Decide whether downstream should re-fire. Backfilling features usually should retrain; backfilling a report usually should not. The graph will happily do either.
    6. The backfill that quietly rewrites history

    The worst version is a backfill that succeeds. Old partitions are replaced with values computed from today's code and today's upstream state, the metrics for last quarter shift, and there is no failure anywhere to investigate.

    If the data is content-addressed as in chapter 3, this is visible: the hash of a historical partition changed, and anything pinned to the old hash still resolves to the old data. Without that, the only record of what last quarter actually looked like was the number in a slide.

    JUDGEMENT

    Five questions about an orchestration setup

  6. What is the critical path, and how long is it? If nobody has computed it, the cluster is probably sized by feel. Here 196 minutes of work floors at 135.
  7. Which task would you speed up? If the answer is the biggest one rather than one on the path, the effort may return exactly nothing.
  8. Are the failures independent? Retries assume they are. At one in five being an outage, the policy stalls at 79.1%.
  9. Does the retry window outlast a typical outage? Three retries with backoff spanned 12.8 minutes against a 20-minute outage and bought nothing.
  10. What alerts if nothing runs at all? A task-level alert cannot fire on a task that never started.
