Model registry and promotion

A registry is a small idea with two jobs: one authoritative answer to "what is in production", and a gate between a training run and real traffic. The gate is where the value is, because an automated retraining loop without one is an automated way to deploy a broken model.

Should this candidate be promoted? A candidate arrives from the pipeline. Six gates decide, and the interesting cases pass some and fail others.

Compare against the live model, not against a fixed number

An absolute threshold — "promote if AUC > 0.85" — decays into meaninglessness, because the achievable score moves with the data. A hard season makes 0.84 excellent; an easy quarter makes 0.87 a regression. The gate that stays correct is relative: the candidate must beat the currently-deployed model on the same held-out data, evaluated in the same run. That requires the registry to know which version is live and the evaluation step to score both — a small amount of plumbing that turns promotion from a judgement into a comparison. It also gives you the number that matters for the deployment decision in chapter 12: not "is this good" but "is this better, and by how much relative to the noise".

registering with enough metadata to be useful
import mlflow
from mlflow.tracking import MlflowClient

client = MlflowClient()

# 1. REGISTER the artefact produced by a tracked run. The link back to the
#    run is the whole point — a registered model with no run is an orphan.
mv = mlflow.register_model(
    model_uri=f"runs:/{run_id}/model",
    name="churn-classifier",
)

# 2. ATTACH THE METADATA THAT MAKES IT DECIDABLE LATER
client.set_model_version_tag(mv.name, mv.version, "data_snapshot", snapshot_path)
client.set_model_version_tag(mv.name, mv.version, "data_sha256", data_hash)
client.set_model_version_tag(mv.name, mv.version, "git_commit", commit)
client.set_model_version_tag(mv.name, mv.version, "test_auc", f"{auc:.4f}")
client.set_model_version_tag(mv.name, mv.version, "worst_slice", worst_slice)
client.set_model_version_tag(mv.name, mv.version, "feature_set", feature_hash)
client.set_model_version_tag(mv.name, mv.version, "trained_by", who)

client.update_model_version(mv.name, mv.version, description=(
    "Adds tenure_bucket and support_ticket_rate. Chosen over run 412 "
    "because recall at the 0.4 operating point is +3.1pp despite lower AUC."
))

# 3. ALIASES rather than stages. MLflow deprecated the fixed
#    None/Staging/Production stages in favour of aliases, which are just
#    named pointers — and they are strictly better, because you can have
#    as many as you need:
client.set_registered_model_alias("churn-classifier", "champion", mv.version)
client.set_registered_model_alias("churn-classifier", "challenger", "41")
client.set_registered_model_alias("churn-classifier", "eu-champion", "39")

# 4. SERVING RESOLVES THE ALIAS, never a version number
model = mlflow.pyfunc.load_model("models:/churn-classifier@champion")

# THAT LAST POINT IS THE IMPORTANT ONE. A service that loads version 42 by
# number must be redeployed to change models. A service that loads
# @champion changes model by moving a pointer — which makes rollback a
# registry operation rather than a deployment, and takes seconds.
#
# The same argument as reading through a database alias, and the same
# payoff: the thing you will want to do in a hurry becomes cheap.

# ROLLBACK, therefore:
client.set_registered_model_alias("churn-classifier", "champion", "41")

What the registry has to answer

QuestionNeeds recorded
What is serving production traffic right now?An alias, resolved at load time
What was serving traffic last Tuesday?An audit log of alias changes, with timestamps
Which run produced this version?The run id — non-negotiable
What data trained it?Data snapshot, hash and row count (chapter 3)
Which features does it expect?A signature, or a feature-set hash
Why was it promoted over the previous one?A description someone wrote
Who approved it?An approval record, if you have a gate
Can we go back?The previous artefact still present, and known-good
Rollback needs a known-good version, which is not the same as a previous one

Registries keep every version, so people assume rollback is solved. Two things routinely break it. The previous model may not be loadable — it was pickled with a library version no longer in the serving image, and unpickling raises. That is why the environment belongs in the registry entry and why a periodic "can we still load version N-1?" check is worth automating. And the previous model may be stale in a way that matters: if it was trained on data from six months ago and the world has moved, rolling back trades a broken model for an obsolete one. Keeping the previous version retrained on current data as a standing fallback is more work and is what "rollback" actually requires for a model that decays.

Automating promotion

the gate as code, which is where it belongs
def promotion_gates(candidate: Metrics, live: Metrics, cfg) -> list[str]:
    """Returns the list of failures. Empty list means promote."""
    fails = []

    # RELATIVE, not absolute
    if candidate.auc < live.auc - cfg.tolerance:
        fails.append(f"auc regression: {candidate.auc:.4f} vs {live.auc:.4f}")

    # NO SLICE MAY REGRESS MATERIALLY, even if the aggregate improves.
    # This is the gate that catches the model that is better overall and
    # much worse for one segment (chapter 10)
    for name in cfg.protected_slices:
        if candidate.slice[name] < live.slice[name] - cfg.slice_tolerance:
            fails.append(f"slice {name} regressed")

    # OPERATIONAL, not statistical
    if candidate.p99_latency_ms > cfg.latency_budget_ms:
        fails.append(f"p99 {candidate.p99_latency_ms}ms over budget")
    if candidate.artifact_mb > cfg.max_artifact_mb:
        fails.append("artefact too large for the serving image")

    # SANITY — a suspiciously large jump is usually a leak, not a triumph
    if candidate.auc > live.auc + cfg.suspicious_gain:
        fails.append("improvement too large; check for leakage")

    # PROVENANCE — refuse to promote what you cannot reproduce
    for field in ("git_commit", "data_snapshot", "data_sha256", "seed"):
        if not candidate.tags.get(field):
            fails.append(f"missing provenance: {field}")

    # BEHAVIOURAL TESTS must pass (chapter 10)
    if candidate.behavioural_failures:
        fails.append(f"{len(candidate.behavioural_failures)} behavioural tests failed")

    return fails

# THE SUSPICIOUS-GAIN GATE deserves attention because it is unusual and it
# earns its place. A candidate that beats the live model by ten points is
# far more likely to have a target leak, a broken split or a
# point-in-time bug (chapter 5) than to be a genuine breakthrough. Making
# that require human review has caught real bugs before deployment, and it
# costs nothing when the improvement is real.

# WHERE THE GATE RUNS: in the pipeline, after evaluation, before
# registration — or as a CI check on a promotion request. Either way it is
# code in version control, reviewed like code, not a checklist in a wiki.

FIVE LINKS. Four of them are a single recorded field, and the whole chain is
the difference between "we think it was trained on Q4 data" and a factual
answer.

WHAT IT LETS YOU DO, concretely:

  * a customer disputes a decision -> find the model, the training data, and
    the feature values used for that specific prediction (chapter 17)
  * a data bug is found -> list every model version trained on the affected
    snapshot, and therefore every model needing a retrain
  * a model behaves oddly for one segment -> check whether that segment was
    represented in its training snapshot
  * a privacy erasure request -> identify which models saw that person's
    data

THE LINK PEOPLE MISS is the first one. A prediction log without a model
version is nearly useless for debugging, because you cannot tell which
model made which prediction — and during a rollout there are two models
serving simultaneously by design (chapter 12). One field.

THE DIRECTION PEOPLE MISS is forward: given a source column, which models
depend on it? That needs the feature definitions to be in one place in code
so the question is a grep, plus a record of which feature set each model
version used. It is the "undeclared consumers" debt from chapter 1, and the
cheap version is a feature-set hash on every registered model.
A bucket and a pointer is a registry

If you have one model and no registry, you do not need to adopt a platform to get most of the benefit. Versioned artefacts in object storage — s3://models/churn/42/model.pkl — a JSON file alongside each one holding the run id, data snapshot, metrics and environment, and a single current pointer that serving reads. That has the four properties that matter: versions are immutable, there is one authoritative answer to what is live, rollback is moving a pointer, and every version carries its provenance. It is an afternoon of work, and adopting MLflow later is straightforward because you already have the metadata the registry wants. What is not straightforward is retrofitting provenance onto artefacts that were saved without it.

The short version

  1. Two jobs: one authoritative answer to what is live, and a gate before real traffic. The gate is where the value is.
  2. Compare against the live model, not a fixed threshold. Absolute thresholds decay as the achievable score moves.
  3. Serving resolves an alias, never a version number. That makes rollback a pointer move rather than a deployment.
  4. Gate on slices as well as aggregates, or you promote a model that is better overall and worse for a segment.
  5. Gate on provenance. Refuse to promote a model you could not reproduce.
  6. Flag suspiciously large improvements. Ten points is usually a leak, not a breakthrough.
  7. Rollback needs a known-good version — loadable in the current image, and not so stale that it is obsolete.
  8. Lineage is five links, four of them one field each. The one people miss is a model version in the prediction log.
