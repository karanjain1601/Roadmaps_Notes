Evaluating and testing models

A single number cannot tell you whether a model is fit to deploy, because averaging is exactly the operation that hides a concentrated failure. The evaluation that catches real problems is broken down by segment, checked for specific behaviours, and applied to the pipeline as well as the model.

Define your slices before you need them, and log them from run one

The slices worth tracking are known in advance and are almost always the same categories: protected attributes where a disparity is a legal and ethical problem; commercially important segments — enterprise accounts, high-value customers — which are usually small and therefore invisible in an average; data-quality cohorts, such as rows with missing optional fields, where the model behaves differently for mechanical reasons; new versus established entities, where a cold-start segment can be arbitrarily bad; and geography, language and platform. Ten to twenty slices, defined once, logged with every run (chapter 7). The value is in the history — after an incident you want to know whether a segment has been degrading for three months, and that answer only exists if you were recording it then.

slices, with the statistics that keep you honest
SLICES = {
    "enterprise":     lambda df: df.plan == "enterprise",
    "new_customer":   lambda df: df.tenure_days < 30,
    "missing_income": lambda df: df.income.isna(),
    "mobile":         lambda df: df.platform == "mobile",
    "region_apac":    lambda df: df.region == "APAC",
    "high_value":     lambda df: df.ltv > df.ltv.quantile(0.95),
}

def evaluate_slices(y, p, df, min_n=200):
    rows = []
    for name, mask_fn in SLICES.items():
        m = mask_fn(df).values
        n = int(m.sum())
        if n < min_n:
            rows.append(dict(slice=name, n=n, auc=None,
                             note="too small to measure"))
            continue
        auc = roc_auc_score(y[m], p[m])
        # bootstrap a confidence interval — a point estimate on 300 rows
        # invites conclusions it cannot support
        boots = [roc_auc_score(*resample(y[m], p[m])) for _ in range(200)]
        lo, hi = np.percentile(boots, [2.5, 97.5])
        rows.append(dict(slice=name, n=n, auc=auc, ci_lo=lo, ci_hi=hi,
                         positives=int(y[m].sum())))
    return pd.DataFrame(rows)

# THREE THINGS THAT MAKE SLICE METRICS MISLEADING, all avoidable:
#
#   1. NO SAMPLE SIZE SHOWN. An AUC of 0.61 on 40 rows and one of 0.61 on
#      40,000 warrant completely different responses, and a bare table of
#      numbers makes them look identical
#
#   2. NO CONFIDENCE INTERVAL. On a small slice the interval is enormous —
#      [0.48, 0.79] is not a finding. Bootstrap it and show it
#
#   3. NO POSITIVE COUNT. AUC on a slice with three positive examples is
#      essentially meaningless whatever the row count, and this is the
#      commonest version of the mistake

# AUTOMATED SLICE DISCOVERY finds the segments you did not think of, by
# searching for feature-value combinations where the loss is unusually
# high. SliceFinder and the "sliced-based learning" literature cover this;
# Fairlearn and Evidently both provide practical implementations.
# Worth running periodically — it surfaces things like "loss is 3x higher
# for rows where currency is JPY and channel is affiliate", which no
# predefined slice list contains.

Behavioural tests

assertions about behaviour, not about metrics
# Metrics tell you the model is 87% right. Behavioural tests assert things
# that must be true regardless of the metric, and they fail loudly.
# The taxonomy is from Ribeiro et al.'s CheckList work.

# 1. INVARIANCE — a change that should not affect the prediction, does not
def test_irrelevant_field_invariance(model, row):
    a = model.predict(row)
    b = model.predict(row.assign(marketing_source="email"))
    assert abs(a - b) < 0.01, "marketing_source should not move the score"

def test_name_invariance(model, row):
    # for a credit model, the applicant's name must not matter
    for name in ["Smith", "Okafor", "Nguyen", "Kowalski"]:
        assert abs(model.predict(row.assign(surname=name)) - baseline) < 0.01

# 2. DIRECTIONAL — a change should move the prediction a known way
def test_income_directional(model, row):
    low  = model.predict(row.assign(income=20_000))
    high = model.predict(row.assign(income=200_000))
    assert high < low, "higher income should not increase default risk"

# 3. MINIMUM FUNCTIONALITY — the easy cases must be right
def test_obvious_fraud(model):
    assert model.predict(KNOWN_FRAUD_PATTERN) > 0.9

def test_obvious_legitimate(model):
    assert model.predict(LONG_STANDING_GOOD_CUSTOMER) < 0.1

# 4. ROBUSTNESS — small perturbations do not flip the answer
def test_rounding_robustness(model, row):
    a = model.predict(row.assign(amount=100.00))
    b = model.predict(row.assign(amount=100.01))
    assert abs(a - b) < 0.05

# 5. EDGE CASES — the inputs that break serving rather than the model
@pytest.mark.parametrize("row", [ALL_NULLS, ZERO_ROW, MAX_VALUES,
                                 UNSEEN_CATEGORY, EMPTY_STRING])
def test_no_crash(model, row):
    p = model.predict(row)
    assert 0.0 <= p <= 1.0 and not math.isnan(p)

# WHY THESE ARE WORTH MORE THAN THEY LOOK: they encode knowledge that no
# metric contains. "Higher income should not increase default risk" is a
# fact about the world, and a model that violates it has learned something
# spurious — which an AUC of 0.87 will not tell you.
#
# They also survive retraining. A metric threshold has to be re-tuned as
# the data moves; "the surname must not matter" is true forever, so these
# tests accumulate value rather than decaying.
#
# WRITE ONE EVERY TIME SOMETHING GOES WRONG. That is the discipline that
# builds a real suite — the same habit as a regression test after a bug.
Compare against a trivial baseline, always

Before any of the above, establish what a model with no intelligence achieves: predict the majority class, predict the historical average, predict "same as last week", or use the single most predictive feature with a threshold. This is skipped constantly and it is embarrassing when it turns out to matter. An 87% accurate classifier on a problem with 86% base rate has learned almost nothing, and a churn model that barely beats "flag anyone who has not logged in for 30 days" is not worth the pipeline that produces it. Log the baseline as a metric in every run so the comparison is permanently visible rather than something someone did once at the start. It also gives you the honest denominator for the business case — the value of the model is the lift over the trivial rule, not its absolute performance.

two tests that catch a surprising amount
# 1. OVERFIT A TINY SAMPLE ON PURPOSE. If the model cannot memorise twenty
#    rows, something is structurally broken — the labels are misaligned, the
#    features are constant, the learning rate is zero, the loss is wired to
#    the wrong output.
def test_can_overfit_small_sample():
    tiny = train_df.sample(20, random_state=0)
    model = train(tiny, tiny, cfg | {"epochs": 200, "regularisation": 0})
    assert accuracy(model, tiny) > 0.95, "cannot fit 20 rows — check wiring"
#    Runs in seconds and catches the class of bug that otherwise presents as
#    "the model just does not learn very well".

# 2. SERIALISATION ROUND-TRIP. Save the model, load it in a fresh process,
#    and assert identical predictions on a fixed sample.
def test_roundtrip_identical(tmp_path):
    p1 = model.predict(SAMPLE)
    save(model, tmp_path / "m.pkl")
    p2 = load(tmp_path / "m.pkl").predict(SAMPLE)
    np.testing.assert_allclose(p1, p2, rtol=1e-6)
#    Catches: custom transformers that do not pickle their fitted state,
#    a preprocessing step applied in training and forgotten at load time,
#    library version differences between environments, and lambdas in a
#    pipeline that silently fail to serialise. All of these produce a model
#    that scores well in training and behaves differently once deployed —
#    which is chapter 14, caught cheaply here instead.

# AND THE ONE THING NOT TO DO: assert an absolute metric threshold in a unit
# test.
#     assert auc > 0.85          # <- will break for the wrong reasons
# The achievable score moves with the data, so this test fails when the
# world changes rather than when the code breaks, and it gets muted. Assert
# RELATIVE performance at promotion time instead (chapter 9), and keep unit
# tests for things that are true regardless of the data.
Do error analysis by reading the predictions

The highest-value hour in any modelling project is usually spent pulling the two hundred worst-scored examples into a notebook and reading them. Not computing a metric on them — reading them. The failures cluster, and the clusters are informative in a way no aggregate is: half of them turn out to have a null in the same field, or to be from one country, or to be duplicates, or to be mislabelled in the training data, or to be a category the feature encoding handles badly. Each of those is a specific fixable cause, and each one becomes a new slice to track and a behavioural test to add. Teams that do this routinely find data problems; teams that only look at metrics find that the model "needs more tuning". It is the one activity in this unit that is genuinely better done in a notebook (chapter 8).

The short version

  1. Averaging is the operation that hides a concentrated failure. Evaluate by slice or you cannot see it.
  2. Define ten to twenty slices in advance and log them from the first run. The value is in the history.
  3. Show sample size, positive count and a confidence interval alongside every slice metric.
  4. Behavioural tests encode knowledge no metric contains, and they survive retraining rather than needing re-tuning.
  5. Write a behavioural test every time something goes wrong. Same habit as a regression test.
  6. Always compare against a trivial baseline, and log it. The model's value is the lift, not the absolute number.
  7. Test that the model can overfit twenty rows, and that it survives a save-and-reload round trip.
  8. Never assert an absolute metric in a unit test. It fails when the world changes and gets muted.
