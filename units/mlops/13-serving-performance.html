Chapter 13 · Serving

Latency, throughput and cost

Inference cost is arithmetic, and doing the arithmetic before building is what separates a viable feature from one cancelled after the first bill. The levers are few and their effects are large — often an order of magnitude between a naive deployment and a considered one.

Batching trades latency for throughput, and the exchange rate is very good

A model processing one request at a time leaves most of the hardware idle — particularly a GPU, which is built for parallel work and spends a single small inference mostly on overhead. Dynamic batching holds arriving requests for a few milliseconds and processes them together, so throughput per instance rises by close to the batch size while each request pays only the waiting window. Ten milliseconds of added latency for an eightfold throughput increase is a trade almost any online workload should take, and it is a configuration flag in every serious model server. The exception is a workload where the latency budget is genuinely single-digit milliseconds, in which case the window itself is unaffordable and you are choosing hardware instead.

the levers, in the order to try them
1. DO NOT SERVE ONLINE AT ALL. Precompute if you can (chapter 11). This is
   an infinite speedup and it is skipped because it feels like cheating.

2. CACHE. If the same entity is scored repeatedly with unchanged features,
   cache the score with a short TTL. On many workloads the request
   distribution is heavily skewed and a small cache absorbs most of it.

3. DYNAMIC BATCHING. A configuration flag. Largest single win for GPU
   serving and a real one on CPU too.
     Triton: dynamic_batching { max_queue_delay_microseconds: 5000 }

4. QUANTISATION. Weights in int8 instead of fp32.
     * ~4x smaller, ~2-4x faster, and quality loss is usually small
     * POST-TRAINING quantisation needs no retraining and is a few lines
     * QUANTISATION-AWARE TRAINING recovers more quality and costs a
       training run
     * always MEASURE the quality change on your slices (chapter 10) —
       quantisation damage is frequently concentrated in a segment rather
       than spread evenly, which an aggregate metric hides

5. A FASTER RUNTIME. Exporting to ONNX Runtime, TensorRT or OpenVINO
   commonly gives 2-5x over a naive framework call, with no change to the
   model. Verify numerical parity after conversion — the export can alter
   results slightly and occasionally more than slightly.

6. A SMALLER MODEL. Distillation, pruning, or simply a smaller
   architecture. Often the largest win and the one requiring most work.
     * and worth checking first whether you need the big model at all:
       measure a gradient-boosted tree against the transformer before
       assuming the transformer is required

7. BETTER HARDWARE. Last, because it is the only lever that increases the
   bill rather than reducing it.

TWO THINGS TO MEASURE BEFORE OPTIMISING ANYTHING:

  GPU UTILISATION. nvidia-smi during load. A "GPU-bound" service at 20%
  utilisation is not GPU-bound — it is bound by the data path, the
  preprocessing, or the request-at-a-time serving pattern. Optimising the
  model would achieve nothing.

  WHERE THE TIME GOES. Break the request down: network, feature lookup,
  preprocessing, inference, postprocessing, logging. On a great many
  services the model is a minority of the total, and on those the useful
  work is in feature lookup — which is chapter 5's territory, not this
  chapter's.

Feature lookup is often the largest term, and it is the one nobody profiles

A model that infers in 8 ms and fetches twelve features with twelve sequential round trips to a feature store is a 60 ms service, and every optimisation effort aimed at the model is wasted. Three fixes, in order of value: issue the lookups as one batched request rather than a loop — the same argument as pipelining in a database; cache the features that change slowly, which is most of them, since a feature aggregating thirty days of history does not change within an hour; and if the online store is in another availability zone, move it. Profile the request breakdown before touching the model. This is the single most common misdiagnosis in ML serving performance.

Batch inference cost

a different and simpler calculation
  entities × seconds per entity ÷ parallelism = wall clock
  wall clock × instance rate × instances      = cost per run
  cost per run × runs per month               = the bill

  10 million entities, 0.4 ms each, 16-way parallel
    = 10e6 × 0.0004 / 16 = 250 seconds of compute
    = 4 minutes on 16 cores. Pennies.

THE POINT OF WRITING THAT OUT: batch inference is almost always cheap, and
dramatically cheaper than the online equivalent for the same number of
predictions — because you pay for the compute you use rather than for
capacity sitting idle waiting for peak traffic.

An online service sized for 200 requests per second at peak is provisioned
for peak all day. A batch job scoring the same population once a night uses
four minutes of compute. That is the cost argument for chapter 11's
question, and it is usually a factor of ten or more.

THREE WAYS TO MAKE BATCH INFERENCE CHEAPER STILL:

  SPOT INSTANCES. A batch job is interruptible by nature — checkpoint the
  partitions completed and resume. 60-90% discount, and the risk is a
  delayed run rather than a failed request.

  SCORE ONLY WHAT CHANGED. Most entities' features are identical to
  yesterday's, so their score will be too. Score the delta and carry the
  rest forward. On a large population this is often a 90% reduction, and it
  requires only a change-detection query.

  RIGHT-SIZE THE HARDWARE. Batch inference on a GPU is frequently slower
  per pound than on CPU for tree models and small networks, because the
  data transfer dominates. Measure rather than assume the GPU helps.

AND THE TRAINING COST, since it belongs somewhere: for most teams training
is a smaller line than serving, because it runs occasionally. It becomes
the larger line when hyperparameter search is unbounded — a hundred trials
on a GPU is a real number, and chapter 8's pruning and sampling advice is
partly a cost argument.
Set the latency budget before choosing the model

The sequence that wastes months: build the best model, then discover it cannot be served within the product's latency budget, then spend a quarter optimising it, then ship something worse than the simple model you could have had immediately. The budget is a design constraint, not a downstream problem — establish what the product can tolerate end to end, subtract the network, feature lookup and preprocessing, and what remains is the inference budget. Then evaluate candidate models against that constraint from the first experiment, logging p99 latency in the serving image alongside the accuracy metric (chapter 7). A model that scores 0.89 in 200 ms and one that scores 0.87 in 15 ms are not comparable until the budget tells you which is deployable, and the second is frequently the better product.

The short version

  1. Do the arithmetic before building. Requests, milliseconds and instance rate give you the bill.
  2. Batching trades a few ms of latency for near-linear throughput. Take that trade unless the budget is single-digit ms.
  3. Precompute if you can. An infinite speedup, and usually a factor of ten on cost (chapter 11).
  4. Measure GPU utilisation first. A "GPU-bound" service at 20% utilisation is bound by something else.
  5. Feature lookup is often the largest term and the one nobody profiles. Batch the lookups and cache.
  6. Quantisation is cheap and its damage is concentrated. Always check the per-slice effect, not the aggregate.
  7. Batch inference: spot instances, score only what changed, and check whether the GPU is actually helping.
  8. Set the latency budget before choosing the model, and log p99 alongside accuracy from the first experiment.
