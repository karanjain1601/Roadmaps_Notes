The infrastructure chapter of an MLOps unit is mostly a chapter about restraint. Nearly every capability here is available managed, the self-hosted version costs a person, and the useful question about each piece is what specific problem it solves that you currently have.

A self-hosted component costs a fraction of an engineer, permanently

The comparison people make is the managed service's bill against zero, because the self-hosted version runs on infrastructure already being paid for. The comparison that matters includes upgrades, backups, certificate rotation, capacity, the database behind it, the incident at 2am, and the fact that whoever set it up will eventually leave. A conservative figure is 5–15% of an engineer per self-hosted component, forever — which at any realistic salary exceeds the subscription for most things on this page. The exceptions are real: an existing platform team whose job this already is, data residency requirements, an air-gapped environment, or a regulatory constraint. "We could run it ourselves" is almost always true and almost never the question.

Kubernetes, and whether you need it

what it gives ML workloads, and what it costs
WHAT IT GENUINELY GIVES YOU:
  * heterogeneous resources — this pod needs a GPU, that one needs 64 GB
  * bin-packing many small models onto shared nodes, which matters at
    twenty models and not at one
  * a scheduler for training jobs with priorities and preemption
  * one deployment story for services, batch jobs and cron
  * an ecosystem: Kubeflow, KServe, Ray, Argo, Volcano, Kueue

WHAT IT COSTS:
  * a real platform skill set, or a managed control plane and someone who
    understands it anyway
  * GPU scheduling is genuinely awkward — device plugins, drivers, node
    taints, and a default scheduler that will happily start a job needing
    four GPUs when three are free
  * debugging a failed training pod through several layers of abstraction
  * a great deal of YAML

CLEARLY YES: your organisation already runs Kubernetes and has people who
operate it. ML workloads become one more tenant, and declining means
building a parallel deployment story nobody else understands.

CLEARLY NO: one model, a small team, no existing cluster. A managed
endpoint plus a scheduled job on Cloud Run, Lambda, Batch or equivalent
does the entire job. Adopting Kubernetes to serve one model is a
well-documented way to spend a quarter on platform work.

THE MIDDLE — several models, some GPU work, no cluster: a managed serving
product plus managed batch, or Ray on managed compute, or a small managed
cluster with KServe. The deciding question is whether anyone will OWN the
cluster. An unowned Kubernetes cluster degrades in ways that are hard to
recover from, and "the ML team" is not an owner.

IF YOU DO RUN IT, the ML-specific settings that matter:
  * resource requests AND limits on every pod, or one training job takes
    the node down with it
  * node taints and tolerations so CPU work never lands on GPU nodes —
    an idle GPU is the most expensive thing in the cluster
  * a gang scheduler (Volcano, Kueue) for multi-GPU jobs, so a job needing
    four GPUs waits for four rather than deadlocking holding three
  * generous terminationGracePeriodSeconds on training pods, so a
    checkpoint can finish before the pod is killed
  * PodDisruptionBudgets on serving, so a node drain does not remove every
    replica at once
  * ephemeral-storage requests, because a training pod that fills the node
    disk evicts its neighbours

GPUs

the most expensive resource, and how it is wasted
THE THREE WAYS GPU MONEY DISAPPEARS:

  1. IDLE. A reserved GPU instance costs the same whether it is computing
     or waiting. A development notebook attached to an A100 overnight is
     the canonical version, and it is extremely common.
       -> idle-shutdown policies on notebooks, non-negotiable
       -> separate development GPUs (small, cheap) from training GPUs

  2. UNDER-UTILISED. A GPU at 15% utilisation costs full price. The cause
     is almost never the model — it is the data path, the preprocessing, or
     serving one request at a time (chapters 8 and 13).
       -> measure with nvidia-smi or DCGM before optimising anything
       -> more dataloader workers, prefetching, and data local to the node

  3. WRONG SIZE. An A100 running a model that fits comfortably on a T4 is
     paying six times the rate for the same result. And in the other
     direction, a job that barely fits and spills is far slower than one
     that fits with headroom.
       -> profile memory use, then pick the smallest device that fits

TWO MECHANISMS FOR SHARING, both worth knowing:
  MIG (Multi-Instance GPU) partitions an A100 or H100 into hardware-
    isolated slices. Real isolation, fixed partition sizes.
  TIME-SLICING lets several pods share one GPU without isolation. Fine for
    development and inference of small models; a job that exhausts memory
    takes its neighbours down with it.

SPOT AND PREEMPTIBLE INSTANCES are 60-90% cheaper and can be reclaimed at
any moment. That is a bad fit for a serving endpoint and an excellent fit
for training, IF checkpointing works:
  * checkpoint frequently, and completely — weights, optimiser state,
    scheduler, dataloader position, RNG state (chapter 8)
  * TEST RESUMPTION by killing a job deliberately on the second day. A
    checkpoint that restores weights but not optimiser state silently
    restarts your training dynamics, and the job "completes" wrong
  * handle the preemption signal to force a final checkpoint

  For batch inference spot is close to free money: the work is
  partitioned and idempotent already (chapter 4), so an interruption
  costs one partition's worth of recomputation.

THE OTHER LEVER, and it is large: committed-use discounts or reserved
instances for the baseline, on-demand or spot for the peak. Most ML
platforms have a very stable floor and a spiky top, which is exactly the
shape that arrangement is priced for.
Tag everything, or you will not be able to explain the bill

An ML platform's cost is dominated by a small number of large items — GPU hours and object storage — and both are usually attributable to specific models, teams and experiments. Without tags the bill is one number and every conversation about reducing it is speculation. Tag every resource with the model, the team, the environment and whether it is training or serving, enforce it in your infrastructure code so an untagged resource fails to provision, and produce a monthly breakdown per model. The result is usually surprising: a model nobody uses running an expensive endpoint, a hyperparameter sweep that never finished but is still charging, six months of intermediate pipeline artefacts in standard storage. Every one of those is found by a report and invisible without one.

Infrastructure as code

the ML-specific parts
Everything the DevOps and Terraform units say applies unchanged: version
the infrastructure, plan before apply, keep state remote and locked, and
never click in a console for anything that matters. Four things are
specific to ML.

  1. GPU QUOTAS ARE THE THING THAT BLOCKS YOU. Cloud GPU quotas are
     per-region, per-family, and frequently zero by default. Request them
     weeks before you need them, and record the request in your
     infrastructure repository so a new environment does not discover the
     problem on its first training run.

  2. STORAGE LIFECYCLE POLICIES MATTER MORE THAN USUAL. ML generates
     enormous quantities of intermediate artefacts — checkpoints, cached
     features, per-trial outputs — and they are all in standard storage by
     default. A lifecycle rule that moves objects older than 30 days to
     infrequent access and deletes intermediate paths after 90 is often
     the single largest cost saving available.
       * but exempt the things you must keep: data snapshots referenced by
         registered models (chapter 3) and the artefacts of production
         model versions. Deleting those destroys reproducibility
         retroactively, and you will not notice until you need them.

  3. THE ENVIRONMENT IS PART OF THE MODEL. Chapter 3's point, expressed as
     infrastructure: the container image digest is an artefact to be
     versioned alongside the code that builds it, and the serving image
     should be built from a separate minimal lockfile (chapter 11).

  4. SECRETS AND DATA ACCESS. A training job usually needs read access to
     production data, which is a broader grant than most services get.
     Scope it to specific tables, use workload identity rather than
     long-lived keys, and log the access — this is where governance and
     infrastructure meet (chapter 17).

WHAT NOT TO CODIFY EARLY: a full multi-environment, multi-region,
multi-account Terraform estate for a two-person ML team. One environment
in code, reproducibly, beats three environments that drifted apart.
The cheapest infrastructure decision is deleting things

ML platforms accumulate. Endpoints for models that were replaced but never undeployed. Notebook instances belonging to people who left. Experiment artefacts from a sweep in March. Feature tables built for a project that was cancelled. Every one costs money monthly and nobody is responsible for noticing. A quarterly audit — list every endpoint, every notebook instance, every scheduled job, and every storage prefix over some size, and require an owner for each — routinely removes 20–40% of an ML platform's bill in its first pass. It also finds correctness problems: an endpoint still serving an old model version that some forgotten caller depends on, which is exactly chapter 1's undeclared-consumer debt showing up as a line item. Put it in a calendar.

The short version

  1. Self-hosting costs 5–15% of an engineer per component, permanently. Compare against that, not against zero.
  2. Adopt Kubernetes if your organisation already runs it, and not to serve one model.
  3. An unowned cluster degrades badly. "The ML team" is not an owner.
  4. Taint GPU nodes so CPU work never lands there. An idle GPU is the most expensive thing you own.
  5. Measure utilisation before optimising. A GPU at 15% is bound by the data path, not the model.
  6. Spot for training and batch inference, never for serving — and test resumption by killing a job deliberately.
  7. Tag everything and produce a per-model bill. The findings are always surprising and always actionable.
  8. Storage lifecycle rules are often the largest saving — but exempt data snapshots that registered models depend on.
