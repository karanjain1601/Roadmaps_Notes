Chapter 03 · The problem

Reproducibility

Everything else in this unit rests on being able to say: given this model, here is exactly what produced it. Four things have to be pinned for that to be true, most teams pin one, and the gap does not become visible until the moment it is expensive.

Data is the one that gets skipped, and it is the one that matters most

Everybody versions code, because git exists and the habit is universal. Almost nobody versions data, because it is large, it lives in a warehouse someone else owns, and there is no obvious tool — so the training script contains SELECT * FROM customers WHERE signup_date < '2026-01-01' and that is considered a data reference. It is not. That query returns different rows every time you run it: late-arriving records, corrections, deletions for privacy requests, a backfill somebody ran, a column whose meaning changed. Six months later the same commit and the same query produce a materially different model, and the difference is invisible because both runs look identical in the log. Pinning data is the difference between a record of results and the ability to recreate them.

Pinning data, in practice

four approaches, roughly in order of cost
# 1. SNAPSHOT TO IMMUTABLE STORAGE. The simplest thing that works.
#    The training pipeline's first step writes the exact rows it used, to a
#    path that includes a run id, and never touches it again.
snapshot_path = f"s3://ml-data/training/{run_id}/train.parquet"
df.to_parquet(snapshot_path)
mlflow.log_param("data_snapshot", snapshot_path)
mlflow.log_param("data_rows", len(df))
mlflow.log_param("data_sha256", hashlib.sha256(pq_bytes).hexdigest())
#    Cheap, obvious, works on day one. Costs storage, which is the cheapest
#    thing in the stack. For most teams this is the right answer and the
#    fancier options are not an improvement.

# 2. A TABLE FORMAT WITH TIME TRAVEL. If your warehouse supports it, the
#    snapshot already exists and you just record which one.
#    Iceberg / Delta / Hudi:
spark.read.option("versionAsOf", 41).table("silver.customers")     # Delta
spark.read.option("snapshot-id", 8492...).table("db.customers")    # Iceberg
#    BigQuery, Snowflake and others have their own time-travel syntax with a
#    retention window — check the window, because it is often 7 or 30 days
#    and a model you need to reproduce in a year is outside it.

# 3. DVC — git-like versioning for large files, with the pointer in git and
#    the bytes in object storage.
#    dvc add data/train.parquet     -> creates data/train.parquet.dvc
#    git add data/train.parquet.dvc && git commit
#    dvc push
#    Then `git checkout  && dvc pull` gives you the exact data for
#    that commit. Good when data lives in files and the team already thinks
#    in git. Less natural when the source of truth is a warehouse.

# 4. A FEATURE STORE with point-in-time retrieval (chapter 5). Solves this
#    as a side effect of solving a harder problem. Do not adopt one for this
#    reason alone.

# WHATEVER YOU CHOOSE, RECORD THREE THINGS with every run:
#   * the identifier — path, version number, snapshot id, or content hash
#   * the row count
#   * a checksum of the actual bytes
#
# The checksum is what catches the case the identifier misses: same query,
# same table version, different bytes because someone ran a correction. It
# costs one line and it is the difference between believing you can
# reproduce a run and knowing.

Determinism

the sources of run-to-run variation
import os, random, numpy as np, torch

SEED = 42
random.seed(SEED)
np.random.seed(SEED)
torch.manual_seed(SEED)
torch.cuda.manual_seed_all(SEED)
os.environ["PYTHONHASHSEED"] = str(SEED)          # must be set before start

# TRUE DETERMINISM ON GPU COSTS SPEED, and is opt-in:
torch.use_deterministic_algorithms(True)
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False            # benchmark picks the
                                                  # fastest kernel, which
                                                  # varies between runs
os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8" # required for some ops

# WHAT STILL VARIES even with all of that:
#
#   * FLOATING-POINT REDUCTION ORDER. Summing in parallel gives slightly
#     different results depending on which thread finished first, because
#     float addition is not associative. Multi-GPU and multi-worker training
#     are affected by construction
#   * DATALOADER WORKER ORDER, unless you seed the workers too:
#       DataLoader(..., worker_init_fn=lambda w: np.random.seed(SEED + w),
#                       generator=torch.Generator().manual_seed(SEED))
#   * NON-DETERMINISTIC KERNELS. Some operations have no deterministic
#     implementation; use_deterministic_algorithms(True) makes them RAISE
#     rather than silently vary, which is the behaviour you want
#   * DIFFERENT HARDWARE. The same code on an A100 and an H100 can produce
#     different weights. Reproducibility is per-architecture
#   * LIBRARY VERSION CHANGES that alter default behaviour or kernel choice

# THE HONEST POSITION: bit-for-bit reproducibility of a large model across
# machines is expensive and often not worth buying. What you actually need
# is usually weaker and entirely achievable:
#
#   STATISTICAL reproducibility — rerunning gives a metric within noise of
#   the original, and you know what that noise is because you measured it
#   by running the same config three times.
#
# Record the seed regardless. Without it you cannot distinguish "this change
# helped" from "this run got lucky", which is the most common false
# conclusion in applied ML and the reason so many reported improvements
# evaporate.
Two runs of the same config is the cheapest experiment you will ever run

Before comparing any two model configurations, run one configuration twice with different seeds and look at the spread in your metric. That number is your noise floor, and every improvement smaller than it is indistinguishable from luck. Teams that skip this step spend weeks chasing differences of 0.3% on a metric whose run-to-run variance is 0.8%, adopt changes that did nothing, and build a folklore of techniques that "work" — and the effect compounds, because each false conclusion becomes the baseline for the next comparison. It costs one extra training run and it invalidates a surprising fraction of the decisions a team has already made.

Environment and config

the boring half, which fails silently
# ENVIRONMENT. requirements.txt with ranges is not a pinned environment.
#   scikit-learn>=1.3        <- a different minor version can change
#                               defaults, solvers and results
# Use a lockfile that records the full transitive graph with hashes:
uv pip compile pyproject.toml -o requirements.lock     # uv
poetry lock                                            # poetry
pip-compile --generate-hashes                          # pip-tools
conda env export --no-builds > environment.yml         # conda

# AND PIN THE CONTAINER BY DIGEST, not by tag. Tags move.
FROM python:3.12-slim@sha256:8f2c...                   # immutable
# FROM python:3.12-slim                                <- a different image
#                                                         next month

# The system layer matters more than people expect: CUDA version, cuDNN,
# BLAS implementation, glibc. Those live in the base image, which is why the
# digest and not just the Python lockfile is what pins the environment.

# CONFIG. Hyperparameters, feature lists, thresholds, data ranges. This is
# ML's largest untested surface and it is routinely edited in place.
#   * put it in a file, in git, not in argparse defaults and not in the code
#   * one file per experiment, or a base plus overrides — Hydra, OmegaConf
#     and plain YAML all work
#   * log the RESOLVED config with the run, after overrides are applied.
#     Logging the base config and the override flags separately means
#     reconstructing what actually ran, and someone will get it wrong

# THE ONE-LINE TEST for whether your setup is real:

    Pick a model from three months ago. Retrain it from its recorded
    metadata alone. Is the metric within noise of the original?

# If you cannot start, you have a tracking system rather than a
# reproducibility system. If you get a materially different number, you have
# an unpinned artefact and now you know which one. Either way the answer is
# worth having before you need it during an incident.
What reproducibility buys, concretely

It is easy to treat this as hygiene rather than capability, so it is worth naming the things that become possible. Honest comparison — you can attribute a metric change to a specific cause instead of guessing. Rollback that works — the previous model can be rebuilt, not just redeployed, which matters when the artefact is corrupt or the format is stale. Debugging a bad prediction — you can find the rows that taught the model that. Regulatory answers — "what data trained the model that made this decision" has a factual answer (chapter 17). Retraining without fear — you can rerun the pipeline knowing you can get back to where you were, which is what makes the retraining loop in chapter 1 safe to automate. Every one of those is unavailable without it, which is why this chapter comes before the rest of the unit.

The short version

  1. Four artefacts must be pinned together: code, data, environment, config. Most teams pin only code.
  2. A SQL query is not a data version. Late arrivals, corrections and deletions change what it returns.
  3. Snapshot to immutable storage and record the path, the row count and a checksum of the bytes.
  4. Lockfiles, not version ranges, and pin the container by digest — the CUDA and BLAS layers matter.
  5. Log the resolved config, after overrides. Reconstructing it from base plus flags goes wrong.
  6. Set seeds always; buy bit-exactness rarely. Statistical reproducibility is what you actually need.
  7. Measure your noise floor by running one config twice. Improvements below it are luck.
  8. Test it: retrain a three-month-old model from its metadata. If you cannot start, you have tracking rather than reproducibility.
