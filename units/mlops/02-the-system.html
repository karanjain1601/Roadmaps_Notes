The model is not where the failures are

Ask anyone who has run ML in production where their incidents came from, and the answers cluster in two places: the data pipeline broke, or the features computed at serving time did not match the features computed at training time. Almost nobody says "the model architecture was wrong". That distribution should determine where you spend effort — and it is the opposite of how most people learn ML, where the model is the entire subject and the data is a CSV that arrives clean. Chapters 4 to 6 and chapter 14 are the ones that address the actual failure modes; the training chapters matter mostly because they are how you get reproducibility.

Two loops, not one

the inner and outer loops
THE INNER LOOP — experimentation. Fast, cheap, throwaway.

    idea -> notebook -> train on a sample -> look at a metric -> repeat

  Optimise for ITERATION SPEED. Small data samples, cached features,
  interactive. This loop runs dozens of times a day and most of its output
  is discarded. Making it rigorous makes it slow, and making it slow means
  fewer ideas get tried.

THE OUTER LOOP — production. Slow, expensive, permanent.

    pipeline -> full training run -> validation gates -> registry ->
    deploy -> monitor -> drift detected -> retrain

  Optimise for REPRODUCIBILITY AND SAFETY. Versioned everything, automated,
  audited. This loop runs weekly or monthly and every output is a candidate
  for real traffic.

THE HARD PART IS THE JOIN BETWEEN THEM, and it is where most MLOps effort
actually goes. A notebook that works is not a pipeline. Getting from one to
the other traditionally means a rewrite, and a rewrite means:

  * feature logic implemented twice, differently — chapter 14's skew
  * a result that cannot be reproduced, because the notebook's data is gone
  * a handoff, with the ownership problem from chapter 1

WHAT GOOD LOOKS LIKE: the same feature code runs in both loops. The notebook
imports the transformation functions the pipeline uses rather than
reimplementing them inline. That single discipline removes most of the
translation cost, and it is a code-organisation decision rather than a
platform one — you can do it on day one with a package and no tooling.

TWO THINGS THIS DIAGRAM GETS RIGHT that simpler ones miss:

  1. THE FEEDBACK EDGE from monitoring back to training. Without it there is
     no loop, and a model is a one-off artefact that decays (chapter 1).

  2. THE FEATURE SPLIT into offline and online. Every serious production ML
     failure story involves those two paths disagreeing (chapter 14).

AND ONE THING TO IGNORE: the vendor version of this diagram has a logo in
every box. Most boxes can start as a table, a script and a cron entry.
Batch and online are almost different products

The diagram looks the same for both and the engineering is not. Batch inference — score every customer nightly, write to a table — needs no serving infrastructure, no latency budget, no online feature store and no autoscaling; it is a pipeline that ends in a write, and a surprisingly large fraction of production ML is this. Online inference — score a request in 50 ms — needs all of it, plus the feature-parity problem, plus a rollback path, plus capacity planning. The instinct to build online serving because it sounds more real is expensive: if the prediction is consumed by a screen that a user opens hours later, batch is correct, cheaper, easier to monitor and easier to roll back. Ask whether the prediction is needed before the next batch run would produce it; if not, do not build a service.

The smallest complete system

It is worth knowing what a legitimately complete ML system looks like at the small end, because the reference diagrams make it seem impossible. A scheduled job that reads from your warehouse, computes features with a shared Python package, trains a model, logs the run to a tracking server, writes the model to object storage with a version, and a second job that loads the current version and writes predictions to a table — plus a third job that compares this week's input distributions to the training set and posts to Slack if they have moved. Three jobs, one shared package, one tracking server, one bucket. That is levels 2 to 3 on chapter 1's ladder, it covers reproducibility, deployment and drift, and it can be built in a fortnight by one person. Almost everything else in this unit is what you add when a specific thing about that arrangement starts hurting.

The short version

  1. The model is the smallest box. The system is ingestion, transformation, features, training, registry, serving, monitoring and orchestration.
  2. Incidents cluster in two places: the data pipeline broke, or serving features did not match training features.
  3. There are two loops — fast experimentation and slow production — and the join between them is where the work is.
  4. Share the feature code between loops. A code-organisation decision, available on day one, that removes most of the translation cost.
  5. Raw storage is the thing you cannot regenerate. Immutable, append-only, open format.
  6. The feedback edge from monitoring to training is what makes it a loop rather than a one-off artefact.
  7. Batch and online inference are almost different products. If the prediction can be precomputed, do not build a service.
  8. Never skip experiment tracking or input monitoring. Both are nearly free and both unlock everything else.
