Data pipelines and orchestration

This is where most ML incidents originate, and the reason is structural: a pipeline runs unattended, depends on things you do not control, and can produce wrong output while reporting success. Four properties fix most of it.

Idempotency is the property everything else depends on

A task is idempotent if running it twice produces the same result as running it once. That sounds like a nicety and it is the foundation of every operational capability you want: automatic retries are only safe if tasks are idempotent, backfills are only safe if tasks are idempotent, and recovering from a partial failure is only possible if you can rerun the failed step without reasoning about what it already did. The mechanism is almost always the same — make the write replace a partition rather than append rows, and key that partition on the logical time the run represents rather than on when it happened to execute. Everything else in this chapter is downstream of getting that one thing right.

Writing a task that can be rerun

the shape that survives retries and backfills
def build_daily_features(logical_date: date) -> None:
    """Idempotent: replaces exactly one partition, derived only from
    logical_date. Running it twice is the same as running it once."""

    # 1. READ A BOUNDED WINDOW, defined by the logical date — never now()
    src = read_events(start=logical_date, end=logical_date + timedelta(days=1))

    # 2. VALIDATE BEFORE WRITING. A failed check must stop the task, not
    #    produce a smaller output (chapter 6)
    assert len(src) > 0, f"no source rows for {logical_date}"
    validate_schema(src)

    out = transform(src)

    # 3. REPLACE THE PARTITION. Not append.
    path = f"s3://features/daily/dt={logical_date}/"
    write_parquet_atomic(out, path)     # temp path, then atomic rename

# THE THREE RULES IN THAT FUNCTION:
#
#   NO now() ANYWHERE. A task whose behaviour depends on wall-clock time
#   cannot be backfilled, because rerunning it for last Tuesday will read
#   today's data. Every date comes from the orchestrator's logical date.
#
#   NO APPEND. Appending means a retry duplicates rows, and duplicates in
#   training data are worse than missing rows — they silently reweight the
#   loss toward whatever was duplicated.
#
#   VALIDATE BEFORE WRITE, and fail loudly. A task that writes a partial
#   result and exits zero is the single worst pipeline behaviour, because
#   the orchestrator reports success and the model trains on it.

# ATOMICITY, since "delete then insert" has a window:
def write_parquet_atomic(df, final_path):
    tmp = final_path.rstrip("/") + ".tmp/"
    write(df, tmp)
    delete(final_path)          # <- crash HERE and the partition is gone
    move(tmp, final_path)
# Better: on object storage, write the new partition alongside and swap a
# pointer. Delta, Iceberg and Hudi give you this as a transactional table
# operation, which is most of why they exist:
#   spark.write.format("delta").mode("overwrite") \
#        .option("replaceWhere", f"dt = '{logical_date}'").save(path)

Backfills

the operation that tests your design
# You find a bug in a transformation. Thirty days of features are wrong,
# and every model trained on them is suspect. What now?
#
# IF TASKS ARE IDEMPOTENT AND PARAMETERISED BY DATE, this is a loop:
#     airflow dags backfill -s 2026-02-14 -e 2026-03-15 daily_features
#     dagster job backfill --from 2026-02-14 --to 2026-03-15
#
# IF THEY ARE NOT, it is an incident: you are hand-writing recovery SQL,
# deduplicating, and reasoning about which runs did what.

# FOUR THINGS THAT BREAK BACKFILLS, all of them common:
#
#   1. now() in the transformation. "Days since signup" computed against
#      today gives a different answer when you rerun it for last month —
#      and the wrong answer, because the model must see what was true THEN
#      (chapter 5's point-in-time correctness)
#
#   2. APPEND-ONLY writes. Rerunning duplicates
#
#   3. MUTABLE UPSTREAM SOURCES. If the source table is overwritten daily
#      rather than partitioned, last month's input no longer exists and the
#      backfill produces today's data with an old date on it. This is the
#      worst of the four, because it succeeds
#
#   4. CONCURRENCY LIMITS. Thirty parallel Spark jobs will either exhaust
#      the cluster or the warehouse. Set max_active_runs and chunk it

# AND ONE OPERATIONAL RULE: a backfill regenerating training data means
# every affected model needs retraining. The backfill is half the job; a
# list of models whose training data moved is the other half. That list only
# exists if you recorded which data version trained which model
# (chapter 3), which is where lineage starts earning its keep.
A pipeline that succeeds with wrong output is worse than one that fails

Orchestrators report on exit codes, so a task that reads a partially-loaded source table, transforms the rows it found and writes them is a green task. Nobody is paged, the model retrains on a fraction of the data, and the metric drops a week later for reasons nobody connects to Tuesday's upstream delay. The defence is an explicit assertion on volume and freshness before the transformation runs — a row count against the same weekday last week, a maximum age on the newest record, a check that the upstream partition is marked complete. Failing loudly on a suspicious input costs you an alert; succeeding quietly costs you a month of quiet degradation and a difficult investigation. This is the single highest-value habit in the chapter.

the distinction worth understanding: tasks or assets
TASK-CENTRIC (Airflow, Argo, Step Functions)
  You declare WORK and its order. "Run extract, then transform, then load."
  The orchestrator knows about tasks and nothing about what they produce.

    extract >> transform >> load

  Consequences: "is the customer features table up to date?" is not a
  question the system can answer. Neither is "what would I need to rerun to
  refresh this table?" You track that in your head, or in a wiki.

ASSET-CENTRIC (Dagster, and dbt within its scope)
  You declare the DATA and what it depends on. The orchestrator derives the
  execution order and knows the current state of every asset.

    @asset(deps=[raw_events])
    def daily_features(): ...

    @asset(deps=[daily_features])
    def churn_model(): ...

  Consequences: lineage is automatic, staleness is queryable, and
  "materialise this asset and whatever it needs" is a single operation.

WHY THIS MATTERS PARTICULARLY FOR ML: an ML system's questions are almost
all asset questions. Which features fed this model? Is this table stale?
What breaks if this column changes? What must be rebuilt after that
backfill? A task graph answers none of them; an asset graph answers all of
them by construction.

That is not a reason to migrate a working Airflow deployment. It is a
reason to know why Dagster exists, and to model your Airflow DAGs around
partitioned outputs rather than around verbs, which gets you part of the
benefit for free.

Batch or streaming

and the honest answer about which you need
BATCH — read a bounded window, write a partition, on a schedule.
  Freshness: minutes to a day.
  Failure handling: rerun the partition. Simple.
  Tools: SQL, dbt, Spark, whatever.

STREAMING — process events as they arrive.
  Freshness: seconds.
  Failure handling: offsets, checkpoints, watermarks, exactly-once
    semantics, and reprocessing means replaying from a retained log.
  Tools: Kafka, Flink, Spark Structured Streaming, Beam.

THE QUESTION THAT DECIDES IT: does the prediction depend on something that
happened in the last few minutes?

  Fraud on a card transaction        -> yes. Streaming.
  Churn score shown in a dashboard   -> no. Batch, nightly.
  "Customers also bought"            -> no. Batch.
  Real-time bidding                  -> yes, and in single-digit ms.
  Content moderation on upload       -> yes, but it is request-time
                                        inference, not streaming ingestion

THAT LAST DISTINCTION CATCHES PEOPLE. "The model must respond in 50 ms" is a
serving requirement (chapter 11), not a streaming-ingestion requirement. You
can serve a request in 50 ms using features computed by a nightly batch job.
Streaming is only needed when the FEATURE VALUES must reflect the last few
minutes — a count of transactions in the past hour, a session's click
history so far.

STREAMING COSTS ARE REAL: exactly-once semantics are genuinely hard,
late-arriving and out-of-order events need watermarks, reprocessing needs a
retained log and a plan, and debugging a stateful streaming job is markedly
harder than reading a failed batch task's log. Adopt it when the freshness
requirement is real, and note that a hybrid — batch for the heavy historical
features, streaming for the handful that must be fresh — is usually the
sensible architecture rather than a compromise.
Test the transformations, not the DAG

Pipeline code is notoriously untested, and the usual excuse is that it needs a warehouse and real data. It does not, if the code is organised for it: keep the transformation logic in plain functions that take a dataframe and return a dataframe, and let the orchestrator's task be a thin wrapper that reads, calls, and writes. Then the logic is unit-testable with ten synthetic rows, in milliseconds, in CI — including the edge cases that actually break things: an empty input, a null in a join key, a duplicate id, a timezone boundary, a currency that arrives as a string. This is the same organisational move as chapter 2's shared feature code, and it pays twice: the tests become possible, and the notebook can import the same functions the pipeline runs.

The short version

  1. Idempotency is the foundation. Retries, backfills and partial-failure recovery all depend on it.
  2. Replace partitions, do not append. A retry that duplicates rows silently reweights your training loss.
  3. No now() in a transformation. Every date comes from the orchestrator's logical date, or backfills are wrong.
  4. Validate before writing, and fail loudly. A green task with partial output is the worst pipeline behaviour there is.
  5. Mutable upstream sources break backfills silently — you get today's data with an old date on it.
  6. A backfill implies retraining. The list of affected models only exists if you recorded data versions.
  7. Asset-centric orchestration answers ML's questions; task-centric orchestration answers none of them.
  8. Streaming is for features that must be fresh, not for low-latency serving. Those are different requirements.
