Deployment strategies

The container playbook — canary, blue-green, progressive rollout — applies to models with one significant modification: the thing you are watching for is usually not an error rate, and it may take days to become measurable.

Shadow mode is the ML-specific one, and it is underused

Send production traffic to the new model, compare its predictions against the current one, and discard its output. Nobody is affected, so it is free of risk — and it catches the two failures that offline evaluation structurally cannot: serving skew, where the features computed on the request path differ from those used in training and the score distribution shifts (chapter 14), and operational problems like latency, memory and load failures, measured under real traffic rather than in a benchmark. The comparison to run is the distribution of the two models' scores on identical inputs; a shift there means something is wrong with the plumbing regardless of what the offline metric said. Run shadow for a day before any canary, on every model.

shadow mode, concretely
@app.post("/predict")
async def predict(req: PredictRequest, bg: BackgroundTasks):
    feats = build_features(req)
    live  = float(CHAMPION.predict(feats[FEATURE_ORDER])[0])

    # the shadow call must not affect the response, ever
    bg.add_task(shadow_score, feats, live, req.id)
    return {"score": live}

def shadow_score(feats, live_score, req_id):
    try:
        t0 = time.perf_counter()
        shadow = float(CHALLENGER.predict(feats[FEATURE_ORDER])[0])
        ms = (time.perf_counter() - t0) * 1000
        log_shadow(req_id, live_score, shadow, ms)
    except Exception as e:
        metrics.increment("shadow.error", tags={"type": type(e).__name__})
        # SWALLOWED. A failing challenger must never affect live traffic.

# THEN COMPARE, after a day of traffic:
#
#   * score distribution — mean, std, quantiles, and PSI between the two
#     (chapter 6). A material shift means the challenger is seeing
#     different inputs than it trained on, or is genuinely different
#   * DISAGREEMENT RATE at your operating threshold. "The two models
#     disagree on 12% of requests" is the number to look at, and to
#     sample from and read
#   * latency, p50 and p99, under real load and real feature distributions
#   * error rate, and what kind
#
# THE THING TO SAMPLE AND READ: the requests where the two models disagree
# most. That set is small, informative and usually explains the whole
# difference in twenty minutes — which is chapter 10's error analysis
# applied to a deployment decision.

# WHAT SHADOW CANNOT TELL YOU: whether the new model is BETTER. No user saw
# its output, so there is no outcome to measure. It rules out breakage; it
# does not establish improvement. That is what a canary and then an A/B
# test are for.

the sequence worth defaulting to
1. OFFLINE GATES              minutes    chapter 9
     beats live on aggregate and on every protected slice, within latency
     budget, fully reproducible, behavioural tests pass

2. SHADOW                     1 day      no user impact
     score distribution matches expectation, disagreement rate explained,
     latency and error rate acceptable under real traffic

3. CANARY AT 5%               1-2 days   5% blast radius
     operational metrics clean, prediction distribution on the canary
     matches the shadow run, no error-rate change

4. RAMP 25% -> 50% -> 100%    days       automatic rollback on any breach

5. HOLD BACK 5% INDEFINITELY  weeks      the honest measurement
     a permanent control group on the previous model, so you can measure
     the business outcome rather than infer it

STEP 5 IS THE ONE PEOPLE SKIP, and it is the only one that answers "did
this model make things better". A holdback costs you 5% of the improvement
and buys you the ability to know whether there was one — which, given how
often a model improves a metric and not an outcome, is a good trade.

It also gives you a live baseline for free: when performance degrades six
weeks later, you can see whether the holdback degraded too. If both fell,
the world changed. If only the new model fell, the model is the problem.
That distinction is otherwise very hard to establish (chapter 15).

WHAT TO AUTOMATE THE ROLLBACK ON, at each stage:
   error rate above baseline + margin
   p99 latency above budget
   prediction distribution PSI above threshold vs the shadow baseline
   null or default feature rate above baseline
   any behavioural test failing against live traffic samples
Not on the model's accuracy, because you do not have labels yet.
The metric you deployed for is usually not measurable during the rollout

This is the modification the container playbook needs. A web service deployment is validated in minutes because errors and latency are immediate. A model's actual quality depends on outcomes — whether the flagged transaction was fraudulent, whether the recommended item was bought, whether the predicted churner churned — and those arrive hours, days or months later (chapter 15). So the rollout must be gated on proxies: prediction distribution, disagreement rate against the previous model, feature null rates, latency, error rate. Every one of them is available immediately and none of them is the thing you care about. Accept that, choose the proxies deliberately, and keep the holdback so the real answer arrives eventually rather than never.

Rolling back a model

three ways it is harder than rolling back code
1. THE PREVIOUS MODEL MAY NOT LOAD. It was pickled with a library version
   the current serving image no longer has, or its custom transformer class
   was refactored. Rollback fails at exactly the moment you need it.
     -> keep the environment with the model version (chapter 9), and run a
        scheduled "can we still load N-1?" check. This is worth automating
        because the failure is invisible until it matters.

2. THE PREVIOUS MODEL MAY BE STALE. If it was trained three months ago and
   the population has moved, rolling back trades a broken model for an
   obsolete one — and the obsolete one may be worse.
     -> for models that decay, the standing fallback should be the previous
        ARCHITECTURE retrained on current data, not the previous artefact.
        That costs a pipeline run and it is what rollback actually requires.

3. THE EFFECTS MAY ALREADY BE PERSISTED. Code rollback restores behaviour;
   model rollback does not undo what the model did. Predictions written to
   a table are still there. A recommender that trained users to click
   different things has changed the world, and the next model trains on
   that behaviour — chapter 1's feedback loop.
     -> know which outputs are persisted and whether they need reverting
        as a separate operation. Frequently they do, and frequently nobody
        has thought about it before the incident.

THE MECHANISM SHOULD BE TRIVIAL, whatever the complications:

     client.set_registered_model_alias("churn", "champion", "41")

Serving resolves the alias on load, or on a short TTL, so rollback is a
pointer move (chapter 9) and takes seconds rather than a redeployment.

A rollback that requires a deploy will not happen fast enough at 2am, and
a rollback nobody has practised does not work. Trigger one deliberately,
in production, on a quiet afternoon, once a quarter — the same argument as
testing a database failover.
Deploy the model and the features together, or not at all

A model and the feature pipeline that feeds it are one deployable unit, and treating them as two is a reliable way to break production. The failure has two directions. New model, old features: the model expects a feature the pipeline does not yet produce, so it arrives null and the model behaves unpredictably rather than erroring. New features, old model: a transformation changed — a new encoding, a different null fill, a rescaled column — and the old model is now receiving inputs unlike its training data, silently. Both are chapter 14's skew arriving through the deployment process. The mitigations are a feature-set hash checked at load time, so a mismatch is a startup failure rather than a quiet degradation, and treating "which feature version does this model require" as part of the registry entry rather than as institutional knowledge.

The short version

  1. Shadow mode is the ML-specific strategy and it is free: real traffic, discarded output, catches skew and operational failure.
  2. Shadow cannot tell you the model is better. It rules out breakage; a canary and an A/B test establish improvement.
  3. Gate the rollout on proxies — prediction distribution, disagreement rate, latency, feature null rate — because outcomes arrive later.
  4. Sample and read the requests where the two models disagree most. Small, informative, and usually explains everything.
  5. Keep a permanent 5% holdback. It is the only way to know whether the model helped, and it gives you a live baseline.
  6. Rollback is a pointer move, not a deployment — and it needs a version that still loads and is not obsolete.
  7. Model rollback does not undo what the model did. Persisted outputs and changed user behaviour are separate problems.
  8. Model and features deploy together. Check a feature-set hash at load time so a mismatch fails loudly.
