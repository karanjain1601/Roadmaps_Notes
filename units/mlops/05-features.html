Feature stores and lineage

A feature store is sold as infrastructure and is really a solution to two specific correctness problems. One of them — point-in-time correctness — quietly inflates offline metrics on a large fraction of models that were never near a feature store, so it is worth understanding whether or not you adopt one.

feature store point-in-time leakage

The join that ruins your metric

You are predicting churn. You have a table of customers who churned and when, and a table of support tickets. The obvious training set is: for each customer, the label, and their support-ticket count as a feature.

The question nobody asks is as of when.

Point-in-time correctness Same data, two joins. One of them tells the model the future.
—offline accuracy
—production accuracy

The feature must be what was knowable at prediction time

A model in production sees the world as it is at the moment of the request. A training set built with a naive join sees the world as it is now — which, for any row whose label is in the past, includes information that arrived after the thing you are predicting. The offline metric is then measuring a model that had access to the answer, and it will look excellent right up until deployment. This is the single most common cause of a model that scores 0.94 in evaluation and 0.71 in production, and it does not require a subtle bug: SELECT customer_id, COUNT(*) FROM tickets GROUP BY 1 joined to a label table is enough. The correct join asks, for each label row, what the aggregate was as of that row's timestamp.

the two joins, written out
-- WRONG: aggregates everything, including events after the label
SELECT l.customer_id, l.churned,
       (SELECT COUNT(*) FROM tickets t
         WHERE t.customer_id = l.customer_id) AS ticket_count
FROM labels l;

-- RIGHT: aggregates only what existed at the label's timestamp
SELECT l.customer_id, l.churned,
       (SELECT COUNT(*) FROM tickets t
         WHERE t.customer_id = l.customer_id
           AND t.created_at < l.event_time) AS ticket_count
FROM labels l;

-- The difference is one predicate, and it is the difference between a
-- metric you can trust and one you cannot.

-- IN PRACTICE IT IS HARDER THAN ONE PREDICATE, because:
--
--   * some features are snapshots rather than event streams. "Customer
--     tier" is a column that was UPDATED in place, so the historical value
--     no longer exists anywhere. This is why chapter 4 insisted on
--     partitioned, append-only sources — a mutable table destroys your
--     ability to build a correct training set, retroactively and forever
--
--   * feature freshness at serving time is not instantaneous. If the online
--     value is refreshed hourly, then at prediction time the model sees a
--     value up to an hour stale. A training set joined at the exact label
--     timestamp is therefore ALSO wrong, just in the other direction. The
--     correct cutoff is `l.event_time - interval '1 hour'`, matching the
--     real staleness
--
--   * late-arriving data. A ticket created at 09:00 that lands in the
--     warehouse at 11:00 was not knowable to a 10:00 prediction, even
--     though its created_at says otherwise. Correct joins use the INGESTION
--     time as well as the event time, which is what bitemporal modelling is
--     for and what most hand-written joins ignore

-- THIS IS WHAT A FEATURE STORE'S "get_historical_features" DOES. Not
-- storage — the point-in-time join, correctly, including the staleness and
-- late-arrival handling, so that every team gets it right by default rather
-- than by remembering.

Offline and online

the second problem: two paths, one definition
OFFLINE (training)                    ONLINE (serving)
------------------                    ----------------
a warehouse table                     a low-latency key-value store
months of history                     the current value only
minutes per query is fine             single-digit milliseconds
Spark or SQL                          Redis, DynamoDB, Cassandra
computed in a batch job               read on the request path

THE PROBLEM: the same feature must be computed the same way in both. And
the natural way to build them is separately — a SQL query for training, and
some Python in the service for serving — which means the same logic exists
twice, in two languages, maintained by two people.

  offline:  AVG(amount) OVER (PARTITION BY customer_id
                              ORDER BY ts RANGE BETWEEN
                              INTERVAL '30 days' PRECEDING AND CURRENT ROW)

  online:   sum(recent_amounts) / len(recent_amounts)

Are those the same? Does the online one include today? Does it handle a
customer with no transactions the same way? Does it use the same currency
conversion? Nobody knows, and nothing checks, and the model quietly gets
different inputs in production than it trained on. That is chapter 14.

THREE WAYS OUT, in increasing order of infrastructure:

  1. ONE DEFINITION, TWO EXECUTION PATHS. Write the transformation once, in
     Python or SQL, and run the same code in the batch job and in the
     service. Cheapest, works on day one, and requires only discipline —
     package the transforms and import them in both places (chapter 2).

  2. BATCH-COMPUTE EVERYTHING, SERVE THE PRECOMPUTED VALUE. The batch job
     writes each entity's current feature vector to a key-value store; the
     service does a lookup and no computation at all. Removes the
     possibility of divergence entirely, at the cost of freshness. This is
     underrated and correct for a great many models.

  3. A FEATURE STORE. One declared definition, from which the platform
     materialises both the offline table and the online store, and provides
     the point-in-time join for training. Feast, Tecton, Vertex/SageMaker
     feature stores, Databricks, Hopsworks.

Option 2 deserves more attention than it gets. If your features are
aggregates over days or weeks, they do not change meaningfully within an
hour, so serving yesterday's precomputed vector is nearly free and
structurally cannot diverge from what you trained on.
Do not adopt a feature store to get a feature store

It is a substantial piece of infrastructure with a real operational cost, and for a single model it solves problems you can solve with a package and a convention. The honest triggers for adopting one are specific: several models or teams share feature definitions and those definitions have started to diverge; you have had a training/serving skew incident and want a guarantee rather than a code-review habit; you need point-in-time joins over many entities and event types and the hand-written SQL has become unmaintainable; or you need feature reuse discoverable across teams, which is as much an organisational problem as a technical one. If none of those describes you, the same money buys better monitoring — and chapter 15 will do more for your models than a feature store will.

Lineage

the questions lineage answers, and what it takes to answer them
QUESTION 1: "This prediction looks wrong. What produced it?"
  needs: prediction log -> model version -> training run -> data version
         -> feature definitions -> source tables

QUESTION 2: "We are changing this upstream column. What breaks?"
  needs: source table -> feature definitions -> models -> deployed endpoints
  This is the FORWARD direction and it is the one people lack. Chapter 1's
  "undeclared consumers" debt lives here.

QUESTION 3: "We backfilled 30 days. What needs retraining?"
  needs: data version -> training runs that used it -> models -> deployments

QUESTION 4: "A customer has exercised their right to erasure. Which models
             were trained on their data?"
  needs: the same chain, and a regulator may ask (chapter 17)

WHAT IT ACTUALLY TAKES, and it is less than a platform:

  * every training run records its data version and feature set (chapter 3)
  * every model version records its training run (chapter 9)
  * every prediction logs its model version (chapter 1)
  * feature definitions live in code, in one place, so "what depends on this
    column" is a grep rather than an investigation

Those four give you the whole chain, and three of them are one extra field
in something you are already writing. The expensive part is the forward
direction — knowing who consumes your outputs — and the cheap approximation
is a README naming known consumers, kept honest by asking.

TOOLS: OpenLineage is the emerging standard for emitting lineage events, and
Marquez, DataHub, OpenMetadata and Amundsen consume them. Dagster and dbt
both derive lineage from their own asset graphs, which is a strong argument
for modelling your pipeline as assets (chapter 4). Adopt one when manual
tracking has visibly failed, not before.
Check your existing models for the leak

Point-in-time correctness is worth auditing retroactively, because the failure is silent and common. For each production model, take one feature and ask: could the value used in training have been affected by anything that happened after the label event? Aggregate counts, "total spend", "number of logins", "days since last activity", and anything derived from a mutable column are all suspect. The empirical test is quick — rebuild the training set with the timestamp predicate added and retrain. If the offline metric drops noticeably, the original number was measuring a model that could see the answer, and your production performance was never going to match it. That is a better thing to discover deliberately than to spend a quarter explaining.

The short version

  1. A feature must be what was knowable at prediction time, not what is true now.
  2. The naive join leaks the future, inflates the offline metric, and is the commonest cause of a 0.94-to-0.71 drop.
  3. Mutable source tables destroy correctness retroactively — the historical value no longer exists to join to.
  4. Match the real staleness. If the online value refreshes hourly, join at the label time minus an hour.
  5. Late-arriving data means event time is not enough; ingestion time matters too.
  6. One definition, two execution paths is the cheap fix. Precomputing everything into a key-value store is the cheaper one.
  7. Adopt a feature store for a named problem: shared definitions diverging, a skew incident, or unmaintainable joins.
  8. Lineage is four extra recorded fields, not a platform. The hard direction is knowing who consumes your outputs.
