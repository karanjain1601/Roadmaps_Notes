Training and serving skew

The model that scored 0.91 in evaluation is scoring 0.68 in production and nothing is broken. No errors, normal latency, healthy dashboards. Skew is the most damaging failure in production ML precisely because every system reports success.

The only reliable defence is one implementation

Every detection mechanism in this chapter is a way of noticing that skew has already happened. The prevention is structural and it is simple to state: the transformation from raw input to feature vector must exist once, in one place, called by both the training pipeline and the serving path. Not "documented the same", not "reviewed carefully", not "tested for equivalence" — the same function. Everything else in MLOps around this problem — feature stores, parity checks, shadow deployments, logged feature vectors — is either enforcement of that property or compensation for not having it. If you take one architectural decision from this unit, it is to package the feature code and import it in both paths (chapters 2, 5 and 11).

the shape that removes the problem
# src/features.py — the single implementation. No I/O, no globals, no now().
def build_features(raw: dict | pd.DataFrame, asof: datetime) -> pd.DataFrame:
    """Pure. Same input, same output, in any caller."""
    df = to_frame(raw)
    df["tenure_days"]   = (asof - df.signup_at).dt.days
    df["amount_log"]    = np.log1p(df.amount.clip(0, 1e6))
    df["income_filled"] = df.income.fillna(MEDIAN_INCOME)   # a CONSTANT,
                                                            # not a runtime
                                                            # median
    df["channel"]       = df.channel.fillna("unknown").astype(CHANNEL_DTYPE)
    return df[FEATURE_ORDER]

# training pipeline
feats = build_features(warehouse_rows, asof=label_time)     # chapter 5

# serving
feats = build_features(request_payload, asof=datetime.utcnow())

# THREE DETAILS IN THAT FUNCTION THAT MATTER MORE THAN THEY LOOK:
#
#   asof IS A PARAMETER, not now(). That is what makes the same function
#   usable for a historical point-in-time join and for a live request, and
#   it is the same discipline as chapter 4's no-now() rule.
#
#   MEDIAN_INCOME IS A CONSTANT, fitted once and saved with the model. If
#   the training pipeline fills with the median of the training batch and
#   the service fills with the median of... what, exactly? — you have skew
#   in the imputation. Every fitted parameter must travel with the model
#   (chapter 11), which is what a sklearn Pipeline does for you.
#
#   FEATURE_ORDER IS EXPLICIT. Positional model formats read column 4 as
#   whatever is in position 4, so a reordering silently reassigns every
#   feature. One shared constant, or an MLflow signature that validates it.

# THE TEST THAT PROVES PARITY, and it belongs in CI:
def test_training_serving_parity():
    for row in GOLDEN_ROWS:                        # ~50 fixed examples
        offline = build_features(as_warehouse_row(row), asof=row.ts)
        online  = build_features(as_api_payload(row),   asof=row.ts)
        pd.testing.assert_frame_equal(offline, online, check_exact=False,
                                      rtol=1e-9)
# If the two paths ever diverge — a new field, a changed default, a
# different dtype — this fails on the commit that caused it rather than in
# production three weeks later.

Detecting it when you cannot prevent it

log the features, not just the prediction
# The single most useful thing you can do. At serving time, log the actual
# FEATURE VECTOR the model received — not the request, the features.

log_prediction({
    "request_id":    req.id,
    "entity_id":     req.entity_id,
    "model_version": MODEL_VERSION,
    "feature_hash":  FEATURE_SET_HASH,
    "features":      feats.iloc[0].to_dict(),   # <- THIS
    "score":         score,
    "ts":            now,
})

# WHY THIS UNLOCKS EVERYTHING:
#
#   1. PARITY CHECK. Recompute the same features offline from the warehouse
#      for the same entity and moment, and compare. Any material difference
#      is skew, named and located. Run it nightly on a sample of a thousand
#      requests and alert on the mismatch rate per feature.
#
#   2. DISTRIBUTION COMPARISON. Compare the served feature distributions
#      against the training baseline you logged with the model (chapter 7).
#      A feature whose mean has moved 40x is not drift, it is a bug.
#
#   3. REPLAY. Feed logged feature vectors to a candidate model to see what
#      it would have predicted, without deploying it.
#
#   4. DEBUGGING A SPECIFIC PREDICTION. "Why did it decline this
#      application" is answerable, exactly, which chapter 17 requires.
#
# COST: on a wide feature vector this is real storage. Sample it — 1-5% of
# requests is plenty for distribution and parity work, and log 100% of the
# small stuff (model version, score, entity) which you will want for
# everything else.

# THE NIGHTLY PARITY JOB, in outline:
sample = read_prediction_log(yesterday).sample(1000)
offline = build_features(warehouse_rows_for(sample.entity_id),
                         asof=sample.ts)                 # chapter 5
for col in FEATURE_ORDER:
    served   = sample.features.apply(lambda d: d[col])
    recomputed = offline[col]
    mismatch = (~np.isclose(served, recomputed, rtol=1e-6)).mean()
    metrics.gauge("parity.mismatch_rate", mismatch, tags={"feature": col})
    if mismatch > 0.01:
        alert(f"{col}: {mismatch:.1%} of served values disagree with offline")

# This job has found real bugs in real systems within a week of being
# switched on, in more than one organisation. It is a day of work.
Skew and drift look identical on a dashboard and have opposite fixes

Both present as a shifted input or prediction distribution. Drift means the world changed and the correct response is to retrain on recent data. Skew means your plumbing is wrong and retraining makes it worse — you would be fitting a model to the corrupted values, which locks in the bug and destroys the evidence, and the next model looks fine on the broken features while the underlying problem is now invisible. Two things distinguish them. Timing: drift is gradual, skew appears at a deployment boundary — check what shipped. And the parity check: recompute the features offline and compare against what was served. If they disagree, it is skew. This is the diagnostic question that matters most in chapter 15's alerts, and getting it backwards is expensive.

The unseen-category case is worth its own paragraph

A one-hot encoder fitted on the training categories, given a value it has never seen, does one of two things. It raises — which is loud and recoverable. Or, with handle_unknown="ignore", it emits a vector of all zeros, and all-zeros is not a representation of "unknown": it is a point in feature space that the model never saw during training and from which it will extrapolate arbitrarily. The prediction is confident and meaningless. The fix is to make "unknown" a real category that appears in training — deliberately map rare values to it during training so the model learns what to do with them — and to alert on the rate of unseen values at serving time. This failure is concentrated in whatever segment carries the new value, so the aggregate metric barely moves while that segment is handled badly (chapter 10).

Two cheap checks that catch most of it

At model load, assert the feature contract. The model artefact carries the list of feature names, their dtypes and their order; the service asserts that what it is about to build matches. A mismatch becomes a startup failure — the pod never becomes ready and the deployment stalls — instead of a silent degradation that runs for weeks. An MLflow signature gives you this almost for free. And at serving time, assert the ranges. If a feature was in [0, 500] across the entire training set and a request produces 40,000, something is wrong upstream; increment a metric and decide deliberately whether to clip, reject or serve. Neither check is sophisticated, both are a few lines, and between them they convert the majority of skew from an invisible ongoing loss into a loud event at the moment it is introduced.

The short version

  1. Skew is the most damaging production ML failure because every system reports success — no errors, normal latency, green dashboards.
  2. The only reliable defence is one implementation of the feature transformation, imported by both paths.
  3. Every fitted parameter must travel with the model — scalers, encoders, imputed medians. Serialise the whole pipeline.
  4. asof is a parameter, never now(), which is what lets one function serve both a historical join and a live request.
  5. Log the feature vector, not just the prediction. It unlocks parity checks, replay and per-prediction debugging.
  6. Run a nightly parity job on a sample — recompute offline, compare, alert per feature. A day of work, and it finds real bugs.
  7. Skew and drift look identical and have opposite fixes. Retraining on skewed features locks in the bug.
  8. All-zeros is not "unknown". Make unknown a real trained category and alert on unseen values.
