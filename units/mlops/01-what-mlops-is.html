Chapter 01 · The problem

What MLOps is

Ordinary software is broken by change. Machine learning systems are broken by the world changing while the code stays still — which is a different failure mode, needs different machinery, and is why this is a discipline rather than a DevOps chapter.

decay vs devops maturity tech debt

The failure that defines the field

A fraud model is deployed in March. It is carefully validated, holds up on a held-out set, and performs well for eleven weeks. In June its precision has fallen by a third. Nobody deployed anything. No code changed. No infrastructure changed. No alert fired, because every service is healthy and every request returns 200.

What happened is that fraudsters adapted, a payment provider changed how it reports card country, and a marketing campaign brought in a cohort of customers who look nothing like the training data. The model is doing exactly what it was trained to do, on a world that has moved.

ML systems have a second input that nobody deploys

A conventional service is a function of its code and its request. You control the code, you version it, and if behaviour changes you look at what shipped. An ML system is a function of its code, its request, and the data it was trained on — and that third input is a frozen snapshot of a world that keeps moving. So the system degrades with no change to anything you version, which breaks the fundamental debugging instinct of software engineering: "what changed?" Nothing changed. That is the problem. Every practice in this unit exists because of it — versioning data so you know which world the model learned, monitoring distributions so you notice the drift, retraining pipelines so you can respond without a project.

Hidden technical debt

the debts that are specific to ML
The 2015 Google paper "Hidden Technical Debt in Machine Learning Systems"
named these, and a decade later they are all still true.

GLUE CODE. A tiny fraction of a real ML system is the model. The rest is
configuration, data extraction, feature engineering, serving infrastructure,
process management and monitoring — and it accumulates as glue because each
piece was added to make the next thing work.

ENTANGLEMENT (the CACE principle: Changing Anything Changes Everything). ML
models have no encapsulation. Add a feature, remove a feature, change a
hyperparameter, change the data — and every output changes, including for
inputs you were not thinking about. There is no interface boundary that
contains the effect of a change.

CORRECTION CASCADES. A model is slightly wrong for a segment, so someone
adds a post-processing rule. Then a rule to handle the rule's edge case.
Then a second model to correct the first. Now improving the base model
breaks all the corrections, so nobody improves the base model.

UNDECLARED CONSUMERS. Your model's predictions are written to a table.
Three other teams start reading that table. You do not know they exist, so
you change the output scale and break them silently. This is the ML version
of a public API you did not know you had.

DATA DEPENDENCIES COST MORE THAN CODE DEPENDENCIES, and there is no
equivalent of a compiler or a linter to find them. An upstream table you
consume can change meaning without changing schema, and nothing tells you.

FEEDBACK LOOPS. Your recommender promotes items, users click them, the
clicks become training data, and the model learns that those items are
good — because it promoted them. DIRECT feedback loops are at least
visible. HIDDEN ones, where two models influence each other through the
world, are extremely hard to detect and reason about.

PIPELINE JUNGLES. Scrapes, joins and transforms accumulate until nobody can
say where a feature comes from. Chapter 4 is about the properties that
prevent this, and chapter 5 is about making lineage explicit.

CONFIGURATION DEBT. ML systems have enormous configuration surface —
features used, data ranges, algorithm settings, pre-processing, thresholds —
and it is routinely untested, unreviewed and unversioned. Chapter 3.
The most common failure is organisational

The technical failures in this unit are real, and the one that stops more models reaching production than all of them together is a handoff. A data scientist produces a notebook that scores well and hands it to an engineering team to "productionise". The engineer rewrites the feature logic in a different language, subtly differently — which is chapter 14's skew, arriving by the front door. The data scientist cannot debug the production system; the engineer cannot evaluate the model. Neither owns the outcome. The arrangements that work all have one property: the person who trains the model can see it running and can deploy a new one. That is a statement about tooling — it needs pipelines, a registry, a deployment path — but the reason to build those things is to remove the handoff, not to have them.

What MLOps is for

Reproducibility
Given a model, recover exactly what produced it — code, data, config, environment. Without this, nothing else is verifiable and every regression is a mystery (chapter 3).
Automation
Retraining and deployment as a pipeline rather than an afternoon. This is what turns "the model has decayed" from a project into an operation (chapters 4 and 8).
Continuous delivery of models
A path from a trained candidate to production traffic, with the same gates and rollback story you expect for code (chapters 9 and 12).
Monitoring that understands ML
Latency and error rate are necessary and tell you nothing about whether predictions are still good. Drift and delayed labels are the actual problem (chapter 15).
Governance
Being able to answer "why did the model decide this" and "what data trained it" — for regulators, for customers, and for yourself during an incident (chapter 17).
Collaboration
Removing the handoff. Shared artefacts, shared environments, one path to production (this chapter, above).
Start with monitoring, not with a platform

If you are running one model with no MLOps practice at all, the highest-value first move is not a pipeline or a registry — it is logging every prediction with its inputs, its output, a model version and a timestamp. That single table costs an afternoon and unlocks nearly everything else: you can measure drift against it, you can compute real performance once labels arrive, you can debug a specific bad prediction, you can compare two model versions on identical traffic, and you can reconstruct a training set that matches production. Teams that skip it end up unable to answer the most basic question in production ML — "is this working?" — and no amount of platform underneath fixes that.

The short version

  1. ML systems degrade with no change to anything you version, because the world moves and the training data does not.
  2. That breaks the "what changed?" instinct. Nothing changed — which is why the discipline exists.
  3. Five artefacts must be versioned, not one: code, data, config, environment and weights.
  4. Correctness is statistical, so testing is a metric on a distribution rather than a pass or fail.
  5. The ML-specific debts are real: entanglement, correction cascades, undeclared consumers, feedback loops, pipeline jungles.
  6. The commonest failure is a handoff, and the arrangements that work let the person who trains a model deploy it.
  7. Build one rung up the ladder, not five. Most teams run one or two models and do not need a platform.
  8. Log every prediction with its inputs and a model version. One afternoon, and it unlocks everything else.
