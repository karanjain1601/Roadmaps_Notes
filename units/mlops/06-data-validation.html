Data validation and drift

The failure worth designing against is not a missing column — that raises an exception and someone fixes it. It is a column that keeps its name, keeps its type, passes every schema check, and now means something different.

Schema checks are necessary and catch the easy half

Types, nullability, required columns and allowed values are cheap to assert and they catch the failures that would have raised an exception anyway — just earlier and with a better message. What they cannot catch is a value that is still the right type and the right range and is now wrong: cents becoming units, a currency conversion applied twice, an identifier space that was renumbered, a timestamp that switched from UTC to local. Every one of those produces valid data. The layer that catches them is distributional — compare this batch's summary statistics against the training baseline and alert on movement — and it is the layer most teams do not have.

# 3. DISTRIBUTIONS, against a stored baseline from the training data.
#    This is the layer that catches semantic changes.
for col in NUMERIC:
    assert_within(df[col].mean(),   baseline[col]["mean"],   tol=0.25)
    assert_within(df[col].std(),    baseline[col]["std"],    tol=0.35)
    assert_within(df[col].isna().mean(), baseline[col]["null_rate"], tol=0.05)

Three kinds of drift

Data drift — the inputs move
P(X) changes. A marketing campaign brings in younger customers, so the age distribution shifts. The relationship between features and label may be unaffected, and the model is now extrapolating into a region it saw little of. Detectable without labels, which is why it is the practical thing to monitor.
Concept drift — the relationship moves
P(y|X) changes. The same customer profile now means something different — fraudsters adapted, a competitor changed prices, a regulation changed behaviour. The inputs may look identical. Only detectable with labels, which is the whole difficulty (chapter 15).
Prediction drift — the outputs move
The distribution of your model's own predictions shifts. A useful early proxy for both of the above, available immediately, requiring no labels and no baseline beyond your own history — and the cheapest ML-specific monitor to add.
measuring drift, and the arithmetic
# POPULATION STABILITY INDEX — the industry standard in credit and
# insurance, and a good default. Bin the baseline, bin the new data,
# compare the proportions.
#
#     PSI = Σ (actual% − expected%) × ln(actual% / expected%)
#
#     < 0.1   no meaningful shift
#     0.1-0.2 moderate — investigate
#     > 0.2   significant — act
#
def psi(baseline, current, bins=10):
    edges = np.quantile(baseline, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(baseline, edges)[0] / len(baseline)
    a = np.histogram(current,  edges)[0] / len(current)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

# KOLMOGOROV-SMIRNOV — max distance between the two CDFs. Gives a p-value,
# which is its problem: on a million rows every trivial difference is
# "significant", so the p-value tells you nothing useful and you end up
# thresholding on the statistic anyway. Prefer PSI or Wasserstein.
#
# WASSERSTEIN DISTANCE (earth mover's) — how far the mass has to move.
# Interpretable in the units of the feature, which is genuinely useful:
# "the mean transaction moved by £14" is actionable, "D = 0.04" is not.
#
# FOR CATEGORICAL FEATURES: PSI works on category proportions directly.
# Also watch for unseen categories, which are a different failure — a new
# value the model has literally never encountered, usually one-hot-encoded
# into all zeros or an error depending on your pipeline.

# THE PRACTICAL SETUP:
#   * store a baseline profile with the model: per feature, the quantile
#     edges, mean, std, null rate and category set of the TRAINING data
#   * on a schedule, profile recent production inputs the same way
#   * compute PSI per feature, alert on the ones that matter
#
# WEIGHT BY FEATURE IMPORTANCE. A large shift in a feature the model barely
# uses is noise; a small shift in the top feature is worth a look. Alerting
# on unweighted per-feature drift across 200 features produces an alert
# every day and trains everyone to ignore it — which is the most common way
# drift monitoring fails in practice.
Drift is a signal, not a verdict

A drift alert says the world has changed. It does not say your model has got worse, and acting on drift alone leads to retraining on a schedule that has nothing to do with performance. Two things are commonly true and worth separating. Drift with no degradation: the shift happened in a region where the model's decision boundary is unaffected, or in a feature it barely uses — no action needed, and retraining costs money and risk for nothing. Degradation with no drift: concept drift, where inputs look identical and the relationship changed — the case drift monitoring cannot see, and the reason you also need delayed-label performance tracking. Treat drift as the trigger for investigation, and treat measured performance as the trigger for retraining.

The single most valuable check is a row count

Before PSI, before schema frameworks, before drift dashboards: assert that today's batch has roughly the number of rows you expect, compared against the same weekday last week. A partial load is the most common data failure there is, it produces perfectly valid data, it passes every schema check, and it silently retrains your model on a biased subset — because the rows that are missing are rarely random. They are one region whose export failed, or one event type whose producer was down, so the shortfall is systematic and the model learns the wrong distribution. One assertion, no dependencies, and it catches more real incidents than anything else in this chapter.

The short version

  1. The dangerous failure keeps the schema and changes the meaning. Cents to units, UTC to local, a renumbered id space.
  2. Schema checks catch the easy half and are still worth having — earlier failure, better message.
  3. Distribution checks against a stored training baseline are the layer that catches semantic change.
  4. Check volume and freshness first. A partial load is the commonest silent failure and produces valid data.
  5. Three drifts: data (inputs), concept (relationship), prediction (outputs). Only the first and third are visible without labels.
  6. PSI over KS. A p-value on a million rows makes every trivial difference significant.
  7. Weight drift by feature importance, or you will get an alert a day and learn to ignore it.
  8. Drift triggers investigation; measured performance triggers retraining. Retraining on a broken pipeline bakes in the bug.
