CHAPTER 07

Features and the feature store

Four small differences between the batch pipeline and the serving code — a rounding, a null fill, a stale value, an off-by-one window — cost 6.3% of decisions while the offline AUC does not move by a single digit. And a training set joined to today's feature values scores 0.9487 offline and 0.3805 in production, which is worse than random.

    THE STRUCTURE

    Two paths to the same number

    A feature is computed once for training and again for serving, usually by different code with different constraints.

    Why the two implementations diverge
    Training pathServing path
    Written inSQL or Spark, over historyApplication code, one row at a time
    Latency budgetMinutesMilliseconds
    SeesThe whole tableOne entity, plus a cache
    Missing valuesImputed from the columnWhatever is at hand
    Time windowWhatever the query saysWhatever the cache holds
    OwnerUsually the data scientistUsually a different team
    None of the differences are mistakes

    The serving path fills a null with zero because it has no column to average over. It rounds because the value arrived as a float32. It uses a value from the last cache refresh because recomputing would blow the latency budget. Each choice is locally correct, and every one of them makes the number different from what the model was trained on.

    That is what makes skew hard: there is no bug to find, and the first demo shows the offline evaluation cannot see any of it.

    The offline column never moves

    0.8396 in every row. Not approximately — identically, because skew lives in the serving path and the offline evaluation never executes it. There is no amount of offline testing, cross-validation or holdout discipline that detects any of this.

    Meanwhile the combination costs 0.0195 of AUC — about 5.7% of the model's skill above chance — and decides 6.25% of cases differently. Neither number appears anywhere in a model report.

    Note also which difference dominates. Rounding costs essentially nothing and the null fill costs 0.0158, twelve times more than the stale value. The intuition that "a day-old feature is the risky one" is not what the arithmetic says here.

    How skew is actually found

    Log the served features. Not the prediction — the input vector the model actually received. Then recompute the same rows through the batch path and compare. Any difference is skew, and this is the only check that finds it directly.

    Score the logged features offline. Once you have the served vectors and eventually the labels, the online AUC in the table above becomes measurable rather than hypothetical.

    Or remove the second implementation entirely, which is what the rest of this chapter is about.

    THE OTHER FAILURE

    Point-in-time correctness

    Building a training set means joining features to labels. The join has to happen at the right moment, and the wrong moment is the default.

    A churn model with two features: how many purchases a user has made, and their rate. Labels come from events scattered through the past. The question is which value of "purchases so far" gets joined to a label from three months ago.

    The leaky model is inverted, not merely useless

    It scores 0.9487 offline — the better of the two by a wide margin, and the one that wins a model bake-off. In production it scores 0.3805, which is below 0.5.

    The mechanism: a user who churned stopped accumulating purchases, so their count today is low. The model learned that a low count today means churn. At serving time it sees the count as of now, when the future churners have not yet stopped, and their counts look perfectly healthy. The relationship it learned runs backwards from the one it faces.

    Nothing was joined wrongly. No key was duplicated, no row was dropped, and every value in the training set was a true value of that feature. It was simply read at the wrong moment.

    The point-in-time row is the tell

    The correct build has an offline-online gap of 0.0000, and that is not luck — it is structural. If the training set is assembled from exactly the values serving would have seen, then offline evaluation is a simulation of production, and there is no gap to have.

    So the diagnostic for this whole class of problem is a single question: is your offline number a prediction of your online number, or just a number? A pipeline that answers "prediction" has solved point-in-time correctness, and one that cannot answer has not.

    Why the default is wrong

    Feature tables are usually kept as "current state per entity" — one row per user, updated in place. That table is the easy thing to join against and it has no history, so joining it to a label from March gives you the March label next to today's features.

    Getting this right needs the feature table to be a log rather than a snapshot: one row per entity per time, joined with an as-of condition. That is more storage and a more awkward query, and it is the single most important thing a feature store does.

    THE COMPONENT

    What a feature store actually is

    Four things wearing one name, and you may need only one of them.

    A definition registry
    Feature logic written once, with an owner, a description and a schema. Solves discovery and duplication — three teams computing "sessions in the last 7 days" three slightly different ways.
    An offline store with history
    The feature log, supporting as-of joins. This is what makes point-in-time correctness the default rather than an achievement, and it is the piece the demo above is about.
    An online store
    A low-latency key-value lookup for serving. Solves the millisecond budget, and by itself does nothing about skew.
    One transformation, both paths
    The same code populating both stores. This is the piece that removes skew, and it is the hardest to retrofit — and the reason a store that only provides the two lookups is only half the product.
    Which pieces solve which problem

    The first demo's 6.25% of changed decisions is solved by the fourth item and nothing else. Adding an online store to an existing serving implementation gives you fast lookups of a feature that is still computed twice.

    The second demo's 0.5682 gap is solved by the second item. An offline store with proper as-of semantics makes the leaky join hard to write by accident, which is a much better guarantee than remembering not to write it.

    If you take one thing from this chapter, take the pairing: skew needs shared computation, leakage needs history. A product that provides one and not the other has solved one of your two problems.

    CALIBRATION

    When you do not need one

    Feature stores are among the most over-adopted components in this unit.

    What the problem actually is, and the cheapest thing that fixes it
    Your situationThe real problemCheapest fix
    One model, batch scoring onlyNone — there is one pathNothing
    One model, online servingSkewOne shared library, called by both
    Point-in-time joins are wrongLeakageAn append-only feature log plus as-of joins
    Teams rebuild the same featuresDiscoveryA registry, which can be a repository
    All of the above, several teamsAll of the aboveA feature store
    Batch-only scoring has no skew by construction

    If both training and inference run the same query over the same warehouse, there is one code path and the first demo's entire subject does not exist. A great many teams adopt a feature store to solve a problem they do not have, and inherit an online store they do not need to keep populated.

    The honest test is the first demo's method: log what serving computed, recompute it through the batch path, and see whether they match. If they match, you have no skew and no reason to buy anything.

    JUDGEMENT

    Five questions about a feature setup

  1. Is any feature computed by two pieces of code? If yes, they have diverged; the only question is by how much, and the offline AUC will not tell you.
  2. Are the served feature vectors logged? Without them, skew is unmeasurable rather than merely unmeasured.
  3. Does the feature table have history, or only current state? Current state makes the leaky join the path of least resistance.
  4. Is your offline AUC a prediction of your online AUC? A point-in-time correct pipeline has a gap of 0.0000 by construction.
  5. Which of the four components do you actually need? Batch-only scoring needs none of them.

    6. Recap

    What to take from this chapter

    1. A feature is computed twice, by different code with different constraints, and none of the differences are bugs.
    2. The offline AUC is 0.8396 under every skew tested — identically, because offline never runs the serving path.
    3. All four differences together cost 0.0195 of AUC and 6.25% of decisions.
    4. The null fill costs 0.0158 and rounding costs nothing, which is not the intuitive ordering.
    5. Skew is found by logging the served feature vectors and recomputing them through the batch path.
    6. A training set joined to today's values scores 0.9487 offline — the better model in any bake-off.
    7. In production it scores 0.3805, which is below random.
    8. It is inverted, not useless: churners stopped accumulating, so a low count today means churn, and at serving time it does not.
    9. Nothing was joined wrongly. The value was read at the wrong moment.
    10. The point-in-time correct build has a gap of 0.0000, and that is structural rather than lucky.
    11. So ask whether your offline number is a prediction of your online number.
    12. Current-state feature tables make the leaky join the default; a feature log makes it hard to write.
    13. A feature store is four things: registry, offline store with history, online store, shared transformation.
    14. Skew needs shared computation; leakage needs history. An online store alone solves neither.
    15. Batch-only scoring has no skew by construction and needs none of it.
    16. Test before buying: log the served features, recompute, compare.
