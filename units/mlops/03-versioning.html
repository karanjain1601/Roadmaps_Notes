CHAPTER 03

Versioning code, data and models

A year of weekly training snapshots costs 20,200 chunks against 520,000 once you store them by content — twenty-six times less, which makes "we cannot keep a copy of the data for every run" false by an order of magnitude. And when a prediction looks wrong, what it carried decides whether you face 201 candidates or exactly one.

    THE PROBLEM

    Three artefacts, three lifecycles

    Git solves one of them completely. The other two are why this chapter exists.

    The row that decides the design

    Data changes by a pipeline, continuously. Nobody commits it, so nothing prompts a version, and the identifier people reach for is a name — a table, a path, a partition, or the word "latest".

    A name is not an identifier. events_daily in March and events_daily today are different datasets wearing the same label, and chapter 1 measured the consequence: with a silently-refreshing source, 35.5% of days ran a combination nobody had tested.

    The fix in every case is the same primitive: identify things by a hash of their content rather than by where they live. Git already does this for code, which is why code is the solved case.

    THE OBJECTION

    What versioning the data actually costs

    The reason given for not doing it is storage. Here is the arithmetic, with the chunks counted rather than assumed.

    Split the dataset into chunks, hash each one, store each distinct hash once. A new snapshot re-uses every chunk that has not changed, so the cost of a version is the cost of what moved.

    The saving is proportional to how stable the data is

    At 2% churn a year of weekly snapshots costs 20,200 chunks — about twice the size of the dataset itself, for fifty-two versions of it. At 0.5% it is 41.4 times cheaper than full copies.

    And at 50% churn the saving falls to 2.0×, which is the honest limit: deduplication pays for slowly-changing data and does very little for a table that is fully rebuilt each run. Append-only data does best of all — 39× at the same 2% — and that is what most event tables are.

    The measured ratio tracks V / (1 + (V−1)f) at every level, so you can predict it from two numbers you already have: how often you snapshot, and how much moves between snapshots. If that comes out near 1, versioning the data really is expensive and you should snapshot less often rather than not at all.

    What you can use instead of building it

    Table formats — Delta Lake, Iceberg, Hudi — give you snapshot isolation and time travel, so "the data as of version 47" is a query rather than a copy. This is the least-effort option when your data is already in a lakehouse.

    Data version tools — DVC, LakeFS — put content addressing over object storage and keep pointers in git, which suits files rather than tables.

    Or simply a partitioned, immutable snapshot written by the pipeline and never mutated, with the path recorded. Crude, and it solves the actual problem.

    When a prediction looks wrong

    Two things about that table

    The first step is the big one. Stamping a model id on each prediction takes 201 candidates to 29 — a seven-fold cut for a single column. It is the cheapest thing in this unit and the one most often missing.

    The last row is qualitatively different. Going from 9 to 1 is not a further narrowing; it is the difference between an investigation and a lookup. With all three input hashes recorded on the model, "what produced this prediction" has an answer rather than a shortlist.

    And it gets worse the more you automate

    Unrecorded, the search grows 104-fold from a month to a year. Fully recorded it stays at 1 — bookkeeping is the only thing here whose cost does not grow with your retention policy.

    Worse, retraining more often makes the unrecorded case dramatically harder: monthly retraining leaves 115 candidates over 90 days, and daily retraining leaves 2,589. Every improvement in automation enlarges the space of things that could have produced yesterday's prediction.

    Which inverts the usual build order. Teams automate retraining first because it is visibly valuable, and add lineage later because it is not. The more automated the pipeline, the more the bookkeeping is worth — so it belongs before the automation, not after.

    THE THIRD ARTEFACT

    Versioning the model itself

    Weights are opaque, so the version is really about everything attached to them.

    The version is metadata, not the file
    You cannot diff two sets of weights meaningfully, so a model version is defined by what produced it: the three input hashes from chapter 2, the hyperparameters, and the metrics it achieved on a named evaluation set.
    Semantic version numbers do not fit
    There is no such thing as a backwards-compatible weight change. What people actually want from a version number is answered by two separate things: an immutable id for the artefact, and a stage saying whether it is a candidate, live, or retired. That is chapter 10.
    Version the interface separately
    The feature schema a model expects is a contract, and it changes far less often than the weights. Treating them as one version means every retrain looks like a breaking change; treating them separately means a retrain is routine and a schema change is not.
    Keep the evaluation set versioned too
    Comparing this month's 0.83 with last month's 0.81 is meaningless if the test set moved, and a test set built by the same pipeline as the training data usually did move.
    The trap in "just keep the last five models"

    Retention on the artefacts is easy. Retention on their inputs is what makes them useful, and the data snapshot is usually the first thing a cleanup job deletes because it is the largest.

    A rollback to a model whose training data has been garbage-collected gives you a working artefact you can no longer explain, retrain or audit. If the storage arithmetic above says a year of snapshots costs twice the dataset, keeping them as long as you keep the models is not the expensive option.

  1. Every input is a hash, not a name. snapshot:.../events@sha256:... resolves to one dataset forever; events_daily resolves to whatever is there today.
  2. The evaluation dataset is pinned too, so metric comparisons across versions mean something.
  3. The environment digest is free — your container registry already computed it.
  4. Predictions carry the model_id, which is the 201-to-29 step, and everything else is reachable from it.
  5. supersedes gives you the chain, so "what changed between the model that worked and the one that did not" is a diff of two of these documents.
    6. The minimum viable version of this

    If the full document is too much for where you are, the ordering from the demo is clear. Stamp the model id on every prediction — one column, and it is the seven-fold cut. Record the three input hashes on the model — about thirty lines in the training job, and it is the collapse to one.

    Everything else on that page is refinement. Those two are the whole difference between an investigation and a lookup.

    JUDGEMENT

    Five questions about a versioning scheme

  6. Is the training data referred to by name or by content? A table name is not a version, however carefully it is documented.
  7. Does a prediction record which model produced it? 201 candidates against 29.
  8. Does a model record which data produced it? 29 against 1.
  9. Are the data snapshots kept as long as the models? If not, a rollback gives you an artefact you cannot explain.
  10. Is the evaluation set pinned? If it moves, every metric comparison between versions is uninterpretable.
