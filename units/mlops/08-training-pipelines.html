Training pipelines

A notebook cannot be scheduled, tested, reviewed properly or reproduced once the kernel dies. Getting out of one is less about adopting a framework than about splitting the work into steps with declared inputs — after which caching, scheduling and testing all follow.

Iteration speed is a first-order concern, not a comfort

The number of ideas a team can test is roughly the working day divided by the cost of one iteration, and that number determines model quality more reliably than any individual technique. A pipeline where changing a hyperparameter means re-reading the warehouse and recomputing every feature turns a two-minute experiment into forty minutes, which means five experiments a day instead of a hundred — and the team stops exploring, because exploring has become expensive. Caching is not an optimisation, it is what keeps the inner loop from chapter 2 alive after you move to a pipeline. This is the main reason the notebook felt better, and it is recoverable.

the shape: steps that declare what they consume
# The essential move is not a framework — it is functions with explicit
# inputs and outputs, and a cache key derived from them.

@step(cache=True)
def load(snapshot: str) -> pd.DataFrame: ...

@step(cache=True)
def features(raw: pd.DataFrame, feature_cfg: dict) -> pd.DataFrame: ...

@step(cache=True)
def split(feats: pd.DataFrame, split_cfg: dict) -> tuple: ...

@step(cache=False)                       # cheap, and you want it fresh
def train(train_df, val_df, model_cfg: dict, seed: int) -> Model: ...

@step(cache=False)
def evaluate(model: Model, test_df, eval_cfg: dict) -> dict: ...

# A step's cache key is a hash of its INPUT VALUES plus its own source code.
# So changing model_cfg invalidates train and evaluate, and leaves load,
# features and split alone. That is the whole mechanism.
#
# THE PROPERTY THAT MAKES IT WORK: no step reads anything it did not declare.
# A step that reaches for a global, an environment variable or the current
# date has an input the cache cannot see, so the cache will hand you a stale
# result and you will spend an afternoon confused. This is the same
# discipline as chapter 4's no-now() rule, for the same reason.

# EVERY FRAMEWORK IS A VERSION OF THE ABOVE:
#   Metaflow    @step, @cache; the most pleasant Python ergonomics
#   ZenML       pipelines and steps with pluggable backends
#   Kubeflow    components as containers; heavy, Kubernetes-native
#   Dagster     assets with automatic materialisation (chapter 4)
#   Sagemaker / Vertex Pipelines   managed, cloud-locked
#   Make        genuinely works for small pipelines and is worth remembering
#
# You do not need one on day one. A Python package with a step registry and
# a hash-keyed parquet cache in a local directory is fifty lines and gets
# you most of the benefit. Adopt a framework when you need remote execution,
# heterogeneous resources per step, or a shared UI.

Leaving the notebook without losing it

the migration that does not end in a rewrite
THE FAILURE MODE: the notebook is handed over, an engineer reimplements the
feature logic in the pipeline, and the two now differ subtly. That is
chapter 14's skew arriving by the front door, and it is caused by the
migration rather than discovered by it.

THE MIGRATION THAT WORKS, in order:

  1. MOVE THE TRANSFORMATIONS INTO A PACKAGE. Take the feature engineering
     out of the cells and into functions in `src/features.py`. The notebook
     imports them. Nothing else changes yet, and nothing breaks.

  2. THE NOTEBOOK NOW ONLY ORCHESTRATES AND VISUALISES. Load, call
     functions, plot. If a cell contains logic, it belongs in the package.

  3. WRITE THE PIPELINE AGAINST THE SAME FUNCTIONS. Not a reimplementation —
     the same imports. The pipeline is a different caller of identical code.

  4. NOW THE NOTEBOOK IS OPTIONAL, and both paths are guaranteed to agree
     because there is only one implementation.

That is it. No framework required, and the ordering matters: doing step 3
before steps 1 and 2 is the rewrite you are trying to avoid.

WHAT NOTEBOOKS ARE STILL FOR, and it is a real list:
  * looking at data, which nothing else does as well
  * error analysis — pulling the 200 worst predictions and reading them
  * plots, and sharing a finding with a colleague
  * the first hour of any new problem

WHAT THEY ARE NOT FOR:
  * anything scheduled
  * anything whose output someone depends on
  * anything you will need to reproduce
  * anything longer than about 200 lines

TOOLS THAT HELP: nbstripout in a pre-commit hook so notebooks stop producing
unreviewable diffs, jupytext to keep a .py mirror that can be reviewed, and
papermill if you genuinely must execute a notebook as a pipeline step — a
legitimate transitional step, and not somewhere to stay.

Hyperparameter search

and how to not waste a week of GPU on it
import optuna

def objective(trial):
    cfg = dict(
        num_leaves    = trial.suggest_int("num_leaves", 16, 256, log=True),
        learning_rate = trial.suggest_float("learning_rate", 1e-3, 0.3, log=True),
        min_child     = trial.suggest_int("min_child_samples", 5, 200, log=True),
        subsample     = trial.suggest_float("subsample", 0.5, 1.0),
    )
    model = train(train_df, val_df, cfg, seed=SEED)
    return evaluate(model, val_df)["pr_auc"]

study = optuna.create_study(
    direction="maximize",
    sampler=optuna.samplers.TPESampler(seed=SEED),
    pruner=optuna.pruners.MedianPruner(n_warmup_steps=5),   # kill bad trials
    storage="postgresql://...",        # resumable, and parallelisable
    study_name="churn-2026-03",
)
study.optimize(objective, n_trials=100, n_jobs=4)

# FOUR THINGS THAT MATTER MORE THAN THE SEARCH ALGORITHM:
#
#   1. RANDOM SEARCH BEATS GRID SEARCH, essentially always. Grid wastes
#      trials on dimensions that do not matter; random covers each dimension
#      at full resolution. Bergstra and Bengio (2012), and it is still the
#      most useful practical result in this area
#
#   2. LOG SCALE FOR SCALE PARAMETERS. Learning rates, regularisation and
#      leaf counts should be sampled logarithmically. A uniform search over
#      [1e-3, 0.3] spends 99% of its trials above 0.003
#
#   3. PRUNE EARLY. Stop trials that are clearly losing after a few
#      iterations. Typically a 2-5x effective speedup for free
#
#   4. TUNE FEATURES BEFORE HYPERPARAMETERS. This is the one people get
#      backwards. A new informative feature is usually worth more than any
#      amount of hyperparameter search, and a hundred trials on a weak
#      feature set is an expensive way to find a local optimum

# AND THE HONEST CAVEAT: the best trial's validation score is optimistically
# biased. You ran a hundred experiments and kept the maximum, so some of
# that number is selection noise (chapter 7). Report the TEST score of the
# chosen configuration, evaluated once, and expect it to be a little lower.

# LOG EVERY TRIAL to your tracking server, not just the winner. The shape of
# the search — which dimensions mattered, where the good region was — is the
# thing you want next quarter when the data has moved and you are deciding
# whether to search again or reuse the configuration.
Distributed training is a last resort, not a milestone

The order to exhaust before distributing: use a smaller sample for the inner loop, since most decisions are visible on 10% of the data; reduce precision to fp16 or bf16, which is often a 2× speedup with no measurable quality cost; fix the data loader, because on a large fraction of "GPU-bound" jobs the GPU is actually idle waiting for input — check utilisation before assuming; use gradient accumulation to get a large effective batch on one device; and rent a bigger machine, because a single 8-GPU node with NVLink is dramatically simpler than two 4-GPU nodes and often no more expensive. Only then distribute. Multi-node training brings gradient synchronisation, a communication backend, stragglers, checkpoint coordination, and reproducibility that is now bounded by floating-point reduction order across workers (chapter 3). It is a large step up in operational complexity and it should be forced on you by a model that genuinely does not fit.

if you must distribute, the three shapes
DATA PARALLEL — every worker holds the whole model, each processes a
different batch, gradients are averaged.
  * the default and the right first answer
  * PyTorch DDP, or torchrun for launching
  * scales until the model no longer fits on one device
  * NOTE the effective batch size is per-device × devices, so you must
    rescale the learning rate. Forgetting this is the commonest bug here,
    and it presents as "distributed training made the model worse"

SHARDED DATA PARALLEL — the model, gradients and optimiser state are split
across workers as well.
  * FSDP, or DeepSpeed ZeRO stages 1-3
  * what you use when the model plus optimiser state exceeds device memory
  * optimiser state is often the largest term — Adam keeps two extra
    tensors per parameter, so sharding it alone (ZeRO-1) is a big win

MODEL PARALLEL — different layers on different devices.
  * pipeline parallelism, tensor parallelism
  * for models too large for any single device even sharded
  * genuinely complex, and you will know if you need it

CHECKPOINTING IS THE PART THAT BITES. A multi-day job on spot instances
will be interrupted, so checkpoints must be frequent, complete (model,
optimiser, scheduler, dataloader position, RNG state) and resumable — and
resumption must be TESTED, because a checkpoint that restores the weights
and not the optimiser state silently restarts your training dynamics. Test
it by killing a job deliberately on the second day.
The pipeline should be runnable end to end in under a minute on a sample

Give the pipeline a --sample flag that reads a thousand rows and trains for one epoch. This is a small addition with three separate payoffs. CI can run the whole pipeline on every commit, so a broken step is caught by a pull request rather than by a nightly job at 3am — and structural failures are most of what breaks. Onboarding stops requiring warehouse credentials and four hours, because a new person can run the real pipeline in a minute and see it work. And you get an executable smoke test after any infrastructure change. It costs an afternoon to add and it is the difference between a pipeline people trust and one people are afraid to touch.

The short version

  1. Split the work into steps with declared inputs. Caching, scheduling and testing all follow from that one property.
  2. A step that reads an undeclared input breaks the cache silently — same discipline as no now() in a transformation.
  3. Iteration speed determines model quality more reliably than any technique. Caching keeps the inner loop alive.
  4. Move transformations into a package first, then write the pipeline against the same functions. Reversing that order is the rewrite you are avoiding.
  5. Random search beats grid search, use log scales for scale parameters, and prune losing trials early.
  6. Tune features before hyperparameters. A hundred trials on a weak feature set finds an expensive local optimum.
  7. Exhaust sampling, mixed precision, the data loader and a bigger machine before distributing anything.
  8. Give the pipeline a sample mode so CI runs it end to end in under a minute.
