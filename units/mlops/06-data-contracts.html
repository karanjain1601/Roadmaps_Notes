    THE FAMILIES

    Three kinds of check

    They cost different amounts to write and catch entirely different things.

    Schema
    Columns exist, types are right, declared not-null columns are not null, values fall in a permitted set. Cheap, generated from a definition, and completely blind to whether the numbers mean anything.
    Distribution
    The mean, spread, null rate or category mix of a column against a reference window. Catches value faults that schema cannot see, and is the source of nearly all the false alarms in a validation suite.
    Semantic
    Freshness, uniqueness, row counts, referential integrity, cross-column consistency. Requires knowing what the data is, which is why teams write it last — and it is the family that catches the faults the other two structurally cannot.
    The reason all three exist

    Each family is blind to a class of fault by construction rather than by oversight. A schema check cannot see a unit change because the type did not change. A distribution check cannot see stale data because the distribution did not change. A semantic check will not notice a new column appearing because nobody wrote a rule about it.

    The next demo runs all three against seven realistic faults and measures which fires on what.

    Stale data passes everything except freshness

    Schema 0%, distribution 0%. Not because the checks are badly written — because they cannot possibly fire. The columns are the right columns, the types are the right types, and the distribution matches the reference perfectly since it is data from the reference period.

    Only the freshness check sees it, at 100%. And freshness is typically the last check a team adds, because it is the one that requires knowing something about the pipeline rather than about the table.

    Duplicated rows behave the same way: distribution 1%, semantic 100%. Duplicating a random 30% of a sample barely moves its mean, so a distributional monitor has nothing to detect.

    Each family is blind by construction

    Schema catches structure and misses meaning. 100% on a dropped column, 0% on a hundred-fold unit change — the type is still a number, so nothing is violated.

    Distribution catches values and misses identity. 100% on the unit change, 0% on stale data and 1% on duplicates.

    Semantic catches the rest, and it is the only family that caught three of the seven faults here.

    The union catches all seven. Schema alone catches three, which is the answer to "we have data validation" when what is meant is a generated schema file.

    This is why validation suites get switched off

    Fifty columns at the conventional three sigma raise a false alarm on 12.6% of clean days — one every eight days, on data with nothing wrong. At two sigma it is 90.3%: an alert almost every morning.

    The rate is exactly 1 − (1−p)n, which is the multiplicity arithmetic arriving through the monitoring dashboard. Nobody chose a 90% false alarm rate; they chose a sensible per-column threshold and then added columns.

    After a fortnight of this the alerts are muted, and the suite's real value — catching the fault it would have caught — goes with them.

    The fix is fewer checks, not stricter ones

    Tightening trades one problem for the other: going from z>2 to z>4 cuts false alarms from 90.3% to 0.3% and detection from 84.1% to 15.9%.

    Fix the alarm budget instead and compare suites fairly. At a budget of 1.34% of days — roughly one false alarm a quarter — here is what each suite can detect:

    Every column you monitor spends part of the budget

    Five columns detect 50.0% of a real shift; two hundred detect 16.2%, for exactly the same number of false alarms. A column that never moves still consumes alarm budget every single day, because it still has a chance to fire.

    So the productive question is not "what threshold" but "which five columns would we actually act on". Monitor those properly, and check the rest with schema and semantic rules, which do not spend a probabilistic budget at all.

    THE INTERFACE

    A contract is an agreement, not a test

    The checks above run in your pipeline. A contract puts them at the producer.

    The same rule, enforced in two places
    Validation in your pipelineA contract at the producer
    When it failsAfter the bad data was publishedBefore
    Who is pagedYouThe team that broke it
    Blast radiusYour pipeline stopsThe change is rejected
    NeedsNothing from anyoneAgreement, and a producer who can enforce it
    CatchesAnything you can expressOnly what was agreed
    Both, in that order

    Validation in your pipeline is unilateral: you can add it this afternoon and it will catch the unit change on the day it arrives. Start there.

    A contract is better and slower, because it requires another team to agree that breaking your model is their problem. The realistic path is to run validation first, collect the incidents it catches, and use those as the argument for a contract — an actual list of dates when a change broke something downstream is far more persuasive than a proposal.

    What belongs in a contract
    Schema and semantics: columns, types, nullability, key uniqueness, permitted values, freshness SLA, and expected volume range. These are properties the producer controls and can test in their own CI.
    What does not
    Distributions. The producer cannot promise your feature's mean will stay within three sigma, because that depends on the world. Distributional monitoring belongs on your side, and finding a shift is the start of a conversation rather than a breach.
    Version it, and deprecate rather than change
    A contract that changes silently is not a contract. New column: additive, fine. Removed or retyped column: a new version, with both served during a migration window.
    Make breaking it fail the producer's build
    A contract nobody tests is documentation. The value comes from the producer's pipeline failing before publishing, which is the only mechanism that moves the cost to where the change was made.

    PLACEMENT

    Where the checks go, and what they do on failure

  1. At ingest, before anything expensive. Chapter 4's pipeline puts validate immediately after ingest for this reason: a fault caught there costs one minute, and the same fault caught after training costs a hundred and two.
  2. Fail the run, do not warn. A warning on a scheduled job is a log line nobody reads. If the check is not worth stopping for, it is not worth running.
  3. Except for distributional checks, which should warn. They are the noisy family, and a 12.6% false-alarm rate that halts the pipeline is worse than the fault it is looking for.
  4. Quarantine rather than drop. Writing the failing rows somewhere inspectable turns "the check fired" into "here are the 340 rows that caused it", which is the difference between a five-minute triage and an afternoon.
  5. Check the output too. Prediction distributions, score ranges, null rates in the output table. Chapter 16 extends this to production, and the same code usually serves both.
    6. The check that hides the fault

    A validation step that silently drops bad rows and continues is worse than no check at all. The pipeline succeeds, the metrics look normal because the anomalous rows are gone, and the fault is invisible in exactly the place it would have been most visible.

    If rows must be dropped, count them and alert on the count. A drop rate that jumps from 0.1% to 12% is the signal, and it is lost the moment the drop is treated as routine cleaning.

    JUDGEMENT

    Five questions about a validation suite

  6. Would it catch yesterday's data being delivered again? Schema 0%, distribution 0%. If there is no freshness check, the answer is no.
  7. Would it catch a unit change? Schema cannot see it. This needs a distributional or range check on the actual values.
  8. How many columns are monitored, and at what threshold? Fifty at three sigma is a false alarm every eight days.
  9. When did an alert last cause an action? If the answer is "we mute them", the suite is already off.
  10. Does a failure stop the run or drop the rows? Silent dropping makes the fault invisible.
