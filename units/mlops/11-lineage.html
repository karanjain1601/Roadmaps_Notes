CHAPTER 11

Lineage and provenance

A dataset turns out to be wrong. On a fifteen-model platform it affects six of them — and 93% of those never read it. They read a feature table that reads it, so searching the codebase for the table name finds the other seven per cent.

    SCOPE

    What lineage adds to versioning

    Chapter 3 gave every artefact an identity. Lineage is the edges between them.

    The forward direction is the expensive one and the useful one

    Backwards provenance is nearly free once chapter 3's hashes are recorded: the model card names its inputs, and you follow the chain.

    Forwards impact needs something chapter 3 does not give you — the set of consumers of an artefact, which nobody records as a side effect of anything. And it is what you need at nine on a Tuesday when someone discovers a fault in a table from three weeks ago.

    Almost none of them read the dataset

    93% of the affected models never touch that dataset directly. They read a feature table that reads it.

    Which means the obvious investigation — search the model repositories for the table name — finds 7% of the problem and misses the rest. On one example graph, direct dependencies give 5 model-dataset links and the transitive closure gives 68.

    This is why lineage has to be captured rather than reconstructed. A one-hop answer feels complete, produces a short list, and is wrong by a factor of thirteen.

    And it is worth more the bigger you get

    A bad dataset touches 53% of a ten-model platform and 15% of a sixty-model one. The number of affected models barely grows — 5.3 to 8.7 — while the platform quadruples.

    So the retraining lineage saves you goes from 47% to 85%. Small platforms can plausibly retrain everything and shrug; large ones cannot, and the argument for capturing lineage strengthens exactly as the cost of not having it becomes unaffordable.

    The corollary is uncomfortable: the best time to start capturing lineage is when it is least obviously worth it.

    How fine the lineage needs to be

    The first and last rows are the argument

    On a 200-column table where models read eight columns each, column-level lineage flags 4.7 models against dataset-level's forty — an 8.5-fold narrowing for the same fault.

    On a 10-column table where models read eight of them, it flags 100% — a narrowing of 1.00×, which is to say none at all. Every reader genuinely is affected, and the finer lineage told you something you already knew.

    So column-level capture is not a platform-wide policy. It pays in proportion to table width divided by columns read, which means it is worth turning on for your wide analytical tables and not for your narrow dimension ones — a per-table decision with an arithmetic answer.

    What each granularity can answer
    GranularityAnswersCost to capture
    Job levelWhich pipelines ran, in what orderFree — the scheduler has it
    Dataset levelWhich tables fed whichLow — parse the queries
    Column levelWhich fields fed whichMedium — needs query analysis
    Row levelWhich records fed whichHigh — scales with data volume
    Job and dataset level are nearly free, and most people do not have them

    Your orchestrator already knows which task ran before which, and most query engines can emit the tables a statement read and wrote. Together those give the entire first demo — the 93% indirect, the transitive closure, the blast radius.

    Row-level lineage is the one that is genuinely expensive, because the metadata scales with the data. It is worth it for a narrow set of obligations — a deletion request, a regulated audit — and almost never worth it as a default.

    BACKWARDS

    From a prediction to a row

    The questions that only provenance can answer, and roughly what each needs.

    "Why did this customer get this score?"
    Needs the model id on the prediction and the feature values it was scored with. That is chapter 3's first step plus chapter 7's logged feature vectors, and it is the most commonly asked and most commonly unanswerable question in this list.
    "What data was this model trained on?"
    Chapter 3's input hashes. One field, resolvable to a snapshot.
    "Which models saw this customer's data?"
    Row-level lineage, or a workable approximation: which training snapshots contained the record, and which models were built from those snapshots. The approximation is usually enough and costs enormously less.
    "Has this metric been computed the same way all year?"
    Column-level lineage plus versioned transformation code. This is the question that reveals a definition quietly changed in March, which is far more common than it sounds.
    Deletion requests are where lineage stops being optional

    A request to delete a person's data reaches beyond the source table into every snapshot that captured it, every feature table derived from those, and arguably every model trained on them. Without lineage the honest answer is "we do not know where it went".

    The tractable position is to bound the problem rather than solve it: snapshots have retention, so data ages out; models have retention tied to their snapshots; and the mapping from person to snapshot is recorded even if the mapping from person to model weights is not. That is a defensible story built from chapter 3's bookkeeping, and it is much cheaper than row-level lineage everywhere.

    PRACTICE

    Capturing it without a project

  1. Start with what the orchestrator knows. Task dependencies are a graph you already have, and they give job-level lineage for the cost of exporting them.
  2. Emit reads and writes from each step. A step that declares its inputs and outputs — which chapter 4 already required for caching — is emitting dataset-level lineage as a side effect.
  3. Parse queries where you can. Most warehouses expose the tables and columns a statement touched. This is where column-level lineage comes from without anyone writing annotations.
  4. Record consumers, not just producers. The forward direction is the expensive one and the one that answers the Tuesday-morning question.
  5. Do not build a catalogue nobody writes to. Lineage entered by hand is stale within a month; lineage emitted by the pipeline that does the work cannot be.
    6. The test of a lineage system

    Not "is the graph complete" but: pick a table at random and ask which models would need retraining if it were corrupt. If the answer takes more than a minute, the graph is not being used, and a graph that is not used is not maintained either.

    JUDGEMENT

    Five questions about lineage

  6. Can you list the consumers of a table? Producers are easy and consumers are the ones you need in an incident.
  7. Does the answer include transitive consumers? A one-hop answer found 7% of the affected models here.
  8. Is the lineage emitted or entered? Hand-maintained lineage is stale within a month.
  9. How wide are your widest tables? Column-level capture pays 8.5× at 200 columns and 1.00× at ten.
  10. What would you do about a deletion request today? If the answer is a meeting, bound the problem with retention rather than solving it with row-level lineage.

    7. The affected count barely grows with the platform — 5.3 models at ten, 8.7 at sixty.
    8. So the saving rises from 47% to 85%, and lineage is worth most when the platform is largest.
    9. Which means the best time to start is when it is least obviously worth it.
