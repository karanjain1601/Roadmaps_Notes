Packaging and serving

The decision that determines most of your serving complexity is made before you write any of it: whether the prediction can be computed in advance. Getting that wrong in the direction of "real time" is the most expensive default in applied ML.

Which serving pattern

Batch, online, or streaming Three questions decide it. The answer is batch far more often than people build for.

Batch inference is a pipeline that ends in a write

It needs no service, no latency budget, no autoscaling, no online feature store, no request-path error handling and no capacity planning. It is chapter 4's pipeline with a model call in the middle, and it inherits every property you already built: idempotency, backfills, validation, caching. A very large fraction of production ML is this and should be, including most churn scoring, lead scoring, recommendation precomputation, forecast generation, risk scoring for review queues and content classification of a corpus. The tell that you need something else is narrow: the prediction depends on input that only exists at request time, or on state that changed in the last few minutes. Absent one of those, building a service is work you can decline.

# inputs and model version to a partitioned table, which is exactly what

# FEATURE_ORDER deserves a note. Many model formats are positional — a
# tree ensemble or a plain numpy-based model receives an array, not a
# dataframe with names. If the column order at serving differs from
# training, every feature is silently read as a different feature. No
# error, and predictions that are confidently meaningless.
#   * pin the order in one shared constant, used by both paths
#   * better, log an MLflow SIGNATURE with the model so the server can
#     validate names and dtypes and reject a mismatch (chapter 7)
# This is one of the four shapes of skew in chapter 14 and it is the
# easiest to prevent.

# THE THING PEOPLE SHIP: a FastAPI app that pickle-loads a model.
# It works, and it is worth knowing what it is missing.

from fastapi import FastAPI
import mlflow.pyfunc

app = FastAPI()
MODEL = None

@app.on_event("startup")
def load():
    global MODEL
    MODEL = mlflow.pyfunc.load_model("models:/churn@champion")   # alias, ch 9

@app.get("/healthz")                # liveness: is the process up
def healthz(): return {"ok": True}

@app.get("/readyz")                 # readiness: is the MODEL loaded
def readyz():
    if MODEL is None: raise HTTPException(503)
    return {"ok": True, "version": MODEL.metadata.run_id}

@app.post("/predict")
def predict(req: PredictRequest):
    feats = build_features(req)              # shared code (chapter 5)
    p = float(MODEL.predict(feats[FEATURE_ORDER])[0])
    log_prediction(req, feats, p, MODEL.metadata.run_id)   # ASYNCHRONOUSLY
    return {"score": p}

# THE FIVE THINGS THAT NAIVE VERSION USUALLY GETS WRONG:
#
#   1. NO SEPARATE READINESS PROBE. A liveness check that returns 200 while
#      the model is still loading means Kubernetes routes traffic to a pod
#      that cannot serve. Two endpoints, not one.
#
#   2. SYNCHRONOUS PREDICTION LOGGING. Writing to a database or Kafka on
#      the request path adds its latency and its failure modes to yours.
#      Buffer in memory and flush on a background task — and accept that
#      you will lose a few records on a hard kill, which is fine for
#      monitoring data.
#
#   3. NO INPUT VALIDATION. A request missing a field, or sending a string
#      where a float is expected, should be a 422 rather than a NaN
#      propagating into a confident prediction. Pydantic plus the model
#      signature covers most of it.
#
#   4. THE MODEL LOADED AT IMPORT TIME, not in a startup hook, which makes
#      the container slow to start and the failure mode a crash loop rather
#      than an unready pod.
#
#   5. NO TIMEOUT OR FALLBACK. If feature lookup is slow, the request hangs.
#      Decide in advance what happens when features are unavailable —
#      usually a default score plus a metric increment, not a 500.

# WHAT A DEDICATED MODEL SERVER ADDS: dynamic batching (chapter 13), multiple
# models and versions per process, GPU sharing, and framework-native
# runtimes. Triton, TorchServe, TF Serving, KServe, BentoML, Ray Serve.
# Worth it when you are GPU-bound or serving many models; unnecessary
# overhead for a scikit-learn model on CPU.

The model is not the whole artefact

What has to travel together is the model and the preprocessing that produced its inputs — the fitted scaler, the encoder's category mapping, the imputer's learned medians, the feature order. Saving the estimator alone and reimplementing the preprocessing in the service is the most common route to skew (chapter 14), because the reimplementation is written from memory and the fitted state is silently different. Serialise the whole pipeline as one object: a scikit-learn Pipeline, an MLflow pyfunc wrapper with a custom predict, or an ONNX graph including the preprocessing operators. Then the round-trip test from chapter 10 — save, reload in a fresh process, assert identical predictions on a fixed sample — actually proves something, because the thing you reloaded is the thing that runs.

Streaming inference

the middle case, and its one hard part
# Events arrive, are scored, and the score is emitted or stored. Between
# batch and online: no request waiting for you, but freshness in seconds.

# Typical shape with Kafka:
for msg in consumer:                          # or Flink / Spark Structured
    event    = parse(msg.value)
    state    = state_store.get(event.entity)  # rolling aggregates
    features = build_features(event, state)   # shared code again
    score    = model.predict(features)

    producer.send("scores", key=event.entity, value=score)
    state_store.update(event.entity, event)
    consumer.commit()                         # AFTER the side effects

# THE HARD PART IS THE STATE, not the model call. Features like "count of
# transactions in the last hour" require a rolling window maintained across
# events, and that state must survive restarts, be correct under
# out-of-order arrival, and be reproducible for training.
#
#   * WATERMARKS decide how long to wait for late events before closing a
#     window. Too short and you drop real data; too long and you add latency
#   * CHECKPOINTS make state recoverable. Flink and Spark do this for you;
#     hand-rolled consumers usually do not, and the failure surfaces as
#     wrong aggregates after a restart rather than as an error
#   * COMMIT AFTER SIDE EFFECTS, or a crash between the two loses the event.
#     Commit before, and you get at-most-once; commit after, at-least-once
#     with possible duplicates. Duplicates are usually the safer failure

# AND THE POINT THAT CONNECTS TO CHAPTER 5: whatever computes these rolling
# features must produce the SAME values that the offline training pipeline
# produced for historical events. A streaming aggregate computed over
# arrival order and an offline aggregate computed over event time will
# disagree, and the model trained on one is served the other.
#
# This is the hardest instance of the parity problem in the whole unit, and
# it is why streaming feature pipelines are where feature stores earn their
# cost — they materialise both sides from one definition.

# THE PRACTICAL ARCHITECTURE that avoids most of this: batch for the heavy
# historical features, streaming for the handful that genuinely must be
# fresh, joined at scoring time. A hybrid rather than a compromise.
Ship a serving container that is not built by the data scientist

The training environment and the serving environment want different things. Training wants pandas, matplotlib, notebook tooling, the whole scientific stack — often two gigabytes of image. Serving wants the minimum that can load the model and respond: no plotting, no notebook, no training-only libraries. A serving image built from a separate, minimal lockfile is smaller, starts faster, has a much smaller vulnerability surface, and forces you to discover which dependencies the model actually needs. That last point is the real benefit — a model whose preprocessing imports something from the training environment will fail to load in the slim image, loudly, in CI, instead of quietly working because everything happened to be present. Build both images from the same base and run chapter 10's round-trip test inside the serving one.

The short version

  1. Ask whether the prediction can be precomputed. If yes, batch — and skip nearly all serving complexity.
  2. Batch inference is a pipeline that ends in a write, and it gives you the prediction log for free.
  3. Feature order matters for positional formats, and getting it wrong is silent. Pin it, or ship a signature.
  4. Liveness and readiness are different probes. One endpoint means traffic to a pod that cannot serve.
  5. Log predictions asynchronously. A write on the request path adds its latency and its failures to yours.
  6. Serialise the whole pipeline, preprocessing included. Reimplementing it in the service is the classic skew.
  7. Streaming's hard part is the state, not the model call — and matching offline aggregates is harder still.
  8. Build a separate, minimal serving image. It exposes hidden dependencies loudly in CI.
