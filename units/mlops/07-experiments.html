Experiment tracking

The highest ratio of value to effort in this unit: a server and a few lines in your training script. What makes it worth a chapter is that most teams log the wrong things and discover it during the one conversation the tracking existed to settle.

mlflow w&b metrics artifacts

The conversation this exists to settle

Six months after a model went live, someone asks why the current version performs worse than the one before it. Or a reviewer asks whether the improvement you reported was real. Or an auditor asks what data trained the model that declined an application.

Each of those is a question about a training run that happened in the past. Whether you can answer depends entirely on what got recorded at the time.

Which questions can you answer? Choose what your runs record, then see which questions have factual answers.

Tracking and reproducibility are different things

A tracked run tells you what happened: these parameters produced this metric. That is enough to compare runs and to notice a regression. It is not enough to recreate one — for that you need the data version, the environment and the seed as well (chapter 3), and those are exactly the three fields that most tracking setups omit because the tracking library does not prompt for them. The result is a table of results you cannot regenerate, which is worth having and is not what people believe they have. The test is the same one from chapter 3: pick a run from three months ago and try to reproduce its number.

Log a business metric alongside the statistical one

AUC of 0.87 is not a fact anyone outside the team can act on, and it is not the quantity you are optimising. What matters is something like "at the threshold we actually use, we catch 62% of fraud and falsely flag 1.4% of good transactions" — or the expected cost, given what a false positive and a false negative each cost. Log that number in every run. Two consequences follow. Comparing models becomes a conversation about outcomes rather than about metrics, so stakeholders can participate. And you discover the cases where AUC improved and the business metric got worse, which happens more than people expect — a model can be better at ranking the middle of the distribution while being worse at the operating point you deploy at, and an aggregate ranking metric cannot see the difference.

THE TOOLS ARE MORE ALIKE THAN THE COMPARISON TABLES SUGGEST. All of them
log parameters, metrics and artefacts, all have a Python decorator or
context manager, all render a comparison table. Picking one is a smaller
decision than it feels.

WHAT ACTUALLY DETERMINES WHETHER TRACKING WORKS:

  1. IS IT AUTOMATIC? If logging is a thing people remember to do, half the
     runs will be missing. Put it in the training entrypoint so every run
     is tracked by construction, including the exploratory ones — the
     exploratory run you cannot find later is the one you wanted.

  2. DOES CI LOG TOO? Runs launched from a pipeline should appear in the
     same place as runs from a laptop, tagged so you can tell them apart.
     A tracking server containing only manual runs is missing the ones that
     produced production models.

  3. IS THERE A NAMING CONVENTION? Experiments named "test", "test2" and
     "final_v3_actually" are a well-known genre. One experiment per
     objective, run names that encode the variant, and tags for anything
     you will filter on.

  4. IS IT WHERE PEOPLE LOOK? A tracking server nobody opens is a write-only
     log. Link runs from your pull requests and post the comparison into the
     channel where the decision gets made.

ON SELF-HOSTING MLFLOW: the default local file store is fine for one person
and falls over as a team. A real deployment is the tracking server, a
Postgres backend for metadata, and object storage for artefacts. That is a
half-day of setup and worth doing properly early, because migrating a file
store full of history later is tedious.

Comparing runs honestly

the three mistakes
1. COMPARING RUNS WITH DIFFERENT DATA. The most common one. You change the
   model, and the data snapshot has also moved because the query picked up
   another week of rows. The metric improved. You attribute it to the model.
   -> Compare only runs sharing a data version. Make the data version a
      first-class filter in your tracking, and treat a change in it as
      invalidating the comparison.

2. COMPARING SINGLE RUNS WHEN THE NOISE FLOOR IS UNKNOWN. Chapter 3's
   point, and it bears repeating because tracking makes it worse: a table
   of runs with three decimal places invites you to believe differences
   that are entirely seed variance.
   -> Log the seed. Run the baseline three times. Put the spread somewhere
      visible, and treat improvements below it as unproven.

3. SELECTING ON THE VALIDATION SET REPEATEDLY. Fifty experiments, each
   evaluated on the same validation split, and you keep the best. That best
   number is optimistically biased — you have fitted your MODEL SELECTION
   to the validation set, which is a real and well-documented effect.
   -> Keep a test set that is used once, at the end, by the run you have
      already decided to ship. If you look at it twice, it is a second
      validation set.

AND ONE THING TO DO RATHER THAN AVOID: write the decision down in the run.
MLflow tags, a note field, a description — anywhere durable. "Chose this
over run 41 because recall at the operating point was better despite lower
AUC" is the sentence that saves an afternoon in six months, and it exists
nowhere else. The metrics record what happened; only you can record why it
mattered.
Log the data profile with the run

A small addition with an outsized payoff later: alongside the metrics, log a JSON profile of the training data — per feature, the mean, standard deviation, null rate, quantile edges and category set (chapter 6). It is a few kilobytes. It becomes the baseline that production drift is measured against, so every model carries the statistical signature of the world it learned, and a drift check is a comparison against a specific model's own training distribution rather than against some global baseline that has itself moved. It also answers "was the data different?" during a regression investigation, immediately, without going back to the warehouse to reconstruct what a snapshot looked like — which by then may not be possible.

The short version

  1. Tracking is a library call. The highest value-to-effort ratio in the unit, and most teams log the wrong fields.
  2. Tracked is not reproducible. Data version, environment and seed are the three usually missing.
  3. Log whether the git tree was dirty. A commit hash from a modified working tree is a false record.
  4. Log a business metric, not only AUC. Models exist where AUC improved and the operating point got worse.
  5. Log per-slice metrics from the start; aggregates hide the failures that matter (chapter 10).
  6. Log the data profile — it becomes the drift baseline that ships with the model.
  7. Make tracking automatic and include CI runs, or half your history is missing.
  8. Compare only runs sharing a data version, know your noise floor, and use the test set once.
