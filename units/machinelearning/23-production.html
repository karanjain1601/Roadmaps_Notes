From notebook to production

A model that scores well in a notebook has completed roughly a third of the work. What remains is making it run reliably on live data, noticing when it stops working, and being able to fix it without breaking anything — which is a software engineering problem with some statistics attached.

What changes

In the notebookIn production
DataA clean, static fileArriving late, malformed, with new categories and missing columns

The reframe that helps

A deployed model is a piece of software with an unusual property: it can fail without erroring. Ordinary bugs crash or produce visibly wrong output; a stale model returns confident, well-formatted, plausible predictions that are simply worse than they used to be. Everything in this chapter exists to make that failure mode visible.

Ship the threshold with the model

Chapter 15 established that the decision threshold is a separate choice from the model, made from cost ratios on validation data. It is astonishingly common for that number to live only in a notebook, so the service defaults to 0.5 and the carefully reasoned operating point is lost. Treat the threshold as part of the artefact, and record why it was chosen.

Serving

PatternHowLatencyUse when
BatchScore everything on a schedule, write to a tableHoursThe default. Simplest to operate, and enough for most business problems
OnlineREST or gRPC endpoint, one request at a timeMillisecondsFeatures only exist at request time — fraud, pricing, ranking
StreamingConsume events, emit predictionsSecondsContinuous event flows
Embedded / edgeModel runs on the deviceMicrosecondsOffline operation, privacy, or no round trip available

Reach for batch unless something forces you not to. It has no availability requirement, no latency budget, retries are free, and a failure means yesterday's scores are still there. Online serving multiplies the operational surface, and a surprising number of "real-time" requirements dissolve when someone asks how quickly the recipient actually acts on the prediction.

Training–serving skew

The most common production defect in classical ML: the preprocessing at training time and the preprocessing at serving time diverge. A rounding difference, a category encoded differently, a missing-value default that changed. The model receives inputs subtly unlike anything it trained on and degrades quietly.

Ship one artefact
The fitted pipeline, containing every transformation. If the service does any feature computation of its own, that code is a divergence risk.
Validate the input schema
Check column names, types and ranges on every request. Reject or flag rather than silently coercing.
Use a feature store, or at least shared code
Aggregation features are the worst offenders because they are recomputed in two places. A feature store computes them once and serves both paths.
Log the features you actually served
Not just the prediction. When something goes wrong, the served feature vector is the only thing that lets you reproduce it.
python — a minimal, defensive service
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
import joblib, pandas as pd, json, time, logging, uuid

app = FastAPI()
model = joblib.load("models/churn_v3.joblib")
meta  = json.load(open("models/churn_v3.meta.json"))
log   = logging.getLogger("predictions")

class Request(BaseModel):
    customer_id:   str
    tenure_months: int   = Field(ge=0, le=600)      # range checks catch upstream bugs
    monthly_spend: float = Field(ge=0)
    plan:          str
    logins_30d:    int   = Field(ge=0)

@app.post("/predict")
def predict(req: Request):
    t0 = time.perf_counter()
    row = pd.DataFrame([req.model_dump()])[meta["feature_names"]]   # enforce column order
    try:
        p = float(model.predict_proba(row)[0, 1])
    except Exception as e:
        log.exception("scoring failed")
        raise HTTPException(500, "scoring failed") from e

    out = {"request_id": str(uuid.uuid4()),
           "probability": round(p, 4),
           "decision": p >= meta["threshold"],
           "model_version": meta["version"]}

    # log FEATURES as well as the prediction — this is what makes drift
    # detection and incident debugging possible three months from now
    log.info(json.dumps({**out, "features": req.model_dump(),
                         "latency_ms": (time.perf_counter() - t0) * 1000}))
    return out

@app.get("/health")
def health():
    return {"status": "ok", "model_version": meta["version"]}

Testing a model

Unit tests do not transfer directly — you cannot assert that a prediction equals 0.7. What you can test is behaviour.

Test typeAssertsExample
Data schemaInputs match the contractColumns present, types correct, values in range, nulls within tolerance
Minimum functionalityObvious cases are handledA customer with zero logins and a cancelled card scores above 0.5
InvarianceIrrelevant changes do not move the outputChanging a customer's name, or their ID, leaves the prediction identical
DirectionalKnown relationships holdIncreasing recent defaults never increases the approval score
Regression on a golden setPerformance has not droppedPR-AUC on a fixed evaluation set stays within tolerance of the recorded value
Serving parityThe service matches the notebookScore 1,000 rows through both paths; predictions must match to 1e-6
LatencyThe budget is metp99 under 80 ms at expected load
The serving-parity test is the one to write first

Take a thousand rows, score them in the training environment, score them through the deployed service, and assert the predictions match. It catches column ordering, dtype coercion, encoder mismatches and library version differences in one shot — the entire training–serving skew family. It takes twenty minutes to write and it will catch a real bug within the first few deployments.

Rolling it out

StrategyHowCatches
ShadowNew model scores live traffic; outputs logged, not usedSkew, latency and distribution problems with zero user risk. Always do this first
CanaryRoute 1%, then 5%, then 25% of trafficReal-world failures, at limited blast radius
A/B testRandomised split, measured on business metricsWhether the model actually improves the outcome — the only test that answers that
Blue-greenTwo environments, switch traffic between themInstant rollback

An offline metric improvement is a hypothesis about the business, not a result. Models that score better offline routinely fail to move the metric anyone cares about, because the intervention downstream is weak, the population differs, or the prediction was never the bottleneck. Chapter 1's question — what will we do differently? — gets its answer here.

The three kinds of drift

Covariate shift
\(P(\mathbf{x})\) changes, \(P(y \mid \mathbf{x})\) does not. Your users get younger; the relationship between age and churn is unchanged. Detectable from inputs alone.
Label shift
\(P(y)\) changes. The fraud rate triples. Detectable from prediction distributions and, eventually, from outcomes.
Concept drift
\(P(y \mid \mathbf{x})\) changes — the world's rules moved. Fraudsters adapt; a competitor launches; a pandemic starts. Invisible in the input distribution, which is why input monitoring alone is not enough.

Retraining

Automated retraining needs guardrails

A retraining pipeline that deploys without checks will eventually train on corrupted data and ship it. At minimum: validate the input data against its schema, require the new model to beat the incumbent on a fixed golden evaluation set, check subgroup metrics have not regressed, deploy to shadow first, and keep the previous version one command away. Feedback loops deserve particular care — if the model's own decisions shape the data it next learns from, it can drift steadily away from reality while every metric it can see looks healthy.

Cost and latency

Serving budget
Rough arithmetic, but the right arithmetic
Batch requests
Scoring 64 rows in one call is far cheaper per row than 64 calls, because the fixed overhead amortises and the matrix operations vectorise. Micro-batching with a few milliseconds of delay often multiplies throughput.
Cache aggressively
Identical inputs recur more often than people expect. A cache keyed on the feature vector is the cheapest optimisation available.
Quantise
float32 to int8 typically gives 2–4× speed and a quarter of the memory for a small accuracy cost. Standard for deployed neural networks.
Distil
Train a small model to mimic a large one's outputs. Often retains most of the quality at a fraction of the cost.
Right-size the model
Chapter 12's advice again: if gradient boosting is within a point of a neural network on tabular data, the boosting model is a hundred times cheaper to serve and easier to debug at 3am.
When something breaks
  1. Roll back first, diagnose second. The previous model version should be one command away, always.
  2. Check the inputs before the model. An upstream schema change or a broken feature pipeline is far more likely than the model itself having changed.
  3. Compare served features against training features. Your prediction logs make this possible — which is why you log them.
  4. Write it down. A short incident note with cause, detection time and fix is what stops the same failure recurring in six months under a different name.

Self-check

  1. Why serialise the pipeline rather than the model?
    Because the fitted preprocessing is part of the model. The imputer's medians, the scaler's means and standard deviations, and the encoder's category mapping were all learned from training data and must be applied identically at inference. Saving only the estimator means reimplementing all of that in the service, where it will drift out of sync — the training–serving skew that is the most common production defect in classical ML.
  2. Your input distributions look unchanged but accuracy has fallen 8 points. What kind of drift is this?
    Concept drift: P(x) is stable but P(y|x) has moved — the relationship between features and outcome changed. Input monitoring is structurally blind to it, which is why you also need prediction-distribution monitoring and, once labels arrive, actual performance tracking. Common causes are adversarial adaptation, a competitor's change, a policy change, or a seasonal effect the model has not seen.
  3. What is a shadow deployment for?
    Running the new model on live traffic while its outputs are logged rather than used. It exposes training–serving skew, latency problems and unexpected input distributions under real conditions with zero user risk, and it lets you compare the new and old models on identical requests. It should be the first stage of any rollout, and it costs almost nothing.
  4. Why log the features you served rather than only the prediction?
    Because without them you cannot reproduce a prediction, compute input drift, or debug an incident. When someone reports a wrong decision three weeks later, the served feature vector is the only record of what the model actually saw — the upstream data will have changed by then. Note the privacy obligations that come with it: retention limits, access control and pseudonymisation apply to these logs like any other personal data.
  5. Your offline PR-AUC improved from 0.58 to 0.63 but the A/B test shows no business improvement. What might explain it?
    Several possibilities, all common. The intervention downstream may be weak — better predictions do not help if the action taken on them rarely works. The gain may be concentrated in a segment that does not matter commercially. The threshold may not have been re-tuned for the new model's score distribution. Or the metric improvement may be within noise once you account for fold-to-fold and seed variance. This is why the A/B test exists: offline improvement is a hypothesis about the business, not a result.
  6. When would you argue against real-time serving?
    Whenever the recipient does not act within the latency you would be buying. If a retention team works a call list each morning, an overnight batch job is equivalent in outcome and dramatically simpler — no availability requirement, no latency budget, free retries, and a failure just means yesterday's scores persist. Ask how quickly the prediction is acted on; a good share of "real-time" requirements do not survive the question.
