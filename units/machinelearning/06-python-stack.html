The most common reason an analysis cannot be re-run is that nobody wrote down what it needed. Ten minutes of setup at the start saves a day later.

Seeds, and the three places randomness hides

python
import random, numpy as np

SEED = 42
random.seed(SEED)                    # the standard library
rng = np.random.default_rng(SEED)    # NumPy — pass this object around, do not use np.random.*

# scikit-learn: every estimator that shuffles or samples takes random_state
train_test_split(X, y, test_size=0.2, random_state=SEED, stratify=y)
RandomForestClassifier(random_state=SEED)

# PyTorch, if you get that far
import torch; torch.manual_seed(SEED)
# full determinism on GPU also needs:
torch.use_deterministic_algorithms(True)      # costs speed; worth it for debugging
Seeding is not the same as reproducibility

A seed makes one run repeatable. It does not make your result trustworthy — that requires the result to hold across seeds. Report the mean and spread over several. Meanwhile, genuine reproducibility also needs pinned library versions (NumPy has changed default behaviours between majors), a recorded data snapshot, and the code in version control.

Mutable default arguments

The bad function above is a genuine Python wart and it catches everyone once. The default list is evaluated at function-definition time, not per call, so state leaks between invocations. The same applies to dicts and to any mutable object. Always default to None and build inside.

NumPy

Two ideas cause almost all NumPy confusion: what axis means, and how broadcasting decides shapes. Both are below, with something to click.

The array

python
import numpy as np

a = np.array([[1, 2, 3], [4, 5, 6]])
a.shape      # (2, 3)   rows, columns
a.ndim       # 2
a.size       # 6
a.dtype      # int64    ← one type for the whole array. This is the speed.
a.nbytes     # 48

# creation
np.zeros((3, 4)); np.ones(5); np.full((2, 2), 7); np.eye(3)
np.arange(0, 10, 2)                # [0 2 4 6 8]  — step
np.linspace(0, 1, 5)                # [0 .25 .5 .75 1] — count, endpoint included
np.empty((1000, 1000))            # uninitialised — fast, contains garbage

# dtype matters for memory: 1M rows × 20 float columns
#   float64 → 160 MB     float32 → 80 MB     float16 → 40 MB
X = X.astype(np.float32)          # usually plenty of precision for ML features

Views versus copies — the silent bug

python
a = np.arange(10)
b = a[2:5]          # slicing gives a VIEW — shares memory
b[0] = 999
a                     # [0 1 999 3 4 5 6 7 8 9]   ← a changed too

c = a[2:5].copy()   # explicit copy when you need independence
d = a[[2, 3, 4]]     # fancy indexing always COPIES
e = a[a > 5]        # boolean masking always COPIES

b.base is not None   # True → it is a view

Views make slicing free, which is why NumPy is fast, and they make in-place modification dangerous, which is why preprocessing functions should copy their input or be explicit that they mutate.

Indexing

python
X = np.arange(24).reshape(4, 6)     # 4 samples, 6 features

X[0]           # first row      → shape (6,)
X[:, 2]        # third column   → shape (4,)
X[1:3, 2:5]    # submatrix      → shape (2, 3)
X[:, -1]       # last column — often the target
X[::2]        # every other row

# boolean masks — the workhorse of filtering

X[mask]                       # rows where the first feature exceeds 5
X[(X > 5) & (X < 15)]        # use & | ~ , NOT and/or/not — and wrap in parentheses
np.where(X > 10, X, 0)         # vectorised if/else

# adding an axis — needed constantly for broadcasting
v = np.array([1, 2, 3])
v[:, None].shape             # (3, 1) — column vector
v[None, :].shape             # (1, 3) — row vector

Axis: which dimension disappears

The rule that removes the confusion: the axis you name is the one that collapses. axis=0 collapses rows, leaving one value per column.

Broadcasting

Broadcasting lets NumPy combine arrays of different shapes without copying data. Two rules, applied right to left:

  1. If the arrays have different numbers of dimensions, the shorter shape is padded on the left with 1s.
  2. Two dimensions are compatible if they are equal, or if one of them is 1. A dimension of size 1 is stretched to match. Anything else is an error.
Broadcasting checker
Pick two shapes and see what NumPy does
python — broadcasting in anger
X = rng.normal(size=(1000, 20))          # 1000 samples, 20 features

# standardise every column — (1000,20) with (20,) → broadcasts across rows
X_std = (X - X.mean(axis=0)) / X.std(axis=0)

# normalise every ROW to unit length — needs an explicit column shape
norms = np.linalg.norm(X, axis=1, keepdims=True)   # (1000, 1), not (1000,)
X_unit = X / norms

# pairwise squared distances between all rows, no loop
diff = X[:, None, :] - X[None, :, :]    # (1000, 1, 20) − (1, 1000, 20) → (1000,1000,20)
D2 = (diff ** 2).sum(axis=-1)            # (1000, 1000)
# elegant, but materialises 20M floats — for large n use the expanded form:
#   D2 = (X**2).sum(1)[:,None] + (X**2).sum(1)[None,:] - 2 * X @ X.T
The silent broadcast

Subtracting a (n,) array from an (n,1) array does not fail — it broadcasts to (n,n). With n = 50,000 that is 20 GB and your process dies with no useful error. This is the single most common cause of mysterious memory explosions in NumPy code, and it comes from a keepdims=True that should have been there or a .ravel() that should not.

Selection: loc, iloc, and the warning everyone ignores

python
df["amount"]                      # a Series
df[["amount", "category"]]        # a DataFrame
df.loc[3, "amount"]                # by LABEL — inclusive slices
df.iloc[3, 0]                     # by POSITION — exclusive slices
df.loc[df.amount > 100, "category"] # boolean mask + column, in one step
df.query("amount > 100 and category == 'food'")   # readable for long conditions

# ✗ chained indexing — may modify a temporary copy and silently do nothing
df[df.amount > 100]["flag"] = True        # SettingWithCopyWarning

# ✓ single .loc call — unambiguous, always works
df.loc[df.amount > 100, "flag"] = True
SettingWithCopyWarning

This warning means pandas cannot tell whether you are writing to the original frame or to a temporary copy, so your assignment may vanish. It is not pedantry — it produces data that is silently wrong. The cure is always the same: one .loc[rows, cols] = value instead of two chained bracket operations. If you deliberately took a subset to work on, call .copy() at that point and the warning disappears for the right reason.

Split, apply, combine

Group-by is the most useful operation in pandas and the one worth understanding visually rather than by memorising syntax.

Split → apply → combine
Change the operation and watch the output shape change
python
# aggregate — one row per group
df.groupby("category")["amount"].mean()

df.groupby("category").agg(
    total   = ("amount", "sum"),
    average = ("amount", "mean"),
    n       = ("amount", "size"),
    p95     = ("amount", lambda s: s.quantile(0.95)),
).reset_index()

# transform — result aligned back to the ORIGINAL rows. The feature-engineering workhorse.
df["amount_vs_category_mean"] = (
    df["amount"] / df.groupby("category")["amount"].transform("mean")
)

# filter — keep or drop whole groups
df.groupby("customer_id").filter(lambda g: len(g) >= 5)

# apply — the flexible, slow escape hatch. Try to avoid it in hot paths.
df.groupby("customer_id").apply(lambda g: g.nlargest(3, "amount"))

Joining, and the row-count trap

python
merged = orders.merge(customers, on="customer_id", how="left", validate="many_to_one")

# ALWAYS check the row count before and after
assert len(merged) == len(orders), "join changed the row count — duplicate keys on the right"

# and check what failed to match
merged = orders.merge(customers, on="customer_id", how="left", indicator=True)
merged["_merge"].value_counts()      # both / left_only / right_only

The validate= argument is the most underused feature in pandas. It raises immediately if the join is not the cardinality you assumed, turning a silent row-duplication bug into an error at the point of the mistake.

Method chaining

python
clean = (
    pd.read_csv("raw.csv", parse_dates=["date"])
      .rename(columns=str.lower)
      .dropna(subset=["customer_id"])
      .assign(
          amount   = lambda d: d.amount.clip(lower=0),
          log_amt  = lambda d: np.log1p(d.amount),
          weekday  = lambda d: d.date.dt.day_name(),
      )
      .query("amount < 10_000")
      .reset_index(drop=True)
)

Chaining reads top to bottom as a sequence of transformations, avoids intermediate variables nobody names well, and sidesteps SettingWithCopyWarning entirely. The lambda d: inside assign refers to the frame as it is at that point in the chain, which is what makes it composable.

Plots that earn their place
  • Log-scale any axis showing money, counts, durations or latency.
  • Use transparency or hexbin when scatter points overlap — a solid blob hides its own density.
  • Label axes with units. A figure you cannot interpret in a month is a figure you will redraw.
  • For a report, fix the figure size and dpi rather than resizing afterwards, or the text ends up unreadable.

When it gets slow

Work down this list in order. Most people jump to step 5 when step 1 would have solved it.

  1. Vectorise. Replace iterrows and apply with array operations. Typically 50–200×, and it is free.
  2. Shrink dtypes. float64 → float32, object strings → category. Often 4–10× less memory, which also makes everything faster through the cache.
  3. Read less. usecols, filters pushed into the query, Parquet instead of CSV.
  4. Profile before optimising further. %timeit in a notebook, cProfile or line_profiler for scripts. Guessing at bottlenecks has a poor hit rate.
  5. Change tool. Polars for larger-than-comfortable dataframes, DuckDB for SQL over Parquet, numba for genuinely loop-shaped numerical code.
  6. Distribute. Dask or Spark. Only once a single machine has actually been ruled out — the coordination overhead is real.

Notebooks, and when to leave them

Notebooks are excellent for exploration and poor for anything that must run twice. Move code into src/ as soon as it is worth keeping — anything you have copy-pasted between cells, anything with a bug you fixed once already, anything another person will run.

Out-of-order execution

A notebook's state depends on the order cells were run, not the order they appear. A notebook that works for you can fail completely for someone running it top to bottom. Before sharing, restart the kernel and run all — every time. If it does not survive that, it does not work.

Self-check

  1. X.shape is (1000, 20). What does X.mean(axis=0) return, and what does X.mean(axis=1) return?
    axis=0 collapses the rows and returns shape (20,) — the mean of each feature across all samples. That is what you want for standardisation. axis=1 collapses the columns and returns (1000,) — the mean of each sample across its features, which is rarely meaningful unless the features share units. The axis you name is the one that disappears.
  2. Why does X / X.std(axis=1) fail or misbehave, while X / X.std(axis=1, keepdims=True) works?
    Without keepdims the result is shape (1000,). Broadcasting pads on the left, making it (1, 1000), which then tries to align against (1000, 20) — 1000 against 20 is incompatible, so it errors. With square data it would not error at all; it would silently divide along the wrong axis, which is worse. keepdims=True gives (1000, 1), which broadcasts across columns as intended.
  3. Your left join turns 10,000 order rows into 10,340. What happened?
    The right-hand table has duplicate keys, so some orders matched multiple customer rows and were duplicated. Find them with customers.customer_id.duplicated().sum(). Fix by deduplicating the right side first, or by aggregating it to one row per key. Adding validate="many_to_one" to the merge would have raised an error at the point of the mistake instead of letting 340 phantom rows into your training data.
  4. What is the difference between groupby().agg() and groupby().transform()?
    agg reduces each group to a single row — you get one row per group, suitable for a summary table. transform returns a result the same length as the input, with each row carrying its group's value, which makes it the right tool for feature engineering: "this customer's spend relative to their segment's average" is a single transform away.
  5. You see SettingWithCopyWarning. Why is ignoring it a bad idea?
    Because pandas is telling you it cannot determine whether your write goes to the original frame or to a temporary copy. If it hits a copy, the assignment silently does nothing and your data is quietly wrong — no exception, no bad output, just a column that was never updated. Replace the chained brackets with a single .loc[rows, cols] = value, or call .copy() when deliberately taking a subset.
  6. A colleague's notebook produces a different accuracy every run. Name three things to check.
    (1) Seeds — random_state on the split and on every estimator that shuffles or subsamples, plus a seeded NumPy generator. (2) Out-of-order cell execution leaving stale variables in scope; restart and run all. (3) Data that changes underneath the notebook — a query against a live table rather than a saved snapshot. Beyond that, some variation across seeds is genuine and should be reported rather than eliminated, as chapter 3 discussed.
