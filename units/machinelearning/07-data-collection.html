Chapter 07 · Working with data

Collecting data

The model is a function of its data. Every decision made here — which source, which sample, which labels, which split — sets a ceiling that no amount of later modelling can lift. This chapter is about making those decisions deliberately instead of by accident.

The mutable-row problem

Most production databases store current state. A customer's status column says what they are today, not what they were on the day you want to predict. Train on that and you have used the future to predict the past — the model looks superb offline and fails completely in production. Ask early whether the source has history: change data capture, an append-only event log, or snapshot tables. If it does not, you may need to start collecting before you can start modelling.

SQL is most of the job

Getting data into a dataframe usually means writing a query that assembles it. Three patterns cover most of it.

sql — aggregate features per entity
SELECT
    c.customer_id,
    COUNT(o.order_id)                              AS n_orders,
    COALESCE(SUM(o.amount), 0)                     AS total_spend,
    AVG(o.amount)                                  AS avg_order,
    MAX(o.created_at)                              AS last_order_at,
    COUNT(DISTINCT DATE_TRUNC('month', o.created_at)) AS active_months
FROM customers c
LEFT JOIN orders o                                  -- LEFT keeps customers with zero orders
       ON o.customer_id = c.customer_id
      AND o.created_at < '2024-01-01'                 -- the cutoff goes in the JOIN, not the WHERE
GROUP BY c.customer_id;

That cutoff placement matters. In a WHERE clause it would filter out customers who had no orders before the cutoff, silently changing your population from "all customers" to "customers who had already ordered".

sql — window functions, and point-in-time correctness
-- rolling features that only ever look backwards
SELECT
    order_id, customer_id, created_at, amount,
    LAG(amount) OVER w                                    AS prev_amount,
    AVG(amount)  OVER (w ROWS BETWEEN 5 PRECEDING AND 1 PRECEDING) AS avg_prev_5,
    ROW_NUMBER() OVER w                                   AS order_seq
FROM orders
WINDOW w AS (PARTITION BY customer_id ORDER BY created_at);

-- note "1 PRECEDING", not "CURRENT ROW": including the current row leaks the
-- value you are trying to predict into its own feature.

APIs, without getting banned

python
import time, requests
from requests.adapters import HTTPAdapter, Retry

session = requests.Session()
session.mount("https://", HTTPAdapter(max_retries=Retry(
    total=5,
    backoff_factor=1.5,                       # 1.5s, 3s, 6s, 12s … exponential backoff
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET"],
)))

def fetch_all(url, params=None):
    """Cursor pagination with a polite delay."""
    out, cursor = [], None
    while True:
        r = session.get(url, params={**(params or {}), "cursor": cursor}, timeout=30)
        r.raise_for_status()
        page = r.json()
        out.extend(page["items"])
        cursor = page.get("next_cursor")
        if not cursor: break
        time.sleep(0.2)                       # stay under the rate limit
    return out
Cache every raw response

Write the untouched JSON to disk before parsing it. Re-running a six-hour collection because you found a bug in your parser is a mistake you make exactly once. The same principle as data/raw being immutable: separate acquiring from interpreting.

Scraping: the questions to ask first

Scraping is technically easy and legally, ethically and operationally messy. Before writing the scraper: check the site's terms of service, check robots.txt, check whether an official API or bulk download exists, and consider whether the data is personal. Rate-limit yourself well below what the server can bear, identify your bot honestly in the user-agent, and cache aggressively so you never fetch the same page twice. Expect the scraper to break — selectors change without notice, so write it to fail loudly rather than silently returning empty strings.

Move to Parquet early

A 1 GB CSV typically becomes 100–200 MB of Parquet, loads five to ten times faster, and remembers its own dtypes so you stop re-specifying them on every read. Column pruning means selecting three columns from a fifty-column file reads roughly three columns' worth of bytes. The one thing you lose is being able to head it in a terminal, which is worth trading.

How much data, and which rows

How much is enough

There is no formula, but there are useful anchors. What matters is not raw row count but the number of examples per class and per parameter.

SituationRough guide
Simple tabular model, 10–20 featuresA few thousand rows; at least a few hundred of the minority class
Gradient boosting, 50+ featuresTens of thousands. It degrades gracefully below that with tuning
Deep learning from scratchHundreds of thousands upward. Below that, transfer learning wins
Fine-tuning a pretrained vision or text modelHundreds to a few thousand labelled examples
Rare event, 0.1% positiveDriven by the positive count. 500 positives needs 500,000 rows

The empirical answer is a learning curve: train on 10%, 20%, … 100% of what you have and plot validation performance. If the curve is still climbing at 100%, more data will help and is probably the cheapest improvement available. If it flattened at 40%, collecting more is wasted effort — better features or a different model class is where the gain is. Chapter 15 covers reading these curves.

Splitting without lying to yourself

A random split is right only when rows are independent. They frequently are not, and the wrong split produces a test score that is pure fiction.

Split strategies
Rows sharing a colour belong to the same user
UseWhenscikit-learn
RandomRows genuinely independent, no time orderingtrain_test_split
StratifiedClassification, especially imbalanced. Always, unless a reason not tostratify=y, StratifiedKFold
GroupedMultiple rows per entity: patients, users, sessions, images of one personGroupKFold, GroupShuffleSplit
Time-basedAny forecasting or drifting problem. Train on the past, test on the futureTimeSeriesSplit

The classic false result

A churn model scores 0.94 AUC in testing and 0.61 in production. Cause: each customer had twelve monthly rows, a random split scattered them across train and test, and the model effectively memorised individual customers rather than learning churn. A GroupKFold on customer_id would have shown 0.63 from the start. If your offline number seems too good, check the split before celebrating.

Deciding the split before you look

Fix your test set once, at the beginning, and do not touch it until the end. Every time you look at test performance and then change something, you leak a little information into your modelling choices — and after twenty such peeks, the test set has quietly become a second validation set. Use a hash of a stable ID rather than a random draw, so the assignment is stable as the dataset grows:

python
import hashlib

def in_test_set(identifier, test_frac=0.2):
    """Stable across runs and as new rows arrive; no state to store."""
    h = hashlib.md5(str(identifier).encode()).hexdigest()
    return (int(h[:8], 16) / 0xFFFFFFFF) < test_frac

test_mask = df["customer_id"].map(in_test_set)
train, test = df[~test_mask], df[test_mask]   # a customer is always on the same side

Labels

Supervised learning needs a target, and where that target comes from determines what you are really predicting.

Naturally occurring
The outcome is recorded anyway — a payment defaulted, a subscription lapsed, a part failed. Cheapest and most reliable, when it exists.
Implicit feedback
Clicks, watch time, purchases. Abundant but biased: users can only click what you showed them, so the data reflects your previous system's choices as much as their preferences.
Explicit feedback
Ratings, thumbs, surveys. Sparse and skewed toward strong opinions.
Human annotation
People label examples against guidelines. Flexible, expensive, and only as consistent as the guidelines.
Weak supervision
Noisy heuristics — keyword rules, regexes, existing systems — combined into probabilistic labels. Useful for bootstrapping when hand-labelling is infeasible.

Label quality caps everything

If 10% of your labels are wrong, no model can exceed roughly 90% accuracy on that data — and worse, it will spend capacity learning to reproduce the errors. Noisy labels hurt more than noisy features, because they corrupt the target the whole optimisation is aimed at.

Measuring annotator agreement

If two annotators disagree on a fifth of the examples, your labels carry that much irreducible noise, and no model will do better than the humans do. Raw percentage agreement flatters — on an imbalanced task, two annotators who both always say "no" agree 95% of the time while conveying nothing. Cohen's kappa corrects for agreement expected by chance:

$$\kappa = \frac{p_o - p_e}{1 - p_e}$$

po is observed agreement; pe is the agreement you would expect if both annotators labelled at random with their own base rates. κ = 1 is perfect, 0 is chance-level, negative is worse than chance.

Practical labelling advice
  • Write guidelines with worked examples, including the hard cases. Then label 50 yourself before asking anyone else to.
  • Double-label 5–10% of the set throughout to monitor agreement over time, not just at the start.
  • Give annotators a way to flag "unclear" rather than forcing a guess — those flags tell you where the guidelines are failing.
  • Label the hard examples first if budget is tight. Active learning formalises this: train on what you have, label the cases the model is least certain about, repeat.
  • Keep a record of who labelled what. When you find a systematic error you will want to know its blast radius.

Write it down

A dataset nobody can interpret is a liability. Two artefacts pay for themselves repeatedly:

Data dictionary

One row per column: name, type, units, allowed values, meaning in plain language, source system, known quirks. Keep it beside the data, not in someone's head.

Datasheet

One page on the dataset as a whole: why it was collected, how it was sampled, who is represented and who is not, known biases, licence, and what it should not be used for.

Personal data

If your dataset contains information about identifiable people, legal obligations attach to it — lawful basis for processing, purpose limitation, retention limits, and in many jurisdictions a right to deletion that extends awkwardly to trained models. Minimise from the start: do not collect fields you do not need, pseudonymise identifiers, aggregate where possible, and keep raw personal data out of notebooks and experiment tracking systems. This is a genuine legal question rather than a technical one — involve whoever owns that at your organisation early, because retrofitting compliance onto a trained pipeline is painful.

Self-check

  1. Your churn model uses a subscription_status column from the production customers table. What is wrong?
    That column holds the customer's status now, not on the historical date each training row represents. For churned customers it already says "cancelled", so the feature contains the answer. You need a point-in-time snapshot or an event history you can reconstruct state from. This is the single most common leak in customer-lifecycle modelling.
  2. You have 60,000 rows covering 5,000 patients. Why is train_test_split(X, y, test_size=0.2) a mistake?
    Rows from the same patient would land in both train and test, so the model can recognise individual patients rather than learning the clinical pattern. The test score would be badly optimistic. Use GroupShuffleSplit or GroupKFold with groups=patient_id, so every patient is entirely in one side of the split.
  3. Two annotators agree on 92% of examples where only 6% of cases are positive. Is that good?
    Probably not. If both annotators say "negative" almost always, chance agreement is already around 89%, so κ works out low — the 92% is almost entirely explained by the base rate rather than by genuine agreement on the hard cases. Compute kappa, and look specifically at agreement among the examples where at least one annotator said positive.
  4. Your learning curve is still rising steeply at 100% of available data. What does that suggest, and what if it had flattened at 30%?
    Still rising means more data is likely the cheapest available improvement — collect or label more before tuning further. Flattening at 30% means additional rows of the same kind will not help; the constraint is elsewhere — feature quality, model capacity, or irreducible noise in the labels. Chapter 15 covers distinguishing those three.
  5. Why store intermediate data as Parquet rather than CSV?
    It preserves dtypes, so you stop re-declaring them and stop losing leading zeros on IDs; it is columnar, so reading three of fifty columns reads roughly three columns' worth of bytes; and it compresses to a fraction of the size while loading much faster. The trade is that it is binary, so you cannot inspect it with a text editor — use duckdb or a quick read_parquet instead.
