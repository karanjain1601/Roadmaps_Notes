Chapter 09 · Working with data

Features and dimensionality

Cleaning gets your data usable. Feature engineering is where you encode what you know about the problem into columns the model can act on — and it remains the highest-leverage work in applied machine learning, well ahead of algorithm choice. Then the opposite problem: too many columns, and what to do about it.

— words— min read3 interactivesNeeds: chapters 02, 08

Why features beat models

Swapping random forest for gradient boosting might buy you a point of AUC. Adding "days since last purchase" to a churn model might buy you fifteen. The gap is not close, and it persists even in the deep learning era for tabular problems.

A model can only combine the columns you give it. Some relationships it can discover — a tree will find a threshold, a network will approximate a curve — but many it cannot express at all without help:

The rule of thumb

If a domain expert would compute something on a napkin to answer the question, make it a column. Models are good at weighing evidence and poor at inventing the arithmetic that produces it.

Engineering by data type

Numeric

python
# ratios and differences carry more signal than the raw parts
df["price_per_sqm"]   = df.price / df.area
df["debt_to_income"]  = df.debt / df.income.clip(lower=1)      # clip to avoid ÷0
df["margin"]          = (df.revenue - df.cost) / df.revenue

# binning turns a continuous variable into a step function a linear model can use
df["age_band"] = pd.cut(df.age, bins=[0, 25, 35, 50, 65, 200],
                        labels=["<25", "25-34", "35-49", "50-64", "65+"])
df["spend_decile"] = pd.qcut(df.spend, 10, labels=False, duplicates="drop")

# interactions — explicit products. Trees find these; linear models cannot.
df["age_x_income"] = df.age * df.income

# flags for meaningful thresholds the model would otherwise have to discover
df["is_new"]      = (df.tenure_months < 3).astype("int8")
df["is_zero"]     = (df.balance == 0).astype("int8")   # zero often means something specific

Datetime

A raw timestamp is nearly useless; its components are among the strongest features in most business problems.

python
ts = df["created_at"]

df["hour"]        = ts.dt.hour
df["dayofweek"]   = ts.dt.dayofweek
df["is_weekend"]  = ts.dt.dayofweek.isin([5, 6]).astype("int8")
df["month"]       = ts.dt.month
df["is_month_end"]= ts.dt.is_month_end.astype("int8")

# elapsed time — nearly always the strongest datetime feature
df["days_since_signup"]     = (ts - df.signup_at).dt.days
df["days_since_last_order"] = (ts - df.last_order_at).dt.days

# cyclical encoding: tells the model that 23 and 0 are neighbours
df["hour_sin"] = np.sin(2 * np.pi * df.hour / 24)
df["hour_cos"] = np.cos(2 * np.pi * df.hour / 24)

Aggregations — the highest-value category

Most real predictive power comes from summarising an entity's history. These are the features that make a model about this customer rather than about this transaction.

python
# per-entity aggregates, joined back on
agg = (orders.groupby("customer_id")
             .agg(n_orders=("amount", "size"),
                  total=("amount", "sum"),
                  avg=("amount", "mean"),
                  std=("amount", "std"),
                  max=("amount", "max")))

# relative features — how does this row compare to its own group's norm?
df["vs_own_avg"]   = df.amount / df.groupby("customer_id").amount.transform("mean")
df["vs_category"]  = df.amount / df.groupby("category").amount.transform("median")

# time windows — recency-weighted behaviour. Multiple windows capture trend.
for w in ["7D", "30D", "90D"]:
    df[f"spend_{w}"] = (df.set_index("date")
                             .groupby("customer_id").amount
                             .rolling(w, closed="left").sum()      # closed="left" excludes today
                             .reset_index(level=0, drop=True))

# trend: the ratio of a short window to a long one
df["momentum"] = df.spend_7D / (df.spend_90D / 13 + 1e-6)
Windows must look backwards only

closed="left" and shift(1) exist for a reason. A rolling window that includes the current row puts today's value inside a feature used to predict today. A centred window is worse — it uses the future outright. Both produce beautiful offline numbers and worthless models. This is temporal leakage from chapter 8, and aggregation features are where it most often creeps in.

from sklearn.feature_selection import VarianceThreshold, mutual_info_classif, RFECV
from sklearn.inspection import permutation_importance

# 1. free wins: drop constants and exact duplicates
X = VarianceThreshold(threshold=0.0).fit_transform(X)

# 2. drop one of each highly correlated pair — they carry the same information
corr = X.corr().abs()
upper = corr.where(np.triu(np.ones(corr.shape), k=1).astype(bool))
drop = [c for c in upper.columns if (upper[c] > 0.95).any()]

# 3. mutual information — non-linear, univariate
mi = pd.Series(mutual_info_classif(X, y, random_state=0), index=X.columns)
mi.sort_values(ascending=False).head(30)

# 4. permutation importance — measures what the MODEL actually uses.
#    Compute on VALIDATION data, not training data.
r = permutation_importance(model, X_val, y_val, n_repeats=10,
                           random_state=0, scoring="roc_auc")
pd.Series(r.importances_mean, index=X_val.columns).sort_values(ascending=False)
Two importance traps

Impurity-based importance is biased. The default feature_importances_ on a random forest inflates high-cardinality and continuous features, because they offer more places to split. Prefer permutation importance, or SHAP (chapter 22).

Correlated features share credit. If two features carry the same information, permuting either one alone barely hurts — the model leans on the other. Both look unimportant while the pair is essential. Drop correlated duplicates before measuring importance, or group them and permute together.

Selection must live inside cross-validation

Ranking features by their correlation with y on the full dataset, then cross-validating the chosen subset, is leakage — the selection saw the validation rows. On wide noisy data this can manufacture impressive scores from nothing, exactly as chapter 5's multiple-comparisons demo showed. Put the selector in the Pipeline so it refits inside every fold.

The curse of dimensionality

Adding features is not free, and the cost is stranger than "more parameters to fit". In high dimensions, geometry stops behaving the way your intuition expects.

Distances in high dimensions
500 random points, distances to one query point
2
Distances concentrate
The gap between the nearest and furthest neighbour shrinks relative to the average distance. Every point becomes roughly equidistant from every other, which quietly destroys k-NN, k-means, and anything else built on "close means similar".
Volume flees to the corners
In a 100-dimensional unit cube, almost all the volume is near the surface. A hypersphere inscribed in the cube occupies a vanishing fraction of it, so "the middle" is essentially empty.
Data becomes sparse
Covering each dimension with 10 sample points needs \(10^d\) samples. At d = 10 that is ten billion. Your data is always sparse in high dimensions, whatever its row count.
Overfitting gets easier
With enough dimensions, some feature will separate your classes by chance alone — the multiple-comparisons problem again, in geometric clothing.
Which models suffer, and which do not

Distance-based methods (k-NN, k-means, RBF-kernel SVM, DBSCAN) degrade badly. Linear models with strong regularisation cope well. Tree ensembles cope reasonably because each split considers one feature at a time. Neural networks cope when they have enough data to learn a useful low-dimensional representation internally — which is really dimensionality reduction by another name.

Principal component analysis

PCA finds a new set of axes, ordered by how much of the data's variance each one captures, and lets you keep only the first few. It is chapter 2's eigen-decomposition applied to the covariance matrix.

  1. Standardise the features. PCA maximises variance, and variance depends on units — without this, whichever feature is measured in the largest numbers dominates.
  2. Compute the covariance matrix \(\mathbf{C} = \frac{1}{n-1}\mathbf{X}^{\top}\mathbf{X}\), which is symmetric and positive semi-definite.
  3. Find its eigenvectors and eigenvalues. Eigenvectors are the new axes — the principal components. Eigenvalues are the variance captured along each.
  4. Sort by eigenvalue, keep the top k, and project: \(\mathbf{Z} = \mathbf{X}\mathbf{W}_k\).

In practice you never form the covariance matrix — SVD on the centred data is faster and numerically better, and gives the same answer, as chapter 2 noted.

Choosing k

Cumulative variance
Keep enough components to reach 90–95% of total variance. The most common rule, and defensible.
Scree plot elbow
Plot eigenvalues in order and look for where the curve flattens. Subjective, but often obvious.
Downstream performance
Treat k as a hyperparameter and tune it against validation score. The only criterion that directly measures what you care about.
python
from sklearn.decomposition import PCA
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

# scaling first is not optional
pipe = make_pipeline(StandardScaler(), PCA(n_components=0.95))   # keep 95% of variance
Z = pipe.fit_transform(X_train)

pca = pipe.named_steps["pca"]
pca.n_components_                       # how many that turned out to be
pca.explained_variance_ratio_[:5]      # variance share of the first five
np.cumsum(pca.explained_variance_ratio_) # the scree curve

# which original features load onto PC1?
pd.Series(pca.components_[0], index=X_train.columns).abs().nlargest(5)
When PCA is the wrong tool
  • You need interpretable features. "Component 3" cannot be explained to a regulator, or acted on by a marketing team.
  • Your model is a tree ensemble. Rotating the axes destroys the axis-aligned structure trees exploit, and usually hurts.
  • Variance is not importance. PCA is unsupervised — it never looks at y. A low-variance direction can be the one that separates your classes, and PCA will discard it first.
  • The structure is non-linear. PCA only finds linear subspaces. A spiral stays a spiral.

Do not feed t-SNE output to a model

t-SNE and UMAP are non-parametric in the way that matters: there is no stable mapping to apply to new data, the result changes with the random seed, and the axes have no meaning. Distances between well-separated clusters in a t-SNE plot are not interpretable — two clusters drawn far apart may be no more different than two drawn adjacent. Use them to look at your data and generate hypotheses, then verify those hypotheses another way.

Self-check

  1. Why encode hour of day as sine and cosine rather than as an integer 0–23?
    Because as an integer, 23 and 0 are 23 units apart when they are actually adjacent, so any model that treats the feature as continuous learns a discontinuity that does not exist. Mapping onto a circle makes the distance between 23:00 and 00:00 the same as between 01:00 and 02:00. You need both sine and cosine — either alone is ambiguous, since sin(hour) takes the same value at two different hours.
  2. Your k-NN classifier works well on 8 features and badly on 80. What is happening?
    Distance concentration. As dimensionality grows, the ratio between the nearest and furthest neighbour distances approaches 1, so "nearest" stops carrying information. The extra 72 features are mostly noise contributing variance to every distance calculation. Fix by selecting features, reducing dimensions with PCA, or switching to a model that is not distance-based — gradient boosting is the usual answer.
  3. You rank features by correlation with the target, keep the top 20, then cross-validate. What is wrong?
    The ranking used the whole dataset, including the rows that later serve as validation folds, so the selection has already seen them. On wide data this can produce strongly positive cross-validation scores from pure noise. Put the selector inside the pipeline so it refits within each fold, and keep a final untouched test set to confirm.
  4. Why standardise before PCA?
    PCA finds directions of maximum variance, and variance is measured in the feature's own units. An income column in units of pounds has variance millions of times larger than an age column in years, so the first principal component would simply be "income" regardless of structure. Standardising puts every feature on equal footing so the components reflect correlation structure rather than choice of units.
  5. Two of your features are 0.98 correlated. Permutation importance says both are unimportant. Are they?
    Not necessarily. Permuting one leaves the other intact, so the model simply relies on its twin and performance barely drops — each looks dispensable while the pair may be essential. Test by permuting both together, or drop one first and re-measure. This is a general property of correlated features and a known weakness of importance measures based on perturbing one column at a time.
  6. When would you keep 200 engineered features rather than selecting down to 20?
    When using a strongly regularised model or a gradient boosting ensemble with enough data — both handle irrelevant features gracefully, and selection risks discarding something useful in combination. The arguments for cutting are then practical rather than statistical: inference latency, the cost of computing each feature at serving time, and the maintenance burden of 200 upstream dependencies that can each break. Those are usually good enough reasons on their own.
