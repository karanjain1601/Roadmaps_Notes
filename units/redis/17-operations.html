Operating it

Redis is unusually easy to run and unusually easy to expose. A default installation has no authentication, several commands that will take it down, and a configuration file where the important settings are the ones nobody changed.

security acl metrics playbook

Security

An unauthenticated Redis on the internet is a compromised machine, not a leaked database

Redis has no authentication by default. Worse than the data exposure: an attacker with write access can use CONFIG SET dir and dbfilename to write an RDB file anywhere the process can write — commonly an SSH authorized_keys file or a cron directory — and get shell access. This has been exploited at scale for a decade, and it is why protected mode exists: since 3.2, a Redis with no password and no explicit bind refuses connections from anything but localhost. That default has prevented a great many incidents and it is routinely disabled by a Docker image or a quickstart guide that binds 0.0.0.0 to make things work.

the settings that matter
# redis.conf
bind 127.0.0.1 10.0.1.15          # never 0.0.0.0 on a reachable network
protected-mode yes                # keep it
port 6379
requirepass   # or better, ACL users below

# TLS — separate port, off by default
tls-port 6380
port 0                            # disable the plaintext port entirely
tls-cert-file /etc/ssl/redis.crt
tls-key-file  /etc/ssl/redis.key
tls-ca-cert-file /etc/ssl/ca.crt
tls-auth-clients yes              # require client certificates

# RENAME OR DISABLE the dangerous commands:
rename-command FLUSHALL ""
rename-command FLUSHDB  ""
rename-command CONFIG   "CONFIG_9f2a41"
rename-command DEBUG    ""
rename-command KEYS     ""
# CONFIG is the one that matters most — it is the command that turns read
# access into remote code execution via the dir/dbfilename trick.
# ACLs (below) are the better mechanism; rename-command is the blunt version
# that works on any version.

# THE NETWORK IS THE REAL CONTROL. Redis auth is a single shared secret with
# no rate limiting and no lockout, so it is a speed bump rather than a wall.
# Put the instance on a private subnet with a default-deny firewall and treat
# authentication as the second layer, not the first.

ACLs

real users, since Redis 6
# Before 6.0 there was one password and everyone had full access. ACLs give
# you users, command permissions and key patterns.

ACL SETUSER cache-app on >secret ~cache:* +@read +@write +@keyspace -@dangerous
ACL SETUSER readonly  on >secret ~* +@read
ACL SETUSER metrics   on >secret allkeys +info +ping +client|list
ACL SETUSER worker    on >secret ~jobs:* ~{jobs}:* +@list +@stream

ACL LIST
ACL GETUSER cache-app
ACL WHOAMI
ACL CAT                    # the command categories
ACL CAT dangerous          # what is in one

#   ~pattern       key patterns this user may touch
#   %R~ / %W~      read-only / write-only key patterns (7.0+)
#   &channel       pub/sub channels (7.0+)
#   +@read +@write +@admin +@dangerous +@keyspace ... categories
#   +get -set      individual commands
#   allkeys / allcommands / nopass — the blunt instruments

# Persist them in a separate file rather than redis.conf:
aclfile /etc/redis/users.acl
ACL SAVE
ACL LOAD

# THE DEFAULT USER is what an unauthenticated client becomes. Lock it down:
ACL SETUSER default off
# or, if you must keep it:
ACL SETUSER default on >password ~* +@all

# WHAT TO ACTUALLY DO: one user per service, with the narrowest key pattern
# and command set that works. -@dangerous alone removes FLUSHALL, CONFIG,
# DEBUG, SHUTDOWN, KEYS and the rest, which is most of the risk for one flag.

ACL LOG                    # authentication failures and denied commands.
ACL LOG RESET              # worth alerting on — it is your intrusion signal

and the settings outside Redis
# Redis warns about the first two at startup and both are routinely ignored.

vm.overcommit_memory = 1     # or fork() can fail during a background save
                             # even though copy-on-write means it would fit
net.core.somaxconn = 1024    # the accept backlog. Redis's tcp-backlog cannot
                             # exceed this, so a burst of connections is
                             # dropped at the kernel
vm.swappiness = 0            # never swap an in-memory database. A
                             # fragmentation ratio below 1.0 means you are
                             # already doing it (chapter 12)

echo never > /sys/kernel/mm/transparent_hugepage/enabled
# THP makes the copy-on-write fork copy 2 MB pages instead of 4 KB, which
# inflates memory and latency during every save (chapter 13).

ulimit -n 65535              # file descriptors: maxclients + replicas +
                             # persistence + headroom

# UPGRADES are undramatic. Minor versions are drop-in; major versions have
# changed the RDB format in ways that are forward-compatible but not
# backward, so a newer Redis reads an older dump and not the reverse.
#
# Rolling upgrade of a replicated setup:
#   1. upgrade each REPLICA: stop, replace the binary, start, wait for
#      master_link_status:up and the offset to catch up
#   2. failover to an upgraded replica
#   3. upgrade the former primary
#
# Check the release notes for defaults that changed. Between 6 and 7 the AOF
# layout changed to multi-part, and 7.0 changed several cluster and script
# behaviours — none of it breaking, all of it worth reading.

The first five minutes

four commands, before forming a theory
# 1. Is it memory?
INFO memory
#   used_memory vs maxmemory, mem_fragmentation_ratio
INFO stats | grep evicted

# 2. Is something blocking the thread?
SLOWLOG GET 20
LATENCY LATEST
INFO persistence | grep -E 'bgsave_in_progress|rewrite_in_progress|fork_usec'

# 3. Who is connected, and what are they doing?
CLIENT LIST
INFO clients
#   connected_clients, blocked_clients, client_recent_max_output_buffer

# 4. Is replication healthy?
INFO replication
#   role, connected_slaves, master_repl_offset, lag

# Then, if you still do not know:
redis-cli --latency          # what the client actually experiences
redis-cli --bigkeys          # is one key the problem
INFO commandstats            # sorted by total usec, not per-call

# NEVER run MONITOR to investigate. It streams every command to your client
# and measurably slows the server — you will make the incident worse and
# then leave it running.

CLIENT UNPAUSE               # in case someone paused writes and forgot
CLIENT KILL ID 42            # kill one connection
SCRIPT KILL                  # a runaway Lua script — only if it has NOT
                             # written. If it has, SHUTDOWN NOSAVE is the
                             # only way out (chapter 8)

Check whether it is Redis at all

Three things present as "Redis is slow" and are not, and all three produce metrics that look like a database problem. An exhausted client connection pool — every operation queues in your application while Redis shows low CPU, few connections and an empty slowlog. Serialisation cost — the JSON encode and decode around each value taking longer than the round trip. The machine — redis-cli --intrinsic-latency on an oversubscribed cloud instance routinely reports milliseconds of scheduler jitter, which is a ceiling no configuration improves. Rule out all three before tuning anything (chapter 14).

What to record before you need it

  • The twelve dashboard metrics as a time series, with a year of history.
  • INFO commandstats snapshotted on a schedule, so "which command changed on Tuesday" is answerable.
  • Key-pattern memory from --memkeys or a sampled scan, weekly.
  • The key-pattern document from chapter 2 — pattern, type, writer, reader, TTL, expected size.
  • Configuration in version control, so "what changed" has an answer.
  • Restore test duration, trended. The RDB load time grows with the dataset.
  • Failover test results, dated. Monthly (chapter 15).
  • ACL LOG, shipped somewhere — it is your intrusion signal.
One instance, one purpose — again

It has come up in chapters 12, 13 and 16 and it belongs in the operations chapter too, because most of the incidents above are made worse by mixing workloads. Separate instances let each one have the maxmemory, eviction policy and persistence configuration its data actually wants; they stop a cache surge from evicting your sessions; they isolate a slow command to one workload rather than all of them; and on one machine they use more than one core. The cost is a few hundred megabytes of process overhead and a little more configuration. It is the cheapest structural improvement available to most Redis deployments, and it does not require clustering, more hardware or a migration.

The short version

  1. An exposed Redis is remote code execution, not just a data leak — via CONFIG SET dir and a written RDB.
  2. The network is the real control. Auth is a shared secret with no rate limiting; put it on a private subnet.
  3. ACLs since 6.0 — one user per service, and -@dangerous removes most of the risk in one flag.
  4. Set maxmemory, a policy, repl-backlog-size and latency-monitor-threshold. All four defaults are wrong for production.
  5. Fix the kernel settings Redis warns about — overcommit, somaxconn, and transparent huge pages off.
  6. Never MONITOR during an incident. It makes the incident worse.
  7. Alert on evicted_keys, not used_memory. Full is normal; evicting is the signal.
  8. One instance, one purpose. The cheapest structural improvement available.
