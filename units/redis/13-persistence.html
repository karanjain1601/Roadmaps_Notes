Persistence

Redis can write its data to disk, and the question is not whether to enable it but what guarantee you are buying and what it costs. The honest starting position: Redis is not a durable datastore, and configuring persistence narrows the gap rather than closing it.

rdb aof fsync fork

Two mechanisms

a snapshot, and a log
# RDB — a point-in-time binary snapshot of the whole dataset.
save 900 1        # snapshot if ≥1 key changed in 900 seconds
save 300 10
save 60 10000
dbfilename dump.rdb
rdbcompression yes
rdbchecksum yes

BGSAVE            # snapshot now, in a forked child
SAVE              # snapshot now, ON THE MAIN THREAD. Never in production
LASTSAVE          # unix time of the last successful save

# AOF — an append-only log of every write command.
appendonly yes
appendfsync everysec        # always | everysec | no
appendfilename "appendonly.aof"
appenddirname "appendonlydir"
BGREWRITEAOF                # compact the log

# THE SHAPE OF THE TRADE:
#   RDB  compact, fast to load, cheap to run — and you lose everything since
#        the last snapshot, which may be fifteen minutes
#   AOF  loses at most a second — and the file is larger, needs periodic
#        rewriting, and loads more slowly
#
# They are not alternatives. The usual production answer is BOTH: AOF for
# the recovery point, RDB for fast restarts and portable backups.

Even appendfsync always is not a database's durability

It fsyncs before replying, so a single-node crash loses nothing — and it costs a disk sync per write, which takes Redis from hundreds of thousands of operations per second to a few thousand, discarding the reason you chose it. More importantly, in any realistic deployment replication is asynchronous (chapter 15), so a primary that dies after acknowledging a write can still lose it during failover even with always. Redis's durability story is "very little loss, very fast" rather than "no loss". If a write genuinely cannot be lost, the durable record belongs in a database with synchronous commit, and Redis holds a derived copy.

The fork

the operational hazard people meet by surprise
# BGSAVE and BGREWRITEAOF both fork a child process. The child writes the
# snapshot while the parent keeps serving.
#
# The fork itself uses COPY-ON-WRITE: parent and child share physical pages
# until one of them writes, at which point the kernel copies that page.
#
# So the memory overhead is proportional to HOW MUCH IS WRITTEN during the
# save, not to the dataset size. An idle instance forks almost for free. An
# instance under heavy write load can approach 2× the dataset in RSS before
# the child finishes.

INFO persistence
#   rdb_last_fork_usec          how long the fork call itself took
#   rdb_bgsave_in_progress
#   aof_rewrite_in_progress
#   rdb_last_bgsave_status      err means saves are FAILING

INFO memory
#   used_memory_rss             includes the COW pages during a save

# THREE WAYS THIS BITES:
#
# 1. THE OOM KILLER. maxmemory set to 80% of RAM, a save forks under load,
#    RSS climbs past 100%, the kernel kills the largest process — which is
#    Redis. This is the single most common Redis outage caused by
#    persistence, and the fix is sizing (chapter 12).
#
# 2. FORK LATENCY. The fork copies page tables, so it is O(memory) and
#    blocks the main thread. On a 64 GB instance that can be hundreds of
#    milliseconds of total unavailability, once per save.
#
# 3. TRANSPARENT HUGE PAGES make both far worse. With 2 MB pages instead of
#    4 KB, a single byte written copies 2 MB. Turn them off:
      echo never > /sys/kernel/mm/transparent_hugepage/enabled
#    Redis logs a warning about this at startup and it is routinely ignored.

# The kernel setting that stops the fork failing outright:
vm.overcommit_memory = 1
# Without it, fork() can fail when the kernel thinks there is not enough
# memory to duplicate the process — even though COW means there almost
# certainly is. Redis also warns about this at startup.

AOF in detail

the log, the rewrite, and the fsync setting
# Every write command is appended to the log. The log therefore grows without
# bound, so Redis periodically REWRITES it — forking a child that produces a
# minimal command sequence reproducing the current state.
auto-aof-rewrite-percentage 100    # rewrite when the file doubles
auto-aof-rewrite-min-size 64mb

# Redis 7 changed the layout to a MULTI-PART AOF: a base file (RDB-format by
# default) plus incremental files, tracked in a manifest, in appenddirname.
# That removed the old rewrite buffer entirely, which used to be a source of
# memory spikes during a rewrite. If you read older advice about
# aof-rewrite-incremental-fsync buffers, it predates 7.0.
aof-use-rdb-preamble yes           # base file in RDB format — smaller, faster

# THE FSYNC SETTING is the whole durability decision:
appendfsync always     # fsync before replying. ~1s of writes never at risk,
                       # and throughput drops by orders of magnitude
appendfsync everysec   # fsync once per second. Lose ≤1s. THE DEFAULT and
                       # almost always the right answer
appendfsync no         # let the OS decide. Typically 30s of exposure

# A DETAIL WORTH KNOWING: with everysec, if the background fsync is still in
# progress when new writes arrive, Redis can either block until it completes
# or write into the buffer anyway:
no-appendfsync-on-rewrite no
# `yes` avoids latency spikes during a rewrite at the cost of a larger loss
# window during it. On slow disks this is the setting that turns a rewrite
# into a latency incident.

# CHECKING AND REPAIRING:
redis-check-aof --fix appendonlydir/appendonly.aof.1.incr.aof
redis-check-rdb dump.rdb
# A truncated AOF from an unclean shutdown is normal and Redis handles it:
aof-load-truncated yes

Turning persistence off on a cache is a real win

It is worth being explicit because the instinct runs the other way. On a dedicated cache instance, save "" and appendonly no remove: the periodic fork and its latency spike, the copy-on-write memory overhead and the OOM risk that comes with it, the disk I/O competing with everything else on the box, and a whole category of "why did latency spike at 03:00" investigation. You are protecting data that is by definition reconstructible. The one thing to think through is the cold-start cost — a cache that restarts empty sends every request to the origin until it refills, so make sure the origin can survive that (chapter 7).

Backups

the RDB file is your backup
# An RDB is a single self-contained file. Copying it is the backup.
BGSAVE
# wait for rdb_bgsave_in_progress to become 0
cp /var/lib/redis/dump.rdb /backup/redis-$(date +%F-%H%M).rdb

# Better: take it from a REPLICA, so the primary never forks for backups
# (chapter 15). A replica configured with save "" can still be told to
# BGSAVE on demand.

# RESTORE is: stop Redis, put the file in dbfilename's location, start.
# Redis loads whichever is configured — AOF takes precedence over RDB if
# appendonly is yes, which is a common surprise:
#
#   You restore dump.rdb, start Redis, and the data is not there — because
#   appendonly yes is set and Redis loaded an empty AOF instead. Either
#   disable AOF for the restore and BGREWRITEAOF afterwards, or restore the
#   whole appendonlydir.

# WHAT AN RDB BACKUP DOES NOT GIVE YOU:
#   * point-in-time recovery. There is no WAL to replay to a chosen moment.
#     The AOF is close, and it is not designed for it — no timestamps, no
#     restore-to-time command
#   * consistency across several Redis instances
#   * protection against a bad write, unless a snapshot predates it
#
# So if you need PITR, Redis is not providing it. That is another form of
# chapter 18's question.

# TEST THE RESTORE. Same argument as every other unit: a backup nobody has
# restored is a hope, and redis-check-rdb passing is not the same as the
# data being correct and complete.

What can go wrong

Saves silently failing
rdb_last_bgsave_status:err — usually a full disk or no write permission. By default Redis then refuses writes (stop-writes-on-bgsave-error yes), which is safe and confusing: a disk problem presents as an application-wide write outage.
The fork triggering the OOM killer
maxmemory set too close to physical RAM, a save under write load, RSS doubles, the kernel kills Redis. Size for the fork.
Latency spikes at save time
The fork blocks the main thread for O(memory). Visible in rdb_last_fork_usec and in your p99. Worse with transparent huge pages on.
AOF growing unboundedly
Rewrites failing, or disabled. The file grows until the disk fills, and then saves fail, and then writes stop.
Restoring the wrong file
AOF takes precedence over RDB. Restoring a snapshot while appendonly yes is set loads nothing.
Disk too slow for everysec
If an fsync takes longer than a second, writes queue behind it. On shared cloud storage with burst credits this can appear suddenly, weeks after deployment.
Replication is not a backup, and it is most of your durability

A replica holds a copy of the data and applies your FLUSHALL faithfully within milliseconds, so it protects against a machine failing and nothing else — the same argument as the PostgreSQL and MongoDB units. But it is worth being clear about the balance here: for most Redis deployments, a replica plus AOF everysec provides more practical protection than any tuning of the fsync setting, because the realistic failure is a machine dying rather than a clean process crash. Configure both, and keep periodic RDB copies somewhere else for the case a replica cannot help with.

The short version

  1. RDB is a snapshot, AOF is a log. Production usually wants both — AOF for the recovery point, RDB for restarts and backups.
  2. appendfsync everysec is the right default. always costs orders of magnitude of throughput.
  3. Even always is not a database's durability, because replication is asynchronous.
  4. The fork is the operational hazard — memory proportional to writes during the save, and a latency spike proportional to dataset size.
  5. Turn transparent huge pages off and set vm.overcommit_memory = 1. Redis warns about both and it is routinely ignored.
  6. Turn persistence off on a pure cache. It removes the fork, the COW memory and a class of latency incident.
  7. AOF takes precedence over RDB on startup — restoring a snapshot with appendonly yes loads nothing.
  8. There is no point-in-time recovery. If you need it, Redis is not providing it.
