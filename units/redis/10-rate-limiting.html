Rate limiting and counting

Four algorithms, in order of accuracy and cost, each mapping onto a Redis structure. The cheapest one has a flaw that lets through double the configured rate, and knowing whether that matters is the whole decision.

fixed window sliding token bucket hyperloglog

Fixed window

two commands, and it is nearly right
# Bucket by time period, count within it.
window=$(( $(date +%s) / 60 ))
key="rl:u41:$window"

INCR   $key
EXPIRE $key 120 NX          # NX so a later request cannot extend the window
# reject if the INCR result exceeds the limit

# One key per user per minute, expiring on its own. Constant memory, two
# commands, no cleanup. This is what most rate limiters actually are.

# Atomically, so the EXPIRE cannot be missed if the process dies between them:
EVAL "
  local n = redis.call('INCR', KEYS[1])
  if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
  return n
" 1 rl:u41:$window 120

# THE BOUNDARY PROBLEM. A limit of 100 per minute permits 200 in a two-second
# span: 100 requests at 11:59:59 fill one window, 100 at 12:00:01 fill the
# next. Both are within the rules and the burst is twice the intended rate.
#
# Whether that matters depends entirely on what you are protecting. For a
# public API quota it is fine — the intent is fairness over an hour, not a
# hard ceiling per instant. For protecting a downstream service with a real
# concurrency limit, it is the difference between working and not.

Sliding window log

exact, and it costs one entry per request
# A sorted set scored by timestamp (chapter 5). Remove what has aged out,
# add this request, count what remains.
EVAL "
  local now    = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  local limit  = tonumber(ARGV[3])

  redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now - window)
  local used = redis.call('ZCARD', KEYS[1])
  if used >= limit then
    return {0, used}
  end
  redis.call('ZADD',   KEYS[1], now, ARGV[4])
  redis.call('PEXPIRE', KEYS[1], window)
  return {1, used + 1}
" 1 rl:u41 1741946400123 60000 100 "1741946400123-a9f2"

# Exactly correct: at most `limit` requests in ANY rolling window, with no
# boundary artefact.
#
# THE MEMBER MUST BE UNIQUE per request, or two requests in the same
# millisecond collapse into one sorted-set member and one of them is not
# counted. A random suffix or a request id does it.
#
# THE COST is one sorted-set entry per request in the window — roughly 70-100
# bytes each. A limit of 1,000 per hour across a million users is a hundred
# million entries, which is several gigabytes for a rate limiter. That is the
# reason the next algorithm exists.
#
# Note the ZREMRANGEBYSCORE runs on every request, so the work is spread out
# rather than accumulating. And PEXPIRE means an inactive user's key vanishes
# instead of lingering (chapter 2).

Sliding window counter

the practical compromise
-- Keep two fixed-window counters and weight the previous one by how much of
-- it still overlaps the rolling window.
--
--     estimate = current + previous * (1 - elapsed_fraction)
--
-- Two seconds into a ten-second window, 80% of the previous window is still
-- inside the rolling one, so 80% of its count is charged.

local now      = tonumber(ARGV[1])
local window   = tonumber(ARGV[2])
local limit    = tonumber(ARGV[3])
local this_win = math.floor(now / window)
local elapsed  = (now % window) / window

local cur  = tonumber(redis.call('GET', KEYS[1] .. ':' .. this_win) or 0)
local prev = tonumber(redis.call('GET', KEYS[1] .. ':' .. (this_win - 1)) or 0)

if cur + prev * (1 - elapsed) >= limit then return 0 end

redis.call('INCR',   KEYS[1] .. ':' .. this_win)
redis.call('EXPIRE', KEYS[1] .. ':' .. this_win, window * 2 / 1000)
return 1

-- Two small integers per user instead of one entry per request. The estimate
-- assumes requests were spread evenly through the previous window, which is
-- usually close enough — Cloudflare published measurements showing under
-- 0.003% of requests wrongly allowed at scale.
--
-- This is what most production rate limiters use. It removes the boundary
-- problem for a fraction of the memory of an exact log.
The sliding window counter is the default worth reaching for

Fixed window is cheapest and lets through twice the rate at a boundary. Sliding log is exact and costs one entry per request, which does not scale to a large user base. The sliding window counter gets essentially the accuracy of the log for the memory of the fixed window — two integers per user — and the approximation error is small enough that it does not show up in practice. Unless you have a specific reason to need exactness, or your limits are so low that the log's memory is irrelevant, this is the one to build.

Token bucket

when you want to permit bursts deliberately
-- Tokens refill at a steady rate up to a capacity. Each request takes one.
-- A user who has been idle has a full bucket and may burst; a sustained user
-- is throttled to the refill rate.

local capacity = tonumber(ARGV[1])       -- max burst
local rate     = tonumber(ARGV[2])       -- tokens per second
local now      = tonumber(ARGV[3])
local want     = tonumber(ARGV[4] or 1)

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local last   = tonumber(state[2]) or now

tokens = math.min(capacity, tokens + (now - last) * rate)

if tokens < want then
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
  return {0, tokens}                     -- rejected, and how many they have
end

redis.call('HSET', KEYS[1], 'tokens', tokens - want, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
return {1, tokens - want}

-- Tokens are computed on read from the elapsed time, so nothing has to run
-- on a timer and an idle bucket costs nothing.
--
-- WHY THIS ONE IS DIFFERENT: the others answer "how many in the last N
-- seconds". This one shapes traffic — it encodes both a sustained rate and
-- an allowed burst as separate parameters, which is what an API quota
-- usually wants. Capacity 100 with a rate of 10/s means "10 per second
-- sustained, but you may spend up to 100 at once if you have been quiet".
--
-- LEAKY BUCKET is the same structure with capacity == 1 burst allowance:
-- perfectly smooth output, no bursts at all. Use it when the downstream
-- service has a hard concurrency limit rather than a rate quota.

the practical details every limiter needs
# TELL THE CLIENT. A 429 with no information means they retry immediately.
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1741946460
Retry-After: 37
# Return the remaining count and reset time FROM the same Lua call, so the
# headers do not require a second round trip and cannot disagree.

# LIMIT ON SEVERAL DIMENSIONS. One key per dimension, all checked:
rl:ip:203.0.113.5        # crude, catches unauthenticated abuse
rl:user:41               # the real quota
rl:user:41:endpoint:search   # per-endpoint, for expensive operations
rl:global:search         # a system-wide ceiling
# Check the cheapest first and short-circuit. Check them all in ONE Lua
# script if you need the decision to be atomic across dimensions.

# FAIL OPEN OR CLOSED? If Redis is unreachable, do you allow or reject?
#   fail open  — an outage removes your protection, and the site stays up
#   fail closed — an outage rejects everything, turning a Redis problem into
#                 a total outage
# Usually fail open with a short client timeout, plus a much cruder local
# in-process limiter as a backstop. Decide deliberately and write it down.

# DO NOT COUNT THE CHECK ITSELF. A limiter that increments before deciding
# charges the user for requests you rejected, so a client in a retry loop can
# never recover — every retry extends the block. Increment only on allow, or
# make the reset time absolute rather than sliding.

Counting things

HyperLogLog — cardinality in 12 KB
# "How many DISTINCT users visited today" over hundreds of millions of
# events. A set is exact and costs memory proportional to the answer.
PFADD   visitors:2026-03-14 "u41" "u9" "u41"
PFCOUNT visitors:2026-03-14        # 2

# Fixed 12 KB per key, regardless of whether you added ten items or ten
# billion. Standard error around 0.81%.
PFMERGE visitors:week visitors:2026-03-08 ... visitors:2026-03-14
PFCOUNT visitors:week              # unique across the week — the union is
                                   # correct, not a sum of the days

# WHAT IT CANNOT DO, and this catches people: it cannot tell you whether a
# specific item is in it. There is no PFEXISTS. It counts and merges; that
# is all. If you need membership, you need a set or a bitmap.
#
# It also cannot be decremented, and merging is one-way.

# THE COMPARISON, for one million distinct user ids:
#   SET       ~60 MB, exact, supports membership and enumeration
#   BITMAP    ~125 KB, exact, needs dense integer ids (chapter 3)
#   HLL       12 KB, ~0.81% error, no membership
#
# So: bitmap if the ids are dense integers, HLL if they are not and you only
# need the count, set if you need to ask about individual members.

# TOP-K AND FREQUENCY. A sorted set is exact and unbounded in members:
ZINCRBY trending:2026-03-14 1 "redis"
ZREVRANGE trending:2026-03-14 0 9 WITHSCORES
# For a very large key space where approximate is fine, the RedisBloom
# module adds Count-Min Sketch and Top-K in bounded memory. Without the
# module, cap the sorted set periodically:
ZREMRANGEBYRANK trending:2026-03-14 0 -10001
A rate limiter is a hot key, and a hot key does not shard

Per-user limits distribute naturally — a million users are a million keys spread across the keyspace. A global limit is one key that every request touches, and in cluster mode that key lives on exactly one node, so your entire request rate serialises through one thread (chapters 1 and 16). At a few thousand requests per second that is fine. At a hundred thousand it is the bottleneck. The fixes are to shard the counter across N keys and check a random one with a limit of total/N, or to do the global limiting locally in each application instance with a share of the budget — both approximate, both far cheaper than the exact version.

Rate limiting is a product decision wearing an engineering costume

The algorithm is the easy part; all four above are twenty lines of Lua. The hard questions are what the limit should be, what happens when someone hits it, whether it is per user or per IP or per key, whether paying customers get more, and whether a burst is abuse or a legitimate batch job. Those get decided by whoever implements it, at the moment of implementation, usually by picking a round number. Instrument first — count what would have been rejected without rejecting it — and set the limit from the distribution you observe rather than from a guess. A limit that fires for 3% of legitimate users is a support burden that outlasts whatever it was protecting against.

The short version

  1. Fixed window is two commands and lets through 2× at a boundary. Often that is fine — decide, do not default.
  2. Sliding log is exact and costs one sorted-set entry per request, which does not scale to many users.
  3. The sliding window counter is the default — log accuracy for fixed-window memory.
  4. Token bucket shapes traffic: a sustained rate plus a deliberate burst allowance, as separate parameters.
  5. Return the remaining count and reset time from the same Lua call, so headers cannot disagree with the decision.
  6. Do not count rejected requests, or a client in a retry loop can never recover.
  7. HyperLogLog counts in 12 KB and cannot answer membership. Bitmap for dense integer ids, set if you need members.
  8. A global limit is one hot key that does not shard. Split it, or limit locally with a budget share.
