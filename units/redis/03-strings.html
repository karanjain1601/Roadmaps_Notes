Strings, counters and bitmaps

The type everyone learns first and stops thinking about. A Redis string is a byte array up to 512 MB, and the commands operating on it include atomic arithmetic, compare-and-set, and bit manipulation that turns a few kilobytes into a million-user presence index.

set incr setnx bitmaps

SET is more than SET

the options are the interesting part
SET key value
SET key value EX 60          # expire in 60 seconds
SET key value PX 500         # milliseconds
SET key value EXAT 1741950000    # absolute unix time
SET key value KEEPTTL        # keep the existing TTL (chapter 2)
SET key value NX             # only if the key does NOT exist
SET key value XX             # only if it DOES
SET key value GET            # return the OLD value (6.2+)

# NX is the important one. It is an atomic test-and-set in a single command,
# which is the basis of every lock in chapter 9:
SET lock:invoice:8842 "worker-3" NX EX 30
# OK    -> you hold the lock for 30 seconds
# (nil) -> someone else does

# Reads and multi-key forms:
GET key
GETDEL key                   # read and delete atomically (6.2+)
GETEX key EX 60              # read and set a new TTL (6.2+)
MSET a 1 b 2 c 3             # atomic across all of them
MGET a b c                   # one round trip for many keys
SETRANGE key 5 "xyz"         # overwrite from an offset
GETRANGE key 0 9             # a substring
STRLEN key
APPEND key "more"            # amortised O(1)

# MGET is worth knowing early: fetching 100 keys individually is 100 round
# trips. MGET is one. Chapter 14 is largely this observation applied
# everywhere.

Counters

atomic arithmetic, and why it matters so much
INCR      views:page:41          # 1
INCRBY    views:page:41 10       # 11
DECR      stock:TSH-001
DECRBY    stock:TSH-001 3
INCRBYFLOAT balance:41 12.50     # floats. See the warning below

# The value is a string that Redis parses as an integer. It must fit in a
# signed 64-bit integer, and INCR on a non-numeric string is an error rather
# than a silent zero.

# WHY THIS IS THE FOUNDATIONAL PRIMITIVE:
#
#   Read-modify-write in an application:
#       n = GET counter       # both clients read 41
#       SET counter n+1       # both write 42 — one increment is LOST
#
#   INCR:
#       INCR counter          # 42, then 43. Cannot be wrong.
#
# One thread executing one command to completion (chapter 1) makes the lost
# update from the SQL unit's chapter 10 structurally impossible. No lock, no
# transaction, no retry loop.

# The pattern that follows immediately — a rate limiter, complete:
INCR  ratelimit:u41:1741946400
EXPIRE ratelimit:u41:1741946400 60 NX
# if the INCR result is > 100, reject. Chapter 10 does this properly.

# DECR for stock, with the check built into the operation:
DECRBY stock:TSH-001 3
# if the result is negative, you oversold — compensate by adding it back.
# Chapter 8 shows the Lua version that checks and decrements indivisibly.
Not for money

INCRBYFLOAT uses long double arithmetic and Redis stores the result as a string, so repeated operations accumulate representation error exactly as any binary float does. This is the same argument as the SQL and MongoDB units and it has an extra edge here: there is no decimal type to switch to. Store money as an integer number of minor units — pence, cents — and use INCRBY. And be clear that a balance whose only copy is in Redis is a balance you can lose (chapter 13); the durable record belongs in a real database, with Redis holding a cache or a working counter that can be rebuilt.

Bitmaps

A million users in 128 KB A bitmap is a string addressed one bit at a time. Pick a use and see the arithmetic.
—as a bitmap
—as a set of ids
—saving
—use
the bit commands
SETBIT active:2026-03-14 41 1        # user 41 was active today
GETBIT active:2026-03-14 41          # 1
BITCOUNT active:2026-03-14           # how many users were active
BITCOUNT active:2026-03-14 0 99      # within a byte range
BITPOS  active:2026-03-14 1          # first set bit — first active user id

# Set operations ACROSS bitmaps, which is where this becomes powerful:
BITOP AND retained:7d active:2026-03-08 active:2026-03-09 ... active:2026-03-14
BITCOUNT retained:7d                 # users active EVERY day for a week

BITOP OR  wau active:2026-03-08 ... active:2026-03-14
BITCOUNT wau                         # weekly active users

BITOP XOR churn active:2026-03-13 active:2026-03-14
BITOP NOT inactive active:2026-03-14

# BITFIELD packs several small counters into one string — useful when you
# need many tiny values and one key per value would be all overhead:
BITFIELD stats:41 SET u8 0 12 SET u8 8 3 INCRBY u8 0 1 GET u8 0
#   u8/i8/u16/i32... at bit offsets, with overflow control:
BITFIELD stats:41 OVERFLOW SAT INCRBY u8 0 250    # saturate instead of wrap

# THE SPARSITY TRAP: SETBIT at offset 10,000,000 allocates the whole string
# up to that bit — 1.25 MB — even if it is the only bit set. So bitmaps are
# excellent for DENSE, sequential ids and terrible for sparse or non-numeric
# ones. A UUID cannot be a bit offset; a monotonic integer user id can.
Bitmaps are the right answer surprisingly often

A year of daily-active-user tracking for a million users is 365 keys of 128 KB, which is 46 MB — and answers "how many were active on any day in March", "who was active every day last week" and "how many active users did we retain from January" with two commands and no scan. The equivalent as sets of user ids is around 40× the memory and much slower to intersect. The requirements are narrow — dense, sequential, integer identifiers, and a question that reduces to a yes/no per identifier — and when they hold, nothing else comes close.

What a string costs

three encodings, chosen automatically
SET n 12345
OBJECT ENCODING n          # "int"    — stored as a long, no allocation
SET s "hello"
OBJECT ENCODING s          # "embstr" — value embedded with the object header,
                           #            one allocation. Up to 44 bytes
SET l "a very long string ..."
OBJECT ENCODING l          # "raw"    — separate allocation, mutable

APPEND s " world"
OBJECT ENCODING s          # "raw"    — appending always converts to raw,
                           #            even if the result is short

# The practical consequences:
#   * a short numeric value costs almost nothing beyond the key
#   * values under 44 bytes get the cheaper single-allocation form
#   * SETRANGE and APPEND over-allocate to make growth amortised, so a string
#     built up incrementally uses more memory than the same value set at once

MEMORY USAGE key           # actual bytes, including key name and overhead

# THE REAL COST IS USUALLY THE KEY, NOT THE VALUE. Every key carries roughly
# 50-80 bytes of overhead — the key string, the dict entry, the object header,
# the expiry entry if it has a TTL. So ten million keys holding a single
# integer each is on the order of 700 MB to hold 40 MB of data.
#
# When you have very many small values, a HASH holding them all is
# dramatically cheaper, because a small hash is stored as a flat list with
# almost no per-field overhead (chapters 4 and 12).

Serialised objects

the most common use, and its downside
SET user:41 '{"name":"Amara","tier":"gold","visits":412}' EX 3600
GET user:41

# Simple, and every read and write moves the WHOLE value. Updating `visits`
# means: GET, parse, modify, serialise, SET — five steps, a race condition in
# the middle, and the whole object across the network twice.

# A hash does the same job with field-level access (chapter 4):
HSET  user:41 name "Amara" tier "gold" visits 412
HGET  user:41 tier            # one field
HINCRBY user:41 visits 1      # atomic, no read, no race

# WHEN A SERIALISED STRING IS STILL RIGHT:
#   * the value is always read and written whole — a rendered HTML fragment,
#     an API response, a compiled template
#   * the shape is nested, and a hash is flat
#   * you want compression: gzip the JSON and store the bytes. On a large
#     document this can be a 5-10x memory saving, at CPU cost on both sides
#
# WHEN IT IS NOT:
#   * you update individual fields  -> hash
#   * you increment something in it -> hash, with HINCRBY
#   * it is large and you read part -> hash, or split the key

# One further note: use a compact serialisation. JSON is readable in
# redis-cli and roughly twice the size of MessagePack or Protobuf for the
# same data. On a cache holding millions of objects that is a real number,
# and the readability is worth something too — decide deliberately.

The short version

  1. SET's options are the interesting part — NX, XX, EX, KEEPTTL, GET.
  2. SET … NX EX is an atomic test-and-set with a lease, and the basis of every lock.
  3. INCR makes the lost update structurally impossible. No lock, no transaction, no retry.
  4. Never INCRBYFLOAT for money. Integer minor units, and the durable record lives elsewhere.
  5. Bitmaps need dense sequential integer ids, and then they are unbeatable — a million users in 128 KB.
  6. SETBIT at a high offset allocates the whole string. Sparse ids are the wrong fit.
  7. The per-key overhead is 50–80 bytes. Many small values belong in one hash, not many keys.
  8. MGET, not a loop of GET. One round trip instead of a hundred.
