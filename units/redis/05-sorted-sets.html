Chapter 05 · The structures

Sorted sets

A set where every member carries a numeric score, kept permanently in score order. It sounds narrow and it is the most versatile structure Redis has — leaderboards, priority queues, sliding-window rate limiters, secondary indexes and scheduled work are all the same type wearing different scores.

zset ranges rank skip list

What it is

unique members, ordered by a score you control
ZADD leaderboard 4820 "u41" 3100 "u9" 5940 "u7"

ZSCORE   leaderboard "u41"          # 4820          O(1)
ZINCRBY  leaderboard 10 "u41"       # 4830, atomic  O(log N)
ZRANK    leaderboard "u41"          # 1 — position, lowest first
ZREVRANK leaderboard "u41"          # 1 — highest first
ZCARD    leaderboard                # 3             O(1)
ZCOUNT   leaderboard 4000 6000      # how many in a score range

# Members are UNIQUE, like a set. ZADD on an existing member updates its
# score rather than adding a duplicate — which is what makes a leaderboard
# work without any deduplication logic.
#
# Ties are broken by lexicographic order of the member, so ordering is
# deterministic and stable across calls. That matters more than it sounds:
# pagination over a leaderboard with tied scores does not skip or repeat.

# Internally: a hash table (member -> score, giving O(1) ZSCORE) plus a
# SKIP LIST (ordered by score, giving O(log N) insert and range queries).
# Two structures kept in step, which is why a sorted set costs roughly twice
# what a plain set does per member.
#
# Small ones use the listpack encoding instead (chapter 4):
OBJECT ENCODING leaderboard         # "listpack" or "skiplist"

Ranges

Range queries, against real data Three coordinate systems — rank, score and lexicographic. Pick a query and see what it returns.
—returned
—complexity
—used for
the range commands
# BY RANK — position in the ordering. 0-based, negative counts from the end.
ZRANGE    leaderboard 0 9 WITHSCORES      # lowest ten
ZRANGE    leaderboard 0 -1                # everything. O(N) — careful
ZREVRANGE leaderboard 0 9 WITHSCORES      # top ten

# BY SCORE — the useful one.
ZRANGEBYSCORE leaderboard 3000 5000
ZRANGEBYSCORE leaderboard (3000 +inf      # ( makes the bound EXCLUSIVE
ZRANGEBYSCORE leaderboard -inf +inf LIMIT 20 10   # offset, count
ZREVRANGEBYSCORE leaderboard +inf 3000

# 6.2 unified all of these into ZRANGE with an argument. Both forms work;
# the older ones are clearer to read and are not going away:
ZRANGE leaderboard 3000 5000 BYSCORE
ZRANGE leaderboard "+inf" "-inf" BYSCORE REV LIMIT 0 10
ZRANGESTORE dest leaderboard 0 9          # store the result (6.2+)

# BY LEX — when every member has the SAME score, ordering falls back to
# lexicographic and you can range over the member strings themselves.
ZADD autocomplete 0 "redis" 0 "redisearch" 0 "relational"
ZRANGEBYLEX autocomplete "[red" "[red\xff"
#   [ = inclusive, ( = exclusive, - = minimum, + = maximum
# This is a prefix index. It is how autocomplete is built on Redis.

# POPPING — take the extremes, atomically.
ZPOPMIN leaderboard          # lowest-scored member, and remove it
ZPOPMAX leaderboard 3        # highest three
BZPOPMIN queue 0             # BLOCKING — a priority queue with no polling
ZMPOP 2 q1 q2 MIN            # from the first non-empty (7.0+)

# BULK REMOVAL — how a sorted set stays bounded.
ZREMRANGEBYSCORE window -inf 1741946340   # everything older than a cutoff
ZREMRANGEBYRANK leaderboard 0 -1001       # keep only the top 1000
Score-range plus LIMIT is the pattern to internalise

ZRANGEBYSCORE key min max LIMIT offset count is O(log N + M) — logarithmic to find the start of the range, then linear in what you actually return. It does not touch the rest of the set. That single property is why a sorted set works as a scheduler (score = due time, take everything up to now), a sliding-window rate limiter (score = timestamp, count what is in the window), a paginated feed (score = created at, take the next twenty) and a priority queue (score = priority, pop the minimum) — the same command with a different meaning attached to the score.

Five things this type does

Leaderboards

the obvious one, done correctly
ZINCRBY leaderboard:2026-03 50 "u41"        # award points, atomically
ZREVRANGE leaderboard:2026-03 0 9 WITHSCORES    # top ten
ZREVRANK  leaderboard:2026-03 "u41"             # "you are #1,204"
ZCARD     leaderboard:2026-03                   # total players

# "Players around me" — the feature every leaderboard needs:
rank=$(redis-cli ZREVRANK leaderboard:2026-03 u41)
ZREVRANGE leaderboard:2026-03 $((rank-2)) $((rank+2)) WITHSCORES

# Ties: members with equal scores are ordered lexicographically, so ranks are
# stable and pagination is consistent. If you want ties broken by who got
# there first, encode the timestamp into the score:
#     score = points * 10^10 + (10^10 - epoch_seconds)
# Careful — a double has 53 bits of integer precision, so composite scores
# have a real ceiling. Above 2^53 you silently lose the low-order part, which
# is exactly the tiebreak you encoded.

# Keep it bounded — a leaderboard for every user who ever played is unbounded:
ZREMRANGEBYRANK leaderboard:2026-03 0 -100001       # keep the top 100k

Time-ordered indexes and feeds

score = timestamp
ZADD feed:u41 1741946400 "post:8842"
ZREVRANGEBYSCORE feed:u41 +inf -inf LIMIT 0 20        # newest 20

# Keyset pagination, exactly as in the SQL and MongoDB units — the next page
# starts below the last score seen, so page 500 costs the same as page 1:
ZREVRANGEBYSCORE feed:u41 (1741946400 -inf LIMIT 0 20

# Retention by time, in one command:
ZREMRANGEBYSCORE feed:u41 -inf $(date -d '30 days ago' +%s)

# Compare with a list: a list can hold the same ids in the same order, and it
# cannot answer "everything since this timestamp", cannot remove by age, and
# cannot tell you an item's position. A sorted set can do all three because
# the ordering key is a value rather than an accident of insertion.

Scheduled and delayed work

score = when it should run
ZADD scheduled 1741950000 "send-reminder:8842"

# A worker, polling once a second:
ZRANGEBYSCORE scheduled -inf $(date +%s) LIMIT 0 100

# The naive version has a race: two workers read the same due jobs and both
# process them. Do the read and the removal atomically in Lua (chapter 8):
EVAL "
  local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, 100)
  if #due > 0 then redis.call('ZREM', KEYS[1], unpack(due)) end
  return due
" 1 scheduled $(date +%s)

# This is a delayed-job queue in about ten lines, with no extra
# infrastructure. It handles retries too: on failure, ZADD it back with a
# score of now + backoff.
#
# What it does not handle is a worker crashing mid-job, since the item was
# already removed. Move it to an in-flight sorted set scored by a deadline
# instead of removing it, and reap entries whose deadline has passed — which
# is the same reliable-queue argument as chapter 4, and the same conclusion:
# if the work must not be lost, chapter 6's streams do this properly.

Sliding-window rate limiting

score = request time
# A precise sliding window: at most 100 requests in any rolling 60 seconds.
now=$(date +%s%3N)
MULTI
  ZREMRANGEBYSCORE ratelimit:u41 -inf $((now - 60000))   # drop old
  ZADD             ratelimit:u41 $now "$now-$RANDOM"     # record this one
  ZCARD            ratelimit:u41                          # count the window
  EXPIRE           ratelimit:u41 60
EXEC
# if ZCARD > 100, reject

# The member must be unique per request — two requests in the same
# millisecond would otherwise collapse into one member. A random suffix or a
# request id does it.
#
# The cost is one entry per request in the window, so this is precise and
# memory-hungry compared with a fixed-window counter. Chapter 10 compares
# all four algorithms against the same traffic.

Secondary indexes

the range query Redis otherwise does not have
# Redis has no WHERE (chapter 2). A sorted set gives you one axis of it.
ZADD idx:product:price 2499 "TSH-001" 1250 "MUG-114"
ZRANGEBYSCORE idx:product:price 1000 3000          # products £10-£30

ZADD idx:user:lastseen 1741946400 "u41"
ZRANGEBYSCORE idx:user:lastseen -inf $(date -d '90 days ago' +%s)  # dormant

# COMBINING indexes — ZINTERSTORE does set algebra with score arithmetic:
ZINTERSTORE tmp 2 idx:product:price idx:in-stock WEIGHTS 1 0
ZRANGEBYSCORE tmp 1000 3000
DEL tmp
#   AGGREGATE SUM (default) | MIN | MAX
#   WEIGHTS multiplies each input's scores before aggregating — the 0 here
#   means "use in-stock only as a filter, keep the price as the score"
ZUNIONSTORE / ZDIFFSTORE work the same way.
ZINTERCARD 2 a b LIMIT 100      # just the count, stopping early (7.0+)

# THE OBLIGATION: every index is a structure YOU maintain. Creating a
# product means ZADD to every index it belongs in; deleting means ZREM from
# each; changing a price means ZADD again with the new score. Miss one write
# path and the index silently diverges from the truth.
#
# That is the trade. You get range queries in a system that has none, and you
# take on the job a real database's index does for you. Worth it for one or
# two hot access patterns; a sign you want a real database if you are
# maintaining eight.
Scores are doubles, so large integers lose precision

A sorted-set score is an IEEE-754 double, which represents integers exactly only up to 253 — about 9×1015. Unix seconds and milliseconds are fine. Microseconds are fine. Nanosecond timestamps are not, and neither are composite scores that multiply a value by a large factor to encode a tiebreak. The failure is silent: two distinct scores compare equal, ordering becomes arbitrary within the collision, and pagination starts repeating or skipping items. If you need more than 53 bits of ordering, put the tiebreak in the member string and rely on lexicographic ordering within equal scores instead.

When you cannot decide, it is probably a sorted set

The recurring shape: you have a list and need "everything since a timestamp", or a set and need ranking, or a hash and need "the top ten". A sorted set does all of those with one structure, at the cost of roughly twice the memory of a plain set and O(log N) writes instead of O(1) — which for anything below tens of millions of members is a difference you will not measure. Reaching for a sorted set slightly too often is a much cheaper mistake than discovering three months in that your list cannot answer the question you now need.

The short version

  1. Unique members, ordered by a numeric score you control — insertion order is not involved.
  2. ZRANGEBYSCORE … LIMIT is O(log N + M) and is the pattern behind almost every use.
  3. The same type is a leaderboard, feed, scheduler, rate limiter and secondary index — only the score's meaning changes.
  4. ZINCRBY is atomic, so a leaderboard needs no locking and no read.
  5. Ties break lexicographically, so ranks are stable and pagination is consistent.
  6. ZRANGEBYLEX on equal scores is a prefix index — this is how autocomplete is built.
  7. Scores are doubles: exact to 253. Nanoseconds and composite scores overflow silently.
  8. Every index is one you maintain. Fine for two access patterns, a warning sign at eight.
