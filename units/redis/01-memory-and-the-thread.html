Chapter 01 · The model

Memory and the thread

Redis makes two decisions that almost nothing else makes together: the data lives in RAM, and one thread executes every command in sequence. Nearly every property people like about Redis, and every constraint that surprises them, follows from those two.

in-memory single-threaded atomicity licensing

What Redis actually is

not a key-value store — a data structure server
# The usual description is "an in-memory key-value store", which is true and
# tells you almost nothing. The values are not blobs. They are DATA STRUCTURES
# with their own operations, executed on the server.

SET   session:8842 "{...}"              # string
LPUSH jobs:pending "job-01"             # list      — a queue
HSET  user:41 name "Amara" tier "gold"  # hash      — an object
SADD  online:now "u41" "u9"             # set       — membership
ZADD  leaderboard 4820 "u41"            # sorted set — ranked
XADD  events * type "click" user "u41"  # stream    — an append-only log
PFADD visitors:today "u41"              # hyperloglog — approximate cardinality

# The difference matters. This is one network round trip, atomic, and the
# server does the work:
ZINCRBY leaderboard 10 "u41"
ZREVRANK leaderboard "u41"

# In a plain key-value store, the same thing is: read the whole leaderboard,
# modify it in your application, write it back — with a race condition in the
# middle and the entire structure crossing the network twice.
#
# That is the pitch. Not "it is fast because it is in memory", but "the
# operations happen where the data is, indivisibly".

One thread

The single-threaded consequence Every command queues behind every other. That is the guarantee and the hazard, and they are the same fact.

The guarantee and the hazard are the same fact

Because one thread runs one command at a time to completion, every single command is atomic for free. No locks, no transactions, no read-modify-write races — INCR cannot lose an update, SETNX is a genuine test-and-set, LPOP hands the item to exactly one consumer. That is an enormous simplification and it is why Redis is good at coordination primitives. The same fact means one slow command blocks the entire server. There is no query running alongside yours; there is a queue. A 200ms command is 200ms of unavailability for every client, and chapter 14 is largely about that.

what "single-threaded" does and does not mean
SINGLE-THREADED:
  command execution. One command at a time, to completion, in arrival order.

NOT SINGLE-THREADED, and has not been for years:
  * I/O threads (6.0+) — reading and writing sockets can be parallel.
    io-threads 4 helps when the network is the bottleneck, not the commands
  * background saving — RDB and AOF rewrites happen in a forked child
    (chapter 13)
  * lazy freeing (4.0+) — UNLINK and async eviction free memory on a
    background thread, so deleting a huge key does not block
  * key expiry sampling, cluster bus, and various housekeeping

Redis 8 extends threading further. The invariant that matters has not moved:
COMMAND EXECUTION IS SERIAL, and reasoning about your data as though it were
is correct.

WHY SINGLE-THREADED AT ALL?
  Because the bottleneck is almost never CPU. For an in-memory store, most
  commands are a hash lookup and a pointer dereference — nanoseconds. The
  time goes on the network and the syscalls. Adding threads to command
  execution would buy little and cost locking on every data structure,
  which would make the common case slower and the semantics far harder.

  The way you use more cores is more PROCESSES: several Redis instances on
  one machine, or cluster mode (chapter 16).

Memory as the medium

Because the data is in RAMConsequence
Reads and writes are memory accessSub-millisecond, and the network dominates the latency
Structures can be pointer-basedSkip lists, linked lists and hash tables with no page layout to worry about
Capacity is your RAMThe hard constraint. A 64 GB machine holds under 64 GB of data
Data is volatilePersistence is a bolted-on option with real trade-offs (chapter 13)
Memory must be reclaimedEviction policies, TTLs, and fragmentation (chapter 12)
Cost per byte is highRAM is roughly two orders of magnitude more expensive than disk
A fork copies page tablesBackground saves can double memory use under write load (chapter 13)
Redis will not tell you it is nearly full until it is

A relational database with more data than memory gets slower. Redis with more data than memory either starts evicting — silently discarding keys according to a policy you may not have chosen — or starts refusing writes with an error. Neither degrades gracefully, and the default maxmemory is unlimited, which means the actual limit is the machine's RAM and the failure is the OOM killer terminating the process. Set maxmemory and an eviction policy deliberately on day one. Chapter 12 covers which, and it is the single most common operational omission in this unit.

What Redis is good at

Natural fits

  • Caching — the obvious one (chapter 7)
  • Counters and rate limits — atomic increments, no contention
  • Sessions — small, hot, expiring, tolerant of loss
  • Queues — lists and streams, with blocking pops
  • Leaderboards and ranked data — sorted sets, unmatched elsewhere
  • Locks and coordination — atomicity is the whole primitive
  • Real-time counting — HyperLogLog, bitmaps
  • Ephemeral pub/sub — presence, live updates

Poor fits

  • Your only datastore, for anything you cannot lose
  • Data much larger than RAM
  • Ad-hoc querying — there is no query language, by design
  • Relational data — no joins, no constraints, no schema
  • Large values — a 50 MB value blocks the thread to move it
  • Analytics over history — it is not a warehouse
  • Guaranteed delivery — without care, pub/sub drops messages

# Commands worth knowing on day one:
INFO             # everything about the server. INFO memory, INFO stats, ...
DBSIZE           # how many keys
COMMAND DOCS GET # built-in documentation for any command
MEMORY USAGE key # how many bytes this key costs
SLOWLOG GET 10   # the ten slowest recent commands (chapter 14)
MONITOR          # every command, live. NEVER in production — it is a
                 # firehose that slows the server measurably

The licence, since it is a real consideration

Redis is not BSD any more, and there are forks

Redis was BSD-licensed for its first fifteen years. In March 2024 the project relicensed to a dual RSALv2/SSPLv1 model — source-available rather than open source by the OSI definition — aimed at preventing cloud providers from offering managed Redis without a commercial arrangement. The Linux Foundation forked the last BSD version as Valkey, backed by AWS, Google and Oracle among others, and most major cloud providers moved their managed offerings to it. Redis subsequently added AGPLv3 as an option in Redis 8 (2025), which restored an OSI-approved licence to the project.

For most people building an application this changes nothing — using Redis as a datastore is unaffected under any of these. It matters if you redistribute Redis, offer it as a service, or have a policy against source-available or copyleft licences. Valkey is API-compatible with Redis 7.2 and diverging slowly; chapter 18 covers the practical difference. Check the current state before committing, because this has moved twice already and may move again.

The short version

  1. Redis is a data structure server, not a key-value store. The operations happen where the data is.
  2. One thread executes every command in sequence. That is why every command is atomic for free.
  3. It is also why one slow command blocks every client. The guarantee and the hazard are the same fact.
  4. I/O, background saves and lazy frees are threaded. Command execution is serial, and reasoning that way is correct.
  5. More cores means more processes, not more threads — several instances, or cluster mode.
  6. Capacity is your RAM. Redis does not degrade gracefully past it; it evicts or refuses writes.
  7. Set maxmemory and a policy on day one. The default is unlimited, and the failure is the OOM killer.
  8. The licence changed in 2024 and Valkey forked. Mostly irrelevant to application use; check before redistributing.
