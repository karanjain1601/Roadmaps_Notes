Redis

Almost everyone meets Redis as a cache and never finds out what else it is. It is a set of data structures with a network interface, executed one command at a time — which makes it a queue, a lock, a rate limiter, a leaderboard and a message log, all with atomicity you would otherwise have to build.

How to use this

No prerequisites. Unlike the PostgreSQL and MongoDB units, this one does not assume you have used a database in anger — Redis is small enough to learn from nothing, and most of its difficulty is in knowing which structure to reach for rather than in operating it.

Chapters 1–2 are the model, and the two facts in chapter 1 explain most of the rest. Chapters 3–6 are the data structures, which are the actual product. Chapters 7–11 are the patterns people build with them, including the ones that are harder than they look. Chapters 12–14 cover memory, persistence and the single thread. Chapters 15–17 are replication, cluster and operations, and chapter 18 is where Redis is the wrong answer.

Demos run real logic — you can watch sorted-set ranges resolve, compare four rate-limiting algorithms against the same traffic, and see eviction policies choose different victims from the same keyspace. Examples target Redis 7 and later, and note where behaviour changed.

Two commitments

Beyond the cache

Caching gets one chapter of eighteen. It is the most common use and the least interesting one, and treating Redis as only a cache means reimplementing in application code several things it already does atomically.

Honest about the sharp edges

Replication is asynchronous, so a failover loses writes. Distributed locks are harder than the tutorials suggest. The licence changed and there are now forks. All of that is in here rather than in a footnote.
