Caching

The use everyone starts with. The basic pattern is four lines and correct; the interesting parts are what happens when a popular key expires, when the underlying data changes, and when the cache and the database disagree about reality.

Cache-aside

the pattern, and the two lines people get wrong
def get_product(pid):
    key = f"cache:product:{pid}:v3"
    cached = r.get(key)
    if cached is not None:
        return decode(cached)

    product = db.query("SELECT ... WHERE id = %s", pid)
    r.set(key, encode(product), ex=300 + random.randint(0, 60))
    return product

# The two details that matter:
#
#   `is not None` — not a truthy check. A cached empty list, zero or empty
#   string is a HIT, and treating it as a miss means the most-cached values
#   are the ones that never cache.
#
#   The jitter on the TTL. Without it, everything cached during a deploy
#   expires in the same second and the database takes the whole load at once
#   (chapter 2). A few percent of random spread costs nothing and removes
#   an entire class of incident.

# WRITE PATH — delete rather than update:
def update_product(pid, changes):
    db.update(pid, changes)
    r.delete(f"cache:product:{pid}:v3")

# Deleting is safer than writing the new value, because two concurrent
# updates can write their values to the cache in the opposite order to the
# database — leaving the cache permanently holding the older one. Deleting
# has no ordering to get wrong: the next read repopulates from the current
# truth.

# And delete AFTER the database write, never before. Before, and a concurrent
# read can repopulate the cache with the old value in the window between.
Delete, do not update

"Write to the database, then write the new value to the cache" is the version people reach for and it has a race with no fix. Two writers, A then B: A writes to the database, B writes to the database, B writes to the cache, A writes to the cache. The database holds B's value and the cache holds A's, permanently, until the TTL expires — and if the TTL is long, that is hours of serving wrong data with nothing to indicate it. Deleting has no such ordering: whichever delete lands last, the next read fetches whatever the database currently holds. The cost is one extra database read after each write, which is almost always the right trade.

Stampedes

What happens when a hot key expires The naive pattern sends every concurrent request to the database at once. Four ways to stop it.
—database hits per expiry

serve stale while revalidating — usually the best answer
# Store the value with a LOGICAL expiry inside it, and give the key a much
# longer real TTL. The value is then never absent — only sometimes old.

def get_with_swr(pid, fresh_for=300, keep_for=3600):
    key = f"cache:product:{pid}:v3"
    raw = r.get(key)

    if raw is None:                              # genuine cold miss
        return recompute_and_store(pid, fresh_for, keep_for)

    entry = decode(raw)
    if time.time() < entry["fresh_until"]:
        return entry["value"]                    # fresh

    # Stale but usable. ONE caller wins the right to refresh; everyone else
    # gets the stale value immediately and nobody waits.
    if r.set(f"lock:refresh:{pid}", "1", nx=True, ex=30):
        background(recompute_and_store, pid, fresh_for, keep_for)

    return entry["value"]

# Properties worth naming:
#   * no user ever waits for a recompute except on a genuine cold miss
#   * exactly one recompute happens per staleness period
#   * the database sees a trickle rather than a spike
#   * the cost is serving data up to `fresh_for` old, which for most reads
#     is invisible
#
# The failure mode to handle: if the recompute keeps failing, the value keeps
# being served past keep_for and then vanishes. Log refresh failures loudly —
# a cache that silently serves hour-old data because the refresh has been
# broken since Tuesday is worse than one that fails.

# VERSION IN THE KEY — invalidate everything at once, with no deletion.
cache:product:8842:v3
# Deploy changes the serialisation? Bump to v4. Every v3 key is instantly
# unreachable and expires on its own schedule. No SCAN, no mass delete, no
# thundering herd of deletions. This costs one stale generation's memory for
# one TTL and it is the cheapest bulk invalidation there is.

# A global generation counter does the same thing dynamically:
INCR cache:generation                     # -> 7
# key = f"cache:gen{gen}:product:{pid}"

# TAG SETS — when one change invalidates a set of keys you cannot enumerate.
SADD tag:product:8842 "cache:page:home" "cache:page:category:5"
SADD tag:product:8842 "cache:api:search:keyboards"

# On change:
SMEMBERS tag:product:8842 | xargs redis-cli UNLINK
UNLINK tag:product:8842

EVAL "
  local keys = redis.call('SMEMBERS', KEYS[1])

  redis.call('UNLINK', KEYS[1])
  return #keys
" 1 tag:product:8842

# The obligation: every write that caches a derived value must also SADD the
# key to every tag it depends on. Miss one and that entry never invalidates.
# Give the tag sets a TTL longer than the cached entries so they clean
# themselves up.
A cache is a second copy, and second copies diverge

Every caching strategy is a bet about how long you can tolerate the copy being wrong, and there is no configuration that makes divergence impossible — a delete can fail, a write path can be missed, a network partition can strand an invalidation. So the design question is not "how do I keep it perfectly correct" but "how wrong can it get, for how long, and what happens then". A TTL is the answer to the last part: it bounds every failure mode, including ones you have not thought of. That is why every cache key should have a TTL even when you invalidate explicitly — the TTL is the backstop for the invalidation you missed.

Negative caching

cache the absence, or the misses go straight through
# A key that does not exist in the database is never cached, so every
# request for it hits the database. Point a scraper at /product/{random}
# and every request is a database query — a cache with a 99% hit rate
# providing zero protection against exactly the traffic you need protecting
# from.

MISSING = b"\x00__miss__"

def get_product(pid):
    key = f"cache:product:{pid}:v3"
    cached = r.get(key)
    if cached == MISSING:
        return None                              # cached absence
    if cached is not None:
        return decode(cached)

    product = db.query(...)
    if product is None:
        r.set(key, MISSING, ex=60)               # SHORT ttl
    else:
        r.set(key, encode(product), ex=300)
    return product

# Use a much shorter TTL for misses than for hits. A product that does not
# exist yet may exist in a minute, and caching that absence for an hour makes
# creation appear broken.

# For very large key spaces where even the negative entries would be too
# many, a Bloom filter in front is the standard answer — either the
# RedisBloom module, or one you maintain with SETBIT (chapter 3):
BF.EXISTS products:filter "8842"     # definitely absent, or maybe present

What to cache

Good candidates

  • Expensive to compute — an aggregation, a rendered page, an external API call
  • Read far more than written — the ratio is the whole argument
  • Tolerant of being slightly stale
  • Small enough to move without blocking the thread
  • Requested repeatedly — a cache with no reuse is pure overhead

Poor candidates

  • Cheap queries already served by an index — you added a network hop
  • Written as often as read — invalidation costs more than it saves
  • Anything that must be exactly current — a balance, a stock level
  • Per-user data with no reuse — one hit per entry
  • Large values — a 50 MB blob blocks the thread (chapter 14)
Measure the hit rate per key pattern, not overall

An aggregate hit rate of 94% sounds healthy and can hide a pattern at 12% that accounts for most of the traffic — the overall figure is dominated by whichever pattern is most cacheable, which is not the one causing you problems. Track hits and misses per pattern, and be prepared to remove a cache that is not earning its place: a cache with a low hit rate costs a round trip on every request, memory for entries nobody reads, and an invalidation path to maintain, in exchange for nothing. INFO stats gives you keyspace_hits and keyspace_misses globally; per-pattern tracking has to come from your application.

Operating a cache

the settings that make it a cache rather than a database
# A dedicated cache instance should be configured to discard data freely.
maxmemory 8gb
maxmemory-policy allkeys-lru        # or allkeys-lfu. NOT volatile-* — those
                                    # only evict keys with a TTL, and if none
                                    # qualify Redis refuses writes (chapter 2)
save ""                             # no RDB snapshots. It is a cache
appendonly no                       # no AOF either

# Persistence on a cache costs fork memory and disk I/O to protect data you
# are willing to lose by definition. Turning it off is one of the few
# genuinely free wins available (chapter 13).

INFO stats

#   evicted_keys                         -> rising means undersized
#   expired_keys
INFO memory
#   used_memory vs maxmemory

# THE NUMBER TO WATCH IS evicted_keys. Steady eviction means the working set
# does not fit and Redis is discarding things that would have been hits. It
# is not an error and there is no alarm — the hit rate simply degrades.

# And separate your instances. A cache and a session store on one instance
# share one maxmemory and one eviction policy, so a cache surge evicts
# sessions and logs everybody out. Different durability requirements mean
# different instances (chapter 18).

The short version

  1. Delete on write, do not update. Writing the new value has an ordering race with no fix.
  2. Delete after the database write, never before.
  3. Jitter every TTL. Without it, everything cached together expires together.
  4. Serve stale while revalidating is usually the best stampede answer — nobody waits, one recompute happens.
  5. Every key gets a TTL, even with explicit invalidation. The TTL is the backstop for the invalidation you missed.
  6. A version in the key invalidates everything at once with no deletion at all.
  7. Cache absences too, with a short TTL — otherwise misses go straight through.
  8. Measure the hit rate per pattern, and remove caches that are not earning their place.
