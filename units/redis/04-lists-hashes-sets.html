Chapter 04 · The structures

Lists, hashes and sets

Three structures covering queues, objects and membership. Most Redis code is made of these plus strings, and choosing between them is mostly a question of which operations you need to be cheap.

lists hashes sets encodings

Lists

a doubly-linked structure — fast at the ends, slow in the middle
LPUSH  jobs "a" "b"        # push left. O(1)
RPUSH  jobs "c"            # push right. O(1)
LPOP   jobs                # pop left. O(1)
RPOP   jobs [count]        # pop right, optionally several
LLEN   jobs                # O(1)
LRANGE jobs 0 9            # O(N) in what you ASK FOR — bound it
LINDEX jobs 5              # O(N) — walks from the nearest end
LSET   jobs 5 "x"          # O(N)
LREM   jobs 1 "x"          # remove occurrences. O(N)
LTRIM  jobs 0 999          # keep the first 1000, discard the rest. O(N)
LPOS   jobs "x"            # find the index of a value (6.0.6+)
LMPOP  2 q1 q2 LEFT        # pop from the first non-empty of several (7.0+)

# BLOCKING pops — the reason lists are used as queues at all:
BLPOP  jobs 0              # block until an element arrives. 0 = forever
BRPOP  jobs 5              # or time out after 5 seconds
BLMPOP 5 2 q1 q2 LEFT      # blocking multi-key (7.0+)

# The client waits on the server rather than polling, so there is no
# busy-loop and no latency between the push and the pop. A worker doing
# BLPOP in a loop is an efficient consumer with no polling interval to tune.

# A CAPPED LIST — a recent-events log that cannot grow without bound:
LPUSH  recent:u41 "event"
LTRIM  recent:u41 0 99     # keep the newest 100
# Two commands. Do them in a pipeline or a MULTI so the trim always follows
# (chapter 8), or the list grows if the second one fails.
A list is a queue, and it is not a message queue

LPUSH plus BRPOP gives you a working job queue in two commands, and it is genuinely good for that. What it does not give you is acknowledgement: once a worker pops an item, the item is gone from Redis, so a worker that crashes mid-job loses the work with no record. LMOVE (or the deprecated RPOPLPUSH) into a processing list is the classic mitigation — the item moves atomically to a second list, and the worker removes it there on success — but you then have to detect and recover abandoned items yourself. If the work must not be lost, you want a stream with consumer groups (chapter 6), which does all of this properly.

the reliable-queue pattern, and its limits
# Atomically move an item from the queue to a per-worker processing list:
LMOVE jobs processing:worker-3 RIGHT LEFT
BLMOVE jobs processing:worker-3 RIGHT LEFT 0     # blocking version

# ... do the work ...
LREM processing:worker-3 1 "the-job"             # acknowledge

# If the worker dies, the job sits in processing:worker-3 forever. You need
# a reaper: something that looks for processing lists belonging to workers
# that have stopped heartbeating and moves their items back.
#
# That reaper is the part people skip, and it is why this pattern quietly
# loses jobs. Chapter 6's consumer groups have the equivalent built in —
# XAUTOCLAIM does exactly this and knows how long each message has been
# pending.

# WHERE A LIST QUEUE IS STILL THE RIGHT CHOICE:
#   * the work is idempotent and cheap to redo, so loss is tolerable
#   * you want the simplest possible thing and one consumer
#   * throughput matters more than delivery guarantees
#   * you are pushing to a fan-out of workers with BRPOP and no state

Hashes

an object, with field-level access
HSET    user:41 name "Amara" tier "gold" visits 412
HGET    user:41 tier                  # one field. O(1)
HMGET   user:41 name tier             # several. O(N) in fields requested
HGETALL user:41                       # ALL of them. O(N) — see the warning
HDEL    user:41 tier
HEXISTS user:41 tier
HLEN    user:41
HKEYS / HVALS user:41                 # also O(N)
HINCRBY user:41 visits 1              # ATOMIC, no read needed
HINCRBYFLOAT user:41 score 1.5
HSETNX  user:41 created "..."         # only if the field is absent
HRANDFIELD user:41 2 WITHVALUES       # random fields (6.2+)
HSCAN   user:41 0 COUNT 100           # iterate a large hash safely

# Field-level TTLs, new in 7.4 — the exception to "TTLs are per key":
HEXPIRE user:41 3600 FIELDS 1 tier
HTTL    user:41 FIELDS 1 tier
HPERSIST user:41 FIELDS 1 tier

# WHY A HASH RATHER THAN A JSON STRING (chapter 3):
#   HINCRBY user:41 visits 1
# is one atomic command with no read. The string version is GET, parse,
# increment, serialise, SET — five steps and a lost-update race.

# WHY A HASH RATHER THAN MANY STRING KEYS:
#   user:41:name, user:41:tier, user:41:visits
# is three keys, each carrying 50-80 bytes of overhead. One small hash holds
# all three fields with almost none, because it is stored as a flat list
# rather than a hash table (see encodings below). At ten million objects
# that difference is measured in gigabytes.
HGETALL is the O(N) command people forget is O(N)

It reads perfectly innocently, it is what every ORM-style wrapper reaches for, and it returns every field over the wire. On a hash with twenty fields that is nothing. On one that has accumulated a field per day for three years, it is a 1,000-field response blocking the thread and crossing the network on every request — and it got there gradually, with no point at which anything broke. Use HMGET for the fields you need, HSCAN to iterate, and treat a hash that grows a field per event as the modelling error it is. The same warning applies to LRANGE 0 -1, SMEMBERS and ZRANGE 0 -1.

Sets

unordered, unique, with set algebra on the server
SADD      online "u41" "u9"          # O(1) per member
SREM      online "u9"
SISMEMBER online "u41"               # O(1) — the membership test
SMISMEMBER online "u41" "u9"         # several at once (6.2+)
SCARD     online                     # O(1) count
SMEMBERS  online                     # O(N) — everything. Careful
SRANDMEMBER online 5                 # random sample, without removing
SPOP      online 5                   # random, removing
SMOVE     online offline "u41"       # atomic move between sets
SSCAN     online 0                   # safe iteration

# SET ALGEBRA, computed server-side:
SINTER      tag:redis tag:database   # members in both
SUNION      tag:redis tag:valkey
SDIFF       tag:redis tag:database   # in the first, not the others
SINTERCARD 2 tag:redis tag:database LIMIT 100   # just the count (7.0+)
SINTERSTORE result tag:redis tag:database       # store the result

# SINTERCARD is worth knowing: "how many users have both tags" without
# materialising the intersection. The LIMIT stops early once it has counted
# that many, which turns an expensive question into a cheap one when you only
# need to know whether it exceeds a threshold.

# The natural uses:
#   * membership:      is this user online, is this token revoked
#   * deduplication:   have I already processed this id
#   * tagging:         which items have all of these tags
#   * relationships:   followers, group members, permissions

# Deduplication in one command — SADD returns how many were NEW:
SADD processed:batch-7 "msg-8842"
# 1 -> new, process it.  0 -> already seen, skip.

Encodings

small collections are stored completely differently
HSET small a 1 b 2
OBJECT ENCODING small        # "listpack" — a flat, contiguous byte array

# ... add 200 fields ...
OBJECT ENCODING small        # "hashtable" — a real hash table

# Redis switches representation once a collection exceeds a threshold. Below
# it, the structure is a compact flat array with almost no per-element
# overhead; above it, a proper data structure with pointers and metadata.

CONFIG GET hash-max-listpack-entries    # 128
CONFIG GET hash-max-listpack-value      # 64  (bytes per value)
CONFIG GET list-max-listpack-size       # 128
CONFIG GET set-max-intset-entries       # 512  (all-integer sets)
CONFIG GET set-max-listpack-entries     # 128  (7.2+, non-integer sets)
CONFIG GET zset-max-listpack-entries    # 128

# THE DIFFERENCE IS LARGE. A 100-field hash as a listpack can be ~10x smaller
# than the same hash as a hashtable, because the hashtable pays a pointer, a
# length and allocator overhead per field.
#
# The trade is time complexity: listpack operations are O(N) over a small N,
# which is fast because it is contiguous and cache-friendly. That is why the
# thresholds are small — the encoding is a memory optimisation that stops
# being a good deal once N grows.

# THE CONVERSION IS ONE-WAY. A hash that briefly exceeded 128 fields and then
# shrank back to 10 stays a hashtable until the key is rewritten. So a
# transient spike permanently costs you memory:
DEBUG OBJECT key             # or just recreate the key

# THE PATTERN THIS ENABLES — sharded hashes. Instead of ten million string
# keys, bucket them into hashes of ~100 fields each:
#   user:meta:{id % 100000}  ->  field "41" = "..."
# Ten million values in a hundred thousand listpack hashes uses a fraction of
# the memory of ten million keys. Chapter 12 works through the arithmetic.

The question is which operation you need to be O(1)

All three add in constant time and count in constant time, so those never decide it. What decides it is the read: if you ask "is X in here" constantly, that is a set. If you ask "what is X's tier", that is a hash. If you ask "give me the next one", that is a list. Picking by what the data is — "it's a collection of users, so a set" — produces code that then does SMEMBERS and filters in the application, which is the whole thing the server-side structure was supposed to avoid. Pick by the access pattern, and if two access patterns disagree, maintain two structures. Duplication is cheap here.

The short version

  1. Lists are fast at the ends and slow in the middle. LINDEX and LSET are O(N).
  2. BLPOP makes a list a queue with no polling — and no acknowledgement. Use a stream if loss matters.
  3. LTRIM after LPUSH is how a list stays bounded. Do both in one pipeline.
  4. A hash beats a JSON string for anything with field-level updates, because HINCRBY is atomic and needs no read.
  5. A hash beats many keys — 50–80 bytes of overhead per key, almost none per listpack field.
  6. HGETALL, SMEMBERS and LRANGE 0 -1 are O(N) and get there gradually.
  7. SADD returning 1 or 0 is a deduplication check in one command.
  8. Small collections use a compact encoding and the conversion is one-way — a transient spike costs memory permanently.
