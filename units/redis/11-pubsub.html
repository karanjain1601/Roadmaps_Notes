Pub/Sub and messaging

Publish a message, every current subscriber receives it, nothing is stored. That is the entire feature — and the word "current" is doing more work than most people notice when they build on it.

publish at-most-once notifications sharded

The mechanism

four commands and no storage
# Subscriber
SUBSCRIBE room:general
# 1) "subscribe"  2) "room:general"  3) (integer) 1
# ... then, for each message:
# 1) "message"    2) "room:general"  3) "hello"

# Publisher
PUBLISH room:general "hello"
# (integer) 2      <- how many subscribers RECEIVED it, right now

PSUBSCRIBE room:*              # glob patterns
PUNSUBSCRIBE room:*
PUBSUB CHANNELS                # active channels with subscribers
PUBSUB NUMSUB room:general
PUBSUB NUMPAT

# The return value of PUBLISH is the only feedback there is, and it is worth
# understanding precisely: it counts subscribers the message was DELIVERED
# to, not subscribers who processed it. Zero means nobody was listening and
# the message is gone — no queue, no retry, no record that it existed.

# A subscribed connection is IN SUBSCRIBER MODE and can only run
# SUBSCRIBE, UNSUBSCRIBE, PSUBSCRIBE, PUNSUBSCRIBE, PING and QUIT. To both
# publish and subscribe you need two connections, which every client library
# handles for you — and which is why a naive implementation that reuses one
# pooled connection fails confusingly.
#
# RESP3 (Redis 6+) relaxes this: with HELLO 3 a client can subscribe and
# still issue other commands on the same connection, because push messages
# are distinguishable from replies at the protocol level.

What gets lost

Where the messages go Pub/sub is at-most-once. Pick a situation and see what the subscriber receives.

At most once, and usually that is the wrong guarantee

A published message is delivered to whoever is connected at that instant and then discarded. A subscriber that is restarting, redeploying, briefly disconnected, or simply slow enough to be disconnected for buffer overrun misses everything that arrived meanwhile, permanently and silently. There is no acknowledgement, no replay, and no signal that anything was missed. That is fine for data that is refreshed anyway — a presence update, a live counter, a cache invalidation hint — because the next message repairs the gap. It is wrong for anything where a missed message means work not done, and "we restart during every deploy" means the gap is not hypothetical.

Slow subscribers get disconnected

the failure mode nobody configures for
CONFIG GET client-output-buffer-limit
# "normal 0 0 0 slave 268435456 67108864 60 pubsub 33554432 8388608 60"
#                                          ^^^^^^ hard  soft  seconds

# For pub/sub clients: disconnect immediately at 32 MB of pending output, or
# after 60 continuous seconds above 8 MB.
#
# A subscriber that cannot keep up accumulates unsent messages in a buffer on
# the SERVER. When that buffer hits the limit, Redis closes the connection.
# The client reconnects, resubscribes, and has lost everything in between —
# with nothing in its own logs to explain the gap beyond a reconnection.

# Watch for it:
CLIENT LIST TYPE pubsub
#   omem=...   output buffer memory for this client
INFO clients
#   client_recent_max_output_buffer

# THE SECOND HAZARD: those buffers are server memory, charged to your
# instance. A few hundred slow subscribers on a busy channel can consume
# gigabytes before the limits kick in, and that memory competes with your
# data for maxmemory (chapter 12).

# Mitigations, in order of usefulness:
#   * do not do slow work in the message handler. Receive, enqueue locally,
#     acknowledge nothing, and process on another thread
#   * publish less — a notification that something changed, not the payload
#   * fan out to fewer subscribers and distribute within your application
#   * use a stream, where a slow consumer falls behind instead of being
#     disconnected, and can catch up afterwards

Keyspace notifications

events from the data itself
CONFIG SET notify-keyspace-events "KEA"      # everything. Usually too much
CONFIG SET notify-keyspace-events "Ex"       # expired events only

SUBSCRIBE __keyevent@0__:expired
PSUBSCRIBE __keyspace@0__:session:*

#   K  keyspace events: __keyspace@__:   -> the event name
#   E  keyevent events: __keyevent@__: -> the key name
#   g generic  $ string  l list  s set  h hash  z zset  x expired  e evicted
#   t stream   d module  m key-miss   n new-key (7.0+)   A = everything but K/E

# Uses that work:
#   * invalidate a local in-process cache when a key changes
#   * a metric on eviction rate
#   * debugging what is touching a key

# Uses that do NOT work, and this is the important part:
#   * "clean up the user's data when their session expires" — a subscriber
#     that is restarting misses the event and the cleanup never happens
#   * anything where a missed event is a bug rather than a delay
#
# These notifications ride on pub/sub, so they inherit every property above.
# They are hints, not triggers.

# TWO FURTHER DETAILS:
#   * the `expired` event fires when the key is actually REMOVED, which may
#     be noticeably after it logically expired (chapter 2)
#   * notifications add work to every matching command. "KEA" on a busy
#     instance has a measurable cost, so enable only the classes you use

# CLIENT-SIDE CACHING (Redis 6, RESP3) is the well-engineered version of
# cache invalidation, and it is a separate mechanism:
CLIENT TRACKING ON
# The server remembers which keys each client has read and pushes an
# invalidation when they change. Purpose-built for a local cache in front of
# Redis, with none of the pattern-matching cost.

Sharded pub/sub

the cluster problem, and the 7.0 fix
# In cluster mode, ordinary PUBLISH is BROADCAST TO EVERY NODE, because any
# node might have a subscriber for that channel. So publishing scales with
# the number of nodes rather than being distributed by them — adding nodes
# makes pub/sub slower, which is the opposite of what sharding is for.

SPUBLISH   room:general "hello"        # 7.0+
SSUBSCRIBE room:general
SUNSUBSCRIBE room:general

# A sharded channel is hashed to a slot exactly like a key, so the message
# goes to one node and its subscribers only. Publishing now distributes.
#
# The cost: subscribers must connect to the node owning that channel's slot,
# and a client must handle the MOVED redirection. Every cluster-aware client
# library does, and it means a subscriber cannot listen to arbitrary channels
# from one connection.
#
# Also note SPUBLISH does not support patterns. Sharding and glob matching
# are fundamentally incompatible — you cannot route a pattern to one node.

# If you use pub/sub at all in cluster mode, use the sharded form. The
# broadcast behaviour of plain PUBLISH is a real scaling problem and it is
# invisible until the cluster is large enough for it to hurt.

Publish the fact, not the payload

A message saying {"type":"product.updated","id":8842} is a few dozen bytes; one carrying the whole product document is kilobytes, multiplied by every subscriber, held in per-client output buffers on the server. It also goes stale the instant it is sent, so a subscriber processing it a second later may act on data that has already changed again. Publish the identifier and let the subscriber fetch what it needs — that keeps the channel cheap, keeps the read authoritative, and means a subscriber that missed three updates to the same entity does one fetch rather than three stale ones.

A pattern that works

pub/sub for latency, a durable store for correctness
# The combination that gets both properties: fast notification from pub/sub,
# and no missed work because the durable record is the source of truth.

# Producer — write the work, THEN announce it.
r.zadd("work:pending", {job_id: time.time()})
r.publish("work:new", job_id)

# Consumer
def run():
    catch_up()                       # 1. on start, drain anything pending

    p = r.pubsub()
    p.subscribe("work:new")
    while True:
        msg = p.get_message(timeout=5.0)
        if msg and msg["type"] == "message":
            claim_and_run(msg["data"])
        else:
            catch_up()               # 2. periodically, regardless

def catch_up():
    for job_id in r.zrangebyscore("work:pending", "-inf", time.time()):
        claim_and_run(job_id)

# The pub/sub message is a HINT that makes the common case fast — the
# consumer reacts in microseconds rather than waiting for the next poll.
# The sorted set is the truth, and the periodic catch-up means a missed
# notification costs latency rather than correctness.
#
# This is the right shape whenever you want low latency and cannot tolerate
# loss, and you do not want the operational weight of a stream. It is also
# what most "we use pub/sub for jobs" systems should have been.

The short version

  1. Fire and forget. Delivered to whoever is connected at that instant, then discarded.
  2. PUBLISH returns the subscriber count — that is the only feedback, and zero means the message is gone.
  3. A slow subscriber is disconnected at the output buffer limit, losing everything in between.
  4. Those buffers are server memory competing with your data.
  5. Keyspace notifications ride on pub/sub, so they are hints and never reliable triggers.
  6. Use SPUBLISH in cluster mode. Plain PUBLISH broadcasts to every node.
  7. Publish the identifier, not the payload — cheaper, and the subscriber reads current data.
  8. Pair pub/sub with a durable record when loss matters: the message is a latency hint, the store is the truth.
