Locking and coordination

A distributed lock in Redis is one command, and every tutorial stops there. The interesting part is the four ways it breaks, which of those you can fix, and the one you cannot — which decides whether you should be using a lock at all.

setnx leases fencing redlock

The lock

acquire and release, done correctly
token = uuid4().hex

# ACQUIRE — atomic test-and-set with an expiry, in one command.
acquired = r.set(f"lock:{resource}", token, nx=True, ex=30)
if not acquired:
    return None                     # someone else holds it

try:
    do_the_work()
finally:
    # RELEASE — only if the token still matches. THIS MUST BE ATOMIC.
    r.eval("""
      if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
      end
      return 0
    """, 1, f"lock:{resource}", token)

# THE TWO NON-NEGOTIABLE DETAILS, and both are commonly wrong:
#
#   1. THE TTL. Without EX, a holder that crashes leaves the lock held
#      forever and the resource is permanently blocked. There is no
#      automatic cleanup, no lock table to inspect, nothing.
#
#   2. THE TOKEN, checked atomically on release. A plain DEL releases
#      whatever lock is there — including one a DIFFERENT holder acquired
#      after yours expired. That turns "my lock expired" into "I deleted
#      someone else's lock", which is strictly worse.
#
# GET-then-DEL is not sufficient. Between the GET and the DEL, your lock can
# expire and be reacquired, and you delete the new holder's lock. Lua makes
# the compare-and-delete indivisible (chapter 8).
A Redis lock is a lease, not a lock

The TTL is not a safety net bolted on — it is the whole design. Because a holder can die without releasing, the lock must expire on its own, which means you hold it for a fixed period rather than until you are finished. If the work takes longer than the lease, you no longer hold the lock and you have no way of knowing that from inside the work. Every failure mode below flows from this one property, and the mitigations are all about narrowing the window rather than closing it. Any design that assumes "I have the lock, therefore I am the only one running" is assuming something Redis cannot guarantee.

Extending a lease

a watchdog, and what it does not solve
# A background thread renews the lease while the work runs, so a long job
# does not lose the lock partway through.

def renew(key, token, ttl=30):
    return r.eval("""
      if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('PEXPIRE', KEYS[1], ARGV[2])
      end
      return 0
    """, 1, key, token, ttl * 1000)

# Renew at roughly a third of the TTL, so two consecutive failures still
# leave time to notice. If renew() ever returns 0, YOU NO LONGER HOLD THE
# LOCK — abort the work immediately rather than continuing.

# EXPIRE gained conditional flags in 7.0, which make this safer:
r.expire(key, 30, gt=True)      # only extend, never accidentally shorten

# WHAT A WATCHDOG FIXES: work that legitimately takes longer than one lease.
#
# WHAT IT DOES NOT FIX: the process being stopped. If a GC pause, a container
# freeze or a hypervisor stall suspends your process for longer than the TTL,
# the watchdog is suspended too — the lock expires, someone else takes it,
# and when your process resumes it carries on believing it is the holder.
#
# The renew check catches this ONLY at the next renewal, which is after the
# damage. There is no way for code inside the critical section to know that
# time has passed and its lease has gone.

Fencing tokens

the only real fix, and it needs the resource's cooperation
# Hand out a monotonically increasing number with every lock acquisition.
token = r.incr("lock:fence:invoice")        # 41, 42, 43, ...
r.set("lock:invoice", token, nx=True, ex=30)

# Then the PROTECTED RESOURCE rejects anything with a stale token:
#
#   writer A gets fence 41, stalls
#   lease expires, writer B gets fence 42, writes with 42
#   A wakes, tries to write with 41  ->  REJECTED, 41 < 42
#
# The resource enforces the mutual exclusion. The lock only decides who
# tries.

# In the database:
UPDATE invoices SET data = %s, fence = %s
WHERE id = %s AND fence < %s

# In Redis itself:
EVAL "
  local cur = tonumber(redis.call('HGET', KEYS[1], 'fence') or 0)
  if tonumber(ARGV[1]) <= cur then return 0 end
  redis.call('HSET', KEYS[1], 'fence', ARGV[1], 'data', ARGV[2])
  return 1
" 1 invoice:8842 42 "..."

# THIS IS THE ONLY MECHANISM THAT MAKES A DISTRIBUTED LOCK SAFE against a
# stalled holder. And note what it requires: the resource must support a
# conditional write on a version number. If the protected thing is an
# external API, a file, or a payment provider, you cannot fence it — and
# then no lock, in Redis or anywhere else, gives you the guarantee you want.

# The realistic conclusion: if you can fence, do — and then ask whether you
# needed the lock at all, since the fence is doing the correctness work.
# If you cannot fence, choose a design where a duplicate execution is
# harmless (idempotency) rather than one that relies on it never happening.
Redlock does not solve the stall problem

Redlock is the algorithm for acquiring a lock across several independent Redis instances, requiring a majority. It addresses a real failure — the single-instance failover case, where an async replica is promoted without the lock — and it is genuinely more robust for that. It does not address a stalled holder, because no amount of consensus about who holds a lease tells you whether the holder is still running. Martin Kleppmann's critique and Salvatore Sanfilippo's reply are both worth reading in full; the practical summary is that Redlock's guarantees depend on bounded clock drift and bounded process pauses, and neither is bounded in a real system. If correctness depends on the lock, you need fencing tokens — and if you have fencing tokens, Redlock's extra complexity buys you little.

What locks are actually good for

Reasonable uses

  • Reducing duplicate work — one cache recompute instead of a thousand (chapter 7)
  • Leader election for a scheduled job, where a rare double run is tolerable
  • Rate-limiting an expensive operation to one at a time
  • Politeness — not hammering a third-party API from every instance
  • Anywhere a duplicate is wasteful but not wrong

Do not

  • Guard financial correctness — use a database transaction
  • Prevent double-charging — use an idempotency key at the provider
  • Enforce uniqueness — use a unique constraint where the data lives
  • Serialise long-running work — the lease will not hold
  • Anywhere a duplicate execution is unrecoverable
The question to ask first

What happens if two processes run this simultaneously? If the answer is "some wasted work", a Redis lock is an excellent, cheap optimisation and none of the failure modes above matter much — they make the optimisation occasionally less effective, not incorrect. If the answer is "we charge the customer twice" or "the ledger is wrong", a lock is the wrong tool regardless of implementation, because you are trying to buy a guarantee it cannot sell. Put the constraint where the data lives: a unique index, a conditional update, a transaction, an idempotency key at the payment provider. The lock reduces contention; the constraint provides correctness. Conflating the two is the actual mistake, and it survives any amount of care with the lock itself.

Other coordination primitives

often a better fit than a lock
# LEADER ELECTION — one instance does the scheduled work.
SET leader:reports "instance-7" NX EX 15
# renew every 5s while leading; if the renew fails, stop being leader
# immediately. Design the job so a brief double-run is harmless, because
# during a failover there WILL be one.

# ONCE-ONLY EXECUTION — cheaper and safer than a lock.
SET job:daily-rollup:2026-03-14 "done" NX EX 172800
# 1 -> you run it. 0 -> already done or in progress.
# There is no lock to release, no expiry mid-work, and no double execution
# unless the key expires. For idempotent daily jobs this is strictly better.

# A SEMAPHORE — at most N concurrent workers, via a sorted set scored by
# acquisition time so stale holders age out.
ZREMRANGEBYSCORE sem:export -inf $(($(date +%s) - 60))    # expire holders
ZADD  sem:export $(date +%s) "worker-3"
ZRANK sem:export "worker-3"
# if rank >= N, ZREM yourself and back off. Chapter 5's structure doing
# coordination work.

# A BARRIER / COUNTDOWN — wait for N things to finish.
DECR pending:batch-7          # each worker decrements on completion
# 0 -> you are the last one; trigger whatever comes next. Atomic, one
# command, no coordination needed at all.

# A QUEUE INSTEAD OF A LOCK — frequently the right answer. If the reason for
# the lock is "only one worker should process this entity at a time", route
# all work for that entity to one consumer by hashing the entity id to a
# stream or a list. No lock, no lease, no stall problem — serialisation by
# construction (chapters 4 and 6).
Use a library, and read what it does

Redlock implementations exist for every language — Redisson for Java, redlock-py, node-redlock — and they handle the token, the Lua release, the retry backoff and the watchdog properly, which is more than most hand-rolled attempts. Use one rather than writing your own. And read its documentation on the guarantees it claims, because some are careful and honest about the stall problem while others describe themselves as providing mutual exclusion without qualification. A library cannot give you a guarantee the underlying algorithm does not have; what it can do is stop you making the three fixable mistakes.

The short version

  1. SET key token NX EX ttl to acquire. Both the token and the TTL are mandatory.
  2. Release with a Lua compare-and-delete. A plain DEL can delete someone else's lock.
  3. A Redis lock is a lease. You hold it for a period, not until you are finished.
  4. A watchdog fixes long work; it does not fix a stalled process, because the watchdog stalls too.
  5. Fencing tokens are the only real fix, and they require the protected resource to reject stale writes.
  6. Redlock addresses failover, not stalls. It cannot make a lease safe against an unbounded pause.
  7. Ask first: what happens if two run at once? "Wasted work" means use a lock; "wrong data" means use a constraint.
  8. Often you want something else — once-only execution, a semaphore, or routing work for an entity to one consumer.
