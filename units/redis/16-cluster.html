Cluster

Sixteen thousand three hundred and eighty-four hash slots, distributed across nodes. The mechanism is simple and the consequences are not — cluster mode quietly invalidates several patterns from earlier chapters, and it is easier to design for than to migrate to.

slots hash tags resharding constraints

Do you need it

Cluster solves two problems, and neither is "we have a lot of keys"

The reasons to shard are memory beyond one machine and write throughput beyond one thread. Read throughput is not one of them — replicas do that (chapter 15). Key count is not one of them; ten million keys on one instance is unremarkable. Before clustering, exhaust the cheaper answers: a bigger machine, a smaller working set (chapter 12), TTLs on everything, better encodings, replicas for reads, and separate instances by purpose — which gets you multiple cores and is dramatically simpler than a cluster. Most deployments that adopt cluster mode did not need to, and pay its constraints indefinitely.

Hash slots

a fixed number of buckets, assigned to nodes
# Every key belongs to exactly one of 16,384 slots:
#     slot = CRC16(key) mod 16384
#
# Each node owns a contiguous-ish range of slots. Three nodes typically:
#     node A: 0-5460     node B: 5461-10922     node C: 10923-16383

CLUSTER KEYSLOT user:41            # (integer) 8106
CLUSTER COUNTKEYSINSLOT 8106
CLUSTER GETKEYSINSLOT 8106 10
CLUSTER SHARDS                     # 7.0+. Slot ranges per shard
CLUSTER NODES
CLUSTER INFO

# Why 16,384 rather than a hash of the node count? Because slots are the
# unit of MIGRATION. Adding a node moves slots, not keys — the mapping from
# key to slot never changes, so a resharding operation reassigns ranges and
# transfers their contents rather than rehashing the whole keyspace.

# CLIENTS DO THE ROUTING. A cluster-aware client fetches the slot map,
# caches it, and sends each command to the right node. When it is wrong:
GET user:41
# (error) MOVED 8106 10.0.1.11:6379      -> the slot lives there. Update the
#                                           cached map and retry
# (error) ASK 8106 10.0.1.12:6379        -> the slot is MIGRATING right now.
#                                           Retry there with ASKING, but do
#                                           NOT update the map
#
# Every decent client library handles both. A non-cluster client pointed at
# a cluster works for keys that happen to land on the node it connected to
# and fails for the rest, which is a confusing way to discover the problem.

redis-cli -c                       # follow redirections in the CLI

Every multi-key operation must stay within one slot

This is the constraint that reaches back into every earlier chapter. MGET, MSET, SINTER, ZINTERSTORE, SMOVE, RENAME, BLMOVE, Lua scripts, MULTI blocks — all of them require every key involved to hash to the same slot, and same node is not sufficient. Two keys can share a node today and be separated by a resharding tomorrow, so Redis enforces the stricter rule and returns CROSSSLOT Keys in request don't hash to the same slot. The workaround is hash tags, and using them well is the whole of cluster schema design.

Hash tags

forcing keys into the same slot
# If a key contains {...}, only the text inside the FIRST pair of braces is
# hashed. Everything else is ignored for routing.

CLUSTER KEYSLOT "{user:41}:profile"     # 8106
CLUSTER KEYSLOT "{user:41}:sessions"    # 8106  — same slot
CLUSTER KEYSLOT "{user:41}:cart"        # 8106

# Now multi-key operations across a user's keys are legal:
MGET {user:41}:profile {user:41}:cart
EVAL "..." 2 {user:41}:cart {user:41}:total

# THE DESIGN RULE: tag by the entity that operations are scoped to. If your
# transactions and scripts always touch one user's data, tag by user. If they
# touch one order's data, tag by order.
#
# THE HAZARD: a tag that is too coarse destroys distribution.
#     {tenant:acme}:...        one tenant's entire dataset on one node
#     {global}:...             everything on one node. You have unsharded
#
# In a multi-tenant system with one enormous tenant, tagging by tenant means
# one node holds most of your data and takes most of your traffic, while the
# others idle. The balancer cannot help — you configured it.

# CHECK THE DISTRIBUTION before committing to a tagging scheme:
redis-cli --cluster check 10.0.1.10:6379
redis-cli --cluster info  10.0.1.10:6379
# and per node:
CLUSTER COUNTKEYSINSLOT 

# Note also that hash tags interact with expiry and eviction: all of a
# tenant's keys expiring at once now hit one node's expiry cycle rather than
# being spread (chapter 2).

Setting one up

and resharding it
# redis.conf on every node
cluster-enabled yes
cluster-config-file nodes.conf        # maintained by Redis, not by you
cluster-node-timeout 15000
cluster-require-full-coverage yes     # see below

# Create it — six nodes, three primaries each with one replica:
redis-cli --cluster create \
  10.0.1.10:6379 10.0.1.11:6379 10.0.1.12:6379 \
  10.0.1.13:6379 10.0.1.14:6379 10.0.1.15:6379 \
  --cluster-replicas 1

# ADD A NODE, then give it slots:
redis-cli --cluster add-node 10.0.1.16:6379 10.0.1.10:6379
redis-cli --cluster reshard 10.0.1.10:6379 \
  --cluster-from all --cluster-to  --cluster-slots 4096

# REMOVE A NODE — move its slots away first, then delete it:
redis-cli --cluster reshard ... --cluster-from  --cluster-to 
redis-cli --cluster del-node 10.0.1.10:6379 

# REBALANCE after changes:
redis-cli --cluster rebalance 10.0.1.10:6379 --cluster-use-empty-masters

# RESHARDING IS ONLINE. Slots move key by key while the cluster serves
# traffic, and clients follow ASK redirections for the slot in flight. It is
# genuinely non-disruptive — and it is slow on large datasets and it adds
# load, so schedule it rather than doing it during a peak.

# cluster-require-full-coverage:
#   yes  the WHOLE cluster refuses writes if any slot is unavailable.
#        Consistent, and one node's failure is a total outage
#   no   the rest keeps serving; requests for missing slots fail
#        Available, and your application must handle partial failure
# The default is yes. For a cache, no is usually the better trade.

Failover

built in — no Sentinel
# Cluster nodes gossip over a separate bus port (the client port + 10000).
# When a majority of PRIMARIES agree a node is unreachable for longer than
# cluster-node-timeout, one of its replicas is promoted.
#
# So cluster mode replaces Sentinel entirely. Running both is a mistake —
# they are alternative answers to the same question (chapter 15).

CLUSTER FAILOVER              # on a replica: planned, coordinated handover
CLUSTER FAILOVER FORCE        # without the primary's agreement
CLUSTER FAILOVER TAKEOVER     # without majority agreement. Dangerous

cluster-replica-validity-factor 10    # a replica too far behind will not
                                      # be promoted. 0 disables the check
cluster-migration-barrier 1           # keep at least this many replicas on a
                                      # primary before migrating one elsewhere
cluster-allow-replica-migration yes   # spare replicas move to primaries with
                                      # none — genuinely useful

# THE SAME DATA LOSS AS CHAPTER 15. Replication is still asynchronous, so a
# promoted replica is missing whatever its primary acknowledged and had not
# yet sent. Cluster mode does not change this — it automates the failover,
# not the durability.

# YOU NEED A MAJORITY OF PRIMARIES. Three primaries tolerate one failure.
# Two primaries tolerate none, because one remaining node is not a majority
# — so a two-shard cluster is strictly worse than a single instance with a
# replica. Three primaries is the practical minimum.

# Note that primaries vote, not replicas. A cluster with three primaries and
# nine replicas still tolerates exactly one primary failure at a time.

A hot key defeats the whole thing

Sharding distributes the keyspace, not the traffic. A single key that every request touches — a global counter, a shared rate limit, a leaderboard everyone reads — lives in one slot on one node and is served by one thread, exactly as it was before you clustered. Adding nodes gives that key no more capacity at all. The fixes are the same as chapter 10's: split the key into N shards and aggregate, or handle it locally in each application instance with a share of the budget. Identify your hot keys with redis-cli --hotkeys before designing the cluster, because a hot key is one of the few problems clustering genuinely cannot solve.

The alternative

client-side sharding, which is often enough
Run several independent Redis instances and choose one in your application:

    instance = instances[hash(key) % len(instances)]

WHAT YOU GET that cluster gives you:
  * memory and throughput across machines
  * full use of your cores
  * complete freedom from CROSSSLOT — because you accept that cross-instance
    operations simply do not exist, rather than fighting the constraint

WHAT YOU GIVE UP:
  * automatic failover — you need Sentinel per instance, or manual promotion
  * online resharding — adding an instance rehashes everything, so you need
    consistent hashing, or a migration, or a maintenance window
  * a single logical endpoint

WHEN IT IS BETTER:
  * the data partitions cleanly by tenant, region or service, so you were
    going to separate it anyway
  * different partitions want different configuration — a cache with
    allkeys-lru next to a queue with noeviction, which one cluster cannot do
  * the instance count is stable, so resharding is rare

Separating instances BY PURPOSE — cache, sessions, queues, rate limits — is
the version of this almost every deployment should do regardless (chapter 12).
It uses more cores, isolates failures, and lets each instance have the
eviction and persistence settings its workload actually wants. Do that first
and see whether you still need to shard.
Design for cluster before you need it, or accept you may never migrate

Retrofitting cluster mode means auditing every multi-key operation, every Lua script, every MULTI, every SCAN loop and every use of SELECT — then adding hash tags to key names, which changes where every key lives and therefore requires a data migration. That is a project, and it is the reason plenty of teams stay on one large instance long past the point where sharding would help. If there is any chance you will need it, adopt the constraints now: prefix instead of SELECT, tag keys by their natural entity, declare Lua keys properly, and keep multi-key operations within one entity. All of it is free on a single instance and removes the migration entirely.

The short version

  1. 16,384 slots, CRC16(key) mod 16384, assigned to nodes. Slots migrate, not keys.
  2. Shard for memory or write throughput. Not for read throughput, and not for key count.
  3. Every multi-key operation needs one slot — same node is not sufficient.
  4. Hash tags force keys together, and a tag that is too coarse unshards your cluster.
  5. Cluster replaces Sentinel. Failover is built in, with the same asynchronous data loss.
  6. Three primaries minimum. Two tolerate no failures, which is worse than one instance with a replica.
  7. A hot key does not shard — one slot, one node, one thread. Find them before designing.
  8. Separate instances by purpose first. It uses your cores, isolates failures, and is far simpler.
