Performance

Redis is fast enough that your own code is usually the bottleneck. When it is not, the cause is almost always one of three things: too many round trips, one command doing too much work, or something outside Redis entirely.

Round trips, not command execution

A GET takes tens of microseconds inside Redis and half a millisecond on a local network — so the network is 95% of the cost and the database is 5%. That single ratio determines almost all Redis performance work: a hundred sequential commands is a hundred round trips, and turning them into one exchange is a 50–100× improvement that no amount of server tuning can approach. Before looking at anything in INFO, count the round trips per request. Most Redis "slowness" is an application issuing commands in a loop.

Pipelining

the highest-value change available
# Sequential — 100 round trips
for uid in user_ids:
    r.hgetall(f"user:{uid}")

# Pipelined — one round trip
pipe = r.pipeline(transaction=False)      # transaction=False → no MULTI
for uid in user_ids:
    pipe.hgetall(f"user:{uid}")
results = pipe.execute()

# Send all the commands, then read all the replies. Nothing is atomic and
# other clients' commands interleave freely — that is fine, and it is why
# pipelining is simpler than MULTI (chapter 8).
#
# Note transaction=False in redis-py: the default wraps the pipeline in
# MULTI/EXEC, which adds atomicity you probably did not want and does not
# work across slots in cluster mode.

# BATCH SIZE. The replies buffer in memory on both sides, so an unbounded
# pipeline of a million commands allocates a million replies at once. A few
# hundred to a few thousand per batch is the useful range:
for chunk in chunks(user_ids, 500):
    pipe = r.pipeline(transaction=False)
    for uid in chunk: pipe.hgetall(f"user:{uid}")
    yield from pipe.execute()

# THE MULTI-KEY COMMANDS do the same job with no client-side machinery, and
# are better where they apply:
MGET  k1 k2 k3                      # instead of three GETs
MSET  k1 v1 k2 v2
HMGET user:41 name tier             # instead of three HGETs
SADD  s a b c                       # variadic — nearly every write command is
DEL   k1 k2 k3
# In cluster mode these require all keys in one slot; a pipeline does not
# (chapter 16).

Big keys and slow commands

one thread, so one command's work is everyone's wait
# THE COMMANDS TO TREAT AS BANNED IN PRODUCTION:
KEYS pattern            # O(N) over the whole keyspace       -> SCAN
FLUSHALL / FLUSHDB      # synchronous by default             -> add ASYNC
DEBUG SLEEP             # blocks deliberately
MONITOR                 # streams every command to a client — measurably
                        # slows the server, and people leave it running

# THE COMMANDS THAT ARE FINE UNTIL THE DATA GROWS:
SMEMBERS  big:set       # O(N) -> SSCAN, or SISMEMBER for the actual question
HGETALL   big:hash      # O(N) -> HMGET the fields you need
LRANGE    big:list 0 -1 # O(N) -> bound the range
ZRANGE    big:zset 0 -1 # O(N) -> ZRANGEBYSCORE with LIMIT
DEL       big:key       # O(N) freeing -> UNLINK

# These are the dangerous ones precisely because they are correct. Written
# against a collection of fifty members they work for years, and there is no
# moment at which anything breaks — the collection grows, the command gets
# slower, and one day it is 400 ms and the server stalls.

# FIND THEM:
redis-cli --bigkeys          # largest key of each type, via SCAN
redis-cli --memkeys          # memory by key
MEMORY USAGE somekey
OBJECT ENCODING somekey

SLOWLOG GET 10               # commands over slowlog-log-slower-than µs
SLOWLOG RESET
CONFIG SET slowlog-log-slower-than 5000     # 5 ms. The default is 10 ms
CONFIG SET slowlog-max-len 512

# The slowlog records EXECUTION time only — not the time spent waiting behind
# another command, and not network time. So a slowlog full of fast commands
# with terrible client-side latency means something else is blocking the
# thread: a fork (chapter 13), a slow Lua script, or a big key you have not
# found yet.
Latency is measured at the client, and the cause is at the server

The most confusing Redis incident is uniform latency across every operation with nothing in the slowlog. That pattern means the thread was occupied — every command waited its turn and each one executed quickly, so none of them appears slow. The usual culprits are the fork during a background save, a Lua script looping over a collection, an UNLINK of a genuinely enormous key, or active defragmentation. LATENCY DOCTOR and redis-cli --latency measure what the slowlog cannot: total delay including queueing, which is the number your application actually experiences.

Measuring

the tools, in the order to use them
# 1. WHAT IS THE BASELINE? Intrinsic latency of the machine itself, with no
#    Redis involved — scheduler, virtualisation, noisy neighbours.
redis-cli --intrinsic-latency 100
#    "Max latency so far: 3 milliseconds"
#    If the machine alone shows milliseconds, Redis cannot do better. This
#    is common on oversubscribed cloud instances and it is the first thing
#    to rule out.

# 2. WHAT IS THE ROUND TRIP? Continuous ping from where your app runs.
redis-cli --latency
redis-cli --latency-history -i 5
redis-cli --latency-dist               # a spectrum of samples

# 3. WHAT SPIKED, AND WHY?
LATENCY RESET
LATENCY LATEST                         # event, last, max
LATENCY HISTORY fork
LATENCY DOCTOR                         # plain-English analysis
CONFIG SET latency-monitor-threshold 100    # ms. Off by default — TURN IT ON
#    Tracked events include: fork, aof-fsync-always, expire-cycle,
#    eviction-cycle, active-defrag-cycle, command

# 4. WHAT IS THE SERVER DOING?
INFO commandstats      # calls, usec, usec_per_call, PER COMMAND
INFO latencystats      # p50/p99/p99.9 per command (7.0+)
INFO stats             # instantaneous_ops_per_sec, total_net_input_bytes
CONFIG RESETSTAT

# INFO commandstats is the most underused diagnostic here. Sort by total
# usec rather than usec_per_call — the same argument as every other unit.
# A 40 µs command called ten million times matters more than a 4 ms one
# called twice.

# 5. WHAT IS THE CEILING?
redis-benchmark -t get,set,lpush -n 100000 -q
redis-benchmark -t get -n 100000 -P 16 -q       # with pipelining
#    The -P difference shows you exactly what pipelining is worth on your
#    network. It is usually startling.

Connections and clients

frequently the actual problem
# Connecting is expensive relative to a command: TCP handshake, TLS if
# enabled, AUTH, SELECT. A client that connects per operation spends more
# time on setup than on work.
#
# Use ONE connection pool per process, sized deliberately:
#   pool size ≈ concurrent operations in flight, not request rate
#   too small  -> requests queue in the client, invisible in Redis metrics
#   too large  -> file descriptors and server memory for nothing

INFO clients
#   connected_clients
#   blocked_clients          BLPOP/BRPOP/XREAD waiters. Normal, and worth
#                            knowing about — they are not stuck
#   client_recent_max_input_buffer / output_buffer

CLIENT LIST                  # age, idle, cmd, omem per connection
CLIENT KILL ID 42
CLIENT NO-EVICT on           # protect an admin connection from eviction

# TCP_NODELAY should be on — Nagle's algorithm batches small packets and
# adds up to 40 ms of latency to a request/response protocol. Every decent
# client library sets it; if you are seeing suspiciously round tens of
# milliseconds, check.

# TLS costs real CPU on the single thread. Measure it before assuming it is
# free, and terminate it at a proxy if the numbers justify the complexity.

# THE CLIENT-SIDE FAILURE THAT LOOKS LIKE A SERVER PROBLEM: an exhausted
# connection pool. Every operation queues waiting for a connection, latency
# climbs uniformly, and Redis itself shows low CPU, few connections and
# nothing in the slowlog. Check the pool before the server.

# This does NOT make command execution parallel. Commands still run one at a
# time on the main thread; only the reading and writing of socket data is
# spread across threads.
#
# So it helps when you are bottlenecked on syscalls and network I/O — many

Check whether it is Redis at all

Three things present as "Redis is slow" and are not. An exhausted client connection pool, where every operation queues in your application and Redis shows low CPU and an empty slowlog. Serialisation cost, where the JSON encode and decode around each value takes longer than the round trip — worth profiling before blaming the network. And the machine itself: redis-cli --intrinsic-latency on an oversubscribed cloud instance routinely reports milliseconds of scheduler jitter, which is a ceiling no configuration can improve. Rule out all three before tuning anything, because each of them produces metrics that look exactly like a database problem.

The short version

  1. The network is 95% of the cost. Count round trips per request before looking at anything else.
  2. Pipelining is the highest-value change available — 10–100× on batch work, with no atomicity semantics to reason about.
  3. Use the multi-key commands — MGET, HMGET, variadic writes — where they apply.
  4. Ban KEYS, MONITOR and synchronous FLUSHALL, and treat SMEMBERS/HGETALL as bombs on a timer.
  5. The slowlog records execution, not queueing. Uniform latency with an empty slowlog means the thread was occupied.
  6. Turn on latency-monitor-threshold — it is off by default and it is what explains spikes.
  7. io-threads does not parallelise commands. More processes is the way to use more cores.
  8. Check the pool, the serialisation and the machine before tuning Redis. All three look like a database problem.
