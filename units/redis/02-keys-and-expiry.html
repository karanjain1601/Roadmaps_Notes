Chapter 02 · The model

Keys and expiry

One flat namespace, no schema, no tables. The key name is the only structure you get, which makes naming a design decision rather than a style preference — and expiry is the feature that keeps the whole thing from filling up.

naming ttl scan keyspace

The namespace is the schema

a convention, and why it matters
# Redis has no tables and no collections. Every key lives in one flat
# namespace, and the only organising tool is the name itself.

user:41                       # a hash — the user object
user:41:sessions              # a set  — their active sessions
session:a3f9                  # a hash — one session
leaderboard:global:2026-03    # a sorted set
ratelimit:api:u41:1741946400  # a string counter, with a TTL
lock:invoice:8842             # a string lock
cache:product:2231:v3         # a cached render

# The colon is convention, not syntax — Redis attaches no meaning to it. But
# every tool, every dashboard and every human reading your keyspace expects
# it, so use it.
#
# A workable pattern:
#     ::[:]
#
# Rules worth adopting on day one:
#   * PREFIX BY SERVICE if several share an instance:  orders:user:41
#   * INCLUDE A VERSION where the value's shape may change:  cache:product:41:v3
#     Bumping the version invalidates everything at once, with no deletion
#   * KEEP THEM SHORT but not cryptic. Every key costs memory, and at ten
#     million keys the difference between a 20-byte and a 60-byte name is
#     hundreds of megabytes — but "u:41:s" that nobody can read is a false
#     economy at any scale below that
#   * NEVER put unbounded user input in a key without validating it. A key
#     is up to 512 MB and nothing stops you creating millions of them
You cannot query, so the name is your only index

There is no WHERE. The only ways to find a key are to know its exact name, or to scan the entire keyspace — and scanning is what chapter 1's demo showed taking the server down. That inverts the usual design process: you must be able to construct the key from what the caller already knows. If answering "which sessions belong to user 41" requires finding keys by pattern, the design is wrong; you need a set at user:41:sessions holding the ids, maintained as sessions are created and destroyed. Every access path you need is a structure you maintain deliberately.

Never KEYS

SCAN, and the guarantees it gives you
# KEYS blocks the server for the whole scan of every key (chapter 1).
KEYS user:*                   # do not

# SCAN walks the keyspace in bounded chunks, returning a cursor.
SCAN 0 MATCH user:* COUNT 100
1) "17408"                    # the cursor for the next call
2) 1) "user:41"
   2) "user:9"

SCAN 17408 MATCH user:* COUNT 100
# ... repeat until the returned cursor is "0"

# WHAT SCAN GUARANTEES:
#   * every key present for the WHOLE iteration is returned at least once
#   * no key absent for the whole iteration is returned
# WHAT IT DOES NOT:
#   * keys added or removed during the iteration MAY or may not appear
#   * a key may be returned MORE THAN ONCE — deduplicate if it matters
#   * COUNT is a HINT about work per call, not a result count. A call can
#     return zero keys and a non-zero cursor. That is normal, not the end

# MATCH filters AFTER retrieval, so a pattern matching nothing still walks
# the whole keyspace — just in bounded chunks that do not block.

# The type-specific variants, which matter for the same reason (chapter 1):
HSCAN user:41 0
SSCAN online:now 0
ZSCAN leaderboard 0

# In cluster mode SCAN is per node, so iterate every master (chapter 16).
redis-cli --scan --pattern 'user:*'      # handles the cursor loop for you

Expiry

How a key actually disappears Expiry is not a timer. Understanding the two mechanisms explains several surprising behaviours.
—removed
—memory freed
—visible to clients
the commands
SET session:a3f9 "{...}" EX 3600      # set with a TTL, in one atomic command
SET session:a3f9 "{...}" PX 500       # milliseconds
SET session:a3f9 "{...}" EXAT 1741950000   # absolute unix time
SET session:a3f9 "{...}" KEEPTTL      # replace the value, keep the existing TTL

EXPIRE  session:a3f9 3600             # set or replace a TTL on an existing key
EXPIRE  session:a3f9 3600 NX          # only if it has no TTL     (7.0+)
EXPIRE  session:a3f9 3600 GT          # only if greater than the current (7.0+)
TTL     session:a3f9                  # seconds remaining
                                      #   -1 = exists, no TTL
                                      #   -2 = does not exist
PERSIST session:a3f9                  # remove the TTL

# THE TRAP: most write commands CLEAR the TTL.
SET  session:a3f9 "new"               # TTL is GONE. The key is now permanent
SET  session:a3f9 "new" KEEPTTL       # TTL preserved
GETSET / SETRANGE / GETDEL            # also clear it
INCR / APPEND / HSET / LPUSH / ZADD   # do NOT clear it — they modify a value
                                      # rather than replacing the key

# That distinction — replacing a key clears the TTL, modifying it does not —
# is the source of a classic leak: a session store that refreshes with plain
# SET, so every active session becomes permanent and memory grows forever.

# TTLs are per KEY, never per element. You cannot expire one field of a hash
# or one member of a set. Hash field TTLs arrived in Redis 7.4 (HEXPIRE) and
# are the exception; for everything else, if elements need individual
# lifetimes they need to be separate keys, or a sorted set scored by
# timestamp that you trim (chapter 5).
Every key that can grow needs a TTL or a bound

Redis has no equivalent of dropping old rows. A key you create and never delete stays until the process restarts or eviction takes it — and if eviction takes it, that was not your decision (chapter 12). The failure is slow and quiet: memory climbs over months, nobody notices because there is plenty of headroom, and then the instance hits maxmemory during a traffic peak and starts evicting session keys. For every key pattern you introduce, answer two questions: what deletes it, and what bounds its size. A TTL answers the first. A capped list, a trimmed sorted set or a bounded stream answers the second.

Key management

the rest of the keyspace API
EXISTS user:41                    # 0 or 1. Variadic: counts how many exist
TYPE   user:41                    # string | list | set | zset | hash | stream
DEL    user:41 user:9             # synchronous — blocks while freeing
UNLINK user:41                    # frees on a background thread. Prefer this
                                  # for anything large (chapter 1)
RENAME old new                    # overwrites new if it exists
RENAMENX old new                  # only if new does not exist
COPY   src dst [DB n] [REPLACE]   # 6.2+
RANDOMKEY                         # a random key. Useful for sampling
DBSIZE                            # how many keys
OBJECT ENCODING key               # the internal representation (chapter 12)
OBJECT FREQ key                   # access frequency, under LFU eviction
MEMORY USAGE key                  # bytes, including overhead

# DEL versus UNLINK is worth internalising. DEL frees the object inline, so
# deleting a set with ten million members blocks the thread for the whole
# free. UNLINK removes the key from the namespace immediately and frees the
# memory in the background. There is essentially no reason to prefer DEL.

# NUMBERED DATABASES — SELECT 0..15 by default. Mostly a historical feature:
SELECT 3
# They share one process, one thread and one memory limit, so they provide
# namespacing and nothing else. Cluster mode supports only database 0, and
# most client libraries handle them poorly. Use key prefixes instead.

# EXPIRY-RELATED SERVER SETTINGS worth knowing (chapter 12):
CONFIG GET maxmemory-policy       # what happens when memory fills
CONFIG GET hz                     # background task frequency, incl. expiry
                                  # sampling. Default 10 times per second

Keyspace notifications

events when keys change — with a large caveat
CONFIG SET notify-keyspace-events "Ex"     # E = keyevent, x = expired
SUBSCRIBE __keyevent@0__:expired
# 1) "message"
# 2) "__keyevent@0__:expired"
# 3) "session:a3f9"

# The flags select what you hear:
#   K  keyspace events, __keyspace@__: -> event name
#   E  keyevent events, __keyevent@__: -> key name
#   g  generic (DEL, EXPIRE, RENAME)    $ strings   l lists
#   s  sets      h hashes    z sorted sets    x expired    e evicted
#   A  everything except K and E

# THE CAVEAT, and it is a big one: notifications are delivered over PUB/SUB,
# which is fire-and-forget (chapter 11). If your subscriber is disconnected,
# restarting, or simply slow, the message is gone. There is no queue, no
# acknowledgement and no replay.
#
# So this is fine for a cache invalidation hint or a metric, and it is NOT a
# reliable trigger. "Clean up the user's data when their session key expires"
# will silently skip cleanups every time a consumer restarts.
#
# Two further points:
#   * the `expired` event fires when the key is actually REMOVED, which may
#     be well after it logically expired (see the demo above)
#   * notifications add work to every matching command, so enabling A on a
#     busy instance has a measurable cost

# For anything that must not be missed, use a stream (chapter 6) or a sorted
# set of pending work scored by due time (chapter 5), and poll it.

Inspecting a keyspace you inherited

what is in here, and what is eating the memory
# A sampled summary of the whole keyspace — memory by pattern, biggest keys,
# type distribution. Safe to run against production:
redis-cli --memkeys
redis-cli --bigkeys              # largest key of each type, by SCAN
redis-cli --hotkeys              # most accessed. Needs maxmemory-policy
                                 # allkeys-lfu

# How many keys have no TTL — usually the most informative single number:
redis-cli --scan | head -100000 | while read k; do
  redis-cli TTL "$k"; done | grep -c '^-1$'

# INFO keyspace gives the summary the server already tracks:
INFO keyspace
#   db0:keys=8412903,expires=6120441,avg_ttl=1840233
#
# The gap between `keys` and `expires` is the count of keys with no TTL. If
# that number is large and growing on an instance used as a cache, you have
# found a leak — and it is usually the SET-clears-the-TTL trap above.

# Sample the key patterns actually in use:
redis-cli --scan --pattern '*' | head -50000 |
  sed 's/[0-9][0-9]*/N/g' | sort | uniq -c | sort -rn | head -20
#   412031 cache:product:N:vN
#    88201 session:N
#      412 lock:invoice:N
#        3 tmp:migration:N          <- residue from something in 2024
Write the key patterns down

There is no schema to read, no information_schema, and no way to ask Redis what patterns exist without sampling. So the only durable record of your keyspace design is a document you maintain: pattern, type, what writes it, what reads it, what expires it, and expected size. It takes an hour and it is the difference between an instance somebody can reason about and one where nobody dares delete anything. The sampling command above tells you what is actually there; the document tells you what is supposed to be, and the gap between them is usually interesting.

The short version

  1. One flat namespace, no schema. The key name is the only structure you get, so naming is design.
  2. You must be able to construct the key from what the caller knows. Every other access path is a structure you maintain.
  3. Never KEYS. SCAN is incremental, may return duplicates, and COUNT is a hint.
  4. Expiry is lazy plus sampled, so memory is freed after the key logically expires, not at the moment.
  5. SET clears the TTL. SET … KEEPTTL, or use a command that modifies rather than replaces.
  6. Every key pattern needs an answer to "what deletes it" and "what bounds it".
  7. UNLINK, not DEL — freeing happens in the background.
  8. Keyspace notifications go over pub/sub, so they are lossy. Never use them as a reliable trigger.
