Memory and eviction

Memory is the hard limit (chapter 1), and Redis does not degrade gracefully when it runs out — it either discards data according to a policy you may not have chosen, or refuses writes. Both of those are configuration decisions, and the default is neither.

maxmemory policies fragmentation encodings

Set maxmemory

the first thing to configure
CONFIG GET maxmemory
# "0"        <- unlimited. The default.

# Unlimited means the real limit is the machine's RAM, and the failure is the
# OOM killer terminating the process — an abrupt total outage with whatever
# data loss your persistence configuration allows (chapter 13).

CONFIG SET maxmemory 8gb
CONFIG SET maxmemory-policy allkeys-lru
CONFIG REWRITE                      # persist to the config file

# HOW MUCH? Not all of the machine's RAM. Leave headroom for:
#   * the COW fork during a background save, which can approach the dataset
#     size under heavy writes (chapter 13)
#   * client output buffers, especially pub/sub (chapter 11)
#   * replication backlog and replica buffers
#   * allocator fragmentation
#
# With persistence enabled, 50-60% of RAM is a common starting point. For a
# pure cache with saving turned off, 75-80% is reasonable.
#
# maxmemory counts the DATASET, not the process. used_memory_rss — what the
# operating system sees — is always larger.

INFO memory
#   used_memory              what Redis thinks it is using
#   used_memory_rss          what the OS has allocated to the process
#   used_memory_peak         the high-water mark
#   used_memory_lua          scripting
#   maxmemory / maxmemory_policy
#   mem_fragmentation_ratio  rss / used_memory

Eviction policies

Which key gets discarded The same keyspace, eight policies. Two of them will refuse writes instead of evicting.

A volatile policy with no TTLs is a write outage

The volatile-* policies only consider keys that have a TTL. If memory fills and nothing qualifies, Redis cannot evict anything and starts returning OOM command not allowed when used memory > 'maxmemory' — a total write outage on a server that is running perfectly and has, from its own point of view, nothing it is allowed to discard. This is the interaction from chapter 2, and it catches people because volatile-lru sounds like the cautious choice. It is cautious only if everything discardable genuinely has a TTL. For a pure cache use allkeys-*; for mixed data use volatile-* and audit that your cache keys all have expiries.

LRU and LFU are approximate, on purpose
# Exact LRU would require a linked list of every key updated on every access
# — memory and time Redis will not spend. Instead it SAMPLES.

CONFIG GET maxmemory-samples
# "5"    <- pick 5 random candidates, evict the best one

CONFIG SET maxmemory-samples 10     # closer to true LRU, more CPU per eviction
# 5 is a good default; 10 is close to exact. Above that the returns are tiny.

# LFU (4.0+) tracks access FREQUENCY with a probabilistic counter that decays
# over time, so a key hammered once last week does not outrank one accessed
# steadily today.
CONFIG SET maxmemory-policy allkeys-lfu
CONFIG SET lfu-log-factor 10        # how quickly the counter saturates
CONFIG SET lfu-decay-time 1         # minutes before the counter halves

OBJECT FREQ mykey                   # the LFU counter, under an LFU policy
OBJECT IDLETIME mykey               # seconds since access, under LRU

# LFU IS USUALLY BETTER FOR A CACHE. LRU is fooled by a scan: iterate a
# million cold keys and every one becomes "recently used", evicting your
# genuinely hot set. LFU is not — one access does not make a key frequent.
#
# The classic version of this is a nightly batch job reading everything,
# which under LRU quietly destroys the cache hit rate every night at 2am and
# it recovers by morning, so nobody connects the two.

# Watch what is happening:
INFO stats
#   evicted_keys      cumulative. The RATE is what matters
#   expired_keys      TTL expiry, which is different and normal
#   keyspace_hits / keyspace_misses

Where the memory goes

it is rarely the values
MEMORY USAGE user:41          # bytes for this key, including overhead
MEMORY DOCTOR                 # a plain-English diagnosis
MEMORY STATS                  # the full breakdown

# PER-KEY OVERHEAD is 50-80 bytes before any data: the key string, the
# dictionary entry, the robj header, and an entry in the expires table if it
# has a TTL. Ten million keys holding one integer each is roughly 700 MB to
# store 40 MB of data.
#
# This is why chapter 4's advice matters: many small related values belong in
# one hash, not in many keys.

# THE ENCODING THRESHOLDS decide the rest:
CONFIG GET hash-max-listpack-entries    # 128
CONFIG GET hash-max-listpack-value      # 64
CONFIG GET list-max-listpack-size       # 128
CONFIG GET set-max-intset-entries       # 512
CONFIG GET set-max-listpack-entries     # 128
CONFIG GET zset-max-listpack-entries    # 128

OBJECT ENCODING mykey         # listpack | hashtable | intset | skiplist | ...

# Below the threshold a collection is a flat contiguous array with almost no
# per-element overhead. Above it, a real data structure with pointers and
# metadata per element — commonly 5-10x more memory.
#
# THE CONVERSION IS ONE-WAY. A hash that briefly exceeded 128 fields and then
# shrank back stays a hashtable until the key is rewritten. A transient spike
# therefore costs memory permanently.

# THE SHARDED HASH PATTERN, which follows directly:
#   instead of  user:meta:41  ... ten million string keys
#   use         user:meta:{41 % 100000}  ->  field "41"
# Ten million values in a hundred thousand listpack hashes, at a fraction of
# the memory. Instagram published this technique years ago and it still
# routinely cuts memory by 5x or more for small-value workloads.

Finding the problem

what is actually in there
# Safe against production — all of these use SCAN internally.
redis-cli --bigkeys      # the largest key of each type
redis-cli --memkeys      # memory by key, sampled
redis-cli --hotkeys      # most accessed. Requires an LFU policy

# Memory by key PATTERN, which is the number that usually explains things:
redis-cli --scan | head -200000 |
  sed 's/[0-9][0-9]*/N/g' | sort | uniq -c | sort -rn | head -20

# How many keys have no TTL — the leak indicator from chapter 2:
INFO keyspace
#   db0:keys=8412903,expires=6120441,avg_ttl=1840233
# The gap between keys and expires, growing over time on a cache, is the
# SET-clears-the-TTL bug.

# THE FOUR THINGS THAT ARE USUALLY EATING THE MEMORY, in order:
#   1. keys with no TTL that should have one
#   2. a collection that grew past its listpack threshold
#   3. per-key overhead on millions of tiny values
#   4. one enormous key nobody knew about — a list or set that grew for years

# And the ones that are not your data at all:
CLIENT LIST                # om= output buffer, per client
INFO clients               # client_recent_max_output_buffer
INFO replication           # the replication backlog
#   A few hundred slow pub/sub subscribers can hold gigabytes in output
#   buffers, charged to your instance (chapter 11).

Fragmentation

when the OS holds more than Redis is using
INFO memory
#   mem_fragmentation_ratio: 1.6

# rss / used_memory.
#   ~1.0-1.5   normal
#   > 1.5      real fragmentation — memory the allocator holds but cannot reuse
#   < 1.0      part of the process has been SWAPPED TO DISK. This is an
#              emergency: swapping an in-memory database destroys its latency
#              entirely. Set vm.swappiness=0 and size the instance properly

# Fragmentation arises when many differently-sized objects are allocated and
# freed — a workload with high churn and variable value sizes is the classic
# case. jemalloc holds the freed space in size-class pools it cannot hand
# back to the OS.

# ACTIVE DEFRAGMENTATION moves objects to compact the heap, incrementally,
# during idle cycles:
CONFIG SET activedefrag yes
CONFIG SET active-defrag-ignore-bytes 100mb
CONFIG SET active-defrag-threshold-lower 10      # start at 10% fragmentation
CONFIG SET active-defrag-threshold-upper 100
CONFIG SET active-defrag-cycle-min 5             # % of CPU, minimum
CONFIG SET active-defrag-cycle-max 25            # maximum

# It costs CPU on the single thread, so it is throttled and enabled only when
# fragmentation is genuinely high. Requires the bundled jemalloc.

# THE OTHER FIX: restart the instance, or fail over to a replica and rebuild
# the old primary. A freshly loaded dataset is compact. On a replicated setup
# this is a rolling operation with no downtime, and it is often simpler than
# tuning defrag parameters.

# TRANSPARENT HUGE PAGES should be OFF. They make the copy-on-write fork
# during a save copy 2 MB pages instead of 4 KB ones, which inflates memory
# use and latency substantially (chapter 13):
echo never > /sys/kernel/mm/transparent_hugepage/enabled

Reducing memory

  • Give every key a TTL that can have one. The single largest win, and usually available.
  • Shard many small values into hashes under the listpack threshold — often a 5–10× reduction.
  • Shorten key names, but only at very high key counts. user:41:sessions to u:41:s is a real saving at ten million keys and a false economy at ten thousand.
  • Compress large values in the client. gzip on a JSON document is frequently 5–10×, at CPU cost on both sides.
  • Use a bitmap or HyperLogLog where the question allows it (chapters 3 and 10).
  • Cap every collection — LTRIM, ZREMRANGEBYRANK, MAXLEN.
  • Store integers as integers. Redis encodes numeric strings as longs with no allocation.
  • Separate instances by purpose — cache and durable data on one instance share one maxmemory and one policy.
One instance, one purpose

Putting the cache, the session store, the job queues and the rate limiters on one instance is the natural thing to do and it couples four workloads with different requirements. They share one maxmemory, so a cache surge evicts sessions and logs everybody out. They share one eviction policy, so you cannot say "evict cache freely, never evict sessions". They share one persistence configuration, so either you fsync data you were happy to lose or you risk losing data you were not. And they share one thread, so a slow command in one workload adds latency to all of them. Separate instances cost a little memory overhead and remove an entire category of incident, and on the same machine they also use more of your cores (chapter 1).

Alert on evicted_keys, not on used_memory

Memory sitting at 95% of maxmemory is exactly what a correctly-sized cache looks like — it fills up and stays full, and an alert on that fires forever and gets muted. The signal that matters is the eviction rate: keys being discarded means the working set no longer fits and your hit rate is silently degrading. There is no error and nothing in the logs; requests simply start missing more often. Track evicted_keys as a rate alongside the hit ratio, and treat a sustained rise as the capacity signal it is.

The short version

  1. maxmemory defaults to unlimited, and the failure is the OOM killer. Set it on day one.
  2. Leave headroom for the save fork, client buffers and fragmentation — 50–60% of RAM with persistence on.
  3. A volatile-* policy with no TTLs refuses writes. allkeys-* for a pure cache.
  4. LFU beats LRU for caches, because a scan does not destroy the hot set.
  5. Per-key overhead is 50–80 bytes. Many small values belong in sharded hashes.
  6. Listpack encodings are 5–10× cheaper, and the conversion above the threshold is one-way.
  7. A fragmentation ratio below 1.0 means swapping — an emergency for an in-memory database.
  8. Alert on evicted_keys, not used_memory. Full is normal; evicting is the signal.
