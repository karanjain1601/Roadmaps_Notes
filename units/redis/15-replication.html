Replication and Sentinel

One command sets up a replica. The consequences take a chapter, because Redis replication is asynchronous by design — which means a failover loses acknowledged writes, and no configuration available to you closes that gap entirely.

replicas async sentinel wait

Setting it up

one command, and what happens next
# On the replica:
REPLICAOF primary.internal 6379
# or in the config file:
replicaof primary.internal 6379
masterauth 
replica-read-only yes           # the default. Keep it

REPLICAOF NO ONE                # promote to a standalone primary
INFO replication

# THE HANDSHAKE:
#   1. the replica connects and asks to synchronise
#   2. PARTIAL RESYNC if the replica has seen this primary before and the
#      primary's backlog still covers the gap — it just sends the missing
#      commands
#   3. FULL RESYNC otherwise — the primary forks, produces an RDB, ships it,
#      and streams everything since
#
# A full resync is expensive: a fork on the primary with all of chapter 13's
# copy-on-write cost, plus transferring the whole dataset. The backlog is
# what avoids it after a brief disconnection:
repl-backlog-size 64mb          # default 1mb — RAISE THIS
repl-backlog-ttl 3600

# 1 MB of backlog on an instance writing 10 MB/s covers 0.1 seconds. Any
# network blip longer than that forces a full resync, which forks the
# primary — so an undersized backlog turns a momentary hiccup into a
# latency incident. Size it for your longest plausible disconnection.

# DISKLESS REPLICATION avoids writing the RDB to disk at all:
repl-diskless-sync yes          # default in 7.0+
repl-diskless-sync-delay 5      # wait, to batch several replicas into one fork
repl-diskless-load on-empty-db  # on the replica side

# After a full resync the replica applies the ongoing command stream. It is
# byte-compatible rather than command-compatible for nondeterministic
# operations — SPOP and EXPIRE are replicated by effect, so replicas never
# diverge from the primary through their own randomness.

Asynchronous, and what that costs

The write you lose Redis acknowledges before replicating. Step through what happens when the primary dies.

The acknowledgement happens before replication

Redis replies to a write as soon as it has applied it locally — it does not wait for any replica. That is why writes are fast, and it means a primary that dies immediately after acknowledging has lost data that the client was told was saved. There is no synchronous_commit, no w: "majority", no configuration that makes an acknowledgement mean "a majority holds this". WAIT gets you closer and is not a guarantee (below). This is the single largest architectural difference from the PostgreSQL and MongoDB units, and it decides what Redis should be trusted with.

WAIT, and its limits
SET order:8842 "..."
WAIT 1 100              # block until 1 replica has it, or 100 ms elapse
# (integer) 1           # how many replicas acknowledged — CHECK THIS

# WAIT does not make the write synchronous retroactively. The write already
# happened; WAIT just blocks you until replicas confirm receipt.
#
# WHAT IT DOES NOT GIVE YOU:
#   * a rollback if the timeout expires. The write is applied on the primary
#     either way — you simply learn that it did not replicate in time
#   * a guarantee that the acknowledging replica will win an election
#   * protection against a primary that dies between the SET and the WAIT
#
# So WAIT converts "I do not know whether this replicated" into "I know it
# did, or I know it might not have". That is genuinely useful for deciding
# whether to proceed, and it is not the same as a majority commit.

# WAITAOF (7.0+) is the stronger relative — it waits for the write to be
# FSYNCED, locally and on replicas:
WAITAOF 1 1 100         # numlocal, numreplicas, timeout
# (integer) 1) 1  2) 1
# Requires appendonly yes. This is the closest Redis comes to a durable
# acknowledgement, and it costs a disk sync per call.

# THE MINIMUM-REPLICAS SETTING — refuse writes when replication is unhealthy:
min-replicas-to-write 1
min-replicas-max-lag 10
# The primary stops accepting writes if fewer than 1 replica has been in
# contact within 10 seconds. It converts "silently accumulating unreplicated
# writes" into a visible error, which is usually the better failure — and it
# means a network problem becomes a write outage, so decide deliberately.

Reading from replicas

useful, with the usual caveats
# Replicas are read-only by default and serve reads at full speed. Sending
# analytics, reporting or heavy scans there keeps them off the primary —
# which matters more in Redis than elsewhere, because one slow command on
# the primary blocks every client (chapter 1).

INFO replication
#   on the primary:  slave0:ip=...,port=...,state=online,offset=...,lag=0
#   on the replica:  master_link_status:up
#                    master_repl_offset       — compare with the primary's
#                    master_last_io_seconds_ago

# WHAT YOU GIVE UP:
#   * READ-YOUR-WRITES. Write to the primary, read from a replica, and the
#     value may not be there yet. Usually milliseconds; occasionally much
#     more. This is the commonest bug introduced by enabling replica reads
#   * expired keys. A replica does not expire keys on its own — it waits for
#     the primary's DEL. Modern Redis returns nil for logically-expired keys
#     on a replica, so reads are CORRECT, but DBSIZE and memory will differ
#     from the primary and that is expected
#
# Also note every write still happens on every replica, so replicas add read
# capacity and nothing else. A write-heavy workload gains nothing.

replica-serve-stale-data yes    # default: serve possibly-stale data when the
                                # link to the primary is down
                                # `no` returns an error instead — safer for
                                # correctness, worse for availability

# A REPLICA IS NOT A BACKUP. It applies your FLUSHALL within milliseconds.
# Keep RDB copies elsewhere (chapter 13).

Sentinel

automatic failover for a non-clustered setup
# sentinel.conf
port 26379
sentinel monitor mymaster 10.0.1.10 6379 2
#                                          ^ QUORUM: how many sentinels must
#                                            agree the primary is down
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster 

# RUN AN ODD NUMBER, AT LEAST THREE, on separate hosts from the Redis nodes.
# Sentinels must form a majority among THEMSELVES to authorise a failover —
# the quorum setting only controls how many must agree the primary is down.
# Both conditions apply, and confusing them is the commonest misconfiguration:
#
#   3 sentinels, quorum 2  ->  2 must agree it is down, and 2 must be
#                              reachable to elect a leader. Correct.
#   2 sentinels, quorum 1  ->  a single sentinel can declare failure, and
#                              cannot form a majority. It will never fail over.

# WHAT SENTINEL DOES:
#   monitors primaries and replicas
#   notifies via a script or pub/sub
#   promotes a replica when the primary is judged down
#   reconfigures the other replicas to follow the new primary
#   acts as a DISCOVERY SERVICE — clients ask it who the primary is

# CLIENTS MUST BE SENTINEL-AWARE. They connect to the sentinels, ask for the
# current primary, and subscribe to +switch-master to learn about failovers.
# A client configured with a hard-coded primary address will not follow one:
#
#   redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
#   SENTINEL replicas mymaster
#   SENTINEL sentinels mymaster
#   SENTINEL failover mymaster        # force one, for testing

# The alternative to a Sentinel-aware client is a proxy or a virtual IP that
# something else moves. Both work; both are one more thing to operate.
Every failover loses writes, by design

Because replication is asynchronous, the promoted replica is missing whatever the primary acknowledged but had not yet sent. Sentinel picks the replica with the highest replication offset, which minimises the loss — it cannot eliminate it. Worse, when the old primary returns it is reconfigured as a replica of the new one and discards its own extra writes to resynchronise, so those acknowledged writes are gone with no record anywhere. This is unavoidable in an asynchronous system and it is why the question "what happens if we lose a few seconds of this data" has to be answered before choosing Redis for it, not after a failover.

Split brain

the partition case
1. A network partition isolates the primary from the sentinels and replicas.
2. Clients on the primary's side keep writing to it. It is healthy and has
   no idea it has been cut off.
3. The sentinels on the majority side promote a replica.
4. Two primaries now accept writes.
5. The partition heals. The old primary is demoted and RESYNCHRONISES from
   the new one, discarding everything written during the partition.

The writes accepted by the old primary during step 2 are gone. The clients
that made them were told they succeeded.

WHAT LIMITS THE DAMAGE:

  min-replicas-to-write 1
  min-replicas-max-lag 10

  The isolated primary sees no replicas in contact and stops accepting
  writes after 10 seconds. That bounds the divergence to roughly that
  window instead of the whole partition.

  This is the closest Redis comes to the self-demotion property that keeps
  MongoDB and Patroni-managed PostgreSQL safe (see those units' chapters on
  failover). It is weaker: a time-based heuristic rather than consensus, and
  the primary continues serving for the lag window before it stops.

WHAT DOES NOT HELP:
  * more sentinels — they are on the other side of the partition
  * a shorter down-after-milliseconds — it makes unnecessary failovers more
    likely without addressing this
  * WAIT — the isolated primary has no replicas to wait for, so WAIT returns
    0, which your code has to actually check

Operating it

what to watch
INFO replication
#   role, connected_slaves
#   master_repl_offset       compare between primary and replicas — the
#                            difference IS your data-loss window
#   slave0:...,lag=0         seconds since the replica last responded

INFO stats
#   sync_full                full resyncs. Each one forks the primary
#   sync_partial_ok / sync_partial_err
#   A rising sync_full with a low sync_partial_ok means the backlog is too
#   small for your disconnection pattern — raise repl-backlog-size.

# FOUR THINGS TO ALERT ON:
#   1. connected_slaves dropping below expected
#   2. replication offset lag, in bytes, sustained
#   3. sync_full increasing — full resyncs fork the primary
#   4. master_link_status:down on any replica

# PLANNED FAILOVER, for maintenance:
SENTINEL failover mymaster        # sentinel coordinates it cleanly
# Do this regularly. A failover path that is never exercised is a failover
# path that does not work, and the thing that usually breaks is not Redis —
# it is a client library that was never configured for Sentinel.

# CHAINED REPLICATION, when many replicas would overload the primary:
replicaof replica-1 6379          # a replica of a replica
replica-announce-ip / replica-announce-port    # behind NAT
# Each level adds lag. Two levels is reasonable; three is a smell.

# Sentinel does NOT shard. It provides availability for a single primary,
# and one primary's capacity is one thread and one machine's memory. When
# you outgrow that, the answer is cluster mode (chapter 16) — and note that
# cluster has its own failover built in, so the two are alternatives rather
# than layers.
Test the failover, and test the client

Trigger SENTINEL failover monthly against production with traffic running, and measure end to end: how long until writes succeed again, and how many failed in between. The component that usually breaks is not Redis or Sentinel — it is a client library that was configured with a direct address instead of the sentinel set, or one whose reconnection logic was never exercised. That failure is invisible until the day it matters, and it converts a ten-second failover into a total outage until someone redeploys. A failover path you have not exercised is not a failover path.

The short version

  1. Replication is asynchronous. The write is acknowledged before any replica has it.
  2. Raise repl-backlog-size — 1 MB is seconds of coverage, and a full resync forks the primary.
  3. WAIT is not a majority commit. It tells you whether replication happened; it cannot roll anything back.
  4. WAITAOF (7.0+) is the closest Redis comes to a durable acknowledgement, at the cost of a disk sync.
  5. Sentinel needs an odd number, at least three, on separate hosts — and a majority among themselves, not just the quorum.
  6. Every failover loses writes, and the old primary discards its extras when it rejoins.
  7. min-replicas-to-write bounds split-brain divergence and turns a partition into a write outage. Decide deliberately.
  8. Test the failover monthly. The thing that breaks is usually the client library.
