Transactions, Lua and functions

Single commands are atomic for free (chapter 1). Making several operations indivisible takes one of three mechanisms, and the one named "transaction" is the least useful of them — because it cannot make a decision based on what it read.

multi watch lua functions

MULTI is not a transaction

what it actually does
MULTI
  INCR   counter        # QUEUED  — not executed yet
  LPUSH  log "event"    # QUEUED
  EXPIRE log 3600       # QUEUED
EXEC                    # all three now run, with nothing interleaved

# WHAT YOU GET:
#   * the queued commands run consecutively — no other client's command runs
#     between them
#   * all of them run
#
# WHAT YOU DO NOT GET, and the names mislead here:
#   * ROLLBACK. If the third command fails at runtime, the first two have
#     already applied and stay applied. There is no undo
#   * READS. Every command returns QUEUED, so you cannot use the result of
#     one command to decide the next. That is the fundamental limitation
#
# Errors split into two kinds:
MULTI
  NOTACOMMAND foo       # syntax error — detected at queue time
EXEC                    # EXECABORT: the whole thing is discarded

MULTI
  LPUSH mykey "x"       # queued fine
  INCR  mykey           # queued fine — mykey is a list, but Redis does not
EXEC                    # know that until it runs
# 1) (integer) 1
# 2) (error) WRONGTYPE ...      <- the LPUSH already happened

DISCARD                 # abandon a queued transaction

# Because there are no reads, MULTI is only useful for "do these unrelated
# writes together" — the LPUSH-then-LTRIM pair from chapter 4, or several
# counters that must move as one. Anything conditional needs WATCH or Lua.
"Atomic" here means uninterrupted, not all-or-nothing

Redis documentation calls MULTI/EXEC a transaction and it does not have the property people expect from that word. It guarantees isolation — no other client's commands interleave — and it does not guarantee atomicity in the failure sense: a runtime error partway through leaves the earlier commands applied. The reasoning given by the project is that such errors are programming bugs rather than runtime conditions, and that rollback support would slow down the common path for no benefit. Whether or not you find that convincing, the practical consequence is the same: do not use MULTI where partial application would be a correctness problem.

WATCH

optimistic concurrency, with a retry loop you write
# WATCH makes EXEC fail if a watched key changed since the WATCH.
WATCH stock:TSH-001
current = GET stock:TSH-001              # a real read — outside MULTI
if current < 3: UNWATCH; return "insufficient"

MULTI
  DECRBY stock:TSH-001 3
EXEC
# (nil)  -> someone modified stock:TSH-001 in between. RETRY the whole thing.
# [ok]   -> it went through

# This is check-and-set. The read happens before MULTI, the decision is made
# in your application, and WATCH guarantees the value did not change
# underneath you — if it did, EXEC returns nil and you start again.

# The costs, and they are the reason for the next section:
#   * a retry loop in every caller, which people get wrong or omit
#   * under contention the retries themselves collide, and throughput
#     degrades quadratically on a hot key
#   * three round trips minimum: WATCH, GET, MULTI+EXEC
#   * WATCH is cleared by EXEC, UNWATCH, or the connection closing — forget
#     UNWATCH on the early-return path and the next transaction on that
#     connection carries a stale watch
#   * with connection pooling, all of the above must happen on ONE
#     connection, which some client libraries make awkward

# WATCH is correct and it is rarely the best available option. The same
# logic as a Lua script is one round trip, needs no retry loop, and cannot
# be interleaved at all.

Lua

the usual answer
-- Runs on the server, atomically, in one round trip. Nothing interleaves.
EVAL "
  local stock = tonumber(redis.call('GET', KEYS[1]) or 0)
  local want  = tonumber(ARGV[1])
  if stock < want then return -1 end
  redis.call('DECRBY', KEYS[1], want)
  return stock - want
" 1 stock:TSH-001 3

-- KEYS and ARGV are separate on purpose. Every key the script touches must
-- be declared in KEYS, because that is how Redis Cluster knows which node
-- the script belongs on (chapter 16). Building a key name from ARGV works on
-- a single instance and breaks the moment you shard.

-- Load once, call by hash — the script body then crosses the network once
-- rather than on every call:
SCRIPT LOAD "return redis.call('GET', KEYS[1])"
-- "a5260dd66ce02462c5b5231c727b3f7772c0bcc5"
EVALSHA a5260dd66ce02462c5b5231c727b3f7772c0bcc5 1 mykey
-- NOSCRIPT means the cache was cleared — fall back to EVAL. Every good
-- client library does this automatically.

SCRIPT EXISTS 
SCRIPT FLUSH                -- clears the cache. Invalidates every EVALSHA
SCRIPT KILL                 -- stop a running script, if it has not written

-- WHAT A SCRIPT CAN DO THAT NOTHING ELSE CAN:
--   read a value and branch on it, atomically
--   loop over a collection server-side
--   return a computed result rather than raw values
--   perform many operations in one round trip
A script blocks the entire server for its whole duration

That is why it is atomic — nothing else runs (chapter 1). A ten-millisecond script is ten milliseconds of total unavailability for every client, and unlike an accidentally slow command this one you deployed on purpose. Worse, SCRIPT KILL only works on a script that has not yet written; once it has, the only way out is SHUTDOWN NOSAVE, which loses everything not persisted. Keep scripts short and bounded. A loop over a collection whose size you do not control is the reliable way to produce latency spikes that no single slow command explains, and busy-reply-threshold (default 5 seconds) is how long the server will accept being stuck before it even starts refusing other clients.

writing scripts that behave
-- DETERMINISM. Scripts are replicated by effect since Redis 5, so the
-- old ban on randomness and time is relaxed — but a script whose result
-- depends on the server clock still behaves differently on a replay during
-- recovery. Pass time in from the caller when it matters:
EVAL "... ARGV[1] is the timestamp ..." 1 key 1741946400

-- redis.call vs redis.pcall:
redis.call('GET', k)     -- an error aborts the whole script
redis.pcall('GET', k)    -- returns the error as a value; you handle it

-- TYPE CONVERSION is the commonest source of bugs. Lua numbers are doubles
-- and Redis integers are 64-bit, so returning a number TRUNCATES it:
return 3.7               -- the client receives 3
return tostring(3.7)     -- "3.7"
return redis.error_reply("insufficient stock")
return redis.status_reply("OK")
-- Lua false becomes nil; Lua nil terminates an array reply early, so never
-- put a nil in the middle of a table you are returning.

-- A useful complete example — rate limit with a token bucket (chapter 10):
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens') or ARGV[1])
local last   = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3])
local now, rate, cap = tonumber(ARGV[3]), tonumber(ARGV[2]), tonumber(ARGV[1])

tokens = math.min(cap, tokens + (now - last) * rate)
if tokens < 1 then return 0 end

redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate))
return 1

-- Read, compute, branch, write, expire — five operations, one round trip,
-- atomic, and impossible to express in MULTI at all.

Functions

Redis 7's answer to "where does the script live"
#!lua name=inventory

local function reserve(keys, args)
  local stock = tonumber(redis.call('GET', keys[1]) or 0)
  local want  = tonumber(args[1])
  if stock < want then return redis.error_reply('insufficient') end
  redis.call('DECRBY', keys[1], want)
  return stock - want
end

redis.register_function('reserve', reserve)

-- Load the library, then call functions by NAME:
FUNCTION LOAD "#!lua name=inventory ..."
FCALL reserve 1 stock:TSH-001 3
FCALL_RO get_stock 1 stock:TSH-001        -- read-only, can run on a replica

FUNCTION LIST
FUNCTION STATS
FUNCTION DUMP / RESTORE                   -- move libraries between servers

-- WHY THIS EXISTS. Scripts are cached per server, evaporate on restart, are
-- addressed by an opaque SHA, and are effectively invisible in the codebase
-- because they live as strings inside application code. Functions are
-- registered by name, PERSIST across restarts, replicate to replicas, and
-- are managed as a first-class server object.
--
-- The practical difference: with EVALSHA the source of truth for your
-- server-side logic is scattered through your application; with functions it
-- is a library you deploy deliberately, which makes it reviewable and
-- versionable like anything else.

-- The trade is deployment. A function must be loaded before it can be
-- called, so you need a step that installs libraries — and on a fresh
-- replica or a restored instance, something must reload them. EVALSHA with
-- an automatic EVAL fallback is self-healing, which is why plenty of
-- production systems still use scripts.

Pipelining is not atomicity, and it is what people usually want

These two get conflated constantly. Pipelining sends many commands without waiting for each reply — it is purely a round-trip optimisation, other clients' commands can interleave freely, and it turns a hundred sequential operations into one network exchange. MULTI additionally guarantees nothing interleaves. If your reason for reaching for MULTI is "this loop of a thousand commands is slow", the answer is a pipeline, and it is simpler, has no error semantics to reason about, and works identically in cluster mode. Reach for MULTI only when the interleaving would actually be wrong. Chapter 14 covers pipelining properly.

The short version

  1. MULTI guarantees no interleaving, not all-or-nothing. A runtime error leaves earlier commands applied.
  2. Every command in MULTI returns QUEUED, so you cannot branch on what you read. That is its real limitation.
  3. WATCH is check-and-set with a retry loop you write — correct, and rarely the best option.
  4. Lua is usually the answer: read, decide, write, in one round trip, atomically.
  5. Declare every key in KEYS, or the script breaks the moment you use cluster mode.
  6. A script blocks the whole server. Keep it short and bounded — a runaway one may need SHUTDOWN NOSAVE.
  7. Lua numbers are doubles, so returning a float truncates. Return strings when precision matters.
  8. Pipelining is not atomicity, and it is what most people reaching for MULTI actually want.
