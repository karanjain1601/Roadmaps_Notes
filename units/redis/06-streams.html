Streams

An append-only log with consumer groups, per-message acknowledgement and recovery of abandoned work. It is the answer to every "but what if the worker crashes" left hanging by lists and pub/sub, and it is the most complex type Redis has.

xadd consumer groups pending trimming

The log

append, and read by range
XADD events * type "click" user "u41" page "/pricing"
# "1741946400123-0"
#   ^ the ID: milliseconds-sequence. The * asks Redis to generate it.

# IDs are monotonically increasing and unique. The sequence number
# disambiguates entries added in the same millisecond, so you can add
# millions per second without collision.

XLEN   events
XRANGE events - +                       # everything. - and + are the extremes
XRANGE events 1741946400000 + COUNT 10  # from a timestamp
XREVRANGE events + - COUNT 1            # the most recent entry
XDEL   events 1741946400123-0           # rarely needed

# Each entry is a set of field-value pairs — a small flat record, not a blob.
XRANGE events - + COUNT 1
# 1) 1) "1741946400123-0"
#    2) 1) "type"  2) "click"  3) "user"  4) "u41"

# READING AS A CONSUMER, without a group — like tail -f:
XREAD COUNT 10 STREAMS events 0            # from the beginning
XREAD BLOCK 0 STREAMS events $             # $ = only NEW entries, blocking
XREAD BLOCK 5000 STREAMS events 1741946400123-0   # after a specific ID

# This is already better than pub/sub: the data persists, so a consumer that
# reconnects can resume from the last ID it saw rather than losing whatever
# arrived while it was away (chapter 11). What it still lacks is any notion
# of which consumer has handled what — that is a consumer group.

Consumer groups

The lifecycle of a message Step through what happens to one entry as workers read, acknowledge, crash and recover.
—message is
—in the PEL
—if everything crashes now
creating and consuming
XGROUP CREATE events processors $ MKSTREAM
#   $        start from new messages only
#   0        start from the beginning of the stream
#   MKSTREAM create the stream if it does not exist

# Each consumer names itself. The group hands each message to exactly ONE
# consumer in the group.
XREADGROUP GROUP processors worker-3 COUNT 10 BLOCK 5000 STREAMS events >
#   >  means "messages never delivered to anyone in this group"
#   0  means "messages already delivered to ME and not yet acknowledged"
#      — i.e. my own pending entries, for recovery after a restart

# ... process ...
XACK events processors 1741946400123-0

# THE PENDING ENTRIES LIST is the whole point. When XREADGROUP hands a
# message to a consumer, the message enters that consumer's PEL and stays
# there until it is acknowledged. If the consumer dies, the message is still
# recorded as owed — nothing is lost and nothing is silently redelivered.

XPENDING events processors                       # a summary
XPENDING events processors - + 10                # the ten oldest, in detail
# 1) 1) "1741946400123-0"
#    2) "worker-3"          <- who has it
#    3) (integer) 421000    <- idle time in ms
#    4) (integer) 1         <- delivery attempts

# RECLAIMING abandoned work — the command that makes this reliable:
XAUTOCLAIM events processors worker-9 60000 0 COUNT 10
#   take up to 10 messages idle for more than 60 seconds and reassign them
#   to worker-9. Returns a cursor for iteration.

XCLAIM events processors worker-9 60000 1741946400123-0   # one specific ID

# XAUTOCLAIM (6.2+) is what a background reaper runs on a timer. It replaces
# the "detect dead workers and move their processing list back" machinery
# that chapter 4's list queue requires you to build yourself.
The pending entries list is what you are actually buying

Everything else in a stream — the ordering, the persistence, the ranges — a sorted set could approximate. What it cannot give you is a server-side record of which consumer was handed which message, when, and how many times, surviving the consumer's death. That record is why a stream can guarantee at-least-once delivery: a message is not gone when it is read, only when it is acknowledged, and anything left unacknowledged for too long can be reclaimed by a healthy worker. Chapter 4's reliable-list pattern is an attempt to rebuild exactly this, badly.

Poison messages

a message that kills every worker that touches it
# XAUTOCLAIM redelivers indefinitely. A malformed message that crashes the
# consumer is therefore reclaimed, crashes the next worker, is reclaimed
# again — a loop that takes down the whole pool one worker at a time.

# The delivery counter is how you detect it:
XPENDING events processors - + 10
#    4) (integer) 47        <- delivered 47 times. This is poison.

# So the reaper must check the count and divert, not just reclaim:
EVAL "
  local claimed = redis.call('XAUTOCLAIM', KEYS[1], ARGV[1], ARGV[2], 60000, '0', 'COUNT', 10)
  -- inspect delivery counts via XPENDING and route the repeat offenders
" ...

# In practice: read XPENDING with IDLE, and for anything above a threshold
XADD  events:dead * original_id "1741946400123-0" reason "max-deliveries"
XACK  events processors 1741946400123-0
# acknowledge it out of the live group and deal with it separately.

# A dead-letter stream is not built in. XAUTOCLAIM has a JUSTID option and
# increments the counter, and deciding what "too many" means and where those
# messages go is yours. Every production stream consumer needs this and it is
# the piece most often missing.

Trimming

a stream grows forever unless you bound it
# Cap on write, which is the only reliable way:
XADD events MAXLEN ~ 100000 * type "click" user "u41"
#   ~  APPROXIMATE — trims to at least this many, at a node boundary.
#      Much cheaper, and the right default
#   =  exact. O(N) in what it removes

XADD events MINID ~ 1741860000000 * ...      # trim by ID/time instead (6.2+)

# Explicit trimming:
XTRIM events MAXLEN ~ 100000
XTRIM events MINID  ~ 1741860000000
XTRIM events MAXLEN ~ 100000 LIMIT 1000      # bound the work per call

# THE TRAP: trimming removes entries whether or not they have been
# acknowledged. A slow consumer group can have its unread messages deleted
# out from underneath it, and the PEL then references entries that no longer
# exist.
#
# So size the cap for your worst consumer lag, not your average, and monitor
# it. XINFO GROUPS gives you the number that matters:
XINFO GROUPS events
#   name, consumers, pending, last-delivered-id, ENTRIES-READ, LAG
#
# `lag` is how many entries the group has not yet read. Alert on it.

XINFO STREAM events
XINFO STREAM events FULL              # includes the full PEL
XINFO CONSUMERS events processors     # per consumer: pending, idle time

# Consumers are not cleaned up automatically. A worker that scales down
# leaves a consumer entry behind forever:
XGROUP DELCONSUMER events processors worker-3
# — and note this DISCARDS its pending entries, so claim them first.
Trimming and acknowledgement are unrelated

This surprises people coming from Kafka, where retention interacts with consumer offsets. In Redis they are entirely independent: MAXLEN removes the oldest entries on a length rule, with no regard for whether any group has read or acknowledged them. A consumer group that falls an hour behind on a stream capped at 100,000 entries simply loses the messages that fell off the end — no error, no warning, and the lag figure quietly resets. Cap the stream generously, alert on group lag, and treat lag approaching the cap as an incident rather than a metric.

A consumer that works

the shape worth copying
GROUP, ME = "processors", f"worker-{os.getpid()}"

try:
    r.xgroup_create("events", GROUP, id="$", mkstream=True)
except ResponseError:
    pass                                    # BUSYGROUP — already exists

# 1. On startup, reclaim anything THIS consumer left pending from a previous
#    life. '0' means "my own pending entries", not new ones.
pending = r.xreadgroup(GROUP, ME, {"events": "0"}, count=100)
for _, entries in pending:
    for msg_id, fields in entries:
        handle(msg_id, fields)              # MUST be idempotent
        r.xack("events", GROUP, msg_id)

# 2. Then the normal loop.
while True:
    resp = r.xreadgroup(GROUP, ME, {"events": ">"}, count=10, block=5000)
    if not resp:
        # 3. Idle time is when a reaper reclaims abandoned work.
        claimed = r.xautoclaim("events", GROUP, ME, min_idle_time=60000,
                               start_id="0-0", count=10)
        for msg_id, fields in claimed[1]:
            if delivery_count(msg_id) > 5:
                dead_letter(msg_id, fields)
                r.xack("events", GROUP, msg_id)
            else:
                handle(msg_id, fields)
                r.xack("events", GROUP, msg_id)
        continue

    for _, entries in resp:
        for msg_id, fields in entries:
            try:
                handle(msg_id, fields)
                r.xack("events", GROUP, msg_id)   # ACK AFTER, never before
            except Exception:
                log.exception(msg_id)              # leave it pending;
                                                   # it will be reclaimed

# The five things that make this correct:
#   * reclaim your OWN pending entries on startup, or a restart strands them
#   * ACK after the work, not before — at-least-once, not at-most-once
#   * an idempotent handler, because at-least-once means duplicates
#   * a reaper for other consumers' abandoned messages
#   * a delivery-count check and a dead-letter path, or one poison message
#     takes down the pool
Redis streams are not Kafka

They look similar and the differences decide whether this is the right tool. Streams live in memory, so retention is bounded by RAM rather than disk — days of high-volume events is a different proposition from Kafka's weeks. There is no partitioning within a stream, so one stream's throughput is one thread's throughput; you shard by using several stream keys and hashing to them yourself. There is no log compaction, no exactly-once semantics, no consumer rebalancing protocol, and no broker-side schema handling. What you get instead is that it is already running. For hundreds of thousands of events a day with a handful of consumers, a stream is an afternoon's work against a Kafka cluster's ongoing operational cost — and at ten million events an hour with a week of retention, that trade reverses.

The short version

  1. An append-only log with time-ordered IDs, readable by range and replayable from any point.
  2. Consumer groups split work across a pool, with each message going to exactly one consumer.
  3. The pending entries list is what you are buying — a server-side record of who holds what, surviving their death.
  4. XAUTOCLAIM reclaims abandoned messages, replacing the reaper a list queue makes you build.
  5. ACK after the work, never before. At-least-once means handlers must be idempotent.
  6. Check the delivery count and dead-letter poison messages, or one bad entry takes down every worker in turn.
  7. Trimming ignores acknowledgement. A slow group loses messages off the end silently — alert on lag.
  8. Not Kafka. Memory-bound retention, no partitioning, no compaction — and already running.
