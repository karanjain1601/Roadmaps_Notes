Chapter 15 · Asynchrony

Promises and async/await

await makes asynchronous code read like synchronous code, which is its great virtue and its one trap: sequential-looking code becomes sequential code. Three requests that could take 100 ms take 300 ms, and nothing warns you. This chapter measures that, and the four combinators that fix it.

The four combinators

Three promises at 10, 20 and 30 ms
Change the scenario and watch any and race diverge
all — everything, or the first failure
Resolves at ~30 ms with all three values, or rejects the moment any one rejects. Fails fast, and gives you nothing about the others.
allSettled — never rejects
Always ~30 ms, always resolves, and hands back a status object per promise. The right choice when partial success is acceptable.
any — the first success
With the 10 ms promise rejecting, it skipped it and resolved at ~20 ms with the next fulfilment. Only if all reject does it reject, with an AggregateError holding every error.
race — the first to settle, rejection included
Same scenario, and it rejected at ~10 ms. That difference between "first success" and "first outcome" is the whole distinction, and picking the wrong one gives a fallback that never fires.

Sequential by accident

Three 100 ms requests, four ways
The third row collects nothing, in no time
300 ms against 100 ms, same three requests
await inside a loop starts each request only after the previous one finished. The code looks efficient and is three times slower.
forEach with an async callback returned in ~0 ms with 0 results
forEach ignores the promise its callback returns, so nothing is awaited and the function continues before any request completes. Silent, and the worst of the four.
The rule is about when promises start, not about loops
Starting all three first and then awaiting them in a loop also took 100 ms. A loop is fine; a loop that creates the promise inside the await is not.
try/catch only catches what you await
An awaited rejection is caught normally. Drop the await and the rejection escapes to the unhandled-rejection handler — measured, it fired.
javascript
const results = await Promise.all(urls.map(fetchIt));       // ✓ 100 ms
for (const u of urls) results.push(await fetchIt(u));       // ✗ 300 ms
urls.forEach(async u => results.push(await fetchIt(u)));    // ✗ 0 results

// when each one DOES depend on the last, sequential is correct — say so:
for (const step of steps) state = await step(state);

// bounded concurrency, when 500 at once would be rude
for (const batch of chunk(urls, 10)) await Promise.all(batch.map(fetchIt));

// the constructor antipattern — this wraps a promise in a promise
new Promise((res, rej) => fetchIt(u).then(res).catch(rej));  // ✗
fetchIt(u)                                                    // ✓ it already is one

// AbortController — the only way to actually cancel
const c = new AbortController();
fetch(url, { signal: c.signal });   c.abort();
Two rejections that get away

Starting a promise you never await. doWork() on its own line, without await or .catch, means any rejection becomes an unhandled rejection — which in Node terminates the process by default and in a browser logs to the console and is missed. If you deliberately want fire-and-forget, say so: void doWork().catch(reportError).

Promise.all after the first rejection. It rejects immediately, and the other promises keep running — they are not cancelled, and if one of them also rejects, that rejection has no handler. This is the common source of a mysterious unhandled rejection alongside a caught error. allSettled avoids it entirely by waiting for everything, which is one more reason to prefer it whenever you can tolerate partial failure.

Check yourself

Self-check

  1. When would Promise.any and Promise.race behave differently?
    Whenever the first promise to settle is a rejection. race takes the first outcome, whatever it is; any takes the first success and ignores rejections until there are no promises left. Measured with three promises where the 10 ms one rejects: race rejected at ~10 ms and any resolved at ~20 ms with the next fulfilment. When all three reject, any rejects with an AggregateError carrying every error, while race rejects with just the first. The practical shape: use any for redundancy — several mirrors, first one that works — and race for timeouts and cancellation, where a rejection genuinely should win. Picking race when you meant any gives a fallback that never fires, because the fast failure beats the slow success every time.
  2. Three independent requests take 300 ms. What is wrong?
    They are being awaited in a loop, so each starts only after the previous one finished. Measured: three 100 ms requests took ~300 ms in a for loop with await inside, and ~100 ms with Promise.all(urls.map(fetchIt)). The code that is three times slower is the one that reads more naturally, which is exactly why the mistake is so common — await was designed to make asynchronous code look sequential and it succeeded. The precise rule is about when the promises are started, not about loops: measured, starting all three first and then awaiting them in a loop also took ~100 ms. So a loop is fine, and a loop that calls the async function inside the await is not. When each step genuinely depends on the previous one, sequential is correct — write it deliberately rather than by accident.
  3. Why does forEach with an async callback collect nothing?
    Because forEach ignores whatever its callback returns. An async callback returns a promise, forEach discards it, and the loop finishes immediately — measured at ~0 ms with 0 of 3 results collected, while three requests carried on in the background. Nothing throws and nothing warns; the array is simply empty when the next line reads it. It is the worst of the four patterns precisely because the other failures are slow and this one is wrong. The same applies to map if you forget to await the resulting array of promises, and to any callback API that does not return the callback's value. The fix is await Promise.all(items.map(async x => …)), or a plain for…of loop if you actually want them sequential. A linter rule (no-misused-promises) catches this class.
  4. Where does the rejection go if you call an async function without awaiting it?
    To the unhandled-rejection handler. try/catch only catches a rejection you await — measured, the awaited call was caught normally, the un-awaited one was not caught by the surrounding try at all, and the process's unhandledRejection handler fired. That matters because Node terminates on an unhandled rejection by default, and browsers log it to a console nobody is reading. Two shapes to watch for. A bare call on its own line, doWork();, which is easy to write when the result is not needed — if that is deliberate, make it explicit with void doWork().catch(reportError). And Promise.all after a rejection: it rejects immediately while the other promises keep running, so a second rejection among them has no handler and surfaces as a mysterious unhandled rejection alongside an error you did catch.
  5. When should you reach for allSettled over all?
    Whenever partial success is acceptable and you want to know what happened to everything. all is all-or-nothing: it rejects on the first failure, gives you no information about the others, and leaves them running unsupervised. allSettled never rejects — measured, it resolved at ~30 ms in all three scenarios including the one where every promise failed — and hands back a status object per promise, so you can report three successes and two failures rather than just "something broke". That is the right shape for loading several independent widgets, notifying multiple channels, or any batch where one bad item should not discard the good ones. Use all when the results are genuinely a unit and a partial answer is worthless, which is less often than its popularity suggests. It also avoids the unhandled-rejection hazard in the previous answer entirely.
  6. What is wrong with new Promise((res, rej) => fetchIt(u).then(res).catch(rej))?
    It wraps a promise in a promise for no reason — fetchIt(u) already is one, so the whole expression can be replaced by fetchIt(u). Beyond the noise, the wrapper introduces real hazards: any error thrown synchronously inside the executor before rej is wired up is swallowed, and it is easy to forget the catch and produce a promise that never settles, which hangs an await forever with no error to debug. The Promise constructor has exactly one legitimate use, which is adapting something that is not promise-based — a callback API, an event, a setTimeout. Everything else should compose the promises it already has. A useful smell: if the word new Promise appears within three lines of a .then, it is almost certainly the antipattern.
  7. How do you cancel an in-flight request?
    With an AbortController — a promise itself cannot be cancelled. Create one, pass controller.signal to fetch (or to any API that accepts a signal, including addEventListener and several Node APIs), and call controller.abort(); the promise rejects with an AbortError. This matters because Promise.race with a timeout is often mistaken for cancellation and is not: the losing promise keeps running, the request keeps consuming a connection, and its result is simply discarded. Combining both is the usual pattern — race against a timer, and abort the request when the timer wins. Two conveniences worth knowing: AbortSignal.timeout(ms) creates a signal that aborts itself, and AbortSignal.any([...]) combines several, so a request can be cancelled by either a timeout or the user navigating away.
