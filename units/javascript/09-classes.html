Classes

Mostly a syntax for chapter 8's prototypes — but "just sugar" is wrong in four places that matter, and one of them is the only genuine privacy the language has. This chapter separates the sugar from the substance, then walks the construction order that catches everyone once.

Where each member lives

One class, six kinds of member
Compare a method's enumerability with an object literal's
Fields on the instance, methods on the prototype, statics on the constructor
Three different objects, and Object.hasOwn tells you which. Getters live on the prototype too — they are accessors on the shared object, not per-instance values.
Class methods are non-enumerable; object literal methods are not
Measured: { m() {} } gives enumerable: true and class C { m() {} } gives false. That is a real behavioural difference, not sugar.
So Object.keys and JSON.stringify see only fields
Object.keys(c) is ["field"] and JSON.stringify(c) is {"field":1}. Spreading a class instance copies its data and drops its behaviour — usually what you want, and worth knowing before it surprises you.
A private field is not a property at all
#secret appears nowhere: not in Object.keys, not in getOwnPropertyNames, and c["#secret"] is undefined because that is just an ordinary string key.
Four things class is not sugar for

Private fields. #x is enforced by the engine — there is no prototype trick that reproduces it, and reading one from outside is a SyntaxError rather than a runtime failure. Strictness. Class bodies are always strict, whatever the file, which chapter 7 measured. The temporal dead zone. A class declaration is not usable before its line, unlike a function declaration — chapter 3. And the new requirement. Calling a class without new throws TypeError: Class constructor C cannot be invoked without 'new', where the old constructor-function pattern would silently run with the wrong this and quietly write globals. Everything else — the prototype chain, super, method lookup — genuinely is chapter 8 with nicer syntax.

The order a subclass is built

Six steps, one of them surprising
Watch what describe() sees at step 4
The base is fully constructed before the subclass's fields exist
Order measured: before super(), base fields, base constructor, then subclass fields, then the subclass constructor body.
Which is the trap
A base constructor calling an overridden method reaches Sub.describe, and this.subField is undefined — even though the field has an initialiser and holds "sub" a moment later.
this does not exist before super()
Touching it is a ReferenceError, and so is a derived constructor that never calls super() at all. Both measured.
So: no overridable calls from a constructor
Do the work in a factory or an explicit init() the caller invokes, or pass what the base needs as a constructor argument rather than reading it from a subclass field.

  #balance = 0;                       // private — engine-enforced
  static #count = 0;                  // private statics too
  static { /* runs once, at class definition */ }   // static block

  constructor(owner) { this.owner = owner; Account.#count++; }
  get balance() { return this.#balance; }           // read-only from outside
  deposit(n) { this.#balance += n; return this; }

  static isAccount(o) { return #balance in o; }     // a BRAND CHECK — true only for
}                                                    // real instances, and it cannot
                                                     // be faked by a lookalike object

class Savings extends Account {
  constructor(owner, rate) {
    super(owner);                     // must come first — `this` does not exist yet
    this.rate = rate;
  }
  toString() { return `${super.toString()} @ ${this.rate}`; }   // super in a method
}
A private field is not the same as an underscore

_balance is a request; #balance is a rule. Measured, the private name appears in no reflection API, survives no serialisation, and reading it from outside the class is a SyntaxError at parse time rather than a runtime error — so it cannot even be reached by accident. Two consequences follow. Because it is not a property, JSON.stringify silently omits it, so a class using private state needs an explicit toJSON if it should serialise. And because access is checked by brand rather than by name, #x in o is a reliable test for "is this genuinely one of mine" — which is stronger than instanceof, since that can be defeated by Object.setPrototypeOf and fails across realms, as chapter 5 covered.

Check yourself

Self-check

  1. Where do a field, a method and a static live?
    Three different objects. A field is an own property of the instance, created fresh for each one. A method is a property of C.prototype, so it is one function shared by every instance — chapter 7 measured that sharing, and it is what a class field arrow gives up. A static is a property of the constructor function C itself. A getter declared in a class body lives on the prototype too, as an accessor, which is why it costs nothing per instance. Object.hasOwn is the way to check: Object.hasOwn(c, "field") is true, Object.hasOwn(C.prototype, "method") is true, and Object.hasOwn(C, "shared") is true. A private field is the exception to the whole scheme — it is not a property of anything and appears in no reflection API at all.
  2. Why does JSON.stringify of a class instance show only its fields?
    Because serialisation walks own enumerable properties, and only fields qualify. Methods are on the prototype rather than the instance, so they are not own; and class methods are additionally non-enumerable, which is a measured difference from object literals — { m() {} } gives enumerable: true while class C { m() {} } gives false. Private fields are not properties at all. So Object.keys(c) came back as ["field"] and JSON.stringify(c) as {"field":1}. This is usually what you want — data serialises, behaviour does not — and it has two consequences worth holding. Spreading a class instance copies its data and silently drops its methods and its prototype, so the result is a plain object. And a class relying on private state needs an explicit toJSON, or that state vanishes from the output with no warning.
  3. A base constructor calls a method the subclass overrides. What does the subclass's field hold?
    undefined — measured, even though the field has an initialiser and holds its value a moment later. The order is: the subclass constructor runs up to super(), then the base's field initialisers run, then the base constructor body runs, and only after all of that do the subclass's field initialisers run, followed by the rest of the subclass constructor. So a method called from the base constructor dispatches to the subclass override — correctly, since this is already a Sub — and finds the subclass's fields not yet initialised. It is a genuinely confusing bug because the value is right if you inspect it after construction. The fix is to never call an overridable method from a constructor: do the work in a factory function or an explicit init() the caller invokes, or pass what the base needs as a constructor argument.
  4. What happens if you touch this before super()?
    ReferenceError. In a derived class, this does not exist until super() creates it — the base constructor is what allocates the object, which is why the call must come first and why a derived constructor that never calls super() at all is also a ReferenceError. Both measured. This is different from a base class, where this is available from the first line. The practical shape is that any setup depending on constructor arguments has to go after the super() call, which is occasionally annoying when you want to validate an argument before doing expensive base work — the answer there is a static factory method that validates and then constructs. Note also that if you write no constructor at all, you get an implicit one that forwards its arguments to super, which is why most subclasses do not need one.
  5. How is #private different from a _underscore convention?
    One is a rule and the other is a request. A private field appears in no reflection API — measured absent from Object.keys and getOwnPropertyNames — and c["#secret"] is undefined, because that is just an ordinary string key with an unusual character. Most tellingly, reading c.#secret from outside the class is a SyntaxError at parse time rather than a runtime failure, so it cannot be reached even by accident or by dynamic access. An underscore prefix does none of that: the property is fully visible, serialisable and writable by anyone. Two knock-on effects. Private state does not serialise, so a class needing that must define toJSON. And access is checked by brand rather than name, which gives you #x in o as a reliable "is this genuinely one of mine" test — stronger than instanceof, which chapter 5 showed can fail across realms and be defeated by Object.setPrototypeOf.
  6. What does calling a class without new do, and why is that an improvement?
    It throws TypeError: Class constructor C cannot be invoked without 'new'. The improvement is over the constructor-function pattern it replaced, where Person("Ada") without new ran perfectly happily: in sloppy mode this became the global object, so this.name = "Ada" created a global called name and the function returned undefined, giving you a silent double failure that surfaced far away. Chapter 1's theme again — the language now refuses rather than guessing. It is one of the four things class is genuinely not sugar for, alongside private fields, always-on strict mode, and the temporal dead zone that makes a class unusable before its declaration where a function declaration would be hoisted. Everything else about classes really is chapter 8's prototype machinery with better syntax.
  7. When is a class the wrong tool?
    When there is no state to encapsulate and no need for many instances. A module exporting functions is simpler than a class with only static methods, which is a namespace wearing a costume — and the functions tree-shake where the class does not. A single configuration object does not need a class either. Classes earn their place when you have several instances each holding their own state, when you genuinely want inheritance (rarely — composition covers most cases and does not entangle construction order), or when private fields give you an invariant worth enforcing. The alternative worth remembering from chapter 6 is the closure factory: it gives real privacy with no this, no binding problems and no construction order to reason about, at the cost of a function object per method per instance. That trade is the same one chapter 7 measured for class field arrows, and for a handful of long-lived objects it is often the better deal.
