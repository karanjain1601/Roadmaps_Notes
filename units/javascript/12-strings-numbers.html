Strings, numbers and dates

A string has three defensible lengths and .length gives the one users never mean. A number is always a float, so integers stop being distinct above 2⁵³. Both facts are older than JavaScript and neither is going to change, so the work is knowing where they surface.

How long is a string?

One numeric type

Where the float shows through
toFixed is the one that costs money
0.1 + 0.2 is 0.30000000000000004
None of the three is exactly representable in binary, so the sum lands next to 0.3 rather than on it. Compare with a tolerance: Math.abs(a - b) < Number.EPSILON.
(1.005).toFixed(2) is "1.00"
Not a rounding bug — the stored value is fractionally below 1.005, so there is nothing to round up. (2.675).toFixed(2) gives "2.67" for the same reason. This is why money is never a Number.
Above 2⁵³ integers stop being distinct
2**53 === 2**53 + 1 is true. Number.MAX_SAFE_INTEGER is 9,007,199,254,740,991, and an id from a 64-bit backend can exceed it — so ids should cross an API as strings.
BigInt fixes it and refuses to mix
2n**53n === 2n**53n + 1n is false, and 1n + 1 throws TypeError rather than silently choosing a precision.
Dates, briefly, and the three things that matter

Months are zero-based. new Date(2024, 0, 31) is 31 January. Days and years are not. This has been wrong since 1995 and cannot be fixed.

Parsing is unreliable except for ISO. new Date("2024-03-15") is parsed as UTC midnight, while new Date("2024-03-15T00:00") — no Z — is local midnight. So the same date can be two different days depending on a suffix. Anything non-ISO is implementation-defined; do not parse it with Date.

A Date is a UTC instant with local-time accessors. There is no way to represent "a date without a time" or "a time in another zone" — which is why every serious application reaches for a library, and why Temporal exists. It is at Stage 3 and shipping in browsers now; when it lands everywhere, all of the above becomes a compatibility note.

Check yourself

Self-check

  1. Why is "👍".length 2 in JavaScript and 1 in Python?
    They count different units. JavaScript strings are sequences of UTF-16 code units, and any character outside the Basic Multilingual Plane needs a surrogate pair — two code units — so .length is 2. Python counts code points, so it says 1. Neither is wrong, and the practical problem is that a length limit enforced in one and validated in the other will disagree: a 20-character field accepting emoji can be rejected by a backend counting differently. The deeper issue is that both answers are wrong for a user, who counts what they see. Measured, the family emoji 👨‍👩‍👧 is 8 code units, 5 code points and 1 grapheme — three people joined by two zero-width joiners — so .length gives none of the three numbers anyone would say. For anything user-facing, Intl.Segmenter with grapheme granularity is the only measure that matches.
  2. What does fam[0] give you for an emoji, and what should you use?
    Half a surrogate pair. Measured, indexing the family emoji gives "\ud83d" — a lone high surrogate, which is not a valid character on its own and renders as a replacement box. Indexing, slice, substring and charCodeAt all work in code units and can all cut a character in half, which is how truncating a user's text to "20 characters" produces a broken glyph at the end. Spreading — [...s] — iterates by code point, so [...fam][0] gives a whole person emoji, and for…of does the same. That is enough for most text. For anything a user will count or a cursor will move through, Intl.Segmenter with grapheme granularity is the right tool: measured, it returns the entire family as one segment where every other method splits it.
  3. Two strings render identically as "café" and have lengths 4 and 5. Explain.
    One uses the single code point U+00E9 for é; the other uses e followed by U+0301, a combining acute accent. Both are valid Unicode, both render the same, and JavaScript compares by code unit sequence — so they are not equal, and their lengths differ by one. This arrives in real systems constantly, because macOS filesystems historically stored decomposed forms while most other sources produce composed ones, so the same filename or username from two places fails to match. The fix is s.normalize("NFC") on both before comparing, hashing or storing — measured, both forms normalise to length 4. Do it once, at the boundary where text enters your program, and store one form. Comparing unnormalised text from two sources is a bug waiting for a name with an accent in it.
  4. Why is (1.005).toFixed(2) equal to "1.00"?
    Because 1.005 cannot be represented exactly in binary, and the nearest double is fractionally below it — so rounding half-up has nothing to round up. It is not a bug in toFixed; the value you asked it to round was never 1.005. (2.675).toFixed(2) gives "2.67" for the same reason. This is the same fact as 0.1 + 0.2 being 0.30000000000000004, seen from a different angle: a decimal fraction with a denominator that is not a power of two has no exact binary form. The consequence is the rule that money is never a Number. Store and compute in the smallest unit as an integer — pence, cents — or use a decimal library, and format only at the very edge. A rounding error of a hundredth is invisible in testing and material in aggregate.
  5. What breaks above Number.MAX_SAFE_INTEGER?
    Integers stop being distinct. Measured, 2**53 === 2**53 + 1 is true — a double has 53 bits of mantissa, so beyond that consecutive integers share a representation and arithmetic silently rounds. Number.MAX_SAFE_INTEGER is 9,007,199,254,740,991, which sounds enormous until you meet a 64-bit database id, a Twitter-style snowflake id or a nanosecond timestamp. The failure is silent and data-corrupting: an id arrives as JSON, gets parsed into a double, loses its last digits, and now points at a different record — or at nothing. Two answers. Send large ids across an API as strings, which costs nothing and removes the problem entirely. Or use BigInt, which is exact and deliberately refuses to mix with Number: 1n + 1 throws TypeError rather than quietly picking a precision.
  6. new Date("2024-03-15") and new Date("2024-03-15T00:00") — same day?
    Not necessarily. A date-only ISO string is parsed as UTC midnight, while a date-and-time string with no offset is parsed as local midnight. So west of Greenwich the first is the previous day in local terms, and formatting them side by side gives two different dates from strings that differ by five characters. It is one of the sharper Date traps because both forms look equally canonical. Two more worth carrying: months are zero-based, so new Date(2024, 0, 31) is 31 January while days and years are not offset; and anything that is not ISO 8601 is implementation-defined, so new Date("03/15/2024") may parse, may parse differently in another engine, and may give Invalid Date. Parse ISO only, keep instants in UTC, and format at the edge — or use Temporal, which exists because none of this is fixable in place.
  7. When should you reach for Intl?
    Whenever text is going in front of a person. It is built in, needs no dependency, and handles things that are genuinely hard: Intl.Collator for sorting, since chapter 10 measured the default comparator putting every capital before every lowercase and accented letters after z; Intl.NumberFormat for currency and thousands separators, which differ by locale in both symbol and position; Intl.DateTimeFormat for dates, which avoids hand-built format strings entirely; Intl.RelativeTimeFormat for "3 days ago" without a pluralisation table; and Intl.Segmenter for the grapheme counting above. One performance note that applies to all of them: constructing a formatter is expensive relative to using it, so build it once outside the loop rather than calling the convenience methods — localeCompare and toLocaleString construct a fresh one on every call.
