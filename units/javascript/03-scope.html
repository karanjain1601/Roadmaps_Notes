Variables, scope and hoisting

"Hoisting" is one word covering three different behaviours, which is why it is explained badly so often. Pulling them apart takes about a page, and it also explains the most-asked JavaScript interview question — why a loop full of closures all report the same number.

The rule, in one line

const by default, let when you genuinely reassign, var never in new code. And const means the binding cannot be reassigned, not that the value cannot change: const a = [] followed by a.push(1) is fine, and a = [] is a TypeError. That distinction is worth being precise about, because "const means immutable" is a common and misleading shorthand — for real immutability you want Object.freeze, which chapter 1 showed fails silently in sloppy mode.

What hoisting actually means

Every declaration is registered when its scope is entered, before any statement runs. What differs is what it is registered as — and there are three answers, not one.

Reading a binding before its declaration
Compare the function declaration with the function expression
var is hoisted and initialised to undefined
So reading it early gives undefined rather than an error — the single most misleading behaviour in the language, because it looks like a value rather than a mistake.
let, const and class are hoisted and left uninitialised
Reading one gives ReferenceError: Cannot access 'x' before initialization. That gap between entering the scope and reaching the declaration is the temporal dead zone. They are hoisted — otherwise the error would say "is not defined".
Only a function declaration is usable early
f() before function f(){} works. A function expression assigned to a var does not: the variable is hoisted, the function is not, so you get undefined and then TypeError: f is not a function.
And typeof can throw
typeof undeclaredName is safely "undefined", but typeof on a name in its temporal dead zone raises. It is the one case where typeof is not safe.
The dead zone starts at the top of the block, not the file

This bites when shadowing. Given let x = "outer" and then a block containing console.log(x) followed by let x = "inner", the log throws a ReferenceError — it does not print "outer". The inner declaration claims the name x for the entire block from its first line, so the outer binding is unreachable there. Measured, that is exactly what happens. The practical consequence is that moving a declaration down a few lines inside a block can turn working code into a runtime error, and the message points at the read rather than at the declaration that caused it. Declaring at the point of first use, which is otherwise good practice, is what keeps this from arising.

Closures over a loop

Three closures, one loop
The last row proves what is actually being captured
var gives 3,3,3 — and so does the setTimeout version
Not 2,2,2. There is one binding for the whole loop, and by the time any closure is called the loop has ended and i holds 3, the value that failed the condition. Both cases print the same thing for the same reason.
The proof is calling them at two different times
The very same three closures give 0,1,2 when called inside the loop and 3,3,3 afterwards. They capture the binding, not the value it held when they were created.
let gives 0,1,2 in every case
A for loop with let creates a fresh binding for each iteration and copies the value across. Three iterations, three separate variables, three closures each holding their own.
The IIFE was how this was solved before let
Wrapping the body in an immediately-invoked function and passing i as an argument creates a new scope per iteration by hand. It works — 0,1,2 — and reads badly, which is why let was worth adding.
javascript
for (var i = 0; i < 3; i++) fns.push(() => i);   // 3,3,3 — one binding
for (let i = 0; i < 3; i++) fns.push(() => i);   // 0,1,2 — three bindings

// the pre-2015 workaround, for reading old code
for (var i = 0; i < 3; i++) (function (j) { fns.push(() => j); })(i);

// note that let only rebinds in a `for` loop, not in a while:
let k = 0;
while (k < 3) { fns.push(() => k); k++; }        // 3,3,3 — one binding again
while (k < 3) { const j = k; fns.push(() => j); k++; }  // 0,1,2

Check yourself

Self-check

  1. Name the three different things "hoisting" refers to.
    All declarations are registered when their scope is entered, and they differ in what they are registered as. A var is hoisted and initialised to undefined, so reading it early gives a value rather than an error. A let, const or class is hoisted and left uninitialised, so reading it early throws ReferenceError: Cannot access 'x' before initialization — that gap is the temporal dead zone, and note the wording proves they are hoisted, because an unhoisted name would say "is not defined" instead. A function declaration is hoisted with its whole body, so calling it before its line genuinely works. The fourth case is the one that catches people: a function expression assigned to a var gets only the variable hoisted, so an early call gives undefined and then TypeError: f is not a function.
  2. Why does for (var i = 0; i < 3; i++) fns.push(() => i) give 3,3,3 rather than 2,2,2?
    Because var creates one binding for the entire loop, and the closures capture that binding rather than its value at the moment they were made. By the time any of them is called, the loop has finished — which required the condition to fail, so i holds 3, not the last value the body saw. The proof is to call the same three closures at two different times: inside the loop they give 0,1,2, and after it they give 3,3,3. Nothing about the closures changed; the one variable they all read did. This also explains why the setTimeout version behaves identically — it is not an asynchrony bug, and treating it as one leads people to reach for the wrong fix. let gives 0,1,2 in every case because a for loop with let creates a fresh binding per iteration.
  3. Does let fix the closure problem in a while loop?
    No. The per-iteration binding is a special rule for for loops specifically — the specification copies the loop variable into a new binding at the top of each iteration. A while loop has no loop variable of its own; the counter is declared outside it, so there is one binding no matter whether you wrote let or var, and closures created inside will all see its final value. The fix is to introduce a binding inside the loop body, which is where the block scope actually applies: const j = k; as the first line, then close over j. This generalises usefully — the reliable mental model is "a new binding is created wherever a let or const declaration is evaluated", and in a for loop that happens to be once per iteration. Reasoning from that rule rather than from "let fixes loops" gets the while case right.
  4. What does const actually prevent?
    Reassigning the binding, and nothing else. const a = [] followed by a.push(1) is perfectly legal, and a = [] throws TypeError: Assignment to constant variable. So const is a statement about the name, not about the value — "this name will always refer to this object" rather than "this object will not change". The shorthand "const means immutable" is common and misleading, and it causes real confusion when someone expects a frozen object and gets a mutable one. For actual immutability you need Object.freeze, which is shallow (nested objects are still mutable) and which chapter 1 showed fails silently in sloppy mode while throwing in strict mode. In practice, use const everywhere by default anyway: it removes a class of bug where a name is reassigned far from where it was declared, which is worth having even though it says nothing about the contents.
  5. When can typeof throw?
    On a name in its temporal dead zone. typeof someNameThatWasNeverDeclared is safe and returns "undefined" — that is a deliberate feature, historically used to feature-detect globals before optional chaining existed. But typeof x where x is declared with let or const later in the same scope throws ReferenceError, because the binding exists and is uninitialised, which is a different state from not existing. It is the only situation in which typeof raises. The practical consequence is small but real: the old "safe check" idiom is no longer universally safe, and if you are guarding a name that might be block-scoped you need a different approach. In modern code the honest answer is that you should rarely be checking whether a name exists at all — globalThis.someFeature !== undefined or optional chaining expresses the actual question better.
  6. An inner block does console.log(x) then let x = "inner", with let x = "outer" above it. What prints?
    Nothing — it throws ReferenceError. The inner declaration claims the name x for the whole block starting at the block's first line, so the outer x is unreachable inside it and the read happens in the temporal dead zone. This surprises people because the outer variable is perfectly valid, visible on the line above, and simply cannot be reached. It matters practically because the failure is positional: moving a let declaration a few lines down inside a block can turn working code into a runtime error, and the error points at the read rather than at the declaration that caused it. Two habits avoid it entirely — declare at the point of first use, and do not shadow a name you also need in the same block. A linter's no-shadow rule catches the rest.
  7. Why does a top-level var behave differently from a top-level let?
    A top-level var in a script creates a property on the global object, so var x = 1 makes globalThis.x equal 1, while let x = 1 creates a binding that is not a global property. Two consequences follow. Any var at the top level of a script is visible to every other script on the page and can collide with a browser or library global — which is what the module pattern and IIFE wrappers existed to prevent. And code that feature-detects with window.something will see var declarations and miss let ones. This is largely historical now, because chapter 1's point applies: in an ES module nothing you declare at the top level touches the global object at all, regardless of keyword, since a module has its own scope. It is worth knowing mainly for reading older scripts, where an unexplained global usually traces back to exactly this.
