Map, Set and weak collections

A plain object was the only dictionary JavaScript had for twenty years, and it is a poor one: it stringifies every key, reorders numeric ones, and comes with inherited names already in it. Map fixes all three. The weak variants fix something else entirely, and this chapter measures it with a real garbage collector.

Map against a plain object

Six cases, both ways
Five of six differ — start with the object key
An object stringifies every key, so distinct objects collide
Two different objects as keys both become "[object Object]", giving one entry. The Map keeps them apart and reports size 2.
Numeric keys survive, and so does insertion order
typeof the first key is "number" in a Map and "string" in an object. And chapter 8's ordering rule applies only to the object: the Map gives b,2,a,10,1 where the object gives 1,2,10,b,a.
An empty object already "has" toString
"toString" in {} is true, because the prototype chain is part of the lookup. new Map().has("toString") is false. For keys arriving from outside your program, that difference is a security question, not a style one.
size is a property; the object equivalent is a computed array
Object.keys(o).length allocates an array to count. On a hot path that matters.
When a plain object is still right

When the keys are a fixed, known set written in your source — a config object, a lookup table, the shape of a record. Then you want the literal syntax, JSON serialisation for free, and destructuring, none of which a Map gives you. Reach for Map when keys are dynamic, arrive from outside, are not strings, or when insertion order matters. And note Map does not serialise: JSON.stringify(new Map([["a",1]])) is "{}", so anything crossing an API boundary needs Object.fromEntries(map) on the way out. Chapter 8's Object.create(null) is the middle option — a plain object with no inherited names, which solves the collision problem but not the key-type or ordering ones.

javascript
const m = new Map([["a", 1], ["b", 2]]);
m.get("a")  ·  m.set("c", 3)  ·  m.has("a")  ·  m.delete("a")  ·  m.size

for (const [k, v] of m) { }         // entries, in insertion order
Object.fromEntries(m)               // → a plain object, for JSON
new Map(Object.entries(o))          // ← and back

const s = new Set([1, 2, 2, 3]);    // size 3 — dedup by SameValueZero
[...new Set(arr)]                   // the idiomatic unique-ify
s.union(other)  ·  s.intersection(other)  ·  s.difference(other)   // ES2025

// grouping, without the reduce incantation
Map.groupBy(items, x => x.kind)     // → a Map;  Object.groupBy → an object

Where a WeakMap is genuinely the answer

Attaching data to objects you do not own and whose lifetime you do not control — metadata for DOM nodes, a per-instance cache keyed by the instance, private state for a class you cannot modify. In each case the entry should disappear when the object does, and a plain Map would pin every object it has ever seen. Two limits worth knowing before reaching for one. It is not a general-purpose cache: you cannot enumerate it, size it, or clear it, so it cannot implement an eviction policy. And collection is not observable or promptly scheduled — the engine decides, so code must never depend on an entry having gone. If you need "cache with a bounded size", write an LRU over a normal Map; if you need "data that lives exactly as long as this object", the WeakMap is the only thing that does it.

Check yourself

Self-check

  1. You use two different objects as keys in a plain object. What happens?
    They collide into one entry. A plain object's keys are strings (or symbols), so any object key is converted with toString() — and every plain object stringifies to "[object Object]". Measured: setting two distinct objects as keys left the object with one key and the second value overwriting the first, while the equivalent Map reported size 2 and returned the right value for each. This is the clearest single reason Map exists. The same conversion explains three related surprises: numeric keys become strings, so typeof Object.keys(o)[0] is "string" where a Map keeps "number"; true and "true" collide; and null becomes the key "null". If your keys are anything other than strings you knew about when you wrote the code, use a Map.
  2. Why does an empty object already contain toString?
    Because in walks the prototype chain, and a plain object inherits from Object.prototype, which carries toString, valueOf, constructor and hasOwnProperty. Measured, "toString" in {} is true while new Map().has("toString") is false. When the keys come from outside your program this stops being a curiosity: a user-supplied key called constructor or __proto__ can collide with something real, and in the worst case reach a shared prototype and change behaviour program-wide — prototype pollution. Map has no such surface, because its keys are not properties of anything. The middle option from chapter 8 is Object.create(null), which removes the inherited names while keeping object syntax, but does nothing about key stringification or ordering.
  3. What order do a Map and an object iterate in?
    A Map iterates in insertion order, always, for every key type. A plain object follows chapter 8's specified rule: integer-like keys first in ascending numeric order, then string keys in insertion order, then symbols. Measured on the same five keys, the Map gave b,2,a,10,1 and the object gave 1,2,10,b,a. So an object keyed by numeric ids silently reorders, and so does JSON.stringify of it — which breaks snapshot comparisons and any UI rendering "in the order they were added". This is one of the quieter reasons to prefer Map: the reordering is invisible in the source, appears only with numeric-looking keys, and produces a bug that looks like a sorting problem somewhere else entirely.
  4. What does a Set consider equal?
    SameValueZero — chapter 4's fourth equality algorithm, which is the one with no operator. Measured: new Set([NaN, NaN]).size is 1, so NaN deduplicates against itself even though NaN === NaN is false; new Set([0, -0]).size is 1, so the two zeros are one member; and new Set([{}, {}]).size is 2, because objects compare by identity. The same algorithm governs Map keys and Array.prototype.includes, which is why includes finds NaN and indexOf does not. The practical consequence is that [...new Set(arr)] — the idiomatic unique-ify — behaves sensibly for primitives and does nothing useful for objects, since every object literal is a distinct member. For deduplicating objects you need a key function and a Map.
  5. What exactly does a WeakMap buy you?
    Its entries do not keep their keys alive. Measured with a real collector: an object held only by a WeakMap was reclaimed once the last ordinary reference was dropped — a WeakRef to it went from true to false. The same code with an ordinary Map added left the object still reachable and Map.size still 1, indefinitely. That second case is precisely how a cache becomes a memory leak: every object the cache has ever seen is pinned by the cache itself. So a WeakMap is the right tool for attaching data to objects whose lifetime you do not control — DOM node metadata, per-instance state for a class you cannot modify, a memo keyed by an argument object. The entry disappears exactly when the object does, which is what you wanted and what a Map cannot express.
  6. Why has a WeakMap no size and no iterator?
    Because there is no consistent answer to give. Entries can disappear whenever the collector runs, which is at a moment the engine chooses and your code cannot observe — so a size read on one line could differ from the next with nothing in between, and an iteration could yield entries that cease to exist partway through. Both measured as undefined. Rather than expose a number that is unreliable by construction, the API omits the question. This is also why a WeakMap cannot be a general-purpose cache: with no way to enumerate, count or clear, there is no way to implement an eviction policy, and no way to know whether a lookup will hit. If you need bounded caching, build an LRU over an ordinary Map; if you need "exactly as long as this object lives", the weak version is the only thing that does it.
  7. When is a plain object still the right choice?
    When the keys are a fixed set you wrote in the source: a configuration object, a lookup table, the shape of a record. There you want object literal syntax, destructuring, and JSON serialisation for free — and a Map gives you none of those. That last point catches people: JSON.stringify(new Map([["a",1]])) is "{}", because a Map's entries are not own enumerable properties, so anything crossing an API boundary needs Object.fromEntries(map) on the way out and new Map(Object.entries(o)) on the way back. The decision rule that covers most cases: if you would write the keys as identifiers in your source, use an object; if keys are dynamic, arrive from outside, are not strings, or if insertion order matters, use a Map. And if you want object syntax without the inherited names, Object.create(null) is the middle path.
