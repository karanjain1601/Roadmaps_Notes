Chapter 14 · Asynchrony

The event loop

One thread, two queues, and one rule: finish all synchronous code, drain every microtask, take one macrotask, drain every microtask again, repeat. Almost every ordering question answers itself once that sentence is in place — and the "every" against "one" asymmetry is where the interesting failures live.

That asymmetry is the whole design
Microtasks exist so a promise chain resolves before the browser does anything else — no rendering, no input, no timers in between. It is what makes .then feel immediate, and it is what makes starvation possible.

200 iterations, and the pending timer fired during them — because each turn takes exactly one macrotask and other timers get their turn.
In a browser, starvation means a frozen tab
Rendering happens between macrotasks, so no paint, no input handling, no scrolling — a page that is technically running and completely unusable.
Which is why long work must yield
Break it into chunks rescheduled with setTimeout or scheduler.yield(), or move it to a Worker. An await alone does not yield to the browser — it queues a microtask.
await is not a yield to the browser

This one catches people building responsive UIs. Putting await null or await Promise.resolve() inside a heavy loop feels like giving the browser a chance to breathe, and it does not: the continuation is a microtask, so it runs before any rendering or input handling, and the loop is exactly as blocking as it was — just with more overhead. What actually yields is a macrotask: await new Promise(r => setTimeout(r, 0)), or await scheduler.yield() where it is available, which is designed for precisely this and keeps your continuation at high priority. For genuinely heavy computation neither is right — the work belongs in a Web Worker, where it cannot block the main thread at all. The tell that you have this bug is a progress bar that never updates until the work finishes.

Check yourself

Self-check

  1. State the event loop's rule in one sentence.
    Run all synchronous code to completion, then drain every microtask, then take one macrotask, then drain every microtask again, and repeat. The asymmetry between "every" and "one" is the entire design and explains most ordering questions. Measured across nine callbacks in one program, the order came out: synchronous code including the async function body, then process.nextTick, then promise callbacks and queueMicrotask, then the code after an await, then setTimeout, then setImmediate. Microtasks are for things that should happen before the world moves on — a promise chain settling — and macrotasks are the world moving on. In a browser the rendering step sits between macrotasks and never between microtasks, which is why a promise chain feels instantaneous and why a microtask loop freezes the page.
  2. Does an async function start running immediately?
    Yes — its body runs synchronously up to the first await. Measured, the async function's body logged before the last synchronous line of the program. Only the code after an await is deferred, and it is deferred as a microtask. Two practical consequences. Setup at the top of an async function — validating arguments, registering something, starting a timer — happens immediately, so an async function is not a way to defer work; if you want that, you need an explicit await null or a scheduled callback. And a synchronous throw before the first await still becomes a rejected promise rather than a thrown exception, because the function's contract is to return a promise. That is usually what you want, and it means a caller who forgets to await or .catch gets an unhandled rejection rather than a crash.
  3. setTimeout(fn, 0) — when does fn run?
    Not now, and not necessarily in zero milliseconds. It runs after the current synchronous work finishes and after the entire microtask queue drains — measured eighth of nine, behind all four microtasks in the test program. So the zero is a minimum delay before the callback becomes eligible, not a promise about when it executes. Two further caveats. Browsers clamp nested timers to about 4 ms after five levels of nesting, so a chain of zero-millisecond timers runs slower than you would expect. And if the microtask queue never empties, the timer never runs at all — which the starvation demo measures: 100,000 recursive microtasks with a pending zero-millisecond timer that never fired. The useful mental model is "as soon as the thread is genuinely free", where free means the stack is empty and no microtasks remain.
  4. How can a zero-millisecond timer never fire?
    If the microtask queue never empties. The loop drains microtasks completely before touching macrotasks, and a microtask that queues another microtask keeps the queue non-empty — so the loop never reaches the timer phase. Measured: a function rescheduling itself with queueMicrotask ran 100,000 times and a setTimeout(fn, 0) registered before it fired during none of them. The identical recursion rescheduled with setTimeout yielded every turn and let the pending timer through after 200 iterations. In Node this shows up as timers and I/O being delayed indefinitely; in a browser it is worse, because rendering and input handling are also macrotask-phase work, so the tab freezes while technically still executing. It is one of the few ways to hang a page without an infinite synchronous loop, and it is much harder to spot in a profiler.
  5. Why does adding await null inside a heavy loop not make the page responsive?
    Because the continuation after an await is a microtask, and microtasks run before rendering, before input handling, before anything the browser wants to do. So the loop is exactly as blocking as it was, with added overhead — this is the starvation case from the previous answer, arrived at by accident. The tell is a progress bar that stays frozen until the work completes and then jumps to 100%. What actually yields is a macrotask: await new Promise(r => setTimeout(r, 0)) gives the browser a full turn, and await scheduler.yield() does the same while keeping your continuation at high priority, which is what it exists for. For genuinely heavy computation neither is really right — chunking still competes with everything else on the one thread, and the work belongs in a Web Worker where it cannot block the main thread at all.
  6. What is the difference between process.nextTick and queueMicrotask?
    Both queue microtasks, and process.nextTick has its own queue that is drained before the promise microtask queue — measured, it ran ahead of both .then and queueMicrotask. It is Node-only and predates promises; queueMicrotask is standard and works in browsers too. The practical advice is to prefer queueMicrotask unless you specifically need to run before promise callbacks, which is mostly a library concern — Node itself uses nextTick to emit events after a constructor returns but before any user promise resolves. The starvation risk is sharper with nextTick for the same reason it is more powerful: because its queue is drained first and completely, a recursive nextTick can starve not just timers but the promise queue as well, which is a failure mode that does not exist for queueMicrotask.
  7. Where does rendering fit in a browser?
    Between macrotasks, never between microtasks. So the loop is: run a macrotask, drain the microtask queue, then possibly render, then take the next macrotask. That single fact explains a family of bugs. Setting a style, doing a second of synchronous work, and setting it again shows only the final value, because no paint happened in between. A promise chain of any length resolves entirely before one frame is drawn. And requestAnimationFrame exists to give you a callback at the right moment — just before a paint, roughly sixty times a second — rather than guessing with a timer. The related measurement worth carrying is the previous answer's: because microtasks are drained completely and rendering is macrotask-phase, a recursive microtask means no paint at all, which is how a page freezes while its JavaScript is still happily executing.
