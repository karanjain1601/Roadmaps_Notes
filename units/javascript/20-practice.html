The pattern in the red column

Almost every entry marked as a problem is a case where JavaScript does something defensible and says nothing. Sloppy mode invents a global; sort reorders as strings and looks correct; forEach discards a promise; a listener holds a megabyte; assert.equal accepts "1" for 1. None of them is a crash, and that is precisely the difficulty — the language almost never stops you, so the discipline has to come from tools you choose and habits you keep. That is the same conclusion the Python unit reached from a different language, which is some evidence it is about programs rather than about either one.

Check yourself

Self-check

  1. Three measurements in this unit came out the opposite way to expectation. Name one and say what it taught.
    Any of three. In chapter 3, the var loop gave 3,3,3 rather than the widely-repeated 2,2,2, because the closures all run after the loop and read i at the value that failed the condition — and the fix was better than the correction, because showing the same closures give 0,1,2 when called during the loop demonstrates that a closure captures the binding rather than the value. In chapter 6, arguments inside an arrow was not a ReferenceError but 5, because Node wraps every CommonJS module in a five-parameter function — the name resolves lexically like this. And in chapter 18, a single run of the string benchmark reported += as faster, and seven runs per size were needed to see the real direction. The common lesson: what you expect to measure shapes what you measure, and one run is not a measurement.
  2. Which single measurement best argues for a linter?
    The unused import in chapter 19, which passed every gate: it parsed, imported, returned the right answer, and both tests passed. That is correct behaviour, because it is not a behaviour difference at all — which is exactly the point. It is a cost rather than a bug, and nothing that executes the code can find a cost. The complementary case is the undefined name in a cold branch, which survived parsing, importing and the hot path and was caught only because a test happened to exercise the cold branch — and error paths are the branches tests usually skip. Between them the two show that the four tools partition the space rather than overlapping, and that "the tests pass" is not an argument against running the other three. A linter finds both in milliseconds without running anything.
  3. A colleague says JavaScript is unpredictable. What is the more accurate statement?
    That it is predictable and quiet. Almost every surprise in this unit follows a rule that can be stated in a sentence: + concatenates if either side is a string; == converts toward number; assignment writes an own property; this is set by the call; the default sort comparator stringifies. Once you know the rule, [] + {} and [1,10,2,20].sort() stop being interesting. What is genuinely difficult is that the language almost never stops you — five of six sloppy-mode behaviours were measured as silent, forEach discards a promise without complaint, and assert.equal accepts "1" for 1. So the failures are quiet and distant from their cause rather than random. That reframing matters because it points at the fix: not memorising oddities, but choosing tools and habits that make the quiet things loud.
  4. You inherit an untooled codebase. What are your first three changes?
    Make it a module ("type": "module"), which buys strict mode everywhere for free and turns chapter 1's five silent sloppy behaviours into errors. Add a linter with the correctness rules rather than the style ones — no-undef, no-unused-vars, eqeqeq with "smart" so chapter 4's useful x == null survives, no-unsafe-finally, and the floating-promise rules — which finds real bugs on the first run and needs no test-writing effort. Then add a formatter, which catches nothing and ends an argument that otherwise consumes review time. Tests are the highest-value tool and the highest-cost, so they come next, starting with a regression test written at the moment you fix the next bug rather than a coverage push — the Python unit measured a suite with 100% coverage catching zero of six injected bugs, and a coverage target reliably produces that suite.
  5. What is the honest limit of the measurements in this unit?
    Two things, both stated where they arise. Everything ran on Node 22 with V8 12.4, so the language semantics are portable but the performance figures are not — a different engine, or a later V8, could move any of them, which chapter 18 demonstrated by finding that a single run inverted a result. And chapter 17 could measure only half of itself: Node implements the EventTarget specification, so the listener behaviour is real, but there is no document, so propagation and delegation are specification behaviour and the chapter labels them as such rather than implying otherwise. Chapter 18 adds a third: the hidden-class claim could not be isolated at all — the one-shape case came out slowest and the sweep was not monotonic — so it is reported as unverified rather than as support or refutation.
  6. Which chapter's rule explains the most other chapters?
    Chapter 3's, that a closure captures the binding rather than the value. It explains the loop giving 3,3,3 and the same closures giving 0,1,2 when called during the loop. It explains why an arrow's this and arguments resolve lexically in chapter 6 and 7, and therefore why an arrow cannot be an object method. It explains chapter 18's leaks, where a listener holds its whole scope alive and the object stays reachable. And it broke the chapter 18 measurement itself: the first version of that test nulled an outer variable and reported everything as collected, because the closure captured the binding and nulling it released the object. A close second is chapter 8's, that reading walks the prototype chain and writing does not — which explains shadowing, class, and half of what people call surprising about objects.
  7. What single habit would have prevented most of the defects here?
    Checking the value rather than the absence of a complaint. Nearly every red entry in the table is code that ran without error and was wrong: sort returned an array that looked sorted; forEach returned in 0 ms having collected nothing; the CommonJS import read a stale 0; the class field was undefined inside a constructor; three assertions passed for code that was broken. In each case something completed successfully and the answer was wrong. The habit has a version needing no tooling, and it takes ten seconds: after writing a test, break the code it covers — flip a comparison, change a constant — and confirm the test fails. If it does not, you have learnt something no coverage report would have told you. The Python unit measured the extreme case, a suite at 100% coverage catching zero of six bugs, and the mechanism is identical here.
That is the unit

Twenty chapters, forty interactives, and every quoted figure reproduced from code that ran while the page was being written — including the three that came out the opposite way to expectation, which are in the chapters rather than quietly corrected. If one thing carries: JavaScript is predictable and quiet, so the checks have to come from you.
