Values, types and coercion

Seven primitive types and objects. That is the whole inventory, and it is small enough to hold in your head — which matters, because the reputation for chaos comes not from the types but from what happens when you mix them. Two of these answers are wrong, and only one is a bug
typeof null === "object"
A bug from 1995, preserved because fixing it would break the web — chapter 1's constraint in its purest form. null is a primitive, not an object.
typeof NaN === "number"
Not a bug. NaN means "a numeric operation produced no meaningful number", so it belongs to the number type. Surprising, correct.
Everything that is not a function reports "object"
Arrays, dates, maps, regexes — all "object". typeof is precise about primitives and gives up on objects entirely.
So use the right tool for the question
Array.isArray(v) for arrays. v instanceof Date when you control the realm. Object.prototype.toString.call(v) for a precise tag — it distinguishes [object Null] from [object Object] and [object Array] from both.

Coercion

Every operator that is not === converts its operands first. There are only three target types — number, string, boolean — and two rules that cause almost all the confusion.

Eighteen expressions, evaluated
Try the four == rows in order
Rule one: + is the only operator that is also concatenation
If either side is a string, + joins. Every other arithmetic operator converts to number, which is why 1 + '2' is "12" and 1 - '2' is -1. All the famous + surprises follow from this one line.
Rule two: == converts toward number, with one exception
[] == false is true because both sides become 0. '0' == false is true for the same reason. The exception is null and undefined, which equal each other and nothing else — null == 0 is false.
Which makes x == null the one useful loose comparison
Measured over [null, undefined, 0, '', false, NaN, []] it gives true true false false false false false — exactly the two nullish values and nothing else. It is the idiomatic "is it either" check, and the only == worth writing on purpose.
NaN == NaN is false
The only value not equal to itself, under both == and ===. Test with Number.isNaN(v), never with a comparison.
Why [] + {} is "[object Object]"

Both operands are objects, so neither is a number and neither is a string — + has to convert them. It asks each for a primitive, which for a plain object means calling toString(): an empty array stringifies to "" and a plain object to "[object Object]". One of them is now a string, so + concatenates, giving "" + "[object Object]". Nothing arbitrary is happening; the same two steps explain [1,2] + [3] giving "1,23", because arrays stringify by joining with commas. This is worth following once, because it is the mechanism behind every "JavaScript is insane" example you will be shown — and once you can predict them they stop being interesting.

What to actually do

javascript
// use === everywhere, with exactly one exception
if (x == null) { ... }              // null OR undefined — idiomatic, keep it
if (x === null) { ... }             // only null. Say what you mean

// convert explicitly, so the reader sees the intent
Number(s)      // "" -> 0, "12px" -> NaN, whitespace trimmed
parseInt(s, 10) // "12px" -> 12. ALWAYS pass the radix
String(v)      // safe for null and undefined; v.toString() throws on them
Boolean(v)     // or !!v — same thing, and the falsy list is short:
               // false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy

// the traps in that list
Boolean([])    // true  — an empty array is truthy
Boolean({})    // true  — so is an empty object
Boolean("0")   // true  — a non-empty string, whatever it contains

// nullish coalescing distinguishes "absent" from "falsy" — chapter 4
const port = cfg.port ?? 8080;      // 0 survives
const bad  = cfg.port || 8080;      // 0 becomes 8080. A real bug
Objects compare by identity, always

{a:1} === {a:1} is false, and so is [1,2] === [1,2] — two objects are equal only when they are the same object. There is no value equality for objects in the language and no operator that gives it to you, which surprises people arriving from languages where == compares contents. For a deep comparison you need a function: JSON.stringify on both sides is the quick version and is wrong often enough to matter (key order, undefined, dates, NaN, cycles), so reach for structuredClone to copy and a real deep-equal helper to compare. The one place the language does help is Object.is, which differs from === on exactly two values — it says NaN is itself and -0 is not 0. Chapter 4 lays out all four equality algorithms side by side.

Check yourself

Self-check

  1. Why is typeof null === "object", and why is typeof NaN === "number" different?
    The first is a genuine bug from the original 1995 implementation, where values were tagged and the null pointer happened to carry the object tag. It has been preserved for the reason chapter 1 set out: fixing it would change the behaviour of existing pages, and there is no version of the web to migrate to. null is a primitive despite what typeof says. The second is not a bug at all. NaN means "a numeric operation produced no meaningful number" — it is a member of the number type by definition, in IEEE 754 as much as in JavaScript, so reporting "number" is correct. The pair is worth holding together because it teaches the right instinct: surprising is not the same as broken, and the way to tell them apart is to ask what the value is for. Only one of the two has an excuse.
  2. Why does 1 + '2' give "12" while 1 - '2' gives -1?
    Because + is the only operator that is both arithmetic and string concatenation. Its rule is: if either operand is a string after conversion to a primitive, concatenate; otherwise add. Every other arithmetic operator has no string meaning, so it converts both sides to number unconditionally — hence '3' * '4' is 12 and 1 - '2' is -1. Essentially every famous + surprise follows from that single line. [] + {} is "[object Object]" because both operands are objects, so each is asked for a primitive, which for a plain object means toString(): "" and "[object Object]". One is a string, so it concatenates. [1,2] + [3] is "1,23" by the same route, since arrays stringify by joining with commas. Once you can predict them they stop being interesting, which is the point.
  3. [] == false is true. Walk through why.
    == converts toward number when the operands are of different types. false becomes 0. [] is an object, so it is converted to a primitive first — toString() on an empty array gives "" — and then "" converts to 0. Both sides are now 0, so the comparison is true. '0' == false is true by the same route, and so is '' == 0. Two things are worth taking away rather than memorising the chain. First, the direction is consistent: == pulls everything toward number, which is why so many unrelated-looking values compare equal. Second, this is exactly why the advice is to use === — not because == is unpredictable, but because predicting it requires you to run a three-step algorithm in your head at every call site, and the reader has to as well.
  4. Which loose comparison is worth writing on purpose?
    x == null. It is true for exactly null and undefined and false for everything else — measured over [null, undefined, 0, '', false, NaN, []] it gives true true false false false false false. That is genuinely useful, because the two nullish values usually mean the same thing to your code ("no value here") while differing in who produced them: undefined is the language's absence, null is yours. The alternative, x === null || x === undefined, says the same thing in four times the characters. This works because of the one exception in the == algorithm: null and undefined are equal to each other and to nothing else, so null == 0 is false even though null converts to 0 in arithmetic. Most style guides that ban == carve out this exact case, and it is worth carving out.
  5. cfg.port || 8080 — what is the bug?
    A configured port of 0 becomes 8080, because || tests truthiness and 0 is falsy. The same bug hits every legitimately falsy value: an empty string for a prefix, false for a flag that defaults to true, 0 for a retry count or a timeout. The pattern is that || answers "is this falsy" when what you meant was "is this absent", and those coincide only when none of your valid values happen to be falsy. cfg.port ?? 8080 is the fix: nullish coalescing falls back only for null and undefined, which is the same predicate as x == null from the previous answer and is exactly the question a default is asking. The falsy list is short enough to keep in your head — false, 0, -0, 0n, "", null, undefined, NaN — and everything else, including [] and {} and "0", is truthy.
  6. How do you check whether two objects have the same contents?
    You write a function, because the language has no operator for it. === and == both compare objects by identity, so {a:1} === {a:1} is false and two objects are equal only when they are literally the same object. The quick workaround, comparing JSON.stringify of both sides, is wrong often enough to matter: it depends on key order, drops undefined values and functions, turns dates into strings, cannot represent NaN and throws on cycles. Use a real deep-equal helper — from a library, or your own recursive one if the shapes are simple and known. Two related tools are worth knowing: structuredClone(v) makes a genuine deep copy including cycles, dates and maps, and Object.is is the language's most precise equality, differing from === on exactly two values by saying NaN is itself and -0 is not 0.
  7. How many numeric types does JavaScript have, and what follows from that?
    Two now, and for most of its life one. number is an IEEE 754 double, so there is no integer type — 1 and 1.0 are the same value, and every integer above 2⁵³ loses precision, which is why Number.MAX_SAFE_INTEGER exists and why an id arriving as JSON from a language with 64-bit integers can silently change. bigint, written 10n, was added for exactly that case and deliberately does not mix with number in arithmetic: 1n + 1 throws a TypeError rather than quietly picking a precision. The single-double-type design also explains the other numeric oddities in one go — 0.1 + 0.2 is not 0.3, -0 exists and is distinguishable only by Object.is, and NaN and Infinity are ordinary number values you can store in an array. Chapter 12 works through the consequences.
