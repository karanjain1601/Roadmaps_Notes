Memory and performance

Garbage collection is automatic and leaks are still possible, because the collector reclaims what is unreachable and reachability is not the same as usefulness. Two of the commonest roots are invisible in the source: a listener and a running timer. Both are measured here, with the collector exposed.

The order to work in, and why this section exists

The Python unit measured the same shape from a different language: one structural change was worth more than every micro-optimisation put together. Here the ratio is 22× against a claim that could not be measured at all. So: do less work, then fix the data structure, then let a built-in do the loop, and only then think about idioms. What this section really demonstrates is the process rather than the answers — a single run inverted the string result, and a plausible claim about engine internals produced a non-monotonic sweep. Both are ordinary outcomes when you actually measure, and neither is visible if you reason from what you have read. Measure on the runtime you ship, at the size you ship, more than once.

Check yourself

Self-check

  1. How can a garbage-collected language leak?
    Because the collector reclaims what is unreachable, and reachable is not the same as useful. Anything still referenced from a root — the global object, the current stack, a live timer, a registered listener — survives, however dead it is to your program. Measured, an object referenced only by an event listener's closure was still alive after collection, and so was one held by a running setInterval. Neither appears as a variable in the source, which is what makes them the two commonest leaks in a long-lived page: there is nothing to see. The general shape is a container that only grows — a cache, a registry, a list of subscribers — and the general fix is that whatever registers must also unregister. Chapter 11's WeakMap measurement is the other half of this: it holds its keys weakly, so its entries disappear when the objects do.
  2. An interval is cleared and a hundred kilobytes are freed. What was happening?
    The interval's callback closed over the object, and a scheduled timer is a garbage-collection root — so the closure, its scope, and everything in that scope stayed reachable for as long as the timer was scheduled. Measured: two runs of identical code one line apart, and clearInterval released a 100,000-element array that was otherwise completely unreachable. This is the same mechanism chapter 6 warned about — a closure keeps its whole scope alive, not only the variables it appears to use — with a root you cannot see. The habits that prevent it: clear every timer when the thing that owns it goes away, disconnect every observer, and abort every listener. And capture the value rather than the object it came from, so a handler closes over a string id rather than the entire response it was extracted from.
  3. Why does an AbortController beat matching function references?
    Because it removes the identity problem entirely. Chapter 17 measured that removeEventListener matches the function object, so a fresh arrow or a fresh fn.bind(this) removes nothing and reports nothing — a silent failure that leaves a listener attached, and with it everything the listener's closure holds. Passing { signal: ac.signal } to every listener a component adds means one ac.abort() removes all of them, with no references to keep straight and no way to get the pairing wrong. It also works across different targets, so a component can clean up its window resize handler and its element click handler in the same line. And since fetch accepts the same signal, one controller can cancel in-flight requests alongside the listeners, which is exactly what a component teardown wants.
  4. Should you build strings with += in a loop?
    It depends on the size, which is more interesting than the usual advice. Measured over seven runs per size: at 2 million appends, push + join was 1.84× faster; at 200,000, += was faster at 0.61×. V8 represents a growing concatenation as a rope rather than copying, which is why the small case is fine — the classic advice describes engines that copied. So the rule holds at scale and is wrong below it. The more useful lesson is in how nearly this was got wrong: a single run of the benchmark reported += as faster at both sizes, and only repeating it seven times per size showed the real direction, with the ratio at 2M ranging from 1.62× to 2.23×. One measurement of a microbenchmark is not a measurement.
  5. Why does this chapter report the hidden-class claim as unverified?
    Because the sweep contradicted it. Reading the same property from arrays of objects with 1, 2, 4, 8 and 16 distinct shapes, the one-shape case came out slowest and the series was not monotonic. That is not evidence that shapes do not matter — V8's inline caches are real and well documented — it is evidence that this benchmark measured something else, most likely allocation patterns and garbage-collection state from building the arrays differently. Reporting it as support would have been dishonest, and reporting it as a refutation would have been equally wrong. The honest statement is that the effect was not isolated by this test. That is worth including rather than quietly dropping, because it is the ordinary outcome of trying to measure engine internals from the outside, and it is a reason to be sceptical of blog posts that report a clean number.
  6. What order should performance work go in?
    Do less work first — cache a repeated computation, stop fetching what you discard, break out early. Then fix the data structure, which is where the large wins live: measured here, a Float64Array against an array of objects was 22×, against a micro-optimisation claim that could not be measured at all. Then let a built-in do the loop, since a C++ implementation beats interpreted bytecode. Only then consider idioms, which are worth single-digit multiples at best. The Python unit measured the same ordering in a different language and found the same shape, which is some evidence it is about programs rather than about either runtime. And measure between steps: the profile changes as you go, so the function that dominated at the start may not after the first fix.
  7. How would you find a leak in a running page?
    Heap snapshots, compared across a repeated action. Take a snapshot, perform the suspect interaction — open and close a dialog, navigate to a route and back — twice, force collection, then snapshot again and compare: objects that survive two full cycles of something that should be symmetrical are the suspects, and devtools will show you the retaining path, which is the actually useful part. The path is what tells you which root is holding it, and in practice it is usually one of the ones measured here: a listener that was never removed, a timer never cleared, an observer never disconnected, or a cache that only grows. Two things that help before you get there: a monotonically climbing baseline across identical interactions is the signal to look at all, and performance.measure marks are worth adding around suspect regions so the timeline shows what was happening when memory moved.
