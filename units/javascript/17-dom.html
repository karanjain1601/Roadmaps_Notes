The DOM and events

The DOM is not JavaScript — chapter 1's distinction, and this is where it bites. What is specified precisely is the event system, and most of the confusion around it comes from two things: what counts as "the same listener", and the difference between where an event started and where you are handling it.

What counts as the same listener

What is measured here, and what is not

Node implements the DOM's EventTarget specification, so every result in the first demo was produced by running the code — the dedup rule, once, signal, stopImmediatePropagation and preventDefault are all genuine measurements. Node has no document, so there is no tree to propagate through: the second demo is specification behaviour rather than a measurement, and is labelled as such. That distinction is worth keeping visible, because the two halves are equally true and only one of them was checked here.

The three DOM habits worth having

Delegate. One listener on a container beats one per row: fewer objects, no re-binding when rows change, and no leak when they are removed. Use e.target.closest(selector) rather than comparing e.target directly, because the click often lands on something inside the element you care about.

Separate reads from writes. Reading a layout property such as offsetHeight after a style write forces the browser to recompute layout synchronously. Interleaving them in a loop does that once per iteration — the classic layout thrash. Read everything, then write everything.

Clean up. Chapter 18 measures this: a listener is a root, and whatever its callback closes over stays alive as long as the listener does. An AbortController passed as { signal } to every listener a component adds lets one abort() remove all of them, which is far harder to get wrong than matching function references.

Check yourself

Self-check

  1. You add the same function twice with addEventListener. How many times does it fire?
    Once. The specification deduplicates listeners on the triple (type, callback, capture), so a second identical registration is a no-op — measured on a real EventTarget, it fired once. The subtlety is the third element of that key: add the same function again with { capture: true } and it is a different listener, so it fires twice. Measured too. Two consequences follow. Defensive re-adding is harmless if you genuinely pass the same function object, which makes idempotent setup easy. And two arrow functions with identical source are different objects, so they are two listeners and both fire — which is the same identity question that makes removeEventListener so unreliable, and the next answer.
  2. Why does removeEventListener so often remove nothing?
    Because it matches on the function object, not on what the function does. Passing a fresh arrow with identical source removes nothing and reports nothing — measured, the original listener still fired. The same trap catches el.removeEventListener("click", this.onClick.bind(this)), because chapter 7 measured that bind returns a new function every call, so the one passed to remove is never the one that was added. The capture flag must match too. The reliable fixes are to keep the reference — assign the handler to a variable or a field once and pass that same value to both calls — or, better, to skip the problem entirely with { signal }: one AbortController can remove any number of listeners with a single abort(), and there are no references to keep straight.
  3. What is the difference between target and currentTarget?
    target is where the event originated; currentTarget is the element whose listener is currently running. They are the same only when the listener is on the element that was actually interacted with. In delegation they differ by design: with one listener on a <ul>, currentTarget is the list and target is whatever was clicked, which may be a button, or a <span> inside that button, or an icon inside that. That last part is the most common delegation bug — comparing e.target directly against the element you expect fails whenever the click lands on a descendant. Use e.target.closest("button[data-id]"), which walks up from the target and returns the first match, and check the result is non-null before using it. currentTarget is also the reliable way to get the element regardless of any binding, which chapter 7 recommended over this.
  4. Why is delegation better than a listener per row?
    Three reasons. Fewer objects — one listener rather than one per row, which matters at a thousand rows and is measurable in memory. It keeps working for rows added later, so no re-binding step after every render, which is a whole category of bug that simply cannot occur. And it removes a leak: chapter 18 measures that a listener is a garbage-collection root, so a listener attached to a removed row keeps that row and everything its callback closes over alive until the listener is removed too — and it is precisely that removal people forget. Delegation works because of bubbling: the event travels from the target up through every ancestor, so a listener on the container sees clicks on everything inside it. The costs are small and worth knowing: it does not work for events that do not bubble, such as focus (use focusin) and most media events.
  5. What does preventDefault do on a non-cancelable event?
    Nothing at all, and it says nothing about it — measured, dispatchEvent returned true and defaultPrevented stayed false, exactly as if the call had not been made. That silence is why passive listeners surprise people: a listener registered with { passive: true } promises not to call preventDefault, and browsers now default touch and wheel listeners to passive so that scrolling need not wait for JavaScript. Call preventDefault in one and the scroll happens anyway, with at most a console warning. If you genuinely need to block the default, register with { passive: false } explicitly. Worth pairing with the distinction in the next answer: preventDefault stops the browser's default action and has nothing to do with whether other listeners run.
  6. stopPropagation, stopImmediatePropagation, preventDefault — what does each do?
    Three unrelated things. preventDefault cancels the browser's default action — following a link, submitting a form, scrolling — and does not affect which listeners run. stopPropagation stops the event travelling any further up or down the tree, so ancestors do not see it, but every remaining listener on the current element still fires. stopImmediatePropagation also skips those siblings — measured, a second listener on the same target never ran. The practical advice is to avoid the propagation stoppers in application code: they make an event invisible to anything above, which silently breaks delegation, analytics and outside-click handlers written by someone else. Prefer a flag on the event or a check in the outer handler. And never use return false in an inline handler, which does all three at once and hides which one you meant.
  7. Why is reading offsetHeight inside a loop that also writes styles slow?
    Because reading a layout property forces the browser to compute layout now, and it can only do that after applying any pending style changes. Writing a style normally just marks layout dirty and defers the work to the next frame, so a loop of writes is cheap. Interleaving a read after each write defeats that: every iteration invalidates layout and then immediately demands the answer, so the browser recomputes once per element instead of once in total. That is layout thrash, and it turns an O(n) loop into something far worse. The fix is to batch by phase — read every value into an array first, then write every style — which the code sample shows. The properties that force it are worth recognising: offsetTop and friends, getBoundingClientRect, getComputedStyle, scrollTop. And requestAnimationFrame is the right place to put the write phase, since it runs just before a paint.
