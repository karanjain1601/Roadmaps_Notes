Iterators and generators

for…of, spread and array destructuring are three syntaxes for one operation: call [Symbol.iterator]() and pull values until it says stop. Implement that method and all three work on your type. A generator writes it for you.

— words— min read2 interactivesNeeds: chapters 05, 06

One method, three syntaxes

What is iterable, and what is not
A plain object fails all three the same way
One method decides all three
Everything with [Symbol.iterator] works with for…of, spread and destructuring; everything without it fails all three with the same TypeError. There is no partial support.
A plain object is not iterable
Which is why {...o} and [...o] are different features: the first is property spread, added later and defined on objects; the second is iterable spread and needs the protocol. Object.entries(o) bridges them.
Array-like is not the same as iterable
arguments has both, but a DOM NodeList from older APIs may have length and no iterator. Array.from accepts either.
A generator method makes your type reusable
*[Symbol.iterator]() { … } returns a fresh generator each call, so the object can be iterated repeatedly. An object that is its own iterator can only be consumed once.
javascript — six lines to make anything iterable
class Range {
  constructor(a, b) { this.a = a; this.b = b; }
  *[Symbol.iterator]() { for (let i = this.a; i < this.b; i++) yield i; }
}
const r = new Range(1, 4);
[...r]                        // [1, 2, 3]
for (const n of r) { }        // works
const [first, second] = r;    // works — and r can be iterated again

// the raw protocol, if you want to see it. A generator writes exactly this:
const manual = {
  [Symbol.iterator]() {
    let i = 0;
    return { next: () => i < 3 ? { value: i++, done: false }
                              : { value: undefined, done: true } };
  }
};

Generators

Lazy, resumable, two-way
The memory row was measured, not estimated
An infinite generator produced exactly 3 values
Taking three from while (true) yield n++ and breaking ran the body three times. The array equivalent cannot be written at all.
7.6 MB against 0.00 MB
Measured with --expose-gc: an array of a million integers against a generator over the same range. The generator holds a counter and a suspended frame.
break calls .return(), which runs the generator's finally
Measured on all three exits — breaking early, running to completion, and calling .return() explicitly. So a generator holding a file handle or a lock releases it even when abandoned.
next(v) makes the paused yield evaluate to v
A generator is a two-way channel, not only a producer. That is the mechanism async/await was originally built on.
javascript — where generators earn their place
function* chunks(rows, size) {                // stream a large file without
  for (let i = 0; i < rows.length; i += size) // holding it all
    yield rows.slice(i, i + size);
}

function* ids() { let n = 0; while (true) yield ++n; }   // infinite, harmless

function* flatten(x) {                        // recursion, lazily
  for (const v of x) {
    if (Array.isArray(v)) yield* flatten(v);  // yield* delegates
    else yield v;
  }
}

// async iteration — one page of an API at a time, on demand
async function* pages(url) {
  let next = url;
  while (next) { const r = await fetch(next).then(r => r.json());
                 yield r.items; next = r.next; }
}
for await (const items of pages("/api/things")) { }
A generator is single-use, and that catches people

Once exhausted it stays exhausted: a second for…of over the same generator object yields nothing, silently. So const g = gen(); [...g]; [...g] gives you the values and then an empty array — no error, just missing data. The same trap appears when a function takes an iterable and walks it twice, which works for an array and quietly fails for a generator. Two defences. Return a function that makes a generator rather than a generator itself, or implement [Symbol.iterator] as a generator method so each iteration gets a fresh one — measured above as re-iterable. And if a function genuinely needs two passes, materialise once with const items = [...input] at the top and be explicit about the memory that costs. This is the same exhaustion trap the Python unit measured for its generators; the mechanism and the fix are identical.

Check yourself

Self-check

  1. What do for…of, spread and array destructuring have in common?
    They are three syntaxes for one operation: call the value's [Symbol.iterator]() method to get an iterator, then call next() repeatedly until it reports done. Measured across eight values, anything with the method works with all three and anything without it fails all three with the same TypeError — there is no partial support, which makes the rule easy to hold. It also means implementing one method makes your own type work with all of them, and a generator method is the shortest way to write it. Worth adding Array.from, Promise.all, new Map(...), new Set(...) and yield* to the list of things driven by the same protocol. The one syntax that looks similar and is not is object spread: {...o} copies own enumerable properties and has nothing to do with iteration.
  2. Why is [...obj] a TypeError when {...obj} works?
    Because they are different features that happen to share three dots. Array spread requires the iteration protocol, and a plain object has no [Symbol.iterator] — measured false, with spread, for…of and destructuring all throwing. Object spread was added later and is defined directly on objects: it copies own enumerable properties, no iterator involved. The confusion is understandable and the fix is straightforward — Object.keys, Object.values or Object.entries turn an object into an array, which is iterable, so for (const [k, v] of Object.entries(o)) is the idiom. Note the asymmetry runs the other way too: {...[1,2]} is legal and gives {0: 1, 1: 2}, because an array's indices are properties. Two operations, two rules, one piece of syntax.
  3. An infinite generator is not an infinite loop. Why not?
    Because the body only runs when someone asks for a value, and it suspends at each yield until the next request. Measured: taking three values from function* naturals() { while (true) yield n++ } and then breaking ran the body exactly 3 times. That is the essential property — a generator describes a sequence rather than building one, so the sequence can be unbounded as long as the consumer is not. It also makes composition cheap: filtering or mapping a generator produces another generator, and nothing is computed until the final consumer pulls. The array equivalent of an infinite sequence cannot be written at all, and even a finite one pays up front — the next answer measures that at 7.6 MB against effectively nothing.
  4. How much memory does a generator over a million integers use?
    Effectively none. Measured with --expose-gc, an array of a million integers cost 7.6 MB of heap and the generator over the same range cost 0.00 MB — it holds a counter and a suspended stack frame, and nothing else. That is the case for streaming: reading a large file, paging an API, or transforming a big collection where you only need one item at a time. The trade is that a generator gives you no length, no random access, and no second pass, so it is the wrong shape whenever you need to know how many there are or to look at them twice. The Python unit measured the same comparison and found an even more extreme ratio, for the same reason — the mechanism is identical, and so is the advice: generators for pipelines, arrays for collections you will interrogate.
  5. What happens to a generator's finally block when you break out of a loop?
    It runs. Breaking out of a for…of calls the iterator's .return() method, which resumes the generator at its suspension point as though a return statement had appeared there — so any finally executes. Measured on all three exits: breaking early, running to completion, and calling .return() by hand each printed the cleanup line. This is what makes generators safe for resources: one holding a file handle, a database cursor or a lock can release it in a finally and be confident it happens even when the consumer abandons the loop halfway. It also applies to throw inside the loop body and to an early return from the enclosing function. The one case it does not cover is the generator simply being garbage collected without ever being resumed — there is no finaliser, so a generator that is dropped rather than closed never runs its cleanup.
  6. What does gen.next("Ada") do?
    It resumes the generator and makes the paused yield expression evaluate to "Ada". So const name = yield "who?" sends "who?" out to the caller, suspends, and then — when the caller calls next("Ada") — assigns "Ada" to name and carries on. Measured with a three-step dialogue ending in "Ada is 36". This makes a generator a two-way channel rather than only a producer, and it is the mechanism async/await was originally built on: libraries like co ran a generator that yielded promises, awaited each one, and fed the resolved value back in with next. Note the first next() takes no useful argument, since there is no paused yield to receive it — the generator has not started. That asymmetry is the one awkward part of the API.
  7. You iterate a generator twice and get nothing the second time. Why?
    A generator object is single-use. Once exhausted it stays exhausted, and further iteration yields nothing — silently, with no error, so the symptom is missing data rather than a failure. const g = gen(); [...g]; [...g] gives the values and then an empty array. The same trap catches a function that accepts "an iterable" and walks it twice: it works for an array and quietly fails for a generator, which is a genuinely nasty bug because it depends on the caller. Two fixes. Pass a function that makes a generator rather than a generator, or put the generator behind *[Symbol.iterator]() on an object, which produces a fresh one per iteration — measured re-iterable above. If a function really needs two passes, materialise once with const items = [...input] at the top and accept the memory. The Python unit found the identical trap with identical fixes.
