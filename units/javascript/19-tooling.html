Chapter 19 · Craft

Tooling and testing

Four tools, each blind to what the others catch. This chapter runs six defects through the gates a real project has — using Node's built-in test runner, so the results are measured rather than described — and then looks at eight assertions, four of which pass when they should not.

Which gate catches what

Six defects, four gates
One passes everything; one is caught only by the runner
An unused import passes every gate
It parses, imports, runs correctly and the tests pass. It is not a behaviour difference, so nothing that executes the code can find it — only a linter addresses that category at all.
An undefined name in a cold branch survives three of four
It parses, imports and returns the right answer on the hot path. It is caught only because a test exercises the cold branch — and error paths are exactly the branches tests usually skip.
The floating rejection is the surprise, in a good way

Assertions that pass anyway

Eight assertions, run for real
Four of them pass and should not
assert.equal and assert.deepEqual are loose
Both accept 1 against "1" — chapter 2's coercion, hiding in a test framework. The strict variants fail correctly. Use strictEqual and deepStrictEqual always.
assert(promise) always passes
A promise object is truthy, so the assertion is about the wrapper rather than the value. It passes even for a promise that rejects.
An assertion that never executes cannot fail
[].forEach(() => assert.fail()) passes. A test whose only assertions are inside a loop over a possibly-empty collection asserts nothing at all.
But an un-awaited async assertion was caught
Better than expected: Node's runner attributes the unhandled rejection to the test and fails it. Not every runner does, so this is worth checking on yours rather than assuming.
The test that cannot fail

Four of the eight above pass regardless of whether the code is right, and none of them looks wrong in review — each is a plausible line that a reviewer reads as an assertion. The cheap defence needs no tooling: after writing a test, break the code it covers and confirm the test fails. If it does not, you have learnt something no coverage report would have told you, and it takes ten seconds. The Python unit measured the extreme version of this — a suite with 100% line coverage that caught zero of six injected bugs — and the mechanism is the same in both languages. Coverage measures which lines ran, not whether anything checked the result.

Check yourself

Self-check

  1. Which defect passed every gate, and what does that tell you?
    The unused import. It parses, it imports, the hot path returns the right answer and both tests pass — measured. That is not a failure of the gates; it is correct, because an unused import is not a behaviour difference at all. It is a cost: import time, a dependency that may not be needed, and a reader's attention. Only static analysis addresses that category, which is why "the tests pass" is not an argument against running a linter. The complementary case is the undefined name in a cold branch, which survived three of the four gates and was caught only because a test happened to exercise that branch — and error paths are precisely the branches tests usually skip. Between them the two show that the four tools partition the space rather than overlapping.
  2. Why does assert.equal(1, "1") pass?
    Because it uses loose equality. assert.equal is specified in terms of ==, so chapter 2's coercion applies inside your test framework: 1 and "1" are equal to it, as are 0 and false, and "" and 0. assert.deepEqual has the same problem recursively — measured, {a: 1} and {a: "1"} were accepted as equal. The strict variants, assert.strictEqual and assert.deepStrictEqual, both failed correctly on the same inputs. The practical rule is to use the strict forms exclusively and treat the loose ones as legacy; most style guides ban them outright. It matters most where a value crosses a boundary that stringifies — an id from a URL parameter, a number from a form field — which is exactly where a test would otherwise be your last chance to notice.
  3. assert(somePromise) — what is being asserted?
    That a promise object is truthy, which it always is. The assertion is about the wrapper rather than the value inside it, so it passes for a promise that resolves to false, for one that is still pending, and for one that rejects — measured, it passed. The intended assertion was almost certainly about the resolved value, which requires awaiting: assert.strictEqual(await p, expected), with the test function marked async. This is chapter 2's falsy list showing up in a new place — the only falsy values are false, 0, -0, 0n, "", null, undefined and NaN, so every object, including every promise, every array and every empty object, is truthy. A bare assert(x) on anything that might be an object is nearly always a mistake.
  4. Why is a test whose assertions are all inside a loop suspicious?
    Because if the collection is empty the loop body never runs and the test passes having asserted nothing — measured, [].forEach(() => assert.fail()) passes. That is a realistic shape: a test that fetches some items, filters them, and asserts something about each survivor will pass silently on the day the filter matches nothing, which is often the day the bug arrived. The fix is to assert the count first — assert.strictEqual(items.length, 3) — before asserting anything about the contents, so an empty result is a failure rather than a vacuous success. The general principle is that a test should be impossible to pass by doing nothing, and the ten-second check is to break the code under test and confirm the test fails. If it does not, it was never testing what you thought.
  5. A floating promise rejection failed the test run even though every assertion held. Good or bad?
    Good, and better than I expected. The function returned the right answer, both assertions passed, and Node's runner still failed the run because it attributes the unhandled rejection to the test — measured. That is the right behaviour: an unhandled rejection is a real defect, it would terminate the process in production, and a test suite that ignores it hides exactly the class of bug chapter 15 warned about. The reason to know it explicitly is that runners differ: not all of them do this, and some report it as a warning after the summary where nobody reads it. So check yours rather than assuming, and back it up statically — no-floating-promises catches the same defect without needing the code path to execute, which matters for the rejections your tests never trigger.
  6. You can add one tool to an untooled JavaScript project. Which?
    A linter, configured with the correctness rules rather than the style ones. no-undef catches the cold-branch name that survived three of four gates here; no-unused-vars catches the defect that survived all four; no-floating-promises catches rejections without needing the path to run; and eqeqeq with the "smart" option bans == while allowing chapter 4's genuinely useful x == null. It runs in seconds, needs no test-writing effort, and finds real bugs on the first run of a codebase that has never had one. A formatter is a close second because it is free and ends an argument, but it catches nothing. Tests are the highest-value tool and the highest-cost, so they are where to go second — starting with a regression test written at the moment you next fix a bug rather than a coverage push.
  7. How would you add type checking without adopting TypeScript?
    Put // @ts-check at the top of a file, or set "checkJs": true in a tsconfig.json, and write the types in JSDoc comments. It is the same checker doing the same analysis, with no build step, no syntax change and no file renaming — the code stays runnable JavaScript. That makes it adoptable one file at a time, and reversible, which matters when the argument against TypeScript is usually about the build rather than the types. You get most of the value: null checks, wrong argument types, misspelled properties, and editor autocomplete that actually knows your shapes. The limits are real but narrow — generics and conditional types are awkward in JSDoc, and some library types resolve less well. If the project later moves to TypeScript, the annotations largely transfer, so it is a step toward rather than an alternative.
