Chapter 1 · Orientation

How JavaScript runs

Almost every confusing thing about this language comes from its history: it shipped in ten days in 1995, it could never break the web, so nothing was ever removed. Instead the mistakes were fenced off — first by strict mode, then by modules. Knowing which fence you are standing behind explains most of what follows.

Four things called JavaScript

The specification — ECMAScript
The language itself: syntax, semantics, built-ins. Standardised as ECMA-262, revised every year since ES2015. It defines Array and Promise and nothing else.
The engine
An implementation: V8 in Chrome and Node, SpiderMonkey in Firefox, JavaScriptCore in Safari. Parses your source, compiles it, runs it, collects the garbage. Engines differ in speed, not in what the language means.
The runtime
The engine plus everything else you actually use. The browser gives you document, fetch and localStorage; Node gives you fs, process and require. None of these are JavaScript. That is why setTimeout is not in the spec and yet works everywhere.
The dialect you are writing in
Sloppy script, strict script, or ES module — three different sets of rules, chosen by a directive, a file extension, or a <script> attribute. This is the one people do not realise they are choosing.
Why nothing is ever removed

The web has no deployment. A page written in 1997 is still expected to load, so any change that breaks existing code is off the table permanently — there is no version 2 of the web to migrate to. Every questionable decision from the first ten days is therefore still in the language, and always will be. What the committee can do is add opt-in modes where the old behaviour is replaced, which is exactly what strict mode and modules are. So the language you write today is not smaller than the 1995 one; it is the 1995 one with two fences inside it, and your job is to stay on the right side of both.

What strict mode changes

Six behaviours, both ways
The first two are the ones that cost real money
A typo becomes a global variable
x = 1 with no declaration creates a property on the global object and reports typeof x === "number". Strict mode throws ReferenceError: x is not defined. One misspelled name, and sloppy mode silently invents a variable that every other file can see.
Writing to a frozen object does nothing
Object.freeze({a:1}) then o.a = 2 leaves a as 1, with no error at all. Strict mode raises TypeError: Cannot assign to read only property. The sloppy version is worse than a crash, because the code carries on believing the write happened.
Three become syntax errors
Duplicate parameter names, delete on a bare variable, and octal literals such as 0755 are all accepted sloppy — 0755 quietly evaluates to 493 — and rejected at parse time under strict.
And this stops being the global object
In a plain function call, sloppy this is the global object and strict this is undefined. Chapter 7 is entirely about the consequences.

A script and a module are different languages

The same four lines, saved as .js and as .mjs, do not behave the same way. This is not a Node quirk — a <script> and a <script type="module"> differ identically in the browser.

The same file, two dialects
Modules are strict whether you ask or not
how you end up in each dialect
// sloppy script — the 1995 rules
<script src="old.js"></script>          // browser
node old.js                              // Node, .js with no "type" in package.json

// strict script — same rules, fences up
"use strict";                            // must be the FIRST statement in the file
                                          // or the first in a function body

// ES module — strict, always, plus its own scope and deferred execution
<script type="module" src="app.js"></script>
node app.mjs                             // or .js with "type": "module"
"use strict" in the wrong place does nothing

It is a string literal, so putting it anywhere except the first statement of a file or function body makes it an expression that is evaluated and discarded — no error, no strictness. The classic failure is concatenating files during a build: if a sloppy file lands first, the strict directive from the second file is no longer at the top and silently stops applying to everything. Two things make this a non-issue today. Bundlers work on modules, and a module is strict regardless. And a linter will flag a misplaced directive. If you are writing new code in modules, you never need to type "use strict" again — it is already on.

Check yourself

Self-check

  1. Is setTimeout part of JavaScript?
    No. It is not in the ECMAScript specification at all — it comes from the runtime. The browser defines it in the HTML specification, and Node defines its own compatible version, which is why it works everywhere and behaves slightly differently in each. The same is true of console, fetch, document, localStorage, process and require: all runtime, none language. The distinction matters for two practical reasons. It tells you where to look when something behaves oddly — a setTimeout question is answered by the HTML spec or the Node docs, never by ECMA-262. And it tells you what will actually port: code using only language features runs in any JavaScript environment, while anything touching the runtime has to be checked. The language itself is smaller than most people assume — roughly the built-ins you can list from memory, and nothing that talks to the outside world.
  2. What happens to x = 1 when x was never declared?
    In sloppy mode it creates a property on the global object, so typeof x reports "number" and every other file in the program can see it. In strict mode it throws ReferenceError: x is not defined. This is the single most valuable thing strict mode does, because the sloppy behaviour turns a typo into a working program with a hidden global — a bug that surfaces much later, in a different file, as a mysterious value appearing from nowhere. The related case is equally bad and less known: assigning to a property of a frozen object silently does nothing in sloppy mode, so Object.freeze({a:1}) followed by o.a = 2 leaves a at 1 with no error, and the surrounding code carries on believing the write succeeded. Strict mode makes that a TypeError. Both failures share a shape worth recognising: sloppy mode's habit is to do something plausible rather than complain.
  3. You add "use strict" to a file and nothing changes. Why might that be?
    Three possibilities. It is not the first statement — the directive only applies when it is the very first statement of a file or of a function body, and anywhere else it is just a string expression that is evaluated and thrown away, with no error to tell you. A build step concatenated your file after a sloppy one, which has the same effect and is the classic version of this bug. Or the file is already an ES module, in which case strict mode was on before you typed anything. That last case is now the common one: any .mjs file, any .js file in a package with "type": "module", and any <script type="module"> is strict by specification and cannot be made sloppy. So in new code the directive is redundant, and the reason to understand it is to read older files correctly rather than to write it.
  4. The same file behaves differently as .js and .mjs. Give two ways.
    Measured, there are three. Top-level this is module.exports in a CommonJS script and undefined in an ES module — so any code doing this.something at the top level breaks on conversion, and top-level this is undefined in browser modules too. Strict mode is off in the script and on in the module, with everything that follows from the previous answers. And an implicit global assignment is allowed in the script and throws ReferenceError in the module, which is a consequence of the second. What does not differ is function hoisting: calling a function declaration before its declaration works in both, because hoisting is a property of the language rather than of the dialect. That is worth knowing because hoisting is often mentioned in the same breath as these differences, and it is not one of them — chapter 3 takes it apart properly.
  5. Why can the committee not simply remove the bad parts?
    Because there is no deployment step for the web and no version to migrate to. A page published in 1997 is still expected to load in a browser released this year, so a change that breaks existing code breaks the web permanently — and unlike a library, nobody can be asked to upgrade. That constraint is absolute and it explains the shape of the whole language: typeof null === "object", == coercion, var hoisting and automatic semicolon insertion are all still here because removing them would break real pages. What the committee can do instead is add opt-in modes where the old behaviour is replaced, which is precisely what strict mode and modules are, and add new constructs alongside the old ones — let beside var, === beside ==. So the practical reading is that the language only ever grows, and learning it means learning which of two or three ways to do something is the current one.
  6. An octal literal 0755 evaluates to what, and why does that matter?
    493 in sloppy mode, because a leading zero on a numeric literal historically meant base 8 — so 0755 is 7×64 + 5×8 + 5. It matters because it is silent: nothing warns you, and the number is simply wrong by a factor you would not predict. The classic bite is copying a Unix file mode or a zero-padded identifier such as 012 straight into source, where it becomes 10 rather than 12. Strict mode rejects it as a SyntaxError at parse time, which is the right outcome, and modern code that genuinely wants base 8 writes 0o755 explicitly. The general lesson is the same one as frozen objects and implicit globals: sloppy mode's failure style is to produce a plausible wrong answer rather than to stop, and almost every one of those cases has a strict-mode version that stops.
  7. Which fence should new code be behind, and what does that cost?
    Modules, which gives you strict mode for free and adds proper scoping, static analysability and real imports. The cost is real but small and mostly historical. Modules are deferred rather than executed immediately, so timing relative to page parsing differs. They are always fetched with CORS in the browser, which surprises people loading from file://. They cannot use require or __dirname without shims in Node, though import.meta covers the common needs. And mixing them with CommonJS dependencies is the one genuinely awkward area, which chapter 16 covers. Against that, everything in this chapter that strict mode fixes is fixed automatically, the tooling assumes modules, and both bundlers and Node treat them as the default path. For new code the decision is not close; the reason to know the older dialects is that you will read them.
