Operators and equality

There are four equality algorithms in JavaScript and you use all four, usually without noticing — because Array.prototype.includes and Array.prototype.indexOf quietly use different ones. This chapter puts them side by side, then covers the two operators that fixed the language's most persistent annoyances.

Four equality algorithms

Nine pairs, four algorithms
Only two pairs make all four disagree
The four differ on exactly two pairs
NaN against itself, and 0 against -0. Every other pair gets the same answer from ===, Object.is and SameValueZero. All the apparent complexity is those two values.
Object.is is === with both corrected
It says NaN is itself and 0 is not -0. That is the whole difference — it is not a deep comparison and does nothing for objects.
SameValueZero is Object.is that treats -0 as 0
You cannot call it directly; it is the algorithm behind includes, Map keys and Set members. It is the most practical of the four, because it treats NaN sensibly without splitting the two zeros.
Which is why includes and indexOf disagree
[NaN].includes(NaN) is true and [NaN].indexOf(NaN) is -1. They differ on exactly one value, and this is the reason includes was added.
javascript — where each one is actually used
a == b            // loose. Only worth writing as `x == null` — chapter 2
a === b           // strict. Your default, everywhere
Object.is(a, b)   // when NaN or -0 genuinely matter. Rare, and precise

// SameValueZero — no operator, but you use it constantly:
arr.includes(v)                // finds NaN;  indexOf does not
new Set([NaN, NaN]).size       // 1
new Set([0, -0]).size          // 1  — the two zeros are one member
map.has(key)  ·  map.get(key)

// and the one that is none of the four:
{a:1} === {a:1}   // false. Objects compare by identity, always.
                  // There is no value-equality operator in the language

Nullish, not falsy

?? against ||
They differ on four of eight, and every one is a real bug
|| asks "is this falsy", ?? asks "is this absent"
They agree on null, undefined, [] and 'x', and disagree on 0, '', false and NaN — four of eight. Each of those four is a legitimate configured value that || silently discards.
So cfg.port || 8080 is a bug waiting for port 0
And cfg.prefix || 'app' for an empty prefix, and cfg.retries || 3 for zero retries, and opts.enabled || true for a flag you wanted off. ?? is the correct default operator.
Mixing ?? with || is a SyntaxError
a ?? b || c does not parse. The committee refused to invent a precedence between them and requires parentheses instead — one of very few places the language declines to guess.
Optional chaining short-circuits the whole rest of the chain
o.missing?.deep.deeper is undefined, not an error, because everything after the ?. is skipped. And o.nope?.(sideEffect()) never evaluates its argument — measured, the counter stayed at 0.
javascript
const port = cfg.port ?? 8080;          // 0 survives. The right default
const name = user?.profile?.name;       // undefined rather than a TypeError
const first = list?.[0];                // index access
onChange?.(value);                      // call only if it exists

cfg.retries ??= 3;                      // assign only if null/undefined
flags.debug ||= isDev;                  // assign if falsy
user.name &&= user.name.trim();         // assign only if truthy — no crash on undefined

// the trap: ?. guards ONE link, not the whole expression
a?.b.c        // safe if a is nullish; STILL throws if a.b is nullish
a?.b?.c       // what you probably meant
Do not reach for ?. everywhere

It is easy to sprinkle optional chaining across a whole expression to stop a crash, and that converts a loud failure into a silent undefined flowing downstream — which is exactly the failure mode chapter 1 spent its time arguing against. Use it where a value is genuinely optional, such as a response field that may be absent or a callback prop that may not be passed. Where a value should always be there, let the TypeError happen: it points at the real problem, which is that something upstream returned nothing. A useful smell is a?.b?.c?.d — four optional links usually means the shape is not actually understood, and the fix is to validate the object once at the boundary rather than defend at every access.

Check yourself

Self-check

  1. Name the four equality algorithms and the two pairs that separate them.
    Loose equality (==), strict equality (===), Object.is, and SameValueZero. The last has no operator — it is the algorithm behind includes, Map keys and Set members. Measured across nine pairs, the last three differ on exactly two: NaN against itself, where === says false and both others say true; and 0 against -0, where === and SameValueZero say true and Object.is says false. Every other pair gets identical answers from all three, so the apparent complexity is entirely those two values. The clean way to hold it: Object.is is === with NaN and -0 both corrected, and SameValueZero is Object.is with the -0 correction dropped — which makes it the most practical of the four, since NaN comparing equal to itself is nearly always what you want and the two zeros being separate nearly never is.
  2. [NaN].includes(NaN) is true and [NaN].indexOf(NaN) is -1. Why?
    They use different algorithms. indexOf predates the others and is specified in terms of ===, which says NaN is not equal to itself — so it can never find one. includes was added later and uses SameValueZero, which treats NaN as equal to itself. They differ on exactly that one value and agree on everything else, and removing that gap was a large part of why includes was added at all. The same algorithm governs Set and Map, so new Set([NaN, NaN]).size is 1 and new Set([0, -0]).size is also 1 — the two zeros are a single member. The practical rule is to use includes when you want to know whether a value is present and indexOf only when you need the position, and to remember that any array that might contain NaN makes them disagree.
  3. const port = cfg.port || 8080 — what breaks, and what else shares the bug?
    A configured port of 0 becomes 8080, because || tests falsiness rather than absence. Measured against eight values, ?? and || agree on null, undefined, [] and 'x' and disagree on 0, '', false and NaN — four of eight, and every one of those four is a value someone might legitimately configure. The same shape appears as cfg.prefix || 'app' discarding a deliberately empty prefix, cfg.retries || 3 turning zero retries into three, and opts.enabled || true making a flag impossible to switch off. ?? falls back only for null and undefined, which is the same predicate as chapter 2's x == null and is exactly the question a default is asking. Use || only when you really do mean "falsy", which is rarer than the habit suggests.
  4. Why is a ?? b || c a syntax error?
    Because the committee declined to define a precedence between ?? and the logical operators, and made the ambiguous form illegal instead. There is no obvious right answer — reading it as (a ?? b) || c and as a ?? (b || c) both look defensible, and either choice would silently do the wrong thing for people who assumed the other. So you must parenthesise, and the parentheses then say which you meant. This is worth noticing as a rare piece of language design: almost everywhere else JavaScript's instinct is to guess and carry on — coercion, implicit globals, silent writes to frozen objects — and here it refuses. It is also a small, useful signal when you meet it in your own code, because hitting this error usually means the expression was doing two different kinds of defaulting at once and would read better split across two lines.
  5. What exactly does a?.b.c guard?
    Only the access of b on a. If a is null or undefined, the whole expression short-circuits to undefined and .c is never evaluated — that part is the good news, and it is why o.missing?.deep.deeper is undefined rather than an error. But if a exists and a.b is nullish, .c throws a TypeError as usual, because there is no ?. on that link. You almost always meant a?.b?.c. Two related facts worth having. The short-circuit is genuinely lazy, so o.nope?.(sideEffect()) never evaluates its argument — measured, the counter stayed at 0. And the temptation to spray ?. across an expression to stop a crash converts a loud failure into a silent undefined travelling downstream, which is worse; where a value should always exist, let it throw.
  6. How do you check that two objects have equal contents?
    None of the four algorithms will do it — all of them compare objects by identity, so [] === [], Object.is([], []) and [] == [] are all false, and two arrays are equal only when they are the same array. The language has no value-equality operator for objects and no plans for one. You write a function, or use one from a library. The quick JSON.stringify comparison is wrong often enough to be worth avoiding: it is sensitive to key order, drops undefined values and functions, converts dates to strings, cannot represent NaN, and throws on cycles. Two adjacent tools are worth knowing at the same time — structuredClone(v) makes a genuine deep copy that handles cycles, dates, maps and sets, and it is built in, so the old JSON.parse(JSON.stringify(v)) cloning trick has the same list of flaws and no longer has an excuse.
  7. When is Object.is the right choice?
    When the difference between NaN and -0 genuinely matters, which is rare and specific. The realistic cases are numerical code where -0 carries meaning — it records the direction from which a value approached zero, so Object.is(x, -0) can distinguish a small negative result that underflowed from a small positive one — and equality helpers where you want a total ordering with no value unequal to itself, which is why React's state comparison and several immutability libraries use it. For everyday code === is right and Object.is adds a lookup for no benefit. The one genuinely common need it addresses, "is this NaN", is better expressed as Number.isNaN(v), which says what you mean and does not require the reader to remember which of the four algorithms this one is.
