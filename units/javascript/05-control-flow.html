Control flow and errors

JavaScript has seven ways to walk an array and they do not agree with each other. Given one array with a gap and a stray property, they produce three genuinely different answers — which is worth knowing before you pick one out of habit.

— words— min read2 interactivesNeeds: chapters 02, 03

Seven loops, three answers

const a = [1, , 3]; a.extra = "x";
One hole, one extra property — and every form treats them differently
Three answers to "what is in this array"
Index and iterator forms report the hole as undefined — 1 undefined 3. The callback methods skip it — forEach gives 1 3. And for…in gives string keys including the extra property — "0" "2" "extra".
a.length is 3 throughout
Length counts the hole; forEach and map do not visit it. So a loop that reports fewer items than length is not a bug in your code.
for…in yields strings, and walks the prototype chain
"0", not 0 — so k + 1 gives "01". And it includes inherited enumerable properties: over an object with a prototype it produced mine, inherited where Object.keys gave only mine. That is the real reason it is discouraged.
map keeps the slot but skips the callback
[1,,3].map(() => 9) gives [9, <hole>, 9] — same length, hole preserved. Serialised to JSON it shows as null, which is how the gap leaks into an API response.
Which to reach for

for…of for values, because it works on anything iterable — arrays, strings, Map, Set, generators — and supports break, continue and await. The array methods when you are transforming rather than iterating, since map, filter and reduce say what they do. Object.entries with for…of for object properties, never for…in. And an index loop only when you genuinely need the index or need to skip around. Holes barely arise in modern code — they come from new Array(3), delete arr[1] and array literals with double commas, all of which are worth avoiding for exactly this reason; Array.from({length: 3}) gives a dense array of undefined instead.

What finally does to control flow

Six shapes of try/catch/finally
The second and third are the ones that lose data
finally always runs, before anything leaves
Including before an exception propagates: the "throw, no catch" case printed finally ran and then the error escaped. That is what makes it right for cleanup.
But a control transfer inside it replaces whatever was happening
return "finally" overrides the try block's return. Worse, it swallows an exception in flight — the throw case returned "finally" and the error vanished entirely.
break and continue do it too
A break in a finally inside a loop discarded a pending return, and the function carried on to return "loop finished".
So: never transfer control out of finally
Use it only for cleanup — closing, releasing, restoring. Every linter has a rule for this (no-unsafe-finally) and it is worth enabling.
javascript — the Error features most code is not using
class ValidationError extends Error {
  constructor(msg, options) {
    super(msg, options);            // pass options through for `cause`
    this.name = "ValidationError";  // otherwise it reports "Error"
  }
}

try { JSON.parse(raw); }
catch (e) {
  throw new ValidationError("config is invalid", { cause: e });   // ES2022
}
// e.cause is the ORIGINAL SyntaxError object — not a string. The whole chain
// survives into the log, and console.error prints it nested

try { risky(); } catch { retry(); }        // optional binding, if you ignore it

// throw anything, but don't: only Error has a stack
throw new Error("no");   // ✓
throw "no";              // ✗ no stack, and `e.message` is undefined downstream

// several failures at once — Promise.any and Promise.allSettled produce these
throw new AggregateError([e1, e2], "all providers failed");
instanceof on a subclassed Error can lie

Two situations break it. If your build targets ES5, a class extending a built-in is transpiled into a function-and-prototype arrangement that does not properly set the prototype chain, so e instanceof ValidationError comes out false — the historical fix is Object.setPrototypeOf(this, new.target.prototype) in the constructor, and the modern fix is to stop targeting ES5. The other is realms: an error thrown inside an iframe, a worker or a Node vm context is an instance of that realm's Error, so instanceof fails across the boundary. When either applies, check a property you control — a code string or e.name — rather than the prototype chain. Setting this.name explicitly is worth doing regardless, because without it every subclass reports "Error" in logs.

Check yourself

Self-check

  1. Given const a = [1, , 3], what do for…of and forEach each report?
    for…of gives 1, undefined, 3 and forEach gives 1, 3 — it skips the hole entirely. The array's length is 3 in both cases, so forEach visits fewer items than the length reports, which looks like a bug and is not. The distinction is that a hole is a missing property, not a property whose value is undefined: index and iterator access find nothing there and yield undefined, while the callback methods check whether the index exists before calling you. map splits the difference — it skips the callback but preserves the slot, so [1,,3].map(() => 9) is [9, <hole>, 9], which serialises to JSON as [9,null,9] and is how a gap leaks into an API response. Holes come from new Array(3), delete arr[1] and double commas in a literal; Array.from({length: 3}) gives a dense array instead.
  2. Why is for…in discouraged for arrays and objects alike?
    Two reasons, and the second is the serious one. It yields string keys, so k + 1 on index 0 gives "01" rather than 1, and it includes non-index properties — over an array carrying an extra property it produced "0" "2" "extra". More importantly it walks the prototype chain, visiting every enumerable inherited property: over an object created with Object.create(base) it gave mine, inherited where Object.keys gave only mine. So anything added to a prototype anywhere in your program — by a library, by an old polyfill — silently appears in your loop. That is why for…in code is so often wrapped in hasOwnProperty checks. The modern answer is to not need the guard: Object.keys, Object.values or Object.entries are own-only by definition, and for…of over Object.entries(obj) reads better than either.
  3. What does a return inside finally do?
    It replaces whatever the function was doing, including an exception in flight. Measured: a function whose try block returns "try" and whose finally returns "finally" returns "finally"; and a function whose try block throws and whose finally returns "finally" also returns "finally" — the error disappears completely, with nothing logged and nothing thrown. That is a silent data-loss bug of exactly the kind chapter 1 kept finding in sloppy mode, except this one is not fixed by strict mode. break and continue behave the same way: a break in a finally inside a loop discarded a pending return and let the function fall through. The rule is simple — use finally only for cleanup, never to produce a value or transfer control — and no-unsafe-finally enforces it.
  4. What does cause give you that a message string does not?
    The original error as a real object, with its own type, message and stack, rather than flattened into text. throw new ValidationError("config is invalid", { cause: e }) keeps e.cause pointing at the SyntaxError that JSON.parse threw, so the log shows both the high-level failure and the low-level one that caused it, and console.error prints the chain nested. The alternative people write — interpolating e.message into a new message — loses the type, the stack and any structured fields, which is precisely the information you need at three in the morning. Two things to pair with it. Set this.name in your subclass constructor, or every custom error reports "Error" in logs. And remember to pass the options object through to super, since super(msg) alone silently drops the cause — a mistake that looks correct in review.
  5. Why might e instanceof MyError be false for something you just threw?
    Two causes. If the build targets ES5, a class extending a built-in like Error is transpiled into a function-and-prototype arrangement that cannot properly establish the chain, so the check fails even though the code looks right — the historical workaround is Object.setPrototypeOf(this, new.target.prototype) in the constructor, and the real fix is to stop targeting ES5, which almost nothing needs now. The other is realms: an error created inside an iframe, a Web Worker or a Node vm context is an instance of that realm's Error constructor, which is a different object from yours, so instanceof is false across the boundary for the same reason [] instanceof Array fails across frames. In both cases the robust check is a property you control — a code string, or e.name — rather than the prototype chain.
  6. Why should you never throw a string?
    Because it carries no stack. The single most valuable thing in a caught error is where it came from, and only an Error instance has a stack property — a thrown string gives you the text and nothing else, so the log tells you what went wrong and not where. It also breaks every downstream assumption: handlers reading e.message get undefined, e instanceof Error is false, and error-reporting services generally discard it. The same argument applies to throwing plain objects, which is common in older code that wanted structured fields — subclass Error and add the fields to the subclass instead, which gets you both. The one thing you cannot control is what libraries throw, so a top-level handler should cope with a non-Error arriving; wrapping it as new Error(String(e), { cause: e }) at the boundary is the tidy way to normalise.
  7. What is AggregateError for?
    Carrying several failures at once, in an errors array. The language produces one itself: Promise.any rejects with an AggregateError when every input promise rejected, because there is no single error to report. It is worth using in your own code wherever the same shape arises — validating a form and collecting every field error, trying several providers and failing when all of them fail, or processing a batch where some items failed and you want to report all of them rather than the first. The alternative most code writes, throwing on the first failure, hides everything after it and turns one debugging session into several. Chapter 15 covers the promise side, where Promise.allSettled gives you the same information in a form you can inspect rather than throw, and choosing between the two is mostly a question of whether partial success is acceptable.
