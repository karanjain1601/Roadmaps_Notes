Arrays and iteration

Eight of the seventeen common array methods modify the array you called them on, and most of those also return it — which is what makes const sorted = list.sort() such a reliable source of confusion. Since ES2023 there is a copying variant of each, so the confusion is now avoidable.

Mutate or copy

Seventeen methods on [3, 1, 2]
Look at what the mutating ones return
Eight of seventeen mutate
push, pop, shift, unshift, splice, sort, reverse, fill. There is no naming pattern that tells you — you either know or you check.
Three of them return the same array they modified
sort, reverse and fill. So const b = a.sort() gives you two names for one array, and mutating b later changes a. That is the classic bug.
The others return something unrelated
push returns the new length, pop the removed element, splice an array of what it removed. Chaining off them almost never does what it looks like.
ES2023 added a copying variant for each
toSorted, toReversed, toSpliced and with — all measured as leaving the original untouched and returning a new array. Prefer them, and reach for the mutating form deliberately.
javascript
const sorted = list.toSorted((a, b) => a - b);   // ✓ list untouched
const sorted = [...list].sort((a, b) => a - b);  // ✓ the pre-2023 idiom
const sorted = list.sort((a, b) => a - b);       // ✗ list is now sorted too

arr.with(0, 9)          // a copy with index 0 replaced — no splice arithmetic
arr.at(-1)              // the last element. arr[-1] is undefined, it is a property
arr.flat(Infinity)      // fully flatten
arr.flatMap(f)          // map then flatten one level — good for expand-or-drop

Array.from({length: 3}, (_, i) => i)   // [0,1,2] — dense, unlike new Array(3)
Object.groupBy(items, x => x.kind)     // ES2024, replaces the reduce idiom

sort

The default comparator is not the one you want
The first row is the one that catches people
The default comparator converts every element to a string
So [1, 10, 2, 20].sort() returns [1, 10, 2, 20] — already in order, as strings. And [10, 9, 1].sort() gives [1, 10, 9], which looks like a bug and is the specification.
Always pass a comparator for numbers
(a, b) => a - b. The contract is: negative if a comes first, positive if b does, zero if equal.
A comparator returning a boolean is broken
(a, b) => a > b yields true or false, which coerce to 1 and 0 — so it can never say "a comes first", and the result is engine-dependent. Measured, [3,1,2] came back unchanged.
Sorting is stable, guaranteed since ES2019
Equal elements keep their relative order — measured, sorting a,b,c,d by group gave bdac. That is what makes multi-pass sorting work: sort by the minor key, then the major one.
Default string sorting is also wrong for text

The default compares UTF-16 code units, so ['b', 'a', 'B'].sort() gives ["B", "a", "b"] — every capital before every lowercase, because B is 66 and a is 97. Accented letters land after z for the same reason, so a list of French or Turkish names comes out in an order no reader recognises. (x, y) => x.localeCompare(y) gives ["a", "b", "B"] and respects the locale's actual collation rules. For long lists build the collator once — const c = new Intl.Collator("fr"); arr.sort(c.compare) — since localeCompare constructs one per call and that dominates the runtime. Check yourself

Self-check

  1. const sorted = list.sort() — name two things wrong with this line.
    First, sort mutates: list is now reordered, so any other code holding a reference sees a different array than it did. Second, sort returns the same array, so sorted and list are two names for one object and the const gives no protection at all — mutating sorted later changes list too. Third, if the elements are numbers, the default comparator is wrong: it converts to strings, so [1, 10, 2, 20] comes back unchanged and [10, 9, 1] becomes [1, 10, 9]. The fixed version is const sorted = list.toSorted((a, b) => a - b), or [...list].sort((a, b) => a - b) if you need to support runtimes before ES2023. sort, reverse and fill are the three methods that both mutate and return the same array, and all three have this shape.
  2. Why does [10, 9, 1].sort() give [1, 10, 9]?
    Because the default comparator converts each element to a string and compares those. As strings, "1" comes before "10" comes before "9", since comparison is character by character and "1" is less than "9" at the first position. It is not a bug — it is what the specification says, and it exists because sort predates any notion of typed collections and had to do something defensible for mixed arrays. The companion case is [1, 10, 2, 20].sort(), which returns the array completely unchanged and therefore looks like it worked. That is the more dangerous one, because a test written against sorted-looking input passes. The rule is simply to always pass a comparator when sorting numbers, and to remember that the default is equally wrong for text — it compares UTF-16 code units, so every capital sorts before every lowercase.
  3. What is wrong with (a, b) => a > b as a comparator?
    It returns a boolean, and the contract needs three outcomes. A comparator must return a negative number when a should come first, a positive one when b should, and zero when they are equal. A boolean coerces to 1 or 0, so it can express "b comes first" and "they are equal" but never "a comes first" — the negative case is unreachable. What happens next depends on the engine's algorithm, so the result is not merely wrong but unpredictable across runtimes and array sizes; measured here, [3,1,2] came back completely unchanged. It is an easy mistake because the expression reads like a plain-English comparison and works in languages taking a boolean "less than" predicate. For numbers write a - b; for anything else, a < b ? -1 : a > b ? 1 : 0, or localeCompare for strings.
  4. What does stability mean for a sort, and what is it for?
    Elements the comparator calls equal keep their original relative order. Measured, sorting four items a, b, c, d by a group key where b and d share one group and a and c the other gave bdac — within each group the original order survived. It has been guaranteed by the specification since ES2019; before that engines differed, and V8 was unstable for arrays above a size threshold, which produced wonderfully intermittent bugs. What it is for is multi-key sorting without writing a compound comparator: sort by the minor key first, then by the major one, and the minor ordering is preserved inside each major group. That is often clearer than a comparator with a chain of tie-breaks, and it composes — three passes for three keys. The one caution is that it only holds for a single sorted array; re-sorting after a filter or a map that reorders gives no such guarantee.
  5. Which array methods mutate, and is there a pattern?
    Eight of the seventeen common ones: push, pop, shift, unshift, splice, sort, reverse and fill. There is no naming pattern that distinguishes them from the copying ones — slice copies and splice mutates, and nothing in either name says so. You either know the list or you check. Their return values are also inconsistent: push gives the new length, pop and shift the removed element, splice an array of what was removed, and sort, reverse and fill the same array back. So chaining off a mutating method almost never does what it looks like. Since ES2023 there is a copying counterpart for the reordering ones — toSorted, toReversed, toSpliced and with — all measured as leaving the original untouched, and worth defaulting to.
  6. What does arr.with(1, "x") do, and why is it useful?
    It returns a copy of the array with index 1 replaced by "x", leaving the original untouched. It is useful because the alternative was genuinely awkward: either mutate (arr[1] = "x"), or spread with splice arithmetic ([...arr.slice(0, 1), "x", ...arr.slice(2)]), which is easy to get off by one and hard to read. That matters most in code that must not mutate — React state, anything with change detection, or a reducer — where the mutating version produces a bug that is invisible until a re-render does not happen. It also accepts negative indices, so arr.with(-1, "x") replaces the last element. Its siblings are worth knowing together: at(-1) for the last element, since arr[-1] is a property lookup that gives undefined, and toSpliced for insertion and removal without mutation.
  7. Why is localeCompare the wrong default for a large list?
    Because it constructs a collator on every call, and a sort makes O(n log n) calls — so the setup cost dominates and a large list can be dramatically slower than it needs to be. The fix is to build the collator once and reuse its compare function: const c = new Intl.Collator("fr"); arr.sort(c.compare). That is the same result with the setup paid once. Worth being clear that localeCompare is still the right semantics — the default comparator compares UTF-16 code units, so ['b','a','B'].sort() gives ["B","a","b"] with every capital before every lowercase, and accented characters sort after z, which produces an order no reader of the language recognises. The choice is not between correct and fast; it is between constructing a collator once and constructing it n log n times. Chapter 12 covers Intl more fully.
