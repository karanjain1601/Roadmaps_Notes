Chapter 6 · The language core

Functions and closures

Functions are ordinary values that happen to be callable, which is the single most important thing about the language. This chapter covers what a parameter list really declares, one place JavaScript is cleanly better than Python, and the five ways an arrow is not simply a shorter function.

What a parameter list declares

Six signatures
Try the one with a default in the middle
fn.length counts parameters before the first default or rest
function (a, b = 1, c) reports 1, not 3 — so length is the number of required leading parameters, which is what a library dispatching on arity actually wants to know.
A default in the middle is legal and awkward
To supply c you must pass something for b, and passing undefined explicitly triggers the default. Put defaults last, or take an options object.
Only undefined triggers a default
null does not. f(null) gives you null, not the default — which is the same nullish-versus-falsy distinction chapter 4 measured, applied to parameters.
Rest and destructuring both count as one
function (a, ...rest) is 1, and function ({a, b}) is 1 — a destructuring pattern is a single parameter however many names it binds.
One place JavaScript is cleanly better than Python

Default parameters are expressions evaluated at call time, freshly, every call. So function push(v, into = []) { into.push(v); return into; } called three times gives [[1], [2], [3]] — three separate arrays. Python evaluates its defaults once at definition time, which produces its most famous beginner bug, where a default list accumulates across calls. JavaScript simply does not have that bug. The same mechanism means a default can be any expression and can reference earlier parameters: function area(w, h = w) works, and area(3) gives 9. Referencing a later parameter is a ReferenceError, because the parameters are initialised left to right and the later one is still in its temporal dead zone — chapter 3's rule, reaching into the parameter list.

Five things an arrow is not

Arrow against function
arguments gives three different answers
An arrow has no this, no arguments, no prototype
It cannot be called with new (TypeError), and being an expression it is not hoisted. Five differences, and only the first is usually why people reach for one.
arguments in an arrow is not an error — it is a free variable
It resolves up the scope chain like any other name, so the answer depends entirely on what encloses it. Inside outer(1,2,3) it gives 3. At CommonJS top level it gives 5. In an ES module it is a ReferenceError.
Five, because Node wraps every CommonJS module in a function
function (exports, require, module, __filename, __dirname) — so an arrow at the top of a .js file really is inside a five-parameter function. Exactly the mechanism behind this, which chapter 7 takes apart.
Names are inferred from the binding
const named = () => {} has name === "named", and { m: () => {} } gives "m". Only a truly anonymous arrow has an empty name, which is why stack traces are usually still readable.
javascript — closures, and what they are for
function counter() {
  let n = 0;                       // not reachable from outside. Genuinely private —
  return {                          // no convention, no underscore, no proxy
    inc: () => ++n,
    get value() { return n; }
  };
}
const a = counter(), b = counter();
a.inc(); a.inc();                   // a.value === 2, b.value === 0 — separate scopes

// each CALL creates a new scope; the closures from one call share it
// (that sharing is exactly chapter 3's loop bug, used deliberately)

const add = x => y => x + y;        // partial application
const add5 = add(5);

// and the everyday one people forget is a closure at all:
button.addEventListener("click", () => save(draft));   // captures `draft`
A closure keeps its whole scope alive

The captured binding cannot be collected while the closure is reachable — that is the point of it. The cost is that a small closure can hold a large object alive indefinitely if they share a scope: a handler that only needs an id, defined in a function that also loaded a megabyte of response data, keeps the whole thing in memory for as long as the handler is attached. Engines are cleverer than they used to be and often keep only the variables actually referenced, but it is not something to rely on across engines. Two habits help: extract the value you need before creating the closure, so it captures a string rather than the object it came from; and remove listeners and clear timers when the thing that owns them goes away. Chapter 18 measures this with WeakRef and --expose-gc.

Check yourself

Self-check

  1. What does fn.length report for function (a, b = 1, c) {}?
    1. The length property counts parameters before the first one with a default or a rest element, so it is the count of required leading parameters rather than of parameters. function (a, ...rest) is also 1, and function ({a, b}) is 1 too, because a destructuring pattern is one parameter however many names it binds. This matters mainly to library code that dispatches on arity — a test framework deciding whether your callback wants a done argument, for instance — and it is why such libraries behave oddly when you add a default to a parameter they were counting. The signature in the question is worth avoiding for a separate reason: with a default in the middle, supplying c requires passing something for b, and the only way to take the default is to pass undefined explicitly. Put defaults last, or take an options object.
  2. Does JavaScript have Python's mutable-default-argument bug?
    No, and the reason is a genuine design difference. JavaScript evaluates default parameters as expressions at call time, freshly, on every call — so function push(v, into = []) { into.push(v); return into; } called three times gives [[1], [2], [3]], three separate arrays. Python evaluates its defaults once when the def executes, so the same shape there accumulates into one shared list, which is its most famous beginner trap. The same mechanism gives JavaScript two abilities Python lacks here: a default can be any expression, including a function call or a counter increment, and it can reference earlier parameters, so function area(w, h = w) works and area(3) is 9. Referencing a later parameter throws ReferenceError, because parameters initialise left to right and the later one is still in its temporal dead zone.
  3. Name three ways an arrow function differs from a function declaration.
    There are five. It has no this of its own, inheriting the enclosing scope's — the reason most people reach for one. It has no arguments of its own. It has no prototype property. It cannot be called with new, which throws TypeError. And being an expression rather than a declaration it is not hoisted, so calling it before its line gives undefined and then TypeError: f is not a function — chapter 3's function-expression trap. Worth adding that it is not merely "shorter syntax": the first two are lexical inheritance rather than absence, which the next answer draws out. And names are still inferred from the binding, so const named = () => {} reports name === "named" and stack traces stay readable — the empty name only appears for a genuinely anonymous arrow passed straight as an argument.
  4. What is arguments.length inside an arrow function?
    It depends on what encloses the arrow, because an arrow does not bind arguments at all — the name is resolved up the scope chain like any other free variable, exactly as this is. Measured, that gives three different answers. Inside a function called as outer(1,2,3) it is 3, the enclosing function's arguments. At the top level of a CommonJS file it is 5, because Node wraps every module body in function (exports, require, module, __filename, __dirname) and the arrow is genuinely inside a five-parameter function. At the top level of an ES module it is a ReferenceError, since a module has no enclosing function. So the common phrasing "an arrow has no arguments" is close but misleading: it has no own arguments, and what it finds instead is often surprising. Use a rest parameter, which is clearer and works identically everywhere.
  5. Two calls to the same factory function — do the closures share state?
    No. Each call creates a new scope, so const a = counter(), b = counter() gives two independent counters: incrementing a twice leaves a.value at 2 and b.value at 0. Closures created within a single call do share that call's scope, which is what makes the factory pattern work — inc and the value getter are reading the same n. That sharing is exactly chapter 3's loop bug seen from the other side: there it was unwanted, here it is the entire point, and the mechanism is identical. It is also the cleanest way to get genuinely private state in JavaScript — n is unreachable from outside, with no naming convention and no proxy involved. Chapter 9's private class fields (#n) are the other way, and they are enforced by the language rather than by scope.
  6. Why can a small closure keep a large object in memory?
    Because a closure keeps its enclosing scope alive, not merely the variables it appears to use. If a function fetched a megabyte of response data into a local variable and then returned a tiny handler that only needs an id, the whole scope — response included — is reachable from that handler for as long as it is attached. Modern engines often optimise this by keeping only the variables actually referenced, but the behaviour varies and is not something to rely on across engines and build tools. Two habits avoid it. Extract the value before creating the closure, so it captures a string rather than the object the string came from. And detach what you attach: remove event listeners, clear intervals, and abort fetches when the owning component goes away, since an attached listener is a root that keeps everything behind it alive. Chapter 18 measures this directly with WeakRef and an exposed collector.
  7. When should you not use an arrow?
    Whenever the function needs its own this. Object methods written as arrows do not work — { v: 1, g: () => this.v } gives undefined, because the arrow inherits this from wherever the object literal was written, which is not the object. Prototype methods and class methods intended to be called on an instance have the same problem. So do DOM event handlers that expect this to be the element, and callbacks in libraries that deliberately invoke you with a bound this, such as some test and jQuery-era APIs. Constructors are out entirely, since new on an arrow throws. The positive rule is the useful one: reach for an arrow when you want the surrounding this — inside a method, in a callback, in a promise chain — and use a normal function when the caller decides this. Chapter 7 makes that precise.
