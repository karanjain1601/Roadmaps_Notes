this and binding

One rule explains all of it: this is decided by how a function is called, not by where it was written. The same function body gives four different answers depending on the call, which is why extracting a method breaks it and why arrows exist.

The call forms

One function, eight ways to call it
Only two rows differ between strict and sloppy
Four different answers from one function body
undefined plainly, the receiver as a method, the fresh instance under new, and whatever you supply with call or bind. Nothing about the function changed.
Only the receiverless rows differ between modes
A plain call and an extracted method give undefined under strict and globalThis under sloppy. Everywhere something did set a receiver, both modes agree — so strict mode does not change the rules, it removes a fallback.
Extracting a method loses its receiver
const f = obj.who copies the function, not the association. The dot in obj.who() is what supplies this, and taking the dot away takes it with you.
Class bodies are always strict
So an extracted class method throws TypeError: Cannot read properties of undefined — measured even inside a sloppy file. That is usually a better outcome than silently writing to the global object.
bind is permanent

Once bound, a function cannot be rebound. Measured: const once = bare.bind({tag:"first"}) then calling once(), once.call({tag:"second"}) and once.bind({tag:"third"})() gives first first first — both the later call and the second bind are ignored. This is by design, so that a bound callback cannot be hijacked by whoever invokes it, and it catches people who expect the last binding to win. It also means bind returns a new function each time, so el.removeEventListener("click", this.onClick.bind(this)) never removes anything — the function you pass to remove is not the one you added. Bind once and keep the reference.

Keeping the receiver

Five approaches, and what each costs
The last one always works — check whether it is shared
A prototype method is one function for every instance
p1.m === p2.m is true, and Object.hasOwn(p1, "m") is false — the function lives on the prototype and instances borrow it.
A class field arrow is a new function per instance
f1.m === f2.m is false, and it is an own property. That is what makes it immune to extraction, and it is also the cost.
So the choice is convenience against sharing
For a handful of long-lived objects, a field arrow is fine and removes a whole class of bug. For thousands of instances, or a class whose methods you want subclasses to override, keep methods on the prototype and bind at the boundary.
The arrow wrapper is usually the least surprising
onClick={() => this.save()} reads clearly, keeps the method on the prototype, and creates one closure per render rather than per instance.
javascript — where this actually bites
setTimeout(obj.tick, 100);            // ✗ extracted — loses obj
setTimeout(() => obj.tick(), 100);    // ✓ the call still has its dot

arr.map(obj.transform);               // ✗ same problem, quietly
arr.map(x => obj.transform(x));       // ✓
arr.map(obj.transform, obj);          // ✓ map/forEach/filter take a thisArg

el.addEventListener("click", obj.onClick);           // this becomes the ELEMENT
el.addEventListener("click", () => obj.onClick());   // ✓ unless you wanted the element

// and the one that looks fine and is not:
const { get } = someInstance;         // destructuring is extraction
get();                                // TypeError

Check yourself

Self-check

  1. State the rule for this in one sentence, then give the four outcomes.
    this is determined by how a function is called, not by where it was defined. Four outcomes follow. A plain call sets no receiver, so this is undefined in strict mode and globalThis in sloppy. A method call — a call with a dot — sets this to whatever was left of the dot. new sets it to the freshly created instance. And call, apply or bind set it to whatever you supply. Arrows are the exception that proves the rule: they have no this of their own, so the name resolves lexically to the enclosing scope's, and no call form can change it — which is exactly the same mechanism as arguments in chapter 6. Measured, the same one-line function body produced undefined, the receiver, the instance and the supplied object depending only on the call site.
  2. Why does setTimeout(obj.tick, 100) break?
    Because obj.tick evaluates to the function alone; the association with obj lives in the call, not in the function. Passing it to setTimeout means the timer eventually calls it with no receiver, so this is undefined in strict code and the timer object in sloppy Node code — either way not obj. The fix is to keep the dot at the moment of the call: setTimeout(() => obj.tick(), 100). The same shape appears constantly and is easy to miss — arr.map(obj.transform), promise.then(obj.handle), and destructuring, which is extraction with different syntax: const { get } = instance; get() throws for exactly this reason. Worth knowing that map, forEach, filter and friends accept a second thisArg argument specifically for this case, though an arrow is usually clearer.
  3. Can a bound function be rebound?
    No. Measured: binding to {tag:"first"} and then calling it directly, through call({tag:"second"}), and through a second bind({tag:"third"}) all gave first. The binding is permanent by design, so that a callback handed to someone else cannot have its receiver hijacked by whoever invokes it. Two practical consequences. Since a second bind is silently ineffective rather than an error, a rebinding bug shows up as the wrong data rather than a crash. And because bind returns a new function object every time it is called, el.removeEventListener("click", this.onClick.bind(this)) removes nothing at all — the function passed to remove is a different object from the one that was added. Bind once, store the result, and pass that same reference to both add and remove.
  4. What does a class field arrow cost?
    Sharing. A method declared normally lives on the prototype, so it is one function object for every instance — measured, p1.m === p2.m is true and Object.hasOwn(p1, "m") is false. A class field arrow is an own property created fresh in each constructor call, so f1.m === f2.m is false and every instance carries its own function. That is precisely what makes it immune to extraction, and it is the trade. For a handful of long-lived objects it is a good deal that removes a whole class of bug. For thousands of instances it is real memory, and it also removes the method from the prototype, which means subclasses cannot override it in the usual way and it will not appear where tooling expects prototype methods. The middle path most codebases settle on is prototype methods plus an arrow wrapper at the point where the callback is handed over.
  5. An extracted class method throws even in a sloppy file. Why?
    Because class bodies are always strict, regardless of the file. So this in a receiverless call is undefined rather than globalThis, and the first property access on it throws TypeError: Cannot read properties of undefined — measured inside a file with no "use strict" anywhere. This is a good outcome. The sloppy alternative would be this silently becoming the global object, so this.n = 1 would write a global and the bug would surface much later somewhere else, which is chapter 1's argument in miniature. It also means the mode discussion mostly does not apply to modern code: class bodies are strict, ES modules are strict, and the only places sloppy behaviour survives are old scripts. Where it does matter, the failure is loud rather than silent, which is why the TypeError is worth recognising on sight.
  6. What is this in an arrow used as an object method?
    Whatever this is in the surrounding scope where the object literal was written — never the object. An object literal does not create a scope, so the arrow looks past it. Measured, the answer depends on context exactly as arguments did in chapter 6: at the top level of an ES module it is undefined, at the top level of a CommonJS file it is module.exports, and inside a function invoked with a receiver it is that receiver. All three are wrong if you wanted the object. The fix is method shorthand — { m() { return this.v; } } — which is both shorter and correct. The reverse case is the one arrows are for: an arrow written inside a method inherits that method's this, which is why arr.map(x => this.scale(x)) works where arr.map(function (x) { return this.scale(x); }) does not.
  7. An event handler's this is the element, not your object. Is that a bug?
    No — it is a deliberate feature of the DOM, which invokes handlers with the element as receiver so that this.value and this.classList work without a closure. It becomes a problem only when you pass a method: el.addEventListener("click", obj.onClick) gives onClick the element rather than obj, which is the extraction problem with an extra twist, because this is not undefined and so the failure is silent rather than a TypeError. If you want your object, wrap it — () => obj.onClick() — and take the element from event.currentTarget, which is the reliable source and is not affected by binding at all. Note currentTarget rather than target: the latter is whatever was actually clicked, which may be a descendant, and confusing the two is its own common bug that chapter 17 covers.
