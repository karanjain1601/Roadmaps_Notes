Chapter 8 · Objects

Objects and prototypes

Every object has a hidden link to another object, and reading a property walks that chain until it finds one. Writing does not — it always creates an own property, with exactly one exception. Those two sentences explain nearly all of JavaScript's object behaviour, including what class is doing underneath.

Reading walks, writing does not

o.x finds "from base" on the prototype. Then o.x = "mine" creates an own property on o and leaves base.x as "from base" — measured. The prototype is never modified by assignment.

Same shape as Python, different keyword
Python's unit found a.total += 1 writing to the instance and leaving the class attribute alone, and a data descriptor intercepting the write. This is the same rule in a language that spells the chain differently.
javascript — the chain, and how to inspect it
const o = Object.create(base);        // o's prototype IS base
Object.getPrototypeOf(o) === base     // true. Use this, not __proto__

Object.hasOwn(o, "x")                 // own only. Replaces hasOwnProperty
"x" in o                              // walks the whole chain

// a plain object's chain is two links long:
//   {} → Object.prototype → null
Object.create(null)                   // no chain at all — a clean dictionary,

// descriptors control more than the value
Object.defineProperty(o, "id", { value: 1, writable: false, enumerable: false });
Object.keys(o)                        // id is absent — enumerable: false
Object.getOwnPropertyNames(o)         // id is here
o.id = 2;                             // silent in sloppy, TypeError in strict — chapter 1
Property order is specified, and it is not insertion order

Integer-like keys come first, in ascending numeric order; then string keys in insertion order; then symbols. Measured: { b: 1, 2: 1, a: 1, 10: 1, 1: 1 } enumerates as 1, 2, 10, b, a. So an object keyed by numeric ids silently reorders itself, and JSON.stringify of it does too — which breaks any code comparing serialised output, and any UI rendering entries in "the order they were added". Note 10 sorts after 2 because the comparison is numeric rather than lexical, which is the one part people get right by accident. If order matters, use a Map, which preserves insertion order for every key type, or an array of pairs. Chapter 11 covers when a Map is the better choice generally.

Copying

Four ways to copy, seven things that can go wrong
Every column loses something different
Spread and Object.assign are shallow, and identical
One level is copied; everything below is shared. c.n === o.n is true for both, so mutating c.n.deep changes the original.
structuredClone is deep and handles the hard cases
Dates stay Dates, Maps stay Maps, and a self-reference survives — c.self === c is true. It is built in, so the old JSON.parse(JSON.stringify(o)) trick no longer has an excuse.
The JSON round trip loses five of the seven
A Date becomes a string, a Map becomes {}, an undefined property vanishes, a method vanishes, and a cycle throws. Four of those are silent.
All four flatten a getter into a plain value
Copying reads the property, so the getter runs once and its result is stored. If you need the accessor itself, Object.defineProperties with Object.getOwnPropertyDescriptors is the only route.
structuredClone throws on functions — and that is the good behaviour

A JSON round trip silently drops a method, so the copy looks fine and fails much later when something calls it. structuredClone raises DataCloneError immediately, which is the failure mode you want — chapter 1's argument again, in a different corner of the language. The same applies to DOM nodes, class instances (you get a plain object with the fields but no prototype, so instanceof fails) and anything holding a socket or a stream. So the practical rule: structuredClone for plain data structures however deeply nested, spread for a shallow copy of a flat object, and a hand-written clone or a library when the values carry behaviour. And note that none of the four preserves the prototype — a copied class instance is never still an instance.

Check yourself

Self-check

  1. o has a prototype carrying x. What does o.x = "mine" change?
    It creates an own property on o and leaves the prototype untouched — measured, base.x was still "from base" afterwards. Reading walks the chain until it finds a match; writing does not walk at all, it writes locally. So the prototype's value is shadowed rather than overwritten, and the shadowing is reversible: delete o.x removes the own property and the prototype's value is visible again. This is the same rule the Python unit found with class attributes, where a.total += 1 read the class attribute and then created an instance one. The practical consequence is that you cannot accidentally corrupt a shared prototype by assigning through an instance, which is a good thing — and that a "the change did not stick" bug is often really "the change went somewhere else and something is still reading the prototype".
  2. What is the one exception to that rule?
    A setter on the prototype. If the property found on the chain is an accessor rather than a data property, assignment calls the setter instead of creating an own property. Measured: with base defining set x(v), the statement o.x = "assigned" passed "assigned" to the setter, Object.hasOwn(o, "x") came back false, and reading o.x returned the getter's value. Nothing was shadowed. This is exactly why setters are useful — validation, computed storage, change notification all work through instances without each instance carrying a property — and also why they surprise people, since an ordinary-looking assignment can run arbitrary code, throw, or store something different from what you wrote. It is the same distinction Python draws between a data descriptor and an ordinary class attribute, and the resolution order is the same too.
  3. { b: 1, 2: 1, a: 1, 10: 1, 1: 1 } — in what order do the keys enumerate?
    1, 2, 10, b, a. Property order is specified, and it is not insertion order: integer-like keys come first in ascending numeric order, then string keys in insertion order, then symbols. So 10 follows 2 rather than sorting lexically between 1 and 2, which is the part people get right by accident. The consequence that bites is that an object keyed by numeric ids silently reorders itself, and so does JSON.stringify of it — which breaks snapshot comparisons of serialised output and any UI rendering "in the order they were added". Note the rule applies to Object.keys, for…in, JSON.stringify and spread alike. If order matters, use a Map, which preserves insertion order for every key type including numbers, or keep an array of pairs.
  4. Which copy method would you use for a deeply nested plain object, and why not the others?
    structuredClone. Spread and Object.assign are shallow and identical in behaviour — measured, c.n === o.n is true for both, so the nested object is shared and mutating the copy changes the original. The JSON.parse(JSON.stringify(o)) trick is deep but loses five of the seven things tested: a Date becomes a string, a Map becomes {}, a property set to undefined disappears, a method disappears, and a cycle throws. Four of those five are silent. structuredClone is built in, deep, and keeps Dates, Maps, Sets and self-references — c.self === c came back true. The one thing to know before reaching for it is the next answer: it refuses functions rather than dropping them, and it does not preserve prototypes.
  5. structuredClone throws on an object containing a method. Is that a problem?
    It is the correct behaviour, and better than the alternative. A JSON round trip silently drops the method, so the copy looks right and fails much later when something tries to call it — a silent loss producing a distant failure, which is the pattern chapter 1 spent its length arguing against. structuredClone raises DataCloneError at the point of the copy, where the cause is obvious. The same applies to DOM nodes and anything holding a socket or a stream. Two related limits worth knowing together. It does not preserve prototypes, so a cloned class instance comes back as a plain object with the right fields and a failing instanceof — and no other copying method preserves them either. And a getter is flattened into a plain value by all four methods, because copying reads the property; keeping the accessor requires Object.defineProperties with Object.getOwnPropertyDescriptors.
  6. When would you use Object.create(null)?
    When you want a dictionary rather than an object — a bag of keys that came from outside your program. A normal object inherits from Object.prototype, so it already "has" toString, constructor, valueOf and hasOwnProperty, which means "toString" in bag is true for an empty bag and a user-supplied key called constructor collides with something real. Object.create(null) has no prototype at all, so a key means exactly what it says. It also removes one route to prototype pollution, where an attacker-supplied __proto__ key in parsed JSON reaches a shared prototype and changes behaviour program-wide. The costs are modest and worth knowing: no toString, so string interpolation throws, and console.log shows it as [Object: null prototype]. A Map solves the same problem with a nicer API and non-string keys, which chapter 11 covers.
  7. Why prefer Object.hasOwn(o, k) over o.hasOwnProperty(k)?
    Because the second is itself a property lookup that walks the chain, so it fails in the two cases you most need it. An object created with Object.create(null) has no hasOwnProperty at all, and calling it throws TypeError. And an object carrying a key literally named hasOwnProperty — quite possible for parsed user data, which is exactly the situation prompting the check — shadows the method with a value, so calling it throws or returns nonsense. The historical workaround was Object.prototype.hasOwnProperty.call(o, k), which is correct and unreadable. Object.hasOwn is a static method doing the same thing legibly, and it is the modern answer. The same reasoning applies to Array.isArray(v) over v instanceof Array and Object.prototype.toString.call(v) from chapter 2: reach for the static form when the object itself might be hostile or unusual.
