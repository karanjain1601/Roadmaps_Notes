Chapter 16 · Structure

Modules

The same three lines of code give 2 under ES modules and 0 under CommonJS. That difference — a live binding against a copied value — is the deepest one between the two systems, and it explains most of the surprises when code moves between them.

Live bindings against copies

Export a counter, bump it twice, read it
Same code, two answers
An ESM import is a view of the exporter's variable
After two increments the importer read 2. It is not a copy — the binding points at the same storage, so later changes are visible.
A destructured require copies the value once
The same sequence read 0. const { count } = require(…) takes whatever was there at require time, and nothing ever updates it.
A getter restores the liveness
get count() { return count; } on the exports object gives 2 again — which is what bundlers emit when they compile ESM down to CommonJS.
And ESM bindings are read-only
Assigning to an imported name is a TypeError. Only the exporting module may change it, which is what makes the live view safe.
javascript
// ESM — static, hoisted, analysable
import { a, b as c } from "./m.js";
import def, { named } from "./m.js";
import * as ns from "./m.js";          // a namespace object, also live
export { a, b };   export default fn;   export * from "./other.js";

// imports are HOISTED and the whole graph is resolved before any code runs,
// so this is not conditional — it runs regardless:
if (false) { import("./heavy.js"); }   // dynamic: a promise, genuinely conditional
if (false) { /* import x from … */ }   // static: a SyntaxError here at all

const m = await import("./heavy.js");  // code-splitting, optional deps, plugins
await import(`./locales/${lang}.js`);  // the one thing static import cannot do

// top-level await — legal in a module, and it delays every importer
const config = await loadConfig();
Named exports over a default

A default export has no name at the definition site, so every importer invents one — and a rename typo becomes a silently different name rather than an error. Named exports also tree-shake more reliably and give editors something concrete to auto-import. The one place a default genuinely fits is a module whose entire purpose is one thing, such as a React component file. Two related habits: avoid re-export barrels (export * from across a whole directory) in large projects, since they defeat tree-shaking and create import cycles that were not obvious; and keep side effects out of module bodies, because a module runs exactly once at an unpredictable point in the graph, and code that depends on when it ran is code you cannot reorder.

Cycles

Two modules importing each other
One throws, one carries on with undefined
ESM throws ReferenceError: Cannot access 'a' before initialization
The binding exists — the graph was linked before anything ran — and it has no value yet. This is chapter 3's temporal dead zone, reaching across a module boundary.
CommonJS hands you undefined, silently
Measured: b.cjs sees a = undefined, and execution continued. require returns a partially-filled exports object, so the missing value looks like an ordinary absent property.
Loud beats quiet, and this is the clearest case
The ESM error names the binding and the module. The CommonJS undefined flows onward and fails somewhere unrelated, often much later.
Either way, the fix is the same
Extract the shared thing into a third module both can import. A cycle is nearly always a sign that two modules are really one, or that a dependency points the wrong way.
Interop, and where it still hurts

An ES module can import a CommonJS one — Node gives you module.exports as the default export, and named exports only when its static analysis can detect them, which fails for anything computed. A CommonJS module cannot require an ES module at all; it needs await import(), which makes the call site async and can ripple a long way. That asymmetry is the whole of the "dual package hazard": a library shipping both formats can end up loaded twice in one process, with two separate module states, so a singleton is not one and an instanceof check across the boundary fails. If you are writing a library, ship ESM and let bundlers deal with it; if you are consuming one, the error message require() of ES Module … not supported means exactly this and the fix is to make the consumer a module too.

Check yourself

Self-check

  1. A module exports a counter. You import it, call bump() twice, and read it. What do you get?
    2 under ES modules and 0 under CommonJS, from identical-looking code. An ESM import is a live binding — a view of the exporting module's variable, pointing at the same storage — so later changes are visible. const { count } = require(…) destructures the exports object at require time and copies the value; nothing ever updates it. Both measured. The CommonJS behaviour can be recovered with a getter on the exports object, get count() { return count; }, which gave 2 again — and is exactly what bundlers emit when compiling ESM down to CommonJS. Worth adding that ESM bindings are read-only from the importer's side: assigning to an imported name is a TypeError, so only the exporting module can change the value. That restriction is what makes a shared live view safe.
  2. Why can you not write import inside an if?
    Because static import declarations are hoisted and resolved before any code in the module runs — the entire dependency graph is fetched, parsed and linked first, then evaluation begins. So there is no moment at which the if could be consulted, and the syntax is only legal at the top level of a module. That constraint is what buys ESM its advantages: tree-shaking, cycle detection, and an editor that can auto-import reliably, all of which need the graph to be knowable without running anything. When you genuinely need conditionality, import() is the dynamic form: it is a function-like expression returning a promise, legal anywhere, and it accepts a computed specifier — await import(`./locales/${lang}.js`) is the one thing static import cannot express. The cost is that the module is no longer statically analysable, so bundlers treat it as a split point rather than inlining it.
  3. Two modules import each other. What happens under each system?
    ESM throws ReferenceError: Cannot access 'a' before initialization; CommonJS hands you undefined and carries on. Both measured with the same two-module cycle. The ESM error is chapter 3's temporal dead zone crossing a module boundary — the binding exists, because linking happened before evaluation, and it has no value yet because the other module has not finished running. CommonJS has no linking step: require executes the module and returns whatever is on exports at that instant, which mid-cycle is partially filled, so a missing export is indistinguishable from an absent property. The ESM behaviour is better because it names the binding and the module at the point of the problem, where the undefined flows onward and fails somewhere unrelated. The fix in both cases is the same: extract the shared thing into a third module.
  4. When is dynamic import() the right tool?
    Four cases. Code splitting — loading a route, a chart library or an editor only when the user reaches it, which is the main reason bundlers care about it. Genuinely optional dependencies, where a feature works if a package is installed and degrades if not. Computed specifiers, such as loading a locale or a plugin by name, which static import cannot express at all. And breaking a cycle as a last resort, by deferring one side until after both modules have finished evaluating. What it is not for is ordinary imports: it returns a promise, so it makes the call site asynchronous and that tends to ripple upward, and it opts the module out of static analysis so the bundler cannot tree-shake into it. The rule of thumb is to use static imports everywhere and reach for the dynamic form when you can name which of those four reasons applies.
  5. Why prefer named exports to a default?
    Because a default export has no name at the definition site, so every importer invents one — and nothing checks that they agree. A typo produces a differently-named local binding rather than an error, and searching the codebase for usages of a thing becomes unreliable because it is called four things. Named exports also tree-shake more predictably, give editors a concrete symbol to auto-import, and make a re-export explicit about what is passing through. The one place a default genuinely fits is a module whose entire purpose is a single thing, such as a file containing one React component, where the file name is the name. Two related habits worth adopting at the same time: avoid barrel files re-exporting a whole directory, since they defeat tree-shaking and create cycles that are not visible in the source; and keep side effects out of module bodies, because a module runs once at a point in the graph you do not control.
  6. What is the dual package hazard?
    A library shipping both a CommonJS and an ES module build can end up loaded twice in one process — once by a require and once by an import — giving two independent copies with separate module state. A singleton is then not one, a cache is two caches, a registry misses half its entries, and an instanceof check against a class from the other copy fails because the constructors are different objects. It is a nasty class of bug because everything looks correct in isolation. The underlying asymmetry is that an ES module can import CommonJS (with named exports detected only when static analysis manages it), while CommonJS cannot require an ES module at all and must use await import(), which makes the call site async. The practical advice: if you write a library, ship ESM only and let bundlers handle the rest; if you consume one, require() of ES Module … not supported means make the consumer a module too.
  7. What does top-level await cost?
    It delays every module that imports you, and everything that imports them. A module using top-level await does not finish evaluating until the promise settles, and its importers cannot begin until it does — so one slow configuration fetch at the top of a widely-imported module serialises a large part of the startup graph. That is the intended semantics rather than a flaw: it exists so a module can be genuinely ready before anyone uses it, which is a real guarantee worth having for something like a WebAssembly instantiation or a database connection. But it is easy to reach for casually and hard to notice the cost. It also only works in modules, not in CommonJS, and a rejection at the top level makes the whole module fail to load, which importers cannot catch. The alternative is exporting a promise or an init() the caller awaits, which keeps the cost visible at the call site.
