CHAPTER 13

Data fetching and the server cache

One reframing does most of the work in this chapter: the data you fetched is not your application's state, it is a cache of somebody else's. Every awkward thing about it — staleness, refetching, races, invalidation — follows from that, and so does the reason you should not be writing this yourself.

Part 4 Building an application·Reading time 45 minutes·Demos key matching, a scripted session·Prerequisites Chapters 6, 9, 12

1Fetched data is not state

Client state is correct by definition. Server data is a photograph.

Client stateServer data
OwnerYouSomeone else
CorrectnessTrue by definition — if the flag says open, it is openTrue at the moment it arrived, and possibly not now
Who else changes itNobodyOther users, other tabs, background jobs
LifetimeAs long as the componentIndependent of any component
StorageuseState, a reducer, a storeA cache, keyed by the request

Putting server data in useState or a global store is a category error, and the symptoms are always the same: two components fetching the same thing, data that never refreshes, a spinner where a cached value would do, and an edit in one place that does not appear in another.

Writing all of that correctly is a few hundred lines and a well-understood problem. That is the argument for a query library: not that fetching is hard, but that caching is, and you are building a cache whether you meant to or not.

3Query keys

The cache is a map, the key is the identity of a request, and prefix matching is how invalidation stays sane.

Key design TanStack Query
// The key is serialised and used as the cache identity. Anything the
// request depends on must be in it — otherwise two different requests
// share one cache entry and you get somebody else's data.
useQuery({
  queryKey: ['orders', { status, page, sort }],
  queryFn: () => fetchOrders({ status, page, sort })
});

// Hierarchical, general → specific. That ordering is what makes
// prefix invalidation useful.
['orders']                              // everything about orders
['orders', 'list']                      // all list views
['orders', 'list', { status: 'open' }]   // one list view
['orders', 'detail', orderId]          // one order

// Keep the keys in one place so they cannot drift apart.
export const orderKeys = {
  all: ['orders'],
  lists: () => [...orderKeys.all, 'list'],
  list: (f) => [...orderKeys.lists(), f],
  detail: (id) => [...orderKeys.all, 'detail', id]
};

4Status, not booleans

Chapter 6's argument, already applied for you.

What a query returns JSX
const { data, error, status, isFetching, isPlaceholderData } = useQuery({ ... });

// status is 'pending' | 'error' | 'success' — one field, not four booleans.
// isFetching is separate and orthogonal: it means "a request is in flight
// right now", which can be true WHILE status is 'success' during a
// background revalidation. That distinction is what lets you show data
// and a subtle refreshing indicator at the same time.

if (status === 'pending') return <Skeleton />;
if (status === 'error')   return <Retry error={error} />;
return <Table rows={data} refreshing={isFetching} />;

Design all three states deliberately. The pending state should be a skeleton shaped like the content, not a spinner that shifts the layout. The error state needs a retry and a human sentence, not a stack trace. And the empty case — a successful response with zero rows — is a fourth state that is not an error and is almost always forgotten.

5Staleness and revalidation

Two timers with confusingly similar names, and four automatic triggers.

SettingMeans
staleTimeHow long a cached value is considered fresh. While fresh, mounting a component that uses it triggers no request at all. Default 0 — everything is stale immediately, which is safe and chatty.
gcTimeHow long an unused entry stays in memory after the last component using it unmounts. Default five minutes. This is what makes going back instant.
Refetch on mountIf stale, fetch in the background while showing the cached value.
Refetch on window focusThe user came back to the tab; the data may be an hour old.
Refetch on reconnectThe connection returned.
refetchIntervalPolling, for genuinely live data. Prefer server-sent events or a websocket where you can.

Set staleTime per query according to how fast the data actually changes: seconds for a dashboard, minutes for a product catalogue, effectively infinite for a country list. Leaving everything at the default is the most common cause of "why is it making so many requests".

6Mutations

Writing is easy. Deciding what the cache should now believe is the work.

The optimistic update, with the step everyone skips JSX
const mutation = useMutation({
  mutationFn: toggleFavourite,

  // 1. Cancel in-flight reads, or one can land AFTER our optimistic
  //    write and revert the UI for two seconds. This is the step
  //    that gets skipped, and the flicker is the symptom.
  async onMutate(next) {
    await qc.cancelQueries({ queryKey: orderKeys.detail(id) });
    const previous = qc.getQueryData(orderKeys.detail(id));
    qc.setQueryData(orderKeys.detail(id), o => ({ ...o, favourite: next }));
    return { previous };                // 2. keep the old value
  },

  // 3. Put it back if the server disagreed
  onError(err, next, ctx) {
    qc.setQueryData(orderKeys.detail(id), ctx.previous);
  },

  // 4. Either way, reconcile with the truth
  onSettled() {
    qc.invalidateQueries({ queryKey: orderKeys.detail(id) });
  }
});
Invalidate, or write the response into the cache
Invalidating is simpler and always correct: mark the affected keys stale and let them refetch. Writing the mutation's response directly with setQueryData saves a round trip and is right when the response is the full updated resource. Do not do both by reflex.
Invalidate the list as well as the item
Editing an order changes the detail and whatever list views include it. Prefix invalidation on ['orders'] handles both in one call, which is the payoff for the key hierarchy in section 3.
Optimism is a judgement call
Right for a toggle, a like, a reorder — cheap, usually succeeds, and cheap to undo. Wrong for a payment or an irreversible delete, where showing success before it is true is worse than a spinner.
Idempotency for retries
If a mutation may be retried, the server needs a client-generated key so a duplicate does not create a second order. That is a server contract, not something the client library can fix.

7Pagination and infinite lists

The page number belongs in the key, which creates one problem with a one-line fix.

The flash of empty
Because ['orders', page] is a different key per page, moving to page two is a cache miss and the table empties while it loads. placeholderData: keepPreviousData keeps the previous page visible with isPlaceholderData true, so you dim it rather than blanking it — Chapter 12's principle about stale content beating spinners.
Prefetch the next page
queryClient.prefetchQuery for page + 1 as soon as the current one settles. The click then hits a warm cache and feels instant.
Cursors beat offsets
Offset pagination shows duplicates and skips rows when the underlying data changes between pages. A cursor is stable. This is a server design decision that determines what the client can do.
Infinite lists
useInfiniteQuery holds pages in one cache entry with a getNextPageParam. Pair it with virtualisation past a few hundred rows, or you have solved fetching and created a rendering problem.

8Where to fetch

The choice that determines whether your requests run in parallel or in a queue.

The component waterfall

A component that fetches when it renders cannot start until its parent has rendered — and if the parent is waiting for its own data, the child's request has not even been created yet. Three nested components each waiting 300ms take 900ms rather than 300. Nothing in the code looks wrong; the network panel shows a staircase. This is the single most common cause of a slow-feeling React application, and no amount of caching fixes it, because the first visit is exactly when it hurts.

WhereCharacter
Route loader
React Router, TanStack Router		Declared with the route, so it starts as soon as navigation begins — in parallel with downloading the route's code. Removes the waterfall by construction. Chapter 15.
Server componentFetch on the server, next to the data, and send only the result. No client cache needed for that data at all. Chapter 19.
Component levelColocated and easy to reason about; the default with a query library. Fine when the requests are not nested. Use prefetchQuery at a parent, or useQueries, to flatten a waterfall.
On interactionPrefetch on hover or focus of a link. Cheap, and it makes navigation feel instant.

9Choosing

Four reasonable answers, and one case where the effect really is fine.

OptionWhen
TanStack QueryThe default. Complete, well documented, excellent devtools, framework-agnostic. Everything in this chapter maps directly onto it.
SWRSmaller and simpler, from the Next.js authors. Fine when you need caching and revalidation and not much else.
RTK QueryYou are already using Redux Toolkit. Generates hooks from an API definition and shares the store.
Your framework's loadersNext.js or React Router already own routing and server rendering. Use their data layer first and add a client cache only where you need client-side revalidation.
A plain effectGenuinely acceptable for a one-off request in a leaf component, with no other consumer, no revalidation requirement, and cleanup written properly. Rare, but not a sin.

10Check yourself

Five questions.

1. Why does calling fetched data "a cache" rather than "state" change what you build?

Because a cache has questions state does not: how old is this, who else might have changed it, should I revalidate, what happens when two components want the same thing, and what becomes wrong after a write. Treating it as state means answering all of those by hand in every component that fetches — and the usual answer is "not at all", which is why the symptoms are so consistent: duplicate requests, data that never refreshes, a spinner where a cached value would do, and an edit in one place that never appears in another. Naming it a cache makes the missing machinery visible, and points at the tool that already implements it.

2. What is the difference between staleTime and gcTime?

staleTime is about freshness: how long a cached value is trusted without checking. While it is fresh, mounting a component that uses it fires no request at all. gcTime is about retention: how long an entry survives in memory after the last component using it unmounts. So a query can be stale but still cached — which is the good case, because the user sees the old value immediately while a background refetch runs. The common misconfiguration is leaving staleTime at its default of zero everywhere, which makes every mount fire a request; tune it per query to how fast the data actually changes.

3. Why does key design matter beyond identifying a request?

Because invalidation is prefix matching, so the key hierarchy is your invalidation vocabulary. With keys ordered general to specific — ['orders'], ['orders', 'list', filters], ['orders', 'detail', id] — one call to invalidate ['orders'] marks every affected view stale after a mutation, which is exactly what you want when editing an item changes both the detail and every list containing it. Flat or inconsistent keys force you to enumerate every affected query at every mutation site, and you will miss one. Two other rules: everything the request depends on must be in the key, or two different requests collide on one entry; and the keys belong in one exported factory so they cannot drift.

4. An optimistic update flickers back to the old value for a moment. What was skipped?

Cancelling the in-flight queries for that key before writing the optimistic value. A read that was already on the wire lands after your write, overwrites it with pre-mutation data, and then the invalidation refetch corrects it again — hence the flicker. The full pattern is four steps: cancelQueries, snapshot the previous value and write the optimistic one, restore the snapshot in onError, and invalidateQueries in onSettled regardless of outcome. It is also worth asking whether the mutation should be optimistic at all: right for a toggle or a reorder, wrong for a payment, where claiming success before it is true is worse than waiting.

5. Three nested components each fetch their own data and the page takes 900ms. Caching does not help. Why?

It is a waterfall, not a cache miss. A component cannot start its request until it renders, and it cannot render until its parent has resolved — so three 300ms requests run in sequence rather than in parallel. Caching only helps the second visit, and the first is where the complaint comes from. The fixes all amount to starting the requests earlier and together: a route loader that declares the route's data so it begins as navigation starts, a server component that fetches next to the data, useQueries or a parent-level prefetchQuery to flatten it, or prefetching on link hover. The network panel makes it obvious — look for a staircase rather than a block.
