CHAPTER 20

The frameworks

React is a rendering library. A framework is everything else you would otherwise assemble: routing, data loading, bundling, server rendering, caching and deployment. Choosing one is mostly choosing whose opinions about caching you would rather live with.

Part 5 Beyond the client·Reading time 40 minutes·Demos strategy advisor, the cache layers·Prerequisites Chapters 15, 19

1What a framework is for

The list you would otherwise build and maintain yourself.

The assembly problem
Routing, code splitting per route, data loading that starts with navigation, server rendering, streaming, hydration, asset hashing, environment handling, image optimisation, and a deployment target that supports all of it. Each is solvable; keeping them working together across upgrades is the actual cost.
Server components need one
They require a bundler that understands the boundary, a server runtime that can stream the payload, and a router that knows what to re-render. This is not something you add to a Vite project by installing a package — Chapter 19 exists inside a framework or not at all.
When you do not need one
An internal dashboard behind a login. An embedded widget. A canvas application. Anything with no SEO requirement, no first-paint pressure and no server. Vite plus React Router in its library mode is a genuinely good stack, and choosing it is not a compromise.
What you are actually buying
Defaults, and a community of people who have hit the same problems. What you are paying is a set of conventions you cannot easily leave.

2A strategy per route

The important shift: this is not one decision for the application.

Which strategy for this route? Answer for one page, not for the whole site.

The same application will use several. A marketing home page is static, the product listing is revalidated hourly, the account page is per request, and the editor is client only.

3Next.js

The most-used framework, and the one where server components are most fully realised.

The file conventions are the API App Router

  page.tsx              // the route itself                          /
  loading.tsx           // automatic Suspense boundary
  error.tsx             // automatic error boundary ('use client')

// loading.tsx and error.tsx are Chapters 12 and 18 given to you per
// route — which is the strongest argument for the conventions.
Strengths
Server components, server actions and streaming work together properly. Image, font and script handling are excellent. The ecosystem is enormous and most problems have been written about.
Costs
The caching model is the hardest part of the framework and has changed meaningfully between versions — section 6. The App Router is opinionated in ways that are awkward to opt out of, and deploying somewhere other than Vercel is possible but less well-trodden.
Where it fits
Content-heavy and commerce sites, anything with SEO pressure, teams who want the full server-component model with the fewest decisions.

4React Router in framework mode

The old Remix, now merged into React Router 7.

The model
Loaders and actions per route, as in Chapter 15, plus server rendering and a build. Data loading is explicit and route-shaped rather than component-shaped, which makes it very easy to reason about what a page requests.
Web-standards leaning
Request, Response, FormData, real form submissions. Progressive enhancement is a first principle rather than a feature, and the knowledge transfers outside React.
Caching
Deliberately not opinionated — you use HTTP caching headers. Much less framework-specific machinery to learn, and correspondingly more work if you want fine-grained invalidation.
Where it fits
Teams who want server rendering and good data loading without adopting the whole server-component model, and anyone who found Next's caching layers frustrating. It also has the smoothest upgrade path if you already use React Router.

5The others worth knowing

Four more, each strongest in a specific situation.

Character
TanStack StartBuilt on TanStack Router, so fully type-safe routes, params and search params, with server functions and streaming. Natural if you already use TanStack Query. Newer than the others, with a correspondingly smaller ecosystem.
AstroContent-first. Ships zero JavaScript by default and hydrates individual components as islands, with React as one of several renderers. Excellent for documentation, blogs and marketing; not the tool for an application.
ExpoReact Native with a router, over-the-air updates and a build service, and increasingly a web target too. Chapter 21.
Vite + React Router (library mode)Not a framework, and often the right answer. Extremely fast development, no server, no conventions. Add TanStack Query for data and you have a capable single-page application with nothing to unlearn.

Why this is hard, stated plainly

Four caches, each with its own lifetime, its own scope and its own way of being invalidated — and a fifth if you count the query cache from Chapter 13, which lives in the browser and knows nothing about any of them. A bug reported as "my change does not appear" could be any one of them, and the layer names are not visible in the browser's network panel. When something is stale, work down the list in order rather than guessing, and remember that caching defaults have changed between major versions: verify the behaviour of the version you are on rather than trusting a blog post.

7Choosing

Five situations and a defensible answer for each.

SituationReasonable choice

Server rendering wanted, server components notReact Router framework mode
Type safety is a priority, already on TanStackTanStack Start
Mobile, with a web version laterExpo

Two things that matter more than the choice: whether your team already knows one, and where you can deploy. A framework nobody has used, on infrastructure it was not designed for, will cost more than any architectural advantage it offers.

8Adopting and leaving

Both directions, briefly, because both happen.

Adopt incrementally
Move one route, or one section, and run the two side by side behind a proxy. A full rewrite of a working application is the highest-risk way to change framework and rarely the fastest.
Keep the framework at the edges
Business logic, data shapes and pure components should not know which framework they are in. What is expensive to move is routing conventions, data loading and anything that reaches into the framework's caching — so keep that layer thin and explicit.
The parts that do not transfer
File conventions, loader and action signatures, caching directives, image and font components, middleware, and deployment configuration. Everything else — your components, hooks, types and tests — is portable.
Do not migrate for a feature you are not using
Server components pay for themselves on content-heavy public pages. On an internal dashboard behind a login they add a mental model and a server for very little return.

9Check yourself

Five questions.

1. Is choosing a rendering strategy an application-level decision?

No, and treating it as one is the mistake. A realistic application uses several at once: the marketing home page is static and served from a CDN, the product listing is regenerated on a schedule, the account page is rendered per request because it is personalised, and the editor is client-only because it is behind a login and has no SEO value. Modern frameworks let you set the strategy per route precisely because the requirements differ per route. The questions that decide it are the same each time — is it personalised, how fast does the content change, does it need to be indexed, and is there one slow section that should stream.

2. When is "no framework" the right answer?

When there is no SEO requirement, no first-paint pressure, and nobody to run a server. An internal dashboard behind a login, an embedded widget, an editor or canvas application — Vite plus React Router in library mode, with TanStack Query for data, is a genuinely good stack rather than a compromise. You get very fast iteration, no conventions to learn, static hosting, and nothing that has to be unlearned later. What you give up is server components, which on that class of application would mostly add a mental model and an operational burden for little return.

3. Why is caching the hardest part of a modern React framework?

Because there are several caches operating at once, each with a different scope, lifetime and invalidation mechanism, and none of them is visible in the network panel. A single request may be answered by the client-side router cache without touching the network, by a cached full route render, by a cached data fetch, or by request-level memoisation within one render — plus a query cache in the browser that knows nothing about any of them. When a change does not appear, the symptom is identical regardless of which layer is responsible, so the only reliable approach is to work down the layers in order. Defaults have also changed between major versions, so verifying the behaviour of your version beats trusting documentation you read a year ago.

4. What actually differs between Next.js and React Router in framework mode?

Mostly how much the framework decides. Next leans into server components and server actions, with a rich caching model it manages for you — powerful, and the source of most of its difficulty. React Router keeps data loading explicit through loaders and actions per route, leans on web standards such as Request, Response and real form submissions, and deliberately does not add a caching layer: you use HTTP headers. So Next gives you more capability with more framework-specific behaviour to understand, and React Router gives you a smaller surface with more of the caching left to you. Both server-render, both stream, both split code per route.

5. What survives a framework migration and what does not?

Your components, hooks, types, business logic and tests are portable — that is most of the codebase. What does not transfer is the layer that touches framework conventions: file-based routing structure, loader and action signatures, caching directives, image and font components, middleware and deployment configuration. The practical implication is architectural: keep that layer thin and explicit, and do not let framework specifics leak into components that could otherwise be plain. Migrate incrementally too — one route or one section at a time, running both behind a proxy — because a full rewrite of a working application is the highest-risk approach and seldom the quickest.
