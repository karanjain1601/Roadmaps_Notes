CHAPTER 23

Patterns and architecture

React has almost no opinion about how to organise a codebase, which means every project invents one. This chapter is the small set of structural decisions that determine whether a React application is pleasant at fifty thousand lines or merely survivable.

Part 6 Craft·Reading time 40 minutes·Demos state placement, folder structure·Prerequisites Parts 2 and 4

1Organise by feature

The default structure everyone starts with is the one that scales worst.

The shape worth adopting Structure
src/
  app/                  // routes, providers, the shell
  features/
    orders/
      components/       // used only by this feature
      api.ts            // requests and query keys
      hooks.ts
      schema.ts         // validation + inferred types (Chapters 14, 17)
      index.ts          // the ONLY public surface
    customers/
    checkout/
  shared/
    ui/                 // design system: Button, Dialog, Table
    lib/                // formatting, dates, fetch client
    hooks/              // genuinely generic ones only

// A feature's index.ts is the boundary. Everything else inside it is
// private, which is what lets you reorganise the inside freely.

2Dependency direction

The rule that keeps a feature-based structure from decaying into the other kind.

Features do not import each other
Once checkout imports from orders and orders imports from checkout, neither can be understood or deleted independently and you have a distributed monolith in one repository.
Everything may import from shared, and shared imports nothing
If something in shared needs to know about orders, it is not shared. This one check catches most drift.
When two features genuinely need each other
Three options in order of preference: move the common part into shared; have the route compose both features rather than letting one reach into the other; or, if they are truly one thing, merge them and admit the boundary was wrong.
Enforce it mechanically
eslint-plugin-boundaries or import/no-restricted-paths. A convention nobody can violate accidentally is worth ten written down in a wiki, because this particular rule is broken under deadline pressure and then never unwound.
Be careful with barrel files
An index.ts per feature is the point. An index.ts re-exporting every component in the project defeats tree shaking, slows the bundler, and creates import cycles that are miserable to diagnose.

3The five kinds of state

The most useful thing in this chapter. Most state-management arguments are really disagreements about which kind is being discussed.

Where does this piece of state belong? Four questions, and they resolve almost every case.

KindLives inExamples
Server dataA query cacheOrders, the current user, a product catalogue. Chapter 13 — it is a cache, not state.
URL stateThe URLFilters, sort, page, search term, the selected tab. Chapter 15 — shareable and survives a refresh for free.
Form stateThe DOM, or a form libraryField values, dirty and touched flags, validation errors. Chapter 14.
Local UI stateuseState in the component that owns itIs this menu open, which accordion panel is expanded, hover state.
Application stateContext or a storeTheme, locale, feature flags, the basket, a permissions object. The smallest of the five in a well-organised app.

Notice how little is left for a global store once the other four have their proper homes. Codebases that reach for Redux early usually put server data and URL state in it, then need middleware to manage caching and synchronisation that the right tool already provides. There is also a sixth thing that is not state at all: values that change without needing a re-render belong in a ref (Chapter 8).

4Composition patterns worth knowing

Five that still earn their place, and one that hooks retired.

Compound components JSX
// Instead of twenty props on one component, expose the parts and let
// the caller arrange them. Shared state travels through context, which
// is invisible to the caller.
<Select value={v} onChange={setV}>
  <Select.Trigger>{v ?? 'Choose a size'}</Select.Trigger>
  <Select.Options>
    {sizes.map(s => <Select.Option key={s} value={s}>{s}</Select.Option>)}
  </Select.Options>
</Select>

// Right when the arrangement genuinely varies. Overkill for a
// component with one sensible layout — you have added a vocabulary
// to learn in exchange for flexibility nobody needed.
Slots via children
Chapter 3 and Chapter 4. The simplest and most valuable pattern in React, and it now does architectural work too — Chapter 19's server-component boundary depends on it.
Provider plus hook
Chapter 7. Export the provider and a useThing() that throws outside it; never export the context. One place to add a selector, memoise, or swap the implementation later.
The dual controlled/uncontrolled API
Accept value, or defaultValue plus internal state. What every native input does, and what a reusable component should do so callers are not forced into either.
Headless behaviour
Chapter 11's useCombobox: logic in a hook, markup at the call site. The pattern behind Radix and React Aria, and the right answer when appearance varies but behaviour must not.
Render props — mostly retired
Custom hooks replaced them for sharing logic. Still correct for genuine rendering injection: a table's renderRow, a list's renderItem, a virtualiser handing you an index. If you are using one to share state, use a hook.
Higher-order components — legacy
You will meet them in older code. They obscure prop origins, break types, and stack into unreadable wrappers. Do not write new ones.

5Component roles

Container and presentational, reconsidered now that hooks and server components exist.

The original split has softened
Hooks let any component fetch and hold state, so a mechanical container-per-presentational-component rule mostly adds files. What survives is the underlying instinct: the components you want to reuse, test in isolation and style should not know where their data came from.
Three useful roles
Route components — own data loading and layout for a screen, and are not reused. Feature components — know about a domain, may use feature hooks, reused within the feature. Shared UI — no domain knowledge, no data access, props in and elements out.
Fetch high, present low
Chapter 13's waterfall argument as an architectural rule: data enters at the route or the feature boundary, and shared UI receives it as props. That also makes the shared layer trivially testable.
The size heuristic
Split when a component has two clearly separable responsibilities, not when it exceeds a line count. A 200-line component doing one thing well is fine; a 60-line one doing three things is not.

6Abstractions that age badly

Six, all created with good intentions.

The abstractionHow it fails
The universal componentChapter 3's argument. Twenty-two props and nine booleans, because every new requirement was met by another flag. Composition instead.
The wrapper around a libraryWritten to "make it easy to swap later". It exposes a subset, so every new need means editing the wrapper, and the swap never happens. Wrap only where you genuinely have two implementations.
The shared utils.tsBecomes a 900-line dumping ground that everything imports and nobody can change safely. Name things by what they do: formatCurrency.ts, parseCsv.ts.
The mega-contextOne provider holding fifteen unrelated values, so every consumer re-renders when any of them changes. Chapter 7: split by change frequency.
The premature generic componentBuilt for three future cases that never arrived, and awkward for the one that did. Write it twice, then extract.
The clever typeChapter 17. A conditional type saving four lines of duplication, which nobody else can modify. Duplication is cheaper than incomprehension.

7Conventions worth writing down

Not because they are correct, but because agreeing once ends the discussion.

Naming
Components PascalCase, hooks useThing, handlers handleX internally and onX as props, booleans isX / hasX / canX. Files named after their default export.
One component per file, with its close relatives
A compound component's parts belong together; two unrelated components do not.
Props order and destructuring
Destructure in the signature, defaults inline, rest spread last. Consistency matters more than the specific choice.
Where types go
Props types beside the component. Domain types in the feature's schema.ts, inferred from validation. Never a project-wide types.ts — it becomes the utils.ts of type definitions.
What lint enforces rather than review
The hooks rules as errors, import boundaries, no default exports from features, exhaustive switch on unions, no any. Anything a machine can check should not consume a reviewer's attention.

8Scaling past one team

Five things that matter more than any pattern once several people share a codebase.

Feature ownership
The folder structure and the ownership map should be the same shape. If they are not, every change needs three reviewers.
A design system with real boundaries
shared/ui as an internal package with its own tests, documentation and versioning. Without a boundary it accumulates domain knowledge and stops being shared.
Write decisions down
A short record per significant choice — why Zustand rather than Redux, why we are not adopting server components yet. Two paragraphs, in the repository. It prevents the same debate annually and tells a new joiner what is settled.
Upgrade on a cadence
Small, regular upgrades. A codebase two major versions behind on React, its router and its framework is not one migration but three interacting ones, and nobody has time for that quarter either.
Make the right thing the easy thing
Templates, generators, a well-organised shared/ui, lint rules that explain themselves. People follow the path of least resistance; architecture is largely the work of choosing which path that is.

9Check yourself

Five questions.

1. Why does grouping files by kind scale badly?

Because work arrives by feature, not by kind. Adding a field to the order form means editing a component, a schema, a type and an API function — which in a components/hooks/api/types layout means four folders, none of which contains anything else related to the change. The costs compound: a reviewer cannot see the shape of the change from the file list, nothing tells you whether you found every file, and deleting a feature means hunting through six directories and hoping nothing is orphaned. Grouping by feature puts everything one change touches in one place, and makes deletion a single rm -r that is verifiably complete.

2. Name the five kinds of state and where each belongs.

Server data in a query cache, because it is a cache of someone else's truth (Chapter 13). URL state in the URL — filters, sort, page, search — so it is shareable and survives a refresh (Chapter 15). Form state in the DOM or a form library (Chapter 14). Local UI state in useState in the component that owns it. Application state — theme, locale, flags, basket — in context or a store, and it should be the smallest of the five. The reason this matters: most "which state manager" arguments are really about which kind is being discussed, and codebases that reach for a global store early usually end up putting server data and URL state in it, then reimplementing caching and synchronisation badly.

3. What single rule keeps a feature-based structure healthy?

Features do not import each other. They may import from shared, and shared imports nothing — so if something in shared needs to know about orders, it is not shared. Without this, checkout reaches into orders, orders reaches back, and neither can be understood, tested or deleted independently; you have layer-based coupling with feature-shaped folders. When two features genuinely need something in common, move the common part to shared, or let the route compose both rather than letting one reach into the other. Enforce it with a lint rule, because this is precisely the rule that gets broken under deadline and never unwound.

4. When is a compound component the right shape, and when is it overkill?

Right when the arrangement genuinely varies between call sites — a select whose trigger is sometimes a button and sometimes a field, a dialog whose footer differs per use. Exposing the parts lets each caller compose what it needs while shared state travels invisibly through context, which is far better than accumulating props for every variation. Overkill when the component has one sensible layout: you have replaced two props with a vocabulary of five subcomponents that every caller must learn and assemble correctly, in exchange for flexibility nobody asked for. The honest test is whether you can name two existing call sites that need different arrangements.

5. Why is a wrapper written to make a library swappable usually a mistake?

Because it is designed against a hypothetical. To be swappable it must expose only the intersection of what several libraries can do, so it is immediately less capable than the one you are using — and every new requirement means editing the wrapper rather than reading the library's documentation. Meanwhile the swap almost never happens, and if it does, the wrapper's surface turns out to be the wrong shape for the replacement anyway. Wrap where you genuinely have two implementations today, or where the boundary buys something else concrete such as testability. Otherwise use the library directly and accept that a future migration is a future migration.
