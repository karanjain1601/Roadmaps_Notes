CHAPTER 11

Custom hooks

A custom hook is a function whose name starts with use and which calls other hooks. There is no registration, no special runtime, no magic — and understanding the very ordinary array that makes it work explains every rule you have been told to follow.

Part 3 Fast and reusable·Reading time 35 minutes·Demos independent state, the slot array·Prerequisites Chapters 5, 8–9

1What a custom hook is

Ordinary function composition, with one naming convention that carries real weight.

Extracting a piece of behaviour JSX
// Before: the same six lines in four components.
function Page() {
  const [online, setOnline] = useState(navigator.onLine);
  useEffect(() => {
    const on = () => setOnline(true), off = () => setOnline(false);
    addEventListener('online', on); addEventListener('offline', off);
    return () => { removeEventListener('online', on); removeEventListener('offline', off); };
  }, []);
  ...
}

// After: one function, four call sites, one place to fix a bug.
function useOnlineStatus() { /* the same six lines */ return online; }

function Page() { const online = useOnlineStatus(); ... }
The use prefix is load-bearing
It tells the linter to enforce the rules of hooks inside the function, tells React DevTools to display it as a hook, and tells the next reader that calling it is not free of consequences. A function that calls no hooks should not be named useSomething — it is just a function.
Nothing is registered
Calling a custom hook is a plain function call. The hooks inside it run in the calling component's context, using the calling component's slots — which is section 4's whole subject.
It can return anything
A value, a tuple, an object, a function, several of each. There is no required shape.

The wrong extraction is a wrapper component that renders both variants behind a flag. Chapter 3's configuration smell, arriving from a different direction. If two things share logic and differ in appearance, the logic goes in a hook and each keeps its own markup — which is exactly how headless component libraries are built (Chapter 16).

3Each call gets its own state

The most common misconception about custom hooks, and the demo settles it.

Three components, one hook A real slot-array harness. The fourth panel uses a module variable instead, for contrast.

A hook is a recipe, not a container

Calling useCounter() in three components creates three independent counters, because the useState inside it runs three times — once per component, against that component's own slots. Nothing about a hook is shared. If you want shared state, the state must live somewhere shared: lifted to a common parent, in a context, or in a store. A hook can then be the interface to it, which is Chapter 7's useTheme() pattern.

4The rules, and the array that explains them

Two rules, one mechanism. Once you have seen the array, neither rule needs memorising.

React stores hook state in an ordered list per component instance and walks it with a cursor on every render. Nothing in a useState call identifies which state it wants — only its position in the sequence does.

Rule 1 · Call hooks unconditionally, at the top level
No hooks in if, in a loop, in a nested function, or after an early return. An early return is fine as long as every hook runs before it.
Rule 2 · Call hooks only from components or other hooks
Because there has to be a slot array. Calling one from a plain function or an event handler means there is no component context to store anything in.
The linter is not optional
eslint-plugin-react-hooks catches both, plus dependency-array mistakes. Configure it as an error. It is also what the React Compiler uses to decide whether a component can be optimised (Chapter 10).
What to do instead of a conditional hook
Call it unconditionally and make the hook conditional internally — pass null as the id and have it skip the work. Or split the component in two, so the branch chooses which component to render rather than which hooks to call.

5Designing a hook worth having

Six decisions, mostly about the interface rather than the implementation.

One job
useUserDashboard() that fetches a user, subscribes to notifications, tracks a tab and syncs the URL is four hooks in a trench coat. Each of those is independently useful; the combination is useful once.
Return an object unless there are exactly two things
A tuple is right when the caller will rename both — const [value, setValue] = useState(). Beyond two, or when some are optional, an object is self-documenting and lets callers destructure only what they need.
Return stable identities
Functions a hook returns should be wrapped in useCallback, and objects in useMemo — otherwise every consumer's effects re-run on every render and every memoised child below them re-renders. This is the one place where memoisation is not premature: you do not know your callers. The React Compiler handles it, but a published hook should not assume the caller has it.
Keep the parameters reactive
A hook taking an id should react when the id changes, the same way a component reacts to a prop change. A hook that only reads its argument on the first render is a common and confusing bug.
Do not hide the important thing
A hook that swallows loading and error states and returns only data forces every caller to reinvent them. Return the whole status.
Effects belong in hooks, not the reverse
A good custom hook usually contains the effect, so the component never writes one. That is the main way to reduce the number of raw useEffect calls in a codebase without losing the behaviour.

6A small library

The handful that end up in almost every project, and what each teaches.

Four that are worth writing yourself once JSX
// Trivial, and it removes a line of noise from every disclosure
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return [on, useCallback(() => setOn(v => !v), [])];   // stable, no captured value
}

// The canonical "value from the previous render"
function usePrevious(value) {
  const ref = useRef(undefined);
  useEffect(() => { ref.current = value; });   // after render, so reads see the old one
  return ref.current;
}

// Note the cleanup — without it, every keystroke leaves a timer running
function useDebounced(value, ms = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(t);
  }, [value, ms]);
  return debounced;
}

// The RIGHT way to read something outside React — section 7
function useMediaQuery(query) {
  const subscribe = useCallback(cb => {
    const m = matchMedia(query);
    m.addEventListener('change', cb);
    return () => m.removeEventListener('change', cb);
  }, [query]);
  return useSyncExternalStore(subscribe,
    () => matchMedia(query).matches,   // client snapshot
    () => false);                      // server snapshot
}
Others worth having
useLocalStorage (careful: it must handle a missing or corrupt value, and syncing across tabs needs the storage event). useEventListener for document-level handlers with automatic cleanup. useIntersection for lazy loading and infinite scroll. useCopyToClipboard. Libraries such as usehooks-ts and react-use ship dozens; take the ones you need rather than the dependency.
One to be suspicious of
useIsMounted. It is nearly always a sign that something is missing a cleanup — the correct fix is to abort the request or clear the timer, not to check a flag before calling a setter. React has not warned about setting state after unmount since version 18, so the usual justification is also gone.

7useSyncExternalStore

The purpose-built primitive for reading anything React does not own.

The obvious way to track something external is useState plus an effect that subscribes. That works and has three flaws that this hook exists to remove.

Problem with state + effectWhat the hook does
Tearing: during a concurrent render, different components can read the external value at different moments and disagreeReads the snapshot consistently for the whole render
Missed updates between render and the effect subscribingRe-checks the snapshot after subscribing
Server rendering has no windowTakes an explicit server snapshot as a third argument

Use it for media queries, online status, the URL, document.visibilityState, a Redux-like store, or anything else with a subscribe-and-read shape. The snapshot function must return a cached value — returning a new object each call causes an infinite loop, which is the one trap.

8When not to extract

Abstraction has a cost and hooks make it very easy to pay it early.

One call site
Moving four lines out of a component so it is "cleaner" adds a file and an indirection with no reuse. Extract on the second or third use, when the shared shape is evident.
A thin wrapper around one hook
useMyState that calls useState and returns it adds a name to learn and nothing else.
Nine parameters and six return values
The hook is doing several jobs and the interface is the evidence. Split it.
A hook that renders
If it returns JSX, it wants to be a component. Hooks return data.
A hook that hides a decision the caller should make
useAuth() that redirects on failure has made a routing decision on behalf of every caller. Return the state and let them decide.

9Testing hooks

Two approaches, and the first is usually better.

Test through a component
Render something that uses the hook and assert on what a user would see. That tests the hook in the context it actually runs in, and it does not break when you change the return shape. Chapter 22.
renderHook when the hook is a published API
Testing Library's renderHook gives you the return value directly and an act-wrapped way to trigger updates. Right for a shared hook in a library, where the return shape is the contract.
Pure logic does not need either
If a hook wraps a pure function — a reducer, a formatter, a validator — test that function on its own, in microseconds, and let a thinner test cover the wiring. Chapter 6's argument.

10Check yourself

Five questions.

1. Three components call useCounter(). Do they share a count?

No. A hook is a recipe, not a container: calling it runs the useState inside it once per component, against that component's own slot array, so there are three independent counters. Nothing about a custom hook is shared — only the code is reused. If you want shared state, the state must live somewhere shared: lifted to a common parent, in a context, or in a store, with the hook acting as the interface to it. The demo's fourth panel shows the contrast: a module-scope variable genuinely is shared, and that is the mechanism people are mistakenly imagining.

2. Explain the rule against conditional hooks in terms of the mechanism.

React stores hook state in an ordered array per component and walks it with a cursor on each render. A useState call contains nothing identifying which state it wants — its position in the call sequence is the identifier. Skip a hook on one render and every subsequent call shifts by one, reading the previous hook's slot: your state returns another hook's value, an effect gets the wrong dependencies, a memo returns something unrelated. Nothing throws; the values are simply wrong, which is why it produces such bizarre bugs. An early return is fine provided every hook runs before it, and the fix for a genuinely conditional hook is to call it unconditionally and let it do nothing internally.

3. When should logic go in a hook rather than a shared component?

When the two places behave the same but look different. A component shares appearance and structure; a hook shares stateful logic and returns data with no opinion about markup. The failure mode of getting it wrong is a wrapper component with a flag choosing between two layouts — Chapter 3's configuration smell. The clearest example is a combobox: the keyboard handling, filtering and selection logic is identical everywhere, while the markup differs per design, so useCombobox() plus per-site JSX is the right split. That is precisely how headless component libraries are built.

4. Why should a hook memoise the functions it returns?

Because you do not know your callers. A function returned fresh on every render will be a changing dependency in someone's effect — re-running it every render, possibly in a loop — and will defeat memo on any child it is passed to, exactly as Chapter 10's demo shows. Inside a single component you can see whether identity matters; inside a hook used in twenty places you cannot, so wrap returned functions in useCallback and returned objects in useMemo. This is the one context where memoisation is not premature. The React Compiler removes the need where it is enabled, but a hook meant to be shared should not assume that.

5. Why prefer useSyncExternalStore over useState plus a subscribe effect?

Three reasons, all of which the manual version gets subtly wrong. It prevents tearing: during a concurrent render, components reading an external value at different moments could otherwise show inconsistent data within one frame. It closes the gap between render and the effect subscribing, during which an update can be missed entirely. And it takes an explicit server snapshot, so the component can be server-rendered without touching window. Use it for media queries, online status, the URL, visibility state and any store-like source. The one trap is that the snapshot function must return a cached value — returning a fresh object each call loops forever.
