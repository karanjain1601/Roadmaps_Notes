CHAPTER 22

Testing React

A test suite is worth having when it catches real breakage and does not fail for reasons nobody cares about. Almost everything in this chapter follows from one principle: test what the component does, never how it does it.

Part 6 Craft·Reading time 40 minutes·Demos surviving a refactor, mocking layers·Prerequisites Chapters 13–14

1The principle

One sentence, and the rest is consequences.

The more your tests resemble the way the software is used, the more confidence they give you. A test that asserts on state variable names, class names, prop plumbing or render counts is coupled to decisions you should be free to change. When it breaks during a refactor that broke nothing, it has cost you time and taught you nothing — and after that happens a few times, people start deleting tests instead of fixing them.

3The stack

Four choices, with a defensible default for each.

ChoiceDefault, and why
RunnerVitest for anything Vite-based — same config, same transforms, fast watch mode. Jest remains fine and is what most existing suites use.
Environmentjsdom by default: fast, and close enough for most component tests. Browser mode (Vitest) or Playwright component testing when layout, scrolling or real events matter — jsdom has no layout engine, so anything measuring sizes will lie to you.

4Interactions and async

Where most of the day-to-day friction is.

The four things to get right JSX
// 1. userEvent, not fireEvent. Typing a character really involves
//    pointerdown, focus, keydown, keypress, input, keyup — fireEvent
//    dispatches one synthetic event and skips the rest, so it passes
//    on components that would fail for a real user.
const user = userEvent.setup();
await user.click(screen.getByRole('button', { name: /save/i }));
await user.type(screen.getByLabelText(/email/i), 'rae@example.com');

// 2. findBy for things that appear later. It retries until it exists.
await screen.findByText(/saved/i);

// 3. queryBy ONLY for asserting absence — it returns null instead of throwing.
expect(screen.queryByRole('alert')).not.toBeInTheDocument();

// 4. No arbitrary waits. Ever.
await new Promise(r => setTimeout(r, 500));    // ✗ slow AND flaky
await waitFor(() => expect(save).toHaveBeenCalled());  // ✓ retries with a timeout
The act() warning
It means state updated outside anything React was tracking — almost always an async update that finished after your assertion. The fix is virtually never to wrap things in act manually: it is to await the thing you were waiting for, with findBy or waitFor. Treat the warning as a signal that a test is racing, not as noise to silence.
Fake timers
Necessary for debounces and polling, and they interact badly with userEvent unless you pass advanceTimers in the setup. If a test hangs after adding fake timers, that is usually why.
Render once, then interact
A test that calls rerender repeatedly to check intermediate output is testing the render cycle rather than the behaviour.

6The levels

Four kinds of test, with a rough allocation that holds up in practice.

LevelShareBest at
Unit~30%Pure functions: reducers, validators, formatters, calculations. Milliseconds each, and the place to test every edge case exhaustively rather than through the interface.
Component~50%One component or a small group, through its interface. The best return on effort, and where most of your suite belongs.
Integration~15%A whole feature with real routing and MSW: submit a form, see the list update. Catches wiring mistakes no component test can see.
End to end~5%A real browser against a real backend. Reserve for the few journeys where failure is unacceptable — sign in, checkout, the main task. Slow and the most likely to flake, so keep the set small and looked after.

Also worth having, and cheap: type checking as the widest safety net (Chapter 17), and visual regression for a design system, where "it looks wrong" is exactly what no assertion catches.

7What not to do

Six habits that produce a suite people stop trusting.

Do not mock the component under test's own children
Mocking them out leaves you asserting that you passed some props, which is the plumbing, not the behaviour.
Do not mock your own hooks or state library
Render with a real provider and real state. Mocking useCart to return fixed data tests nothing about how the component uses it.
Do not chase 100% coverage
Coverage measures which lines ran, not whether they were verified. The last twenty per cent is usually error paths and glue, and pursuing the number produces tests written for the number.
Do not snapshot whole components
Large snapshots fail on every markup change, get regenerated without being read, and end up asserting nothing while looking thorough. Small, targeted snapshots of serialisable data are fine.
Do not assert on render counts
That is Chapter 10's territory and it changes with a compiler upgrade.
Do not test the library
React Router routes, React Query caching and your component library's internals are already tested. Test your usage of them.

8Flakiness

A suite that fails randomly is worse than no suite, because it trains people to ignore red.

Where it comes from
Arbitrary timeouts instead of findBy. Shared state leaking between tests. Real timers and animations. Test order dependence. Unmocked network. Time zones and locale differences between your machine and CI.
Fixes
Reset everything between tests — MSW handlers, the query client, storage, mocks. Never use a bare setTimeout to wait. Freeze time and locale. Run the suite in a random order locally so ordering bugs surface before CI finds them.
The compounding arithmetic
A single test that fails one time in two hundred is invisible. Four hundred such tests means most runs are red, and at that point every failure gets a re-run rather than an investigation.
Quarantine rather than retry
Automatic retries hide flakes and let them accumulate. Move a flaky test out of the blocking suite with an owner and a date; fix it or delete it.

9Check yourself

Five questions.

1. What makes a test "implementation" rather than "behaviour"?

Whether it would survive a change that nothing visible depends on. Asserting that a state variable is called isOpen, that a .menu--active class is applied, that a callback was invoked once, or that a snapshot matches — all of those couple the test to decisions you should be able to change freely. The demo is the practical test: rename the state, swap the class names, replace a div with a real button, and see which assertions break even though the user experience is identical. Every such failure costs time and teaches nothing, and after enough of them people delete tests rather than fix them.

2. Why is getByRole the recommended query?

Because it finds elements the way assistive technology does — by their role in the accessibility tree and their accessible name — which is both the most refactor-resistant identifier and a real property of the interface. Class names and test ids are invented; a button's role as a button is not. The side effect is the valuable part: if you cannot query something by role, it usually means it has no accessible name or the wrong semantics, so it is also broken for a screen-reader user. The test suite becomes a partial accessibility check without anyone deciding it should be one.

3. Why prefer MSW over mocking your fetch module?

Because it intercepts at the network layer, leaving your real client code, real error handling, real parsing and real cache configuration in the path — so a bug in any of those can still be caught. Mocking the module replaces all of that with a stub, meaning the test cannot see a wrong URL, a missing header, a mishandled non-200 response, or a broken retry. The same handlers also work in the browser during development and in end-to-end tests, and they do not break when you rename or restructure the client. The demo's point is the count: each layer you mock away is a set of bugs the test becomes structurally unable to detect.

4. A test logs an act() warning. What is it telling you?

That state updated outside anything React was tracking — nearly always an async operation that resolved after your assertions ran and the test finished. It is a race, and the fix is almost never to wrap code in act manually. Await the outcome instead: await screen.findByText(...) for something that appears, or await waitFor(() => expect(...)) for a condition. Treat the warning as a genuine signal rather than noise, because a test that passes while racing will eventually fail on a slower CI machine, and it will be blamed on infrastructure.

5. Why is 90% coverage a poor target?

Because coverage measures which lines executed, not whether anything meaningful was asserted about them — a test that renders a component and asserts nothing produces excellent coverage. Chasing the number therefore produces tests written for the number: snapshots that nobody reads, assertions on implementation details that break on refactor, and effort spent on error paths and glue code that were never going to fail. Coverage is useful read in the other direction, as a way to spot important code with no tests at all. What matters is whether the suite catches real breakage and stays quiet during safe changes, and no percentage measures that.
