CHAPTER 02

JSX and what it compiles to

JSX looks like HTML in your JavaScript, which is a useful illusion and an occasionally expensive one. It is neither HTML nor a template language: it is syntax for a function call that returns a plain object. Once you have seen the object, most of JSX's rules stop being rules and become obvious.

Part 1 The model·Reading time 40 minutes·Demos a working renderer, what renders·Prerequisites Chapter 1

1It is a function call

One transform, applied by your build step. Everything in this chapter follows from it.

What the compiler does before and after
// You write:
<button className="primary" onClick={save}>
  Save {count} items
</button>

// The compiler emits (modern automatic runtime):
jsx('button', {
  className: 'primary',
  onClick: save,
  children: ['Save ', count, ' items']
});

// Which returns, at runtime, a plain object:
{
  $$typeof: Symbol(react.element),
  type: 'button',
  props: { className: 'primary', onClick: save, children: [...] },
  key: null
}
The tag becomes the type
A lowercase name becomes the string 'button', which React understands as a DOM element. A capitalised name becomes a reference to your function. That is the entire reason components must be capitalised: <card /> compiles to the string 'card' and React looks for an HTML element called card.
Attributes become props
An ordinary object. Which is why a prop can be a number, a function, an array, another element — anything JavaScript has.
Nested tags become children
children is just another prop. <Card>hello</Card> and <Card children="hello" /> are the same call.
Nothing has rendered yet
Creating an element is cheap and does nothing. It is a description sitting in memory. Rendering happens later, when React decides to — Chapter 4.

You may still see React.createElement in older code and older articles. It produces the same objects; the newer jsx() runtime just removes the need to import React in every file.

Why this matters more than it looks

Because elements are ordinary values, you can put them in a variable, in an array, in a Map, return them from a function, pass them as props, and choose between them with an if. There is no template syntax to learn for conditionals or loops — you use JavaScript, because it is JavaScript. That is JSX's actual advantage over template languages, and it is also why the composition patterns in Chapter 23 are possible at all.

3The syntax rules, and their reasons

Each of these is a consequence of section 1, not an arbitrary decision.

RuleBecauseExample
One root element A function returns one value Wrap in a <div>, or in a fragment <>…</> when you do not want the extra node
className, not class Props map to DOM properties, and class is a reserved word className, htmlFor
camelCase props Same reason — they are JavaScript identifiers onClick, tabIndex, strokeWidth
data- and aria- stay hyphenated They are genuine attributes with no property equivalent aria-label, data-testid
Everything self-closes The parser needs to know where children end <img />, <br />, <Spinner />
Braces for values Anything not in braces is a string literal count={3} is a number; count="3" is a string
style takes an object It is a property assignment, not an attribute string style={{ marginTop: 8 }} — the double braces are an object inside an expression
Comments go in braces There is no JSX comment syntax {/* like this */}
Spreading, defaults and the props object JSX
// Spread works because props is an object
const shared = { size: 'lg', tone: 'quiet' };
<Button {...shared} onClick={save}>Save</Button>

// Later keys win, so this lets a caller override a default…
<Button size="sm" {...shared} />   // size is 'lg' — shared wins
<Button {...shared} size="sm" />   // size is 'sm' — order matters

// A boolean prop with no value is `true`
<input disabled />              // disabled={true}

// Defaults are ordinary JavaScript, in the parameter list
function Button({ size = 'md', tone = 'solid', children, ...rest }) {
  return <button className={`btn ${size} ${tone}`} {...rest}>{children}</button>;
}
// The ...rest spread is how a component stays open to aria-*, data-*,
// id, and every other attribute you did not think to enumerate.

4What actually renders

The rules are short, and one of them is responsible for a bug you will write within a month.

Each value, put in a slot The middle column is real output from a faithful implementation of React's rules.

Strings and numbers render as text
Including 0 and NaN. React escapes them, so a value containing <script> appears as text rather than markup — which is why React applications are largely free of the injection problems of string templating.
null, undefined, true and false render nothing
Not the string "null" — literally nothing. This is what makes conditional rendering work at all.
Arrays are flattened and each item rendered
Which is why {items.map(...)} works with no special syntax. React will warn about missing keys — section 6.
Objects throw
"Objects are not valid as a React child" is almost always a forgotten property access: {user} where you meant {user.name}. The one exception is an element, which is technically an object React recognises.

5Conditionals

Three forms, and the trap in the most popular one.

Choosing what to render JSX
// 1. Ternary — when you need one thing OR another
{isLoggedIn ? <Dashboard /> : <SignIn />}

// 2. Logical AND — when you need one thing OR nothing
{hasErrors && <ErrorSummary errors={errors} />}

// 3. Early return — when the whole component differs
if (!data) return <Skeleton />;
return <Report data={data} />;
The zero trap

{items.length && <List items={items} />} renders a literal 0 on the page when the list is empty. && returns its left operand when that operand is falsy, and unlike false, the number 0 does render — section 4's table shows it. The same happens with an empty string in some contexts. Fix it by coercing to a boolean (items.length > 0 && …) or by using a ternary. This is the single most common JSX bug and it survives code review constantly, because the code looks correct.

Nested ternaries
Two is the practical limit before nobody can read it. Beyond that, extract a small function that returns an element, or use a lookup object keyed by status — which reads better and pairs well with the discriminated unions in Chapter 17.
Do not conditionally call hooks
An early return is fine, but every hook must run before it. if (!data) return null; placed above a useState breaks rule 3 from Chapter 1. The linter catches this.

6Lists and keys

Keys are not for you and not for the DOM. They are how React knows which element is which between two renders.

The standard shape JSX
<ul>
  {orders.map(o => (
    <li key={o.id}>{o.reference} — {money(o.total)}</li>
  ))}
</ul>

// The key goes on the outermost element produced by the map.
// If the map returns a component, the key goes on the component,
// not on something inside it.

// With a fragment that needs a key, use the long form —
// the shorthand <> cannot take props.
{rows.map(r => (
  <Fragment key={r.id}>
    <dt>{r.term}</dt><dd>{r.def}</dd>
  </Fragment>
))}
What a key actually does
During reconciliation React matches the new children against the old ones. With keys it matches by key; without them it matches by position. The key tells React "this is the same item as before, keep its DOM node and its state" — or "this is a different item, throw the old one away".
Why the index is usually wrong
Delete the first item and every subsequent element is compared against the wrong original. Instead of removing one node, React patches text down the entire list, and anything attached to the element rather than to the data moves to the wrong row: input values, focus, an open menu, a running transition, uncontrolled component state. Index keys are safe only for a list that is never reordered, inserted into or deleted from — at which point they are doing nothing.
Keys must be stable and unique among siblings
Not globally unique. And never Math.random() or crypto.randomUUID() generated during render: a new key every render means React destroys and recreates every node, every time, which is both slow and state-destroying.
Keys work outside lists too
Changing the key on any element tells React to discard the old instance and mount a fresh one. That is the idiomatic way to reset a component's state when a prop changes — <Editor key={documentId} /> — and it appears again in Chapter 5.
Keys are not readable from inside
props.key is undefined; React consumes it. If the child needs the id, pass it again as a normal prop.

7Five things worth knowing early

Small pieces of JSX behaviour that cause disproportionate confusion.

Whitespace
JSX trims leading and trailing whitespace on lines and collapses blank lines, so two elements on separate lines have no space between them. When you need one, write {' '} explicitly — or better, use CSS gap, which does not depend on invisible characters.
dangerouslySetInnerHTML
The escape hatch for rendering HTML strings: <div dangerouslySetInnerHTML={{ __html: html }} />. The name is a warning label, and the awkward shape is deliberate. Sanitise with DOMPurify first, always — there is no exception where trusting the source is sufficient.
Elements as props
<Modal footer={<Actions />} /> is completely normal. A prop holding an element is the basis of slot-style composition, and Chapter 23 builds several patterns on it.
JSX does not evaluate lazily
{cond ? <Heavy /> : null} only creates the element when the condition holds — but note that creating an element never runs the component. The function runs when React renders it, which is Chapter 4's distinction between describing and rendering.
Capitalisation and dots
<Card.Header /> works because a member expression is treated as a reference. A variable holding a component must be capitalised at the point of use — const Icon = icons[name]; <Icon /> — or JSX will emit the string.

8Check yourself

Six questions.

1. Why must component names be capitalised?

Because the compiler uses the case of the tag to decide what to put in type. A lowercase name becomes a string — jsx('div', …) — which React interprets as a DOM element to create. A capitalised name becomes a reference to the identifier in scope — jsx(Card, …). So <card /> compiles to the string 'card' and React tries to create an unknown HTML element, silently producing nothing useful. The same rule bites when you pull a component out of an object or array: assign it to a capitalised variable first.

2. {cart.length && <Basket />} renders a stray "0". Explain precisely.

&& evaluates to its left operand when that operand is falsy, so with an empty cart the expression's value is the number 0, not false. React's rendering rules then apply: false, null, undefined and true render nothing, but numbers render as text — so 0 appears on the page. The fix is to make the left operand a genuine boolean (cart.length > 0 && …) or to use a ternary with an explicit null. Empty strings behave similarly in some positions. It is the most common JSX bug precisely because the code reads as correct.

3. What is an element, and what has happened by the time one exists?

A plain JavaScript object of roughly the shape { type, props, key } — a description of what should be on screen, not a thing on screen. Creating one is cheap: it does not touch the DOM, does not run your component function if the type is a component, and does not schedule anything. It is a value, which is why you can store it in a variable, put it in an array, pass it as a prop or return it from a function. Rendering — turning descriptions into DOM operations — happens separately, when React decides to, which is Chapter 4.

4. Why is key={Math.random()} worse than a bad key?

Because it guarantees a mismatch on every single render. A key's job is to say "this is the same item as last time". A fresh random value means no new child ever matches an old one, so React unmounts every node and mounts a replacement each render: all DOM nodes recreated, all component state in the list destroyed, focus lost, transitions restarted, and scroll position in any child reset. An index key at least matches sometimes and only misbehaves when the list changes shape. The right answer is a stable id from the data; if the data genuinely has none, generate ids once when the items are created and store them, not during render.

5. You see "Objects are not valid as a React child". What happened?

Something rendered a plain object where React expected text or elements — almost always a missing property access, such as {user} instead of {user.name}, or a Date, or the whole response from an API. React can render strings, numbers, elements, arrays of those, and the render-nothing values (null, undefined, true, false); everything else throws rather than showing [object Object], which is a deliberate and helpful choice. The error message usually names the offending keys, which is enough to find the expression.

6. What does changing the key on a single, non-list element do?

It tells React the element is a different thing from the one that was there before, so React unmounts the old instance — destroying its state and running any cleanup — and mounts a fresh one. That is not a side effect of keys, it is what keys mean; lists are simply the most common place you need to express it. In practice it is the idiomatic way to reset a component when a prop changes: <ProfileEditor key={userId} /> clears the draft when you switch users, with no effect and no useEffect resetting state. Chapter 5 returns to this as the preferred alternative to a resetting effect.
