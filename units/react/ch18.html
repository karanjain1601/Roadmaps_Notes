CHAPTER 18

Errors, boundaries and resilience

By default, one thrown error during render unmounts your entire application and leaves a white page. That is deliberate — React would rather show nothing than something wrong — and it means deciding where the damage stops is your job.

Part 4 Building an application·Reading time 35 minutes·Demos what boundaries catch, where to place them·Prerequisites Chapters 12–13

1The default is a white page

And that is a considered choice, not an oversight.

If a component throws during render and nothing catches it, React unmounts the whole tree from the root. The reasoning: a half-rendered interface built on inconsistent state can show a wrong balance, submit the wrong form or delete the wrong record, and a blank page is less dangerous than a plausible lie. Your job is not to prevent the unmount but to contain it — so a broken recommendations panel does not take checkout with it.

The only thing that still requires a class JSX
class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };            // render phase — decide what to show
  }

  componentDidCatch(error, info) {
    report(error, { componentStack: info.componentStack });   // commit phase — log
  }

  render() {
    if (this.state.error) {
      return this.props.fallback(this.state.error, () => this.setState({ error: null }));
    }
    return this.props.children;
  }
}

// In practice use react-error-boundary: same thing plus onReset,
// resetKeys, a useErrorBoundary hook and sensible TypeScript types.
// Frameworks provide their own — Next's error.tsx, React Router's
// errorElement — which are route-level boundaries with the same model.

The rule of thumb
A boundary catches errors thrown during rendering, in lifecycle methods, and in constructors of the tree below it. Everything asynchronous or user-initiated escapes it, because by the time those run React is no longer on the stack.
Event handlers
Wrap in try/catch and set an error state, or let a mutation library own it — useMutation gives you an error field without any try/catch. To route a handler error into a boundary deliberately, react-error-boundary's showBoundary does exactly that.
Async and promises
An unhandled rejection in an effect never reaches a boundary. Either handle it and set state, or use a query library whose error you render — and note that a query can also be configured to throw to the nearest boundary, which is often the tidiest arrangement.
Server rendering
Boundaries work during server rendering, but an error there means the HTML is already partly streamed. Frameworks handle this by streaming the fallback for the affected boundary; it is another reason to have more than one.
Errors in the fallback itself
Caught by the next boundary up, and if there is none you are back to a white page. Keep fallbacks trivial: no data access, no hooks that can fail, no clever formatting of the error object.

4Pairing with Suspense

Two boundaries, two jobs, and the order matters.

The standard arrangement JSX
<ErrorBoundary fallback={<ReportError />}>
  <Suspense fallback={<ReportSkeleton />}>
    <Report id={id} />
  </Suspense>
</ErrorBoundary>

// Error boundary OUTSIDE. Suspense handles "not ready yet"; the error
// boundary handles "it went wrong". If a suspended promise rejects, the
// error must be able to escape the Suspense boundary to reach it.
//
// The two fallbacks should occupy the same space as the content, so
// neither loading nor failing shifts the rest of the page (Chapter 12).
They are not alternatives
Suspense has no error concept and an error boundary has no loading concept. A region that fetches wants both, and the pair is what makes a boundary a genuine unit of independent failure.
Reset them together
resetKeys={[id]} on the error boundary clears the error when the id changes, so navigating to a different report does not leave the previous failure on screen. Without it a user is stuck until a full reload.
Frameworks give you both per route
Next's error.tsx and loading.tsx, React Router's errorElement plus deferred data. Use them rather than hand-rolling the route level, and add feature-level boundaries yourself.

Two things a fallback must never do

Throw. A fallback that reads error.response.data.message will itself throw on a network error, and the failure escalates to the next boundary — often the root, converting a contained problem into a white page. Keep fallbacks trivial.

Retry automatically, forever. A boundary that resets itself on a timer against a component that always throws produces an infinite render loop that pins the CPU. Retry must be user-initiated, or bounded and backed off.

6Recovery

An error boundary that can only be escaped by reloading is barely better than the white page.

Reset on the thing that changed
resetKeys, or a key on the boundary tied to the route or the entity id. Navigating away and back should clear the error without a reload.
Retry that actually retries
Resetting the boundary re-renders the same component with the same inputs, so unless something else changed it will throw again immediately. Pair the reset with an action that changes the input — invalidating the query, refetching, incrementing an attempt counter.
Distinguish transient from permanent
A network blip deserves a retry button. A 404 deserves "this order does not exist" and a link to the list. A 403 deserves "you do not have access". Rendering all three as "something went wrong" wastes information you already have — which is why HTTP errors are better handled as data by a query library than thrown to a boundary.
Degrade rather than fail
If the recommendations service is down, render the page without recommendations. The best error handling is often a region that quietly does not appear.
The chunk-load failure
After a deploy, an open tab's lazily imported chunk may no longer exist, so the import rejects and the route never renders. Detect it specifically and prompt a reload — it is the one case where "reload the page" is genuinely the right answer, and it is common enough to deserve its own message.

7Reporting

An error you cannot reproduce is an error you cannot fix. Context is the whole game.

What to attach JSX
componentDidCatch(error, info) {
  report(error, {
    componentStack: info.componentStack,   // React's tree, not just the JS stack
    route: currentRoute(),
    release: __BUILD_ID__,                 // attribute a spike to a deploy
    userSegment: plan,                     // never PII
    lastActions: breadcrumbs()             // what they did in the last few seconds
  });
}

// Also capture what boundaries never see:
addEventListener('error', e => report(e.error));
addEventListener('unhandledrejection', e => report(e.reason));
Source maps, uploaded at build time
Without them every stack trace is minified nonsense and the tracker is decoration. Upload them privately rather than serving them.
The component stack is the useful part
A JavaScript stack tells you which function threw; the component stack tells you where in the interface, which is usually what you need to reproduce it.
Filter aggressively
Browser extensions, third-party scripts, cancelled navigations and offline blips generate enormous volume. An unfiltered tracker is one nobody reads, which is the same failure as not having one.
Alert on a rate change, not on errors
Every application has a baseline. What matters is a spike, and whether it started at a deploy.
Error tracking is not monitoring
The most damaging failures often throw nothing at all — a button that silently does nothing, a form that posts to the wrong endpoint. Pair the tracker with metrics on things users actually complete.

8Check yourself

Five questions, closing Part 4.

1. Why does React unmount the entire tree on an uncaught render error?

Because a partially rendered interface built on inconsistent state can be actively dangerous — showing a stale balance, enabling the wrong action, or submitting against the wrong record — and React's designers judged that a blank page, while bad, is less harmful than a plausible-looking lie. It is also honest: something is broken and the user finds out immediately rather than discovering it after acting on wrong information. The consequence for you is that containment is a design decision you must make explicitly, by placing boundaries where you have decided a failure is allowed to stop.

2. Your click handler throws and the error boundary does nothing. Why?

Because boundaries only catch errors thrown while React is rendering — during render, lifecycle methods and constructors of the tree below them. An event handler runs in response to a browser event, long after rendering finished, so React is not on the stack and there is nothing to catch it; the error goes to window.onerror and the interface simply does not respond. The same applies to timers, promise callbacks and effects that reject. Handle it locally with try/catch and an error state, let a mutation library own it, or deliberately push it into a boundary with showBoundary from react-error-boundary.

3. Where should error boundaries go?

Three levels. One at the root, always, so the worst case is a branded page rather than a white one, and so everything gets reported. One per route, which is the highest-value addition: a broken page keeps the shell, so the user can navigate elsewhere without reloading and without losing their session. And one around each independent feature — a widget, a panel, a third-party embed — so an optional region cannot remove an essential one. Not around every component: eight "something went wrong" boxes on one page is worse than one honest error, and nobody designs eight fallbacks properly.

4. Why does resetting an error boundary often not fix anything?

Because it re-renders the same component with the same props and state, so whatever threw will throw again immediately — and if the reset is automatic, that is an infinite loop pinning the CPU. A reset must be paired with something that changes the input: invalidate or refetch the query, increment an attempt counter that flows into the component, or tie the boundary's resetKeys to the route or entity id so navigating away genuinely clears it. And retry should be user-initiated or bounded with backoff, never an unconditional timer.

5. Should a 404 from your API be thrown to an error boundary?

Usually not. A 404 is not an exceptional condition — it is a known outcome with a specific, useful response: "this order does not exist" plus a link back to the list. The same for 403, and for a validation failure. Throwing all of them to a boundary collapses distinct situations into one generic "something went wrong", discarding information you already had and giving the user no way forward. Handle expected HTTP outcomes as data, which is what a query library's error field is for, and reserve boundaries for the genuinely unexpected: a bug in your rendering code, a malformed response that broke a component, a chunk that failed to load.
