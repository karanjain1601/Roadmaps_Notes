CHAPTER 07

Context

Context is a delivery mechanism, not a store. It answers "how does this value reach a component forty levels down" and says nothing at all about how the value is managed — and the gap between those two questions is where most misuse of it comes from.

Part 2 State·Reading time 35 minutes·Demos re-render cost, plumbing comparison·Prerequisites Chapters 4–5

1The problem, and the cheaper fix

Prop drilling is a symptom. Context is one of four treatments and not always the right one.

Passing a value through four components that do not use it is tedious and makes each of those components harder to reuse. The instinct is to reach for context — but the alternatives are often better, and the demo below counts the actual cost of each.

Try these first, in order
Move the state down if only one branch needs it. Pass the rendered element as children so the intermediate layers never see the value — Chapter 3's answer and Chapter 4's escape hatch, in one move. Colocate the data so the consumer fetches what it needs. Only then reach for context.
Context is right for genuinely ambient values
Theme, locale, the current user, a router, a feature-flag set, a form's registration object. Things that a large and unpredictable set of components might need, where enumerating the path would be absurd.
The real cost of drilling is not typing
It is that four components now have a prop they do not use, so none of them can be reused without it, and their interfaces lie about what they need. That is the argument — not the keystrokes.

2The API

Three pieces, and one of them changed recently.

Create, provide, consume JSX
// 1. Create it once, at module scope. The argument is the value used
//    when a consumer has no provider above it.
const ThemeContext = createContext('light');

// 2. Provide. React 19 lets you render the context itself;
//    before that it was <ThemeContext.Provider>.
<ThemeContext value={theme}>
  <App />
</ThemeContext>

// 3. Consume, at any depth.
const theme = useContext(ThemeContext);

// The nearest provider above wins, so a subtree can override —
// a dark panel inside a light page needs no special support.
The default value is a fallback, not a default
It is used only when there is no matching provider anywhere above. In practice that usually means a bug, which is why section 5 wraps useContext in a hook that throws instead.
Context is not global
It is scoped to a subtree. Two providers of the same context in different parts of the tree hold independent values, and nesting overrides.
It carries anything
A value, an object, a function, a whole [state, dispatch] pair from Chapter 6. Nothing about context knows or cares.

3What it costs

One sentence, and it is the reason this chapter is not shorter: context has no selector.

When a provider's value changes, every component that calls useContext for it re-renders — whether or not the part it reads actually changed. There is no way to subscribe to a slice. On a context holding one string this is irrelevant; on a context holding an object with eight fields consumed by ninety components, it is the performance problem.

The identity trap

<Ctx value={{ user, setUser }}> creates a new object on every render of the provider component. React compares context values with Object.is, so every consumer re-renders every time the provider re-renders — even when user has not changed at all. Wrap it: const value = useMemo(() => ({ user, setUser }), [user]). Select the second option in the demo to see the difference; it is the most common context performance bug and it is invisible until you profile.

4Splitting providers

Without a selector, the only lever you have is granularity.

The state/dispatch split, and why it works JSX
// Two contexts instead of one. `dispatch` is stable forever, so
// components that only dispatch never re-render when state changes.
const CartStateContext = createContext(null);
const CartDispatchContext = createContext(null);

function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, initial);
  return (
    <CartStateContext value={state}>
      <CartDispatchContext value={dispatch}>{children}</CartDispatchContext>
    </CartStateContext>
  );
}

// An "Add to basket" button anywhere in the app now costs nothing
// when the cart changes — it reads dispatch, which never changes.
Split by update frequency
Theme changes twice a year; a toast queue changes every few seconds; a cursor position changes sixty times a second. Putting all three in one provider means the theme consumers re-render at 60Hz. Separate contexts, always.
Split state from actions
The pattern above. Actions are stable, so their consumers are free.
Memoise the value
Any object or array passed as a context value needs useMemo, and any function inside it needs useCallback — or, better, comes from a reducer's dispatch, which is stable without either.
Keep high-frequency data out entirely
Scroll position, drag coordinates, form field values while typing. These belong in local state, a ref, or a store with a selector — never in a context that a large subtree consumes.
Provider nesting is not a smell
Six providers at the root looks alarming and costs nothing at runtime. If the wrapper pyramid bothers you, compose them into a single <AppProviders> component.

5Always wrap it in a hook

Four lines that improve every call site and catch the most common setup bug.

The standard shape TypeScript
const ThemeContext = createContext<Theme | null>(null);

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (ctx === null) {
    throw new Error('useTheme must be used inside <ThemeProvider>');
  }
  return ctx;   // narrowed to Theme — no null checks at 40 call sites
}

// Export the hook and the provider. Do NOT export the context itself:
// consumers should not be able to read it raw, and you keep the freedom
// to swap the implementation for a store later without touching them.

Three benefits: the null case becomes an immediate, well-worded error instead of a silent default that produces confusing behaviour much later; TypeScript narrows the type once rather than at every call site; and the context becomes an implementation detail you can change.

6Context or a store?

They are not competitors so much as answers to different questions.

ContextExternal store (Zustand, Jotai, Redux)
What it isDelivery — a value available to a subtreeStorage plus delivery, with subscriptions
SelectorsNone. Consumers re-render on any changeYes. Subscribe to one slice
ScopingPer subtree; nesting overridesUsually one global instance, though most support scoped ones
Outside ReactNoYes — read and write from anywhere
Devtools, time travelNoUsually
DependenciesNone, it is built inOne more library
Server componentsClient components onlyClient components only

A reasonable default: context for ambient values that change rarely — theme, locale, user, router, feature flags — and a small store for shared UI state that changes often and is read by many components. Server data belongs in neither: it goes in a query cache, which is Chapter 13, and putting it in a store is the single most common architectural mistake in React applications.

7Five mistakes

Each is common enough to have caused a rewrite somewhere.

1 · One context holding everything
An AppContext with user, theme, cart, modals, toasts and a scroll position. Every consumer re-renders on every change of any of them, and nothing can be moved without touching everything. Split it.
2 · An unmemoised object value
Section 3's identity trap. Costs nothing to fix and is invisible until profiled.
3 · Server data in context
Fetching in a provider and sharing the result gives you a hand-rolled cache with no staleness policy, no deduplication, no revalidation, no error state and no cancellation. Chapter 13.
4 · Context as a substitute for composition
Reaching for a provider when passing children would have done. The provider makes the dependency invisible: nothing in a component's signature says it needs a theme, so moving it breaks it at runtime rather than at the type level.
5 · Testing pain as a signal ignored
If every component test needs six providers wrapped around it, the components are coupled to ambient state they should probably receive as props. Build a single test wrapper by all means — but notice what it is telling you.

8Check yourself

Five questions.

1. Why is context described as a delivery mechanism rather than a store?

Because it holds nothing and manages nothing. The value still lives in ordinary state somewhere — usually useState or useReducer in a provider component — and context only makes that value readable from anywhere below without threading it through props. Everything a store gives you beyond that is absent: no subscriptions to a slice, no reading or writing from outside React, no devtools, no middleware. That is why "should I use context or Redux" is a slightly malformed question: context is how a value reaches a component, and a store is how a value is managed. You can and often do use both together.

2. A context value is {{ user, setUser }} written inline. What is the consequence?

A new object is created on every render of the provider component, and React compares context values by identity — so every single consumer re-renders whenever the provider re-renders, even if user is unchanged and even if the provider re-rendered for an unrelated reason. On a large subtree that is a continuous, invisible cost. Wrap it in useMemo with the real dependencies, and make sure any functions inside are stable too, either via useCallback or by using a reducer's dispatch, which never changes identity. The demo's second option shows the difference: the same change re-renders every consumer instead of only the ones that care.

3. What is the fundamental limitation context has that a store does not?

No selector. Subscribing to a context means subscribing to the whole value: a component that reads only theme from a context also holding cart re-renders on every cart change. A store lets each component subscribe to a slice and re-render only when that slice changes, which is precisely the capability context lacks. Without it, granularity is the only lever you have — split the provider by update frequency, split state from dispatch, and keep high-frequency values out entirely. Once you find yourself splitting a context five ways to control re-renders, you have reimplemented a store badly and should use one.

4. Why wrap useContext in a custom hook that throws?

Because a missing provider otherwise fails silently. Without a provider, useContext returns the default value passed to createContext, so the component renders with a fallback theme or a null user and misbehaves somewhere unrelated, much later. A hook that checks for null and throws with a specific message turns that into an immediate, self-explaining failure at the exact component. It also narrows the type once instead of forcing a null check at forty call sites, and it hides the context object itself — so the storage can be swapped for a store later without touching any consumer.

5. Should fetched data go in context?

No. Fetching in a provider and sharing the result means hand-rolling a cache, and you will get a poor one: no staleness policy, no background revalidation, no deduplication when three components ask for the same thing, no cancellation of superseded requests, no retry, no error state per query, and no invalidation after a mutation. That is a large amount of well-understood machinery to reimplement badly. Server data belongs in a query cache — Chapter 13 — which does all of it and needs no context at all, because the cache is keyed rather than positional. Context remains right for the client values around it: the current user's identity, the selected locale, the theme.
