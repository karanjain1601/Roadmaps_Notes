CHAPTER 26

Performance

Not "make it fast" but "measure the specific thing users experience, attribute it to a cause, and fix the cause". Three metrics, each of which decomposes into parts you can act on independently — and a discipline for stopping the improvement from decaying next quarter.

Part 7 Shipping and practice·Reading time 50 minutes·Demos interaction latency, LCP attribution·Prerequisites Chapters 1–3, 23

1What to measure

Metrics that correspond to a question a user would ask, rather than to something easy to instrument.

MetricThe user's questionGoodDefinition
LCPIs it loaded?≤ 2.5 s When the largest text block or image in the viewport finishes rendering. A proxy for "the main content is there".
INPIs it responsive?≤ 200 ms Interaction to Next Paint: for each interaction, the time from input to the next frame showing a visual response. The reported value is roughly the worst of the visit, so it reflects the frustrating one rather than the average.
CLSDoes it stay still?≤ 0.1 Cumulative Layout Shift: the largest burst of unexpected movement, scored as impact fraction × distance fraction.
TTFB—≤ 0.8 s Diagnostic. Everything from navigation start to the first byte. Chapters 1 and 2.
FCPIs anything happening?≤ 1.8 s Diagnostic. The first pixel of content.
TBT—≤ 200 ms Total Blocking Time: the sum of everything over 50 ms in each long task during load. The lab stand-in for INP, because a synthetic run has no real interactions to measure.

The thresholds are applied at the 75th percentile of real visits. "Good LCP" means three quarters of your users saw it in 2.5 seconds — not that the median did.

The metrics that stopped being useful

load and DOMContentLoaded measure browser events, not experience: a page can fire load in 800 ms and be blank, or fire it at 12 s having been usable since second two. First Input Delay was replaced by INP because it measured only the first interaction and only its queuing delay, which flattered pages that were slow throughout. Time to Interactive was dropped for being noisy and hard to act on.

2Lab and field

Two kinds of data that answer different questions, and disagree for good reasons.

Lab (synthetic)Field (real user monitoring)
What it isOne scripted run on a controlled machineMeasurements from actual visits, aggregated
Answers"Did my change help?" and "why is this slow?""Are users having a good time?"
ReproducibleYes — that is the pointNo, and that is also the point
Has INPNo real interactions; uses TBT insteadYes, the real thing
ToolsLighthouse, WebPageTest, DevToolsThe web-vitals library, CrUX, your analytics
Why they disagree
Lab runs on one device, one network, one location, with a cold cache and no extensions, and it does not scroll or click. Real users have warm caches, ad blockers, forty tabs open, a two-year-old phone and an interaction pattern nobody scripted. A perfect Lighthouse score alongside poor field data is common and is not a contradiction — it means your synthetic profile is not your audience.
Percentiles, never averages
An average is dominated by the fast majority and hides the tail. Report p75 because that is what the thresholds use, and watch p95 because that is where the people who leave are.
CrUX
Chrome's public dataset of field metrics for popular origins, and the source behind PageSpeed Insights' "real user" section and Search Console. Free, and it includes your competitors.
Collect your own
The web-vitals library is a few kilobytes and reports each metric with attribution — which element was the LCP, which interaction caused the worst INP, which node shifted. Send it to your analytics with the route, the device class and the connection type, or you will know something is slow without knowing where.
Field collection, with the attribution that makes it actionable JavaScript
import { onLCP, onINP, onCLS } from 'web-vitals/attribution';

function send(metric) {
  navigator.sendBeacon('/rum', JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,              // good | needs-improvement | poor
    route: currentRoute(),              // aggregate per route, not per site
    attribution: metric.attribution     // the element, the target, the sub-parts
  }));
}

3LCP, in four parts

The single most useful debugging model in front-end performance. Attribute first, then fix the biggest part.

LCP is not one thing. It decomposes into four consecutive intervals, and the fix for each is completely different — which is why "make LCP faster" is not actionable and "your resource load delay is 1.4 s" is.

LCP attribution Move the sliders to match your trace; the recommended fix follows the largest part.

Share of total—

    1 · Time to first byte
    Before you own anything. Fixes are server-side: cache at the CDN, parallelise data fetching, add a data cache, or move to a more static rendering strategy — Chapter 21.
    2 · Resource load delay
    The gap between the HTML arriving and the LCP resource starting to download. Almost always the largest and most fixable part. Causes: the image is not in the initial HTML so the preload scanner cannot see it (Chapter 3); it is behind a lazy-loading attribute it should not have; it is a CSS background image; it is discovered only after a JavaScript bundle runs; or it is queued behind lower-priority requests.
    3 · Resource load duration
    The download itself. Fixes are byte-level: a modern format, correct dimensions rather than a 3000px file displayed at 600, better compression, a CDN closer to the user.
    4 · Element render delay
    The resource has arrived but is not painted yet — blocked by a stylesheet still loading, by a font, by a long task occupying the main thread, or by the element existing only after hydration.

    4INP and the main thread

    Chapter 1's Constraint 2, given a number and a threshold.

    Every interaction decomposes into three parts: input delay (the browser could not start your handler because the main thread was busy), processing time (your handler running), and presentation delay (the time from your handler finishing to the next frame being painted). On real sites the first and third usually dominate, which surprises people who go straight to optimising their handler.

    Press the button a few times with background work off to get a baseline, then switch on long tasks and press it again.

    Reduce input delay
    Break up long tasks. Anything over 50 ms is a long task; anything over about 200 ms guarantees a visibly delayed interaction if the user happens to click during it. Chapter 15's yielding pattern, scheduler.yield(), and moving genuine computation to a worker.
    Reduce processing time
    Do the minimum needed to give feedback, then defer the rest. Update the visual state, yield, then run the expensive work. Debounce anything triggered by typing.
    Reduce presentation delay
    Usually a large re-render: a state change high in the tree re-rendering everything below (Chapter 18), or an enormous list. Virtualise long lists, move state down, and use content-visibility to skip off-screen work (Chapter 3).
    Third-party scripts
    Frequently the dominant cause and the least visible one, because they schedule their own long tasks. Load them with async or after interaction, put tag managers on a diet, and measure with the third-party filter in the Performance panel.

    5Layout shift

    Five causes, each with a mechanical fix. This is the most fixable of the three.

    CauseFix
    Images without dimensionswidth and height attributes, so the aspect ratio reserves space before the file arrives. Chapter 4.
    Web fonts swappingMetric overrides on the fallback, or font-display: optional. Chapter 11.
    Ads, embeds and iframesReserve the space with a fixed min-height sized to the most common case. Never let a slot collapse to zero and then expand.
    Content injected above existing contentBanners, cookie notices, "you have unsaved changes" bars. Reserve space, or overlay rather than insert.
    Animating layout propertiesUse transform, which does not shift anything. Chapter 3.

    Shifts within 500 ms of a user interaction are excluded from the score, on the grounds that the user caused them and expects movement. That is why an accordion opening is fine and a banner appearing on its own is not.

    Find them
    DevTools Rendering panel → Layout Shift Regions highlights the moving elements as they move. The Performance panel marks each shift on the timeline with the affected nodes. In the field, the web-vitals attribution build names the largest shift's element.
    The back/forward cache
    Restoring a page from bfcache is effectively instant. An unload listener disqualifies the page from it entirely — use pagehide instead — as do some cache-control headers and open connections. DevTools has a bfcache tester under Application; it is one of the largest wins available on a multi-page site and costs almost nothing.

    6Loading strategy, summarised

    Everything from Parts 1 and 6 in the order you should apply it.

    #ActionWhy it is in this position
    1Serve the LCP element in the initial HTMLNothing else matters if the preload scanner cannot see it. Usually free.
    2fetchpriority="high" on the hero, and never loading="lazy" on itTwo attributes; commonly worth several hundred milliseconds.
    3Inline critical CSS, load the rest asynchronouslyRemoves a render-blocking round trip. Chapter 1's simulator.
    4defer every script; audit third partiesStops the parser blocking and moves execution after paint.
    5Preconnect to the two or three origins you will definitely useRemoves DNS, TCP and TLS from the critical path for those.
    6Split by route and prefetch on hoverChapter 23. Cuts the initial bundle without making navigation feel slower.
    7Lazy-load below-the-fold images and iframesPure saving with no downside, once step 2 has protected the hero.
    8Ship less JavaScriptThe largest lever and the slowest to pull. Chapters 21 and 22.
    Third parties deserve a policy, not a case-by-case argument

    Analytics, tag managers, chat widgets, A/B testing, consent banners, session recorders. Each is added by someone who is not measuring the cost, and collectively they routinely exceed the first-party bundle. A workable policy: every third-party script has a named owner and a review date; nothing render-blocking; anything non-essential loads after interaction or on idle; and the total has a byte budget of its own. Partytown can move some of them to a worker, though it is not free of edge cases.

    7Keeping it fast

    Performance work decays. Only a mechanism prevents that, and the mechanism has to fail a build.

    Budgets in CI
    A byte limit per entry chunk and a metric limit from a Lighthouse run, both failing the build. The number matters less than the conversation it forces at the moment the bytes are added — six months later nobody can attribute the regression to a change.
    Watch the field, alert on the field
    Lab numbers in CI catch regressions before release; field p75 tells you whether users are actually having a good time. Alert on the second. A change that improves the lab and degrades the field has made things worse.
    Segment
    By route, device class, connection and country. A site-wide average hides that the product page is fine and checkout is terrible, which is precisely the one that costs money.
    Test on the hardware users have
    Chapter 1's advice, repeated because it is the single most attitude-changing item: a real cheap Android, or at minimum 4× CPU throttling and a network profile, as the default rather than the exception.
    Profile before optimising
    Every experienced developer has spent a day optimising something that was not the bottleneck. Record a trace, find the largest block, fix that. The Performance panel's summary and the "bottom-up" view answer "where did the time go" in about ninety seconds.

    8Check yourself

    Six questions.

    1. Lighthouse gives you 98 and your field data says LCP is poor. Who is wrong?

    Neither. Lighthouse is one scripted run on a specific simulated device and network, from one location, with a cold cache and no extensions. Your field data is thousands of real visits at the 75th percentile, on devices and connections you did not choose, in places you did not test. A gap between them means your lab profile does not represent your audience — often a faster device, a better network, or a location near your CDN's origin. Use the lab to compare before and after a change, and the field to decide whether there is a problem at all. If they disagree, the field wins, because it is what users experienced.

    2. LCP is 4.1 s. What do you look at before changing anything?

    The four-part breakdown, because the fixes are unrelated. TTFB is a server or caching problem. Load delay — usually the largest — means the browser did not start fetching the LCP resource early enough, so the fix is discoverability: put it in the initial HTML, remove loading="lazy", stop it being a CSS background, add fetchpriority="high". Load duration is a byte problem: format, dimensions, compression, CDN. Render delay means it arrived and could not paint: a blocking stylesheet, a font, a long task, or an element that only exists after hydration. Optimising the image when the problem is a 1.4 s discovery delay achieves almost nothing, which is what the demo in section 3 is for.

    3. Why did INP replace First Input Delay?

    FID measured only the first interaction, and only its queuing delay — not how long the handler ran, and not how long until anything appeared on screen. A page could score well on FID because the first click happened to land in a quiet moment, while every subsequent interaction was sluggish. INP looks at essentially all interactions during the visit, reports near the worst one, and measures the full path from input to the next painted frame including your handler and the rendering that follows. It is a much harder metric to pass and a far better description of whether the page feels responsive.

    4. Your handler runs in 12 ms and INP is still 480 ms. Where is the time?

    Either side of your handler. Input delay: the main thread was already busy with a long task when the click arrived, so the browser could not run your handler for hundreds of milliseconds — a bundle executing, a third-party script, a big render. Presentation delay: your handler finished quickly but the resulting re-render was enormous, so the next frame did not paint for a long time. The demo in section 4 separates the three parts precisely because the middle one is usually the smallest and the one people optimise first. Fix long tasks by chunking and yielding; fix presentation delay by rendering less.

    5. A cookie banner appears 800 ms after load and pushes the page down. How much CLS is that, and how do you fix it?

    Potentially a lot: the score is the impact fraction — how much of the viewport moved — multiplied by the distance fraction, and a banner inserted at the top moves the entire visible page by its own height. It is not excluded, because the exclusion window only covers shifts within 500 ms of a user interaction, and nobody interacted. Two fixes: overlay it with position: fixed so nothing reflows, which is usually also better design; or reserve the space in the initial HTML and reveal the banner into it. The general rule for this whole category is that content injected above existing content is the most expensive possible way to add something.

    6. Why does a single unload listener matter for performance?

    It disqualifies the page from the back/forward cache. With bfcache, pressing back restores the entire page from memory in a few milliseconds — no request, no parse, no execution, scroll position and form state intact — which is by far the fastest navigation available. An unload handler makes that impossible because the browser cannot guarantee the page can be frozen and resumed. Use pagehide instead, which fires in the same situations and is bfcache-compatible, and check the Application panel's bfcache tester for the other disqualifiers such as open connections and certain cache-control headers.
