CHAPTER 06

Reducers and state machines

A setter per field works until the fields start depending on each other. Then the transitions get scattered across six handlers, two of them disagree, and a state nobody designed appears in production. A reducer collects the transitions into one place; a state machine goes further and makes the bad ones impossible.

Part 2 State·Reading time 40 minutes·Demos boolean explosion, a running machine·Prerequisites Chapter 5

1When useState stops scaling

Three signals, all of which are about transitions rather than about the number of fields.

Several fields change together
Submitting a form sets saving, clears error, increments attempts and disables dirty. Four setters in one handler, and four more in the failure path, and the handler is now the only documentation of what a submit means.
The next value depends on the current one in a non-trivial way
Not count + 1, but "if we are in step 3 and the answer was no, go to step 5 and clear the notes". That logic wants a name and a home.
The same transition happens from more than one place
A cancel button, an escape key and a route change all mean "reset". Three copies of the reset logic is three chances to forget one field, which is Chapter 1's imperative problem returning in a new costume.

A reducer answers all three: transitions live in one pure function, each has a name, and any number of places can dispatch the same action.

2useReducer

Same storage as useState, different interface. There is nothing magic in it.

The whole API JSX
function reducer(state, action) {
  switch (action.type) {
    case 'submitted':
      return { ...state, status: 'saving', error: null, attempts: state.attempts + 1 };
    case 'succeeded':
      return { ...state, status: 'saved', dirty: false };
    case 'failed':
      return { ...state, status: 'error', error: action.message };
    case 'reset':
      return initial;
    default:
      throw new Error('Unknown action: ' + action.type);
  }
}

const [state, dispatch] = useReducer(reducer, initial);

// Lazy initialisation, same idea as useState's function form:
const [state, dispatch] = useReducer(reducer, userId, createInitialState);

dispatch({ type: 'failed', message: err.message });
dispatch is stable
Like a setter, it never changes identity, so it is safe to pass down and to leave out of dependency arrays. That alone removes a class of useCallback from Chapter 10.
The reducer must be pure
No fetching, no mutation, no Date.now(). React runs it during rendering and twice in StrictMode. Side effects belong in the handler that dispatches, or in an effect reacting to the resulting state.
It is not Redux
Same shape, entirely local. No store, no middleware, no devtools by default, no global anything. Chapter 23 covers when a real store is warranted.
Return a new object
Chapter 5's rule applies unchanged. Returning the same object means React bails out and nothing renders — which is occasionally what you want, and is worth doing deliberately for a no-op action.

3Writing a reducer worth having

The difference between a reducer that clarifies and one that is a switch statement full of setters.

Name actions for what happened, not for what to change

{ type: 'setStatusToSavingAndClearError' } is a setter with extra ceremony — the component still knows the mechanics, and every new consequence means a new action. { type: 'submitted' } describes an event in the world, and the reducer decides what that implies. When the requirements change, one function changes and every dispatcher is untouched.

HabitWhy
Past tense, event-shaped namessubmitted, retryRequested, fieldEdited. Reads as a log of what happened, which is what it is.
Payload under a key, not spread{ type, payload } or named fields — consistency matters more than which. Flux Standard Action is one convention; pick one and hold it.
Throw on unknown actionsA silent default: return state hides typos forever. Throwing turns a typo into an immediate, obvious failure.
Switch on state first when transitions are state-dependentswitch (state.status) then switch (action.type) inside. This is the shape that turns into section 6's machine.
Keep the reducer in its own fileIt is pure and has no React in it, so it can be imported by tests, by a worker, or by the server. Section 7.
Do not dispatch from inside the reducerIt is a pure function computing a value. Sequencing belongs to the caller or to an effect.
Immer, if the state is deep
useImmerReducer lets a case body read draft.rows[i].cells[j].value = next and still produce a correct immutable update. Genuinely useful for editor-like state; for most reducers it hides the spread patterns you should be able to read.
useState or useReducer?
One independent value: useState, always. Several values that change independently: several useState calls. Several values that change together, or transitions with real logic, or the same transition dispatched from several places: useReducer. It is not a scale of sophistication — a component with three unrelated toggles should not have a reducer.

The same feature, made honest TypeScript
// ✗ Four independent booleans: 16 combinations, 4 of them sensible.
{ isIdle: boolean; isLoading: boolean; isError: boolean; isSuccess: boolean }

// ✓ One field. Four states. The other twelve cannot be written down.
//   And notice the data hangs off the state it belongs to — you can no
//   longer read `error` while loading, because it does not exist there.
type Request<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: T };

// TypeScript then narrows on the tag, and the compiler enforces
// that every branch is handled — Chapter 17.
switch (req.status) {
  case 'success': return <Table rows={req.data} />;   // req.data exists
  case 'error':   return <Retry message={req.error} />; // req.error exists
  case 'loading': return <Spinner />;
  case 'idle':    return null;
}

This works without TypeScript too — a single status string is already unable to hold two values at once. Types make the compiler enforce exhaustiveness on top, which is a large additional win but not the primary one.

5State machines

A reducer where the transitions are declared as data, so the illegal ones cannot be reached even by a bug.

A discriminated union removes impossible states. A machine goes one step further and removes impossible transitions: from idle, the only event that does anything is SUBMIT. A stray SUCCESS arriving from a cancelled request is ignored rather than dragging the UI into a wrong state.

    The cheap version
    You do not need a library. A plain object mapping state to event to next state, read by a five-line reducer, gives you most of the benefit — that is exactly what the demo above runs.
    When XState earns its weight
    Hierarchical and parallel states, guards, delayed transitions, invoked services with automatic cancellation, and a visualiser that a designer or product manager can read. Worth it for multi-step flows with real branching: onboarding, checkout, media players, anything with a specification document. Overkill for a modal.
    The diagram is the point
    Even without a library, drawing the states and arrows before writing the code finds missing cases — what happens if the user hits back during payment, or the token expires while confirming. Those are the bugs that reach production, and they are cheap to find on paper.

    6Testing the logic

    The quiet advantage: a reducer is a pure function, so testing it needs no React at all.

    No render, no DOM, no mocking Vitest
    import { reducer, initial } from './checkout-reducer';

it('clears the previous error when a retry is submitted', () => {
  const failed = reducer(initial, { type: 'failed', message: 'Declined' });
  const next = reducer(failed, { type: 'submitted' });
  expect(next.error).toBeNull();
  expect(next.attempts).toBe(2);
});

it('ignores a success that arrives after cancellation', () => {
  const cancelled = reducer(saving, { type: 'cancelled' });
  expect(reducer(cancelled, { type: 'succeeded' })).toBe(cancelled);   // same object
});

// Milliseconds each, no flakiness, and the second test describes a race
// condition that would be genuinely awkward to reproduce through the UI.

    Chapter 22 covers testing components. The point here is that pulling state logic out of components makes a large slice of it testable at the cheapest layer, which is exactly the trade the testing trophy recommends.

    7Check yourself

    Five questions.

    1. When is a reducer the right choice over several useState calls?

    When the values change together or the transitions have logic. Three signals: several fields updated in the same handler, so a submit means four setters and the handler is the only record of what a submit implies; a next value that depends on the current one in a non-trivial way; and the same transition dispatched from more than one place, which otherwise means duplicated logic and a field somebody forgets. If the values are genuinely independent — three unrelated toggles — several useState calls are simpler and a reducer is ceremony. It is a question of coupling, not of how many fields there are.

    2. What is wrong with an action called setStatusAndClearError?

    It names the mechanism rather than the event, which means the component dispatching it still knows what a submit implies — so the reducer has gained nothing except a switch statement. When a submit later also needs to increment an attempt counter, every call site must change. Name it for what happened in the world: submitted. The reducer then owns the consequences, several unrelated places can dispatch the same action without knowing anything, and the action list reads as a description of the feature rather than a list of assignments. It also makes the log genuinely useful when debugging.

    3. Why is one status field better than four booleans?

    Four independent booleans describe sixteen combinations, of which about four are meaningful — so twelve states exist that nobody designed, nobody tested, and a handler that sets one flag while forgetting another will eventually reach. The failure is silent: nothing throws, the component just renders a spinner over an error, or nothing at all. A single field holding one of four literal values cannot hold two at once, so those twelve states are not merely discouraged, they are unwriteable. Attaching the data to the state it belongs to compounds the benefit — error only exists on the error variant — and with TypeScript the compiler then enforces that every branch is handled.

    4. A cancelled request's success response arrives late and puts the UI into a confusing state. How does a machine help?

    Because a machine defines transitions per state, not globally. In the cancelled state there is no entry for a SUCCESS event, so dispatching one returns the current state unchanged — the late response is ignored by construction rather than by a guard somebody remembered to write. With loose setters, the response handler simply calls setStatus('success') and there is no layer that could refuse. It is the same benefit as unrepresentable states, applied to time: not only can the state be wrong, the path to it cannot be taken. Cancellation of the request itself is still worth doing (Chapter 13); the machine is the defence for the case where it arrives anyway.

    5. What does moving state logic into a reducer buy you for testing?

    It becomes a pure function of two arguments, so tests need no React, no DOM, no rendering, no user-event simulation and no mocking — just expect(reducer(state, action)). They run in milliseconds and cannot be flaky. More importantly, cases that are awkward to reach through the interface become trivial: a success arriving after cancellation, a retry after three failures, a transition from a state the UI takes six clicks to reach. That moves a large slice of your logic coverage down to the cheapest, most reliable layer, leaving component tests to verify that the right things are rendered and dispatched.
