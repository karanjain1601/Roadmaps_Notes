CHAPTER 27

Security and authentication

Your code runs on a machine controlled by someone who may not be your user, and every byte you send is readable and modifiable. That is the starting position. What the browser gives you is a set of boundaries — origins, cookie rules, a content policy — and this chapter is about what each one does and where it stops.

1What the front end can and cannot protect

Getting this boundary wrong is the source of most real vulnerabilities.

The client canOnly the server can
Improve the experience with fast feedback; make attacks harder; avoid introducing vulnerabilities such as XSS; protect what is in the user's own browser Authenticate; authorise; validate; enforce rate limits; keep secrets; decide what data a user may see

Client-side validation is a usability feature. Hiding an admin button is a usability feature. Both are trivially bypassed with devtools, and neither is a control. The rule: every check that matters is repeated on the server, and the client's version exists so the user finds out sooner.

The attacker's positions
A malicious user with devtools open, editing requests. A malicious site the user also visits, trying to act on your site's behalf. A malicious script that got into your page — through a dependency, an advertisement, or your own template. A network observer, handled by TLS. Each section below addresses one of these.
Never in client code
API secrets, private keys, database credentials, admin endpoints "nobody knows about". Chapter 23's environment variables are inlined into the bundle as plain text.

2The same-origin policy

The foundation. Everything else is either an extension of it or a hole deliberately cut in it.

An origin is scheme + host + port. https://app.example.com and https://api.example.com are different origins; so are http:// and https:// versions of the same host, and :3000 versus :8080. The policy says a document from one origin cannot read data from another.

Blocked without permissionAlways allowed
Reading a cross-origin fetch response; reading another origin's DOM through an iframe; reading its cookies or storage; reading pixels from a cross-origin canvas image Sending a request; embedding an image, script, stylesheet, video or iframe; submitting a form; navigating

That asymmetry is the crucial detail and it is the entire basis of CSRF, section 5: a malicious page cannot read your bank's responses, but it can send a request to your bank with your cookies attached.

The other consequence is opaque responses. A no-cors fetch succeeds but hands you an unreadable response with status 0. This is why an image loaded into a canvas from another origin without crossorigin taints it, and why reading its pixels then throws.

3CORS, end to end

A server saying "this origin may read my response". Almost every CORS problem is one of four mistakes.

CORS decision engine Configure both sides; the verdict and the exact browser error are computed.

The request, from https://app.example.com

The response, from https://api.other.com

Simple versus preflighted
A request avoids the preflight only if it is GET, HEAD or POST, carries no headers beyond a short safe list, and its Content-Type is one of text/plain, application/x-www-form-urlencoded or multipart/form-data. application/json is not on that list, which is why almost every real API call is preflighted.
The wildcard and credentials are mutually exclusive
Access-Control-Allow-Origin: * with credentials: 'include' always fails. The server must echo the specific origin, and must therefore validate it against an allow-list rather than reflecting whatever arrives.
The request happened anyway
CORS blocks your JavaScript from reading the response. On a simple request the server already executed it. CORS is not authorisation and never has been.
You cannot fix it from the client
No fetch option, no header you set, no library. Either the server sends the headers, or you proxy through your own origin — which is what a dev-server proxy does and why the problem disappears locally and returns in production.
Response headers are hidden by default
Only a handful are readable cross-origin. Anything custom — a pagination count, a rate-limit header — needs Access-Control-Expose-Headers, or res.headers.get() silently returns null.

4Cross-site scripting

The vulnerability a front-end developer is most likely to introduce personally.

XSS is attacker-controlled content being interpreted as code in your origin. Once that happens the attacker has everything your page has: the DOM, the session, any token in JavaScript-readable storage, and the ability to make authenticated requests that look exactly like yours.

Sink analyser The same input through six different sinks. Parsed with DOMParser, never executed.

What textContent shows — the safe sink, rendered live

The three kinds
Stored: the payload is saved by the server and served to everyone — the most damaging. Reflected: it comes back in the response to a crafted URL. DOM-based: the server never sees it; your own JavaScript reads from the URL or storage and writes it into a dangerous sink. The third is entirely a front-end bug.
Frameworks escape output, and have escape hatches
React, Vue, Svelte and Angular all escape interpolated values by default, which removes most of the risk. The holes are named to be conspicuous — dangerouslySetInnerHTML, v-html, {@html}, bypassSecurityTrustHtml — and they are where the vulnerabilities are. Also remember that escaping is contextual: a value safe inside text is not safe inside href, inside a <script>, or inside a CSS url().
Sanitise when you must render HTML
User-authored rich text is a real requirement. Use DOMPurify, or the built-in Element.setHTML() where available, with an allow-list of elements and attributes. Never a regular expression, and never a deny-list.
javascript: URLs
Any user-supplied value used as an href or src must have its scheme validated against an allow-list of http, https and mailto. A link is an execution sink.
Trusted Types
A browser feature that makes assigning a plain string to innerHTML throw, so every write must pass through a policy you define. It converts an entire bug class into a build-time and runtime error. Enable it in report-only first.

5Content Security Policy

Defence in depth: assume a script gets in, and stop it running.

A policy that is actually strict HTTP header
Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  require-trusted-types-for 'script';
  report-uri /csp-report

// Every inline script carries the matching nonce, regenerated per response:
//   <script nonce="r4nd0m">…</script>
// 'strict-dynamic' lets a trusted script load further scripts, which is
// what makes a nonce policy workable with a bundler.
DirectiveWhy it is in the policy above
script-src with a nonceThe important one. Only scripts carrying this response's nonce run, so an injected <script> does nothing.
'strict-dynamic'Propagates trust to scripts loaded by trusted scripts, so you do not have to list every CDN — and an allow-list of hosts is weak anyway, since one host with an old library on it defeats the whole policy.
object-src 'none'Blocks plugin content, a legacy bypass route.
base-uri 'none'Stops an injected <base> tag redirecting every relative URL on the page.
frame-ancestorsClickjacking, section 7. Supersedes X-Frame-Options.
require-trusted-types-forTurns unsafe DOM sinks into runtime errors.

'unsafe-inline' and 'unsafe-eval' defeat most of the point. If a policy needs them, it is documentation rather than a control.

Roll out with Report-Only

Ship Content-Security-Policy-Report-Only first with a reporting endpoint. Collect violations for a couple of weeks, fix the legitimate ones — usually inline event handlers, an analytics snippet and a stray eval in a dependency — then switch to enforcing. Turning on a strict policy without this reliably breaks something in production on a Friday.

6Cross-site request forgery

Section 2's asymmetry, weaponised: another site makes your browser send an authenticated request.

The user is logged in to your bank. They visit a malicious page containing a form that posts to the bank's transfer endpoint and submits itself. The browser attaches the bank's cookies because that is what cookies do. The attacker cannot read the response — that would be blocked — but the transfer already happened.

DefenceHow it works and what it misses
SameSite cookies Lax — now the default — sends the cookie on top-level GET navigations but not on cross-site POSTs, which stops the classic attack. Strict is stronger and means a user following a link from an email arrives logged out. None requires Secure and reopens the exposure, so use it only where a genuine cross-site flow needs it.
Anti-CSRF tokens A random value tied to the session, sent in a form field or header and validated server-side. The attacker's page cannot read it because of the same-origin policy. Still the standard for cookie-based sessions and the right belt-and-braces alongside SameSite.
Custom request headers Requiring a header such as X-Requested-With forces a preflight for cross-origin requests, which a simple form post cannot perform. Reasonable as an additional layer, not as the only one.
Not using cookies A token in an Authorization header is not attached automatically, so CSRF does not apply. It trades the problem for the storage question in section 8.

7Clickjacking

Your page, invisible, on top of theirs.

An attacker embeds your site in a transparent iframe positioned over their own decoy button. The user thinks they are clicking "Play video" and actually clicks "Confirm payment" in your interface. The fix is one header.

8Authentication in the browser

The storage question, which is argued about more than any other topic here and has a fairly clear answer.

Where the credential livesExposed to XSSExposed to CSRFVerdict
httpOnly cookie No — JavaScript cannot read it Yes, without SameSite and a token The default choice. The CSRF exposure has a well-understood, complete fix; the XSS exposure of the alternatives does not.
localStorage Yes — any script reads it No Convenient and the weakest option. Any XSS anywhere on the origin, including in a dependency, exfiltrates the token.
In-memory variable Only while the page lives No Better than storage; lost on refresh, so it needs a refresh token in an httpOnly cookie — which is the hybrid most token-based apps end up at.
sessionStorage Yes No Same as localStorage with a shorter life. Not meaningfully safer.

The framing "cookies are vulnerable to CSRF, so use localStorage" trades a solved problem for an unsolved one. Cookies with httpOnly, Secure, SameSite=Lax and a CSRF token are the well-trodden path.

Sessions or JWTs
A server session is a random id in a cookie pointing at server-side state: revocable instantly, small, and requires a lookup. A JWT is self-contained and verifiable without a lookup, which is why it suits distributed services — and it cannot be revoked before it expires, which is why short lifetimes plus a refresh token are mandatory. Choosing a JWT for a single monolithic application usually adds complexity and removes the ability to log someone out.
OAuth and OIDC in a browser
Authorization Code flow with PKCE, always. The implicit flow is deprecated because it returned tokens in the URL fragment, where they end up in history and logs. PKCE means a public client can complete the exchange without a client secret, which it could never keep anyway. Use a maintained library — oidc-client-ts, your provider's SDK — rather than implementing the flow; the details that matter are the ones that are easy to get subtly wrong.
Refresh properly
Short access tokens, a refresh token in an httpOnly cookie, refresh-token rotation with reuse detection. Deduplicate concurrent refresh attempts or five parallel 401s trigger five refreshes and four of them invalidate the others — Chapter 16's deduplication pattern applies directly.
Log out on the server
Clearing client state is cosmetic. The session or refresh token must be invalidated server-side, or the credential still works from anywhere it was copied.
Passkeys
WebAuthn credentials bound to the origin, unphishable by construction, and now well supported. Worth offering as a primary method rather than only as a second factor.

9The other headers, and hygiene

Cheap, mostly one line each.

HeaderEffect
Strict-Transport-SecurityForces HTTPS for the next n seconds, removing the plaintext first request an attacker could intercept. Add includeSubDomains; consider preload once you are certain.
X-Content-Type-Options: nosniffStops the browser second-guessing your Content-Type, which is how an uploaded "image" becomes a script.
Referrer-Policystrict-origin-when-cross-origin is a good default: full URLs stay internal, only the origin leaks outward. Stops query strings with ids and tokens appearing in third-party logs.
Permissions-PolicyDisables capabilities you do not use — camera, microphone, geolocation — including for embedded frames.

Dependencies are your attack surface
Chapter 22's supply-chain section is a security section. A compromised package runs with the full privileges of your page and can read every token in it.
Do not log secrets
Error trackers capture request bodies, headers, local storage and console output. Configure redaction before you have an incident, not after.
Check the headers you actually ship
Security Headers and Mozilla Observatory grade a live URL in seconds, and a header that was configured but not deployed is common enough to be worth verifying.

10Check yourself

Six questions.

1. Why does adding Content-Type: application/json to a cross-origin POST suddenly cause a CORS failure?

Because it turns a simple request into a preflighted one. The simple-request rules allow only text/plain, application/x-www-form-urlencoded and multipart/form-data — the three a plain HTML form can produce. Anything else triggers an OPTIONS preflight, and that preflight must be answered with Access-Control-Allow-Origin, Allow-Methods and Allow-Headers. A server configured only to add CORS headers to its GET responses will fail the preflight, so the real request is never sent. This is why "it worked until I sent JSON" is such a common report.

2. Does CORS protect your API?

No. CORS controls whether a browser lets page JavaScript read a cross-origin response. It does nothing against curl, a script, a mobile app or a server-side request, none of which enforce it. For a simple request the server has already executed the operation before the browser discards the response — the write happened. CORS is a relaxation of the same-origin policy for browser clients, not an authorisation mechanism. Authorisation is a server-side check on every request, every time.

3. Your framework escapes output, so why is XSS still possible?

Three ways. The deliberate escape hatches — dangerouslySetInnerHTML, v-html, {@html} — which exist for rendering rich text and are where the bugs are. Contexts the framework does not escape for: a user-controlled value in an href can be a javascript: URL, and a value interpolated into a <script> block or a CSS url() needs different escaping entirely. And DOM-based XSS in your own non-framework code — reading location.hash and assigning it to innerHTML, or passing it to a chart library that does the same. Escaping is contextual, and the framework only handles one context.

4. Where should an access token live, and why is localStorage the popular wrong answer?

In an httpOnly, Secure, SameSite=Lax cookie, or in a JavaScript variable in memory backed by a refresh token in such a cookie. localStorage is popular because it is easy and because "cookies are vulnerable to CSRF" — but that trades a problem with a complete, well-understood fix (SameSite plus an anti-CSRF token) for one with no fix at all. Any XSS anywhere on the origin, including inside a dependency you did not audit, reads localStorage and exfiltrates the token in one line. httpOnly means the same injected script cannot read the credential at all.

5. What does a nonce-based CSP protect against that output escaping does not?

It is defence in depth for the case where escaping failed. Escaping is a preventive control with many places to slip — one innerHTML, one unescaped context, one vulnerable dependency. A strict CSP assumes injection succeeded and stops the injected script from executing, because it lacks the per-response nonce. It also mitigates whole adjacent categories: base-uri 'none' blocks an injected <base> hijacking every relative URL, object-src 'none' closes plugin bypasses, and the connect and form directives limit where a compromised page can send data. Host allow-lists are much weaker than nonces, since one permitted CDN hosting an old vulnerable library defeats the policy.

6. A colleague says the admin panel is safe because the button only renders for admins. What is the response?

That is not a security control, it is a user-interface decision. The entire bundle is on the user's machine: the admin routes, the API paths, the request shapes and the role check itself are all readable, and any of them can be called directly with fetch or curl. Hiding the button changes nothing about what the server will accept. The server must check authorisation on every request, for every resource, regardless of what the client displayed — and ideally the admin code should not be in the public bundle at all, both to reduce the information given away and to save the bytes.
