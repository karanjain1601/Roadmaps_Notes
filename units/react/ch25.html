CHAPTER 25

Testing the front end

Tests exist to let you change code without fear. That framing decides everything else: which tests to write, how to write them so they survive a refactor, and why a suite that fails at random is worse than no suite at all.

Part 6 The toolchain·Reading time 45 minutes·Demos query priority, suite economics·Prerequisites Chapters 5–6, 14, 19

1What tests are for

Confidence that a change did not break something, at a cost proportional to the confidence.

A test is not a proof of correctness and it is not documentation, although it can accidentally be both. It is a mechanism that lets someone who has never seen this code change it and find out quickly whether they broke anything. Every decision in this chapter follows from asking whether a given test increases that confidence or merely increases the count.

The guiding principle

The more your tests resemble the way your software is used, the more confidence they can give you. Kent C. Dodds' formulation, and the most useful sentence in front-end testing. A test that clicks a button labelled "Save" and checks that "Saved" appears will survive any refactor that preserves behaviour. A test that asserts a component's internal state variable equals 3 breaks when you rename it, and passes when the button is broken.

The pyramid was written for back-end systems. The front end has a different cost curve.

3Unit tests

Cheap, precise, and easy to write far too many of.

What deserves one Vitest
import { describe, it, expect } from 'vitest';
import { parseFilters } from './filters';

describe('parseFilters', () => {
  it('defaults page to 1 when absent', () => {
    expect(parseFilters(new URLSearchParams())).toEqual({ page: 1, sort: 'relevance' });
  });

  it('clamps a negative page to 1', () => {
    expect(parseFilters(new URLSearchParams('page=-4')).page).toBe(1);
  });

  it('ignores an unknown sort value', () => {
    expect(parseFilters(new URLSearchParams('sort=;drop')).sort).toBe('relevance');
  });
});

// Worth a unit test: branching logic, edge cases, anything you had to
// think about. Not worth one: a function that reads one property, or a
// component's render output — that is section 4's job.
Vitest or Jest
Vitest for anything new: it reuses your Vite config so transforms match your build, and it is fast. Jest remains everywhere and is fine. The APIs are close enough that migrating is mostly mechanical.
Name the behaviour, not the function
it('clamps a negative page to 1') tells you what broke from the failure output alone. it('works') means opening the file.
Arrange, act, assert
Three visually separated parts. A test with assertions interleaved through fifteen lines of setup is hard to read when it fails at 2am.
One reason to fail
Several expect calls are fine if they check one behaviour. A test asserting six unrelated things tells you almost nothing when it goes red.

4Component tests, and how you query

The most valuable layer, and the single decision that determines whether the tests survive: how you find elements.

Query priority, run against a real form These are actual DOM queries. Refactor the markup and see which survive.

#QueryWhen
1getByRole(role, { name })The default. It is how assistive technology finds things, so a passing test is also weak evidence of accessibility. If you cannot query by role, the element probably has no accessible name — a real bug, found by the test.
2getByLabelTextForm fields, where the label is the user-visible handle.
3getByPlaceholderTextOnly when there is genuinely no label — which Chapter 5 says is already wrong.
4getByTextNon-interactive content: a heading, a message, a total.
5getByDisplayValueFinding a filled-in field by its current value.
6getByTestIdThe escape hatch. Legitimate for things with no accessible handle — a chart container, a specific row in a virtualised list. Reaching for it first means your tests no longer resemble use.
A component test that survives refactoring Testing Library
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('shows an error when the email is missing', async () => {
  const user = userEvent.setup();
  render(<SignupForm />);

  await user.click(screen.getByRole('button', { name: /create account/i }));

  // findBy* = getBy* + waitFor. Use it for anything that appears async.
  expect(await screen.findByText(/enter your email/i)).toBeVisible();
  expect(screen.getByRole('textbox', { name: /email/i })).toBeInvalid();
});

// getBy*   → throws if not found. The default assertion.
// queryBy* → returns null. ONLY for asserting absence.
// findBy*  → returns a promise. For anything that appears later.
userEvent, not fireEvent
fireEvent.click dispatches one event. A real click produces pointerdown, mousedown, focus, pointerup, mouseup and click, and typing produces keydown, keypress, input and keyup per character. userEvent simulates the full sequence, which is why it catches bugs in focus handling and in code that listens for keydown rather than click.
Do not test implementation
No assertions on state variables, no calling instance methods, no checking that a child component "was rendered with these props". Those all break on refactor and none of them tell you the feature works.
Mock as little as possible
Every mock is a place where the test and reality can diverge. Mock the network — section 5 — and things genuinely outside your control such as time, randomness and geolocation. Do not mock your own modules to make a test easier to write; that usually means the design is awkward, and the mock hides it.
Where component tests run
jsdom is fast and approximate: no layout, no real paint, so anything about size, visibility or scrolling is unreliable. Browser-mode runners — Vitest browser mode, Cypress or Playwright component testing — run the same tests in a real engine, slower and honest. A common split is jsdom for logic-heavy components and a real browser for anything visual.

5Mocking the network

Intercept at the network layer, not at your code.

MSW: one set of handlers for tests, dev and the browser JavaScript
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/products', () => HttpResponse.json([{ id: '1', name: 'Seed tray' }]))
);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());   // no leakage between tests
afterAll(() => server.close());

// Override for one test — the error path, which is the one that is
// never exercised manually and always broken.
it('shows a retry prompt when the server fails', async () => {
  server.use(http.get('/api/products', () => new HttpResponse(null, { status: 500 })));
  render(<ProductList />);
  expect(await screen.findByRole('button', { name: /try again/i })).toBeVisible();
});
Why the network layer
Mocking fetch or your API client couples the test to how the request is made. Intercepting at the network means your real client code runs — including headers, serialisation, status handling and the retry logic from Chapter 16 — and the test only replaces what is on the other end. Change from fetch to a library and the tests keep passing, correctly.
The same handlers everywhere
MSW runs in Node for tests and in a service worker in the browser, so one set of handlers serves unit tests, component tests, Storybook and local development against a back end that does not exist yet.
Fail on unhandled requests
onUnhandledRequest: 'error'. Otherwise a real request escapes into a test run and either hangs or hits a real server.
Test the unhappy paths
Error responses, empty lists, slow responses, and the shapes from Chapter 17's boundary demo. These are the states nobody clicks through by hand and where most user-visible bugs live.

6End-to-end tests

The only tests that prove the whole thing works, and the ones most likely to ruin your week.

Cover journeys, not features
Sign up, search and buy, the main create-and-save flow, and anything where failure costs money. Five to twenty well-chosen tests. Every additional one adds runtime and a flake probability that compounds — the demo below makes that arithmetic uncomfortably concrete.
Playwright or Cypress
Playwright: multiple real engines, parallel by default, excellent tracing, and it auto-waits on every action. Cypress: a superb interactive debugging experience and a large ecosystem, historically Chromium-centric. Either is a good choice; Playwright has the momentum.
Never sleep
await page.waitForTimeout(2000) is the single largest cause of flaky suites: too short on a loaded CI runner, wasted time everywhere else. Wait for a condition — an element visible, a request completed, a URL changed. Modern runners retry assertions automatically until a timeout, so await expect(locator).toBeVisible() is both correct and self-waiting.
Do not sign in through the UI every time
Authenticate once in a setup project, save the storage state, and reuse it. It removes twenty seconds and one flake source from every test.
Control the data
Each test creates what it needs and cleans up, or runs against a seeded database reset between runs. Tests that depend on data another test created will fail the moment they run in a different order or in parallel.
Where flakiness comes from
Fixed waits; shared state between tests; animations that move a target mid-click; real network calls; time and time zones; test order dependence; and parallel tests fighting over the same record. Each has a specific fix, and none of them is "retry three times" — retries hide the failure and let it grow.

7Visual and accessibility testing

Two things assertions cannot easily express.

Snapshot tests
Serialise output and compare against a stored copy. They catch unintended changes, and they degrade badly: a large snapshot changes on every refactor, nobody reads the diff, and -u becomes reflexive. Keep them small and targeted — a serialised error object, a generated query string — and never snapshot a whole component tree.
Visual regression
Screenshot a component or page and compare pixels. Genuinely useful for a design system, where a CSS change can break a component nobody thought to test. Needs a consistent rendering environment — a container, pinned fonts, disabled animations — or it produces noise. Hosted services handle that; self-hosting is possible and fiddly.
Automated accessibility checks
axe-core runs inside a component or end-to-end test and fails the build on violations. It catches roughly the third that is machine-decidable (Chapter 6) — missing names, contrast, invalid ARIA — which is real value for near-zero effort. It cannot tell you the focus order is confusing, so it supplements the manual pass rather than replacing it.
Storybook as a test surface
Stories are already the states you care about, so they can be reused as the input to interaction tests, accessibility checks and visual regression rather than maintained separately.

8Practices that keep a suite alive

Six habits, in the order they pay off.

Coverage is a signal, never a target
Low coverage in an area is worth investigating. A mandated 80% produces tests written to touch lines rather than to verify behaviour, and a false sense of safety — 100% line coverage with no meaningful assertions is entirely achievable. Look at what is uncovered and ask whether it matters.
Determinism above all
Freeze the clock with fake timers, seed randomness, fix the time zone and locale in the runner config, and never depend on test order. A test that passes 99 times in 100 is a test that will waste an hour of someone's day this month.
Factories, not fixtures
makeUser({ role: 'admin' }) with sensible defaults beats a shared JSON blob every test partly depends on. The test then states only what it cares about, which is also what makes it readable.
Quarantine flakes immediately
Skip it, open a ticket, fix or delete within the sprint. Chapter 24's point: once red sometimes means nothing, people stop reading failures and the whole suite's value collapses.
Split the CI stages
Static checks and unit tests on every push for fast feedback; component tests next; end-to-end on the pull request or before deploy. Waiting eleven minutes to learn about a lint error is a broken loop.
Write the test when you fix the bug
The highest-value test you will ever write is the one reproducing a bug that actually happened, written at the moment you understand it. It is also the easiest to justify, because you have proof the scenario occurs.

9Check yourself

Six questions, closing Part 6.

1. Why prefer getByRole('button', { name: /save/i }) over getByTestId('save-btn')?

Because it queries the way a user — and assistive technology — finds the control, so it verifies two things at once: that a button exists, and that it has an accessible name. A test id verifies only that you added a test id. The role query also survives markup refactors that preserve behaviour and correctly fails when behaviour changes, such as the button becoming a div or losing its label. The strongest argument is the failure mode: if you cannot write the role query, the element has no accessible name, which is a real accessibility bug the test just found for you.

2. What is wrong with mocking your API client module in a component test?

It stops your real client code from running, so everything it does — URL construction, headers, serialisation, status handling, the retry and error mapping from Chapter 16 — is untested and can be wrong while the test passes. It also couples the test to the module's shape, so changing the client breaks tests that were about a component. Intercepting at the network layer with MSW replaces only the server, leaving all your own code in the path. As a bonus the same handlers serve local development and Storybook.

3. Your end-to-end suite fails about once in every five runs, always on a different test. What do you do?

Treat it as the highest-priority defect in the suite, because a suite that is red at random trains everyone to re-run rather than read, and at that point it protects nothing. Diagnose rather than retry: the usual causes are fixed waitForTimeout sleeps, shared state or data between tests, animations moving a target between the locator resolving and the click, real network calls, time zone or clock dependence, and parallel tests contending for the same record. Each has a specific fix. In the meantime quarantine the flaky tests so the signal from the rest stays trustworthy — and note from the demo that with enough tests even a very low per-test flake rate makes a green run unlikely.

4. Is 90% coverage a good goal?

As an observation it can be healthy; as a mandate it is counterproductive. Coverage measures which lines executed, not whether anything was verified — a test that renders a component and asserts nothing covers it completely. Making the number a gate produces tests written to touch lines, which are expensive to maintain and catch nothing, plus pressure to test trivial code because it is easy to cover. The useful practice is to look at what is not covered and ask whether it matters: an uncovered error branch in payment handling is a finding, an uncovered getter is not.

5. Why does userEvent.click() catch bugs that fireEvent.click() misses?

Because a real click is not one event. The browser fires pointerdown, mousedown, focus, pointerup, mouseup and then click, and typing fires keydown, keypress, input and keyup for each character. fireEvent dispatches exactly the one event you name, so code listening for mousedown, relying on focus having moved, or handling keydown for a keyboard shortcut appears to work in tests and fails in a browser. userEvent simulates the full sequence, including checking that the element is actually visible and enabled first — which itself catches a category of bug.

6. A component's test suite breaks every time the component is refactored, though behaviour is unchanged. What is the underlying problem?

The tests are coupled to implementation rather than behaviour — asserting on internal state, on child components being rendered with particular props, on CSS class names, or on DOM structure via container queries. Those are all things a refactor is allowed to change, so the tests are measuring the wrong thing and actively discouraging improvement. Rewrite them around what a user can observe: render, interact through roles and labels, assert on visible output. The test then fails only when the feature genuinely breaks, which is the entire point of having it.

Carry forward
