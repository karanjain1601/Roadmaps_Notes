2A debugging routine

Most time lost to a bug is lost before anyone forms a hypothesis worth testing.

1 · Reproduce it reliably
You cannot fix what you cannot trigger. Find the exact steps, browser, viewport, data and account state. If it only happens sometimes, the intermittency is the clue — it usually means timing, ordering, cache state or a race.
2 · Read the error properly
All of it, including the stack, including the "caused by". undefined is not a function names the thing; the frame above it names where. If the trace is minified, that is a source-map problem to fix now, permanently (Chapter 29).
3 · Bisect the space, not the code
Halve it each time. Does it happen with an empty cache? In a private window? With extensions disabled? On the previous deploy? With one item instead of a thousand? Each answer eliminates half the possibilities, and four questions get you from "somewhere in the app" to one module. git bisect does the same over history (Chapter 24).
4 · Verify assumptions before theories
Is that request actually being sent — check the Network panel, not the code. Is that element actually in the DOM. Is the state actually what you think — log the value, do not reason about it. Most stuck debugging sessions rest on one confidently held false belief.
5 · Change one thing
Change three, watch it work, and you have learned nothing and left two changes you do not understand.
6 · Write the test, then fix
A failing test that reproduces the bug proves you understand it and stops it returning. Chapter 25 — this is the highest-value test you will ever write.
7 · Ask, with a good question
After roughly forty minutes stuck, describe it to someone: what you expected, what happened, what you have ruled out. The description alone solves it surprisingly often, and if it does not, you have written the ticket.

6Where this goes next

Thirty chapters in, the useful question is what the gaps are.

What this unit covered
The platform and how a page actually loads; markup, semantics, forms and accessibility; CSS from the cascade to design tokens; JavaScript from the type system to the event loop and the network; frameworks by mechanism rather than brand, plus state, routing, web components and rendering strategies; the toolchain from packages through bundlers to tests; and shipping — performance, security, the browser as a platform, and deployment with observability.
What it deliberately did not
Any single framework in depth — Part 5 explains the mechanisms so that framework documentation makes sense, which is a better use of thirty chapters than a tutorial that expires. Also: design and visual craft, back-end work beyond the boundary, data modelling, and the parts of a career that are not technical.
The adjacent units
React, Vue, Angular or Next.js for a specific framework, now that Chapter 18 has explained what each is doing. TypeScript to go beyond Chapter 17. CSS for depth on Part 3. Node.js or Back-end Developer to see the other side of Chapter 16's boundary. System Design for the architecture behind Chapter 21. DevOps for Chapter 29 at scale.
The honest summary of the craft
Most of it is not knowing more APIs. It is caring what happens on a cheap phone on a bad connection; making things work for people who navigate differently from you; keeping code changeable by someone who is not you; and measuring rather than assuming. Those habits outlast every tool named in this unit.
