CHAPTER 08

Refs and escaping React

A ref is a box React will hold for you and otherwise ignore. That makes it the deliberate exit from the declarative model — for values that must survive a render without causing one, and for the handful of things the DOM only lets you do imperatively.

Part 2 State·Reading time 35 minutes·Demos ref versus state, stale closures·Prerequisites Chapters 4–5

1Two jobs, one hook

They look unrelated and are the same mechanism.

The whole API JSX
// Job 1: a mutable box that survives renders and never triggers one.
const timerRef = useRef(null);
timerRef.current = setTimeout(...);          // no render, no batching, no queue

// Job 2: a handle to a DOM node. React fills it in during commit.
const inputRef = useRef(null);
<input ref={inputRef} />
inputRef.current.focus();

// It is the same thing: useRef returns { current } and keeps the
// object identical across renders. Passing it as `ref` just tells
// React to assign the node into that same box.
The object is stable, the contents are yours
React creates { current: initial } once and hands you the same object on every render. Writing to .current is an ordinary assignment: instant, synchronous, and completely invisible to React.
Refs are not reactive
Changing .current does not schedule a render, does not batch, does not appear in a queue. Which is exactly the point, and exactly the trap.
The initial value is only used once
Same as useState. And note that useRef(expensive()) calls the expensive thing on every render even though the result is discarded — there is no lazy form, so guard it: if (ref.current === null) ref.current = expensive().

One question decides it: does the screen need to change?

The rule: if it appears in the returned JSX, it is state. A ref read during render makes the component impure — React may render at a moment you did not expect and produce output that does not match a later render with the same props, which is Chapter 3's whole argument.

3DOM refs

The legitimate uses are a short list. Everything else is a declarative problem in disguise.

LegitimateNot — do it with state
Focus, selection, text-cursor position; scrolling a node into view; measuring size or position; playing, pausing or seeking media; triggering a native dialog; integrating a non-React widget such as a map or a chart Changing text, classes, styles, visibility, attributes or children. If you are writing ref.current.style or ref.current.textContent, React is about to overwrite it and the two will disagree.
Timing, and the null you must handle JSX
const ref = useRef(null);

// During render: null. React has not committed yet (Chapter 4).
console.log(ref.current);            // null on the first render

useEffect(() => {
  ref.current.focus();               // populated — effects run after commit
}, []);

// It is set back to null when the node is removed, so any code that
// runs later must check. This is not defensive programming, it is the
// actual lifecycle.
function scrollToEnd() { ref.current?.scrollIntoView({ block: 'end' }); }
Ref callbacks, for when a ref object will not do
Passing a function as ref gets you called with the node on attach and with null on detach — so you can measure immediately, or keep a Map of nodes for a dynamic list. In React 19 the callback may return a cleanup function instead, which is tidier.
Measuring
A ref callback fires before effects, so it is the earliest point you can measure. For anything that must not flicker, read in useLayoutEffect — Chapter 4's commit order. And prefer ResizeObserver to measuring on every render.
Lists of refs
Do not call useRef in a loop — hooks are positional. Keep one ref holding a Map, and populate it from a ref callback keyed by id.

4Passing refs through components

Simplified considerably in React 19.

Then and now JSX
// React 19: ref is an ordinary prop. Nothing special required.
function TextField({ label, ref, ...rest }) {
  return <label>{label}<input ref={ref} {...rest} /></label>;
}

// Before 19: ref was not a prop, so it needed a wrapper.
// You will still meet this constantly in existing code.
const TextField = forwardRef(function TextField({ label, ...rest }, ref) {
  return <label>{label}<input ref={ref} {...rest} /></label>;
});

// Expose a narrow API instead of the raw node when the node is an
// implementation detail you may want to change.
useImperativeHandle(ref, () => ({
  focus: () => innerRef.current.focus(),
  clear: () => { innerRef.current.value = ''; }
}), []);
Forward the ref on anything input-like
A field, a button, a menu item. Without it, a parent cannot focus it, a form library cannot register it, and a tooltip cannot position against it. It is the same courtesy as forwarding rest props (Chapter 3).
useImperativeHandle sparingly
It is a deliberate imperative API on a declarative component, so every method is a piece of state living outside React. Legitimate for focus, scrollTo, play — genuinely imperative verbs. A red flag when it starts exposing setValue or open, which are props.
Refs are not props to memo
Passing a ref does not defeat memo, because the object identity is stable across renders by construction.

5The latest-ref pattern

The standard fix for a callback that must be stable and must not go stale.

Chapter 5 established that every function created during a render captures that render's values, permanently. Usually that is what you want. It is not what you want when the function is handed to something long-lived — an interval, a subscription, an event listener registered once.

      The pattern, written out JSX
      function useEvent(handler) {
  const ref = useRef(handler);
  useLayoutEffect(() => { ref.current = handler; });   // keep it current
  return useCallback((...args) => ref.current(...args), []);  // stable forever
}

// The returned function never changes identity, so it will not
// re-trigger effects or defeat memo — and it always calls the newest
// version, so it never sees stale props or state.
//
// Use it for: callbacks passed to long-lived subscriptions, handlers
// you do not want in a dependency array, and anything you were about
// to add an eslint-disable comment for.
//
// Do NOT use it during render, and do not reach for it before trying
// the updater form from Chapter 5 — setCount(c => c + 1) removes the
// captured value entirely and needs no ref at all.

      6Where React's ownership ends

      The rule for coexisting with anything that manipulates the DOM itself.

      Do not remove or add children React manages
      React's element tree still says those nodes exist. The next render will diff against a DOM that no longer matches, and the result ranges from a stale screen to a thrown exception. Modifying a node React does not render children into is fine.
      Give third-party widgets their own node
      Render an empty <div ref={host} /> with no children and let the library own everything inside it. React never diffs inside an empty element, so there is no conflict.
      Initialise in an effect, tear down in the cleanup
      Create the chart, map or editor instance in useEffect, keep it in a ref, and destroy it in the returned cleanup. StrictMode's double mount will catch you immediately if you skip the teardown — Chapter 4.
      Sync props into the instance, do not recreate it
      A second effect that watches the props and calls the library's own update methods. Recreating the whole instance on every prop change is slow and loses its internal state.
      Portals are not an escape from the tree
      createPortal renders into a different DOM node while staying in the React tree: context still flows, events still bubble through the React hierarchy rather than the DOM one. That is usually what you want for modals, and occasionally surprising.

      7Check yourself

      Five questions.

      1. What is the single question that decides between a ref and state?

      Does the screen need to change when this value changes? If yes, it is state — a ref update schedules nothing, so the value will be correct while the display is stale, which the demo in section 2 shows directly. If no, a ref is better: it avoids a render, updates synchronously, and keeps the value out of the reactive system where it does not belong. Timer ids, DOM nodes, previous values, third-party library instances and "has this already run" flags are all refs. The corollary is the practical test: if it appears in the returned JSX, it is state.

      2. Why is reading ref.current during render a problem?

      Because it makes the component impure. Purity means the same props and state produce the same output, and a ref is deliberately outside that system — it can be written at any moment by an effect, a handler or a timer, so two renders with identical props can produce different results. React relies on purity to batch, to render speculatively and to abandon work, so the failures are the intermittent kind: fine in development, wrong under a transition, different in StrictMode. Write to a ref in effects and handlers; read it in effects and handlers. During render, use state.

      3. Your useEffect logs ref.current as null. When is it populated?

      During commit, which happens after render and before effects — so an effect body should see the node. Null usually means one of three things: it is the first render and you are reading during render rather than in the effect; the element carrying the ref is conditionally rendered and currently absent; or the ref was passed to a component that does not forward it, so it was never attached to anything. React also sets it back to null when the node unmounts, which is why any code running later needs optional chaining. If you need the node earlier than an effect — to measure without a visible flicker — use a ref callback or useLayoutEffect.

      4. An interval set up once always logs the initial count. Explain, and give two fixes.

      The callback was created during the first render and captured that render's count constant. Later renders create new closures, but the interval is still holding the first one — this is not a bug, it is Chapter 5's snapshot model applied to a long-lived function. Two fixes. If you only need to update state, use the updater form: setCount(c => c + 1) has no captured value at all. If you need to read the current value, keep it in a ref that an effect updates on every render and read ref.current inside the callback — the latest-ref pattern, which the demo runs side by side. The third option, listing count as a dependency, works but tears down and recreates the interval on every change.

      5. How should a charting library that owns its own DOM be integrated?

      Give it a node React does not render children into: an empty <div ref={host} />. React never diffs inside an empty element, so the library can do whatever it likes in there without the two fighting. Create the instance in a useEffect with an empty dependency array, store it in a ref, and destroy it in the cleanup — StrictMode's double mount will expose a missing teardown immediately. Then sync props with a second effect that calls the library's own update methods rather than recreating the instance, which would be slow and would discard its internal state such as zoom or selection. Resize is usually a ResizeObserver in the same effect.
