CHAPTER 04

The render cycle

"Re-render" is the most overloaded word in React and the source of most confusion about it. It does not mean the DOM changed. This chapter separates the three things that actually happen, in order, and shows the diff engine that decides what survives.

Part 1 The model·Reading time 45 minutes·Demos a working reconciler, render triggers·Prerequisites Chapters 1–3

1Three steps, always in this order

Keeping them separate in your head resolves most React confusion on its own.

1 · Trigger
Something says "this component needs to render again". Either the initial mount, or a state update. That is the complete list of root causes — section 2.
2 · Render
React calls your component functions, top down, collecting the element objects they return. Nothing touches the DOM here. This step is pure, discardable, and may be interrupted. "A component re-rendered" means only that its function ran again.
3 · Commit
React compares the new element tree with the previous one and applies the minimum set of DOM operations. Then it attaches refs, runs layout effects, lets the browser paint, and finally runs effects.
The sentence to internalise

A re-render does not mean a DOM update. A component whose function runs a hundred times and returns identical output causes zero DOM operations. The cost of an unnecessary re-render is the JavaScript — calling the function, allocating the elements, running the diff — not the browser work. That is why Chapter 10's advice is about avoiding calls, and why a page can be slow while the DOM is perfectly stable.

3Reconciliation

The diff. Two heuristics, and everything else follows from them.

A general tree comparison is O(n³), which is unusable, so React makes two assumptions. Different element types produce entirely different trees — so if the type at a position changed, throw the old subtree away rather than trying to match inside it. And children can be matched by a key you provide — otherwise they are matched by position.

Identity is position plus type plus key

        
React does not know your component is "the same one". It knows that at position 3 of this parent there was a <Row> with key a7, and there still is. Change any of the three and it is a different thing: unmount the old, mount the new, discard state.

        
Different type destroys everything below

        
Changing <div> to <section> at the top of a subtree recreates every DOM node inside it and resets every component's state, even though the children are identical. Same for swapping which component renders at a position.

        
Conditional wrappers are the sneaky case

        
{isMobile ? <div>{form}</div> : form} changes the type at that position when the viewport crosses a breakpoint, so the form remounts and loses everything the user typed. Render the same wrapper both times and change its class instead.

        
State lives with the position, not the variable

        
Two sibling <Counter /> elements each have their own state because they occupy different positions. Render one in an if and the other in the else at the same position and they share state, which is almost never what you meant. A key on each separates them.

      

    


    
    

      
4Commit, and what runs when

      
The order matters, and one of these steps blocks the browser from painting.


      

        
The commit sequence order of operations

        
render phase   →  your component functions run (pure, interruptible)
                  the new element tree exists in memory

commit phase   →  1. DOM mutations applied
                  2. refs detached from old nodes, attached to new
                  3. useLayoutEffect cleanup, then useLayoutEffect
                     ── the browser has NOT painted yet ──
                  4. browser paints
                  5. useEffect cleanup, then useEffect

      


      

        
Why useLayoutEffect exists

        
It runs after the DOM is updated but before paint, so you can measure a node and adjust position without the user seeing an intermediate frame — tooltip placement, scroll restoration, measuring for an animation. The cost is that it blocks painting, so anything slow in it delays the frame. Default to useEffect; reach for the layout variant only when a flicker proves you need it.

        
Refs are attached during commit

        
Which is why ref.current is null during render and populated by the time effects run. Chapter 8.

        
Effects run after paint

        
Deliberately: the user sees the update immediately and the subscription, fetch or measurement happens a moment later. Chapter 9.

        
Commit is not interruptible

        
The render phase can be paused, abandoned and restarted; the commit phase cannot, because a half-applied DOM update would be visible. This is the boundary that makes concurrent rendering safe, and Chapter 12 builds on it.

      

    


    
    

      
5Batching

      
Why the value does not change on the line after you set it.


      

        
Three setters, one render JSX

        
function handleSubmit() {
  setSaving(true);
  setError(null);
  setAttempts(attempts + 1);

  console.log(saving);   // false — still the old value!

  // React collected all three updates, then renders ONCE.
  // `saving` in this scope is a const from the render that is
  // still executing; it cannot change. Chapter 5 calls this the
  // snapshot model and it is the single biggest source of
  // "why is my state one step behind" questions.
}

      


      

        
Automatic batching

        
Since React 18, updates are batched everywhere — event handlers, promises, timeouts, native listeners. Before 18 only event handlers were batched, which is why old articles warn about it.

        
Bail-outs

        
If a setter is called with a value that is Object.is-equal to the current one, React may skip the render entirely. It sometimes renders once anyway before bailing, which is harmless and occasionally visible in the profiler.

        
flushSync

        
Forces a synchronous render and commit, for the rare case where you must read the updated DOM immediately — scrolling to a row you just added, for instance. It defeats batching and concurrency, so it is a deliberate escape hatch, not a fix for confusion about the snapshot model.

      

    


    
    

      
6StrictMode

      
It is not broken, it is a test, and it only runs in development.


      
Wrapped in <StrictMode>, React deliberately double-invokes component functions, initialisers and updater functions, and mounts-unmounts-remounts each component once on first mount, running effects twice.


      

        

          
What the double invoke catchesHow it shows up

          
            
Impure componentsA counter increments twice, a log has duplicates, a random value differs — Chapter 3's checker

            
Effects with no cleanupTwo subscriptions, two intervals, two websockets, a request fired twice

            
State initialisers with side effectsTwo ids generated, two entries written

            
Code that assumes it mounts onceAnything that breaks when mounted, unmounted and mounted again — which is exactly what happens with fast navigation or offscreen rendering

          
        

        
The correct response to "my effect runs twice in development" is never to remove StrictMode. It is to write the cleanup, which the effect needed anyway. Chapter 9.

      

    


    
    

      
7The children escape hatch

      
A structural trick that removes re-render cascades without memoising anything.


      
A parent re-render calls its children — but "its children" means the components it creates elements for during its own render. An element passed in as children was created by someone else's render, so when the parent re-renders it receives the same element object it had before, and React skips that subtree entirely.


      

        
Same tree, two shapes JSX

        
// ✗ Counter's state change re-renders ExpensiveList every time,
//   because Counter creates that element during its own render.
function Counter() {
  const [n, setN] = useState(0);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <ExpensiveList />
    </div>
  );
}

// ✓ The element is created by the PARENT of Counter and handed in.
//   Counter re-renders on every click; ExpensiveList never does.
function Counter({ children }) {
  const [n, setN] = useState(0);
  return <div><button onClick={() => setN(n + 1)}>{n}</button>{children}</div>;
}

<Counter><ExpensiveList /></Counter>

      


      
No memo, no dependency array, nothing to keep in sync — a change of shape. Select the last option in section 2's demo to see it in the tree. It is the same idea as Chapter 3's answer to prop drilling, and it is the first thing to try before Chapter 10's memoisation.

    


    
    

      
8Check yourself

      
Six questions, closing Part 1.


      

        
1. Does a re-render mean the DOM changed?

        
        

          
No. A re-render means React called your component function again and collected the elements it returned. It then diffs that against the previous output and applies only the differences — which is frequently none. A component can re-render a hundred times with zero DOM operations. The cost of an unnecessary re-render is JavaScript: the function call, the allocations, the diff. That distinction matters because it tells you where to look when something is slow — the profiler's render counts, not the DOM inspector — and it explains why a perfectly stable-looking page can be janky.

        

      


      

        
2. What are the only things that trigger a render?

        
        

          
The initial mount, and a state update. Everything else is downstream: a parent rendering causes its children to render, and a context value changing causes its consumers to render, but both of those were themselves ultimately caused by a state update somewhere. What does not trigger a render is just as important: mutating an object, assigning to a variable outside the component, the DOM changing, a response arriving, or time passing. None of those tell React anything at all. Something must call a setter, which is why Chapter 1's demo of a silent mutation matters.

        

      


      

        
3. A form loses everything the user typed when the window is resized past a breakpoint. What is happening?

        
        

          
A conditional wrapper is changing the element type at that position — something like {isMobile ? <div className="stack">{form}</div> : form}. When the boolean flips, React sees a different type where the subtree used to be, and its first reconciliation heuristic says different types produce entirely different trees: unmount everything below, mount it fresh. All DOM nodes are recreated, all component state is discarded, inputs reset, focus is lost. The fix is to keep the structure identical and change only a class or a style, so the type at that position never changes. The same trap appears with a wrapper that only exists when a feature flag is on.

        

      


      

        
4. Why does console.log(count) immediately after setCount(count + 1) print the old value?

        
        

          
Because count in that scope is a constant belonging to the render that is currently executing, and nothing can change it — a setter does not assign to your variable, it schedules a re-render during which the function will be called again with a new value. React also batches, so several setters in one handler produce a single later render rather than one each. Chapter 5 calls this the snapshot model. The practical rules that follow: use the updater form setCount(c => c + 1) when the next value depends on the previous one, and if you need the new value in the same handler, compute it into a local variable and use that rather than reading state back.

        

      


      

        
5. Your effect fires twice in development. What is the correct response?

        
        

          
Write the cleanup. StrictMode deliberately mounts, unmounts and remounts each component once on first mount, running effects twice, precisely to surface effects that assume they run once. An effect that opens a subscription without closing it, starts an interval without clearing it, or fires a request without an abort signal is already broken — it will leak on every real unmount and every fast navigation too, just less visibly. Removing StrictMode hides the symptom and keeps the bug. The one legitimate exception is genuinely idempotent one-off work such as an analytics page view, where the standard answer is still to make it idempotent rather than to disable the check.

        

      


      

        
6. How does passing a component as children stop it re-rendering?

        
        

          
Because element creation, not rendering, is what a parent's render does to its children. When a component creates <ExpensiveList /> inside its own JSX, every render produces a new element object, so React reconciles that subtree again. When the element is created by a component higher up and handed in as children, the inner component's re-render does not recreate it — props.children is the same object as last time, React sees identical input, and skips the whole subtree. It is a change of shape rather than a memoisation, so there is no dependency array to keep correct and nothing to forget, which is why it is worth trying before memo.
