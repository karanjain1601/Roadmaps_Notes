CHAPTER 01

What React is, and what it is not

React is one idea with a decade of machinery attached. The idea takes a paragraph; the machinery takes this unit. Starting with the idea — and with the specific problem it removes — makes every later chapter a consequence rather than a rule to memorise.

Part 1 The model·Reading time 35 minutes·Demos manual versus declarative, state as input·Prerequisites JavaScript and the DOM

1The one idea

Everything else in this unit is an implementation detail of this sentence.

The interface is a function of state. You write a function that takes data and returns a description of what the screen should look like for that data. You never write instructions for changing the screen. When the data changes, the function runs again and React works out the difference.

The whole premise conceptual
// Imperative: you describe the CHANGES.
//   "when the count goes up, find the label and set its text,
//    and update the badge, and enable the button, and…"

// Declarative: you describe the RESULT.
function Cart({ items }) {
  return (
    <div>
      <h2>{items.length} items</h2>
      <p>Total: {format(total(items))}</p>
      <button disabled={items.length === 0}>Checkout</button>
    </div>
  );
}

// There is no code anywhere that updates the heading when an item
// is added. There does not need to be. The heading is derived.

The payoff is not less typing. It is that you can no longer forget an update path, because there are no update paths. A view that is derived from state cannot disagree with the state.

3What React actually provides

A short list. Shorter than most people assume.

A component model
A function that takes props and returns a description of UI. Components compose, so a screen is a tree of them. That is the unit of reuse, the unit of reasoning and the unit of testing.
Reconciliation
Given the previous description and a new one, work out the minimum set of DOM operations. This is the part that lets you re-describe the whole screen on every change without rebuilding it. Chapter 4.
State attached to position in the tree
useState and its relatives give a component memory that survives re-renders and is destroyed when the component is removed. Chapter 5.
A scheduler
React decides when to render, can batch several updates into one pass, and since version 18 can interrupt low-priority work to keep the page responsive. Chapter 12.
A rendering target abstraction
The same component tree can be committed to the DOM, to native views, to a canvas, to a PDF, or to a string on a server. react-dom is one renderer among several, which is why the core package contains no DOM code at all.

That is the whole of React. It is a library for describing and updating a tree, not a framework for building applications — which is the subject of the next section and the reason Part 4 exists.

5State in, description out

A rendering function made literal, so the shape of the idea is visible before any React syntax appears.

The component is a function; the state is its argument Edit the state and the output is regenerated from scratch. No update code exists.

Output

Two consequences worth carrying forward

The function must be pure. Same state in, same description out, with no side effects during the call. React relies on this to be allowed to run your component whenever it likes, twice, or not at all. Chapter 3 makes it a rule.

Mutating state changes nothing on screen. The demo's second button shows this: the data is different, the output is not, because nothing told the renderer to run. React's answer is that you never mutate — you produce a new value and call a setter, which is Chapter 5.

6What it costs

An honest ledger. React is a good default and it is not free.

CostDetail
BytesReact plus react-dom is roughly 45 KB compressed before you write anything, and that is downloaded, parsed and executed on the user's device. Small on a laptop, not small on a cheap phone.
Work done twiceServer-rendered React runs your components once on the server for the HTML and again in the browser to attach behaviour. That gap is where "looks finished, ignores clicks" comes from. Chapter 19.
Re-render cascadesBy default a parent re-render re-runs every descendant. This is the source of most React performance problems, and the reason memo, useMemo and useCallback exist. Chapter 10.
IndirectionA bug is now somewhere in your code, in a hook, in a library, or in an interaction between them. Debugging requires understanding the render cycle rather than reading the DOM.
Assembly requiredSection 4. Eight decisions before the first feature, each of which the team must agree on and maintain.
Ecosystem churnReact's own API has been remarkably stable — hooks arrived in 2019 and are still the model. The surrounding ecosystem has not been, and a four-year-old React tutorial usually recommends three libraries nobody uses now.

7When not to use it

A chapter that only lists advantages is marketing.

SituationBetter answer
A content site: marketing pages, a blog, documentationStatic HTML, or Astro with islands. The interactivity is a search box and a menu; shipping a rendering library to make a paragraph appear is a poor trade.
A handful of interactive widgets on server-rendered pagesPlain JavaScript, web components, Alpine, or htmx. React expects to own a tree.
A widget embedded in third-party pagesPreact or a web component — smaller, and it will not conflict with whatever the host page is running.
The absolute smallest possible bundleSvelte or Solid. Front-end Developer Chapter 18 explains why their update model needs less runtime.
A team that already knows Vue or Angular wellThat one. Fluency beats a benchmark difference nobody will measure.

Where React is the right answer: an application with genuine interactive complexity, many components, shared state and a long life — dashboards, editors, admin tools, anything app-like. Also, honestly, when hiring is the constraint, because the labour market and the ecosystem are larger than the alternatives combined and that is a legitimate engineering input.

8Starting a project

One decision, then two commands.

Library or framework?
The one real decision. Vite gives you React and a build, and you assemble the rest — correct for a single-page application behind a login, an internal tool, or anything embedded. A framework — Next.js, React Router 7 — gives you routing, data loading, server rendering and server components already wired together, which you want for anything public-facing where the first load and search indexing matter. Chapter 20 compares them properly; if you are unsure while learning, use Vite, because it hides less.
Not create-react-app
It was the standard for years and is deprecated. Anything recommending it is out of date, which is a useful signal about the rest of that source.
The commands
npm create vite@latest my-app -- --template react-ts, then npm install and npm run dev. Choose the TypeScript template even if you are new to it — Chapter 17 covers it, and retrofitting types later is much more work than starting with them.

9The rules, stated once

Four constraints. Almost every confusing React bug is one of them being broken.

1 · Components must be pure
Given the same props and state, return the same output, and change nothing outside yourself while rendering. No writing to variables declared outside, no mutating props, no network calls, no DOM manipulation during render. Chapter 3.
2 · Never mutate state
Produce a new object or array and pass it to the setter. React compares by reference; a mutated array is the same array and the change is invisible. Chapter 5.
3 · Hooks run unconditionally, in the same order, every render
No hooks in conditions, loops, or after an early return, and only in components or other hooks. They are matched by call order, not by name. Chapter 5 explains why, which makes the rule obvious rather than arbitrary.
4 · Render is for describing; effects and handlers are for doing
Anything that touches the outside world — requests, timers, subscriptions, logging, navigation — belongs in an event handler if a user caused it, and in an effect if it is synchronising with something external. Chapter 9 is largely about how often the answer is "neither".

The linter enforces rule 3 and part of rule 1. eslint-plugin-react-hooks is not optional; install it before your second component.

10Check yourself

Five questions.

1. What does "declarative" buy you that is not just a matter of taste?

The elimination of a bug class. In imperative code, every pair of state and view needs an update path, and correctness depends on remembering all of them on every change — so the failure mode is a screen showing something that was true a moment ago, and it gets worse as the interface grows. When a view is derived from state, it cannot disagree with the state, because there is nowhere for the disagreement to live. The demo in section 2 shows this concretely: adding a sixth view to the declarative version costs one line and cannot go stale; adding it to the imperative version costs one line plus remembering every setter that must now update it.

2. React is described as a library rather than a framework. What follows from that in practice?

That it gives you a component model, reconciliation, state and a scheduler — and nothing else. Routing, data fetching, forms, styling, global state and the build setup are all decisions you make, which is why two React codebases can share no libraries at all and why "learning React" is really learning eight things. The upside is that the same core runs in a browser, a mobile app, a server render and a VS Code extension. The practical implication for a new project is section 8's single real decision: assemble it yourself with Vite, or take a framework that has already made the choices.

3. Why does React insist components are pure?

Because purity is what makes it safe for React to control when and how often your function runs. It batches updates, renders speculatively, discards work that is no longer needed, and — since concurrent rendering — can start a render, abandon it, and start again. All of that is only correct if calling your component has no observable effect beyond returning a description. Break purity and you get bugs that appear only under StrictMode, only in production, or only when a user types quickly, which are the hardest kind to track down. It is also why StrictMode deliberately double-invokes in development: to make the impurity fail loudly and early.

4. When would you actively recommend against React?

When the page is mostly content. A marketing site, a blog or documentation needs to load fast and be indexable, and its interactivity is a menu and a search box — so shipping a 45 KB runtime plus your components, and then hydrating them, makes every metric worse for no gain. Static HTML or Astro with islands is the better answer. Similarly for a few widgets on server-rendered pages, where React expects to own a tree and does not fit; for embeddable third-party widgets, where Preact or a web component avoids imposing anything on the host; and for a team already fluent in another framework, where fluency outweighs any benchmark difference.

5. In the state demo, mutating the object changed the data but not the screen. What is React's version of that problem?

Exactly the same problem, and it is one of the most common beginner bugs: items.push(x) followed by setItems(items) does nothing visible. React needs two things to happen — it must be told that state changed, via a setter, and the new value must be a different reference, because comparison is by identity. A mutated array satisfies neither properly: you called the setter, but the value is the same object, so React can legitimately conclude nothing changed. The fix is always to produce a new value: setItems([...items, x]). Chapter 5 covers the patterns for every shape of state, and Chapter 10 explains why reference identity matters even more once memoisation is involved.
