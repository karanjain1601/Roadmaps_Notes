CHAPTER 17

TypeScript with React

Most React and TypeScript friction comes from fighting inference that would have worked, or from typing the wrong thing. This chapter is the small set of patterns that cover almost everything, and the handful of habits that cause the rest of the pain.

1Typing props

One decision, made once per component, and three conventions that have shifted.

The shape to use TypeScript
type ButtonProps = {
  children: React.ReactNode;
  tone?: 'solid' | 'outline' | 'ghost';      // a union, not string
  onPress: (id: string) => void;
};

function Button({ children, tone = 'solid', onPress }: ButtonProps) { ... }

// Not React.FC. It adds nothing now that implicit children are gone,
// it makes generic components awkward, and it interferes with
// defaultProps typing. Annotate the parameter instead.

// Accept every attribute the underlying element takes, then add yours.
type Props = React.ComponentPropsWithoutRef<'button'> & { tone?: Tone };
// …WithRef<'button'> if you are forwarding a ref.
// ComponentProps<typeof MyComponent> gets another component's props.

type or interface
For props, either works. type composes with unions and intersections, which props often need; interface supports declaration merging, which props never want. Pick one for the codebase and stop discussing it.
Children
React.ReactNode for anything renderable — the right answer almost always. React.ReactElement only when you genuinely require a single element and intend to clone or inspect it. Never JSX.Element for children: it excludes strings, numbers, arrays and null, all of which are valid.
Prefer unions to string
tone: 'solid' | 'outline' gives autocomplete, catches typos and lets the compiler check exhaustiveness. tone: string gives you nothing at all, which the demo shows.

2Events and handlers

Two ways to get an event typed, and only one of them requires you to know the name.

Let inference do it where you can TypeScript
// ✓ Inline: the event is inferred from the element. Nothing to import.
<input onChange={e => setValue(e.target.value)} />

// ✓ Extracted: now you must name the type.
function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setValue(e.target.value);
}

// The ones you will actually use:
//   React.MouseEvent<HTMLButtonElement>
//   React.ChangeEvent<HTMLInputElement | HTMLSelectElement>
//   React.FormEvent<HTMLFormElement>
//   React.KeyboardEvent<HTMLInputElement>
//
// target vs currentTarget: currentTarget is the element the handler is
// ON and is correctly typed; target is whatever was clicked and is
// typed as EventTarget. Reach for currentTarget by default.

// Typing a handler PROP — describe the function, not the event.
type Props = { onSelect: (id: string) => void };

// Returning void in the type means callers may return anything and it
// is ignored — which is what lets `onClick={() => setOpen(true)}` work
// even though setOpen returns void|undefined.

Exhaustiveness, enforced TypeScript
function render(r: Result<Order[]>) {
  switch (r.status) {
    case 'idle':    return null;
    case 'loading': return <Skeleton />;
    case 'error':   return <Retry message={r.error} />;
    case 'success': return <Table rows={r.data} />;
    default: {
      const _exhaustive: never = r;   // add a 5th state → compile error here
      return _exhaustive;
    }
  }
}

// The same trick for props: mutually exclusive combinations.
type ButtonProps =
  | { href: string; onClick?: never }      // a link
  | { onClick: () => void; href?: never };  // a button
// Passing both is now a compile error rather than a code review note.

4Generic components and hooks

Less exotic than it sounds — any list or table component wants one.

A generic list, and a generic hook TypeScript
// The item type flows from `items` into `renderItem` and `getKey`,
// so the caller gets full autocomplete inside the render function.
type ListProps<T> = {
  items: T[];
  getKey: (item: T) => string;
  renderItem: (item: T) => React.ReactNode;
};

function List<T>({ items, getKey, renderItem }: ListProps<T>) {
  return <ul>{items.map(i => <li key={getKey(i)}>{renderItem(i)}</li>)}</ul>;
}

<List items={orders} getKey={o => o.id} renderItem={o => o.reference} />
//                                    ↑ o is Order, inferred, no annotation

// Constrain when the component needs something from T
function Table<T extends { id: string }>({ rows }: { rows: T[] }) { ... }

// A hook returning a tuple needs `as const`, or TypeScript widens it
// to (T | Setter)[] and destructuring gives you a union.
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return [on, useCallback(() => setOn(v => !v), [])] as const;
}
Let inference work
useState(0) is already number. Annotate only when the initial value does not describe the eventual type: useState<User | null>(null), or an empty array that will hold objects.
Typing a ref
useRef<HTMLInputElement>(null) gives you RefObject with a possibly-null current, which is correct — the node does not exist during the first render. For a mutable value box, useRef<number | null>(null) and check before use rather than asserting.
Typing a reducer
Annotate the reducer function's parameters and the state and action types are inferred at the useReducer call. A union of action objects with a literal type field gives you exhaustiveness in the switch, exactly as in section 3.
satisfies for configuration objects
const routes = {…} satisfies Record<string, Route> checks the shape while keeping the specific literal keys, so routes.orders autocompletes. A plain annotation would widen it and lose them.

5Context, and the null problem

Chapter 7's hook wrapper, now doing a second job.

Narrow once, not at forty call sites TypeScript
// There is no sensible default, so the context is nullable…
const CartContext = createContext<CartApi | null>(null);

// …and the hook narrows it away for everyone.
export function useCart(): CartApi {
  const ctx = useContext(CartContext);
  if (!ctx) throw new Error('useCart must be used inside <CartProvider>');
  return ctx;
}

// The alternative — createContext({} as CartApi) — compiles and lies:
// a missing provider becomes undefined property access at runtime
// instead of a clear error, and the type system helped nobody.

6The boundary problem

The most important thing in this chapter: types are erased, so they check nothing at runtime.

as User is a claim, not a check

const user = await res.json() as User tells the compiler to stop asking questions. It does not inspect the response. If the API renamed a field, returned null, sent a number as a string, or replied with an error envelope, TypeScript is now confidently wrong everywhere downstream — and the failure surfaces three components away as "cannot read property of undefined", with a stack trace pointing at innocent code. Every as at a data boundary is a place where your types and reality are allowed to disagree.

Validate at the edge, infer the type from the schema Zod
const userSchema = z.object({
  id: z.string(),
  name: z.string(),
  joinedAt: z.coerce.date(),
  plan: z.enum(['free', 'pro', 'team'])
});
type User = z.infer<typeof userSchema>;   // derived, cannot drift

async function getUser(id: string): Promise<User> {
  const res = await fetch('/api/users/' + id);
  if (!res.ok) throw new HttpError(res.status);
  return userSchema.parse(await res.json());   // throws HERE, with a useful message
}

// The same schema validates the form in Chapter 14 and the search
// params in Chapter 15. One definition, three jobs, no drift.

The boundaries worth validating: HTTP responses, localStorage and sessionStorage, URL search params, postMessage data, environment variables, and anything from a third-party script. Everything inside those boundaries can then be trusted, which is the whole point of doing it at the edge.

Where the pain usually is
A generic component whose inference collapses, a library with weak types, or an over-clever conditional type someone wrote to save four lines. In all three cases the answer is to simplify rather than to escalate. If a type takes twenty minutes to write, it will take the next person twenty minutes to read.

8Check yourself

Five questions.

1. Why is React.FC no longer recommended?

Its main historical benefit — implicitly adding children to every component's props — was removed in React 18's types, because it was wrong: most components do not accept children, and typing them as though they do hides a real error. What remains is friction: it makes generic components awkward to declare, it interacts badly with defaultProps, and it adds a layer of indirection for no checking benefit. Annotate the props parameter directly — function Button(props: ButtonProps) — and declare children: React.ReactNode when the component actually takes them.

2. Why prefer a union of literals over string for a variant prop?

Because string accepts everything and therefore checks nothing. With tone: 'solid' | 'outline' | 'ghost' you get autocomplete at the call site, a compile error for a typo such as "outlined", and the ability to switch exhaustively so adding a fourth tone produces errors everywhere that needs updating. With tone: string, a misspelling compiles happily and produces a component that silently falls through to a default style — the demo shows exactly that call site being accepted. The same argument applies to sizes, statuses, alignments and anything else with a closed set of values.

3. What does as User actually do at a fetch boundary?

Nothing at runtime. Types are erased at compile time, so the assertion only instructs the compiler to stop checking — it performs no inspection of the response whatsoever. If the API renamed a field, returned null, stringified a number or sent an error envelope, the value flows onward with a type that is a lie, and the failure appears somewhere unrelated as an undefined property access. Validate instead: parse the response with a schema, derive the TypeScript type from that schema with z.infer so the two cannot drift, and let it throw at the boundary with a message naming the field. The boundaries that need it are responses, storage, URL params, postMessage and environment variables.

4. How do you make two props mutually exclusive?

A discriminated union of prop shapes, with never to forbid the other member: { href: string; onClick?: never } | { onClick: () => void; href?: never }. Passing both is then a compile error rather than something caught in review or not at all. The same technique handles a component where one prop makes another required — for example { variant: 'link'; href: string } | { variant: 'button'; href?: never }. It is Chapter 6's "make illegal states unrepresentable" applied to the props interface, and it is usually a better answer than runtime warnings or documentation.

5. Your build succeeds but the application has type errors. How?

Because your bundler is not the type checker. Vite, esbuild and SWC strip TypeScript syntax without analysing it — that is exactly why they are fast — so a file full of type errors transpiles perfectly and the build is green. Nothing is verifying your types unless you run tsc --noEmit separately, which belongs in CI and ideally as a pre-push check. The editor shows errors because it is running the language server, which is a different tool again; a project can therefore be red in every developer's editor and green in the pipeline for months.
