CHAPTER 10

Re-renders and memoisation

React's default is to re-run everything below a change. That is usually fine and occasionally the reason an interface feels sticky. This chapter is about telling the two apart, and about the four fixes in the order you should try them — because three of them are structural and free, and the one everybody reaches for first is neither.

Part 3 Fast and reusable·Reading time 40 minutes·Demos what defeats memo, the fix ladder·Prerequisites Chapters 4–5

1First, does it matter?

Most re-renders are free. Optimising the ones that are is how codebases fill with noise.

A re-render is a function call, not a DOM update
Chapter 4. Re-rendering a component that returns identical output produces zero DOM operations. The cost is the call, the element allocations and the diff — cheap enough that a hundred of them per second is unremarkable.
It matters when the work is real
A list of five hundred rows. A component doing genuine computation during render. A chart. A tree deep enough that the diff itself is measurable. An interaction on a cheap phone where the main thread is already busy.
Measure before and after
The React DevTools Profiler tells you which components rendered, why, and how long each took. If you cannot point at a number, you are guessing — and memoisation added on a guess is pure cost.
The user-visible symptom
Typing that lags, a slider that stutters, a click that takes a moment. If nothing feels slow, there is no problem to solve, regardless of how many highlight flashes DevTools shows.

2The four fixes, in order

1 · Move the state down
If only one subtree cares about the value, put it there. The re-render circle shrinks to that subtree and nothing above it runs. Chapter 4's demo showed this: state at the top re-runs eight components, state at a leaf re-runs one. Free, and it usually makes the component more reusable as well.
2 · Lift the expensive content up and pass it as children
Chapter 4's escape hatch. The expensive element is created by a component that is not re-rendering, so the stateful component receives the same element object and React skips the subtree. No dependency array, nothing to keep in sync.
3 · Split the component
Often the state and the expensive markup are in one function only by accident. Extracting the input and its state into a small sibling means the table is no longer below the thing that changes.
4 · Memoise
Only when the structure genuinely cannot be changed — a shared component library, an unavoidable context, a legitimately expensive computation. It works, and it is the option with ongoing maintenance cost.

// memo takes a second argument if you need a custom comparison —
// but reaching for it usually means the props are the wrong shape.
export default memo(Row, (prev, next) => prev.item.id === next.item.id);
Memoisation is all-or-nothing per boundary

A memoised component with eight props is only skipped when all eight compare equal. One unstable prop makes the other seven irrelevant — and nothing warns you. That is why memoisation silently stops working over time: someone adds an inline handler in a hurry, the component starts re-rendering again, and the wrapper stays in the code looking like protection it no longer provides.

4useMemo and useCallback

Two hooks, one purpose: keep a value the same between renders.

CachesUse when
useMemo(fn, deps) The result of calling fn The computation is genuinely expensive, or the result is an object or array that feeds a memoised child, an effect dependency, or a context value.
useCallback(fn, deps) The function itself The function is passed to a memoised child, used as an effect dependency, or handed to a long-lived subscription. It is useMemo(() => fn, deps) with nicer syntax.

Both take the same dependency rules as an effect, and the same linter enforces them. Neither is a guarantee: React may discard a memoised value to free memory, so they are performance hints, never a place to store something you cannot recompute.

Two distinct reasons, often confused
Expensive computation — sorting ten thousand rows — where you memoise because the work is slow. Referential stability — an options object passed to a memoised child — where the work is trivial but the identity matters. The second is far more common, and it is the one that fails silently when the dependency array is wrong.
Memoising a value nobody compares does nothing
useMemo around a cheap calculation whose result feeds only plain JSX is pure overhead: an extra array, an extra comparison, more code to read.
Measure "expensive"
Wrap it in console.time, or use the Profiler. Under about a millisecond it is not expensive. Also test with the CPU throttled — Chapter 1 of the Front-end unit — because your laptop is not the constraint.
The chain has to be complete
A memoised callback passed to a non-memoised child buys nothing. A memoised child receiving one unstable prop buys nothing. Half-applied memoisation is common and is all cost.

5The React Compiler

Most of this chapter, automated — with conditions.

The compiler analyses your components at build time and inserts memoisation where it can prove it is safe. Written correctly, a component gets the equivalent of memo, useMemo and useCallback applied precisely, without any of it appearing in your source.

What it changesWhat it does not
You stop hand-writing useCallback and most useMemo; inline handlers and object props stop defeating memoisation; the memoisation cannot drift out of date, because it is derived from the code every build It only optimises code it can prove is safe — a component that mutates props or state, or reads a ref during render, is skipped silently. Structural fixes still beat it: moving state down avoids the work entirely rather than caching it. And it cannot fix an algorithm that is genuinely slow.

Practical consequence: the compiler rewards code that already follows the rules from Chapter 3. eslint-plugin-react-hooks reports which components the compiler had to skip and why, which makes it a correctness tool as much as a performance one. Adopt it, keep the lint rule as an error, and delete hand-written memoisation only after checking the Profiler.

6Finding the problem

Four tools, roughly in the order you should reach for them.

React DevTools Profiler
Record an interaction, then read the flame chart: which components rendered, how long each took, and — with "record why each component rendered" enabled in the settings — whether it was props, state, hooks or a parent. That last column is the one that tells you which fix applies.
Highlight updates
A checkbox in DevTools that flashes a border around every component as it re-renders. Ten seconds of setup, and it makes a cascade immediately obvious — including the ones you would never have suspected.
The browser Performance panel
For the whole picture: long tasks, layout, paint, and whether the problem is React at all. A slow interaction is often a large DOM or an expensive style recalculation rather than a render count.
Throttle the CPU
4× or 6× slowdown in the Performance panel. A cascade that costs three milliseconds on a laptop costs eighteen on a mid-range phone, which is the difference between imperceptible and sticky.

7What memoisation costs

The section most performance advice omits.

Runtime
Every useMemo and useCallback allocates a dependency array and compares it on every render, and keeps the previous value alive in memory. Small — and applied indiscriminately across a large codebase, no longer negligible, while providing nothing where it was not needed.
Reading cost
A component wrapped in three layers of memoisation is harder to read and change than one that is not. Every dependency array is a small piece of state that must stay correct.
Silent decay
Section 3's warning: memoisation stops working when someone adds an inline prop, and nothing tells you. The wrapper stays, looking like protection.
It can hide the real problem
Memoising around a component that renders eight hundred DOM nodes treats the symptom. Virtualisation, pagination, or simply rendering less is the actual answer, and the memo makes it less obvious that anything is wrong.
The honest summary
Prefer structure. Memoise deliberately, at a measured boundary, and write down why. Adopt the compiler so the mechanical cases stop being your problem.

8Check yourself

Five questions.

1. A colleague wraps every component in memo. What is wrong with that?

Most of it is pure cost. Each wrapper adds a props comparison on every render of the parent and keeps the previous props alive, in exchange for skipping a function call that was probably free — a component returning a few elements costs microseconds. It also makes the codebase harder to read and creates the illusion of protection, because a single inline arrow function passed to any of those components defeats its memo entirely and nothing warns you. Memoise at measured boundaries, after the Profiler has shown a real cost, and prefer the structural fixes that avoid the work rather than caching it.

2. Why does an inline onClick={() => select(id)} defeat memo?

Because an arrow function written in JSX is a new function object on every render, and memo compares props with Object.is. Two functions with identical source are not equal, so the comparison fails and the child re-renders exactly as if memo were not there. The same applies to object literals such as style={{...}} and to arrays built during render. Fixes: useCallback for the handler, a hoisted constant or a CSS class for the style, useMemo for the array — or the React Compiler, which handles all three automatically. And note the all-or-nothing rule: one unstable prop makes the other seven irrelevant.

3. Typing in a filter box lags because a large table below re-renders. What do you try first?

Move the state down. If the input's value is only needed by the input and the filtering logic, extract them into a small component so the table is no longer below the thing that changes — the cascade disappears rather than being cached. If the table genuinely needs the value, the next structural option is to hoist the table up and pass it as children to the stateful component, so React receives the same element object and skips the subtree. Only when the structure truly cannot change does memo plus useCallback become the answer, and at that point you should also ask whether eight hundred rows should be virtualised regardless.

4. What are the two distinct reasons to use useMemo?

Expense and identity. Expense: the computation itself is slow — sorting thousands of rows, parsing something large — and you want to avoid redoing it. Identity: the computation is trivial but the result is an object or array whose reference matters, because it is passed to a memoised child, used as an effect dependency, or provided as a context value. The second reason is far more common and easier to get wrong, since a stale dependency array produces a subtly wrong value rather than merely slow code. Memoising a cheap value that feeds only plain JSX serves neither purpose and is overhead.

5. If the React Compiler inserts memoisation automatically, is this chapter obsolete?

No, for three reasons. It only optimises components it can prove are safe, and silently skips ones that mutate props or state or read refs during render — so you still need to know the rules, and the lint rule that reports skipped components becomes a correctness tool. It caches work rather than avoiding it, so the structural fixes still win: moving state down means the component never runs, which beats running it and discarding the result. And it cannot help with genuinely slow algorithms, oversized DOM trees, or a list that should be virtualised. What it does remove is the mechanical layer — hand-written useCallback everywhere, and the silent decay when someone adds an inline prop.
