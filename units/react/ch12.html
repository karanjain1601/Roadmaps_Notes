CHAPTER 12

Concurrent React

React can now start rendering, stop halfway, do something more urgent, and resume — or throw the work away entirely. That one capability is what transitions, deferred values and Suspense are all built on, and it changes what "the app is slow" means.

Part 3 Fast and reusable·Reading time 40 minutes·Demos measured input latency, boundary placement·Prerequisites Chapters 4, 10

1What concurrent means

Not threads. Interruptibility.

Chapter 4 established that the render phase is pure and the commit phase is not. That separation is what makes interruption safe: React can call your components, get partway through building a new tree, notice something more important has happened, abandon the work entirely, and start again — because nothing was committed and no side effects ran. All of it still happens on the single main thread.

It does not make anything faster
The same total work happens. What changes is when, and which work gets to jump the queue. A transition does not reduce the cost of rendering five thousand rows; it stops that cost from sitting between a keystroke and its character appearing.
Render can now run more than once per update
An interrupted render is discarded and restarted, so your component function may be called several times for one visible change. Harmless if it is pure, and the reason Chapter 3 insisted.
Commit is still atomic
Once React starts applying DOM changes it finishes. The user never sees half an update.
You opt in per update
Everything is urgent by default. Marking something non-urgent is a deliberate act with two hooks, which is sections 3 and 4.

2Urgent and non-urgent

The distinction React cannot infer and you can.

Urgent — must feel instantNon-urgent — can lag slightly
The character appearing as you type. A checkbox ticking. A button showing pressed state. Anything that is direct feedback for a physical action. The filtered results below the input. A chart redrawing. A route's content while the navigation is in progress. Anything derived from the urgent thing.

Both come from the same keystroke. Without transitions React treats them as one indivisible update, so the input cannot paint until the list has rendered. The whole point is to let the first commit without waiting for the second.

The shape JSX
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  setQuery(e.target.value);                      // urgent — the input
  startTransition(() => setFilter(e.target.value));  // non-urgent — the list
}

// isPending is true while the transition is rendering, so you can
// dim the stale content — WITHOUT replacing it with a spinner, which
// would be worse than the slight lag you were trying to fix.
<Results style={{ opacity: isPending ? 0.6 : 1 }} />

// The setter must be called INSIDE the callback, synchronously.
// This does not work — the await breaks the transition scope:
//   startTransition(async () => { await load(); setFilter(x); })
// Put the setter in a second startTransition after the await.

4useDeferredValue

For when you do not own the setter — a prop, or a value from a hook.

Deferring a value instead of an update JSX
function SearchResults({ query }) {           // query is a prop — no setter here
  const deferred = useDeferredValue(query);
  const isStale = query !== deferred;

  // React renders once with the old value (fast), then again with
  // the new one at low priority. The second render is interruptible.
  return <List query={deferred} style={{ opacity: isStale ? 0.6 : 1 }} />;
}

// It pairs with memo: without it, List re-renders on the urgent pass
// anyway and the deferral achieves nothing.
const List = memo(function List({ query }) { ... });

Neither replaces debouncing outright. Debouncing skips work; a transition does all of it but out of the way. For an expensive network call, debounce. For expensive rendering, a transition — and the two combine happily.

5Suspense

A boundary that shows a fallback while something below it is not ready.

Boundaries are about grouping
Everything inside one boundary appears together. That is a design decision: three separate spinners can look busier and worse than one skeleton that resolves into a finished page.
Design the fallback to match the layout
A skeleton with the same dimensions as the content prevents the layout shift a spinner causes. This is the most common Suspense mistake and it is measured as CLS.
Transitions suppress fallbacks
If an update inside startTransition causes a suspension, React keeps showing the old content instead of replacing it with the fallback. That is what makes navigating between routes feel continuous rather than flashing a skeleton on every click.
Suspense is not error handling
A rejected promise needs an error boundary, which is a separate component and usually sits just outside the Suspense boundary. Chapter 18.
The waterfall risk
A component that only starts fetching when it renders cannot start until its parent has resolved. Nested boundaries make that sequential loading look deliberate. Start requests as early as possible — a route loader, or a server component — which is Chapters 13 and 19.

6Actions, pending state and optimistic UI

Three hooks that make the async parts of a form honest with very little code.

The modern form shape JSX
// useActionState: the pending flag and the result, without four useStates
const [state, formAction, isPending] = useActionState(async (prev, formData) => {
  const res = await saveProfile(formData);
  return res.ok ? { ok: true } : { error: res.message };
}, { });

<form action={formAction}>
  <input name="email" />
  <SubmitButton />
  {state.error && <p role="alert">{state.error}</p>}
</form>

// useFormStatus: a child reads the enclosing form's state — no prop drilling
function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>;
}

// useOptimistic: show the result immediately, roll back automatically
// if the action throws. No manual snapshot, no manual revert.
const [shown, addOptimistic] = useOptimistic(messages, (cur, next) => [...cur, next]);

All three assume the async work is expressed as an action — a function passed to <form action> or run inside a transition. That is the same framing as Chapter 6's events: describe what happened, and let the framework derive the pending and error states rather than hand-maintaining four booleans.

7Pitfalls

Five ways to make things worse with the right tools.

A transition is not a performance fix
It reprioritises; it does not reduce work. If rendering the list takes 900ms it still takes 900ms, and the list is still 900ms stale. Fix the rendering — virtualise, paginate, memoise — and use a transition for the residue.
A spinner where the stale content would do
Replacing visible results with a fallback on every keystroke is worse than showing slightly old results dimmed. Use isPending for opacity, not for swapping in a loader.
Fallbacks that shift the layout
A 40px spinner replacing a 600px table moves everything below it twice. Size the skeleton to the content.
Forgetting that render may run twice
An interrupted render is discarded and restarted, so any impurity now fails visibly. Chapter 3's rules, enforced by the scheduler rather than only by StrictMode.
Deferring without memoising
useDeferredValue on a value passed to a non-memoised child does nothing: the child re-renders on the urgent pass regardless.

8Check yourself

Five questions, closing Part 3.

1. Does concurrent rendering make React faster?

No — it makes it more responsive, which is different. The same total work still happens on the same single thread. What changes is that React can interrupt a low-priority render to handle something urgent, and can discard work that has become irrelevant. So a keystroke can paint immediately even though the expensive list below it takes 300ms, because the two are no longer one indivisible update. If something is genuinely slow, a transition relocates the slowness rather than removing it: fix the rendering first — virtualise, paginate, render less — and use transitions for what remains.

2. When do you reach for useDeferredValue rather than useTransition?

When you do not own the setter. useTransition marks an update, so you need to be the one calling the setter — typically in the same handler that also does the urgent update. useDeferredValue marks a value, which is what you have when the fast-changing thing arrives as a prop or from a hook you do not control. React then renders once with the previous value and again with the new one at low priority. The catch is that it only helps if the expensive child is memoised; otherwise the child re-renders on the urgent pass anyway and the deferral achieves nothing.

3. Why does a Suspense fallback sometimes not appear during a navigation?

Because the update was inside a transition. When a transition causes something to suspend, React deliberately keeps the existing content on screen instead of swapping in the fallback — on the grounds that the user was already looking at something valid, and flashing a skeleton over it is a downgrade. That is what makes route changes in a modern router feel continuous. You surface the pending state with isPending instead, usually by dimming the stale content. Fallbacks still show on the first mount of a boundary, where there is nothing to keep.

4. What decides where a Suspense boundary should go?

What you want to appear together. Everything inside one boundary reveals at once, so a single root boundary means the whole page waits for its slowest section, while one boundary per section reveals each as it arrives — faster to first content, at the cost of the page assembling itself in front of the user and possibly shifting. Nested boundaries impose an order, which is right for genuinely dependent content and wrong when it merely hides a waterfall. The other half of the decision is the fallback: size it like the content it replaces, or you trade a loading delay for a layout shift.

5. Your handler is startTransition(async () => { await save(); setDone(true); }) and the transition seems to have no effect. Why?

Because the transition scope ends at the first await. React marks updates as non-urgent only for setters called synchronously inside the callback; anything after an await runs in a later task, by which time the scope is gone, so setDone is an ordinary urgent update. The fix is to wrap the post-await setter in its own startTransition, or to use an action-based API — useActionState and <form action> — which handles the async sequencing and the pending flag for you. It is an easy mistake because nothing errors; the code simply behaves as though you had not used a transition.
