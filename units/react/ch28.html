CHAPTER 28

PWAs and browser APIs

A service worker is a proxy you install on the user's device that outlives your page and intercepts its requests. That is an enormous amount of power, and the reason most PWA problems are not about caching strategy but about the update lifecycle nobody read.

Part 7 Shipping and practice·Reading time 45 minutes·Demos caching strategies, the update problem, live capability check·Prerequisites Chapters 2, 15–16

1What a progressive web app is

Three properties, not a badge in an audit tool.

Installable
It can be added to a home screen or dock and launched without browser chrome. Requires a manifest, HTTPS and — on most platforms — a registered service worker.
Reliable
It loads on a bad connection or none, because a service worker can answer from a cache rather than the network.
Capable
It uses the platform: files, camera, notifications, background sync, sharing. Section 7 is the inventory.

The strategic point is that each property is independent and incremental. Adding an offline fallback page to an ordinary website is a two-hour job that makes it measurably more reliable, and does not commit you to anything else. "Building a PWA" as a project is usually the wrong framing; adding one of these three because it solves a real problem is the right one.

Do not install a service worker just to have one

It is persistent code on the user's device that intercepts every request within its scope, and it survives long after your deploy. A bad one can serve a stale application to a user who has no way to escape short of clearing site data. Register one when caching, offline or push earns its place — and always ship the kill switch in section 2 before you need it.

2The service worker lifecycle

The part that causes the bugs. Read this section twice.

Registration and the three events JavaScript
// In the page — after load, so it never competes with the first paint
if ('serviceWorker' in navigator) {
  addEventListener('load', () => navigator.serviceWorker.register('/sw.js'));
}

// In sw.js — a separate worker context. No DOM, no window.
self.addEventListener('install', e => {
  e.waitUntil(caches.open('shell-v3').then(c => c.addAll(['/', '/offline', '/app.css'])));
});

self.addEventListener('activate', e => {
  // Delete old caches here — this is the only safe moment
  e.waitUntil(caches.keys().then(keys =>
    Promise.all(keys.filter(k => k !== 'shell-v3').map(k => caches.delete(k)))));
});

self.addEventListener('fetch', e => {
  // Not calling respondWith lets the request go to the network normally
  if (e.request.mode === 'navigate') {
    e.respondWith(fetch(e.request).catch(() => caches.match('/offline')));
  }
});
The update problem Two tabs, one new deploy. Step through and watch which version each tab is running.

Scope
A worker at /sw.js controls the whole origin; one at /app/sw.js controls only /app/. It cannot be widened above its own path without a Service-Worker-Allowed header, which is a deliberate restriction — a script on a shared host must not be able to intercept the whole domain.
The waiting state is the default and it is correct
A new worker installs but does not activate while any tab is still controlled by the old one, because two versions of your application running against one cache is worse than a delayed update. The consequence surprises everyone: refreshing does not update a service worker. The old tab must be fully closed, since a reload never leaves the page uncontrolled.
skipWaiting() is not a free fix
It activates immediately, which means an open tab loaded with version 1's JavaScript is suddenly being served version 2's assets. If your chunk hashes changed, that tab's next dynamic import fetches a file the new worker's cache does not have. Use it only alongside clients.claim() and a reload prompt, or when your assets are genuinely version-independent.
The pattern that works
Detect the waiting worker, show a small "A new version is available — reload" affordance, and post skipWaiting to it only when the user accepts, then reload on controllerchange. The user chooses the moment, so nothing is half-updated.
Ship the kill switch first
A worker that unregisters itself and clears every cache, ready to deploy at /sw.js. Without it, a broken service worker is very difficult to recover from remotely. Also note the browser revalidates the worker script itself roughly every 24 hours regardless of cache headers, which is the mechanism that eventually rescues you.

Five patterns. The skill is matching each resource type to the right one.

Never cache-first an unhashed HTML document

It is the classic way to trap users on an old version of your site. The document names your hashed assets, so a stale document points at chunks that no longer exist, and every navigation confirms the trap. HTML gets network-first or stale-while-revalidate; only content-hashed filenames earn cache-first.

4Working offline

Three levels, each a genuine step up in cost.

Level 1 — an offline page
Pre-cache one branded page and serve it when a navigation fails. Two hours of work, and it turns the browser's dinosaur into something that looks like your product and can say what to do next. Almost every site should do this.
Level 2 — an offline-readable app
Cache the shell and previously visited content, so a user who loses signal can still read what they had. Needs a storage plan — IndexedDB for structured data, the Cache API for responses — and a clear indication of what is stale.
Level 3 — offline writes
Queue mutations locally and replay them when connectivity returns, via Background Sync where available and a manual retry queue where not. This is where the real cost is, and it is not the queueing: it is conflict resolution. Two devices edited the same record offline; now what? Last-write-wins loses data silently. Deciding this properly is a product question before it is a technical one.
StorageUse
Cache APIRequest/response pairs. What a service worker uses; not for structured queries.
IndexedDBStructured data, large volumes, transactions, indexes. The raw API is unpleasant — use idb or Dexie.
localStorageSmall, synchronous, string-only. Synchronous means it blocks the main thread, so it is not for anything sizeable. Preferences only.
Origin Private File SystemA real file system per origin, with synchronous access from workers. For applications handling large binary data.

Quota is a browser decision and storage can be evicted under pressure. navigator.storage.estimate() reports usage and quota; navigator.storage.persist() requests exemption from eviction, and may be refused. Never treat browser storage as durable.

Maskable icons
Android crops icons to whatever shape the launcher uses. Without a maskable variant with adequate padding, your logo gets a corner cut off. It is the single most common visible manifest mistake.
Control the prompt
Listen for beforeinstallprompt, call preventDefault(), store the event, and show your own install affordance at a moment that makes sense — after a second visit, or after the user has done something worth keeping. Then call prompt() on the stored event. An unprompted banner on first load is dismissed and cannot be shown again for a long time.
iOS is different
Installation is manual through the share sheet, so an installed-app experience needs an instructional prompt. Push notifications require the app to be installed to the home screen first. Storage limits are tighter and eviction more aggressive. Test on a real device; the differences are not documented anywhere convenient.
Detect the installed mode
matchMedia('(display-mode: standalone)') tells you the app is running installed, which is when to hide the install button and possibly adjust navigation, since there is no browser back button.

6Push and notifications

Two separate APIs, one permission, and a large opportunity to annoy people.

Push delivers a message from your server to a browser push service to the user's service worker — which then usually shows a notification. The Notifications API can also be used entirely locally, without push.

Ask in context, never on load
A permission prompt on first visit is refused by the overwhelming majority, and a refusal is close to permanent — the browser will not ask again and the user must dig into site settings. Ask after the user does something that implies interest: "notify me when this is back in stock". Explain the value in your own interface first, and only call requestPermission() once they have said yes to that.
Browsers now suppress abusive prompts
Chrome and Firefox demote notification requests to a quiet indicator for sites whose prompts are usually blocked. Bad prompting is not just ineffective, it is penalised at the origin level.
What you need
VAPID keys to identify your server, a subscription obtained via pushManager.subscribe() and stored server-side, and a push handler in the worker. Subscriptions expire and are revoked; handle pushsubscriptionchange and prune dead endpoints or your send volume becomes meaningless.
Every push should show a notification
Silent pushes are restricted precisely because they could be used for background tracking. Budget-based exceptions exist and are limited.

8Check yourself

Six questions.

1. You deploy a fix, a user refreshes, and they still see the old version. Why?

The new service worker installed and went into the waiting state, because a reload never leaves the page uncontrolled — the old worker is still in charge of that tab throughout. The new one activates only when every tab controlled by the old one has closed. This is intentional: running two versions of your application against one shared cache is worse than a delayed update. The fix is not to bypass it blindly with skipWaiting(), which can hand version-1 JavaScript a version-2 asset set, but to detect the waiting worker, prompt the user to reload, and activate on their say-so.

2. Why is cache-first the wrong strategy for an HTML document?

Because the document's filename does not change when its content does, so a cached copy can be served indefinitely with no mechanism to notice it is stale. That traps the user on an old version — and it compounds, because the document names your content-hashed asset files, so a stale document points at chunks the new deployment no longer serves, and the page fails to load properly. Cache-first is correct precisely and only for content-hashed filenames, where the name is the version. HTML gets network-first with a cache fallback, or stale-while-revalidate.

3. What does stale-while-revalidate actually do, and what is the cost?

It returns the cached response immediately — so the user waits for nothing — and simultaneously fetches from the network in the background, updating the cache for next time. The cost is that the user always sees data one request behind: the first visit after a change still shows the old version, and only the visit after that is current. That is fine for an avatar, a list of categories or a non-critical panel, and wrong for a price, a balance or anything the user is about to act on. It also uses the network on every request, so it saves latency rather than bandwidth.

4. Why should you not request notification permission on page load?

Because the user has no context in which to say yes, so the overwhelming majority say no — and a refusal is effectively permanent: the browser will not prompt again, and the user would have to find site settings to change it. You get one attempt per user, ever. Spend it after they have done something implying interest, having explained the value in your own interface first, so the native prompt only appears once they have already agreed. Browsers also now demote prompts to a quiet indicator for origins whose requests are usually blocked, so bad prompting damages the origin, not just the moment.

5. What is genuinely hard about offline writes?

Not the queue — storing pending mutations in IndexedDB and replaying them on reconnect is straightforward. The hard part is conflict resolution: while the user was offline, the same record was changed elsewhere. Last-write-wins is simple and silently destroys someone's work. The alternatives — merging field by field, presenting the conflict to the user, or CRDTs that merge deterministically — each carry real cost and each need a product decision about what should happen. There is also ordering (a delete replayed before its update), idempotency so a retried mutation is not applied twice (Chapter 16), and telling the user honestly what has and has not been saved.

6. What is the one thing to build before shipping your first service worker?

The kill switch: a replacement sw.js that unregisters itself and deletes every cache, ready to deploy. A service worker is persistent code on the user's device that intercepts every request in its scope and survives your deploys, so a broken one is very hard to fix remotely — the user may be trapped on an old version with no obvious escape short of clearing site data. The browser does revalidate the worker script roughly every 24 hours regardless of cache headers, which is what eventually lets a fix propagate, but 24 hours is a long outage. Have the replacement written and tested before you need it.
