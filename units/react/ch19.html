CHAPTER 19

Server components and the boundary

Some of your components never run in the browser and never ship to it. That single change reorganises where data fetching lives, what your bundle contains, and which React features are available in which file — and almost all the confusion comes from one misunderstanding about how 'use client' spreads.

Part 5 Beyond the client·Reading time 45 minutes·Demos the import graph, what can cross·Prerequisites Chapters 12–13

1The idea

A component that runs once, on the server, and sends its output rather than its code.

What a server component looks like JSX
// No directive needed — server is the default in an RSC framework.
async function OrderPage({ params }) {
  const order = await db.order.findUnique({ where: { id: params.id } });
  return (
    <article>
      <h1>{order.reference}</h1>
      <AddToBasket id={order.id} />   {/* this one IS a client component */}
    </article>
  );
}

// Three things worth noticing:
//   1. It is async and awaits directly. No useEffect, no loading state.
//   2. It talks to the database. There is no API route in between.
//   3. Neither the query, the ORM, nor this function reaches the browser.
What is sent
Not HTML, and not the component's code. React serialises the rendered output — a description of the element tree, with placeholders where client components go — and streams it. The browser reconciles that into its existing tree, which is why a server-driven update does not blow away client state below it.
They render once, on the server
No re-rendering, no state, no effects, no lifecycle. A server component is closer to a template function that happens to be able to await.
The dependency stays behind
A markdown renderer, a date library, a syntax highlighter, an ORM — imported by a server component, none of it is in the browser's bundle. This is where most of the size win comes from, and section 4's demo makes it concrete.

A real page uses both: server components produce the tree, the client components within it are server-rendered to HTML for the first paint, then hydrated. And static generation is a third axis — when the server work happens, at build time or per request. Chapter 21 of the Front-end unit covers the strategies; this chapter is about the boundary.

3'use client' marks a boundary, not a file

The one misunderstanding responsible for most surprise bundle sizes.

It is an entry point, and it is contagious downwards

'use client' at the top of a file does not merely make that file a client component. It declares a doorway into client-land: that module and everything it imports, transitively, becomes part of the client bundle. Put it at the top of your root layout and you have opted your entire application out of server components while still paying for the architecture.

Where the boundary goes decides what ships Toggle components. The bundle is computed by walking the real import graph.

The escape hatch: children cross the boundary the other way JSX
// ✗ A client component IMPORTING a server component — impossible.
//   The import makes it a client module, and it cannot await the DB.
'use client';
import Reviews from './Reviews';      // Reviews is now a client component

// ✓ A client component RECEIVING one as children — fine.
//   The server rendered <Reviews /> already; the client component
//   only positions the resulting element.
// page.jsx — a server component
<Tabs>                            {/* client: holds the selected tab */}
  <Reviews productId={id} />      {/* server: queries the database */}
</Tabs>

// This is Chapter 4's children escape hatch again, now doing
// architectural work rather than performance work. Design client
// components to take children, and the boundary stays thin.

5Server actions

The write half. A function you can call from the client that only ever runs on the server.

Definition and use JSX
'use server';   // at the top of a file, or inside a single function

export async function updateOrder(formData) {
  const session = await auth();
  if (!session) throw new Error('Unauthorised');        // ← see below

  const data = orderSchema.parse(Object.fromEntries(formData));
  await db.order.update({ where: { id: data.id }, data });
  revalidatePath('/orders');      // the cached server render is now stale
}

// Used directly by a form — works before hydration.
<form action={updateOrder}>…</form>

// Or from a client component with the hooks from Chapter 12.
const [state, formAction, isPending] = useActionState(updateOrder, {});
Every server action is a public HTTP endpoint

The framework generates a URL for it and the client calls that URL. Anyone can call it with any arguments, in any order, at any time — the fact that your interface only invokes it from behind a permission check is irrelevant. Authenticate and authorise inside every action, validate every argument with a schema rather than trusting the types, and never accept an identifier that lets the caller pick whose record to modify without checking ownership. This is exactly the discipline an API route needs; the syntax hides that it is one.

Revalidation is the other half
A mutation that does not tell the framework what is now stale leaves the user looking at the old page. revalidatePath and revalidateTag are the server-side equivalent of Chapter 13's query invalidation, and forgetting them produces the same symptom.
Actions can be passed to client components
A function normally cannot cross the boundary; a server action is the deliberate exception. React sends a reference, not the code.
Progressive enhancement is real
A form with an action posts natively if JavaScript has not loaded. That is the reason the API is shaped around FormData rather than arbitrary arguments.

6What you gain and what you give up

Honest accounting, because the marketing tends to cover only the first column.

GainGive up
Bundle — heavy formatting, parsing and data libraries never ship. A second mental model. Two kinds of component with different capabilities, and the compiler errors are not always clear about which side you are on.
Data access without an API layer — query the database in the component that displays the result. A server to run. No more static hosting on a CDN alone, and someone must operate it.
No client waterfall — nested awaits happen server-side, next to the data, at microsecond latency. Sequential awaits still cost. Two dependent queries in one component are still two round trips; Promise.all is still your job.
Secrets stay secret — API keys, tokens and internal URLs never reach the browser. New ways to leak. Pass the wrong object as a prop and it is serialised into the response. Section 4's rules matter for security, not only correctness.
Streaming — send the shell immediately and let slow sections arrive in Suspense boundaries. Ecosystem friction. Any library that needs a context provider or a browser API needs a client wrapper. Runtime CSS-in-JS does not work at all (Chapter 16).

7The mistakes everyone makes first

Six, in roughly the order you will hit them.

1 · 'use client' at the top of the tree
One hook in a layout, one directive, and the whole application is a client bundle again. Push the directive down to the smallest component that genuinely needs interactivity.
2 · Wrapping a server component in a client one by importing it
The import converts it. Pass it as children instead.
3 · Reaching for hooks in a server component
useState, useEffect, useContext, event handlers and browser APIs are all unavailable. The error message names the hook, not the reason, so the fix is to ask whether this really needs to be interactive.
4 · Assuming a server action is private
Section 5. It is an endpoint.
5 · Forgetting to revalidate
The mutation works and the page still shows the old data, which looks like a caching bug in the framework and is not.
6 · Sequential awaits in one server component
await getUser() then await getOrders() is two serial round trips even on the server. Independent queries go in Promise.all; genuinely slow ones go behind their own Suspense boundary so they stream.

8Check yourself

Five questions.

1. How are server components different from server-side rendering?

Server-side rendering runs your components on the server to produce HTML for the first paint, then ships those same components to the browser so they can hydrate and become interactive — the code is in the bundle either way. A server component's code never reaches the browser: it runs on the server, and what is sent is a serialised description of its output. It therefore cannot have state, effects or event handlers, but it can await a database query directly and import a large library without any cost to the user. They are complementary: server components produce the tree, and the client components inside it are still server-rendered to HTML and hydrated.

2. What exactly does 'use client' do?

It declares a boundary — an entry point into the client bundle. That module and everything it imports, transitively, becomes client code. It is not a per-file annotation you sprinkle on the components that happen to be interactive; it marks the doorway, and everything beyond the doorway is inside. This is why putting it at the top of a root layout silently opts the entire application out of server components, and why the demo shows the bundle jumping when the page itself is marked: a heavy markdown renderer that was previously server-only gets dragged along. Push the directive to the smallest components that genuinely need state or events.

3. You need a server component inside a client component. How?

Pass it as children from a server component higher up, rather than importing it. Importing is what converts a module to client code, so a client component that imports <Reviews /> turns it into a client component and its database query stops being possible. Composition avoids that entirely: a server component renders <Tabs><Reviews /></Tabs>, the server evaluates Reviews, and the client Tabs component receives the already-rendered element and only decides where to put it. It is Chapter 4's children escape hatch doing architectural work, and designing client components to accept children is what keeps the boundary thin.

4. Why can a function not be passed as a prop across the boundary, and what is the exception?

Because props crossing the boundary are serialised into the response stream, and there is no way to serialise a closure — its captured scope exists only in the server process. So an onClick defined in a server component cannot be handed to a client component; the handler must be defined on the client side. The exception is a server action: a function marked 'use server', for which React sends a reference rather than the code. Calling it from the client performs an HTTP request back to the server, which is why every action needs its own authentication and validation.

5. Your mutation succeeds but the page still shows the old data. Why?

Because nothing told the framework the cached server render is now stale. The action updated the database, but the page it came from was rendered earlier and cached; without revalidatePath or revalidateTag, that cached output is served again. It is precisely Chapter 13's invalidation problem moved to the server, and the symptom is identical — the write works, the read is stale, and it looks like a framework bug. The habit to build is the same as with a query cache: every mutation declares what it invalidated, and the key hierarchy or path structure is what makes that one line rather than an enumeration.
