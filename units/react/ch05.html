CHAPTER 05

State and the snapshot model

State is not a variable you change. It is a value React hands your function each time it calls it, and a request to be called again with a different one. Getting that distinction straight resolves the single most common category of React confusion — the one where the value is always one step behind.

Part 2 State·Reading time 45 minutes·Demos the update queue, state shape·Prerequisites Chapters 3–4

1What useState gives you

Memory attached to a position in the tree, and a way to ask for another render.

The shape, and the two things it returns JSX
const [count, setCount] = useState(0);
//     ↑ this render's value    ↑ ask React to render again with a new one

// Lazy initialisation: pass a FUNCTION when the initial value is
// expensive. Passing the value calls the work on every render and
// throws the result away; passing the function calls it once.
const [rows, setRows] = useState(() => parseHugeCsv(raw));   // ✓
const [rows, setRows] = useState(parseHugeCsv(raw));         // ✗ every render
State belongs to a position, not to a variable
React stores it against the component's slot in the tree — Chapter 4's identity rule. Two sibling <Counter /> elements have independent counts because they occupy different positions. Remove one from the tree and its state is gone for good.
Hooks are matched by call order
React keeps an array of state slots per component and walks it in order on every render. That is why hooks cannot be called conditionally: skip one and every subsequent hook reads the wrong slot. It is not a stylistic rule, it is how the storage works.
The setter is stable
setCount is the same function object across renders, so it never needs to be a dependency of anything.
The initial value is only used once
On the first render at that position. Passing a different initial value later does nothing — which is the source of the "why won't my component update when the prop changes" question, answered in section 7.

2State is a snapshot

The idea that makes every "one step behind" bug obvious.

Each render is a separate call to your function, with its own const bindings. Inside that call, count is a fixed number and cannot change — calling a setter does not assign to it, it schedules another call in which a different number will be bound. So every function, every closure and every event handler created during a render sees that render's values, permanently.

Three puzzles with the same answer JSX
// 1. The log prints 0, not 1.
function handleClick() {
  setCount(count + 1);
  console.log(count);          // 0 — `count` is this render's const
}

// 2. This increments by ONE, not three.
setCount(count + 1);          // count is 0 → queue "replace with 1"
setCount(count + 1);          // count is STILL 0 → queue "replace with 1"
setCount(count + 1);          // count is STILL 0 → queue "replace with 1"

// 3. The alert shows the count as it was when you clicked,
//    even though three seconds have passed and it has changed.
function handleClick() {
  setTimeout(() => alert(count), 3000);
}
The mental model that fixes all three

Do not think "the state changed". Think "React will call my function again with a different value". A render is a photograph: the handlers in it captured what was true at the moment it was taken, and no later event can develop the film differently. Case 3 is often described as a stale closure and treated as a bug in effects; it is not a bug at all, it is the model working exactly as designed.

3The update queue

Setters do not set. They enqueue, and React processes the queue before the next render.

Build a queue and watch React process it This runs React's actual algorithm: walk the queue, replace or apply, in order.

Add a call — these are what your handler would run

Two kinds of queue entry
A value — setCount(5) — replaces whatever the pending state was, discarding earlier updates. An updater function — setCount(c => c + 1) — receives the pending state and returns the next one, so it composes with what came before.
Use the updater form when the next value depends on the previous
That is the whole rule. Three setCount(count + 1) calls give you one increment; three setCount(c => c + 1) calls give you three. It also removes the value from any closure, which is what makes an interval or a subscription callback stop going stale.
Updater functions must be pure
Same reason as components, and with more force: React runs them during rendering and, in StrictMode, twice. No side effects, no mutation of the incoming state.
Bail-out
If the resulting value is Object.is-equal to the current state, React may skip the re-render entirely. Which is also why setItems(items) after mutating items does nothing at all — same reference, no change detected.

4Structuring state

Most state bugs are shape bugs. Five principles, in order of how often they matter.

Three designs for the same feature A list with a selection and a filter. Press the button and watch the first two go wrong.

1 · Do not store what you can derive
If fullName is first + ' ' + last, compute it. Two copies of one fact can disagree, and the version in state is the one that will be stale. This includes filtered lists, totals, counts and validity flags.
2 · Do not duplicate objects — store ids
selectedItem holding a copy of an object that also lives in items is the demo above. Store selectedId and look the object up. One source of truth, and deletion cannot leave a ghost behind.
3 · Make contradictions unrepresentable
isLoading plus isError plus isSuccess is eight states of which five are nonsense, and eventually two will be true at once. One status field with a union of literals cannot do that. Chapter 6 goes further.
4 · Group what changes together
If two fields are always updated in the same handler, they are one piece of state. If they never are, they are two. Splitting or grouping against that grain creates either redundant renders or awkward updates.
5 · Flatten deep nesting
Updating state.a.b.c.d immutably means recreating four levels of object. Normalise instead: a map of items by id, and arrays of ids for order. This is what Redux's normalisation advice was always about, and it applies without Redux.

5Updating objects and arrays

You are always producing a new value. Here are the patterns for each shape.

The patterns worth memorising JavaScript
// Object: one field
setUser({ ...user, email: next });

// Object: nested — every level on the path must be copied
setForm({ ...form, address: { ...form.address, city: next } });

// Array: add, remove, replace, insert
setItems([...items, item]);                       // append
setItems(items.filter(i => i.id !== id));          // remove
setItems(items.map(i => i.id === id ? { ...i, done: true } : i));   // replace one
setItems([...items.slice(0, n), item, ...items.slice(n)]);        // insert

// Array: sort and reverse MUTATE. Copy first, or use the new methods.
setItems([...items].sort(by.name));               // or items.toSorted(by.name)

// The four that mutate: push, pop, splice, sort, reverse.
// The safe replacements: concat/spread, slice, filter, map,
// toSorted, toReversed, toSpliced, with.
Why copying is required
React compares by reference. A mutated array is the same array, so the bail-out in section 3 fires and nothing renders. And once memo is involved (Chapter 10), the same identity means children skip too. Mutation is not merely discouraged — it is invisible.
Copies are shallow, and that is fine
{ ...user } shares every nested object with the original. That is correct: only the objects on the path you are changing need to be new. Deep-cloning everything is wasteful and defeats memoisation elsewhere.
Immer, when the nesting is real
useImmer lets you write draft.address.city = next and produces a correct immutable update underneath. Worth it for genuinely deep state; usually a sign you should flatten instead.
Mutating during creation is fine
Building an array in a loop and then passing it to a setter mutates only a local you just created. The rule is about values that already exist in state.

6Where state should live

One rule, and the demo in Chapter 4 already showed why.

The rule
The lowest component that needs it. When two siblings need it, lift it to their nearest common parent — not to the root, and not to a global store. Every level you lift it widens the re-render circle from Chapter 4's demo and makes the component harder to reuse.
Lifting costs something
Moving state up means the parent re-renders on every change, and everything below it re-renders too. That is often fine and occasionally the cause of a slow list — which is why "move state down" is the first fix in Chapter 10, before any memoisation.
Controlled or uncontrolled is the same question
A component that owns its state internally is easier to use; one that takes value and onChange lets the parent coordinate. Good components support both, which is Chapter 3's pattern and Chapter 14's default for form fields.
Not everything needs to be state
Derivable values: compute them. Values that do not affect rendering: a ref (Chapter 8). Server data: a query cache (Chapter 13). Anything shareable by URL: the address bar (Chapter 15). What is left is genuinely local UI state, and it is usually a smaller list than expected.

7Resetting and preserving state

Two questions with one answer, and it is not an effect.

Resetting when a prop changes JSX
// ✗ The effect approach: renders once with stale state, then again.
//   Also runs after paint, so the user briefly sees the old user's draft.
useEffect(() => { setDraft(''); }, [userId]);

// ✓ Change the component's identity. React discards the old instance
//   and mounts a fresh one — all its state, at every depth, gone.
<ProfileEditor key={userId} userId={userId} />

// ✓ Or, for one field, derive it and adjust during render —
//   the rare legitimate "set state while rendering" pattern.
const [prevId, setPrevId] = useState(userId);
if (userId !== prevId) { setPrevId(userId); setDraft(''); }
State survives when position and type are unchanged
Chapter 4's identity rule. Hiding a component with display: none preserves its state; removing it from the tree destroys it. Both are sometimes what you want, and they are easy to confuse.
The shared-slot surprise
{isA ? <Counter /> : <Counter />} — two different-looking counters at the same position with the same type share one piece of state. Toggling keeps the count. Add a distinct key to each and they separate.
Deriving beats resetting
Before reaching for either technique, check whether the value needs to be state at all. A "selected tab" that should reset when the section changes is often just selectedTab ?? defaultForSection.

8Check yourself

Six questions.

1. Why does calling setCount(count + 1) three times increment by one?

Because count is a constant belonging to the render that is executing, and no setter changes it. All three calls read the same number — say 0 — compute 1, and enqueue "replace the pending value with 1". React processes the queue in order and each entry overwrites the last, so the next render gets 1. The fix is the updater form: setCount(c => c + 1) enqueues a function that receives whatever the pending value is, so the three compose to 3. The rule that follows: use the updater whenever the next value depends on the previous one.

2. What is wrong with const [fullName, setFullName] = useState('') alongside first and last name state?

It stores a fact that can be derived, creating two sources of truth that can disagree — and the derived copy is the one that will be stale, because keeping it current requires remembering to update it in every handler that touches either name. It also costs an extra render if you sync it in an effect: the component renders with the old name, the effect runs, state is set, it renders again. Just compute it: const fullName = first + ' ' + last. It cannot be wrong, needs no dependency array and does no extra work. The same argument applies to filtered lists, totals and validity flags.

3. items.push(newItem); setItems(items); renders nothing. Explain both halves of why.

The push mutated the array that state already points at, so the setter received the same reference it already held. React compares with Object.is, concludes nothing changed, and bails out of the render entirely. Two separate problems are hiding in that: the data is now different from what React last rendered, and React has no way to know. Even if it did render, memoised children comparing props by reference would still skip. Produce a new array — setItems([...items, newItem]) — and both problems disappear. The four array methods to watch are push, splice, sort and reverse.

4. A component stores selectedItem as a copy of an object from a list. What goes wrong?

The copy and the list drift apart. Edit the item in the list and the selection still shows the old values; delete it and the selection is a ghost pointing at something that no longer exists, so the detail panel renders stale data or crashes on the next update. It is the duplication principle: the same fact stored twice will eventually disagree. Store selectedId and look the object up during render — items.find(i => i.id === selectedId). There is then exactly one copy of every item, the selection automatically reflects edits, and a deleted item yields undefined, which you can handle explicitly.

5. Why is key={userId} better than an effect for resetting a form?

Because it expresses the actual intent — "this is a different editor now" — and lets React do the work. Changing the key makes React unmount the old instance and mount a fresh one, so all state at every depth is reset in one step, before anything is painted. The effect version resets one field, renders once with the previous user's draft still visible, runs after paint, then renders again — so there is a real frame where the wrong data is on screen, and every additional piece of state needs another line. The key approach also cannot fall out of sync, because there is no list of things to remember to reset.

6. Why can hooks not be called conditionally?

Because React stores hook state in an ordered list per component and walks it positionally on every render — the first useState call gets slot 0, the second gets slot 1, and so on. Nothing about the call identifies which state it wants; only its position does. Skip a hook on one render and every subsequent hook shifts by one, reading another hook's value: your useState returns the array from a useMemo, an effect gets the wrong dependencies, and the failure is silent and bizarre. An early return is fine as long as every hook runs before it. eslint-plugin-react-hooks enforces this and is worth treating as an error, not a warning.
