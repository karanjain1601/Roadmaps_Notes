CHAPTER 16

Styling and component libraries

CSS is global and components are not, and every styling approach for React is an answer to that mismatch. The answers differ less in what they can express than in when they run — which turned out to matter far more than anyone expected once rendering moved to the server.

Part 4 Building an application·Reading time 40 minutes·Demos approach comparator, variant builder·Prerequisites CSS fundamentals

1The mismatch

Three problems, and every approach in section 2 solves the first two.

Scope
A CSS class name is global. Two components each defining .card collide, and the winner depends on stylesheet order — which depends on import order, which nobody is thinking about.
Dead code
Deleting a component does not delete its CSS. Over a few years a stylesheet accumulates rules nobody dares remove because nothing can prove they are unused.
Dynamic values
A progress bar's width comes from a prop. CSS has no way to receive that, so it must be an inline style or a custom property — and how gracefully each approach handles that is a real differentiator.

Note what is not on the list: the cascade, specificity and the box model do not change because you are using React. Everything in Part 3 of the Front-end unit still applies underneath whichever of these you choose.

3The runtime question

      
Why the styling conversation changed, and it was not fashion.


      
Runtime CSS-in-JS — styled-components, Emotion — generates class names and injects stylesheets while your components render. That buys genuinely dynamic styling from props with no ceremony. It costs three things that became decisive.


      

        

          
CostDetail

          
            
Per-render workSerialising styles, hashing, checking the cache and possibly inserting a rule, on every render of every styled component. Small individually; measurable on a large tree, and it lands on the main thread during interaction.

            
BundleThe runtime ships to every user, plus the style definitions themselves as JavaScript rather than CSS — so they cannot be cached separately or loaded in parallel with the bundle.

            
Server componentsThe decisive one. A server component does not run in the browser and has no React context, so a library that needs a runtime theme provider and client-side injection cannot be used in one at all. Chapter 19.

          
        

        
Hence the move to zero-runtime alternatives — Panda CSS, vanilla-extract, StyleX, Linaria — which keep the authoring experience of writing styles in TypeScript and extract real CSS files at build time. And hence Tailwind's rise, which was always build-time. None of this makes existing Emotion codebases wrong; it does mean starting a new project with a runtime library needs a reason.

      

    


    
    

      
4Tokens and theming

      
Custom properties are the substrate every approach shares.


      

        
Three tiers, and theming for free CSS

        
/* 1. Primitives — raw values, no meaning */
:root {
  --blue-600: oklch(0.55 0.14 240);
  --grey-100: oklch(0.97 0.005 250);
  --space-3: 12px;

  /* 2. Semantic — what it is FOR. Components only use these. */
  --surface: white;
  --text-primary: var(--grey-900);
  --action-bg: var(--blue-600);
}

/* 3. A theme reassigns tier 2 only. No component changes. */
[data-theme="dark"] {
  --surface: var(--grey-900);
  --text-primary: var(--grey-100);
}

/* Or let the browser pick, with no JavaScript at all: */
:root { color-scheme: light dark; --surface: light-dark(white, #101820); }

      


      

        
Theme through CSS, not React state

        
Putting the theme in context means every consumer re-renders on a theme change and none of it works in a server component. Setting data-theme on <html> costs one attribute write and no re-render at all. Keep the preference in React if you need a toggle; keep the values in CSS.

        
The flash of the wrong theme

        
If the theme is read from storage after hydration, the user sees light mode for a frame. The fix is a tiny inline script in the document head that sets the attribute before first paint — one of the few legitimate blocking inline scripts.

        
Custom properties cross every boundary

        
They inherit, so they reach into shadow DOM, into third-party components, and into any styling approach at once. That makes them the one theming mechanism that works regardless of what each part of your application chose.

The three tools JSX

        
// clsx / classnames — conditional joining
clsx('btn', isActive && 'btn-active', { 'btn-disabled': disabled })

// cva — a declared variant API with types and defaults
const button = cva('inline-flex items-center rounded font-medium', {
  variants: {
    size: { sm: 'h-8 px-3 text-sm', md: 'h-10 px-4', lg: 'h-12 px-6 text-lg' },
    tone: { solid: 'bg-blue-600 text-white', outline: 'border border-blue-600 text-blue-700' }
  },
  compoundVariants: [{ size: 'lg', tone: 'outline', class: 'border-2' }],
  defaultVariants: { size: 'md', tone: 'solid' }
});

// tailwind-merge — later utilities of the same kind win, so a caller's
// className can actually override the component's. Without it,
// "px-4 px-8" leaves the CSS to decide by source order, not by intent.
<button className={twMerge(button({ size, tone }), className)} />

      

    


    
    

      
6Three kinds of component library

      
They solve different problems and get compared as though they were interchangeable.


      

        

          
KindExamplesGives you / costs you

          
            

              Full kit
              MUI, Mantine, Chakra, Ant Design
              Everything styled and working on day one. You inherit their design language, their theming system and their bundle, and fighting the design becomes the main activity once your brand diverges.
            

            

              Headless primitives
              Radix UI, React Aria, Ark UI, Base UI, Headless UI
              Behaviour, accessibility and state with no styling at all. You write every pixel, which is the point when you have a design system — and is a lot of work when you do not.
            

            

              Copy-in
              shadcn/ui and the pattern it popularised
              Source files copied into your repository, built on headless primitives and Tailwind. Not a dependency: you own and edit them. The trade is that you also maintain them — upstream fixes do not arrive by themselves.
            

          
        

        
A reasonable default for a product with its own design: headless primitives plus your own styling, whether written directly or adopted via the copy-in pattern. A full kit is a good choice for internal tools, prototypes and admin interfaces, where the design language not being yours is a feature rather than a problem.

      

    


    
    

      
7What headless primitives actually do

      
The reason "we'll just build our own select" is a bigger commitment than it looks.


      

        
Keyboard interaction to the specification

        
A listbox needs Up, Down, Home, End, Escape, Enter, Space, type-ahead matching, and wrapping behaviour that matches what screen-reader users expect. A menu adds arrow-key traversal into submenus. Each is written down in the ARIA Authoring Practices and none of it is guessable.

        
Focus management

        
Trapping focus in a dialog, restoring it to the trigger on close, roving tabindex in a toolbar, and the difference between focus and virtual focus in a combobox.

        
Correct ARIA, wired up

        
The relationships between trigger, popup and active option, maintained as state changes — which is where hand-rolled versions drift.

        
Positioning that survives reality

        
Collision detection, flipping, scroll containers, and the fact that a dropdown near the bottom of a viewport must open upwards.

        
The parts nobody thinks of

        
Touch and pointer differences, right-to-left layouts, forced-colours mode, prefers-reduced-motion, portal rendering that keeps React context, and behaving correctly inside a form.

        
The honest recommendation

        
Build a simple disclosure or tabs yourself; it is a good exercise. Do not build a combobox, a date picker or a modal from scratch for production. Use a primitive and spend the time on the parts that are specific to your product.

      

    


    
    

      
8Practical guidance

      
Five habits that keep a styled codebase workable regardless of which approach you picked.


      

        
Forward className and the rest of the props

        
Chapter 3's rule, applied to styling. A component that cannot be given a margin by its parent forces a wrapper div at every call site. Merge it properly — twMerge or equivalent — so the caller's value can genuinely win.

        
Spacing belongs to the layout, not the component

        
A Card with margin-bottom baked in is wrong in the next context. Let the parent's gap or a layout component own the space between things.

        
Semantic tokens in components, primitives only in the token file

        
A component referring to --blue-600 rather than --action-bg cannot be themed, and the day the brand colour changes you are editing a hundred files.

        
One approach per codebase

        
Two styling systems means two sets of tokens, two mental models and an unresolvable question about specificity order. Migrating is fine; running both indefinitely is not.

        
Pick for the constraints, not the discourse

        
Server components in the plan means build-time CSS. A team that already knows Tailwind and ships quickly should keep doing that. A design system consumed outside React points at CSS Modules or plain CSS with custom properties. The style debate generates far more heat than the decision warrants.

      

    


    
    

      
9Check yourself

      
Five questions.


      

        
1. Why did runtime CSS-in-JS fall out of favour for new projects?

        
        

          
Three reasons, of which the third is decisive. It does work on every render — serialising, hashing, cache lookup, sometimes a stylesheet insertion — which is small per component and measurable across a large tree, on the main thread, during interaction. It ships a runtime and turns your styles into JavaScript, so they cannot be cached or downloaded as CSS. And it is fundamentally incompatible with server components, which do not run in the browser and have no access to a client-side theme provider or injection mechanism. Zero-runtime tools such as Panda, vanilla-extract and StyleX keep the authoring experience and extract real CSS at build time, which is why they exist.

        

      


      

        
2. Why theme with CSS custom properties rather than React context?

        
        

          
Because a theme change through context re-renders every consumer, and there may be hundreds — Chapter 7's no-selector problem at its worst, since the theme is exactly the kind of value everything reads. Setting data-theme on the root element instead is one attribute write, no re-render at all, and the browser recalculates styles far faster than React can re-render a tree. Custom properties also inherit across every boundary, including shadow DOM and third-party components, so they theme parts of the page React does not own. And they work in server components, which context does not. Keep the user's preference in React if you need a toggle; keep the values in CSS.

        

      


      

        
3. What problem does tailwind-merge solve that clsx does not?

        
        

          
Conflicts. clsx joins class names conditionally, so clsx('px-4', className) with className="px-8" produces the string "px-4 px-8" — both classes are applied, and which wins is decided by their order in the compiled stylesheet, not by the caller's intent. Since Tailwind's utilities all have the same specificity, that ordering is essentially arbitrary from the component's point of view. tailwind-merge understands which utilities belong to the same property group and drops the earlier one, so a later px-8 genuinely overrides an earlier px-4. That is what makes "forward className so callers can adjust" actually work.

        

      


      

        
4. When is a full component kit the right choice?

        
        

          
When their design language being yours is acceptable or desirable: internal tools, admin interfaces, prototypes, back-office applications, anything where shipping quickly matters more than a distinctive appearance. You get a coherent, accessible, documented set of components immediately and no design work. It becomes the wrong choice when a real brand exists, because you end up overriding their styles at every turn — fighting a theming system designed for a different visual language, and inheriting a bundle you use a third of. At that point headless primitives plus your own styling costs less in total, and the copy-in pattern is a reasonable middle ground.

        

      


      

        
5. Why not build your own combobox?

        
        

          
Because the visible part is a small fraction of it. A correct combobox needs the full keyboard specification — arrows, Home, End, Escape, Enter, type-ahead, wrapping — plus virtual focus so the input keeps real focus while the active option changes, the ARIA relationships between input, listbox and option maintained through every state change, positioning with collision detection and flipping, correct behaviour inside a form, touch and pointer differences, right-to-left support, forced-colours mode, and reduced-motion handling. Each of those is a documented specification, and the failures are silent for anyone testing with a mouse. Build a disclosure or tabs yourself as an exercise; use a primitive for the hard ones and spend the time on what is specific to your product.
