CHAPTER 09

Effects, and when not to use one

More React bugs come from unnecessary effects than from any other single cause. An effect is an escape hatch for synchronising with something outside React — and most of the time people reach for one, the answer is that no effect is needed at all.

Part 2 State·Reading time 45 minutes·Demos effect advisor, a real race condition·Prerequisites Chapters 4–5, 8

1What an effect is for

One sentence, and the word that matters is "external".

An effect synchronises your component with a system outside React. A subscription, a timer, a browser API, a non-React widget, an analytics endpoint, a websocket. If the code is not talking to something outside React, it almost certainly belongs in render or in an event handler instead.

Caused by a specific user actionHappens because the component is on screen
An event handler. Buying something, submitting a form, sending a message, tracking a click. You know exactly when it happened, so say so. An effect. Connecting to a chat room because the room is displayed, observing an element's size, subscribing to a store.

That single test resolves most cases. "Should submitting the form send the request in an effect watching submitted?" — no: a user pressed a button, so it goes in the handler that runs when they press it.

2Anatomy

Setup, cleanup, dependencies. Three parts, three behaviours.

The shape and the three dependency forms JSX
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);   // setup
  connection.connect();
  return () => connection.disconnect();                    // cleanup
}, [serverUrl, roomId]);                                    // dependencies

// No array      → after every render.        Almost always a mistake.
// []            → setup once, cleanup on unmount.
// [a, b]        → cleanup + setup whenever a or b changes.
Effects run after paint
Chapter 4's commit order: DOM updated, refs attached, browser paints, then effects. So an effect never blocks the user seeing the update.
Cleanup runs before the next setup, and on unmount
Not only on unmount. If a dependency changes, React tears down the old effect before starting the new one, which is what keeps the subscription pointing at the right room.
The cleanup is not optional
Any effect that starts something must have a way to stop it. StrictMode's double mount (Chapter 4) exists precisely to make a missing cleanup fail on the first render rather than as a slow leak in production.

3Stop thinking in mount and unmount

The single most useful reframing in this chapter.

An effect is not a lifecycle event

Do not read useEffect(..., []) as "on mount". Read every effect as "start synchronising" and its cleanup as "stop synchronising". React may start and stop the synchronisation any number of times — on mount, when a dependency changes, in StrictMode, when a component is hidden and restored, and in future when offscreen rendering lands. An effect written to be started and stopped repeatedly is correct in all of those; one written as "do this once when I appear" is broken in most of them and will look fine in development for months.

Mount/unmount thinkingSynchronisation thinking
"Connect on mount""While this room is displayed, be connected to it" — so a room change disconnects and reconnects, automatically
"Fetch on mount""The displayed data should match this id" — so an id change refetches and the old response is discarded
"Add the listener on mount""While mounted, listen" — and the cleanup removes it, so remounting cannot double up
"Run this only once, ever"Usually not an effect at all. Module scope, or a handler, or a ref guard if it truly must be once per session

4The dependency array

Not a configuration option. A statement of fact that the linter checks.

Every reactive value used inside must be listed
Props, state, and anything derived from them — including functions and objects declared in the component body. Values that cannot change are not reactive: module-scope constants, refs (the object), setters, and dispatch.
You cannot "choose" dependencies
The array is determined by the effect's code. If the linter wants something you do not want to re-run for, the fix is to change the code so it no longer needs that value — not to lie. Suppressing the rule produces stale closures, and it is the most reliable way to create a bug that appears once a week and cannot be reproduced.
Four ways to legitimately remove a dependency
Move the value outside the component if it never changes. Move it inside the effect if it is only used there. Use the updater form — setX(x => …) removes x entirely (Chapter 5). Or wrap the handler in the latest-ref pattern from Chapter 8 for a callback that must be stable.
Objects and functions are the usual culprits
Declared in the component body, they are new on every render, so the effect re-runs every render — often causing an infinite loop when the effect sets state. Move them into the effect, hoist them out of the component, or memoise them.
An empty array is a claim
It says "this effect uses nothing reactive". If it does, the effect is wrong, not the array.

5You might not need an effect

Five patterns that account for most of the effects in a typical codebase, and none of them need one.

Do I need an effect? Pick what you are trying to do. The verdict comes with the replacement.

6Cleanup and race conditions

The one case where a hand-written fetching effect is defensible — and it still needs this.

A search box with slow, out-of-order responses Real timers with real jitter. Type quickly and watch which response wins.

Requests in flight

Requests sent—
Responses applied—
Wrong result shown—
Network wasted—

The two correct shapes JSX
// The ignore flag — works everywhere, does not cancel the request
useEffect(() => {
  let ignore = false;
  search(query).then(r => { if (!ignore) setResults(r); });
  return () => { ignore = true; };
}, [query]);

// AbortController — also stops the request, so the network is freed
useEffect(() => {
  const ac = new AbortController();
  fetch('/search?q=' + query, { signal: ac.signal })
    .then(r => r.json())
    .then(setResults)
    .catch(e => { if (e.name !== 'AbortError') setError(e); });
  return () => ac.abort();
}, [query]);

// Both work because cleanup runs BEFORE the next setup, so the
// superseded attempt is disarmed the instant a new one begins.
Everything you start, you stop
Subscription → unsubscribe. Interval → clear. Listener → remove. Observer → disconnect. Animation → cancel. Request → abort or ignore. Library instance → destroy.
One AbortController can do most of it
Its signal works with fetch, with addEventListener's signal option, and with anything you write yourself — so a single ac.abort() in the cleanup can tear down several things at once and cannot be partially forgotten.
This is why StrictMode double-mounts
An effect that is correct under a start-stop-start cycle is correct everywhere. If StrictMode breaks it, so will a fast navigation.

7Effects that are genuinely right

After all the warnings, the legitimate list.

Subscribing to an external store
And the better tool is useSyncExternalStore, which is designed for it: it avoids tearing under concurrent rendering, handles server rendering, and needs no dependency array. Use it whenever you are subscribing to something outside React — a store, matchMedia, navigator.onLine, the URL.
Browser APIs and observers
IntersectionObserver, ResizeObserver, MutationObserver, media queries, keyboard shortcuts registered on document. All start-and-stop by nature.
Non-React widgets
Chapter 8's boundary: create in the effect, keep in a ref, destroy in the cleanup, sync props in a second effect.
Connections
Websockets, server-sent events, WebRTC. The canonical example, and the one the "start syncing" framing was written for.
Sending analytics for a view
A page view is caused by the component being displayed, not by a click, so it is an effect. Make it idempotent so the double mount does not double-count.
Imperative DOM work React does not do
Setting document.title, managing focus after navigation, scrolling to a node. Small, and legitimately outside the render output.

8The other two effect hooks

Rarely needed, and worth recognising when you meet them.

HookRunsUse for
useEffectAfter paintEverything, by default.
useLayoutEffectAfter DOM mutation, before paintMeasuring and adjusting position in the same frame — tooltip placement, scroll restoration. Blocks painting, so keep it small. Does not run during server rendering, which produces a warning if you use it in a component that is server-rendered.
useInsertionEffectBefore any DOM mutationInjecting stylesheets. For CSS-in-JS library authors; you will almost certainly never write one.

Default to useEffect and switch to the layout variant only when a visible flicker proves you need it.

9Check yourself

Six questions, closing Part 2.

1. What is the test for whether something belongs in an effect or a handler?

Ask what caused it. If a specific user action caused it — a click, a submit, a drag — it belongs in the handler for that action, because you already know precisely when it happened and can do it there directly. If it happens because the component is displayed — a connection that should exist while a room is on screen, an observer watching an element that exists — it is an effect. The common failure is setting a piece of state in a handler and then watching that state with an effect to do the real work; that adds a render, splits one operation across two places, and makes the ordering harder to follow.

2. Why is "run this once on mount" a misleading way to read useEffect(fn, [])?

Because React does not promise it runs once. StrictMode deliberately mounts, unmounts and remounts in development; a component can be unmounted and remounted by navigation, by a changing key, or by a parent's conditional; and offscreen rendering will make this more common. The reliable reading is "start synchronising" with the cleanup as "stop synchronising" — an effect written that way is correct however many times the cycle runs. Genuinely once-per-session work does not belong in an effect at all: put it at module scope, in an event handler, or behind a ref guard if it truly must be once.

3. The linter wants a dependency you do not want the effect to re-run for. What do you do?

Change the code, never the array. The array is not a configuration option — it is a claim about what the effect reads, and lying produces stale closures that fire intermittently and cannot be reproduced. Four legitimate removals: move the value outside the component if it never changes; move it inside the effect if that is the only place it is used; use the updater form, since setCount(c => c + 1) does not read count at all; or wrap a callback in the latest-ref pattern from Chapter 8 so it is stable but never stale. If the value is an object or function created during render, that is usually the real problem — hoist it or memoise it.

4. An effect sets state, which changes a dependency, which re-runs the effect. How does that happen?

Almost always because a dependency is an object, array or function created during render, so it is a new reference every time — the effect runs, sets state, triggers a render, the dependency is recreated, and the comparison fails again. The other version is an effect that sets a piece of state it also depends on. Both are usually symptoms of deriving state in an effect, which section 5 says to compute during render instead. Concrete fixes: move the object or function inside the effect, hoist it out of the component, memoise it, or use the updater form so the effect no longer reads the state it writes.

5. Two search requests return out of order and the older one wins. What fixes it?

Cleanup, because React runs the cleanup of the previous effect before the setup of the next one — so the superseded attempt is disarmed the moment a newer one starts. Either set a local ignore flag in the cleanup and check it before calling the setter, which works with any promise, or use an AbortController and call abort(), which also stops the request and frees the network. Both are shown in the demo. Note that the ignore flag prevents the wrong render but still pays for the response; the abort does both. And note that a query library does all of this by default, which is Chapter 13's argument for not hand-writing this at all.

6. When is useLayoutEffect the right choice?

When you must measure the DOM and change it again before the user sees the intermediate state. Positioning a tooltip that would otherwise appear in the wrong place for one frame, restoring a scroll position, or measuring for an animation that starts immediately. It runs after the DOM is updated and before paint, so it eliminates the flicker — and it blocks paint, so anything slow in it delays the frame for every user. Default to useEffect and switch only when a visible flicker proves the need. It also does not run during server rendering, so a component using it will warn if it is server-rendered.
