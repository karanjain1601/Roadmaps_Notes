CHAPTER 14

Forms

Forms are where React's model and the platform's model collide most directly. The browser already knows how to collect, validate, label and submit a form; React wants to own every value. The good approaches take as much of the platform as they can and add only what is missing.

Part 4 Building an application·Reading time 40 minutes·Demos render cost, accessible errors·Prerequisites Chapters 5, 12

1Start with the platform

A real <form> with real inputs gives you a great deal before you write anything.

What you get free
Enter submits. Password managers and autofill work. The correct mobile keyboard appears for type="email" and inputmode="numeric". required, min, maxlength and pattern validate before you write a line. Labels are announced, focus moves properly, and the whole thing works if your JavaScript fails to load.
What you lose by rebuilding it
A "form" of divs with an onClick handler loses every item above. This is the single most consequential decision in the chapter and it is usually made by accident, by a designer's component that happens to render a div.
Always a real <label>
Associated by htmlFor or by wrapping. A placeholder is not a label: it disappears on focus, fails contrast, and is not reliably announced. Chapter 6 of the Front-end unit covers why in detail.
Use native validation as a first pass, not the only one
It is free, instant and accessible. It is also stylable only within limits and its messages are not translatable by you — so most applications turn off the browser bubble with noValidate and reimplement the messages, while keeping the semantic attributes for assistive technology and autofill.
And validate on the server regardless
Everything on the client is a usability feature. Chapter 27 of the Front-end unit; nothing about React changes it.

3FormData and actions

The uncontrolled path, and how React 19 made it first-class.

Three levels of the same thing JSX
// 1. Plain: read everything on submit. No state at all.
function onSubmit(e) {
  e.preventDefault();
  const data = Object.fromEntries(new FormData(e.currentTarget));
  save(data);
}

// 2. React 19 action: the form calls it with the FormData directly,
//    resets on success, and works before hydration.
<form action={async (formData) => { await save(formData); }}>

// 3. With state and pending, without four useStates (Chapter 12)
const [state, formAction, isPending] = useActionState(async (prev, formData) => {
  const parsed = schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { errors: parsed.error.flatten().fieldErrors };
  await save(parsed.data);
  return { ok: true };
}, {});
FormData gotchas worth knowing
A field only appears if it has a name. A disabled field is omitted entirely — which is how a disabled submit button silently drops a value. An unchecked checkbox is absent rather than false. Multiple values with the same name need getAll. And everything is a string, so numbers and booleans need coercing, which section 5's schema does for you.
Which button submitted
e.nativeEvent.submitter, or give each button a name and value so it appears in the FormData. Save-versus-publish forms need this.
Actions degrade
A <form action> pointing at a server function posts natively if JavaScript has not loaded yet. That is a genuine progressive-enhancement win and the reason the API is shaped this way. Chapter 19.

4Form libraries

What React Hook Form is actually doing, which explains when you need it.

Register, not control React Hook Form
const { register, handleSubmit, formState: { errors, isSubmitting } } =
  useForm({ resolver: zodResolver(schema) });

<form onSubmit={handleSubmit(save)} noValidate>
  <label htmlFor="email">Email</label>
  <input id="email" {...register('email')}
         aria-invalid={!!errors.email}
         aria-describedby={errors.email ? 'email-error' : undefined} />
  {errors.email && <p id="email-error">{errors.email.message}</p>}
</form>

// register() attaches a ref and native listeners. The inputs stay
// uncontrolled, so typing causes NO React render — the library
// re-renders only the parts subscribed to what changed, which is why
// a fifty-field form stays smooth.
When a library earns its place
More than about six fields; validation with real rules; dependent fields; arrays and repeaters; multi-step flows; anything where "is it dirty" matters. Below that, plain FormData plus a schema is less code than the library's setup.
The alternatives
TanStack Form — newer, framework-agnostic, strong typing. Formik — was the default, largely controlled, and slower on big forms. Conform — built around the platform and server actions, worth a look if you are on a framework.
Controlled components inside an uncontrolled form
A custom select or date picker does not expose a DOM value, so it needs the library's Controller wrapper — a controlled island inside an otherwise uncontrolled form. Perfectly normal; just know that those fields do re-render.

5Validation

Define the rules once, in a form both the client and the server can execute.

One schema, three jobs Zod
export const profileSchema = z.object({
  email: z.string().email('Enter a valid email address'),
  age: z.coerce.number().int().min(16, 'You must be 16 or over'),
  password: z.string().min(12, 'Use at least 12 characters'),
  confirm: z.string()
}).refine(d => d.password === d.confirm, {
  message: 'Passwords do not match', path: ['confirm']     // cross-field
});

export type Profile = z.infer<typeof profileSchema>;

// 1. Client validation   → zodResolver(profileSchema)
// 2. Server validation   → profileSchema.parse(body)
// 3. The TypeScript type → inferred, so it cannot drift from the rules
//
// z.coerce handles FormData's everything-is-a-string problem.
When to validateWhy
On submit — the defaultNobody wants to be told their email is invalid after typing two characters.
On blur, after the first submit attemptThe best compromise: quiet until the user has finished a field, then responsive while they fix things.
On change, only after that field has erroredClear the error as soon as it is fixed. Validating every keystroke from the start is hostile.
Async — is this username takenDebounce it, show a pending state on that field, and re-check on the server at submit; the answer can change between the two.

6Errors people can actually use

Four techniques. Leaving any of them out breaks the form for someone.

The same failed submission, with pieces switched off A real form. The panel shows what a screen reader would have to work with.

The four, and what each is for
Label association so the field has a name at all. aria-describedby pointing at the error, so it is announced when the field is focused rather than only being visible. aria-invalid so the state is programmatic, not just a red border. An error summary at the top, focused on submit, listing every failure with links to the fields — the only thing that tells a keyboard or screen-reader user that the submit did not work and there are four problems, not one.
Never colour alone
A red border says nothing to a screen reader and little to a colour-blind user. Text plus an icon plus the ARIA state.
Say what to do
"Invalid input" is not a message. "Use at least 12 characters" is. Put the requirement in the message, and put it near the field before they type where you can.
Keep what they typed
A server error that clears the form is the worst outcome in this chapter. Return the submitted values along with the errors and re-render them.

7The genuinely hard parts

Six things that turn a simple form into a project.

ProblemApproach
Dependent fieldsCountry changes the address format and the postcode rule. Derive whatever you can rather than storing it, and keep the rules in the schema with a discriminated union on the country.
Arrays and repeatersuseFieldArray or equivalent. Each row needs a stable key from the data, not the index — Chapter 2's rule, and removing a row is exactly the case that breaks.
Multi-stepKeep one state object for the whole flow, validate per step, and put the step in the URL so back works and a refresh does not lose everything. Chapter 15.
File uploadsNot JSON. Use FormData, show real progress via XHR or a resumable protocol, validate type and size on the client for feedback and on the server for truth.
Unsaved changesA dirty flag plus beforeunload for a tab close, plus a router-level block for in-app navigation. The two are separate mechanisms and forgetting the second is common.
AutosaveDebounce, show the save state honestly, handle failure without losing the buffer, and decide what happens when two tabs edit the same record.

8Submission

The last hundred milliseconds, where most of the remaining bugs are.

Disable the submit while in flight
Or a double-click creates two orders. useFormStatus gives a nested button the pending state without prop drilling (Chapter 12).
Idempotency for anything that creates
Generate a key on the client, send it, and let the server deduplicate. A disabled button does not survive a retry or a flaky connection.
Announce the outcome
Success and failure both need a live region, and failure needs focus moved to the summary. A toast that appears and fades is invisible to a screen reader unless it is in a live region.
Do not clear on failure
Repeated from section 6 because it is worth repeating.
Optimistic only where it is safe
useOptimistic is excellent for adding a comment. It is wrong for a payment.

9Check yourself

Five questions.

1. What exactly does a controlled input cost?

A render of whatever component owns the state, on every keystroke — and therefore of everything below it that is not memoised. On a small form that is unmeasurable. On a form with forty fields, or where the state lives high enough that a large subtree re-renders, it is the difference between typing that feels immediate and typing that lags, especially on a slower device. The demo makes the ratio visible: the uncontrolled column does not render at all while you type. What you buy for the cost is genuine: live formatting, dependent fields, instant validation, and the value being available anywhere in the tree.

2. Why is a form of divs and an onClick handler a serious mistake?

Because it discards a large amount of behaviour the browser was providing. Enter no longer submits. Password managers and autofill stop recognising the form. Mobile keyboards no longer adapt to the field type. Native constraint attributes stop working, so validation must be entirely hand-built. Screen readers lose the form semantics and the label associations that come with real controls. And the whole thing stops working if the JavaScript fails. None of this is visible in the design review, which is why it usually arrives through a component library that renders a div, and it is expensive to retrofit once every field is built on it.

3. Why does React Hook Form stay fast on a large form?

Because it keeps the inputs uncontrolled. register() attaches a ref and native listeners, so the value lives in the DOM and typing causes no React render at all — the library holds the values outside React state and re-renders only the specific subscribers of whatever changed, such as the one error message that appeared. A controlled form re-renders its owner on every keystroke by construction. The trade is that fields without a DOM value — a custom select, a rich date picker — need the Controller wrapper and become controlled islands, which is fine as long as you know which fields those are.

4. Why define validation as a schema rather than as functions on each field?

Because the same rules are needed in at least three places and any duplication will drift. One schema drives client validation, server validation, and — with something like Zod — the TypeScript type, inferred rather than hand-written so it cannot disagree with the rules. It also handles the practical problems in one place: coercing FormData's strings to numbers and booleans, expressing cross-field rules such as password confirmation, and producing a structured error object you can map straight onto fields. Hand-written per-field validators give you two copies of the rules, one of which will be more lenient, and the lenient one is usually the server.

5. A submission fails with four field errors. What must happen beyond showing red borders?

Four things. The errors need to be text, since colour alone is unavailable to screen-reader and colour-blind users. Each message needs aria-describedby from its field, so it is announced when that field is focused, and aria-invalid so the state is programmatic. There must be a summary at the top listing every failure with links to the fields, and focus must move to it on submit — otherwise a keyboard user presses submit, nothing appears to happen, and there is no indication that four problems exist further down. And the values the user typed must be preserved. The demo turns each of these off in turn and shows what is left to work with.
