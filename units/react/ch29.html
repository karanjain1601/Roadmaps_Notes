CHAPTER 29

Deploy, monitor and beyond the browser

Shipping is not the end of the work — it is the point at which you stop being able to see what is happening unless you built the instruments first. This chapter covers getting code out safely, finding out what it did, and where these skills apply outside a browser tab.

1Where it runs

Four options, and the choice follows almost entirely from Chapter 21's rendering strategy.

A common and sensible split is the marketing site on the cheapest static option and the application on a platform, deployed independently. Two things with different requirements and different release cadences do not have to share infrastructure.

2The pipeline

Build once, promote the same artefact, make it atomic and reversible.

Build once, deploy many
Rebuilding per environment means staging tested a different artefact from the one production runs. Build the bundle once, and promote that exact output through staging to production. This conflicts with build-time environment inlining, which is why section 4 exists.
Preview deploys
Every pull request gets a full, working URL. It changes review from reading a diff to using the feature, and it is the single highest-value piece of front-end deployment tooling. Protect them from indexing (Chapter 7) and never point them at production data.
Atomic
A deploy must flip from entirely old to entirely new. A rolling file copy leaves a window where the new HTML is live and half its assets are missing — and that window is where a real user lands.
Two caching rules, and only two
Content-hashed assets get Cache-Control: public, max-age=31536000, immutable. HTML documents get no-cache, meaning revalidate every time. Chapter 2 explains the mechanism; getting this pair wrong causes both the never-updates bug and the never-caches bug.
Keep the previous build's assets
Do not delete old hashed files on deploy. A user with a tab open still holds the old HTML and will request the old chunks. Retain a few deploys' worth — it costs pennies and prevents the failure in the demo below.
Rollback is a button, not a revert
Re-pointing to the previous artefact takes seconds. Reverting a commit, rebuilding and redeploying takes ten minutes, during which the incident continues. Know which one your setup gives you before you need it.
The stale chunk failure A user has a tab open. You deploy. Walk through what happens.

3Release strategies

Deploying and releasing are different actions, and separating them is most of the value.

Feature flags separate deploy from release
Merge to main continuously behind a flag that is off, then turn it on for staff, then 1%, then everyone — and turn it off instantly if something is wrong, with no deploy at all. This is what makes trunk-based development (Chapter 24) practical, and it converts most rollbacks into a toggle.
Flags are debt with an expiry date
Every flag doubles the paths through that code, and a codebase with forty stale flags is untestable. Record an owner and a removal date when you create one, and delete it the week the rollout finishes.
Canary on real signal
A small share of traffic on the new version with automated comparison of error rate and Core Web Vitals against the old, and automatic rollback on regression. The value is that detection is a machine's job rather than someone noticing.
Watch after deploying
Ten minutes on the error dashboard beats any amount of pre-release confidence. Most of the value of monitoring is realised in the first quarter of an hour after a change.

4Configuration

The awkward corner where "build once" meets "the front end has no runtime environment".

A server reads process.env at start-up, so one artefact serves every environment. A browser bundle has no environment — Chapter 23's variables are textually inlined at build time — so the naïve approach forces a rebuild per environment and breaks build-once.

ApproachNotes
Same URLs everywhereServe the API from a relative path such as /api and let each environment's routing point it at the right back end. No configuration in the bundle at all, which is the cleanest answer when it is available.
A config endpointThe application fetches /config.json on start-up. Fully runtime, at the cost of one blocking request before anything can happen.
Injected into the HTMLThe server writes window.__CONFIG__ into the document it renders. Runtime, no extra request, and it works with static hosting if the CDN supports edge injection.
Build-time inliningFine for values that genuinely never differ — a public analytics id, the build number. Not for anything environment-specific if you want one artefact.

Whichever you pick: no secrets. Everything in the bundle, in a config endpoint, or in the HTML is public. Chapter 27.

5Knowing what happened

Four signals. Without them, your evidence is whatever a user chose to tell support.

Error tracking
Sentry, Rollbar, Bugsnag or equivalent. Three things make it useful rather than noise: upload source maps as part of the build, or every stack trace is minified nonsense; tag each event with release, route and user segment so you can attribute a spike to a deploy; and filter aggressively — browser extensions, third-party scripts and cancelled requests generate enormous volumes of errors you cannot fix and must not drown in.
Real user monitoring
Chapter 26's field metrics, segmented by route and device. Alert on p75 regressions rather than on averages.
Logs and traces
For anything server-rendered, propagate a request id from the browser through to the back end so one user's slow page can be followed end to end. OpenTelemetry is the vendor-neutral way to do it.
Session replay
Extremely effective for reproducing "it just breaks", and a serious privacy responsibility: mask inputs by default, exclude payment and authentication screens entirely, sample rather than record everyone, and be certain your legal basis is real.
Alert on symptoms, not causes
"Checkout conversion dropped 30%" is worth waking someone for. "CPU is at 71%" is not. Alert on what users experience, then use the other signals to find out why. Every alert that fires without requiring action trains people to ignore the next one — the same dynamic as Chapter 25's flaky tests.
What the browser gives you free
window.onerror and unhandledrejection for anything the tracker misses, PerformanceObserver for timings, and Reporting API endpoints for CSP violations, deprecations and browser interventions. The CSP report endpoint from Chapter 27 doubles as an early warning that something is injecting scripts.

6Beyond the browser

Where these skills transfer, and what changes when they do.

PlatformWhat it isWhat changes
Electron Chromium plus Node in a desktop app You ship the browser, so bundle size becomes hundreds of megabytes. Node access in the renderer is a serious security boundary — context isolation on, node integration off, validate everything crossing the IPC bridge.
Tauri The OS webview plus a Rust core A fraction of the size, at the cost of rendering in whatever webview the user's OS provides — so cross-platform testing matters again in a way it had stopped mattering.
React Native React targeting native views Components and state management transfer; CSS, the DOM and every browser API do not. Flexbox survives in a modified form.
Capacitor Your web app in a native shell with plugin access to device APIs Almost everything transfers. Store review, app updates and native permissions are the new concerns.
Browser extensions HTML, CSS and JavaScript against extension APIs Manifest V3's service-worker background scripts, a strict CSP, and content scripts that run inside pages you do not control. Store review is slow.
HTML email — A genuinely different discipline: tables for layout, inline styles, no JavaScript, and client support roughly two decades behind. Do not assume your CSS knowledge carries over; it mostly does not.

The durable skills are the ones underneath the platform: how the network behaves, how to structure state, accessibility, performance discipline, testing, and reading specifications. Those transfer everywhere. Framework-specific knowledge has a half-life measured in a few years.

7Staying current without drowning

The field generates more noise than signal. A filter is a professional skill.

Learn the layer that lasts
HTTP, the DOM, CSS, JavaScript, accessibility and the browser's rendering model change slowly and explain everything built on top. Time spent there compounds; time spent on the seventh state-management library does not.
A small, high-quality intake
MDN and the specifications for reference. web.dev and the browser vendors' release notes for what is new. Baseline for what is safe to use. A handful of people whose judgement you trust. That is enough — a larger intake mostly increases anxiety.
Ignore the discourse
Most framework arguments are about preferences held with unwarranted confidence. The useful question is never "what is best" but "what does this solve, what does it cost, and does my project have that problem".
Build something with it
Reading about a technology produces recognition; using it produces knowledge. An afternoon building something small teaches more than a week of articles.
Adopt deliberately
New tools should enter through a low-risk project with an owner and a review date, not through the critical path because someone was enthusiastic on a Friday.
Depth beats breadth after the first year
Knowing one framework properly — including how it fails and what it costs — is worth more than a shallow acquaintance with five, and the deep knowledge is what transfers when you move to the sixth.

8Check yourself

Six questions.

1. After every deploy a few users report "Failed to fetch dynamically imported module". What is happening?

They had a tab open from before the deploy. Their HTML — and the running JavaScript — references the old build's content-hashed chunk filenames. When they navigate to a lazily loaded route, the browser requests reports.9f3c1a.js, which the new deployment replaced with a differently hashed file and, if the deploy deleted old assets, no longer serves at all. Two fixes, both worth doing: retain the previous few builds' hashed assets so old references keep resolving, and catch the import failure to prompt a reload rather than leaving the page broken. Ensure the HTML itself is served no-cache so a refresh genuinely picks up the new document.

2. Why deploy behind a feature flag rather than simply deploying when ready?

It separates two things that are usually conflated. Deploying is a technical act with risk; releasing is a product decision. With a flag you can merge continuously — keeping branches short and avoiding the merge pain from Chapter 24 — while the feature stays dark, then enable it for staff, then a small percentage, then everyone, watching the metrics at each step. If something is wrong you flip the flag off in seconds with no deploy, no rebuild and no rollback window. The cost is real: every flag doubles the paths through that code, so give each one an owner and a removal date and delete it as soon as the rollout finishes.

3. Your build inlines API_URL at build time. Why does that conflict with build-once-deploy-many?

Because the value is baked into the artefact, so staging and production need different artefacts — which means production runs a bundle that was never tested, only a sibling of it. Any build-time difference can hide a build-time bug. The runtime alternatives are: use relative URLs such as /api and let each environment's routing resolve them, which is cleanest; fetch a small /config.json at start-up, at the cost of one blocking request; or have the server inject window.__CONFIG__ into the HTML. Build-time inlining stays appropriate for genuinely invariant values such as the build number.

4. Your error tracker reports 40,000 events a day and nobody looks at it. What went wrong?

It was not filtered, so signal is buried. The usual sources of volume are browser extensions injecting scripts, third-party tags failing, network errors from users who navigated away mid-request, and a couple of noisy known issues repeating thousands of times. Fix it by ignoring errors from origins you do not control, dropping the known-benign patterns, grouping properly so one bug is one issue rather than thousands, and sampling high-volume events. Then make it actionable: upload source maps so traces are readable, tag every event with release and route so a spike attaches to a deploy, and alert on a rate change rather than on any error at all.

5. Why alert on "checkout conversion dropped 30%" rather than on CPU or memory?

Because the first is a statement about users and the second is a statement about machines. High CPU may be entirely normal; low CPU with a broken checkout is a disaster nobody is paged for. Symptom-based alerting catches the failures you did not predict, including ones with no infrastructure signature at all — a bad deploy, a third-party outage, a JavaScript error on one browser version. Resource metrics remain valuable for diagnosis after the alert. There is also a human factor: every alert that fires without needing action erodes trust in all of them, exactly as a flaky test suite does.

6. Which parts of your front-end knowledge transfer to React Native, and which do not?

Transferring: React itself — components, hooks, state, the reactivity model from Chapter 18 — plus state management, data fetching, testing discipline, accessibility thinking and performance instincts. Not transferring: the DOM, CSS as such (styles are a JavaScript object subset, with flexbox in a modified form and no cascade, no media queries, no pseudo-classes), every browser API, routing, and the whole loading and caching model. New concerns arrive too: the native bridge, platform differences, app store review and over-the-air update rules. The general pattern holds across every platform in this section — the durable knowledge is the layer beneath the framework, and the platform-specific layer is always re-learned.
