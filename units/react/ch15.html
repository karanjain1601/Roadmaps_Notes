CHAPTER 15

Routing

A router maps a URL to a view. Everything interesting about it is the second job: taking over navigation from the browser, and then owing the user all the things the browser used to do for free.

Part 4 Building an application·Reading time 40 minutes·Demos what survives a navigation, load timelines·Prerequisites Chapters 12–13

1What a router provides

Six things, and only the first is obvious.

URL to component
Pattern matching, with dynamic segments, optional segments, splats and a not-found case.
Nesting
A URL matches a chain of routes, each contributing a layer of the interface. Section 2, and the reason routers are more than a switch statement.
Navigation
<Link> that intercepts the click and pushes history instead of reloading — while still being a real anchor, so middle-click, cmd-click and "open in new tab" work. A router whose links are divs is broken.
Data
Loaders and actions declared with the route, so fetching starts when navigation starts. Section 4.
Pending state
Knowing that a navigation is in progress, so you can show it honestly rather than freezing.
Everything the browser stopped doing
Title, focus, announcements, scroll, cancellation. Section 7, and the part most implementations get wrong.

2Nested routes and layouts

The central idea: a URL selects a stack of layers, not a single screen.

A route tree React Router

  <Route index element={<Home />} />

Why it matters beyond tidiness
A flat router re-renders the whole screen for every navigation, so the sidebar scroll resets, the open panel closes, and any layout-level state is destroyed. Nesting is what makes navigation between siblings feel like moving within an application rather than loading a new page.
Layout routes without a path
A route with an element and no path wraps its children without adding a URL segment — useful for an authenticated shell or a shared error boundary around a group.
Watch the identity rule
Chapter 4 again: the innermost layer stays mounted if the same component occupies the same position, so navigating from order 4182 to 4183 reuses OrderDetail and its state. That is usually right; when it is not, give it key={orderId} and it will remount cleanly.

3Params, search params and where state belongs

Three places a value can live in a URL, plus one that is not the URL at all.

WhereLooks likeFor
Path param/orders/4182Identifying what resource. Part of the resource's address.
Search param?status=open&page=2How the resource is being viewed: filters, sort, page, a search term, an open tab worth linking to.
Hash#deliveryA position within the page. Never sent to the server.
History stateinvisibleSmall transient data attached to an entry — where a modal was opened from. Not shareable, so not a substitute for search params.

The test for putting something in the URL: would a user reasonably expect to bookmark it, share it, or reach it again with the back button? If yes, it goes in the search params — and you get refresh survival and back-button behaviour free. If it is transient UI, sensitive, large, or changes many times a second, keep it out.

4Loaders: fetching before rendering

The largest performance difference between routers, and the fix for Chapter 13's waterfall.

Declaring data with the route React Router
{
  path: 'orders/:orderId',
  lazy: () => import('./routes/order-detail'),      // code
  loader: async ({ params, request }) => {              // data — in parallel
    const [order, events] = await Promise.all([        // and in parallel
      fetchOrder(params.orderId, { signal: request.signal }),
      fetchEvents(params.orderId, { signal: request.signal })
    ]);
    return { order, events };
  }
}

// request.signal is aborted if the user navigates away mid-load,
// which is Chapter 9's cancellation, handled by the router.
Loaders and a query cache are complementary
Use the loader to start the request as navigation begins, and have it call queryClient.ensureQueryData so the result lands in the same cache your components read from. You get parallel loading and client-side revalidation, rather than choosing.
Actions are the write half
A route action receives a form submission, performs the mutation and revalidates the route's loaders automatically. Chapter 14's form action, at the router level.
Do not block on everything
Fast-critical data blocks the navigation; slow-secondary data should be deferred and streamed into a Suspense boundary. Otherwise one 1.5-second recommendation query holds up the whole page — Chapter 12's boundary demo.

5Splitting and prefetching

The route is the natural split point, and hover is the natural prefetch trigger.

Split by route by default
lazy on a route, or React.lazy plus a Suspense boundary. The initial bundle becomes one screen instead of the whole application.
Prefetch on intent
On hover, on focus, or when the link scrolls into view. A user's pointer arrives on a link a few hundred milliseconds before the click, which is usually enough to download the chunk and start the data — hence the third bar in the demo. React Router's <Link prefetch="intent"> and Next's automatic viewport prefetching both do this.
Do not split too finely
A chunk per component produces dozens of small requests that compress badly. Route-level, plus a separate chunk for anything genuinely heavy and rarely used — a chart library, a rich editor.
Handle the chunk that fails to load
After a deploy, an open tab's chunk filenames may no longer exist. The import rejects, and without handling the route simply never appears. Catch it and prompt a reload — Chapter 29 of the Front-end unit covers the cause.

6Navigation states

A navigation that fetches takes time. The user should be told, without the screen going blank.

Pending, not blank
useNavigation() or the router's equivalent tells you a navigation is in flight. Keep the current page visible and dim it, or show a top progress bar — Chapter 12's principle that stale content beats a spinner. This is also why routers wrap navigations in a transition: it suppresses Suspense fallbacks so the old page stays.
Blocking a navigation
Unsaved changes need useBlocker or the router's equivalent for in-app navigation, and beforeunload for a tab close. Two separate mechanisms; forgetting the second is the common half-implementation, and it is the one that loses work.
Redirects belong in the loader
An auth check that redirects should do so before rendering, by throwing a redirect from the loader. Rendering a component that immediately navigates away in an effect flashes the protected page and is Chapter 9's "you might not need an effect" in another costume.
Scroll restoration
Top on a forward navigation, saved position on back. Most routers provide a component for it; verify it, because getting it wrong is very noticeable on a long list and it is easy to break with a scrolling container that is not the window.

7The five obligations

A full page load did all of these. Once you intercept the click, they are yours.

#ObligationWhat breaks without it
1Update document.titleThe tab and the history entry are wrong, so the back menu is unusable and a bookmark is mislabelled.
2Move focus to the new view's heading, with tabindex="-1"Focus stays on a link that no longer exists. A keyboard user's next Tab starts from the top of the document; a screen-reader user gets no signal that anything happened at all. The most commonly missed, and the most damaging.
3Announce the new page in a polite live regionSilent navigation. Belt and braces with 2 — some combinations announce on focus, some do not.
4Reset scroll on forward, restore on backArriving halfway down a new page, or losing your place in a long list when you go back.
5Cancel requests belonging to the view you leftResponses render into a screen the user has moved on from, or set state on a route that is gone. A loader's request.signal handles it if you pass it through.

Routers vary in how many they handle. Assume none, verify each, and test with the keyboard and a screen reader rather than by reading the documentation — this is a place where "supported" and "works" diverge.

Four realistic choices, distinguished by how much they decide for you.

9Check yourself

Five questions.

1. What does nesting buy beyond tidier configuration?

Persistence. A URL matches a chain of routes, each rendering a layer, so navigating between siblings changes only the innermost one — every layout above stays mounted and keeps its state. The sidebar keeps its scroll position, an open filter panel stays open, a running animation is not restarted, and any data those layers loaded is not refetched. A flat router replaces the whole screen on every navigation, which is why such applications feel like a series of page loads. It also gives you a natural place to put shared error boundaries, shared pending states and shared data.

2. Path param or search param?

A path param identifies what resource you are looking at and is part of its address — /orders/4182. A search param describes how you are looking at it: filters, sort, page, search term, a linkable tab. The practical test for search params is whether a user would expect to bookmark or share that view, or reach it again with the back button; if so it belongs in the URL and you get refresh survival free. Keep transient UI, sensitive values, large blobs and high-frequency values such as scroll position out. And validate whatever you read — a query string is user input, and ?page=-4 will arrive.

3. Why is a route loader faster than fetching in the component?

Because it removes a dependency between two things that do not actually depend on each other. A component cannot fetch until it renders, and it cannot render until its code chunk has downloaded — so code and data load in series, and nested fetching components stack up further round trips behind that. A loader is declared with the route, so the router starts it the instant navigation begins, in parallel with downloading the chunk, and a single loader can fire several requests with Promise.all. The demo shows the effect: two serialised round trips become one, and the gap widens with latency and with nesting depth.

4. Which of the five obligations is most damaging to miss, and why?

Focus management. After a real page load the browser resets focus to the document; after a client navigation it does not, so focus remains on a link that no longer exists in the tree. For a keyboard user the next Tab starts over from the top of the page — every navigation costs them a full re-traverse. For a screen-reader user there is often no signal at all that anything happened, because nothing was focused and nothing was announced. The fix is small: give the new view's heading tabindex="-1" and focus it, and pair it with a polite live region since announcement behaviour varies. It is missed constantly because nothing about it is visible to a mouse user.

5. An auth guard renders a component that redirects in an effect. What is wrong?

The protected page renders first. The component mounts, returns its markup, the browser paints, and only then does the effect run and navigate away — so there is a real frame where unauthorised content is on screen, and any data fetching inside it has already started. It is also Chapter 9's pattern: an effect used to react to something that was already known before rendering. The fix is to decide before rendering — throw a redirect from the route's loader, or check in a parent layout route that renders either the child or the sign-in view. That also puts the rule in one place rather than in every protected component.
