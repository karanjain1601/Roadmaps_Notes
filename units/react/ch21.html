React Native and the other renderers

React has never been about the DOM. It is a reconciler — an algorithm for working out what changed — and the DOM is one of several things it can be pointed at. Understanding that split explains React Native, and also why "write once, run anywhere" was never the promise.

Part 5 Beyond the client·Reading time 35 minutes·Demos what transfers, one component four renderers·Prerequisites Chapters 4, 16

1The split

Why you install two packages, and what each one does.

react
Components, hooks, elements, context, the reconciler's public surface. It knows nothing about any output target. This is why useState is imported from react and not from react-dom.
react-dom, react-native, and the rest
A host config: how to create a node, set a property, insert a child, remove one, measure, and commit. The reconciler works out what should change; the renderer knows how to change it.
The consequence
Everything in Parts 1 to 3 of this unit — the render cycle, state, keys, effects, memoisation, transitions, Suspense — is renderer-independent. It behaves identically whether the output is DOM nodes, native views, terminal characters or a 3D scene graph.
What is not portable
The host elements themselves and everything platform-specific around them: styling, layout defaults, gestures, navigation, storage, permissions. That is section 4's subject, and it is a larger fraction than people expect.

3How React Native runs

      
Worth knowing because the architecture changed substantially, and older explanations are now wrong.


      

        
Real native views

        
A <View> becomes an actual UIView or Android ViewGroup. There is no web view and no HTML anywhere. That is the difference from Cordova-era hybrid apps and the reason the result feels native.

        
Your JavaScript still runs in an engine

        
Hermes, purpose-built for React Native: fast startup, small memory footprint, ahead-of-time bytecode.

        
The bridge is gone

        
The old architecture serialised every call between JavaScript and native as asynchronous JSON, which is where the historical complaints about list performance and gesture lag came from. The new architecture uses JSI — direct, synchronous access to native objects — with Fabric for rendering and TurboModules for native APIs, loaded lazily.

        
Practical consequences

        
Synchronous measurement, much better gesture and animation handling, faster startup, and concurrent React features working properly. If you are reading advice about "batching across the bridge", it predates this.

        
Expo is the default way in

        
Routing, build service, over-the-air updates, and a large set of vetted native modules. Starting a React Native project without it now needs a reason.

5Styling and layout

      
Flexbox you already know, with three defaults changed and most of CSS absent.


      

        
The differences that catch people React Native

        
const styles = StyleSheet.create({
  card: {
    flexDirection: 'row',      // default is 'column', not 'row'
    alignItems: 'center',
    padding: 16,                // numbers are density-independent pixels
    backgroundColor: '#fff'      // camelCase, always
  }
});

// Also true:
//   • Every View is display:flex already. There is no `display: block`.
//   • No cascade and no inheritance — except text styles down through
//     nested <Text>, which is the one exception and a common surprise.
//   • All text must be inside <Text>. A bare string in a <View> throws.
//   • No media queries. Use useWindowDimensions() and conditionals.
//   • No hover. Pressable gives you pressed, and that is the model.
//   • Shadows differ per platform: elevation on Android, shadow* on iOS.
//   • overflow: 'hidden' does not clip shadows the way you expect.

      


      

        
The styling libraries

        
NativeWind brings Tailwind's syntax across, which is the shortest path for a team already using it. Tamagui and Restyle offer typed design systems that work on both targets. Unistyles is a lighter option. All of them exist because plain StyleSheet has no theming story.

        
Design tokens still travel

        
Colours, spacing scales and type scales are plain values, so they can be shared as a TypeScript module even though the styling mechanism differs. That is usually the single most valuable thing to share between web and native.

      

    


    
    

      
6Navigation and platform reality

      
Chapter 15's ideas, with different expectations attached.


      

        
Expo Router or React Navigation

        
Expo Router is file-based and closest to what you know from Next; React Navigation is the underlying library and is configured in code. Both give you native stack, tabs and drawer navigators that use the platform's own transitions.

        
Screens are not pages

        
A stack keeps previous screens mounted underneath, back is a gesture as well as a button, and deep linking is how the URL concept survives. Users expect the platform's transition, not yours.

        
Platform differences are real work

        
Safe areas, the status bar, the keyboard covering inputs, back-button semantics on Android, permission dialogs, and app-store review. None of it is hard individually; together it is the reason a native app is not a web app with different tags.

        
Branch deliberately

        
Platform.select and .ios.tsx / .android.tsx file extensions. Scattering Platform.OS === 'ios' through component bodies is how a codebase becomes unreadable.

      

    


    
    

      
7Sharing code, realistically

      
The valuable sharing is not the components.


      

        

          
ShareDo not bother sharing

          
            

              Types and schemas. Validation. Business logic and calculations. API clients. Custom hooks with no DOM dependency. Data-fetching setup and query keys. Design tokens. Copy and translations. Formatting and date handling.
              Presentational components — the platforms have different conventions and users notice. Navigation structure. Styling implementation. Anything touching gestures, layout or platform APIs.
            

          
        

        
A monorepo with a shared core package and separate web and mobile applications is the arrangement that holds up. React Native for Web can share components too, and it works — but it is a real constraint on both platforms, so adopt it because you want one interface everywhere, not to save effort.

      


      

        The trap
        
"Write once, run anywhere" turns into a component full of platform branches that is worse on both platforms than two separate components would have been. The question is not "can this be shared" but "would sharing it make both versions better". For a login form, often yes. For a navigation shell, almost never.

      

    


    
    

      
8When it is the right choice

      
Four situations for, three against.


      

        

          
Good fitReach for something else

          
            

              A React team that needs mobile without hiring two more disciplines. A product whose mobile app is mostly screens, lists and forms. Something that must ship on both platforms at once. An existing React web app whose logic can be shared.
              Anything performance-critical at the graphics level — a game, heavy real-time rendering. Apps built around deep platform integration such as widgets, watch apps or complex background work. A team that already has strong Swift and Kotlin skills and only one platform to serve.
            

          
        

        
The alternatives are worth naming honestly: Flutter has excellent performance and its own widget system but means learning Dart; native means two codebases and the best possible result on each; and a well-built responsive web app plus a thin wrapper is sometimes all that was actually needed.

      

    


    
    

      
9Check yourself

      
Five questions, closing Part 5.


      

        
1. Why are react and react-dom separate packages?

        
        

          
Because React is a reconciler — the algorithm that works out what changed between two element trees — and that algorithm has no opinion about what the output is. react provides components, hooks, elements and context; a renderer such as react-dom or react-native provides a host config saying how to create a node, set a property, insert a child and commit. That is why useState comes from react rather than react-dom, and why everything in Parts 1 to 3 of this unit behaves identically regardless of target. The split is also what makes renderers for the terminal, 3D scenes and PDFs possible without changing React itself.

        

      


      

        
2. What actually transfers from web React to React Native?

        
        

          
All of React itself: components, props, hooks, state, keys, context, effects, memoisation, Suspense, error boundaries, the render cycle. Your data layer, types, validation and business logic transfer unchanged. Host elements are renamed but conceptually similar — div to View, button to Pressable. What does not transfer is the entire platform layer: CSS and its cascade, media queries, hover, the DOM API, localStorage, URL-based routing, and every browser global. The demo's proportions are the useful part — React knowledge carries over almost completely, and web-platform knowledge largely does not.

        

      


      

        
3. What changed with the new React Native architecture?

        
        

          
The asynchronous, JSON-serialising bridge between JavaScript and native was replaced. JSI gives JavaScript direct, synchronous access to native objects; Fabric is the new renderer built on it; TurboModules load native modules lazily rather than all at startup. The practical effects are faster startup, synchronous layout measurement, much better gesture and animation handling, and concurrent React features working properly. It matters when reading older material: advice about batching calls to minimise bridge traffic, or explanations of list-scrolling lag in terms of serialisation, describes an architecture that no longer exists.

        

      


      

        
4. Which code is worth sharing between a web and a native app?

        
        

          
Everything that is not about presentation: types and schemas, validation, business logic and calculations, API clients, data-fetching configuration and query keys, custom hooks with no DOM dependency, design tokens, copy and translations. That is a substantial fraction of a real application and it shares cleanly. Presentational components generally should not be shared, because the platforms have genuinely different interaction conventions and users notice when an app ignores them — and a shared component full of platform branches ends up worse on both than two focused ones. The test is not "can this be shared" but "would sharing make both versions better".

        

      


      

        
5. Someone proposes React Native for a 3D-heavy game. What do you say?

        
        

          
That it is the wrong fit. React Native's strength is screens, lists, forms and navigation built from real platform views — a UI-shaped problem. A game is a render-loop-shaped problem with continuous animation, physics and graphics-pipeline work, where you want direct access to the GPU and a frame budget you control, not a reconciler diffing a view tree sixty times a second. Better answers are a real game engine, or a native renderer with a thin React layer only around the menus. Worth noting the nuance though: React can drive 3D through react-three-fiber, and that works well for declarative scenes and product visualisations — the objection is to a game loop, not to 3D as such.
