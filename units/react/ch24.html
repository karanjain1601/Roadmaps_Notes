1How to use this

Four sections, three of them tools rather than prose.

The checklist
Run it against a component or feature you are about to submit for review, or against something you inherited. Ticking a box marks it as considered, not necessarily as done — several items are judgement calls where the right answer is "not applicable here".
The symptom lookup
Something is behaving strangely. Search for the symptom in the words you would use to describe it, and it will name the likely cause and the chapter. Most React bugs are one of thirty things.
The glossary
Every term this unit used, defined in one line. Useful when reading somebody else's code, a library's documentation, or a job description.
The quiz
Thirty-two questions, scored per part. The score matters less than which part scored lowest.

6Where to go from here

Four directions, depending on what you want next.

Read the source of something small
Not React itself — start with a library you use: Zustand is a few hundred readable lines, react-error-boundary is short and clear, and TanStack Query's cache is well worth an afternoon. Reading real implementations of Chapters 7, 11 and 13 makes them concrete.
Build the thing that is hard for you
A combobox from scratch, once, to appreciate Chapter 16's argument. A tiny reconciler with react-reconciler, to feel Chapter 21's split. A working signal implementation, to see Chapter 18 of the Front-end unit from the other side.
Go deeper on the platform, not the framework
Most of what limits a React application is the browser: layout, paint, the event loop, caching, network. The Front-end Developer unit covers those directly, and that knowledge does not expire when the framework changes.
Follow the primary sources
The React documentation is genuinely excellent now and worth rereading rather than skimming. The React blog and the RFC repository are where changes are argued before they arrive, which is a much better signal than commentary about them.

That is the unit. Twenty-four chapters, and the through-line was one idea: React gives you a description of what the interface should be for a given state, and everything else — keys, effects, memoisation, boundaries, the server split — exists to make that description cheap enough to recompute.
