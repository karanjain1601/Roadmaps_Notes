CHAPTER 03

Components, props and composition

A component is a function that takes data and returns elements. That definition is complete, and almost everything that makes React codebases pleasant or awful is about two things it does not say: whether the function is honest about being a function, and where you choose to draw the lines between them.

Part 1 The model·Reading time 40 minutes·Demos purity checker, configuration versus composition·Prerequisites Chapters 1–2

1What a component is

Less than you might expect. There is no class, no registration, no lifecycle to declare.

The whole definition JSX
// A function. Capitalised. Takes one argument. Returns elements.
function OrderRow({ order, onCancel }) {
  return (
    <li className="row">
      <span>{order.reference}</span>
      <button onClick={() => onCancel(order.id)}>Cancel</button>
    </li>
  );
}

// That is it. No base class, no decorator, no registration step.
// React knows it is a component because you used it as one.
Capitalised, always
Chapter 2's transform rule. Lowercase produces a string type and React looks for an HTML element of that name.
One argument
The props object. Destructuring it in the parameter list is the near-universal convention, because the alternative is props. forty times.
Returns elements, or nothing
null is a valid return and means "render nothing here". A component that returns nothing still exists in the tree and still holds state.
Class components
You will meet them in older code. They are not deprecated but they are not where the platform is going, and every feature since 2019 — hooks, concurrent rendering, server components — is function-only. The one thing still requiring a class is an error boundary, which is Chapter 18.
Where they live
One component per file for anything reused; several in one file when they are only used together and would never be imported separately. Name the file after the component. Chapter 23 covers structure at scale.

2Props

An ordinary object, with one non-negotiable constraint.

Props are read-only
A component must never assign to its props or mutate an object it received. It is not a stylistic preference: the same object is often shared with the parent and with siblings, and React compares by reference to decide what changed. Mutating a prop produces a change nobody is told about, in a place nobody owns.
Anything can be a prop
Strings, numbers, objects, arrays, functions, and elements. Passing an element as a prop is how you build slots: <Panel header={<Title />} />.
Defaults go in the parameter list
function Button({ size = 'md' }). The old defaultProps static is deprecated for function components.
Forward the rest
function Input({ label, ...rest }) then <input {...rest} />. Without this, every consumer who needs aria-describedby, data-testid, autoComplete or maxLength has to come and ask you to add it. This one habit prevents a large amount of future friction.
Callbacks flow the other way
Data goes down as props, intent comes back up as function calls. Name them for the event, not the implementation: onSelect, not setSelectedIdInParent.
children is a prop like any other
Written between the tags for convenience, but ordinary. It is the single most important prop in React and section 4 is about why.

3Purity, and why React insists

Rule 1 from Chapter 1, stated precisely, with the failures made visible.

Given the same props and state, a component must return the same result and change nothing outside itself while doing so. React relies on this to batch updates, to render speculatively, to abandon a render in progress and start again, and — in concurrent mode — to run your component at a moment you did not choose. Break purity and the resulting bugs appear only sometimes, only in production, or only when a user types quickly.

Purity checker Each function is called twice with identical input, exactly as StrictMode does. Real calls, real outputs.
ComponentFirst callSecond callVerdict

Breaks purityDo this instead
Writing to a variable declared outside the componentUse state, or a ref if it must not trigger a render (Chapter 8)
Mutating props or an object from a propCopy it, or ask the owner to change it
Reading or writing the DOM during renderAn effect, or a ref callback (Chapters 8 and 9)
Fetching, logging, or setting a timer during renderAn event handler if a user caused it; a query library or effect otherwise
Math.random() or Date.now() in the returned outputCompute it in an event handler or in state, so it is stable across renders
Mutating a value created in a previous renderMutating something created during this render is fine — it is local

StrictMode exists to make these fail loudly: in development it calls each component twice, so a component that increments a counter or pushes to an outer array produces visibly wrong output immediately rather than in six months under load.

4Composition over configuration

The most consequential design habit in this chapter, and the easiest to get wrong slowly.

A component that grows a boolean flag per requirement is describing structural variants through a configuration API. Each flag doubles the number of states it can be in, and the implementation becomes a nest of conditionals nobody wants to touch. Accepting children instead pushes the structure back to the caller, where it is visible.

The test

        
If a prop's only job is to decide whether a piece of markup appears, it should probably be children instead. If it changes how something looks — size, tone, variant — a prop is right, and a union of string literals beats several booleans.

        
Named slots

        
When a component needs several regions, take several element props: <Layout sidebar={…} main={…} footer={…} />. Explicit, typed, and it keeps the arrangement inside the component where it belongs.

        
Compound components

        
<Tabs><Tabs.List>…</Tabs.List><Tabs.Panel>…</Tabs.Panel></Tabs> — related parts sharing state through context, arranged freely by the caller. The pattern behind most good component libraries; Chapter 23 builds one.

        
Composition also fixes prop drilling

        
If a value is only needed by a deep child, render that child at the top and pass it down as children. The intermediate components then never see the value, and no context is required. This is the first thing to try before reaching for a store — Chapter 7.

      

    


    
    

      
5Where to draw the lines

      
A good boundary is a seam that the next change is likely to respect.


      

        
Split on responsibility, not on length

        
A 250-line component doing one coherent job is fine. Three 40-line components that always change together are worse, because the change is now spread across three files and a props interface.

        
Separate the thing from its data

        
<UserCard user={…} /> renders whatever it is given: reusable, testable, easy to put in Storybook. The same component fetching its own user by id is none of those. Put the fetching one level up, in a container or a route loader.

        
Extract behaviour, not markup

        
Two components needing the same debounced search should share a hook, not a wrapper component that renders both. Chapter 11.

        
Extract early only when you know the axis of change

        
Premature abstraction produces a component with eleven props that is harder to use than duplication would have been. Duplicate twice; extract on the third, when the shared shape is evident.

        
Name the thing, not the position

        
<OrderSummary />, not <RightPanel />. Positional names age badly and are the ones people are afraid to move.

Polymorphism, forwarding and controlled-or-not JSX

        
// 1. The `as` prop — same styling and behaviour, different element.
//    Essential for accessibility: a "button" that navigates must be an
//    anchor, not a div with onClick.
function Action({ as: Tag = 'button', ...rest }) {
  return <Tag className="action" {...rest} />;
}
<Action as="a" href="/orders">View orders</Action>

// 2. Rest forwarding — stay open to attributes you did not enumerate
function Field({ label, id, ...inputProps }) {
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} {...inputProps} />   {/* aria-*, maxLength, … */}
    </div>
  );
}

// 3. Controlled or uncontrolled — let the caller decide who owns the value
function Disclosure({ open, defaultOpen = false, onOpenChange, children }) {
  const [inner, setInner] = useState(defaultOpen);
  const isControlled = open !== undefined;
  const isOpen = isControlled ? open : inner;
  const toggle = () => {
    if (!isControlled) setInner(!isOpen);
    onOpenChange?.(!isOpen);
  };
  // …the pattern every serious component library uses. Chapter 14.
}

      

    


    
    

      
7Five mistakes worth naming

      
Each produces a bug that does not look like its cause.


      

        1 · Defining a component inside another component
        
A function declared in a render body is a new function on every render, so its type differs from last time — and Chapter 4's reconciler treats a different type as a different component. React unmounts the old subtree and mounts a fresh one every single render: state destroyed, DOM recreated, inputs cleared, focus lost, transitions restarted. It looks like a state bug and it is a definition-location bug. Move the component to module scope and pass what it needs as props.

      


      

        
2 · Mutating a prop

        
props.items.sort() sorts the parent's array in place. [...items].sort() or items.toSorted() instead. The four mutating array methods — sort, reverse, splice, push — are the usual culprits.

        
3 · Prop explosion

        
Eleven props of which six are booleans is section 4's signal. Split the component, or accept children.

        
4 · A component per div

        
The opposite failure. Wrapping every element in a named component adds a layer of indirection for no reuse; readers now have to open four files to picture one card.

        
5 · Passing setters down

        
<Child setUser={setUser} /> hands the child unrestricted write access to the parent's state. Pass a narrow callback — onNameChange — so the parent keeps control of what a change means and can validate, log or reject it.

      

    


    
    

      
8Check yourself

      
Five questions.


      

        
1. Why is purity a hard rule rather than good practice?

        
        

          
Because React's scheduling guarantees depend on it. React decides when and how often to call your component: it batches several state updates into one render, renders speculatively during a transition, abandons work that has become irrelevant, and may call a component twice or not at all. All of that is only correct if calling the function has no observable effect beyond returning a description. When purity breaks, the symptoms are the worst kind — intermittent, load-dependent, and different between development and production. StrictMode's deliberate double-invoke exists to convert those into an obvious failure on the first render instead.

        

      


      

        
2. A component has showHeader, showFooter, showBadge, compact and bordered. What is it telling you?

        
        

          
That flags are being used to describe structural variants, which is configuration where composition belongs. Five booleans is thirty-two reachable states, most of which are untested and some of which are nonsense, and the implementation becomes conditionals nested around each other. The distinction to apply: a prop that decides whether markup appears should be children or a named element slot; a prop that decides how something looks — size, tone — is legitimate, though a union of string literals beats several booleans. Accepting children moves the arrangement to the caller, where it is visible, and the component's own API stops growing.

        

      


      

        
3. Every keystroke in a nested input clears it. The state logic looks correct. What would you check first?

        
        

          
Whether the component containing that input is defined inside another component's body. A function declared during render is a new function identity every render, so when React reconciles it sees a different type at that position, unmounts the whole subtree and mounts a replacement — destroying state, recreating DOM nodes, clearing the input and dropping focus. Nothing in the state code is wrong; the component's location is. Move it to module scope. The same symptom can also come from a changing key, which is the other way to tell React "this is a different thing".

        

      


      

        
4. Why prefer onNameChange over passing setUser down?

        
        

          
Because a setter is unrestricted write access to the parent's state, and handing it over means the parent no longer controls what a change means. It cannot validate, cannot normalise, cannot log, cannot reject, and cannot later change how the state is stored without touching every child that writes to it. A narrow callback keeps the parent as the owner and states the child's intent — "the name changed" — rather than the mechanism. It also makes the child testable and reusable in a context where the state is held somewhere else entirely, and it matches the props-down-events-up direction that makes a tree readable.

        

      


      

        
5. What is the first thing to try when a value has to travel through four components that do not use it?

        
        

          
Composition, before context and long before a global store. If the deep child is the only consumer, render it higher up — where the value already exists — and pass the resulting element down as children. The intermediate components then accept and render children without ever seeing the value, and the drilling disappears with no new machinery. Other options in order: move the state lower if it can live closer to its consumer; colocate the data fetch with the consumer; use context when the value is genuinely ambient, such as theme, locale or the current user; and reach for a store only when many unrelated consumers need it and re-render cost matters, which is Chapter 7.
