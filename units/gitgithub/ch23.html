Repository archaeology and surgery

A repository that has existed for five years accumulates questions nobody can answer and objects nobody wants. Archaeology is answering the questions; surgery is removing the objects — and the second is disruptive enough that most of this chapter is about deciding whether you actually need it.

git bisect

Binary search over history. The highest-leverage command most people never run.

You know the tests pass at v2.3.0 and fail on main, with four hundred commits between. Reading them is hopeless; testing them one at a time is four hundred builds. Bisect finds the culprit in about nine.

by hand
$ git bisect start
$ git bisect bad                  # HEAD is broken
$ git bisect good v2.3.0          # this tag was fine
Bisecting: 203 revisions left to test after this (roughly 8 steps)
[8f3d2a1…] Add rate limiting

# ...build and test the checked-out commit, then say which it was:
$ git bisect good     # or: git bisect bad     # or: git bisect skip
# ...repeat until:
8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3 is the first bad commit

$ git bisect reset                # back to where you started
automated, which is how you should use it
$ git bisect start HEAD v2.3.0
$ git bisect run npm test -- tests/auth.test.js

# any script works; the exit code is the answer:
#   0        = good
#   1..124   = bad        (except 125)
#   125      = skip this commit, it cannot be tested
#   126, 127 = bad
$ git bisect run ./scripts/reproduce.sh

$ git bisect log > bisect.log      # share it, or replay after a mistake
$ git bisect replay bisect.log

Bisecting things that are not build failures

good and bad are just labels for "before" and "after". git bisect start --term-old=fast --term-new=slow lets you search for the commit where something got slower, or where a feature started working. And on a merge-heavy history, git bisect start --first-parent restricts the search to the mainline, which finds the offending merge rather than a commit inside somebody's branch — usually the more useful answer.

Finding things in an old repository

The queries you reach for once a year and cannot remember.

what is making this repository so large?
$ git count-objects -vH            # loose vs packed, and total size

# every blob in history, biggest first
$ git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1 == "blob" { print $3, $4 }' \
  | sort -nr | head -20

# which commit introduced that blob?
$ git log --all --oneline --find-object=<blob-sha>

# per-object sizes inside a packfile, including delta chain depth
$ git verify-pack -v .git/objects/pack/pack-*.idx | sort -k 3 -n | tail -20
and the archaeology from earlier chapters
$ git log -S "AWS_SECRET" --all --oneline        # when did this string appear? (ch. 6)
$ git log --diff-filter=D --oneline -- old/path   # which commit deleted this?
$ git log -L :funcName:file.js                     # this function's whole history
$ git reflog --date=iso                            # where has HEAD been? (ch. 4)
$ git fsck --full --no-reflogs --unreachable        # orphaned objects (ch. 8)
$ git cat-file --batch-all-objects --batch-check | wc -l    # every object, ever

--find-object is the one worth remembering: once the size query names a 250 MB blob, that flag tells you which commit brought it in, which is the input to every decision in the next section.

Surgery: rewriting all of history

Effective, irreversible for everyone else, and almost never the first step.

Chapter 2 established why a deleted file still costs you: the blob remains reachable from the commit that added it. The only way to remove it is to rebuild every commit from that point without it — which changes every subsequent hash, exactly as chapter 12 described, but for the entire repository.

git filter-repo, on a fresh clone
$ pip install git-filter-repo
$ git clone --mirror git@github.com:acme/api.git && cd api.git

# remove one path from all of history
$ git filter-repo --path secrets.env --invert-paths

# remove every blob over 10 MB, whatever its name
$ git filter-repo --strip-blobs-bigger-than 10M

# extract a subdirectory as the new repository root
$ git filter-repo --subdirectory-filter services/payments

# redact a string everywhere it appears
$ git filter-repo --replace-text replacements.txt    # lines like: literal:AKIA…==>REDACTED

# normalise author addresses across history
$ git filter-repo --mailmap ../mailmap

filter-repo replaces filter-branch, which was slow enough to take hours on a large repository and subtly wrong in ways that corrupted history. Git itself now prints a warning recommending the replacement. filter-repo refuses to run on a repository that is not a fresh clone, which is a feature: it wants you to do surgery on a copy.

For a leaked secret, rewriting is the second step

The credential was readable by everyone with access, is in CI logs, may be in someone's shell history, is in every existing clone, and survives in any fork and in GitHub's cached views of the old commits. Rotate it first. Once it is invalid, the rewrite is housekeeping rather than an emergency — and you can take the time to coordinate it, because rewriting a shared repository invalidates every open pull request and requires everyone to re-clone.

the aftermath, in order
# 1. rotate the credential. Everything below is cleanup, not containment.
# 2. tell everyone to stop pushing, and to re-clone afterwards
# 3. do the surgery on a mirror clone, verify it, then publish
$ git push --force --mirror git@github.com:acme/api.git

# 4. ask GitHub support to garbage-collect the old objects — a force-push does not
#    remove them from their side, and old commit URLs stay viewable
# 5. re-create branch protection if the push needed it lifted
# 6. everyone: rm -rf api && git clone …   (a pull will merge the old history back)

gc, packfiles and corruption

Storage maintenance, and what to do when the store is damaged.

routine maintenance
$ git gc                          # repack, prune unreachable objects older than 2 weeks
$ git gc --prune=now               # ...with no grace period. Loses reflog-only commits
$ git repack -adf                  # one packfile, recomputing deltas
$ git maintenance start            # register scheduled background maintenance
$ git commit-graph write --reachable   # precomputed graph: faster log, merge-base, bisect

$ git fsck --full --strict         # verify every object against its hash
$ git fsck --lost-found            # write dangling objects to .git/lost-found/

git maintenance start is the modern answer to periodic manual gc: it installs a schedule that prefetches from remotes, writes the commit-graph, repacks incrementally and expires the reflog, all in the background and without the pauses that gc --auto causes mid-command.

SymptomLikely causeAction
fatal: loose object … is corruptDisk or filesystem damageGet the object from another clone: git fetch, or copy the file into .git/objects
error: object file … is emptyInterrupted write, often a crashDelete the empty file and re-fetch; git fsck to find the rest
dangling commit … from fsckPerfectly normal — reset, amend, rebase leftoversNothing. It is not an error message
Repository suddenly hugeA big blob, or a runaway gc-less loose-object pileThe size query above, then gc, then consider surgery
git status takes ten secondsLarge working tree, no fsmonitorcore.fsmonitor, feature.manyFiles, or scalar (ch. 17)

The most reassuring fact about corruption: because every object is named by its own hash and every clone holds the same objects, a damaged repository can nearly always be repaired from a colleague's copy. Chapter 2's content addressing is what makes that possible.

.gitattributes, properly

Per-path configuration that travels with the repository, unlike config.

.gitattributes
# line endings — settle this once (ch. 1)
* text=auto
*.sh text eol=lf
*.bat text eol=crlf

# opaque files: no line-based diff or merge
*.png binary
*.pdf binary

# generated files: no diff noise, resolve merges by regenerating (ch. 11)
package-lock.json  -diff merge=ours
*.min.js           -diff linguist-generated

# better hunk headers in diffs: "@@ … def validate_token(…)" instead of a guess
*.py  diff=python
*.rb  diff=ruby
*.md  diff=markdown

# large files (ch. 17)
*.psd filter=lfs diff=lfs merge=lfs -text

# append-only files merge by concatenation (ch. 11)
CHANGELOG.md merge=union

# keep these out of `git archive` tarballs
.github/    export-ignore
tests/      export-ignore

# language statistics on GitHub
vendor/**   linguist-vendored
docs/**     linguist-documentation

The diff=python family is underrated: Git ships hunk-header patterns for a couple of dozen languages, and turning them on means every diff header names the enclosing function instead of whatever line the heuristic guessed. Two minutes of setup improves every code review afterwards.

a custom driver, when the built-ins do not cover it
$ git config diff.terraform.xfuncname '^(resource|module|variable|data).*'
$ echo '*.tf diff=terraform' >> .gitattributes

Hooks, the whole list

Chapter 5 covered the commit-time ones. Here is the rest, and where the real enforcement lives.

a pre-push hook that is actually worth having
#!/bin/sh
# .githooks/pre-push — refuse to push conflict markers or debugging leftovers
if git diff --cached --check >/dev/null 2>&1; then :; fi
if git grep -n --cached -E '^<<<<<<< |console\.log\(.*DEBUG' -- '*.js' >&2; then
  echo "pre-push: found conflict markers or debug logging" >&2
  exit 1
fi
exit 0
share them, since .git/hooks is not cloned
$ git config core.hooksPath .githooks && chmod +x .githooks/*
Server-side hooks on GitHub

github.com does not let you install pre-receive hooks — GitHub Enterprise Server does. On github.com the equivalent controls are branch protection and rulesets (chapter 16), required status checks running in Actions, and push protection for secrets (chapter 18). This is the same conclusion chapter 5 reached from the other direction: local hooks are a courtesy, and enforcement belongs where the code lands.

Long-term care

What to do once a quarter so surgery is never needed.

  • Watch the size. git count-objects -vH and the biggest-blob query. A repository that grows faster than its source code has a binary problem, and catching it at 200 MB is a conversation rather than an operation.
  • Keep generated files out. Build output, lockfile-adjacent caches, compiled assets, screenshots in test snapshots. Each is a small decision that becomes permanent.
  • Normalise authorship with .mailmap rather than rewriting history for it — it fixes shortlog and blame output with no hash changes at all.
  • Run git maintenance start on any repository you work in daily.
  • Prune branches. git fetch --prune, auto-delete merged head branches (chapter 18), and a quarterly pass over git branch --no-merged.
  • Turn on push protection so the secret never enters history and none of this chapter's surgery is needed.

Commit it at the repository root and git shortlog -sne, git blame and git log all collapse the duplicates. It is the correct answer to "our contributor stats are wrong", and it costs nothing.

The short version

Chapter 23 in eight lines

  • git bisect is a binary search over history: the number of tests is bounded at about log₂ of the candidate count, and bisect run makes it a single command.
  • --term-old/--term-new bisect anything with a before and after; --first-parent finds the offending merge instead of a commit inside a branch.
  • To find bloat: rev-list --objects --all piped into cat-file --batch-check, then git log --find-object to see which commit introduced it.
  • git filter-repo replaces the deprecated filter-branch, and insists on a fresh clone so the surgery happens on a copy.
  • For a leaked secret: rotate first. Rewriting does not un-leak it, and forks, caches, CI logs and existing clones all retain it.
  • git maintenance start is better than occasional manual gc; a dangling commit in fsck output is normal, not damage.
  • Corruption is usually repairable from any other clone, because objects are named by their own content.
  • .gitattributes travels with the repository: line endings, binary, -diff for generated files, diff=python for real hunk headers, merge=union, export-ignore.

Check yourself

A test started failing sometime in the last 400 commits. Write the fastest path to the culprit.

git bisect start HEAD <last-known-good> then git bisect run npm test -- tests/that_one.test.js. That is one command and roughly nine builds rather than four hundred, and it needs no judgement from you between steps. Two refinements: if the history is full of merges, add --first-parent so the answer is the merge that introduced it; and if some commits cannot build, have the script exit 125 for those so bisect skips them instead of recording a false result.

An AWS key was committed eight months ago and deleted the next day. Order your response.

Rotate the key first — everything else is cleanup. It has been readable in every clone, every fork, GitHub's cached commit views and probably a CI log for eight months, so assume it is compromised regardless of what you do to the repository. Then, unhurried: audit for use of the old key, find the blob with git log -S, and if you still want it gone, do a filter-repo pass on a mirror clone, coordinate a freeze, force-push, ask GitHub support to garbage-collect their side, and have everyone re-clone. Enabling push protection is what prevents the next one.

Why does a force-push after filter-repo not actually remove the old objects from GitHub?

Because the objects are still on their side and still referenced by things a push does not touch: pull request refs (refs/pull/N/head, chapter 16), cached commit views, and any fork's object store — forks share storage on GitHub's network. A force-push moves branch refs; it does not garbage-collect the server. Old commit URLs keep resolving, which is exactly the problem when the point was to remove a secret. You have to ask GitHub support to run garbage collection, and even then a fork can retain it — which is the practical reason rotation is the real fix.

Your contributor stats show one colleague as four different people. Two options, and which do you pick?

Rewrite history with filter-repo --mailmap to fix the author fields, or commit a .mailmap file that maps the aliases to one identity. Pick the .mailmap: it fixes shortlog, blame and log output immediately, changes no hashes, invalidates nobody's clone, breaks no pull requests, and can be edited later when someone changes their email again. Rewriting history to tidy up metadata is the clearest example of surgery whose cost far exceeds the problem.
