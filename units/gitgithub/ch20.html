GitHub Actions: the model

Actions is four nested things and one expression language. Most workflow debugging is really confusion about which of the four you are configuring, or about what a context contained at the moment an expression was evaluated. This chapter builds the model and then runs the expression language so you can see it decide.

The object model

Event, workflow, job, step. Everything else is configuration on one of those.

ThingIsKey facts
EventSomething happening in the repositoryA push, a PR, a schedule, a manual click, an API call
WorkflowOne YAML file in .github/workflows/Triggered by events; several can run for one event
JobA set of steps on one machineFresh machine each time; jobs run in parallel unless needs says otherwise; nothing on disk survives
StepOne run: command or one uses: actionSequential; shares the filesystem and shell with its siblings

The consequence people trip over: jobs share nothing. Two jobs are two machines, so a file written in one is invisible in the other unless you upload an artifact or pass an output. Steps in the same job share everything, which is why almost every workflow should be fewer, longer jobs rather than many small ones.

.github/workflows/ci.yml — the whole shape
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read          # least privilege for GITHUB_TOKEN

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # supersede an in-flight run on the same branch

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm test

  build:
    needs: test              # only if test succeeded
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

concurrency with cancel-in-progress is the highest-value four lines in most workflows: push twice to a branch and the first run is cancelled rather than burning minutes on code nobody will look at.

pull_request from a fork, and why pull_request_target is a trap

A pull_request run from a fork gets a read-only token and no secrets — deliberately, because the PR contains code you have not read. pull_request_target exists to work around that: it runs the base branch's workflow with full secrets. The trap is that many people then check out the PR's code inside it, which executes an untrusted contributor's build script with your secrets in the environment. If you must use it, do not check out the head, or check it out into a job with no secrets and pass only data between them.

One more asymmetry worth knowing: workflows for issue_comment, issues and similar platform events always run the version of the file on the default branch. You cannot test a change to them on a branch, which is a common half-hour of confusion.

Passing data between steps and jobs

Four mechanisms, and using the wrong one is the usual cause of "it works locally".

the four channels
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}     # job output, for other jobs
    steps:
      - id: meta
        run: echo "version=$(git describe --tags)" >> "$GITHUB_OUTPUT"   # step output
      - run: echo "CACHE_KEY=v2" >> "$GITHUB_ENV"                        # env for later STEPS
      - run: echo "./tools/bin" >> "$GITHUB_PATH"                         # PATH for later steps
      - run: echo "### Built ${{ steps.meta.outputs.version }}" >> "$GITHUB_STEP_SUMMARY"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploying ${{ needs.build.outputs.version }}"
ChannelScopeSurvives
$GITHUB_OUTPUTLater steps, and other jobs via outputs:Yes, as strings
$GITHUB_ENVLater steps in the same jobNot across jobs
$GITHUB_PATHLater steps in the same jobNot across jobs
ArtifactsAny job, any later workflow runYes — files, with a retention period

Note that echo "X=1" >> $GITHUB_ENV does not affect the current step — the environment is assembled before each step starts. And a plain export X=1 in a run: block dies with that step's shell, which is the single most common workflow bug.

Contexts and expressions

${{ }} is a small language with real semantics, and two of them are surprising.

job, runnerCurrent job status and container; runner OS, arch, temp paths

Expression evaluator

A real parser and evaluator for the subset that matters, against a fixed event context

FunctionDoes
contains(a, b)Substring of a string, or membership in an array

format('{0}/{1}', a, b)Positional substitution; {{ escapes a brace
join(array, ', ')Flatten an array to a string

The two surprising semantics

First: && and || return an operand, not a boolean — which is why ${{ cond && 'a' || 'b' }} is the idiomatic ternary. Second: string comparison ignores case, so runner.os == 'linux' is true on Linux. Also worth knowing: in an if: you may omit ${{ }} entirely, and a step with any if: that does not call a status function implicitly requires success of previous steps — which is why if: always() exists.

and the flags that control it
strategy:
  fail-fast: false        # default true: one failure cancels the rest
  max-parallel: 4
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [18, 20, 22]
    exclude:
      - os: windows-latest
        node: 18
    include:
      - os: ubuntu-latest
        node: 22
        experimental: true      # ADDS a property to an existing combination
      - os: macos-latest
        node: 23                 # creates a NEW combination

fail-fast: false is usually what you want during development and usually not what you want in a required check — with it off you get the full picture of what broke, at the cost of running every remaining job after the first failure.

Runners and what they cost

A fresh virtual machine per job, priced by the minute and by the platform.

RunnerBilling multiplierUse for
ubuntu-latest1×Nearly everything
windows-latest2×Windows-specific builds and tests
macos-latest10×Apple platforms only — and keep the matrix small
Larger hosted runnersHigher, by core countBuilds that are genuinely CPU or memory bound
Self-hostedNo minutes billedSpecial hardware, private networks; you own the security

Public repositories get free minutes on standard runners; private ones consume an allowance. The multipliers are why a three-OS matrix costs about thirteen times a Linux-only one rather than three times — the demo above prices it.

containers and services
jobs:
  test:
    runs-on: ubuntu-latest
    container: node:20-bookworm          # run the steps inside this image
    services:
      postgres:                           # a sidecar container, reachable by name
        image: postgres:16
        env: { POSTGRES_PASSWORD: postgres }
        options: >-
          --health-cmd pg_isready --health-interval 10s --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test
        env:
          DATABASE_URL: postgres://postgres:postgres@postgres:5432/postgres
Self-hosted runners and untrusted code

A self-hosted runner is a persistent machine on your network. A workflow triggered by a fork's pull request would run a stranger's code on it, and unlike a hosted runner it is not destroyed afterwards — so anything installed or written persists into the next job. Never enable self-hosted runners for public repositories without ephemeral, isolated runners, and restrict which workflows may use them.

Debugging workflows

The loop is slow, so make each iteration count.

from the terminal
$ gh workflow list
$ gh workflow run ci.yml -f environment=staging      # trigger workflow_dispatch
$ gh run list --workflow ci.yml --limit 5
$ gh run view 1234567 --log-failed                   # only the failing step's log
$ gh run rerun 1234567 --failed --debug               # rerun with debug logging on
$ gh run watch                                        # follow the current run

The short version

Chapter 20 in eight lines

  • Event → workflow → job → step. Each job is a fresh machine; steps in a job share a filesystem, jobs share nothing.
  • concurrency with cancel-in-progress stops paying for runs nobody will read.
  • pull_request from a fork has no secrets, on purpose. pull_request_target has them — and checking out the PR's code inside it hands them to a stranger.
  • Pass data with $GITHUB_OUTPUT (steps and jobs), $GITHUB_ENV and $GITHUB_PATH (later steps only), or artifacts. export does nothing beyond its own step.
  • && and || return operands, not booleans — hence cond && 'a' || 'b' as the ternary.
  • String comparison is case-insensitive, and if: needs no ${{ }}.
  • include merges into an existing combination when its overlapping keys match, and otherwise adds a new one.
  • Billing multipliers are 1× Linux, 2× Windows, 10× macOS, so matrix width costs more than it looks.

Check yourself

A step runs export VERSION=1.2.3 and the next step echoes an empty string. Why, and what are the two fixes?

Each run: step is a separate shell invocation, so its exported variables die with it. The environment for each step is assembled before it starts. Fixes: write to the special file — echo "VERSION=1.2.3" >> "$GITHUB_ENV" — which affects later steps but not the current one; or write a step output with >> "$GITHUB_OUTPUT" and reference it as steps.<id>.outputs.version, which is also the only form that can cross into another job via outputs:.

What does ${{ github.event_name == 'push' && 'deploy' || 'skip' }} evaluate to on a pull request, and why is that idiom possible?

'skip'. The operators return operands rather than booleans: false && 'deploy' yields false, and false || 'skip' yields 'skip'. That is why the pattern works as a ternary — and also why it breaks subtly if the "true" branch can itself be falsy, since true && '' || 'skip' gives 'skip' rather than the empty string you asked for. The evaluator above shows each operand's value.

Your matrix has os: [ubuntu, windows] and node: [18, 20], plus include: {os: ubuntu, node: 20, coverage: true}. How many jobs run?

Four, not five. The include entry's overlapping keys (os and node) match an existing combination, so it adds the coverage property to that job rather than creating a new one. Change it to node: 22 and you get five jobs, because nothing matches and it becomes a new combination. This is the single most misunderstood part of matrix configuration, and the calculator above shows both behaviours side by side.

A contributor's PR needs a secret to run the integration tests. What do you do?

Not pull_request_target with a checkout of their head — that runs their code with your secrets. Options, roughly in order: run the secret-requiring tests only on the merge to main and let the PR run the rest; split into two workflows where an unprivileged job builds and uploads an artifact and a privileged workflow (triggered by workflow_run) consumes only that artifact; use an environment with required reviewers so a maintainer must approve before the privileged job runs; or have a maintainer push the branch to the main repository, where it is no longer a fork PR.
