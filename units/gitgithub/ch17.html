Submodules, subtrees, LFS and sparse checkout

Git was designed for a large tree of text edited by many people. Three situations break that assumption — a project made of other projects, a repository full of binaries, and a tree too big to check out — and Git has a distinct, awkward, useful answer to each. All four tools here are things you adopt reluctantly and then depend on.

Four problems, four tools

They get confused with each other constantly. They solve different things.

ProblemToolWhat it stores
This project depends on that repository, at a specific commitSubmoduleA pointer: one commit hash of another repository
I want another project's code inside mine, in my historySubtreeThe actual files, merged into a subdirectory
My repository is full of large binary filesLFSA small text pointer in Git; the bytes elsewhere
The tree is too large to check out or cloneSparse checkoutNothing extra — it limits what lands in the working tree

Two of these have real alternatives worth considering first. A submodule is often better replaced by a published package with a version number, and LFS is often better replaced by not committing the artefact at all. Reach for these when the alternative genuinely does not fit.

Submodules

Chapter 2 met mode 160000. This is what it is for.

A submodule is one tree entry with mode 160000 — a gitlink — whose hash is a commit in a different repository. Your repository stores that hash and nothing else: no files, no history, just "at this path, that commit of that project".

what it looks like in the object store
$ git submodule add https://github.com/acme/shared vendor/shared
$ git cat-file -p HEAD^{tree}
100644 blob a45bd4f...    README.md
040000 tree 2b3c4d5...    src
160000 commit 9f8e7d6...  vendor/shared     <- a gitlink, not a tree

$ cat .gitmodules
[submodule "vendor/shared"]
	path = vendor/shared
	url = https://github.com/acme/shared

.gitmodules is an ordinary tracked file mapping paths to URLs; the commit hash lives in the tree, not there. That split is why cloning needs two steps: read .gitmodules to know where to fetch from, then check out the commit the gitlink names.

the commands
$ git clone --recurse-submodules <url>      # clone and populate in one step
$ git submodule update --init --recursive    # after an ordinary clone
$ git config --global submodule.recurse true # make pull/checkout update them too

$ git submodule status                        # ' ' ok, '+' different, '-' not initialised
$ git submodule foreach 'git switch main'      # run a command in each
$ git submodule update --remote vendor/shared  # move the pointer to the branch tip
$ git submodule deinit vendor/shared            # stop populating it
$ git rm vendor/shared                          # remove it properly

Inside a submodule you are on a detached HEAD by default (chapter 4), because the parent names a commit, not a branch. Commit there and switch away, and your work is unreferenced — which is the first of several ways submodules lose work.

Subtrees

The other project's files, actually in your repository.

A subtree merge copies another repository's tree into a subdirectory of yours, as real commits in your history. There is no pointer, no second clone step, and no way for a colleague to have the wrong version — they get whatever your commit contains.

subtree
$ git subtree add --prefix=vendor/shared https://github.com/acme/shared main --squash
$ git subtree pull --prefix=vendor/shared https://github.com/acme/shared main --squash
$ git subtree push --prefix=vendor/shared git@github.com:me/shared.git my-changes
$ git subtree split --prefix=vendor/shared -b extracted    # pull a directory out as its own history

The honest summary: submodules are correct and unfriendly; subtrees are friendly and imprecise. If the dependency has releases, a package manager beats both.

Git LFS

Chapter 2 explained why a deleted 300 MB file is still in every clone. LFS is the answer.

Git stores every version of every file forever, and binaries do not delta-compress — so a 5 MB image edited twenty times adds 100 MB to every clone, permanently. Git LFS replaces the file's content in Git with a small text pointer and stores the bytes on a separate server, fetched only when needed.

what is actually committed
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 2516582

Three lines, 130-odd bytes. The substitution happens through Git's clean and smudge filters, configured by .gitattributes: on git add the clean filter replaces the binary with the pointer, and on checkout the smudge filter replaces the pointer with the binary.

setting it up
$ git lfs install                      # register the filters in your git config
$ git lfs track "*.psd" "*.mp4"        # writes to .gitattributes — commit that file
$ git add .gitattributes assets/hero.psd && git commit -m "Add hero art"

$ git lfs ls-files                      # what is stored in LFS
$ git lfs status
$ git lfs env                            # is it configured? where does it point?
$ git lfs fetch --recent                 # only recent versions, not all of history
$ git lfs prune                           # delete local copies you no longer need
$ git lfs migrate import --include="*.psd" --everything   # retrofit an existing repo
.gitattributes, written by lfs track
*.psd filter=lfs diff=lfs merge=lfs -text
*.mp4 filter=lfs diff=lfs merge=lfs -text

LFS pointer explorer

What is in the working tree, what is in Git, and what a clone downloads

The failure that looks like corruption

Clone an LFS repository on a machine without git-lfs installed and the smudge filter never runs — so your working tree contains the pointer text where the image should be. Nothing is broken and nothing warns you: the build fails with "invalid PNG", the designer's editor shows a garbled file, and git status is clean. git lfs install && git lfs pull fixes it. Deliberately skipping the download is GIT_LFS_SKIP_SMUDGE=1, which is what CI jobs that do not need the assets should use.

What LFS costs: your host must support it (GitHub does, with quotas), history rewrites become harder, and git lfs must be installed everywhere including CI. What it does not fix: binaries still cannot be merged, so two people editing one asset is still a lock-or-lose problem — which is why game studios stay on Perforce (chapter 1).

Sparse checkout

Every commit, only some of the files on disk.

Sparse checkout does not change what your repository contains — it changes what gets written to the working tree. Combined with a partial clone (chapter 15), it means the blobs for the paths you skipped are never downloaded at all.

the monorepo setup
$ git clone --filter=blob:none --sparse https://github.com/acme/monorepo
$ cd monorepo
$ git sparse-checkout set services/payments libs/common

$ git sparse-checkout list
$ git sparse-checkout add services/billing
$ git sparse-checkout reapply       # after a checkout that confused it
$ git sparse-checkout disable        # back to a full working tree

Cone mode (the default since 2.37) restricts patterns to whole directories, which lets Git decide inclusion by directory rather than testing every path against a pattern list — the difference between a fast and an unusable git status on a large tree. --no-cone accepts full gitignore-style patterns and is correspondingly slower.

and the rest of the large-repo toolkit
$ git config core.fsmonitor true       # watch the filesystem instead of scanning it
$ git config feature.manyFiles true     # index v4, untracked cache, fsmonitor
$ git maintenance start                  # background gc, commit-graph, prefetch
$ git commit-graph write --reachable      # precomputed graph: faster log and merge-base

$ scalar clone https://github.com/acme/monorepo    # all of the above, preconfigured

scalar ships with Git and is the opinionated bundle: partial clone, sparse checkout in cone mode, filesystem monitor, commit-graph and scheduled maintenance, applied for you. On a repository where git status takes ten seconds, it is the first thing to try.

What sparse checkout does not do

It does not hide files from commands that work on the repository rather than the working tree: git log, git grep <rev> and git diff between commits still see everything, because all of that data is still there. It also interacts with --skip-worktree index flags, so a file both sparse-excluded and locally modified can behave strangely — the reason git sparse-checkout reapply exists.

The short version

Chapter 17 in seven lines

  • A submodule is a gitlink: mode 160000, one commit hash of another repository, plus a URL in .gitmodules.
  • Its defining failure is pushing the parent without pushing the submodule — nobody else can clone. push.recurseSubmodules = check prevents it.
  • Inside a submodule you are detached by default, so commits there are easy to lose.
  • A subtree puts the other project's files in your history: friendlier, larger, and imprecise about versions. A package manager beats both when there are releases.
  • LFS swaps a file's content for a 130-byte pointer using clean and smudge filters; the bytes live on a separate server and are fetched on demand.
  • Without git-lfs installed, checkout leaves the pointer text in your working tree and nothing warns you.
  • Sparse checkout limits the working tree, not the repository; with --filter=blob:none the skipped blobs are never downloaded. scalar clone bundles the whole large-repo configuration.

Check yourself

A colleague reports that git clone --recurse-submodules fails with "did not contain 9f8e7d6". What did you do?

Committed a new submodule pointer in the parent and pushed the parent, without pushing the submodule's commit to its own remote. The gitlink names a commit that exists only in your local copy of the submodule, so their clone fetches the submodule and cannot find it. Fix: push the submodule. Prevent: git config --global push.recurseSubmodules check, which refuses the parent push while the pointer is unpushed, or =on-demand, which pushes both.

Your designer says the logo file in their checkout is "three lines of text". Diagnose it.

The repository uses LFS and their machine has no git-lfs, so the smudge filter never ran and the working tree holds the pointer file that is genuinely what Git stores. It is not corruption and git status is clean, because the pointer is the committed content. git lfs install then git lfs pull replaces the pointers with real files. The same three lines appear deliberately when GIT_LFS_SKIP_SMUDGE=1 is set, which is what a CI job that does not need the assets should do.

You need one directory of a 40 GB monorepo and full git log for it. Which combination, and why not --depth 1?

git clone --filter=blob:none --sparse then git sparse-checkout set <dir>. Every commit and tree arrives, so log, blame within what you have, bisect and merge-base all work; only the file contents you never check out are skipped. --depth 1 would be smaller but discards the history you explicitly need, and it breaks merge-base — which chapter 15's model and its CI warning covered. On a tree this size add core.fsmonitor and a commit-graph, or just use scalar clone.

When would you choose a subtree over a submodule?

When the other project is something you vendor rather than co-develop, and you care more about contributors not tripping over an extra step than about pinning a reviewable version. Subtree files are in your history, so a clone is complete with no --recurse-submodules, no empty directories and no unpushed-pointer failure. The costs are that your repository grows by their project, updates are a merge rather than a one-line hash bump, and pushing changes back upstream is genuinely fiddly. If the dependency publishes versioned releases, prefer a package manager to either.
