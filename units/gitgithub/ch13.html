Cherry-pick, revert and backports

Merge and rebase move whole lines of work. Sometimes you want one commit: this fix, on that release branch, and nothing else. Cherry-pick is a three-way merge in disguise — which explains its conflicts, its new hashes, and the interesting question of how Git later recognises that the same change now exists in two places.

24 min2 demos7 sections4 self-checks

Cherry-pick is a merge

Not a patch application. The distinction explains everything else.

To apply commit C onto your branch, Git performs a three-way merge with:

  • base = C's parent — the state the change was written against
  • ours = your current HEAD
  • theirs = C itself

So it uses the machinery of chapter 10, gets chapter 11's conflicts and marker styles, and produces a new commit: same message and author, new committer, new parent, new hash. It is not git apply — it does not need the context lines to match textually, because a merge can reconcile changes around them.

the basic move
$ git switch release/2.4
$ git cherry-pick 8f3d2a1
[release/2.4 4c5d6e7] Fix expiry off-by-one
 Date: Mon Sep 1 09:14:22 2025 +0100
 1 file changed, 2 insertions(+), 1 deletion(-)

$ git log -1 --format='%h  author:%an  committer:%cn'
4c5d6e7  author:Priya Raman  committer:You

Note the Date: line in the output — Git prints it precisely because the author date is older than the commit you just made, which is the visible sign that this content came from elsewhere.

$ git cherry-pick A..B                          # every commit after A up to B

$ git cherry-pick -n A..B && git commit -m "Backport auth fixes"   # squash them

$ cat .git/sequencer/todo      # what is left to pick, during a multi-commit run
-x is not the default, and should be

Without it, a backported commit on a release branch has no record of where it came from, so nobody can answer "is this fix the same as the one on main, or a different attempt?" without reading diffs. The trailer -x adds costs nothing and turns that into a hash lookup. Git leaves it off by default because in a private rearrangement the reference would point at a commit that no longer exists.

How Git spots the same change twice

Different hashes, identical content — and a fingerprint that notices.

A cherry-picked commit has a different hash from its original, so reachability cannot tell you the change was already applied. Git solves this with a patch id: a hash of the diff itself, with whitespace removed and position information dropped. Two commits with the same patch id introduce the same change, whatever their messages, authors or hashes.

the commands built on it
$ git cherry -v main release/2.4
- 4c5d6e7 Fix expiry off-by-one        # '-' : an equivalent patch is already in main
+ 9a8b7c6 Bump version to 2.4.1        # '+' : not in main, would need picking

$ git log --oneline --cherry-mark --left-right main...release/2.4
= 4c5d6e7 Fix expiry off-by-one         # '=' : present on both sides
> 9a8b7c6 Bump version to 2.4.1
< 7e2a91c Add rate limiting

$ git log --cherry-pick main...release/2.4    # omit the equivalent ones entirely
$ git show 8f3d2a1 | git patch-id --stable    # the fingerprint of one commit

Patch equivalence detector

Real SHA-1 over the normalised diff — the fingerprint is computed, not stored

Where equivalence detection stops working

A patch id is a hash of the diff, so any change to the diff changes it. If a backport had to be adapted — a renamed function, a different variable, an extra guard for the older code — its patch id differs and git cherry reports it as missing forever. That is the practical argument for -x: the trailer survives adaptation, and a grep for the original hash answers the question that the fingerprint no longer can.

The duplicate commit problem

What happens when a cherry-picked branch is later merged.

You cherry-pick a fix from feature onto main because it was urgent. A week later feature is merged. What happens?

Usually: nothing bad. The merge compares both sides against the base; your cherry-pick and their original commit produce the same content, so the region agrees and merges cleanly — chapter 10's "both sides made the same change" case. The cost is cosmetic: main's history now contains the change twice, under two hashes, and git log shows two commits with the same message.

Occasionally: a conflict. If the cherry-pick was adapted, or if either side was subsequently modified, the two versions no longer agree and you resolve a conflict caused entirely by your own earlier shortcut.

Instead of cherry-picking...ConsiderBecause
...one commit off a branch you will merge anywayMerge the branch early, or split the fix onto its own branch and merge thatNo duplicate, no adapted copy to maintain
...a series of commits to a new basegit rebase --onto (ch. 12)Moves the whole series at once, keeps the order
...between two unrelated repositoriesgit format-patch and git am (ch. 7)Preserves authorship across repositories with no shared history
...fixes upward from a release branch to mainMerge the release branch into main periodicallyGit tracks what has been merged; nobody has to remember

The last row is the standard alternative to backporting entirely: fix on the oldest supported branch, then merge that branch forward into the next, and so on up to main. Merges are tracked, so "did this fix reach main?" is answerable by reachability rather than by fingerprints. The cost is that release branches then carry merge commits, and every fix must be written against the oldest code.

Cherry-picking and reverting merges

Both need -m, and for the same reason.

A merge commit has two parents, so "the change this commit introduced" is undefined until you say relative to which parent. -m 1 means "treat the first parent as the base", which for a normal merge means "the change the merged branch brought in".

merges, both directions
$ git cherry-pick -m 1 <merge-sha>     # apply everything the branch brought in
$ git revert -m 1 <merge-sha>           # undo everything the branch brought in

$ git log --oneline <merge-sha>^1..<merge-sha>^2    # what the second parent added

Cherry-picking a merge is usually the wrong tool: it squashes an entire branch's worth of change into one commit on the target, losing the individual commits and their authorship. Picking the branch's commits as a range, or merging the branch itself, is nearly always better.

Reverting a merge, again

Chapter 8's trap is worth repeating here because backporting is where it bites hardest: git revert -m 1 undoes a merge's content but leaves the merge in the graph, so the branch still counts as merged and re-merging brings in nothing. On a release branch that means a fix can be reverted, later "re-merged", and silently not present. Revert the revert, or cherry-pick the individual commits afresh.

Maintaining a release line

The workflow, and the bookkeeping it demands.

The rule from chapter 9: fix on main first, then backport. The failure mode of that direction is a forgotten backport, which is detectable. The failure mode of the reverse is a fix missing from the version you are about to ship, which is not.

the loop
# 1. what is on main that this release line does not have?
$ git cherry -v release/2.4 main | grep '^+'

# 2. take the ones that qualify — bug fixes, not features
$ git switch release/2.4
$ git cherry-pick -x 8f3d2a1

# 3. if it needs adapting, say so in the message
$ git cherry-pick -x -e 7e2a91c

# 4. tag and publish
$ git tag -a v2.4.2 -m "Release 2.4.2"
$ git push origin release/2.4 --follow-tags

# 5. confirm afterwards
$ git tag --contains 8f3d2a1        # which releases now carry this fix?
$ git branch --contains 8f3d2a1     # which lines have it at all?

Automating the bookkeeping

Teams that backport routinely stop doing it by hand. The common patterns:

  • A backport/2.4 label on the pull request, and a bot that opens the cherry-pick PR when it merges.
  • A scheduled job running git cherry -v release/2.4 main and posting anything with a fix: prefix that is missing.
  • A required checklist item on every bug-fix PR: which supported lines need this?

All three are chapter 22 material. The Git-level point is that git cherry and --contains are the primitives any of them are built on.

When a pick conflicts

Same mechanics as a merge, with one useful difference.

during a conflicted pick
$ git cherry-pick 8f3d2a1
error: could not apply 8f3d2a1... Fix expiry off-by-one
hint: After resolving the conflicts, mark them with
hint: "git add/rm <pathspec>", then run "git cherry-pick --continue".

$ git status                       # 'You are currently cherry-picking commit 8f3d2a1'
$ git show 8f3d2a1                 # what was the change supposed to be?
$ git diff                          # what does the conflict look like now?
# ...resolve, then:
$ git add src/auth/token.js && git cherry-pick --continue

Unlike a merge, --ours here is your branch (the target) and --theirs is the commit being picked — the same orientation as a merge, not the inverted one from rebase. The reason is that HEAD stays on your branch throughout; nothing is checked out from elsewhere.

CommandEffect
--continueCommit the resolution and carry on with any remaining picks
--skipAbandon this commit, continue with the rest of the range
--abortUndo everything, including commits already made in this run
--quitStop the sequencer but keep what has been applied so far

--quit versus --abort is worth remembering when a range of ten picks conflicts on the eighth: --abort throws away the seven that worked, --quit keeps them and leaves you to deal with the rest.

The short version

Chapter 13 in seven lines

  • Cherry-pick is a three-way merge with the commit's parent as the base — not a textual patch application. Hence conflicts, and hence a new hash.
  • Author and message are preserved; you become the committer. Always use -x on anything published, so the copy records its origin.
  • A patch id is a hash of the diff with whitespace and position removed, so the same change has the same id under a different hash. git cherry and --cherry-mark are built on it.
  • Adapting a backport changes its patch id, so equivalence detection stops working — which is exactly when the -x trailer earns its keep.
  • Cherry-picking then merging the same branch is usually clean (both sides made the same change) and leaves a cosmetic duplicate.
  • Merges need -m 1 for both cherry-pick and revert, because "the change" is undefined without a base.
  • Fix on main, backport down, verify with git cherry -v and git tag --contains. Or invert it: fix on the oldest branch and merge forward, so reachability does the bookkeeping.

Check yourself

You cherry-pick a commit whose context has drifted a lot on the target branch, and it applies cleanly. git apply of the same patch fails. Why?

Because they are different operations. git apply is textual: it needs the context lines to be present, at the stated position or a nearby offset (ch. 7). git cherry-pick runs a three-way merge with the commit's parent as base, so it reconciles your drift against the change the way a merge would — it can succeed whenever the drift and the change touch different lines, even if no context matches textually. The same reasoning is why git apply --3way narrows the gap.

git cherry -v release/2.4 main shows a fix as + (missing), but you know it was backported months ago. What happened?

The backport was adapted — a renamed symbol, an extra guard, different indentation of surrounding code that ended up inside the diff — so its patch id no longer matches the original's, and equivalence detection cannot see it. Whitespace alone would not do it (patch ids ignore whitespace), so something about the change itself differs. Confirm by grepping for a (cherry picked from commit …) trailer, which is why -x matters, or by comparing the two diffs by hand.

A range of eight cherry-picks conflicts on the sixth. You resolve nothing and want to keep the five that worked. Which command?

git cherry-pick --quit. It stops the sequencer and leaves the branch where it is, so the five completed commits stay. --abort would roll the branch back to where it started, discarding all five, and --skip would drop the sixth and continue with the remaining two — which may be what you want instead, if the sixth is genuinely not applicable to this branch.

Your team supports 2.3, 2.4 and main. Argue for merge-forward over cherry-picking, and say what it costs.

Merge-forward means fixing on the oldest affected branch (2.3), then merging 2.3 into 2.4 and 2.4 into main. Every fix's presence becomes a reachability question — git branch --contains answers definitively, no patch ids, no forgotten backports, no adapted copies drifting apart. The costs are real: every fix must be written against the oldest supported code, which may be structured quite differently; release branches accumulate merge commits; and a fix that is only relevant to newer code has to be handled the other way anyway. Teams with two or three live versions usually merge forward; teams with one occasionally-patched old release usually cherry-pick.
