Undoing anything

"How do I undo this" is the most-asked Git question, and it has about nine answers because there are about nine different things people mean. Every one of them is decided by three questions: which of the three trees is wrong, has anyone else seen it, and do you want the content back or gone. Answer those and the command follows.

The three questions

There is no general "undo" because there is no single thing being undone.

  1. What is wrong? Edits on disk, content in the index, the last commit, an older commit, or where the branch is pointing.
  2. Has it been published? If others have the commit, you must add a new commit rather than remove the old one.
  3. Do you want the content back? "Undo the commit but keep my work" and "make it never have happened" are different commands.

The one genuinely unrecoverable loss

Uncommitted, unstaged edits. If you have never run git add and never committed, the content exists only in your working tree, so git restore or git checkout -- overwrites it with nothing to fall back on — no object, no reflog, no recovery. Everything else in this chapter is reversible. Staged content is slightly better off: git add wrote a blob to the object store, so git fsck --unreachable can sometimes find it.

Undoing uncommitted work

Two commands, four directions, one that bites.

restore
$ git restore src/app.js                 # index → working tree: discard my edits
$ git restore --staged src/app.js        # HEAD → index: unstage, keep my edits
$ git restore --staged --worktree src/app.js    # HEAD → both: forget everything
$ git restore --source=HEAD~2 src/app.js        # an older version, into the working tree
$ git restore .                          # every tracked file, from the index

The old spelling of all of these is git checkout, which is why every answer written before 2019 tells you to run git checkout -- file. It still works; restore exists because checkout could not be made safe while it also meant "switch branch".

clean — for untracked files only
$ git clean -n                # dry run: what would be deleted
$ git clean -nd               # ...including untracked directories
$ git clean -fd               # actually delete them
$ git clean -fdx              # ...and ignored files too. Read the next paragraph first.
$ git clean -fdi              # interactive: choose what goes
Trap: -x deletes your .env

git clean -fdx removes files matched by .gitignore, which is exactly where teams keep local credentials, database files and build caches. It is the right command on a CI runner and a bad habit on a laptop. Always run -nd or -ndx first and read the list; clean deletes from the file system, so there is no object, no reflog and no undo.

reset, all five modes

Everyone knows three. The other two are the safe ones.

ModeHEADIndexWorking treeBehaviour
--softmovesuntoucheduntouchedThe commit's content stays staged, ready to recommit

--hardmovesresetoverwrittenUncommitted work is destroyed; untracked files survive

reset in practice
$ git reset --soft HEAD~          # "let me redo that commit"
$ git reset HEAD~                 # "unmake the commit, I'll re-stage"
$ git reset --hard origin/main    # "make my branch identical to the remote"
$ git reset --keep HEAD~2         # "move back, but refuse if it costs me work"
$ git reset --hard ORIG_HEAD      # "undo that merge/rebase entirely"

--keep deserves to be better known: it does what people mean by --hard most of the time — move the branch, bring the tree along, but stop with an error instead of silently eating uncommitted changes.

reset with a path is a different command

git reset <commit> moves HEAD. git reset <commit> -- <path> does not move HEAD — it copies that path from the commit into the index, i.e. it unstages. Same word, unrelated operations, which is precisely the confusion git restore --staged was introduced to remove. Prefer restore for paths and keep reset for moving branches.

revert: undo by adding

The only correct answer for anything already published.

git revert computes the inverse of a commit's diff and commits it. History grows; nothing is rewritten; everyone's clone stays compatible.

revert
$ git revert 8f3d2a1                 # one commit, one new inverse commit
$ git revert --no-edit 8f3d2a1        # accept the generated message
$ git revert -n 8f3d2a1 7e2a91c       # stage the inverses, commit them together
$ git revert OLD..NEW                 # a range, reverted newest-first
$ git revert --abort                  # a revert can conflict, like any merge

Reverting a merge

A merge commit has two parents, so "the inverse of this commit" is ambiguous until you say which side to keep:

reverting a merge
$ git revert -m 1 <merge-sha>     # keep the first parent: undo what was merged in
$ git revert -m 2 <merge-sha>     # keep the second parent: rarely what you want
The revert-a-merge trap

Reverting a merge undoes the content but not the graph: the merge commit is still there, so as far as Git is concerned that branch is still merged. Re-merging the same branch later brings in nothing, because there is nothing new to bring. The fix when you want the work back is to revert the revert (git revert <revert-sha>), which is legitimate and reads oddly in the log — or to rebase the original work onto a new branch and merge that instead.

What rewriting does to other people

The rule everyone repeats, demonstrated mechanically.

"Don't rewrite published history" is usually justified with a vague warning about confusing your colleagues. The actual failure is specific and worth seeing: their clone still contains the commit you removed, their next git pull merges it back, and their next push restores it to the shared branch. Your deletion is silently undone.

When force-pushing is fine

On a branch only you use — your own feature branch before review, or after a rebase you were asked to do. Always with --force-with-lease, which refuses if the remote moved since your last fetch, so you cannot clobber a colleague's commit you never saw. Chapter 12 covers the mechanics; the line to hold is: rewrite your own branch freely, never a shared one.

Recovery recipes

Chapter 4 built the reflog. Here is what to do with it at 2am.

the two commands to try first, always
$ git reflog                       # where has HEAD been? 90 days of history
$ git status                        # what state is Git in right now?

# then, before anything drastic, take a snapshot you cannot lose
$ git branch panic-$(date +%s)      # a ref pointing at wherever you are now

That last line is the single most valuable habit in this chapter. Creating a branch costs 41 bytes and makes the current position permanently findable, which turns almost any subsequent mistake into an inconvenience.

recovering a dropped stash, in full
$ git fsck --unreachable | grep commit
unreachable commit 7e2a91c4d5f6a8b9c0d1e2f3a4b5c6d7e8f9a0b1

$ git show 7e2a91c --stat          # a stash looks like a merge commit with your work
$ git stash apply 7e2a91c          # apply it as if it were still on the stack

The short version

Chapter 08 in eight lines

  • Three questions decide everything: which tree is wrong, has it been published, do you want the content back.
  • restore moves content between HEAD, index and working tree; reset moves the branch. Use restore for paths.
  • reset has five modes, not three: --keep does what people usually mean by --hard, but refuses rather than destroying uncommitted work.
  • git clean -fdx deletes ignored files — including the .env nobody has a copy of. Dry-run first, every time.
  • Anything published gets revert: a new commit, no rewriting, everyone stays compatible.
  • Reverting a merge undoes the content but leaves the graph, so the branch still counts as merged; revert the revert to bring it back.
  • Rewriting a shared branch fails mechanically, not socially: a colleague's pull merges your removed commit back and their push republishes it.
  • Before anything drastic: git branch panic-$(date +%s). Then git reflog. Uncommitted, never-staged edits are the only thing truly unrecoverable.

Check yourself

You committed a debug line to main and pushed. Your colleague has already pulled. What do you run, and what happens if you use reset --hard and force-push instead?

git revert <sha> then push — a new commit that undoes the change, compatible with every existing clone. If you reset and force-push, your colleague's clone still contains the commit; their next git pull merges origin/main into their branch, keeping the commit as an ancestor, and their next push puts it back on the shared branch. You would also have rewritten a commit anyone with a running build might be sitting on. The simulator above walks through exactly that sequence.

What is the difference between git reset --hard HEAD~ and git revert HEAD in terms of the object graph?

reset --hard HEAD~ moves the branch ref backwards; the commit still exists as an object but nothing points at it, so it is unreachable and will eventually be pruned. History looks as though it never happened. revert HEAD leaves the original commit exactly where it is and adds a new commit whose diff is the inverse, so the tree matches the earlier state while the record of both the change and its undoing remains. Same resulting files, opposite treatment of history.

You ran git reset --hard with uncommitted work in three files. One had been staged, two had not. What can you recover?

The staged one, probably: git add writes a blob into the object store immediately, so git fsck --unreachable can list it and git cat-file -p <blob> prints the content — you just have to identify which blob it is. The two unstaged files are gone: their content never entered the object store, so there is nothing to find. This asymmetry is the practical argument for staging work-in-progress you care about, or stashing rather than resetting.

A feature branch was merged, then the merge was reverted because it broke production. The bug is fixed. Why does re-merging the branch do nothing, and what do you do?

Because the merge commit is still in history, so the branch's commits are already ancestors of main — there is nothing left to merge, and Git says "Already up to date". The content was undone by a separate revert commit, which the graph knows nothing about. Either revert the revert (git revert <revert-sha>) and then merge the new fix on top, or rebase the branch's commits onto current main as new commits and merge that. The first is honest and cheap; the second gives a cleaner story.
