Orientation: what Git actually is

Most people learn Git as a list of spells. It works until the day it doesn't, and then there is nothing underneath to reason with. Git is roughly five ideas, and the commands are a thin and occasionally inconsistent skin over them. This chapter installs the first idea and sets up your machine properly, once.

The problem version control solves

Before the tool, the failure modes.

Every team that has ever written code without version control has independently reinvented the same folder:

the universal disaster
report.doc
report-v2.doc
report-v2-mark-edits.doc
report-FINAL.doc
report-FINAL-actually.doc
report-FINAL-actually (Priya's copy).doc

That folder is a version control system. A terrible one, but it is trying to answer the same questions any real one answers. Naming them makes it obvious what Git has to be able to do:

The questionWhat the tool must storeWhere this unit answers it
What did this look like last Tuesday?Complete states, addressable by time or nameCh. 2, 6
Who changed this line, and why?Authorship and intent attached to each changeCh. 5, 6
Can two people edit at once?Divergent lines of work, plus a way to rejoin themCh. 9–12
Which change broke the tests?An ordered, bisectable historyCh. 23
Can I undo this safely?Immutable old states that a mistake cannot overwriteCh. 8
Is this change good?A reviewable unit smaller than "the whole project"Ch. 16, 19
What is deployed right now?Names pinned to exact statesCh. 4, 9

Notice how much of that is not about storing files. Storage is the easy part. The hard parts are identity (this state, exactly, forever), divergence (two people, one project), and recovery (unwinding without losing anything). Git's design is unusual because it takes identity as the foundation and derives the other two from it.

Centralised and distributed

Why "everyone has the whole thing" changes the ergonomics of everything.

In a centralised system — CVS, Subversion, Perforce, TFVC — there is one server that owns history. Your machine holds a working copy of one revision plus enough bookkeeping to talk to the server. Committing is a network operation, and so is looking at history.

In a distributed system — Git, Mercurial, Fossil — git clone copies the entire repository: every commit, every branch, all the way back. Your machine holds a complete, independent repository that happens to know about other copies. Committing is a local file-system operation.

Centralised (SVN, Perforce)Distributed (Git)
CommitNetwork round trip, immediately publicLocal write, published when you choose
View historyServer queryLocal, instant, works on a plane
BranchOften a server-side directory copyWriting 41 bytes to a file
Server diesHistory at risk if backups are staleEvery clone is a full backup
Access controlFine-grained, per directoryAll or nothing per repository
Exclusive file locksSupported, and the reason studios use PerforceNot really; painful for unmergeable binaries
Partial checkoutNatural — check out one subdirectoryBolted on later (sparse-checkout, partial clone)

The trade is real and still live. If your repository is 400 GB of uncompressible art assets that two artists must never edit simultaneously, Perforce is not a legacy choice, it is the right one. For source code, the distributed model won decisively, because cheap local branching changes how people work: you stop treating a branch as a ceremony and start treating it as a thought.

Where Git came from

In 2005 the Linux kernel lost free access to BitKeeper, the proprietary DVCS it depended on. Linus Torvalds wrote the first version of Git in about ten days, optimising for three things the kernel needed: speed on a huge tree, strong resistance to corruption or tampering, and support for thousands of contributors merging through a chain of maintainers. Those three constraints explain most of Git's design, including the parts that feel strange.

Snapshots, not differences

The one sentence that makes the rest of Git make sense.

Ask most people what a commit is and they will say "a change" or "a diff". That is how Subversion thinks, and it is how Git presents itself in git show, but it is not what Git stores.

A Git commit stores a complete snapshot of every tracked file. Not the change — the whole state. When a file did not change between two commits, Git does not store it twice; both commits point at the same stored copy, because content that is identical has an identical name (chapter 2 explains why). A diff is not a stored thing at all. It is computed on demand by comparing two snapshots.

This sounds wasteful and turns out not to be. It also has consequences you feel every day:

  • Checking out any commit costs the same, whether it is the newest or the ten-thousandth from the end. There is no chain to replay.
  • History cannot subtly rot. A snapshot either verifies against its name or it doesn't.
  • Branching and merging get cheap, because comparing two branches means comparing two complete states, not reconciling two chains of edits.
  • git log -p can be slow on huge histories, because those diffs are being generated as you scroll.

Delta chain versus snapshot store

Pick a version to restore and watch what each model has to read

The honest footnote

Git does delta-compress — inside packfiles, at the storage layer, when it garbage-collects. Two versions of a large file are not usually both stored in full on disk. But that is an implementation detail beneath the model, invisible to every command you run, and it can be undone and redone at any time without changing a single commit. The model is snapshots; the disk format is an optimisation. Chapter 2 opens the packfile.

The four places your work can be

Almost every Git command moves data between two of these.

Confusion about Git is nearly always confusion about where something currently is. There are four locations, and the whole command set is a map of the arrows between them.

Working tree
The ordinary files and folders you edit. Your editor knows only about this. Git regards it as scratch space — anything here that has not been committed is at risk.
Index (also: staging area, cache)
A single file, .git/index, listing exactly what the next commit will contain. This is Git's most distinctive and most misunderstood component, and the reason you can commit half of your changes.
Local repository
Everything under .git/objects and .git/refs: the permanent object store plus the pointers that give parts of it names. This is the actual repository. Delete the working tree and it survives; delete this and only the working tree remains.
Remote repository
Someone else's copy — usually on GitHub — that yours knows how to exchange objects with. Nothing is shared until you explicitly push, and nothing arrives until you explicitly fetch.

Two entries there deserve early attention. git fetch touches nothing you are working on — it is always safe. git pull is fetch followed by a merge or rebase, which is why it is the command that surprises people. Chapter 15 argues for making that split explicit.

A configuration worth keeping

Run this once. Every line has a reason, given below.

~/.gitconfig — the essentials
$ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"

$ git config --global init.defaultBranch main
$ git config --global pull.ff only              # refuse surprise merge commits on pull
$ git config --global push.default simple
$ git config --global push.autoSetupRemote true # 2.37+: first push needs no -u
$ git config --global fetch.prune true          # drop remote branches that were deleted

$ git config --global diff.algorithm histogram  # markedly better diffs than the default
$ git config --global merge.conflictstyle zdiff3  # 2.35+: shows the common ancestor
$ git config --global rerere.enabled true       # remember conflict resolutions
$ git config --global rebase.autosquash true
$ git config --global rebase.autostash true
$ git config --global commit.verbose true       # show the diff while writing the message

$ git config --global log.date iso
$ git config --global column.ui auto
$ git config --global help.autocorrect prompt   # "git stauts" offers to run status
pull.ff only
By default git pull creates a merge commit whenever your branch and the remote have both moved. Setting ff only makes Git stop and tell you instead, so you choose --rebase or an explicit merge. Some teams prefer pull.rebase true; either is better than the default. Chapter 15 makes the case.
diff.algorithm histogram
The default Myers algorithm sometimes produces diffs that shift a closing brace instead of showing the function you added. Histogram is a refined patience algorithm and produces noticeably more readable output on real code, at a small speed cost.
merge.conflictstyle zdiff3
Turns a two-way conflict block into a three-way one that also shows the common ancestor, so you can see what each side changed rather than guessing. Chapter 11 shows the difference on a real conflict; it is one of the highest-value settings here.
rerere.enabled
"Reuse recorded resolution." Git remembers how you resolved a conflict and replays it if the same conflict appears again — which it will, every time you rebase a long-lived branch.
help.autocorrect prompt
Offers the intended command instead of a lecture. Avoid the numeric form (help.autocorrect 20), which runs the guess automatically after two seconds.

Line endings, once and for all

The single most common source of "the whole file changed" diffs on mixed teams.

line endings
# Windows: check out CRLF, commit LF
$ git config --global core.autocrlf true

# macOS / Linux: never write CRLF into a commit
$ git config --global core.autocrlf input

Better still, stop relying on per-developer settings and commit a .gitattributes file so the repository itself decides. Chapter 23 covers attributes properly; the two-line version that solves 95% of cases:

.gitattributes
* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary

Two identities on one machine

Work email on work repositories, personal email everywhere else, decided by directory rather than by memory:

~/.gitconfig
[user]
	name = Your Name
	email = you@personal.example

[includeIf "gitdir:~/work/"]
	path = ~/.gitconfig-work
~/.gitconfig-work
[user]
	email = you@company.example
[commit]
	gpgsign = true

The trailing slash on gitdir:~/work/ matters — it means "and everything below". Verify with git config user.email inside a repository in each location.

Inspecting what you've got

git config --list --show-origin prints every setting in force with the file it came from — the fastest way to find the stray .git/config line overriding your global one. git config --global --edit opens the file directly, which is easier than a dozen --global invocations.

Your first repository, narrated

Six commands, and what each one actually did.

terminal
$ mkdir scratch && cd scratch
$ git init
Initialized empty Git repository in /home/you/scratch/.git/

git init created one directory, .git, and nothing else. Your files are untouched — Git is now watching this folder, and that is the entire installation. Deleting .git turns the project back into an ordinary folder, losing all history and nothing else.

terminal
$ echo "# Scratch" > README.md
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)

Untracked is a real state, not a warning. Git will never store a file you have not explicitly added — no automatic capture, no watching. This is why .gitignore exists to silence the noise rather than to prevent accidents.

terminal
$ git add README.md
$ git status --short
A  README.md

$ git commit -m "Add readme"
[main (root-commit) 8f3d2a1] Add readme
 1 file changed, 1 insertion(+)
 create mode 100644 README.md

Read that output closely, because it names four things you will meet again. main is the branch. root-commit means this commit has no parent. 8f3d2a1 is the short form of the commit's 40-character name. 100644 is the file's mode — regular, non-executable — one of only a handful Git records.

terminal
$ git log
commit 8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3 (HEAD -> main)
Author: Your Name <you@example.com>
Date:   Mon Sep 1 09:14:22 2025 +0100

    Add readme

$ ls .git
HEAD  config  description  hooks/  index  info/  logs/  objects/  refs/

Everything the repository knows is in those nine entries, and by the end of chapter 2 you will be able to explain all of them. Two are worth pointing at now: objects/ holds your content, and refs/ holds the names — including refs/heads/main, which is a file containing that commit hash and nothing else.

Porcelain, plumbing, and reading the manual

Git's own vocabulary for its two interfaces.

Git ships roughly 150 commands split into two layers, and the distinction is not decoration:

  • Porcelain — the human-facing commands: status, add, commit, log, merge. Output is formatted for reading and may change between releases.
  • Plumbing — the low-level commands the porcelain is built from: hash-object, cat-file, ls-tree, rev-parse, update-ref, rev-list. Output is stable, machine-readable, and deliberately joyless.

The practical rule: never parse porcelain output in a script. Either use plumbing, or use the machine-readable mode most porcelain commands offer.

scripting safely
$ git status --porcelain=v2 --branch     # stable, versioned, parseable
$ git rev-parse HEAD                     # full hash of the current commit
$ git rev-parse --abbrev-ref HEAD        # current branch name
$ git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/
$ git rev-list --count HEAD              # number of commits reachable from HEAD

Those five lines cover most of what CI scripts need, and none of them will break when Git changes its wording. Chapter 22 uses them heavily.

Finding answers in Git's own docs

help
$ git help rebase          # full manual page
$ git rebase -h            # one-screen summary of the flags
$ git help -g              # the guides: everyday, glossary, revisions, workflows
$ git help glossary        # precise definitions of every term in this unit
$ git help revisions       # the syntax of HEAD~3, main@{2}, A...B and friends

Two of those are unusually good. git help revisions is the reference for every way of naming a commit, which is the vocabulary chapter 6 is built on. git help glossary settles arguments — it is where terms like "index", "ref" and "fast-forward" are defined normatively rather than by folklore.

Reading a synopsis

In Git's manual pages, [] means optional, <> is a placeholder you replace, | means choose one, and ... means repeatable. So git reset [<mode>] [<commit>] tells you both arguments can be omitted — which is exactly why git reset alone does something surprising until you know the defaults.

The short version

Chapter 01 in seven lines

  • Version control exists to answer questions about identity, divergence and recovery. Storage is the easy part.
  • Git is distributed: every clone holds the complete history, so commits, branches and history browsing are local file operations, not network calls.
  • A commit stores a complete snapshot, not a diff. Unchanged files are shared between commits rather than duplicated. Diffs are computed when you ask for one.
  • Packfiles delta-compress at rest, but that is beneath the model and changes nothing you reason about.
  • Work lives in four places — working tree, index, local repository, remote — and nearly every command moves data between two of them.
  • Config is layered system → global → local → worktree → -c, last one wins; git config --list --show-origin shows you exactly which.
  • Porcelain is for humans and may change wording; plumbing is for scripts and doesn't. Use --porcelain=v2 or rev-parse in automation.

Check yourself

Your colleague says "Git only stores what changed, that's why it's efficient." What's wrong with that, and what's right about it?

Wrong at the model level: each commit references a full tree of every tracked file, and checking out an old commit reads that tree directly with no chain to replay. Right at the storage level: when Git packs objects it stores many of them as deltas against similar objects, so the disk usage resembles what they described. The distinction matters the moment you reason about performance — checkout cost does not grow with history depth, but git log -p cost does, because those diffs are being computed live.

You set user.email with --global, but commits still show the old address. Where do you look, in what order?

git config --list --show-origin | grep user.email. The likely culprit is a user.email in this repository's .git/config (local beats global), or an includeIf block pulling in a work config for this directory. Also possible: the commits already exist and carry the old address permanently — config changes are not retroactive, and fixing past commits means rewriting them (ch. 12).

Why is git fetch always safe to run, while git pull sometimes surprises people?

fetch only downloads objects and updates remote-tracking refs like origin/main. It never touches your branch, your index or your working tree, so there is nothing it can conflict with or overwrite. pull is fetch plus an integration step — a merge by default — which can create a merge commit you didn't ask for, or stop halfway with conflicts in your working tree. Setting pull.ff only converts that surprise into a clear error.

A CI script does git status | grep "nothing to commit" to check for a clean tree. Why is that fragile, and what would you write instead?

It parses porcelain output, whose wording is explicitly allowed to change between releases and varies with locale — set LANG=fr_FR and the grep silently fails, reporting dirty forever. Use a plumbing check instead: git diff --quiet && git diff --cached --quiet exits non-zero when there are changes, or test -z "$(git status --porcelain)" for a version that also catches untracked files.
