GitHub essentials

Everything until now was Git, which is a protocol and a data model. GitHub is a product built on top, and the parts worth learning properly are the ones that change behaviour rather than appearance: the permission model, the search syntax, and the handful of files in .github/ that quietly configure the whole repository.

Issues, labels and templates

A tracker whose main advantage is that it is next to the code.

Issues are cheap and unstructured by default, which is fine until you have a thousand. The structure worth adding, in order of value:

  • A label scheme with prefixes, so labels group and sort: type:bug, area:auth, prio:p1, status:blocked. Flat labels become unusable at about thirty.
  • Issue forms (.yml in ISSUE_TEMPLATE/), which produce real fields rather than a Markdown template people delete. Required fields mean bug reports arrive with a version number.
  • Milestones for "which release", which give a progress bar and a due date and are the only built-in grouping that is not a label.
  • Closing keywords in PR descriptions (chapter 5), so the tracker updates itself.
.github/ISSUE_TEMPLATE/bug.yml
name: Bug report
description: Something behaves incorrectly
labels: ["type:bug", "status:triage"]
body:
  - type: input
    id: version
    attributes:
      label: Version
      placeholder: "2.4.1"
    validations:
      required: true
  - type: textarea
    id: steps
    attributes:
      label: Steps to reproduce
    validations:
      required: true
  - type: dropdown
    id: severity
    attributes:
      label: Severity
      options: ["blocks release", "workaround exists", "cosmetic"]
Issues or Discussions

An issue has a state and should be closable by a change to the code. A discussion does not — it is for questions, ideas and announcements, and it can be marked as answered. Teams that use issues for everything end up with a hundred open "issues" nobody can close, which is a naming problem masquerading as a backlog.

Search and filter syntax

The highest-value five minutes on this page.

Every issue and PR list on GitHub is a query, and the query language is the same everywhere including the global search. Qualifiers are ANDed; a leading - negates.

Projects

A spreadsheet over issues, with the useful property that it stays in sync.

A Project is a set of items — issues, PRs, and free-text drafts — with custom fields you define, viewed as a table, a board or a roadmap. Its advantage over a spreadsheet is that the title, state, labels and assignees come from the issue itself, so it cannot go stale; its advantage over labels is that a field can be a number, a date or an iteration.

ConceptUse for
Single-select fieldStatus, workstream — anything a board column represents
Number fieldEstimate or size, with sum and average shown per group
Iteration fieldSprints, with automatic date ranges and a burn-down-shaped roadmap
ViewsSaved slice plus layout: "my team's current iteration, grouped by status"
Built-in workflowsAuto-add new issues matching a filter; set Status when an item closes

Where Projects earns its keep is a board that nobody has to update, because moving a card and closing an issue are the same event. Where it does not: it is not a planning tool with dependencies or capacity, and pretending otherwise is how teams end up maintaining both a Project and a spreadsheet.

Organisations, teams and permissions

The model people most consistently misremember.

Access to a repository is the maximum of everything that grants it: the organisation's base permission, every team you are in that has access, and any direct grant to you. Organisation owners are admins everywhere regardless. Outside collaborators get only their direct grants — no base permission, no team membership.

Repository roleAdds
ReadClone, pull, open issues and PRs, comment
TriageManage issues and PRs — label, assign, close, mark duplicate — but no push
WritePush, merge PRs, create branches and releases, run workflows
MaintainRepository settings short of destructive or security ones
AdminBranch protection, secrets, collaborators, transfer, delete

The security surface

Five features, all free on public repositories, all worth turning on.

FeatureDoesWatch out for
Dependabot alertsTells you a dependency has a known vulnerabilityNoise without triage; use it with a severity threshold
Dependabot updatesOpens PRs bumping dependenciesGroup them (groups: in dependabot.yml) or drown in PRs
Secret scanningDetects committed credentials, and with push protection blocks the pushDetection after the fact means the secret must still be rotated (ch. 23)
Code scanning (CodeQL)Static analysis as a required checkTune the query suite, or reviewers learn to ignore it
Private vulnerability reportingA private channel for reporters, and draft advisoriesNeeds SECURITY.md to tell people it exists

Push protection is the one that changes outcomes. Everything else tells you about a problem you already have; push protection stops the credential entering history at all, which is the only intervention that avoids a rotation. Chapter 23 covers what to do when it is already in there, and the short version is: rotate first, rewrite second.

The short version

Chapter 18 in seven lines

  • The settings that change behaviour: default branch, one merge method, auto-delete head branches, and visibility — which exposes all history, not just the current tree.
  • Files in .github/ configure the repository; an org-level .github repository supplies defaults for every repo that lacks its own.
  • Prefix your labels (type:, area:, prio:) and use issue forms so reports arrive with the fields you need.
  • Every issue list is a query. no:label, no:assignee and review-requested:@me are the three that change your day.
  • Permission is the maximum of base permission, team grants and direct grants; org owners are admins everywhere; outside collaborators get only direct grants.
  • Triage is the underused role: manage issues and PRs with no push access.
  • Secret scanning push protection is the one security feature that prevents rather than reports.

Check yourself

A contractor needs to triage issues but must never push code. What do you give them, and what would most people give them by mistake?

The Triage role, as an outside collaborator or via a team — it allows labelling, assigning, closing and marking duplicates with no write access to the code. Most people reach for Write because triage "obviously needs more than read", which hands over push and merge rights as well. Also check the organisation's base permission: if that is set to Write, every member already has push access to every repository and the role you assign this person is irrelevant.

Write the query for "open pull requests waiting on my review, excluding drafts, oldest first".

is:open is:pr review-requested:@me draft:false sort:created-asc. Points worth noting: is:pr is needed because issues and PRs share one index; review-requested:@me covers requests via a team you belong to as well as direct ones; and sort: orders rather than filters, so it never changes the match count. Save it as a bookmark — the demo above evaluates each qualifier separately so you can see which one is doing the work.

Someone made a private repository public "to share one file". What is the actual exposure?

Every commit ever made, including anything deleted in a later commit — chapter 2's point that removing a file changes only later trees. Any credential, customer data or internal URL that was ever committed is now public and must be treated as compromised: rotate first, then decide about rewriting history (chapter 23). Forks and caches may retain it regardless. Secret scanning will start reporting on it immediately, which is useful and also too late — push protection is what would have prevented it.

Your org has base permission Read, you are in a team with Write on this repo, and you have a direct grant of Triage. What can you do?

Everything Write allows — push, merge PRs, create releases. Permissions combine as a maximum, not a minimum or an override, so the direct Triage grant does not reduce anything; it is simply redundant. This trips people up when they try to restrict someone by giving them a lower direct role, which does nothing. To remove access you must remove it from every source: the team, the direct grant, and possibly the org base permission.
