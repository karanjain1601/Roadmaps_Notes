Stash, worktrees and parallel work

"I need to look at something else, but I am in the middle of this." Git has two answers, and most people only know the first. Stash hides your work; a worktree means you never have to. Both are more mechanical than they look — a stash is just commits, and a worktree is a second checkout sharing one object store.

A stash is commits

There is no special stash storage format. It is the object model again.

git stash creates two commits (three with -u) and points refs/stash at the top one:

looking at a stash as a graph
$ git stash push -m "half-done rate limiter"
Saved working directory and index state On feature: half-done rate limiter

$ git log --graph --oneline --all stash@{0}
*-.   9f8e7d6 On feature: half-done rate limiter      <- the stash commit (W)
|\ \
| | * 7d6c5b4 untracked files on feature              <- only with -u    (U)
| * 8e7d6c5 index on feature: 4b7c9e2 Add parser      <- the index state (I)
|/
* 4b7c9e2 Add parser                                  <- HEAD when you stashed

$ git cat-file -p stash@{0} | head -4
tree 2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e
parent 4b7c9e2...      # where you were
parent 8e7d6c5...      # the index
parent 7d6c5b4...      # untracked, if any

So a stash records the working tree and the index separately, which is why it can put both back exactly. The stack is the ref's reflog — stash@{0}, stash@{1} are reflog entries, not separate refs, which is why dropping the middle one renumbers the rest.

What actually gets stashed

Four options, and each changes both what is saved and what you are left with.

the options in words
$ git stash push                    # tracked changes, staged and unstaged
$ git stash push -u                 # ...and untracked files
$ git stash push -a                 # ...and ignored files too. Rarely what you want
$ git stash push --keep-index        # stash everything, but leave the index intact
$ git stash push --staged            # 2.35+: stash ONLY what is staged

--keep-index exists for one specific job: you have staged the change you want to commit, and you want to run the tests against only that change, without your other edits confusing the result. Stash with --keep-index, run the tests, commit, then pop.

--staged is the inverse and newer: it stashes the staged change and leaves everything else alone — the quickest way to set aside a coherent piece you are not ready to commit.

Each has bitten someone this week.

recovering a dropped stash
$ git fsck --unreachable | grep commit
unreachable commit 9f8e7d6...

$ git show 9f8e7d6 --stat      # a stash looks like a merge commit with your work
$ git stash apply 9f8e7d6      # apply it directly by hash

This works because git stash drop only removes a reflog entry — the commits stay until they are pruned, exactly as chapter 4 described. It is recovery, not magic, and it stops working after a couple of weeks.

Why a WIP commit is usually better

A stash is an unnamed, branchless, unpushable pile of work.

Stash is excellent for the two-minute interruption. For anything longer it compares badly with simply committing:

the WIP habit
$ git add -A && git commit -m "wip: rate limiter, buckets not wired up yet"
$ git switch main            # go do the other thing
# ...later...
$ git switch feature
$ git reset --soft HEAD~     # the commit dissolves back into a staged change
# or keep it and fold it in later:
$ git commit --fixup=HEAD~   # ch. 5, then rebase --autosquash before pushing

The one thing a WIP commit cannot do is survive a branch switch without being committed — which is precisely what stash is for, and precisely what a worktree makes unnecessary.

Worktrees: several checkouts, one repository

The feature that removes most of the need for stash.

git worktree add creates another directory with its own working tree, its own HEAD and its own index, sharing the original's object store and refs. No second clone, no duplicated history, no network.

worktrees
$ git worktree add ../review pr-42          # existing branch, new directory
$ git worktree add -b hotfix ../hotfix main # new branch off main
$ git worktree add --detach ../old v1.2.0   # a tag, detached (ch. 4)

$ git worktree list
/home/you/project      4b7c9e2 [feature/rate-limit]
/home/you/review       7e2a91c [pr-42]
/home/you/hotfix       8f3d2a1 [hotfix]

$ git worktree remove ../review     # refuses if it is dirty
$ git worktree prune                 # tidy up after deleting a directory by hand
$ git worktree lock ../old           # stop prune from reclaiming it (removable media)

A linked worktree's .git is not a directory but a one-line file: gitdir: /home/you/project/.git/worktrees/review. That is the entire mechanism — a pointer back to the real repository, plus a small directory there holding this worktree's HEAD and index.

What worktrees are actually good for

  • Reviewing a pull request while your own work sits untouched in the other directory, running.
  • Running a long test suite on one branch while you keep editing another — no shared index to fight over.
  • Bisecting (chapter 23) in a dedicated worktree, because refs/bisect is per-worktree.
  • Comparing two versions side by side in two editor windows, or building an old release to reproduce a bug.
  • Stacked branches (chapter 9), one worktree per level of the stack.
Worktree or a second clone?

A clone duplicates the object store, needs a fetch to stay current, and has its own refs — so it is the right choice when you want genuine isolation, for instance running something you do not trust. A worktree shares everything, costs one working copy on disk, and is instantly consistent with your branches. For "I need to look at another branch", a worktree wins on every axis. The catch: submodules and some build tools assume .git is a directory and get confused by the pointer file.

The short version

Chapter 14 in seven lines

  • A stash is two commits (three with -u): the working tree, the index, and optionally untracked files, with refs/stash's reflog as the stack.
  • Untracked files are not included by default, and apply does not restore staged-ness unless you pass --index.
  • --keep-index is for testing just the change you staged; --staged stashes only that change and leaves the rest.
  • A conflicted pop deliberately keeps the stash; drop it yourself once resolved. A dropped stash is recoverable via git fsck --unreachable for a couple of weeks.
  • The stash stack is per repository — not per branch, and shared between worktrees.
  • For anything longer than an interruption, a WIP commit beats a stash: named, on a branch, pushable, visible.
  • A worktree is another checkout sharing one object store: private HEAD and index, shared branches and stash. A branch can only be checked out in one worktree at a time.

Check yourself

You stash, switch branch, and your new file notes.md is still sitting there. Did the stash fail?

No — notes.md was untracked, and git stash only stashes tracked changes by default. Untracked files are not in the index, so from Git's point of view there is nothing to save and nothing to restore; they simply stay on disk as you switch branches. git stash push -u includes them (creating the third parent commit), and -a additionally includes ignored files, which is almost never what you want because it sweeps up build output and local environment files.

You carefully staged half your changes, then stashed and popped. Everything is unstaged. Why, and what should you have done?

git stash apply and pop restore the working tree but flatten the index by default, so the staged/unstaged split is lost even though the stash recorded it — that is what the second parent commit holds. git stash pop --index restores it. This is a good reason to prefer a WIP commit when the staging arrangement itself represents work you care about.

git worktree add ../hotfix main fails with "already checked out". Why does Git care, and what do you do?

Because HEAD and the index are per-worktree but the branch ref is shared. If main were checked out in two places, committing in one would move the branch under the other, whose index and working tree would silently no longer correspond to its HEAD. Git refuses rather than allowing that. Options: create a new branch (git worktree add -b hotfix ../hotfix main), or check out the commit detached (--detach) if you only need to read or build it.

You have three worktrees. You stash in one and then look for the stash in another. What do you see, and is that a bug?

You see it — refs/stash is a single shared ref, so git stash list shows the same stack from every worktree, and you can pop a stash created elsewhere. Not a bug, but a genuine hazard: applying a stash taken against a different branch's code can produce conflicts or, worse, apply cleanly and wrongly. It is another argument for WIP commits, which are attached to the branch they belong to, and for using -m so git stash list tells you which worktree and branch a stash came from.
