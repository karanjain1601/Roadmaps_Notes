Committing well

A commit is the unit of everything downstream: review, revert, bisect, blame, changelog, cherry-pick. Badly sized commits break all six at once, and no tooling can fix them afterwards. This chapter is about choosing what goes in one, shaping it before it's final, and writing the message that makes it useful in two years.

What belongs in one commit

Three tests, all objective, none aesthetic.

"Atomic commit" is advice you have heard and probably cannot operationalise. Here are the three questions that actually decide it, in order of usefulness:

TestQuestionFails when
RevertIf this turns out to be wrong, can it be reverted on its own without taking something good with it?A bug fix and a dependency upgrade share a commit
BisectDoes the project build and pass its tests at this commit?You split one change across three commits, two of which are broken
ReviewCan a reader hold the whole change in their head at once?Reformatting 200 files hides the two real lines

Notice the revert and bisect tests pull in opposite directions: revert says split, bisect says keep it working. The resolution is that each commit should be one complete change — small, but not a fragment. "Add the function" and "call the function" are usually one commit; "reformat the file" and "fix the bug in it" are always two.

The reformatting rule

Never mix a formatting pass with a behavioural change. Reviewers cannot see the two real lines among four hundred whitespace lines, and git blame attributes every line in the file to you forever. Commit the reformat alone, then record its hash in .git-blame-ignore-revs so blame skips past it (ch. 6).

Shaping a commit before it's final

The gap between "I have made a commit" and "I have pushed it" is where all the freedom lives.

Anything not yet pushed can be reshaped freely. Three tools, in increasing power:

amend: rewrite the tip
$ git commit --amend                  # edit message and/or fold in staged changes
$ git commit --amend --no-edit        # fold in staged changes, keep the message
$ git commit --amend --reset-author   # also update the author name/date to you, now

Amend does not modify a commit — chapter 2 established that it cannot. It builds a new commit with the same parent and moves the branch, leaving the old one in the reflog. That matters because amending a pushed commit means your branch and the remote have diverged, and you are now in force-push territory (ch. 12).

fixup and squash: amend something older

You are five commits deep and notice a typo belonging to the second one. Amending only works on the tip, so instead you record where the fix belongs and let a rebase apply it later:

deferred amends
$ git add -p                          # stage just the fix
$ git commit --fixup b2c3d4e          # message becomes "fixup! feat: validate password"
$ git commit --squash b2c3d4e         # same, but your message gets folded in too
$ git commit --fixup=reword:b2c3d4e   # 2.32+: change only that commit's message

# later, before pushing — one command, no interactive editing needed
$ git rebase -i --autosquash HEAD~6

With rebase.autosquash true set (chapter 1), the reordering happens automatically on any interactive rebase. The demo below builds the todo list so you can see exactly what it does.

Splitting a commit you already made

one commit becomes two
$ git reset HEAD~                # undo the commit, keep the changes unstaged
$ git add -p                     # stage the first coherent piece
$ git commit -m "Extract token parser"
$ git add -A && git commit -m "Return 401 for expired tokens"

That is the whole technique, and it relies on nothing more than chapter 3's three trees: reset without --hard moves HEAD and the index while leaving your files alone.

Fixes #421

Subject, blank line, body, blank line, trailers. The rules and the reasons:

RuleWhy it exists
Subject on line 1, ≤ 50 charactersgit log --oneline prefixes 8 characters of hash, and 50 keeps it inside 80 columns. GitHub truncates the subject at 72.
Line 2 blankGit itself uses the first blank line to split subject from body. Without it, %s swallows your whole message.
Imperative mood: "Add", not "Added"Git's own generated messages are imperative ("Merge branch", "Revert"). The message completes the sentence "applying this commit will…".
No full stop on the subjectIt is a title. The character is wasted where you have 50.
Body wrapped at 72git log indents the body by four spaces; 72 + 4 fits 80. Git does not wrap for you.
Body says why, not whatThe diff already says what. Only you know what you were thinking.

Conventional Commits

A machine-readable subject convention: type(scope)!: description. It exists so tooling can derive version bumps and changelogs — fix: means a patch release, feat: a minor, and either ! or a BREAKING CHANGE: trailer a major.

conventional subjects
feat(auth): return 401 for expired tokens
fix: guard against empty upload bodies
perf(parser): avoid re-scanning the buffer
refactor!: drop support for v1 config files
chore(deps): bump axios to 1.7.4

It is worth adopting if something consumes it — semantic-release, release-please, a changelog generator. Adopted as pure ceremony it just adds a prefix to guess at, and reviewers start arguing about whether a change is refactor or chore instead of reading it.

Trailers, templates and issue links

Structured metadata at the foot of a message, parsed by Git and by GitHub.

TrailerMeaningRead by
Co-authored-by: Name <email>Shared authorship of one commitGitHub — both get contribution credit

adding trailers
$ git commit -s                              # append Signed-off-by from your identity
$ git commit --trailer "Reviewed-by=Ada <ada@example.com>"
$ git interpret-trailers --trailer "Fixes=#421" --in-place COMMIT_EDITMSG
$ git log --format='%(trailers:key=Co-authored-by,valueonly)'   # query them

Signed-off-by is a legal statement about your right to submit the code. It is not a cryptographic signature and proves nothing about who ran the command — that is the next section.

A commit template

wire it up
$ git config --global commit.template ~/.gitmessage

Lines starting with # are stripped, so the prompts never reach the commit. For a repository-wide version, commit .gitmessage and set commit.template in a setup script — config itself cannot be committed.

Author, committer and dates

Four fields, two of which you can set and one of which you should rarely touch.

Every commit carries an author (who wrote it, with a date) and a committer (who created this object, with a date). They diverge whenever someone else applies your work — a maintainer applying a patch, or your own rebase.

setting them deliberately
$ git commit --author="Priya Raman <priya@example.com>" -m "Apply patch from mailing list"
$ git commit --date="2025-08-14T09:00:00" -m "Backdate the author date only"
$ GIT_COMMITTER_DATE="2025-08-14T09:00:00" git commit -m "Set both dates"

$ git log --format='%h  a:%an %ad  c:%cn %cd' --date=short -3
$ git commit --allow-empty -m "Trigger CI"       # a commit with no changes, on purpose
Committer dates and rebase

A rebase preserves author dates and stamps now as the committer date, which is why rebased history can look out of order in tools that sort by committer date and why git log (author date by default) usually looks fine. If a chronology matters to you, know which date your tooling shows — %ad is author, %cd is committer.

Signing commits

Because the author field is just text you typed.

Nothing stops anyone setting user.email to your address and committing as you. Hashes prove integrity, not identity (chapter 2). Signatures close that gap, and since Git 2.34 you can sign with an SSH key you already have rather than setting up GPG:

SSH signing — the easy path
$ git config --global gpg.format ssh
$ git config --global user.signingkey ~/.ssh/id_ed25519.pub
$ git config --global commit.gpgsign true
$ git config --global tag.gpgsign true

# to verify other people's signatures locally you need a list of who is trusted
$ echo "priya@example.com ssh-ed25519 AAAAC3Nz..." >> ~/.ssh/allowed_signers
$ git config --global gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers
checking
$ git log --show-signature -1
$ git verify-commit HEAD
$ git log --format='%h %G? %aN' -5      # G good, B bad, U unknown, N none
8f3d2a1 G Priya Raman
7e2a91c N You

On GitHub, upload the same public key a second time as a signing key (the authentication key it already holds does not count) and commits get the Verified badge. Requiring signed commits on protected branches is a chapter 16 setting.

Hooks at commit time

Useful for catching mistakes. Useless as a control.

HookRunsTypical job
pre-commitBefore the message editor opensFormat, lint, run fast tests; non-zero exit aborts
prepare-commit-msgBefore you see the messageInsert a ticket number from the branch name
commit-msgAfter you save the messageValidate the format — the linter above, enforced
post-commitAfter the commit existsNotifications; cannot abort anything
.git/hooks/commit-msg
#!/bin/sh
# $1 is the path to the file holding the message
subject=$(head -n1 "$1")
if [ ${#subject} -gt 72 ]; then
  echo "commit-msg: subject is ${#subject} characters; keep it under 72." >&2
  exit 1
fi
exit 0
sharing hooks with the team
$ git config core.hooksPath .githooks    # a directory you can commit
$ chmod +x .githooks/*                    # hooks must be executable
Hooks are advice, not policy

.git/hooks is not cloned, hooks are not executed by the server, and git commit --no-verify skips them entirely. They are a courtesy that saves you a round trip to CI. Anything that genuinely must not enter the repository belongs in a required status check or a branch protection rule (ch. 16, ch. 21) — enforced where the code lands, not where it is written.

The short version

Chapter 05 in eight lines

  • Size a commit by three tests: can it be reverted alone, does it build on its own, can a reviewer hold it in their head.
  • Never mix reformatting with behaviour — it destroys both review and git blame.
  • --amend rewrites the tip into a new object; the old one waits in the reflog. Amending anything pushed means a force-push.
  • --fixup and --squash defer an amend to an older commit; rebase -i --autosquash applies them all in one pass.
  • Split a commit with git reset HEAD~ then stage in pieces — the three trees again.
  • Message shape: subject ≤ 50 in the imperative, blank line, body wrapped at 72 explaining why, trailers last.
  • Author and committer are separate fields with separate dates; rebase keeps the author and replaces the committer.
  • Signed-off-by is a legal attestation; signing is cryptography — SSH signing needs three config lines and closes the "anyone can commit as you" gap.

Check yourself

You spot a typo in a commit four back on an unpushed branch. What is the least disruptive way to fix it?

Stage the fix and run git commit --fixup <hash-of-that-commit>, then git rebase -i --autosquash HEAD~5 before you push. The fixup lands in the right commit with no message noise and no manual reordering. If only the message is wrong, git commit --fixup=reword:<hash> (2.32+) or an interactive rebase marking that line reword.

Why does a commit message need a blank second line, technically rather than stylistically?

Git splits subject from body at the first blank line. Without it, the whole message is the subject: %s in a pretty-format expands to everything, git log --oneline becomes unreadable, GitHub shows a wall of text as the commit title, and any tooling reading the subject gets the body too. It is a parsing boundary that happens to also look tidy.

Your team has a pre-commit hook that runs the linter, and unlinted code keeps reaching main. What is going wrong and what fixes it?

Hooks live in .git/hooks, which is not cloned, so new teammates simply do not have it; and anyone can pass --no-verify. Commit the hooks to .githooks/ and set core.hooksPath so they are at least installable, but the actual fix is a required status check on the branch: CI runs the linter and the merge is blocked until it passes. Hooks catch your own mistakes early; they cannot enforce anything.

A commit shows your name as author but you did not write it. Is that a security breach?

Not necessarily, and not detectable from the author field, which is just text from the committer's config — anyone can set it to anything. Legitimately, it happens whenever someone applies your patch or rebases your branch: they become the committer and you stay the author. The only way to tell an impersonation from a legitimate application is a signature: git log --show-signature, or requiring signed commits on the branch so unsigned ones cannot land.
