Rebase and rewriting history

Rebase does not move commits. Commits are immutable — chapter 2 settled that. It replays them: takes each one's diff, applies it somewhere else, and builds a new commit with the same content and a different parent, hence a different hash. Everything confusing about rebase follows from that one fact, including why force-pushing is required and why it is dangerous.

What rebase actually does

Replay, not relocate.

git rebase main on branch feature does this:

  1. Work out which commits are yours: everything in main..feature (chapter 6's range syntax, exactly).
  2. Move HEAD to main's tip.
  3. For each of your commits in order, apply its change and create a new commit — same message, same author, new committer date, new parent, new hash.
  4. Move the feature ref to the last new commit.

The originals are untouched and unreachable, sitting in the reflog for a few weeks (chapter 4). Nothing was edited; a parallel copy was built.

seeing it happen
$ git log --oneline main..feature       # exactly what will be replayed
7e2a91c Return 401 on expiry
c3d4e5f Add expiry check
a1b2c3d Add token parser

$ git rebase main
Successfully rebased and updated refs/heads/feature.

$ git log --oneline main..feature       # same messages, all-new hashes
9f8e7d6 Return 401 on expiry
8e7d6c5 Add expiry check
7d6c5b4 Add token parser

$ git reflog feature                     # the originals are still named here
7e2a91c feature@{1}: rebase (finish): refs/heads/feature onto 4b7c9e2

That fifth row matters more than people expect: the tree is recomputed, so a rebased commit contains code that never existed in that combination before. It compiled on the old base; nobody has proven it compiles on the new one. This is why --exec exists, later in this chapter.

Rebasing, and its conflicts

Including the inversion that catches everyone once.

the everyday forms
$ git rebase main                    # replay my branch on top of main
$ git rebase origin/main             # ...on top of what the remote currently has
$ git rebase --autostash main        # stash dirty work first, restore it after
$ git rebase -i HEAD~5               # interactive, over my last five commits
$ git rebase --onto main old-base feature    # surgical; see below

$ git rebase --continue              # after resolving a conflict
$ git rebase --skip                  # drop the commit currently being replayed
$ git rebase --abort                 # restore everything to the pre-rebase state
$ git rebase --edit-todo             # change the remaining plan, mid-rebase
During a rebase, "ours" and "theirs" are swapped

Git checks out the new base and replays your commits onto it, so at any conflict HEAD is the base branch. That makes --ours the branch you are rebasing onto — usually main, other people's work — and --theirs your own commit being replayed. It is the exact opposite of a merge, where --ours is your branch. Nothing is broken; the labels are relative to HEAD, and during a rebase HEAD is not where you think. When in doubt, use git status, which names the actual commit being applied.

Conflicts during a rebase arrive one commit at a time, and the same underlying disagreement can surface repeatedly — once per replayed commit that touches the region. That is what rerere (chapter 11) is for.

not losing your place
$ git status
interactive rebase in progress; onto 4b7c9e2

Next command to do (1 remaining command):
   pick 7e2a91c Return 401 on expiry

$ git rebase --show-current-patch     # the commit being applied, in full

The interactive todo list

Seven verbs, and the order of the lines is itself an instruction.

the two flags that make it usable
$ git rebase -i --autosquash main         # place fixup!/squash! commits automatically (ch. 5)
$ git rebase -i --exec "npm test" main    # run the tests after EVERY replayed commit
$ git rebase -i --root                     # include the very first commit in the todo list

--exec is the answer to the point made earlier: after a rebase every commit contains an untested combination of code. --exec runs your test command at each step and stops on the first failure, which turns "the branch passes" into "every commit passes" — the property git bisect depends on.

Surgery with --onto

Three arguments, and it can do things nothing else can.

git rebase --onto <newbase> <upstream> <branch> replays the commits in upstream..branch onto newbase. Being able to name all three independently is what makes it surgical.

the cases that need it
# my branch was based on 'develop', which is being abandoned — move it to main
$ git rebase --onto main develop feature

# drop a commit from the middle without an interactive editor
$ git rebase --onto bad-commit~1 bad-commit feature

# a stacked branch: B was built on A, and A has just been rebased
$ git rebase --onto A B~3 B

# rebase a stack and fix every intermediate branch ref at once (2.38+)
$ git rebase --update-refs main

# preserve the branch topology instead of flattening merges
$ git rebase --rebase-merges main

--update-refs is a genuine quality-of-life change if you stack branches: without it, rebasing the top of a stack leaves every branch below pointing at abandoned commits, and you fix them by hand. With it, Git rewrites the intermediate refs as it goes. Set rebase.updateRefs = true to have it always on.

What happened to --preserve-merges

It was the old attempt at rebasing merge commits, it was buggy in ways that silently produced wrong history, and it was deprecated and then removed. --rebase-merges is the replacement and works by generating label, reset and merge commands in the todo list — you can see the topology being rebuilt if you run it interactively.

The golden rule, and force-pushing safely

Chapter 8 showed why rewriting shared history fails. Here is how to rewrite your own without collateral damage.

After any rebase your branch and its remote counterpart have diverged — same content, different commits — so a normal push is refused as non-fast-forward. You must force. The question is which force.

FlagRefuses whenProtects against
--forceNeverNothing. The remote becomes whatever you have
--force-with-leaseThe remote has moved since your last fetchOverwriting a commit you never knew existed
--force-if-includesYou have not integrated the remote tip you last fetchedFetching, ignoring what arrived, and overwriting it anyway

The gap between the second and third is the interesting one, and it is where people who "always use --force-with-lease" still lose a colleague's work. A lease only checks that your view of the remote is current. git fetch makes it current — without integrating anything — so a fetch followed by a lease-protected force-push passes the check and destroys the commit you just fetched.

Where the golden rule actually bites

Rewriting your own unshared branch: fine, do it constantly. Rewriting a branch someone else has checked out: their next pull merges your abandoned commits back in, duplicating every commit you rewrote (chapter 8's simulator). Rewriting main: everyone's clone disagrees with the remote, CI reruns from a history that no longer exists, and any deploy pinned to a hash is now pointing at an unreachable commit. Branch protection (chapter 16) exists to make the last one impossible rather than merely inadvisable.

Rebase or merge?

The argument is real but narrower than the internet suggests.

RebaseMerge
History shapeLinearRecords that a branch existed
Commit hashesRewrittenPreserved

Bisect qualityGood, if every commit was tested (--exec)Good, with a noisier graph
"When was this integrated?"UnanswerableThe merge commit's date

The workable consensus for most teams: rebase your own work, merge other people's. Rebase while a branch is yours and unshared — to tidy commits, drop debugging, and sit on top of current main. Merge (or squash-merge) when it lands, so the integration point is recorded and nobody's clone is invalidated.

and stop merging on every pull
$ git config --global pull.rebase true     # pull = fetch + rebase
$ git config --global pull.ff only         # or: refuse to guess, make me choose

$ git pull --rebase                        # one-off
$ git fetch && git rebase origin/main      # the same thing, explicitly

Default git pull creates a merge commit whenever your branch and the remote have both moved, which is how histories acquire dozens of "Merge branch 'main' of github.com:org/repo" commits that record nothing anyone wanted. Either setting above removes them permanently.

The short version

Chapter 12 in eight lines

  • Rebase replays commits: same message and author, new parent, new tree, new hash. The originals sit unreachable in the reflog.
  • A rebased commit contains a code combination nobody has tested — --exec "npm test" fixes that per commit.
  • During a rebase, --ours is the branch you are rebasing onto and --theirs is your own commit. The opposite of a merge.
  • Interactive verbs: pick, reword, edit, squash, fixup, drop, break, exec — and reordering the lines reorders history.
  • Commits before the first modified line keep their hashes; everything from there on is rebuilt.
  • --onto takes three independent arguments, which is what makes it surgical; --update-refs fixes stacked branches automatically.
  • --force-with-lease checks your view of the remote is current; it does not check that you integrated it. Add --force-if-includes (or push.useForceIfIncludes) for that.
  • Rebase your own unshared work; merge other people's. Set pull.rebase or pull.ff only so a pull never invents a merge commit.

Check yourself

Mid-rebase you hit a conflict and want to keep the version from main. Do you use --ours or --theirs?

--ours. Git has checked out main as HEAD and is applying your commits on top, so "ours" is the rebase target — main — and "theirs" is the commit of yours currently being replayed. If you reason from "ours means my branch", you take the wrong side and it looks like your change simply vanished. During a merge the same flags mean the opposite, which is why it is worth reading git status rather than relying on the words.

You always use --force-with-lease. Describe a sequence where a colleague's commit is still destroyed.

You rebase your branch. Your colleague pushes a commit to the same branch. You run git push --force-with-lease, it is rejected as stale, so you git fetch — which updates your origin/feature ref and makes the lease current — and push again. The lease now passes, because your view of the remote is up to date; but you never integrated their commit, so your push replaces it. That is exactly what --force-if-includes prevents: it additionally requires the remote tip you last saw to be reachable from what you are pushing. The simulator above walks the whole sequence.

You interactively rebase five commits and mark only the fifth as reword. How many commits get new hashes, and why?

One — the fifth. Commits before the first modified todo line are unchanged in every respect (same parent, tree, message, author and committer), so Git fast-forwards over them and they keep their original hashes. The fifth gets a new message, hence a new hash, and has no descendants in the range to invalidate. Mark the first commit as reword instead and all five are rebuilt, because each one's parent hash changed.

A branch is based on develop, which the team is retiring. You need it on main without dragging in develop's commits. What do you run?

git rebase --onto main develop feature. The three arguments mean: replay the commits in develop..feature — just yours — on top of main. A plain git rebase main feature would compute the range from the merge base of main and feature, which is somewhere below develop, and so would replay develop's commits too. Naming the upstream explicitly is the whole point of --onto.
