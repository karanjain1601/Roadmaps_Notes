Inside .git: the object database

Underneath the 150 commands there is a key–value store with four kinds of value and one rule: the key is the hash of the value. Everything else — branches, merges, the impossibility of quietly editing history, the reason rebasing rewrites commit IDs — falls out of that rule. This chapter builds the store by hand.

Content addressing

The name is computed from the value, so the same content always has the same name.

An ordinary file system addresses content by location: /home/you/notes.txt is a name you chose, and the bytes behind it can change without the name changing. Git addresses content by hash: the name of a piece of content is the SHA-1 digest of that content, prefixed with a small header. You do not choose it, and you cannot change the content without also changing the name.

the whole idea, in one command
$ echo "hello world" | git hash-object --stdin
3b18e512dba79e4c8300dd08aeb37f8e728b8dad

$ echo "hello world" | git hash-object --stdin      # same input, anywhere, forever
3b18e512dba79e4c8300dd08aeb37f8e728b8dad

Run that on your machine and on a build server in Frankfurt in 2031 and you get the same forty characters. Four properties follow immediately, and they carry the entire design:

PropertyBecauseWhat it buys you
DeduplicationIdentical content computes to one nameAn unchanged file across 5,000 commits is stored once
IntegrityContent that changed no longer matches its nameSilent disk corruption is detectable — git fsck
ImmutabilityEditing content produces a different objectNothing in history can be altered in place, only replaced
Cheap comparisonEqual names imply equal contentComparing two directory trees is comparing two hashes

That last one is why Git can diff a huge tree fast: at any level, if the two hashes match, the entire subtree beneath is identical and can be skipped without reading a single byte.

The four object types

Blob, tree, commit, tag. There is no fifth.

Every object is stored the same way: a header <type> <size in bytes>\0, then the content, all zlib-compressed and written to a file named after the hash of the uncompressed header plus content.

TypeHoldsNotably does not hold
blobThe raw bytes of one fileIts name, its path, its permissions, any timestamp
treeA directory listing: mode, type, hash and name per entryIts own name, timestamps, owner, group
commitOne tree hash, zero or more parents, author, committer, messageAny diff — a commit contains no changes
tagA target object, its type, a tag name, tagger, messageNothing much; only annotated tags create an object at all

Read the "does not hold" column again — it explains a lot of Git's behaviour. A blob has no name, so renaming a file creates no new blob and Git has to infer renames by comparing content later. A tree has no timestamps, so checking out old code gives you files dated today. Nothing records ownership, so Git cannot be used as a backup tool for a system directory.

inspecting any object
$ git cat-file -t 3b18e51      # type
blob
$ git cat-file -s 3b18e51      # size in bytes
12
$ git cat-file -p 3b18e51      # pretty-print the content
hello world

Short hashes work anywhere a full one does, as long as they are unambiguous in your repository — usually seven characters, more in a very large one. Git resolves them for you.

Why the header exists

Without blob 12\0 in front, a blob and a commit with the same bytes would collide, and the type would have to be stored somewhere else. The header also means the hash of an empty file is not the hash of nothing: it is e69de29bb2d1d6434b8b29ae775ad8c2e48c5391, a constant you will eventually recognise on sight because empty files are common.

Trees: how directories are stored

A tree is a sorted list of pointers, and nothing else.

a real tree, pretty-printed
$ git cat-file -p HEAD^{tree}
100644 blob a45bd4f1c9b7e2d3f8a01c5e6b7d8e9f0a1b2c3d    README.md
100755 blob 7d9f3c2b8a4e1f6d5c0b9a8e7f6d5c4b3a2f1e0d    build.sh
040000 tree 2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e    src

On disk each entry is <mode> <name>\0 followed by the 20 raw bytes of the target hash — no separators, no padding, no order but one: entries are sorted by name, with directory names compared as though they ended in /. That sort order is part of the format, which is why two people building the same directory always produce the same tree hash.

ModeMeansNotes
100644Regular fileThe overwhelming majority
100755Executable fileThe only permission bit Git records
120000Symbolic linkThe blob contains the link target as text
040000SubdirectoryPoints at another tree object
160000GitlinkA submodule: a commit hash from another repository (ch. 17)

So Git's permission model is one bit. If your deploy depends on a file being mode 600, the repository cannot express that and something else must set it.

Trap: empty directories

There is no object type for "empty directory". A tree is a list of entries; a directory with nothing in it produces no entries and therefore does not exist as far as Git is concerned. This is why projects contain files called .gitkeep — an arbitrary convention, not a Git feature, whose only job is to give the directory something to hold.

Commits and the graph

A commit is a text file that names a tree and its parents.

git cat-file -p HEAD
tree 9c1f7a4b2e8d5c0a3f6b9e2d1c4a7b0e3f6d9c2a
parent 4a7b0e3f6d9c2a1f8e5b2c9d6a3f0e7b4c1d8a5f
author A U Thor <author@example.com> 1700000000 +0000
committer A U Thor <author@example.com> 1700000000 +0000

Brute-force attempts were unbounded.

That is the entire object. Hash those bytes with a commit header and you get the commit ID. Several consequences worth stating explicitly:

  • A commit contains no changes. It names one complete tree. What git show displays as a diff is computed against the parent's tree at display time.
  • Parents make it a graph. Zero parents means a root commit. One is ordinary. Two or more is a merge (ch. 10). The result is a directed acyclic graph — the "commit DAG" — and branches are just names pointing into it.
  • Author and committer are different people. The author wrote the change; the committer created this object. They diverge whenever a maintainer applies your patch, and whenever you rebase — rebasing preserves the author and stamps you as committer, which is why rebased commits show a new date in some views.
  • The parent hash is inside the hash. Change anything about a commit — even one character of its message — and its ID changes; since its child names it as parent, the child's ID changes too, and so on to the tip. This is what people mean by "rewriting history": not editing commits, but building new ones and abandoning the old chain (ch. 12).

Git is, structurally, a Merkle DAG — the same shape as a blockchain's integrity mechanism, five years earlier and for the same reason: so that naming the tip is enough to pin down everything reachable from it.

The pattern to take away

Changing one file deep in a tree creates a new blob, a new tree for every directory on the path up to the root, and a new commit. Nothing else is touched. A commit in the Linux kernel that edits one driver file creates perhaps five or six objects, not eighty thousand.

The .git directory, entry by entry

Nine things, no magic.

a repository with some history
$ ls -A .git
COMMIT_EDITMSG  HEAD  ORIG_HEAD  config  description
hooks/  index  info/  logs/  objects/  packed-refs  refs/
HEAD
Usually one line: ref: refs/heads/main. A pointer to the branch you are on. When it holds a raw commit hash instead, you are in "detached HEAD" (ch. 4).
objects/
The store. Loose objects live at objects/3b/18e512... — first two hex characters as the directory, to keep any one directory small. objects/pack/ holds packfiles; objects/info/ holds metadata for alternates and packs.
refs/
refs/heads/ is your branches, refs/tags/ your tags, refs/remotes/origin/ the last known state of the remote. Each is a file containing a 40-character hash and a newline — 41 bytes. That is all a branch is.
packed-refs
Once you have thousands of refs, one file each is wasteful, so Git packs them into this single text file. A ref may live in either place; git rev-parse and friends check both.
index
A binary file listing what the next commit will contain, plus cached stat data so git status can skip unchanged files without reading them. Chapter 3 is about this file.
logs/
The reflog: an append-only record of every value each ref has held, with timestamps. This is the undo history that makes "I lost a commit" almost always false (ch. 4, ch. 8).
config
Repository-local configuration, including the remote URLs. description next to it is used only by GitWeb and can be ignored.
hooks/
Executable scripts Git runs at defined moments. Ships full of .sample files, all disabled (ch. 23).
ORIG_HEAD, MERGE_HEAD, FETCH_HEAD, COMMIT_EDITMSG
Scratch state. ORIG_HEAD is where HEAD was before the last drastic operation — a one-step undo. MERGE_HEAD exists only during a conflicted merge. COMMIT_EDITMSG is the message buffer your editor just wrote.
proving a branch is a 41-byte file
$ cat .git/refs/heads/main
8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3

$ wc -c .git/refs/heads/main
41 .git/refs/heads/main

$ git branch experiment          # create a branch
$ cat .git/refs/heads/experiment # ...is one more 41-byte file
8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3

That is why Git's branches are described as cheap. Creating one writes 41 bytes; deleting one removes a file. Compare with systems where a branch is a server-side copy of the tree.

Loose objects, packfiles and gc

Where the delta compression from chapter 1 actually happens.

A freshly created object is written loose: one zlib-compressed file per object. That is fast to write and terrible at scale — a repository with a million objects would be a million files, most of them nearly identical to another.

So Git periodically repacks. A packfile (.pack) holds many objects in one file, with an index (.idx) for random access, and inside it objects may be stored as deltas against a similar object rather than in full. Git chooses delta bases by heuristics on size and name similarity, and caps chain depth (default 50) so reconstruction stays bounded.

looking at the store
$ git count-objects -vH
count: 43              # loose objects
size: 172.00 KiB
in-pack: 15284         # objects inside packfiles
packs: 2
size-pack: 8.42 MiB
prune-packable: 0
garbage: 0

$ git gc                       # repack, and prune unreachable objects older than 2 weeks
$ git gc --aggressive          # slower, recomputes deltas from scratch — rarely worth it
$ git verify-pack -v .git/objects/pack/pack-*.idx | head    # per-object sizes and chain depths

Two behaviours surprise people:

  • Deleting things does not shrink the repository. An object stays until it is unreachable and pruned, and the default grace period is two weeks. A 200 MB video committed once and deleted in the next commit is still in every clone, forever, unless the history is rewritten (ch. 23).
  • gc runs on its own. Commands that create many objects trigger git gc --auto, which is why an occasional push or commit pauses for a second. git maintenance start moves that work to a background schedule.
Reachability

An object is reachable if you can walk to it from any ref — a branch, a tag, the index, a stash, or an entry in the reflog. Everything else is garbage awaiting collection. This is why the reflog is such an effective safety net: for two weeks after you "lose" a commit, the reflog still names it, so it is still reachable and still on disk.

SHA-1, collisions, and the move to SHA-256

A cryptographic footnote with real operational consequences.

SHA-1 has been considered theoretically weak since 2005, and in 2017 Google and CWI demonstrated SHAttered: two different PDF files with the same SHA-1 digest. Since object names are SHA-1 digests, this is a legitimate question for Git.

Three things are true at once:

  • Git has shipped collision-detecting SHA-1 (sha1dc) since version 2.13. It detects the bit patterns characteristic of known collision attacks and aborts rather than accepting the object, at a small speed cost.
  • An attack must produce a collision against an object that already exists in your repository, and get you to accept it — much harder than producing two colliding files of your own.
  • Git supports a full SHA-256 object format (git init --object-format=sha256) since 2.29. It works, but repositories in the two formats cannot yet interoperate, and major hosts including GitHub do not accept them, so in practice everything you touch is SHA-1.

The practical takeaway is small: do not treat a Git hash as a security boundary on its own. If you need to prove a commit came from a specific person, sign it (ch. 5) — signatures, not hashes, are the authentication mechanism.

Making a commit without porcelain

The best twenty minutes you can spend on Git.

Everything the previous sections described can be driven directly. Doing this once, in a scratch repository, converts the model from something you have read into something you have operated.

a commit built from plumbing only
$ mkdir plumb && cd plumb && git init -q

# 1. write a blob into the object store (-w writes; without it, just prints the hash)
$ echo 'hello world' | git hash-object -w --stdin
3b18e512dba79e4c8300dd08aeb37f8e728b8dad

# 2. put that blob in the index under a name and mode
$ git update-index --add --cacheinfo 100644,3b18e512dba79e4c8300dd08aeb37f8e728b8dad,hello.txt

# 3. turn the index into a tree object
$ git write-tree
68aba62e560c0ebc3396e8ae9335232cd93a3f60

# 4. wrap the tree in a commit (no parent — this is a root commit)
$ echo 'First commit, by hand' | git commit-tree 68aba62
d4c1f0a7b3e2519f8c6a0d4b7e3f2a1c9d8b7e6f

# 5. point a branch at it
$ git update-ref refs/heads/main d4c1f0a

$ git log --oneline
d4c1f0a (HEAD -> main) First commit, by hand
$ git status
On branch main
nothing to commit, working tree clean

No git add, no git commit. Those two commands are convenience wrappers over exactly these steps — which is precisely what "porcelain over plumbing" means.

The short version

Chapter 02 in eight lines

  • Git is a key–value store where the key is the SHA-1 of the value, prefixed with <type> <size>\0.
  • Four object types: blob (bytes), tree (a sorted directory listing), commit (one tree plus parents and metadata), tag (an annotated pointer).
  • Blobs have no names and trees have no timestamps — which is why renames are inferred, checkouts have today's dates, and only the executable bit survives.
  • A commit stores no diff. Diffs are computed by comparing its tree with its parent's.
  • Because a parent's hash is part of a commit's hash, changing any commit changes every descendant. That is all "rewriting history" means.
  • A branch is a 41-byte file under .git/refs/heads/ containing a commit hash.
  • Objects start loose and get packed, with delta compression inside the packfile. Unreachable objects survive until pruned, so deleting a big file does not shrink the clone.
  • SHA-1 is collision-hardened in Git and SHA-256 exists but isn't interoperable yet; use signatures, not hashes, for authenticity.

Check yourself

Two files in a repository, a/config.json and b/config.json, have byte-identical contents. How many blobs?

One. A blob is content, with no name and no path, so both tree entries point at the same object. Copy that file into fifty directories and the store still gains no blobs — only the trees change, because they list different names pointing at the same hash.

You amend the message of a commit that has ten commits after it. How many commit objects does the repository now contain for that line of history?

Twenty-two, temporarily. The original eleven still exist (unreachable but not yet pruned, and still named in the reflog), and eleven new ones have been created — the amended commit plus rebuilt copies of all ten descendants, each with a new hash because its parent's hash changed. The old chain disappears from the store only after it falls out of the reflog and gc prunes it.

A colleague committed a 300 MB dataset, then deleted it in the next commit and pushed. The clone is still 300 MB. Why, and what actually fixes it?

The blob is still reachable — from the earlier commit, which is still in history. Deleting a file in a later commit only changes later trees; it does not remove anything from the object store. The fix is to rewrite history so no commit references that blob (git filter-repo, ch. 23), force-push, and have every collaborator re-clone, then let gc prune. On GitHub you also need support to run garbage collection server-side.

Why can Git tell instantly that two large directory trees are identical, without reading any files?

Because each directory is a tree object whose hash covers the names, modes and hashes of everything inside it, recursively. If the two root trees have the same hash, every byte beneath them is identical by construction. Git exploits this constantly — during diff, merge and status it prunes whole subtrees whose hashes match, which is why operations scale with what changed rather than with repository size.
