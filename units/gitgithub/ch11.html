Conflicts

A conflict is not an error. It is Git declining to guess, which is the correct behaviour — two people changed the same thing and only a human knows what the result should mean. What makes conflicts painful is the default presentation, which hides the single most useful piece of information: what the line said before either of you touched it.

What Git's state is during a conflict

Three files and an index. Knowing this turns panic into inspection.

When a merge stops, Git has already done most of the work. Every cleanly merged path is staged at stage 0. Each conflicted path is stored in the index three times — chapter 3's stage numbers:

the index, mid-conflict
$ git ls-files --unmerged
100644 a45bd4f1c9b7e2d3f8a01c5e6b7d8e9f0a1b2c3d 1	src/config.js    # base
100644 7d9f3c2b8a4e1f6d5c0b9a8e7f6d5c4b3a2f1e0d 2	src/config.js    # ours
100644 2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e 3	src/config.js    # theirs

$ git show :1:src/config.js      # the merge base version
$ git show :2:src/config.js      # our version, in full
$ git show :3:src/config.js      # their version, in full

Those three blobs are the whole conflict. The file on disk with markers in it is just Git's attempt to present them; the authoritative data is in the index, which is why git checkout --ours and friends work even after you have mangled the file.

Status saysShort codeStages presentMeans
both modifiedUU1, 2, 3The ordinary case
both addedAA2, 3Each side created the same path independently
deleted by usUD1, 3We deleted it, they changed it
deleted by themDU1, 2They deleted it, we changed it

The delete-versus-modify cases are the ones people mishandle: there is no textual conflict to resolve, only a decision — does the file exist afterwards? Resolve with git rm <file> or git add <file>, not by editing markers that are not there.

the rest of the state
$ cat .git/MERGE_HEAD        # the commit being merged in — exists only during a merge
$ cat .git/MERGE_MSG          # the prepared commit message
$ git status --short          # UU / AA / UD / DU on the conflicted paths
$ git diff                    # a COMBINED diff: two columns of +/- , ours and theirs
$ git diff --ours             # what the merge result would change relative to our side
$ git diff --theirs           # ...relative to their side
$ git diff --base             # ...relative to the merge base

The three marker styles

Same conflict, three presentations, wildly different usefulness.

The default style shows what each side wants and nothing about where they started. That is fine when the two versions are obviously different, and nearly useless when they are similar — you cannot tell who changed what, so you cannot tell which parts to combine.

Marker style comparator

One conflict, computed by the real merge engine, rendered three ways

set this and never think about it again
$ git config --global merge.conflictStyle zdiff3     # 2.35 or newer
$ git config --global merge.conflictStyle diff3      # older Git
Why zdiff3 rather than diff3

Both show the base. zdiff3 additionally hoists lines that both sides added out of the conflict region, so the markers wrap only the part that genuinely disagrees. On a conflict where two people each added a logging line and then changed the return value differently, diff3 makes you read the logging line three times; zdiff3 shows it once, outside the conflict, and leaves you looking at the two return values. The comparator above counts the difference.

The resolution workflow

Five steps, in order, every time.

  1. Read git status. How many paths, and which kind of conflict each is. Delete-versus-modify needs a decision, not an edit.
  2. Understand the disagreement. git diff for the combined view, or git show :1:file for what the base actually said.
  3. Produce the correct file. By editing, by taking one side wholesale, or with a mergetool.
  4. Stage it. git add <file> collapses the three stages to one and marks the path resolved.
  5. Finish. git merge --continue, or git rebase --continue if you are mid-rebase.
taking one side wholesale
$ git checkout --ours src/config.js     # our version of the WHOLE file
$ git checkout --theirs src/config.js   # their version of the WHOLE file
$ git restore --source=:1 src/config.js # go back to the base version and start over
$ git checkout --merge src/config.js    # regenerate the markers after you mangled the file
$ git checkout --conflict=zdiff3 src/config.js   # ...in a different style
--ours takes the whole file, not the conflicting part

It is not "resolve this conflict in our favour" — it replaces the entire file with our version, silently discarding every change the other side made to it, including the parts that merged cleanly. On a file with one conflict and nine clean changes from their side, you have just thrown away nine changes and nothing will tell you. Use it only when you genuinely want their edits to that file gone; otherwise edit the conflicted region.

Mergetools

Three panes beat one file with markers, for anything non-trivial.

configuring one
$ git mergetool --tool-help          # what your machine already supports
$ git config --global merge.tool vimdiff
$ git config --global mergetool.keepBackup false   # stop leaving .orig files behind
$ git config --global mergetool.prompt false        # don't ask before each file

# VS Code as the merge tool
$ git config --global merge.tool vscode
$ git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'

$ git mergetool                       # walk through every conflicted path

The four variables a mergetool receives are worth knowing because they name the same four things this chapter keeps returning to: $BASE is stage 1, $LOCAL is stage 2 (ours), $REMOTE is stage 3 (theirs), and $MERGED is the file on disk you are producing.

A three-pane tool earns its keep when both sides made structural changes — you are reading two coherent versions rather than an interleaving. For a one-line disagreement it is slower than editing the file. Modern editors bundle their own three-way view (VS Code's merge editor, IntelliJ's) and those are usually the path of least resistance.

rerere: resolve once, replay forever

The setting that makes rebasing a long-lived branch bearable.

Reuse recorded resolution. When enabled, Git records a fingerprint of every conflict it shows you along with the resolution you produced. The next time the identical conflict appears, it applies your previous answer automatically.

rerere
$ git config --global rerere.enabled true
$ git config --global rerere.autoUpdate true    # also stage the auto-resolved files

$ git rerere status         # which paths have recorded conflicts in this operation
$ git rerere remaining      # which are still unresolved
$ git rerere diff           # what your recorded resolution does
$ git rerere forget src/config.js   # I resolved that wrongly — discard the memory
$ ls .git/rr-cache          # one directory per remembered conflict

Where this matters: you rebase a five-commit branch onto a moving main, and the same conflict in the same file appears once per commit, five times. Without rerere you resolve it five times identically. With it, you resolve it once. The same applies to repeatedly merging main into a long-running branch.

It replays your mistakes too

rerere has no idea whether your resolution was correct — it replays whatever you did. If you resolved a conflict badly and it keeps reappearing correctly resolved, that is rerere being loyal. git rerere forget <path> clears one memory; deleting .git/rr-cache clears them all. This is a reason to look at what a "clean" rebase actually produced rather than trusting the absence of conflicts.

Avoiding conflicts structurally

Most recurring conflicts are a repository problem, not a people problem.

The four sources worth engineering away

Recurring conflict inReal causeFix
Everything, on whitespaceNo agreed formatterCommit a formatter config, run it in CI, one formatting commit in .git-blame-ignore-revs
CHANGELOG.mdEveryone appends to the same placemerge=union, or generate it from commits (ch. 6)
LockfilesTwo dependency changes, both regeneratingTake one side, then re-run the package manager. Never hand-merge
Generated or built filesThey are committed at allRemove from the repository; build them
.gitattributes
# take both sides, in order — right for append-only files
CHANGELOG.md      merge=union

# never try to merge these; resolve by regenerating
package-lock.json merge=ours
yarn.lock         merge=ours

# treat as opaque: no line merging, no diff noise
*.pdf             binary
*.png             binary
the "ours" driver has to be defined
$ git config --global merge.ours.driver true    # 'true' the command: succeed, keep ours

# then, after a merge that touched dependencies
$ npm install && git add package-lock.json

merge=union is the one built-in driver worth knowing: on a conflict it concatenates both sides with no markers. Correct for changelogs and lists, actively dangerous for code — it will happily produce a file with two contradictory function definitions and no indication that anything happened.

And the habits

  • Short-lived branches. Chapter 9 quantified why: overlap risk climbs with age.
  • Rebase or merge from main daily, not at the end. Conflicts resolved one day at a time are small.
  • Land refactors and moves separately from behaviour changes, and land them fast.
  • Tell people before you reformat a shared file. This is a calendar problem, not a Git one.

The short version

Chapter 11 in seven lines

  • Mid-conflict, the authoritative data is the index with three stages per path — base, ours, theirs — readable as :1:, :2:, :3:. The markers on disk are just a rendering.
  • UU is a normal conflict; UD and DU are delete-versus-modify and need a decision (git rm or git add), not editing.
  • The default marker style hides the base. Set merge.conflictStyle zdiff3 — it shows the base and keeps lines both sides agreed on outside the markers.
  • git checkout --ours <file> takes the whole file, discarding their clean changes too. Rarely what you want.
  • Resolve, git add, git merge --continue. Git does not check for leftover markers — git diff --check does.
  • rerere.enabled true records resolutions and replays them, which is what makes rebasing a long branch tolerable — including replaying your mistakes.
  • Recurring conflicts are usually structural: agree a formatter, merge=union for changelogs, regenerate lockfiles, and stop committing generated files.

Check yourself

You mangled a conflicted file while editing and want the markers back. What do you run?

git checkout --merge -- <file> regenerates the conflicted version from the index's three stages, and git checkout --conflict=zdiff3 -- <file> does the same in a more informative style. Nothing was lost, because the file on disk is only a rendering — the base, ours and theirs blobs are all still in the index until you git add. That is also why git show :1:<file> works at any point during the conflict.

git status says "deleted by them" for a file you modified. What are your options and how do you tell Git which you chose?

Two options: keep the file (their deletion loses) with git add <file>, or accept the deletion (your modification loses) with git rm <file>. There are no conflict markers to edit, because the disagreement is about the file's existence, not its contents. Before deciding, look at what you changed — git diff :1:<file> :2:<file> — and at why they deleted it, since a deletion usually means the code moved somewhere else and your change may need to move with it.

You are rebasing a six-commit branch and the same conflict in the same file appears on commit after commit. What is happening, and what would have prevented it?

Rebase replays each commit onto the new base in turn, so a change on main that conflicts with something all six of your commits touch produces the conflict six times — once per replay. rerere.enabled true would have recorded your first resolution and applied it automatically to the remaining five. Failing that, git rebase --continue after each is correct but tedious; squashing your branch into fewer commits first also reduces the number of replays.

Your team keeps conflicting on package-lock.json. Someone suggests merge=union. Why is that a bad idea, and what is the right answer?

union concatenates both sides, producing a lockfile with duplicated and contradictory dependency entries and no markers to warn you — it would be silently invalid, and the failure would appear later as a mysterious install. Lockfiles are generated artefacts: mark them merge=ours (with merge.ours.driver true defined) so the merge takes one side without complaint, then re-run the package manager and commit the regenerated file. union is correct only for genuinely append-only text such as a changelog.
