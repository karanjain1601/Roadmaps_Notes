Collaborating through pull requests

A pull request is not a Git concept. It is a web page around two refs and a conversation — but the button at the bottom performs a real Git operation, and which of the three you press determines what your history looks like forever. This chapter is about that button, and the rules that decide who may press it.

Forks or branches

Forks exist for the case where a contributor cannot be trusted with write access — which is also why GitHub does not expose repository secrets to workflows triggered by a fork's pull request. That restriction is a frequent source of "CI works for us and fails for contributors", and chapter 21 covers the safe way around it.

keeping a fork current
$ git remote add upstream https://github.com/original/api.git
$ git config remote.pushDefault origin      # ch. 15's triangular setup

$ git fetch upstream
$ git switch main && git merge --ff-only upstream/main && git push
# or, without leaving your branch:
$ git fetch upstream && git rebase upstream/main

Fast-forward-only is the right merge for syncing a fork's main: your copy should be a pure mirror, and if it cannot fast-forward, something has been committed to it that should not have been.

What a pull request is, in Git terms

A base ref, a head ref, and a diff computed the way chapter 6 described.

GitHub stores a pull request as two references and publishes them in the base repository, whether or not the head is a fork:

RefIs
refs/pull/42/headThe tip of the PR branch, as pushed
refs/pull/42/mergeA test merge of the PR into the base, recomputed by GitHub. This is what "can be merged cleanly" is checked against, and what many CI systems actually build
reviewing a PR locally, without adding a remote
$ git fetch origin pull/42/head:pr-42       # ch. 15's refspec, in anger
$ git switch pr-42

$ gh pr checkout 42                          # the GitHub CLI does the same thing
$ gh pr diff 42
$ gh pr view 42 --comments

The diff you see is a three-dot diff. GitHub compares the merge base of base and head against the head, so changes that landed on main after you branched do not pollute your PR — exactly git diff main...feature from chapter 6. This is why a PR's "files changed" count can be smaller than git diff main feature suggests, and why the number changes when you rebase.

Commits view versus files view

The Files tab shows the cumulative diff; the Commits tab shows each commit. A reviewer reading the Files tab does not see your development history at all — which is the practical argument for both keeping commits clean (chapter 5) and not agonising over them if the team squash-merges. If your commits tell a story worth reading, say so in the PR description, because the default view hides it.

Review mechanics

The parts that are not obvious from the buttons.

  • Batch your comments. Starting a review and submitting once sends one notification; commenting line by line sends one per comment.
  • Suggestions are commits. A suggestion code block renders as a diff the author can apply with a click, which becomes a commit authored by them and co-authored by you.
  • Three review states. Comment (no verdict), Approve, Request changes. Only the last two count toward protection rules, and "request changes" from one reviewer blocks merging until they revisit it.
  • CODEOWNERS maps paths to people or teams, and combines with "require review from code owners" so the right people are pulled in automatically.
  • After a force-push, GitHub shows a "force-pushed" timeline entry with a compare link. Locally, git range-diff (chapter 7) tells you what actually changed between the two versions of the branch.

Pick one and enforce it. The genuinely bad outcome is a repository where all three are enabled and used at random, because then no property holds: history is neither linear nor complete, reverting requires investigation, and --first-parent shows an arbitrary subset of the work.

A defensible default

Squash for most teams. One commit per pull request on main means the log reads like a changelog, reverting is trivial, and bisect lands on a reviewed unit rather than a half-finished commit — and it removes any need for contributors to master interactive rebase. Keep merge commits if your commits are carefully crafted and you want them, and reach for rebase-and-merge only when you both want linear history and value the individual commits.

Merge queues

"Require branches to be up to date" is correct and does not scale: with twenty merges a day, every PR must rebase after every other PR merges. A merge queue fixes it by testing the combination for you — it builds a temporary branch with your PR on top of the queue's current state, runs the checks there, and merges only if they pass, kicking out anything that fails. The result is main-is-always-green without every author re-testing by hand.

Making a PR reviewable

The mechanical parts, which are most of them.

  • Size. Under about 400 changed lines gets a real review; several thousand gets an approval. If it must be large, split it into a stack (chapter 9) and say which order to read them in.
  • Separate the mechanical from the meaningful. Renames, moves and reformatting in their own PR, merged first. A reviewer should never have to find three real lines among four hundred.
  • Say what and why in the description, not just the ticket number. A template in .github/pull_request_template.md makes it the default.
  • Link the issue with a closing keyword — Closes #421 — so the tracker updates itself on merge (chapter 5).
  • Draft until it is ready. A draft PR gets CI and no reviewer notifications, which is the right way to open something early.
  • Answer every comment, even with "done". Unresolved threads are how a PR stalls for a week.

The short version

Chapter 16 in seven lines

  • Forks exist for contributors without write access, and are why PR workflows from forks do not get repository secrets.
  • A pull request is two refs: refs/pull/N/head and GitHub's test merge refs/pull/N/merge. Both are fetchable with an ordinary refspec.
  • The PR diff is a three-dot diff against the merge base, so unrelated changes on main never appear in it.
  • Merge commit keeps every commit and records integration; squash gives one commit per PR with Co-authored-by trailers; rebase replays commits with new hashes and no merge point.
  • Pick one button and enforce it — mixing all three means no property of your history holds.
  • Protection rules are the enforcement layer: required PR, approvals, checks, up-to-date, linear history, signatures, no force-push. "Include administrators" is off by default.
  • "Require up to date" does not scale; a merge queue tests the combination so every author does not have to rebase after every merge.

Check yourself

Your team squash-merges. A contributor asks whether they should clean up their 14 commits before review. What do you tell them?

That the commits will not survive the merge, so tidying them is optional — but the Commits tab is still how a reviewer follows a large change, so a coherent sequence helps review even when it is discarded. What matters much more is the PR title and description, because with squash merging those become the commit message on main forever. If the team used merge commits or rebase-and-merge instead, the answer flips: those commits are permanent history and worth an interactive rebase.

A PR's "Files changed" shows 3 files, but git diff main feature locally shows 40. Who is wrong?

Neither. GitHub shows the three-dot diff — merge base to head — so it displays only what the branch changed. Your two-dot git diff main feature compares the two tips, which also includes the reversal of everything that landed on main since you branched, appearing as if your branch removed it. Run git diff main...feature (three dots) to match what the reviewer sees. Chapter 6's demo shows the two interpretations side by side.

A required status check called ci/test was renamed to ci/unit. What happens to the protection rule?

The rule still requires ci/test, which now never reports — so every PR blocks with "Expected — Waiting for status to be reported" and never clears, since nothing will ever post that name. The inverse is worse: if the rule is deleted or the name is not required, PRs merge with no check at all and nothing flags it. Renaming a CI job is therefore a two-part change: rename the job and update the required-checks list in the same breath.

Your repo has all three merge buttons enabled. Describe a concrete problem this causes six months later.

You need to revert a feature that shipped last month. If it was squash-merged it is one commit and one revert; if it was merge-committed you need revert -m 1 and must know that; if it was rebase-and-merged there is no single object representing it at all — you must find its commits by reading the log and revert each. Meanwhile git log --first-parent, the tool for reading main, shows the merge-committed PRs as one entry each and the rebased ones as every individual commit, so it is no longer a summary of anything. Enforcing one button makes all of these questions have one answer.
