The three trees

Git's reputation for confusing commands comes almost entirely from one design choice: there is a third place your files exist, between the folder you edit and the history you commit. Learn to see all three at once and add, reset, restore and status stop being folklore.

30 min2 demos7 sections4 self-checks

Three trees, one question each

Git's own term. "Tree" here means "a complete set of tracked files with their contents".

TreeAnswersLives inChanged by
HEADWhat did my last commit contain?The object store, via .git/HEADcommit, checkout, switch, reset, merge
IndexWhat will my next commit contain?.git/indexadd, rm, restore --staged, reset
Working treeWhat am I editing right now?Your actual folderYour editor, restore, checkout, reset --hard

The index is the unusual one. Most version control systems commit whatever is on disk; Git commits what is in the index, and git add is the act of copying content from disk into it. That indirection is the price of a genuinely useful feature: you can commit a subset of what you have changed, and you can shape that subset line by line before committing.

It also explains a phrase that otherwise makes no sense — "staged for commit". Staging is not a flag on a file. It is the fact that the index copy of that file differs from the HEAD copy.

Three names, one thing

The documentation calls it the index, the tutorials call it the staging area, and the plumbing calls it the cache — hence git diff --cached and git rm --cached. All three refer to .git/index. When you see "cached" in a flag, read "index".

The index is a file, not a metaphor

Once you have seen its contents, staging stops being mysterious.

the index, printed
$ git ls-files --stage
100644 a45bd4f1c9b7e2d3f8a01c5e6b7d8e9f0a1b2c3d 0	README.md
100755 7d9f3c2b8a4e1f6d5c0b9a8e7f6d5c4b3a2f1e0d 0	build.sh
100644 2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e 0	src/app.js

Mode, blob hash, stage number, path. It is a flat list — no directory structure, because paths are stored whole. When you commit, Git converts this flat list into the nested tree objects of chapter 2, which is what git write-tree does.

Two details matter in practice:

The stat cache is why status is fast

Alongside each entry the index stores the file's size, inode, mode and modification times as of the last time Git looked. git status compares those cached numbers against the file system; only when they differ does it read the file and hash it. On a large repository, this turns "hash a hundred thousand files" into "stat a hundred thousand files", which is orders of magnitude cheaper — and it is why git status is sometimes slow the first time after a clone or a checkout, then fast.

when the cache goes stale
$ git update-index --refresh     # re-stat everything and quietly fix the cache
$ git status --untracked-files=no  # skip the untracked scan on huge trees
$ git config core.fsmonitor true   # 2.37+: use a filesystem monitor instead of scanning

Stage numbers exist for conflicts

The 0 column above means "no conflict". During a conflicted merge the same path appears three times, with stages 1, 2 and 3 — the common ancestor, our version, and theirs. That is where the conflict markers in your file come from, and resolving a conflict means writing a stage-0 entry that replaces all three. Chapter 11 takes this apart.

Two flags people misuse

--assume-unchanged and --skip-worktree both tell Git to stop noticing local modifications to a tracked file, and both are routinely misused to keep local edits to a committed config.json out of sight. They are not a secret-keeping mechanism: the file is still tracked, a checkout or merge can still overwrite it, and the moment you or a script forces a refresh, your edits show up or get lost. If a file must differ per developer, it should not be tracked — commit config.example.json instead.

The three resets, in one line each

--soft moves HEAD only — your staged changes survive and now include what was in the discarded commit. --mixed (the default) moves HEAD and rewrites the index — changes survive, unstaged. --hard moves HEAD and rewrites the index and your working tree — uncommitted work is gone. Try each in the simulator and watch which columns change colour.

Reading git status properly

Two columns, and everyone reads only the first.

The short form prints two characters per file. X is the index versus HEAD; Y is the working tree versus the index. Once you know that, every combination is decodable.

git status --short --branch
## main...origin/main [ahead 2, behind 1]
M  src/app.js        <- staged modification, working tree matches the index
 M src/util.js       <- modified on disk, nothing staged
MM README.md         <- staged a change, then edited the file again
A  src/new.js        <- new file, staged
 D docs/old.md       <- deleted on disk, deletion not staged
D  docs/gone.md      <- deletion staged
R  a.txt -> b.txt    <- rename detected and staged
?? scratch.tmp       <- untracked
!! build/            <- ignored (only shown with --ignored)
UU src/merge.js      <- unmerged: both sides changed it (ch. 11)

MM is the one worth internalising. It means the version you staged is not the version on disk, so git commit will record the older one. Roughly half of all "but I fixed that" moments are an MM nobody read.

for scripts
$ git status --porcelain=v2 --branch --untracked-files=all
# branch.oid 8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3
# branch.head main
# branch.upstream origin/main
# branch.ab +2 -1
1 M. N... 100644 100644 100644 a45bd4f 7d9f3c2 src/app.js
? scratch.tmp

Version 2 of the porcelain format is explicitly stable and includes the hashes and modes, so a script never has to run a second command to get them. Use it instead of parsing the human output — chapter 1 explained why.

The diff matrix

Three trees means three interesting pairs, and git diff shows you a different one depending on flags nobody remembers.

CommandComparesAnswers
git diffIndex → working treeWhat have I changed but not staged?
git diff --staged
git diff --cached		HEAD → indexWhat exactly will this commit contain?
git diff HEADHEAD → working treeEverything I have changed since the last commit
git diff <commit>That commit → working treeHow far has the tree drifted from there?
git diff A BTwo commitsWhat differs between these two states?
git diff A...BMerge base of A and B → BWhat did B add since it diverged? (ch. 6)

Useful modifiers, all composable with the above:

diff modifiers worth knowing
$ git diff --stat                 # summary: files changed, insertions, deletions
$ git diff --name-only            # just the paths — pipe this into other tools
$ git diff --word-diff=color      # word-level, for prose and long lines
$ git diff -w                     # ignore whitespace changes entirely
$ git diff --find-renames=40%     # be more eager about detecting renames
$ git diff -- src/                # limit to a path
$ git diff --diff-filter=M        # only modified (A added, D deleted, R renamed…)

Before committing, the habit worth building is git diff --staged, not git diff. The first shows what you are about to record; the second shows what you are about to leave behind. Setting commit.verbose true (chapter 1) puts that staged diff in your editor automatically while you write the message.

Staging on purpose

The feature the index exists for.

You fixed a bug, and while you were in there you renamed a variable, added a log line and reformatted a function. Committing that as one change makes it unreviewable and unrevertable. git add -p splits it:

interactive staging
$ git add -p src/app.js
@@ -14,7 +14,7 @@ function login(user) {
-  if (attempts > 3) lock(user)
+  if (attempts >= MAX_ATTEMPTS) lock(user)

(1/3) Stage this hunk [y,n,q,a,d,s,e,?]?
KeyDoes
y / nStage this hunk / skip it
sSplit into smaller hunks — try this first when a hunk is too big
eEdit the hunk by hand: delete + lines to skip them, turn - into a space to keep a deletion out
a / dStage all remaining hunks in this file / skip all of them
qQuit; what you have already staged stays staged
?Explain every key

Three companions to it:

  • git add -N <file> registers an untracked file with no content, so add -p will offer its hunks. Without this, brand-new files are all-or-nothing.
  • git restore --staged -p is the inverse: remove selected hunks from the index.
  • git stash push -p stashes selected hunks, useful when you want to test the half you kept (ch. 14).

The four ways to say "add everything"

CommandNew filesModifiedDeletionsScope
git add .yesyesyesCurrent directory down
git add -AyesyesyesWhole repository
git add -unoyesyesTracked files only
git add *yesyesnoWhatever the shell expands — avoid

git add * is a shell glob, not a Git feature: the shell expands it before Git sees it, so it skips dotfiles and cannot represent deleted files. Use . or -A.

How .gitignore really resolves

Four sources, ordered patterns, and one rule that catches everyone.

Git consults several ignore sources, later ones overriding earlier:

  1. core.excludesFile — your personal global list (editor swap files, OS junk)
  2. .git/info/exclude — repository-local, not committed, invisible to teammates
  3. .gitignore files in the tree, with deeper directories overriding shallower ones
  4. Patterns passed on the command line to plumbing commands

Within one file, the last matching pattern wins, which is what makes ! negation work at all.

PatternMatches
*.logAny .log file at any depth
/*.logOnly in the directory holding this .gitignore
build/Directories named build, at any depth — never a file
doc/*.txtContains a slash, so it is anchored: doc/a.txt but not doc/api/a.txt
doc/**/*.txt** crosses directory boundaries: doc/api/v2/a.txt too
!keep.logRe-includes a file an earlier pattern excluded
temp?.dat? is exactly one character, never /
[Dd]ebug/Character classes work as in shell globs

The trap everyone hits

.gitignore only affects untracked files. Once a file is in the index, Git tracks it forever regardless of what you add to .gitignore afterwards. Committing .env and then ignoring it changes nothing — the file keeps showing up in diffs and stays in history.

stop tracking, keep the file on disk
$ git rm --cached .env
$ echo ".env" >> .gitignore
$ git commit -m "Stop tracking local env file"

# and if it held a real secret, rotate it — it is still in history (ch. 23)
debugging ignore rules
$ git check-ignore -v build/output.js
.gitignore:2:build/	build/output.js       # file, line number, pattern that won

$ git status --ignored --short          # list what is being hidden from you
$ git config --global core.excludesFile ~/.gitignore_global

The short version

Chapter 03 in seven lines

  • Three trees: HEAD (last commit), index (next commit), working tree (what you're editing). Nearly every command moves content between two of them.
  • The index is a real file listing mode, blob hash, stage and path, plus a stat cache that makes git status fast.
  • "Staged" is not a flag — it means the index copy differs from the HEAD copy.
  • git status --short prints XY: X is index versus HEAD, Y is working tree versus index. MM means you staged one version and then changed the file again.
  • Plain git diff shows what you did not stage; git diff --staged shows what you are about to commit.
  • reset --soft moves HEAD; --mixed also rewrites the index; --hard also rewrites the working tree and can lose work.
  • .gitignore is last-match-wins per file, and applies only to untracked files — already-tracked files need git rm --cached.

Check yourself

You stage a file, edit it again, then run git commit. What gets committed, and how would you have spotted the problem first?

The version you staged — the index copy — not what is on disk. git status --short would have shown MM, and git diff (index versus working tree) would have shown the edits that are about to be left out. Setting commit.verbose true shows the staged diff in your editor as you write the message, which catches this without any extra command.

What is the difference between git restore --staged file and git restore file? Which one can lose work?

--staged copies HEAD's version over the index entry: it unstages, and your working-tree edits are untouched. Plain git restore file copies the index version over the file on disk: it discards your uncommitted edits, permanently, with no reflog and no recovery. The second one is the dangerous one. (git restore --staged --worktree file does both and is equivalent to the old git checkout HEAD -- file.)

Your .gitignore contains logs/ then !logs/keep.log, but logs/keep.log is still ignored. Why?

Git does not descend into an excluded directory, so a negation for something inside it never gets evaluated — a performance decision baked into the algorithm. Re-include the directory first and then exclude its contents: logs/* followed by !logs/keep.log. The simulator above reproduces this exactly; toggle the pattern and watch.

You ran git reset --soft HEAD~ by mistake. What state are you in, and how do you get back?

HEAD moved back one commit; your index and working tree are untouched, so everything from the discarded commit is still staged. Nothing is lost. git commit -c ORIG_HEAD recreates it reusing the original message and authorship, or git reset --soft ORIG_HEAD puts HEAD back exactly where it was. The commit object itself was never deleted — it is unreachable, not gone, and the reflog still names it (ch. 4).
