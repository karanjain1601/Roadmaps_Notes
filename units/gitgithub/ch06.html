Reading history

A repository is a database, and git log is its query language. Most people know three flags and answer every question by scrolling. The interesting queries are about ranges and content — what does this branch have that main doesn't, when did this string appear, who deleted this function — and each has a one-line answer.

The flags that earn their keep

git log takes over a hundred options. These are the ones worth memorising.

shape and volume
$ git log --oneline --graph --decorate -20     # the "what is going on here" view
$ git log --stat -3                            # which files, how many lines
$ git log -p -1                                # the full patch of the last commit
$ git log --name-status --oneline -5           # A/M/D per file, compactly
$ git log --no-merges --first-parent           # a readable spine of a merge-heavy history
filtering
$ git log --since="2 weeks ago" --until="yesterday"
$ git log --author="Priya" --oneline
$ git log --grep="401" --grep="token" --all-match -i    # both patterns, case-insensitive
$ git log --oneline -- src/auth/                        # only commits touching this path
$ git log --follow -- src/auth/token.js                 # ...and keep going across renames
$ git log -L 40,60:src/auth/token.js                    # the history of those lines only
$ git log -L :validateToken:src/auth/token.js           # the history of that function

Two of these are underused. -L gives the evolution of a specific region or function, which is usually the actual question when someone reaches for blame. And --follow is the only way to see history across a rename, because chapter 2 established that Git stores no rename information — it infers one by comparing content, and only --follow asks it to keep doing so backwards past the rename.

Why -- matters

git log foo is ambiguous: foo could be a branch or a file. Git guesses, and errors out if both exist. -- ends the revision list, so git log main -- foo is unambiguous. Any time a command takes both revisions and paths, put -- between them and the ambiguity disappears.

Revision ranges

The single most valuable syntax in Git, and the one most consistently misremembered.

A range is not "commits between two points" — histories branch, so there is no line to take a segment of. A range is set arithmetic over reachability:

ExpressionMeansPlain English
BEverything reachable from BB's whole history
A..Breachable(B) − reachable(A)What B has that A doesn't
^A BIdentical to A..BThe general form: any mix of includes and excludes
A...BSymmetric differenceWhat either side has that the other doesn't
A^!A, excluding its parentsJust that one commit
--allEvery ref as an includeEverything in the repository

So git log main..feature answers "what would I be merging?" and git log feature..main answers "how far behind is my branch?". They are different questions and neither is symmetric.

Range explorer

Same expression, two commands. Watch how log and diff interpret three dots differently.

Three dots means two different things

For git log, A...B is the symmetric difference — commits unique to either side. For git diff, A...B means "compare the merge base of A and B against B" — the change B introduced since it diverged. Same punctuation, unrelated meanings, and the diff one is what you want when reviewing a branch: git diff main...feature shows the feature's work without the unrelated changes that landed on main meanwhile.

who has what
$ git log --oneline --left-right main...feature
< c3d4e5f Update deployment docs      # < is on main only
> e5f6a7b Add cache layer             # > is on feature only

$ git rev-list --count --left-right main...feature
2	2

$ git merge-base main feature          # where they diverged
$ git merge-base --is-ancestor v1.0 HEAD && echo "v1.0 is in this history"

merge-base --is-ancestor is a silent yes/no via exit code, which makes it the right tool in a CI script asking "has this commit shipped?".

Blame, done properly

The default output is often wrong, and there is a fix for the usual reason.

blame
$ git blame src/auth/token.js
$ git blame -L 40,60 src/auth/token.js       # only these lines
$ git blame -w src/auth/token.js             # ignore whitespace-only changes
$ git blame -C -C src/auth/token.js          # follow lines moved from other files
$ git blame --reverse v1.0..HEAD -- file     # when did each line LAST exist?

-w and -C should almost be defaults. Without them, a line that was merely re-indented or moved between files is credited to whoever moved it, and the real history is one hop further back than blame admits.

Making reformat commits invisible

The bigger problem is the commit that reformatted everything. It blames every line in the repository on one person on one day, and it is unfixable after the fact — except that Git can be told to look through it:

.git-blame-ignore-revs
# Run prettier across the whole tree
9c1f7a4b2e8d5c0a3f6b9e2d1c4a7b0e3f6d9c2a
# Convert tabs to spaces
4b7c9e2f1a8d3c6b0e9f2a5d8c1b4e7a0f3d6c9b
wire it up once, for everyone
$ git config blame.ignoreRevsFile .git-blame-ignore-revs
$ git blame src/app.js       # reformat commits are now looked through

Commit the file, and tell people to run that config line — or put it in a setup script. GitHub reads .git-blame-ignore-revs automatically in its blame view, so the fix applies on the web with no configuration at all.

Searching content, not messages

The pickaxe: find the commit where a string appeared or disappeared.

Commit messages are what people wrote; the diff is what actually happened. Two flags search the diffs, and the difference between them matters:

FlagFinds commits where…Use for
-S<string>The number of occurrences of the string changedWhen was this introduced or removed?
-G<regex>The diff text contains a match anywhereAny commit that touched a line matching this
-S… --pickaxe-regexAs -S, with the string treated as a regexCounting occurrences of a pattern

The distinction: a commit that moves a line containing API_KEY from one file to another does not change the count, so -S ignores it while -G reports it. When hunting for the origin of something, -S is far less noisy.

the pickaxe in anger
$ git log -S "validateToken" --oneline --all      # when did this identifier come and go?
$ git log -S "AWS_SECRET" --all --patch           # did a secret ever exist in history?
$ git log -G "console\.log" --oneline -- src/     # every commit touching a debug log
$ git log --diff-filter=D --oneline -- src/old/   # which commit deleted these files?
$ git log --diff-filter=A --oneline -- src/new.js # which commit added this file?

git grep: search the code, at any revision

grep that understands revisions
$ git grep -n "TODO"                         # working tree, tracked files only, fast
$ git grep -n "validateToken" v1.0           # search a tag's tree without checking it out
$ git grep -n --heading --break "token"      # grouped by file, readable
$ git grep -e "token" --and -e "expiry"      # both on the same line
$ git grep -c "console.log" -- src/          # count per file

git grep beats grep -r in a repository for two reasons: it skips untracked files and everything in .gitignore (no searching node_modules), and it can search a commit that is not checked out.

The short version

Chapter 06 in seven lines

  • --oneline --graph --decorate for orientation; --stat, -p, --name-status for detail; --first-parent to read a merge-heavy history as a spine.
  • Ranges are set arithmetic on reachability: A..B is reachable(B) minus reachable(A), and ^A B is the same thing written generally.
  • A...B is the symmetric difference in log and merge-base-to-B in diff. Two meanings, one punctuation.
  • git diff main...feature is the right way to review a branch — it excludes what landed on main meanwhile.
  • --format turns log into a report generator; %h %s %an %ar plus %C() covers most needs.
  • Blame with -w -C, and commit a .git-blame-ignore-revs so reformat commits stop hiding real authorship — GitHub honours it too.
  • -S finds where a string's count changed (low noise); -G finds any diff mentioning it; git grep <rev> searches a commit you have not checked out.

Check yourself

Someone asks "what's in my feature branch that isn't in main yet?" — and separately, "show me the diff a reviewer would see". Which two commands?

git log --oneline main..feature lists the commits unique to the branch. For the reviewer's diff, git diff main...feature — three dots, because that compares the merge base with the branch tip and therefore excludes anything that landed on main since you branched. Using git diff main feature (or two dots) mixes in the reversal of main's newer work, which is why branch diffs sometimes look bizarre.

You need to know which commit removed the string LEGACY_MODE. Why is -S better than --grep or -G here?

--grep searches commit messages, and whoever removed it almost certainly did not mention it. -G "LEGACY_MODE" matches every commit whose diff touches any line containing it — including reformats and moves, so you get noise. -S "LEGACY_MODE" only reports commits where the number of occurrences changed, so the youngest hit is the removal and the oldest is the introduction.

git blame says your colleague wrote every line of a 900-line file last Tuesday. What probably happened, and what do you do?

A whole-tree reformat or a file move. Try git blame -w -C -C first, which ignores whitespace-only changes and follows lines moved from other files. If it was a formatting commit, record its hash in .git-blame-ignore-revs and set blame.ignoreRevsFile — blame then looks through it to the real authorship, and GitHub's web blame picks the file up automatically.

In CI you need to fail a job unless the current commit already exists on main. What is the cheapest check?

git merge-base --is-ancestor "$SHA" origin/main — it prints nothing and exits 0 for yes, 1 for no, so it drops straight into a shell conditional. Alternatives like git branch --contains produce output you would have to parse, and git log ranges do far more work than a reachability test needs. Note the job must have fetched origin/main: CI checkouts are often shallow and single-branch (ch. 20).
