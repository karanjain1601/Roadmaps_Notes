Diffs and patches

Chapter 2 established that Git stores no diffs — every one you see was computed on demand, by an algorithm, with choices. Different algorithms produce different diffs of the same change, one of them much easier to read. And a diff written to a file becomes a patch, which is how code moved between people for twenty years before pull requests existed.

Three lines of context is the default because it is the minimum that reliably lets a patch be applied to a file that has drifted slightly. -U0 makes a patch that only applies to the exact file it came from.

Algorithms, and why your diff looks wrong

Every diff is a guess about intent, and some guesses are better.

Given two versions of a file, there are many valid edit scripts that transform one into the other. Finding the shortest one is a well-defined problem — the longest common subsequence — and Git's default myers algorithm solves it. The trouble is that "shortest" and "most readable" are not the same thing: when a file contains many identical lines like } or blank lines, the shortest script happily matches your new closing brace with somebody else's, and the diff attributes your change to the wrong function.

What to actually set

git config --global diff.algorithm histogram. Every algorithm here produces a correct patch — this is purely about the human reading it, which is most of what a diff is for. Two honest caveats. Git's myers is not a textbook LCS: its tie-breaking, plus --indent-heuristic (on by default since 2.14), already avoids many of these artifacts, so the gap is smaller than older write-ups suggest. And the divergence grows with file size and repetition — on a six-line example the algorithms almost always agree, as the demo will show you.

Whitespace, words and moved code

Four flags that turn an unreadable diff into a reviewable one.

seeing through the noise
$ git diff -w                        # ignore all whitespace changes
$ git diff --ignore-blank-lines      # ignore added/removed empty lines
$ git diff --word-diff               # mark changes within a line, not whole lines
$ git diff --word-diff-regex='\w+'   # define what a "word" is
$ git diff --color-moved=zebra       # show moved blocks in a distinct colour
$ git diff --color-moved-ws=allow-indentation-change   # ...even if re-indented

--word-diff is transformative for prose, YAML and long lines — a one-character change stops rendering as a removed line plus an added line:

--word-diff on a config change
-timeout: 30
+timeout: 60
the same change, word diff
timeout: [-30-]{+60+}

--color-moved is the one to reach for when reviewing a refactor. A pull request that moves 400 lines between files and changes three of them is unreviewable by default; with move detection on, the moved blocks are dimmed as a class and the three real changes stand out. Turn it on permanently with diff.colorMoved = zebra.

Rename and copy detection

Git stores no rename information. Every rename you see was inferred.

Chapter 2 established that a blob has no name. So when a file appears at a new path and disappears from an old one, Git compares content and decides whether to call it a rename. The threshold is a similarity percentage:

a detected rename
diff --git a/src/auth.js b/src/auth/token.js
similarity index 91%
rename from src/auth.js
rename to src/auth/token.js
index a45bd4f..7d9f3c2 100644
tuning it
$ git diff -M                     # detect renames (on by default since 2.9)
$ git diff --find-renames=40%     # be more willing to call it a rename
$ git diff -C -C                  # also detect copies, searching all files
$ git log --follow -- new/path    # follow one file's history back through renames
$ git diff --no-renames           # show them as a delete plus an add

Two consequences. First, a rename combined with heavy editing crosses below the threshold and shows up as an unrelated delete and add, losing the file's history in --follow; committing the rename separately from the edits avoids this entirely. Second, git log --follow only accepts a single path, because the inference is per-file — there is no repository-wide rename log to consult.

Patches: diffs as a transport

Write a diff to a file and it becomes something you can email.

Two ways to produce one, and they are not interchangeable:

Preserves authorshipnoyes

producing patches
$ git diff > wip.patch                    # unstaged changes
$ git diff --staged > staged.patch        # staged changes
$ git format-patch -3                     # the last three commits, one file each
$ git format-patch main..feature          # every commit the branch adds
$ git format-patch --stdout main..feature > series.mbox     # one mailbox file
$ git format-patch --cover-letter -3      # plus a 0000-cover-letter.patch to fill in
applying them
$ git apply --check wip.patch      # dry run: will this apply cleanly?
$ git apply --stat wip.patch       # what does it claim to change?
$ git apply wip.patch              # apply to the working tree only
$ git apply --index wip.patch      # ...and stage it at the same time
$ git apply --3way wip.patch       # fall back to a three-way merge, leaving conflicts
$ git apply --reject wip.patch     # apply what fits, write the rest to .rej files

$ git am 0001-fix-thing.patch      # recreate the commit, preserving authorship
$ git am -3 series.mbox            # with three-way fallback
$ git am --abort                   # give up and restore the branch
$ git am --skip                    # skip this patch, continue the series

Why three-way works when plain apply fails

The index a45bd4f..7d9f3c2 line in a Git-generated patch names the blob the patch was made against. If your repository happens to contain that blob — likely, if you share history — --3way can perform a real merge between the original, the patched version and your current file, exactly like merging a branch. Plain apply has only text matching to work with, so it either finds the context or gives up. This is also why git apply --3way can leave conflict markers, while plain apply never does.

Comparing two versions of a change

The tool for reviewing a force-pushed branch.

Someone rewrites a branch and force-pushes. Every commit has a new hash, so a plain diff of the two tips tells you nothing about what actually changed between the two versions of the work. git range-diff compares two commit ranges pairwise and diffs the diffs:

git range-diff
$ git range-diff main old-feature main new-feature
1:  a1b2c3d = 1:  9f8e7d6 Add token parser
2:  b2c3d4e ! 2:  8e7d6c5 Return 401 for expired tokens
    @@ -14,7 +14,7 @@ function validateToken(raw) {
       const parsed = parse(raw)
     -  if (parsed.exp < now()) {
     -    throw new Error("bad token")
     +  if (parsed.exp <= now()) {
     +    throw new ExpiredToken()
3:  --------- > 3:  7d6c5b4 Add regression test

Read the markers: = means unchanged, ! means this commit's content changed and shows how, > means newly added, < means dropped. In one screen you can see that commit 1 is untouched, commit 2 changed a comparison operator, and a test was added — which is precisely what a reviewer needs after a rewrite.

shorthands
$ git range-diff @{u}...HEAD        # my branch before and after I rebased it
$ git range-diff main old..new      # explicit bases

Check yourself

A colleague sends a patch file. git apply fails with "patch does not apply", but git apply --3way succeeds. What was different?

Plain apply is pure text matching: it needs the context lines to be present, at the stated position or a small offset away. Your file had drifted enough that the context no longer matched. --3way reads the blob hashes from the patch's index line, finds that original blob in your object store, and performs a genuine three-way merge between it, the patched result and your current file — which succeeds whenever the drift and the patch touch different lines, and leaves conflict markers when they overlap.

Why does a diff sometimes show a closing brace being removed and added in a place you didn't edit?

Because } appears many times in the file and a minimal edit script is free to pair any occurrence with any other. The algorithm optimises for the fewest changed lines, not for matching structure, so it can pick a pairing that is minimal and semantically wrong. Patience and histogram avoid it by anchoring only on lines that are unique on both sides, which repetitive syntax lines never are. The demo shows the ambiguity directly: on its constructed fixture the two algorithms emit different scripts for the same change, both valid, differing only in which repeated line they treat as unchanged.

You want to send three commits to a project with no write access and no pull request workflow. Which commands, and why not git diff?

git format-patch -3 (or --stdout into one mailbox), then the maintainer runs git am. A plain git diff would flatten all three commits into one anonymous blob of changes: no messages, no separation, and you would not be recorded as the author — am recreates each commit with your name, date and message, and the maintainer appears only as committer.

A pull request you already reviewed gets force-pushed. What do you run to see what changed since your review?

git range-diff between the two versions, for example git range-diff main old-sha..new-sha after saving the old tip (or using your reflog / origin/feature@{1}). It pairs up commits across the rewrite and shows a diff-of-diffs, so you see that four commits are identical and one changed a single line — rather than re-reviewing the whole branch because every hash is new.
