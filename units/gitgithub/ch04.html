Refs, HEAD and the reflog

Chapter 2 built a store of immutable objects. On its own that is a graph with no entrances. Refs are the entrances — mutable names pointing into an immutable graph — and the reflog is a record of every name that ever pointed anywhere. Together they are why Git is much harder to lose work in than its reputation suggests.

28 min2 demos7 sections4 self-checks

What a ref is

A name, a file, a hash. There is no more to it than that.

the ref namespace
$ find .git/refs -type f
.git/refs/heads/main
.git/refs/heads/feature/caching
.git/refs/tags/v1.0
.git/refs/remotes/origin/main

$ cat .git/refs/heads/main
8f3d2a19c1b0e4f8a7d6c5b4a3928170f6e5d4c3

Note feature/caching: a slash in a branch name is a real directory on disk, which is why feature and feature/caching cannot both exist — a file cannot also be a directory. That is the entire explanation for an error message that reads like a bug.

refs/tags/Tagsgit tag; conventionally never moved again
refs/remotes/<remote>/The last known position of a remote's branchesgit fetch — never you (ch. 15)
refs/stashThe stash stackgit stash (ch. 14)
refs/notes/Notes attached to commits after the factgit notes
refs/pull/<n>/headPull request heads — a GitHub convention, fetchableGitHub (ch. 16)

Symbolic refs

A ref may point at another ref instead of an object. .git/HEAD is the one you meet daily:

symbolic refs
$ cat .git/HEAD
ref: refs/heads/main

$ git symbolic-ref HEAD
refs/heads/main

$ git symbolic-ref refs/remotes/origin/HEAD    # which branch is the remote's default
refs/remotes/origin/main

Packed refs, and why a ref can be in two places

Thousands of one-line files is wasteful, so Git periodically consolidates them into .git/packed-refs. A ref may then exist as a loose file, a packed entry, or both — in which case the loose file wins. This is invisible in normal use, and the reason to know it is debugging: if find .git/refs shows nothing but git branch lists forty branches, they are packed.

listing refs the right way
$ git for-each-ref --format='%(refname) %(objecttype) %(objectname:short)'
refs/heads/main commit 8f3d2a1
refs/tags/v1.0 tag 4b7c9e2
refs/remotes/origin/main commit 8f3d2a1

$ git pack-refs --all      # consolidate; harmless, occasionally tidy

for-each-ref reads loose and packed refs together, which is why scripts should use it rather than walking the directory.

Legal names

Ref names cannot contain a space, ~ ^ : ? * [ \, two consecutive dots, or ASCII control characters; cannot begin or end with a slash or dot; and cannot end with .lock. Git will tell you, but if you are generating branch names in a script, validate them yourself:

validating a generated name
$ git check-ref-format --branch "feature/JIRA-42_cache"   && echo ok
$ git check-ref-format --branch "fix: broken thing"        || echo rejected

HEAD, attached and detached

One file explains an error message that has frightened a generation.

Normally HEAD is symbolic: it names a branch, and the branch names a commit. Committing moves the branch, and HEAD follows because it points at the branch, not the commit.

Sometimes HEAD holds a commit hash directly. That is detached HEAD, and it is not an error — it is Git telling you the truth: there is no branch here, so if you commit, nothing will be recording where your commits went except HEAD itself.

You didHEAD becomesWhy
git switch mainref: refs/heads/mainAttached — the normal state
git checkout 8f3d2a1The raw hashA commit is not a branch
git checkout v1.0The tag's commit hashTags are not branches either
git checkout origin/mainThe raw hashRemote-tracking refs are read-only locally
Mid rebase or bisectThe raw hashGit is replaying commits, temporarily
actions/checkout in CIThe raw hashCI checks out one commit, not a branch (ch. 20)

Detached HEAD is genuinely useful: it is how you inspect an old state, test a tag, or bisect. The only hazard is committing there and then switching away, at which point your commits are unreachable from any ref. Git warns you loudly, and the reflog still has them.

rescuing work made on a detached HEAD
# still detached — give the current position a name and stay on it
$ git switch -c rescue

# already switched away, and Git printed a warning you scrolled past
$ git reflog                        # find the commit you made
7e2a91c HEAD@{2}: commit: Try the faster hash
$ git branch rescue 7e2a91c         # a ref now points at it; it is safe
switch and restore, not checkout

git checkout does two unrelated jobs — moving HEAD and overwriting files — which is why git checkout main and git checkout main.py do wildly different things depending on whether the argument happens to be a branch. Since 2.23 there are two focused commands: git switch for HEAD, git restore for files. Use them. Keep reading checkout, because every answer written before 2019 uses it.

Naming any commit

The syntax in git help revisions, which is the vocabulary of every later chapter.

ExpressionMeans
HEAD, @The current commit. @ is a legal shorthand for HEAD
HEAD~, HEAD~3Walk back n generations, always taking the first parent
HEAD^, HEAD^2Select a parent: ^ is the first, ^2 the second (merges only)
HEAD^0The commit itself — used to peel a tag to its commit
HEAD^{tree}The tree object of that commit, not the commit
v1.0^{}Peel an annotated tag to the object it points at
@{u}, @{upstream}The upstream of the current branch, usually origin/main
@{push}Where a push would go — differs from upstream in triangular workflows
HEAD@{2}Where HEAD pointed two moves ago, from the reflog
main@{yesterday}Where main pointed then, from the reflog
:/fix quotingThe most recent commit whose message contains that text
HEAD:src/app.jsNot a commit — the blob at that path in that commit
:2:src/app.jsStage 2 of a conflicted path in the index (ch. 11)

The pair that causes most of the damage is ~ versus ^. They are identical until they meet a merge, and then they are completely different: HEAD~2 is "two commits back along the main line", HEAD^2 is "the branch that was merged in". Reach for the demo rather than trusting your memory.

Two facts that settle arguments

HEAD~2 and HEAD^^ are exactly the same thing. And HEAD~ on a merge commit follows the first parent, which is the branch you were on when you merged — that is what makes git log --first-parent a readable summary of a merge-heavy history (ch. 6).

Branches are ref operations

Every branch command is create, move, or delete a file.

branch operations, and what they do to refs
$ git branch feature              # write refs/heads/feature = HEAD
$ git switch -c feature           # the same, then point HEAD at it
$ git branch -m old new           # rename the file (and fix up config)
$ git branch -d feature           # delete — refuses if unmerged commits would be orphaned
$ git branch -D feature           # delete anyway
$ git branch -f main 8f3d2a1      # move main, without checking it out. Sharp.
$ git update-ref refs/heads/main 8f3d2a1   # the plumbing underneath all of the above

git branch -d versus -D is worth internalising: lowercase refuses to strand commits, uppercase does not care. Uppercase is not dangerous in the way it feels — the reflog keeps the commits alive for weeks — but the difference is a genuine safety check, so let it stop you and read what it says.

Upstream tracking

"Tracking" is two lines of config, nothing more:

.git/config
[branch "main"]
	remote = origin
	merge = refs/heads/main

That is what lets you type bare git pull and git push, and what @{u} resolves through. Manage it explicitly when it goes wrong:

tracking
$ git branch -vv                            # every branch, its upstream, ahead/behind
  feature 7e2a91c [origin/feature: ahead 2] Add cache warmer
* main    8f3d2a1 [origin/main] Merge pull request #218

$ git branch -u origin/main                 # set the upstream of the current branch
$ git branch --unset-upstream
$ git rev-list --left-right --count main...origin/main    # the ahead/behind numbers, exactly
2	1

Ahead and behind are computed, not stored, and they are computed against your last fetch. "Behind 0" after a week offline means nothing at all — it means nothing new has arrived in your copy of origin/main, not that nothing has happened.

Tags: two kinds, one recommendation

One is a ref. The other is an object with a ref pointing at it.

Created bygit tag v1.0git tag -a v1.0 -m "..."
Stored asA ref pointing straight at the commitA tag object — with its own hash — plus a ref pointing at it

tags in practice
$ git tag -a v1.2.0 -m "Release 1.2.0"
$ git tag -a v1.2.0 8f3d2a1 -m "Tag an older commit"
$ git tag -l 'v1.*' --sort=-v:refname        # version-aware sort, newest first
$ git show v1.2.0                            # the tag object, then the commit
$ git cat-file -p v1.2.0                     # just the tag object

$ git push origin v1.2.0                      # tags are NOT pushed by git push
$ git push --follow-tags                      # push annotated tags that point into what you pushed

$ git describe                                # v1.2.0-14-g7e2a91c: 14 commits past v1.2.0
$ git describe --tags --always --dirty         # the version string for a build
Trap: moving a published tag

git tag -f v1.0 then force-pushing looks like it works. It does not, for anyone who already fetched: Git does not update an existing tag on fetch, so their v1.0 keeps pointing at the old commit, silently and indefinitely. Two people then build "v1.0" from different code. Treat published tags as immutable and ship v1.0.1 instead. If you truly must, everyone needs git fetch --tags --force, and you have to tell them.

The reflog

Every value every ref has held, for the last few weeks.

Whenever a ref moves, Git appends a line to a log for that ref. Nothing consults these logs during normal operation; they exist purely so you can undo.

.git/logs/HEAD, raw
4b7c9e2 8f3d2a1 You <you@example.com> 1700003600 +0000	commit: Add cache warmer
8f3d2a1 7e2a91c You <you@example.com> 1700004100 +0000	reset: moving to HEAD~1
7e2a91c 8f3d2a1 You <you@example.com> 1700004500 +0000	reset: moving to 8f3d2a1

Old hash, new hash, who, when, why. Read it through the porcelain instead:

reading the reflog
$ git reflog                       # HEAD's reflog, newest first
8f3d2a1 HEAD@{0}: reset: moving to 8f3d2a1
7e2a91c HEAD@{1}: reset: moving to HEAD~1
8f3d2a1 HEAD@{2}: commit: Add cache warmer

$ git reflog show main             # one branch's own reflog
$ git reflog --date=relative       # "2 hours ago" instead of hashes-and-numbers
$ git log -g --oneline             # the reflog as a log, with messages

Four properties matter:

  • It is local. The reflog is never cloned, pushed or fetched. Your colleague's reflog cannot rescue your mistake, and a fresh clone has an almost empty one.
  • It keeps objects alive. A commit named only by a reflog entry is still reachable, so gc will not prune it. This is the mechanism behind almost every recovery in chapter 8.
  • It expires. Reachable entries after 90 days (gc.reflogExpire), unreachable ones after 30 (gc.reflogExpireUnreachable). Recovery is a matter of weeks, not forever.
  • Deleting a branch deletes its reflog. .git/logs/refs/heads/feature goes with the ref, which is why you recover a deleted branch from HEAD's reflog, not the branch's.

When there is no reflog entry

Commits made on a detached HEAD in a clone you then deleted, or objects that arrived by fetch and were never referenced, have no reflog line. They are still on disk until pruned, and fsck finds them:

last resort
$ git fsck --full --no-reflogs --unreachable --lost-found
unreachable commit 7e2a91c4d5f6a8b9c0d1e2f3a4b5c6d7e8f9a0b1
unreachable blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad

$ git show 7e2a91c            # is this the one?
$ git branch rescue 7e2a91c   # then it is saved

Unreachable blobs are worth knowing about too: a file you staged and then reset was written to the object store by git add, so an "unstaged and lost" edit is sometimes recoverable this way even though no commit ever held it.

The short version

Chapter 04 in eight lines

  • A ref is a file containing a hash. Branches, tags and remote-tracking refs differ only by which directory they live in — and may be consolidated into packed-refs, so list them with for-each-ref.
  • HEAD is normally symbolic (ref: refs/heads/main); when it holds a hash you are detached, which is fine until you commit and walk away.
  • ~ walks generations along first parents; ^n picks the nth parent. They differ only at merges, and that is where the mistakes happen.
  • @{u}, HEAD@{2}, :/text and HEAD:path all name things; git rev-parse resolves any of them.
  • Tracking is two config lines, and ahead/behind is computed against your last fetch — not against reality.
  • Annotated tags are objects and can be signed; lightweight tags are bare refs. Use annotated for anything published, and never move a published tag.
  • The reflog records every ref movement, is local only, keeps objects from being pruned, and expires after 90 days (30 if unreachable).
  • Deleting a branch deletes its reflog, so recover deleted branches from HEAD's reflog — and if there is no entry at all, git fsck --unreachable.

Check yourself

On a merge commit M, what is the difference between M~1 and M^2? Which one is the branch that got merged in?

M~1 is M's first parent: the tip of the branch you were standing on when you ran git merge. M^2 is the second parent: the tip of the branch you merged into it. So M^2 is the incoming feature branch. M~1 and M^1 are the same commit; the expressions only diverge when you go further, because ~2 keeps taking first parents while ^2 is a one-step parent selection.

You created a branch called release, and later git branch release/2.0 fails. Why?

Because refs are files. refs/heads/release exists as a file, and refs/heads/release/2.0 would need release to be a directory. Git reports it as a lock/creation failure. Either delete or rename the first branch, or adopt a naming scheme where no branch name is a prefix of another — release-2.0, or release/1.0 and release/2.0 with nothing at the bare release path.

A colleague force-pushed and your local main now points at a commit nobody wants. You have no idea what the previous hash was. How do you find it?

git reflog show main — the branch's own reflog lists every position it has held locally, including where it was before the fetch moved it. git reset --hard main@{1} puts it back. If you want the position from a time rather than a count, main@{2.hours.ago} works. Note this recovers your copy; fixing the remote is a separate conversation (ch. 12).

Why does git push not push your tags, and what happens if you use git tag -f to fix a mistagged release?

Push sends the refs its refspec names, which by default is branches only — tags need git push origin <tag>, --tags, or --follow-tags. Force-moving a published tag is worse than useless: git fetch does not overwrite a tag that already exists locally, so everyone who fetched the old one keeps it forever and their build of "v1.0" differs from yours, with nothing to indicate why. Publish a new version instead.
