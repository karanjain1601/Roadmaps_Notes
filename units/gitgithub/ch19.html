Reviewing code and writing docs

Review and documentation are the two places where a repository's quality is actually decided, and both are usually done badly for structural reasons rather than lazy ones. Most review problems are size problems, and most documentation problems are location problems — and both have mechanical fixes.

What review is for

Being specific about this changes how you do it.

Review is good atReview is bad at
Is this the right approach?Finding every bug — tests do that
Will the next person understand it?Formatting and style — a formatter does that
Does it fit the system's existing shape?Verifying it builds — CI does that
Spreading knowledge of what changedReviewing 2,000 lines meaningfully
Catching missing cases the author assumed awayJudging performance without measurement

The practical consequence: anything a machine can check should be a required status check, not a review comment (chapter 16). Every "missing semicolon" comment is a reviewer's attention spent where a linter would have done better, and it displaces the comment about the approach that only a human could have made.

Label your comments

The single cheapest improvement to review tone is marking which comments block. A convention like blocking:, suggestion:, question:, nit: — the "conventional comments" idea — tells the author what to act on and lets you raise a small preference without it reading as a demand. nit: in particular gives everyone permission to ignore it.

Mechanics worth knowing

The parts of GitHub's review UI that are not obvious.

  • Start a review, do not comment line by line. Individual comments send a notification each; a review sends one.
  • Suggestions become commits. A suggestion fenced block renders as an applicable diff — the author clicks once and it lands as a commit authored by them, co-authored by you.
  • "Viewed" checkboxes per file survive a page reload and reset when the file changes again, which is the only way to review a large PR across two sittings.
  • Request changes blocks until that reviewer returns. Use it for genuine blockers; a comment review is enough for "some notes".
  • Re-request review explicitly after pushing — without it, the reviewer has no signal, and with "dismiss stale approvals" on (chapter 16) their approval is gone anyway.
  • Press y on any file view to convert the URL to a permalink pinned to a commit SHA. Links to main rot; permalinks do not.
reviewing from the terminal
$ gh pr list --search "review-requested:@me draft:false"
$ gh pr checkout 42 && npm test          # the only way to review behaviour
$ gh pr diff 42 --name-only
$ gh pr review 42 --comment -b "Two questions inline"
$ gh pr review 42 --request-changes -b "Needs a test for the expiry path"
$ gh pr review 42 --approve

Checking a PR out locally is underrated. Reading a diff tells you whether the change looks right; running it tells you whether it is.

CODEOWNERS routing

Path-based review assignment, with one rule everyone gets wrong.

CODEOWNERS maps path patterns to owners, and GitHub requests review from the owners of every changed file. The syntax is gitignore-like, with two exceptions: negation with ! is not supported, and character ranges are not supported. And the rule that surprises people:

Only the last matching pattern applies. Owners do not accumulate. A file matching both /infra/ and *.sql is owned by whichever appears later in the file — the other team is not asked at all.

CODEOWNERS matcher

Real pattern matching, showing every rule that matches and which one wins

PatternMatches
*Everything — put it first as a fallback
*.sqlAny .sql file at any depth
/src/auth/Everything under that directory, anchored at the repository root
docs/Any directory named docs, at any depth, and everything in it
/*.jsOnly .js files at the top level
@acme/teamA team — needs write access to the repository to be requestable
Ordering is the whole design

Because the last match wins, CODEOWNERS must go from general to specific: the * fallback first, then directories, then narrow file-type rules. Put *.sql above /infra/ and your database team stops being asked about database files inside infra/. Pair it with "require review from Code Owners" in branch protection, or it is only a suggestion.

Why size dominates everything

The one variable that changes review outcomes more than any process.

Reviewer attention is finite and decays within a sitting. That means a fixed review budget spent on one large pull request buys less inspection than the same budget spread over several small ones — not because small diffs are magic, but because each session starts fresh.

Review capacity model

An illustrative model — the assumptions are listed under it and are the interesting part

What this model is

Illustrative, with every parameter exposed above. It assumes a reviewer inspects a fixed number of lines per minute, that attention beyond an hour in one sitting is worth 40% of the first hour, and that a defect in inspected code is caught with fixed probability. None of those are measured facts about your team — they are knobs. The shape is the claim: splitting work recovers review capacity because sessions restart, and adding a second reviewer has diminishing returns compared with halving the diff. If the numbers move you, measure your own team rather than quoting these.

Documentation that gets read

Location matters more than quality.

Documentation decays in proportion to its distance from the code. A wiki page has no reviewer, no CI, and no reason to change when the code does; a Markdown file next to the module is in the same pull request as the change that invalidates it.

A README structure that works

README.md
# project-name

One sentence: what it does and who it is for.

## Quick start
    git clone … && make dev
Three commands maximum, copy-pasteable, tested.

## How it works
A paragraph and one diagram. Not the whole architecture.

## Common tasks
Run the tests · add a migration · deploy · roll back.

## Where things are
A short table of directories, so nobody has to guess.

## Getting help
Who to ask, which channel, how to report a bug.

The test of a README is not completeness but time to first successful command. If a new colleague cannot get the project running from it, nothing further in the document matters.

Architecture decision records

An ADR is a short, numbered, immutable file recording one decision: the context, the options, the choice, and the consequences. When the decision changes, you add a new ADR superseding the old one rather than editing it. The value is not the document — it is that six months later "why on earth did we do this" has an answer, and the answer includes what was rejected.

Two of these do real work. Mermaid diagrams mean an architecture diagram lives in the repository as text, gets reviewed in the pull request, and cannot drift out of sync with the file it describes — unlike an image exported from a drawing tool. And <details> is what makes long CI logs and reproduction steps includable without ruining the page.

Relative links, and why they matter

A link to https://github.com/acme/api/blob/main/src/auth/token.js breaks in a fork, in a clone opened in an editor, and when the file moves. A relative link [the parser](src/auth/token.js) works in all three, and GitHub resolves it correctly on the web. Use absolute URLs only for things that genuinely live elsewhere.

The short version

Chapter 19 in seven lines

  • Review is for approach, comprehensibility and knowledge transfer. Anything a machine can check belongs in a required status check, not a comment.
  • Prefix comments with blocking:, suggestion:, question: or nit: so the author knows what to act on.
  • Start a review rather than commenting line by line; suggestions apply as commits; press y for a permalink.
  • CODEOWNERS: only the last matching pattern applies. Order general to specific, or a team silently stops being asked.
  • Negation (!) and character ranges are not supported in CODEOWNERS, unlike .gitignore.
  • Size dominates review quality, and the mechanism is attention decay — the same review budget spread over smaller PRs inspects more.
  • Docs decay with distance from the code: README for the first five minutes, module docs beside the module, ADRs for decisions, Mermaid so diagrams get reviewed.

Check yourself

Your CODEOWNERS has /infra/ @platform then *.sql @data. Who is asked to review infra/db/schema.sql, and is that what you wanted?

Only @data. The last matching pattern wins and owners do not accumulate, so the platform team — who own everything else in infra/ — are not requested at all for a file inside their own directory. If you want both, GitHub cannot express it: put both teams on a single more specific rule (/infra/db/ @platform @data) placed after the general ones. The demo above shows every matching rule so you can see exactly which one is winning.

A reviewer leaves fourteen comments about naming and formatting and misses a race condition. What is the process failure?

Formatting was not automated, so it consumed the reviewer's attention budget where a formatter and linter as required checks would have handled it silently. The fix is not "review better" — it is committing a formatter config, running it in CI as a required check, and adding one formatting commit to .git-blame-ignore-revs (chapter 6). Then the review conversation starts at the level where a human is the only option. Labelling comments as nit: helps too, but removing the class of comment entirely helps more.

The model above suggests splitting a PR helps. What is doing the work in that result, and what would falsify it?

Attention decay. With a fixed total review budget, coverage per line is unchanged by splitting in a purely linear model — the improvement comes entirely from the assumption that minutes after the first hour of a sitting are worth less. So the claim is really "review sessions have diminishing returns, and small PRs let you start fresh". It would be falsified if your reviewers show no decay across a long session, or if per-PR overhead (context switching, re-reading surrounding code) exceeds what the decay costs — which is a real effect for changes that genuinely cannot be understood in pieces.

Why is a Mermaid diagram in a Markdown file better than an exported PNG, beyond file size?

It is text, so it appears in the pull request diff and gets reviewed alongside the change that invalidates it. A PNG changes as an opaque binary — a reviewer cannot see what moved, nobody notices when it stops matching the code, and it bloats every clone forever (chapter 17). The diagram-as-code version can also be grepped, edited without the original tool, and updated by whoever is changing the system rather than whoever owns the drawing file.
