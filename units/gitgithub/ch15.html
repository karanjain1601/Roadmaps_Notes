Remotes and refspecs

Everything so far worked with no network. Now other people exist — and Git's model for them is smaller than you would guess: a remote is a URL plus a rule for renaming refs. Learn to read that rule and fetch, push, tracking branches and every "why did that end up there" question become mechanical.

30 min2 demos7 sections4 self-checks

What a remote is

Three lines of config, and no persistent connection to anything.

.git/config, after a clone
[remote "origin"]
	url = git@github.com:acme/api.git
	fetch = +refs/heads/*:refs/remotes/origin/*

[branch "main"]
	remote = origin
	merge = refs/heads/main

That is a complete remote. origin is not special — it is the name git clone happens to use. The second line is a refspec: "take every branch on the other side and store it locally under refs/remotes/origin/". Everything git fetch does follows from that one line.

managing remotes
$ git remote -v
origin	git@github.com:acme/api.git (fetch)
origin	git@github.com:acme/api.git (push)

$ git remote add upstream https://github.com/original/api.git
$ git remote rename origin fork
$ git remote set-url origin git@github.com:acme/api.git
$ git remote set-url --push origin no-push       # read-only in practice
$ git remote show origin                          # what it has, and how it maps
$ git remote prune origin --dry-run                # which local copies are stale

$ git ls-remote origin                             # ask the server, clone nothing
$ git ls-remote --heads origin 'refs/heads/rel*'

git ls-remote is the underused one: it answers "what branches exist over there" without fetching a single object, which makes it the right tool in a script that needs to check whether a tag or release branch exists.

Refspecs

[+]<source>:<destination>. That is the whole syntax.

PartMeans
+Allow a non-fast-forward update — the same permission --force grants
<source>Where the objects come from. On fetch, a ref on the remote; on push, a local ref or any revision
<destination>The ref to write. On fetch, local; on push, on the remote
*One wildcard per side, and both sides must have it
Empty source:refs/heads/old — delete that ref on the other side
^ prefixA negative refspec: exclude matches (2.29+)

Refspec explorer

refspecs you will actually type
$ git push origin main                       # shorthand for main:refs/heads/main
$ git push origin HEAD                        # push the current commit to its upstream name
$ git push origin HEAD:refs/heads/release-2.4 # push here, land there
$ git push origin :refs/heads/old-branch      # delete a remote branch, the old way
$ git push origin --delete old-branch          # ...the readable way
$ git push origin +feature                     # force, for this ref only

$ git fetch origin pull/42/head:pr-42          # fetch a GitHub PR into a local branch
$ git fetch origin 'refs/tags/v*:refs/tags/v*' # only version tags
$ git config --add remote.origin.fetch '^refs/heads/wip/*'   # never fetch wip branches
The shorthand that surprises people

git push origin main expands to main:refs/heads/main — but only because main exists locally as a branch. git push origin v1.0 where v1.0 is a tag pushes the tag. And if a branch and tag share a name, Git refuses rather than guessing. Writing the destination explicitly (refs/heads/… or refs/tags/…) removes all of that ambiguity, which is why scripts should.

fetch, and why pull is two commands

Chapter 1 asserted that fetch is always safe. Here is the mechanism.

git fetch downloads objects and updates remote-tracking refs — the ones under refs/remotes/. It never touches your branches, your index or your working tree. There is nothing it can conflict with, which is why it can be run on a timer.

fetch
$ git fetch                       # the configured refspec for the current branch's remote
$ git fetch --all                  # every remote
$ git fetch --prune                # delete origin/* refs for branches deleted upstream
$ git fetch --prune-tags           # ...and tags. Not implied by --prune
$ git fetch --dry-run              # what would arrive
$ git fetch origin main            # one branch now; also updates origin/main via the refspec
$ cat .git/FETCH_HEAD              # what the last fetch brought, one line per ref

git pull is git fetch followed by an integration step — merge by default, rebase if configured. That second step is where surprises live: it can create a merge commit you did not ask for, or stop halfway with conflicts in your working tree.

make pull predictable
$ git config --global pull.ff only     # refuse anything but a fast-forward; you decide
# or
$ git config --global pull.rebase true # always rebase, never merge on pull
$ git config --global fetch.prune true  # prune on every fetch
"Behind 0" means nothing after a week offline

Ahead/behind counts are computed against your copy of the remote, which only changes when you fetch. A branch reporting "up to date with origin/main" simply means nothing new has arrived in your clone. This is also why CI that checks "is this branch current?" must fetch first — and why chapter 12's force-push lease depends on exactly this ref.

Tracking, and triangular workflows

Two config lines decide where a bare push and pull go.

upstream
$ git branch -vv                        # every branch, its upstream, ahead/behind
$ git branch -u origin/main              # set the upstream of the current branch
$ git push -u origin feature             # push and set upstream in one go
$ git config --global push.autoSetupRemote true    # 2.37+: never need -u again

In a triangular workflow — you fetch from a shared repository and push to your own fork — the two directions differ, and Git models that explicitly:

fetch from upstream, push to your fork
$ git remote add upstream https://github.com/original/api.git
$ git config remote.pushDefault origin       # bare 'git push' goes to my fork
$ git branch -u upstream/main                 # bare 'git pull' comes from upstream

$ git rev-parse @{u}         # upstream/main — where I pull from
$ git rev-parse @{push}       # origin/main — where I would push to
push.defaultA bare git push pushes
simple (default since 2.0)The current branch to a remote branch of the same name, refusing if the upstream has a different name
currentThe current branch to the same name, creating it if needed — the friendliest for forks
upstreamThe current branch to its upstream's name, even if different
matchingEvery local branch that already exists on the remote. The pre-2.0 default, and a footgun
nothingRefuse. For people who want a refspec every time

Clone strategies

A full clone downloads every version of every file ever committed. Often you do not need that.

and how to undo each one

$ git fetch --deepen=100                     # ...or just go back further

$ git config uploadpack.allowFilter true
Shallow clones in CI, and the cost nobody predicts

--depth 1 is the standard CI clone and usually correct. Two things break: anything needing a merge base — git diff main...HEAD, "which files changed in this PR", merge-base --is-ancestor — because the base commit is not present; and git describe, because tags and their history are missing. Both fail confusingly rather than clearly. The fix is a deeper fetch for those jobs (fetch-depth: 0 in actions/checkout), not a workaround in the script.

Since 2.26 Git speaks protocol v2 by default, whose main practical benefit is that the server no longer advertises every ref before you ask: on a repository with 50,000 refs, a fetch of one branch stopped downloading a megabyte of ref names first. If you are stuck on an old server, git -c protocol.version=1 forces the old behaviour.

$ git config --global http.postBuffer 524288000  # very large pushes over HTTPS

The short version

Chapter 15 in seven lines

  • A remote is a URL plus a refspec. origin is a name, not a feature.
  • A refspec is [+]<src>:<dst>: + permits non-fast-forward, an empty source deletes, one wildcard per side.
  • git push origin main is shorthand for main:refs/heads/main — write the destination explicitly in scripts.
  • fetch only updates refs/remotes/* and is always safe; pull adds an integration step, which is the part that surprises people.
  • Ahead/behind is computed against your last fetch, so "up to date" means "nothing new has arrived here".
  • Triangular workflows are first-class: remote.pushDefault plus an upstream, with @{u} and @{push} naming the two directions.
  • --depth 1 saves the most and breaks merge-base and describe; --filter=blob:none keeps all history but fetches old file contents on demand.

Check yourself

Your CI job runs git diff --name-only main...HEAD to find changed files and it returns nothing useful. The clone is --depth 1. Why?

Three dots needs the merge base of main and HEAD, and a depth-1 clone contains one commit with no parents and usually no main at all — so there is no common ancestor to compute against. Either fetch enough history (fetch-depth: 0, or a targeted git fetch --deepen), or fetch main explicitly and accept that shallow merge-base results can be wrong. The failure is quiet, which is what makes it expensive.

What does git push origin :refs/heads/old do, and what is the modern equivalent?

It pushes nothing to refs/heads/old on the remote, which Git interprets as deleting that ref — the empty-source form of a refspec. The readable equivalent is git push origin --delete old. The old syntax is worth recognising because it appears in scripts and in every answer written before the flag existed, and because it explains why a stray colon in a push command can delete a branch.

You fork a repository. What remote layout do you want, and which config makes bare push and pull do the right thing?

origin pointing at your fork (you can write to it) and upstream at the original (you cannot). Then git config remote.pushDefault origin so pushes go to your fork, and set branches to track upstream/main so pulls come from the original. push.default current also helps, because it creates the branch on your fork rather than refusing when the upstream name differs. @{u} then resolves to upstream and @{push} to your fork — Git models the asymmetry directly.

A monorepo clone takes 20 minutes and 8 GB. Developers only work in one directory. What would you try, and what breaks?

--filter=blob:none plus sparse-checkout (chapter 17): all commits and trees arrive, so log, bisect and merge-base still work, but file contents are fetched only for the paths checked out. What breaks: anything touching old file contents — git log -p, git blame beyond what is local, checking out an old commit — needs the network, so offline work degrades and a laptop on a train behaves differently from CI. It also requires the server to allow filters (uploadpack.allowFilter). A depth-limited clone would be smaller still, but it sacrifices the history those developers actually use.
