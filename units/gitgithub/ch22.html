Automating GitHub

Everything the web interface does is an API call, and most of what a team does repeatedly should be a script. The interesting decisions are which API, which token, and push or pull — and each has a wrong answer that works fine until you have a hundred repositories or a rate limit.

The gh CLI

Start here. It handles auth, pagination and JSON, and most scripts never need more.

the high-level commands
$ gh auth login && gh auth status
$ gh repo clone acme/api && gh repo view --web
$ gh pr create --fill --draft && gh pr checks && gh pr merge --squash --delete-branch
$ gh issue list --label "prio:p1" --json number,title,assignees
$ gh run watch && gh run view --log-failed
$ gh release create v2.5.0 --generate-notes
$ gh workflow run deploy.yml -f environment=staging

The part worth learning properly is gh api, which is a thin authenticated HTTP client with pagination and jq built in:

gh api
$ gh api repos/acme/api --jq '.default_branch, .open_issues_count'

$ gh api --paginate 'repos/acme/api/pulls?state=open&per_page=100' \
    --jq '.[] | [.number, .user.login, .title] | @tsv'

$ gh api --method POST repos/acme/api/issues \
    -f title='Flaky auth test' -f body='Fails about 1 run in 20' \
    -f 'labels[]=type:bug'

$ gh api graphql -f query='
  query($owner:String!, $name:String!) {
    repository(owner:$owner, name:$name) {
      pullRequests(states:OPEN, first:20) { nodes { number title author { login } } }
    }
  }' -f owner=acme -f name=api

$ gh api rate_limit --jq '.resources.core'      # never counts against the limit
Two flags that change how you script

--paginate follows Link headers until there are no more pages, so you never write a pagination loop. --jq applies a filter in-process, which means no jq dependency and no shell quoting fight. Together they turn a twenty-line Python script into one line — and in Actions, gh is preinstalled and picks up GH_TOKEN from the environment.

The REST API

Predictable, complete, and chatty.

the shape of a raw call
$ curl -sS https://api.github.com/repos/acme/api/pulls?per_page=100 \
    -H "Authorization: Bearer $TOKEN" \
    -H "Accept: application/vnd.github+json" \
    -H "X-GitHub-Api-Version: 2022-11-28" -D headers.txt

$ grep -i '^link:' headers.txt
link: <https://api.github.com/repositories/1300192/pulls?per_page=100&page=2>; rel="next", …

$ grep -i '^x-ratelimit' headers.txt
x-ratelimit-limit: 5000
x-ratelimit-remaining: 4987
x-ratelimit-reset: 1756742400
MechanicDetail
Paginationper_page up to 100; follow the Link header's rel="next" rather than incrementing page
VersioningX-GitHub-Api-Version. Pin it, or a future change is your problem
Rate limit5,000 requests per hour authenticated; 60 unauthenticated; 1,000 per hour per repository for GITHUB_TOKEN inside Actions
Conditional requestsSend If-None-Match with a stored ETag; a 304 Not Modified does not count against the primary limit
Secondary limitsSeparate, undocumented-in-detail throttles on concurrency and content creation. Respect Retry-After
SearchIts own much lower limit, and a 1,000-result cap. Not a database

The failure mode of REST is the N+1 problem: listing 200 pull requests is two calls, and getting each one's reviews is another 200. That is what GraphQL is for.

GraphQL, and when it wins

One request, exactly the fields you asked for, priced by how much you asked for.

nested data in one round trip
query($owner:String!, $name:String!, $cursor:String) {
  repository(owner:$owner, name:$name) {
    pullRequests(states:OPEN, first:50, after:$cursor) {
      pageInfo { hasNextPage endCursor }
      nodes {
        number title
        author { login }
        labels(first:10) { nodes { name } }
        reviews(first:10) { nodes { state author { login } } }
        commits(last:1) { nodes { commit { statusCheckRollup { state } } } }
      }
    }
  }
  rateLimit { cost remaining resetAt }
}

Include the rateLimit field and the response tells you what the query cost — the only reliable way to tune a large query.

Tokens, and which one to use

Four kinds, with genuinely different security properties.

CredentialScopeLifetimeUse for
Classic PATCoarse scopes, every repository you can reachOptional expiryNothing new. It is the credential most often over-privileged
Fine-grained PATChosen repositories, per-permission read or writeMandatory expiry; org approval possiblePersonal scripts and one-off automation
GITHUB_TOKENThe one repository, permissions you declareThe jobAnything inside Actions (ch. 21)
GitHub App installation tokenInstalled repositories, per-permissionOne hour, minted on demandReal automation: bots, org-wide tooling, anything shared
the app flow, which is the one worth learning
# 1. sign a short JWT with the app's private key  (10 minutes max)
# 2. exchange it for an installation token
$ curl -sS -X POST \
    -H "Authorization: Bearer $APP_JWT" \
    -H "Accept: application/vnd.github+json" \
    https://api.github.com/app/installations/$INSTALLATION_ID/access_tokens

# in Actions, an action does both steps for you
- uses: actions/create-github-app-token@v1
  id: app-token
  with:
    app-id: ${{ vars.APP_ID }}
    private-key: ${{ secrets.APP_PRIVATE_KEY }}
- run: gh pr create --fill
  env:
    GH_TOKEN: ${{ steps.app-token.outputs.token }}

Three reasons apps beat a shared PAT for anything more than a personal script: the token expires in an hour so a leak has a short blast radius; the rate limit scales with the number of repositories the app is installed on rather than being one shared 5,000; and actions appear as the app rather than as whichever employee's account happened to own the token — which still works after they leave.

Webhooks

Push instead of poll — and the one thing you must get right.

HeaderIs
X-GitHub-EventThe event name: push, pull_request, issue_comment
X-GitHub-DeliveryA unique delivery id — your idempotency key, because retries happen
X-Hub-Signature-256sha256= plus the HMAC of the raw request body using your webhook secret

Anyone who learns your endpoint URL can post to it. The signature is the only thing that distinguishes a real delivery from a forgery, so verifying it is not optional — and it must be computed over the exact bytes received.

Webhook signature verifier

Real HMAC-SHA256, computed in the page — it matches what GitHub would send
in transit
the body GitHub signed
the body your server received

verification, done correctly
import crypto from "node:crypto"

// the raw body, NOT the parsed object re-serialised
app.post("/hook", express.raw({ type: "application/json" }), (req, res) => {
  const sent = req.get("X-Hub-Signature-256") || ""
  const mine = "sha256=" + crypto
    .createHmac("sha256", process.env.WEBHOOK_SECRET)
    .update(req.body)                       // a Buffer of the exact bytes
    .digest("hex")

  const a = Buffer.from(sent), b = Buffer.from(mine)
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    return res.status(401).send("bad signature")
  }

  const id = req.get("X-GitHub-Delivery")   // idempotency: retries reuse this
  enqueue(id, req.get("X-GitHub-Event"), JSON.parse(req.body))
  res.status(202).end()                      // ack fast, work later
})
Three ways this goes wrong

Re-serialising the body. Frameworks that parse JSON automatically hand you an object; JSON.stringify of it is not the bytes that were signed, and every signature fails. Capture the raw body. Comparing with ==. A non-constant-time comparison leaks the correct signature a byte at a time; use timingSafeEqual. Doing the work before responding. GitHub expects a fast acknowledgement and retries on timeout, so a slow handler turns one event into several — which is what the delivery id is for.

developing against webhooks
$ gh extension install cli/gh-webhook
$ gh webhook forward --repo=acme/api --events=push,pull_request \
    --url=http://localhost:3000/hook

$ gh api repos/acme/api/hooks/12345/deliveries --jq '.[0]'
$ gh api --method POST repos/acme/api/hooks/12345/deliveries/98765/attempts   # redeliver

Redelivery from the API or the settings UI is the thing that makes webhook development bearable: fix the handler, replay the exact delivery, no need to reproduce the event.

The loop-prevention rule that looks like a bug

Events caused by GITHUB_TOKEN do not trigger new workflow runs. A workflow that commits with the default token will not cause your on: push CI to run, and a PR it opens will not trigger on: pull_request. This is deliberate — it stops infinite loops — and it is the usual explanation for "my bot's PR has no checks". To trigger downstream workflows you need a different identity: a GitHub App token or a PAT. Which also means you have re-enabled the loop, so add a guard such as if: github.actor != 'my-bot[bot]'.

a scheduled report, end to end
on:
  schedule: [{ cron: '0 8 * * 1' }]
permissions:
  issues: write
  pull-requests: read
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - name: Stale pull requests
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh api --paginate 'repos/${{ github.repository }}/pulls?state=open&per_page=100' \
            --jq '.[] | select(.updated_at < "'"$(date -u -d '14 days ago' +%Y-%m-%d)"'")
                  | "- #\(.number) \(.title) — \(.user.login)"' > body.md
          gh issue create --title "Stale PRs, week of $(date -u +%F)" --body-file body.md

The short version

Chapter 22 in seven lines

  • gh api with --paginate and --jq replaces most scripts; gh is preinstalled in Actions and reads GH_TOKEN.
  • REST: follow the Link header, pin X-GitHub-Api-Version, 5,000 requests an hour — but only 1,000 per repository per hour for GITHUB_TOKEN in Actions.
  • REST's failure mode is N+1; GraphQL exists for nested data, is priced in points, and will tell you the cost if you ask for rateLimit.
  • Credentials in order of preference: GITHUB_TOKEN inside Actions, a GitHub App for shared automation, a fine-grained PAT for personal scripts, a classic PAT for nothing.
  • App tokens expire in an hour, scale their rate limit with installations, and survive the departure of whoever set them up.
  • Verify X-Hub-Signature-256 over the raw body with a constant-time comparison, use X-GitHub-Delivery for idempotency, and acknowledge before doing the work.
  • Events caused by GITHUB_TOKEN do not trigger workflows — deliberate loop prevention, and the reason a bot's PR appears to have no CI.

Check yourself

Your webhook handler rejects every delivery as having a bad signature, and the secret is definitely correct. What is the most likely cause?

The framework parsed the JSON body and you are computing the HMAC over a re-serialised version of it. Key order, whitespace and unicode escaping all differ from what GitHub actually sent, so the digest cannot match even though the data is identical. Capture the raw bytes — express.raw(), request.data in Flask, ctx.request.rawBody — and verify those, parsing only afterwards. The demo above reproduces this exactly with the "reformatted" option: the data is unchanged and the signature still fails.

A nightly job needs each of 400 open PRs with its reviews. Estimate the REST cost and say what you would do instead.

REST: four list calls at per_page=100, plus one /pulls/{n}/reviews call per PR — about 404 requests. That is 8% of a personal hourly limit, or over 40% of the 1,000-per-repository budget a GITHUB_TOKEN gets in Actions, before anything else in the job. GraphQL does it in roughly four paginated queries with reviews(first:10) nested inside pullRequests(first:100), costing a handful of points. The planner above prices both.

An Actions workflow uses GITHUB_TOKEN to open a pull request, and the PR shows no status checks. Why, and what are the fixes?

Events created with GITHUB_TOKEN deliberately do not trigger further workflow runs, so no pull_request event fires. Fixes, roughly best first: mint a GitHub App installation token and open the PR with that; use a fine-grained PAT stored as a secret; or restructure so the check runs in the same workflow that created the branch. If you do switch identity you have re-enabled the loop risk, so guard the triggered workflow with a condition on the actor.

Why prefer a GitHub App over a shared classic PAT for org-wide automation, beyond "it is more secure"?

Three concrete reasons. Rate limits: a PAT gives you one shared 5,000 per hour across every script using it, while an app's limit scales with how many repositories it is installed on. Lifetime: installation tokens last an hour and are minted on demand, so a leaked token is briefly useful rather than indefinitely. Ownership: a PAT belongs to a person, so it dies with their offboarding and its actions appear under their name in every audit log — an app acts as itself, with per-permission scopes you can narrow per repository.
