Branching models

Git makes branching nearly free, which is why teams end up with branching strategies — the constraint was never the tool. Every model is a different answer to one question: how long may work sit outside the shared line? This chapter quantifies what that costs, then compares the four models honestly, including where the popular one is wrong.

What cheap branching actually changed

Chapter 4 established that a branch is a 41-byte file. The consequences are cultural, not technical.

In Subversion, a branch was a server-side directory copy and merging was painful enough that teams branched perhaps twice a year, for releases. Git made creating a branch cost a file write and merging cost an algorithm, so branches stopped being events and became units of work: one per change, created and destroyed in a day.

what branching costs
$ git switch -c feature/rate-limit      # writes 41 bytes, moves HEAD
$ git switch -                          # back to the previous branch
$ git branch -d feature/rate-limit      # deletes a file

Nothing is copied, because both branches point into the same object store. Two branches that share 99% of their history share 99% of their objects — chapter 2's content addressing again.

What remains expensive is divergence. A branch is free to create and free to keep; the cost is that the world moves while it exists, and that cost grows with time. That is the actual subject of this chapter.

finding and clearing dead branches
$ git branch --sort=-committerdate -vv          # newest first, with upstream state
$ git branch --merged main                       # fully contained in main: safe to delete
$ git branch --no-merged main                     # still holds unique commits
$ git fetch --prune                               # drop origin/* refs deleted on the remote

# delete every local branch already merged into main, except main itself
$ git branch --merged main | grep -v '^[* ] main$' | xargs -r git branch -d

# what has nobody touched in three months?
$ git for-each-ref --sort=committerdate refs/remotes/origin \\
    --format='%(committerdate:short) %(refname:short) %(authorname)' | head -20

git branch -d refusing to delete an unmerged branch is the safety net here — the xargs line above cannot lose work, because lowercase -d declines anything not fully merged.

The cost of a long-lived branch

"Merge early, merge often" is good advice. Here is the shape of the curve behind it.

While your branch exists, other people commit to main. Each of those commits touches some files. If your branch touches a file that also changed upstream, integrating gets harder — and the chance of that grows with every day you stay out.

Divergence model

A deliberately simple probability model — read the assumptions below before quoting it

What this model does and does not say

It assumes every commit touches files chosen uniformly at random, which is false: real work clusters, so two people on the same subsystem collide far sooner than the curve suggests, and two people in unrelated directories may never collide at all. It also measures file overlap, not conflicts — Git merges different regions of the same file cleanly, so only a fraction of overlaps become real conflicts. Treat it as the shape of the relationship, not a prediction: the honest claim is that the risk rises with branch age and team velocity, quickly, and is what every short-lived-branch policy exists to control.

They differ in exactly one dimension: how many long-lived branches exist, and why.

On git-flow specifically

It is the most-diagrammed model on the internet and the wrong default for most teams today. Vincent Driessen, who published it in 2010, added a note to his own article in 2020 saying so: it was designed for software with explicit release numbers and multiple supported versions, and if you deliver continuously to one production environment, GitHub flow is the better fit. Its five branch types are a real cost — more merges, more places for a fix to be missing, and a develop branch that is permanently not what is deployed.

Running a feature branch well

Independent of model, the same four habits.

  1. Start from an up-to-date base. git switch main && git pull && git switch -c feat/x. Branching from a stale main imports someone else's problems into your diff.
  2. Keep it small. A branch that changes 200 lines gets reviewed properly; one that changes 2,000 gets approved. Size is a review-quality lever more than a Git one.
  3. Sync deliberately. Either rebase onto main regularly (linear, rewrites your commits) or merge main in (preserves them, adds merge commits). Chapters 10 and 12 make the case for each; the wrong answer is doing neither for three weeks.
  4. Delete it after merging. The commits live on in main; the branch ref is just clutter, and stale refs make git branch useless as a status display.
the routine
$ git switch main && git pull
$ git switch -c feat/rate-limit

# ...work, commit, commit...

$ git fetch origin                        # see what has landed, without touching your branch
$ git rebase origin/main                  # replay your commits on the new base
# or, if the branch is shared with someone:
$ git merge origin/main

$ git push -u origin feat/rate-limit      # -u is unnecessary with push.autoSetupRemote
# ...review, approve, merge...
$ git switch main && git pull && git branch -d feat/rate-limit

Stacked branches

When a change is genuinely too big for one review, stack it: branch B off branch A, open both, review A first. Git supports this fine; the friction is that rebasing A means rebasing B onto the new A (git rebase --onto, chapter 12), and most review tools show B's diff against main rather than against A. Worth it for a large refactor, overkill otherwise.

Releases and supported versions

Where long-lived branches are genuinely necessary.

If you deploy one version to one place, you need no release branches at all: tag main and deploy the tag. Release branches earn their keep the moment two versions are alive at once — because a customer runs 2.x while you develop 3.x, or because a release must be stabilised while feature work continues.

cutting and maintaining a release line
$ git switch -c release/2.4 v2.4.0          # a branch from the tag
$ git tag -a v2.4.1 -m "Release 2.4.1"      # patches tagged on the branch
$ git push origin release/2.4 --follow-tags

# a fix that belongs in both places: land it on main, then backport
$ git switch release/2.4
$ git cherry-pick -x 8f3d2a1                # -x records the original hash in the message
$ git push

$ git tag --contains 8f3d2a1                # which releases already have this fix?

The direction matters: fix on main first, then cherry-pick to the release branch. Fixing on the release branch and merging up works too, but it is easy to forget, and a fix present in 2.4 and missing in 3.0 is the classic release-branch failure. Chapter 13 covers backporting properly.

The alternative to branching

If long-lived branches are the problem, stop having them.

Trunk-based development sounds impossible for a feature that takes three weeks — until you separate merging from releasing. Merge the incomplete work into main behind a flag that is off, and it ships to production dead:

the shape of it
if (flags.enabled("new-checkout", user)) {
  return newCheckout(cart)
}
return legacyCheckout(cart)

What you gain: no divergence, continuous integration in the literal sense, and the ability to enable for 1% of users. What you pay: both code paths exist for a while, tests must cover both, and flags left in place become permanent complexity — so give every flag an owner and a removal date, and delete it the week after full rollout.

The related technique for structural change is branch by abstraction: introduce an interface over the thing you are replacing, migrate callers to the interface on main in small commits, build the new implementation behind it, switch, then delete the old one. Slower per step, and it never produces a three-week branch.

The short version

Chapter 09 in seven lines

  • Creating a branch is a 41-byte file write; the expensive thing is divergence, and it grows with branch age times team velocity.
  • Naming: type or ticket prefix, lowercase and hyphens, and never let one branch name be a prefix of another.
  • git branch --merged main plus -d is a safe cleanup; git fetch --prune clears deleted remote refs.
  • The four models differ only in how many long-lived branches exist: trunk-based (one), GitHub flow (one plus short-lived), release branches (one per supported version), git-flow (five kinds).
  • git-flow's own author now recommends against it for continuously delivered software — it was designed for versioned, shipped products.
  • Release branches earn their keep only when two versions are alive at once; fix on main first, then cherry-pick with -x.
  • Feature flags let you merge incomplete work into main, trading divergence for temporary dual code paths — with an owner and a deletion date.

Check yourself

A team of 12 deploying twice a day is using git-flow with a develop branch. What specific problems would you predict?

develop is never what is in production, so "does it work on develop" answers a question nobody asked, and there are two integration points to keep green instead of one. Release branches add a window in which a fix must be applied in two or three places, which is where fixes go missing. And with twice-daily deploys the ceremony of cutting a release branch buys nothing — there is no stabilisation period to protect. GitHub flow (main plus short-lived branches, deploy from main) removes both the extra branch and the duplicate fix paths; git-flow's value appears only when you support several released versions simultaneously.

Your feature will take three weeks. What are your options, and what does each cost?

Three real options. Long branch: simplest day to day, but divergence grows for three weeks and the final integration is one big risky merge. Regular syncs: rebase or merge main in every day or two — the integration risk is amortised, at the cost of repeated conflict resolution (rerere helps, ch. 11). Merge continuously behind a flag: no divergence at all, at the cost of both code paths existing and needing tests, plus the discipline to delete the flag afterwards. For a three-week change touching shared code, the third is usually right; for a self-contained new module, the first is fine.

Why fix on main and cherry-pick to the release branch, rather than fixing on the release branch and merging up?

Because the failure modes are asymmetric. Fix-on-main-then-backport can only fail by the backport being forgotten — and git tag --contains or a "fix present in main?" check catches that. Fix-on-release-then-merge-up fails by the merge being forgotten, which means the bug is fixed for customers on 2.4 and still live in the version you are about to ship — and nothing in the tooling notices, because main simply never received the commit. Merging up also drags release-only history into main.

The divergence model says a 30-day branch has a high chance of touching changed files. Why should you not put that number in a slide?

Because it assumes files are picked uniformly at random, and real work is clustered — two people refactoring the same module collide almost immediately, while a docs change and a database migration may never interact. It also measures file overlap rather than conflicts: Git merges separate regions of a file without complaint, so the true conflict rate is a fraction of what the curve shows. The model is useful for its shape (risk climbs fast with age and velocity, which is why short-lived branches are policy) and useless as a specific prediction for your repository.
