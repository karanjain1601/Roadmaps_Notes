Merging

A merge answers a question with three inputs, not two: what did this look like before we diverged, what did I do, and what did you do. Find the common ancestor and most merges answer themselves — and the cases that don't are exactly the ones where two people changed the same thing, which no algorithm can decide for you.

What a merge computes

Three trees again, but a different three.

To merge feature into main, Git needs:

  1. The merge base — the best common ancestor of the two tips, found by walking the graph.
  2. Ours — the tree at the current branch's tip.
  3. Theirs — the tree at the branch being merged.

For every path, it compares each side against the base. If only one side changed, take that side. If neither changed, keep the base. If both changed identically, take it once. If both changed differently, that is a conflict and the algorithm stops and asks you. Then it records the result as a commit with two parents, which is what makes HEAD^2 meaningful (chapter 4).

seeing the inputs
$ git merge-base main feature            # the common ancestor
c3d4e5f1a2b3c4d5e6f708192a3b4c5d6e7f8091

$ git merge-base --all main feature      # sometimes there is more than one
$ git merge-base --is-ancestor main feature && echo "a fast-forward is possible"

$ git diff main...feature                # what feature changed since the base (ch. 6)
$ git log --oneline main..feature         # the commits that would come in
Multiple merge bases

If two branches have already been merged into each other in both directions, there can be several equally-good common ancestors. Git's default strategy handles this by merging the bases together first, recursively, and using the result as the base — which is why the old strategy was called recursive. You will rarely see this happen, and when you do it shows up as a merge that conflicts in a place neither side seems to have touched.

Fast-forward versus three-way

Half of all "merges" are not merges at all.

If the current branch's tip is the merge base — that is, nothing has happened on your branch since the other one diverged — there is nothing to reconcile. Git can simply move your branch pointer forward. That is a fast-forward: no merge commit, no new objects, just a ref update.

There is no universally right choice. Squash-merging keeps main readable and makes reverting trivial, at the cost of throwing away the development history and the intermediate authorship. Merge commits keep everything, at the cost of a graph that needs --first-parent to read. Fast-forward-only produces the cleanest history and requires every branch to be rebased before merging, which means every contributor must be comfortable rebasing.

Inside the content merge

Once Git has base, ours and theirs for a file, the merge is a line-level reconciliation of two edit scripts. The demo below implements it: it diffs the base against each side, converts each diff into hunks over base line ranges, and then reconciles them. Non-overlapping hunks are applied from both sides. Overlapping hunks are compared — identical results are taken once, differing ones become a conflict.

Why "both changed the same line identically" is clean

Because the merge compares results, not authorship. If you and a colleague independently made the same fix, both sides differ from the base but agree with each other, so there is nothing to ask about. This is also why cherry-picking a commit into two branches and then merging them usually just works — chapter 13 relies on it.

Strategies and their options

One default worth knowing about, and a handful of options worth reaching for.

StrategyWhat it is
ortThe default since Git 2.34. A rewrite of recursive — same semantics, much faster on large trees, better rename handling, and it can merge without a working tree.
recursiveThe old default. Still selectable; you will see it named in older documentation and log messages.
resolveSimple three-way using one merge base. Rarely useful now.
octopusMerges more than two branches at once. Refuses if there are conflicts. Used for "merge these six trivial branches".
oursRecords a merge but keeps our tree entirely, discarding theirs. For declaring a branch merged without taking its content.
subtreeFor merging a project into a subdirectory of another (ch. 17).
strategy options — the useful ones
$ git merge -X ours feature           # on conflicts only, prefer our side
$ git merge -X theirs feature          # on conflicts only, prefer their side
$ git merge -X ignore-space-change feature      # whitespace-only differences merge clean
$ git merge -X diff-algorithm=histogram feature  # better hunk alignment, fewer conflicts
$ git merge -X renormalize feature      # fix line-ending churn during the merge
$ git merge -s ours feature             # STRATEGY ours: discard their content entirely
-X ours and -s ours are not the same command

-X ours is an option to the normal strategy: merge everything as usual, and where a conflict would occur, silently take our side. -s ours is a strategy: keep our tree exactly as it is and record a merge commit claiming their branch is merged. The second one throws away the entire other branch while making the graph say otherwise — occasionally what you want, catastrophic when typed by accident.

Merge commits and getting out

Controlling what a merge records, and abandoning one safely.

during and around a merge
$ git merge --no-commit feature      # do the merge, leave it staged for inspection
$ git merge --edit feature           # write a real message instead of the default
$ git merge --log feature            # list the merged commits' subjects in the message
$ git merge --abort                  # give up mid-conflict, restore the pre-merge state
$ git merge --continue               # after resolving, finish the merge

$ git merge --verify-signatures feature   # refuse unless the tip commit is signed
$ git log --merges --oneline -5            # what has been merged recently
$ git log --oneline --first-parent         # main's own story, ignoring merged-in commits

Default merge messages ("Merge branch 'feature' into main") are fine for routine integration and useless for anything notable. If a merge is a decision — bringing in a big refactor, integrating a release branch — use --edit and say why.

Recovering from a merge you regret

SituationCommand
Conflicts on screen, want outgit merge --abort

A merge is a normal commit until you finish it

While a merge is in progress, .git/MERGE_HEAD exists and the index holds three entries per conflicted path (chapter 3's stage numbers). That is the entire state — which is why git merge --abort can restore things exactly, and why git status during a conflict is worth reading rather than skipping.

The short version

Chapter 10 in seven lines

  • A merge takes three inputs: the merge base, ours and theirs. Only where both sides changed the same region does it need you.
  • A fast-forward happens when your tip is the merge base: no merge commit, just a ref moving. --no-ff forces a commit, --ff-only refuses anything else.
  • Merge commits record integration and keep every commit; squash merges keep history linear and discard the branch's commits and authorship.
  • The content merge reconciles two edit scripts over base line ranges — non-overlapping hunks apply from both sides, overlapping ones conflict unless identical.
  • Both sides making the same change is clean, because the merge compares results rather than who made them.
  • ort is the default strategy since 2.34; -X ours resolves conflicts in our favour, while -s ours throws their whole branch away.
  • Escape hatches: --abort mid-merge, reset --hard ORIG_HEAD after, revert -m 1 once pushed.

Check yourself

You run git merge feature and get no merge commit at all. What happened, and how would you have forced one?

Your branch had not moved since feature diverged, so your tip was the merge base and Git fast-forwarded: it moved main's ref to feature's tip without creating anything. Nothing was merged because nothing needed reconciling. git merge --no-ff feature forces a merge commit anyway, which is what teams do when they want main's history to record that a branch existed — it is also what GitHub's "Create a merge commit" button does.

Two developers independently fixed the same typo in the same line, then their branches were merged. Conflict or clean, and why?

Clean. Both sides differ from the merge base, but they are identical to each other, so there is no ambiguity about what the result should be — the merge takes it once. Conflicts require the two sides to disagree, not merely both to have changed something. This is also why cherry-picking the same fix into two branches and later merging them normally works without complaint.

A colleague ran git merge -s ours release/2.4 intending "prefer our side on conflicts". What actually happened?

The entire content of release/2.4 was discarded. -s ours selects the ours strategy, which produces a merge commit whose tree is identical to the current branch's — no lines from the other side are taken at all — while the graph now claims the release branch is fully merged. So future merges of that branch bring in nothing, and the missing fixes are invisible. What they wanted was -X ours, an option to the normal strategy that only takes effect on conflicting regions. Recovery: reset --hard ORIG_HEAD if unpushed, otherwise revert the merge and redo it.

Your team wants a readable main but also wants to keep each contributor's commits. Which merge style, and what does it cost?

Merge commits (--no-ff or GitHub's merge-commit button), then read main with git log --first-parent, which follows only the mainline and shows one entry per integration while the individual commits remain in the graph for blame and bisect. The cost is that plain git log and --graph get busy, and reverting a whole feature needs -m 1. Squash-merging gives the readable log for free but discards the commits and credits the squasher as author unless trailers are added.
