Floating point arithmetic

Chapter 2 spent a fixed-width field on whole numbers and ran out of range. Spend the same field on fractions and you run out of something worse: exactness. Floating point is the trade every language makes on your behalf, and almost nobody reads the terms.

Why 0.1 does not exist

A binary fraction can only represent numbers whose denominator is a power of two. One tenth is not one of them, so the number your program stores when you write 0.1 is not one tenth. It never was.

Decimal has the same limitation with a different set of victims. One third has no finite decimal expansion, so we write 0.333… and accept that any finite version is approximate. Nobody finds this shocking, because we learned it at school. Binary's blind spot simply falls in a different place: it can write ½, ¼ and ⅛ exactly, and cannot write ⅒ at all.

Every digit above is exact, not an approximation of an approximation. A binary floating-point value is always some integer multiplied by a power of two, and any such number has a finite decimal expansion — a long one, but finite. Your language hides those digits by printing the shortest decimal string that round-trips back to the same bits, which is why 0.1 prints as "0.1" and lulls everyone into a false sense of security. The moment two of these approximations interact, the illusion breaks.

The one-sentence version

Floating point is scientific notation in binary, with a fixed budget of significant digits. You keep roughly 15–17 decimal digits of precision no matter how large or small the number is, and you pay for that range by giving up the guarantee that any particular decimal fraction is stored exactly.

The IEEE 754 layout

IEEE 754, first standardised in 1985, defines the formats every mainstream CPU and language uses. Two matter day to day.

Two design choices in that formula are worth pausing on.

The hidden leading 1
Every normal number in binary scientific notation starts with a 1 before the point, because you always shift until it does. Storing a bit that is always 1 would be wasteful, so it is implied. A 52-bit mantissa field therefore buys 53 bits of precision. This is why the largest exactly representable integer in a double is 253, and why Number.MAX_SAFE_INTEGER is 9,007,199,254,740,991.
The biased exponent
The exponent field holds an unsigned number and the bias is subtracted, rather than using two's complement. The reason is comparison: with a bias, the bit pattern of a positive float increases monotonically with its value, so hardware can compare two positive floats using the integer comparison circuit. Two's complement in the exponent field would have broken that ordering.

Zero, subnormals, infinity and NaN

Two exponent patterns are reserved. All-zeros and all-ones do not mean what the formula says; they select four special families of values.

What the reserved exponent patterns mean
Exponent bitsMantissaMeaning
all zeroszeroSigned zero. Both +0 and −0 exist, and they compare equal.
all zerosnon-zeroSubnormal. The hidden leading bit becomes 0, trading precision for the ability to get closer to zero.
all oneszeroInfinity, positive or negative.
all onesnon-zeroNaN, not a number. The mantissa bits carry an unused diagnostic payload.

Subnormals: gradual underflow

Without them, the smallest positive double would be about 2.225 × 10−308 and the next value below it would be zero — a cliff. Subnormals fill that gap by giving up the implied leading 1, so numbers get progressively coarser as they shrink rather than vanishing all at once. The smallest positive double is 5 × 10−324, which has a single significant bit.

The property this preserves is worth stating, because it is the reason subnormals were fought for during the standardisation of IEEE 754: without them, a - b == 0 can be true even when a != b. With gradual underflow, subtracting two distinct numbers can never produce exactly zero.

Subnormals can be slow

Some CPUs handle subnormals in microcode rather than in the fast path, and an operation that produces one can cost tens or hundreds of cycles instead of a few. Audio and physics code that decays toward silence can drift into subnormal territory and mysteriously slow down. The usual fix is a flush-to-zero mode, or adding a tiny DC offset to keep values away from the floor.

NaN and the rules it breaks

NaN is produced by operations with no sensible answer: 0/0, ∞ − ∞, sqrt(−1), 0 × ∞. Its defining property is that it is not equal to itself. Every comparison with NaN is false, including NaN == NaN, which is how Number.isNaN is often implemented: x !== x.

That single rule breaks a surprising amount of code. Sorting an array containing a NaN gives an unpredictable order, because the comparator's answers are inconsistent. A binary search can miss. A hash set can hold two NaNs. Any invariant of the form "either a < b, or a > b, or a == b" is false in floating point.

Signed zero leaks through division

+0 and −0 compare equal, so no test based on == can tell them apart. But 1/+0 is +Infinity and 1/−0 is −Infinity, so the distinction reappears the moment you divide. It also survives in Object.is in JavaScript and copysign in C. Negative zero arises naturally from underflow of a small negative value, so it is not an exotic case you can ignore.

Rounding, epsilon and ULPs

Real arithmetic produces real answers; floating point must round each one to a representable value. IEEE 754 guarantees that the basic operations — add, subtract, multiply, divide and square root — return the correctly rounded result: exactly as if the operation were computed with infinite precision and then rounded once. That guarantee is stronger than it sounds and it is what makes error analysis possible at all.

The default mode is round to nearest, ties to even. Ties go to whichever candidate has a zero in its last mantissa bit. Rounding ties always up would bias every long computation upward; ties-to-even cancels out on average.

Two measures of granularity

Machine epsilon
The gap between 1.0 and the next representable value above it: 2−52 ≈ 2.22 × 10−16 for a double. It is the relative precision of the format, and the right constant to use when reasoning about how much precision an operation can cost you.
ULP — unit in the last place
The gap between two adjacent representable values at a given magnitude. Near 1.0 an ULP is epsilon. Near 1000 it is 2−43 ≈ 1.14 × 10−13. Near 1016 it is 2. Absolute error is only meaningful relative to the local ULP.

The consequence of ULPs growing with magnitude is that the density of floats is wildly uneven. Half of all doubles lie between −1 and 1. Above 253 there are no odd integers left. This is why 1e16 + 1 == 1e16 is true while 1e16 + 2 == 1e16 is false: the increment simply cannot be expressed at that scale.

Integers in floats

Every integer up to 253 = 9,007,199,254,740,992 is exactly representable in a double, and arithmetic on them is exact as long as the result also stays under that limit. Above it, integers silently start skipping. This is the reason JSON is a bad transport for 64-bit database IDs read by JavaScript, and the reason JavaScript later gained BigInt. A 32-bit float loses integer exactness far earlier, at 224 = 16,777,216.

How error accumulates

Each individual operation is correctly rounded, so it is off by at most half an ULP. Chain thousands of them and those halves can conspire. Three named failure modes cover almost everything you will hit.

Absorption
Adding a small number to a much larger one, where the small one falls entirely below the last bit of the large one and disappears. 1e16 + 1 returns 1e16. Do it a thousand times and you have lost a thousand.
Catastrophic cancellation
Subtracting two nearly equal numbers. The leading digits cancel and what survives is made almost entirely of the rounding error that was already there. The relative error explodes even though no individual operation misbehaved.
Accumulation
A long chain of roundings all leaning the same way. Summing n values naively has a worst-case relative error proportional to n, which is why a running total over a large dataset drifts.

Cancellation is the sharpest of the three because it destroys information that was never recoverable. Evaluating √(x² + 1) − x at x = 108 gives exactly 0 in double precision, because x² + 1 rounds back to x² and the subtraction is then x − x. Algebraically rearranging the same expression to 1 / (√(x² + 1) + x) turns the subtraction into an addition and returns 5 × 10−9, which is correct. Same mathematics, different numerics.

With ten thousand copies of 0.1, the naive left-to-right sum returns 1000.0000000001588. The exact sum of the ten thousand stored values is 1000.0000000000000555…, so the naive answer is off by 1.59 × 10−10, which is about 1,397 ULPs. Pairwise summation and Kahan compensation both return exactly 1000, which is within half an ULP of the true answer and therefore correctly rounded. Naive is roughly 2,860 times worse than either.

Sorting makes no difference at all on that dataset, because every value is identical — a useful reminder that "sort before summing" is folklore, not a rule. Switch to the mixed dataset and the picture inverts: naive summation absorbs every single one of the thousand ones into the huge leading value and returns 1016 exactly, losing 1000, while sorting ascending recovers the correct answer completely.

Kahan's compensated summation

six lines that recover the lost bits
function kahanSum(values) {
  let sum = 0, c = 0;             // c carries the error from the last step
  for (const x of values) {
    const y = x - c;              // pay back what we lost last time
    const t = sum + y;            // this rounds, losing the low bits of y
    c = (t - sum) - y;            // recover exactly what was lost
    sum = t;
  }
  return sum;
}

The trick is line four. (t - sum) recovers the part of y that actually made it into the total, and subtracting y leaves precisely the part that did not. That residue gets subtracted from the next input, so nothing is thrown away twice. The error bound stops depending on n altogether.

Optimisers will delete this

Under real arithmetic, c = (t - sum) - y where t = sum + y simplifies to zero, and a compiler permitted to assume real-number algebra will do exactly that simplification. GCC and Clang with -ffast-math, or ICC's default settings, can silently turn Kahan summation back into naive summation. If you rely on it, disable fast-math for that translation unit or use a library implementation that is marked volatile.

Comparing floats without lying to yourself

Exact equality on computed floats is almost always a bug. The usual first fix is a fixed tolerance, and that is also a bug, just a less obvious one.

three approaches, in increasing order of correctness
// 1. exact — wrong for anything computed
a === b

// 2. absolute tolerance — right near zero, useless at scale.
//    At a = 1e9 the gap between adjacent doubles is already ~2e-7,
//    so this is stricter than the format can express.
Math.abs(a - b) < 1e-9

// 3. relative tolerance, with an absolute floor for values near zero
function close(a, b, rel = 1e-9, abs = 1e-12) {
  if (a === b) return true;                     // handles both infinities
  const diff = Math.abs(a - b);
  return diff <= abs || diff <= rel * Math.max(Math.abs(a), Math.abs(b));
}

The absolute floor matters because relative comparison is meaningless when the expected answer is zero: any non-zero result is infinitely far from zero in relative terms. The two thresholds cover different regimes, and you need both.

Comparing in ULPs

The most precise approach reinterprets the two floats as integers and compares the bit patterns. Because the biased-exponent layout makes positive floats monotonically ordered as integers, the integer difference between two float bit patterns is exactly the number of representable values between them. "Within 4 ULPs" is then a tolerance that automatically scales with magnitude. It needs care around zero and across the sign boundary, so reach for a library — Math.ulp in Java, numpy.isclose or math.isclose in Python, approx_eq crates in Rust.

Never use floats for money

Currency has exact decimal semantics, legal rounding rules and a requirement that sums balance to the cent. Floating point provides none of that. Use an integer count of the smallest unit (cents, satoshis, tenths of a cent), or a decimal type with defined rounding: BigDecimal in Java, decimal.Decimal in Python, NUMERIC in PostgreSQL, Decimal in C#. This is not caution for its own sake — accumulated half-cent errors on millions of transactions are a real and repeatedly litigated class of bug.

When floats are the wrong tool

Floating point is the right default for physical quantities, graphics, statistics and anything where inputs are already measurements with their own uncertainty. It is the wrong default for anything with exact semantics.

The alternatives and what each one costs

A note on decimal floating point: IEEE 754-2008 added decimal64 and decimal128, which are floating point with a base-10 significand. They make 0.1 exact and keep the range advantage. Hardware support exists on IBM POWER and z/Architecture but not on x86 or ARM, so in practice they are software-emulated and slow — which is why the financial world mostly uses scaled integers instead.

The decision in one line

If the quantity is a measurement, use a double. If it is a count, use an integer. If it is money, use a scaled integer or a decimal type. If two people would argue about the last digit, do not use floating point.

Check yourself

Why can 0.5 and 0.25 be stored exactly while 0.1 cannot?

A binary fraction is a sum of negative powers of two, so it can represent exactly those rationals whose denominator in lowest terms is a power of two. 0.5 is 1/2 and 0.25 is 1/4, both fine. 0.1 is 1/10, and 10 = 2 × 5 has a factor of five, which no power of two can supply. The same argument explains why decimal cannot store 1/3: three is not a factor of ten. Neither base is more "accurate", they just fail on different fractions.

A double has a 52-bit mantissa field but 53 bits of precision. Where does the extra bit come from, and what does it cost?

From the hidden leading 1. Normalised binary scientific notation always has a 1 immediately before the point, so storing it would waste a bit; it is implied instead. The cost is that the trick stops working near zero, where you can no longer normalise without the exponent underflowing. That is exactly the region the standard hands over to subnormals, which set the implied bit to 0 and lose precision gradually instead of falling off a cliff.

1e16 + 1 === 1e16 is true but 1e16 + 2 === 1e16 is false. Explain using ULPs.

1016 sits between 253 ≈ 9.007 × 1015 and 254, so the exponent is 53 and adjacent doubles are 253−52 = 2 apart. Adding 1 lands exactly halfway between two representable values; round-to-nearest-ties-to-even picks the one with an even last bit, which is 1016 itself. Adding 2 lands exactly on the next representable value, so it survives. Check it in demo 1: type 1e16 and the ULP readout is 2.

Why does Math.sqrt(x*x + 1) - x collapse to zero at large x, and what is the fix?

At x = 108, x² is 1016, where the ULP is 2. Adding 1 rounds straight back to x², so the square root returns exactly x and the subtraction gives 0. Every significant digit of the answer was destroyed by the cancellation. Multiplying by the conjugate gives the algebraically identical 1 / (√(x²+1) + x), which replaces the subtraction with an addition and returns 5 × 10−9. The general lesson: when a formula subtracts two nearly equal quantities, look for an algebraic rearrangement that does not.

Someone reports that a total is wrong and suggests sorting the inputs before summing. When does that help, and when is it useless?

Sorting ascending helps when the magnitudes differ widely, because it delays absorption: small values are combined with each other while the running total is still small enough to represent them. Demo 2's mixed dataset shows the extreme case — naive summation loses all 1000 ones into a 1016 leading value, and sorting recovers every one. It is useless when the values are all similar, as with the ten-thousand-copies-of-0.1 dataset, where sorting produces bit-for-bit the same answer as naive. Pairwise or Kahan summation helps in both cases and does not need an O(n log n) sort.

Why is Math.abs(a - b) < 1e-9 a poor general-purpose float comparison?

It applies a fixed absolute tolerance to a format whose granularity varies by 600 orders of magnitude. Near a = 109 the gap between adjacent doubles is already about 2 × 10−7, so the test is stricter than the representation can satisfy and will reject values that are genuinely as close as they can possibly be. Near a = 10−15 it is so loose that every number in the region passes. A relative tolerance scaled by the operands, plus a small absolute floor for the region around zero, handles both ends.

Your test suite has an assertion that fails only on one build machine. The code computes a sum of doubles. What are the likely causes?

Several, and all of them are about the order and precision of operations rather than the arithmetic being wrong. Compiler flags such as -ffast-math permit reassociation, so the same source can produce a different summation order and a different last bit. Auto-vectorisation splits a sum into several partial accumulators, which changes the result — usually improving it, but changing it. Fused multiply-add computes a*b + c with a single rounding instead of two. Older x87 code kept intermediates in 80-bit registers. And a parallel reduction gives a non-deterministic order across runs. If a test depends on the exact bits of a floating-point sum, the test is the thing that needs fixing.

Ten things to carry forward

  1. Binary fractions can only express denominators that are powers of two, so 0.1 is stored as something slightly larger than one tenth and always has been.
  2. The layout is sign, biased exponent, mantissa, with a hidden leading 1 that buys an extra bit of precision and a bias that keeps positive floats integer-comparable.
  3. A double gives about 15–17 significant decimal digits regardless of magnitude. Range is cheap; exactness is not.
  4. Reserved exponents give you signed zero, subnormals, infinity and NaN, and each one breaks an assumption you probably hold.
  5. NaN is not equal to itself, which invalidates trichotomy and quietly breaks sorting, searching and set membership.
  6. Basic operations are correctly rounded — off by at most half an ULP — but chains of them are not.
  7. An ULP grows with magnitude. Near 1 it is 2−52; near 1016 it is 2. Absolute error means nothing without knowing the local ULP.
  8. Absorption, cancellation and accumulation are the three ways a correct-looking formula goes wrong. Cancellation is the worst because it destroys information rather than adding noise.
  9. Pairwise and Kahan summation cost almost nothing and fix most of it, turning an error that grows with n into one that does not.
  10. Never store money in a float. Use scaled integers or a decimal type, and reserve floating point for quantities that were approximate to begin with.
