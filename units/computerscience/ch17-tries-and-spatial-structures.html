Tries and spatial structures

Every structure so far compares whole keys. Branch on one character at a time instead and lookup stops depending on how many keys you have. Branch on coordinates and you can ask which point is nearest — a question no comparison tree can express.

Branching on the key instead of comparing it

A BST asks "is my key less than this node's key?" and each answer discards half the remaining candidates. A trie asks "what is the next character?" and each answer discards every key that does not start that way. The difference in what that buys is worth stating precisely.

The last row is the catch, and section three is about it. Everything else is upside: a trie never compares two keys against each other, so its cost has no n in it at all, and it fails fast — looking up zebra in a dictionary with no z-words costs exactly one step.

Words with that prefix

The four words car cat cart dog need 9 nodes: the root, a shared c-a spine, two branches, and a three-node chain for dog that shares nothing. Looking up cat costs 3 steps and looking up cz costs 2 — it gives up the moment the branch is missing, without touching the rest of the dictionary.

The operations

insert, find, and the prefix walk
node = { children: Map<char, node>, isWord: false }

insert(word):
  n = root
  for c of word:
      if (!n.children.has(c)) n.children.set(c, newNode())
      n = n.children.get(c)
  n.isWord = true        // the flag is essential: "car" being stored does not
                        // make "ca" a word, even though the path exists

find(word):
  n = walk(word)
  return n !== null && n.isWord

withPrefix(p):
  n = walk(p)
  return n === null ? [] : collectAllWordsBelow(n)   // O(L + k)

The isWord flag is the part people leave out. Without it there is no way to distinguish a key that happens to be a prefix of another key from one that is merely a waypoint, and every prefix of every stored word becomes a false positive. It is also what makes deletion fiddly: removing a word means clearing the flag and then pruning upward only while nodes have no children and no flag.

Prefix search is where the structure earns its place. Walk to the node for the prefix — Θ(L) — and every word below it is a match, so collecting them costs only the output size. That single operation is autocomplete, and it is why tries sit behind search boxes, IDE completion, and IP routing tables, where "longest matching prefix" is the entire question a router asks of every packet.

The memory problem, and radix compaction

A trie stores one node per character position, not per key, and each node needs somewhere to put its children. The naive layout is an array of 26 pointers — or 256 for bytes — and that is where it goes wrong.

Most nodes have one child. A radix tree (also called a compressed trie or PATRICIA trie) collapses every chain of single-child nodes into one node holding the whole substring, so branching only happens where the keys actually diverge. On the dictionary above that removes 42% of the nodes; on data with long shared prefixes — file paths, URLs, IP prefixes — it removes far more.

The layouts that made tries practical again

Three ideas fixed the memory problem. Adaptive nodes (the ART trie) use four node layouts — 4, 16, 48 or 256 children — and switch as a node grows, so sparse nodes cost almost nothing. Double-array tries pack the whole structure into two integer arrays with no pointers at all. And succinct tries encode the shape as a bit vector, approaching the information-theoretic minimum, which is how a phone can hold an entire language model's vocabulary.

Suffix structures

Insert every suffix of one string into a trie and you get a structure that answers questions about substrings, because every substring is a prefix of some suffix.

Two ways to index the suffixes of a string of length n
Suffix treeSuffix array
What it isA compressed trie of all suffixesThe starting positions of all suffixes, sorted
SpaceΘ(n) nodes, but 10–20 bytes eachn integers, plus n more for the LCP array
BuildΘ(n) with Ukkonen's algorithm, intricateΘ(n) with SA-IS, or Θ(n log n) simply
Substring searchΘ(m)Θ(m log n) by binary search
In practiceRarely used — the constants are brutalThe standard choice

A suffix array is just a sorted list of integers, which is why it wins: it is contiguous, cache-friendly, and five to ten times smaller than a suffix tree holding the same information. Paired with an LCP array — the longest common prefix of each adjacent pair — it can do everything a suffix tree can, including finding the longest repeated substring in linear time.

These structures underpin bioinformatics (aligning reads against a genome), full-text search, plagiarism detection and data compression. The Burrows-Wheeler transform at the heart of bzip2 is a suffix array in disguise, and the FM-index that makes short-read aligners like Bowtie work is a compressed suffix array.

k-d trees: branching on coordinates

A different question entirely. "Which of these ten thousand points is nearest to here?" has no answer in a BST, because closeness in one dimension says nothing about closeness overall. A k-d tree handles it by cycling through the dimensions: split on x at the root, on y one level down, on x again, and so on, each node partitioning space with an axis-aligned plane.

The search is a depth-first descent with one pruning rule, and the rule is the whole algorithm: after searching the side of the splitting plane the query falls on, check the other side only if the plane is closer than the best distance found so far. If it is not, an entire half of the remaining space cannot contain anything better and is skipped without being examined.

In two dimensions that prunes almost everything. Over 10,000 random points a nearest-neighbour query visits 19.5 nodes on average — 0.2% of the data, a 512-fold reduction against scanning — and it agrees with a full scan on every query, because pruning only removes regions that provably cannot win.

The curse of dimensionality

Raise the dimension and the pruning rule stops firing. Measured over 4,096 points, a query visits 0.4% of them in 2 dimensions, 1.4% in 4, 15.6% in 8, and 98.7% in 16 — at which point the tree is a slower linear scan with pointer chasing. The reason is that in high dimensions almost all the volume of a ball is near its surface, so the nearest point is barely nearer than the average point and the "is the plane closer than my best?" test almost always says yes. Note the failure mode: the answer stays exact at every dimension, and only the speed collapses. Past roughly 10–20 dimensions, use approximate methods — locality-sensitive hashing, HNSW graphs, product quantisation — which is exactly what vector databases do.

Geohash / S2Interleaving coordinate bits into one numberTurning 2-D proximity into a 1-D key a B-tree can index

The geohash idea is the one worth understanding, because it connects back to everything else. Interleave the bits of latitude and longitude into a single integer and nearby points get numerically close values — a space-filling curve. That means an ordinary B-tree index can answer proximity queries, with no new structure at all. It is imperfect, since points either side of a major bit boundary end up far apart numerically despite being adjacent, which is why implementations query several neighbouring cells. Google's S2 and Uber's H3 are more careful versions of the same trick.

The common thread

Every structure in this chapter replaces "compare two keys" with "decompose the key". A trie decomposes a string into characters; a k-d tree decomposes a point into coordinates; a geohash decomposes a position into bits. Once a key has parts you can branch on, you stop needing to compare keys to each other, and the cost stops depending on how many keys there are.

Choosing

  1. Exact lookup only, no ordering needed — hash table. A trie's advantage over hashing is prefix work, and if you never do prefix work you are paying memory for nothing.
  2. Autocomplete, longest-prefix matching, or spell checking — trie, and use a radix tree or an adaptive-node layout unless the dictionary is small.
  3. Substring search in a fixed body of text — suffix array plus LCP. Build once, query many times.
  4. Nearest neighbour in 2 or 3 dimensions — k-d tree for points, R-tree for shapes, quadtree if the space is uniformly occupied.
  5. Nearest neighbour above about 20 dimensions — do not use an exact tree. Approximate methods are faster and the exact answer is usually not what you wanted anyway.
  6. Proximity in a system that already has a B-tree — geohash the coordinates and index the result.

Check yourself

Why is trie lookup Θ(L) with no n in it, when a balanced BST is Θ(L log n)?

Because a trie never compares two keys against each other. Each step consumes one character of the query and follows one edge, so the number of steps is the key's length no matter how many keys are stored. A BST must perform log n comparisons, and each comparison of two strings costs up to L character examinations. Adding a millionth word to a trie does not slow down any existing lookup by a single step.

Why does a trie node need an isWord flag when the path already exists?

Because the path to a node exists for every prefix of every stored word, whether or not that prefix is itself a word. Storing cart creates nodes for c, ca, car and cart; without a flag, ca would be reported as present. The flag also drives deletion: clear it, then prune upward only while a node has no children and no flag of its own.

112 words occupy 401 bytes of characters and 50,544 bytes as a trie. Where did the memory go, and what would you do?

Into 243 nodes each holding a 26-pointer array — 208 bytes per node to store on average one or two children. That is a 126-fold overhead over the raw text. Three fixes, in increasing order of effort: radix-compact the single-child chains, which removes 42% of the nodes here and far more on path-like data; replace the fixed array with a small map or sorted list of the children that actually exist; or use adaptive node layouts that switch between 4, 16, 48 and 256 slots as a node grows, which is what ART does.

What does a radix tree change, and when does it barely help?

It collapses every chain of single-child nodes into one node holding the whole substring, so branching happens only where keys diverge. It helps most when keys share long prefixes and then split rarely — file paths, URLs, IP prefixes. It helps least when the keys diverge immediately, since there are no chains to collapse: try the "no shared prefixes" preset in demo 1, where every word branches at the root and compaction has almost nothing to merge.

What is the single pruning rule that makes k-d tree search fast?

After searching the side of the splitting plane the query point falls on, examine the other side only if the perpendicular distance to that plane is smaller than the best distance found so far. If the plane is further away than the current best, nothing beyond it can be closer, so the whole subtree is skipped unexamined. This is why the tree is both fast and exact — pruning only discards regions that provably cannot contain a better answer, which the demo confirms by checking every query against a full scan.

A k-d tree over 4,096 points visits 0.4% of them in 2 dimensions and 98.7% in 16. What happened?

The pruning test stopped firing. In high dimensions almost all the volume of a ball lies near its surface, so distances between random points concentrate — the nearest point is barely nearer than a typical one. The current best distance is therefore almost always larger than the distance to the splitting plane, so the "can I skip this side?" test says no and both subtrees get searched. The tree degenerates into a linear scan with pointer chasing on top. Note that the answers stay exact; only the speed collapses, which is why the fix is to give up exactness and use approximate nearest neighbour instead.

You need "find restaurants within 2 km" in a system that already has a relational database. What is the cheapest thing that works?

Geohash the coordinates and index the resulting string or integer with the B-tree you already have. Interleaving the bits of latitude and longitude maps nearby points to nearby values, so a prefix range query on the geohash gives you a bounding cell, and you filter by exact distance afterwards. It needs no new index type. The caveat is boundary effects — two adjacent points can straddle a high-order bit and land far apart — so query the target cell plus its eight neighbours. If the database has PostGIS or an equivalent, an R-tree index is better still and handles shapes rather than just points.

Ten things to carry forward

  1. A trie branches on the key's characters, so lookup costs Θ(L) with no dependence on how many keys are stored.
  2. It fails fast. A missing branch ends the search at the first character that diverges.
  3. Prefix search is the reason to use one. Walk to the prefix node and everything below it matches, at Θ(L + k).
  4. The isWord flag is not optional, because the path to every prefix exists whether or not it is a key.
  5. Memory is the weakness. 401 bytes of text became 50,544 as a 26-pointer trie — a 126× overhead.
  6. Radix compaction merges single-child chains, removing 42% of the nodes here and much more on path-like keys.
  7. Suffix arrays beat suffix trees in practice, because a sorted array of integers is contiguous and several times smaller.
  8. A k-d tree cycles through the dimensions, and its one pruning rule is to skip the far side unless the splitting plane is closer than the current best.
  9. In two dimensions that skips 99.8% of the work; in sixteen it skips 1.3%, and the tree becomes a slow linear scan.
  10. Every structure here decomposes the key instead of comparing it, which is what removes n from the cost.

What comes next

Chapter 18 closes Part 4 by dropping the last restriction. A tree gives every node exactly one parent; remove that and you have a graph, which can model roads, dependencies, social networks, web pages and state machines — and needs its own representations and traversals.
