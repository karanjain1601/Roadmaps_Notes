Distributed systems and scaling

Adding a tenth server to nine moves 90% of your cached keys under modulo hashing and 9.3% under consistent hashing. Five services at 99.9% each give you 99.5%, which is 43.7 hours of downtime a year rather than 8.8. Distribution is mostly arithmetic, and the arithmetic is unforgiving.

Vertical first

Vertical: a bigger machine

No code changes, no distributed reasoning, no new failure modes. A single server can now have hundreds of cores and terabytes of RAM, which is more than the overwhelming majority of applications need. It has a ceiling, and it is a single point of failure.

Horizontal: more machines

No ceiling, and redundancy comes free. It also brings partial failure, network partitions, consistency choices, clock skew, and the entire rest of this chapter. Every one of those is a permanent tax on development.

Scale up until you cannot

The honest default is vertical scaling, because the complexity cost of distribution is paid forever and by everyone who touches the system. A single well-tuned PostgreSQL instance handles workloads that people routinely reach for a distributed database to serve. Distribute when you have a measured reason — a genuine ceiling, a geographic latency requirement, or an availability target a single machine cannot meet — and not because the architecture diagram looks more serious with more boxes on it.

The fourth row is worth knowing because it is surprising. "Pick two servers at random and use the less loaded" performs almost as well as querying every server, and dramatically better than pure random — chapter 25's concentration bounds are what prove it. It is the standard choice when you want good balance with no coordination.

Layer 4 balancing forwards packets by IP and port and is fast; layer 7 reads the request and can route by path, header or cookie, at the cost of terminating the connection. And a balancer must do health checks and drain connections before removing a node, or a deploy becomes an outage.

Partitioning, and why modulo hashing fails

Sharding splits data across machines so that no single one holds it all. The scheme decides everything about how the system behaves when the machine count changes.

Modulo hashing — server = hash(key) % n — is the obvious scheme and it is catastrophic under change. Adding a tenth server to nine moves 90% of the keys; going from 99 to 100 moves 99%. The fraction is n/(n+1), which approaches 1 as the cluster grows, so the bigger your cluster the worse a single addition is. For a cache, that is a complete cold start; for a database, it is a full data migration.

Consistent hashing places both servers and keys on a ring and sends each key to the next server clockwise. Adding a server captures only the arc between it and its predecessor, so it moves about 1/(n+1) of the keys — measured at 9.3% against modulo's 90%, a tenfold improvement.

Consistent hashing alone is badly unbalanced

With one point on the ring per server, nine servers give a coefficient of variation of about 71% — the busiest server holds roughly seven times the least busy one's share. The ring solves the reassignment problem and creates a balance problem, because random points do not divide a circle evenly.

Virtual nodes fix it: place each server at many points instead of one. At 150 virtual nodes the variation falls to about 5% — a spread of a few percent around the mean — while the fraction of keys moved stays at about 9%. This is why every real implementation — Dynamo, Cassandra, Riak, memcached clients — uses somewhere between 100 and a few hundred virtual nodes per server, and why the number appears arbitrary until you measure it.

The other thing a partition scheme must handle is hot keys. Hashing distributes keys evenly, not traffic: one celebrity account or one popular product can overwhelm its shard no matter how good the hash. The fixes are to split the hot key artificially, to cache it in front of the shard, or to accept that some keys need dedicated capacity.

Replication and consistency

Sharding splits data to get capacity; replication copies it to get availability and read throughput. The question replication forces is what a reader is allowed to see.

Consistency models, strongest first
ModelGuaranteesCosts
LinearizableEvery read sees the latest write, as if there were one copyCoordination on every operation
SequentialAll nodes see operations in the same orderSlightly cheaper; the order may lag real time
CausalCausally related operations are seen in order; concurrent ones may differNeeds causality tracking, but no global agreement
Read-your-writesYou see your own writes; others may lagSession stickiness. Often the one users actually notice
EventualReplicas converge, given enough quietStale reads, and conflicts you must resolve

Quorums are the standard tuning mechanism. With N replicas, requiring W acknowledgements to write and R to read gives strong consistency whenever R + W > N, because every read set must then intersect every write set and therefore include at least one node holding the latest value. With 3 replicas, R = W = 2 works. With 5 you can choose R = 1, W = 5 for fast reads, or R = 3, W = 3 for balance — but not R = W = 2, which fails the inequality.

When two replicas accept conflicting writes, something must resolve them. Last-write-wins is simple and silently discards data — and depends on clocks, which in a distributed system disagree. Vector clocks detect the conflict properly and hand it to the application. CRDTs are data types designed so that concurrent updates merge deterministically, which is the only approach that removes the problem rather than relocating it.

CAP, and the more useful version

During a network partition, a distributed system must choose between consistency and availability.

That is the accurate statement of CAP, and the popular "pick two of three" phrasing is misleading. Partition tolerance is not a choice — networks partition — so the theorem is a conditional: when a partition happens, either you refuse requests you cannot safely answer (choosing consistency) or you answer them from possibly stale data (choosing availability).

PACELC says more

CAP only describes behaviour during a partition, which is rare. PACELC adds the common case: if there is a Partition, choose Availability or Consistency; Else — the other 99.9% of the time — choose Latency or Consistency. That second clause is the one you live with daily, because coordination costs round trips whether or not anything has failed. A system that is CP during partitions and chooses latency otherwise behaves very differently from one that insists on consistency always, and CAP cannot tell them apart.

The practical reading is that consistency is not a system-wide setting but a per-operation choice. Transferring money should refuse rather than guess; showing a follower count should serve a stale number rather than fail. Most systems need both, and the useful design question is which operations belong in which category.

Queues and delivery guarantees

A queue decouples producer from consumer: it absorbs bursts, allows independent scaling, and survives a consumer being down. It also adds latency, another thing to operate, and a hard question about duplicates.

What happens when the acknowledgement is lost
GuaranteeMechanismOutcome
At most onceSend, do not retryThe message is lost
At least onceRetry until acknowledgedThe message is duplicated
Exactly onceAt-least-once plus deduplicationProcessed once — see below
Exactly-once delivery does not exist

Consider the sender's position after a timeout: it cannot distinguish "the message was lost" from "the message arrived and the acknowledgement was lost". There is no number of additional messages that resolves this — it is the Two Generals problem, and it is provably unsolvable over an unreliable channel. So there is no exactly-once delivery.

What is achievable is exactly-once processing: at-least-once delivery plus an idempotent consumer, so a duplicate has no additional effect. Give every message a unique ID and record which you have handled, or design the operation so that applying it twice is the same as once — SET balance = 500 rather than ADD 100. Systems advertising "exactly once" are doing this internally, and understanding that is the difference between using them correctly and being surprised.

Two operational details matter as much as the guarantee. A dead-letter queue catches messages that fail repeatedly, so one bad message does not block the queue forever. And ordering is usually only guaranteed within a partition, so if order matters you must key related messages to the same partition — which reintroduces the hot-key problem from section three.

Dependencies multiply down. Five services each at 99.9%, all required synchronously, give 99.501% — 43.7 hours of downtime a year rather than 8.8. Thirty of them give 97.043%, or nearly 11 days. Every synchronous dependency you add lowers your ceiling, and this is the arithmetic that makes a microservice architecture harder to keep available than the monolith it replaced.

Redundancy multiplies up. Two independent 99.9% components in parallel give 99.9999% — 31.6 seconds a year — and three give nine nines. That is why redundancy is the standard answer.

Redundancy only works if the failures are independent

Move the correlation slider and watch the benefit evaporate. With 1% of failures taking out both copies — a shared rack, a shared power feed, a shared configuration push — two 99.9% components give 99.9989% rather than 99.9999%. At 10% correlation they give 99.9899%, and the annual downtime goes from 31.6 seconds to 53 minutes: a hundredfold loss from a 10% shared-fate assumption.

This is why real outages take out both replicas at once. The failures that matter are almost never independent: the same bad deploy reaches both, the same certificate expires on both, the same dependency fails for both. Redundancy protects against uncorrelated hardware failure, which is not what usually breaks things.

Which leads to the patterns for surviving failure rather than preventing it. Timeouts on everything, because a hung call is worse than a failed one. Retries with exponential backoff and jitter — without jitter, every client retries in lockstep and the retry becomes the outage. Circuit breakers, so a failing dependency is stopped being called rather than hammered. Bulkheads, so one saturated dependency cannot consume the thread pool everything else needs. And graceful degradation: serve the page without recommendations rather than serving no page.

The fallacies, still true after thirty years

Peter Deutsch's list of assumptions that distributed systems violate: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology does not change, there is one administrator, transport cost is zero, the network is homogeneous. Every distributed bug you will ever debug is one of these assumptions surfacing. The most expensive is the first, because it is the one that makes a remote call look like a local one in the source code.

Check yourself

Why is hash(key) % n a bad way to pick a cache server?

Because n appears in the calculation, so changing it renumbers everything. Adding a tenth server to nine moves 90% of the keys, and going from 99 to 100 moves 99% — the fraction is n/(n+1), which gets worse as the cluster grows. For a cache that is a total cold start at the moment you were adding capacity, which is usually the moment you could least afford it. Consistent hashing moves about 1/(n+1) instead: 9.3% measured, a tenfold improvement.

Why do real implementations use 100 or more virtual nodes per server?

Because consistent hashing with one point per server is very unbalanced. Across nine servers, a single point each gives a coefficient of variation of about 71%, with the busiest server holding roughly seven times the least busy one's share — random points do not divide a circle evenly. Placing each server at 150 points brings the variation down to about 5%, without changing the fraction of keys that move on a topology change. The number looks arbitrary until you measure the alternative.

What does R + W > N guarantee, and why?

That every read observes the latest write. If you require W replicas to acknowledge a write and read from R replicas, then R + W > N forces the two sets to overlap by at least one node — by the pigeonhole principle — and that node holds the newest value. With N = 3, R = W = 2 satisfies it. With N = 5 you may choose R = 1, W = 5 for fast reads or R = W = 3 for balance, but R = W = 2 does not: 4 is not greater than 5, so a read can miss the write entirely.

What is wrong with "CAP: pick two of three"?

That partition tolerance is not something you pick — networks partition whether you planned for it or not, so "CA" is not an option for a distributed system. The theorem is a conditional: during a partition you must choose between refusing requests you cannot safely answer and answering them from possibly stale data. PACELC is the more useful framing because it adds the common case: else, when there is no partition, you still choose between latency and consistency, since coordination costs round trips regardless. That second clause is the one you live with every day.

Why can't a queue offer exactly-once delivery?

Because after a timeout the sender cannot distinguish "the message was lost" from "the message arrived and the acknowledgement was lost", and no additional messages resolve that — it is the Two Generals problem, provably unsolvable over an unreliable channel. So the real choice is at-most-once, which loses messages, or at-least-once, which duplicates them. What is achievable is exactly-once processing: at-least-once delivery plus an idempotent consumer, using a message ID and a record of what has been handled, or an operation whose second application changes nothing. Products advertising exactly-once are doing this internally.

Five services at 99.9% each. What is the system's availability?

99.501%, if all five are required synchronously — availabilities multiply, so 0.999⁵. That is 43.7 hours of downtime a year rather than the 8.8 each component promises. Thirty such services give 97.043%, or nearly 11 days. This is the arithmetic that makes a microservice architecture harder to keep available than the monolith it replaced, and the fixes are to remove synchronous dependencies — make calls asynchronous, cache aggressively, or degrade gracefully so a failed dependency does not fail the request.

Two redundant copies at 99.9% give six nines. Why do real outages still take out both?

Because the calculation assumes independent failures, and real failures are correlated. With just 1% of failures affecting both copies — a shared rack, a shared power feed, one bad configuration push — the pair gives 99.9989% rather than 99.9999%. At 10% correlation it gives 99.9899%, and annual downtime rises from 31.6 seconds to 53 minutes: a hundredfold loss. The failures that actually cause outages are exactly the correlated kind — the same deploy, the same expired certificate, the same failing dependency — so redundancy protects best against the thing that breaks least often.

Ten things to carry forward

  1. Scale vertically until you cannot, because distribution's complexity is paid forever by everyone.
  2. "Random with two choices" beats random by a lot and costs almost nothing in coordination.
  3. Modulo hashing moves n/(n+1) of your keys when the cluster changes — 90% at nine servers.
  4. Consistent hashing moves about 1/(n+1) instead, measured at 9.3%.
  5. Virtual nodes are not optional. One point per server gives about 71% load variation; 150 gives about 5%.
  6. R + W > N forces read and write sets to overlap, which is what makes a quorum consistent.
  7. CAP is a conditional about partitions, and PACELC's "else latency or consistency" is the clause you live with.
  8. Exactly-once delivery is impossible; exactly-once processing is at-least-once plus idempotency.
  9. Dependencies multiply down. Five 99.9% services give 99.5% — 43.7 hours a year, not 8.8.
  10. Redundancy only works if failures are independent, and 10% correlation turns 31.6 seconds into 53 minutes.

The end of the unit

Thirty chapters, and it is worth naming what actually connected them, because the through-lines are more useful than the individual facts.

The physical machine never stops mattering. Chapter 5's cache hierarchy explained why chapter 12's contiguous array beats a linked list by 18×, why chapter 15's B-trees have fan-out in the hundreds, why chapter 16's heapsort loses to quicksort despite better asymptotics, and why chapter 17's k-d tree beats a scan only in low dimensions. Asymptotic analysis tells you which algorithm wins eventually; the memory hierarchy tells you which one wins today.

Worst cases are usually the common case. Sorted input destroys a plain BST and quicksort's naive pivot, and it is what a database returns. A loop slightly larger than the cache gives LRU a hit rate of zero, and loops are everywhere. Chosen keys turn a hash table quadratic. The pattern is that the input you did not test is the input you will get.

Randomisation converts an adversary's advantage into your own coin flips. Random pivots, seeded hashes, skip lists, random eviction — all the same move, and all of them trade a guarantee about the input for a guarantee about the algorithm.

Measure, then believe. This unit found a dozen places where the received number was wrong at realistic sizes: the 2 ln n BST depth that overstates by 26%, the A* heuristic that prunes nothing without tie-breaking, the FNV hash whose low bits leave half a table unreachable, the Boyer-Moore variant that is best on one input and worst on a one-character variation of it. Every one of those was found by asserting what a model should not do.

What to do next

Implement something from each part without looking: a hash table with open addressing, a balanced tree, Dijkstra, a small DP. The gap between reading and writing is where the understanding is. Then read real code — Redis, SQLite, the Go runtime, your language's sort — because all four are readable and all four contain decisions this unit explains.
