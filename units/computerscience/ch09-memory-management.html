Chapter 9 · The operating system

Memory management

Your program's addresses are fiction. Between the pointer you hold and the DRAM chip that answers sits a four-level lookup table, a cache of that table, a page fault handler and an allocator — and every one of them can be the reason a program is slow or wrong.

Two allocators with different rules

Every process gets two places to put data at runtime, and they differ in exactly one respect that explains everything else: whether the lifetime is known at compile time.

A stack allocation is one subtraction from the stack pointer because deallocation is guaranteed to happen in exactly the reverse order. That single guarantee removes the need for any bookkeeping at all: there is nothing to search, nothing to coalesce, nothing to fragment. The heap gives up the guarantee, and pays for it with everything in the rest of this chapter.

Stack overflow is not a heap problem

An 8 MiB stack sounds enormous until you recurse. Each frame holds saved registers, the return address and locals, so a recursive function with a 1 KiB local array overflows after roughly 8,000 levels; deep recursion over a linked list of a million nodes has no chance. The failure mode is also worse than running out of heap: instead of a null return you get a guard-page fault and the process dies. Threads make it worse again, since each one reserves its own stack. This is why converting recursion to iteration, or using an explicit stack on the heap, is a real technique rather than a style preference.

Virtual memory and the page table

Chapter 6 asserted that every process sees its own address space. This is how. Memory is divided into fixed-size pages, almost always 4 KiB, and physical memory into frames of the same size. A page table maps one to the other, and the hardware consults it on every single memory access.

A flat table would be absurd: 248 addresses ÷ 4 KiB = 64 billion entries, 512 GiB of table per process. So the table is a sparse tree. On x86-64, four levels of 9 bits each index four tables of 512 entries, with the low 12 bits as the offset within the page.

a 2 MiB huge page stops at the PD level and uses a 21-bit offset:
9 + 9 + 9 + 21 = 48, one fewer level to walk

Each entry holds a frame number plus flags: present, writable, user-accessible, accessed, dirty, no-execute. Those flags are not decoration. Present is what makes demand paging and swapping possible. Writable is what makes copy-on-write work. Accessed and dirty are what page replacement algorithms read. No-execute is what stops a buffer overflow from running data as code.

The TLB

Walking four levels means four memory accesses before you even touch the data you wanted — a fivefold slowdown on every single access. The translation lookaside buffer caches recent translations so the common case is one access. It is small, fully associative, and typically holds a few hundred to a couple of thousand entries.

The first touch of a page misses and costs five memory accesses: four to walk the table, one for the data. The second touch hits and costs one. Switch to 2 MiB pages and even a miss costs four, because there is one level fewer to walk.

The two "touch pages" buttons show why TLB reach matters more than hit rate arithmetic. Twelve pages fit in a sixteen-entry TLB, so a second pass over them hits every time — 12 misses, 36 hits. Twenty pages do not fit, and because the walk is a loop, each entry has been evicted by the time you come back to it: every single access misses, on every pass. This is the same capacity-versus-thrashing cliff as chapter 5's cache, one level up.

Why huge pages exist

A 1,536-entry TLB with 4 KiB pages reaches 6 MiB of address space. With 2 MiB pages the same TLB reaches 3 GiB, five hundred and twelve times more. Any workload with a large, randomly accessed structure — a database buffer pool, a big hash table, a JVM heap — can spend more time on page-table walks than on data cache misses, and huge pages are the fix. The cost is coarser granularity: a 2 MiB page is either resident or not, so sparse access wastes memory, and transparent huge pages can cause latency spikes when the kernel compacts memory to produce one.

Page faults and what they are for

A page fault is not an error. It is the mechanism by which almost every interesting memory feature is implemented: the hardware finds the present bit clear, traps to the kernel, and the kernel decides what that absence meant.

Demand-zero faults explain a result that surprises people: malloc(1_000_000_000) succeeds instantly and uses almost no memory, because it only reserves address space. The memory materialises page by page as you touch it. This is also why a container can be killed by the out-of-memory killer long after the allocation that "succeeded", and why calloc of a huge block can be faster than malloc plus memset — the kernel can hand over pages that are already zero.

Thrashing

When the working set exceeds physical memory, every page that gets evicted is needed again immediately, and the system spends its time swapping instead of computing. Throughput collapses by orders of magnitude while CPU utilisation looks low and disk utilisation looks pinned. The only fixes are more memory, a smaller working set, or fewer concurrent processes — adding load makes it worse, which is why a thrashing server does not recover on its own. Modern Linux prefers to invoke the OOM killer rather than thrash indefinitely, on the grounds that a dead process is more useful than a live one making no progress.

Which page to evict is a cache replacement question, and chapter 23 covers the policies in general. The practical note here is that true LRU is impossible in a kernel — you cannot afford to update a timestamp on every memory access — so real systems approximate it with the hardware accessed bit and a clock algorithm that sweeps through pages clearing bits and evicting the ones still clear on the second pass.

What malloc actually does

The kernel deals in pages. An allocator sits between that and your 37-byte request, and its job is to hand out and reclaim arbitrary sizes from a much smaller number of large regions obtained with mmap or brk.

The classic design keeps a free list and a placement policy:

First fit
Take the first hole big enough. Fast, and tends to leave small fragments near the start of the list.
Best fit
Take the smallest hole that fits. Wastes the least per allocation and produces many tiny unusable slivers.
Worst fit
Take the largest hole, on the theory that the leftover will still be usable. In practice it destroys the large blocks you will later need.
Next fit
First fit, but resume from where the last search stopped. Spreads allocations out and avoids re-scanning the same crowded prefix.

External fragmentation is 75%: three quarters of the free memory is outside the largest usable block. This is the failure mode people mean when they say a long-running process "leaks" memory that no leak detector can find.

The policy comparison shows that the obvious ranking is wrong. On the fixed workload, first fit, best fit and next fit all satisfy 4 of 4 later requests, while worst fit satisfies only 3 — and it fails despite leaving 304 bytes free against the others' 104, because by always splitting the biggest hole it destroys the one block large enough for the final request. Leaving more free memory and being less able to use it is the whole of fragmentation in one result.

What real allocators do instead

Modern allocators — glibc's ptmalloc, jemalloc, tcmalloc, mimalloc — barely resemble the free list above. They share a few ideas:

  • Size classes. Round every small request up to one of a few dozen fixed sizes and keep a separate free list per class, so allocation is a pop off a list rather than a search. This trades external fragmentation for internal.
  • Per-thread caches. Each thread gets its own arena, so the common path needs no lock at all. This is the single biggest reason modern allocators outperform older ones under concurrency.
  • Separate handling for large requests. Anything above roughly 128 KiB goes straight to mmap and is returned to the kernel on free, so it cannot fragment the main heap.
  • Coalescing with boundary tags. A size header before and a footer after each block, so a freed block can find its neighbours in constant time and merge with them.

The classic memory bugs

Buffer overflowWriting past the end of a blockOverwrites the next block's header, or a return address on the stack
Uninitialised readReading memory before writing itNon-deterministic behaviour; sometimes leaks previous contents

A use-after-free is the most dangerous of these because it is not merely wrong, it is controllable. An attacker who can get the allocator to hand the freed block to some other part of the program can choose what the stale pointer now sees. Microsoft and Google have both reported that memory-safety issues account for around 70% of their serious security vulnerabilities, and use-after-free is a large slice of that.

The three answers

Discipline plus tooling: C and C++ with AddressSanitizer, Valgrind and MemorySanitizer in CI. Catches most bugs on paths you actually execute. Ownership in the type system: Rust's borrow checker, or C++ smart pointers and RAII used rigorously — the compiler rejects the program rather than the sanitizer catching it at runtime. Automatic memory management: a garbage collector removes the class of bug entirely, at the cost of pauses and memory overhead. All three are legitimate; what does not work is discipline alone.

Garbage collection

A collector's job is to decide which objects are still needed. It cannot know that, so it approximates: an object is kept if it is reachable from a set of roots — the stack, registers, globals. Unreachable is a safe proxy for unneeded; the reverse is not true, which is why a reachable-but-forgotten cache entry is a leak even in a garbage-collected language.

Reference counting

Keep a count per object; free it when the count hits zero. Deallocation is immediate and predictable, which is why Python, Swift and C++'s shared_ptr use it. Three costs: every pointer assignment updates counters, those updates must be atomic if threads share objects, and cycles are never collected — two objects pointing at each other keep each other alive with nothing else pointing at either. Python bolts a cycle detector on top; Swift makes you break cycles by hand with weak references.

Tracing

Periodically start from the roots and mark everything reachable, then reclaim the rest. Handles cycles naturally and costs nothing on ordinary pointer writes, but has to stop or coordinate with the program to get a consistent view.

Tracing strategies
StrategyHowTrade
Mark and sweepMark reachable, sweep the rest into free listsSimple; leaves the heap fragmented
Mark and compactMark, then slide survivors togetherRemoves fragmentation; must update every pointer
CopyingCopy survivors to a second space, then swapAllocation becomes a pointer bump; needs twice the address space
GenerationalCollect a small young space often, the old space rarelyExploits the fact that most objects die young; needs write barriers

The generational hypothesis — most objects die very young, and old objects rarely point to young ones — is the single most productive observation in the field. Collecting only the young generation means touching a small fraction of the heap, which is why a modern JVM or .NET minor collection can take under a millisecond on a multi-gigabyte heap. The bookkeeping cost is a write barrier: a small check on every pointer store to record old-to-young references, so the young collection knows about them without scanning the old space.

"No pauses" usually means "shorter pauses"

Concurrent collectors such as Go's, ZGC and Shenandoah do most of their work alongside the program, but they still need brief stop-the-world points to scan roots, and they pay for concurrency with barriers on reads or writes and with higher allocation rates. The real trade is a three-way one between pause time, throughput and memory footprint, and you can pick any two. A collector given twice the heap will nearly always be faster, because it collects half as often — which is why "the GC is slow" is very often "the heap is too small".

What to do about all of this

  1. Allocate less. The fastest allocation is the one that does not happen. Reuse buffers, allocate in bulk, keep short-lived data on the stack.
  2. Use arenas for phase-structured work. If a request, frame or parse produces many objects that all die together, allocate them from one region and release the whole region at once. Allocation becomes a pointer bump and deallocation becomes free.
  3. Use object pools for uniform, hot objects — connections, buffers, particles. Fixed-size pools cannot fragment.
  4. Let ownership be explicit. RAII in C++, ownership in Rust, defer in Go, context managers in Python. Every construct that ties a lifetime to a scope removes an opportunity to get it wrong.
  5. Size the heap deliberately in managed languages. Too small and you collect constantly; too large and pauses grow and the working set exceeds cache.
  6. Measure the right number. RSS, PSS and heap-profile totals answer different questions; chapter 6 covered why. valgrind --tool=massif, heaptrack, pprof and JFR show where the bytes went rather than how many there were.
Arenas in one sentence

Group allocations by lifetime rather than by type, and the hardest problem in memory management — deciding when to free — disappears for that group.

Check yourself

Why is a stack allocation a single instruction while a heap allocation is a search?

Because the stack guarantees that deallocation happens in exactly the reverse order of allocation. That makes the free region always one contiguous block above the stack pointer, so allocating is subtracting from a register and freeing is adding back. No metadata, no search, no fragmentation. The heap allows objects to die in any order, so the free space becomes a set of holes that has to be tracked, searched, split and merged — and that data structure is the entire cost.

Why is the page table a four-level tree instead of a flat array?

A flat table for a 48-bit space with 4 KiB pages needs 236 entries — about 64 billion — at 8 bytes each, which is 512 GiB of table per process. A tree is sparse: a level is only allocated if something below it is mapped, so a process using a few megabytes needs a handful of 4 KiB tables. The cost is that translation takes four dependent memory accesses instead of one, which is exactly why the TLB exists.

A loop over 20 pages runs far slower than a loop over 12, on a 16-entry TLB. Explain.

Twelve translations fit, so after the first pass every access hits: 12 misses and 36 hits over four passes. Twenty do not fit, and because the loop returns to page 0 only after touching 19 others, each entry has already been evicted by the time it is needed again — LRU is the worst possible policy for a cyclic scan slightly larger than the cache. Every access misses on every pass. Confirm it with the two buttons in demo 1. The fix is the same as for data caches: shrink the working set, or use larger pages so fewer entries cover it.

malloc(1_000_000_000) returns instantly and the process's RSS barely moves. Why?

The allocator reserved a gigabyte of address space via mmap, but no physical frames were allocated. The page table entries are marked not-present, and the first write to each page triggers a demand-zero fault that hands over one zeroed frame at a time. RSS grows only as you touch pages. This is also why an allocation can "succeed" and the process still be killed later by the OOM killer when it actually writes, and why calloc of a large block can beat malloc plus memset: the kernel's frames are already zero.

512 bytes are free but a 256-byte request fails. What is the state of the heap, and what would fix it?

External fragmentation: the free space exists as several non-adjacent holes, none of which is 256 bytes. In the demo it is eight 128-byte holes alternating with eight allocated blocks, giving 75% external fragmentation. Coalescing does not help because no two free blocks are adjacent. The fixes are compaction (impossible in C, since pointers would move), size-segregated pools so blocks of one size share a region, arenas so related allocations are freed together, or going to the kernel for a fresh region and accepting the waste.

Worst fit leaves more free memory than best fit but satisfies fewer requests. How?

Because usable free memory is not total free memory. Worst fit always splits the largest hole, so the largest hole shrinks with every allocation and the heap ends up with many medium holes and no big one. In the demo it leaves 304 bytes free against the others' 104, and still fails a 200-byte request because its largest hole is 130. External fragmentation is the right metric — free bytes outside the largest usable block — and by that measure worst fit is worse (57.2%) despite having more free bytes.

Your Python service's memory grows steadily. The objects are unreachable from your code. What could be happening?

Several candidates. Reference cycles: CPython frees on refcount zero, and two objects referring to each other never reach zero, so they wait for the cycle detector — which can be disabled, or defeated by objects with __del__ in older versions. Something is still reachable that you have forgotten: a module-level cache, a logging handler holding formatted records, a closure capturing a large object, an exception traceback holding an entire frame stack. Or it is not a leak at all but heap fragmentation — CPython returns memory to the OS only when whole arenas become empty, so a transient spike can permanently raise RSS. tracemalloc, objgraph and gc.get_referrers distinguish these.

Ten things to carry forward

  1. The stack is cheap because its lifetimes are ordered. Everything the heap costs comes from giving that guarantee up.
  2. Virtual addresses are translated on every access through a sparse multi-level tree, four levels deep on x86-64.
  3. A TLB miss costs four extra memory accesses; a hit costs none. That is the whole reason the TLB exists.
  4. TLB reach, not hit rate, is the number that matters. A working set slightly larger than the TLB misses on every access, and huge pages multiply reach by 512.
  5. Page faults are a mechanism, not an error. Demand paging, copy-on-write, memory-mapped files and swapping are all built on the present bit.
  6. Allocation reserves address space; touching it commits memory. This is why a huge malloc is instant and free.
  7. External fragmentation means free memory you cannot use. Half a heap can be free and a quarter-heap request still fail.
  8. More free memory is not better memory. Worst fit leaves the most and satisfies the fewest.
  9. Real allocators use size classes and per-thread arenas, trading external fragmentation for internal and removing the lock from the fast path.
  10. Collectors free the unreachable, not the unneeded. A forgotten reference is still a leak, and a bigger heap usually means a faster collector.
