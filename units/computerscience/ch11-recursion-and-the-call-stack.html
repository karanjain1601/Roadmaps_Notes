Recursion and the call stack

Naive Fibonacci at n = 30 makes 2,692,537 function calls and never gets more than 30 frames deep. Understanding why those two numbers are so different — and how to make the first one 59 — is most of what there is to know about recursion.

What a function call costs

Recursion has no special machinery. A function calling itself uses exactly the mechanism a function calling anything else uses, and the only thing that makes it interesting is that many copies of the same frame are alive at once.

A stack frame holds everything one invocation needs: the arguments that did not fit in registers, the local variables, the saved registers the caller expects back unchanged, and the return address. Calling pushes a frame; returning pops it. Because the stack pointer only ever moves in one direction at a time, allocation is a single subtraction — which is why chapter 9 called it free.

Every frame is separate memory, so every recursive call has its own copy of every local. That is what makes recursion work at all, and it is also what limits it: an 8 MiB stack holds about 174,762 frames of 48 bytes, but only 8,192 if each frame declares a 1 KiB local array. Stack overflow is not a function of how many calls you make, only of how deep they nest.

Depth and call count are different numbers

Naive Fibonacci at n = 30 makes 2,692,537 calls and reaches a maximum depth of 30. The call tree is enormous; the path from root to deepest leaf is short, and only one path is alive at a time. Total calls determine time; maximum depth determines stack space. Confusing them is the most common analysis error with recursive code.

Base case, recursive case, progress

Every correct recursive function answers three questions, and getting any one wrong produces a different failure.

What is the smallest problem I can answer outright?
The base case. Omit it and the recursion never stops; the stack overflows. Get it subtly wrong — handling n == 1 but not n == 0 — and it works until someone passes an empty input.
How do I reduce a larger problem to smaller ones of the same shape?
The recursive case. This is the part people find hard and it is usually the shorter of the two.
Does every recursive call move strictly closer to the base case?
Progress. rec(n) calling rec(n) compiles fine and never terminates. rec(n/2) on integers eventually reaches 0 and stops; rec(n/2) on floats never does.
The leap of faith

The thing that makes recursion click is refusing to trace it. Assume the recursive call already works correctly for smaller inputs, and only verify that you combine its answer properly and that you shrink the problem. This is induction: base case plus inductive step. Trying to hold the whole call tree in your head is how recursion feels impossible, and it is unnecessary.

Compare the shapes. factorial(20) makes 20 calls and reaches depth 20 — a straight line, one child per node. fib(10) makes 177 calls and reaches depth 10, because each node has two children and the tree branches. hanoi(10) makes 2,047 calls for 1,023 moves at depth 11. And gcd(1071, 462) finishes in 4 calls, because each step replaces the pair with a much smaller one.

The Euclid case is worth pushing on. Its worst input is a pair of consecutive Fibonacci numbers, which is Lamé's theorem: gcd(6765, 4181) takes 19 calls, and no pair below those values takes more. That gives the algorithm an O(log min(a, b)) bound, and it was the first worked-out complexity analysis of any algorithm, in 1844.

The third row contains the entire distinction between good and terrible recursive algorithms, and it is not about branching. Merge sort and naive Fibonacci both make two recursive calls per invocation. Merge sort halves the input, so the tree has log n levels and Θ(n log n) total work. Naive Fibonacci reduces the input by one, so the tree has n levels and 2n-ish total work. What matters is how fast the problem shrinks, not how many branches there are.

The exact growth is prettier than 2n. Naive Fibonacci makes exactly 2·F(n+1) − 1 calls, so the count grows by a factor of the golden ratio, 1.618, for each increment of n. That is why fib(40) is not slow and fib(50) is unusable.

Tail calls

A call is in tail position if it is the last thing the function does — nothing is computed with its result. When that holds, the caller's frame is dead the moment the call is made, so a compiler can reuse it instead of pushing a new one. The recursion becomes a loop and the stack stops growing.

the same function, before and after
// NOT a tail call: the multiplication happens after the call returns,
// so this frame must survive to do it
function fact(n) {
  if (n <= 1) return 1;
  return n * fact(n - 1);        // depth grows with n
}

// a tail call: the result is returned unchanged, so this frame is dead
function fact(n, acc = 1) {
  if (n <= 1) return acc;
  return fact(n - 1, n * acc);   // depth stays at 1, IF the language optimises it
}

The trick that turns the first into the second is an accumulator: carry the partial result down as an argument instead of building it up on the way back. The same transformation works for list reversal, sums, and most linear recursions.

Most languages do not do this

Scheme requires tail call elimination; Haskell, OCaml, Erlang, Elixir, Scala (for self-calls) and Lua do it. C and C++ compilers usually do it at -O2 but are not required to, so you cannot depend on it. Python, Java, Go, C# and JavaScript do not. Guido van Rossum rejected it for Python explicitly, arguing that losing the stack trace costs more than the recursion is worth, and Python caps recursion at 1,000 frames by default to turn a crash into an exception. ES6 specified proper tail calls but only Safari ever shipped them. So in those languages, a tail-recursive function overflows at exactly the same depth as a non-tail-recursive one — write the loop.

Overlapping subproblems and memoisation

The reason naive Fibonacci is catastrophic is not that it recurses. It is that it computes the same answers over and over. fib(5) calls fib(3) twice, and each of those recomputes the entire subtree beneath it from scratch.

At n = 30 the naive version makes 2,692,537 calls to answer 31 distinct questions. Memoisation makes 59 — exactly 2n − 1 — which is a reduction of 45,636 times. Iteration makes 30 steps and uses no stack at all. All three return 832,040.

Memoisation converts exponential to linear here because of two properties that appear together often enough to have a name:

Overlapping subproblems

The same sub-question is asked many times. If every sub-question were distinct, caching would only add overhead — which is why memoising merge sort gains nothing.

Optimal substructure

The answer to a big problem is built from answers to smaller ones. Both together are the definition of a dynamic programming problem, and chapter 22 develops it properly.

Top-down and bottom-up

Memoisation is dynamic programming top-down: keep the natural recursive shape and add a cache. Tabulation is bottom-up: fill an array in dependency order with no recursion at all. Memoisation is easier to write from a recursive definition and only computes the subproblems it actually needs; tabulation avoids the stack and the hash lookups, and often lets you throw away all but the last row or two. The iterative Fibonacci above is tabulation with a window of two.

Turning recursion into iteration

Any recursive algorithm can be written iteratively, because you can always do by hand what the call stack was doing for you. There are three levels of difficulty.

  1. Tail recursion becomes a loop directly: replace the call with an assignment to the parameters and jump back to the top. This is exactly what tail call elimination does mechanically.
  2. Linear recursion with work after the call becomes a loop with an accumulator, if the combining operation is associative. Factorial and list sum work this way.
  3. Tree recursion needs an explicit stack. You push the state you would have kept in a frame, pop it and resume. This is more code and it is the only option when the depth would overflow.
depth-first traversal, both ways
// recursive: the call stack IS the stack
function walk(node) {
  if (!node) return;
  visit(node);
  walk(node.left);
  walk(node.right);
}

// iterative: the same traversal, stack made explicit
function walk(root) {
  const stack = [root];
  while (stack.length) {
    const node = stack.pop();
    if (!node) continue;
    visit(node);
    stack.push(node.right);   // right first, so left is popped first
    stack.push(node.left);
  }
}

The explicit version is not faster in any interesting way — pushing to a heap-allocated array costs about what pushing a frame costs. What it buys is a stack limited by available memory rather than by the 8 MiB thread stack, which is the difference between handling a million-node tree and crashing on it. It also makes the traversal pausable and resumable, which is how iterators and generators are implemented.

When to reach for recursion

Good fits

Recursively defined data: trees, filesystems, JSON, expression grammars. Divide and conquer: sorting, searching, matrix algorithms. Backtracking: permutations, N-queens, sudoku, where the stack naturally holds the partial solution you need to undo.

Bad fits

Simple iteration over a flat sequence. Anything where depth scales with input size in a language without tail calls. Numeric loops in a hot path, where the call overhead is a real fraction of the work.

The practical test is the depth. If maximum depth is bounded by the logarithm of the input — a balanced tree, a halving search — recursion is safe at any realistic size, because log₂ of a billion is 30. If depth scales linearly with the input, ask how large the input can get: a linked list of a million nodes will overflow, and a recursive JSON parser will overflow on adversarially nested input, which is a real denial-of-service technique.

Unbalanced structures are the trap

Recursion over a binary search tree is depth Θ(log n) if the tree is balanced and Θ(n) if it is not — and a BST built from sorted input is a linked list. The same code is safe on one input and fatal on another. Chapter 15 is about the structures that guarantee the balanced case; the lesson here is that "recursion depth is logarithmic" is a property of the data, not of the code.

Check yourself

Naive fib(30) makes 2.7 million calls but only reaches depth 30. Why are these so different, and which one causes a stack overflow?

Total calls count every node in the call tree; maximum depth counts the longest root-to-leaf path. Fibonacci branches twice per node, so the tree has roughly 1.618n nodes but only n levels — and only one path is alive at any instant, since a call returns before its sibling starts. Depth determines stack space and causes overflow; total calls determine time. Factorial has both equal to n, which is why the distinction is easy to miss until you meet a branching recursion.

Merge sort and naive Fibonacci both make two recursive calls. Why is one Θ(n log n) and the other exponential?

Because of how fast the input shrinks, not how many branches there are. Merge sort halves the input, so after log n levels the subproblems are trivial and the tree has 2log n = n leaves. Fibonacci reduces by one, so the tree has n levels and roughly 1.618n nodes. Branching factor and shrink rate multiply: a branches with the input divided by b gives nlogba leaves, which is the master theorem from chapter 10.

Rewrite sum(n) = n + sum(n-1) so it is tail recursive. Does that fix the stack overflow in Python?

Add an accumulator: sum(n, acc=0) = acc if n == 0 else sum(n-1, acc+n). The call is now the last thing the function does, so no frame needs to survive it. And no, it does not fix anything in Python, which does not implement tail call elimination and caps recursion at 1,000 frames by default. The transformation only helps in languages that guarantee the optimisation — Scheme, Erlang, Haskell, OCaml. In Python, Java, Go, C# and JavaScript you write the loop.

Why does memoising Fibonacci help enormously while memoising merge sort helps not at all?

Memoisation only pays when subproblems overlap. Fibonacci asks the same 31 questions millions of times, so caching turns 2,692,537 calls into 59. Merge sort partitions the input, so every subproblem is a distinct slice that is asked about exactly once — there is nothing to reuse, and the cache would add lookups and memory for no benefit. The test is whether the recursion tree revisits the same arguments, not whether it is recursive.

Euclid's algorithm on 1071 and 462 takes 4 steps. What input makes it slowest?

Consecutive Fibonacci numbers. Each step replaces (a, b) with (b, a mod b), and the slowest shrink happens when the quotient is always 1, which is precisely the Fibonacci recurrence running backwards. gcd(6765, 4181) takes 19 calls, and no smaller pair takes more. This is Lamé's theorem from 1844, which gives the algorithm its O(log min(a, b)) bound and was the first complexity analysis of an algorithm ever written down.

Your recursive JSON parser crashes on some user uploads. What is happening and what would you change?

Deeply nested input — thousands of open brackets — drives recursion depth past the stack limit. It is a known denial-of-service vector precisely because the payload is tiny and the crash is total. Two fixes, and you want both: impose an explicit maximum nesting depth and reject input that exceeds it, and rewrite the parser with an explicit stack on the heap so depth is bounded by memory rather than by the 8 MiB thread stack. Most production JSON parsers do both.

Recursing over a binary search tree is described as Θ(log n) depth. When is that wrong?

Whenever the tree is unbalanced. A BST built by inserting already-sorted keys degenerates into a linked list, giving depth Θ(n) — so the same traversal code is safe on random input and overflows on sorted input. Depth is a property of the data, not the code. Either use a structure that guarantees balance (chapter 15) or write the traversal iteratively so the worst case is a memory question rather than a crash.

Ten things to carry forward

  1. Recursion uses the ordinary call mechanism. What is unusual is that many frames of the same function are alive at once.
  2. Each frame has its own copy of every local, which is what makes recursion work and what limits its depth.
  3. Total calls and maximum depth are different numbers. Calls determine time; depth determines stack space and whether you crash.
  4. Three questions define a correct recursion: base case, recursive case, and strict progress toward the base case.
  5. Take the leap of faith. Assume the recursive call works for smaller inputs and check only the combination and the shrink.
  6. How fast the input shrinks beats how many branches there are. Two calls on half the input is n log n; two calls on n−1 is exponential.
  7. A tail call lets the frame be reused, and an accumulator is the standard way to create one — but most mainstream languages do not implement the optimisation.
  8. Memoisation pays only when subproblems overlap. It takes fib(30) from 2,692,537 calls to 59 and does nothing for merge sort.
  9. An explicit stack converts any recursion to iteration, trading 8 MiB of thread stack for as much heap as you have.
  10. Logarithmic depth is always safe; linear depth needs a size bound. And whether a tree traversal is logarithmic depends on the data, not the code.
