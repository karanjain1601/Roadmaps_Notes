Chapter 2 · The machine

Binary, bits and bitwise operators

A register holds a fixed number of bits and nothing else. Whether those bits mean 200, or −56, or the letter È, or a colour, is a decision made entirely by the instruction that reads them. Most integer bugs are a disagreement about that decision.

Positional notation, in any base

Decimal is a positional system: the digit 4 in 427 means four hundreds because of where it sits, not because of what it is. The rule is that a numeral dk…d1d0 in base b denotes the sum of each digit multiplied by b raised to its position.

Binary is the same rule with b = 2 and only two digits. Hexadecimal is the same rule with b = 16 and sixteen digits, borrowing A–F for ten to fifteen. Nothing conceptual changes; only the number of symbols does.

The number 182 written three ways

Hexadecimal earns its place because 16 = 24, so exactly one hex digit covers exactly four bits, with no carrying between them. Converting is a lookup, not arithmetic: split the bits into groups of four from the right and translate each group independently. 1011 0110 becomes B 6. Going the other way is the same table read backwards. Octal (base 8, three bits per digit) survives for the same reason in Unix file permissions, where chmod 755 is really three groups of three bits.

Powers of two worth knowing by sight

28 = 256, 210 = 1024, 216 = 65,536, 220 ≈ one million, 230 ≈ one billion, 232 = 4,294,967,296, 253 ≈ 9.0 × 1015 (the largest exactly representable integer in a double), 263 ≈ 9.2 × 1018. Recognising these on sight is how you spot an overflow bug from a log line.

The kilobyte argument

Because 210 = 1024 is close to 1000, the metric prefixes got quietly redefined by the computing industry, and then quietly un-redefined by standards bodies. The IEC binary prefixes are kibi, mebi, gibi and tebi: 1 KiB = 1024 bytes, 1 MiB = 1024 KiB, 1 GiB = 1024 MiB. The SI prefixes keep their real meaning: 1 kB = 1000 bytes.

The gap compounds. At the kilo level it is 2.4%; at the giga level it is 7.4%. This is exactly why a drive sold as 500 GB shows up in your operating system as roughly 465.7 GiB. Neither party is lying — the manufacturer counts in powers of ten, the operating system reports in powers of two, and 500 × 109 ÷ 230 = 465.7.

Fixed widths and what falls off the end

Mathematics has infinitely many integers. A register has 8, 16, 32 or 64 bits. Every integer type in every language is a choice about how much of the number line to keep, and arithmetic that leaves that range does not raise its hand — the extra bits simply have nowhere to go.

Two of these limits have their own historical incidents. The 32-bit signed limit of 2,147,483,647 is the "year 2038 problem": Unix time counts seconds since 1970 in a signed 32-bit integer, and that counter overflows on 19 January 2038. The 16-bit signed limit of 32,767 was the reason the Boeing 787 needed a power cycle every 248 days and the reason countless spreadsheet row counts stopped at 32,767.

Overflow is not an error in most languages

In C and C++, unsigned overflow is defined to wrap, but signed overflow is undefined behaviour. That is not pedantry: it licenses the compiler to assume signed overflow never happens, so a check written as if (x + 1 < x) can be optimised away entirely, because the compiler reasons that it can never be true. Java and Go wrap silently. Rust panics in debug builds and wraps in release, unless you ask for checked_add or saturating_add. Python promotes to arbitrary precision and never overflows at all, which is why it is slower.

How negative numbers are stored

There is no minus sign in hardware. Three schemes have been tried for putting negative numbers into a fixed-width field, and only one is still in use.

Three ways to encode −5 in eight bits
SchemeBitsHowWhy it lost
Sign and magnitude10000101Top bit is the sign, rest is the sizeTwo zeros (00000000 and 10000000); addition needs special cases
One's complement11111010Invert every bit of +5Still two zeros; needs an end-around carry
Two's complement11111011Invert every bit, then add 1Won

Two's complement won because it makes subtraction disappear. The same adder circuit that computes 7 + 3 computes 7 − 3, by feeding it 7 and the two's complement of 3. There is exactly one zero. And the negation rule is uniform: −x = ~x + 1, with no special case for zero (invert 00000000 to get 11111111, add 1, wrap back to 00000000).

The mental model that makes it click: in an n-bit two's complement field, the top bit has weight −2n−1 instead of +2n−1. Every other bit keeps its usual positive weight. So in eight bits:

reading 11111011 as signed and unsigned
bit      1     1    1    1    1    0    1    1
weight -128   +64  +32  +16   +8   +4  +2   +1     signed
       +128   +64  +32  +16   +8   +4  +2   +1     unsigned

signed:   -128 +64 +32 +16 +8 +2 +1  =  -5
unsigned: +128 +64 +32 +16 +8 +2 +1  =  251

Both readings are correct. The bits do not know which one you meant. That is the whole story of signed-versus-unsigned bugs: some part of the program wrote 251 and another part read −5.

The asymmetric range

Eight bits give you −128 through 127. There are 128 negative values and only 127 positive ones, because zero takes up a slot on the positive side. The practical consequence is that -(-128) cannot be represented in eight bits, so abs(INT_MIN) is negative in C, and Math.abs(Integer.MIN_VALUE) in Java returns Integer.MIN_VALUE. Any code that assumes negating a number is always safe has a bug at exactly one input.

Carry and overflow are different flags

After an addition the ALU sets several status bits. Two of them get confused constantly.

Carry (also borrow)
Set when the result does not fit if you read the operands as unsigned. It is literally the bit that fell off the top end.
Overflow
Set when the result does not fit if you read the operands as signed. The rule: adding two numbers with the same sign and getting the opposite sign.

These are independent. A single addition can set either, both or neither, and the hardware sets both every time because it does not know which interpretation you had in mind. Your comparison instruction, or your compiler, picks which flag to look at.

Two presets make the distinction concrete. In eight bits, 127 + 1 gives the bit pattern 10000000: unsigned that is 128, which fits fine, so no carry; signed it is −128, and two positives produced a negative, so overflow is set. 200 + 100 gives 00101100: unsigned that is 44 rather than 300, so carry is set; but read as signed the operands were −56 and +100, and −56 + 100 = 44 is perfectly correct, so overflow is clear.

Subtraction behaves the same way in reverse. 5 − 9 in eight bits yields 11111100: 252 unsigned with a borrow, −4 signed with no overflow. If you have ever seen a length or a size wrap around to four billion, this is the mechanism — a subtraction on an unsigned type went below zero.

The bitwise operators

Six operations, each applied to every bit position independently and in parallel. They are among the cheapest instructions a CPU has — typically one cycle, often several per cycle.

The operators, with the mental shorthand for each
OperatorSymbolResult bit is 1 when…Use it to…
AND&both inputs are 1clear bits, test bits, take a remainder mod a power of two
OR|either input is 1set bits, merge flag sets
XOR^the inputs differflip bits, detect difference, cheap parity and checksums
NOT~the input is 0invert a mask

Shift right>> / >>>Move every bit down n places. Two variants — see below.
Two right shifts, not one

A logical right shift fills the vacated top bits with zeros. An arithmetic right shift copies the existing sign bit into them, so negative numbers stay negative. Languages differ in how they expose this: Java and JavaScript spell them >> (arithmetic) and >>> (logical); C and Rust pick one based on whether the type is signed. Verify it in the demo: 11111000 is −8, and shifting it right by one gives 124 logically but 252 arithmetically, which reads as −4.

Arithmetic shift is not division

Right-shifting a negative number rounds toward negative infinity; C-style integer division truncates toward zero. So -7 >> 1 is −4 while -7 / 2 is −3. Replacing a division by a shift is only safe for unsigned values or non-negative signed ones. Modern compilers already turn division by a constant power of two into the correct shift-and-fixup sequence, so writing the shift by hand buys nothing and risks this bug.

Shifting too far is undefined

In C and C++, shifting by an amount greater than or equal to the width of the type is undefined behaviour. On x86 the hardware masks the shift count to the low 5 or 6 bits, so x << 32 on a 32-bit value is x << 0, which is x — the opposite of the zero most people expect. JavaScript inherits exactly this: all bitwise operators convert to 32-bit signed integers first, so 1 << 32 is 1, and 0x80000000 | 0 is −2,147,483,648.

Bit patterns worth memorising

A small vocabulary of idioms covers most real uses of bit manipulation. Each one is a single-cycle replacement for something that would otherwise be a loop or a branch.

the working set
// test, set, clear and toggle bit i
isSet   = (x >> i) & 1
x |=  (1 << i)                // set
x &= ~(1 << i)                // clear
x ^=  (1 << i)                // toggle

// masks
low8    = x & 0xFF             // keep the bottom eight bits
mod16   = x & 15               // x % 16, for unsigned x only
alignUp = (x + 7) & ~7         // round up to a multiple of 8

// the lowest set bit
x & (x - 1)                    // clear it
x & -x                         // isolate it
(x & (x - 1)) == 0 && x != 0   // x is a power of two

// count the set bits (Kernighan's loop: iterations = number of 1s)
while (x) { x &= x - 1; count++; }

// swap without a temporary — see the warning below
a ^= b; b ^= a; a ^= b;

Take 10110110 as a worked example. Subtracting one gives 10110101, and ANDing the two gives 10110100: the lowest set bit is gone, everything else survived. Kernighan's loop repeats that until nothing is left, so it runs once per set bit — five iterations here, not eight. Meanwhile x & -x gives 00000010, isolating that lowest bit, which is how a scheduler finds the first free slot in a bitmap.

The XOR swap is a trap, not a trick

It fails when both arguments name the same storage: swap(&v[i], &v[i]) zeroes the value instead of leaving it alone, because the first a ^= b already makes it zero. It is also slower than a temporary variable on any modern CPU, because the three operations are strictly dependent while a temporary swap can be done in parallel or eliminated entirely by register renaming. Know it so you can recognise it in old code; do not write it.

Flag sets: the honest use case

The most common real use of bitwise operators is packing a set of booleans into one integer. Instead of eight separate fields, one byte with named masks:

permission flags, the way filesystems and APIs do it
const READ = 1, WRITE = 2, EXEC = 4, DELETE = 8;   // 0001 0010 0100 1000

let perms = READ | WRITE;          // 0011  -> 3

perms & WRITE                      // 2, truthy: writing is allowed
perms & EXEC                       // 0, falsy: it is not
perms |= EXEC;                     // grant  -> 0111 -> 7
perms &= ~WRITE;                   // revoke -> 0101 -> 5
perms ^= DELETE;                   // toggle -> 1101 -> 13

This is why Unix permissions are three octal digits, why O_RDONLY | O_CREAT looks the way it does, and why so many APIs take an integer called flags. It costs one machine word for up to 64 independent booleans, and testing one is a single AND.

Endianness

A 32-bit value occupies four consecutive bytes in memory. Which of those four bytes gets the lowest address is not determined by anything in the value itself. It is a convention the machine picked, and two conventions exist.

Little-endian

Least significant byte at the lowest address. Used by x86, x86-64, and ARM in its usual configuration. Reading fewer bytes than were written gives you the low part of the number, which makes casting a 32-bit value to 8-bit a no-op.

Big-endian

Most significant byte at the lowest address. Used by older SPARC, PowerPC and 68000 machines, and — the reason it still matters — by every internet protocol header. Bytes appear in memory in the order you would write the number down.

The names come from Gulliver's Travels, where two factions go to war over which end of a boiled egg to crack. Danny Cohen borrowed the joke in a 1980 note about network protocol design, and it stuck.

With the defaults, a little-endian writer stores the id 0x12345678 as the bytes 78 56 34 12. A big-endian reader walks those same bytes from the lowest address and reconstructs 0x78563412, which is 2,018,915,346 instead of 305,419,896. The port fares no better: 8080 is 0x1F90, stored little-endian as 90 1F, and read big-endian as 0x901F = 36,895.

The flags byte comes through untouched, every time. A single byte has no internal ordering to get wrong, which is the general rule: endianness only affects multi-byte values. It is also why byte-oriented text formats such as JSON and CSV never have this problem, and why binary formats always have to specify a byte order in their spec.

Network byte order

Internet protocols fixed the argument by decree: IP, TCP and UDP headers are big-endian, and that convention is called network byte order. The POSIX functions htons, htonl, ntohs and ntohl convert between host and network order, and on a big-endian machine they compile to nothing at all. Any time you write a binary format that crosses machines — a file, a wire protocol, a memory-mapped structure — you must pick an order and write it in the specification.

Detecting it at runtime

Write the 32-bit value 1 into memory and read back the first byte. If it is 1 the machine is little-endian; if it is 0 it is big-endian. In C that is a union or a cast; in JavaScript, new DataView(buf) lets you specify the order explicitly on every read and write, which is the better habit anyway.

Check yourself

Convert 0b11010110 to hexadecimal and to decimal, in your head.

Split into nibbles: 1101 0110. That is D and 6, so 0xD6. For decimal, either add the weights (128 + 64 + 16 + 4 + 2 = 214) or use the hex: 13 × 16 + 6 = 214. As a signed 8-bit value the top bit is set, so it is 214 − 256 = −42.

Why does two's complement need only one adder circuit for both addition and subtraction?

Because a − b equals a + (−b), and −b in two's complement is ~b + 1. Inverting bits is free (one NOT gate per bit) and the "+1" can be fed into the adder's carry-in, which already exists. So subtraction is the same adder with the second input inverted and carry-in set to 1. No separate subtractor, no special cases for signs.

An 8-bit addition sets the carry flag but not the overflow flag. Give operands that do this, and explain who should care.

200 + 100. Unsigned, the true answer 300 does not fit in eight bits, so carry is set. Signed, the operands are −56 and +100, and the answer −56 + 100 = 44 fits perfectly, so overflow is clear. Code treating the values as unsigned has a bug; code treating them as signed does not. The hardware sets both flags on every operation and lets the instruction stream decide which one to branch on — which is why C has separate comparison behaviour for signed and unsigned types.

You want x / 8 and someone suggests x >> 3. When is that wrong?

When x can be negative. Arithmetic right shift rounds toward negative infinity, while C-family integer division truncates toward zero, so -9 >> 3 is −2 while -9 / 8 is −1. It is also wrong if x is a floating-point value, and pointless in general: every mainstream compiler already emits the correct shift-plus-correction sequence for division by a constant power of two, so the hand-written version gains no speed and loses correctness at negative inputs.

How many iterations does while (x) { x &= x - 1; count++; } perform on 0b10110110, and why is that better than checking all eight bits?

Five, one per set bit. Each iteration clears exactly the lowest remaining 1. A naive loop over all positions runs once per bit of the word — eight here, sixty-four on a 64-bit value — regardless of how sparse the value is. Kernighan's loop is proportional to the number of set bits, which matters for sparse bitmaps. In practice, use the hardware: popcount on x86, CNT on ARM, Integer.bitCount in Java, x.count_ones() in Rust.

A colleague says a bug "must be endianness" because a 1-byte status field is coming back wrong across a network. Are they right?

No. A single byte has no internal byte order, so it can never be affected by endianness. Confirm it in demo 2: switch the writer and reader to opposite orders and the flags field is identical every time, while the id and port are mangled. The real cause is something else — struct padding, a field offset mismatch, a signed/unsigned reinterpretation, or a protocol version difference.

In JavaScript, 0x80000000 | 0 evaluates to −2147483648. Explain, and give the fix.

JavaScript numbers are doubles, but every bitwise operator first converts its operands to 32-bit signed integers, applies the operation, and converts the 32-bit signed result back to a double. 0x80000000 has the top bit set, so as a signed 32-bit value it is −2147483648. The fix is >>> 0, the unsigned right shift by zero, which is the standard idiom for reading the result as unsigned: (0x80000000 | 0) >>> 0 gives 2147483648. For anything wider than 32 bits, use BigInt.

Ten things to carry forward

  1. Bits carry no type. The same eight bits are 251 or −5 depending only on which instruction reads them.
  2. Hex is a shorthand for bits, not a different number system to learn. One hex digit is exactly four bits, always.
  3. Every integer type is a range, and arithmetic that leaves the range does not announce itself. It wraps, saturates, panics or invokes undefined behaviour depending on the language.
  4. Two's complement gives the top bit a negative weight. That one change makes subtraction reuse the adder and leaves exactly one zero.
  5. −x = ~x + 1, and the range is asymmetric, so the most negative value has no positive twin.
  6. Carry means unsigned overflow, overflow means signed overflow. They are set independently on every operation.
  7. Right shift comes in two flavours. Arithmetic preserves sign and rounds toward negative infinity; logical fills with zeros.
  8. A handful of idioms cover most bit work: masks for clearing and testing, x & (x-1) to clear the lowest set bit, x & -x to isolate it, and flag sets for packing booleans.
  9. Endianness is a byte-order convention, not a property of the number. It affects only multi-byte values, and it is why binary formats must specify an order.
  10. Network byte order is big-endian by decree, and every protocol that crosses machine boundaries needed a decree like it.
