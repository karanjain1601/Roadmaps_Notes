Trees and binary search trees

The same thousand keys inserted in a different order give a tree of height 9 or a tree of height 999. Identical data, identical code, a hundredfold difference in every lookup — and nothing in the structure notices or objects.

Terminology, and the shapes that matter

A tree is a connected graph with no cycles, drawn with one node designated the root and everything hanging beneath it. The vocabulary is worth pinning down because the definitions are used inconsistently in the wild.

Root, parent, child, sibling, leaf
The root has no parent; a leaf has no children; everything else is internal. Each node has exactly one parent, which is what distinguishes a tree from the graphs in chapter 18.
Depth and height
Depth of a node is its distance from the root; the root has depth 0. Height of a node is the longest distance down to a leaf; a leaf has height 0. The height of the tree is the height of the root. A single node is a tree of height 0, and an empty tree is conventionally height −1.
Degree and arity
The number of children. A binary tree allows at most 2, an n-ary tree at most n.

The perfect tree gives the bound everything else is measured against: n nodes need height at least ⌈log₂(n+1)⌉ − 1. For a thousand nodes that is 9; for a million it is 19. Anything that keeps a tree near that bound turns linear search into logarithmic search.

The four traversals

Three depth-first orders, distinguished only by when the node itself is visited relative to its subtrees, plus one breadth-first order that is not depth-first at all.

the same three lines, reordered
function preorder(n)  { if(!n) return; visit(n); go(n.left); go(n.right); }
function inorder(n)   { if(!n) return; go(n.left); visit(n); go(n.right); }
function postorder(n) { if(!n) return; go(n.left); go(n.right); visit(n); }

// level order is different in kind: a queue, not the call stack
function levelorder(root) {
  const q = [root];
  while (q.length) {
    const n = q.shift();
    visit(n);
    if (n.left)  q.push(n.left);
    if (n.right) q.push(n.right);
  }
}

The tree built from 50 30 70 20 40 60 80 65 gives in-order 20 30 40 50 60 65 70 80 — sorted, as it always is. Pre-order gives 50 30 20 40 70 60 65 80, and post-order gives 20 40 30 65 60 80 70 50. Switch to the sorted input and the tree becomes a straight chain, at which point all three depth-first orders collapse to the same thing.

Two orders reconstruct a tree; one does not

In-order alone tells you nothing about shape — every BST holding the same keys has the same in-order. Pre-order alone is enough for a BST specifically, because the ordering constraint tells you where each subtree ends. For a general binary tree you need two traversals, and they must be in-order plus one of the others: pre-order plus post-order is not enough, because it cannot distinguish a left child from a right child when a node has only one. This is a standard interview question and the reasoning is the answer.

The binary search tree property

For every node: every key in the left subtree is smaller, and every key in the right subtree is larger.

Note "every key in the subtree", not "the immediate children". A tree where each node beats its own children but violates the ordering against a grandparent is not a BST, and it is the standard bug in a hand-written validator. The correct check passes a range down: at every node, verify the key falls inside (low, high) and recurse with the range narrowed.

Given that invariant, search is a decision at each node rather than a scan:

search, insert and the min
search(node, key):
  while node:
      if key == node.key: return node
      node = key < node.key ? node.left : node.right   // discard half
  return null

insert(node, key):
  // exactly the same walk; the new node goes where the search failed
  if (!node) return newNode(key)
  if (key < node.key) node.left  = insert(node.left, key)
  else if (key > node.key) node.right = insert(node.right, key)
  return node

minimum(node): while (node.left) node = node.left; return node

Every one of these costs Θ(height). That is the whole analysis, and it is why the next section matters so much: the height is not controlled by anything.

Deletion, and its three cases

No children

Detach it. Nothing else changes.

One child

Replace the node with its child. The subtree's ordering relative to everything above is unaffected.

Two children

Copy in the in-order successor — the smallest key in the right subtree — then delete that successor, which by construction has at most one child. The predecessor works symmetrically.

The third case is the only interesting one, and the reason it works is that the successor is precisely the key that can sit in the deleted node's place without violating the ordering against anything on either side. It is also the reason deletion is where most hand-written BST implementations have their bug: alternating between successor and predecessor is what keeps a hand-rolled tree from drifting one-sided, and always taking the successor slowly skews the tree left.

Degeneration

Nothing in the insert code above mentions balance. The shape a BST ends up with is determined entirely by the order the keys arrived in, and one common order is catastrophic.

With a thousand keys the four orders are not close. Sorted insertion gives height 999 and an average depth of 499.5 — a linked list, with every insert appended to the bottom right. Reversed is identical in the mirror. Balanced order, inserting the median first and recursing, gives height 9, the theoretical minimum, and an average depth of 7.99. Searching for the largest key costs 1,000 comparisons in the first case and 10 in the last: a hundredfold difference for identical data.

Random insertion sits close to the good end. Measured across 300 random permutations of a thousand keys, the height has a median of 21 and a mean of 20.87, never exceeding 28. The average node depth comes out at 10.95, which matches the exact expected internal path length 2(n+1)Hn/n − 4 = 10.99 almost precisely.

The asymptotic overstates it here

The result usually quoted for average depth is 2 ln n, which at n = 1000 gives 13.8 — 26% above the measured 10.95, because it is only the leading term and the −4n correction is not negligible at this size. Reed's asymptotic for the height, 4.311 ln n − 1.953 ln ln n − 2, gives 24.0 against a measured mean of 20.9. Both asymptotics are correct and both converge slowly. When n is in the thousands rather than the billions, measure.

Sorted input is not a rare case

It is the default. Database rows arrive by primary key. Log entries arrive by timestamp. A file is read in order. A migration replays IDs ascending. Building a BST by iterating any of these produces a linked list, and the code that does it looks correct and passes every test written against random data. This is the single strongest argument for the self-balancing structures in chapter 15, and for the rule that a plain BST is a teaching structure rather than a production one.

What a tree gives you that a hash table cannot

Chapter 13's hash table beats a balanced tree on the single operation both support: Θ(1) against Θ(log n) for lookup by exact key. The tree earns its place on everything that depends on order, which hashing destroys by design.

This is why the standard libraries ship both. C++ has map (a red-black tree) and unordered_map; Java has TreeMap and HashMap; Rust has BTreeMap and HashMap. It is also why a database index is a B-tree and not a hash table — WHERE created_at BETWEEN ... AND ... and ORDER BY are the entire point, and a hash index cannot serve either.

Other trees, and where they appear

Heaps (chapter 16) relax the ordering to parent-versus-child only, which is weaker but enough for a priority queue and cheap enough to store in a flat array. Tries (chapter 17) branch on characters instead of comparisons, giving lookup proportional to key length rather than to n. B-trees (chapter 15) widen the fan-out to hundreds so each node fills a disk page. And expression trees, ASTs, DOM trees and filesystem hierarchies are trees where the ordering property is irrelevant and the structure is the point.

Practical notes

  1. Do not write a plain BST for production. Use the standard library's balanced map. Write one to understand it, then use the one that maintains its invariant.
  2. Validate with a range, not with children. Checking only left.key < node.key < right.key accepts trees that are not BSTs.
  3. Prefer iterative search. The loop version has no stack depth at all, so it cannot overflow on a degenerate tree — which is exactly the case where recursion would.
  4. Decide your duplicate policy explicitly: reject, keep a count on the node, or send them consistently to one side. Silently discarding them is the default in most textbook code and is usually wrong.
  5. Remember the constant factors. Chapter 5's argument applies: each level of a pointer-based tree is a cache miss, and those misses are serialised. For a few thousand elements a sorted array with binary search is often faster despite identical complexity, because it is contiguous.

Check yourself

Which traversal of a BST produces sorted output, and why?

In-order: left subtree, then the node, then the right subtree. The BST property says everything left of a node is smaller and everything right is larger, so visiting in that order emits all smaller keys, then the node, then all larger ones — recursively, at every level. It is the reason a BST is useful at all, and it means an in-order walk gives you a sort for free in Θ(n) once the tree exists.

Why is checking node.left.key < node.key < node.right.key at every node not a valid BST test?

Because the BST property constrains entire subtrees, not just immediate children. A tree with root 50, left child 30, and 30's right child 60 passes the local check at every node — 30 < 50, and 60 > 30 — yet 60 sits in the left subtree of 50, so an in-order walk emits 30, 60, 50 and search for 60 goes right from the root and misses it. The correct validator passes a permitted range down: at each node check low < key < high, then recurse with (low, key) and (key, high).

Deleting a node with two children replaces it with the in-order successor. Why does that particular key work?

Because the successor — the smallest key in the right subtree — is the only key larger than everything in the left subtree and smaller than everything else in the right. Putting it in the deleted node's place preserves the ordering against both sides. It also has at most one child, since it is the leftmost node of its subtree, so deleting it afterwards falls into an easy case. The in-order predecessor works identically by symmetry, and alternating between the two keeps a hand-rolled tree from skewing.

Inserting 1,000 sorted keys gives a tree of height 999. What went wrong, and what did not?

Nothing went wrong in the code. Each key is larger than everything present, so it walks to the bottom right and attaches there — a degenerate tree, which is a linked list with extra pointers. Every operation becomes Θ(n): searching for the largest key takes 1,000 comparisons against 10 in a balanced tree. The BST invariant is still perfectly satisfied. Nothing in the structure has any mechanism to notice or object, which is exactly what chapter 15's structures add.

Is random insertion order good enough in practice?

Statistically yes, practically no. Across 300 random permutations of 1,000 keys the height had a median of 21 and never exceeded 28, against a minimum of 9 — a factor of two or three from optimal, and comfortably logarithmic. But you rarely control the order. Real keys arrive sorted by ID, by timestamp, or by whatever the previous stage emitted, and adversarial input can be sorted deliberately. Randomised structures such as treaps and skip lists get the guarantee by randomising internally rather than trusting the input.

You need to find every record with a timestamp in a given range. Why is a hash index useless?

Because hashing deliberately destroys order — that is what makes it uniform. Keys adjacent in value land in unrelated buckets, so there is no way to enumerate a range without scanning every bucket, which is Θ(n). A tree keeps order, so you descend to the low end in Θ(log n) and then walk in-order until you pass the high end: Θ(log n + k) for k results. Minimum, maximum, predecessor, successor and ORDER BY all have the same shape, which is why database indexes are B-trees.

A balanced BST and a sorted array both support Θ(log n) search. When is the array faster, and when is it not?

The array is faster for lookups because it is contiguous: binary search touches log n positions in one block, and the later probes are usually already in cache, while every level of a tree is an independent pointer chase and a serialised cache miss. For a few thousand elements the array often wins outright. The tree wins when the data changes: inserting into a sorted array is Θ(n) because everything after the insertion point shifts, while the tree is Θ(log n). Static data indexes better as a sorted array; mutable data wants a tree.

Ten things to carry forward

  1. Depth counts down from the root, height counts up from the leaves. A tree's height is the root's height.
  2. n nodes need height at least ⌈log₂(n+1)⌉ − 1 — 9 for a thousand, 19 for a million. That is the target.
  3. The three depth-first traversals differ only in when the node is visited. Level-order uses a queue instead of the stack.
  4. In-order on a BST is sorted order, which is the whole reason the structure is useful.
  5. The BST property constrains entire subtrees, so a validator must carry a range down rather than compare with children.
  6. Every BST operation costs Θ(height), and nothing in a plain BST controls the height.
  7. Deletion with two children uses the in-order successor, the one key that can take the deleted node's place without breaking the ordering.
  8. Insertion order decides the shape. A thousand sorted keys give height 999; a balanced order gives 9. A hundredfold difference in lookups for identical data.
  9. Random order is close to optimal — median height 21 at n = 1000 — but you rarely control the order, and real data arrives sorted.
  10. Trees earn their place on ordered operations: min, max, predecessor, successor, range and sorted iteration, none of which a hash table can do.
