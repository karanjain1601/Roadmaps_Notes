Greedy, backtracking and dynamic programming

Three strategies for the same shape of problem

All three attack optimisation problems — find the best arrangement, the cheapest route, the largest subset — and they differ in how much of the search space they are willing to look at.

The trade in one table
StrategyExploresCostOptimal?
GreedyOne path, never reconsideringUsually Θ(n log n)Only if the problem has the right structure
BacktrackingEverything, abandoning branches that cannot workExponential, minus what pruning removesYes
Dynamic programmingEvery distinct subproblem, exactly oncePolynomial when the subproblems are fewYes

Several algorithms you already know are instances. Dijkstra, Prim and Kruskal are greedy. Bellman-Ford is dynamic programming — its k-th pass computes the shortest paths using at most k edges. A DFS that abandons a branch is backtracking.

Greedy, and the two conditions

A greedy algorithm takes the locally best option at each step and never revisits it. That is fast and often wrong, and two properties determine which.

Optimal substructure
An optimal solution contains optimal solutions to its subproblems. Shared with dynamic programming — without it neither approach works.
The greedy choice property
A globally optimal solution can be reached by making the locally optimal choice first. This is the one that fails, and proving it usually needs an exchange argument: take any optimal solution that does not make the greedy choice, show you can swap the greedy choice in without making it worse.

US coins are a canonical system: greedy is optimal for every amount, which is not an accident but a property that was designed in. Change the denominations to 1, 3 and 4 and greedy fails on 24 of the first 100 amounts, starting at 6 — where it takes 4 + 1 + 1 and the answer is 3 + 3. Greedy fails quietly, and the test data hides it

Every failure above is a plausible-looking answer that happens to be worse. Nothing throws, nothing is malformed, and the total is always correct. Testing with US or euro coins would give a perfect pass rate on an algorithm that is fundamentally unsound for arbitrary denominations — and checking whether a coin system is canonical is itself a nontrivial problem. If you cannot prove the greedy choice property with an exchange argument, do not assume it.

Backtracking: search everything, but leave early

When no greedy rule is sound, search the space — but abandon a partial solution the moment it cannot possibly extend to a valid one. That single check is the difference between infeasible and routine.

the shape every backtracking algorithm has
solve(partial):
    if (complete(partial)) { record(partial); return }
    for (choice of candidates(partial)) {
        if (!feasible(partial, choice)) continue     // ← the pruning. everything.
        apply(choice)
        solve(partial)
        undo(choice)                            // ← the backtrack
    }

On an 8 × 8 board the pruned search visits 15,720 nodes. Placing a queen anywhere in each row and only checking validity at the end means examining 8⁸ = 16,777,216 arrangements. Both find exactly 92 solutions; pruning is 1,067 times cheaper, and the gap grows with n.

Note where the pruning happens. It is not at the leaves but at every level: rejecting a queen in row 2 eliminates every arrangement of rows 3 through 8 beneath it in one step. That is why the saving compounds, and it is the same reason branch-and-bound and alpha-beta pruning work.

Improving a backtracking search

Three levers, in rough order of value. Prune harder: detect infeasibility as early as possible, and add derived constraints — constraint propagation in a Sudoku solver eliminates far more than the direct rules do. Order the choices: try the most-constrained variable first, so failures happen near the root where they cost most to leave. And break symmetry: for N-queens, fixing the first queen to the left half of the first row halves the work with no loss.

Dynamic programming

Backtracking explores a tree of choices; often that tree contains the same subproblem many times over. Dynamic programming applies when two conditions hold together:

  1. Optimal substructure — an optimal solution is built from optimal solutions to subproblems.
  2. Overlapping subproblems — the same subproblems recur, so solving each once and reusing the answer is a saving.

Chapter 11 measured this on Fibonacci: naive recursion for fib(30) makes 2,692,537 calls, and memoising makes 59 — a 45,636-fold reduction, from nothing more than remembering. The exponential blowup was entirely recomputation.

Top-down: memoisation

Write the recursion naturally, add a cache. Only the subproblems you actually need get computed, and the code reads like the definition. Costs stack depth and hash lookups.

Bottom-up: tabulation

Fill a table in dependency order. No recursion, no stack limit, better locality, and it makes the space optimisation below possible. Costs you having to work out the order, and it computes every cell whether needed or not.

d[0][j] = j                    // insert j characters

d[i][j] = if a[i-1] === b[j-1]  then  d[i-1][j-1]        // free: characters match

                        d[i-1][j],     // delete from a
                        d[i][j-1] )    // insert into a

Getting the recurrence right is the whole job. Once you have it, the implementation is a nested loop, and every DP problem reduces to three questions: what is the state? what is the recurrence? what is the base case?

Space, and getting the answer back out

Edit distance on two 1,000-character strings fills a million cells. But look at the recurrence: row i depends only on rows i and i−1. Keep two rows and the memory drops from 1,001,000 cells to 2,002 — a 500-fold reduction with no change to the running time.

The space optimisation costs you the answer

Reducing to two rows gives the optimal value and destroys the ability to reconstruct the optimal solution, because reconstruction walks backwards through the full table. If you need the actual edit script or the actual set of items, you must either keep the whole table, store parent pointers, or use Hirschberg's divide-and-conquer trick, which recovers the alignment in linear space at twice the time. Deciding whether you need the value or the solution should come before you optimise anything.

Two other traps are worth naming. Pseudo-polynomial: knapsack's Θ(n·W) looks polynomial but W is a number, not an input size, so a capacity written in 64 bits makes the table astronomically large — knapsack is NP-hard, as chapter 24 explains. And state design: if your recurrence needs information the state does not carry, the answer is wrong rather than slow, and the fix is always to enlarge the state.

Choosing between the three

  1. Try greedy first, but prove it. Write the exchange argument or find a counterexample. If you can do neither, assume it is wrong.
  2. Write the brute-force recursion. It is usually easy and it makes the state explicit.
  3. Look for repeats. If the recursion tree revisits states, memoise — that is often the whole optimisation, and it is one line.
  4. Convert to a table if you need the space optimisation or you are hitting the stack.
  5. If the subproblems do not overlap, DP buys nothing. Merge sort is divide and conquer, not DP, because its halves never share anything.
  6. If nothing overlaps and nothing is greedy, backtrack and prune. Then prune harder.
A quick diagnostic

Does the problem have optimal substructure? If no, none of these apply and you may be facing something genuinely hard. If yes: do subproblems overlap? If no, divide and conquer. If yes: is the locally best choice provably safe? If yes, greedy; if no, dynamic programming. And if the state space is too large to tabulate, backtracking with pruning, or an approximation.

Check yourself

Greedy change-making is optimal for US coins and fails for 1, 3, 4. What is the difference?

The denominations, not the algorithm. US coins form a canonical system, in which the greedy choice property provably holds for every amount. With 1, 3 and 4 it fails for 24 of the first 100 amounts, starting at 6: greedy takes 4 + 1 + 1 and the answer is 3 + 3. With 1, 7 and 10, the amount 14 costs five coins greedily and two optimally. The failure is silent — the total is always right, just made from more coins than necessary — so testing against real currency would give a perfect pass rate on an unsound algorithm.

Greedy by value-to-weight ratio is optimal for fractional knapsack and wrong for 0/1. Why?

Because the exchange argument depends on being able to split. In the fractional version, if an optimal solution omits some of a better-ratio item, you can always swap in a fraction of it for an equal weight of something worse and not lose — so the greedy choice is safe. In 0/1 you must take all or nothing, so a high-ratio item may leave capacity that nothing fits into. On four items with capacity 7, greedy scores 8 and the optimum is 9; allow fractions and the same rule scores 9.7. One word in the problem statement changes which strategy is correct.

Where does backtracking's saving actually come from?

From rejecting partial solutions high in the tree, not from anything at the leaves. Refusing a queen in row 2 eliminates every arrangement of rows 3 through 8 below it in one step, so the saving compounds multiplicatively with depth. On 8 × 8 that is 15,720 nodes against 8⁸ = 16,777,216 placements — a factor of 1,067 for the same 92 solutions. It is the same mechanism as branch-and-bound and alpha-beta, and it is why detecting infeasibility earlier is worth more than detecting it more cheaply.

What two conditions must hold for dynamic programming to help?

Optimal substructure and overlapping subproblems, and both are needed. Without optimal substructure an optimal answer cannot be assembled from optimal sub-answers, so the recurrence is invalid. Without overlap there is nothing to reuse, and caching adds bookkeeping for no gain — merge sort has optimal substructure but its two halves share no subproblems, which is why it is divide and conquer rather than DP. Fibonacci has both, which is why memoisation takes fib(30) from 2,692,537 calls to 59.

Memoisation or tabulation?

Memoisation when the recursion is the natural way to express the problem and you only need part of the state space — it computes exactly the subproblems you reach. Tabulation when you need the space optimisation, when recursion depth would overflow the stack, or when locality matters, since filling an array in order is far kinder to the cache than chasing a hash map. Tabulation also forces you to work out the dependency order explicitly, which is sometimes the hardest part and sometimes exactly the clarity you needed.

You reduce an edit-distance table to two rows and save 500× memory. What did you lose?

The ability to reconstruct the answer. You still get the optimal distance — 3 for kitten to sitting — but recovering the actual sequence of edits requires walking backwards through the full table, which no longer exists. The options are keeping the whole table, storing a parent pointer per cell, or Hirschberg's algorithm, which recovers the alignment in linear space at twice the running time by divide and conquer. Decide whether you need the value or the solution before optimising the space.

Knapsack's DP is Θ(n·W). Why is that not a polynomial-time algorithm?

Because W is a numeric value, not the size of the input. A capacity is written in about log W bits, so a 64-bit capacity has an input size of 64 and a table of 2⁶⁴ columns — exponential in the input length. Algorithms polynomial in the numeric value but exponential in the encoding length are called pseudo-polynomial, and knapsack remains NP-hard despite having one. The distinction is invisible until the numbers get large, which is exactly when it bites.

Ten things to carry forward

  1. Greedy, backtracking and DP differ in how much of the search space they look at, and in what they give up for it.
  2. Greedy needs optimal substructure and the greedy choice property, and only the second one usually fails.
  3. Prove greedy with an exchange argument or assume it is wrong. Testing cannot establish it.
  4. Greedy fails silently. Coins 1, 3, 4 give a wrong answer for 24 of the first 100 amounts, and every one looks fine.
  5. Fractional knapsack is greedy, 0/1 is not — the ability to split is the whole difference.
  6. Backtracking's saving comes from pruning near the root, which is why it compounds: 15,720 nodes against 16.8 million.
  7. DP needs overlapping subproblems too, or caching is bookkeeping for nothing.
  8. Memoisation is one line on a working recursion, and it turned 2,692,537 calls into 59.
  9. Keeping two rows instead of the whole table saves 500× memory and destroys your ability to reconstruct the answer.
  10. Θ(n·W) is pseudo-polynomial, not polynomial, because W is a value and its input size is log W.
