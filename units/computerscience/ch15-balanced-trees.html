What "balanced" has to mean

Chapter 14 ended with a structure that is correct and useless on the most common input. The fix is to add an invariant that bounds the height, and machinery that restores it after every modification.

Perfect balance — every leaf at the same depth — is too strong. It can only be maintained by rebuilding, since inserting a single key into a perfect tree of 2k−1 nodes makes perfection impossible until 2k+1−1. Every practical structure therefore picks a looser condition that is cheap to restore and still forces O(log n) height.

The trade every row makes

A stricter invariant means a shorter tree and faster lookups, and it means more work to restore after every insert and delete. AVL is stricter than red-black and therefore searches faster and modifies slower — which is exactly why read-heavy structures (in-memory indexes) tend to be AVL-like and write-heavy ones (language standard libraries, kernel schedulers) tend to be red-black.

Rotation, the only primitive

Every comparison-based balanced tree is built on one operation. A rotation changes the shape of a three-node neighbourhood while leaving the in-order sequence untouched.

right rotation about y — read the in-order sequence on both sides
        y                             x
       / \                           / \
      x   C     ── rotate right ──>  A   y
     / \                                / \
    A   B                              B   C

  in-order: A x B y C          in-order: A x B y C     identical

  rotateRight(y):
    x = y.left
    y.left  = x.right    // B moves from x's right to y's left
    x.right = y
    return x              // x is the new subtree root

Three pointer assignments, constant time, and the BST property survives because B was already between x and y in value. Left rotation is the mirror image. That is the entire toolkit — AVL and red-black trees differ only in when they rotate and what bookkeeping they use to decide.

The four cases

After an insert makes a node unbalanced, the fix depends on which grandchild direction the new key went. Two cases need one rotation; two need two.

Naming is by the path from the unbalanced node to the new key
CaseShapeFix
Left-LeftLeft child's left subtree is too tallOne right rotation
Right-RightRight child's right subtree is too tallOne left rotation
Left-RightLeft child's right subtree is too tallLeft-rotate the child, then right-rotate the node
Right-LeftRight child's left subtree is too tallRight-rotate the child, then left-rotate the node

The double cases exist because a single rotation on a zig-zag shape just produces the mirror-image zig-zag. The first rotation converts the zig-zag into a straight line, and then the single-rotation case applies.

Sorted input is the AVL's best case, not its worst

A thousand sorted keys give a plain BST height 999 and an AVL height 9 — the theoretical minimum. The same thousand keys shuffled give an AVL height of 11. Sorted insertion produces a shorter tree, because every rotation fires in the same direction and builds an almost perfect shape, and it costs 990 rotations — 0.99 per insert, all of them single. Random insertion needs only 473 rotations and ends up two levels taller. The structure that catastrophically fails on ordered input becomes the one that handles it best.

AVL trees

Adelson-Velsky and Landis, 1962 — the first self-balancing tree. Each node stores its height, and the balance factor (left height minus right height) must stay in {−1, 0, +1}. After an insert or delete, walk back up the path and rotate wherever it leaves that range.

Insertion

At most one rotation (single or double) restores the whole tree, because the rotation shortens the subtree back to its pre-insert height and nothing above notices.

Deletion

Up to log n rotations, because a rotation can shorten the subtree, which may unbalance the parent, and so on all the way to the root. This asymmetry is why AVL is called expensive to modify.

The height bound is 1.44 log₂(n+2) − 0.33, and the constant comes from the worst-case AVL shape, which turns out to be built from Fibonacci numbers: the smallest AVL tree of height h has F(h+3) − 1 nodes. So an AVL tree is at most 44% taller than perfect, and in practice much closer — the measurements above hit the exact minimum on sorted input and one or two levels above it on random input.

Red-black trees

The structure your standard library almost certainly uses. Each node carries one bit of colour, and five rules hold:

  1. Every node is red or black.
  2. The root is black.
  3. Every leaf (the null sentinels) is black.
  4. A red node's children are both black — no two reds in a row.
  5. Every path from a node to its descendant leaves contains the same number of black nodes.

Rules 4 and 5 do all the work. Rule 5 says every path has the same black height; rule 4 says reds cannot be consecutive, so no path can be more than twice as long as another. That gives height ≤ 2 log₂(n+1) — looser than AVL's 1.44, and correspondingly cheaper to maintain: insertion needs at most 2 rotations and deletion at most 3, against AVL's O(log n) for deletion.

Colour is just a 2-3-4 tree in disguise

A red-black tree is exactly a 2-3-4 tree encoded in binary. A black node with red children is a 4-node; a black node with one red child is a 3-node; a black node alone is a 2-node. That is why the black height is uniform — it is the 2-3-4 tree's actual height — and why the recolouring cases look arbitrary until you see them as node splits. If red-black rules feel unmotivated, learn 2-3 trees first and the encoding makes them obvious.

B-trees: stop thinking in twos

Every structure so far assumes a comparison is the unit of cost. On disk that is wrong: the unit is the page, typically 4 or 16 KiB, and reading one byte costs the same as reading all of it. A binary tree wastes almost the entire page on every visit.

A B-tree of order m stores up to m−1 keys and m child pointers in one node, sized so a node is a page. All leaves sit at the same depth, and every node except the root is at least half full.

With a 4 KiB page and 8-byte keys and pointers, one node holds 256 children and 255 keys. A billion keys then fit in a tree of height 3 to 4 — 4 to 5 page reads per lookup — against a balanced binary tree's height of 29, meaning 30 reads. That is a sixfold reduction in the operation that actually costs anything.

Move to 16 KiB pages and the fan-out becomes 1,024, putting a billion keys in 3 levels. In practice the top one or two levels stay cached in memory permanently, so a real B-tree index lookup is usually one or two actual disk reads regardless of table size. This is why every relational database index, every filesystem directory structure (NTFS, ext4, HFS+, XFS) and every key-value store's on-disk format is a B-tree or a close relative.

The general principle

Match the node size to the transfer unit of the level below. On disk that is a page; in memory it is a cache line, which is why cache-conscious in-memory B-trees with fan-outs of 8 or 16 beat red-black trees despite identical asymptotics. Chapter 5's argument does not stop applying just because the structure is a tree.

Skip lists: balance by coin flip

A completely different answer. Take a sorted linked list and give some nodes extra forward pointers that skip ahead. A node's height is chosen by flipping a coin: level 1 always, level 2 with probability ½, level 3 with ¼, and so on.

a skip list, and the search path through it
  L3  H ─────────────────────────────> 17 ──────────> NIL
  L2  H ───────────> 9 ──────────────> 17 ──────────> NIL
  L1  H ──> 3 ─────> 9 ────> 12 ─────> 17 ──> 21 ──> NIL
  L0  H ──> 3 ─> 6 ─> 9 ─> 12 ─> 15 ─> 17 ─> 21 ─> 25 ─> NIL

  search(15): start top-left, go right while the next key is smaller,
              otherwise drop a level.
              L3: 17 > 15, drop.  L2: 9 < 15, move.  17 > 15, drop.
              L1: 12 < 15, move.  17 > 15, drop.  L0: 15. Found.

Expected height is log₂ n and expected search is O(log n), with an expected 1/(1−p) = 2 pointers per node. There is no invariant to maintain and no rotation: insertion finds the position, flips coins for a level, and splices in.

Why people like them

Far simpler to implement correctly than a red-black tree — no cases to get wrong. Much easier to make concurrent, because an insert touches only a few pointers and there is no rebalancing that has to lock a path. Redis sorted sets and LevelDB's memtable both use them.

Why they are not the default

The bound is expected, not guaranteed — a bad run of coin flips can produce a tall list, though the probability falls exponentially. They use more memory than a tree, and their pointer-chasing has worse locality than a B-tree.

Treaps take the same idea back into tree form: give each node a random priority, maintain the BST property on keys and the heap property on priorities, and the shape becomes that of a random BST regardless of insertion order. The randomness comes from your generator rather than from the input, which is exactly the guarantee chapter 14 said sorted input destroys.

Do not write a red-black tree

Deletion has around a dozen cases, several of which are hit only by inputs a test suite will not think of, and a subtly wrong one produces a tree that is still a valid BST and quietly degrades. Sedgewick invented left-leaning red-black trees specifically to reduce the case count, and even that is fiddly. Use the library. If you must implement a balanced structure by hand, pick a skip list or a treap, where correctness follows from a much smaller argument.

Check yourself

Why does a rotation preserve the BST property?

Because it only changes which of two nodes is the parent, and re-attaches the one subtree that sits between them in value. In a right rotation about y with left child x, subtree B was x's right child, so every key in it is greater than x; it was also inside y's left subtree, so every key is less than y. Moving it to be y's left child keeps both facts true. Reading the in-order sequence before and after gives A x B y C either way — which is the check to make when you write one.

Why do Left-Right and Right-Left need two rotations?

Because a single rotation on a zig-zag just mirrors it. If the left child's right subtree is the tall one, rotating right about the unbalanced node moves that subtree across without shortening it — you get the same imbalance leaning the other way. Rotating the child left first converts the zig-zag into a straight Left-Left line, and then the single rotation works. Try 1 3 2 against 1 2 3 in demo 1: the same three keys and the same final tree, reached by one rotation or by two.

A thousand sorted keys give an AVL of height 9 and a shuffled thousand give height 11. Explain.

Sorted insertion makes every rotation fire in the same direction, and the repeated left rotations assemble an almost perfectly balanced tree — height 9 is the theoretical minimum ⌈log₂(1001)⌉−1. It costs 990 rotations, 0.99 per insert, all single. Random insertion produces a lumpier shape that the invariant tolerates without correcting, since a balance factor of ±1 is legal at every node, so it ends two levels taller with only 473 rotations. The input that destroys a plain BST is the AVL's best case, which is worth remembering because the intuition runs the other way.

AVL guarantees height 1.44 log n and red-black only 2 log n. Why is red-black the more common choice?

Because the guarantee is not the only cost. AVL deletion can require O(log n) rotations, since shortening a subtree may unbalance its parent all the way to the root; red-black deletion needs at most three, and insertion at most two. For a structure that is modified as often as it is read — a standard-library map, a scheduler's run queue — bounded rebalancing work matters more than 40% fewer levels. AVL wins when the tree is built once and read many times.

Why do databases use B-trees with fan-out in the hundreds instead of balanced binary trees?

Because the cost unit on disk is the page, not the comparison. Reading one byte of a 4 KiB page costs the same as reading all of it, so a binary node wastes 99% of every read. Packing 255 keys into a page turns a billion-key index from 30 page reads into 4 or 5. In-memory the same argument applies one level down with cache lines, which is why cache-conscious B-trees with fan-out 8 or 16 beat red-black trees despite identical asymptotics.

A skip list has no balance invariant. Why is it still O(log n)?

Because the randomness is in the structure rather than the input. Each node's level comes from independent coin flips, so about half the nodes reach level 2, a quarter level 3, and so on — the expected height is log₂ n and the expected number of steps at each level is constant. Crucially this does not depend on the order the keys arrived in, so sorted input is no worse than random. The bound is expected rather than guaranteed, but the probability of a bad structure falls exponentially, and the same argument makes treaps work.

You need an ordered map of ten thousand integers, built once at startup and then only read. What would you use?

A sorted array with binary search. All of these structures give Θ(log n) lookup, but the array is contiguous, so binary search's probes are in one block and the later ones are usually already in cache, while every level of a pointer tree is an independent serialised cache miss. It also uses a fraction of the memory — no pointers, no colour bits, no height fields — and supports range scans as a direct slice. The moment you need to insert, that answer flips, because an array insert is Θ(n).

Ten things to carry forward

  1. Perfect balance is too expensive to maintain, so every practical structure picks a looser invariant that still forces logarithmic height.
  2. Rotation is the only primitive. Three pointer assignments, constant time, and the in-order sequence is unchanged.
  3. Four cases, two of them double. A zig-zag needs one rotation to straighten it before the ordinary case applies.
  4. AVL keeps balance factors in {−1, 0, +1}, giving height ≤ 1.44 log₂ n — at most 44% above perfect.
  5. Sorted input is an AVL's best case. A thousand sorted keys give height 9 for 990 rotations; shuffled gives 11 for 473.
  6. Red-black relaxes the bound to 2 log₂ n and buys bounded rebalancing: 2 rotations per insert, 3 per delete.
  7. A red-black tree is a 2-3-4 tree in binary. The recolouring cases are node splits, and they stop looking arbitrary once you see that.
  8. B-trees match the node to the transfer unit. Fan-out 256 turns 30 page reads into 5 for a billion keys.
  9. Skip lists get the bound from a coin, not an invariant, which makes them simple to write and easy to make concurrent.
  10. Use the library. Red-black deletion has a dozen cases and a subtly wrong one still produces a valid BST that quietly degrades.
