Searching and string matching

Binary search, and why it is hard

Halve the range, compare against the midpoint, discard the half that cannot contain the answer. Over 1,000 sorted values the worst case is 10 comparisons — ⌈log₂(n+1)⌉ — against linear search's 1,000, and the average for a successful search is 8.99. Doubling the array adds exactly one comparison.

the version that is actually correct
search(a, target):
  lo = 0, hi = a.length - 1
  while (lo <= hi) {                        // <= not <, or you miss the last element
      mid = lo + ((hi - lo) >> 1)          // not (lo + hi) / 2 — see below
      if (a[mid] === target) return mid
      if (a[mid] < target) lo = mid + 1     // + 1 and - 1, or it never terminates
      else                hi = mid - 1
  }
  return -1

Four decisions in ten lines, and each has a wrong version that works on most inputs.

The variants you actually want

Plain "find me an index holding this value" is the least useful of the three, because with duplicates it returns an arbitrary one. On the array 1 3 3 3 5 7 7 9 searching for 3 returns index 3 — the last one, by accident of where the midpoints fell.

lower_bound
The first index whose value is ≥ target. Returns 1 for the array above, the first 3. If the target is absent, it returns the position where it would be inserted.
upper_bound
The first index whose value is > target. Returns 4 above. Together with lower_bound it gives the range of equal elements, and their difference is the count — 3, computed in 2 log n comparisons without touching the elements.

Both are total functions: they always return a valid insertion point in [0, n], with no −1 sentinel to handle. That is why C++'s lower_bound, Python's bisect_left, Rust's partition_point and Java's negative-return convention all exist, and why they should be your default over a plain find.

Binary search is not about sorted arrays

It works on any monotonic predicate: some property that is false up to a point and true after it. Find the smallest x where the predicate flips, and the array is incidental. That reframing solves a huge class of problems — the smallest capacity that lets you ship in d days, the largest rate limit that keeps latency under a threshold, the square root of n to a given precision, the first failing commit in a bisect. Whenever a question has the shape "smallest value that works", binary search applies whether or not there is an array in sight.

Finding a pattern in text

Given text of length n and a pattern of length m, find every occurrence. The obvious algorithm tries every alignment and compares until it mismatches.

naive matching, and its problem
for i = 0 to n - m:
    j = 0
    while (j < m && text[i+j] === pat[j]) j++
    if (j === m) report a match at i

// on ordinary text this is nearly linear: most alignments die on
// the first character. the worst case is n-m+1 alignments x m
// comparisons each, and it is easy to construct.

The insight every better algorithm shares: a mismatch tells you something. The naive version throws that information away and restarts one position later. The three classic improvements each keep a different part of it.

On ordinary English prose of 3,380 characters looking for lazy dog, the four algorithms cost 3,673 (naive), 3,467 (KMP), 761 (Horspool) and 160 character comparisons (Rabin-Karp). That last figure is misleading on its own, and section six explains why.

KMP: never re-examine a character

Knuth-Morris-Pratt precomputes, for every prefix of the pattern, the length of the longest proper prefix that is also a suffix of it. When a mismatch happens after matching k characters, that table says how much of the match is still usable, so the pattern slides forward without the text pointer ever going backwards.

the failure function, and what it means
pattern:  A  B  A  B  C
index:    0  1  2  3  4
f[i]:     0  0  1  2  0

f[3] = 2 means: the prefix "ABAB" has a proper prefix "AB" that is
also its suffix. So after matching ABAB and failing on C, we already
know the next two characters of the text are "AB" — slide the pattern
two places and resume at index 2, without re-reading anything.

other tables:  AAAA   -> 0 1 2 3      (every prefix is also a suffix)
               ABCDE  -> 0 0 0 0 0    (nothing repeats; slide the full width)
               ABABAB -> 0 0 1 2 3 4

Because the text index never moves backwards, each character is examined at most twice — once on a successful advance and once per failure step — giving a worst case of at most 2n comparisons regardless of the pattern. Measured on the adversarial input below, KMP does 4,019 comparisons for a 2,000-character text, or 2.01 per character.

The input that separates them

Text of 2,000 as, pattern aaaaaaaaaaaaaaaaaaaab — twenty as and a b. Every alignment matches 20 characters and fails on the last. Naive matching pays for that at every position: 41,580 comparisons, exactly (n−m+1)·m. KMP does 4,019, ten times better, because it never re-reads the as it has already seen.

Boyer-Moore: skip characters entirely

A different idea, and often a better one. Compare the pattern right to left. When the text character aligned with the pattern's last position does not occur in the pattern at all, no alignment overlapping it can match, so the pattern can jump its whole width — examining fewer characters than there are in the text.

the bad-character shift for EXAMPLE
pattern:  E  X  A  M  P  L  E     (m = 7)
shift:    E:6  X:5  A:4  M:3  P:2  L:1   anything else: 7

the shift for a character is its distance from the END of the pattern,
using its LAST occurrence in pat[0 .. m-2]. A character not in the
pattern shifts the full width.

text:  ... T H I S   I S   A N   E X A M P L E ...
                              ^ compare here first (position m-1)
       if it is a space, and space is not in the pattern, jump 7 places.

This is why Boyer-Moore is sublinear in practice: on natural language with a pattern of eight characters, most alignments are rejected by a single comparison and skip several positions. On the English text above, Horspool — the simplified single-table variant almost everyone actually implements — does 761 comparisons against naive's 3,673, examining under a quarter of the text.

Every one of them has an adversarial input

Change the pattern to aaaaaaaaaaaaaaaaaaaa — twenty as, with no b — against the same 2,000 as, and the table turns over completely. Now every alignment matches, so Horspool compares all 20 characters and shifts by 1: 39,620 comparisons, quadratic. Naive is equally bad at 39,620, and Rabin-Karp is too, at 39,620, because every hash matches and must be verified. Only KMP stays linear, at 2,019. Swap the pattern back to the one ending in b and Horspool becomes the best of the four at 1,980. There is no algorithm here that wins on every input, and the demo lets you produce each reversal.

Rabin-Karp and the rolling hash

Hash the pattern once. Hash the first window of the text. Compare hashes, and slide. The trick is that the next window's hash is computable from the current one in constant time: remove the leading character's contribution, shift, add the trailing character.

rolling a polynomial hash forward one character
hash(s) = s[0]·B^(m-1) + s[1]·B^(m-2) + … + s[m-1]   (mod M)

roll(h, out, in) = ((h - out·B^(m-1)) · B + in) mod M

one multiply, one subtract, one add per position — independent of m.
a hash match is only a HINT: verify the characters before reporting,
because two different windows can share a hash.

The comparison counter flatters Rabin-Karp badly, and it is worth being explicit about that. On the English text it does 160 character comparisons — a fifth of Horspool's — but it also performs over 3,400 hash updates that the counter does not see, each a multiply and a modulo. Comparing algorithms by one metric when they do different kinds of work is exactly the mistake chapter 10 warned about.

Where Rabin-Karp genuinely wins is the case none of the others handle: multiple patterns at once. Hash all k patterns into a set, roll one hash across the text, and check set membership at every position — Θ(n + km) rather than k separate scans. That is how plagiarism detection, the rsync algorithm and content-defined chunking in deduplicating backup systems work.

The modulus is the whole algorithm

Choose a small or non-prime modulus and collisions become common, so every position needs verification and the algorithm degrades to naive matching. Choose a fixed public one and an attacker can construct colliding inputs on purpose — the same hash-flooding attack as chapter 13, in a different costume. Use a large prime and a randomly chosen base per run.

In practice: use your language's indexOf or find, which is already a tuned hybrid — usually a Boyer-Moore-Horspool variant with a naive fallback for short patterns, and vectorised first-character scanning in the fastest implementations. Reach for KMP when you need a hard linear guarantee on untrusted input, for Rabin-Karp when you are matching many patterns or streaming, and for the suffix arrays of chapter 17 when the text is fixed and you will query it repeatedly.

Beyond exact matching there is a whole further family: Aho-Corasick builds a trie of many patterns with KMP-style failure links and finds all of them in one pass, which is how virus scanners and intrusion detection work; regular expressions compile to automata; and edit distance handles approximate matches through the dynamic programming of chapter 22.

Check yourself

Why is mid = (lo + hi) / 2 wrong, and why did it survive for decades?

Because lo + hi can overflow the integer type before the division happens, producing a negative midpoint and an out-of-bounds access. It survived because it only triggers on arrays larger than half the type's maximum — over a billion elements for a 32-bit signed int — which nobody tested. The bug was in Java's Arrays.binarySearch for nine years and in Bentley's own published version. lo + ((hi - lo) >> 1) computes the same value without the intermediate sum.

Binary search for 3 in 1 3 3 3 5 7 7 9 returns index 3. Is that a bug?

Not a bug, but almost never what you want. Plain binary search promises only that the returned index holds the target, and which one depends on where the midpoints happened to fall. Use lower_bound for the first occurrence (index 1) and upper_bound for one past the last (index 4). Their difference is the count of equal elements — 3 here — obtained in 2 log n comparisons, and both return a valid insertion point when the target is absent, so there is no −1 sentinel to handle.

What is the actual precondition for binary search?

Not "the array is sorted" but "there is a monotonic predicate" — some property that is false for a prefix and true for the remaining suffix. A sorted array with the predicate a[i] >= target is the familiar instance; it is not the only one. The same search finds the smallest ship capacity that delivers in d days, the largest concurrency that keeps latency under a threshold, an integer square root, or the first commit that broke a test. Recognising the shape "smallest value for which this works" is worth more than memorising the loop.

What does KMP's failure function record, and how does it save work?

For each prefix of the pattern, the length of the longest proper prefix that is also a suffix of it. For ABABC the table is 0 0 1 2 0: f[3] = 2 because ABAB ends with AB, which is also how it starts. So after matching ABAB and failing on C, you already know the next two text characters are AB — slide the pattern two places and resume at pattern index 2 without re-reading any text. The text pointer never moves backwards, which bounds the whole search at 2n comparisons.

How can a search examine fewer characters than the text contains?

By comparing right to left and skipping. Boyer-Moore aligns the pattern's last character first; if the text character there does not appear in the pattern at all, no alignment covering it can match, so the pattern jumps its entire width and those characters are never read. On English prose with an eight-character pattern, Horspool does 761 comparisons over 3,380 characters — under a quarter of the text. The skip is larger for longer patterns and bigger alphabets, which is the reverse of the usual intuition that longer patterns are harder.

Why does Rabin-Karp's low comparison count overstate how fast it is?

Because the counter measures character comparisons and Rabin-Karp mostly does something else. On the English text it makes 160 character comparisons against Horspool's 761 — and over 3,400 hash updates, each a multiply and a modulo, which the counter never sees. Judging two algorithms by one metric when they do different kinds of work is the mistake chapter 10 warned about. Rabin-Karp's real advantage is elsewhere: it can match many patterns in one pass by checking a set of hashes, which none of the others do.

Which of these algorithms is best?

None of them, and the demo will show you the reversal. On a text of 2,000 as: with the pattern a×20 + b, Horspool is best at 1,980 comparisons and naive is worst at 41,580. Change the pattern to a×20 and Horspool collapses to 39,620 — as do naive and Rabin-Karp, since every alignment now matches — while KMP stays at 2,019. KMP is the only one with a linear worst case, and it is rarely the fastest in the common case. That is why production implementations are hybrids that detect what they are given.

Ten things to carry forward

  1. Binary search is ten lines with four ways to get it wrong, and one of them shipped in the JDK for nine years.
  2. Compute the midpoint as lo + (hi − lo)/2 so the intermediate sum cannot overflow.
  3. lower_bound and upper_bound beat a plain find, because they are total, they handle duplicates, and their difference is the count.
  4. The precondition is a monotonic predicate, not a sorted array, which is why "smallest value that works" problems are binary searches.
  5. Naive matching throws away what a mismatch told you, and costs (n−m+1)·m in the worst case — 41,580 comparisons on a 2,000-character text.
  6. KMP's failure function is the longest prefix that is also a suffix, and it keeps the text pointer from ever moving backwards.
  7. KMP is the only one of the four with a linear worst case, at most 2n comparisons on any input.
  8. Boyer-Moore reads right to left and skips, examining under a quarter of ordinary text.
  9. Every algorithm here has an input that defeats it. Change the pattern by one character and the best becomes the worst.
  10. Rabin-Karp's cheap comparison count hides its hashing, and its real advantage is matching many patterns in one pass.
