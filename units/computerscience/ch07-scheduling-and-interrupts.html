Chapter 7 · The operating system

Scheduling, interrupts and context switches

There are more runnable threads than cores, so something has to choose. Every choice trades one victim's latency for another's throughput, and there is no algorithm that wins on all the metrics at once — a fact that stops being frustrating once you can see it happen.

The problem, stated honestly

A scheduler picks which runnable thread gets a core next, and for how long. It runs constantly, has to decide in microseconds, and knows almost nothing about what it is scheduling. In particular it does not know how long anything will take, which rules out most of the algorithms that would be optimal if it did.

It gets control at only a few moments, and the list is short enough to memorise:

  • A thread blocks on I/O, a lock, or a sleep.
  • A thread exits.
  • A timer interrupt fires and the current thread's quantum has expired.
  • A thread becomes runnable — I/O completed, a lock was released — and may deserve the CPU more than whoever holds it.

A scheduler that only acts on the first two is non-preemptive: once a thread has the CPU it keeps it until it gives it up voluntarily. That was how early Macintosh and Windows worked, and it is why one misbehaving program could freeze the whole machine. A scheduler that acts on all four is preemptive, and needs a timer interrupt to take the CPU back by force.

What we are optimising

Turnaround time
Completion minus arrival. The total elapsed time a job spent in the system. What a batch job cares about.
Waiting time
Turnaround minus the time actually spent running. Pure overhead from the job's point of view.
Response time
Arrival to first time on the CPU. What an interactive user feels — the delay between a keypress and something happening.
Throughput
Jobs completed per unit time. Hurt by every context switch.
Fairness
Nobody starves and, ideally, everybody gets a share proportional to their weight. Hard to define, easy to violate.
These conflict, permanently

Minimising average turnaround means running short jobs first, which starves long ones. Minimising response time means switching often, which costs throughput. Guaranteeing fairness means sometimes running a job that is not the best choice for any other metric. Every real scheduler is a heuristic compromise, and the compromise is retuned every few kernel releases.

Then look at what that costs. SRTF gives P1 a turnaround of 16 against FCFS's 7: the algorithm with the best average has the worst individual outcome, because P1 is the long job and gets pushed behind everything. Switch to the starvation workload and it becomes stark — by time 17 the long job has completed 1 unit of 20 under SRTF and 6 under round robin, six times the progress for identical total work.

Turnaround cannot see starvation

On the starvation workload both SRTF and round robin give the long job a turnaround of 36, and that is not a coincidence. Whichever job finishes last always has turnaround = makespan − arrival, and the makespan is the same for any work-conserving scheduler, because the total work is the same. Averages and turnaround simply cannot express "this job made no progress for sixteen units". Progress over time can, which is why real schedulers track accumulated runtime rather than completion.

Multi-level feedback queues

The practical answer to "SJF is optimal but you cannot know burst lengths" is to guess from behaviour. An MLFQ keeps several queues at different priorities and moves jobs between them:

  1. New jobs enter at the highest priority.
  2. A job that uses its entire quantum is assumed to be CPU-bound and is demoted one level. Lower levels get longer quanta.
  3. A job that blocks before its quantum expires is assumed to be interactive and stays where it is.
  4. Periodically, everything is promoted back to the top so nothing starves and so jobs that change behaviour are re-evaluated.

The result approximates SJF without any advance knowledge: interactive jobs, which are short by nature, float to the top and get fast response, while long computations sink and run efficiently with big quanta. Rule 4 exists because without it a batch job could starve forever, and because programs change phase — a compiler is I/O-bound reading source and CPU-bound optimising.

What Linux actually does

From 2007 to 2023 the Linux default was the Completely Fair Scheduler. Its idea is elegant: instead of queues and quanta, give each task a virtual runtime and always run the task with the smallest one.

vruntime += actual_runtime × (weight_of_nice_0 / weight_of_this_task)

// a nice 0 task advances vruntime at real time
// a nice -5 task advances it more slowly, so it is picked more often
// a nice +5 task advances it faster, so it is picked less often

// runnable tasks live in a red-black tree keyed by vruntime;
// "pick the next task" is just "take the leftmost node"

Each nice level changes the weight by roughly 1.25×, so the ten steps from nice 0 to nice 19 change a task's CPU share by about a factor of ten. There is no fixed quantum: CFS computes a target latency (a few milliseconds) and divides it among the runnable tasks in proportion to weight, with a floor so that a hundred runnable tasks do not each get a microsecond. A newly woken task gets its vruntime clamped so it can jump the queue slightly, which is how interactive tasks get their responsiveness without any explicit notion of interactivity.

In Linux 6.6, CFS was replaced by EEVDF — Earliest Eligible Virtual Deadline First — which keeps virtual runtime but adds an explicit deadline per task, letting the scheduler give short-running tasks lower latency without the pile of heuristics CFS had accumulated. The core idea, that fairness is bookkeeping over accumulated virtual time rather than a queue, is unchanged.

How the kernel gets control

A running user thread owns the CPU. The kernel is not a process sitting alongside it waiting for a turn; it is code that runs when something forces a transition. There are exactly three kinds of forcing event, and they differ in where they come from and whether they were expected.

The three ways control leaves user code
SourceTimingExamples
InterruptExternal hardwareAsynchronous — unrelated to the current instructionTimer tick, key press, network packet, disk completion
Trap (or exception)The current instructionSynchronous, deliberateSystem call, breakpoint, debugger
FaultThe current instructionSynchronous, accidentalPage fault, divide by zero, invalid opcode, segmentation fault

All three take the same route. The CPU switches to kernel mode, saves enough state to resume, looks up a handler in the interrupt descriptor table, and jumps to it. The handler runs, and then execution returns to the interrupted instruction — or to the next one, depending on the cause. A page fault re-runs the faulting instruction after the page is mapped; a system call resumes after it; a segmentation fault usually does not resume at all.

Why system calls cost more than function calls

A system call is not a jump into a library. It is a privilege transition: syscall on x86-64 switches to ring 0, swaps to the kernel stack, and on return restores everything. The direct cost is a few hundred cycles; since Spectre and Meltdown, the mitigations — flushing branch predictors, switching page tables under KPTI — have added several hundred more.

That cost is why so much systems engineering is about making fewer, bigger calls. Buffered I/O batches many small writes into one write. epoll and io_uring report many ready sockets per call instead of one. sendfile and splice move data between descriptors without copying it through userspace at all. And gettimeofday does not enter the kernel at all on Linux: the vDSO maps a page of kernel-maintained data into every process so the time can be read with an ordinary load.

Top halves and bottom halves

An interrupt handler runs with interrupts disabled and blocks everything else on that core, so it must be short. The convention is to split it: the top half does the minimum — acknowledge the device, copy the data out, schedule the rest — and a bottom half (a softirq, tasklet or workqueue in Linux) does the real processing later with interrupts enabled. A network card raising 100,000 interrupts per second would otherwise leave no time for anything else, which is also why high-rate NICs switch to polling under load. That mechanism is called NAPI, and it is a scheduler decision in disguise.

What a context switch costs

Switching threads means saving registers into one task structure and loading them from another. That part is genuinely cheap, a few hundred cycles. The expensive parts are everything else:

  • Entering and leaving the kernel, with the mitigation overhead above.
  • Switching page tables if the new thread belongs to a different process, which historically flushed the whole TLB. Tagged TLBs (PCID on x86, ASIDs on ARM) avoid the flush but not the pressure.
  • Cold caches. The incoming thread finds L1 and L2 full of the outgoing thread's data and takes hundreds of misses before it is back at speed. This usually dominates everything else and it does not show up as scheduler time in any profile.
  • Scheduler bookkeeping: updating vruntime, re-inserting into the red-black tree, load balancing across cores.

The textbook approximation for efficiency is q / (q + c), and the simulator confirms it to within half a percent — it is always a slight under-estimate, because there is no switch before the very first slice. Set the switch cost to 0 and utilisation is 100% at every quantum, which is the check that the model is measuring what it claims to.

The rule of thumb

Pick a quantum an order of magnitude or two larger than the switch cost, then make sure n × q stays under the response time a human notices. With a switch around 1–5 µs and a perception threshold around 100 ms, that lands in the range of 1–10 ms, which is exactly where real quanta sit. Linux does not use a fixed quantum at all: it divides a target latency of a few milliseconds among the runnable tasks, with a floor so the quantum never shrinks below something the switch cost would dominate.

Practical consequences

Priority inversion
A low-priority thread holds a lock a high-priority thread needs, and a medium-priority thread — which needs no lock — preempts the low one and prevents it from ever releasing. The high-priority thread is blocked by a thread it outranks. This is what repeatedly reset Mars Pathfinder in 1997. The standard fix is priority inheritance: a thread holding a lock temporarily inherits the priority of the highest-priority waiter.
The convoy effect
One long or I/O-heavy job at the front of a non-preemptive queue makes everything behind it wait, including jobs that would have finished instantly. It is the reason FCFS is unusable for interactive work, and it reappears at every layer: a slow query holding a database connection, a large request occupying a worker, a single slow shard delaying a scatter-gather.
Thread pool sizing
For CPU-bound work, roughly one thread per core: more only adds switches and cache damage. For I/O-bound work you want enough threads to keep the CPU busy while others block, which is cores × (1 + wait/compute). A task that waits 90% of the time justifies about ten threads per core. Guessing here is why so many services get slower when their thread pool is enlarged.
CPU affinity and NUMA
Pinning a thread to a core keeps its cache warm and avoids migration, which can be worth a great deal for latency-sensitive work. On a multi-socket machine, memory is attached to a particular socket and accessing another socket's memory is measurably slower, so the scheduler tries to keep threads near their memory. taskset and numactl let you take that decision yourself.
Real-time priority is a loaded gun

A SCHED_FIFO thread runs until it blocks or yields. If it busy-loops, it will not be preempted by anything at a lower priority — including, on a single-core machine, the shell you would use to kill it. Linux defaults to reserving 5% of each period for non-real-time tasks precisely so this is recoverable, and that reservation is configurable and sometimes disabled by people who then discover why it existed.

Check yourself

SJF gives the lowest average waiting time. Why does no real operating system use it?

Two reasons. It needs to know each job's total burst before running it, which is impossible for interactive work — the scheduler cannot know how long you will hold down a key. And it starves long jobs: a steady arrival of short jobs means a long one never becomes the shortest and never runs. MLFQ and CFS both approximate the benefit by inferring behaviour instead: a job that repeatedly blocks before using its quantum is treated as short, and periodic promotion or virtual-runtime accounting stops anything starving.

Round robin with an enormous quantum behaves identically to which algorithm, and why?

FCFS. If the quantum exceeds every burst, no job is ever preempted, so each runs to completion in arrival order and the queue never rotates. The demo confirms this: set the quantum above the longest burst and the metrics and switch count match FCFS exactly. At the other extreme, a quantum of one time unit approaches processor sharing, where every job progresses at 1/n speed — good response, poor turnaround, and, once switching is not free, terrible throughput.

SRTF has the best average turnaround on the demo workload and the worst individual one. Explain.

SRTF always runs whatever will finish soonest, which is exactly what minimises the average — many jobs finish early and few finish late. But the long job is by definition never the one that finishes soonest, so it is preempted every time anything shorter arrives and is pushed to the end. On the default workload P1 gets a turnaround of 16 under SRTF against 7 under FCFS, while the average falls from 8.75 to 7. Averages reward exactly this kind of redistribution, which is why fairness has to be measured separately.

On the starvation workload both SRTF and round robin give the long job a turnaround of 36. Does that mean neither starves it?

No, it means turnaround cannot detect starvation. The job that finishes last always has turnaround = makespan − arrival, and every work-conserving scheduler has the same makespan because the total work is identical. What differs is when the work happened: by time 17 the long job has completed 1 unit of 20 under SRTF and 6 under round robin. Progress over time is the metric that sees it, which is precisely why CFS schedules on accumulated virtual runtime rather than on completion.

A context switch costs 5 µs. Is a 10 µs quantum reasonable?

No. Efficiency is roughly q/(q+c) = 10/15 = 67%, so a third of the machine is spent switching, and the real figure is worse because that formula ignores cache damage. You want the quantum one to two orders of magnitude above the switch cost — here, 0.5 to 5 ms — subject to n × q staying below the latency a user notices. Verify the shape in demo 2 by setting the switch cost to 5 and sweeping.

Your service handles requests that spend 90% of their time waiting on a database. How many worker threads per core?

Around ten. The rule is cores × (1 + wait ÷ compute), and 0.9/0.1 = 9, giving a factor of 10. With one thread per core the CPU would idle 90% of the time; with a hundred you would pay for switches and stacks and memory without gaining throughput, since the CPU is already saturated at ten. The better answer for large numbers is usually to stop using a thread per request and use async I/O, which lets one thread hold thousands of in-flight requests without a stack each.

A high-priority thread is blocked and never runs, even though the thread holding its lock is low-priority and ready. What is going on?

Priority inversion. The low-priority lock holder is ready but not running, because medium-priority threads that need no lock keep preempting it. It therefore never reaches the point of releasing, and the high-priority thread waits behind a thread it outranks — effectively running at the low thread's priority. The fix is priority inheritance: while holding a contended lock, a thread temporarily runs at the priority of its highest-priority waiter. Mars Pathfinder rebooted repeatedly in 1997 for exactly this reason, and was fixed in flight by enabling priority inheritance on the offending mutex.

Ten things to carry forward

  1. The scheduler only gets control at four moments: block, exit, timer interrupt, and wake-up. Preemption exists because of the third.
  2. Turnaround, waiting, response, throughput and fairness conflict. No algorithm optimises all of them.
  3. SJF is optimal for average waiting and unusable in practice, because burst lengths are unknowable and long jobs starve.
  4. Round robin buys bounded response, at most (n−1)·q before first run, and pays for it in turnaround and switches.
  5. Averages hide starvation. The best average turnaround can coexist with the worst individual one.
  6. Turnaround cannot see starvation at all for the last-finishing job, because makespan is invariant across work-conserving schedulers. Measure progress over time.
  7. MLFQ infers what SJF assumes, by demoting jobs that use a full quantum and promoting periodically so nothing starves.
  8. Linux schedules on virtual runtime, weighted by nice, picking the leftmost node of a red-black tree — CFS until 6.6, EEVDF since.
  9. Interrupts, traps and faults are the three doors into the kernel, and a system call is a privilege transition, not a function call.
  10. The quantum should be one or two orders of magnitude above the switch cost, and the switch's real price is the cold cache that follows it.
