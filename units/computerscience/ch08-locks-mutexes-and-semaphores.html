Chapter 8 · The operating system

Locks, mutexes and semaphores

Two threads incrementing a shared counter get the right answer in exactly two of the twenty possible schedules. The other eighteen silently lose an update. Concurrency bugs are not rare events you were unlucky to hit; they are the common case, hidden by a scheduler that usually happens to be kind.

Why counter++ is broken

The statement looks atomic because it is short. It is not. It compiles to three separate operations, and a thread can be preempted between any two of them.

one line of C, three machine operations
counter++;

// becomes, roughly:
mov  eax, [counter]     // LOAD   read the current value into a register
add  eax, 1             // INC    add one, in the register
mov  [counter], eax     // STORE  write the register back

The register is private to the thread. If a second thread loads counter before the first has stored, both compute the same new value and both write it. Two increments, one net change. This is a lost update, and it is the simplest possible data race.

With two threads there are 20 ways to interleave six operations, and only 2 produce the right answer — the two fully serial orders where one thread finishes before the other starts. 90% of schedules are wrong. With three threads it is worse: 1,680 schedules, of which 6 are correct, or 0.36%. Tick the mutex and the space collapses to just the serial orders, all of them correct.

Why the bug hides in testing

The schedule space being 90% wrong does not mean 90% of runs are wrong. A real scheduler rarely preempts inside a three-instruction window, so the correct schedules are the ones that almost always happen. The bug shows up under load, on a different core count, after an unrelated change moves the code, or in production at 3am. That asymmetry — cheap to write, nearly impossible to reproduce — is why concurrency is treated with more formality than most programming. Use a tool that explores the space instead of sampling it: ThreadSanitizer, Helgrind, Go's -race, or a model checker.

Vocabulary that gets muddled

A race condition is when correctness depends on timing. A data race is the narrower case of two threads accessing the same location concurrently with at least one writing and no synchronisation between them; in C++ and Rust it is undefined behaviour, not merely wrong. A critical section is the code that must not run concurrently. Mutual exclusion is the guarantee that it does not. You can have a race condition with no data race — check-then-act on a file, for instance — so a clean race detector run is not a proof of correctness.

Atomicity from the hardware up

You cannot build mutual exclusion out of ordinary loads and stores efficiently — Dekker's and Peterson's algorithms prove it is possible, but they are slow and rely on memory ordering guarantees that modern CPUs do not give for free. Real locks are built on instructions that the hardware performs indivisibly.

Test-and-set
Write 1 to a location and return what was there before, as one indivisible operation. If it returns 0 you got the lock. The simplest primitive, and enough on its own.
Fetch-and-add
Add a value and return the previous one. This is what an atomic counter compiles to — lock xadd on x86 — and it is why an atomic increment is correct where counter++ is not.
Compare-and-swap (CAS)
"If this location still holds expected, replace it with new, and tell me whether you did." The most general primitive, and the foundation of every lock-free algorithm. cmpxchg on x86.
Load-linked / store-conditional
ARM, RISC-V and POWER use a pair instead: load with a reservation, then store only if nothing has touched the address since. More flexible than CAS and the reason ARM code around atomics looks like a retry loop.
a lock-free increment, built from CAS
do {
    old = counter;                     // read what we think is there
    next = old + 1;
} while (!compare_and_swap(&counter, old, next));
// if another thread changed counter in between, the CAS fails
// and we simply try again with the new value. No lock, no blocking,
// and someone always makes progress.

These instructions are not free. On x86 a lock-prefixed instruction takes exclusive ownership of the cache line and orders memory around itself, costing tens of cycles uncontended and far more under contention, because the line has to be pulled away from whichever core has it. This is the same cache-line ping-pong that chapter 5 called false sharing, and it is why a single atomic counter incremented by sixteen cores can be slower than sixteen separate counters summed at the end.

Mutexes: spinning, sleeping and futexes

A mutex has two states and two operations, and the interesting question is what a thread does when it cannot have the lock.

Spinlock

Loop on test-and-set until it succeeds. No system call, no context switch, so acquisition is a few tens of nanoseconds when the lock is free or held briefly. Burns a whole core while waiting, and is catastrophic if the holder is preempted — you spin for a full quantum waiting for a thread that is not running.

Blocking mutex

Ask the kernel to put the thread to sleep and wake it when the lock is released. Costs a system call and a context switch, several microseconds, but frees the core for other work. Correct under any amount of contention or preemption.

The right answer depends on how long you expect to wait, which is why modern implementations do both. A futex — fast userspace mutex — keeps the lock word in user memory and only enters the kernel when there is contention:

  1. Try to take the lock with a single CAS. If it succeeds, done, with no system call at all. This is the overwhelmingly common path.
  2. If it fails, spin briefly — an adaptive number of iterations — in case the holder is about to release.
  3. Only then call into the kernel to sleep, and record that a waiter exists so the releaser knows to issue a wake.

The result is that an uncontended lock costs roughly the price of one atomic operation, around 20 ns, while a contended one degrades gracefully instead of burning cores. Linux's futex, Windows' SRWLOCK and Go's sync.Mutex all have this shape.

Reader-writer locks are slower than you expect

They look free for read-heavy workloads and often are not. The read path still has to modify a shared reader count atomically, which is exactly the cache-line ping-pong a plain mutex would have caused, so short read critical sections gain nothing and lose to the extra complexity. They also introduce a fairness question — do queued writers block new readers? If not, a steady stream of readers starves writers forever. Measure before reaching for one; for read-mostly data, a copy-on-write pointer swap or RCU is usually the better answer.

Semaphores and condition variables

A semaphore is a counter with two atomic operations, invented by Dijkstra in 1965 and still the cleanest way to express "at most n of these at once".

the two operations, and the classic use
wait(s)   // P: if s > 0 decrement and continue, else block
signal(s) // V: increment, and wake one waiter if there is one

// bounded buffer, the textbook producer-consumer
sem empty = N;      // how many free slots
sem full  = 0;      // how many filled slots
mutex m;            // protects the buffer itself

producer:                          consumer:
  wait(empty)                        wait(full)
  lock(m); put(item); unlock(m)      lock(m); item = take(); unlock(m)
  signal(full)                       signal(empty)

A semaphore initialised to 1 behaves like a mutex but is not one: any thread may signal it, not only the one that waited. That difference makes it the right tool for signalling between threads and the wrong tool for protecting data, where accidental release by the wrong thread is a bug you want the type system to catch.

Order the waits, or deadlock

Swap the first two lines of the producer so it takes the mutex before wait(empty), and a full buffer deadlocks instantly: the producer sleeps holding the mutex, and the consumer cannot take the mutex to drain the buffer. The rule that falls out of this is general — never block while holding a lock, and if you must acquire two things, acquire them in a fixed global order.

Condition variables

A condition variable lets a thread wait for a predicate to become true while holding a mutex, without spinning. wait atomically releases the mutex and sleeps; when woken it re-acquires it before returning. That atomicity is the whole point: without it, a wake-up arriving between the check and the sleep would be missed forever.

the only correct shape
lock(m);
while (!condition)        // while, NEVER if
    cond_wait(cv, m);
// condition is true here, and we hold m
unlock(m);
Why it must be while and not if

Three reasons, any one of which is enough. Spurious wakeups are permitted by POSIX and do occur, so a wake does not mean the predicate holds. Broadcast wakes every waiter, but only one may be able to proceed. And on most implementations a woken thread must re-acquire the mutex, during which a third thread can slip in and invalidate the condition again — this is called mesa semantics, and every mainstream library uses it. Re-checking in a loop handles all three; if handles none.

Deadlock and the four conditions

Coffman's 1971 result is that deadlock requires all four of these simultaneously. Break any one and deadlock becomes impossible.

No preemptionResources cannot be taken backUse try_lock with a timeout, and back off releasing what you hold
Circular waitA cycle exists in the wait-for graphImpose a global order on lock acquisition. The usual answer

The naive policy deadlocks with any number of philosophers from two upwards. In the first round everyone successfully picks up their left fork; in the second, everyone reaches for a right fork that their neighbour is already holding, and the wait-for graph closes into a cycle 0 → 1 → 2 → 3 → 4 → 0. Nobody eats, ever.

Each of the other three policies breaks a different Coffman condition. Global fork ordering breaks circular wait: with the lower-numbered fork always taken first, the last philosopher reaches for fork 0 instead of fork 4, and the cycle cannot close. The asymmetric policy does the same thing with one special case. The arbitrator takes both forks atomically, breaking hold and wait, and it gets more meals through — 26 in twenty rounds against 18 — because it never leaves a fork idle in the hand of a blocked philosopher.

Lock ordering is the practical rule

Give every lock in the system a rank and always acquire in increasing rank. The rank can be an address, a name, a documented layer number — anything total and consistent. This makes circular wait structurally impossible rather than merely unlikely, and it is checkable: Linux's lockdep and Java's ThreadMXBean both detect out-of-order acquisition, and clang's thread-safety analysis can enforce it at compile time.

Two conditions worth distinguishing from deadlock: in livelock threads keep running and keep responding to each other but make no progress, which is what naive back-off-and-retry produces without randomised delays. In starvation some threads do make progress and one never does, usually because a lock is unfair and a steady stream of arrivals keeps jumping the queue.

Beyond locks

Memory ordering

Everything above assumed that if thread A writes X then Y, thread B sees X before Y. It does not. Compilers reorder instructions, and CPUs reorder loads and stores and buffer writes. Both are allowed to, because both must only preserve the behaviour of a single thread.

The C++11 and Java memory models make this explicit through a happens-before relation. In practice you need three levels:

Memory orderings, weakest to strongest
OrderingGuaranteesUse for
relaxedAtomicity only, no ordering with respect to anything elseStatistics counters where only the final total matters
acquire / releaseA release-store is visible to any acquire-load that reads it, along with everything written before itThe standard pairing for locks, flags and handoffs
seq_cstA single global order that every thread agrees onThe default. Slower on ARM and POWER, nearly free on x86

The practical advice is to use the default sequential consistency unless a profiler tells you it costs something, and to treat hand-written relaxed atomics as expert territory. The classic bug — a volatile bool ready flag guarding data written just before it — is broken in C and C++ because volatile says nothing about ordering or atomicity. It means "do not optimise away this access", which is a statement about compilers and hardware registers, not about threads. Java's volatile is a different keyword with genuine memory-model meaning; the confusion between the two is a reliable source of bugs.

Lock-free, and RCU

A lock-free algorithm guarantees that some thread always makes progress; a wait-free one guarantees every thread does, in bounded steps. Both are built from CAS retry loops. They avoid deadlock and priority inversion by construction and are genuinely faster under moderate contention, but they are extremely hard to get right — the ABA problem alone (a value changes from A to B and back to A, so the CAS succeeds when it should not) has produced a long history of subtly broken published algorithms. Use a library.

Read-copy-update takes a different angle for read-mostly data: readers take no lock at all and pay nothing, while a writer builds a new version and swaps a pointer, then waits until every pre-existing reader has finished before freeing the old copy. It is heavily used inside the Linux kernel, and the same shape appears in userspace as immutable-data-plus-atomic-pointer-swap, which is one reason persistent data structures are popular in concurrent functional code.

The advice that actually scales

Do not share mutable state. Message passing between threads that own their data — Go channels, Erlang processes, actors, worker queues — removes whole categories of these bugs by construction. Rust encodes the same discipline in its type system: Send and Sync make data races a compile error rather than a production incident. When you do share, hold locks for as short a time as possible, never call unknown code while holding one, and prefer one coarse lock you understand to five fine-grained ones you do not.

Check yourself

Two threads each increment a shared counter once. How many of the possible schedules give the right answer?

Two out of twenty. Each thread performs load, increment, store, so there are C(6,3) = 20 ways to interleave six operations. The answer is correct only when one thread's store happens before the other's load, which means one thread ran entirely before the other — exactly two orders. The other 18 have both threads loading the same value, so both store the same result and one increment vanishes. With three threads it is 6 correct out of 1,680, or 0.36%.

Your race never reproduces locally but appears weekly in production. Why, and what would you do?

Because the interleavings that are wrong are also the ones the scheduler rarely produces — preemption inside a three-instruction window is uncommon, and it becomes likelier with more cores, more load, and different timing. Reproducing by running more is a bad strategy. Use a tool that explores the schedule space rather than sampling it: ThreadSanitizer, Helgrind, Go's -race, or Java's jcstress. They detect unsynchronised access even when the run happened to be correct, which is the whole point.

Why can mutual exclusion not be built from ordinary loads and stores in practice?

It can in theory — Peterson's and Dekker's algorithms do it for two threads with only loads and stores. In practice they are unusable: they need sequential consistency, which modern CPUs do not provide by default, so you need memory fences anyway, and they scale badly past two threads while spinning the whole time. Real locks use one hardware instruction that reads and writes indivisibly — test-and-set, fetch-and-add, or compare-and-swap — which is both correct and one operation instead of a protocol.

Why is a condition variable wait always written inside a while loop?

Three independent reasons. POSIX permits spurious wakeups, so returning from wait does not mean anything happened. Broadcast wakes all waiters when perhaps only one can proceed. And under mesa semantics, which every mainstream implementation uses, a woken thread must re-acquire the mutex, and another thread can take it first and invalidate the condition again. A while loop re-checks the predicate and handles all three; an if handles none and produces a bug that appears under load.

Five philosophers each pick up their left fork then their right. What happens, and which Coffman condition would you break?

Deadlock. Everyone acquires a left fork, then everyone blocks on a right fork their neighbour holds, closing a cycle in the wait-for graph. Any of the four conditions can be broken, but circular wait is the practical target: number the forks and always take the lower-numbered one first. The last philosopher then reaches for fork 0 rather than fork 4, so no cycle can form. Confirm it in demo 2 — the naive policy deadlocks at every size from 2 to 9, and the ordered policy at none.

The arbitrator policy gets more meals through than fork ordering. Why, if both prevent deadlock?

Because preventing deadlock and maximising throughput are different goals. Under fork ordering a philosopher can hold one fork while blocked on the second, so that fork is idle in a blocked hand and unavailable to a neighbour who could have used it. The arbitrator takes both or neither, so a fork is never held by someone unable to eat. In the demo that is 26 meals in twenty rounds against 18. The cost is that the arbitrator is itself a central point of contention, which is exactly the trade you make every time you replace fine-grained locking with a coarse one.

A colleague guards shared data with volatile bool ready in C++. What is wrong?

volatile in C and C++ means only "do not optimise away or cache this access" — it was designed for memory-mapped hardware registers. It provides neither atomicity nor any ordering with respect to other variables, so the compiler and the CPU are both still free to move the data writes after the flag write, and the reader may see ready == true with the data not yet visible. The correct tool is std::atomic<bool> with release on the write and acquire on the read, or simply a mutex. Java's volatile is a different keyword that does carry memory-model guarantees, which is why the advice differs between the two languages.

Ten things to carry forward

  1. counter++ is load, increment, store, and a preemption between any two of them loses an update.
  2. Two threads have 20 schedules and 18 are wrong. Three threads have 1,680 and 1,674 are wrong. The bug is the default, not the exception.
  3. Rarity in testing is the danger, not the reassurance. Use a race detector that explores rather than samples.
  4. Locks are built on one indivisible hardware instruction — test-and-set, fetch-and-add or compare-and-swap — not on clever use of ordinary loads and stores.
  5. A futex takes the fast path in userspace and only enters the kernel under contention, which is why an uncontended lock costs about one atomic operation.
  6. Semaphores count, mutexes own. Any thread may signal a semaphore; that flexibility makes it good for signalling and bad for protecting data.
  7. Condition variable waits go in a while loop, because of spurious wakeups, broadcast, and mesa semantics.
  8. Deadlock needs all four Coffman conditions. Breaking circular wait with a global lock order is the practical answer.
  9. Preventing deadlock is not the same as getting work done: a policy that leaves resources idle in blocked hands is correct and slow.
  10. The best concurrency is no shared mutable state. Message passing, immutability and ownership remove these bugs instead of managing them.
