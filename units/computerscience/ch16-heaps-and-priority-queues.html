Heaps and priority queues

Give up almost all of the ordering a search tree maintains — keep only "a parent beats its children" — and you get a structure with no pointers at all, built in linear time, that answers the one question a scheduler, a shortest-path algorithm and a merge all need to ask.

The priority queue, and the cost of the obvious answers

A priority queue is an abstract data type with three operations: insert, peek at the highest-priority item, and extract it. Nothing else. No indexing, no search, no ordered iteration.

Four ways to implement it
ImplementationInsertPeekExtract
Unsorted arrayΘ(1)Θ(n)Θ(n)
Sorted arrayΘ(n)Θ(1)Θ(1)
Balanced BSTΘ(log n)Θ(log n)Θ(log n)
Binary heapΘ(log n)Θ(1)Θ(log n)

The two array options each push all the cost onto one side. A balanced BST does everything in logarithmic time but maintains far more ordering than anyone asked for, and pays for it in pointers, rebalancing and cache misses. The heap gives the same asymptotics as the tree with a constant factor several times smaller, plus Θ(1) peek, because it maintains exactly the one relationship the interface requires.

Weaker invariant, cheaper structure

A BST orders every pair of nodes that stand in an ancestor relationship and across subtrees. A heap orders only parent against child. Sibling order is undefined; a node three levels down may be smaller than a node one level down in another subtree. That looseness is what allows the array embedding, the linear build, and the tiny constants.

The heap property and the array trick

A min-heap is a complete binary tree in which every node is ≤ both of its children. A max-heap flips the comparison. Complete means every level is full except possibly the last, which fills left to right — and that is the property that removes the pointers.

a complete tree is an array, with arithmetic instead of pointers
            1                    index:  0  1  2  3  4  5  6
          /   \                  array: [1, 3, 2, 7, 4, 9, 8]
         3     2
        / \   / \                parent(i) = (i - 1) / 2      integer division
       7   4 9   8               left(i)   = 2i + 1
                                 right(i)  = 2i + 2

  node 3 sits at index 1; its children 7 and 4 are at indices 3 and 4.
  parent(3) = 1, parent(4) = 1. No pointers, no allocation, perfect locality.

Three consequences follow immediately. The structure costs exactly one array — no node objects, no pointer overhead, no allocator involvement. Traversal is index arithmetic, so a parent and its children are usually in the same cache line near the top of the array. And the last element of the array is always the last leaf, which is what makes extraction work.

Note also that a heap is not sorted. [1, 3, 2, 7, 4, 9, 8] is a valid min-heap and is not in ascending order. The only guarantee is that index 0 holds the minimum.

Insert — sift up

Append to the end of the array, which keeps the tree complete, then swap upward with the parent while the new value is smaller. At most one swap per level, so Θ(log n).

Extract — sift down

Take index 0 as the answer, move the last element into its place, shrink by one, then swap downward with the smaller child while it is smaller than the node. Also Θ(log n).

Sift down must pick the smaller child

Swapping with either child that happens to be smaller than the parent is the classic bug. If you swap with the larger of two children that are both smaller than the parent, the new parent is larger than its remaining sibling and the heap property is broken one level down. The code must compare the two children first, then compare the winner against the parent — which is why sift down needs two comparisons per level and sift up needs one.

Why building a heap is linear

Given n items already in an array, there are two ways to make a heap of them. Insert them one at a time, or run Floyd's bottom-up heapify: start at the last internal node, index ⌊n/2⌋ − 1, and sift down from each index back to 0.

Inserting one at a time is Θ(n log n) in the worst case. Bottom-up heapify is Θ(n), which surprises people because it looks like n calls to a log n operation.

the argument, in one sum
a complete tree has about n/2 nodes at height 0, n/4 at height 1,
n/8 at height 2 … and one at height log n.

sifting down from height h costs at most h swaps, so:

  total  ≤  Σ (n / 2^(h+1)) × h   for h = 0 … log n
         =  n × Σ h / 2^(h+1)
         =  n × 1                    the series converges to 1
         =  O(n)

the cheap case is the common one: HALF the nodes are leaves and
move zero levels, and three quarters move at most one.

On 100,000 elements in descending order — the worst case for both — heapify does 99,990 swaps, almost exactly one per element, and repeated insertion does 1,468,946, an average of 14.7 per element against log₂(100,000) = 16.6. That is 14.7 times the work for the same result.

The scaling table shows which one is actually linear. Multiply n by ten and heapify's swaps multiply by about ten; repeated insertion's multiply by more than fourteen, because the per-element cost is itself growing with log n.

Descending is heapify's worst case, not its best

The intuition runs the other way, so it is worth being explicit. A descending array is a valid max-heap, so building a min-heap from it requires every element to sift as far as it can go — heapify's maximum. It is still linear: 99,990 swaps for 100,000 elements, one per element, because most elements have nowhere far to go. An ascending array is already a valid min-heap and both methods do zero swaps.

Both builds produce a valid heap, and generally different valid heaps. A heap is not unique for a given multiset of keys, which is another way of saying the invariant is weak.

Heapsort

Once you can build a heap in linear time, sorting falls out. Build a max-heap in place, then repeatedly swap the root with the last unsorted element and sift down over the shrinking prefix. When the prefix is empty, the array is ascending.

Heapsort is the only one of the three with a worst-case guarantee and constant extra space, and it is still rarely the default. The reason is the last row: sift down jumps from index i to 2i+1, so once the array exceeds the cache every step is a miss, while quicksort scans contiguously. Measured on 100,000 random elements, heapsort uses about 3.0 million comparisons — roughly 2n log₂ n — and quicksort typically uses fewer with far better locality.

Where heapsort does appear is as a safety net. Introsort, the algorithm behind C++'s std::sort, runs quicksort and switches to heapsort once the recursion exceeds about 2 log n levels. That gives quicksort's speed in the common case and heapsort's Θ(n log n) guarantee against adversarial input.

Variants

d-ary heaps
Give each node d children instead of 2. The tree gets shorter — a million elements is height 19 for d = 2, 10 for d = 4, 7 for d = 8 — so insert gets cheaper. But extract must compare all d children at every level, so its comparison count goes the other way: 2 × 19 = 38, 4 × 10 = 40, 8 × 7 = 56. A 4-ary heap is often fastest in practice because the children are contiguous and fit in one cache line.
Binomial and Fibonacci heaps
Support merge of two heaps in Θ(log n) and Θ(1) respectively. A Fibonacci heap also gives Θ(1) amortised decrease-key, which lowers Dijkstra's bound from O(E log V) to O(E + V log V). The constants are large enough that binary heaps usually win in practice, which makes it a standard example of an asymptotic improvement that rarely pays.
Indexed heaps
A binary heap plus a map from item to array position, so you can find and update an arbitrary element. This is what Dijkstra's and Prim's algorithms actually need, since they must lower the priority of a node already in the queue. Without it, the usual workaround is to insert a duplicate and discard stale entries on extraction.
Pairing heaps
Much simpler to implement than Fibonacci heaps with similar practical performance, and the structure the Linux kernel's timer subsystem and several graph libraries use.

Top-k with a heap of size k

To keep the k largest items from a stream of n, use a min-heap of capacity k. Push until it is full; after that, compare each new item against the root and, if it is larger, replace the root and sift down. The root is always the weakest of your current best k, so it is the right thing to evict. The cost is Θ(n log k) time and Θ(k) space — you never hold the whole stream, which is what makes it work on data that does not fit in memory. Using a max-heap here is the natural mistake and gives you no cheap way to find the item to drop.

Check yourself

Why can a heap be stored in a plain array while a BST cannot?

Because a heap is required to be a complete tree: every level full except the last, which fills left to right. That means the positions are fully determined by the count, so index arithmetic replaces pointers — left(i) = 2i+1, right(i) = 2i+2, parent(i) = (i−1)/2. A BST's shape depends on its keys and their insertion order, so the same array position could mean different things; storing one in an array leaves gaps that in the degenerate case are exponentially large.

Is [1, 3, 2, 7, 4, 9, 8] a valid min-heap? Is it sorted?

It is a valid min-heap and it is not sorted. Check each parent: 1 ≤ 3 and 1 ≤ 2; 3 ≤ 7 and 3 ≤ 4; 2 ≤ 9 and 2 ≤ 8. Every parent beats its children, which is the whole invariant. Nothing constrains siblings or cross-subtree pairs, so 3 sitting before 2 is fine. Only index 0 is guaranteed to be the minimum — which is precisely why peek is Θ(1) and everything else costs a sift.

Why must sift-down compare the two children with each other before comparing with the parent?

Because swapping with the wrong one breaks the invariant. If both children are smaller than the parent and you swap with the larger of them, that larger value becomes the parent of the smaller sibling and is now greater than it — the heap property is violated one level down, and the sift continues past the damage without noticing. Comparing the children first and swapping with the winner guarantees the new parent beats both. This is why sift-down costs two comparisons per level and sift-up costs one.

Building a heap calls sift-down n/2 times, each Θ(log n). Why is the total Θ(n) and not Θ(n log n)?

Because almost no node is at the top. In a complete tree about n/2 nodes are leaves and sift zero levels, n/4 sift at most one, n/8 at most two, and only one node can sift log n. The total is n × Σ h/2h+1, and that series converges to 1, so the bound is n. The log n factor is real but applies only to a vanishing fraction of the nodes. Confirm it in demo 2: at n = 100,000 the worst input gives 99,990 swaps, about one per element.

Which input order is worst for bottom-up heapify when building a min-heap?

Descending. A descending array is already a valid max-heap, so building a min-heap from it forces every element to sift as far as it can go — heapify's maximum work. The intuition usually runs the other way, and the point of measuring is that the answer is still linear: 99,990 swaps for 100,000 elements. An ascending array is already a valid min-heap, so both build methods do zero swaps. Repeated insertion has the opposite worst case for the same reason: descending input makes every new element the new minimum, so it sifts all the way to the root, giving 1.47 million swaps.

Heapsort has a Θ(n log n) worst case and uses Θ(1) extra space. Why is quicksort usually the default?

Cache behaviour. Sift-down jumps from index i to 2i+1, so once the array exceeds the cache almost every step is a miss, and chapter 5 measured that at up to 80× a hit. Quicksort scans contiguously from both ends, which prefetches perfectly. Quicksort also does fewer comparisons on average. The usual resolution is introsort — run quicksort, and switch to heapsort if the recursion goes deeper than about 2 log n levels — which gets quicksort's constants with heapsort's guarantee.

You need the 100 largest values from a billion-record stream. What do you build?

A min-heap of capacity 100. Fill it with the first 100 records, then for each subsequent record compare it against the root: if it is larger, replace the root and sift down; otherwise discard it. The root is always the smallest of your current top 100, which is exactly the one to evict, and finding it is Θ(1). Cost is Θ(n log k) time and Θ(k) space — you never store more than 100 records, so the stream size is irrelevant. A max-heap is the natural-sounding choice and is wrong: its root is the largest, which tells you nothing about what to drop.

Ten things to carry forward

  1. A priority queue needs only insert, peek and extract, and a heap maintains exactly enough ordering to serve them.
  2. The heap property is parent versus child only. Siblings and cross-subtree pairs are unordered, and a heap is not sorted.
  3. Completeness is what allows the array embedding: left = 2i+1, right = 2i+2, parent = (i−1)/2, no pointers at all.
  4. Insert sifts up, extract sifts down, both Θ(log n), and peek is Θ(1) because the answer is index 0.
  5. Sift-down must compare the children first and swap with the smaller one, or it breaks the invariant one level below.
  6. Bottom-up heapify is Θ(n), because half the nodes are leaves and the level sum converges.
  7. Descending input is heapify's worst case and still linear — one swap per element — while repeated insertion needs 14.7.
  8. Heapsort is in place with a worst-case guarantee and loses on locality, which is why it lives inside introsort as a fallback.
  9. Larger fan-out shortens the tree and lengthens each extract. 4-ary heaps usually win because the children share a cache line.
  10. Top-k from a stream uses a min-heap of size k, so the item to evict is always the one you can see for free.
