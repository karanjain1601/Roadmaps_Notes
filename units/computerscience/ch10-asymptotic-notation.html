Chapter 10 · Measuring computation

Asymptotic notation and runtimes

A thousand times more compute buys a thousand times more input for a linear algorithm, thirty-two times for a quadratic one, and ten extra items for an exponential one. That asymmetry is the whole reason this notation exists, and it does not care how fast your machine is.

Why count operations instead of timing things

Timing an algorithm tells you about your machine, your compiler, your input, the state of your cache and what else was running. Change any of those and the number changes. What does not change is the shape of the curve — how the work grows as the input grows — and that shape is what determines whether a program that handles a thousand records will handle a million.

Asymptotic analysis makes three deliberate simplifications:

  1. Count operations, not seconds. Machine-independent.
  2. Ignore constant factors. An algorithm doing 3n work and one doing 100n are both linear; hardware improvements can close a constant-factor gap, and never close a complexity gap.
  3. Care only about large n. Below some size everything is fast enough, so the interesting question is what happens as the input grows without bound.

Each simplification throws away real information, and section seven is about when the discarded information turns out to matter. But the thing that survives is the thing that decides whether a system is viable.

O, Ω and Θ

Three notations, describing three different relationships between a function and a bound. They are frequently used interchangeably in conversation and should not be.

Big-O — an upper bound
f(n) = O(g(n)) means there exist constants c > 0 and n0 such that f(n) ≤ c·g(n) for all n ≥ n0. It grows no faster than. Note that this makes O(n²) a perfectly true statement about a linear algorithm — just a useless one.
Big-Omega — a lower bound
f(n) = Ω(g(n)) means f(n) ≥ c·g(n) beyond some point. It grows at least as fast as. This is the notation for proving a problem is hard: comparison sorting is Ω(n log n) no matter what algorithm you invent.
Big-Theta — a tight bound
f(n) = Θ(g(n)) means both at once. It grows exactly as fast as, to within constant factors. This is usually what people mean when they say Big-O.

Two habits are worth forming. First, always say what you are measuring: time or space, worst case or average. "Quicksort is O(n log n)" is false for the worst case and true for the average, and the sentence does not say which. Second, drop constants and lower-order terms but keep the variables you actually have: 3n² + 5n + 100 is Θ(n²), but O(V + E) for a graph traversal must keep both, because vertices and edges vary independently.

"Big-O is the worst case" is a common muddle

Big-O is a statement about a function's growth; best, average and worst case are statements about which input you are measuring. They are independent axes. You can perfectly well say that insertion sort's best case is Θ(n) and its worst case is Θ(n²). The confusion arises because worst-case upper bounds are the most commonly quoted combination, not because the notations mean the same thing.

At a billion operations per second with one second to spend, a linear algorithm handles 109 items, n log n handles about 4 × 107, quadratic handles 31,622, cubic handles 1,000, exponential handles 29, and factorial handles 12.

Now move to the trillion-ops machine — a thousand times faster — and watch what each class does with it. Linear gets a thousand times more input. Quadratic gets 31.6 times more, because the square root of a thousand is 31.6. Cubic gets ten times. Exponential gets ten extra items. Factorial gets two: from 12 to 14.

This is the whole argument

Hardware multiplies your budget. Complexity determines the exchange rate between budget and input size, and for anything worse than polynomial the exchange rate is so bad that no plausible amount of hardware helps. Buying a machine a thousand times faster to run a factorial algorithm buys you two more items. Improving the algorithm is not one optimisation among several; for the classes at the bottom of the table it is the only one that exists.

Analysing code

Four rules cover most straight-line and looping code.

the mechanical rules
// 1. sequential blocks: take the maximum, not the sum
doA();   // O(n)
doB();   // O(n^2)
// -> O(n^2), because n + n^2 is dominated by n^2

// 2. nested loops: multiply
for (i = 0; i < n; i++)
  for (j = 0; j < n; j++)  // -> O(n^2)

// 3. but read the bounds. this is NOT quadratic in the loop count:
for (i = 0; i < n; i++)
  for (j = i; j < n; j++)  // n + (n-1) + ... + 1 = n(n+1)/2 -> still O(n^2)

// 4. and this one is logarithmic, because i multiplies rather than adds
for (i = 1; i < n; i *= 2)  // -> O(log n)

Rule 3 is worth pausing on. Halving the number of iterations does not change the class — n(n+1)/2 is still Θ(n²) — which is exactly the kind of constant factor the notation deliberately discards. Rule 4 is the signature of every logarithmic algorithm: something is being multiplied or divided rather than incremented.

Recurrences and the master theorem

Recursive algorithms are described by a recurrence. Divide-and-conquer recurrences of the form T(n) = a·T(n/b) + f(n) are solved by comparing f(n) against nlogba — the total work done at the leaves.

The interesting cases are the ones where changing a changes everything. Naive matrix multiplication splits into 8 subproblems of half the size with Θ(n²) combining, giving nlog₂8 = n³. Strassen's algorithm gets it down to 7 subproblems, and nlog₂7 = n2.807. Karatsuba multiplication does the same trick for big integers, turning 4 subproblems into 3 and n² into nlog₂3 = n1.585. In both cases the entire gain came from removing one recursive call.

Space complexity too

The same notation applies to memory, and the recursion stack counts. A recursive merge sort is Θ(n) auxiliary space for the merge buffers plus Θ(log n) for the stack; quicksort is Θ(log n) stack if you recurse into the smaller side first and Θ(n) if you do not. Time-space trade-offs are the most common lever in algorithm design: memoisation buys time with space, and streaming algorithms buy space with accuracy.

Amortised analysis

Appending to a dynamic array is O(1). Except when the array is full, at which point it allocates a bigger one and copies everything, which is O(n). Both statements are true and neither is the useful one.

Amortised analysis measures the average cost per operation over a worst-case sequence, which is a stronger and more useful claim than average-case analysis: there is no probability involved and no assumption about the input distribution. It says that n appends cost O(n) in total, regardless of what happens.

With doubling and 1,000 pushes there are 10 resizes and 1,023 element copies. The most expensive single push copies 513 elements; 990 of the 1,000 cost exactly one. Total work is 2,023 units for 1,000 pushes, an amortised cost of 2.023.

The intuition for why the spikes do not accumulate: each resize copies n elements, but the previous resize happened at n/2, so at least n/2 cheap pushes occurred in between to pay for it. Every element is copied at most once per doubling and the total is a geometric series that sums to less than 2n.

Switch to +1 growth to see what happens without the geometric series. Every push after the first triggers a resize, copies grow as 0 + 1 + 2 + … + 999 = 499,500, and the amortised cost is 500.5 per push — which is not a constant at all. Double n and the copies quadruple. Growing by a constant amount makes appending Θ(n) amortised and building a list Θ(n²).

Choosing the factor

A larger factor means fewer copies and more wasted capacity. Worst-case waste is (g−1)/g: 33% at 1.5, 50% at 2, 75% at 4. Amortised cost stays bounded by 1 + g/(g−1) in every case, so any g > 1 is O(1). There is also a subtler argument for 1.5: with doubling, the sum of all previously freed blocks (1 + 2 + 4 = 7) is always less than the next request (8), so the allocator can never reuse them. Below the golden ratio it can, which is why some implementations chose 1.5 — although with virtual memory and modern allocators the effect is largely historical.

The last two rows are where judgement is required. Quicksort's worst case is quadratic and it is still the standard library sort in many languages, because random pivot selection makes the bad case astronomically unlikely — and because when it does matter, introsort switches to heapsort after too many levels, giving a genuine Θ(n log n) worst case with quicksort's constants.

Hash tables are the sharper case. Average O(1) assumes the keys are not chosen to collide. If they can be — user-supplied keys in an HTTP form, JSON object keys, a URL query string — an attacker who knows your hash function can drive every insert into one bucket and turn an O(n) parse into O(n²). That is a real denial-of-service technique, and it is why modern languages seed their hash functions randomly at process start. Average-case analysis is a statement about the input distribution, and an adversary controls the input distribution.

What the notation deliberately ignores

Everything discarded in section one comes back somewhere.

Constants can dominate at real sizes
2n² beats 200·n log n until n = 997. If your inputs are always in the hundreds, the asymptotically worse algorithm is the faster one, and this is exactly why every good sort switches to insertion sort for small partitions.
Memory access is not one operation
Chapter 5's whole point. An L1 hit and a DRAM miss both count as one array access and differ by a factor of eighty. This is why std::vector routinely beats std::list, why B-trees with hundreds of children beat binary search trees, and why a linear scan can beat a tree for thousands of elements.
Which variable is n
"Checking a substring is O(1)" is meaningless without saying whether n is the number of strings or their length. Graph algorithms need both V and E. Numeric algorithms need the number of bits of the input, not its value — which is why an algorithm that is O(n) in the value of n is exponential in its size, and why that distinction decides whether knapsack is tractable.
It says nothing about parallelism or I/O
Two algorithms with identical complexity can differ by an order of magnitude in whether they vectorise, distribute or stream. And when data does not fit in memory, the number of disk accesses is the only complexity that matters, which is a different model entirely.
Use it for the decision it is good at

Asymptotic analysis answers "will this still work when the input is a hundred times bigger?" and it answers it definitively. It does not answer "which of these two implementations is faster today", and using it for that is how people end up with an elegant tree that loses to an array. Reach for complexity when choosing an approach, and a profiler when choosing between implementations of the same approach.

Check yourself

Is it correct to say that binary search is O(n²)?

Technically yes and practically never. Big-O is an upper bound, and log n is certainly bounded above by n², so the statement is true. It is also useless, which is why Θ exists: binary search is Θ(log n), meaning log n is both an upper and a lower bound. When someone says "the tightest bound", they are asking for Θ.

Your quadratic algorithm handles 30,000 items in a second. Your budget allows a machine a thousand times faster. How many items then?

About 31.6 times more, so roughly 950,000 — not a million-fold improvement but a thirty-fold one, because the input size scales as the square root of the budget. If you need ten million items you cannot buy your way there: 107 items quadratically is 1014 operations, a hundred seconds even on the trillion-op machine. The only route is an algorithm with a better exchange rate. Compare in demo 1 by switching machine speeds.

What is the complexity of for (i = 0; i < n; i++) for (j = i; j < n; j++)?

Θ(n²). The inner loop runs n times, then n−1, and so on down to 1, summing to n(n+1)/2 ≈ n²/2. Halving the constant does not change the class. This is the standard shape for anything that examines each unordered pair once — all-pairs distances, collision checks, similarity matrices — and it is why those become impossible somewhere in the tens of thousands.

Merge sort is T(n) = 2T(n/2) + Θ(n). Solve it, and explain what changes if the merge step were Θ(n²).

With a = 2 and b = 2, nlog₂2 = n, which matches the Θ(n) merge exactly — case two, giving Θ(n log n). Intuitively there are log n levels and each level does Θ(n) total work. If merging were Θ(n²) the root would dominate (case three) and the whole thing would be Θ(n²): the recursion would buy you nothing, because the top-level merge alone costs as much as the entire quadratic alternative.

A single append can copy 512 elements. Why is appending still called O(1)?

Because it is O(1) amortised, which is a claim about any sequence rather than any single operation. Each resize copies n elements but only happens after n/2 cheap pushes since the last one, so the expensive work is paid for in advance. Over 1,000 pushes the demo counts 1,023 copies in total — 2.023 units of work per push — and 990 of those pushes cost exactly one. The total for n pushes is a geometric series bounded by a constant times n.

What happens if a dynamic array grows by a constant 10 elements instead of by a factor?

Appending becomes Θ(n) amortised and building a list of n elements becomes Θ(n²). With growth by one, the demo counts 499,500 copies for 1,000 pushes — an amortised cost of 500.5 rather than a constant — and doubling n quadruples the copies. Growing by 10 divides that by ten and changes nothing asymptotically. The geometric factor is what makes the series converge; an arithmetic one gives you a sum of an arithmetic progression, which is quadratic.

You are told an O(n log n) algorithm is slower in production than the O(n²) one it replaced. Give three plausible explanations.

First, n is below the crossover: 2n² beats 200·n log n until n = 997, and real constants differ by that much. Second, memory behaviour: the quadratic algorithm may be a tight cache-friendly scan while the linearithmic one chases pointers or allocates, and chapter 5 showed an eight-times traffic difference from layout alone. Third, the analysis may be measuring the wrong thing — a different variable, an amortised bound that does not apply to this access pattern, or an average case whose distributional assumption the production data violates. Profile before assuming the theory is wrong, and before assuming it is right.

Ten things to carry forward

  1. Asymptotic analysis measures growth, not time, which is why it survives changes of machine, compiler and input.
  2. O is an upper bound, Ω a lower one, Θ both. Most people say O and mean Θ.
  3. Bound and case are independent axes. "Best case Θ(n)" and "worst case Θ(n²)" are both meaningful statements about the same algorithm.
  4. Complexity sets the exchange rate between hardware and input size. A thousand times more compute buys 1000× for linear, 31.6× for quadratic, and two more items for factorial.
  5. Nested loops multiply, sequential blocks take the maximum, and a loop whose counter multiplies is logarithmic.
  6. Divide-and-conquer recurrences hinge on the branching factor. Removing one of eight recursive calls took matrix multiplication from n³ to n2.807.
  7. Amortised is a worst-case claim about sequences, stronger than average-case because it assumes nothing about the input distribution.
  8. Geometric growth makes appends constant; arithmetic growth makes them linear. Any factor above 1 works; the factor only trades copies against wasted capacity.
  9. Average case is a claim about the input distribution, and an adversary controls the input distribution — which is why hash functions are seeded randomly.
  10. The notation ignores constants, memory hierarchy and which variable n is. Use it to choose an approach, and a profiler to choose an implementation.
