Chapter 5 · The machine

The memory hierarchy

A modern core can issue several instructions per nanosecond and has to wait roughly eighty nanoseconds for a value from main memory. Everything between those two numbers — three levels of cache, prefetchers, out-of-order execution — exists to hide one gap. Where your data sits matters more than what your code does to it.

The gap, and why it exists

Memory that is fast is small and expensive. Memory that is large is slow and cheap. Nobody has solved this, so instead we stack several kinds and hope the fast one is usually enough.

The constraint is physical. SRAM, used for cache, needs six transistors per bit and holds its value as long as it has power. DRAM, used for main memory, needs one transistor and one capacitor per bit, which is far denser and far cheaper, but the capacitor leaks so every row has to be refreshed thousands of times a second, and reading it is a slow analogue operation. On top of that, signals travel at a finite speed: light covers about 30 cm in a nanosecond, and electrical signals in silicon rather less, so a DRAM chip several centimetres away has a hard latency floor no engineering can remove.

Those ratios are the point. DRAM is about 80 times slower than an L1 hit. An SSD read is about 1,250 times slower than a DRAM read. A disk seek is another 80 times beyond that. Any optimisation that moves work up one level beats almost any optimisation that reduces instruction count at the same level.

The bet the hierarchy makes

Caches only work because real programs do not access memory at random. They reuse the same data soon after touching it, and they touch neighbouring addresses. Those two observations are called temporal locality and spatial locality, and every level of the hierarchy is a bet on them. Write a program that violates both and the hierarchy collapses to the speed of DRAM.

How a cache actually works

A cache never stores single bytes. It stores fixed-size blocks called cache lines, almost universally 64 bytes on x86-64 and ARM64. Ask for one byte and the hardware fetches the whole aligned 64-byte block containing it. That single design choice is where spatial locality gets cashed in, and where it gets punished.

Splitting the address

Given an address, the cache splits it into three fields with no arithmetic beyond shifting and masking:

a 32 KiB, 8-way, 64-byte-line cache decoding an address
32768 bytes / 64-byte lines           = 512 lines
512 lines / 8 ways                    = 64 sets

  ┌──────────── tag ────────────┬─ set index ─┬─ offset ─┐
  │        upper bits           │   6 bits    │  6 bits  │
  └─────────────────────────────┴─────────────┴──────────┘

offset     which byte inside the 64-byte line   (log2 64  = 6 bits)
set index  which of the 64 sets to look in      (log2 64  = 6 bits)
tag        everything else, stored alongside the data so the
           cache can tell which of many possible blocks it holds

Lookup is then: use the set index to pick one set, compare the tag against all 8 entries in that set in parallel, and if one matches, use the offset to pick the byte. All of it is a fixed, small amount of work, which is why an L1 hit costs about four cycles rather than a search.

Associativity

Direct-mapped (1 way)
Every block has exactly one place it can live. Lookup is one comparison, which is fast and cheap. Two hot blocks that map to the same slot evict each other endlessly, even if the rest of the cache is empty.
Fully associative
A block can live anywhere. No block ever evicts another unnecessarily. Requires comparing the tag against every entry, which is only feasible for very small caches — the TLB is usually built this way.
N-way set associative
The compromise everybody ships. A block maps to one set and can occupy any of the N ways within it. Typical numbers today are 8-way for L1 and 16-way for L2 and L3. Replacement within a set is approximately least-recently-used.
Where a way-slice boundary falls

In the cache above, 64 sets × 64-byte lines means addresses 4096 bytes apart map to the same set. Any access pattern with a stride that is a multiple of 4096 bytes will pile everything into one set and use 8 lines out of 512. Power-of-two array dimensions are extremely good at producing exactly this pattern, which is why matrix code sometimes gets dramatically faster when you pad a 1024-wide row to 1032.

Stride, and the cliff

Because a miss fetches 64 bytes whether you want them or not, the useful question is how many of those bytes you go on to use before the line is evicted. Walking an array of 8-byte doubles one element at a time uses all eight. Walking it eight elements at a time uses one and throws away seven, so you pay the same memory traffic for one eighth of the work.

With the defaults — a 1 MiB array of doubles through a 32 KiB, 8-way, 64-byte-line cache — the hit rates fall in exactly the pattern the line size predicts. Stride 1 uses all eight doubles in each line and hits 87.5% of the time. Stride 2 uses four and hits 75%. Stride 4 uses two and hits 50%. At stride 8 each access lands in a different line and the hit rate goes to zero, where it stays for every larger stride. The cliff is at stride = line size ÷ element size, and it does not get any worse after that, because you cannot waste more than a whole line.

Two settings are worth changing deliberately. Shrink the array to 16 KiB so it fits inside the cache and the hit rate is above 99% at every stride, because after the first pass nothing needs to be fetched again. And set ways to 1 to see how a direct-mapped cache behaves at strides that are powers of two.

Why a miss happened: the three Cs

Not all misses are the same, and the fix differs. Mark Hill's classification splits them into three causes, distinguished by asking what a different cache would have done.

Compulsory (cold) miss
The first ever reference to this block. No cache of any size or shape could have avoided it. The only fixes are prefetching it earlier or touching less data.
Capacity miss
The block was evicted because the working set is larger than the cache. A fully associative cache of the same size would also have missed. The fix is to shrink the working set — blocking, tiling, smaller types.
Conflict miss
The block was evicted even though a fully associative cache of the same size would have kept it. Too many hot blocks mapped to one set. The fix is to change the addresses: pad arrays, offset allocations, or increase associativity.

The definitions are operational, which is what makes them measurable: run the same address stream through a fully associative cache of the same capacity, and any miss the real cache suffers that the ideal one did not is a conflict miss.

Three patterns are worth stepping through. The sequential walk over 128 bytes produces exactly 8 compulsory misses and 24 hits with 16-byte lines — one miss per line, then three free accesses inside it. The conflict pattern touches three blocks that all map to set 0 in a 2-way cache, so after the three compulsory misses every subsequent access is a conflict miss, and the classifier proves it by noting a fully associative cache of the same size would have held all three comfortably. Raise ways to 4 and the conflicts vanish without changing the total capacity at all.

The nine-lines pattern is the contrast: nine distinct blocks into an eight-line cache. Now even a perfect cache would miss, so those misses are classified as capacity, not conflict, and adding associativity does not help. The fix there is algorithmic — process the data in blocks that fit.

A fourth C, for multicore

The original list has three. On a multiprocessor there is a fourth: coherence misses, caused by another core invalidating your copy of a line. They are indistinguishable from conflict misses in a single-core simulator, and they are the subject of the false sharing section below.

Data layout beats cleverness

Once you accept that memory moves in 64-byte units, several familiar design choices look different.

Array of structs versus struct of arrays

the same data, two layouts
// Array of structs — one particle is contiguous
struct Particle { double x, y, z, vx, vy, vz; int id; bool alive; };
Particle p[100000];                // 56–64 bytes each

// Struct of arrays — one field is contiguous
struct Particles {
  double x[100000], y[100000], z[100000];
  double vx[100000], vy[100000], vz[100000];
  int id[100000]; bool alive[100000];
};

A loop that sums every x reads 8 useful bytes out of each 64-byte line in the array-of-structs layout, wasting seven eighths of every fetch. In the struct-of-arrays layout the same loop is a stride-1 walk that uses every byte, and it vectorises cleanly because the values are adjacent. If instead you process whole particles one at a time, array-of-structs is the better layout, because everything you need arrives together.

Neither is universally right. The question is which fields your hot loop touches together. Game engines and physics code usually go struct-of-arrays for the simulation step; anything that iterates whole records keeps array-of-structs.

Padding and alignment

Compilers insert padding so each field sits at an address that is a multiple of its size, because unaligned accesses are slower or, on some architectures, illegal. Field order therefore changes the size of a struct:

The same three fields, two orders, on a typical 64-bit ABI
Declaration orderLayoutTotal
char a; long b; char c;a + 7 pad + b + c + 7 pad24 bytes
long b; char a; char c;b + a + c + 6 pad16 bytes

A third of the memory saved by reordering two declarations. Across a million-element array that is 8 MB, which is the difference between fitting in L3 and not. Sorting struct fields from largest to smallest is a reliable habit; Rust reorders fields automatically unless you ask for C layout, and Go and C do not.

False sharing

The bug that makes threads slower than one thread

Cache coherence works at line granularity, not variable granularity. Eight int64 counters fit in one 64-byte line, so eight threads each incrementing their own counter are all writing to the same line. Every write invalidates the other seven cores' copies, and the line ping-pongs between cores over the interconnect. The variables are private, the contention is total. The fix is to pad each counter to its own cache line, which costs eight times the memory and can be worth it many times over. Look for alignas(64) in C++, @Contended in Java, CachePadded in Rust's crossbeam.

Prefetchers, TLBs and the other caches

Hardware does not wait passively for misses. Every modern core has prefetchers that watch the address stream and speculatively fetch lines they expect you to want. They reliably detect sequential forward and backward walks and simple constant strides within a page. They cannot follow a linked list, because the next address is not known until the current node has arrived.

This is the real reason a linked list loses to an array so badly. It is not only that nodes are scattered; it is that each node's address depends on the previous load, so the misses are serialised. A hundred sequential array misses can be in flight at once; a hundred linked-list misses happen strictly one after another, each paying the full DRAM latency. That effect is called a dependent load chain or pointer chasing, and it is why an array-backed structure often beats a pointer-based one even when the pointer-based one has better asymptotic complexity at small sizes.

The TLB

Virtual addresses have to be translated to physical ones, and the page table that does it lives in memory. To avoid a memory access per memory access, translations are cached in the translation lookaside buffer, a small fully associative cache of typically a few hundred to a couple of thousand entries. With 4 KiB pages, 1,536 entries covers about 6 MiB of address space.

Exceed that and you start taking TLB misses, which cost a page-table walk — several dependent memory accesses — on top of any data cache miss. Workloads with large, randomly accessed data structures often spend more time on TLB misses than data misses, which is what huge pages (2 MiB instead of 4 KiB) exist to fix: the same TLB then covers 512 times as much memory.

Other caches with the same shape

The pattern generalises. Branch target buffers cache jump destinations. The micro-op cache stores already-decoded instructions. Your database has a buffer pool; your web app has Redis in front of Postgres; your browser has an HTTP cache; a CDN is a cache with geography. All of them have a line size, an associativity, a replacement policy and the three Cs. Chapter 23 works through replacement policies in general, and everything there applies here.

What to do about it

Cache-conscious programming is a small number of habits, applied only where a profiler says it matters.

  1. Prefer contiguous storage. A vector of values beats a list of pointers to values for almost any traversal-heavy workload, and usually beats it for insertion too until the sizes get large.
  2. Walk memory in the order it is laid out. Inner loop over the last index in row-major languages. This is the single highest-value rule.
  3. Block or tile large computations so the working set of each block fits in cache. Matrix multiply goes from O(n³) memory traffic to O(n³/√C) with tiling, and the speed-up is several-fold on real hardware.
  4. Shrink your data. An int32 instead of int64 halves the traffic. So does removing a field you never read in the hot loop.
  5. Order struct fields large to small and check the actual size rather than assuming.
  6. Pad shared-but-independent data to cache lines when threads write to it.
  7. Avoid power-of-two strides in multi-dimensional arrays. Padding a row from 1024 to 1032 elements can eliminate a set of conflict misses entirely.
  8. Measure, do not guess. perf stat on Linux reports cache misses and references directly; cachegrind simulates; Instruments and VTune do the same on other platforms.
The complexity table lies about constants

Big-O counts operations and treats every memory access as equal. On real hardware an access can cost 4 cycles or 300, a difference of nearly two orders of magnitude that the notation cannot see. This is why a linear scan of a sorted array often beats a binary search tree for a few thousand elements, why std::vector usually beats std::list, and why B-trees with hundreds of children per node beat binary search trees on disk. Chapter 10 explains what asymptotic notation does say; this chapter is the reason you cannot stop there.

Check yourself

A 64 KiB, 4-way set-associative cache has 64-byte lines. How many sets, and which address bits select one?

65536 ÷ 64 = 1024 lines; 1024 ÷ 4 ways = 256 sets. The low 6 bits are the byte offset within the line (26 = 64), the next 8 bits are the set index (28 = 256), and everything above is the tag. Addresses 256 × 64 = 16,384 bytes apart therefore land in the same set, so a stride of 16 KiB will use 4 lines out of 1024.

Why does the hit rate stop getting worse once the stride exceeds the line size?

Because the worst case is already reached. At stride = line size ÷ element size, each access lands in a different line and no line is ever reused, so the hit rate is zero and one full line is fetched per useful element. Larger strides cannot waste more than a whole line per access. Confirm it in demo 1: with 8-byte doubles and 64-byte lines, strides 8, 16, 64 and 512 all report 0% and a waste factor of exactly 8.

A loop over a 512 × 512 double matrix runs eight times slower one way round than the other, with identical arithmetic. Explain in terms of bytes.

Row-major storage puts a[i][0..511] contiguously. Iterating j in the inner loop walks with stride 8 bytes, so each 64-byte line serves eight accesses: 262,144 accesses cause 32,768 misses and 2 MiB of traffic. Iterating i in the inner loop walks with stride 512 × 8 = 4,096 bytes, so every access is a new line: 262,144 misses and 16 MiB of traffic. Eight times the bytes moved for the same additions. The 4,096-byte stride is also exactly one way-slice on a 32 KiB 8-way cache, so the misses are conflict misses on top of everything else.

How would you tell a conflict miss from a capacity miss, and why does the distinction matter?

Run the same address stream through a fully associative cache of identical capacity. If that cache would have hit, the miss was caused by the mapping, not the size, so it is a conflict miss. If it would also have missed, the working set is genuinely too large and the miss is a capacity miss. It matters because the fixes are different: conflict misses go away with more associativity or by changing addresses (padding an array, offsetting an allocation), while capacity misses only go away if you touch less data — blocking, tiling, or smaller types.

Eight threads each increment their own private counter and the program runs slower than a single thread doing all eight. What is happening?

False sharing. Eight int64 counters occupy 64 bytes, which is one cache line. Coherence operates on lines, so when core 0 writes its counter it invalidates that line in the other seven cores' caches, and they must re-fetch it before their next write. The line ping-pongs across the interconnect on every increment. Nothing is logically shared and every access still contends. Padding each counter to its own 64-byte line fixes it at eight times the memory, which is almost always the right trade.

Why is a linked list so much worse than an array here, beyond just poor spatial locality?

Because the misses are serialised. To find node n + 1 you must first have node n in hand, so each miss cannot begin until the previous one has completed and you pay the full latency every time. An array walk has no such dependency: the prefetcher recognises the stride and issues many fetches concurrently, and the core's memory-level parallelism overlaps them. Ten misses on an array can cost barely more than one; ten misses down a list cost ten. That is why the practical break-even point between contiguous and pointer-based structures sits at much larger sizes than complexity analysis suggests.

Your struct is {char flag; double value; char kind;} and you have ten million of them. What would you change, and what does it buy?

Reorder to put the double first: {double value; char flag; char kind;}. The original needs 7 bytes of padding after flag to align value, then 7 more at the end to keep the struct's alignment, giving 24 bytes. The reordered version needs only 6 bytes of trailing padding, giving 16. Across ten million elements that is 240 MB versus 160 MB — 80 MB saved, and a third less memory traffic for any traversal. If the hot loop only reads value, going further to a struct-of-arrays layout would cut the traffic again by another third.

Ten things to carry forward

  1. Fast memory is small, large memory is slow, and the hierarchy is a stack of compromises rather than a solution.
  2. DRAM is roughly 80× an L1 hit; an SSD is another 1,250× beyond that. Moving work up one level beats almost any instruction-level optimisation.
  3. Caches store 64-byte lines, never single bytes. Every miss fetches a whole line whether you use it or not.
  4. An address decodes into tag, set index and offset, so lookup is a fixed amount of shifting, masking and parallel comparison.
  5. The stride cliff is at line size ÷ element size. Past that point the hit rate is zero and cannot get worse.
  6. Row-major versus column-major is an eight-times traffic difference on a matrix of doubles, for identical arithmetic.
  7. Misses are compulsory, capacity or conflict, and each has a different fix: prefetch, shrink the working set, or change the addresses.
  8. Layout is a performance decision. Array-of-structs versus struct-of-arrays, field order, and element width all change how many useful bytes ride in each line.
  9. False sharing makes private data contended, because coherence works on lines and not on variables.
  10. Prefetchers follow strides but cannot follow pointers, so pointer chasing serialises its misses and pays full latency on every one.
