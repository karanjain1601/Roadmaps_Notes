Design patterns and UML

A stable concrete class is the worst position in a design: everything depends on it and it cannot change. That is not an opinion — it is a distance of exactly 1.0 from Martin's main sequence, and dependency injection halves it. This chapter measures the claims it makes.

What a pattern is, and what it is not

A design pattern is a named solution to a recurring design problem, together with the trade-offs it makes. The name is a large part of the value: "use an observer here" communicates a structure, its costs and its failure modes in three words.

What they are for

Shared vocabulary, and a record of solutions that have already been tried. The GoF book documented what good designers were already doing, rather than inventing anything.

What they are not

Goals. A design is not better for containing more patterns. Every pattern adds indirection, and indirection is a cost paid immediately against a benefit that may never arrive.

A pattern is a workaround for a missing language feature

This is Peter Norvig's observation, and it is worth taking seriously: 16 of the 23 GoF patterns are simpler or invisible in a language with first-class functions. Strategy is a function parameter. Command is a closure. Iterator is a generator. Template Method is a function taking callbacks. Factory Method is a function that returns an object. If you find yourself writing a class with one method to pass to another class, check whether your language already has the feature.

The organising question

Find what varies and encapsulate it.

That single line organises the whole catalogue better than the creational/structural/behavioural split does, because it maps a problem you have to a pattern rather than a pattern to a definition. Every pattern below is an answer to "this thing keeps changing, and I want the changes not to spread".

Two of these have important limits. Visitor makes adding operations easy and adding classes hard — every new type forces a change to every visitor — so it only pays when the hierarchy is genuinely stable. Dependency injection, measured

The claim is that depending on abstractions rather than concrete classes improves a design. That is testable, using Robert Martin's package metrics applied at class level.

Ce, efferent coupling
How many things this depends on. Outgoing arrows.
Ca, afferent coupling
How many things depend on this. Incoming arrows.
I = Ce/(Ca+Ce), instability
0 means nothing depends on you and everyone depends on it — hard to change. 1 means the reverse — easy to change.
A, abstractness
1 for an interface or abstract class, 0 for a concrete one.
D = |A + I − 1|, distance from the main sequence
The rule is that stable things should be abstract and unstable things should be concrete. D = 0 satisfies it; D = 1 is as wrong as possible.

The measurement on the default design: MySqlRepo has Ce = 0 and Ca = 1, so I = 0 — maximally stable — and it is a concrete class, so A = 0 and D = 1. That is the worst possible position: something depends on it, and it is a database detail that will certainly change.

Introduce Repository and Mailer interfaces and the picture changes in a specific way. OrderService no longer depends on MySqlRepo at all — the business logic has stopped knowing about the database. MySqlRepo gains an outgoing edge to the interface, so its I rises from 0 to 0.5 and its D halves from 1 to 0.5. The interfaces take over the stable position with I = 0 and A = 1, giving D = 0. Average distance across the whole design falls from 0.583 to 0.222.

The cost is real and lands in one place

Injection does not make dependencies disappear; it moves them. Controller's efferent coupling rose from 1 to 3, because something still has to construct the concrete classes and hand them over. That something is the composition root, and concentrating all the concrete knowledge there is the point — one place that knows what everything really is, and no other. A DI container automates the wiring; it does not remove the coupling, and a container is not required to do dependency injection.

The demo also reports dependency cycles, which no metric can excuse. A cycle means the classes cannot be understood, tested, compiled or deployed separately — they are one unit pretending to be several. The fix is always to extract an interface that one side owns and the other depends on, which is the same move as injection.

Two patterns not in the GoF book

Null Object

Instead of returning null and forcing every caller to check, return an object that implements the interface and does nothing. A NullLogger that discards, an empty collection instead of null. It removes an entire class of branches and an entire class of crashes.

Type Object

When you would otherwise write a subclass per kind — Goblin, Orc, Troll — make the kind a piece of data instead: one Monster class holding a MonsterType. New types become configuration rather than code, which is how every game and every rules engine handles this.

The five UML diagrams worth drawing

UML has fourteen diagram types. Five are used in practice, and none of them should be drawn to specification — the value is in the communication, not the notation.

Aggregation versus composition, concretely

A Playlist aggregates Songs: delete the playlist and the songs still exist. A House composes Rooms: demolish the house and the rooms go with it. The distinction matters because it decides cascade behaviour in your database, ownership in your memory model, and whether a delete is safe. If you cannot answer "does the part survive the whole?", you do not yet understand the relationship.

The realistic advice on UML is that a sequence diagram on a whiteboard, drawn to explain one interaction, is worth a great deal. A complete formal model of a system, maintained in a tool, is worth almost nothing — it goes stale immediately and nobody reads it. Draw the diagram, explain the thing, photograph it, and let the code be the specification.

Using patterns without overusing them

  1. Refactor to a pattern; do not design to one. Patterns are recognised in code that already has the problem, not imposed on code that might.
  2. Wait for the third case. Two implementations of something is a coincidence; three is a variation worth encapsulating.
  3. Check your language first. Strategy, Command, Iterator and Template Method are all one function in a language with closures.
  4. Name the pattern in the code. PricingStrategy, OrderStateMachine — the shared vocabulary only pays if it reaches the reader.
  5. Count the indirections you added. Every one is a jump the next reader has to follow, and a pattern that saves no change is pure cost.
  6. Depend on abstractions at boundaries, not everywhere. An interface with exactly one implementation and no prospect of a second is ceremony.
The failure mode is over-application

An abstract factory producing a builder that configures a strategy, for a system with one concrete case, is a real thing that gets written — usually by someone who has just read the book. It is worse than the naive version on every axis: harder to read, harder to change, and it has not bought flexibility because nobody knows which flexibility will be needed. The Design Patterns authors are on record that this was the main way their work was misused.

Check yourself

What single question organises the pattern catalogue best?

"What varies?" Every pattern is an answer to something that keeps changing and whose changes you want to contain. Varying algorithm gives Strategy, or Template Method if the skeleton is fixed, or State if the variation is driven by an internal mode. Varying construction gives the factories. Varying interface gives Adapter and Facade. This maps a problem you actually have onto a pattern; the creational/structural/behavioural split maps patterns onto definitions, which is only useful once you already know which pattern you want.

Why is a stable concrete class the worst place to be?

Because things depend on it and it cannot change without breaking them. Numerically, MySqlRepo in the demo has Ce = 0 and Ca = 1, so instability I = 0; it is concrete so abstractness A = 0; and D = |A + I − 1| = 1, the maximum possible distance from the main sequence. The rule the metric encodes is that stable things should be abstract and unstable things concrete. A database class is a detail that will certainly change, so having anything depend on it directly is the wrong shape.

What does dependency injection actually change, and what does it cost?

It changes who depends on the concrete class. Before, OrderService depended on MySqlRepo directly; after, it depends on a Repository interface and so does MySqlRepo — the arrow between business logic and detail is gone. MySqlRepo's D halves from 1 to 0.5, and the design's average D falls from 0.583 to 0.222. The cost is that Controller's efferent coupling rises from 1 to 3: something must still construct the concrete classes. Concentrating that in one composition root is the point, not an accident.

Norvig says 16 of 23 patterns are simpler in a language with first-class functions. Give three examples.

Strategy is a function passed as a parameter — no interface, no implementing classes, no factory to pick one. Command is a closure capturing its arguments, which can be stored in a list and invoked later. Iterator is a generator, and the language's for loop already consumes it. Template Method is a function taking callbacks for the varying steps. Factory Method is just a function that returns an object. The general test: if you are writing a class whose only purpose is to hold one method and be passed somewhere, your language may already have that.

Why does the demo hide Singleton unless you explicitly ask for a single instance?

Because it is the most reached-for and least defensible pattern in the catalogue. It is a global variable with a class around it: it hides dependencies, since a class using one does not declare it; it makes tests hard, since you cannot substitute it and state leaks between tests; and it creates initialisation-order and thread-safety problems. Wanting one instance is usually satisfied better by creating one instance at the composition root and injecting it, which gives the same singleness without the global. Several of the original authors have said they would drop it.

When is Visitor the right pattern, and when is it a trap?

Visitor makes adding operations cheap and adding types expensive: a new operation is one new visitor class, but a new type forces a change to every existing visitor. It is right when the hierarchy is genuinely stable and the operations keep growing — an AST with a fixed set of node kinds and an endless supply of analyses. It is a trap when types are added regularly, which is the common case in business software, because every new type triggers a change across the whole codebase. Ask which axis actually varies before choosing it.

Aggregation or composition: a playlist and its songs?

Aggregation — the hollow diamond. Deleting the playlist does not delete the songs, which exist independently and may appear in other playlists. Composition, the filled diamond, is for parts that die with the whole: a house and its rooms, an order and its line items. The distinction is not decoration. It decides whether your foreign key cascades on delete, who owns the memory, and whether a deletion is safe. If you cannot say whether the part survives the whole, you have not finished modelling the relationship.

Ten things to carry forward

  1. A pattern is a named solution with known trade-offs, and the name is most of the value.
  2. "What varies?" organises the catalogue far better than the creational/structural/behavioural split.
  3. Many patterns are missing language features. Strategy, Command, Iterator and Template Method are one function each with closures.
  4. Instability is Ce/(Ca+Ce), and the rule is that stable things should be abstract.
  5. A stable concrete class scores D = 1, the worst possible distance from the main sequence.
  6. Injection moves dependencies, it does not remove them — average D fell from 0.583 to 0.222 while the composition root's coupling tripled.
  7. A dependency cycle has no defence. The classes cannot be understood, tested or deployed separately.
  8. Null Object and Type Object are not in the book and are worth more than several patterns that are.
  9. Five UML diagrams matter, and the sequence diagram matters most.
  10. Refactor to a pattern, do not design to one, and wait for the third case before generalising.
