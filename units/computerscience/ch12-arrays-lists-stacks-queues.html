Chapter 12 · Data structures

Arrays, lists, stacks and queues

There are exactly two ways to store a sequence: put the elements next to each other, or store the address of the next one alongside each. Every list-like structure in every language is one of those two, and the complexity table that compares them leaves out the thing that usually decides.

Contiguous storage

An array is a block of memory holding equally sized elements back to back. That single property gives it its defining feature: the address of element i is base + i × size, one multiplication and one addition, so indexing is Θ(1) regardless of i or of the array's length.

It also gives the array its limitations. The size must be known when the block is allocated. Inserting in the middle means shifting everything after the insertion point. And the whole thing has to be one contiguous region, so allocating a very large array can fail even when plenty of total memory is free — chapter 9's external fragmentation, in the form you meet it.

An array of pointers is not an array

In Java, Integer[] and ArrayList<Integer> store references, so the values themselves are scattered on the heap and traversal chases a pointer per element. int[] stores the values inline. Python lists are always arrays of pointers; NumPy arrays are not, which is most of why NumPy is faster. The performance argument for contiguity only applies when the data is contiguous, not merely the handles to it.

Dynamic arrays

Almost nobody uses raw arrays directly. What you actually use is a dynamic array — vector, ArrayList, list, Vec, slice — which wraps a fixed block plus a length and reallocates when it fills.

Chapter 10 did the analysis: with geometric growth, appending is Θ(1) amortised. Doubling from capacity 1 to hold 1,000 elements costs 10 reallocations and 1,023 element copies, an amortised 2.023 units of work per append, and 990 of those 1,000 appends cost exactly one. Growth factors trade copies against wasted capacity, with worst-case waste of (g−1)/g.

Reallocation invalidates everything

When a vector grows it allocates a new block and copies. Every pointer, reference and iterator into the old block is now dangling. In C++ this is undefined behaviour and a classic source of crashes: holding a reference to v[0] across a push_back is a bug even though the code looks obviously fine. Rust makes it a compile error via the borrow checker; Java and Python detect concurrent modification and throw. If you know the final size, reserve it up front — it eliminates the copies and the invalidation both.

Linked storage

A linked list stores each element in its own node along with the address of the next one. Nothing is contiguous, so nothing needs to move when the structure changes — but nothing can be indexed either, because the only way to reach element k is to follow k pointers.

Those byte counts are the first thing the complexity table hides. A doubly linked list of 32-bit integers spends 24 bytes per element against the array's 4 — six times the memory — and every one of those extra bytes has to travel through the cache alongside the data you wanted.

Where linked lists genuinely win

Not "insertion is O(1)", which is misleading, but three real cases. Splicing: moving a range from one list to another is O(1) with no copying, which is why LRU caches pair a hash map with a doubly linked list — you get a node pointer from the map and move it to the front in constant time. Stable addresses: nodes never move, so pointers into the structure stay valid across insertions, which a vector cannot promise. No reallocation stalls: useful in real-time code where a single Θ(n) copy would blow a deadline. Intrusive lists, where the links live inside the object, are used throughout the Linux kernel for exactly these reasons.

Read the fourth and fifth rows together. The list's famous O(1) insertion is only O(1) if you already hold a pointer to the position. Reaching that position by index costs Θ(k), which is exactly the work the array was doing — so for "insert at index k" they are the same complexity class, and the array does its work as a contiguous memmove while the list does its work as a pointer chase.

With 100,000 int32 values, the array traversal takes 6,250 misses — one per 16 elements, since 16 fit in a 64-byte line — for a hit rate of 93.75%. A contiguous singly linked list of 16-byte nodes takes 25,000, four times as many, because only four nodes fit per line and each node is read twice. Scatter the nodes across the heap, which is what a real allocator does after any churn, and it becomes 112,500 misses — 18 times the array. That is slightly more than one miss per node, because an 8-byte-aligned 16-byte node straddles a cache-line boundary one time in eight and costs two.

Chapter 5 explained the other half of why that gap is worse than it looks. Array misses are independent, so the prefetcher issues many concurrently and the core overlaps them. List misses are serialised — the address of node i+1 is inside node i, so nothing can start until the previous load lands. Sixteen times the misses, each one paying full latency instead of being overlapped.

The practical rule

Use a dynamic array by default. Reach for a linked list when you need stable addresses across insertion, O(1) splicing of ranges, or a node you already hold a pointer to. Bjarne Stroustrup's much-repeated demonstration is that even for the operation lists should win — insert into a sorted sequence, requiring a linear search and then an insertion — the vector beats the list at every size he tested, because the linear search dominates and the vector does it 16 elements per cache line while the list does it one node per miss.

Stacks and queues are interfaces, not structures

A stack and a queue are abstract data types: a set of operations with defined behaviour, saying nothing about implementation. Both can be built on an array or a list, and the choice is invisible to the caller.

Stack — LIFO

push, pop, peek, isEmpty. Last in, first out. On a dynamic array, push and pop at the end so nothing shifts.

Queue — FIFO

enqueue, dequeue, front, isEmpty. First in, first out. On a plain array this is the trap in the next section.

Stacks appear everywhere once you look: the call stack from chapter 11, undo history, expression evaluation and the shunting-yard algorithm, matching brackets, depth-first search, and backtracking, where the stack holds precisely the decisions you need to undo. Queues appear in breadth-first search, task and message queues, request buffers, and any producer-consumer handoff.

The naive array queue is quadratic

Enqueue by appending and dequeue by removing element 0, and each dequeue shifts every remaining element down one. Processing n items costs Θ(n²). This is a real and common bug: list.pop(0) in Python and array.shift() in JavaScript are both Θ(n), and a work queue written that way collapses under load while looking perfectly reasonable. Python's answer is collections.deque; the general answer is the next section.

Ring buffers and deques

A ring buffer fixes the queue problem by never moving the data. Keep a fixed array plus a head index and a count, and let both ends wrap around modulo the capacity. Every operation is Θ(1) and the memory is one contiguous block, so it keeps the array's cache behaviour.

The elements moved counter stays at zero no matter how many operations you perform. That is the entire point: an array-backed queue that removes from the front moves Θ(n) elements per dequeue, and the ring buffer moves none, by moving the indices instead.

Notice what happens when head and tail coincide. An empty buffer has head equal to tail; so does a completely full one. The indices alone cannot tell them apart, which is why this implementation keeps an explicit count. The alternative used in hardware and in lock-free designs is to leave one slot permanently empty, so full means "tail is one behind head" — it wastes a slot and buys you an implementation with two variables instead of three, which matters when those variables have to be updated atomically.

A deque — double-ended queue — supports push and pop at both ends in Θ(1). A ring buffer is one way to build one; the other is a list of fixed-size chunks, which is what C++'s std::deque and Python's collections.deque do. The chunked version gives up contiguity, so indexing costs two lookups instead of one, but it grows without ever copying the elements and it keeps stable references, which the ring buffer cannot promise across a resize.

A trick worth knowing

When you need O(1) removal from the middle and do not care about order, swap the element with the last one and shrink by one. That turns a Θ(n) shift into a single move while keeping everything contiguous. It is standard in entity systems, particle simulations and free-list management, and it is often the right answer when someone reaches for a linked list.

Check yourself

Why is array indexing Θ(1) while list indexing is Θ(k)?

Because an array's elements are equally sized and adjacent, so the address of element k is base + k × size — arithmetic the CPU does in one instruction, independent of k. A list's nodes are at unrelated addresses, and the only place the address of node k is recorded is inside node k−1, so you must follow the chain. The array is buying random access with the requirement that everything be contiguous and the same size.

"Insertion into a linked list is O(1)." When is this claim misleading?

Whenever you have to find the position first. Insertion given a pointer to the node is genuinely O(1); insertion at index k is O(k) because reaching the node dominates. So for "insert at index k" the array (Θ(n−k) to shift) and the list (Θ(k) to walk) are in the same class, and the array does its work as a contiguous memmove at many bytes per cycle while the list does its work as dependent pointer loads. The claim is only useful when a pointer to the position arrives from somewhere else — which is exactly what an LRU cache's hash map provides.

Traversing 100,000 int32 values: the array takes 6,250 cache misses and a scattered list takes 112,500. Where does the factor of 18 come from?

A 64-byte cache line holds 16 int32 values, so the array pays one miss and gets 15 free hits — 100,000 ÷ 16 = 6,250. A scattered list puts each node on its own line, so every element costs at least one miss, and an 8-byte-aligned 16-byte node crosses a line boundary one time in eight, costing two: 1.125 misses per node, or 112,500. The gap is worse in wall-clock terms than 16× suggests, because array misses are independent and can be prefetched and overlapped, while list misses are serialised: the address of the next node is inside the current one, so each miss pays full DRAM latency in sequence.

A doubly linked list of 32-bit integers uses how much memory per element, and why does that matter beyond the byte count?

24 bytes: 4 for the value, 4 of alignment padding, and 8 each for two 64-bit pointers — six times the array's 4 bytes, before allocator overhead. It matters because all 24 bytes travel through the cache. Fewer elements fit per line, fewer fit in L1, and the working set crosses the cache size six times sooner. On the traversal in demo 1, that is the difference between a structure that fits in L2 and one that does not.

Your job queue uses list.pop(0) in Python and gets slower as the backlog grows. Why, and what fixes it?

pop(0) removes the first element of a contiguous array, so every remaining element shifts down one: Θ(n) per dequeue and Θ(n²) to drain a queue of n. It looks fine at ten items and collapses at ten thousand. Use collections.deque, which is a chunked doubly linked structure with O(1) at both ends, or a ring buffer. The same trap exists as Array.shift() in JavaScript and List.remove(0) in Java.

In a ring buffer, an empty buffer and a full one have head equal to tail. How is that resolved?

Two standard options. Keep an explicit count alongside head, which is what demo 2 does — full is count == capacity, empty is count == 0, and the capacity is fully usable. Or leave one slot permanently empty so full means (tail + 1) % cap == head, wasting a slot but needing only two variables. The second is preferred in hardware and lock-free designs, where fewer variables means fewer things to update atomically.

You need to remove elements from the middle of a collection in O(1), order does not matter. What would you do?

Swap-and-pop on a dynamic array: overwrite the element to remove with the last element, then shrink the length by one. One move instead of a Θ(n) shift, and the storage stays contiguous with all the cache benefits intact. The cost is that order is destroyed and any index you handed out for the last element is now wrong — so pair it with a map from stable IDs to current indices if callers hold references. This is standard in entity-component systems and particle simulations, and it is usually a better answer than the linked list people reach for.

Ten things to carry forward

  1. There are two ways to store a sequence: adjacent in memory, or linked by address. Everything else is a variation.
  2. Contiguity buys Θ(1) indexing through address arithmetic, and costs you shifting, a fixed size and a contiguous allocation.
  3. Dynamic arrays make appending Θ(1) amortised, and reallocation invalidates every pointer into the old block.
  4. A doubly linked node costs 24 bytes to hold a 4-byte integer — six times the memory, all of it moving through the cache.
  5. The list's O(1) insertion assumes you already hold the pointer. By index, both structures are in the same complexity class.
  6. Cache behaviour usually decides. 6,250 misses versus 112,500 for the same 100,000 values, and list misses are serialised while array misses overlap.
  7. Lists win on splicing, stable addresses and predictable latency, not on insertion complexity.
  8. Stacks and queues are interfaces, implementable on either storage, and the choice is invisible to the caller.
  9. An array-backed queue that shifts on dequeue is quadratic. A ring buffer moves indices instead of elements and moves nothing.
  10. Swap-and-pop gives O(1) middle removal when order does not matter, and is usually the right answer instead of a linked list.
