Chapter 6 · The operating system

Processes, threads and forking

A program is a file. A process is that file plus an address space, a set of open handles, and permission to run. The operating system's central trick is convincing every process that it owns the whole machine, and fork is the strangest expression of it: a system call that returns twice.

What a process actually is

A process is an address space plus a thread of execution plus the kernel's bookkeeping about both. Take away any one of the three and you have something else: a file, a thread, or a zombie.

The address space is the part people underestimate. Every process sees memory starting at address zero and running to the top of the virtual range, and every process sees a different physical machine behind those identical addresses. Two processes can both hold a pointer to 0x7fff0000 and be looking at completely unrelated bytes. Chapter 9 covers the page tables that make this work; what matters here is the consequence: a process cannot corrupt another process's memory even if it tries, because it has no way to name it.

The process control block

Everything the kernel knows about a process lives in one structure, called the process control block or, on Linux, task_struct. It holds the process ID and parent ID, the saved register state for when the process is not running, a pointer to the page tables, the file descriptor table, the current working directory, the user and group IDs, signal handlers and the signal mask, resource limits and accounting, and the exit status. Creating a process means allocating one of these and filling it in; a context switch means saving into one and restoring from another.

Program versus process versus thread

A program is a passive file on disk. A process is a running instance of one, with its own address space. A thread is one flow of execution inside a process; a process has at least one and may have thousands, all sharing that address space. Running the same program twice gives you two processes with no shared memory. Starting two threads gives you one process with everything shared except the stacks.

fork, exec and the call that returns twice

Unix does not have a "create a process running this program" call. It has two calls that compose: fork duplicates the current process, and exec replaces the current process's image with a different program. Everything from a shell running a command to a web server spawning workers is those two, in that order.

the shape of every process creation on Unix
pid_t pid = fork();

if (pid < 0) {
    // fork failed — out of memory or process limit reached
} else if (pid == 0) {
    // we are the CHILD. fork() returned 0 here.
    execvp("ls", args);      // never returns if it succeeds
    _exit(127);                // only reached if exec failed
} else {
    // we are the PARENT. fork() returned the child's pid.
    int status;
    waitpid(pid, &status, 0);  // reap the child, collect its exit code
}

One call, two returns, in two different processes. The child is a near-exact duplicate: same code, same variables with the same values, same open file descriptors, same program counter pointing at the instruction after fork. The only observable differences are the return value, the process ID, the parent ID, and a few counters that are reset.

What the child inherits, and what it does not

Copied or shared

The entire address space (copy-on-write), all open file descriptors including their shared file offsets, the current working directory, environment variables, user and group IDs, signal dispositions, resource limits.

Reset or not inherited

A new process ID and parent ID. Pending signals are cleared. File locks are not inherited. CPU time counters restart at zero. And critically, only the calling thread exists in the child — every other thread is gone.

The buffered printf trap

Compare the buffered and flushed programs. Both create four processes. The buffered one prints four lines from one printf that ran before any fork existed, because C's stdio buffer is part of the process's memory and gets duplicated along with everything else; each child later flushes its inherited copy at exit. Calling fflush first, or writing to a terminal where stdio is line-buffered, prints once. This is a real and frequently reported bug: output that appears once when run interactively and several times when piped to a file, because piping switches stdio from line buffering to full buffering.

The exec program shows the other half of the story. The child inherits the buffer, then exec replaces the entire process image and the buffer goes with it, so the duplicate never appears. That is one reason the fork-then-exec pattern rarely exhibits the bug, and why posix_spawn and vfork exist as shortcuts for the common case where you were going to exec immediately anyway.

Copy-on-write

Duplicating a process that is using four gigabytes ought to cost four gigabytes and a long pause. It does not, and the reason is that fork does not copy any of it.

Instead the kernel copies the page tables — which are small — and marks every writable page read-only in both processes, recording that the underlying physical frame now has two users. Both processes then run against the same physical memory. The moment either one writes to a page, the hardware raises a protection fault, the kernel notices the page is marked copy-on-write, allocates a fresh frame, copies 4 KiB into it, points the writer's page table at the copy, marks both writable again, and resumes the instruction. Neither process can tell any of this happened.

Immediately after the fork, virtual pages double to 128 while physical frames stay at 64. Write eight pages and physical rises to 72, not 128. Only if both sides eventually write every page does copy-on-write degenerate into a full copy, and by then the cost has at least been spread out instead of paid up front in one stall.

Why your monitoring tool is confused

This is exactly why the memory numbers in ps and top mislead. VSZ counts virtual pages and can be enormous and meaningless. RSS counts resident frames but charges every shared frame in full to every process, so summing RSS across a fork-heavy server double-counts badly. PSS divides each shared frame equally among its users and is the number that actually adds up. A pre-fork web server with a 500 MiB parent and 16 workers can show 8.5 GiB of total RSS while using well under 1 GiB.

Garbage collectors defeat copy-on-write

A tracing garbage collector walks the whole heap and often writes mark bits into object headers, which touches nearly every page and forces nearly every page to be copied. Pre-fork servers in Ruby and Python spent years fighting this. The fixes were to move mark bits out of objects into a separate bitmap, and to run a full collection and compaction before forking so the shared pages are as settled as possible.

Threads: everything shared but the stack

A thread is a second program counter and stack inside an existing address space. Creating one is far cheaper than creating a process, because nothing has to be duplicated.

Signal handlers (the dispositions)Signal mask (which signals are blocked)
Current working directoryThread-local storage
User and group IDserrno
Resource limits and accountingScheduling priority and affinity

The left column is the reason threads are fast and the reason they are dangerous. Passing a pointer between threads costs nothing because both can dereference it. Two threads writing the same variable is a data race, and chapter 8 is entirely about controlling that.

errno has to be per-thread

The C library reports errors through a global called errno. If it were genuinely global, thread A could fail a system call and thread B could overwrite the code before A read it. Modern C libraries define errno as a macro that expands to a thread-local lookup, which is why you can no longer write extern int errno;. It is a small example of a general pattern: any interface with hidden global state has to be redesigned or made thread-local before it can be used concurrently. The same applies to strtok, gmtime and the whole family of functions with _r reentrant variants.

User threads, kernel threads and the models

1:1 — one kernel thread per user thread
What Linux (NPTL), Windows and macOS do. The kernel schedules each thread directly, so a blocking call blocks only that thread and threads can run on different cores. The cost is that each thread needs kernel resources and a full stack reservation, typically 8 MiB of virtual address space even though only a few kilobytes are resident.
N:1 — many user threads on one kernel thread
Green threads, scheduled entirely in userspace. Switching is very cheap, but one blocking system call stalls all of them and they cannot use more than one core. Early Java and Ruby did this.
M:N — many user threads multiplexed onto a pool of kernel threads
Go's goroutines, Erlang's processes, Rust's async tasks on a work-stealing runtime. You get cheap creation and cheap switching plus real parallelism, at the cost of a runtime that has to intercept blocking operations and reschedule around them. A goroutine starts with about 2 KiB of stack that grows on demand, which is why a Go program can hold a million of them.
Rough costs. Vary by kernel, hardware and load; the ratios are the point.

The indirect cost of a switch usually exceeds the direct one. Whichever thread runs next arrives to find the caches full of somebody else's data, so it takes hundreds of misses before it is back at full speed. That is why thread pools sized near the core count generally beat thread-per-request, and why a server with ten thousand threads can spend most of its time switching.

Lifecycle, zombies and orphans

A process moves between a small number of states, and the transitions are worth naming because monitoring tools report them directly.

                                        a lock, or a signal

  ps codes:  R running or ready   S interruptible sleep   D uninterruptible sleep

Two of these deserve attention.

Zombie (Z)
The process has exited but its parent has not called wait. The address space is gone; all that remains is the entry holding the exit status, because the parent may still want it. Zombies use almost no memory but they consume PID table entries, and a parent that never reaps in a loop will exhaust the table. The fix is to call waitpid, or to set SIGCHLD to SIG_IGN so the kernel reaps automatically.
Orphan
The parent exited first. The child is re-parented to init (PID 1) or to the nearest subreaper, which reaps it when it finishes. Orphans are harmless; this is also the mechanism daemons historically used to detach, by forking and letting the parent exit.
Uninterruptible sleep (D)
Blocked in the kernel in a way that cannot be interrupted, usually waiting on hardware. A process stuck in D state cannot be killed even with SIGKILL, because signals are delivered on the way back to userspace and it never gets there. A pile of D-state processes almost always means storage or a network filesystem is not responding.
PID 1 in a container

Inside a container your application is often PID 1, which inherits init's responsibility for reaping orphans — and most applications do not do it. Zombies accumulate. PID 1 also has special signal semantics: default signal handlers are not installed, so a SIGTERM from docker stop may be ignored entirely and the container gets killed ten seconds later instead of shutting down cleanly. The standard fixes are docker run --init, a small init such as tini or dumb-init, or handling SIGTERM and reaping children yourself.

The design most modern systems land on uses both: a small number of processes for isolation and fault containment, and threads or green threads inside each for concurrency. Chrome runs each site in its own process precisely so a renderer bug cannot read another site's memory; PostgreSQL uses one process per connection for robustness; nginx runs one worker process per core and handles thousands of connections in each with an event loop rather than threads.

fork in a multithreaded program is close to unusable

Only the calling thread survives into the child. Any lock held by another thread at the moment of the fork stays locked forever in the child, because the thread that would have released it does not exist. If that lock happens to be the allocator's — and it very often is, since every thread calls malloc — the child deadlocks the first time it allocates, which may be inside a library function you did not know allocates. POSIX's rule is that between fork and exec in a multithreaded process you may only call async-signal-safe functions, a list that excludes malloc, printf and almost everything else. Use posix_spawn, or fork before you start any threads.

Check yourself

How many processes does fork(); fork(); fork(); create, and how many exist afterwards?

Each fork doubles the population, so after three you have 2³ = 8 processes in total, of which 7 were created and one is the original. A single printf after them prints eight lines. The general rule is 2n for n unconditional sequential forks; guarding a fork with if (pid == 0) so only the child forks again gives you n + 1 instead, which the demo's third preset shows landing at 3.

A program prints one line when run in a terminal and four lines when its output is redirected to a file. Explain.

The printf happens before two forks and the output is still sitting in the stdio buffer. When stdout is a terminal, stdio is line-buffered, so the newline flushes it immediately and only one copy is ever written. When stdout is a file or pipe, stdio switches to full buffering, the text stays in the process's memory, fork duplicates that memory along with everything else, and each of the four processes flushes its own inherited copy at exit. The fix is fflush(stdout) before forking, or writing with write(), which is unbuffered.

Why does forking a process using 4 GiB not take 4 GiB or a long time?

Copy-on-write. The kernel duplicates the page tables, which are a few megabytes at most, marks every writable page read-only in both processes, and records that each physical frame now has two users. No data is copied. A frame is only duplicated when one side writes to it, at which point a protection fault triggers a 4 KiB copy. If the child immediately calls exec, essentially nothing is ever copied, which is why the fork-then-exec pattern is cheap despite looking wasteful.

Summing RSS across a pre-fork server's workers gives a number larger than the machine's memory. What is wrong?

RSS charges every resident frame in full to every process that maps it, so a copy-on-write frame shared by 17 processes is counted 17 times. Summing RSS across related processes therefore double-counts all the shared text, libraries and un-written heap. Use PSS, which splits each shared frame equally among its users and does sum correctly, or read smaps_rollup. VSZ is worse still — it counts address space that may never have been touched.

Two threads both call a function with a local variable and a global counter. Which is safe?

The local is safe: locals live on the stack and each thread has its own, so the two calls cannot see each other's copy. The global is not: it lives in the shared data segment, both threads have the same address for it, and an increment is a read-modify-write that can interleave. Note the boundary is storage location, not syntax — a local static variable, or a local whose address has been handed to another thread, is just as shared as a global.

Your service leaks PIDs until the machine cannot start new processes, but memory usage is flat. What is happening?

Zombie processes. Children have exited but the parent never calls wait or waitpid, so the kernel keeps an entry per child holding the exit status. Zombies hold almost no memory, which is why the memory graph looks fine, but each one occupies a PID and the table is finite. Fix it by reaping — call waitpid(-1, &st, WNOHANG) in a loop from a SIGCHLD handler, or set SIGCHLD to SIG_IGN and let the kernel do it. In a container, also check whether your app is PID 1 and therefore responsible for reaping orphans it never created.

Why is calling fork from a multithreaded program considered dangerous?

Because only the calling thread exists in the child, but the entire memory image is copied — including any lock that another thread was holding at that instant. That lock will never be released, since its owner does not exist in the child. The allocator's lock is the usual victim, so the child hangs the first time anything calls malloc, which may be deep inside a library. POSIX restricts the child to async-signal-safe functions between fork and exec, a list that excludes almost everything useful. Prefer posix_spawn, or do all your forking before any threads are started.

Ten things to carry forward

  1. A process is an address space plus execution state plus kernel bookkeeping. Isolation is a property of the address space, not of good behaviour.
  2. Every process sees the same virtual addresses and different physical memory behind them, which is why one cannot name another's data.
  3. fork returns twice: zero in the child, the child's PID in the parent, and −1 on failure. exec replaces the image and does not return.
  4. n sequential forks make 2n processes. Guard the recursive one and it becomes n + 1.
  5. The stdio buffer is memory, so fork duplicates it. One printf can produce many lines when output is redirected.
  6. Copy-on-write makes fork cheap by sharing frames read-only and copying a page only when someone writes to it.
  7. RSS double-counts shared frames; PSS does not. Memory numbers across related processes need the right metric.
  8. Threads share everything but the stack, registers, TLS, errno and the signal mask. That is both the speed and the danger.
  9. A context switch costs more indirectly than directly, because the new thread arrives to cold caches.
  10. Zombies hold PIDs, not memory, and orphans are re-parented to init. In a container your app is often PID 1 and inherits that duty.
