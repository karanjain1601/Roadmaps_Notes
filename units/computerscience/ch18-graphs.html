Graphs: representation and traversal

Remove the rule that every node has one parent and a tree becomes a graph — which can then model roads, dependencies, friendships, web links, git history and every state machine you will ever write. Two representations and two traversals cover most of what you need.

Terminology worth being precise about

A graph is a set of vertices and a set of edges joining them. Conventionally n or V is the vertex count and m or E the edge count, and complexity is quoted in both because they vary independently.

Directed or undirected
An edge either points one way (a Twitter follow, a build dependency) or both (a friendship, a two-way road). Almost every algorithm behaves differently on the two, and the difference is the source of a specific bug in section five.
Weighted or unweighted
Edges may carry a cost. Unweighted shortest paths are BFS; weighted ones need chapter 21.
Degree
The number of edges at a vertex; in-degree and out-degree for directed graphs. The handshake lemma: the degrees sum to exactly 2m, because every edge contributes one to each endpoint.
Path, cycle, connectivity
A path visits distinct vertices along edges; a cycle returns to its start. An undirected graph is connected if a path exists between every pair. A directed graph is strongly connected if that holds respecting direction, and weakly connected if it holds when you ignore direction.
Sparse or dense
m can be anywhere from 0 to n(n−1)/2 for a simple undirected graph. Sparse means m is closer to n; dense means closer to n². Nearly every real graph is sparse, which decides the next section.
DAG
A directed acyclic graph. Dependencies, schedules, build systems, git history, spreadsheet formulas and neural network architectures are all DAGs, and being acyclic is exactly what makes them orderable.
Trees are a special case

A tree is a connected undirected graph with no cycles, and it has exactly n−1 edges. Add any edge and you create exactly one cycle; remove any edge and it splits into two components. Everything from chapters 14 to 16 is a graph algorithm restricted to that case, which is why they could assume a single parent and no revisiting.

Adjacency matrix or adjacency list

Adjacency matrix

An n × n grid where cell (u, v) says whether the edge exists. Θ(n²) space regardless of how many edges there are, Θ(1) to test one edge, Θ(n) to list a vertex's neighbours.

Adjacency list

An array of n lists, each holding a vertex's neighbours. Θ(n + m) space, Θ(degree) to test an edge or list neighbours.

The default is a plausible social graph: 10,000 vertices and 50,000 edges, a density of 0.1%. A one-byte-per-cell matrix takes 100 MB and a bit-packed one takes 12.5 MB; the adjacency list takes 880 KB. Iterating every edge touches 100 million matrix cells against 60,000 list entries — 1,667 times less work for exactly the same traversal.

The crossover, found by searching for the edge count at which the list stops being smaller than a bit-packed matrix, lands at about 1.5% density for graphs of this size. Almost nothing real is that dense: a social network has an average degree in the hundreds against millions of users, the web graph averages tens of links per page, and a road network has a degree of about four.

Use a matrix anyway when…

The graph is genuinely dense, or small enough that n² fits comfortably; you need Θ(1) edge tests in a tight loop; or the algorithm is expressed as matrix arithmetic. Floyd-Warshall all-pairs shortest paths is Θ(n³) either way and is far simpler on a matrix, and adjacency matrices raised to the kth power count walks of length k, which is a genuinely useful trick. For everything else, use a list — and for the very largest graphs use compressed sparse row: two flat arrays, one of neighbours and one of offsets into it, which is an adjacency list with perfect locality and no pointers.

Two traversals, one difference

Both visit every reachable vertex exactly once, both cost Θ(n + m) with an adjacency list, and the code is identical except for one line.

the whole difference is queue versus stack
traverse(start):
  seen = {start}
  frontier = [start]
  while (frontier not empty) {
      u = frontier.removeFirst()     // QUEUE  -> breadth first
      u = frontier.removeLast()      // STACK  -> depth first
      visit(u)
      for (v of neighbours(u))
          if (v not in seen) { seen.add(v); frontier.push(v) }
  }
Mark when you enqueue, not when you dequeue

If a vertex is only marked seen when it comes off the queue, it can be pushed several times before that happens — once per incoming edge. The queue then grows to Θ(m) instead of Θ(n), and on a dense graph that is the difference between working and running out of memory. Mark at push time.

What BFS gives you

Because BFS expands vertices in order of distance from the source, the first time it reaches a vertex it has done so along a shortest path. On the default graph, BFS from 0 gives distances 0 1 1 2 3 4 4 and vertex 7 stays at −1 because nothing reaches it. Recording each vertex's parent as you go builds a shortest-path tree, and following parents backwards from any vertex reconstructs the route.

That property is exactly what breaks once edges have weights, and it is worth being precise about why: BFS counts edges, not cost. A two-edge route can be more expensive than a five-edge one, and BFS will confidently return the two-edge one. Chapter 21 is about the fix.

What DFS gives you

DFS goes as deep as it can before backtracking, which produces something BFS does not: a pair of timestamps per vertex, discovery and finish. Those timestamps nest — one vertex's interval is either wholly inside another's or wholly disjoint — and that nesting is what lets DFS classify every edge.

Cycles, and the bug everyone writes

In a directed graph the test is clean: a back edge exists if and only if the graph has a cycle. Track three states — undiscovered, on the stack, finished — and an edge to a vertex that is on the stack closes a loop.

The undirected version needs one extra condition

Run that same code on an undirected graph and it reports a cycle in every graph with at least one edge, including a tree. The reason is that every undirected edge appears in both adjacency lists, so as soon as DFS steps from u to v it immediately sees v → u pointing back at an ancestor that is still on the stack. That is not a cycle; it is the edge you just arrived on. The fix is to pass the parent down and skip exactly one occurrence of it — one occurrence, not all, or a genuine multi-edge between two vertices would be missed too. This is a real bug that a naive test suite will not catch, because a graph with any actual cycle still answers correctly.

Try it in demo 2: load the tree preset and the cycle indicator says no; add one edge between two existing branches and it says yes. The same classification also explains a second fact worth knowing — in an undirected DFS there are no forward or cross edges at all. Every edge is a tree edge or a back edge, because an undirected edge to a finished vertex is simply the other view of an edge already recorded.

Topological sort

A DAG can be laid out in a line so every edge points forward. Two standard algorithms, both Θ(n + m):

DFS, reverse postorder

Run DFS and push each vertex onto a list when it finishes; reverse the list. A vertex finishes only after everything it points to has finished, so reversing puts it before them. Detecting a back edge along the way tells you no order exists.

Kahn's algorithm

Repeatedly take a vertex with in-degree 0, output it, and decrement its neighbours. If fewer than n vertices come out, the remainder is a cycle. This one is easy to parallelise and naturally reports which vertices are stuck.

They generally produce different valid orders — on the DAG preset, DFS gives 5 4 2 3 1 0 and Kahn gives 4 5 2 0 3 1, and both satisfy every dependency. A topological order is not unique unless the DAG happens to be a chain, which is why build systems can legitimately choose different orders on different runs.

This is the algorithm behind make, package managers resolving install order, spreadsheet recalculation, task schedulers, course prerequisites and instruction scheduling in a compiler. The failure message "circular dependency detected" is a back edge.

Components

Loop over the vertices; whenever you find one not yet visited, run a traversal from it and everything reached is one connected component. Θ(n + m) for the whole graph, because each vertex and edge is touched once in total, not once per component.

In a directed graph "connected" splits in two. Weakly connected ignores direction. Strongly connected requires a directed path both ways, and finding those components needs a cleverer algorithm — Kosaraju's runs DFS twice, once on the graph and once on the reversed graph, and Tarjan's does it in a single pass. Both are Θ(n + m).

Contracting each strongly connected component to a single vertex always produces a DAG, called the condensation. That is a genuinely useful move: it turns any directed graph into one you can topologically order, and it is how a compiler handles mutually recursive functions or a package manager handles a dependency cycle it is willing to treat as one unit.

Modelling things as graphs

The hard part is usually not the algorithm but noticing that a problem is a graph problem at all. Two habits help.

Look for the implicit graph. A maze is a graph whose vertices are cells and whose edges are open walls. A puzzle is a graph whose vertices are states and whose edges are legal moves — BFS then finds the shortest solution, and it never needs the graph to exist in memory, only a function that produces a state's neighbours. Word ladders, sliding puzzles, git commit ancestry and regular-expression matching all have this shape.

Check whether the direction and weights match reality. Modelling a one-way street as an undirected edge, or an unweighted friendship graph when the strength of ties is the thing you care about, is where most graph modelling goes wrong — well before any algorithm runs.

A checklist for graph problems

Directed or undirected? Weighted or not? Can there be self-loops or parallel edges? Is it connected, or must you handle multiple components? Is it acyclic? Is it sparse? Those six answers select the representation and eliminate most of the candidate algorithms before you write a line.

Check yourself

10,000 vertices, 50,000 edges. Matrix or list, and by how much?

List, by two orders of magnitude. A one-byte-per-cell matrix is 100 MB and a bit-packed one 12.5 MB; the adjacency list is 880 KB. The density is 0.1%, so 99.9% of the matrix is zeros. Traversal is worse still: iterating every edge touches 100 million matrix cells against 60,000 list entries, 1,667 times the work. The crossover where a list stops being smaller sits at about 1.5% density, and almost no real graph reaches it.

Why does BFS find shortest paths in an unweighted graph, and why does it stop working with weights?

BFS expands vertices strictly in order of edge count from the source, so the first time it reaches a vertex it cannot have taken a longer route — everything at distance k is finished before anything at k+1 begins. That argument depends entirely on every edge costing the same. Add weights and a two-edge route can cost more than a five-edge one, and BFS will return the two-edge one because it counts hops. Dijkstra fixes it by expanding in order of accumulated cost rather than hop count, which is chapter 21.

Why must a vertex be marked as seen when it is pushed rather than when it is popped?

Because between being pushed and being popped, every other neighbour that points at it will also push it. Mark on pop and the frontier grows to Θ(m) rather than Θ(n) — on a dense graph, the difference between a queue of thousands and one of millions. The vertex would also be visited more than once, so any per-visit work is repeated. Mark at push, and each vertex enters the frontier exactly once.

Your cycle detector reports a cycle in a tree. What is wrong?

You are running the directed test on an undirected graph. Every undirected edge appears in both adjacency lists, so the moment DFS steps from u to v it sees v → u pointing at an ancestor still on the stack and calls it a back edge — but that is the edge it just arrived on. Pass the parent down and skip it. Skip exactly one occurrence, not every occurrence, or a genuine parallel edge between the same two vertices would also be missed. The bug is easy to ship because any graph with a real cycle still answers correctly.

Two topological sorts of the same DAG give different orders. Is one wrong?

No. A topological order is only unique when the DAG is a single chain; otherwise any two vertices with no path between them may appear in either order. On the demo's DAG, DFS reverse postorder gives 5 4 2 3 1 0 and Kahn's algorithm gives 4 5 2 0 3 1, and both satisfy every edge. Validate by checking that every edge points forward in the order, not by comparing against a reference answer — which is also why build systems can legitimately vary their order between runs.

What is the difference between weakly and strongly connected, and why does the condensation matter?

Weakly connected means connected when you ignore edge direction; strongly connected means a directed path exists both ways between every pair. A graph shaped 1 → 2 → 3 is weakly connected and not strongly connected. Contracting each strongly connected component to one vertex always yields a DAG, which is the useful part: any directed graph, however tangled, becomes topologically orderable at the component level. That is how a compiler handles mutually recursive functions and how a package manager treats a dependency cycle as one unit.

You need the fewest moves to solve a sliding puzzle. What is the graph?

Vertices are board configurations and edges are single legal moves; BFS from the start state finds the shortest solution because every move costs the same. The point is that the graph never has to exist — you need only a function that returns a state's neighbours and a set of states already seen, and BFS builds exactly the reachable part as it goes. This implicit-graph pattern covers word ladders, puzzle solvers, reachability in state machines and regular-expression matching. The practical limit is the seen-set, since the state space is usually exponential, which is where A* and the heuristics of chapter 21 come in.

Ten things to carry forward

  1. A graph is vertices and edges, and complexity is quoted in both because n and m vary independently.
  2. The degrees sum to 2m, and a tree is a connected acyclic graph with exactly n−1 edges.
  3. Adjacency lists win on anything sparse, and the crossover with a bit-packed matrix is around 1.5% density.
  4. BFS and DFS differ by one line: take from the front of the frontier, or from the back.
  5. Mark vertices when you push them, or the frontier grows from Θ(n) to Θ(m).
  6. BFS gives shortest paths only because every edge costs the same. It counts hops, not weight.
  7. DFS timestamps nest, which is what lets it classify edges as tree, back, forward or cross.
  8. A back edge means a cycle — but in an undirected graph you must skip one occurrence of the parent edge, or every tree looks cyclic.
  9. Topological order is DFS reverse postorder, or Kahn's algorithm, and it is not unique.
  10. Most graph problems are recognising the graph. States and moves, cells and walls, files and imports — and the graph often never needs to be built.
