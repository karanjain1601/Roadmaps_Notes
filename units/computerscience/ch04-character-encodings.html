Chapter 4 · The machine

Character encodings

Numbers have one true value that everyone agrees on. Text does not. A string is a sequence of bytes plus a shared belief about what those bytes mean, and every text bug you have ever chased is that belief coming apart.

Three layers people collapse into one

A character set says which characters exist. A coded character set gives each one a number. An encoding says how to turn those numbers into bytes. Confusing the three is the root of nearly every text problem.

Character
An abstract unit of text. The Latin letter A. The idea, not any particular drawing of it.
Code point
The number Unicode assigns to that character, written U+0041. It is just an integer between 0 and 1,114,111. Nothing about it says how many bytes it takes.
Code unit
The fixed-size chunk an encoding works in: 8 bits for UTF-8, 16 for UTF-16, 32 for UTF-32. One code point may need several code units.
Byte sequence
What actually goes in the file or on the wire, once you have picked an encoding and, for the multi-byte units, a byte order.
Glyph
The shape a font draws. One character can have many glyphs, and one glyph can render several characters. This layer belongs to typography, not to text processing, but it is the layer users see and therefore the one they describe bugs in terms of.
The rule that follows from this

There is no such thing as plain text. A sequence of bytes is meaningless without knowing its encoding, and nothing inside most byte sequences tells you what that encoding is. Every time you read a file, receive a request body, or open a socket, an encoding has been assumed on your behalf. Knowing which one, and making it explicit, is the whole job.

ASCII and the code page mess

ASCII, standardised in 1963, assigns 128 code points to the characters an American teleprinter needed: 33 control codes, space, digits, both cases of the Latin alphabet, and punctuation. Seven bits, which fitted a byte with one to spare.

Several of its choices still shape programming today. Digits start at 48, so c - '0' converts a digit character to its value. Uppercase starts at 65 and lowercase at 97, exactly 32 apart, so ASCII case conversion is a single bit flip: c ^ 32. The control codes at 0–31 are why a text file can contain \n (10) and \r (13), and why Windows and Unix still disagree about which of them ends a line.

The spare eighth bit was the problem. Everybody used it for their own 128 extra characters, and there was no way to tell which set a given file used. Latin-1 put Western European accents there. Windows-1252 put slightly different things there, including the curly quotes that still turn into question marks in badly configured systems. KOI8-R held Cyrillic; Shift-JIS and Big5 used elaborate multi-byte schemes for Japanese and Chinese. The same byte 0xE9 was é, Ω, or half of a Japanese character depending on a setting nobody transmitted.

Latin-1 will never fail

ISO 8859-1 maps all 256 byte values to characters, so decoding any byte sequence as Latin-1 always succeeds. That makes it a catastrophic default: instead of an error you get silently wrong text. UTF-8, by contrast, has invalid byte sequences, so a wrong guess usually raises an exception. When a library offers Latin-1 as a fallback encoding, it is offering to hide your bug.

Unicode: one number space for everything

Unicode's contribution is a single code point space large enough for every writing system, plus a database of properties for each character: its category, its case mappings, its script, whether it combines with the one before it, which direction it runs. The code point range is U+0000 to U+10FFFF, about 1.1 million slots, of which roughly 150,000 are currently assigned.

The space is divided into 17 planes of 65,536 code points each.

The planes that matter
PlaneRangeNameContents
0U+0000–U+FFFFBasic Multilingual PlaneAlmost every living script. The plane most software was designed around.
1U+10000–U+1FFFFSupplementary MultilingualEmoji, historic scripts, mathematical alphanumerics.

One range inside the Basic Multilingual Plane is permanently unusable for characters: U+D800 to U+DFFF, the surrogates. They exist purely to let UTF-16 reach the higher planes, and the section below explains the cost of that decision.

Unicode is not an encoding

"Save as Unicode" in older Windows dialogs meant UTF-16LE, and the phrase has confused people ever since. Unicode assigns numbers; UTF-8, UTF-16 and UTF-32 turn those numbers into bytes. Saying a file is "in Unicode" is like saying a distance is "in numbers".

UTF-8, UTF-16 and UTF-32

Three encodings of the same code point space, with genuinely different trade-offs.

UTF-8

A variable-length encoding using one to four bytes per code point. The lead byte announces the length in unary, and every continuation byte starts with the bits 10.

The UTF-8 bit templates
Code pointsBytesTemplatePayload bits
U+0000–U+007F10xxxxxxx7

U+0800–U+FFFF31110xxxx 10xxxxxx 10xxxxxx16

Four properties fall out of that design, and together they are why UTF-8 won.

  1. ASCII is unchanged. Any ASCII file is already a valid UTF-8 file with identical bytes, so decades of existing text and tooling kept working.
  2. No ASCII byte ever appears inside a multi-byte sequence. Every byte of a multi-byte character is ≥ 0x80. So code that scans for /, \0 or \n cannot be fooled by a byte that happens to sit inside a Japanese character. This is the property that let Unix filesystems adopt Unicode without changing anything.
  3. It is self-synchronising. Given a random byte you can tell instantly whether it starts a character or continues one, so you can seek into the middle of a stream and resynchronise by skipping at most three bytes.
  4. Byte order is not a question. The unit is one byte, so there is no little-endian versus big-endian argument, and no byte order mark is needed.

UTF-16 and the surrogate mechanism

UTF-16 uses 16-bit code units. Code points in the Basic Multilingual Plane take one unit. Everything above takes two, drawn from the surrogate range: subtract 0x10000, split the remaining 20 bits into halves, and put the high half in U+D800–U+DBFF and the low half in U+DC00–U+DFFF.

encoding U+1F600 as a surrogate pair
code point   U+1F600  =  0001 1111 0110 0000 0000
minus 0x10000         =  0000 1111 0110 0000 0000   (20 bits)

high 10 bits  0000111101  ->  0xD800 + 0x03D  =  U+D83D
low  10 bits  1000000000  ->  0xDC00 + 0x200  =  U+DE00

so the emoji is two 16-bit units, and every UTF-16 string
index into it is an index into halves of a character

UTF-16 exists because Java, JavaScript, C# and Windows all committed to it when Unicode still promised to fit in 16 bits. When it did not, surrogates were retrofitted, and those languages inherited a string type whose length counts code units rather than characters. It is the worst of both worlds: variable-length like UTF-8, but without ASCII compatibility, and with an endianness problem on top.

Type pure ASCII and UTF-8 uses exactly one byte per character while UTF-16 uses two and UTF-32 uses four, so UTF-8 is half the size of the alternative that a Java or JavaScript program holds in memory. Type Chinese and UTF-8 needs three bytes where UTF-16 needs two, so UTF-16 is 33% smaller. Type emoji and both need four. There is no universally smaller encoding; there is only a question of what your text actually contains, and for the web — which is mostly markup, and markup is ASCII — UTF-8 wins decisively.

UTF-32 is not the escape hatch it looks like

Fixed 4 bytes per code point makes indexing O(1), which sounds like it solves everything. It does not, because a code point is still not a character: combining marks, surrogate-free though they are, mean one user-perceived character can be several code points. UTF-32 gives you random access to the wrong unit, at four times the memory. It is used internally by some libraries and almost never for storage or transport.

What is the length of a string?

There are at least four defensible answers and they disagree constantly. For the family emoji 👩‍👩‍👧‍👦 the answers are 11, 7, 25 and 1.

That is the honest trade: you cannot have both O(1) random access and a unit that matches human perception, because the human unit is variable-length by nature.

Grapheme clusters

A grapheme cluster is what a reader would call one character. Unicode defines the rules in Annex #29, and the cases that break naive code are:

  • Combining marks. e followed by U+0301 combining acute renders as é. Two code points, one cluster. Some scripts stack several marks on one base.
  • Surrogate pairs. Any code point above U+FFFF is two UTF-16 units, so splitting a JavaScript string by index can cut an emoji in half and produce an unpaired surrogate, which is not valid text at all.
  • Zero-width joiners. U+200D glues emoji together. The family above is four people joined by three ZWJs: seven code points, one cluster.
  • Regional indicators. A flag is two letter-shaped code points that a font draws as one flag. 🇮🇳 is U+1F1EE U+1F1F3, four UTF-16 units, one cluster.
  • Indic and other complex scripts. Tamil நি is a consonant plus a vowel sign: two code points, one cluster, and no combining-mark rule alone would tell you that.

Normalisation forms

Load the two é presets in turn. They render identically and they are not equal: one is a single code point U+00E9 taking two UTF-8 bytes, the other is U+0065 U+0301 taking three. Both are one grapheme cluster. Any comparison, deduplication, database unique index or login check that does not normalise first will treat them as different strings, and a user who typed one on macOS and the other on Windows will be told their username is taken by a name that looks identical.

Normalisation and case

Unicode defines four normalisation forms, along two independent axes: composed versus decomposed, and canonical versus compatibility.

The four forms
FormDoesLossless?Use for
NFCCompose: prefer single code points where they existYesStorage, transport, comparison. The web's default.
NFDDecompose: split into base plus combining marksYesSorting, stripping accents, text analysis
NFKCCompose, and fold compatibility variantsNoSearch indexing, identifier matching
NFKDDecompose, and fold compatibility variantsNoSearch indexing where you also strip marks

The K forms are lossy and that is deliberate. NFKC turns the ligature ﬁ into fi, superscript ² into 2, and the full-width Ａ into A. That is what you want for a search index, where someone typing "fi" should find "ﬁle". It is emphatically not what you want for storage, because you cannot get the original back.

Canonical equivalence has one genuinely surprising case: the Kelvin sign U+212A is canonically equivalent to the ordinary letter K, so even plain NFC rewrites it. It exists as a separate code point only for round-tripping with older East Asian standards.

The rule to adopt

Normalise to NFC at the system boundary — as input arrives, before it is stored or compared. Store NFC. Compare NFC. Use NFKC only to build a separate search or uniqueness key, never to overwrite the user's original text. macOS filesystems historically hand you NFD filenames while everything else gives you NFC, which is why filename comparison across platforms is a recurring bug.

Case conversion is not per-character

Three assumptions that hold in ASCII and fail in Unicode:

  • Length is preserved. German ß uppercases to SS: one character becomes two.
  • It is reversible. Uppercasing ß then lowercasing gives ss, not ß.
  • It is locale-independent. Turkish has dotted and dotless i as separate letters, so "I".toLowerCase() is i in English and ı in Turkish. A system that lowercases identifiers with the machine's locale will behave differently on a Turkish laptop, which is a real and well-documented class of bug.
Case-insensitive comparison needs case folding, not lowercasing

Lowercasing is a display operation and is locale-sensitive. Case folding is a separate, locale-independent Unicode operation designed specifically for caseless matching. Use str.casefold() in Python, String.equalsIgnoreCase or a locale-invariant toLowerCase(Locale.ROOT) in Java, and localeCompare with sensitivity: "base" in JavaScript. Never lowercase with the ambient locale to compare identifiers.

Mojibake, BOMs and the practical rules

Mojibake is text decoded with the wrong encoding. The signature case: é encoded as UTF-8 is the two bytes C3 A9, and reading those as Latin-1 gives Ã©. If you see Ã, Â or â scattered through otherwise readable text, you are looking at UTF-8 bytes decoded as a single-byte code page, and the fix is at the decoding step, not a find-and-replace on the output.

Two failure shapes worth recognising:

Double encoding

Correct UTF-8 gets decoded as Latin-1 and then re-encoded as UTF-8. Two bytes become four. Each round makes it worse, and each round is reversible only if you know exactly how many happened.

Replacement characters

A run of � means the decoder hit bytes that were not valid in the target encoding and substituted U+FFFD. This is lossy and permanent: the original bytes are gone. Unlike mojibake, it cannot be undone.

The byte order mark

U+FEFF at the start of a file signals byte order for UTF-16 and UTF-32. In UTF-8 it encodes as EF BB BF and signals nothing useful, because UTF-8 has no byte order. Microsoft tools add it anyway as an encoding hint, which is why shell scripts written in Notepad fail with a mysterious error on the shebang line, and why a UTF-8-with-BOM CSV puts three invisible bytes in your first column name.

Homoglyphs are a security problem, not a curiosity

Cyrillic а (U+0430) and Latin a (U+0061) look identical in most fonts. Domain names, usernames and package names built from mixed scripts are a live phishing technique. The defences are Punycode display rules in browsers, restricting identifiers to a single script, and Unicode's UTS #39 confusable-detection data. Right-to-left override characters can also make report‮fdp.exe render as an innocent-looking PDF filename. If you accept user-supplied text that becomes an identifier, you need an explicit allowlist.

Seven rules that prevent most of this
  1. UTF-8 everywhere: files, databases, HTTP headers, source code.
  2. Declare it explicitly. <meta charset="utf-8">, Content-Type: …; charset=utf-8, utf8mb4 in MySQL, an explicit encoding= on every file open.
  3. Decode at the boundary, work with strings inside, encode on the way out. Never concatenate bytes and strings.
  4. Normalise to NFC on input.
  5. Size limits in bytes, user-facing limits in grapheme clusters. Never mix them up.
  6. Truncate and reverse on grapheme boundaries, never on indices.
  7. Test with the hard cases: an emoji, a combining mark, a right-to-left string, and a CJK character.

Check yourself

Why can no byte inside a multi-byte UTF-8 sequence be confused with an ASCII character?

Because every byte of a multi-byte sequence has its top bit set. Lead bytes match 110xxxxx, 1110xxxx or 11110xxx, and continuation bytes match 10xxxxxx; all of them are ≥ 0x80, while ASCII occupies 0x00–0x7F. So a C function scanning for / or \0 can walk UTF-8 bytes without decoding and never produce a false match. Shift-JIS did not have this property, which is why it caused years of path-handling bugs.

Encode U+20AC (the euro sign) into UTF-8 by hand.

0x20AC is 8,364, which is in U+0800–U+FFFF, so three bytes with template 1110xxxx 10xxxxxx 10xxxxxx holding 16 payload bits. In binary 0x20AC is 0010 0000 1010 1100. Split into 4 + 6 + 6: 0010, 000010, 101100. Fill the template: 11100010 10000010 10101100 = E2 82 AC. Confirm it in demo 1 by typing the euro sign and clicking its row.

"😀".length is 2 in JavaScript but 1 in Python 3. Neither is wrong. Explain.

They are measuring different units. JavaScript strings are sequences of UTF-16 code units, and U+1F600 is above the Basic Multilingual Plane so it needs a surrogate pair: two units. Python 3 strings are sequences of code points, and this is one code point. Both are also arguably wrong in the sense that matters to a user, for whom the answer is one character — which is what Swift's count reports, since it counts grapheme clusters.

Two users register with what looks like the same name and the database accepts both. What happened and what is the fix?

Almost certainly a normalisation difference: one submitted é as the single code point U+00E9 and the other as e plus combining acute U+0301. They render identically and are different byte sequences, so a unique index sees two distinct values. The fix is to normalise to NFC at the boundary before storing or comparing, and ideally to keep a separate NFKC-folded, case-folded key column for uniqueness while storing the user's original text unchanged.

Why is NFKC the wrong thing to store, given that it makes more strings compare equal?

Because it is lossy and irreversible. NFKC turns ﬁ into fi, ² into 2, and full-width forms into ASCII. Those distinctions carry meaning in typography, mathematics and East Asian text, and once folded they cannot be recovered. NFC is defined to be lossless: it only replaces sequences with canonically equivalent ones. Store NFC, derive an NFKC key for searching, and never let the derived key overwrite the original.

You need to truncate user-entered text to fit a 100-byte database column. Sketch the correct approach.

The limit is in bytes, so measure in UTF-8 bytes, but you must cut on a grapheme cluster boundary or you will produce broken text. Segment the string into grapheme clusters, accumulate their UTF-8 byte lengths, and stop before the first cluster that would exceed 100. Cutting on a byte index can split a multi-byte sequence and yield invalid UTF-8; cutting on a code point index can split a family emoji into three people and a joiner. If you also show the user a character count, count clusters, not bytes — otherwise a Japanese user sees their allowance shrink by two-thirds for no visible reason.

A shell script written on Windows fails with an error about an unrecognised command on line 1, but the line looks correct. What would you check?

A UTF-8 byte order mark. The editor prepended EF BB BF before #!/bin/sh, so the kernel does not see the shebang at the start of the file and the shell tries to execute the invisible bytes as part of the first command. It is invisible in most editors and does not show in a diff. Check with head -c 3 file | xxd and save without a BOM. The same three bytes are why a UTF-8 CSV opened by a strict parser sometimes has a first column named something that will not match any string you compare it to.

Ten things to carry forward

  1. Character, code point, code unit, byte and glyph are five different things. Most text bugs are two of them being confused.
  2. There is no plain text. Bytes mean nothing without a declared encoding, and nothing in the bytes usually declares it.
  3. Unicode assigns numbers; UTF-8, UTF-16 and UTF-32 turn them into bytes. "Unicode" is not an encoding.
  4. UTF-8 won on four properties: ASCII compatibility, no ASCII bytes inside multi-byte sequences, self-synchronisation, and no byte-order question.
  5. UTF-16 is variable-length too. Surrogate pairs mean length in JavaScript, Java and C# counts halves of characters.
  6. A string has at least four lengths. Use bytes for storage limits, code points for parsing, grapheme clusters for anything a person counts.
  7. Grapheme clusters are the user's unit, and they are built from combining marks, joiners, regional indicators and script-specific rules.
  8. Normalise to NFC at the boundary. The K forms are lossy and belong in derived search keys, never in storage.
  9. Case conversion changes length, is not reversible, and depends on locale. Use case folding for comparison.
  10. Mojibake is fixable at the decoder; U+FFFD is not fixable at all. Get the encoding right at the boundary and the rest of the system stops caring.
