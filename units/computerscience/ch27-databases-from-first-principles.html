The relational model

Codd's 1970 idea was to separate what data means from how it is stored. A relation is a set of tuples over named, typed attributes — a table with no duplicate rows and no inherent order. Everything else follows.

Candidate key
A minimal set of attributes that uniquely identifies a row. Minimal matters: if (email) is unique then (email, name) is not a candidate key, merely a superkey.
Primary key
The candidate key you chose. Natural keys carry meaning and change; surrogate keys are meaningless integers or UUIDs and do not. Prefer surrogate, because business meaning changes and primary keys should not.
Foreign key
An attribute referencing another relation's primary key. This is where referential integrity is enforced, and it is the thing you lose when you skip constraints "for performance".
NULL
Not a value but a marker for absence, with three-valued logic attached. NULL = NULL is not true; it is unknown. Chapter 20's binary search assumptions do not survive contact with it, and neither does most people's mental model of WHERE.

The declarative part is what earns the model its place: you state the result you want and the query planner decides how to get it. That separation is why the same SQL can survive a schema change, a new index, or a hundredfold growth in data — and why the planner needs statistics, which section three is about.

Normalisation, and the three anomalies

Normalisation is usually taught as a list of numbered forms. It is better understood as the removal of three specific failure modes, all caused by storing one fact in more than one place.

Update anomaly

Ada's address appears in 4 rows. Change it and miss one, and the database now holds two different addresses for one customer — with no error and no way for a constraint to notice.

Delete anomaly

Deleting order 6 deletes Alan, because that row was the only place his existence was recorded. Deleting order 3 loses the Cable product entirely.

Insert anomaly

A customer with no orders cannot be stored at all, because the primary key is the order. You would have to invent a fake order, which is how NULL-riddled tables begin.

The normal forms, stated as what each one forbids
FormForbids
1NFRepeating groups and multi-valued columns. One value per cell.
2NFA non-key attribute depending on only part of a composite key.
3NFA non-key attribute depending on another non-key attribute — transitive dependency.

The informal version is exact enough for most work: every non-key attribute must depend on the key, the whole key, and nothing but the key. Normalising the demo's table gives 3 customers, 4 products and 7 orders, cuts storage by 23% on this tiny example and by 66% once customers have many orders each — and, crucially, makes an address change touch exactly one row.

When to denormalise on purpose

Normalisation optimises for correct writes; reads pay for it in joins. Denormalise deliberately when a join is measurably too slow, when you need a value frozen at a point in time — the price at time of order genuinely is a different fact from the current price, so copying it is normalisation, not a violation — or when you are building a read model that is rebuilt rather than edited. The rule is to normalise until it hurts, then denormalise until it works, and to know which one you are doing.

Indexes, and why the planner needs statistics

An index is chapter 15's B+ tree over one or more columns: values in the leaves, leaves chained for range scans, and a height of three or four for a very large table. It turns a scan into a descent.

Consider a million rows at 100 rows per page — 10,000 pages. Fetching one row by index costs the tree height plus one leaf, 4 page reads, against 10,000 for a full scan: 2,500 times cheaper. That is the case everyone has in mind, and it is why indexes feel free.

An unclustered index stops paying at about 1% selectivity, because each matching row may sit on its own page and a random read is not cheaper than a sequential one. Past that point the index is slower than no index. A clustered index — where the table itself is stored in index order — keeps winning to nearly 100%, because matching rows share pages.

Why the same query gets different plans

The crossover depends on how many rows match, which depends on the value, not the query text. WHERE country = 'Liechtenstein' should use the index and WHERE country = 'China' should not, from the same statement. That is what table statistics are for, and it is why a plan can change overnight after a data load, why ANALYZE exists, and why parameter sniffing causes production incidents. When a query is suddenly slow and nothing was deployed, stale statistics are the first thing to check.

ACID

Atomicity
All of a transaction happens or none of it does. Implemented with a write-ahead log: record the intent, then apply, so a crash can be undone or replayed.
Consistency
The odd one out. It is not a property the database provides so much as one it preserves — your constraints, foreign keys and triggers hold before and after. Most of the acronym's real content is in the other three letters.
Isolation
Concurrent transactions do not see each other's partial work. This is the letter with a dial on it, and section five is entirely about what the settings mean.
Durability
A committed transaction survives a crash. Implemented by flushing the log to stable storage before acknowledging — which is why fsync behaviour and disk write caches are a correctness issue, not a tuning one.

The write-ahead log deserves a sentence of its own, because it explains both atomicity and durability at once and it is the same idea as chapter 15's journal: write what you intend to do before doing it. On recovery, replay the log for committed transactions and undo it for uncommitted ones. Sequential log writes are also far cheaper than random data-page writes, so the mechanism that provides the guarantee is also the one that makes it fast.

Isolation levels, and what each one still allows

Perfect isolation means transactions behave as though run one at a time, and it is expensive. The SQL standard therefore defines four levels by naming the anomalies each one permits.

At read committed it reads 1,000 both times in that schedule, but in the second schedule it reads 1,000 and then 500: the same row, twice, in one transaction, with different answers.

The lost update, which the standard's table does not mention

Two transactions read a balance of 1,000. One adds 100 and commits; the other subtracts 100 and commits. The correct final balance is 1,000. At read uncommitted, read committed and repeatable read the demo measures a final balance of 900: the second write simply overwrote the first, and the +100 is gone with no error anywhere. Only serializable catches it — by aborting one transaction with a serialisation failure, leaving 1,100 for the surviving one.

That last point is the one to internalise. Serializable does not make the conflict disappear; it converts silent data corruption into a retryable error. Which means your application must actually retry, and code that runs a transaction without a retry loop is not using serializable correctly.

The names are not portable

PostgreSQL's READ UNCOMMITTED behaves as READ COMMITTED; it simply does not implement dirty reads. Its REPEATABLE READ is snapshot isolation, which prevents phantoms that the standard permits, but allows write skew — two transactions each reading a condition and each writing something that invalidates it for the other. Oracle offers only read committed and serializable. MySQL's InnoDB defaults to repeatable read and uses gap locks to prevent phantoms. So "we use repeatable read" says less than it appears to, and the only reliable way to know what your database does is to test the schedule.

How isolation is implemented

Two-phase locking

Acquire all locks, then release all locks, never interleaving. Shared locks for readers, exclusive for writers. Simple, provably serialisable — and readers block writers, which is why it hurts under load.

MVCC

Keep multiple versions of each row with visibility timestamps. Readers see a consistent snapshot without taking any locks at all, so readers never block writers and writers never block readers. This is what PostgreSQL, Oracle and InnoDB do, and it is why a long analytical query does not stop the application.

MVCC's cost is that old versions accumulate and must be reclaimed — PostgreSQL's VACUUM, and the reason a long-running transaction can bloat a database by preventing cleanup of rows that nothing else can still see.

Deadlock is the other implementation reality: T1 holds A and wants B, T2 holds B and wants A. This is chapter 18's cycle detection applied to a wait-for graph, and databases resolve it by detecting the cycle and killing the cheaper victim. The prevention is the same as chapter 8's: always acquire locks in a consistent order.

BASE, and what is actually being traded

BASE — Basically Available, Soft state, Eventually consistent — is the deliberate counterpoint to ACID, and the backronym is a chemistry joke rather than a design.

The honest framing is that it is not a philosophy but a consequence. Chapter 30's CAP theorem says a distributed system facing a network partition must choose availability or consistency; a single-node database never faces the choice, so ACID costs it nothing. The moment data spans machines, strong consistency requires coordination, coordination requires round trips, and round trips cost latency and availability.

Where each model belongs
Choose ACID whenChoose eventual consistency when
Money moves, or an invariant must never be violatedThe invariant tolerates temporary violation
Reading stale data causes a wrong decisionStale reads are merely slightly wrong for a moment
The data fits on one machine, which it usually doesScale or geography genuinely forces distribution
You want the database to enforce correctnessYou are prepared to enforce it in the application, forever

The point of the last row is that giving up ACID does not remove the requirement for correctness; it relocates it into your code, where it must be re-implemented and re-tested by every team that touches the data. That is a real cost, frequently underestimated, and it is why "we chose NoSQL for scale" at a data volume a single Postgres instance handles comfortably is such a common and expensive mistake.

Check yourself

Name the three anomalies that normalisation removes, with a concrete instance of each.

Update: Ada's address is stored in 4 rows; change 3 and the database holds two different addresses for one customer, with no constraint able to notice. Delete: removing order 6 removes Alan entirely, because that row was the only record of his existence. Insert: a customer with no orders cannot be stored at all, since the primary key is the order. All three come from the same cause — one fact stored in more than one place, or stored only as a side effect of another fact.

Storing the price on the order line duplicates the product's price. Is that a normalisation violation?

No — it is correct normalisation, because they are different facts. The product's current price and the price at the time of that order are separate pieces of information, and the second must not change when the first does. The test is whether the two values are logically required to stay equal: if they are, duplication is a violation; if the copy is a snapshot with independent meaning, it is a distinct attribute that happens to start with the same value. Getting this wrong in either direction causes real bugs, most visibly on invoices that retroactively change.

Why might adding an index make a query slower?

Because an unclustered index costs one random page read per matching row, and past about 1% selectivity that exceeds the cost of reading the whole table sequentially. On a million rows at 100 per page, a full scan is 10,000 page reads; an index matching 300,000 rows costs 300,003 — thirty times worse. A good planner will refuse to use the index, so the visible cost is usually the write overhead instead: every index must be updated on every insert, update and delete. Indexes are a read optimisation paid for by writes.

The same query is fast for one parameter value and slow for another. What is happening?

The right plan depends on how many rows match, which depends on the value rather than the query text. country = 'Liechtenstein' matches few rows and should use the index; country = 'China' matches many and should scan. The planner decides using table statistics, so the same statement legitimately gets different plans. When a query goes slow with no deployment, suspect stale statistics — after a bulk load the planner may still believe the old distribution — or a cached plan built for an unrepresentative parameter.

Two transactions read a balance of 1,000; one adds 100, one subtracts 100, both commit. What is the balance?

It should be 1,000, and at read uncommitted, read committed and repeatable read the demo measures 900. The second write overwrote the first, and the +100 vanished with no error raised anywhere. This is the lost update, and it is not in the SQL standard's anomaly table at all. Only serializable catches it, and it does so by aborting one transaction with a serialisation failure — leaving 1,100 for the survivor. The fixes at lower levels are SELECT … FOR UPDATE, an atomic UPDATE … SET balance = balance - 100, or optimistic concurrency with a version column.

What does serializable actually give you, and what does it require from your code?

It gives you the guarantee that the outcome is equivalent to running the transactions one at a time. It does not make conflicts disappear — it converts them from silent corruption into an explicit serialisation failure, which means your application must catch that error and retry the transaction. Code that runs a transaction at serializable without a retry loop is not using serializable; it is using an intermittent error. The other cost is throughput: more conflicts under contention means more aborts and more retried work.

What does MVCC buy over locking, and what does it cost?

It buys the property that readers never block writers and writers never block readers, because a reader is given a consistent snapshot assembled from row versions rather than a lock. That is why a half-hour analytical query does not stop the application, which under two-phase locking it would. The cost is that old versions accumulate and must be reclaimed — PostgreSQL's VACUUM — and a single long-running transaction prevents cleanup of every version it might still need, which is the usual cause of unexplained table bloat.

Ten things to carry forward

  1. The relational model separates meaning from storage, which is what lets a planner choose the access path.
  2. Normalisation removes three anomalies, all caused by one fact living in more than one place.
  3. Every non-key attribute depends on the key, the whole key, and nothing but the key.
  4. A price at time of order is a different fact from the current price, so copying it is normalisation, not a violation.
  5. An unclustered index stops paying at about 1% selectivity — 300,003 page reads against 10,000 for a scan.
  6. The right plan depends on the value, not the query, which is what statistics are for and why plans change.
  7. The write-ahead log provides atomicity and durability at once, and makes them cheap by being sequential.
  8. Isolation levels are named by the anomalies they still allow, and the names differ between databases.
  9. Lost updates happen at every level below serializable — 900 where the answer is 1,000, silently.
  10. Serializable turns corruption into a retryable error, so the retry loop is part of using it.
