Hash tables

Turn a key into an array index and lookup becomes one memory access instead of a search. The idea is a sentence long; everything difficult about it comes from the fact that many keys map to the same index, and that somebody might arrange for all of them to.

The idea, and the immediate problem

An array gives Θ(1) access by index. A hash table gives Θ(1) access by anything, by computing an index from the key: bucket = hash(key) % capacity. Look up "Karan" and you compute a number, take it modulo the table size, and go straight there.

The problem arrives immediately. There are unboundedly many possible keys and a fixed number of buckets, so by the pigeonhole principle some keys must share one. Worse, they start sharing far earlier than intuition suggests. This is the birthday problem: with 4,096 buckets, the chance of a collision passes 50% at just 76 keys — about 1.2 × √m, not anywhere near m.

Collisions are the normal case

A hash table is not "an array with a clever index and occasional collisions". It is a collision-handling structure that happens to be fast. Every design decision below — the hash function, chaining versus probing, the load factor, when to resize — is about keeping the number of colliding keys per bucket small and bounded.

What makes a hash function good

Deterministic
The same key must always hash to the same value within one process. If it does not, you cannot find what you stored. Note the qualifier: across processes it may legitimately differ, which section six is about.
Uniform
Keys should spread evenly across buckets. A hash that maps every key to 0 is deterministic and useless.
Avalanche
Changing one bit of the input should change about half the output bits. Without this, similar keys — which real data is full of — land in similar buckets.
Fast
It runs on every lookup. A cryptographic hash is beautifully uniform and ten to a hundred times too slow for a hash map.
Consistent with equality
If a == b then hash(a) == hash(b), always. Override equals without hashCode in Java, or __eq__ without __hash__ in Python, and objects vanish into the table. Mutating a key after insertion does the same thing.

Three failures are worth producing deliberately. Hashing 93 English words by length uses 6 of 64 buckets and puts 33 words in one, with a chi-squared of 1,497 against FNV-1a's 47. Hashing anagrams by sum of characters gives every permutation the same value, so 24 anagrams collapse into 3 buckets. And using the integer itself on multiples of 16 with 64 buckets lands everything in exactly 4 buckets, because 16 divides 64 — the classic reason to prefer a prime table size when the hash is weak.

A real defect, found by measuring

Uniform hashing predicts that at load factor 1 a fraction 1/e ≈ 0.368 of buckets stay empty. Hashing the keys key0 … key255 with plain FNV-1a into 256 buckets leaves 0.484 empty — nowhere near. The cause is that % 256 keeps only the low byte, and FNV-1a's final multiply mixes the low bits least: those 256 keys produce just 132 distinct low bytes, so half the table is unreachable. Add an xor-shift finaliser and the empty fraction becomes 0.367, essentially exactly 1/e. Switch between the two options in the demo with the sequential key set and watch it happen. This is why serious implementations either use a prime modulus, take the high bits, or append a finalising mix — and why "FNV-1a is a good hash" is only true of the whole word.

Separate chaining

The simplest resolution: each bucket holds a container of the entries that landed there, traditionally a linked list.

chaining, in outline
get(key):
  b = buckets[hash(key) % capacity]
  for entry in b:
      if entry.key == key: return entry.value   // compare keys, not hashes alone
  return not_found

With n entries in m buckets the load factor is α = n/m, and that is also the average chain length. A successful lookup costs about 1 + α/2 comparisons and an unsuccessful one about α. Both stay constant as long as α stays bounded, which is what resizing is for.

Why chaining is forgiving

It degrades gracefully past α = 1 rather than failing. Deletion is trivial — unlink the node. And it tolerates a mediocre hash function, because a bad bucket only slows down the keys in it.

Why it is slower than it looks

Every chain step is a pointer chase to a separately allocated node, which chapter 12 measured at up to 18× the cache misses of a contiguous walk. And each node carries pointer overhead on top of the entry.

Real implementations soften both problems. Java 8 onward converts a bucket to a balanced tree once its chain exceeds 8 entries, turning the worst case from Θ(n) into Θ(log n). Many C++ and Rust maps store the first entry inline in the bucket so the common case needs no indirection at all.

Open addressing

The alternative: no chains at all. Every entry lives in the table itself, and a collision means probing for another slot by a rule that lookup can reproduce.

Slide the load factor and watch linear probing come apart. In a 1,024-slot table an unsuccessful lookup costs about 2.8 probes at α = 0.5, 7.5 at α = 0.75, and 26 at α = 0.9. Double hashing over the same table costs 2.0, 4.0 and 9.8 — and those three figures track the uniform-hashing prediction of 1/(1−α) = 2.0, 4.0 and 10.0 to within 2%, which is the check that the simulator is measuring what it claims.

The closed forms explain the divergence. Linear probing's unsuccessful cost is ½(1 + 1/(1−α)²), which has a squared term; uniform hashing's is 1/(1−α), which does not. At α = 0.9 that is 50.5 predicted against 10. The linear measurement of 26 sits well below its own prediction and swings a great deal between runs — that is not an error, it is linear probing's genuinely enormous variance at high load, where a single unlucky run of occupied slots dominates the average. The ratio is the durable part: at α = 0.9 linear probing costs roughly 2.7 times what double hashing does.

The mechanism is primary clustering. A key landing anywhere in an occupied run walks to the end of it and extends it, so long runs attract more keys and grow faster than short ones. The map above makes it visible: at high load the red runs are most of the table.

Why linear probing is still popular

Because the probe formula is not the whole cost. Linear probing walks forward through contiguous memory, so several probes usually hit the same cache line and the prefetcher handles the rest. Double hashing jumps randomly and pays a cache miss per probe. Below α ≈ 0.7 linear probing's extra probes are nearly free while double hashing's are not, which is why Google's Swiss tables, Rust's hashbrown and most modern high-performance maps use linear probing over groups of slots — and keep the load factor well away from the cliff.

Deletion is the hard part

You cannot simply empty a slot. Lookup stops probing at the first empty slot, so clearing one in the middle of a run makes everything after it unreachable. The standard fix is a tombstone: a marker meaning "empty, but keep probing". Tombstones then accumulate and behave like occupied slots for probe-length purposes, so a delete-heavy table degrades until it is rehashed. Chaining has none of this — you unlink the node and you are done.

Load factor and resizing

Everything above depends on α staying bounded, so a table grows when it gets too full: allocate a bigger array and rehash every entry, because the bucket index depends on the capacity.

Rehashing is Θ(n), and by the same geometric argument as chapter 10's dynamic array it is Θ(1) amortised as long as the capacity grows by a constant factor. The catch is the same too: an individual insert can take Θ(n), which is a latency spike, not an average cost. Latency-sensitive systems either pre-size the table or use incremental rehashing, keeping both tables alive and migrating a few entries per operation — which is what Redis does.

Shrinking is not symmetric

Most implementations never shrink. A map that held a million entries and now holds ten usually still owns the million-entry array, because shrinking on delete would make an alternating insert/delete pattern rehash on every operation. If memory matters, rebuild the map explicitly.

The adversary who picks your keys

Every complexity claim in this chapter is average-case, and chapter 10 warned that average-case is a claim about the input distribution. If an attacker controls the keys and knows your hash function, they can compute thousands of keys that all hash to the same bucket. Every insert then walks the same chain and an O(n) parse becomes O(n²).

This is hash flooding, and it is not theoretical. A 2011 presentation demonstrated it against PHP, Java, Python, Ruby, ASP.NET and others simultaneously: a single HTTP POST of a few hundred kilobytes of colliding form-field names could occupy a CPU for minutes. Every one of those languages shipped a fix.

Randomised seeding

Choose a random seed per process and mix it into the hash. An attacker cannot precompute collisions without knowing the seed. Python enables this by default; Java offers alternative string hashing; Node and V8 randomise too.

Keyed hashing

Use a hash designed to be unpredictable without the key, such as SipHash. Rust's default hasher is SipHash-1-3 precisely because HashMap is often fed untrusted input — and this is why Rust maps benchmark slower than C++ ones by default, a deliberate trade.

The consequence for your code

Hash iteration order is not stable and must never be relied on. It varies with insertion order, with capacity, and with the per-process seed, so the same program can produce different orderings on two runs. Python dicts preserve insertion order as of 3.7, which is a different guarantee and does not extend to sets. If you need a deterministic order, sort explicitly or use an ordered map.

Using them well

  1. Pre-size when you know the count. new HashMap<>(expected / 0.75 + 1) avoids every rehash and every latency spike.
  2. Keys must be immutable, or at least never mutated while stored. Mutating a key changes its hash and the entry becomes unreachable while still occupying space — a leak that no leak detector reports.
  3. Implement hash and equality together, and derive them from the same fields.
  4. Do not use a hash map for ordered queries. Range scans, nearest-neighbour and "the smallest key" all need a tree; chapters 14 and 15 cover those.
  5. For small maps, a sorted array or a linear scan often wins. Below roughly 8–16 entries the hash computation and the cache miss cost more than scanning a contiguous block.
  6. Be careful hashing floats. NaN != NaN, so a NaN key can never be found again, and +0.0 == -0.0 with different bit patterns.

Check yourself

You have 4,096 buckets and expect 100 keys. Is a collision likely?

Yes — more likely than not by 76 keys. This is the birthday problem: the chance of no collision is the product of (m−i)/m, which falls below one half at roughly 1.2 × √m, not at anything close to m. At 100 keys in 4,096 buckets a collision is close to certain. Collisions are the ordinary case, which is why the resolution strategy matters more than the table size.

Why does summing character codes handle anagrams so badly?

Because addition is commutative, so it discards position entirely and every permutation of the same characters gets the same hash. In the demo, 24 anagrams land in 3 of 16 buckets. Real hashes multiply the running value by a constant before mixing in each character, so a character's contribution depends on where it appeared. That is what djb2's h * 33 + c and FNV-1a's multiply-then-xor are doing.

FNV-1a is a well-regarded hash, yet hash(key) % 256 leaves 48% of buckets empty instead of 37%. Explain.

Taking a value modulo a power of two keeps only the low bits and discards everything else. FNV-1a's structure — xor a byte, then multiply — propagates changes upward, so its low bits are the least mixed part of the word. On the 256 sequential keys key0…key255 it produces only 132 distinct low bytes, so half the table is unreachable and the occupied half is overloaded. Adding an xor-shift finaliser brings the empty fraction to 0.367, within 0.001 of the 1/e theory predicts. The fixes in production code are the same three: mix at the end, use a prime modulus, or take the high bits.

Why does linear probing degrade so much faster than double hashing as the table fills?

Primary clustering. A key that hashes anywhere inside an occupied run must walk to the end of it and lands there, extending it — so long runs grow faster than short ones and eventually merge. The cost formulas show it: linear probing's unsuccessful lookup is ½(1 + 1/(1−α)²) while uniform hashing's is 1/(1−α). At α = 0.9 that is 50.5 against 10, and the simulation measures 44 against 8.7. Linear probing is still preferred below about 0.7, because its probes are contiguous in memory and double hashing's are a cache miss each.

Why can you not delete from an open-addressed table by clearing the slot?

Because lookup uses an empty slot as its stopping signal. If key X was placed at position 7 after colliding at 5, and you clear 5, a later lookup for X probes 5, finds it empty, and concludes X is absent. The standard fix is a tombstone marking "was occupied, keep probing". Tombstones count as occupied for probe-length purposes, so a table with heavy churn slowly degrades until it is rehashed — one of chaining's genuine advantages, since unlinking a node is complete.

A JSON endpoint becomes unresponsive when fed a large object with unusual keys. What is happening?

Hash flooding. The keys were chosen to collide, so every insertion walks the same bucket and building the object costs Θ(n²) instead of Θ(n) — a few hundred kilobytes of request body can occupy a CPU for minutes. The 2011 disclosure affected PHP, Java, Python, Ruby and ASP.NET simultaneously. Defences are randomised per-process hash seeds so collisions cannot be precomputed, keyed hashes such as SipHash, tree-ifying long chains as Java does, and capping the number of accepted parameters.

You store a mutable object as a key, then modify one of its fields. What happens?

The entry becomes unreachable. It was placed in the bucket implied by its old hash; lookups now compute the new hash and go to a different bucket, so get returns nothing even with the original object in hand — and contains is false for something that is demonstrably in the map. The entry still occupies memory, so it is a leak that no leak detector reports because it is genuinely still referenced. Use immutable keys, or derive the hash only from fields you never change. Python enforces this by refusing to hash lists and dicts at all.

Ten things to carry forward

  1. A hash table turns a key into an index, and everything hard about it comes from two keys producing the same one.
  2. Collisions arrive at about 1.2 × √m keys, not at m. They are the normal case, not the exception.
  3. A good hash is deterministic, uniform, avalanching, fast, and consistent with equality. Dropping the last one makes entries vanish.
  4. Taking a hash modulo a power of two keeps only the low bits, and some good hashes mix those least — measure before trusting.
  5. Chaining is forgiving: it degrades gracefully past α = 1, deletes cleanly, and tolerates a mediocre hash.
  6. Open addressing keeps everything in one array, which is faster in cache terms and much harder to delete from.
  7. Linear probing suffers primary clustering, with an unsuccessful cost that has a squared term — 50.5 predicted probes at α = 0.9 against uniform hashing's 10.
  8. Load factor is the control knob, and resizing is amortised Θ(1) with a Θ(n) latency spike that pre-sizing removes.
  9. Average-case guarantees assume the keys are not chosen against you. Randomised seeds and keyed hashes exist because they sometimes are.
  10. Iteration order is not a guarantee, and mutating a stored key makes its entry unreachable while keeping it alive.
