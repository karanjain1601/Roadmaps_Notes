Chapter 1 · The machine

How a computer runs a program

A processor has no idea what a function is, or a loop, or a string. It repeats one short ritual billions of times a second: read a number from memory, treat that number as an order, carry it out. Everything above that is a story we tell on top.

Programs are just numbers in memory

The single most important idea in computer architecture is that a program and its data live in the same memory, in the same format, and are told apart only by how the machine happens to look at them.

Before this idea took hold, machines were wired for a task. Changing what a machine did meant physically re-plugging it. The ENIAC, finished in 1945, was reprogrammed by moving cables and setting switches, a job that could take days. The stored-program design — usually credited to the 1945 First Draft of a Report on the EDVAC, and built on Alan Turing's earlier notion of a universal machine — replaced the cables with numbers. Instructions became data you could load, copy, generate and overwrite like any other data.

That single change is why software exists as a separate discipline. A compiler is a program that writes numbers that another program will later interpret as instructions. A virus is data that persuades a machine to treat it as code. A JIT compiler generates machine code at runtime and jumps into it. All of these are only possible because instructions and data are made of the same stuff.

The core loop

A CPU holds one special register called the program counter (PC), which contains the address of the next instruction. Its entire job is: read the word at PC, add one to PC, do what the word says, repeat. Branches, calls, returns, exceptions and interrupts are all just different ways of writing a new value into PC.

The parts you are told about

The classical description of this machine, still called the von Neumann architecture, has four components: a memory holding both instructions and data, an arithmetic and logic unit (ALU) that computes, a control unit that decodes instructions and drives everything else, and input/output. The control unit and ALU together are the CPU.

The one structural weakness of the design has a name too. Because instructions and data travel over the same path to the same memory, the processor cannot fetch an instruction and a data word at the same time. That bottleneck is the reason nearly every real CPU splits the first level of cache into a separate instruction cache and data cache, which is a Harvard architecture bolted onto a von Neumann memory. You get the flexibility of shared memory at the top and the parallelism of separate paths at the bottom.

Inside the box

Five pieces of hardware do the work. Everything else is optimisation.

Registers
A tiny set of storage slots inside the CPU itself, each one word wide. A 64-bit x86-64 core has 16 general-purpose integer registers; a 64-bit ARM core has 31. They are the only storage the ALU can read directly, and access takes zero extra cycles. Everything a program computes passes through them.
The arithmetic and logic unit
A block of combinational logic that takes two input words and a small operation code and produces one output word plus a handful of status flags — zero, carry, negative, overflow. It has no memory of its own. Give it the same inputs and it gives the same answer, every time, within one clock tick.
The control unit
Reads the current instruction and sets the switches: which registers feed the ALU, what operation the ALU performs, whether memory is read or written, where the result goes, what PC becomes next. On older machines this was a small program of its own, stored in microcode.
Memory
A very large array of bytes with numeric addresses. Slow compared to registers: hundreds of times slower for main memory. Chapter 5 is entirely about coping with that gap.
Buses
The wires between them. An address bus carries the location, a data bus carries the value, a control bus carries the read/write signal. The width of the address bus sets how much memory can be addressed at all — 32 wires gives 232 distinct addresses, which is the 4 GiB ceiling that defined an era of computing.
Why registers exist at all

You could imagine a machine where the ALU reads its operands straight from memory. Some early machines did exactly that, and they were slow, because the ALU spent nearly all its time waiting. Registers are a small, fast staging area so the ALU can run at full speed. The cost is that compilers must decide which values live in registers and which get spilled back to memory — register allocation, one of the hardest jobs a compiler does.

One instruction, close up

An instruction set architecture (ISA) is the contract between hardware and software: which operations exist, how many registers there are, how instructions are encoded as bits. x86-64, ARM64 (AArch64), RISC-V and MIPS are all ISAs. A program compiled for one will not run on another, because the numbers mean different things.

The toy machine used in this chapter has a deliberately small ISA. Every instruction is exactly 16 bits, split into four fields.

RISC and CISC, briefly

Real ISAs fall roughly into two camps. A RISC design (ARM, RISC-V, MIPS) keeps instructions fixed-width and simple: only explicit load and store instructions touch memory, everything else works register to register. A CISC design (x86-64) allows variable-length instructions — one to fifteen bytes — some of which do a great deal, such as reading memory, adding, and writing the result back in a single instruction.

The distinction matters less than it used to. Modern x86 cores decode those complex instructions into simple internal operations called micro-ops and then run a RISC-like machine underneath. What survives is the encoding: fixed-width instructions are far easier to fetch and decode several at a time, which is why the decode front end of a big x86 core is one of its most complicated and power-hungry parts.

Common confusion

Assembly language is not the same thing as machine code. Assembly is text a person can read: ADD R0, R1. Machine code is the number: 16640. An assembler translates one to the other, nearly one line to one instruction. A disassembler goes the other way. When a debugger shows you assembly, it is disassembling bytes it read out of memory, and it can be fooled into showing nonsense if it starts reading part-way through a variable-length instruction.

The fetch–decode–execute cycle

Here is the entire behaviour of a simple processor, written as a loop:

the whole machine, in eight lines
while (!halted) {
  ir      = memory[pc];        // FETCH   read the instruction word
  pc      = pc + 1;            //         point at the next one
  fields  = decode(ir);        // DECODE  split it into opcode + operands
  result  = execute(fields);   // EXECUTE ALU work, or compute an address
  writeBack(result);           // WRITE   store into a register or memory
}

Four phases, and notice the order of the first two. PC is incremented during fetch, before the instruction has run. That is why a jump instruction works by overwriting PC during execute: by then the "next instruction" has already been chosen, and the jump changes the choice. It is also why, on many architectures, a relative branch offset is measured from the address after the branch rather than from the branch itself.

Where the phases actually go

Fetch

Put PC on the address bus, read one word back into the instruction register (IR), advance PC. This is a memory access, and if the instruction is not in cache it is the slowest thing that will happen all instruction.

Decode

Pull the bit fields apart, look up what the opcode means, and read the source registers. Nothing has changed state yet.

Execute

The ALU does arithmetic, or computes a memory address, or evaluates a branch condition. Flags are set here. Nothing is committed yet.

Write back

The result lands in a register or in memory. Until this moment the instruction could still be abandoned, which is exactly what speculative execution relies on.

Raise n to 8 and the answer becomes 36, because the loop body runs three more times.

Try to break it

Overwrite the HALT at the end with a jump back to itself and the machine will spin forever — no error, no exception, just a program counter bouncing between two addresses. Nothing in the hardware knows the difference between a useful loop and a useless one. The demo caps the run at a few thousand phases so your tab survives; a real CPU has no such courtesy.

Pipelining, and where it breaks

The four-phase machine above wastes almost everything it owns. While the ALU is executing, the fetch unit sits idle. While the fetch unit is reading memory, the ALU sits idle. If each phase takes one clock tick, one instruction takes four ticks and three-quarters of the hardware is asleep at any moment.

Pipelining fixes this the way a laundry fixes it: start washing the second load while the first is in the dryer. Split the datapath into stages separated by latches, and let a different instruction occupy each stage. The classic textbook shape has five stages:

The classic five-stage pipeline
StageNameWhat happens
IFInstruction fetchRead the instruction from the instruction cache, advance PC.
IDInstruction decodeSplit the fields, read the source registers.
EXExecuteALU operation, address calculation, or branch resolution.
MEMMemory accessLoad or store, for the instructions that need it.
WBWrite backWrite the result into the register file.

The pipeline does not make any single instruction faster. An instruction still takes five cycles to get from one end to the other, and probably slightly longer than before because of the latches between stages. What changes is throughput: once the pipeline is full, one instruction finishes every cycle. Running n instructions takes n + 4 cycles instead of 5n. That is close to a fivefold speed-up for long runs, and it is entirely free — until the instructions start depending on each other.

The three kinds of hazard

Data hazard
An instruction needs a value that an earlier, still-in-flight instruction has not written yet. ADD R2, R1, R3 immediately after LW R1, 0(R10) wants R1 in its decode stage, but the load will not have R1 until its memory stage.
Control hazard
A branch changes PC, but the pipeline has already fetched the instructions that sequentially follow it. If the branch is taken, those fetches were wrong and must be thrown away.
Structural hazard
Two instructions in different stages want the same piece of hardware in the same cycle — for example a single memory port needed by both IF and MEM. Split instruction and data caches exist mostly to remove this one.

Two hardware tricks blunt the first two. Forwarding (also called bypassing) runs a wire from the output of one stage straight to the input of the next instruction's execute stage, so a value can be used the cycle after it is computed rather than waiting for it to reach the register file. Branch prediction guesses which way a branch will go and fetches down that path speculatively; if the guess was right, nothing is lost.

The one hazard forwarding cannot remove

A load produces its value at the end of MEM, one stage later than an ALU op produces its value at the end of EX. So an instruction that uses the result of the load immediately after it still has to wait one cycle no matter how much forwarding hardware you build. This is the load-use hazard, and it is why compilers try to schedule an unrelated instruction into the slot right after a load.

With forwarding on and the branch not taken, the eight instructions finish in 13 cycles against an ideal of 12. The single lost cycle is the load-use hazard, and nothing else stalls. Turn forwarding off and the same eight instructions take 19 cycles, because every dependent instruction now has to wait for its producer to reach write back. Forwarding is worth six cycles here, about a third of the runtime, for a handful of wires.

The branch toggle shows a subtler cost. With forwarding on and the branch taken, the run still finishes in 13 cycles — but only six instructions retire instead of eight, because two were fetched down the wrong path and discarded. Same wall-clock time, less work done: cycles per instruction climbs from 1.63 to 2.17. That is the real currency of a mispredicted branch.

Scale this up

This demo uses a five-stage pipeline, so a mispredicted branch throws away two instructions. Modern high-performance cores are fourteen to twenty stages deep and fetch several instructions per cycle, so a misprediction typically costs on the order of fifteen to twenty cycles of work. That is why branch predictors are now elaborate machine-learning-adjacent structures with multi-kilobyte history tables, and why branchless code — computing both sides and selecting with arithmetic — sometimes beats an if.

What a real CPU adds on top

The five-stage pipeline is a teaching model. A current desktop or phone core keeps the same fetch–decode–execute skeleton and then piles on five more ideas.

Superscalar issue
More than one instruction enters the pipeline per cycle. A wide core can decode four to six instructions and retire a similar number every cycle, so cycles per instruction can drop below 1. The metric usually gets flipped at this point and quoted as IPC, instructions per cycle.
Out-of-order execution
Instructions are held in a queue and dispatched as soon as their operands are ready, not in program order. A load that misses cache no longer freezes everything behind it; independent work runs past it. Results are then retired in the original program order so the visible state stays consistent.
Register renaming
The sixteen architectural registers are mapped onto a much larger pool of physical registers. Two instructions that both write RAX but are otherwise unrelated get different physical registers, so the false dependency disappears. This is what makes aggressive out-of-order execution possible.
Speculation
The core executes down the predicted path before it knows the branch outcome, and unwinds if it guessed wrong. The unwinding restores registers and memory, but it does not restore the cache — which is exactly the leak that Spectre and Meltdown exploited in 2018.
SIMD and multiple cores
One instruction operating on a vector of values at once (SSE, AVX, NEON, SVE), and several complete cores on one chip. Both give more work per cycle, and both require the software to be written to use them.
Why your code is not four times faster on a four-wide core

Superscalar width is an upper bound, not a promise. To issue four instructions in a cycle the core needs four instructions that are ready, independent, and use different execution ports. A chain of dependent operations — each one needing the previous result — runs at exactly one instruction per cycle no matter how wide the machine is. This is why algorithms with independent work (summing four partial totals and combining at the end) can beat the obvious single-accumulator loop by two or three times.

From source text to a running process

Nothing so far explains how a file of text becomes those numbers. Four steps, and they are worth keeping distinct because each one fails differently.

The classic compile pipeline, with the error you get when each step fails
StepInput → outputTypical failure
PreprocessSource → expanded sourceMissing header, macro expanded wrongly
CompileSource → assemblySyntax and type errors
AssembleAssembly → object file (machine code + a symbol table)Bad instruction for the target CPU
LinkObject files + libraries → one executableundefined reference, duplicate symbol
LoadExecutable on disk → process in memoryShared library not found at runtime

The linker's job is the one most people are hazy about. Each object file contains machine code with holes in it: the compiler knew you called printf but had no idea what address printf would end up at. The object file records "there is a call here, please fill in the address of the symbol printf" as a relocation entry. The linker collects every object file, decides a layout, resolves every symbol to an address, and patches the holes. Static linking copies library code into your executable; dynamic linking leaves a stub and lets the loader resolve it when the process starts.

Compiled, interpreted, and the middle ground

Ahead-of-time compiled

C, C++, Rust, Go. Source becomes native machine code before it runs. Fastest start, fastest steady state, one binary per platform, no runtime type information unless you build it yourself.

Interpreted

Classic Python, Ruby, shell. A program reads your program and acts on it, statement by statement. Portable and flexible; ten to a hundred times slower for tight numeric loops, because every operation carries interpretive overhead.

Bytecode plus a virtual machine

Java, C#, CPython internally. Source compiles once to a compact instruction set for an imaginary machine, and a VM executes that. Portability of an interpreter with a cheaper decode step.

Just-in-time compiled

JVM HotSpot, V8, .NET, PyPy. The VM watches which code is hot, compiles those parts to native machine code while the program is running, and re-optimises using facts it observed. Slow to warm up, then close to native.

A JIT can beat an ahead-of-time compiler in specific cases precisely because it knows things a static compiler cannot: that this polymorphic call site has only ever seen one type, that this branch has never once been taken, that this loop bound is always 3. It compiles for the program's actual behaviour and keeps a guard to bail out if the assumption breaks. The whole strategy is only possible because instructions are data you can write at runtime.

A language is not compiled or interpreted

These are properties of an implementation, not of a language. There are C interpreters and Python compilers. When someone says "Python is slow", the accurate statement is that the reference implementation, CPython, interprets bytecode without a JIT, so a numeric loop pays interpretive overhead per operation.

Clock speed, IPC and why GHz stopped rising

Performance decomposes into three multiplied factors, and this is the only formula in the chapter worth memorising:

the iron law of processor performance
time  =  instructions  ×  cycles per instruction  ×  seconds per cycle
         ─────────────     ──────────────────────     ────────────────
         your algorithm    the microarchitecture      the clock
         and compiler      and your memory access     and the physics

Three ways to go faster, and they belong to different people. Executing fewer instructions is an algorithm and compiler problem, and it is where the largest wins live: an O(n log n) sort beats an O(n2) sort by a margin no clock speed can close. Lowering cycles per instruction is mostly about cache behaviour and branch predictability, which chapter 5 covers. Shortening the cycle is the hardware vendor's job, and it stopped improving.

Clock frequency climbed steeply through the 1990s and then flattened around 2005, in the neighbourhood of 3–4 GHz, where it has broadly stayed. The reason is power. Dynamic power in CMOS scales roughly with capacitance × voltage² × frequency, and pushing frequency higher also requires higher voltage, so power rises faster than linearly and the heat becomes impossible to remove from a small die. Dennard scaling — the observation that shrinking transistors let you keep power density constant — broke down because leakage current stopped shrinking with everything else.

Transistor counts kept growing after that, so the extra transistors went into more cores, wider issue, bigger caches and specialised accelerators instead of a faster clock. That is the technical reason concurrency stopped being a niche skill: single-threaded performance now improves by a few percent a year, and the remaining headroom is in doing several things at once.

What this chapter buys you

Every later chapter leans on something here. Complexity analysis in chapter 10 counts operations because the other two factors are roughly constant. The cache work in chapter 5 is entirely about the middle term. Concurrency in chapters 6–8 exists because the third term stopped shrinking. And the whole idea of a data structure is a plan for arranging memory so the machine's ritual runs into fewer obstacles.

Check yourself

Why must the program counter be incremented during fetch rather than after the instruction finishes?

Because the instruction itself may want to change it. If PC were incremented after execute, a jump would set PC to the target during execute and then the increment would immediately move it one past the target. Incrementing during fetch makes "next instruction" the default, which execute can then override. It also matters for pipelining: the next fetch has to start before the current instruction finishes, so PC must already be pointing at the right place.

The toy machine has a 4-bit opcode and 16 words of memory. What limits does each of those impose, and which one bites first?

Four opcode bits allow 16 distinct operations; the machine defines 8, so there is room for 8 more. Sixteen words of memory is the harder limit — the demo programs already use 9 words of code plus 2 or 3 of data. The 8-bit immediate field can express addresses up to 255, far more memory than exists, so the address field is not the binding constraint. This mismatch between what an encoding can express and what the hardware provides is extremely common in real ISAs.

A five-stage pipeline runs 100 independent instructions with no hazards. How many cycles, and what is the speed-up over a non-pipelined machine that takes 5 cycles per instruction?

100 + 4 = 104 cycles. The non-pipelined machine takes 500. The speed-up is 500 / 104 ≈ 4.8×, approaching but never reaching the number of stages, because the first instruction still has to fill the pipeline. For 10 instructions the speed-up would only be 50 / 14 ≈ 3.6×, which is why pipelining pays off on long straight runs and pays much less on short, branch-heavy code.

Forwarding removes most data stalls. Why can it not remove the stall after a load?

Forwarding can only send a value backwards in time as far as the moment it exists. An ALU result exists at the end of EX, so it can reach the next instruction's EX. A loaded value does not exist until the end of MEM, one stage later, so the earliest it can reach a consumer's EX is two instructions later. An instruction immediately following the load must wait one cycle. Confirm it in demo 2: with forwarding on, the ADD that uses R1 executes in cycle 5, not cycle 4.

In demo 2, taking the branch does not change the total cycle count, yet the mispredict is described as costly. Explain.

Cycles are only half the measurement. The not-taken run finishes 8 instructions in 13 cycles; the taken run finishes 6 instructions in the same 13 cycles, because two fetched instructions were squashed and the correct target could not be fetched until the branch resolved. Equal time, less work: CPI rises from 1.63 to 2.17. Judging a pipeline by wall-clock cycles alone hides the waste; you need work-per-cycle to see it.

Someone claims their language is "compiled, therefore fast". What is wrong with the reasoning?

Two things. First, compiled versus interpreted is a property of an implementation, not a language. Second, the iron law says time = instructions × CPI × cycle time. Compilation attacks the first factor and helps the second a little. It does nothing about an algorithm that executes a quadratic number of operations, and nothing about a data layout that misses cache on every access. A well-written Python program using a good algorithm regularly beats a badly written C program using a poor one.

Ten things to carry forward

  1. Instructions and data are the same stuff. A program is numbers in memory that the CPU has been pointed at. Compilers, JITs and self-modifying code all depend on that.
  2. The program counter is the whole story. Every control-flow construct you know is a way of writing a value into PC.
  3. An instruction is a bit field. Opcode plus operands, packed into a fixed or variable width word. Assembly is the human-readable spelling of that number.
  4. The cycle is fetch, decode, execute, write back, and PC advances during fetch so that jumps can override it during execute.
  5. Pipelining raises throughput, not latency. n instructions in n + (stages − 1) cycles, once nothing gets in the way.
  6. Three hazards get in the way: data, control and structural. Forwarding fixes most data hazards; prediction hides most control hazards; separate caches remove the common structural one.
  7. The load-use hazard survives forwarding, because a loaded value simply does not exist early enough to forward.
  8. A mispredicted branch costs work, not necessarily time. Measure instructions retired per cycle, not cycles alone.
  9. Real cores add width, reordering, renaming and speculation on top of this skeleton, and every one of those is an attempt to keep the execution units busy despite dependencies and memory latency.
  10. Time = instructions × CPI × cycle time. The clock stopped improving around 2005; the two factors left are yours to control, and the algorithmic one is by far the larger lever.
