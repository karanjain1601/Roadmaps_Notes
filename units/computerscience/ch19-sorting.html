Sorting

A thousand random values need at least 8,530 comparisons — that is a theorem, not an estimate. Merge sort does it in 8,720. Bubble sort does it in 496,872. The gap between those two numbers is most of what algorithm design is for.

The properties that decide which one you want

Everyone learns the complexity column. The other four properties are what actually determine the choice in practice.

Stable
Records with equal keys keep their original relative order. This is what lets you sort by one field and then another to get a compound ordering, which is how every spreadsheet and data table works.
In place
Uses Θ(1) or Θ(log n) extra memory rather than Θ(n). Matters when the data barely fits, and matters less than people assume otherwise.
Adaptive
Runs faster on data that is already partly ordered. Real data very often is — appended logs, re-sorted tables, merged streams — so this is worth more than its reputation suggests.
Comparison-based
Uses only "is a before b?". Universal, and subject to the lower bound in section five. Sorts that look at the key's structure escape that bound.

Two rows deserve a second look. Selection sort does the most comparisons of any of them and the fewest moves — 2,970 against bubble's 763,167 — because it makes at most one swap per pass. If moving an element is expensive and comparing is cheap, that trade can be the right one. And merge sort's 8,720 comparisons are only 2.2% above the theoretical minimum, which is about as good as a comparison sort can be.

The quadratic sorts, and where they still win

Bubble sort

Repeatedly sweep the array swapping adjacent out-of-order pairs. With an early exit when a pass makes no swaps it becomes adaptive. Its only virtue is being easy to explain; there is no input on which it beats insertion sort.

Insertion sort

Take each element and slide it back into the sorted prefix. Stable, in place, adaptive, and genuinely the fastest option for small or nearly sorted arrays. Every serious sort in the world falls back to it.

Selection sort

Find the minimum of the rest and swap it into place. Always exactly n(n−1)/2 comparisons regardless of input — completely non-adaptive — but the fewest possible moves.

Why insertion sort survives

Below roughly 16 to 32 elements it beats every n log n sort outright. It has almost no per-call overhead, it works on contiguous memory with perfect locality, its inner loop is a handful of instructions, and it is adaptive. Every production sort — introsort, Timsort, pdqsort — switches to insertion sort once the partition is small enough, and that switch is worth a substantial fraction of their total speed.

Merge sort

Split in half, sort each half recursively, merge the two sorted halves. The recurrence is T(n) = 2T(n/2) + Θ(n), which chapter 10 solved as Θ(n log n) — and it is Θ(n log n) on every input, because the splitting does not depend on the data at all.

the merge, and the one character that makes it stable
merge(left, right):
  out = []
  i = j = 0
  while (i < left.length && j < right.length)
      if (left[i] <= right[j]) out.push(left[i++])   // <= not <
      else                    out.push(right[j++])
  return out.concat(rest of left, rest of right)

// with <= a tie takes from the LEFT half, which held the earlier
// elements. Change it to < and the sort silently stops being stable.

That comparison operator is the entire stability guarantee, and it is a one-character bug that no test of sortedness will catch. Measured on the demo's 1,000 random values, merge sort's best and worst inputs differ by a factor of only 1.77 — the most predictable of any sort here.

Its cost is Θ(n) extra space for the merge buffer. In-place merge algorithms exist but are complicated and slow enough that nobody uses them; the practical version allocates one scratch buffer up front and reuses it. Merge sort is also the natural algorithm for data that does not fit in memory — sort chunks, write them out, then merge the runs with a heap — and the only one of the classic sorts that parallelises cleanly.

Quicksort, and the pivot

Pick a pivot, partition the array so smaller elements go left and larger go right, recurse on each side. No merge step: the partition does the work, so it sorts in place.

Quicksort's average case is Θ(n log n) with the smallest constant factor of any comparison sort, because partitioning is a tight sequential scan with excellent locality. Its worst case is Θ(n²), and it happens when the pivot is consistently extreme, splitting off one element at a time.

The bad case is the common case

With a first-element pivot, already-sorted input is the worst case. On 1,000 sorted values it does 499,500 comparisons — exactly the quadratic count — against 10,873 on random data. Sorted or reverse-sorted input is not exotic: it is what you get from a database, a log file, or a previous sort. Switching to median-of-three brings the same input down to 9,520, a 52-fold reduction, and random pivot selection does the same thing.

Two more details matter in practice. Recurse into the smaller partition first and loop on the larger, which bounds stack depth at Θ(log n) even in the worst case. And use three-way partitioning — less than, equal to, greater than — when duplicates are likely, or an array of all-equal keys degrades to quadratic under a two-way scheme.

The lower bound, and how to beat it

Any sort that learns about the data only by comparing pairs needs at least log₂(n!) comparisons in the worst case. For n = 1,000 that is 8,530.

The argument is a counting argument. There are n! possible orderings and the algorithm must be able to produce each one, so the decision tree of comparisons must have at least n! leaves. A binary tree with n! leaves has height at least log₂(n!), and the height is the number of comparisons on the worst input. By Stirling's approximation, log₂(n!) ≈ n log₂ n − 1.44n, so the bound is Θ(n log n) and merge sort is asymptotically optimal.

It is a worst-case bound, not a per-input one

The bound says no comparison sort can beat log₂(n!) on every input, not that no sort can beat it on some input. Insertion sort on an already-sorted array of 1,000 elements uses 999 comparisons — a ninth of the bound — because the decision tree only needs one leaf for that path. Adaptive sorts live entirely in this gap.

Escaping the bound

The bound assumes the algorithm only ever asks "is a before b?". Look at the key's structure instead and it does not apply.

Counting sort over a range of 100 sorts 1,000 items in 2,099 operations and zero comparisons — against merge sort's 8,720. Widen the range to a million and the same 1,000 items cost 1,001,999 operations, because the algorithm must walk the whole count array whether or not it is occupied. That is the trap: counting sort's cost is driven by the key range, not the data size.

Radix sort fixes it by processing the key in digits. Three passes of 8 bits over 24-bit keys costs 6,765 operations for the same 1,000 items, and the cost now scales with the key width rather than its range. Note that radix sort requires each pass to be stable, since later passes must not disturb the ordering established by earlier ones — one of the few places where stability is a correctness condition rather than a convenience.

Stability, concretely

Sort a table of employees by name, then by department. If the second sort is stable, everyone within a department is still in name order and you have a compound sort for free. If it is not, the first sort was wasted.

Demo 1 tests this empirically rather than quoting a table: it tags every element with its original position, sorts data with only five distinct keys, and checks whether ties came out in their original order. Bubble, insertion and merge pass; selection, quicksort and heapsort fail. Any sort that swaps distant elements — which is exactly how selection, quicksort and heapsort get their speed — can jump one equal element over another.

Making any sort stable

Append the original index to the key and compare pairs. Ties are then broken by position, which is the definition of stability, at the cost of Θ(n) memory for the indices. This is worth knowing because several standard libraries offer only an unstable sort by default — C++'s std::sort is unstable and std::stable_sort is a separate function with a different memory profile.

What your standard library actually runs

None of the textbook algorithms is shipped unmodified. Every production sort is a hybrid that switches strategy based on what it observes.

Real implementations
NameUsed byHow it works
IntrosortC++ std::sortQuicksort, switching to heapsort past ~2 log n recursion depth, and to insertion sort under ~16 elements. Quicksort's speed with heapsort's guarantee.
TimsortPython, Java objects, Android, SwiftFinds existing sorted runs, extends short ones with insertion sort, merges with a stack of runs under invariants that keep the merges balanced. Stable, and linear on already-sorted input.
pdqsortRust, newer C++ libraries, GoPattern-defeating quicksort: detects sorted runs and adversarial patterns, switches partitioning scheme, uses branchless partitioning to avoid mispredictions.
Dual-pivot quicksortJava primitivesTwo pivots, three partitions. Fewer passes over memory, measurably faster on primitives — where stability does not matter because you cannot tell two equal ints apart.

Java's choice is the clearest illustration that stability is a language-visible decision. Arrays.sort(int[]) uses dual-pivot quicksort, which is unstable and faster; Arrays.sort(Object[]) uses Timsort, which is stable — because two equal integers are indistinguishable but two objects that compare equal may differ in every other field.

Choosing, in five lines

Use the standard library. If you need stability, use the stable variant explicitly. If the keys are small integers and the range is bounded, counting or radix sort will beat it. If the data is nearly sorted and your library is not Timsort, insertion sort may win outright. And if you only need the top k, do not sort at all — use the heap from chapter 16, at Θ(n log k).

Check yourself

Selection sort does more comparisons than bubble sort and is often preferred over it. Why?

Moves. On 1,000 random values selection sort does 499,500 comparisons and 2,970 moves; bubble sort does 496,872 comparisons and 763,167 moves. Selection makes at most one swap per pass, so it is the right choice when moving an element is far more expensive than comparing two — large records, or writes to flash memory where each write has a cost. When both are cheap, insertion sort beats them both.

Why is merge sort's running time the same on every input while quicksort's is not?

Because merge sort splits at the midpoint, which does not depend on the data, so the recursion tree is always perfectly balanced with log n levels of Θ(n) work. Quicksort splits at the pivot, whose position depends entirely on the values, so an unlucky pivot produces a 1-and-(n−1) split and a tree of depth n. Measured across random, sorted and reversed input, merge sort's counts vary by a factor of 1.77; quicksort with a first-element pivot varies by a factor of 46.

Quicksort with a first-element pivot is quadratic on sorted input. Why is that worse than it sounds?

Because sorted input is the normal case, not an unlucky one. Data arrives sorted from a database with an ORDER BY, from an append-only log, from a previous sort, or from a merge. The demo measures 499,500 comparisons on sorted input against 10,873 on random — the exact quadratic count. Median-of-three brings it to 9,520, a 52-fold reduction, and a random pivot does the same. This is also a denial-of-service vector: if an attacker can supply the array and knows your pivot rule, they can force the worst case deliberately.

Where does the log₂(n!) lower bound come from?

From counting outcomes. There are n! possible input orderings and the algorithm must distinguish all of them, so its decision tree of comparisons needs at least n! leaves. Each comparison has two outcomes, so a tree of height h has at most 2h leaves, giving h ≥ log₂(n!). For n = 1,000 that is 8,530, and merge sort's measured 8,720 is 2.2% above it. Stirling gives log₂(n!) ≈ n log₂ n − 1.44n, which is why the bound is Θ(n log n).

Insertion sort uses 999 comparisons on 1,000 sorted values. Does that violate the bound?

No, because the bound is a worst-case statement: no comparison sort can beat log₂(n!) on every input. Any single input can be handled in far fewer comparisons — the decision tree only needs a short path to that particular leaf. Insertion sort's short path happens to be the already-sorted case, which is what makes it adaptive. Its worst case is still 499,500, comfortably above the bound. Adaptive algorithms live entirely in this gap between the worst case and the common case.

When does counting sort lose to merge sort, and what fixes it?

When the key range dwarfs the element count. Counting sort is Θ(n + k), and it must allocate and walk a count array of size k whether or not the values are there. Sorting 1,000 items with keys up to 100 takes 2,099 operations; the same 1,000 items with keys up to a million take 1,001,999, over a hundred times merge sort's comparison count. Radix sort fixes it by processing the key in fixed-width digits, so the cost depends on the key's width rather than its range: three 8-bit passes over 24-bit keys cost 6,765 operations for the same 1,000 items.

Why does radix sort require its per-digit sort to be stable?

Because it sorts from the least significant digit upward, and each pass must preserve the ordering the previous passes established. Sorting by the tens digit has to leave items with the same tens digit in the order the units pass produced, or that information is destroyed. Here stability is a correctness condition rather than a convenience — it is the mechanism by which several single-digit sorts compose into a full-key sort. Counting sort is used for each pass precisely because it can be made stable by walking the input backwards when placing.

Ten things to carry forward

  1. Stability, in-placeness and adaptivity decide the choice more often than the complexity column does.
  2. Selection sort trades the most comparisons for the fewest moves — 2,970 against bubble sort's 763,167 on the same data.
  3. Insertion sort is genuinely fast below about 32 elements and adaptive, which is why every production sort falls back to it.
  4. Merge sort is Θ(n log n) on every input because its split ignores the data, and its measured count is 2.2% above optimal.
  5. One character makes merge sort stable. <= takes ties from the left half; < does not, and no sortedness test will catch it.
  6. Quicksort's worst case is sorted input with a naive pivot — 499,500 comparisons against 9,520 with median-of-three.
  7. log₂(n!) comparisons is a theorem, and it is 8,530 for a thousand elements.
  8. The bound is worst-case, not per-input, which is the whole space adaptive sorts occupy.
  9. Counting sort's cost follows the key range, not the data size, and radix sort fixes that by following the key width instead.
  10. Real libraries ship hybrids — introsort, Timsort, pdqsort — that detect what they are given and switch.
