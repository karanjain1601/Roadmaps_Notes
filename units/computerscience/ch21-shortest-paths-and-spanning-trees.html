Shortest paths and spanning trees

Dijkstra's algorithm does not merely run slowly on a graph with a negative edge. It returns the wrong answer, confidently, with no indication that anything happened — and understanding exactly why is the most useful thing in this chapter.

Relaxation, the common core

Every shortest-path algorithm in this chapter is built from one operation. Keep a tentative distance for each vertex, initially infinity except zero at the source, and repeatedly ask whether some edge offers a better route.

relax — the whole idea
relax(u, v, w):
    if (dist[u] + w < dist[v]) {
        dist[v] = dist[u] + w
        prev[v] = u
    }

// dist[] only ever decreases, and it is always the length of SOME
// real path. The algorithms differ only in which edges they relax,
// in what order, and how they know when to stop.

The gap between Dijkstra and Bellman-Ford is large. On a graph with 1,000 vertices and 5,000 edges, Dijkstra does roughly 59,795 units of work and Bellman-Ford does 5,000,000 — 84 times more. That is what you pay for the ability to handle negative weights, so the first question to ask about any weighted graph is whether it needs them.

Dijkstra

Grow a set of vertices whose shortest distance is final. Repeatedly take the unfinalised vertex with the smallest tentative distance, mark it done, and relax its outgoing edges. A priority queue makes "smallest tentative distance" cheap; that is the only data structure involved.

The correctness argument is one sentence, and it is worth reading carefully because it is exactly what breaks later. When a vertex is popped with tentative distance d, no shorter route to it can exist, because any other route must leave the finalised set through some vertex whose tentative distance is already ≥ d, and every subsequent edge only adds more.

Why negative weights break it

The correctness argument depended on "every subsequent edge only adds more". A negative edge destroys it: a route that looks worse now can become better later, but Dijkstra has already closed the door.

the smallest graph on which Dijkstra is wrong
  0 ──1──> 1 ──1──> 3
  │                 ▲
  └──5──> 2 ──-10───┘

  step 1: pop 0.  dist = [0, 1, 5, ∞]
  step 2: pop 1 (tentative 1).  relax 1→3.  dist[3] = 2
  step 3: pop 3 (tentative 2).  FINALISED at 2
  step 4: pop 2 (tentative 5).  relax 2→3: 5 + (-10) = -5 < 2
          … but 3 is already done, so the update is discarded.

  Dijkstra answers 2.  The true shortest path is -5.

Load the second preset in the demo and watch the finalisation order: 0 → 1 → 3 → 2. Vertex 3 is closed before vertex 2 is even examined. No error is raised, nothing looks wrong, and the answer is off by seven.

This matters more than it sounds

Negative weights are not exotic. Currency arbitrage uses negative log exchange rates, where a negative cycle is the profit opportunity. Task scheduling with rewards, network flow with costs, and difference constraints all produce them. And "we don't have negative weights" is a claim about your data, not your code — the failure is silent, so nothing will tell you when it stops being true.

Bellman-Ford

Give up on cleverness. Relax every edge, V−1 times. Since a shortest path in a graph with no negative cycle uses at most V−1 edges, and each full pass guarantees that every path of one more edge has been accounted for, after V−1 passes every distance is final.

The V-th pass is the interesting one. If any edge still relaxes, some path got shorter by adding a V-th edge, which is only possible if it went round a cycle of negative total weight. That gives negative-cycle detection for free, and there is no shortest path at all in that case — you can go round again for less. Load the third preset and Bellman-Ford flags it; Dijkstra returns numbers without comment.

The early exit

If a full pass changes nothing, every distance is final and you can stop. On graphs that are not adversarial this usually happens after a handful of passes rather than V−1, which is why Bellman-Ford's practical cost is often far below its Θ(V·E) bound. The demo's positive preset converges in 2 rounds rather than 4.

A*, and what a heuristic actually buys

Dijkstra explores in every direction equally, because it has no idea where the target is. A* adds an estimate h(v) of the remaining distance and orders the queue by f = g + h — cost so far plus estimated cost to go — which biases exploration toward the goal.

The guarantee depends on one property. A heuristic is admissible if it never over-estimates the true remaining cost. With an admissible heuristic A* returns the optimal path; without one it does not. Straight-line distance is admissible when edges are physical distances, because no route can be shorter than a straight line. Manhattan distance is admissible on a grid with unit-cost moves.

Inadmissible means wrong, not just slower

Consider two routes from 0 to 3: 0→1→3 costing 101, and 0→2→3 costing 51. With h(2) = 60, an over-estimate of the true 1, A* pops the goal via the first route at f = 101 while the better route still sits in the queue at f = 110. It returns 101. Dijkstra, which is exactly A* with h = 0 and therefore trivially admissible, returns 51. Speeding up a search with a heuristic you have not checked is a way of getting fast wrong answers.

A measurement that is not what you expect

On an empty 30 × 30 grid, searching from one corner to the other with unit-cost moves, all three of the following find the correct distance of 58:

The Manhattan heuristic on an open grid is exact — and it prunes nothing. Every monotone path from corner to corner is optimal, so f = g + h equals 58 at every single cell, and the whole grid is one enormous plateau of ties. A* has no reason to prefer any cell over any other and expands them all.

Breaking ties toward the larger g — preferring the node that has already made more progress — collapses it to 59 cells, a fifteenfold reduction that comes entirely from the tie-break rather than from the heuristic. Put a wall in the way, so the heuristic actually has to discriminate between directions, and A* expands 620 cells against Dijkstra's 871 for the same 87-step answer.

The general lesson

A heuristic helps in proportion to how much it differentiates between candidates, not to how accurate it is. A perfectly accurate heuristic that assigns the same value to everything is useless. This is why real pathfinders add a tiny tie-breaking term — a fraction of the cross product with the start-goal vector, or a preference for straight lines — and why that one line often matters more than the heuristic itself.

Minimum spanning trees

A different question about the same weighted graph: choose a subset of edges connecting every vertex, with no cycles, of minimum total weight. Not shortest paths — a minimum spanning tree minimises the total, not any individual route.

Both standard algorithms are greedy, and both are correct because of the same fact. The cut property: for any partition of the vertices into two sets, the lightest edge crossing the partition belongs to some minimum spanning tree. If it did not, adding it would create a cycle containing a heavier crossing edge, which you could remove for a lighter tree.

Kruskal

Sort every edge by weight and add each one that does not close a cycle. The cut is implicit: the lightest edge joining two different components is the lightest edge across that cut. Needs a union-find structure to answer "are these already connected?" quickly.

Prim

Grow one tree from a start vertex, repeatedly adding the lightest edge that reaches a vertex not yet in it. The cut is explicit: tree versus everything else. Needs a priority queue, exactly like Dijkstra.

On the seven-vertex preset both find total weight 39 and, in this case, the same six edges — but in completely different orders. Kruskal takes 0-3, 2-4, 3-5, 0-1, 1-4, 4-6, strictly by weight; Prim takes 0-3, 3-5, 0-1, 1-4, 4-2, 4-6, always adjacent to what it has already built.

An MST is not a shortest-path tree

They are different problems with different answers. On the demo's graph the MST has total weight 39, and the shortest path from 0 to 6 is 22 — but travelling from 0 to 6 within the MST costs more than 22, because the MST minimised the total edge weight rather than any individual route. If you need everyone connected as cheaply as possible, build an MST; if you need each vertex reachable as quickly as possible, run Dijkstra. Confusing the two is a common and expensive modelling error.

Load the tied-weights preset and the two algorithms still both report weight 3, but there is no longer a single correct answer: with ties, several distinct minimum spanning trees exist and which one you get depends on the algorithm and on the sort's tie-breaking.

Union-find

Kruskal needs one operation: are u and v already in the same component, and if not, merge them. The disjoint-set structure does both in near-constant amortised time using two tricks together.

the two optimisations, which only work as a pair
// path compression: on the way up, point every node straight at the root
find(x):  while (p[x] !== x) { p[x] = p[p[x]]; x = p[x] }; return x

// union by rank: attach the shorter tree under the taller one
union(a, b):
    a = find(a); b = find(b)
    if (a === b) return false              // already connected — this edge closes a cycle
    if (rank[a] < rank[b]) swap(a, b)
    p[b] = a
    if (rank[a] === rank[b]) rank[a]++
    return true

With both, m operations on n elements cost Θ(m · α(n)), where α is the inverse Ackermann function — below 5 for any input that will ever exist, so effectively constant. Union-find turns up far beyond Kruskal: connected components in a stream, cycle detection, image segmentation, Kruskal-like clustering, and percolation.

Reweighting, and why it is not as easy as it looks

The tempting fix for negative edges is to add a constant to every weight until they are all positive. It does not work: adding c to each edge adds c × (number of edges) to each path, which penalises paths with more hops and can change which one is shortest. Johnson's algorithm does it correctly by computing a per-vertex potential with Bellman-Ford and reweighting each edge as w(u,v) + p(u) − p(v), which telescopes along any path so all paths between the same pair shift by the same amount.

Check yourself

Why exactly does a negative edge break Dijkstra?

Because its correctness rests on a single claim: when a vertex is popped with tentative distance d, nothing shorter can arrive later, since any alternative route leaves the finalised set through a vertex already at ≥ d and edges only add. A negative edge makes "edges only add" false. In the demo's second preset, vertex 3 is finalised at 2 before vertex 2 is examined at all; the −10 edge would give −5, but the update is discarded because 3 is already closed. Dijkstra reports 2 with no error.

Why does Bellman-Ford relax every edge exactly V−1 times?

Because a shortest path with no negative cycle visits each vertex at most once, so it uses at most V−1 edges. Each full pass over all edges guarantees that every shortest path of one more edge has been found, so after V−1 passes every distance is final. The V-th pass is then a test: if anything still improves, some path got shorter by adding another edge, which requires a negative cycle. That is why the algorithm gets cycle detection for free, and why it is the only one here that can report "there is no shortest path".

Why can't you just add a constant to every weight to make them positive?

Because it adds the constant once per edge, not once per path. A two-edge route gains 2c and a five-edge route gains 5c, so paths with more hops are penalised and the shortest path can change. Johnson's algorithm does it properly with a per-vertex potential: reweight w(u,v) to w + p(u) − p(v), which telescopes along any path so every route between the same pair shifts by the same p(source) − p(target) and the ordering is preserved.

A* with an exact Manhattan heuristic expands all 900 cells of an open 30 × 30 grid. How can that be?

Because every monotone path from corner to corner is optimal, so f = g + h equals 58 at every cell in the grid. A* orders by f, and when every candidate ties there is nothing to prefer — the whole grid is one plateau and it expands all of it. Breaking ties toward larger g, so the node that has made more progress wins, drops it to 59 cells: a fifteenfold reduction that comes from the tie-break, not the heuristic. A heuristic helps in proportion to how much it discriminates, not how accurate it is.

What goes wrong with an inadmissible heuristic?

You lose optimality, not just speed. Take two routes to a target costing 101 and 51, with h = 60 at the second route's midpoint where the true remaining cost is 1. A* pops the goal via the expensive route at f = 101 while the cheap route is still queued at f = 110, and returns 101. Dijkstra — which is A* with h = 0, trivially admissible — returns 51. Over-estimating heuristics are sometimes used deliberately in games, where a good-enough path found fast beats an optimal one found slowly, but that has to be a choice rather than an accident.

Prim and Kruskal pick edges in completely different orders. Why must the total match?

Because both rely on the cut property: for any partition of the vertices, the lightest edge crossing it is in some minimum spanning tree. Kruskal's cut is implicit — the lightest edge joining two components — and Prim's is explicit — tree versus the rest. Both therefore only ever add edges that belong to a minimum tree, so the totals agree at 39 on the demo's graph even though the orders differ. The edge sets can differ too, when weights tie: an MST is unique only if all edge weights are distinct.

You need every office connected to the network as cheaply as possible. MST or shortest paths?

MST — it minimises the total cable laid. But be clear about what you are giving up: the MST does not minimise the distance between any particular pair. On the demo's graph the shortest route from 0 to 6 costs 22, while travelling between them inside the MST costs more, because the tree optimised the global total. If latency between specific pairs matters, an MST is the wrong structure and you want shortest-path routing, or a compromise like a shortest-path tree from a hub.

Ten things to carry forward

  1. Every algorithm here is relaxation — they differ only in which edges, in what order, and how they know to stop.
  2. Dijkstra's correctness rests on edges only adding cost. One negative edge and the argument collapses.
  3. The failure is silent. Dijkstra returns 2 where the answer is −5, with no error and nothing to notice.
  4. Bellman-Ford relaxes everything V−1 times and gets negative-cycle detection from the V-th pass for free.
  5. The price is 84× the work on a 1,000-vertex, 5,000-edge graph — so ask whether you need negative weights before paying it.
  6. Adding a constant to every weight does not fix negative edges, because it charges per edge and so penalises longer paths.
  7. A* is Dijkstra plus an estimate, and it is only correct if that estimate never over-estimates.
  8. An inadmissible heuristic gives wrong answers, not slow ones — 101 where the truth is 51.
  9. A heuristic helps by discriminating, not by being accurate. An exact one that ties everywhere prunes nothing, and tie-breaking bought a 15× speed-up where the heuristic bought none.
  10. An MST minimises the total, not any route. Prim and Kruskal always agree on the total, and an MST is unique only when all weights differ.
