Asynchronism: queues, streams, jobs

Moving work off the request path is the single most effective architectural move available: it makes responses fast, failures retryable, and load absorbable. It also introduces duplicates, reordering, backlogs and a second system to operate. This chapter is what queues actually guarantee, what they do not, and the patterns that make the difference survivable.

17.1What going asynchronous buys

  1. Latency. The user waits for the durable write, not for the six things that follow it. A 900 ms checkout becomes 80 ms plus a queue append.
  2. Load levelling. A queue absorbs a spike that would otherwise have to be provisioned for. Ten times the traffic for two minutes becomes a backlog that drains in twenty, instead of an outage.
  3. Retryability. A failed synchronous call is an error the user sees. A failed message is retried, with backoff, until it succeeds or is quarantined.
  4. Decoupling. The producer does not know who consumes. Adding a fourth consumer of "order placed" requires no change to the order service — which is the property that lets teams move independently.
  5. Fan-out. One event, many independent reactions, each failing and retrying on its own.

And what it costs: eventual consistency everywhere downstream, duplicate deliveries you must tolerate, ordering you must not assume, a backlog that can grow without anyone noticing, and a whole second system with its own failure modes, capacity limits and on-call burden.

The test for what goes behind a queue

Does the user need the result of this work to consider their action complete? Publishing a post: the post must be durable before you return success. Generating thumbnails, notifying followers, updating the search index, recomputing trending, sending the confirmation email: none of these. If the answer is "they need to know it will happen, not that it has happened", it belongs in a queue.

17.2Queues and logs are different things

Both are called "message brokers" and they have genuinely different semantics. Choosing the wrong one produces a system that fights its infrastructure.

Queue versus log
Queue (RabbitMQ, SQS, Redis lists)Log (Kafka, Kinesis, Pulsar, Redpanda)
ModelMessages are handed out and removedAn append-only, immutable, ordered sequence per partition
After consumptionDeleted on acknowledgementStill there — consumers hold an offset
Multiple consumer groupsNeeds fan-out to separate queuesNative — each group reads independently at its own pace
ReplayGoneReset the offset and reprocess history
OrderingPer queue, lost with competing consumersStrict per partition

A useful heuristic: if the message is a command ("resize this image") it wants a queue; if it is an event ("an order was placed") it wants a log, because you cannot know today who will want to react to it tomorrow.

17.3Delivery semantics

What a broker can promise
SemanticMechanismFailure modeUse when
At most onceAcknowledge before processingA crash loses the message silentlyMetrics, telemetry, anything where a gap is cheaper than a duplicate
At least onceAcknowledge after processing; redeliver if no ackDuplicates on retry, crash, or a slow consumer exceeding its timeoutAlmost everything — combined with idempotent consumers
Exactly onceBroker transactions plus deduplicationOnly holds inside the broker's own boundaryStream processing wholly within one system
"Exactly once" is a scoped claim, not a general one

Kafka's exactly-once semantics are real and useful: within Kafka, a consume-transform-produce cycle can be made atomic, so reprocessing after a crash does not duplicate the output. What it cannot do is make a side effect in another system exactly once — sending an email, charging a card, calling a third-party API. The moment a message causes an effect outside the broker's transaction, you are back to at-least-once delivery plus an idempotent handler. In a design discussion the correct phrasing is "at-least-once delivery with effectively-once processing", and the mechanism is a deduplication key, not a broker setting.

An idempotent consumer 
def handle(msg):
    # The dedup key must come from the MESSAGE, not be generated here.
    # Prefer a business identity over a message id: two different
    # messages describing the same event should collapse.
    key = msg.headers.get("event_id") or f"{msg.type}:{msg.payload['order_id']}"

    with db.transaction():
        claimed = db.execute(
            "INSERT INTO processed_events (key, at) VALUES (?, now()) "
            "ON CONFLICT DO NOTHING", key)
        if claimed.rowcount == 0:
            return ACK                    # already handled; drop silently

        do_the_work(msg)                  # side effect and the claim commit
                                          # together, or neither happens
    return ACK

# Retain processed_events for longer than the maximum possible redelivery
# window — typically days — then prune. An unbounded dedup table is a
# slow-motion outage of its own.

17.4Ordering

Global ordering across a distributed system is expensive and almost never required. What is usually required is ordering per entity: this user's events in order, this conversation's messages in order, this account's transactions in order. That is cheap, and it is what partitioning gives you.

  • Partition by the entity key. All events for order_42 go to the same partition and are therefore consumed in order by one consumer. Different orders proceed in parallel.
  • Ordering dies with competing consumers. Two workers pulling from one queue will finish out of order regardless of the order they received messages in. If you need order, you need one consumer per key — which is what partitioning enforces.
  • A retry breaks order too. Message 5 fails, goes back on the queue, and is redelivered after message 6 has already been processed. If order matters, the consumer must either block the partition on failure or the messages must be commutative.
  • Prefer designing for out-of-order. Carry a version or timestamp and ignore anything older than what you have applied. Ordering-independent handlers are far more robust than ordering-dependent ones, and they let you parallelise freely.

17.5Consumers, scaling and rebalancing

In a queue, adding consumers adds throughput linearly until the broker or the downstream becomes the bottleneck. In a log, parallelism is capped by the partition count: with 12 partitions, the 13th consumer in a group gets nothing. Partition count is therefore a capacity decision made in advance, and increasing it later changes which keys map where — breaking the per-key ordering guarantee across the change.

Rebalance storms

When a consumer joins, leaves or is presumed dead, the group rebalances and — in the naive protocol — every consumer stops, gives up its partitions and is reassigned. A consumer that takes too long between polls (because one message is slow) is evicted, which triggers a rebalance, which stalls everyone, which makes more consumers look slow. Defences: keep per-message processing well under the poll interval, or hand long work to a separate thread and keep polling; use cooperative/incremental rebalancing so only the affected partitions move; and set the session timeout deliberately rather than leaving the default.

17.6Failure: retries, poison messages, dead letters

  • Distinguish transient from permanent. A timeout is worth retrying; a validation error never will be. Retrying permanent failures wastes capacity and delays the messages behind them — fail those straight to the dead-letter queue.
  • Exponential backoff with jitter, and a cap. Without jitter, everything that failed together retries together, forever.
  • Bound the attempts, then dead-letter. The count belongs in the message headers, not in the consumer's memory.
  • Alert on the DLQ. A dead-letter queue nobody monitors is a data-loss mechanism with extra steps. Alert on depth greater than zero, and on its age.
  • Make redrive routine. Fix the bug, replay the DLQ back into the main queue. This only works if consumers are idempotent — which is the same requirement as everything else in this chapter.
  • Visibility timeouts must exceed processing time. If a consumer takes 90 seconds and the timeout is 30, the message is redelivered to a second consumer while the first is still working — and now you are running it three times concurrently. This is one of the most common causes of mysterious duplicate work.

17.7Backlogs and backpressure

A queue's job is to absorb bursts. Its danger is that it absorbs them silently — nobody notices until a backlog is hours deep and the business has been shipping stale results all afternoon.

The only two numbers that matter 
depth  = messages waiting
age    = how old is the OLDEST unprocessed message

Little's Law:   drain time = depth / (consumer rate − producer rate)

  depth 500 000, consumers 2 000/s, producers 1 800/s
    → net drain 200/s → 2 500 s ≈ 42 minutes, IF producers stay flat

  If producers ≥ consumers, drain time is infinite and the queue
  is not a buffer, it is a leak.

ALERT ON AGE, NOT DEPTH. Depth of 100 000 is fine at a million
messages a second and catastrophic at ten. Age is expressed in the
same units as your SLO, which makes it directly actionable.

Backpressure is telling the producer to slow down. Systems that lack it fail in the worst possible way: the queue grows until the broker runs out of disk, and then everything stops at once. Options, in order of preference: bound the queue and reject or block producers when it is full; rate-limit at the entry point so excess is refused cheaply at the edge with a 429; shed low-priority messages while the backlog is deep; or, at minimum, autoscale consumers on age and alert loudly when the backlog cannot drain.

17.8The dual-write problem and the outbox

The most common correctness bug in event-driven systems, and it looks entirely innocent:

The bug 
db.save(order)              # succeeds
broker.publish(OrderPlaced) # ... process dies here

Result: the order exists and nobody downstream knows.
No warehouse pick, no confirmation email, no analytics row.
Nothing retries, because nothing recorded that it needed to.

Reversing the order is no better:
broker.publish(OrderPlaced) # succeeds
db.save(order)              # fails

Now the warehouse is picking an order that does not exist.

There is no way to make two independent systems commit atomically without a distributed transaction, and distributed transactions across a database and a broker are unavailable in practice. The transactional outbox resolves it by making the publication part of the database transaction:

Two ways to run the relay. A poller reads unsent outbox rows on an interval — simple, works on any database, adds latency and load. Change data capture tails the database's own replication log and publishes from it — lower latency, no polling load, and it captures every change including those made by migrations and manual fixes. CDC is the more robust option and is what Debezium and similar tools exist to do.

The mirror-image pattern is the inbox: a consumer records the message id it has processed in the same transaction as the effect, which is exactly the idempotent consumer from §17.3. Outbox on the way out, inbox on the way in, and the seam between systems becomes safe.

17.9Sagas

A business operation spanning several services cannot be one transaction. A saga makes it a sequence of local transactions, each with a compensating action that semantically undoes it.

Booking a trip 
  step                     compensation
  ─────────────────────    ────────────────────────
  1  reserve seat          release seat
  2  reserve hotel room    cancel room
  3  charge card           refund card
  4  issue tickets         void tickets

If step 3 fails: run compensations for 2 and 1, in reverse order.

Properties you must accept:
  · NOT isolated — another user can observe the seat reserved
    and then released. Use a "pending" status so the intermediate
    state is legible rather than confusing.
  · Compensations are semantic, not rollbacks. A refund is not the
    absence of a charge; both appear on the statement.
  · Compensations can fail too. They must be retried and idempotent,
    and some need human escalation.
  · Some steps are irreversible (an email was sent). Order the saga
    so irreversible steps come last.
Two ways to run one
ChoreographyOrchestration
HowEach service reacts to events and emits its ownA coordinator holds the state machine and issues commands
CouplingLow — no central componentServices depend on the orchestrator
Understanding the flowRequires reading every serviceOne place shows the whole process
Debugging a stuck sagaHard — no single stateQuery the coordinator

Beyond roughly three steps, orchestration wins in practice, because the ability to answer "where is order 8817 stuck and why" is worth more than the coupling you avoid. The orchestrator's state must itself be durable — this is what workflow engines such as Temporal, Step Functions and Camunda provide.

Two design details that come up repeatedly. Missed schedules: decide explicitly whether a job that did not run at 02:00 because the fleet was down should run late, skip, or run twice for the two windows — the right answer differs for "send daily digest" and "charge subscriptions". And returning results to a user when the work is asynchronous: return 202 Accepted with a job id and a status URL for polling; use a webhook when the caller is another system; push over SSE or WebSocket when a person is watching a progress bar. Polling with a sensible interval is underrated — it is simple, stateless and survives disconnects.

17.11Operating the async layer

  • Alert on backlog age, DLQ depth and consumer error rate. These three catch nearly everything.
  • Track end-to-end latency, from the moment the event was produced to the moment its effect is visible — not just consumer processing time, which hides queue wait entirely.
  • Use a schema registry for event payloads, with compatibility checking on publish. An event with no schema is a contract that everyone has independently guessed at.
  • Include a correlation id and a producer timestamp in every message, so a trace can cross the async boundary — otherwise every distributed trace stops dead at the queue.
  • Version events additively, exactly as in Chapter 16. Old consumers must tolerate new fields and unknown enum values.
  • Rehearse replay. If you rely on being able to reprocess a topic, do it in staging on real volume, and know how long it takes and what it does to downstream systems.
Your consumers are idempotent, so why does the visibility timeout still matter?

Because idempotency prevents duplicate effects, not duplicate work. If processing takes 90 seconds and the timeout is 30, the message is redelivered twice while the first attempt is still running — so three consumers are doing the same expensive job simultaneously, and only the first to commit accomplishes anything. That is a threefold waste of capacity, which under load is the difference between draining a backlog and never catching up. Worse, if the work involves an external call, that system may see three requests regardless of your dedup logic. Set the timeout above your p99.9 processing time, or better, extend the lease periodically while working so slow items do not get redelivered at all.

The order service writes to the database and publishes an event. Why is that wrong, and what is the smallest fix?

It is a dual write: two independent systems, no atomicity, so a crash between them leaves the order saved and unpublished (silent loss downstream) or published and unsaved (downstream acting on nothing). The smallest fix is a transactional outbox — insert a row into an outbox table in the same transaction as the order, and have a separate relay read that table and publish. Publication becomes as durable as the order itself. The relay is at-least-once, since it can crash after publishing and before marking the row sent, so consumers must dedupe — which they should be doing anyway. If you want lower latency and no polling load, drive the relay from the database's replication log with change data capture instead.

Your Kafka topic has 12 partitions and you need more consumer throughput. You add a 20th consumer. What happens?

Eight consumers sit idle. Within a consumer group each partition is assigned to exactly one consumer, so parallelism is capped by partition count. You have also just triggered a rebalance, which briefly stops all consumption. The real options: increase partitions (which changes the key-to-partition mapping, so per-key ordering is not preserved across the change, and existing consumers must handle the reassignment); make each consumer faster by batching, increasing concurrency inside the consumer, or removing whatever downstream call dominates; or, if ordering is not needed, decouple fetching from processing — one poller feeding a local worker pool, with careful offset management so you only commit what has actually been processed. The lesson for design is that partition count is a capacity decision you make in advance, and it is worth over-provisioning it at the start.

Recap

  1. Move work off the request path when the user does not need its result — it buys latency, load levelling, retryability, decoupling and fan-out.
  2. Queues distribute commands; logs record events and let many groups read independently and replay.
  3. Assume at-least-once. "Exactly once" holds only inside a broker's boundary; effectively-once comes from an idempotent consumer with a dedup key.
  4. Order per entity, not globally, by partitioning on the entity key — and prefer handlers that do not care about order.
  5. Log parallelism is capped by partition count. Choose it generously up front.
  6. Bound retries, use jittered backoff, dead-letter permanent failures, and alert on the DLQ.
  7. Visibility timeout must exceed p99.9 processing time, or you triple your own work.
  8. Alert on backlog age, not depth. Age is in the same units as your SLO.
  9. Never dual-write. Use a transactional outbox, relayed by a poller or CDC.
  10. Sagas trade isolation for progress; orchestrate rather than choreograph once there are more than about three steps.
