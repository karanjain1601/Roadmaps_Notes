Monitoring and observability

A design is not finished when it works. It is finished when you can tell that it is working, find out quickly when it is not, and answer a question you did not anticipate. This chapter covers the three signals and what each costs, the frameworks that stop you guessing what to measure, cardinality as the thing that actually bankrupts you, and burn-rate alerting — the only alerting scheme that reliably wakes people for the right reasons.

~35 min read Metrics · logs · traces · RED/USE · alerting 2 interactive panels Prerequisite: chapter 4

18.1Monitoring, observability, and the difference that matters

Monitoring is watching for conditions you anticipated: is the error rate above 1%, is disk above 85%. Observability is the ability to answer questions you did not anticipate: why are requests from Android clients in Brazil failing only for accounts created this week? The first is a set of alerts; the second is a property of the data you collect — specifically, whether it retains enough dimensions to slice along an axis nobody thought of in advance.

The practical implication is about where you aggregate. A pre-aggregated counter of "total errors" answers one question forever. The same errors recorded with attributes — endpoint, status, region, client version, tenant — answer thousands, at a cost. Most of this chapter is about managing that cost without collapsing back to numbers that cannot explain anything.

A fourth signal is worth knowing: continuous profiling, which samples CPU and memory stacks in production. It answers "which function is burning the CPU right now", a question no other signal can. It is cheap enough to run permanently on modern runtimes and is chronically underused.

How they compose in an incident

A metric tells you something is wrong and when it started. A dashboard slice tells you which dimension — one region, one endpoint, one client version. A trace tells you where in the call graph the time or the error appears. A log line tells you exactly what that request did. Skipping a step is how incidents run long: people jump from "errors are up" straight to reading logs, and drown. The signals form a funnel and are worth using in order.

18.3Metrics: types and traps

Counter
Only goes up; you query its rate. http_requests_total. Resets on restart, which the query engine handles for you — so never compute rates yourself in application code.
Gauge
A value that moves in both directions: queue depth, memory in use, active connections, temperature.
Histogram
Counts observations into buckets, so percentiles can be computed after aggregating across instances. This is the only correct way to get a fleet-wide p99.
Summary
Percentiles computed per instance. Cheaper to query and mathematically un-aggregatable — see below.
You cannot average percentiles

Ten instances each reporting a p99 of 100 ms does not mean the fleet's p99 is 100 ms. Percentiles are not linear, and the average of ten p99s is a number with no meaning at all — it can be far below the true fleet p99 when one instance is slow, which is exactly the case you built the alert for. Emit histograms and let the query engine sum the buckets before computing the quantile. If your dashboards show "avg(p99)" anywhere, they are lying to you, and they are lying most during an incident.

Cardinality is the thing that bankrupts you

Each unique combination of label values is a separate time series, stored and indexed independently. Series count is the product of the cardinalities of every label, and products grow explosively.

How it happens 
http_requests_total{ method, status, endpoint, region }
  5 methods × 8 statuses × 40 endpoints × 4 regions   =  6 400 series
  Fine.

Someone adds a user id "for debugging":
  × 2 000 000 users                        = 12 800 000 000 series
  The metrics system falls over within the hour.

Labels that are ALWAYS wrong:
  user id · session id · request id · trace id · email
  full URL with path parameters (/orders/8f2c1…)
  raw error message · timestamp · IP address

Those belong in logs and traces, which are built for high
cardinality. Metrics are built for bounded dimensions.

The rule: a label's value set must be small and bounded by design, not merely small today. Normalise URL paths to route templates (/orders/{id}), bucket continuous values, and treat any label whose cardinality grows with traffic as a bug.

18.4What to measure: RED, USE and the golden signals

Three frameworks that between them cover almost everything, and prevent the usual failure of instrumenting whatever was easy.

Pick by what you are measuring
FrameworkApplies toMeasure
REDRequest-driven servicesRate (requests/s), Errors (failed/s or as a ratio), Duration (a latency histogram)
USEResources: CPU, disk, network, poolsUtilisation (% busy), Saturation (queue depth / wait), Errors (drops, retries)
Four golden signalsAnything user-facingLatency, traffic, errors, saturation — RED plus saturation

Saturation is the one people omit and the one with the most predictive power. Utilisation tells you how busy something is; saturation tells you how much work is waiting — the queue depth, the pool wait time, the run queue length. Per Chapter 3, latency is a hyperbola in utilisation, so saturation starts climbing while utilisation still looks acceptable. It is your earliest reliable warning.

For each dependency your service calls, emit RED metrics from the caller's side as well. The provider's dashboard says the database is fine; yours says calls to it are timing out. Both can be true — the difference is the connection pool, the network, or a slow query only you issue — and only the caller-side view finds it.

18.5Logs

  • Structured, always. JSON or logfmt with typed fields, never interpolated prose. {"event":"payment_failed","order_id":"o91","reason":"insufficient_funds","amount_cents":4999} is queryable; "Payment failed for order o91 because of insufficient funds" is a regular expression waiting to break.
  • One correlation id through everything. Generated at the edge, propagated on every call and every message, present in every log line. Without it, correlating a user's failure across six services is manual work; with it, it is one query.
  • Levels with a policy. ERROR means a human should look; WARN means it is degraded but handled; INFO is the record of what happened; DEBUG is off in production, and enableable per request or per tenant when you need it.
  • Sample the boring ones. Log every error, and 1% of successes. You lose nothing diagnostically and cut volume by two orders of magnitude.
  • Never log secrets or personal data. Redact at the logging library, not by remembering — because the one place you forget is the one that ends up in an incident report. Field-level allow-lists beat deny-lists.
  • Derive metrics from logs sparingly. It works and it is expensive; a counter costs a millionth of what the equivalent log query costs. Use logs to explain, metrics to alert.

18.6Traces

A trace is a tree of spans — each span an operation with a start, a duration, attributes and a parent. The trace id and parent span id travel in request headers (traceparent, per W3C) and in message metadata, which is how the tree is assembled from services that never talk to each other.

Sampling strategies
StrategyHowTrade-off
Head samplingDecide at the first span, propagate the decisionCheap and simple. You throw away the slow and failing traces you actually wanted
Tail samplingBuffer the whole trace, decide after it completesKeep every error and every slow trace. Needs a collector holding traces in memory until complete
Rate-limited headN traces per second per endpointGuarantees coverage of rare endpoints that percentage sampling would miss entirely

Tail sampling is what you want if you can afford the collector: keep 100% of errors, 100% of anything slower than a threshold, and 0.1% of the rest. The traces you need during an incident are precisely the ones head sampling discards. Instrument HTTP and RPC boundaries, database and cache calls, queue publish and consume, and any expensive internal computation — and add attributes for tenant, route and version, since traces are where high cardinality belongs.

Traces stop dead at a queue unless you carry the context

The natural boundary of a trace is a synchronous call. Publish a message and the trace ends; a consumer starts a new, unrelated one. Put the trace context in the message headers and link the consumer span to the producer's, and you can follow an order from the checkout button through the outbox, the broker, three consumers and back to the confirmation email. Without it you have two disconnected halves of every asynchronous flow — which is most of your interesting flows.

18.7Alerting that works

Two rules cover most of it.

Alert on symptoms, not causes. "Error rate for checkout exceeds the SLO" is a symptom — it is always worth waking someone for, whatever caused it. "CPU above 80%" is a cause, and it is usually fine: a service can run at 90% CPU while serving perfectly. Cause-based alerts produce false pages when the cause is benign, and miss real outages caused by something you did not think to alert on. Keep cause metrics on dashboards for diagnosis, and page on user-visible symptoms.

Every page must be actionable. If the recipient's only possible response is "yes, I see it too", it should not have been a page. The test: can you write a runbook with a first step? If not, it is a dashboard panel, not an alert.

Burn-rate alerting

The problem with "error rate above 1% for 5 minutes" is that it is simultaneously too sensitive (a 90-second blip pages you) and too insensitive (0.9% errors for three days silently destroys a month's budget). Burn-rate alerting fixes both by measuring consumption of the error budget from Chapter 4.

The definition 
burn rate = observed error rate / (1 − SLO)

  SLO 99.9%  →  budget is 0.1% errors
  observed 1% errors  →  burn rate 10×
  At 10× you consume a 30-day budget in 3 days.

The standard multi-window, multi-burn scheme:

  burn ≥ 14.4× over 1h   (and 5m)   → PAGE   2% of budget gone
  burn ≥ 6×    over 6h   (and 30m)  → PAGE   5% of budget gone
  burn ≥ 3×    over 24h  (and 2h)   → TICKET 10% gone
  burn ≥ 1×    over 72h  (and 6h)   → TICKET 10% gone

The short second window stops an alert firing on an incident that
has already ended; the long window stops it firing on a blip.

18.8The five kinds of monitoring

Coverage checklist for a design review
KindQuestionTypical signals
HealthIs each component alive and able to work?Liveness and readiness checks, dependency probes, instance counts
AvailabilityCan a user complete the core journey?SLIs measured at the edge, plus synthetic checks running the journey continuously
PerformanceIs it fast enough, and where is the time?Latency histograms per route, saturation, traces, real-user monitoring
SecurityIs anyone doing something they should not?Auth failure rates, permission denials, anomalous access patterns, audit logs
UsageWho uses what, how much, and what does it cost?Per-tenant request and storage counters, feature adoption, cost per request

Two are habitually missing. Synthetic monitoring — a robot performing the real user journey from outside your network every minute — catches whole classes of failure that internal metrics cannot see: an expired certificate, a broken DNS record, a CDN misconfiguration, a JavaScript bundle that fails to load. Your servers report perfect health while nobody can use the product. And usage monitoring is what lets you answer "which customer caused this spike" and "what does this feature cost to run", both of which turn out to be operational questions as often as commercial ones.

18.9Dashboards

Two kinds, and conflating them is why dashboards rot. A service dashboard is small, standard across every service, and answers "is this healthy" in five seconds:

  1. Request rate, split by status class.
  2. Error rate against the SLO threshold, with the error budget remaining.
  3. Latency p50/p95/p99, with the SLO threshold drawn on it.
  4. Saturation: the resource nearest its limit — pool wait, queue depth, CPU, connections.
  5. Dependencies: RED for each downstream call, from this service's point of view.

A debugging dashboard is deep, specific to one subsystem, and exists to answer a question you had during an incident. Build them freely, link them from the runbook, and delete them when the subsystem changes. Attempting to make one dashboard do both jobs produces a wall of forty panels that nobody can read under pressure.

Practical details that matter more than they should: put the SLO threshold as a line on the graph, so "is this bad" needs no interpretation; annotate deploys on the time axis, because the answer is usually "the deploy"; and make every panel's time range linked, so shifting one shifts all.

18.10Controlling the cost

Observability routinely reaches 10–30% of infrastructure spend, and unlike most spend it grows with traffic and with the number of things you instrument. Four levers, roughly in order of value:

  • Cardinality discipline. The single biggest lever. Audit series counts by metric, and reject unbounded labels in code review.
  • Sampling. Tail sampling for traces; 1% of successful logs; full fidelity for errors.
  • Retention tiers. Full resolution for a week, downsampled for a year. Nobody queries per-second data from nine months ago.
  • Drop what nobody queries. Most systems can report which metrics have never appeared in a dashboard or an alert. That list is usually long.
Your service dashboard shows the average of each instance's p99 latency. Why is that dangerous, and what should it show?

Percentiles do not average. If nine instances have a p99 of 50 ms and one has 3 000 ms, the mean of the ten p99s is 345 ms — a number describing no request that occurred, and one that badly understates the true fleet p99 while also failing to reveal that a single instance is broken. It fails in exactly the situation you built the panel for. Emit latency as a histogram with shared bucket boundaries, sum the buckets across instances at query time, and compute the quantile from the merged distribution. Then add a second panel showing p99 by instance, which is what makes a single sick host visible instead of averaged away.

Why alert on burn rate rather than on "error rate above 1% for five minutes"?

Because a fixed threshold cannot express both urgency and significance. A 90-second spike to 5% errors crosses it and pages someone at 3 a.m. for an event that is already over and consumed 0.1% of the month's budget. Meanwhile 0.5% errors sustained for four days never crosses it and quietly burns the entire budget. Burn rate normalises the error rate by the budget, so the alert means "at this rate you will exhaust the month", and pairing a long window with a short one ensures the alert both requires a sustained problem and stops firing when it ends. The result is fewer pages, each of which corresponds to something that genuinely threatens the objective you agreed to.

A user reports a failure. Your metrics look fine. What is the most likely explanation and what would have caught it?

Most likely: the failure is in a dimension your aggregate metrics wash out — one region, one client version, one tenant, one endpoint — or it is outside your servers entirely, in DNS, TLS, the CDN, or an asset that failed to load. Aggregate error rate over millions of requests moves imperceptibly when one tenant is completely broken. What catches it: metrics with enough (bounded) dimensions to slice by region, route and version; per-tenant usage metrics so a single customer's error rate is visible; synthetic checks running the real journey from outside the network, which is the only signal that sees an expired certificate or a broken bundle; and real-user monitoring from the browser, which measures what actually happened to the user rather than what happened to your server.

Recap

  1. Monitoring answers anticipated questions; observability answers new ones. The difference is how many dimensions survive aggregation.
  2. Metrics to alert, traces to locate, logs to explain. Use them in that order during an incident.
  3. Emit histograms, not summaries. Percentiles cannot be averaged across instances.
  4. Cardinality is a product. Never label a metric with a user, session, request or trace id — those belong in logs and traces.
  5. RED for services, USE for resources, and never skip saturation — it moves before utilisation looks alarming.
  6. Emit dependency metrics from the caller's side. Both dashboards can be right and disagree.
  7. Carry the trace context through queues, or every asynchronous flow is two disconnected halves.
  8. Page on symptoms, not causes, and only when there is a first step in a runbook.
  9. Use multi-window multi-burn-rate alerts so pages correspond to real threats to the SLO.
  10. Add synthetic checks. They catch the outages where every internal signal says everything is fine.
