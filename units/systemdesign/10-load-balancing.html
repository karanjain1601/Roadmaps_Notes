Load balancers and reverse proxies

The box that decides which of your servers handles a request, and therefore the box that decides how badly one slow server ruins everyone's day. This chapter covers the L4/L7 split, the balancing algorithms with a simulation showing why the obvious one is the worst, health checking that catches half-dead nodes, and how the load balancer itself avoids being the single point of failure.

~35 min read L4/L7 · algorithms · health checks · HA 2 interactive panels Prerequisite: chapters 3, 4

10.1Four boxes that all sit in the same place

The vocabulary overlaps confusingly because the products overlap. What distinguishes them is whose interests they serve.

Forward proxy
Sits in front of clients, on their behalf. Corporate egress filtering, caching for a network, hiding client addresses. Not part of your service.
Reverse proxy
Sits in front of servers, on their behalf. Terminates TLS, serves cached content, rewrites requests, hides the topology behind it. nginx, HAProxy, Envoy, Caddy.
Load balancer
A reverse proxy whose defining job is choosing among several equivalent backends and removing unhealthy ones. Every load balancer is a reverse proxy; not every reverse proxy balances.
API gateway
A load balancer that also knows about your API: authentication, rate limiting per key, request validation, response aggregation, protocol translation. Discussed in Chapter 11.

The practical arrangement in most large systems is both: an L4 layer at the edge that is stateless, absurdly fast, and spreads connections across a fleet of L7 proxies, which then make the intelligent per-request decisions. The L4 tier survives at network speed and needs almost no configuration; the L7 tier holds the logic that changes weekly.

L4 balancing plus long-lived connections is a load imbalance generator

An L4 balancer assigns a whole connection to a backend. With HTTP/1.1 keep-alive, gRPC, or HTTP/2, a client opens one connection and sends thousands of requests down it — so the balancing decision was made once, for what turned out to be an enormous amount of work. Add a backend and it gets zero traffic, because no new connections are being made. The standard fixes are an L7 proxy that balances per request, a maximum connection lifetime that forces periodic rebalancing, or client-side load balancing that is aware of the backend set.

Why "power of two choices" is the quiet winner

Choosing the least loaded of two randomly picked servers reduces the maximum load from O(log n / log log n) — the result for pure random — to O(log log n). That is an exponential improvement for one extra comparison, and it needs no global state, which matters because in a real deployment there are many load balancers and none of them knows the others' decisions. Perfect least-connections across a fleet of balancers is not achievable anyway; P2C gets most of the benefit while being honest about that. It is the default in Envoy for good reason.

10.4Health checking

Choosing well among healthy backends matters less than not choosing dead ones. Two mechanisms, and you want both.

Active health checks
The balancer polls each backend on a schedule — GET /healthz every few seconds, N consecutive failures to eject, M consecutive successes to restore. Simple and predictable. Its weakness is that it tests a synthetic request, so a backend that answers /healthz instantly while failing every real request stays in the pool.
Passive health checks / outlier ejection
The balancer watches the real traffic it is already sending and ejects backends whose error rate or latency is a statistical outlier relative to their peers. This is what catches grey failure, and the relative comparison matters: if every backend is at 5% errors, that is a dependency problem and ejecting hosts makes it worse.

Three parameters govern the behaviour and all three are worth setting deliberately:

  • Interval × threshold = detection time. Two seconds by three failures is six seconds of users hitting a dead backend. Faster detection means more false positives from GC pauses and brief spikes.
  • Ejection duration with backoff. Eject for 30 seconds, then let a probe through; if it fails again, eject for longer. This prevents flapping without permanently losing capacity.
  • Panic threshold. Never eject more than a set fraction — typically 50%. If the majority of backends look unhealthy, the health check or a shared dependency is far more likely to be the problem than every server dying at once, so send traffic to possibly-broken hosts rather than to none.

10.5Session persistence, and why to avoid it

Sticky sessions pin a client to a backend, usually with a cookie the balancer sets, sometimes by hashing the source address. It exists because some application keeps state in local memory.

The costs are steep. Load becomes uneven, because sessions are long-lived and unevenly active. Deploys become disruptive, because restarting a backend logs out everyone pinned to it. Autoscaling barely works, because new instances receive only new sessions. And source-IP hashing is actively unreliable — an entire office behind one NAT address is one "client", and a mobile client's address changes as it moves.

Where the state should go instead
  1. In a signed token held by the client (a JWT or a signed cookie) for small, non-secret, non-revokable-in-a-hurry state. No server storage at all.
  2. In a shared store — Redis or a database — keyed by session id. One extra sub-millisecond lookup per request, and every backend becomes interchangeable.
  3. Nowhere: re-derive it from the request. Most "session state" is a user id and a set of preferences that could be loaded on demand.

Affinity is still legitimate as a performance optimisation — consistent hashing on a cache key so a backend's local cache stays warm — but then it must be advisory. If the preferred backend is unavailable, the request goes elsewhere and still works.

10.6Connections, TLS and the details that leak

Keep-alive on both sides
The balancer should reuse connections to backends, or you pay a TCP handshake per request and burn ports. Watch for the classic mismatch: the backend's idle timeout shorter than the balancer's, so the backend closes a connection at the moment the balancer sends a request down it, producing intermittent 502s that are maddening to trace. Make the balancer's idle timeout shorter than the backend's.
Connection draining
When removing a backend for a deploy, stop sending it new requests but let in-flight ones finish, with a deadline. Without draining, every deploy kills a burst of live requests. The full sequence is: mark unready → wait for the balancer to notice → drain → then terminate. Applications must handle SIGTERM by failing readiness first and exiting only after in-flight work is done.
Slow start
A freshly started backend has cold caches, an unwarmed JIT and empty connection pools. Least-connections sees an empty server and floods it, so its first thousand requests are slow and it may fall over. Slow start ramps its weight over 30–60 seconds.
TLS termination vs passthrough
Terminating at the balancer lets it read requests (needed for L7 anything) and centralises certificate management. Passthrough keeps traffic encrypted end to end, which some compliance regimes require, at the cost of L4-only behaviour. The common middle ground is terminate at the edge and re-encrypt to the backend.
Losing the client's identity
Once a proxy is in the path, the backend sees the proxy's address. X-Forwarded-For and Forwarded carry the original for HTTP; the PROXY protocol does it for L4. Two hazards: these headers are client-supplied unless the proxy overwrites them, so trusting them naively lets anyone spoof an address past your rate limiter or IP allow-list; and if you forget them entirely, every log line and every rate limit sees one address for the whole internet.

10.7Who balances the balancer?

Four mechanisms, used in combination:

  • Anycast + ECMP. Many machines announce the same address; routers hash each flow onto one of them. Adding capacity is announcing the address from another machine. This is how large-scale L4 tiers work.
  • Floating / virtual IP. A pair of balancers share an address; a protocol like VRRP moves it to the survivor within seconds. Simple, common in self-hosted setups, and limited to a pair.
  • DNS across balancers. Multiple A records, health-checked. Slow (see Chapter 8) but it is the only mechanism that works across regions.
  • Client-side load balancing. The client gets the backend list from a discovery service and balances itself, removing the middle box from the data path entirely. Lowest latency, no shared bottleneck; costs you a smart client library in every language and a rollout problem when the policy changes. This is what a service mesh automates by putting that smart client in a sidecar.

10.8How load balancers cause outages

Failure modes that originate at this layer

Timeout mismatchBalancer timeout is longer than the client's, so work continues on requests nobody is waiting forTimeout budgets that shrink at each hop, and cancellation propagation
You add four new servers to a pool of eight. Traffic to them stays near zero. What is going on?

Almost certainly long-lived connections plus connection-level balancing. Existing clients already hold established connections to the original eight and keep reusing them, so the new servers only receive traffic when a new connection is made — which, with keep-alive or HTTP/2, is rarely. Confirm by looking at established connections per backend rather than requests per second. Fixes: balance per request at L7; set a maximum connection lifetime or maximum requests per connection so clients periodically reconnect and get rebalanced; or, if clients are internal, use client-side balancing that watches the backend set. A related variant with the same symptom is sticky sessions, where existing sessions never migrate.

Round robin and least connections both look fine in your load test. In production, one backend's p99 is ten times the others. Why might least connections be the better choice?

Because the load test almost certainly used homogeneous machines and uniform request costs, which is the one case where round robin is optimal. In production, machines differ (noisy neighbours, older hardware, a node running a background compaction) and request costs vary by orders of magnitude. Round robin keeps sending a fixed share to the struggling server regardless, so its queue grows without bound while others idle. Least connections — or power of two choices — notices the growing in-flight count and routes around it automatically, which is a form of automatic grey-failure mitigation you get for free. Run the simulator above with one backend slowed down and the difference is immediate.

Why is a deep health check that queries the database a risky thing to put in a load balancer's config?

Because it converts a partial dependency problem into a total outage. Every backend shares the database, so when the database has a brief hiccup every backend fails its health check at the same moment and the balancer removes the entire pool — turning "some requests are slow" into "the service does not exist". It also creates a feedback loop, because health checks themselves add database load. The right structure is a shallow liveness check for the balancer's remove-from-pool decision, a readiness check that covers only local startup concerns, and deep dependency checks exported as metrics for alerting and for outlier ejection that compares backends to each other rather than to an absolute standard. Plus a panic threshold so that mass unhealthiness is treated as a measurement problem rather than obeyed.

Recap

  1. L4 is fast and connection-scoped; L7 is per request and can act on content. Large systems use L4 at the edge feeding an L7 tier.
  2. Round robin balances counts, not work. Least connections and power-of-two-choices adapt to slow backends automatically.
  3. Power of two choices is the default worth picking: near-least-connections behaviour with no shared state, which matters because balancers do not see each other's decisions.
  4. Use active checks for dead backends and outlier ejection for half-dead ones, with a panic threshold that refuses to eject more than half the fleet.
  5. Avoid sticky sessions. Put state in a token or a shared store; keep affinity only as an advisory cache optimisation.
  6. Draining, slow start and timeout ordering are where deploys quietly break — and where intermittent 502s come from.
  7. Preserve the client address deliberately with X-Forwarded-For or PROXY protocol, and overwrite it at the trusted edge so it cannot be spoofed.
  8. Long-lived connections defeat connection-level balancing. Bound connection lifetime or balance per request.
  9. Retries at the balancer amplify overload. Use retry budgets, not unlimited retries.
