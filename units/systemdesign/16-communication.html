Communication: protocols and API styles

Two services talking is where most of a distributed system's latency and most of its subtle bugs live. This chapter goes down to the handshakes that cost you round trips, up through the four API styles and what each is actually good at, and then spends real time on idempotency and versioning — the two things that decide whether your API survives contact with retries and time.

~45 min read TCP/TLS/HTTP · REST · gRPC · GraphQL · idempotency 2 interactive panels Prerequisite: chapter 3

16.1What a request costs before it starts

Before any application byte moves, a client typically pays: a DNS lookup, a TCP handshake, and a TLS handshake. Each is at least one round trip, and a round trip is physics — 1 ms inside a datacenter, 70 ms across a continent, 150 ms across the world. Counting round trips is how you predict latency without measuring anything.

Connection reuse eliminates every setup cost, which is why keep-alive, connection pooling and long-lived gRPC channels matter far more than protocol version for server-to-server traffic. Protocol version matters most for the first request from a cold client on a slow network.

16.2TCP and UDP

The transport choice
TCPUDP
ConnectionThree-way handshake before any dataNone — send and hope
ReliabilityRetransmits lost segmentsNothing. Lost is lost
OrderingBytes delivered in orderDatagrams may arrive in any order, or twice
Flow / congestion controlYes — adapts to the networkYou implement it or you melt the network
Head-of-line blockingYes — one lost segment stalls everything behind itNo — each datagram is independent
Overhead20+ byte header, state per connection8-byte header, no state
Use forAlmost everythingDNS, real-time voice and video, game state, metrics, QUIC's foundation

The reason to know this in a system design is head-of-line blocking, which drives the entire HTTP version story. TCP guarantees in-order delivery of a byte stream, so if segment 5 is lost, segments 6–20 sit in the kernel buffer, already received, and cannot be given to the application until 5 is retransmitted. On a lossy mobile link that is a stall of one round trip or more, applied to everything sharing that connection.

The reason to reach for UDP is when late data is worthless. In a voice call, a packet that arrives 400 ms late cannot be played — retransmitting it wastes bandwidth and delays everything behind it, so it is better to drop it and conceal the gap. Same for live game state: you want the newest position, not a complete history.

16.3TLS

TLS 1.3 cut the handshake from two round trips to one by removing the negotiation round trip: the client guesses the key-exchange parameters and sends its key share immediately. It also removed most of the legacy cipher suites, which is why "just use 1.3" is unusually good advice.

  • Session resumption lets a returning client skip the handshake with a ticket from the previous session — the single biggest TLS optimisation for repeat visitors.
  • 0-RTT sends application data in the very first packet. It is not replay-safe: an attacker can capture and resend that data, so it must be restricted to idempotent requests. Never allow 0-RTT for a request that charges a card.
  • mTLS makes the client present a certificate too, which is how services authenticate each other without shared secrets in config. Its real cost is certificate lifecycle — issuance, rotation, revocation — which is exactly what a service mesh automates.
  • Terminating close to the user converts multi-round-trip handshakes from intercontinental to local. This is a large part of what a CDN buys even for uncacheable traffic.

16.4The HTTP versions

HTTP/1.1
One request at a time per connection. Browsers work around it by opening about six connections per host — which is why domain sharding used to help. Pipelining was specified and is unusable in practice because responses must return in order, so one slow response blocks the rest.
HTTP/2
One connection, many concurrent streams, binary framing, and header compression (HPACK) which matters more than it sounds when every request carries a kilobyte of cookies. Removes application-level head-of-line blocking — but not TCP's, so a single lost packet still stalls every stream on that connection. Server push was specified, barely used, and has been removed from browsers.
HTTP/3 / QUIC
The same multiplexing, but over UDP with its own reliability and ordering per stream. A lost packet stalls only the stream it belonged to. It also merges transport and crypto setup into one round trip, and supports connection migration: the connection is identified by a connection ID rather than by the four-tuple, so a phone moving from wifi to cellular keeps its connection instead of re-handshaking.
HTTP/2 made one problem worse

One connection carrying everything is excellent for browsers and awkward for infrastructure. An L4 load balancer assigns whole connections, so all of a client's requests pin to one backend — the imbalance described in Chapter 10. It is more acute for gRPC, where a service opens a single long-lived channel and then sends millions of requests down it. The fixes are the same: balance per request at L7, cap the connection's lifetime or maximum streams, or use client-side load balancing that knows the backend set.

Status codes people get wrong: 400 means the request is malformed, 422 that it is well-formed but semantically invalid, 401 that you are not authenticated, 403 that you are but may not do this, 404 that it does not exist (or that you should not know it does), 409 that there is a state conflict, 412 that a precondition failed, 429 that you are rate limited — always with Retry-After — and 503 that the service is temporarily unavailable, also with Retry-After. The distinction that matters operationally is retryable versus not: 5xx and 429 are retryable, 4xx generally is not, and a client that retries 4xx is generating load that cannot possibly succeed.

REST, done properly

  • Nouns in paths, verbs in methods. POST /orders, not POST /createOrder. When an action genuinely is not CRUD, a sub-resource is cleaner than contorting the model: POST /orders/{id}/cancellation.
  • Cursor pagination. Return an opaque nextCursor; never ?page=N&size=M, which is O(offset) at the database and produces duplicates and gaps when the underlying list changes.
  • Envelope your collections — { "items": [...], "nextCursor": "..." } — so you can add metadata later without breaking parsers. A bare top-level array is a versioning dead end.
  • Filtering, sorting and sparse fields as query parameters, with a documented and bounded set. Unbounded filtering is how a public API becomes an unindexed query generator.
  • Consistent errors — RFC 7807 problem details gives you type, title, status, detail and instance, plus room for your own fields. Include a machine-readable code and a correlation id; clients should never parse prose.
  • HATEOAS — hypermedia links in responses — is in the original definition and is rarely implemented, because clients are written against documentation, not discovered at runtime. Know what it means; do not lose an argument over it.

gRPC

Protobuf schemas compiled into client and server stubs, over HTTP/2. Four call shapes: unary, server streaming, client streaming and bidirectional. What you get is a binary wire format that is typically 3–10× smaller than the equivalent JSON and far cheaper to parse, a schema that cannot drift from the code, native streaming, and deadlines that propagate — a caller's remaining time budget travels with the call, so downstream services stop working on requests nobody is waiting for. That last feature is worth more than the performance for most systems.

The costs: browsers cannot speak it without a proxy; you cannot inspect traffic with curl; HTTP caching does not apply; and load balancing needs care because of the single long-lived connection.

GraphQL

The client sends a query describing exactly the shape it wants, and gets exactly that. It solves two real problems — over-fetching (a mobile client downloading a 40-field object to show two) and under-fetching (six round trips to assemble one screen) — and it does so without a new endpoint per client, which is why it appears wherever one backend serves web, iOS, Android and partners with divergent needs.

What GraphQL moves rather than removes
  • N+1 moves to the server. A query for 50 posts each with an author becomes 51 database calls unless you batch. DataLoader-style per-request batching is not optional; it is part of the runtime.
  • Caching gets hard. Everything is a POST to one URL, so HTTP caching is unavailable. You need persisted queries (send a hash instead of a query, which also lets you cache at the edge and reject unknown queries) or a client-side normalised cache.
  • Cost becomes unbounded. A client can request a deeply nested query that fans out enormously. You need depth limits, complexity scoring, and query timeouts — for a public API, an allow-list.
  • Observability gets harder. Every request is POST /graphql, so per-endpoint metrics are meaningless until you instrument per operation name and per resolver.

If the flow is server-to-client only, prefer SSE over WebSockets: it is plain HTTP, it works through proxies, browsers reconnect for you, and it costs a fraction of the implementation effort. Reach for WebSockets when the client genuinely needs to push.

Scaling persistent connections is a different discipline from scaling requests. Five million connections is not five million requests per second; it is five million file descriptors and their memory, spread across a dedicated stateless gateway tier. Because a connection lives on exactly one gateway, delivering a message to a user requires knowing which gateway — a presence registry mapping user to gateway, plus a pub/sub fabric between gateways. The business logic stays elsewhere. That split is the standard chat architecture and is worked through in Chapter 22.

16.8Idempotency

A client sends a request and the response never arrives. It cannot tell whether the server never received it, processed it and the reply was lost, or is still working. Its only options are to retry — risking a duplicate — or to give up — risking a lost operation. Every network client eventually retries, so your server must make duplicates harmless. This is not an edge case; it is the normal condition of distributed systems.

The idempotency key protocol 
POST /v1/payments
Idempotency-Key: 6f1e2c40-7b2a-4a1e-9a7f-2e2c0b9d1a55
{ "amount": 4999, "currency": "GBP", "source": "card_9x" }

Server:
  1  Look up the key in a store, scoped to (account, endpoint).
  2  Not found  → claim it atomically (INSERT … ON CONFLICT DO NOTHING).
                  If the claim fails, another request has it: go to 4.
  3  Process the request. Persist the response body and status
     against the key, in the SAME transaction as the side effect.
  4  Found, completed  → return the stored response verbatim, with a
                         header marking it a replay. Do NOT re-execute.
     Found, in flight  → return 409, so the client backs off and retries.
  5  Expire keys after 24h–7d. Long enough for any sane retry,
     short enough that the table does not grow forever.

Also: if the same key arrives with a DIFFERENT body, that is a client
bug — return 422 rather than silently serving the first response.

The subtlety that trips people: storing the response and performing the side effect must be atomic. If you charge the card and then crash before recording the key, the retry charges again — you have implemented the illusion of idempotency without the property. If the side effect is in an external system, record the key and an "in progress" marker first, then reconcile: the external system almost certainly accepts an idempotency key of its own, and passing yours through is how the guarantee composes.

16.9Versioning and compatibility

Any API with more than one client is permanently in a state where old and new callers coexist. Two rules cover most of it.

Change classification
Safe (additive)Breaking
Adding an optional request fieldAdding a required request field
Adding a response fieldRemoving or renaming a response field
Adding a new endpoint or methodChanging a field's type or its units
Adding a new enum value if clients tolerate unknownsAdding an enum value if they do not — design for it from day one
Relaxing a validation ruleTightening one
Making a response field nullable that was never guaranteedChanging default behaviour, pagination size, or error codes
  • Version in the URI (/v1/) for public APIs: visible, cacheable, trivially routable, and easy to reason about in logs. Header-based versioning is theoretically cleaner and practically harder to debug.
  • Version rarely. Every version is a codebase you maintain. Prefer additive evolution, and reserve a new major version for changes that cannot be made additively.
  • Protobuf's rules exist for this: never reuse a field number, never change a field's type, mark removed fields reserved. Follow them and old and new binaries interoperate indefinitely.
  • Deprecate on a schedule — announce, instrument who is still calling it, contact them, then remove. Without usage metrics per client you can never actually delete anything.

The practical guidance: JSON at the public edge, because debuggability and universality genuinely matter there; a binary schema format internally, where volume is high and both ends are yours. And regardless of format, enable compression — gzip or brotli on JSON typically saves 60–80%, which is usually a larger win than switching formats and costs one configuration line.

A mobile client on a 200 ms link loads a screen needing six API calls. What are your options, ranked?

Six sequential calls is 1.2 seconds of pure round trips. In order of value: parallelise them if there are no dependencies, which turns 6 × 200 into 200 ms plus the slowest response — often the entire fix. Aggregate them into one endpoint or a backend-for-frontend that fans out server-side over fast internal links, turning six client round trips into one. Use GraphQL if the client's needs vary enough that a fixed aggregate keeps changing. Reuse the connection, so at least the six calls do not each pay a handshake. And render progressively — show the screen with the two calls that returned and fill the rest in — because perceived latency is what the user experiences. Notice that only one of these is a protocol change; the rest are shape changes, and they matter more.

Why does a POST need an idempotency key when the client could just check whether the operation succeeded before retrying?

Because "check then retry" is itself a race. Between the check and the retry, the original request — which the server may still be processing — can complete, and now you have two. It also requires a query endpoint that can answer "did my specific request happen?", which needs a client-supplied identifier — at which point you have reinvented the idempotency key, just with an extra round trip and a window of inconsistency. The key does the same job atomically at the moment of the write, with a claim that either succeeds or reveals the in-flight duplicate. And it is strictly cheaper: no extra call on the happy path.

When is GraphQL the wrong choice?

When there is one client with stable needs — a fixed set of REST endpoints is simpler, cacheable at the edge, and trivially observable. When the API is public and untrusted, because arbitrary query shapes are an unbounded cost surface that requires complexity limits, depth limits and probably an allow-list, at which point you have a REST API with extra steps. When responses are highly cacheable, since POST-to-one-URL forfeits HTTP caching, which is often the single biggest performance lever you have. And for service-to-service calls, where gRPC's typed contracts, binary encoding and deadline propagation matter more than client-specified response shapes. GraphQL earns its complexity when several clients with genuinely divergent and changing data needs are served by one backend team.

Recap

  1. Count round trips. Cold HTTP/1.1 with TLS 1.2 is five before your first byte; an open connection is one.
  2. TCP's in-order guarantee is head-of-line blocking — the reason HTTP/3 moved to UDP and recovers loss per stream.
  3. TLS 1.3 halves the handshake; resumption removes it; 0-RTT is not replay-safe.
  4. HTTP/2's single connection helps browsers and hurts L4 balancing. Balance per request or bound connection lifetime.
  5. REST for public and cacheable, gRPC for internal and high-volume, GraphQL for many divergent clients, and never a state-changing GET.
  6. GraphQL relocates N+1, caching and cost control into your server; batching, persisted queries and complexity limits are mandatory, not optional.
  7. Prefer SSE to WebSockets when the flow is one-directional.
  8. Idempotency keys, with the response stored atomically alongside the side effect. Retries are the normal case, not the exception.
  9. Evolve additively; version rarely; never reuse a protobuf field number; instrument usage before deprecating anything.
