Scaling a database

There is a correct order to do this in, and it is cheapest-first rather than most-impressive-first. Almost every database that "needs sharding" turns out to need an index, a cache, or the removal of one pathological query. This chapter is the ladder, with the arithmetic for each rung and the migration mechanics for the rungs that hurt.

~40 min read Tuning · replicas · pooling · federation · sharding 2 interactive panels Prerequisite: chapters 6, 7, 12

13.1The ladder

  1. 1
    Fix the queries
    Add the missing index, kill the N+1, stop selecting columns you do not use. Typical gain: 10–1000× on the affected query, for hours of work, with no new infrastructure.
  2. 2
    Cache
    Put the expensive, repeated, tolerably-stale results in memory. Typical gain: reads drop by 10–100×. Covered in Chapter 15.
  3. 3
    Buy a bigger machine
    Unfashionable and frequently correct. Doubling RAM can turn a disk-bound workload into a memory-bound one, which is a step change, not an increment. Gain: up to the largest instance available, which is very large.
  4. 4
    Add read replicas
    Reads scale linearly with replicas; writes do not scale at all. Gain: read capacity × N, at the cost of replication lag becoming visible to users.
  5. 5
    Pool connections
    Not a scaling technique so much as a prerequisite — without it, adding application servers reduces database throughput. Gain: removes a ceiling you did not know you had.
  6. 6
    Federate by function
    Move a table group to its own database: sessions, events, audit. Gain: a whole machine's worth of capacity per split, and far easier than sharding because the split follows existing boundaries.
  7. 7
    Denormalise and precompute
    Materialised views, counter tables, read models. Gain: turns an expensive aggregate into a lookup, paid for with write complexity and staleness.
  8. 8
    Partition and archive
    Split one table by time or range within one database; move cold partitions to cheap storage. Gain: keeps the hot working set small, which is often the entire problem.
  9. 9
    Shard
    Split rows across independent databases. Gain: unlimited write capacity. Cost: everything in Chapter 7.
  10. 10
    Use a different store
    Some access patterns should never have been in a relational database — search, time series, graphs, blobs. Gain: the right data structure. See Chapter 14.

Which rung are you on?

Describe the workload; the model works out where the ceiling is and what the next move buys.

13.2Query tuning that pays

The recurring offenders, roughly by how much load they cause
PatternWhat it doesFix
N+1 queriesOne query for a list, then one per item. 200 rows on a page becomes 201 round tripsJoin, or a single WHERE id IN (…) batch. In an ORM this is eager loading
Missing indexA sequential scan on every request. Usually one query causing 80% of the loadFind it in the slow query log or pg_stat_statements, ordered by total time — not by mean time
SELECT *Fetches large columns nobody reads and defeats covering indexesName the columns. Often converts an index scan into an index-only scan
OFFSET paginationOFFSET 100000 reads and discards 100 000 rowsKeyset pagination: WHERE (created_at, id) < (?, ?) ORDER BY … LIMIT 20
COUNT(*) on a big tableScans everything, every time, for a number nobody reads preciselyAn approximate count from statistics, a maintained counter, or "1000+"
Implicit castsComparing a text column to a number disables the index silentlyMatch the types; check the plan for a cast
Unbounded queriesNo LIMIT; one bad request returns ten million rows and exhausts memoryAlways bound, and set statement_timeout so no query can run forever
Long transactionsHold locks and block cleanup for the whole databaseShort transactions; no network calls inside; alert on oldest transaction age
Sort by total time, not by slowest

The query taking 4 seconds and running twice an hour costs 8 seconds an hour. The query taking 12 milliseconds and running 5 000 times a second costs 60 seconds of database time per second — it is the entire load, and it will never appear in a slow query log with a one-second threshold. Rank by calls × mean_time. The biggest wins are nearly always fast queries running absurdly often.

13.3Read replicas

The mechanics are in Chapter 6; the design questions here are about routing.

  • Route deliberately, not automatically. Some frameworks send all reads to replicas by default, which breaks read-your-writes everywhere at once. Better to default to the primary and move specific queries to replicas as you verify they tolerate lag.
  • Session pinning after writes. Send a user's reads to the primary for a few seconds after they write. Cheap, and fixes the anomaly users actually report.
  • Lag-aware routing. The router should stop using a replica lagging beyond a threshold. Fail towards the primary, not towards stale answers.
  • Dedicate replicas to workloads. Analytics and report queries on the same replica as user traffic will occasionally take a shared lock or consume all the buffer pool. A separate replica for long queries costs one machine and removes a whole class of incident. In Postgres it also needs care: a long query on a replica can conflict with replay and either be cancelled or stall replication.
  • Replicas do not help writes at all, and each one adds write work to the primary's replication stream. Twenty replicas is usually a sign that the read path should be cached instead.

13.4Connections

An unpooled connection is expensive: in Postgres it is a whole operating system process with its own memory; in most databases it is at minimum a thread, a buffer and a scheduling entity. The arithmetic bites early.

The multiplication nobody does 
40 application instances
× 20 connections each in the pool
= 800 connections to the database

A Postgres instance is generally happiest below ~200 active connections;
past a few hundred, throughput *falls* as context switching and lock
contention grow. More connections is not more capacity.

With a pooler in transaction mode:
  800 client connections  →  ~40 real server connections
  and throughput goes UP, not down.

The right number of server connections is small — roughly cores × 2 + effective_spindles is the classic rule, which for a 16-core box is around 40. Everything above that is queueing, and it is better to queue in a pooler than inside the database. Pooling modes matter: session pooling assigns a server connection for the client's whole session (safe, minimal benefit), transaction pooling assigns it only for the duration of a transaction (the big win, but prepared statements, session variables and advisory locks stop working as expected), and statement pooling is per statement and breaks transactions entirely.

Connection pool arithmetic

How many real connections you are creating, what the database can take, and where the queue forms.

13.5Federation: splitting by function

Federation moves whole table groups to separate databases along domain lines — users here, orders there, events somewhere else. It is much easier than sharding because the boundaries already exist in the schema and no row is ever in the wrong place.

Federation versus sharding
Federation (by function)Sharding (by row)
Split alongTable groups / domainsA key within one table
Capacity gainedOne machine per domain — bounded by your number of domainsUnbounded
EffortModerate — move tables, fix cross-domain joinsHigh, and close to irreversible
What breaksJoins and transactions across domainsJoins, transactions, uniqueness, ordering, auto-increment
Good first targetWhatever is both high-volume and weakly connected to the rest: sessions, audit logs, events, notifications, analytics

The practical rule: federate first, because it is reversible, it follows boundaries you already have, and the biggest table is very often something appendable and self-contained that never needed to share a machine with your transactional data.

13.6Denormalisation and precomputation

Normalisation optimises for write correctness — one fact in one place. Denormalisation optimises for read cost by keeping the answer, not the ingredients. The forms, from least to most machinery:

Redundant columns
Store author_name on the post so rendering does not need a join. Cost: it must be updated when the author renames, and you must decide whether a historical name is a bug or a feature.
Counter columns and summary tables
comment_count on the post rather than COUNT(*) on every render. Update it in the same transaction as the insert, or asynchronously with a periodic reconciliation job — pick one and write down which, because the failure modes differ.
Materialised views
The database maintains a physical table from a query. Refresh strategies range from manual, to scheduled, to concurrent refresh, to incremental. Convenient, and the refresh cost can be large enough to be a scaling problem of its own.
Separate read models (CQRS)
Writes go to a normalised model; a change stream builds one or more denormalised read models shaped exactly like the queries. Maximum read performance, eventual consistency, and a whole pipeline to operate.
Every denormalisation is a consistency obligation

The moment a fact exists in two places, they can disagree — and they will, because of a failed job, a partial transaction, a bug in one write path, or a backfill that missed rows. Two rules make this survivable: always know which copy is authoritative, so a repair job has a source of truth; and write the reconciliation job at the same time as the denormalisation, not after the first incident. A drifted counter that nobody can recompute is a permanent scar.

13.7Partitioning and archiving inside one database

Native table partitioning splits one logical table into physical pieces by range, list or hash, inside the same database. It is not sharding — there is one server — and it solves a different set of problems:

  • Partition pruning: a query bounded to last week reads one partition rather than three years of rows.
  • Cheap deletion: dropping a partition is instantaneous; DELETE FROM events WHERE ts < … on a billion rows is an hours-long operation that bloats the table and floods the WAL.
  • Smaller indexes: per-partition indexes stay in memory when a single global index would not.
  • Tiering: old partitions can be moved to cheaper storage or exported to object storage and dropped.

Time-partitioning any append-heavy table — events, logs, messages, metrics — with an automated policy that creates future partitions and drops expired ones is one of the highest-value pieces of schema design available, and it is far easier to do at the start than to retrofit.

13.8Schema changes without downtime

At small scale a migration is a command. At large scale it is a project, because two versions of the application run simultaneously during a deploy and because a lock on a hot table stops the product.

Expand and contract 
Goal: rename column `email` to `email_address`.

1 EXPAND    add the new column, nullable, no default
            (a default on an existing column can rewrite the whole table
             on older engines — check your version)
2 DUAL WRITE deploy code that writes BOTH columns and reads the old one
3 BACKFILL  copy old → new in batches, with a pause between batches
            so replication and vacuum keep up
4 VERIFY    compare counts and checksums on real data
5 SWITCH    deploy code that reads the new column, still writes both
6 CONTRACT  deploy code that writes only the new column
7 DROP      remove the old column, days later
Migration hazards
OperationHazardSafe approach
Adding an indexTakes a write lock for the duration on a large tableCREATE INDEX CONCURRENTLY (Postgres) or an online DDL tool; it is slower and does not hold the lock
Adding a NOT NULL column with a defaultCan rewrite the entire tableAdd nullable, backfill in batches, then add the constraint with a validation step
Changing a column typeFull rewrite plus an exclusive lockNew column, dual write, backfill, switch
Any DDL on a busy tableThe lock request queues behind running queries, and every new query queues behind the lock — instant pile-upSet a short lock_timeout and retry; never let DDL wait indefinitely
Backfilling in one statementOne enormous transaction: WAL flood, replica lag spike, bloat, lock durationBatches of a few thousand rows with a short pause, monitoring replica lag between batches
Dropping a columnOld application instances still reference it during a rolling deployStop referencing it in code first, deploy fully, then drop days later

The common resolution is a hybrid: shared tables for the long tail, with row-level security or a query layer that makes omitting tenant_id impossible rather than merely discouraged, plus dedicated databases for the few large tenants who need isolation and will pay for it. That requires the routing indirection from Chapter 7 to exist from the beginning.

Your database CPU is at 90%. Reads are 95% of traffic. What is the order of investigation?

First, find out which queries — rank by total time (calls × mean_time), not by slowest, because a fast query running constantly usually dominates. Second, look at the plans for the top three; a missing index or an N+1 is the most common finding and often accounts for most of the CPU. Third, check the buffer pool hit rate: if it is low the machine is reading from disk constantly and more RAM is a genuine fix. Only then consider replicas, and only after asking whether those reads should be hitting the database at all — 95% read traffic with repeated queries is a caching problem wearing a database costume. Adding replicas first is tempting because it is a config change, but it multiplies a wasteful query across more machines rather than removing it.

You add 30 application servers and database throughput goes down. Why?

Connection count. Thirty more servers × the pool size each is several hundred more connections, and past a few hundred active connections a database spends an increasing share of its time on context switching, lock contention and per-connection memory rather than on queries. The classic shape is throughput rising with connections up to roughly twice the core count and then falling. The fix is a connection pooler in transaction mode between the application and the database, which lets you keep hundreds of client connections while the database sees a few dozen — and it usually raises throughput above where it was before you added the servers. Check for the tell: high CPU with low query throughput, and many sessions in a waiting state.

Why is federating "events" out of the main database usually a better first move than sharding "users"?

Because the event table is typically the largest, the fastest-growing, the most write-heavy, and the least connected to anything else — nothing joins to it in the request path, it is append-only, and it is queried by time range rather than by relationships. Moving it to its own database (or an entirely different store shaped for time series) reclaims most of the disk, most of the write volume and most of the WAL traffic in one reversible operation that touches a handful of code paths. Sharding users, by contrast, is close to irreversible, breaks joins and uniqueness that the application actually relies on, and buys write capacity you may not need. Do the reversible thing that removes the most load first, and re-measure.

Recap

  1. Work the ladder cheapest-first: queries, cache, bigger machine, replicas, pooling, federation, denormalisation, partitioning, sharding, different store.
  2. Rank queries by total time, not by mean. The load is usually a fast query running constantly.
  3. Keyset pagination, no SELECT *, no N+1, always a LIMIT, and a statement timeout.
  4. Route reads to replicas deliberately, pin after writes, refuse lagging replicas, and give long analytical queries their own replica.
  5. Connections are not capacity. Aim for a few dozen server connections behind a transaction-mode pooler.
  6. Federate by function before sharding by row — reversible, follows existing boundaries, and the biggest table is usually self-contained.
  7. Every denormalisation needs an authoritative source and a reconciliation job, written at the same time.
  8. Time-partition append-heavy tables early. Dropping a partition is instant; deleting a billion rows is an incident.
  9. Migrate with expand, dual write, backfill in batches, verify, switch, contract — and never let DDL wait on a lock.
