22.1How to read these

Every walkthrough is deliberately compressed to the decisions that matter, and every one has an identifiable pressure point — the single place where the requirement is genuinely hard and where the design earns its complexity. Finding that point quickly is the transferable skill; the rest of the design is usually the default skeleton from Chapter 1.

22.2URL shortener

Pressure: read amplification100 writes/s10 k reads/s36 TB/5 yr

Requirements

Create a short link for a long URL; resolve it with a redirect; optional expiry; basic click counts. Out of scope: custom aliases, user accounts, analytics dashboards. Non-functional: 100 million new links a day is unrealistic — assume 10 million, read:write around 100:1, redirects must be fast globally, links are immutable once created, 99.9% availability, and a redirect that fails is far worse than a create that fails.

Numbers

Envelope
writes   10^7/day ÷ 10^5 s          = 100/s     peak ×5 = 500/s
reads    100 × writes               = 10 000/s  peak    = 50 000/s
metadata 10^7 × 500 B × 3 replicas  = 15 GB/day → 27 TB over 5 years
ids      62^7 = 3.5 × 10^12         = 350 000 days of supply

Interface and keys

HTTP
POST /v1/links  { url, expiresAt? }  -> { code, shortUrl }   Idempotency-Key
GET  /{code}                          -> 301/302 to the target

link(code PK, target_url, created_at, expires_at, owner_id?)
  partition by hash(code) — every read is by code, nothing else

The id

Three options. Hash the URL and take the first 7 base62 characters: deterministic and deduplicating, but collisions need a read-before-write on every create and identical URLs cannot have separate expiry. A global counter encoded in base62: collision-free but sequential, so links are enumerable and a competitor can count your traffic. Pre-allocated ranges: each server claims a block of a million ids from a small coordinator and hands them out locally, shuffled within the block. Collision-free, no read on the write path, not sequential across the fleet, and the only cost is some wasted ids when a server dies. Take the third.

Design and the deep dive

Client → CDN → load balancer → stateless resolver → cache → metadata store. The pressure point is read amplification: a link posted somewhere popular can take a million requests a minute, all for one row. Immutability makes this easy, and it is the whole trick — set a long Cache-Control on the redirect and the CDN absorbs essentially all of it, with the origin seeing one request per point of presence per TTL. Add a Redis cache in front of the store for the warm tail. Use a 301 when you never want to see the request again and a 302 when you want click counts, because a 301 is cached by browsers permanently and your analytics disappear — that is a product decision with an infrastructure consequence, and it is the detail interviewers probe.

Click counting must never be on the redirect path: emit an event, aggregate asynchronously (Chapter 17). Expiry is handled twice — a check at read time, because sweepers lag, and a background sweeper or a TTL on the row. Cost is dominated by storage growth and CDN egress, not compute, which makes an aggressive default expiry a genuine financial lever.

22.3Distributed rate limiter

Pressure: shared counters at request rate100 k checks/ssub-ms budget

Requirements

Limit requests per API key, per endpoint class, with different tiers. Must work across a fleet of gateway instances. The check itself must cost well under a millisecond, because it runs on every request. Accuracy matters less than availability: it is better to allow a few extra requests than to reject legitimate traffic because the limiter's store is unreachable.

The core decision

Three placements, and the answer is usually a combination. Purely local per instance: fastest, no dependency, but with 50 gateways each enforcing 1/50th of the budget, a client whose requests land unevenly is throttled early. Purely central in Redis: accurate, and it adds a network round trip and a hard dependency to every single request. Local with periodic reconciliation: each instance holds a local token bucket seeded with a share of the budget, and asynchronously reports usage and receives an adjusted share every second or so. Approximate, bounded error, no per-request round trip, and it degrades to purely local if the coordinator is unreachable.

The central path, done atomically
-- Token bucket in one round trip. Must be atomic, or two
-- concurrent checks both read the same token count.
-- Redis Lua script, keyed so it runs on the right shard:
--   KEYS[1] = "rl:{api_key}:{class}"
--   ARGV    = rate, capacity, now, cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate)
if tokens < cost then
  redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
  return {0, math.ceil((cost - tokens) / rate)}   -- denied, Retry-After
end
redis.call('HMSET', KEYS[1], 'tokens', tokens - cost, 'ts', now)
redis.call('EXPIRE', KEYS[1], 3600)
return {1, 0}

Deep dive and failure

Token bucket rather than fixed window, for the boundary reason in Chapter 20. Shard the counter store by key so no single node holds every counter, and note that a single very hot API key is a hot-key problem that sharding cannot fix — for those, fall back to local buckets with a fixed share. Always return 429 with Retry-After, or clients retry immediately and the limiter becomes a load amplifier.

The critical failure decision: fail open. If the counter store is unavailable, allow traffic and alert. A rate limiter that rejects everything when its own dependency fails has converted a capacity-protection mechanism into an outage — the opposite of its purpose. The exception is any limit protecting against abuse rather than overload, where failing open is a security decision and needs to be made deliberately.

22.4News feed

Pressure: fan-out10 k posts/s300 k feed reads/s1000:1 read heavy

Requirements

Post; follow; see a reverse-chronological feed of posts from people you follow. Out of scope: ranking, ads, stories. Non-functional: 300 million daily actives, average 200 follows, feed opened 10 times a day, feed load under 200 ms, a few seconds of staleness is fine.

Numbers, and the decision they force

Envelope
posts        3×10^8 × 0.3/day  = 10^8/day  →  1 000/s   peak 5 000/s
feed loads   3×10^8 × 10/day   = 3×10^9/day → 30 000/s  peak 150 000/s

PULL (fan-out on read): each load queries 200 followees' recent posts
     150 000/s × 200 = 30 million lookups/s at peak.  Not viable.

PUSH (fan-out on write): each post is appended to every follower's list
     5 000 posts/s × 200 average followers = 1 000 000 list appends/s.
     Large, but appends to a sharded Redis list are cheap and it is
     off the read path entirely.

  → push, EXCEPT for accounts with millions of followers, where one
    post would be tens of millions of appends and a multi-minute
    delivery lag.

The hybrid, which is the actual answer

Fan out on write for the long tail; leave celebrity posts out of precomputed feeds entirely; at read time, merge the precomputed list with a small live query over the handful of celebrities the user follows. The threshold — perhaps 100 000 followers — is a tuning parameter, and the merge is cheap because a user follows very few such accounts.

Details that decide whether it works

Store ids, not content in timelines — a post edited or deleted after fan-out would otherwise require rewriting every copy. Cap each timeline at ~1 000 entries; nobody scrolls further, and unbounded lists are the failure mode in Chapter 19. Fan out only to active users: if 70% of accounts have not opened the app in a month, fanning out to them is 70% waste — mark them inactive and rebuild their timeline on next login. And accept eventual consistency explicitly: a post appears in followers' feeds over some seconds, which is invisible to users and is what makes the whole design affordable.

Fan-out on write versus read

The computation that decides this design. Move the follower distribution and watch the answer flip.

22.5Chat

Pressure: stateful connections5 M concurrent sockets40 k msgs/s440 TB/yr

Requirements

One-to-one and small group messaging, delivery and read receipts, presence, history, offline delivery, push notification when the recipient is not connected. Non-functional: 50 million daily actives, 10% concurrently connected, messages delivered in under a second, nothing acknowledged may be lost, history kept indefinitely.

Numbers

Envelope
sends       5×10^7 × 40/day ÷ 10^5    = 20 000/s   peak ×2 = 40 000/s
deliveries  × 5 recipients average    = 200 000/s peak
sockets     10% of 5×10^7             = 5 000 000 concurrent
            ~10 KB each               = 50 GB of connection state
            200 k sockets per gateway = 25 nodes minimum, ~60 with
                                        headroom and zone loss
storage     2×10^9 msgs/day × 200 B × 2.5 metadata × 3 replicas
                                      = 3 TB/day → 1.1 PB/year
                                      → compress and tier: ~440 TB/yr

Structure

The deep dive: delivery and ordering

Message ids must be sortable and generated without coordination — a Snowflake-style 64-bit id (timestamp, machine, sequence) gives both. Partition by conversation_id and cluster by (sent_at, message_id), so "last 50 messages" is one sequential read on one partition and ordering within a conversation is free. Bucket the partition key by month for very active conversations, or the partition grows without bound.

Delivery is three acknowledgements, and conflating them is the classic mistake: sent (the server has durably stored it), delivered (the recipient's client has it), read (the user saw it). Only the first is a server guarantee. The client keeps a local sequence number and, on reconnect, asks for everything after it — which handles the missed-message problem without server-side per-device queues. Offline recipients get a push notification; the message is already durable, so the notification is a hint, not the payload.

Presence is deceptively expensive: naive implementations broadcast every status change to every contact, which is quadratic. Publish presence changes to a per-user topic that only currently-viewing clients subscribe to, and use a heartbeat with a short TTL so a crashed client ages out rather than appearing online forever.

22.6Notification system

Pressure: unreliable third partiesfan-out burstsat-least-once

Requirements

Send push, email and SMS triggered by application events. Support user preferences and quiet hours, templating and localisation, deduplication, and per-channel rate limits. Non-functional: bursty by nature (one marketing campaign is 10 million notifications in ten minutes), transactional notifications must not queue behind marketing ones, and third-party providers are slow, rate-limited and occasionally down.

Structure

Pipeline
event → ingest API → dedup (idempotency key per event+user+channel)
      → preference & quiet-hours filter (drop or defer)
      → template render + localise
      → per-channel priority queues
          transactional  ─┐
          marketing      ─┴→ workers → provider adapters → APNs / FCM / SES / SMS
      → delivery-status webhooks → status store → analytics

The deep dive: surviving the providers

Everything hard here is at the boundary with systems you do not control. Separate queues by priority — a password reset must not sit behind a two-hour marketing backlog, and priority within one queue is not enough because a single slow provider blocks the consumer. Rate limit per provider, since each imposes its own quota and exceeding it gets you throttled or blocked; a token bucket per provider per account, shared across workers. Circuit-break per provider so a dead SMS gateway does not consume every worker. And have a fallback: if the primary email provider is down, route to a secondary — this is the one part of most systems where multi-vendor redundancy is routinely worth it.

Deduplication is essential because at-least-once delivery means a retry sends a second push, and users notice that immediately. Key on (event_id, user_id, channel) with a retention window longer than any possible retry. Delivery status arrives asynchronously by webhook and must be reconciled against sends, both for analytics and to detect a provider silently dropping messages — a provider reporting success while delivering nothing is a real failure mode and only reconciliation catches it.

22.7Search autocomplete

Pressure: latency per keystroke< 50 ms p995× query volume

Requirements

Suggest completions as the user types, ranked by popularity, updated at least daily. Non-functional: every keystroke is a request, so volume is roughly five times the search volume; p99 under 50 ms including network, which means it must be served near the user; suggestions being a few hours stale is fine.

The key insight

This is not a search problem, it is a precomputed lookup problem. Do not query an index at request time; compute the top N completions for every prefix offline and serve them from a key-value store or from the edge.

Offline build, online read
OFFLINE (hourly or daily)
  query logs → aggregate counts by query, last 7 days, decayed
             → for each prefix (1..~20 chars) of each popular query,
               keep the top 10 completions by score
             → write prefix → [suggestions] into a KV store
             → versioned: build into "suggest:v41:*", flip a pointer

  Prefixes are bounded: only prefixes of queries that actually occur,
  which is millions of keys, not the combinatorial space.

ONLINE
  GET /suggest?q=lond  →  KV lookup on "lond"  →  10 strings
  One hash lookup. No ranking, no scan, no index traversal.

Deep dive

A trie is the textbook answer and is worth knowing — each node stores its subtree's top N so a lookup is a walk of the prefix length. In practice a flat prefix-to-suggestions map in a key-value store is simpler, trivially shardable and easier to serve from the edge, and the trie's advantage (sharing memory between prefixes) matters less than the operational simplicity. Either way, the structure is rebuilt offline and swapped atomically by version, which makes rollback instant and makes the online path read-only.

Serve from the edge with a short TTL — suggestions are identical for everyone, so the cache hit ratio approaches 100% and the 50 ms budget becomes achievable across continents. Debounce on the client at 50–100 ms so a fast typist generates three requests, not twelve. Personalisation, if required, is a small per-user overlay merged client-side rather than a per-user index, which would destroy the cacheability that makes the whole thing work. And maintain a deny-list applied at build time: autocomplete surfaces whatever people type, which is a content-moderation problem before it is an engineering one.

22.8Video platform

Pressure: storage and egress165 PB/5 yr1.6 Tbps peak~$2M/mo egress

Requirements

Upload, transcode, stream adaptively, search by title. Out of scope: recommendations, live streaming, monetisation. Non-functional: 100 million daily actives, uploads are large and slow, playback must start in under two seconds and adapt to bandwidth, and cost is a first-class constraint rather than an afterthought.

Numbers

Envelope
uploads    10^8 × 0.002/day        = 200 000/day  → ~2/s, peak 10/s
storage    200 000 × 500 MB source = 100 TB/day of source
           + renditions ≈ 1.5×     = 250 TB/day
           × 365 × 5, erasure-coded ≈ 1.5×  →  ~165 PB
watch      10^8 × 20 min/day at 2 Mbps average
           = 3×10^13 bytes/day? — recompute:
           10^8 × 1200 s × 250 KB/s = 3×10^16 B/day = 30 PB/day egress
peak       30 PB/day ÷ 10^5 s × 5   = 1.5 TB/s ≈ 12 Tbps

Those two numbers decide everything. Petabytes of storage means object storage with erasure coding and lifecycle tiering, not block volumes. Terabits of egress means a CDN is not an optimisation but the primary serving infrastructure, and that egress cost dwarfs every other line — which makes codec efficiency and rendition strategy financial decisions.

Structure

Upload and transcode pipeline
client → POST /videos → { videoId, uploadUrl }      (valet key)
       → PUT direct to object storage, chunked and resumable
       → completion event → transcode queue
           split into segments → parallel workers
           → renditions: 240p 360p 480p 720p 1080p (+ AV1 for the popular tail)
           → package HLS/DASH: 2–6 s segments + manifest
           → thumbnails, duration, subtitles
       → mark ready, index for search, notify uploader
playback: manifest from CDN → player picks a rendition per segment
          based on measured bandwidth and buffer level

Deep dive: the cost levers

Transcoding is embarrassingly parallel — split the source into segments, transcode them independently, concatenate — so a two-hour film is minutes of wall-clock time across a worker pool, and the pool is a perfect fit for interruptible spot capacity. Transcode lazily for the long tail: the vast majority of uploads are watched almost never, so generating every rendition for every video wastes both compute and storage. Produce a couple of common renditions on upload and generate the rest on first request, accepting a slower first play for unpopular content.

Storage tiering follows the same distribution: hot content on standard storage, everything untouched for 90 days moved to a cold tier at a tenth of the price. And since egress dominates, a codec that is 30% more efficient saves more money than any infrastructure change available — which is why platforms invest heavily in newer codecs for their most-watched content even though encoding costs more.

22.9File sync (cloud drive)

Pressure: conflicts and diffingbandwidth-sensitiveoffline clients

Requirements

Files sync across a user's devices and to the web; edits made offline reconcile on reconnect; sharing with other users; version history. Non-functional: bandwidth is the scarce resource on client links, clients are frequently offline, and a lost edit is unacceptable.

The two core mechanisms

Chunking and content addressing. Split each file into chunks — content-defined boundaries via a rolling hash rather than fixed 4 MB offsets, so inserting a byte at the start does not shift every subsequent boundary — and address each chunk by the hash of its content. A file becomes an ordered list of chunk hashes. Uploading a changed file means uploading only the chunks whose hashes the server does not already have, which for a small edit in a large document is a few kilobytes instead of a few megabytes. It also gives deduplication for free across versions and across users.

Sync protocol
client:  compute chunk hashes for the changed file
         POST /has-chunks  [h1,h2,…]      → server returns which are missing
         PUT  /chunks/{hash} for each missing chunk (idempotent by construction)
         POST /files/{id}/versions { chunkList, baseVersion, mtime }

server:  if baseVersion == current  → accept, bump version, notify devices
         else                        → CONFLICT, return current version

notify:  long-lived connection or long poll per device; the notification
         carries only "namespace X changed to cursor N", and the client
         then pulls the delta. Small, idempotent, and safe to miss.

Deep dive: conflicts

Two devices editing the same file offline is not an edge case, it is the normal condition. Attach a version to every file and require writes to state the version they are based on — a compare-and-set. If the base is stale, the server rejects and the client must resolve. For most file types, automatic merging is impossible, so the honest resolution is to keep both: create report (Alice's conflicted copy).docx alongside the original. Users understand this and no data is lost, which is the property that matters. For structured formats you control, a CRDT (Chapter 5) enables true automatic merge, which is how collaborative editors work — but that is a different product decision, not a general file-sync solution.

Metadata and content have completely different shapes and belong in different stores: file and version metadata in a relational database partitioned by user or namespace, chunks in object storage keyed by hash. The notification path should carry a cursor rather than the change itself, so a missed notification is harmless — the client pulls the delta from its last known cursor and converges regardless.

22.10Ticket booking

Pressure: correctness under contention100× spikeno overselling

Requirements

Browse events, select seats, hold them while paying, complete purchase. Non-functional: normal load is trivial; an on-sale is a hundred thousand people arriving in the same second for ten thousand seats. Overselling is unacceptable. Underselling — seats held by abandoned sessions — is merely bad.

Why this is different

Every other design in this chapter scales by relaxing consistency. This one cannot: a seat is a unique, non-fungible resource, and two people cannot have it. The contention is extreme and concentrated on a handful of rows, which is precisely the case distributed systems handle worst.

Structure

The three phases
1  QUEUE at the edge.  Admission control before anything else:
   a virtual waiting room issuing signed tokens with a position.
   Only N thousand users are admitted to the booking system at a
   time. This converts a 100× spike into steady, plannable load —
   and it is the single most important component in the design.

2  HOLD.  Selecting a seat creates a hold row with a short TTL
   (5–10 minutes), via a conditional write:
     UPDATE seats SET state='held', hold_id=?, expires_at=now()+'10 min'
      WHERE seat_id=? AND state='available'
   -- zero rows affected means someone else got it. No locks held
   -- across the payment; the TTL is what releases abandonment.

3  CONFIRM.  Payment succeeds → state='sold' in a transaction that
   also checks the hold is still valid and belongs to this session.
   Payment is idempotent (Chapter 16) so a retry cannot double-charge.

Deep dive

Correctness comes from a single conditional update on the seat row — the compare-and-set from Chapter 12 — which is atomic in any relational database and needs no distributed transaction. Partition by event_id, so all contention for one event lands on one shard and cross-shard coordination never arises; the trade is that a single enormous on-sale is one shard's worth of write throughput, which the waiting room exists to bound.

Expiry must be handled twice: a sweeper releasing expired holds, and a check at read time, because sweepers lag and a seat that looks held but has expired should be purchasable. Read paths — the seat map — can be stale and cached, provided the authoritative check happens at hold time; showing a seat as available and then failing the hold is acceptable, whereas the reverse is lost revenue. Finally, the waiting room's fairness properties are a product decision with a technical shape: a strict FIFO queue is fair and requires a durable ordered structure, while random admission is cheaper and will generate complaints.

22.11Metrics and monitoring system

Pressure: write throughput and cardinality10 M points/scompression 10×

Requirements

Ingest metrics from a fleet, store them, query by name and labels over time ranges, evaluate alert rules, downsample and expire. Non-functional: 10 000 hosts × 1 000 series each, scraped every 15 seconds; queries over a month must return in seconds; retention is 15 days at full resolution and two years downsampled.

Numbers

Envelope
series      10^4 hosts × 10^3          = 10^7 active series
ingest      10^7 ÷ 15 s                = 670 000 points/s
raw size    16 B per point (ts + float)
            670 000 × 16               = 10.7 MB/s = 925 GB/day
compressed  delta-of-delta + XOR ≈ 10× =  ~93 GB/day
15 days full resolution                = 1.4 TB
downsampled 5-minute rollups, 2 years  = ~110 GB
  → one storage tier is a few terabytes. Entirely tractable.
  → the hard part is 670 k writes/s and 10^7 series in the index.

Structure and deep dive

Every property of this design comes from the workload shape: append-only, always increasing timestamps, read as ranges of one series, never updated, deleted wholesale. So: an LSM-style or purpose-built columnar store (Chapter 12), because writes are sequential appends. Delta-of-delta encoding for timestamps — regular intervals compress to almost nothing — and XOR encoding for floats, which is where the 10× comes from. Partition by time and by series hash, so old partitions are dropped rather than deleted and queries prune to a few blocks.

The genuinely hard part is the inverted index over labels: a query like {job="api", region="eu"} must resolve to the matching series ids fast, over ten million series. That is a posting-list intersection, the same structure a search engine uses, and it is what fails first when cardinality grows — see Chapter 18. Enforce limits at ingest: reject series above a per-tenant cap, and expose which metric names are producing them, or one bad deploy takes the monitoring system down at the moment you most need it.

Two structural choices worth defending. Pull over push for scraping — the system knows what should exist, so a target that disappears is detectable, whereas with push a silent target is indistinguishable from a healthy one with nothing to say. And alert evaluation as queries on the same store, run on a schedule, rather than a separate streaming path: it is simpler, alerting rules are the same language as dashboards, and the cost is that alert latency is bounded by the evaluation interval rather than being instant.

The interview compression

If you have five minutes and one of these comes up: state the two or three numbers that decide the architecture, name the pressure point, give the two candidate approaches and pick one with its cost, then describe what happens when the busiest component fails. That is a complete answer. The diagram is scaffolding for the conversation, not the deliverable — a design defended in numbers with a named trade-off beats a beautiful diagram every time.

Take the news feed design and change one number: average following goes from 200 to 5 000 (a professional network). What changes?

The pull cost per feed load rises 25× — 150 000 loads/s × 5 000 = 750 million lookups per second — so fan-out on read becomes even more impossible. But fan-out on write does not get worse from following; it scales with followers, which may be unchanged. So push remains right, and the merge step at read time gets more expensive because a user now follows more celebrities. The bigger change is elsewhere: with 5 000 follows, a reverse-chronological feed is unusable — the user cannot possibly read it — so the product almost certainly needs ranking, which means the timeline stops being a simple append-ordered list and becomes a candidate-generation plus scoring pipeline. That is a much larger design change than the fan-out arithmetic, and noticing it is the point: a change in the numbers can invalidate the product assumption rather than just the infrastructure.

Why does the ticket booking design put a waiting room in front, rather than just scaling the booking service?

Because the contention is on individual rows, and no amount of horizontal scaling relieves that. A hundred thousand concurrent attempts to update ten thousand seat rows means most of them fail their conditional update, retry, and fail again — the retry storm from Chapter 19, with the added property that the useful work is bounded by the number of seats regardless of how many servers you add. The waiting room converts an unbounded arrival spike into a controlled admission rate that the shard can actually serve, which also makes capacity planning possible and gives users an honest position rather than an error. It is admission control, and it is a better answer than capacity for any problem where demand can exceed supply by two orders of magnitude for a few seconds.

Across these ten, when was denormalisation the wrong answer?

Wherever the duplicated fact was contended or authoritative. Seat state in the booking system cannot have a second copy — the whole design rests on exactly one row being the arbiter, and a cached "available" is explicitly non-authoritative and re-checked at hold time. Payment records and file version numbers are the same: single source, compare-and-set. Everywhere else denormalisation was right, because the copies were derived views of immutable or eventually-consistent facts — timeline entries, autocomplete suggestions, metric rollups, search indexes — all of which are rebuildable from a source of truth and none of which anyone contends over. That is the general rule the chapter demonstrates: duplicate derived data freely, never duplicate the thing two actors are competing for.

Recap, and the end of the unit

  1. Find the pressure point first. Every one of these designs is the default skeleton plus one hard thing, and the hard thing is where all the interesting decisions are.
  2. Two or three numbers decide the architecture. Read:write ratio, item size, and peak concurrency did most of the work across all ten.
  3. Precompute what is read far more than it is written, and keep the precomputed thing rebuildable.
  4. Separate the blobs from the facts about the blobs. They have different stores, different costs and different lifecycles.
  5. Design a special case for the tail — celebrities, hot keys, large tenants, popular videos. The median case is never the whole design.
  6. Admission control beats capacity when demand can spike by orders of magnitude.
  7. Duplicate derived data freely; never duplicate a contended fact. One conditional update on one row is how correctness is actually achieved.
  8. Finish with failure. For each design, the honest question is what happens when the busiest component dies — and in most of them the answer required a decision made in advance.
