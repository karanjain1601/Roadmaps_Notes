The cloud design pattern catalogue

Roughly forty named patterns recur across distributed systems. Most are a paragraph of idea wrapped in a memorable name, and their value is compression: "use the claim check pattern" replaces two minutes of explanation. This chapter is the catalogue, organised by the problem each one solves, with the part everyone omits — when not to use it.

~35 min read ~40 patterns, grouped 2 interactive panels Prerequisite: parts 1–6

21.1How to use a catalogue

Patterns are vocabulary, not architecture. They are useful in three specific ways: they let you name a solution quickly in a discussion, they carry the known failure modes along with the idea, and they stop you reinventing something with a well-documented sharp edge. They are not a design method — a system assembled by picking patterns from a list is how you get twelve components serving four hundred requests per second.

Pattern-driven design fails in a predictable way

The sequence is always the same: someone recognises a pattern that fits, applies it, and the pattern brings its own infrastructure. Event sourcing arrives with a projection pipeline, a replay mechanism and a snapshotting strategy — all necessary, none of which the original problem asked for. Apply a pattern when you have the problem it solves and have decided its cost is worth paying, and be able to say what you would have done instead.

21.2Messaging patterns

Getting work between components asynchronously — background in Chapter 17
PatternProblem → mechanismWatch out for
Queue-based load levellingBursty load overwhelms a service → put a queue in front so the consumer works at its own paceLatency becomes unbounded during a backlog; needs age monitoring and backpressure or it hides the problem
Competing consumersOne consumer is not enough → many consumers pull from the same queue, each message going to exactly oneOrdering is lost by construction; consumers must be idempotent
Publisher–subscriberMany components must react to one event → publish to a topic; subscribers receive independentlyNobody knows who consumes what; a schema change breaks unknown consumers. Use a registry
Priority queueSome work matters more → separate queues per priority, or a priority-aware brokerStarvation of low priority. Reserve a share of capacity for it
Claim checkMessages are too large for the broker → store the payload in object storage, put only a reference in the messageLifecycle mismatch: the blob must outlive the message and be cleaned up when it does not
Pipes and filtersA long transformation is a monolith → decompose into stages connected by queues, each independently scalableEach stage boundary is a serialisation cost and a failure point; do not over-decompose
Sequential convoyOrder matters within a group but not globally → partition by the group key so each group is processed in order, groups in parallelExactly the partitioning rule from Chapter 7: a hot group becomes a serial bottleneck
Async request–replyThe work is too slow for a synchronous response → return 202 with a status URL; the client polls or is called backClients must handle the second phase; define the status resource and its terminal states clearly
ChoreographyA multi-service flow → each service reacts to events and emits its own, with no coordinatorNo single place shows the state of a flow. Past three steps, use orchestration instead
Scheduler–agent–supervisorDistributed work fails halfway → a scheduler assigns steps, agents perform them, a supervisor detects timeouts and retries or compensatesThe supervisor is itself a component that can fail; it needs its own state and leader election

21.3Data management patterns

Where data lives and how it is read — background in Part 4
PatternProblem → mechanismWatch out for
Cache-asideRepeated expensive reads → check the cache, load and populate on a missStampedes and stale entries. See Chapter 15
Materialised viewA query is expensive and repeated → precompute and store the answer in the shape the query wantsIt is a denormalisation, so it needs an authoritative source and a rebuild path
Index tableQueries by a non-key field on a partitioned store → maintain a secondary table keyed by that fieldTwo writes per change; usually asynchronous, so the index lags
ShardingOne node cannot hold or serve the data → partition rows across independent storesEverything in Chapter 7. Do it last, not first
Static content hostingApplication servers waste capacity serving files → put static assets in object storage behind a CDNAlmost no downside. One of the few unambiguously good patterns
Valet keyLarge uploads and downloads through your API tier consume bandwidth and connections → issue a short-lived, narrowly-scoped signed URL and let the client talk to storage directlyScope tightly: one object, one operation, minutes of validity. A leaked broad key is a data breach
CQRSReads and writes have incompatible shapes and scaling profiles → separate the write model from one or more read modelsTwo models to keep in step; eventual consistency becomes visible to users
Event sourcingYou need the full history, not just current state → store the sequence of events as the source of truth and derive state by replaying themHeavy: snapshots, versioned event schemas, replay time, and queries that must go through projections. Justified by audit or temporal requirements, rarely by preference

CQRS and event sourcing, unbundled

These two travel together and are independent. CQRS alone says: the model you write is not the model you read. A normalised transactional schema takes writes; one or more denormalised read models, updated from a change stream, serve queries. That is often worth it on its own — it is how you get a search index, a timeline cache and an analytics table without contorting the write schema.

Event sourcing is a stronger claim: the events are the truth, and current state is a fold over them. It gives you a complete audit trail, the ability to ask "what did this look like on 3 March", and the ability to build a new read model retroactively over all history. It costs you the ability to query the store directly, a schema-evolution problem for events that live forever, snapshotting so replay does not take hours, and a team that has to think in a different model. Adopt it where history is the requirement — ledgers, compliance, collaborative editing — and not because it sounds like the modern way to do CQRS.

21.4Design and implementation patterns

Structuring services and their edges — background in Chapter 11
PatternProblem → mechanismWatch out for
Gateway routingClients should not know the topology → one entry point routes by path or host to internal servicesA shared component on every request path; it must be highly available and independently scalable
Gateway aggregationA client needs six calls over a slow link → the gateway fans out internally and returns one responseTail amplification (Chapter 3) and partial failure: decide per sub-call whether it is optional
Gateway offloadingEvery service reimplements TLS, auth, rate limiting, compression → do it once at the gatewayCross-cutting concerns only. Business logic in the gateway is how it becomes unownable
Backends for frontendsWeb, mobile and partner clients have divergent needs → one thin backend per client type, owned by that client's teamDuplication between BFFs; keep shared logic in the services below
SidecarEvery service needs the same infrastructure behaviour in five languages → run it as a separate process alongside each instanceResource overhead per instance, an extra hop, and a new layer between you and the network when debugging
AmbassadorClients need retries, timeouts and circuit breaking to a remote service → a sidecar that proxies outbound calls and implements themThe outbound half of the sidecar idea; same trade-offs
Anti-corruption layerA legacy or third-party model would infect your domain → a translation layer that maps their model to yours at the boundaryIt is extra code with no user-visible value, and it is worth it — without it the foreign model spreads irreversibly
Strangler figA rewrite is too risky → put a façade in front, route slices of functionality to the new system one at a time, delete the old parts as they are replacedThe façade and dual running are long-lived; budget for the last 10% taking as long as the first 90%
External configuration storeConfig baked into deployments cannot change quickly and drifts between services → centralise it, watch for changesNow a runtime dependency for startup. Cache last-known-good on disk and fail static
Leader electionExactly one instance must do a thing → elect a leader via consensus with a leaseNeeds fencing (Chapter 6) or a paused ex-leader does damage on waking
Compute resource consolidationMany tiny services each with fixed overhead → co-locate related workloads in fewer deploymentsThe deliberate counterweight to over-decomposition, and it reintroduces shared failure

Strangler fig, because you will do this one

The single most useful pattern in the catalogue for real work, because most systems that need designing already exist. Put a façade — a proxy or gateway — in front of the legacy system so that every request passes through something you control. Then move functionality across one route at a time: the façade sends /orders to the new service while everything else still goes to the old one. Traffic can be shifted by percentage, by tenant, or by user, and shifted back instantly if something is wrong.

What makes it work is that every step is independently reversible and the system is fully functional at every point. What makes it fail is data: two systems reading and writing the same records need either a shared store during the transition, dual writes with reconciliation, or a clean split of ownership per entity. Decide which before you move the first route, because that decision is the actual project.

21.5Reliability and resiliency patterns

Surviving failure — background in Chapter 20
PatternProblem → mechanismWatch out for
RetryTransient failures → retry with exponential backoff and full jitterAmplification. Retry at one layer, under a budget, only for retryable errors
Circuit breakerCalling a failing dependency wastes resources and prevents its recovery → stop calling it after a failure threshold; probe to reopenTrip on a rate with a minimum volume; pair with a fallback or you have only made failure faster
BulkheadOne consumer exhausts a shared resource → partition pools per dependency, tenant or priorityPartitioned capacity is less efficient than shared; that inefficiency is the insurance premium
ThrottlingDemand exceeds capacity → limit per client and shed the rest, returning 429 with Retry-AfterReject cheaply at the edge; a rejection that costs a full request path is not shedding load
Health endpoint monitoringYou cannot tell whether an instance works → expose a checked endpoint and probe it externallyShallow for load-balancer decisions, deep for observability. Never let a shared dependency mark the whole fleet unhealthy
Compensating transactionA multi-step operation fails partway and cannot be rolled back → run semantic undo actions in reverse orderCompensations fail too, are not isolated, and some steps are irreversible — order those last
Deployment stampsOne shared stack means one blast radius and one scaling ceiling → deploy N independent copies, each serving a subset of usersThe routing layer becomes a global dependency; per-stamp overhead and N× the operational objects
GeodesUsers are global but the system is regional → geographically distributed nodes each able to serve any request, with data replicated between themRequires the data model to tolerate multi-region writes — the CAP decision from Chapter 5, made explicit

21.6Security patterns

Boundaries and credentials
PatternProblem → mechanismWatch out for
Federated identityEvery service implementing authentication is a liability → delegate to an identity provider; services trust a signed tokenToken lifetime versus revocation: short TTLs plus a strongly consistent deny-list, or a revoked session stays valid
GatekeeperExposing an application directly widens the attack surface → a hardened, minimal broker validates and sanitises requests before forwarding, holding no credentials of its ownIt must genuinely be minimal; a gatekeeper full of logic is just another application with the same vulnerabilities
Valet keyHanding out broad credentials to allow one operation → issue a signed, scoped, expiring token for exactly that object and operationScope and expiry are the whole security property. Log issuance so a leak is traceable

Three principles underlie all three and are worth stating separately, because they generalise. Least privilege: every credential grants the narrowest access for the shortest time. Defence in depth: a gateway does not excuse services from authorising requests themselves — assume every layer can be bypassed. And fail closed on authorisation: when the identity service is unreachable, deny. This is the one place where the fail-open reasoning that protects availability elsewhere is exactly wrong.

21.8Four ways patterns are misused

  1. Applied without the problem. Event sourcing on a CRUD application, a service mesh for five services, CQRS where one table would do. The test: state the problem in a sentence that includes a number.
  2. Applied at the wrong granularity. A circuit breaker per process rather than per dependency; a bulkhead around the whole service rather than around the slow call. Patterns have a natural scope, and applying them too broadly usually inverts the benefit.
  3. Applied without the accompanying obligation. Retry without a budget. A breaker without a fallback. A queue without backlog monitoring. Denormalisation without reconciliation. Each pattern comes with a duty, and skipping it is how the pattern becomes the incident.
  4. Used as an argument instead of a reason. "It is the sidecar pattern" is not a justification. The justification is the problem it removes and the cost you have agreed to pay for it.
Someone proposes event sourcing for a standard e-commerce catalogue. What do you ask?

Whether anyone needs the history. Event sourcing's distinctive benefits are a complete audit trail, temporal queries ("what was the price on 3 March"), and the ability to build a new read model over all past events. A product catalogue usually needs none of those — it needs current state and fast reads, which is a table and a cache. Then ask what they intend to do about the costs the pattern brings: schema evolution for events that must be readable forever, snapshots so replay does not take hours, projections for every query shape because you can no longer query the store directly, and a team that must think in a different model. If the real motivation is "we want an audit log", that is a table of changes, which is a hundredth of the work. If it is "we want CQRS", note that CQRS is independent and can be adopted alone.

Why is the valet key pattern a performance pattern as much as a security one?

Because the alternative is proxying the bytes. If a client uploads a 5 GB file through your API tier, that tier spends the entire upload duration holding a connection, a thread and a buffer, and it pays the bandwidth twice — once inbound from the client and once outbound to storage. A hundred concurrent uploads can exhaust a fleet that handles fifty thousand ordinary requests per second. A signed URL removes your servers from the data path entirely: they issue a token in a millisecond and the client talks to object storage directly, which is a service designed for exactly that and priced accordingly. The security property — narrow scope, short expiry — is what makes it safe to do; the capacity property is usually why it gets built.

Deployment stamps and geodes both replicate the whole stack. What is the difference?

What the copies are for. Stamps (cells) partition users: each user belongs to exactly one stamp, stamps do not talk to each other, and the purpose is blast-radius containment and horizontal scale by cloning. A stamp failure affects 1/N of users, and deploys go stamp by stamp. Geodes partition geography: every node can serve any request, and the purpose is latency, so data must be replicated between them rather than partitioned. That difference is the hard part — geodes force a multi-region write consistency decision (CAP, made explicit), whereas stamps sidestep it because a user's data lives in exactly one place. Many systems use both: geo-distributed regions, each containing several stamps.

Recap

  1. Patterns are vocabulary and compressed experience, not a design method. Assemble from requirements, name with patterns.
  2. Messaging: level load with queues, distribute with competing consumers, fan out with pub/sub, keep order per key with sequential convoy, keep payloads small with claim check.
  3. Data: cache-aside, materialised views and index tables all trade write work for read speed and all owe you a rebuild path.
  4. CQRS and event sourcing are separable. CQRS is often worth it alone; event sourcing is justified by a history requirement, not by preference.
  5. Gateways handle cross-cutting concerns; BFFs handle per-client shapes. Business logic belongs in neither.
  6. Strangler fig plus an anti-corruption layer is how legacy systems are actually replaced — and the data-ownership decision is the real project.
  7. Resiliency patterns come in a set: retry, breaker, bulkhead, throttle, health checks. Each is weak alone and strong together.
  8. Stamps partition users for blast radius; geodes partition geography for latency and force a multi-region consistency decision.
  9. Security: least privilege, defence in depth, and fail closed on authorisation.
  10. Every pattern carries an obligation. Skipping it is how the pattern becomes the outage.
