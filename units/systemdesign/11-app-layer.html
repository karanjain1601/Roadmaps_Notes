The application layer

The tier you own most completely, and the one where architecture fashion does the most damage. This chapter is about what makes a service disposable, why autoscaling is usually too slow, how to decide whether to split a system into services and what that split actually costs in availability and latency, and the machinery — discovery, gateways, meshes — that appears once you have more than one of anything.

~40 min read Stateless · autoscaling · services · discovery 2 interactive panels Prerequisite: chapters 3, 4, 10

11.1Stateless is the whole trick

Everything easy about the application tier — add a node, kill a node, deploy without downtime, autoscale, run in three zones — follows from one property: no instance holds anything that cannot be lost. Any request can go to any instance, and terminating an instance costs nothing but the requests currently in flight.

"Stateless" does not mean the process holds no memory. It means the process holds no authoritative state. Caches are fine, because a cold cache is a slow request rather than a wrong one. Connection pools are fine. What is not fine is anything whose loss changes the outcome.

Where state that used to live in a process should go
StateBad homeGood home
User sessionIn-process map keyed by session idSigned token held by the client, or a shared store (Redis) — one sub-millisecond lookup
Uploaded file mid-processingLocal /tmpObject storage, with the job referencing a key
Scheduled job timerssetInterval in every instanceA scheduler with leader election, or a queue with delayed delivery — otherwise N instances run the job N times
Rate-limit countersPer-instance countersA shared store, or accept per-instance limits and divide the budget explicitly
WebSocket connectionsUnavoidably in-processKeep it there, but put the routing elsewhere: a registry of which gateway holds which user, so other services can reach them
Feature flags and configFetched at startup onlyFetched with a TTL, with the last known good value cached on disk so a config outage does not stop startup

The last row is worth dwelling on, because it is the most common way a "stateless" service turns out not to be. Code that responds quickly and finishes the work afterwards, in the background, in memory, has created state that a rolling deploy destroys. Every such queue must either be durable or the work must be reconstructible.

11.2Autoscaling, and why it is usually late

Autoscaling has an intuitive appeal — capacity follows demand, you pay for what you use — and a control-loop problem that intuition misses. The loop is: observe a metric, wait for the evaluation period, decide, start an instance, wait for it to become useful, receive traffic. Every one of those steps has a delay, and their sum is your reaction time.

The delay budget 
metric scrape and aggregation     15–60 s
evaluation period / alarm periods 60–180 s
instance provisioning             20–120 s   (container: 2–20 s)
application start and warm-up     10–300 s   (JIT, caches, pool fill)
health check passes, joins pool   5–30 s
                                  ─────────
total                             2–10 minutes for VMs
                                  30 s–2 min for containers

A traffic spike that arrives in thirty seconds — a marketing email, a link from a broadcast, a retry storm — is over before autoscaling has finished thinking. Autoscaling handles trends: the daily curve, weekly growth, a slow ramp. It does not handle spikes. Spikes are handled by headroom, queues, and load shedding.

What to scale on
SignalGood whenFails when
CPU utilisationWork is CPU-bound and homogeneousThe service mostly waits on I/O — CPU stays at 20% while every request queues
Requests per second per instanceRequests are roughly uniform in costRequest cost varies by orders of magnitude
Concurrency / in-flight requestsAlmost always — it is Little's Law, so it captures both rate and costRarely. This is usually the best signal available
Queue depth or ageWorker pools consuming a queue — scale on age of the oldest message, which directly expresses the SLONothing much; it is the correct signal for async work
p99 latencyNever, as a scaling inputIt is a lagging, noisy indicator, and it rises for reasons scaling cannot fix — such as a slow dependency, where adding instances makes things worse
Scale up fast, scale down slowly

The asymmetry is deliberate. Being under-provisioned costs an outage; being over-provisioned costs money. So scale-up should be aggressive (add several instances at once, short evaluation, minimal cooldown) and scale-down should be timid (one instance at a time, long cooldown, a much lower threshold to avoid oscillation). Set the gap between the up and down thresholds wide enough that the system cannot flap between them — if adding an instance drops utilisation below the scale-down threshold, you have built an oscillator.

11.3One service or many

The honest framing: splitting a system into services is an organisational technique with technical costs. It lets separate teams deploy independently without coordinating, which is genuinely valuable once you have enough teams. It does not make software faster, simpler or more reliable — it makes all three worse — and the trade is worth it only when the coordination cost it removes is larger than the distribution cost it adds.

What a network boundary actually changes
In one processAcross services
A function call: nanoseconds, cannot half-failAn RPC: milliseconds, can time out, can succeed with no response received
A transaction spanning several tablesA saga with compensating actions, or accepted inconsistency
A joinN+1 calls, or duplicated data, or an aggregation service
A refactor across modules: one commit, compiler-checkedA coordinated release across repositories with version compatibility windows
A stack traceDistributed tracing, if you set it up
One availability numberMultiplied availabilities down the call chain — see Chapter 4
Run it locallyRun twelve of them locally, or develop against a shared environment

What a call chain costs

Availability multiplies down; latency adds up, or takes the slowest if parallel.

Where to draw the boundary, if you draw one

Three tests, all of which should agree before you split:

  1. Team boundary. Can one team own it end to end and deploy it without asking anyone? If two teams must coordinate every release anyway, the split has bought nothing.
  2. Data boundary. Does it own its data outright, with no other service reading its tables? If two services share a database, you have a distributed monolith: all the operational cost of services, none of the independence.
  3. Different scaling or reliability profile. Video transcoding needs CPU and can be interrupted; the checkout path needs low latency and must never be down. Splitting these lets you provision and operate them differently, which is a real technical reason rather than an organisational one.
The distributed monolith

The failure mode to recognise: services that must be deployed together, share a database, call each other synchronously in long chains, and break when any one changes. It arises from splitting along technical layers ("the API service", "the business logic service", "the data access service") rather than along domains. The test is simple — if a typical feature requires changing three services and releasing them in a particular order, the boundaries are in the wrong place, and you would be better off with one deployable containing well-separated modules.

The pragmatic path most successful systems take: start as a modular monolith, with strict internal module boundaries, separate schemas per module, and no cross-module database access. It deploys as one unit, so it keeps transactions, joins, stack traces and local development. When a module genuinely needs its own team or its own scaling profile, the boundary already exists and extracting it is a week rather than a rewrite. The strangler fig pattern is how the extraction happens without a big-bang migration.

11.4Service discovery

The moment instances are ephemeral, addresses stop being knowable in advance. Something must answer "where is the payments service right now?".

Discovery mechanisms
ApproachHowNotes
DNSA name resolves to current instance addresses; SRV records add ports and weightsUniversal, needs no library — but caching and TTL make changes slow, and many clients resolve once forever. See Chapter 8
Load balancer as the addressClients talk to one stable name; the balancer knows the instancesSimplest thing that works. An extra hop and one more thing to keep available
Registry, server-sideInstances register with Consul/etcd/Eureka; a proxy queries itFast propagation, health-aware, clients stay dumb
Registry, client-sideClients fetch and watch the instance list and balance themselvesLowest latency, no middle box; requires a capable client library per language
Orchestrator-nativeKubernetes Services: a stable virtual address plus DNS, with endpoints updated as pods come and goWhat most teams actually use; the registry is the control plane

Whatever the mechanism, three properties decide whether it works under stress. Deregistration must be fast — a dead instance that stays in the registry receives traffic, so registration is a lease that must be renewed rather than a permanent entry. The registry must not be on the critical path for every request: clients cache the instance list and refresh it in the background, so a registry outage degrades to stale routing rather than total failure. And it must fail static: if the registry is unreachable, keep using the last known list rather than concluding that no instances exist.

11.5The gateway

One entry point in front of many services, doing the work that would otherwise be duplicated in each.

  • Authentication and token validation — verify once at the edge, pass a trusted identity inward.
  • Rate limiting and quotas per API key or tenant.
  • Routing from public paths to internal services, decoupling your URL structure from your topology.
  • Request validation and size limits, so malformed input never reaches a service.
  • Protocol translation — public REST or GraphQL outside, gRPC inside.
  • Aggregation — one client call fanning out to several services, which is how you avoid a mobile client making twelve round trips over a slow link.
  • Observability — one place where every request is logged with a correlation id.
Do not put business logic in the gateway

It is tempting, because the gateway sees everything. It is also how the gateway becomes a shared component that every team must change and nobody owns, deployed on its own schedule, holding logic that belongs in a service — and a single point of failure for the entire product. Keep it to cross-cutting concerns that are genuinely uniform. When a specific client needs a tailored aggregation, build a backend for frontend: a thin service owned by that client's team, one per client type, so the mobile app's needs do not distort the web API.

11.6Service mesh

A mesh moves the networking concerns — retries, timeouts, circuit breaking, mutual TLS, load balancing, telemetry — out of application code and into a sidecar proxy deployed next to every instance. The proxies are the data plane; a controller distributing configuration to them is the control plane.

What a mesh gives and what it charges
GivesCharges
mTLS between every service, with automatic certificate rotationA proxy per instance: memory, CPU, and one or two milliseconds per hop
Uniform retries, timeouts, circuit breaking and outlier ejection, in every languageA control plane to run, upgrade and debug
Consistent metrics and traces for all traffic without touching codeA new layer between you and the network when something is mysteriously broken
Traffic shifting for canaries and mirroring, controlled by policySignificant conceptual surface for the team to learn

The judgement: a mesh is worth it when you have many services in several languages and need uniform policy — the alternative is reimplementing retries and mTLS in five client libraries and keeping them consistent, which is worse. With five services in one language, a good shared client library does the same job at a fraction of the operational cost. Adopt it for a concrete problem you already have, not in anticipation of one.

11.7Getting new code out safely

Deployment strategies
StrategyMechanismRollbackCost
RollingReplace instances in batchesRoll forward or repeat with the old version — minutesTwo versions run simultaneously, so both must be compatible
Blue-greenTwo full environments; switch traffic at onceInstant — switch backDouble the capacity during the switch; database schema must serve both
Canary1% of traffic to the new version, watch metrics, rampFast, and affects few usersNeeds good per-version metrics and an automated decision
Shadow / mirrorDuplicate real traffic to the new version, discard its responsesNo user impact at allDouble load on dependencies; must not cause side effects
Feature flagsDeploy the code dark, enable per user or percentageInstant, no deploy neededFlag debt; combinatorial testing surface

Two rules that make all of these work. Deployment and release are separate events — ship the code disabled, then turn it on independently, and rollback becomes a config change rather than a redeploy. And every deployment strategy above requires backwards-compatible changes, because two versions run at once: expand the schema, deploy code that writes both old and new, migrate, then contract. Any database change that is not additive turns a rolling deploy into an outage.

Graceful shutdown

The sequence an instance must implement, in this order, or every deploy drops requests:

  1. Receive SIGTERM.
  2. Immediately start failing the readiness check, so the load balancer stops sending new requests.
  3. Keep serving for a few seconds — the balancer has not noticed yet, and requests are still arriving.
  4. Stop accepting new connections; finish in-flight requests up to a deadline.
  5. Flush buffers, close connections, deregister, exit.

Step 3 is the one everyone omits. An instance that stops serving the instant it receives SIGTERM will reject every request already routed to it during the health-check propagation window — which is exactly the mysterious burst of 502s that accompanies each deploy.

11.8Cells: limiting the blast radius

A cell is a complete, independent copy of the stack — application, cache, database shard — serving a subset of users. Users are assigned to exactly one cell by a thin routing layer, and cells never talk to each other.

What it buys is the ability to make guarantees about scope. A bad deploy affects one cell. A poison-pill request cannot spread. A hot tenant saturates their own cell only. Deploys and migrations go cell by cell, so the first cell is a canary with a genuine blast-radius bound rather than a percentage of shared infrastructure. And each cell is small enough to reason about, which quietly solves several scaling problems by never letting any component get large.

The costs are real: per-cell fixed overhead, a routing layer that must be extremely reliable and is itself global, cross-cell operations that become awkward or forbidden, and N times the operational objects to observe. It is worth it above a certain scale, and premature below it — but the cheap version, designing so that cells could be introduced later (routing indirection, no global mutable state, no cross-user queries in the hot path), costs almost nothing now.

Your service autoscales on CPU. It calls a slow downstream API. During a downstream slowdown, CPU stays at 15% while latency triples. What happens, and what should you scale on?

Nothing happens — that is the problem. The instances are almost entirely idle, waiting on the network, so CPU never crosses the threshold and no instances are added, while every request pool fills with blocked work and queueing time explodes. Meanwhile the correct response might not be scaling at all: adding instances sends more concurrent requests to a downstream that is already struggling, making it worse. Scale on concurrency — in-flight requests per instance, which by Little's Law captures both rate and latency — and combine it with a concurrency limit and circuit breaker toward the downstream so that a slow dependency causes fast failures rather than unbounded queueing. See Chapter 20.

A team wants to split a working monolith into twelve services to "scale better". What do you ask?

Which component is actually at its limit, and why the limit cannot be raised where it is. Usually the answer is the database, which splitting the application layer does not help at all — twelve services against one shared database is strictly worse than one service against it. Then: how many teams are blocked on each other's releases today, since independent deployability is the real benefit; whether each proposed service would own its data outright; and whether they have measured what the current end-to-end availability would become once five services are in series on the request path. If the honest answers are "the database", "one team" and "they would share the schema", the right move is a modular monolith with clean internal boundaries plus work on the database — and extraction of the one or two modules that genuinely have a different scaling profile.

Why does adding an instance sometimes make latency worse for a minute?

Because a new instance is cold: empty local caches, an unwarmed JIT, unfilled connection pools, and lazily initialised code paths. Least-connections balancing sees an instance with zero in-flight requests and preferentially sends it traffic, so the coldest instance gets the largest share at the worst moment — and its slow responses show up directly in your p99. It can also cascade: the flood of new connections opens fresh connections to every downstream, and a burst of connection setup arrives at the database at the same moment. Fixes are slow start (ramp the new instance's weight over 30–60 seconds), warming caches and pools before passing the readiness check, and adding capacity ahead of demand rather than during a spike.

Recap

  1. Stateless means no authoritative state in the process. Caches and pools are fine; in-memory work queues and session maps are not.
  2. Autoscaling reacts in minutes, so it handles trends, not spikes. Spikes need headroom, queues and load shedding.
  3. Scale on concurrency or queue age, not on p99 latency. Scale up fast and down slowly, with a wide gap between thresholds.
  4. Splitting into services is an organisational technique with technical costs: multiplied availability, added latency, sagas instead of transactions, coordinated releases.
  5. Split on team ownership, data ownership and scaling profile — all three. Two services sharing a database is a distributed monolith.
  6. Start with a modular monolith and extract when a module earns it.
  7. Discovery must deregister fast, be cached by clients, and fail static using the last known instance list.
  8. Gateways handle cross-cutting concerns only; per-client aggregation belongs in a backend for frontend owned by that client's team.
  9. Separate deployment from release, make every change backwards compatible, and implement graceful shutdown including the keep-serving pause after SIGTERM.
  10. Cells bound the blast radius. Even if you never build them, design so you could.
