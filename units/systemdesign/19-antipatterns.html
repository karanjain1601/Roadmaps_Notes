Performance antipatterns

Systems do not usually fail in novel ways. They fail in about a dozen well-documented ways, each with a recognisable signature. Learning the catalogue turns "the site is slow" from an open-ended investigation into a short list of things to check — and turns a design review into a search for patterns you already know end badly.

~35 min read Ten patterns · symptoms · detection · fixes 2 interactive panels Prerequisite: chapters 3, 12, 18

19.1How to use this chapter

Each antipattern below has the same four parts: the symptom you would observe, the mechanism that produces it, how to detect it specifically, and the fix. Two properties recur across almost all of them and are worth noticing in advance.

  1. They are invisible at low load. Every one of these works fine in development and in a load test with ten users. They are properties of scale, contention or failure, and they appear at the worst moment by construction.
  2. Most have a positive feedback loop. The condition makes itself worse: slower responses mean more concurrent requests mean more contention mean slower responses. That is why they present as sudden collapse rather than gradual degradation.

19.2Busy database

Doing work in the wrong tier

Busy database

Symptom
Database CPU is saturated while application servers idle. Adding application instances changes nothing. Scaling the database up buys a few weeks.
Mechanism
Work that could run on cheap, horizontally scalable application servers has been pushed into the one component that cannot be scaled out: heavy stored procedures, business logic in triggers, string formatting and JSON assembly in SQL, sorting and aggregating large result sets, or the reporting query that scans the orders table every minute. The database is a shared, expensive, hard-to-replicate resource, so every cycle spent there costs more than the same cycle spent anywhere else.
Detect
Rank queries by total time (calls × mean_time). Look for high CPU with low I/O — that combination is computation, not data access. Check whether triggers or procedures appear in the plan.
Fix
Move computation to the application tier. Keep in the database only what genuinely needs to be there: filtering, joining and aggregating that reduces the data volume. Push analytical work to a replica or a separate analytical store. Precompute aggregates rather than recomputing them per request.
Caveat
The opposite error is real too — pulling a million rows into the application to filter them there is far worse. The rule is that work belonging in the database is work that reduces the number of bytes crossing the wire.

19.3Busy front end

Doing work in the wrong tier

Busy front end

Symptom
Request latency is high and highly variable; thread pools are exhausted; the service is unresponsive while CPU is pegged. Users waiting on trivial requests are blocked behind expensive ones.
Mechanism
Expensive work runs on the request-handling threads: generating a PDF, resizing an image, processing an upload, calling six slow services. Those threads are the scarcest resource in the tier, and one long-running task occupies the capacity of hundreds of short ones. Because everything shares the pool, the slow work degrades all traffic, not just its own.
Detect
Latency distribution with a heavy tail on specific endpoints; thread pool saturation metrics; a profiler showing request threads doing CPU-heavy work. The tell is that unrelated endpoints slow down together.
Fix
Move the work behind a queue and return 202 Accepted with a status URL (Chapter 17). If it must be synchronous, isolate it in a separate pool or a separate service so it cannot exhaust the shared one — that is the bulkhead in Chapter 20.

19.4Chatty I/O

Too many round trips

Chatty I/O

Symptom
Latency dominated by waiting, not by work. Every component reports low utilisation and the overall response is still slow. Latency scales with distance rather than with data volume.
Mechanism
Many small requests where a few larger ones would do. The canonical case is N+1: fetch 200 orders, then fetch each order's customer individually — 201 round trips instead of one. Also: reading a file line by line over the network, a loop calling an API once per item, and a page assembling itself from twelve sequential service calls.
Detect
A trace with a long horizontal ladder of near-identical short spans. A query log showing the same statement with different parameters thousands of times per second. Count queries per request in development — a threshold check in tests catches this before it ships.
Fix
Batch (WHERE id IN (…), a bulk endpoint, DataLoader-style per-request coalescing), join, or parallelise where there is no dependency. Reducing round trips beats making each one faster, because the cost is latency multiplied by count.

Round trips versus payload

Chatty and extraneous are opposite errors. Find the shape that is actually costing you.

19.5Extraneous fetching

Too much data

Extraneous fetching

Symptom
High network utilisation and memory pressure with modest request rates. Response times scale with data volume rather than with request count. Garbage collection pauses grow.
Mechanism
Retrieving far more than the request needs, then discarding most of it. SELECT * pulling large text and blob columns to render a list of titles. Fetching an entire collection to count it or to find one member. Loading a full object graph via an ORM's eager loading when three fields were required. Retrieving a whole page of results to display the first five.
Detect
Compare rows or bytes returned against bytes rendered. Watch for large result sets in query plans and for serialisation appearing high in profiles. In an ORM, log the generated SQL — the gap between what you asked for and what it fetched is usually startling.
Fix
Project only the needed columns, which often also enables an index-only scan (Chapter 12). Filter and aggregate at the source. Paginate. Use sparse fieldsets or GraphQL-style field selection at API boundaries. Beware the overcorrection: splitting one fetch into ten to avoid over-fetching converts this antipattern into the previous one.

19.6Improper instantiation

Wasted setup

Improper instantiation

Symptom
High CPU and memory allocation for the work performed. Connection or socket exhaustion. Latency that grows steadily with uptime, or under load in a way profiling attributes to object construction.
Mechanism
Creating expensive, shareable objects per request instead of once: an HTTP client (each one with its own connection pool, so pooling never happens and ports run out), a database connection, a serialiser, a compiled regular expression, a cryptographic context, an ORM session factory. The inverse also occurs — sharing something that is not thread-safe, which trades performance for corruption.
Detect
Allocation profiling; counts of open sockets or connections far exceeding concurrency; construction methods appearing near the top of a CPU profile.
Fix
Instantiate once per process and reuse — check the documentation for whether an object is intended to be shared, because for most clients the answer is "yes, and you are meant to". Reuse HTTP clients so connection pooling and keep-alive actually work; precompile regular expressions; use connection pools rather than connections.

19.7Monolithic persistence

Contention on a shared store

Monolithic persistence

Symptom
One data store is the bottleneck for everything. Unrelated features affect each other's latency. A batch job or an analytics query degrades the checkout path.
Mechanism
All data for all purposes lives in one store: transactional rows, session state, audit logs, telemetry, search, analytics, blobs. They have completely different access patterns and completely different growth rates, and they contend for the same buffer pool, the same locks, the same I/O and the same connection limit. The largest and least important table is usually the one causing the most damage.
Detect
Table sizes and growth rates by table; I/O and query time attributed by table; a correlation between a batch job's schedule and user-facing latency.
Fix
Federate by function — move the append-heavy, self-contained data out first (Chapter 13). Put blobs in object storage and keep only metadata in the database. Send analytics to an analytical store. This is usually reversible and it removes more load than any tuning.

19.8No caching

Repeating avoidable work

No caching

Symptom
The same expensive computation or query executes repeatedly with identical inputs and identical results. Load scales linearly with traffic when most of that traffic is asking the same questions.
Mechanism
No cache, or a cache that never hits because the key includes something that varies (a timestamp, a session id, a tracking parameter), or a TTL so short it expires before reuse, or a cache that is invalidated far more often than necessary.
Detect
Query fingerprints with high call counts and identical parameters. Cache hit ratio broken down per key prefix — a global number hides a prefix at 0%. Evictions near zero alongside a low hit ratio means the data is not being reused at all, which is a different problem.
Fix
Chapter 15. And note the mirror-image antipattern: caching things that are never read again, which costs memory and evicts what would have been reused.

19.9Noisy neighbour

Unfair sharing

Noisy neighbour

Symptom
Unpredictable latency with no correlation to your own traffic. One tenant, job or instance degrades everyone. Performance varies by host in a way that changes when workloads move.
Mechanism
A shared resource with no per-consumer limit: CPU on an oversubscribed hypervisor, IOPS on a shared volume, a connection pool, a thread pool, a cache, a database. One heavy consumer takes a disproportionate share and everyone else queues. In multi-tenant systems this is usually a single customer running an unusual query pattern.
Detect
Per-tenant and per-instance breakdowns of request rate, latency and resource use — which is why the usage monitoring in Chapter 18 is an operational tool, not just a billing one. CPU steal time reveals the hypervisor-level case.
Fix
Quotas and rate limits per tenant. Separate pools per consumer class (bulkheads). Dedicated capacity for the largest tenants. Cells, so a noisy tenant is confined to one cell's blast radius. At the infrastructure level, dedicated hosts or provisioned IOPS.

19.10Synchronous I/O

Blocking the wrong thread

Synchronous I/O

Symptom
Low CPU utilisation and high latency simultaneously. Throughput plateaus well below what the hardware should deliver. Thread counts climb; adding threads helps briefly then stops.
Mechanism
A thread blocks waiting for I/O and cannot do anything else. Since threads are expensive — roughly a megabyte of stack each, plus scheduling — concurrency is capped by thread count rather than by the work. Ten thousand concurrent connections needs ten thousand threads, which needs ten gigabytes of stack before any application memory. This is why event loops, async/await and virtual threads exist.
Detect
The signature is unmistakable: CPU under 30% while latency and queueing rise. Check thread pool saturation and the number of threads in a blocked state.
Fix
Non-blocking I/O, or lightweight threads (virtual threads, goroutines, coroutines) which give blocking-style code with non-blocking cost. Whichever you choose, never mix: one blocking call on an event loop stalls every request that loop is serving, and it is the most common way an async application performs worse than a threaded one.

19.11Retry storm

Positive feedback

Retry storm

Symptom
A small failure becomes a total outage. Traffic to the struggling component increases as it degrades. The service does not recover when the original cause is fixed, and load stays high after traffic has stopped.
Mechanism
A dependency slows down. Callers time out and retry. Retried requests add load, so it slows further, so more time out, so more retry. Worse, retries multiply through layers: if each of four layers retries three times, one user request becomes 3⁴ = 81 requests at the bottom. The system cannot recover because the retries alone now exceed its capacity.
Detect
Request rate at a downstream service exceeding the rate at the entry point — the ratio between them is your amplification factor and should be on a dashboard. Also: load that does not fall when traffic does.
Fix
Retry at one layer only, ideally the outermost that can meaningfully retry. Exponential backoff with full jitter. A retry budget capping retries at a small percentage of total traffic. Circuit breakers so a failing dependency is not called at all. All of this is Chapter 20.

CPU is at 20%, latency is 2 seconds, and adding instances does not help. What do you check first?

Low CPU with high latency means the system is waiting, so the question is on what. In order: is a downstream dependency slow (caller-side RED metrics will show it immediately); is there a concurrency limit that is full (thread pool, connection pool, semaphore — check wait time to acquire, not just utilisation); is it chatty I/O, visible in a trace as a ladder of many short spans; or is it blocking I/O on a fixed thread pool. Adding instances not helping is itself diagnostic — it means the constraint is shared rather than per-instance, which points at a downstream dependency or a shared limit rather than at your own capacity. That is also why scaling on CPU would never have fired here.

Traffic drops to zero but your service stays saturated. What is happening?

Retries, and possibly queued work. The load is self-generated: requests already in flight are timing out and being retried, each retry adding more load, and any retries buffered at intermediate layers are still being drained. It is the defining signature of a retry storm, and it is why such incidents do not end when you stop traffic. The immediate actions are to shed load and to open circuit breakers so the failing dependency is left alone long enough to recover; if there is a queue involved, you may need to purge or pause it. The durable fixes are a retry budget capping retries at a few percent of traffic, backoff with jitter, retrying at exactly one layer, and monitoring the ratio of downstream to upstream request rate so amplification is visible before it becomes an outage.

A load test at 2× expected traffic passes cleanly, but production falls over at 1.2×. Why might that be?

Because the load test almost certainly lacked the conditions these antipatterns need. Common differences: it used a small key set, so every request hit a warm cache and a warm buffer pool, hiding both the cold-miss path and cache pollution; it used homogeneous requests, so it never produced the variable service times that make queueing explode (Chapter 3); it ran against homogeneous, healthy instances, so no noisy neighbour or slow node appeared; it had no batch jobs, backups or deploys running concurrently; its dataset was small enough that a missing index did not matter; and it was a closed-loop generator, so it never sent requests faster than the system could answer — which means it never measured the system in the state that actually kills it. Test with production-shaped key distributions, mixed request costs, an open-loop generator, and a deliberately degraded instance in the pool.

Recap

  1. Busy database / busy front end: work is in a tier that cannot scale out or that owns the scarcest resource. Move it.
  2. Chatty I/O: cost is round trips × latency. Batch, join, parallelise. Extraneous fetching is the opposite error — do not overcorrect into it.
  3. Improper instantiation: expensive shareable objects created per request defeat pooling entirely.
  4. Monolithic persistence: unrelated data contending for one store. Federate the append-heavy tables out first.
  5. No caching: check hit ratio per key prefix, not globally.
  6. Noisy neighbour: shared resources need per-consumer limits, and per-tenant metrics to find the culprit.
  7. Synchronous I/O: low CPU plus high latency plus a thread-count ceiling. Never block an event loop.
  8. Retry storm: the only one with a feedback loop strong enough to prevent recovery. One retry layer, jittered backoff, a budget, and breakers.
  9. Bound every resource and jitter every schedule at the moment you create them.
  10. Low CPU with high latency means waiting; high CPU with high latency means working. That one pair narrows the search immediately.
