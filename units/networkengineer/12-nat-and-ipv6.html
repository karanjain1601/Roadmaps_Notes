NAT and the IPv6 transition

Address translation was a temporary measure adopted in the mid-1990s to buy time until IPv6 arrived. Thirty years later it is load-bearing infrastructure, and understanding precisely what it breaks is what makes the case for the transition concrete rather than ideological.

~28 min read NAT · port exhaustion · CGNAT · dual stack 2 interactive panels Prerequisite: chapters 4, 9

12.1What NAT actually does

The translation, and the state it requires 
OUTBOUND
  A packet arrives from 10.0.1.55:51234 heading for
  203.0.113.9:443. The router rewrites the SOURCE to its own
  public address and a port it chooses:

    10.0.1.55:51234  →  198.51.100.7:40219

  and records the mapping in a state table.

INBOUND
  The reply comes back to 198.51.100.7:40219. The router
  looks that up, finds the mapping, rewrites the destination
  back to 10.0.1.55:51234 and forwards it.

THE CONSEQUENCE THAT DEFINES EVERYTHING ELSE
  The mapping is created BY AN OUTBOUND PACKET. There is no
  entry for a connection nobody initiated, so an unsolicited
  inbound packet has nowhere to go and is dropped. That is
  why NAT is often described as a firewall, and the
  description is misleading — it blocks inbound connections
  as a SIDE EFFECT of not knowing where to send them, not
  as a policy decision. It provides no egress control, no
  logging worth the name, and no protection whatsoever
  against anything a client initiates.        → ch 16

THE STATE TABLE IS THE SCALING LIMIT
  Every concurrent connection is an entry. Entries expire on
  idle timers — commonly 24 hours for established TCP, a few
  minutes for UDP, 30 seconds for a half-open connection.
  Too short and long-lived idle sessions die; too long and
  the table fills with dead entries.

  A table that fills does not degrade gracefully. New
  connections simply fail, while existing ones work — which
  presents as "the internet is broken for new things but my
  download is fine", and is memorably confusing.

12.2Port exhaustion

How many subscribers fit behind one address?

A public address has about 64,000 usable ports. Every concurrent session takes one.

A modern web page opens far more sessions than people assume

The instinct is that a user is one or two connections. A single page load frequently opens dozens — to the site, to a content delivery network, to analytics, to fonts, to embedded video, to advertising exchanges — and each connection is a distinct port mapping held for the duration plus the idle timeout. Add a phone with push notifications, several tabs, a video call and a synchronising cloud drive, and a hundred and fifty concurrent sessions per device is an ordinary figure rather than a heavy one. This is why carrier-grade NAT ratios that look conservative on paper exhaust in practice, and why the symptom is characteristic: existing connections keep working while new ones fail, so the user reports that "some sites load and some do not" and reloading sometimes helps. It is also why fixed port blocks are common in carrier deployments despite being less efficient — they cap what one heavy user can consume, and they make the mapping loggable in a way dynamic allocation is not.

12.3What NAT breaks

The costs, roughly in order of how much they matter
BreaksDetail
Inbound connectionsNothing can reach you unless you initiate first, or configure a forward. Peer-to-peer, hosting anything, and remote access all need a workaround
Protocols carrying addresses in the payloadSIP, FTP in active mode, some games. The router must inspect and rewrite the payload — an "application layer gateway" — which is fragile and frequently makes things worse
End-to-end attributionThousands of subscribers share one address, so an abuse report or a block affects all of them. Logging must record the port and the exact time to identify anyone
Geolocation and reputationAddress-based decisions become wrong or unfair, because the address represents a region rather than a user
Long-lived idle connectionsThe mapping expires on the idle timer and the connection silently dies. This is why so many protocols send keepalives — they exist to hold a NAT mapping open
TroubleshootingCaptures on either side show different addresses for the same flow, so correlating them requires the translation table at the moment in question
A single point of failureThe state table is not easily replicated, so a failover drops every established connection unless the platform synchronises state
NAT is not a security control

It blocks unsolicited inbound connections, which is genuinely useful, and it does so as a consequence of having no mapping rather than as a policy — so it is worth exactly as much as a default-deny inbound rule and no more. What it conspicuously does not do: control what leaves, log usefully, inspect anything, distinguish one internal host from another, or stop a client fetching malware and beaconing outward. Two further points make the "NAT is security" claim actively harmful. It hides internal hosts from your own monitoring as effectively as from outsiders, so attributing outbound traffic to a device requires correlating translation logs. And it encourages a flat, unfiltered internal network on the reasoning that the perimeter is handled — which is precisely the arrangement Chapter 16 argues against. Where the address space is IPv6 and NAT is unnecessary, the correct replacement is a stateful firewall with a default-deny inbound policy, which provides the same protection explicitly and adds everything NAT never had.

12.4Running both

Dual stack, and the failure mode people meet first

Clients prefer IPv6 and fall back to IPv4. How gracefully depends on the client and on how the path fails.

The transition mechanisms, and which are worth using 
DUAL STACK                                     ← the default
  Run both, everywhere. Conceptually simplest, and it means
  running two of everything: two address plans, two sets of
  firewall rules, two routing tables, two of every bug.
  The firewall rules are where mistakes concentrate —
  a policy applied to IPv4 and forgotten on IPv6 is a hole,
  and it is invisible in an IPv4-only audit.

NAT64 + DNS64                        ← the interesting option
  Clients are IPv6 ONLY. DNS64 synthesises an IPv6 address
  for IPv4-only destinations, and NAT64 translates at the
  boundary. You operate one address family internally and
  reach the whole internet.
  Used at scale by large mobile operators. The caveat is
  anything that hands out literal IPv4 addresses rather than
  names — it bypasses DNS64 and simply fails.

464XLAT                              adds a client-side
  translator so IPv4-only applications work over an IPv6-
  only network. This is what makes IPv6-only mobile networks
  practical.

TUNNELS — 6to4, Teredo, ISATAP
  Historical. Poor performance, awkward failure modes,
  largely deprecated. If you find one running, it is
  probably the cause of whatever you are investigating.

DO NOT
  Deploy IPv6 without extending your monitoring, firewall
  policy and address management to cover it. Half-deployed
  IPv6 is worse than none: it is the black hole in the panel
  above, and users experience it as general slowness that
  nobody attributes to IPv6.
Why do users say "the internet is slow" when the IPv6 path is broken?

Because clients prefer IPv6 when a AAAA record exists, and a broken path fails much worse than an absent one. If IPv6 is simply not configured, the client sees no AAAA record, uses IPv4 immediately and nothing is affected. But if the address is advertised and the path silently discards packets, the client attempts IPv6 first, gets no response, and waits for a connection timeout before trying IPv4 — so every connection to every dual-stacked destination takes the timeout plus the real connection time. With a strict-preference client and a twenty-second timeout, that is twenty seconds of delay on essentially every new connection, and the user reports general slowness rather than an IPv6 problem because nothing in their experience mentions IPv6. Happy Eyeballs is the mitigation and it is why this is less catastrophic than it used to be: the client starts an IPv6 connection, waits a short interval — a few hundred milliseconds — then starts an IPv4 connection in parallel and uses whichever completes first. That caps the damage at a small delay rather than a timeout, and it also handles the case where IPv6 works but is slower. It is not a fix, though, since the delay is still paid on every connection and some clients and libraries do not implement it. Two things follow for operations. Treat half-deployed IPv6 as worse than none — if you advertise it, it must work, and if it stops working the right emergency action is to stop advertising the AAAA records. And monitor IPv6 reachability independently, because an IPv4-only synthetic check will report everything healthy throughout.

What actually makes carrier-grade NAT exhaust, given the ratios look reasonable?

Concurrent session counts far higher than the intuitive estimate, combined with idle timeouts that hold mappings open long after they are useful. A public address offers roughly 64,000 usable ports, and the tempting arithmetic is one or two connections per subscriber, which suggests enormous ratios are safe. Real devices hold a hundred to two hundred concurrent sessions routinely: a single page load opens connections to the site, a content delivery network, analytics, fonts, embedded video and several advertising endpoints, all separately; a phone adds push notification channels, a synchronising cloud drive, and background application traffic; multiply by several tabs and a couple of devices per person. At a hundred and fifty sessions each, one public address supports about four hundred and thirty subscribers, not the thousands the naive figure suggests. Two aggravating factors. Idle timeouts keep a mapping allocated after the conversation ends — commonly minutes for UDP and much longer for established TCP — so the table holds substantially more entries than there are active conversations, and shortening the timers to compensate kills long-lived idle sessions like SSH and message queues. And the failure is ungraceful: when ports run out, new connections fail while existing ones continue, so users report that some sites load and others do not and that reloading sometimes helps, which sounds like an application problem. The mitigations in practice are more public addresses, fixed port blocks per subscriber to cap heavy users and make the mapping loggable for abuse attribution, and — the actual solution — deploying IPv6 so the majority of traffic never touches the translator at all.

If NAT is not a security control, why does removing it feel risky?

Because it has been providing one specific protection incidentally — no unsolicited inbound connections — and organisations have frequently built on the assumption that internal hosts are unreachable without ever writing that down as a policy. Move to IPv6 with globally routable addresses and that protection disappears unless you replace it deliberately, and the internal network is now reachable in a way it has never been. The feeling is justified; the conclusion "therefore keep NAT" is not. The correct replacement is a stateful firewall with a default-deny inbound policy, which provides exactly the same protection explicitly, plus everything NAT never offered: egress control, per-host visibility, logging that identifies which device did what, and rules you can read and audit rather than a behaviour you infer. Three things make the transition safe rather than nerve-racking. Write the inbound policy before the addresses become routable, and verify it from outside — the failure mode is deploying IPv6 addressing first and the policy afterwards. Ensure your firewall rules, monitoring, logging and intrusion detection all cover IPv6 as first-class, because a rule set applied to IPv4 and silently absent on IPv6 is a hole that an IPv4-only audit will never find. And expect the visibility to improve: without translation, a log entry names the actual host rather than a shared public address, which makes attribution during an incident dramatically easier. The residual honest concern is that some environments genuinely want address opacity, and for those the answer is unique local addressing with a proxy, not NAT — but that is a narrow case rather than the default.

Recap

  1. The mapping is created by an outbound packet, which is why unsolicited inbound has nowhere to go.
  2. NAT blocks inbound as a side effect, not a policy. It is worth a default-deny rule and no more.
  3. A full state table fails ungracefully — new connections break while existing ones work.
  4. A device holds 100–200 concurrent sessions routinely, so one public address supports a few hundred subscribers.
  5. Fixed port blocks cap heavy users and make mappings loggable, at the cost of efficiency.
  6. Keepalives largely exist to hold NAT mappings open.
  7. Half-deployed IPv6 is worse than none — a black-holed path costs a timeout on every connection.
  8. Happy Eyeballs caps that damage by racing both families rather than waiting.
  9. NAT64 with DNS64 lets you run IPv6-only internally, and breaks on literal IPv4 addresses.
  10. Replace NAT with a default-deny stateful firewall, written and verified before the addresses become routable.
