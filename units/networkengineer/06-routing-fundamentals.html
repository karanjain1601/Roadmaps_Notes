Routing fundamentals

A router makes one decision, several million times a second: which interface does this packet leave by? Everything else — protocols, metrics, policy — exists to populate the table that answers it.

~28 min read Longest prefix · sources · distance · metrics 2 interactive panels Prerequisite: chapter 4

6.1The decision

What happens to a packet at a router 
1  Frame arrives. Check the FCS; discard if corrupt.
2  Is the destination MAC mine? If not, and I am not a
   switch, drop it.
3  Strip the frame. Now I have an IP packet.
4  Verify the header. Decrement TTL — if it hits zero,
   discard and send ICMP time exceeded. This is what makes
   traceroute work.
5  LOOK UP the destination address in the forwarding table.
   → LONGEST PREFIX MATCH. This is the whole chapter.
6  The entry gives an outgoing interface and a next-hop
   address.
7  Resolve that next hop to a MAC address (ARP or neighbour
   discovery), build a NEW frame, transmit.

RIB AND FIB — two tables, and the distinction matters
  RIB  the routing information base. Everything the router
       has learned from every source, including routes it
       is not using. Built in software by the control plane.
  FIB  the forwarding information base. Only the winning
       routes, in a structure optimised for lookup, held in
       hardware. Built from the RIB and consulted per packet.

  "show ip route" shows the RIB. What actually forwards your
  packet is the FIB, and on a bad day they disagree — which
  is a genuinely confusing fault and worth knowing exists.

THE ROUTER DOES NOT KNOW THE PATH
  It knows the NEXT HOP only. No router anywhere holds the
  end-to-end route; each one independently decides the next
  step, and the path is an emergent property of all those
  decisions. That is why a loop is possible and why
  asymmetric paths are normal rather than a fault.

6.2Longest prefix match

The rule that decides everything: the most specific matching route wins, regardless of how it was learned, what its metric is, or how it was ordered in the configuration.

Which route wins?

A realistic table and a destination. Note which properties are considered and in what order.

Specificity beats everything, including your intentions

This is the source of a large fraction of routing surprises. A /32 host route learned from anywhere will beat a /24 you configured deliberately, because the comparison happens on prefix length before anything else is considered. Administrative distance and metric only ever act as tie-breakers between routes of identical prefix length — they never let a less specific route win. So if traffic is going somewhere you did not intend, the question is not "which protocol won" but "is there a more specific route I did not expect?", and the command to answer it is the one that shows the matching entry for a specific destination rather than the whole table. The corollary is a useful technique: to override routing for one destination without touching anything else, add a more specific route. It will win by construction.

Distance, metric and the order they apply

Several routes to the same prefix. Only one is installed, and the tie-break sequence is fixed.

The static route that outlives its usefulness

A static route has a distance of 1, so it beats every dynamic protocol. That is exactly what you want when you add one to work around a problem at two in the morning, and it is exactly the problem eighteen months later: the underlying issue was fixed, the dynamic protocol now has a correct and better path, and the static route silently continues to win. Nothing alerts on it, it does not appear as an error, and it survives every reconvergence — so traffic keeps taking a path nobody has thought about since. Worse, a static route pointing at a next-hop address stays in the table as long as that address is reachable by any means, so it can persist long after the link it was written for has gone. Two habits: give every temporary static route a comment with a date and a ticket reference, and audit them periodically against what the IGP would choose. Where a static route is genuinely meant to be a backup, make it floating with a distance above the protocol's, so it installs only when the dynamic route is gone.

6.4Equal-cost paths and default routes

Two things that come up constantly 
EQUAL-COST MULTIPATH
  When two routes tie on prefix length, distance AND metric,
  most routers install both and hash flows across them —
  the same mechanism as link aggregation in chapter 5, and
  with the same consequence: a single flow does not exceed
  one path.

  Hashing must be CONSISTENT per flow, or packets reorder
  and TCP interprets it as loss. This is why per-packet load
  sharing is almost always the wrong setting despite looking
  fairer on a graph.

  It also makes traceroute confusing: successive probes may
  take different paths, so the output shows a topology that
  no single packet ever experienced.               → ch 20

THE DEFAULT ROUTE  0.0.0.0/0
  Prefix length zero, so it matches everything and loses to
  every other route by definition. It is the "I have no
  better idea" entry.

  · An access router usually has one and little else.
  · A core internet router has none — that is what "carrying
    a full table" means, and it is why those routers need so
    much memory.                                    → ch 8

  A DEFAULT ROUTE HIDES REACHABILITY PROBLEMS. With one
  present, a packet for an unreachable destination is
  forwarded upstream rather than rejected, so the failure
  happens somewhere else and is harder to attribute. Without
  one, the router answers "network unreachable" immediately,
  which is a much better diagnostic.

NULL ROUTES
  A route pointing at a discard interface. Used to drop
  traffic efficiently in hardware, and to make summarisation
  safe — advertise a summary, and null-route the summary
  locally so anything unallocated inside it is dropped
  rather than looping.                              → ch 4
Traffic to one host is taking the wrong path. Where do you look?

For a more specific route than the one you expect to be used, because prefix length is compared before anything else and nothing about distance or metric can overcome it. The usual instinct is to ask which protocol won, and that is the wrong question — administrative distance and metric are only tie-breakers between routes of identical prefix length. A /32 host route learned from anywhere, a /25 someone added as a workaround, or a more specific route redistributed in from another protocol will all beat the /24 you configured, silently and by design. So the first command is the one that shows the matching entry for that specific destination rather than the whole table, since that resolves the longest-prefix question immediately and tells you the source. From there the likely culprits, in rough order of frequency: a leftover static route added during an incident and never removed, which wins at distance 1 over everything dynamic; a redistribution from another protocol bringing in specifics you did not intend; a route learned from a neighbour that should not be advertising it, which is a filtering problem; and occasionally a summary that is less specific than something else, so traffic that should follow the summary follows the specific instead. Two further checks worth running. Confirm the FIB agrees with the RIB — they normally match, and when they do not the symptoms are baffling because the table you are reading is not the one forwarding. And verify the return path separately, since routing is independently decided in each direction and asymmetry is normal rather than a fault, but it interacts badly with stateful firewalls.

What is a floating static route and when do you use it?

A static route configured with an administrative distance deliberately set above that of the dynamic protocol covering the same prefix, so it sits in the routing information base unused and only gets installed if the dynamic route disappears. It is the standard idiom for a backup path. The reason it needs the distance adjustment is that a static route defaults to distance 1 and would therefore beat OSPF at 110 or EIGRP at 90 all of the time — which is the opposite of a backup, since it would take over permanently and the expensive primary link would sit idle. Setting the static route to, say, 130 inverts that: while OSPF has a route the static one loses and is not installed, and the moment OSPF withdraws it the static becomes the best remaining candidate and takes over. The classic use is a secondary WAN circuit or a cellular link that should carry traffic only when the primary fails, where running a routing protocol over the backup is not possible or not worth it. Two details that catch people out. The failover only happens when the dynamic route is actually withdrawn, so it depends on the protocol detecting the failure — if the primary link stays up but is black-holing traffic, the OSPF route persists and the static never installs; that is what BFD and reachability tracking are for. And a static route pointing at a next-hop address rather than an interface remains valid as long as that address is reachable by any path, which can keep it installed long after the intended link is gone; pointing at an interface, or tracking the next hop explicitly, makes the failure detection honest.

Why does having a default route make troubleshooting harder?

Because it converts a clean local failure into a remote and ambiguous one. Without a default route, a packet for a destination the router has no entry for is dropped immediately and an ICMP network-unreachable message is returned — so the sender gets a fast, specific error, and the router that produced it is the one holding the missing route. That is close to an ideal diagnostic. With a default route present, the same packet matches 0.0.0.0/0 and is forwarded upstream, where it may be forwarded again, and again, until something further away discards it or it simply disappears. The symptom the user reports is a timeout rather than an error, the failure appears to be somewhere other than where the missing route is, and the natural instinct is to investigate the far end of the path rather than the near end. It gets worse in two specific ways. If two routers each hold a default route pointing at the other — which happens easily in a partial mesh or after a failover — packets loop until the TTL expires, consuming bandwidth and producing a traceroute that oscillates between two hops. And a default route can mask the loss of a summary or an entire routing adjacency, because traffic keeps flowing to a plausible-looking upstream rather than failing visibly, so the underlying outage goes unnoticed until something depends on the missing specifics. None of this argues against default routes, which are entirely correct at the edge of a network. It argues for knowing they are there when diagnosing, for null-routing your own summarised space so internal destinations fail locally rather than escaping upstream, and for not configuring defaults pointing in both directions between a pair of routers.

Recap

  1. A router knows the next hop, not the path. The route is emergent, which is why asymmetry is normal.
  2. The RIB is everything learned; the FIB is what forwards. They can disagree.
  3. Longest prefix match wins before anything else is considered.
  4. Distance and metric are tie-breakers between equal prefix lengths only.
  5. To override routing for one destination, add a more specific route. It wins by construction.
  6. Connected is distance 0 and static is 1, so a hand-written route beats every protocol.
  7. The static route added at 2am is still winning eighteen months later. Date them and audit them.
  8. A floating static has distance above the protocol's and installs only when the dynamic route goes.
  9. Equal-cost paths hash per flow, so one flow does not exceed one path — and traceroute gets confusing.
  10. A default route turns a clean local failure into a distant ambiguous one.
