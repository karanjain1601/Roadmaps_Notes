Network security

The Cyber Security unit covers what firewalls and intrusion prevention do. This chapter is the network engineer's half: where filtering belongs in a topology, what segmentation costs to operate, and the layer-2 attacks that every switch can prevent and almost none is configured to.

Filter as close to the source as the control allows

Traffic dropped at the ingress port consumed one port's worth of resources. The same traffic dropped at the firewall has already crossed the access switch, the distribution layer and the core, consuming capacity and buffer at every hop — and during a flood, that is capacity legitimate traffic needed. So the ordering principle is to push each control to the earliest point that can enforce it: anti-spoofing and port security at the access port, coarse address and port filtering at the first router, and stateful or application-aware policy at the trust boundary where it genuinely needs the context. The counter-consideration is manageability, since a rule replicated across two hundred access switches is two hundred places to get it wrong — which is the argument for a central policy engine that generates the distributed configuration rather than for centralising the enforcement itself.

16.4The layer-2 attacks nobody mitigates

What a device on your access VLAN can do

Every one of these has a one-line switch feature that prevents it, and most switches ship without them.

The default switch configuration assumes everyone is trustworthy

Ethernet was designed for a cooperative environment, and the defaults still reflect that. Out of the box, a switch will accept a DHCP server from any port, believe any ARP reply, learn unlimited MAC addresses, negotiate a trunk with whatever is plugged in, and participate in spanning tree with an unknown device. Each of those is a documented attack that takes a laptop and a few minutes, and each is prevented by a single line of configuration that costs nothing and breaks nothing. The reason they are not enabled is simply that they are not defaults, and access switch configuration tends to be copied forward from whatever was deployed years ago. This is the cheapest security work available in most networks — a template change and a rolling reconfiguration, with no purchase and no architecture project.

Why is east-west filtering usually the bigger gap than the perimeter?

Because almost every organisation has invested in the perimeter for thirty years and comparatively little between internal segments, so an attacker who reaches any internal host frequently reaches everything. The perimeter firewall is well configured, monitored and reviewed; internal traffic between a user VLAN and a server VLAN commonly passes through a router with no policy at all, or through a switched fabric with none possible. The consequence is that the difficulty of an intrusion is entirely front-loaded — get one foothold, by phishing or a compromised device or someone plugging in a laptop, and the remaining lateral movement is unimpeded. That is the mechanism behind most of the incidents in Cyber Security chapter 4. Three practical moves, in order of value for the effort. Put a policy between the user population and the servers, which is one boundary, is usually achievable with existing equipment, and removes the single most useful path an attacker has. Isolate the management network so that reaching a switch or a hypervisor console requires being on a segment users cannot reach — without this, every other segment boundary is enforced by devices the attacker can reconfigure. And separate the things that cannot be patched: cameras, door controllers, building systems and industrial equipment, which are frequently the entry point and almost never need to reach anything except their controller. Note the cost side honestly: internal filtering means discovering which flows genuinely exist, and the way to do that without breaking things is to deploy in monitoring mode first and read the logs for a few weeks.

How many segments should a network have?

As many as have genuinely different policy, and no more. The test is simple and rarely applied: will the rules between this new segment and its neighbour differ from the rules that already exist? If not, the segment adds an address block, a gateway, a DHCP scope, a set of firewall rules, a monitoring target and a place for a misconfiguration, in exchange for no security benefit. Segmentation has a real and non-linear cost, because policy is written between pairs — twenty segments is a hundred and ninety possible pairings, and even if most are simply denied, the ones that are not must each be described, reviewed and maintained. That is how organisations end up with rule sets nobody understands, which is its own security problem: a rule set too large to reason about accumulates permissive entries that nobody can safely remove. Two structural answers to that cost. Use a tiered model rather than writing rules per pair — group segments into tiers and define policy between tiers, so the rule count grows with tiers rather than with the square of segments. And generate the policy from a source of truth rather than editing it by hand, so that adding a segment is a data change and the rules are derived; this is what makes fine-grained segmentation tractable at all and it is the real prerequisite for anything described as micro-segmentation. Where to start if you have one flat network: management, guest, unpatchable devices, and a boundary between users and servers. Those four capture most of the available risk reduction, and each is defensible on its own.

What is the cheapest security improvement available on most networks?

Enabling the layer-2 protections that every switch already supports and almost none has configured. The default Ethernet configuration assumes a cooperative environment, which was reasonable when it was designed and is not now, so out of the box a switch will accept a DHCP server from any port, believe any ARP reply, learn unlimited MAC addresses, negotiate a trunk with whatever is plugged in, and let an unknown device participate in spanning tree. Each of those is a documented attack requiring a laptop and a few minutes, and each is closed by one line of configuration. Specifically: DHCP snooping, which permits DHCP responses only from ports you have marked as trusted and stops a rogue server handing out its own address as the gateway; dynamic ARP inspection, which validates ARP against the snooping table and prevents an attacker claiming to be the gateway; port security, capping learned addresses per port so that MAC flooding cannot turn the switch into a hub; BPDU guard, shutting a port that sends spanning tree messages, which prevents both the accidental patch-cable loop and a device trying to become root; and setting access ports to access mode explicitly rather than leaving dynamic trunk negotiation on, which prevents a device negotiating itself a trunk and reaching every VLAN. None of these costs money, none requires new hardware, and none breaks a correctly-behaving device. The reason they are absent is not disagreement — it is that they are not defaults and access switch configuration gets copied forward from whatever was deployed years ago. The work is a template change and a rolling reconfiguration, which is a genuinely small project for the amount of attack surface it removes.

Recap

  1. Filter as close to the source as the control allows; traffic dropped late has already consumed the path.
  2. Centralise policy generation, not necessarily enforcement.
  3. Segment by trust and function, because departments reorganise and trust relationships do not.
  4. Only add a segment if the policy will differ. Otherwise it is cost with no benefit.
  5. Rules written per pair grow with the square of segments. Use tiers, and generate them.
  6. East-west is the usual gap — start with users-to-servers, management, and unpatchable devices.
  7. An attacker who reaches the management network has undone every other boundary.
  8. 802.1X is what MAC filtering pretends to be. Roll it out in monitor mode first.
  9. Switch defaults assume everyone is trustworthy. Snooping, ARP inspection, port security, BPDU guard.
  10. Set access ports to access mode explicitly, or a device can negotiate itself a trunk.
