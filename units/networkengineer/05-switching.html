Switching

A switch does three things: learn, forward, flood. Almost every catastrophic layer-2 failure comes from the third one running out of control, and this chapter is mostly about why a single miswired cable can take a site down in under a millisecond.

~30 min read MAC learning · VLANs · loops · STP · LACP 2 interactive panels Prerequisite: chapter 3

5.1Learn, forward, flood

The entire forwarding algorithm 
ON RECEIVING A FRAME ON PORT p:

  1  LEARN
     Record  source MAC → port p  in the MAC address table,
     scoped to the VLAN. Refresh the age timer.
     This is how the table is built — there is no protocol
     and no announcement. A switch learns only by watching
     traffic go past.

  2  LOOK UP the destination MAC in the table, for this VLAN.

  3a HIT     → forward out that one port. Done.
  3b MISS    → FLOOD out every port in the VLAN except p.
  3c BROADCAST or multicast → flood likewise.

WHY "UNKNOWN UNICAST FLOODING" MATTERS
  A miss is not an error. It is normal for the first frame
  to a device that has been quiet, and the reply teaches the
  switch where it lives. But note what it means: traffic for
  an unknown destination goes to EVERY port in the VLAN,
  which is both a performance cost and a confidentiality one.

AGEING
  Entries expire, typically after 300 seconds. A device that
  is silent for longer than that must be flooded to again.
  This interacts with ARP caches in a way that produces
  periodic, mysterious floods on quiet networks.

THE ASYMMETRY THAT CAUSES REAL PROBLEMS
  If traffic to a host takes a different path from traffic
  FROM it, the switches on the return path never learn where
  it is — so every frame to it is flooded, forever. That is
  the classic symptom of asymmetric routing meeting a
  first-hop redundancy protocol.                     → ch 18
MAC table exhaustion

The table is finite — a few thousand entries on an access switch, tens of thousands on a core one. When it fills, the switch cannot learn new addresses, so every frame to an unlearned destination is flooded to every port. The result is a switch behaving like a hub: performance collapses, and every device on the VLAN can see traffic intended for others. This can happen accidentally on a very large flat segment, and it can be caused deliberately in seconds by an attacker generating frames with random source addresses — the classic MAC flooding attack. The defence is port security: cap the number of addresses learned per access port, since a legitimate desk port needs one or two and never a thousand. Combined with the broadcast limits in §5.3, this turns a whole class of layer-2 attacks into a shut-down port and an alert.

5.2VLANs

The concepts, and where people get confused
TermMeans
VLANOne broadcast domain. Cutting a physical switch into several logical ones — a frame in VLAN 10 never reaches VLAN 20 without a router
Access portCarries one VLAN, untagged. What an end device connects to. The device has no idea a VLAN exists
Trunk portCarries several VLANs, tagged with 802.1Q so the far end can tell them apart. Switch-to-switch
Native VLANThe one VLAN sent untagged on a trunk. A mismatch between the two ends silently merges two broadcast domains — set it explicitly on both sides and never use VLAN 1
Voice VLANA port carrying an untagged data VLAN for the PC and a tagged voice VLAN for the phone it plugs through
SVIA virtual interface giving the switch an IP address in a VLAN — usually the default gateway for hosts in it
Inter-VLAN routingMoving between VLANs requires layer 3. On a layer-3 switch this is one device doing both jobs, which is the normal modern arrangement
A VLAN is a broadcast domain, and that is the whole design rationale

Every reason to create a VLAN reduces to one of two things: containing broadcasts so the segment scales, or creating a policy boundary so that traffic between two groups must pass a router where it can be filtered. Anything else is decoration. That test is worth applying when someone proposes a new one, because VLAN sprawl is real: each one needs an address block, a gateway, a DHCP scope, firewall rules and a place in the spanning tree, so a hundred VLANs is a hundred of each. The modern counter-argument matters too — with layer-3 access designs, where routing happens on the access switch and each port is its own tiny subnet, the broadcast domain shrinks to nothing and the spanning tree disappears entirely. That approach is common in data centres and increasingly in campus networks, and it removes most of this chapter's failure modes by construction.

5.3Loops, and why they are catastrophic

What a loop does

One broadcast frame, one accidental cable between two switch ports. Watch the time scale.

Why an IP packet survives a loop and a frame does not 
AN IP PACKET has a TIME TO LIVE field. Every router
decrements it, and at zero the packet is discarded and an
ICMP message goes back to the sender. A routing loop is
therefore self-limiting and diagnosable — traceroute exists
precisely because of this field.

AN ETHERNET FRAME HAS NO SUCH FIELD.
  Nothing in the header counts hops. Nothing expires. A
  frame that enters a loop circulates until the loop is
  broken or the equipment fails.

AND IT MULTIPLIES.
  Each switch floods the broadcast out every port except the
  one it arrived on — so one frame becomes two, two become
  four. Combined with no TTL, this is exponential growth
  with no ceiling except the link rate.

THE THREE THINGS THAT THEN HAPPEN, TOGETHER
  1  Links saturate — in microseconds, not seconds.
  2  MAC tables thrash. The same source address appears on
     different ports thousands of times a second, so the
     table is rewritten constantly and legitimate forwarding
     stops working.
  3  Switch CPUs saturate processing broadcasts, so the
     management plane dies too — which is why you frequently
     cannot log in to fix it, and end up walking to the rack.

THIS IS WHY LAYER 2 NEEDS A LOOP-PREVENTION PROTOCOL and
layer 3 does not. It is not a preference; it is the absence
of a hop count.

5.4Spanning tree

Convergence

The protocol blocks redundant links to make a loop-free tree. What it costs when the topology changes.

The settings that matter, and the defaults that bite 
SET THE ROOT BRIDGE EXPLICITLY
  The default election is by lowest bridge ID, which is
  priority plus MAC address — so with everything at the
  default priority, the OLDEST switch wins, because older
  hardware tends to have lower MAC addresses. Your root
  bridge is then whichever access switch happened to be
  bought first, and traffic bends through it.
    → set priority low on your intended root, and second
      lowest on its backup. Two commands, and it is the
      single most valuable spanning tree change you can make.

EDGE PORTS (PORTFAST)
  An access port with a PC on it should not wait through
  listening and learning — that is the 30-second delay users
  experience as "the network takes ages after I plug in".
  Mark access ports as edge so they forward immediately.

BPDU GUARD, ALWAYS, ON EVERY EDGE PORT
  If a switch appears on a port that should have a PC on it,
  shut the port down. This single feature prevents:
    · someone plugging a desk switch in and becoming root
    · the accidental loop from a patch cable in two wall
      sockets, which is the most common cause of the outage
      in the panel above
  It costs nothing and it is off by default.

ROOT GUARD on ports facing downstream, so an unexpected
switch cannot claim to be root.

LOOP GUARD where a unidirectional failure could turn a
blocking port into a forwarding one.

AND THE DESIGN-LEVEL ANSWER
  Do not rely on spanning tree for anything you care about.
  Use it as a safety net, and build the topology so that it
  has nothing to block: link aggregation for redundancy
  between two devices, and layer 3 for redundancy between
  more than two.

5.5Link aggregation

Bonding several links into one logical link

Why does a layer-2 loop take a network down but a routing loop does not?

Because an IP packet carries a time-to-live field and an Ethernet frame carries nothing equivalent. Every router decrements the TTL, and at zero the packet is discarded and an ICMP message is returned — so a routing loop wastes some bandwidth, produces a distinctive traceroute, and is self-limiting and diagnosable. The Ethernet header has no hop count, no expiry and no sequence number, so a frame that enters a loop circulates until someone breaks the loop or the equipment fails. On its own that would be bad; what makes it catastrophic is that it multiplies. A broadcast is flooded out every port except the one it arrived on, so each pass round the loop doubles the number of copies, and exponential growth with no ceiling other than the link rate saturates a gigabit link in a few hundred microseconds. Three things then fail simultaneously, which is why the outage is total rather than partial. The links saturate, so no legitimate traffic gets through. The MAC tables thrash, because the same source address keeps appearing on different ports thousands of times a second, and a switch that is rewriting its table constantly cannot forward correctly even for unaffected traffic. And the switch CPUs saturate processing the broadcast flood, which takes the management plane down with everything else — which is why you often cannot log in to diagnose it and end up physically unplugging cables. The defences follow from the mechanism: spanning tree to prevent the loop existing, BPDU guard so an unexpected switch on an access port is shut down rather than merged, and storm control to cap broadcast rate per port as a last resort.

You bonded four 1 Gbps links and a single file transfer still runs at 1 Gbps. Why?

Because link aggregation distributes flows across member links, not packets, and it does so by hashing header fields to choose a link. That is deliberate: spreading a single flow's packets across several links round-robin would deliver them out of order, and out-of-order delivery makes TCP interpret the gaps as loss, triggering retransmission and congestion backoff that would make the bundle slower than one link. So the hash is a feature, and the consequence is that a single conversation is capped at one member link's speed no matter how many links you bond. Four bonded gigabit links give four gigabits of aggregate capacity across many flows, and one gigabit to any individual transfer. What to do about it depends on what you need. If the requirement is genuinely a single fast flow, you need a faster link rather than more links — one 10 Gbps connection instead of four bonded 1 Gbps ones. If the requirement is aggregate throughput across many users, the bundle is doing its job and the thing to check is the hash distribution: the default on some equipment hashes only source and destination MAC, which on a link between two switches means every flow hashes identically and lands on one member. Including IP addresses and, better, layer-4 port numbers in the hash spreads traffic properly, and it is a one-line change that frequently fixes an "aggregation isn't working" complaint. Also worth checking: with a small number of very large flows, hashing is statistically lumpy even when configured well, so two backups can land on the same member while others idle — that is expected behaviour rather than a fault, and the fix is again a faster single link.

What are the two spanning tree settings worth making before anything else?

Set the root bridge explicitly, and enable BPDU guard on every edge port. The root election defaults to the lowest bridge identifier, which is a priority value plus the switch's MAC address — and since every switch ships with the same default priority, the tie is broken by MAC address, which correlates loosely with manufacturing age. So an unconfigured network elects whichever switch happens to have the lowest MAC address, frequently an old access switch in a cupboard, and the entire tree bends traffic through it. Every inter-VLAN flow then takes a path nobody designed, redundant links block in the wrong places, and a failure of that cupboard switch reconverges the whole network. Setting a low priority on your intended root and the next-lowest on its backup is two commands and it makes the topology deterministic. BPDU guard is the second because it prevents the most common real-world layer-2 outage: someone plugs a small unmanaged switch into a desk port, or patches a cable between two wall sockets, and either creates a loop or introduces a device that wins the root election. With BPDU guard, a port that should have a PC on it and instead receives a spanning tree message is shut down immediately and logged — the outage becomes one dead port and an alert instead of a site-wide storm. It is off by default and costs nothing. Two more worth adding once those are in place: mark access ports as edge so users are not waiting thirty seconds after plugging in, and use root guard on downstream-facing ports. And at the design level, treat spanning tree as a safety net rather than a mechanism — build with link aggregation between pairs and layer 3 above that, so the protocol has nothing to block.

Recap

  1. Learn, forward, flood. A switch builds its table only by watching traffic; there is no protocol.
  2. Unknown unicast flooding is normal, and asymmetric paths make it permanent.
  3. A full MAC table turns a switch into a hub. Port security caps addresses per access port.
  4. A VLAN is a broadcast domain — create one to contain broadcasts or to force traffic past a router.
  5. Set the native VLAN explicitly on both ends, and never leave it as VLAN 1.
  6. Frames have no TTL, which is the entire reason layer 2 needs a loop-prevention protocol.
  7. A loop saturates a gigabit link in microseconds and kills the management plane with it.
  8. Set the root bridge explicitly or the oldest switch in the building wins the election.
  9. BPDU guard on every edge port turns the classic patch-cable loop into one dead port.
  10. Aggregation hashes flows, so one transfer never exceeds one member link.
