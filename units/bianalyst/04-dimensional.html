    THE FIRST DECISION

    Grain is what everything else follows from

    One sentence, and it decides the rest of the model

    The grain of a fact table is the answer to "what does one row mean?" — stated as a sentence, not a list of columns. One row per order line. One row per account per day. One row per support ticket state change.

    Everything downstream is determined by it: which measures can live on the table, which dimensions can attach, which questions are answerable, and — as the first demo shows — whether a sum is correct or off by a factor of six.

    The single most common modelling failure is not choosing a wrong grain. It is having two grains in one table because nobody wrote the sentence down, and then discovering it when a total looks odd.

    The vocabulary, briefly
    TermWhat it isTest
    FactA row recording something that happenedHas a time, and numbers you would sum
    MeasureA number on a fact rowWould you ever add it up?
    DimensionA thing you slice byWould you ever group by it?
    GrainWhat one fact row meansCan you say it in one sentence?
    Degenerate dimensionAn identifier with no attributes — an order numberUseful to group by, nothing to look up
    Conformed dimensionOne shared definition used by several factsCan two facts be compared on it?

    Dividing by the average works only when nothing is correlated

    When line count is independent of order size, the inflation is the average line count — 3.493 against 3.486 — so dividing by it works to within 0.2%.

    When bigger orders have more lines, which is nearly always true, the inflation is 6.631 against an average of 4.163. Dividing by the average still leaves you 59.3% high, and the residual is concentrated in exactly the large orders anyone would look at.

    So the correction is not merely approximate. It is worst where the numbers matter most.

    Two measures on one table need two different corrections

    On the same joined rows, the shipping fee inflates by 4.16 rather than 6.63, because it does not correlate with line count. One correction factor cannot fix both columns.

    That is the point at which correcting stops being sensible. Aggregating to order grain before joining recovers £10,087,643 and £324,817 exactly — both measures, one fix, no factors to remember.

    How to catch it in thirty seconds

    Count the rows before and after every join. If the count changed and you did not intend it to, a measure somewhere is now wrong. This is the single highest-value habit in analytical SQL and it costs one extra line.

    The other tell is a total that is suspiciously round-numbered against expectation — 6.6 times budget rather than 1.1 times. Fan-outs produce implausible numbers, which is fortunate; the dangerous version is a fan-out of 1.02 on a rarely-multi-row dimension, which just looks like a good week.

    Semi-additive means the rule changes with the dimension

    Stock on hand is perfectly fine summed across stores and nonsense summed across time: 5,170 against a real 1,293, inflated by exactly the four periods in the window.

    So one measure needs a different aggregation rule per dimension. No tool can infer that from the data, which means a default SUM is silently wrong roughly half the time it is applied to a balance, a headcount, a level, or an inventory position.

    How the average-of-averages error behaves

    It saturates, and the ceiling is set by the rates rather than the sizes

    The error is zero when every group is the same size, rises steeply, and then saturates at 27%. At a hundred-thousand-fold disparity it is still 27.4%.

    That ceiling is not set by how unequal the stores are — it is set by how far apart their rates are. Which is worth knowing, because it means the damage is bounded but the bound can still be enormous when your segments genuinely behave differently.

    The practical reading: "average the rates" is safe exactly when nobody needed to segment in the first place, and wrong precisely when segmentation matters.

    The rule that follows

    Store the numerator and the denominator as additive facts, and compute the ratio at query time. Then every roll-up is correct by construction at every grain, and chapter 3's guardrail comes free — the numerator is already on the page because the model requires it.

    A stored conversion_rate column is a measure that can only be aggregated correctly by someone who already knows the answer.

    PRACTICE

    Choosing a grain

  1. Go as fine as the source allows. You can always aggregate up; you can never recover detail you threw away. The exception is genuine volume, and it is rarer than people assume.
  2. Write the grain sentence in the model, in a comment, at the top. It costs nothing and it is the thing every future reader needs first.
  3. One grain per table. Header totals and line totals in the same table guarantees the first demo's problem.
  4. Add a count column of 1. Then row counts survive aggregation and a fan-out becomes visible as a count that no longer matches.
  5. Test the grain with a uniqueness check. If the declared grain is one row per order line, assert that order_id plus line_number is unique. This catches duplicate-source problems before they reach a number.
  6. Name the aggregation rule for every measure, per dimension, where it is not plain sum. Chapter 7 is about somewhere to put that.

    7. JUDGEMENT

    Five questions about a fact table

  7. Can you state the grain in one sentence? If it takes two, there are probably two tables.
  8. Is the declared grain actually unique? One assertion, and it catches the whole class.
  9. Do row counts change across your joins? The thirty-second check that prevents a 6.63× error.
  10. Which measures are semi-additive? Balances, levels and headcounts all are, and a default sum will be wrong on them.
  11. Are any ratios stored as columns? Store the parts instead and compute at query time.
