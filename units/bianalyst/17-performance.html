    10 × 104 = 1,043, exactly

    Column pruning alone saves 10×, partition pruning alone 104×, and together exactly 1,043× — the product.

    They multiply because each cuts a different dimension of the same rectangle. Which means the order you apply them in does not matter, and neither does arguing about which is "the" optimisation. Do both.

    Which one wins depends entirely on the query

    Short window, wide selection: partitions win. Long window, narrow selection: columns win. Since you cannot know in advance which queries people will write, the useful habit is to do both rather than to reason about it.

    And note the floor: SELECT * costs 10× on this table whatever else you fix, because forty columns is forty columns.

    Defaults decide the compute bill as well as the question set

    A cache is worth nothing when every query is distinct and almost everything when they repeat. A dashboard with fixed defaults caches beautifully; one with a free-text date picker does not.

    Chapter 13 found that the default window decides which questions the dashboard can answer. It turns out to decide the bill too, and for the same reason — almost nobody changes a default, so a fixed default means five distinct queries rather than four hundred.

    The ratio is view-count independent

    Twelve seconds at forty views a day and twelve seconds at four views a day both give 652×. Both costs scale with the number of runs, so the view count cancels.

    What decides it is latency against cost per run. Which is worth knowing, because "it's only opened a few times a day" is the usual reason not to optimise something, and it is not a reason at all — it lowers both costs equally.

    Pruning moves you into the regime where compute stops mattering

    A pruned query balances at 0.02 seconds, so any human-visible latency is dominated by the wait. A full scan balances at 19.2 seconds — below that, the compute genuinely costs more than the waiting, and that is the only regime where optimising the bill is the right instinct.

    Which produces a tidy consequence I had not expected. The two optimisations are the same work. Prune properly and you have also moved yourself out of the regime where the bill was worth arguing about, so there is never a stage at which you have to choose between them.

    The rule the two costs imply

    Optimise interactive queries for latency and scheduled ones for compute, and never the other way round.

    A nightly job that takes four minutes is free. A dashboard that takes four minutes is abandoned, and chapter 1 measured what an unopened dashboard is worth: 103 of 200 never opened at all, contributing nothing but maintenance.

    PRACTICE

    What to do, in order

  1. Name the columns. SELECT * is a fixed 10× on a 40-column table, before anything else you might fix.
  2. Partition by the column people filter on, which is almost always the date. 104× on a seven-day window.
  3. Check the plan says the partitions were pruned. A function on the partition column — DATE(ts), a cast, a timezone conversion — silently disables it, and the query still returns the right answer.
  4. Pre-aggregate the daily grain for anything a dashboard reads. 300× on top of the rest, and it is the same rollup chapter 4 needed to fix the fan-out.
  5. Fix the defaults so the cache works. Five distinct queries hit 99%; four hundred hit zero.
  6. Resolve surrogate keys at load, per chapter 6 — it removes the 2.6× range-join penalty at query time.
  7. Keep the hot dimension under the broadcast limit, per chapter 5. That was a 4.2× cliff with no warning on it.
    8. The optimisation that is not one

    Adding indexes to a columnar warehouse. Columnar engines scan and prune; they do not seek. Time spent looking for the missing index is time not spent on the partition key, which is the thing that actually cuts the scan.

    The row-store instinct is strong and it is the wrong instinct here — the same mismatch chapter 5 found in the snowflake storage argument, which was also written for hardware that no longer applies.

    JUDGEMENT

    Five questions about a slow report

  8. How many columns does it actually need? The gap to 40 is your column-pruning multiple.
  9. Did the plan prune partitions? A function on the partition column silently disables it.
  10. Is a human waiting? If yes, latency dominates by hundreds of times.
  11. How many distinct queries does the dashboard generate? That is the cache hit rate.
  12. Would a daily rollup answer it? 300×, and it is a rollup you probably need anyway.
