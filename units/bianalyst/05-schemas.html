CHAPTER 5

Star against snowflake

Three extra joins onto tables of a few hundred rows cost 1.0%. Growing a single dimension from 8M to 9M rows costs 4.2 times more. Join count is nearly free; dimension size has a cliff in it — and the storage argument that started this debate has largely evaporated.

    What the argument is actually about

    Classic argument forFewer joins, faster queriesLess storage, one place to change
    Both classic arguments were formed on different hardware

    "Fewer joins is faster" comes from row-store engines where every join was a nested loop over disk pages. "Less storage" comes from an era before columnar dictionary encoding, when a repeated string was genuinely repeated on disk.

    Neither holds the way it used to. What replaces them is worth measuring rather than repeating, so the rest of this chapter measures both.

    The extra joins touch the dimension, not the fact

    With push-down the snowflake costs 1.0% more than the star, because the three additional joins run at dimension grain — 2M rows — rather than fact grain at 200M. The first join is 99.0% of the work and the other three together are 1.0%.

    Without push-down the identical schema costs 3.97 times as much, because every fact row is carried through each hop.

    So "how many joins" is the wrong question. The right one is whether the planner reorders them, and you answer that by reading the query plan rather than the schema diagram.

    There is a cliff, and it is not where people look for it

    Growing a dimension from 8M to 9M rows costs 4.2 times more, because it stops fitting in memory and the join changes kind. Adding three whole extra joins to tables of a few hundred rows costs 1.0%.

    Join count is nearly free. Dimension size has a cliff in it, and the cliff arrives with no warning — the query was fine last quarter and the customer table has grown 15%.

    Which reframes the tuning question entirely. If a star-schema query is slow, the useful thing to check is whether the big dimension has crossed the broadcast threshold, not whether you can remove a join.

    STORAGE

    The argument that evaporated

    Columnar engines dictionary-encode repeated values, which is exactly what a denormalised dimension produces.

    A foreign key is a dictionary code

    The attributes people snowflake away are exactly the ones that compress best. Country name on every one of 2M rows costs 2.00 MB dictionary-encoded — which is the same as the foreign key that would replace it, because they are the same construct.

    Across the whole geography branch: 8.34 MB flattened against 4.21 MB normalised. That is a 2× ratio and a 4.14 MB absolute difference, beside a 200M-row fact table. The ratio sounds meaningful and the number does not.

    Note the last row too: an attribute with one distinct value per row does not compress — 53 MB against 48 raw, because the dictionary is as large as the column. Denormalising a high-cardinality attribute really does cost storage. It is only the low-cardinality ones, which is to say the ones anyone would think to snowflake, where the cost vanishes.

    What a change costs

    An update cost, not a storage cost

    Renaming one country touches one row in the snowflake and 10,204 in the star. That cost did not evaporate with columnar storage, and it is the one that should decide the shape.

    Which means the answer depends on how often your dimension attributes change, not on how large they are — the opposite of how the decision usually gets framed.

    There is a correctness dimension to it as well. Ten thousand copies of a value is ten thousand chances for a partial update, and a country that is renamed in 9,900 rows and not the other 304 produces two countries in a group-by. The snowflake makes that impossible by construction.

    The rule this leaves you with

    Attributes that change rarely and are read constantly belong flattened onto the dimension. Attributes that change often, or that several dimensions must agree on, belong in their own table.

    Not to save 4.14 MB — to have one row to change, and one authoritative value. That is a governance argument rather than a performance one, and it is the argument that survived.

    Chapter 6 takes the "changes often" case seriously, because what happens to last year's numbers when an attribute changes turns out to be a bigger question than where the column lives.

    PRACTICE

    What to actually do

  1. Default to a star, and snowflake by exception. The exceptions are frequently-changing attributes and dimensions several facts must share.
  2. Read the plan before optimising the schema. A snowflake that pushes down costs 1%; the same schema without push-down costs 4×, and only the plan tells you which you have.
  3. Watch your largest dimension against the broadcast threshold. That is where the cliff is, and it arrives silently as the table grows.
  4. Never snowflake a high-cardinality attribute for storage reasons. It is the one case where the storage argument still holds — and it is also the case where the extra join is least likely to be free.
  5. Offer a flattened view over a snowflaked model. The comprehension cost of four joins is real even when the compute cost is 1%, and a view removes it without changing the storage.
  6. Count the joins your analysts have to write, not the ones the engine runs. Those are different numbers, and only the first one causes mistakes.

    7. JUDGEMENT

    Five questions about a schema

  7. How large is your biggest dimension, against the broadcast limit? 8M to 9M was a 4.2× cost step.
  8. Does the plan push small joins to dimension grain? The difference is 1% against 4×.
  9. Which attributes change more than once a quarter? Those are the snowflake candidates.
  10. Is anything snowflaked purely to save space? Compute the dictionary-encoded size before defending it.
  11. How many joins does a typical analyst write for a common question? If it is four, a view is cheaper than a re-model.
