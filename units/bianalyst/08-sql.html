    The revenue is identical to the penny

    Only the customer count moved — from 200,000 to 124,440. Seventy-five thousand five hundred and sixty customers vanished, 38% of the base, and the number anyone would sanity-check did not change at all.

    That is why it survives review. A WHERE predicate on the right-hand table of a LEFT JOIN silently converts it to an inner join, because the unmatched rows have NULL there and NULL fails the test.

    And the rows lost are precisely the customers who bought nothing — the group the question named. The query answers a different question perfectly.

    Every derived metric inherits it, uniformly

    The numerator did not change and the denominator lost its zeroes, so every per-customer figure is out by about 60% — and consistently so across regions, which makes it look like a real level rather than an error.

    A ratio that is wrong in one segment invites investigation. A ratio that is wrong everywhere by the same amount just becomes what people believe the number is.

    The same with WHERE col IS NOT NULL inside176,019 rows
    COUNT(*)200,000

    Zero rows, and a 3.0% difference from one word

    NOT IN against a list containing NULL returns zero rows — not fewer rows, zero — because x NOT IN (…, NULL) is never true under three-valued logic. That one at least announces itself, since an empty result gets noticed.

    COUNT(region) skips NULLs and reads 3.0% lower. Plausible either way, and only wrong if you meant the other one.

    The ranking by danger is the inverse of the ranking by drama. The loudest bug is the safest; the WHERE-clause trap changes nothing anyone checks.

    Three habits that catch the whole class

    Count rows after every join — chapter 4's habit, and it catches fan-out and silent-inner-join alike.

    Put filters on the outer table in the JOIN condition, not WHERE. If a predicate mentions the right-hand table of a LEFT JOIN, it almost always belongs in ON.

    Use NOT EXISTS instead of NOT IN. It has no NULL pathology, and it usually plans the same or better.

    The unweighted mean is chapter 4's non-additive measure in a retention chart

    Cohort 4 was a paid push: 62,000 sign-ups against a normal month's 5,000, and it retains worse. The unweighted mean gives it the same vote as a 5,000-person cohort, so month 3 reads 47.9% against a true 38.4%.

    This is exactly chapter 4's finding — averaging rates across groups of different sizes — arriving in a place nobody thinks of as an aggregation problem. And it flatters you precisely when the biggest cohort behaves worst, which is precisely when you would want to know.

    "Active by now" reads 100% at every month

    Counting a user as retained at month 6 if they were active in any month up to 6 gives 100% against a true 14.5% — nearly seven times higher, and flat across the whole chart.

    Both are legitimate metrics. They are not the same metric, and the SQL for each differs by one word: MAX over the window rather than the value at month m. A retention curve that barely declines is almost always this, rather than an unusually sticky product.

    The error grows with the month index, which is the shape of a retention curve

    At month 11 only one cohort has reached it, so dividing by all twelve reads 0.5% against a true 10.5% — five per cent of the real figure.

    The curve does not decay that fast. The denominator is counting cohorts that simply have not had the chance yet, and because the shortfall grows with the month index, the resulting chart looks like a perfectly normal steep decay. Nothing about it invites suspicion.

    The fix is one line: exclude any cohort-month cell where the cohort had not yet reached that age at the time of the extract. Which means the extract date has to be a column somewhere, and it usually is not.

    TOOLS

    Window functions, briefly

    Running totals and moving averages
    SUM(x) OVER (PARTITION BY … ORDER BY …). The thing to be careful about is the frame: the default with ORDER BY is RANGE UNBOUNDED PRECEDING, which ties on equal values. If two rows share an order date, both get the same running total. Specify ROWS explicitly when you mean rows.
    Period comparison
    LAG(x, 12) OVER (ORDER BY month) is right only if every month is present. A missing month shifts the comparison silently by one, and a gap in a sparse series is common. Join to a date spine instead of trusting the sequence.
    Rank, dense_rank, row_number
    Three different answers to ties. ROW_NUMBER breaks them arbitrarily, which makes it non-deterministic unless the ordering is total — a common source of "the report changed and nothing changed".
    First and last value
    LAST_VALUE with a default frame gives you the current row, not the last one, which surprises everybody once. FIRST_VALUE with a descending order is usually clearer than fighting the frame.
    Filtered aggregates
    COUNT(*) FILTER (WHERE …) or SUM(CASE WHEN … THEN 1 ELSE 0 END). Prefer this to several self-joins; it reads better and it computes the whole set of segment counts in one pass.
    The date spine

    A table with one row per date, joined to everything. It fixes missing periods in LAG, makes zero-activity days appear as zeroes rather than absences, and turns "revenue by week" into a query that returns a row for the week the site was down.

    It is fifteen lines to build and it removes an entire category of quietly-wrong answers — the ones where a gap in the data becomes a gap in the chart and then a gap in someone's mental model.

    JUDGEMENT

    Five checks before you send a number

  1. Did the row count change across each join? The WHERE trap cost 38% of the base with no change to the total.
  2. Do the zeroes appear? If your "including customers with no orders" query returns no zero rows, it is not including them.
  3. Is any NOT IN pointed at a nullable column? That returns zero rows, always.
  4. Does your retention curve weight cohorts by size? The unweighted mean read 47.9% against 38.4%.
  5. Are immature cohorts excluded from the later months? Otherwise month 11 reads 0.5% of the truth.
