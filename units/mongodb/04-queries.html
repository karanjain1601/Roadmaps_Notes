Queries and projection

A query is a document describing what you want to match. Most of it is unsurprising — and the array matching rules are not, and they are the source of more MongoDB bugs than anything else in this unit.

find operators arrays projection

The basic shape

a query is a document
db.orders.find({ status: "paid" });                     // equality
db.orders.find({ status: "paid", total: { $gt: 100 } }); // AND, implicitly

db.orders.find(
  { status: "paid" },                        // filter
  { reference: 1, total: 1, _id: 0 }         // projection
).sort({ placedAt: -1 }).limit(20);

// Dot notation reaches into nested objects and arrays alike:
db.orders.find({ "customer.email": "amara@example.com" });
db.orders.find({ "items.sku": "TSH-001" });      // any element matches
db.orders.find({ "items.0.sku": "TSH-001" });    // the FIRST element

// findOne returns a document or null; find returns a cursor.
const one = await db.orders.findOne({ reference: "NW-8842" });

// The comparison to keep in mind: this is the SQL unit's WHERE clause with a
// different syntax, and mostly the same semantics — until arrays, where the
// semantics genuinely differ because SQL has no equivalent.

Arrays

Array matching, run against real documents Four queries that look equivalent and are not. This is the section to actually play with.

Dot notation matches across elements; $elemMatch matches within one

{"items.qty": {$gte: 2}, "items.sku": "MUG-114"} asks: does some element have a qty of 2 or more, and does some element have that sku? They do not have to be the same element. That is almost never what anyone means, it silently returns extra documents, and the bug survives testing because it is correct whenever the array has one element. $elemMatch is the version that asks for a single element satisfying every condition, and it is the right default whenever an array of objects has more than one condition on it.

the array rules, stated once
// Given: { tags: ["gift", "urgent"] }

{ tags: "gift" }                    // MATCHES — an array matches if ANY
                                    // element equals the value. This is the
                                    // rule that makes arrays pleasant.

{ tags: ["gift", "urgent"] }        // MATCHES — but as an EXACT array,
                                    // same elements, same ORDER
{ tags: ["urgent", "gift"] }        // does NOT match. Order matters here.

{ tags: { $all: ["gift", "urgent"] } }   // MATCHES — contains all of these,
                                         // order irrelevant, extras allowed

{ tags: { $size: 2 } }              // MATCHES — exactly two elements.
                                    // NOT INDEXABLE. If you need this, keep
                                    // a tagCount field and index that.

{ tags: { $ne: "gift" } }           // does NOT match — $ne on an array means
                                    // "no element equals this", which is
                                    // usually right but surprises people who
                                    // read it as "some element differs"

// And the one that catches everyone, on an array of OBJECTS:
{ "items.qty": 2, "items.sku": "X" }              // different elements OK
{ items: { $elemMatch: { qty: 2, sku: "X" } } }   // the SAME element

// Rule of thumb: one condition on an array field, dot notation is fine.
// Two or more conditions that must hold together, $elemMatch. Always.

Projection

fetch less, because you pay for what you transfer
db.orders.find({}, { reference: 1, total: 1 });        // these, plus _id
db.orders.find({}, { reference: 1, total: 1, _id: 0 }); // these only
db.orders.find({}, { internalNotes: 0 });               // everything except

// You cannot mix inclusion and exclusion, with ONE exception: _id may
// always be excluded alongside inclusions.
db.orders.find({}, { reference: 1, notes: 0 });   // ERROR

// Nested fields:
db.orders.find({}, { "customer.name": 1, _id: 0 });

// Array projection — return only the matching element(s):
db.orders.find(
  { "items.sku": "MUG-114" },
  { "items.$": 1 }                       // the FIRST matching element only
);
db.orders.find({}, { items: { $slice: 3 } });        // first three
db.orders.find({}, { items: { $slice: [10, 5] } });  // skip 10, take 5
db.orders.find(
  {},
  { items: { $elemMatch: { qty: { $gte: 2 } } } }    // first element matching
);

// Projection is not cosmetic. A document with a 200 KB description costs
// that much to read and transfer whether you display it or not, and it
// occupies that much cache. On a list endpoint returning 50 documents this
// is the difference between 10 KB and 10 MB per request.
A covered query never touches the documents at all

If every field a query needs — both in the filter and in the projection — is present in one index, MongoDB answers it from the index alone and never reads a document. That is dramatically faster, especially when the collection does not fit in memory. It requires excluding _id explicitly, since _id is returned by default and is not in most indexes. Chapter 8 shows how to confirm it in explain output — look for totalDocsExamined: 0, which is the signature.

Sorting

the 32 MB wall
db.orders.find({ status: "paid" }).sort({ placedAt: -1 }).limit(20);

// If no index supplies the sort order, MongoDB performs an in-memory sort —
// and it aborts at 32 MB:
//   QueryExceededMemoryLimitNoDiskUseAllowed
//
// The fix is an index that provides the sort, which means a COMPOUND index
// with the filter fields first and the sort field after (chapter 7's ESR):
db.orders.createIndex({ status: 1, placedAt: -1 });

// Direction matters for compound sorts. This index serves:
//   .sort({ status: 1, placedAt: -1 })      exactly
//   .sort({ status: -1, placedAt: 1 })      the exact reverse
// and NOT { status: 1, placedAt: 1 }, which needs its own index.

// Sorting is also not stable unless it is total. Two documents with the same
// placedAt can come back in either order, and the order can differ between
// runs — the same non-determinism as the SQL unit's chapter 2. Add a
// tiebreaker:
.sort({ placedAt: -1, _id: -1 })

Pagination

skip is wrong, for the same reason OFFSET is
// This gets slower on every page. To reach page 500, MongoDB walks and
// discards 10,000 documents before returning 20.
db.orders.find({}).sort({ placedAt: -1 }).skip(10000).limit(20);

// It is also INCORRECT under concurrent writes: a document inserted while
// the user is on page 3 shifts everything, so they see one item twice and
// miss another entirely.

// KEYSET pagination — constant time, and correct:
db.orders.find({
  status: "paid",
  $or: [
    { placedAt: { $lt: lastPlacedAt } },
    { placedAt: lastPlacedAt, _id: { $lt: lastId } }   // tiebreaker
  ]
}).sort({ placedAt: -1, _id: -1 }).limit(20);

// The index serves both the filter and the sort, so the query starts exactly
// where the last page ended and reads 20 documents. Page 500 costs the same
// as page 1.
//
// What you give up is jumping to an arbitrary page number, which almost no
// interface genuinely needs — infinite scroll and next/previous do not.
// This is the SQL unit's chapter 14 argument, unchanged.

Type comparison

what happens when a field holds two types
// BSON defines a total order ACROSS types, so a comparison never errors —
// it just compares by type first:
//
//   MinKey < Null < Numbers < String < Object < Array < Binary
//         < ObjectId < Boolean < Date < Timestamp < Regex < MaxKey

// So if a collection has both, this returns nothing surprising and
// nothing useful:
db.orders.find({ amount: { $gt: 100 } });
//   matches NumberDecimal("129.99") and NumberInt(150)
//   does NOT match the string "150" — strings sort after all numbers

// Numeric types DO compare with each other correctly: Int32, Int64, Double
// and Decimal128 are compared by value, not by type. That part is sane.

// Finding the drift, which every long-lived collection has:
db.orders.aggregate([
  { $group: { _id: { $type: "$amount" }, n: { $sum: 1 } } }
]);
//   { _id: "decimal", n: 41203 }
//   { _id: "string",  n: 87 }      <- the import from 2024
//   { _id: "double",  n: 12 }      <- someone in mongosh

// This query is worth running on any collection you inherit, for every field
// you rely on. Then add schema validation (chapter 1) so it cannot recur.
$ne, $nin and negation cannot use an index efficiently

An index is an ordered structure, so "everything equal to X" is a range lookup and "everything not equal to X" is everything else — which means scanning. The same applies to $nin, $not and most uses of $exists: false. When a negation is on a hot path, invert it: store a positive field you can match on, or use $in with the list of values you do want. This is the same SARGability argument as the SQL unit's chapter 12, and it costs just as much here.

Cursors

find returns a cursor, and it matters at scale
// Documents arrive in batches — 101 first, then up to 16 MB per batch.
// Nothing is fetched until you iterate.
const cursor = db.orders.find({ status: "paid" });
for await (const order of cursor) { … }        // streams, constant memory

await db.orders.find({ … }).toArray();          // loads EVERYTHING into
                                                // application memory
// toArray on an unbounded query is how a service runs out of memory.
// Always pair it with a limit, or iterate.

.batchSize(500)      // tune round trips against per-batch memory
.maxTimeMS(5000)     // give up rather than run forever. Use this on any
                     // query serving a user request
.hint({ status: 1 }) // force an index — for diagnosis (chapter 8), not
                     // as a permanent fix
.allowDiskUse()      // permit sorts larger than 32 MB to spill

// Idle cursors time out after 10 minutes. A long-running export that pauses
// between batches will fail with CursorNotFound — either process faster,
// or paginate with keyset instead of holding a cursor open.

Counting

three functions, and only one is usually right
db.orders.countDocuments({ status: "paid" });
//   Accurate. Runs the query and counts. Costs what the query costs.

db.orders.estimatedDocumentCount();
//   Instant — reads collection metadata. NO FILTER possible, and it can be
//   wrong after an unclean shutdown. Fine for "roughly how many documents".

db.orders.count();
//   Deprecated. Behaviour differed between the two above depending on
//   arguments, which is exactly why it was deprecated. Do not use it.

// The pattern from the SQL unit's chapter 14 applies unchanged: an exact
// count of a large filtered set is expensive and usually unnecessary.
// "Showing 20 of many" is cheaper and no worse for the user than
// "Showing 20 of 4,127,338".
//
// If you genuinely need the number on a hot path, maintain it (chapter 3's
// computed pattern) rather than counting on every request.

The short version

  1. A query is a document. Multiple fields are an implicit AND.
  2. Dot notation matches across array elements; $elemMatch matches within one. Two or more conditions on an array of objects always want $elemMatch.
  3. {tags: ["a","b"]} is an exact, ordered match. $all is the containment version.
  4. $size cannot be indexed. Keep a count field.
  5. Projection is not cosmetic — you pay to read and transfer everything you do not exclude.
  6. A covered query reads no documents at all. It needs _id: 0.
  7. skip is wrong for pagination, on performance and on correctness. Use keyset.
  8. Negation cannot use an index. Invert to a positive match on hot paths.
