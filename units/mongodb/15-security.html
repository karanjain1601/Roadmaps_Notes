Security

MongoDB's security reputation was earned by a default that no longer exists: for years a fresh install listened on all interfaces with no authentication. Tens of thousands of databases were found and ransomed. The default changed; the habits it created are still in circulation.

authentication rbac injection encryption

The history, because it matters

What actually happened

Before MongoDB 3.6, mongod bound to 0.0.0.0 by default and access control was off unless you turned it on. Anyone who started a server and did not read the security page had an open database on the internet, and from 2017 onwards automated scanners found them at scale — tens of thousands of databases were wiped and held for ransom. MongoDB 3.6 changed the default bind to localhost, and modern packages and Atlas require authentication. The remaining risk is not the default any more; it is a Docker image, a Helm chart, a tutorial or a development compose file written in the old style and carried into production. Check bindIp and security.authorization on every deployment you inherit.

mongod.conf — the four lines that matter
net:
  bindIp: 127.0.0.1,10.0.1.15      # never 0.0.0.0 on a reachable network
  port: 27017
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongodb.pem
    CAFile: /etc/ssl/ca.pem

security:
  authorization: enabled            # OFF by default in a bare mongod
  keyFile: /etc/mongo/keyfile       # members authenticate to each other

setParameter:
  authenticationMechanisms: SCRAM-SHA-256

# Then, on the client, the setting people get wrong:
#   mongodb://…/?tls=true                          encrypted, NOT verified
#   mongodb://…/?tls=true&tlsCAFile=/etc/ca.pem    verified   ← this
#
# tlsAllowInvalidCertificates and tlsAllowInvalidHostnames exist for
# development and turn verification off entirely. Finding either in a
# production connection string means the TLS is decorative.

Roles

Least privilege, by consumer Pick who is connecting. The role, the reasoning, and what it deliberately cannot do.
—role
—scope
—cannot
built-in roles, and a custom one
// Per database:  read, readWrite, dbAdmin, dbOwner, userAdmin
// Cluster-wide:  clusterMonitor, clusterManager, hostManager, backup, restore
// All databases: readAnyDatabase, readWriteAnyDatabase, dbAdminAnyDatabase
// Superuser:     root  — should belong to nobody in normal operation

use admin;
db.createUser({
  user: "orders-api",
  pwd: passwordPrompt(),                    // never a literal in a script
  roles: [{ role: "readWrite", db: "shop" }]
});

// Custom roles are where least privilege actually happens — restricted to
// specific collections and specific actions:
db.createRole({
  role: "ordersWriter",
  privileges: [
    { resource: { db: "shop", collection: "orders" },
      actions: ["find", "insert", "update"] },      // note: no "remove"
    { resource: { db: "shop", collection: "customers" },
      actions: ["find"] }
  ],
  roles: []
});

db.getUser("orders-api");
db.getRole("ordersWriter", { showPrivileges: true });

// The pattern from the PostgreSQL unit applies unchanged: the application
// role should not be able to change the schema. readWrite includes
// createCollection, createIndex and dropCollection — so an application
// running as readWrite CAN drop your collections. A custom role restricted
// to find/insert/update/remove is the version that cannot.

Injection

no string concatenation, and still injectable
// Queries are documents, not strings, so classic SQL injection does not
// apply. A different version does.

// THE OPERATOR INJECTION. A JSON body posts:
//     { "username": "admin", "password": { "$ne": null } }
// and this authenticates as admin:
await users.findOne({ username: body.username, password: body.password });
//     -> { username: "admin", password: { $ne: null } }
// which matches, because the stored hash is not null.

// The fix is to constrain types at the boundary, before the value ever
// reaches a query:
if (typeof body.password !== "string") throw new BadRequest();
// or a schema validator — zod, joi, ajv — on every request body.
// Most frameworks and ODMs cast to the declared type, which handles this;
// raw driver code does not.

// THE $where / $function INJECTION — arbitrary JavaScript on the server:
db.users.find({ $where: `this.name === '${input}'` });    // NEVER
// Disable server-side JavaScript entirely unless you have a specific need:
//   security.javascriptEnabled: false
// It also blocks $accumulator, $function and mapReduce, which is usually fine.

// AGGREGATION PIPELINE INJECTION — a user-supplied pipeline stage can read
// other collections with $lookup, or write with $merge:
db.orders.aggregate(JSON.parse(req.query.pipeline));      // NEVER

// REGEX DENIAL OF SERVICE — a crafted pattern that backtracks catastrophically:
db.users.find({ name: { $regex: userInput } });
// Escape it, or constrain the pattern shape. Never pass raw user input
// as a regex.

// The general rule: NEVER let user input decide the SHAPE of a query.
// Values are fine once type-checked; field names, operators and pipeline
// stages must come from your code.
Operator injection is the one to test for

It is easy to miss because it does not look like injection — there is no quoting, no escaping, no string building, and the code reads as a normal query. Any endpoint that passes a request field straight into a filter is vulnerable if the field can arrive as an object rather than a string, which in JSON it always can. Test it directly: send {"$ne": null}, {"$gt": ""} and {"$regex": ".*"} where a string is expected and see what the endpoint does. Validating request body types is the single fix, and it belongs at the boundary rather than at each query.

client-side field level encryption
// The driver encrypts specific fields before they leave the application.
// The server stores and returns ciphertext and never holds the key — so a
// database compromise does not expose those fields.

const client = new MongoClient(uri, {
  autoEncryption: {
    keyVaultNamespace: "encryption.__keyVault",
    kmsProviders: { aws: { accessKeyId: …, secretAccessKey: … } },
    schemaMap: {
      "shop.patients": {
        bsonType: "object",
        properties: {
          nationalId: {
            encrypt: {
              bsonType: "string",
              algorithm: "AEAD_AES_256_CBC_HMAC_SHA_512-Deterministic"
            }
          }
        }
      }
    }
  }
});

//   Deterministic  — the same input gives the same ciphertext, so equality
//                    queries work. It also leaks equality: an attacker with
//                    the database can see which rows share a value, and
//                    frequency analysis applies to low-cardinality fields
//   Random         — no queries at all on that field, and no leakage
//
// QUERYABLE ENCRYPTION (6.0+, GA in 7.0) supports equality and range
// queries on encrypted fields with much better leakage properties than
// deterministic. Use it in preference where the driver supports it.

// The point worth being clear about: encryption at rest protects a stolen
// disk. It does nothing against anyone who can run a query — which is the
// threat most people are actually worried about. Only client-side
// encryption addresses that, and it costs queryability and key management.

A review checklist

  • security.authorization: enabled and bindIp not 0.0.0.0 — check on every deployment, especially containerised ones.
  • TLS with certificate verification, and no tlsAllowInvalidCertificates in any production connection string.
  • SCRAM-SHA-256, not SCRAM-SHA-1. X.509 or a cloud IAM mechanism where available.
  • A keyFile or X.509 for internal authentication between replica set members.
  • No root in normal operation. Per-service users with the narrowest role that works.
  • The application cannot change the schema — a custom role, not readWrite.
  • Request body types validated at the boundary, so an operator cannot arrive where a string is expected.
  • javascriptEnabled: false unless something genuinely needs it.
  • The database is on a private network with a default-deny firewall. Access control is the last line, not the first.
  • Backups encrypted and access-controlled separately — a backup is a full copy of everything.
The two most common findings on an inherited cluster

Everything connects as the same user, usually one with readWriteAnyDatabase or root, because that is what the first tutorial did and nothing ever forced a change. Every service, every script and every developer therefore shares one credential with full access, and rotating it means coordinating every consumer at once — which is why nobody does. And the connection string is in an environment variable in a repository, or in a Kubernetes ConfigMap rather than a Secret. Neither is a MongoDB flaw and both are worth checking first, because they are the ones that turn a minor compromise into a total one.

The short version

  1. The insecure default was fixed in 3.6. The risk now is a container image or chart written in the old style.
  2. Check bindIp and security.authorization on every deployment you inherit.
  3. TLS without tlsCAFile is encryption without verification — the same trap as sslmode=require.
  4. Operator injection is real — {"$ne": null} where a string was expected. Validate request body types.
  5. Never let user input decide the shape of a query: no $where, no user-supplied pipelines, no raw regex.
  6. readWrite includes dropping collections. Use a custom role for the application.
  7. Encryption at rest protects a stolen disk and nothing against someone who can query. Only client-side encryption does that.
  8. One shared credential for everything is the most common finding, and the reason a small compromise becomes a total one.
