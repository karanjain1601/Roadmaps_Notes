The document model

Two things genuinely change when a row becomes a document: the unit of atomicity gets bigger, and the schema moves from the database into your application. Everything people say about MongoDB is downstream of those, and most of it is said imprecisely.

The two things that actually change

The unit of atomicity is the document, not the row. A single write to that order — adding an item, changing the status and updating the total together — is atomic with no transaction. In a relational schema the same change spans three tables and needs one. And the schema moves. It has not disappeared; every application reading that document assumes items is an array of objects with a sku. The database no longer enforces that assumption, so something else has to.

MongoDB does have schema validation, and most people never enable it
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["reference", "status", "amount", "placedAt"],
      properties: {
        reference: { bsonType: "string", pattern: "^NW-[0-9]{4}$" },
        status:    { enum: ["pending", "paid", "shipped", "cancelled"] },
        amount:    { bsonType: "decimal", minimum: 0 },
        placedAt:  { bsonType: "date" },
        items: {
          bsonType: "array",
          minItems: 1,
          items: {
            bsonType: "object",
            required: ["sku", "qty"],
            properties: {
              sku: { bsonType: "string" },
              qty: { bsonType: "int", minimum: 1 }
            }
          }
        }
      }
    }
  },
  validationLevel: "strict",      // or "moderate": only validate documents
                                  // that already pass, so existing bad data
                                  // is left alone
  validationAction: "error"       // or "warn": log it and accept the write
});

// Adding it to an existing collection:
db.runCommand({ collMod: "orders", validator: { … }, validationLevel: "moderate" });

// This is the closest thing to the SQL unit's chapter 11, and it is genuinely
// useful. It is also opt-in and off by default, which is why so many MongoDB
// collections contain three spellings of the same status value.
Flexibility is a loan

Not having to declare a schema up front is a real advantage during early development — you change the shape of a document by writing a different one. The cost arrives later: a collection that has accumulated four document shapes over three years, where every read path has to handle all four, nobody knows which are still in use, and there is no information_schema to ask. The flexibility is borrowed against future clarity, and the interest is paid by whoever maintains the code in year three. Chapter 17 is about repaying it deliberately; enabling validation early is how you borrow less.

two type traps worth knowing on day one
// 1. The shell stores every bare number as a Double.
db.orders.insertOne({ amount: 129.99 });          // Double — do not do this
db.orders.insertOne({ amount: NumberDecimal("129.99") });   // correct
db.orders.insertOne({ qty: NumberInt(3) });                 // not 3.0

// Drivers differ: most language drivers map an integer to Int32 or Int64
// correctly, so this is mainly a shell and mongosh hazard. It is also how
// collections end up with the same field stored as three different types.

// 2. Missing and null are DIFFERENT, and this catches everyone.
db.orders.find({ discount: null });
//   matches documents where discount IS null
//   AND documents where discount DOES NOT EXIST

db.orders.find({ discount: { $exists: false } });     // only missing
db.orders.find({ discount: { $type: "null" } });      // only actually null

// Three states, not two: has a value, is null, is absent. Decide which you
// mean and be consistent — the SQL unit's chapter 3 argument, with an extra
// state to get wrong.

_id

every document has one, and you can choose it
// If you do not supply _id, the driver generates an ObjectId client-side.
// It is unique, roughly time-ordered, and it is always indexed — the _id
// index is the one index you cannot drop.

// ObjectId encodes its creation time, which is occasionally useful:
ObjectId("65f1a2b3c4d5e6f7a8b9c0d1").getTimestamp();

// You can use your own value, and sometimes should:
db.users.insertOne({ _id: "amara@example.com", name: "Amara" });
db.daily.insertOne({ _id: { device: "d-41", day: "2026-03-14" }, … });

// A natural _id gives you free uniqueness on that value and saves an index.
// The catch is the same as the SQL unit's chapter 4: _id is IMMUTABLE. If
// the natural key can ever change, you cannot update it — you delete and
// reinsert, and anything referencing it breaks.
//
// The usual right answer is the same as in relational: a surrogate _id, plus
// a unique index on the natural key.
db.users.createIndex({ email: 1 }, { unique: true });

// One sharding note now, because it is irreversible later (chapter 13):
// ObjectIds are monotonically increasing, so if you shard on _id every insert
// goes to the same shard. Use a hashed shard key, or a different field.

The 16 MB document limit is a design constraint, not a technicality

It sounds generous and it decides your schema. Any array that grows without bound — comments on a post, events for a device, line items on a subscription that runs for years — will eventually hit it, and the failure arrives as a write error on one unlucky document long after the design was settled. The limit exists deliberately: a document is the unit of atomicity and the unit of transfer, so unbounded documents would mean unbounded write amplification and network transfer. Every unbounded array is a modelling bug, and chapters 2 and 3 are largely about noticing them early.

The storage engine

WiredTiger, briefly — it explains several later chapters
// WiredTiger is the default and only supported engine since MongoDB 4.2.
// The parts that surface elsewhere in this unit:
//
//   * DOCUMENT-LEVEL CONCURRENCY. Two writers touching different documents
//     in one collection do not block each other
//
//   * MVCC with snapshots, like the PostgreSQL unit's chapter 2 — readers do
//     not block writers. Unlike Postgres there is no vacuum to operate,
//     because old versions live in a cache and are discarded rather than
//     accumulating in the collection
//
//   * COMPRESSION by default. Snappy for data, prefix compression for
//     indexes. Typically 2-4x on real data, which changes the arithmetic
//     for how much fits in memory
//
//   * A CHECKPOINT every 60 seconds, plus a journal flushed every 100ms.
//     A crash loses at most ~100ms of writes at default settings, and the
//     journal is what bounds it (chapter 11)
//
//   * The CACHE, defaulting to 50% of RAM minus 1 GB. This is the number
//     that matters for performance, and chapter 9 is largely about it

What people get wrong about MongoDB

ClaimStatus
"It has no transactions"Out of date. Multi-document transactions since 4.0, sharded since 4.2 (chapter 12)
"It has no joins"Out of date. $lookup since 3.2 — with real limits (chapter 5)
"It loses writes by default"Out of date. The default has been w: majority since 5.0 (chapter 11)
"It has no schema"Misleading. The schema is in your application, and validation exists
"It cannot enforce constraints"Partly true. Unique indexes and validation yes; foreign keys no
"It is faster than SQL"Not a claim that means anything. It is faster at some access patterns and slower at others
"It is web scale"Sharding is real and the shard key decision is hard and nearly irreversible (chapter 13)
"You will regret it"Sometimes. Chapter 18 is about telling in advance
The version matters more than with most databases

MongoDB changed enormously between 3.x and 7.x, and much of the criticism that circulates describes the earlier ones accurately. Default write concern, transactions, joins, schema validation, sharded transactions, time-series collections and the query planner have all changed substantially. When you read advice about MongoDB — including strongly-worded advice — check which version it was written against. This unit targets MongoDB 7 and flags version-dependent behaviour where it matters.

The short version

  1. Two things change: the unit of atomicity is the document, and the schema moves into your application.
  2. "Schemaless" is wrong. The schema exists — the database just stopped enforcing it, unless you enable validation.
  3. Flexibility is borrowed against future clarity. Enable schema validation early to borrow less.
  4. Use Decimal128 for money, and beware the shell storing bare numbers as Double.
  5. Missing and null are different, and {field: null} matches both.
  6. _id is immutable and always indexed. Surrogate _id plus a unique index on the natural key is usually right.
  7. The 16 MB limit is a design constraint. Every unbounded array is a modelling bug.
  8. Most criticism of MongoDB describes version 3. Check what version the advice was written against.
