Replica sets

A group of servers holding the same data, one of which accepts writes. The election protocol is built in and it works — which is the single largest operational difference from the PostgreSQL unit, where the same capability required Patroni, etcd and a chapter of your attention.

The shape

three members, one primary
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "mongo-a:27017", priority: 2 },
    { _id: 1, host: "mongo-b:27017", priority: 1 },
    { _id: 2, host: "mongo-c:27017", priority: 1 }
  ]
});

rs.status();      // state of every member, election metrics, lag
rs.conf();        // the configuration
rs.hello();       // what THIS member thinks it is

// One PRIMARY accepts writes. SECONDARIES replicate from it and can serve
// reads if the client asks for them.
//
// Elections are majority-based, which is why the count should be ODD.
// Three members tolerate one failure; four also tolerate only one, and give
// you an extra machine to maintain for nothing.
//
// An ARBITER votes without holding data. It makes an even set odd cheaply
// and it is a trap — see below.

// The driver discovers the topology itself. Give it every host and it finds
// the primary, follows failovers, and reconnects:
//   mongodb://mongo-a,mongo-b,mongo-c/orders?replicaSet=rs0
// or a DNS seedlist, which is what Atlas provides:
//   mongodb+srv://cluster.example.mongodb.net/orders
The client is part of the failover mechanism

MongoDB drivers are topology-aware: they maintain a view of the replica set, monitor each member, and route writes to whichever node is currently primary. When the primary changes, the driver notices within seconds and follows — and with retryWrites on, which is the default, a single-document write interrupted by a failover is retried automatically against the new primary. That is why MongoDB failover feels seamless where PostgreSQL's needs HAProxy or a multi-host connection string configured deliberately. Give the driver every host and let it do this; a connection string pointing at one node defeats the entire arrangement.

Elections

What happens when something fails A three-member set. Pick a failure and see whether writes continue, and what it costs.

how an election is decided
// Members heartbeat every 2 seconds. If a secondary has not heard from the
// primary within electionTimeoutMillis (default 10s), it calls an election.
//
// To win, a candidate needs:
//   * a MAJORITY of votes from the configured members
//   * an oplog at least as recent as every voter's
//   * priority > 0
//
// The freshness requirement is the important one: a member that is behind
// cannot win, so a failover never promotes a node missing writes that
// another member has. That bounds data loss without any configuration.

cfg = rs.conf();
cfg.settings.electionTimeoutMillis = 10000;   // lower = faster failover,
                                              // more false positives
rs.reconfig(cfg);

// Per-member settings worth knowing:
{
  priority: 0,        // never becomes primary — for an analytics node or
                      // a member in a distant region
  votes: 0,           // participates without voting (max 7 voters total)
  hidden: true,       // invisible to clients; implies priority 0
  slaveDelay: 3600,   // secondaryDelaySecs in 5.0+ — deliberately behind
  buildIndexes: false // rarely a good idea
}

rs.stepDown(60);          // planned handover. Waits for a secondary to catch
                          // up, then steps down for 60 seconds
rs.freeze(120);           // this member will not seek election for 2 minutes
Do not use an arbiter

An arbiter votes without holding data, so it looks like a cheap way to make a two-member set electable. It is a trap. With a primary, a secondary and an arbiter, losing the secondary leaves a majority — so the primary stays up and now has no copy of your data anywhere else, and w: "majority" writes can be acknowledged by a single node. You have a set that reports healthy while running with no redundancy at all, which is worse than a two-member set that visibly steps down. The extra machine for a real third data-bearing member is cheaper than that failure mode. MongoDB's own guidance has moved to discouraging arbiters, and the reasoning is this.

The oplog

a capped collection every secondary tails
// The primary records every change in local.oplog.rs. Secondaries read it
// and apply the entries. It is the mechanism behind replication, change
// streams (chapter 14), point-in-time restore and initial sync.

use local;
db.oplog.rs.find().sort({ $natural: -1 }).limit(3);
//   { op: "u", ns: "shop.orders", ts: Timestamp(...),
//     o: { $v: 2, diff: { u: { status: "paid" } } },
//     o2: { _id: ObjectId("...") } }

// Operations are IDEMPOTENT by construction. An $inc in your application
// becomes an absolute $set in the oplog, so replaying an entry twice
// produces the same result — which is what makes recovery and resumption
// safe.

rs.printReplicationInfo();
//   "oplog first event time" and "last event time" — the difference is your
//   OPLOG WINDOW, and it is the number that matters operationally.

// THE WINDOW IS THE CONSTRAINT. A secondary offline longer than the window
// can no longer catch up: the entries it needs have been overwritten, and it
// requires a full resync — hours, and heavy load on the primary.
//
// The same window bounds how long a change stream can be disconnected before
// its resume token expires (chapter 14).

// Size it for the longest maintenance you might do, not for the average.
// 24-72 hours is a common target. It is a capped collection, so it costs
// disk and nothing else.
db.adminCommand({ replSetResizeOplog: 1, size: 51200 });   // MB, no restart

// Watch it, because write volume grows and the window shrinks silently:
db.getSiblingDB("local").oplog.rs.stats().maxSize;

db.orders.find({ … }).readPref("secondaryPreferred", [{ region: "eu" }]);
//   tags let you target specific members

// Constrain how stale you will accept:
.readPref("secondary", null, { maxStalenessSeconds: 90 });
//   the driver excludes members lagging more than this. Minimum 90s

// WHAT YOU GIVE UP:
//   * READ-YOUR-WRITES. A user saves, the redirect reads from a secondary,
//     and their change is not there. This is the commonest bug introduced by
//     enabling secondary reads, and it is intermittent
//   * every write still happens on every member, so a write-heavy workload
//     gains nothing — you are only offloading read CPU and cache
//   * during a failover, secondaries are also busy

// If you need read-your-writes AND secondary reads, causal consistency does
// it properly (chapter 11):
const session = client.startSession({ causalConsistency: true });
await coll.insertOne(doc, { session });
await coll.findOne({ _id }, { session });   // guaranteed to see the insert

// The honest summary is the same as the PostgreSQL unit's: secondary reads
// are for workloads that tolerate staleness and would otherwise evict your
// hot data from the primary's cache. They are not spare capacity.

Rollback

when a former primary has writes nobody else does
1. The primary accepts writes and acknowledges them with w: 1.
2. It fails before those writes reach any secondary.
3. A secondary is elected. It does not have them.
4. The old node returns and finds its oplog has diverged.

Those writes cannot be applied — the new primary's history is authoritative.
They are ROLLED BACK: written to a rollback file and removed.

  /rollback/./removed..bson

The application was told those writes succeeded. They no longer exist.
Nothing surfaces this to the application; the files sit on disk until
somebody looks. Since 4.4 they may go to a rollback collection instead,
which is more discoverable and no more automatic.

THE PREVENTION IS ONE SETTING. With w: "majority", a write is not
acknowledged until a majority has it — and any node that can win an election
must have everything the majority had. So an acknowledged write can never be
rolled back.

  w: "majority" has been the DEFAULT since MongoDB 5.0.

Which means: on a current version you are protected unless somebody
explicitly set w: 1 to make writes faster. That trade — a millisecond of
latency against silently losing acknowledged writes — is almost never worth
taking, and it is the single most consequential setting in chapter 11.

A delayed member is cheap insurance

secondaryDelaySecs: 3600 keeps one hidden member deliberately an hour behind. When someone runs a deleteMany with the wrong filter, or a migration corrupts a field, the correct data is on a running server you can query immediately — rather than at the end of a multi-hour restore. It costs one machine. It is not a backup and does not replace one; it is the fastest possible recovery from the specific, common failure of a human destroying data. Same argument as the PostgreSQL unit, and it is easier to set up here.

Monitoring

four things to watch
rs.printSecondaryReplicationInfo();     // per-member lag in seconds

// 1. REPLICATION LAG. Alert above a few seconds sustained.
db.adminCommand({ replSetGetStatus: 1 }).members.forEach(m =>
  print(m.name, m.stateStr, m.optimeDate));

// 2. OPLOG WINDOW. Alert below ~24 hours. It shrinks as write volume grows,
//    silently, and it is what bounds both resync and change-stream resume.
rs.printReplicationInfo();

// 3. ELECTIONS. Frequent elections mean network instability or an
//    overloaded primary, and each one is a brief write outage.
db.serverStatus().electionMetrics;

// 4. MEMBER STATE. Anything other than PRIMARY or SECONDARY needs attention:
//      RECOVERING   catching up, or unable to
//      STARTUP2     initial sync in progress
//      ROLLBACK     rolling back diverged writes — check for rollback files
//      DOWN         unreachable from this member's perspective

// A member stuck in RECOVERING is usually one that fell outside the oplog
// window and now needs a full resync. That is the failure the window
// setting exists to prevent, and it is much easier to prevent than to fix.

The short version

  1. Elections are built in and majority-based. Use an odd number of data-bearing members.
  2. The driver is part of the mechanism — give it every host and let it follow failovers.
  3. A candidate must be as fresh as every voter, so a failover never promotes a node missing writes others have.
  4. Do not use an arbiter. It produces a set that reports healthy while running with no redundancy.
  5. The oplog window is the operational constraint — it bounds resync and change-stream resume, and it shrinks silently.
  6. Secondary reads cost read-your-writes and are not spare capacity. Use causal consistency if you need both.
  7. Rollback discards acknowledged writes to a file nobody reads. w: "majority" prevents it, and is the default since 5.0.
  8. A delayed hidden member is one machine and the fastest recovery from a human deleting data.
