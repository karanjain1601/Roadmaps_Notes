Read and write concerns

Two per-operation dials that decide what "the write succeeded" and "this is the current value" actually mean. Most applications never touch them, which is fine — the defaults are now good. It stops being fine the moment somebody changes one to make something faster.

Write concern

what has to happen before you are told it worked
await coll.insertOne(doc, {
  writeConcern: { w: "majority", j: true, wtimeout: 5000 }
});

//   w          how many members must have it
//                1            the primary only
//                "majority"   a majority of voting members   ← DEFAULT (5.0+)
//                2, 3, …      a specific count
//                a tag name   e.g. "eu" for two members in Europe
//
//   j          must it be in the on-disk journal?
//                the default is true when w is "majority"
//
//   wtimeout   give up waiting after this. WITHOUT ONE, a write with
//              w: "majority" can block indefinitely if members are down

// Set it once on the client, override where it matters:
new MongoClient(uri, { writeConcern: { w: "majority", wtimeout: 5000 } });
await auditLog.insertOne(entry, { writeConcern: { w: 1 } });   // disposable
wtimeout is not a rollback

The subtlety that catches people: if wtimeout expires, the write has already been applied on the primary. You are told it timed out, and it may still replicate a moment later and become permanent. So a timeout means "I do not know", not "it did not happen" — the same ambiguity as a network failure. The correct response is to make the operation idempotent (chapter 6) and retry, not to assume failure and write something different. Treating a wtimeout as a rollback is how you get duplicates.

The default returns whatever the node has, including writes not yet replicated to a majority. If the primary then fails, those writes are rolled back (chapter 10) — so your application read a value, acted on it, and the value never existed as far as the surviving cluster is concerned. This is rare and it is not theoretical. For a read that gates a consequential action — checking a balance before a transfer, confirming a booking is still free — use readConcern: "majority", which by definition can only return data that cannot be rolled back. For a product listing, "local" is fine and faster.

Causal consistency

read-your-writes across nodes
// The problem: write to the primary, read from a secondary, and the write
// may not have arrived. The user saves a form and the next page does not
// show their change.

const session = client.startSession({ causalConsistency: true });   // default

await orders.insertOne(doc, { session });
const found = await orders.findOne({ _id: doc._id }, {
  session, readPreference: "secondaryPreferred"
});
// GUARANTEED to see the insert — the secondary waits until it has caught up
// to the session's cluster time before answering.

session.endSession();

// The guarantees a causally consistent session provides:
//   read your own writes
//   monotonic reads      — never see time go backwards
//   monotonic writes     — your writes apply in the order you issued them
//   writes follow reads  — a write after a read lands after what you read
//
// The mechanism is an operation time carried on every reply and sent with
// every subsequent request. The cost is that a read may WAIT for the
// secondary to catch up, so a lagging secondary makes your read slow rather
// than wrong — which is the right trade.
//
// To get the full guarantee the session also needs w: "majority" and
// readConcern: "majority". With weaker settings it is best-effort.

// The important practical note: sessions are PER LOGICAL USER FLOW, not per
// application. A single shared session across all requests serialises
// unrelated work and gives you nothing. Create one per request or per user
// interaction, and pass it to every operation in that flow.

What the defaults give you

and how they got there
// MongoDB 5.0 and later, out of the box:
//   writeConcern:    { w: "majority" }
//   readConcern:     "local"
//   readPreference:  primary
//   retryWrites:     true
//   retryReads:      true

// That combination means: acknowledged writes cannot be lost to a failover,
// reads come from the primary and are current, and transient network errors
// are retried automatically. It is a sensible default and it was not always
// the default — before 2.6 the default was effectively w: 0, and the
// reputation MongoDB acquired for losing data dates from that era.
//
// Anyone repeating that criticism today is describing a version from over a
// decade ago. Anyone who has explicitly set w: 1 has reintroduced it.

// Cluster-wide default, which overrides the driver's:
db.adminCommand({
  setDefaultRWConcern: 1,
  defaultWriteConcern: { w: "majority", wtimeout: 5000 },
  defaultReadConcern: { level: "local" }
});
db.adminCommand({ getDefaultRWConcern: 1 });

// Worth running getDefaultRWConcern on any cluster you inherit. A cluster
// default of w: 1 set years ago to fix a latency problem is invisible from
// the application code, and it silently reintroduces rollback.

The pattern: raise the concern for the small number of operations where being wrong is consequential, and leave everything else on the defaults. Applying linearizable everywhere is a performance decision disguised as a safety one.

Retryable writes

on by default, and worth understanding
// A network failure between the server applying a write and your driver
// receiving the acknowledgement is indistinguishable from the write never
// happening. Drivers retry — once — and MongoDB makes that safe.

// The mechanism: every retryable write carries a session id and a
// statement id. The server records which statement ids it has executed, so
// a retry of one it already ran returns the ORIGINAL result rather than
// applying it twice.

// What is retryable:
//   insertOne, updateOne, deleteOne, replaceOne, findAndModify
//   insertMany, bulkWrite (only if every operation is single-document)
//
// What is NOT:
//   updateMany, deleteMany — multi-document, so a partial application
//   cannot be safely resumed. These you must make idempotent yourself.

// This works alongside your own idempotency and does not replace it. The
// driver retries once, for one class of failure. An application-level retry
// after a longer outage has no such protection, which is why the
// construction matters (chapter 6):
//   a conditional filter that only matches once
//   a unique index on a client-supplied key
//   $set rather than $inc, $addToSet rather than $push

new MongoClient(uri, { retryWrites: true, retryReads: true });   // defaults
The cost of majority is smaller than it looks, and not zero

Within one datacentre, waiting for a second member typically adds a fraction of a millisecond — the members are close and the write is already going to disk. Across regions it is a round trip, and that changes the arithmetic completely: w: "majority" with a member on another continent adds that latency to every write. This is why multi-region deployments usually keep the majority within one region and treat the distant member as a disaster-recovery copy rather than a voting one. Measure it before assuming either that it is free or that it is expensive.

The short version

  1. Write concern is how many members must have it before you are told it worked. w: "majority" since 5.0.
  2. wtimeout is not a rollback — the write already applied on the primary and may still replicate. Retry idempotently.
  3. Always set wtimeout with w: "majority", or a write can block indefinitely.
  4. readConcern: "local" can return data that is later rolled back. Use "majority" for reads that gate a consequential action.
  5. Causal consistency gives read-your-writes on secondaries — one session per user flow, not per application.
  6. The current defaults are good. Check getDefaultRWConcern on any cluster you inherit.
  7. Retryable writes are on by default and cover one retry of single-document operations. Not updateMany.
  8. Raise the concern where being wrong is consequential, and leave the rest alone.
