Chapter 03 · Documents

Modelling for access patterns

Relational design starts from the entities and derives the queries. Document design goes the other way, and doing it in the wrong order is the single most reliable way to produce a MongoDB schema you will regret.

the inversion bucket computed subset

The inversion

Relational

  1. Identify the entities and their relationships
  2. Normalise until each fact lives in one place
  3. Write whatever queries you need
  4. Add indexes where they are slow

The schema is derived from the domain, and the query engine adapts. This works because joins are cheap and the optimiser is good.

Document

  1. List the operations the application performs
  2. Rank them by frequency and latency sensitivity
  3. Design documents so the top ones are single-document reads
  4. Accept duplication and computation on write to achieve that

The schema is derived from the workload. This works because a single-document read is very fast and a $lookup is not.

A normalised document schema gets the worst of both

The commonest way to fail with MongoDB is to design the relational schema and transliterate it — a collection per entity, ids between them, and $lookup wherever a join used to be. You now pay for joins that are less capable than SQL's, without foreign keys, without the optimiser's join reordering, and without the constraint system. If your document schema looks like your relational one, you have chosen the wrong database or done the wrong modelling. Chapter 18 is about telling which.

Doing it

the workload table, which is the actual deliverable
Before writing any schema, fill this in. It takes an hour and it decides
everything that follows.

  Operation                       Freq/sec   Latency   Reads or writes
  ------------------------------  ---------  --------  ----------------
  Show a product page                  400      50ms   read
  Add to basket                         40     100ms   write
  Show basket                          120      50ms   read
  Place an order                         4     500ms   write
  Show my order history                 20     200ms   read
  Warehouse: today's orders            0.1        5s   read
  Analytics: revenue by category      0.01       60s   read

Then, for each one:
  * which documents does it touch
  * what does it filter on, and what does it sort by
  * can it be one query against one collection

The top three by frequency should each be a single-document read or a single
indexed query. If they are not, the schema is wrong, and no amount of
indexing will fix it later.

Note the bottom two rows. They are rare and latency-tolerant, so they are
ALLOWED to be slow, complicated aggregations — and designing the schema
around them at the expense of the top rows is the classic mistake.
Designing from a workload Pick the dominant operation. The schema that serves it well is usually not the normalised one.

Bucket

the one that fixes time-series and unbounded arrays
// One document per reading: 8 million documents a day, each with its own
// _id index entry and per-document overhead. Queries over a day scan
// millions of documents.
{ device: "d-41", t: ISODate("2026-03-14T09:31:02Z"), temp: 21.4 }

// BUCKETED: one document per device per hour.
{
  device: "d-41",
  hour:   ISODate("2026-03-14T09:00:00Z"),
  count:  3600,
  min:    20.9, max: 22.1, sum: 76840.2,     // precomputed, for free
  samples: [ { s: 2, v: 21.4 }, { s: 3, v: 21.5 }, … ]   // second offsets
}

db.readings.updateOne(
  { device: "d-41", hour: hourStart },
  { $push: { samples: { s: secondOfHour, v: 21.4 } },
    $inc:  { count: 1, sum: 21.4 },
    $min:  { min: 21.4 }, $max: { max: 21.4 } },
  { upsert: true }
);

// 3600x fewer documents, 3600x fewer index entries, and the hourly rollup
// is already computed. The bucket is bounded by construction, so it never
// approaches 16 MB.
//
// Pick the bucket size so the document stays comfortably under a few hundred
// KB — per hour, per day, or a fixed count, whichever suits the rate.
//
// MongoDB 5.0+ has TIME-SERIES COLLECTIONS, which do this automatically with
// better compression. Use them for genuine time-series; the manual pattern
// is still the right answer for anything that is not (a chat thread, an
// audit trail, a feed).
db.createCollection("readings", {
  timeseries: { timeField: "t", metaField: "device", granularity: "seconds" },
  expireAfterSeconds: 7776000
});

Computed

pay on write, because reads outnumber writes
// Recomputing on every read: an aggregation over the comments collection,
// 400 times a second, for a number that changes twice an hour.
const count = await db.comments.countDocuments({ postId: id });

// Computed: maintained when the underlying data changes.
db.posts.updateOne({ _id: postId }, { $inc: { commentCount: 1 } });

// Now the listing page reads one document and has everything. The trade is
// that the count can drift if an update path is missed — so:
//   * do the increment in the SAME operation as the insert where possible
//   * or drive it from a change stream (chapter 14), which cannot be missed
//   * and run a periodic reconciliation job that recomputes and corrects
//
// The reconciliation job is the part people skip, and it is what makes this
// pattern safe rather than merely fast. Once a night, cheap, and it turns
// "the count is wrong and nobody knows why" into a fixed bug.

// APPROXIMATION, when even the increment is too much: update the counter
// only 1 time in 100, adding 100. The number is statistically close and the
// write load is 1% of what it was. Correct for view counts; not for money.
if (Math.random() < 0.01) {
  db.posts.updateOne({ _id: id }, { $inc: { views: 100 } });
}

Subset

the top N, embedded; the rest, referenced
// A product has 4,000 reviews. The page shows five, and almost nobody
// clicks through to the rest.
{
  _id: ObjectId("p1"),
  name: "Wireless keyboard",
  reviewCount: 4127,
  averageRating: 4.3,
  topReviews: [                        // maintained, bounded, embedded
    { by: "Amara", stars: 5, body: "…" },
    …                                  // five of them
  ]
}
// The full set lives in its own collection, fetched only if asked for.

// Maintaining the subset atomically:
db.products.updateOne({ _id: id }, {
  $push: {
    topReviews: { $each: [newReview], $sort: { helpful: -1 }, $slice: 5 }
  }
});
// $each + $sort + $slice keeps the best five in one atomic operation and
// discards the rest. This is the operator that makes the pattern practical.

Attribute

many optional fields, one index
// Products across categories have wildly different attributes. Indexing
// every possible field is impossible, and most are null on most documents.
{ _id: …, name: "…", screenSize: 15.6, ram: 16, weight: 1.4, isbn: null, … }

// ATTRIBUTE PATTERN: a single array of key/value pairs.
{
  _id: …, name: "Laptop",
  specs: [
    { k: "screenSize", v: 15.6 },
    { k: "ram", v: 16 },
    { k: "weight", v: 1.4 }
  ]
}
db.products.createIndex({ "specs.k": 1, "specs.v": 1 });   // ONE index, all fields

db.products.find({ specs: { $elemMatch: { k: "ram", v: { $gte: 16 } } } });

// Note this contradicts chapter 2's "arrays as maps" antipattern, and the
// distinction is the index. Use an object when the keys are KNOWN and few:
// specs.ram is simpler to read and query. Use this pattern when the keys are
// OPEN-ENDED and you need to index across all of them — which is exactly the
// case an object cannot serve, because you cannot index a field you do not
// know the name of.

Outlier

when 1% of your data breaks the design
// Almost every user has under 100 followers. A handful have 40 million.
// Designing for the celebrity ruins the common case; ignoring them breaks.

{ _id: ObjectId("u1"), name: "…", followers: [ … ] }               // normal
{ _id: ObjectId("u9"), name: "…", followers: [ … 1000 of them ],
  hasExtras: true }                                                // outlier

// The flag tells the application to check the overflow collection. 99% of
// reads take the fast path and never know the other one exists.
db.followerOverflow.find({ userId: ObjectId("u9") });

// The pattern is: OPTIMISE FOR THE COMMON CASE, and add an escape hatch for
// the tail rather than degrading everything to accommodate it. The cost is
// two code paths, and the flag is what keeps the second one cheap to check.

Denormalisation, deliberately

Every copy needs an owner and a reconciliation

These patterns all trade consistency for read speed, and that trade is only sound when someone has decided which write path owns each duplicated value and how it gets corrected when that path is missed. Write both down next to the field. A computed count with no reconciliation job is a number that will be wrong within a year and nobody will be able to say when it started — which is measurably worse than recomputing it on read, because at least that was slow and correct. The reconciliation job is not optional polish; it is what makes the pattern honest.

A method

1 · List every operation, with frequency and latency budgetThe workload table above. An hour's work, and it decides everything
↓
2 · Rank by frequency × latency sensitivityThe top three get designed for; the rest are allowed to be awkward
↓
3 · For each of the top three, aim for one querySingle document, or one indexed find. If you cannot, ask why
↓
4 · Apply the patterns to close the gapExtended reference, subset, computed, bucket
↓
5 · Check the writes still workEvery duplicated field is now a write-path obligation
↓
6 · Check the growthWhich arrays grow? What bounds them? Chapter 2
↓
7 · Write down the invariants and how they are maintainedIncluding the reconciliation jobs. This is the document that survives you
Design for the workload you have, not the one you might have

The mirror image of the earlier mistake: designing for a hypothetical future scale rather than the actual current workload. Bucketing a collection that receives forty documents a day, sharding at ten thousand documents, or building an outlier escape hatch for a tail that does not exist all add complexity for nothing — and the complexity is permanent while the imagined scale may never arrive. Model the workload you can measure, keep the schema simple enough to change, and apply the patterns when a specific number says to.

The short version

  1. Relational design derives queries from entities. Document design derives documents from queries.
  2. A normalised document schema gets the worst of both — all the joins, none of the constraints.
  3. Write the workload table first: operation, frequency, latency budget. It decides the schema.
  4. The top three operations should each be one query. Rare, latency-tolerant ones are allowed to be complicated.
  5. Bucket fixes time-series and unbounded arrays. Time-series collections do it automatically for genuine time-series.
  6. Computed pays on write because reads outnumber writes — and needs a reconciliation job to stay honest.
  7. Subset plus $push/$sort/$slice keeps a bounded hot list next to an unbounded cold one.
  8. Design for the workload you can measure, not the one you imagine.
