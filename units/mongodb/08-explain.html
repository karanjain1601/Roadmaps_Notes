Chapter 08 · Making it fast

Reading explain output

Three numbers answer nearly every performance question in MongoDB: keys examined, documents examined, and documents returned. The ratios between them tell you what is wrong, and the stage tree tells you where.

executionStats the ratios stages covered

The three numbers

always use executionStats
db.orders.find({ status: "paid" }).sort({ placedAt: -1 })
         .explain("executionStats");

//   "queryPlanner"        the chosen plan only. No numbers. Nearly useless
//   "executionStats"      RUNS the query and reports actuals   <- this one
//   "allPlansExecution"   plus what the rejected candidates did

// The numbers to read, in the executionStats block:
{
  nReturned:              20,      // documents the query produced
  totalKeysExamined:      20,      // index entries read
  totalDocsExamined:      20,      // documents fetched from disk or cache
  executionTimeMillis:    2,
  executionSuccess:       true
}

// An ideal query has all three EQUAL. Every index entry read led to a
// document, and every document was returned. Nothing was read and discarded.
//
// Note that explain("executionStats") actually executes the query — safe for
// a find, and worth thinking about for an update or a delete, where explain
// does NOT apply the write but does do the work of finding the documents.
Diagnosing from the ratios Six realistic outputs. The two ratios identify the problem before you read the stage tree.
—keys ÷ returned
—docs ÷ returned
—diagnosis
Two ratios, and each points at a different fix

keysExamined ÷ nReturned measures how well the index narrows things down. Above about 1 means the index is being scanned and filtered — the fields are wrong, or in the wrong order. docsExamined ÷ nReturned measures how much of the filtering happened after fetching documents. Above 1 means MongoDB read documents only to discard them, which is the expensive kind of wrong. Both at 1 is ideal; docsExamined: 0 is better still and means the query was covered.

The stage tree

read it inside out — children run first
LIMIT
  └── SORT                      ← a SORT stage means an in-memory sort
        └── FETCH               ← reading documents
              └── IXSCAN        ← reading the index

The stages you will see:

  COLLSCAN          reading every document. Fine on a tiny collection,
                    a bug on a large one
  IXSCAN            reading an index. Look at indexBounds to see how much
  FETCH             getting the document for an index entry. Its
                    "filter" field shows conditions applied AFTER the fetch
  SORT              an in-memory sort. 32 MB ceiling. Usually fixable with
                    an index (chapter 7's ESR)
  SORT_KEY_GENERATOR  always accompanies SORT
  LIMIT / SKIP      as expected
  PROJECTION_COVERED  the good one — answered from the index alone
  PROJECTION_SIMPLE / PROJECTION_DEFAULT  ordinary projections
  OR / SORT_MERGE   an $or served by several indexes
  AND_SORTED / AND_HASH   index intersection. Rarer than people expect
  SUBPLAN           an $or where each branch is planned separately
  EOF               the query provably matches nothing

The single most useful habit: find the FETCH stage and read its "filter".
Anything listed there is a condition that could not be answered by the index
and required the document. That is your index gap, named explicitly.

Covered queries

totalDocsExamined: 0
db.orders.createIndex({ status: 1, placedAt: -1, reference: 1 });

db.orders.find(
  { status: "paid" },
  { reference: 1, placedAt: 1, _id: 0 }      // _id: 0 is REQUIRED
).sort({ placedAt: -1 });

//   totalDocsExamined: 0
//   stage: PROJECTION_COVERED

// Every field the query needs — filter, sort and projection — is in the
// index, so MongoDB never touches a document. On a collection larger than
// memory this is the difference between an index page read and a random
// disk seek per result.

// The conditions:
//   * every filter field is in the index
//   * every projected field is in the index
//   * _id is explicitly excluded, unless _id is in the index
//   * the index is NOT multikey — an array index has one entry per element
//     and cannot reconstruct the original array
//   * on a sharded collection, the shard key fields must also be present

// The trade is index size: adding a field purely to cover a query makes
// every write to that field maintain a larger index. Worth it for a query
// running hundreds of times a second on a collection that does not fit in
// memory; not worth it otherwise.

Plan selection

MongoDB races the candidates, then caches the winner
// There is no cost model like PostgreSQL's. When several indexes could serve
// a query, MongoDB runs each candidate for a short trial period and picks
// whichever produces results fastest. The winning plan is then CACHED for
// that query shape.

db.orders.explain("allPlansExecution").find({ … });
//   rejectedPlans, each with its own executionStats — genuinely useful for
//   seeing why the index you expected was not chosen

db.orders.getPlanCache().list();
db.orders.getPlanCache().clear();      // after adding an index, or when
                                       // diagnosing a bad cached plan

// The cache is keyed by query SHAPE — the fields and operators, not the
// values. So { status: "paid" } and { status: "cancelled" } share a plan.
// If one value is 90% of the collection and another is 0.01%, the cached
// plan may suit one and not the other. This is parameter sniffing under a
// different name, and the symptom is a query that is fast for most inputs
// and inexplicably slow for a few.

// The cache is cleared automatically by: index changes, a restart, enough
// writes to the collection, or the plan performing much worse than at
// trial time.

// Force an index, for diagnosis only:
db.orders.find({ … }).hint({ status: 1, placedAt: -1 });
// A permanent hint freezes a decision that should adapt as data changes.
// Same argument as the PostgreSQL unit's chapter 7.
A fast query on a small collection tells you nothing

COLLSCAN on ten thousand documents takes a few milliseconds, so a missing index is invisible in development and in most test suites. The scan grows linearly and the indexed alternative barely grows at all, so the query that was fine at ten thousand documents is a serious problem at ten million — and it degrades gradually rather than breaking, which is why it is usually found by a user rather than by a test. Read explain against production-scale data, or at minimum treat any COLLSCAN on a collection that will grow as a defect regardless of how fast it currently runs.

Explaining an aggregation

what got rewritten, and where the index stopped helping
db.orders.explain("executionStats").aggregate([ … ]);

// The output shows the pipeline AS EXECUTED, which is not always what you
// wrote — the optimiser moves some $match stages earlier, merges adjacent
// $sort and $limit into a top-N, and pushes some $project stages down.
// Comparing your pipeline to the executed one is the fastest way to see
// whether the optimisation you were relying on actually happened.

// What to look for:
//   * the FIRST stage should be an IXSCAN, not a COLLSCAN
//   * "$cursor" holds the initial find, with its own executionStats
//   * a $lookup shows the plan used for EACH lookup — if it says COLLSCAN,
//     the foreign field is unindexed and you are doing one collection scan
//     per input document
//   * "usedDisk": true on a blocking stage means it exceeded 100 MB and
//     spilled — since 6.0 that happens silently instead of erroring

// Slow queries are also logged automatically, with these numbers attached:
db.setProfilingLevel(1, { slowms: 100 });
db.system.profile.find().sort({ ts: -1 }).limit(10);

//   level 0  off (the default; slow ops above 100ms still go to the log)
//   level 1  log operations slower than slowms
//   level 2  log EVERYTHING — for a short diagnostic window only
//
// The profiler writes to a capped collection in the same database, so it
// costs write throughput. Use level 1 with a sensible threshold, or read
// the ordinary log, which contains the same fields.

↓

↓

↓

Read the numbers before the tree

The stage tree is where attention naturally goes and it is the second thing to look at. The three numbers tell you whether there is a problem and which kind in about five seconds; the tree tells you where. Reversing the order means reading a plan carefully to discover it was fine, or getting absorbed in stage names when docsExamined: 2,400,000 and nReturned: 12 had already said everything. Numbers first, then the tree, then the fix.

The short version

  1. Always explain("executionStats"). queryPlanner has no actuals.
  2. Three numbers: nReturned, totalKeysExamined, totalDocsExamined. Equal is ideal.
  3. keys ÷ returned above 1 means the index is wrong or wrongly ordered.
  4. docs ÷ returned above 1 means filtering happened after fetching — the expensive kind.
  5. docsExamined: 0 is a covered query. It needs _id: 0 and a non-multikey index.
  6. The FETCH stage's filter names your index gap explicitly.
  7. Plans are cached by query shape, not by value — so one shape can be fast for most inputs and slow for a few.
  8. A fast query on a small collection tells you nothing. Treat COLLSCAN on a growing collection as a defect.
