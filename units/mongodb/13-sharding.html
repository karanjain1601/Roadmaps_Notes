Sharding

Splitting a collection across several replica sets, coordinated so it still behaves like one collection. The mechanism is sound and largely automatic. The shard key is a single decision that determines whether the result works, and it is the hardest thing to change afterwards in this unit.

shard key chunks targeting irreversible

Do not shard yet

Sharding is the last option, not the next one

It adds config servers, routers, a balancer, cross-shard query semantics, slower transactions, restricted unique indexes and an operational surface several times larger. Before reaching for it, exhaust the cheaper answers: a bigger machine (a single replica set on modern hardware handles a great deal), a smaller working set (chapter 9), archiving cold data, fixing the schema (chapters 2 and 3), and secondary reads for genuinely read-heavy analytics. Shard when you have a specific number saying you must — write throughput exceeding one primary, or a working set that cannot fit in the largest machine available — and not because the collection is large.

The pieces

what a sharded cluster is made of
//   mongos          the router. Stateless. Clients connect here.
//                   Run several, close to the application
//   config servers  a replica set holding the chunk map and metadata.
//                   Three members. Losing it is losing the cluster
//   shards          each one a full replica set holding a subset of the data

sh.enableSharding("shop");
sh.shardCollection("shop.orders", { customerId: 1, _id: 1 });
sh.status();

// A CHUNK is a contiguous range of shard key values. The balancer moves
// chunks between shards to keep them evenly distributed — automatically,
// in the background, one at a time.
//
// Since MongoDB 6.0 the balancer works on DATA SIZE rather than chunk
// COUNT, which is a meaningful improvement: it no longer treats a chunk
// holding 10 documents as equivalent to one holding a million. Advice
// written before 6.0 talks a lot about chunk splitting and jumbo chunks;
// most of that is now handled for you.

sh.getBalancerState();
sh.disableBalancing("shop.orders");    // during a bulk load, then re-enable
sh.startBalancer();

Choosing the key

Evaluate a shard key Four properties decide whether a key works. All four have to hold.
—verdict
—this query is
—shards touched
PropertyMeansFailure if missing
High cardinalityMany distinct valuesChunks cannot split. A value larger than a chunk is stuck on one shard
Low frequencyNo value dominatesOne shard holds a disproportionate share
Non-monotonicNot always increasingEvery insert lands on the same shard — a hot shard
Query-alignedYour common queries filter on itEvery query is scatter-gather across all shards
All four must hold. A key with three of them will produce a cluster that works badly in a way that is expensive to fix.
A monotonically increasing key gives you one hot shard

_id as an ObjectId, a timestamp, an auto-incrementing counter — all increase over time, so every new document has a key higher than the last, so every insert lands in the highest chunk, which lives on one shard. That shard takes 100% of the write load while the others idle, and the balancer spends its time migrating chunks away from it. You have added machines and made writes slower. Either hash the key, or lead the compound key with something that distributes — which is the single most common shard-key mistake and it is not visible until you are under load.

Targeted and scatter-gather

the distinction that decides everything
// Shard key: { customerId: 1, createdAt: 1 }

// TARGETED — mongos knows the shard key, so it routes to one shard.
db.orders.find({ customerId: 4821 });
db.orders.find({ customerId: 4821, createdAt: { $gte: d } });

// SCATTER-GATHER — no shard key in the filter, so every shard is queried
// and mongos merges the results.
db.orders.find({ status: "paid" });

// Scatter-gather is not automatically wrong. It is proportionally more
// expensive: latency becomes the SLOWEST shard's response, not the average,
// and total work is multiplied by the shard count. Occasional is fine; on
// the hot path it means the cluster does N times the work to serve the same
// query, which is the opposite of why you sharded.

db.orders.find({ … }).explain();
//   "shards": which were consulted
//   look for SHARD_MERGE and SINGLE_SHARD in the winning plan

// UPDATES AND DELETES are stricter. updateOne, deleteOne and findAndModify
// need either the shard key or _id in the filter — otherwise MongoDB cannot
// know which shard holds the single document to change. (Since 7.0 they can
// broadcast, and it is slower and worth avoiding.)
db.orders.updateOne({ _id: id }, { … });                    // fine
db.orders.updateOne({ customerId: 4821, _id: id }, { … });  // better

// SORTING across shards works — mongos merges sorted streams — but a sort
// on a field that is not the shard key requires every shard to sort its
// portion first.

Hashed sharding

even distribution, at a price
sh.shardCollection("shop.events", { deviceId: "hashed" });

// MongoDB hashes the value and shards on the hash, so distribution is even
// regardless of the underlying values. This solves the monotonic problem
// completely — sequential ids scatter perfectly.

// WHAT YOU LOSE:
//   * RANGE QUERIES on the shard key become scatter-gather. Adjacent values
//     hash to unrelated shards, so { createdAt: { $gte: d } } on a hashed
//     createdAt touches every shard
//   * zone sharding by value is not possible
//   * you cannot control locality at all

// So: hashed for point lookups on a high-cardinality field where you never
// range-query it. Ranged when locality matters and you can find a
// non-monotonic leading field.

// The compound middle ground, often the best answer:
sh.shardCollection("shop.orders", { customerId: 1, createdAt: 1 });
//   customerId distributes (many customers, no one dominant, not monotonic)
//   createdAt gives locality WITHIN a customer, so "this customer's recent
//   orders" is a targeted range read on one shard
//
// This is the shape to reach for first: a distributing field, then a
// locality field.

Changing the shard key

Since MongoDB 5.0 you can reshard a collection — sh.reshardCollection() — which rewrites the entire collection under a new key while it stays online. This is a genuine improvement over the previous answer, which was "dump, drop, recreate, restore". It is still a heavy operation: it needs disk for a second copy of the collection, takes hours to days at scale, and puts sustained load on every shard for the duration. From 8.0 there is also moveCollection and unsharding for collections that should never have been sharded. Treat all of these as recovery from a bad decision rather than as a reason to be casual about the original one.

Zones

pinning ranges to specific shards
// Data residency — EU customer data stays on EU hardware:
sh.addShardToZone("shard-eu-1", "EU");
sh.addShardToZone("shard-us-1", "US");
sh.updateZoneKeyRange("shop.orders",
  { country: "AT", customerId: MinKey },
  { country: "DE", customerId: MaxKey }, "EU");

// Requires the zone field to be the LEADING part of the shard key, which
// means this has to be designed in from the start.

// Tiered storage — recent data on fast shards, old data on cheap ones:
sh.updateZoneKeyRange("shop.events",
  { createdAt: ISODate("2020-01-01") },
  { createdAt: ISODate("2025-01-01") }, "archive");

// The obvious risk: a zone whose range receives most of the writes is a hot
// shard by design. Zones override the balancer, so it cannot fix an
// imbalance you have configured. Check that the ranges are roughly even in
// traffic and not just in value span.

Operating it

what to watch
sh.status();                                   // shards, chunks, zones
db.adminCommand({ balancerStatus: 1 });

// Distribution — the number that says whether the key is working:
db.orders.getShardDistribution();
//   per shard: document count, data size, average object size
//   a shard holding 60% of the data means the key is not distributing

// Are queries targeted?
db.adminCommand({ serverStatus: 1 }).shardingStatistics;
db.serverStatus().metrics.query;
//   compare targeted against scatter-gather rates over time

// Chunk migrations in progress:
use config;
db.changelog.find({ what: /moveChunk/ }).sort({ time: -1 }).limit(10);

// FOUR THINGS TO ALERT ON:
//   1. distribution skew  — one shard well above the average
//   2. scatter-gather rate rising  — a new query pattern with no shard key
//   3. balancer not running, or migrations constantly failing
//   4. config server replica set health — this is the single point whose
//      loss takes down the entire cluster, and it is easy to under-resource

// A mongos restart is harmless; a config server outage is not.

A decision procedure

1 · Confirm you need itA specific number: write throughput past one primary, or a working set past the biggest machine
↓
2 · List the queries, with frequencyChapter 3's workload table. The shard key must serve the top ones
↓
3 · Find a field the hot queries filter onIf none exists, everything will be scatter-gather and sharding will not help
↓
4 · Check all four propertiesCardinality, frequency, monotonicity, alignment
↓
5 · Add a locality field if usefulDistributing field first, then the range field
↓
6 · Check every unique indexEach must contain the shard key. This has killed candidate keys late
↓
7 · Test with real data volumesDistribution skew and hot shards are invisible at small scale
If no field serves the hot queries, sharding will not help

This is the finding worth reaching before the migration rather than after. Sharding improves throughput by letting queries hit one shard instead of all of them; if your access patterns have no common field to route on, every query becomes scatter-gather and the cluster does N times the work for the same result — with more latency, because you now wait for the slowest shard. Adding machines makes it worse. The honest conclusion in that case is that the workload needs a different data model, a different partitioning strategy, or a different database (chapter 18).

The short version

  1. Shard last. A bigger machine, a smaller working set and a better schema are all cheaper.
  2. The shard key needs all four properties: high cardinality, low frequency, non-monotonic, query-aligned.
  3. A monotonic key gives you one hot shard taking every write. The commonest mistake, invisible until load.
  4. Targeted queries include the shard key; everything else is scatter-gather across every shard.
  5. Hashed distributes perfectly and destroys range queries. A compound key — distributing field, then locality field — is usually better.
  6. Every unique index must contain the shard key. Check this before committing.
  7. Resharding exists since 5.0 and is a heavy recovery operation, not a licence to be casual.
  8. If no field serves the hot queries, sharding will not help — it will make things worse.
