Schema evolution

There is no ALTER TABLE, and it is a mixed blessing. Adding a field is free and needs no migration at all; the flexibility that makes it free is the same flexibility that lets four document shapes accumulate in one collection with no record of which are still in use.

versioning lazy migration backfill validation

The two halves of the trade

Genuinely free

  • Adding a field — write it on new documents, handle its absence on read
  • Adding a nested object or array — same
  • Widening a type — nothing enforces the old one
  • No table lock, no long-running DDL, no maintenance window

Still work

  • Renaming — every document, and every read path
  • Changing a type — every document, and comparisons break in between
  • Splitting or merging documents — a real migration
  • Removing a field — safely, only once nothing reads it
  • Knowing what shapes exist — no information_schema
The absence of a migration is not the absence of a change

In a relational database a schema change is a visible, reviewable, versioned artefact: a migration file, in the repository, applied in order. In MongoDB, adding a field is a code change in one service — no artefact, no review of the data implications, no record. That is convenient right up to the point where nobody can say which shapes exist in a collection or which code still reads the old one. Keep a migration directory anyway, even when the migration is a comment saying "v3 adds shippingTier, no backfill needed". The value is the record, not the mechanism.

Schema versioning

a version field, and the discipline it enables
// Stamp every document with the shape it uses.
{ _id: …, schemaVersion: 3, name: "Amara", contact: { email: …, phone: … } }

// The read path handles the versions that exist:
function normalise(doc) {
  switch (doc.schemaVersion ?? 1) {
    case 1: doc = { ...doc, contact: { email: doc.email } };  // v1 had a
                                                              // flat email
    case 2: doc.contact.phone ??= null;                       // v2 lacked
                                                              // phone
    case 3: break;
  }
  return doc;
}
// Note the deliberate fall-through: a v1 document is upgraded through every
// step to the current shape.

// Without a version field, the read path becomes a pile of defensive checks
// — doc.contact?.email ?? doc.email ?? doc.emailAddress — that nobody can
// ever safely delete, because nobody knows whether the shape it handles
// still exists in the collection.

// The version field makes that knowable:
db.users.aggregate([
  { $group: { _id: { $ifNull: ["$schemaVersion", 1] }, n: { $sum: 1 } } },
  { $sort: { _id: 1 } }
]);
//   { _id: 1, n: 412 }     <- 412 documents still on v1
//   { _id: 3, n: 8412903 }
//
// When the count for a version reaches zero, you can delete that branch of
// the read path with confidence. That is the whole point, and it is the
// thing an unversioned collection can never give you.

Lazy migration

upgrade documents as they are touched
// Migrate on read, when a document is loaded anyway:
async function getUser(id) {
  const doc = await users.findOne({ _id: id });
  if ((doc.schemaVersion ?? 1) < 3) {
    const upgraded = normalise(doc);
    await users.replaceOne({ _id: id, schemaVersion: doc.schemaVersion },
                           upgraded);         // guarded, so concurrent
    return upgraded;                          // upgrades do not fight
  }
  return doc;
}

// WHAT IT BUYS: no bulk write, no load spike, and hot documents migrate
// almost immediately because they are the ones being read.
//
// WHAT IT COSTS: the migration never finishes on its own. Cold documents
// stay on the old shape indefinitely, so the read path can never be
// simplified — which is the outcome the version field was supposed to
// prevent.

// The combination that actually works:
//   1. deploy readers that handle both shapes
//   2. write the new shape for all new documents
//   3. lazy-migrate on read, so hot documents convert for free
//   4. run a BACKGROUND BACKFILL for the cold tail
//   5. wait until the version count hits zero
//   6. delete the old branch of the read path
//
// Step 4 is the one people skip, and skipping it means step 6 never happens.

Backfills

resumable, throttled, verifiable
// Never a single updateMany across ten million documents. It generates an
// enormous amount of oplog at once, floods replication, and cannot be
// stopped or resumed.

async function backfill() {
  let lastId = await state.get("backfill:users") ?? MinKey;

  while (true) {
    const batch = await users.find(
      { _id: { $gt: lastId }, schemaVersion: { $lt: 3 } }
    ).sort({ _id: 1 }).limit(1000).toArray();
    if (batch.length === 0) break;

    await users.bulkWrite(batch.map(doc => ({
      updateOne: {
        filter: { _id: doc._id, schemaVersion: doc.schemaVersion },  // guard
        update: { $set: toV3(doc) }
      }
    })), { ordered: false });

    lastId = batch[batch.length - 1]._id;
    await state.set("backfill:users", lastId);      // resumable
    await sleep(50);                                 // throttled
  }
}

// The five properties that matter:
//   RESUMABLE   — progress persisted, so a crash costs one batch
//   IDEMPOTENT  — the schemaVersion filter means a rerun is a no-op
//   THROTTLED   — a pause between batches so replication keeps up
//   OBSERVABLE  — log progress; a silent 6-hour job is unmanageable
//   VERIFIABLE  — the version histogram tells you when it is done
//
// Watch replication lag WHILE it runs (chapter 16). If it climbs, increase
// the sleep. A backfill that puts secondaries an hour behind has turned a
// maintenance task into an availability problem.
//
// An update pipeline computes new values from old ones, server-side, with
// no round trip per document:
db.users.updateMany({ schemaVersion: { $lt: 3 } }, [
  { $set: { contact: { email: "$email" }, schemaVersion: 3 } },
  { $unset: "email" }
]);
// Still batch it — the pipeline form does not change the oplog volume.
Deploy readers before writers, always

The ordering rule that makes online migration safe. First deploy code that can read both the old and the new shape, and wait for it to be everywhere. Then deploy code that writes the new shape. Reverse it and, during the rollout window, an old instance reads a new-shape document and fails — usually as a null dereference in one endpoint, on a fraction of requests, which is exactly the kind of intermittent error that takes an afternoon to diagnose. The same rule applies to rollbacks: if you might roll back the writer, the reader must handle both shapes for at least as long.

Introducing validation

on a collection that already has bad data
// Chapter 1 argued for schema validation. Adding it to an existing
// collection is where the argument meets reality, and there is a path.

// 1. Find out what is actually in there.
db.orders.aggregate([
  { $group: { _id: { $type: "$amount" }, n: { $sum: 1 } } }
]);
//   { _id: "decimal", n: 412039 }
//   { _id: "string",  n: 87 }      <- the import from 2024
//   { _id: "double",  n: 12 }      <- someone in mongosh

// 2. Add the validator in WARN mode. Nothing is rejected; violations are
//    logged, so you learn which write paths are producing bad data.
db.runCommand({ collMod: "orders",
  validator: { $jsonSchema: { … } },
  validationAction: "warn", validationLevel: "moderate" });

// 3. Fix the write paths the log identifies.
// 4. Backfill the existing bad documents.
// 5. Switch to error, and moderate -> strict.
db.runCommand({ collMod: "orders",
  validationAction: "error", validationLevel: "strict" });

//   validationLevel "moderate" validates only documents that ALREADY pass,
//   so existing bad data can stay while new writes are checked. That is what
//   makes this sequence possible on a live collection.
//
//   Note that validation applies to the WHOLE document on any update, so a
//   $set touching one field of a non-conforming document will be rejected
//   under strict. Under moderate it is allowed, which is usually what you
//   want during a transition.

Discovering what you have

there is no information_schema, so build one
// Which fields exist, and how often — sampled, so it is cheap:
db.orders.aggregate([
  { $sample: { size: 10000 } },
  { $project: { fields: { $objectToArray: "$$ROOT" } } },
  { $unwind: "$fields" },
  { $group: { _id: "$fields.k", n: { $sum: 1 },
              types: { $addToSet: { $type: "$fields.v" } } } },
  { $sort: { n: -1 } }
]);
//   { _id: "status", n: 10000, types: ["string"] }
//   { _id: "legacyRef", n: 143, types: ["string", "null"] }   <- residue
//   { _id: "amount", n: 10000, types: ["decimal", "string"] } <- drift

// Documents missing an expected field:
db.orders.countDocuments({ shippingTier: { $exists: false } });

// Array length distribution — the growth check from chapter 9:
db.orders.aggregate([
  { $project: { n: { $size: { $ifNull: ["$items", []] } } } },
  { $group: { _id: null, max: { $max: "$n" }, avg: { $avg: "$n" } } }
]);

// Run these on any collection you inherit, and again periodically. A field
// appearing on 0.1% of documents is either a bug, a removed feature nobody
// cleaned up, or a shape somebody added without telling anyone — and all
// three are worth knowing about.

A checklist

  • Keep a migration directory even when there is nothing to run. The record is the point.
  • Add a schemaVersion field before you need it. Retrofitting one is itself a migration.
  • Readers before writers, with a wait between the deploys.
  • Backfill in batches, resumable, throttled, watching replication lag.
  • Guard every migration update with the version it expects, so reruns and concurrency are safe.
  • Verify with the version histogram, not by assuming the job finished.
  • Remove the old read path only when the count is zero — and actually remove it.
  • Add validation in warn mode first, then moderate, then strict.
The cleanup is the part that gets skipped

The migration is interesting and the cleanup is not, so codebases accumulate branches handling shapes that no longer exist anywhere — and each one makes the next change harder, because nobody can tell which are load-bearing. The version histogram is what makes deletion safe: when schemaVersion: 1 returns zero documents, the v1 branch is provably dead and can go. Put the cleanup in the backlog when you write the migration, with the histogram query attached as the condition. Otherwise the flexibility this chapter opened with quietly becomes the debt it warned about.

The short version

  1. Adding a field is free. Renaming, retyping and restructuring are real migrations.
  2. No migration artefact means no record. Keep a migration directory anyway.
  3. A schemaVersion field is what makes old read paths safely deletable.
  4. Lazy migration never finishes. Pair it with a background backfill or the cleanup never happens.
  5. Backfills must be resumable, idempotent, throttled, observable and verifiable.
  6. Deploy readers before writers, and keep both working as long as you might roll back.
  7. Add validation in warn mode, fix the write paths, backfill, then switch to strict.
  8. Verify with the version histogram and then actually delete the old branch.
