Change streams and the oplog

A supported, resumable feed of every change to a collection, built on the replication log the database already maintains. It is the mechanism that makes several of the earlier chapters' patterns practical — and it has exactly one operational constraint that decides whether it works.

Watching a collection

the whole API, essentially
const stream = db.collection("orders").watch();

for await (const change of stream) {
  console.log(change.operationType);   // insert, update, replace, delete,
                                       // drop, rename, invalidate
  console.log(change.documentKey);     // { _id: ... }
  console.log(change.fullDocument);    // inserts and replaces; updates only
                                       // if you ask (see below)
  console.log(change.updateDescription);
  //   { updatedFields: { status: "paid" }, removedFields: [] }
  console.log(change._id);             // THE RESUME TOKEN
}

// Watch at three levels:
db.collection("orders").watch();     // one collection
db.watch();                          // every collection in a database
client.watch();                      // the entire deployment

// Filter server-side with a pipeline, so unwanted events never reach you:
db.collection("orders").watch([
  { $match: { operationType: "update",
              "updateDescription.updatedFields.status": "paid" } }
]);

// Requires a replica set or a sharded cluster — the oplog is what it reads.
// Not available on a standalone mongod.
This is a supported API, not oplog tailing

Before change streams arrived in 3.6, applications read local.oplog.rs directly. That worked and it coupled you to an internal format, gave no resumption guarantees, broke on failover, and required each consumer to reimplement ordering and deduplication. Change streams are the same data behind a stable interface with resume tokens, correct failover behaviour and cluster-wide ordering. If you find code tailing the oplog directly, it predates 3.6 and should be replaced. Everything in this chapter assumes the supported API.

persisting the token, which is the whole job
// Every event carries change._id — an opaque resume token. Store it AFTER
// processing the event, in the same place you write the results if you can.

let token = await tokens.findOne({ _id: "orders-consumer" });

const stream = db.collection("orders").watch([], {
  resumeAfter: token?.value,           // pick up after this event
  fullDocument: "updateLookup"
});

for await (const change of stream) {
  await handle(change);                                    // do the work
  await tokens.updateOne({ _id: "orders-consumer" },        // then record it
    { $set: { value: change._id } }, { upsert: true });
}

// Order matters. Process, THEN store — so a crash between the two replays
// the last event rather than skipping it. That makes delivery AT LEAST ONCE,
// which is why handlers must be idempotent (chapter 6).
//
// Better still: do both in one transaction, or write the result and the
// token into the same document, so they cannot disagree.

// Three ways to position a new stream:
{ resumeAfter: token }        // after a specific event
{ startAfter: token }         // like resumeAfter, but survives an invalidate
                              // (a dropped or renamed collection)
{ startAtOperationTime: ts }  // from a timestamp — no token needed
The oplog window is the constraint

A resume token points at a position in the oplog. If a consumer is offline longer than the oplog window (chapter 10), the entry it wants has been overwritten and the stream cannot resume — you get ChangeStreamHistoryLost, and there is no way to recover the missed events from MongoDB. Your options are a full reconciliation pass or accepting the gap. Since the window shrinks silently as write volume grows, this failure arrives one day without any configuration having changed. Monitor the window, size the oplog for your longest plausible consumer outage, and alert when a consumer's lag approaches it.

fullDocument

an update event does not contain the document
// By default an update event gives you only what CHANGED:
{ operationType: "update",
  documentKey: { _id: ObjectId("A") },
  updateDescription: { updatedFields: { status: "paid" }, removedFields: [] } }

// To get the whole document:
db.collection("orders").watch([], { fullDocument: "updateLookup" });

// IMPORTANT: updateLookup fetches the document AS IT IS NOW, at lookup time
// — not as it was immediately after the change. If the document was updated
// twice in quick succession, both events may return the same later state,
// and a deleted document returns null.
//
// So updateLookup gives you the current state, not a point-in-time snapshot.
// For an audit trail or anything order-sensitive, use updateDescription and
// build the state yourself.

// Since 6.0, with pre- and post-images enabled on the collection:
db.runCommand({ collMod: "orders", changeStreamPreAndPostImages: { enabled: true } });
db.collection("orders").watch([], {
  fullDocument: "whenAvailable",
  fullDocumentBeforeChange: "whenAvailable"
});
// Now you get the actual before and after states of the change itself,
// which makes proper auditing and change-data-capture possible.
// The cost is storage: pre-images are retained in a system collection.

The natural fix for denormalisation drift

Chapters 2 and 3 kept saying the same thing: every duplicated field needs an owner and a reconciliation. A change stream is the best available owner, because it cannot be bypassed — it sees every write regardless of which service or script made it, so a copy maintained this way stays correct even when someone updates the source directly in a console. Compare that with maintaining the copy in application code, which every other write path can skip. It does not remove the need for a periodic reconciliation job, since a stream can fall behind or lose history, but it makes drift the exception rather than the expectation.

Guarantees

What you get

  • Total ordering, including across shards
  • At-least-once delivery, with a persisted token
  • Only majority-committed changes — never an event for a write that gets rolled back
  • Survives failover; the stream follows the new primary
  • Server-side filtering with a pipeline

What you do not

  • Exactly-once — handlers must be idempotent
  • History beyond the oplog window
  • Events for TTL deletions distinguishable from ordinary ones
  • The before-image, unless you enable pre-images
  • Low overhead at very high change rates on a sharded cluster
ordering, and what it costs on a sharded cluster
// On a replica set, ordering is free — one oplog, one sequence.
//
// On a SHARDED cluster, mongos merges streams from every shard into one
// totally ordered sequence. To do that it must wait until it has heard from
// every shard up to a given cluster time — so a shard with NO activity still
// has to report periodically, and one slow shard delays the whole stream.
//
// The practical effect: change stream latency on a sharded cluster is bounded
// by the slowest shard, and an idle shard adds a small constant delay. This
// is fine at moderate rates and is a real consideration at very high ones.

// A change stream is a cursor and behaves like one (chapter 4):
const stream = coll.watch([], { maxAwaitTimeMS: 1000, batchSize: 100 });
// maxAwaitTimeMS controls how long the server waits for new events before
// returning empty — the trade between latency and polling overhead.

// It reads from wherever your read preference points, and secondaries lag —
// so a stream on a secondary is behind by the replication lag. For anything
// driving a side effect, read from the primary.

// Resource cost: each open stream is a cursor holding server resources.
// Hundreds of streams — one per connected user, say — is a design that will
// not scale. Run a small number of consumers and fan out in your application.

A consumer that works

the shape worth copying
async function consume() {
  const state = db.collection("_streamState");
  const NAME = "orders-projector";

  while (true) {
    const saved = await state.findOne({ _id: NAME });
    let stream;
    try {
      stream = db.collection("orders").watch(
        [{ $match: { operationType: { $in: ["insert", "update", "replace"] } } }],
        { startAfter: saved?.token, fullDocument: "updateLookup" }
      );

      for await (const change of stream) {
        await handleIdempotently(change);          // safe to run twice
        await state.updateOne({ _id: NAME },
          { $set: { token: change._id, at: new Date() } }, { upsert: true });
      }
    } catch (err) {
      if (err.code === 286 || err.codeName === "ChangeStreamHistoryLost") {
        // The oplog window was exceeded. There is no way to recover the
        // missed events — run a full reconciliation, then start fresh.
        await reconcileEverything();
        await state.deleteOne({ _id: NAME });
      } else {
        await sleep(backoff());                    // transient — reconnect
      }
    } finally {
      await stream?.close();
    }
  }
}

// The four things that make this correct:
//   startAfter rather than resumeAfter — survives a collection drop
//   process THEN persist — at-least-once rather than at-most-once
//   an idempotent handler — because at-least-once means duplicates
//   an explicit path for history loss — because it will happen eventually
//
// Also: monitor how far behind the consumer is. now() minus the timestamp
// of the last processed event, compared against the oplog window, is the
// number that tells you whether you are about to lose history.
Only one consumer per stream, or you will duplicate work

A change stream is not a queue with competing consumers — every open stream receives every event. Running three instances of a projector for availability means every change is processed three times, and since handlers are idempotent this often looks fine while tripling the write load and occasionally interleaving badly. If you need high availability, use leader election (a lock document with a TTL, or your orchestrator's leader mechanism) so exactly one instance is consuming. If you need throughput, either partition the stream with a $match on a hash of _id, or feed events into a real queue and scale the workers behind it.

The short version

  1. Change streams are a supported, resumable feed over the oplog. Do not tail local.oplog.rs directly.
  2. Persist the resume token after processing each event, ideally with the result in one write.
  3. The oplog window decides everything. Offline longer than it and the stream cannot resume — no recovery, only reconciliation.
  4. Delivery is at-least-once. Handlers must be idempotent.
  5. fullDocument: "updateLookup" returns the document as it is now, not as it was at the change.
  6. Only majority-committed changes appear, so you never see an event for a write that gets rolled back.
  7. They are the best available owner for denormalised copies, because nothing can bypass them.
  8. Every open stream gets every event. Use leader election, not multiple instances.
