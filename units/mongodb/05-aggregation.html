The aggregation pipeline

A sequence of stages, each transforming the stream of documents it receives and passing the result on. It is procedural where SQL is declarative, which makes it easier to reason about step by step and easier to write in a catastrophically wrong order.

stages order matters $lookup $group

Stages in sequence

the shape
db.orders.aggregate([
  { $match:  { status: "paid", placedAt: { $gte: startOfMonth } } },
  { $unwind: "$items" },
  { $group:  { _id: "$items.sku",
               units:   { $sum: "$items.qty" },
               revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } } } },
  { $sort:   { revenue: -1 } },
  { $limit:  10 }
]);

// Read it top to bottom: filter to this month's paid orders, split each into
// one document per line item, group by sku summing quantity and revenue,
// sort, take ten.
//
// The SQL equivalent is one statement the optimiser rearranges freely. Here
// the order you write IS largely the order of execution — with a few
// automatic optimisations noted below. That is the trade: more control,
// more responsibility.

$match first, always

Only the first stage can use an index — once documents are flowing through the pipeline, there is no index on the intermediate stream. A $match at the top is an indexed query that reads a hundred documents; the same $match after a $group reads the entire collection, groups all of it, and then throws nearly all of it away. MongoDB does move some $match stages earlier automatically, and it cannot move one past a $group or $project that changed the field it references. Put the filter first yourself and do not rely on the optimiser.

$group

the accumulator set
{ $group: {
    _id: "$customerId",                        // the grouping key
    orders:    { $sum: 1 },                    // count
    revenue:   { $sum: "$total" },
    average:   { $avg: "$total" },
    biggest:   { $max: "$total" },
    first:     { $first: "$placedAt" },        // needs a $sort before it
    last:      { $last: "$placedAt" },
    allRefs:   { $push: "$reference" },        // array of every value
    uniqueSkus:{ $addToSet: "$items.sku" },    // array of distinct values
    stdDev:    { $stdDevPop: "$total" }
} }

// _id: null groups everything into one document.
// _id can be a composite:
{ $group: { _id: { year: { $year: "$placedAt" },
                   month: { $month: "$placedAt" } }, … } }

// Conditional aggregation — the SQL unit's chapter 6, same idea:
{ $group: {
    _id: "$region",
    paid:      { $sum: { $cond: [{ $eq: ["$status", "paid"] }, 1, 0] } },
    cancelled: { $sum: { $cond: [{ $eq: ["$status", "cancelled"] }, 1, 0] } },
    paidValue: { $sum: { $cond: [{ $eq: ["$status", "paid"] }, "$total", 0] } }
} }

// $push and $addToSet are UNBOUNDED. Grouping a million documents and
// pushing each into an array builds a document that exceeds 16 MB and the
// stage fails. Use them only when the group is known to be small — or add
// { $slice: … } after, which does not help because the array was already
// built. Bound the input instead.
Blocking stages buffer, and they have limits

$group, $sort, $bucket and $setWindowFields cannot emit anything until they have seen all their input, so they hold state in memory — capped at 100 MB per stage. Exceed it and the pipeline fails unless allowDiskUse: true lets it spill, which works and is much slower. From MongoDB 6.0 spilling is allowed by default, so the failure mode became "mysteriously slow" rather than "clear error", which is arguably worse. The real fix is nearly always $match earlier and $project away fields you do not need before the blocking stage.

$lookup

it is a join, and it is not SQL's join
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $lookup: {
      from: "customers",
      localField: "customerId",
      foreignField: "_id",
      as: "customer"            // ALWAYS an array, even for one match
  } },
  { $unwind: "$customer" }      // usually needed immediately after
]);

// The general form, when you need conditions beyond equality:
{ $lookup: {
    from: "reviews",
    let: { pid: "$_id" },
    pipeline: [
      { $match: { $expr: { $and: [ { $eq: ["$productId", "$$pid"] },
                                   { $gte: ["$stars", 4] } ] } } },
      { $sort: { helpful: -1 } },
      { $limit: 5 }
    ],
    as: "topReviews"
} }

// WHAT TO KNOW:
//   * it is a LEFT OUTER join. No match gives an empty array, not nothing
//   * it is executed as a nested loop: one lookup PER INPUT DOCUMENT.
//     Index the foreign field or it is a collection scan per document
//   * there is no join reordering, no hash join, no merge join. The
//     optimiser will not rescue a badly-shaped pipeline
//   * on a SHARDED collection the foreign side has restrictions, and
//     performance is materially worse (chapter 13)
//   * the result must fit in one 16 MB document, arrays included

// The honest summary: $lookup exists and works, and it is for occasional
// joins on modest result sets, not for a schema built around joining. If
// your hot path needs $lookup, chapter 2's extended reference is usually
// the answer — and if most paths do, chapter 18 is.

$unwind

one document per element, with the costs that implies
// { _id: 1, items: [a, b, c] }  ->  three documents, each with one item
{ $unwind: "$items" }

{ $unwind: {
    path: "$items",
    preserveNullAndEmptyArrays: true,   // keep documents with no items —
                                        // otherwise they VANISH silently
    includeArrayIndex: "position"
} }

// That default is a real trap: an order with an empty items array disappears
// from the pipeline entirely, so counts come out low and nobody notices
// because the documents that vanished are the ones nobody was looking at.

// $unwind multiplies the stream. Five thousand orders averaging four items
// becomes twenty thousand documents, each carrying a full copy of the order.
// $project away what you do not need FIRST:
[
  { $match: { … } },
  { $project: { items: 1, placedAt: 1 } },   // drop everything else
  { $unwind: "$items" },
  { $group: { … } }
]

// And often you do not need it at all. To sum an array within each document,
// use an expression rather than unwinding and regrouping:
{ $addFields: { itemCount: { $sum: "$items.qty" } } }
{ $addFields: { total: { $reduce: {
    input: "$items", initialValue: 0,
    inVal: { $add: ["$$value", { $multiply: ["$$this.qty", "$$this.price"] }] }
} } } }

$facet

results and their count, in one round trip
db.products.aggregate([
  { $match: { category: "keyboards", active: true } },
  { $facet: {
      results: [ { $sort: { popularity: -1 } }, { $skip: 0 }, { $limit: 24 } ],
      total:   [ { $count: "n" } ],
      byBrand: [ { $group: { _id: "$brand", n: { $sum: 1 } } },
                 { $sort: { n: -1 } } ],
      byPrice: [ { $bucket: { groupBy: "$price",
                              boundaries: [0, 50, 100, 200, 10000],
                              default: "other",
                              output: { n: { $sum: 1 } } } } ]
  } }
]);

// Each sub-pipeline sees the SAME input documents. One pass over the data
// produces the page of results, the total count and both facet breakdowns —
// which would otherwise be four round trips.
//
// Two caveats. Sub-pipelines cannot use an index (only the $match before
// $facet can), and the whole result must fit in 16 MB. So $facet is right
// for a filtered set of thousands and wrong for a whole large collection.

Window functions

$setWindowFields, since 5.0
// Running totals, rankings and comparisons to neighbouring rows, without
// collapsing the documents — the SQL unit's chapter 8, arriving late but
// arriving.
db.sales.aggregate([
  { $setWindowFields: {
      partitionBy: "$region",
      sortBy: { day: 1 },
      output: {
        runningTotal: {
          $sum: "$amount",
          window: { documents: ["unbounded", "current"] }
        },
        sevenDayAvg: {
          $avg: "$amount",
          window: { range: [-6, 0], unit: "day" }
        },
        rank:      { $rank: {} },
        previous:  { $shift: { output: "$amount", by: -1 } }
      }
  } }
]);

// Before 5.0 this required $group with $push, then $unwind, then arithmetic
// on array indices — which is exactly as unpleasant as it sounds. If you
// find that pattern in an existing codebase, this is what replaces it.

$merge

materialising a rollup
// Chapter 3's rollup pattern, implemented. Run on a schedule; the dashboard
// then reads documents instead of aggregating.
db.orders.aggregate([
  { $match: { placedAt: { $gte: yesterday, $lt: today } } },
  { $group: {
      _id: { day: "$day", category: "$category" },
      revenue: { $sum: "$total" }, orders: { $sum: 1 } } },
  { $merge: {
      into: "dailyRevenue",
      on: "_id",
      whenMatched: "replace",      // or "merge", "keepExisting", "fail",
                                   // or a custom update pipeline
      whenNotMatched: "insert"
  } }
]);

// $merge is INCREMENTAL — it updates matching documents and inserts new
// ones, so re-running it for one day is safe and idempotent.
// $out REPLACES the whole target collection, which is simpler and means the
// collection is briefly wrong if anyone reads it mid-run. Prefer $merge.

Writing a fast pipeline

  • $match first, and make sure an index serves it. Only the first stage can use one.
  • $sort early if an index supplies it, late otherwise — a sort on an indexed field as stage one is free.
  • $project or $unset before an expensive stage. Do not carry fields through a $unwind or a $group that you will discard.
  • $limit as early as correctness allows. $sort followed by $limit is optimised into a top-N and never materialises the full sort.
  • Index the foreign field of every $lookup, or each input document triggers a collection scan.
  • Avoid $unwind when an expression will do — $sum, $reduce, $filter, $map operate on arrays in place.
  • Watch for unbounded $push in a $group, which builds documents that hit 16 MB.
  • Check it with explain: db.c.aggregate(p, {explain: true}) shows which stages ran and what got rewritten.
Build it one stage at a time

The pipeline's procedural nature is its best debugging property. Run the first stage alone with a $limit and look at the output. Add the second. Look again. A pipeline that produces the wrong answer is nearly always a stage where the documents stopped being the shape the next stage assumed — usually a $unwind dropping empty arrays, a $project removing a field a later stage references, or a $group renaming everything into _id. Watching the stream at each step finds all three in seconds, where reading the whole pipeline finds none of them.

When the pipeline is the wrong tool

The aggregation framework can express a great deal, and expressing something is not the same as it being a good idea. A pipeline with eight $lookup stages across five collections is a query the SQL unit would write in fifteen readable lines with an optimiser that reorders the joins — and it is a sign your data is normalised in a database that does not reward normalising. The honest options are: denormalise so the query becomes simple (chapters 2 and 3), materialise it with $merge so it runs once rather than per request, or move that workload somewhere relational. An enormous pipeline is a schema symptom, not a skill to develop.

The short version

  1. Stages transform a stream in sequence. Only the first stage can use an index.
  2. $match first, always. The optimiser moves some filters earlier and cannot move them past a $group.
  3. $group and $sort are blocking, capped at 100 MB, and spill to disk by default since 6.0 — so the failure looks like slowness.
  4. $lookup is a nested loop, per input document. Index the foreign field, and do not build a schema around it.
  5. $unwind silently drops documents with empty arrays unless you set preserveNullAndEmptyArrays.
  6. Prefer array expressions to $unwind + $group — $sum, $reduce, $filter, $map.
  7. $facet gets results, counts and breakdowns in one pass; $merge materialises rollups incrementally.
  8. Build it one stage at a time, and treat an enormous pipeline as a schema symptom.
