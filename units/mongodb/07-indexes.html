Indexes

B-trees, as in any database, with two differences that matter: an index on an array field indexes every element, and the order of fields in a compound index is decided by a rule most people have never heard of.

compound esr multikey partial & ttl

The ESR rule

A compound index is ordered by its first field, then its second within that, and so on. Which field goes where is not a matter of taste — there is a rule, and it is Equality, Sort, Range.

Design the index Describe a query. The ESR rule produces the index, and the wrong orders show what they cost.

why the order is E, then S, then R
db.orders.find({ status: "paid", total: { $gt: 100 } })
         .sort({ placedAt: -1 });

// CORRECT — Equality, Sort, Range
db.orders.createIndex({ status: 1, placedAt: -1, total: 1 });

// EQUALITY first, because it narrows the index to one contiguous section.
//   Everything after it is scanned within that section only.
//
// SORT second, because within a fixed equality value the index is already
//   ordered by this field — so MongoDB reads it in order and does NO SORT.
//
// RANGE last, because a range spans many index entries. Anything AFTER a
//   range field is no longer in sorted order across that range, so a sort
//   placed after it cannot be served by the index.

// Get it wrong and you pay:
db.orders.createIndex({ status: 1, total: 1, placedAt: -1 });
//   The range on total spreads across many entries, and placedAt is only
//   ordered WITHIN each total value. MongoDB must fetch everything matching
//   and sort it in memory — with a 32 MB ceiling (chapter 4).

// The rule in one line: put every equality field first, then the sort
// fields in sort order, then the range fields last.
The prefix rule

A compound index on {a: 1, b: 1, c: 1} serves queries on a, on a and b, and on all three — any left prefix. It does not serve a query on b alone, or on c alone, because the index is sorted by a first and entries for a given b are scattered throughout it. This is why one well-ordered compound index often replaces three single-field ones, and why the order is the whole design decision. Same rule as the PostgreSQL unit's chapter 6 — B-trees do not care which database they are in.

Multikey

indexing an array indexes every element
// { _id: 1, tags: ["gift", "urgent", "fragile"] }
db.orders.createIndex({ tags: 1 });
//   creates THREE index entries for that one document, all pointing at it.
//   A document with 200 tags creates 200 entries.

db.orders.find({ tags: "gift" });     // ordinary indexed lookup. Fast.

// The costs, which are real:
//   * index size scales with total elements, not documents
//   * every write that changes the array rewrites all its entries
//   * a document with a large array is disproportionately expensive to write

// TWO LIMITS TO KNOW:
//
// 1. A compound index may contain AT MOST ONE array field. This fails:
db.orders.createIndex({ tags: 1, "items.sku": 1 });
//   MongoDB cannot index the cross product of two arrays — it would be
//   len(tags) × len(items) entries per document. The error appears at
//   INSERT time, not at index creation, which is a nasty surprise: the
//   index builds fine on existing data and then rejects a document that
//   happens to have both arrays populated.
//
// 2. A multikey index cannot support a covered query. The index has one
//    entry per element and cannot reconstruct the original array, so
//    MongoDB must fetch the document (chapter 8).

// Indexing inside an array of objects works normally, and is common:
db.orders.createIndex({ "items.sku": 1, "items.qty": 1 });
// but note this is still multikey, and $elemMatch semantics apply at query
// time (chapter 4) — the index will return candidates where different
// elements matched each condition, and MongoDB filters afterwards.

Partial indexes

index the documents you actually query
// A jobs collection: 50 million rows, of which 400 are pending at any moment.
// A full index on status wastes almost all of its size on a value nobody
// queries by.
db.jobs.createIndex(
  { runAfter: 1 },
  { partialFilterExpression: { status: "pending" } }
);
// Tiny index, and it only has to be updated when a document enters or
// leaves the pending state.

// A unique constraint that applies conditionally — the "only one active
// subscription per customer" rule, which a plain unique index cannot express:
db.subscriptions.createIndex(
  { customerId: 1 },
  { unique: true, partialFilterExpression: { active: true } }
);

// THE CATCH: the query must PROVABLY fall inside the partial filter, or
// MongoDB will not use the index at all.
db.jobs.find({ runAfter: { $lte: now } });                    // NOT used
db.jobs.find({ status: "pending", runAfter: { $lte: now } }); // used

// Including the redundant-looking status condition is what makes it work,
// and forgetting it is the commonest reason a partial index appears to do
// nothing. Same argument as the PostgreSQL unit's chapter 6.

// SPARSE is the older, cruder version — index only documents where the field
// exists. Partial can express the same thing and more:
{ partialFilterExpression: { email: { $exists: true } } }

Unique indexes

the only real constraint MongoDB has
db.users.createIndex({ email: 1 }, { unique: true });
db.memberships.createIndex({ userId: 1, teamId: 1 }, { unique: true });

// A unique index is what makes an upsert race-free (chapter 6), and it is
// essentially the only server-side data constraint besides schema validation.

// The null trap: a unique index treats MISSING as a value, so two documents
// without the field collide with each other. Combine with partial:
db.users.createIndex(
  { nationalId: 1 },
  { unique: true, partialFilterExpression: { nationalId: { $exists: true } } }
);
// Now documents without the field are simply not in the index.

// Case-insensitive uniqueness — do NOT do this by storing a lowercased copy:
db.users.createIndex(
  { email: 1 },
  { unique: true, collation: { locale: "en", strength: 2 } }
);
// strength: 2 ignores case and accents. Note the QUERY must specify the same
// collation to use this index, which is easy to forget:
db.users.find({ email: "A@B.com" }).collation({ locale: "en", strength: 2 });

// On a SHARDED collection, a unique index must include the shard key —
// uniqueness cannot be enforced across shards without one (chapter 13).
// This is a real constraint on schema design and it arrives late.

TTL indexes

automatic expiry
db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 });
//   deletes documents an hour after lastSeen

db.events.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
//   uses the DATE IN THE FIELD as the expiry moment — much more flexible,
//   since each document carries its own lifetime

// Notes that matter operationally:
//   * a background thread runs every 60 SECONDS, so deletion is approximate.
//     Not a security control
//   * it only runs on the PRIMARY. Secondaries get the deletes via the oplog
//   * the deletes are real deletes — oplog volume, replication load, and no
//     space returned to the filesystem (chapter 6)
//   * the field must be a Date, or an array of Dates. A document with a
//     string there is silently never expired
//   * changing the value: collMod, not dropping and recreating
db.runCommand({ collMod: "sessions",
  index: { keyPattern: { lastSeen: 1 }, expireAfterSeconds: 7200 } });

// For high-volume time-series, dropping a whole bucketed collection or using
// a time-series collection's expireAfterSeconds beats deleting documents one
// at a time — the same argument as partitioning in the PostgreSQL unit.

What indexes cost

Every index you add

  • Is updated on every write that touches its fields
  • Occupies memory — and index pages compete with documents for the WiredTiger cache
  • Is another thing the planner must evaluate
  • Slows index builds, restores and initial syncs

So

  • One well-ordered compound index often replaces three single-field ones
  • Drop unused indexes — $indexStats tells you which
  • Partial indexes cost proportionally less
  • Aim for the indexes your top queries need, not one per field
finding indexes that earn nothing
db.orders.aggregate([{ $indexStats: {} }]).forEach(i =>
  print(i.name, i.accesses.ops, i.accesses.since));
//   ops: 0 since a date well in the past means nothing has used it

// Read this carefully before dropping anything:
//   * counters reset when the server restarts, so a recent restart means
//     everything looks unused
//   * check EVERY member of the replica set — a secondary may serve an
//     analytics query that never touches the primary
//   * a unique index is a CONSTRAINT. Zero reads does not mean unused
//   * a quarterly report's index is used four times a year

db.orders.totalIndexSize();
db.orders.stats().indexSizes;      // per index

// Hide before dropping — reversible, and it tells you what breaks:
db.orders.hideIndex("status_1_total_1");    // 4.4+. Planner ignores it,
                                            // writes still maintain it
db.orders.unhideIndex("status_1_total_1");  // instant, if something broke
db.orders.dropIndex("status_1_total_1");    // after a week of no complaints
Hiding is the safe way to drop an index

Dropping a large index takes seconds and rebuilding it takes hours, which makes "drop it and see" a bad experiment on a production system. hideIndex makes the planner ignore it while writes continue to maintain it — so the query that secretly depended on it gets slow immediately, and unhiding is instant. Leave it hidden for a week that includes your monthly reporting run, then drop it. This is the same technique as the PostgreSQL unit's hypopg in reverse, and it is one of the more useful operational features MongoDB has added.

Building an index on a live system

it is safe now, and it was not always
db.orders.createIndex({ status: 1, placedAt: -1 });

// Since MongoDB 4.2, index builds do NOT hold an exclusive lock for their
// duration. Reads and writes continue throughout; there is a brief lock at
// the start and the end. The old {background: true} option is deprecated and
// ignored — if you see it in a codebase or in advice, that advice predates 4.2.

// It is still real work: it reads the whole collection, uses CPU and memory
// (maxIndexBuildMemoryUsageMegabytes, default 200 MB), and on a replica set
// the build runs on every member simultaneously.

db.currentOp({ "command.createIndexes": { $exists: true } });
//   progress and phase

db.orders.dropIndex("status_1_placedAt_-1");   // to abort, drop it

// One thing to check before building a UNIQUE index on existing data: it
// fails if duplicates exist, after doing all the work. Find them first:
db.users.aggregate([
  { $group: { _id: "$email", n: { $sum: 1 } } },
  { $match: { n: { $gt: 1 } } }
]);

A worked set

indexes for a workload, not for a schema
// The workload table from chapter 3, turned into indexes.

// 1. Product page by slug — 400/sec
db.products.createIndex({ slug: 1 }, { unique: true });

// 2. Category listing, sorted by popularity — 120/sec
//    E: category, active   S: popularity   R: none
db.products.createIndex({ category: 1, active: 1, popularity: -1 });

// 3. My orders, newest first — 20/sec
//    E: customerId   S: placedAt
db.orders.createIndex({ customerId: 1, placedAt: -1 });

// 4. Pending jobs, oldest first — polled constantly, tiny result set
db.jobs.createIndex({ runAfter: 1 },
  { partialFilterExpression: { status: "pending" } });

// 5. Comments on a post, paginated — 60/sec
db.comments.createIndex({ postId: 1, createdAt: -1 });

// 6. "My comments" across posts — 2/sec
db.comments.createIndex({ userId: 1, createdAt: -1 });

// 7. Sessions expire after an hour
db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 });

// Seven indexes for seven access patterns. Note what is NOT here: an index
// on every field, an index per query variant, or an index for the quarterly
// analytics job — which is allowed to be slow (chapter 3).

The short version

  1. ESR: Equality, Sort, Range. That is the field order for a compound index, and it is a rule rather than a preference.
  2. Left prefix only. {a,b,c} serves a, a+b, a+b+c — never b alone.
  3. An array index creates one entry per element. At most one array field per compound index, and the error arrives at insert time.
  4. Multikey indexes cannot cover a query — the document always gets fetched.
  5. Partial indexes need the filter condition in the query or they are not used at all.
  6. A unique index treats missing as a value. Combine with partial to allow absent fields.
  7. TTL runs every 60 seconds on the primary only. Approximate, and not a security control.
  8. Hide before dropping. Dropping takes seconds; rebuilding takes hours.
