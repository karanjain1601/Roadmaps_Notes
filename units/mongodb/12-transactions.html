Transactions

MongoDB has had multi-document ACID transactions since 4.0, and they work. They are also slower and more constrained than the equivalent in a relational database, which means the interesting question is not how to use them but how often you should need to.

document atomicity sessions limits alternatives

Start from what is already atomic

a single-document write needs no transaction
// Atomic. Every field changes together, or none does, and no reader ever
// observes a partial state.
await orders.updateOne(
  { _id: id, status: "pending" },
  { $set:  { status: "paid", paidAt: new Date() },
    $inc:  { version: 1 },
    $push: { events: { type: "payment", at: new Date() } } }
);

// Also atomic — the filter is part of the operation, so this is a
// compare-and-set. If another process already moved the order out of
// "pending", matchedCount is 0 and nothing happened.

// The design consequence, which is the whole chapter in one line:
//   the more invariants that live inside one document, the fewer
//   transactions you need.
//
// That is not a workaround for a missing feature. It is what chapter 2 was
// arguing for, arriving as a correctness property: an order and its line
// items in one document are updated atomically by construction, where the
// relational version needs a transaction spanning three tables.
Do you need a transaction? Describe what must change together. Often the answer is a schema change rather than a transaction.

Using one

withTransaction, which handles the retries for you
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await accounts.updateOne(
      { _id: from, balance: { $gte: amount } },
      { $inc: { balance: -amount } },
      { session }                       // ← every operation needs this
    );
    await accounts.updateOne(
      { _id: to }, { $inc: { balance: amount } }, { session }
    );
    await ledger.insertOne({ from, to, amount, at: new Date() }, { session });
  }, {
    readConcern:    { level: "snapshot" },
    writeConcern:   { w: "majority" },
    readPreference: "primary"
  });
} finally {
  await session.endSession();
}

// USE withTransaction. The manual startTransaction/commitTransaction form
// requires you to implement the retry loop for TransientTransactionError and
// UnknownTransactionCommitResult yourself, and almost everyone gets it
// slightly wrong. withTransaction retries both correctly.

// THE CALLBACK MUST BE IDEMPOTENT. It can run several times — on a write
// conflict, on a failover, on a network blip. Do not send an email, charge a
// card or increment an application counter inside it.

// Forgetting { session } on one operation is the classic mistake: that
// operation executes OUTSIDE the transaction, commits immediately, and is
// not rolled back if the transaction aborts. It produces exactly the
// inconsistency the transaction was added to prevent, and it is silent.
Every operation needs the session, and the callback must be idempotent

Two rules, and they cause most transaction bugs in MongoDB codebases. An operation without { session } is simply not in the transaction — it commits on its own and survives an abort, which is worse than having no transaction at all because the code reads as though it is protected. And the callback genuinely re-executes: withTransaction retries transient errors, so anything with an external side effect inside it will happen more than once. Reads and writes to MongoDB only; everything else goes after the commit.

Keep them short and small

The failure mode is not that transactions are slow — it is that a long one degrades the whole cluster. An open transaction holds a WiredTiger snapshot, which prevents older versions being discarded and grows cache pressure; on a busy system a few long transactions can push the cache into eviction thrashing and slow every other operation. The guidance from MongoDB is under a second and under a thousand documents, and it is not conservative advice — a transaction that processes 100,000 documents is not a transaction you should be writing. Batch it into many small ones, each idempotent, and track progress in a document.

Write conflicts

optimistic, so contention costs retries
// MongoDB transactions use optimistic concurrency. If two transactions
// modify the same document, one aborts with a TransientTransactionError and
// withTransaction retries it. There is no lock queue and no waiting.
//
// That is fine at low contention and quadratically bad at high contention:
// every retry re-executes the whole callback, and under load the retries
// themselves collide.

// The pathological shape — every transaction touching one hot document:
await inventory.updateOne({ _id: "global-counter" },
  { $inc: { total: 1 } }, { session });
// A hundred concurrent transactions here spend most of their time retrying.

// Three ways out, in order of preference:
//   1. Move the contended change OUT of the transaction and make it a
//      single-document atomic $inc, which never conflicts
//   2. Shard the hot document across N documents and sum on read (chapter 3)
//   3. Order operations consistently so transactions collide predictably
//      rather than in a cycle

// Diagnose it:
db.serverStatus().transactions;
//   totalStarted, totalCommitted, totalAborted
//   a high abort ratio is contention, not errors
db.serverStatus().metrics.operation.writeConflicts;

Designing them away

three patterns that replace most transactions
// 1. PUT THE INVARIANT IN ONE DOCUMENT.
//    Stock and reservations together, so the check and the decrement are
//    one atomic compare-and-set:
await inventory.updateOne(
  { sku: "TSH-001", available: { $gte: qty } },
  { $inc: { available: -qty, reserved: qty } }
);
// matchedCount === 0 means there was not enough stock. No transaction, no
// race, no read-then-write window.

// 2. THE OUTBOX PATTERN. When a write must trigger something elsewhere,
//    record the intent in the SAME document, then act on it separately.
await orders.insertOne({
  _id: orderId, status: "paid",
  outbox: [{ type: "send-receipt", at: new Date(), done: false }]
});
// A worker (or a change stream, chapter 14) picks up the outbox entry and
// performs the side effect, marking it done. The order and the intent to
// send commit together atomically; the side effect is retried until it
// succeeds. This removes the dual-write problem entirely.

// 3. THE SAGA. For a genuinely multi-step process, model the state machine
//    explicitly with compensating actions rather than one long transaction.
{ _id: bookingId, state: "flight-booked",
  steps: [ { name: "flight", status: "done", ref: "…" },
           { name: "hotel",  status: "pending" } ] }
// Each step is a single-document atomic transition. If a later step fails,
// run the compensating action for the earlier ones. More code than a
// transaction, and the only thing that works when steps involve external
// systems that cannot participate in one anyway.
The outbox pattern is the one to internalise

Most requests for a transaction turn out to be a dual-write problem: change the database and send an email, publish an event, call a payment provider. A transaction does not help, because the external system is not in it — the classic failure is the transaction committing and the email failing, or the email sending and the transaction aborting. Writing the intent into the same document as the data makes the two atomic by construction, and a worker retries the side effect until it succeeds. It is more moving parts than a transaction and it is the version that is actually correct.

When to use one

Genuinely appropriate

  • Moving value between two accounts
  • A migration that must not leave data half-converted
  • Maintaining a referenced pair where both must exist
  • An occasional operation spanning collections, not a hot path
  • Anywhere the invariant genuinely cannot fit in one document

A signal to redesign

  • Every write in the application uses one
  • A transaction touching thousands of documents
  • A transaction wrapping an external API call
  • Transactions to compensate for a normalised document schema
  • High abort rates from contention on a hot document
Needing them everywhere means the schema is wrong

Transactions were added because there are real cases that need them, and their existence does not make a normalised document schema a good idea. If most operations in your application span several collections, you have built a relational schema in a document database — you are paying for distributed transactions to get consistency that a relational database would give you with a foreign key and a cheap local transaction. That is a legitimate finding, and the right response is either chapter 2's modelling or chapter 18's honest conclusion, not more transactions.

The short version

  1. A single-document write is already atomic, however many fields it touches. Start there.
  2. Use withTransaction, not the manual form — it implements the retry loop correctly.
  3. Every operation needs { session }. One without it commits independently and is not rolled back.
  4. The callback re-executes. No external side effects inside it.
  5. Under a second, under a thousand documents. A long transaction degrades the whole cluster through cache pressure.
  6. Conflicts abort and retry rather than queueing, so a hot document under contention gets quadratically worse.
  7. The outbox pattern solves the dual-write problem that most transaction requests actually are.
  8. Needing them everywhere is a schema signal, not a usage pattern.
