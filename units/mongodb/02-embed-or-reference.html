Embed or reference

The decision that determines whether a MongoDB deployment is pleasant or miserable, made hundreds of times across a schema, and expensive to reverse once data exists. There is a reliable way to make it, and it is not "embed by default".

embedding references cardinality duplication

The two shapes

the same relationship, both ways
// EMBEDDED — the items live inside the order
{
  _id: ObjectId("..."), reference: "NW-8842", status: "paid",
  items: [
    { sku: "TSH-001", name: "T-shirt", qty: 2, price: NumberDecimal("24.99") },
    { sku: "MUG-114", name: "Mug",     qty: 1, price: NumberDecimal("12.50") }
  ]
}
// One read gets everything. One write updates everything atomically.
// The items cannot be queried independently of their order.

// REFERENCED — the items are their own documents
// orders
{ _id: ObjectId("A"), reference: "NW-8842", status: "paid" }
// items
{ _id: ObjectId("X"), orderId: ObjectId("A"), sku: "TSH-001", qty: 2 }
{ _id: ObjectId("Y"), orderId: ObjectId("A"), sku: "MUG-114", qty: 1 }
// Two reads, or a $lookup. Items are queryable on their own and can grow
// without limit. Updating an order and its items together needs a transaction.
The question is not "which is better"

It is "is this data read and written as part of the parent, or independently of it?" Order line items are meaningless without their order, are always fetched with it, and are bounded — embed. Comments on a popular post are read separately, paginated, and unbounded — reference. That single question, applied honestly, gets the right answer most of the time. The failure mode is answering "how would I do this in SQL" instead, which produces a normalised document schema that has all the joins and none of the constraints.

Bounded is the word to be honest about

"An order has a few line items" is true until a wholesale customer orders four hundred SKUs. "A user has a few addresses" is true until someone integrates an address-book import. The question is not what is typical, it is what is the maximum, and is it enforced. If nothing prevents the array growing, it will grow — and the failure arrives as a write error on one document, in production, long after the design was settled and the code that assumed the array was small is everywhere. Either bound it in schema validation with maxItems, or reference.

Duplication

the extended reference, and when it is correct
// A reference plus a copy of the few fields you always need. This is the
// most common and most useful hybrid.
{
  _id: ObjectId("..."),
  reference: "NW-8842",
  customer: {
    id: ObjectId("65f1..."),           // the reference
    name: "Amara Okafor",              // duplicated, for display
    email: "amara@example.com"         // duplicated
  },
  items: [ … ]
}

// Reading an order list now needs no lookup at all, which is the point.
// The cost: if the customer changes their name, every order carries the old
// one until something updates them.

// TWO CASES, and they are completely different:
//
// 1. A CACHE of the current value. It must be kept in sync, and that is your
//    job — a change stream (chapter 14), a background job, or accepting
//    staleness deliberately.
//
// 2. A HISTORICAL RECORD. An invoice should show the name and address AS
//    THEY WERE when it was issued. That is not duplication at all; it is a
//    different fact that happens to look similar, and updating it would be
//    a bug.
//
// Most extended references in practice are case 2 and people treat them as
// case 1, which produces sync machinery for data that should never change.
// Decide which you have, and write it down in the field name if you can:
//   customerNameAtOrder  vs  customerNameCached
Duplication is the deliberate trade, not an accident

Relational design treats storing a fact twice as an error, because the two copies can disagree (SQL chapter 4). Document design treats it as a tool: you accept the risk of divergence in exchange for removing a join from a hot read path. That is a legitimate trade and it is only legitimate when made deliberately, with a plan for keeping the copies consistent or a decision that they should not be. Duplication that nobody decided on is exactly the bug the relational rule was warning about.

References in practice

which side holds the pointer
// CHILD POINTS TO PARENT — one-to-many, the default
{ _id: ObjectId("X"), postId: ObjectId("A"), body: "…" }
db.comments.createIndex({ postId: 1, createdAt: -1 });
// Adding a comment does not touch the post. The list is paginated and
// sorted by the index. This is right for almost every one-to-many.

// PARENT HOLDS AN ARRAY OF IDS — one-to-few, when you need the order
{ _id: ObjectId("A"), title: "…", tagIds: [ObjectId("t1"), ObjectId("t2")] }
// Preserves ordering and gets you the whole set in one read. Only for
// bounded lists — the array grows in the parent document.

// BOTH SIDES — a two-way reference
// Faster in both directions, and now two things to keep consistent.
// Justify it with a measured read pattern, not with symmetry.

// Resolving a reference is application-side, or $lookup (chapter 5):
const post = await posts.findOne({ _id: id });
const comments = await db.comments
    .find({ postId: id }).sort({ createdAt: -1 }).limit(20).toArray();

// Note what is NOT here: there is no foreign key. Nothing stops you deleting
// the post and leaving orphaned comments. That is a real loss compared with
// the SQL unit's chapter 11, and the mitigations are all application-side:
// delete children explicitly, or tolerate orphans and filter them out.

The shapes that go wrong

The unbounded array
Comments, events, log lines or readings embedded in a parent that never stops receiving them. Works beautifully in development and fails on one document in production. The commonest MongoDB modelling error by a wide margin.
The relational transplant
Every entity in its own collection with ids between them, because that is how the relational schema looked. You now have all the joins, done in application code or $lookup, and none of the foreign keys, transactions or referential integrity that made the relational version work. Strictly worse than either option.
The god document
A user document containing their profile, preferences, session history, notifications and activity feed. Every read fetches all of it, every write rewrites all of it, and it grows forever.
Embedding something shared
Product details copied into every order line, then a price correction requires updating a million documents — and half of them should not have been updated, because they were historical records.
Arrays as maps
attributes: [{k: "colour", v: "red"}] when it could be attributes: {colour: "red"}. Harder to query, harder to index, and usually written that way to imitate a relational key-value table.
Separate collections per tenant
Or per day, or per user. Thousands of collections cost metadata, memory and index overhead, and every operation has to know which one to use. Use a field and an index instead.
Reversing this decision is expensive

Changing embedded to referenced means writing a migration that splits every document, rewriting every read path, and doing both without downtime while writes continue. It is achievable — chapter 17 covers the mechanics — and it is a project rather than a change. That is why this chapter comes second: the schema decisions are the ones with the longest half-life, and unlike an index they cannot be added later in one command. Spend the time here that you would have spent on normalisation in a relational design.

Growth

why an array that grows is worse than it looks
// WiredTiger does not update a document in place when it grows. A document
// that gains a field or an array element is rewritten, and every index entry
// that references it may need updating.
//
// So an array that grows by one element per hour means rewriting the WHOLE
// document, every hour, at whatever size it has reached. The write cost grows
// with the array — quadratic over the document's lifetime.

// This is bad:
db.devices.updateOne(
  { _id: id },
  { $push: { readings: { t: new Date(), v: 21.4 } } }   // forever
);

// This is the bucket pattern (chapter 3): a new document per period, so each
// one stays bounded and old ones are never rewritten.
db.readings.updateOne(
  { device: id, hour: currentHour },
  { $push: { samples: { t: new Date(), v: 21.4 } },
    $inc:  { count: 1 } },
  { upsert: true }
);

// And if you genuinely need a bounded recent list, MongoDB will do it:
{ $push: { recent: { $each: [event], $slice: -50, $sort: { t: -1 } } } }
// Keeps the newest 50 and discards the rest, in one atomic operation.

A worked example

a blog, decided relationship by relationship
// posts
{
  _id: ObjectId("A"),
  slug: "the-document-model",
  title: "The document model",
  body: "…",

  // EMBED: one per post, always read together, small
  seo: { description: "…", ogImage: "…" },

  // EMBED: bounded, read with the post, and denormalised for display.
  // Historical: the author's name at publication is what we want.
  author: { id: ObjectId("u1"), name: "Amara Okafor", avatar: "…" },

  // EMBED: bounded set of scalars, and directly queryable and indexable
  tags: ["mongodb", "modelling"],

  // EMBED as a bounded slice: the three most recent comments, for the
  // preview on the listing page. The full list is referenced below.
  recentComments: [ { by: "…", body: "…", at: ISODate("…") } ],

  // COMPUTED: maintained on write, so the listing page needs no aggregation
  commentCount: 412,
  readingMinutes: 9
}

// comments — REFERENCED: unbounded, paginated, queryable by author
{ _id: ObjectId("X"), postId: ObjectId("A"), userId: ObjectId("u9"),
  body: "…", createdAt: ISODate("…") }
db.comments.createIndex({ postId: 1, createdAt: -1 });
db.comments.createIndex({ userId: 1, createdAt: -1 });   // "my comments"

// users — REFERENCED: shared across posts and comments, updated
// independently, and a first-class entity in its own right
{ _id: ObjectId("u1"), name: "Amara Okafor", email: "…", bio: "…" }

// Note that this schema is neither fully embedded nor fully normalised.
// Each relationship was decided on its own, by the question at the top of
// this chapter — and that is what good document modelling looks like.

The short version

  1. The question is "is this read and written as part of the parent, or independently of it?"
  2. Embed for bounded, always-together, meaningless-alone data. Reference for unbounded, independently-queried, or shared.
  3. Be honest about "bounded". If nothing enforces a limit, the array will grow — bound it in validation or reference.
  4. Duplication is a deliberate trade, and only legitimate with a plan for consistency — or a decision that the copy is historical.
  5. Most extended references are historical records, not caches. Say so in the field name.
  6. There are no foreign keys. Orphans are your problem to prevent or tolerate.
  7. A growing array means rewriting the whole document every time. Use buckets or $slice.
  8. Decide each relationship separately. Neither "embed everything" nor a relational transplant is a schema.
