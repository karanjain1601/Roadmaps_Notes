Chapter 09 · Making it fast

Performance patterns

Once the indexes are right, performance is mostly one question: does the data you touch fit in memory? Everything else in this chapter is either a way of making the answer yes, or a way of noticing that the problem is not the database at all.

working set wiredtiger cache antipatterns not the database

The working set

Not the size of your data — the size of the part you actually touch, plus the indexes you touch it through. When that fits in the WiredTiger cache, reads are memory reads. When it does not, every miss is a disk seek, and performance falls off a cliff rather than degrading smoothly.

Does it fit? The cliff is sharp. A few percent past it, latency changes by orders of magnitude.

measuring it
db.serverStatus().wiredTiger.cache;
//   "maximum bytes configured"                       the cache size
//   "bytes currently in the cache"                   how full
//   "tracked dirty bytes in the cache"               awaiting write
//   "pages read into cache"                          cumulative misses
//   "unmodified pages evicted"                       pressure indicator

// The cache defaults to 50% of RAM minus 1 GB. The other half is left to the
// filesystem cache, which also holds compressed copies of the same pages —
// so the effective total is larger than the cache figure suggests.

db.stats();                     // dataSize, storageSize, indexSize
db.orders.stats().wiredTiger;   // per collection, including compression

// The number that actually tells you: how often a read had to go to disk.
db.serverStatus().wiredTiger["cache"]["pages read into cache"];
// Rising steadily under steady load means the working set does not fit.

// Compression matters here. WiredTiger uses snappy by default and typically
// gets 2-4x on real documents, so 200 GB of logical data may be 60 GB on
// disk — and the cache holds UNCOMPRESSED pages, while the filesystem cache
// holds compressed ones. Measure storageSize, not the size of your JSON.
The fix is usually to shrink the working set, not to add RAM

Adding memory works and it is linear in cost and finite in ceiling. Shrinking what you touch is often free and frequently larger: project fewer fields so a listing endpoint does not pull 200 KB documents to display three lines; cover the hot query so it reads index pages instead of documents (chapter 8); bucket or archive cold data so old rows stop competing for cache; drop unused indexes, which occupy the same cache as documents. A collection where 5% is hot behaves like a small collection — right up until a full scan pulls all of it through the cache and evicts everything useful.

Document size

every read pays for the whole document
// A product document with a 180 KB description and 40 embedded reviews
// costs 180 KB of cache and 180 KB of transfer EVERY time it is read,
// including on the listing page that shows a name and a price.

// Projection helps the transfer and not the cache — the whole document is
// still read into memory to project from:
db.products.find({ category: c }, { name: 1, price: 1, thumb: 1 });

// A COVERED query avoids the document entirely (chapter 8):
db.products.createIndex({ category: 1, popularity: -1, name: 1, price: 1 });
db.products.find({ category: c }, { name: 1, price: 1, _id: 0 })
           .sort({ popularity: -1 });

// Or split the document, which is chapter 2's argument arriving as a
// performance problem: the hot fields in one collection, the cold bulk in
// another, fetched only when someone opens the detail page.

// Finding the offenders:
db.products.aggregate([
  { $project: { size: { $bsonSize: "$$ROOT" }, name: 1 } },
  { $sort: { size: -1 } }, { $limit: 20 }
]);
db.products.aggregate([
  { $group: { _id: null, avg: { $avg: { $bsonSize: "$$ROOT" } },
                         max: { $max: { $bsonSize: "$$ROOT" } } } }
]);
// A max far above the average is chapter 3's outlier pattern telling you it
// is needed.

Document growth

why a growing array is quadratic
// WiredTiger does not update in place. A document that grows is written out
// again in full — so appending one element to an array of N costs O(N).
// Over the document's lifetime that is O(N²) of writes.

db.devices.updateOne({ _id: id },
  { $push: { readings: { t: now, v: 21.4 } } });   // slower every hour

// At 100 readings the document is 4 KB and a push writes 4 KB.
// At 100,000 readings it is 4 MB and a push writes 4 MB.
// The rate did not change; the cost went up 1000x.

// It also churns the cache: each rewrite dirties a large page, and dirty
// pages must be written before they can be evicted.

// The fixes, in order of preference:
//   1. BUCKET — a new document per period (chapter 3). The gold standard
//   2. Time-series collections, for genuine time-series
//   3. A bounded array with $slice, when you only need the recent N
//   4. A separate collection with a compound index, when you need all of it

// A quick check for collections suffering from this:
db.devices.aggregate([
  { $project: { n: { $size: { $ifNull: ["$readings", []] } } } },
  { $group: { _id: null, max: { $max: "$n" }, avg: { $avg: "$n" } } }
]);
// A max in the thousands and climbing is a modelling bug, not a tuning one.

The antipatterns

Unbounded arrays
The one above. Quadratic write cost, ending at the 16 MB limit. The commonest serious MongoDB performance problem, and it is a schema problem rather than a tuning one.
skip for pagination
Linear in the page number, and incorrect under concurrent writes. Keyset pagination is constant-time and correct (chapter 4).
Too many collections
One per tenant, per day, per user. Each carries metadata and at least one index in cache. Thousands of collections degrade startup, replication and memory. Use a field and an index.
Unbounded results
find({}).toArray() on a collection that grew. Always pair a query with a limit, or iterate the cursor.
Case-insensitive regex
{name: /amara/i} cannot use an index — the anchoring and case-sensitivity requirements from chapter 4. Use a collation index, or store a normalised field.
$lookup on the hot path
A nested loop per input document. Occasional joins are fine; a schema built on them is chapter 2's extended reference waiting to be applied.
Individual writes in a loop
A thousand round trips instead of one bulkWrite. Typically 10–50× slower, and the easiest win available (chapter 6).
Indexing every field
Every index is maintained on write and competes for cache. Index the access patterns, not the schema.
A single hot document
A global counter every write touches. Document-level concurrency means those writes serialise. Shard the counter or approximate it (chapter 3).

Connections

one client, one pool
// MongoDB drivers pool connections internally. Create ONE MongoClient per
// process and reuse it — creating a client per request is the classic
// serverless and framework mistake, and it produces connection storms.

const client = new MongoClient(uri, {
  maxPoolSize: 20,            // per client. Default 100, usually too high
  minPoolSize: 5,
  maxIdleTimeMS: 60000,
  waitQueueTimeoutMS: 5000,   // fail fast rather than queueing forever
  serverSelectionTimeoutMS: 5000,
  retryWrites: true,          // default. Keep it
  retryReads: true
});

// A connection is a thread on the server, not a process — much cheaper than
// PostgreSQL's model — but not free. maxPoolSize × instances is the number
// the server sees, and that multiplication is the thing that surprises
// people during an autoscale event.

db.serverStatus().connections;      // current, available, totalCreated
// totalCreated growing fast relative to current means connections are being
// churned rather than pooled — usually a client created per request.

// Atlas and most managed deployments cap connections by tier. Exceeding it
// produces connection errors that look like the database being down.

Frequently it is not the database

Before tuning MongoDB, rule out the two things that make it look guilty. The connection pool — if it is exhausted, every request queues and the symptom is total unavailability while the server sits nearly idle. The application's own work — an N+1 pattern issuing 200 queries per page request is 200 round trips of network latency that no index will fix, and the answer is one query or one $lookup rather than a faster individual query. Both present as "the database is slow" and neither is improved by touching the database.

Sensible defaults

  • One MongoClient per process, with maxPoolSize set deliberately rather than left at 100.
  • A limit on every query that could match a growing set, and maxTimeMS on anything serving a user request.
  • Projection on list endpoints. Do not transfer fields you will not render.
  • Keyset pagination, not skip.
  • bulkWrite with ordered: false for any batch of independent operations.
  • An index for each of your top queries, designed by ESR, and no others.
  • Bucket anything append-heavy before it becomes a problem, not after.
  • Watch document size and array length trends, not just query latency — those degrade first and silently.
Measure at production scale or do not bother

Every performance characteristic in this chapter is a function of size. A collection scan on 50,000 documents is 20 milliseconds and a missing index is undetectable; the working set always fits; a growing array is small; skip(1000) is instant. Development and CI datasets are typically three to five orders of magnitude smaller than production, which means almost none of these problems can be observed there — they are found by users. Keep a restored production-sized dataset available and run explain against it before shipping anything on a hot path.

The short version

  1. Performance is mostly one question: does the working set fit in the WiredTiger cache? The cliff is sharp.
  2. The cache defaults to 50% of RAM minus 1 GB, and holds uncompressed pages while the filesystem cache holds compressed ones.
  3. Shrinking the working set usually beats adding RAM — project less, cover the hot query, archive cold data, drop unused indexes.
  4. Every read pays for the whole document, so large documents cost cache even when you project.
  5. A growing array is quadratic. Bucket it.
  6. One MongoClient per process. A client per request is the classic serverless failure.
  7. Sort the slow query log by total time, not average.
  8. None of these problems are visible at development scale. Test against production-sized data.
