# mongodump — fine below ~100 GB, painful above it
mongodump --uri="mongodb://…/?replicaSet=rs0" \
  --readPreference=secondary \
  --oplog \
  --gzip --archive=/backup/shop-$(date +%F).gz

#   --oplog captures operations occurring DURING the dump, so the restore is
#   consistent. Without it, a dump of a live database is a smear across time:
#   collection A as of 02:00, collection B as of 02:40, and any change
#   between them may be half-captured.
mongorestore --oplogReplay --gzip --archive=/backup/shop-2026-03-14.gz

# FILESYSTEM SNAPSHOT — the usual answer for anything large.
#   * take it on a HIDDEN secondary, so the primary is untouched
#   * journal and data files MUST be in the same snapshot. If pg_wal's
#     equivalent — the journal directory — is on a separate volume snapshotted
#     a moment later, the result may be unrecoverable
#   * db.fsyncLock() flushes and blocks writes on that member if your
#     platform cannot snapshot atomically; db.fsyncUnlock() afterwards

# POINT IN TIME = snapshot + the oplog since. Restore the snapshot, then
# replay oplog entries up to the moment before the mistake. This is the only
# thing that undoes a bad deploy, and it depends entirely on the oplog window
# (chapter 10) covering the gap between snapshots.

# SHARDED CLUSTERS need coordination: snapshots of every shard plus the
# config servers, at a consistent cluster time, with the balancer stopped.
# Do not assemble this yourself — use Ops Manager, Atlas, or a tool built
# for it. A naive per-shard backup restores to an inconsistent cluster.
A replica set is not a backup

It replicates the deleteMany with the wrong filter within a second, faithfully, to every member. It protects against a machine failing and nothing else. This needs saying because MongoDB's replication is good enough that teams treat three members as their durability story and discover otherwise during an incident. Keep real backups, keep a delayed hidden member for the fast recovery from human error (chapter 10), and — the part that actually matters — restore from a backup on a schedule and time it. The restore duration is your real recovery objective, whatever the runbook claims, and it grows with the database.

Upgrades

rolling, one minor version at a time
# MongoDB upgrades are rolling and generally undramatic, with one concept
# you must understand: the FEATURE COMPATIBILITY VERSION.

db.adminCommand({ getParameter: 1, featureCompatibilityVersion: 1 });

# The FCV gates features that change the on-disk or wire format. After
# upgrading binaries to 7.0, the cluster still behaves as 6.0 until you
# raise the FCV — and while the FCV is still 6.0, you can DOWNGRADE the
# binaries safely. Once raised, you cannot.
#
# That is the whole safety mechanism: upgrade binaries, run for a week,
# then commit.

# The procedure, for a replica set:
#   1. check the release notes for your version jump
#   2. upgrade each SECONDARY: stop, replace binaries, start, wait for
#      SECONDARY state and zero lag
#   3. rs.stepDown() on the primary — a clean handover
#   4. upgrade the former primary
#   5. run for a week on the new binaries at the OLD FCV
#   6. db.adminCommand({ setFeatureCompatibilityVersion: "7.0" })

# ONE MAJOR VERSION AT A TIME. 5.0 -> 7.0 is not supported directly; you go
# through 6.0, raising the FCV at each step. Skipping is the commonest
# upgrade planning error, and it doubles the timeline people budgeted.

# Sharded clusters: config servers first, then shards, then mongos. Stop the
# balancer for the duration.

# Also check: driver compatibility. An old driver against a new server
# usually works; the reverse frequently does not.

//   read: ns, op, secs_running, planSummary, waitingForLock

// 4. Cache and disk.

// Keep these in a file. Reconstructing them during an incident is not a
// skill worth developing, and mongosh history is not a runbook.

db.killOp(opid);      // stop one operation. Read the query first
Ask whether it is the database at all

Two things make MongoDB look guilty when it is not. The connection pool — if it is exhausted, every request queues and the symptom is total unavailability while the server sits nearly idle; the classic cause is a MongoClient created per request rather than per process (chapter 9). The application's own work — an N+1 pattern issuing two hundred queries per page is two hundred round trips of network latency, and no index makes that faster. Both present as "the database is slow", both are visible in db.serverStatus().connections and your application traces, and neither is improved by touching the database.

Reclaiming space

deletes do not shrink anything
// WiredTiger marks freed space reusable within its files. A collection that
// held 500 GB and now holds 50 still occupies 500 on disk.

db.orders.stats().wiredTiger["block-manager"]["file bytes available for reuse"];

// Options, in increasing disruption:
//   1. Do nothing. The space is reused by new data. Usually correct
//   2. compact — reclaims to the filesystem. Blocks operations on that
//      collection for the duration. Run on secondaries, then step down and
//      do the former primary
db.runCommand({ compact: "orders" });

//   3. RESYNC A SECONDARY — remove its data directory and let it do an
//      initial sync. The rebuilt files are compact, and the member is out
//      of the set while it happens. Rolling this around the members is the
//      standard way to reclaim space with no downtime

// PREVENTION is better in every case: TTL indexes for retention (chapter 7),
// or bucketing plus dropping whole collections (chapter 3). Dropping a
// collection returns its space immediately, where deleting its documents
// does not.

What to record before you need it

  • The twelve dashboard metrics as a time series, with at least a year of history.
  • The slow query log, aggregated by shape and sorted by total time — not average.
  • explain output for your critical queries, captured before every upgrade and major deploy.
  • Collection and index sizes weekly, so growth is a trend rather than a surprise.
  • Document size and array length distributions, which degrade silently before latency does.
  • Configuration in version control, so "what changed" has an answer.
  • Restore test duration, trended.
  • The oplog window, because it shrinks as write volume grows and nothing announces it.
The question you will be asked is "when did this start"

Nearly every serious investigation reduces to it, and answering requires history you were recording before anyone knew there was a problem. All of the above is cheap on a quiet afternoon and impossible to obtain retroactively. If you do one thing: aggregate the slow query log into a table on a schedule, keyed by query shape. With it, "which query changed behaviour on Tuesday" is one query against your own data; without it, it is a deploy log and guesswork.

The short version

  1. Snapshot plus oplog is the production backup. mongodump is for small databases and moving data.
  2. mongodump --oplog, or a dump of a live database is a smear across time.
  3. A replica set is not a backup. It replicates your mistakes within a second.
  4. The FCV is the upgrade safety mechanism — upgrade binaries, run a week, then commit. One major version at a time.
  5. Sharded backups need coordination. A naive per-shard snapshot restores to an inconsistent cluster.
  6. Deletes do not reclaim disk. Resync a secondary, or prevent it with TTL and collection drops.
  7. Check the pool and the application first — both look exactly like a slow database.
  8. Record history before you need it. "When did this start" is the question, and it cannot be answered retroactively.
