Chapter 06 · Working with data

Writing data

Every write to a single document is atomic — that is the guarantee the whole model is built on. Using it well means expressing changes as operators the server applies, rather than reading a document into your application and writing it back.

operators atomicity upsert bulk

Atomicity at the document

the guarantee, and what it does not cover
// This is ATOMIC. All four changes apply, or none do. No transaction needed,
// no other reader ever sees a half-applied state.
db.orders.updateOne(
  { _id: id, status: "pending" },
  { $set:  { status: "paid", paidAt: new Date() },
    $inc:  { version: 1 },
    $push: { events: { type: "payment", at: new Date() } } }
);

// This is NOT atomic — two documents, two operations.
db.orders.updateOne({ _id: orderId }, { $set: { status: "paid" } });
db.accounts.updateOne({ _id: accId }, { $inc: { balance: -100 } });
// Between them, a crash leaves the order paid and the account unbilled.
// That needs a transaction (chapter 12) — or a schema where both facts
// live in one document (chapters 2 and 3).

// The design consequence, stated once: the more your invariants fit inside a
// single document, the less you need transactions. That is not a workaround;
// it is the point of the document model, and it is why chapter 2 matters
// more than this chapter does.

Never read-modify-write

Fetching a document, changing a value in your application and writing the whole thing back is the pattern to eliminate. Between the read and the write, another process can change the same document — and your write silently overwrites their change with a value computed from stale data. It is the lost update from the SQL unit's chapter 10, in a system where you may not have a transaction to fall back on. Express the change as an operator and the server applies it atomically to whatever the current state is: $inc rather than read-add-write, $push rather than read-append-write, $min rather than read-compare-write.

Upserts

insert or update, atomically
db.counters.updateOne(
  { device: "d-41", hour: hourStart },      // the filter identifies it
  { $inc: { count: 1, sum: value },
    $setOnInsert: { createdAt: new Date() } },
  { upsert: true }
);

// If nothing matches, MongoDB builds a document from the FILTER's equality
// fields plus the update operators, and inserts it. So the document above
// gets device and hour from the filter — you do not repeat them.
//
// $setOnInsert applies only on the insert path, which is how createdAt gets
// set once and never touched again.

// THE THING THAT MATTERS: an upsert is only race-free if a UNIQUE INDEX
// covers the filter fields. Without one, two concurrent upserts can both
// find nothing and both insert, and you get duplicates.
db.counters.createIndex({ device: 1, hour: 1 }, { unique: true });

// With the unique index, one of the two racing inserts fails with a
// duplicate key error (code 11000) — RETRY it and the second attempt
// updates the row the first one created. That retry is not optional; it is
// part of the pattern.
try {
  await coll.updateOne(filter, update, { upsert: true });
} catch (e) {
  if (e.code === 11000) await coll.updateOne(filter, update, { upsert: true });
  else throw e;
}

// This is exactly the SQL unit's chapter 9 argument about ON CONFLICT: an
// upsert without the unique index is a race condition wearing a costume.

findAndModify

when you need the document back
// Atomically update AND return the document — before or after the change.
const claimed = await db.jobs.findOneAndUpdate(
  { status: "pending", runAfter: { $lte: new Date() } },
  { $set: { status: "running", claimedAt: new Date(), worker: workerId } },
  { sort: { runAfter: 1 }, returnDocument: "after" }
);

// This is a WORK QUEUE, and it is correct: the find and the update are one
// atomic operation, so two workers cannot claim the same job. The document
// model gives you this without SELECT ... FOR UPDATE SKIP LOCKED — the
// atomicity is already at the right granularity.

// OPTIMISTIC CONCURRENCY, when the change genuinely must be computed in the
// application — a state machine, a complex validation:
const doc = await coll.findOne({ _id: id });
const next = computeNextState(doc);
const res = await coll.updateOne(
  { _id: id, version: doc.version },              // the guard
  { $set: { ...next, version: doc.version + 1 } }
);
if (res.matchedCount === 0) {
  // someone else changed it — re-read and retry, do not overwrite
}

// The version field turns a read-modify-write into a safe operation: the
// update applies only if nothing changed underneath. Check matchedCount, and
// retry rather than ignoring it. Ignoring it is the lost update again.

Bulk writes

one round trip instead of a thousand
await db.orders.bulkWrite([
  { insertOne: { document: { … } } },
  { updateOne: { filter: { _id: a }, update: { $set: { status: "shipped" } } } },
  { updateMany: { filter: { batch: 7 }, update: { $inc: { attempts: 1 } } } },
  { deleteOne: { filter: { _id: b } } },
  { replaceOne: { filter: { _id: c }, replacement: { … }, upsert: true } }
], { ordered: false });

//   ordered: true  (default) — sequential; STOPS at the first error
//   ordered: false           — may run in parallel; continues past errors
//                              and reports them all at the end
//
// Use ordered: false for independent operations — it is substantially faster
// and one bad document does not abandon the rest of the batch. Use the
// default when later operations depend on earlier ones.

// A bulk write is NOT a transaction. Individual operations are each atomic;
// the batch as a whole is not, and a failure halfway leaves earlier
// operations applied.

// Batch size: a few hundred to a few thousand. The wire limit is 100,000
// operations or 16 MB per batch, and much smaller batches are usually better
// for memory and for not holding up replication.
for (const chunk of chunks(items, 1000)) {
  await coll.bulkWrite(chunk.map(toOperation), { ordered: false });
}

// A thousand individual updateOne calls is a thousand network round trips.
// The same work as bulkWrite is typically 10-50x faster, and this is the
// single most common easy performance win in a MongoDB application.

Update pipelines

since 4.2, an update can be an aggregation
// Set a field from OTHER fields of the same document — impossible with
// plain operators, and previously required reading the document first.
db.orders.updateMany({}, [
  { $set: {
      total: { $sum: { $map: {
        input: "$items", as: "i",
        in: { $multiply: ["$$i.qty", "$$i.price"] }
      } } },
      updatedAt: "$$NOW"
  } }
]);

// Conditional logic in a single atomic write:
db.accounts.updateOne({ _id: id }, [
  { $set: {
      tier: { $switch: { branches: [
        { case: { $gte: ["$spend", 10000] }, then: "gold"   },
        { case: { $gte: ["$spend", 1000]  }, then: "silver" }
      ], default: "bronze" } }
  } }
]);

// Only $addFields/$set, $project/$unset, $replaceRoot/$replaceWith are
// allowed — no $lookup, no $group. Still, this removes most of the remaining
// reasons to read a document before writing it, which is the point.
replaceOne and a document without operators are the same trap

updateOne(filter, {status: "paid"}) — with no $set — does not set the status. It replaces the entire document with {_id, status: "paid"}, discarding every other field. Modern drivers reject an update document with no operators, which is a relief, but replaceOne does exactly this by design and is occasionally reached for by mistake. The same hazard appears in ORMs that read a document, mutate the object and call replaceOne to save it: any field added by another process between the read and the write is silently destroyed. Use operators.

What a write returns

check it, because silence is not success
const res = await db.orders.updateOne(
  { _id: id, status: "pending" },
  { $set: { status: "paid" } }
);

res.matchedCount    // 0 means the FILTER matched nothing — the document does
                    // not exist, or its status was not "pending". This is
                    // usually the interesting case and it is not an error
res.modifiedCount   // 0 with matchedCount 1 means it matched and the values
                    // were already what you set. Also not an error
res.upsertedId      // present if an upsert inserted

// A conditional update that matches nothing is how you detect a state
// transition that was not valid — and it is silent unless you check.
if (res.matchedCount === 0) {
  throw new ConflictError("order was not pending");
}

// deleteMany and updateMany with a filter that matches nothing also succeed
// quietly. A migration that "ran fine" and changed nothing is the classic
// version of this (chapter 17) — always assert the count.

Deleting

and why it does not free space
db.orders.deleteOne({ _id: id });
db.orders.deleteMany({ status: "cancelled", placedAt: { $lt: cutoff } });

// deleteMany over millions of documents is slow, generates a lot of oplog,
// and does NOT return space to the filesystem — WiredTiger marks the space
// reusable within its files, exactly like the PostgreSQL unit's chapter 3.
// The collection on disk stays the same size.
//
// db.runCommand({ compact: "orders" });   // reclaims it. Blocks writes on
//                                         // that collection. Consider
//                                         // resyncing a secondary instead.

// TTL INDEXES — the right answer for anything with a retention policy.
// A background thread deletes expired documents automatically.
db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 });
db.events.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
//   the second form uses the DATE IN THE FIELD as the expiry time

// The TTL thread runs every 60 seconds, so deletion is approximate — a
// document may survive up to a minute past its expiry, more under load.
// Fine for sessions and caches; not a security control.

// And for genuine time-series or high-volume append data, chapter 3's
// bucketing plus dropping whole collections beats deleting documents
// entirely — the same argument as partitioning in the PostgreSQL unit.
Idempotency, since retries are inevitable

A network failure between the server applying a write and your driver receiving the acknowledgement is indistinguishable from the write never happening. The driver retries — MongoDB's retryable writes do this automatically for single-document operations — and your write may therefore apply twice. Operators differ: $set is naturally idempotent, $inc and $push are not. Where it matters, make the operation idempotent by construction: a conditional filter that only matches once ({status: "pending"}), a unique index on a client-supplied key, or $addToSet instead of $push. This is the SQL unit's chapter 9 argument, and it applies with more force here because the retry is automatic.

The short version

  1. A write to one document is atomic, however many fields it changes. Across documents it is not.
  2. Never read-modify-write. Express the change as an operator the server applies to current state.
  3. An upsert without a unique index on the filter fields is a race condition. Add the index and retry on error 11000.
  4. findOneAndUpdate gives you an atomic claim — a correct work queue with no extra machinery.
  5. When the change must be computed in the application, use a version guard and check matchedCount.
  6. bulkWrite with ordered: false is the easiest large performance win in most MongoDB applications.
  7. replaceOne discards every field you did not include. Use operators.
  8. Deletes do not return space, and retries are automatic — so make writes idempotent by construction.
