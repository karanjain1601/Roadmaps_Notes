Reshaping and joining

The most common way a wrong number reaches a decision is a join that duplicated rows. It produces no error, the query runs, the total is simply too big — and nothing in the output indicates that anything happened.

Grain is the single most useful concept in this chapter

The grain of a table is what one row represents: one order, one line item, one customer-day, one event. A join between tables of different grain changes the grain of the result to the finer of the two, and every aggregate written afterwards is computed at that new grain whether you intended it or not. That is the whole mechanism of fan-out: joining orders (one row per order) to line items (several rows per order) gives you a table at line-item grain, in which the order total appears several times, and summing it counts the same money repeatedly. State the grain of every table you touch and the grain you want in the answer. If they differ, you need an aggregation step, not a join.

the three-line check that prevents nearly all of it
Before joining, establish that the right-hand table is unique on the key.
This is the whole discipline, and it takes ten seconds.

  -- is the right-hand side unique on the join key?
  SELECT COUNT(*), COUNT(DISTINCT order_id) FROM line_items;
  -- 6 and 3 -> NOT unique. A join here will fan out.

  -- and after any join:
  SELECT COUNT(*) FROM result;              -- did the count change?
  SELECT COUNT(DISTINCT order_id) FROM result;   -- did the population?

IF THE COUNTS DIVERGE, you have one of two situations and they need
different fixes:

  YOU WANTED THE FINER GRAIN — you are analysing line items. Fine, and
  every aggregate must now be computed at line-item grain. Do not sum
  order_total; sum item_total.

  YOU WANTED ORDER GRAIN — aggregate the right-hand table first, then
  join to a table that is already unique:

    WITH item_agg AS (
      SELECT order_id, COUNT(*) AS n_items, SUM(item_total) AS items_total
      FROM line_items GROUP BY order_id
    )
    SELECT o.*, i.n_items, i.items_total
    FROM orders o LEFT JOIN item_agg i USING (order_id);

  Now the right side is unique on order_id, no fan-out is possible, and
  SUM(order_total) is correct.

THE HABIT WORTH FORMING: aggregate to the target grain BEFORE joining,
every time. It costs a CTE and it makes the fan-out class structurally
impossible rather than something you check for.
SELECT DISTINCT is not a fix for fan-out

It is the reflex, and it does two bad things. When the duplicated rows are genuinely identical, deduplicating them appears to work — and if there was any legitimate repetition in the data, that repetition is now destroyed too, invisibly (chapter 4). When the rows differ in any column, DISTINCT does not deduplicate them at all: the join brought different item names or prices, so each row is unique, and the sum stays inflated while the query looks like it has been fixed. The second case is worse because it produces a wrong number with a plausible-looking remedy applied, which is much harder to catch in review than an obviously wrong number. Fix the grain, not the symptom — aggregate before joining, or select at the finer grain deliberately.

Long and wide

and which one you actually want
WIDE — one row per entity, one column per measure or period:

  customer   jan    feb    mar
  A          120    140    90
  B          80     85     95

  Good for: reading, presenting, spreadsheets, a report someone signs off.
  Bad for: adding a period (schema change), filtering by period, grouping.

LONG — one row per entity-measure-period:

  customer   month   value
  A          jan     120
  A          feb     140
  ...

  Good for: everything computational — grouping, filtering, joining,
  plotting, adding periods without touching the schema.
  Bad for: reading. Nobody wants a report in this shape.

THE RULE: analyse in long, present in wide. Reshape at the last step.

Analysts who fight their tools are usually working wide when they should
be long — the tell is writing the same expression once per column, or a
formula that has to be extended every month.

TWO THINGS THAT GO WRONG IN THE RESHAPE:

  PIVOTING LOSES ROWS SILENTLY. If a customer has no March value, wide
  gives you a null and long simply has no row. Which is correct depends on
  whether the absence means zero or unknown (chapter 4) — and a pivot with
  a default of 0 has just made that decision for you.

  UNPIVOTING CREATES SPURIOUS ROWS. Melting a wide table with nulls gives
  you rows whose value is null, which then get counted. Drop them
  deliberately, or keep them deliberately, and know which you did.
Reconcile the total after every reshape

Sum the measure before the operation and after it. If it changed and you did not intend it to, stop. This one check catches fan-out, dropped rows from an inner join, nulls introduced by a pivot, and rows lost in an unpivot — the entire error class in this chapter, with a single number. It works because almost every reshaping operation should be total-preserving, and the ones that are not are ones you chose deliberately, so any unexplained change is a bug by definition. Build it into how you work rather than treating it as a review step: a one-line assertion after each join in a notebook, or a `HAVING` clause comparing a control total in SQL. It is the cheapest quality control available in analytics and it is skipped almost universally.

The short version

  1. Grain is what one row represents. A join changes the grain to the finer of the two tables.
  2. Fan-out produces no error. The query runs, the total is too big, and nothing indicates it happened.
  3. Check COUNT(*) against COUNT(DISTINCT key) on the right-hand table before joining.
  4. Aggregate to the target grain before joining. This makes fan-out structurally impossible.
  5. DISTINCT does not fix fan-out — and when rows differ it does nothing while appearing to.
  6. Nulls do not match each other. Rows with a null join key vanish from an inner join.
  7. Analyse long, present wide. Fighting your tool usually means working in the wrong shape.
  8. Reconcile the total after every reshape. One number catches the whole error class.
