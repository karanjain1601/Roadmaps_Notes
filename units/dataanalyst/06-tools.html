Excel, SQL or Python

The tool argument is usually the wrong argument. Each of the three is clearly best at something, and the useful skill is recognising the moment you have stopped using a tool and started fighting it — because that moment has recognisable signs.

The signs you are fighting the tool

Each tool fails in a characteristic way, and the signs are specific enough to act on. In a spreadsheet: you are writing the same formula once per column, extending ranges by hand each month, or you have a sheet nobody else can safely open. In SQL: you have five levels of nested subquery, you are reaching for a window function to do something a loop would do in three lines, or you want to iterate. In Python or R: you are reimplementing a join, pulling a million rows into memory to compute a group-by the database could have done, or writing a script for something one query answers. The correct response is almost never to get better at the fight. It is to move the operation to the tool that does it natively — and the boundary is usually clean: filter and aggregate in the warehouse, analyse in a notebook, present in a spreadsheet.

the division of labour that works
PUSH FILTERING AND AGGREGATION DOWN TO THE DATABASE. Always. It is what
databases are for, it avoids moving data you will discard, and it is the
difference between a query that returns in seconds and a notebook that
runs out of memory.

  bad   SELECT * FROM events;          -- then filter in pandas
  good  SELECT day, COUNT(*) FROM events
        WHERE day >= '2026-01-01' GROUP BY day;

BRING BACK THE SMALLEST TABLE THAT ANSWERS THE QUESTION. An aggregate is
usually thousands of rows, not millions, and thousands of rows fits
comfortably anywhere.

THEN ANALYSE IN A NOTEBOOK. Statistics, intervals, plots, sensitivity
checks — the things SQL is bad at and Python and R are built for.

PRESENT WHEREVER THE AUDIENCE LIVES. That is frequently a spreadsheet, and
that is fine: a small, clean, final table in a format people can open
beats a beautiful notebook nobody runs.

THE ONE THING TO AVOID: analysis whose logic is split across all three
with no record of the order. A query someone ran, pasted into a sheet,
manually adjusted, then charted, is unreproducible and — more
importantly — unauditable when the number is questioned. If the pipeline
crosses tools, the SQL belongs in a file, in version control, next to the
notebook that consumes it.

AND THE PRACTICAL FLOOR: know enough SQL to be independent. An analyst
who cannot get their own data is bottlenecked on someone else's queue for
every question, and that constraint shapes what they will even attempt.
Spreadsheet errors are a documented, serious category

Studies of production spreadsheets consistently find errors in a large majority of them, and the failures have real history: a widely-cited economics paper whose conclusions changed when a range error was found; a public-health data loss where a legacy row limit silently truncated case records. The problem is not that people are careless. It is that spreadsheets make errors invisible — a formula that skips a row looks identical to one that does not, a range that failed to extend produces a plausible number, and there is no test, no diff and no review path. Two habits that help disproportionately: never mix inputs, calculations and outputs on one sheet, and keep a control total that you can reconcile against a known figure (chapter 5). If a spreadsheet's output matters to a decision that recurs, that is the signal to move the logic into a query or a script where it can be reviewed.

What to learn, in order

the return on each
1. SQL TO THE POINT OF INDEPENDENCE. Joins, GROUP BY, HAVING, CTEs,
   window functions, and date handling. This is the highest-return skill
   in the job because it removes your dependency on someone else's queue
   and it is where most analytical work actually happens. The SQL unit
   covers it properly.

2. SPREADSHEET FLUENCY. Pivot tables, lookups, and enough discipline to
   keep inputs separate from calculations. Underrated by technical
   analysts, and it is the medium most of your audience thinks in.

3. ONE SCRIPTING LANGUAGE, PROPERLY. Python or R — the choice matters far
   less than the depth. Enough to reshape, join, compute an interval, fit
   a simple model and plot. The Python for Data Analysis unit covers the
   Python stack.

4. VERSION CONTROL. Enough git to keep your queries and notebooks in a
   repository. The step that converts your work from personal artefacts
   into something a team can rely on and audit.

5. YOUR ORGANISATION'S BI TOOL. Not glamorous, and it is where recurring
   reporting belongs, and knowing it well means you can stop hand-building
   the same monthly extract.

WHAT NOT TO PRIORITISE EARLY: distributed compute, a second language, or
a deep learning framework. Each is a real skill and none is what makes an
analyst effective, and reaching for them is often a sign of avoiding
chapters 2 and 18 — the scoping and the communicating, which are harder
and matter more.
Make the boring parts reproducible before making anything sophisticated

The single upgrade that improves an analyst's output most is not a new tool. It is that the query lives in a file rather than in a query editor's history, the notebook runs top to bottom without manual steps, and the output is produced by running something rather than by assembling it. That is what makes a number defensible three months later when someone asks how it was computed, and it converts a re-run from an afternoon of reconstruction into a keystroke — which in turn makes you willing to re-run it, which is what makes the sensitivity checks in chapter 4 actually happen. None of this requires engineering skill. A folder with a named SQL file, a notebook that reads it, and both in a repository covers most of the benefit.

The short version

  1. Each tool has characteristic failure signs. Repeating a formula per column, five nested subqueries, reimplementing a join.
  2. Push filtering and aggregation to the database, bring back the smallest table that answers the question.
  3. Analyse in a notebook, present where the audience lives. Frequently a spreadsheet, and that is fine.
  4. Avoid logic split across tools with no record of the order. Unreproducible, and unauditable when questioned.
  5. Spreadsheet errors are a documented category because spreadsheets make errors invisible — no test, no diff, no review.
  6. SQL to the point of independence is the highest-return skill, because it removes the dependency on someone else's queue.
  7. One scripting language properly beats two superficially. The choice matters less than the depth.
  8. Reproducible beats sophisticated. A query in a file and a notebook that runs top to bottom covers most of the benefit.
