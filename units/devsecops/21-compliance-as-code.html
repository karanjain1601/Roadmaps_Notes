Compliance as code

The Cyber Security unit covers frameworks, risk registers and what auditors want. This chapter is the engineering response: stop collecting evidence and start emitting it, so that being compliant and demonstrating it are the same activity rather than two.

The framing that makes this tractable

Most compliance requirements are restatements of things you should be doing anyway: access is restricted and reviewed, changes are approved, systems are patched, logs are retained, data is encrypted, backups are tested. If those are implemented as mechanisms — a policy engine, an admission controller, a pipeline, an identity provider — then each one is already producing a record every time it runs. The audit problem is not gathering evidence, it is that the mechanisms exist and nobody wired their output to the control they satisfy. That wiring is a few days of work per framework and it removes an annual scramble permanently.

21.3What it costs, and what it saves

Evidence collection, manual against generated

The build cost is real and paid once. The collection cost is paid every cycle, forever.

Overlap is the reason this pays so well

Organisations report against several frameworks and treat each as a separate programme, which is how a hundred controls becomes four hundred pieces of work. In reality the frameworks overlap heavily — access control, change management, logging, encryption, vulnerability management and incident response appear in all of them, phrased differently. So the correct structure is a single internal control set, each control implemented once and evidenced once, with a mapping table saying which external requirement each one satisfies. Adding a framework then becomes a mapping exercise of days rather than an implementation programme of months, and the residue — the genuinely framework-specific requirements — is usually a small fraction. Getting this structure right before the second framework arrives is one of the highest-leverage decisions available to a compliance programme.

21.5The audit itself

Making it short 
GIVE THEM THE GENERATOR, NOT THE OUTPUT
  An auditor's job is to be satisfied the control operates.
  A folder of screenshots demonstrates that someone took
  screenshots. A query they can watch you run, against the
  live system, answers the question directly — and it
  answers the follow-up questions too, which is where the
  time normally goes.

SAMPLING BECOMES POPULATION TESTING
  Manual evidence forces sampling: the auditor checks 25 of
  4,000 changes. Generated evidence covers all 4,000, which
  is a stronger assurance statement and less work for both
  sides. Auditors generally like this once they trust the
  generator, so expect to spend the first cycle
  demonstrating the generator itself.

EXCEPTIONS ARE NOT FAILURES
  A control with 14 documented, owned, expiring exceptions
  reads as managed. The same control with an unknown number
  of undocumented deviations reads as broken. Enumerate
  them.                                             → ch 10

WHAT ACTUALLY GOES WRONG IN AUDITS
  Not the sophisticated controls. It is: an asset inventory
  that does not match reality, leavers who still have
  access, an exception with no expiry that is three years
  old, and a control that was implemented and then quietly
  stopped running. Every one of those is caught by
  continuous checking and missed by an annual scramble.
Why is generated evidence stronger than a screenshot, and not just cheaper?

Because it answers a different and better question. A screenshot demonstrates that the control was in the desired state at one moment, on one system, as observed by someone with an interest in the outcome — and it says nothing about the other three hundred and sixty-four days, the other forty systems, or whether it was configured specially for the screenshot. Generated evidence is a query against the live system, run repeatedly on a schedule and retained, so it establishes that the control was in effect continuously and everywhere. That converts the assurance statement from a point-in-time sample to a population test, which is strictly stronger. Three consequences follow. Sampling disappears: an auditor testing manual evidence checks perhaps twenty-five of four thousand changes and extrapolates, whereas a generated check covers all four thousand — better assurance and less work for both parties. Drift is caught in a day rather than a year: the failure that hurts is not a control you never built, it is one you built and that quietly stopped running, and only continuous checking notices that. And the evidence is harder to dispute, because the auditor can watch you run the query and can ask a follow-up question that gets answered in the room rather than in a two-week evidence request. There is a real cost to be honest about: the first audit cycle involves demonstrating the generator — showing the query is correct, covers the full population and cannot be selectively run — and that takes effort. It is paid once, and after it, adding a framework becomes a mapping exercise instead of another evidence-collection programme.

Which controls genuinely cannot be evidenced automatically?

Fewer than people assume, and the residue is real and worth naming in advance so nobody wastes effort trying. Three categories. Things about people rather than systems — that staff completed training, that a background check was performed, that the security team is adequately resourced, that responsibilities are appropriately segregated. Parts of these can be pulled from an HR or learning system, so the evidence is at least generated from a record rather than assembled by hand, but the underlying facts are administrative. Judgement and design — that a risk assessment was performed and was reasonable, that a threat model considered the right threats, that an architecture is appropriate to the sensitivity of the data. You can automate evidence that the activity happened — a threat model document exists in the repository, updated within the last year, reviewed by two people — which is usually what the requirement actually asks for, while the quality remains a matter of professional opinion. And physical and third-party matters — data centre access, a supplier's own controls — where the honest answer is that you inherit someone else's attestation and your control is that you obtained it, read it, and checked it covers what you rely on. Two useful moves for the residue: automate the metadata even where you cannot automate the substance, since "this review happened, on this date, by these people" is mechanical and is often the whole requirement; and keep the genuinely manual items on a short explicit list with owners and dates, because a small enumerated set of manual controls is manageable, whereas an unbounded one silently becomes the annual scramble again.

Your organisation is adding a second compliance framework. What should you do first?

Build a single internal control set with a mapping table, before implementing anything for the new framework. The failure to avoid is treating each framework as its own programme, which produces duplicated controls, duplicated evidence, duplicated tooling and two teams doing the same work in different vocabularies — and it scales linearly with frameworks, so the third and fourth are as expensive as the second. The frameworks overlap heavily by construction, because they are all describing the same small set of security ideas: restrict and review access, approve and record changes, patch things, retain logs, encrypt data, test backups, respond to incidents. So the structure that works is one control per mechanism you actually operate, implemented once, evidenced once, with a table recording which external requirement each satisfies. Adding a framework then means walking its requirement list, ticking the ones your existing controls already cover, and implementing only the genuine residue — which in most pairings is a modest fraction. Three practical notes. Do the mapping from your controls outward rather than from the framework inward, or you will end up with a control set shaped by whichever framework you started with and awkward for the next one. Keep the mapping in version control next to the control definitions, so it changes when they do rather than becoming a stale spreadsheet. And use the exercise to cut scope before you add controls — isolating regulated data into its own accounts, or not holding it at all, removes requirements entirely and is almost always cheaper than satisfying them across a wider estate.

Recap

  1. Most requirements restate things you should already do. The gap is wiring mechanism output to the control.
  2. A control is a rule that runs, not a paragraph in a document.
  3. Generated evidence turns sampling into population testing, which is stronger as well as cheaper.
  4. Drift is caught the day it happens rather than at the next audit, or never.
  5. One internal control set, mapped outward to frameworks. Adding a framework becomes days, not months.
  6. Do the mapping from your controls outward, or the set is shaped by whichever framework came first.
  7. Cutting scope beats complying more broadly. Data you do not hold needs no controls.
  8. Give the auditor the generator, not the output — and expect the first cycle to be about the generator.
  9. Enumerated, expiring exceptions read as managed; unknown deviations read as broken.
  10. Automate the metadata even where the substance is human — "this happened, on this date, by these people".
