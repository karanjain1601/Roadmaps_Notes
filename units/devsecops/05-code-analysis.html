Finding flaws in code

Five categories of tool, each with a genuine speciality and a set of things it structurally cannot see. Choosing well matters less than understanding the gaps — and far less than the one operational decision, baselining, that determines whether any of it gets read.

The two questions that predict a tool's behaviour

Does it run the code? If not, it must guess at reachability and will over-report. If it does, it can only report what it exercised and will under-report. That single distinction explains most of the difference between SAST's false positives and DAST's false negatives, and it is not a quality problem either vendor can fix. Does it see the source? If yes, it can point at a line and a developer can act immediately; if no, someone has to translate a symptom into a location, which is most of the remediation cost. IAST scores well on both, which is why it is attractive, and it costs you an agent in the runtime and coverage limited by your tests.

5.2The triage problem, and baselining

Point a static analyser at an established codebase and it returns thousands of findings. What happens next decides whether the tool becomes useful or becomes a dashboard nobody opens — and the deciding factor is not the tool's accuracy.

Whole codebase, or only the diff?

The same scanner, the same accuracy, two operating models.

Baselining is not ignoring the backlog

Suppressing the existing findings so that only new ones are reported is the difference between a tool that changes behaviour and one that produces a number for a slide. It works because a finding attached to the change that introduced it arrives with an owner, context and a fast fix — while the same finding in a list of four thousand has none of those. The honest caveat is that the baseline is debt, not absolution: it must be recorded, sized, and worked down deliberately — a percentage per quarter, or opportunistically whenever a file is touched anyway. What must not happen is the baseline being created and then forgotten, at which point you have a tool that guarantees no new defects of a class while permanently ignoring several thousand existing ones.

Why does SAST produce so many false positives, and is that fixable?

Because it reasons about code without running it, and the missing information is exactly what determines whether a finding is real. A static analyser sees that data flows from a source to a dangerous sink and cannot generally know whether that path is reachable in practice, whether a framework sanitises in between, whether the configuration disables the feature, whether the input is actually attacker-controlled, or whether a validation function three layers up already made it safe. Answering those questions in general requires solving problems that are undecidable, so every analyser makes a trade: assume paths are reachable and over-report, or require proof and miss real defects. Most choose the first, because a missed vulnerability is a worse advertisement than a wasted hour. It is improvable rather than fixable. Better inter-procedural analysis, framework-aware rules that understand your web stack's sanitisers, and taint tracking that models your own validation helpers all raise precision substantially — which is why a tuned deployment behaves very differently from a default one, and why the tuning is the work rather than the installation. Custom rules matter more than most people expect, because your recurring defects are specific to your codebase and no vendor ships a rule for them. But the more important response is operational rather than technical: baseline the existing findings and report only new ones. That does not improve precision at all, and it changes the experience completely, because three findings attached to today's change arrive with an owner and context, while four thousand in a dashboard arrive with neither.

Your DAST scan is clean. What have you actually learned?

That the scanner did not demonstrate a vulnerability on the paths it reached — which is a much narrower claim than it sounds, because reaching paths is the hard part of dynamic testing. An unauthenticated crawler typically explores a small fraction of a real application: it cannot log in, so everything behind authentication is invisible; it cannot construct valid multi-step workflows, so anything past the first form is unreached; it does not know your API's shape unless you give it a specification; and single-page applications frequently defeat crawling entirely because the routes exist only in JavaScript. So a clean result may mean the application is sound, or it may mean the scanner saw a login page and a marketing site. Three things to check before treating it as reassurance. Coverage: how many distinct endpoints did it exercise, against how many your application actually has — most tools report this and almost nobody reads it. Authentication: was it logged in, did the session stay valid throughout, and did it test as more than one role, since cross-role authorisation flaws need at least two. Input: was it driven by an OpenAPI specification or a recorded session rather than by crawling, which is the single biggest improvement available. Also worth knowing what DAST structurally cannot find regardless of coverage: it has no view of the source, so it cannot see hardcoded secrets, insecure cryptographic choices, or vulnerable dependencies that are present but not reachable through the interface — and it cannot tell you where in the code a flaw it does find actually lives, which is most of the remediation cost.

Why is baselining more valuable than improving the scanner's accuracy?

Because it changes who receives the finding and when, and those determine whether anything happens — whereas accuracy only changes how many findings there are. Consider the arithmetic. A four-hundred-thousand-line codebase at a few findings per thousand lines yields well over a thousand results; at twelve minutes each that is months of triage before anyone fixes anything, so in practice nobody starts, the list becomes a permanent dashboard, and the tool's real contribution is zero regardless of its precision. Halving the false positive rate halves a number nobody was going to work through anyway. Baselining changes the unit of work: the existing findings are recorded as debt, and each pull request is compared against that baseline so it reports only what the change introduced — typically a handful, often zero. Those few arrive attached to the diff that caused them, in front of the person who wrote it, while they still have the context, and they can be fixed in minutes. That is the same tool with the same accuracy producing an entirely different outcome, and it is why baselining is usually the first thing to configure rather than a later refinement. Two things to get right. The baseline must be recorded as debt with a plan — a percentage per quarter, or fixing whatever is in a file you were touching anyway — because a baseline created and forgotten means permanently ignoring several thousand real issues. And the comparison should be by fingerprint rather than line number, or every refactor re-reports the whole file and the noise returns.

Recap

  1. Does it run the code, and does it see the source? Those two answers predict a tool's whole behaviour.
  2. SAST over-reports because it cannot know reachability; DAST under-reports because it only sees what it reached.
  3. IAST scores well on both at the cost of an agent and coverage limited by your tests.
  4. SCA has the best value per unit of effort, because most reported vulnerabilities are in dependencies.
  5. Baseline the existing findings and report only new ones. It matters more than accuracy.
  6. The baseline is debt, not absolution. Size it and work it down.
  7. Fingerprint findings rather than keying on line numbers, or refactors re-report everything.
  8. Fast and precise blocks; slow or noisy runs asynchronously and raises tickets.
  9. Trial on your own repositories. Benchmark scores are optimised against by vendors.
  10. No tool finds business logic or authorisation flaws — that is what Chapter 4's review questions are for.
