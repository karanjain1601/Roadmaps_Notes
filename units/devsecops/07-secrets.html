Secrets

The most common serious finding in most codebases, and the one with the shortest path from mistake to consequence. It is also the area where the technically correct answer — store them properly — solves less of the problem than people expect, because the hard parts are history, sprawl and rotation.

7.1Why this keeps happening

Not carelessness. Secrets leak because every reasonable-looking shortcut leads there, and because the failure is silent — a hardcoded credential works perfectly, passes every test, and gives no feedback that anything is wrong.

The permanence problem

A secret committed to Git is not removed by deleting it in a later commit — it remains in history, in every clone, in every fork, and in the caches of anything that mirrored the repository. Rewriting history removes it from your copy and not from anyone else's, and on a public repository it may already be in an archive or a dataset. So the only reliable response to a committed secret is to treat it as compromised and rotate it, and history rewriting is a tidiness measure that happens afterwards, if at all. This is why the pre-commit hook is worth more than every downstream control combined: it is the last point at which the problem is still cheap.

7.2The exposure window

Leak to detection to rotation

What matters is whether you close the window before someone uses it.

Public repositories are scraped continuously

Secret-hunting against public code hosting is automated and constant — researchers planting honeytokens have repeatedly measured cloud credentials being used within minutes of being pushed, sometimes under a minute. The commit does not need to be noticed by a human, does not need the repository to be popular, and deleting the commit shortly afterwards does not help because the scraper already has it. The practical consequence is that for a public repository the exposure window is effectively zero regardless of how good your detection is, so the only controls that matter are the ones that act before the push and the ones that make the credential worth little — short lifetimes and narrow scope.

Getting a secret into a running process 
ENVIRONMENT VARIABLES
  Ubiquitous, and leaky in specific ways: they appear in
  child processes, in crash dumps, in `/proc`, in container
  inspection output, and in any library that logs its
  environment on startup. Acceptable, with awareness.

FILES MOUNTED AT RUNTIME
  Better. Not inherited by child processes, permissions can
  be restricted, and the file can be updated in place when
  the secret rotates. Prefer tmpfs so it never touches disk.

FETCHED BY THE APPLICATION AT STARTUP
  The application authenticates to the secret manager itself
  using its workload identity, and holds the secret only in
  memory. Best, and it makes the secret manager a startup
  dependency you must plan for.

WHAT NOT TO DO
  · pass secrets as command-line arguments — visible in the
    process list to every user on the host
  · bake them into an image at build time — present in the
    layer history even if a later layer deletes the file
  · log the configuration object on startup, which is how
    most secrets reach a log aggregator

THE BOOTSTRAP QUESTION
  Every scheme needs one credential to obtain the others.
  The answer is to make that one thing not a secret: an
  instance identity document, an OIDC token from the CI
  provider, or a Kubernetes service account token — all
  attested by the platform rather than stored by you.

7.4Detection, and its false positives

Where secrets actually accumulate

Scanning the default branch covers one of these. The others are where the ones you have not found are.

On false positives: secret scanners fire on test fixtures, example values, base64 blobs, UUIDs and anything that looks high-entropy. The two things that make a scanner tolerable are verification — actually calling the provider to check whether the credential is live, which most modern scanners do for common formats and which collapses the false positive rate — and allow-listing by fingerprint rather than by file, so a known-fake test value stays suppressed when the file moves.

7.5When one leaks

The order matters, and the first step is not the obvious one 
1  ROTATE OR REVOKE. Immediately, before anything else.
   Not "investigate whether it was used" — the credential is
   compromised the moment it was exposed, and every minute
   spent establishing impact is a minute it still works.

2  ONLY THEN, work out what it could reach.
   Scope of the credential, what it had access to, and
   whether that access is itself audited.

3  CHECK WHETHER IT WAS USED.
   Provider audit logs, from before the leak as well as
   after — you need a baseline of normal use to spot
   abnormal use. Look for use from unfamiliar addresses,
   at unusual times, or for API calls this credential has
   never made.

4  FIND EVERY COPY.
   The same secret is usually in more places than the one
   you found: another repository, a CI variable, a
   colleague's laptop, a wiki page, an old image.

5  REMOVE IT FROM HISTORY — optional and last.
   Rewriting history is disruptive, does not reach clones
   or forks, and does not un-compromise anything. Do it for
   tidiness after the credential is dead, not as the fix.

6  ASK WHY THE CONTROL DID NOT FIRE.
   A leak that reached the default branch means the
   pre-commit hook was absent, bypassed or not installed
   on that machine — which is a fixable systemic thing,
   unlike the individual mistake.

THE PREPARATION THAT MAKES THIS SURVIVABLE
  Know, in advance, how to rotate each class of credential
  and what depends on it. The reason teams hesitate at
  step 1 is that they do not know what will break, and
  that hesitation is the whole exposure.
A secret was committed and removed in the next commit. Is that fine?

No — the secret must be treated as compromised and rotated, and the removal commit changes almost nothing. Git keeps the full history, so the value remains reachable by commit hash, it is in every clone anyone has taken, it is in every fork, and it may be in caches and mirrors you do not control. On a public repository it is very likely already collected: automated scraping of public code hosting is continuous, and honeytoken research has repeatedly measured cloud credentials being used within minutes of a push — the commit does not need to be noticed by a human or the repository to be popular. Even on a private repository, the exposure is to everyone with read access, which is usually a much larger group than the people who should hold that credential, plus anyone who has ever cloned it including former employees. So the correct sequence is the one in §7.5: rotate first, then investigate. Rewriting history with a filter tool is worth doing afterwards for tidiness and to stop the value being rediscovered by future scans, but it is not remediation — it does not reach other people's copies, and it will not un-use a credential someone already took. Two follow-ups matter as much as the rotation. Find every other copy, because the same value is usually also in a CI variable, a wiki page and an old image. And ask why the pre-commit hook did not fire, since a secret reaching the default branch means the control was absent, bypassed or not installed on that developer's machine — and that systemic gap will produce the next one.

You move every secret into a secret manager. What have you not fixed?

A good deal, and it is the right foundation. What it does not address falls into four groups. History and sprawl: the copies already in Git history, in old container layers, in CI variables, in tickets and in wikis are all still there, still valid unless you rotated them, and a secret manager does not go and find them — migrating to one without rotating everything you migrated just means the same live credentials now exist in two places. Rotation: central storage makes rotation possible and does not make it happen, and a manager full of five-year-old static credentials is a tidier version of the same risk. The step that genuinely changes the picture is moving to dynamic, short-lived credentials issued on demand, at which point there is no long-lived secret to leak. The bootstrap credential: every workload now needs something to authenticate to the manager with, and if that something is a static token in an environment variable you have concentrated the problem rather than solved it — the answer is platform-attested identity, an instance identity document, an OIDC token from the CI provider or a service account token, so the one credential that starts the chain is not stored anywhere. And runtime exposure: once fetched, the secret is in the process, so it can still reach a crash dump, a log line that prints the configuration, a child process's environment, or an error message returned to a user. Scrubbing at the point of logging and preferring mounted files over environment variables both address that, and neither is a property of the manager.

Why rotate before investigating?

Because investigation takes time during which the credential still works, and the investigation rarely changes the decision. The instinct is to establish whether the secret was actually used before causing disruption — but for anything exposed publicly the base rate of automated collection is high enough that "probably nobody took it" is not a defensible assumption, and for anything exposed privately the group with access is larger than the group who should have it. So you are almost certainly rotating anyway, and the only question is whether you do it now or after an hour of log analysis during which an attacker has a live credential. Rotate first, then investigate with the pressure off. The reason teams hesitate is worth naming because it is fixable: they do not know what will break. Nobody is sure which services use that database password, whether the API key is embedded in a mobile app that cannot be updated quickly, or whether rotating it takes down a batch job at 3am. That uncertainty is the real exposure, and it is preparation work rather than incident work — knowing, per class of credential, how to rotate it and what depends on it, ideally by having rotated it deliberately at some point when nothing was on fire. Organisations that rotate routinely find incidents cheap; organisations for whom rotation is an exceptional event find every leak expensive. Two practical notes: prefer adding a new credential and revoking the old one over changing one in place, since that allows a brief overlap and a rollback; and check the provider's audit log from before the leak too, because you need a baseline of normal use to recognise abnormal use.

Recap

  1. Secrets leak because every shortcut leads there and the failure is silent — the hardcoded credential works.
  2. A committed secret is permanent. Deleting it in a later commit changes nothing.
  3. Public pushes are scraped within minutes, so for public repositories the window is effectively zero.
  4. The pre-commit hook is worth more than every downstream control, because it is the last cheap moment.
  5. A secret manager is the baseline; dynamic short-lived credentials are the answer.
  6. Every scheme has a bootstrap credential. Make it platform-attested rather than stored.
  7. Prefer mounted files over environment variables, which leak into child processes and crash dumps.
  8. Scan history, CI variables, image layers and wikis, not just the current default branch.
  9. Rotate first, investigate second. The investigation rarely changes the decision.
  10. Teams hesitate because they do not know what will break. That is preparation work, not incident work.
