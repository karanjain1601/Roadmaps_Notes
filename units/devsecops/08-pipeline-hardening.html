Hardening the pipeline

Chapter 3 established that the build system belongs in tier 0. This is the work that follows from taking that seriously — and almost none of it is a purchase. It is a set of configuration decisions about isolation, credentials and who may change what.

8.1Runner isolation

A build job executes code from your repository, from every dependency it installs, and from every third-party action it calls. The question is what that execution can see and what it leaves behind.

Three models, and what leaks between jobs
Long-lived sharedCleaned between jobsEphemeral
Filesystem residueCaches, credentials, checked-out source from other teamsWorkspace cleared; caches and system state remainNothing — the instance is destroyed
Memory and processesA background process planted by one job survives into the nextSameGone
Installed toolingA modified compiler or package manager persistsSameRebuilt from the image
Credential exposureWhatever any job put in the environmentReduced, and process memory is still reachableOnly this job's
CostCheapest, fastest startModerateSlower cold start; needs a warm pool to stay fast
Ephemeral runners are the highest-value single change

They collapse most of the blast radius in Chapter 3's model at once: nothing persists, nothing leaks between teams, and a compromise is bounded to one job rather than to everything that ran on that machine afterwards. The objection is always cold-start latency, and it is answerable — a warm pool of pre-provisioned instances gives you ephemeral isolation with near-zero start time, and caching can be restored from a shared read-only layer rather than from a mutable directory the previous job could write to. Where you genuinely cannot be ephemeral, the compensating controls are dedicated runner pools per trust level, so a public-repository job never shares a machine with a production deployment job.

8.3Untrusted contributions

If anyone outside your organisation can open a pull request, then anyone outside your organisation can propose code that your CI will execute. That is the intended behaviour of a public repository, and it is fine — provided the execution has nothing worth stealing.

Trigger types, and what they should have access to
TriggerRunsShould have
Push to a protected branchReviewed codeFull credentials for its purpose
Pull request from a branch in the repoCode from someone with write accessBuild and test credentials; not deploy
Pull request from a forkArbitrary code from anyoneNothing. No secrets, read-only token, no cache write
Triggers that run in the base repository's contextPrivileged, and easy to misuse — they exist so a workflow can label or comment on an untrusted PRNever check out or execute the pull request's code. This is the specific footgun
Scheduled and manualWhatever is on the branchScoped to the task; manual runs should record who triggered them
The privileged-trigger footgun

Most CI systems offer a trigger that fires on a pull request but runs with the base repository's permissions and secrets — it exists so that a workflow can post a comment, apply a label or update a status on a contribution from a fork, which an unprivileged trigger cannot do. The failure is checking out and running the pull request's code inside that privileged context, which hands full credentials to whoever opened it. The rule is absolute: a privileged trigger may read metadata about the change and must never execute the change. If you need to build untrusted code and then act on the result, split it into two workflows — an unprivileged one that builds and uploads an artefact, and a privileged one triggered by its completion that consumes the artefact without executing it.

Why does OIDC federation beat a rotated long-lived key?

Because it removes the secret rather than shortening its life, and the two are different guarantees. A rotated key still exists as a string sitting in the CI system's variable store for the whole rotation period — typically thirty or ninety days — during which it is readable by every job in that scope, printable by any script that decides to echo its environment, extractable by any compromised dependency running in the build, and usable by anyone who obtains it from anywhere on the internet. Rotation bounds the damage after you discover a leak; it does nothing about the window before you discover it, and secret leaks are frequently found by outsiders rather than by you. Federation changes the shape: the CI system presents a signed assertion describing the job — this repository, this branch, this workflow, this environment — and the cloud provider issues a credential valid for minutes. There is no stored secret at all, so there is nothing to leak, nothing to rotate, and nothing to find in a log six months later. What replaces the secret is a trust policy, and that is where the mechanism is usually undermined: a condition like repo:acme/* means a compromise of any repository in the organisation yields the credential, and a condition that omits the branch means a pull request from a fork can obtain production access. The conditions must pin the repository, the ref and ideally the environment, and environments can additionally require a human approval. Two further points: the permissions the credential grants still need scoping separately — federation controls who gets a credential, not what it can do — and short-lived credentials also make the audit trail cleaner, because each issuance is a logged event tied to a specific job.

Your public repository runs tests on fork pull requests. Is that dangerous?

Not inherently — it is the point of accepting contributions, and running the proposed tests is how you find out whether the change works. It becomes dangerous the moment that execution has access to anything worth stealing. The safe arrangement has three properties. The workflow triggered by a fork pull request runs with a read-only token, no secrets, and no ability to write to shared caches or registries, so an attacker who submits malicious code gets code execution in a sandbox containing nothing but public source. Most CI systems now default to withholding secrets from fork triggers, which is good, and the default is worth verifying rather than assuming. The failures come from three places. First, the privileged trigger from §8.3 — a workflow that runs in the base repository's context with full credentials, which is safe only if it never checks out or executes the contributed code; the moment someone adds a build step to it, opening a pull request becomes equivalent to running code with your deploy credentials. Second, cache poisoning: if the fork's job can write to a cache that later trusted jobs restore from, the attacker affects builds that never ran their code, which is a subtle and frequently missed path. Third, self-hosted runners, where a fork job runs on a machine you own that other jobs also use — that combination should simply not exist, and fork pull requests belong on ephemeral hosted runners. If you need to act on the result of building untrusted code, split it: an unprivileged workflow builds and uploads an artefact, and a separate privileged workflow triggered by its completion consumes that artefact as data without executing it.

Why pin third-party actions by commit digest rather than by version tag?

Because a tag is a mutable pointer and a digest is not. When you write @v3 you are asking for whatever the author currently points that label at, which means the code executing in your build with your credentials can change after you reviewed it — without any change to your repository, without a pull request, and without anything to notice. That is not a hypothetical mechanism: retargeting a tag takes one command, and it applies retroactively to everyone referencing it. The threat model is not only a malicious author; it is far more commonly a compromised maintainer account, which is the same route that hits application dependencies in Chapter 6 and lands here with substantially more privilege, because a build step runs with the pipeline's credentials rather than inside a sandboxed application. Pinning by digest means the bytes you reviewed are the bytes that run, and a change requires a commit to your repository that goes through review like anything else. Three practical notes. Pinning without a mechanism to update means you accumulate stale actions with unfixed bugs, so pair it with a bot that proposes digest bumps and actually review the diff when it does — the review is the point, and a bot that auto-merges digest bumps has recreated the tag. The same argument applies to base images for build containers and to any script fetched over the network during a build. And where an action is small and important, vendoring it into your own organisation removes the dependency entirely, which is worth doing for anything in the critical path of signing or deployment.

Recap

  1. Ephemeral runners are the highest-value single change — nothing persists and nothing leaks between teams.
  2. Where you cannot be ephemeral, separate runner pools by trust level.
  3. Federation removes the secret; rotation only shortens its life.
  4. The OIDC trust policy is where it goes wrong. Pin the repository, the ref and the environment.
  5. Scope what the credential may do separately from who may obtain it.
  6. A fork pull request should get a read-only token, no secrets and no cache writes.
  7. A privileged trigger may read the change and must never execute it.
  8. Pin actions and base images by digest, with a bot proposing bumps and a human reviewing them.
  9. A writable shared cache is a trust boundary, and poisoning it affects builds that never ran the attacker's code.
  10. Default the job token to read-only and grant permissions per job.
