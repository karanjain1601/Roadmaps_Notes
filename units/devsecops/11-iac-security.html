Infrastructure as code

Defining infrastructure in files is the largest security opportunity the cloud offers: a misconfiguration becomes a reviewable, testable artefact instead of something someone clicked. It also introduces three problems that do not exist when you click — the state file, drift, and the fact that a module used by fifty teams is fifty deployments of one decision.

11.1Modules are where the leverage is

The single highest-return activity in this area, and it is design work rather than scanning. A module encodes a decision once; every team that uses it inherits the decision without making it.

Two modules that create the same resource 
THE ONE THAT WILL BE MISCONFIGURED
  variable "public"          { default = false }
  variable "encryption"      { default = null  }
  variable "logging_bucket"  { default = null  }
  variable "versioning"      { default = false }

  Safe only if every caller sets four variables correctly,
  forever. The defaults are "whatever the provider does",
  which is not a decision anyone made.

THE ONE THAT WILL NOT
  # Private, encrypted, logged and versioned. Not optional.
  # Public access requires the separate public-bucket module,
  # which requires an owner and a review.

  resource "aws_s3_bucket_public_access_block" "this" {
    block_public_acls       = true
    block_public_policy     = true
    ignore_public_acls      = true
    restrict_public_buckets = true
  }
  # …encryption, logging and versioning likewise fixed.

  variable "name"  { type = string }
  variable "owner" { type = string }   # required — no default
  # and that is the entire interface.

THE DESIGN RULES
  · Make the secure configuration NON-OPTIONAL, not defaulted.
    A default can be overridden by a copy-paste; an absent
    variable cannot.
  · Require the metadata your policies depend on — owner,
    environment, data classification — as variables with no
    default, so an untagged resource cannot be created.
                                                    → ch 10
  · Put the unsafe case in a SEPARATE module with a name
    that shows up in review: `public-bucket`, not
    `bucket(public = true)`. A grep for the module name is
    then a complete inventory of the exceptions.
  · Version modules and pin them, so a module change is a
    deliberate upgrade rather than a surprise on next apply.
A module fix is a fleet fix

When a scanner reports the same finding across two hundred resources, the question to ask before raising two hundred tickets is whether they come from one module — and they usually do. Fixing the module and bumping the pinned version resolves the whole set in one change, reviewed once. This inverts how vulnerability management usually feels in infrastructure: the finding count is misleading, because the distinct defect count is far smaller. It is also the argument for having modules at all rather than each team writing raw resources: without them there is no single place a fix can be made.

11.2Scanning the definition, and its limits

What a static scan of the code can and cannot see
Can seeCannot see
A literal insecure setting — a public bucket, an open security group, encryption disabledAnything computed at apply time from a variable, a data source or a remote state output
Missing required attributesWhat the value will actually be when the module is called with real inputs
Hardcoded secrets in the definitionResources created outside this codebase
Provider-version and module-source problemsWhether the resulting architecture makes sense

That second column is why scanning the plan beats scanning the code. A plan is the resolved, concrete set of changes about to be made — variables substituted, data sources read, references resolved — so a policy evaluated against it sees what will actually exist rather than what the template says. It is also the natural review artefact: a diff of resources to be created, changed and destroyed is far more reviewable than a diff of template text, particularly when a one-line variable change produces a fifty-resource replacement.

Read the destroy list

The most consequential line in a plan is the count of resources to be destroyed, and it is the one people skim past. A change that renames a resource, alters an identifier that forces replacement, or moves something between modules will show as destroy-then-create — which for a database, a load balancer with a fixed address, or a stateful volume is an outage or data loss rather than a refactor. Make the plan output part of the pull request, require an explicit acknowledgement when the destroy count is non-zero in production, and treat forces replacement in the plan as a phrase that stops the review. This is not strictly a security control and it prevents more incidents than most of the ones that are.

11.3State

The state file is a secret store nobody labelled as one 
WHAT IT CONTAINS
  Every attribute of every resource it manages, as returned
  by the provider — including generated database passwords,
  private keys, connection strings and access tokens. In
  plaintext, in JSON, regardless of whether the value was
  marked sensitive in the configuration.
  `sensitive = true` hides it from CONSOLE OUTPUT. It does
  not remove it from state.

THEREFORE
  · A remote backend with encryption at rest, not a file in
    the repository and not an unencrypted bucket.
  · Access control as tight as the secrets inside it — read
    access to state is read access to those credentials.
  · Locking, so two applies cannot corrupt it. A corrupted
    state file is a genuinely bad day: the infrastructure
    exists and your record of it does not.
  · Versioning on the backend, so you can recover one.
  · Audit logging on reads, not only writes.

AND THE STRUCTURAL FIX
  Prefer resources that do not put secrets in state at all:
  generate credentials at runtime from a secret manager,
  use IAM-based database authentication rather than a
  password, and reference secrets by ARN or path rather
  than by value.                                     → ch 7

SPLIT STATE BY BLAST RADIUS
  One state file for the whole estate means one lock, one
  slow plan, and one credential that can destroy everything.
  Split per environment and per bounded area, and let
  read-only remote state outputs be the interface between
  them.

11.4Drift

Where drift comes from, and what it costs

The gap between what the code says and what exists. It is not only a tidiness problem.

Why drift is a security problem specifically
ConsequenceDetail
Your policy checks the wrong thingScanning the code tells you about a configuration that is not what is running. The check passes and the estate is non-compliant
The next apply reverts a security fixSomeone tightened a rule by hand during an incident; the following apply puts the loose one back, silently
Or reverts an attacker's change, hiding itWhich sounds good and destroys the evidence that it happened
Emergency changes never come backA port opened at 3am to restore service is still open a year later, because nothing tracks it
Review stops meaning anythingIf production can be changed outside the pipeline, the reviewed artefact is not the deployed artefact
Why scan the plan rather than the templates?

Because the templates describe intentions and the plan describes what will exist. A static scan of the code sees literal values, so it catches an obviously public bucket and misses anything computed — a setting that comes from a variable, a value resolved from a data source, an attribute derived from another module's output, a conditional that depends on the workspace. In a codebase that uses modules properly, which is most of them, the majority of security-relevant settings are exactly those computed values, so template scanning has poor coverage precisely where the abstraction is good. The plan has all of that resolved: variables substituted, data sources read, references followed, and the concrete before-and-after for every resource. A policy evaluated against it is evaluating reality. Three further advantages. The plan is a much better review artefact than a template diff, because a one-line change to a variable can produce a fifty-resource replacement and only the plan shows that. It exposes the destroy list, which is the most consequential thing in any infrastructure change and is invisible in the template diff. And it lets you write policies about the change rather than the end state — "no production database may be replaced", "no security group may become more permissive" — which is a class of rule templates cannot express at all. The cost is that generating a plan needs credentials and access to real state, so the check runs later in the pipeline and needs care about who can trigger it on which branch. The usual arrangement is both: fast template linting on the pull request for immediate feedback, and plan-based policy as the gate before apply.

A scanner reports the same misconfiguration on 200 resources. What is your first move?

Find out how many distinct defects that actually is, which usually means checking whether the resources come from a shared module. If 180 of them are instances of one module used across the estate, then there is one defect, one fix and one review — change the module, bump the pinned version, and the finding count collapses on the next apply. Raising 200 tickets, or asking 40 teams each to make the same edit, is enormously more work and produces an inconsistent result because some teams will fix it differently and some will not fix it at all. This is the practical payoff of having modules in the first place: without them there is no single place the fix can be made, and 200 findings really are 200 pieces of work. Three things to check alongside. Whether the module is pinned by version — if callers track a branch, your fix propagates on the next apply without anyone reviewing it, which is convenient and is also how an unrelated breaking change reaches production unannounced; pinned callers need a version bump, which is more work and is the correct trade. Whether the remaining resources outside the module can be migrated into it, since the finding will otherwise recur. And whether the module's interface allowed the misconfiguration at all — if the insecure setting was reachable by passing a variable, fixing the default is weaker than removing the variable, because a default can be overridden by the next copy-paste. The general lesson is that finding counts in infrastructure are misleading, and the metric worth tracking is distinct defects and the share of resources created through vetted modules.

Is drift a security problem or a tidiness problem?

Both, and the security half is underrated because it is indirect. The direct problem is that your checks are evaluating the wrong artefact: if you scan the code and something else is running, a passing check is a statement about a file rather than about the estate, and you have a control that reports success while the thing it protects is non-compliant. That is worse than no check, because it produces false confidence. Three further consequences. An apply can silently revert a security fix — someone tightens a rule by hand during an incident, the next apply restores the loose configuration from code, and nobody is told. An apply can equally revert an attacker's change, which superficially sounds like self-healing and actually destroys the evidence that anything happened, so an intrusion becomes invisible. And emergency changes never come back: the port opened at 3am to restore service is still open a year later, because there is no mechanism tracking it and the person who opened it has forgotten. Underneath all of that is the structural point — if production can be changed outside the pipeline, then the reviewed artefact is not the deployed artefact, and every control that operates on the code is operating on a fiction. The fixes are ordered: remove standing console access so drift has fewer sources, provide break-glass access that is time-boxed and loudly logged so emergencies have a legitimate path, run a scheduled plan so drift is detected in days rather than at the next apply months later, and make the scheduled plan fail loudly rather than produce a report nobody reads. And when drift is found, reconcile deliberately — decide whether the code or the reality is correct, rather than letting the next apply decide by accident.

Recap

  1. Modules are the leverage. A decision encoded once is inherited by everyone who uses it.
  2. Make the secure setting non-optional, not defaulted — a default survives until the first copy-paste.
  3. Require owner and environment as variables with no default, so untagged resources cannot be created.
  4. Put the unsafe case in a separately named module so a grep is a complete inventory of exceptions.
  5. A module fix is a fleet fix. Check for clustering before raising two hundred tickets.
  6. Scan the plan, not the templates — computed values are where the security-relevant settings live.
  7. The destroy list is the most consequential line in a plan, and the most skimmed.
  8. State is a secret store. sensitive = true hides console output, not the file.
  9. Split state by blast radius, and prefer resources that keep no secret in state at all.
  10. Drift makes your checks evaluate a fiction. Remove standing console access, then detect on a schedule.
