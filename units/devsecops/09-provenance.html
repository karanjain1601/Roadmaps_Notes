Artefacts and provenance

Everything so far has been about making the build trustworthy. This chapter is about making that trustworthiness checkable — producing evidence that a given artefact came from a given source, through a given process, so that a consumer can verify it rather than assume it.

~28 min read Signing · attestation · SLSA · admission 2 interactive panels Prerequisite: chapters 6, 8

9.1The question provenance answers

At deploy time you have an artefact and a claim about where it came from. Without provenance the claim is unverifiable, and every control upstream becomes an assumption.

What you want to be able to prove, and what proves it 
"This image is the one our pipeline built"
  → a SIGNATURE over the artefact's digest

"…from this commit, in this repository"
  → an ATTESTATION recording the source

"…by this workflow, on this trusted builder"
  → provenance metadata the BUILDER produces, not the
    build script. A build cannot honestly attest to itself.

"…and these were its dependencies"
  → an SBOM, attached as an attestation      → ch 6

"…and nothing has changed since"
  → immutable references. A DIGEST, not a tag.

THE ORDER MATTERS
  A signature over a mutable tag proves nothing, because the
  tag can be repointed afterwards. Sign the digest, refer to
  the digest, and verify the digest at admission.

AND THE THING PEOPLE MISREAD
  A signature says "this came from that builder". It does
  NOT say the artefact is safe, that the code was reviewed,
  or that the dependencies are sound. It is an authenticity
  claim, and it is only as meaningful as the process behind
  the key.
Signing must not happen inside the build it signs

If the build job holds the signing key, then anything that achieves code execution in that job — a malicious dependency, a compromised action, a contributed test — can sign whatever it likes, and every downstream verification will pass. That is the exact scenario in Chapter 3's blast radius panel, and it is why "we sign our artefacts" is compatible with shipping a backdoor. The separation that works: the build produces an artefact and a description of how it was produced; a separate signing service verifies that description against policy — the right repository, the right workflow, a trusted builder — and only then signs. The signer's trust is in the builder's identity rather than in whoever asks.

9.2Keys, and the problem with them

Three models for holding a signing identity
Long-lived keyKey in an HSM or KMSKeyless / short-lived certificates
Where the private key isA file, a secret store, sometimes a developer's laptopHardware that will not export itGenerated in memory, used once, discarded
Compromise meansEvery past and future signature is suspect until you know whenMisuse is possible while access lasts; the key itself does not leakOne signing event
RotationPainful — every verifier must learn the new keyManageableNot applicable
Who signedWhoever had the keyWhoever could call it, if you log callsBound to a workload identity in the certificate
Verifier needsThe public key, distributed somehowThe sameA trusted root plus a transparency log to check against

The keyless model deserves the extra explanation because it is genuinely different. Instead of holding a long-lived key, the builder authenticates with its workload identity (the OIDC token from Chapter 8), receives a certificate valid for a few minutes that binds the signature to that identity, signs, and discards the private key. The signature is recorded in a public transparency log, which is what makes verification possible afterwards without a stored key — and which also means anyone can detect a signature they did not expect, in the same way certificate transparency works for TLS.

9.3SLSA levels

Where does your build sit?

A maturity ladder for build integrity. Each level assumes the one below it.

Provenance the build script writes is not provenance

The distinction between the levels turns on who makes the claim. If the build script generates its own provenance document, then anything that can modify the build can modify the document — so a compromised build produces an artefact and a matching, plausible, signed description of how it was legitimately produced. The claim has to come from the platform, from outside the part the build controls: the CI service records which repository, which commit, which workflow definition and which runner, and signs that with its own identity. This is the same reason a process cannot attest to its own integrity, and it is why "we generate SBOMs and provenance in our pipeline" needs the follow-up question of which component actually emits them.

9.4Verification at admission

Producing provenance and never checking it is a common and complete waste. The check belongs at the point of deployment, where refusal is still cheap.

9.5Reproducible builds

The strongest form of build integrity: the same source produces a bit-for-bit identical artefact, so anyone can rebuild and compare rather than trusting your builder at all. It is also genuinely difficult, and worth understanding why.

What breaks reproducibility, roughly in order of how often 
TIMESTAMPS       embedded build dates, archive mtimes
FILE ORDERING    directory iteration order differs by filesystem
PATHS            absolute build paths baked into binaries
LOCALE           sorting and formatting differ by environment
RANDOMNESS       generated identifiers, hash seeds
PARALLELISM      output order depending on scheduling
DEPENDENCIES     unpinned versions resolving differently
TOOLCHAIN        a different compiler minor version

WHAT IT BUYS
  · Independent verification — a third party rebuilds and
    confirms the artefact matches, so a compromised builder
    is DETECTABLE rather than merely constrained.
  · Cache validity you can trust.
  · Debugging: "the same input gave a different output" is
    a real signal rather than background noise.

WHAT IT COSTS
  Considerable effort, and it is ongoing rather than one-off —
  a dependency upgrade can reintroduce non-determinism.

WHO SHOULD DO IT
  Anyone shipping software others install: distributions,
  package maintainers, security-critical tooling. For a
  typical internal service the return is lower, and the
  effort is usually better spent on levels 2 and 3 of §9.3.
  Say so honestly rather than treating it as a universal goal.
Why does signing inside the build job undermine the whole point?

Because the signature is meant to answer "did our pipeline produce this?", and if the key is available to the build then anything running in the build can answer yes on its own behalf. A malicious dependency, a compromised third-party action, a contributed test — any of them gets code execution in the job, and code execution in a job holding a signing key is the ability to sign arbitrary content. Downstream verification then passes perfectly, which is worse than no signature at all, because your deployment process now has cryptographic confirmation of something false and will carry it to production with approvals attached. The separation that fixes it puts the signer outside the build's control: the build produces an artefact and the platform produces a description of how it was built, and a separate signing service checks that description against policy — expected repository, expected workflow, trusted builder identity — before signing. The signer's trust is in the builder's identity, established by the platform, rather than in whoever presents an artefact. Keyless signing makes this natural, because the certificate binds the signature to a workload identity that the build cannot forge and that appears in the transparency log for anyone to inspect. Two related points: the same reasoning explains why provenance generated by the build script is worthless (§9.3) — a compromised build writes a plausible document — and why verification at admission matters, since a signature nobody checks is a ritual. The question worth asking of any signing setup is simply: what would an attacker with code execution in the build be unable to do?

You sign images and verify signatures at admission. Are you protected against a compromised dependency?

No, and this is the most common misreading of what signing provides. A signature is an authenticity claim — it says this artefact came from that builder and has not been altered since. It says nothing about whether the contents are safe. If a malicious package was pulled in during a perfectly legitimate build, the resulting image is genuinely yours, correctly signed, with accurate provenance recording the real repository and the real workflow, and admission control will admit it — as it should, because every claim being made is true. The backdoor arrived through a channel signing was never designed to inspect. What actually addresses that is a different set of controls: dependency scanning and pinning at the point the dependency enters (Chapter 6), an SBOM attached as an attestation so you can answer "where is this library running?" when it turns out to be bad, and runtime detection for behaviour the artefact should not exhibit. Provenance still helps in that scenario, but in the aftermath rather than the prevention: because the attestation records the exact commit, workflow and dependency set, you can determine precisely which builds contain the bad version and which do not — which turns an estate-wide question into a query. The general framing worth holding: provenance answers "where did this come from", scanning answers "what is in it", and runtime answers "what is it doing". Each is blind to the others' questions, and a programme that has one and believes it has the others is the failure this question describes.

Should a typical internal service invest in reproducible builds?

Usually not, and it is worth being direct about that rather than treating reproducibility as a universal aspiration. What it buys is independent verifiability: because the same source produces bit-identical output, a third party can rebuild and compare, which makes a compromised builder detectable rather than merely constrained. That property is extremely valuable when your consumers cannot trust your infrastructure — a Linux distribution, a widely-installed package, a security tool, anything where users are downloading binaries and have no relationship with your build system. For an internal service deployed by the same organisation that runs the pipeline, the consumer and the builder are the same party, so the independent-verification property has nobody to serve. Meanwhile the cost is real and continuous rather than one-off: eliminating timestamps, file ordering, absolute paths, locale effects and toolchain variation takes sustained effort, and a routine dependency upgrade can silently reintroduce non-determinism, so it needs a check in CI to stay true. The better place for that effort in most organisations is the earlier rungs of §9.3 — platform-generated signed provenance, a hardened isolated build environment, and actual verification at admission — because those close the paths an attacker would use and they are achievable in weeks rather than quarters. Two caveats. Partial determinism is still useful even without full reproducibility, since "the same input gave different output" becomes a signal worth investigating. And if you ship anything customers install on their own machines, the calculation flips, because then you do have consumers who cannot audit your builder and reproducibility is what lets them verify without trusting you.

Recap

  1. Sign the digest, refer to the digest, verify the digest. A signature over a mutable tag proves nothing.
  2. Signing must happen outside the build it signs, or code execution in the build is the ability to sign anything.
  3. Provenance must come from the platform, not from the build script that a compromise would also control.
  4. Keyless signing binds the signature to a workload identity and records it in a transparency log.
  5. A signature is an authenticity claim, not a statement that the contents are safe.
  6. Provenance answers where it came from; scanning answers what is in it; runtime answers what it does.
  7. Producing provenance and never verifying it is a ritual. Check at admission, where refusal is cheap.
  8. Enforce digests and an allow-listed registry alongside signatures, or the checks can be sidestepped.
  9. Reproducible builds make a compromised builder detectable, which matters most when consumers cannot trust you.
  10. For internal services, the earlier rungs pay better than reproducibility. Say so rather than aspiring vaguely.
