Kubernetes security

Kubernetes is a distributed system with an API that creates workloads, so its security is mostly about two questions: who may call that API and with what, and what may talk to what once things are running. The defaults on both are more permissive than almost anyone expects.

The one-line summary of Kubernetes hardening

Turn off the automatic service account token, add a default-deny network policy per namespace, and enforce a restricted pod security standard. Those three changes address the largest defaults, cost nothing, and are the difference between a cluster where one compromised pod is contained and one where it is a starting position. Everything else in this chapter is refinement on top of them.

13.3Network policy

The cluster is flat by default. Network policy makes it not flat, and the mechanics have two traps worth knowing before you write one.

Default-deny, and the two things that surprise people 
# Deny everything in this namespace, then allow deliberately.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: payments }
spec:
  podSelector: {}                 # every pod in the namespace
  policyTypes: [Ingress, Egress]  # both directions

---
# Then allow the specific flows that should exist.
spec:
  podSelector: { matchLabels: { app: ledger } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { name: api } }
          podSelector:       { matchLabels: { app: gateway } }
      ports: [{ protocol: TCP, port: 8080 }]

TRAP 1 — POLICIES ARE ADDITIVE, NEVER SUBTRACTIVE
  There is no "deny" rule. A pod is denied only when it is
  selected by SOME policy and no rule in any policy allows
  the traffic. So a broad allow-all policy somewhere else
  that also selects the pod re-opens everything, and you
  cannot write a policy that overrides it.

TRAP 2 — EGRESS BREAKS DNS FIRST
  A default-deny egress policy blocks DNS, so every name
  lookup fails and the symptom looks like everything is
  broken rather than like a network policy. Always allow
  UDP and TCP 53 to the cluster DNS service alongside it.

AND
  · Policies are namespaced; a default-deny is needed in
    EVERY namespace, including new ones — which makes it a
    thing to enforce at namespace creation.
  · They need a CNI that implements them. Some do not, and
    the policy is then silently accepted and ignored.
  · They select by LABEL, so a mislabelled pod is
    unprotected and looks fine.

13.4Admission control and pod security

The three pod security standards, and what they stop
LevelPermitsUse for
PrivilegedEverything, including privileged containers, host namespaces and host pathsInfrastructure components that genuinely need it, in their own namespace
BaselineBlocks the known escapes — privileged, host namespaces, host ports, most host paths — and still allows running as rootA realistic first step for an existing estate
RestrictedNon-root required, all capabilities dropped, seccomp profile required, no privilege escalationThe target for application workloads

Apply them per namespace in three modes at once: enforce at the level you have reached, audit and warn at the level you are moving to. That gives immediate feedback to anyone deploying something that would fail the stricter level, without breaking them — the same warn-then-block sequence as Chapter 10, and here the platform does it for you.

Beyond the built-in standards, a general admission controller enforces everything the standards do not: image signatures and registries, required labels, resource limits, no latest tags, no default service account, ingress hostname ownership. That is policy as code, applied at the moment the object is created.

Secrets in Kubernetes are encoded, not encrypted

A Secret object is base64, which is an encoding for transport rather than protection. Three consequences. Without encryption at rest configured for the datastore, anyone with access to etcd or a backup of it reads every secret in the cluster. Anyone with get secrets in a namespace reads them through the API, and that permission is granted far more casually than its effect warrants. And a secret mounted into a pod is readable by anything that compromises the pod, which is unavoidable — so the mitigations are to keep the blast radius small (one secret per workload rather than a shared bundle), prefer short-lived credentials fetched at runtime from an external manager, and use workload identity so that no long-lived cloud credential exists in the cluster at all.

13.5Multi-tenancy

Cluster per tenantNearly everythingOperational cost, and it multiplies the number of things to patch

The decision rests on whether tenants are cooperating or mutually untrusting. Teams in one company sharing a cluster is a soft-multi-tenancy problem, and namespaces with RBAC, quotas and network policy handle it well. Running customers' arbitrary code is hard multi-tenancy, and namespaces are not sufficient — that needs node or runtime isolation at minimum, and frequently separate clusters.

Why is create pods nearly equivalent to cluster-admin within a namespace?

Because a pod specification is a request to run arbitrary code with attributes you choose, and several of those attributes are privilege. Someone who can create a pod in a namespace can mount any secret in that namespace into it and read the contents, which usually includes tokens for other service accounts. They can specify serviceAccountName and run as a more privileged account than their own. Unless a pod security standard forbids it, they can request a privileged container, mount the host filesystem, or share the host's PID namespace — each of which is an escape to the node, and from the node to every other pod scheduled on it. They can set a node selector to land on a specific node, including a control-plane node in some configurations. And they can pull any image from anywhere unless admission control says otherwise. So the permission reads as narrow and is effectively "execute code of your choosing with the union of everything reachable in this namespace". Several other verbs are similar and worth auditing for: pods/exec runs commands in existing pods, patch on a Deployment changes the image that runs, get secrets is direct credential access, and escalate, bind and impersonate exist specifically to work around the privilege-escalation prevention. Two practical conclusions. Enforce the restricted pod security standard so that the privileged variants of this are unavailable regardless of RBAC, and audit effective permissions by asking the API — kubectl auth can-i --list --as=… — rather than reading role YAML, because permissions compose across bindings in ways nobody tracks by hand.

You add a default-deny egress policy and everything breaks. Why?

DNS. A default-deny egress policy blocks all outbound traffic including UDP port 53 to the cluster's DNS service, so every name resolution fails — and because almost nothing in a cluster connects by IP, the symptom is that all traffic appears broken rather than that a network policy is in effect. Applications report connection failures, timeouts and unknown-host errors that look like the destination is down, and the causal link back to the policy is not obvious from any single error message. The fix is to pair every default-deny egress with an explicit allow to the DNS service on UDP and TCP 53, usually by selecting the kube-system namespace and the DNS pod labels. TCP matters too because responses larger than the UDP limit fall back to it, and omitting it produces intermittent failures on large responses, which is worse than a clean break because it is harder to diagnose. Three related traps in the same area. Policies are additive with no deny, so a broad allow-all policy elsewhere that also selects your pods re-opens everything and you cannot write a policy to override it — you have to find and remove the permissive one. They are namespaced, so a default-deny must exist in every namespace including ones created later, which makes it something to enforce at namespace creation rather than apply once. And they select by label, so a pod that is mislabelled or unlabelled is simply not selected and remains fully open while the policy appears healthy. Finally, verify your CNI actually implements policies: some do not, and the API accepts the object and silently ignores it, which produces a cluster that looks segmented and is not.

Is a namespace a security boundary?

Not on its own — it is a naming scope with hooks that let you build a boundary. By default a namespace gives you nothing isolating: pods in one namespace can reach pods in every other, service accounts are separate but the default one is mounted everywhere, there are no resource limits, and nothing prevents a workload in one namespace consuming a node shared with another. What turns it into a boundary is what you add: RBAC so subjects can only act within their namespace, network policy with a default-deny so traffic between namespaces is explicit, resource quotas and limit ranges so one tenant cannot starve another, and a pod security standard so nobody can request the privileged variants that escape to the node. With those four, a namespace is a reasonable boundary between cooperating teams. It is still not a boundary between mutually untrusting parties, because everything in the cluster shares a kernel per node and a single control plane: a container escape reaches other pods on the same node regardless of namespace, and a control-plane vulnerability reaches everything. So the right question is who you are separating. Teams within one organisation who are careless rather than hostile — namespaces plus those four controls are appropriate and proportionate. Customers running arbitrary code, or workloads at genuinely different trust levels — you need node-level separation at minimum, a sandboxed runtime, or separate clusters, and the operational cost of that is the honest price of hard multi-tenancy. Stating which model you are in is worth doing explicitly, because most clusters drift into hosting both without anyone deciding.

Recap

  1. Three changes carry most of the value: no automatic token, default-deny network policy, restricted pod security standard.
  2. Every pod gets an API credential by default, and most workloads never call the API.
  3. create pods is near cluster-admin in a namespace — as are exec, patch on Deployments, and get secrets.
  4. Audit effective permissions by asking the API, not by reading role YAML.
  5. Network policies are additive with no deny. A permissive policy elsewhere cannot be overridden.
  6. Default-deny egress blocks DNS first, so always allow UDP and TCP 53 alongside it.
  7. Policies select by label, so a mislabelled pod is unprotected and looks fine.
  8. Secrets are base64. Configure encryption at rest and treat get secrets as a serious grant.
  9. Run pod security standards in enforce, audit and warn at once to get warn-then-block for free.
  10. Namespaces separate cooperating teams, not untrusting tenants. Decide which you have.
