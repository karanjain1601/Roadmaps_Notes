Runtime protection

Everything up to this point tried to prevent the bad thing from shipping. This chapter assumes something got through anyway — which it will — and asks what you can see once the artefact is running that no amount of scanning could tell you beforehand.

~28 min read eBPF · workload detection · response · cost 2 interactive panels Prerequisite: chapters 12–13, and Cyber Security ch 16

15.1What only runtime knows

Containers make baselining tractable — which is not the same as precise

The base-rate problem from Cyber Security chapter 12 applies here unchanged: genuine compromise is rare, so precision is low for essentially every detection, and container detections are no exception. What containers change is alert volume. A container runs one process, from a known image, with a fixed set of binaries, talking to a small set of destinations, and it is replaced rather than modified — so "a process started that is not in the image" produces a handful of alerts a day rather than thousands. That is the property that matters operationally: a queue small enough to triage every item, where each item takes thirty seconds to resolve, beats a high-precision detector nobody can keep up with. Judge these rules on volume and triage cost, not on precision.

DetectionWhy the benign rate is low here

Killing the pod is the tempting wrong answer

It is the obvious response, the orchestrator immediately replaces it, and the graphs return to normal — which is precisely the problem. You have destroyed the memory, the process state, the network connections and the filesystem of the one instance that had evidence on it, and the replacement is built from the same image with the same vulnerability, so if the entry route was the image or a dependency, the attacker simply returns. It also looks like resolution, so nobody investigates. Isolate rather than kill: apply a deny-all network policy, capture forensics, and leave the pod running under observation, which is the container equivalent of the containment argument in Cyber Security chapter 17. Kill only when damage is accruing faster than the investigation can proceed.

Why is "a shell was spawned in a container" a high-precision detection when the equivalent on a server is useless?

Because the base rate is completely different, and base rate is what determines precision (Cyber Security chapter 12). On a general-purpose server, shells run constantly — administrators log in, cron jobs invoke scripts, management tooling shells out, deployment scripts run — so "a shell started" describes normal operation and an alert on it is pure noise. A container is a different kind of object: it runs one process, from an immutable image, and is replaced rather than administered. Most application containers never spawn a shell in their entire lifetime, and a container built from a distroless image cannot, because there is no shell binary present. So the event moves from "constant" to "essentially never", and an alert on it means either a genuine compromise or one of a small, enumerable set of legitimate cases — usually a developer debugging, which can be allow-listed by identity and time or, better, redirected to ephemeral debug containers that are distinguishable in the telemetry. This is the general reason runtime detection works better for containers than for hosts: the workload's regularity is the detection's precision. It also explains the ordering advice in §15.5 — the same property that makes the detection precise usually means you could have prevented it instead. A distroless image with a read-only root filesystem and dropped capabilities makes several of the best detections in this chapter fire on something that is now impossible rather than merely unusual, and prevention that costs nothing beats detection that costs an agent and an on-call rota.

Your runtime tool detects a compromised pod. Do you kill it?

Isolate it, capture forensics, and leave it running unless damage is accruing faster than you can investigate. Killing is the instinct because it is one command, the orchestrator replaces the pod immediately, and everything looks healthy again — which is exactly why it is usually wrong. You destroy the memory, the process tree, the open connections, the files written at runtime and the environment of the only instance that had evidence, so you lose the ability to establish how the attacker got in, what they reached, and whether other pods are affected. And the replacement is created from the same image with the same dependencies, so if the entry route was in the artefact rather than in that specific instance, the attacker returns within seconds and you have learned nothing. Worst of all, it looks like resolution, so the investigation that should follow often does not happen. The better sequence: apply a deny-all network policy to that pod, which stops exfiltration and lateral movement while preserving everything; capture the forensic snapshot the tooling offers; scale the deployment up by one so capacity is unaffected; and then investigate a live, contained instance. That is the container form of the "isolate rather than reimage" argument in Cyber Security chapter 17, and it has the same exception — active destruction, ransomware, or live exfiltration you cannot otherwise stop justify killing it, as a deliberate decision with someone's name on it rather than as a reflex. One practical prerequisite: isolation has to be a prepared, one-command action, because deciding how to isolate a pod during an incident is how people end up killing it instead.

Should you buy a runtime security tool?

Only after the configuration work, and only if someone will read the alerts. Three questions in order. Have you done the prevention that makes the best detections unnecessary? Distroless images remove the shell so it cannot be spawned; a read-only root filesystem makes system-path writes impossible rather than merely visible; dropped capabilities make privileged operations fail; a default-deny network policy makes unexpected egress impossible. Those four are free, they remove whole detection categories by making the behaviour impossible, and doing them first means the tool is catching what hardening missed rather than what hardening should have covered. Are you already collecting what is free? The Kubernetes audit log records every exec into a pod, every secret read and every RBAC change, and in most clusters it is emitted and discarded — that is a meaningful fraction of the value of a runtime product, available today. Will anyone respond? Unstaffed runtime detection is expensive telemetry, exactly as with EDR, and the default rule packs need weeks of tuning before the output is worth reading. If the answer to that last one is no, the honest options are a managed service or waiting. Where it does earn its place, the strongest arguments are the ones nothing else provides: runtime reachability, which tells you which of your thousands of vulnerability findings involve code that actually executes, and the forensic timeline, which is the difference between an investigation that takes an hour and one that takes three weeks. Both are worth real money, and neither is what the marketing leads with.

Recap

  1. Runtime answers what static analysis structurally cannot — most valuably, whether the vulnerable path actually executes.
  2. Containers make baselining work, because one process from a fixed image has genuinely narrow normal behaviour.
  3. eBPF gives per-node visibility into every container, including ones with no shell to instrument.
  4. The orchestrator audit log is free and usually discarded. Check before buying anything.
  5. Shell spawned, unexpected binary, and system-path write have the lowest benign volume — judge on volume, not precision.
  6. Prevention removes the need for the detection. Distroless and read-only root make three of them impossible.
  7. Isolate, do not kill. Killing destroys the evidence and the replacement has the same vulnerability.
  8. Make isolation a prepared one-command action, or people will kill the pod instead.
  9. The agent is a new privileged component on every node. Weigh that honestly.
  10. Unstaffed runtime detection is expensive telemetry. Managed, or not yet.
