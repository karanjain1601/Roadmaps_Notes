Container security

A container is a process with a restricted view of the machine, not a virtual machine. Most container security work is therefore about two things: putting less inside the image, and narrowing what the process may do — and neither is about the container runtime at all.

~28 min read Images · minimal bases · capabilities · isolation 2 interactive panels Prerequisite: Cyber Security ch 3

12.1What a container actually is

Understanding the mechanism removes most of the confusion about what containers do and do not protect against.

Three kernel features, and one shared thing 
NAMESPACES     what the process can SEE
               separate views of processes, mounts, network
               interfaces, hostnames, users and IPC. The
               process believes it is alone on the machine.

CGROUPS        what the process can USE
               limits on CPU, memory, I/O and process count.
               Not a security boundary in themselves, and a
               missing limit IS a denial-of-service surface.

CAPABILITIES,  what the process may DO
SECCOMP,       which privileged operations are permitted, and
LSM            which system calls it may even attempt.

AND THE SHARED THING
  ONE KERNEL. Every container on the host calls into the same
  kernel as the host and as every other container. A kernel
  vulnerability reachable from a container is a path out of
  it — which is the fundamental difference from a virtual
  machine, and the reason "containers are isolated" needs
  a qualifier.

SO THE THREAT MODEL IS
  Good     against a process misbehaving within its own
           expected scope.
  Weaker   against deliberate escape, which depends on the
           kernel's syscall surface and on how much privilege
           the container was given.
  None     against everything the container was legitimately
           handed: mounted secrets, network reach, service
           account tokens.                            → ch 13

Privileged is not "a bit more access"

Running a container as privileged disables essentially all of the confinement: it grants every capability, removes the seccomp filter, and gives access to host devices. A privileged container is a root process on the host with extra steps, and the standard escape from one is a few lines. The same applies to several individual settings that look narrower than they are — mounting the host filesystem, sharing the host process or network namespace, adding CAP_SYS_ADMIN, or mounting the container runtime's own socket. That last one deserves naming: a container with access to the Docker socket can start another container with the host filesystem mounted, which is a complete escape, and it appears in countless CI and monitoring setups because it is the easy way to let a container build images.

12.2The image

Base image choice

Almost every image vulnerability comes from the base layer, and almost none of it is code you use.

A build that produces a small, boring image 
# --- build stage: has the compiler, the source, the tests
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                    # cached separately
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# --- runtime stage: has the binary and nothing else
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

WHAT THE MULTI-STAGE BUILD REMOVES
  The compiler, the package manager, the source code, the
  test fixtures, the build-time credentials, and the shell.
  None of it ships, so none of it can be used by an attacker
  and none of it appears in your scan results.

THE LAYER TRAP
  Deleting a file in a later layer does not remove it — the
  earlier layer still contains it and anyone can extract it.
    RUN curl -H "Authorization: $TOKEN" … && rm /tmp/creds
  The credential is in the image forever. Use build secrets
  that are never committed to a layer, or a separate stage
  whose output you copy from.                        → ch 7

OTHER THINGS WORTH DOING
  · Pin the base by DIGEST, not by tag              → ch 8
  · USER before ENTRYPOINT, and a numeric UID so the
    orchestrator can enforce runAsNonRoot
  · No shell in the final image if you can manage it — it
    removes most post-exploitation convenience
  · .dockerignore, so the build context does not carry .git,
    .env and node_modules into the daemon

12.3Scanning, and what it is telling you

Reading image scan results without drowning
ObservationWhat to do
Most findings are in the base layerFix the base once, rebuild everything. Not a per-team ticket — see the module argument in ch 11
Most base findings are in packages you never callReachability matters more than count. A vulnerability in a mail utility you do not invoke is not the same as one in your TLS library
Many have no fix availableTrack them, do not block on them. A policy that fails the build on unfixable findings teaches people to add exceptions
The count grows with no code changeCorrect and expected — new CVEs are published against the same image. Rebuild weekly; an old image is an unpatched image
Language dependencies are separateImage scanners see OS packages well and application dependencies variably. Run software composition analysis too — ch 6
Scanners disagreeNormal. They use different databases and different matching. Pick one for gating and treat the others as second opinions
The single highest-value container control

A small vetted base image, rebuilt centrally on a schedule, that every team inherits. It reduces the finding count by an order of magnitude on day one, it makes a base-layer vulnerability a single rebuild instead of a fleet-wide campaign, and it removes the shell and package manager that make post-exploitation convenient. Everything else in this chapter is worth doing and none of it has the same leverage — and unlike most security work it makes builds faster and images cheaper to store, which means teams adopt it without being asked.

Why is a distroless or scratch image so much better than a slim distribution image?

Two separate reasons, and the second is usually undersold. The obvious one is surface: a slim distribution image still carries something like eighty packages — a shell, a package manager, coreutils, a libc, SSL libraries, and various things you have never heard of — and every one of them is code that appears in your scan results, needs patching, and has to be reasoned about when a CVE lands. Distroless carries your application's runtime dependencies and effectively nothing else, so the vulnerability count drops by an order of magnitude and most of what remains is genuinely relevant. The less obvious reason is post-exploitation. An attacker who achieves code execution inside a container immediately wants to orient: list processes, read files, resolve names, download a tool, open a connection. A slim image hands them a shell, curl or wget, a package manager to install anything missing, and the standard Unix toolkit. A distroless image gives them a running process and no shell to spawn, no interpreter, no download utility and no way to install one — so their options collapse to whatever they can do inside the compromised process, which is a dramatically weaker position and one that generates more noise. This is the container equivalent of the living-off-the-land argument in Cyber Security chapter 3: removing the tools removes the technique. Two practical notes. Debugging is harder, and the answer is ephemeral debug containers attached to the running pod rather than putting a shell back in the image. And distroless is not magic — it does not protect against a vulnerability in your own code or your language dependencies, which is what Chapter 6 is for.

Your image scan count went up this week and nobody changed the code. Is that a problem?

It is expected, and the useful response is a process rather than an investigation. Vulnerability counts are a function of time as much as of content: new CVEs are published continuously against packages that were already in your image, so an unchanged image accumulates findings simply by existing. An image built six months ago contains six months of unpatched base packages even if your application has not changed a line. That means the metric worth tracking is not the count but the age of the base layer, and the control is a scheduled rebuild — weekly is a reasonable default — so that base patches flow in without anyone raising a ticket. Three things follow. If the rebuild is centralised on a shared base image, one rebuild fixes every downstream image at once, which is the leverage argument from §12.3; if every team maintains its own base, the same work happens dozens of times or does not happen. Gating policy should reflect this too — failing a build on findings that have no fix available punishes teams for something outside their control and reliably produces blanket exceptions, so gate on fixable findings and track the rest. And it changes what a rising count means: a rise with a fresh base is genuine new exposure worth looking at, whereas a rise with a stale base is just the clock. Worth also checking one confounder before concluding anything: scanner database updates and version changes shift counts on their own, so a jump that coincides with a scanner upgrade may be measurement rather than reality.

Is a container a security boundary?

A partial one, and the honest answer depends on what you are separating. Against a process misbehaving within its own expected scope — a memory bug, a crash, a runaway resource consumer — the isolation is real and effective: namespaces limit what it can see, cgroups limit what it can consume, and the blast radius is genuinely the container. Against a deliberate escape attempt it is weaker than people assume, because every container shares the host kernel, so the attack surface is the entire syscall interface and a kernel vulnerability reachable from inside is a path out. Container escapes are not exotic; they appear regularly, and the ones that matter are usually enabled by configuration rather than by novel research — a privileged container, a mounted host path, the container runtime's socket, an added CAP_SYS_ADMIN, or a shared host namespace. And against everything the container was legitimately given — mounted secrets, network reach to other services, a service account token — it provides nothing at all, which is where most real incidents actually go. So the practical position: treat containers as a strong boundary between your own cooperating workloads and a weak one between mutually untrusting tenants. For genuinely untrusted code — a customer's build, a plugin, a multi-tenant platform — use a stronger runtime such as a micro-VM or a syscall-sandboxing runtime, or separate the workloads onto different nodes or clusters entirely. And in all cases, the configuration matters more than the runtime: a non-root container with all capabilities dropped, a read-only root filesystem and a tightened seccomp profile is a much smaller target than the default, and none of that costs anything.

Recap

  1. A container is namespaces, cgroups and capabilities over one shared kernel. The shared kernel is the qualifier.
  2. Privileged disables essentially all confinement, as do host mounts, host namespaces and the runtime socket.
  3. A container with the Docker socket can mount the host filesystem. That is a complete escape.
  4. Most image findings come from the base layer — fix it once centrally rather than per team.
  5. Multi-stage builds leave the compiler, source and build secrets behind.
  6. Deleting a file in a later layer does not remove it. The earlier layer still has it.
  7. Distroless removes the attacker's toolkit, not only the vulnerability count.
  8. Counts rise without code changes. Track base-layer age and rebuild weekly.
  9. Do not gate on unfixable findings — it produces blanket exceptions.
  10. Containers separate cooperating workloads well and untrusted tenants poorly. Use a stronger runtime for the latter.
