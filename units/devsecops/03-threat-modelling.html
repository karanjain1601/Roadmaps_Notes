Threat modelling the build

Threat modelling is usually pointed at the application. This chapter points it at the machinery that produces the application — which is a system with credentials to everything, executes code from anywhere, and is very often the least defended thing an organisation runs.

~28 min read STRIDE on a pipeline · build attack surface 2 interactive panels Prerequisite: chapters 1–2

3.1Why the pipeline is the target

An attacker wanting to reach many organisations at once has a choice: compromise each of them, or compromise something they all install. The second is dramatically cheaper, and the delivery pipeline is where that substitution happens — it is the point at which trusted code is manufactured.

What makes a build system unusually attractive
PropertyConsequence
It holds credentials to everythingRegistries, cloud accounts, production deploy rights, signing keys, package publishing tokens. Frequently more than any single human has
It executes arbitrary code by designThat is its job. Build scripts, test suites, dependency install hooks, and anything a contributor puts in a pull request
Its output is trusted downstreamA change made here is signed, promoted and deployed by systems that assume the build was honest
It is exempted from controlsAgents are excluded from endpoint tooling "because it breaks builds"; its network access is broad because dependency resolution needs it
Nobody owns its securityToo infrastructural for the product team, too much like a developer tool for the security team
Changes to it look like normal workA commit to a pipeline definition is a code change, reviewed by whoever reviews code, often less carefully than application logic
The pipeline is tier 0

In the tiering model from the Cyber Security unit (Chapter 10), tier 0 is the set of systems whose compromise means compromise of everything: domain controllers, the identity provider, PKI, backups. Your CI system belongs in that set and is almost never treated as though it does. It can deploy to production, it holds the keys that make artefacts trustworthy, and it runs code from every contributor. Everything in Part 3 of this unit follows from taking that seriously — and the first step is simply to notice that a system most organisations administer casually has the blast radius of a domain controller.

3.4What a compromised runner reaches

Blast radius of one build job

An attacker gets code execution inside a build — through a dependency, a fork pull request, or a compromised contributor account.

The pipeline definition is code that grants itself permissions

In most CI systems the workflow file lives in the repository it builds, which means a change to that file changes what the build is allowed to do — and it takes effect on the branch that contains it. If branch protection does not cover the pipeline definition, or if a workflow is triggered by a pull request from a fork with access to secrets, then proposing a change is equivalent to executing code with the pipeline's credentials. This is the mechanism behind a whole family of real incidents, and the defences are specific: never expose secrets to workflows triggered by untrusted pull requests, require review for changes to workflow files specifically, pin third-party actions by commit digest rather than by tag, and default the job's token to read-only with permissions granted per job.

Why is a build runner a more valuable target than most production servers?

Because of what it can reach and what downstream systems assume about it. A production server typically holds the credentials for its own job — a database connection, a queue, a couple of service tokens — and compromising it gets you that workload's data and a position to move from. A build runner holds the credentials needed to produce and ship software: registry push rights, cloud deployment roles, package publishing tokens, and often signing keys. In aggregate that is frequently broader access than any individual employee has, sitting on a machine that is administered casually. The second difference is more important. Output from the build is trusted downstream by construction — the artefact gets signed, promoted through environments, and deployed by systems whose entire job is to assume the build was honest. So an attacker who modifies the build does not need to attack production at all; they let your own deployment process carry the change there, through every control you have, with the correct approvals attached. That is what makes it a supply chain position rather than a foothold, and it is why the same technique reaches your customers if you ship software to anyone. Three properties compound it: the runner executes arbitrary code as its normal function, so there is no anomaly to detect in "it ran a script"; it is commonly exempted from endpoint tooling because agents interfere with builds; and its network egress is broad because dependency resolution requires it. The conclusion in §3.1 follows — it belongs in tier 0, alongside the identity provider and the backup system, and should be administered like one.

Your workflow file is in the repository it builds. Why is that a security property?

Because it means changing the file changes what the build is permitted to do, and the change takes effect on whichever branch contains it — so the ability to propose a change to that file is close to the ability to execute code with the pipeline's credentials. Keeping the definition in the repository is genuinely good practice for every other reason: it is versioned, reviewable, and travels with the code. The consequence is simply that the file needs to be treated as more sensitive than the application code around it, and by default it usually is not. The specific failure modes worth knowing. A fork pull request that receives secrets means anyone on the internet can submit a workflow change that exfiltrates them — which is why most CI systems now withhold secrets from untrusted pull request triggers by default, and why the triggers that do grant them need care. Branch protection that does not cover the workflow path lets a change land without the review everything else gets. Third-party actions pinned by tag rather than by commit digest mean the code you execute can be changed by someone else after you reviewed it, since a tag is mutable. And a default-permissive job token means every workflow starts with broad rights nobody chose. The defences are correspondingly specific: default the token to read-only and grant permissions per job, pin external actions by digest, require review for changes to workflow files as a distinct rule, never expose secrets to workflows triggered by untrusted contributors, and prefer short-lived federated credentials so that what leaks expires. Chapter 8 works through each.

What makes a threat model useful rather than an artefact nobody reads?

Three things, and the first two are about who is in the room rather than about technique. It has to be produced with the people who built the thing, because they know where the shortcuts are, which assumptions are load-bearing and which parts of the diagram are aspirational — an external reviewer working from documentation models the system as designed rather than as built. It has to produce a small number of owned, dated decisions, because a model that ends with sixty unranked findings gets filed, whereas one that ends with five actions and names attached becomes work. And it has to be cheap enough to repeat, since a model of last year's architecture describes a system that no longer exists — which argues for ninety minutes on a whiteboard several times a year over a two-week formal exercise once. A few practical habits raise the yield considerably. Keep it in the repository as a markdown file updated by pull request, so it changes when the system changes rather than when someone remembers. Write down the assumptions explicitly — "we assume the internal network is not reachable from the internet", "we assume this queue is only written to by our own services" — because assumptions are what silently stop being true, and a documented one can be checked. Say the unlikely threats out loud rather than filtering them, since the filtering happens with the same blind spots that built the system. And treat disagreement about what the diagram should even say as valuable rather than as a delay; that argument is frequently where the real finding is, because it means two people held incompatible mental models of the system they are jointly responsible for.

Recap

  1. Compromising the thing everyone installs is cheaper than compromising everyone, which is what makes build systems a target.
  2. The pipeline is tier 0 — it holds more access than most people and is administered casually.
  3. It executes arbitrary code as its normal function, so there is no anomaly in "it ran a script".
  4. Its output is trusted downstream, so a change there is carried to production by your own controls.
  5. Two untrusted inputs cross into it: external contributions and third-party packages.
  6. The workflow file grants the build its permissions, so proposing a change to it is close to executing code.
  7. Pin third-party actions by digest, because tags are mutable and can change after review.
  8. Ephemeral runners and short-lived federated credentials collapse most of the blast radius.
  9. Model with the builders, produce a few owned actions, and keep it in the repository.
  10. Write down the assumptions. They are what quietly stops being true.
