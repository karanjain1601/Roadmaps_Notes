Caching

The highest-leverage optimisation available and the source of the strangest bugs. This chapter covers where caches live and which one to reach for, the four write strategies and what each guarantees, why eviction policy matters more than people think, and the five failure modes — stampede, hot key, penetration, avalanche, and the cache that takes the database down when it dies.

15.1Why caching works at all

Caching is a bet on locality: that what was recently or frequently requested will be requested again. In real systems that bet is overwhelmingly good, because request popularity follows a Zipf-like distribution — a small head of items takes a large share of traffic. Twenty per cent of items typically serve eighty per cent of requests, and in consumer systems it is often closer to five and ninety-five.

The arithmetic of hit ratio is worth internalising, because it is not linear in the way it feels:

What a hit ratio buys 
origin load = requests × (1 − hit ratio)

  hit ratio 0%    → 100% of load reaches the origin
  hit ratio 50%   →  50%          (2× relief)
  hit ratio 90%   →  10%          (10×)
  hit ratio 95%   →   5%          (20×)
  hit ratio 99%   →   1%          (100×)
  hit ratio 99.9% →   0.1%        (1000×)

Going from 90% to 99% is a 10× reduction in origin load —
the same relief as going from 0% to 90%. The last few
percent are where all the value is, and where all the
difficulty is, because they are the long tail.

The near-cache pattern

Two tiers together: a small in-process cache in front of the shared Redis. The local tier absorbs the very hot keys at zero latency and removes almost all network round trips; the shared tier holds the long tail and provides one place to invalidate. The catch is coherence — each instance has its own local copy, so invalidation must either be a short TTL (seconds), or a broadcast over a pub/sub channel telling every instance to drop a key. Short TTLs are simpler and usually sufficient; the broadcast is the correct answer when staleness is unacceptable and the data changes rarely.

15.3Read strategies

Cache-aside (lazy loading)
The application checks the cache; on a miss it reads the database, writes the cache, and returns. The overwhelming default: simple, resilient to a cache outage, and only caches what is actually asked for. Its weaknesses are a cold start after any restart, three code paths to get right at every call site, and the stampede problem below.
Read-through
The cache itself loads from the database on a miss, so the application only ever talks to the cache. Cleaner call sites and a natural place to implement coalescing — and it makes the cache a hard dependency, since if it is down there is no path to the data.
Cache-aside, with the details that matter 
def get_user(user_id):
    key = f"user:v3:{user_id}"          # version the key format:
                                        # changing the shape? bump v3 → v4
                                        # and every old entry is orphaned,
                                        # not stale
    hit = cache.get(key)
    if hit is not None:
        return None if hit == NEGATIVE else deserialize(hit)

    with single_flight(key):            # only one loader per key per process
        hit = cache.get(key)            # re-check: someone may have filled it
        if hit is not None:
            return deserialize(hit)

        row = db.get_user(user_id)
        if row is None:
            cache.set(key, NEGATIVE, ttl=30)      # negative caching
            return None

        cache.set(key, serialize(row),
                  ttl=jitter(300, 0.1))           # ±10% so TTLs do not align
        return row

15.4Write strategies

What happens to the cache when data changes

Write-aroundWrite the database; invalidate the cache entryAvoids polluting the cache with write-only dataThe next read is a miss
Write-behind (write-back)Write cache, acknowledge, flush to the database laterVery fast writes; batches and coalesces repeated updatesData loss if the cache dies before flushing. Only for data you can afford to lose
Refresh-aheadProactively refresh entries before they expireHot keys never expire under load, so no stampedeWasted work refreshing things nobody asks for again
Invalidate, do not update

When data changes, deleting the cache entry is safer than writing the new value into it. Updating creates a race: two concurrent writers can interleave so the cache ends up holding the older value permanently, while the database holds the newer one. Deletion has a much smaller window and self-heals on the next read. And order matters: write the database first, then delete the cache. The reverse — delete then write — leaves a window where a concurrent reader repopulates the cache from the old database state, and that stale entry then lives for a full TTL. For the residual race, some systems use a delayed second delete a second later; more robustly, drive invalidation from the database's change stream so it cannot be skipped by a code path that forgot.

15.5Eviction

A cache is finite, so something must go. The policy matters more than people expect, because the difference between a good and bad policy at the same memory size can be tens of percentage points of hit ratio — which, per the arithmetic above, is the difference between 10× and 2× origin relief.

15.6Invalidation

The hard problem, in ascending order of correctness:

  1. TTL only. Data is wrong for up to the TTL, and that is the whole design. Perfectly adequate for a great deal of content — a follower count that is 60 seconds old harms nobody.
  2. Explicit delete on write. The write path removes affected keys. Correct when every write path remembers, which is until someone adds a new one, or a backfill script changes rows directly.
  3. Versioned keys. Include a version in the key: user:v3:18:profile. Changing the format bumps the version, and every old entry becomes unreachable rather than wrong. Also lets you invalidate a whole class instantly by bumping a namespace counter.
  4. Tags / dependency tracking. Entries record which entities they depend on; changing an entity evicts everything tagged with it. Necessary once a cached item is derived from several sources.
  5. Change-stream driven. Invalidation is generated from the database's own replication log, so no code path can forget it and a backfill invalidates correctly for free. The most robust option and the most machinery. See Chapter 17.

15.7The five failure modes

Stampede (thundering herd)

A popular key expires. Every request that arrives during the recompute window misses, and all of them go to the database to compute the same value. A key taking 200 ms to compute and serving 5 000 requests per second produces 1 000 simultaneous identical queries.

  • Single-flight / request coalescing. Only one caller recomputes; the rest wait for its result. One line of library code and the single most effective fix.
  • Probabilistic early expiration. As an entry approaches expiry, each reader has a small and rising chance of refreshing it early — so the refresh happens before the cliff, by one caller, without any coordination.
  • Serve stale while revalidating. Return the expired value immediately and refresh in the background. Latency never spikes at all.
  • Locking. A distributed lock per key. Works, and adds a dependency and a lock-timeout failure mode; prefer single-flight within each process plus one of the above.

Stampede at expiry

What the origin sees when a hot key expires, with each mitigation applied.

Hot key

One key takes so much traffic that the single cache node holding it saturates — a celebrity's profile, a flash-sale product, a global configuration entry. Sharding does not help, because the key is atomic. Three fixes: replicate the key across several cache nodes with a suffix chosen at random by the client; put a small local cache in front so most requests never leave the process; or, for counters, split the key into sub-keys and sum on read.

Penetration

Requests for keys that do not exist miss the cache every time and hit the database every time. Under a scraping or attack pattern of random ids, the cache provides zero protection. Two fixes: negative caching — store a short-lived marker meaning "this does not exist" — and a Bloom filter of existing keys, checked before the cache, which answers "definitely absent" cheaply for a fraction of the memory.

Avalanche

Many keys expire at the same instant, usually because they were all populated together after a deploy or a cache flush, all with the same TTL. The origin receives a wall of misses. The fix is one line: add jitter, so a nominal 300-second TTL is actually 270–330 seconds, and expiry spreads out instead of aligning.

The cache falling over

The most dangerous one, because it is a capacity problem disguised as a dependency problem. If your cache serves 95% of reads and it goes away, the database instantaneously receives twenty times its normal load — and dies, and cannot serve the traffic needed to refill the cache. This is a cold-start deadlock, and it has taken down large services.

Design for the cache being empty
  • Know the multiplier. Compute origin load at a 0% hit ratio and decide, explicitly, whether you can survive it. If not, you have a hidden single point of failure with a nice name.
  • Coalesce and rate-limit misses, so a cold cache produces one origin request per key rather than thousands.
  • Shed load rather than collapse. Serving 20% of traffic and rejecting the rest lets the cache refill; trying to serve everything means serving nothing.
  • Replicate the cache tier, so a single node failure loses a fraction of the keyspace rather than all of it — consistent hashing means only that node's share is affected.
  • Warm before taking traffic. A new instance or a restarted cache should be populated with the top keys before the load balancer sends it work.

Two sizing notes. Cache size should be driven by the working set, not by a round number: measure the number of distinct keys requested in a window equal to your intended TTL, multiply by average value size, add 30%. And serialisation format matters more than it seems — JSON is often the largest cost in a cache round trip, both in bytes and in CPU on both ends; a compact binary format can halve latency and memory for the same data.

Your cache hit ratio is 99% and the p99 latency of your service is still bad. What is going on?

The 1% is doing the damage. If a hit costs 1 ms and a miss costs 200 ms, then at a 99% hit ratio one request in a hundred takes 200 ms — which is your p99, by definition. Improving the hit ratio to 99.5% halves the tail; making the miss path faster helps just as much. And if a page makes twenty cached calls, the chance it contains at least one miss is 1 − 0.99²⁰ ≈ 18%, so nearly a fifth of pages inherit the miss latency — the fan-out amplification from Chapter 3 applies to cache misses exactly as it does to service calls. Fixes: serve stale while revalidating so a miss never blocks a user, coalesce so misses do not queue behind each other, and reduce the number of separate cached lookups per request.

Why does deleting the cache entry beat updating it, and why is order significant?

Updating creates a lost-update race between two writers: A reads, B reads, B writes DB, B writes cache, A writes DB, A writes cache — the cache now holds A's value while the database holds… whichever committed last, and they can disagree permanently until the TTL expires. Deletion narrows the window to the moment between the database write and the delete, and it self-heals on the next read. On ordering: write the database first, then delete. If you delete first, a concurrent reader can miss, read the old row from the database, and repopulate the cache with stale data just before your write lands — and that stale entry now survives for a full TTL. The remaining race in write-then-delete is much narrower, and is closed properly by driving invalidation from the database's change stream rather than from application code.

A nightly report job reads every row in the products table. The next morning, cache hit ratio has collapsed. Explain and fix.

Classic LRU scan pollution. The job touched every key once, and under LRU each of those touches promoted a cold item and evicted a hot one, so by the end the cache contains the last N products the job happened to read — none of which any user wants. The hot set has to be rebuilt from scratch during the morning peak, which is exactly the wrong time. Fixes, in order of effort: have the batch job bypass the cache entirely (a read path that does not populate); use an admission policy such as W-TinyLFU, which refuses to admit a one-off item over a frequently-used resident one; segment the cache so batch and interactive traffic cannot evict each other; or run the job against a replica with its own cache. The eviction simulator above reproduces this exactly — raise the batch sweep percentage and watch LRU shed several points of user hit ratio while frequency-based eviction barely moves.

Recap

  1. Origin load is requests × (1 − hit ratio). 90% to 99% is another 10× — the last few percent carry the value.
  2. Pick the layer deliberately. Local caches are fastest and impossible to invalidate; distributed caches are one authoritative copy; the near-cache pattern combines both with a short TTL or a broadcast.
  3. Cache-aside is the default; read-through centralises the logic and makes the cache a hard dependency.
  4. Invalidate rather than update, and write the database before deleting the key.
  5. Eviction policy is worth real hit ratio. LRU dies on scans; LFU dies on shifting popularity; admission-based policies handle both.
  6. Version keys, jitter TTLs, and cache negatives. Three one-line habits that prevent three whole failure classes.
  7. Coalesce misses. Single-flight plus serve-stale-while-revalidating removes stampedes entirely.
  8. Hot keys need replication or a local tier; sharding cannot split a single key.
  9. Know your origin load at a 0% hit ratio. If the answer is "we die", the cache is a single point of failure and needs replication, load shedding and warm-up.
