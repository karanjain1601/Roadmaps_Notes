The NoSQL families

"NoSQL" names seven unrelated things that share only a marketing decade. What actually distinguishes them is the access pattern each data model makes cheap — and choosing correctly means starting from your queries rather than from your entities. This chapter is each family, what it is shaped for, and how to model in the two that most often appear in designs.

14.1What the label actually means

The term is defined by what it is not, which is useless. Two things do unite most of these systems:

  1. A data model chosen to make one access pattern very cheap, at the cost of the others. Relational storage is a generalist: any query is expressible, and the planner works out how. These are specialists.
  2. Horizontal scaling designed in from the start, usually by requiring a partition key on every operation. That requirement is what makes them scale — it is also why they cannot do arbitrary joins, because a join has no partition key.
The design method inverts

In a relational database you model the entities, normalise, and then write whatever queries you need — the schema comes first and the queries adapt. In every store below you enumerate the queries first, then design tables and keys so that each query is a single-partition lookup. Adding an unanticipated query later can require a new table or index and a backfill. That trade — expensive flexibility for cheap scale — is the actual decision, and it is why "we might need to query it differently later" is a strong argument for relational.

14.2Key-value

A dictionary: get(key), put(key, value), delete(key). The value is opaque, so the store never parses it and cannot query inside it. That restriction is what makes it fast and trivially partitionable — the key is the partition key.

Where it fits
Good forBad for
Caches and sessionsAny query that is not by exact key
Feature flags, configurationRelationships between values
Rate-limit counters, deduplication keysAggregates and reporting
Precomputed results and materialised viewsAnything needing a transaction across many keys

Redis deserves separate mention because it is a key-value store with typed values — lists, sets, sorted sets, hashes, streams, bitmaps, HyperLogLog — and server-side operations on them. A sorted set turns "top 100 by score" into an O(log n) operation, which is why leaderboards, rate limiters, delayed queues and recent-item lists so often end up in Redis rather than in the primary database. It is single-threaded for command execution, so a single slow command (a big KEYS scan, a large sort) blocks every other client — the most common Redis incident, and entirely avoidable.

14.3Document

Values are JSON-like documents that the store can see into, so you can query and index on nested fields. Each document is self-contained, which suits data that is naturally hierarchical and usually retrieved whole.

Embed or reference 
EMBED when the child is owned by the parent, bounded in size,
and almost always read together with it:

  { _id: "order_9f2", customer_id: "u_18",
    items: [ {sku:"A1", qty:2, price:1299}, {sku:"B7", qty:1, price:450} ],
    shipping: { line1:"…", city:"…" },
    total: 3048 }

  → one read renders the whole order. No join exists to be slow.

REFERENCE when the child is shared, unbounded, or independently updated:

  { _id: "u_18", name:"…", email:"…" }          // user
  { _id: "post_1", author_id:"u_18", body:"…" } // post

  → an unbounded `comments` array inside a post is the classic mistake:
    documents have a size limit, and every comment rewrites the whole post.

Document stores are attractive because the model matches application objects and the schema is flexible. Both benefits have a shadow. Flexible schema means the schema moved into your application code, where nothing enforces it — five years of writes produce five variants of the same document and every reader must handle all of them. And joins are absent or weak, so denormalised copies proliferate and each one is a consistency obligation. Use schema validation where the store offers it, and treat "we do not need a schema" as a decision to maintain the schema yourself.

14.4Wide-column

The Bigtable/Cassandra model, and the one most often misunderstood. It is not "a table with lots of columns". The mental model is a nested sorted map:

The shape 
partition key  →  sorted map of ( clustering key  →  columns )

  Rows with the same partition key live together on one node,
  physically sorted by the clustering key.

CREATE TABLE messages (
  conversation_id  uuid,      -- partition key: which node
  sent_at          timestamp, -- clustering key: sort order within it
  message_id       uuid,
  sender_id        uuid,
  body             text,
  PRIMARY KEY ((conversation_id), sent_at, message_id)
) WITH CLUSTERING ORDER BY (sent_at DESC);

-- "last 50 messages in a conversation" is one sequential read
-- on one node. That is the only query this table can answer,
-- and it answers it at any scale.

Everything follows from that. You cannot query by a column that is not in the key without a scan. There are no joins. You design one table per query, writing the same data several times in different shapes — which is normal practice here, not a hack, because disk is cheap and coordination is not. Updates are writes with a newer timestamp; deletes are tombstones. The design skill is choosing partition keys that are neither too large (a partition that grows forever becomes a hot, oversized row) nor too small (a partition per item destroys the locality that makes reads cheap).

The unbounded partition

Partitioning messages by conversation_id is correct until one conversation has ten million messages, at which point that partition is gigabytes on one node and every read of it is slow. The standard fix is a bucketed compound partition key: ((conversation_id, month), sent_at). Reads for a time range hit one or two buckets; the partition size is bounded by construction. Decide the bucket granularity from the arithmetic — target partitions in the tens of megabytes — rather than discovering it in production.

14.5Graph

Nodes, edges and properties, where an edge is a first-class object you can traverse in constant time from either end. The distinguishing capability is variable-depth traversal: "friends of friends of friends", "every path between these two accounts", "everything reachable from this permission".

In a relational database that is a self-join per level of depth, and the cost multiplies at each one — three levels of a social graph is a three-way join over a table with billions of rows. A graph database stores adjacency directly, so hopping from a node to its neighbours is a pointer dereference and the cost is proportional to the number of edges actually walked rather than the size of the table.

The honest caveat: a graph database is worth it when traversal is the workload, not when your data merely has relationships. All data has relationships. A social network storing "friends of a user" needs an index, not a graph database; one running fraud-ring detection or shortest-path queries across a hundred million edges needs a graph database. Fraud detection, recommendations, network topology, identity resolution and permission hierarchies are the recurring genuine use cases.

14.6Time series

A workload with a distinctive shape: overwhelmingly append-only, always written with an increasing timestamp, almost always queried as "this series over this range", rarely updated, and eventually deleted wholesale. Purpose-built stores exploit every one of those properties.

  • Columnar layout and delta-of-delta encoding for timestamps, plus XOR encoding for floats — real compression ratios of 10–20× against row storage.
  • Automatic downsampling: keep raw data for a week, one-minute averages for a month, one-hour averages for two years. Storage stops growing linearly.
  • Retention as a first-class policy — dropping a time partition rather than deleting rows.
  • Query primitives that match the questions: rate, moving average, percentile over a window, alignment across series.

You can do this in a relational database with time partitioning and it works well up to a point — the point being roughly where the compression ratio and the retention automation start to matter more than SQL flexibility. Examples: Prometheus, InfluxDB, TimescaleDB (Postgres extension, so you keep SQL), ClickHouse (analytical rather than strictly time series, and remarkably good at both).

14.7Search and vector

Search engines invert the index: instead of document → terms, they store term → documents, so "which documents contain these words" is a lookup rather than a scan. They add analysis (tokenising, stemming, synonyms, language handling) and relevance ranking, which is what a LIKE '%term%' query fundamentally cannot do. Elasticsearch and OpenSearch dominate; Postgres full-text search is genuinely good and worth trying before adding a cluster.

Vector stores index embeddings — high-dimensional numeric representations — and answer "what is semantically nearest to this?" using approximate nearest-neighbour indexes such as HNSW or IVF. They power semantic search and retrieval for language models. Exact nearest-neighbour search is linear in the number of vectors, so the "approximate" is not a shortcut but the whole technique, and its recall/latency trade-off is the parameter you tune. Increasingly this is a feature of existing stores (pgvector, Elasticsearch, Redis) rather than a separate system, which is usually the better choice.

Both are almost always secondary stores, fed asynchronously from the system of record. They are indexes, not sources of truth: rebuildable, allowed to lag, and never the place a write lands first.

14.8Distributed SQL: refusing the choice

A newer category — Spanner, CockroachDB, TiDB, YugabyteDB, Vitess, Aurora — that keeps the relational model, SQL and transactions while sharding underneath. Rows are partitioned into ranges, each range is a consensus group, and distributed transactions use two-phase commit over those groups.

What it costs to have both
KeepsCharges
SQL, joins, secondary indexes, constraintsCross-partition transactions pay consensus latency — milliseconds within a region, far more across regions
Real distributed transactionsContention on a hot row serialises through one consensus group
Horizontal write scalingHigher baseline latency than a single-node database for simple queries
Automatic resharding and rebalancingOperational complexity, cost, and a smaller pool of people who have run one

The design implication: schema locality matters enormously. If your access patterns keep related rows in one range — interleaving a customer's orders under the customer — most transactions stay single-partition and are fast. If they scatter, every transaction is distributed and you have bought the cost without the benefit.

14.9Modelling worked: single-table design

DynamoDB-style stores give you one partition key and one sort key per table, plus a small number of secondary indexes. The technique is to put several entity types in one table and use composite key values so that each access pattern is one query on one partition.

One table, four entity types 
Access patterns to support:
  1  get a user by id
  2  list a user's orders, newest first
  3  get an order with all its line items in one query
  4  list all orders for a product (analytics-ish, lower volume)

PK                 SK                    attributes
─────────────────  ────────────────────  ─────────────────────────
USER#u18           PROFILE               name, email, created_at
USER#u18           ORDER#2026-08-30#o91  total, status          ← 2
USER#u18           ORDER#2026-07-02#o44  total, status
ORDER#o91          META                  user_id, total, status ← 3
ORDER#o91          ITEM#sku-A1           qty, price
ORDER#o91          ITEM#sku-B7           qty, price

  1  PK = USER#u18, SK = PROFILE                     → one item
  2  PK = USER#u18, SK begins_with ORDER#            → one query, sorted
  3  PK = ORDER#o91                                  → all items, one query
  4  GSI: PK = PRODUCT#sku-A1, SK = ORDER#o91        → a second projection

Notice: the sort key encodes the date so "newest first" is free,
and orders are written twice — once under the user, once under
the order. Duplication is the mechanism, not a mistake.

14.10Polyglot persistence, and its bill

"Use the right tool for each job" is correct and incomplete. Each additional store adds: an operational surface (upgrades, backups, monitoring, capacity, failure modes), a consistency seam between it and the system of record, a set of people who need to learn it, and a new way for an incident to be confusing. Three stores is a normal, healthy architecture. Nine is usually an accident.

Two disciplines keep it under control. One system of record per fact — every other store is a derived index that can be rebuilt from it, which means a corrupted search index or a stale cache is a rebuild rather than data loss. And feed derived stores from a change stream, not from application code writing twice, because dual writes fail halfway and leave you permanently inconsistent with no way to tell. This is the outbox and change-data-capture pattern from Chapter 17.

Your team wants Cassandra for a system whose main query is "orders in the last 30 days, filtered by status, sorted by total". What do you say?

That the query does not fit the model. Wide-column stores answer "range within one partition"; this query has no partition key at all — it spans all users, filters on a column that is not part of the key, and sorts on another. Getting it to work would require a partition scheme by time bucket, a table per status, in-application sorting of everything returned, or a secondary index that scatter-gathers to every node. Any of those is worse than a relational database with an index on (status, created_at), or an analytical store if the volume is genuinely large. The right question back to the team is what problem they are solving: if it is write volume, ask what the write rate actually is; if it is availability, note that a relational primary with replicas gets a long way; if it is "the data is large", partitioning by time inside one database is far cheaper than a new cluster.

Why is duplicating data across several tables normal in a wide-column store and a mistake in a relational one?

Because the two systems make opposite things expensive. In a relational database a join is cheap — indexed, planned, executed on one machine — so a second copy buys little and costs a permanent consistency obligation. In a wide-column store a join does not exist and a query without a partition key means contacting every node, so writing the data again in the shape of each query is the only way to answer it in one lookup; writes are cheap and sequential, so the duplication is nearly free on the write side. The consistency obligation is the same in both cases — it is just that in one system it buys a fundamental capability and in the other it buys a marginal optimisation.

When should search be a separate cluster rather than a feature of your database?

Start with the database's own full-text support; Postgres handles hundreds of thousands of documents with ranking, stemming and highlighting perfectly well, and it comes with transactional consistency for free. Move to a dedicated cluster when you need things the database cannot do: relevance tuning with per-field boosts and custom scoring, faceted aggregations over large result sets, fuzzy matching and typo tolerance, multi-language analysis, or index sizes and query volumes that would compete with your transactional workload for the same buffer pool. Note the last one is often the real reason — separating search is as much about resource isolation as about capability. When you do separate it, feed it from a change stream, treat it as rebuildable, and never let a write land there first.

Recap

  1. Each family makes one access pattern cheap and the rest expensive. Start from your queries, not your entities.
  2. Key-value: exact key only. Redis adds server-side data structures that turn several hard problems into one command.
  3. Document: embed what is owned and bounded, reference what is shared or unbounded. Flexible schema means you own the schema.
  4. Wide-column is a sorted map of sorted maps. One table per query, duplication is the mechanism, and partitions must be bounded — bucket the key.
  5. Graph databases win on multi-hop traversal, not on having relationships.
  6. Time series buys compression, downsampling and retention; relational time partitioning covers a lot of the same ground.
  7. Search and vector stores are secondary indexes: rebuildable, allowed to lag, never the system of record.
  8. Distributed SQL refuses the choice at the cost of latency and a schema that must keep related rows co-located.
  9. One system of record per fact; feed everything else from a change stream. Dual writes from application code are how permanent inconsistency happens.
