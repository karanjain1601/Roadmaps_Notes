Databases: engines, indexes, transactions

Most system design conversations treat the database as a box labelled "DB". The box has internals, and they determine everything: whether writes are cheap, whether a query is a lookup or a scan, and which concurrency bugs are possible at all. This chapter opens the box far enough to make those predictions yourself.

12.1The two halves of a database

Every database splits into a storage engine — how bytes are laid out on disk and in memory, and how they are found and updated — and an execution layer — how a query is parsed, planned and turned into calls to the storage engine. Two databases with the same SQL dialect can behave completely differently because they use different engines, and the same engine can be wrapped in a SQL interface, a key-value interface or a document interface.

The storage engine answers one question: given a key, what is the cheapest way to find the value, and what does it cost to change it? There are essentially two answers in production use.

12.2B-trees

A B-tree (in practice a B+tree, where only leaves hold data) keeps keys sorted in fixed-size pages, typically 4–16 KB, matching the unit the disk and the operating system move anyway. Interior pages hold keys and pointers to child pages; leaf pages hold the actual rows or pointers to them.

And the top levels are always in memory, so a point lookup in a
billion-row table is typically one or two disk reads.

Updates happen in place: find the leaf page, modify it, write it back. That is simple and gives excellent read behaviour, but it means a single 200-byte row update rewrites an entire 8 KB page. Because a crash mid-page-write would corrupt the tree, every change is first appended to a write-ahead log, so recovery can replay it. So one logical write becomes: one WAL append plus, eventually, one full page write.

Two structural consequences worth remembering. Pages split when full, which is why a B-tree is typically only 70% full and why insert-in-random-order is slower than insert-in-sorted-order. And random writes scatter dirty pages across the whole file, so the flush is random I/O — cheap on SSD, catastrophic on spinning disks, which is the historical reason for the next design.

12.3LSM trees

A log-structured merge tree never updates in place. Writes go to an in-memory sorted structure (the memtable) plus a WAL append. When the memtable is full it is written out, sequentially, as an immutable sorted file (an SSTable). Background compaction merges SSTables, discarding overwritten and deleted entries.

A deletion writes a tombstone — a marker saying "this key is gone" — which is why an LSM store can temporarily grow when you delete data, and why compaction is what actually reclaims space. Three amplification factors describe the cost of the whole arrangement, and they are the vocabulary for comparing engines:

Write amplification
Bytes written to disk per byte of user data. LSM: each level rewrite multiplies it, so leveled compaction with a size ratio of 10 costs roughly 10 per level. B-tree: the page-to-row ratio, plus the WAL.
Read amplification
Disk reads per lookup. LSM: potentially one per level, cut to near one by bloom filters. B-tree: the tree depth, mostly cached.
Space amplification
Disk used per byte of live data. LSM leveled: ~1.1. LSM tiered: 2 or more, since old versions linger. B-tree: ~1.4 from partially full pages.

The one-line rule

Write-heavy and append-shaped → LSM. Read-heavy with updates and range scans → B-tree. If your workload is metrics, events, logs or messages, an LSM engine will absorb writes that would flatten a B-tree. If it is an application's transactional data with lots of updates and ad-hoc queries, a B-tree gives you steadier latency and simpler operations.

Storage engine cost model

The same workload through both engines. Amplification factors are estimates, but the shape of the comparison is real.

12.4Indexes

An index is a second data structure that maps a column's values to row locations, so a query can find rows without reading all of them. Everything about indexes is a trade of write cost and disk space for read cost.

Clustered index / primary storage
The table itself is stored in the order of this key, so the index leaf is the row. There can only be one, and looking up by it costs nothing extra. InnoDB always clusters on the primary key; Postgres does not cluster at all by default, storing rows in a heap.
Secondary index
Maps values to a pointer at the row. Using it costs two lookups: index, then the row itself. In InnoDB the pointer is the primary key, so a secondary lookup is an index descent plus a clustered index descent.
Composite index
An index on several columns in order. Usable for a query only if the query constrains a leftmost prefix — an index on (a, b, c) helps queries filtering on a, on a, b, or on a, b, c, and is useless for a query filtering only on b. Column order is a design decision, not a formatting one.
Covering index
An index containing every column the query needs, so the row itself is never read. This often makes a query several times faster, and it is the single most effective index technique that people underuse.
Partial index
Indexes only rows matching a predicate: WHERE status = 'pending'. When 99% of rows are complete and you only query the pending ones, the index is 1% of the size and stays in memory.
Expression index
Indexes the result of a function — lower(email). Necessary because WHERE lower(email) = … cannot use a plain index on email.
Why the database ignored your index
  • Low selectivity. If the predicate matches more than roughly 5–15% of rows, a sequential scan is genuinely faster than millions of random row fetches. The planner is right and the index is the wrong tool.
  • A function or cast on the column. WHERE date(created_at) = … or comparing a varchar column to a number defeats the index. Rewrite as a range, or index the expression.
  • Leading wildcard. LIKE '%term' cannot use a B-tree. Use a trigram or full-text index.
  • Wrong prefix. The composite index is on (a, b) and you filter on b.
  • Stale statistics. The planner's row estimates come from sampled statistics; after a bulk load they can be wildly wrong until analysed.
  • OR across columns. Often prevents index use; a UNION of two indexed queries can be dramatically faster.

And the cost side, which is invisible until it is not: every index must be updated on every insert, update of an indexed column, and delete. A table with eight indexes does roughly nine times the write work of one with none, the indexes may collectively exceed the table's own size, and they compete for the same buffer pool. Auditing for unused indexes — every mature database exposes index usage statistics — is one of the highest-yield hours of database work available.

12.5How a query is executed

Reading a query plan is the most transferable database skill there is. Four things to look for, in order:

  1. The access method. Sequential scan (read everything), index scan (walk the index, fetch rows), index-only scan (never touch the table), bitmap scan (collect row locations, then fetch in physical order — Postgres's answer to medium selectivity).
  2. The join algorithm. Nested loop: for each row of A, look up in B — excellent when A is tiny and B is indexed, quadratic otherwise. Hash join: build a hash table from the smaller side, probe with the larger — the workhorse for large unsorted joins, needs memory. Merge join: both inputs sorted, walk them together — great when the sort comes free from an index.
  3. Estimated versus actual rows. The single most useful diagnostic. A plan that expected 10 rows and got 2 million chose a nested loop and is now doing two million lookups. The fix is statistics or a rewrite, not a hint.
  4. Where the time actually went. Sorts spilling to disk, filters applied after the fetch rather than pushed into the index, and rows discarded late are all visible in the plan.

EXPLAIN (ANALYZE, BUFFERS) SELECT …;

12.6ACID, precisely

Atomicity
All of a transaction's changes apply, or none do. It is about abortability — the ability to throw everything away on failure — not about concurrency.
Consistency
The database moves from one valid state to another, where "valid" means your constraints, foreign keys and invariants hold. This is largely the application's property; the database only enforces the constraints you declared. It is the weakest letter and shares no meaning with the C in CAP.
Isolation
Concurrent transactions do not observe each other's partial work. This is the letter with a dial on it — see below — and the one that causes real bugs.
Durability
Once committed, it survives a crash. In practice this means "written to a WAL and fsynced", and in a distributed setting it means "on more than one machine" — a single disk's fsync does not survive the disk.

12.7Isolation levels and the anomalies they allow

Perfect isolation means transactions behave as if they ran one after another. That is expensive, so databases offer weaker levels, each permitting specific anomalies. Write skew is the one that gets shipped

It survives every level below serializable, including snapshot isolation, and it is invisible in testing because it needs true concurrency. The shape: each transaction reads a set of rows, makes a decision based on what it read, and then writes a different row. Neither write conflicts, so no conflict is detected, and the invariant that spanned both breaks. Booking the last seat, going off call, staying within a budget, enforcing "at most one primary" — all write skew. The fixes are to use SERIALIZABLE, to materialise the conflict by locking the rows you read with SELECT … FOR UPDATE, or to introduce a row that both transactions must write so the conflict becomes real.

MVCC, and why it needs a vacuum

Most modern databases implement isolation with multi-version concurrency control: an update writes a new version of a row rather than overwriting it, and each transaction sees the versions that were committed when it started. The enormous benefit is that readers never block writers and writers never block readers — a long analytical query does not stop the application from writing.

The cost is that old versions accumulate and must be reclaimed. In Postgres that is VACUUM; in InnoDB it is the purge thread and the undo log. Two operational consequences follow directly, and both cause real incidents: a long-running transaction holds back cleanup for the whole database, because any version it might still need must be kept, so an idle-in-transaction session left open by a buggy client can bloat a table by hundreds of gigabytes. And a table with a high update rate can accumulate dead rows faster than they are reclaimed, so queries slowly scan more and more dead space. Monitor the age of your oldest transaction; it is a leading indicator for both.

12.8Locking, and deadlocks

Even with MVCC, writes need locks. Two transactions cannot both modify the same row, so the second waits.

  • Row locks are what you normally hit. Held from the moment of the write until commit — so a transaction that writes early and commits late holds locks for its whole duration. Keep transactions short, and do the network calls before you open one.
  • SELECT … FOR UPDATE takes a write lock on rows you have only read, which is how you turn a read-modify-write into a safe operation without moving to serializable.
  • Table and DDL locks are the dangerous ones. A migration that needs an exclusive lock will queue behind every open transaction, and every new query will queue behind it — a table that was fine a second ago now has a thousand waiting connections. Always set a short lock timeout on DDL.
  • Deadlocks happen when two transactions each hold what the other wants. The database detects the cycle and kills one. They are normal and your application must retry — but the frequency drops close to zero if every transaction acquires locks in a consistent order (for instance, always update accounts in ascending id order).

12.9Practical guidance

  1. Default to read committed and handle concurrency explicitly where it matters, using conditional updates (UPDATE … WHERE version = ?) or FOR UPDATE. Reach for SERIALIZABLE on the specific transactions with an invariant across rows, and be prepared to retry on serialization failures.
  2. Do updates in the database, not in the application. UPDATE counters SET n = n + 1 is atomic; read-then-write from application code is a lost update waiting to happen.
  3. Keep transactions short and never hold one across a network call. An HTTP request inside a transaction holds locks for as long as the remote service takes to respond, which under an incident is forever.
  4. Retry on serialization failures and deadlocks with jitter, and make the transaction idempotent so a retry is safe.
  5. Index for your queries, then delete the indexes nothing uses. Check the usage statistics rather than guessing.
  6. Look at plans with real numbers, and treat a large gap between estimated and actual rows as the finding, not a detail.
Two users buy the last item in stock at the same moment. Both succeed. Which anomaly, and what are three fixes?

Lost update if both did SELECT stock then UPDATE stock = 4; write skew if each read the stock row and then inserted an order row without writing the stock row at all. Three fixes, in increasing cost. Conditional update: UPDATE items SET stock = stock - 1 WHERE id = ? AND stock > 0 and check that one row was affected — atomic, no extra locking, and the correct answer most of the time. Pessimistic lock: SELECT … FOR UPDATE on the item row before deciding, which serialises buyers of the same item. Serializable isolation, which detects the conflict and aborts one transaction for you, at the cost of retry handling and lower throughput. Note that only the first works if the check and the write are separated by application logic you cannot avoid.

A query on a 50-million-row table takes 4 seconds. You add an index and it is still 4 seconds. What are the likely explanations?

In rough order of likelihood: the predicate is not selective enough, so a scan really is cheaper and the planner declined the index; the column is wrapped in a function or implicitly cast, so the index is unusable; the index is on the wrong prefix of a composite; statistics are stale, so the planner is estimating badly; the query returns so many rows that the time is in transferring them, not finding them; or the cost is not in the filter at all but in a sort, a join or an aggregate further up the plan. Run EXPLAIN (ANALYZE, BUFFERS) and look at where the time and the buffer reads actually accumulate — the answer is nearly always visible immediately, and guessing at indexes without the plan is the slow way to find it.

Why does a write-heavy workload favour an LSM engine, and what do you give up?

Because every LSM write is a sequential append to a memtable and a log, whereas a B-tree write eventually rewrites a whole page — so a 200-byte insert costs 8 KB of page write plus WAL in a B-tree, and roughly its own size, deferred and batched, in an LSM. Compaction does eventually rewrite the data several times, but sequentially and in the background rather than randomly and on the critical path. What you give up: predictable latency, because compaction periodically steals I/O and CPU and produces visible spikes; read amplification on keys not in the top level, which bloom filters reduce but do not remove; and space that briefly balloons after mass deletes because tombstones only free space once compaction runs. In a design discussion, the honest phrasing is "sequential writes and higher throughput, paid for with background work and less predictable read latency".

Recap

  1. B-trees update pages in place with a WAL for safety, giving shallow trees, predictable reads and page-sized write amplification.
  2. LSM trees append and compact, converting random writes into sequential ones at the cost of background work and latency spikes.
  3. Write-heavy → LSM; update-and-range-scan-heavy → B-tree. Compare on write, read and space amplification.
  4. Indexes trade write cost and space for read speed. Composite indexes need a leftmost prefix; covering indexes avoid touching the table at all.
  5. Above roughly 5–15% selectivity a scan beats an index, and the planner is right to switch.
  6. Read plans with actual row counts. A large estimate-versus-actual gap is the diagnosis.
  7. ACID's isolation is the letter with a dial. Learn the anomalies, not the level names.
  8. Write skew survives snapshot isolation and is the anomaly most likely to reach production. Serializable, FOR UPDATE, or materialise the conflict.
  9. MVCC means readers never block writers — and that a long-running transaction blocks cleanup for the whole database.
  10. Keep transactions short, acquire locks in a consistent order, and retry deadlocks.
