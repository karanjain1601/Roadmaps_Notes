Partitioning, sharding, consistent hashing

Replication makes copies; partitioning makes pieces. It is the only way past one machine's write capacity, and the shard key you pick is the most expensive decision in the design to change later. This chapter covers the schemes, how to choose the key, what skew does, the consistent hashing ring, and how to reshard something that is already serving traffic.

~40 min read Shard keys · the ring · rebalancing · routing 2 interactive panels Prerequisite: chapter 6

7.1What partitioning buys, and what it charges

A partition (shard) is a subset of the data that lives on its own node or replica set. Every shard handles the writes and reads for its own keys, so total write capacity, storage and memory scale with the number of shards. That is the entire benefit, and it is enormous — it is the difference between a ceiling and no ceiling.

The charges are all consequences of one fact: operations that span shards are no longer cheap. A join across shards becomes a distributed query. A transaction across shards becomes two-phase commit or a saga. A "list everything sorted by date" becomes a scatter-gather across every shard with a merge at the end. An auto-increment id becomes a coordination problem. Uniqueness constraints stop being enforceable by the database.

Do not shard before you must

Sharding is close to irreversible and it removes capabilities you may not notice you were using. Exhaust the cheaper options first, roughly in this order: add the missing index; move reads to replicas; cache; archive or tier old rows out of the hot table; buy a bigger machine; split by function into separate databases (federation) which is much easier than splitting by row; and only then partition. A single modern database node with a well-designed schema handles a few thousand writes per second and terabytes of data — most systems die of complexity long before they hit that.

The compound key deserves emphasis because it is the answer most often reached for in practice. A messaging system partitioned on conversation_id and sorted by (conversation_id, sent_at) spreads load evenly across conversations while making "the last fifty messages in this conversation" a single sequential read on one shard. That is hash partitioning's distribution with range partitioning's locality, and the trick is available whenever queries always know the first component.

7.3Choosing the shard key

Four criteria, all of which must hold. Failing any one of them produces a system that works in staging and falls over in production.

1 · High cardinality
There must be far more distinct key values than shards, or you cannot spread. country has ~200 values; boolean is_premium has two. Neither can partition a thousand-shard cluster.
2 · Even distribution
Values must be roughly uniformly used. country fails again — a tenth of the world's users are in one of them. Cardinality without uniformity is not enough.
3 · Query alignment
Your dominant queries must include the key, or every query becomes a scatter-gather across all shards. If you shard orders by order_id but always query "all orders for this customer", you have made every read touch every shard.
4 · Immutability
Changing a record's shard key means deleting it from one shard and inserting into another — not a transaction any more. Choose something that never changes: user_id, not email; account_id, not subscription_tier.

7.4Skew and hot spots

Even a mathematically perfect hash cannot fix skew in the access pattern. Three distinct problems get called "hot spots":

  1. Hot shard — one shard holds more data or takes more traffic than its peers. Usually caused by a low-cardinality or non-uniform key.
  2. Hot key — a single key is so popular that no partitioning scheme helps, because the key is atomic. A celebrity account, a flash-sale product, a global config row.
  3. Sequential hot spot — the write cursor is always at the end of the key space: timestamps, auto-increment ids, ULIDs. Every write goes to one shard while the others idle.

7.5Consistent hashing

Why hash(key) mod N is a trap

The obvious scheme works perfectly until the number of nodes changes. Go from 4 nodes to 5 and hash(key) mod 4 becomes hash(key) mod 5 — which reassigns roughly 80% of all keys. For a cache that means a near-total miss storm and a thundering herd against the origin. For a database it means moving four fifths of your data over the network before the cluster is usable again. Adding one machine should move about 1/N of the keys, not most of them.

The ring

Map the hash space onto a circle, from 0 to 232 (or whatever the hash width is) wrapping back to 0. Place each node at one or more positions on that circle, determined by hashing the node's name. To find the owner of a key, hash the key to a point on the circle and walk clockwise to the first node position you meet. That node owns the key.

The property that makes this work: when a node leaves, only the keys that were walking clockwise into that node need to move, and they move to the next node round. Every other key keeps the same owner. When a node joins, it takes over only the arc immediately behind its new position. Both operations touch approximately 1/N of the keys and nothing else.

Virtual nodes

With one position per node, the arcs are wildly uneven — hashes cluster, and with 5 nodes it is entirely normal for one to own 40% of the ring. The fix is to place each physical node at many positions (typically 100–256 "virtual nodes"), so each physical node owns many small arcs whose total length converges on its fair share. Virtual nodes also make heterogeneous hardware easy: give a machine with twice the RAM twice as many virtual nodes and it takes twice the load.

Automatic rebalancing during an incident

Fully automatic rebalancing is dangerous in combination with automatic failure detection. A node becomes slow, is declared dead, and the cluster starts moving its data — which saturates the network, makes other nodes look slow, which triggers more rebalancing. A busy cluster can rebalance itself into an outage. Most mature systems require a human to approve adding or removing capacity, while allowing automatic failover of leadership. Detection can be automatic; large data movement should be deliberate.

7.7Routing: who knows where the key lives?

  • Client-side — fastest, one network hop, no extra tier. The cost is a fat client library in every language you use, and the pain of rolling out a change to the map. Cassandra and Kafka work this way.
  • Proxy tier — thin clients, central control, easy to change behaviour. Adds a hop and another thing to scale and keep available. Vitess, PgBouncer-style poolers and most managed offerings work this way.
  • Redirect — nodes tell clients where to go when they guess wrong; the client caches the correction. Cheap to operate, occasional extra round trip. Redis Cluster's MOVED and ASK responses are the well-known example.

7.8Secondary indexes across shards

Partitioning is defined by the primary key, so every other query dimension needs an index — and there are only two ways to place it.

Local versus global secondary indexes
Local (document-partitioned)Global (term-partitioned)
LayoutEach shard indexes only its own rowsThe index itself is partitioned by the indexed term, independently of the data
WriteLocal — one shard, atomic with the rowCross-shard — the row is on shard 3, its index entry on shard 7

Local indexes make writes cheap and reads expensive; global indexes do the reverse. Since scatter-gather is subject to the tail amplification from Chapter 3, a local index over 100 shards will have a p99 governed by your slowest shard's p99.9. That is the practical reason large systems tend to build a separate, purpose-built search index fed asynchronously from the change stream, rather than trying to make the partitioned primary store answer every query shape.

7.9Operations that span shards

Cross-shard reads (scatter-gather)
Query every shard, merge and sort in the coordinator. Cost is the slowest shard plus the merge, and it does not scale — adding shards makes each such query worse. Bound the damage with deadlines, partial results, and by designing so the common queries are single-shard.
Cross-shard transactions: two-phase commit
A coordinator asks every participant to prepare (durably promise it can commit), and if all agree, tells them to commit. Correct, and it has a nasty property: between prepare and commit, participants hold locks and cannot act unilaterally. If the coordinator dies in that window, the participants are stuck — the classic blocking problem. Modern systems make the coordinator itself fault-tolerant with consensus, which is exactly what Spanner and CockroachDB do, and it is why they can offer distributed transactions at a latency cost rather than not at all.
Sagas
Give up atomicity and build the operation as a sequence of local transactions, each with a compensating action if a later step fails. Reserve stock; charge card; if charging fails, release stock. Not isolated — other actors can observe intermediate states — but it does not hold locks across services. The standard answer in microservice architectures, covered in Chapter 17.
Unique constraints
"No two users may have the same email" cannot be enforced by a database that has been split by user_id. The usual solution is a separate, small, strongly consistent registry keyed by the unique attribute — a table sharded by email, or a row in a consensus store — that you claim before creating the user.

7.10Resharding a live system

This is where the interview goes when you have got the basics right, and it is genuinely hard. The playbook, which is the same whether you are splitting a shard or changing the key entirely:

  1. Add the routing indirection first, if it does not exist. You cannot change the mapping if the mapping is hard-coded in application logic.
  2. Backfill. Copy existing data to its new home in the background, at a rate that does not disturb production. This may run for days.
  3. Dual-write. Application writes go to both old and new locations. Both must succeed, or you need a reconciliation job — this is where an outbox or change stream is much safer than writing twice from application code.
  4. Verify. Read from both and compare, on real traffic, for long enough to be convincing. Count rows, checksum ranges, sample records.
  5. Shift reads gradually, by percentage or by tenant, with a fast switch back. This is the step where you find out what you missed.
  6. Stop writing to the old location, and only then delete it — after a retention period long enough to recover from a problem discovered late.
The pre-split trick

If you suspect you will need to shard eventually, hash into a large fixed number of logical partitions on day one — 1 024 is a common choice — and map many logical partitions to each physical node. On a single node this costs almost nothing: it is a column, or a prefix on the key. When you need to grow, you move logical partitions between nodes without ever rehashing a key or touching application code. Choosing this on day one is minutes of work; retrofitting it is the multi-week project described above.

You shard a URL shortener by hash(short_code). Traffic grows and you add nodes. Reads are fine but analytics queries — "top 100 links this hour" — have become unusable. Why, and what would you do?

The shard key is right for the dominant operation (resolve one code) and useless for the analytics query, which has no short_code in it and therefore must scatter to every shard, take the top 100 from each, and merge. That gets worse with every node you add. The fix is not to change the shard key — it would break the fast path that matters. It is to stop asking the transactional store analytical questions: emit click events to a stream, aggregate them in a purpose-built store (a time-series database, a warehouse, or a Redis sorted set per hour), and serve the leaderboard from there. Different access pattern, different store, fed asynchronously.

Why do virtual nodes matter, and roughly how many should you use?

With one ring position per node, arc lengths are random and the variance is large — with a handful of nodes it is common for the largest to own several times the share of the smallest, and removing a node dumps its entire arc on a single neighbour rather than spreading it. Many positions per node average out the randomness: load imbalance falls roughly with the square root of the number of virtual nodes, so 100–256 per machine brings imbalance to a few percent, which is where most implementations settle. They also let you weight heterogeneous machines and spread a departing node's load across all survivors instead of one.

A multi-tenant SaaS shards by tenant_id. One customer is 40% of all traffic. What are your options?

Four, in increasing order of effort. Dedicated shard: move that tenant to its own node or replica set — a directory-based routing map makes this a config change, and it also isolates the blast radius, which the customer will probably pay for. Sub-partition within the tenant: use a compound key like (tenant_id, sub_bucket) so the big tenant spreads across shards while small tenants stay on one; the cost is that cross-bucket queries for that tenant become scatter-gather. Read replicas for that tenant only, if the load is read-dominated. Separate tiers: a "large tenant" cluster and a "long tail" cluster with different provisioning. Whichever you pick, the important part is that the routing layer already supports per-tenant placement — if the mapping is hash(tenant) mod N baked into application code, none of these options is available to you.

Recap

  1. Partitioning is the only way past one node's write capacity, and it costs you cheap joins, transactions, ordering and uniqueness.
  2. Exhaust indexes, replicas, caching, archiving, bigger hardware and functional splits first. Sharding is close to irreversible.
  3. A shard key must have high cardinality, even distribution, alignment with your dominant queries, and immutability. All four.
  4. Compound keys — hash the first component, sort within it — give distribution and locality at once.
  5. Skew is separate from partitioning: hot shards need a better key, hot keys need caching or sub-key splitting, sequential keys need a hash prefix.
  6. hash mod N remaps most keys when N changes. A hash ring remaps 1/N; virtual nodes make the split even and let you weight machines.
  7. Many small partitions mapped to nodes is the practical rebalancing strategy — move partitions, never rehash keys.
  8. Local indexes are cheap to write and expensive to read; global indexes are the reverse. Scatter-gather inherits tail amplification.
  9. Reshard with routing indirection, backfill, dual writes, verification, gradual read shift, then deletion — and pre-split into logical partitions on day one to avoid ever needing it.
