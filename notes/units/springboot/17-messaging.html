Events, scheduling and messaging

Everything Spring offers for work that should not happen on the request thread — and the two defaults that surprise people: an event listener runs inside your transaction, and a scheduled job runs on every instance you deploy.

— words— min read2 interactivesNeeds: chapters 06, 11 · Backend ch 18

Application events

A publish–subscribe mechanism inside one JVM. Useful for decoupling a side effect from the code that caused it — and the default timing is almost never what you want for anything external.

When does the listener run?
Try the plain listener with a rollback, then the last toggle
java — publishing and listening
@Service
class OrderService {
    private final ApplicationEventPublisher events;

    @Transactional
    public void place(CreateOrder cmd) {
        var order = repo.save(Order.from(cmd));
        events.publishEvent(new OrderPlaced(order.id(), order.total()));
    }                       ↑ publish a record with IDs and values —
}                             never a managed entity, which will be
                              detached by the time a listener reads it

@Component
class OrderPlacedListeners {

    @TransactionalEventListener(phase = AFTER_COMMIT)
    void sendConfirmation(OrderPlaced e) { … }     ← external side effects

    @TransactionalEventListener(phase = AFTER_COMMIT)
    @Transactional(propagation = REQUIRES_NEW)      ← after commit there is NO
    void writeAuditRow(OrderPlaced e) { … }          transaction. Without this,
                                                      each statement autocommits
    @TransactionalEventListener(phase = AFTER_COMMIT)
    @Async
    void reindex(OrderPlaced e) { … }              ← off the request thread. Note
}                                                     the failure is now invisible
                                                      unless you handle it
Events are not a message broker

They exist entirely inside one JVM: nothing is persisted, nothing is retried, and if the process dies between commit and the listener running, the side effect is simply lost. That is acceptable for cache invalidation and acceptable-ish for a nice-to-have notification. It is not acceptable for anything another service depends on — that is the dual-write problem from chapter 18 of the Backend unit, and the answer is the outbox below. The useful rule: if losing it would be a bug, it needs a durable record inside the transaction.

Scheduling

A nightly job, and three instances
The default runs it three times
SettingMeans
fixedDelayWaits n after the previous run finishes. Cannot overlap or pile up. The safe default
fixedRateFires every n regardless of duration. An overrunning job queues behind itself, and with a bigger pool they overlap
cronWall-clock expressions. Mind the time zone, and mind that daylight saving makes some times happen twice or not at all
spring.task.scheduling.pool.sizeDefaults to 1. Every scheduled method in the application shares one thread, so a slow job delays all the others
initialDelayWorth setting, so a rolling deploy does not fire every job the moment each instance starts
java — the outbox, in Spring
// ① the write path: business row and outbox row, one transaction
@Transactional
public void place(CreateOrder cmd) {
    var order = orders.save(Order.from(cmd));
    outbox.save(new OutboxRow(order.id(), "order.placed", toJson(order)));
}   ↑ both are inserts into the same database, so they are atomic in
      the ordinary way. Nothing is published here.

// ② the relay: a scheduled job, locked so only one instance runs it
@Scheduled(fixedDelay = 500)
@SchedulerLock(name = "outbox-relay", lockAtMostFor = "PT30S")
void relay() {
    for (var row : outbox.findUnpublished(100)) {   ← FOR UPDATE SKIP LOCKED,
        kafka.send(row.type(), row.aggregateId().toString(),    so several relays
                   row.payload())                               could share the work
             .join();
        outbox.markPublished(row.id());
    }
}
// if it dies between send and mark, the event goes twice — which is
// fine, because the consumer is idempotent. That is the deal.

// ③ the consumer: idempotent, and acknowledging after the work
@KafkaListener(topics = "order.placed", groupId = "fulfilment")
@Transactional
void on(ConsumerRecord<String, String> rec) {
    if (processed.existsById(rec.key() + ":" + rec.offset())) return;
    processed.save(new Processed(...));      ← unique index does the enforcing;
    apply(parse(rec.value()));                  same transaction as the effect
}

@Async, honestly
Fire and forget, with three sharp edges: it is a proxy, so chapter 6's rules apply; a void method swallows its exception unless you register an AsyncUncaughtExceptionHandler; and the default executor in older Boot versions is unbounded. Configure a ThreadPoolTaskExecutor with a bounded queue, or enable virtual threads — chapter 7. Return CompletableFuture so failures are visible.
Spring Kafka and Spring AMQP
Listener containers with concurrency, batch mode, manual acknowledgement, retry topics and dead-letter routing. Thin, well-designed wrappers — the concepts are chapter 18 of the Backend unit, and the annotations are a day's reading.
Spring Batch
Chunk-oriented processing with a job repository, restartability, skip and retry policies. Genuine value for reprocessing millions of records where a mid-run failure must resume rather than restart. Considerable machinery for a nightly job that updates two hundred rows — a @Scheduled method with a lock is the honest answer there.
Spring Integration
Channels, transformers and adapters for enterprise integration patterns. Powerful, and largely displaced by plain messaging for new work.

Self-check

  1. Why is a plain @EventListener the wrong place to send an email?
    Because it runs synchronously inside the publishing transaction, before the commit. If the transaction later rolls back, the email has already gone — describing an order that does not exist — and it cannot be recalled. It also adds its duration to the transaction, holding a database connection while an SMTP call happens. @TransactionalEventListener(phase = AFTER_COMMIT) fires only once the data is actually durable.
  2. What must you remember when writing to the database from an AFTER_COMMIT listener?
    That there is no transaction any more — it just committed. Repository calls will each autocommit individually, so a listener writing several rows has no atomicity, and a failure halfway leaves partial data. Add @Transactional(propagation = REQUIRES_NEW) to open a fresh one. Note also that a failure here cannot undo the original commit, so the listener has to be safe to fail.
  3. You add @TransactionalEventListener and the listener never runs. Why?
    Because nothing published the event inside a transaction. A transactional listener binds to the current transaction's synchronisation, and with no transaction there is nothing to bind to, so the event is silently dropped — no warning, no error. It happens when the publisher is called from a scheduled method, a test without @Transactional, or a controller with no service boundary. Set fallbackExecution = true to run it immediately in that case, or ensure the publisher is transactional.
  4. A @Scheduled job runs on three instances. What happens and how do you fix it?
    It runs three times, concurrently, because every instance has its own scheduler and no coordination — so invoices are generated three times, or three copies of a nightly email go out. The usual fix is a distributed lock such as ShedLock, which takes a row in the database keyed by job name so exactly one instance proceeds; alternatives are leader election or moving the trigger outside the application into a cron job or an orchestrator that runs one pod.
  5. Why is fixedDelay safer than fixedRate?
    Because it measures from the end of the previous run, so a job that takes longer than its interval simply runs less often and can never overlap or accumulate. fixedRate fires on a fixed schedule regardless of duration: with the default single-thread pool the runs queue behind each other and drift ever further behind, and with a larger pool they overlap and race on the same data. Unless you specifically need wall-clock cadence, use fixedDelay.
  6. Why does the default scheduler pool size of one matter?
    Because every @Scheduled method in the application shares that single thread. One job that takes four minutes delays every other job behind it, so a health-reporting task that should run each minute silently stops for the duration — and the symptom is a metric going flat rather than an error. Set spring.task.scheduling.pool.size to something matching your number of jobs, and remember that this makes overlap possible where it previously was not.
