What Spring actually is

Spring is usually described as magic, which is another way of saying nobody explained the mechanism. There are only three of them — a container that builds objects, a set of conditional beans that configure themselves, and proxies that wrap your methods. Everything in this unit is one of those three, and this chapter is where they get named.

Framework, Boot, and the naming problem

A large share of early confusion is vocabulary rather than concepts. Four things share the word "Spring" and do entirely different jobs.

Spring Framework
The core, dating from 2003. An inversion of control container that constructs your objects and wires them together, plus an aspect-oriented proxy mechanism, plus a web layer. This is where @Component, @Autowired and @Transactional come from.
Spring Boot
Not a rewrite — a layer on top of the framework that removes its configuration burden. Starters, auto-configuration, an embedded server, sensible defaults, and one runnable jar. Boot is why a working web service is twenty lines instead of six XML files.
Spring Data, Security, Batch, Integration…
Separate projects that build on the framework. Each has its own version and documentation. You add the ones you need.
Spring Cloud
A further set of projects for distributed systems — gateway, config server, circuit breakers, service discovery. Frequently adopted by teams who do not need any of it. Chapter 18.
What Boot actually does, concretely
  1. Starters. One dependency, spring-boot-starter-web, pulls in a coherent, version-matched set of about thirty jars. You stop resolving dependency conflicts by hand.
  2. Auto-configuration. On startup, Boot evaluates a few hundred conditional configuration classes: if a datasource is on the classpath and none is defined, create one. Chapter 4.
  3. An embedded server. Tomcat is a library inside your jar rather than a container you deploy into. java -jar app.jar is the whole deployment story.
  4. Externalised configuration. One consistent property system with a defined precedence order, profiles and type-safe binding. Chapter 3.
  5. Production endpoints. Health, metrics, tracing and environment info, one dependency away. Chapter 15.

Two things to turn on today

--debug, once. It prints the auto-configuration report: every candidate, whether it matched, and precisely which condition decided. It is the single best cure for believing Spring is magic, and chapter 4 is largely about reading it.

spring.jpa.open-in-view: false. The default is true, it is almost certainly wrong for an API, and it produces a startup warning that everyone ignores. Chapter 11 explains what it does and why leaving it on causes lazy-loading behaviour you did not ask for and connections held far longer than necessary.

The javax to jakarta rename

Oracle retained the javax trademark when Java EE moved to the Eclipse Foundation, so every package was renamed to jakarta. Nothing about the APIs changed — but every import, every third-party library and every code sample written before 2023 did. This is why an otherwise-correct Stack Overflow answer will not compile, and why an old library with no Jakarta release blocks the upgrade entirely. When reading anything about Spring, check whether it predates Boot 3; this unit is written against Boot 3.x on Java 21 throughout.

How to read this unit

The three mechanisms, again, because everything reduces to them. A container that instantiates your objects and injects their dependencies (chapter 2). Conditional configuration that creates beans depending on what is on the classpath and what you have already defined (chapter 4). And proxies that wrap your beans so a method call can be intercepted (chapter 6). When something surprising happens, it is one of those three, and the debugging question is which.

Build something alongside. A small order API is enough: it will need JPA in chapter 8, transactions in chapter 11, security in chapter 12, tests in chapter 14 and a container in chapter 19. Reading about LazyInitializationException teaches you far less than causing one.

Self-check

  1. What is the difference between Spring Framework and Spring Boot?
    The framework is the container, the AOP proxies and the web layer — the actual programming model, and it dates from 2003. Boot is a layer on top that removes the configuration work: starters that give coherent dependency sets, auto-configuration that creates beans conditionally, an embedded server, a unified property system and production endpoints. Boot introduces almost no new programming concepts; it makes the framework usable without a large XML or Java configuration effort.
  2. Why must the @SpringBootApplication class sit at the root of your package tree?
    Because it implies @ComponentScan, which scans the annotated class's package and everything beneath it. A component in a sibling package is never discovered, so it is not a bean, so injecting it fails — and the error talks about a missing bean rather than about packages, which makes it hard to recognise. Placing the class at the root makes the whole application visible by default.
  3. Name the three mechanisms that account for essentially all of Spring's behaviour.
    The IoC container, which constructs your objects and injects their dependencies rather than you calling new. Conditional auto-configuration, which creates beans based on what is on the classpath and what you have not already defined yourself. And proxies, which wrap beans so that annotated methods can be intercepted — the mechanism behind @Transactional, @Async, @Cacheable and method security. When behaviour surprises you, the useful first question is which of the three is responsible.
  4. Where does startup time go in a typical Spring Boot application?
    Mostly into work proportional to how much is on the classpath: scanning it, evaluating a few hundred auto-configuration conditions, and then instantiating beans. In an application with JPA, Hibernate's initialisation — scanning entities, building the metamodel, validating the schema — is usually the single largest phase. Tomcat starting is comparatively cheap. This is why adding dependencies costs startup time even when you never call them, and why a native image, which does all of this at build time, starts in tens of milliseconds.
  5. What does --debug give you, and why start with it?
    The auto-configuration report: every candidate configuration class, whether it matched, and the exact condition that decided — a missing bean, a class not on the classpath, a property not set. It converts "Spring did something I did not ask for" into a line you can read. Running it once on a new project is the fastest way to stop treating auto-configuration as magic, and it is how you debug both a bean that appeared and one that did not.
  6. You find a Spring code sample that will not compile. What is the first thing to check?
    Whether it uses javax.* imports. Boot 3 moved to the jakarta.* namespace, so anything written before 2023 imports packages that no longer exist — the APIs are identical and only the names changed. The same applies to third-party libraries: one without a Jakarta release will block a Boot 3 upgrade entirely, which is usually the hardest part of that migration.
