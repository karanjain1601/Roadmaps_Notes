Proxies and AOP

The third mechanism, and the one that produces Spring's most confusing bug. An annotation cannot change what a method does — so something must be sitting between the caller and the method. Once you can see that object, a whole family of "it just silently didn't work" problems becomes obvious.

— words— min read2 interactivesNeeds: chapter 02

The object you are actually holding

When a bean has a proxy-based annotation anywhere on it, the container does not give you your object. It gives you a wrapper that holds your object, and the wrapper is where the behaviour lives.

Where it happens
Chapter 2's lifecycle, step 8 — a BeanPostProcessor runs after initialisation, notices the annotation and returns a proxy in place of the bean. Everything injected with that type from then on receives the proxy.
JDK dynamic proxy
Implements the same interfaces as your class. Requires an interface, and only interface methods can be intercepted.
CGLIB proxy
Subclasses your class and overrides its methods. Boot's default since 2.0, and it works without an interface — which is why you no longer need a FooServiceImpl for every FooService.
The consequences
A final class cannot be subclassed and a final method cannot be overridden, so neither can be advised. A private method is invisible to the subclass. And a call that never leaves the object never passes through the wrapper at all.
The same method, called two ways
Run the internal call and watch the annotation do nothing
java — the bug, and the three ways out
@Service
class ImportService {

    @PostMapping
    public void handle(List<Row> rows) {
        importAll(rows);            ← ✗ a plain Java call on `this`.
    }                                 The proxy is not involved, so
                                      @Transactional does nothing.
    @Transactional
    public void importAll(List<Row> rows) { … }
}

// ── ① move it to another bean. The right answer almost always: the
//    call now crosses a bean boundary, so it goes through the proxy. ──
@Service class ImportOrchestrator {
    private final RowImporter importer;                ← a different bean
    public void handle(List<Row> rows) { importer.importAll(rows); }
}

// ── ② self-injection. Works, and advertises that the design is off. ──
@Service class ImportService {
    @Lazy private final ImportService self;         ← @Lazy avoids the cycle
    public void handle(List<Row> rows) { self.importAll(rows); }
}

// ── ③ TransactionTemplate — no proxy, no annotation, explicit. ──
public void handle(List<Row> rows) {
    txTemplate.executeWithoutResult(status -> importAll(rows));
}
//    verbose and completely unambiguous, which is sometimes what you
//    want in a method whose transaction boundaries have caused a bug.
The rules that follow from "it is a wrapper"
  • Public methods only. A private, protected or package-private method cannot be intercepted by a CGLIB subclass. Annotating one is silently ignored — no warning, no error.
  • No self-invocation. The demo above. This applies to every proxy-based annotation, not just @Transactional.
  • No final. A final class or method cannot be proxied by CGLIB, and Boot will fail at startup telling you so — which at least is loud. Kotlin classes are final by default, hence the allopen compiler plugin.
  • Not in a constructor or @PostConstruct. The proxy does not exist yet at that point, so a transactional or cached call made during initialisation runs unadvised.
  • Beware injecting the concrete class. With a JDK proxy the object does not extend your class, so injecting FooServiceImpl rather than FooService fails to cast. CGLIB avoids this, which is part of why it became the default.

Several annotations on one method

Each proxy-based feature adds an interceptor, and they nest. Which one is outermost changes the behaviour, and for some of them the order is not defined unless you define it.

java — an aspect, and the vocabulary
@Aspect @Component
@Order(100)                                   ← never omit this
class TimingAspect {

    // pointcut — WHERE the advice applies
    @Around("@annotation(com.shop.Timed)")      ← by annotation. Prefer this
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        long t = System.nanoTime();
        try {
            return pjp.proceed();               ← forget this and the method
        } finally {                               never runs. It returns null
            metrics.record(pjp.getSignature().getName(),    and nothing complains
                           System.nanoTime() - t);
        }
    }
}

When an aspect is the right tool

Genuinely cross-cutting concerns that would otherwise be copied into every method: timing, audit logging, retry, rate limiting per method. The test is whether the concern is orthogonal to what the method does. An aspect that encodes business logic is a rule nobody reading the method can see, and it will be rediscovered during an incident by someone who greps for a behaviour and finds nothing. Spring itself uses proxies heavily precisely because transactions and caching are orthogonal — that is the shape to copy, not the frequency.

Self-check

  1. Why can an annotation change a method's behaviour at all?
    Because you are not holding your object. During bean creation a post-processor sees the annotation and replaces the bean with a proxy — a CGLIB subclass, by default — that overrides the method, runs the extra behaviour and delegates to your instance. Everything injected with that type gets the proxy, so an ordinary-looking call goes through the wrapper first. The annotation is a marker; the wrapper is the mechanism.
  2. Why does calling a @Transactional method from another method in the same class do nothing?
    Because this.method() is a direct Java call on the target object, and the proxy is a different object wrapping it. The call never leaves the instance, so nothing intercepts it and no transaction is started. Nothing errors — the annotation is simply inert, which is what makes it hard to spot. Move the method to another bean, self-inject with @Lazy, or use a TransactionTemplate.
  3. Why is annotating a private method with @Cacheable silently useless?
    Because a CGLIB proxy works by subclassing and overriding, and a private method cannot be overridden — the subclass cannot see it. The same applies to final methods, though a final class at least fails loudly at startup. There is no warning for the private case, so the annotation reads as active and does nothing. Proxy-based annotations belong on public methods only.
  4. Should @Cacheable sit outside or inside @Transactional?
    Outside. With caching outermost, a cache hit returns without opening a transaction at all — no connection taken from the pool, no work. Inside, every hit still begins and commits a transaction to return a value from memory, which wastes a pooled connection on each one and can become the bottleneck under load. Both default to LOWEST_PRECEDENCE, so the relative order is not guaranteed; set it explicitly on @EnableCaching or @EnableTransactionManagement if it matters.
  5. Why does @PreAuthorize run before the transaction?
    By design — its interceptor has a much lower order value, so it wraps everything else. A rejected caller should be turned away before any work happens, including acquiring a database connection and starting a transaction. It also means an AccessDeniedException is thrown outside the transaction, so there is no transaction to roll back and no wasted connection.
  6. Why prefer @annotation(...) pointcuts over execution(...) name patterns?
    Because a name pattern is invisible from the call site and breaks silently. execution(* com.shop..*Service.*(..)) stops matching the day someone renames a class or moves a package, and nothing fails — the advice just quietly stops applying, so you lose the timing, the audit log or the retry without any signal. An annotation is visible in the code being advised and cannot drift out of scope by accident.
