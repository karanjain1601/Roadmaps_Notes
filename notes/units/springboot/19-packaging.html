FROM eclipse-temurin:21-jre AS build
WORKDIR /app
COPY build/libs/app.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted
#   produces four directories, ordered least- to most-frequently changed:
#     dependencies/  spring-boot-loader/  snapshot-dependencies/  application/

# ── one COPY per layer, in that order ──
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -m app && chown app /app
USER app
COPY --from=build /app/extracted/dependencies/ ./          ← changes monthly
COPY --from=build /app/extracted/spring-boot-loader/ ./
COPY --from=build /app/extracted/snapshot-dependencies/ ./
COPY --from=build /app/extracted/application/ ./           ← changes every deploy

ENTRYPOINT ["java", "-jar", "app.jar"]     ← no shell, so the process is
                                             PID 1 and receives SIGTERM

  shutdown: graceful                     ← not the default. Without it the

  lifecycle.timeout-per-shutdown-phase: 25s   ← how long to drain

# deployment.yaml
spec:
  terminationGracePeriodSeconds: 40      ← MUST exceed preStop + drain,
  containers:                              or SIGKILL cuts it short
    - lifecycle:

          exec:

      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8081 }

Why preStop is not optional

Kubernetes sends SIGTERM and starts removing the pod's endpoint at the same time, and the removal is asynchronous — kube-proxy on every node, the ingress controller, the service mesh sidecar and any client-side load balancer each learn about it independently, over one to five seconds. Without a delay, your application has already stopped accepting connections while traffic is still being routed to it, and those requests fail with a connection reset. A preStop sleep does nothing except keep serving during that window, and it is the difference between a clean rolling deploy and a burst of 502s on every release. It costs five seconds per pod and it is the single most common omission in a Spring Boot deployment.

Config in a container
Environment variables for plain settings, a mounted volume for secrets — chapter 3's configtree import reads one file per key, which is exactly the shape Kubernetes Secrets produce. Never bake either into the image.
Native images, revisited
Startup in tens of milliseconds and a fraction of the resident memory, at the cost of a build measured in minutes, declared reflection, no dynamic class loading, hints for some libraries, and peak throughput that can trail a warmed JIT on long-running work. Right for functions, CLIs and scale-to-zero; rarely right for a service that starts once a day. CDS gets you a third of the startup benefit for a build flag and no behavioural change — chapter 16 — and is the better first move.
What must never be in the image
Secrets, a .git directory, build tools, a shell as the entrypoint, or root as the user. A shell entrypoint is the subtle one: it becomes PID 1, may not forward SIGTERM, and your graceful shutdown never runs.
Migrations in the pipeline
A separate step before the deploy, not on application startup — otherwise a failed migration takes down every instance trying to boot, and several instances race to apply it. Flyway's lock prevents corruption, not the outage. Chapters 8 and 21 of the Backend unit.

Self-check

  1. Why does a layered image matter when the total size is identical?
    Because layers are cached and addressed by content. Your dependencies change monthly and your code changes every deploy, so splitting them means a deploy pushes and pulls only the small application layer — a couple of megabytes instead of sixty. That is faster CI, faster pod starts, and dramatically less registry traffic when you multiply by deploys per day and pods per deploy. A single-layer fat jar invalidates the whole cache on every commit.
  2. Why is server.shutdown: graceful not enough on its own?
    Because it only governs what happens after SIGTERM: the server stops accepting new connections and drains in-flight requests. It does nothing about traffic still being routed to the pod, since endpoint removal propagates asynchronously across kube-proxy, the ingress and any mesh sidecar over one to five seconds. During that window your application is correctly refusing connections and the network is correctly sending them, so requests fail. A preStop sleep covers the gap.
  3. What exactly does a preStop sleep accomplish?
    It delays SIGTERM while the container keeps serving normally, giving the endpoint removal time to reach every routing component. Nothing else — it is not draining, not signalling, not cleaning up. Kubernetes runs it and only then sends the signal, so the pod is out of rotation by the time the application starts shutting down. Five seconds is a reasonable default, sized above your readiness probe period.
  4. Why must terminationGracePeriodSeconds exceed preStop plus the drain timeout?
    Because it is a hard deadline: when it expires Kubernetes sends SIGKILL regardless of what the process is doing. If preStop is 5 seconds and the drain timeout is 25, the process needs 30 — and a grace period of 30 or less means it is killed mid-request, which is precisely the failure graceful shutdown was configured to prevent. The three numbers have to be set together, and only one of them lives in the application's own configuration.
  5. Why is a shell entrypoint a problem?
    Because the shell becomes PID 1 and the JVM becomes its child. Depending on how the command is written, the shell may not forward SIGTERM to the child at all — so the application never learns it is shutting down, graceful shutdown never runs, in-flight requests are lost, and the container is eventually SIGKILLed. Use the exec form so the JVM is PID 1 and receives signals directly.
  6. Why run migrations as a pipeline step rather than at application startup?
    Because a failed migration at startup takes down every instance that tries to boot, turning a schema problem into a total outage — and during a rolling deploy several instances race to apply it, so you are relying on the migration tool's lock to avoid corruption. As a separate step it either succeeds or halts the deploy before any new instance starts, which is a contained failure. It also forces the migration to be backwards compatible with the running version, which is chapter 8's expand-and-contract.
