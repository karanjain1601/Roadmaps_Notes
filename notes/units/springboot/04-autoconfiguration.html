Starters and auto-configuration

The second mechanism, and the one people mean when they call Spring magic. It is not magic: it is a few hundred configuration classes, each guarded by conditions, evaluated in a defined order at startup — and Boot will print the whole decision for you if you ask.

— words— min read2 interactivesNeeds: chapters 02, 03

What a starter is

A starter contains no code. It is a build file listing a coherent, version-matched set of dependencies — and the reason you stop resolving conflicts between Jackson, Tomcat and Hibernate by hand.

How auto-configuration decides

Each starter's jar contains a file listing auto-configuration classes. Boot loads all of them, then evaluates each one's conditions — and rejects most.

java — an auto-configuration class, annotated
// registered in META-INF/spring/…AutoConfiguration.imports — a plain
// text file of class names. That is the whole discovery mechanism.

@AutoConfiguration(after = DataSourceAutoConfiguration.class)   ← ordering
@ConditionalOnClass(EntityManager.class)          ← is JPA on the classpath?
@ConditionalOnBean(DataSource.class)             ← did something create one?
@ConditionalOnProperty(name = "spring.jpa.enabled",
                       havingValue = "true", matchIfMissing = true)
public class HibernateJpaAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                     ← THE important one. If you
    EntityManagerFactory entityManagerFactory(…) {     declared your own, this
        …                                            method never runs.
    }
}
ConditionMatches when
@ConditionalOnClassA class is on the classpath. Checked from bytecode, so the class is never loaded — that is why a missing type does not throw
@ConditionalOnMissingClassIt is absent
@ConditionalOnBeanA bean of that type is already defined. Ordering-sensitive, so it is mostly used inside auto-configurations
@ConditionalOnMissingBeanNothing has defined one. This is the mechanism that lets you override anything by simply declaring your own
@ConditionalOnPropertyA property has a value — with matchIfMissing deciding the default
@ConditionalOnWebApplicationThe context is servlet-based, or reactive. Why a batch job creates no Tomcat
@ConditionalOnResourceA file exists on the classpath
@ConditionalOnExpressionA SpEL expression is true. The escape hatch, and a smell in your own code
The condition report
This is what --debug prints. Change the classpath and watch it re-decide
The one insight that makes this stop being magic

Nearly every bean Boot creates is annotated @ConditionalOnMissingBean. That single fact explains the whole override story: to replace anything Spring configured, define a bean of that type yourself and Boot's version silently steps aside. No exclusion, no property, no subclassing. It also explains a class of confusing bug — declare a bean of a type Boot was going to create and you may switch off a dozen other things that depended on it, all quietly, because their conditions no longer match.

Overriding and excluding

java — four ways, in the order you should try them
// ① define your own bean. Works because of @ConditionalOnMissingBean,
//    and it is the right answer perhaps nine times in ten.
@Bean
ObjectMapper objectMapper() {
    return JsonMapper.builder().addModule(new JavaTimeModule()).build();
}

// ② customise rather than replace. Most auto-configurations expose a
//    customizer interface precisely so you do not have to take over.
@Bean
Jackson2ObjectMapperBuilderCustomizer json() {
    return b -> b.failOnUnknownProperties(false).simpleDateFormat("yyyy-MM-dd");
}
//    prefer this: you keep every default Boot set and change one thing.

// ③ a property, where one exists
//    spring.jpa.open-in-view: false        spring.flyway.enabled: false

// ④ exclude the whole auto-configuration. Last resort — it is a
//    blunt instrument and takes its dependants with it.
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
//    or: spring.autoconfigure.exclude=org.springframework...DataSourceAutoConfiguration
java — your own auto-configuration, for a shared internal library
// src/main/java/com/acme/audit/AuditAutoConfiguration.java
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@ConditionalOnProperty(prefix = "acme.audit", name = "enabled", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean              ← always. Let consumers override
    AuditClient auditClient(AuditProperties props) {
        return new AuditClient(props.endpoint(), props.timeout());
    }
}

// src/main/resources/META-INF/spring/
//   org.springframework.boot.autoconfigure.AutoConfiguration.imports
// containing one line:
//   com.acme.audit.AuditAutoConfiguration

// naming convention, and it matters for discoverability:
//   acme-audit-spring-boot-starter      ← yours
//   spring-boot-starter-acme-audit      ← reserved for the Spring team
Diagnosing it
  • --debug, or debug: true in your yml. Prints positive matches, negative matches and exclusions with the deciding condition for each.
  • /actuator/conditions gives the same report as JSON on a running application — useful when the failure only happens in an environment you cannot restart with a flag.
  • "Consider defining a bean of type X" usually means a condition you did not notice failed upstream. Search the report for the auto-configuration that would have created X and read its reason.
  • A bean appeared that you did not want. The report tells you which class created it and which condition allowed it — then override with your own bean rather than excluding.
  • It works in a test and not in production. Test slices load a restricted set of auto-configurations, so the two contexts genuinely differ. Chapter 14.

Self-check

  1. What does a starter actually contain?
    No code — just a build file declaring a coherent set of dependencies, with versions supplied by Boot's bill of materials. Its value is that the combination is tested together, so you never resolve a conflict between Jackson, Tomcat and Hibernate yourself. The auto-configuration classes live in the libraries the starter pulls in, not in the starter.
  2. How does Boot discover auto-configuration classes?
    From a plain text file inside each jar — META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports — listing class names one per line. Boot reads every copy on the classpath, loads the listed classes and evaluates their conditions. There is no scanning and no reflection over your packages; that is why adding a dependency can add beans, and why the mechanism is cheap enough to run at every startup.
  3. Why is @ConditionalOnMissingBean the most important condition?
    Because it is what makes Boot's defaults overridable by simply declaring your own bean of that type. There is no exclusion list to maintain and no subclassing — Boot checks whether you already provided one and steps aside. It also explains a confusing failure mode in the other direction: defining a bean of a type Boot was going to create can silently disable other auto-configurations whose @ConditionalOnBean expected Boot's version.
  4. Why prefer a customizer bean over replacing the auto-configured one?
    Because replacing it discards every default Boot applied — and those defaults are numerous, sensible and undocumented in your codebase. A Jackson2ObjectMapperBuilderCustomizer changes one setting and keeps the rest, including future ones added by a Boot upgrade. Taking over the whole bean means silently freezing behaviour at whatever you knew on the day you wrote it.
  5. Startup fails with "Consider defining a bean of type X". What do you do?
    Run with --debug and find the auto-configuration that would have created X in the negative matches — the report names the exact condition that failed. Usually a class is missing from the classpath, a required property is unset, or an upstream bean was not created so a @ConditionalOnBean did not match. The error names the symptom; the report names the cause.
  6. When is excluding an auto-configuration the right move?
    Rarely, and mostly when you want a dependency's classes on the classpath without its configuration — a driver present for a tool but no datasource wanted, for instance. It is blunt: excluding one class also disables everything whose conditions depended on the beans it would have created, and those failures appear far from the exclusion. Try defining your own bean first, then a customizer, then a property; exclusion last.
