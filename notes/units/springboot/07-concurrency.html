Servlet, virtual threads and WebFlux

For twenty years Spring had one answer — a thread per request — and one escape hatch for when that was too expensive, which was to rewrite everything reactively. Java 21 changed the arithmetic, and the honest conclusion is that most teams reaching for WebFlux today no longer need to.

— words— min read2 interactivesNeeds: chapter 05

Three models

Platform threads — the classic model
Tomcat takes a thread from a pool of 200 and it belongs to that request until the response is written. Simple, debuggable, and every stack trace and ThreadLocal works the way you expect. The limit is the pool: at 200 concurrent slow requests, the 201st waits.
Virtual threads — Boot 3.2 on Java 21
The same programming model, with threads that cost a few kilobytes instead of a megabyte and unmount from their carrier when they block. One property, no code change, and the 200-thread ceiling effectively disappears.
WebFlux — reactive
A handful of event-loop threads and a chain of Mono and Flux operators. Very high concurrency on modest hardware, and a substantially harder model: no blocking anywhere, different stack traces, and every library in the path must be reactive too.

//        pooled thread. ScopedValue is the replacement.

Why this is the significant change

The reactive argument was never that callbacks are nicer. It was that a thread costs a megabyte of stack and a context switch, so tens of thousands of concurrent connections needed a model that did not use one per request — and the price was rewriting your code as operator chains, giving up ordinary stack traces, and requiring every library in the path to be non-blocking. Virtual threads deliver the same scalability while keeping the blocking programming model, which removes most of the reason to pay that price. WebFlux remains the better answer for genuine streaming, for backpressure across a pipeline, and for teams already fluent in it — but "we need reactive to scale" is now a claim worth testing rather than assuming.

java — the same endpoint in both styles
// ── MVC. Reads top to bottom; a stack trace points at line 4. ──
@GetMapping("/{id}")
OrderView get(@PathVariable UUID id) {
    var order = repo.findById(id).orElseThrow(NotFoundException::new);
    var user  = users.fetch(order.userId());       ← blocking, and fine
    return OrderView.of(order, user);
}

// ── WebFlux. Never blocks, and never returns a value directly. ──
@GetMapping("/{id}")
Mono<OrderView> get(@PathVariable UUID id) {
    return repo.findById(id)                          ← Mono<Order>, R2DBC
        .switchIfEmpty(Mono.error(new NotFoundException()))
        .flatMap(order -> users.fetch(order.userId())  ← Mono<User>, WebClient
            .map(user -> OrderView.of(order, user)));
}
// what you give up, concretely:
//   · stack traces describe the operator chain, not your call path.
//     Reactor's checkpoint() and onOperatorDebug() exist because of this
//   · ThreadLocal does not work — no MDC logging, no SecurityContext,
//     no transaction bound to the thread. Context propagation is manual
//   · @Transactional is replaced by a reactive transaction manager, and
//     JPA does not participate at all: R2DBC or nothing
//   · every library must be non-blocking. One synchronous SDK in the
//     chain undoes the whole thing, as the demo above shows
BlockHound, and why you want it in tests

A blocking call on an event loop is not a slow endpoint — it is a stalled server, and it is invisible in development where you are the only user. BlockHound instruments the JVM to throw whenever a blocking call happens on a non-blocking thread, which turns a production outage into a failing test. If you run WebFlux, add it to the test classpath; it is the single highest-value safeguard available, and it catches the third-party SDK you did not know was synchronous.

Choosing, in one paragraph

Start with MVC. Turn on virtual threads if you are on Java 21 and expect high concurrency — it costs one property and no code. Use CompletableFuture where you need to fan several calls out in parallel. Reach for WebFlux when you have a specific reason: streaming with backpressure end to end, tens of thousands of long-lived connections, an existing reactive codebase, or a gateway-shaped service that is almost entirely I/O with no blocking libraries anywhere. Do not mix them casually — a WebFlux application with one blocking JDBC call is worse than either option chosen honestly, and the failure looks like the server being down rather than an endpoint being slow.

Self-check

  1. What limits concurrency in the classic servlet model?
    The thread pool — 200 by default in Tomcat. A thread belongs to a request until the response is written, so 200 requests waiting on a slow dependency occupy the entire pool and the 201st queues at the connector. The cost is not CPU; it is that a platform thread reserves around a megabyte of stack, which is what made a pool necessary in the first place.
  2. What does spring.threads.virtual.enabled actually change?
    Tomcat serves each request on a newly created virtual thread instead of borrowing a pooled platform thread, and @Async and @Scheduled get virtual-thread executors. Your code is untouched — blocking calls are fine, stack traces still make sense, ThreadLocal still works. The practical effect is that the thread pool stops being the ceiling on concurrency, since a virtual thread costs kilobytes and unmounts from its carrier while blocked.
  3. You enable virtual threads and throughput does not improve. Why might that be?
    Because the bottleneck was somewhere else. Ten thousand virtual threads reaching for a connection pool of twenty is a queue rather than throughput — you have moved the constraint to the database. Other candidates: the work is CPU-bound, so cores remain the ceiling; a synchronized block is pinning carriers on JDK 21; or a downstream service is itself the limit. Virtual threads remove one specific constraint and reveal whatever was behind it.
  4. Why is one blocking call in a WebFlux handler so much worse than in MVC?
    Because there are only a handful of event-loop threads — usually one per core — and they serve every request. Blocking one removes a large fraction of the server's total capacity, and blocking all of them stops the application entirely, including endpoints that touch nothing. In MVC the same call occupies one of 200 threads and affects one request. The symptom is also different: not a slow endpoint but a server that appears to be down.
  5. What do you give up by choosing WebFlux, beyond the syntax?
    Ordinary stack traces, which become operator chains rather than call paths. ThreadLocal, which means MDC logging, the security context and thread-bound transactions all need explicit context propagation. JPA and Hibernate entirely — R2DBC or nothing. And the requirement that every library in the request path is non-blocking, which is the constraint that most often turns out to be violated by a third-party SDK.
  6. Why add BlockHound to a WebFlux project's test classpath?
    Because a blocking call on an event loop is invisible in development, where you are the only user, and catastrophic in production. BlockHound instruments the JVM to throw as soon as a blocking operation happens on a non-blocking thread, so the problem becomes a failing test at the moment it is introduced. It is the cheapest way to catch the synchronous dependency nobody realised was synchronous.
