Web MVC and REST controllers

A request arrives at Tomcat and eventually one of your methods is called with typed arguments. Between those two events sit about a dozen components, and knowing which is which is the difference between fixing a binding problem in a minute and guessing at annotations for an hour.

The consequence people meet first

An exception thrown in a filter never reaches your @ControllerAdvice, because the advice lives inside the DispatcherServlet and the filter ran before it. You get the container's error page instead — which is why an authentication failure returns something that does not match your API's error format. Spring Security has its own AuthenticationEntryPoint and AccessDeniedHandler for exactly this reason, and wiring them to produce the same body as your advice is a real task rather than an oversight. Controllers and binding

java — the argument types worth knowing
@RestController                                ← @Controller + @ResponseBody
@RequestMapping("/v1/orders")
class OrderController {

    @GetMapping
    Page<OrderSummary> list(
            @RequestParam(defaultValue = "PENDING") Status status,  ← String→enum,
            @RequestParam Optional<LocalDate> since,               automatically
            Pageable pageable) { … }                          ← ?page=2&size=50&sort=id,desc

    @GetMapping("/{id}")
    OrderResponse get(@PathVariable UUID id) { … }         ← name inferred from the
                                                               parameter, if -parameters
    @PostMapping                                          is on. Boot's plugin sets it
    @ResponseStatus(HttpStatus.CREATED)
    OrderResponse create(@Valid @RequestBody CreateOrder body,
                          @RequestHeader("Idempotency-Key") String key,
                          UriComponentsBuilder uri) { … }

    @PatchMapping("/{id}")
    ResponseEntity<OrderResponse> patch(@PathVariable UUID id,
                                        @RequestBody JsonNode patch) { … }
}

// records make excellent request and response types: immutable,
// concise, and Jackson binds them by constructor since 2.12.
record CreateOrder(@NotNull UUID productId,

Never expose an entity as a request or response type

It couples your API to your schema, so a column rename becomes a breaking change; it leaks fields nobody meant to publish; on the way in it is mass assignment, letting a client set id, status or accountId by adding them to the body — chapter 15 of the Backend unit; and on the way out it triggers lazy loading during serialisation, which is chapter 11's open-session-in-view problem in its most common form. Use records for the boundary and map explicitly. The mapping code is boring and it is the boundary doing its job.

Errors

The default behaviour is reasonable for the exceptions Spring knows about and wrong for every exception you define — which is most of the interesting ones.

What the client actually receives
Try the custom exception with no handling first
java — one advice class for the whole application
@RestControllerAdvice
class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    // your own exceptions → a stable, documented problem type
    @ExceptionHandler(NotFoundException.class)
    ProblemDetail notFound(NotFoundException e) {
        var p = ProblemDetail.forStatusAndDetail(NOT_FOUND, e.getMessage());
        p.setType(URI.create("https://api.shop/problems/not-found"));   ← clients
        p.setTitle("Resource not found");                                branch on
        return p;                                                       this, never
    }                                                                   on the text

    // override the framework's handling of validation to add field detail
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException e, HttpHeaders h,
            HttpStatusCode status, WebRequest req) {
        var p = ProblemDetail.forStatus(UNPROCESSABLE_ENTITY);
        p.setTitle("Validation failed");
        p.setProperty("errors", e.getFieldErrors().stream()
            .map(f -> Map.of("field", f.getField(),
                             "code",  f.getCode(),
                             "detail", f.getDefaultMessage())).toList());
        return ResponseEntity.of(p).build();
    }

    // the catch-all. Log the cause; tell the client nothing about it.
    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception e) {
        String id = MDC.get("traceId");
        log.error("unhandled traceId={}", id, e);
        var p = ProblemDetail.forStatusAndDetail(INTERNAL_SERVER_ERROR,
                    "Unexpected error. Quote this id when contacting support.");
        p.setProperty("traceId", id);          ← chapter 15. This one field turns
        return p;                               a support ticket into a log query
    }
}

// and one property, which switches the built-in errors to ProblemDetail:
//   spring.mvc.problemdetails.enabled: true

Converters and negotiation

Message converters
A @RequestBody parameter is deserialised, and a returned object serialised, by an HttpMessageConverter chosen from the Content-Type and Accept headers. With Jackson on the classpath, JSON is the default and you rarely think about it — until you add a second format, or return a String and discover it goes through the plain-text converter instead.
Content negotiation
Boot's default is the Accept header only. Path extensions and a format parameter are off by default in Boot 3, which is correct — extension-based negotiation has been a source of security problems.
Configuring Jackson
Use properties (spring.jackson.*) or a Jackson2ObjectMapperBuilderCustomizer, not a replacement ObjectMapper bean. Chapter 4 — replacing it discards a dozen defaults you did not know were there, including the ones that make Instant serialise as ISO-8601 rather than a number.
Dates
Set spring.jackson.serialization.write-dates-as-timestamps: false and use java.time throughout. An epoch number in an API response is a decision you will regret in a different language's client.

Self-check

  1. Why does an exception thrown in a servlet filter not reach your @ControllerAdvice?
    Because filters run outside the DispatcherServlet, and the advice mechanism lives inside it. By the time a filter throws, the dispatcher has either not been entered or has already returned, so the container handles the error with its own page. This is why authentication failures come back in a shape that does not match the rest of your API — Spring Security throws in a filter, and you have to wire an AuthenticationEntryPoint to produce the same body.
  2. You throw a custom OrderNotFoundException and the client gets a 500. Why?
    Because Spring has no idea what it means. It knows how to map its own exceptions to statuses, and yours is just an unhandled runtime exception, so it becomes an internal server error. Three fixes: annotate the exception with @ResponseStatus(NOT_FOUND), throw a ResponseStatusException instead, or — best for anything beyond a small application — handle it in a @RestControllerAdvice so the status and the body shape are defined in one place.
  3. Why should an entity never be a request or response type?
    Four reasons at once. It couples the API to the schema, so renaming a column breaks clients. It publishes every field, including ones nobody intended. On the way in it is mass assignment — a client can set id or accountId by adding them to the body. And on the way out, serialising it walks lazy associations, which triggers extra queries during response writing. A record at the boundary costs a few lines of mapping and removes all four.
  4. What does @Valid on a nested object do that its absence does not?
    Cascades validation into it. Constraints on a nested type's fields are simply not evaluated unless the field holding it is annotated @Valid — so an Address with @NotBlank on every field passes validation silently if the parent record's shipTo field lacks the annotation. It is a quiet failure: nothing errors, the constraints just never run.
  5. When is a filter the right choice over an interceptor?
    When you need to run for every request including static resources and error dispatches, when you need to wrap or read the request or response body, or when you must run before Spring MVC is involved at all — security, correlation ids, request logging, compression. An interceptor is better when you want to know which handler method was selected, since it runs after handler mapping: per-endpoint timing, feature flags, auditing that needs the method name.
  6. Why configure Jackson with a customizer rather than your own ObjectMapper bean?
    Because Boot's auto-configured mapper carries a set of defaults — module registration, date handling, null inclusion, well-known feature flags — and declaring your own replaces all of them via @ConditionalOnMissingBean. A Jackson2ObjectMapperBuilderCustomizer changes one setting and inherits the rest, including any added by a future Boot upgrade. Taking over the bean silently freezes your serialisation behaviour at whatever you knew that day.
