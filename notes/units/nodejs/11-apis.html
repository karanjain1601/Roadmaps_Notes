Building an API

JavaScript has no types at runtime, so every request body is any until you check it. A schema at the boundary is therefore not a nicety in Node — it is the only thing standing between a client's imagination and your database.

OpenAPI, generated
If the schema is JSON Schema — TypeBox, or Fastify's native form — the specification falls out of the route definitions with a plugin. Hand-written OpenAPI drifts from the code within weeks; generated OpenAPI cannot.
Set a body limit
Every framework has one and the default is often 1 MB or absent. Set it per route: an upload endpoint and a JSON endpoint have very different needs, and the JSON one should refuse anything large before it is parsed rather than after.
Version by adding, not changing
New optional fields and new endpoints do not break clients; removing a field or tightening a type does. Chapter 5 of the Backend unit — the tolerant-reader argument applies to you as a provider as well as a consumer.
Never return the database row
Same argument as chapter 5 of the Spring Boot unit, and it is worse in Node because there is no compiler stopping you: an ORM object serialises every column it loaded, including passwordHash and internal flags, and a new column appears in your API the day it appears in the schema.

Self-check

  1. Why is a schema at the boundary more necessary in Node than in a typed runtime?
    Because TypeScript's types are erased at compile time. Declaring a parameter as CreateOrder tells you nothing about what arrives at runtime — the body is genuinely any, and asserting a type on it is a lie the compiler happily accepts. A schema is the only thing that actually checks, and deriving the type from the schema means the two cannot drift apart.
  2. What is wrong with passing unknown keys through to your handler?
    It is mass assignment. If the object reaches an ORM or a spread into an update, a client can set fields you never exposed — id, status, accountId, role, priceOverride. Nothing errors, because the extra keys are simply extra properties. Strip unknown keys or reject them outright; the default in most schema libraries is to strip, which is safe, and passthrough is the option to avoid.
  3. Why does every string field need a maximum length?
    Because otherwise the client decides how much memory a row occupies, how large your indexes grow, and how much CPU is spent serialising it back. A 900 KB "product name" passes a type check perfectly. It is also a denial-of-service vector that costs the attacker one request, and it is the field constraint most often omitted because the happy path never needs it.
  4. At what point does JSON.stringify become an availability problem?
    When its CPU time multiplied by your request rate approaches one thread. Serialisation is synchronous, so a 500 KB response costs a few milliseconds during which nothing else in the process runs — and at a couple of hundred requests a second that is the whole thread. The symptom is rising event loop lag and a failing health check rather than a slow endpoint, which is chapter 3's blocking demo arriving through the response path.
  5. What does a schema-compiled serialiser buy over JSON.stringify?
    Roughly twice the speed, because it generates straight-line code for a known shape instead of walking an arbitrary object — and, more importantly, it is a whitelist: any property not in the response schema is dropped. That makes accidental field leakage structurally impossible rather than a matter of remembering to map to a DTO. A performance feature that is also a security property is rare enough to take.
  6. Why must the idempotency key be inserted in the same transaction as the effect?
    Because otherwise a crash between them leaves the effect applied with no record of the key, so the retry does the work again — the exact failure the mechanism exists to prevent. Insert the key with on conflict do nothing inside the transaction that creates the order, and let the unique index be the enforcement rather than a check-then-act, which has a window two concurrent requests will find.
