Express, Fastify, NestJS, Hono

Four answers to the same question, and they differ far more in structure than in speed. The throughput numbers are the part everyone quotes and almost never the part that matters; the request lifecycle is what you will live inside every day.

  @UseGuards(AuthGuard)

  return c.json(toDto(order));

Middleware against hooks
Express's model is one list: every concern is a function that may call next(), and ordering is the only structure. Fastify names the stages, so "validate before this, serialise after that" is expressible rather than implied by registration order — and its plugins are encapsulated, so a plugin registered inside a scope does not leak into its siblings. That encapsulation is the real difference, more than the hooks.
NestJS is a structure, not a speed choice
Modules, providers and constructor injection, with guards, interceptors, pipes and filters as named extension points. It pays for itself on a large codebase and a team that needs conventions, and it is a lot of ceremony for six endpoints. If chapters 2 and 4 of the Spring Boot unit felt familiar, this will too — deliberately.
Hono and the web-standard shape
Handlers take a Request and return a Response, so the same code runs on Node, Bun, Deno, Cloudflare Workers and Lambda. If you may deploy to more than one of those, that portability is worth more than any benchmark on this page.
The migration nobody plans
Framework choice is stickier than it looks: middleware, error shapes, testing helpers and the DI container all leak into your code. Choosing for benchmark numbers and living with the structure for four years is the wrong trade in nearly every case.

Self-check

  1. Why is Express 4 a poor choice for new work?
    Because it does not await your handlers. A rejected promise from an async route is floating, so nothing observes it and Node terminates the process — chapter 5. Every other framework here, including Express 5, awaits the handler and routes a rejection into its error pipeline. The workaround on Express 4 is a wrapper around every async handler, and relying on that discipline in a growing codebase is a bet you will eventually lose.
  2. What does Fastify's schema do beyond validation?
    It serialises. A response schema is compiled into a purpose-built stringifier, which is both substantially faster than JSON.stringify and a whitelist — any field not in the schema is dropped, so an accidentally returned passwordHash cannot leak. The same schema also generates OpenAPI documentation. One declaration covering validation, serialisation, security and docs is the strongest argument for the framework.
  3. What is plugin encapsulation and why does it matter?
    In Fastify, anything registered inside a plugin scope — hooks, decorators, parsers — applies only within that scope and its children, not to sibling routes. So an authentication hook added for the admin routes cannot accidentally start running on the public ones. Express has no such boundary: middleware registered on the app applies to everything after it, and ordering is the only mechanism you have.
  4. At four kilobytes and one database query, does the framework choice affect throughput much?
    Barely. A 6 ms query caps a single thread at about 165 requests a second regardless of framework, and the frameworks differ by tens of microseconds per request — a rounding error against six milliseconds of waiting. The benchmarks people quote measure a handler that returns a constant, which is not a workload anyone deploys. Framework speed becomes relevant only when the handler is genuinely cheap: a proxy, a cache-hit path, a health endpoint.
  5. When does payload size make the framework matter?
    When serialisation starts to dominate. JSON.stringify on a large response is CPU work on the one thread, so at a few hundred kilobytes it becomes the largest single cost in the request — and a schema-compiled serialiser is roughly twice as fast at that point. Above that, the right answer is usually not a faster serialiser but streaming the response, which is chapter 6.
  6. Why is framework choice stickier than it appears?
    Because it leaks into everything: middleware packages, the error shape, request-scoped context, testing helpers, and in NestJS's case the whole dependency-injection model. None of that is portable, so a migration touches every file rather than one adapter. That makes structure and team fit the decision criteria, and benchmark numbers close to irrelevant — you are choosing what the codebase will look like for years.
