Deployment and process management

Node deploys easily and shuts down badly. The default action for SIGTERM is immediate termination, which means an application that ignores it drops in-flight requests on every single release — and that is only the first of four things the shutdown path needs.

The image

Six changes to a Dockerfile
The second one changes the deploy, not the size
dockerfile — the end state
# ---------- build ----------
FROM node:22-slim AS build
WORKDIR /app

COPY package*.json ./            # ① package files FIRST, so the
RUN npm ci --ignore-scripts      #   install layer is cached until a
                                 #   dependency actually changes.
COPY . .                         #   Chapter 8 on --ignore-scripts.
RUN npm run build

# ---------- runtime ----------
FROM gcr.io/distroless/nodejs22-debian12
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
# distroless has no shell, no package manager, no curl — so an RCE
# has nothing to pivot with. It also means no exec debugging: keep a
# :debug variant of the tag for when you need one.

USER nonroot
ENV NODE_ENV=production
ENV NODE_OPTIONS="--max-old-space-size=768 --enable-source-maps"
#   ✱ ~75% of the container's memory limit. V8 sizes its default heap
#     ceiling from the HOST, so without this it grows past your limit
#     and is OOM-killed instead of running a major GC. Chapter 16.

CMD ["dist/server.js"]           # no shell form, so the process is
                                 # PID 1 and receives SIGTERM directly

# ✱ do NOT run PM2, nodemon or a shell wrapper in a container. The
#   orchestrator is the process manager; a wrapper swallows signals
#   and hides crashes from the restart policy. PM2 and systemd are
#   for a VM, where nothing else is supervising you.

# ✱ .dockerignore — node_modules, .git, dist, coverage, .env
#   Without it the build context is hundreds of megabytes and your
#   local node_modules can shadow the installed one.

Parse every environment variable into a typed, frozen object at startup and refuse to start if something required is missing or malformed. A missing variable should be a container that never becomes ready, not a TypeError at 4pm on the one code path that reads it — chapter 3 of the Spring Boot unit.

Chapter 15's warning, and it applies to any library sizing a pool from core count. Check what your worker pool, image library and thread-pool settings are actually reading.
Migrations are a pipeline step
A job before the rollout, never on application start — several instances would race, and a failed migration would stop every one of them from booting. Expand and contract: add the column, deploy code that writes both, backfill, deploy code that reads the new one, drop the old. Every intermediate state must work with both versions running, because during a rolling deploy they are.
Pin the Node version everywhere
The same version in engines, the .nvmrc, the Dockerfile and CI. A minor difference in fetch, structuredClone or the module resolver is a genuine and very confusing source of "works on my machine".

Self-check

  1. Why does copying package*.json before the source change the deploy rather than the image?
    Because Docker layers are cached by their inputs. If the source is copied before npm ci, any code change invalidates the install layer and the dependencies are reinstalled and re-pushed every build. Copying the manifests first means the install layer is reused until a dependency actually changes, so a code-only deploy transfers a few megabytes instead of hundreds. The final image is the same size; the build and the push are transformed.
  2. What does a distroless base buy, and cost?
    It removes the shell, the package manager and every utility, so a remote code execution has nothing to pivot with — no curl to fetch a payload, no sh to run one — and the vulnerability scanner has almost nothing to report. The cost is that you cannot exec into it to investigate. Keep the :debug tag available for when you need a shell, and rely on logs and metrics the rest of the time.
  3. Why must a Node process handle SIGTERM explicitly?
    Because the default action is immediate termination. Every in-flight request is cut off mid-response and every keep-alive connection is severed, and since a rolling deploy sends SIGTERM to each instance in turn, an application without a handler drops requests on every release. It shows up as a small burst of 502s correlated with deploys, which is easy to attribute to the deploy tooling rather than to the application.
  4. Why is server.close() alone not enough?
    For two reasons. It stops accepting new connections and waits for existing ones to end — but an idle keep-alive connection is not ended, so the callback may not fire until the keep-alive timeout, and the process is SIGKILLed at the end of the grace period. closeIdleConnections() fixes that. And it does nothing about requests still arriving, because the load balancer has not yet learned this instance is going away.
  5. Why does a preStop delay matter more than everything else?
    Because SIGTERM and the load-balancer update are concurrent, not sequential. The endpoint removal takes seconds to propagate, and during that window traffic is still being routed to a process that has stopped accepting it — at a few hundred requests a second, that is by far the largest number in the demo. Marking readiness false and sleeping a few seconds before closing the server lets the propagation finish while the instance is still serving.
  6. Why not run PM2 inside a container?
    Because it duplicates what the orchestrator does and interferes with it. PM2 becomes PID 1, may not forward signals correctly, and restarts a crashed process internally — so the container stays "healthy" while the application is crash-looping invisibly, and the restart policy and crash metrics you actually rely on never fire. One process per container, PID 1, signals direct. PM2 and systemd are for a VM, where nothing else is supervising.
