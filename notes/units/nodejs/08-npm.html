Chapter 08 · Platform

npm, versions and supply chain

The registry is the best thing about Node and the largest liability in it. A dozen direct dependencies routinely become several hundred packages written by several hundred people, all of whom can run code on your machine at install time. This chapter is about seeing that clearly enough to make deliberate choices.

What semver promises, and what it does not

Semver is a statement of intent by the author, not a property the registry verifies. A patch release can and regularly does break you — through a behaviour change nobody classified as breaking, a transitive dependency bump, a tightened type definition, or a genuine mistake. That is why the lockfile is the actual contract and npm ci is the only install command that honours it. Ranges describe what you are willing to accept when you next update; the lock describes what you tested.

Why pnpm is worth considering
A content-addressed store with hard links, so one copy of a version on disk regardless of how many projects use it — and a strict layout where a package can only import what it declared. That second property is the real benefit: npm's flat node_modules lets you import something you never listed, and it works until a version resolution changes and it does not.
Workspaces
One lockfile and one install for several packages in a repository, with local packages linked rather than downloaded. Native in npm, pnpm and yarn; use imports from chapter 2 for internal aliases rather than deep relative paths.
Before adding a dependency
Check whether Node already has it — chapter 1's list is longer than most people think. Then check its own dependency count, its last release, whether it has one maintainer, and how much of it you actually need. A four-line utility is not worth a package.
Version your Node too
engines plus a .nvmrc or .node-version, and the same version pinned in the Dockerfile and in CI. "Works on my machine" is very often a minor Node version difference in something like structuredClone or fetch.

Self-check

  1. What does ^1.2.3 allow, and what does ^0.4.1 allow?
    ^1.2.3 allows anything from 1.2.3 up to but not including 2.0.0 — any minor or patch release. ^0.4.1 allows only 0.4.1 to 0.5.0, exclusive, because semver treats the leading zero as "unstable" and shifts the caret's meaning down a level: for 0.x versions the minor position behaves like a major. So the same operator is permissive on a 1.x package and conservative on a 0.x one, which surprises people in both directions.
  2. Why must CI use npm ci rather than npm install?
    Because npm install may update the lockfile — resolving ranges to newer versions and writing them back — so two builds of the same commit can install different code. npm ci installs exactly what the lock says, fails if the lock and package.json disagree, and deletes node_modules first. It is also considerably faster, since there is nothing to resolve.
  3. Why is the lockfile the real contract rather than the range?
    Because semver is a statement of intent by the author, not something the registry verifies. Patch releases break things regularly — a behaviour change nobody classified as breaking, a transitive bump, a tightened type. The range describes what you are willing to accept the next time you deliberately update; the lock records the exact tree you tested, with integrity hashes. Committing it is what makes a build reproducible and stops an upstream release from reaching you unasked.
  4. Why are install scripts the most important item on the risk list?
    Because they are arbitrary code executed on your machine and in your CI at install time, with your environment, your credentials and your network access — before any test runs or any review happens. Every package in the tree can have one, so the count is in the dozens for a normal project. --ignore-scripts turns that off, and the honest way to find out what you need is to try it: for most applications nothing breaks.
  5. Why read the maintainer count as a permission grant?
    Because any one of those accounts publishing a new version can put code into your build. Nearly every real supply-chain incident has been a compromised or transferred maintainer account rather than a clever exploit, so the number of people who could do that is a more useful measure of exposure than a vulnerability count. It is also why a committed lockfile matters so much: it means a new publish does not reach you until you choose to look.
  6. What does pnpm's strictness buy beyond disk space?
    It stops you importing packages you never declared. npm's flat node_modules hoists transitive dependencies to the top level, so import x from "some-transitive-thing" resolves and works — until a version resolution changes the layout and it suddenly does not, in a build you did not touch. pnpm's layout only exposes declared dependencies, so that class of accidental coupling becomes an error immediately.
