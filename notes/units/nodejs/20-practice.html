Diagnosing by symptom

Three questions in order, and they route almost every Node problem. Is the loop busy? Is memory growing? Is the process dying?

SymptomUsuallyCh
One endpoint slow, every endpoint slowSynchronous CPU work somewhere. Check loop lag, then take a CPU profile03, 16

    Projects worth building

    An order API, end to end

    The one this unit was written around. Small enough to finish, wide enough to hit every chapter.

    • Fastify with a schema per route, driving validation, serialisation and OpenAPI
    • Postgres with a query builder and a transaction helper
    • pino plus AsyncLocalStorage, OpenTelemetry via --import
    • node:test with Testcontainers in globalSetup
    • A distroless image, a real shutdown path, three probes

    A streaming export endpoint

    The fastest way to internalise chapter 6, because getting it wrong is visible in a memory graph.

    • A million rows from a cursor to the client as NDJSON
    • pipeline with an async-generator transform
    • Watch rss stay flat, then break it with .pipe()
    • Abort halfway and confirm nothing leaks

    A CPU-bound endpoint, three ways

    Chapters 3 and 15, measured rather than argued.

    • Load-test it inline and watch loop lag and the health check
    • Chunk it with setImmediate — fairness, not capacity
    • Move it to piscina and compare clone against transfer
    • Then try more replicas and see which you would actually ship

    A deliberately leaky service

    Build all four leak shapes on purpose, then find each one from the outside.

    • An unbounded Map, a per-request listener, a captured closure, a Buffer pile
    • Three heap snapshots, compared by delta
    • Read the retainer path back to the variable
    • Confirm the Buffer case is invisible in heapUsed
    Where to go next

    If this unit landed, the natural continuations are TypeScript for the type system this codebase probably runs on, PostgreSQL for what is underneath chapter 13, Docker and Kubernetes for what chapter 19 only touched, and System Design for the questions that start once one service works.

    And a closing observation. Nineteen chapters of Node problems reduce to a very small number of causes: something computed on the one thread, something was not awaited or not observed, something was retained past its request, or something was multiplied per process. That list is short enough to hold in your head, and holding it is most of what separates debugging Node from guessing at it.
