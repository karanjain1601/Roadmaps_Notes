HTTP without a framework

Worth doing once, because it shows exactly what a framework is for — and because two things you must configure yourself live at this level regardless of which framework sits on top: the server's timeouts, and how long it keeps a connection alive.

What req and res actually are

javascript — a server with no dependencies, and what it does not do
import { createServer } from "node:http";

const server = createServer(async (req, res) => {
  // req is a Readable stream — chapter 6. res is a Writable.
  // That is the whole abstraction.

  // ✱ req.url is a STRING, and only the path and query:
  //     "/orders?status=paid"   — no host, no parsing
  const url = new URL(req.url, `http://${req.headers.host}`);
  const status = url.searchParams.get("status");

  // ✱ headers are lowercased, and a repeated header may be an array.
  //   req.headersDistinct if you need the raw multiplicity.

  // ✱ there is no body until you read it, and no size limit
  //   unless you impose one:
  const chunks = [];
  let size = 0;
  for await (const c of req) {
    size += c.length;
    if (size > 1 * 1024 * 1024) {         ← without this, a client
      res.writeHead(413).end();                 chooses your memory
      return req.destroy();                     usage. Chapter 6.
    }
    chunks.push(c);
  }

  res.writeHead(200, { "content-type": "application/json" });
  res.end(JSON.stringify({ ok: true }));
});

// the four timeouts. Their defaults are the subject of the next demo.
server.headersTimeout   = 10_000;
server.requestTimeout   = 30_000;
server.keepAliveTimeout = 65_000;
server.listen(3000);

The rule, and the second half of it

server.keepAliveTimeout must be greater than the idle timeout of whatever sits in front of you. AWS ALB defaults to 60 seconds, nginx to 75, most others somewhere between. Node defaults to 5. Whoever closes first should be the client side of the connection, because a proxy that closes knows not to send on that socket, and a proxy that discovers the close mid-write can only report a 502.

And the part usually missed: headersTimeout must also exceed keepAliveTimeout, because on a reused connection the headers clock starts when the connection went idle. Set keepAliveTimeout to 65 and leave headersTimeout at 60 and you have created a different intermittent failure while fixing the first one.

Terminate TLS somewhere else
Node can do HTTPS and HTTP/2 perfectly well, and in production a proxy, load balancer or ingress almost always does it — for certificate management, session resumption and offloading the handshake from your single thread. Trust x-forwarded-proto and x-forwarded-for only from a known proxy, and configure your framework's trust setting accordingly.
Outbound connections need an agent
The default global agent has changed over versions and is not what you want for a service making many calls to a few hosts. Set keepAlive: true and a maxSockets per host — or use undici, which backs fetch and gives you a proper pool. Without keep-alive you pay a handshake per request to your own dependencies.
server.maxRequestsPerSocket
Bounds how many requests one connection may serve before the server asks for a new one. Useful behind a load balancer that would otherwise pin a client to one instance indefinitely — the same stickiness problem as chapter 19 of the Backend unit.
Read res.writableEnded before writing
Writing to a response that already ended throws ERR_STREAM_WRITE_AFTER_END, and it happens when an error handler runs after a stream already sent a body. Chapter 6's truncated-export problem, from the other side.

Self-check

  1. What is req.url, and what is it not?
    A string containing only the path and query — "/orders?status=paid". It is not parsed, and it has no scheme or host, because those come from the Host header. Build a URL from it with a base if you need components, and never assume it is safe: it is attacker-controlled input that will be used to look things up, which is chapter 7's traversal problem arriving over the network.
  2. Why must you impose your own body size limit?
    Because node:http imposes none. The request is a stream, and if you accumulate it into an array of chunks the client decides how much memory you allocate — a single request can exhaust the heap. Check the running total as you read and respond 413 while destroying the request. Content-Length is a hint, not a guarantee, so the check has to be on bytes actually received.
  3. Which timeout catches a client that sends its headers one byte at a time?
    headersTimeout, which bounds the time from the first byte to the end of the headers — 60 seconds by default. That is generous: an attacker holding a socket for a minute each needs relatively few connections to accumulate thousands, so lowering it to about 10 seconds costs nothing legitimate and removes most of the value of the attack. requestTimeout, at 300 seconds by default, covers the whole request including a slow body.
  4. Which slow client has no server-side timeout by default?
    One that reads the response slowly. server.timeout — the socket inactivity timeout — has defaulted to 0 since Node 13, so a client that requests a large file and then reads a byte a second holds the connection, the file descriptor and the read stream indefinitely. Nothing fires. You need server.timeout or response.setTimeout, or an AbortSignal on the pipeline as in chapter 6.
  5. Why does a short keepAliveTimeout behind a load balancer cause intermittent 502s?
    Because the load balancer keeps the connection in its pool for far longer than Node keeps it open — 60 seconds against 5 by default. When the server closes an idle connection the proxy may not have processed the close before it sends the next request on that socket, so the request is lost in flight and the only thing the proxy can report is a 502. It appears as a small, constant error rate correlated with traffic gaps, and it never reproduces in testing because a single client never idles for exactly that long.
  6. Why must headersTimeout exceed keepAliveTimeout?
    Because on a reused connection the headers clock starts when the connection went idle, not when the next request's first byte arrives. If keep-alive is 65 seconds and the headers timeout is 60, a connection idle for longer than 60 has already breached the headers timeout by the time a legitimate request arrives on it — producing exactly the intermittent failure you were trying to eliminate. Raise both together, with headers comfortably above keep-alive.
