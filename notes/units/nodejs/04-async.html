Callbacks, promises and async/await

Three generations of the same idea, all still present in the ecosystem. async/await makes asynchronous code read like synchronous code — which is its value and its trap, because the most common performance bug in Node is a loop that awaits when it did not have to.

Three generations

javascript — the same operation, three ways
// ── ① error-first callbacks. Still the shape of every Node API's
//    underlying implementation, and of a great deal of npm. ──
readFile(path, (err, buf) => {
  if (err) return cb(err);      ← the `return` is load-bearing.
  parse(buf, (err, data) => {        Without it, execution continues
    if (err) return cb(err);      and cb is called twice
    cb(null, data);
  });
});
// the three classic bugs: forgetting the return, throwing inside a
// callback (nothing catches it — chapter 5), and calling back twice.

// ── ② promises. A value that will exist, with composition. ──
readFile(path)
  .then(parse)
  .then(data => cb(null, data))
  .catch(cb);
// the rule that fixes most promise bugs: RETURN the promise from a
// .then handler, or the chain does not wait for it.

// ── ③ async/await. Sugar over promises, and worth using. ──
async function load(path) {
  const buf = await readFile(path);
  return parse(buf);              ← try/catch works, stack traces are
}                                     readable, and control flow is plain

// promisifying a callback API you cannot change:
import { promisify } from "node:util";
const lookup = promisify(dns.lookup);
// or, for one that follows no convention at all:
const once = (emitter, ev) => new Promise((res, rej) => {
  emitter.once(ev, res);
  emitter.once("error", rej);     ← never omit this half
});
// though node:events already exports `once` and `on` for exactly this.

javascript — the three shapes, and the one to reach for
// ✗ sequential, and almost always by accident
const out = [];
for (const id of ids) out.push(await fetchOne(id));   ← n × latency

// ✗ unbounded. Correct for 5 ids, a denial of service for 50,000.
const out = await Promise.all(ids.map(fetchOne));
//   opens every connection at once: exhausts the pool, blows through
//   the downstream rate limit, and buffers every result in memory.

// ✓ bounded. The default you want for a list of unknown length.
import pLimit from "p-limit";
const limit = pLimit(8);
const out = await Promise.all(ids.map(id => limit(() => fetchOne(id))));

// ✓ and when the calls are different rather than a list, name them:
const [user, orders, prefs] = await Promise.all([
  users.byId(id),
  orders.forUser(id),
  prefs.forUser(id),
]);
// three round trips become one wait. This is the single easiest
// latency win in most Node handlers.

// ✓ cancellation, which people forget exists
const ac = new AbortController();
setTimeout(() => ac.abort(), 2000).unref();
const res = await fetch(url, { signal: ac.signal });
// or simply: AbortSignal.timeout(2000) — and note that fetch has NO
// default timeout, so without this a hung server hangs your handler.

Why Promise.all can crash your process

Promise.all rejects as soon as one input rejects — but it does not cancel the others, and it stops observing them. If a second promise rejects a moment later, nothing is attached to it, so Node reports an unhandled rejection and (since version 15) terminates the process by default. The handler that returned a clean 500 five milliseconds earlier is irrelevant. Two fixes: use allSettled when several inputs can plausibly fail and decide yourself; or attach a no-op .catch() to each input before passing them in, which is uglier and explicit about what you are ignoring.

Self-check

  1. Why is array.forEach(async x => …) almost always a bug?
    Because forEach discards its callback's return value, so the promises each invocation produces are never awaited or observed. The surrounding function returns before any of the work completes, results are missing, and a rejection in any of them becomes an unhandled rejection that can crash the process. Use for…of with await for sequential work, or map into Promise.all for concurrent.
  2. What is the cost of await inside a loop over independent items?
    The total becomes the sum of the latencies instead of the maximum — twelve calls at eighty milliseconds is 960 ms rather than 80. Nothing is blocked in the event-loop sense, so the process stays responsive and there is no CPU cost; you have simply chosen to wait for each before starting the next. It is correct when each call depends on the previous result and a pure waste when they do not.
  3. Why is unbounded Promise.all over a large array dangerous?
    Because it starts everything at once. Fifty thousand concurrent requests exhaust your connection pool, breach the downstream service's rate limit, open more sockets than the process has file descriptors, and buffer every result in memory simultaneously. It is also indistinguishable from an attack from the receiving end. Bound it — eight or sixteen at a time — and the same code becomes safe at any input size.
  4. How can a handler that already returned a 500 still crash the process?
    Through Promise.all. It rejects on the first failure and stops observing the remaining promises without cancelling them, so a second rejection arriving later has nothing attached to it. Node treats an unhandled rejection as fatal by default since version 15, so the process exits — long after the response went out. Use allSettled, or attach a deliberate no-op catch to each input.
  5. When is Promise.any the right choice over Promise.race?
    When you want the first success rather than the first result. race settles on whichever promise finishes first, including a rejection — so a fast failure beats a slower success, which is what you want for a timeout and wrong for redundancy. any ignores rejections until every input has failed, then rejects with an AggregateError containing them all. Three mirrors of the same data is an any; a call with a deadline is a race.
  6. Why does fetch need an explicit signal?
    Because it has no default timeout. A server that accepts the connection and never responds will keep your handler waiting indefinitely, holding whatever it holds — and under load that is the cascade from chapter 19 of the Backend unit. AbortSignal.timeout(2000) is one argument and bounds it. The same applies to any client library: if you cannot find its timeout setting, assume there is not one.
