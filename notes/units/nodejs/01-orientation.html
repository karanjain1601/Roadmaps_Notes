Chapter 01 · The runtime

What Node actually is

A JavaScript engine, an asynchronous I/O library, and a rule: your code gets one thread. That rule is the whole design. It is why Node handles ten thousand idle connections on a small machine, and why one badly written loop can take an entire service offline.

The sentence to remember

Node is single-threaded for your code and multi-threaded for everything else. When you call fs.readFile or issue a database query, the work leaves your thread — to libuv's thread pool, or to the kernel via epoll — and your thread is immediately free to do something else. That is why one process can hold thousands of connections that are mostly waiting. The corollary is exactly as strong: when you compute for fifty milliseconds, nothing else in the process happens for fifty milliseconds. Not another request, not a timer, not the health check.

How to read this unit

Chapter 3 is the load-bearing one. Almost every confusing Node behaviour — why a timer fired late, why await did not yield where you expected, why one endpoint made every endpoint slow, why the health check failed under load — is the event loop doing exactly what it is specified to do. Read it carefully rather than quickly.

Build something alongside. An order API is enough: it needs modules in chapter 2, error handling in 5, a framework in 10, a database in 13, tests in 17 and a container in 19. And the parts of Node that are genuinely hard — backpressure, unhandled rejections, memory retention — are not hard to read about. They are hard to notice, which only happens under load.

Self-check

  1. What does "Node is single-threaded" actually mean?
    That your JavaScript runs on one thread. The process has several others: libuv's thread pool of four, V8's own threads for garbage collection and compilation, and the kernel doing network I/O through epoll or kqueue. So file reads, DNS lookups, compression and crypto all happen off your thread — but only one piece of your code executes at a time, and while it does, nothing else in the process can run.
  2. Why can one Node process hold ten thousand mostly-idle connections?
    Because a waiting connection costs almost nothing. There is no thread per connection reserving a megabyte of stack — just a socket registered with the kernel's event notification mechanism and a callback waiting in the loop. The runtime is notified when data arrives and runs the relevant callback. Compare chapter 7 of the Spring Boot unit: this is exactly the property virtual threads were introduced to give the JVM.
  3. Why is a fifty-millisecond synchronous computation a serious problem?
    Because for those fifty milliseconds the process does nothing else — no other request progresses, no timer fires, no health check is answered, no socket is accepted. At two hundred requests a second each spending fifty milliseconds on CPU, the queue grows without bound and latency climbs for every endpoint, including ones touching nothing. The failure looks like the whole service being down rather than one route being slow.
  4. Where does Node's startup time mostly go?
    Into loading modules. The runtime itself starts in tens of milliseconds; resolving and compiling a thousand files from node_modules takes several times that, because each one is a filesystem lookup plus a parse plus a compile. That is why bundling to a single file measurably improves cold start, and why a dependency you never call still costs you time.
  5. Why must a Node server handle SIGTERM explicitly?
    Because the default action for SIGTERM is immediate termination: in-flight requests are cut off and nothing drains. Since a container deploy sends SIGTERM on every rollout, an application without a handler drops requests on every release. Call server.close() to stop accepting and let existing responses finish, and set a timeout so a stuck socket cannot hang the shutdown forever — chapter 19.
  6. Why check the platform before adding a dependency?
    Because a lot of what packages used to provide is now built in — fetch, a test runner, file watching, .env loading, AbortController, structuredClone. Each dependency you avoid is startup time you do not pay, code you do not have to audit, and one fewer entry in a tree that chapter 8 shows is larger and more security-relevant than most people expect.
