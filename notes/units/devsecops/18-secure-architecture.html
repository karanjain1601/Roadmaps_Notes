Secure architecture patterns

Four patterns that decide how much a single compromised service is worth to an attacker: how services authenticate each other, how requests carry authority, how APIs are shaped, and what happens when traffic arrives that you did not want.

~28 min read Service identity · mTLS · API design · load 2 interactive panels Prerequisite: chapters 13, and Cyber Security ch 9

18.1How services authenticate each other

The default in most estates is that they do not — a service accepts any request that reaches it, and the only control is whether the network permits the connection. That is the flat-network problem from Chapter 13, expressed at the application layer.

Service-to-service authentication

Each step answers a question the previous one could not.

The confused deputy, which is what all of this is really about

Service A is allowed to read any customer record, because some of its callers legitimately need any customer record. Service B calls A on behalf of a user. If A trusts B's word about who the user is — or does not ask at all — then anyone who can make B issue a request can read any record, and B has become a deputy confused about whose authority it is exercising. Mutual TLS does not fix this: it authenticates B, which was never in doubt. The fix is to propagate the end user's identity as a signed token the callee verifies independently, so A authorises against the user rather than against B. Getting this wrong is one of the most common serious flaws in service architectures, and it survives every network control you can put in front of it.

18.3Surviving unwanted traffic

Where load gets absorbed

Each layer is cheaper than the one behind it. What reaches your origin is what you pay for.

The expensive request is the one to worry about

Volumetric attacks are largely a solved commercial problem — a CDN absorbs them and you pay a bill. The harder case is the request that is indistinguishable from legitimate and disproportionately expensive to serve: a search with a pathological query, a report spanning three years, a GraphQL query nesting six levels, an export that joins four tables. A few hundred of those exhaust a database that shrugs off a million cache hits, and no network-layer control can tell them apart from real use. The defences are all inside the application: cost-based limits rather than request counts, query depth and complexity ceilings, mandatory pagination with a server-side cap, timeouts on every query, and moving genuinely expensive operations to an asynchronous job with a queue you control. This is a design property, not something you can buy.

You have mutual TLS between all services. Is service-to-service authorisation solved?

No — mTLS answers who is calling and leaves what they may do and on whose behalf untouched. It is a genuine improvement: every connection is authenticated with a cryptographic workload identity, so reaching the network is no longer sufficient to be trusted, and it removes an entire class of lateral movement. But two gaps remain. The first is authorisation: without a policy on the callee, an authenticated service can call any endpoint on any other service, so a compromise of the least important workload in the estate yields the full API surface of the most important. mTLS establishes identity; something still has to decide what that identity may invoke, which is a per-service allow-list of who may call which methods. The second is the confused deputy, and it is the more serious of the two. A service authorised to read any customer record — because some callers legitimately need that — will happily serve a request from a compromised upstream that is acting for the wrong user, since mTLS confirms only that the upstream is who it claims. The fix is to propagate the end user's identity as a token the callee verifies independently against the issuer's key, and to authorise against that rather than against the calling service. A header the caller sets is self-asserted and worthless here. Two refinements worth adding: narrow the token at each hop so it is audience-restricted and scoped to what the next service needs, which bounds what a compromise of any single hop yields; and remember that all of this authorises the call, not the data — an over-broad query behind a perfectly authorised request still returns too much, which is §18.2's problem.

Why is an expensive endpoint harder to defend than a volumetric flood?

Because the defences that work against volume operate on properties the expensive request does not have. A volumetric flood is characterised by rate and by traffic that is obviously not real — a CDN and network-layer scrubbing absorb it upstream at a cost you can plan for, and the requests never reach code you wrote. An expensive request is indistinguishable from legitimate use at every layer that could filter it: it comes from a real authenticated user, it is well-formed, it uses a documented endpoint, and there are only a few hundred of them. A search with a pathological pattern, a report spanning three years, a deeply nested GraphQL query, an export joining four tables — each is a request the application is supposed to serve, and a few hundred concurrently will exhaust a database that would shrug off a million cache hits. No network control can distinguish them, and rate limiting by request count does not help because the count is low; the problem is that the requests are not equal and the limiter treats them as if they were. The defences are architectural and all live in the application. Cost-based limiting, where a request consumes budget proportional to its estimated expense rather than counting as one. Complexity ceilings — maximum query depth, maximum joins, maximum date range — enforced before execution. Mandatory pagination with a server-side cap, so no endpoint can be asked for everything. Timeouts on every query, so a pathological one fails rather than holding a connection. And moving genuinely expensive operations to an asynchronous job with a queue whose depth you control, which converts a denial-of-service surface into a scheduling problem. Note that most of these also improve normal operation, which is usually how they get prioritised.

Should an authorisation service fail open or closed?

Closed, essentially always, because failing open converts an availability incident into an authorisation bypass — and an attacker who can cause the outage thereby removes the control, which makes the outage an attractive thing to cause. That is the one case where the usual availability argument inverts: for most dependencies a failure should degrade rather than block, but a component whose entire job is deciding what people may do cannot safely be absent. The real work is making the closed failure survivable, because "deny everything when the policy service is down" is a total outage and teams will quietly reverse it after the first one. Four things help. Cache recent decisions for a short window, so a brief outage is invisible and the exposure is bounded to the cache lifetime and to permissions that changed within it. Evaluate locally where possible — distribute the policy to a sidecar or library that decides in-process, so the central service is needed for distribution rather than for every request, which removes it from the hot path entirely. Run it for availability: multiple instances, multiple zones, and excluded from anything that could take it down alongside the workloads it serves. And set short timeouts so a slow policy service degrades to the cached path rather than hanging every request. Two adjacent decisions worth making explicitly at the same time, because they are usually made by accident: certificate validation should also fail closed and is the most common emergency shortcut, and the audit log's behaviour should be a deliberate choice, since failing open means continuing to operate with no record — defensible for availability, and not if the record is a legal obligation.

Recap

  1. mTLS authenticates the caller and authorises nothing. Both are needed.
  2. The confused deputy survives every network control. Propagate verified user identity, not the caller's word.
  3. A header the caller sets is self-asserted. Verify a signed token against the issuer.
  4. Narrow the token at each hop so one compromised service is not the user's full authority.
  5. Filter at the query, not in the response — by then the data is loaded, logged and cached.
  6. An unbounded list endpoint is an unlabelled bulk export. Cap page size server-side.
  7. Rate-limit per identity, not per address.
  8. Volumetric floods are a commercial problem; expensive requests are a design problem.
  9. Use cost-based limits, complexity ceilings and timeouts for the requests that are legitimate and costly.
  10. Authorisation and certificate validation fail closed. Make it survivable with caching and local evaluation.
