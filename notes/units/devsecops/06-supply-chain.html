Dependencies and the supply chain

Most of the code you ship, you did not write and have never read. The useful way to think about that is not as a list of packages with advisories attached, but as a list of people who can execute code inside your build — which is a much shorter list, and a much more alarming one.

6.1The maintainer surface

Dependency counts are the usual framing and they understate the problem in one direction and overstate it in another. What matters is not how many packages resolve into your build but how many independent parties can put code into it — and because maintainers own multiple packages, that number is smaller than the package count and far more actionable.

Who can execute code in your build?

From direct dependencies to the set of accounts whose compromise would reach you.

Install scripts are the part people miss

In several ecosystems a package can run arbitrary code at install time — before any of your code executes, before any test runs, on every machine that installs it including every developer laptop and every CI runner. That means a malicious dependency does not need you to call it; being resolved into the tree is sufficient. It also means the blast radius is the build environment from Chapter 3, with its credentials. Disabling install scripts (npm ci --ignore-scripts and equivalents) breaks a small number of packages that genuinely need them, which you then allow-list explicitly — and it removes the single most direct path from "a package was compromised" to "code ran with our deploy credentials".

6.2How dependencies get compromised

Attack vectors and what stops each

Six routes into a dependency tree. Note how few of them a vulnerability scanner addresses.

Dependency confusion

The one that catches large organisations rather than careless ones. If your build resolves package names against both a public registry and an internal one, and a name exists only internally, an attacker can publish that name publicly — often with a higher version number — and many resolvers will prefer it. The internal package is silently replaced by the attacker's, and it runs at install time. It requires no compromise of anything you own; it only requires knowing the name of an internal package, which leaks through job adverts, public repositories, error messages and stack traces. The defences are specific: use a scoped or namespaced prefix that you control on the public registry so the name cannot be squatted, configure the resolver to fetch internal names only from the internal registry rather than falling through, and prefer a proxy with an explicit allow-list over one that transparently falls back to public.

Two things frequently confused

Answers"What is in this artefact?""Do we actually call the vulnerable code?"

LimitationIt is an inventory, not an assessment. An SBOM with no process attached is a fileDefeated by reflection, dynamic dispatch, plugin loading and data-driven paths. "Unreachable" is a claim about today's build

The reason SBOMs became mandatory in several procurement regimes is the incident shape they address: a critical vulnerability lands in a library used everywhere, and organisations spend days establishing whether they use it, in what version, in which services. That question should be a query. Generate the SBOM at build time from the actual resolved tree rather than from the manifest — the manifest says what you asked for and the lockfile says what you got — and store it alongside the artefact so it can be looked up by image digest.

Why count maintainers rather than packages?

Because the maintainer account is the unit an attacker actually compromises, and it is the unit you can do something about. A dependency tree of a couple of thousand packages sounds unmanageable and is not a useful risk statement — nobody is going to review two thousand packages. The set of distinct accounts able to publish into that tree is much smaller, because maintainers typically own several packages, and it is the right denominator for the question "who could put code into our build". That reframing makes several things actionable at once. It tells you the concentration risk: a small number of maintainers frequently account for a disproportionate share of the tree, so a handful of account compromises reaches most of it, and those are the accounts whose security posture — two-factor authentication, whether publishing is automated from a repository, whether the account has a recovery email that still exists — actually matters. It highlights single-maintainer packages, where there is no second person to notice a strange release and no succession plan when the maintainer loses interest, which is both a security and an availability risk. And it correctly counts a widely-used package with a large organisation behind it as lower risk than three obscure ones with the same total download count, which a package count treats identically. The practical output is not a review of everything but a shortlist: the maintainers your build depends on most heavily, checked for the properties above, with the load-bearing single-maintainer packages either vendored, replaced, or contributed to so that you are the second maintainer.

You pin every dependency by exact version. Are you safer?

Against some things, yes, and you have taken on a new obligation that many teams do not meet. Pinning buys reproducibility — the same commit produces the same tree, which is a prerequisite for reasoning about what you shipped, for provenance, and for debugging. Adding integrity hashes goes further and pins the content rather than the name, which defeats a registry serving altered bytes for a version you already reviewed. Both are correct and neither is optional. The obligation is that a pinned tree does not receive security fixes either. An unpinned range would have quietly picked up the patch; a pinned one sits on the vulnerable version until someone acts, so pinning without an active update process trades a supply chain risk for a patching risk, and the second one is more likely to be exploited because it is a published advisory with public exploit code rather than a hypothetical malicious release. The combination that works is pin everything and update constantly — automated update pull requests, running continuously, so that updates are frequent, individually small, and tested by your existing suite. That is a better position than either extreme, and it has a delivery benefit too, since a hundred small updates are easier than one enormous one a year later. Two refinements worth adding. A short cooling-off delay before adopting new releases means malicious packages are often yanked before you take them, at the cost of a few days on genuine fixes — worth it for most dependencies, not for a critical advisory. And pin container base images and CI actions by digest rather than tag, because tags are mutable and can be repointed by someone else after you reviewed them.

A vulnerability scanner reports 340 findings in your dependencies. Where do you start?

Not at the top of the list sorted by severity, because that ordering is close to uninformative here for the reasons in Cyber Security Chapter 13. Four filters, applied in this order, will usually reduce 340 to something like a dozen. Reachability first: most findings are in code paths your application never calls, and reachability analysis typically removes a large majority — this is the single biggest reduction available and it is a tooling choice rather than an effort. Then exploitability in context: a vulnerability in a build-time dependency that never ships is different from one in a running service, and one behind authentication differs from one on an unauthenticated endpoint. Then evidence of real-world exploitation: the CISA Known Exploited catalogue and EPSS scores predict actual risk far better than CVSS does. Then fix cost: among what remains, some are a version bump that takes minutes and some are a major upgrade with breaking changes, and doing the cheap ones immediately shrinks the list while you plan the expensive ones. Two structural moves matter more than the triage itself. Many of the 340 will be transitive and fixed by updating one direct dependency, so grouping findings by the direct dependency that pulls them in frequently collapses dozens of rows into a single upgrade. And if this list exists at all, the underlying problem is usually update cadence rather than triage capacity — a codebase with continuous automated updates does not accumulate 340 findings, because each one arrived alone and was handled when it was one.

Recap

  1. Count maintainers, not packages. The account is what gets compromised and what you can act on.
  2. Install scripts run before any of your code does, on every laptop and every runner. Disable and allow-list.
  3. Build and test dependencies execute in CI, so they are in scope even though they never ship.
  4. Dependency confusion needs no compromise — only the name of an internal package. Scope your namespace before you need to.
  5. A lockfile pins the version; integrity hashes pin the content. Use both.
  6. Pin base images and CI actions by digest, because tags are mutable.
  7. Pinning stops security fixes too. Pin everything and update continuously.
  8. A short cooling-off delay means malicious releases are often yanked before you take them.
  9. An SBOM turns "are we affected?" from days into a query — generate it from the resolved tree, store it by digest.
  10. Reachability removes most findings, and is a claim about today's build rather than a permanent one.
