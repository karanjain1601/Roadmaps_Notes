Vulnerability management for delivery teams

The Cyber Security unit covers the programme — prioritisation, backlog dynamics, why the queue never empties. This chapter is the delivery-team half: getting from thousands of findings to a handful that matter, and making the fix a pull request rather than a conversation.

~28 min read Reachability · targets · auto-upgrade · routing 2 interactive panels Prerequisite: Cyber Security ch 13, ch 6

16.1The funnel

A scanner reports every known vulnerability in everything you ship. Most of those findings describe code that is never loaded, never called, or not reachable by anyone. Filtering is not cheating — it is the difference between a programme that finishes and one that is permanently behind.

From findings to what actually matters

Each filter is a real, defensible reduction. The last two are where the leverage is.

Reachability is the filter that changes the programme

Every other prioritisation input — severity, exploitability, asset value — reorders the list. Reachability shortens it, often by an order of magnitude, because a large majority of the vulnerable code in a modern dependency tree is in paths your application never enters. A vulnerability in an XML parser bundled by a library you use only for JSON is genuinely not your problem, and saying so with call-graph evidence is a defensible engineering position rather than an excuse. Two honest caveats: static reachability has false negatives around reflection, dynamic dispatch and configuration-driven loading, so treat it as strong evidence rather than proof; and it says nothing about a library loaded by a framework at startup, which runtime confirmation covers.

16.3Automating the upgrade

Automated dependency upgrades

A bot opens pull requests. Whether that helps depends almost entirely on your test suite.

Auto-merge without tests is auto-deploying someone else's code

Automated upgrades are the single most effective control against known-vulnerable dependencies, and they invert the supply chain argument from Chapter 6: you are now merging new third-party code continuously, with less scrutiny than before, on a schedule an attacker can predict. That is the right trade when the test suite is genuinely load-bearing and the pipeline verifies provenance, because staying current prevents far more harm than the rare malicious release causes. It is the wrong trade when a green build means little. The mitigations that make it safe are specific: a cooldown so a version must exist for some days before the bot proposes it, which catches most malicious releases through other people's misfortune; auto-merge restricted to patch versions where the semantic contract is narrowest; and provenance verification so an unsigned or unexpected publisher stops the merge.

Is filtering out unreachable vulnerabilities just moving the goalposts?

No, provided the filter is evidence-based and the residue is tracked rather than deleted. The distinction is between suppressing a finding because it is inconvenient and establishing that the vulnerable code cannot execute in your application. A modern dependency tree contains thousands of packages, and a large majority of the vulnerable functions in them sit in code paths your application never enters — an XML parsing flaw in a library you use only for JSON, a server-mode vulnerability in a client-only usage, a feature guarded by a configuration flag you do not set. Treating those identically to a flaw in a code path that handles untrusted input every request is not rigour, it is an inability to distinguish, and it produces a backlog so large that the genuinely urgent finding is indistinguishable from noise. That said, three honest caveats belong with it. Static reachability has false negatives — reflection, dynamic dispatch, service loaders and configuration-driven instantiation can all reach code the call graph does not show — so it is strong evidence rather than proof, and runtime confirmation of what actually loads is a useful second signal. The analysis must be re-run on every change, because a code change can make a previously unreachable path reachable and nothing will tell you. And the filtered findings should be recorded with their evidence, not discarded, both so the judgement can be revisited when the situation changes and so that you can answer an auditor without redoing the work. Done that way it is the single largest legitimate reduction available, and it is what makes the remaining targets meetable.

Should you auto-merge dependency upgrades?

For patch versions with a genuinely load-bearing test suite, yes — and the reasoning is a comparison of two risks rather than an appeal to safety. The risk of not upgrading is certain and cumulative: known vulnerabilities accumulate, the version gap widens until upgrading becomes a migration project, and the team ends up doing large risky upgrades rarely instead of small safe ones continuously. The risk of auto-merging is a malicious or broken release reaching production, which is real and rare. Where the tests meaningfully verify behaviour, the second risk is much smaller than the first, and the teams that stay current are measurably less exposed. The conditions matter though. A green build must actually mean something — if coverage is thin, auto-merge is deploying third-party code on the strength of a compile check, which is the failure the trap in §16.3 describes. Restrict it to patch versions, where the semantic contract is narrowest, and keep minors and majors human-reviewed. Add a cooldown of a few days before the bot proposes a version, which catches a good proportion of malicious releases through other people's detection rather than your own. Verify provenance so an unexpected publisher blocks the merge. And keep a fast rollback, because the honest position is that something will occasionally get through and the recovery time is what bounds the damage. One further practical point: group upgrades into a weekly batch per ecosystem rather than one pull request per dependency, or the review load itself becomes the reason the programme is abandoned.

Why measure the age of the oldest reachable finding rather than the open count?

Because the open count rewards the wrong behaviour and is barely connected to risk. A team that scans more thoroughly, adds a new scanner, or onboards more repositories will see its count rise while its actual exposure falls, which punishes exactly the behaviour you want. A team that suppresses aggressively, scans less, or excludes repositories will look excellent. The count also moves with things nobody controls — a busy month for CVE publication in a popular library shifts every team's number at once — so it is noisy in a way that makes trends meaningless. Age is better on all three counts. It is hard to game: the only way to reduce the age of your oldest finding is to fix it or to formally accept it with a dated exception, both of which are the outcomes you want. It tracks the thing that hurts, since the finding that causes an incident is almost never the one raised yesterday — it is the one everyone agreed was important eight months ago and nobody picked up. And it is robust to volume, so a team is not penalised for looking harder. Pair it with median time to remediate, which shows whether the process is working in the normal case while age shows whether anything is stuck. Two refinements worth adding: apply both only to reachable, fixable findings, so the metric is not dominated by things nobody can act on; and escalate on age specifically rather than on severity, because severity is already accounted for in prioritisation and escalating on it just re-raises the same argument.

Recap

  1. Reachability shortens the list; everything else reorders it. That is the filter that makes the programme finishable.
  2. Treat static reachability as strong evidence, not proof — reflection and dynamic loading are its blind spots.
  3. Record filtered findings with their evidence, so the judgement is revisitable and auditable.
  4. Apply deadlines to reachable, fixable findings only, or the policy is missed universally and then ignored.
  5. Start the clock when the finding reaches the owning team, not at disclosure.
  6. Split targets by effort. A patch bump and a major migration are not the same work.
  7. Automated upgrades are the most effective single control against known-vulnerable dependencies.
  8. Auto-merge patch versions only, with a cooldown and provenance checks, and only if tests are load-bearing.
  9. Route by pull request into the team's own repository, never into a separate security portal.
  10. Measure age of the oldest reachable finding, not open count — the count rewards scanning less.
