Policy as code

A rule written in a document is a hope. The same rule written as code is evaluated on every change, identically, in milliseconds, with a test suite proving it does what it says. This chapter is how to write those rules, where to put them, and how to introduce one without breaking everybody's Tuesday.

~28 min read Where to enforce · rollout · exceptions · testing 2 interactive panels Prerequisite: chapter 2

10.1What makes a rule expressible

Not every policy can become code, and pretending otherwise produces rules that technically pass while missing the intent. The test is whether the rule can be decided from data the evaluator can see.

Three kinds of rule
KindExampleAutomate?
Structural"No storage bucket may be public." "Every container must set a non-root user." "Images must come from an allow-listed registry."Fully. Decidable from the manifest alone
Contextual"Production databases must be encrypted with a customer-managed key." "Services handling card data must be in the PCI account."Yes, once the context is data — a tag, a label, an inventory entry. Which means the tagging becomes a policy too
Judgement"The design must be appropriate to the sensitivity of the data." "Access must be justified by business need."No. Encode the observable proxies and route the rest to a human
The dependency nobody plans for

Almost every interesting policy is contextual, and contextual policies depend on metadata being correct: an environment tag, a data-classification label, an owner field, a service catalogue entry. So the moment you write "production databases must be encrypted", you have implicitly created a second policy — "everything must be correctly tagged as production" — and the first one is only as good as the second. This is where policy programmes quietly fail: the rules are right, the enforcement works, and a third of the estate is untagged and therefore unevaluated. Start by making the metadata mandatory and enforced at creation, and treat untagged resources as failing rather than as exempt.

10.2Where to enforce

The same rule, at five different points

Each placement has a different feedback latency, coverage and cost. Most rules want more than one.

A rule worth reading, and the parts that make it so 
# Deny containers that run as root.
package kubernetes.admission

import rego.v1

deny contains msg if {
    some container in input.request.object.spec.containers
    not container.securityContext.runAsNonRoot

    msg := sprintf(
      "container %q must set securityContext.runAsNonRoot. " +
      "See https://wiki/paved-road/pods. To request an " +
      "exception: https://wiki/policy-exception",
      [container.name])
}

WHAT MAKES THIS USABLE RATHER THAN ANNOYING
  · It names the specific container, not "a container".
  · It says what to set, not just what is wrong.
  · It links to the paved road — the fix, not the rule.
  · It links to the exception process, so a legitimate
    special case has somewhere to go other than a Slack
    message to the security team.

A DENIAL IS A USER INTERFACE
  It is read by someone who is blocked, in a hurry, and does
  not know your policy library. The message is the entire
  product as far as they are concerned, and a rule that says
  "PolicyViolation: rule-0047" will be worked around rather
  than complied with.

AND TEST THE POLICY ITSELF
  test_denies_root_container if {
      deny with input as {...}   # a manifest that must fail
  }
  test_allows_nonroot if {
      count(deny) == 0 with input as {...}   # must pass
  }
  A policy without tests is a rule nobody can safely change.

10.3Rolling one out without a revolt

Warn, then block

Turning a new rule straight to blocking breaks whatever already violates it. Model the rollout.

The exception process is the policy

Every rule will be wrong for someone, and what happens next determines whether the whole programme survives. If the answer is "message the security team and wait", then policy becomes a gate (Chapter 2) and everything in that chapter applies. The workable form is an exception that is self-service, recorded, scoped and expiring: a file in the repository granting a named resource an exemption from a named rule, with an owner, a reason and a date, reviewed by the same pull request process as everything else. That gives you an audit trail for free, makes the total exception count a metric worth watching, and means an expiring exception reappears as a finding rather than becoming permanent silence. An exception mechanism with no expiry is just a slower way of deleting the rule.

10.4Operating a policy library

The practices that keep it healthy
PracticeWhy
Policies live in version control with testsA rule you cannot safely change is a rule that ossifies. Tests let you tighten it later
Every rule has an owner and a rationale"Why does this exist?" is asked constantly, and an unanswerable rule gets deleted or bypassed
Ship rules in warn mode first, alwaysYou find out what already violates it, and how often it is wrong, before anyone is blocked
Measure per-rule false positivesThe same argument as detection rules: a noisy policy teaches people that policy output is noise
Version the bundle and roll it out graduallyA bad policy pushed everywhere at once is an outage across every pipeline simultaneously
Fail open or closed — decide deliberatelyIf the policy service is unreachable, does everything stop or everything pass? Both are defensible; the default is usually whichever nobody chose
Retire rulesA rule made redundant by a platform change is pure cost. A library that only grows is one nobody trusts

Why is enforcing a rule only at deploy time insufficient, and only in CI also insufficient?

Because they fail in opposite directions and each covers the other's gap. Only at deploy — an admission controller or a cloud policy that refuses the change — gives you complete coverage of anything that reaches the platform, including resources created by hand in a console, by a script someone ran, or by a pipeline you did not know existed. That is genuinely valuable and it is the last line rather than the first. Its weakness is feedback: the engineer learns about the problem at the end of the pipeline, after build and test have run, sometimes minutes or hours after the commit, and the failure arrives as a deployment error rather than as a comment on the change they were making. That is the long loop from Chapter 1. Only in CI inverts it: the feedback is fast and lands on the right person while they still have context, but coverage is limited to changes that go through your pipeline. Anything created outside it — a console change, an emergency fix, a different team's tooling, a resource made before the policy existed — is invisible, and in most organisations that set is much larger than anyone assumes. So the arrangement that works is the same rule expressed once and evaluated in both places, plus a third: a periodic scan of what actually exists, to catch drift and pre-existing resources. The pull request check is for speed, admission is for coverage, and the continuous scan is for the things that were already there. Where you can only afford one, admission is the safer choice because it cannot be bypassed — but the loop is long enough that people will experience it as an obstacle rather than as help, which is a cost worth naming.

Your new policy would block 18% of existing resources. What do you do?

Not enable it. Blocking a fifth of the estate on day one produces a queue of broken teams, an emergency exception process, and a lasting reputation for the policy programme as something that breaks things — and the rule will probably be reverted, which is the worst outcome because you have now spent the credibility and gained nothing. The sequence that works has four steps. Warn everywhere first, for long enough to see the real number: the 18% estimate is usually wrong in both directions, because some violations are duplicates of one misconfigured module and some are legitimate cases the rule did not anticipate. Measure the false positive rate during that period, per rule, because a policy that is wrong 15% of the time needs fixing before it needs enforcing — and you only find that out by running it against reality. Block new violations while warning on existing ones, which is the step people skip and which does most of the work: it stops the number growing while the backlog drains, and it means nobody is broken by a change they did not make. Then set a deadline with the fix rate in mind — if teams remediate 40 a week and there are 250 genuine violations, the deadline is six weeks, not two. Two things make the drain much faster. If the violations cluster in a shared module or base image, fixing that one artefact resolves hundreds at once, which is worth checking before asking anyone to do anything. And a clear denial message linking to the fix rather than to the rule turns a support conversation into a self-service one.

Should the policy engine fail open or fail closed?

It depends on what the policy protects, and the important thing is that it is a decision rather than a default nobody examined. Fail closed — if the policy service is unreachable, nothing is admitted — is right when the policy is the only thing standing between an attacker and something serious, because an attacker who can take the policy service offline should not thereby get a free pass, and that is a genuinely attractive move for them. The cost is that your policy engine becomes a hard dependency for every deployment and, in the case of a Kubernetes admission webhook, potentially for every pod creation including the ones that would restore the policy service itself. That failure mode is circular and unpleasant: the cluster cannot heal because healing requires admitting pods and admitting pods requires the thing that is down. Fail open avoids the outage and means a determined attacker has an obvious route: break the webhook, then deploy. In practice the workable answer is usually to split by severity. Rules that prevent catastrophe — no public buckets, no privileged containers, signature verification — fail closed, with the policy service itself deployed for high availability and excluded from its own webhook scope so it can always recover. Rules that enforce hygiene — tagging, resource limits, naming — fail open, because an outage is a worse outcome than a temporarily untagged resource. Three supporting details: exclude system namespaces from the webhook so cluster components are not caught in the loop, set a short webhook timeout so a slow policy service degrades rather than hangs, and alert loudly when the engine is unavailable in either mode, because in fail-open that alert is your only signal that enforcement has stopped.

Recap

  1. Structural rules automate fully; contextual ones need metadata; judgement rules need a human.
  2. A contextual policy creates a second policy — that the metadata it depends on is correct.
  3. Treat untagged resources as failing, not as exempt.
  4. The same rule belongs in CI for speed and at admission for coverage, plus a periodic scan for drift.
  5. A denial message is a user interface. Name the resource, say what to set, link to the fix.
  6. Test the policies themselves, or you have a rule nobody can safely change.
  7. Warn everywhere, then block new, then block all — with a deadline set by the actual fix rate.
  8. Check whether violations cluster in one module before asking teams to do anything.
  9. Exceptions must be self-service, scoped and expiring, or the mechanism becomes a slow deletion of the rule.
  10. Decide fail-open or fail-closed per rule severity, and exclude the policy service from its own scope.
