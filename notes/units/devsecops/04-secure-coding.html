Secure coding

The Cyber Security unit covers what the attacks are. This chapter is the other side: which of them you can make structurally impossible, which merely require care, and why that distinction decides everything about how a codebase ages.

~28 min read Construction vs discipline · parsing · review 2 interactive panels Prerequisite: chapter 1

4.1Two ways to defend

Every defence is one of two kinds, and they behave completely differently over the life of a codebase.

The distinction that matters more than any specific technique
By constructionBy discipline
MeansThe defect cannot be expressed — the unsafe thing is not available, or is harder than the safe thingThe defect can be expressed and you rely on nobody doing it
Failure rateZero, for that classSmall per instance, and instances accumulate. At ten thousand opportunities, "usually right" is not right
NeedsA decision once, usually about tooling or an interfaceEvery engineer, forever, including the one hired next month at 5pm on a Friday
Verified byThe type checker, the compiler, the absence of an APIReview and scanning, both of which have gaps
ExampleAn ORM with no string-concatenation path; a template engine that encodes by context"Always parameterise queries"; "always escape output"
Count the opportunities

The useful question about any defence is how many chances there are to get it wrong. A codebase with four hundred database queries has four hundred opportunities to concatenate a string; at a 99% per-instance success rate that is four expected defects, and the rate for a distracted engineer under deadline is not 99%. Making the safe path the only path takes the count to zero and keeps it there through every future change by every future engineer — which is why the highest-leverage secure-coding work is usually not teaching people to be careful but removing the thing they have to be careful about.

4.2Parse, do not validate

The single most useful idea in this chapter, and it is a design technique rather than a security one. Validation checks a value and gives you back the same untyped thing; parsing converts it into a type that cannot hold an invalid value, so the check cannot be forgotten downstream because it has already been encoded in the type.

The difference, and why it compounds 
VALIDATE
  function handle(email: string) {
    if (!isValidEmail(email)) throw new Error("bad email");
    sendWelcome(email);        // still a string
    store(email);              // still a string
    audit(email);              // still a string
  }
  Every downstream function receives a `string` and has no
  way to know whether it was checked. So each one either
  re-checks, or trusts — and "trusts" is the default.

PARSE
  function parseEmail(raw: string): Email | null { … }

  function handle(raw: string) {
    const email = parseEmail(raw);
    if (!email) return badRequest();
    sendWelcome(email);        // Email
    store(email);              // Email
    audit(email);              // Email
  }
  Now the type system carries the guarantee. A function
  taking `Email` cannot be called with an unchecked string,
  and the check exists in exactly one place.

THE SAME MOVE, APPLIED ELSEWHERE
  UserId vs string        stops passing an order id to a
                          user lookup — which is how broken
                          object-level authorisation happens
  SafeHtml vs string      makes "already escaped" a type
  Cents vs number         stops the floating-point money bug
  Validated<T>            a wrapper carrying the guarantee

AND THE RULE THAT MAKES IT WORK
  Parse at the BOUNDARY — once, where untrusted data enters —
  and let the interior deal only in domain types. A codebase
  where strings from the request reach the database layer
  has no boundary, which is why the checks scatter.
Allow-list, and validate the decoded form

Two failures that survive careful validation. Blocklists lose: enumerating bad input means anticipating every encoding, every Unicode equivalent and every parser quirk, and you will miss one — while also rejecting legitimate values, which is how people named O'Brien cannot register. Define what is permitted instead, and reject everything else. Decode before you check: validating a URL-encoded, base64-wrapped or Unicode-normalised string checks the wrapper rather than the payload, and the component downstream will decode it after you approved it. Canonicalise first, then validate, then use the canonical form — and never validate one representation and pass a different one along.

4.3Memory safety

Worth separating out because it is the one class where the language choice does essentially all the work. Analyses by several large vendors of their own historical vulnerabilities have repeatedly put memory-safety defects at around two thirds of serious findings in large C and C++ codebases — a figure stable enough across independent studies to take seriously.

What each option removes
ChoiceRemovesLeaves
A memory-safe languageBuffer overflows, use-after-free, double free, type confusion — the whole classLogic flaws, injection, authorisation, deserialisation, and unsafe blocks or foreign-function calls
Rust specificallyThe above, plus data races, at compile timeThe same, plus whatever is inside unsafe
Modern C++ disciplineMuch of it, if applied consistentlyThe consistency requirement. One raw pointer in a decade of code is enough
Sanitizers and fuzzingFinds instances during testingOnly the paths you exercised. Very valuable, not a guarantee
Compiler and OS mitigationsRaises exploitation cost — ASLR, stack protectors, CFIThe bug itself. Mitigations make exploitation harder, not impossible

The pragmatic position for an existing C or C++ codebase is not a rewrite. It is writing new components in a safe language at the boundaries where untrusted data arrives — parsers, decoders, network handlers — because that is where the density of memory-safety defects is highest, and it is achievable incrementally in a way a rewrite is not.

4.4Failing safely

Error handling is a security control 
FAIL CLOSED, DELIBERATELY
  if (!authorised(user, resource)) return deny();
  ...
  try { allowed = policy.check(user, resource); }
  catch (e) { allowed = false; }        ← not `true`, and
                                           not "log and
                                           continue"

  The dangerous shape is a check that THROWS and is caught
  by a generic handler that proceeds. Make the failure of a
  security decision an explicit denial.

DO NOT LEAK IN ERRORS
  Stack traces, SQL, internal hostnames, library versions,
  and whether an account exists — all routinely returned to
  the caller in a 500. Return an opaque error and a request
  id; log the detail server-side.          → ch 15 of cs

BE CAREFUL WHAT YOU LOG
  Logs accumulate passwords typed into the username field,
  tokens in URLs, and whole request bodies. Scrub at the
  point of logging, not afterwards.                  → ch 7

TIMING
  A comparison that returns early leaks how much matched.
  Use a constant-time comparison for secrets, tokens and
  signatures — the library has one.

RESOURCE EXHAUSTION IS A FAILURE MODE TOO
  Unbounded request bodies, unbounded result sets, regular
  expressions that backtrack, recursive parsers with no
  depth limit, and decompression bombs. Every limit you
  do not set is one an attacker chooses.

4.5Review

Tools and humans find different things, and the overlap is smaller than people assume. Knowing which is which stops review from being a slower, worse scanner.

Who finds what

Defect classes against reviewers. The interesting column is the one only humans cover.

What to actually ask in a security review

Not "is this secure", which nobody can answer. Six questions that find real things: What is the untrusted input here, and where is it parsed? Who is allowed to do this, and where is that enforced — is ownership in the query? What happens when this fails, and does the failure deny? What does this log, and could it log a secret? What new dependency, permission or network path does this add? And what did this change assume that the rest of the system does not guarantee? The last one finds the most, because it is the question tools cannot ask.

Why is "always parameterise your queries" a weaker control than an ORM with no raw-string path?

Because it is a defence by discipline, and discipline degrades with scale and time in ways that are entirely predictable. A rule of that shape has to be followed at every one of hundreds or thousands of call sites, by every engineer who ever touches the codebase, including the one who joins next month and has not read your guidelines, the one adding a feature at the end of a difficult sprint, and the one who copies an existing pattern from a corner of the code that predates the rule. At four hundred query sites and a genuinely high 99% per-instance success rate, the expected number of defects is four — and 99% is optimistic for a rule that competes for attention with everything else a developer is holding. The rate also does not improve over time; if anything it worsens, because the codebase grows and the original context is lost. An interface with no raw-string path removes the question entirely: the unsafe thing is not expressible, so there is nothing to remember, nothing to review for, and nothing for a scanner to miss. The count of possible defects goes to zero and stays there through every future change by every future engineer. Two honest caveats. Most ORMs do provide an escape hatch for raw SQL, because occasionally you need it — the useful move is to make that escape hatch a distinct, greppable, lint-flagged call rather than the same function with different arguments, so the exceptions are countable and reviewable. And parameterisation still cannot cover identifiers or structure, so dynamic table and column names need an allow-list regardless of which approach you take.

What does "parse, don't validate" buy that a validation function does not?

It moves the guarantee from a fact about the program's history into a fact the type system enforces at every point of use. A validation function checks a value and hands back the same untyped thing, so every downstream function receives a plain string with no way to know whether it was checked — which leaves each of them with a bad choice between re-checking, which is wasteful and drifts out of sync, and trusting, which is the default and is what breaks. The checks then scatter through the codebase, some of them subtly different, and removing one becomes safe-looking because three others exist elsewhere. Parsing converts the value into a type that cannot hold an invalid instance, so a function taking Email or UserId or SafeHtml simply cannot be called with unchecked input, and the validation exists in exactly one place — the constructor. Three consequences follow that are worth more than the original safety property. It makes the boundary explicit: you can see where untrusted data enters, because that is where the parsing happens, and a codebase where request strings reach the data layer is visibly missing one. It catches confusion between values of the same underlying type, which is the mechanism behind broken object-level authorisation — passing an order id where a user id is expected is a compile error rather than a data leak. And it makes the invariant discoverable, since a new engineer reading the signature learns the rule without reading the guidelines. The cost is real and small: a little ceremony at the boundary, and a language with a type system expressive enough to make it worthwhile.

Your team reviews every pull request and still ships authorisation bugs. Why?

Because authorisation defects are invisible in a diff, and review reads diffs. The change that introduces one usually looks entirely reasonable in isolation: a new endpoint that fetches a record by id, written in the same style as the twenty endpoints around it, none of which the reviewer is looking at. Whether it is a vulnerability depends on facts outside the diff — who is allowed to see that record, whether ownership is enforced somewhere else in the stack, whether the middleware that covers the adjacent routes also covers this one. A reviewer would have to hold the whole authorisation model in their head and notice an absence, and noticing absences is the thing humans are worst at. Several factors compound it. Large diffs collapse review quality sharply, and the effect is not linear — beyond a few hundred lines attention degrades badly. Rotating reviewers who do not know the domain cannot evaluate whether the rule is right, only whether the code is tidy. And tools do not cover this either, because a scanner cannot know your authorisation policy, which is exactly why it remains the most common serious flaw. What works is structural rather than procedural. Put ownership in the query — WHERE id = $1 AND tenant_id = $2 — so a wrong owner returns no rows and there is nothing to remember. Use distinct types for identifiers so passing the wrong one does not compile. And add a test per endpoint where user A requests user B's object and expects a 404, because that is the only defence that scales to the endpoint nobody thought about. Review then has a chance, because it is checking that the test exists rather than reasoning about the policy from scratch.

Recap

  1. Defend by construction where you can, by discipline only where you must.
  2. Count the opportunities. At four hundred call sites, "usually right" is several defects.
  3. Parse at the boundary into domain types, so the guarantee is carried by the type rather than by memory.
  4. Distinct id types turn broken object-level authorisation into a compile error.
  5. Allow-list, and validate the decoded form — never check one representation and pass another.
  6. Memory safety is decided by the language, and new boundary components are where a safe language pays first.
  7. Make the failure of a security decision an explicit denial, not an exception a generic handler swallows.
  8. Every limit you do not set is one an attacker chooses.
  9. Review finds design and domain flaws; tools find patterns. Do not use review as a slower scanner.
  10. Authorisation bugs are invisible in a diff. Put ownership in the query and test it per endpoint.
