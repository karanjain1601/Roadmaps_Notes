Getting set up

Ten minutes of setup decisions that determine whether your projects still run in six months. What Python actually is, which version to use, how a file becomes a running program, and why every serious project gets its own isolated environment.

What Python is, and is not

Python optimises for the programmer's time rather than the computer's. That single trade explains nearly everything about it — the readable syntax, the enormous standard library, the dynamic typing, and the performance.

On the speed question

Pure Python is roughly 30–100× slower than C for tight numeric loops, and it usually does not matter — because the heavy work happens inside libraries written in C or Fortran. NumPy, pandas, PyTorch and scikit-learn are Python interfaces over compiled kernels. The skill is knowing when your code is orchestrating (fine) versus computing (move it into a library). Chapter 17 covers where the time really goes.

Versions and implementations

Which version
Use the latest stable release minus one for production work, and never below 3.9. Each October brings a new minor version supported for five years. Python 2 has been dead since 2020; if you meet it, the task is migration, not learning it.
What changed recently, roughly
3.8 gave the walrus operator; 3.9 dictionary merge with |; 3.10 structural pattern matching and much better error messages; 3.11 a large speed increase and exception groups; 3.12 improved f-strings and type-parameter syntax. Each release is meaningfully faster than the last.
CPython
The reference implementation, written in C, and what you have unless you deliberately installed something else.
PyPy
A just-in-time compiler. Often several times faster on pure-Python code, less good with C extensions.
Others
MicroPython for microcontrollers, Pyodide for the browser via WebAssembly. Specialist tools rather than alternatives.

What the interpreter does before anything runs
__pycache__

Those directories hold compiled bytecode so imports do not re-parse unchanged files. They are safe to delete and should be in .gitignore. If you ever see behaviour that survives a source edit, a stale .pyc from a deleted module is a rare but real cause — find . -name __pycache__ -exec rm -rf {} + clears it.

Installing Python

Do not use the system Python

macOS and most Linux distributions ship a Python that the operating system itself depends on. Installing packages into it with sudo pip install can break system tools, and it will eventually be upgraded out from under you. Install your own, and give every project its own environment.

Virtual environments

The single most important habit in this chapter. A virtual environment is a directory containing its own interpreter link and its own site-packages, so each project's dependencies are invisible to every other project.

Why environments exist
Two projects, one machine, incompatible requirements
Where it lives
.venv/ inside the project directory. Editors detect it automatically, and it disappears when the project does.
Never commit it
Add .venv/ to .gitignore. It contains platform-specific binaries and is regenerated from your lockfile.
Activation is optional
source .venv/bin/activate puts the environment's binaries first on your PATH. You can skip it entirely by calling .venv/bin/python or uv run.
How to tell which one is live
python -c "import sys; print(sys.executable)". When something is "not installed" despite you having installed it, this is the first command to run.

Pinning dependencies

The distinction between the first two matters. pyproject.toml says "this project works with pandas 2 or later"; the lockfile says "on 4 March we resolved that to pandas 2.2.1 with these 47 transitive dependencies at these exact versions". Chapter 18 covers the resolution machinery.

The src/ layout has one concrete advantage: your package is not importable from the project root, so your tests are forced to import the installed version rather than accidentally picking up the source directory. That catches packaging mistakes before your users do.

bash — four ways to run Python, and when each is right
python                       # the REPL — for exploring. Try it constantly
python script.py             # run a file
python -m mypackage          # run a package's __main__.py — respects the import system
python -m pytest             # run an installed tool as a module

# -m matters more than it looks: it uses the CURRENT interpreter's
# environment. `pytest` might be a different install entirely.

python -i script.py          # run, then drop into the REPL with everything still loaded
python -c "import sys; print(sys.version)"
Live in the REPL

Python's interactive prompt is unusually good, and using it constantly is the fastest way to learn the language. Three commands to know:

  • dir(obj) — everything the object can do
  • help(obj) — its documentation, inline
  • type(obj) — what it actually is, when you are surprised

Install ipython for tab completion, syntax highlighting, and ? and ?? to inspect objects and their source.

The Zen, and what it implies

Type import this in a REPL and Python prints nineteen aphorisms by Tim Peters. Three of them do real work:

"Readability counts"
Code is read far more often than it is written. This is why Python enforces indentation, why the standard library favours long descriptive names, and why clever one-liners are discouraged rather than admired.
"There should be one — and preferably only one — obvious way to do it"
An aspiration rather than a description, but it explains the language's resistance to adding syntax. When there is a conventional way, use it; readers are expecting it.
"Explicit is better than implicit"
Why self appears in method signatures, why there is no automatic type coercion between strings and numbers, and why from module import * is discouraged.
"Pythonic"

The word means code that uses the language's own idioms rather than transliterating another language's. Iterating with for item in items instead of indexing; using a comprehension instead of building a list with append; unpacking instead of indexing a tuple; context managers instead of manual cleanup. Chapters 3, 5 and 9 are largely about what those idioms are and why they exist rather than being arbitrary style preferences.

Self-check

  1. Why is "Python is interpreted" a simplification?
    Because there is a compilation step. Source is tokenised, parsed into an abstract syntax tree, and compiled to bytecode, which is then executed by the CPython virtual machine. The bytecode is cached in __pycache__ so unchanged modules do not need recompiling. What Python does not do is compile to native machine code ahead of time — which is where the performance difference comes from.
  2. You pip install requests, then import requests fails. What do you check?
    Which interpreter is running. Run python -c "import sys; print(sys.executable)" and compare it with which pip. Almost always they point at different installations — pip put the package in one environment and you are running another. Using python -m pip install avoids this entirely, because it guarantees the pip that matches the interpreter you just invoked.
  3. What is the difference between pyproject.toml and a lockfile?
    pyproject.toml states loose constraints you wrote by hand — "pandas 2 or later". The lockfile records the exact resolved versions and hashes of every package including transitive dependencies, as produced by the resolver on a particular day. The first expresses intent, the second guarantees reproducibility. Commit both; edit only the first.
  4. Why does the src/ layout help?
    Because the package is not importable from the project root, so tests must import the installed version rather than silently finding the source directory on sys.path. That means packaging errors — a missing module, a file left out of the distribution — surface in your own test run rather than in a user's install.
  5. What does python -m pytest do that pytest does not?
    It runs pytest using the interpreter you named, so it uses that interpreter's environment and adds the current directory to sys.path. The bare pytest command resolves through PATH and may belong to an entirely different installation. The same reasoning applies to python -m pip.
