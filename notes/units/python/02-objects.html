Chapter 02 · The language core

Names, objects and types

The most valuable page in this unit. Python does not have variables in the sense most languages do — it has objects, and names that refer to them. Once that model is solid, aliasing, mutable defaults, surprising copies and identity comparison all stop being surprises and become predictions.

— words— min read2 interactivesNeeds: chapter 01

Names are labels, not boxes

In C, int x = 5 reserves a box in memory and puts 5 in it. Assigning to x overwrites the contents of that box. Python does something different, and the difference is the source of most early confusion.

The model

Objects live somewhere in memory and hold values. Names are labels tied to objects, like sticky notes. Assignment attaches a label to an object; it never copies the object, and it never puts anything "into" the name. Several labels can sit on the same object, and an object with no labels left is discarded.

Two operations look similar in code and are completely different in effect:

Rebinding
b = something moves the label b to a different object. Other labels on the old object are unaffected.
Mutating
b.append(3) changes the object itself. Every label on that object now sees the change, because there is only one object.

The three attributes every object has

python
x = [1, 2, 3]

id(x)      # 140234... — its identity. In CPython, its memory address.
type(x)    # <class 'list'> — what it is. Never changes.
x          # [1, 2, 3] — its value. May change, if the type allows it.

# identity is what `is` compares; value is what `==` compares
y = x
y is x        # True  — same object
z = [1, 2, 3]
z is x        # False — different object…
z == x       # True  — …with an equal value

Mutable and immutable

*A tuple's own contents cannot be reassigned, but if it holds a mutable object, that object can still change. t = ([1], [2]) — you cannot do t[0] = ..., but t[0].append(9) works fine. The tuple's immutability is one level deep.

Why this matters constantly
  • Only immutable objects can be dictionary keys or set members, because hashing requires the value not to change underneath the container.
  • Passing a mutable object to a function lets that function change your object. There is no "pass by value" copy.
  • Mutable default arguments are created once, at definition time, and shared across every call — chapter 5's most notorious trap.
  • x += 1 on an integer creates a new object; lst += [1] on a list mutates in place. The same operator, two different behaviours, decided by the type.

Equality versus identity

python
a = [1, 2]; b = [1, 2]
a == b            # True  — equal values
a is b            # False — different objects

# ── the caching that confuses people ──
x = 256; y = 256
x is y            # True  — CPython pre-creates small integers −5 to 256

x = 257; y = 257
x is y            # False in a REPL… but often True inside a single script,
                  # because the compiler folds constants within one code object

s1 = "hello"; s2 = "hello"
s1 is s2          # True  — short literals are interned
s3 = "".join(["hel", "lo"])
s1 is s3          # False — built at runtime, not interned
Use is for exactly three things

is None, is True, is False — plus your own sentinel objects. Everything else uses ==. The caching behaviour above is a CPython implementation detail that varies by version and context; code that relies on it will work in testing and fail somewhere else. Linters flag == None for the opposite reason: None is a singleton, so identity is the correct and faster check.

Copying

python
import copy

original = [[1, 2], [3, 4]]

alias    = original                # no copy at all — a second label
shallow  = original[:]             # new outer list, SAME inner lists
shallow2 = list(original)          # identical to the above
shallow3 = copy.copy(original)     # and so is this
deep     = copy.deepcopy(original) # new everything, recursively

original[0].append(99)

alias      # [[1, 2, 99], [3, 4]]  — same object
shallow    # [[1, 2, 99], [3, 4]]  — outer is new, inner is shared ⚠
deep       # [[1, 2], [3, 4]]      — fully independent

# dicts behave the same way
d = {"a": [1]}
d2 = d.copy()                      # shallow
d2["a"].append(2)
d                                  # {'a': [1, 2]} — the list was shared

Shallow copying is the default everywhere in Python and is usually what you want, because deep copying an object graph is expensive and occasionally impossible. But when a "copy" mysteriously changes with the original, this is why — switch the demo above to the shallow-copy scenario and watch the shared inner lists.

Strings

A str is an immutable sequence of Unicode code points. Immutable means every "modification" produces a new string — which matters for performance in loops, and means strings are safe as dictionary keys.

python
s = "  Hello, World  "

# ── the methods you will use weekly ──
s.strip()                  # 'Hello, World'   — also lstrip, rstrip
s.lower(); s.upper()
s.replace("World", "there")
s.split(",")               # ['  Hello', ' World  ']
"-".join(["a", "b", "c"])     # 'a-b-c'  — note: the SEPARATOR owns the method
s.startswith("  H"); s.endswith("  ")
"World" in s              # True — membership, not a method
s.find("World")            # 9, or -1 if absent (.index raises instead)

# ── slicing: [start:stop:step], stop is exclusive ──
t = "abcdefgh"
t[0]        # 'a'
t[-1]       # 'h'    negative indices count from the end
t[2:5]      # 'cde'
t[:3]       # 'abc'
t[::2]      # 'aceg'
t[::-1]     # 'hgfedcba'  — the idiomatic reverse

# ── f-strings: the only formatting you need ──
name, n, x = "Ada", 42, 3.14159
f"{name} has {n} items"
f"{x:.2f}"              # '3.14'
f"{n:,}"                # '42'      thousands separator
f"{n:>8}"               # '      42' right-aligned in 8 columns
f"{x=}"                 # 'x=3.14159' — prints the expression too. Superb for debugging

# ── building strings in a loop ──

for item in items:
    parts.append(str(item))
result = "".join(parts)    # ✓ one allocation
# result += str(item) in the loop is O(n²) — a new string every time
Raw strings and escapes

r"C:\new\table" keeps the backslashes literal, which is why regular expressions and Windows paths are almost always written as raw strings. Without the r, \n and \t become a newline and a tab. Triple quotes """...""" span lines and are what docstrings use.

None, booleans and truthiness

None is a singleton object meaning "no value" — the return value of a function that returns nothing. It is not zero, not an empty string, and not false in the sense that those are.

Duck typing

"If it walks like a duck and quacks like a duck, it is a duck." Python code conventionally cares about what an object can do, not what class it belongs to. A function that iterates over its argument works with a list, a tuple, a generator, a file or anything else defining __iter__ — and checking isinstance(x, list) would gratuitously reject most of them. Chapter 7 covers the protocols this rests on, and chapter 11 covers how to express "anything iterable" in the type system.

How objects get cleaned up

CPython counts references. When an object's count drops to zero — the last label removed, the last container holding it destroyed — it is freed immediately. A separate cycle collector handles the case where objects reference each other and would otherwise never reach zero.

python
import sys

a = [1, 2, 3]
sys.getrefcount(a)     # 2 — your name, plus the temporary argument reference
b = a
sys.getrefcount(a)     # 3
del b                  # removes the NAME b, not the object
sys.getrefcount(a)     # 2 — the list is still very much alive

del x deletes the label, not the object. The object goes when nothing refers to it any more. In practice you rarely need del — leaving a function's scope drops its local names automatically, which is what frees most objects.

Self-check

  1. What does this print, and why?
    python
    a = [1, 2]
b = a
b += [3]
print(a)
    [1, 2, 3]. For a list, += calls __iadd__, which extends the list in place — so both names still point at the same, now-longer object. Contrast b = b + [3], which builds a new list and rebinds only b, leaving a as [1, 2]. The same operator behaves differently depending on whether the type is mutable.
  2. Why is x is 257 unreliable while x is None is fine?
    Because CPython pre-creates integer objects from −5 to 256, so equal small integers really are the same object — but 257 may or may not be, depending on constant folding and whether the values were computed or written literally. That is an implementation detail, not a language guarantee. None, by contrast, is genuinely a singleton: there is exactly one None object, so identity is both correct and the intended check.
  3. You copy a dictionary with d.copy(), modify a list inside the copy, and the original changes. What happened?
    .copy() is shallow: it creates a new dictionary whose values are the same objects as the original's. Mutating one of those shared inner objects is visible through both dictionaries. Use copy.deepcopy(d) for full independence, or restructure so the nested values are immutable — a tuple instead of a list — which removes the possibility entirely.
  4. Why does result += str(item) inside a loop scale badly?
    Strings are immutable, so each += allocates a whole new string and copies everything accumulated so far. Over n iterations that is O(n²) character copies. Collect the pieces in a list and call "".join(parts) once, which allocates the final buffer a single time. CPython has an optimisation that sometimes rescues the naive version, but it is fragile and you should not rely on it.
  5. A function receives a list and appends to it. Does the caller see the change?
    Yes. The parameter is another label on the same object, so appending mutates the caller's list. If the function instead does items = items + [x] or items = [], it rebinds its local label and the caller sees nothing. Functions that mutate their arguments should say so in the name and the docstring — or take a copy and return a new object, which is usually the friendlier design.
  6. Why should Decimal be constructed from a string rather than a float?
    Because Decimal(0.1) receives a float that is already the nearest double to 0.1, which is 0.1000000000000000055511151231257827…, and faithfully preserves that error. Decimal("0.1") parses the decimal text directly and is exactly one tenth. The literal 0.1 in your source is a float before Decimal ever sees it.
