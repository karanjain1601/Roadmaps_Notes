GraphQL, gRPC and real-time

REST is the default and it is not always right. Three situations push you elsewhere: clients that need different shapes of the same data, service-to-service calls where JSON over HTTP/1.1 is wasteful, and anything where the server needs to speak first. Each alternative solves a real problem and creates new ones, and the new ones are the part usually left out.

The honest default

Start with REST. It is the only one of the four that gets HTTP caching, CDN support, browser tooling, curl-ability and universal client support without any work — and those add up to a great deal. Move away from it when you have a specific, present problem: your mobile client is making eleven calls to render a screen (GraphQL), your internal services are spending real money on JSON serialisation (gRPC), or something needs to happen without the client asking (§6.4). Adopting one because it is more modern is how teams acquire an extra runtime, a caching problem and an authorisation problem in exchange for nothing.

6.2GraphQL

One endpoint, a typed schema, and the client sends a query describing exactly the shape it wants back. The problems it genuinely solves are real: over-fetching (a mobile client downloading forty fields to show three), under-fetching (eleven round trips to assemble one screen), and client-server coupling (every new screen needing a new backend endpoint).

The shape of it 
type Query {
  order(id: ID!): Order
}
type Order {
  id: ID!
  total: Money!
  customer: Customer!        # a graph edge, resolved on demand
  lines: [OrderLine!]!
}

query {                      # the client asks for exactly this
  order(id: "o_9f21") {
    total { amount currency }
    customer { name }        # …and nothing else about the customer
    lines { quantity product { name } }
  }
}

One POST. One response. Exactly those fields.

What it relocates

Every problem GraphQL solves on the client reappears on the server in a different form. These are not reasons to avoid it — they are the work you are signing up for.

The four you must plan for
ProblemWhy it appearsStandard answer
N+1 queriesEach field resolver runs independently, so lines { product { name } } over 50 lines calls the product resolver 50 timesBatching with a DataLoader — collect the ids requested in one tick, issue one WHERE id IN (…)
No HTTP cachingOne URL, POST bodies, and every query is different. CDNs and browser caches cannot helpPersisted queries with GET so the URL is cacheable; plus a normalised client cache and server-side caching per resolver
Unbounded costA client can request a deeply nested or enormously wide query — and a malicious one can request a cyclic graphDepth limits, complexity scoring with a per-query budget, pagination required on every list, and an allow-list in production
Authorisation per fieldThere is no endpoint to protect. Every field is separately reachable, and a nested path can expose data the top-level query would notAuthorise in resolvers or in the data layer, never at the query level — and test the nested paths, which is where the holes are

The N+1 problem, and what batching does

One query for a page of orders, each with lines, each with a product and a category.

Two further operational notes. GraphQL returns 200 with an errors array for field-level failures rather than an HTTP error status, so your monitoring will report a perfectly healthy service while a third of responses contain errors — you must parse the body to know. And a query can partially succeed, returning null for a failed non-null-able field and propagating that null up the tree, which surprises clients that assumed a successful response was complete.

6.3gRPC

A binary RPC protocol over HTTP/2, with interfaces defined in protobuf and client and server code generated from the definition. It is the default for internal service-to-service communication at scale, for four concrete reasons.

A service definition, and what you get from it 
syntax = "proto3";

message GetOrderRequest { string order_id = 1; }
message Order {
  string id       = 1;
  int64  total_cents = 2;
  string currency = 3;
  repeated OrderLine lines = 4;
}

service Orders {
  rpc GetOrder   (GetOrderRequest) returns (Order);
  rpc WatchOrders(WatchRequest)    returns (stream Order);   // server stream
  rpc BulkImport (stream Order)    returns (ImportSummary);  // client stream
  rpc Sync       (stream Event)    returns (stream Event);   // bidirectional
}

WHAT THIS BUYS
  · Generated clients and servers in a dozen languages, so the
    contract cannot drift from the code.
  · Binary encoding — typically 3–10× smaller than the equivalent
    JSON, and much cheaper to parse.
  · Four call shapes including real streaming, over one connection.
  · Deadlines propagated automatically across hops — the timeout
    budget from chapter 4, enforced by the framework.

THE FIELD NUMBERS ARE THE CONTRACT
  Never reuse or renumber a field. Adding a field is safe;
  removing one means reserving its number forever. This is what
  makes protobuf backward and forward compatible, and violating
  it corrupts data silently rather than failing loudly.

6.4When the server needs to speak first

HTTP is client-initiated (Chapter 3), so every mechanism for pushing data to a browser is a workaround. There are four, and they differ enormously in cost.

Real-time transports compared

The same requirement through each mechanism. Server cost scales with connected clients, not with events.

Server-sent events are underused

Most "real-time" requirements are one-directional: a notification badge, a progress bar, a live dashboard, a chat window where sending goes over an ordinary POST. For all of those, SSE gives you immediate delivery over plain HTTP with automatic reconnection and event replay built into the browser, for a fraction of the complexity of WebSockets. Reach for WebSockets when you genuinely need low-latency traffic in both directions — collaborative editing, games, trading — and accept that you are now responsible for heartbeats, reconnection, message ordering and backpressure yourself.

Whichever you choose, the same three problems arrive with any persistent connection. Connections are state, so a client is pinned to one server and your load balancer needs sticky routing or a shared pub/sub layer so any server can deliver to any client. Idle connections get killed by proxies and mobile networks, so you need heartbeats — SSE has comment-line pings, WebSockets have ping frames. And a deploy disconnects everyone at once, so clients must reconnect with jittered backoff or your restart becomes a self-inflicted thundering herd.

6.5Webhooks

The server-to-server equivalent: instead of a partner polling you, you POST to a URL they registered. It removes an enormous amount of wasted polling, and it makes you a client of someone else's unreliable endpoint, which is a different set of obligations.

What a webhook sender owes its consumers 
SIGN EVERY PAYLOAD
  X-Signature: sha256=<hmac(secret, timestamp + "." + body)>
  X-Timestamp: 1780000000
  Include the timestamp IN the signed material and reject old
  ones, or a captured request can be replayed forever.

RETRY WITH BACKOFF, AND GIVE UP
  Exponential with jitter, over hours not seconds. After the
  final attempt, disable the endpoint and tell the owner —
  retrying a dead endpoint forever is a cost to both sides.

MAKE IT REPLAYABLE
  Every event gets a stable id, and consumers can re-request
  it. This is what turns "we lost a webhook" from an incident
  into a self-service fix.

ORDER IS NOT GUARANTEED
  Retries and parallel delivery mean event 5 can arrive before
  event 4. Include a sequence number or a version so consumers
  can discard stale ones.

AT LEAST ONCE, SO CONSUMERS MUST BE IDEMPOTENT
  Send the event id; document that duplicates happen.

TIME OUT FAST AND EXPECT A 2xx QUICKLY
  Document that the consumer must acknowledge in a couple of
  seconds and do the work asynchronously. Consumers that do
  real work inline will time out and cause duplicate deliveries.
Why does GraphQL make HTTP caching harder, and what can be done about it?

Because HTTP caching is keyed on method and URL, and GraphQL uses one URL with a POST body. Every query hits POST /graphql, so a CDN, a reverse proxy and the browser cache all see identical requests with different meanings and none of them can safely store anything. You lose a layer that REST gets for free, and it is a significant layer — a well-designed REST API can serve a large share of reads from a CDN without touching your servers at all. Three partial answers. Persisted queries: register queries ahead of time, and clients send GET /graphql?id=abc123&variables=…, which restores a cacheable URL and additionally prevents arbitrary queries. Normalised client caches such as Apollo's or Relay's store entities by id, so a field already fetched for one query serves another — this is genuinely effective and is the main reason GraphQL clients feel fast. And server-side caching per resolver, which is where a shared cache like Redis does the work instead. The honest summary is that you replace one free, universal caching layer with three you must build and operate, which is a real cost that belongs in the decision.

Your notification feature needs to update a badge count in the browser. What would you choose?

Server-sent events, almost certainly. The requirement is one-directional — the server tells the browser a number changed — which is exactly SSE's shape, and it gives you three things for nearly no work: immediate delivery, automatic reconnection built into the browser's EventSource, and event replay via Last-Event-ID so a client that briefly disconnects catches up rather than silently missing updates. WebSockets would work and would cost you heartbeats, a reconnection strategy, message framing and a second protocol to secure and monitor, in exchange for a return channel you do not need. Short polling would also work and is genuinely the right answer if the client count is small and a delay of a few seconds is fine — do not dismiss it, because it is stateless, survives deploys without a reconnect storm, and needs no sticky routing. The question that decides it is client count against acceptable delay: with a few hundred clients and a five-second tolerance, polling is simpler and cheaper; with tens of thousands, the wasted requests dominate and a held connection is cheaper. And whichever you pick, remember that a persistent connection pins a client to one server, so you need a shared pub/sub layer for a deploy or a scale-out not to lose deliveries.

Why is a DataLoader necessary in GraphQL but not usually in REST?

Because of how the two decide what to load. In REST you write one handler for one endpoint, so you can see the whole shape of the response and issue one query with the joins it needs — the batching is implicit in the fact that a human wrote the query. In GraphQL the response shape is chosen by the client at runtime, and it is assembled by independent field resolvers that each know only about their own parent object. So a query for 25 orders, each with 4 lines, each with a product, calls the product resolver 100 separate times, and each call by default issues its own query. Nothing in the code looks wrong; the N+1 is emergent from the resolver model. A DataLoader fixes it by deferring: within a single tick of the event loop it collects every id the product resolver was asked for, issues one WHERE id IN (…), and distributes the results back — turning 100 queries into 1. It also deduplicates, so an id requested twice is fetched once. The reason it is close to mandatory rather than an optimisation is that the problem scales with the client's query, so a client can construct a request that issues thousands of queries without doing anything unusual — which is also why depth and complexity limits belong alongside it.

Recap

  1. REST is the default because it gets HTTP caching, CDN support and universal tooling for free. Leave it for a specific present problem.
  2. GraphQL solves over-fetching, under-fetching and client-server coupling, and relocates each as a server-side problem.
  3. The four you must plan for: N+1 resolvers, no HTTP caching, unbounded query cost, and per-field authorisation.
  4. GraphQL returns 200 with an errors array, so your monitoring will look healthy while responses are failing.
  5. gRPC is for internal service-to-service: generated clients, compact binary, real streaming, propagated deadlines — and no browser support or HTTP caching.
  6. Protobuf field numbers are the contract. Add freely, never reuse.
  7. SSE is underused. Most real-time needs are one-directional, and it gives immediate delivery with automatic reconnection over plain HTTP.
  8. Any persistent connection is state: sticky routing or shared pub/sub, heartbeats, and jittered reconnect so a deploy is not a thundering herd.
  9. Webhook senders owe consumers signed payloads with timestamps, bounded retries, replay, event ids and an explicit at-least-once contract.
