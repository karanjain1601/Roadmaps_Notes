What a backend actually does

Someone clicks a button and 340 milliseconds later a page changes. Between those two events are roughly forty distinct steps across four machines, and almost none of the time is spent computing anything. This chapter walks that path once, in full, with numbers — because every remaining chapter in this unit is about one of those steps, and the numbers are what tell you which ones are worth your attention.

1.1The job description

Strip away the frameworks and a backend does five things. Every chapter in this unit expands one of them.

What the whole discipline reduces to

The one property that shapes everything

A backend is concurrent and shared. At any moment it is handling many requests from people who do not know about each other, over state they all touch. Almost every difficulty specific to backend work — locking, isolation levels, race conditions, connection pools, cache stampedes, idempotency, rate limiting — exists because of that one sentence. Single-user code has none of these problems, which is why backend correctness feels harder than it looks.

1.3Where the time goes

Thirty steps, and if you had to guess which one dominates you would probably guess wrong. Below is the same request as a waterfall with realistic numbers. Change the conditions and watch which segment grows.

The request waterfall

Click any hop for detail. Purple is network, green is your code, amber is disk or an external system, grey is waiting.

The thing the waterfall shows every time

Your code is almost never the bottleneck. In a healthy request, the CPU time your application spends is a few milliseconds out of a few hundred — the rest is waiting: for the network, for the disk, for another system, or for a resource someone else is holding. That is why backend performance work is mostly about removing round trips and not waiting, and why optimising an algorithm from O(n log n) to O(n) usually changes nothing at all. Measure before you assume otherwise; the profiler will point at waiting.

1.4The numbers worth memorising

Backend judgement is largely a feel for magnitudes. The operations you use every day differ in cost by a factor of a hundred million, and knowing roughly where each sits lets you dismiss most bad ideas in seconds.

Latency across nine orders of magnitude

Real times are impossible to feel. Scale them to human units and the reason for every caching decision becomes obvious.

Three consequences fall straight out of that table, and they explain most backend architecture:

  1. A round trip is the unit of cost. One query returning 500 rows is dramatically cheaper than 500 queries returning one row each, even though the same data moves. This is the N+1 problem, and it is the most common performance defect in the field — Chapter 12.
  2. Memory beats disk beats network beats a distant network. Each step is roughly 100× worse. That single sentence is the entire justification for caching — Chapter 13.
  3. Anything involving another company's server is in a different category. 50–500 ms, occasionally never. It does not belong on a request the user is waiting for unless it must be — Chapter 15.

1.5Stateless servers and where state actually lives

The most consequential structural rule in backend work: the application process should hold no state that matters. Not the user's session, not a cached object another request needs, not an in-memory counter, not an uploaded file.

Four things stop working the moment a process holds state. You cannot add a second server, because half the requests land on the one without the data. You cannot deploy without losing whatever was held. A crash loses it too. And you cannot reproduce a bug, because the behaviour depends on which process happened to serve which earlier request.

Where each kind of state belongs
StateNot hereHere
User sessionsIn-process memoryA signed cookie, or Redis — ch 7
Cached valuesA local dictionaryA shared cache, or a local cache you accept may differ per process — ch 13
Uploaded filesThe local diskObject storage
Background workA thread you startedA queue and a worker — ch 15
Scheduled jobsAn in-process timerA scheduler with leader election, or an external trigger
Counters and rate limitsA local variableThe shared cache, atomically — ch 5
ConfigurationHard-coded per hostEnvironment, identically for every process — ch 19

The exception worth naming: connections are legitimate process-local state. A connection pool, an open socket to a broker, a compiled template cache — these are per-process resources rather than application state, and they are re-established on start rather than lost. The distinction is whether losing it changes what a user sees.

1.6Everything fails, and mostly it fails slowly

The mental model that separates working backends from fragile ones is that every remote call has three outcomes, not two: it succeeds, it fails, or it hangs. The third is the dangerous one, because a hung call holds a thread, a connection and a memory allocation while contributing nothing — and if requests keep arriving, the resources run out and a slow dependency becomes a total outage.

The five rules that prevent most of it 
1  EVERY remote call has a timeout.
   No exception. A call with no timeout is a promise to
   wait forever, and something will eventually take it up.

2  Timeouts shrink as you go deeper.
   If the user's budget is 2 s, the database call gets less,
   not the same. Otherwise the outer call times out while
   the inner one is still holding resources.

3  Retry only what is safe to repeat.
   A GET, yes. A payment, only with an idempotency key.
   Retrying a non-idempotent write turns one failure into
   two charges.                                     → ch 5

4  Retry with jitter, and only at ONE layer.
   Three layers each retrying three times is 27 calls to a
   service that is already struggling.

5  Fail fast when a dependency is known to be down.
   A circuit breaker turns a 30-second timeout into an
   instant error, which is what protects the resources.

This is the shortest possible version; the System Design unit works through the full set — bulkheads, load shedding, and the feedback loops that turn a slowdown into a cascade.

Why does making your application code twice as fast usually not make the request twice as fast?

Because application CPU time is a small fraction of the total. In the warm scenario above, the code executes for a handful of milliseconds inside a request lasting several hundred — the rest is network transit, TLS negotiation, waiting for a database round trip, waiting for a commit to reach disk, and waiting for an external service. Halving a component that accounts for 3% of the total buys 1.5%, which nobody will notice. This is Amdahl's law applied to a request, and it is why the productive backend optimisations are structural rather than algorithmic: remove a round trip, cache a result so the trip does not happen, batch N queries into one, move an external call off the critical path, or put a CDN nearer the user. Each of those attacks a segment that is actually large. The corollary is that you should always measure before optimising, because intuition about where the time goes is reliably wrong — and a trace or a flame graph will point at waiting, not at computing.

Your app stores the user's shopping cart in a module-level dictionary. What breaks, and when?

Nothing, until the day it all breaks at once. With one process it works perfectly, which is why this survives into production. Then: you add a second server for capacity, and now roughly half of each user's requests land on the process without their cart, so items vanish and reappear depending on which machine answered — an intermittent bug that is nearly impossible to reproduce locally. You deploy, and every cart in memory is discarded, so customers mid-checkout lose everything. A process crashes or is restarted by the orchestrator for a routine reason, same result. Memory grows without bound because nothing removes abandoned carts, and eventually the process is killed for using too much. And you cannot use a zero-downtime deployment strategy, because every strategy involves running new processes alongside old ones. The fix is to move the cart to shared state — Redis with a TTL, or a database table — at which point every process is interchangeable and all six problems disappear together. The general rule: if losing it would change what a user sees, it does not belong in the process.

A dependency starts responding in 30 seconds instead of 50 milliseconds. Why can that take down a service that has nothing to do with that dependency?

Because the slow calls hold resources that everything else needs. Suppose the server has 200 worker threads and normally handles 400 requests a second, each taking 50 ms — that needs about 20 threads. Now one endpoint's dependency takes 30 seconds. Requests to that endpoint arrive at, say, 20 per second, and each holds a thread for 30 seconds, so within ten seconds it is holding 200 threads and there are none left. Requests to every other endpoint now queue behind them and time out, including the health check, at which point the load balancer marks the instance unhealthy and sends its traffic to the remaining instances, which fill up the same way. One slow dependency has become a total outage, and the mechanism is resource exhaustion rather than the dependency itself. The defences are the ones listed in §1.6 plus two more: a bulkhead limiting how many concurrent calls that one dependency may hold, so it can never consume more than its share, and a circuit breaker that stops calling it entirely once failures cross a threshold. Both are in the System Design unit.

Recap

  1. A backend accepts, decides, remembers, integrates and keeps running. Every chapter here expands one of those.
  2. It is concurrent and shared, which is the source of nearly every difficulty specific to the work.
  3. A request is about thirty steps across four machines, and almost all the time is waiting rather than computing.
  4. Memory, disk, network, distant network — each roughly 100× the last. That single progression justifies caching.
  5. A round trip is the unit of cost. One query for 500 rows beats 500 queries for one.
  6. Anything involving another company's server is 50–500 ms and occasionally never; keep it off the critical path.
  7. Application processes hold no state that matters, so any process can serve any request. Connections are the legitimate exception.
  8. Every remote call succeeds, fails, or hangs. The third exhausts resources and turns a slow dependency into an outage.
