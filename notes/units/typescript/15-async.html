Async types

The inference around await is better than most people realise and the checking around forgetting to await is almost absent. That asymmetry is not an oversight — it follows from void meaning "the caller ignores this", which is a rule the language needs and which quietly swallows promises.

An async function always returns a promise
So annotating its return as Order rather than Promise<Order> is an error, and returning a promise from inside it is flattened rather than nested — Promise<Promise<T>> is not a type you can construct by returning. That flattening is why Awaited has to recurse.
require-await is worth less than it looks
A function marked async with no await inside is usually harmless — it is a promise-returning function, which may be exactly the interface you want. The rule catches genuine mistakes and also flags deliberate ones; enable it and expect exceptions.
Errors from a rejected promise are still unknown
Chapter 14 applies unchanged in a catch around an await. The one extra hazard is that an AbortError is a DOMException rather than a subclass of your error hierarchy, so a narrowing chain that only checks your own classes will re-throw a cancellation as an unexpected fault.
Concurrency is a runtime concern, not a type one
The compiler will not tell you that an await inside a loop serialises what could have run together, or that an unbounded Promise.all opens ten thousand connections. Chapter 4 of the Node unit is where those live; the types are identical either way.

Self-check

  1. What does await do to a non-promise?
    Returns it, after a microtask tick. The type is unchanged — await 42 is number — which is why Awaited<T> for a non-promise T is T. It is useful for a value that may or may not be a promise, and await-thenable will flag it where it is clearly accidental, since the tick is a real cost in a hot loop.
  2. Why is Promise.allSettled's result awkward?
    It resolves to PromiseSettledResult<T>[], which is an array of a discriminated union — each element is either { status: "fulfilled"; value: T } or { status: "rejected"; reason: any }. So there is no .value until you narrow on status, which is chapter 3 doing exactly what it should. People expect an array of values and get an array of outcomes; the type is right and the expectation is wrong.
  3. Why does items.forEach(async x => …) compile?
    Because forEach's callback is typed to return void, and void in a return position means "the caller ignores this" — so any return type is assignable, including a promise. Chapter 5. The language needs that rule for arr.forEach(x => set.add(x)) to work, and the cost is that every void-typed callback slot silently accepts an async function whose promise nobody observes.
  4. What actually catches a floating promise?
    A lint rule. @typescript-eslint/no-floating-promises for a dropped statement and no-misused-promises for a promise handed to a void slot — both need type information, so ESLint has to be pointed at your tsconfig. The compiler catches essentially none of these on its own, and the failure mode is severe: an unhandled rejection terminates a Node process by default.
  5. How do you deliberately not await something?
    Write void somePromise(), which is the convention the lint rule recognises as intentional. But a discarded promise still rejects, so unless the operation genuinely cannot fail you want .catch() on it instead — which both silences the rule and handles the failure. The bare void is for the rare case where a rejection is already handled inside.
  6. Why is useEffect(async () => …) wrong?
    Because the effect callback's return value is React's cleanup function, and an async function returns a promise instead — so React receives something it will try to call on unmount. The types do flag this one, since the slot is void | Destructor rather than plain void, which is a good illustration of the difference: a precisely typed callback slot catches the mistake and a void-typed one cannot.
