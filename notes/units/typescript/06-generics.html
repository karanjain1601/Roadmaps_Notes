Generics

A type parameter exists to relate two places — an argument to a return, one argument to another, a key to the value it fetches. If it appears in only one position it is not abstracting anything; it is an assertion the caller writes, wearing angle brackets.

// ── a constraint: what T must have, and what you may do with it ──
function byId<T extends { id: string }>(xs: T[], id: string): T | undefined {
  return xs.find(x => x.id === id);      ← .id is allowed because
}                                            the constraint promises it
// without the constraint, T is unknown inside the body and you can
// do nothing with it. A constraint is a two-way contract: it limits
// callers and it enables the implementation.

// ── keyof, and the indexed access that makes it worth it ──
function pick<T, K extends keyof T>(o: T, k: K): T[K] {
  return o[k];
}
pick(order, "total");      ← number. Not `any`, not a union of
pick(order, "nope");         every field type. And a typo is
                               an error at the call site.

// ── defaults, for the parameter you rarely need to name ──
interface Store<S = Record<string, unknown>> { state: S }

// ── const type parameters, TypeScript 5.0 ──
function route<const T extends readonly string[]>(paths: T): T { return paths; }
route(["/a", "/b"]);        ← readonly ["/a", "/b"] — the caller
                               no longer has to write `as const`

function pickFrom<T>(xs: T[], fallback: NoInfer<T>): T { … }

                               it — the error lands on the
                               fallback, where the mistake is

Is this generic earning its keep?

Count the positions
Once is never enough
The rule, and the one exception

A type parameter must appear at least twice. Once in a parameter and once in the return, or twice in the parameters, or in a constraint and a return — anywhere that makes it relate two things. If it appears only in the return type, the caller is choosing it and nothing checks the choice, which is as with extra syntax. If it appears only once in a parameter, it should be unknown.

The exception is get<T>(url): Promise<T>, which breaks the rule and is everywhere — every HTTP client is shaped like this. It is genuinely a cast, and the honest version returns Promise<unknown> and makes the caller parse it. Chapter 13 is about why that is worth the friction.

Generic classes are rarer than generic functions
A class parameterised over T commits every method to the same T, which is right for a container — Box<T>, Result<T, E>, Repository<T> — and wrong when only one method actually varies. Put the parameter on the method instead.
Inference is per-call, and greedy
The compiler collects candidates from every inference site and picks the best common supertype, favouring the first sites it sees. That is why an argument passed later can fail to widen T in the way you expected, and why NoInfer exists.
Explicit type arguments switch inference off entirely
Writing first<string>(xs) means the compiler no longer checks xs against a candidate — it checks it against string[]. Usually equivalent, and occasionally it hides a mismatch you would rather see. Prefer letting inference run.
Constraints are also documentation
T extends { id: string } tells the reader what the function needs, tells the caller what will be accepted, and tells the body what it may touch — all from six characters. An unconstrained T is unknown inside the body, which is why unconstrained parameters usually indicate the function does not actually use the value.

Self-check

  1. What is a type parameter actually for?
    Relating two or more positions so the compiler can carry information from one to another — from an argument to the return type, from one argument to another, or from a key to the type of the value it retrieves. That relation is the whole value; a parameter that appears once relates nothing and either should be unknown or is a cast the caller writes.
  2. Why is parse<T>(s: string): T a cast in disguise?
    Because T appears only in the return position, so nothing in the call determines it and nothing checks it — the caller writes parse<Order>(json) and the compiler simply believes them. It is JSON.parse(json) as Order with more syntax and a false air of safety. The honest signature returns unknown and forces a runtime check, which is chapter 13.
  3. What does a constraint give the implementation?
    Permission. An unconstrained T is unknown inside the body, so you cannot read a property, call a method or compare it — you can only pass it along. T extends { id: string } lets the body use .id. So a constraint is a two-way contract: it restricts which callers are accepted and in exchange tells the compiler what the body may rely on.
  4. What does a const type parameter change?
    It infers as though the argument had as const written on it, so an array literal becomes a readonly tuple of literal types rather than a widened array. That moves the burden from the caller to the signature — previously every call site had to remember as const for the derived types to be useful, and forgetting it silently produced string[]. Chapter 2's widening problem, fixed at the declaration.
  5. What does NoInfer solve?
    A site contributing to inference when it should only be checked against it. In pickFrom(xs: T[], fallback: T), passing a fallback that is not in the array widens T to include it, so the call compiles and the error you wanted never appears. Wrapping the fallback in NoInfer<T> stops it being an inference site, so T comes from the array alone and the mismatch is reported on the fallback — where the mistake is.
  6. Why is first([]) worth knowing about?
    Because there is nothing to infer from, so T falls back to never — and the return type becomes never | undefined, which is just undefined. The call compiles and the result is unusable, with no error to explain why. It appears in practice when an array is built up conditionally and one branch produces an empty literal; the fix is an annotation on the variable or an explicit type argument.
