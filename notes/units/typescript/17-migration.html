Migrating a JavaScript codebase

The failure mode is not technical. It is a six-month branch that never merges, or a conversion that renamed every file and typed nothing. The whole discipline is to keep the build green at every step and to make each step small enough that someone can finish it between other work.

The ladder

Seven steps, in this order. Each one ends with a green build — the spike is absorbed by suppressions you then burn down, not by leaving the build red.

Which file next?

Leaves inward, or entry points inward?
Same number of files converted, very different results
40%
Never rename and retype in the same commit
A rename from .js to .ts should be a pure rename that still compiles; the annotations come after. Otherwise every review mixes a thousand-line diff of moved code with the twenty lines that matter, and a genuine mistake is invisible in it.
The suppression count is the migration's progress bar
Insert @ts-expect-error with a ticket reference for every error a new flag produces, then enforce in CI that the total only decreases. It converts an unbounded "turn on strict someday" into a number that goes down, and it lets you enable the flag today rather than after the cleanup.
Do not convert a file you are not touching
Conversion is most valuable where change is frequent, because that is where the types will catch something. A stable module nobody has edited in two years is not producing bugs; typing it is real work with little return. Combine the leaves-first ordering with "and only in code that is actually moving".
Third-party any will undo your work quietly
Chapter 16. A fully converted, fully strict module that imports an untyped package is unchecked from that import outward, and nothing on the dashboard says so. Audit the dependency list for missing declarations early — it is often a bigger source of any than the remaining .js files.

Self-check

  1. Why start with allowJs rather than renaming anything?
    Because it lets .ts and .js coexist in one program, so the first commit changes no source files and produces no errors — the build stays green and the team keeps shipping. Everything after it is incremental. A migration that begins with a mass rename begins with a diff nobody can review and a branch that drifts.
  2. What does // @ts-check buy over converting the file?
    Real type checking with no rename, no build change and no risk — the file is still JavaScript, still runs through the existing pipeline, and now reports errors. With JSDoc annotations you get most of the checking too. It is the right first move on a large codebase precisely because it is reversible, and it is verbose enough that nobody wants to stop there.
  3. Why convert leaves before entry points?
    Because a converted file's types are only as good as its imports. A route handler converted while its service and model layers are still .js imports any from all of them, so the file is annotated and unchecked — the dashboard says converted and the compiler is verifying almost nothing. Convert a utility with no imports and it is genuinely typed the moment you finish, and it improves every file that imports it.
  4. Which flag first, and which last?
    noImplicitAny first, because it makes the remaining work visible — every unchecked region becomes an error you can count. strictNullChecks is the one that finds real bugs and produces the largest spike, so it comes once enough of the codebase is converted for the count to be finite. The rest of strict is comparatively cheap afterwards, and the flags outside strict last of all.
  5. Why @ts-expect-error rather than @ts-ignore for a migration?
    Because it expires. When the underlying error is fixed the suppression itself becomes an error, so the build tells you to remove it — which means the count is honest and cannot quietly include hundreds of suppressions that stopped being needed. @ts-ignore would also hide any new error appearing on those lines, so a migration marker from last year ends up concealing a real mistake. Chapter 9.
  6. Why can a fully converted codebase still be substantially unchecked?
    Untyped dependencies. A strict, fully annotated module importing a package with no declarations is any from that import outward, and chapter 9's propagation carries it through everything derived. No file-count dashboard shows this, and it is frequently a larger source of any than the remaining JavaScript. Audit the dependency list early and either find @types, write a small declaration, or wrap it — chapter 16.
