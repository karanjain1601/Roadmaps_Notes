The type space

TypeScript's most distinctive move is that a single value can be a type. From literal types plus unions you get enums, exhaustiveness, state machines and most of what other languages need generics or inheritance for — provided you can predict when the compiler will widen a literal back to string.

Literals, and when they widen

What did the compiler infer?
Case four surprises everyone
typescript — the enum replacement, and why it is better
// ── if you only need the type ──
type Status = "pending" | "paid" | "refunded";
// autocompletes, narrows, exhausts, erases to nothing. Done.

// ── if you also need the values at runtime ──
export const STATUSES = ["pending", "paid", "refunded"] as const;
export type Status = typeof STATUSES[number];   ← the union, derived
                                                  from the array
STATUSES.forEach(…);              ✓ iterable at runtime
const s: Status = "paid";         ✓ and the type is exact
// ONE source of truth. Adding a status to the array extends the
// type, and every non-exhaustive switch starts failing. Chapter 14.

// ── against the enum it replaces ──
enum Status { Pending, Paid }
//  ✗ emits an object with a reverse map (chapter 1)
//  ✗ numeric enums accept ANY number: Status.Paid + 99 type-checks
//  ✗ does not tree-shake
//  ✗ nominal, so a plain "paid" is not assignable — awkward at
//    boundaries, where every value arrives as a plain string
//  ✓ the one real advantage: the values are namespaced, so you
//    write Status.Paid rather than a bare string. `as const` gives
//    the same thing without any of the costs above.

The two ends, and any

The assignability matrix
Click a cell — the any row and column are the story
unknown is the top type
Everything is assignable to it and it is assignable to nothing without narrowing. That makes it the correct type for anything arriving from outside — a parsed JSON value, a caught error, a message payload — because the compiler then forces you to establish what it is before using it. Chapters 3 and 13.
never is the bottom type
Assignable to everything, and nothing is assignable to it. It is the type of a value that cannot exist, so it is what a function that always throws returns, what an impossible union member collapses to, and — most usefully — the tool that turns a forgotten switch case into a compile error. Chapter 14.
any is neither, and that is the problem
It is assignable both ways, so it is a hole in the lattice rather than a position in it. An any propagates: a property of an any is any, a call on it returns any, and the values that flow onward are unchecked too — which is how one wrong declaration in a @types package silently disables checking across a module. Chapter 9.
void is not undefined
void means "the caller should ignore this". A function returning void may in fact return a value, which is precisely why arr.forEach(x => set.add(x)) compiles even though add returns the set. Assigning undefined to a void variable works; the reverse does not.
strictNullChecks is the flag that matters most
With it off, null and undefined are assignable to every type and the compiler cannot find a single null-dereference. With it on, they are ordinary union members you must narrow. It is on under strict, and turning it off is the single largest reduction in TypeScript's value available to you.
Intersections, briefly

A & B is a value satisfying both — the union of the members, not of the values, which is the opposite of the intuition the word "intersection" suggests. It is how mixins, branding (chapter 1) and "these props plus the standard div props" are expressed.

Two things to know: intersecting primitives usually produces never, since nothing is both a string and a number; and intersecting object types with a conflicting property gives a property of type never rather than an error at the declaration, so the failure appears later at the assignment. Seeing never where you expected a value is nearly always this.

Self-check

  1. Why does let s = "paid" infer string but const s = "paid" infer "paid"?
    Because a let can be reassigned, so the useful inference is the widest type the variable could hold. A const cannot, so the literal type is both accurate and more useful. This is called literal widening, and it applies to the mutability of the binding — which is exactly why the object case below behaves differently.
  2. Why does a property of a const object still widen?
    Because const freezes the binding, not the object — o.status = "pending" is legal JavaScript, so the property is mutable and widens to string. That breaks every use that needs the literal: it cannot be a discriminant, cannot index a lookup type, and will not satisfy a narrower parameter. as const marks the members readonly and preserves the literals.
  3. What does satisfies do that an annotation does not?
    It checks the value against a type without changing the value's inferred type. An annotation checks and then replaces the inferred type with the annotation, so the literals are lost and keyof typeof gives you the annotation's key type rather than the actual keys. as preserves the literals and skips the check. satisfies is the only one that does both.
  4. Why is unknown the right type for a parsed JSON value?
    Because it accepts anything and permits nothing until you narrow it, so the compiler forces you to establish the shape before using it. Declaring it any would let every subsequent access compile and every one of them could fail at runtime; declaring it as the shape you hope for is a lie, since JSON.parse returns whatever was in the string. unknown makes the check a requirement rather than a habit.
  5. Why is any a hole rather than a position in the lattice?
    Because it is assignable in both directions: anything can be given to an any and an any can be given to anything. So it is not the top or the bottom — it is an edge connecting every pair of types, which is why one any can silently disable checking far from where it was introduced. It also propagates through inference: properties, calls and awaits on an any are all any.
  6. Why does an intersection of object types with a conflicting property give never rather than an error?
    Because the intersection is computed member by member, and the property's type becomes the intersection of the two conflicting types — string & number, which is never. The declaration itself is well-formed, so nothing complains there; the error appears later when you try to assign anything to that property, since nothing is assignable to never. Encountering an unexpected never is almost always this.
