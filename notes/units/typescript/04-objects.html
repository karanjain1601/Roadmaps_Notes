Objects, interfaces and aliases

Most TypeScript is object types, and most of the friction in writing them comes from three questions with unobvious answers: which declaration form to use, what "optional" actually permits, and why a perfectly valid extra property is sometimes an error.

— words— min read2 interactivesNeeds: chapters 02, 03

interface or type?

Ten things you might need
Only two of them actually decide it
A rule that survives contact with a codebase

Use interface for object shapes you own and expect to extend; use type for everything else — unions, tuples, function types, mapped and conditional types, and anything derived with keyof or typeof. Either is defensible for a plain shape, and a team that picks one and stops arguing is ahead of a team that picks the better one. The two cases where it genuinely matters: declaration merging, which only interface can do and which you need for module augmentation (chapter 16); and anything computed, which only type can express.

Four ways a property can be missing

typescript — index signatures, Record, and the honest version
// ── an index signature: any string key ──
interface Headers { [name: string]: string }
h.anything;                ✓ string — even keys that are not there
//   ✗ every declared property must also fit the signature, so you
//     cannot add `count: number` to this interface.

// ── Record: the same thing, and it accepts a key union ──
type Handlers = Record<Status, () => void>;
//   now the keys are EXACTLY "pending" | "paid" | "refunded", so
//   forgetting one is an error and adding a status breaks the map.
//   This is the single most useful application of Record.

// ── Partial<Record<K, V>> when the keys are optional ──
type Cache = Partial<Record<string, Order>>;
cache[id]?.total;          ✓ the ?. is now required, correctly

// ✱ noUncheckedIndexedAccess — off by default, and truthful:
//     without it:  h["missing"]  is string        ← a lie
//     with it:     h["missing"]  is string | undefined
//   It also makes arr[0] `T | undefined`, which is why enabling it
//   in an existing codebase produces hundreds of errors. Worth it
//   on new code; a project of its own on old code. Chapter 11.

// ── readonly, and what it is not ──
interface Config { readonly port: number; readonly tags: string[] }
c.port = 8080;             ✗ cannot assign to a readonly property
c.tags.push("x");         ✓ SHALLOW — the array itself is mutable
//   use readonly string[] for the array, or Readonly<T> for one
//   level, or a DeepReadonly helper for all of it (chapter 7).
// ✱ and readonly erases: nothing is frozen at runtime, and a
//   Readonly<T> is assignable to a mutable T through an alias.
Excess property checking, precisely
It fires only on a fresh object literal assigned directly to a typed target — a variable with an annotation, an argument, a return value. It does not fire on a value that came from elsewhere, which is why assigning the literal to an unannotated variable first makes the error vanish. The rationale is that a key you just typed and got wrong is a typo; a key on an existing object may be legitimate.
Optional members and Partial
Partial<T> makes every property optional one level deep, which is right for a patch payload and wrong as a way to avoid thinking about which fields are required. A type where everything is optional carries no information and pushes every check to the reader — chapter 3's argument again.
Getters, setters and methods
Method shorthand (m(): void) and a property with a function type (m: () => void) differ in exactly one way: parameter variance. The shorthand is checked bivariantly and the property form is checked strictly under strictFunctionTypes — chapter 5.
Recursive types work
Both forms can refer to themselves, so a JSON value, a tree or a nested menu is expressible directly. Recursion depth is where the checker's limits show up, which is chapter 19.

Self-check

  1. Which two capabilities actually decide between interface and type?
    Declaration merging and computed types. Only an interface can be declared twice and merged, which is what module augmentation requires — adding a property to Express's Request, for instance. Only a type can be a union, a tuple, a mapped type or a conditional type. Everything else on the list is either supported by both or a difference small enough to ignore.
  2. Why does an object literal with an extra property fail when an equivalent variable does not?
    Excess property checking, which applies only to fresh literals assigned straight to a typed target. A key written on the spot that the target does not declare is almost always a typo or a misunderstanding, so the compiler flags it — while a value from elsewhere may legitimately carry extra members and is accepted by ordinary structural assignability. Putting the literal in an unannotated variable first removes the freshness and the error.
  3. What is the difference between name?: string and name: string | undefined?
    The optional form lets you omit the key entirely; the union form requires the key to be present, with undefined as an allowed value. So the union catches a forgotten field at the construction site, which is often what you want for a shape you build yourself, while the optional form is right for input you may not receive. By default the optional form also accepts an explicit undefined, which blurs the two.
  4. What does exactOptionalPropertyTypes change?
    It stops name?: string from accepting an explicit undefined, so the key must either be absent or hold a real string. That matters wherever presence is meaningful — a JSON patch where { name: undefined } should clear a field and an absent key should leave it alone, or a check using in. It is not in strict and it produces real errors in existing code, most of them worth fixing.
  5. Why is readonly weaker than it looks?
    It is shallow and it erases. Shallow: readonly tags: string[] stops you replacing the array and not mutating it, so push compiles. Erased: nothing is frozen at runtime, and a Readonly<T> remains assignable to a mutable T, so passing it to a function that mutates is accepted. It documents intent and catches direct assignment, and it is not a guarantee.
  6. Why is Record<Status, Handler> better than an index signature here?
    Because the keys are exactly the union members, so omitting one is a compile error and adding a new status breaks every map that has not been updated. An index signature accepts any string, gives no completion for the real keys, and — without noUncheckedIndexedAccess — claims a value exists for keys that do not. The Record version turns a lookup table into an exhaustiveness check.
