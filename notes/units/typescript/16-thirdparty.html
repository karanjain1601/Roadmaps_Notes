Typing code you do not control

A dependency's declarations are a claim by someone who may not have written the library, may not have updated them, and is certainly not running your tests. Treating them as facts is how a fully strict codebase acquires unchecked regions it does not know about.

Declaration merging, and why augmentation needs it

An interface declared twice merges — chapter 4's one deciding capability. Inside a declare module "pkg" block, that lets you reopen a library's interface and add to it, which is the only supported way to say "Express's Request also has a user". Three constraints catch people out: the file must be a module (it needs a top-level import or export, or the block declares a new module instead of augmenting one); the module specifier must resolve exactly as your imports do; and you can add members but not change existing ones — a conflicting redeclaration is an error, not an override.

Check the @types major version against the library's
They are separate packages on separate release cycles, so @types/foo@2 alongside foo@4 installs cleanly and describes a library you are not running. Most modern packages bundle their own declarations; a separate @types entry is worth a glance every time you see one.
Declare only what you call
A hand-written declaration for an untyped package should cover the three functions you use, accurately, and nothing else. A complete-looking declaration that nobody verified is worse than a small one, because its size implies a diligence that was not applied. Reaching an undeclared member then becomes a compile error, which is the correct outcome.
Prefer augmentation to a local shadow
A declare module "pkg" in your own .d.ts with no import in the file replaces the package's types entirely — which silently discards everything the package correctly declared, and stops tracking its updates. Augmenting inside a module file adds to them instead. The difference is one import statement and it is easy to get wrong in either direction.
An upstream fix should remove your patch
Every workaround here is a small permanent liability unless something makes it expire. Put the issue link in a comment, and where the patch is a suppression use @ts-expect-error — chapter 9 — so the build tells you when the fix lands.

Self-check

  1. Why is a hand-written declaration for three functions better than a complete one?
    Because you can actually verify three functions against the library's behaviour, and a complete declaration nobody checked is a large surface of unverified claims that looks authoritative. With a small declaration, calling something you did not declare is a compile error — which tells you to go and check that member before using it. Size implies diligence, so only claim what you have confirmed.
  2. What are the three constraints on module augmentation?
    The file must be a module, meaning it has a top-level import or export — otherwise the declare module block declares a new module rather than augmenting the existing one, silently replacing its types. The specifier must resolve exactly as your imports do. And you may add members, not change them: a conflicting redeclaration is an error rather than an override.
  3. What is the difference between augmenting and shadowing a package's types?
    Augmenting reopens the package's own interfaces and adds to them, so everything it correctly declared still applies and updates still reach you. Shadowing — a declare module "pkg" in a file with no imports — replaces the declarations wholesale, discarding everything the package got right and freezing your view of it. The syntactic difference is one import statement in the file.
  4. Why is a wrong declaration worse than a missing one?
    Because a missing one produces an any that noImplicitAny reports, so you know where you stand. A wrong one gives you a confident type over an incorrect assumption, and there is no flag for that — the compiler is doing precisely what it was told and every reader downstream believes something was verified. It is chapter 9's laundering, performed by a dependency on your behalf.
  5. What does a wrapper module buy?
    It reduces the number of files that depend on the untrusted types from however many use the library to exactly one. So a corrected type, a parse, or an upgrade that changes the API is a change in one place rather than a search across the codebase — and the rest of your code depends on a signature you wrote and can verify. The cost is one small module and a rule that nobody imports the library directly.
  6. Why check the @types version against the library's?
    Because they are separate packages with separate release cycles, so nothing stops @types/foo@2 being installed beside foo@4. The declarations then describe a library you are not running — usually with the majority still correct, which is what makes the incorrect parts hard to find. Most modern packages bundle their own types; a separate @types entry deserves a look at its version whenever you notice one.
