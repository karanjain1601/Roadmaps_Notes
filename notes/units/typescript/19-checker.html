Why the checker is slow

Almost never the number of files. It is the number of type instantiations — and a handful of ordinary-looking patterns multiply that number without looking expensive. The good news is that the causes are few, measurable, and mostly fixed by writing types down instead of computing them.

# ① is it slow, and where?
tsc --noEmit --extendedDiagnostics
#   Files, Types, Instantiations, Memory used, and a time breakdown.
#   INSTANTIATIONS is the number to watch. Under ~1M is comfortable;
#   past ~5M something is generating types combinatorially.
#   "Check time" dominating means types; "Parse time" means too
#   many files in the program — check `include` and `--listFiles`.

# ② which files are even in the program?
tsc --noEmit --listFilesOnly | wc -l
#   A stray include pulling in test fixtures, or a `types` array you
#   never set so every @types package in node_modules is loaded.

# ③ what specifically is expensive?
tsc --noEmit --generateTrace ./trace
#   Open trace/trace.json in Perfetto (ui.perfetto.dev), or:
npx @typescript/analyze-trace ./trace
#   which prints the hot spots as text — usually one type alias and
#   one file, and usually a surprise.

# ④ is the editor slow for a different reason?
#   VS Code → "TypeScript: Open TS Server log", or the
#   Performance command. The editor checks the OPEN FILE and its
#   dependencies, so an unbearable editor with a fast CI build
#   means one import graph, not the whole project.

# ⑤ the two settings that are nearly free
#   "incremental": true      — caches the last build
#   "skipLibCheck": true     — stops checking .d.ts files

The editor and the build are different problems
The language server checks the open file and what it imports, not the whole program — so a slow editor with a fast CI build points at one import graph, and the reverse points at total program size. Diagnose them separately or you will optimise the wrong thing.
Naming a type is a caching hint
An inlined multi-level conditional is re-instantiated at every use; an aliased one gives the compiler something to memoise and the reader something to hold. Chapter 8 made the legibility argument — this is the same advice for a different reason, and on a hot type it can be the whole fix.
Type-level programming has a budget
Recursive conditionals, template literal parsing and deep mapped types are genuinely useful and genuinely expensive, and the cost lands on everyone who opens the editor. A router that infers path parameters from a string earns it; a type-level arithmetic library in your domain model does not. Measure before and after adding one.
skipLibCheck and incremental first, always
Two lines, no code changes, and often a third off the build. Do them before investigating anything, so the number you then measure is the real one. Chapter 18 covers what skipLibCheck hides in exchange.

Self-check

  1. What number should you look at first?
    Instantiations, from tsc --extendedDiagnostics. It counts how many times generic types were instantiated, which is what the checker actually spends its time on — under about a million is comfortable, and past five million something is generating types combinatorially. File count is a much weaker predictor: a thousand plain modules check faster than fifty that compute their types.
  2. Why do inferred return types on exported functions cost so much?
    Because every consumer of the function has to re-derive the type by checking its body, and if that body calls other functions with inferred returns, the derivation is transitive. Annotating the return turns an inference across the whole call graph into a lookup. It is usually the single largest win available, and it is also chapter 5's advice for a different reason — an inferred public signature can change without anyone deciding to change it.
  3. What does a recursive conditional cost, and how do you contain it?
    Each level is a fresh instantiation, so a type recursing over a long string or a deep object multiplies quickly, and nested recursion hits "excessively deep" at around fifty levels. Write it in tail position with an accumulator so the compiler iterates rather than nests — chapter 8 — cap the depth deliberately, and alias each stage so the results can be cached.
  4. Why does an intersection cost more than the equivalent interface?
    Because the compiler keeps the members separate and resolves them on each property access, rather than having one flat member list to look up. It also makes error messages expand into the full structure. A single interface, or an identity mapping to flatten it — chapter 7's Prettify — is both faster and far more legible.
  5. When are project references worth the setup?
    When you have several packages and most changes touch one of them. References let tsc --build skip unchanged packages entirely and read a dependency's declarations rather than re-checking its source, so an incremental build scales with what you changed rather than with the repository. The costs are real: you must build dependencies before consumers, and a stale declaration produces errors that look like your code is wrong.
  6. The editor is unusable but CI passes in twenty seconds. What is that?
    One import graph, not the whole project. The language server checks the open file and its dependencies, so an expensive type reached from the file you happen to be editing dominates — while the full build amortises it across everything else. Open the TS server log or the performance command and look at what that particular file pulls in; the culprit is usually a single computed type in a shared module.
