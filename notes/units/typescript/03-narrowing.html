Narrowing and control flow

The chapter that changes how you write code. The compiler tracks a union's type separately down every branch, which means an ordinary if is also a type operation — and once you model state as a tagged union rather than a bag of optional fields, a large class of bug becomes unrepresentable rather than merely unlikely.

typescript — predicates, assertions, and the pattern in full
// ── the shape ──
type Fetch<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "ok";    data: T }
  | { status: "error"; error: Error };
// each variant carries exactly the fields that state has, so
// `data` cannot be read unless status is "ok" — the compiler will
// not let you, which is the entire point.

function view<T>(f: Fetch<T>) {
  switch (f.status) {
    case "idle":    return null;
    case "loading": return spinner();
    case "ok":      return list(f.data);     ← f is the ok variant
    case "error":   return err(f.error);
    default:        return exhaustive(f);   ← chapter 14
  }
}

// ── a type predicate: your own guard ──
function isOk<T>(f: Fetch<T>): f is { status: "ok"; data: T } {
  return f.status === "ok";
}
// ✱ the compiler does NOT verify the body matches the claim. A
//   predicate is an assertion with a return type — write it once,
//   keep it tiny, and test it. TypeScript 5.5 infers many simple
//   predicates for you, so check whether you still need it.

results.filter(isOk).map(r => r.data);    ← the reason predicates

  if (x == null) throw new Error("expected a value");
}

Narrowing survives more than you expect, and less
It flows through return and throw in earlier branches, through && and ||, through a condition stored in a const (since 4.4), and through destructured discriminants (since 4.6). It is discarded inside a nested function for anything mutable, because the compiler cannot know when that function runs.
It is not invalidated by a function call
After if (o.v) { mutate(); o.v.trim(); } the compiler still believes o.v is defined, even though mutate() could have cleared it. That is a deliberate unsoundness — tracking it properly would reject enormous amounts of correct code — and it is worth knowing when a "cannot be undefined" value is undefined at runtime.
Optional chaining does not narrow afterwards
a?.b is an expression, not a check. The next line still sees a as possibly nullish, which is correct and reads as though it should not be.
find, pop and index access
find and pop return T | undefined and you must handle it. arr[0] is typed T and is a lie — enable noUncheckedIndexedAccess and it becomes T | undefined, which is truthful and will produce a great many new errors in an existing codebase.

Self-check

  1. What is control-flow analysis doing that a type annotation cannot?
    Tracking a variable's type per program point rather than once at its declaration. A parameter declared string | number | null has a different type inside each branch of a guard chain, and the compiler recomputes it after every condition, assignment, early return and throw. So an ordinary if is simultaneously a runtime check and a type operation, which is what makes unions usable in place of the inheritance hierarchies other languages need.
  2. Why is if (x) a poor guard for a string or a number?
    Because it narrows on truthiness, which excludes "", 0, NaN and false as well as null and undefined. So a valid empty string or a legitimate zero takes the "missing" branch — the classic version being a quantity of 0 or a page number of 0 silently treated as absent. Use x != null, which catches exactly null and undefined and nothing else.
  3. Why does a discriminated union beat a boolean with optional fields?
    Because each variant carries exactly the fields its state has, so the invalid combinations cannot be constructed at all. A loading flag with optional data and error can represent "loading and also errored with data" — the compiler will happily build it, and every consumer has to defend against combinations that should be impossible. The union has one field to switch on, and the compiler gives you the right fields in each branch.
  4. How many impossible states does a boolean plus two optional fields allow?
    Five. Eight combinations are representable and only three are meaningful, so the type permits five states your code must either handle or ignore. And it is exponential: each additional optional field doubles the representable set while adding one real state, which is why these types accumulate defensive checks over time and why the union stays linear.
  5. What does a type predicate not do?
    Verify itself. function isOk(f): f is Ok tells the compiler to trust the return value as evidence, and the body is not checked against the claim — you could return true unconditionally and everything downstream would compile. So a predicate is an assertion with a nicer signature: write few of them, keep each one small enough to read at a glance, and test them. TypeScript 5.5 infers many simple ones automatically, which removes most of the need.
  6. Why is narrowing not invalidated by an intervening function call?
    Because tracking it soundly would mean assuming any call could mutate any reachable property, which would discard narrowing constantly and reject a great deal of correct code. So the compiler keeps the narrowing across calls, and if (o.v) { reset(); o.v.trim(); } compiles even when reset clears o.v. It is a known hole worth remembering whenever a value the types say is defined turns out not to be.
