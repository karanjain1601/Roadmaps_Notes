Functions, overloads and variance

Function assignability is where a type system's rules stop being obvious, and where TypeScript keeps two deliberate holes that let ordinary JavaScript compile. Both are worth knowing exactly, because both let a genuine type error through.

Variance

Given class Dog extends Animal, which of these substitutions is safe? Two of the answers TypeScript gives are wrong on purpose.

Can I use this where that is expected?
Watch the sound column
The two holes, stated plainly
  • Method parameters are bivariant. A property written m: (x: Dog) => void is checked strictly under strictFunctionTypes; the same thing written m(x: Dog): void is not. The exemption exists because Array<Dog>'s methods would otherwise make it incompatible with Array<Animal>, and that would break an enormous amount of correct code.
  • Arrays are covariant. Dog[] is assignable to Animal[], and then animals.push(cat) compiles — putting a Cat in an array everyone else believes holds Dogs. The fix, where it matters, is readonly T[], which is covariant and sound because there is nothing to write through.

Overload resolution picks the first match
Not the best one. So order matters: put the most specific signature first, or a broad one will swallow calls the narrow one should have handled. The implementation signature is not itself callable and is not checked against the overloads with any rigour, which makes overloads a place bugs hide.
Prefer a union parameter to two overloads
If the return type does not depend on which argument you passed, overloads add nothing but a maintenance surface. They earn their place when the return type does depend on the input and a conditional type would be worse to read — the classic being DOM APIs where the tag name determines the element type.
Optional parameters and undefined
(x?: number) means the argument may be omitted or passed as undefined — unlike optional properties, this is unaffected by exactOptionalPropertyTypes. And an optional parameter cannot precede a required one, which is why option objects beat long parameter lists.
Assertion and predicate signatures are declarations, not proofs
Chapter 3: the body of a function returning x is T or asserts x is T is not verified against the claim. They are the two function-level escape hatches, and they belong in the same mental category as as — chapter 9.

Self-check

  1. Why can a handler taking Animal stand in for one taking Dog?
    Because the caller will only ever pass a Dog, and a function that accepts any Animal handles a Dog perfectly well. Parameters are contravariant: a substitute may accept more than required, never less. The reverse — a Dog-only handler where any Animal may arrive — would receive a Cat and break, which is why it is rejected.
  2. Why are method parameters checked more loosely than function-property parameters?
    Because strict checking would make Array<Dog> incompatible with Array<Animal> — the array's own methods take T in parameter position, so contravariance would forbid the assignment that everybody relies on. Rather than break that, TypeScript exempts method-shorthand parameters from strictFunctionTypes and checks them bivariantly. It is a deliberate hole, and it means the two ways of writing a callback member are not equivalent.
  3. What can go wrong once Dog[] is assignable to Animal[]?
    You can write through the alias: animals.push(cat) compiles, and now an array everyone else believes holds only Dogs contains a Cat. Array covariance is unsound for exactly this reason and is accepted because forbidding it would reject an enormous amount of reasonable code. Use readonly T[] where it matters — it is covariant and sound, because there is no write to exploit.
  4. Why do overloads fail on a union argument?
    Because resolution picks a single overload that matches the whole argument, and a value of type string | number matches neither the string signature nor the number one. The compiler does not split the call across overloads. A union parameter accepts it but loses precision at every call site; a generic with a conditional return distributes over the union and keeps it — which is chapter 8.
  5. Why does a void-returning callback accept a function that returns something?
    Because void in a return position means "the caller will ignore this", not "this returns nothing". So any return type is assignable, which is what makes arr.forEach(x => set.add(x)) compile despite add returning the set. The cost is that an async callback passed into a void-typed slot is accepted and never awaited, so its rejection is unhandled — chapter 15.
  6. Why annotate the return type of exported functions?
    Three reasons. The contract becomes deliberate rather than whatever the body happened to produce; an internal change cannot silently widen or narrow your public type, so the diff shows up where the decision was made; and the checker skips inferring it, which is a measurable saving on a large codebase and on editor responsiveness — chapter 19. It also stops literal widening from surprising you, as in chapter 2's return-position case.
