Modules and declaration files

TypeScript resolves a specifier to a type and the runtime resolves the same specifier to a file, and keeping those two answers in agreement is most of what module configuration is. The rest is knowing where a package's types come from — and what happens when there are none.

typescript — declaration files, and the import forms
// ── a module declaration: types for a package that ships none ──
// src/types/legacy-widget.d.ts
declare module "legacy-widget" {
  export interface Options { theme?: "light" | "dark" }
  export default function mount(el: Element, o?: Options): void;
}
// declare only what you actually call. A partial declaration you
// trust beats a complete one nobody checked — chapter 16.

// ── ambient globals ──
declare global {
  interface Window { __APP_VERSION__: string }   ← merging, so
  namespace NodeJS {                                it must be an
    interface ProcessEnv { DATABASE_URL: string }    interface —
  }                                                  chapter 4
}
// ✱ typing process.env this way is a lie: the variable may be
//   absent at runtime and the type says string. Validate at boot
//   instead — chapter 13, and chapter 19 of the Node unit.

// ── type-only imports, and why they matter ──
import type { Order } from "./order.js";      ← erased entirely
import { type Order, createOrder } from "./order.js";  ← mixed

//   ① a single-file transpiler (esbuild, SWC, babel) cannot know
//      whether an imported name is a type, so without `type` it
//      emits the import — and a type-only module becomes a runtime
//      dependency, or a circular import appears from nowhere
//   ② it stops a side-effecting module being loaded by accident
//   ③ verbatimModuleSyntax makes the rule explicit: imports are
//      emitted exactly as written, and `type` is how you elide

// ── paths, and its one catch ──
{ "paths": { "@app/*": ["./src/*"] } }
// tsc REWRITES NOTHING. The emitted JavaScript still says
// "@app/order.js", so the bundler or Node must be told the same
// mapping. Prefer package.json "imports" (#config) — chapter 2 of
// the Node unit — which the runtime honours on its own.
A file with no top-level import or export is a script, not a module
Everything it declares is global, and it will silently collide with another file's declarations. This is the cause of "duplicate identifier" errors in files that look unrelated. Add export {} to make an otherwise side-effect-only file a module.
.d.ts files declare and never define
They contain types and declared values, emit nothing, and are how every package describes itself. You write them by hand for untyped dependencies and for globals; for your own code, declaration: true generates them — chapter 18.
isolatedModules and verbatimModuleSyntax
Both exist because most builds no longer use tsc to emit. They forbid the patterns a per-file transform cannot handle — re-exporting a type without type, const enum across files — so your code stays compatible with esbuild, SWC and Vite. Turn them on before you need them, not after.
Triple-slash directives are legacy
/// <reference types="node" /> still works and is occasionally needed in a .d.ts, but for ordinary code the types array in tsconfig and plain imports have replaced it.

Self-check

  1. Why does import "./util.js" resolve to util.ts?
    Because under nodenext the specifier describes what the runtime will resolve, and the runtime will see util.js after compilation. So you write the output path and TypeScript maps it back to the input file. It looks wrong the first ten times and it is the only self-consistent answer: the compiler does not rewrite specifiers, so the one in your source has to be the one that works at runtime.
  2. What does moduleResolution: "bundler" permit that nodenext does not?
    Extensionless relative specifiers, and it drops the CJS/ESM dual-format rules. That matches what bundlers actually do, and it is the right choice when a bundler owns resolution. It is the wrong choice for code Node will run directly, because Node requires the extension in ESM — the build would pass and the program would fail to start.
  3. Where does TypeScript look for a package's types, in order?
    The types condition in the package's exports map first; then the top-level types or typings field; then a .d.ts sitting beside the resolved JavaScript; then node_modules/@types/<name>; then your own declare module. If none of those match, the import is any — or an error, if noImplicitAny is on.
  4. What does an untyped dependency actually cost?
    Every value imported from it is any, so chapter 9's propagation applies from the import statement outward: every call, every property, every derived value is unchecked, and assignments into typed variables are accepted. With noImplicitAny the import errors and you are forced to decide; without it the module is silently unchecked and nothing in the codebase indicates where the checking stopped.
  5. Why is import type necessary rather than merely tidy?
    Because a single-file transpiler cannot tell whether an imported name is a type or a value — it never sees the other file. Without the marker it must keep the import, so a module you only import types from becomes a runtime dependency, which can pull in side effects or create a circular import that did not exist in the type graph. verbatimModuleSyntax makes the rule explicit and the failures immediate.
  6. Why is paths not enough on its own?
    Because tsc does not rewrite specifiers — the emitted JavaScript still contains @app/order.js, which means nothing to Node or to a bundler that has not been given the same mapping. So every alias has to be configured twice, in two places that can drift. The imports field in package.json is the standards-based alternative and the runtime honours it directly.
