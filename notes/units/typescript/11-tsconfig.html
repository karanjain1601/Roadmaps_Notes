tsconfig, option by option

There are around a hundred compiler options and roughly a dozen that matter. They split cleanly: the ones that change what the compiler accepts, which is where all the value is, and the ones that change what it emits, which mostly need to agree with whatever actually runs your code.

Six kinds of project
Two combinations the compiler refuses outright
skipLibCheck is on in every template, and it is a trade
It stops the compiler type-checking .d.ts files, which is a large speed win and a way to survive a dependency whose declarations do not compile. The cost is that a genuine conflict between two packages' types goes unreported until it produces a confusing error in your own code. Keep it on; know what it hides.
target and lib are different questions
target decides what syntax is emitted; lib decides which built-ins the compiler believes exist. Setting target: "es2022" gives you Array.prototype.at in the type system whether or not your runtime has it — so a browser support matrix needs lib chosen deliberately, not inherited from target.
Do not put strict: false in a new project
It is not a smaller version of TypeScript; it is a different and much weaker one. strictNullChecks alone is most of the value — with it off, the compiler cannot find a single null dereference. If an existing codebase cannot turn it on today, chapter 17 is about getting there incrementally.
Extend a base config rather than writing one
@tsconfig/node22, @tsconfig/strictest and the rest encode the correct target, lib and module settings for a platform, and they are updated when the platform changes. Extend one and override the two or three things specific to you.

Self-check

  1. Which single flag matters most, and why?
    strictNullChecks. With it off, null and undefined are assignable to every type, so the compiler cannot report a single null dereference — the largest class of runtime error in JavaScript becomes invisible. noImplicitAny is a close second, because without it whole regions of a codebase are unchecked while reporting zero errors. Both are in strict.
  2. What does noUncheckedIndexedAccess change, and why is it not in strict?
    It makes arr[0] and record[key] return T | undefined rather than T, which is the truth. It is not in strict because it produces a very large number of errors in existing code — every array index in the codebase — and many of them are at sites the author knows are safe. It is close to free on a new project and a project of its own on an old one.
  3. What does exactOptionalPropertyTypes fix?
    It stops an optional property accepting an explicit undefined, so name?: string means the key is absent or holds a string — nothing else. That makes optionality mean presence, which is what the syntax always looked like it meant, and it matters wherever the difference is semantic: a JSON patch where clearing a field and omitting it should differ, or code branching on in. Chapter 4.
  4. Why must module and moduleResolution agree?
    Because they answer two halves of one question — what output format is emitted, and how specifiers are resolved — and the compiler rejects combinations that cannot describe a real setup. module: "nodenext" requires moduleResolution: "nodenext", and moduleResolution: "bundler" requires module: "esnext" or "preserve". Getting them out of step produces resolution errors that look like missing packages.
  5. Why is target not enough to describe what you can use?
    Because target only controls emitted syntax, while lib controls which built-ins the compiler believes exist. So target: "es2022" lets you call Array.prototype.at and Object.hasOwn in the type system regardless of whether your oldest supported browser has them, and the failure is at runtime with no compile error. Choose lib from your support matrix and target from what your build tool will downlevel.
  6. What does skipLibCheck hide?
    Errors inside .d.ts files, including genuine conflicts between two packages that declare incompatible versions of the same global or interface. Those conflicts then surface as confusing errors in your own code, or as silently wrong types. It is on in every sensible template because the speed win is large and because one dependency with broken declarations should not stop your build — but it is a suppression, not a fix.
