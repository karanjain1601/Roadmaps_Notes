Networking for defenders

Every attack crosses a network, and most detection and nearly all containment happens there. You do not need a network engineer's depth, but you do need to read an address, know which protocols carry what, and understand why the answer to "how far can they get?" is decided by decisions made long before the intrusion.

2.1The layered model, as a tool

The OSI model is worth knowing not because networks are built that way — they are not, TCP/IP has four layers and the mapping is loose — but because it gives you a ladder to climb when something is wrong and a vocabulary for saying where a control operates.

The diagnostic use

When something is unreachable, climb the ladder from the bottom and stop at the first failure. Link: is the interface up, is there an ARP entry for the gateway? Network: can you ping the gateway, then something beyond it, and is there a route? Transport: is the port open — nc -vz host port? Application: does the protocol respond, does TLS complete, does the name resolve? Each step eliminates everything below it, and doing it in order takes a fraction of the time of guessing. The same ladder tells you which control could be blocking: a dropped TCP handshake is layer 4 (firewall), a TLS error is layer 6 (certificate or cipher), an HTTP 403 is layer 7 (WAF or authorisation).

2.2Addressing

An IPv4 address is 32 bits, written as four decimal octets. A prefix length says how many leading bits identify the network; the rest identify the host. That single idea is all of subnetting.

Two addressing facts that cause real incidents

169.254.169.254 is the cloud instance metadata service on AWS, Azure and GCP. A server-side request forgery that reaches it can retrieve instance credentials, and that is the mechanism behind several of the largest cloud breaches on record. IMDSv2 requires a token obtained by PUT with a hop limit, which defeats the simple case — enforce it.

IPv6 is enabled by default on modern operating systems and is frequently unfiltered and unmonitored even where IPv4 is tightly controlled. An attacker who can send router advertisements on a local segment can become the default gateway for IPv6 traffic on hosts that have no IPv6 policy at all. If you are not using it, disable it or filter it — do not merely ignore it.

The pattern worth extracting: the dangerous ports are the management and data ports, not the application ones. An exposed web server is expected and defended; an exposed RDP, SMB, database or admin interface is an accident, and scanners find it faster than you will. Which is why the first question about any host is not "is it patched" but "what is listening, and who can reach it".

2.4How a packet actually arrives

One HTTPS request from a laptop, at the protocol level 
1  DHCP  — at boot, the laptop broadcasts and is given an
   address, a mask, a gateway and DNS servers.
   ATTACK: a rogue DHCP server answers first and becomes the
   gateway and resolver for everyone. Defence: DHCP snooping.

2  DNS   — resolve the name to an address.
   ATTACK: poisoning, spoofed responses, a malicious resolver.
   Defence: DNSSEC validation, controlled resolvers, logging.

3  ROUTING DECISION — is the destination in my subnet?
   Compare destination AND mask against my network address.
   Same subnet → send directly.  Different → send to gateway.
   THIS is why the mask matters: it decides local vs remote.

4  ARP   — I have an IP for the next hop; I need its MAC.
   Broadcast "who has 10.20.30.1?", cache the reply.
   ATTACK: ARP poisoning — anyone on the segment can answer,
   and become the machine-in-the-middle. ARP has no
   authentication whatsoever. Defence: dynamic ARP inspection.

5  SWITCH — forwards the frame by MAC address.
   ATTACK: MAC flooding overflows the CAM table and forces the
   switch to broadcast everything, making sniffing trivial.
   Defence: port security limiting MACs per port.

6  ROUTER / NAT — rewrites the private source address to a
   public one and tracks the translation.
   NOTE: NAT is not a security control. It makes inbound
   connections awkward as a side effect; it stops nothing
   outbound, and outbound is how C2 works.

7  TCP + TLS handshakes, then the request.        → ch 9

Three of those steps — DHCP, ARP and the switch's forwarding table — have no authentication at all. They were designed for cooperative networks, and anything on the local segment can lie to all three. That is the single most important fact in this chapter, and it is why being on the same segment as something valuable is itself a risk, which leads directly to the next section.

2.5Segmentation

The highest-leverage network control there is. A flat network means one compromised laptop can reach the domain controller, the backup server, the finance database and the building's access control system. Segmentation makes each of those a separate decision.

The zone that deserves naming: a DMZ is a segment for systems that must be reachable from the internet, arranged so that a compromise there does not give access to the internal network. The rule that makes it work is that the DMZ initiates nothing inbound — internal systems may pull from it, but a compromised DMZ host must not be able to open a connection to the internal network. A "DMZ" whose web server holds database credentials for an internal database, and can reach it, is a naming convention rather than a control.

Two attacks to recognise. An evil twin is a rogue access point broadcasting your SSID, often with a stronger signal, so devices associate with it and the operator becomes the machine-in-the-middle — which is why certificate validation on the client side matters more than the wireless encryption. And deauthentication frames, which in older standards are unauthenticated, let anyone forcibly disconnect a client — used both as denial of service and to force a reconnection so the handshake can be captured. Management frame protection, mandatory in WPA3, closes that.

Why is NAT not a security control?

Because it constrains the wrong direction. NAT translates private addresses to a shared public one and keeps a table of active translations, so an unsolicited inbound packet has nowhere to go — which looks protective and is genuinely a side effect worth having. But it does nothing to outbound connections, and outbound is how essentially every modern intrusion operates: malware calls out to its command-and-control server, the connection is established from inside, and NAT dutifully creates a translation entry and forwards traffic in both directions for the life of that connection. It also does nothing about anything already inside the network, which is where lateral movement happens. Three further points. NAT is often confused with a stateful firewall because they are usually the same appliance — the firewall is doing the security work and the NAT is doing address conservation. IPv6 largely removes the need for NAT, so anyone relying on it as a control loses it as IPv6 arrives. And a badly configured NAT can be worse than none, since hairpinning and port-forwarding rules accumulate and are rarely reviewed. The control you actually want for the inbound direction is a stateful firewall with a default-deny policy, and for the outbound direction it is egress filtering — which is the control most organisations do not have.

Two hosts are on 10.20.30.44/24 and 10.20.31.5/24. Can they reach each other, and does a firewall see the traffic?

They are in different subnets, so the traffic must be routed — and that is what makes it inspectable. With a /24 mask the first host's network is 10.20.30.0 and the second's is 10.20.31.0, so when host A wants to reach B it compares B's address against its own network and mask, finds no match, and sends the frame to its default gateway instead of ARPing for B directly. The router then makes a forwarding decision, and any ACL or firewall on that path sees the packet. So yes, they can reach each other if policy permits, and yes, a firewall between the subnets sees it. Change the mask to /16 and both facts reverse: both hosts are now in 10.20.0.0/16, host A ARPs for B directly, the frame goes through the switch without ever reaching a router, and no layer-3 control sees it at all. That is the single most important practical consequence of subnetting for a defender — the mask decides whether traffic is inspectable. It is also why host-based firewalls matter: they are the only control that sees peer-to-peer traffic within a subnet, and within-subnet traffic is exactly where lateral movement happens.

Why is DNS the most abused outbound protocol?

Because it is allowed everywhere, rarely inspected, and structurally suited to carrying data. Almost no organisation blocks outbound DNS, because doing so breaks everything, and many that filter HTTP and HTTPS heavily do not look at port 53 at all. That gives an attacker a channel out of even a well-egress-filtered network. The mechanism is straightforward: encode data into subdomain labels and query them against a domain you control — <base32-of-stolen-data>.exfil.attacker.com — and your authoritative nameserver receives the query and therefore the data, with the response carrying instructions back. It is slow and noisy but reliable, and it works from hosts that can reach nothing else. Detection looks for the shape rather than the content: unusually long query names, high query volume to a single domain, high proportion of unique subdomains under one parent, TXT and NULL record types in volume, and queries to domains registered very recently. The controls that help are forcing all clients through a controlled resolver and blocking direct port 53 egress, logging every query with the client that made it, and applying newly-registered-domain and DGA detection to that log. The same argument applies to ICMP and to HTTPS to a legitimate cloud service — the general principle is that a permitted channel is a channel.

Recap

  1. Use the layer model as a diagnostic ladder, climbing from the bottom and stopping at the first failure.
  2. The mask decides local versus routed, and therefore whether any layer-3 control ever sees the traffic.
  3. Know the private ranges on sight, and know that 169.254.169.254 is the cloud metadata endpoint SSRF targets.
  4. IPv6 is on by default and often unfiltered even where IPv4 is tightly controlled.
  5. The dangerous ports are management and data ports, not application ones. Ask what is listening before asking what is patched.
  6. DHCP, ARP and switch forwarding have no authentication. Anything on the segment can lie to all three.
  7. Segmentation is the highest-leverage network control, and a DMZ only works if it initiates nothing inbound.
  8. Host firewalls are the only control that sees within-subnet traffic, which is where lateral movement happens.
  9. NAT is not a security control. It constrains inbound as a side effect and does nothing about outbound, which is how C2 works.
  10. DNS is the favourite covert channel because it is permitted everywhere and rarely inspected.
