Cryptography

You will almost never implement any of this, and you will constantly make decisions that depend on understanding it: which algorithm, which key length, what a certificate error actually means, whether an incident exposed anything. This chapter is the working model — what each primitive guarantees, and what it does not.

8.1What each primitive gives you

Four tools, four different guarantees — and none of them substitutes for another
PrimitiveProvidesDoes not provideExamples
Symmetric cipherConfidentiality, fast, at any volumeIntegrity, unless it is an AEAD mode. Also no way to share the keyAES-GCM, ChaCha20-Poly1305
Asymmetric cipherConfidentiality without a shared secret; signaturesSpeed. Orders of magnitude slower, so it is used on keys, not dataRSA, ECIES
HashA fixed-length fingerprint; integrity checkingConfidentiality — a hash of a small input space is reversible by guessing. And no authenticitySHA-256, SHA-3, BLAKE3
MAC / signatureIntegrity and authenticityConfidentiality. A signed message is still readableHMAC-SHA256, Ed25519, ECDSA
Encryption is not integrity

The mistake that produces real vulnerabilities. Encrypting data stops someone reading it; it does not stop them changing it. With a stream cipher or CTR mode, flipping a bit in the ciphertext flips exactly that bit in the plaintext — so an attacker who knows the message structure can alter an amount or a username without knowing the key. With CBC, manipulating the ciphertext plus an oracle that reveals whether padding was valid lets you decrypt the whole message. The fix is authenticated encryption: AES-GCM or ChaCha20-Poly1305, which produce a tag that fails loudly on any modification. Use an AEAD mode by default and treat any design that encrypts without authenticating as a defect.

8.2Symmetric encryption

One key, shared by both parties, used to encrypt and decrypt. Fast enough to encrypt everything, which is why all bulk data ends up here — the asymmetric parts of a protocol exist mainly to agree on a symmetric key.

Modes matter more than the cipher 
AES is fine. What people get wrong is the MODE.

ECB   Never. Each identical block encrypts identically, so
      structure in the plaintext survives into the ciphertext.
      The classic demonstration is an image encrypted with ECB
      in which you can still see the picture.

CBC   Needs a random, unpredictable IV per message. Vulnerable
      to padding-oracle attacks if error handling leaks whether
      padding was valid. Provides no integrity on its own.

CTR   Turns a block cipher into a stream cipher. NEVER reuse a
      nonce with the same key — doing so lets an attacker XOR
      two ciphertexts together and remove the keystream entirely.
      No integrity on its own.

GCM   CTR plus an authentication tag. AEAD: confidentiality and
      integrity together. The default choice. Same nonce rule:
      reuse is catastrophic, and worse here because it also
      leaks the authentication key.

ChaCha20-Poly1305
      AEAD, no hardware acceleration needed, so it is faster
      than AES on devices without AES-NI. Equally good.

THE RULE
  Use an AEAD mode. Generate nonces randomly or with a strict
  counter you can guarantee never repeats. Never write your
  own mode.

8.3Asymmetric encryption

A mathematically linked key pair: what one encrypts, only the other decrypts. That asymmetry solves the problem symmetric cryptography cannot — establishing confidentiality with someone you have never met.

Two uses, and they run in opposite directions 
CONFIDENTIALITY            encrypt with the RECIPIENT'S PUBLIC key
                           only their private key decrypts it
                           → anyone can send; only they can read

AUTHENTICITY (signing)     sign with YOUR PRIVATE key
                           anyone verifies with your public key
                           → only you could have sent it, and it
                             has not been altered

The two are mirror images, and confusing them is the most
common conceptual error in this area. "Encrypt it with my
private key" is not a thing you want — everyone has your
public key, so everyone can read it.

IN PRACTICE, ASYMMETRIC IS USED ON KEYS, NOT DATA
  RSA-2048 encrypts at roughly a thousandth the speed of AES
  and can only encrypt a few hundred bytes at a time. So a
  protocol uses it to agree a symmetric key, then switches:

    1  agree a shared secret          (asymmetric, once)
    2  derive symmetric keys from it  (a KDF)
    3  encrypt everything else        (symmetric, fast)

  This is the hybrid construction, and it is what TLS, SSH,
  PGP and Signal all do.                              → ch 9

8.4Key strength

What a key length actually buys

Equivalence figures follow NIST SP 800-57. Note that symmetric and asymmetric bit counts are not comparable.

Bit counts across families are not comparable

RSA-2048 and AES-256 are not "2048-bit" and "256-bit" on the same scale. RSA's security comes from the difficulty of factoring, and the best known factoring algorithms are far better than brute force, so a 2048-bit modulus provides roughly 112 bits of security. Elliptic curves have no comparable shortcut, so a 256-bit curve gives about 128 bits — which is why ECC keys are so much smaller for equivalent strength, and why they are preferred for anything constrained. Reading "2048" as stronger than "256" is a common and consequential error: it leads to specifying large RSA keys, taking the performance cost, and ending up with less security than a small curve would give.

8.5Hashing

Three properties, which fail in this order
PropertyMeansBroken means
Pre-image resistanceGiven a hash, you cannot find an input producing itThe hash is reversible. Catastrophic
Second pre-image resistanceGiven an input, you cannot find a different one with the same hashAny signed document can be substituted
Collision resistanceYou cannot find any two inputs with the same hashThe first to fall, because of the birthday bound. Enough to forge certificates

The birthday bound is why collision resistance is only half the hash length: finding a collision in an n-bit hash takes about 2n/2 work, not 2n. SHA-256 therefore offers 128 bits of collision resistance and 256 bits of pre-image resistance. That is also why MD5 (128-bit, so 64-bit collision resistance) and SHA-1 (160-bit, 80-bit) fell to collisions long before anything else about them broke.

8.6Key exchange and forward secrecy

Diffie–Hellman lets two parties who have never met agree on a shared secret over a channel an eavesdropper is watching, without ever transmitting the secret. The property that matters operationally is what the ephemeral variants add.

Why ephemeral keys change the threat model 
WITHOUT FORWARD SECRECY (RSA key transport, as in old TLS)
  The client picks a secret, encrypts it with the server's
  public key, and sends it. The session key is recoverable
  from the transcript by anyone holding the server's private
  key.

  CONSEQUENCE: an adversary who records traffic today and
  obtains the private key in five years — by compromise,
  by court order, by the key simply leaking — can decrypt
  ALL of it retroactively. "Harvest now, decrypt later."

WITH FORWARD SECRECY (ECDHE)
  Both sides generate a throwaway key pair per session, agree
  a secret, and discard the private halves. The long-term key
  is used only to SIGN the exchange, proving identity — it
  never encrypts the session key.

  CONSEQUENCE: compromising the server's long-term key lets
  an attacker impersonate the server FROM THAT POINT ON, but
  it does not decrypt a single past session. Each session's
  secret died with the session.

THIS IS WHY TLS 1.3 REMOVED NON-EPHEMERAL EXCHANGE ENTIRELY.
It is not optional any more, and that was the right call.

8.7PKI — binding keys to names

Everything above assumes you have the right public key. That assumption is the entire problem: a key with no name attached proves only that whoever holds the private half is consistent, not who they are. Public key infrastructure is the answer, and a certificate is simply a public key plus a name, signed by someone you already trust.

Certificate chain validation

Every check a client runs, in order. Break one and see what happens.

The parts of the system, and what each is for
ComponentRole
Root CAA self-signed certificate distributed with your operating system or browser. Kept offline; its private key signs only intermediates
Intermediate CASigned by the root, and what actually issues leaf certificates. Exists so that a compromise can be contained by revoking one intermediate rather than a root that lives in a billion trust stores
Leaf certificateYour server's. Contains the public key, the names it is valid for (Subject Alternative Names — the Common Name is deprecated and ignored), validity dates, and permitted uses
CRL / OCSPRevocation. Both are weak in practice: CRLs grow large and are cached, OCSP adds a request that leaks browsing and is usually soft-failed. OCSP stapling is better — the server presents a recent signed status itself
Certificate TransparencyPublic append-only logs of every issued certificate. This is what actually catches misissuance, because you can monitor for certificates issued for your domains that you did not request
PinningTrusting only a specific key or CA for a given service. Powerful and dangerous — a pin you cannot rotate is an outage waiting for the renewal date
The weakest link is the whole system

Your browser trusts well over a hundred root certificate authorities, and any one of them can issue a valid certificate for any domain. There is no technical restriction preventing a CA in one jurisdiction from issuing a certificate for a bank in another; the constraints are contractual, auditable and occasionally violated. This is the structural weakness of PKI, and it is why Certificate Transparency exists — it does not prevent misissuance, but it makes it publicly visible, which turns an undetectable attack into one with a timestamp and an audit trail. If you own domains, monitoring CT logs for unexpected issuance costs almost nothing and is one of the few controls that detects an attack you have no other way of seeing.

8.8Where cryptography actually fails

Almost never in the mathematics. The failures are in everything around it:

In rough order of frequency

Why is RSA-2048 roughly equivalent to AES-112 rather than being far stronger?

Because the two are attacked by completely different methods and only one of them is brute force. Breaking AES means trying keys: with a 128-bit key there are 2128 of them and no better approach is known, so the work is genuinely exponential in the key length. Breaking RSA means factoring the modulus, and factoring has algorithms — the general number field sieve being the best known — that are dramatically faster than trying every possibility, running in sub-exponential time. So the key has to be much larger to reach the same difficulty, and the relationship is not linear: RSA-2048 gives about 112 bits of security, RSA-3072 about 128, and reaching 256-bit-equivalent strength requires roughly 15,360 bits, which is why nobody does it. Elliptic curves sit in between conceptually but behave like the symmetric case: the discrete logarithm problem on a well-chosen curve has no known sub-exponential attack, so a 256-bit curve gives about 128 bits of security and key sizes stay small. Three practical consequences. Comparing bit counts across families is meaningless, and doing it leads people to specify enormous RSA keys that are slower and weaker than a small curve. RSA's cost grows badly with security level, which is why new systems use ECDSA or Ed25519. And when someone says "we use 256-bit encryption", the number alone tells you nothing until you know which family it refers to.

An expired certificate and a revoked one both fail validation. Why are they very different findings?

Because one is an operational lapse and the other means a key is known to be compromised. Expiry is a deadline nobody met — the certificate was legitimate, the key is presumably still exclusively yours, and the failure is that a renewal did not happen. It is an availability incident, usually embarrassing, occasionally very expensive when it takes down a payment path, and the fix is automation: short-lived certificates renewed by a process rather than a calendar reminder, with alerting well before expiry. Revocation is a security incident. A certificate is revoked because the private key leaked, the CA misissued it, or the domain changed hands — meaning someone other than you may be able to impersonate that name, and the certificate is being explicitly disowned. The uncomfortable part is that revocation barely works in practice. CRLs are large and cached so the news arrives late; OCSP requires an extra request that leaks which sites a user visits and is therefore usually soft-failed, meaning that if the responder is unreachable the client proceeds anyway — which an attacker positioned in the middle can simply arrange by blocking it. So a revoked certificate may well continue to be accepted by real clients for its remaining validity period. The practical responses are OCSP stapling with the must-staple flag, short certificate lifetimes so the window is small by construction, and monitoring Certificate Transparency logs so you learn about misissuance rather than relying on revocation to fix it afterwards.

What does forward secrecy protect against that ordinary TLS does not?

Retroactive decryption of traffic that was recorded before the key was compromised. Without it — as in TLS's old RSA key transport mode — the client generates the session secret, encrypts it with the server's public key and sends it across the wire. Anyone recording that exchange has everything they need except the server's private key, so the moment they obtain that key they can decrypt every session they ever captured. That key might be obtained years later by breaching the server, by a legal order, by an insider, by a backup being lost, or by the algorithm weakening over time, and none of those events help the victim because the traffic was captured long ago. This is the "harvest now, decrypt later" model, and it is a real strategy rather than a theoretical one. Ephemeral Diffie–Hellman removes it: both sides generate a throwaway key pair for the session, derive a shared secret from the exchange, and destroy the private halves when the session ends. The long-term key is used only to sign the exchange, proving who you are talking to, and is never used to protect the session secret. So compromising it lets an attacker impersonate the server going forward — which matters and is worth preventing — but recovers nothing from any past session, because the material needed to derive those keys no longer exists anywhere. TLS 1.3 removed non-ephemeral key exchange entirely for this reason. It is also the property that matters most for the quantum question: an adversary recording traffic now cannot decrypt it later with a quantum computer if the session keys were ephemeral and the exchange itself is post-quantum secure, which is why hybrid key exchange is being deployed ahead of any working quantum computer existing.

Recap

  1. Four primitives, four guarantees. Encryption is not integrity, a hash is not a MAC, and a signature is not confidentiality.
  2. Use an AEAD mode — AES-GCM or ChaCha20-Poly1305 — and never reuse a nonce with the same key.
  3. Asymmetric cryptography is used on keys, not data, because it is orders of magnitude slower.
  4. Encrypt with the recipient's public key; sign with your private key. Confusing the two is the common conceptual error.
  5. Bit counts are not comparable across families. RSA-2048 ≈ ECC-256 ≈ AES-112 to 128.
  6. Collision resistance is half the hash length, which is why MD5 and SHA-1 fell there first.
  7. Forward secrecy makes recorded traffic worthless later, which is why TLS 1.3 requires it.
  8. A certificate is a public key plus a name, signed by someone you trust — and any of a hundred CAs can sign for any name.
  9. Revocation barely works. Prefer short lifetimes, stapling, and CT log monitoring.
  10. Cryptography fails at key management, randomness and validation, almost never at the mathematics.
