Hosts and operating systems

Intrusions end on a host. Whatever the entry route, the attacker eventually needs code running somewhere, privileges it did not start with, and a way to still be there tomorrow. This chapter is the three mechanisms that decide all of that — process, identity and permission — in the two operating systems you will meet, and where to look when you suspect a machine.

3.1The three questions about any host

Whether you are hardening a machine, triaging an alert or reading a forensic image, the same three questions come first and everything else is detail.

The triage triad 
1  WHAT IS RUNNING?
   Every process, its parent, its command line, the binary
   behind it and who started it. Most detections are really
   "an unexpected process, or an expected one with an
   unexpected parent or argument".

2  WHAT IS IT RUNNING AS?
   The identity attached to the process, and what that
   identity may do. Privilege is a property of the token or
   the credential, not of the person at the keyboard.

3  WHAT WILL BE RUNNING AFTER A REBOOT?
   Everything that starts automatically. This is where
   persistence lives, and it is a finite, enumerable list —
   which is why it is one of the most productive things to
   baseline.
Parent–child relationships carry most of the signal

powershell.exe running is unremarkable. winword.exe spawning powershell.exe is not, because Word has no legitimate reason to start a shell — that is a macro. Similarly w3wp.exe (IIS) spawning cmd.exe means a web shell, and sshd spawning something other than a login shell is worth reading. Detection engineering leans heavily on this because the process tree encodes intent in a way the binary name alone does not, and it survives renaming — an attacker can call their payload svchost.exe, but they cannot easily make it a child of the right parent at the right time from the right path.

3.2Identity and privilege

Both operating systems implement the same abstraction with different vocabulary: a process carries an identity, that identity has rights, and every access is checked against them. The differences are in how the identity is represented and how it can be changed.

What this means

Three mechanisms escalate privilege on Linux, and all three are worth being able to enumerate:

setuid binaries
A file with the setuid bit runs as its owner rather than its caller. That is how passwd can write to /etc/shadow when you cannot. It is also the classic escalation path: any setuid-root binary that can be made to read, write or execute something arbitrary hands you root. find / -perm -4000 -type f 2>/dev/null enumerates them, and every entry should have a justification.
Capabilities
The finer-grained replacement: instead of all-or-nothing root, a binary gets a specific power — cap_net_raw to open raw sockets, cap_net_bind_service to bind below 1024. Better than setuid, and several capabilities are effectively root anyway (cap_sys_admin, cap_dac_override, cap_setuid), so granting them is not the mitigation it appears to be. getcap -r / 2>/dev/null.
sudo
Rule-based escalation, and the rules are where the mistakes are. NOPASSWD on a binary that can execute arbitrary code — vim, less, find, awk, tar, anything with a shell escape — is equivalent to full root. This is what the GTFOBins project catalogues, and sudo -l is the first command an attacker runs after landing.

Windows privileges

Windows attaches an access token to each process, containing the user's SID, group SIDs, and a list of privileges — named rights that are separate from object permissions. Several are effectively administrative on their own:

Token privileges that are escalation paths
PrivilegeGrants
SeDebugPrivilegeOpen any process, including LSASS — which means reading credentials out of memory
SeImpersonatePrivilegeAct as another token. Held by service accounts, and the basis of the "potato" escalation family
SeBackupPrivilegeRead any file regardless of its ACL — including the SAM and the NTDS database
SeRestorePrivilegeWrite any file regardless of its ACL
SeTakeOwnershipPrivilegeTake ownership of any object, then grant yourself access to it
SeLoadDriverPrivilegeLoad kernel code, which is the end of the security model on that host

Two Windows-specific points that surprise people. UAC is not a security boundary — Microsoft says so explicitly. It is a convenience prompt to make administrative actions deliberate, and there are many documented bypasses; an account in the Administrators group should be treated as administrative whether or not it is currently elevated. And SYSTEM outranks Administrator on the local machine, which is why a service running as SYSTEM with a writable binary path is a complete local compromise regardless of who is logged in.

3.3Where attackers persist

Code execution is temporary; persistence is what survives a reboot, and it is a finite enumerable list. That finiteness is the defender's advantage — you cannot enumerate every possible exploit, but you can enumerate every autostart location and diff it against a baseline.

3.6Baselines

Almost every host-level detection reduces to "this differs from what it should be", and that requires knowing what it should be. Six things are worth baselining because each is small, stable and enumerable:

What to record, and what a change in it means
BaselineA deviation suggests
Listening ports and the process behind eachA new service — a backdoor, a web shell, a proxy, or an unapproved install
Autostart entries across every mechanismPersistence. The highest-yield single check
Local accounts and group membershipAn added account, or a user added to Administrators — a classic and easily missed step
Installed software and running servicesTooling brought in by an attacker, or shadow IT

Hashes of system binaries and scheduled scriptsReplacement or trojanising of a legitimate file
Living off the land

The reason "unknown binary" detection is not enough. Modern intrusions deliberately use tools that are already present and legitimately signed — powershell, certutil, bitsadmin, rundll32, mshta, regsvr32, wmic on Windows; curl, bash, python, tar, find on Linux. Nothing is dropped, nothing is unsigned, and file-hash detection sees nothing. The projects that catalogue this are LOLBAS for Windows and GTFOBins for Unix, and they are as useful to a defender as to an attacker — they are the list of what to watch. Detection has to move to behaviour: certutil downloading a file, rundll32 with a network argument, a signed binary with an unusual parent. That is why the process tree in §3.1 carries so much weight.

Why is a setuid-root copy of a text editor equivalent to giving away root?

Because almost every substantial interactive tool can execute a command, and a setuid binary runs with the file owner's privileges rather than the caller's. If vim is setuid root, any user who runs it is running code as root — and :!sh from inside it produces a root shell. The same applies to less and more (!sh), find (-exec), awk (system()), tar (--checkpoint-action), git (via a pager or a hook), and a long list catalogued by GTFOBins. The same reasoning applies to sudo rules: NOPASSWD: /usr/bin/find is not a narrow grant, it is unrestricted root with extra typing. The general principle is that a privilege boundary is only as narrow as the least constrained thing on the privileged side of it, so the question to ask about any setuid binary or sudo rule is not "is this program trustworthy" but "can this program be made to run something else". Practically: enumerate setuid binaries and sudo rules as part of your baseline, prefer capabilities to setuid where they genuinely narrow the grant, and check every sudo rule against GTFOBins before approving it.

A process named svchost.exe is running from C:\Users\amy\AppData\Local\Temp. What is wrong, and what else would you check?

The path. Legitimate svchost.exe lives in C:\Windows\System32 and nowhere else — a copy in a user-writable temporary directory is masquerading, which is a well-known technique precisely because the name is familiar enough that people skim past it. Four things to check next, in order. The parent process: real svchost is started by services.exe; anything else, particularly a browser, an Office application or a script host, tells you the delivery route. The command line: genuine svchost always runs with a -k group argument, so its absence is conclusive. The signature and hash: the real binary is Microsoft-signed, and the hash can be checked against a known-good source. The network connections: what is it talking to, and does that destination appear in your DNS or proxy logs from other hosts too, which would tell you the scope. Beyond that host, the important question is how it got there — check for a scheduled task or Run key pointing at that path, look at the parent's own history, and search the estate for the same filename and hash, because one machine is rarely the whole picture. Note the general lesson: identity of a binary is path plus signature plus parent, never the filename, and any detection keyed on name alone is trivially defeated.

Why should you not trust the tools on a host you believe is compromised?

Because they run above the layer an attacker may control, and their job is to ask the operating system what is happening. A kernel-level rootkit can hook the calls those tools make and filter the answers — hiding a process from ps and Task Manager, hiding a port from netstat, hiding a file from directory listings, and hiding itself from anything that asks. Even without kernel access, an attacker with administrative rights can replace the tools themselves, so ps is a wrapper that omits one process. This is why the classic advice is to use known-good static binaries from removable media rather than the ones on the host, and, more usefully, to corroborate from outside: a listening port the host denies having will still appear in network flow logs; a connection the host does not show will still appear at the firewall; a process the host hides will still appear in memory. That external corroboration is the practical version of the principle, because carrying a trusted toolkit is rare and reading network telemetry is routine. It also drives the forensic order in Chapter 18: capture memory first, because a memory image analysed on a different machine is not subject to the compromised kernel's lies, then image the disk from outside the running operating system.

Recap

  1. Three questions: what is running, what is it running as, and what will run after a reboot.
  2. The process tree carries the signal. Word spawning a shell is the detection; the binary name is not.
  3. Both operating systems implement identity, rights and a check — the vocabulary differs, the model does not.
  4. setuid, capabilities and sudo rules are the three Linux escalation paths, and all three are enumerable.
  5. A privilege boundary is only as narrow as the least constrained thing behind it — which is what GTFOBins catalogues.
  6. UAC is not a security boundary, and SYSTEM outranks Administrator locally.
  7. Several Windows token privileges are administrative on their own, starting with SeDebug and SeImpersonate.
  8. Persistence locations are a finite list. Enumerate and diff them — the highest-yield host check there is.
  9. Living off the land defeats file-based detection. Watch behaviour and parentage instead.
  10. Do not trust a suspect host's own tools. Corroborate from the network, and capture memory before anything else.
