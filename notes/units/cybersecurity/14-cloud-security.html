Cloud security

The cloud does not change what attackers want, and it changes almost everything about how they get it. The network perimeter mostly disappears, identity replaces it, infrastructure becomes an API call, and the dominant failure mode shifts from unpatched software to a permission somebody set too broadly and nobody reviewed.

~30 min read Shared responsibility · IAM · misconfiguration · IaC 2 interactive panels Prerequisite: chapters 10, 11

14.1Shared responsibility

The provider secures the platform; you secure what you put on it. The line moves depending on the service model, and misunderstanding where it sits for a given service is a recurring cause of exposure.

Who owns what

The same stack across four service models. Note how much moves — and how little of the important part ever does.

The part that is always yours

Across every model, four things never transfer: your data, who may access it, how your application is configured, and the accounts and credentials in your tenant. Those are also where essentially all cloud breaches happen. The provider genuinely does secure the hypervisor and the physical estate to a standard almost no organisation could match alone, which is why moving to cloud usually improves infrastructure security — and it is why the residual risk concentrates so completely in the configuration and identity layer that remains yours.

14.2Identity is the perimeter

In a data centre, reaching a server requires network access. In a cloud account, everything is an API call to a public endpoint, authenticated by a credential — so the question "who can do what" replaces "what can reach what" as the primary control.

14.4The control plane

The thing with no on-premises equivalent, and the reason cloud incidents move faster. The control plane is the API that creates, modifies and destroys infrastructure — and a credential with control-plane access does not need to touch a single server to be catastrophic.

What control-plane access permits, without touching a workload 
· snapshot a database and copy it to another account
· create a new administrative user or access key
· change a bucket policy to public
· modify a security group to permit inbound from anywhere
· delete every backup, then every resource
· change logging configuration so none of the above is recorded
· deploy compute for cryptomining, at your expense

WHICH IS WHY
  · Control-plane audit logs are the single most important
    telemetry in a cloud environment, and they must be shipped
    OUT of the account they describe — logs an attacker can
    delete are not evidence.
  · Alert on control-plane actions specifically: root account
    use, IAM policy changes, logging changes, key creation,
    security group changes to 0.0.0.0/0, and any use of a
    region you do not operate in.
  · The blast radius of a credential is the account boundary,
    which is the strongest isolation the cloud offers — and
    the argument for many small accounts.
  · Guardrails at the organisation level (service control
    policies and their equivalents) constrain what any
    principal in an account can do, INCLUDING its
    administrators. This is the only control that survives
    the account admin being compromised.

14.5Infrastructure as code

Cloud configuration is defined in files, which is the largest security opportunity the model offers: a misconfiguration becomes a reviewable, testable, version-controlled artefact rather than something someone clicked at 2am.

Two failure modes specific to this model

State files contain secrets. A Terraform state file records the actual values of resources including generated passwords and keys, in plaintext. Storing it in a repository, or in a bucket with loose permissions, hands over the credentials the code was careful not to hardcode. Use a remote backend with encryption, strict access control and locking.

The pipeline is the most privileged principal you have. It can create and destroy anything, which makes it a more valuable target than any individual administrator. It frequently has long-lived credentials, runs untrusted code from pull requests, and is exempted from controls for convenience. Treat it as tier 0: federated short-lived credentials rather than static keys, no secrets exposed to pull-request builds from forks, and separate pipelines with separate permissions for production.

Why is a public storage bucket still one of the most common cloud breaches when defaults are now private?

Because the default only governs the moment of creation, and the exposures come from everything afterwards. A bucket is made public deliberately for a legitimate reason — hosting static assets, sharing a file with a partner, a debugging session — and the change outlives the reason, because nothing expires it and nobody revisits it. Permissions also arrive by several routes that a "private by default" setting does not cover: an overly broad bucket policy, an object-level ACL set by whatever uploaded the file, a wildcard in an IAM policy that grants read to a principal much wider than intended, a presigned URL with a very long expiry, or a snapshot or backup copied somewhere with different permissions. There is also the discovery asymmetry: bucket names are frequently guessable, scanners enumerate them continuously, and researchers and attackers both find them within hours of exposure — so the window between misconfiguration and discovery is short, and the data is often already indexed by the time anyone notices. The controls that work are structural rather than vigilant. Account-level public access blocks mean an individual bucket cannot be made public even if someone tries, which converts the whole class from a detection problem into an impossibility. Preventive policy in the deployment pipeline refuses the configuration before it exists. Posture management catches anything created outside the pipeline. And the underlying data control matters more than any of them: encryption with a key the bucket policy does not grant, and not storing data you do not need, both mean an exposure is survivable.

Why ship cloud audit logs to a different account?

Because logs stored in the account being investigated are under the control of whoever compromised it, and an attacker with control-plane access can delete them, stop the trail entirely, or alter the retention configuration — usually as one of their first actions, since it costs them nothing and removes the record of everything after it. That turns your primary evidence into something you cannot rely on, and it is worse than having no logs at all, because you will reason from an incomplete record without knowing it is incomplete. A separate logging account with write-only permissions from the source accounts, object lock or equivalent immutability, and a distinct set of administrators means the attacker would need to compromise a second, much smaller and more tightly controlled boundary. Three related points. The same argument applies to backups, and for the same reason — a ransomware operator's first objective is the backup system, so backups that the production account can delete are not backups. It applies to alerting: if the alerting pipeline runs in the compromised account, disabling it is one API call, whereas a separate account raises an alarm that survives. And it applies to the organisation layer: service control policies that forbid disabling logging apply even to account administrators, which is the only control that holds when the account admin is the attacker. The general principle is that a control an attacker can turn off is not a control at the moment you need it, and the cloud makes this unusually stark because turning things off is an API call rather than a physical act.

Your organisation has one cloud account with strict IAM. Is that safer than many accounts with looser IAM?

Usually not, because account boundaries are a stronger isolation mechanism than policy inside an account, and they fail differently. IAM policy is a large, interconnected system where the effective permissions of a principal are the result of identity policies, resource policies, permission boundaries, session policies and group memberships interacting — so "strict" is genuinely hard to verify, and privilege escalation paths within an account are common enough that tools exist specifically to find them. A single mistake, or a principal with a permission like the ability to modify policies, can expand to everything. An account boundary does not have those subtleties: a principal in one account has no access to another unless a trust relationship explicitly grants it, and that relationship is a small, visible, reviewable object rather than an emergent property of hundreds of statements. So many accounts gives you a blast radius per workload or per environment, and a compromise stays inside one. The pattern that actually works combines both: many accounts for isolation, a consistent baseline applied to all of them through automation so that "looser IAM" does not follow from having more accounts, and organisation-level guardrails that constrain every account including its administrators. Two caveats worth stating. Many accounts is only safer if you can manage them consistently — a sprawl of accounts nobody inventories reintroduces the forgotten-resource problem from chapter 13, and unowned accounts are how shadow infrastructure survives. And centralised logging, identity federation and network connectivity all need deliberate design once you have more than a handful, which is real work rather than a free win.

Recap

  1. Your data, your access control, your configuration and your credentials never transfer, whatever the service model.
  2. Identity replaces the network perimeter, because everything is an authenticated API call.
  3. Wildcards and managed policies are how over-permission starts. Compare granted against used, then narrow.
  4. A policy that can edit policies is administrative. IAM permissions are themselves an escalation path.
  5. Service principals outnumber humans, have no MFA, and are rarely reviewed.
  6. Enforce IMDSv2 so an SSRF cannot retrieve instance credentials.
  7. Control-plane access is catastrophic without touching a workload — snapshots, keys, policies, backups, logging.
  8. Ship audit logs out of the account they describe. Logs an attacker can delete are not evidence.
  9. Account boundaries isolate better than policy inside an account, and organisation guardrails constrain even account admins.
  10. Terraform state holds secrets, and the pipeline is your most privileged principal. Treat both as tier 0.
