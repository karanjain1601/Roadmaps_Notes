Hardening

Everything in Part 2 needed something to attack. Hardening is the discipline of having less of it — removing what is not used, constraining what is, and making the secure configuration the one that arrives by default rather than the one someone remembers to apply.

~30 min read Attack surface · baselines · allow-listing · drift 2 interactive panels Prerequisite: chapters 3, 7

11.1Attack surface

The set of points where an untrusted input can reach your system. It is the only security property you can reduce to zero for a given component, by removing the component — which makes it the cheapest control available and the one most often skipped, because deleting things feels less like progress than adding them.

Four surfaces, and what reduces each
SurfaceConsists ofReduce by
NetworkListening ports, exposed services, reachable hostsClose ports, bind to loopback, segment, put management behind a bastion
SoftwareInstalled packages, enabled features, loaded modules, dependenciesMinimal images, uninstall rather than disable, remove unused dependencies
IdentityAccounts, groups, permissions, tokens, keysDeprovisioning, access reviews, just-in-time, short-lived credentials
DataWhat you hold, where, for how longRetention limits and not collecting it. Data you do not have cannot be stolen

What removing each thing buys

A typical server build. Toggle each item and see what it removes from the surface.

Disabled is not removed

A disabled service is one configuration change, one misapplied update or one dependency away from running again, and it still contains the vulnerable code — so it still appears in your scanner, still needs patching, and still counts against you in an audit. An uninstalled service is none of those things. The same distinction applies throughout: a firewall rule blocking a port is weaker than nothing listening on it, an unused account disabled is weaker than deleted, and a feature flag off is weaker than the code not being shipped. Prefer removal wherever removal is possible, and use disabling only where it is not.

11.2Baselines

Hardening at scale means writing down what "correct" is, applying it everywhere, and detecting when a machine stops matching. The writing-down part is largely solved — you should not invent your own.

Where the baselines come from
SourceNatureNote
CIS BenchmarksConsensus-developed, per platform, with two levelsLevel 1 is broadly safe to apply; Level 2 is stricter and will break things. Freely available
DISA STIGsUS defence configuration standardsStricter and more prescriptive. Useful even outside that context as a reference
Vendor baselinesMicrosoft Security Baselines, cloud provider foundationsBest integration with the platform's own tooling
Your own overlayThe deltas you need on topInevitable and should be small, documented, and each exception justified with an owner
Applying a benchmark wholesale will break production

A CIS Level 2 benchmark applied to a running estate breaks applications, and the reaction is usually to abandon the whole exercise. The sequence that works: apply the baseline to a new build rather than an existing one, run it in audit mode first to see what would change, exempt the small number of controls that genuinely conflict with your applications and record why, then enforce the rest and make new machines inherit it from birth. Retrofitting a hardened configuration onto a live server is difficult; making the next server born hardened is straightforward, and after a rebuild cycle the estate is compliant without anyone touching a running system.

11.4Application allow-listing

The strongest endpoint control and the hardest to run. Instead of blocking known-bad, permit only known-good — which inverts the arms race, because an attacker's novel payload is not on the list and novelty stops being an advantage.

The four ways to identify permitted software, worst to best 
PATH RULES        "anything in C:\Program Files may run"
                  Weakest. Any user-writable directory inside a
                  permitted path defeats it, and there are always
                  more of those than you expect.

HASH RULES        exact file hashes
                  Precise and unmaintainable — every update
                  changes every hash.

PUBLISHER RULES   signed by a trusted certificate
                  The practical choice. Survives updates. Note
                  that "signed by Microsoft" permits every
                  living-off-the-land binary in chapter 3.

MANAGED INSTALLER combination: software deployed by your
                  deployment system is trusted, everything else
                  is not. Handles updates automatically and is
                  what makes the whole thing operable at scale.

THE PART EVERYONE UNDERESTIMATES
  Allow-listing executables is the easy half. Scripts,
  macros, DLLs, LOLBins and interpreted code are the other
  half, and an allow-list that permits powershell.exe while
  blocking unknown .exe files has not achieved much.
  Constrained language mode is the companion control.

HOW TO DEPLOY IT WITHOUT A REVOLT
  1  Audit mode for weeks. Collect what actually runs.
  2  Build rules from that, not from an inventory document.
  3  Enforce on servers first — their software set is stable
     and small. Workstations last.
  4  Have a same-day exception route. Without one, people
     will find a way around the control, and the workaround
     will be worse than the gap.

11.5Configuration drift

A hardened estate does not stay hardened. Engineers make changes to fix incidents, software updates reset settings, new machines are built from stale images, and exceptions granted for a week persist for years. Without something pulling configuration back, compliance decays.

Drift over a year

Machines diverge at some rate; enforcement pulls them back. Whether the fleet converges depends on which is faster.

Immutability solves drift by removing the opportunity

If machines are never modified after creation — changes are made by building a new image and replacing the instance — drift cannot accumulate, because the only configuration that exists is the one in the image definition. The fleet's average age becomes its maximum divergence, and shortening the replacement cycle shortens that automatically. This is why containerised and cloud-native estates are frequently better hardened than long-lived servers despite nobody working harder at it: the architecture does the enforcing. Where you cannot be immutable, the next best thing is continuous enforcement rather than periodic auditing — a configuration management tool that reapplies the desired state on a schedule turns drift into a transient condition instead of a permanent one.

11.6Golden images and supply chain

  Every change goes into the image definition and produces a

  Vulnerabilities in a base layer are inherited by every

  once rather than everywhere.

Why is uninstalling a service better than disabling it, given neither is running?

Because disabling changes the runtime state while uninstalling changes what exists, and only the second one is durable. A disabled service still has its binaries and libraries on disk, so it still contains whatever vulnerabilities they contain, still appears in vulnerability scans as an installed package requiring patching, and still counts as a finding in a compliance audit — you have taken on all of the maintenance burden and none of the function. It is also one step from running again: a configuration management run that resets state, a software update that re-enables it as part of installation, a dependency that starts it, an administrator troubleshooting something unrelated, or an attacker with sufficient privilege simply turning it back on. Uninstalling removes all of that, and it removes it in a way that is visible — the package is absent from the inventory rather than present-but-off, which is a much easier property to verify across a fleet than a runtime setting. There are cases where disabling is the only option, typically where a component is an inseparable part of the operating system or where an application depends on the package being present but not active, and in those cases disabling plus a firewall rule plus monitoring for it starting is the right combination. But the default should be removal, and the general principle applies well beyond services: delete unused accounts rather than disabling them, remove unused dependencies rather than excluding them from the build, and do not collect data you do not need rather than protecting it carefully.

Application allow-listing is the strongest endpoint control. Why do so few organisations run it?

Because the security properties are excellent and the operational demands are severe, and most attempts fail on the second rather than the first. Three specific difficulties. Discovering what legitimately runs is hard: the inventory in the asset system is not the list of what executes, and the real list includes the finance team's twenty-year-old macro-enabled spreadsheet, a consultant's utility, an installer that unpacks to a temporary directory, and self-updating software that changes its own binaries. You only find these by running in audit mode for weeks and reading what comes back. Updates fight the rules: hash rules break on every patch, path rules are defeated by any user-writable directory inside a permitted path, and publisher rules are the practical answer but require the software to be signed, which not all of it is. The exception process is the real product: if a developer needs a new tool and the path to permission takes three days, they will find a route around the control, and that route will be worse than the gap you were closing. What makes it work is a managed installer model, where anything deployed by your software distribution system is trusted automatically, which makes updates a non-event; starting on servers, whose software set is small and stable, rather than on workstations; and a same-day exception route with a named owner. It is also worth noting where the strength actually comes from and where it does not: allow-listing executables while permitting the scripting hosts from chapter 3 leaves the living-off-the-land techniques untouched, so constrained language mode and script controls are companions rather than extras.

Your fleet is 95% compliant with the baseline. Is that good?

It depends on two things the number hides, and on its own it is close to meaningless. The first is which 5%. If the non-compliant machines are randomly distributed laptops missing a low-severity setting, that is a reasonable steady state. If they are the four domain controllers, the jump host and the backup server — which is a very common pattern, because the most important machines are the ones nobody dares change and the ones with the most exceptions — then the 95% figure is actively misleading and the real posture is poor. Compliance percentages should always be weighted by asset criticality, or reported per tier, because an unweighted average lets the long tail of unimportant machines hide the important ones. The second is which controls. A baseline contains hundreds of settings of wildly varying value, and 95% compliance across all of them says nothing about whether the ten that break the escalation path from chapter 10 are among the misses. A machine that meets 300 of 315 CIS settings but has local administrator rights for its user, a shared local admin password and LLMNR enabled is compliant by the metric and fully exposed by the path. So the useful reporting is per-control rather than per-machine: for each of the handful of controls that break a known attack path, what proportion of the estate has it, and specifically which machines do not. Finally, the direction matters more than the level — 95% and improving with a shrinking exception list is a healthy programme; 95% and static, where the remaining 5% are permanent exceptions nobody revisits, is a programme that has stopped.

Recap

  1. Attack surface is the one property you can take to zero by removing the component.
  2. Disabled is not removed. A disabled service still carries its vulnerabilities and its maintenance burden.
  3. Do not invent baselines. Start from CIS, STIGs or vendor guidance and keep your overlay small.
  4. Apply baselines to new builds, not running servers, and use audit mode before enforcement.
  5. The high-return controls are known: local admin, LAPS, LLMNR, macros, exposed RDP, egress.
  6. Allow-listing inverts the arms race and is the hardest control to operate. Managed installer plus a same-day exception route.
  7. Allow-listing executables while permitting script hosts leaves the living-off-the-land techniques untouched.
  8. Drift is continuous, so enforcement must be too. Quarterly audits lose to monthly drift.
  9. Immutability removes the opportunity to drift, and fleet age becomes maximum divergence.
  10. Rebuild images on a schedule — an old image is an unpatched image even if your code has not changed.
