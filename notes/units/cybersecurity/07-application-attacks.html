Application attacks

Applications are where the data is, and unlike the network they are written fresh every time — so the same handful of mistakes recur indefinitely. Almost all of them reduce to one confusion: data supplied by a user being treated as instructions by something downstream.

~32 min read Injection · XSS · CSRF · SSRF 2 interactive panels Prerequisite: chapter 4

7.1The one mistake

Every injection vulnerability has the same shape, and seeing it once makes the whole family obvious:

The general form 
Your code builds a STRING that some interpreter will parse.
Part of that string came from an attacker.
The interpreter cannot tell which part.

  interpreter        the injection
  ─────────────      ─────────────────────────
  SQL engine         SQL injection
  the shell          command injection
  the browser        cross-site scripting
  an LDAP server     LDAP injection
  an XML parser      XXE
  a template engine  server-side template injection
  a log processor    log injection, and worse downstream
  an ORM's filter    NoSQL injection

THE FIX IS ALWAYS THE SAME IDEA
  Do not build the string. Send the instruction and the data
  through separate channels, so the interpreter is told which
  is which before it ever sees the data.

WHAT IS NOT THE FIX
  · Escaping by hand — you will miss a context. See §7.3.
  · A blocklist of dangerous words — trivially evaded, and it
    breaks legitimate input. Nobody named O'Brien can register.
  · A WAF — useful defence in depth, defeated by encoding, and
    it is not a substitute for fixing the code.

7.2SQL injection, and why parameterisation works

What the database actually parses

The same input through concatenation and through a bound parameter. Watch where the boundary between instruction and data falls.

The code

What the SQL parser sees

The point the panel makes concretely: with a bound parameter, the query is parsed and planned before the data arrives. The database has already decided the statement's structure, and the parameter is inserted into that structure as a value — there is no path by which its content can become syntax. That is a categorical guarantee rather than a filtering effort, which is why it is the only acceptable answer.

Where parameterisation does not reach

You can bind values, not identifiers or structure. ORDER BY ? and SELECT * FROM ? are not valid — so dynamic table names, column names and sort directions cannot be parameterised. This is where injection survives in otherwise careful codebases, typically in an admin filter or a sortable table. The only safe approach is an allow-list: map the user's input to a known-good identifier through a lookup you control, and reject anything not in it. Never interpolate the value even after "cleaning" it. The same applies to LIMIT in some drivers, and to any place a query is assembled conditionally.

7.3Cross-site scripting

The browser is the interpreter, and the injected instruction is script that runs with the privileges of your site — able to read the DOM, make authenticated requests, and read any token not held in an HttpOnly cookie.

Three kinds, and why the third is different
TypePathNote
StoredAttacker input is saved, then served to other usersThe worst. One injection, every visitor affected, no interaction needed
ReflectedInput in a request is echoed into the responseNeeds the victim to follow a crafted link, so it is usually paired with phishing
DOM-basedClient-side code takes untrusted input and writes it into the pageThe payload may never reach the server, so server-side controls and logs see nothing

Encoding depends on where the value lands

One escaping function is not enough — the same string is safe in one context and dangerous in another.

The practical conclusion: do not escape by hand. Use a template engine that encodes automatically and knows the context, keep untrusted data out of places no encoding makes safe — inside a <script> block, in an event handler attribute, as a URL scheme — and add a Content Security Policy as the layer that catches what you missed. In React and similar frameworks the equivalent rule is: never use dangerouslySetInnerHTML with untrusted input, and sanitise with a maintained library if you must render user HTML.

7.4CSRF and SSRF

Two attacks with similar names and nothing else in common. Both exploit a system making a request that something else chose.

Which direction the forged request goes
CSRF — cross-site request forgerySSRF — server-side request forgery
Who makes the requestThe victim's browserYour server
Abused trustYour site trusts the browser's cookieInternal systems trust your server
Looks likeA hidden form on a malicious page submitting to your bankAn "import from URL" feature fetching http://169.254.169.254/
DamageActions performed as the victimReaching the internal network, and cloud credentials
DefenceSameSite cookies, anti-CSRF tokens, re-authentication for sensitive actionsAllow-list destinations, block link-local and private ranges, resolve then validate, IMDSv2
SSRF is the one that turned into breaches

Any feature that fetches a URL the user supplies — a webhook tester, an avatar importer, a PDF renderer following an image, a document converter, a health-check endpoint — is a candidate. Reaching 169.254.169.254 retrieves cloud instance credentials; reaching localhost hits admin interfaces bound to the loopback that were considered safe because they were "not exposed". Blocklisting the address is insufficient, because of DNS rebinding (the name resolves to a safe address when you check and to the target when you connect), redirects (fetch a benign URL that 302s to the target), and alternative encodings of the same address. The defences that hold are an allow-list of permitted destinations rather than a blocklist, resolving the hostname and validating the resolved address immediately before connecting while refusing to follow redirects, making the fetch from an egress-restricted network segment, and enabling IMDSv2 so the metadata service requires a token that a simple GET cannot obtain.

7.6What actually reduces this

The uncomfortable observation about application security is that the same categories have topped the list for two decades, which tells you awareness is not the binding constraint. What changes outcomes is removing the opportunity to make the mistake:

In order of effect 
1  SAFE DEFAULTS IN THE FRAMEWORK
   An ORM that parameterises, a template engine that encodes,
   a cookie helper that sets SameSite and HttpOnly. This is
   why modern stacks have less SQL injection — not because
   developers learned, but because the easy path became safe.

2  MAKE THE UNSAFE PATH VISIBLE
   Lint rules and static analysis that flag raw query
   construction, dangerouslySetInnerHTML, disabled TLS
   verification. Fail the build, not the review.

3  TESTS FOR THE ACCESS-CONTROL CASE
   For every endpoint taking an id, a test where user A
   requests user B's object and expects 404. This is the
   only reliable defence against the most common flaw,
   because it is the one nobody remembers to check manually.

4  DEPENDENCY INVENTORY AND A FAST PATCH ROUTE
   Most reported vulnerabilities in most applications are
   in dependencies, not in your code.

5  THREAT MODEL THE FEATURES THAT MOVE MONEY OR DATA
   Business logic flaws are invisible to every tool.

6  A WAF, LAST
   Real value as defence in depth and for virtual patching
   while a fix ships. Not a substitute for any of the above,
   and reliably bypassed by anyone paying attention.
Why is a parameterised query safe when escaping the same input is not?

Because they act at different points in the process. Escaping tries to neutralise dangerous characters in a string that will still be parsed as a whole, so its correctness depends on anticipating every way the parser can be steered — and that varies by database, by character set, by whether the value lands inside quotes or not, and by context. Multi-byte character set handling has produced escaping bypasses; a numeric field concatenated without quotes needs no quote character to be injected at all; and a developer who escapes for HTML instead of SQL, or applies the wrong library's function, produces something that looks defended and is not. Parameterisation removes the question. The driver sends the statement text to the database first, the database parses and plans it, and only then are the parameter values transmitted and bound into the already-fixed plan as values. There is no stage at which the parameter's content is parsed as syntax, so no content can change the statement's meaning — x' OR '1'='1 becomes a search for a product literally named that, which returns nothing. It is a structural guarantee rather than a filtering effort, which is why it holds against inputs nobody anticipated. Two caveats. It only covers values, so identifiers and structure need an allow-list instead. And some libraries offer an interpolating function that looks parameterised but builds a string client-side — check what your driver actually does, because the syntax can be nearly identical.

You HTML-encode all output. Why might you still have XSS?

Because HTML entity encoding is correct for one context and wrong for several others, and a single global escape function guarantees you will apply it in the wrong place. Consider the value javascript:alert(1) placed in <a href="…">: entity encoding changes nothing about it, since there are no characters to encode, and the link executes script when clicked — the URL context needs scheme validation, not entity encoding. Consider a value placed inside a <script> block as a JavaScript string: entity encoding does not neutralise a quote in that context because the HTML parser has already handed the block's contents to the JavaScript parser, so ';steal();// breaks out. Consider an unquoted attribute — <input value=$x> — where a space is enough to introduce a new attribute such as onerror, and spaces are not entity-encoded. Consider a value used as a CSS property, or as an attribute name rather than a value, or inside a srcdoc. Each needs different treatment, and some contexts are unsafe with any encoding, which is the important realisation: the correct rule is not "escape harder" but "do not put untrusted data there at all". Practically that means using a template engine that tracks context and encodes accordingly, validating URLs by scheme allow-list, passing data into JavaScript through a JSON block or a data attribute rather than string interpolation, and deploying a nonce-based Content Security Policy so that injected inline script does not execute even when an escaping gap exists.

Why is blocking 169.254.169.254 insufficient against SSRF?

Because a blocklist has to be right about every representation and every moment, and the attacker controls both. Four routes around it. Alternative encodings of the same address — decimal, octal, hexadecimal, IPv6-mapped forms, and shorthand notations — all reach the same host while not matching a literal string comparison. Redirects: the attacker supplies a URL on a domain they control that returns a 302 to the metadata address, so your check passes on the original URL and your HTTP client follows the redirect for you. DNS rebinding: the attacker's domain resolves to a harmless address when you validate it and to the metadata address a moment later when the connection is made, exploiting the gap between check and use. And the rest of the internal network: even if the metadata endpoint is blocked, localhost, private ranges and internal hostnames remain reachable, and admin interfaces bound to loopback are frequently unauthenticated precisely because they were considered unreachable. The defences that hold are structural. Prefer an allow-list of permitted destinations over any blocklist. Resolve the hostname yourself, validate the resolved IP against private, loopback and link-local ranges, and connect to that address rather than re-resolving — which closes the rebinding gap. Refuse to follow redirects, or re-validate at each hop. Make the fetch from an egress-restricted segment that cannot reach internal ranges at all, which is the control that survives a bug in the others. And enable IMDSv2, which requires a PUT to obtain a token with a restricted hop limit, so a plain GET from a proxied request cannot retrieve credentials.

Recap

  1. Every injection is the same mistake: a string an interpreter will parse, partly written by an attacker.
  2. Parameterisation is a structural guarantee, not a filtering effort — the plan is fixed before the data arrives.
  3. You cannot bind identifiers or structure. Use an allow-list for table names, columns and sort order.
  4. Encoding depends on context. One global escape function guarantees a gap.
  5. Some contexts are unsafe with any encoding. Keep untrusted data out of script blocks and event handlers.
  6. CSRF abuses the browser's trust in your cookie; SSRF abuses your server's position. Different directions, different fixes.
  7. SSRF blocklists fail to encodings, redirects and DNS rebinding. Allow-list, validate the resolved address, restrict egress.
  8. Broken access control is the most common serious flaw, and the only reliable defence is a test per endpoint.
  9. Business logic flaws are invisible to tooling. Threat model anything that moves money or data.
  10. Safe framework defaults beat awareness. The unsafe path should be the hard one, and the build should fail on it.
