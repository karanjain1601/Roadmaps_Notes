The working principles

The short rules that get quoted in code review. Most are genuinely useful and most are quoted in a form that has drifted from what they meant — DRY in particular is the single most damaging piece of misapplied advice in the field. This chapter is each one precisely, with the case against it, because a principle you cannot argue against is a slogan.

~30 min read DRY · YAGNI · Demeter · composition · inversion 2 interactive panels Prerequisite: chapters 5, 7, 8

9.1DRY

The most misquoted

Don't repeat yourself

"Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." — Hunt and Thomas, and note that the word is knowledge, not code.

The misreading
"Never have two similar-looking pieces of code." That turns DRY into a text-deduplication exercise, and it produces the worst outcome in this unit: two things that happen to look alike get merged, then diverge, then acquire a flag, then three flags, and now two unrelated features are coupled through a shared function neither of them fits.
The correct test
Not "do these look the same?" but "if this business rule changed, would both have to change?" If yes, it is one piece of knowledge duplicated — unify it. If no, the similarity is coincidental and unifying it creates coupling out of nothing.
Where the real duplication usually is
Not in code at all: a validation rule enforced in the front end, the API and the database constraint; a status enum defined in three languages; a business rule in a spreadsheet and in a service. That is the duplication DRY was written about, and it is the kind that silently diverges.
The cost of applying it
Every unification is a new coupling. Two modules that share a function now change together. That is correct when they share knowledge, and pure loss when they do not.
Coincidental similarity — leave it alone
function validateUsername(s: string) {
  return s.length >= 3 && s.length <= 20;
}

function validateProductCode(s: string) {
  return s.length >= 3 && s.length <= 20;
}

// Identical today. But usernames and product codes
// are governed by different people for different
// reasons and will diverge. Merging them into
// validateLength(s, 3, 20) creates a link that has
// to be broken again the first time either changes.
One rule, three copies — unify it
// checkout.ts
if (order.total > 5000) requireApproval();

// reporting.ts
const large = orders.filter(o => o.total > 5000);

// alerts.ts
if (order.total >= 5001) notifyFinance();   // and it drifted

// One business rule — "what counts as a large order" —
// in three places, already inconsistent.

// Money.ts
export const isLargeOrder = (o: Order) =>
  o.total.isGreaterThan(LARGE_ORDER_THRESHOLD);

Is this duplication worth removing?

The question is never how similar the code looks. It is whether one change would have to touch both.

9.2YAGNI

Against speculation

You aren't gonna need it

Do not build a capability until there is a real, present requirement for it.

Why it holds
Speculative features cost four times: building them, understanding them forever after, the bugs they carry, and the constraint they place on the design you actually needed. And the prediction is usually wrong — when the requirement finally arrives it is a different shape, so the flexibility you built points along the wrong axis and has to be removed before the real thing can be added.
What it does not say
It is not an argument against design. Choosing a sensible data model, keeping modules decoupled and writing tests are not speculative features — they are what makes the unanticipated change cheap. YAGNI targets functionality and configurability nobody asked for, not the structural work that keeps options open.
The tension with reversibility
Chapter 1 said to make expensive decisions reversible. YAGNI says not to build for imagined futures. They meet at a clear line: do not build the feature; do keep the seam. Not writing a plugin system is YAGNI; putting the payment call behind an interface so a future provider is a swap is reversibility, and it costs one file.
When to override it
When the thing is genuinely much cheaper now than later. Choosing a UUID over an auto-increment id, adding a version field to an event schema, or making a table's key composite from day one all cost minutes now and weeks later. The test is not "will we need it?" but "what is the ratio between doing it now and retrofitting it?"

9.3Law of Demeter

Limiting reach

Only talk to your immediate friends

A method may call methods on: itself, its parameters, objects it creates, and its own fields. Not on objects returned by any of those.

The symptom
The train wreck: order.getCustomer().getAddress().getCountry().getTaxRate(). That single line couples you to four types and to the shape of the path between them, so a change anywhere along the chain breaks you — and you are not even using three of those objects for anything.
The fix that is not a fix
Adding order.getCustomerAddressCountryTaxRate() satisfies the letter and misses the point — the coupling is still there, now with a worse name. The real fix is to move the behaviour: ask the order for what you want (order.taxRate()) and let it delegate, or better, tell it to do the thing (order.applyTax()) so the chain never surfaces.
When it does not apply
Fluent interfaces and builders (query.where(…).orderBy(…).limit(10)) return this or a value of the same type, so there is no navigation and no hidden coupling. Nor does it apply to plain data structures with no behaviour — reaching into a parsed JSON response is fine, because there is no object to tell. The law is about navigating an object graph to find behaviour, not about counting dots.

What a call chain couples you to

Each step in a navigation is a type you now depend on and a place a change can break you.

9.4Tell, don't ask

Where logic lives

Tell objects what to do rather than asking them for data to decide

If you pull state out of an object to make a decision about that object, the decision belongs inside it.

Why
The rule ends up duplicated at every call site, and every one of them is coupled to the object's internal representation. Moving the decision inside puts it in one place, next to the data it needs, where the object can also enforce it.
Related smell
Feature envy — a method using another object's data more than its own. The refactoring is the same: move the method to the class whose data it keeps reaching for.
The limit
Some decisions genuinely span several objects and belong to none of them — pricing against a promotion, a customer tier and a stock level. That is a domain service, and it is a legitimate answer. The warning sign is when every rule ends up in a service and the objects are left as data holders, which is the anemic model from Chapter 5.
Also
It conflicts with command–query separation less than it appears. account.canWithdraw(amount) is a query and perfectly compatible; the point is that the rule lives on the account rather than at the call site.

9.5Composition over inheritance

Structuring reuse

Prefer holding an object to becoming one

Reuse by delegation rather than by subclassing, unless substitutability genuinely holds.

Why
Inheritance couples a subclass to the parent's internals and call order, not just its interface — the fragile base class problem in Chapter 5. Composition couples you only to a declared interface, and the relationship is visible in the constructor rather than in a hierarchy.
The quantitative argument
With several independent axes of variation, inheritance needs one subclass per combination while composition needs one part per option — a product versus a sum. Three axes of three options is 27 classes against 9.
When inheritance wins
A genuine "is-a" that satisfies Liskov, a shallow hierarchy you fully own, and a base class explicitly designed for extension with documented hooks. A template method with two or three protected steps is a good use; a five-level hierarchy is not.
Cost of composition
More wiring, and delegation boilerplate in languages without a forwarding syntax. A composed object with six collaborators is also its own smell — see Chapter 3 on what six mocks means.

9.6The Hollywood principle

Direction of control

Don't call us, we'll call you

A framework calls your code at the points it defines; your code does not call the framework's main loop. This is inversion of control, and it is the general form of dependency inversion.

Where you have met it
Every event handler, every lifecycle hook, every test framework's beforeEach, every template method's protected step, every middleware pipeline. The framework owns the flow; you supply behaviour into it.
Why it is useful
The framework can change how and when it calls you without you changing anything, and it can add cross-cutting behaviour — logging, transactions, retries — around your code without your code knowing.
The cost, which is real
You lose the ability to read the flow. There is no call site to follow; control arrives from somewhere you cannot see, in an order you did not choose. This is why heavily framework-driven code is hard to onboard into, and why debugging a lifecycle problem means learning the framework rather than reading the program.
Distinguish it from dependency injection
Inversion of control is the general idea; dependency injection is one narrow instance of it (something else supplies your collaborators). A DI container is a specific tool for the latter and is often confused with the former.

9.7Encapsulate what varies

The one that generates the others

Identify what changes and separate it from what stays the same

The most general design heuristic there is — most of the Gang of Four catalogue is this sentence applied to a specific kind of variation.

How to use it
Look at the last several changes to a file. Whatever kept changing is the varying part; put it behind an interface, in its own class, or in configuration, so that the stable part stops being edited. This is observation rather than prediction, which is what makes it compatible with YAGNI.
Relation to the patterns
Strategy encapsulates a varying algorithm; state encapsulates varying behaviour by mode; factory encapsulates varying construction; decorator encapsulates varying additions; adapter encapsulates a varying interface. Recognising the underlying move makes the catalogue in Part 4 much smaller than it looks.
The failure
Encapsulating something that does not vary. Now you have an abstraction with one implementation and an indirection for the reader, which is the over-engineering from Chapter 1. Variation must be observed, not assumed.

9.8The remaining short rules

Worth knowing, mostly self-explanatory, each with a real caveat

9.9When principles conflict

They do, constantly, and knowing the usual resolutions saves a lot of circular review discussion.

The standard collisions
ConflictUsual resolution
DRY vs decouplingDecoupling wins. Duplication is cheap to remove; a wrong shared abstraction is not
YAGNI vs open–closedYAGNI wins until the second variant. Then extract along the axis the second case revealed
SRP vs cohesionCohesion wins. Splitting a coherent concept into fragments is worse than a class with several closely-related methods
Tell-don't-ask vs command–query separationNot really a conflict: a query that encapsulates a rule is fine. What matters is that the rule lives with the data
Inversion of control vs readabilityReadability wins in application code; inversion wins at framework boundaries. Do not invert control inside your own domain for its own sake
Composition vs simplicitySimplicity wins with one axis of variation. Composition wins from two upwards
Any principle vs the actual change historyThe change history wins. It is evidence; the principle is a heuristic about evidence
The meta-rule

Every principle here is a compressed argument about a change that is expected to happen. So the useful form in a review is never the name — it is the change. "Adding a payment provider would mean editing these four files, and we have added two this year" is a finding. "This violates the open–closed principle" is a citation. The first can be agreed or disagreed with on evidence; the second can only be deferred to, which is how principles turn into ritual.

Two classes have an identical 15-line method. Should you extract it?

Only after answering one question: if the underlying rule changed, would both need to change? If yes, it is one piece of knowledge in two places and you should unify it. If no — they are identical by coincidence, governed by different people for different reasons — extracting it creates a dependency between two things that had none, and the first divergence will be handled by adding a boolean parameter, which is how a shared helper becomes a mess. Two further signals worth checking: how many parameters the unified version needs (each one is a difference you are papering over, and past two or three the abstraction is probably wrong), and whether they have already drifted, because drift is evidence that they were never the same rule. If it is genuinely ambiguous, leave the duplication — it stays cheap to remove later, whereas an unwarranted abstraction gets depended upon and becomes expensive to remove.

How do you reconcile YAGNI with "make expensive decisions reversible"?

They target different things, and the line between them is features versus seams. YAGNI is about functionality and configurability: do not build the plugin system, the multi-currency support, the admin override, the "make it configurable" option, for a requirement nobody has. Reversibility is about structure: keep the payment provider behind an interface, keep the domain free of framework imports, choose an id format that will not need migrating. The first costs code, tests, documentation and comprehension forever; the second usually costs one file and no behaviour. The practical test when they seem to collide is the ratio: what does doing this now cost, and what would retrofitting it cost? A one-file interface now versus a week of untangling later is worth it even if the swap never happens, because it also buys testability today. A configuration framework now versus a day of work later is not.

Is builder.setName("x").setAge(30).build() a Law of Demeter violation?

No, and the reason clarifies what the law is actually about. Each call returns the same object (or another builder of the same known type), so you are not navigating a graph and you are not learning anything about the internal structure of anything. Your coupling is to the builder alone — exactly one type — regardless of how many dots appear. The law targets navigation: a.getB().getC().getD() couples you to four types and to the fact that B contains a C which contains a D, so a restructuring anywhere along that path breaks your line even though you only wanted the D. The rule of thumb that avoids miscounting: ask how many distinct types the expression depends on, not how many dots it has. One type, any number of dots, is fine. Four types is a train wreck whether it is written on one line or four.

Recap

  1. DRY is about knowledge, not text. The test is whether one rule change would force both to change — not whether they look alike.
  2. A wrong abstraction is worse than duplication, because duplication is cheap to remove and an abstraction gets depended upon.
  3. YAGNI targets features, not structure. Do not build the capability; do keep the seam.
  4. Demeter is about navigating an object graph, not counting dots. Move the behaviour rather than adding a pass-through getter.
  5. Tell, don't ask puts a rule in one place next to its data — with domain services for logic that genuinely spans objects.
  6. Composition beats inheritance from two axes of variation upwards, and inheritance is fine where substitutability genuinely holds.
  7. Inversion of control buys extensibility and costs readability of the flow. Use it at framework boundaries, not inside your domain.
  8. Encapsulate what varies is the principle that generates most of the patterns — and it requires observed variation, not predicted variation.
  9. When principles conflict, the change history wins. Argue the expected change, not the acronym.
