SOLID

Five principles, four of which are routinely quoted in a form that means something different from what they say — and one of which, applied literally, produces the over-engineering it was meant to prevent. This chapter is each principle in its precise form, the misreading to avoid, and the specific cost of following it.

~32 min read SRP · OCP · LSP · ISP · DIP 2 interactive panels Prerequisite: chapters 4–5

7.1What SOLID is, and what it is not

The five principles were collected by Robert Martin in the early 2000s from ideas dating to the 1970s and 80s. They are not a checklist and not a definition of good code — they are five specific answers to one question: how do you arrange classes so that a change lands in one place? Every one of them is a technique for managing coupling, which is the subject of Chapter 1.

They also share a failure mode. Each one, taken absolutely, produces a system with more indirection than the problem justifies, because each is a purchase and none of them is free. Applied where the corresponding change is not happening, you pay the price and collect nothing — the over-engineering from Chapter 1, wearing a respectable name.

7.2Single responsibility

S

A module should have one reason to change

And "a reason to change" means a person or role who requests the change — not a task the code performs.

The misreading
"A class should do one thing." That is unfalsifiable — any class does one thing at some level of description and many at another — and it leads to classes with a single method and no cohesion, which makes systems harder to navigate.
What it actually asks
Look at who would ask for a change. If the finance team asks for changes to calculatePay and operations asks for changes to reportHours, those must not share a class — because a change requested by one group can break the other's feature through shared private code, and neither group knows the other exists.
The test
List the last ten changes to a file and who requested each. If they come from more than one role, the file is doing more than one job. This is measurable from version control history, which makes it the most objective of the five.
Cost
More classes, and genuinely shared logic must be extracted deliberately rather than reused by accident. That deliberateness is the point, but it is work.

The related and more common failure is the opposite: shotgun surgery, where one conceptual change touches eleven files. Single responsibility taken too far causes it. The pair of tests to hold together: does this file change for unrelated reasons? (split it) and does one reason force changes in many files? (gather them). Both are the same underlying rule — what changes together should live together.

7.3Open–closed

O

Open for extension, closed for modification

You should be able to add behaviour by adding code rather than by editing code that already works.

The mechanism
Polymorphism, as in Chapter 5. Existing code calls an interface; a new variant is a new class implementing it. Nothing that was working gets touched, so nothing that was working can break.
The misreading
"Never modify existing code." Taken literally this produces configuration systems, plugin frameworks and abstract factories for requirements that never arrive. Editing code is normal and fine; the principle is about the code you have decided to protect.
The part usually left out
You cannot be open to every kind of change. Being closed against new payment types means being open to editing when a new operation is added to all of them — the expression problem again. Choosing an axis means choosing which change is cheap and accepting that the others are not, so the choice must be based on which change actually happens.
Cost
An interface, a level of indirection, and a dispatch the reader must follow. Worth it when variants arrive regularly; pure overhead when they do not.
Apply it on the second variant, not the first

You cannot know the right axis of variation from one example, so an abstraction built before the second case is a guess. The practical sequence: write the first case concretely; when the second arrives, look at what actually differs and extract the interface along that line; the third is then free. This is the rule of three from Chapter 1 applied to polymorphism, and it converts open–closed from prediction into observation.

7.4Liskov substitution

L

Anywhere the base type works, a subtype must work

A caller written against the base type must not be able to tell which subtype it received — not by the answer, not by an exception, not by a broken assumption.

The four rules
A subtype may not strengthen preconditions (it may not demand more than the base did), may not weaken postconditions (it must promise at least as much), must preserve the base's invariants, and must not throw new kinds of exception the caller was not told about.
Why it matters beyond inheritance
It applies to any interface with several implementations, and to any drop-in replacement — a cache that is "just like the real one but occasionally returns stale data" is a Liskov violation, and so is a test double that accepts inputs the real thing rejects. Every substitutability bug is one of the four rules broken.
The symptom
Callers testing for the concrete type. if (shape instanceof Square) in code that was supposed to work with any shape is proof that substitution failed, and it means every new subtype will require finding those checks.
Cost
It constrains hierarchies severely, which is a feature: most of the time the honest conclusion is that inheritance was the wrong tool and composition is the answer.
The classic violation
class Rectangle {
  setWidth(w)  { this.w = w; }
  setHeight(h) { this.h = h; }
  area()       { return this.w * this.h; }
}

class Square extends Rectangle {
  setWidth(w)  { this.w = w; this.h = w; }   // also sets height
  setHeight(h) { this.w = h; this.h = h; }
}

// A caller written against Rectangle:
function stretch(r: Rectangle) {
  r.setWidth(5);
  r.setHeight(4);
  assert(r.area() === 20);   // fails for Square: area is 16
}

A square is a rectangle mathematically. It is not a subtype of this Rectangle, because Rectangle promises that width and height vary independently and Square cannot keep that promise. Subtyping is about behaviour, not taxonomy.

Immutable, so the promise holds
interface Shape { area(): number; }

class Rectangle implements Shape {
  constructor(readonly w: number, readonly h: number) {}
  area() { return this.w * this.h; }
  withWidth(w: number) { return new Rectangle(w, this.h); }
}

class Square implements Shape {
  constructor(readonly side: number) {}
  area() { return this.side ** 2; }
}

The mutating setters were the problem, because they were the promise nobody could keep. Removing them removes the violation — which is a general lesson: most Liskov problems are mutation problems.

Does this subtype substitute?

Choose what the subtype does differently from the base. Each rule is checked separately.

7.5Interface segregation

I

No client should be forced to depend on methods it does not use

A fat interface couples every client to every other client's requirements.

The mechanism of harm
If Repository has twenty methods and your class needs two, your class is now recompiled, redeployed and potentially broken when any of the other eighteen change. In a compiled language that is literal rebuild coupling; in any language it is a test double with eighteen stub methods, and a reader who cannot tell what you actually use.
Role interfaces
Split by who needs what, not by what the implementation offers. One class can implement several small interfaces, so PostgresOrderStore can be a SavesOrders, a FindsOrdersByCustomer and an ArchivesOrders — and each caller depends only on the role it uses.
The misreading
"Every interface should have one method." Sometimes right, often not: an interface whose methods are genuinely used together by the same clients is cohesive and should stay whole. Splitting a coherent role into fragments produces a caller that has to accept four constructor arguments to do one job.
Cost
More interfaces to name and navigate. The dependency-injection wiring gets longer.

What a fat interface costs

How many clients are affected when one method on a shared interface changes.

7.6Dependency inversion

D

High-level policy must not depend on low-level detail; both depend on an abstraction

And the abstraction belongs to the high-level module — that is the half people leave out, and it is the half that does the work.

Why ownership decides everything
If your domain defines OrderRepository and the Postgres adapter implements it, the source dependency points from infrastructure into the domain: the domain compiles, tests and is understood alone. If the ORM defines the shape and your domain conforms, the dependency points outwards and you have coupled your business rules to a vendor. Identical file count, opposite architecture.
Express it in the caller's language
An interface named IUserDao with selectByPk is the database's vocabulary wearing an interface. UserDirectory.findByEmail is the domain's. The second can be implemented by a database, an LDAP server or a file, because it says what the domain wants rather than how the current storage does it.
The misreading
"Put an interface in front of everything." An interface with one implementation that changes in lockstep with it inverts nothing — it is a second file with the same reasons to change. Invert where the dependency is on something volatile: a vendor, a protocol, a framework, a delivery mechanism.
Cost
Indirection, and a wiring layer that constructs the real implementations somewhere. That layer is genuine complexity, and it is where dependency-injection containers earn their keep or become a mystery.

7.7How the five fit together

They are not independent, and seeing the chain makes them easier to remember than the acronym does.

  1. SRP decides where the boundaries go — one actor per module.
  2. ISP keeps each boundary narrow, so crossing it couples you to as little as possible.
  3. DIP decides which way the dependency across that boundary points.
  4. OCP is what you get once DIP is in place: new implementations behind the interface require no edits.
  5. LSP is the condition that makes OCP actually true — if a new implementation is not substitutable, callers grow type checks and the extension was not free after all.

So the sequence is: draw the boundary, keep it small, point the dependency inwards, and then substitutability is what keeps the arrangement honest. A violation of LSP quietly destroys the benefit of the other four.

7.8The criticisms, and which land

Common objections
CriticismVerdict
"They are vague — 'one reason to change' means anything"Partly fair. SRP is precise once you use the actor definition; without it, it is unfalsifiable. Insist on the actor version
"They assume object orientation"Partly fair. LSP and ISP are about types and interfaces. But SRP, OCP and DIP translate directly to modules and function types in any paradigm
"Following them produces enterprise astronaut code"Fair, when applied speculatively. Each principle costs indirection. Apply on evidence — the second variant, the actual second actor
"OCP is impossible — you cannot predict the axis"Fair as stated, wrong as an objection. The answer is not prediction but delay: extract the abstraction when the second case shows you the axis
"They say nothing about the things that matter — data, concurrency, boundaries"Fair. SOLID is class-level. Coupling and cohesion (Chapter 8) and architectural principles (Chapter 17) cover more ground
"LSP is just correct subtyping and needs no name"True and unimportant. It needs a name because people violate it constantly while believing they are modelling reality
The failure mode to watch for in review

SOLID gets cited as an argument rather than a reason. "That violates the open–closed principle" is not a finding; "adding a fourth payment type will mean editing these five switch statements, and we add one about twice a year" is. Every one of these principles is a claim about a change that will happen — so the productive version of the conversation is always about the change, with the principle as shorthand afterwards.

Is a class with one public method and five private helpers a good example of single responsibility?

Not necessarily — the number of methods is unrelated to the principle. The question is who asks for changes to it. A single-method class whose one method encodes a finance rule, a formatting decision and a persistence detail has three actors and violates SRP despite having one entry point. Conversely a class with fifteen methods that all serve one role, changed only ever by one team for one reason, satisfies it perfectly. The version of the test that works: look at the last several commits touching the file and ask who requested each. If the answers name different roles, split. If the file only ever changes for one role's reasons, its method count is irrelevant.

You add an interface with a single implementation "for dependency inversion". When is that justified?

Three cases justify it, and none of them is the principle by itself. First, when the concrete thing is volatile — a vendor SDK, a protocol client, a framework — so the interface is protecting stable rules from something you do not control. Second, when you need to test without it: an interface lets the surrounding logic be tested with a fake, and that is a benefit you collect today rather than a bet on tomorrow. Third, when it makes the dependency point inwards, so the domain module compiles without infrastructure on its path — that is an architectural property, not an anticipated swap. If none of the three applies — the implementation is yours, stable, in-process and needs no faking — the interface is a second file with the same reasons to change, and its cost is real: a reader tracing behaviour now has to find the implementation.

A cache implements the same interface as the real repository but occasionally returns stale data. Liskov violation?

Yes, if the interface's contract promises current data — the cache has weakened a postcondition, and a caller written against the base cannot tell why its read is wrong. The useful response is not to abandon caching but to fix the contract so the promise matches reality. Two honest options. Weaken the interface: document that find may return a value up to n seconds old, so every implementation including the direct one satisfies it, and callers that cannot tolerate staleness are forced to notice. Or split the roles: FreshOrderReader and CachedOrderReader as separate types, so the choice is explicit at the injection site rather than hidden behind a shared name. The general lesson is that Liskov violations are usually contracts written optimistically — the substitution is fine once the promise is stated accurately.

Recap

  1. SRP: one actor, not one thing. Test it against who requested the last ten changes, and watch for its opposite — shotgun surgery.
  2. OCP buys you one axis of free variation and makes the others more expensive. Extract the abstraction when the second case reveals the axis.
  3. LSP has four concrete rules: no stronger preconditions, no weaker postconditions, invariants preserved, no surprise exceptions. Most violations are mutation problems.
  4. A caller checking the concrete type is proof that substitution failed.
  5. ISP: split interfaces by client role, not by implementation. Cohesive interfaces should stay whole.
  6. DIP's decisive half is ownership — the abstraction belongs to the high-level module, and it should be phrased in the caller's language.
  7. The chain: SRP places the boundary, ISP narrows it, DIP points it, OCP is the payoff, LSP keeps it honest.
  8. Each principle is a purchase. Apply on evidence of the change it protects against, and argue the change rather than the acronym.
