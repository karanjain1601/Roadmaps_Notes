Refactoring and legacy code

Everything in this unit describes where you would like the code to be. This chapter is about getting there from where it actually is — which is usually a system with no tests, no seams, and a queue of features that cannot wait. The techniques are specific, and the governing idea is that improvement must be a sequence of steps each of which is small, safe and shippable.

~32 min read Two hats · seams · parallel change · Mikado 2 interactive panels Prerequisite: chapters 2, 3

21.1What refactoring is, precisely

Refactoring is changing the internal structure of code without changing its observable behaviour. The definition is narrow deliberately, and two things follow from it that are routinely ignored.

  1. If behaviour changed, it was not a refactoring. It was a rewrite, or a bug fix, or a feature — all legitimate, all requiring different review and different testing. Calling them refactoring is how untested behaviour changes reach production under a label that suggests safety.
  2. "Behaviour-preserving" is a claim requiring evidence. Without tests you are asserting it, not demonstrating it. This is why §21.4 exists: for legacy code the first move is never the refactoring, it is getting into a position where the claim can be checked.
The two hats

Kent Beck's rule, and the single most useful discipline here: at any moment you are either adding behaviour or refactoring, never both. When adding, do not tidy. When refactoring, do not change what the code does. Switch as often as you like — many times an hour — but know which hat you have on, and commit them separately. The reason is diagnostic: when a test breaks during refactoring you know the refactoring caused it, because nothing else changed. Mix the two and every failure requires investigation.

21.2The core catalogue

Fowler's book lists dozens. In practice a small number account for most real work, and they compose — nearly every large restructuring is a sequence of these.

The pattern to notice: the low-risk refactorings are about naming and the higher-risk ones are about moving. Naming is nearly free and improves comprehension immediately, which is why it is the right first move in code you do not understand — extract a variable, give it the name you believe it deserves, and see whether the rest of the function still makes sense.

21.3Legacy code: the working definition

Michael Feathers defines legacy code as code without tests, and the definition is useful because it names the actual problem. Age is irrelevant; code written last week without tests has the same property. The problem is that you cannot change it safely, and therefore you will not change it, and therefore it decays.

That produces the characteristic deadlock: to change it safely you need tests; to write tests you need to instantiate the thing; to instantiate it you need to break its dependencies; breaking its dependencies is a change. The techniques below are all ways out of that loop.

21.4Characterisation tests

A characterisation test does not assert that the code is correct. It asserts that the code does what it currently does, whatever that is, including the bugs. It is a net, not a specification.

The procedure, which is mechanical 
1  Write a test that calls the code with some plausible input
   and asserts something you know is wrong:
       expect(calculateFee(order)).toBe("PLACEHOLDER");

2  Run it. The failure message tells you the actual value:
       Expected "PLACEHOLDER", received 47.5

3  Change the assertion to the observed value. The test now
   passes and pins current behaviour.

4  Repeat for boundaries, empties, nulls, negatives, and the
   inputs that look like they exercise different branches.

5  Use a coverage tool to find branches you have not pinned,
   and add cases until the ones you intend to touch are covered.

Now the refactoring claim is checkable.

NOTE: if a pinned value is obviously wrong, DO NOT fix it here.
Record it, pin it as-is, and fix it as a separate, visible
behaviour change afterwards — the two hats rule. Something
downstream may depend on that bug.

21.5Seams

A seam is a place where you can change behaviour without editing the code at that place. Finding one is what lets you substitute a dependency in a test, and Feathers classifies them by where the substitution happens.

Three kinds of seam, and their enabling point
SeamSubstitution happensMechanismAvailability
Object seamAt runtime, by passing a different objectDependency injection, an overridable method, an interfaceBest — explicit and visible in the signature
Link seamAt build or load time, by resolving a different implementationClasspath order, a stub library, module aliasing, linker optionsUseful when you cannot change the source at all
Preprocessing seamBefore compilationMacros, conditional compilation, code generation, bytecode weavingLast resort — invisible and hard to reason about

The practical sequence for a class you cannot instantiate: find the dependency that is blocking you, apply the smallest possible change that creates an object seam — usually extracting an interface, or making a hard-coded construction into a constructor parameter with a default — and get one test running. That first test is disproportionately valuable, because everything afterwards is normal work.

21.6Adding to code you cannot safely change

Sometimes there is no time to get a large method under test and a feature is due. Feathers's four techniques let you add the new behaviour cleanly even though its surroundings are not.

Sprout and wrap
TechniqueWhat you doResult
Sprout methodWrite the new logic as a new, fully-tested method; call it from one line in the old codeNew code is clean and tested; old code gains one line
Sprout classSame, but the new logic is a new class — used when the old class cannot even be instantiatedNew code is completely independent of the legacy mess
Wrap methodRename the old method, create a new one with the original name that calls both the old one and your new behaviourNew behaviour runs alongside; callers unchanged
Wrap classA decorator implementing the same interface, adding behaviour around the legacy objectWorks when you cannot modify the class at all

All four accept a compromise honestly: the legacy code stays untested, and the new code is not tangled into it. That is strictly better than adding untested logic into an untested method, and it leaves a clean, extracted piece that later refactoring can build on.

21.7Parallel change

Also called expand–contract. The technique for changing an interface that has callers you cannot update atomically — a public API, a database schema, a message format, a widely-used internal function. It is the single most useful large-scale refactoring pattern, because every intermediate state is deployable and reversible.

21.8The other large-scale techniques

Branch by abstraction
Replacing a component while continuing to ship. Introduce an abstraction over the existing implementation and route all callers through it; build the new implementation behind the same abstraction; switch with a flag, one caller or one percentage at a time; remove the old one and, if you like, the abstraction. Everything happens on the main branch — the name is a deliberate contrast with a long-lived feature branch, which is the alternative and is far riskier because the merge is one enormous step.
Strangler fig
The same idea at system scale, from Chapter 20: a facade in front, capabilities moved across one at a time, the old system retired when empty. The failure mode is stopping halfway and operating two systems indefinitely, so it needs a named owner and a completion criterion from the start.
The Mikado method
For a change whose full extent is unknown. Attempt the change naively. It breaks; note what broke as prerequisites on a graph, then revert. Take one prerequisite and attempt it; if it breaks, note its prerequisites and revert again. Recursing produces a graph of leaves that can be done independently, and you work back up from them. The counter-intuitive part is the reverting — it feels like losing work, and it is what stops you accumulating a half-finished change you cannot ship or abandon.
Scratch refactoring
Refactor aggressively to understand the code, with no intention of keeping it, then throw it away and do it properly with tests. Reading is passive; restructuring forces you to find out what depends on what. Cheap, and often the fastest route to understanding a large unfamiliar function.

Which technique for this situation?

The answer depends on what you are allowed to touch and how much time you have.

How improvement actually happens

Not in a "refactoring sprint", which gets cut when a deadline arrives and produces a large risky change when it does not. It happens through the opportunistic rule: when you touch a file for another reason, leave it slightly better — one rename, one extracted function, one characterisation test. That way effort automatically concentrates on the code that changes most, which is exactly where it pays, and the improvements arrive in small reviewable pieces alongside work that is already justified. Budget for it by treating it as part of the estimate rather than as a separate item to be negotiated away.

You are pinning legacy behaviour with characterisation tests and discover the code has a clear bug. What do you do?

Pin the bug. Write the test asserting the wrong value, note it clearly — a comment saying this is believed incorrect and a ticket reference — and carry on. Three reasons. The purpose of a characterisation test is to detect unintended change during refactoring, and it can only do that if it reflects reality; a test asserting what the code should do will fail immediately and tell you nothing. Something downstream may depend on the bug: a report that has always been off by one, a downstream system compensating for it, a workflow built around it. And fixing it now mixes a behaviour change into a refactoring, which breaks the two hats rule and makes any subsequent failure ambiguous. Once the refactoring is complete and the tests are green, change the pinned assertion in its own commit with its own review — now the fix is visible, attributable and testable, and if it breaks something downstream you know exactly which change caused it.

Why does the Mikado method insist on reverting after each failed attempt?

Because the alternative is a working tree that is neither the old thing nor the new one. Attempt a change, find it breaks four places, start fixing those, find each of them breaks two more — and within a day you have a large uncommitted change that does not compile, cannot be tested, cannot be shipped and cannot be abandoned without losing the discovery. Reverting keeps the tree green at all times and converts the exercise into pure information gathering: each attempt costs minutes and yields one node on the prerequisite graph. When the graph is complete you work from the leaves inward, and every single step is small, independently testable and independently shippable — often over several days with other work interleaved, which is impossible with a giant work-in-progress. The psychological difficulty is real; it feels like throwing away work. What you keep is the knowledge, written down as the graph, and that was the expensive part.

When is parallel change necessary rather than just changing the interface?

Whenever the callers cannot all be updated in the same atomic deployment. Inside one codebase with one deploy, a rename with tool support across twelve call sites is one commit and parallel change would be ceremony. It becomes necessary the moment updates cannot be simultaneous: separate services deployed independently, so there is always a window where old and new run together; a public API with consumers you do not control; a database schema where migration and application deploy are different events; a mobile client where old versions persist for months. In every one of those, changing the interface in one step guarantees a period of breakage — and rolling back is equally broken, which is the worse property. Parallel change removes the window: during the expand phase both forms work, so old and new callers coexist and either deploy order is safe. The cost is that you must remember to contract; abandoned expand phases accumulate, which is why the contract step deserves a ticket created at the same time as the expand step.

Recap

  1. Refactoring preserves observable behaviour. If behaviour changed it was something else, and it needs different review.
  2. The two hats: adding behaviour or refactoring, never both, committed separately — so a failing test has one possible cause.
  3. Naming refactorings are nearly free and highest value; moving refactorings carry the risk.
  4. Legacy code is code without tests, and the deadlock is that testing it requires changing it.
  5. Characterisation tests pin current behaviour, bugs included. Fix them afterwards, visibly.
  6. Seams are where you can substitute without editing. Object seams are best; create one with the smallest possible change.
  7. Sprout and wrap let new code be clean even when its surroundings cannot be.
  8. Parallel change — expand, migrate, contract — is required whenever callers cannot be updated atomically.
  9. Branch by abstraction, strangler fig and Mikado keep large changes shippable at every intermediate step.
  10. Improvement is opportunistic, concentrated where code changes most, not scheduled as a sprint.
