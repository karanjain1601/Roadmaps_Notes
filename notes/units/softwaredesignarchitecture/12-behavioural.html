Behavioural patterns

Eleven patterns about how objects communicate and how responsibility is assigned between them. This is the largest group and the most useful: strategy, observer and command turn up in almost every codebase, usually without anyone naming them, and state is the one that most reliably replaces a mess of conditionals with something you can draw.

12.1Strategy

Behavioural · everywhere

Strategy

Put an interchangeable algorithm behind an interface so the caller can be given a different one.

Signature
An object that holds a reference to something with one meaningful method, and delegates to it. Sorting comparators, pricing rules, retry policies, compression algorithms, validation rules.
In a language with first-class functions
Strategy is a parameter. sort(items, byPrice) is the pattern, complete, with no interface and no class. Reach for the class form when the strategy needs state, several methods, or a name it can be registered under.
Cost
One indirection, and the caller must now choose. If there is only ever one algorithm, you have added a decision nobody makes.
Relation to others
Structurally identical to bridge (which separates two hierarchies) and to state (where the object swaps its own strategy as it changes). The code is the same; the intent differs.

12.2Observer

Behavioural · everywhere

Observer

Let objects register interest in an event so the emitter does not need to know who cares.

What it buys
The dependency inverts: the subject depends on an Observer interface, and observers depend on the subject only to subscribe. Adding a fifth listener requires no change to the emitter, which is open–closed at runtime.
The costs, and they are real
Control flow becomes invisible. Reading the emitter tells you nothing about what happens next. Ordering is undefined unless you define it, and code will come to depend on it accidentally. Cascades — an observer that triggers another event — can loop or fan out unpredictably. And leaks: an observer that never unsubscribes keeps the subject alive and keeps being called, which is one of the most common memory leaks in long-lived applications.
Synchronous or not
Synchronous observers run inside the emitter's call, so an exception in one can abort the emitter and a slow one blocks it. Asynchronous delivery fixes both and introduces eventual consistency. Decide deliberately; the default in most libraries is synchronous.
At larger scale
This is publish–subscribe, and every caveat above reappears — see the messaging patterns in the System Design unit.

12.3Command

Behavioural

Command

Turn a request into an object, so it can be stored, queued, logged, replayed, undone or authorised.

Why reify a method call
Because an object can be put in a list and a method call cannot. Undo stacks, job queues, macro recording, audit logs, retry-after-failure, and transactional outboxes all need the request to exist as data before it is executed.
Undo
Add undo() and each command must capture enough state to reverse itself. Note that the reverse is semantic, not a rollback: undoing a send means a retraction, not the message never having existed — the same distinction as compensating transactions in distributed systems.
Cost
A class per operation, and parameters that used to be arguments become fields. In a language with closures, a command with one method is a function plus its captured environment — which is why job queues in dynamic languages often just serialise a name and arguments.
Where you have met it
Every background job, every editor's undo, every CQRS command handler, every HTTP request treated as an object.

12.4State

Behavioural · the highest-value one

State

Let an object change its behaviour by swapping the object that implements it, so each state's rules live in one place and illegal transitions cannot happen.

The problem it replaces
A status field plus conditionals scattered through every method. Every method has to handle every state, no method shows the full lifecycle, and nothing prevents a transition that makes no sense.
Mechanism
One class per state, each implementing the operations and returning the next state. The transition table becomes the type signatures, so an operation a state does not support simply does not exist on it.
Cost
A class per state, and shared data must be passed to each. Worth it above roughly four states or when transitions have real rules; below that, a conditional is clearer.
Alternative worth knowing
An explicit transition table — a map from (state, event) to (next state, action). Less object-oriented, often clearer, and it makes the whole machine visible in one place, which is the main thing the pattern is trying to achieve.

State machine versus scattered conditionals

Drive an order through its lifecycle. Illegal transitions are not rejected at runtime — they do not exist.

12.5Template method

Behavioural

Template method

A base class defines the skeleton of an algorithm and leaves named holes for subclasses to fill.

Mechanism
A public method that calls protected steps in a fixed order. Subclasses override the steps, never the order. This is the Hollywood principle from Chapter 9 in its smallest form.
The trade against strategy
Template method uses inheritance and fixes the sequence; strategy uses composition and swaps whole behaviours. Template method is more constrained and therefore safer against misuse, and it carries every inheritance cost from Chapter 5 — subclasses are coupled to protected members and to the call order.
When it is right
A genuinely fixed sequence with two or three variable steps, all subclasses under your control, and the hooks documented as the extension contract.
When it goes wrong
When the number of hooks grows past a handful, or when a subclass needs to change the order. At that point the sequence was not fixed after all, and composition — a pipeline of steps you assemble — is the honest answer.

12.6Visitor

Behavioural · specialised

Visitor

Add operations to a fixed set of types without editing them — the answer to the other half of the expression problem.

What it is for
Polymorphism makes adding a type free and adding an operation expensive (Chapter 5). Visitor reverses that: with a stable set of node types, each new operation is one new visitor class and no edits to the nodes.
Where it genuinely fits
Compilers and interpreters over an abstract syntax tree, document object models, query planners, serialisers over a fixed schema. All cases where the type set is settled and the operations keep multiplying.
Cost, which is high
Double dispatch is awkward in most languages — each node needs an accept method, and the indirection is genuinely hard to read. Adding a type now means changing every visitor. And it usually breaks encapsulation, because visitors need access to node internals.
Modern alternative
Pattern matching over a sealed union does the same job with none of the ceremony, and the compiler checks exhaustiveness. If your language has it, use it — visitor is largely a workaround for its absence.

12.7Chain of responsibility

Behavioural

Chain of responsibility

Pass a request along a chain of handlers until one deals with it, so the sender does not know which will.

Where you already use it
Every HTTP middleware stack, every event bubbling model, every logging hierarchy, every approval workflow with escalation levels.
Two variants worth distinguishing
First match wins — the request stops at the first handler that can deal with it. All handlers run — each may transform and pass on, which is really a pipeline and is what middleware actually does. Confusing the two produces bugs where a handler assumes it is last.
Cost
A request can fall off the end unhandled unless you add a terminal handler. The order is significant and invisible from the sender, exactly as with decorators. And debugging means knowing what the chain was assembled as.

12.8The remaining five

Less frequently reached for, still worth recognising
PatternPurposeCost / caveat
MediatorObjects communicate through a hub instead of directly, turning a mesh of n² relationships into nThe mediator becomes a god class holding everyone's coordination logic. Useful for UI form interactions; dangerous as a general answer
IteratorTraverse a collection without exposing its structureBuilt into every modern language. Worth knowing only so you recognise that for…of and generators are this pattern
MementoCapture and restore an object's state without breaking encapsulationSnapshots get large; and it is often simpler to keep the object immutable and hold old versions, which is memento for free
InterpreterRepresent a grammar as classes and evaluate expressionsOnly for small, stable languages. Anything real wants a parser generator
Null objectA real instance with neutral behaviour, so callers need no null checksNot GoF, and one of the most useful. The risk is hiding a genuine error as silence — use it where "nothing" is a legitimate case, not where absence is a failure

12.9The ones that are the same shape

Several behavioural patterns compile to nearly identical code, and the confusion is worth resolving directly.

Same structure, different intent
These look alikeDistinguished by
Strategy vs stateWho chooses. In strategy the caller supplies the algorithm and it does not change; in state the object swaps its own behaviour as a consequence of what happens to it
Strategy vs bridgeScope. Strategy varies one algorithm; bridge separates two whole hierarchies that both keep growing
Command vs strategyWhat is captured. A strategy is how to do something; a command is a specific request including its arguments, so it can be stored and replayed
Chain of responsibility vs decoratorWhether the call always continues. A decorator always delegates and adds around it; a chain handler may stop and not pass on
Observer vs mediatorDirection. Observer is one-to-many broadcast with the subject unaware of listeners; mediator is many-to-many coordination with the hub knowing everyone
Template method vs strategyMechanism. Template method fills holes via inheritance and fixes the order; strategy replaces a whole behaviour via composition

Your order class has a status string and eleven methods that each begin with a switch on it. Is that a state pattern candidate?

Almost certainly. The specific signal is not the switch but the repetition of the same switch across methods — eleven copies of the same transition knowledge, none of which shows the lifecycle, and no single place you could read to learn which transitions are legal. Introducing state classes gathers each stage's rules into one class and, crucially, makes illegal operations disappear rather than throw: a ShippedOrder simply has no addItem, so the compiler enforces what the runtime was checking. Two things to confirm first. Count the states — with two or three, a conditional is genuinely clearer and the classes are ceremony. And check whether the states share much data; if each state needs all of the order's fields, you will be passing the order into every state object, which is workable but worth knowing before you start. If you want most of the benefit for less, an explicit transition table — a map from (state, event) to (next state, action) — puts the whole machine in one readable place without a class per state.

Why does the observer pattern make debugging harder, and what mitigates it?

Because it removes the call site. Reading the emitter tells you that an event is published and nothing about what happens next; to know the consequences you must find every subscription, which may be registered in unrelated modules at startup or dynamically at runtime. Then three further problems compound it: ordering is undefined but code accidentally comes to depend on it, one observer can trigger another event and produce a cascade nobody designed, and a synchronous observer that throws can abort the emitter's own work. Mitigations that actually help: name events after facts that happened rather than actions to take, so a listener adding behaviour cannot be mistaken for the emitter's business logic; register subscriptions in one visible place rather than scattered; log emission and handling with a correlation id so a cascade can be reconstructed; make delivery asynchronous at boundaries so a slow or failing listener cannot damage the emitter; and cap or detect re-entrancy so a cycle fails loudly instead of overflowing the stack.

When is a plain function better than a strategy class?

Whenever the strategy has one method and no state, which is most of the time. sort(items, (a, b) => a.price - b.price) is the strategy pattern with all its benefits and none of its ceremony — the algorithm is interchangeable, the caller supplies it, and there is no interface, no class and no file. The class form earns its place in three cases. When the strategy carries configuration — a retry policy with a backoff base and a cap — the object holds that state naturally where a closure would hide it. When it needs several related methods, so it is really a role rather than an operation. And when strategies must be named and looked up — registered in a map, chosen by a configuration string, discovered by a plugin loader — because a class has an identity and a name that a lambda does not. Outside those, a function keeps the code shorter and the indirection lower, and the pattern is no less present for being unnamed.

Recap

  1. Strategy is a function parameter in any language with closures. Use the class form when it has state, several methods or a registered name.
  2. Observer inverts the dependency and costs you visible control flow. Ordering, cascades and unsubscription are all your problem.
  3. Command turns a request into data so it can be queued, logged, replayed or undone — and undo is semantic, not a rollback.
  4. State replaces a repeated switch on a status field and turns runtime checks into operations that do not exist. Worth it above about four states.
  5. Template method fixes the order and uses inheritance; strategy swaps whole behaviours and uses composition.
  6. Visitor is the answer to adding operations over fixed types, and pattern matching over a sealed union is a better one where available.
  7. Chain of responsibility: decide whether it is first-match or pipeline, and add a terminal handler.
  8. Several of these are the same code with different intent. The distinguishing questions are who chooses, what is captured, and whether the call always continues.
