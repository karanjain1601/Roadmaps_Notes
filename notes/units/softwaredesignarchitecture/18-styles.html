Architectural styles

A style is a family of structures with a characteristic set of trade-offs. They are not exclusive — a real system is usually layered and event-driven and client-server at once — and the useful thing about naming them is that each comes with a known profile of what it makes easy and what it makes expensive.

18.1Styles are combined, not chosen

The question "are we microservices or a monolith?" is less useful than it sounds, because styles operate on different axes and stack. A typical system is:

One system, four styles 
client-server        browser talks to a server            (topology)
layered              controllers → use cases → domain     (internal structure)
event-driven         order placed → invoicing, shipping   (integration)
pipes and filters    the ingestion job                    (one subsystem)

None of these contradicts another. "Microservices" is a decision
about DEPLOYMENT — whether those layers and events live in one
process or many — and it is a different question from all four.

So the productive framing is: what topology, what internal structure, what integration mechanism, and how many deployable units. Those are four decisions with four sets of trade-offs, and conflating them is what makes architecture arguments circular.

18.2Structural styles

How the code inside one unit is organised
StyleStructureStrengthsWeaknesses
MonolithicOne deployable, no enforced internal boundariesSimplest possible operation, one deploy, one debugger, refactoring across the whole system is trivialBoundaries erode without enforcement; one team's change can break another's; scales as a unit
Modular monolithOne deployable, boundaries enforced by module rulesAlmost all the operational simplicity, plus real boundaries and clear ownership. Boundaries can be moved by refactoringNeeds enforcement tooling and discipline; still one scaling and failure unit
LayeredHorizontal slices — presentation, application, domain, infrastructureUniversally understood; clear place for everything; easy to teachFeature changes touch every layer; layers often become anaemic pass-throughs; the domain ends up depending on infrastructure. See Chapter 19
Component-basedVertical slices by feature, each with its own internalsA change lands in one place; deletion is rm -rf; ownership is obviousCross-cutting concerns need a home; genuinely shared code needs deliberate placement
Vertical beats horizontal, almost always

Layering is horizontal and features are vertical, so a layered structure guarantees that every feature change crosses every layer — the shotgun surgery smell, built into the directory tree. Organising the top level by feature (billing/, catalogue/, auth/) and layering inside each gets both: a change lands in one directory, and the dependency rule still holds within it. This is the same conclusion as bounded contexts in Chapter 14, arrived at from the file system.

18.3Topological styles

Client–server
Asymmetric: clients request, a server responds and holds the authoritative state. Almost everything you build is this. The design consequences are that the server is the trust boundary — client-side validation is a convenience, never a control — and that the server is a shared fate: its capacity and availability bound everyone's.
Peer-to-peer
Symmetric: every node is both client and server. Removes the central bottleneck and the single point of failure, and pays for it in discovery, consistency and trust — with no authority, every peer must be assumed hostile. Used where centralisation is the thing being avoided: BitTorrent, blockchains, some mesh and CRDT-based collaboration systems.
Tiered
Physical separation into presentation, application and data tiers. Historically the default for scaling; now often collapsed, because a stateless application tier plus a managed database achieves the same thing with fewer moving parts. The term survives mostly in enterprise procurement documents.

18.4Integration styles

How separate parts communicate is the decision with the largest downstream consequences, because it determines coupling in time as well as in code.

Four ways to connect things
StyleCouplingFailure behaviourUse when
Direct call / RPCTemporal — both must be up; caller knows the calleeCallee's failure is the caller's failure unless handledYou need an answer now; a query; a strong consistency requirement
Request–reply over a queueCaller knows the callee, but not its availabilityCallee can be down; the message waitsYou need an answer but can tolerate latency
Event-driven / publish–subscribeEmitter does not know its subscribersSubscribers can be down and catch upSomething happened and others may care; adding consumers should not touch the emitter
Shared dataTotal — both bound to a schemaSchema change breaks both simultaneouslyRarely. Usually an accident rather than a choice

Event-driven, in its two forms

Worth separating because they behave differently and are constantly conflated:

  • Event notification — a thin message saying something happened, carrying an id. Consumers call back for details. Low coupling on the payload; high coupling on availability, and a race, because the entity may have changed since.
  • Event-carried state transfer — the message carries the facts. Consumers need no callback, so they can process while the emitter is down, at the cost of a larger payload and a published schema to maintain.

And the caveats from Chapter 12 apply at this scale with more force: control flow is invisible, ordering is not guaranteed, cascades are possible, and the system becomes hard to reason about end to end. The mitigations — past-tense names describing facts rather than instructions, correlation ids, an event catalogue, and explicit versioning — are not optional at system scale.

18.5Pipes and filters

Style

Pipes and filters

A sequence of independent processing stages, each consuming a stream and producing one, connected by pipes and knowing nothing about their neighbours.

Strengths
Each filter is independently testable and reusable, stages can be reordered or inserted without touching the others, and parallelism is natural — each stage can run concurrently, and each stage can be scaled independently.
Where you use it
Unix shell pipelines, compilers, ETL, log processing, streaming systems, HTTP middleware, and image or video processing.
Weaknesses
Error handling across a pipeline is awkward — a failure in stage four must be attributed and the partial work decided upon. Shared context has to be threaded through explicitly. And it is a poor fit for anything interactive, since the model assumes a flow rather than a conversation.

18.6Service-oriented and microservices

Both split a system into independently deployable services; they differ in emphasis and in era.

SOA and microservices
SOA (2000s)Microservices (2010s)
Service sizeCoarse — often whole business capabilitiesFine — one bounded context, sometimes smaller
CommunicationThrough an enterprise service bus with routing and transformationDirect or via a broker; "smart endpoints, dumb pipes"
DataOften a shared enterprise databaseA database per service — the defining property
GovernanceCentralised standardsDecentralised; teams choose
Failure modeThe bus becomes the bottleneck and the coupling pointA distributed monolith: services that must be deployed together
The distributed monolith

The characteristic failure. You have services with a network between them but they must still be released together, because they share a database, or share a library that changes constantly, or call each other synchronously in long chains, or were split along technical rather than domain lines. You have paid every cost of distribution — latency, partial failure, tracing, versioning, on-call — and collected none of the independence. The diagnostic question is direct: can you deploy one service without deploying any other? If the answer is no, the split has not delivered anything, and the fix is to work out which coupling is preventing it rather than to add more services.

What splitting into services actually costs

The independence is real. So is the arithmetic of latency and failure across a call chain.

18.8Choosing, in practice

  1. Start with a modular monolith unless you have a specific reason not to. It gives you the cheap independences from Chapter 17, its boundaries are refactorable, and it can be split later along lines that have proved themselves. Nothing about it prevents becoming distributed; everything about starting distributed prevents becoming simple.
  2. Organise the top level by feature or context, not by technical layer. Layer inside each.
  3. Split out a service when there is a concrete forcing reason — a component needing to scale very differently, a team that must release on its own cadence, a compliance boundary, a technology that cannot live in the same process. "It will scale better" is not a reason; "this component handles 40× the traffic of everything else and we cannot scale it alone" is.
  4. Prefer events for anything that does not need an immediate answer. This is what makes services genuinely independent rather than a distributed call graph.
  5. Check the deployability question regularly. If services cannot be released independently, the split is not paying and you should find the coupling.
Why is "layered" so widely taught and so often unsatisfying in practice?

Because it is easy to explain and it slices the system along the wrong axis. Layering answers "what kind of code is this?" — presentation, application, domain, infrastructure — which gives every file an obvious home and makes the structure teachable in one diagram. But work arrives as features, and features are vertical, so adding one touches every layer: a controller, a service, a domain change, a repository method, a migration. That is shotgun surgery designed into the directory tree, and it also makes it impossible to see from the file system what the application does — you see four folders describing techniques rather than the business. Two further problems compound it. Layers tend to degenerate into pass-throughs, where a service method exists only to call a repository method, adding a hop and no value. And the classical layering has the domain sitting above infrastructure, so the dependency points from policy to detail, which is precisely what Chapter 19 exists to invert. The fix is not to abandon layering but to put it inside a vertical slice: feature at the top level, layers within.

What single question tells you whether a microservices split is working?

Can you deploy any one service to production without deploying any other? Everything else follows from that. If the answer is no, find out why, and the reason will be one of four couplings. A shared database, so a schema change requires coordinated releases — the most common, and it means you have distributed the code but not the data. A shared library that changes frequently, so a version bump ripples. Synchronous call chains with no versioning discipline, so a contract change must land everywhere at once. Or a split along technical lines — a "validation service", an "orchestration service" — so any feature spans several services by construction. Each of those has a different fix, and none of them is more services. It is also worth asking the question quantitatively rather than in principle: look at the last thirty deployments and count how many involved more than one service. Teams generally believe they have independent deployability long after they have lost it, because the coupling accumulates one shared table at a time.

When is event-driven integration the wrong choice?

When the caller needs an answer to proceed, and when you need a strong consistency guarantee across the participants. Events buy decoupling by giving up synchrony, so if the user is waiting for a result — "is this seat available?", "did the payment authorise?" — an event is the wrong shape and you want a request with a timeout. Likewise, if two things must be true simultaneously or not at all, events give you eventual consistency and a window in which the system is observably inconsistent; sometimes that is acceptable and sometimes it is a regulatory problem. Three further cases where events cost more than they give: a small system with two components, where the indirection buys decoupling nobody needs and removes the ability to read the flow; a team without the operational maturity for it, since debugging an event cascade requires correlation ids, tracing and a way to replay, and without those an outage becomes archaeology; and any place where ordering genuinely matters across partitions, because guaranteeing it is difficult and code will silently start depending on the ordering you happen to get.

Recap

  1. Styles combine. Topology, internal structure, integration mechanism and number of deployables are four separate decisions.
  2. Vertical slices beat horizontal layers at the top level — layering inside a feature gets both.
  3. A modular monolith buys real boundaries at almost no operational cost, and its boundaries are refactorable.
  4. Integration style determines coupling in time, not just in code. Direct calls couple availability; events do not.
  5. Event notification and event-carried state transfer behave differently. One trades payload size for a callback and a race.
  6. The distributed monolith is the characteristic microservices failure: all the cost, none of the independence.
  7. Split for a concrete forcing reason, not for anticipated scale.
  8. The test is deployability: can one service ship without any other? Check it against the last thirty deployments, not in principle.
