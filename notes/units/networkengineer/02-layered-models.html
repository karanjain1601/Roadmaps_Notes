The layered models

OSI is taught as seven names to memorise, which is why most people find it useless. Its actual value is as a diagnostic instrument: a way of cutting the problem in half repeatedly until the fault has nowhere left to hide.

~28 min read OSI · TCP/IP · encapsulation · MTU 2 interactive panels Prerequisite: chapter 1

2.1Why layers exist

Layering is not a description of how networks were designed — much of the internet was built before the model was finished. It is an abstraction contract: each layer offers a service to the one above and depends only on the one below, so any layer can be replaced without touching the others. That is why the same TCP connection works over Ethernet, Wi-Fi, a mobile network and a satellite link, and why HTTP did not need rewriting when IPv6 arrived.

The session and presentation layers describe things that in practice live inside applications or inside TLS, and almost nobody troubleshoots at "layer 6". The layers that do real work in a network engineer's life are 1, 2, 3, 4 and 7, and the informal extension to "layer 8" — the user — is a joke that is also, frequently, the correct diagnosis. Where the model earns its place is not taxonomy but method: it gives you an ordered sequence of questions where each answer eliminates everything below it, which is what turns troubleshooting from guessing into bisection.

2.3MTU, and the failures it causes

The classic MTU symptom: small things work, large things hang

A connection where ping succeeds, the TCP handshake completes and small requests return normally, but a large response hangs forever, is an MTU problem until proven otherwise. The mechanism: something in the path — a tunnel, a VPN, an overlay — has a smaller MTU than the endpoints assumed. IPv4 routers could once fragment, but almost everything now sets don't fragment, so the oversized packet is dropped and an ICMP "fragmentation needed" message is sent back. If a firewall blocks that ICMP message, the sender never learns. It retransmits the same too-large packet forever, and the connection stalls rather than failing cleanly — which is why it presents as a hang rather than an error. Two consequences worth remembering: blanket-blocking ICMP breaks path MTU discovery and is a genuinely bad idea, and any tunnel you add needs its MTU accounted for, usually by clamping the TCP maximum segment size at the tunnel endpoint.

Why is layering useful for troubleshooting rather than just for describing?

Because it gives you an ordered set of dependencies, and a dependency order is what lets you eliminate half the possibilities with each test. Every layer relies entirely on the one beneath it, so a positive result at layer 3 proves that layers 1 and 2 are working along that path — you do not need to check the cable if you can ping the far end, and conversely there is no point examining a routing table on a port with no link. That turns an unbounded problem into a bisection, and bisection is why the model is worth knowing when the seven names on their own are not. The direction to work in depends on the shape of the failure, which is the part people usually miss. When nothing works, go bottom-up, because layer 1 faults are the most common and the cheapest to rule out — a dead port, a bad optic, a duplex mismatch — and every higher-layer investigation is wasted effort if one of those is the cause. When one thing is broken and everything else from the same host to the same destination works, go top-down, because that working traffic has already proved layers 1 to 3 and starting at the cable throws away evidence you already have. A third pattern is often faster than either: bisect the path rather than the stack, testing from the midpoint between the last known-good element and the failure. And underneath all of it, the highest-yield question is "what changed?" — networks that worked yesterday and do not today have almost always had something altered, and the change log finds that faster than any capture.

Small requests succeed and large transfers hang. What is happening?

Path MTU discovery is being broken, almost certainly by an ICMP filter. The mechanism has three steps. Something in the path — a VPN, a GRE or VXLAN tunnel, a provider link — has a smaller MTU than the endpoints negotiated, so once the transfer ramps up to full-size segments, those packets are too big for that hop. Because essentially all modern IPv4 traffic sets the don't fragment bit, and IPv6 removed router fragmentation entirely, the router cannot split the packet and instead drops it and returns an ICMP "fragmentation needed" message naming the correct MTU. That message is how the sender learns to send smaller packets. If a firewall or ACL somewhere blocks ICMP — often as a blanket rule someone added years ago believing ICMP to be dangerous — the sender never receives it, keeps retransmitting the identical oversized packet, and the connection stalls rather than fails. That distinctive signature is the giveaway: the handshake completed, small responses returned, and the transfer hangs the moment the segment size grows. To confirm, send progressively larger pings with the don't-fragment bit set and find the size at which they stop returning; the boundary is the real path MTU. There are three fixes and they are not equivalent. Permit ICMP type 3 code 4, which repairs the mechanism properly and is the correct answer. Clamp the TCP maximum segment size at the tunnel endpoint so both ends negotiate a size that fits, which works reliably and only helps TCP. Or lower the endpoint MTU, which is blunt and costs efficiency everywhere. Note also that UDP-based protocols get no help from MSS clamping, so the ICMP fix matters more as QUIC traffic grows.

Why is a device's packets-per-second figure often more important than its bandwidth rating?

Because forwarding work is done per packet, not per byte. Each packet requires the same table lookups, header rewrites, access-list evaluations and counter updates whether it carries 1,460 bytes of payload or none — so a device's real capacity is bounded by how many forwarding decisions per second it can make, and the bandwidth figure on the datasheet assumes those packets are large. The arithmetic is stark: at 1 Gbps a stream of 1,500-byte frames is about 81,000 packets per second, while a stream of minimum-size 64-byte frames is 1,488,095 — eighteen times the decision rate for the same bits on the wire. A device comfortably rated for one gigabit may fall over completely at the second figure, and it will do so while its bandwidth graphs look healthy, which makes the failure genuinely confusing to diagnose. Three practical consequences. When sizing equipment, look for the small-packet forwarding rate, which vendors quote separately precisely because it is the binding constraint. Understand that a small-packet flood is an attack on the packet budget rather than the bandwidth, which is why it can saturate a device far below its rated throughput and why mitigation belongs upstream. And be aware that anything doing per-packet work in software — a virtual appliance, a firewall performing deep inspection, a router with a complex access list — has a much lower ceiling than hardware forwarding, and that the ceiling is expressed in packets. The related detail from §2.2 belongs here too: the 20 bytes of preamble and interframe gap are invisible in a capture and real on the wire, so throughput calculations that omit them overstate capacity, increasingly so as packets shrink.

Recap

  1. Layering is an abstraction contract, which is why TCP survived every change of medium beneath it.
  2. Layers 5 and 6 are largely vestigial. The working set is 1, 2, 3, 4 and 7.
  3. The model's value is bisection, not taxonomy — each answer eliminates everything below it.
  4. Bottom-up when nothing works; top-down when one thing is broken.
  5. Twenty bytes of preamble and interframe gap are on the wire and absent from your capture.
  6. Forwarding cost is per packet. 1 Gbps is 81,000 large packets or 1.49 million small ones.
  7. Standard 1500-byte TCP over IPv4 is about 95% efficient; jumbo frames reach 99%.
  8. Every tunnel eats MTU, and the cost compounds when you stack them.
  9. Small works, large hangs means path MTU discovery is broken — usually by an ICMP filter.
  10. Ask what changed before opening a packet capture.
