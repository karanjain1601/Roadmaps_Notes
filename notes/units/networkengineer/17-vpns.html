Tunnels and VPNs

A tunnel carries one network's packets inside another's. Whether you want it for privacy, for reachability, or to make two sites look adjacent changes almost nothing about how it works and everything about which one you should choose.

~28 min read IPsec · WireGuard · topology · zero trust 2 interactive panels Prerequisite: chapters 2, 12, and Cyber Security ch 9

17.1What a tunnel is for

Three different reasons, frequently conflated
ReasonMeansEncryption is
PrivacyThe path between two points is untrusted, so hide the contentsThe whole point
ReachabilityPrivate address space at both ends, or a protocol the path will not carryOptional — GRE carries traffic with no encryption at all
AdjacencyMake two distant networks behave as if directly connected, so routing protocols and multicast work across themOptional, and usually combined with IPsec
A tunnel is a routing decision wearing a disguise

Once a tunnel exists, the interesting questions stop being cryptographic and become routing questions: which traffic enters it, what happens when it is down, and whether the interface state reflects reality. Two failure modes recur because of that. A tunnel interface frequently reports itself up whenever the underlying path is up, regardless of whether the far end is answering — so a routing protocol keeps the route installed and traffic disappears into it. The answer is a keepalive mechanism or a reachability check that fails the interface when the far end stops responding. And recursive routing is the other one: if the route to the tunnel's own destination is learned through the tunnel, the tunnel flaps continuously, which is a confusing failure that is obvious once named. Keep the route to the tunnel endpoint out of anything the tunnel carries.

  Without it, a tunnel whose far end has vanished stays

WHY WIREGUARD IS DIFFERENT
  One cipher suite, no negotiation, a few lines of
  configuration, and it runs in the kernel. There is nothing

  you control, it is dramatically simpler.

The VPN grants network access, and network access is the wrong unit

A traditional remote access VPN authenticates a user once and then places their device on the internal network, where it can reach whatever the network permits — which is usually a great deal. So a compromised laptop, a stolen credential or a piece of malware on a home machine obtains the same reach as a desk in the building, and the authentication event that made it possible happened hours earlier. The zero trust argument is not that VPNs are bad but that the unit of access should be an application, not a network: authenticate the user and the device, authorise each request against a policy, and never place anyone on a flat internal segment at all. For a network engineer the practical consequences are concrete — internal services need to be individually reachable through a proxy rather than collectively reachable through a tunnel, identity becomes part of the policy decision rather than a gate in front of it, and the VPN concentrator stops being the thing every remote worker depends on. It is a substantial change and it is usually incremental: start with the applications where broad network access is most obviously excessive.

Why does an IPsec tunnel usually fail in phase 1, and what do you check?

Because phase 1 is where the two ends must agree on a set of parameters exactly, and there are many of them with no negotiation of last resort — if any one differs, the peers cannot establish the channel in which everything else would be negotiated. The list to compare, in roughly the order of how often each is wrong: the pre-shared key or certificate, including invisible whitespace when it was copied from an email; the peer identity, which may be an address on one side and a name on the other; the encryption and integrity algorithms; the Diffie-Hellman group, which is a common mismatch because defaults differ by vendor and by software version; the lifetime, where a mismatch may let the tunnel come up and then fail at rekey, which presents as a tunnel that breaks every eight hours; and the IKE version. Get a written parameter sheet from the other party before configuring anything — that single habit removes most of the wasted time, because the log messages tend to name the phase rather than the parameter. Two other things worth checking early. Whether UDP 500 and 4500 and ESP are permitted by every firewall in the path, in both directions, since ESP is a protocol number rather than a port and is dropped by some devices silently. And if phase 1 completes and phase 2 does not, look at the traffic selectors — the subnets each side declares the tunnel covers — because they must match as a mirror image, and a mismatch there is the single most common phase 2 failure. Finally, if the tunnel comes up and no traffic passes, suspect MTU and clamp the maximum segment size, since the roughly 57 bytes of overhead is exactly the case Chapter 2 describes.

Hub and spoke or full mesh?

Hub and spoke unless site-to-site traffic is both substantial and latency-sensitive, in which case dynamic tunnels are usually better than a static full mesh. The arithmetic drives it: a full mesh needs n(n−1)/2 tunnels, so twenty-four sites is 276 tunnels and fifty sites is 1,225 — each of which must be configured, monitored, rekeyed and troubleshot, and each of which is a place for a parameter mismatch. That is unmanageable by hand well before it is unmanageable in principle. Hub and spoke needs one tunnel per site, which is trivially maintainable, and the cost is that traffic between two spokes crosses the hub — adding latency, consuming the hub's capacity twice, and making the hub a single point of failure for site-to-site communication. Whether that matters depends entirely on the traffic mix. If almost everything is a site talking to a data centre or to the internet, the hub is on the path anyway and there is nothing to optimise. If sites talk to each other constantly — voice between branches, replication, distributed applications — the detour is paid on every packet and the hub becomes a bottleneck. The middle answer is dynamic tunnels, where spokes register with a hub and build direct tunnels to each other on demand for the flows that warrant it, then tear them down. That gives mesh paths with hub-and-spoke configuration, and it is what most modern SD-WAN products implement under a different name. Two supporting points regardless of topology: run two hubs rather than one, because a single hub failing takes down every spoke's connectivity; and prefer a topology your tooling can generate rather than one you maintain by hand.

Should split tunnelling be allowed?

For most organisations now, yes, and the reasoning has shifted in the last few years. The historical argument for full tunnel — sending all traffic through the corporate network — was inspection and control: every request passes your proxy, your filtering and your logging, and the user's device cannot simultaneously be on a hostile home network and your internal one. Those are real benefits. What changed is where the applications went. When most traffic goes to SaaS platforms rather than to internal servers, a full tunnel sends every one of those requests to your data centre and back out again, which adds latency to everything the user does, and consumes your internet circuit twice for traffic that never needed to touch it. Video conferencing is the worst case and the one that forces the decision, because the detour is directly audible. So the pragmatic default is split tunnel: internal destinations through the VPN, everything else direct. The honest costs are that you lose visibility of the direct traffic and the device is on two networks at once, which is a genuine bridging concern on a compromised machine. Three mitigations make it defensible. Enforce security on the endpoint rather than on the network path — a device-based agent with filtering and logging travels with the user and works whether or not the tunnel is up. Use a cloud-delivered security service so inspection happens near the user rather than at your data centre. And narrow what the tunnel grants: split tunnelling reduces the traffic through the VPN and does nothing about the reach it provides once connected, which is the more serious problem and the one the note above is about.

Recap

  1. Privacy, reachability and adjacency are three different reasons for a tunnel, and only one needs encryption.
  2. A tunnel interface can report itself up while the far end is gone. Use dead peer detection or a reachability check.
  3. Never learn the route to the tunnel endpoint through the tunnel. That is recursive routing, and it flaps.
  4. Most IPsec failures are phase 1 parameter mismatches. Get a written parameter sheet first.
  5. Phase 2 failures are usually traffic selectors, which must mirror exactly.
  6. NAT traversal wraps ESP in UDP 4500, and its absence is why a tunnel works from the office and not from home.
  7. WireGuard removes the negotiation, so there is nothing to mismatch — and nothing to interoperate with either.
  8. A full mesh is n(n−1)/2 tunnels. Dynamic tunnels give mesh paths with hub-and-spoke configuration.
  9. Run two hubs. One hub failing removes every spoke's site-to-site connectivity.
  10. The VPN grants network access, and the application is the better unit.
