Designing for failure

Redundancy is not a property you add to a network; it is a mechanism you install, and the mechanism can fail. This chapter is about when a second device genuinely helps, when it makes things worse, and why the convergence figure that matters is the one the application experiences rather than the one the protocol reports.

18.1The first hop

A host has one default gateway, so the gateway must be able to move 
THE PROBLEM
  A host learns one gateway address from DHCP and uses it
  until told otherwise. If the router holding that address
  fails, every host on the segment is stranded — they have
  no mechanism to discover the alternative.

THE SOLUTION: a virtual address shared by two routers
  VRRP     the standard. One router is master and owns the
           virtual address and a virtual MAC; the backup
           takes over if advertisements stop.
  HSRP     Cisco's equivalent, functionally similar.
  GLBP     shares load across both, rather than one idling.

  The virtual MAC matters: when the backup takes over it
  answers to the SAME MAC address, so hosts do not need to
  re-ARP and switches do not need to relearn. Failover is
  invisible to the host, which is the whole point.

TIMERS
  VRRP defaults to a 1-second advertisement and a 3-second
  down interval, so a plain failover takes about 3 seconds.
  That is a long pause for voice and unremarkable for most
  other things. Sub-second timers work; better still, tie
  the group to a reachability check.

TRACKING — the part people leave out
  Without it, the master keeps the virtual address even when
  its UPLINK has failed. Hosts happily send traffic to a
  gateway that cannot forward it anywhere, while a perfectly
  healthy backup sits idle. Configure the group to track the
  uplink and decrement its priority when it goes, so the
  backup takes over.

  This is the most common first-hop redundancy defect and it
  is invisible until the exact failure it exists for.

AND THE ALTERNATIVE THAT AVOIDS ALL OF IT
  A layer-3 access design or an anycast gateway gives every
  switch the same gateway address, so there is no election
  and nothing to fail over.                          → ch 5

18.2The convergence budget

How long the user actually waits

Each layer detects the failure independently, and the delays add up rather than overlapping.

Convergence is measured at the application, not at the protocol

A routing protocol reporting sub-second reconvergence is telling you when it finished, not when the user's session recovered. Between those two moments sit several other clocks that nobody configured together: the first-hop redundancy group deciding to move the gateway, a stateful firewall discovering it has no entry for an established connection and resetting it, TCP waiting out a retransmission timer that doubles on each attempt, a connection pool marking a backend dead and waiting before retrying, and the application's own retry interval. Each is reasonable alone and they add rather than overlap, because each layer only starts its clock once the one below has given up. That is why a network that converges in 400 milliseconds can produce a thirty-second outage for a database-backed application, and why the number worth measuring during a failover test is time to a working transaction rather than time to a route in the table.

18.3When redundancy makes things worse

Two devices, honestly modelled

A pair helps only if the failover works and the mechanism does not cause its own outages.

The failure modes redundancy introduces

Every pairing mechanism adds ways to fail that a single device did not have. Split brain is the worst: the two members lose contact with each other while both remain up, so both believe they are active, both claim the virtual address, and the resulting duplicate addressing and asymmetric flows are far more disruptive than a clean failure. Configuration divergence is the most common: the pair drifts apart because a change was applied to one member during an incident, so the failover reveals a device configured for a network that no longer exists. Shared bugs defeat redundancy entirely, because identical devices running identical software hit the same defect at the same moment — which is the argument for staggering upgrades rather than applying them to both members together. And a pair is more complex to reason about, so changes carry more risk and are made less often, which has its own cost. None of this argues against redundancy; it argues for treating the mechanism as a component that needs testing rather than as an assurance that comes free with the second chassis.

Design principles that hold across every layer 
PREFER MECHANISMS WITH NOTHING TO FAIL OVER
  Equal-cost paths where both forward, link aggregation, an
  anycast gateway, a layer-3 access design. A mechanism that
  is always in use is a mechanism that is always tested; a
  standby path is exercised for the first time during an
  incident.                                       → ch 5, 6

MAKE THE FAILURE VISIBLE
  A redundant system that has silently lost a member is a
  single system that everyone believes is redundant. Alert
  on degraded state as urgently as on outage — this is the
  single most commonly missing alarm.

DECIDE PREEMPTION DELIBERATELY
  Should the primary take back over when it returns? Yes
  means a second interruption and a predictable topology.
  No means you stay on the backup until someone acts, and
  the primary's recovery is not a customer-visible event.
  For most networks, no preemption plus an alert is better.

STAGGER UPGRADES ACROSS A PAIR
  Identical software fails identically. Upgrading one member
  and waiting turns a shared defect from an outage into a
  failover.

BOUND THE BLAST RADIUS BEFORE ADDING REDUNDANCY
  Two core switches that carry every VLAN in the building
  are a large failure domain made slightly more reliable.
  Several smaller independent domains frequently deliver
  more availability than a redundant large one, and cost
  less.

AND THE UNCOMFORTABLE ONE
  Count the failure modes you have added and be willing to
  conclude that a simple single device with a spare on the
  shelf is the better answer for a small site.
The network reconverges in 400 ms but users report a 30-second outage. Explain.

Because the routing protocol's figure measures when it finished, and several other clocks start only after it does. The layers stack rather than overlap, since each one waits for the one below to give up before beginning its own recovery. Walk it through: the link fails and detection takes some interval; the first-hop redundancy group waits out its own hold time before moving the gateway; the routing protocol reconverges — the 400 ms being quoted; a stateful firewall in the path now receives packets for connections it has no entry for and sends resets, so every established session must be rebuilt; TCP waits out a retransmission timeout that doubles on each attempt; the application's connection pool marks the backend dead and waits a fixed interval before retrying, which is frequently five to thirty seconds and is the term that dominates here; and the application's own retry logic adds another interval on top. Thirty seconds is entirely consistent with a network that did its part in under half a second. Three things follow. Measure at the application: during a failover test, the number to record is time to a successful transaction, not time to a route appearing in the table, and the gap between those two is where the work is. State synchronisation on stateful devices removes one of the largest terms, because established connections survive the failover rather than being reset — and it is worth verifying it actually works, since it is frequently configured and rarely tested. And tune the application side, since a connection pool with a ten-second dead-backend timer will dominate any network improvement you make; that conversation belongs with the application team and is usually more productive than further network tuning.

When is a redundant pair worse than a single device?

When the failover is unreliable, or when the pairing mechanism causes outages of its own at a rate that exceeds the failures it prevents. The arithmetic is more brutal than intuition suggests. A pair fails if both members fail, or if one fails and the failover does not work, or if the pairing mechanism itself causes an outage — and only the first of those is the one people model. At 99% per-device availability, a pair with perfect failover and no mechanism risk gives about an hour of downtime a year against eighty-eight for a single device, which is the case everyone imagines. Introduce a failover that works only nine times in ten and it rises to eighteen hours; add a mechanism that causes an outage in one year in fifty and it passes the single device entirely. With a failover that works half the time, any mechanism risk at all makes the pair worse. The mechanism risks are concrete rather than theoretical: split brain when the members lose contact but both stay up, so both claim the virtual address; configuration divergence, where a change applied to one member during an incident is discovered during the next failover; and shared bugs, where identical software fails identically and redundancy provides nothing. What to do rather than abandoning redundancy. Test the failover, by pulling power rather than shutting down gracefully, under load, and specifically by breaking the uplink rather than the device — that last one finds missing interface tracking, which is the commonest defect. Stagger upgrades so a shared defect becomes a failover instead of an outage. Alert on degraded state, because a pair that silently lost a member is a single device everyone believes is redundant. And for a small site, seriously consider one device and a configured spare on the shelf.

Why is interface tracking the most commonly missing piece of first-hop redundancy?

Because without it the mechanism protects against the failure that is easy to imagine and not against the one that actually happens more often. First-hop redundancy exists so that hosts on a segment are not stranded when their gateway dies, and the default configuration handles exactly that: the master stops sending advertisements, the backup notices and takes over the virtual address and virtual MAC, and hosts continue without re-ARPing. But a router failing entirely is not the common case. What happens far more often is that the router stays perfectly healthy while its uplink fails — a circuit goes down, an upstream device fails, a routing adjacency drops. The master is still running, still sending advertisements, still holding the virtual address, and hosts happily send it traffic that it now has nowhere to forward. Meanwhile the backup, whose uplink is fine, sits idle because it can still hear the master. The result is a complete outage for the segment with both routers up and no alarm from the redundancy protocol, which is exactly the scenario it was bought to prevent. The fix is tracking: configure the group to monitor the uplink interface — or better, a reachability check to something beyond it — and decrement the master's priority when it fails, so the backup's priority becomes higher and it takes over. Two refinements worth adding. Track reachability rather than interface state where you can, because an interface that is up while black-holing traffic is the failure that link state misses entirely, the same argument as BFD in Chapter 7. And make sure the decrement is large enough to actually invert the priorities, which is a small arithmetic error that silently disables the whole thing.

Recap

  1. A shared virtual MAC is what makes gateway failover invisible — no re-ARP, no relearning.
  2. Interface tracking is the most commonly missing piece, and without it the master strands the segment.
  3. Track reachability rather than interface state where you can.
  4. Convergence terms add rather than overlap, because each layer waits for the one below to give up.
  5. Measure time to a working transaction, not time to a route in the table.
  6. A connection pool's dead-backend timer can dominate everything the network does.
  7. A pair fails if both fail, or failover does not work, or the mechanism causes an outage.
  8. Split brain, configuration divergence and shared bugs are the mechanism's own failure modes.
  9. Prefer mechanisms with nothing to fail over. A path always in use is always tested.
  10. Alert on degraded state. A pair that quietly lost a member is a single device nobody knows about.
