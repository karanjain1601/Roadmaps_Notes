Network automation

Automation is usually sold as saving time, and the time saving is the smaller half of the benefit. The larger half is that a generated configuration is consistent, reviewable and reversible — which removes a whole category of outage that manual work produces reliably.

~28 min read Source of truth · idempotency · testing · intent 2 interactive panels Prerequisite: chapters 4, 16

21.1Start with the source of truth

The thing to build before any scripts 
THE MISTAKE is to start by scripting the commands you type.
That gives you a faster way to make the same mistakes, on
more devices, at once.

START INSTEAD WITH DATA: a structured description of what
the network should be.

  site: manchester
    address_block: 10.24.0.0/16
    vlans:
      - {id: 10, name: users,      subnet: 10.24.0.0/22}
      - {id: 20, name: voice,      subnet: 10.24.4.0/23}
      - {id: 99, name: management, subnet: 10.24.255.0/24}
    uplinks:
      - {to: core-1, port: Te1/1/1}
      - {to: core-2, port: Te1/1/2}

FROM THAT DATA YOU CAN GENERATE
  · device configuration, per platform
  · DNS and DHCP scopes                        → ch 11
  · monitoring targets and thresholds          → ch 19
  · firewall rules between segments            → ch 16
  · the documentation, which is now correct by
    construction rather than by discipline

  Every one of those is a place the network drifts from its
  own description today, and the drift is what makes an
  outage take three hours instead of twenty minutes.

THE TEST OF WHETHER YOU HAVE ONE
  Add a site. If that means editing configuration on twelve
  devices, three spreadsheets, a DHCP server and a
  monitoring system by hand, you have twelve sources of
  truth and no source of truth.

AND THE UNCOMFORTABLE FIRST STEP
  Reconcile what you think is deployed against what is
  actually deployed. The gap is always larger than expected,
  and finding it is most of the value.        → ch 11

21.2Does it pay?

Automation payback

Break-even is a fixed number of device-changes, so estate size decides how quickly it arrives.

A third of the benefit is not the typing

The business case usually gets written as minutes saved per change, and that undersells it. A generated configuration is identical across every device that should be identical, which eliminates the drift that makes troubleshooting slow; it is reviewable before it is applied, so a second person can catch the mistake; and it is reversible, because the previous state is in version control rather than in somebody's scrollback. Those properties reduce the rate at which changes cause incidents, and at realistic figures — a few percent of manual changes going wrong, several hours to resolve each — the avoided incidents are roughly a third of the total benefit. That also explains why automating a small estate can still be worth it even when the time arithmetic says otherwise: five devices configured consistently and changed safely is worth something that five devices configured by hand is not.

21.3Idempotency on equipment that resists it

The hard part, and it is not the connection 
IDEMPOTENT means running it twice leaves the same result as
running it once. Most modern tooling assumes this and most
network equipment makes it awkward.

THE PROBLEM
  Sending "ip route 10.0.0.0/8 10.1.1.1" twice is harmless.
  Removing a route that should no longer exist requires
  knowing it is there — and a command-line interface has no
  concept of "make the configuration match this document".

THREE APPROACHES, IN ASCENDING ORDER OF SAFETY

  1  COMMAND PUSH        send lines, hope
     Fast to write, and it can only ADD. Configuration
     accumulates and never gets cleaned up, so devices drift
     apart in ways nothing detects.

  2  DECLARATIVE MODULES  the tooling reads current state,
     computes the difference, applies only that
     Much better, and coverage is uneven — the module for
     the feature you need may not exist on your platform.

  3  FULL CONFIGURATION REPLACE
     Generate the entire configuration and replace it
     atomically. Genuinely idempotent, genuinely
     terrifying the first time, and the only approach
     that removes what should not be there.
     Needs a platform that supports candidate configurations
     and commit-confirm.

COMMIT-CONFIRM IS THE FEATURE THAT MATTERS
  Apply a configuration with a timer. If you do not confirm
  within it — because you just cut off your own access —
  the device rolls back automatically.

  This turns the worst outcome of a remote change from a
  drive to a data centre into a two-minute wait. If your
  platform has it, use it for everything; if it does not,
  a scheduled rollback job is a workable substitute.

THE STATE THAT IS NOT IN THE CONFIGURATION
  Interface counters, ARP entries, routing tables, licences,
  the software version. A tool that manages configuration
  does not manage these, and they matter.

21.4Making a change safely

Which guardrails catch what

Each one intercepts a different class of mistake, and they are not interchangeable.

Automation makes a mistake faster and wider

The reason to be careful is not that automated changes are more likely to be wrong — they are considerably less likely — but that when one is wrong it is applied consistently to every device in scope within seconds, and a human making the same mistake by hand would probably have noticed after the second or third. So the failure mode shifts from many small inconsistent errors to one large uniform one. Everything in the panel above exists to address that: a canary deployment bounds the blast radius to one device, commit-confirm bounds it in time, and post-change verification catches the case where the configuration applied cleanly and the network stopped working anyway. The specific danger to plan for is locking yourself out, since a management-plane mistake removes the means of fixing it — which is why out-of-band access is a prerequisite for automation rather than an optional extra, and why the first automated change should never be to the management network.

Where should you start with network automation?

With reading rather than writing, and with data rather than scripts. The instinct is to script the commands you currently type, and that produces a faster way to make the same mistakes on more devices simultaneously — the failure mode the note above describes. Two better starting points, in order. First, collect and reconcile: gather the running configuration from every device, put it in version control, and diff it daily. This is read-only, so it cannot break anything, and it delivers value immediately — you discover configuration drift, undocumented changes, devices nobody knew were there, and the gap between your documentation and reality. That gap is always larger than expected and finding it is most of the initial value; it also gives you the "what changed?" answer from Chapter 20 for free. Second, build a source of truth: a structured description of what the network should be — sites, address blocks, VLANs, links, roles — from which you can generate device configuration, DHCP scopes, DNS records, monitoring targets and firewall rules. The test of whether you have one is whether adding a site means editing one data file or twelve devices and three spreadsheets. Only then start writing changes, and start somewhere low-risk and repetitive: a new access switch built from a template, or a VLAN added consistently across a site. Two prerequisites worth having before any of it. Out-of-band access to every device, because a management-plane mistake removes the means of fixing it. And commit-confirm where the platform supports it, which turns the worst outcome of a remote change into a two-minute wait.

Why is idempotency hard on network equipment?

Because a command-line interface has no concept of "make the configuration match this document" — it accepts instructions to add and remove individual lines, and it cannot be told what the complete desired state is. Sending the same command twice is generally harmless, so adding is idempotent by accident. The problem is removal: to delete a route, an access-list entry or a VLAN that should no longer exist, the tooling must first know that it is there, which means reading and parsing the current configuration and computing a difference. Configuration formats vary by vendor, by platform and by software version, and parsing them reliably is more work than it sounds. The consequence in practice is accumulation: command-push automation only ever adds, so devices collect configuration that nobody intended and nothing detects, and they drift apart in ways that make troubleshooting slow. Three approaches address it with increasing safety. Declarative modules in the tooling read current state and apply only the difference, which works well where the module for your feature and platform exists — coverage is the limitation. Full configuration replace generates the entire configuration and applies it atomically, which is genuinely idempotent and the only approach that removes what should not be there; it needs a platform supporting candidate configurations and it is alarming the first time. And commit-confirm, which does not provide idempotency but makes pursuing it survivable, since a configuration that cuts off your own access rolls back on a timer. Worth remembering the limit of all of it: interface counters, ARP tables, routing state, licences and software versions are not in the configuration, so a tool that manages configuration does not manage them.

Which guardrail is worth the most, if you can only have one?

Deploying to one device first, because it is the only guardrail that bounds the blast radius of a mistake nothing else caught. Every other control catches a specific class of error: linting finds syntax, peer review finds intent and logic, a lab finds behaviour under a modelled topology, and post-change tests find the case where the configuration applied cleanly and the network stopped working. All are worth having and all can miss something, because the thing that gets you is by definition the thing you did not think to check. A canary deployment does not care what the mistake was — it limits it to one device, where you find out before the other two hundred are affected. That property is what makes it the highest-value single control, and it directly addresses automation's characteristic failure mode: not being more error-prone than manual work but applying one uniform error everywhere within seconds. Two close seconds worth arguing for. Commit-confirm bounds the damage in time rather than in scope, and it specifically covers the worst case — a change that removes your own access, which is otherwise a drive to a data centre. And post-change verification is the only control that checks the outcome rather than the change, catching the case where every device accepted the configuration and the network is nonetheless broken, which happens more than people expect because a syntactically perfect configuration can be semantically wrong. If forced to rank a starter set: canary, then commit-confirm, then post-change tests, then review, then lint, then the lab — the lab last only because it is the most expensive to build and maintain accurately, not because it is least useful.

Recap

  1. Start with data, not scripts. Scripting what you type is a faster way to make the same mistakes.
  2. Start read-only — collect configurations, version them, diff them daily. It cannot break anything.
  3. The gap between documentation and reality is the first thing you find, and most of the initial value.
  4. One source of truth generates configuration, DHCP, DNS, monitoring and firewall rules.
  5. Break-even is a fixed number of device-changes, so a large estate reaches it almost immediately.
  6. Around a third of the benefit is avoided incidents, not saved keystrokes.
  7. Command push can only add, so configuration accumulates and devices drift apart.
  8. Commit-confirm turns a lockout into a two-minute wait. Use it for everything.
  9. Automation applies one uniform mistake everywhere in seconds. Canary first.
  10. Out-of-band access is a prerequisite, and the management network is the last thing to automate.
