TCP and UDP

Everything below this layer moves packets. TCP is what turns an unreliable stream of independently-routed packets into something an application can treat as a pipe — and understanding how it does that explains most of the performance complaints you will be handed.

The real distinction is what a retransmission is worth

"TCP is reliable and UDP is not" is the textbook line and it obscures the engineering decision. A retransmitted packet arrives one round trip later. For a file transfer that is fine — the bytes are correct and slightly late. For a voice call it is useless: the moment that audio should have been played has passed, and playing it now would be worse than the small gap the codec conceals. So real-time protocols choose UDP not because they tolerate loss but because retransmission cannot help them, and they would rather spend that effort on forward error correction or concealment. The same reasoning explains DNS: a query and a response fit in one packet each, so a lost query is retried by the application at the cost of one round trip, while establishing a connection would have cost one round trip before the query even started.

9.3Why a fast link can be slow

The throughput ceiling of a single flow

Three separate limits. The link rate is frequently not the binding one.

On a long path, a loss rate too small to notice destroys throughput

Loss-based congestion control treats every lost packet as a signal that the network is congested, so it halves its window and climbs back slowly. The steady-state result is captured by the Mathis relationship: throughput is roughly the segment size divided by the round-trip time times the square root of the loss rate. Two consequences follow that people find hard to believe. Loss hurts far more on long paths, because recovery takes round trips and there are more of them per second on a short path — the same 0.01% loss that costs you nothing across a data centre caps a transatlantic flow at around 15 Mbps. And the link rate does not appear in the formula at all, so upgrading a 1 Gbps circuit to 10 Gbps changes nothing whatsoever for a flow limited this way. When someone reports that an expensive international link performs like a domestic broadband connection, this is nearly always why, and the diagnosis is to measure loss at fractions of a percent rather than to look at utilisation graphs.

9.4Congestion control, and which one you are running

The algorithms you will meet
AlgorithmSignalBehaviour
RenoLossThe classic. Halve on loss, increase by one segment per round trip. Too timid for modern links
CUBICLossThe common default on Linux and Windows. Grows as a cubic function of time since the last loss, so it recovers far faster on high-bandwidth long paths
BBRMeasured bandwidth and round-trip timeModels the path rather than waiting for loss, so it is not fooled by deep buffers or by random loss. Much better on lossy long paths, and it can be aggressive toward loss-based flows sharing a link
ECNAn explicit mark from the routerNot an algorithm but a signal: the router marks a packet instead of dropping it, so congestion is communicated without loss. Needs support at both ends and in the middle
The phases, and what each one is doing 
SLOW START           not slow — exponential
  Congestion window starts around 10 segments and DOUBLES
  every round trip. It is called slow only relative to the
  original behaviour of sending everything at once.

  The consequence is a ramp: filling a 1 Gbps, 80 ms path
  takes about 9 round trips, which is roughly 750 ms of
  not going at full speed. Short transfers therefore never
  reach the link rate at all, which is why a page of small
  objects performs so differently from one big file.

CONGESTION AVOIDANCE  linear, cautious
  After the first loss, growth becomes additive — roughly
  one segment per round trip for Reno, a cubic curve for
  CUBIC — so recovery from a loss event is slow on a long
  path.

FAST RETRANSMIT / FAST RECOVERY
  Three duplicate acknowledgements mean a segment is missing
  but later ones arrived, so the path is still working.
  Retransmit immediately rather than waiting for a timeout.

TIMEOUT — the expensive case
  No acknowledgement at all. The sender assumes serious
  trouble, drops the window to one segment, and re-enters
  slow start. A single timeout on a long path costs far more
  than the packet it lost, and the retransmission timer
  doubles on each successive failure.

SELECTIVE ACKNOWLEDGEMENT (SACK)
  Lets the receiver say exactly which segments arrived, so
  the sender retransmits only what is missing rather than
  everything after the gap. Essentially always on, and
  worth checking is not being stripped by a middlebox.

A 1 Gbps international link tests at 15 Mbps for a single transfer. What is wrong?

Almost certainly a small amount of packet loss interacting with the long round-trip time, and possibly a receive window too small for the path. Work through the three ceilings in order. First, the window limit: throughput cannot exceed the window divided by the round-trip time, so a 64 KB window on an 80 ms path caps a flow at 6.6 Mbps no matter what the link does — check that window scaling is negotiated and not being stripped by a middlebox, which some older firewalls do. Second, the loss limit, which is the usual answer at these numbers: loss-based congestion control gives throughput of roughly the segment size over the round-trip time times the square root of the loss rate, so 0.01% loss on an 80 ms path lands almost exactly at 15 Mbps. That is a loss rate invisible on any utilisation graph and unremarkable on a ping test, which is why it goes undiagnosed — you have to measure it explicitly over a large sample. Third, the link rate, which at these figures is nowhere near binding. The critical thing to explain to whoever is about to buy more bandwidth: the link rate does not appear in the loss formula at all, so upgrading to 10 Gbps changes nothing. What actually helps: find and fix the loss, which is often a single congested interface, a marginal optic, or an overly aggressive policer on the provider circuit; verify window scaling and selective acknowledgement survive the path; use parallel connections as a workaround, since n flows get roughly n times the throughput; and consider BBR, which models the path rather than treating every loss as congestion and performs dramatically better on exactly this profile.

Why does a page of many small files behave so differently from one large file?

Because small transfers live entirely in the part of TCP's behaviour that is not yet at full speed, and they pay the setup costs repeatedly. Three effects compound. Slow start never finishes: the congestion window begins at about ten segments and doubles each round trip, so filling a 1 Gbps, 80 ms path takes around nine round trips — three-quarters of a second. A 20 KB object completes in one or two round trips, entirely within the ramp, so it never sees anything like the link rate and the measured throughput is a function of round-trip time rather than bandwidth. Connection setup is paid per connection: a TCP handshake plus a TLS handshake is two or three round trips before the first byte, which at 80 ms is 160–240 ms of pure latency per new connection. And if the requests are sequential, every one of them costs a full round trip minimum, so two hundred small requests take at least sixteen seconds regardless of bandwidth — which is an application architecture problem that presents as a network complaint. The mitigations are all about amortising or removing round trips rather than adding capacity: connection reuse so the handshake and the ramp are paid once and subsequent requests inherit a warmed-up window; multiplexing so requests are concurrent rather than sequential; TLS session resumption to remove a round trip from repeat connections; and moving content closer, since halving the round-trip time halves every one of these costs simultaneously. QUIC helps meaningfully here too, combining the transport and cryptographic handshakes into one round trip and removing head-of-line blocking between streams.

Thousands of sockets are in TIME_WAIT on a server. Is that a problem?

Usually not — it is normal and expected on any server handling many short-lived connections, and it is frequently misdiagnosed as a leak. When a connection closes, the side that closed first holds the socket in TIME_WAIT for roughly twice the maximum segment lifetime, commonly sixty seconds. The purpose is correctness: a delayed duplicate packet from the old connection could otherwise arrive during a new connection using the same four-tuple and be accepted as valid data. So the state is doing real work, and a server closing ten thousand connections a minute will legitimately hold hundreds of thousands of sockets in it. It becomes an actual problem in one specific case: when the machine is the one initiating connections — a proxy, a load balancer, or an application calling a backend — and it exhausts the ephemeral port range toward a single destination address and port, at which point new connections fail. The four-tuple must be unique, so the ceiling is roughly the size of the ephemeral range per destination, typically around 28,000. The right fixes address the cause rather than the symptom: connection reuse with keep-alive or a connection pool, which removes the churn entirely and is almost always the correct answer; widening the ephemeral port range; and adding destination addresses so the four-tuple space is larger. The tempting fixes are worse than they look — shortening the timeout weakens the protection it exists for, and enabling aggressive socket reuse options has historically caused subtle failures behind network address translation. If the machine is only accepting connections and the peer closes first, the peer holds TIME_WAIT and there is nothing to fix.

Recap

  1. Real-time protocols choose UDP because retransmission cannot help them, not because loss is fine.
  2. A reset means nothing is listening; silence means something dropped it. The best transport signal there is.
  3. TIME_WAIT is normal. It matters only when the initiating side exhausts ephemeral ports.
  4. Throughput is window over round-trip time whenever the window is below the bandwidth-delay product.
  5. Slow start needs about nine round trips to fill a 1 Gbps, 80 ms path. Short transfers never get there.
  6. Loss hurts in proportion to round-trip time — 0.01% caps a transatlantic flow near 15 Mbps.
  7. The link rate does not appear in the loss formula, so a bigger circuit changes nothing.
  8. Parallel connections multiply a window-limited or loss-limited flow — which is why transfer tools use them.
  9. BBR models the path instead of trusting loss, and is dramatically better on long lossy links.
  10. QUIC encrypts the transport headers, so mid-path performance troubleshooting largely stops working.
