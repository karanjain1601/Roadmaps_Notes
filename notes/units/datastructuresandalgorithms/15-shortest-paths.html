Shortest paths

Add weights to the edges and BFS stops working, because fewest hops is no longer cheapest. The replacement is a greedy algorithm resting on one assumption — that costs never decrease as you go — and most of this chapter is about what happens when that assumption fails.

— words— min read2 interactivesNeeds: chapters 13, 14

Dijkstra's algorithm

Explore vertices in order of distance from the source rather than in order of hops. A priority queue supplies the closest unfinalised vertex; taking it out settles its distance forever.

Why the greedy step is safe

When the closest unfinalised vertex comes off the queue, no shorter route to it can still exist. Any alternative route would have to pass through some other unfinalised vertex, which is by definition at least as far away — and since every edge costs zero or more, going through it and continuing can only cost more. That argument is the whole correctness proof, and it collapses the moment an edge can be negative.

Dijkstra, step by step
Distances tighten; the queue always yields the nearest
python — with lazy deletion, the form everyone actually writes
import heapq

def dijkstra(g, src):                     # g[u] = [(v, weight), …]
    dist = {src: 0}
    prev = {}
    done = set()
    pq = [(0, src)]

    while pq:
        d, u = heapq.heappop(pq)
        if u in done:                       # a stale entry — skip it.
            continue                        # this is the lazy-deletion trick
        done.add(u)                          # u's distance is now final

        for v, w in g[u]:
            nd = d + w
            if nd < dist.get(v, float("inf")):   # "relaxing" the edge
                dist[v] = nd
                prev[v] = u
                heapq.heappush(pq, (nd, v))  # push a duplicate rather than
    return dist, prev                        # decreasing a key in place

def path_to(prev, src, dst):                 # reconstruct by walking backwards
    out = [dst]
    while out[-1] != src:
        out.append(prev[out[-1]])
    return out[::-1]

# O((V + E) log V) with a binary heap — the log comes from the queue
Two implementation details worth knowing

Lazy deletion. A binary heap cannot lower an existing entry's priority — chapter 13's decrease-key problem. So instead of updating, push a second entry with the better distance and ignore any entry for a vertex already finalised. The queue can grow to O(E) rather than O(V), which is a memory cost, not a correctness one.

Stop early if you only need one target. Once the destination comes off the queue its distance is final; there is no need to finish. On a road network that often halves the work.

What negative edges do

Dijkstra does not detect the problem, refuse to run, or produce an obviously wrong answer. It returns a plausible number that is simply too large.

One negative edge
Four vertices are enough to break it
python — Bellman-Ford
def bellman_ford(vertices, edges, src):    # edges = [(u, v, w), …]
    dist = {v: float("inf") for v in vertices}
    dist[src] = 0

    for _ in range(len(vertices) - 1):     # V−1 rounds is always enough:
        changed = False                     # a shortest path has at most V−1 edges
        for u, v, w in edges:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                changed = True
        if not changed:                     # early exit — usually far sooner than V−1
            break

    for u, v, w in edges:                 # one extra round: anything that still
        if dist[u] + w < dist[v]:          # improves is reachable from a
            raise ValueError("negative cycle")  # negative cycle
    return dist                            # O(V·E)
Negative cycles

If a cycle's total weight is negative, going round it again always lowers the cost, so no shortest path exists — the answer is negative infinity. Bellman-Ford detects this by running one round beyond the V−1 it needs: if anything still improves, some vertex is reachable from a negative cycle. This is not a curiosity. Currency arbitrage is exactly the detection of a negative cycle in a graph of exchange rates with logarithmic weights.

A*

Dijkstra explores outward in every direction. If you know roughly where the target is, that is wasteful — A* adds an estimate of the remaining distance and explores toward the goal instead.

$$f(n) = \underbrace{g(n)}_{\text{cost so far}} + \underbrace{h(n)}_{\text{estimated cost remaining}}$$
Admissible
The heuristic must never overestimate. Straight-line distance is admissible for road networks because no route is shorter than flying. An overestimate makes A* fast and wrong.
Consistent
Stronger: h(u) ≤ cost(u,v) + h(v) for every edge. Guarantees that a vertex is never reopened, which is what makes A* behave like Dijkstra with a shifted priority.
The two extremes
With h = 0, A* is Dijkstra. With a perfect heuristic it walks straight to the target. Everything useful is in between, and the quality of the heuristic is the entire performance story.
Practical notes
  • Reconstruct paths from a predecessor map, not by storing whole paths in the queue — that turns O(V) memory into O(V²).
  • Bidirectional search from both ends roughly square-roots the explored area on large graphs.
  • Real routing engines do not run Dijkstra at query time; they precompute contraction hierarchies so a continent-scale query takes microseconds.
  • Turn a maximising problem into a minimising one by negating weights — but only if the graph is a DAG, since Dijkstra cannot handle the negatives that creates.

Self-check

  1. Why does BFS fail on a weighted graph?
    Because it explores in order of edge count, so the first time it reaches a vertex it has used the fewest hops — which is not the same as the lowest cost once edges differ. A single edge of weight 10 beats three of weight 1 in hop count and loses on cost. Dijkstra fixes this by ordering exploration by accumulated cost rather than hops, which is exactly what the priority queue provides.
  2. Explain in one sentence why Dijkstra's greedy choice is correct.
    The nearest unfinalised vertex cannot be reached more cheaply later, because any alternative route would have to pass through another unfinalised vertex that is already at least as far away, and non-negative edges mean continuing from there can only add cost. Every word of that depends on weights being non-negative, which is precisely why one negative edge invalidates it.
  3. Dijkstra returns a distance of 2 where the true distance is 1. What happened?
    A negative edge. The vertex was finalised at 2 before a cheaper route through a more distant vertex was discovered — and once finalised, Dijkstra never revisits it. The failure is silent: no error, no warning, just a number that is too large. Bellman-Ford relaxes every edge repeatedly instead of finalising anything, so later improvements still propagate. The demo shows this on four vertices.
  4. Why does Bellman-Ford run exactly V−1 rounds?
    Because a shortest path can contain at most V−1 edges — any more and it would repeat a vertex, which only helps if the cycle is negative, in which case no shortest path exists. Each round guarantees that all shortest paths of one more edge have been found, so V−1 rounds cover the longest possible. A V-th round that still improves something proves a negative cycle is reachable.
  5. What must a heuristic satisfy for A* to be correct, and what happens otherwise?
    It must be admissible: never overestimate the remaining cost. If it overestimates, A* may finalise a vertex through a route that looked cheap because the true remaining cost was underrated elsewhere, and return a suboptimal path. It will still return quickly, and still return an answer — which is why inadmissible heuristics are sometimes used deliberately when a good-enough path fast beats an optimal path slowly.
  6. You need the shortest path between all pairs in a 200-vertex graph. Which algorithm?
    Floyd-Warshall: 200³ is eight million operations, trivial, and the implementation is three nested loops. Running Dijkstra from every vertex is O(V·(V+E) log V), which can be faster on a sparse graph but takes far more code. With 200 vertices the constant factors and simplicity decide it. Floyd-Warshall also handles negative edges, which repeated Dijkstra does not.
