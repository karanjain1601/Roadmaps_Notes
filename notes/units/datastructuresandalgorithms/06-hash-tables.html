Chapter 06 · Linear structures

Hash tables

The structure that makes more problems tractable than any other. It converts a key into an array index by computing on it — and everything difficult about hash tables follows from the fact that two different keys will sometimes compute the same index.

— words— min read2 interactivesNeeds: chapters 02, 03

The idea

Arrays give O(1) access by position. Hash tables give O(1) access by key, by computing the position from the key.

$$\text{index} = \text{hash}(\text{key}) \bmod m$$

Store the key at that index; to look it up, recompute the same index and go straight there. No searching, no comparisons — one computation and one array access, regardless of how many entries the table holds.

A good hash function isBecause
DeterministicThe same key must always produce the same index, or you can never find anything again
UniformKeys should spread evenly across the table. Clumping is what turns O(1) into O(n)
FastIt runs on every single operation. A slow hash destroys the point
AvalanchingChanging one bit of the key should change roughly half the bits of the output, so similar keys land far apart

It does not need to be cryptographic. SHA-256 is an excellent hash and a terrible choice here — far too slow. Real tables use fast non-cryptographic functions such as SipHash, MurmurHash or FNV.

Collisions are not a flaw, they are arithmetic

There are infinitely many possible keys and only m slots, so by the pigeonhole principle some keys must share an index. Worse, they arrive far sooner than intuition suggests: the birthday paradox means a table of 365 slots has a 50% chance of a collision after just 23 insertions. Collision handling is therefore not an edge case bolted on — it is half the design.

Resolving collisions

Two strategies, same keys
Watch where the probes go

Separate chaining

Each slot holds a small collection — usually a linked list — of every entry that hashed there. Insertion appends to the list; lookup hashes, then scans that one list.

Advantage
Simple, tolerates load factors above 1, and deletion is trivial — just unlink the node.
Cost
A pointer per entry plus allocator overhead, and chasing those pointers means poor cache behaviour. Java's HashMap converts long chains into red-black trees to bound the worst case at O(log n).

Open addressing

Every entry lives in the table itself. On a collision, probe for another slot by a fixed rule until an empty one appears.

Probe sequenceNext slotBehaviour
Lineari + 1, i + 2, i + 3 …Excellent cache locality
Quadratici + 1, i + 4, i + 9 …Breaks up clusters; can fail to visit every slot
Double hashingi + k·h₂(key)Each key gets its own stride, so clusters do not form
Primary clustering, and the deletion problem

Clustering. Linear probing builds runs of occupied slots, and every new key landing anywhere in a run must traverse the whole thing. Worse, runs merge, so they grow faster than linearly with the load factor. Double hashing avoids this by giving each key a different step size — which is why it degrades more gracefully at high load, at the cost of the cache locality linear probing enjoys.

Deletion. You cannot simply empty a slot in an open-addressed table: doing so breaks the probe chain, and every key that probed past that slot becomes unreachable. The fix is a tombstone — a marker meaning "occupied for probing, free for insertion". Tombstones accumulate and slow lookups, so tables that delete heavily must periodically rehash.

Load factor and resizing

$$\alpha = \frac{n \text{ entries}}{m \text{ slots}}$$

The load factor is the single number that governs performance. Expected probes per operation depend only on α, not on n — which is why the table stays O(1) as it grows, provided α is kept bounded. That is what resizing is for: when α crosses a threshold, allocate a larger table and rehash everything into it.

What a key has to be

# keys must be hashable, which in practice means immutable
d = {}
d[(1, 2)] = "ok"          # tuple — fine
d[[1, 2]] = "boom"        # TypeError: unhashable type: 'list'

# the reason: mutate a key and its hash changes, so the entry is
# stranded in a bucket the lookup will never visit again

# ── the contract, for your own classes ──
# if a == b then hash(a) == hash(b).   The converse need not hold.

class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, o):    return (self.x, self.y) == (o.x, o.y)
    def __hash__(self):     return hash((self.x, self.y))   # derive from the same fields

# defining __eq__ without __hash__ makes the class unhashable in Python 3 —
# deliberately, because the alternative is silent, unfindable entries

# the easy way
from dataclasses import dataclass
@dataclass(frozen=True)
class Point:
    x: int
    y: int                            # __eq__ and __hash__ generated, and immutable

def two_sum(nums, target):
    seen = {}                                  # value → index
    for i, x in enumerate(nums):
        if target - x in seen:
            return seen[target - x], i
        seen[x] = i

Python's dict, specifically
  • Insertion order is preserved since 3.7, and it is a language guarantee, not an implementation detail. Do not rely on any other ordering.
  • Open addressing, with a compact array of entries and a separate index array — which is why dicts got both faster and smaller in 3.6.
  • String hashing is randomised per process, so hash("a") differs between runs. That is a security feature; never persist a hash value.
  • Sets are the same machinery without values. Use a set when you only need membership — it is smaller and clearer.

Self-check

  1. Why can't you delete from an open-addressed table by emptying the slot?
    Because the probe sequence would break. Any key that originally collided and probed past that slot is found by walking from its home position until an empty slot appears — emptying a slot in the middle makes the walk stop early, so those keys become unreachable even though they are still stored. The fix is a tombstone marking the slot as "occupied for probing, free for insertion". Chaining has no such problem, which is one reason it is simpler.
  2. Your hash table's operations have degraded to O(n). Name three possible causes.
    A poor or adversarial hash sending many keys to the same slot; a load factor allowed to climb toward 1 without resizing; and tombstone accumulation from heavy deletion. Two more worth checking: an expensive __eq__ making each probe costly, and a custom __hash__ that ignores most of the key's fields. Adversarial collisions are a genuine denial-of-service vector when keys come from user input, which is why modern runtimes randomise the hash seed per process.
  3. Why must dictionary keys be immutable?
    Because the slot is chosen from the hash at insertion time. If the key mutates, its hash changes, and a lookup computes a different index — the entry is stranded in a bucket no search will ever visit. It is still there, consuming memory, and unreachable. Python enforces this by making mutable built-ins unhashable rather than allowing the silent corruption.
  4. Why does linear probing degrade faster than double hashing at high load?
    Primary clustering. Linear probing forms contiguous runs of occupied slots, and any key hashing anywhere into a run must traverse the rest of it. Runs also merge, so they grow faster than linearly with α. Double hashing gives each key its own stride, so keys that collide at the home slot diverge immediately and clusters never form. The trade-off is cache locality — linear probing's next slot is almost always in the same cache line, which is why it stays competitive below α ≈ 0.7.
  5. You need lookup by key and the ability to iterate in sorted order. What do you use?
    Not a hash table on its own — hashing deliberately destroys ordering. Use a balanced binary search tree (C++ std::map, Java TreeMap), which gives O(log n) lookup plus ordered iteration and range queries. In Python, either keep a hash map alongside a sorted structure such as sortedcontainers.SortedDict, or hold a sorted list and use bisect if insertions are rare.
  6. Why is expected probe count a function of α alone rather than n?
    Because it depends on how full the table is, not how large. With a uniform hash, the chance that a probe hits an occupied slot is α, so the expected number of probes follows from α by the same argument whether the table has 100 slots or 100 million. That is exactly why keeping α bounded by resizing preserves O(1) as the table grows — the constant does not drift.
