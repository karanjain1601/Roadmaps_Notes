Heaps and priority queues

A tree that gives up almost all ordering in exchange for one thing: the smallest element, instantly, always. That is a weaker promise than a search tree makes, and the weakness is exactly why a heap needs no pointers, no balancing and no rotations — it is just an array.

The heap property

The invariant

In a min-heap, every node is smaller than or equal to both of its children. That is all. There is no ordering between siblings, no ordering between subtrees, and no way to search for an arbitrary value faster than scanning. The only guaranteed knowledge is that the minimum sits at the root.

Compare with a BST, where a node separates its two subtrees completely. The heap's weaker rule has two consequences: finding an arbitrary element is O(n), and — because the constraint is so loose — the tree can always be kept perfectly complete, every level full except the last, filling left to right. A complete tree needs no pointers:

$$\text{left}(i) = 2i+1 \qquad \text{right}(i) = 2i+2 \qquad \text{parent}(i) = \left\lfloor \frac{i-1}{2} \right\rfloor$$

So a heap is a plain array with arithmetic standing in for links. No allocation per node, no pointer chasing, and the whole structure sits in contiguous memory — chapter 3's cache argument, collected in full.

Push and pop
The tree and the array are the same thing
python — the whole structure
class MinHeap:
    def __init__(self): self.a = []

    def peek(self): return self.a[0]                # O(1)

    def push(self, x):
        self.a.append(x)                            # keeps the tree complete…
        i = len(self.a) - 1
        while i > 0:                              # …then sift UP to restore the property
            p = (i - 1) // 2
            if self.a[p] <= self.a[i]: break
            self.a[p], self.a[i] = self.a[i], self.a[p]
            i = p                                   # O(log n)

    def pop(self):
        top = self.a[0]
        last = self.a.pop()
        if self.a:
            self.a[0] = last                       # move the last leaf to the root…
            self._sift_down(0)                     # …then sift DOWN
        return top                                 # O(log n)

    def _sift_down(self, i):
        n = len(self.a)
        while True:
            small, l, r = i, 2*i + 1, 2*i + 2
            if l < n and self.a[l] < self.a[small]: small = l
            if r < n and self.a[r] < self.a[small]: small = r
            if small == i: return
            self.a[i], self.a[small] = self.a[small], self.a[i]
            i = small

Why building a heap is O(n)

Pushing n items one at a time is O(n log n). Building bottom-up from an existing array is O(n) — a genuinely surprising result, and the reasoning is worth carrying around.

Where the work actually is
Almost every node is near the bottom, and near the bottom there is nowhere to fall
1,023
$$\sum_{d=0}^{h} \frac{n}{2^{d+1}} \cdot (h-d) \;=\; n\sum_{k=1}^{h} \frac{k}{2^{k+1}} \;\le\; n \cdot 1 \;=\; O(n)$$

Half the nodes are leaves and sift down zero levels. A quarter sift down at most one. The series \(\sum k/2^k\) converges to 2, so the total work is bounded by a constant times n — no logarithm survives.

python
def heapify(a):
    for i in range(len(a) // 2 - 1, -1, -1):   # from the last internal node, backwards
        sift_down(a, i)                            # O(n) total, not O(n log n)

Priority queues in practice

python — heapq, and its quirks
import heapq

h = [5, 1, 8, 3]
heapq.heapify(h)               # O(n), in place
heapq.heappush(h, 2)
smallest = heapq.heappop(h)    # heapq is a MIN-heap, always

# ── max-heap: negate on the way in and out ──
heapq.heappush(h, -x)
largest = -heapq.heappop(h)

# ── priority with a payload: push tuples, smallest first element wins ──
heapq.heappush(pq, (priority, counter, task))
#                            ↑ a tie-breaker, because if two priorities are
#                              equal Python compares the next element — and
#                              comparing arbitrary task objects raises TypeError

# ── the combined operations, cheaper than doing both ──
heapq.heappushpop(h, x)        # push then pop — one sift
heapq.heapreplace(h, x)        # pop then push — also one sift

# ── top k without sorting: O(n log k), not O(n log n) ──
heapq.nlargest(10, data, key=lambda r: r.score)
heapq.nsmallest(10, data)

# ── merge sorted streams lazily, using O(k) memory ──
for item in heapq.merge(stream_a, stream_b, stream_c):
    process(item)

The decrease-key problem

Dijkstra's textbook form wants to lower the priority of a vertex already in the queue. A plain binary heap cannot find that vertex in less than O(n), and heapq offers no such operation. Two standard workarounds: keep a dictionary mapping each item to its index and maintain it through every swap (an indexed heap), or use lazy deletion — push the improved entry as a duplicate and skip stale ones when popped, checking a visited set. Lazy deletion is what almost everyone does, it costs a little extra memory, and chapter 15 uses it.

Self-check

  1. Why can a heap be stored in a flat array when a BST cannot?
    Because the heap property is weak enough that the tree can always be kept complete — every level full except the last, filled left to right. A complete tree's structure is fully determined by its node count, so positions can be computed arithmetically: children of i at 2i+1 and 2i+2. A BST's shape is dictated by its data, so it can have gaps anywhere, and an array representation would waste exponential space on a skewed tree.
  2. Why is building a heap O(n) rather than O(n log n)?
    Because sift-down work is bounded by distance to the bottom, and almost all nodes are already there. Half the nodes are leaves and do zero work; a quarter can fall at most one level; an eighth at most two. Summing n/2^(d+1) × (h−d) over all levels gives a series that converges to about 2n. Only the single root can fall the full height. Pushing one at a time is different — each new element enters at the bottom and can rise the full height, which really is O(n log n).
  3. You need the 100 largest of ten million records. What do you do?
    Keep a min-heap of size 100. Push each record; whenever the heap exceeds 100, pop the smallest. At the end the heap holds the 100 largest. That is O(n log k) time and O(k) memory — you never hold more than 100 records, which matters if the data is streaming or does not fit in memory. Sorting would be O(n log n) and require all ten million in memory to produce an ordering you discard.
  4. How do two heaps give you a running median?
    A max-heap holds the lower half and a min-heap the upper half, with their sizes kept equal or differing by one. The median is then the top of the larger heap, or the average of the two tops — O(1). Insertion places the value in the appropriate heap and rebalances by moving one element across if the sizes drift, which is O(log n). The trick is that you never need the whole ordering, only the boundary between the halves.
  5. Why does heapq have no decrease-key, and what do people do instead?
    Because a binary heap cannot locate an arbitrary element in less than O(n) — there is no ordering to guide a search. Supporting it requires an index map maintained through every swap. The common workaround is lazy deletion: push the improved entry as a duplicate, and when popping, skip any entry for something already finalised. It costs extra memory and some wasted pops, and it is what nearly every Dijkstra implementation in Python does.
  6. Heapsort is O(n log n) in every case and sorts in place. Why is quicksort still the default?
    Cache behaviour. Sifting jumps between index i and 2i+1, so as the heap grows past cache size almost every comparison is a miss. Quicksort scans contiguous memory with two pointers, which the prefetcher handles perfectly, so despite an O(n²) worst case it is typically two to three times faster on real data. Introsort takes both: quicksort by default, heapsort only if recursion runs too deep.
