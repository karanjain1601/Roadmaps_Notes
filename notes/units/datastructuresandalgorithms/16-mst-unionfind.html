Spanning trees and union-find

A different question about the same weighted graph: not the cheapest route between two places, but the cheapest set of edges that connects everything. Two greedy algorithms answer it, and one of them needs a structure so efficient its complexity is written with an inverse Ackermann function.

— words— min read2 interactivesNeeds: chapters 13, 14

The minimum spanning tree

Given a connected weighted undirected graph, find the subset of edges that connects every vertex with the lowest total weight. Such a subset is always a tree — any cycle would contain a removable edge — so it has exactly V − 1 edges.

PropertyStatementWhy it matters
Cut propertyFor any way of splitting the vertices into two groups, the lightest edge crossing the split is in some MSTThis is what makes both algorithms correct — each one is repeatedly applying it
Cycle propertyThe heaviest edge on any cycle is in no MSTJustifies discarding edges that would close a loop
UniquenessIf all weights are distinct, the MST is uniqueTies are why two correct algorithms can return different edge sets
Kruskal against Prim
Different strategies, same total weight
python — Kruskal
def kruskal(n, edges):              # edges = [(weight, u, v), …]
    dsu = DSU(n)
    mst, total = [], 0
    for w, u, v in sorted(edges):     # O(E log E) — this dominates
        if dsu.union(u, v):           # False if they were already connected
            mst.append((u, v, w))
            total += w
            if len(mst) == n - 1:      # a spanning tree is complete
                break
    return mst, total
python — Prim, which is Dijkstra with a different key
import heapq

def prim(g, start=0):                  # g[u] = [(v, weight), …]
    seen = {start}
    pq = [(w, start, v) for v, w in g[start]]
    heapq.heapify(pq)
    mst, total = [], 0

    while pq and len(seen) < len(g):
        w, u, v = heapq.heappop(pq)
        if v in seen: continue          # lazy deletion again
        seen.add(v)
        mst.append((u, v, w)); total += w
        for nxt, wt in g[v]:
            if nxt not in seen:
                heapq.heappush(pq, (wt, v, nxt))
    return mst, total                   # O(E log V)

# the only difference from Dijkstra: the priority is the EDGE weight,
# not the accumulated distance from the source. One term, entirely
# different problem.

Union-find

Maintain a collection of disjoint sets under two operations: find which set an element belongs to, and union two sets together. Two small optimisations take it from O(n) per operation to effectively constant.

Path compression and union by rank
Turn both off, run the unions, then turn them on
python — the whole structure in fifteen lines
class DSU:
    def __init__(self, n):
        self.parent = list(range(n))     # everyone is their own root
        self.rank = [0] * n              # an upper bound on tree height
        self.count = n                   # number of disjoint sets

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving:
            x = self.parent[x]                             # point at the grandparent
        return x                                           # as you walk up

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                # already together — in Kruskal, a cycle
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra              # attach the SHORTER tree under the taller
        self.parent[rb] = ra
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1          # height only grows on a tie
        self.count -= 1
        return True
Union by rank
Always hang the shorter tree beneath the taller one. Without it, repeatedly attaching a tree to a single element builds a chain of length n and every find becomes O(n). With it, height is bounded by log n.
Path compression
While walking up to the root, re-point each node closer to it. Every find makes the next one cheaper, so the structure repairs itself through use.
Together
Amortised O(α(n)) per operation, where α is the inverse Ackermann function. It is below 5 for any n that could exist in the physical universe, so the cost is constant in every practical sense — though not formally constant.
Union-find is not only for Kruskal
  • Dynamic connectivity. "Are these two things connected?" as edges keep arriving. BFS would be O(V + E) per query; union-find is effectively O(1).
  • Cycle detection while building. An edge whose endpoints already share a root would close a cycle.
  • Merging accounts or records. Given pairs known to be the same person, group them — a classic union-find problem in disguise.
  • Percolation and image segmentation. Merge adjacent similar cells and ask when a path forms across the grid.
  • Kruskal. The application it is usually taught with, and not the most common one in practice.

Its one real limitation: there is no un-union. The structure only merges, never splits. Problems needing deletion require rebuilding, or an offline trick such as processing the edges in reverse.

A spanning tree is not a shortest-path tree

They answer different questions and are usually different trees. An MST minimises the total weight of the edges used; a shortest-path tree minimises the distance from one source to each vertex individually. In the demo above, Kruskal's MST includes B–D at weight 5, whereas Dijkstra's tree from chapter 15 also uses it — but change one weight and they part company. If someone asks for "the cheapest way to connect everything", that is an MST; if they ask "the fastest route from here to everywhere", that is Dijkstra.

Self-check

  1. Why does Kruskal need union-find rather than just a visited set?
    Because it must answer "would this edge close a cycle?", which means "are these two vertices already in the same component?" — and the components merge as the algorithm runs. A visited set cannot express membership of a changing partition. Union-find maintains exactly that partition, answering the query and performing the merge in effectively constant time. Running a traversal per edge instead would make Kruskal O(E·V).
  2. What does union by rank prevent?
    Degenerate chains. Without it, repeatedly attaching a large tree beneath a single element produces a path of length n, so every find walks the whole thing — O(n) per operation. Attaching the shorter tree beneath the taller keeps height at O(log n), because the height only increases when two trees of equal height merge, which can happen at most log n times. Turn the toggle off in the demo and watch the depth climb.
  3. How can amortised O(α(n)) be described as "effectively constant" without being constant?
    The inverse Ackermann function grows so slowly that α(n) ≤ 4 for any n up to roughly 2^65536 — far beyond the number of atoms in the observable universe. So for every input that can physically exist the cost is at most a small constant, even though the function is unbounded in theory. It is a rare case where the asymptotic result and the practical one are technically different and practically identical.
  4. Kruskal and Prim return different edges on the same graph. Is one wrong?
    No, provided both totals are equal. When several edges share a weight there can be more than one minimum spanning tree, and the two algorithms may break the tie differently. The MST is unique only when all weights are distinct. Both are correct as long as the total weight matches; if it does not, one of them has a bug.
  5. Why is an MST not the same as a shortest-path tree?
    They optimise different objectives. The MST minimises the sum of the edges used to connect everything; the shortest-path tree minimises each vertex's distance from a single source, and does not care about the total. A shortest-path tree may include an expensive direct edge because it saves distance for one vertex, while an MST would route around it. Neither is a substitute for the other, and the question asked determines which you want.
  6. You must answer "are these two accounts connected?" as merge instructions stream in. What do you use?
    Union-find. Each merge instruction is a union and each query is two finds compared for equality, both effectively O(1) — whereas a traversal-based answer would be O(V + E) per query. The one thing to check is whether merges are ever undone: union-find cannot split, so if accounts can be separated again you need a different approach, such as rebuilding or processing operations offline in reverse.
