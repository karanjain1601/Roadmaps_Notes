And read the constraints

n ≤ 10 permutations, so backtracking · n ≤ 20 subsets or bitmask DP · n ≤ 100 O(n⁴) is fine · n ≤ 500 O(n³), often interval DP or Floyd-Warshall · n ≤ 5,000 O(n²), many DP tables · n ≤ 10⁵ O(n log n) — sort, heap, window or binary search · n ≤ 10⁷ O(n), a single pass · n ≥ 10⁹ O(log n) or O(1), so maths or binary search on the answer.

Working through a problem

Under pressure, in an interview or otherwise, the failure is almost never a missing algorithm. It is starting to code before the problem is understood.

  1. Restate it in your own words and get agreement. Half of all wrong answers are answers to a different question.
  2. Ask about the edges. Empty input? Duplicates? Negatives? Sorted already? How large can n be — that answer names your complexity budget.
  3. Work a small example by hand. Not a trivial one; one with enough structure to expose the pattern. This is where most insights actually arrive.
  4. State the brute force and its cost, out loud. It proves you understand the problem, it gives you a correct fallback, and its inefficiency usually points at the improvement.
  5. Ask what is being recomputed or wasted. Repeated subproblems suggest DP. Repeated scanning suggests a window or a hash map. Repeated searching suggests sorting or an index.
  6. Say the approach before writing it. Naming the pattern and the complexity lets a wrong direction be corrected before you have spent ten minutes on it.
  7. Code it, narrating the invariants rather than the syntax. "left is always the start of a valid window" is worth more than reading your own code aloud.
  8. Trace a real example through it, then the edge cases. Empty, single element, all identical, already sorted, the maximum size.
  9. State the final complexity, both time and space, and say whether you think it can be improved.

    Where to go from here

    Practise deliberately

    Forty problems solved slowly with debriefs beat two hundred pattern-matched. Attempt for twenty minutes, then read, then re-solve cold three days later — chapter 1's method, and the only part of it that matters.

    Go deeper on theory

    Cormen et al. for rigour, Erickson's free Algorithms for the clearest treatment of recursion and DP, Sedgewick for implementations you can read.

    Go wider

    The Computer Science unit for the surrounding theory, System Design for what happens when the data outgrows one machine, LeetCode Patterns for problem drilling by shape.

    Apply it

    Every structure here exists in something you use. Read a database's index code, a language's dict implementation, a router's prefix table. The structures make far more sense once you have seen them earning their keep.

    The short version of the whole unit
    1. A data structure is a decision about which operations will be cheap.
    2. Ask how the cost scales, not what it is today.
    3. Contiguous memory beats the complexity table more often than you expect.
    4. Hash table for lookup, balanced tree for order, heap for the extreme, trie for prefixes.
    5. Recursion is a base case plus a shrinking step — trust it rather than tracing it.
    6. BFS and DFS are one algorithm with one substitution.
    7. Greedy needs an exchange argument; without one, use DP.
    8. Read the constraints before choosing the approach.
    9. Write the brute force first. It is correct, and its waste tells you what to fix.

    That is the unit. Twenty-one chapters, from counting operations to dynamic programming. If you have worked the demos and attempted the self-checks, the remaining distance is closed by solving problems, not by reading more chapters.
