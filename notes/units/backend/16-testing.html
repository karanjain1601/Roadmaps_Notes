Chapter 16 · Speed and safety

Testing services

Tests exist so that you can change the system without being afraid. That is the goal, and it explains the awkward parts: why a hundred per cent coverage number means little, why the suite has to be fast, and why a test that fails at random is worse than no test at all.

Why the pyramid has that shape

The shape is not a rule handed down; it falls out of arithmetic. Tests differ by two orders of magnitude in cost and by which failures they can see at all, and the optimum is whatever balances those.

The trophy, and what the argument is actually about

A common revision to the pyramid pushes weight into the middle: fewer isolated unit tests, many integration tests, a handful of end-to-end. The reasoning is that heavily-mocked unit tests verify that your code calls the mocks you wrote, which is a tautology, while the bugs are in the seams. That critique is largely right for a typical web service, where the interesting failures are SQL, serialisation and transaction boundaries rather than algorithms. The real principle underneath both shapes is the same: test at the highest level you can afford to run on every commit. Where that line falls depends on how fast your integration tests are, which is a solvable engineering problem — and the teams with fast integration suites end up with a trophy, while the teams with slow ones end up with a pyramid.

Test doubles, and the one you should not use

Stub
Returns canned answers. The workhorse — "this API returns these three products".
Fake
A real, working, simplified implementation: an in-memory queue, a dictionary-backed repository. Behaves correctly, so tests using it stay meaningful.
Spy
Records what happened so you can assert on it afterwards. Useful for verifying an email was sent.
Mock
Has expectations baked in and fails if the interaction differs. Powerful, and the main source of tests that pass while the system is broken — they assert on how the code works rather than what it does, so every refactor breaks them.
Dummy
Filler passed to satisfy a signature and never used.
Do not mock the database

A mocked query returns what you told it to, which proves nothing about whether the SQL is valid, whether the migration ran, whether the constraint fires, whether the transaction commits, or whether the ORM generated three hundred queries. Those are the failures that reach production. Run tests against the real engine in a container — testcontainers or a compose file — and the entire class of "it worked against the mock" disappears. The exception worth naming is a third-party API you do not control: stub it, and cover the real agreement with a contract test.

python — a real database, isolated per test, still fast
# ── one container for the whole session, migrated once ──
@pytest.fixture(scope="session")
def engine():
    with PostgresContainer("postgres:16") as pg:
        e = create_engine(pg.get_connection_url())
        run_migrations(e)              ← the real migrations, so they are
        yield e                          tested too. A migration that fails
                                         in CI has not failed in production
# ── isolation by rollback: each test runs inside a transaction that is
#    never committed. Faster than truncating, and perfectly isolated. ──
@pytest.fixture
def db(engine):
    conn = engine.connect()
    tx = conn.begin()
    session = Session(bind=conn)
    yield session
    session.close(); tx.rollback(); conn.close()
#    the caveat: code under test must not commit or begin its own
#    top-level transaction. Use SAVEPOINTs if it does.

# ── factories, not fixture files. Every test states only what it cares
#    about, and stays readable when the schema grows a column. ──
def make_order(db, **kw):
    defaults = dict(status="pending", total_cents=1999, user=make_user(db))
    return Order(**{**defaults, **kw})

def test_cancelling_a_shipped_order_is_rejected(db):
    order = make_order(db, status="shipped")     ← the only detail that matters
    with pytest.raises(InvalidTransition):       is visible in the test
        cancel(db, order)
python — a contract test, which replaces most cross-service integration
# the consumer records what it needs from the provider
(pact.given("order 7c3a exists")
     .upon_receiving("a request for order 7c3a")
     .with_request("GET", "/v1/orders/7c3a")
     .will_respond_with(200, body={
         "id": Like("7c3a"),                 ← match the TYPE, not the value.
         "total_cents": Like(1999),             a contract on exact values breaks
         "status": Term("pending|paid|shipped", "pending"),     constantly
     }))

Flaky tests

A test that fails at random does not merely waste a rerun. It compounds across the suite, and it destroys the one thing tests are for.

The policy that works

Quarantine, then fix or delete, on a deadline. A flaky test is moved out of the blocking suite the day it is noticed, with an owner and a date; if it is not fixed by then it is deleted. This feels wrong and is correct — a test nobody trusts provides no signal and consumes attention every single run, and the greater damage is cultural: once "just rerun it" becomes the reflex, genuine failures get rerun too. The alternative, automatic retries, hides the flakiness and lets it accumulate until the green-run probability collapses.

On coverage

Coverage measures which lines executed, not whether anything was verified — a suite that calls every function and asserts nothing reports one hundred per cent. It is a useful negative signal: an untested module shows up clearly, and a sharp drop in a pull request is worth a question. As a target it produces tests written to touch lines rather than to check behaviour, which cost maintenance and buy confidence they do not deliver. Watch the trend and the uncovered error paths; ignore the number.

Self-check

  1. Why is a heavily-mocked unit test sometimes worthless?
    Because it verifies that your code calls the doubles you wrote in the way you told them to expect — a statement about your test, not about the system. It passes when the SQL is invalid, when the serialisation is wrong, when the transaction never commits, and after a refactor that changed nothing observable. Mocks are worth using for genuinely external, slow or non-deterministic things; using them for your own collaborators mostly tests the wiring diagram in your head.
  2. Why run integration tests against a real database rather than a mock?
    Because the failures worth catching are the ones only a real engine produces: invalid SQL, a migration that does not apply, a constraint that fires, a transaction that does not commit, a query that turns out to be N+1. A mock returns whatever you configured, so all of those pass. Containers make this cheap now — one container per session, migrations run once, and each test isolated by a transaction that is rolled back.
  3. What does a contract test give you that an integration test between two services does not?
    Independence. The consumer records what it needs and the provider replays those expectations in its own CI, so neither team runs the other's service and no shared staging environment is required. Failures also point at the right place: the provider's build breaks when it removes a field a consumer relies on, at the moment of the change, rather than surfacing later as a mysterious error in someone else's system.
  4. Two thousand tests, each 99.9% reliable. What fraction of runs are green?
    About 13.5%, since 0.999 to the power of 2,000 is roughly 0.135. Nearly seven runs in eight fail for no reason, which means the suite has effectively stopped being a signal — every red build is presumed spurious until proven otherwise, including the real ones. This is why per-test reliability has to be extremely high in a large suite, and why "it only fails occasionally" is not a small problem.
  5. Why quarantine a flaky test rather than adding an automatic retry?
    Because retries hide the problem while it accumulates. Each newly flaky test slightly lowers the green-run rate, retries mask that, and the count grows until the suite is slow and unreliable in ways nobody can attribute. Worse is the cultural effect: once rerunning is the standard response to red, genuine failures get rerun too. Quarantining removes the noise immediately, keeps the signal honest, and puts a name and a date against the fix.
  6. Why is high coverage not the same as being well tested?
    Because coverage records which lines ran, not whether the result was checked — a suite that calls everything and asserts nothing reports full coverage. Chasing the number produces tests written to execute lines rather than to verify behaviour, which cost maintenance and provide little confidence. It is a good negative signal: untested modules and uncovered error paths show up clearly. Use it to find gaps, not as a target.
