Queues, logs and events

Not everything has to happen while someone waits. Moving work off the request path is the standard way to absorb bursts, survive a failing dependency and fan one action out to five consumers — and it introduces a problem that has no clean solution, only a well-known workaround.

Queues against logs

Two categories of thing that both look like "message broker" in a diagram and behave completely differently. Choosing the wrong one is a design error you feel a year later.

Commands and events

The distinction that usually resolves the choice. A command is addressed: send this email. It has one intended handler, the sender expects it to be done, and a queue is the right shape. An event is an announcement: an order was placed. The publisher does not know or care who is listening, any number of services may react, and a log is the right shape. Naming matters here — a topic called send-welcome-email is a command wearing an event's clothes, and it will acquire a second consumer eventually and behave badly.

Delivery semantics

GuaranteeMeansReality
At most onceAcknowledge before processingA crash loses the message. Only for data you can afford to drop, such as metrics
At least onceAcknowledge after processingA crash between processing and acking causes a redelivery. This is what you will use
Exactly onceDelivered and processed precisely onceNot achievable across a network in general. What brokers offer is at-least-once delivery plus deduplication within their own boundary
"Exactly once" is at-least-once plus an idempotent consumer

The consumer acknowledges after doing the work; if it crashes in between, the broker redelivers, and it must. There is no protocol that avoids this, because the acknowledgement itself can be lost. So the property you actually need lives in the consumer, not the broker: record the message id you have processed and skip repeats, in the same transaction as the effect. That is chapter 5's idempotency key applied to a different transport, and it is the difference between a system that tolerates redelivery and one that sends the same customer four emails after a deploy.

python — an idempotent consumer, which is most of the work
def handle(msg):
    with db.transaction():
        if db.already_processed(msg.id):     ← a unique index on message_id
            return                             does the enforcing; the check
        db.mark_processed(msg.id)              is only an optimisation
        apply_effect(msg)                    ← same transaction as the marker,
    ack(msg)                                   or a crash between them undoes
                                               the idempotence
# three further rules that are learned the hard way:
#  · handlers must tolerate OUT OF ORDER delivery too. A redelivered
#    old message must not overwrite a newer state — compare versions.
#  · never do slow external work inside the transaction. Chapter 10.
#  · expire the processed-ids table, or it grows forever.

The dual-write problem

Save the order and publish "order placed". Two systems, two writes, no transaction spanning them — and the gap between them is where the data corruption lives.

A crash at the worst moment
Same failure, two designs
sql + python — the outbox, in full
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,     -- ordering comes free
  aggregate_id uuid NOT NULL,
  event_type   text NOT NULL,
  payload      jsonb NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz                  -- null until the relay sends it
);
CREATE INDEX ON outbox (id) WHERE published_at IS NULL;   -- partial: the
-- relay's query stays fast no matter how large the table grows. Ch 9.

# the write path — one transaction, so the two cannot disagree
with db.transaction():
    order = db.insert_order(...)
    db.insert_outbox(aggregate_id=order.id, event_type="order.placed",
                     payload=serialise(order))
# nothing is published here. The request returns; the effect is durable.

# the relay — a separate process, or change-data-capture from the WAL
while True:
    for row in db.fetch_unpublished(limit=100):    # FOR UPDATE SKIP LOCKED
        broker.publish(row.event_type, row.payload,
                       key=str(row.aggregate_id),      ← partition key: all
                       headers={"message-id": str(row.id)})    events for one
        db.mark_published(row.id)                        order stay ordered
    sleep(0.2)

# if the relay crashes between publish and mark_published, the event is
# sent twice. That is fine and expected — the consumer is idempotent,
# which is why the previous section came first.

Sagas, and webhooks

Chapter 17 ended on the observation that a transaction cannot span two services. A saga is what you use instead: a sequence of local transactions, each with a compensating action that undoes it.

a saga, and the part people underestimate
place order   →  reserve stock  →  take payment  →  arrange shipping
                       ↓                 ↓                  ↓
                 release stock    refund payment      cancel shipment
                                  ← compensations run in reverse →

choreography — each service reacts to events. No coordinator, minimal
  coupling, and no single place that describes the process. Fine for
  three steps; unfollowable at eight.

orchestration — one service drives the sequence and holds the state.
  Explicit, visible, testable; a component everything depends on.
  Prefer this the moment the flow has branches or timeouts.

the hard part is not the happy path. It is that compensation is not
rollback: the email has been sent, the warehouse has moved the item,
the customer saw a confirmation. You are not undoing the effect, you
are performing a NEW business action that addresses it — and someone
has to decide what that action is for every step. That decision is a
product question, not a technical one, and it is why sagas are much
more expensive than the diagram suggests.
Webhooks are events for other people
The same problem with none of your infrastructure. You are now a broker whose consumers you do not control, cannot restart, and who will be offline when you deliver.
What a receiver needs from you
A signature over the raw body with a shared secret, and a timestamp inside the signed payload so old deliveries cannot be replayed. A stable event id so they can deduplicate. Retries with backoff over hours, not minutes. A way to see and replay failed deliveries.
What you need from a receiver
A fast acknowledgement. They should persist and return 200 immediately, then process asynchronously — a receiver that does real work before responding will time out under load and cause redeliveries that make it worse.
Sending them safely
The URL is user-supplied and your server fetches it: this is SSRF by design. Chapter 15 — resolve, validate the address, refuse redirects, and send from an egress-restricted worker rather than from your application.

Self-check

  1. When is a log the right choice over a queue?
    When more than one thing may care about the message, when you may want to add a consumer later that needs the history, when replay is valuable, or when strict ordering matters. Those all describe events — announcements about something that happened. A queue suits commands: one addressed handler, work distributed among competing workers, and per-message operations like delay, priority and dead-lettering, which a log does not offer.
  2. Why is exactly-once delivery not achievable?
    Because the acknowledgement can be lost. If the consumer processes a message and crashes before acking, the broker cannot distinguish that from a consumer that never received it, so it must redeliver or risk losing the message. Acking first gives at-most-once and loses messages on a crash. What brokers market as exactly-once is at-least-once delivery plus deduplication inside their own boundary, which does not extend to the side effects your handler performs.
  3. What is the dual-write problem?
    Writing to two systems that cannot participate in one transaction — commit the order, then publish the event. A crash in between leaves the order saved and no event, so every downstream service is permanently unaware of it; reversing the order gives an event for an order that does not exist. Neither ordering is safe, and retries do not fix it because the process may not survive to retry. The window is small and it is hit constantly at scale.
  4. How does the outbox pattern solve it, and what does it not solve?
    The event is written into a table in the same transaction as the business data, so the two are atomic — either both exist or neither does. A separate relay then reads unpublished rows and sends them, retrying until it succeeds. What it does not give you is exactly-once: if the relay crashes between publishing and marking the row sent, the event goes out twice. That is deliberate and acceptable, provided consumers are idempotent — which is why the two sections belong together.
  5. Why does one poison message require a dead-letter queue?
    Because retrying forever blocks everything behind it. In an ordered partition the consumer cannot move past a message it will not successfully process, so a single malformed payload halts the whole stream indefinitely while lag climbs. Moving it aside after a bounded number of attempts keeps the stream flowing and turns an outage into an item on a list — provided somebody actually watches that list, which is the part usually missing.
  6. Why is compensation not the same as rollback?
    Because the effect already happened in the world. A database rollback erases an uncommitted change as if it never existed; a compensating action cannot un-send an email, un-charge a card without a visible refund, or un-move an item in a warehouse. You are performing a new business action that addresses the earlier one, and what that action should be has to be decided per step — usually by someone outside engineering. That is the real cost of a saga, and it is not visible in the diagram.
