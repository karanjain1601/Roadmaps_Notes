Designing REST APIs

An API is a contract you cannot easily change, written for people you will never meet, who will use it in ways you did not intend and will not upgrade when you ask them to. Most of the craft is in the parts that are hard to alter later: URIs, pagination, versioning and error shape.

Resources and URIs

The organising idea is that URLs name things, and the method says what to do to them. Almost every convention below follows from that one commitment.

Pagination

Two approaches. One is obvious, universally taught, and quietly wrong for any list that changes while it is being read.

Offset against cursor
Fetch page one, let the list change, fetch page two
sql — and the reason offset gets slow, not just wrong
-- OFFSET does not skip rows. It finds them, counts them, and throws
-- them away. Page 5,000 reads 100,020 rows to return 20.
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- keyset pagination seeks straight to the position in the index and
-- reads 20 rows. The cost is identical on page 1 and page 5,000.
SELECT * FROM orders
WHERE (created_at, id) < ('2026-02-14 09:31:02', '7c3a1b')   -- the cursor
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- the id tiebreaker is not optional: without it, rows sharing a
-- timestamp can be skipped or repeated at a page boundary.
-- the sort key must be unique, or made unique.

Idempotency keys

The network can fail after your server committed but before the client heard about it. The client cannot tell that apart from a request that never arrived — so it retries, and something happens twice.

A retry after a lost response
Same sequence of events, one header different
python — the server side, with the details that matter
@app.post("/v1/charges")
def create_charge(body, idempotency_key: str | None = Header(None)):
    if not idempotency_key:
        return do_charge(body)             # caller accepted the risk

    with db.begin():
        prior = db.get_idempotency_record(idempotency_key, for_update=True)

        if prior and prior.status == "completed":
            if prior.request_hash != hash_body(body):
                raise Conflict("key reused with a different body")   # 422
            return prior.response            # ← the whole point: replay it

        if prior and prior.status == "in_flight":
            raise Conflict("a request with this key is still running")  # 409

        db.insert_idempotency_record(idempotency_key, hash_body(body),
                                     status="in_flight")

    result = do_charge(body)                 # the side effect, exactly once

    db.complete_idempotency_record(idempotency_key, result, ttl_hours=24)
    return result

# four things people miss:
#  · the key must be stored in the SAME transaction as the effect, or a
#    crash between them leaves you charged with no record — see chapter 18's
#    outbox pattern for the general form of this problem
#  · hash the body: the same key with different content is a client bug
#  · handle the concurrent case, not just the sequential retry
#  · expire the keys, or the table grows forever
Who generates the key, and when

The client generates it — a UUID — and reuses the same value for every retry of the same logical operation. That is what makes it work: the key identifies the intent, not the attempt. A key generated per HTTP call would be different on the retry and protect nothing. In a browser, generate it when the user opens the form rather than when they press submit, so a double-click sends the same key twice.

What actually breaks a client

Safe: adding an endpoint, adding an optional request field, adding a response field, adding a new enum value if you documented that clients must tolerate unknown ones, relaxing a validation rule.

Breaking: removing or renaming any field, changing a type — including "3" to 3, which breaks strict parsers — making an optional field required, tightening validation, changing a default, changing a status code, changing the order of an array clients treat as stable. The most commonly underestimated one is adding an enum value, because half of all clients have a switch statement with no default branch.

HATEOAS, honestly

In Fielding's original formulation, a truly RESTful client discovers what it can do next from links in the response, the way a browser does with a web page. Almost nobody builds this, because almost no client is a general-purpose agent — it is code written against documentation, by a developer who already knows the endpoints. What is worth taking from it is narrower and genuinely useful: return a links.next for pagination so clients never construct cursors themselves, and return the URL of anything you just created. Those two save real bugs. Building a full hypermedia state machine because the maturity model has four levels is optimising for a client that will not exist.

Self-check

  1. Why is POST /createOrder worse than POST /orders?
    The method already carries the verb, so the path repeating it is redundant — and once you start naming actions in paths you need a new URL for every operation, losing the property that one URL identifies one thing. That property is what lets caching, permissions, logging and routing all key off the path. The exception is genuine actions that are not CRUD, where POST /orders/7c3a/refund is clearer than any noun you could invent.
  2. A client fetches page 1, a new item is created, then it fetches page 2 using offset. What goes wrong?
    The insert shifts every row down by one, so the item that was last on page 1 is now the first on page 2 and the client receives it twice. A deletion causes the mirror image — everything shifts up and one item is silently skipped. Offset addresses positions in a list, and positions change. A cursor addresses a specific row's sort key, which does not, so the next page continues from exactly where the last one ended regardless of what happened in between.
  3. Why does OFFSET 100000 get slow?
    Because the database cannot skip rows without finding them. It walks the index or table, counts off 100,000 rows, discards them all, and returns the next 20 — so page 5,000 does 5,000 times the work of page 1. Keyset pagination puts the cursor in a WHERE clause instead, so the index seeks directly to the position and reads exactly 20 rows. The cost is identical on every page, which is why every high-volume API uses it.
  4. Who generates an idempotency key, and why does that matter?
    The client, once per logical operation, reusing the same value on every retry. The key identifies the intent rather than the attempt — a key generated fresh for each HTTP call would differ on the retry and protect nothing. In a browser, generate it when the form opens rather than on submit, so a double-click also carries the same key. The server stores the key with the response and replays it on a repeat, so the effect happens exactly once.
  5. Why must the idempotency record be written in the same transaction as the effect?
    Otherwise a crash between the two leaves the effect applied and no record of the key. The retry finds nothing, does the work again, and the customer is charged twice — the exact failure the mechanism exists to prevent. Committing them together makes the pair atomic. When the effect is in an external system that cannot join your transaction, this becomes the general problem chapter 18 solves with the outbox pattern.
  6. Why is adding a new enum value a breaking change in practice, when it looks additive?
    Because a large share of clients parse it with a switch or a strict enum type that has no default branch, so an unrecognised value throws or falls through silently. It is additive in the specification and breaking in the field. The mitigations are to document from day one that clients must tolerate unknown values, to introduce new values behind a version or a flag, and to check what your generated client libraries do with unknown variants before you find out from a support ticket.
