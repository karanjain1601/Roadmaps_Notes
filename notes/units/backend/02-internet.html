How the internet works

The first hundred milliseconds of chapter 1's waterfall, unpacked. A name becomes an address, an address becomes a connection, a connection becomes an encrypted one — three separate systems, each with its own failure modes, all running before your process is aware anything is happening.

The layers

Each layer solves one problem and hands the rest downward. The reason this is worth knowing is not the model itself but the debugging: when something breaks, the layer tells you which tool to reach for.

shell — the layer tells you the tool
# is the name resolving, and to what?
dig api.example.com +short
dig api.example.com @1.1.1.1        # bypass the local resolver
dig +trace api.example.com          # walk the delegation from the root

# can I reach the host at all?
ping api.example.com                # ICMP — often blocked, so silence proves little
traceroute api.example.com          # where does the path stop?

# is the PORT open, and is something listening?
nc -vz api.example.com 443
ss -tlnp                            # what is listening on THIS machine

# what is the TLS layer doing?
openssl s_client -connect api.example.com:443 -servername api.example.com

# and finally the application layer
curl -v https://api.example.com/health
curl -w "dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n" \
     -o /dev/null -s https://api.example.com/
That last command is the one to remember

It prints chapter 1's waterfall for any URL. If time_namelookup is large the problem is DNS; if time_connect minus it is large the problem is the network path; if time_appconnect is large the problem is TLS; and if time_starttransfer minus that is large, the problem is finally yours. Thirty seconds of diagnosis before opening a single dashboard.

Three things people get wrong about DNS

"Propagation" is not a thing. Nothing propagates. Changes are visible immediately at the authoritative server; what you are waiting for is every cache in the world to reach the TTL you set before the change. If you plan to move a record, lower the TTL to 60 seconds a day in advance, make the change, then raise it again. The delay is your own previous TTL, not a network in transit.

DNS is not a load balancer. Returning several A records distributes clients roughly, but there is no health checking, caching ignores your intentions, and a failed host keeps receiving traffic until its record expires everywhere. Use it for coarse geographic steering, not for failover.

A TTL is a promise you cannot revoke. A 24-hour TTL means some resolver may keep serving the old answer for 24 hours after you delete it. Long TTLs are cheap and fast until the day you need to move quickly.

TCP, and what a connection costs

IP delivers packets to a machine, unreliably and out of order. TCP turns that into an ordered, reliable byte stream between two processes — and every guarantee it adds costs a round trip somewhere.

The handshake
SYN, SYN-ACK, ACK. One full round trip before any data moves, spent agreeing initial sequence numbers and confirming both directions work.
Reliability
Every byte is numbered and acknowledged; anything unacknowledged is retransmitted. This is also the source of head-of-line blocking — one lost packet stalls everything behind it, even data that already arrived.
Flow control
The receiver advertises a window saying how much it can accept, so a fast sender cannot overwhelm a slow reader.
Congestion control
Separate from flow control and more consequential. The sender starts cautiously and grows — slow start — so a new connection cannot use the full bandwidth immediately even on an idle link. Another reason connection reuse matters: a warm connection has already grown its window.
Ordered delivery
Bytes arrive in the order sent. Convenient, and the reason HTTP/2's multiplexing still suffers when a packet is lost — which is what HTTP/3 exists to fix.

TLS and certificates

TLS provides three things, and it is worth separating them because people usually only think of the first.

Confidentiality
Nobody in the middle can read the traffic. This is the one everyone names.
Integrity
Nobody can modify it undetected — which historically mattered as much, since ISPs happily injected advertising into unencrypted pages.
Authenticity
You are talking to who you think. Encryption without this is worthless: an encrypted channel to an attacker is still a channel to an attacker. This is what certificates are for, and why an expired certificate is a hard failure rather than a warning.
How the chain of trust works

Your operating system ships with a few hundred root certificates from certificate authorities. A CA signs an intermediate certificate; the intermediate signs yours. The client verifies each signature up the chain until it reaches a root it already trusts, and separately checks the name matches, the dates are valid, and the certificate has not been revoked. The most common production failure is not an expired leaf certificate but a missing intermediate — the server sends only its own certificate, browsers paper over it by fetching the intermediate themselves, and then a command-line client or a mobile app fails with an error nobody can reproduce in a browser.

shell — checking a certificate before it embarrasses you
# expiry dates and the subject
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject

# the full chain the server actually sends — count the certificates.
# one means a missing intermediate, which browsers hide and clients do not
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# -servername is SNI: it tells the server which hostname you want BEFORE
# encryption starts, so one IP can host many certificates. Omit it against
# a shared host and you get the wrong certificate and a confusing error.

The address, port and socket, precisely

An IP address identifies a machine. A port identifies a process on it — 80 for HTTP, 443 for HTTPS, 5432 for Postgres, 6379 for Redis. A socket is the four-tuple of source address, source port, destination address and destination port, and it is what makes a connection unique. That is why one server can hold hundreds of thousands of simultaneous connections on port 443: each client contributes a different source port. It is also why a machine making many outbound connections can exhaust its ephemeral port range — roughly 28,000 by default — which surfaces as mysterious connection failures under load and is almost always fixed by pooling connections rather than opening one per request.

Self-check

  1. Your DNS change is live at the registrar but users still reach the old server. What is happening, and what should you have done?
    Resolvers are still serving the previous answer from cache until its TTL expires — the TTL you set before the change, not the new one. Nothing is propagating; you are waiting out your own earlier decision. The fix is preparation: drop the TTL to 60 seconds a day before the move, make the change, confirm, then raise it back. There is no way to flush the world's caches after the fact.
  2. Why does a fresh HTTPS connection cost three round trips before any application data?
    One for the TCP handshake (SYN, SYN-ACK, ACK), one for the TLS 1.3 handshake, and one for the request and its response. TLS 1.2 needed two round trips of its own, making four in total; QUIC folds transport and cryptographic setup into a single round trip, making two. At 30 ms this is the difference between 90 ms and 60 ms; on a 200 ms mobile connection it is 600 ms against 400 ms.
  3. What does a certificate provide that encryption alone does not?
    Authenticity — proof you are talking to the party you intended. An encrypted channel to an attacker who intercepted the connection is perfectly private and completely useless. The certificate chains to a root your system already trusts, and the client also checks the hostname matches and the dates are valid. This is why browsers treat certificate errors as hard failures rather than warnings.
  4. A service works in the browser but fails from curl and a mobile app with a TLS error. What is the likely cause?
    A missing intermediate certificate. The server is sending only its own leaf, and browsers compensate by fetching the intermediate themselves or by having cached it from another site — most other clients do not. Check with openssl s_client -showcerts: if only one certificate comes back, the chain is incomplete. Configure the server to send the full chain.
  5. Why can one server hold hundreds of thousands of connections on port 443, while a client machine can run out of ports making a few thousand outbound ones?
    A connection is identified by the four-tuple of source IP, source port, destination IP and destination port. Inbound connections all share the server's address and port but each client supplies a different source address and port, so the tuples stay unique. An outbound-heavy machine talking to one destination varies only its own ephemeral port, and that range is roughly 28,000 entries — exhausted quickly if you open a connection per request. Connection pooling is the fix, which is why it appears in every chapter that touches a network.
  6. Why does TCP make a new connection slower than a warm one even on an idle, fast link?
    Congestion control's slow start. A new connection cannot know how much bandwidth is available, so it begins with a small window and doubles it each round trip until it sees loss. A connection that has been in use has already grown its window and can send at full rate immediately. Combined with the handshake savings, this is why keep-alive and connection pooling improve throughput as well as latency.
