Chapter 04 · Serving requests

Web servers and concurrency

Your application handles one request at a time. Everything that makes it handle thousands — the proxy in front, the worker model underneath, the pool of database connections beside it — is configuration you probably inherited. It is also where a surprising share of production incidents begin.

What sits in front

Almost nobody exposes an application server directly to the internet. Something sits in front, and it is doing more than forwarding.

TLS termination
Certificates live in one place instead of every application instance. Chapter 2.
Load balancing
Spread requests across instances, and stop sending them to one that has stopped answering.
Buffering slow clients
The one people forget. A client on a poor mobile connection takes two seconds to send its request body; the proxy absorbs that so your expensive application worker is occupied for milliseconds rather than seconds. This alone can multiply effective capacity.
Static files and compression
Serving a file from disk and gzipping a response are things a proxy does far better than an application runtime.
A place for cross-cutting concerns
Rate limits, IP allow-lists, request size caps, header rewriting, redirects — all configurable without a deploy.

Health checks are the part that matters

A load balancer without health checks distributes failures evenly. Two distinctions are worth making. Liveness asks "is this process wedged and in need of a restart?"; readiness asks "should this instance receive traffic right now?" — which is false during startup, during a slow warm-up, and while draining before shutdown. Second, do not make your health check test your database. If it does, a brief database blip marks every instance unhealthy simultaneously, the balancer removes them all, and a recoverable incident becomes a total outage. Check that the process can answer; check dependencies separately and alert on them.

The three concurrency models

A request spends its time in two very different ways: burning CPU, and waiting for something else. The right model depends entirely on the ratio, and the crossover is sharper than most people expect.

The failure that catches every team once

One synchronous call inside an async handler. A blocking database driver, a CPU-heavy image resize, time.sleep, an ordinary requests.get — anything that does not yield. In a threaded server it slows one request. In an event loop it stops every request on that process, including the health check, so the load balancer removes the instance and the traffic moves to the next one, which promptly does the same thing.

The symptom is distinctive: latency across all endpoints degrades together, including trivial ones, and the process shows one core pinned. If you use an async framework, the discipline is absolute — every library in the request path must be async, and CPU-bound work goes to a thread pool or a queue.

python — the same mistake in three frameworks
# ── FastAPI: this blocks the entire event loop ──
@app.get("/report")
async def report():
    data = requests.get("https://slow.example.com")   # ✗ synchronous
    return heavy_pdf_render(data)                     # ✗ CPU-bound

# ── correct: async client, and CPU work moved off the loop ──
@app.get("/report")
async def report():
    async with httpx.AsyncClient() as c:
        data = await c.get("https://slow.example.com", timeout=2.0)
    return await run_in_threadpool(heavy_pdf_render, data)

# ── FastAPI will also do the right thing if you simply drop `async`: ──
@app.get("/report")
def report():                                       # note: not async
    ...                                              # run in a threadpool for you
    # a plain `def` handler is safer than a badly written `async` one

Connection pools

Opening a database connection costs a round trip and real memory on the server, so nobody opens one per request. A pool holds a fixed number open and hands them out — which turns your database into a queue, with all the behaviour queues have.

300/s
20 ms
10
$$L = \lambda W$$

Little's Law. The number of requests in the system equals the arrival rate multiplied by the time each spends there — and it holds for any stable system regardless of the distributions involved. Rearranged, it sizes the pool: to serve λ requests per second where each holds a connection for s seconds, you need at least λ·s connections just to keep up, and more to absorb variation.

Bigger pools are not better pools

The instinct when requests start queueing is to raise the pool size. Often that makes things worse. A database has a fixed amount of parallelism — cores, disks, lock contention — and beyond it, more concurrent queries do not run faster, they run slower and all together. You have moved the queue from your application, where it is visible and boundable, into the database, where it is neither.

A common starting point for a relational database is (cores × 2) + effective spindles, which for a modern 8-core server on SSDs is roughly 20 connections in total across every application instance. Teams running fifty instances with a pool of twenty each are asking a database sized for twenty concurrent queries to run a thousand. Count the total, not the per-instance number.

Timeouts and shutdown

python — every outbound call needs a deadline
# the default timeout for most HTTP clients is: none. Forever.
# one slow dependency then consumes every worker you have.
httpx.get(url, timeout=httpx.Timeout(connect=1.0, read=2.0, write=2.0, pool=1.0))

# databases need one too — at the statement level, not just the client
engine = create_engine(
    dsn,
    pool_size=10, max_overflow=5,
    pool_timeout=2,            # fail fast rather than queue forever
    pool_recycle=1800,        # reopen before a firewall silently drops it
    pool_pre_ping=True,       # cheap liveness check on checkout
    connect_args={"options": "-c statement_timeout=3000"},
)

# the budget must shrink as you go down the stack, or it is not a budget:
#   client 10s  >  gateway 8s  >  service 5s  >  database 3s
# if the database timeout exceeds the gateway's, the gateway gives up first
# and the query keeps running — work nobody is waiting for. Chapter 19.
Graceful shutdown, in order
  1. Fail the readiness check so the load balancer stops sending new requests. Do this first, and wait a few seconds — the balancer needs a moment to notice.
  2. Stop accepting new connections, but keep serving the ones in flight.
  3. Drain, with a deadline. Finish outstanding requests, then stop waiting.
  4. Close pools and flush — database connections, buffered logs, metrics.
  5. Exit. If the orchestrator's grace period expires first it will send SIGKILL, and everything in flight is lost, so the drain deadline must be shorter than that period.

Self-check

  1. Why put a reverse proxy in front of an application server that can already speak HTTP?
    Several reasons, but the most underrated is buffering slow clients: a proxy absorbs the two seconds a mobile client takes to upload a request body so your application worker is busy for milliseconds instead. It also centralises TLS, serves static files and compresses far more efficiently than an application runtime, and gives you a place for rate limits and header rules that does not require a deploy.
  2. Why should a health check not test the database?
    Because a brief database problem then marks every instance unhealthy at once. The load balancer removes them all and a recoverable blip becomes a total outage — and once the database recovers, all traffic returns simultaneously to cold instances. A readiness check should answer "can this process serve traffic", which is about the process. Monitor dependencies separately and alert on them there.
  3. When does an event loop lose to a thread pool?
    When requests are CPU-bound rather than waiting. An event loop runs on one core, so if each request needs 40 ms of computation it can complete at most 25 per second per process, while a thread pool spreads that across every core. The demo shows the crossover clearly: with heavy I/O the event loop wins by an order of magnitude, and as CPU time rises the lines converge and then invert. Multiple loop processes recover the cores, which is what production async deployments actually do.
  4. An async endpoint calls a synchronous HTTP library. What is the symptom in production?
    Every endpoint on that process gets slow together, including trivial ones and the health check, and one core sits pinned. The blocking call prevents the loop from servicing anything else, so it is not one slow endpoint but a stalled process. Because the health check also stalls, the load balancer removes the instance and moves traffic to the next one, which does the same thing — the failure walks through the fleet.
  5. Requests are queueing for connections. Why might raising the pool size make it worse?
    Because the database has fixed parallelism. Past that point, more concurrent queries do not complete faster — they contend for cores, buffers and locks, so every query slows down and they all slow down together. You have moved the queue from your application, where it is visible and can be bounded with a timeout, into the database, where it is neither. The real fix is usually a faster query, a cache, or fewer queries per request.
  6. Why must the timeout budget shrink as a request goes down the stack?
    Because otherwise an inner call outlives the caller waiting for it. If the gateway gives up after 8 seconds but the database statement timeout is 30, the client gets an error while the query keeps running — consuming a connection and CPU for a result nobody will read. Under load those orphaned queries accumulate and make recovery slower. Each layer's timeout should be comfortably less than its caller's.
