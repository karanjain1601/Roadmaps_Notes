Architectural styles

The question is never how many services to have. It is where the boundaries go — and whether you are prepared to pay, in availability and latency and operational surface, for every boundary that becomes a network hop.

Start with a modular monolith. Almost always.

One deployable, one database, one transaction — but with real internal boundaries: modules that talk through explicit interfaces, no reaching into another module's tables, and a dependency rule the build enforces. This gets you nearly every benefit attributed to microservices except independent deployment, and it costs none of the distributed-systems tax. Crucially, it is far easier to split a well-modularised monolith later than to merge microservices whose boundaries turned out wrong — and boundaries drawn before you understand the domain are usually wrong. The failure mode to avoid is not "we should have started with microservices"; it is a monolith with no internal structure, which is what makes people believe the network is the only boundary that works.

Cohesion
Things that change together should live together. If a feature request routinely touches four services, those four have one boundary between them in the wrong place.
Coupling
The real metric. Two services that must be deployed together are one service with a network in the middle — all the cost, none of the independence.
Conway's law
A system's structure will come to mirror the communication structure of the organisation that builds it. This is descriptive, not aspirational, and it means architecture and team structure are the same decision made twice.
Domain boundaries
The useful ones follow the business: ordering, payments, fulfilment, identity. Boundaries drawn along technical layers — "the database service", "the validation service" — produce chatty, deploy-together services every time.

The fallacies, still being rediscovered

Peter Deutsch's list is from 1994 and every item is still assumed daily. The network is reliable — it is not, and an in-process call that could not fail is now one that can. Latency is zero — half a millisecond per hop, thousands of times a memory access. Bandwidth is infinite — serialising and deserialising every object at every boundary is real CPU. The network is secure — internal traffic needs authentication too. Topology does not change — instances come and go constantly. There is one administrator — now there are six teams with six deploy schedules. Transport cost is zero — someone pays for the cross-zone traffic. The network is homogeneous — it is not. Every one of these is a bug class that did not exist before you drew the boundary.

1.  Put a facade in front of the functionality — a route, an interface,
    an internal module boundary. Nothing else changes yet.

2.  Build the new implementation behind the facade, deployed but idle.

3.  Shadow: send real traffic to both, use the old answer, and compare.
    This is where you discover the twelve behaviours nobody documented.

4.  Shift a percentage of traffic. 1%, then 10%, then 50%, watching the
    error rate and latency at each step. Keep the switch instant.

5.  Move the data last, and only once the new path is trusted. Data
    migration is the irreversible step; keep it separate from the
    reversible ones.

6.  Delete the old path — genuinely delete it. A dead code path that is
    still deployed is a code path that will be executed by accident.

The rule that decides whether you have services or a distributed monolith

Each service owns its data, and no other service touches its tables. A shared database means every schema change is a cross-team negotiation, every service can violate another's invariants, and nothing can be deployed or scaled independently — you have paid the full network cost and kept the full coupling.

The consequence people find hardest is that cross-service transactions do not exist. Two writes in two services cannot be atomic, so you need sagas with compensating actions, or an outbox that makes the second write eventually happen — chapter 18. If your proposed split requires a distributed transaction to be correct, the boundary is in the wrong place, and that is a signal worth taking seriously rather than engineering around.

Self-check

  1. Five services each at 99.9% availability. What is the request path's availability?
    About 99.5%, since 0.999 to the fifth is 0.995 — roughly 3.6 hours of downtime a month against 43 minutes for a single service. Availability multiplies along a serial dependency path, so adding services makes the whole worse than any part. The mitigations are to reduce the number of hard dependencies, degrade gracefully when a non-essential one fails, and make each individual service more available, in roughly that order of effectiveness.
  2. Every service in a fan-out responds within 100 ms at the 99th percentile. Why is the overall request slow?
    Because a parallel fan-out waits for the slowest response, so the request's tail is governed by the probability that at least one call is slow. With 100 calls, the chance all of them beat their p99 is 0.99 to the hundredth — about 37% — so the request's p99 is determined by each service's p99.99, not its p99. Tail latency amplifies with fan-out, which is why hedging, timeouts with fallbacks, and simply calling fewer services all matter more than making the average faster.
  3. What distinguishes a modular monolith from a monolith?
    Enforced internal boundaries. Modules communicate through explicit interfaces, no module reaches into another's tables, and the build fails if a dependency rule is violated. You keep one deployment, one database and real transactions, while gaining the boundaries that make later extraction feasible. It is deliberately most of the benefit of microservices without the distributed cost, and it is much easier to split later than to merge services whose boundaries were drawn wrong.
  4. Why is a shared database between services the defining anti-pattern?
    Because it reinstates every coupling the split was supposed to remove while keeping all the new costs. Schema changes need cross-team coordination, any service can break another's invariants by writing directly, and nothing can be deployed or scaled independently. You have added network latency, partial failure and operational surface, and kept the single point of contention. Each service owning its data is what makes the boundary real.
  5. Your proposed service split needs a distributed transaction. What does that tell you?
    That the boundary is in the wrong place. Two writes across two services cannot be atomic, so you would need a saga with compensating actions or an outbox with eventual consistency — substantial complexity, chosen to work around a split you decided on. If two pieces of data must change together to remain correct, that is strong evidence they belong in the same service. Treat the requirement as a signal about the design rather than a problem to engineer past.
  6. Why does the strangler fig work better than a rewrite?
    Because every step is small and individually reversible, and the system keeps working throughout. Shadow traffic reveals the undocumented behaviours before they matter; a percentage-based shift means problems surface at one per cent rather than one hundred; and the irreversible step, moving the data, comes last and alone. A big-bang rewrite has to land everything at once, so it is either abandoned when the scope becomes clear or shipped with the behaviours nobody knew about still missing.
