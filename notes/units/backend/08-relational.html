Chapter 08 · Data

Relational data modelling

Services get rewritten every few years. The database is still there a decade later with everyone's data in it, and every mistake you made in the schema is still being worked around. This is the most expensive part of the system to get wrong and the cheapest to get right, because it costs nothing but thought at the start.

Keys and constraints

A constraint is a rule the database will enforce no matter which service, script, migration or hurried manual fix touches the data. Application validation is a courtesy to the user; constraints are the actual guarantee.

sql — a table with its invariants written down
CREATE TABLE orders (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  status        text NOT NULL DEFAULT 'pending',
  total_cents   bigint NOT NULL,
  currency      char(3) NOT NULL,
  placed_at     timestamptz NOT NULL DEFAULT now(),
  cancelled_at  timestamptz,

  CONSTRAINT total_non_negative CHECK (total_cents >= 0),
  CONSTRAINT status_known       CHECK (status IN ('pending','paid','shipped','cancelled')),
  CONSTRAINT cancelled_has_time CHECK (
      (status = 'cancelled') = (cancelled_at IS NOT NULL))  -- the good kind:
);                                                          -- two columns that
                                                            -- must agree, forever
-- a partial unique index: one active cart per user, any number of
-- historical ones. Expressing this in application code is a race condition;
-- expressing it here is a guarantee.
CREATE UNIQUE INDEX one_open_cart ON carts (user_id) WHERE status = 'open';
ChoiceTake
Surrogate or natural keySurrogate, almost always. Natural keys change — email addresses, ISBNs, national identifiers all turn out to be mutable or non-unique eventually, and by then they are foreign keys in nine tables
Sequential integer or UUIDIntegers are compact and index beautifully; UUIDs avoid enumeration and can be generated client-side. Use UUIDv7 or ULID, which are time-ordered — random UUIDv4 primary keys scatter inserts across the whole index and hurt write throughput badly
ON DELETE behaviourRESTRICT by default so deletes fail loudly; CASCADE only where the child genuinely cannot exist alone, such as order line items
Soft deleteAdds WHERE deleted_at IS NULL to every query forever, and the one you forget is a data leak. Prefer moving rows to an archive table, or accept the cost knowingly
EnumsA CHECK constraint or a lookup table beats a native enum type, which needs a migration to add a value and cannot remove one
Nullable columnsDefault to NOT NULL. Every nullable column is a branch in every query and a case somebody forgets

Normalisation

The formal definitions are less useful than the thing they prevent. Redundancy is not a storage problem — it is a correctness problem, because the same fact stored twice can disagree with itself.

Three anomalies
Try each operation against both designs
FormRuleIn plain terms
1NFAtomic values; no repeating groupsNo tags column holding "red,blue,green". No phone1, phone2, phone3
2NFNo partial dependency on a composite keyIf the key is (order_id, product_id), the product's name depends on only half of it — so it belongs elsewhere
3NFNo transitive dependencyStoring city and country against a postcode means the postcode determines them, so they belong with the postcode
BCNFEvery determinant is a candidate keyA stricter 3NF. Rarely the thing that bites you
Normalise first, then denormalise on evidence

3NF is the right starting point for essentially every transactional schema. It is easy to reason about, it makes each fact live in exactly one place, and it lets the database enforce consistency rather than hoping the application does.

Denormalise when you have a measured problem, and when you do, follow two rules. Have one authoritative copy — the derived one must be reconstructible from it. Update it in the same transaction, or accept explicitly that it is eventually consistent and can be stale. The legitimate cases are real: a cached comment_count to avoid counting a million rows, a denormalised seller_name on an order so it reflects the name at the time of sale rather than today's, or a reporting table built for a dashboard. Each is a deliberate trade with a named benefit — not "joins are slow", which is usually a missing index. Chapter 9.

Time is worse than you think

Store instants in UTC as timestamptz and convert only for display. But note that future local events are different: "the meeting is at 09:00 Berlin time on 3 March" cannot be stored as a UTC instant, because Germany may change its rules before then — and countries do this with a few months' notice. Store the local time and the IANA zone name separately, and resolve to an instant when you need one. Also: never store a zone as an offset like +02:00, because that is a fact about one moment rather than a place, and Europe/Berlin is the durable answer.

Migrations without downtime

During a rolling deploy, the old and new versions of your code run at the same time against the same database. Every schema change must therefore be compatible with both — which rules out the obvious way to do almost everything.

Renaming a column, twice
Try the obvious way first
ChangeSafe?Note
Add a nullable columnYesMetadata-only in modern Postgres and MySQL
Add a column with a defaultYes, since PG 11 / MySQL 8Older versions rewrote the entire table. Check your version before assuming
Add NOT NULL to an existing columnNo — full table scan under a lockAdd a CHECK … NOT VALID, validate it separately, then convert
Rename a column or tableNever, in one stepExpand and contract. The demo above
Create an indexBlocks writesUse CREATE INDEX CONCURRENTLY — slower, no lock, and it can fail and leave an invalid index to clean up
Add a foreign keyLocks both tables to validateAdd NOT VALID, then VALIDATE CONSTRAINT — which takes a weaker lock
Drop a columnFast, and irreversibleDeploy code that stops referencing it first, and wait a full release cycle before dropping
Change a column's typeUsually a full rewriteNew column, backfill, switch, drop. The same expand-and-contract shape
Backfill a large tableNot in one statementBatch it — a few thousand rows per transaction, with a pause. One giant UPDATE holds locks and bloats the write-ahead log
The migration checklist
  1. Is it backwards compatible? The currently-deployed code must keep working after the migration and before the next deploy.
  2. Does it take a lock, and for how long? A lock held for two seconds on a busy table queues every query behind it, and the queue may not drain.
  3. Set a lock timeout. SET lock_timeout = '3s' so the migration fails fast instead of blocking production while it waits for a long-running transaction to finish.
  4. Is the backfill batched? With a pause between batches, and restartable if it dies halfway.
  5. Can it be rolled back? Not every migration can — dropping a column is not reversible — which is precisely why the drop comes a release after the code change.

Self-check

  1. Why is redundancy a correctness problem rather than a storage one?
    Because two copies of the same fact can disagree. Storing a customer's email on every one of their order rows means updating an email is a multi-row write, and any path that misses a row leaves the database asserting two different emails for one person — with no way to tell which is right. Disk is cheap; a system that contradicts itself is not. Normalisation makes each fact live in exactly one place, so it cannot be half-updated.
  2. When is denormalisation justified, and what two rules apply?
    When you have measured a problem that normalisation causes — counting a million rows for a comment count, or a report that cannot meet its latency budget. The rules: keep one authoritative copy so the derived one can always be rebuilt, and either update it in the same transaction or state explicitly that it is eventually consistent. "Joins are slow" is not evidence; it is usually a missing index.
  3. Why should money never be a float?
    Because binary floating point cannot represent most decimal fractions exactly — 0.1 + 0.2 is 0.30000000000000004 — so errors accumulate across arithmetic and totals stop reconciling. Use an integer count of minor units (cents, pence) or a fixed-point numeric type. Integers are usually simpler: exact, fast, and they make you think about rounding at the one point where it matters rather than everywhere.
  4. Why is renaming a column unsafe during a rolling deploy?
    Because both versions of the code run simultaneously against the one database. The instant the rename commits, every still-running old instance references a column that no longer exists, and its queries fail — a period of errors lasting until the rollout finishes, which is exactly when you cannot roll back either, since reverting the code breaks against the new name. Expand and contract keeps both names valid across the overlap.
  5. What does "expand and contract" actually consist of?
    Add the new column without removing the old one. Deploy code that writes to both and reads the old. Backfill existing rows in batches. Deploy code that reads the new column, still writing both. Then, a release later, stop writing the old one and drop it. Each step is compatible with the version before and after it, so at no point does a running instance depend on something that does not exist.
  6. Why avoid a native enum type in favour of a CHECK constraint?
    Because a native enum requires a schema migration to add a value, and removing one ranges from awkward to impossible — which matters because status values change more often than anyone expects. A text column with a CHECK gives the same validation, and altering the constraint is a cheap operation. A lookup table goes further: values become data, so adding one is an insert, and you get somewhere to hang labels and ordering.
