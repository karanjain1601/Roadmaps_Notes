Transactions and isolation

A single user is easy. The interesting bugs live where two requests touch the same rows at the same moment, and they are the kind that pass every test, survive review, and appear in production as a double charge or a negative balance nobody can reproduce.

— words— min read2 interactivesNeeds: chapter 08

ACID, precisely

Atomicity
All of the transaction's changes happen, or none do. It says nothing about concurrency — the name misleads people constantly. A better word would be abortability: the guarantee is that a failure halfway leaves no trace.
Consistency
The odd one out, and arguably not a database property at all. It means the transaction takes the database from one valid state to another according to your rules — which the database can only help with through constraints. The C was included largely to make the acronym work.
Isolation
The one this chapter is about. How much concurrent transactions can see of each other. In principle it means "as if they ran one at a time"; in practice it is a dial, and the default setting is not that.
Durability
Once committed, it survives a crash — written to a write-ahead log and flushed. On a single node this is well understood; in a replicated system it becomes "durable where?", which is chapter 19.
The default is not serialisable

Almost every database you will use defaults to read committed, which prevents exactly one of the five anomalies below. Most developers assume transactions mean "as if run one at a time" and write code accordingly. The gap between that assumption and the actual default is where a large share of concurrency bugs live, and the demo below is the fastest way to see it.

The row that matters is the last one

Write skew is the anomaly people have not heard of, and the only one that survives repeatable read. Two transactions each read some data, each check a condition that currently holds, and each write to different rows — so they never conflict directly, and snapshot isolation sees no problem. But together their writes break the invariant that each checked individually. The textbook case is two on-call doctors each going off duty after confirming the other is still on; the practical cases are booking the last seat twice, spending the same budget twice, and letting two people claim one username. If your invariant spans multiple rows, repeatable read will not save you — you need serialisable, or an explicit lock on something both transactions must touch.

MVCC and locking

Postgres, Oracle and MySQL's InnoDB all avoid read locks entirely by keeping multiple versions of each row. A reader sees the version that was current when its snapshot began, so readers never block writers and writers never block readers — the property that makes these databases usable under load.

How it works
Every row version carries the transaction id that created it and the one that deleted it. A transaction's snapshot determines which versions are visible. An UPDATE is therefore an insert of a new version plus a mark on the old one, not an in-place edit.
What it costs
Dead versions accumulate and must be cleaned up — VACUUM in Postgres. A long-running transaction pins every version created since it started, so one forgotten open transaction can bloat a table by gigabytes and make every scan slower.
What still locks
Writes to the same row. Two transactions updating one row serialise: the second waits for the first to commit or roll back. This is the correct behaviour and the source of most lock waits.

SELECT quantity FROM cart_items WHERE id = 'x';   -- 1
UPDATE cart_items SET quantity = 2 WHERE id = 'x';   -- computed in app

-- ② pessimistic: take the row lock on read. Correct; serialises writers.
SELECT quantity FROM cart_items WHERE id = 'x' FOR UPDATE;
UPDATE cart_items SET quantity = 2 WHERE id = 'x';
--    add NOWAIT to fail instantly rather than queue, or SKIP LOCKED to

-- ③ optimistic: no lock. Detect the conflict at write time and retry.
SELECT quantity, version FROM cart_items WHERE id = 'x';
UPDATE cart_items SET quantity = 2, version = version + 1
 WHERE id = 'x' AND version = 7;
--    0 rows updated means somebody got there first: re-read and retry.
--    this is what HTTP's If-Match and ETag do at the API layer.

-- ④ atomic: let the database do the arithmetic. No window at all.
UPDATE cart_items SET quantity = quantity + 1 WHERE id = 'x';
--    correct, one round trip, no retry loop. When the new value is a

Deadlocks, and the one rule that prevents most of them

Transaction A locks row 1 then wants row 2; transaction B locks row 2 then wants row 1. Neither can proceed. The database detects the cycle after a second or so and kills one with a deadlock error — which your application must be prepared to retry, because it is a normal event rather than a bug.

Acquire locks in a consistent order — sort the ids before updating a batch, and always touch tables in the same sequence — and most deadlocks disappear. Beyond that: keep transactions short, do not perform network calls inside one, and never begin a transaction before validating input. The commonest real-world deadlock is a bulk update that processes rows in whatever order the application happened to have them in.

Practical rules
  • Keep transactions short. Every millisecond a transaction is open is a millisecond of held locks, pinned row versions and replication lag.
  • No HTTP calls inside a transaction. A slow payment provider should not be holding your database's locks. Chapter 18's outbox pattern exists for this.
  • Use atomic statements where the new value derives from the old. It removes the problem rather than guarding it.
  • Make retryable errors retryable. Serialisation failures and deadlocks are expected; wrap the transaction in a retry with backoff and treat it as ordinary.
  • Raise the isolation level for the transactions that need it, not globally. Serialisable costs throughput and aborts; apply it where an invariant spans rows.
  • Put the invariant in a constraint if you possibly can. A unique index cannot be defeated by any interleaving, which is a stronger guarantee than any isolation level and costs nothing to check.

Self-check

  1. What does atomicity not promise?
    Anything about concurrency. Atomicity says a transaction's changes are all applied or none are — a guarantee about failure, not about other transactions. Isolation is the property that governs what concurrent transactions see of each other, and it is a dial rather than a binary. Conflating the two is why people assume a transaction means "as if it ran alone", which is only true at the serialisable level.
  2. What is write skew, and why does repeatable read not prevent it?
    Two transactions each read a set of rows, each verify a condition that currently holds, then each write to different rows — so there is no direct write-write conflict for snapshot isolation to detect. Individually both are valid; together they break the invariant, such as two doctors both going off call after each confirms the other is still on. Repeatable read only checks that the rows you wrote were not changed by someone else, and here they were not. Serialisable tracks read-write dependencies as well, and aborts one.
  3. Why does MVCC mean readers never block writers?
    Because a read does not need a lock — it needs a version. Each row keeps multiple versions tagged with the transactions that created and deleted them, and a reader's snapshot selects which version is visible. A writer creating a new version does not disturb the old one, so the reader continues undisturbed. The cost is that dead versions accumulate and need vacuuming, and a long-running transaction pins every version created since it started.
  4. Two requests increment the same counter and it only goes up by one. Name three fixes and pick the best.
    SELECT … FOR UPDATE to lock on read; an optimistic version column so the second update matches zero rows and retries; or a single atomic statement, SET n = n + 1. The atomic statement is best here: one round trip, no lock held across a network hop, no retry loop, and no window between reading and writing because there is no separate read. Reach for the others when the new value is not a simple function of the old one.
  5. When is optimistic concurrency the right choice over a lock?
    When conflicts are rare, and especially when the gap between reading and writing spans a user's thinking time. You cannot hold a database lock while someone edits a form for four minutes, so the edit-conflict case must be optimistic: read the version, submit it with the write, and reject the write if it changed. HTTP's ETag and If-Match are the same mechanism at the API layer. Under heavy contention it inverts, since every conflicting transaction does its work and then throws it away.
  6. Why is a unique index a stronger guarantee than any isolation level?
    Because it is enforced by the storage engine on every write regardless of transaction, interleaving, isolation level or which service issued the statement. An application-level check-then-insert has a window between the check and the insert that some interleaving will find; a unique index has no window. Wherever an invariant can be expressed as a constraint — including partial and multi-column unique indexes — that is the cheapest and most reliable place to put it.
