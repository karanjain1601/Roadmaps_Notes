Authentication and authorization

Two different questions that get one word between them. Who is this, and what may they do — and the second is where the expensive mistakes are, because getting authentication wrong locks people out while getting authorization wrong lets them into other people's data.

Sessions or tokens

The most consequential architectural choice in authentication, and it is usually made by copying a tutorial. The trade is not really about scale — it is about whether you can take access away.

JWT traps, in the order people hit them
  • No revocation. The defining property. A stolen or fired user's token is valid until it expires, and the usual response — a denylist checked on every request — reintroduces exactly the state the token was meant to avoid, plus a signature check.
  • Long expiry. The workaround for having no revocation is a short lifetime, so access tokens should live minutes, not weeks. Anything longer is a bearer credential with no off switch.
  • Algorithm confusion. alg: none, and passing an RSA public key as an HMAC secret. Never let the token tell you how to verify it — pin the algorithm in your validation config.
  • Missing claim checks. Verifying the signature is not enough. Check exp, nbf, iss and aud, or a valid token for a different service is a valid token for yours.
  • Storing it in localStorage. Any XSS reads it. An HttpOnly cookie cannot be read by script, which is why the "JWTs avoid CSRF" argument is usually made by people who then put the JWT in a cookie.
  • Putting secrets in the payload. It is base64, not encryption. Anyone holding the token can read every claim.

The honest default: for a browser application talking to your own backend, an opaque session id in an HttpOnly, Secure, SameSite=Lax cookie is simpler, smaller and revocable. Reach for JWTs when you genuinely need stateless verification across services or a federated identity provider — not because they are newer.

OAuth 2.0 and OIDC

OAuth is a delegated authorization protocol: it lets an application act on a user's behalf without seeing their password. OIDC is a thin layer on top that adds identity, and it is the one you want for "sign in with…".

Refresh token rotation and reuse detection

Access tokens are short-lived; refresh tokens are not, which makes them the valuable thing to steal. Rotation means each refresh returns a new refresh token and invalidates the old one. Reuse detection is what makes rotation worth doing: if an already-used refresh token is presented again, either it was replayed by an attacker or the legitimate client is retrying — and since you cannot tell which, you revoke the entire token family and force a fresh login. The theft is contained to one access-token lifetime, and you get a signal that it happened.

python — where authorization must actually happen
# ✗ broken: authenticated, but not authorised. Any logged-in user can
#   read any invoice by changing the id. This is IDOR — consistently
#   the most common serious flaw in real APIs.
@app.get("/v1/invoices/{invoice_id}")
def get_invoice(invoice_id, user = Depends(current_user)):
    return db.get_invoice(invoice_id)

# ✓ scope the query by the actor, rather than checking afterwards.
#   a filter cannot be forgotten the way a conditional can.
@app.get("/v1/invoices/{invoice_id}")
def get_invoice(invoice_id, user = Depends(current_user)):
    inv = db.get_invoice(invoice_id, account_id=user.account_id)
    if inv is None:
        raise NotFound()      ← 404, not 403: do not confirm that an
    return inv                  invoice with this id exists elsewhere

# in a multi-tenant system, make it structural rather than a habit:
#   · a session-level tenant id plus row-level security in Postgres, or
#   · a repository layer where every query requires a tenant argument
# any design where a developer must remember to add the filter will
# eventually meet a developer who does not.
Four authorization mistakes worth checking for today
  • Enforcing in the UI. Hiding the delete button is not access control. Every endpoint must check independently, because the endpoint is the interface.
  • Checking on read but not on write. The GET is scoped by tenant, the PATCH takes the id from the path and trusts it.
  • Trusting client-supplied identifiers. An account_id in the request body is a suggestion. Derive the actor's identity from the session or token, never from the payload.
  • Mass assignment. Binding a request body straight onto a model lets a user set role or account_id by adding the field. Use an explicit allow-list of updatable fields.

Self-check

  1. Why is SHA-256 wrong for passwords even with a unique salt per user?
    Because the salt solves a different problem. It defeats precomputed rainbow tables, but does nothing about brute force — and SHA-256 is designed to be fast, so commodity hardware tries billions of candidates per second against a stolen hash. Password hashes must be deliberately slow and memory-hard, which is what argon2id, scrypt and bcrypt are for. The cost parameter is the security property; the salt is table stakes.
  2. What is the real trade between server sessions and stateless JWTs?
    Revocation, not performance. A session lookup is a sub-millisecond cache hit, so the stateless advantage is small; what you give up is the ability to end a session. A JWT stays valid until it expires, so a fired employee, a stolen token or a demoted role remains in effect for the token's lifetime. Adding a denylist restores revocation and reintroduces the state — at which point you have a session with extra steps and a larger cookie.
  3. Why must you pin the algorithm when verifying a JWT?
    Because the token's own header names the algorithm, and trusting it lets the attacker choose. Historically that meant alg: none, where a library would accept an unsigned token; the subtler version is submitting an HS256 token signed with your published RSA public key, which a naive verifier treats as the HMAC secret. Configure the accepted algorithm on the verification side and reject anything else before looking at the payload.
  4. What does PKCE prevent, and why is it needed even with HTTPS?
    Interception of the authorization code before the exchange. On mobile, a malicious app can register the same custom URI scheme and receive the redirect; a code arriving over TLS can still land in the wrong application's hands. PKCE makes the client commit up front to a secret verifier by sending only its hash, so a stolen code cannot be exchanged without the verifier — which never left the legitimate client. It is now recommended for every client type, not just public ones.
  5. What is refresh token reuse detection and why does rotation need it?
    Rotation issues a new refresh token on every use and invalidates the old one. Reuse detection is what happens when an already-consumed token is presented again: either an attacker is replaying a stolen copy or the real client is retrying after a lost response, and you cannot tell which — so you revoke the whole token family and require a fresh login. Without detection, rotation only makes the stolen token stale; with it, theft is bounded to one access-token lifetime and you get an alert.
  6. Why return 404 rather than 403 for a resource belonging to another tenant?
    Because 403 confirms the resource exists. An attacker enumerating identifiers learns which ones are real, which leaks customer counts, growth rates and sometimes the identifiers themselves for use elsewhere. Answering 404 makes "not yours" indistinguishable from "not there". The stronger version is structural: scope the query by tenant so a row from another account is never fetched, rather than fetching it and then deciding.
