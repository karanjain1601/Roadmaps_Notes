Caching

The cheapest way to make something fast is not to do it. Caching is also where correctness quietly goes wrong, because a cache is a second copy of the truth that nothing forces to agree with the first — and the failure mode is not an error, it is a plausible wrong answer.

Cache furthest from the database first

A response served by a CDN costs you nothing — no bandwidth, no CPU, no connection, no database. A response served from Redis still costs a round trip and a worker. A page cached in application memory saves the query but not the request. The layers compound, so the ordering of effort is: make it cacheable by the browser and CDN, then cache the expensive computation, then cache the query result, then optimise the query. Most teams do that list backwards.

The stampede

One popular key expires. Every request that arrives in the next few hundred milliseconds misses, and all of them go to the database to compute the same value at the same instant.

# ── ① single-flight: one recomputes, the rest wait briefly ──
def get_with_lock(key, compute, ttl=300):
    hit = redis.get(key)
    if hit: return json.loads(hit)

    if redis.set(key + ":lock", "1", nx=True, ex=10):   # exactly one wins
        try:
            val = compute()
            redis.set(key, json.dumps(val), ex=ttl)
            return val
        finally:
            redis.delete(key + ":lock")

    time.sleep(0.05)                    # everyone else waits and re-reads.
    return get_with_lock(key, compute, ttl)   # bound this recursion in real code

# ── ② stale-while-revalidate: nobody waits at all ──
def get_swr(key, compute, fresh=300, keep=3600):
    entry = redis.get(key)                       # stored with its own expiry
    if entry:                                    # timestamp INSIDE the value, and
        e = json.loads(entry)                    # a much longer Redis TTL
        if e["expires"] < time.time():
            if redis.set(key + ":lock", "1", nx=True, ex=30):
                background.submit(refresh, key, compute, fresh, keep)
        return e["value"]                      ← returns instantly, fresh or not
    return get_with_lock(key, compute, keep)     # only the very first caller waits

Three related failures worth naming
  • Cache penetration. Requests for a key that does not exist miss every time and hit the database every time — trivially weaponised by requesting random ids. Cache the negative result with a short TTL, or use a Bloom filter.
  • Cache avalanche. Many keys expiring together, usually because they were all populated at the same moment by a deploy or a warm-up script. Jitter every TTL.
  • The cold restart. The cache is flushed or the Redis instance is replaced, and every request goes to a database sized for a ninety per cent hit rate. This is a genuine outage cause and the reason people are nervous about failing over their cache — warm it before sending traffic.

What not to cache
  • Anything you must not serve stale. Balances, stock levels at the point of purchase, permission checks. Cache the expensive parts around them if you must, and read the decisive value live.
  • Data that changes on nearly every read. The hit rate will be near zero and you have added a network hop and a failure mode for nothing.
  • Cheap queries. An indexed lookup at 1 ms and a Redis round trip at 1 ms are the same speed. Cache what is expensive, not what is frequent.
  • Personalised responses in a shared cache, without the user in the key. Chapter 3's Vary problem in another layer.

And the honest caveat: a cache hiding a slow query is a slow query you will meet again — during a cold start, a cache failover, or the first request after a deploy. Fix the query where you can, and cache what remains genuinely expensive.

Self-check

  1. Why delete a cache key on write rather than update it?
    Because updating races. Two concurrent writers can set the key in the opposite order to their database commits, leaving the older value cached indefinitely — and a reader that missed just before your write can repopulate the key with pre-update data after it. Deleting is idempotent and cannot leave a wrong value behind: the worst case is an extra miss. It also avoids caching values nobody will read.
  2. Why invalidate after committing rather than before?
    Because between the invalidation and the commit there is a window in which the row still holds its old value. A concurrent read misses the cache, loads the pre-commit row, and populates the cache with data that is about to become stale — and now the cache is wrong with a full TTL ahead of it. Committing first shrinks the window to the gap between commit and delete, where the cache is stale but about to be cleared.
  3. Describe a cache stampede and the mechanism that prevents waiting entirely.
    A hot key expires and every request arriving during the recomputation misses, so hundreds of identical expensive queries run simultaneously — often enough to overwhelm the database, which makes recomputation slower, which widens the window. Single-flight locking fixes the load by letting one caller compute while the rest wait. Stale-while-revalidate goes further and removes the waiting too: keep the value past its freshness deadline, return it immediately, and refresh in the background. Nobody blocks, and the database sees one query.
  4. Why jitter TTLs?
    Because keys populated at the same moment expire at the same moment. A deploy, a warm-up script or a cache flush creates thousands of entries with identical TTLs, and five minutes later they all expire together — a synchronised avalanche rather than one stampede. Adding a random offset of ten per cent or so spreads the expiries across a window and turns a spike into a trickle. It costs one line.
  5. What is cache penetration and why is it a security concern?
    Requests for keys that do not exist never populate the cache, so every one reaches the database. An attacker who requests random product ids therefore bypasses your cache entirely and sends full load to the database — a denial of service against a system that looks well protected. The fix is to cache the negative result with a short TTL, so the second request for a missing id is also served from cache, optionally with a Bloom filter to reject impossible keys before touching either layer.
  6. Your endpoint is fast because of caching. What should still worry you?
    What happens when the cache is empty. Cold starts, deploys that flush a local cache, a Redis failover, or an eviction storm all send full traffic to a database that has been sized for a ninety per cent hit rate — and it will not cope. The cache is hiding the real cost rather than removing it. Know what your uncached latency and throughput are, keep the underlying query survivable, and warm the cache before sending traffic to a new instance.
