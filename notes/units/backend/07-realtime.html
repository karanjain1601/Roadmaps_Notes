Real-time and streaming

Everything so far assumes the client asks and the server answers. Notifications, live dashboards, chat and collaborative editing invert that, and HTTP was not designed for it. Four workarounds exist; two of them are good, and choosing between those two is mostly not a technical question.

The choice that matters is SSE against WebSockets

The demo shows their bandwidth is nearly identical — an SSE event costs about eight bytes of framing, a WebSocket frame about six. Efficiency is not the deciding factor, and picking WebSockets for performance is picking it for the wrong reason.

SSE is ordinary HTTP. Your existing authentication, cookies, compression, load balancer, logging and HTTP/2 multiplexing all work unchanged, and the browser reconnects automatically and tells the server which event it last saw. WebSockets leave HTTP behind after the upgrade: no status codes, no headers per message, no standard authentication, no automatic reconnection, and a protocol you now design yourself. That is a fair price for genuine bidirectional messaging and far too much to pay for a notification feed. If the data flows one way, use SSE.

Three SSE gotchas
  • Proxy buffering. nginx buffers responses by default, so events accumulate and arrive in a batch — or never. X-Accel-Buffering: no, or proxy_buffering off.
  • The HTTP/1.1 connection limit. Six connections per origin, and an open SSE stream permanently occupies one. Two tabs and a few parallel requests can deadlock the page. Under HTTP/2 the streams are multiplexed and the problem disappears, which is a concrete reason to enable it.
  • Send a keepalive. A comment line — : ping — every fifteen seconds or so. Idle connections are reaped by proxies, load balancers and mobile networks with no notification to either end.

WebSockets, and what they cost to run

The connection is easy. Everything after the connection — authentication, reconnection, backpressure, and the fact that you now have more than one server — is the actual work.

One message, several instances

3
Authentication
The browser's WebSocket API cannot set headers, so no Authorization. The options are a cookie sent with the upgrade — which works and inherits CSRF concerns — or a short-lived ticket in the query string, exchanged for a session as the first message. Never a long-lived token in the URL: it lands in access logs and referrer headers.
Reconnection
You write it. Exponential backoff with jitter, or every client reconnects in unison the moment a deploy finishes and takes down the instance that just came up. Chapter 19.
Message ordering and loss
Delivery is ordered within a connection and lost across a reconnection. If the client must not miss anything, send sequence numbers and let it request a replay — the same idea as SSE's Last-Event-ID, built by hand.
Backpressure
A slow client cannot keep up, and the server's send buffer grows until memory does. Bound the queue per connection and decide the policy explicitly: drop the oldest, drop the newest, coalesce, or disconnect. Silently buffering is how one bad mobile connection exhausts a server.
Deploys
Every deploy severs every connection. With a thousand clients that is a thundering reconnect; with a hundred thousand it is an outage. Drain gradually, and stagger the reconnect with jitter.
javascript — the client half nobody writes until it breaks
let attempt = 0, ws;

function connect() {
  ws = new WebSocket(url);

  ws.onopen = () => { attempt = 0; ws.send(JSON.stringify({resume: lastSeq})); };

  ws.onclose = () => {
    const base  = Math.min(30000, 1000 * 2 ** attempt++);
    const delay = base * (0.5 + Math.random() * 0.5);   ← the jitter is the point
    setTimeout(connect, delay);   // without it, every client returns
  };                              // at the same instant after a deploy

  ws.onmessage = e => { const m = JSON.parse(e.data); lastSeq = m.seq; apply(m); };
}

// and a heartbeat, because a dead TCP connection looks exactly like an
// idle one until you try to write to it — often minutes later
setInterval(() => ws.readyState === 1 && ws.send('{"t":"ping"}'), 20000);
Sticky sessions are not the fix

A common first response to the fan-out problem is to make the load balancer pin each client to an instance. That solves a different problem — it keeps a client on the instance holding its connection — and does nothing about a message published elsewhere, because the recipients were never on the publisher's instance to begin with. It also makes deploys and autoscaling worse, since traffic cannot be rebalanced. The fan-out problem needs a shared bus: Redis pub/sub for simplicity, or a proper broker when you need durability and replay. Chapter 18.

Self-check

  1. Why is short polling wasteful even when the poll interval seems reasonable?
    Because the cost is driven by the interval rather than by how often anything happens. Ten thousand clients polling every five seconds generate two thousand requests per second whether there is one event an hour or none at all, and each carries full HTTP headers and cookies for a response that usually says "nothing new". Push transports cost roughly the number of actual events, so their overhead scales with useful work instead of with time.
  2. SSE and WebSockets use almost the same bandwidth. So what actually distinguishes them?
    Direction and integration. SSE is one-way and remains ordinary HTTP, so authentication, cookies, compression, HTTP/2 multiplexing, logging and load balancing all work unchanged, and the browser handles reconnection and resumption for you. WebSockets are bidirectional and abandon HTTP after the upgrade, so you design the message protocol, the authentication, the reconnection and the resumption yourself. Choose on whether the client needs to send messages, not on efficiency.
  3. Your SSE endpoint works locally and delivers nothing through nginx. Why?
    Response buffering. nginx accumulates the response before forwarding it, which is normally an optimisation and is fatal for a stream that never ends — events pile up in the buffer and the client sees nothing. Setting X-Accel-Buffering: no on the response, or proxy_buffering off in the configuration, disables it. The same class of problem appears with any intermediary that assumes responses are finite.
  4. A client on instance B does not receive a message published on instance A. What is happening?
    Each instance holds only its own connections, so publishing on A can only reach clients connected to A. With three instances roughly two thirds of recipients get nothing, and the failure is partial and confusing rather than total. The fix is a shared bus — Redis pub/sub, or a broker — so a message published anywhere is delivered to every instance, each of which forwards it to its own connections.
  5. Why do sticky sessions not solve that?
    Because stickiness keeps a client on the instance holding its connection, which was never the problem — the recipients are on other instances by design, since connections are distributed. Stickiness also makes deploys and autoscaling harder, since traffic cannot be rebalanced and draining an instance means severing its clients. Fan-out is a routing problem between servers, and it needs a bus between them.
  6. Why does reconnection backoff need jitter?
    Because without it every client that was disconnected together retries together. A deploy severs all connections at once, and one second later the whole population reconnects simultaneously — a synchronised spike that can overwhelm the instance that just started, causing another failure and another synchronised retry. Multiplying the delay by a random factor spreads the returns across the window and turns a spike into a ramp.
