Indexes and query performance

The single highest-leverage topic in the unit. An index turns a query that reads two million rows into one that reads forty, and most production slowdowns are one missing or unusable index. The second half of the chapter is the more useful half: why the index you created is being ignored.

— words— min read2 interactivesNeeds: chapter 08

What an index is

A separate, sorted structure holding the indexed columns plus a pointer to the row. Because it is sorted, the database can find a value by descending a tree instead of reading everything — the same B-tree from chapter 12 of the algorithms unit, sized so each node is one disk page.

What it buys
Lookups by the indexed columns, range scans, sorted output without a sort, and uniqueness enforcement — all in logarithmic rather than linear time.
What it costs
Every insert, update and delete must maintain it. A table with eight indexes does roughly nine writes per row written. Indexes also occupy space, often more than the table, and compete for cache.
The consequence
Indexes are not free and more is not better. The right number is the smallest set that serves your actual query patterns, which means you need to know what those are — pg_stat_statements rather than intuition.

Composite indexes and column order

An index on three columns is not three indexes. It is one index sorted by the first column, then the second within that, then the third — like a phone book ordered by surname, then forename. That ordering is the whole rule.

sql — the ordering rule, and the rules of thumb that follow from it
CREATE INDEX ON orders (status, created_at, user_id);

-- ① equality columns first, range columns last. A range "opens up" the
--    index: everything after it can no longer be used for filtering,
--    because the rows are no longer contiguous by the next column.

-- ② ORDER BY can be served by the index only if the preceding columns
--    are all equalities — and the direction must match, or be exactly
--    reversed for every column.

-- ③ if you have (a, b), you do NOT also need (a). The composite index
--    already serves any query on a alone. You DO need (b) separately.

-- ④ a partial index is often better than a wider one:
CREATE INDEX ON orders (created_at) WHERE status = 'pending';
--    if 2% of orders are pending, this index is 2% of the size, stays in
--    cache, and is only maintained when a pending row changes.

-- ⑤ an expression index, for when the query wraps the column:
CREATE INDEX ON users (lower(email));   -- makes WHERE lower(email) = …
--                                          usable. Chapter section below.
Covering indexes and index-only scans

An index scan normally does two things: find the matching entries in the index, then fetch each row from the table to read the columns the query wants. That second step is a random read per row, and it is most of the cost. If every column the query touches is already in the index, the table is never visited — an index-only scan, and often an order of magnitude faster. Postgres supports INCLUDE for exactly this: CREATE INDEX ON orders (user_id) INCLUDE (total_cents, status) keeps the extra columns in the leaf pages without making them part of the sort key. It is the cheapest large win available on a hot read path, and the cost is a wider index.

Indexes you should delete

Unused indexes cost write throughput, space and cache on every single insert, and they accumulate because nobody feels able to remove one. pg_stat_user_indexes reports idx_scan — the number of times each index has been used since statistics were reset. Any index with a scan count of zero after a full business cycle, that is not enforcing a uniqueness constraint, is dead weight. Also look for redundant prefixes: if you have an index on (a, b) then a separate index on (a) is almost always pointless, because the composite serves those queries already.

Self-check

  1. Why is an index not always faster?
    Because an index scan is a random access per matching row — descend the tree, then fetch that row from the table — while a sequential scan reads pages in order, which storage and prefetching handle far better. Once the query matches enough of the table, doing hundreds of thousands of scattered reads costs more than streaming everything in order. The crossover is typically somewhere between five and fifteen per cent, and when the planner picks a scan above it, it is usually right.
  2. You have an index on (status, created_at). Which of these can use it: filtering on status, on created_at, on both?
    Status alone, and both together. Created_at alone cannot use it, because the index is sorted by status first — rows for a given date are scattered across every status group rather than being contiguous, so there is no range to seek to. This is the leftmost prefix rule, and it is why column order in a composite index is a design decision rather than a formatting one.
  3. Why should equality columns come before range columns?
    Because a range opens the index up. With status = 'pending' AND created_at > d, an index on (status, created_at) seeks to the pending block and then reads a contiguous run of dates — both columns used. Reverse the order and the index seeks to a date range, within which statuses are mixed, so status can only be checked row by row afterwards. Everything after the first range column stops being useful for narrowing.
  4. What is an index-only scan and why is it so much faster?
    A scan where every column the query needs is present in the index, so the table itself is never read. That removes one random access per matching row, which is normally the dominant cost — often an order of magnitude on a wide table. Postgres's INCLUDE clause adds payload columns to the leaf pages without making them part of the sort key, which is the cheap way to get one on a hot read path.
  5. WHERE date(created_at) = '2026-03-01' does not use the index on created_at. Why, and what are the two fixes?
    Because the index stores created_at, not date(created_at). Applying a function means the database would have to compute it for every row to compare, which is precisely the scan an index avoids. Either index the expression — CREATE INDEX ON t (date(created_at)) — or rewrite the predicate as a range on the raw column: created_at >= '2026-03-01' AND created_at < '2026-03-02'. The rewrite is usually better, since it keeps one index serving every date query rather than only whole-day ones.
  6. Which query should you optimise first: one averaging 2 seconds, or one averaging 4 ms?
    Whichever has the higher total time. If the 4 ms query runs fifty thousand times a minute it consumes over three minutes of database time per minute, while the 2-second query run twice an hour consumes four seconds. Sort pg_stat_statements by total_exec_time, not by mean — the slowest query is rarely the most expensive one, and optimising by anecdote sends you to the wrong place.
