Chapter 06 · Serving requests

GraphQL, gRPC and the alternatives

REST has two well-known weaknesses: it sends clients data they did not want, and it makes them ask several times for data they did. Both alternatives in this chapter start from that observation and end up somewhere very different — one optimising for the client's freedom, the other for the wire.

— words— min read2 interactivesNeeds: chapter 05

The problem being solved

A screen needs a specific shape of data. A REST API exposes resources. Those two things rarely line up, and the mismatch has two names.

Over-fetching
GET /users/me returns forty fields because some other screen needs them. Your header shows a name and an avatar. The rest was bandwidth, serialisation and database work spent on nothing.
Under-fetching
You need orders, and then the products in those orders. That is two round trips minimum, three if you also want the seller. On a 30 ms connection nobody notices; on a 200 ms mobile connection the screen takes most of a second to assemble.

GraphQL

One endpoint, a typed schema, and the client states exactly what it wants. The server returns that shape and nothing else.

graphql — schema, then a query against it
# the schema is the contract, and it is machine-readable — which is where
# the tooling, the editor autocomplete and the type generation come from
type User {
  id: ID!
  name: String!
  orders(first: Int = 10, after: String): OrderConnection!
}
type Order {
  id: ID!
  total: Money!
  items: [OrderItem!]!
}

# the client asks for a shape, and gets exactly that shape back
query HomeScreen {
  me {
    name
    avatarUrl
    orders(first: 3) {
      nodes {
        id total placedAt
        items { product { title } }    # the nested fetch, in one trip
      }
    }
  }
}
Where GraphQL bites

N+1 in the resolvers. The query above looks like one request. Naively resolved it is one query for the user, one for the orders, then one per order for the items and one per item for the product — dozens of queries behind a single HTTP call. The fix is batching with DataLoader, which collects the ids requested within a tick and issues one WHERE id IN (…). It works well and it is not optional; chapter 12 covers the same problem in its ORM form.

HTTP caching stops working. One URL, POST bodies, and a response shape that varies per client means CDNs and browser caches have nothing to key on. You end up rebuilding caching inside the application, or adopting persisted queries so that each distinct query gets a stable identifier and can be sent as a cacheable GET.

A client can write an expensive query. Deep nesting, or a cyclic traversal, can ask for an enormous amount of work in a few lines. Public GraphQL endpoints need depth limits, complexity scoring and often an allow-list of known queries — which, notably, gives back much of the constraint REST had by default.

Errors are awkward. The specification returns 200 OK with an errors array, which is precisely the anti-pattern chapter 3 warned about, and it defeats status-code-based monitoring, retries and alerting. Every team ends up building conventions on top.

When GraphQL is the right answer

Many different clients with genuinely different data needs — a web app, two mobile apps, a partner integration — where building a bespoke endpoint for each screen would mean a permanent backlog of backend work. That is the case it was invented for, and in that case it is a clear win. A single web front end talking to a single backend rarely qualifies: you can just add the endpoint the screen needs, and you will spend less time on it than on schema stitching, DataLoaders and complexity limits.

gRPC and binary encodings

A different bet entirely: keep the interface rigid, describe it in a schema, generate the client and server from it, and make the wire format as small as possible.

protobuf — the .proto file generates both sides
syntax = "proto3";

service Orders {
  rpc GetOrder   (GetOrderRequest)  returns (Order);
  rpc ListOrders (ListRequest)      returns (stream Order);   // server streaming
  rpc Ingest     (stream Event)     returns (IngestSummary); // client streaming
  rpc Sync       (stream Change)    returns (stream Change);  // bidirectional
}

message Order {
  string id        = 1;    // the NUMBER is the wire identity, not the name.
  string user_id   = 2;    // rename freely; never reuse or change a number
  int64  total_cents = 3;
  repeated OrderItem items = 4;
  reserved 5, 6;         // fields that once existed. Reserving them stops
}                          // a future developer silently reusing the tag

The honest summary

These are not stages of an evolution and the newest is not the best. REST remains the right answer for most public APIs, because every tool, proxy, cache and developer already understands it. GraphQL solves a real organisational problem — backend teams becoming a bottleneck for front-end iteration — and is a poor trade if you do not have that problem. gRPC is excellent where both ends are yours and neither is a browser. The failure mode worth naming is choosing a style for its novelty and inheriting its operational burden without its benefit, which is how teams end up running a GraphQL gateway in front of one service for one client.

Self-check

  1. Distinguish over-fetching from under-fetching, and say which one latency punishes.
    Over-fetching is receiving fields the screen does not use — a bandwidth and serialisation cost, roughly linear in payload size. Under-fetching is needing several sequential requests because one resource references another — a latency cost, and it is multiplied by round-trip time. On a fast connection over-fetching dominates; on a slow one under-fetching does, because each extra round trip costs a fixed penalty that no amount of payload trimming touches.
  2. A GraphQL query is one HTTP request. Why can it still cause dozens of database queries?
    Because resolvers run per field and per item. Fetching a user, then their orders, then each order's items, then each item's product means the item and product resolvers fire once per parent row — the N+1 problem wearing different clothes. Batching with DataLoader collects the ids requested during one tick and issues a single WHERE id IN (…), turning the fan-out back into a handful of queries. It is standard practice rather than an optimisation.
  3. Why does adopting GraphQL usually mean giving up HTTP caching?
    Because caches key on the URL and method, and GraphQL uses one URL with POST bodies whose contents differ per client. A CDN has nothing to distinguish two requests by, and cannot safely reuse a response. Teams recover some of it with persisted queries — registering each query so it gets a stable identifier that can be sent as a GET — but the free layer of caching that REST gets from the protocol has to be rebuilt deliberately.
  4. Why is the field number in a protobuf message more important than the field name?
    Because the number is what goes on the wire. Names exist only in the schema and generated code, so renaming a field is a compatible change — old and new peers still agree on tag 3. Changing or reusing a number is not: a new field with an old tag will be decoded as the old one, silently producing wrong values rather than an error. This is why reserved exists, marking retired tags so nobody reuses them by accident.
  5. When is choosing gRPC over REST clearly right, and when is it clearly wrong?
    Clearly right for high-volume service-to-service calls inside your own network, where you control both ends, want generated clients and enforced contracts, and benefit from streaming and propagated deadlines. Clearly wrong at a public or browser-facing edge, where browsers cannot speak it without a proxy, partners cannot curl it, and your existing HTTP infrastructure understands nothing about it. Running gRPC internally and REST at the boundary is a common and sensible arrangement.
  6. A single web app talks to a single backend. Is GraphQL a good fit?
    Usually not. GraphQL's benefit is letting many dissimilar clients shape their own responses without backend work, which matters when the backend team is a bottleneck for several front ends. With one client you can simply add the endpoint that screen needs — cheaper than DataLoaders, complexity limits, persisted queries and the loss of HTTP caching. The question to ask is whether you have the organisational problem it solves, not whether the technology is appealing.
