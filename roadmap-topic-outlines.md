# Roadmap Notes — Topic Outlines

All 82 roadmaps from the uploaded roadmap.sh PDFs, each broken down as roadmap → topics → subtopics. They are ordered and grouped by the eleven lines of the Roadmap Notes catalogue.

**How to read each outline.** Each roadmap is listed as topics (bold), with their subtopics nested underneath. Where a roadmap groups subtopics under a heading, the heading is in *italics* and its items are nested one level deeper. Text set between dashes, like **— Backend starts here —**, is a section label printed on the roadmap itself rather than a topic. Lines starting _Note:_ are explanatory text from the roadmap, not topics.

**How it was produced.** Labels are taken verbatim from each PDF's text layer, including the roadmaps' own spellings such as "Ownsership" and "Cybsecurity". Hierarchy comes from the drawing: yellow boxes are topics, beige boxes are subtopics, white, grey or tinted boxes are group headings, and dotted connectors are traced box to box. 8 roadmaps were checked against rendered pages, and 2 were structured by hand from the PDF text. The rest are auto-extracted, and each one says which applies under its title. Six of the 88 PDFs were byte-identical duplicates and appear once.

### Vibe Coding

_Hand-structured from the PDF text (notes and tips placed by reading order)._

- **What is vibe coding?**
- **The vibe coder mindset**
- **AI Assisted Coding Tools**
  - Claude Code
  - Gemini
  - ChatGPT
  - Cursor
  - Windsurf
  - Replit
  - *Frontend-Focused*
    - v0
    - Lovable
- **Plan before you Code**
  - Plan what you need to develop (MVP, Different Phases)
  - Work step by step rather than trying to build everything at once
  - Illustrate AI with examples (mockups, code samples, images)
  - _Callout — AI Tools can Help with Planning: For example if you are using "Claude Code", tell the tool what you are trying to build, ask it to help refine the idea, establish the different phases, and once done ask it to document everything in a document so that you can refer to that when actually building the product._
- **Tech Stack and Coding**
  - Pick a popular tech stack rather than new/niche ones
  - If you have style/coding preferences, document them for AI
  - Ask AI to keep the code modular and aim for smaller modules/files
  - Regularly ask the AI to review and refactor the codebase
  - _Callout — Establishing Standards Early is Important: When you're starting out, carefully review the AI's initial outputs - coding patterns, styles, architecture decisions. If you don't catch bad habits early, the AI will reinforce them with every iteration, and they'll compound fast._
  - _Callout — Force refactoring sessions regularly: AI will take the path of least resistance (appending code, growing files, skipping cleanup). Periodically ask it to step back and refactor: break things into smaller modules, remove dead code, improve performance._
- **Prompting Best Practices**
  - Be specific about what you want, rather than high-level, vague instructions
  - Ask for one task at a time rather than five different items.
  - Based on your previous coding sessions, tell AI what NOT to do
  - Give AI mockups, reference files and material that can help it
  - Use "act as" framing when helpful (e.g. act as a UX researcher)
  - Use skills created by others
  - Regularly update your context document (e.g. CLAUDE.md)
  - Explicitly tell AI to "think" or "brainstorm" before complex problems
  - _Callout — Keep Context Document Up to Date: If you see yourself repeating some instructions, document the instructions in the context document. One more thing that helps is: after a discussion session if you feel like AI can benefit from learnings in the session, ask it to update the context document (e.g. claude.md) with the learnings from the session._
- **Context**
  - If AI fails after 3 prompts, stop, and start a fresh chat
  - Leverage long context window when available and necessary
  - For unrelated tasks, proactively clean and start new sessions
  - Ask AI to use subagents, if possible
  - _Callout — Clear Context Regularly: Clear context for better results and to save token costs. Whenever you are about to start a new/unrelated task, it's better to clear the context and start fresh._
- **Debugging**
  - If errors persist, Ask AI to create a list of possible causes
  - Prompt the error message and let AI do the rest
  - Tell AI to add logs to find the error faster
  - Install and ask AI to use MCP (e.g. Playwright for browser), when possible
  - _Callout — Let AI Debug, But Understand what Went Wrong: When something breaks, paste the error and relevant code and ask AI to explain the error. Don't just accept the fix — make sure you understand it. If you don't, ask AI to explain it in simple terms._
- **Master Version Control**
  - Start each new feature with a clean Git slate
  - Use `git commit` regularly (e.g. after every successful AI task)
  - If you need to revert, use Git rather than AI native revert functionality
  - Ask AI to handle your Git and GitHub CLI tasks
  - _Callout — Commit Often, With Clear Messages: After each working feature or fix, make a commit. Ask AI to suggest a clear commit message that describes what changed and why. This gives you a safe checkpoint to roll back to if something goes wrong later._
- **Testing**
  - Consider Test-driven development (TDD)
  - Ask AI to write tests (E2E tests can help build a stable product)
  - When you find a bug, ask AI to write a breaking test and then fix
  - Once tests are in place, refactor regularly
  - _Callout — Force AI To Test by Default: Most AI tools' default behavior produces implementation-first code with minimal test coverage. Whenever AI builds a feature, force it to write basic tests right away. This way bugs get caught early and you always know when something new breaks something old._
- **Security Best Practices**
  - Never hardcode secrets or credentials; use env variables instead
  - Explicitly ask AI to perform a security audit of the application
  - _Callout — Never Hardcode your Secrets: Never let the AI put passwords, API keys, or tokens directly in the code. If you see it doing this, stop it and ask it to use environment variables instead. This is one of the most common beginner mistakes and one of the most dangerous._
